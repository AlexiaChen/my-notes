# 《算法》（Sedgewick & Wayne）第1章 · 基础 —— 读书笔记

> **阅读提示**：这一章看似是"Java 入门 + 几个基础数据结构"的拼盘，实则整本书的方法论地基。我用**第一性原理**重新梳理：不从"这章讲了什么"出发，而从"要解决什么问题 → 什么是最朴素的解决方案 → 朴素方案为什么不够 → 如何从根本上改进"这条主线重构，并在每一节给出我自己的洞见。

## 一、本章总纲：整本书在 1.4 节就剧透了

在动笔之前，必须先点破一个**被绝大多数读者忽略的结构性事实**：Sedgewick 把整本书的"算法研发方法论"完整压缩在了 **1.4 节（算法分析）**​ 和 **1.5 节（union-find 案例）**​ 里。可以概括为一个五步循环：

1. **建模**（Model the problem）—— 把现实问题抽象成能计算的数学模型；
    
2. **找算法**（Find an algorithm）；
    
3. **评估**（Fast enough? Fits in memory?）；
    
4. **若不行，定位瓶颈**（Figure out why not）；
    
5. **迭代优化**，直到满意。
    

**洞见 ①**：第1章不是"基础知识汇编"，而是**全书算法思维的微缩演练**。后面的排序、查找、图论，本质上都是这套"建模 → 算法 → 分析 → 优化"循环的重复应用。读懂了这一层，第1章的价值立刻翻倍。

## 二、1.1 基础编程模型 —— 一切算法的"物理定律"

### 2.1 从第一性原理看"编程模型"

算法必须运行在某种语言之上。Sedgewick 选择 Java，并只抽取了最小子集：**原始数据类型（int/double/boolean/char）、语句、数组、静态方法、字符串、标准 I/O、API**。这不是偷工减料，而是刻意为之——**算法描述应当独立于语言细节**。

|核心要素|第一性原理视角|
|---|---|
|原始类型 + 表达式|算法操作的"原子"——可计算的值与运算|
|数组|连续、定长、O(1) 随机访问的存储原语|
|静态方法|函数的抽象——把"做什么"和"怎么做"分离|
|API|契约——调用者与实现者之间的**接口屏障**​|
|标准 I/O / 重定向 / 管道|让算法成为**可组合的数据流过滤器**​|

### 2.2 本节关键洞见

**洞见 ②：API 是"调用与实现分离"的第一性原理体现。**​ 一个设计良好的 API（如 `public static int rank(int key, int[] a)`）让客户端只依赖"能做什么"，而非"怎么做"。这是后面所有抽象数据类型（ADT）的雏形——1.1.7 的 API 概念，正是 1.2 数据抽象的先声。

**洞见 ③：数组的"别名陷阱"值得单独警惕。**​ 数组赋值是**引用拷贝**而非数据拷贝（`a = b` 后两者指向同一底层数组）。这个看似语言的细节，实则是后续链表、对象图操作的思维源头——**区分"值"与"指向值的引用"，是理解一切非平凡数据结构的前提。**

**洞见 ④：递归的三要素（基准情形 / 规模递减的子问题 / 子问题不重叠）**​ 不只在 1.1 是语法糖，它是分治、动态规划、图搜索等高级算法的思维基石，应在此刻就建立肌肉记忆。

### 2.3 二分查找（1.1.10）—— 用"减而治之"诠释递归与循环

二分查找要求数组**有序**，每次将搜索区间对半收缩，时间复杂度 O(log N)。它在本节的真正意义，是作为**"减而治之（decrease-and-conquer）"的第一个范例**——把一个大问题，确定性地缩减为一半规模的小问题。这个思想范式，将在后续二分查找树、分治排序中反复回响。

## 三、1.2 数据抽象 —— 用"类型"封装复杂度

### 3.1 第一性原理：为什么要抽象？

如果只有原始类型和数组，程序会变成一锅"数据 + 零散函数"的乱炖。**数据类型 = 一组值 + 这组值上的一组操作**；**抽象数据类型（ADT）= 把表示（representation）对客户端隐藏起来的数据类型**。

> 用一句话概括：**数据抽象让我们把"如何组织数据"和"能用数据做什么"解耦。**

### 3.2 本节关键洞见

**洞见 ⑤：ADT 是"封装"这一工程原则的算法层面表达。**​ 1.2.5 数据类型的设计，强调 API 先行、实现后填。这种"面向接口"的思想，使同一 ADT（如后面的 Stack）既能用数组实现、也能用链表实现，而客户端代码零修改。**这正是算法书中"可替换实现"的根本保障**——后面 1.3 节的栈/队列就是用同一套 API 演示两种实现的。

**洞见 ⑥：从"函数抽象"（1.1 静态方法）到"数据抽象"（1.2 ADT）是一次质的跃迁。**​ 函数抽象只隐藏"怎么做"，数据抽象连"数据长什么样"一起隐藏。理解这一跃迁，就理解了为什么现代算法实现几乎都以类/对象为载体。

## 四、1.3 背包、队列和栈 —— 三种"秩序"的选择

### 4.1 从问题出发：为什么需要三个几乎一样的 API？

背包（Bag）、队列（Queue）、栈（Stack）的 API 高度相似，差异仅在**移除/访问元素的秩序**：

|数据结构|秩序|核心操作|典型场景|
|---|---|---|---|
|**Bag**​|无序（仅收集 + 遍历）|`add()`|求平均值等统计计算，顺序无关|
|**Queue (FIFO)**​|先进先出|`enqueue / dequeue`|按到达顺序处理任务|
|**Stack (LIFO)**​|后进先出|`push / pop`|表达式求值、撤销、递归模拟|

**洞见 ⑦：三者的本质区别是"秩序策略"，而非"能力大小"。**​ 它们都能存、都能取；选哪一个，取决于**问题本身对元素处理顺序的约束**。这是"数据结构服务于问题建模"的第一个鲜活例子——选错秩序（如在需要 FIFO 的地方用 Stack），算法逻辑就会错。

### 4.2 数组 vs. 链表 —— 一次"表示方式"的权衡课

Sedgewick 用同一组 ADT，分别给出**数组实现**与**链表实现**，逼读者直面两种底层表示的取舍：

|维度|数组（顺序分配）|链表（链式分配）|
|---|---|---|
|访问|O(1) 索引直达|需沿引用遍历 O(N)|
|大小|固定（需扩容）|与元素数成正比，灵活|
|插入/删除|中间操作 O(N)|头部 O(1)|
|内存|可能预留浪费|每节点额外引用开销|

**洞见 ⑧：没有"更好"的表示，只有"更契合操作模式"的表示。**

- 栈的 `push/pop` 只在头部，链表 O(1) 完美匹配 → 链表实现栈极自然；
    
- 队列需头删尾插，链表维护 `first/last` 双指针即可 O(1)；
    
- 若需频繁按索引随机访问，数组更优；若大小剧烈变化，链表更省内存。
    

**洞见 ⑨：链表是一个"递归数据结构"——它要么是空（null），要么是一个"元素 + 指向下一个链表的引用"。**​ 这个递归定义不仅优雅，更是理解树、图等递归结构的起点。掌握了"在头部插入 / 从头部删除 / 遍历"这三个链表 idiom，后续复杂结构的实现就有了脚手架。

**洞见 ⑩（工程洞见）：可调整数组（resizing array）是数组与链表的折中。**​ 满时翻倍、四分之一空时减半，使 `push/pop/enqueue/dequeue` 均摊 O(1)。这告诉我们：**好的数据结构设计，常常不是二选一，而是在两种极端之间取一个"均摊最优"的平衡点。**

### 4.3 栈的经典应用：Dijkstra 双栈算法

用两个栈（操作数栈 + 运算符栈）即可在无语法树的情况下求值中缀表达式。这是栈"反转顺序 / 延迟处理"能力的经典体现——**栈天然适合需要"先记住、后回头处理"的场景**。

## 五、1.4 算法分析 —— 全章的方法论核心

### 5.1 科学方法：让"快不快"从直觉变成可证伪的命题

Sedgewick 强调用**科学方法**分析算法：实验必须可复现、假设必须可证伪。分析的总时间 ≈ **每条语句耗时 × 每条语句执行频率**；前者取决于硬件/编译器，后者取决于程序与输入。因此我们用**增长数量级（order of growth）**​ 忽略常数与低阶项，抓住随输入规模 N 增长的主导项。

### 5.2 增长数量级的"直觉标尺"

|数量级|名称|直觉|
|---|---|---|
|1|常数|与 N 无关|
|log N|对数|每次减半（二分）|
|N|线性|逐个处理|
|N log N|线性对数|分治排序|
|N²|平方|双重循环|
|N³|立方|三重循环|
|2ᴺ|指数|穷举子集|

**洞见 ⑪：增长数量级的意义不在于"精确预测秒数"，而在于"预测当 N 放大 10 倍时，运行时间大致放大多少倍"。**​ 例如 O(N³) 的 ThreeSum 三重循环，N 放大 10 倍，时间约放大 1000 倍——这解释了为什么"在小数据上跑得动"绝不等于"在大数据上能跑"。

### 5.3 数学建模 + 倍率实验：双剑合璧

- **数学模型**：推导操作次数与 N 的关系式（如二分查找比较次数 ≤ lg N + 1）；
    
- **倍率实验**：让 N 翻倍，观察运行时间 ratio，验证模型是否符合实际。
    

**洞见 ⑫：理论与实验必须互相校验。**​ 仅靠数学容易忽略常数因子和缓存效应；仅靠跑分无法外推到更大的 N。Sedgewick 的"建模 + 实验"双轨法，是工程实践中最稳健的算法评估方式。

### 5.4 内存分析：算法的"第二约束"

除时间外，1.4.9 专门讨论内存。每个对象都有"对象开销"（一般 16 字节）+ 字段 + 填充对齐；链表相对数组有额外的引用开销。**洞见 ⑬：在大数据场景，"能否装进内存"往往先于"跑得快不快"成为瓶颈**——这也是后面外部排序、流式算法存在的根本原因。

## 六、1.5 案例研究：union-find —— 全章思想的集大成者

这是第1章的**高潮**：用一个完整案例，把"建模 → 朴素算法 → 分析瓶颈 → 逐层优化"的方法论走通一遍。

### 6.1 问题建模：动态连通性

给定 N 个对象，支持两个操作：**连接两对象**、**判断两对象是否连通**。假设"连通"是等价关系（自反 / 对称 / 传递），问题即维护若干**连通分量（connected components）**。

应用极广：网络中的计算机、社交网络中的好友、芯片中的晶体管、Fortran 程序中的变量名等价性。

### 6.2 从第一性原理出发：四种实现的演进

所有实现都用**以站点为索引的数组 `id[]`**，差别在于对 `id[]` 的解释——这正是"同一数据、不同不变式"的演化。

#### （1）Quick-find（ eager 思路）

- **不变式**：`p` 与 `q` 连通 ⟺ `id[p] == id[q]`（同分量所有站点值相同）。
    
- `find` O(1)；`union` 需遍历全数组改值 O(N)。
    
- **总代价**：处理 N 对 union 可达 O(N²)。
    

#### （2）Quick-union（ lazy 思路）

- **不变式**：`id[i]` 是 `i` 的父节点，沿链接追溯至**根（root）**；`p`、`q` 连通 ⟺ 根相同。
    
- `union` 只需把一个根指向另一个根 O(1)（不含 find）；`find` 需沿树追溯 O(树深)。
    
- 最坏情况树退化成链，深度 O(N)，`find`/`union` 均 O(N)。
    

#### （3）加权 quick-union（smart union）

- **核心改进**：维护每棵树的大小，**始终把小树挂到大树上的根上**。
    
- **为什么有效（第一性原理）**：当节点 `x` 的深度增加 1 时，它所在树的大小至少**翻倍**（两棵树合并）。从 1 翻倍到 N，最多翻倍 log₂N 次 ⇒ **任意节点深度 ≤ log₂N**。
    
- 代价：`find/connected/union` 最坏 O(log N)。
    

#### （4）加权 quick-union + 路径压缩

- 在 `find` 过程中，把路径上所有节点**直接挂到根上**。
    
- 与按大小合并完全兼容；单次 `find` 代价略增，但未来访问这些节点代价骤降。
    
- 最坏情况降至 **O(α(N))**，其中 α 是**反 Ackermann 函数**——增长极慢，实际应用中可视为常数。
    

### 6.3 四种实现的代价对比（N 个对象、M 次操作，M ≥ N）

|算法|初始化|union|find|M 次操作总代价|
|---|---|---|---|---|
|Quick-find|N|N|1|MN|
|Quick-union|N|N|N|MN|
|加权 quick-union|N|log N|log N|N + M log N|
|加权 + 路径压缩|N|α(N)|α(N)|N + M α(N)|

> 直观感受：对 10⁹ 个元素执行 10⁹ 次 union-find，**加权 quick-union 把运行时间从约 30 年缩短到约 6 秒**——超级计算机帮不上忙，是**好算法本身让问题可解**。

### 6.4 本节关键洞见

**洞见 ⑭：union-find 是"建模 + 迭代优化"方法论的完美示范。**​ 同一问题、同一数据结构（`id[]`），仅通过**改变不变式与合并策略**，就把不可用的 O(N²) 优化到近乎常数。这印证了 1.4 的核心主张——**先建模、再分析、定位瓶颈、再优化**。

**洞见 ⑮：quick-find 与 quick-union 是两种极端的权衡。**​ 前者"查找快、合并慢"（eager），后者"合并快、查找可能慢"（lazy）。**加权 + 路径压缩的本质，是把两种极端各自的优点结合起来**——这正是算法设计中"权衡（trade-off）"思维的典范。

**洞见 ⑯：路径压缩体现了"用一点当前工作的代价，换取未来多次访问的加速"的 amortized 思想。**​ 这与缓存、splay tree 的"顺势调整"哲学一脉相承——**让频繁访问的节点靠近根，是"局部性原理"在并查集中的体现**。

**洞见 ⑰（跨章预告）：union-find 将在第4章（图）中大放异彩。**​ Kruskal 最小生成树算法正是用并查集来判断"加入一条边是否会形成环"。**学完 1.5 不要孤立地放下它——它是后续图算法的关键子例程。**
