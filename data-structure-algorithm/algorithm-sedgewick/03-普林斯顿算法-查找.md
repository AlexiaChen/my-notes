# 《算法》（Sedgewick & Wayne）第3章 · 查找 —— 读书笔记

> **开篇锚点（第一性原理）**：查找问题的本质是 **"给定一个键，如何最快地定位到它（及关联的值）"**。一切查找结构的演进，都是在回答同一个问题——**"如何把'键→位置'的映射信息，组织得越来越有利于快速定位"**。从"遍历全部"（无序链表），到"利用顺序+二分"（有序数组），到"让键自己长成一棵可导航的树"（BST/红黑树），再到"用算术直接计算位置"（散列表）——每一步，都是**用某种'额外的结构/约束'去换取'更少的比较次数'**。理解这条主线，本章就是一部"查找效率进化史"。

---

## 一、3.1 符号表 —— 一切查找的"契约"

### 1.1 API：把"键值关联"抽象成统一契约（3.1.1–3.1.2）

符号表（Symbol Table）是存储**键值对（Key-Value Pair）**的抽象数据结构，核心操作只有几个：`put(key, val)`、`get(key)`、`delete(key)`、`contains(key)`、`size()`、`keys()`。有序符号表额外支持 `min/max`、`floor/ceiling`、`rank/select`、`deleteMin/deleteMax`、范围查找——这些"有序性操作"正是**有序实现**区别于**无序实现**的价值所在。

**洞见 ①：符号表 API 是"关联数组"抽象。**​ 字典（单词→释义）、图书索引（术语→页码）、账户系统（账号→交易详情）、编译器符号表（变量名→类型/值）、网络搜索（关键词→网页）——看似风马牛不相及的应用，底层都是同一套 `get/put` 契约。**学会把具体问题"归约"为符号表操作，是工程抽象能力的核心训练。**

**洞见 ②：API 里藏着一个关键设计抉择——"是否要求键有序"。**​ 不要求有序（仅 `equals` 语义）→ 可实现为 O(1) 期望的散列表；要求有序（需 `Comparable`/`compareTo` 语义）→ 只能依赖比较树结构，代价是对数级别。这个抉择会在 3.5.1 的选型表中最终兑现。

### 1.2 无序链表中的顺序查找（3.1.4）—— 基线，也是天花板

`get` 沿链表逐个用 `equals()` 比较；`put` 先查找，命中则更新值，未命中则在表头插入新结点（O(1) 插入）。**命题 A：N 次插入到空链表共需 ~N²/2 次比较；查找未命中/插入均摊 N 次比较。**

**洞见 ③：链表法是"零结构开销"的基线——它不要求键可比较，只要求 `equals`，且仅用 N 个结点指针。**​ 这决定了它的定位：**适用于"小型问题"或"键类型无法比较、只能相等判断"的场景**。同时它也是散列表"拉链法"的子结构（每个桶就是一条 SequentialSearchST 链表）——**看似最朴素的算法，反而是更复杂算法（散列）的零部件。**

### 1.3 有序数组中的二分查找（3.1.5–3.1.6）—— 用"顺序"换"对数查找"

用**两个平行数组**分别按序存放键和值，核心是 `rank(key)`：返回"小于 key 的键的数量"，即 key 在表中的正确位置。查找：`rank` 定位，命中则返回值；插入：`rank` 定位后把较大键整体后移一位腾出空位。

|操作|查找|插入|
|---|---|---|
|无序链表|N（最坏/平均）|N|
|有序数组（二分）|**lg N**​|**N**（要搬移元素）|

**洞见 ④：二分查找是"以插入变慢为代价，把查找从线性压到对数"的经典权衡。**​ 它"最优查找效率 + 最优空间"，但"插入很慢"。**适用判据：当你的工作负载是"一次构建、海量查找、极少插入"时（如静态字典、只读配置表），BinarySearchST 是最干净、最省内存的选择。**​ 这也是本章反复出现的主旋律——**没有全局最优，只有匹配负载特征的最优。**

**洞见 ⑤（分析视角）：二分查找每次把搜索区间对半收缩，比较次数 ≤ lg N + 1。**​ 它与第1章 union-find 的"减而治之"、第2章归并/快排的"分治"共享同一思维内核——**每次操作成倍削减"剩余不确定性"**，这正是从 O(N) 跃迁到 O(log N) 的根本机制。

## 二、3.2 二叉查找树（BST）—— 让数据"自己长出导航结构"

### 2.1 基本实现（3.2.1）：一棵"左小右大"的递归结构

BST 是二叉树，每个结点含一个键、一个值、左右子链接，且满足**二叉查找树性质**：任意结点，其左子树所有键 < 该结点键 < 右子树所有键。**洞见 ⑥：BST 的精妙在于——它把"有序性"编码进了树的结构本身。**​ 查找沿一条路径下行（比当前小走左、大走右）；插入 = 查找未命中时在该位置挂上新结点。

### 2.2 分析（3.2.2）：形状决定一切

BST 的性能完全取决于**树的形状**，而形状又取决于**键的插入顺序**。

- **最好**：树完全平衡，查找路径长度 ~lg N；
    
- **最坏**：键按序插入，树退化为链表，查找/插入最坏 O(N)；
    
- **平均（随机键）**：查找命中/插入/查找未命中平均比较次数约 **2 ln N ≈ 1.39 lg N**​ 。
    

**洞见 ⑦：BST 平均性能极好（仅 1.39 lg N，常数比归并/快排还小），但"最坏"毫无保证。**​ 这是它与"有序数组二分"的根本分野——二分查找有最坏 lg N 保证，但插入慢；BST 插入快（平均），却可能被恶意/特定顺序的输入打垮。**这个"好平均、坏最坏"的短板，正是 3.3 节"平衡查找树"要解决的问题——给 BST 加上"不会退化"的保证。**

### 2.3 有序性相关方法与删除（3.2.3）

BST 的价值很大程度在"有序性操作"：`min/max`（一路向左/右）、`floor/ceiling`、`select(k)`（找排名为 k 的键）、`rank(key)`（key 的排名）、范围查找。**洞见 ⑧：`select` 与 `rank` 是互逆操作，它们的实现依赖在每个结点额外维护"子树大小 size(x)"。**​ 这个"在结点中缓存子树规模"的技巧，是后来线段树、Treap、Order Statistic Tree 等高级结构的共同祖先——**用 O(1) 额外存储换 O(log N) 的排名查询能力。**

删除是 BST 最棘手的操作，分三种情况（Hibbard 删除法，1962）：

- 无子结点：直接删除；
    
- 单子结点：用其唯一子结点替代；
    
- **双子结点**：用其**后继（右子树的最小键结点）**替代，再递归删除原后继。
    

**洞见 ⑨：Hibbard 删除有一个"不完美"的缺陷——它不对称（总是用后继而非前驱），长期随机删除后树会趋向轻微右重，影响平衡。**​ Sedgewick 明确指出这一点，正是为引出 3.3 的红黑树删除（用"叶子结点借用/合并"保持平衡）。**理解 Hibbard 的不完美，才能体会"平衡树删除"为何必须另起炉灶。**

## 三、3.3 平衡查找树 —— 给 BST 装上"不退化"的保险

### 3.1 2-3 查找树（3.3.1）：允许"一个结点存两个键"

2-3 树是**绝对平衡**的多路查找树：结点可以是 2-结点（1 个键、2 个子链接）或 3-结点（2 个键、3 个子链接），且**任意空链接到根的距离相同**（完美平衡）。插入时，先在底部找到位置，若遇 3-结点则"分裂"——中间键上移给父结点，左右键各成 2-结点；上移可能递归传播到根。

**洞见 ⑩：2-3 树"绝对平衡"的代价是——结点类型不统一（2-/3-结点）、分裂逻辑分支繁多，直接实现既繁琐又易错。**​ 这引出一个极优美的工程思想：**能不能用"统一的二叉结构"来等价表示 2-3 树？**​ 答案就是红黑树。

### 3.2 红黑二叉查找树（3.3.2–3.3.3）：用"红色链接"粘合 3-结点

红黑树 = 标准 BST + 结点颜色位（红/黑，表示该结点被父结点**指向它的那条链接**的颜色）。**核心编码规则（左倾红黑树 LLRB）**：

1. **红链接均为左链接**（3-结点表示为"两个 2-结点 + 一条左倾红链接"）；
    
2. **没有任何结点同时连着两条红链接**；
    
3. **树是完美黑色平衡的**（任意空链接到根的黑链接数相同）。
    

由这三条 ⇄ 与 2-3 树**一一对应**。实现只需在普通 BST 插入后，用三个基本操作恢复平衡：

|操作|触发条件|作用|
|---|---|---|
|**左旋转 rotateLeft**​|出现右倾红链接|转为左倾|
|**右旋转 rotateRight**​|出现连续两条左红链接|把红链接右倾以便颜色翻转|
|**颜色翻转 flipColors**​|一个黑父有两个红子（临时 4-结点）|拆分 4-结点，中间键上移（红）|

插入逻辑（Sedgewick 经典几行）：

```
private Node put(Node h, Key key, Value val) {
    if (h == null) return new Node(key, val, RED);
    int cmp = key.compareTo(h.key);
    if      (cmp < 0) h.left  = put(h.left,  key, val);
    else if (cmp > 0) h.right = put(h.right, key, val);
    else               h.val   = val;
    if (isRed(h.right) && !isRed(h.left))      h = rotateLeft(h);
    if (isRed(h.left)  &&  isRed(h.left.left)) h = rotateRight(h);
    if (isRed(h.left)  &&  isRed(h.right))     flipColors(h);
    return h;
}
```

**洞见 ⑪（全书最精彩的"表示即实现"范例）：红黑树告诉我们——同一个抽象数据结构（2-3 树），换一种底层表示（红黑链接编码），就能把"繁琐的多类型分裂"变成"统一的二叉旋转+变色"。**​ 这是"封装/表示"思想的高阶应用：**好的表示，能让复杂算法变得出奇简洁。**​ 这也是 Sedgewick 本人（与 Guibas）1978 年对红黑树的核心贡献。

### 3.3 红黑树的性质与删除（3.3.4–3.3.5）

**命题（性质）**：含 N 个结点的红黑树，**高度 ≤ 2 lg N**（最坏）；典型应用中平均路径长度 ~1.00 lg N。因此查找、插入、删除、min/max、floor/ceiling、rank、select、范围查找**最坏均为 O(log N)**。

**证明要点**：由"无连续红边"⇒ 最长路径 ≤ 2×黑高；由"黑高恒定"⇒ N ≥ 2^(bh)−1 ⇒ bh ≤ lg(N+1)；故 h ≤ 2 lg(N+1) = O(log N)。**洞见 ⑫：红黑树的五条性质里，第④条（红不连续）限"红节点密度"，第⑤条（黑高恒定）保"局部平衡"）——双重约束共同把树高压死在对数级别。**​ 这正是"用局部不变式换取全局最坏保证"的典范。

**删除（3.3.4）**：远比插入复杂。核心思想是**"自底向上"维护 2-3-4 树的删除不变式**——沿查找路径下行时，若当前结点的子结点是 2-结点，则通过"向兄弟借一个键"或"与兄弟合并"将其变为 3-/4-结点，确保删除底部时总有冗余键可移除；删除后再自底向上用旋转/变色恢复红黑性质。**洞见 ⑬：Sedgewick 讲删除时特意提到一个"战争故事"（war story）——某电话公司数据库用红黑树+Hibbard 删除，因 Hibbard 不对称导致树长高、超出 80 层高度限制而触发大范围服务中断、惹上官司。**​ 这给我们两点警示：① 生产环境务必用**平衡删除**（LLRB 的删除实现），而非 Hibbard；② "最坏情况"不是学术噪音——它会在真实系统里炸。

## 四、3.4 散列表 —— 用算术"直接计算"位置，放弃有序性

### 4.1 第一性原理：散列表是"时间—空间权衡"的教科书

Sedgewick 的导语一针见血：若内存无限，可直接用"键"作超大数组索引，查找 O(1)；若无时间限制，可用无序数组+顺序查找，内存极少。**散列表正是在这两个极端之间取平衡——用"适度空间+算术映射"换取"期望 O(1) 的查找/插入"。**​ 它分两步：① 散列函数把键映射到数组索引；② 处理碰撞冲突。

### 4.2 散列函数（3.4.1）：均匀 + 高效 + 与键无关

对整数键常用"除留余数法"（取素数 M，`hash = (key.hashCode() & 0x7fffffff) % M`，掩码保证非负）。**洞见 ⑭：好的散列函数的理想是——对任意键，0~M−1 每个索引被命中的概率相等且与键无关。**​ 这看似简单，实则深刻：它把"键的任意分布"规整为"索引的均匀分布"，是散列表性能的地基。**若散列函数偏斜（如所有键落入同一桶），再好的冲突处理也救不回 O(N) 的退化。**

### 4.3 基于拉链法的散列表（3.4.2）

每个数组元素指向一条链表（即 SequentialSearchST），冲突的键值对挂在同一条链上。`get`：先 `hash` 定位桶，再在链表中 `equals` 查找；`put`：定位桶后插入/更新。**平均查找长度 ≈ 1 + α/2（命中）、α（未命中），α = N/M 为负载因子。**

### 4.4 基于线性探测法的散列表（3.4.3）

开放地址法：用数组直接存键值对（M > N），冲突时索引递增探测（`i = (i+1) % M`）直到遇空位/命中。**插入平均探测 ≈ ½(1 + 1/(1−α)²)（未命中），命中 ≈ ½(1 + 1/(1−α))**（Knuth 经典分析）。**洞见 ⑮（关键工程结论）：线性探测对负载因子 α 极其敏感——α→1 时探测次数急剧发散（α=0.9 时命中约 5.5 次、未命中约 50 次；α=0.95 时超 200 次）。因此开放地址法通常要求 α ≤ 0.7（Java HashMap 默认 0.75 是"时间/空间折中"的经验最优）。**​ 相比之下，拉链法对 α 宽容得多（即使 α>1 也不会急剧恶化）。

**洞见 ⑯：两种冲突处理各有取舍。**​ 拉链法——实现简单、对 α 不敏感、支持 α>1，但每条结点多一个指针开销、缓存局部性较差；线性探测——数据连续存储、缓存友好、空间紧凑，但 α 高时主聚集（primary clustering）严重、删除需"重新插入被删键右侧的簇"。**现代引擎（Redis/Python dict/UE5）明知开放寻址更复杂仍选用它，正是因为 α≤0.75 时"平均探测≈2.0"+连续内存让缓存直接起飞。**

### 4.5 调整数组大小与内存使用（3.4.4–3.4.5）

为维持性能，散列表需**动态扩容**：当 N/M 超过阈值（拉链法可到 ~1，线性探测 ≤0.5 时扩容翻倍）。扩容 = 新建更大数组 + 把所有键值对重新 `put` 进新表（rehash）。**洞见 ⑰：动态调整让散列表"既省内存（小表）又保性能（满则扩容）"，是"自适应"思想的体现。**​ 内存方面，拉链法每条结点额外一个 `next` 引用（64 位系统 8 字节）；线性探测无指针开销但需预留空槽——**这正是"用空间换时间、再用动态策略回收空间"的闭环。**

**洞见 ⑱（散列表的根本取舍）：为换取 O(1) 期望性能，散列表主动放弃了"有序性相关操作"（floor/ceiling/rank/范围查找都无法高效支持）。**​ 这再次印证全章主旋律——**算法选型本质是"你想要什么、愿意放弃什么"的权衡。**

## 五、3.5 应用 —— 把"查找"用到真实问题上

### 5.1 我应该使用符号表的哪种实现（3.5.1）

综合全书实现的成本总结（N 次插入后）：

|数据结构|查找（最坏）|插入（最坏）|查找（平均）|有序性操作|关键特征|
|---|---|---|---|---|---|
|SequentialSearchST（无序链表）|N|N|N/2|否|小型问题、仅 equals|
|BinarySearchST（有序数组）|lg N|N|lg N / N/2|是|最优查找+空间，插入慢|
|BST|N|N|1.39 lg N|是|平均快，最坏无保证|
|RedBlackBST（2-3 树）|2 lg N|2 lg N|~1.00 lg N|是|查找插入均对数最坏保证|
|SeparateChainingHashST|N|N|1+α/2|否|快速查找插入，需散列|

**洞见 ⑲（选型第一性原理）**：按顺序问三个问题即可定方案——① **需要有序性操作吗？**​ 需要→RedBlackBST；不需要→散列表。② **键能比较吗？**​ 不能→只能散列表/链表。③ **负载特征？**​ 一次构建海量查找→BinarySearchST（最省内存）；动态高频插入+查找→HashMap（O(1) 期望）。**把约束列清楚，实现自己会"跳出来"——这正是符号表抽象的价值。**

### 5.2–5.5 集合 API / 字典 / 索引 / 稀疏向量

- **集合 Set API**（3.5.2）：符号表值类型设为 `null`，仅关心"键是否存在"→ 字典/索引的底层。
    
- **字典类用例**（3.5.3）：单词→释义、变量名→类型值，是符号表最经典的应用。
    
- **索引类用例**（3.5.4）：术语→一串页码（值类型为 `Queue<Integer>`），展示"一对多"关联。
    
- **稀疏向量**（3.5.5）：用符号表表示"绝大多数分量为 0"的向量（仅存非零项 索引→值），点积等运算从 O(N) 降到 O(非零项数)。**洞见 ⑳：稀疏向量是"用符号表规避无效计算"的范例——它把"数据结构选择"直接转化为"算法复杂度的数量级下降"，是全书"好结构造就好算法"主题的又一次回响。**

## 六、全章脉络图（章节间的"第一性原理"联系）

```
3.1 符号表 (键值关联的抽象契约 + API)
   │  • 无序链表 SequentialSearchST: O(N) 基线, 也是散列"拉链"的子结构
   │  • 有序数组 BinarySearchST: 二分 → lg N 查找, 但插入 O(N)
   │  • 洞察: "有序性"换"对数查找", 但以"插入变慢"为代价
   ▼
3.2 二叉查找树 BST
   │  • 让数据自组织成"左小右大"的递归结构 → 平均 1.39 lg N
   │  • 但形状依赖插入顺序, 最坏退化为链表 O(N) ← 短板
   ▼
3.3 平衡查找树 (2-3 树 → 红黑树 LLRB)
   │  • 2-3 树: 允许 3-结点 + 绝对平衡, 但实现繁琐
   │  • 红黑树: 用"左倾红链接"编码 3-结点 ↔ 与 2-3 树一一对应
   │  • 旋转+变色 → 最坏 O(log N) 保证 (高度≤2lgN)
   │  • 洞察: "好的表示让复杂算法变简洁"
   ▼
3.4 散列表 (拉链法 / 线性探测)
   │  • 用算术直接计算位置, 放弃有序性 → 期望 O(1)
   │  • 散列函数须均匀; 冲突处理: 拉链(对α宽容) vs 线性探测(缓存友好,α≤0.7)
   │  • 动态调整扩容维持性能
   ▼
3.5 应用: 选型 + 字典/索引/稀疏向量
      • 选型三问: 要有序? 键可比较? 负载特征? → 实现自现
      • 稀疏向量: 好结构把复杂度从 O(N) 降到 O(非零项数)
```

**一句话总结全章**：第3章是一部 **"查找效率的进化史"**——从遍历全部（O(N)），到利用顺序+二分（O(log N) 查找但插入慢），到让数据自组织成可导航的树（BST 平均快、最坏无保证 → 红黑树补齐最坏保证），再到用算术直接计算位置（散列表期望 O(1)，放弃有序性）。每一步进化的本质，都是**用某种"额外结构/约束"换取"更少的比较次数"，并在"时间—空间—有序性"三者间做出明确权衡**。掌握这条主线，你就拥有了"面对任何查找需求都能理性选型"的能力。
