

## 1.1 引言

### 1.1.1 性能方面

书中开宗明义：算法值得学，是因为它们**快、通用，或两者兼具**。作者 Aditya Bhargava 在 Manning 第2版预览里明确把"算法实践者思维"作为全书基调——描述算法、走查例子、分析运行时间、映射到相似问题，并在数据结构与排序策略之间做权衡。

**我的洞见**：很多人学算法是从"怎么写"入手，但 Bhargava 的切入点其实是"怎么比"。第一性原理是——**任何算法的价值都不能脱离输入规模来谈**。一个在 100 条数据上跑得挺快的写法，到了 10 亿条数据可能直接让服务崩溃。所以"性能"在这一章不是 benchmark 上的数字，而是**增长曲线本身的形状**。

### 1.1.2 问题解决技巧

书中用电话簿查公司、字典查单词、Facebook 登录校验用户名等例子引出"搜索问题"的共性。

**洞见**：这些例子的共同结构是——**目标元素藏在某个有序集合中，我们需要用最少的"提问次数"定位它**。这里的第一性原理是"**信息论视角下的搜索**"：每次比较都应该最大化地削减不确定性。简单查找每次只排除 1 个元素，而二分查找每次排除一半——这就是**信息增益**的差异。工业上这种思维不只用于查数据，也用于调试（二分定位 bug 引入的版本）、A/B 测试（二分找最优参数）、甚至监控告警（二分定位故障时间点）。

## 1.2 二分查找

### 1.2.1 更佳的查找方式

书中核心例子："猜 1 到 100 之间的数字"。从 1 开始一个个猜（简单查找）最坏要 99 次；猜 50，根据"高了/低了"每次排除一半，最多 7 次就能锁定。

**关键约束（书中强调）**：二分查找要求输入是**已排序的列表**。只有有序，中间元素的"大了/小了"才能告诉我们目标在哪一半。

**我的洞见（第一性原理）**：

二分查找的本质不是"对半砍"，而是**把搜索空间以乘法方式收缩**：

- 第 1 次比较后：剩余 ≤ n/2
    
- 第 2 次比较后：剩余 ≤ n/4
    
- 第 k 次比较后：剩余 ≤ n/2^k
    

当 n/2^k ≤ 1 时停止，解得 **k ≥ log₂n**。所以严格的最坏比较次数是 `1 + ⌊log₂n⌋`。

📌 **工业映射**：这个"有序 + 二分"的模式在现代数据管道里无处不在。一个典型场景是**时间戳日志检索**——服务端日志（Nginx、Syslog、Java stdout）天然按时间单调递增，因此可以用二分查找做时间范围查询，把传统 O(n) 的全文扫描降到 O(log k)，k 是可索引的时间切片数。开源工具 logbinsearch 就是这么做的：先建块索引记录每个压缩块的起止时间戳，再二分定位故障窗口，TB 级压缩日志也能做到亚秒级响应。

另一个更深刻的工业视角来自 _TheLinuxCode_ 的一篇生产复盘：作者在支付 API 上用二分查找判断 transaction ID 是否重复。团队问："有没有比二分更快的？"答案是——**在"比较模型 + 有序数据"这个设定下，二分查找的对数复杂度 O(log n) 就是理论天花板**。但在生产里你可以换维度取胜：哈希表平均 O(1) 的点查更快；B 树减少磁盘随机 I/O 更适合磁盘数据；trie 树适合前缀匹配。所以**二分查找是基线，不是终点**。

### 1.2.2 运行时间

书中给出震撼对比：

- 100 个元素：简单查找 100 步，二分查找 7 步
    
- 40 亿个元素：简单查找 40 亿步，二分查找 32 步
    

**洞见**：注意"双倍数数据量，只多 1 步"这个反直觉事实。如果 n=1,000,000,000，log₂n ≈ 30。这意味着**百亿数据翻一倍，二分查找只多一次比较**。这是对数复杂度的核心魔力——它几乎像常数时间一样"抗规模"。

## 1.3 大 O 表示法

### 1.3.1 算法的运行时间以不同的速度增加

书中明确：**算法速度不是用秒衡量的，而是用"随着输入增长，操作数如何增长"来衡量**，并用"折纸"类比——O(log n) 折几下就到头，O(n) 线性增长，O(n²) 则是二次爆炸。

**洞见（第一性原理）**：大 O 的本质是**忽略常数因子，只看增长曲线的阶**。为什么可以忽略常数？因为硬件、语言、实现细节带来的常数差异，在 n 足够大时都会被高阶项碾压。Dartmouth 的讲义讲得很透：大 O 读作"order"，表达的是"运行时间**增长得像**什么"——线性查找增长得像 n，二分查找增长得像 log₂n，而 log₂ 与 log₁₀ 只差一个常数系数，所以 O(log₂n) = O(log n)。

### 1.3.2 理解不同的大O运行时间

书中给出常见复杂度阶梯（从快到慢）：

- **O(1)**​ 常数时间
    
- **O(log n)**​ 对数时间（二分查找）
    
- **O(n)**​ 线性时间（简单查找）
    
- **O(n log n)**​ 线性对数时间（多数高效排序）
    
- **O(n²)**​ 二次时间（简单排序如选择/冒泡）
    
- **O(n!)**​ 阶乘时间（旅行商暴力解）
    

**我的洞见**：这个阶梯的真正含义是**"每次操作削减不确定性的比例"**。

- O(1)：零不确定性，直接命中
    
- O(log n)：每次砍掉固定比例（一半）
    
- O(n)：每次只推进常数步
    
- O(n²)：嵌套循环，内外层都随 n 增长
    
- O(n!)：每个决策都开启 n 个新分支
    

工业上选算法就是选这条曲线。比如在数据库里，OLTP 点查走哈希索引 O(1)，范围查询走 B+ 树 O(log n)；而在 AI 推理里，attention 计算是 O(n²)（n 是序列长度），这就是为什么长上下文那么烧显存——Transformer 的 quadratic bottleneck 是行业痛点，也是 Mamba、Linear Attention 等新架构想突破的核心。

### 1.3.3 大O表示法指出了最糟情况下的运行时间

书中强调：大 O 关注的是**最坏情况的上界**。

**重要纠偏**（CMU 讲义讲得更严谨）：二分查找在最好情况下第一步就命中，是 O(1)；但**最坏情况是 Θ(log₂n)**。大 O 是渐进上界，所以"二分查找是 O(log₂n)"在所有情况下都成立；但"二分查找是 Θ(log₂n)"只在最坏情况成立。**实际工程中我们报 O(log n) 是最稳妥的上界承诺**——它告诉调用方："无论什么输入，我都不会比你想象的更慢"。

这种"最坏情况保证"在工业系统里至关重要：SLA 承诺、超时熔断、资源预算都依赖最坏情况而非平均情况。一个平均很快但偶尔爆掉的算法，比一个稳定 O(log n) 的算法更危险。

书中列举并配图对比了 O(log n)、O(n)、O(n log n)、O(n²)、O(n!) 的增长曲线。

**洞见**：看这些曲线时不要只看"快慢"，要看**"规模临界点"**——即在这个规模之后，高阶算法开始反超低阶算法。对于二分 vs 简单查找，临界点在 n=2 左右就开始显现；对于 O(n log n) 排序 vs O(n²) 排序，临界点大约在 n=10~20。这就是为什么小数组上插入排序反而比快排快——常数因子在低阶交叉区占主导。工业级排序算法（如 TimSort，Python 和 Java 的默认排序）就是利用了这一点：**小片段用插入排序，大片段用归并/快排**，把两者的优势拼接起来。

### 1.3.5 旅行商

书中用旅行商问题（TSP）展示 O(n!) 的可怕：n 个城市的所有路线排列是 n! 条，12 个城市就是 4.79 亿条路线。

**洞见（第一性原理）**：TSP 属于 **NP-hard**​ 问题——没有已知多项式时间算法，且所有 NP 问题都能归约到它。这里的深刻教训是：**不是所有问题都配得到"最优解"**。当问题是指数级难度时，工程师必须转向：

- **近似算法**：接受一个 (1+ε) 倍近似比的解
    
- **启发式算法**：遗传算法、模拟退火、蚁群优化
    
- **实际问题简化**：现实中的路径规划（如快递配送、网约车派单）往往有约束（时间窗、容量、实时路况），这些约束反而让问题在某些假设下可被近似求解
    

📌 **工业映射**：美团/饿了么的骑手调度、滴滴的订单分配、亚马逊的仓储拣货路径，本质上都是 TSP 或其变体（VRP，车辆路径问题）。它们用的不是暴力枚举，而是**分层策略**——先用聚类把城市/订单分组（每组的规模可控），组内用精确或近似算法，组间用元启发式。这种"分而治之 + 近似"的工程哲学，恰好呼应了本书后续章节的递归与分治思想。

## 1.4 小结

书中本章小结给出 5 条核心要点：

1. 二分查找比简单查找快得多，尤其数据量越大优势越夸张
    
2. O(log n) 比 O(n) 快，且随列表增大优势急剧扩大
    
3. 算法速度不以秒计，而以**增长速率**计
    
4. 算法时间用大 O 表示法书写
    
5. 大 O 表示最糟情形下的运行时间
    

**我的整体洞见**：

第1章真正教给你的，是一种**新的直觉衡量标准**——面对任何问题时，先问自己："**当输入规模放大 10 倍、100 倍、10000 倍时，我的解法会怎样？**" 这个问题的答案决定了你的系统是能平滑scale还是会在某个临界点雪崩。

二分查找是这个思维的第一个载体，但它背后的第一性原理更具普适性：**任何能通过"每次以固定比例削减搜索/解空间"的问题，都能达到对数级复杂度**。这不仅仅是"查数组"——二分答案（binary search the answer）是一种通用技巧：当你可以对"答案"本身做有效性判断时，就可以在答案空间上二分。工业上的经典用例包括：

- **在有序数组中找第一个满足条件的元素**（lower_bound）
    
- **求最大最小值问题的二分答案法**（如"使最大负载最小的分割方案"）
    
- **浮点数值的精确求解**（如方程求根、机器学习里的超参搜索）
    
- **高性能硬件层面的优化**：现代二分查找在工程上还有 branchless 写法、Eytzinger 缓存友好布局、SIMD 并行扫描等演进——ClickHouse、Apache Arrow、Rust 标准库都用了这些技巧，在十亿级数组上能做到 1.5~2× 加速。
    

> 💡 一句话带走第1章：**不要问"这个算法现在跑多快"，要问"当世界变大 100 万倍，它还能跑吗"**。这个问题，会在你读完全书每一章时反复回响。
