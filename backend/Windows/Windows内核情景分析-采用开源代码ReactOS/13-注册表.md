
第13章是整本书从"运行机制"走向"运行配置"的关键一跃。前面你学了系统调用、对象管理、设备驱动、文件系统、安全模型——所有这些机制都需要一个**持久的、结构化的配置数据库**来记录"系统有哪些驱动要加载、每个驱动的服务类型是什么、用户环境怎么初始化、安全策略如何设定"。注册表（Registry）就是 Windows 的答案：一个**内核态的分层配置数据库**，以"键-值"对的形式组织，存储在称为 HIVE 的二进制文件中。

我的核心洞见先抛在面前：**注册表的第一性原理是"把系统配置从分散的文本文件收敛为统一的内核可寻址数据库"**。相比 Linux 把配置分散在 `/etc/` 下的无数文本文件，Windows 选择把配置集中到几个 HIVE 文件中，由内核的配置管理器（Configuration Manager，CM）统一管理。这样做的好处是：配置访问走内核 API（Zw/NT 系列），受对象管理器和安全模型保护（每个键都是安全对象，有自己的 DACL）；坏处是：注册表损坏 = 系统无法启动（这就是为什么 Windows 有"最后一次正确的配置"和注册表 hive 备份机制）。

> 💡 读这一章的正确姿势：把注册表想象成**内核的"配置内存"**——HIVE 文件是它在磁盘上的持久化形态，CM 是管理它的"内存分配器+索引器"，`RtlQueryRegistryValues` 等 RTL 函数是驱动程序访问它的"便捷包装"。理解这三层（HIVE 文件格式 → CM 内存管理 → RTL 查询 API），你就理解了 Windows 配置的心脏。

## 13.1 注册表操作

**书的脉络**：注册表操作通过 `ZwCreateKey`/`ZwOpenKey`/`ZwQueryValueKey`/`ZwSetValueKey` 等内核 API 进行。用户态通过 `RegCreateKeyEx`/`RegOpenKeyEx`/`RegQueryValueEx` 等 ADVAPI32 函数，最终调用到 NTDLL 的 `Nt*` 系列，陷入内核后由配置管理器（CM）处理。注册表键是安全对象，访问时执行第12章讲过的 `SeAccessCheck`。

**注册表的逻辑结构**：

```
注册表五大预定义键（HKEY）：
├── HKEY_LOCAL_MACHINE (HKLM)     # 系统硬件与软件配置
│   ├── HARDWARE                   # 硬件描述（启动时重建）
│   ├── SAM                        # 安全账户管理器数据库
│   ├── SECURITY                   # 安全策略
│   ├── SOFTWARE                   # 软件配置
│   └── SYSTEM                     # 系统配置（驱动、服务、启动）
├── HKEY_USERS (HKU)               # 所有用户配置
│   └── S-1-5-21-...-1001          # 每个用户的 HKCU
├── HKEY_CURRENT_USER (HKCU)       # 当前用户配置（HKU\<当前用户SID> 的符号链接）
├── HKEY_CLASSES_ROOT (HKCR)       # 文件关联（HKLM\Software\Classes + HKCU\Software\Classes 的合并视图）
└── HKEY_CURRENT_CONFIG (HKCC)     # 当前硬件配置文件
```

**典型的内核态注册表操作流程**（以驱动加载为例）：

ReactOS 中 I/O 管理器加载驱动时会查询 `HKLM\SYSTEM\CurrentControlSet\Services\<DriverName>` 下的配置 ：

```
RTL_QUERY_REGISTRY_TABLE QueryTable[2];
RtlZeroMemory(&QueryTable, sizeof(QueryTable));
RtlInitUnicodeString(&ImagePath, NULL);

// 查询 Type 值（必需）
QueryTable[0].Name = L"Type";
QueryTable[0].Flags = RTL_QUERY_REGISTRY_DIRECT | RTL_QUERY_REGISTRY_REQUIRED;
QueryTable[0].EntryContext = &Type;

// 查询 ImagePath 值（可选）
QueryTable[1].Name = L"ImagePath";
QueryTable[1].Flags = RTL_QUERY_REGISTRY_DIRECT;
QueryTable[1].EntryContext = &ImagePath;

// 执行查询
Status = RtlQueryRegistryValues(
    RTL_REGISTRY_ABSOLUTE,
    LoadParams->ServiceName->Buffer,
    QueryTable, NULL, NULL);
```

这个例子揭示了注册表操作的**第一性原理模式**：

> 📌 **驱动/服务的配置全部集中在 `HKLM\SYSTEM\CurrentControlSet\Services\<Name>` 下**：
> 
> - `Type`：驱动类型（内核驱动/文件系统驱动/服务）
> - `Start`：启动时机（0=引导时/1=系统初始化/2=自动/3=手动/4=禁用）
> - `ImagePath`：驱动映像路径
> - `ErrorControl`：加载失败时的处理（忽略/正常/严重/关键）
> - `Group`：驱动加载分组（决定加载顺序）

**图形子系统也依赖注册表**：ReactOS 的 `EngpGetDisplayDriverParameters` 从 `HKLM\HARDWARE\DEVICEMAP\VIDEO\...` 读取显示设置 ，一张查询表对应多个键值：

```
RTL_QUERY_REGISTRY_TABLE DisplaySettingsTable[] = {
    READ(dmBitsPerPel, "DefaultSettings.BitsPerPel"),
    READ(dmPelsWidth, "DefaultSettings.XResolution"),
    READ(dmPelsHeight, "DefaultSettings.YResolution"),
    // ... 分辨率、刷新率、方向等
    {0}
};
RtlQueryRegistryValues(RTL_REGISTRY_HANDLE, (PWSTR)hKey, 
    DisplaySettingsTable, ...);
```

**我的洞见——注册表操作是"内核态的配置查询语言"**：

注册表操作的第一性原理是**用统一的键值查询替代分散的配置文件解析**：

> 💡 **为什么不用文本配置文件？**
> 
> - 文本解析慢且复杂（需要词法分析、语法分析）
> - 难以保证原子性和事务性
> - 难以做权限控制（每个键都是安全对象）
> - 难以做二进制数据（REG_BINARY、REG_MULTI_SZ）
> 
> **注册表的优势**：
> 
> - 二进制格式，O(log n) 查找（B+ 树索引，类似 NTFS 目录）
> - 每个键都是对象管理器的命名对象，天然继承第12章的安全模型
> - 支持事务（现代 Windows 通过 `KTM` 内核事务管理器）
> - 支持注册表 hive 的懒加载和分页（不常用部分可换出到磁盘）

**注册表操作的 IRQL 限制**：

> ⚠️ **注册表操作只能在 `PASSIVE_LEVEL` 进行**​ 。配置管理器的实现依赖内存管理器和对象管理器，这些组件在 `DISPATCH_LEVEL` 及以上无法安全运行。如果你的驱动需要在高 IRQL 时"记录"某些信息，正确做法是：
> 
> - 用 `CmRegisterCallback` 在 `PASSIVE_LEVEL` 注册回调
> - 或者通过工作项（Work Item）延迟到 `PASSIVE_LEVEL` 执行

**现代映照**：现代 Windows 注册表操作增加了：

- **事务性注册表操作**：通过 `KTM` + `ZwCreateTransaction` 实现，要么全部修改成功，要么全部回滚
- **注册表虚拟化**：UAC 下，写 `HKLM\Software` 会被重定向到 `HKCU\Software\Classes\VirtualStore`（兼容老程序）
- **注册表 hive 的懒加载**：`HKLM\HARDWARE` 每次启动重建，`HKCU` 在用户登录时挂载

工业界：注册表是**所有 Windows 软件的基础设施**——驱动、服务、COM 组件、文件关联、用户偏好、安全策略全部存在注册表里。理解注册表操作是逆向工程、取证分析、恶意软件检测的基础。

## 13.2 注册表的初始化和装载

**书的脉络**：注册表初始化是系统启动的关键环节。FreeLoader 引导加载器先把 `HKLM\SYSTEM` 对应的 HIVE 文件加载到内存，扫描其中的启动驱动列表和 NLS（国家语言支持）数据，然后内核的配置管理器接管，将 HIVE 解析为内存中的 B+ 树结构，供后续访问。

**HIVE 文件格式**（ReactOS 完整实现）：

HIVE 文件是注册表在磁盘上的持久化格式，由三部分组成 ：

```
HIVE 文件结构：
┌─────────────────────────────────────┐
│ BASE_BLOCK (4KB)                     │ ← 文件头
│   包含：HIVE 签名、序列号、            │
│   版本、时间戳、根 cell 偏移等         │
├─────────────────────────────────────┤
│ BIN #1 (4KB 对齐)                    │ ← 数据容器
│   ┌─────────────────────────────────┐ │
│   │ CELL #1 (键/值/子键列表)        │ │
│   │ CELL #2 (键/值/子键列表)        │ │
│   │ ...                             │ │
│   └─────────────────────────────────┘ │
├─────────────────────────────────────┤
│ BIN #2 (4KB 对齐)                    │
│   ┌─────────────────────────────────┐ │
│   │ CELL #N ...                     │ │
│   └─────────────────────────────────┘ │
├─────────────────────────────────────┤
│ ... 更多 BIN                          │
└─────────────────────────────────────┘
```

- **BASE_BLOCK**：4KB 文件头，存储 HIVE 的全局元数据
- **BIN**：4KB 对齐的数据块容器，管理若干 CELL
- **CELL**：实际存储键、值、子键列表的数据单元，大小可变

**系统启动时的注册表装载流程**：

```
1. BIOS/UEFI → FreeLoader 引导加载器
   ↓
2. WinLdrInitSystemHive(LoaderBlock, BootPath, FALSE)
   ↓ 加载系统 HIVE 文件（通常 \Windows\System32\CONFIG\SYSTEM）
   ↓
3. WinLdrScanSystemHive(LoaderBlock, BootPath)
   ↓ 扫描系统 HIVE：
   ↓   - 加载 NLS 数据（代码页、排序表）
   ↓   - 提取引导驱动列表（Boot Driver List）
   ↓
4. LoadAndBootWindowsCommon()
   ↓ 加载 ntoskrnl.exe + hal.dll
   ↓
5. 内核初始化配置管理器（CM）
   ↓ 将内存中的 HIVE 解析为 B+ 树
   ↓
6. 会话管理器 smss.exe 启动
   ↓ 挂载其他 HIVE（SAM、SECURITY、SOFTWARE、DEFAULT）
   ↓
7. 用户登录 → 挂载 HKCU（对应用户的 NTUSER.DAT）
```

ReactOS 的 FreeLoader 在 `winldr.c` 中调用 `WinLdrInitSystemHive` 和 `WinLdrScanSystemHive` 完成系统 HIVE 的初始装载 。装载后，启动驱动列表被提取出来，FreeLoader 按列表顺序加载关键的启动驱动（如 `cdfs.sys`、`uniata`、`storahci`、`fastfat` 等）。

**HIVE 文件在磁盘上的位置**：

ReactOS 的注册表信息存储在 `\ReactOS\System32\CONFIG\SYSTEM` 文件中 。现代 Windows 的对应路径是 `\Windows\System32\CONFIG`，包含：

|HIVE 文件|对应 HKEY|说明|
|---|---|---|
|`SYSTEM`|`HKLM\SYSTEM`|系统配置（驱动、服务、启动）|
|`SOFTWARE`|`HKLM\SOFTWARE`|软件配置|
|`SAM`|`HKLM\SAM`|安全账户管理器数据库|
|`SECURITY`|`HKLM\SECURITY`|安全策略|
|`DEFAULT`|`HKU\.DEFAULT`|默认用户配置|
|`NTUSER.DAT`|`HKCU`|每个用户的配置（位于用户目录）|

**安装阶段的注册表初始化**：

ReactOS 在安装阶段调用 `NtInitializeRegistry(CM_BOOT_FLAG_SETUP)` 创建默认 HIVE ，然后通过 INF 文件（如 `hivedef.inf`）填充初始键值 。这个过程揭示了：

> 💡 **注册表不是"天生就有"的**——它需要初始化创建：
> 
> - 安装程序创建空的 HIVE 文件
> - 通过 INF 文件定义初始键值（如软件路径、安装信息）
> - 首次启动时内核填充 `HKLM\HARDWARE`（硬件描述）
> - 用户首次登录时创建 `NTUSER.DAT`

**我的洞见——注册表装载是"系统启动的配置基石"**：

注册表初始化的第一性原理是**在系统启动的最早阶段就建立起"配置内存"**：

> 📌 **为什么注册表装载如此关键？**
> 
> - 驱动加载顺序依赖 `HKLM\SYSTEM\CurrentControlSet\Services\<Driver>\Group` 和 `Start` 值
> - 内核需要 NLS 数据来支持 Unicode 字符串操作
> - 安全策略（第12章）依赖 `HKLM\SECURITY` 和 `SAM`
> - 用户环境依赖 `HKCU` 的挂载
> 
> **如果 HIVE 损坏会怎样？**
> 
> - `SYSTEM` HIVE 损坏 → 系统无法启动（需要"最后一次正确的配置"或修复控制台）
> - `SAM` HIVE 损坏 → 无法验证任何用户（需要离线重置）
> - `NTUSER.DAT` 损坏 → 用户登录后配置丢失，但系统可启动

**HIVE 的内存管理**：

配置管理器将 HIVE 文件映射到内核内存后，通过 `HHIVE` 结构管理：

```
typedef struct _HHIVE {
    UINT HiveSignature;       // 标识 HIVE 类型
    PGETCELL_ROUTINE GetCell; // 获取 CELL 的回调函数
    PALLOCATECELL_ROUTINE AllocateCell; // 分配 CELL
    // ... 
    LIST_ENTRY BaseBlock;     // BASE_BLOCK 信息
    // ...
} HHIVE, *PHHIVE;
```

CELL 的分配通过 `HvAllocateCell` 实现——从空闲 CELL 列表中找到合适大小的块，类似堆分配器 。

**现代映照**：现代 Windows 注册表装载增加了：

- **注册表 hive 的事务日志**：`SYSTEM.LOG`、`SOFTWARE.LOG` 等，用于崩溃恢复（类似 NTFS 的 `$LogFile`）
- **注册表 hive 压缩**：Windows 10+ 对不常用的 hive 进行压缩
- **VBS 保护**：关键 hive（如 `SAM`、`SECURITY`）的访问受安全内核监控
- **WSL 互操作**：Linux 应用的配置映射到 `HKCU\Software\Microsoft\Windows\CurrentVersion\Lxss`

工业界：注册表装载机制是**系统启动分析、取证、灾难恢复**的核心。理解 HIVE 格式让你能够：

- 离线挂载 hive 文件进行分析（`reg load` 命令）
- 从损坏的系统中提取 `SAM` 进行离线破解（ Mimikatz 等工具的原理）
- 通过修改 `SYSTEM` HIVE 改变启动配置（如禁用驱动签名验证）

## 13.3 库函数 RtlQueryRegistryValues()

**书的脉络**：`RtlQueryRegistryValues` 是 RTL 层提供的注册表查询便捷函数，允许调用者通过一张查询表（Query Table）一次性查询多个键值，自动处理类型转换、默认值、内存分配等细节。它内部调用 `ZwQueryValueKey` 获取原始数据，再通过 `RtlpCallQueryRegistryRoutine` 分派到具体的处理函数（如 `RtlpQueryRegistryDirect`）。

**函数原型**：

```
NTSTATUS RtlQueryRegistryValues(
    IN ULONG RelativeTo,           // 路径基准（RTL_REGISTRY_ABSOLUTE 等）
    IN PCWSTR Path,                // 注册表键路径
    IN PRTL_QUERY_REGISTRY_TABLE QueryTable,  // 查询表
    IN PVOID Context,              // 回调上下文
    IN PVOID Environment OPTIONAL  // 环境变量（用于 RTL_QUERY_REGISTRY_DELETEABLE 等）
);
```

**查询表（RTL_QUERY_REGISTRY_TABLE）的结构**：

```
typedef struct _RTL_QUERY_REGISTRY_TABLE {
    PRTL_QUERY_REGISTRY_ROUTINE QueryRoutine;  // 自定义回调函数（NULL 时用 Direct）
    ULONG Flags;                                // 查询标志
    PWSTR Name;                                 // 值名
    PVOID EntryContext;                         // Direct 模式下的输出缓冲区
    ULONG DefaultType;                          // 默认值类型
    PVOID DefaultData;                          // 默认值数据
    ULONG DefaultLength;                        // 默认值长度
    PVOID AllocatedMemory;                      // 函数内部分配的内存（需调用者释放）
} RTL_QUERY_REGISTRY_TABLE, *PRTL_QUERY_REGISTRY_TABLE;
```

**Flags 的关键取值**：

|标志|含义|
|---|---|
|`RTL_QUERY_REGISTRY_DIRECT`|直接将值复制到 `EntryContext` 指定的缓冲区|
|`RTL_QUERY_REGISTRY_REQUIRED`|值必须存在，否则返回错误|
|`RTL_QUERY_REGISTRY_DELETEABLE`|允许 `Environment` 参数参与处理|
|`RTL_QUERY_REGISTRY_NOEXPAND`|不展开环境变量|
|`RTL_QUERY_REGISTRY_TYPECHECK`|类型检查|

**内部调用链**（基于 ReactOS/Windows 实现）：

```
RtlQueryRegistryValues
  ↓ 遍历 QueryTable 数组（直到 Name==NULL 的终止项）
  ↓
  for each table entry:
    ↓
    ZwQueryValueKey(KeyHandle, ValueName, KeyValueFullInformation, ...)
    ↓ 获取键值的完整信息（类型、长度、数据）
    ↓
    RtlpCallQueryRegistryRoutine(QueryTable, KeyValueInformation, ...)
    ↓ 根据 Flags 分派：
    ↓
    ├─ RTL_QUERY_REGISTRY_DIRECT:
    ↓     RtlpQueryRegistryDirect(Type, ValueData, ValueLength, EntryContext)
    ↓     直接复制到 EntryContext
    ↓
    └─ QueryRoutine != NULL:
          QueryRoutine(Context, ValueName, Type, ValueData, 
                       ValueLength, EntryContext, ...)
          调用自定义的回调函数
```

**REG_MULTI_SZ 的特殊处理**​ ：

```
// 如果是 REG_MULTI_SZ 类型，追加一个 NUL 终止符
if (KeyValueInformation->Type == REG_MULTI_SZ) {
    *(PWCHAR)((PUCHAR)KeyValueInformation + KeyResultLength) = UNICODE_NULL;
    KeyValueInformation->DataLength += sizeof(UNICODE_NULL);
}
```

这是因为 `REG_MULTI_SZ` 是多字符串数组，需要双重 NUL 终止（`string1\0string2\0\0`）。

**内存管理的重要细节**​ ：

> ⚠️ **RtlQueryRegistryValues 可能内部分配内存**：
> 
> - 当查询的值是 `REG_MULTI_SZ`、`REG_BINARY` 或 `REG_SZ` 且长度超过 `EntryContext` 缓冲区时
> - 分配的内存记录在 `QueryTable[i].AllocatedMemory` 字段
> - **调用者必须手动释放**：`if (QueryTable[i].AllocatedMemory) ExFreePool(QueryTable[i].AllocatedMemory);`
> - 不释放会导致内核内存泄漏

**典型用法示例**（驱动加载查询服务类型）：

```
RTL_QUERY_REGISTRY_TABLE QueryTable[2];
ULONG Type;
UNICODE_STRING ImagePath;

RtlZeroMemory(&QueryTable, sizeof(QueryTable));
RtlInitUnicodeString(&ImagePath, NULL);

// 第一个查询：Type（必需）
QueryTable[0].Name = L"Type";
QueryTable[0].Flags = RTL_QUERY_REGISTRY_DIRECT | RTL_QUERY_REGISTRY_REQUIRED;
QueryTable[0].EntryContext = &Type;

// 第二个查询：ImagePath（可选）
QueryTable[1].Name = L"ImagePath";
QueryTable[1].Flags = RTL_QUERY_REGISTRY_DIRECT;
QueryTable[1].EntryContext = &ImagePath;
// 注意：QueryTable[1] 是数组最后一个元素，Name=NULL 自动终止

// 执行查询
Status = RtlQueryRegistryValues(
    RTL_REGISTRY_ABSOLUTE,
    L"\\Registry\\Machine\\System\\CurrentControlSet\\Services\\MyDriver",
    QueryTable, NULL, NULL);

if (NT_SUCCESS(Status)) {
    // 使用 Type 和 ImagePath
    // ...
    
    // 释放可能分配的内存
    if (QueryTable[1].AllocatedMemory) {
        ExFreePool(QueryTable[1].AllocatedMemory);
    }
}
```

**我的洞见——RtlQueryRegistryValues 是"注册表查询的批处理优化器"**：

这个函数的第一性原理是**用"声明式查询表"替代"命令式多次调用"**：

> 📌 **传统方式（多次调用）**：
> 
> ```
> ZwOpenKey(&hKey, ...);
> ZwQueryValueKey(hKey, "Type", ...);
> ZwQueryValueKey(hKey, "ImagePath", ...);
> ZwQueryValueKey(hKey, "Start", ...);
> // ... 每个值都要单独调用
> ```
> 
> **RtlQueryRegistryValues 方式（批处理）**：
> 
> ```
> // 一张表声明所有要查的值
> // 一次函数调用完成所有查询
> // 自动处理类型转换、默认值、内存分配
> ```

**设计优势**：

1. **减少函数调用开销**：一次调用 vs N 次调用
2. **减少键打开次数**：内部只打开一次键
3. **声明式编程**：调用者声明"我要查什么"，而不是"怎么查"
4. **自动类型处理**：`RTL_QUERY_REGISTRY_DIRECT` 标志自动将数据复制到 `EntryContext`
5. **默认值支持**：`DefaultType`/`DefaultData` 提供值不存在时的回退
6. **自定义回调**：`QueryRoutine` 允许复杂的后处理

**与用户态的对应**：

用户态的 `RegQueryValueEx` 是单次查询，而 `RtlQueryRegistryValues` 是内核态的批处理版本。两者底层都走到 `ZwQueryValueKey` → 配置管理器。

**现代映照**：现代 Windows 的 `RtlQueryRegistryValues` 增加了：

- **RTL_QUERY_REGISTRY_TYPECHECK**：严格的类型检查，类型不匹配时返回错误
- **更好的内存管理**：Windows 10+ 对 `AllocatedMemory` 的处理更加健壮
- **Wow64 重定向**：32位程序访问 `HKLM\Software` 时被重定向到 `HKLM\Software\WOW6432Node`

工业界：理解 `RtlQueryRegistryValues` 是**编写 Windows 驱动的基础技能**。每个驱动都需要在 `DriverEntry` 中查询自己的服务配置（服务类型、启动类型、镜像路径等）。EDR 和杀毒软件的 minifilter 驱动也通过它读取配置。

**注册表监控的现代应用——CmRegisterCallback**：

现代 Windows 提供了 `CmRegisterCallback` 函数，用于注册注册表操作的回调函数 ：

```
NTSTATUS CmRegisterCallback(
    PEX_CALLBACK_FUNCTION Function,  // 回调函数
    PVOID Context,                   // 上下文
    PLARGE_INTEGER Cookie);          // 回调句柄

// 回调函数原型
NTSTATUS RegistryCallback(
    PVOID CallbackContext,
    PVOID Argument1,                 // REG_NOTIFY_CLASS 操作类型
    PVOID Argument2);                // 操作详细信息
```

通过注册回调，内核驱动可以：

- **监控**注册表的创建、修改、删除操作
- **拦截**敏感的注册表操作（如修改 `HKLM\SYSTEM\CurrentControlSet\Services` 添加恶意驱动）
- **审计**谁在什么时候修改了哪些键值

> 💡 **这是现代 EDR 监控注册表攻击的核心机制**：
> 
> - 检测 `HKLM\...\Run` 和 `RunOnce` 的修改（持久化）
> - 检测 `HKLM\System\CurrentControlSet\Services` 的新增（驱动级 rootkit）
> - 检测 `HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\Shell Folders` 的修改（文件重定向）
> - 检测 `HKLM\Software\Microsoft\Windows NT\CurrentVersion\Image File Execution Options` 的修改（IFEO 劫持）

对应的注销函数是 `CmUnRegisterCallback(Cookie)` 。

## 全章串联：一次驱动加载的完整注册表访问

```
系统启动 → FreeLoader 加载 SYSTEM HIVE
  ↓
内核初始化配置管理器（CM）
  ↓
解析 HIVE 为内存 B+ 树
  ↓
I/O 管理器开始加载启动驱动
  ↓
对于驱动 X：
  ↓
1. 构造查询表：
   QueryTable[0] = {Name="Type", Flags=DIRECT|REQUIRED, EntryContext=&Type}
   QueryTable[1] = {Name="ImagePath", Flags=DIRECT, EntryContext=&ImagePath}
   QueryTable[2] = {Name="Start", Flags=DIRECT, EntryContext=&Start}
   QueryTable[3] = {Name=NULL}  // 终止项
  ↓
2. 调用 RtlQueryRegistryValues(
     RTL_REGISTRY_ABSOLUTE,
     L"\Registry\Machine\System\CurrentControlSet\Services\X",
     QueryTable, NULL, NULL)
  ↓
3. RtlQueryRegistryValues 内部：
   ├─ ZwOpenKey 打开键
   ├─ 遍历 QueryTable：
   │   ├─ ZwQueryValueKey("Type") → RtlpQueryRegistryDirect → 复制到 &Type
   │   ├─ ZwQueryValueKey("ImagePath") → RtlpQueryRegistryDirect → 复制到 &ImagePath
   │   └─ ZwQueryValueKey("Start") → RtlpQueryRegistryDirect → 复制到 &Start
   └─ 返回 STATUS_SUCCESS
  ↓
4. I/O 管理器根据 Type/Start/ImagePath 加载驱动 X
  ↓
5. 驱动 X 的 DriverEntry 中可能再次调用 RtlQueryRegistryValues
   读取自己的私有配置（如超时参数、日志级别等）
  ↓
6. 如果查询失败 → 驱动加载失败
  ↓
系统继续加载下一个驱动，直到所有启动驱动加载完成
```

**这张图揭示了第13章的真正主线**：

1. **13.1 注册表操作**：Zw* 系列 API + 注册表逻辑结构（五大预定义键）+ 安全对象模型
2. **13.2 注册表的初始化和装载**：HIVE 文件格式（BASE_BLOCK/BIN/CELL）+ FreeLoader 装载 + 配置管理器接管 + 各 HIVE 文件映射
3. **13.3 RtlQueryRegistryValues()**：查询表驱动的批处理查询 + 内部调用链（ZwQueryValueKey → RtlpCallQueryRegistryRoutine → RtlpQueryRegistryDirect）+ 内存管理

**与前十二章的联系**：

- 第2章系统调用 → `ZwQueryValueKey` 等是系统调用，陷入内核
- 第4章对象管理 → 注册表键是命名对象，存在于 `\REGISTRY` 对象目录下
- 第9章设备驱动 → 驱动加载依赖注册表查询（Type/Start/Group）
- 第12章安全性 → 注册表键是安全对象，访问时执行 `SeAccessCheck`；DACL 决定谁能读/写键值
- 第11章文件操作 → HIVE 文件本身是文件，通过文件系统驱动加载（但 SYSTEM HIVE 在 FS 驱动加载前就需要，所以 FreeLoader 特殊处理的）
- 配置管理器（CM）本身建立在**内存管理器**（第3章）和**缓存管理器**（第11章）之上——HIVE 文件通过缓存管理器映射到内存

## 工业界实际应用与安全视角

### 🛡️ 安全领域

**1. 注册表作为攻击面**：

注册表是攻击者最常使用的持久化位置：

- **Run/RunOnce 键**：`HKLM\...\CurrentVersion\Run`、`HKCU\...\CurrentVersion\Run`
- **服务键**：`HKLM\SYSTEM\CurrentControlSet\Services\<Malware>` —— 注册为驱动/服务
- **WMI 消费者**：`HKLM\SOFTWARE\Microsoft\Wbem\...`
- **IFEO 劫持**：`HKLM\...\Image File Execution Options\<Target.EXE>` —— 调试器注入
- **文件关联劫持**：`HKCR\...\shell\open\command` —— 修改文件打开方式

**2. 注册表监控与防御**：

现代 EDR 通过 `CmRegisterCallback` 注册回调，监控：

- 敏感键的创建/修改/删除
- 异常的注册表操作模式（如批量修改 Run 键）
- 未签名的驱动尝试注册为服务

Sysmon 的 `Event ID 12/13/14` 就是注册表监控的外部表现。

**3. 注册表取证**：

- **Registry Hive 离线分析**：通过 `reg export` 或专业工具（如 Registry Explorer）分析
- **Registry Hive 时间戳**：每个键有 `LastWriteTime`，揭示修改时间
- **Registry Hive 删除恢复**：CELL 删除后数据仍在 BIN 中，可通过取证工具恢复
- **Registry Hive 事务日志**：`*.LOG` 文件记录未完成的事务

**4. 注册表与 Credential Guard**：

Windows 10+ 的 Credential Guard 将 `SAM` 和 `SECURITY` HIVE 的访问重定向到安全内核（VTL1），防止 Pass-the-Hash 攻击。

### ⚙️ 工业应用

**1. 组策略（GPO）**：

企业通过 GPO 批量配置注册表键值，实现统一的系统配置管理。GPO 本质上就是注册表设置的集合。

**2. 软件部署**：

- MSI 安装包通过注册表记录安装信息（`HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall`）
- ClickOnce 和 MSIX 使用注册表进行应用注册

**3. 系统配置管理**：

- **PowerShell**：`Get-ItemProperty`/`Set-ItemProperty` 操作注册表
- **DISM**：离线挂载 WIM/ESD 映像后修改注册表
- **MDT/SCCM**：批量部署时通过注册表定制系统

**4. 虚拟化与容器**：

- **Hyper-V**：VM 的配置存储在注册表中
- **WSL**：Linux 应用的配置映射到 `HKCU\Software\Microsoft\Windows\CurrentVersion\Lxss`
- **App-V**：虚拟化的应用程序配置隔离在独立的 hive 中

**5. 云与现代化部署**：

- **Azure AD Join**：将设备注册信息写入注册表
- **Intune MDM**：通过 MDM 策略配置注册表
- **Windows Autopilot**：通过注册表标识设备部署状态

## 给你的读书建议

1. **重点理解"三层结构"**：HIVE 文件格式（磁盘） → 配置管理器（内存管理） → RTL 查询 API（便捷访问）。这三层是理解注册表的主线。
2. **clone ReactOS 源码，重点看**：
    - `ntoskrnl/config/`：配置管理器（CM）实现——`cmhook.c`、`cmparse.c`、`cmkey.c`、`cmsysini.c`（**必读**）
    - `ntoskrnl/include/internal/cm.h`：HHIVE、HCELL 等核心结构定义
    - `sdk/lib/rtl/registry.c`：`RtlQueryRegistryValues` 的实现（**必读**）
    - `boot/freeldr/freeldr/ntldr/wlregistry.c`：`WinLdrInitSystemHive` 的实现
    - `drivers/filesystems/`：HIVE 文件通过文件系统驱动加载
3. **用 WinDbg 实操**：
    - `!reg hivelist`：列出所有已加载的 hive
    - `!reg openkey \Registry\Machine\System`：打开指定键
    - `!reg querykey <Key>`：查询键的值
    - `dt nt!_CM_KEY_BODY`：查看键对象结构
    - `dt nt!_HHIVE`：查看 Hive 结构
    - `bp nt!RtlQueryRegistryValues`：观察注册表查询
4. **用 Sysinternals 工具实地观察**：
    - **Process Monitor**：实时捕获 `RegOpenKey`/`RegQueryValue`/`RegSetValue` 操作
    - **Registry Explorer**：高级注册表编辑器，支持离线 hive 分析
    - **Autoruns**：查看所有注册表持久化位置（Run 键、服务等）
    - **RegDelNull**：删除名称包含 null 字符的注册表键（rootkit 常用技巧）
5. **动手实验**：
    - 用 `reg save` 导出 hive 文件，用 `reg load` 挂载分析
    - 编写一个简单的内核驱动，在 `DriverEntry` 中用 `RtlQueryRegistryValues` 读取自己的配置
    - 注册 `CmRegisterCallback` 监控注册表操作，用 DbgPrint 输出
6. **下一章（第14章，如果有）可能深入系统关闭/崩溃转储/电源管理等领域**。这些机制大量依赖注册表配置——例如崩溃转储的设置存储在 `HKLM\SYSTEM\CurrentControlSet\Control\CrashControl` 下，电源策略存储在 `HKLM\SYSTEM\CurrentControlSet\Control\Power` 下。理解注册表是理解这些系统机制的前提。

书是 2009 年的，但基于 ReactOS 的注册表实现**在核心数据结构（HIVE 格式、CM 内存管理、RTL 查询 API）上与今天的 Windows 10/11 高度一致**——变的只是：

- **事务性支持**：通过 KTM 实现注册表操作的事务
- **VBS 保护**：关键 hive 的访问受安全内核监控
- **压缩与优化**：Windows 10+ 对不常用 hive 的压缩
- **CmRegisterCallback 的增强**：Vista 后提供完整的注册表操作信息（不仅仅是允许/拒绝）
- **注册表虚拟化**：UAC 下的 `HKLM\Software` 写操作重定向

抓住"**HIVE 是磁盘格式、CM 是内存管理器、RTL 是便捷 API**"这三个第一性原理，你就能穿透任何版本的 Windows 注册表实现。
