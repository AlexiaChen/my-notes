
第3章是整本书真正的分水岭。前两章你学会了"用户态怎么敲门进内核"，这一章开始，内核把你敲的那声门背后的房间打开了——**虚拟内存是怎么被"凭空"造出来的、物理页是怎么被管账的、页表是怎么被改写的、缺页时内核怎么兜底**。

我的核心洞见先抛在前面：**Windows 内存管理的第一性原理，是把"地址空间""物理页""页表项"这三件事彻底解耦**。用户要的不是物理内存，而是一段"可用的虚拟地址"——至于背后有没有真物理页、是不是共享的、是不是换出到磁盘了，那是内核lazy到不能再lazy才会去处理的事。整章 3.1 到 3.5 都在讲这三个对象怎么被分别管理、又在何处汇合。

> 💡 读这一章的正确姿势：把 `NtAllocateVirtualMemory` 当成主线剧情，VAD 是"虚拟地址的账本"、PFN 数据库是"物理页的账本"、PTE 是"两者之间的桥梁"、Hyperspace 是"修桥时用的临时脚手架"、缺页异常是"桥没修好时的补救"、Section 是"多座桥共享同一片物理土地"的机制。

## 3.1 内存区间的动态分配

### 3.1.1 内核对用户空间的管理

**书的脉络**：用户进程调用 `VirtualAlloc` → `ntdll!NtAllocateVirtualMemory` → 陷阱门进内核 → `ntoskrnl!NtAllocateVirtualMemory`。内核在目标进程的 **VAD（Virtual Address Descriptor）树**​ 上找一个空闲区间，插入一个 VAD 节点记账，必要时批量设置 PTE。

**我的洞见——VAD 是"虚拟地址的产权登记处"**：

进程拥有的不是物理页，而是一段段**被登记的虚拟地址区间**。每个进程 `EPROCESS` 里挂着一棵 **VAD 的 AVL 树**（`VadRoot`），按地址排序。VAD 节点记录这段区间的起止页号、保护属性（R/W/X）、后备存储（是私有内存还是映射了某个 Section）。

为什么用 AVL 树而不是链表？因为进程的虚拟地址区间可能非常多（加载几十个 DLL、每个 DLL 多个段、堆/栈/TLS/mapped file 各自占区间），查找"一段足够大的空洞"如果用链表是 O(N)，AVL 树是 O(log N)。ReactOS 的 `MiFindEmptyAddressRangeInTree` 就是在 AVL 树上做带范围约束的二叉搜索。

**关键设计哲学：分层验证 + 延迟提交**

`NtAllocateVirtualMemory` 干的事分两层：

1. **RESERVE（预留）**：只在 VAD 树上记账，"我这个进程从现在起拥有 `[0x00400000, 0x00500000)` 这段虚拟地址"。此时**没有任何物理页被分配**，PTE 全置 0。
2. **COMMIT（提交）**：真正给这段区间分配物理页、设置 PTE 指向物理页。

这套机制让一个进程可以"RESERVE 1GB 虚拟地址但只 COMMIT 4KB"——虚拟地址便宜（只是 VAD 树上的一个节点），物理页贵（要真的从 PFN 数据库抠出来）。这就是为什么你在 WinDbg 里看进程虚拟地址空间，经常能看到大片"reserved but not committed"的区域。

> 📌 **双重加锁的顺序是铁律**：`NtAllocateVirtualMemory` 先拿 **Working Set Lock**（工作集锁），再拿 **Address Creation Lock**（地址创建锁）。顺序颠倒会死锁。这是 ReactOS/NT 内核里少数几个"顺序即正确性"的地方。

**现代映照**：x64 Windows 的 VAD 机制与 x86 完全一致，只是虚拟地址空间从 2GB 扩展到 **128TB 用户空间**（低 48 位全 0：0x00000000`00000000 ~ 0x0000FFFF`FFFFFFFF）。VAD 树的 AVL 结构、RESERVE/COMMIT 分离、双重加锁顺序——**这些第一性原理在现代 Windows 10/11 里一字未改**。你在 WinDbg 里用 `!vad` 命令看到的，就是书里讲的这颗树。

工业界应用：现代 EDR（端点检测）对 `NtAllocateVirtualMemory` 的监控是标配——因为**无文件攻击、shellcode 注入、Process Hollowing 全都是在 VAD 树上做手脚**：要么在非可执行区间 COMMIT 后改保护属性为 `PAGE_EXECUTE_READWRITE`，要么在合法模块的 VAD 区间内偷偷映射恶意 Section。理解 VAD 是理解这些攻击手法的钥匙。

### 3.1.2 内核对于物理页面的管理

**书的脉络**：物理内存被切成固定 4KB 的页帧（Page Frame），每个页帧用 **PFN 数据库**​ 中的一个条目描述。PFN 条目记录：页的状态（空闲/已分配/待命/已修改/坏页）、链表指针（挂到对应状态链表上）、引用计数、对应 PTE 的反向指针等。

**我的洞见——PFN 数据库是物理内存的"进程表"**：

如果说 VAD 树是虚拟地址的账本，那 PFN 数据库就是物理页的账本。内核维护着几条关键链表：

|链表|含义|用途|
|---|---|---|
|**Zeroed Page List**​|已清零的页|快速分配（用户要 0 初始化内存时直接拿）|
|**Free Page List**​|空闲页|常规分配|
|**Standby Page List**​|待命页|保留内容但可被回收（相当于"软"空闲）|
|**Modified Page List**​|已修改页|脏页，换出前必须先写回|
|**Bad Page List**​|坏页|硬件故障标记|

这个设计的精妙之处在于**"页的流转"就是链表节点的搬运**：分配物理页 = 从 Zeroed/Free 链表摘一个节点；页面换出 = 从 Modified 链表搬到 Standby 链表；页面被改写 = 从 Standby 搬回 Modified。整个物理内存管理就是一场**链表杂技**。

> 💡 **为什么要有 Zeroed Page List？**​ 因为安全原因，分配给用户进程的物理页必须清零（否则能看到上一个进程残留的密码、密钥）。清零是个开销不小的操作。NT 内核的策略是：用一个**专门的"零页线程"（Zero Page Thread）**在系统空闲时提前把 Free 页清零、搬到 Zeroed 链表。这样当用户调用 `VirtualAlloc(MEM_COMMIT)` 时，直接从 Zeroed 链表摘页即可，零等待。

**现代映照**：x64 Windows 的 PFN 数据库结构基本延续 NT 设计。现代 Windows 还引入了 **"页面合并"（Page Combining）**​ 和 **"内存压缩"（Memory Compression）**——前者把内容相同的物理页合并成一张（类似写时复制），后者把冷页压缩后留在内存而非换出到磁盘，这都是 PFN 链表管理的进化版。

工业界：理解 PFN 链表是理解 **Windows 内存取证**​ 的基础。取证工具（如 Volatility 的 `windows.pfn` 插件）直接遍历 PFN 数据库，重建"哪些物理页被哪些进程映射"的关系——这正是 3.1.2 讲的知识在实战中的应用。

### 3.1.3 虚存页面的映射

**书的脉络**：虚拟地址到物理地址的映射通过 **页表（Page Table）**​ 完成。x86 下是经典的二级页表（PD→PT→物理页），x86 PAE 是三级，x64 是四级（PXE→PPE→PDE→PTE）。PTE（Page Table Entry）是映射的最小单元，4 字节（x86）或 8 字节（PAE/x64）。

**我的洞见——PTE 是连接"虚拟"和"物理"的原子开关**：

每一个 PTE 就是一个**承诺**："虚拟地址 `Va` 对应的物理页帧是 `PFN`，访问权限是 `R/W/X`"。内核修改 PTE 就是在改写这个承诺。

但这里有个鸡生蛋问题：**内核要修改某个 PTE，必须先能访问这个 PTE 本身；而 PTE 存在于内核的页表里，要访问它又得有它的虚拟地址**——如果目标 PTE 是"别的进程的用户态页面对应的 PTE"，内核根本没有它的虚拟地址映射。

这就引出了 3.1.4 的 Hyperspace。这里先记住：**PTE 操作是内存管理最热的路径**，每次页面映射/解除映射/保护属性变更都要改 PTE；而 PTE 本身的"可访问性"又依赖 Hyperspace 这种临时映射机制。这是 3.1.3 和 3.1.4 藕断丝连的根本原因。

**关键数据结构**：ReactOS 里 PTE 是 `MMPTE` 联合体，按位域解释：

- 物理页帧号（PFN）
- 访问权限位（R/W、U/S、NX）
- 状态位（Valid/Present、Dirty、Accessed）
- 软件位（Prototype PTE 标记、写时复制标记）

> ⚠️ 注意 **Prototype PTE（原型页表项）**​ 这个概念——它是 Section 共享映射的基础。多个进程的 PTE 可以指向同一个 Prototype PTE，后者再指向物理页。当物理页被换出时，只需修改 Prototype PTE 一处，所有进程的 PTE 通过"指向 Prototype"间接感知到变化。这是 3.1.4 和 3.4 之间的暗线。

**现代映照**：x64 四级页表下，一个虚拟地址被切成 9+9+9+9+12 位：PML4E → PDPE → PDE → PTE → 页内偏移。PTE 本身是 8 字节。现代 CPU 的 PCID（Process Context ID）和 INVPCID 指令优化了 TLB 刷新——这是 3.1.3 在硬件层的进化。

### 3.1.4 Hyperspace 的临时映射

**书的脉络**：Hyperspace 是系统空间里预留的一块虚拟地址区间，专门用于**临时映射任意物理页**。x86 下起点 `HYPERSPACE = 0xC0400000`（PAE 下 `0xC0800000`），大小 4MB（1024 个 PTE 槽位）。

**我的洞见——Hyperspace 是 x86 架构缺陷的工程补丁**：

x86 没有像 MIPS 那样的 `KSEG0`（固定虚拟地址直接映射物理地址的低段）。在 x86 上，**内核想访问任意一个物理页，必须先有它的虚拟地址**——但虚拟地址空间是有限的，不可能把所有物理页都永久映射进来（物理内存可能比内核虚拟地址空间还大）。

Hyperspace 的解法是**"按需临时映射"**：要用某个物理页了，从 Hyperspace 的 1024 个槽位里挑一个，写 PTE 把物理页映射进来，用完即释放。典型场景：

- **初始化新分配的物理页**（清零、写 PFN 数据）
- **访问/修改别的进程的页表页**（修改 PTE 自身）
- **跨进程内存操作**（如 `MmCopyVirtualMemory`）
- **DMA 准备**（取物理地址交给 DMA 控制器）

核心函数是一对：`MiMapPageInHyperSpace(PFN)` 返回虚拟地址，`MiUnmapPageInHyperSpace()` 解除映射。

**为什么 Hyperspace 每个进程独立？**​ 因为 Hyperspace 操作靠**自旋锁**保护。如果所有进程共享一个 Hyperspace 池，进程 A 映射时进程 B 就得自旋等——这是不可接受的跨进程锁竞争。所以**每个进程有自己独立的 Hyperspace 槽位集合**，用 `Process->HyperSpaceLock` 保护。

> 📌 这是书里一个非常容易被忽略但极其重要的细节：**Hyperspace 是"进程私有"的少数内核空间区域之一**（另一个是页表映射区 PAGETABLE_MAP）。其他内核空间区域（非分页池、分页池、系统缓存）是所有进程共享的。

**现代映照**：x64 下这个问题依然存在，但有了更优雅的解法——**"直接映射区"（Direct Mapping）**。x64 Windows 在内核空间划出一块**固定虚拟地址区间，线性映射所有物理内存**（类似 MIPS 的 KSEG0）。这样任何物理页都有"永久的虚拟地址"，不需要 Hyperspace 临时映射。但 Hyperspace 机制作为"访问别的进程页表"的工具依然保留。

### 3.1.5 系统空间的映射

**书的脉络**：系统空间（高 2GB，x64 下高 128TB）是所有进程共享的内核虚拟地址空间。它进一步被切成固定区域：

```
MmNonPagedSystemStart      ← 非分页系统区起始
MmNonPagedPoolStart        ← 非分页池起始
MmNonPagedPoolExpansionStart
MmNonPagedPoolEnd          ← 非分页池结束
MmPagedPoolStart           ← 分页池起始
MmPagedPoolEnd             ← 分页池结束
MmSystemCacheStart         ← 系统缓存起始
MmSystemCacheEnd           ← 系统缓存结束
```

**我的洞见——系统空间布局是"按用途静态划分"的典范**：

用户空间是动态的（VAD 树管理），但系统空间是**静态划分**的——启动时就定死每块区域的位置和大小。这是因为内核自己用的内存必须"常驻且可预测"：

- **非分页池（NonPaged Pool）**：任何时候（包括 DISPATCH_LEVEL 以上 IRQL）都能访问的内存。因为高 IRQL 下不能触发缺页（缺页处理本身可能需要申请内存，死循环），所以这块内存**永远在物理内存里、永不换出**。驱动开发里所有 DPC、ISR、自旋锁临界区里用的内存都得从这里分配。
- **分页池（Paged Pool）**：可以换出的内核内存。用于那些不需要在任意 IRQL 访问的数据结构。
- **系统缓存（System Cache）**：文件系统缓存，把磁盘文件缓存在内存里。

**非分页池大小的动态计算**：

```
最小 256KB + 每 MB 物理内存加 32KB，默认上限 1MB，每 MB 物理内存最多加 400KB
```

这是 NT 内核"按物理内存大小自适应"的经典策略。

> ⚠️ **系统空间映射和 Hyperspace 的关系**：Hyperspace 本身就是系统空间里切出来的一块特殊区域（0xC0400000 附近）。系统空间的"静态划分"保证了 Hyperspace 的虚拟地址在编译/启动时就是确定的，运行时只需要动态改它的 PTE 内容。

**现代映照**：x64 系统空间 128TB 被静态划分为：PML4 自映射区、HyperSpace、内核镜像、HAL、非分页池、分页池、系统缓存、会话空间、PFN 数据库等。**非分页池/分页池/系统缓存这三块的功能划分与 x86 完全一致**。

工业界：现代 Windows 引入了 **"系统空间随机化（KASLR）"**——每次启动，系统空间各区域的基址随机化，防止内核漏洞利用写死地址。这是对 3.1.5 静态布局的重要安全加固。

### 3.1.6 系统调用 NtAllocateVirtualMemory()

**书的脉络**：把前面 3.1.1~3.1.5 的所有知识串起来的一条完整调用链：

```
用户态 VirtualAlloc(NULL, 1MB, MEM_COMMIT, PAGE_READWRITE)
  ↓
ntdll!NtAllocateVirtualMemory (stub, 系统调用号入 eax)
  ↓
sysenter / int 0x2E
  ↓
ntoskrnl!NtAllocateVirtualMemory [ARM3/virtual.c:4457]
  ① 参数检查（PreviousMode=UserMode 时 Probe 用户指针）
  ② 转换 BaseAddress 到 MEMORY_AREA / VAD
  ③ 检查调用进程是否有足够配额
  ④ MmAllocateVirtualMemory → MiAllocateVirtualMemory
  ⑤ 返回 STATUS_SUCCESS
```

`MiAllocateVirtualMemory` 的内部流程：

1. **参数验证**：Length 是否页对齐、Protect 是否合法、MEM_RESET 是否独占
2. **获取当前进程 EPROCESS**
3. **双重加锁**：Address Creation Lock（写）+ Process Working Set Lock（写）——顺序不能颠倒
4. **查找空闲区段**：`MiFindEmptyAddressRangeInTree` 在 VAD AVL 树中找空洞
5. **创建 VAD 节点**：从 NonPagedPool 分配 `MMVAD`，初始化字段
6. **插入 AVL 树**：`MiInsertVad` → `MiInsertNode`
7. **若 MEM_COMMIT**：对每个 PTE 调用 `MiAllocatePte` 设置 PTE（此时才真正从 PFN 数据库分配物理页）
8. **解锁、返回**

**我的洞见——这个函数是"虚拟内存三层解耦"的集大成展示**：

- **第一层（虚拟地址）**：VAD 树记账 ✅ 步骤 4-6
- **第二层（物理页）**：PFN 数据库分配 ✅ 步骤 7 内部
- **第三层（映射）**：PTE 设置 ✅ 步骤 7

书里这一节最该记住的不是流程，而是**延迟提交的本质**：`MEM_RESERVE` 只做步骤 4-6，`MEM_COMMIT` 才做步骤 7。这个分离让"稀疏数组"场景（声明 1GB 但实际只用 4KB）成为可能。

> 💡 **配额检查（步骤 ③）常被忽视**：每个进程有"虚拟内存配额"和"分页/非分页池配额"。`NtAllocateVirtualMemory` 会检查这次分配会不会超出进程配额。这是 Windows 多用户环境下防止"一个进程吃光系统内存"的关键机制。现代 Windows 的 Job Object（作业对象）进一步强化了配额管理。

**现代映照**：现代 Windows 10/11 的 `NtAllocateVirtualMemory` 实现逻辑与 ReactOS ARM3 版本高度相似，但增加了：

- **VBS/HVCI 环境下的额外校验**：在基于虚拟化的安全（VBS）开启时，内核内存分配要走"安全内核"的校验路径
- **Mitigation 策略**：根据进程的 Mitigation 标志（如 BlockNonMicrosoftBinaries、CFG）限制可执行内存的分配
- **Hardware-enforced Stack Protection**：对栈内存的分配有特殊处理

工业界：现代安全软件的 **"用户态内存分配监控"**​ 正是 Hook `NtAllocateVirtualMemory`（或它的 ETW 事件 `VirtualAlloc`/`VirtualAllocEx`）实现的。Process Hollowing、Shellcode Injection、Reflective DLL Loading 等攻击手法，本质都是对 `NtAllocateVirtualMemory` 的"创造性误用"。

## 3.2 页面异常

**书的脉络**：当 CPU 访问一个虚拟地址，而对应 PTE 的 Present 位为 0（页面不在物理内存）或保护位不符（如写只读页）时，触发 **#PF（Page Fault，中断号 14）**。陷阱处理程序 `KiTrap0E` 调用 `MmAccessFault` / `MmNotPresentFault` 进入内存管理器的缺页处理路径。

ReactOS 的入口 `MmArmAccessFault` 处理流程：

```
CPU 缺页（CR2 = 故障地址）
  ↓
KiTrap0E (x86 汇编中断处理程序)
  ↓
MmArmAccessFault(FaultCode, Address, Mode, TrapInformation)
  ↓
第一阶段：高 IRQL 故障处理（IRQL >= DISPATCH_LEVEL 直接失败）
  ↓
第二阶段：定位故障地址所属的内存区域（MEMORY_AREA）
  ↓
第三阶段：按 MEMORY_AREA 类型分派
  - MEMORY_AREA_SECTION_VIEW → MmNotPresentFaultSectionView
  - MEMORY_AREA_CACHE → MmNotPresentFaultCacheSection
  ↓
第四阶段：处理各类缺页
  - 请求零页故障（Demand Zero Fault）
  - 分页文件故障（Page File Fault）
  - 转换故障（Transition Fault）
  - 原型 PTE 故障（Proto PTE Fault / Copy on Write）
  - 用户栈自动扩展
  - 访问权限检查
```

**我的洞见——缺页异常是"虚拟内存谎言"的兑现时刻**：

前面 3.1.6 讲了 `MEM_RESERVE` 只是记账、不分配物理页。那物理页什么时候分配？**就是缺页异常触发的时刻**。这是 NT 内核"懒到极致"的设计：

- **Demand Zero Fault**：访问一个 COMMIT 但未分配物理页的地址 → 从 Zeroed/Free 链表摘一页清零，设置 PTE
- **Page File Fault**：访问的页被换出到 pagefile.sys → 从 pagefile 读回物理页，设置 PTE
- **Transition Fault**：页在 Standby 链表里（未被回收） → 直接把 PTE 指回去
- **Copy-on-Write Fault**：写时复制页被写 → 分配新物理页，复制内容，修改 PTE 指向新页
- **Prototype PTE Fault**：Section 共享页首次访问 → 通过 Prototype PTE 找到物理页或触发进一步缺页

> 📌 **缺页异常是"性能关键路径"**：据统计，一个典型应用程序的执行过程中，缺页异常的次数与"内存访问总次数"之比约为 1:10000，但**每一次缺页的开销可能是普通内存访问的 1000 倍以上**（涉及 PFN 数据库锁、可能触发 I/O 读 pagefile、可能触发页面换出）。所以 NT 内核花大量精力优化缺页处理——AVL 树查找 VAD 是 O(log N)、PTE 操作用 Interlocked 原语、热路径上尽量避免锁。

**现代映照**：x64 Windows 的缺页处理路径与 x86 基本一致，但增加了：

- **PCID/INVPCID 优化**：减少 TLB 刷新范围
- **VBS 环境下的特殊路径**：某些缺页要经安全内核处理
- **Memory Compression**：Modern Windows 8.1+ 引入，缺页时优先从压缩存储里解压而非读磁盘

工业界：缺页异常是**安全攻防的核心战场**。

- **攻方**：利用缺页异常的"延迟物理页分配"特性，配合 `NtAllocateVirtualMemory` 做 Process Hollowing——先 RESERVE 一段可执行虚拟地址，写入 shellcode 后 COMMIT，此时才触发缺页分配物理页并写入 shellcode
- **守方**：EDR 通过 ETW 的 `PageFault` 事件监控异常频繁的缺页（可能是解密前的 shellcode 在逐页触发）、监控 CoW 故障（可能是 DLL 劫持）

## 3.3 页面的换出

**书的脉络**：当物理内存紧张时，内存管理器需要把一些页换出到 pagefile.sys（分页文件）。换出由 **"平衡器线程"（Balance Manager）**​ 周期性驱动：

```
MmInitPagerThread → PagerThreadMain (系统线程)
  ↓
收到 MmWaitForFreePages 事件
  ↓
遍历各进程：MmTryPageOutFromProcess → MmTrimWorkingSet
  ↓
对选中的页：
  - 若是脏页 → 写 pagefile → 移到 Modified 链表
  - 若是干净页 → 直接移到 Standby 链表
  ↓
释放物理页到 Free/Zeroed 链表
```

**我的洞见——页面换出是"链表杂技"的高潮**：

物理页在 PFN 数据库的链表间流转：

```
Active (在进程工作集) → Modified (脏页) → Standby (待命) → Free/Zeroed → 被重新分配
                          ↓                    ↓
                      写回 pagefile        内容仍保留（可被软回收）
```

关键设计哲学：**"Standby 链表是物理内存的缓存"**。一个页被换出后并不立即销毁内容，而是留在 Standby 链表里——如果很快又被访问，直接从 Standby 搬回 Active（这就是 Transition Fault，极快）；如果长时间不被访问，才真正回收。这是 NT 内核的"软换出"机制，极大地提升了内存复用效率。

> 💡 **工作集（Working Set）的概念**：每个进程有一个"工作集"，即"最近一段时间内访问过的物理页集合"。换出时，平衡器优先换出"不在工作集里"的页（即最近最少使用的页）。这是经典的 LRU 近似算法。

**现代映照**：现代 Windows 的页面换出机制进化明显：

- **Memory Compression（内存压缩）**：Windows 8.1+ 引入，冷页不直接写 pagefile，而是压缩后存在内存里（Compression Store），访问时解压。这比磁盘 I/O 快一个数量级
- **SysMain（原 SuperFetch）**：学习用户习惯，预加载常用程序到 Standby 链表
- **VBS 环境下的换出**：安全内核管理的页不能被普通内核换出

工业界：**页面换出是性能问题的头号嫌疑**。当系统开始频繁换页（Page Faults/sec 指标飙升），性能会断崖式下降。现代 APM（应用性能监控）工具都把"硬缺页率"（访问 Standby 链表未命中、必须读 pagefile）作为关键指标。理解 3.3 的链表流转，是诊断"为什么我的服务突然变慢"的基础。

## 3.4 共享映射区（Section）

**书的脉络**：Section（映射区）是 NT 内核中**"文件对象"和"虚拟内存"之间的桥梁**。创建一个 Section 对象，相当于"把一个文件（或页面文件）映射到虚拟地址空间"。多个进程可以映射同一个 Section，实现**共享内存**。

ReactOS 中的 `ROS_SECTION_OBJECT` 结构：

```
typedef struct _ROS_SECTION_OBJECT {
    CSHORT Type;
    CSHORT Size;
    LARGE_INTEGER MaximumSize;       // Section 大小
    ULONG SectionPageProtection;     // 页面保护模式
    ULONG AllocationAttributes;      // 属性
    PFILE_OBJECT FileObject;         // 指向文件对象（如果是文件映射）
    union {
        PMM_IMAGE_SECTION_OBJECT ImageSection;  // PE 映像
        PMM_SECTION_SEGMENT Segment;             // 数据文件
    };
} ROS_SECTION_OBJECT;
```

调用链：`NtCreateSection` → `MmCreateSection` → （按文件类型分流）

- `SEC_IMAGE` → `MmCreateImageSection`（PE 文件）
- 普通文件 → `MmCreateDataFileSection`
- 无文件（页面文件 Section）→ 纯内存共享

**我的洞见——Section 是"虚拟内存三层解耦"中"物理页"层的共享机制**：

回顾一下 3.1 的三层解耦：

- 虚拟地址层：VAD（每进程独立）
- 物理页层：PFN 数据库（全局共享）
- 映射层：PTE（每进程独立）

Section 是在**物理页层做共享**的机制——多个进程的 VAD 各自记录一段虚拟地址区间，但它们的 PTE 都指向**同一个物理页**（通过 Prototype PTE 间接指向）。

这就带来了 NT 内核最优雅的几个设计：

1. **DLL 共享**：多个进程加载同一个 `kernel32.dll`，物理内存中只有一份代码页，所有进程的 PTE 都指向它。写时复制（CoW）保证某个进程修改自己的数据页时不影响别人
2. **可执行文件加载**：`notepad.exe` 运行时，系统创建 Section 对象映射 exe 文件，进程地址空间的代码段/数据段都来自这个 Section
3. **内存映射文件**：`CreateFileMapping` + `MapViewOfFile` 让用户态直接把文件"当作内存"读写
4. **跨进程共享内存**：`CreateFileMapping` 无文件句柄时，创建的是"页面文件 Section"——纯内存共享，常用于 IPC

> 📌 **Section 与 3.1.3 Prototype PTE 的关系**：Section 的核心是 `MM_SECTION_SEGMENT`（段），每个段对应一组 Prototype PTE。多个进程映射同一个 Section 时，它们的 PTE 都指向这些 Prototype PTE。当物理页被换出时，只需修改 Prototype PTE，所有进程的 PTE 通过"指向 Prototype"间接感知变化——**一处修改，全局生效**。

**现代映照**：x64 Windows 的 Section 机制与 x86 完全一致。现代 Windows 还引入了：

- **Large Pages Section**：大页映射，减少 TLB miss
- **VBS 下的 Section 保护**：某些敏感 Section（如 Credential Guard 的凭据页）受安全内核保护

工业界：Section 是现代 Windows 安全攻防的关键战场：

- **Process Hollowing**：攻击者创建进程（如 `svchost.exe`），但**不映射真实的 Section**，而是清空原 Section、映射恶意的 Section
- **DLL 注入**：通过 `NtCreateSection` + `NtMapViewOfSection` 把恶意 DLL 映射到目标进程
- **EDR 监控**：通过 `ObRegisterCallbacks` 监控 Section 对象的创建（特别是 `SEC_IMAGE` 类型的 Section），这是检测进程注入的有效手段

## 3.5 系统空间的缓冲区管理

**书的脉络**：系统空间的内存分配通过 **"池（Pool）"**​ 机制管理。ReactOS 的池分配核心在 `pool.c`：

```
ExAllocatePoolWithTag(PoolType, Size, Tag)
  ↓
若 Size <= 桶上限（如 1024 字节）→ 走小块分配
  - 按 Size 选桶（8/16/32/64/128/256/512/1024 字节桶）
  - 桶内用 SLIST（无锁单链表）管理空闲项
  - 优先从 SLIST 弹（无锁），失败才加桶锁
  ↓
若 Size > 桶上限 → 走大块分配 MiAllocatePoolPages
  - 分配一组连续物理页
  - 映射到池虚拟地址空间
  - 写 PTE
  - 返回虚拟地址
```

**我的洞见——池分配器是"物理页管理"在"内核空间"的具体应用**：

池分配器底层仍然依赖 3.1.2 讲的 PFN 数据库。区别是：

- **池分配器面向"内核组件"**：驱动、执行体、各种内核数据结构
- **虚拟内存分配（NtAllocateVirtualMemory）面向"用户进程"**

两者的共同点是都用 PFN 数据库管理物理页，区别在于**池分配器更强调"小对象的高效分配"**：

- **小块分配**：用固定大小的桶（bucket）+ SLIST 无锁链表。8 字节的对象放 8 字节桶，16 字节的对象放 16 字节桶……这样分配/释放都是 O(1) 且无锁（多数情况下）
- **大块分配**：直接找 PFN 数据库要连续物理页，映射到池虚拟地址空间

> 💡 **为什么池分配要分桶？**​ 如果所有大小的对象都从一个大链表分配，会产生严重的**外部碎片**（external fragmentation）——内存被切成大量不连续的小块，无法满足大块分配请求。分桶法把"大小相近"的对象归类，每个桶内部碎片控制在最小化。

**Paged Pool vs NonPaged Pool**：

- **NonPaged Pool**：从非分页系统区分配，永不换出。用于高 IRQL 下必须访问的数据（DPC、ISR、自旋锁临界区）
- **Paged Pool**：可以换出。用于普通内核数据结构

**并发控制**：

- 每个桶有自己的自旋锁（`PoolDescriptor->Lock`）
- 小块分配优先走 SLIST（无锁），失败才加锁
- 大块分配用全局 PoolDescriptor 锁
- 现代优化：每个 CPU 有"本地缓存"，进一步降低锁竞争

**现代映照**：x64 Windows 的池分配器机制与 ReactOS 基本一致，但有以下进化：

- **VBS/HVCI 强制**：NonPaged Pool 中的代码页必须签名（防止驱动注入 shellcode 到内核）
- **Kernel Data Protection（KDP）**：某些敏感池内存受安全内核保护，普通内核无法篡改
- **Pool 随机化**：池内存布局随机化，防止池溢出攻击

工业界：池分配器是**内核漏洞利用的主要战场**：

- **Pool Overflow**：经典的内核漏洞利用手法，溢出池对象改写相邻对象
- **Use-After-Free**：池对象释放后被重用，配合堆喷（heap spray）控制内容
- **防御**：现代 Windows 引入了池内存的 **"隔离分配"（Isolated Pool）**​ 和 **"类型隔离"（Type Isolation）**，不同类型的池对象放在不同区域，防止跨类型溢出

```
用户态                              内核态
──────                              ──────
VirtualAlloc                        
  ↓                                  
ntdll!NtAllocateVirtualMemory       
  ↓ syscall                         
═══════════════════════════════════════════════════════════
                                     NtAllocateVirtualMemory
                                            ↓
  ┌─────────────────────────────────────────────────────┐
  │ ① VAD 树（虚拟地址层）                              │
  │    EPROCESS.VadRoot → AVL 树                        │
  │    [0x00400000, 0x00500000) Reserved+Committed      │
  └─────────────────────────────────────────────────────┘
                                            ↓
  ┌─────────────────────────────────────────────────────┐
  │ ② PFN 数据库（物理页层）                             │
  │    Zeroed/Free/Standby/Modified/Bad 链表            │
  │    从 Zeroed 链表摘一页                              │
  └─────────────────────────────────────────────────────┘
                                            ↓
  ┌─────────────────────────────────────────────────────┐
  │ ③ PTE（映射层）                                    │
  │    Va → PTE → PFN → 物理页                         │
  │    必要时通过 Hyperspace 临时映射访问 PTE 本身       │
  └─────────────────────────────────────────────────────┘
                                            ↓
                                    返回用户态
                                    
  ─── 后续访问虚拟地址 ─────────────────────────────────────
  
  CPU 访问 Va → PTE.Present=0 → #PF → KiTrap0E
    → MmArmAccessFault
    → Demand Zero Fault：从 Zeroed 链表摘页、清零、设 PTE
    → 或 Page File Fault：从 pagefile.sys 读回
    → 或 CoW Fault：分配新页、复制、改 PTE
    → 或 Prototype PTE Fault：通过 Section 找到共享物理页
```

**这张图揭示了第3章的真正主线**：

1. **3.1 讲的是"三层结构的静态搭建"**：VAD（虚拟地址账本）、PFN（物理页账本）、PTE（映射桥梁）、Hyperspace（修桥的脚手架）、系统空间（内核自己的账本）
2. **3.2 讲的是"三层结构的动态兑现"**：缺页异常触发时，三层结构被"即时缝合"——VAD 找到区间、PFN 分配物理页、PTE 建立映射
3. **3.3 讲的是"物理页层的回收"**：当内存紧张，PFN 链表上的页被搬到 Standby/Modified，必要时写回 pagefile
4. **3.4 讲的是"物理页层的共享"**：Section 让多个进程的 PTE 通过 Prototype PTE 指向同一物理页
5. **3.5 讲的是"内核空间自己的三层结构"**：池分配器是内核组件使用的"精简版 NtAllocateVirtualMemory"

## 工业界实际应用补充

**🔐 安全领域**

- **EDR 对内存分配的监控**：现代 EDR（CrowdStrike、Carbon Black、Microsoft Defender for Endpoint）通过 ETW 事件 `VirtualAlloc`/`VirtualAllocEx`/`NtAllocateVirtualMemory` 监控异常内存分配——特别是 `PAGE_EXECUTE_READWRITE` 属性的分配、非空基址的分配（可能是 Process Hollowing）
- **Direct Syscall 绕过**：红队直接用 `syscall` 指令调用 `NtAllocateVirtualMemory`，绕过 ntdll 的 Hook。防御方改用 **"内核回调"**（ObRegisterCallbacks、PsSetCreateProcessNotifyRoutine）在 `NtAllocateVirtualMemory` 的内核路径上埋点
- **VBS/HVCI 的内核保护**：基于虚拟化的安全把敏感内核数据结构放到 VTL1（安全内核）隔离，普通内核（VTL0）无法篡改。HVCI 强制所有内核代码签名验证，阻断未签名驱动加载
- **KDP（Kernel Data Protection）**：把敏感内核数据（如 PFN 数据库的关键字段）设为只读，防止 rootkit 篡改

**⚙️ 性能工程**

- **Working Set Tuning**：通过 `SetProcessWorkingSetSize` 调整进程工作集大小，直接影响 3.3 的换出行为
- **Large Page 使用**：数据库、Java 虚拟机等内存密集型应用启用 Large Page（2MB/1GB），减少 PTE 数量、降低 TLB miss
- **NonPaged Pool 泄漏排查**：驱动开发中 NonPaged Pool 泄漏是常见 bug，通过 `!poolused` 命令（WinDbg）排查 Tag 对应的泄漏点
- **Memory Compression**：Windows 8.1+ 的压缩存储机制，比 pagefile 读写快一个数量级

**🛠️ 驱动开发**

- **ExAllocatePoolWithTag 的正确使用**：驱动中分配内存必须用带 Tag 的版本（如 `'MyDr'`），便于排查泄漏
- **IRQL 与池类型匹配**：<= DISPATCH_LEVEL 才能用 Paged Pool；更高的 IRQL 只能用 NonPaged Pool
- **MmProbeAndLockPages**：直接 I/O 操作中，必须将用户态缓冲锁到物理内存，防止访问时被换出
