
第5章是整本书的"成人礼"。前面四章你分别学了"系统调用之门"（第2章）、"内存怎么造"（第3章）、"对象怎么管"（第4章）——这一章把这三件事**揉成一个能跑起来的实体**：进程是资源的容器，线程是执行的实体，调度器决定谁上 CPU，APC 决定异步事件怎么投递。整章 5.1~5.14 就是 NT 内核"活"起来的全过程。

我的核心洞见先抛在前面：**进程与线程设计的本质，是把"资源所有权"和"执行流"彻底解耦**。进程拥有地址空间、句柄表、访问令牌——但不执行；线程拥有上下文、栈、优先级、APC 队列——但不拥有资源。调度器调度的不是进程而是线程，对象管理器管理的不仅是进程/线程对象本身还有其它对象，跨进程操作本质上就是"线程 A 拿着句柄去碰进程 B 的资源"。理解了这个解耦，整章 14 节就连成了一条主线。

> 💡 读这一章的正确姿势：把"进程创建"想象成盖楼——NtCreateProcess 是打地基、立框架（EPROCESS + 地址空间），NtCreateThread 是装修入住（ETHREAD + 栈 + 上下文）；把"调度"想象成物业调度——32 个优先级就是 32 条候梯队列，KiSwapContext 就是电梯换人的那一瞬间；把"APC"想象成快递柜——投递时不在家（线程忙），回家时（线程回到可警告状态）才取件。

## 5.1 概述

**书的脉络**：NT 内核中进程和线程在微内核层和执行体层上都有对应的数据结构——进程对象 KPROCESS 提供了线程的基本执行环境（地址空间和公用参数），线程对象 KTHREAD 提供了为参与线程调度所必需的各种信息；执行体层则是 EPROCESS 和 ETHREAD，它们不仅内嵌了内核层对象，还包含了更多涉及进程与线程管理的信息。PspCidTable 是系统范围的全局句柄表，PID/TID 是它的索引，PsLookupProcessByProcessId 就是从这里查 EPROCESS 指针。

**我的洞见——"进程是容器，线程是灵魂"不是比喻，是数据结构事实**：

EPROCESS 内嵌 KPROCESS 作为第一个字段，ETHREAD 内嵌 KTHREAD 作为第一个字段。这意味着：

- **KPROCESS/KTHREAD 是"调度器视角"**：只关心和 CPU 调度相关的信息（优先级、亲和性、时间片、栈指针、状态）。HAL 和调度器只认这两个结构
- **EPROCESS/ETHREAD 是"执行体视角"**：在 K 层结构基础上扩展出对象管理、安全令牌、句柄表、Section 映射、创建时间等执行体层信息

这个分层不是偶然。它意味着**调度器可以完全不关心"进程是什么对象"**——它只看 KTHREAD。这也解释了为什么 NT 内核的调度单位是线程而非进程：调度器的输入就是 KTHREAD 队列，跟 EPROCESS 无关。

> 📌 **PspCidTable 是被严重低估的关键结构**：它不是某个进程的私有句柄表，而是全局的"PID/TID → EPROCESS/ETHREAD"映射表。任何内核代码想通过 PID 找到进程对象，都走 `PsLookupProcessByProcessId` → `ExMapHandleToPointer(PspCidTable, Pid)`。这是跨进程操作、进程枚举、Rootkit 隐藏（抹掉 PspCidTable 中的条目）的核心战场。

**现代映照**：现代 Windows 10/11 的 EPROCESS/ETHREAD 结构远比书里丰富（加入了 VBS 相关字段、Mitigation 标志、Timing 信息等），但**"KPROCESS 内嵌于 EPROCESS 头部、KTHREAD 内嵌于 ETHREAD 头部"的布局一字未改**。你在 WinDbg 里 `dt nt!_EPROCESS` 和 `dt nt!_KPROCESS` 就能看到这种继承关系。PspCidTable 依然是全局 CID 表，Process Explorer 的进程枚举、Task Manager 的 PID 解析都依赖它。

## 5.2 Windows 进程的用户空间

**书的脉络**：每个进程有独立的用户空间（x86 下 0x00000000~0x7FFFFFFF）。典型布局（从低到高）：

- **NULL 指针保护区**（0x00000000 附近 64KB）：故意留空，捕获空指针解引用
- **PE 映像基址**（默认 0x00400000）：exe 映像
- **堆区**：多个堆（进程堆 + CRT 堆 + 自定义堆）
- **DLL 映像区**：各 DLL 加载地址
- **线程栈**：每个线程一个栈（默认 1MB）
- **TEB 区**：每个线程一个 TEB
- **PEB 区**（0x7FFDF000 附近）：进程环境块
- **环境变量、命令行参数、堆句柄等**

**我的洞见——用户空间布局是"静态框架 + 动态填充"的结合**：

静态部分是 Windows 子系统规定的"地址空间契约"：NULL 保护区、PEB 位置、DLL 加载区间（0x10000000~0x7FFFFFFF 的上半部分）都是固定的。动态部分是各进程实际加载的模块、分配的堆、创建的线程栈——这些通过 VAD 树（第3章）记录。

> 💡 **PEB 和 TEB 是进程/线程的"用户态化身"**：内核态有 EPROCESS/ETHREAD，用户态对应物就是 PEB/TEB。fs/gs 段寄存器在用户态指向 TEB，内核通过 `KeGetCurrentThread()->Teb` 快速访问。这种设计让用户态代码（如 ntdll 的堆管理、Rtl 系列函数）能在不进内核的情况下访问自己的上下文。

**现代映照**：x64 下用户空间扩展到 128TB，但布局思想一致。现代 Windows 引入了：

- **ASLR**（地址空间随机化）：每次启动 PE 映像基址、DLL 基址、堆基址、栈基址都随机化
- **High-Entropy ASLR**：x64 下提供 1TB 随机化空间，极大提高暴力破解难度
- **CFG**（Control Flow Guard）：在用户态间接调用前验证目标地址合法性

工业界：理解用户空间布局是**逆向工程和漏洞利用的基础**。Shellcode 注入、Process Hollowing、DLL Hijacking 全都是在用户空间的"动态填充"区域做手脚。

## 5.3 系统调用 NtCreateProcess()

**书的脉络**：NtCreateProcess 只是"在内核中创建该进程的 EPROCESS 数据结构并为其建立起地址空间"——这只是个空壳架子，实际调用链：

```
CreateProcessInternalW
  ↓
解析命令行、打开可执行文件、创建 Section 对象
  ↓
ntdll!NtCreateProcess → syscall
  ↓
ntoskrnl!NtCreateProcess → PspCreateProcess
  ├─ 创建 EPROCESS 对象（ObCreateObject）
  ├─ 创建地址空间（MiCreateProcessAddressSpace）
  ├─ 初始化 KPROCESS
  ├─ 设置安全令牌（从父进程继承）
  ├─ 初始化句柄表
  ├─ 映射 Section 到地址空间（映像文件映射）
  ├─ 分配 PID
  ├─ 创建 PEB
  ├─ 将进程挂入 ActiveProcessLinks
  └─ 返回进程句柄
```

关键点：**NtCreateProcess 只创建"空壳"进程，没有线程就谈不上运行**。后续还要调用 NtCreateThread 创建主线程，进程才能真正开始执行。

**我的洞见——NtCreateProcess 的本质是"资源容器的实例化"**：

这一节揭示了一个第一性原理：**进程创建 = 资源所有权初始化 + 地址空间搭建**。它做的一切事情都是在"准备环境"：

- EPROCESS 是资源所有权的载体（句柄表、令牌、Section 引用）
- 地址空间是资源访问的基础（页表、VAD 树、工作集）
- PEB 是用户态的"资源清单"（堆句柄、DLL 列表、环境变量）

但**没有执行流**——没有线程，调度器无事可做，进程只是 ActiveProcessLinks 链表上的一个节点。

> ⚠️ **NtCreateProcess vs CreateProcess**：CreateProcess 是用户态 Win32 API，它内部依次调用 NtCreateProcess + NtCreateThread + 一系列 Nt* 调用，最后 Resume 主线程。NtCreateProcess 单独调用只能得到一个"僵尸进程"——有 EPROCESS 但没有 ETHREAD。

**现代映照**：现代 Windows 的进程创建路径与此一致，但增加了：

- **PPL（Protected Process Light）**：通过划分进程保护级别，防止恶意代码攻击受保护进程
- **Mitigation 标志**：进程创建时通过 `NtCreateUserProcess` 的 Attribute 列表传入 Mitigation 策略（CFG、ACG、BlockDLL 等）
- **VBS 下的安全进程**：当进程属于 VTL1 安全域时，PspInsertThread 会调用 VslCreateSecureThread 在安全内核创建对应的安全线程

工业界：现代 EDR 通过 `PsSetCreateProcessNotifyRoutineEx` 注册进程创建回调，在进程"空壳"刚创建时就介入——这时可以修改句柄权限、注入 DLL、设置 Mitigation。Magniber 勒索软件等恶意代码通过直接 syscall 调用 `NtCreateProcess`/`NtCreateThreadEx` 绕过用户态 Hook。

## 5.4 系统调用 NtCreateThread()

**书的脉络**：NtCreateThread 的核心调用链：

```
kernel32!CreateThread / CreateRemoteThread
  ↓
ntdll!NtCreateThread → syscall
  ↓
ntoskrnl!NtCreateThread → PspCreateThread
  ├─ 参数校验
  ├─ 解析进程句柄（可为别的进程！）
  ├─ 创建 ETHREAD 对象
  ├─ 初始化 ETHREAD 字段
  ├─ 创建内核栈
  ├─ 初始化 KTHREAD
  ├─ 创建用户栈（InitialTeb 指定）
  ├─ 设置线程上下文（ThreadContext 指定初始寄存器）
  ├─ 分配 TID
  ├─ 插入线程链表（EPROCESS.ThreadListHead）
  ├─ 设置调度参数（优先级等）
  ├─ 创建 TEB
  ├─ 插入 PspCidTable
  └─ 返回线程句柄
```

**关键参数解读**：

- **ProcessHandle**：已打开进程对象的句柄。这意味着 **NtCreateThread 可以为别的进程创建线程**——这是 CreateRemoteThread、NtCreateThreadEx 的底层原语
- **CreateSuspended**：是否一出生就挂起，等待 NtResumeThread 才运行
- **ThreadContext**：指向一个 CONTEXT 结构，规定新线程降生之初各寄存器的值
- **InitialTeb**：指定新线程用户空间堆栈的位置

**我的洞见——NtCreateThread 是"执行流的实例化"**：

与 NtCreateProcess 对应，NtCreateThread 做的是"让进程活起来"：

- ETHREAD 是执行流的载体（所属进程、TID、起始地址、创建时间）
- 内核栈 + 用户栈是执行流的"工作台"
- ThreadContext 是执行流的"初始姿态"——EIP 指向线程入口，ESP 指向栈顶
- TEB 是执行流的"用户态身份证"

> 📌 **ProcessHandle 参数的深层含义**：NtCreateThread 可以为任意有 PROCESS_CREATE_THREAD 权限的进程创建线程。这是 NT 内核"执行流与资源容器解耦"的直接体现——线程不必属于创建它的进程。这也是远程线程注入（Remote Thread Injection）的底层机制：OpenProcess → NtCreateThread(ProcessHandle=目标进程) → 线程在目标进程地址空间执行。

**现代映照**：现代 Windows 的 NtCreateThread 演变为 NtCreateThreadEx，增加了：

- **ThreadFlags**：指定线程属性（如 THREAD_CREATE_FLAGS_HIDE_FROM_DEBUGGER）
- **Mitigation 标志**：新线程继承进程的 Mitigation 策略
- **VBS 安全线程**：若目标进程是安全进程，创建的是 VTL1 安全线程

工业界：Magniber 勒索软件等的注入链：

```
NtOpenProcess → NtAllocateVirtualMemory → NtWriteVirtualMemory →
NtProtectVirtualMemory → NtCreateThreadEx → NtResumeThread
```

全程使用直接 syscall 绕过 EDR Hook。现代 EDR 通过 ObRegisterCallbacks 监控线程句柄的创建，特别是跨进程创建线程的操作。

## 5.5 Windows 的可执行程序映像

**书的脉络**：PE（Portable Executable）文件格式是 Windows 的可执行映像标准。关键结构：

- **DOS Header**（`MZ` 开头）：兼容 DOS，e_lfanew 指向 NT Header
- **NT Header**：包含 File Header（机器类型、节数）和 Optional Header（映像基址、入口点、节对齐、数据目录）
- **Section Table**：`.text`(代码)、`.data`(已初始化数据)、`.rdata`(只读数据)、`.pdata`(异常处理)、`.rsrc`(资源)等
- **Data Directories**：导出表、导入表、资源表、重定位表、调试信息、TLS 目录、加载配置等

**我的洞见——PE 格式是"进程与文件系统之间的契约"**：

当 CreateProcess 打开 exe 文件并创建 Section 对象时，内存管理器并不立即把整个文件读入内存，而是**建立文件到虚拟地址空间的映射**（第3章 3.4 节 Section 机制）。PE 文件的各个 Section 对应 VAD 树上的不同区间，各有不同的保护属性（PAGE_EXECUTE_READ 对应 `.text`，PAGE_READWRITE 对应 `.data` 等）。

> 💡 **这就是"按需分页"在可执行文件上的应用**：进程启动时，只有 PE Header 和少量代码页被加载。当执行流首次触及某个尚未加载的 Section 时，触发缺页异常，内存管理器从 Section 对应的文件偏移读入物理页（第3章 3.2 节）。

**现代映照**：现代 PE 格式增加了：

- **ASLR 支持**：Optional Header 中的 `DLLCharacteristics` 设置 `IMAGE_DLLCHARACTERISTICS_DYNAMIC_BASE` 标志
- **CFG 表**：Load Config Directory 中的 `_IMAGE_LOAD_CONFIG_CODE_INTEGRITY` 结构
- **数字签名**：通过 Security Directory 存储 Authenticode 签名

## 5.6 Windows 的进程创建和映像装入

**书的脉络**：完整的进程创建流程：

```
用户态 CreateProcessInternalW
  ↓
① 解析命令行、环境变量
② NtOpenFile 打开 exe
③ NtCreateSection 创建映像 Section
④ NtCreateProcess 创建 EPROCESS（空壳）
⑤ NtCreateThread 创建主线程
⑥ 主线程上下文：EIP = exe 入口点，ESP = 用户栈顶
⑦ NtResumeThread 恢复主线程
  ↓
调度器选中主线程
  ↓
主线程开始在用户态执行
  ↓
ntdll!_LdrInitializeThunk（LdrpInitialize）
  ↓
加载 ntdll.dll 的其他部分
  ↓
LdrpRunInitializeRoutines：遍历 IAT，加载所有隐式 DLL
  ↓
调用 exe 的入口点（main/WinMain）
```

**我的洞见——进程创建是"两阶段引导"**：

第一阶段（内核）：NtCreateProcess + NtCreateThread 创建"骨架"——EPROCESS + ETHREAD + 地址空间 + PEB。此时进程是"死的"，主线程处于 Suspended 状态。

第二阶段（用户态）：主线程被 Resume 后，从 ntdll 的 `_LdrInitializeThunk` 开始执行——这是 NT 用户态的"引导加载程序"。它负责：

- 初始化 PEB 中的加载器数据
- 遍历 exe 的导入表（Import Address Table），对每个 DLL 调用 `LdrpLoadDll`
- 每个 DLL 的 `DllMain(DLL_PROCESS_ATTACH)` 被调用
- 最后跳到 exe 的 `main/WinMain`

> 📌 **`_LdrInitializeThunk` 是用户态的"内核入口"**：类比 KiSystemService 是用户态进入内核态的门，_LdrInitializeThunk 是新进程从"内核态创建"过渡到"用户态执行"的门。理解它就理解了"进程是怎么从内核走出来跑到用户态的"。

**现代映照**：现代 Windows 的进程创建路径增加了：

- **AppContainer**：UWP 应用和 Edge 浏览器沙箱使用 AppContainer SID 隔离
- **Job Objects**：将进程分组管理，统一限制 CPU、内存等资源
- **VBS 下的安全进程创建**：若进程属于 VTL1 安全域，PspInsertThread 调用 VslCreateSecureThread 在安全内核创建关联的安全线程

工业界：Process Hollowing（进程镂空）攻击正是在这一阶段做手脚——创建 Suspend 状态的进程后，Unmap 原始 exe 的 Section，Map 入恶意代码，修改主线程上下文的 EIP，Resume。整个过程从外部看是一个正常的 svchost.exe，但执行的是恶意代码。

## 5.7 Windows DLL 的装入和连接

**书的脉络**：DLL 加载的完整流程：

```
LdrpLoadDll → LdrpFindOrMapDll
  ↓
① 检查是否已加载（LdrpHashTable 查找）
② 若未加载：LdrpMapDll（NtCreateSection + NtMapViewOfSection）
③ 解析 DLL 的导入表，递归加载依赖 DLL
④ 对 DLL 的每个 Section 建立映射（代码段 PAGE_EXECUTE_READ，数据段 PAGE_READWRITE）
⑤ 处理重定位（若 DLL 未加载到首选基址）
⑥ 处理绑定导入（Bound Import）
⑦ 调用 DllMain(DLL_PROCESS_ATTACH)
⑧ 将 DLL 加入 PEB.Ldr 的 InMemoryOrderModuleList
```

**我的洞见——DLL 加载是"Section + 重定位 + 重绑"三重奏**：

1. **Section 映射**：DLL 文件通过 Section 对象映射到进程地址空间（复用第3章 3.4 节机制）。多个进程加载同一 DLL 时，物理内存中只有一份代码页，所有进程的 PTE 都指向它（通过 Prototype PTE 共享）
2. **重定位**：如果 DLL 的首选基址（Optional Header 中的 ImageBase）被占用，加载器需要通过重定位表（Relocation Table）修改代码中对绝对地址的引用。这是一个**开销极大的操作**——每个重定位项都要改写 4/8 字节
3. **导入绑定**：Bind 技术预先解析 DLL 的导出函数地址，写入 IAT（Import Address Table），避免运行时解析。但 ASLR 普及后，Bind 技术基本失效——每次加载地址都不同，必须运行时解析

> ⚠️ **DLL 加载顺序劫持（DLL Search Order Hijacking）**：Windows 默认按 `应用程序目录 → 系统目录 → 16位系统目录 → PATH 环境变量目录 → 当前目录` 顺序查找 DLL。攻击者如果在应用程序目录下放置同名恶意 DLL，就会被优先加载。这是 Windows 平台最经典的持久化/提权手法之一。

**现代映照**：现代 Windows 的 DLL 加载机制增加了：

- **Known DLLs**：`HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\KnownDLLs` 注册表中列出的 DLL 从系统目录预映射，防止劫持
- **CFG 验证**：每次间接调用前验证目标地址是否在合法 DLL 的范围内
- **ACG（Arbitrary Code Guard）**：禁止从数据页生成可执行页，终结 JIT 喷射和 DLL 注入
- **Code Integrity Guard（CIG）**：进程可设置 CIG 标志，只允许加载签名的 DLL

工业界：DLL 劫持检测是 EDR 的标配能力。现代 EDR 通过 `ObRegisterCallbacks` 监控 Section 对象的创建（特别是 `SEC_IMAGE` 类型的 Section），可以识别异常 DLL 加载行为。

## 5.8 Windows 的 APC 机制

**书的脉络**：APC（Asynchronous Procedure Call，异步过程调用）允许内核或用户态代码将一个函数投递到指定线程，使其在特定时机执行。APC 的分类：

- **内核模式特殊 APC**：在 IRQL=APC_LEVEL 执行，会抢先所有用户模式和 PASSIVE_LEVEL 内核模式代码。KernelRoutine 必须提供，NormalRoutine 为空
- **内核模式常规 APC**：在所有特殊 APC 执行完后，IRQL=PASSIVE_LEVEL 执行。用于文件系统
- **用户模式 APC**：APC 函数在用户空间执行。**只有当线程处于 alertable 状态时才能被调度执行**

APC 投递流程：

```
KeInitializeApc → 初始化 KAPC 对象
  ↓
KeInsertQueueApc → KiInsertQueueApc
  ↓
KAPC 插入 KTHREAD.ApcState.ApcListHead[0/1] 队列
  ↓
当线程回到可警告状态（alertable wait）/ 从内核返回用户态时
  ↓
KiDeliverApc 派发 APC
  ↓
执行 KernelRoutine（内核态）→ NormalRoutine（用户态/内核态）
```

**我的洞见——APC 是 NT 内核"异步世界观"的粘合剂**：

NT 内核是**全面异步**的。I/O 是异步的、对象是异步的、线程调度是异步的。APC 就是连接"内核异步完成"和"线程同步假象"的桥。

> 💡 **用户 APC 为什么必须 alertable？**​ 因为用户 APC 会打断线程当前的执行流。如果线程正在做关键计算，突然跳去执行一个 APC 函数，可能导致数据不一致。所以 NT 内核规定：只有当线程**主动**进入可警告等待（如调用 `SleepEx`、`WaitForSingleObjectEx` 等 Ex 后缀函数）时，才允许执行用户 APC。这是一种"协作式异步"。

**APC 的典型应用**：

- **I/O 完成**：I/O 管理器完成 IRP 时，构造一个内核 APC 插入发起 I/O 的线程。APC 执行时把 IO_STATUS_BLOCK 从内核拷贝到用户态，如果用户提供了完成例程，再构造一个用户 APC
- **定时器**：定时器到期时，内核 APC 唤醒等待的线程
- **线程终止**：TerminateThread 通过 APC 强制目标线程在合适时机终止
- **跨线程操作**：`QueueUserAPC` 就是 NtQueueApcThread 的用户态封装

**现代映照**：现代 Windows 的 APC 机制与此一致，但在 VBS 环境下，某些 APC 可能涉及安全内核的验证。APC 仍是 I/O 完成端口（IOCP）、异步 RPC、ALPC 等现代 IPC 机制的底层基础。

工业界：APC 注入是经典的免杀技术——`OpenProcess` → `VirtualAllocEx` → `WriteProcessMemory` → `QueueUserAPC`。由于 APC 注入不创建新线程（规避了线程注入检测），且 APC 执行时机不确定（规避了行为分析），长期是恶意软件的优选。现代 EDR 通过监控 `NtQueueApcThread` 的调用、特别是跨进程 QueueUserAPC 来检测这种攻击。

## 5.9 Windows 线程的调度和切换

### 5.9.1 x86 系统结构与线程切换

**书的脉络**：x86 下线程切换通过 `KiSwapContext` 完成。核心汇编操作：

```
pushad                          ; 保存所有通用寄存器到旧线程内核栈
mov [OldThread.KernelStack], esp  ; 保存旧线程栈指针
; ... FPU/NPX 状态处理
mov esp, [NewThread.KernelStack]   ; 切换到新线程栈
popad                           ; 恢复新线程寄存器
mov cr3, [NewProcess.DirBase]   ; 切换页表（若进程不同）
; ... 返回新线程
```

**我的洞见——线程切换的本质是"栈切换 + 页表切换"**：

CPU 执行什么代码，取决于 CS:EIP；访问什么数据，取决于 SS:ESP 和 CR3。所以线程切换的核心：

1. **保存旧线程寄存器到旧线程内核栈**（pushad）
2. **切换到新线程内核栈**（esp 赋值）
3. **如果新旧线程所属进程不同，切换页表**（mov cr3）——这就是"进程切换"
4. **恢复新线程寄存器**（popad）

> 📌 注意：**"进程切换"不是独立的操作，而是"线程切换"的附属品**。当两个线程属于不同进程时，线程切换的同时顺便切换了 CR3。这再次印证了"调度单位是线程"的设计哲学。

### 5.9.2 几个重要的数据结构

**书的脉络**：

- **KTHREAD**：调度器视角的线程。关键字段：State（运行/就绪/等待）、Priority、BasePriority、Affinity、Quantum、KernelStack、ApcState、WaitBlock
- **KPROCESS**：调度器视角的进程。关键字段：Affinity、BasePriority、Quantum
- **KPRCB**（Processor Control Block）：每 CPU 一个，记录该 CPU 的调度状态。关键字段：CurrentThread、NextThread、DispatcherReadyListHead[32]（32 个优先级就绪队列）、WaitListHead、DeferredReadyListHead
- **CONTEXT**：线程的寄存器上下文

**我的洞见——KPRCB 是"每 CPU 的调度中枢"**：

现代多核系统下，**调度器是 per-CPU 的**。每个 CPU 有自己的 KPRCB，自己的就绪队列，自己的当前线程。这避免了全局锁竞争——每个 CPU 独立调度自己的线程。

> 💡 **32 个就绪队列的设计**：Windows 线程优先级 0~31，每个优先级一条双向链表。KPRCB.DispatcherReadyListHead[32] 就是这个数组。调度时从优先级 31 向下找第一个非空队列，O(1) 时间复杂度。

### 5.9.3 线程的切换

**书的脉络**：线程切换的触发时机：

1. **主动让出**：线程调用 `KeWaitForSingleObject`、`KeDelayExecutionThread`、`NtYieldExecution` 等
2. **时间片到期**：时钟中断触发 `KiQuantumEnd`，当前线程时间片耗尽
3. **有更高优先级线程就绪**：中断/异常/DPC 中唤醒了更高优先级线程
4. **线程被抢占**：更高优先级线程变为就绪，当前线程被抢占

所有路径最终都走到 `KiSwapThread → KiSwapContext`。

**我的洞见——抢占式调度的"原子性保证"**：

线程切换必须在 **DISPATCH_LEVEL**​ 以上 IRQL 进行。原因：切换线程时需要修改 KPRCB.CurrentThread 等全局结构，如果此时被中断，数据会不一致。所以：

- 时钟中断在 DIRQL 触发，Interrupt Handler 提升到 DISPATCH_LEVEL
- DPC（Delayed Procedure Call）在 DISPATCH_LEVEL 执行，其中做调度决策
- KiSwapContext 在 DISPATCH_LEVEL 完成切换

> ⚠️ **这就是为什么 DISPATCH_LEVEL 以上不能访问分页内存**：因为此时调度器可能被抢占，如果访问分页内存触发缺页，而缺页处理又需要调度器——死锁。

### 5.9.4 线程的调度

**书的脉络**：Windows 采用**基于优先级的抢占式多级反馈队列**调度策略：

- **实时优先级（16-31）**：用于时间关键任务，优先级不会被动态提升
- **动态优先级（1-15）**：普通应用程序线程，I/O 完成后优先级临时提升
- **系统优先级（0）**：零页线程（Zero Page Thread）

调度算法核心：

```
KiFindReadyThread:
  for i = 31 downto 0:
    if DispatcherReadyListHead[i] 非空:
      return 该队列第一个线程
```

优先级动态提升场景：

- **I/O 完成**：等待 I/O 的线程完成 I/O 后，优先级提升 1~2 级（避免 I/O 密集型线程饿死）
- **前台进程**：Windows 动态调整前台进程的优先级，提升用户界面响应性
- **长时间运行**：连续运行超过一定时间片的线程，优先级逐渐降低（防饿死）

**我的洞见——调度器的第一性原理是"优先级 + 时间片 + 动态反馈"**：

静态优先级保证"重要任务先执行"，时间片保证"公平性"，动态优先级提升保证"I/O 密集型任务响应性"。三者结合，形成了一个既能跑实时任务、又能公平调度普通任务的混合调度器。

> 📌 **Quantum（时间片）的精妙之处**：默认时间片约 2 个时钟中断间隔（约 120ms）。但前台进程的时间片是后台进程的 2 倍——这是 Windows 桌面响应性的关键设计。

**现代映照**：现代 Windows 调度器增加了：

- **NUMA 感知**：调度器优先在本地 NUMA 节点上分配线程，减少跨节点内存访问
- **节能调度**：根据 CPU 负载动态关闭核心
- **VBS 下的安全线程调度**：安全内核本身没有专有调度器，完全依赖普通 NT 内核调度

工业界：理解调度器是性能调优的基础。任务管理器"设置优先级"、Process Explorer"设置亲和性"、Job Object 的 CPU 限制，全都是在与这个调度器对话。

## 5.10 线程和进程的优先级

**书的脉络**：

- **进程 BasePriority**：进程创建时从父进程继承，范围 0~31。它影响进程内线程的初始优先级
- **线程 BasePriority**：线程创建时从进程 BasePriority 继承，可被 `SetThreadPriority` 调整（-2 ~ +2 相对进程 BasePriority）
- **线程 CurrentPriority**：实际调度用的优先级，可在 BasePriority 基础上动态提升
- **IRQL vs 线程优先级**：IRQL 是 CPU 当前硬件优先级，线程优先级是软件调度优先级。高 IRQL 代码会抢占低 IRQL 代码，与线程优先级无关

**我的洞见——优先级是"分层"的**：

```
IRQL（硬件层）：PASSIVE_LEVEL < APC_LEVEL < DISPATCH_LEVEL < DIRQL
  ↓ 在 PASSIVE_LEVEL 才有线程调度
线程优先级（软件层）：0~31
  ↓ 线程在用户态运行
进程 BasePriority（资源分配层）：决定线程优先级的基准
```

这三层优先级是正交的：

- IRQL 决定"当前 CPU 在做什么"（硬件中断 > DPC > 线程）
- 线程优先级决定"哪个线程上 CPU"
- 进程 BasePriority 决定"线程优先级的基准线"

> ⚠️ **常见误解**：很多人以为"实时优先级线程（16-31）能抢占一切"。错。实时优先级线程只能抢占其他线程，不能抢占 DPC 和硬件中断。如果你的实时线程需要做微秒级精确操作，必须同时考虑 IRQL。

**现代映照**：现代 Windows 的优先级模型一致。多媒体应用、游戏引擎、实时音频处理都依赖实时优先级线程。但 Windows 引入了 **Priority Boosting 的限制**——为了防止优先级反转和饿死，系统会定期"衰减"被提升的优先级。

## 5.11 线程本地存储 TLS

**书的脉络**：TLS（Thread Local Storage）让每个线程拥有变量的独立副本。两种实现：

- **静态 TLS**：`__declspec(thread)` 声明的变量，编译时在 PE 文件中分配 `.tls` 段。每个线程创建时，加载器从 `.tls` 段复制初始值到线程的 TLS 区域
- **动态 TLS**：`TlsAlloc`/`TlsGetValue`/`TlsSetValue`，通过 TEB 中的 `TlsSlots` 数组（默认 64 个槽位）实现

**我的洞见——TLS 是"线程私有全局变量"的优雅实现**：

全局变量的问题是"所有线程共享"。但很多场景下，我们需要"每个线程有独立副本的全局变量"——如 errno、C 运行时库的线程私有状态、COM 的 Apartment 状态。

TLS 的实现机制：

- **静态 TLS**：TEB 中有一个指向 TLS 数组的指针。`.tls` 段的内容在模块加载时复制到每个线程的 TLS 区域。访问 `__declspec(thread)` 变量时，编译器生成 `mov eax, fs:[0x2C]`（TEB.TlsPointer）→ 加上偏移访问
- **动态 TLS**：`TlsAlloc` 返回一个槽位索引，`TlsGetValue` 通过 `TEB.TlsSlots[index]` 访问

> 💡 **fs/gs 段寄存器的关键作用**：在 x86 上，fs 寄存器指向 TEB；在 x64 上，gs 寄存器指向 TEB。这意味着**任何代码在任何线程中执行时，都能通过 fs/gs 立即访问当前线程的 TEB**——这是 TLS、异常处理、CRT 状态等所有"线程私有数据"的基础。

**现代映照**：现代 Windows 的 TLS 机制一致。C++11 `thread_local`、C# `[ThreadStatic]`、Java `ThreadLocal` 在 Windows 上都映射到 TLS 机制。Fls（Fiber Local Storage）是 TLS 的纤程版本。

## 5.12 进程挂靠

**书的脉络**：进程挂靠（Process Attach/KeAttachProcess）允许线程临时"借用"另一个进程的地址空间。典型场景：

- 调试器读写目标进程内存（Debugport 处理）
- 跨进程内存操作（如 `MmCopyVirtualMemory`）
- 系统线程访问用户进程地址空间

实现机制：

```
KeAttachProcess(Process):
  ├─ 保存当前线程的 ApcState 到 SavedApcState
  ├─ 切换 CR3 到目标进程的 DirBase
  ├─ 设置 KTHREAD.ApcStateIndex = 1（挂靠状态）
  └─ ApcStatePointer[0] 指向 SavedApcState，ApcStatePointer[1] 指向 ApcState

KeDetachProcess():
  ├─ 恢复 SavedApcState 到 ApcState
  ├─ 切换 CR3 回原进程
  ├─ 设置 ApcStateIndex = 0
  └─ ApcStatePointer[0] 指向 ApcState
```

**我的洞见——进程挂靠是"地址空间漫游"机制**：

线程原本属于进程 A（所属进程），但通过挂靠可以临时访问进程 B 的地址空间。这需要：

1. **CR3 切换**：让 MMU 把虚拟地址解析到 B 的页表
2. **APC 队列分离**：A 的 APC 队列存到 SavedApcState，B 的 APC 队列存到 ApcState（避免 APC 函数访问错误的地址空间）
3. **ApcStateIndex 标记**：标识当前处于挂靠状态

> ⚠️ **为什么 APC 队列要分离？**​ 因为 APC 函数是在线程所属进程的地址空间中执行的。如果线程挂靠到 B 进程，但 APC 队列里还有 A 进程的 APC 函数，执行时就会访问错误的地址空间。所以必须把 A 的 APC 队列"暂存"到 SavedApcState，挂靠期间只处理 B 的 APC。

**现代映照**：现代 Windows 的进程挂靠机制一致。跨进程操作（如 `NtReadVirtualMemory`、`NtWriteVirtualMemory`）的底层都使用进程挂靠。VBS 环境下，跨 VTL 的地址空间访问受到严格限制。

工业界：进程挂靠是**跨进程内存读写**的底层机制。OpenProcess → NtReadVirtualMemory 的调用链中，内核通过进程挂靠切换到目标进程地址空间，读取数据后切回。恶意软件利用同样的机制实现进程注入和隐蔽内存操作。

## 5.13 Windows 的跨进程操作

**书的脉络**：跨进程操作的核心原语：

- **NtOpenProcess**：获取目标进程的句柄（需要 PROCESS_QUERY_INFORMATION 或 PROCESS_ALL_ACCESS 等权限）
- **NtOpenThread**：获取目标线程的句柄
- **NtReadVirtualMemory / NtWriteVirtualMemory**：读写目标进程内存（需要 PROCESS_VM_READ/WRITE）
- **NtProtectVirtualMemory**：修改目标进程内存保护属性（需要 PROCESS_VM_OPERATION）
- **NtCreateThreadEx**：在目标进程创建线程（需要 PROCESS_CREATE_THREAD）
- **NtDuplicateObject**：复制跨进程句柄

**我的洞见——跨进程操作的本质是"句柄 + 权限 + 挂靠"三件套**：

1. **句柄**：通过 NtOpenProcess 获取目标进程的 HANDLE（第4章对象管理）
2. **权限**：句柄的 GrantedAccess 决定能做什么操作（PROCESS_VM_READ、PROCESS_CREATE_THREAD 等）
3. **挂靠**：实际读写内存时，通过 KeAttachProcess 切换到目标进程地址空间（5.12 节）

> 📌 **句柄权限是跨进程操作的"防火墙"**：即使你 OpenProcess 成功，如果句柄没有 PROCESS_VM_WRITE 权限，NtWriteVirtualMemory 也会失败。这就是为什么进程保护的核心是"在 Ob 回调中剥离危险权限"。

**现代映照**：现代 Windows 的跨进程操作受到多重限制：

- **PPL（Protected Process Light）**：受保护进程（如防病毒、Credential Guard）的句柄创建受到严格限制，即使是 Administrator 也无法获取 PROCESS_ALL_ACCESS
- **VBS/HVCI**：跨 VTL 的进程操作被安全内核拦截
- **ObRegisterCallbacks**：EDR 通过 Ob 回调监控和限制跨进程句柄创建
- **Mitigation 策略**：目标进程的 Mitigation 标志（如 BlockNonMicrosoftBinaries）限制跨进程线程创建

工业界：跨进程操作是攻防焦点。Magniber 勒索软件通过直接 syscall 调用 `NtOpenProcess` → `NtAllocateVirtualMemory` → `NtWriteVirtualMemory` → `NtProtectVirtualMemory` → `NtCreateThreadEx` → `NtResumeThread` 实现注入。现代 EDR 的防护策略：

- **Ob 回调拦截**：在 OnPreOpenProcess 中剥离 PROCESS_TERMINATE、PROCESS_VM_WRITE 等危险权限
- **进程创建回调**：PsSetCreateProcessNotifyRoutineEx 监控子进程创建
- **线程创建回调**：监控跨进程 NtCreateThreadEx

## 5.14 Windows 线程间的相互作用

**书的脉络**：线程间同步机制：

- **内核同步对象**：Event、Mutex、Semaphore、Timer（都是对象，通过 NtCreateEvent 等创建）
- **等待原语**：`KeWaitForSingleObject`、`KeWaitForMultipleObjects`——线程阻塞在这些原语上，进入 WaitListHead 队列
- **APC 唤醒**：线程在可警告等待时，用户 APC 可以唤醒它
- **DPC**：延迟过程调用，在 DISPATCH_LEVEL 执行，用于定时器、I/O 完成等

**我的洞见——线程相互作用的本质是"等待/唤醒"**：

线程间相互作用无非两种模式：

1. **共享状态 + 锁**：Event/Mutex/Semaphore 保护共享数据
2. **异步通知**：APC、DPC 实现"事件发生时不打扰线程当前工作，合适时机再处理"

> 💡 **为什么需要这么多同步原语？**​ 因为不同场景需要不同语义：
> 
> - **Event**：信号通知（一次性的或自动重置的）
> - **Mutex**：互斥访问（带所有权和优先级继承）
> - **Semaphore**：资源计数（允许多个线程同时访问）
> - **APC**：线程定向通知（特定线程执行特定函数）

**现代映照**：现代 Windows 线程同步机制一致，但增加了：

- **WaitChain Traversal**：检测死锁（通过 `WaitChainEngine` API）
- **SRW Lock**：轻量级读写锁，用户态实现，性能优于内核互斥体
- **Condition Variable**：条件变量，配合 SRW Lock 使用

工业界：死锁检测、竞态条件分析、线程 dump 分析是性能工程师的日常。理解 5.14 的同步机制是诊断"程序卡死"、"CPU 100%"、"内存泄漏"的基础。

## 全章串联：进程与线程的全景图

```
用户态                                   内核态
──────                                   ──────
CreateProcess()
  ↓
① 打开 exe → NtCreateSection
② NtCreateProcess → EPROCESS（空壳）
     ├─ KPROCESS（地址空间、亲和性）
     ├─ 句柄表、访问令牌
     ├─ PEB（用户态进程环境）
     └─ 挂入 ActiveProcessLinks
  ↓
③ NtCreateThread → ETHREAD（主线程）
     ├─ KTHREAD（优先级、状态、栈）
     ├─ 内核栈 + 用户栈
     ├─ TEB（用户态线程环境）
     ├─ 初始上下文（EIP=exe 入口）
     └─ 插入 PspCidTable
  ↓
④ NtResumeThread → 主线程进入就绪队列
  ↓
⑤ 调度器选中（KiFindReadyThread）
  ↓
⑥ KiSwapContext → CR3 切换 + 栈切换
  ↓
⑦ 主线程在用户态执行
  ↓
ntdll!_LdrInitializeThunk
  ↓
⑧ 加载 DLL（LdrpLoadDll 递归）
  ↓
⑨ 调用 exe 入口点（main/WinMain）
  ↓
⑩ 应用运行 → 创建更多线程
  ↓
⑪ 线程间通过 Event/Mutex/APC 同步
  ↓
⑫ 跨进程操作：OpenProcess + 挂靠 + 内存读写
```
