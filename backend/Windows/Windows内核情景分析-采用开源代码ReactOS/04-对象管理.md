
第4章是 NT 内核"一切皆对象"哲学的集中展现。读完第3章你知道了内核怎么管内存，这一章告诉你：**内核怎么管"一切"**——进程、线程、文件、事件、信号量、Section、驱动对象……统统是"对象"。

我的核心洞见先抛在前面：**对象管理的第一性原理，是用"句柄"这种不透明令牌，在"用户态的能力"和"内核态的资源"之间建立一道安全闸门**。句柄不是指针（直接给指针等于把内核地址空间交给用户态，一写就蓝屏），而是进程私有句柄表中的一个索引——索引背后才是真正的对象指针、访问掩码、继承标志。整章 4.1 到 4.9 都在讲这套"能力令牌"怎么造出来、怎么查、怎么复制、怎么销毁、怎么继承。

> 💡 读这一章的正确姿势：把对象管理器想象成一个"内核资源的派出所"——对象类型是户籍种类（人/车/房），对象目录是地址系统（`\ObjectTypes` 这种路径），句柄表是每个人的身份证本（进程私有），ObReferenceObjectByHandle 是"出示身份证换取实体"，NtClose 是"注销身份证"，NtDuplicateObject 是"办副卡"。

## 4.1 对象与对象目录

**书的脉络**：所有内核对象在内存中都有一个统一的 **OBJECT_HEADER**​ 头，位于对象体（如 EPROCESS、ETHREAD、KEVENT）之前（低位地址）。头部记录：引用计数、名称、安全描述符、类型指针、句柄计数等。对象可以被插入到**对象目录（Object Directory）**这棵全局名字树中，路径形如 `\ObjectTypes\Process`、`\Device\HarddiskVolume1`、`\Global??\C:`。

**我的洞见——OBJECT_HEADER 是"对象的多态基类"**：

NT 内核用 C 语言模拟了面向对象。所有对象"头部在低位、对象体在高位"——给定一个对象体指针 `p`，`p - 1`（或 `CONTAINING_RECORD` 反推）就能拿到 OBJECT_HEADER。这种设计有两个工程收益：

1. **统一处理**：对象管理器不需要知道对象体的具体类型，只看 OBJECT_HEADER 就能做引用计数、权限检查、名字查找
2. **类型分发**：OBJECT_HEADER 里存着 `TypeIndex`，指向全局的 OBJECT_TYPE 结构体，后者是一张"方法表"（创建/打开/关闭/删除/解析路径/安全复查）

对象目录则是**内核里的文件系统**——只不过挂的不是磁盘文件，而是对象。目录项本身也是对象（ObpDirectoryObjectType），形成递归的树结构。Hash 表加速查找（质数个桶减少碰撞，链头插入 LIFO）。

> 📌 **对象 vs 句柄的关键区别**：对象是全局的（所有进程可见，通过名字或继承句柄访问），句柄是进程私有的（每进程一张句柄表）。同一个对象可以被多个进程的句柄表项指向，这就是"跨进程共享内核对象"的本质。

**现代映照**：现代 Windows 10/11 的对象管理机制与 ReactOS 高度一致。你在 WinDbg 里用 `dt nt!_OBJECT_HEADER`、`dt nt!_OBJECT_TYPE` 看到的，就是书里讲的这些结构。对象目录依然挂在 ``\` 根下，可以通过``WinObj.exe`（Sysinternals 工具）可视化浏览——这是把书里抽象概念"看见"的最快方式。

工业界：对象目录是**安全软件监控的重点**。微软提供的 `ObRegisterCallbacks` 允许驱动注册"对象创建/打开"的回调，EDR 正是用这个机制监控进程/线程/桌面等敏感对象的打开操作——这是现代 Windows 取代"SSDTHook"的官方、稳定、PatchGuard 友好的监控方式。

## 4.2 对象类型

**书的脉络**：每种内核对象都有一个全局的 **OBJECT_TYPE**​ 结构体，在系统初始化时通过 `ObCreateObjectType` 注册。OBJECT_TYPE 相当于 C++ 的 vtable，记录了一组"方法指针"：

- **OpenProcedure**：打开对象时的回调
- **CloseProcedure**：句柄计数递减到 0 时调用（如 File 类型触发 IRP_MJ_CLEANUP，释放文件锁、取消重叠 I/O）
- **DeleteProcedure**：对象真正销毁时调用
- **ParseProcedure**：名字解析时的回调（最复杂的一种）
- **SecurityProcedure**：安全描述符操作
- **QueryNameProcedure**：查询对象名
- **OkayToCloseProcedure**：NtClose 之前的"最后一关"，返回 FALSE 可拒绝关闭

**我的洞见——OBJECT_TYPE 是 NT 内核"多态"的核心机制**：

这里揭示了一个深层设计哲学：**对象管理器对对象一无所知，它只负责"通用生命周期管理"（引用计数、句柄表、名字空间、权限检查），而把"类型相关的行为"通过 OBJECT_TYPE 的方法表委托出去**。

举个例子，`NtClose` 一个文件句柄时：

1. 对象管理器递减句柄计数
2. 如果句柄计数归零，调用 `OBJECT_TYPE.CloseProcedure`
3. 对于 File 类型，CloseProcedure 会向文件系统驱动发送 `IRP_MJ_CLEANUP`，释放文件锁、取消未完成的 I/O
4. 对象管理器再递减指针计数
5. 如果指针计数也归零，调用 `OBJECT_TYPE.DeleteProcedure` 真正释放对象内存

> 💡 **ParseProcedure 是最精妙的回调**：当解析路径 `\??\C:\foo.txt` 时，对象管理器走到 `\??` 这个符号链接对象，它的 ParseProcedure 把 `C:` 解析成 `\Device\HarddiskVolume1`；然后走到 HarddiskVolume1 这个 Device 对象，它的 ParseProcedure（由文件系统驱动注册）继续解析剩余的 `foo.txt` 路径。换句话说，**路径解析是"沿着对象链、逐个对象委托 ParseProcedure"的过程**——这是 NT 内核"一切皆对象"哲学的最优雅体现。

**现代映照**：现代 Windows 的 OBJECT_TYPE 机制完全一致。这就是你用 WinDbg 执行 `dt nt!_OBJECT_TYPE` 看到的 `TypeInfo` 字段里的那张方法表。驱动开发者用 `ObCreateObjectType` 注册自定义对象类型，WDF 框架的设备对象、WPP 的追踪对象都建立在这套机制上。

**工业界补充**：`ObRegisterCallbacks` 注册的回调，本质上是在 OBJECT_TYPE 的 OpenProcedure 调用链中插入"第三方钩子"——微软官方提供的、PatchGuard 友好的"对象打开监控点"。现代 EDR 用它监控：

- `PsProcessType` 的打开（检测 OpenProcess 注入）
- `PsThreadType` 的打开（检测 OpenThread 注入）
- `IoFileObjectType` 的打开（检测敏感文件访问）

## 4.3 句柄和句柄表

**书的脉络**：每个进程在初始化时，内核为其创建一张独立的**句柄表（Handle Table）**。这张表本质上是**稀疏数组**（通常 1024 项起步，可动态扩展），每一项（HANDLE_TABLE_ENTRY）存储：

- 对象指针（指向 OBJECT_HEADER）
- 访问掩码（Access Mask）——该句柄被授予的权限
- 继承标志（Inheritable Flag / ObAttributes）
- 对象类型索引

当用户调用 `CreateFile`、`CreateEvent` 等 API 时，系统实际执行：

1. 在内核中创建对应类型的对象
2. 将其插入全局对象目录（如果具名）
3. 在当前进程的句柄表中查找空闲槽位
4. 填入对象指针及相关属性
5. 返回该槽位索引作为 HANDLE 值

此外还有一张全局的 **ObpKernelHandleTable**，供内核态自身使用（内核句柄通过 `KERNEL_HANDLE_FLAG` 标志位与用户句柄区分）。

**我的洞见——句柄表是"能力系统"的工程实现**：

计算机科学里有个经典概念叫" capability system（能力系统）"：主体的权限不靠"引用+权限检查"组合，而是靠"持有不可伪造的令牌"。Windows 的句柄就是这种令牌：

- 句柄值是进程私有的索引，跨进程无意义
- 即使两个进程"碰巧"有相同的句柄值，指向的也可能是完全不同的对象
- 持有句柄 = 拥有该句柄被授予的访问权限，无需再做全局权限检查
- 句柄的访问掩码在创建/打开时一次性确定，后续访问不再重新鉴权（除非 ObCheckObjectAccess 显式调用）

> ⚠️ **这就是为什么"句柄泄露"是 Windows 编程最常见的 bug**：每次 `CreateFile`/`OpenProcess` 都必须配对 `CloseHandle`，否则句柄表中的条目永远不释放，对象引用计数永远不归零，对象永远不销毁。long-running 的服务进程句柄泄露到几万、几十万个条目，最终导致创建新对象失败（`STATUS_INSUFFICIENT_RESOURCES` 或 `STATUS_NO_MEMORY`）。

**现代映照**：x64 Windows 的句柄表结构与 x86 基本一致，但表项是 16 字节（容纳 64 位对象指针）。现代 Windows 10/11 引入了 **"句柄表随机化"**​ 和 **"句柄审计"**（通过 ETW 的 `Handle` 事件类别）。任务管理器的"句柄数"列、Process Explorer 的"Handle"视图，直接读取的就是进程的句柄表。

**工业界**：

- **句柄泄露排查**：用 Process Explorer 查看进程的句柄列表，按类型排序，找出异常多的某种句柄（如几千个 Event、几百个 File）——这是定位句柄泄露最快的方法
- **句柄注入攻击**：恶意软件通过 `NtDuplicateObject` 把句柄复制到目标进程，再用 `WriteProcessMemory` 写入 shellcode 到目标进程映射的文件——这就是"句柄劫持"
- **防护**：现代 EDR 监控 `NtDuplicateObject` 的调用，特别是跨进程、高权限句柄的复制

## 4.4 对象的创建

**书的脉络**：对象创建的典型路径：

```
NtCreateEvent / NtCreateFile / NtCreateProcess ...
  ↓
ObCreateObject()  // 分配 OBJECT_HEADER + 对象体
  ↓
ObInsertObject()  // 插入对象目录（如果具名）
  ↓
ObpCreateHandle() // 在当前进程句柄表创建句柄
  ↓
返回 HANDLE 给用户态
```

`ObCreateObject` 的工作：

1. 根据 OBJECT_TYPE 的 `PoolType` 和对象体大小，从 NonPaged/Paged Pool 分配内存
2. 在对象体之前布置 OBJECT_HEADER
3. 初始化 OBJECT_HEADER：TypeIndex、引用计数=1（自身）、句柄计数=0、安全描述符
4. 调用 OBJECT_TYPE 的 `ParseProcedure`（如果有）和初始化回调
5. 返回对象体指针

`ObInsertObject` 的"先占位后填充"策略：HANDLE_TABLE_ENTRY 的 ObjectHeader 字段在创建时为 NULL，ObInsertObject 后续填充——这是为了避免在长路径上持有锁。

**我的洞见——对象创建是"两阶段提交"**：

NT 内核的对象创建严格区分"内存分配+初始化"（ObCreateObject）和"命名+暴露"（ObInsertObject）。这种分离带来灵活性：

- 匿名对象（如大多数 Event）只走第一阶段，不进对象目录
- 具名对象（如 `\Global??\C:`）走两阶段，进对象目录后被其他进程通过名字打开
- 内核态可以用 `ObReferenceObjectByName` 直接按名字找对象，绕过句柄表

> 💡 **引用计数的初始值**：ObCreateObject 后对象指针计数=1（被创建者引用），句柄计数=0。只有当 ObInsertObject 创建句柄后，句柄计数才变为 1。这就是为什么"创建对象后必须配对 ObDereferenceObject"——否则指针计数永远不归零。

**现代映照**：现代 Windows 的对象创建路径与此一致，但增加了：

- **VBS 环境下的安全校验**：某些敏感对象（如进程、线程）的创建需要经过安全内核的验证
- **Mitigation 标志检查**：根据进程的 Mitigation 策略限制某些对象类型的创建
- **对象回调**：ObRegisterCallbacks 注册的 PreCreate/PostCreate 回调会在对象创建前后被调用

## 4.5 几个常用的内核函数

这一节是对象管理器的"API 参考手册"，但每个函数背后都有设计哲学。

### 4.5.1 ObReferenceObjectByHandle()

**书的脉络**：签名：

```
NTSTATUS ObReferenceObjectByHandle(
    HANDLE Handle,                    // 句柄
    ACCESS_MASK DesiredAccess,        // 需要的权限
    POBJECT_TYPE ObjectType,          // 期望的对象类型
    KPROCESSOR_MODE AccessMode,       // UserMode / KernelMode
    PVOID *Object,                    // 输出对象指针
    POBJECT_HANDLE_INFORMATION HandleInformation  // 输出句柄信息
);
```

核心逻辑：

1. 判断是否是伪句柄 `NtCurrentProcess()` / `NtCurrentThread()`——直接返回 EPROCESS/ETHREAD 指针
2. 判断是否是内核句柄（KERNEL_HANDLE_FLAG）——用 `ObpKernelHandleTable`，否则用当前进程的 `EPROCESS.ObjectTable`
3. `ExMapHandleToPointerEx` 从句柄表取出 HANDLE_TABLE_ENTRY
4. 校验 ObjectType 是否匹配（类型不符返回 `STATUS_OBJECT_TYPE_MISMATCH`）
5. 校验 DesiredAccess（用户态调用必须检查，内核态调用跳过）
6. 校验通过则 `ObpIncrPointerCount` 增加对象指针引用计数
7. 返回对象体指针

**关键**：调用成功后**对象的引用计数+1**，调用方必须在不再需要时调用 `ObDereferenceObject` 减回。

**我的洞见——这个函数是"能力令牌兑换实体"的兑换机**：

用户态给你一个 HANDLE（不透明的索引），你用这个函数"兑换"出真正的对象指针。兑换过程做了三件事：

- **身份验证**：AccessMode=UserMode 时必须做权限检查，内核态调用可豁免（PreviousMode 的再次体现）
- **类型验证**：ObjectType 参数防止"拿进程句柄当线程用"
- **生命周期延长**：引用计数+1，保证在你用对象期间它不会被销毁

> ⚠️ **最常见的驱动开发 bug**：调用 ObReferenceObjectByHandle 后忘记配对 ObDereferenceObject，导致对象指针计数永远不归零，对象永远不销毁——典型的内存泄露。

**现代映照**：现代 Windows 驱动开发中，ObReferenceObjectByHandle 仍是获取对象指针的标准方式。搭配使用的还有 `ObReferenceObjectByHandleWithTag`（带 Tag 便于 Pool 泄露排查）。

### 4.5.2 ObReferenceObjectByPointer()

**书的脉络**：如果你已经有了对象指针（比如从别的内核组件传来的），用这个函数增加引用计数：

```
NTSTATUS ObReferenceObjectByPointer(
    PVOID Object,               // 对象指针
    ACCESS_MASK DesiredAccess,
    POBJECT_TYPE ObjectType,
    KPROCESSOR_MODE AccessMode
);
```

**我的洞见**：与 4.5.1 的区别在于——4.5.1 是从"句柄"兑换对象（走句柄表查找+权限校验），4.5.2 是已经有对象了，只是"再持有一份引用"。后者更轻量，因为跳过了句柄表查找和权限校验（调用者已经持有指针，说明它已经有权限）。

> 📌 这是一个**性能优化**：内核内部传递对象指针时，用 ObReferenceObjectByPointer 比 ObReferenceObjectByHandle 快得多。

### 4.5.3 ObpLookupEntryDirectory()

**书的脉络**：在对象目录的 Hash 表中查找一个条目。37 个桶（质数减少碰撞），链头插入（LIFO），查找上下文缓存避免重复查找。

**我的洞见——这是对象目录的"哈希表查询"原语**：

对象目录用质数个桶的哈希表，每个桶是一条链表。插入时链头插入（O(1)），查找时遍历链表。37 这个质数选择是工程经验——太小则碰撞多，太大则浪费内存。

> 💡 **目录锁**：调用方必须持有目录的自旋锁。这意味着对象目录的查找/插入/删除是"短平快"的原子操作，不能在其中做耗时工作。

### 4.5.4 ObpLookupObjectName()

**书的脉络**：完整的路径解析函数，签名：

```
NTSTATUS ObpLookupObjectName(
    HANDLE RootHandle OPTIONAL,
    PUNICODE_STRING ObjectName,   // 如 \Device\HarddiskVolume1\foo
    ULONG Attributes,
    POBJECT_TYPE ObjectType,
    KPROCESSOR_MODE AccessMode,
    PVOID ParseContext,
    PSECURITY_QUALITY_OF_SERVICE SecurityQos OPTIONAL,
    PVOID InsertObject OPTIONAL,  // 创建时使用
    PACCESS_STATE AccessState,
    POBP_LOOKUP_CONTEXT LookupContext,
    PVOID *FoundObject
);
```

路径解析流程：

1. 解析 RootHandle 得到起始目录对象
2. 把 ObjectName 按 `` 分段
3. 逐段在目录中 ObpLookupEntryDirectory 查找
4. 如果找到的是目录对象，继续解析下一段
5. 如果找到的对象有 ParseProcedure（如 Device、File），调用 ParseProcedure 委托解析剩余路径
6. 遇到符号链接对象，调用 ObpParseSymbolicLink 解析
7. 最终找到目标对象或到达路径终点

**我的洞见——这是 NT 内核最优雅的"迭代式路径解析"算法**：

路径解析不是"一次性字符串匹配"，而是**"沿对象链逐步委托"**：

```
\??\C:\foo.txt
  ↓ 解析 \??（符号链接对象）
  → ObpParseSymbolicLink → \Device\HarddiskVolume1
  ↓ 解析 \Device（目录对象）
  ↓ 解析 HarddiskVolume1（Device 对象，有 ParseProcedure）
  → 文件系统驱动的 ParseProcedure 接管 "foo.txt"
  ↓ 解析 foo.txt（File 对象）
  → 返回文件对象
```

每一步都可以被不同类型对象的 ParseProcedure 定制。这种"责任链模式"让 NT 内核能够支持任意复杂的名字空间——文件系统、注册表、内核对象目录，全都跑在同一套解析框架上。

> ⚠️ **这也是为什么 ``\??\` 和``\DosDevices` 等价**：`\??` 是一个符号链接对象，指向 `\DosDevices`。解析 `\??\C:` 时，ObpParseSymbolicLink 把它翻译成 `\DosDevices\C:`，再继续解析。

**现代映照**：现代 Windows 的路径解析机制完全一致。你在 WinDbg 里用 `!object ` 命令，就是在调用类似 ObpLookupObjectName 的逻辑遍历对象目录树。

### 4.5.5 ObOpenObjectByName()

**书的脉络**：用户态 `OpenEvent`、`OpenProcess`、`CreateFile` 等"打开已有对象"的 API，最终走到 ObOpenObjectByName。它内部调用 ObpLookupObjectName 找到对象，然后在当前进程句柄表创建句柄，返回给用户态。

**我的洞见——"打开"的本质是"查找+创建句柄"**：

与 4.4 的"创建"对比：

- **创建**：ObCreateObject + ObInsertObject + ObpCreateHandle（可能新建对象）
- **打开**：ObpLookupObjectName + ObpCreateHandle（对象已存在）

共同点是最后一步都是 ObpCreateHandle——在当前进程句柄表里增加一个条目，指向已存在的对象，对象引用计数+1。

### 4.5.6 ObReferenceObjectByName()

**书的脉络**：内核态按名字直接获取对象指针（不走句柄表）：

```
NTSTATUS ObReferenceObjectByName(
    PUNICODE_STRING ObjectName,
    ULONG Attributes,
    POBJECT_TYPE ObjectType,
    KPROCESSOR_MODE AccessMode,
    PVOID ParseContext,
    PVOID *Object
);
```

**我的洞见——内核态的"快捷方式"**：

用户态必须通过句柄访问对象（安全检查+句柄表），但内核态代码（尤其是执行体、驱动）经常需要直接按名字获取对象指针。ObReferenceObjectByName 就是干这个的——它内部调用 ObpLookupObjectName，找到对象后 ObReferenceObjectByPointer 增加引用计数，返回指针。

> 📌 典型用例：文件系统驱动在挂载时，用 ObReferenceObjectByName(`\??\C:`) 找到对应的 Device 对象，建立关联。

### 4.5.7 ObDereferenceObject()

**书的脉络**：

```
void ObDereferenceObject(PVOID Object);
```

递减对象的指针引用计数。当指针计数和句柄计数**都**归零时，调用 OBJECT_TYPE.DeleteProcedure 销毁对象。

**我的洞见——这是对象生命周期管理的"另一半"**：

|操作|引用计数变化|
|---|---|
|ObCreateObject|指针计数 +1|
|ObpCreateHandle（创建句柄）|句柄计数 +1|
|ObReferenceObjectByHandle|指针计数 +1|
|ObReferenceObjectByPointer|指针计数 +1|
|NtClose（关闭句柄）|句柄计数 -1|
|ObDereferenceObject|指针计数 -1|
|**指针计数=0 且 句柄计数=0**​|**调用 DeleteProcedure 销毁对象**​|

> ⚠️ **关键规则**：对象销毁的必要条件是**指针计数 AND 句柄计数都为 0**。这意味着：
> 
> - 即使所有句柄都关闭了，只要有内核指针引用着对象，对象就不销毁
> - 即使所有内核指针都释放了，只要还有句柄开着，对象就不销毁
> - 必须两者都清零，对象才真正消失

这就是为什么进程对象特别顽固：进程退出时，所有用户态句柄被关闭（句柄计数归零），但系统里可能还有其他进程通过 `OpenProcess` 拿着句柄，或者内核驱动通过指针引用着——必须这些都释放，EPROCESS 才真正销毁。

**现代映照**：现代 Windows 的引用计数机制完全一致。驱动开发中"引用计数失衡"是最常见的 bug 类——忘记 ObDereferenceObject 导致对象泄露，或者多调用一次导致对象过早销毁（Use-After-Free）。

## 4.6 对象的访问控制

**书的脉络**：每当有进程尝试通过句柄访问对象时，**安全引用监视器（Security Reference Monitor, SRM）**​ 根据对象的安全描述符（Security Descriptor）进行权限检查。安全描述符包含：

- **DACL（自主访问控制列表）**：哪些用户/组有什么权限
- **SACL（系统访问控制列表）**：审计规则
- **Owner**：对象所有者
- **Group**：对象主组

**我的洞见——句柄权限在"打开时"一次性确定，而非"访问时"**：

这是一个反直觉但极其重要的设计：

- **打开对象时**：SRM 检查调用者的 Token 与对象 DACL，如果允许，创建一个带有 `GrantedAccess`（被授予的权限）的句柄
- **后续访问时**：内核直接检查句柄的 GrantedAccess，**不再查 DACL**

为什么这么设计？**性能**。每次访问都查 DACL 太慢了。所以 NT 内核把"权限检查"前置到"句柄创建"那一刻，后续访问只是位与运算（`DesiredAccess & GrantedAccess == DesiredAccess`）。

> 💡 **这带来一个重要推论**：如果你用 `OpenProcess(PROCESS_VM_WRITE)` 打开一个进程，但 DACL 只允许 `PROCESS_VM_READ`，那么句柄的 GrantedAccess 只包含 `PROCESS_VM_READ`。后续你尝试 `WriteProcessMemory`，内核检查 GrantedAccess 发现没有 `PROCESS_VM_WRITE`，直接拒绝——**即使目标进程的安全描述符理论上可以改**。

**现代映照**：现代 Windows 的访问控制机制在此基础上增加了：

- **Mandatory Integrity Control（强制完整性控制）**：除了 DACL 的自主访问，还有完整性级别的强制访问（低完整性进程不能写高完整性对象）
- **AppContainer**：Metro/UWP 应用的 SID 隔离
- **VBS 下的安全内核校验**：某些敏感对象的访问必须经过 VTL1 的安全内核

## 4.7 句柄的遗传和继承

**书的脉络**：进程创建时，如果父进程标记了某些句柄为"可继承"（ObAttributes 中的 `OBJ_INHERIT` 标志），那么子进程会继承这些句柄——即在子进程的句柄表中创建指向同一对象的条目，对象引用计数相应增加。

**我的洞见——句柄继承是"能力传递"的受控通道**：

默认情况下，句柄是进程私有的，子进程不能通过 fork（Windows 没有 fork）获得父进程的句柄。但 Windows 允许父进程显式标记某些句柄为"可继承"，这样 `CreateProcess` 时，内核会遍历父进程句柄表，把所有 `OBJ_INHERIT` 标记的句柄复制到子进程句柄表。

> 📌 **典型用例**：父进程创建一个 Event 对象，标记为可继承，然后 CreateProcess 启动子进程。子进程自动获得这个 Event 的句柄，父子进程可以通过这个 Event 同步。

但这里有个**微妙之处**：继承发生在 `CreateProcess` 的时刻，且只对标记为 `OBJ_INHERIT` 的句柄生效。如果父进程在 CreateProcess 之后才创建句柄，子进程不会自动获得。

**现代映照**：现代 Windows 的句柄继承机制一致，但增加了：

- **Handle Inheritance 的精细控制**：CreateProcess 的 `bInheritHandles` 参数控制是否继承
- **AppContainer 下的句柄继承受限**：UWP 应用的子进程不能继承父进程的句柄
- **Cross-session 继承**：不同会话间的句柄继承受限制

## 4.8 系统调用 NtDuplicateObject()

**书的脉络**：句柄复制（特别是跨进程），框架：

```
源进程 (SourceProcess)              目标进程 (TargetProcess)
┌────────────────────┐              ┌────────────────────┐
│ HandleTable        │              │ HandleTable        │
│ [SourceHandle]     │              │ [TargetHandle]     │
│ - Object ──── 指向 ├─── 同一对象 ──▶│ - Object           │
│ - GrantedAccess    │              │ - GrantedAccess    │
│ - ObAttributes     │              │ - ObAttributes     │
└────────────────────┘              └────────────────────┘
```

流程：

1. 验证源/目标进程句柄（需要 `PROCESS_DUP_HANDLE` 权限）
2. 解析源句柄 → 找到对象
3. 计算新 GrantedAccess（**只能缩减，不能放大**——安全边界）
4. 在目标进程中分配新句柄 Entry
5. 复制 ObAttributes（可指定）
6. 递增对象的引用计数

**我的洞见——NtDuplicateObject 是"能力委派"的原语**：

`DuplicateHandle` 在用户态是 `kernel32!DuplicateHandle`，最终调用 `NtDuplicateObject`。它的威力在于**跨进程**：

- 同一进程内复制：相当于"办副卡"，新旧句柄指向同一对象，但可以有不同访问权限（新句柄的权限 ≤ 旧句柄）
- 跨进程复制：把句柄"传送"给另一个进程，是 IPC 的基础原语

> ⚠️ **权限单调性**：新句柄的 GrantedAccess 只能是源句柄 GrantedAccess 的子集。你不能通过 DuplicateHandle "提升权限"——这是安全边界。

**工业界**：NtDuplicateObject 是**攻击与防御的焦点**：

- **攻击**：恶意软件通过 `DuplicateHandle` 把高权限进程的句柄（如 `PROCESS_ALL_ACCESS`）复制到自己的进程，然后用 `WriteProcessMemory` 注入 shellcode 到目标进程
- **防御**：现代 EDR 监控 `NtDuplicateObject` 的跨进程调用，特别是目标进程是浏览器、杀毒软件、系统进程等高价值目标时
- **Process Injection 技术**：`DuplicateHandle` + `WriteProcessMemory` 是经典的"句柄劫持注入"手法

**现代映照**：现代 Windows 10/11 引入了**"Handle Hardening"**：

- 高完整性进程（如 SYSTEM）的句柄默认不能被低完整性进程 Duplicate
- VBS 环境下，某些敏感句柄（如 `PROCESS_VM_WRITE` 到 protected process）的 Duplicate 会被安全内核拦截
- 现代 EDR 普遍 Hook 或回调监控 NtDuplicateObject

## 4.9 系统调用 NtClose()

**书的脉络**：关闭句柄，流程：

```
NtClose(Handle)
  ↓
ObpCloseHandle(Handle, PreviousMode)
  ↓
① 从当前进程句柄表找到 HANDLE_TABLE_ENTRY
② 调用 OBJECT_TYPE.OkayToCloseProcedure（如果返回 FALSE，拒绝关闭）
③ 递减对象的句柄计数（ObpDecrementHandleCount）
④ 如果句柄计数归零：
   - 调用 OBJECT_TYPE.CloseProcedure（如 File 触发 IRP_MJ_CLEANUP）
⑤ 递减对象的指针计数（ObDereferenceObject）
⑥ 如果指针计数也归零：
   - 调用 OBJECT_TYPE.DeleteProcedure 销毁对象
⑦ 释放 HANDLE_TABLE_ENTRY（句柄值可被复用）
```

**我的洞见——NtClose 是"能力回收"**：

NtClose 做的不仅是"释放句柄"，它触发了一连串的清理动作：

1. **安全检查**：OkayToCloseProcedure 可以拒绝关闭（用于调试或特殊保护对象）
2. **业务清理**：CloseProcedure 让对象类型有机会做业务级清理（文件锁释放、I/O 取消）
3. **生命周期管理**：引用计数递减，归零则销毁
4. **句柄值回收**：HANDLE_TABLE_ENTRY 被标记为空闲，该句柄值可以被后续创建复用

> ⚠️ **这就是为什么 CloseHandle 之后要把变量设为 NULL**：句柄值会被复用。如果你之后错误地再次使用这个句柄值，它可能指向一个完全不同的对象——这是经典的"use-after-close" bug。

**现代映照**：现代 Windows 的 NtClose 路径一致，但增加了：

- **VBS 下的句柄关闭校验**：某些受保护句柄的关闭需要经过安全内核
- **Handle Auditing**：通过 ETW 的 `Handle/Duplicate` 和 `Handle/Close` 事件审计
- **Protected Process 的句柄关闭受限**：低完整性进程不能随意关闭高完整性进程的句柄

**工业界**：

- **句柄泄露检测**：现代 APM 工具通过 ETW 的 Handle 事件追踪句柄的创建和关闭，识别泄露模式
- **攻击检测**：恶意软件经常"借"目标进程的句柄做坏事，然后 NtClose 掩盖痕迹。EDR 通过关联 NtDuplicateObject 和 NtClose 的事件序列检测这种行为

2. **4.2 对象类型**：定义了"对象的行为"（OBJECT_TYPE 方法表，多态分发）
3. **4.3 句柄和句柄表**：定义了"用户态怎么安全地引用对象"（进程私有句柄表，不透明令牌）
4. **4.4 对象的创建**：定义了"对象怎么出生"（ObCreateObject + ObInsertObject + ObpCreateHandle）
5. **4.5 常用内核函数**：定义了"内核态怎么操作对象"（引用/解引用/查找/打开）
6. **4.6 对象的访问控制**：定义了"谁能访问对象"（SRM + DACL，权限前置到句柄创建时）
7. **4.7 句柄的遗传和继承**：定义了"能力怎么传递给子进程"（OBJ_INHERIT 标志）

## 工业界实际应用补充

**🔐 安全领域**

- **ObRegisterCallbacks**：现代 EDR 取代 SSDT Hook 的标准方式。注册 `OB_OPERATION_HANDLE_CREATE` 和 `OB_OPERATION_HANDLE_DUPLICATE` 回调，监控进程/线程/桌面等敏感对象的打开和复制。这是微软官方推荐、PatchGuard 友好的监控机制
- **句柄注入检测**：监控 NtDuplicateObject 的跨进程调用，特别是目标进程是浏览器、杀毒软件、系统进程等高价值目标时。典型攻击链：`OpenProcess(PROCESS_DUP_HANDLE)` → `DuplicateHandle` 获取目标进程的高权限句柄 → `WriteProcessMemory` 注入
- **句柄泄露审计**：通过 ETW 的 `Handle` 事件类别（`Handle/Create`、`Handle/Duplicate`、`Handle/Close`）追踪句柄生命周期，识别泄露模式。Process Explorer 的"Handle"视图就是基于这种机制
- **VBS/HVCI 强化**：基于虚拟化的安全把敏感对象（如 protected process 的 EPROCESS）放到 VTL1 隔离，普通内核（VTL0）的 ObReferenceObjectByHandle 调用会被安全内核拦截

**⚙️ 驱动开发**

- **引用计数规则**：ObReferenceObjectByHandle 必须配对 ObDereferenceObject；ObReferenceObjectByPointer 也必须配对 ObDereferenceObject。失衡是驱动最常见 bug
- **带 Tag 的引用**：现代驱动推荐使用 `ObReferenceObjectByHandleWithTag`，便于通过 `!poolfind` 和 `!object` 命令排查引用计数泄露
- **对象回调注册**：驱动可以用 ObRegisterCallbacks 监控其他进程的对象操作，是开发安全软件的基础
- **跨进程句柄复制**：驱动中慎用 NtDuplicateObject，因为涉及跨进程句柄表操作，必须在正确的进程上下文中执行

**🛡️ 系统管理**

- **句柄泄露排查**：任务管理器"句柄数"列、Process Explorer 的 Handle 视图、WinDbg 的 `!handle` 命令
- **对象目录浏览**：WinObj.exe（Sysinternals）可视化浏览 ``\ObjectTypes\`、``\Device`、`\Global??` 等对象目录
- **句柄审计**：Windows 事件日志的"对象访问"审计策略，配合 ETW Handle 事件
