
第12章是整本书从"机制"走向"信任"的关键一跃。前面你学了系统调用、对象管理、设备驱动、文件系统——所有这些机制都需要一个"守门人"来决定"谁能对什么对象做什么操作"。这一章告诉你：当线程试图打开一个文件、进程、线程、信号量等任何安全对象时，Windows 如何通过**访问令牌（书里称"证章"）+ 安全描述符/ACL + SeAccessCheck**​ 这三件套做出允许/拒绝的决策。整章 12.1~12.4 就是这条授权链的完整解剖：从安全模型概述 → 证章（Token）→ 安全描述块与 ACL → 访问权限检查。

我的核心洞见先抛在前面：**Windows 安全模型的第一性原理是"用令牌表达主体身份，用安全描述符表达客体保护策略，用统一的访问检查函数 SeAccessCheck 执行决策"**。这三个概念构成了一个**声明式授权系统**——对象自己"声明"谁可以访问（通过 DACL），主体"携带"自己的身份和权限（通过 Token），内核的 SeAccessCheck 是裁判。理解了这个三角关系，你就能解释为什么 Windows 的权限模型既灵活（每个对象可有独立 DACL）又可审计（SACL 记录访问尝试）。

> 💡 读这一章的正确姿势：把访问检查想象成**夜店门口的保镖查票**。你的 Token 是你的身份证+会员卡（里面有你的 SID、所属组 SID、特权列表），夜店的 DACL 是墙上贴的"准入规则"（允许/拒绝名单），保镖 SeAccessCheck 逐条比对规则——显式拒绝优先，然后显式允许，最后没有匹配就默认拒绝。这套机制从 Windows NT 3.1 到现在 30 多年没变过核心逻辑。

## 12.1 概述

**书的脉络**：Windows 安全模型基于 Windows NT 的安全架构，主要包含：安全描述符（描述对象的安全信息）、访问控制列表 ACL（定义访问权限）、安全标识符 SID（标识用户、组和进程）、权限（如读取、写入、执行等）、安全策略（如密码策略、账户策略等）。

**Windows 安全的两大支柱**：

1. **身份认证（Authentication）**：证明"你是谁"——通过 SSPI 调用具体的 SSP（NTLM/Kerberos/Negotiate），成功后由 LSA 创建访问令牌
2. **授权（Authorization）**：决定"你能做什么"——用访问令牌与对象的安全描述符比对

**安全参考监视器（SRM, Security Reference Monitor）**：

ReactOS 中 SRM 的实现位于 `ntoskrnl/se/`，核心组件包括：

|文件|职责|
|---|---|
|`se/accesschk.c`|`SeAccessCheck`——访问检查核心函数|
|`se/token.c`|令牌操作（创建、赋值、复制）|
|`se/priv.c`|特权常量定义与管理|

**我的洞见——安全模型的第一性原理是"主体-客体-策略"三元组**：

Windows 安全模型脱胎于经典的**访问控制模型**：

> 📌 **三个核心概念**：
> 
> - **主体（Subject）**：进程/线程，携带访问令牌（Token）
> - **客体（Object）**：安全对象（文件、进程、线程、互斥体等），携带安全描述符（Security Descriptor）
> - **策略（Policy）**：DACL 中的 ACE 列表，声明"谁可以做什么"

**认证与授权的分离**：

```
用户登录 → LSA 认证 → 创建访问令牌 → 进程继承令牌
                                          ↓
进程访问对象 → 内核调用 SeAccessCheck(令牌, 对象SD, 请求权限)
                                          ↓
                                  允许 / 拒绝
```

这种分离让**认证机制可插拔**（NTLM/Kerberos/智能卡），**授权机制统一**（都是 Token vs SD 的比对）。

**现代映照**：现代 Windows 在此基础上增加了：

- **完整性级别（Integrity Level）**：除了 DACL 检查，还有 IL 检查——低完整性进程不能写入高完整性对象（UAC 的基础）
- **VBS（Virtualization-Based Security）**：将授权决策的关键部分放到隔离的安全内核（VTL1）中执行
- **HVCI**：防止内核安全结构被篡改
- **PatchGuard**：保护 SRM 的关键数据结构

工业界：理解 Windows 安全模型是**所有安全软件的基础**——EDR 通过回调监控 SeAccessCheck 的决策，杀毒软件通过 minifilter 在文件系统层做额外的访问控制，企业 DLP 通过拦截敏感文件的打开操作实现数据防泄漏。

## 12.2 证章（Token）

**书的脉络**：证章即访问令牌（Access Token），是与特定 Windows 账户关联的数据结构。账户环境下启动的所有进程都会获得该令牌的副本，进程中的线程默认获得这个令牌。

**Token 的核心组成**：

|组件|说明|
|---|---|
|**用户 SID**​|标识具体用户（如 `S-1-5-21-...-1001`）|
|**组 SID 列表**​|用户所属的所有组（如 Administrators、Everyone）|
|**受限 SID 列表**​|受限令牌中的拒绝 SID（DenyOnly）|
|**特权列表（Privileges）**​|该账户拥有的特权（如 `SeDebugPrivilege`、`SeShutdownPrivilege`）|

**Token 的类型**：

- **主令牌（Primary Token）**：进程级，描述进程的安全上下文
- **模拟令牌（Impersonation Token）**：线程级，线程可临时"扮演"另一个用户

**Token 的创建流程**：

```
用户登录 → LSA 调用 NTLM/Kerberos 认证
  ↓
认证成功 → LSA 创建访问令牌
  ↓
Winlogon 创建初始进程（userinit.exe）→ 继承令牌
  ↓
用户启动的应用程序 → 继承父进程令牌
```

ReactOS 中 Token 相关函数在 `ntoskrnl/se/token.c`，核心包括 `SeAssignPrimaryToken`、`SeCreateTokenPrivilege` 等。

**我的洞见——Token 是"安全身份的护照"**：

Token 的第一性原理是**把"用户身份"与"进程执行"解耦**：

> 💡 **为什么需要 Token？**
> 
> - 同一个用户可能同时有多个进程（资源管理器、浏览器、命令行）
> - 每个进程都需要"代表用户"去访问对象
> - Token 就是这个"代表凭证"——进程拿着它去访问任何对象
> 
> 更精妙的是**模拟令牌**：服务进程（如 IIS）可以模拟客户端身份，用客户端的 Token 去访问文件，实现"委托访问"。

**受限令牌与 UAC**：

Windows Vista 引入 UAC 后，管理员账户实际有两个 Token：

- **标准用户令牌（Filtered Token）**：去掉管理员组、去掉敏感特权——默认使用
- **提升令牌（Elevated Token）**：完整管理员权限——"以管理员身份运行"时使用

这就是 UAC 弹窗提示的根本原因：**默认用低权限令牌运行，需要时再提升到高权限令牌**。

**Token 与完整性级别**：

Windows 引入了完整性级别（IL）：

```
System (0x4000) > High (0x3000) > Medium (0x2000) > Low (0x1000)
```

即使是管理员，默认 IL 是 Medium；IE 等浏览器进程 IL 是 Low（沙箱化）。**IL 检查在 DACL 检查之前**——低 IL 进程不能写入高 IL 对象，即使 DACL 允许。

**现代映照**：现代 Windows Token 机制增加了：

- **AppContainer SID**：UWP/Edge 沙箱使用，Token 中包含 AppContainer SID 和能力（Capabilities）
- **VBS 隔离**：Token 的关键字段在安全内核中保护
- **Credential Guard**：NTLM/Kerberos 的密钥与散列存放在 VTL1，防止 Pass-the-Hash 攻击

工业界：理解 Token 是**权限提升研究、横向移动检测**的核心。著名的**令牌窃取（Token Stealing）**攻击（如 Metasploit 的 `steal_token`）就是通过 `OpenProcessToken` + `DuplicateToken` + `SetThreadToken` 窃取 SYSTEM 令牌。现代 EDR 监控 `SeAssignPrimaryToken` 和模拟操作，检测此类攻击。

## 12.3 安全描述块和 ACL

**书的脉络**：安全描述符（Security Descriptor）用于描述对象的安全信息，包括所有者、组、ACL 等。ACL 定义了对象的访问权限，包含允许和拒绝的权限。

**安全描述符（SECURITY_DESCRIPTOR）的结构**：

```
SECURITY_DESCRIPTOR
├── Owner SID          # 对象所有者的 SID
├── Group SID          # 主组 SID
├── DACL (自主访问控制列表)  # 谁可以访问
└── SACL (系统访问控制列表)  # 审计规则
```

**DACL（Discretionary Access Control List）**：

DACL 包含零个或多个 **ACE（Access Control Entry）**：

```
typedef struct _ACE_HEADER {
    BYTE AceType;      // ACCESS_ALLOWED_ACE / ACCESS_DENIED_ACE
    BYTE AceFlags;     // 继承标志
    USHORT AceSize;
} ACE_HEADER;

typedef struct _ACCESS_ALLOWED_ACE {
    ACE_HEADER Header;
    ACCESS_MASK AccessMask;   // 允许的权限位
    ULONG AceSidOffset;       // SID 偏移
    // SID 数据紧跟其后
} ACCESS_ALLOWED_ACE;
```

**ACE 的类型**：

|ACE 类型|作用|
|---|---|
|`ACCESS_ALLOWED_ACE`|允许指定 SID 访问|
|`ACCESS_DENIED_ACE`|拒绝指定 SID 访问|
|`SYSTEM_AUDIT_ACE`|审计指定 SID 的访问尝试|
|`ACCESS_ALLOWED_OBJECT_ACE`|针对特定对象类型的允许|
|`ACCESS_DENIED_OBJECT_ACE`|针对特定对象类型的拒绝|

**ACE 的四个关键字段**：

- **SID**：标识受信者（用户/组/计算机）
- **Access Mask**：允许的权限位（如 `FILE_READ_DATA`、`PROCESS_VM_READ`）
- **AceType**：允许/拒绝/审计
- **Inheritance Flags**：是否继承到子对象

**ACE 的匹配顺序（关键！）**：

```
1. 显式拒绝（Explicit Deny）
2. 显式允许（Explicit Allow）
3. 继承的拒绝（Inherited Deny）
4. 继承的允许（Inherited Allow）
```

> ⚠️ **这就是为什么"拒绝 ACE 必须先于允许 ACE"**——系统按顺序检查，遇到第一个匹配的 ACE 就停止。如果用户同时匹配"拒绝"和"允许"，拒绝优先。

**DACL 的特殊情况**：

- **空 DACL（DACL 存在但 ACE 数为 0）**：**拒绝所有人访问**
- **无 DACL（NULL）**：**允许所有人完全访问**（危险！）

**ReactOS 中的安全描述符操作**：

ReactOS 提供完整的安全描述符 API：

```
// 安全描述符捕获（从用户态复制到内核态）
SeCaptureSecurityDescriptor(OriginalSecurityDescriptor, 
    CurrentMode, PoolType, CaptureIfKernel, 
    &CapturedSecurityDescriptor);

// 安全描述符释放
SeReleaseSecurityDescriptor(CapturedSecurityDescriptor, 
    CurrentMode, CaptureIfKernelMode);

// 查询安全描述符信息
SeQuerySecurityDescriptorInfo(SecurityInformation, 
    SecurityDescriptor, Length, 
    ObjectsSecurityDescriptor);
```

**通用权限映射（Generic Mapping）**：

Windows 定义了通用权限到具体权限的映射：

```
GENERIC_MAPPING ObpTypeMapping = {
    STANDARD_RIGHTS_READ,    // GenericRead
    STANDARD_RIGHTS_WRITE,   // GenericWrite
    STANDARD_RIGHTS_EXECUTE, // GenericExecute
    0x000F0001               // GenericAll
};
```

**我的洞见——安全描述符是"对象自我保护的能力"**：

安全描述符的第一性原理是**让每个对象"自带防火墙"**：

> 📌 **传统系统的做法**：权限集中在系统表里，对象本身不知道谁可以访问它
> 
> **Windows 的做法**：每个对象都携带自己的安全描述符，自我声明访问策略
> 
> 这种"去中心化"的设计让权限管理极其灵活：
> 
> - 每个文件可以有独立的 DACL
> - 每个进程可以有独立的 DACL
> - 每个注册表键可以有独立的 DACL
> - 继承机制让目录下的文件自动获得父目录的权限

**ACE 累积原则**：

如果多个 ACE 适用于同一个用户（通过用户 SID 或所属组 SID），权限是**累积**的。例如：

```
DACL:
  ACE1: User U1 → Read
  ACE2: Group G1 (U1 是成员) → Write
  
结果：U1 拥有 Read + Write
```

**SACL 与审计**：

SACL 控制审计——当指定 SID 尝试访问对象时，系统记录事件到安全日志。这是企业合规审计的基础。

**现代映照**：现代 Windows 的安全描述符增加了：

- **完整性级别 ACE**：`SYSTEM_MANDATORY_LABEL_ACE` 类型，控制 IL 要求
- **资源属性 ACE**：Windows Server 的"集中式授权策略"使用，基于文件分类（如"机密"、"财务"）
- **CAPABILITY SID**：AppContainer 的能力 SID
- **WSL 互操作**：Linux 文件的权限映射到 NT 安全描述符

工业界：理解安全描述符是**文件系统权限管理、注册表权限、服务权限配置**的基础。企业 IT 通过组策略批量设置 DACL，实现统一的权限治理。现代 EDR 通过 `IRP_MJ_SET_SECURITY` 监控 DACL 修改，检测攻击者篡改权限以持久化。

## 12.4 访问权限检查

**书的脉络**：访问权限检查是安全模型的核心执行环节——用主体的 Token 与客体的安全描述符进行比对，做出允许/拒绝决策。核心函数是 `SeAccessCheck`，位于 `ntoskrnl/se/accesschk.c`。

**SeAccessCheck 的简化逻辑**：

```
BOOLEAN NTAPI SeAccessCheck(
    PSECURITY_DESCRIPTOR SecurityDescriptor,  // 对象的安全描述符
    PSECURITY_SUBJECT_CONTEXT SubjectSecurityContext,  // 主体的安全上下文（Token）
    BOOLEAN SubjectContextLocked,
    ACCESS_MASK DesiredAccess,                // 请求的权限
    ACCESS_MASK PreviouslyGrantedAccess,
    PPRIVILEGE_SET* Privileges,
    PGENERIC_MAPPING GenericMapping,         // 通用权限映射
    KPROCESSOR_MODE AccessMode,
    PACCESS_MASK GrantedAccess,               // 输出：实际授予的权限
    PNTSTATUS AccessStatus)
{
    // 1. 内核态快速路径：除非指定 OBJ_FORCE_ACCESS_CHECK，否则跳过
    if (AccessMode == KernelMode) {
        if (DesiredAccess & MAXIMUM_ALLOWED) {
            *GrantedAccess = GenericMapping->GenericAll;
        } else {
            *GrantedAccess = DesiredAccess;
        }
        *GrantedAccess |= PreviouslyGrantedAccess;
        *GrantedAccess |= (DesiredAccess & ~MAXIMUM_ALLOWED);
        *AccessStatus = STATUS_SUCCESS;
        return TRUE;
    }
    
    // 2. 用户态路径：完整的 DACL 检查
    //    - 遍历 DACL 中的 ACE
    //    - 匹配 Token 中的 SID（用户 SID + 组 SID）
    //    - 按"显式拒绝 > 显式允许 > 继承拒绝 > 继承允许"顺序
    //    - 累积允许的权限
    //    - 特权检查（如 SeBackupPrivilege 可绕过某些 DACL 检查）
    //    - 完整性级别检查
}
```

**访问检查的详细流程**：

```
线程请求访问对象（如 OpenProcess(PID, PROCESS_VM_READ)）
  ↓
内核获取线程的 Token
  ↓
内核获取对象的 SecurityDescriptor
  ↓
调用 SeAccessCheck(Token, SD, DesiredAccess=PROCESS_VM_READ)
  ↓
1. 通用权限映射：GenericRead → 具体权限位
  ↓
2. DACL 检查：
   - 遍历 ACE 列表
   - 匹配 Token 中的 SID
   - 按优先级处理（显式拒绝优先）
   - 累积允许的权限
  ↓
3. 特权检查：
   - 如果 DACL 拒绝但 Token 有相应特权（如 SeDebugPrivilege）
   - 特权可覆盖 DACL 检查
  ↓
4. 完整性级别检查（现代 Windows）：
   - 线程 IL >= 对象 IL 才允许写入
  ↓
5. 返回 GrantedAccess 或 STATUS_ACCESS_DENIED
```

**ACE 匹配示例**（微软官方文档）：

假设文件的 DACL：

```
ACE1: Group Accounting → Allow Write
ACE2: Group Legal → Deny Write
```

进程的 Token SID 列表：`User Jim`, `Group Accounting`, `Group Legal`, `Group Everyone`

遍历顺序：

1. 检查 Jim 的 SID → 无匹配
2. 检查 Accounting → **匹配 ACE1，授予 Write**
3. 检查 Legal → 匹配 ACE2，但**显式拒绝优先**
4. **最终结果：拒绝写入**

如果 ACE 顺序反过来（Legal Deny 在前），结果相同——因为显式拒绝总是优先。

**受限令牌的特殊处理**：

当 Token 包含"拒绝 SID"（DenyOnly）时，匹配逻辑改变：

> ⚠️ **受限令牌中的拒绝 SID 只能匹配 DACL 中的拒绝 ACE**——也就是说，即使 DACL 有"允许 Accounting 组写入"的 ACE，如果 Token 中 Accounting 是 DenyOnly，则该 ACE **不生效**。

这是 Windows 实现**沙箱**的核心机制——受限令牌通过 DenyOnly SID 剥夺特定组的权限。

**访问检查的缓存优化**：

访问检查是昂贵的操作（需要遍历 DACL、匹配多个 SID）。Windows 的优化策略：

> 💡 **句柄表缓存**：访问检查只在"打开/创建对象"时执行一次，结果缓存在句柄表（Handle Table）的 `GrantedAccess` 字段中。后续通过该句柄的操作不再重复检查，直接查询缓存即可。

这就是为什么 `CreateFile` 时指定 `dwDesiredAccess` 很重要——它决定了句柄的 `GrantedAccess`，影响后续所有操作。

**ReactOS 中 SeAccessCheck 的真实调用场景**：

1. **进程创建**：`NtCreateProcess` 中调用 `SeAccessCheck(Process->Token, ...)` 检查调用者是否有权创建进程
2. **文件打开**：FastFAT 等文件系统驱动调用 `SeAccessCheck` 检查 DACL
3. **设备访问**：FastFAT 的 `FatExplicitDeviceAccessGranted` 函数演示了复杂的访问检查——它创建一个**去除 Everyone SID 的受限令牌**，重新执行访问检查，判断是否是"显式授权"而非"Everyone 授权"

```
// FastFAT 的受限令牌访问检查（acchksup.c）
Status = FatCreateRestrictEveryoneToken(OriginalAccessToken, 
                                        &RestrictedAccessToken);
// 用受限令牌重新检查
SeAccessCheck(DeviceObject->SecurityDescriptor,
              &AccessState->SubjectSecurityContext,
              FALSE, AccessState->OriginalDesiredAccess, ...);
```

**我的洞见——SeAccessCheck 是"授权决策的仲裁者"**：

SeAccessCheck 的第一性原理是**在"声明式策略"（DACL）和"运行时身份"（Token）之间做匹配**：

> 📌 **三个关键设计决策**：
> 
> 1. **内核态快速路径**：内核模式代码默认绕过检查（`if (AccessMode == KernelMode)`），除非显式指定 `OBJ_FORCE_ACCESS_CHECK`——这是因为内核代码被认为可信
> 2. **特权覆盖**：某些特权（如 `SeBackupPrivilege`、`SeDebugPrivilege`）可以绕过 DACL 检查——这是"管理员万能"的根源
> 3. **累积授权**：多个 ACE 的权限累积，让用户获得其用户 SID + 所有组 SID 的并集权限

**特权与 DACL 的关系**：

特权（Privilege）是**账户级**的能力，DACL 是**对象级**的权限。两者的交互：

```
DACL 拒绝访问 + Token 有覆盖特权 → 允许访问
DACL 允许访问 + Token 无特权 → 允许访问
DACL 拒绝访问 + Token 无特权 → 拒绝访问
```

典型的特权覆盖场景：

- **`SeBackupPrivilege`**：绕过文件 DACL 读取（备份软件用）
- **`SeDebugPrivilege`**：打开任意进程（调试器用）
- **`SeRestorePrivilege`**：绕过文件 DACL 写入（恢复软件用）
- **`SeTakeOwnershipPrivilege`**：夺取对象所有权

**现代映照**：现代 Windows 的访问检查增加了：

- **完整性级别检查**：在 DACL 检查之前执行，低 IL 不能写高 IL
- **AppContainer 能力检查**：UWP 应用需要 Capability 匹配
- **VBS 增强**：关键检查在安全内核中执行
- **Conditional ACE**：Windows Server 的集中式授权策略使用，基于用户/设备属性动态评估

工业界：理解访问权限检查是**权限提升研究、沙箱逃逸检测**的核心。典型的攻击链：

1. **令牌窃取**：`OpenProcessToken` + `DuplicateToken` 获取 SYSTEM 令牌
2. **特权启用**：`AdjustTokenPrivileges` 启用 `SeDebugPrivilege`
3. **绕过 DACL**：用 `SeDebugPrivilege` 打开系统进程
4. **注入代码**：`WriteProcessMemory` 注入恶意代码

现代 EDR 通过以下方式检测：

- 监控 `SeAssignPrimaryToken`、`AdjustTokenPrivileges` 的调用
- 监控异常 DACL 修改（`IRP_MJ_SET_SECURITY`）
- 监控受限令牌的创建（沙箱逃逸指标）
- 使用 ETW 事件 `Microsoft-Windows-Security-Auditing` 记录访问检查结果

## 全章串联：一次 OpenProcess 的完整访问检查

```
应用程序：OpenProcess(PROCESS_VM_READ, FALSE, 1234)
  ↓
【用户态】
kernel32!OpenProcess
  ↓
NtOpenProcess（系统调用，进入内核）
  ↓
【内核态】
PspOpenProcess
  ↓
获取调用线程的 Token（从 ETHREAD 中）
  ↓
获取目标进程的 SecurityDescriptor
  ↓
构造 SUBJECT_SECURITY_CONTEXT
  ↓
SeAccessCheck(
    TargetProcess->SecurityDescriptor,  // SD
    &SubjectSecurityContext,           // 调用者的 Token
    FALSE,                              // 不锁定
    PROCESS_VM_READ,                    // 请求的权限
    0,                                  // 之前已授予的权限
    NULL,                               // 特权集
    &PsProcessType->GenericMapping,     // 通用权限映射
    PreviousMode,                       // UserMode
    &GrantedAccess,                     // 输出
    &AccessStatus)                      // 输出
  ↓
SeAccessCheck 内部：
  1. 通用权限映射：PROCESS_VM_READ → 具体权限位
  2. 遍历目标进程 DACL 的 ACE
  3. 匹配调用者 Token 中的 SID（用户 SID + 组 SID）
  4. 按优先级处理（显式拒绝 > 显式允许）
  5. 特权检查：调用者是否有 SeDebugPrivilege？
  6. 完整性级别检查：调用者 IL >= 目标进程 IL？
  ↓
决策：
  - 匹配允许 ACE 且无拒绝 → 允许
  - 匹配拒绝 ACE → 拒绝
  - 无匹配 ACE → 隐式拒绝
  - 有 SeDebugPrivilege → 覆盖 DACL 检查
  ↓
【结果】
成功 → 创建句柄，GrantedAccess 缓存到句柄表
失败 → 返回 STATUS_ACCESS_DENIED
  ↓
【用户态】
OpenProcess 返回句柄 或 NULL（GetLastError=ERROR_ACCESS_DENIED）
```

**这张图揭示了第12章的真正主线**：

1. **12.1 概述**：Windows 安全模型 = 认证 + 授权，SRM 是裁判
2. **12.2 证章（Token）**：主体的安全身份护照（SID + 组 + 特权）
3. **12.3 安全描述块和 ACL**：客体的自我保护策略（Owner + DACL + SACL）
4. **12.4 访问权限检查**：SeAccessCheck 执行"Token vs SD"的比对仲裁

**与前十一章的联系**：

- 第2章系统调用 → `NtOpenProcess` 等进入内核，触发访问检查
- 第4章对象管理 → 每个安全对象都有 SecurityDescriptor；句柄表缓存 GrantedAccess
- 第5章进程与线程 → 进程/线程是安全对象，有自己的 SD 和 Token
- 第6章进程间通信 → 命名管道、邮槽的访问检查
- 第7章视窗报文 → 窗口station/windowstation 的 IL 检查
- 第9章设备驱动 → 设备对象有自己的 SD，驱动的 IRP 处理中调用 SeAccessCheck
- 第10章网络 → AFD 的 socket 对象访问检查
- 第11章文件操作 → 文件对象在 IRP_MJ_CREATE 中执行访问检查

## 工业界实际应用与安全视角

### 🛡️ 安全领域

**1. 权限提升与防御**：

- **令牌窃取**：`OpenProcessToken` + `DuplicateToken` + `ImpersonateLoggedOnUser`
- **特权启用**：`AdjustTokenPrivileges` 启用 `SeDebugPrivilege`
- **防御**：LSASS 保护（RunAsPPL）、Credential Guard、HVCI
- **检测**：EDR 监控令牌操作

**2. DACL 篡改攻击与防御**：

- **攻击**：`SetSecurityDescriptorDacl` 修改关键对象的 DACL，获取持久化
- **防御**：PatchGuard 保护关键系统对象的 SD；WMI/ETW 监控 DACL 变化
- **检测**：Sysmon Event ID 4670（权限修改）

**3. 沙箱与 AppContainer**：

- **沙箱逃逸**：通过受限令牌的 DenyOnly SID 弱点逃逸
- **AppContainer**：UWP/Edge 使用 Capability SID 实现细粒度隔离

**4. 完整性级别与 UAC**：

- **UAC 绕过**：通过 DLL 劫持、服务漏洞等获取 High IL 令牌
- **防御**：UIPI（用户界面特权隔离）、IL 强制检查

### ⚙️ 工业应用

**1. 企业权限治理**：

- 通过组策略批量设置 DACL
- 使用 `icacls.exe` 管理文件和目录权限
- 使用 `Set-Acl` PowerShell cmdlet 自动化权限管理

**2. 服务账户安全**：

- 服务使用专门的 Service Account，Token 中只包含必要的特权
- Managed Service Account（gMSA）自动管理密码和 SPN

**3. 文件系统过滤与 EDR**：

- minifilter 在 IRP_MJ_CREATE 中执行额外的访问检查
- EDR 通过 `IRP_MJ_SET_SECURITY` 回调监控 DACL 修改
- 防勒索软件通过监控异常的文件访问模式

**4. 虚拟化安全**：

- Hyper-V VM 的 Worker Process 使用受限令牌
- VBS 将授权决策的关键部分放到 VTL1 安全内核

## 给你的读书建议

1. **重点理解"Token vs SD"的仲裁模型**：这是 Windows 安全的灵魂。任何安全对象的访问都归结为这两个结构的比对。
2. **clone ReactOS 源码，重点看**：
    - `ntoskrnl/se/accesschk.c`：SeAccessCheck 的完整实现（**必读**）
    - `ntoskrnl/se/token.c`：令牌的创建、复制、模拟
    - `ntoskrnl/se/priv.c`：特权常量定义
    - `ntoskrnl/ob/obsecure.c`：对象管理器的安全描述符操作
    - `drivers/filesystems/fastfat_new/acchksup.c`：文件系统如何调用 SeAccessCheck
3. **用 WinDbg 实操**：
    - `!token <ETHREAD>`：查看线程的令牌
    - `!sd <SecurityDescriptor>`：查看安全描述符
    - `!acl <DACL>`：查看 DACL 内容
    - `bp nt!SeAccessCheck`：观察访问检查入口
    - `bp nt!NtOpenProcess`：观察进程打开时的访问检查
4. **用 Sysinternals 工具实地观察**：
    - **Process Explorer**：查看进程的 Token（SID、组、特权、IL）
    - **Process Monitor**：实时捕获 Access Check 事件（显示 Granted Access）
    - **AccessChk**：`accesschk.exe -v C:\Windows` 查看对象的 DACL
5. **实验：创建受限令牌**：
    
    ```
    // 创建一个去除 Administrators 组的受限令牌
    CreateRestrictedToken(hExistingToken, ..., &hRestrictedToken);
    // 用受限令牌模拟，观察访问检查结果的变化
    ```
    
6. **下一章（第13章，如果有）可能深入注册表、配置管理器或其他系统机制**。注册表的 key 也是安全对象，每个 key 有自己的 SecurityDescriptor——这正是本章访问检查模型的延伸应用。

书是 2009 年的，但基于 ReactOS 的 SRM 实现**在核心设计上与今天的 Windows 10/11 高度一致**——变的只是：

- **完整性级别（IL）**：Windows Vista 引入，增加了第四维检查
- **AppContainer 与 Capability**：Windows 8 引入，用于 UWP 沙箱
- **VBS/HVCI**：将 SRM 的关键数据结构和决策逻辑放到安全内核保护
- **Conditional ACE 与集中式授权**：Windows Server 的动态访问控制

抓住"**Token 表达身份 + SD 声明策略 + SeAccessCheck 执行仲裁**"这三个第一性原理，你就能穿透任何版本的 Windows 安全模型。
