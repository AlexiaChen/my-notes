
第7章是整本书的"奇点"——前面你学了对象（第4章）、进程线程（第5章）、IPC（第6章），这一章把所有这些都拉进了一个**特殊战场：Win32k 图形子系统**。这里的内核不再是纯粹的 ntoskrnl，而是 win32k.sys——它运行在 Ring0，却要处理大量本应在用户态的 GUI 逻辑；它走的是"影子系统调用表"（Shadow SSDT）而非普通 SSDT；它的核心操作模式是"内核发起、用户态完成、再回到内核"的双向通道。整章 7.1~7.8 就是这条双向通道的完整解剖。

我的核心洞见先抛在前面：**视窗报文的本质是"以内核态 Win32k 为调度中枢、以用户态回调为执行末端"的跨特权级消息总线**。SendMessage 表面是"发个消息"，底层是跨线程的同步 RPC；KeUserModeCallback 表面是"回调一下"，底层是内核主动降特权去执行用户代码；RIT（Raw Input Thread）表面是"处理键鼠"，底层是把硬件中断翻译成 VIQ（Virtualized Input Queue）消息的内核线程。理解了这个"跨特权级"本质，你就能解释为什么 Win32k 是 Windows 内核漏洞的最高危区域——CVE-2015-2546 等漏洞就出在"回调返回后内核未重新校验用户态可能销毁的对象"这条信任边界上。

> 💡 读这一章的正确姿势：时刻记住"现在有两个执行上下文在交织"——Ring0 的 Win32k（管消息队列、窗口对象、焦点、调度）和 Ring3 的 user32（管 WndProc、Hook、实际绘制）。NtUserMessageCall 是连接两者的门，KeUserModeCallback 是反向的门。每一次消息处理都是这两扇门之间的往返。

## 7.1 视窗线程与 Win32k 扩充系统调用

**书的脉络**：普通线程（ETHREAD）一旦创建窗口或参与 GUI，就升级为"视窗线程"——Win32k 在 ETHREAD 上挂载 PTHREADINFO（内核态）结构，在 TEB 上挂载 CLIENTINFO（用户态）结构。PTHREADINFO 包含：

- **消息队列**：Sent Messages、Posted Messages、Hardware Messages、Paint Messages、Timer Messages 五个子队列
- **窗口列表**：该线程创建的所有 WND 对象
- **钩子链**：WH_KEYBOARD、WH_MOUSE、WH_CALLWNDPROC 等钩子
- **IME/键盘布局**：每线程独立
- **线程局部状态**：焦点窗口（spwndFocus）、激活窗口（spwndActive）、捕获窗口（spwndCapture）、退出代码
- **回调内存**：用于内核态/用户态参数传递

**Win32k 扩充系统调用**：普通系统调用走 `KiSystemService` → ntoskrnl 的 `KeServiceDescriptorTable`（SSDT）。但 GUI 相关的系统调用（NtUser_、NtGdi_）走的是 **Shadow SSDT**——由 win32k.sys 提供的第二张系统调用表：

```
用户态 user32.dll/GDI32.dll
  ↓ syscall (int 0x2E / sysenter)
KiSystemService
  ↓ 根据调用号高位判断
  ├─ 0x0000-0x0FFF → ntoskrnl!KeServiceDescriptorTable (SSDT)
  └─ 0x1000-0x1FFF → win32k!KeServiceDescriptorTableShadow (Shadow SSDT)
  ↓
win32k!NtUserMessageCall / NtUserGetMessage / NtUserCreateWindowEx ...
  ↓
UserEnterExclusive()  // 获取全局 USER 锁
  ↓
按 FNID_* 分发
```

**我的洞见——"视窗线程"是 NT 线程的 GUI 特化**：

ETHREAD 是调度器视角的线程（第5章），PTHREADINFO 是 Win32k 视角的线程——后者在前者基础上扩展出"消息队列 + 窗口所有权 + 钩子状态"。这意味着：

- 一个线程可以**不是**视窗线程（纯控制台/服务线程，没有 PTHREADINFO）
- 一旦调用 `CreateWindowEx` 或 `GetMessage`，Win32k 就在 ETHREAD 上挂起 PTHREADINFO，线程"升级"为视窗线程
- **全局 USER 锁**（UserEnterExclusive/UserLeave）是 Win32k 的"Big Kernel Lock"——任何 NtUser* 调用都要拿这把锁，保证 GUI 状态的串行化访问

> 📌 **Shadow SSDT 的存在意义**：ntoskrnl 的 SSDT 是"通用系统调用表"，win32k 的 Shadow SSDT 是"GUI 专用系统调用表"。分离的原因是 Win32k 可以独立加载/卸载，且 GUI 系统调用数量庞大（NtUser* 有数百个）。这种"主表+影子表"的设计让 Windows 的 GUI 子系统成为一个**可加载的内核扩展**——这也是为什么现代 VBS 环境下可以通过 Win32k Filter 限制某些进程不加载 Win32k。

**现代映照**：现代 Windows 10/11 中，win32k.sys 拆分为三个驱动：win32k.sys（基础）、win32kbase.sys（基础服务）、win32kfull.sys（完整 GUI）。Shadow SSDT 仍然存在，但调用号空间已扩展。关键演进：

- **Win32k Filter**：通过 `Win32kFilter` 注册表项，可以禁止特定进程加载 Win32k——这是减少攻击面的关键手段（Edge、Chrome 等浏览器渲染进程默认禁用 Win32k）
- **VBS 下的 Win32k 隔离**：敏感窗口操作需经安全内核验证
- **WSL2 不需要 Win32k**：Linux 子系统完全绕过 GUI 子系统

工业界：理解 Shadow SSDT 是**安全软件做 GUI 层 Hook 的基础**。传统 SSDT Hook 技术 Hook ntoskrnl 的 SSDT，而现代 EDR 更多使用**ObRegisterCallbacks**​ 和 **ETW**​ 来监控——因为 PatchGuard（KPP）会检测 Shadow SSDT 的修改并触发 BSOD。

## 7.2 视窗报文的接收

**书的脉络**：`GetMessage`/`PeekMessage` 是消息循环的心脏。用户态调用最终陷入 `win32k!NtUserGetMessage`，内核按 **MSDN 规定的优先级**依次扫描各种消息源：

```
1. Sent Messages（被发送的消息，优先级最高）
   ↓
2. Posted Messages（被投递的消息）
   ↓
3. Hardware Messages（键盘/鼠标等硬件消息）
   ↓
4. Sent Messages（再次检查，处理嵌套 SendMessage）
   ↓
5. Paint Messages（WM_PAINT）
   ↓
6. Timer Messages（WM_TIMER）
   ↓
7. WM_QUIT（退出消息）
```

`GetMessage` 是**阻塞**的——没有消息时线程进入等待状态（WaitReason = UserRequest），让出 CPU；`PeekMessage` 是**非阻塞**的——没有消息立即返回 FALSE。

**我的洞见——消息接收的本质是"按优先级调度的多源队列消费"**：

Win32k 不是简单的"从队列取一个消息"，而是**六个不同队列的优先级调度器**。这个设计的精妙之处在于：

- **Sent Messages 优先级最高**：因为 SendMessage 是同步的，发送方线程在等待，必须优先处理以避免死锁
- **Hardware Messages 排在 Posted Messages 之后**：听起来违反直觉，但这是故意的——如果硬件消息优先级高于 Posted，那么 SendMessage 的回复就会饥饿
- **Paint/Timer 最低**：这两个是"有机会才处理"的消息，不应阻塞关键路径

> 💡 **为什么需要 6 个独立队列而不是 1 个？**​ 因为不同类型的消息有不同的生命周期：Sent 消息需要等待/回复机制（USER_SENT_MESSAGE 结构 + Completion Event），Posted 消息是单向入队，Hardware 消息来自 RIT 线程，Paint 消息是"按需合成"的（只有窗口无效区非空才生成）。分开存储让每种消息的处理逻辑清晰独立。

**Sent Message 的同步机制**：

```
线程 A: SendMessage(hwndB, WM_XXX, ...) → NtUserMessageCall(FNID_SENDMESSAGE)
  ↓
Win32k 构造 USER_SENT_MESSAGE 结构
  ├─ 发送方线程 ID
  ├─ 接收方窗口
  ├─ 消息内容
  └─ pkCompletionEvent（完成事件）
  ↓
线程 A 调用 KeWaitForMultipleObjects(pkCompletionEvent, ...) → 阻塞
  ↓
Win32k 切换到线程 B 的上下文，调用 B 的 WndProc
  ↓
B 的 WndProc 返回 → Win32k 调用 ReplyMessage → SetEvent(pkCompletionEvent)
  ↓
线程 A 被唤醒，从 NtUserMessageCall 返回
```

这是第6章"LPC 是跨进程同步 RPC"思想在 GUI 子系统里的具体实现——**SendMessage 就是针对窗口的同步 RPC**。

**现代映照**：消息优先级调度机制在现代 Windows 中完全一致。工业界应用：

- **消息钩子（WH_GETMESSAGE）**：在 GetMessage 返回用户态之前拦截消息，是实现键盘记录器、消息注入的经典位置
- **消息死锁检测**：Win32k 在 SendMessage 时检测"A 等 B、B 等 A"的环路，超时时返回 `WAITE_TIMEOUT` 或 `WAIT_TIMEOUT`
- **MsgWaitForMultipleObjects**：GUI 线程同时等待内核对象和消息队列，是现代 UI 框架（WinForms、WPF、Qt）事件循环的基础

## 7.3 Win32k 的用户空间回调机制

**书的脉络**：这是整章**最重要的一节**——Win32k 运行在 Ring0，但 WndProc、Hook 过程、IME 处理等用户代码运行在 Ring3。内核如何调用用户态代码？答案是 **KeUserModeCallback**。

完整流程：

```
Win32k (Ring0)
  ↓ KeUserModeCallback(ApiNumber, Input, InputLength, &Output, &OutputLength)
  ↓
构造回调帧：KAPC_FRAME + KTRAP_FRAME
TrapFrame->Eip = KeUserCallbackDispatcher  // ntdll 中的分发器
通过 KiServiceExit 返回用户态
  ↓
ntdll!KiUserCallbackDispatcher
  ↓
查 PEB.KernelCallbackTable[ApiNumber]  // 用户态回调表
  ↓
调用 user32.dll 中的对应函数
（如 __fnCOPYDATA、__fnNCDESTROY 等）
  ↓
user32 完成后调用 NtCallbackReturn()
  ↓
内核恢复原始 TrapFrame，继续执行 Win32k
```

**回调类型（ApiNumber）**：`USER32_CALLBACK_*` 枚举定义了几十种回调，包括：

- `USER32_CALLBACK_WINDOWPROC`：调用窗口过程（WndProc）
- `USER32_CALLBACK_HOOKPROC`：调用钩子过程
- `USER32_CALLBACK_EVENTPROC`：调用事件回调
- `USER32_CALLBACK_LOADDLR`：加载 DLL
- `USER32_CALLBACK_CBT`：CBT 钩子
- `USER32_CALLBACK_CLIENTSTRING`：处理 ANSI/Unicode 字符串转换

**消息参数打包/解包**：跨边界传递复杂参数时，Win32k 使用 `PackParam`/`UnpackParam` 序列化 lParam 中的指针（如 CREATESTRUCT、COPYDATASTRUCT），因为用户态和内核态地址空间不同。

**我的洞见——KeUserModeCallback 是"反向系统调用"，是 Win32k 信任模型的阿喀琉斯之踵**：

普通系统调用是"用户态 → 内核态"（通过 syscall/sysenter），内核完全信任自己；而 KeUserModeCallback 是"内核态 → 用户态"——**内核主动降特权去执行用户代码，然后还要信任返回的結果**。

这个"信任边界"极其危险，因为：

- 用户态回调期间，用户代码可以**销毁内核正在操作的窗口/菜单/钩子**
- 用户态回调返回后，Win32k 必须**重新校验所有内核对象的有效性**
- 如果校验缺失 → Use-After-Free → 内核提权

> ⚠️ **CVE-2015-2546 就是这个信任边界的崩塌**：`xxxMNMouseMove` 在处理菜单鼠标移动时，通过 `xxxSendMessage` 发起用户态回调。攻击者在回调中销毁 Menu 窗口、释放 tagPOPUPMENU 对象、然后用 Accelerator Table 占位重用。回调返回内核后，`xxxMNMouseMove` **未重新校验**​ pPopupMenu 指针，继续使用已被攻击者控制的 UAF 对象，最终实现内核任意代码执行。补丁新增的检查就是：回调返回后重新验证 `tagMENUWND->pPopupMenu` 是否被修改过。

**现代映照**：KeUserModeCallback 机制在现代 Windows 中完全一致，KernelCallbackTable 仍在 PEB 中（偏移 0x58）。但攻击面持续演化：

- **HVCI 的局限**：HVCI 通过 EPT 将内核代码页强制设为只读只执行，成功封堵了传统的内联 Hook 和代码段篡改。但 HVCI **无法阻止 KeUserModeCallback 滥用**——因为这个机制本身就是设计用来从内核回调用户态的
- **Win32k 回调绕道注入（2024 年新披露）**：攻击者不再直接覆盖 KernelCallbackTable 表项（易被完整性校验检测），而是解析表中合法回调目标（如 `__fnCOPYDATA`），在函数入口处**安装内联钩子**（inline hook），跳转到 shellcode。由于修改的是 user32.dll 中的函数序言而非 PEB 表本身，传统的回调表完整性检查失效。触发方式：向目标窗口 `SendMessage(WM_COPYDATA)`——通过正常的 GUI 回调路径执行 shellcode

**工业防守**：现代 EDR 检测这类攻击的手法：

- 监控 **KernelCallbackTable 引用函数的意外内联修改**（特别是 user32.dll 中的回调例程）
- 关联 **NtAllocateVirtualMemory(PAGE_EXECUTE_READWRITE) + NtWriteVirtualMemory + SendMessage(WM_COPYDATA)**​ 的异常序列
- 使用 **内存完整性校验**（如 Microsoft 的 VBS HVCI + 受保护的代码完整性 CI）

## 7.4 用户空间的外挂函数

**书的脉络**：所谓"外挂函数"，指的就是通过 KeUserModeCallback 回调到用户态的各种处理函数：

- **窗口过程（WndProc）**：每个窗口类都有一个 WndProc，通过 `RegisterClass` 注册
- **钩子过程（HookProc）**：通过 `SetWindowsHookEx` 安装，如 WH_KEYBOARD、WH_MOUSE、WH_CALLWNDPROC、WH_GETMESSAGE 等
- **DLL 回调**：如 `co_IntClientLoadLibrary`——Win32k 需要加载用户态 DLL 时回调
- **IME 回调**：输入法编辑器处理
- **子类化（Subclassing）**：通过 `SetWindowLong(GWL_WNDPROC)` 替换窗口过程

**我的洞见——"外挂函数"是 Windows GUI 扩展性的根基，也是攻击面的源头**：

Win32k 之所以能支持无穷无尽的 GUI 行为（自定义控件、输入法、辅助功能、屏幕录制、消息拦截），就是因为所有的"具体行为"都外挂到用户态实现。内核只管"什么时候调用、调用哪个"，用户态管"调用后干什么"。

但这种扩展性带来严重安全风险：

- **全局钩子（WH_KEYBOARD_LL/WH_MOUSE_LL）**：可以拦截系统中所有键鼠输入——键盘记录器的标准实现
- **SetWindowsHookEx 注入**：通过在目标线程安装钩子，强制目标线程加载攻击者的 DLL
- **WndProc 子类化**：替换窗口过程，拦截/篡改消息流

> 📌 **SetWindowsHookEx 注入的原理**：`SetWindowsHookEx(WH_GETMESSAGE, hHookProc, hMod, tidTarget)` 安装钩子时，Win32k 会把 hMod（攻击者 DLL）注入到目标线程的进程空间。当目标线程调用 GetMessage 时，Win32k 通过 KeUserModeCallback 调用钩子过程——此时攻击者 DLL 已在目标进程中加载。这是 Windows 上最经典的 DLL 注入技术之一。

**现代映照**：现代 Windows 对钩子机制进行了多重限制：

- **Win32k Filter**：通过注册表 `HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\Win32kFilter` 禁止特定进程加载 Win32k，从根本上消除钩子攻击面（Edge、Chrome 渲染进程默认启用）
- **VBS 隔离**：敏感进程的 GUI 操作被隔离到 VTL1
- **HVCI**：防止内核代码页被篡改，但**无法阻止用户态钩子**（因为钩子本来就应该在用户态）

工业界：现代 EDR 普遍监控 `SetWindowsHookEx` 的调用，特别是：

- 跨会话/跨完整性级别的钩子安装
- 钩子 DLL 来自非常规路径（如临时目录、无签名 DLL）
- 全局钩子（WH_KEYBOARD_LL/WH_MOUSE_LL）的安装

## 7.5 视窗报文的发送

**书的脉络**：发送消息有 4 种变体：

1. **co_IntSendMessage**：同步发送，等待回复
2. **co_IntSendMessageTimeoutSingle**：带超时的同步发送
3. **co_IntSendMessageNoWait**：异步发送，不等待
4. **co_IntSendMessageWithCallBack**：带回调的发送

**同线程 vs 跨线程的优化路径**：

```
SendMessage(hwnd, msg, wParam, lParam)
  ↓
user32!SendMessageW → NtUserMessageCall(FNID_SENDMESSAGE)
  ↓
Win32k 判断接收窗口的所属线程：
  ├─ 同线程同窗口 → 直接调用 WndProc（fast path，无系统调用开销）
  └─ 跨线程/跨进程 → 走完整 RPC 路径
       ↓
       构造 USER_SENT_MESSAGE
       ↓
       发送方：KeWaitForMultipleObjects(pkCompletionEvent)
       接收方：被调度执行 WndProc
       ↓
       接收方 ReplyMessage → SetEvent
       ↓
       发送方唤醒，返回结果
```

**跨进程边界检查**：某些敏感消息禁止跨进程发送：

- `WM_CREATE`、`WM_INITDIALOG`：只能在窗口创建时由系统发送
- 密码框相关消息：防止跨进程窃取密码
- `WM_COPYDATA`：虽然可以跨进程，但需要特殊权限

**死锁检测**：SendMessage 可能死锁（A 等 B 的回复，B 同时等 A 的回复）。Win32k 的解决方案：

- 维护线程的"等待链"
- 检测到环路时，返回 `WAIT_TIMEOUT` 或触发特殊处理
- 超时时间默认为 `SMTO_NORMAL` = 5 秒（可通过 `SendMessageTimeout` 调整）

**我的洞见——SendMessage 是"窗口对象上的同步 RPC"，PostMessage 是"窗口对象上的异步消息队列写入"**：

|维度|SendMessage|PostMessage|
|---|---|---|
|同步性|同步（阻塞等待）|异步（立即返回）|
|底层机制|USER_SENT_MESSAGE + Completion Event|消息入队到目标线程的 Posted 队列|
|跨线程|需要线程切换 + 等待|直接入队，无需等待|
|返回值|接收方 WndProc 的返回值|TRUE/FALSE（入队成功与否）|
|典型用途|查询窗口状态、请求操作|通知事件、触发处理|

> 💡 **SendMessage 跨线程时的"线程切换"本质**：发送方线程阻塞在 `pkCompletionEvent` 上，调度器切换到接收方线程执行 WndProc，执行完后唤醒发送方。这意味着**SendMessage 跨线程调用会导致发送方线程的上下文切换**——这就是为什么 UI 线程中不应该向其他线程 SendMessage 耗时操作，否则会导致 UI 卡顿。

**现代映照**：SendMessage/PostMessage 机制在现代 Windows 中一致。工业界应用：

- **COM 的跨线程封送（Marshaling）**：COM 在跨线程调用时底层使用 SendMessage 实现同步
- **WinRT 的 UI 线程亲和性**：所有 UI 操作必须通过 SendMessage 转发到 UI 线程
- **Cobalt Strike Beacon**：通过 `PostMessage` 向隐蔽窗口发送控制消息，规避网络检测

## 7.6 键盘输入线程

**书的脉络**：键盘输入的处理流程：

```
硬件中断（键盘 IRQ 1）
  ↓
键盘端口驱动（i8042prt.sys）→ 类驱动（kbdclass.sys）
  ↓
kbdclass 维护按键记录缓冲区
  ↓
Win32k!RawInputThread 通过 ZwReadFile 读取
  ↓
InputApc 回调 → win32k!ProcessKeyboardInput
  ↓
遍历按键记录：
  ├─ VKFromVSC：扫描码 → 虚拟键码（VK）转换
  ├─ xxxProcessKeyEvent：更新全局按键状态数组
  ├─ 调用 WH_KEYBOARD_LL 钩子
  ├─ 处理热键（_RegisterHotKey）
  ├─ 向 gpqForeground 队列投递按键消息
  ↓
目标线程的 VIQ 收到 WM_KEYDOWN/WM_KEYUP/WM_CHAR
```

**关键数据结构**：

- **gafAsyncKeyState**：异步按键状态数组，供 `GetAsyncKeyState`/`GetKeyState` 查询
- **gptiForeground**：前台线程（接收键盘输入的线程）
- **spwndFocus**：焦点窗口（接收键盘消息的窗口）

**RIT（Raw Input Thread）的架构**：RIT 是 Win32k 创建的系统线程，它通过 `KeWaitForMultipleObjects` 同时等待键盘设备、鼠标设备和定时器。当有输入时，APC（InputApc）被触发，调用 `ProcessKeyboardInput` 或 `ProcessMouseInput`。

**我的洞见——键盘输入是"硬件中断 → 内核线程 → 消息队列"的三段式流水线**：

```
① 硬件层：IRQ 1 中断 → kbdclass 缓冲区
② 内核线程层：RIT 通过 ZwReadFile 读取 → 翻译为 VK 码 → 调用 LL 钩子
③ 消息层：向目标线程 VIQ 投递 WM_KEYDOWN/WM_KEYUP
```

这个流水线的精妙之处在于**解耦**：

- **硬件中断处理极快**：只是把扫描码放入缓冲区，立即返回
- **RIT 线程做翻译**：扫描码 → VK 码 → 字符（通过键盘布局和 IME）
- **目标线程异步处理**：从 VIQ 取出消息，调用 WndProc

> ⚠️ **为什么键盘消息只发给前台线程？**​ 因为 Windows 的设计哲学是"当前用户正在交互的窗口才应该接收键盘输入"。RIT 维护 `gptiForeground` 指向当前前台线程，所有键盘消息都投到这个线程的 VIQ。Alt+Tab 切换窗口的本质就是改变 `gptiForeground`。

**现代映照**：键盘输入模型在现代 Windows 中基本一致，但增加了：

- **Raw Input API**：通过 `RegisterRawInputDevices` 可以直接接收原始输入数据（扫描码级别），绕过消息翻译
- **Windows Hello/Passkey**：生物识别输入作为特殊键盘输入处理
- **VBS 下的键盘保护**：敏感进程的键盘输入通过 VTL1 隔离，防止 keylogger

工业界：

- **键盘记录器**：通过 `SetWindowsHookEx(WH_KEYBOARD_LL)` 实现全局键盘钩子，是 malware 的经典手法
- **EDR 检测**：监控 `WH_KEYBOARD_LL` 钩子的安装，特别是跨会话安装的钩子
- **游戏反作弊**：通过 Raw Input API 读取原始输入，防止鼠标宏

## 7.7 鼠标器输入线程

**书的脉络**：鼠标输入比键盘复杂得多：

- **多种输入类型**：移动、左/中/右键、XButton、滚轮、水平滚轮、触摸板手势
- **高频事件**：鼠标移动产生的事件频率极高，需要消息合并（Coalesce）
- **空间敏感性**：鼠标消息的路由取决于光标位置（Hit-Test）
- **捕获机制**：鼠标按下后可以"捕获"到特定窗口（SetCapture）
- **双击判定**：基于时间间隔 + 位置距离
- **Hover/Leave 跟踪**：基于定时器

RIT 处理鼠标输入的流程：

```
硬件中断（鼠标 IRQ 12）
  ↓
鼠标端口驱动（i8042prt.sys）→ 类驱动（mouclass.sys）
  ↓
mouclass 维护输入数据
  ↓
RIT 通过 ZwReadFile 读取 → InputApc → win32k!ProcessMouseInput
  ↓
ProcessMouseInput：
  ├─ 更新光标坐标
  ├─ 调用 WH_MOUSE_LL 钩子
  ├─ 调用 GreMovePointer 移动光标
  ├─ Hit-Test 确定目标窗口
  ├─ 检查鼠标捕获（spwndCapture）
  ├─ 消息合并（Coalesce WM_MOUSEMOVE）
  ├─ 双击判定
  ↓
向目标线程 VIQ 投递 WM_MOUSEMOVE/WM_LBUTTONDOWN/...
```

**消息合并（Coalesce）的必要性**：鼠标移动事件频率可达 1000Hz，如果不合并，消息队列会爆炸。Win32k 的做法是：在 RIT 处理鼠标输入时，**只保留最新的 WM_MOUSEMOVE**，丢弃中间的移动事件。这样目标线程收到的 WM_MOUSEMOVE 反映的是当前光标位置，而不是历史轨迹。

**我的洞见——鼠标输入是"高频事件流 + 空间路由 + 消息合并"的三位一体**：

与键盘输入"线性流水线"不同，鼠标输入是**网状路由**：

- **空间维度**：根据光标位置 Hit-Test 决定消息发给哪个窗口
- **时间维度**：消息合并压缩高频事件
- **状态维度**：捕获状态、双击状态、按钮状态共同决定消息类型

> 💡 **为什么鼠标消息不只用"前台线程"？**​ 因为鼠标是空间敏感的——用户点击哪个窗口，消息就应该发给哪个窗口。所以 RIT 在路由鼠标消息时，通过 `Win32k!HITTEST` 找到光标下的窗口，再找到该窗口的所属线程，把消息投到这个线程的 VIQ。这与键盘消息"只投前台线程"形成鲜明对比。

**现代映照**：鼠标输入模型在现代 Windows 中一致，但增加了：

- **高精度鼠标**：5K/8K Hz 游戏鼠标需要更精细的消息合并策略
- **触控屏**：Touch 输入作为特殊的"鼠标输入"处理，但通过 Raw Input API 单独暴露
- **Pen/Stylus**：Windows Ink 平台使用单独的输入管线

工业界：

- **鼠标劫持**：通过 `SetCapture` + `SetWindowsHookEx(WH_MOUSE_LL)` 实现鼠标事件拦截和篡改
- **游戏外挂**：通过 Raw Input API 读取原始鼠标数据，实现"自瞄"；通过 `SendMessage` 伪造鼠标点击
- **EDR 检测**：监控异常的 `SetCapture` 调用和跨进程鼠标消息注入

## 7.8 默认的报文处理

**书的脉络**：当应用程序的 WndProc 不处理某个消息时，会调用 `DefWindowProc` 进行默认处理。`DefWindowProc` 在内核态对应 `IntDefWindowProc`，通过 `NtUserMessageCall(FNID_DEFWINDOWPROC)` 调用。

`IntDefWindowProc` 的核心逻辑：

```
LRESULT FASTCALL IntDefWindowProc(
    PWND Wnd, UINT Msg, WPARAM wParam, LPARAM lParam, BOOL Ansi)
{
    PTHREADINFO pti = PsGetCurrentThreadWin32Thread();
    LRESULT lResult = 0;
    USER_REFERENCE_ENTRY Ref;
    
    if (Msg > WM_USER) return 0;  // WM_USER 以上的应用私有消息不处理
    
    switch (Msg) {
        /* 100+ cases */
        case WM_PAINT: ...
        case WM_CLOSE: ...
        case WM_DESTROY: ...
        case WM_NCPAINT: ...
        case WM_NCCALCSIZE: ...
        case WM_NCHITTEST: ...
        // ... 系统定义的几百个消息
    }
}
```

**关键设计**：

- **WM_USER 以上的消息直接返回 0**：这些消息是应用程序私有的，系统不知道如何处理
- **Ansi 参数**：决定 WndProc 的字符集（ANSI/Unicode），用于子类化场景
- **USER_REFERENCE_ENTRY**：引用窗口对象，防止在处理期间窗口被销毁（UAF 防护）
- **调用方为 NtUserMessageCall**：通过 FNID_DEFWINDOWPROC 分发到此处

**我的洞见——DefWindowProc 是"系统消息的兜底处理器"，体现了"职责链模式"**：

Windows 的消息处理是一个**职责链**：

```
应用程序 WndProc → 不处理 → DefWindowProc → 系统默认行为
```

`IntDefWindowProc` 处理了几百个系统消息，包括：

- **窗口生命周期**：WM_CREATE、WM_DESTROY、WM_CLOSE、WM_NCDESTROY
- **绘制**：WM_PAINT、WM_NCPAINT、WM_ERASEBKGND
- **非客户区（标题栏、边框）**：WM_NCHITTEST、WM_NCCALCSIZE、WM_NCACTIVATE
- **大小位置**：WM_SIZE、WM_MOVE、WM_GETMINMAXINFO
- **滚动条**：WM_VSCROLL、WM_HSCROLL
- **系统命令**：WM_SYSCOMMAND、WM_?

> 📌 **为什么 WM_USER 以上的消息不处理？**​ 因为 WM_USER（0x0400）以上的消息是应用程序自定义的私有消息（如 `WM_APP+0`、`RegisterWindowMessage` 返回的）。系统无法知道这些消息的语义，所以直接返回 0。这是 Windows 消息空间的"用户态/系统态分界线"。

**DefWindowProc 的安全意义**：

`IntDefWindowProc` 中的 `USER_REFERENCE_ENTRY Ref` 是关键——它在处理消息前**引用窗口对象**，防止在处理期间窗口被其他线程销毁。这是 Win32k 防范 UAF 的基础机制之一。但在历史上，这个防护并非无懈可击——CVE-2015-2546 等漏洞正是因为在某些情况下，系统未正确重新校验回调返回后的对象有效性。

**现代映照**：DefWindowProc 机制在现代 Windows 中一致。工业界应用：

- **子类化（Subclassing）**：通过 `SetWindowLong(GWL_WNDPROC)` 替换 WndProc，在新 WndProc 中不处理的消息调用 `DefWindowProc`——这是 Windows GUI 编程的标准模式
- **超类化（Superclassing）**：基于已有窗口类创建新类，复用其 WndProc 并扩展
- **安全研究**：`IntDefWindowProc` 是 Win32k 攻击面的重灾区——大量 CVE（CVE-2014-4113、CVE-2018-0810、CVE-2021-1732、CVE-2021-40449、CVE-2024-21338）都涉及默认窗口过程的漏洞

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  ↓
kbdclass/mouclass 驱动缓冲区
  ↓
Win32k!RawInputThread (RIT)
  ↓ ZwReadFile + InputApc
  ↓

  ↓

  ↓

  ↓

  ↓

  ↓

  ↓

```

**与前六章的联系**：

## 工业界实际应用与安全视角

### 🛡️ Win32k 是 Windows 内核漏洞的最高危区域

历史 CVE 统计：

|CVE 编号|年份|漏洞类型|利用技术|
|---|---|---|---|
|CVE-2014-4113|2014|类型混淆|回调返回数据校验不足|
|CVE-2015-2546|2015|UAF|菜单窗口回调中销毁对象|
|CVE-2018-0810|2018|栈内存泄露|KeUserModeCallback 未初始化栈|
|CVE-2021-1732|2021|未初始化 + 回调|KernelCallback 信任边界瓦解|
|CVE-2021-40449|2021|GreResetDC UAF|回调中 ResetDC 触发 UAF|
|CVE-2024-21338|2024|appid.sys 权限绕过|PreviousMode + KernelCallbackTable|

**共同点**：都涉及 **KeUserModeCallback 信任边界**——内核回调用户态后，未正确重新校验内核对象的有效性。

### 🔑 现代注入技术：Win32k 回调绕道

2024 年披露的新型注入技术：

```
1. 读取目标进程 PEB.KernelCallbackTable（偏移 0x58）
2. 解析 __fnCOPYDATA 函数指针
3. 在目标进程分配可执行内存，写入 shellcode
4. 在 __fnCOPYDATA 函数序言安装 inline hook（跳转到 shellcode）
5. 向目标窗口 SendMessage(WM_COPYDATA) 触发回调
6. shellcode 执行完毕后恢复原始字节
```

**为什么这种技术难以检测**：

- **不创建远程线程**：规避传统线程注入检测
- **不改 KernelCallbackTable 表项**：规避 PEB/表完整性校验
- **修改的是 user32.dll 中的函数序言**：传统 Hook 检测可能忽略
- **通过正常 GUI 回调路径执行**：看起来像系统行为

**EDR 检测思路**：

- 监控 **NtAllocateVirtualMemory(PAGE_EXECUTE_READWRITE) + NtWriteVirtualMemory + SendMessage(WM_COPYDATA)**​ 的异常序列
- 监控 **user32.dll 中回调函数的入口点修改**（通过内存完整性校验）
- 关联 **跨进程 WM_COPYDATA 消息流量**与**近期内存权限变更**

### ⚙️ 现代 Windows 的 Win32k 加固

- **Win32k Filter**：通过注册表限制哪些进程可以加载 Win32k.sys（Edge、Chrome 渲染进程默认禁用）
- **VBS/HVCI**：通过 EPT 将内核代码页强制设为只读只执行，封堵内核代码篡改
- **Win32k 攻击面减少**：微软持续将高危 Win32k API 标记为 deprecated，推动开发者使用更安全的替代方案

### 🎯 给你的读书建议

1. **重点理解 KeUserModeCallback 的信任边界**——这是 7.3 节的核心，也是现代 Win32k 漏洞的根源
2. **clone ReactOS 源码，重点看**：
    - `win32ss/user/ntuser/message.c`：消息发送/接收的核心实现
    - `win32ss/user/ntuser/winctrl/win32k.rc`：资源文件
    - `ntoskrnl/ke/i386/usercall.c`：KeUserModeCallback 实现
    - `win32ss/user/ntuser/defwnd.c`：IntDefWindowProc 实现
3. **用 WinDbg 实操**：
    - `bp win32k!NtUserMessageCall`：观察消息发送的入口
    - `bp nt!KeUserModeCallback`：观察内核到用户态的回调
    - `!process 0 0` + `dt nt!_ETHREAD Win32Thread`：查看视窗线程结构
    - `dt win32k!_THREADINFO`：查看 PTHREADINFO 结构
4. **装 Windows 10/11 虚拟机 + WinDbg**，实地观察：
    - 用 Spy++ 观察消息流
    - 用 Process Monitor 观察 SendMessage/PostMessage
    - 用 Sysmon 监控 SetWindowsHookEx 和跨进程 WM_COPYDATA
5. **下一章（第8章 结构化异常处理）将深入 SEH/VEH**——这些机制在 Win32k 回调中扮演关键角色（回调期间的异常处理）

书是 2009 年的，但基于 ReactOS 的 Win32k 实现**在核心设计上与今天的 Windows 10/11 高度一致**——变的只是：Win32k 拆分为三个驱动（win32k.sys/win32kbase.sys/win32kfull.sys）、Shadow SSDT 调用号空间扩展、增加了 Win32k Filter 和 VBS 隔离、以及攻击面持续演化（从直接覆盖 KernelCallbackTable 到 inline hook 绕道）。抓住"视窗线程是 ETHREAD 的 GUI 特化"、"Win32k 通过 Shadow SSDT 扩展系统调用"、"KeUserModeCallback 是反向系统调用且是信任边界"、"SendMessage 是窗口上的同步 RPC"这四个第一性原理，你就能穿透任何版本的 Windows GUI 子系统。
