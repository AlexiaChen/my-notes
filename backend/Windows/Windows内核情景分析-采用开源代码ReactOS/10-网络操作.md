
第10章是整本书的"对外窗口"——前面你学了系统调用（第2章）、对象管理（第4章）、设备驱动与 IRP（第9章），这一章告诉你：当应用程序调用 `socket()`/`send()`/`recv()` 时，这个调用如何穿越用户态与内核态的边界，经过 **Winsock → AFD → TDI → TCP/IP → NDIS → Miniport**​ 五层转换，最终从网卡发出去。整章 10.1~10.6 就是这条网络 I/O 路径的完整解剖：从概述 → NDIS 库（协议与网卡的解耦层）→ 网络驱动堆叠（NIC/LAN/TCP-IP/AFD/Winsock）→ Socket 无连接通信（UDP）→ Socket 有连接通信（TCP）→ Winsock 实现。

我的核心洞见先抛在前面：**Windows 网络栈的第一性原理是"用统一的 IRP/IOCTL 管道承载 BSD socket 语义，并通过 NDIS 实现协议与网卡的彻底解耦"**。应用程序以为自己在调用 BSD 风格的 `socket()`/`send()`/`recv()`，实际上每个调用都被封装成 `IOCTL_AFD_*` 的 IRP 进入内核；AFD.sys 是这个转换的总枢纽——它把 socket 语义翻译成 TDI（传输驱动接口）操作；TDI 操作再交给 tcpip.sys 做真正的协议处理；tcpip.sys 通过 NDIS 库把数据包交给网卡 Miniport 驱动。理解了这个"五层转换"，你就能解释为什么 Windows 网络栈既兼容 UNIX 网络编程模型，又能支持任意协议、任意网卡——因为每一层都是可替换的插件。

> 💡 读这一章的正确姿势：把"网络数据包"想象成一个跨国快递包裹。Winsock 是寄件人填的单子（BSD 风格 API），AFD 是本地邮局（把单子转成标准内部运单），TDI 是运输公司接口标准（不关心用什么车），tcpip.sys 是分拣中心（按 IP/TCP 协议打包），NDIS 是物流调度中心（不关心是卡车还是飞机），Miniport 是具体的运输工具（网卡硬件）。每一层都只关心自己的抽象，对整个链条的运转至关重要。

## 10.1 概述

**书的脉络**：Windows 网络栈从下到上由多层构成：**NIC Miniport → NDIS 库 → 协议驱动（LAN Manager）→ TCP/IP 协议栈 → TDI → AFD → Winsock**。设计哲学是"**分层协议独立**"：

- 应用层不直接接触硬件
- Winsock 提供 BSD 风格的 socket API
- AFD 把 socket API 转为内核操作
- TCP/IP 是众多协议之一，可被替换
- NDIS 抽象 NIC，多协议可共享

**ReactOS 中的对应模块与源码路径**：

|层级|模块|源码路径|
|---|---|---|
|用户态 Winsock|ws2_32.dll / msafd.dll|`dll/win32/ws2_32/`、`dll/win32/msafd/`|
|内核 AFD|afd.sys|`drivers/network/afd/afd/`|
|TCP/IP 协议栈|tcpip.sys|`drivers/network/tcpip/tcpip/`（基于 lwIP）|
|LAN 协议驱动|lan.sys|`drivers/network/lan/lan/`|
|NDIS 库|ndis.sys|`drivers/network/ndis/ndis/`|
|NIC 驱动|dc21x4/e1000/rtl8139|`drivers/network/dd/`|

**我的洞见——网络栈分层的第一性原理是"接口标准化 + 实现可替换"**：

Windows 网络栈的每一层都定义了一个标准接口，上下层都只依赖接口而非实现：

- **Winsock 接口**（用户态 API）：`ws2_32.dll` 暴露 `socket`/`bind`/`connect`/`send`/`recv`
- **AFD 接口**（IOCTL_AFD_*）：用户态通过 `DeviceIoControl` 对 `\Device\Afd` 发起 IOCTL
- **TDI 接口**（IRP_MJ_INTERNAL_DEVICE_CONTROL）：AFD 通过 TDI IRP 与传输驱动通信
- **NDIS 接口**（Protocol/Miniport 两套接口）：协议驱动与网卡驱动之间的契约

> 📌 **这种"全链路接口化"的设计让 Windows 网络栈具有极高的扩展性**：
> 
> - 换网卡？只需换 Miniport 驱动，上层一无所知
> - 换协议？只需换协议驱动（如用 IPX/SPX 替代 TCP/IP），上层 Winsock 不变
> - 换 socket 语义？AFD 是适配层，可适配 N 种协议驱动

**现代映照**：现代 Windows 10/11 的网络栈在整体分层上保持一致，但有几个重要演进：

- **TDI 已被弃用**：微软在 Windows 10 上明确不推荐使用 TDI 框架，新版本内核网络编程应使用 **WSK（Winsock Kernel）**
- **Winsock 仍然是用户态标准 API**：`ws2_32.dll` 的地位未变
- **AFD.sys 仍然是核心**：Windows 11 的 afd.sys 依然创建 `\Device\Afd` 设备对象，分发 `IRP_MJ_DEVICE_CONTROL` 到 `AfdDispatchDeviceControl`，并新增了 `AfdWskDispatchInternalDeviceControl` 用于处理 WSK 内部设备控制
- **NDIS 6.x 全面取代 NDIS 5.x**：ReactOS 实现的是 NDIS 5.1，现代 Windows 使用 NDIS 6.x（Vista 引入），数据包结构从 `NDIS_PACKET` 改为 `NET_BUFFER_LIST`/`NET_BUFFER`/`MDL` 三层结构

工业界：理解网络栈分层是**网络驱动开发、防火墙/IDS、网络性能优化**的基础。从 Windows 7 开始，**WFP（Windows Filtering Platform）**​ 成为取代了传统 TDI 过滤和 NDIS 中间驱动的首选网络过滤框架。

## 10.2 NDIS 及其实现

**书的脉络**：NDIS（Network Driver Interface Specification）库位于协议驱动和 Miniport 驱动之间，是**协议与网卡解耦的核心枢纽**。NDIS 定义了三套标准接口：

1. **Miniport 接口**：Miniport 驱动实现的回调（如 `MiniportInitialize`、`MiniportSend`、`MiniportISR`）
2. **Protocol 接口**：协议驱动调用的 API（如 `NdisOpenAdapter`、`NdisSend`、`NdisCloseAdapter`）
3. **IM（Intermediate）接口**：中间层驱动接口，用于防火墙、VPN、QoS

**NDIS 库的核心架构**：

- **注册和管理**：维护协议/Miniport 全局列表
- **通信转发**：把 Protocol API 调用转发到 Miniport，反之亦然
- **资源抽象**：包池、缓冲池、内存管理
- **同步与序列化**：确保多协议多实例的并发安全

**NDIS 库的三个全局链表**：

```
LIST_ENTRY ProtocolListHead;    // 所有已注册的协议驱动
LIST_ENTRY MiniportListHead;    // 所有已注册的 Miniport 驱动
LIST_ENTRY AdapterListHead;     // 所有已绑定的适配器
```

**ReactOS 的 NDIS 实现**：

- 实现在 `drivers/network/ndis/ndis/`
- 主要文件：`main.c`、`miniport.c`、`protocol.c`、`buffer.c`、`co.c`、`cl.c`、`cm.c`、`io.c`、`memory.c`、`object.c`、`time.c`、`workitem.c`
- **NDIS 版本**：ReactOS 实现的是 **NDIS 5.1**
- 不支持 NDIS 6.x 的新特性（如 NetBuffer 结构、VMQ）
- 包含 CoNDIS（连接导向 NDIS）代码，但实际使用较少
- 对 IM（中间层）驱动支持有限
- 未实现 RSS、LSO、校验和卸载等性能优化

**我的洞见——NDIS 是"协议无关性"的极致体现**：

NDIS 库的核心设计理念是"**协议无关性**"——上层协议驱动（如 TCP/IP）不需要知道底层 NIC 的具体型号和特性，下层 Miniport 驱动也不需要知道上层使用什么协议。

> 💡 **这种解耦通过两套标准接口实现**：
> 
> - **Protocol 接口**：协议驱动调用的 API（`NdisSend` 等）
> - **Miniport 接口**：Miniport 驱动实现的回调（`MiniportSend` 等）
> 
> NDIS 库在中间做"翻译"——协议驱动的 `NdisSend` 调用被转换成对 Miniport 驱动 `MiniportSend` 回调的调用。双方都不知道对方的存在。

**NDIS 的三层模式**：

```
NDIS 协议驱动（tcpip.sys 等）
       ↓
NDIS 中间层驱动（IM/Filter）
       ↓
NDIS 微端口驱动（网卡驱动）
```

这个三层模型从最早的 Windows 版本到最新版本都保持兼容。Windows 7 之后，NDIS Filter 驱动模型简化了包过滤驱动的开发——不再需要同时实现 Miniport 和 Protocol 两套接口。

**现代映照**：NDIS 6.x 是 Windows Vista 引入的重大升级，关键变化：

1. **新的数据包结构**：`NET_BUFFER_LIST`（NBL）→ `NET_BUFFER`（NB）→ `MDL` 三层结构，取代 NDIS 5.x 的 `NDIS_PACKET` 和 `NDIS_BUFFER`
2. **Scatter/Gather DMA 优化**：Miniport 驱动在映射数据包之前就有权访问数据包，可以优化小包/碎片包的传输
3. **更快的 Filter 驱动**：NDIS 6.0+ 的 Filter 驱动不再是"Miniport + Protocol"的组合，而是具有独特接口的轻量级过滤器
4. **完全 TCP 卸载（Chimney Offload）**：NIC 硬件可以直接处理 TCP 状态，减少主机 CPU 开销
5. **RSS（接收端缩放）、LSO（大发送卸载）、校验和卸载**：性能优化的硬件卸载

**NDIS 6.x 的 NBL/NB/MDL 关系**：

```
NET_BUFFER_LIST (NBL)
  ├── NET_BUFFER (NB#1) → MDL#1 → MDL#2 → 物理页
  └── NET_BUFFER (NB#2) → MDL#3 → 物理页
```

- **NBL**：描述一组具有共同带外（OOB）数据的包
- **NB**：描述单个网络包
- **MDL**：描述虚拟连续的数据缓冲区（物理页可能碎片化）

工业界：理解 NDIS 是**网络驱动开发的基础**。现代 Windows 网络驱动开发：

- **NIC 驱动**：使用 NDIS 6.x Miniport 模型
- **协议驱动**：使用 NDIS 6.x Protocol 模型
- **包过滤**：使用 NDIS 6.x Filter 模型（取代老的 IM 模型）
- **性能关键场景**：使用 RSS、LSO、Chimney Offload 等硬件卸载特性

### 10.3.1 NIC 驱动

**书的脉络**：Miniport 驱动直接操作网卡硬件，源码在 `drivers/network/dd/`：

- `dd/dc21x4/`：DEC 21x4x NIC 驱动
- `dd/e1000/`：Intel PRO/1000 驱动
- `dd/rtl8139/`：Realtek 8139 驱动

Miniport 驱动的核心回调：

|回调|作用|
|---|---|
|`MiniportInitialize`|初始化网卡|
|`MiniportHalt`|停止网卡|
|`MiniportSend`|发送数据包|
|`MiniportISR`|中断服务例程|
|`MiniportQueryInformation`|查询网卡信息|
|`MiniportSetInformation`|设置网卡参数|

**我的洞见——Miniport 驱动是"硬件协议的翻译器"**：

Miniport 驱动的本质是**把 NDIS 的标准发送/接收接口翻译成对具体网卡寄存器的操作**。同一份 TCP/IP 协议栈代码，可以驱动 Intel、Realtek、Broadcom 等不同厂商的网卡——因为每家厂商提供自己的 Miniport 驱动来做"最后一公里"的硬件操作。

> 📌 **关键设计**：Miniport 驱动不直接与协议驱动通信，所有交互都通过 NDIS 库转发。这意味着：
> 
> - 换网卡 → 只需换 Miniport 驱动
> - 上层 TCP/IP、AFD、Winsock 完全不受影响
> - 这是 Windows "硬件兼容性"的基石

### 10.3.2 LAN 驱动模块

**书的脉络**：LAN Manager（`lan.sys`）是 NDIS 协议驱动，源码在 `drivers/network/lan/lan/`，主要文件：`lan.c`、`routines.c`、`info.c`、`receive.c`。

LAN 驱动的职责：

- 作为 NDIS 协议驱动注册到 NDIS 库
- 绑定到 Miniport 驱动创建的适配器
- 接收来自上层（AFD/TCP-IP）的协议请求
- 通过 NDIS 接口发送到 Miniport
- 接收来自 Miniport 的数据包，向上递交

**我的洞见——LAN 驱动是"NDIS 协议驱动的范例"**：

LAN Manager 展示了 NDIS 协议驱动的标准结构：`NdisRegisterProtocol` 注册协议 → `NdisOpenAdapter` 绑定适配器 → `NdisSend` 发送数据 → `ProtocolReceive` 回调接收数据。

> 💡 **TCP/IP 协议栈与 LAN 驱动的关系**：在 ReactOS 中，tcpip.sys 是真正的 TCP/IP 协议实现，而 lan.sys 是 NDIS 协议驱动层。两者关系是：tcpip.sys 通过 TDI 接口接收 AFD 的请求，然后调用 lan.sys 的 NDIS Protocol 接口发送数据。

### 10.3.3 TCP/IP 驱动模块

**书的脉络**：tcpip.sys 是 Windows 的 TCP/IP 协议栈实现，源码在 `drivers/network/tcpip/tcpip/`，基于 lwIP 实现。

tcpip.sys 内部实现：

- **IP 层**：IP 包解析、路由、分片/重组
- **TCP 层**：三次握手、滑动窗口、重传、拥塞控制
- **UDP 层**：无连接数据报
- **ICMP**：错误消息处理

**TCP 协议的关键机制**：

- **三次握手**：SYN → SYN-ACK → ACK
- **滑动窗口**：流量控制
- **重传机制**：超时重传、快速重传
- **拥塞控制**：慢启动、拥塞避免、快速恢复
- **状态机**：CLOSED → LISTEN → SYN_RCVD → ESTABLISHED → FIN_WAIT → TIME_WAIT

**我的洞见——tcpip.sys 是"协议状态机的执行者"**：

TCP 协议的复杂性在于**状态机**——同一个 `send()` 调用，在连接建立前、连接建立后、连接关闭时，行为完全不同。tcpip.sys 内部维护每个 socket 的 TCP 状态，根据状态决定如何处理数据。

> ⚠️ **SYN 洪水攻击与 AFD 的动态 Backlog**：AFD.sys 通过注册表 `HKLM\System\CurrentControlSet\Services\AFD\Parameters\EnableDynamicBacklog` 控制是否启用动态 backlog，可以修改最大半连接数来防范 SYN 洪水攻击。这是理解 TCP 协议栈安全性的关键。

### 10.3.4 AFD 驱动与 Winsock

**书的脉络**：AFD.sys（Ancillary Function Driver）是内核态的 socket 语义实现核心，源码在 `drivers/network/afd/afd/`：

**AFD 的核心职责**：

- **套接字创建/销毁**：管理 AFD_FCB（每个套接字的文件控制块）
- **状态机管理**：CREATED → BOUND → CONNECTED/LISTENING → CLOSED
- **IOCTL 分发**：处理 40+ 种 `IOCTL_AFD_*` 请求
- **数据缓冲管理**：维护发送窗口和接收窗口
- **异步 IRP 管理**：挂起/完成用户态 IRP
- **select 多路复用**：AFD_ACTIVE_POLL 管理
- **事件通知**：将 TDI 事件转换为 Winsock 事件
- **TDI 桥接**：通过 tdihelpers 与 tcpip.sys 通信

**AFD 的源文件组织**：

|文件|功能|
|---|---|
|`main.c`|DriverEntry、AfdDispatch 分发、套接字创建/关闭|
|`bind.c`|IOCTL_AFD_BIND：绑定地址|
|`connect.c`|IOCTL_AFD_CONNECT：连接远端|
|`listen.c`|IOCTL_AFD_START_LISTEN / WAIT_FOR_LISTEN / ACCEPT|
|`read.c`|IOCTL_AFD_RECV / RECV_DATAGRAM|
|`write.c`|IOCTL_AFD_SEND / SEND_DATAGRAM|
|`select.c`|IOCTL_AFD_SELECT / EVENT_SELECT|
|`event.c`|TDI 事件处理|
|`lock.c`|内存锁定（MmProbeAndLockPages）、状态锁|

**完整调用链**：

```
应用程序 (App.exe)
  ↓
Winsock 用户态库 (ws2_32.dll)  ← 用户态 API 入口
  ↓ WSP 服务提供者 (AFD Provider)
  ↓ 通过 DeviceIoControl 进入内核
AFD.sys (辅助功能驱动)  ← 内核态 socket 语义实现
  ↓ IOCTL_AFD_* 翻译为 TDI 操作
TDI (传输驱动接口)  ← 内核态网络接口标准
  ↓ IRP_MJ_INTERNAL_DEVICE_CONTROL
tcpip.sys (TCP/IP 协议驱动)  ← 真正的协议实现
  ↓
NDIS 库 (ndis.sys) → 网卡驱动
```

**Windows 11 的 AFD.sys**：

现代 AFD.sys 的分发例程：

```
[00] IRP_MJ_CREATE                      afd!AfdDispatch
[05] IRP_MJ_DEVICE_CONTROL              afd!AfdDispatchDeviceControl
[0f] IRP_MJ_INTERNAL_DEVICE_CONTROL     afd!AfdWskDispatchInternalDeviceControl
[10] IRP_MJ_SYSTEM_CONTROL              afd!AfdEtwDispatch
```

这说明现代 AFD.sys 不仅处理传统的 `IOCTL_AFD_*`，还通过 `AfdWskDispatchInternalDeviceControl` 支持 WSK（Winsock Kernel）内部设备控制。

**我的洞见——AFD 是"BSD socket 语义到 Windows 内核机制的翻译器"**：

AFD.sys 的第一性原理是**桥接两个不同的世界**：

- **用户态世界**：BSD 风格的 socket API（`socket()`/`bind()`/`connect()`/`send()`/`recv()`）
- **内核态世界**：Windows 的 IRP/I/O 模型、TDI 接口、对象管理

> 💡 **AFD 的三个核心转换**：
> 
> 1. **API 转换**：`ws2_32.dll` 的 `send()` → AFD 的 `IOCTL_AFD_SEND`
> 2. **语义转换**：无连接/有连接、阻塞/非阻塞、同步/异步 → AFD_FCB 状态机
> 3. **传输转换**：AFD IOCTL → TDI IRP → tcpip.sys 处理

**AFD 与 IOCP 的关系**：AFD.sys 是 Windows I/O 完成端口（IOCP）的底层支撑组件。`CreateIoCompletionPort` 绑定 socket 时，实际上是绑定到 AFD 创建的套接字对象。这就是为什么 Windows 上高性能网络服务器（IIS、SQL Server）都基于 IOCP。

**现代映照**：

- **TDI 已被 WSK 取代**：Windows 10 上微软明确不推荐使用 TDI 接口
- **WSK（Winsock Kernel）**：内核态驱动可以直接使用 WSK 进行网络通信，API 与应用层 Winsock 高度一致
- **AFD 仍然是用户态 Winsock 的内核后端**：尽管内部可能使用 WSK 而非 TDI，但对外的 `IOCTL_AFD_*` 接口保持稳定

## 10.4 Socket 的无连接通信

**书的脉络**：UDP 是无连接的传输层协议。一次 UDP 通信的流程：

**发送端（sendto）**：

```
应用调用 sendto(sock, data, len, 0, (sockaddr*)&dest, sizeof(dest))
  ↓
ws2_32.dll: WSPConnect / WSPSendTo
  ↓
DeviceIoControl(\Device\Afd, IOCTL_AFD_SEND_DATAGRAM, ...)
  ↓
AFD.sys: 创建 AFD_FCB（如果尚未绑定）
  ↓
AFD 通过 TDI_SEND_DATAGRAM 发送
  ↓
tcpip.sys: UDP 封装（添加 UDP 头）
  ↓
tcpip.sys: IP 封装（添加 IP 头）
  ↓
NDIS: NdisSend
  ↓
Miniport: 发送到网卡
```

**接收端（recvfrom）**：

```
网卡收到数据包
  ↓
Miniport: 中断触发
  ↓
NDIS: NdisIndicateReceive
  ↓
tcpip.sys: IP 解包 → UDP 解包
  ↓
TDI 事件通知 → AFD 事件
  ↓
AFD: 将数据放入对应套接字的接收缓冲区
  ↓
唤醒等待的 recvfrom IRP
  ↓
应用从 recvfrom 返回
```

**UDP 的关键特征**：

- **无连接**：`sendto` 不需要预先 `connect`
- **不可靠**：不保证送达、不保证顺序
- **数据报边界**：保留消息边界（每个 sendto 对应一个 recvfrom）
- **无状态**：server 端不需要为每个 client 维护连接状态

**我的洞见——UDP 通信是"单次 IRP 的独立事务"**：

与 TCP 不同，UDP 的每个 `sendto` 都是**独立的、自包含的 IRP**——不需要建立连接状态机，不需要维护发送窗口，不需要处理重传。

> 📌 **这就是为什么 UDP 在 AFD 中的处理相对简单**：
> 
> - `IOCTL_AFD_SEND_DATAGRAM`：直接通过 TDI_SEND_DATAGRAM 发送
> - `IOCTL_AFD_RECV_DATAGRAM`：从接收队列取出数据报
> - 不需要 AFD_FCB 的复杂状态机（TCP 需要）

**UDP 的实际应用**：

- DNS 查询：单次请求-响应
- DHCP：广播发现
- SNMP：网络管理
- 音视频流：容忍丢包，要求低延迟
- 游戏：实时性要求高

**现代映照**：UDP 在现代网络中仍然不可或缺，但增加了：

- **UDP 隧道**：用于 VPN（如 WireGuard）
- **QUIC 协议**：基于 UDP 的 HTTP/3 传输协议
- **RTP/RTCP**：实时媒体传输

工业界：理解 UDP 通信是**网络编程和协议设计的基础**。现代高性能 UDP 服务器使用 **RIO（Registered I/O）**​ API 或 **DPDK**​ 实现用户态协议栈，绕过内核 AFD 的开销。

## 10.5 Socket 的有连接通信

**书的脉络**：TCP 是有连接的传输层协议。TCP 通信的核心是**状态机**——从 `socket()` 到 `close()`，套接字经历多个状态转换。

**TCP 连接建立的完整流程（client 端 connect）**：

```
应用调用 connect(sock, (sockaddr*)&server, sizeof(server))
  ↓
ws2_32.dll: WSPConnect
  ↓
DeviceIoControl(\Device\Afd, IOCTL_AFD_CONNECT, ...)
  ↓
AFD.sys: 创建 AFD_FCB，状态变为 BOUND
  ↓
AFD 通过 TDI_CONNECT 发起连接
  ↓
tcpip.sys: 发送 SYN
  ↓
（网络传输）
  ↓
tcpip.sys: 收到 SYN-ACK，发送 ACK
  ↓
AFD 收到 TDI 事件：连接建立
  ↓
唤醒 connect IRP，返回成功
  ↓
应用从 connect 返回
```

**TCP 三次握手的状态转换**：

```
Client: CLOSED → SYN_SENT → ESTABLISHED
Server: LISTEN → SYN_RCVD → ESTABLISHED
```

**TCP 数据传输**：

```
send(sock, data, len, 0)
  ↓
ws2_32.dll: WSPSend
  ↓
DeviceIoControl(\Device\Afd, IOCTL_AFD_SEND, ...)
  ↓
AFD: 将数据放入发送缓冲区
  ↓
TDI_SEND → tcpip.sys
  ↓
TCP 分段、IP 封装、NDIS 发送
  ↓
（网络传输）
  ↓
接收端 TCP 确认
  ↓
AFD 收到确认，释放发送缓冲区
  ↓
send IRP 完成，返回
```

**TCP 的关键机制**：

1. **滑动窗口**：流量控制
2. **重传**：超时重传、快速重传
3. **拥塞控制**：慢启动、拥塞避免
4. **TIME_WAIT 状态**：确保最后一个 ACK 到达

**AFD 中的 TCP 状态机**：

```
CREATED → BOUND → CONNECTED/LISTENING → CLOSED
```

每个状态转换都对应特定的 `IOCTL_AFD_*` 操作。

**我的洞见——TCP 通信是"状态机驱动的 IRP 流"**：

与 UDP 的单次事务不同，TCP 的每个操作都依赖于**当前状态**：

> ⚠️ **TCP 的复杂性本质**：
> 
> - `send()` 在 ESTABLISHED 状态才有效
> - `connect()` 触发三次握手状态机
> - `recv()` 从接收缓冲区取数据，可能涉及等待
> - `close()` 触发四次挥手
> 
> AFD 必须在 AFD_FCB 中维护完整的 TCP 状态，每个 IOCTL 都先检查状态再执行。

**TCP 与 AFD 的深度整合**：

- **接收窗口管理**：AFD 维护接收缓冲区，TCP 滑动窗口与之对应
- **发送窗口管理**：AFD 维护发送缓冲区，TCP 根据拥塞窗口控制发送速率
- **异步通知**：通过 `WSAEventSelect` 或 IOCP 实现事件驱动
- **select 多路复用**：AFD_ACTIVE_POLL 管理多个套接字的状态查询

**现代映照**：TCP 在现代 Windows 中的演进：

- **TCP Chimney Offload**：网卡硬件处理 TCP 状态，减轻 CPU 负担
- **RSS（接收端缩放）**：多核 CPU 并行处理网络中断
- **LSO（Large Send Offload）**：网卡硬件做 TCP 分段
- **RIO（Registered I/O）**：Windows 8 引入的高性能网络 API
- **WSK**：内核态 TCP 通信

工业界：理解 TCP 通信是**高性能服务器开发的基础**。现代 Windows 服务器（IIS、SQL Server）全部基于 IOCP + TCP，通过 AFD 实现高并发连接管理。

## 10.6 Winsock 的实现

**书的脉络**：Winsock 是 Windows 上的 BSD socket API 实现，分为用户态和内核态两部分：

**用户态**（ws2_32.dll + msafd.dll）：

- `ws2_32.dll`：提供标准 socket API
- `msafd.dll`（Microsoft Winsock AFD Provider）：Winsock 服务提供者（WSP），通过 `DeviceIoControl` 调用 AFD.sys

**Winsock 服务提供者架构（WSP）**：

```
应用调用 send()
  ↓
ws2_32.dll 调用 WSP 函数指针（lpWSPSend）
  ↓
msafd.dll（AFD Provider）:
  1. 维护内核句柄：socket() 时通过 CreateFile("\Device\Afd") 获取
  2. 组织 IOCTL 缓冲：将参数填入 AFD_* 结构
  3. 发起 DeviceIoControl：调用 NtDeviceIoControlFile
  4. 处理完成事件：通过事件对象接收内核通知
```

**关键 Winsock API 与 AFD IOCTL 的对应关系**：

|Winsock API|AFD IOCTL|
|---|---|
|`socket()`|`IOCTL_AFD_CREATE`|
|`bind()`|`IOCTL_AFD_BIND`|
|`connect()`|`IOCTL_AFD_CONNECT`|
|`listen()`|`IOCTL_AFD_START_LISTEN`|
|`accept()`|`IOCTL_AFD_WAIT_FOR_LISTEN` + `IOCTL_AFD_ACCEPT`|
|`send()`|`IOCTL_AFD_SEND`|
|`recv()`|`IOCTL_AFD_RECV`|
|`sendto()`|`IOCTL_AFD_SEND_DATAGRAM`|
|`recvfrom()`|`IOCTL_AFD_RECV_DATAGRAM`|
|`select()`|`IOCTL_AFD_SELECT`|
|`WSAEventSelect()`|`IOCTL_AFD_EVENT_SELECT`|

**Winsock 的两种 I/O 模式**：

1. **阻塞模式**：`recv()` 无数据时线程挂起
2. **非阻塞模式**：`ioctlsocket(sock, FIONBIO, &mode)` 设置

**Winsock 的五种 I/O 模型**：

1. **阻塞 I/O**：最简单，但并发性差
2. **非阻塞 I/O**：立即返回，需轮询
3. **select 模型**：多路复用
4. **WSAAsyncSelect**：基于消息通知
5. **WSAEventSelect + WSAWaitForMultipleEvents**：基于事件
6. **IOCP（完成端口）**：最高性能，AFD 是底层支撑

**我的洞见——Winsock 是"用户态 API 与内核 AFD 的契约"**：

Winsock 的第一性原理是**在用户态提供 BSD 兼容 API，同时与内核 AFD 建立稳定的 IOCTL 契约**：

> 💡 **Winsock 的三个核心设计决策**：
> 
> 1. **API 兼容 BSD socket**：让 UNIX 网络程序可以轻松移植到 Windows
> 2. **SPI（服务提供者接口）可扩展**：LSP（分层服务提供者）允许插入自定义提供者（如代理、过滤）
> 3. **IOCTL 契约稳定**：`IOCTL_AFD_*` 是 ws2_32 与 AFD 之间的"二进制接口"，从 Windows NT 4.0 到现在基本未变

**LSP（分层服务提供者）的安全意义**：

- **正面用途**：代理、过滤、审计、压缩
- **负面用途**：恶意 LSP 可以拦截/篡改所有网络流量（如广告注入、数据窃取）
- **现代处置**：Windows 10 开始 LSP 机制被弃用，改用 **WFP（Windows Filtering Platform）**

**ReactOS 的现状**：

- `mswsock.dll` 的 AFD 提供者部分仍是 stub
- AFD.sys 本身已实现完整的 IOCTL 接口
- 等待用户态提供者对接

**现代映照**：现代 Windows Winsock 的演进：

- **Winsock 2.2 是主流版本**
- **LSP 被 WFP 取代**：WFP 提供更好的性能和安全性
- **WSK 用于内核态 socket 编程**
- **RIO（Registered I/O）**：Windows 8 引入，专为高吞吐量设计
- **QUIC 协议**：HTTP/3 的底层传输，用户态实现

工业界：理解 Winsock 实现是**网络应用开发、网络安全、协议分析**的基础：

- **网络调试工具**：Wireshark、tcpdump 通过 NDIS 抓包
- **防火墙/IDS**：通过 WFP 或 NDIS Filter 拦截
- **代理工具**：通过 LSP 或 WFP 实现流量重定向
- **性能优化**：IOCP + RIO 实现百万级并发连接

## 工业界实际应用与安全视角

### 🛡️ 安全领域

**1. 网络栈攻击面**：

- **AFD.sys 攻击**：通过 `IOCTL_AFD_*` 的畸形参数触发漏洞
- **tcpip.sys 攻击**：IP/TCP 协议解析漏洞（如 Ping of Death、TCP 序列号预测）
- **NDIS Filter 攻击**：恶意 Filter 驱动拦截/篡改网络流量
- **Winsock LSP 注入**：恶意 LSP 拦截 Winsock 调用

**2. 现代防御机制**：

- **WFP（Windows Filtering Platform）**：取代 LSP，提供内核级包过滤
- **HVCI**：防止网络驱动代码篡改
- **VBS 隔离**：敏感网络操作在 VTL1 执行

**3. 网络取证与监控**：

- **ETW 网络事件**：通过 Microsoft-Windows-TCPIP 提供程序监控 TCP 连接
- **Sysmon**：监控网络连接和 DNS 查询
- **EDR**：通过 WFP 拦截恶意网络通信

### ⚙️ 工业应用

**1. 高性能网络服务器**：

- **IIS/SQL Server**：基于 IOCP + AFD 实现百万级并发
- **RIO（Registered I/O）**：Windows 8+ 的高性能网络 API
- **DPDK on Windows**：用户态协议栈，绕过 AFD 开销

**2. 网络虚拟化**：

- **Hyper-V 虚拟交换机**：基于 NDIS Filter 实现
- **Azure 网络**：SR-IOV 直通网卡，VM 直接使用 VF

**3. 现代网络协议**：

- **HTTP/3 (QUIC)**：基于 UDP，用户态实现
- **WireGuard**：UDP 隧道 VPN
- **SMB 3.x over RDMA**：高性能文件共享

**4. 内核态网络编程**：

- **WSK（Winsock Kernel）**：内核驱动直接使用 socket API
- **AFD 内部**：Windows 11 的 AFD 已支持 WSK 内部设备控制
