
第11章是整本书从"设备驱动"走向"文件系统语义"的关键一跃。前九章你学了系统调用、对象管理、IRP 和设备栈，第10章看了网络栈如何用 IRP 承载 socket 语义——这一章告诉你：**当应用程序调用 `CreateFileW("D:\\test.txt")` 时，这个字符串如何穿越对象管理器、卷挂载、文件系统驱动、缓存管理器，最终变成一个文件对象句柄**。整章 11.1~11.10 就是这条文件 I/O 路径的完整解剖：从 CreateFileW 的用户态入口 → NT 路径名 → 路径解析 → FAT32 实现 → 文件系统驱动装载 → 卷安装 → 文件创建 → 缓存管理 → 文件读写 → NTFS 简介。

我的核心洞见先抛在前面：**Windows 文件系统的第一性原理是"用对象管理器的名字空间统一所有可打开的东西，并用 IRP 作为文件系统驱动与卷设备之间的通用请求货币"**。`CreateFileW` 不只是"创建文件"——它实际上是"打开任意有名字的内核对象"，当这个名字解析到一个卷设备对象时，I/O 管理器才会进一步创建文件对象、调用文件系统驱动的 IRP_MJ_CREATE。理解了这个"名字解析 → 设备栈定位 → 文件系统语义"的三段式，你就能解释为什么 Windows 可以把文件、设备、管道、邮槽统统用 `CreateFile` 打开——因为它们在对象管理器看来都是"名字"。

> 💡 读这一章的正确姿势：把"文件路径"想象成邮寄地址。`D:\test.txt` 就像"中国北京市海淀区某某路1号"——`D:` 是"国家/省份"（卷设备），`\test.txt` 是"具体门牌"（文件系统内的文件）。CreateFileW 先把这个地址标准化成 NT 路径 `\??\D:\test.txt`，对象管理器查 `\??\D:` 找到卷设备对象，然后把剩下的 `\test.txt` 交给文件系统驱动去解析。每一层只管自己那一段。

## 11.1 Win32 API 函数 CreateFileW()

**书的脉络**：CreateFileW 是 Win32 API 中最"名不副实"的函数——它叫"Create"但实际上主要工作是"Open"。它的真正语义是：**打开任意有名字的内核对象，如果对象不存在且允许创建，则先创建再打开**。

**CreateFileW 的参数到 NT 语义的映射**：

```c
HANDLE WINAPI CreateFileW(
    LPCWSTR lpFileName,              // 文件路径/设备名/符号链接
    DWORD dwDesiredAccess,           // 访问权限
    DWORD dwShareMode,               // 共享模式
    LPSECURITY_ATTRIBUTES lpSecAttr, // 安全描述符
    DWORD dwCreationDisposition,     // 创建/打开策略
    DWORD dwFlagsAndAttributes,      // 文件属性与标志
    HANDLE hTemplateFile)            // 模板文件
```

`dwCreationDisposition` 到 NT `CreateDisposition` 的映射：

| Win32 值 | NT 值 | 语义 |
|---|---|---|
| `CREATE_NEW` | `FILE_CREATE` | 文件必须不存在 |
| `CREATE_ALWAYS` | `FILE_OVERWRITE_IF` | 存在则覆盖 |
| `OPEN_EXISTING` | `FILE_OPEN` | 文件必须存在 |
| `OPEN_ALWAYS` | `FILE_OPEN_IF` | 不存在则创建 |
| `TRUNCATE_EXISTING` | `FILE_OVERWRITE` | 存在则清空 |

**CreateFileW 的核心流程**：

1. **DOS 路径 → NT 路径**：`RtlDosPathNameToNtPathName_U` 把 `D:\test.txt` 转换为 `\??\D:\test.txt`
2. **填充 OBJECT_ATTRIBUTES**：包含 NT 路径、安全描述符等
3. **调用 NtCreateFile**：进入内核
4. **I/O 管理器调用 IoCreateFile**：填充 OPEN_PACKET
5. **ObReferenceObjectByName**：通过对象管理器解析名字
6. **ObpLookupObjectName**：创建或打开文件对象
7. **ObpCreateHandle**：创建句柄并返回

**关键洞见**：`CreateFileW` 的第一个 `\` 是对象根目录，`\??` 是盘符符号链接所在的位置。所以 `\??\D:` 实际上解析到 `\Device\HarddiskVolumeN` 这样的卷设备对象。

**我的洞见——CreateFileW 是"对象管理器名字空间的统一入口"**：

CreateFileW 的第一性原理是**用一套 API 打开一切内核对象**：

> 📌 **这就是为什么 CreateFileW 可以打开这么多不同的东西**：
> - 普通文件：`C:\test.txt`
> - 设备：`\\.\PhysicalDrive0`
> - 管道：`\\.\pipe\mypipe`
> - 邮槽：`\\.\mailslot\myslot`
> - 控制台：`CONIN$`、`CONOUT$`
>
> 它们在用户态看起来都是"路径"，在内核里都走 NtCreateFile → 对象管理器解析 → 找到目标设备对象 → 文件系统/设备驱动处理。

**dwFlagsAndAttributes 的关键标志**：

- `FILE_FLAG_OVERLAPPED`：异步 I/O（不设置则隐含 `FILE_SYNCHRONOUS_IO_NONALERT`）
- `FILE_FLAG_NO_BUFFERING`：绕过缓存管理器（直接磁盘 I/O）
- `FILE_FLAG_WRITE_THROUGH`：写操作直达磁盘（不经过延迟写）
- `FILE_FLAG_DELETE_ON_CLOSE`：关闭时删除
- `FILE_FLAG_BACKUP_SEMANTICS`：备份语义（访问目录、卷等）

**现代映照**：现代 Windows 中 CreateFileW 的行为基本一致，但增加了：

- **Reparse Point 处理**：`FILE_FLAG_OPEN_REPARSE_POINT` 标志允许直接打开 reparse point 而非跟随它
- **句柄继承与保护**：通过 `LPSECURITY_ATTRIBUTES` 精细控制
- **WSL 互操作**：NT 路径 `\??\` 背后可能涉及 WSL 的 VolFS/DrvFS 挂载

工业界：理解 CreateFileW 是**文件系统过滤驱动开发的基础**——每个商业杀毒软件都通过拦截 `IRP_MJ_CREATE` 来扫描即将打开的文件。

## 11.2 NT 路径名

**书的脉络**：NT 路径名是 Windows 内核中对象的全局唯一标识符。它遵循对象管理器的名字空间层次：

```
\ (根目录)
├── ?? (DOS 设备符号链接)
│   ├── C: → \Device\HarddiskVolume1
│   ├── D: → \Device\HarddiskVolume2
│   └── PhysicalDrive0 → \Device\Harddisk0\DR0
├── Device (设备对象目录)
│   ├── Harddisk0
│   │   ├── Partition0 → \Device\Harddisk0\DR0
│   │   ├── Partition1 → \Device\HarddiskVolume1
│   │   └── DR0 (磁盘驱动设备)
│   ├── AFD (AFD 套接字驱动)
│   └── Tcp (TCP 协议驱动)
├── Driver (驱动对象目录)
└── FileSystem (文件系统注册目录)
```

**DOS 路径到 NT 路径的转换**：

- `D:\Windows\WINOBJ.INI` → `\??\D:\Windows\WINOBJ.INI`
- 第一个 `\` 是对象根目录
- `\??` 是 DOS 设备符号链接目录
- `D:` 解析到 `\Device\HarddiskVolumeN`

**符号链接的创建**：系统启动时，I/O 管理器遍历磁盘分区表，为每个分区创建符号链接：

- `Partition0` → `\Device\Harddisk0\DR0`（整个磁盘）
- `Partition1` → `\Device\HarddiskVolume1`（第一个卷）
- 依此类推

**我的洞见——NT 路径名是"对象管理器名字空间的邮政编码"**：

NT 路径的第一性原理是**用统一的层次名字空间标识所有内核对象**：

> 💡 **这种设计的精妙之处**：
> - 用户态用 DOS 路径（`C:\...`）—— 友好但模糊
> - 内核态用 NT 路径（`\??\C:\...`）—— 精确且统一
> - 对象管理器负责转换和解析
> - 每个"卷设备对象"（`\Device\HarddiskVolumeN`）才是真正的文件系统入口

**路径解析的两个阶段**：

1. **对象管理器阶段**：解析 `\??\D:` 找到卷设备对象
2. **文件系统阶段**：把剩余的 `\test.txt` 交给文件系统驱动解析

**特殊 NT 路径**：

- `\Device\Null`：空设备
- `\Device\PhysicalDrive0`：物理磁盘
- `\Device\Tcp`：TCP 协议驱动
- `\Device\Afd`：AFD 套接字驱动
- `\FileSystem\FastFAT`：FastFAT 文件系统驱动

**现代映照**：现代 Windows 的 NT 路径结构基本一致，但增加了：

- **Volume GUID 路径**：`\??\Volume{GUID}` 形式，更稳定（不受盘符变化影响）
- **WSL 挂载**：`\??\C:\` 可能实际指向 WSL 的 DrvFS
- **Reparse Point**：NT 路径解析过程中可能遇到 reparse point，需要特殊处理

工业界：理解 NT 路径是**文件系统过滤驱动、卷管理、备份软件**的基础。现代 EDR 通过监控 `\Device\HarddiskVolume` 的 IRP 来追踪文件操作。

## 11.3 文件路径名的解析

**书的脉络**：当 CreateFileW 进入内核后，路径解析是一个分阶段的过程：

**阶段1：对象管理器解析（ObpLookupObjectName）**

- 从 `\` 根开始，逐级查找对象目录
- `\??\D:` 解析到卷设备对象 `\Device\HarddiskVolume2`
- 剩余路径 `\test.txt` 将交给该设备对象关联的驱动

**阶段2：文件系统驱动解析**

- I/O 管理器向卷设备对象发送 `IRP_MJ_CREATE`
- 文件系统驱动（如 FastFAT）解析剩余路径
- 逐级查找目录项（FAT32）或 MFT 记录（NTFS）
- 找到则打开文件对象，否则根据 CreateDisposition 决定是否创建

**绝对路径 vs 相对路径**：

- **绝对路径**：`D:\Windows\test.txt` —— 从卷根开始解析
- **相对路径**：以某个已打开的目录文件对象为参照

**ReactOS 中的路径解析关键函数**：

- `ObpLookupObjectName`：对象管理器核心解析函数
- `IopParseDevice`：设备对象解析例程（文件系统驱动入口）
- `FastFAT` 的 `FATBuildName` / `VFATFindDirEntry`：FAT32 目录项查找
- `NTFS` 的 `NtfsMoonWalkID`：通过 MFT 记录 ID 反向构造路径

**我的洞见——路径解析是"对象管理器与文件系统驱动的分工协作"**：

路径解析的第一性原理是**责任分割**：

> 📌 **对象管理器只认"卷设备"，文件系统驱动才认"文件"**：
> - `\??\D:` 这一段由对象管理器解析 → 找到卷设备对象
> - `\test.txt` 这一段由文件系统驱动解析 → 找到文件
>
> 这种分割让"卷管理"和"文件系统"彻底解耦——同一个 FAT32 文件系统驱动可以挂载到任何卷设备上。

**路径解析中的关键问题**：

1. **长文件名 vs 短文件名（8.3 格式）**：FAT32 需要同时处理 `test.txt` 和 `TEST~1.TXT`
2. **大小写敏感性**：Windows 默认不敏感，但 POSIX 子系统要求敏感
3. **路径规范化**：`..` 和 `.` 的处理，符号链接的跟随
4. **Reparse Point**：遇到 reparse point 时需要重新解析

**NTFS 的路径解析特殊性**：

NTFS 通过 MFT 记录组织文件，每个文件对应一个 MFT 记录。路径解析实际上是：

```
文件名 → MFT 记录 ID → 文件属性（包括文件名属性）
```

`NtfsMoonWalkID` 函数展示了这个反向过程：给定 MFT 记录 ID，通过遍历 `$Parent` 链反向构造完整路径。

**现代映照**：现代 Windows 的路径解析增加了：

- **Reparse Point 处理**：符号链接、挂载点、DFS 等都需要 reparse
- **WSL 互操作**：NT 路径解析可能需要跨文件系统边界
- **Case Sensitivity**：Windows 10+ 支持按目录设置大小写敏感

工业界：理解路径解析是**文件系统过滤驱动、杀毒软件、备份工具**的核心。现代 EDR 通过 minifilter 驱动拦截 `IRP_MJ_CREATE` 并在路径解析完成后检查文件。

## 11.4 FAT32 文件系统

**书的脉络**：FAT32 是最简单的文件系统之一，ReactOS 的 FastFAT 驱动实现了完整的 FAT12/FAT16/FAT32 支持。

**FAT32 的核心数据结构**：

**1. Boot Sector（引导扇区）**：

```c
typedef struct _PACKED_BOOT_SECTOR_EX {
    UCHAR JumpInstruction[3];
    UCHAR OEMName[8];
    USHORT BytesPerSector;
    UCHAR SectorsPerCluster;
    USHORT ReservedSectors;
    UCHAR NumberOfFATs;
    USHORT RootEntries;
    USHORT TotalSectors16;
    UCHAR MediaDescriptor;
    USHORT SectorsPerFAT16;
    USHORT SectorsPerTrack;
    USHORT NumberOfHeads;
    ULONG HiddenSectors;
    ULONG TotalSectors32;
    ULONG SectorsPerFAT32;    // FAT32 特有
    USHORT ExtFlags;
    USHORT FileSystemVersion;
    ULONG RootCluster;        // FAT32 的根目录起始簇
    // ...
} PACKED_BOOT_SECTOR_EX;
```

**2. FSINFO 扇区**：

```c
typedef struct _FSINFO_SECTOR {
    ULONG SectorBeginSignature;  // 0x41615252
    UCHAR ExtraBootCode[480];
    ULONG FsInfoSignature;       // 0x61417272
    ULONG FreeClusterCount;      // 空闲簇数
    ULONG NextFreeCluster;       // 下一个空闲簇
    UCHAR Reserved[12];
    ULONG SectorEndSignature;    // 0xAA550000
} FSINFO_SECTOR;
```

**3. FAT 表项**：

```c
#define FAT32_ENTRY_MASK 0x0FFFFFFFUL
#define FAT_CLUSTER_AVAILABLE 0x00000000
#define FAT_CLUSTER_RESERVED  0x0ffffff0
#define FAT_CLUSTER_BAD       0x0ffffff7
#define FAT_CLUSTER_LAST      0x0fffffff
```

**4. 目录项（Directory Entry）**：

```c
typedef struct _PACKED_DIRENT {
    FAT8DOT3 FileName;     // 8.3 文件名
    UCHAR Attributes;      // 文件属性
    UCHAR NtByte;          // NT 特定字节
    UCHAR CreationMSec;    // 创建时间毫秒
    FAT_TIME_STAMP CreationTime;
    FAT_DATE LastAccessDate;
    union {
        USHORT ExtendedAttributes;
        USHORT FirstClusterOfFileHi;  // 文件首簇号高16位
    };
    FAT_TIME_STAMP WriteTime;
    FAT_DATE WriteDate;
    USHORT FirstClusterOfFileLo;  // 文件首簇号低16位
    ULONG FileSize;               // 文件大小
} PACKED_DIRENT;
```

**簇链查找**：FAT32 通过 FAT 表维护簇链。ReactOS 的 `FAT32GetNextCluster` 函数展示了这个过程：

```c
NTSTATUS FAT32GetNextCluster(
    PDEVICE_EXTENSION DeviceExt,
    ULONG CurrentCluster,
    PULONG NextCluster)
{
    // 通过 CcMapData 将 FAT 表映射到缓存
    CcMapData(DeviceExt->FATFileObject, &Offset, ChunkSize,
              MAP_WAIT, &Context, &BaseAddress);
    // 读取 FAT 表项
    CurrentCluster = (*(PULONG)((char*)BaseAddress +
                    (FATOffset % ChunkSize))) & 0x0fffffff;
    // 解除映射
    CcUnpinData(Context);
    *NextCluster = CurrentCluster;
}
```

**我的洞见——FAT32 是"扁平结构的极致简单"**：

FAT32 的第一性原理是**用一张"簇分配表"管理整个磁盘**：

> 💡 **FAT32 的三个核心抽象**：
> 1. **簇（Cluster）**：分配的基本单位（一个或多个扇区）
> 2. **FAT 表**：记录每个簇的状态和下一个簇的编号
> 3. **目录项**：记录文件名、属性、首簇号、大小
>
> 文件的完整数据 = 从首簇开始，沿着 FAT 表形成的簇链读取所有簇。

**FAT32 的局限性**：

- **单表结构**：FAT 表损坏 = 整个卷不可用
- **无日志**：断电可能导致严重损坏
- **无权限**：只有只读、隐藏、系统等简单属性
- **簇大小限制**：大磁盘上浪费空间（或簇太大）
- **文件大小限制**：最大 4GB

**FAT32 在缓存管理器中的集成**：

FastFAT 通过 `CcMapData` 将 FAT 表映射到系统缓存，这样 FAT 表的读取就变成了对缓存的访问——第一次读可能触发页错误从磁盘加载，后续读直接从缓存获取。这是 Windows 文件系统"缓存一切"哲学的体现。

**现代映照**：FAT32 在现代 Windows 中仍然是：

- **U 盘、SD 卡、EFI 系统分区**的默认格式
- **兼容性最佳**的文件系统（所有操作系统都支持）
- 但**不作为系统盘**使用（Windows 要求系统盘必须是 NTFS）

工业界：理解 FAT32 是**嵌入式系统、固件、引导加载程序**的基础。UEFI 固件只能读取 FAT32 格式的 EFI 系统分区。

## 11.5 文件系统驱动的装载和初始化

**书的脉络**：文件系统驱动（FSD）是内核模式驱动，遵循 WDM 模型。装载过程：

**1. 驱动注册**：

- 文件系统驱动在 `DriverEntry` 中调用 `IoCreateDevice` 创建设备对象
- 设备类型通常是 `FILE_DEVICE_DISK_FILE_SYSTEM`
- 初始化 `IRP_MJ_*` 分发例程

**2. 文件系统识别**：

- I/O 管理器通过 `IoRegisterFileSystem` 将驱动注册到 `\FileSystem` 对象目录
- 系统启动时识别每个卷的文件系统类型

**ReactOS 的 NTFS 驱动初始化**：

```c
NTSTATUS NTAPI DriverEntry(
    PDRIVER_OBJECT DriverObject,
    PUNICODE_STRING RegistryPath)
{
    // 创建设备对象
    IoCreateDevice(DriverObject, sizeof(NTFS_GLOBAL_DATA),
                   &DeviceName, FILE_DEVICE_DISK_FILE_SYSTEM,
                   0, FALSE, &DeviceObject);
    // 初始化全局数据
    NtfsGlobalData = DeviceObject->DeviceExtension;
    // 读取注册表，判断是否启用写支持
    // 注意：ReactOS 的 NTFS 驱动默认禁用写支持！
    NtfsGlobalData->EnableWriteSupport = FALSE;
    // 初始化 IRP 分发函数
    NtfsInitializeFunctionPointers(DriverObject);
    // 初始化缓存管理器回调
    NtfsGlobalData->CacheMgrCallbacks.AcquireForLazyWrite =
        NtfsAcqLazyWrite;
    NtfsGlobalData->CacheMgrCallbacks.ReleaseFromLazyWrite =
        NtfsRelLazyWrite;
    NtfsGlobalData->CacheMgrCallbacks.AcquireForReadAhead =
        NtfsAcqReadAhead;
    NtfsGlobalData->CacheMgrCallbacks.ReleaseFromReadAhead =
        NtfsRelLazyWrite;
    // 初始化 FastIo 分发
    NtfsGlobalData->FastIoDispatch.FastIoRead = NtfsFastIoRead;
    NtfsGlobalData->FastIoDispatch.FastIoWrite = NtfsFastIoWrite;
}
```

**关键初始化组件**：

| 组件 | 作用 |
|---|---|
| `IRP_MJ_*` 分发例程 | 处理各类 I/O 请求 |
| `FastIoDispatch` | 快速 I/O 例程（绕过 IRP） |
| `CacheMgrCallbacks` | 缓存管理器的回调（延迟写、预读） |
| 全局数据 | 驱动级别的全局状态 |

**我的洞见——文件系统驱动的初始化是"三重身份注册"**：

FSD 初始化时必须同时注册三种"身份"：

> 📌 **FSD 的三重身份**：
> 1. **WDM 驱动**：注册 IRP_MJ_* 分发例程
> 2. **缓存管理器客户端**：注册 AcquireForLazyWrite/ReadAhead 回调
> 3. **FastIo 提供者**：注册 FastIoRead/FastIoWrite 等快速 I/O 例程
>
> 只有完成这三重注册，FSD 才能完整地接入 Windows 的 I/O 和缓存体系。

**FastIo 的意义**：

FastIo 是 Windows 文件系统的一个优化机制——当文件已被缓存时，I/O 管理器可以直接调用 FastIo 例程而无需创建 IRP：

```
I/O 请求到达
  ↓
I/O 管理器检查是否有 FastIo 例程
  ↓
有 → 调用 FastIoRead/FastIoWrite（绕过 IRP 创建）
  ↓
FastIo 返回 TRUE → 操作完成
  ↓
FastIo 返回 FALSE → 回退到 IRP 路径
```

**现代映照**：现代 Windows 的文件系统驱动装载流程基本一致，但增加了：

- **Minifilter 注册**：文件系统过滤驱动通过 Filter Manager 注册
- **WOF（Windows Overlay Filter）**：支持压缩/加密卷的叠加层
- **ReFS**：弹性文件系统作为 NTFS 的替代

工业界：理解 FSD 初始化是**文件系统驱动开发、minifilter 开发**的基础。现代杀毒软件通过 minifilter 模型注册到 Filter Manager，拦截文件操作。

## 11.6 文件卷的安装

**书的脉络**：卷安装（Volume Mount）是文件系统驱动与具体卷设备的绑定过程。

**卷安装的触发**：

1. **系统启动时**：PnP 管理器枚举磁盘设备，为每个分区创建卷设备对象
2. **可移动介质插入时**：如 U 盘插入
3. **显式挂载**：通过 `mountvol` 命令或 `SetVolumeMountPoint`

**卷安装流程**：

```
1. 磁盘驱动识别分区，创建卷设备对象（VDO）
2. I/O 管理器发送 IRP_MJ_FILE_SYSTEM_CONTROL
   子类型：IRP_MN_MOUNT_VOLUME
3. 每个已注册的文件系统驱动尝试"认领"卷
4. 文件系统驱动检查引导扇区，识别文件系统类型
5. 匹配成功则创建 VCB（Volume Control Block）
6. 将 VCB 附加到卷设备对象
7. 返回 STATUS_SUCCESS，卷安装完成
```

**VCB（Volume Control Block）**：

VCB 是文件系统驱动为每个已挂载卷创建的核心数据结构：

```c
typedef struct _VCB {
    // 卷设备对象
    PDEVICE_OBJECT VolumeDeviceObject;
    // 文件系统类型（FAT32/NTFS等）
    // 卷的几何信息（扇区大小、簇大小等）
    // 缓存管理器相关结构
    // 文件对象树（FCB 树）
    // 脏标志、锁定状态等
} VCB, *PVCB;
```

**ReactOS 中 FastFAT 的 VCB**：

- FastFAT 驱动具有清晰的 VCB/FCB 分层架构
- VCB 管理卷级别的全局信息
- FCB（File Control Block）管理单个文件的打开实例

**我的洞见——卷安装是"文件系统驱动与卷设备的婚礼"**：

卷安装的第一性原理是**延迟绑定**：

> 💡 **为什么需要延迟绑定？**
> - 系统启动时并不知道每个分区是什么文件系统
> - 同一个 FAT32 驱动可以挂载到多个卷
> - 可移动介质随时可能插入/拔出
>
> 所以 Windows 采用"卷设备先创建，文件系统后绑定"的策略——只有当 I/O 管理器收到对该卷的第一个 I/O 请求时，才触发卷安装。

**卷安装的关键检查**：

文件系统驱动在 `IRP_MN_MOUNT_VOLUME` 处理中：

1. 读取卷的引导扇区
2. 验证文件系统签名（如 FAT32 的 `0xAA55`）
3. 检查文件系统参数（扇区大小、簇大小等）
4. 创建并初始化 VCB
5. 将 VCB 附加到卷设备对象栈

**卷卸载（Dismount）**：

当卷需要被卸载时（如介质移除、格式化）：

1. I/O 管理器发送 `IRP_MN_DISMOUNT_VOLUME`
2. 文件系统驱动刷新所有脏数据到磁盘
3. 关闭所有打开的文件对象
4. 释放 VCB 和相关资源
5. 从设备栈分离

**现代映照**：现代 Windows 的卷安装机制增加了：

- **BitLocker**：卷安装时可能涉及解密
- **WOF**：Windows Overlay Filter 在卷安装时叠加压缩/加密层
- **CSV（Cluster Shared Volume）**：故障转移集群中的共享卷

工业界：理解卷安装是**存储管理、备份软件、加密软件**的基础。现代杀毒软件的 minifilter 在卷安装时注册回调，监控该卷上的所有文件操作。

## 11.7 文件的创建

**书的脉络**：文件创建是 `IRP_MJ_CREATE` 的核心处理，涉及文件系统驱动的复杂逻辑。

**文件创建的完整流程**：

```
NtCreateFile(dwCreationDisposition = CREATE_NEW)
  ↓
I/O 管理器创建 IRP_MJ_CREATE
  ↓
对象管理器解析路径 → 找到卷设备对象
  ↓
IRP 沿着设备栈传递到文件系统驱动
  ↓
FastFAT/NTFS 的 Create 分发例程
  ↓
解析路径，查找目录项
  ↓
不存在且允许创建 → 分配 FAT 簇 / NTFS MFT 记录
  ↓
创建 FCB（File Control Block）
  ↓
创建文件对象（FILE_OBJECT）
  ↓
返回文件句柄
```

**FCB（File Control Block）**：

FCB 是文件系统驱动为每个打开的文件维护的核心结构：

```c
typedef struct _FCB {
    // 文件引用计数
    // 文件大小、属性
    // 簇链首簇号（FAT32）/ MFT 记录号（NTFS）
    // 缓存映射相关结构（SectionObjectPointer）
    // 文件锁状态
    // 目录项位置
} FCB, *PFCB;
```

**ReactOS 的 NTFS 文件创建**：

NTFS 的 Create 处理涉及：

1. **路径解析**：`NtfsMakeAbsoluteFilename` 构造绝对路径
2. **MFT 记录查找**：通过 `ReadFileRecord` 读取 MFT 记录
3. **文件名属性处理**：`GetBestFileNameFromRecord` 选择最佳文件名
4. **FCB 创建**：为新文件或打开的文件创建 FCB
5. **文件对象关联**：将 FCB 绑定到文件对象

**我的洞见——文件创建是"FCB 与文件对象的配对仪式"**：

文件创建的第一性原理是**分离"磁盘上的文件"和"打开实例"**：

> 📌 **三个层级的概念区分**：
> 1. **磁盘上的文件**：物理存储介质上的数据
> 2. **FCB**：文件系统驱动内部对该文件的表示（每个文件唯一）
> 3. **文件对象**：每次打开创建的实例（可能多个）
>
> 同一个文件可以被多个进程打开，产生多个文件对象，但共享同一个 FCB。

**CreateDisposition 的精确语义**：

- `FILE_CREATE`：文件必须不存在，否则失败
- `FILE_OPEN`：文件必须存在，否则失败
- `FILE_OPEN_IF`：不存在则创建
- `FILE_OVERWRITE`：存在则清空内容
- `FILE_OVERWRITE_IF`：存在则覆盖，不存在则创建
- `FILE_SUPERSEDE`：替换（先删除再创建）

**NTFS 文件创建的特殊性**：

NTFS 中每个文件对应一个 MFT 记录，文件创建实际上是：

1. 分配 MFT 记录
2. 创建标准信息属性（$STANDARD_INFORMATION）
3. 创建文件名属性（$FILE_NAME）
4. 如果是目录，创建索引根属性
5. 更新 $Bitmap 标记 MFT 记录为已用

**现代映照**：现代 Windows 的文件创建增加了：

- **事务支持**：TxF（Transaction NTFS）允许回滚文件创建
- **硬链接/软链接**：创建时可能涉及多个文件名属性
- **Extended Attributes**：EA 缓冲区从模板文件复制
- **Oplocks**：创建时可能打破其他进程的 oplock

工业界：理解文件创建是**文件系统过滤驱动、备份/恢复软件**的核心。现代 EDR 通过 minifilter 的 `IRP_MJ_CREATE` 回调监控文件创建事件，检测勒索软件行为。

## 11.8 缓存管理

**书的脉络**：缓存管理器（Cache Manager，Cc）是 Windows I/O 架构中最精妙的设计之一，它介于内存管理器（MM）和文件系统驱动之间。

**缓存管理器的核心思想**：

> 💡 **虚拟块缓存（Virtual Block Caching）**：缓存管理器以虚拟块为基础缓存数据，跟踪记录哪些文件的哪些部分位于缓存中。这使得可以在不涉及文件系统驱动程序的情况下进行智能预读（Read-Ahead）和延迟写（Lazy-Write）。

**缓存管理器的关键 API**：

| 函数 | 作用 |
|---|---|
| `CcInitializeCacheMap` | 将文件映射到系统缓存 |
| `CcCopyRead` | 从缓存复制数据到用户缓冲区 |
| `CcCopyWrite` | 从用户缓冲区复制数据到缓存 |
| `CcFlushCache` | 刷新缓存到磁盘 |
| `CcZeroData` | 清零缓存数据 |
| `CcMapData` / `CcUnpinData` | 映射/解除映射（FastFAT 用它访问 FAT 表） |

**缓存读取流程**：

```
ReadFile() 调用
  ↓
I/O 管理器检查 FastIo 例程
  ↓
有 FastIo → 调用 FastIoRead
  ↓
FastIoRead 检查文件对象是否已被缓存
  ↓
已缓存 → CcCopyRead 从系统缓存复制数据
  ↓
缓存未命中 → 触发页错误
  ↓
内存管理器 MmAccessFault 处理
  ↓
通过 IoPageRead 向文件系统发送 IRP_MJ_READ
  ↓
文件系统从磁盘读取数据到缓存
  ↓
CcCopyRead 完成，数据返回用户态
```

**缓存写入流程**：

```
WriteFile() 调用
  ↓
I/O 管理器检查 FastIo 例程
  ↓
有 FastIo → 调用 FastIoWrite
  ↓
FastIoWrite 检查文件对象是否已被缓存
  ↓
已缓存 → CcCopyWrite 写入系统缓存
  ↓
写入节流检查（CcCanIWrite）
  ↓
缓存页标记为脏
  ↓
延迟写入线程（Lazy Writer）定期将脏页刷盘
  ↓
通过 MmFlushSection → IoAsynchronousPageWrite
  ↓
发送 IRP_MJ_WRITE（IRP_NOCACHE）到 FSD
  ↓
FSD 直接发送到存储驱动写盘
```

**写入节流机制**：

Windows 缓存管理器有精密的写入节流：

- **脏页阈值**：系统缓存允许的脏页上限
- **CcCanIWrite**：文件系统调用此函数询问是否可以写入
- **CcDeferWrite**：异步写入时设置回调，允许时自动写入
- **卷感知**：对 USB 盘的写入不会节流 SSD 的写入

**预读线程**：

缓存管理器包含预读线程，依据文件对象的私有缓存映射中存储的读取历史，主动预读数据到缓存。

**我的洞见——缓存管理器的第一性原理是"把文件 I/O 变成内存访问"**：

缓存管理器的核心洞见是：**文件 I/O 的本质是内存管理问题，而不是磁盘 I/O 问题**。

> 📌 **这个设计的精妙之处**：
> 1. **统一缓存与内存**：系统缓存就是内核空间的页缓存
> 2. **页错误驱动 I/O**：缓存未命中时触发页错误，由内存管理器通过 IRP 从文件系统读取
> 3. **延迟写合并**：多个写操作合并为一个磁盘 I/O
> 4. **预读优化**：基于访问模式主动预读
> 5. **零拷贝潜力**：映射文件（Memory-Mapped File）可直接访问缓存页

**FastFAT 如何使用缓存管理器**：

FastFAT 在访问 FAT 表时使用 `CcMapData`：

```c
// 访问 FAT 表项
CcMapData(DeviceExt->FATFileObject, &Offset, ChunkSize,
          MAP_WAIT, &Context, &BaseAddress);
// 读取 FAT 表项
CurrentCluster = (*(PULONG)((char*)BaseAddress +
                (FATOffset % ChunkSize))) & 0x0fffffff;
// 解除映射
CcUnpinData(Context);
```

这样 FAT 表就被缓存了——第一次访问从磁盘读取，后续访问直接从缓存获取。

**现代映照**：现代 Windows 缓存管理器增加了：

- **写入节流优化**：更精细的卷感知节流
- **ReFS 缓存集成**：弹性文件系统使用不同的缓存策略
- **CSV 缓存**：集群共享卷的缓存一致性
- **WOF 集成**：压缩/加密卷的缓存处理

工业界：理解缓存管理器是**高性能文件服务器、数据库系统**的基础。现代 SQL Server 使用 `FILE_FLAG_WRITE_THROUGH` 和 `FILE_FLAG_NO_BUFFERING` 绕过缓存管理器，实现自己的 I/O 管理。

## 11.9 文件的读写

**书的脉络**：文件读写是 `IRP_MJ_READ` 和 `IRP_MJ_WRITE` 的处理，涉及缓存管理器、内存管理器、文件系统驱动的紧密协作。

**读取操作的完整流程**：

```
ReadFile(hFile, buffer, length, ...)
  ↓
NtReadFile
  ↓
I/O 管理器创建 IRP_MJ_READ
  ↓
检查文件对象是否有 FastIo 例程
  ↓
有 → FastIoRead → CcCopyRead（从缓存复制）
  ↓
缓存未命中 → 页错误 → MmAccessFault
  ↓
通过 IoPageRead 发送 IRP_MJ_READ（IRP_NOCACHE）
  ↓
文件系统驱动（FastFAT/NTFS）处理
  ↓
解析 FCB，找到数据所在的簇/扇区
  ↓
通过卷设备对象发送 IRP 到磁盘驱动
  ↓
磁盘驱动通过 DMA 读取数据
  ↓
数据到达缓存，CcCopyRead 复制到用户缓冲区
  ↓
ReadFile 返回
```

**写入操作的完整流程**：

```
WriteFile(hFile, buffer, length, ...)
  ↓
NtWriteFile
  ↓
I/O 管理器创建 IRP_MJ_WRITE
  ↓
检查文件对象是否有 FastIo 例程
  ↓
有 → FastIoWrite → CcCopyWrite（写入缓存）
  ↓
缓存页标记为脏
  ↓
延迟写入线程定期刷盘
  ↓
MmFlushSection → IoAsynchronousPageWrite
  ↓
发送 IRP_MJ_WRITE（IRP_NOCACHE）到 FSD
  ↓
FSD 写入磁盘
```

**同步 vs 异步 I/O**：

- **同步 I/O**：`ReadFile` 阻塞直到完成
- **异步 I/O**：`FILE_FLAG_OVERLAPPED` + OVERLAPPED 结构，立即返回

**缓存 vs 非缓存 I/O**：

- **缓存 I/O**（默认）：经过缓存管理器
- **非缓存 I/O**（`FILE_FLAG_NO_BUFFERING`）：绕过缓存，直接磁盘操作
  - 要求缓冲区对齐到扇区大小
  - 要求读写长度对齐到扇区大小
  - 常用于数据库、虚拟机磁盘等高性能场景

**我的洞见——文件读写是"IRP 在缓存与磁盘之间的舞蹈"**：

文件读写的第一性原理是**IRP 的双重角色**：

> 💡 **同一个 ReadFile 调用可能产生两种完全不同的 IRP**：
> 1. **缓存读**：FastIoRead → CcCopyRead → 缓存命中 → 无 IRP（直接从缓存复制）
> 2. **缓存未命中**：页错误 → IoPageRead → IRP_MJ_READ（IRP_NOCACHE）→ 文件系统驱动
>
> 写操作类似：CcCopyWrite 写入缓存，延迟写入线程后续发送 IRP_MJ_WRITE（IRP_NOCACHE）到磁盘。

**关键性能因素**：

1. **顺序访问 vs 随机访问**：`FILE_FLAG_SEQUENTIAL_SCAN` 提示顺序访问，优化预读；`FILE_FLAG_RANDOM_ACCESS` 提示随机访问，禁用预读
2. **缓存命中率**：高命中率 = 高性能
3. **写入节流**：大量写入时可能被节流
4. **对齐要求**：非缓存 I/O 要求扇区对齐

**FAT32 的读写实现**：

FastFAT 的读写核心是通过 FAT 表查找簇链：

```c
// 读取文件的第 N 个簇
FAT32GetNextCluster(DeviceExt, CurrentCluster, &NextCluster);
// 通过卷设备对象发送 IRP 读取该簇的数据
```

**NTFS 的读写实现**：

NTFS 通过 MFT 记录的数据属性找到数据流的位置：

- **常驻属性**：小文件直接存储在 MFT 记录内
- **非常驻属性**：大文件通过数据运行（Data Run）描述簇位置

**现代映照**：现代 Windows 文件读写增加了：

- **SMB 3.x 多通道**：远程文件读写通过多网络连接
- **RDMA**：SMB Direct 使用 RDMA 实现零拷贝远程文件访问
- **ReFS**：弹性文件系统使用校验和和数据完整性功能
- **WOF**：压缩/加密卷的透明读写

工业界：理解文件读写是**数据库系统、虚拟机、备份软件**的基础。现代高性能应用广泛使用 `FILE_FLAG_NO_BUFFERING` 和 `FILE_FLAG_WRITE_THROUGH` 实现精细的 I/O 控制。

## 11.10 NTFS 文件系统简介

**书的脉络**：NTFS 是 Windows 的现代文件系统，相比 FAT32 具有革命性的设计。

**NTFS 的核心设计理念**：

> 💡 **一切皆属性**：NTFS 中每个文件由一个 MFT（Master File Table）记录表示，记录中包含多个属性（Attribute）。文件数据是其中一个属性，文件名是另一个属性，权限是第三个属性……这种设计让 NTFS 极具扩展性。

**MFT（主文件表）**：

NTFS 卷的核心是一个 MFT，每个文件对应一个 MFT 记录（默认 1KB）。ReactOS 的 NTFS 驱动中定义了 MFT 记录 ID 到文件名的映射：

```c
static PCWSTR MftIdToName[] = {
    L"$MFT", L"$MFTMirr", L"$LogFile", L"$Volume",
    L"AttrDef", L".", L"$Bitmap", L"$Boot",
    L"$BadClus", L"$Quota", L"$UpCase", L"$Extended"
};
```

**NTFS 的关键特性**：

| 特性 | 说明 |
|---|---|
| **MFT 记录** | 每个文件对应一个 MFT 记录 |
| **属性流** | 文件数据作为属性存储，支持多个数据流 |
| **B+ 树索引** | 目录使用 B+ 树，支持高效查找 |
| **日志（Journal）** | `$LogFile` 记录所有元数据操作，支持恢复 |
| **压缩** | 透明的文件级压缩 |
| **加密（EFS）** | 文件级加密 |
| **配额** | 用户级磁盘配额 |
| **硬链接/软链接** | 支持高级文件链接 |
| **稀疏文件** | 高效存储大量零数据 |
| **重解析点（Reparse Point）** | 符号链接、挂载点的基础 |

**NTFS 的文件创建**：

ReactOS 的 NTFS 驱动在创建文件时：

1. 通过 `NtfsMakeAbsoluteFilename` 构造绝对路径
2. 通过 `ReadFileRecord` 读取父目录的 MFT 记录
3. 在 MFT 中分配新记录
4. 创建 `$STANDARD_INFORMATION` 属性
5. 创建 `$FILE_NAME` 属性
6. 如果是目录，创建 `$INDEX_ROOT` 属性（B+ 树根）
7. 更新 `$Bitmap` 标记 MFT 记录为已用

**NTFS 的路径解析**：

NTFS 支持通过 MFT 记录 ID 反向构造路径（`NtfsMoonWalkID`）：

```
给定 MFT 记录 ID
  ↓
读取该记录的 $FILE_NAME 属性
  ↓
获取父 链接（指向父目录的 MFT 记录 ID）
↓

递归反向构造每一级目录名

↓

拼接得到完整路径（如 `\Windows\System32\ntdll.dll`）


这个"Moon Walk"（月球漫步，即**倒着走**）算法的精妙之处在于：**NTFS 的目录不是"路径的容器"，而是"指向子文件的 B+ 树索引"**。常规解析是"从根目录顺着 B+ 树往下找文件名"，而 Moon Walk 是"从文件记录顺着 `$Parent` 指针往回跳到每一级父目录，取出目录名再拼接"。前者是正向路径解析（CreateFile 时用），后者是反向路径重建（打开文件后获取完整路径、或进程管理器显示文件位置时用）。

**我的洞见——NTFS 的"一切皆属性"是文件系统设计的范式跃迁**：

FAT32 是"扁平结构"：目录项里有文件名、首簇号、大小——所有元数据挤在一个固定 32 字节的目录条目里。想加新功能？没地方放。NTFS 则是"**面向属性的对象存储**"：每个文件是一个 MFT 记录，记录里是一组变长的属性（Attribute），每个属性有类型、长度、内容。

> 📌 **这种属性模型的第一性原理优势**：
> 1. **可扩展**：要加新功能（压缩、加密、配额、扩展属性），只需加新属性类型，不改 MFT 记录格式
> 2. **常驻优化**：小文件（如几字节的配置）可以直接存在 MFT 记录内（常驻属性），无需分配外部簇，一次 I/O 搞定
> 3. **多数据流**：一个文件可以有多个数据流（`file.txt:streamName`），这是 NTFS 独有的特性
> 4. **B+ 树目录**：目录项不再是线性链表，而是 B+ 树索引，查找复杂度从 O(n) 降到 O(log n)，十万级文件的目录也能秒开

**NTFS 的关键属性类型**：

| 属性类型 | 说明 |
|---|---|
| `$STANDARD_INFORMATION` | 标准信息（时间戳、属性、所有者 SID） |
| `$FILE_NAME` | 文件名（可多个，支持硬链接） |
| `$DATA` | 文件数据（可多个流） |
| `$INDEX_ROOT` / `$INDEX_ALLOCATION` | B+ 树目录索引 |
| `$BITMAP` | 位图（MFT 和卷簇的使用情况） |
| `$LOGGED_UTILITY_STREAM` | EFS 加密数据 |
| `$REPARSE_POINT` | 重解析点（符号链接、挂载点） |

**NTFS 的日志与恢复机制**：

NTFS 的 `$LogFile` 是实现**元数据日志（Journaling）** 的核心。所有对 MFT 的元数据修改都先写入日志，再应用到磁盘。系统崩溃后，恢复过程可以：

- **重放（Redo）**：把已提交但未落盘的修改重新应用
- **撤销（Undo）**：把未提交的不完整修改回滚

> ⚠️ **这是 NTFS 相比 FAT32 的杀手锏**：FAT32 断电 = 可能严重损坏（FAT 表半更新状态），NTFS 断电 = 自动恢复一致性。这也是 Windows 系统盘强制要求 NTFS 的根本原因。
```

```
**现代映照**：现代 Windows 的 NTFS 已远超 ReactOS 的实现，关键演进：

- **存储空间（Storage Spaces）**：在 NTFS 之下增加虚拟化层，实现镜像、奇偶校验、分层存储
- **ReFS（Resilient File System）**：微软推出的下一代文件系统，采用**写时复制（Copy-on-Write）** 和**校验和完整性**，彻底消除静默数据损坏
- **WOF（Windows Overlay Filter）**：支持 NTFS 卷上的透明压缩和去重
- **VBS 集成**：受保护进程的文件访问通过安全内核验证

**NTFS vs ReFS 的定位分化**：

| 维度 | NTFS | ReFS |
|---|---|---|
| 定位 | 通用/系统盘 | 数据中心/大容量存储 |
| 恢复机制 | 日志回放 | 写时复制 + 校验和 |
| 最大卷大小 | 256 TB | 35 PB（理论） |
| 压缩/加密 | 支持 | 不支持（依赖上层） |
| 可作为系统盘 | ✅ | ❌（需 NTFS 系统分区） |
| 静默损坏防护 | 有限 | 强（端到端校验和） |

工业界：NTFS 的**最小文件记录段（USN）变更日志**（Update Sequence Number）是现代文件监控的基础——EDR 和备份软件通过读取 `$Extend\$UsnJrnl` 的 USN 日志，能高效地增量感知文件变化，而无需轮询整个卷。这是理解 Windows 文件监控（如 Sysmon 的 FileCreate 监控）底层原理的关键。
```

```
## 工业界实际应用与安全视角

### 🛡️ 安全领域

**1. Minifilter 是 EDR 的眼睛和手**：

现代杀毒软件、EDR、备份工具全部通过**文件系统 minifilter** 挂载到文件栈上，拦截 `IRP_MJ_CREATE`/`IRP_MJ_READ`/`IRP_MJ_WRITE`/`IRP_MJ_SET_INFORMATION`（删除/重命名）。例如：

- **勒索软件检测**：监控大量文件的 `IRP_MJ_WRITE` + 后续 `IRP_MJ_SET_INFORMATION`（加密后重命名），结合扩展名突变模式识别
- **防篡改保护**：通过 `FLT_FLUSH_BUFFERS` 回调阻止对受保护文件的写入
- **进程注入检测**：监控可执行文件（`SectionReadOnly`/`SectionReadWrite`）的创建映射

**2. USN 变更日志的高效监控**：

读取 `$Extend\$UsnJrnl` 的 USN 日志，增量感知文件变化，比轮询整个卷高效几个数量级。Sysmon 的 `FileCreate`/`FileDelete` 事件底层就依赖 USN。

**3. 缓存攻击面**：

缓存管理器是内核漏洞的温床——TOCTOU（Time-of-Check-to-Time-of-Use）竞争条件、Oplock 状态机漏洞、CcCopyRead/CcCopyWrite 的边界检查缺失，都是历史 CVE 的来源。

### ⚙️ 工业应用

**1. 数据库与虚拟化**：SQL Server、Hyper-V、VMware 广泛使用 `FILE_FLAG_NO_BUFFERING` + `FILE_FLAG_WRITE_THROUGH` 绕过缓存管理器，实现自己的 I/O 调度和崩溃一致性。

**2. SMB 3.x 与 RDMA**：远程文件读写通过 SMB 多通道 + SMB Direct（RDMA），实现零拷贝远程文件访问，延迟接近本地。

**3. 存储分层与去重**：Windows Server 的**存储空间直通（Storage Spaces Direct）** 在 NTFS/ReFS 之下做镜像、纠删码、自动分层（SSD → HDD 冷热迁移）。

**4. WSL 文件互操作**：`drvfs` 把 Linux 文件系统挂载到 NT 路径空间，让 `\??\C:\Users\...\AppData\Local\Packages\...\LocalState\rootfs` 映射到 WSL 的 ext4——这正是 11.2 节"NT 路径名是统一名字空间"理念的现代延伸。
```

## 11.1 Win32 API 函数 CreateFileW()

**书的脉络**：CreateFileW 是 Win32 打开/创建"一切有名字内核对象"的统一入口。参数 `dwCreationDisposition` 决定"存在/不存在时怎么办"，`dwFlagsAndAttributes` 控制缓存模式、异步模式、安全语义。内部通过 `RtlDosPathNameToNtPathName_U` 把 DOS 路径转成 NT 路径，再调用 `NtCreateFile` 进入内核。

**我的洞见——CreateFileW 是"对象管理器的万能开门钥匙"**：

它的第一性原理是**用一个 API 统一打开所有内核命名对象**。你以为它在"创建文件"，其实它在"打开对象"——文件名、设备名、管道名、邮槽名，对对象管理器来说都是名字空间里的节点。只有名字解析到卷设备对象后，I/O 管理器才会把剩余路径交给文件系统驱动，这才进入真正的"文件语义"。

**现代补充**：现代 Windows 增加了 `FILE_FLAG_OPEN_REPARSE_POINT`、事务性 NTFS（TxF，现已弃用）、以及 WSL 互操作路径的处理。EDR 通过 minifilter 拦截 `IRP_MJ_CREATE` 来监控所有打开操作。

## 11.2 NT 路径名

**书的脉络**：NT 路径是内核对象管理器的全局层次名字空间。`\??\C:` 是 DOS 符号链接，解析到 `\Device\HarddiskVolumeN`。对象管理器负责从 `` 根开始逐级查找，找到卷设备对象后，剩余路径交给文件系统驱动。

**我的洞见——NT 路径是"统一名字空间的邮政编码"**：

用户态用 DOS 路径（`C:\...`）只是友好别名，内核态用 NT 路径（`\??\C:\...`）才是真实地址。对象管理器只管"找到卷设备"，不管"卷上有什么文件"——这是卷管理与文件系统的彻底解耦。

**现代补充**：现代 Windows 增加了 Volume GUID 路径（`\??\Volume{GUID}`），不受盘符变化影响，更稳定。

---

## 11.3 文件路径名的解析

**书的脉络**：路径解析分两阶段——对象管理器解析卷设备对象（如 `\??\D:` → `\Device\HarddiskVolume2`），然后文件系统驱动解析剩余部分（如 `\test.txt`）。绝对路径从卷根开始，相对路径以已打开目录为参照。

**我的洞见——路径解析是"责任分割"**：

对象管理器只认卷设备，文件系统驱动才认文件。这种分割让同一个文件系统驱动可以挂载到任意卷上。NTFS 通过 MFT 记录 ID 和 `$Parent` 链接可以反向构造路径（Moon Walk），但正向解析是顺着 B+ 树往下找。

---

## 11.4 FAT32 文件系统

**书的脉络**：FAT32 用引导扇区描述卷参数，FAT 表记录簇链，目录项记录文件名/首簇/大小。文件数据通过簇链串联。FastFAT 驱动通过 `CcMapData` 将 FAT 表映射到缓存。

**我的洞见——FAT32 是"一张表管整个磁盘"**：

第一性原理极简——簇是分配单位，FAT 表是簇的链表，目录项是文件的元数据入口。没有日志、没有权限、没有 B+ 树，所以简单但脆弱。断电可能损坏 FAT 表，导致整个卷不可用。

**现代补充**：FAT32 仍用于 U 盘、SD 卡、EFI 系统分区，但不再作为系统盘。

## 11.5 文件系统驱动的装载和初始化

**书的脉络**：FSD 在 `DriverEntry` 中创建设备对象，注册 IRP_MJ_* 分发例程、FastIo 例程、缓存管理器回调。通过 `IoRegisterFileSystem` 注册到 `\FileSystem` 目录。

**我的洞见——FSD 初始化是"三重身份注册"**：

必须同时注册为 WDM 驱动（IRP 分发）、缓存管理器客户端（延迟写/预读回调）、FastIo 提供者（绕过 IRP 的快速路径）。缺一个就无法完整接入 Windows I/O 体系。

**现代补充**：现代增加了 minifilter 注册（Filter Manager），杀毒软件通过 minifilter 挂载到文件栈。

## 11.6 文件卷的安装

**书的脉络**：卷安装是文件系统驱动与卷设备的绑定。I/O 管理器发送 `IRP_MN_MOUNT_VOLUME`，FSD 检查引导扇区签名，匹配则创建 VCB（Volume Control Block）并附加到卷设备栈。

**我的洞见——卷安装是"延迟绑定"**：

卷设备先创建，文件系统后绑定。系统启动时不知道每个分区是什么文件系统，只有当第一个 I/O 到达时才触发挂载。这让同一 FSD 可以挂载到多个卷。

**现代补充**：现代增加了 BitLocker 解密、WOF 叠加层、CSV（集群共享卷）等。

## 11.7 文件的创建

**书的脉络**：`IRP_MJ_CREATE` 处理中，FSD 解析路径，查找/创建 FCB（File Control Block），创建文件对象。FCB 是文件的内部表示（每文件唯一），文件对象是打开实例（可多个）。

**我的洞见——文件创建是"FCB 与文件对象的配对"**：

磁盘上的文件、FCB、文件对象是三个层级。同一文件被多个进程打开产生多个文件对象，但共享一个 FCB。NTFS 创建文件即分配 MFT 记录并创建属性。

**现代补充**：现代增加了事务支持（TxF）、硬链接/软链接、oplock 处理。EDR 通过 minifilter 的 Create 回调检测勒索软件创建行为。

## 11.8 缓存管理

**书的脉络**：缓存管理器以虚拟块缓存文件数据，通过 `CcCopyRead`/`CcCopyWrite` 在缓存和用户缓冲区之间复制。缓存未命中触发页错误，由内存管理器通过 `IoPageRead` 从磁盘读取。延迟写入线程定期将脏页刷盘。

**我的洞见——缓存管理器的第一性原理是"把文件 I/O 变成内存访问"**：

文件 I/O 本质是内存管理问题。缓存命中 = 直接复制；缓存未命中 = 页错误 → 内核自动从磁盘加载。写入先到缓存，延迟刷盘合并 I/O。FastFAT 用 `CcMapData` 缓存 FAT 表本身。

**现代补充**：现代增加了更精细的写入节流、ReFS 缓存策略、CSV 缓存一致性。

## 11.9 文件的读写

**书的脉络**：读操作优先走 FastIo → 缓存命中则 `CcCopyRead`；未命中则页错误 → `IoPageRead` → IRP_MJ_READ（非缓存）→ 磁盘。写操作类似，缓存写后由延迟写入线程刷盘。非缓存 I/O（`FILE_FLAG_NO_BUFFERING`）绕过缓存，要求扇区对齐。

**我的洞见——文件读写是"IRP 的双重角色"**：

同一个 ReadFile 可能产生两种 IRP：缓存命中时无 IRP（直接复制），缓存未命中时产生 `IRP_NOCACHE` 从磁盘读。写操作类似。这是性能与一致性的平衡。

**现代补充**：数据库/虚拟化用 `FILE_FLAG_NO_BUFFERING` + `FILE_FLAG_WRITE_THROUGH` 绕过缓存实现精细控制。SMB 3.x + RDMA 实现远程零拷贝。

## 11.10 NTFS 文件系统简介

**书的脉络**：NTFS 以 MFT 为核心，每个文件是一个 MFT 记录，包含多个属性（文件名、数据、索引等）。支持 B+ 树目录、日志恢复、压缩、加密、多数据流、硬链接。ReactOS 的 NTFS 驱动是只读实现。

**我的洞见——NTFS 是"一切皆属性"的范式跃迁**：

相比 FAT32 的扁平固定结构，NTFS 的属性模型可扩展、支持常驻优化（小文件直接放 MFT）、多数据流、B+ 树目录（O(log n) 查找）。`$LogFile` 提供元数据日志，断电可恢复——这是系统盘强制 NTFS 的原因。

**现代补充**：ReFS 采用写时复制+校验和，提供更强完整性。NTFS 的 USN 日志是 EDR/备份工具高效监控文件变化的基础。
