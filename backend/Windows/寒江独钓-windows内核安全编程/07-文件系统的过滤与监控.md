## 7.1 文件系统的设备对象

### 7.1.1 控制设备与卷设备

**📌 书中的世界**

文件系统驱动（ntfs.sys、fastfat.sys、cdfs.sys 等）会创建两类设备对象：

- **控制设备对象（CDO，Control Device Object）**：路径通常为 `\FileSystem\Filters\SFilter` 或 `\FileSystem\SFilterCDO`，用于接收文件系统控制 IRP（主功能号 `IRP_MJ_FILE_SYSTEM_CONTROL`），主要任务是修改整个驱动的内部配置、捕获卷设备的生成信息
- **卷设备对象（VDO，Volume Device Object）**：一个卷对应一个逻辑盘（如 C:、D:），发送给卷设备的 IRP 一般则是文件操作 IRP

**🔍 第一性原理视角：为什么文件系统要分两个设备对象？**

这是"控制平面与数据平面分离"思想在文件系统驱动中的体现：

- **CDO 是"管理平面"**：处理文件系统级的控制请求（如卷挂载 `IRP_MN_MOUNT_VOLUME`、加载/卸载文件系统等）
- **VDO 是"数据平面"**：处理针对具体卷的文件操作（Create/Read/Write/Close 等）

sfilter 必须先绑定 CDO，才能捕获卷挂载事件，进而绑定新生成的 VDO。这是 sfilter 框架的核心思路：**绑定 CDO → 捕获卷挂载 → 绑定 VDO → 过滤文件 I/O**。

> 💡 **洞见**：理解 CDO 与 VDO 的分工，是理解整个文件系统过滤架构的钥匙。CDO 让你"看见文件系统的诞生"，VDO 让你"看见文件的读写"。

### 7.1.2 生成自己的一个控制设备

**📌 书中的世界**

过滤驱动在 `DriverEntry` 中调用 `IoCreateDevice` 创建自己的 CDO：

```
RtlInitUnicodeString(&name, L"\\FileSystem\\Filters\\SFilter");
IoCreateDevice(DriverObject, 0, &name, 
    FILE_DEVICE_DISK_FILE_SYSTEM, FILE_DEVICE_SECURE_OPEN, FALSE, &gSFilterCDO);
```

注意书中强调的兼容性细节：低版本 Windows 可能没有 ``\FileSystem\Filters\` 这个目录，此时要 fallback 到``\FileSystem\SFilterCDO`。

**🔍 第一性原理视角：过滤驱动自己的 CDO 是"用户态与内核态的通信端点"**

过滤驱动创建 CDO 的目的：

1. 提供一个**命名设备**，让用户态服务可以通过 `CreateFile("\\.\SFilter")` 打开它
2. 通过 `DeviceIoControl` 下发控制命令（启用/禁用监控、查询策略、收集日志）
3. 与绑定到文件系统 CDO/VDO 的过滤设备对象（FiDO）区分开——过滤驱动自己的 CDO 不参与 I/O 过滤，只做控制通道

> ⚠️ **关键认知**：过滤驱动有两类设备对象——**自己的 CDO**（用户态通信用）和**绑定到文件系统设备栈上的 FiDO**（过滤用）。这两类设备对象职责完全不同，初学者极易混淆。

## 7.2 文件系统的分发函数

### 7.2.1 普通的分发函数

**📌 书中的世界**

过滤驱动必须设置 `MajorFunction` 数组中的所有 IRP 分发函数。与第6章磁盘过滤一样，过滤驱动必须为所有可能到达下层驱动的 IRP 类型提供派遣函数，否则那些 IRP 会被 I/O 管理器用默认的 `STATUS_INVALID_DEVICE_REQUEST` 完成——导致下层功能失效。

**🔍 第一性原理视角：IRP 是文件 I/O 的"默认机制"**

微软文档明确：**IRP 是请求 I/O 操作的默认机制**，可用于同步或异步 I/O、缓存或非缓存 I/O，也可用于分页 I/O。内存管理器通过发送适当的 IRP 到文件系统来处理页错误。所有文件系统操作和 legacy 文件系统过滤驱动都必须支持 IRP。

### 7.2.2 文件过滤的快速 IO 分发函数

**📌 书中的世界**

除了普通 IRP 分发函数，过滤驱动还必须设置 `FastIoDispatch` 结构体中的快速 I/O 回调函数指针。

**🔍 第一性原理视角：Fast I/O 是"缓存命中时的快捷通道"**

微软文档的解释非常精辟：

> "Fast I/O is designed for rapid synchronous I/O on cached files. In fast I/O operations, data is transferred directly between user buffers and the system cache, bypassing the file system and the storage driver stack."

换句话说：当文件数据已经在系统缓存中时，I/O 管理器**不走 IRP**，而是直接调用文件系统的 Fast I/O 例程，在用户缓冲区和系统缓存之间拷贝数据。这避免了构造和下发 IRP 的开销——而 IRP 的构造/传递开销在缓存 I/O 场景下往往"得不偿失"。

**为什么过滤驱动必须实现 Fast I/O 例程？**

微软文档说得很清楚：文件系统和 legacy 过滤驱动**必须实现 Fast I/O 例程**。即使不支持 Fast I/O 功能，也必须定义一个返回 `FALSE` 的 Fast I/O 例程。

> 💡 **洞见**：如果过滤驱动不提供 Fast I/O 分发函数，会导致附加的设备栈上的 Fast I/O 处理被禁用，从而丧失系统性能优势。这就是为什么书中用了整整 7.2.2-7.2.4 三节来讲 Fast I/O——它不是可选项，而是过滤驱动完整性的关键。

OSR 的技术文章也印证了这一点：I/O 管理器总是调用位于设备栈顶部的 Fast I/O 分发表。一旦过滤驱动附加到顶部，它就会收到 Fast I/O 请求。如果过滤驱动不注册 Fast I/O 分发表，那么该设备栈的 Fast I/O 处理就会被禁用。

### 7.2.3 快速 IO 分发函数的一个实现

**📌 书中的世界**

书中给出了 Fast I/O 分发函数的标准实现模式：

- 对于不需要特殊处理的 Fast I/O 操作，调用下层驱动的对应 Fast I/O 例程
- 对于需要过滤的操作（如 `FastIoRead`、`FastIoWrite`），先做过滤逻辑，再调用下层
- 必须保证调用链不中断——否则 Fast I/O 功能就会失效

**🔍 第一性原理视角：Fast I/O 过滤 = "旁路拦截"**

与 IRP 过滤不同，Fast I/O 没有"完成例程"机制。Fast I/O 例程要么：

- 返回 `TRUE`：表示操作已处理完成（数据已传输或错误已设置）
- 返回 `FALSE`：表示 Fast I/O 无法处理，I/O 管理器会退回到构造 IRP 的路径

这意味着 Fast I/O 过滤是**同步的、即时的**——你必须在 Fast I/O 例程中当场决定"放行/拦截/修改"，而无法像 IRP 那样"下发后等完成例程再处理"。

> ⚠️ **工业级陷阱**：Fast I/O 读/写操作的"拦截"必须在例程返回前完成。如果你需要异步处理（比如查询云端策略），Fast I/O 路径下做不到——只能返回 `FALSE` 让 I/O 管理器走 IRP 路径。这就是为什么现代 EDR 产品往往在 pre-operation 回调中做"同步策略判断"，把耗时的操作放到用户态服务异步处理。

### 7.2.4 快速 IO 分发函数逐个简介

**📌 书中的世界**

书中逐一介绍了需要实现的 Fast I/O 例程：

- `FastIoCheckIfPossible`：检查 Fast I/O 是否可行
- `FastIoRead` / `FastIoWrite`：快速读写
- `FastIoQueryBasicInfo` / `FastIoQueryStandardInfo`：查询文件信息
- `FastIoLock` / `FastIoUnlockSingle` / `FastIoUnlockAll`：文件锁
- `FastIoDetachDevice`：卷卸载时必须实现
- `FastIoDeviceControl`：设备控制
- `FastIoQueryNetworkOpenInfo`：网络文件信息查询
- `FastIoAcquireFile` / `FastIoReleaseFile`：文件资源获取/释放

**🏭 现代工业实践**

微软文档列出可以同时是 IRP 或 Fast I/O 的操作：`IRP_MJ_DEVICE_CONTROL`、`IRP_MJ_QUERY_INFORMATION`（特定信息类）、`IRP_MJ_READ`、`IRP_MJ_WRITE`、`IRP_MJ_LOCK_CONTROL`。

minifilter 驱动可以通过设置 `FLTFL_OPERATION_REGISTRATION_SKIP_CACHED_IO` 标志来避免接收 Fast I/O 的 `IRP_MJ_READ`/`WRITE` 操作和缓存的基于 IRP 的读写——这是现代 minifilter 优化性能的重要手段。

## 7.3 设备的绑定前期工作

### 7.3.1 动态地选择绑定函数

**📌 书中的世界**

不同文件系统（NTFS、FAT、CDFS、UDF）的 CDO 特性略有不同，过滤驱动需要根据实际情况动态选择合适的绑定策略。

**🔍 第一性原理视角：绑定是"时机游戏"**

文件系统过滤的最大挑战是：**文件系统驱动是动态加载的**。系统启动时 ntfs.sys 加载，U 盘插入时 cdfs.sys 或 udfs.sys 加载，移动硬盘接入时可能触发 rawfs.sys……过滤驱动不可能在 `DriverEntry` 里"绑定所有文件系统"——因为那时它们还没加载。

所以必须**动态感知文件系统的加载**，并在加载的第一时间绑定其 CDO。

### 7.3.2 注册文件系统变动回调

**📌 书中的世界**

通过 `IoRegisterFsRegistrationChange` 注册一个回调函数，当系统中有文件系统驱动加载/卸载时，该回调函数会被调用：

```
IoRegisterFsRegistrationChange(DriverObject, SfFsNotification);
```

回调函数原型：

```
VOID SfFsNotification(
    IN PDEVICE_OBJECT DeviceObject,  // 文件系统的 CDO
    IN BOOLEAN Active);              // TRUE=加载, FALSE=卸载
```

**🔍 第一性原理视角：这是"订阅-通知"模式在内核中的经典应用**

`IoRegisterFsRegistrationChange` 让过滤驱动订阅了"文件系统变动"事件。每当有新文件系统激活，回调函数就被调用，过滤驱动趁机绑定该文件系统的 CDO。

> 💡 **洞见**：这种"动态注册 + 回调"的模式是 Windows 内核中处理动态事件的通用范式——类似的还有 PnP 事件通知、电源事件通知、注册表键通知。理解了这个范式，你就能理解为什么现代 Windows 内核编程大量使用"回调"而非"轮询"。

### 7.3.3 文件系统变动回调的一个实现

**📌 书中的世界**

在回调函数中：

1. 检查 `Active` 参数——`TRUE` 表示文件系统刚加载
2. 调用 `IoGetDeviceObjectPointer` 或 `ObReferenceObjectByName` 获取文件系统 CDO 的指针
3. 调用 `IoCreateDevice` 创建过滤设备对象（FiDO）
4. 调用 `IoAttachDeviceToDeviceStack` 将 FiDO 绑定到文件系统 CDO
5. 跳过"文件系统识别器"（详见 7.3.4）

**🏭 现代工业实践**

sfilter 源码中的 `SfFsNotification` 是这一机制的经典实现。它确保了无论文件系统何时加载，过滤驱动都能第一时间附着到其 CDO 上，从而捕获后续的卷挂载事件。

### 7.3.4 文件系统识别器

**📌 书中的世界**

Windows 中有一个特殊的"文件系统识别器"（File System Recognizer，如 `fs_rec.sys`），它的作用是：当系统遇到一个尚未加载对应文件系统驱动的设备时，先由识别器判断该设备使用什么文件系统，然后加载真正的文件系统驱动。

**关键陷阱**：过滤驱动**不应该绑定到文件系统识别器**——因为它是用来加载真正的文件系统驱动程序的。如果绑定了识别器，当真正的文件系统加载时，还需要解除绑定并重新绑定到真文件系统上。

**🔍 第一性原理视角：识别器是"文件系统加载的引子"**

识别器的设备对象名通常有特定模式。sfilter 的做法是：在绑定前检查设备对象名，如果是识别器则跳过。或者在 `IRP_MN_LOAD_FILE_SYSTEM` 发生时处理——当识别器决定加载真正的文件系统时，会产生这样一个 IRP，过滤驱动此时应该解除对识别器的绑定，转而绑定真正的文件系统。

> ⚠️ **工业级细节**：Windows 文件系统识别器机制在不同版本中有所差异。在现代 Windows 上，`fs_rec` 仍然是系统的一部分，但过滤驱动通常通过更精细的判断（设备类型、驱动名称等）来避免绑定到识别器。

## 7.4 文件系统控制设备的绑定

### 7.4.1 生成文件系统控制设备的过滤设备

**📌 书中的世界**

针对每个文件系统 CDO，过滤驱动创建一个无名 FiDO，并附着到 CDO 所在的设备栈上：

```
IoCreateDevice(DriverObject, sizeof(SFILTER_DEVICE_EXTENSION), NULL,
    FILE_DEVICE_DISK_FILE_SYSTEM, 0, FALSE, &newDeviceObject);
IoAttachDeviceToDeviceStack(newDeviceObject, fileSystemCDO);
```

**🔍 第一性原理视角：无名设备的铁律**

与过滤驱动自己的 CDO（有名，用于用户态通信）不同，**附着到文件系统设备栈上的 FiDO 必须无名**。这是微软的硬性安全要求——有名设备对象可能被用户态程序直接打开，从而绕过文件系统的安全机制。

### 7.4.2 绑定文件系统控制设备

**📌 书中的世界**

绑定 CDO 的目的是**捕获卷挂载事件**。当文件系统为某个卷创建 VDO 时，会先收到一个 `IRP_MJ_FILE_SYSTEM_CONTROL` 的 `IRP_MN_MOUNT_VOLUME` 请求。过滤驱动在 CDO 的 FiDO 上拦截这个 IRP，就能知道"有新卷要挂载了"，从而进一步绑定 VDO。

**🔍 第一性原理视角：这是"绑定的连锁反应"**

```
绑定文件系统 CDO
    ↓ 捕获 IRP_MN_MOUNT_VOLUME
    ↓ 卷挂载时，文件系统创建 VDO
绑定 VDO
    ↓ 捕获针对该卷的所有文件 I/O
    ↓ 实现文件监控/过滤
```

### 7.4.3 利用文件系统控制请求

**📌 书中的世界**

在 `IRP_MJ_FILE_SYSTEM_CONTROL` 的派遣函数中：

- `IRP_MN_MOUNT_VOLUME`：卷挂载请求——这是绑定 VDO 的关键时机
- `IRP_MN_LOAD_FILE_SYSTEM`：加载文件系统请求——处理识别器到真实文件系统的切换
- `IRP_MN_USER_FS_REQUEST`：用户态发出的文件系统控制请求

**🔍 第一性原理视角：MOUNT_VOLUME 是"卷生命的起点"**

`sfilter` 源码中对 `IRP_MN_MOUNT_VOLUME` 的处理是教科书级的：

```
// 在 SfFsControlMountVolume 中：
// 1. 从 IRP 的 VPB 参数中获取 RealDevice
storageStackDeviceObject = irpSp->Parameters.MountVolume.Vpb->RealDevice;

// 2. 提前创建 FiDO（因为完成例程中不能失败）
IoCreateDevice(..., &newDeviceObject);

// 3. 保存 RealDevice 指针到设备扩展
newDevExt->StorageStackDeviceObject = storageStackDeviceObject;

// 4. 设置完成例程并下发 IRP
IoSetCompletionRoutine(Irp, SfFsControlCompletion, ...);
IoCallDriver(devExt->AttachedToDeviceObject, Irp);

// 5. 等待 IRP 完成（Windows XP+ 可以同步等待）
KeWaitForSingleObject(&waitEvent, ...);

// 6. 在完成函数 SfFsControlMountVolumeComplete 中绑定 VDO
```

> 💡 **洞见**：sfilter 源码中有一段重要注释——"We need to save the RealDevice object pointed to by the vpb parameter because this vpb may be changed by the underlying file system. Both FAT and CDFS may change the VPB address if the volume being mounted is one they recognize from a previous mount." 这说明 VPB 指针在卷挂载完成后可能失效，必须提前保存 RealDevice 指针，挂载完成后再重新获取正确的 VPB 和 VDO。

## 7.5 文件系统卷设备的绑定

### 7.5.1 从 IRP 中获得 VPB 指针

**📌 书中的世界**

在 `IRP_MN_MOUNT_VOLUME` 的处理中，通过 `irpSp->Parameters.MountVolume.Vpb` 获取 VPB（Volume Parameter Block）指针。VPB 是连接"存储设备对象"和"文件系统卷设备对象"的数据结构。

**🔍 第一性原理视角：VPB 是"存储栈与文件系统栈的桥梁"**

```
存储设备对象（由 volmgr.sys 创建，代表物理分区）
    ↑ VPB 连接
文件系统卷设备对象（由 ntfs.sys 创建，代表 C: 盘）
```

VPB 中的关键字段：

- `RealDevice`：指向存储设备对象（即卷管理器创建的设备）
- `DeviceObject`：指向文件系统创建的卷设备对象

**关键陷阱**：VPB 指针在卷挂载过程中可能被底层文件系统替换（FAT/CDFS 都有这种行为）。所以 sfilter 的做法是：在下发 IRP 前保存 `VPB->RealDevice`，在挂载完成后的完成例程中，通过这个 RealDevice 指针重新获取最新的 VPB，然后从 `VPB->DeviceObject` 得到需要绑定的 VDO。

### 7.5.2 设置完成函数并等待 IRP 完成

**📌 书中的世界**

书中详细描述了如何正确设置完成例程并处理卷挂载 IRP：

```
// Windows XP 及以后：可以同步等待
KEVENT waitEvent;
KeInitializeEvent(&waitEvent, NotificationEvent, FALSE);
IoCopyCurrentIrpStackLocationToNext(Irp);
IoSetCompletionRoutine(Irp, SfFsControlCompletion, &waitEvent, TRUE, TRUE, TRUE);
status = IoCallDriver(devExt->AttachedToDeviceObject, Irp);
if (STATUS_PENDING == status) {
    KeWaitForSingleObject(&waitEvent, Executive, KernelMode, FALSE, NULL);
}
// IRP 完成后，调用 SfFsControlMountVolumeComplete 绑定 VDO
```

**🔍 第一性原理视角：为什么必须等待 IRP 完成才能绑定 VDO？**

因为 VDO **尚未被创建**——VDO 是文件系统在处理 MOUNT_VOLUME IRP 的过程中创建的。过滤驱动必须等文件系统完成挂载、VDO 真正存在后，才能附着到它上面。

sfilter 源码中的注释解释了 Windows 2000 与 XP 的区别：

- Windows 2000：不能同步等待回到调度例程，必须在完成例程中把后续工作排队到工作线程
- Windows XP 及以后：可以在 `PASSIVE_LEVEL` 同步等待，然后在调度例程中直接做后期挂载处理

> ⚠️ **工业级细节**：这种"下发 IRP + 等待完成 + 后期处理"的模式是 WDM 驱动开发中的常见范式，特别是在处理 PnP/挂载等异步事件时。核心原则是：**不要在 IRP 未完成前假设下层设备对象已经就绪**。

### 7.5.3 卷挂载 IRP 完成后的工作

**📌 书中的世界**

在完成例程 `SfFsControlMountVolumeComplete` 中：

1. 通过之前保存的 `StorageStackDeviceObject` 重新获取 VPB
2. 从 VPB 中获取文件系统的 VDO（`VPB->DeviceObject`）
3. 将之前创建的 FiDO 附着到 VDO 上
4. 初始化 FiDO 的设备扩展，记录绑定的 VDO 和下层设备对象

**🔍 第一性原理视角：这是"两级绑定"的收尾**

```
第一级绑定：FiDO_CDO → 文件系统 CDO（在 SfFsNotification 中完成）
第二级绑定：FiDO_Volume → 文件系统 VDO（在 MountVolume 完成后完成）
```

只有完成第二级绑定，过滤驱动才能真正拦截到针对该卷的文件 I/O。

### 7.5.4 完成函数的相应实现

**📌 书中的世界**

书中给出了 `SfFsControlCompletion` 和 `SfFsControlMountVolumeComplete` 的具体实现。

**🏭 现代工业实践**

sfilter 源码中的实现要点：

- 在完成例程中设置事件（用于同步等待）或排队工作项（Windows 2000 兼容）
- 在 `SfFsControlMountVolumeComplete` 中调用 `IoAttachDeviceToDeviceStackSafe`（Windows 2000 SP4 及以后可用，更安全）
- 绑定后复制下层 VDO 的标志（DeviceType、IoType 等）
- 清理 `DO_DEVICE_INITIALIZING` 标志

### 7.5.5 绑定卷的实现

**📌 书中的世界**

书中总结了绑定卷的完整流程，并强调了几个关键点：

1. **不要二次绑定**：对于已经附加过过滤设备的卷设备，不要重复附加
2. **VPB 锁**：访问 VPB 参数时要先获取 VPB 锁，访问结束后释放
3. **设备类型匹配**：FiDO 的 DeviceType 必须与下层 VDO 一致

**🔍 第一性原理视角：绑定卷的"三重保险"**

- **检查是否已绑定**：通过设备扩展中的标志位
- **保护 VPB 访问**：VPB 是共享数据结构，多核并发访问需要同步
- **设备类型一致性**：保证 I/O 管理器和下层行为一致

> 💡 **洞见**：sfilter 框架的健壮性来自于对这些边界情况的细致处理。一个生产级过滤驱动与示例代码的差距，往往就在这些"看似琐碎"的细节上。

## 7.6 读/写操作的过滤

### 7.6.1 设置一个读处理函数

**📌 书中的世界**

在 FiDO 的 `IRP_MJ_READ` 派遣函数中，过滤驱动可以：

- 直接放行（不关心）
- 拦截并修改读取的数据
- 拦截并阻止读取（返回错误）
- 异步处理（设置完成例程）

**🔍 第一性原理视角：读过滤的两种模式**

1. **pre-处理模式**：在派遣函数中直接处理，同步完成
2. **post-处理模式**：下发 IRP + 设置完成例程，在下层完成后再处理数据

对于读操作，**修改读取的数据必须在完成例程中做**——因为派遣函数被调用时，数据还没从下层返回。

### 7.6.2 设备对象的区分处理

**📌 书中的世界**

过滤驱动必须区分收到的 I/O 是针对哪个设备的：

- 如果是针对 FiDO_CDO（绑定到文件系统 CDO 的过滤设备）：处理文件系统控制请求
- 如果是针对 FiDO_Volume（绑定到 VDO 的过滤设备）：处理文件 I/O 请求

**🔍 第一性原理视角：设备扩展中的"身份标识"**

通过设备扩展中的 `TypeFlag` 字段区分 FiDO 的类型：

```
typedef struct _SFILTER_DEVICE_EXTENSION {
    ULONG TypeFlag;  // SFLT_POOL_TAG 标识这是 sfilter 的设备扩展
    PDEVICE_OBJECT AttachedToDeviceObject;  // 下层设备
    PDEVICE_OBJECT StorageStackDeviceObject;  // 存储设备对象
    // ...
} SFILTER_DEVICE_EXTENSION;
```

### 7.6.3 解析读请求中的文件信息

**📌 书中的世界**

在读请求的派遣函数中，可以通过 `Irp->Tail.Overlay.OriginalFileObject` 获取文件对象，进而获取文件名、文件 ID 等信息。

**🔍 第一性原理视角：文件对象是"文件 I/O 的上下文"**

每个打开的文件都有一个对应的 `FILE_OBJECT`。通过它，过滤驱动可以获取：

- 文件名（`FILE_OBJECT->FileName`）
- 文件对象头部（`FOBX`）
- 关联的 VDO
- 文件大小、状态等信息

**关键挑战**：`FILE_OBJECT->FileName` 在文件打开过程中可能还不完整（特别是短名/长名的转换），这就是为什么 7.8 节专门讲"路径过滤的实现"。

### 7.6.4 读请求的完成

**📌 书中的世界**

在读完成例程中：

1. 检查 `Irp->IoStatus.Status` 是否为 `STATUS_SUCCESS`
2. 如果成功，从 `Irp->AssociatedIrp.SystemBuffer`（或 MDL）中获取读取的数据
3. 可以修改数据（实现"透明解密"效果）
4. 可以记录日志（实现"审计"功能）
5. 必须处理 `Irp->PendingReturned`——若为 `TRUE`，调用 `IoMarkIrpPending`

**🔍 第一性原理视角：读完成例程是"数据拦截的黄金点"**

与磁盘过滤类似，完成例程是获取"已读取数据"的唯一正确位置。在这里你可以：

- **审计**：记录"谁读了什么文件"
- **解密**：将密文转换为明文（透明加密产品的核心）
- **脱敏**：对敏感数据做掩码处理
- **阻断**：虽然读已经完成，但可以修改返回的数据或返回错误

> ⚠️ **工业级约束**：
> 
> - 完成例程运行在 `DISPATCH_LEVEL`（对于某些 I/O），此时不能访问分页内存
> - 不能在完成例程中调用 `IoDeleteDevice`
> - 使用的所有数据结构必须位于非分页内存

**🏭 现代工业实践**

现代 EDR 的读过滤架构：

```
内核 minifilter 的 post-read 回调
    ↓ 提取文件信息 + 读取的数据
    ↓ 通过事件/共享内存传递给用户态服务
用户态服务
    ↓ 做深度分析（威胁情报、ML 检测、策略匹配）
    ↓ 必要时通知内核 minifilter 阻断后续 I/O
```

这种"内核采集 + 用户态分析"的分层架构是现代安全产品的标准范式。

## 7.7 其他操作的过滤

### 7.7.1 文件对象的生存周期

**📌 书中的世界**

文件对象的生命周期：

1. `IRP_MJ_CREATE`：创建文件对象（打开文件）
2. 文件对象被使用（读写、查询信息等）
3. `IRP_MJ_CLEANUP`：最后一个句柄关闭时触发
4. `IRP_MJ_CLOSE`：文件对象被销毁时触发

**🔍 第一性原理视角：CREATE 与 CLOSE 的"引用计数"语义**

- `IRP_MJ_CREATE`：增加文件对象的引用计数
- `IRP_MJ_CLEANUP`：当文件的最后一个句柄被关闭时发送，此时文件中止 I/O 操作，等待所有待处理的 I/O 完成
- `IRP_MJ_CLOSE`：文件对象引用计数归零时，销毁文件对象

> 💡 **洞见**：理解文件对象的生命周期，是正确实现"文件审计"、"防勒索"、"透明加密"的基础。例如防勒索产品通常在 `IRP_MJ_CREATE` 时检查进程信誉，在 `IRP_MJ_WRITE` 时检测勒索行为特征，在 `IRP_MJ_CLEANUP` 时做最终判断。

### 7.7.2 文件的打开与关闭

**📌 书中的世界**

`IRP_MJ_CREATE` 是文件过滤中**最重要的 IRP**——因为它是"文件操作的起点"，防病毒扫描、访问控制、审计都在这里做：

```
// 在 pre-create 回调中：
// 1. 获取文件名
// 2. 检查进程信誉
// 3. 查询威胁情报
// 4. 决定是否放行
//    - 放行：下发 IRP 让文件系统继续处理
//    - 拦截：直接完成 IRP 并返回错误
```

**🔍 第一性原理视角：CREATE 是"决策点"**

`IRP_MJ_CREATE` 的特殊性在于：

- 它是**第一个**针对该文件对象的 I/O 请求
- 此时还没有数据读写，拦截成本最低
- 拦截 `CREATE` 等于"拒绝打开文件"——这是防病毒最有效的拦截点

**🏭 现代工业实践**

微软文档明确指出防病毒/反恶意软件是文件系统过滤驱动的典型应用之一。现代 EDR 产品在 pre-create 回调中：

- 检查文件是否匹配已知恶意哈希
- 检查打开进程是否在黑名单中
- 对可执行文件做启发式扫描
- 对敏感目录（如系统目录）做额外保护

### 7.7.3 文件的删除

**📌 书中的世界**

文件的删除在 Windows 中是一个"两阶段"过程：

1. `IRP_MJ_SET_INFORMATION` with `FileInformationClass = FileDispositionInformation`：设置 `DeletePending = TRUE`
2. 当文件的最后一个句柄关闭时（`IRP_MJ_CLEANUP`），文件系统才真正删除文件

**🔍 第一性原理视角：删除是"标记 + 延迟执行"**

Windows 的文件删除不是立即发生的，而是：

1. 先"标记"文件为待删除
2. 等所有句柄关闭
3. 才真正从磁盘移除

> 💡 **洞见**：这种"软删除"机制给了过滤驱动一个拦截窗口——在 `IRP_MJ_SET_INFORMATION` 中检测到删除意图，可以：
> 
> - 阻止删除（防勒索的核心）
> - 备份文件（防误删）
> - 记录审计日志
> - 通知用户态服务做二次确认

**🏭 现代工业实践**

防勒索产品（如 Microsoft Defender Attack Surface Reduction、CrowdStrike、Carbon Black）都在 `IRP_MJ_SET_INFORMATION` 的 pre-operation 回调中监控 `FileDispositionInformation`，结合行为分析判断是否为勒索行为。

## 7.8 路径过滤的实现

### 7.8.1 取得文件路径的 3 种情况

**📌 书中的世界**

获取文件路径的时机有三种：

1. **文件打开成功后**：在 CREATE 的完成例程中获取
2. **其他时刻**：通过文件对象查询
3. **打开请求完成之前**：在 pre-create 回调中获取（最困难但最有价值）

**🔍 第一性原理视角：路径获取的"时序困境"**

文件路径是最关键的过滤依据，但获取路径的时机直接影响过滤的有效性：

- **太早**（pre-create）：路径可能不完整（文件尚未打开，文件名可能还在解析中）
- **太晚**（post-create 完成例程）：路径完整，但文件已经打开，拦截成本高
- **异步 I/O 时**：文件路径的获取更加复杂

### 7.8.2 打开成功后获取路径

**📌 书中的世界**

在 `IRP_MJ_CREATE` 的完成例程中，通过 `FILE_OBJECT->FileName` 获取完整路径。此时文件已成功打开，路径信息是最准确的。

**🔍 第一性原理视角：这是"准确性优先"的策略**

优点：路径 100% 准确

缺点：文件已经打开，如果此时决定拦截，需要做"事后补救"（如立即关闭文件、回滚已读取的数据）

### 7.8.3 在其他时刻获得文件路径

**📌 书中的世界**

对于已经打开的文件对象，可以通过 `IoQueryFileInformation` 或解析 `FILE_OBJECT` 结构获取路径。但这往往需要查询文件系统，可能涉及下发 IRP。

**🔍 第一性原理视角：路径查询的"代价"**

查询已打开文件的路径需要：

1. 发送 `IRP_MJ_QUERY_INFORMATION` 请求
2. 等待文件系统返回
3. 解析返回的文件名信息

这在高频率 I/O 场景下会成为性能瓶颈。

### 7.8.4 在打开请求完成之前获得路径名

**📌 书中的世界**

在 pre-create 回调中获取路径是最有价值的，因为：

- 可以在文件打开前就做出拦截决策
- 拦截成本最低
- 是防病毒扫描的理想时机

**技术挑战**：

- pre-create 时，`FILE_OBJECT->FileName` 可能只是"相对路径"或"待解析路径"
- 需要通过 `IoGetRequestorProcess` 等 API 获取进程上下文
- 可能需要查询文件系统以获取完整路径

**🔍 第一性原理视角：这是过滤驱动开发的"圣杯"**

在 pre-create 中获取准确路径，需要深入理解：

- `FILE_OBJECT` 结构的各个字段含义
- 文件打开过程中的"路径解析"机制
- 文件系统如何处理相对打开、链接、重解析点

> 💡 **洞见**：现代 minifilter 通过 `FltGetFileNameInformation` 等 API 大大简化了路径获取。但在 legacy 过滤驱动中，开发者必须手动处理这些复杂性。

### 7.8.5 把短名转换为长名

**📌 书中的世界**

Windows 文件系统支持 8.3 短文件名（如 `PROGRA~1`）和长文件名（如 `Program Files`）。过滤驱动可能需要将短名转换为长名以便统一处理。

**🔍 第一性原理视角：路径规范化是过滤的"前置处理"**

在路径过滤中，路径规范化至关重要：

- 短名 → 长名
- 相对路径 → 绝对路径
- 符号链接 → 目标路径
- 重解析点 → 最终路径

只有规范化后的路径，才能进行准确的策略匹配。

**🏭 现代工业实践**

minifilter 提供了 `FltGetFileNameInformation` 系列 API，支持多种名称格式查询（`FLT_FILE_NAME_NORMALIZED`、`FLT_FILE_NAME_OPENED` 等）。这大大简化了路径处理的复杂性。

## 7.9 把 sfilter 编译成静态库

### 7.9.1 如何方便地使用 sfilter

**📌 书中的世界**

把 sfilter 的核心逻辑编译成静态库（`.lib`），其他项目只需要：

1. 链接 sfilter.lib
2. 实现几个回调钩子（初始化、绑定、I/O 处理）
3. 编译成最终的过滤驱动

**🔍 第一性原理视角：这是"框架化思维"的早期实践**

将通用的过滤框架（设备绑定、PnP 处理、Fast I/O 转发等）抽象成库，让具体业务（文件审计、防病毒、加密）通过回调注入——这正是现代软件工程的"框架 + 插件"模式。

> 💡 **洞见**：sfilter.lib 的思想与后来的 minifilter 模型高度一致——都是"通用框架 + 业务回调"。不同的是：
> 
> - sfilter.lib：手动框架，开发者仍需处理大量底层细节
> - minifilter：由微软提供的 fltmgr.sys 作为框架，开发者只需注册回调

### 7.9.2 初始化回调、卸载回调和绑定回调

**📌 书中的世界**

sfilter.lib 暴露的关键回调：

- `DriverEntry` 中的初始化回调
- 文件系统变动回调（绑定 CDO）
- 卷挂载完成回调（绑定 VDO）
- I/O 处理回调（读/写/创建等）

**🔍 第一性原理视角：回调是"控制反转（IoC）"在内核编程中的体现**

sfilter.lib 掌握了"何时绑定、何时处理 I/O"的控制权，业务驱动通过实现回调来"注入"具体逻辑。这与现代 minifilter 的 `PFLT_FILTER_UNLOAD_CALLBACK`、`PFLT_POST_OPERATION_CALLBACK` 等回调注册机制，是同一个第一性原理。

### 7.9.3 绑定与回调

**📌 书中的世界**

书中阐述了 sfilter.lib 内部的绑定流程与回调的对应关系。

**🏭 现代工业实践**

对比 minifilter 的注册方式：

```
// minifilter 注册回调
FLT_OPERATION_REGISTRATION Callbacks[] = {
    { IRP_MJ_CREATE, 0, PreCreate, PostCreate },
    { IRP_MJ_WRITE, 0, PreWrite, PostWrite },
    { IRP_MJ_OPERATION_END }
};
FltRegisterFilter(DriverObject, &FilterRegistration, &FilterHandle);
FltStartFiltering(FilterHandle);
```

minifilter 的注册方式更加声明式——你只需要"声明"你对哪些操作感兴趣，fltmgr 会在适当时机调用你的回调。这与 sfilter.lib 的"过程式"框架形成鲜明对比。

### 7.9.4 插入请求回调

**📌 书中的世界**

sfilter.lib 允许业务驱动在 I/O 处理的各个阶段插入自定义逻辑。

**🔍 第一性原理视角：AOP（面向切面编程）的内核版本**

"在 I/O 处理的特定切点插入自定义逻辑"——这正是 AOP 的核心思想。sfilter.lib 通过回调机制实现了内核级的 AOP。

### 7.9.5 如何利用 sfilter.lib

**📌 书中的世界**

书中给出了使用 sfilter.lib 的具体步骤和示例代码。

**🏭 现代工业实践**

虽然 sfilter.lib 的思想有价值，但**现代项目不应直接使用 legacy sfilter 模型**。微软明确建议：

> "Filter developers should develop file system minifilter drivers with Filter Manager support instead of legacy file system filter drivers."

minifilter 的优势（微软官方文档归纳）：

1. **简化开发**：fltmgr 处理了设备栈绑定、IRP 转发、Fast I/O 等复杂细节
2. **确定性排序**：通过 altitude 机制保证多个过滤器之间的确定顺序
3. **动态加载/卸载**：minifilter 可以在系统运行时动态加载和卸载，无需重启
4. **更好的互操作性**：fltmgr 作为"框架内的框架"，协调不同供应商的过滤器

> ⚠️ **关键认知**：altitude 机制解决了 legacy 过滤驱动最大的痛点——多个过滤器的加载顺序不确定。minifilter 通过数字 altitude 值（如防病毒在 320000-329999 范围，加密在 140000-149999 范围）确保：
> 
> - 加密过滤在防病毒过滤之下（防病毒看到的是明文）
> - 活动监视在防病毒之上（看到所有操作）
> - 顺序是确定性的，与机器无关

## 🎯 本章核心洞见总结

读完第7章，我希望你带走的不只是"怎么写一个 legacy 文件系统过滤驱动"，而是这四个**第一性原理**：

**1. 文件系统过滤的本质是"在 I/O 路径上插入决策点"**

无论是 legacy sfilter 还是现代 minifilter，核心思想都是：**在文件 I/O 到达文件系统之前/之后，插入一个"观察-决策-干预"的点**。这个决策点可以：

- 审计（记录操作）
- 观察（收集信息）
- 修改（改变数据/行为）
- 阻止（拒绝操作）

**2. IRP 与 Fast I/O 是"两条平行的 I/O 路径"**

这是本章最重要的技术洞察。微软文档明确指出：IRP 是默认机制，Fast I/O 是缓存命中时的快捷通道。过滤驱动必须**同时处理这两条路径**，否则要么丢失功能，要么丧失性能。

> 💡 **现代映射**：minifilter 通过 fltmgr 自动处理了 Fast I/O 与 IRP 的路由，开发者只需注册一个回调，fltmgr 会确保该回调在两种路径下都被调用（除非显式设置 `SKIP_CACHED_IO`）。

**3. 动态绑定是文件系统过滤的"工程精髓"**

文件系统是动态加载的，卷是动态挂载的。过滤驱动必须：

- 通过 `IoRegisterFsRegistrationChange` 订阅文件系统变动
- 在文件系统时绑定 CDO
- 在卷挂载时（MOUNT_VOLUME IRP 完成后）绑定 VDO
- 跳过文件系统识别器

这套"动态绑定链"是 sfilter 框架最核心的贡献。

**4. legacy → minifilter 是必然的演进**

微软官方文档明确将 legacy 文件系统过滤驱动标记为"不应用于新开发"。这不是因为 legacy 模型"错了"，而是因为：

- legacy 模型的工程复杂度过高（手动处理 IRP、Fast I/O、设备栈绑定）
- 多过滤器排序不确定，供应商之间容易冲突
- 不能动态加载/卸载，调试困难
- 一个 bug 就可能导致 BSOD

minifilter 通过 fltmgr.sys 这个"框架内的框架"，解决了所有这些痛点。**但 legacy sfilter 仍然是理解文件系统过滤第一性原理的最佳教材**——因为只有理解了"为什么难"，才能理解 minifilter"为什么好"。

### 从书中环境到现代工业环境的迁移清单

|书中技术 (Legacy sfilter)|现代工业做法 (Minifilter)|优势|
|---|---|---|
|`IoRegisterFsRegistrationChange`|fltmgr 自动管理|开发者无需关心文件系统动态加载|
|手动绑定 CDO/VDO|`FltRegisterFilter` + altitude|确定性排序，自动绑定|
|手动处理 IRP 分发|pre/post 回调函数|只注册关心的操作|
|手动实现 Fast I/O 分发表|fltmgr 自动路由|无需关心 IRP/Fast I/O 差异|
|设备扩展管理上下文|`FltAllocateContext` 系列|自动生命周期管理|
|手动路径解析|`FltGetFileNameInformation`|规范化路径一键获取|
|无法动态卸载|`FltUnregisterFilter`|运行时动态加载/卸载|
|sfilter.lib 静态库框架|fltmgr.sys 系统框架|微软维护，持续更新|
|无确定性排序|altitude 机制|加密在 AV 之下，确定性强|

> 📌 **最后一句话**：第7章的价值不仅在于教你写 sfilter，更在于让你**完整经历一次"从复杂到简单"的工程演进认知**——legacy 模型让你看见文件系统过滤的所有底层细节和陷阱，minifilter 模型让你看见微软如何把这些细节抽象成优雅的框架。现代 EDR、防病毒、防勒索、DLP、透明加密产品的内核核心几乎都是 minifilter，但**只有理解了 sfilter 的底层机制，你才能在 minifilter 出现诡异问题时快速定位根因**。这就是第一性原理式学习的真谛：不只学"怎么做"，更要学"为什么这么做"以及"为什么不这么做"。
