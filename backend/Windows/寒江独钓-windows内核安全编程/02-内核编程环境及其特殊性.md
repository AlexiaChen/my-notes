## 2.1 内核编程的环境

### 2.1.1 隔离的应用程序

**📌 书中的世界**

书中对比了用户态与内核态：每个应用程序运行在自己的私有地址空间里，一个程序崩溃通常不会拖垮整个系统。这种隔离是 Windows 体系结构的基石——用户态进程权限受限，不能直接访问硬件或内核内存，越权操作会触发保护性异常。

**🔍 第一性原理视角：隔离的本质是"信任边界"**

用户态应用程序之所以"安全"，不是因为它们本身无害，而是因为操作系统在它们之间建了一堵墙：

- 每个进程有独立的虚拟地址空间（隔离）
- 只能通过系统调用进入内核（受控入口）
- 内核代为完成特权操作（权限代理）

这堵墙的存在，让"写用户态程序"和"写内核程序"变成了两种完全不同的工种。用户态程序员享受着"有人兜底"的奢侈；内核程序员则要直面一个残酷事实——**墙是你自己建的，也是你来维护的**。

> 💡 **洞见**：用户态的"隔离"是一种"责任转移"——把稳定性责任从开发者转移给了操作系统。而内核编程则是责任的回归：你不再有 OS 替你擦屁股，每一次空指针、每一次错误的锁使用、每一次 IRQL 违规，代价都是 BSOD。

### 2.1.2 共享的内核空间

**📌 书中的世界**

所有内核驱动共享同一个内核地址空间——也就是 `ntoskrnl.exe` 所在的虚拟地址空间，运行在 Ring 0，与内核本身享有同等权限。一个驱动有 bug 或有恶意行为，就能不受限制地访问物理内存和任意内核结构。

**🔍 第一性原理视角：共享 = 无隔离 = 极度危险**

这是全书最重要的一句话：**内核模块之间没有任何内存隔离**。这意味着：

1. 一个驱动的野指针可能改写另一个驱动的数据结构
2. 一个驱动可以扫描并篡改任意内核内存（包括 NT 内核自身）
3. 恶意驱动一旦加载，等同于获得了内核级控制权

这也是为什么"内核态 Rootkit"如此可怕，以及为什么现代 Windows 用 DSE（Driver Signature Enforcement）强制要求驱动签名——**因为内核空间的共享性使得"谁能进内核"成了一个安全问题，而不仅仅是技术问题**。

> ⚠️ **工业现实**：第三方内核驱动一直是攻击者的首选落脚点。因为一旦加载，它就拥有对物理内存和所有内核结构的无限制访问权。这也是为什么微软要通过 DSE 来拦截未签名驱动加载的原因。

**🏭 现代工业实践**

- Windows 10 1607+ 强制 DSE，要求 EV 证书签名 + WHLK 测试
- 微软的 HVCI（Hypervisor-protected Code Integrity）进一步限制内核态可执行代码的完整性
- **VBS（Virtualization-Based Security）+ HVCI**​ 的组合，把内核代码完整性验证放到 hypervisor 层，即使内核被攻破也难以加载未授权代码
- 但所有这些防御都有同一个前提：**开发者必须先理解"共享内核空间"带来的责任**

### 2.1.3 无处不在的内核模块

**📌 书中的世界**

书中指出：从磁盘、网卡、GPU、USB 到文件系统、防病毒引擎，Windows 系统所做的超越原始计算的一切，最终都要通过驱动完成。一个驱动本质上是一个加载到 `ntoskrnl.exe` 地址空间的内核模块，运行在 Ring 0。

**🔍 第一性原理视角：内核模块是 Windows 的"器官"**

Windows 不是一个"内核 + 应用"的二层结构，而是"硬件 → 内核驱动 → 内核 → 用户态服务 → 应用程序"的多层结构。每一个内核模块都是系统的一个"器官"：

- 总线驱动枚举设备
- 功能驱动操作设备
- 过滤驱动观察/修改数据流
- 文件系统驱动管理文件 I/O
- 网络驱动处理协议栈

**安全研究的真正战场就在这里**——防病毒要挂过滤驱动、加密软件要挂文件系统过滤、防火墙要挂网络过滤、EDR 要 hook 内核对象。理解了"内核模块无处不在"，你才能理解为什么《寒江独钓》后面要讲串口过滤、键盘过滤、文件系统过滤、网络过滤——**过滤（filter）是内核安全编程最核心的范式**。

## 2.2 数据类型

### 2.2.1 基本数据类型

**📌 书中的世界**

内核编程使用一组固定的 typedef：

- `ULONG` / `UCHAR` / `UINT` 替代 `unsigned long` / `unsigned char` / `unsigned int`
- `PVOID` 替代 `void*`
- `NTSTATUS` 作为返回状态类型

**🔍 第一性原理视角：为什么不直接用 C 原生类型？**

这不是"换汤不换药"的语法糖，而是**ABI 稳定性的需要**：

- 内核 API 是跨 Windows 版本长期稳定的二进制契约
- C 原生类型的宽度（如 `long` 在 x86 是 4 字节、在某些平台可能是 8 字节）因编译器和平台而异
- `ULONG` 等 WDK 类型明确规定了宽度（4 字节无符号），保证内核 API 在不同编译环境下行为一致

> 💡 **洞见**：内核 API 的稳定性要求比用户态高一个数量级——用户态 DLL 可以版本化，内核导出表一旦变更就可能让无数第三方驱动崩溃。所以内核编程的数据类型不是"风格"，是"契约"。

### 2.2.2 返回状态

**📌 书中的世界**

NTSTATUS 是内核 API 的统一返回类型，0 表示成功（具体是 `STATUS_SUCCESS`），负值表示错误，正值表示警告或特殊状态。

**🔍 第一性原理视角：为什么内核 API 不用 errno + 返回值？**

用户态 C 库习惯用 `errno` 全局变量 + 返回值表示错误。这种方式在内核态有两个致命问题：

1. **多线程并发**：`errno` 是线程局部存储，但在内核态"任意上下文"下，线程局部性并不总是成立
2. **信息密度不足**：内核操作可能失败的维度太多（权限不足、资源耗尽、设备离线、超时、参数无效……），一个 `int` 返回值承载不了

`NTSTATUS` 是一个 32 位值，其高位编码了**严重性（Severity）、客户（Customer）、设施（Facility）和状态码（Code）**——这是一种自描述的错误编码体系。例如 `STATUS_ACCESS_DENIED` (0xC0000022) 的高位 `0xC` 表示错误严重性，`0x22` 是具体代码。

**🏭 现代工业实践**

- 微软的 SAL 注解（如 `_Must_inspect_result_`）让静态分析工具能验证 NTSTATUS 是否被正确处理
- OSR 最佳实践明确建议：**用 `/W4 /WX` 编译，把警告当错误**，并启用 Code Analysis 和 Static Driver Verifier
- 忽略 NTSTATUS 检查是内核漏洞的头号来源之一

### 2.2.3 字符串

**📌 书中的世界**

内核使用 `UNICODE_STRING` 和 `ANSI_STRING` 结构，而不是 C 风格的 `char*` 以 `\0` 结尾的字符串。

**🔍 第一性原理视角：为什么内核不敢用 `char*`？**

C 字符串的三个假设在内核态都不成立：

1. **假设字符串在可分页内存中**​ —— 但 DISPATCH_LEVEL 以上不能访问分页内存
2. **假设字符串以 `\0` 结尾**​ —— 但内核经常处理不可信输入（来自用户态的 IOCTL 缓冲），`\0` 可能缺失导致越界读取
3. **假设字符串长度有限**​ —— 但内核经常处理任意长度的缓冲区

`UNICODE_STRING` 的设计哲学是**显式长度 + 显式最大长度**：

```
typedef struct _UNICODE_STRING {
    USHORT Length;        // 当前字符串字节数
    USHORT MaximumLength; // 缓冲区最大容量（字节）
    PWCH   Buffer;       // 指向 Unicode 字符数组的指针
} UNICODE_STRING;
```

这种"带有边界信息的字符串"是内核安全编程的基础设施——它让字符串操作从"相信调用者"变成"验证边界"。

> ⚠️ **微软 Surface 团队最佳实践**明确指出：处理来自 IOCTL 的缓冲区时，最常见的错误之一就是**不验证缓冲区长度**。这是内核漏洞的经典来源。

## 2.3 重要的数据结构

### 2.3.1 驱动对象

**📌 书中的世界**

每个内核模块必定有一个驱动对象（`DRIVER_OBJECT`），由 I/O 管理器在驱动加载时创建并传给 `DriverEntry`。驱动对象的最重要成员是 `MajorFunction` 数组——按 IRP 主功能码（如 `IRP_MJ_CREATE`、`IRP_MJ_READ`、`IRP_MJ_WRITE`、`IRP_MJ_DEVICE_CONTROL`）索引的派发函数表。

**🔍 第一性原理视角：驱动对象是"驱动的身份证 + 能力声明"**

`DriverEntry` 的本质工作是**填写这张派发表**——它声明了"我这个驱动能处理哪些种类的请求"。没填的槽位由 I/O 管理器填充默认值（通常是直接完成 IRP）。

这背后是一个深刻的架构思想：**I/O 管理器是"路由器"，驱动对象是"路由表"**。用户态的 `CreateFile` / `ReadFile` / `WriteFile` / `DeviceIoControl` 最终都变成 IRP，由 I/O 管理器根据 MajorFunction 派发到对应驱动。

**🏭 现代工业实践**

现代 KMDF 驱动虽然不再直接填 `MajorFunction` 数组，而是由框架注册自己的派发例程，再回调驱动的 `EvtXxx` 事件处理函数，但**底层机制没变**——依然是 I/O 管理器 → 框架 → 驱动的回调链。理解 `DRIVER_OBJECT` 仍然是理解 KMDF 的基础。

### 2.3.2 设备对象

**📌 书中的世界**

一个驱动对象可以创建多个设备对象（`DEVICE_OBJECT`），简称为 DO。设备对象才是 I/O 请求的真正目标。设备对象可以被命名为 `\Device\Xxx`，并通过符号链接（如 `\DosDevices\Xxx` 或 `\GLOBAL??\Xxx`）暴露给用户态。

**🔍 第一性原理视角：设备对象是"服务的入口"**

书中把设备对象比作"窗口"、把 IRP 比作"消息"——这个比喻很准确。但我想补充一层：

**设备对象与驱动对象的关系，是"服务"与"服务提供者"的关系**：

- 驱动对象是服务提供者（who）
- 设备对象是服务入口（what）
- IRP 是通过入口提交的服务请求（how）

一个驱动可以提供多种服务（多个设备对象），每种服务对应不同的 IRP 处理路径。设备对象通过 `IoAttachDeviceToDeviceStack` 形成**设备栈**——这是过滤驱动的技术基础。

> 💡 **洞见**：理解设备栈是理解"过滤"的关键。当 I/O 管理器向设备栈顶端的设备对象发送 IRP 时，请求沿着设备栈向下传；每个驱动处理它关心的部分，然后把 IRP 传给下一个设备对象（`IoCallDriver`），或者完成它（`IoCompleteRequest`）。防病毒、加密、防火墙——所有安全产品都是通过"在设备栈上插入自己的设备对象"来实现的。

### 2.3.3 请求

**📌 书中的世界**

内核中大多数请求都以 IRP（I/O Request Packet）的形式传递。IRP 结构里包含一个栈——因为**一个 IRP 往往要传递 N 个设备才能完成**。

**🔍 第一性原理视角：IRP 是"数据包 + 调用栈"的合体**

IRP 最反直觉的设计是：**它是一个自包含的数据结构，同时携带了"请求本身的信息"和"请求处理过程的上下文"**。

IRP 包含两个关键部分：

1. **固定头部**：状态、缓冲区、发起请求的线程等所有参与驱动共享的信息
2. **IO_STACK_LOCATION 数组**：每个设备栈位置一个，存放该层驱动专属的参数（当前 MajorFunction、MinorFunction、请求参数如读取长度和偏移量）

这种设计让 IRP 可以在设备栈中"旅行"——`IoCallDriver` 把它向下传一层，`IoCompleteRequest` 把它向上回一层。**每一次向下传递，当前 IO_STACK_LOCATION 指针就前进一格；每一次向上完成，就后退一格**。

**🏭 现代工业实践**

微软官方文档明确指出：IRP 是自包含的（self-contained），它持有驱动处理 I/O 请求所需的全部信息。

现代 KMDF 虽然包装了 IRP（变成 `WDFREQUEST`），但**IRP 仍然是内核 I/O 的通用货币**。安全研究人员在分析恶意驱动、Rootkit、内核漏洞时，依然要直接面对 IRP 结构——这也是为什么《寒江独钓》坚持讲 WDM 层的 IRP，而不是上来就用 KMDF 抽象。

## 2.4 函数调用

### 2.4.1 查阅帮助

**📌 书中的世界**

书中指导读者查阅 WDK 帮助文档，了解每个内核函数的用法、参数、返回值、调用约束（尤其是 IRQL 约束）。

**🔍 第一性原理视角：内核函数的"帮助"和用户态函数的"帮助"本质不同**

用户态 API 文档告诉你"怎么调用"；内核 API 文档还必须告诉你"在什么 IRQL 下能调用"、"会导致页错误吗"、"会阻塞吗"、"是幂等的吗"。

这是因为内核函数的正确性不仅取决于参数，还取决于**调用上下文**。同一个 `ExAllocatePoolWithTag`，在 PASSIVE_LEVEL 可以分配分页内存，在 DISPATCH_LEVEL 只能分配非分页内存——**调用上下文错了，函数就可能引发 BSOD**。

> 💡 **洞见**：读内核 API 文档的正确姿势——先看"Requirements"小节里的 IRQL 要求，再看参数，再看返回值。IRQL 要求是内核函数的"宪法"，违反它必崩。

### 2.4.2 帮助中有的几类函数

**📌 书中的世界**

WDK 文档化的函数主要包括：

- **I/O 管理函数**：`IoCreateDevice`、`IoCallDriver`、`IoCompleteRequest` 等
- **内存管理函数**：`ExAllocatePoolWithTag`、`MmMapLockedPagesSpecifyCache` 等
- **对象管理函数**：`ObReferenceObjectByHandle`、`ObDereferenceObject` 等
- **字符串函数**：`RtlInitUnicodeString`、`RtlCopyUnicodeString` 等
- **同步函数**：`KeInitializeSpinLock`、`KeAcquireSpinLock` 等

**🔍 第一性原理视角：文档化的函数 = 微软承诺稳定性的接口**

WDK 文档化的函数有两层含义：

1. **语义稳定**：微软保证这些函数的行为在 Windows 版本间保持一致
2. **支持保障**：使用这些函数的驱动可以通过 WHQL 认证

但这只是冰山一角。Windows 内核导出了大量**未在 WDK 中文档化**的函数——它们被称为 Native API（`Nt*` / `Zw*` 系列），约有 250 个，其中只有约 25 个在 DDK/WDK 中有描述。

### 2.4.3 帮助中没有的函数

**📌 书中的世界**

安全研究和高级内核编程中，经常需要调用 WDK 帮助里查不到的函数，例如：

- `ZwQuerySystemInformation` —— 查询系统信息
- `ZwOpenProcess` —— 打开进程句柄
- `NtCreateThread` / `ZwCreateThread` —— 创建线程（未文档化）
- 各种 `Nt*` / `Zw*` Native API

**🔍 第一性原理视角：未文档化函数 = 内核的"暗门"**

Windows Native API 大部分是未文档化的，微软的策略是鼓励开发者使用稳定的文档化 API（如 Win32 和 WinRT），从而使开发者的代码免受系统更新时内部 Native API 潜在 ABI 变更的影响。

安全研究人员为什么要碰这些"暗门"？

- **能力**：某些能力（如查询系统进程列表、创建内核线程）只有 Native API 提供
- **性能**：绕过 Win32 API 层，直达内核
- **早期启动**：在系统启动早期，只有 Ntdll.dll 可用

**🏭 现代工业实践：未文档化函数的"灰色生态"**

由于微软不提供完整的 Native API 文档，安全研究社区形成了成熟的逆向工程工具链：

- **Geoff Chappell 的网站**：详细记录了未文档化函数的结构、参数和版本变化
- **winsiderss/phnt**（原 Process Hacker 项目）：在 GitHub 上维护了 300+ 个 Native API 原型
- **ReactOS**：开源的 Windows 兼容操作系统，提供了许多 Native API 的参考实现
- **Vergilius Project**：从微软 PDB 符号文件中提取的内核结构数据库
- **NtDoc**：社区驱动的 Native API 文档集合
- **Undocumented NT 网站**：编译了内核、Native API 和驱动函数的底层细节

> ⚠️ **重要警示**：使用未文档化函数意味着**微软可以在任何时候不经通知地更改其签名或行为**。在工业级驱动开发中，微软的《驱动程序安全清单》第一条就是"确认内核驱动程序是必需的"——能用文档化 API 完成的，绝不用未文档化函数。未文档化函数应仅限于安全研究、Rootkit 分析、EDR 等"必须深入内核"的场景。

## 2.5 Windows 的驱动开发模型

**📌 书中的世界**

书中兼顾 WDM 与 WDF 两种模型。《寒江独钓》选择以 WDM 为主线，同时提及 WDF。

**🔍 第一性原理视角：为什么这本书选 WDM？**

这是一个看似矛盾的选择——微软早在 2000 年代中期就推出了 WDF（Windows Driver Frameworks），其中包含 KMDF（内核态）和 UMDF（用户态），用来解决 WDM 的复杂性问题。但《寒江独钓》作为一本"内核安全编程"书籍，选择 WDM 是有深刻理由的：

**WDM vs WDF 的本质差异**：

|维度|WDM|WDF (KMDF)|
|---|---|---|
|编程模型|直接处理 IRP|框架对象 + 事件回调|
|PnP/电源管理|驱动手动处理状态机|框架自动管理|
|I/O 取消|驱动协调 CancelRoutine|框架提供取消机制|
|资源生命周期|大量手动管理|父子对象 + 清理回调|
|IRQL 约束|驱动自行维护|回调有明确的 IRQL 契约|
|学习曲线|陡峭，贴近内核|平缓，但有抽象壁垒|

**WDM 让开发者直面 IRP、DEVICE_OBJECT、驱动栈、IRQL 等内核原语**——这些恰恰是安全编程要理解和操控的对象。如果你用 KMDF 写驱动，框架替你隐藏了 IRP 的细节，你也失去了"过滤 IRP"、"Hook 派发函数"、"遍历设备栈"的能力——而这些正是 Rootkit 检测、防病毒、EDR 的核心技术。

**🏭 现代工业实践：模型选择的工程现实**

微软官方立场很明确：**新驱动开发优先用 WDF**。具体选型原则：

1. **能在用户态完成就优先 UMDF v2**——错误局限于宿主进程，可靠性极高
2. **需要内核态硬件访问或高性能数据路径 → KMDF**——PCIe、存储、网络等
3. **只有维护遗留代码或框架无法覆盖的特殊需求 → 才直接用 WDM**

微软 Surface 团队的最佳实践文档列出了驱动开发的常见错误，其中许多（如 IOCTL 缓冲区长度验证、同步锁误用、WDFREQUEST 生命周期管理）都是工业级驱动的真实痛点。

> 💡 **洞见**：《寒江独钓》选 WDM 不是为了"过时"，而是为了"透视"。学安全编程的人必须先看见内核的骨头，然后才能在骨头上长肉（用 WDF 写生产驱动）。**WDM 是"理解"，WDF 是"工程"——两者缺一不可**。

## 2.6 WDK 编程中的特殊点

### 2.6.1 内核编程的主要调用源

**📌 书中的世界**

内核代码并非从 `main()` 开始线性执行，它的"调用源"多种多样：

- 系统启动时由 SCM 调用 `DriverEntry`
- I/O 管理器调用 MajorFunction 派发例程
- PnP 管理器调用 `AddDevice` 及相关例程
- 电源管理器调用电源相关例程
- 系统线程调用驱动创建的线程函数
- DPC（Deferred Procedure Call）例程
- I/O 定时器回调
- 工作线程回调

**🔍 第一性原理视角：内核代码是"事件驱动"的，且运行在"任意上下文"**

这是内核编程最难适应的一点：**你的代码可能在任何进程上下文中执行**。当用户态线程发起 `ReadFile` 时，你的 `IRP_MJ_READ` 派发例程运行在该用户线程的上下文中；但当 DPC 触发时，你的 `DpcForIsr` 运行在"任意线程上下文"（Arbitrary Thread Context）中——此时当前进程可能不是你期望的那个。

这意味着：

- **不能假设"当前进程"是谁**——必须用 `PsGetCurrentProcess()` 显式获取
- **不能依赖用户态线程的地址空间**——DISPATCH_LEVEL 下的代码不能访问用户态内存
- **不能长时间阻塞**——DPC 中调用 `KeWaitForSingleObject` 等待非零间隔会导致致命错误

> 💡 **洞见**：用户态程序员习惯"我在 main 里，我知道我是谁"；内核程序员必须时刻问"我现在在哪个上下文？"。这是思维方式的切换。

### 2.6.2 函数的多线程安全性

**📌 书中的世界**

内核代码几乎无时无刻不运行在多线程之下。一个驱动的全局数据可能被多个线程同时访问，必须用锁保护。

**🔍 第一性原理视角：内核态的并发比用户态凶险 10 倍**

用户态多线程的"并发"受限于进程内的线程调度；内核态的并发则是**真正的并行**——多核处理器上，多个 CPU 核心可能同时执行你的驱动代码，访问同一份全局数据。

WDK 提供的同步原语：

|原语|适用 IRQL|特点|
|---|---|---|
|**Mutex（内核互斥体）**​|PASSIVE_LEVEL|可阻塞，不能用于 DISPATCH_LEVEL|
|**Fast Mutex**​|≤ APC_LEVEL|比普通 Mutex 快，但仍有约束|
|**Spin Lock**​|≤ DISPATCH_LEVEL|忙等，持有期间代码不可分页|
|**Interlocked 操作**​|任意 IRQL|原子操作，适合简单计数器|

**🏭 现代工业实践**

微软 Surface 团队总结了同步的常见错误：

- **持有锁时间过长**——只在真正需要保护的少数操作上持有锁，而不是整个函数
- **持锁调用外部代码**——这是死锁的首要原因
- **该用 Spin Lock 的地方用了 Mutex**——或在反之
- **用 interlocked 原语手搓锁方案**——而不是使用系统提供的合适原语

> ⚠️ **关键约束**：在 DISPATCH_LEVEL 或更高 IRQL 持有 Spin Lock 的代码必须遵守严格规则——**不能引起页错误**（因为操作系统无法等待分页 I/O 完成），**不能调用可能阻塞的函数**，**代码必须驻留在非分页内存**。违反任何一条都会导致 `IRQL_NOT_LESS_OR_EQUAL` 蓝屏。

### 2.6.3 代码的中断级

**📌 书中的世界**

IRQL（Interrupt Request Level）是内核编程最重要的概念之一。常见级别：

- **PASSIVE_LEVEL (0)**​ —— 最低级，可阻塞，可访问分页内存
- **APC_LEVEL (1)**​ —— APC 中断被屏蔽
- **DISPATCH_LEVEL (2)**​ —— 调度器禁用，DPC 和定时器在这个级别运行
- **DIRQL**​ —— 设备中断级别，高于 DISPATCH_LEVEL
- **HIGH_LEVEL**​ —— 最高级，用于 bug check 回调

**🔍 第一性原理视角：IRQL 是内核的"优先级天花板"**

IRQL 不是"中断优先级"那么简单，它是**内核代码执行时的"权限等级 + 环境约束"的合体**：

1. **屏蔽规则**：IRQL 决定了哪些中断被屏蔽。DISPATCH_LEVEL 屏蔽了 DISPATCH_LEVEL 及以下的所有中断
2. **调用约束**：每个内核函数都有"最高可调用 IRQL"。例如 `KeWaitForSingleObject` 只能在 PASSIVE_LEVEL 调用
3. **内存约束**：IRQL > APC_LEVEL 时不能访问分页内存，否则页错误就是致命错误
4. **对称性**：`KeRaiseIrql` 和 `KeLowerIrql` 必须成对出现，且在同一函数中

**🏭 现代工业实践**

微软的 IRQL 规则在今天依然严格适用：

- `DriverEntry`、`AddDevice`、`Unload`、大多数派发例程、驱动创建的线程 → **PASSIVE_LEVEL**
- `StartIo`、`DpcForIsr`、`Cancel`、`CustomTimerDpc` → **DISPATCH_LEVEL**
- `InterruptService` 例程 → **DIRQL**

> 💡 **洞见**：IRQL 违规是内核漏洞和 BSOD 的头号来源。OSR 建议用 **SAL 注解**标注每个函数的 IRQL 约束，让 Static Driver Verifier 在编译期捕获违规。这是现代工业界的标准做法。

### 2.6.4 WDK 中出现的特殊代码

**📌 书中的世界**

WDK 代码中经常出现一些"看起来奇怪"的写法：

- `NTSTATUS` 状态检查的宏（`NT_SUCCESS`）
- `try/except` 结构化异常处理（`ProbeForRead` / `ProbeForWrite`）
- `#pragma alloc_text` 控制代码分页属性
- `PAGED_CODE()` 宏断言当前 IRQL 允许分页
- SAL 注解（`_In_`, `_Out_`, `_IRQL_requires_max_`）

**🔍 第一性原理视角：这些"特殊代码"都是 IRQL 规则的具象化**

1. **`try/except` + `ProbeForRead/Write`**：用户态传来的指针是不可信的。在 DISPATCH_LEVEL 以下访问用户态内存前，必须用 `ProbeForXxx` 探测，并用 `try/except` 捕获可能的异常——否则恶意用户态程序传入无效指针就让内核崩
2. **`#pragma alloc_text` + `PAGED_CODE()`**：把代码显式放入分页段，节省非分页内存。但 `PAGED_CODE()` 宏会在运行时断言当前 IRQL ≤ APC_LEVEL——如果在 DISPATCH_LEVEL 调用了标记为分页的代码，立即触发断言
3. **SAL 注解**：这是现代 WDK 最重要的补充。通过 `_IRQL_requires_max_(PASSIVE_LEVEL)` 等注解，让静态分析工具能在编译期验证 IRQL 合规性

**🏭 现代工业实践**

- **代码分析（Code Analysis）**：OSR 建议每次构建都启用，至少用 "Microsoft Native Recommended Rules"
- **Static Driver Verifier (SDV)**：形式化验证工具，能证明驱动是否满足并发和 IRQL 约束
- **Driver Verifier**：运行时验证器，开启后能让绝大多数驱动 bug 在测试阶段暴露
- **HVCI 兼容代码**：现代驱动必须编写与 HVCI 兼容的代码，这意味着不能动态生成可执行代码

> 💡 **工业级驱动开发的标准动作**：
> 
> 1. 用最新 WDK + Visual Studio 2022/2026
> 2. `/W4 /WX` 编译，警告即错误
> 3. 全程启用 Code Analysis + SDV
> 4. 测试机常开 Driver Verifier
> 5. 通过 HLK（Hardware Lab Kit）测试
> 6. EV 代码签名 + WHQL 认证

## 🎯 本章核心洞见总结

读完第2章，我希望你带走的不只是"内核编程有哪些特殊点"，而是这三个**第一性原理**：

**1. 内核代码运行在"无隔离的共享空间"中**

没有 OS 替你兜底，每一次错误都是系统级灾难。这决定了内核编程的所有特殊性——数据类型要显式、字符串要带长度、状态要自描述、内存要分区。

**2. 内核代码是"事件驱动 + 任意上下文"的**

你的函数可能被 I/O 管理器调用、被 DPC 调用、被系统线程调用、被工作项调用。你不能假设"我在哪里、我是谁、我能等多久"。IRQL 是这个混沌世界的秩序——它规定了"在这个级别你能做什么、不能做什么"。

**3. 现代工业界用"框架 + 验证器"来消化内核编程的复杂性**

WDF 把 IRP、PnP、电源管理、取消逻辑等易错部分收编到框架里；Code Analysis、SDV、Driver Verifier 在编译期和运行期双重把关。**但《寒江独钓》讲 WDM 的意义在于：你必须先理解框架之下是什么，才能真正驾驭框架之上**。

### 从书中环境到现代工业环境的迁移清单

|书中概念 (XP/Vista 时代)|现代工业做法 (Win10/11)|
|---|---|
|WDM 直接处理 IRP|优先 KMDF/UMDF v2，特殊需求才用 WDM|
|手动管理 PnP/电源状态机|框架自动管理，驱动实现事件回调|
|手动 IRP 取消逻辑|WDFQUEUE 提供取消机制|
|用 `NTSTATUS` 返回值|SAL 注解 + Code Analysis 验证|
|`char*` 字符串|`UNICODE_STRING` + 长度验证|
|未文档化 Native API 自由调用|phnt/ReactOS/Vergilius Project 辅助 + 生产代码慎用|
|IRQL 靠人工遵守|SAL `_IRQL_requires_` 注解 + SDV 静态验证|
|无自动化验证|Driver Verifier + HLK + Static Driver Verifier|
|无签名要求|DSE + EV 签名 + WHQL 认证 + HVCI 兼容|

> 📌 **最后一句话**：第2章讲的是"内核编程的物理学"——它告诉你在这个环境里，什么是可能的、什么是不可能的、什么是致命的。把这一章吃透，你才能理解后面章节里所有"过滤"、"Hook"、"回调"技术的设计动机：它们本质上都是在"共享内核空间 + 任意上下文 + IRQL 约束"这三座大山下，寻找安全的切入点。
