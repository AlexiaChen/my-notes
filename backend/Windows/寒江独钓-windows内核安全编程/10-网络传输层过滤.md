
第10章"网络传输层过滤"是全书**从本地内核迈向网络内核**的关键转折——前9章都在讲文件系统、键盘、磁盘这些"本地对象"，从第10章起进入网络栈。书中选择 **TDI（Transport Driver Interface）**​ 作为传输层过滤的切入点，带你写一个 TDI 过滤驱动，实现网络防火墙的雏形。

但这一章有一个**必须 upfront 指出的工业现实**：**TDI 从 Windows 8 起已被微软正式弃用**，微软官方文档明确说："As of Windows 8, the Transport Driver Interface (TDI) feature and Layered Service Providers (LSPs) feature are deprecated"。TDI 函数页也写着："The TDI feature is deprecated and will be removed in future versions of Microsoft Windows. Depending on how you use TDI, use either the Winsock Kernel (WSK) or Windows Filtering Platform (WFP)"。

## 10.1 TDI 概要

### 10.1.1 为何选择 TDI

**📌 书中的世界**

书中选择 TDI 作为传输层过滤的入手点，理由有三：

1. TDI 是 Windows 网络栈中"传输层"的标准接口——afd.sys（Ancillary Function Driver）作为 TDI 客户端，将所有 socket 操作翻译成 TDI 请求发给 tcpip.sys
2. TDI 过滤驱动可以**拦截所有 TCP/UDP 连接**，实现网络防火墙
3. TDI 模型相对 NDIS（网卡驱动接口）更"高层"、更接近应用语义（IP+端口），开发难度低于 NDIS

**🔍 第一性原理视角：TDI 是"socket 语义与传输层协议之间的契约"**

应用程序调用 `socket()` / `connect()` / `send()`，这些 Winsock API 在内核中由 afd.sys 接管，afd.sys 将"创建 socket"翻译为"创建 TDI 地址对象"，将"connect"翻译为"TDI_CONNECT IRP"，将"send"翻译为"TDI_SEND IRP"——**TDI 就是 afd.sys 与 tcpip.sys 之间对话的"协议"**。

过滤驱动只要挂在 `\Device\Tcp` 和 `\Device\Udp` 上，就能看到 afd.sys 发来的每一个 TDI 请求——这是网络防火墙、EDR 网络遥测、主机入侵检测系统（HIDS）的经典入手点。

> 💡 **洞见**：选择 TDI 过滤，本质是选择"在 socket 语义层做过滤"——你能看到的是"进程 X 连接了 IP:Port"，而不是 NDIS 层的"以太网帧"。这种语义级可见性正是防火墙最需要的能力。

### 10.1.2 从 socket 到 Windows 内核

**📌 书中的世界**

书中梳理了从应用层 socket 调用到内核 TDI 请求的完整链路：

```
用户态: socket() / connect() / send()
    ↓
ws2_32.dll (Winsock API)
    ↓
afd.sys (Ancillary Function Driver)
    ↓ 创建 TDI 地址对象 + 连接对象
    ↓ 翻译为 TDI IRP
tcpip.sys (TCP/IP 协议栈)
    ↓
NDIS (网络接口层)
    ↓
网卡
```

**🔍 第一性原理视角：这张调用链图是理解 Windows 网络栈的"地图"**

关键在于理解 afd.sys 的角色——它是"Winsock 语义"与"TDI 语义"的翻译官。每一个用户态 socket 操作，afd.sys 都会：

1. 打开 `\Device\Tcp` 或 `\Device\Udp` 设备对象
2. 创建一个**地址对象**（Address Object，对应本地 IP:Port 绑定）
3. 创建一个**连接对象**（Connection Object，对应一个具体连接）
4. 通过 `TDI_ASSOCIATE_ADDRESS` 把连接对象与地址对象关联
5. 下发 `TDI_CONNECT` 发起连接

**🏭 现代工业实践：Vista 之后的架构演变**

Windows Vista 重构了网络栈——afd.sys **不再通过 TDI 与 tcpip.sys 通信**，而是使用一个新的未公开接口 **TLNPI（Transport Layer Network Provider Interface）**。

为了向后兼容旧的 TDI 客户端和 TDI 过滤驱动，微软引入了 **TDX.sys**——它创建原本由 tcpip.sys 创建的 `\Device\Tcp`、`\Device\Udp` 等设备对象，对外模拟 TDI 接口，对内把 TDI 请求翻译成 TLNPI 调用。

> ⚠️ **工业现实**：这就是为什么你在 Win10/Win11 上写 TDI 过滤驱动时会发现——设备对象仍然存在（由 TDX.sys 创建），但微软已经明确这条路是"deprecated"且"will be removed in future versions"。**新的网络过滤驱动开发应当使用 WFP**。

### 10.1.3 TDI 过滤的代码例子

**📌 书中的世界**

书中给出了 TDI 过滤的最小骨架：通过 `IoGetDeviceObjectPointer` 获取 `\Device\Tcp` 和 `\Device\Udp` 的设备对象指针，然后用 `IoAttachDeviceToDeviceStack` 把自己的过滤设备挂接到 TDI 设备栈上。

**🔍 第一性原理视角：与文件系统过滤的同构性**

如果你读过第7章，会发现 TDI 过滤的"挂接"手法与文件系统过滤驱动如出一辙：

- 文件系统过滤：绑定 CDO → 捕获卷挂载 → 绑定 VDO
- TDI 过滤：绑定 `\Device\Tcp` / `\Device\Udp` → 捕获地址对象创建 → 跟踪连接

**它们都是"在设备栈上插一层"的经典 WDM 模式**。这种模式在 Minifilter 和 WFP 出现后逐渐被框架化，但理解它对于理解 Windows 内核的"过滤哲学"至关重要。

## 10.2 TDI 的过滤框架

### 10.2.1 绑定 TDI 的设备

**📌 书中的世界**

TDI 过滤驱动在 `DriverEntry` 中：

1. 创建无名过滤设备对象
2. 绑定到 `\Device\Tcp`、`\Device\Udp`（以及 IPv6 的 `\Device\Tcp6`、`\Device\Udp6`）
3. 设置分发函数

**关键代码模式**：

```
IoGetDeviceObjectPointer(&tcpDeviceName, FILE_READ_DATA | FILE_WRITE_DATA,
    &tcpFileObject, &tcpDeviceObject);
IoAttachDeviceToDeviceStack(myFilterDevice, tcpDeviceObject);
```

**🔍 第一性原理视角：绑定 = "在设备栈顶部插入自己"**

绑定后，所有发往 `\Device\Tcp` 的 IRP 都会**先经过你的过滤设备**。这是 WDM 过滤的通用范式——与第7章绑定文件系统 CDO 完全同构。

> ⚠️ **Win10+ 注意事项**：在 Win10 及以后，TCP/UDP 的设备对象由 TDX.sys 创建，设备对象名仍是 `\Device\Tcp` 和 `\Device\Udp`，但内部实现已变。社区开发者证实："the drive object of the TCP and UDP device objects on Win10 becomes TDX"——你的绑定代码形式上仍然有效，但底层走的是 TDX 兼容层。

### 10.2.2 唯一的分发函数

**📌 书中的世界**

TDI 过滤驱动的分发函数与常规 WDM 驱动不同——TDI 的主要请求都是通过 **`IRP_MJ_INTERNAL_DEVICE_CONTROL`**​ 主功能号下发的，次功能号（MinorFunction）区分具体操作：

- `TDI_ASSOCIATE_ADDRESS`
- `TDI_CONNECT`
- `TDI_DISASSOCIATE_ADDRESS`
- `TDI_SEND`
- `TDI_RECEIVE`
- `TDI_SET_EVENT_HANDLER`
- 等等

所以 TDI 过滤驱动的分发函数看起来像这样：

```
NTSTATUS TdiHookDeviceDispatch(PDEVICE_OBJECT DeviceObject, PIRP Irp) {
    PIO_STACK_LOCATION irpSp = IoGetCurrentIrpStackLocation(Irp);
    if (irpSp->MajorFunction == IRP_MJ_INTERNAL_DEVICE_CONTROL) {
        switch (irpSp->MinorFunction) {
            case TDI_CONNECT:
                return tdi_connect(Irp, irpSp, &completion);
            case TDI_ASSOCIATE_ADDRESS:
                return tdi_associate_address(Irp, irpSp, &completion);
            // ... 其他次功能号
        }
    }
    // 其他 IRP 直接下发
    return g_oldDriverObject.MajorFunction[irpSp->MajorFunction](DeviceObject, Irp);
}
```

**🔍 第一性原理视角：为什么是 INTERNAL_DEVICE_CONTROL？**

`IRP_MJ_INTERNAL_DEVICE_CONTROL` 是内核组件之间的"内部对话"——afd.sys 调用 `IoCallDriver` 向 tcpip.sys 发送 TDI 请求时，主功能号就是 `IRP_MJ_INTERNAL_DEVICE_CONTROL`，次功能号指定具体操作。这与用户态 `DeviceIoControl` 产生的 `IRP_MJ_DEVICE_CONTROL` 不同——后者是"外部"控制，前者是"内部"通信。

> 💡 **洞见**：理解 `IRP_MJ_INTERNAL_DEVICE_CONTROL` 是理解 TDI 过滤的钥匙。TDI 过滤驱动本质是"窃听"afd.sys 与 tcpip.sys 之间的内部对话。

### 10.2.3 过滤框架的实现

**📌 书中的世界**

书中给出一个完整的 TDI 过滤框架：

1. `DriverEntry` 中绑定 `\Device\Tcp` / `\Device\Udp`
2. 设置分发函数（主要处理 `IRP_MJ_INTERNAL_DEVICE_CONTROL` 和 `IRP_MJ_CREATE`）
3. 在 TDI 请求的分发函数中，根据次功能号分派到具体的过滤处理函数
4. 使用完成例程（Completion Routine）在 IRP 完成后做后处理

**🏭 现代工业实践：tdifw 框架**

书中第10.5节介绍的 `tdifw.lib` 正是一个开源的 TDI 过滤框架（源自 SourceForge 的 tdifw 项目）。它把 TDI 过滤的通用逻辑封装成库，业务驱动只需实现四个回调：

- `tdifw_driver_entry`：替代 DriverEntry
- `tdifw_driver_unload`：驱动卸载
- `tdifw_user_device_dispatch`：用户态通信设备的 IRP 分发
- `tdifw_filter`：网络事件过滤决策（返回 `FILTER_ALLOW` 或 `FILTER_DENY`）

tdifw 的核心设计思想是："**过滤只有两种选择：允许或者禁止**"——这是防火墙最本质的语义。

### 10.2.4 主要过滤的请求类型

**📌 书中的世界**

TDI 过滤驱动主要关心的请求类型：

|次功能号|含义|过滤价值|
|---|---|---|
|`TDI_ASSOCIATE_ADDRESS`|连接对象关联地址对象|捕获"连接 ↔ 本地地址"的绑定关系|
|`TDI_CONNECT`|发起连接|**防火墙核心拦截点**​|
|`TDI_SEND` / `TDI_RECEIVE`|发送/接收数据|深度包检测（DPI）|
|`TDI_SET_EVENT_HANDLER`|设置事件回调|拦截接收事件、连接事件|
|`TDI_DISASSOCIATE_ADDRESS`|解除关联|清理跟踪状态|
|`TDI_SEND_DATAGRAM` / `TDI_RECEIVE_DATAGRAM`|UDP 发送/接收|UDP 防火墙|

**🔍 第一性原理视角：TDI 过滤的"黄金三点"**

OSR 的资深网络驱动专家 Thomas Divine 早在 2000 年就指出："filtering TDI is fairly messy"——TDI 过滤的混乱根源在于：**地址对象、连接对象、事件处理器三者必须自己跟踪关联**。

具体来说，过滤驱动必须：

1. **在地址对象创建时**（IRP_MJ_CREATE）：建立跟踪结构
2. **在 TDI_ASSOCIATE_ADDRESS 时**：记录"连接对象 ↔ 地址对象"的关联
3. **在 TDI_SET_EVENT_HANDLER 时**：保存原始的 EventHandler 和 EventContext，替换为自己的代理，从而截获 TDI_EVENT_CONNECT、TDI_EVENT_RECEIVE 等事件回调

> 💡 **洞见**：TDI 过滤的复杂度不在于"怎么拦截 IRP"，而在于"怎么把零散的 TDI 请求拼装成有意义的连接上下文"。这是 TDI 模型最反人性的地方——也是 WFP 后来通过"ALE 层（Application Layer Enforcement）"解决的痛点。

## 10.3 生成请求：获取地址

### 10.3.1 过滤生成请求

**📌 书中的世界**

"生成请求"指的是**主动发起连接**的场景（如客户端 connect）。过滤驱动在 `TDI_CONNECT` 的次功能号中拦截，可以：

- 解析目标 IP 和端口
- 获取发起进程的 PID
- 根据防火墙规则决定放行/拦截

**🔍 第一性原理视角：TDI_CONNECT 是"出站连接的决策点"**

`TDI_CONNECT` 是防火墙拦截出站连接的最佳位置——此时连接尚未建立，拦截成本最低，效果最好。

解析目标地址的方法：

```
TA_ADDRESS *remote_addr = 
    ((TRANSPORT_ADDRESS *)(irpSp->Parameters.Others.Argument2))->Address;
// 提取 IP 和端口
ULONG ip = ntohl(((TDI_ADDRESS_IP *)(remote_addr->Address))->in_addr);
USHORT port = ntohs(((TDI_ADDRESS_IP *)(remote_addr->Address))->sin_port);
```

这是社区 TDI 过滤代码示例中的典型写法——通过 `irpSp->Parameters.Others.Argument2` 获取 `TDI_CONNECT` 请求中的远程地址结构。

### 10.3.2 准备解析 IP 地址与端口

**📌 书中的世界**

书中详细介绍了 `TDI_ADDRESS_IP` 结构：

```
typedef struct _TDI_ADDRESS_IP {
    USHORT sin_port;       // 端口（网络字节序）
    ULONG in_addr;         // IP 地址（网络字节序）
    UCHAR sin_zero[8];     // 保留
} TDI_ADDRESS_IP;
```

**🔍 第一性原理视角：网络字节序是"协议级契约"**

`sin_port` 和 `in_addr` 都是网络字节序（big-endian），在 x86/x64（little-endian）平台上必须通过 `ntohs()` / `ntohl()` 转换为本机字节序才能正确使用。这是网络编程的第一性原理——**协议规定了字节序，CPU 有自己的字节序，两者之间的转换是网络栈的基础操作**。

### 10.3.3 获取生成的 IP 地址和端口

**📌 书中的世界**

在 `TDI_CONNECT` 的 pre 回调中，通过 `irpSp->Parameters.Others.Argument2` 获取 `TDI_CONNECT` 请求的参数，进而提取远程 IP 和端口。

**🏭 现代工业实践**

tdifw 框架的 `tdi_connect` 处理函数就是这样做的：

```
int tdi_connect(PIRP irp, PIO_STACK_LOCATION irps, struct completion *completion) {
    TA_ADDRESS *remote_addr = 
        ((TRANSPORT_ADDRESS *)(irps->Parameters.Others.Argument2))->Address;
    ULONG ip = ntohl(((TDI_ADDRESS_IP *)(remote_addr->Address))->in_addr);
    USHORT port = ntohs(((TDI_ADDRESS_IP *)(remote_addr->Address))->sin_port);
    // 记录：进程 PID + 远程 IP:Port
    DbgPrint("pid:%d tdi_connect: %d.%d.%d.%d:%u\n", 
        PsGetCurrentProcessId(), ...);
    return FILTER_ALLOW;  // 或 FILTER_DENY
}
```

这段代码正是社区 TDI 过滤驱动的标准写法——它揭示了防火墙的核心数据：**"哪个进程（PID）连接了哪个远程地址（IP:Port）"**。

### 10.3.4 连接终端的生成与相关信息的保存

**📌 书中的世界**

过滤驱动必须维护一张"连接跟踪表"，记录：

- 地址对象（Address Object）
- 连接对象（Connection Object）
- 本地 IP:Port
- 远程 IP:Port
- 进程 PID
- 连接状态

**🔍 第一性原理视角：连接跟踪是"有状态防火墙"的基础**

无状态防火墙只看单个包（如"禁止访问 192.168.1.1:443"），有状态防火墙跟踪整个连接生命周期。TDI 过滤驱动天然处于"连接语义层"，可以轻松实现有状态过滤：

- 在 `TDI_ASSOCIATE_ADDRESS` 时建立跟踪条目
- 在 `TDI_CONNECT` 时填充远程地址
- 在 `TDI_DISASSOCIATE_ADDRESS` 或文件对象关闭时清理条目

> 💡 **洞见**：现代 WFP 的 ALE 层（Application Layer Enforcement）正是把"连接跟踪"框架化了——WFP 自动维护连接状态，callout 驱动只需在 ALE 层做决策。这是 WFP 相比 TDI 过滤的核心优势之一。

## 10.4 控制请求

### 10.4.1 TDI_ASSOCIATE_ADDRESS 的过滤

**📌 书中的世界**

`TDI_ASSOCIATE_ADDRESS` 是连接对象与地址对象关联的请求。过滤驱动通过它获取：

- 连接对象（irpSp->FileObject）
- 地址对象的句柄（irpSp->Parameters.Others.Argument2）

```
int tdi_associate_address(PIRP irp, PIO_STACK_LOCATION irps, ...) {
    HANDLE addr_handle = 
        ((TDI_REQUEST_KERNEL_ASSOCIATE *)(&irps->Parameters))->AddressHandle;
    // 通过句柄获取地址对象
    ObReferenceObjectByHandle(addr_handle, GENERIC_READ, NULL, 
        KernelMode, &addr_obj, NULL);
    // 记录：conn_obj <-> addr_obj 的关联
    // ...
    ObDereferenceObject(addr_obj);
    return FILTER_ALLOW;
}
```

这段代码模式来自社区 TDI 过滤实现——它揭示了 TDI 过滤的关键技术：**通过句柄解析出内核对象，建立对象间的关联跟踪**。

**🔍 第一性原理视角：TDI_ASSOCIATE_ADDRESS 是"连接上下文的锚点"**

CSDN 博客对 TDI 驱动结构的总结非常精准："`TDI_ASSOCIATE_ADDRESS` 可以通过它截取出自己和对端的套接字信息，一般就是 IP 地址+端口号，可以在此 IRP 功能响应中进行套接字信息的记录"。

但 OSR 专家指出一个陷阱：**"`TDI_ASSOCIATE_ADDRESS` 不总是被调用"**——在某些 TDI 客户端的使用模式下，关联可能通过其他方式建立。这就是为什么 TDI 过滤被称为"fairly messy"：你必须处理各种边界情况。

### 10.4.2 TDI_CONNECT 的过滤

**📌 书中的世界**

`TDI_CONNECT` 是出站连接的核心拦截点。过滤驱动在 pre 回调中：

1. 提取远程 IP:Port
2. 获取进程 PID
3. 查询防火墙规则
4. 返回 `FILTER_ALLOW` 或 `FILTER_DENY`

**🏭 现代工业实践**

这是网络防火墙、EDR 网络遥测的最核心数据点。现代安全产品（如 CrowdStrike、Microsoft Defender for Endpoint）在网络层的连接监控，本质上做的就是这件事——**"进程 X 试图连接 IP:Port，是否放行？"**

但在现代 Windows 上，这件事通过 **WFP 的 ALE Connect 层 callout**​ 实现，而不是 TDI_CONNECT 拦截。WFP 的 ALE 层直接提供"进程 ID + 用户 ID + IP + 端口"的完整上下文，开发者无需自己解析 TDI 结构。

### 10.4.3 其他的次功能号

**📌 书中的世界**

书中逐一介绍其他 TDI 次功能号的过滤：

- `TDI_SEND` / `TDI_RECEIVE`：数据收发过滤（深度包检测）
- `TDI_SEND_DATAGRAM` / `TDI_RECEIVE_DATAGRAM`：UDP 数据报过滤
- `TDI_DISASSOCIATE_ADDRESS`：清理连接跟踪
- `TDI_SET_INFORMATION` / `TDI_QUERY_INFORMATION`：连接信息查询

**🔍 第一性原理视角：TDI_SEND 拦截的"数据修改"难题**

如果你想在 `TDI_SEND` 中修改发送数据，会遇到一个棘手问题：数据缓冲区可能已经被下层锁定，或者 IRP 已经完成。OSR 专家 David Cattley 指出：TDI 过滤驱动如果想拦截 `TDI_SEND` 并修改数据，必须在 pre 回调中完成 IRP 并自行构造新的发送——这是非常复杂的操作。

这也解释了为什么**深度包检测（DPI）在现代网络安全产品中更多使用 WFP 的 callout 驱动**——WFP 提供了 `FWPS_LAYER_STREAM_V4` 等流式层，专门用于流的修改和注入。

### 10.4.4 设置事件的过滤

**📌 书中的世界**

`TDI_SET_EVENT_HANDLER` 是 TDI 中用于注册事件回调的请求。afd.sys 通过它告诉 tcpip.sys："当有重要事件（如收到数据、有新连接）时，调用我的回调函数。"

过滤驱动必须拦截这个请求，**保存原始的 EventHandler 和 EventContext，替换为自己的代理函数**——这样当事件发生时，先经过你的代理，你再决定是否转发给原始回调。

**🔍 第一性原理视角：事件回调劫持是 TDI 过滤的"黑魔法"**

OSR 专家 Thomas Divine 明确指出这是 TDI 过滤的标准做法：

> "Filter SetEvent calls on each address object. In this filter we save the original caller's EventHandler and EventContext and replace both with our own proxies."

具体步骤：

1. 在 `TDI_SET_EVENT_HANDLER` 的 pre 回调中，提取 `EventHandler` 和 `EventContext`
2. 保存到地址对象的跟踪结构中
3. 替换为过滤驱动自己的 `MyEventHandler`
4. 当 tcpip.sys 调用 `MyEventHandler` 时，过滤驱动可以：
    - 记录事件信息
    - 修改事件参数
    - 决定是否转发给原始 `EventHandler`

**🏭 现代工业实践**

现代 WFP 通过 **callout 驱动**​ 机制取代了这种"事件回调劫持"——开发者只需注册一个 callout 函数到指定的 WFP 层（如 `FWPS_LAYER_INBOUND_TRANSPORT_V4`），WFP 会在数据包到达该层时自动调用 callout。这是框架化的巨大优势：**开发者不再需要手动劫持事件回调**。

### 10.4.5 TDI_EVENT_CONNECT 类型的设置事件的过滤

**📌 书中的世界**

`TDI_EVENT_CONNECT` 是**服务器端**被动接受连接时触发的事件。当客户端 connect 上来时，tcpip.sys 会调用 afd.sys 注册的 `TDI_EVENT_CONNECT` 回调。

过滤驱动通过劫持这个事件回调，可以：

- 获取客户端的 IP:Port
- 决定是否接受连接
- 记录连接审计日志

**🔍 第一性原理视角：入站连接的决策点**

与 `TDI_CONNECT`（出站）对应，`TDI_EVENT_CONNECT` 是入站连接的拦截点。博客园的文章详细解释了 TDI 事件模型："`TDI_EVENT_CONNECT` 是作为服务器端的 TCP 相应的事件，当有客户端连上来，此事件回调函数会被 tcpip.sys 调用"。

> 💡 **洞见**：完整的 TDI 防火墙必须同时处理：
> 
> - **出站**：`TDI_CONNECT`（客户端主动连接）
> - **入站**：`TDI_EVENT_CONNECT`（服务器端被动接受）
> 
> 这两个拦截点缺一不可。这也是为什么 tdifw 框架把 `tdi_connect` 和 `tdi_event_connect` 作为两个独立的过滤回调。

### 10.4.6 直接获取发送函数的过滤

**📌 书中的世界**

TDI 提供了一个特殊机制：通过 `IOCTL_TDI_QUERY_DIRECT_SEND_HANDLER`，afd.sys 可以查询到 tcpip.sys 的"直接发送函数"指针，绕过 IRP 直接调用发送函数。

**🔍 第一性原理视角：这是 TDI 性能优化的"后门"**

常规的 `TDI_SEND` 通过 IRP 下发，涉及 IRP 分配、设备栈遍历、完成例程等开销。对于高性能场景（如大量小包发送），afd.sys 可以通过 `IOCTL_TDI_QUERY_DIRECT_SEND_HANDLER` 获取 tcpip.sys 的直接发送函数指针，**绕过 IRP 直接调用**。

但这对过滤驱动是个噩梦——**如果 afd.sys 使用直接发送函数，过滤驱动就看不到 TDI_SEND IRP 了**！

**书中给出的解决方案**：在 `IOCTL_TDI_QUERY_DIRECT_SEND_HANDLER` 的完成例程中，替换返回的直接发送函数指针为过滤驱动自己的代理函数。这样每次 afd.sys 调用"直接发送"时，实际调用的是过滤驱动的代理。

> ⚠ **工业级陷阱**：这是 TDI 过滤中最黑暗的角落之一。社区开发者在实现时经常遗漏这一步，导致"某些发送看不到"。这也从侧面说明了为什么 TDI 过滤"fairly messy"——OSR 专家的原话。

### 10.4.7 清理请求的过滤

**📌 书中的世界**

`IRP_MJ_CLEANUP` 和 `IRP_MJ_CLOSE` 是文件和设备的清理请求。在 TDI 过滤中：

- 地址对象或连接对象被关闭时，过滤驱动需要清理对应的跟踪结构
- 防止内存泄漏和悬空指针

**🔍 第一性原理视角：资源清理是内核驱动的生命线**

CSDN 的 TDI 驱动分析明确指出："`TDI_DISASSOCIATE_ADDRESS` 它的 IRP 包是在 closesocket 函数时发生的，所以如果我们在 `TDI_ASSOCIATE_ADDRESS` 中记录了信息，需要在此 IRP 的功能响应中取消之前的记录"。

> 💡 **洞见**：连接跟踪表的生命周期管理，是 TDI 防火墙稳定性的关键。任何一个泄漏的条目都可能导致：
> 
> - 内存耗尽（内核池耗尽 → BSOD）
> - 悬空指针引用（BSOD）
> - 防火墙规则错误匹配

现代 WFP 通过 ALE 层自动管理连接生命周期，开发者无需手动清理——这又是框架化的优势。

## 10.5 本书例子 tdifw.lib 的应用

### 10.5.1 tdifw 库的回调接口

**📌 书中的世界**

tdifw.lib 是一个开源的 TDI 过滤框架（源自 SourceForge 的 tdifw 项目）。它将 TDI 过滤的复杂逻辑封装为库，业务驱动只需实现四个回调：

```
// 1. 驱动入口（替代 DriverEntry）
extern NTSTATUS tdifw_driver_entry(
    IN PDRIVER_OBJECT theDriverObject,
    IN PUNICODE_STRING theRegistryPath);

// 2. 驱动卸载
extern VOID tdifw_driver_unload(
    IN PDRIVER_OBJECT DriverObject);

// 3. 用户态通信设备的 IRP 分发
extern NTSTATUS tdifw_user_device_dispatch(
    IN PDEVICE_OBJECT DeviceObject,
    IN PIRP irp);

// 4. 网络事件过滤决策（核心）
extern int tdifw_filter(struct flt_request *request);
```

`tdifw_filter` 是整个框架的核心——它在每个网络事件发生时被调用，开发者返回 `FILTER_ALLOW`（允许）或 `FILTER_DENY`（拒绝）。

**🔍 第一性原理视角：tdifw 是"框架化思维"在网络过滤领域的体现**

tdifw.lib 的设计哲学与第7章的 sfilter.lib 完全一致：**把通用的过滤框架（设备绑定、IRP 分发、TDI 请求解析、连接跟踪）封装成库，把业务决策（防火墙规则）通过回调注入**。

`flt_request` 结构包含了过滤决策所需的所有信息：

- 事件类型（connect / event_connect / send / recv 等）
- 进程 PID
- 本地 IP:Port
- 远程 IP:Port
- 协议类型

开发者在 `tdifw_filter` 中检查这些信息，返回允许或拒绝。

### 10.5.2 tdifw 库的使用例子

**📌 书中的世界**

书中给出了一个最小化的 tdifw 使用示例 `tdifw_smpl.c`：

- 包含 `tdi_fw_lib.h`
- 实现 `tdifw_driver_entry`、`tdifw_driver_unload`、`tdifw_user_device_dispatch`、`tdifw_filter` 四个回调
- 在 `tdifw_filter` 中简单打印进程 ID、本地/远程 IP:Port
- 不注册自定义设备（不与用户态通信）
- 编译链接 tdifw.lib，得到一个 TDI 防火墙雏形

运行后用 DbgView 可以看到：哪个进程打开了哪个端口、在哪个端口上建立了连接等信息。

**🏭 现代工业实践**

tdifw 的架构思想在现代网络安全产品中仍有体现：

```
内核 TDI 过滤驱动（采集层）
    ↓ 通过 tdifw_filter 回调做决策
    ↓ 返回 FILTER_ALLOW / FILTER_DENY
用户态服务（策略层）
    ↓ 管理防火墙规则
    ↓ 通过通信端口下发规则到内核
```

但这种架构在现代 Windows 上已经被 **WFP callout 驱动 + 用户态 WFP API**​ 取代。

**从 tdifw 到 WFP 的迁移映射**：

|tdifw (TDI)|WFP 等价物|优势|
|---|---|---|
|`tdifw_filter` 回调|ALE Connect/Accept callout|WFP 自动提供进程上下文|
|手动解析 `TDI_ADDRESS_IP`|`FWPS_INCOMING_VALUES` 直接给出 IP:Port|无需解析二进制结构|
|劫持 `TDI_SET_EVENT_HANDLER`|注册 WFP callout 到指定层|框架化管理|
|拦截 `IOCTL_TDI_QUERY_DIRECT_SEND_HANDLER`|WFP 流式层 callout|无需对抗性能优化后门|
|手动维护连接跟踪表|ALE 层自动维护连接状态|无内存泄漏风险|
|`FILTER_ALLOW/DENY` 返回值|`FWP_ACTION_BLOCK/PERMIT`|语义一致|
|tdifw.lib 静态库|WFP 内核态 API (Fwps*)|微软官方维护|

> 💡 **洞见**：tdifw 的四个回调与 WFP callout 的注册机制，本质上是同一个第一性原理的不同表达——**"框架处理复杂的基础设施，业务通过回调注入决策"**。理解 tdifw 的回调模型，你就理解了 WFP callout 的设计哲学。

## 🎯 本章核心洞见总结

读完第10章，我希望你带走的不只是"怎么写一个 TDI 过滤驱动"，而是这四个**第一性原理**：

**1. TDI 过滤的本质是"在 socket 语义层做拦截"**

TDI 是 afd.sys 与 tcpip.sys 之间的"协议"。过滤驱动挂在 `\Device\Tcp` / `\Device\Udp` 上，窃听 afd.sys 发来的每一个 TDI 请求——从而获得"进程 X 连接 IP:Port"的语义级可见性。

这与 NDIS 过滤（以太网帧级）形成互补：NDIS 看到的是"帧"，TDI 看到的是"连接"。**防火墙需要的是连接级语义，所以 TDI 过滤是防火墙的经典入手点**。

**2. TDI 过滤的复杂度来自"对象关联的拼接"**

OSR 专家 20 年前就断言："filtering TDI is fairly messy"。混乱的根源在于：

- **地址对象**（本地 IP:Port 绑定）
- **连接对象**（具体连接）
- **事件处理器**（接收数据、接受连接）  
    这三者分散在不同的 TDI 请求中，过滤驱动必须自己**跟踪它们的关联关系**——这是 TDI 模型最反人性的地方。

**3. 从 TDI 到 WFP 是 Windows 网络过滤的必然演进**

微软的官方立场非常明确：

- Windows 8 起 TDI 和 LSP **正式弃用**
- TDI 函数"will be removed in future versions"
- Vista 起 afd.sys 不再通过 TDI 与 tcpip.sys 通信，改为 TLNPI；TDX.sys 仅为向后兼容而存在
- **新的网络过滤开发应当使用 WFP**

WFP 通过以下设计解决了 TDI 过滤的所有痛点：

- **ALE 层（Application Layer Enforcement）**：自动维护连接状态，提供进程上下文
- **Callout 驱动**：在指定层注册回调，框架自动调用
- __用户态 API（Fwpm_）+ 内核态 API（Fwps_）**：统一的开发接口
- **应用感知**：基于进程 ID、用户 ID 的过滤策略
- **有状态过滤**：跟踪连接而非单个包

**4. 工业现实：TDI 过滤在现代 Windows 上仍可运行，但不应新开发**

CSDN 的分析文章指出："TDI 网络过滤驱动之 tdifw 实现原理分析"——tdifw 至今仍是理解 TDI 过滤原理的最佳教材。社区开发者证实在 Win10 上 TDI 过滤驱动仍然可以工作，但需要注意到设备对象已由 TDX.sys 创建。

> ⚠️ **关键认知**：2026 年的现实是：
> 
> - **所有主流网络安全产品（防火墙、EDR、IPS、DLP 网络模块）都已迁移到 WFP**
> - Windows 内置的高级安全防火墙（WFAS）就是用 WFP 实现的
> - TDI 过滤驱动只在维护老代码时有意义
> - **新项目应当使用 WFP callout 驱动**

### 从书中环境到现代工业环境的迁移清单

|书中技术（TDI 过滤）|现代工业做法（WFP callout）|优势|
|---|---|---|
|绑定 `\Device\Tcp` / `\Device\Udp`|注册 callout 到 ALE / Transport 层|WFP 自动管理分层|
|`IRP_MJ_INTERNAL_DEVICE_CONTROL` 分发|`FwpsCalloutRegister` 注册回调|声明式 vs 过程式|
|解析 `TDI_ADDRESS_IP` 结构|`FWPS_INCOMING_VALUES` 直接提供|无需二进制解析|
|劫持 `TDI_SET_EVENT_HANDLER`|在指定层注册 callout|框架化事件模型|
|手动维护连接跟踪表|ALE 层自动维护|无泄漏风险|
|拦截 `TDI_CONNECT`|ALE Connect 层 callout|自动提供进程上下文|
|拦截 `TDI_EVENT_CONNECT`|ALE Accept 层 callout|入站连接决策|
|拦截 `TDI_SEND` / `TDI_RECEIVE`|Stream 层 callout|流式数据修改|
|对抗 `IOCTL_TDI_QUERY_DIRECT_SEND_HANDLER`|WFP 流式层自动处理|无需对抗性能后门|
|tdifw.lib 静态库|WFP 内核 API（Fwps*）|微软官方维护|
|`FILTER_ALLOW/DENY`|`FWP_ACTION_PERMIT/BLOCK`|语义一致|
|无确定性排序|WFP 多层过滤架构|每层有明确语义|

> 📌 **最后一句话**：第10章的价值不仅在于教你写 TDI 过滤驱动，更在于让你**完整经历一次"从 messy 到 clean"的工程演进认知**——TDI 过滤让你看见网络栈过滤的所有底层细节和陷阱（对象关联、事件劫持、直接发送后门），WFP 让你看见微软如何把这些细节抽象成优雅的 callout 框架。现代 EDR（CrowdStrike、Microsoft Defender for Endpoint、Carbon Black）的网络遥测核心几乎都是 WFP callout 驱动——但**只有理解了 TDI 过滤的底层机制，你才能在 WFP 出现诡异问题时快速定位根因**。这就是第一性原理式学习的真谛：不只学"怎么做"，更要学"为什么这么做"以及"为什么不这么做"。
