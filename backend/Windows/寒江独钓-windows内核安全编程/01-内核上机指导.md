## 1.1 下载和使用 WDK

### 1.1.1 下载安装 WDK

**📌 书中的世界**

《寒江独钓》写于 Windows XP/Vista 时代，那时候的 WDK（更早叫 DDK）是一个相对独立的 ISO 镜像，装完在开始菜单里出现"Windows Driver Kits"程序组，然后用 `build.exe` 命令行工具去编译。书中让你去 connect.microsoft.com 注册、下载、挂载 ISO、下一步下一步——这是那个年代的标准动作。

**🔍 第一性原理视角：WDK 到底是什么？**

WDK 不是"一个编译器"，它是**一整套针对内核态代码的 SDK + 构建系统 + 头文件集合 + 链接器 + 签名工具链**的总称。它的存在是因为：内核代码不能链接到 libc、不能用 main() 入口、要遵循内核 ABI、要匹配目标 Windows 版本的 NT 内核符号，普通 VC++ 工具链根本不知道这些东西。

所以"装 WDK"的本质是：**为你的构建环境注入"内核世界观"**——让编译器知道 `_IRQL_requires_` 是什么、让链接器知道该怎么生成一个 `.sys` 而不是 `.exe`、让头文件知道你针对的是哪个 NT 内核版本。

**🏭 现代工业实践对照**

今天微软官方的 WDK 早已经进化成多种分发形态：

- **WDK NuGet 包**（微软推荐）：`Microsoft.Windows.WDK`，在 Visual Studio 里通过 NuGet 包管理器引入，自动管理对 Windows SDK 的依赖
- **WDK MSI 安装包**：传统布局，配合 Visual Studio 2022/2026 使用
- **Enterprise WDK (EWDK) ISO**：自包含的命令行构建环境，内置 Visual Studio Build Tools + SDK + WDK，挂在虚拟光驱里跑 `LaunchBuildEnv.cmd` 就能构建，**无需安装完整 Visual Studio**
- **WDK with Visual Studio 2026**：截至 2026 年 5 月已 GA，版本号 10.0.28000.1839，全面支持 VS 2026，且首次支持 VS Build Tools SKU——这意味着你可以在 CI/CD agent 上做无头构建

> 💡 **洞见**：从"ISO 下一步安装"到"NuGet + CI 无头构建"，反映的是驱动开发从"个人黑客手艺"走向"企业级软件工厂"的产业变迁。今天的驱动开发工程师，理应掌握 EWDK + MSBuild 的自动化构建能力，而不只是会在 VS 里点"编译"。

如果你的目标是现代 Windows 10/11 驱动开发，正确姿势是：

1. 安装 Visual Studio 2022 或 2026（社区版即可）
2. 在 VS Installer 的"单个组件"里勾选 **Windows Driver Kit**
3. 或者通过 NuGet 引入 `Microsoft.Windows.WDK`
4. 构建号（build number）必须与 Windows SDK 的构建号匹配——这是新手最容易踩的坑

### 1.1.2 编写第一个 C 文件

**📌 书中的世界**

书中让你写一个 `first.c`，配套 `makefile` 和 `sources` 文件——这是老式 WDK `build.exe` 构建系统的产物。`sources` 文件里要声明 `TARGETNAME`、`TARGETTYPE`、`SOURCES` 等宏，相当于今天 CMakeLists.txt 或 `.vcxproj` 的远古版本。

**🔍 第一性原理视角：为什么内核 C 文件"看起来不像 C 程序"？**

当你写下第一个内核模块，你会发现：

- 没有 `main()`，取而代之的是 `DriverEntry()`
- 不能 `#include <stdio.h>`，要 `#include <ntddk.h>` 或 `<wdm.h>`
- 打印不用 `printf()`，要用 `DbgPrint()`
- 内存分配不用 `malloc()`，要用 `ExAllocatePoolWithTag()`

这不是语法糖的差异，而是**运行时环境的根本不同**：

- 用户态程序运行在 OS 提供的"保护伞"下，有 libc 替你处理系统调用、有堆管理器、有标准输入输出
- 内核态代码本身就是"伞"，它运行在 CPU Ring 0，**没有任何东西在它下面替它兜底**

所以 `first.c` 的真正意义不在于"Hello World"，而在于让你第一次体验到：**你写的每一行代码，都在直接操控这台机器的硬件抽象层**。

**🏭 现代工业实践**

现代 WDK 推荐使用 **Visual Studio 项目模板**（KMDF/UMDF/WDM 驱动模板），不再手写 `sources` 文件。`DriverEntry` 依然是入口，但配套的是 `KmdfFramework` 版本绑定、`INF` 文件描述安装元数据。工业界的实际做法是：

- 用 **KMDF（Kernel-Mode Driver Framework）**​ 而非裸 WDM 写驱动——框架替你处理了即插即用、电源管理、I/O 队列等 boilerplate
- 但《寒江独钓》讲的是**安全编程**，安全研究者往往需要贴近 WDM 甚至裸内核 API，因为你要审计/劫持/监控的恰恰是框架之下的东西。所以这本书坚持 WDM 视角是有道理的

> ⚠️ **关键认知**：框架让你"写得快"，但安全研究要求你"看得深"。这本书选择 WDM 路线，本质是让你看见内核编程的骨头，而不是穿着框架的衣服。

### 1.1.3 编译一个工程

**📌 书中的世界**

用 WDK 的 `build.exe` 命令行工具编译，输出一个 `.sys` 文件。

**🔍 第一性原理视角**

编译驱动和编译普通程序的根本差异在于**链接阶段**：

- 普通程序链接到 `kernel32.lib`、`user32.lib` 等，最终依赖 DLL 在运行时解析
- 驱动链接到 `ntoskrnl.lib`，但**所有符号在运行时必须由 NT 内核本体解析**——换句话说，你的 `.sys` 是 NT 内核的一个"插件"，它调用 `ntoskrnl.exe` 的导出函数，就像插件调用宿主的导出函数

这就是为什么驱动的编译必须**精确匹配目标内核版本**——NT 内核的导出表在不同 Windows 版本间会有细微差异，build number 不匹配就可能导致加载失败甚至 BSOD。

**🏭 现代工业实践**

- 用 **MSBuild**​ 替代 `build.exe`（老 build 工具已基本退出历史舞台）
- CI/CD 中用 **EWDK + MSBuild**​ 做无头构建
- 用 `Inf2Cat` 做签名前的 catalog 生成
- 用 `SignTool` 做 EV 证书签名（Windows 10 1607+ 强制要求 EV 签名 + HLK 测试才能上 WHQL）

## 1.2 安装与运行

### 1.2.1 下载一个安装工具

**📌 书中的世界**

书中提到用 `srvinstw.exe` 把 `.sys` 注册为 NT 服务，因为内核驱动本质上是以"服务"形式由 SCM（Service Control Manager）加载的。你还要用 `DebugView` 来捕获 `DbgPrint()` 的输出。

**🔍 第一性原理视角**

这里藏着一个关键的系统机制：**内核驱动不是"运行"的，是"加载"的**。用户态程序双击就跑；内核驱动必须由 SCM 调用 `NtLoadDriver` 把它映射到内核地址空间，并调用它的 `DriverEntry`。这意味着：

1. 驱动的生命周期由 SCM 管理，不是由用户双击管理
2. 驱动的"安装"本质是向注册表 `HKLM\SYSTEM\CurrentControlSet\Services\<DriverName>` 写入服务项
3. `srvinstw.exe` 这类工具只是帮你写注册表的 GUI 外壳

**🏭 现代工业实践**

- 现代驱动安装通过 **INF 文件 + `pnputil`/`devcon`**​ 完成，不再手动改注册表
- `sc create` 命令也能创建服务项，比 `srvinstw` 更脚本化
- **测试签名模式**：`bcdedit /set testsigning on` 允许加载测试签名的驱动——这是安全研究和驱动开发必备
- **Windows 10 1607+ 启用了 DSE（Driver Signature Enforcement）**，没有有效数字签名的驱动无法加载；研究者在测试机上必须开 testsigning 或彻底禁用 DSE（后者需要过 PatchGuard，即所谓"PG 绕过"，是另一个研究领域）

### 1.2.2 运行与查看输出信息

**📌 书中的世界**

用 `DebugView` 捕获 `DbgPrint()` 输出。

**🔍 第一性原理视角**

`DbgPrint()` 的输出去哪儿了？它去了**内核的日志缓冲区**，只有两种消费者能读到：

1. 通过 `DbgPrint` 输出的字符串被送到内核调试器（如果系统处于调试模式）
2. `DebugView` 这种工具通过 `\\.\Device\Null` 之类的机制直接读取 DbgPrint 缓冲区

这揭示了一个事实：**内核代码的"printf 调试法"和用户态完全不同**——你不能在驱动里弹 MessageBox，不能写 stdout，唯一轻量级的观测手段就是 `DbgPrint` + 外部工具捕获。

**🏭 现代工业实践**

- `DebugView` 依然可用，但现代更常见的是 **WPP Tracing（Windows Software Trace Preprocessor）**——编译期注入的 ETW 追踪，性能损耗极低，适合生产环境
- **ETW（Event Tracing for Windows）**​ 是工业级驱动的标配日志机制
- 内核调试器直连时，`DbgPrint` 输出直接流向 WinDbg 控制台

### 1.2.3 在虚拟机中运行

**📌 书中的世界**

强调在虚拟机里跑驱动——因为驱动崩了就是 BSOD，物理机重启成本高。

**🔍 第一性原理视角：这是本章最重要的安全工程思想**

内核代码 bug = BSOD = 整机停机。在物理机上迭代驱动开发是不可想象的。**虚拟机不是"为了方便"，是"为了活命"**：

- 快照（snapshot）让你在"加载可能崩的驱动之前"存个档，崩了秒回滚
- 虚拟机监控器（VMM）可以提供**独立的调试通道**——宿主机上的 WinDbg 通过管道连到客户机的 COM 口
- 哪怕客户机内核彻底挂掉，宿主机毫发无损

> 💡 **洞见**：虚拟机在这里扮演的角色，本质上是**把"内核态"降维成"可观测、可回滚的用户态实验"**。这是现代安全研究的基石方法论——Fuzzing、漏洞利用开发、Rootkit 研究，全都在虚拟机里完成。

**🏭 现代工业实践**

- VMware Workstation / Hyper-V / QEMU/KVM 均可作为调试目标
- 现代推荐做法：**KDNET（网络内核调试）**​ 比传统 COM 管道快得多，微软官方推荐
- 但为了避开 KDNET 对网卡型号的挑剔，**VMware 命名管道串口**依然是"最稳的兜底方案"
- 安全研究圈还有 **VirtualKD-Redux**​ 这种加速方案，把串口协议替换成高效的宿主-客户机通道，调试吞吐量提升 10-50 倍

## 1.3 调试内核模块

### 1.3.1 下载和安装 WinDbg

**📌 书中的世界**

书中让你下载 WinDbg（那时还是独立安装包）。

**🔍 第一性原理视角**

为什么内核调试必须用 WinDbg？不能用 Visual Studio 的调试器吗？

**不能**。因为：

- 内核调试要求**调试器与被调试系统分离**——当目标系统命中断点时，整个 OS 冻结，调试器必须运行在另一台机器（或宿主机）上
- 用户态调试器（包括 VS 自带的）运行在被调试进程所在的 OS 内，OS 冻结它就一起死
- WinDbg 是微软官方的内核调试器前端，通过 KDCOM/KDNET/KDUSB 等传输协议与目标机的内核调试引擎（Kd）通信

WinDbg 的本质是 **KD（Kernel Debugger）协议的 GUI 封装**。它干的事是：通过串行/网络/USB 通道，向目标机内核里的 `Kd` 模块发送命令，读写内存、设置断点、单步执行。

**🏭 现代工业实践**

- WinDbg 现在以 **WinDbg Preview**（Microsoft Store 应用）形式分发，UI 现代化，支持 JavaScript 脚本扩展
- 支持 **Time Travel Debugging (TTD)**——记录完整执行轨迹，可前进可回退，对排查竞态条件极有价值（但内核态 TTD 支持受限）
- 工业级驱动开发现在常用 VS 2022/2026 集成的调试器，但底层仍是 WinDbg 引擎

### 1.3.2 设置 Windows XP 调试执行 & 1.3.3 设置 Vista 调试执行

**📌 书中的世界**

修改 `boot.ini` 添加 `/debug /debugport=com2 /baudrate=115200` 启动选项（XP）；Vista 改用 `bcdedit` 命令。

**🔍 第一性原理视角**

这一段是全书最"时代烙印"的部分，但它背后的原理永不过时：

**要让内核可被调试，必须在 boot 阶段就告诉 NT 内核："启用 Kd，使用 COM2，波特率 115200"**。这是因为：

- 内核调试引擎 `Kd` 是 NT 内核的一个早期初始化组件
- 它需要在内核刚刚起来时就建立通信通道，等待宿主机调试器连接
- 这个配置**必须持久化在 boot 配置里**，因为调试通道要在任何驱动加载之前就就绪

XP 用 `boot.ini` 文本文件，Vista 之后改用 `BCD（Boot Configuration Data）` 存储，通过 `bcdedit` 命令操作——这是 Windows 启动架构的一次大升级，但语义没变：**在 boot 配置数据库里标记"本系统启用内核调试，通道参数如下"**。

**🏭 现代工业实践**

现代 Windows 10/11 的设置命令：

```
bcdedit /debug on
bcdedit /dbgsettings serial debugport:1 baudrate:115200
```

或者更推荐的 KDNET：

```
bcdedit /debug on
bcdedit /dbgsettings net hostip:<宿主机IP> port:50000 key:1.2.3.4
```

> ⚠️ 注意：启用调试前可能需要临时关闭 BitLocker 和安全启动（Secure Boot），否则 boot 配置修改会被阻断

### 1.3.4 设置 VMWare 的管道虚拟串口

**📌 书中的世界**

在 VMware 里添加一个 Serial Port，映射到宿主机的命名管道 `\\.\pipe\com_2`，然后 WinDbg 用 `com:pipe,port=\\.\pipe\com_2,baud=115200,pipe` 连接。

**🔍 第一性原理视角**

这里是全书最精妙的一笔——它揭示了**虚拟化技术如何"伪造"硬件**：

VMware 客户机里看到的 `COM2` 串口，**根本不是真实的 16550 UART 芯片**，而是 VMM 虚拟化出来的设备。它的"另一端"不是一个物理串口线，而是宿主机上的一个**命名管道**。宿主机上的 WinDbg 打开同一个命名管道，于是：

```
客户机内核 Kd ──→ 虚拟 COM2 ──→ VMware 管道 ──→ 宿主机 WinDbg
```

这就是"虚拟机内核调试"的全部秘密：**用命名管道模拟串口线**。

> 💡 **洞见**：虚拟化在这里的价值不只是"隔离"，更是"仿真"——它让宿主机上的调试器以为自己连着一根真实的 null modem 线缆，而实际上中间全是软件。理解了这一点，你就能理解为什么 Hyper-V 用 `bcdedit /hypervisorsettings`、QEMU 用 `-serial tcp::1234,server`、VMware 用命名管道——**本质都是"在 VMM 层面造一根调试通道"**。

**🏭 现代工业实践**

微软官方文档给出的标准流程：

1. 客户机：`bcdedit /debug on` + `bcdedit /dbgsettings serial debugport:n baudrate:115200`（n 是 VMware 里分配的 COM 端口号）
2. VMware 设置里添加 Serial Port → 输出到命名管道 → 管道名 `\\.\pipe\kd_Win11` → This end is server → The other end is an application → Connect at power on
3. 宿主机 WinDbg 以管理员身份运行：`windbg -k com:pipe,port=\\.\pipe\kd_Win11,resets=0,reconnect`

**关键细节**：

- WinDbg 必须以**管理员权限**运行（内核调试需要）
- VMware 场景下**不要加 `resets=0` 之外的 reset 参数**，因为 VMware 在 VM 重启时会保持管道
- KDNET 是现代首选（速度更快），但在 VMware 里 COM 管道是"least resistance"方案，因为它不挑虚拟网卡型号

### 1.3.5 设置 Windows 内核符号表

**📌 书中的世界**

配置 Symbol Path 指向微软公共符号服务器 `SRV*C:\symbols*https://msdl.microsoft.com/download/symbols`。

**🔍 第一性原理视角：为什么内核调试离不开符号？**

没有符号的调试是什么样？你看到的将是：

- 全是 `nt!0xfffff80001234567` 这种裸地址
- 栈回溯是一串无意义的函数地址
- 结构体字段只能靠偏移量手工解析

符号文件（`.pdb`）包含了：函数名、全局变量名、结构体定义、行号信息。**有了符号，WinDbg 才能把 `0xfffff80001234567` 翻译成 `nt!NtCreateFile+0x123`**。

内核符号的特殊性在于：

- NT 内核（`ntoskrnl.exe`）的符号由微软托管在公共符号服务器上
- 第三方驱动的符号由厂商自己提供
- 你自己驱动的私有符号由你在编译时生成（WDK 默认生成 PDB）

**🏭 现代工业实践**

```
.sympath SRV*C:\symbols*https://msdl.microsoft.com/download/symbols
.sympath+ <你的驱动PDB所在目录>
.reload /f
```

工业级实践中：

- 用 `!sym noisy` 打开符号加载详细日志，排查符号匹配问题
- 用 `lm` 命令查看已加载模块的详细信息
- 用 `x` 命令搜索符号（如 `x nt!*`）
- 现代 WinDbg Preview 支持自动符号配置

### 1.3.6 实战调试 first

**📌 书中的世界**

用 WinDbg 连接虚拟机，下断点在 `first` 驱动的 `DriverEntry`，单步执行，观察 `DbgPrint` 输出。

**🔍 第一性原理视角：这是你第一次"在内核里单步行走"**

当 WinDbg 断在 `first!DriverEntry` 时，你实际上在做一件非常震撼的事：

> **你让整个 Windows 操作系统在你手里暂停了，CPU 的 Ring 0 权限暂时交给了你的调试器，你可以读写任意内核内存、查看任意进程的内核数据结构、修改执行流。**

这种"上帝视角"是内核安全研究的起点。从这里出发，你可以：

- 用 `!process 0 0` 枚举所有进程
- 用 `dt nt!_EPROCESS <addr>` 解析进程结构体
- 用 `!token` 查看访问令牌
- 用 `bp` 在任意内核函数上下断点（比如 `bp nt!NtOpenProcess`）
- 用 `ba w4 <addr>` 设硬件写入断点监控某块内核内存的改写

**🏭 现代工业实践：内核调试的核心命令集**

安全研究场景下最常用的 WinDbg 命令：

|命令|用途|
|---|---|
|`!process 0 0`|列出所有进程及 EPROCESS 地址|
|`dt nt!_EPROCESS @$proc`|解析当前进程结构体|
|`!token -n 0`|查看当前线程的访问令牌|
|`!drvobj <driver>`|查看驱动对象和分发表|
|`!devobj <device>`|查看设备对象和安全描述符|
|`!irp <irp>`|查看 IRP 结构和 I/O 栈|
|`!pool`|查看内核池分配|
|`bp / ba`|软件断点 / 硬件断点|
|`!analyze -v`|自动崩溃转储分析|

> 📌 **工业洞见**：现代内核漏洞研究（如 CVE-2023-21554 的 `afd.sys` 漏洞、CVE-2024 系列内核池溢出）的分析流程，本质就是这一节"实战调试 first"的放大版——**先在 WinDbg 里让系统跑起来，用断点定位到可疑的内核函数，用 `dt` 和 `!pool` 解析内存布局，用 `ba` 监控攻击者可控的内存写入，最后用 `!analyze -v` 还原 BSOD 现场**。

## 🎯 本章核心洞见总结

读完第1章，我希望你带走的不只是"怎么装 WDK、怎么配 WinDbg"，而是这三个**第一性原理**：

**1. 内核代码不是"程序"，是"插件"**

你的 `.sys` 是 NT 内核的一个插件，依赖内核导出表生存，受内核版本约束，崩了整个系统陪葬。这种"宿主-插件"关系决定了驱动开发的所有特殊性。

**2. 内核调试的本质是"远程控制"**

因为调试器必须运行在被调试系统之外，所以才有了 KDCOM/KDNET/管道这套传输机制，才有了虚拟机调试的方法论。**WinDbg 不是"一个调试器"，是"KD 协议的一个客户端"**。

**3. 虚拟化是内核安全研究的"反应堆外壳"**

没有虚拟机，内核安全研究寸步难行。快照、回滚、管道调试、网络调试——这些构成了现代安全研究的实验基础设施。
