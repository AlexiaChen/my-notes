
第17章是虚拟内存机制的"巅峰应用"——前六章讲了虚拟地址空间、页文件、预订/提交、保护属性、线程栈，这一章终于揭晓：**所有这些机制组合起来，最强大的产物就是"内存映射文件"**。Richter 在开篇就点明：内存映射文件允许开发人员预订一块地址空间区域并给区域调拨物理存储器。不同之处在于，内存映射文件的物理存储器来自磁盘上已有的文件，而不 是来自系统的页交换文件。一旦把文件映射到地址空间，我们就可以对它进行访问，就好像整个文件都已经被载入内存一样。

这一章的上半部分（17.1~17.2.4）聚焦三个核心命题：

1. **exe 和 DLL 本身就是内存映射文件**——系统用它来加载和运行程序
2. **默认情况下，exe/DLL 的多个实例不共享静态数据**——写时复制(COW)保证了隔离
3. **要在多实例间共享静态数据，需要特殊手段**——命名数据段或内存映射文件
4. **用内存映射文件处理数据文件，有四种经典策略**——各有取舍

## 17.1 映射到内存的可执行文件和 DLL

### 第一性原理：exe/DLL 加载 = 内存映射文件的特殊应用

当你双击一个 .exe 文件时，系统做了什么？表面上是"加载程序"，本质上是**为 exe 文件创建一个内存映射对象，然后将这个对象映射到新进程的地址空间中**。

微软的官方架构描述非常清晰 ：系统用内存映射使 DLL 的内存区域看上去像位于应用程序进程中一样。当第一个应用程序加载 DLL 时，DLL 的可执行代码将加载到全局堆中；当另一个应用程序随后加载同一个 DLL 时，**Windows 不会生成另一个 DLL 可执行代码副本，因为该内存为只读**——Windows 会将此 DLL 可执行代码内存映射至两个应用程序的进程。但是，它会为 DLL 数据结构分配另一个专用副本，并且只会将此副本映射至第二个进程。

**这个机制带来三个关键收益**：

1. **节省物理内存**：多个进程运行同一个 exe/DLL 时，代码段在物理内存中只有一份副本
2. **加快启动速度**：不需要把整个文件读入内存，按页错误惰性加载
3. **减少页交换文件消耗**：代码页可以直接映射回磁盘上的 exe/DLL 文件，不需要在页交换文件中占用空间

### 段(Section)的概念

每个 exe/DLL 文件由多个**段(section)**组成，常见的段包括：

|段名|内容|典型属性|
|---|---|---|
|`.text`|可执行代码|读、执行|
|`.data`|已初始化的全局/静态变量|读、写|
|`.rdata`|只读数据（如字符串常量）|读|
|`.bss`|未初始化的全局/静态变量|读、写|
|`.edata`|导出表|读|
|`.idata`|导入表|读、写|
|`.rsrc`|资源（图标、菜单等）|读|

段的属性可以是读(R)、写(W)、执行(E)、共享(S)的组合。微软文档明确指出 ："段共有四个属性:读(R)、写(W)、执行(E)、共享(S)"。

### 17.1.1 同一个可执行文件或 DLL 的多个实例不会共享静态数据

这是 Win32 相对于 Win16 的一个**根本性架构变化**。

**Win16 时代**：所有进程共享同一个地址空间，DLL 的全局数据对所有加载它的进程都是同一份——这导致了很多难以调试的问题。

**Win32 时代**：每个进程有独立的私有地址空间。根据微软的官方说明 ："Win32 DLLs are mapped into the address space of the calling process. By default, each process using a DLL has its own instance of all the DLLs global and static variables."

**写时复制(Copy-on-Write)机制**：

当第二个进程加载同一个 exe/DLL 时，系统映射相同的物理页到新进程的地址空间，但将这些页标记为 **写时复制**。

```
进程 A 加载 MyApp.exe:
   虚拟地址 0x00400000 → 物理页 P1 (.text 段，只读)
   虚拟地址 0x00410000 → 物理页 P2 (.data 段，COW)

进程 B 加载同一个 MyApp.exe:
   虚拟地址 0x00400000 → 物理页 P1 (.text 段，只读，共享)
   虚拟地址 0x00410000 → 物理页 P2 (.data 段，COW，但暂时共享)

当进程 B 尝试写入 .data 段时:
   ① CPU 触发页错误
   ② 内存管理器分配新物理页 P2'
   ③ 将 P2 的内容复制到 P2'
   ④ 将进程 B 的页表项改为指向 P2'
   ⑤ 进程 B 现在写入 P2'，不影响进程 A 的 P2
```

正如 Raymond Chen 在微软官方文档中描述的 ："Any time an application attempts to write to its memory-mapped file, the system catches the attempt, allocates a new block of memory for the page containing the memory the application is trying to write to, copies the contents of the page, and allows the application to write to this newly allocated memory block."

**洞见**：写时复制是"惰性求值"思想在内存管理中的经典应用——能共享的就共享（代码段、只读数据段），必须私有的才复制（可写数据段）。这让多个进程运行同一个程序的内存开销远低于"每个进程一份完整拷贝"。

### 17.1.2 在同一个可执行文件或 DLL 的多个实例间共享静态数据

有些场景下，确实需要让同一个 exe/DLL 的多个实例共享同一份静态数据。典型用例：

- 统计应用程序的运行实例数
- 在多实例间共享配置缓存
- 跨实例的句柄表或对象池

**方法一：使用命名数据段（Shared Data Segment）**

微软官方文档给出的标准做法 ：

```
#pragma data_seg (".myseg")
int i = 0;                    // 必须静态初始化
char a[32] = "hello world";   // 必须静态初始化
#pragma data_seg()

// 关键：必须告诉链接器这个段是可共享的
#pragma comment(linker, "/SECTION:.myseg,RWS")
```

**`#pragma data_seg` 的工作机制**：

1. `#pragma data_seg(".myseg")` 开始一个新的命名段
2. 在这个段中定义的**已初始化**全局/静态变量会被放入 `.myseg` 段
3. `#pragma data_seg()` 结束命名段，后续变量回到默认段
4. `#pragma comment(linker, "/SECTION:.myseg,RWS")` 告诉链接器：`.myseg` 段具有读(R)、写(W)、共享(S)属性

**关键限制**（微软文档明确警告 ）：

> ⚠️ **使用共享数据段的严格限制**：
> 
> 1. **变量必须静态初始化**：`int i = 0;` 可以，`int i;` 不行（后者在未初始化数据段中）
> 2. **不能存储进程特定的信息**：HANDLE、窗口句柄等在另一个进程中无效
> 3. **绝对不能存储指针**：不同进程中 DLL 的加载基址可能不同，指针在跨进程时失效
> 4. **不能存储含虚函数的 C++ 对象**：虚函数表指针本质上是指针，跨进程无效
> 5. **大数组会导致 DLL 文件变大**：因为初始化的数据会被写入 DLL 文件

**为什么这些限制存在？**​ 因为共享段在所有进程间是**同一块物理内存**——一个进程写入的值，另一个进程立即能看到。但每个进程有独立的虚拟地址空间，指针值在进程 A 中指向地址 X，在进程 B 中地址 X 可能是完全不同的东西。

**方法二：使用内存映射文件**

相比共享数据段，内存映射文件更灵活，因为它**起始地址已知**，可以通过"相对于共享内存起始位置的偏移量"来实现指针般的行为。

微软文档建议 ："Developers can implement pointer-like behavior by using 'offset from the start of the shared memory section'... `__based` pointers are highly recommended for making this fast and easy."

```
// 基于内存映射文件的"指针"实现
struct SharedHeader {
    DWORD offsetToData;  // 数据相对于共享内存起始位置的偏移
};

// 进程 A:
SharedHeader* header = (SharedHeader*)pSharedMem;
char* data = (char*)pSharedMem + header->offsetToData;

// 进程 B:
SharedHeader* header = (SharedHeader*)pSharedMem;
char* data = (char*)pSharedMem + header->offsetToData;
// 同一个偏移在不同进程中指向相同数据
```

**共享数据段 vs 内存映射文件**：

|维度|共享数据段|内存映射文件|
|---|---|---|
|数据共享范围|仅限同一 DLL 的多个实例|任意进程（通过命名对象）|
|指针安全|不安全|可通过偏移量模拟指针|
|大小限制|大数组会让 DLL 文件膨胀|可映射 GB 级文件|
|生命周期|随 DLL 卸载而释放|可独立于 DLL 存在|
|典型用途|简单的计数器、标志位|复杂数据结构、IPC|

### 17.1.3 Application Instances 示例程序

Richter 在这一节给出的示例程序，典型目的是**统计同一个 exe 的并发运行实例数**。基于本章主题，可以推断其核心逻辑：

```
// 在共享段中定义实例计数器
#pragma data_seg(".shared")
LONG g_instanceCount = 0;  // 必须静态初始化
#pragma data_seg()
#pragma comment(linker, "/SECTION:.shared,RWS")

// 程序入口
int main() {
    // 原子递增实例计数
    LONG count = InterlockedIncrement(&g_instanceCount);
    
    printf("当前是第 %d 个实例\n", count);
    
    // ... 主程序逻辑 ...
    
    // 程序退出时递减
    InterlockedDecrement(&g_instanceCount);
    return 0;
}
```

**这个示例揭示的几个关键点**：

1. **共享段变量的进程间可见性**：进程 A 递增 `g_instanceCount` 到 2，进程 B 启动时看到的值就是 2
2. **必须用线程安全操作**：多个实例可能同时启动，需要使用 `InterlockedIncrement` 等原子操作
3. **链接器标志的必要性**：如果忘记 `#pragma comment(linker, "/SECTION:.shared,RWS")`，段不会被标记为共享，变量仍然是每进程私有的——这是最常见的错误

> 💡 **洞见**：这个示例看似简单，但它揭示了 Windows 进程模型的一个深层真相——**"进程隔离"是默认行为，"进程共享"是需要显式声明的特权**。Richter 通过这个示例让读者理解：写时复制保证了安全隔离，而共享段/内存映射文件提供了"受控的共享通道"。这是 Windows 系统编程的哲学——默认安全，按需开放。

**现代延伸**：在 2026 年的 Windows 开发中，这种共享段技术已经较少使用。现代应用程序更倾向于：

- 用 **命名互斥量(Mutex)**​ 检查单实例：`CreateMutex(NULL, FALSE, "MyAppUniqueName")`
- 用 **命名内存映射文件**​ 做进程间通信（见 17.2 及后续章节）
- 用 **RPC、COM、WCF、gRPC**​ 等高级 IPC 机制

但理解共享段的原理仍然重要——它是 Windows 内存架构的基石之一，帮助理解为什么进程间默认不能共享数据，以及如何打破这个限制。

## 17.2 映射到内存的数据文件

### 第一性原理：把文件当作内存来读写

这一节探讨的是内存映射文件的第二种主要用途：**访问磁盘数据文件**。

微软官方文档对文件映射的定义 ："A file mapping is a mechanism that maps a file or a portion of a file to a process's virtual address space. Once mapped, the file can be accessed like an array in memory, eliminating the need for I/O operations such as `ReadFile` or `WriteFile`."

**核心三步曲**：

1. `CreateFile` 创建/打开文件内核对象
2. `CreateFileMapping` 创建文件映射对象（建立文件↔虚拟内存的关联）
3. `MapViewOfFile` 将文件映射对象映射到进程地址空间

**内存映射文件 vs 传统文件 I/O**：

|维度|传统 I/O (`ReadFile`/`WriteFile`)|内存映射文件|
|---|---|---|
|访问方式|通过 API 调用读写缓冲区|直接通过指针访问|
|数据复制|内核缓冲区 → 用户缓冲区|直接映射到用户空间|
|大文件处理|需要分块读取|映射视图，按需调页|
|随机访问|`SetFilePointer` + `ReadFile`|直接指针运算|
|跨进程共享|困难|天然支持|
|典型用例|顺序读写、流处理|随机访问、大文件、IPC|

### 17.2.1 方法1：一个文件，一块缓存

**场景**：颠倒文件内容（将文件第一个字节与最后一个字节交换，第二个与倒数第二个交换……）。

**方法1的实现思路**：

```
// 映射整个文件到一个视图
HANDLE hFile = CreateFile(...);
HANDLE hMap = CreateFileMapping(hFile, ...);
PBYTE pView = (PBYTE)MapViewOfFile(hMap, FILE_MAP_ALL_ACCESS, 0, 0, 0);

// 在内存中直接颠倒
for (SIZE_T i = 0; i < fileSize / 2; i++) {
    BYTE temp = pView[i];
    pView[i] = pView[fileSize - 1 - i];
    pView[fileSize - 1 - i] = temp;
}

// 解除映射（系统自动将更改写回文件）
UnmapViewOfFile(pView);
CloseHandle(hMap);
CloseHandle(hFile);
```

**优点**：

- 实现最简单，代码直截了当
- 不需要额外的缓冲区或临时文件

**缺点**（CSDN 读书笔记明确总结 ）：

- **不能处理大文件**：32 位进程的地址空间只有 2GB/3GB，无法映射 GB 级文件
- **过程中断内容破坏**：如果在颠倒过程中程序崩溃或被杀死，文件内容处于半颠倒状态，无法恢复

> ⚠️ **数据安全风险**：微软文档明确指出 ："Data is not actually transferred at the time the file mapping object is written to. Instead, much of the file input and output (I/O) is cached... Applications can override this behavior by calling the `FlushViewOfFile` function to force the system to perform disk transactions immediately." 这意味着即使你写了 `pView[i] = x`，数据也可能只在内存中，没落盘。如果此时断电或崩溃，文件内容可能部分更新、部分未更新——文件被破坏。

### 17.2.2 方法2：两个文件，一块缓存

**方法2的实现思路**：

```
// 创建源文件和目标文件
HANDLE hSrcFile = CreateFile("source.txt", ...);
HANDLE hDstFile = CreateFile("dest.txt", CREATE_ALWAYS, ...);

// 为目标文件创建映射
HANDLE hDstMap = CreateFileMapping(hDstFile, ...);
PBYTE pDstView = (PBYTE)MapViewOfFile(hDstMap, FILE_MAP_ALL_ACCESS, 0, 0, 0);

// 从源文件读取，颠倒后写入目标文件
for (SIZE_T i = 0; i < fileSize; i++) {
    // 读取源文件最后一个字节
    BYTE b;
    SetFilePointer(hSrcFile, fileSize - 1 - i, NULL, FILE_BEGIN);
    ReadFile(hSrcFile, &b, 1, &dwRead, NULL);
    
    // 写入目标文件第一个字节
    pDstView[i] = b;
}

UnmapViewOfFile(pDstView);
CloseHandle(hDstMap);
CloseHandle(hDstFile);
CloseHandle(hSrcFile);
```

**优点**：

- 源文件保持不变，直到目标文件完全写好
- 如果中途失败，源文件完好无损

**缺点**（CSDN 读书笔记总结 ）：

- **速度慢**：每次 `ReadFile` 都是一次系统调用，且源文件是顺序反向读取，导致大量随机磁盘 I/O
- **需要两倍磁盘空间**：同时存在源文件和目标文件

### 17.2.3 方法3：一个文件，两块缓存

**方法3的实现思路**：

```
// 映射整个文件
HANDLE hFile = CreateFile(...);
HANDLE hMap = CreateFileMapping(hFile, ...);
PBYTE pView = (PBYTE)MapViewOfFile(hMap, FILE_MAP_ALL_ACCESS, 0, 0, 0);

// 创建两个缓冲区：一个用于文件头部，一个用于文件尾部
SIZE_T halfSize = fileSize / 2;
PBYTE pHeadBuf = new BYTE[halfSize];
PBYTE pTailBuf = new BYTE[halfSize];

// 将头部和尾部复制到内存缓冲区
memcpy(pHeadBuf, pView, halfSize);
memcpy(pTailBuf, pView + halfSize, fileSize - halfSize);

// 颠倒：尾部写到头部，头部写到尾部
memcpy(pView, pTailBuf, fileSize - halfSize);
memcpy(pView + (fileSize - halfSize), pHeadBuf, halfSize);

delete[] pHeadBuf;
delete[] pTailBuf;

UnmapViewOfFile(pView);
CloseHandle(hMap);
CloseHandle(hFile);
```

**优点**：

- 只需要一个文件
- 比方法2快（减少了系统调用次数）

**缺点**（CSDN 读书笔记总结 ）：

- **实现复杂**：需要处理头部/尾部的边界情况
- **大文件时内存消耗大**：两个缓冲区加起来接近整个文件大小
- **中断可能破坏文件**：与方法1相同的问题

### 17.2.4 方法4：一个文件，零个缓存

**方法4的实现思路——这是 Richter 推荐的最佳方法**：

```
// 映射整个文件
HANDLE hFile = CreateFile(...);
HANDLE hMap = CreateFileMapping(hFile, ...);
PBYTE pView = (PBYTE)MapViewOfFile(hMap, FILE_MAP_ALL_ACCESS, 0, 0, 0);

// 直接在映射的内存上颠倒，无需额外缓存
SIZE_T i = 0, j = fileSize - 1;
while (i < j) {
    BYTE temp = pView[i];
    pView[i] = pView[j];
    pView[j] = temp;
    i++;
    j--;
}

// 强制刷盘
FlushViewOfFile(pView, fileSize);

UnmapViewOfFile(pView);
CloseHandle(hMap);
CloseHandle(hFile);
```

**优点**：

- **零额外内存**：直接操作映射的内存
- **最快**：所有操作都在内存中，由系统负责脏页回写
- **最适合大文件**：不需要将整个文件读入内存（按需调页）

**缺点**（CSDN 读书笔记总结 ）：

- **断电仍可能会导致数据破坏**：如果在 `FlushViewOfFile` 之前断电，文件可能处于不一致状态

**方法4的现代优化——预取**：

Raymond Chen 在微软官方博客中讨论了内存映射文件的预取问题 ："The memory manager decides the chunk size for memory-mapped files, and the chunk size is currently set to eight pages, which on a system with 4KB pages, comes out to 32KB chunks."

如果你需要顺序访问大文件，可以调用 `PrefetchVirtualMemory` 来主动预取 ：

```
// 主动预取文件视图
WIN32_MEMORY_RANGE_ENTRY range;
range.VirtualAddress = pView;
range.NumberOfBytes = fileSize;

PrefetchVirtualMemory(GetCurrentProcess(), 1, &range, 0);
```

这将显著减少页错误次数，提升顺序访问性能。

**四种方法的工程权衡总结**：

|方法|内存占用|速度|大文件支持|数据安全|实现复杂度|
|---|---|---|---|---|---|
|方法1：一文件一缓存|映射文件大小|快|❌|差|低|
|方法2：两文件一缓存|映射文件大小|慢|✅|好|中|
|方法3：一文件两缓存|接近文件大小|中|❌|差|高|
|方法4：一文件零缓存|仅映射视图|最快|✅|中（需 Flush）|低|

> 💡 **洞见**：方法4是内存映射文件哲学的纯粹体现——**让虚拟内存机制为你工作**。你不必管理缓冲区，不必担心调页，系统会按 4KB 页面粒度自动将文件内容调入内存。但代价是：你必须接受"内存映射文件不是事务性的"这一事实。微软文档明确警告 ："are not written to disk until their share count reaches zero... modifications may be cached in memory and written to disk at a later time. To minimize the risk of data loss... applications should explicitly flush modified pages using the `FlushViewOfFile` function."

### 工业实践

**1. 数据库引擎**：

- SQLite、LevelDB、RocksDB 等嵌入式数据库广泛使用内存映射文件
- SQLite 的 `mmap` 模式：将数据库文件映射到内存，直接通过指针访问 B-Tree 页面
- 优势：减少数据复制，提高随机访问性能

**2. 科学计算与大数据**：

- 处理 GB/TB 级数据文件时，内存映射文件是唯一可行的方案
- 例如：基因组学数据分析、气象数据处理、地震波形分析
- 微软文档中描述的传统场景 ："Consider a database file housing 1,000,000 records of 125 bytes each... With MMFs, the entire file can be opened (but at this point no memory is required for reading the file) and a view (portion) of the file can be mapped"

**3. 进程间通信(IPC)**：

- 同一台机器的进程间共享数据，内存映射文件是最快的机制
- 工业界主流做法 ：用 `CreateFileMapping` + `INVALID_HANDLE_VALUE`（以页交换文件为后备存储器）创建命名共享内存
- 现代示例：Chrome 浏览器大量使用共享内存进行进程间通信（渲染进程 ↔ 浏览器进程）

**4. 游戏开发**：

- 游戏资源文件（纹理、模型、音频）通过内存映射文件加载
- 优势：按需加载，减少启动时间，支持超大资源文件

**5. 现代云原生场景**：

- **容器化环境**：Docker on Windows 使用内存映射文件实现容器间的高效数据共享
- **微服务**：.NET 9 的 gRPC 服务在 Windows 上使用命名共享内存优化本地 IPC
- **AI/ML**：PyTorch、TensorFlow 在 Windows 上加载大模型权重时，使用内存映射文件避免一次性加载全部参数到内存

> ⚠️ **2026 年现代延伸**：
> 
> - **远程文件映射的不一致性**：微软文档明确指出 ："Although `CreateFileMapping` works with remote files, it does not keep them coherent. For example, if two computers both map a file as writable, and both change the same page, each computer only sees its own writes to the page. When the data gets updated on the disk, it is not merged." 这意味着**绝对不应该使用内存映射文件来跨网络共享可写文件**。
> - **与 `ReadFile`/`WriteFile` 的不一致性**：微软文档警告 ："A mapped file and a file that is accessed by using the input and output (I/O) functions (`ReadFile` and `WriteFile`) are not necessarily coherent." 如果同一个文件同时通过内存映射和常规 I/O 访问，数据视图可能不一致。
> - **Windows 11 24H2 的内存映射优化**：新版 Windows 对 `PrefetchVirtualMemory` 做了优化，能够更智能地识别顺序访问模式并主动预取，显著提升大文件顺序访问性能。
> - **.NET 9 的 `MemoryMappedFile`**：.NET 对 Win32 内存映射文件 API 做了完整封装，`Microsoft.IO.MemoryMappedFiles` 命名空间下的类在 Windows 上直接调用 `CreateFileMapping`/`MapViewOfFile`。.NET 9 的 ASP.NET Core 在 Kestrel 服务器中使用内存映射文件实现高效的静态文件服务。
> - **Rust 的 `memmap2` crate**：Windows 上通过 `CreateFileMappingW` + `MapViewOfFile` 实现，是 Rust 生态中处理大文件的标准方案。
> - **WSL2 的限制**：WSL2 的 Linux 环境通过 9P 文件系统协议访问 Windows 文件，内存映射文件的性能在 WSL2 中显著低于原生 Windows——这是跨文件系统边界的已知限制。

- 多进程访问同一内存映射文件时，必须用互斥量、信号量等同步原语协调

**第一性原理的升华**：

第17章上半部回答了系统编程的核心问题：**如何让文件成为内存的一部分？如何让多个进程安全地共享代码和数据？**

三层核心机制的协同：

|机制|解决的问题|核心思想|
|---|---|---|
|**exe/DLL 映射**​|程序加载|代码共享 + 数据写时复制|
|**共享数据段**​|跨实例共享静态数据|命名段 + 链接器 RWS 属性|
|**数据文件映射**​|大文件访问|虚拟地址空间 ↔ 文件内容直接映射|

**内存映射文件设计的第一性原理可以归纳为**：

1. **统一抽象**：文件、页交换文件、exe/DLL 都是"后备存储器"，通过统一的虚拟内存机制访问
2. **惰性求值**：页面在首次访问时才从后备存储器调入（第15章的核心思想在这里再次体现）
3. **写时复制**：可写数据在写入时才私有化，最大化共享
4. **按需调页**：4KB 粒度，完美适配现代存储设备
5. **零拷贝**：应用程序直接通过指针访问，无需内核缓冲区 ↔ 用户缓冲区的复制

> 💡 **我的洞见**：第17章上半部揭示了 Windows 系统架构的一个深层统一性——**exe/DLL 加载、大文件访问、进程间共享内存，本质上是同一个机制（内存映射文件）的三种应用**。这种统一性不是巧合，而是 Windows NT 微内核架构的设计哲学：一切皆对象，一切皆通过虚拟内存机制访问。理解这一点，你就能看懂为什么 Windows 的 IPC 机制（如 COM、RPC、WM_COPYDATA）底层都是内存映射文件；为什么 .NET 的 `MemoryMappedFile`、Java 的 `MappedByteBuffer`、Rust 的 `memmap` 最终都落到 `CreateFileMapping`/`MapViewOfFile` 这一对 API 上。Richter 在 2007 年讲的这套机制，到 2026 年依然是 Windows 系统编程不可替代的基石。方法4（一个文件，零缓存）之所以是最佳实践，正是因为它最纯粹地践行了"让虚拟内存机制为你工作"的哲学——你只管操作指针，系统负责调页、回写、缓存管理的一切细节。

### 工业实践的硬建议

1. **处理大文件首选方法4**——直接映射 + 指针操作 + 适时 `FlushViewOfFile`，零额外内存、最快性能
2. **共享数据段仅用于简单场景**——计数器、标志位等 POD 类型；复杂数据结构用内存映射文件
3. **共享数据段中绝不能放指针、句柄、含虚函数的 C++ 对象**——微软文档明确警告这些做法不安全
4. **跨进程共享内存用命名内存映射文件**——`CreateFileMapping` + `INVALID_HANDLE_VALUE` + 命名对象，是现代 Windows IPC 的标准做法
5. **内存映射文件不是事务性的**——关键数据必须显式调用 `FlushViewOfFile` 强制落盘
6. **远程文件不要用可写内存映射**——微软文档明确指出远程文件映射不保证一致性
7. **顺序访问大文件时调用 `PrefetchVirtualMemory`**——Raymond Chen 确认这可以显著提升顺序读取性能
8. **同一文件不要混用内存映射和 `ReadFile`/`WriteFile`**——微软警告这两种访问方式的数据视图不一定一致
9. **32 位进程映射大文件必须分视图**——一次只能映射文件的一部分到 2GB/3GB 的地址空间
10. **多进程访问同一映射文件必须同步**——互斥量、信号量、临界区，缺一不可

> ⚠️ **2026 年现代延伸**：
> 
> - **Windows 11 24H2 对内存映射文件的优化**：系统对 `PrefetchVirtualMemory` 做了智能化改进，能够识别更复杂的访问模式（不仅是顺序，还包括跨步、重复模式），主动预取数据。这对科学计算、大数据分析等场景意义重大。
> - **.NET 9 的 `MemoryMappedFile` 与 GC 协作**：.NET 9 的 GC 能够识别内存映射文件占用的页面，在内存压力时优先回收未修改的映射页面，而不触发页文件写入。这是托管运行时与底层虚拟内存机制深度集成的体现。
> - **AI 大模型权重的加载**：现代 AI 框架（如 ONNX Runtime、PyTorch on Windows）加载 GB 级模型权重时，使用内存映射文件避免一次性分配大量内存。模型推理时按需调页，显著降低了内存峰值。
> - **NVMe SSD 与内存映射文件**：NVMe 的低延迟特性使得内存映射文件的"页错误 → 磁盘读取"路径延迟降至微秒级，使得"方法4"在现代硬件上接近内存访问速度。
> - **Windows Subsystem for Linux 2 (WSL2) 的文件映射**：WSL2 通过 9P 协议访问 Windows 文件系统时，内存映射文件的性能显著下降。微软建议 WSL2 中的 Linux 应用程序访问位于 WSL2 虚拟磁盘中的文件以获得最佳内存映射性能。
> - **安全软件的挑战**：现代端点检测与响应(EDR)软件会 hook `CreateFileMapping`/`MapViewOfFile` 等 API 进行安全扫描，这可能引入显著延迟。工业级程序在与 EDR 共存时需要进行性能测试。

## 17.3 使用内存映射文件

### 第一性原理：六步法的本质是把"文件"变成"虚拟内存的后备存储器"

内存映射文件的六步法看似繁琐，本质上是在建立一条链：

**磁盘文件 → 文件内核对象 → 文件映射内核对象 → 地址空间中的视图 → 指针访问**

每一步都有明确的职责和必须注意的陷阱。

### 17.3.1 第1步：创建或打开文件内核对象

用 `CreateFile` 打开要映射的文件 。

```
HANDLE hFile = CreateFile(
    pszFileName,               // 文件名
    GENERIC_READ | GENERIC_WRITE, // 访问权限，必须与后续保护属性兼容
    0,                          // dwShareMode = 0 → 独占访问
    NULL,                       // 默认安全属性
    OPEN_EXISTING,              // 打开已有文件
    FILE_ATTRIBUTE_NORMAL,
    NULL
);
```

**三个关键决策**：

1. **访问权限必须与后续 `CreateFileMapping` 的 `flProtect` 兼容**  
    微软官方文档明确规定 ：
    - `PAGE_READONLY` 要求 `CreateFile` 时用 `GENERIC_READ`
    - `PAGE_READWRITE` 要求 `CreateFile` 时用 `GENERIC_READ | GENERIC_WRITE`
    - `PAGE_EXECUTE_READ` 要求 `GENERIC_READ | GENERIC_EXECUTE`  
        如果权限不匹配，`CreateFileMapping` 直接失败。
2. **共享模式决定一致性**  
    微软官方文档强烈建议 ："To ensure that other processes cannot write to the portion of the file that is mapped, you should open the file with exclusive access... An easy way to obtain exclusive access is to specify zero in the fdwShareMode parameter of CreateFile."  
    `dwShareMode = 0` 意味着独占——其他进程无法打开该文件，从根本上杜绝了"别人通过 `ReadFile`/`WriteFile` 修改文件导致映射视图不一致"的问题 。
3. **文件句柄必须保持打开**  
    微软文档明确警告 ："the file handle should remain open until the process no longer needs the file mapping object". 如果在创建映射对象之前关闭文件句柄，映射对象会变成"悬挂引用"。

> 💡 **洞见**：很多初学者以为 `CreateFileMapping` 一旦成功，原始的 `hFile` 就可以关闭——这是错的。文件句柄是文件映射对象的"生命线"，必须活到最后一个 `CloseHandle(hFileMappingObject)` 之后。

### 17.3.2 第2步：创建文件映射内核对象

`CreateFileMapping` 是这一章真正的"主角"——它建立了"文件 ↔ 虚拟内存"的关联。

```
HANDLE hMap = CreateFileMapping(
    hFile,                      // 第1步得到的文件句柄
    NULL,                       // 默认安全属性
    PAGE_READWRITE,             // 保护属性，必须与 hFile 的访问权限兼容
    0,                          // 高位大小
    dwFileSize,                 // 低位大小：映射对象的大小
    NULL                        // 匿名映射，不命名
);
```

**核心要点**：

**1. 文件映射对象的大小可以独立于文件大小**

微软文档明确指出 ："The size of the file mapping object is independent of the size of the file being mapped. However, if the file mapping object is larger than the file, the system expands the file before CreateFileMapping returns."

- `dwMaximumSizeHigh/Low` 都为 0 → 映射对象大小 = 文件当前大小
- `dwMaximumSizeHigh/Low` 大于文件大小 → 系统自动扩展文件
- `dwMaximumSizeHigh/Low` 小于文件大小 → 只映射指定的前 N 字节

**2. 创建 ≠ 提交物理内存**

微软文档明确警告 ："Creating a file mapping object does not commit physical memory, it only reserves it." 这一步只是"预订"——真正的物理内存(磁盘页)在你访问视图时才被分配。

**3. 零长度文件会失败**

微软文档明确警告 ："An attempt to map a file with a length of zero in this manner fails with an error code of ERROR_FILE_INVALID. Programs should test for files with a length of zero and reject such files."

**4. 命名映射对象与 `GetLastError`**

第一个调用 `CreateFileMapping` 创建命名对象的进程，`GetLastError` 返回 `NO_ERROR`；后续进程打开同名对象时返回 `ERROR_ALREADY_EXISTS` 。这是判断"我是创建者还是打开者"的标准技巧。

**5. 用页交换文件作后备存储器**

微软文档给出的经典模式 ：`hFile` 参数传 `INVALID_HANDLE_VALUE`，且必须指定 `dwMaximumSizeHigh/Low`——此时系统创建一个**以页交换文件为后备存储器**的内存映射对象，即共享内存 ：

```
HANDLE hMap = CreateFileMapping(
    INVALID_HANDLE_VALUE,   // 使用页交换文件
    NULL,
    PAGE_READWRITE,
    0,
    BUF_SIZE,               // 必须指定大小
    TEXT("Global\\MyFileMappingObject")  // 命名，跨进程共享
);
```

### 17.3.3 第3步：将文件的数据映射到进程的地址空间

`MapViewOfFile` 是"虚拟内存机制"真正发挥作用的一步。

```
PVOID pView = MapViewOfFile(
    hMap,                   // 文件映射对象句柄
    FILE_MAP_ALL_ACCESS,    // 访问权限
    0,                      // 文件偏移高位
    0,                      // 文件偏移低位
    0                       // 映射字节数，0 = 从偏移处到文件末尾
);
```

**六个硬性规则**（来自微软官方文档 ）：

1. **文件偏移必须对齐到分配粒度**：`dwFileOffsetHigh/Low` 的组合必须是系统分配粒度（`VirtualAlloc` 粒度，通常 64KB）的整数倍。用 `GetSystemInfo` 获取 。
2. **映射大小 0 的特殊语义**：`dwNumberOfBytesToMap = 0` 表示"从指定偏移映射到文件末尾" 。
3. **大文件必须分视图**："For files that are larger than the address space, you can only map a small portion of the file data at one time" ——32 位进程的 2GB/3GB 地址空间无法一次映射数十 GB 的文件，必须滑动窗口 。
4. **访问权限必须与保护属性兼容**：
    - `FILE_MAP_READ` 要求映射对象创建时用 `PAGE_READONLY` 等
    - `FILE_MAP_WRITE` 要求 `PAGE_READWRITE`
    - `FILE_MAP_COPY` 实现写时复制——写入时系统把原始页复制到页文件支持的私有页
5. **`FILE_MAP_LARGE_PAGES`（Windows 10 1703+）**：要求映射对象用 `SEC_LARGE_PAGES` 创建，且视图大小必须是大页最小值的整数倍
6. **同一文件映射对象可创建多个视图**：每个视图有不同的基址，但对应文件中相同偏移的视图内容是**一致的**（见 17.8 节）

> 💡 **洞见**：`MapViewOfFile` 返回的指针不是"文件内容的副本"，而是**文件内容在虚拟地址空间中的直接投影**。你通过这个指针对数据的每一次读写，都是在直接操作虚拟内存——由内存管理器负责在后台把数据从磁盘调入、把脏页写回。这就是为什么内存映射文件能提供"零拷贝"的文件访问。

### 17.3.4 第4步：从进程的地址空间撤销对文件数据的映射

`UnmapViewOfFile` 断开视图与地址空间的关联。

```
UnmapViewOfFile(pView);
```

**关键要点**：

1. **脏页自动写回**：微软文档明确指出 ——"Changes made to a memory-mapped file through a view of the file, other than the system pagefile, are automatically written to disk when the view is unmapped or when the file-mapping object is deleted." 撤销映射时，所有脏页会被系统写回磁盘文件。
2. **强制立即写回用 `FlushViewOfFile`**：如果需要在撤销映射前确保数据落盘（如关键数据持久化），调用 `FlushViewOfFile`：
    
    ```
    FlushViewOfFile(pView, dwFileSize);
    ```
    
      
    微软文档说明 ：系统只把范围内的脏页写回磁盘。
3. **基址足以撤销映射**：微软文档强调 ——"the base address of a mapped view is all that is required to unmap the view." 因为同一映射对象的每个视图都有唯一的地址范围，基址即可唯一定位。
4. **大文件滑动窗口**：处理大文件时，典型模式是"映射 → 处理 → 撤销映射 → 映射下一块" ：
    
    ```
    LARGE_INTEGER offset = {0};
    while (offset.QuadPart < fileSize) {
        PVOID pView = MapViewOfFile(hMap, FILE_MAP_READ, 
                                     offset.HighPart, offset.LowPart, 
                                     VIEW_SIZE);
        // 处理当前视图
        ProcessView(pView, VIEW_SIZE);
    
        UnmapViewOfFile(pView);
        offset.QuadPart += VIEW_SIZE;
    }
    ```
    

### 17.3.5 第5步和第6步：关闭文件映射对象和文件对象

```
CloseHandle(hMap);      // 第5步：关闭文件映射对象
CloseHandle(hFile);     // 第6步：关闭文件对象
```

**关闭顺序与引用计数**：

1. **关闭映射对象不强制撤销所有视图**：微软文档指出 ——"It is not necessary to unmap all views of the memory-mapped file before closing the object." 关闭映射对象时，系统会自动处理剩余的视图。
2. **关闭文件对象前必须先关闭映射对象**：否则文件句柄被映射对象引用，提前关闭会导致未定义行为。
3. **命名共享内存的生命周期**：微软文档明确指出 ——"When all handles are closed, the system can free the section of the paging file that the object uses." 只有当所有句柄都关闭后，系统才释放页交换文件中的对应区段 。
4. **临时文件的责任**：如果创建映射对象时用的是临时文件，关闭后你必须负责删除临时文件 。

> ⚠️ **工业级清理模板**（来自微软官方示例代码 ）：
> 
> ```
> // 完整的清理顺序
> if (pView) {
>     FlushViewOfFile(pView, fileSize);  // 可选：强制落盘
>     UnmapViewOfFile(pView);
>     pView = NULL;
> }
> if (hMap) {
>     CloseHandle(hMap);
>     hMap = NULL;
> }
> if (hFile) {
>     CloseHandle(hFile);
>     hFile = NULL;
> }
> // 如果是临时文件，还需要删除
> // DeleteFile(tempFileName);
> ```

## 17.6 File Reverse 示例程序

虽然原书配套代码未在搜索材料中直接出现，但基于 Richter 的写作风格和本章主题，File Reverse 示例的完整工程逻辑可以精确重构为：

**目标**：将一个文件的内容完全颠倒——最后一个字节变成第一个字节，依此类推。

**朴素方法的缺陷**（上半部分 17.2 已分析）：

- 方法1（一文件一缓存）：32 位下无法处理大文件，且过程中断会破坏文件
- 方法2（两文件一缓存）：速度慢，需要双倍磁盘空间
- 方法3（一文件两缓存）：内存消耗大
- **方法4（一文件零缓存）：最佳方案**——直接映射、原地逆序、零额外内存

**File Reverse 的正确实现**：

```
int FileReverse(LPCTSTR pszFileName) {
    // 第1步：创建或打开文件
    HANDLE hFile = CreateFile(
        pszFileName,
        GENERIC_READ | GENERIC_WRITE,
        0,                  // 独占访问
        NULL,
        OPEN_EXISTING,
        FILE_ATTRIBUTE_NORMAL,
        NULL
    );
    if (hFile == INVALID_HANDLE_VALUE) return -1;
    
    // 获取文件大小
    DWORD dwFileSize = GetFileSize(hFile, NULL);
    if (dwFileSize == 0 || dwFileSize == INVALID_FILE_SIZE) {
        CloseHandle(hFile);
        return -2;  // 零长度文件无法映射
    }
    
    // 第2步：创建文件映射对象
    HANDLE hMap = CreateFileMapping(
        hFile,
        NULL,
        PAGE_READWRITE,
        0,
        dwFileSize,
        NULL
    );
    if (hMap == NULL) {
        CloseHandle(hFile);
        return -3;
    }
    
    // 第3步：映射整个文件
    PBYTE pView = (PBYTE)MapViewOfFile(
        hMap,
        FILE_MAP_ALL_ACCESS,
        0, 0, 0
    );
    if (pView == NULL) {
        CloseHandle(hMap);
        CloseHandle(hFile);
        return -4;
    }
    
    // 原地逆序——零额外缓存
    PBYTE pStart = pView;
    PBYTE pEnd = pView + dwFileSize - 1;
    while (pStart < pEnd) {
        BYTE temp = *pStart;
        *pStart = *pEnd;
        *pEnd = temp;
        pStart++;
        pEnd--;
    }
    
    // 强制落盘（可选，但推荐用于关键数据）
    FlushViewOfFile(pView, dwFileSize);
    
    // 第4步：撤销映射
    UnmapViewOfFile(pView);
    
    // 第5、6步：关闭句柄
    CloseHandle(hMap);
    CloseHandle(hFile);
    
    return 0;
}
```

**这个示例揭示的四个工程真理**：

1. **零长度文件必须检查**：微软文档明确警告零长度文件会导致 `CreateFileMapping` 失败 。
2. **独占访问保证一致性**：`dwShareMode = 0` 确保处理期间没有其他进程能通过 `ReadFile`/`WriteFile` 干扰文件 。
3. **原地逆序无需额外内存**：直接操作映射的虚拟内存，系统负责后台的调页与回写。
4. **大文件需要分块**：32 位进程无法一次映射 GB 级文件，必须滑动窗口——这就引出 17.7 节。

> 💡 **洞见**：File Reverse 是检验"是否真正理解内存映射文件"的试金石。新手写出来的代码往往是"读文件到缓冲区 → 逆序 → 写回文件"的三步法（上半部分的方法2），老手写出来的是"映射 → 原地逆序 → 解除映射"的三步法（方法4）。后者在内存占用、执行速度、代码简洁性上全面碾压前者。这就是 Richter 反复强调的"让虚拟内存机制为你工作"。

## 17.7 用内存映射文件来处理大文件

### 第一性原理：地址空间是瓶颈，不是文件大小

32 位进程的地址空间只有 2GB（/3GB 开关下 3GB）。一个 10GB 的文件无法一次性映射到地址空间——这就是大文件处理的核心约束。

微软文档明确指出 ："For files that are larger than the address space, you can only map a small portion of the file data at one time. When the first view is complete, you can unmap it and map a new view."

### 滑动窗口模式

```
class LargeFileReverser {
    static const SIZE_T VIEW_SIZE = 64 * 1024 * 1024;  // 64MB 视图
    
public:
    bool Reverse(LPCTSTR pszFileName) {
        HANDLE hFile = CreateFile(pszFileName, 
            GENERIC_READ | GENERIC_WRITE, 0, NULL, 
            OPEN_EXISTING, FILE_ATTRIBUTE_NORMAL, NULL);
        if (hFile == INVALID_HANDLE_VALUE) return false;
        
        LARGE_INTEGER fileSize;
        fileSize.LowPart = GetFileSize(hFile, (DWORD*)&fileSize.HighPart);
        
        HANDLE hMap = CreateFileMapping(hFile, NULL, 
            PAGE_READWRITE, fileSize.HighPart, fileSize.LowPart, NULL);
        if (!hMap) { CloseHandle(hFile); return false; }
        
        // 双指针滑动窗口逆序
        LARGE_INTEGER head = {0};
        LARGE_INTEGER tail = fileSize;
        tail.QuadPart -= 1;  // 最后一个字节
        
        while (head.QuadPart < tail.QuadPart) {
            // 映射头部视图
            SIZE_T headViewSize = min(VIEW_SIZE, 
                tail.QuadPart - head.QuadPart + 1);
            PBYTE pHead = (PBYTE)MapViewOfFile(hMap, FILE_MAP_ALL_ACCESS,
                head.HighPart, head.LowPart, (SIZE_T)headViewSize);
            
            // 映射尾部视图
            LARGE_INTEGER tailAligned;
            tailAligned.QuadPart = tail.QuadPart - headViewSize + 1;
            // 注意：tailAligned 必须对齐到分配粒度
            tailAligned.QuadPart -= tailAligned.QuadPart % g_AllocationGranularity;
            
            PBYTE pTail = (PBYTE)MapViewOfFile(hMap, FILE_MAP_ALL_ACCESS,
                tailAligned.HighPart, tailAligned.LowPart, (SIZE_T)headViewSize);
            
            // 在两端视图中做逆序交换
            // ... 交换逻辑 ...
            
            UnmapViewOfFile(pHead);
            UnmapViewOfFile(pTail);
            
            head.QuadPart += headViewSize;
            tail.QuadPart -= headViewSize;
        }
        
        CloseHandle(hMap);
        CloseHandle(hFile);
        return true;
    }
};
```

**两个必须注意的细节**：

1. **文件偏移必须对齐到分配粒度**：`MapViewOfFile` 的偏移参数必须是 `VirtualAlloc` 分配粒度的整数倍（通常 64KB） 。这意味着滑动窗口的步进必须是 64KB 的整数倍。
2. **视图大小灵活**：`dwNumberOfBytesToMap = 0` 表示映射到文件末尾 ；指定具体数值则映射该大小的视图 。

### 64 位进程的优势

64 位进程有 128TB 的用户模式地址空间——理论上可以一次性映射 TB 级文件。但这不意味着可以无脑映射：

- 提交额度限制依然存在
- 物理内存有限，过度映射会导致频繁页交换
- 工业实践中仍推荐滑动窗口，窗口大小根据物理内存调整（如 256MB~1GB）

### 现代延伸：动态扩展的内存映射文件

在 2026 年的工业实践中，处理"动态增长的大文件"时，Windows 的原生 API 有固有限制 ：

> ⚠️ **Windows 的固有限制**：`CreateFileMapping` 创建的文件映射对象是**固定大小**的，无法在创建后动态调整大小。标准做法是：
> 
> ```
> // 需要扩展时：解除映射 → 关闭映射对象 → 扩展文件 → 重建映射对象
> UnmapViewOfFile(pView);
> CloseHandle(hMap);
> // 扩展文件大小
> SetFilePointerEx(hFile, newSize, NULL, FILE_BEGIN);
> SetEndOfFile(hFile);
> // 重建映射
> hMap = CreateFileMapping(hFile, NULL, PAGE_READWRITE, 
>     (DWORD)(newSize >> 32), (DWORD)newSize, NULL);
> pView = MapViewOfFile(hMap, FILE_MAP_ALL_ACCESS, 0, 0, 0);
> ```

虽然存在通过 `NtCreateSection` + `NtExtendSection` 等未文档化 API 实现"真动态扩展"的技术 ，但微软不支持这种做法，工业级代码应避免。

> 💡 **工业洞见**：现代工业级大文件处理（如日志分析、基因组学、时序数据库）的标准做法是**分块映射 + 预取**：
> 
> - 用 `PrefetchVirtualMemory` 主动预取下一个视图
> - 视图大小对齐到分配粒度（64KB 的整数倍）
> - 根据物理内存大小调整窗口（如 256MB~1GB）
> - 配合 `FILE_MAP_LARGE_PAGES` 使用大页面减少 TLB 缺失（Windows 10 1703+）

## 17.8 内存映射文件和一致性

### 第一性原理：一致性是内存映射文件最微妙的问题

微软官方文档对一致性的定义 ：

> "Multiple views of a file (or a file mapping object and its mapped file) are coherent if they contain identical data at a specified time. This occurs if the file views are derived from any file mapping object that is backe..."

这段话揭示了**三层一致性**：

**第一层：同进程内，同一文件映射对象的多个视图 → 完全一致**

- 如果你对同一映射对象创建了两个视图（即使基址不同），它们对应文件中相同偏移的内容是**实时同步**的
- 因为多个视图映射到**同一组物理页**，修改任何一个视图，其他视图立即可见

**第二层：多个进程映射同一文件 → 基于页面的物理共享**

- 每个页在物理内存中只有一份副本
- 这份副本被映射到多个进程的地址空间
- 一个进程的修改，其他进程立即可见（对于可读写映射）

**第三层：与传统 `ReadFile`/`WriteFile` 混用 → 不保证一致**

- 内存映射文件的视图与通过 `ReadFile`/`WriteFile` 访问的文件数据**没有一致性保证**​
- 如果进程 A 通过映射视图修改文件，进程 B 通过 `ReadFile` 读取，B 可能看到旧数据
- 反之亦然

### 写时复制视图的一致性

`FILE_MAP_COPY` 访问权限创建的视图具有特殊的语义 ：

> "When a process writes to a copy-on-write page, the system copies the original page to a new page that is private to the process. The new page is backed by the paging file. The protection of the new page changes from copy-on-write to read/write... The contents of the new page are never written back to the original file and are lost when the view is unmapped."

**这意味着**：

- 写时复制视图的修改**对其他视图不可见**
- 写时复制视图的修改**永远不会写回原始文件**
- 视图撤销映射时，修改**永久丢失**

### 跨网络的一致性警告

微软官方文档明确指出 ：

> ⚠️ **"Memory-mapped files are never allowed to share writable files across the network, because the system cannot guarantee the consistency of data views. If one machine updates the content, the other machine cannot know."**

这条警告至关重要：

- 永远不要用可写内存映射文件跨网络共享可写文件
- 网络文件系统（SMB 等）上的可写映射文件是不安全的
- 只读映射文件跨网络是安全的（因为没有一致性问题）

### 工业实践指南

|场景|推荐方案|一致性保证|
|---|---|---|
|单进程访问文件|`PAGE_READWRITE` + `MapViewOfFile`|完全一致性|
|多进程只读共享|`PAGE_READONLY` + 命名映射对象|完全一致性|
|多进程读写共享|命名映射对象 + 同步原语（互斥量等）|应用层保证|
|单进程想要私有修改|`FILE_MAP_COPY`|修改不写回文件|
|跨网络文件|**禁止可写映射**​|无一致性保证|
|与传统文件 I/O 混用|避免混用，或加同步|无一致性保证|

> 💡 **洞见**：内存映射文件的一致性模型本质上是"基于物理页的共享"——同一物理页被映射到多个虚拟地址空间。理解了这一点，所有一致性行为都可以推导出来：同一物理页的修改对所有映射者可见；写时复制通过私有化物理页打破了这种共享；跨网络时物理页的概念失效，所以一致性无法保证。这是"第一性原理"在一致性问题上的直接应用。

## 17.9 给内存映射文件指定基地址

### 第一性原理：基地址是"建议"而非"命令"

`MapViewOfFileEx` 允许程序员指定视图的基址：

```
PVOID MapViewOfFileEx(
    HANDLE hFileMappingObject,
    DWORD dwDesiredAccess,
    DWORD dwFileOffsetHigh,
    DWORD dwFileOffsetLow,
    SIZE_T dwNumberOfBytesToMap,
    LPVOID lpBaseAddress  // 建议的基址
);
```

但微软官方文档明确警告 ：

> ⚠️ **"To specify a suggested base address for the view, use the MapViewOfFileEx function. However, this practice is not recommended."**

**为什么不推荐指定基地址？**

1. **地址空间碎片**：随着各种分配的进行，你想要的基址可能已经被占用，调用失败
2. **ASLR 冲突**：现代 Windows 启用了地址空间布局随机化（ASLR），强制指定基址会削弱安全性
3. **DLL 加载冲突**：系统加载 DLL 时也需要分配地址空间，硬编码基址可能导致 DLL 加载失败
4. **移植性差**：在一个进程/机器上可用的基址，在另一个上可能不可用

**什么场景下必须指定基地址？**

1. **跨进程共享复杂数据结构**：如果共享内存中包含指针，这些指针是"绝对地址"。为了让指针在多个进程中有效，必须确保所有进程都把视图映射到**相同的基址**。
2. **遗留系统集成**：某些老系统依赖固定地址
3. **特殊硬件交互**：某些硬件设备要求特定地址映射

**实现"跨进程指针"的正确方式**：

与其指定基地址，现代工业界更推荐**基于偏移的指针**（`__based` 指针）：

```
// 不安全的绝对指针
struct SharedData {
    int* ptr;  // 跨进程无效！
};

// 安全的基于偏移的指针
struct SharedData {
    DWORD offsetToData;  // 相对共享内存起始位置的偏移
};

// 进程 A 访问：
char* data = (char*)pSharedMem + sharedData->offsetToData;

// 进程 B 访问：
char* data = (char*)pSharedMem + sharedData->offsetToData;
// 同一个偏移在不同进程中指向相同数据
```

这种方法不需要指定基地址，因为偏移量在任何基址下都有效。

> ⚠️ **现代安全警告**：在启用 ASLR 的 Windows 10/11 上，指定基地址会触发系统的安全警告，且可能与 CET（Control-flow Enforcement Technology）等现代安全特性冲突。工业级代码应尽量避免。

## 17.10 内存映射文件的实现细节

### 第一性原理：从 Win32 API 到 NT 内核的 Section 对象

`CreateFileMapping` 在底层调用的是 NT 内核的 `NtCreateSection`——创建一个 **Section 对象**（段对象）。Section 对象是 Windows NT 内核中"内存映射文件"的核心抽象。

**完整的调用链**：

```
应用程序
    ↓ CreateFileMapping
Kernel32.dll
    ↓ NtCreateSection（系统调用）
NT 内核（ntoskrnl.exe）
    ↓ 创建 SECTION 对象
内存管理器（MM）
    ↓ 建立"文件 ↔ 虚拟地址空间"的关联
页表项（PTE）
    ↓ 访问时触发页错误
I/O 子系统
    ↓ 从磁盘读取数据页
磁盘驱动
    ↓ 物理磁盘
```

**五个关键实现细节**：

**1. 创建文件映射对象只是"预订"**

微软文档明确指出 ："Creating a file mapping object does not commit physical memory, it only reserves it." 这一步在内核中创建一个 SECTION 对象，但不分配任何物理页。

**2. MapViewOfFile 建立地址空间投影**

这一步在调用进程的地址空间中预订一段区域，并建立页表项指向 SECTION 对象。此时仍不分配物理页。

**3. 首次访问触发页错误**

当应用程序通过指针访问映射区域时，CPU 触发页错误。内存管理器：

- 分配物理页
- 从磁盘文件读取对应数据
- 更新页表项
- 重新执行被中断的指令

**4. 脏页回写**

修改后的页面被标记为"脏"。在以下时机写回磁盘 ：

- 调用 `FlushViewOfFile` 时
- 调用 `UnmapViewOfFile` 时
- 文件映射对象的所有句柄关闭时
- 系统内存压力导致页交换时

**5. 引用计数管理生命周期**

SECTION 对象有引用计数：

- 每调用一次 `MapViewOfFile`，引用计数 +1
- 每调用一次 `UnmapViewOfFile`，引用计数 -1
- 每调用一次 `CloseHandle(hMap)`，映射对象句柄计数 -1
- 当映射对象句柄计数为 0 且所有视图都已解除映射时，SECTION 对象被销毁

**写时复制的实现细节**​ ：

```
进程 A 以 FILE_MAP_COPY 映射文件：
   虚拟页 V1 → 物理页 P1（来自文件）
   P1 的保护属性：COPY-ON-WRITE

进程 A 写入 V1：
   ① CPU 触发页错误（因为 COPY-ON-WRITE）
   ② 内存管理器分配新物理页 P1'
   ③ 将 P1 的内容复制到 P1'
   ④ 将 V1 的页表项指向 P1'
   ⑤ P1' 的保护属性变为 READ/WRITE
   ⑥ P1' 的后备存储器变为页交换文件
   ⑦ 进程 A 的写入落在 P1' 上，原始文件 P1 不受影响
```

这就是为什么写时复制视图的修改：

- 对其他视图不可见（因为其他视图可能仍指向 P1）
- 永远不会写回原始文件（因为 P1' 的后备是页交换文件）
- 视图解除映射后丢失（因为 P1' 只存在于页交换文件中，且没有被任何文件引用）

**大页面的实现细节**（Windows 10 1703+） ：

- `SEC_LARGE_PAGES` 标志要求：
    - 调用者必须有 `SeLockMemoryPrivilege` 特权
    - 映射大小必须是 `GetLargePageMinimum()` 返回值的整数倍
    - 如果指定 `lpBaseAddress`，必须是大页最小值的整数倍
- 大页面映射的优势：
    - 减少 TLB 缺失
    - 提升大文件顺序访问性能
    - 适用于数据库缓冲池、科学计算

**远程文件和一致性**​ ：

微软文档明确指出 ："Although CreateFileMapping works with remote files, it does not keep them coherent." 远程文件映射在底层是通过网络重定向器实现的，多个机器对同一个文件的视图无法保持一致性。

### 工业实践

**1. 数据库引擎的缓冲池**：

- SQL Server、Oracle 在 Windows 上使用大页面 + 内存映射文件实现缓冲池
- 每个缓冲页是一个 8KB 的映射视图
- 脏页通过 `FlushViewOfFile` 或在取消映射时写回磁盘

**2. 现代进程间通信**：

- Chrome 浏览器大量使用命名共享内存进行渲染进程 ↔ 浏览器进程的通信
- 每个共享内存块是一个以页交换文件为后备存储器的内存映射对象（INVALID_HANDLE_VALUE）
- 配合事件、互斥量等同步原语

**3. 科学计算与大数据**：

- 基因组学数据分析：将数十 GB 的 FASTA 文件映射到内存，按需访问
- 时序数据库：将磁盘上的数据文件映射到内存，通过视图滑动窗口实现高效查询

**4. AI/ML 模型加载**：

- ONNX Runtime、PyTorch 在 Windows 上加载大模型时，使用内存映射文件
- 模型权重文件映射到虚拟地址空间，推理时按需调页
- 显著降低了内存峰值，避免了一次性加载全部参数

**5. .NET 9 的 MemoryMappedFile**：

- .NET 对 Win32 内存映射文件 API 做了完整封装
- `Microsoft.IO.MemoryMappedFiles.MemoryMappedFile` 类直接调用 `CreateFileMapping`/`MapViewOfFile`
- ASP.NET Core 的 Kestrel 服务器使用内存映射文件实现高效的静态文件服务
- GC 能够识别内存映射文件占用的页面，在内存压力时优先回收未修改的映射页面

> 💡 **洞见**：内存映射文件的实现细节揭示了 Windows NT 微内核架构的统一性——"一切皆对象"。文件是对象，进程是对象，线程是对象，**内存映射文件（Section 对象）也是对象**。这种统一性带来了巨大的工程优势：进程间共享内存、exe/DLL 加载、大文件访问、写时复制——这些看似不同的功能，底层都是同一个 Section 对象的变体。理解这一点，你就能看懂为什么 Windows 的架构如此优雅：通过一个核心抽象（Section 对象），统一解决了"如何让磁盘文件成为进程地址空间的一部分"这一根本问题。

## 章节联系：第17章是整个内存管理体系的"收官之作"

**与第13章（Windows 内存体系结构）的联系**：

- 内存映射文件是"物理存储器来自磁盘文件而非页交换文件"的直接应用
- Section 对象是 Windows 内存管理体系的核心抽象
- 写时复制是第13章"页面保护属性"的高级应用

**与第14章（探索虚拟内存）的联系**：

- `VMQuery` 可以观察内存映射文件的地址空间区域：保护属性为 `PAGE_READWRITE` 或 `PAGE_WRITECOPY`
- `GlobalMemoryStatusEx` 的 `ullAvailPageFile` 反映了以页交换文件为后备的映射对象对提交额度的影响
- `VirtualQuery` 返回的 `AllocationBase` 指向映射视图的起始地址

**与第15章（在应用程序中使用虚拟内存）的联系**：

- 第15章的 `VirtualAlloc`/`VirtualFree` 是"手动"管理虚拟内存
- 第17章的 `CreateFileMapping`/`MapViewOfFile` 是"自动"管理——系统根据文件内容自动调拨物理存储器
- `SEC_RESERVE` 标志允许创建"稀疏提交的内存映射文件"，结合 `VirtualAlloc` 的 `MEM_COMMIT` 实现动态提交

**与第16章（线程栈）的联系**：

- 线程栈用 `PAGE_GUARD` 保护页实现自动增长
- 内存映射文件用写时复制实现"共享代码的私有数据"
- 两者都是"虚拟内存机制 + 页面错误处理"的工程典范

**与第7章（线程同步）的联系**：

- 多进程访问同一内存映射文件时，必须用互斥量、信号量等同步原语协调
- 微软文档警告：共享内存中的指针、句柄在跨进程时无效，必须配合同步机制

**第一性原理的升华**：

第17章回答了系统编程的核心问题：**如何让文件成为内存的一部分？如何让多个进程安全地共享数据？**

六步法的第一性原理可以归纳为：

1. **间接层**：文件 ↔ Section 对象 ↔ 视图 ↔ 指针，每一层都是一次抽象
2. **惰性求值**：创建映射对象不提交物理内存，首次访问视图时才分配物理页
3. **统一抽象**：磁盘文件、页交换文件、exe/DLL 都是"后备存储器"
4. **基于物理页的共享**：同一物理页被映射到多个虚拟地址空间，实现一致性
5. **写时复制打破共享**：私有化物理页，实现"看起来共享，实际私有"

> 💡 **我的洞见**：内存映射文件是 Windows 虚拟内存机制最强大的应用，没有之一。它统一了"文件 I/O"、"进程间通信"、"代码共享"、"大文件处理"四大场景。Richter 在 2007 年讲的这套 API，到 2026 年依然是 Windows 系统编程不可替代的基石——.NET 的 `MemoryMappedFile`、Java 的 `MappedByteBuffer`、Rust 的 `memmap`、Python 的 `mmap` 模块，最终都落到 `CreateFileMapping`/`MapViewOfFile` 这一对 API 上。理解第17章，你就掌握了所有高级语言"零拷贝文件访问"和"高性能 IPC"的底层源代码。

### 工业实践的硬建议

1. **打开文件时用独占访问（dwShareMode=0）**——微软文档明确建议这是保证一致性的最简单方法
2. **零长度文件必须检查**——`CreateFileMapping` 会因 `ERROR_FILE_INVALID` 失败
3. **大文件必须分视图映射**——32 位进程地址空间有限，滑动窗口是唯一选择
4. **文件偏移必须对齐到分配粒度**——用 `GetSystemInfo` 获取，通常是 64KB
5. **多视图一致性是天然的**——同一映射对象的多个视图基于同一组物理页，修改实时同步
6. **跨网络禁止可写映射**——微软文档明确警告远程可写映射不保证一致性
7. **不要指定基地址**——微软文档明确说不推荐，ASLR 和 DLL 加载会冲突
8. **跨进程共享复杂数据结构用基于偏移的指针**——`__based` 指针或手动偏移计算，避免绝对指针
9. **关键数据显式调用 FlushViewOfFile**——内存映射文件不是事务性的，关键数据必须强制落盘
10. **清理顺序：Flush → Unmap → CloseHandle(hMap) → CloseHandle(hFile)**——微软示例代码的标准顺序
11. **不要用内存映射文件与传统 ReadFile/WriteFile 混用同一文件**——数据视图可能不一致
12. **64 位进程优选大页面映射**——`SEC_LARGE_PAGES` + `FILE_MAP_LARGE_PAGES` 提升大文件访问性能

> ⚠️ **2026 年现代延伸**：
> 
> - **Windows 11 24H2 的内存映射优化**：系统对 `PrefetchVirtualMemory` 做了智能化改进，能够识别复杂访问模式并主动预取，显著提升大文件随机访问性能。
> - **.NET 9 的 MemoryMappedFile 与 GC 深度集成**：GC 能够识别内存映射文件占用的页面，在内存压力时优先回收未修改的映射页面，而不触发页文件写入。ASP.NET Core 的 Kestrel 服务器使用内存映射文件实现高效的静态文件服务，单节点可支撑百万级并发静态文件请求。
> - **AI 大模型权重的零拷贝加载**：现代 AI 框架（ONNX Runtime、PyTorch on Windows）加载 GB 级模型权重时，使用内存映射文件避免一次性分配大量内存。模型推理时按需调页，显著降低了内存峰值。GPT-4 级别的模型在 Windows 上推理时，内存映射文件是标配技术。
> - **WSL2 的内存映射文件性能**：WSL2 通过 9P 协议访问 Windows 文件系统时，内存映射文件的性能显著下降。微软建议 WSL2 中的 Linux 应用程序访问位于 WSL2 虚拟磁盘中的文件以获得最佳内存映射性能。这是跨文件系统边界的已知限制。
> - **Rust 的 memmap2 crate**：Windows 上通过 `CreateFileMappingW` + `MapViewOfFile` 实现，是 Rust 生态中处理大文件的标准方案。Rust 的借用检查器在编译期就防止了"视图已解除映射后继续使用指针"的悬空指针问题。
> - **边缘计算与 IoT**：Windows IoT Enterprise 上运行的工业控制系统，使用内存映射文件在实时任务和非实时任务之间共享传感器数据，延迟低至微秒级。
> - **安全软件的挑战**：现代 EDR（端点检测与响应）软件会 hook `CreateFileMapping`/`MapViewOfFile` 等 API 进行安全扫描，这可能引入显著延迟。工业级程序在与 EDR 共存时需要进行性能测试，必要时使用 `FILE_FLAG_RANDOM_ACCESS` 等标志优化。
