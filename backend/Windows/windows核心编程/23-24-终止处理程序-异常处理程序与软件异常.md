
这两章是 Windows 系统编程的**"安全网之章"**——Richter 在前 22 章教会了我们如何管理内存、线程、DLL、注入；这两章要解决的终极问题是：**当一切失控时，如何让进程优雅地收拾残局？**​ 终止处理程序（`__try/__finally`）保证"清理代码必然执行"，异常处理程序（`__try/__except`）则决定"遇到错误时谁来接管、如何接管"。这两个机制通过"栈展开"（stack unwinding）紧密耦合——理解这一点，就理解了 Windows 错误处理的灵魂。

## 第23章 终止处理程序

### 第一性原理：无论 `__try` 块如何退出，`__finally` 块必然执行

终止处理程序的核心承诺极其简洁——**"保证清理代码的执行"**。微软官方文档的原话是："The `__try` and `__finally` keywords are used to construct a termination handler... The `__finally` block is executed whenever the flow of control leaves the `__try` block" 。

这意味着无论 `__try` 块是**正常落到结尾**、**执行了 `return/break/continue/goto`**、**发生了异常被上层 `__except` 接管**、还是**被 `longjmp` 跳转走**——`__finally` 块都会被执行 。

### 关键语义（基于微软官方文档）

**1. 异常终止 vs 顺序终止**

微软提供了 `AbnormalTermination()` 函数，在 `__finally` 块内调用可以判断 `__try` 块的退出方式 ：

- 返回 `0`：顺序终止——控制流自然到达 `__try` 块的结束大括号 `}`
- 返回非零：异常终止——因 `return/break/continue/goto/longjmp/异常` 离开 `__try` 块

**2. 三个"不执行 finally"的例外**

微软官方明确指出 ，如果在 `__try` 块中调用以下函数，`__finally` 块**不会**执行：

- `ExitProcess` —— 终止整个进程
- `ExitThread` —— 终止当前线程
- `abort` —— 异常终止程序

> 💡 **洞见**：这三个函数之所以绕过 finally，是因为它们本质上是"进程/线程的硬终止"——`ExitProcess` 直接杀掉进程，`abort` 调用 `raise(SIGABRT)` 后触发进程终止。finally 块的"保证执行"仅适用于"进程/线程继续存在"的场景。这是一个深刻的工程哲学：**清理代码的执行前提是进程还活着**。

**3. 全局展开（Stack Unwinding）中的 finally 执行顺序**

当异常在深层函数中发生时，系统会从异常发生点开始，**逆序遍历调用栈**，依次执行每个栈帧上注册的 `__finally` 块 。微软文档的经典图示：

```
函数 D 抛出异常
    ↓
异常被函数 A 的 __except 处理
    ↓
栈展开顺序：D 的 __finally → C 的 __finally → B 的 __finally
    ↓
最后执行 A 的 __except 块
```

**关键事实**：`__finally` 块**不阻断**异常搜索——它执行完清理后，异常继续向栈上传播，直到被某个 `__except` 处理 。

### `__leave`：避免"异常终止"性能惩罚的关键字

这是第23章最重要的性能洞见。微软文档明确警告 ：

> "Failure to terminate sequentially causes the system to search through all stack frames in reverse order to determine whether any termination handlers must be called. This can result in performance degradation due to the execution of hundreds of instructions."

**问题本质**：

- 如果 `__try` 块因 `return/break/continue/goto` 退出，系统视作"异常终止"
- 异常终止触发"局部展开"（local unwinding）——系统必须检查调用栈上是否有待执行的终止处理程序
- 这个过程需要执行数百条指令（x86 架构），RISC 架构上甚至需要数千条

**`__leave` 的解决方案**：

```
__try {
    // 使用 __leave 而不是 return/break/goto
    if (error_condition) {
        __leave;  // 立即跳到 __try 块末尾，视为"顺序终止"
    }
    // 正常逻辑...
}
__finally {
    // 清理代码
}
```

`__leave` 的语义是"**立即跳转到 `__try` 块的结束大括号**"，系统将其视为顺序终止，避免了局部展开的性能开销 。

### 第23章的工业实践模式

**1. 资源清理的标准惯用法**：

```
HANDLE hFile = INVALID_HANDLE_VALUE;
LPVOID pMem = NULL;

__try {
    hFile = CreateFile(...);
    if (hFile == INVALID_HANDLE_VALUE) __leave;
    
    pMem = VirtualAlloc(...);
    if (pMem == NULL) __leave;
    
    // 业务逻辑...
}
__finally {
    // 无论成功失败，资源都被清理
    if (pMem) VirtualFree(pMem, 0, MEM_RELEASE);
    if (hFile != INVALID_HANDLE_VALUE) CloseHandle(hFile);
    
    // 使用 AbnormalTermination() 判断是否需要特殊清理
    if (AbnormalTermination()) {
    }
}
```

**2. 错误码的传递模式**：

```
DWORD Func() {
    DWORD dwError = ERROR_SUCCESS;
    
    __try {
        if (/* 条件1 */) {
            dwError = ERROR_XXX;
            __leave;
        }
        if (/* 条件2 */) {
            dwError = ERROR_YYY;
            __leave;  // 使用 __leave 而非 return，避免局部展开
        }
        // 正常逻辑
    }
    __finally {
        // 清理资源
        CleanupResources();
    }
    
    return dwError;  // 在 __finally 之后返回
}
```

> ⚠️ **工业级建议**：永远不要在 `__finally` 块中使用 `return`——这会导致 `__finally` 块本身的"异常终止"，触发又一次局部展开 。正确的做法是：在 `__finally` 块中仅做清理，返回值在 `__finally` 块之后给出。

### 终止处理程序的现代定位

微软官方文档明确建议 ：

> "Structured exception handling works with Win32 for both C and C++ source files. However, it is not specifically designed for C++. You can ensure that your code is more portable by using C++ exception handling. Also, C++ exception handling is more flexible, in that it can handle exceptions of any type. For C++ programs, we recommend you use native C++ exception-handling: try, catch, and throw statements."

**现代工业实践**：

- **C++ 项目**：优先使用标准 C++ 异常（`try/catch/throw`）
- **系统级编程**：在需要与 Windows API 交互、捕获硬件异常（访问违规、除零等）时，使用 SEH
- **混合使用**：通过 `/EHa` 编译选项，使 C++ 异常和 SEH 异常能够互操作
- **插件/宿主场景**：宿主程序用 `__try/__except` 包裹插件调用，防止插件崩溃拖垮宿主

## 第24章 异常处理程序与软件异常

### 第一性原理：异常过滤器决定"谁来处理、如何处理"

`__try/__except` 的核心是一个**过滤器表达式（filter expression）**——它返回一个整数值，告诉系统如何处理异常 。微软文档明确给出了三种返回值 ：

|返回值|常量|数值|系统行为|
|---|---|---|---|
|继续执行|`EXCEPTION_CONTINUE_EXECUTION`|-1|忽略异常，从异常发生点**重新执行**​|
|继续搜索|`EXCEPTION_CONTINUE_SEARCH`|0|异常未被识别，向栈上**搜索下一个**处理函数|
|执行处理程序|`EXCEPTION_EXECUTE_HANDLER`|1|异常被识别，执行 `__except` 块，完毕后**从 `__except` 块之后继续**​|

### 24.1 通过实例理解异常过滤程序和异常处理程序

#### 24.1.1 Funcmeister1 函数

Richter 在书中用 `Funcmeister1` 演示了最基本的 `__except` 用法——过滤器表达式直接返回一个常量，决定"是否处理这个异常"。

**基本模式**：

```
void Funcmeister1() {
    __try {
        // 可能抛出异常的代码
        *((int*)0) = 0;  // 故意触发访问违规
    }
    __except (EXCEPTION_EXECUTE_HANDLER) {
        // 异常处理代码
        printf("异常被捕获！\n");
    }
    // 处理完毕后从这里继续执行
    printf("继续执行...\n");
}
```

**关键点**：

- 过滤器表达式 `EXCEPTION_EXECUTE_HANDLER` 直接告诉系统"我处理这个异常"
- 异常被处理后，控制流从 `__except` 块之后继续
- 如果 `__try` 块中没有异常发生，直接跳过 `__except` 块

#### 24.1.2 Funcmeister2 函数

`Funcmeister2` 演示了**过滤器表达式可以调用函数**——这是工业级异常处理的核心模式。

```
LONG ExceptionFilter(DWORD dwExceptionCode) {
    if (dwExceptionCode == STATUS_ACCESS_VIOLATION) {
        // 记录日志
        LogException("Access violation");
        return EXCEPTION_EXECUTE_HANDLER;
    }
    // 其他异常不处理，继续搜索
    return EXCEPTION_CONTINUE_SEARCH;
}

void Funcmeister2() {
    __try {
        // 可能抛出异常的代码
    }
    __except (ExceptionFilter(GetExceptionCode())) {
        // 异常处理
    }
}
```

**为什么要把过滤器逻辑放进函数**：

- 过滤器表达式本身的计算**发生在异常发生的瞬间**
- 复杂的过滤逻辑（日志记录、状态检查、条件判断）放在独立函数中更清晰
- 函数可以返回三个常量值中的任何一个，实现灵活的过滤策略

### 24.2 EXCEPTION_EXECUTE_HANDLER

#### 24.2.1 一些有用的例子

`EXCEPTION_EXECUTE_HANDLER` 是最常用的返回值——它表示"这个异常我处理了，执行 `__except` 块"。

**典型工业场景**：

```
__try {
    // 调用可能有问题的第三方库
    ThirdPartyLibrary_Call();
}
__except (EXCEPTION_EXECUTE_HANDLER) {
    // 第三方库崩溃了，但我们存活了下来
    fprintf(stderr, "Third-party library crashed: 0x%08X\n", 
            GetExceptionCode());
    // 使用备用方案
    FallbackImplementation();
}
```

**关键语义**：

- 当过滤器返回 `EXCEPTION_EXECUTE_HANDLER` 时，系统**先展开栈**（执行所有待执行的 `__finally` 块）
- 然后执行 `__except` 块
- 执行完毕后，从 `__except` 块之后的第一条指令继续

#### 24.2.2 全局展开

这是第24章最深刻的概念。当异常发生且过滤器返回 `EXCEPTION_EXECUTE_HANDLER` 时，系统必须**先展开调用栈**：

```
异常发生在函数 D
    ↓
函数 D 没有 __except，或过滤器返回 EXCEPTION_CONTINUE_SEARCH
    ↓
异常向栈上传播，检查函数 C
    ↓
函数 C 的过滤器返回 EXCEPTION_EXECUTE_HANDLER
    ↓
系统开始全局展开：
  1. 执行函数 D 的 __finally 块（如果有）
  2. 执行函数 C 的 __finally 块（如果有）
  3. 展开到函数 C 的 __except 块
    ↓
执行 __except 块，然后从 __except 块之后继续
```

微软文档的描述 ："During this process, the stack is unwound. That is, local non-static variables of terminated functions get cleared from the stack. As it unwinds the stack, the operating system calls any termination handlers that you've written for each function."

**全局展开的价值**：确保深层函数异常时，所有中间函数的资源都能被正确清理。这就是"栈展开"机制的精髓。

#### 24.2.3 停止全局展开

**关键洞见**：`__except` 块的过滤器返回 `EXCEPTION_EXECUTE_HANDLER` 时，**全局展开在该 `__except` 块处停止**——异常不会再向更上层的栈帧传播。

```
void DeepFunction() {
    __try {
        *((int*)0) = 0;  // 异常发生
    }
    __except (EXCEPTION_EXECUTE_HANDLER) {
        // 在这里处理异常，全局展开停止
        printf("异常在此处被完全处理\n");
    }
    // 从这里我们"恢复正常"，继续向上返回
    return;
}

void MiddleFunction() {
    DeepFunction();  // 如果 DeepFunction 处理了异常，这里不会感知到异常
    printf("DeepFunction 正常返回\n");
}
```

> 💡 **洞见**：这正是 SEH 与 C++ 异常的关键差异之一。C++ 异常一旦被 `catch` 捕获，异常对象就被销毁，传播停止；SEH 的 `EXCEPTION_EXECUTE_HANDLER` 同理——它在处理点"吸收"了异常，调用栈上的更外层 `__except` 永远不会看到这个异常。

### 24.3 EXCEPTION_CONTINUE_EXECUTION

#### 第一性原理：修复问题，从异常点重新执行

`EXCEPTION_CONTINUE_EXECUTION`（-1）告诉系统：**"异常已被过滤器修复，请从异常发生的那条指令重新开始执行"**​ 。

**典型工业场景**：

**1. 写时复制（Copy-on-Write）的软件实现**：

```
LONG COWFilter(LPEXCEPTION_POINTERS lpEP) {
    if (lpEP->ExceptionRecord->ExceptionCode == STATUS_ACCESS_VIOLATION) {
        // 获取违规地址
        PVOID faultAddr = (PVOID)lpEP->ExceptionRecord->ExceptionInformation[1];
        
        // 为这个地址分配可写内存（实现 COW 逻辑）
        VirtualProtect(faultAddr, PAGE_SIZE, PAGE_READWRITE, &oldProtect);
        
        // 返回 -1，重新执行导致异常的指令
        return EXCEPTION_CONTINUE_EXECUTION;
    }
    return EXCEPTION_CONTINUE_SEARCH;
}

__try {
    // 访问只读内存，触发异常
    *readonly_ptr = new_value;
}
__except (COWFilter(GetExceptionInformation())) {
    // 不会执行到这里，因为过滤器返回了 -1
}
```

**2. 垃圾回收器的"读屏障"**：

- GC 将对象标记为"待迁移"并设置内存保护
- 应用程序访问对象时触发异常
- 过滤器将对象迁移到新位置，更新指针
- 返回 `EXCEPTION_CONTINUE_EXECUTION` 重新执行

> ⚠️ **重要限制**：微软官方文档明确警告 ——"Some exceptions cannot be continued. If filter evaluates to -1 for such an exception, the system raises a new exception." 并非所有异常都可以"继续执行"——例如堆栈溢出（Stack Overflow）无法被修复和继续。

### 24.4 EXCEPTION_CONTINUE_SEARCH

#### 第一性原理：这个异常我不处理，让上层决定

`EXCEPTION_CONTINUE_SEARCH`（0）告诉系统：**"我不认识这个异常，请继续向调用栈的上层搜索处理函数"**​ 。

**典型工业场景**：

```
// 只处理访问违规，其他异常交给上层
__except (GetExceptionCode() == STATUS_ACCESS_VIOLATION ? 
          EXCEPTION_EXECUTE_HANDLER : EXCEPTION_CONTINUE_SEARCH) {
    // 只有访问违规才会执行到这里
}
```

**与异常代码过滤结合**：

```
__except (GetExceptionCode() == STATUS_INTEGER_DIVIDE_BY_ZERO ? 
          EXCEPTION_EXECUTE_HANDLER : EXCEPTION_CONTINUE_SEARCH) {
    // 仅处理除零异常
}
```

### 24.5 GetExceptionCode

`GetExceptionCode()` 是一个**编译器内联函数**（intrinsic），用于在过滤器表达式或 `__except` 块中获取异常代码 。

**常见异常代码**（来自 `winnt.h`）：

- `STATUS_ACCESS_VIOLATION` (0xC0000005) —— 访问违规
- `STATUS_INTEGER_DIVIDE_BY_ZERO` (0xC0000094) —— 除零
- `STATUS_STACK_OVERFLOW` (0xC00000FD) —— 栈溢出
- `STATUS_IN_PAGE_ERROR` (0xC0000006) —— 页错误
- `STATUS_NO_MEMORY` (0xC0000017) —— 内存不足

**使用限制**：

- 必须在 `__except` 的过滤器表达式中调用
- 也可以在 `__except` 块中调用
- **不能**在 `__finally` 块或普通函数中调用

### 24.6 GetExceptionInformation

`GetExceptionInformation()` 返回 `EXCEPTION_POINTERS` 结构指针，包含完整的异常上下文 ：

```
typedef struct _EXCEPTION_POINTERS {
    PEXCEPTION_RECORD ExceptionRecord;  // 异常记录
    PCONTEXT ContextRecord;             // 异常发生时的 CPU 上下文
} EXCEPTION_POINTERS, *PEXCEPTION_POINTERS;
```

**关键使用限制**（微软官方文档明确）：

> "You can use the `_exception_code` function within the exception handler. However, you can use `_exception_info` only within the exception filter. The information it points to is generally on the stack and is wiped out when control is transferred to the exception handler."

**这意味着**：

- `GetExceptionInformation()` **只能在过滤器表达式中调用**
- 一旦进入 `__except` 块，这些信息可能被栈展开清除
- 如果需要在 `__except` 块中使用 `EXCEPTION_POINTERS`，必须在过滤器表达式中将其保存到全局变量或局部变量中

```
EXCEPTION_POINTERS* g_pExceptionPointers = NULL;

__except (g_pExceptionPointers = GetExceptionInformation(), 
          EXCEPTION_EXECUTE_HANDLER) {
    // 现在可以使用 g_pExceptionPointers
    // 通过 ContextRecord 修改 CPU 寄存器状态
    // 通过 ExceptionRecord 获取异常详细信息
}
```

### 24.7 软件异常

#### 第一性原理：用 RaiseException 触发"结构化异常"

软件异常是通过 `RaiseException` API 手动触发的 SEH 异常 ：

```
VOID RaiseException(
    DWORD dwExceptionCode,      // 异常代码
    DWORD dwExceptionFlags,     // 异常标志
    DWORD nNumberOfArguments,   // 参数数量
    CONST ULONG_PTR* lpArguments // 参数数组
);
```

**典型用法**：

```
// 定义自定义异常代码（建议使用 0xE 前缀，表示软件异常）
#define MY_SOFTWARE_EXCEPTION 0xE0000001

__try {
    // 业务逻辑检测到错误条件
    if (invalid_state) {
        ULONG_PTR args[] = { (ULONG_PTR)"Invalid state detected" };
        RaiseException(MY_SOFTWARE_EXCEPTION, 0, 1, args);
    }
}
__except (GetExceptionCode() == MY_SOFTWARE_EXCEPTION ? 
          EXCEPTION_EXECUTE_HANDLER : EXCEPTION_CONTINUE_SEARCH) {
    // 处理自定义异常
    printf("捕获到自定义软件异常\n");
}
```

**软件异常 vs C++ 异常**：

- 软件异常是 Windows 操作系统的原生机制，跨语言兼容
- C++ 异常是 C++ 语言标准的机制，需要编译器支持
- 通过 `/EHa` 编译选项，两者可以互操作

## 章节联系：第23、24章是 Windows 错误处理的"双塔"

**与前面章节的联系**：

- **第22章（DLL 注入和 API Hook）**：注入的 DLL 必须使用 `__try/__except` 包裹其代码，防止 DLL 内部错误拖垮宿主进程。这是"插件隔离"的核心技术——宿主用 SEH 保护边界，插件崩溃不影响宿主。
- **第20章（DLL 高级技术）**：`DllMain` 中如果发生异常且未被处理，会导致整个进程崩溃。因此 `DllMain` 必须极其谨慎，或使用 SEH 保护。
- **第19章（DLL 基础）**：DLL 映射到进程地址空间后，其代码执行过程中的异常会影响整个进程。SEH 是"进程级错误隔离"的关键。
- **第7章（线程同步）**：在 `__finally` 块中释放锁、退出临界区，是确保异常情况下不发生死锁的标准模式。
- **第13-18章（内存管理）**：`__finally` 块中释放内存、关闭句柄、释放映射视图——SEH 是资源管理的"最后一道防线"。

**与后面章节的联系**（如果后面还有章节）：

- **未处理异常过滤器**：`SetUnhandledExceptionFilter` 是进程级的"最终异常处理器"
- **崩溃转储**：通过 `MiniDumpWriteDump` 在异常过滤器中生成 dump 文件
- **向量化异常处理（VEH）**：Windows XP 引入的 VEH 与 SEH 并存，VEH 优先级更高

### 第一性原理的升华

第23、24章回答了 Windows 编程的终极问题：**当代码失控时，如何保证系统的健壮性？**

SEH 机制的第一性原理可以归纳为：

1. **终止处理程序保证清理**：`__finally` 块在任何控制流离开 `__try` 时都执行（除了进程/线程硬终止）
2. **异常过滤器决定命运**：`__except` 的过滤器表达式返回三个值之一，决定"继续执行/继续搜索/执行处理程序"
3. **栈展开连接两者**：异常触发时，系统先逆序执行所有 `__finally` 块（清理资源），再执行匹配的 `__except` 块
4. **`__leave` 是性能优化的关键**：避免"异常终止"带来的局部展开开销
5. **软件异常桥接业务逻辑**：`RaiseException` 让应用程序可以触发"结构化异常"，与硬件异常统一处理
6. **`GetExceptionCode` 和 `GetExceptionInformation` 的时序约束**：前者在过滤器和 `__except` 块中都可用，后者只能在过滤器中使用

> 💡 **我的洞见**：第23、24章表面上讲的是"错误处理语法"，实质上揭示了 Windows 操作系统的**健壮性哲学**——"错误是不可避免的，但错误的后果是可以控制的"。这套机制的设计体现了几个深邃的工程决策：
> 
> **第一，清理与处理分离**。`__finally` 负责"无论发生什么都要执行的清理"，`__except` 负责"决定如何处理异常"。这种分离让程序员可以清晰地表达两种不同意图：资源清理是无条件的，而异常处理是有条件的。
> 
> **第二，过滤器表达式的强大**。`__except` 的过滤器不仅是一个布尔判断，它可以调用任意复杂的函数、修改 `CONTEXT` 记录、甚至修复导致异常的问题并返回 `EXCEPTION_CONTINUE_EXECUTION` 让程序从异常点继续执行。这种"在异常发生的瞬间拥有完全控制权"的能力，是 Windows 系统编程最强大的特性之一——它让"自修复程序"成为可能（如 COW、GC 读屏障、内存压缩等）。
> 
> **第三，`AbnormalTermination()` 暴露了实现的代价**。微软坦诚地告诉我们：非顺序终止会触发局部展开，带来数百条指令的开销。这种"诚实"的设计哲学让程序员能够做出明智的性能决策——使用 `__leave` 而非 `return/goto`。
> 
> **第四，SEH 是 Windows 生态的"通用错误语言"**。从硬件异常（访问违规、除零）到软件异常（`RaiseException`），从 C 代码到 C++ 代码，从用户态到内核态——SEH 提供了一致的错误处理机制。这就是为什么第22章的 DLL 注入、第20章的延迟加载、第19章的 DLL 基础，都建立在 SEH 之上：它是 Windows 系统的"免疫系统"。
> 
> Richter 在 2007 年讲 SEH 时，Windows 的异常处理机制已经基本成熟。今天，Windows 11 24H2 的 SEH 机制在底层原理上与 2007 年完全一致，但围绕它的安全生态发生了巨大变化：
> 
> - **向量化异常处理（VEH）**​ 在 Windows XP 引入，与 SEH 并存，VEH 优先级更高
> - **CFG（Control Flow Guard）**​ 验证了 SEH 的异常处理路径，防止异常处理器本身被劫持
> - **C++ 异常与 SEH 的互操作**：通过 `/EHa` 编译选项，C++ 异常和 SEH 异常能够统一处理
> - **崩溃转储与分析**：`MiniDumpWriteDump` + `SetUnhandledExceptionFilter` 成为工业级应用的标配
> 
> 这就是为什么第23、24章在今天依然是最具工程价值的章节——它教会你的不仅是 `__try/__except/__finally` 的语法，更是**如何设计一个"打不死的"Windows 应用程序**。

### 工业实践的硬建议

**1. 终止处理程序的最佳实践**：

- 在 `__finally` 块中**只做资源清理**，不做复杂逻辑
- 使用 `__leave` 而非 `return/goto` 离开 `__try` 块，避免局部展开开销
- 绝不在 `__finally` 块中使用 `return`——这会导致嵌套的局部展开
- 使用 `AbnormalTermination()` 判断是否需要特殊的清理逻辑

**2. 异常处理程序的最佳实践**：

- 过滤器表达式**尽量简单**，复杂逻辑放入独立函数
- 精确过滤异常代码：只处理你能处理的异常，其他用 `EXCEPTION_CONTINUE_SEARCH` 上交
- 在 `__except` 块中获取 `EXCEPTION_POINTERS` 时，必须在过滤器表达式中将其保存到变量
- 使用 `EXCEPTION_CONTINUE_EXECUTION` 时要极度谨慎——只有你能真正修复问题时才使用

**3. 现代 C++ 项目的 SEH 策略**：

- 优先使用 C++ 标准异常（`try/catch/throw`）
- 在系统级代码、与 Windows API 交互的边界处使用 SEH
- 通过 `/EHa` 编译选项启用 SEH 与 C++ 异常的互操作
- 使用 `SetUnhandledExceptionFilter` 作为进程级的"最后防线"

**4. 插件/宿主架构的 SEH 隔离**：

```
// 宿主程序调用插件时的 SEH 保护
__try {
    Plugin_Call();
}
__except (GenerateCrashDump(GetExceptionInformation()), 
          EXCEPTION_EXECUTE_HANDLER) {
    // 插件崩溃了，但宿主存活
    fprintf(stderr, "Plugin crashed: 0x%08X\n", GetExceptionCode());
    UnloadPlugin();  // 卸载崩溃的插件
}
```

> ⚠️ **2026 年现代延伸**：
> 
> - **Windows 11 24H2 的 SEH 安全增强**：CFG 验证了 SEH 异常处理器的调用目标，防止攻击者通过覆盖异常处理链实现代码执行。这意味着传统的"SEH 劫持"攻击（通过栈溢出覆盖异常处理记录）在现代 Windows 上已基本失效。
> - **Rust 与 SEH**：Rust 在 Windows 上使用 SEH 作为 panic 的底层机制。Rust 的 `panic!` 宏在 Windows 上触发 SEH 异常，通过 `catch_unwind` 可以捕获。这证明了 SEH 作为"系统级错误处理机制"的持久生命力。
> - **.NET 9 与 SEH**：.NET 的异常机制在 Windows 上映射到 SEH。CLR 通过 SEH 捕获硬件异常（如 NullReferenceException 对应 STATUS_ACCESS_VIOLATION），将其转换为托管异常。.NET 9 的 Native AOT 编译直接生成使用 SEH 的原生代码。
> - **崩溃分析工业标准**：现代工业级应用（Chrome、VS Code、Office）普遍使用 `SetUnhandledExceptionFilter` + `MiniDumpWriteDump` + Windows Error Reporting 实现崩溃收集和分析。这是第24章"软件异常"和"未处理异常过滤器"在现代 DevOps 中的直接应用。
> - **游戏行业的 SEH 应用**：游戏引擎（Unreal Engine 5、Unity）使用 SEH 保护渲染线程、物理线程等关键线程。当某个子系统崩溃时，SEH 确保游戏不退出，而是降级到"安全模式"或显示错误提示。
> - **AI 框架的 SEH 使用**：PyTorch、TensorFlow 在 Windows 上使用 SEH 捕获 GPU 内存访问违规、CUDA 错误等硬件级异常，转换为 Python 异常向上抛出。这使得 Python 训练脚本能够优雅处理底层硬件错误。
> - **eBPF on Windows 与 SEH 监控**：eBPF 可以 hook `RaiseException`、`RtlDispatchException` 等 SEH 核心函数，实时监控异常发生频率和类型，检测异常的恶意利用（如利用异常隐藏控制流）。
> - **向量化异常处理（VEH）的现代价值**：VEH 在 Windows XP 引入，与 SEH 并存且优先级更高 。现代反作弊系统（如 Riot Vanguard）使用 VEH 在异常发生的最早时刻介入，检测并利用异常处理机制进行反调试、反注入。这是第24章知识在现代安全攻防中的高级应用。
> - **C++ 异常与 SEH 的编译选项演进**：`/EHa`（异步异常模型）允许 C++ 异常捕获 SEH 异常；`/EHsc`（同步异常模型）是 C++ 标准异常；`/EHs`（无异常规范）是旧模型。现代 Visual C++ 默认使用 `/EHsc`，但系统级代码推荐使用 `/EHa` 以确保硬件异常能被 C++ `catch(...)` 捕获。
