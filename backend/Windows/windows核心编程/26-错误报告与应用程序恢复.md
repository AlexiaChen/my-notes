
第26章是 Windows 系统编程的**"工业级收官之章"**——前几章我们讲了帧异常处理（23）、进程级兜底的未处理异常过滤器（25）；这一章要解决的是**工程化问题**：当程序崩溃时，如何将"崩溃现场"标准化、分桶、上报、回收，形成一个**用户—系统—开发者**三方协作的闭环？Richter 在 2007 年讲这一章时，Windows Error Reporting（WER）刚在 Windows Vista 引入不久；今天，WER 已经成为 Windows 生态中**最具工业规模的遥测基础设施**——每天处理来自全球数十亿台设备的崩溃报告。

> 💡 **第一性原理**：错误报告不是一个"弹窗"，而是把"不可复现的崩溃"转化为"可复现的 bucket（分桶）"的标准化流水线。其核心命题是——**如何让用户的痛苦变成开发者的财富？**

## 26.1 Windows 错误报告控制台

### 第一性原理：从 Dr. Watson 到 WER 的范式跃迁

Windows XP 及更早版本的"Dr. Watson"只是一个本地的崩溃记录器。Windows Vista 开始，WER 彻底重构为**客户端-服务端**架构 ：

- **客户端**：`Wer.dll` + `WerSvc` 服务，负责检测崩溃、收集数据、构建报告、按策略提交
- **服务端**：WinQual（Windows Quality Online Services），负责分桶、聚合、分析、反馈解决方案

### WER 的默认行为（Windows 11 依然如此）

微软官方文档明确 ：**从 Windows Vista 开始，Windows 默认提供崩溃、无响应和内核错误的报告能力，无需应用程序做任何修改**。具体流程：

```
1. 问题事件发生（崩溃/无响应/内核错误）
2. 操作系统调用 WER
3. WER 收集数据，构建报告
4. 如需用户同意，弹出同意对话框
5. 用户同意后，WER 将报告发送至 Microsoft Watson 服务器
6. 服务端请求额外数据时，WER 再次收集并征求同意
7. 如果应用程序注册了恢复和重启，WER 在压缩和发送数据期间执行注册的回调函数
8. 如果 Microsoft 有该问题的解决方案，通知用户
```

**关键工程洞察**：

- **应用程序不应该自己处理致命异常**——这是微软官方给的明确建议
- 因为 Windows 会自动报告未处理异常，应用只需专注于"非致命错误"的自定义报告
- 无响应的判定标准：用户在尝试交互时，应用程序**5 秒内不响应 Windows 消息**​

### WER 控制台（wercon.exe）

用户可以通过 `Control Panel → Problem Reports and Solutions`（运行 `wercon.exe`）查看本机历史上所有的失败事件，检查问题是否已查明、是否有解决方案 。

### 工业现实：企业内 WER 部署

现代企业的典型 WER 配置 ：

- **本地 dump 收集**：通过注册表 `HKLM\SOFTWARE\Microsoft\Windows\Windows Error Reporting\LocalDumps` 配置，崩溃时在本地保存 full/mini dump
- **企业 WER 服务器**：通过 SCOM（System Center Operations Manager）+ AEM（Agentless Error Monitoring）将所有报告转发到企业内部监控服务器，而非 WinQual
- **隐私合规**：金融、医疗等行业需要配置"仅收集基本信息而不发送内存 dump"以满足监管要求

> ⚠️ **2026 年现代延伸**：Windows 11 24H2 的 WER 服务（`WerSvc`）默认启用且受到 VBS（基于虚拟化的安全）保护。企业 IT 管理员可以通过组策略精细控制 WER 行为——完全禁用、仅本地收集、或转发到企业内部服务器 。这对于符合 GDPR、HIPAA 等数据合规要求至关重要。

## 26.2 可编程的 Windows 错误报告

### 第一性原理：非致命错误也需要"上报通道"

WER 不仅处理崩溃，应用程序也可以利用 WER API 主动上报**非致命错误**​ 。这正是 Richter 在本节要阐述的核心——**把 WER 当作应用程序的"遥测通道"**。

### 两类 WER API

**1. 进程级注册函数**（影响系统自动生成的报告）：

|函数|作用|
|---|---|
|`WerRegisterFile`|注册错误报告时要收集的文件|
|`WerRegisterMemoryBlock`|注册要收集的内存块|
|`WerSetFlags`|设置当前进程的故障报告标志|
|`WerUnregisterFile`|取消文件注册|
|`WerUnregisterMemoryBlock`|取消内存块注册|
|`WerGetFlags`|获取故障报告设置|
|`WerAddExcludedApplication`|将应用排除在 WER 之外|
|`WerRemoveExcludedApplication`|恢复应用的错误报告|

**2. 自定义报告函数**（应用程序主动创建的报告）：

```
WerReportCreate → WerReportSetParameter → WerReportAddDump 
→ WerReportAddFile → WerReportSetUIOption → WerReportSubmit 
→ WerReportCloseHandle
```

### 关键设计哲学

微软官方文档明确指出 ："Because Windows automatically reports unhandled exceptions, application should not handle fatal exceptions."

这句话蕴含了深刻的工程哲学：

- **致命异常（崩溃、无响应）**：交给系统 WER 自动处理，应用不应干预
- **非致命错误（业务逻辑错误、可降级故障）**：应用主动创建自定义报告上报
- **这种分工**避免了"每个应用都自己发明崩溃报告"的碎片化

### 排除应用程序

如果开发者确定不需要 WER（极少情况），可以使用 ：

```
WerAddExcludedApplication(L"MyApp.exe", 0);  // 排除
WerRemoveExcludedApplication(L"MyApp.exe", 0);  // 恢复
```

> 💡 **工业洞见**：在现代 Windows 开发中，"排除 WER"几乎不再被推荐。相反，主流做法是**拥抱 WER**——通过 WinQual 注册获取自己产品的崩溃报告，或在企业内部部署 WER 转发服务器。这就是 Richter 在 2007 年预见的方向：**崩溃数据是企业最宝贵的资产之一**。

## 26.3 对进程中所有的问题报告进行定制

### 第一性原理：进程级 WER 设置的"全局影响"

本节 Richter 讲的是如何通过 `WerSetFlags` 等 API 为**整个进程**定制 WER 行为，而非单次报告。

### WerSetFlags 的标志位

```
typedef enum _WER_FAULT_REPORTING {
    WER_FAULT_REPORTING_INLINE = 0x10,  // 内联报告（不弹 UI）
    // ... 其他标志
} WER_FAULT_REPORTING;
```

**典型用法**：

```
// 设置当前进程的 WER 行为
WerSetFlags(WER_FAULT_REPORTING_INLINE);

// 获取当前设置
DWORD dwFlags;
WerGetFlags(GetCurrentProcess(), &dwFlags);
```

### 与"自定义报告"的区别

|维度|进程级设置（`WerSetFlags`）|自定义报告（`WerReportCreate`）|
|---|---|---|
|作用范围|整个进程的**所有**自动报告|单次**特定**报告|
|调用时机|进程启动早期，一次性设置|发生特定事件时按需创建|
|典型用途|设置全局行为（如禁用 UI）|上报具体的业务错误|
|API 组合|`WerSetFlags` + `WerRegisterFile` + `WerRegisterMemoryBlock`|`WerReportCreate` → `WerReportSubmit`|

### 工业实践

**大型应用程序的典型 WER 配置**：

```
// 应用启动时配置 WER
void ConfigureWER() {
    // 1. 注册要收集的文件（日志、配置文件等）
    WerRegisterFile(L"C:\\MyApp\\logs\\latest.log", 
                    WerRegFileTypeOther, 
                    WER_FILE_ANONYMOUS_DATA);
    
    // 2. 注册要收集的内存块（关键数据结构）
    WerRegisterMemoryBlock(&g_CriticalData, sizeof(g_CriticalData));
    
    // 3. 设置故障报告标志
    WerSetFlags(WER_FAULT_REPORTING_INLINE);
}
```

**Office、Visual Studio、Chrome 等工业级应用**都采用这种模式——它们在启动早期就注册 WER 文件收集器，确保崩溃时能拿到最完整的诊断信息。

## 26.4 问题报告的创建与定制

这是本章的**技术核心**——如何通过 WER API 创建一份自定义的、工业级的错误报告。完整流程 ：

```
WerReportCreate          → 创建报告句柄
WerReportSetParameter     → 设置报告参数（最多 10 个键值对）
WerReportAddDump         → 添加 mini dump
WerReportAddFile         → 添加任意文件
WerReportSetUIOption     → 修改对话框文本
WerReportSubmit          → 提交报告
WerReportCloseHandle     → 关闭报告句柄
```

### 26.4.1 创建一个自定义的问题报告

`WerReportCreate` 的官方签名 ：

```
HRESULT WINAPI WerReportCreate(
    PCWSTR pwzEventType,              // 事件类型名（必须在 WinQual 注册）
    WER_REPORT_TYPE repType,          // 报告类型
    PWER_REPORT_INFORMATION pReportInformation,  // 可选的报告信息
    HREPORT* phReportHandle            // 输出报告句柄
);
```

**`WER_REPORT_TYPE` 枚举**​ ：

|值|含义|进程行为|
|---|---|---|
|`WerReportNonCritical` (0)|非致命错误|不终止、不重启，静默排队|
|`WerReportCritical` (1)|致命错误（崩溃/无响应）|默认终止或重启进程|
|`WerReportApplicationCrash` (2)|应用崩溃|—|
|`WerReportApplicationHang` (3)|应用无响应|—|
|`WerReportKernel` (4)|内核错误|—|
|`WerReportInvalid` (5)|无效返回|—|

**关键约束**：

- 所有 WER 系列函数**仅支持 Unicode 字符串**
- `pwzEventType` 必须在 WinQual 网站注册过，否则报告无法正确分桶
- 返回值是 `HRESULT`，`S_OK` 表示成功

### 26.4.2 设置报告参数：WerReportSetParameter

**官方签名**​ ：

```
HRESULT WINAPI WerReportSetParameter(
    HREPORT hReportHandle,    // WerReportCreate 返回的报告句柄
    DWORD dwParamID,          // 参数索引（WER_P0 ~ WER_P9，共 10 个）
    PCWSTR pwzName,           // 可选的参数名
    PCWSTR pwzValue           // 参数值（Unicode 字符串）
);
```

**核心机制**：

- 每个自定义报告有**最多 10 个主键参数**（WER_P0 到 WER_P9）
- 这些参数构成报告的"签名"，用于**分桶（bucketing）**
- 相同签名的报告会被聚合到同一个 bucket，便于开发者分析高频问题

**工业级示例**：

```
WerReportSetParameter(hReport, WER_P0, L"EventType", L"DataProcessingError");
WerReportSetParameter(hReport, WER_P1, L"ErrorCode", L"0x80070057");
WerReportSetParameter(hReport, WER_P2, L"ModuleName", L"DataEngine.dll");
WerReportSetParameter(hReport, WER_P3, L"Version", L"3.2.1.456");
// ... 最多到 WER_P9
```

**次级参数（Secondary Parameters）**：

```
HRESULT WerReportAddSecondaryParameter(
    HREPORT hReportHandle,  // 报告句柄
    PCWSTR pwzKey,          // 参数名
    PCWSTR pwzValue         // 参数值
);
```

次级参数用于**添加品牌信息和自定义查询信息**，不影响分桶，但丰富报告的元数据 。

### 26.4.3 将小型转储文件放入报告：WerReportAddDump

**官方签名**​ ：

```
HRESULT WINAPI WerReportAddDump(
    HREPORT hReportHandle,              // 报告句柄
    HANDLE hProcess,                    // 进程句柄（需 PROCESS_QUERY_INFORMATION 权限）
    HANDLE hThread,                     // 线程句柄（用于获取调用栈）
    WER_DUMP_TYPE dumpType,             // dump 类型
    PWER_EXCEPTION_INFORMATION pExceptionParam,  // 异常信息
    PWER_DUMP_CUSTOM_OPTIONS pDumpCustomOptions, // 自定义选项
    DWORD dwFlags                       // 标志
);
```

**关键参数详解**：

- `hProcess`：通常是 `GetCurrentProcess()`，需有 `PROCESS_QUERY_INFORMATION` 权限
- `hThread`：通常是 `GetCurrentThread()`，WER 用它获取线程调用栈供事后调试
- `pExceptionParam`：包含 `PEXCEPTION_POINTERS`，结构如下：
    
    ```
    WER_EXCEPTION_INFORMATION wei;
    wei.bClientPointers = FALSE;  // 我们在进程内，所以传 FALSE
    wei.pExceptionPointers = pExceptionInfo;  // 来自 GetExceptionInformation()
    ```
    

**dump 类型**：

- `WerDumpTypeMicroDump`：仅包含堆栈跟踪
- `WerDumpTypeMiniDump`：标准 mini dump
- `WerDumpTypeHeapDump`：包含堆信息的扩展 dump
- `WerDumpTypeLargeDump`：大型 dump（含更多内存）

> 💡 **洞见**：`WerReportAddDump` 的精妙之处在于——它**内部调用 `MiniDumpWriteDump`**，但将 dump 文件的管理、压缩、传输全部委托给 WER 基础设施。开发者无需关心 dump 文件存储在哪里、如何传输、如何与 Microsoft 服务器协商。这就是"基础设施即服务"在操作系统层面的体现。

### 26.4.4 将任意文件放入报告：WerReportAddFile

**官方签名**​ ：

```
HRESULT WINAPI WerReportAddFile(
    HREPORT hReportHandle,  // 报告句柄
    PCWSTR pwzPath,         // 文件完整路径（可使用环境变量）
    WER_FILE_TYPE repFileType,  // 文件类型
    DWORD dwFileFlags       // 文件标志
);
```

**`WER_FILE_TYPE` 枚举**​ ：

|值|含义|
|---|---|
|`WerFileTypeMinidump`|小型转储文件|
|`WerFileTypeMicrodump`|仅含堆栈跟踪的有限 dump|
|`WerFileTypeHeapdump`|含进程内存的扩展 mini dump|
|`WerFileTypeOther`|任意其他文件（始终加入 cab，但仅当服务器请求时）|
|`WerFileTypeUserDocument`|事件发生时应用程序正在使用的文档（仅当服务器请求时添加）|

**`dwFileFlags` 标志**：

- `WER_FILE_ANONYMOUS_DATA`：文件不含个人身份信息
- `WER_FILE_DELETE_WHEN_DONE`：报告提交后自动删除文件

**典型用法**：

```
// 添加日志文件
WerReportAddFile(hReport, L"%APPDATA%\\MyApp\\logs\\error.log", 
                 WerFileTypeOther, 
                 WER_FILE_ANONYMOUS_DATA | WER_FILE_DELETE_WHEN_DONE);

// 添加用户文档（需谨慎，涉及隐私）
WerReportAddFile(hReport, L"C:\\Docs\\important.docx", 
                 WerFileTypeUserDocument, 
                 0);
```

> ⚠️ **隐私警告**：`WerFileTypeUserDocument` 涉及用户文档，微软官方明确——如果文件存储在加密文件系统（EFS）上，此组合不被支持 。工业级应用在处理用户文档时必须格外小心，确保符合隐私法规。

### 26.4.5 修改对话框文本：WerReportSetUIOption

`WerReportSetUIOption` 允许开发者**定制 WER 显示给用户的交互对话框文本**​ ：

```
HRESULT WINAPI WerReportSetUIOption(
    HREPORT hReportHandle,
    WER_REPORT_UI repUIType,
    PCWSTR pwzValue
);
```

**可定制的 UI 元素**：

- 对话框标题
- 问题描述文本
- "提交"按钮文本
- "不提交"按钮文本
- 隐私声明链接

**工业价值**：让用户看到**应用程序品牌化的错误对话框**，而非冷冰冰的"应用程序已停止工作"。这极大提升了用户体验——用户感觉"开发者在乎这个问题"。

### 26.4.6 提交错误报告：WerReportSubmit

```
HRESULT WINAPI WerReportSubmit(
    HREPORT hReportHandle,
    WER_CONSENT consent,
    DWORD dwFlags,
    PBWER_SUBMIT_RESULT pSubmitResult
);
```

**`WER_CONSENT` 枚举**：

- `WerConsentAlwaysPrompt`：总是询问用户
- `WerConsentMaximum`：基于系统策略

**`dwFlags` 关键标志**：

- `WER_SUBMIT_HONOR_RESTRICTION`：遵守系统限制
- `WER_SUBMIT_OUTOFPROCESS`：在 WER 服务进程外处理
- `WER_SUBMIT_NO_ARCHIVE`：不存档
- `WER_SUBMIT_ARCHIVE_PARAMETERS_ONLY`：仅存档参数

**提交流程的行为**​ ：

- 根据标志不同，Windows 可能将报告放入队列、提示用户发送、或直接发送
- 如果系统策略要求用户同意，会弹出同意对话框
- 报告发送后，WinQual 服务端会进行分桶处理

### 26.4.7 关闭问题报告：WerReportCloseHandle

```
HRESULT WINAPI WerReportCloseHandle(HREPORT hReportHandle);
```

**关键工程纪律**：

- 与所有 Windows 句柄一样，报告句柄必须显式关闭
- 即使在 `WerReportSubmit` 之后，也必须调用 `WerReportCloseHandle`
- 忘记关闭会导致资源泄漏

### 26.4.8 Customized WER 示例程序

Richter 在书中提供了一个完整的自定义 WER 示例。基于微软官方文档和 WER API 的标准用法，重建这个示例的核心结构：

```
// 完整的自定义 WER 报告流程
void GenerateCustomErrorReport(DWORD dwExceptionCode, 
                                PEXCEPTION_POINTERS pExInfo) {
    // 1. 创建报告
    HREPORT hReport;
    WER_REPORT_INFORMATION werInfo = { sizeof(WER_REPORT_INFORMATION) };
    wcscpy_s(werInfo.wzFriendlyAppName, L"My Application");
    
    HRESULT hr = WerReportCreate(
        L"MyCustomErrorEvent",           // 必须在 WinQual 注册的事件类型
        WerReportCritical,               // 致命错误
        &werInfo,
        &hReport
    );
    if (FAILED(hr)) return;
    
    // 2. 设置报告参数（用于分桶）
    WerReportSetParameter(hReport, WER_P0, L"ExceptionCode", 
                          L"0xC0000005");
    WerReportSetParameter(hReport, WER_P1, L"Module", L"MyApp.exe");
    WerReportSetParameter(hReport, WER_P2, L"Version", L"1.0.0.1");
    
    // 3. 添加 mini dump
    WER_EXCEPTION_INFORMATION werExInfo;
    werExInfo.bClientPointers = FALSE;
    werExInfo.pExceptionPointers = pExInfo;
    
    WerReportAddDump(hReport, 
                     GetCurrentProcess(), 
                     GetCurrentThread(),
                     WerDumpTypeMiniDump, 
                     &werExInfo, 
                     NULL, 
                     0);
    
    // 4. 添加日志文件
    WerReportAddFile(hReport, 
                     L"%APPDATA%\\MyApp\\error.log",
                     WerFileTypeOther,
                     WER_FILE_ANONYMOUS_DATA | WER_FILE_DELETE_WHEN_DONE);
    
    // 5. 定制 UI 文本
    WerReportSetUIOption(hReport, WerUIAdditionalText, 
                         L"我们非常重视此错误，您的报告将帮助我们改进产品。");
    
    // 6. 提交报告
    WER_SUBMIT_RESULT submitResult;
    WerReportSubmit(hReport, WerConsentMaximum, 
                    WER_SUBMIT_HONOR_RESTRICTION, &submitResult);
    
    // 7. 关闭报告句柄
    WerReportCloseHandle(hReport);
}
```

> 💡 **工业洞见**：这个看似简单的 7 步流程，背后是微软 20 年崩溃报告经验的结晶。每一个 API 调用都对应着崩溃报告流水线的关键环节：
> 
> - `WerReportCreate` → 创建"报告对象"
> - `WerReportSetParameter` → 定义"分桶签名"
> - `WerReportAddDump` → 捕获"崩溃现场"
> - `WerReportAddFile` → 附加上下文
> - `WerReportSetUIOption` → 用户沟通
> - `WerReportSubmit` → 传输
> - `WerReportCloseHandle` → 资源清理
> 
> 现代工业级应用（如 Visual Studio、Office、Chrome）都实现了类似的完整流程，并叠加了自己的"崩溃恢复"逻辑。

## 26.5 应用程序的自动重启与恢复

### 第一性原理：崩溃后用户体验的"连续性"

WER 不仅报告错误，还提供**应用程序恢复与重启（Application Recovery and Restart, ARR）**机制 。核心命题：**让用户不因软件崩溃而丢失工作**。

### 26.5.1 应用程序的自动重启

**`RegisterApplicationRestart` 的官方签名**​ ：

```
HRESULT RegisterApplicationRestart(
    PCWSTR pwzCommandLine,  // 重启时的命令行参数
    DWORD dwFlags           // 重启限制标志
);
```

**关键行为**​ ：

- WER 会在应用程序崩溃或无响应后自动重启它
- **前提条件**：应用程序必须已运行**至少 60 秒**
- 重启时，系统会将 `pwzCommandLine` 指定的参数传递给应用程序

**`RestartRestrictions` 枚举**：

```
enum RestartRestrictions {
    None = 0,           // 所有情况都重启
    NotOnCrash = 1,     // 崩溃时不重启
    NotOnHang = 2,      // 无响应时不重启
    NotOnPatch = 4,     // 打补丁时不重启
    NotOnReboot = 8     // 重启时不重启
};
```

**典型用法**：

```
// 注册重启，并传递 /restart 参数
RegisterApplicationRestart(L"/restart", RestartRestrictions::None);

// 应用程序入口点
int main(int argc, char* argv[]) {
    // 检查是否因崩溃重启
    if (argc > 1 && strcmp(argv[1], "/restart") == 0) {
        // 执行恢复逻辑
        RestorePreviousState();
    }
    // ...
}
```

**配套 API**：

- `UnregisterApplicationRestart()`：取消重启注册
- `GetApplicationRestartSettings()`：获取当前重启设置

### 26.5.2 对应用程序恢复的支持

**核心 API 三角**​ ：

```
// 1. 注册恢复回调
HRESULT RegisterApplicationRecoveryCallback(
    APPLICATION_RECOVERY_CALLBACK pRecoverFunc,  // 回调函数
    LPVOID pvParameter,                         // 传给回调的参数
    DWORD dwPingInterval,                       // Ping 间隔（毫秒）
    DWORD dwFlags                               // 标志（保留）
);

// 2. 通知系统恢复仍在进行中
HRESULT ApplicationRecoveryInProgress(
    PBOOL pbCancelled  // 输出：用户是否取消了恢复
);

// 3. 通知系统恢复完成
void ApplicationRecoveryFinished(
    BOOL bSuccess  // TRUE=恢复成功，FALSE=恢复失败
);
```

**`APPLICATION_RECOVERY_CALLBACK` 回调签名**：

```
DWORD WINAPI RecoveryRoutine(LPVOID lpParam);
```

**完整的恢复实现模式**​ ：

```
// 恢复回调实现
DWORD WINAPI MyRecoveryCallback(LPVOID lpParam) {
    bool bCancelled;
    
    // 1. 启动"心跳"定时器，定期通知系统恢复仍在进行
    while (true) {
        // 检查用户是否取消
        ApplicationRecoveryInProgress(&bCancelled);
        if (bCancelled) {
            // 用户取消了恢复，立即退出
            ApplicationRecoveryFinished(FALSE);
            return 0;
        }
        
        // 2. 保存应用程序状态
        SaveApplicationState();  // 保存用户文档、窗口位置、编辑历史等
        
        // 3. 更新重启命令行参数（包含恢复所需的上下文）
        RegisterApplicationRestart(L"/restart /session=12345", 
                                   RestartRestrictions::None);
        
        // 4. 模拟耗时操作的心跳
        Sleep(1000);  // 实际工作中应分块保存，每块后 ping 一次
        
        // 假设保存完成
        break;
    }
    
    // 5. 通知系统恢复完成
    ApplicationRecoveryFinished(TRUE);
    return 0;
}

// 应用程序启动早期注册
void SetupRecovery() {
    RegisterApplicationRecoveryCallback(
        MyRecoveryCallback,
        NULL,
        5000,  // 每 5 秒 ping 一次
        0
    );
    
    RegisterApplicationRestart(L"/restart", RestartRestrictions::None);
}
```

**Ping 机制的重要性**：

- `dwPingInterval` 指定了应用程序必须调用 `ApplicationRecoveryInProgress` 的频率
- 如果超过 `dwPingInterval` 时间未 ping，WER 认为应用程序恢复卡死，**强制终止**
- 这是防止"恢复回调死锁导致进程无法终止"的安全机制

### 工业级 ARR 实践

**1. Microsoft Office**：

- 崩溃时自动保存文档到 ASD 文件
- 重启后自动提示恢复未保存的文档
- 使用 ARR API 实现"文档恢复"功能

**2. Google Chrome**：

- 渲染进程崩溃后，浏览器进程自动重启渲染进程
- 使用 `RegisterApplicationRestart` 实现渲染进程自愈
- 标签页状态通过会话恢复机制保存

**3. Visual Studio**：

- 崩溃时自动保存未提交的更改
- 重启后恢复打开的文档和断点

**4. Adobe Photoshop**：

- 崩溃时保存 PSD 备份
- 重启后提示恢复

> 💡 **工业洞见**：ARR 机制的设计哲学是——**崩溃是不可避免的，但用户数据的丢失是可以避免的**。这个哲学与 Richter 在第23章强调的"终止处理程序保证清理"一脉相承，但提升到了**进程级、用户感知**的高度。
> 
> ARR 的三个关键设计决策：
> 
> 1. **60 秒门槛**：避免"启动即崩溃、立即重启、再崩溃"的无限循环
> 2. **Ping 机制**：防止恢复回调本身卡死
> 3. **命令行参数传递**：让重启后的应用知道"我是被崩溃重启的"，从而执行恢复逻辑
> 
> 这三点构成了健壮的"崩溃-恢复-重启"闭环。

## 章节联系：第26章是整本书的"工业化出口"

**与第25章（未处理异常、VEH、C++ 异常）的联系**：

- 第25章的 `SetUnhandledExceptionFilter` 是进程级崩溃的"最后防线"
- 第26章的 WER 是系统级崩溃的"工业级管道"
- 两者的关系：**`SetUnhandledExceptionFilter` 在进程内捕获异常 → 调用 `WerReportCreate` 等 API 创建自定义报告 → WER 基础设施负责传输和分析**
- 现代工业实践：**不要自己处理致命异常**，让 WER 自动捕获；仅在需要上报非致命错误时使用自定义 WER 报告

**与第23、24章（SEH）的联系**：

- `WerReportAddDump` 内部调用 `MiniDumpWriteDump`，而 `MiniDumpWriteDump` 需要 `EXCEPTION_POINTERS`——这正是第24章 `GetExceptionInformation()` 返回的结构
- 在 `UnhandledExceptionFilter` 中调用 `WerReportAddDump` 时，`bClientPointers` 必须设为 `FALSE`（因为我们在进程内）

**与第22章（DLL 注入）的联系**：

- 注入的 DLL 如果崩溃，会触发宿主进程的 WER 报告
- 插件开发者**不应该**调用 `SetUnhandledExceptionFilter`（会破坏宿主的崩溃处理），而应该：
    - 使用 `__try/__except` 隔离插件代码
    - 或使用 WER 的 `WerRegisterFile` 注册插件特定的日志文件

**与第7章（线程同步）的联系**：

- 在恢复回调 `ApplicationRecoveryInProgress` 期间，应用程序的其他线程可能仍在运行
- 恢复回调必须安全地访问应用程序状态，可能需要同步机制
- 如果恢复回调需要获取锁，必须确保不会发生死锁

### 第一性原理的升华

第26章回答了 Windows 编程中**最具工业价值**的问题：**如何让崩溃成为产品改进的燃料？**

WER 与 ARR 机制的第一性原理可以归纳为：

1. **崩溃数据的标准化**：通过 `WerReportSetParameter` 定义分桶签名，让相同根因的崩溃聚合同一个 bucket
2. **崩溃现场的完整捕获**：`WerReportAddDump` + `WerReportAddFile` 确保开发者拿到分析所需的全部信息
3. **用户参与的温和化**：`WerReportSetUIOption` 让错误对话框从"冷冰冰的崩溃"变成"有温度的反馈"
4. **提交策略的灵活性**：`WerReportSubmit` 根据用户策略、企业策略、系统策略决定何时、如何提交
5. **崩溃后的连续性**：ARR 机制通过 `RegisterApplicationRestart` + `RegisterApplicationRecoveryCallback` 实现"崩溃-恢复-重启"的用户无感闭环
6. **基础设施的服务化**：WER 将"崩溃报告"这件复杂的事（收集、压缩、传输、存储、分析、反馈）完全基础设施化，开发者只需关注"上报什么"

> 💡 **我的洞见**：第26章表面上讲的是"错误报告 API"，实质上揭示了微软的**产品哲学**——**用户的痛苦是产品最大的资产**。这个哲学体现在：
> 
> **第一，崩溃不再是终点，而是起点**。传统软件工程中，崩溃意味着"失败"。WER 把这个叙事颠覆了——崩溃是"用户愿意帮助开发者改进产品的时刻"。每一次崩溃报告的上传，都是用户与开发者的一次协作。
> 
> **第二，分桶（bucketing）是数据驱动的灵魂**。通过 `WER_P0`~`WER_P9` 十个参数构成的签名，WER 服务端能够将海量崩溃报告聚合成有限的 bucket。开发者看到的不是"100 万个崩溃报告"，而是"3 个主要 bucket，分别占 60%、30%、10%"。这直接指导了 bug 修复的优先级——这就是数据驱动开发的精髓。
> 
> **第三，ARR 机制是对"脆弱性"的工程承认**。软件必然有 bug，进程必然会崩溃。与其假装"我的软件不会崩"，不如坦诚接受并建立"崩溃后恢复"的机制。这是 Windows 生态系统 20 年来最务实的工程智慧。
> 
> **第四，隐私与诊断的精细平衡**。`WerFileTypeUserDocument` + EFS 的限制、`WER_FILE_ANONYMOUS_DATA` 标志、企业内 WER 转发服务器——微软在"诊断价值"与"用户隐私"之间建立了精细的控制面。这对今天 GDPR、HIPAA 等合规要求具有前瞻性。
> 
> Richter 在 2007 年讲这一章时，WER 还在早期阶段，WinQual 还在用旧的"Windows Quality Online Services"品牌。今天，WER 已经演变为：
> 
> - **Windows 11 24H2**：WER 服务（`WerSvc`）受 VBS 保护，崩溃报告的完整性得到虚拟化安全增强
> - **Microsoft App Center / Visual Studio App Center**：提供现代化的崩溃分析仪表板
> - **BugSplat、Sentry 等第三方服务**：基于 WER 的 `WerReportCreate` API 构建企业级崩溃管理
> - **AI 驱动的崩溃分析**：Microsoft 使用机器学习对 bucket 进行自动聚类、根因分析、相似问题匹配

### 工业实践的硬建议

**1. 现代 Windows 应用的 WER 最佳实践**：

```
// 应用程序启动早期
void InitializeWER() {
    // 注册要收集的日志文件
    WerRegisterFile(g_szLogPath, WerRegFileTypeOther, 
                    WER_FILE_ANONYMOUS_DATA);
    
    // 注册关键内存块
    WerRegisterMemoryBlock(&g_CriticalState, sizeof(g_CriticalState));
    
    // 设置故障报告标志（内联报告，不弹 UI）
    WerSetFlags(WER_FAULT_REPORTING_INLINE);
    
    // 注册应用程序恢复和重启
    RegisterApplicationRecoveryCallback(
        MyRecoveryCallback, NULL, 5000, 0);
    RegisterApplicationRestart(L"/restart", 
                               RestartRestrictions::None);
}
```

**2. 自定义非致命错误上报**：

- 对于可降级、可恢复的业务错误，使用 `WerReportCreate` 主动上报
- 不要滥用——仅上报对产品改进有价值的错误
- 使用有意义的 `pwzEventType` 并在 WinQual 注册

**3. 崩溃恢复的设计原则**：

- **频繁保存**：不要依赖崩溃时的恢复回调做"全量保存"，平时就应定期持久化状态
- **快速恢复**：恢复回调应在 `dwPingInterval` 内完成一次 ping，避免长时间操作
- **用户可取消**：定期检查 `ApplicationRecoveryInProgress` 的 `pbCancelled` 输出
- **重启参数传递**：通过 `RegisterApplicationRestart` 的命令行参数传递恢复所需的上下文

**4. 企业部署建议**：

- 配置本地 dump 收集（`HKLM\...\Windows Error Reporting\LocalDumps`）
- 对于敏感行业，将 WER 转发到企业内部服务器而非 Microsoft
- 使用组策略统一管理 WER 行为

> ⚠️ **2026 年现代延伸**：
> 
> - **Windows 11 24H2 的 WER 与 VBS**：基于虚拟化的安全将 WER 服务的关键组件置于安全 enclave 中，防止恶意软件篡改崩溃报告。这使得 WER 报告本身成为"可信诊断通道"。
> - **AI 驱动的崩溃分析**：Microsoft 使用 Transformer 模型对 bucket 进行语义聚类，自动识别"看似不同但根因相同"的崩溃。开发者在 WinQual 中看到的 bucket 建议已经是 AI 辅助的结果。
> - **Rust 与 WER**：Rust 程序在 Windows 上的 `panic` 机制可以桥接到 WER——通过 `set_unhandled_exception_filter` 捕获 Rust panic，转换为 SEH 异常，再由 WER 收集。这证明了 WER 作为"系统级崩溃基础设施"对现代语言的普适性。
> - **.NET 9 与 WER**：.NET 的 `System.Environment.FailFast` 直接触发 WER 报告。.NET 9 的 Native AOT 编译程序可以使用完整的 WER API，与 C++ 程序享受同等水平的崩溃诊断。
> - **游戏行业的 ARR 实践**：Unreal Engine 5 使用 `RegisterApplicationRestart` 实现渲染线程崩溃后的游戏重启；使用 `RegisterApplicationRecoveryCallback` 在崩溃时保存玩家进度。这是 ARR 在工业级实时应用中的典范。
> - **Chromium 的 WER 架构**：Chrome 的多进程模型完美契合 WER——每个渲染进程独立注册 WER，崩溃时不影响浏览器主进程。Chrome 还使用 `WerRegisterFile` 注册各渲染进程的日志，使得崩溃分析可以精确到具体标签页。
> - **eBPF on Windows 与 WER 监控**：eBPF 可以 hook `WerReportSubmit`、`WerReportCreate` 等 WER API，实时监控应用程序的错误上报行为。在企业环境中，这可以检测"恶意软件模拟 WER 报告"的伪装行为。
> - **MITRE ATT&CK 中的 WER 滥用**：T1543.004 (Create or Modify System Process) 等技术涉及对 WER 配置的篡改。理解第26章的机制，有助于安全分析师识别这类攻击——例如，攻击者修改 `LocalDumps` 注册表项以窃取其他进程的 crash dump。
> - **崩溃报告的合规边界**：在欧盟 GDPR 框架下，crash dump 可能包含个人数据（如用户输入、文档内容）。工业级应用必须在 `WerReportAddFile` 时使用 `WER_FILE_ANONYMOUS_DATA` 标志，或在企业内 WER 服务器中实施数据脱敏。这是第26章知识在现代合规环境下的必备延伸。
