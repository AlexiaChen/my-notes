
第3章是整个 Windows 编程模型的奠基之石。前两章我们讲了"错误"和"字符串"——它们是函数边界和文化边界上的状态显式化；这一章更进一步：**内核对象是"资源边界"上的状态显化**，而句柄是进程通往内核资源的"受控入口"。理解这一章，关键是抓住一句话——**Windows 不是一个把资源直接给你的系统，而是一个让你通过"句柄"间接接触资源的系统**。这套间接层，就是 Windows 安全性、稳定性和扩展性的根源。

## 3.1 何为内核对象

### 第一性原理视角

内核对象的本质是：**内核态内存里的一块数据结构，由对象管理器（Object Manager）统一管理，用户态只能通过句柄间接访问**。

为什么需要这一层间接？三个底层原因：

1. **隔离性**：应用程序不能随便篡改内核数据结构，否则一个野指针就能搞崩整个系统。所有对内核对象的操作，必须经过内核代码走完权限检查后执行。
2. **统一性**：进程、线程、文件、事件、互斥量、信号量、作业、令牌……几十种资源，共用同一套生命周期、安全描述符、引用计数框架。这就是 NT 对象管理器被称为"executive component"的原因——它是管"对象"这个概念的行政层。
3. **跨边界**：内核对象可以被命名、被跨进程共享、被导出到用户态。这是用户对象和 GDI 对象做不到的——后两者的句柄是"系统范围/session 范围"有效的，而内核对象的句柄是"进程私有"的。

**判断一个对象是不是内核对象，最简单的方法**：看创建它的 API 有没有 `SECURITY_ATTRIBUTES*` 参数。几乎所有这些创建函数都有这个参数，因为内核对象受安全描述符保护；而 `CreateIcon`、`CreateMenu` 这类用户对象/GDI 对象创建函数则没有。

### 3.1.1 使用计数

书里讲的"使用计数"（usage count），在现代 NT 内核里其实是**两个独立的计数器**：

- **HandleCount**：用户态句柄的数量
- **PointerCount**：内核态指针引用的数量

对象只有在**两个计数都归零**时才被销毁。这个细节非常关键——它解释了为什么内核对象可以"比创建它的进程活得更久"：即使所有用户态句柄都关了，只要内核某处还拿着一个指针引用（比如一个未完成的 I/O 请求），对象就不会被释放。这在异步 I/O 场景里是保障数据完整性的基石。

我们可以用调试器直观看到这两个计数。对 `\BaseNamedObjects\AgentToWkssvcEvent` 这个事件对象做 `!object` 调试器扩展，能看到：

```
HandleCount: 2
PointerCount: 3
```

这说明该事件对象当前有 2 个用户态句柄在引用，同时有 3 处内核指针在引用。

> 💡 **工程洞见**：HandleCount 和 PointerCount 的双计数设计，本质上是在分离"用户态视角"和"内核态视角"。这套机制让 Windows 能在用户关闭句柄后，依然安全地完成正在进行的 I/O 操作——因为内核自己还握着一个 PointerCount 引用。**这就是为什么 Windows 的异步 I/O 模型如此健壮**：你关掉文件句柄，不代表磁盘读写会立即终止，内核会等它完成才真正释放。

### 3.1.2 内核对象的安全性

每个内核对象都带一个**安全描述符（Security Descriptor, SD）**：

- **DACL**（自主访问控制列表）：决定哪些用户/组可以对该对象做什么操作
- **SACL**（系统访问控制列表）：决定哪些操作会被审计记录
- **Owner SID / Group SID**：对象的所有者

创建内核对象时传入的 `SECURITY_ATTRIBUTES` 结构体里，`lpSecurityDescriptor` 字段就指向这个 SD。绝大多数应用程序传 `NULL`，意味着使用默认安全描述符——其具体权限取决于当前进程的安全令牌。

**安全设计的精妙之处**：权限检查发生在**句柄创建的那一刻**。也就是说，当你调用 `CreateFile` 打开一个文件时，系统会检查你的令牌是否有相应权限，然后把"已验证的访问权"记录在句柄表项里（`GrantedAccess` 字段）。之后你用这个句柄去 `ReadFile`、`WriteFile`，系统**不再重复检查 ACL**——它只看句柄表项里记录的 GrantedAccess。这是一个典型的"一次检查、多次使用"的性能优化，也是 Windows 安全模型的核心范式。

> ⚠️ **工业安全警示**：这套机制的反面是——**一旦攻击者拿到一个高权限的句柄，他不需要再绕过 ACL**。这也是为什么"句柄复制"会成为特权提升攻击的常用手段：攻击者通过 `OpenProcess` 拿到高权限进程句柄，再用 `DuplicateHandle` 复制其令牌，最后 `SetThreadToken` 让自己的线程以高权限运行。防御这类攻击的关键是：对高价值命名对象定期审计 ACL、用 Sysmon Event ID 10 监控异常的 `PROCESS_ACCESS`、最小化不必要的高权限句柄。

## 3.2 进程内核对象句柄表

### 第一性原理视角

句柄到底是什么？**句柄是进程私有句柄表里的一个索引**。

这个设计有几个深远的含义：

1. **句柄值在同一进程内可能复用，但跨进程绝无意义**。你把 `0x1234` 这个句柄值发给另一个进程，那个进程用它去调 API，要么失败，要么访问到完全不相干的对象。这正是 Windows CE 5.0 升级到 6.0 时重点修复的"句柄猜测攻击"漏洞——CE 5.0 里句柄是全球共享的，攻击者可以靠猜句柄值提权；CE 6.0 开始每个进程独立的句柄表，句柄猜测被彻底消除。
2. **句柄表本身位于内核态地址空间**，用户态无法直接修改。这意味着句柄表是可信的——内核可以放心地用它来做权限决策。
3. **句柄表项里存的不只是对象指针，还有 GrantedAccess**（该句柄被授予的访问权限）和**继承标志**等元数据。

### 3.2.1 创建一个内核对象

当你调用 `CreateEvent`、`CreateMutex`、`CreateFileMapping` 等函数时，完整的流程是：

1. 对象管理器在内核堆上分配对象内存（可能是可分页的，也可能是不可分页的）
2. 初始化对象头：`PointerCount=1, HandleCount=0`，挂上安全描述符
3. 在调用进程的句柄表里分配一个空闲项，填入对象指针、`GrantedAccess`、继承标志
4. 返回该项在句柄表中的索引值，即"句柄"
5. 此时 `HandleCount` 变为 1

**关键洞见**：创建函数返回的句柄值，在同一个进程里下一次创建时可能复用，但因为句柄表项里记录了完整元数据，**内核永远不会把你的句柄误认为别人的**。这也是为什么 Windows 的句柄复用要经过一个 16 位的 reuse count 计数器——需要约 64000 次创建/关闭循环才会复用一个句柄值，极大降低了"陈旧句柄"误用的风险。

### 3.2.2 关闭内核对象

`CloseHandle` 的流程：

1. 检查调用进程的句柄表，确认该句柄索引有效且确实属于本进程
2. 取出对应的内核对象指针
3. 句柄表项标记为空闲，`HandleCount` 减 1
4. 如果 `HandleCount == 0` 且 `PointerCount == 0`，对象被销毁；否则对象继续存在

**最常见的工程错误**：忘记调用 `CloseHandle` 导致句柄泄露。在长生命周期的服务进程里，句柄泄露会缓慢耗尽系统资源，最终导致创建新对象失败。现代工业实践中：

- **用 RAII 封装句柄**：C++ 里可以用 `std::unique_ptr` 配合自定义 deleter，或者直接用 Windows 自己提供的 `unique_handle` 模式
- **用智能指针语义**：把 `HANDLE` 包装成移动语义类型，确保离开作用域时自动 `CloseHandle`
- **监控句柄数**：通过 Task Manager 的 "Handles" 列、Process Explorer、或 PowerShell `Get-Process | Select-Object -ExpandProperty Handles` 来观察进程的句柄增长趋势

> 💡 **一个反直觉的事实**：调用 `CloseHandle` 后，你传入的那个变量值不会被自动置 `NULL`。如果你之后不小心再次 `CloseHandle` 同一个值，会导致**二次关闭**——这是未定义行为，可能关闭一个完全不相干的对象（因为句柄值可能已被复用）。所以良好的实践是：`CloseHandle(h); h = NULL;`。

## 3.3 跨进程边界共享内核对象

这是本章最核心的工程价值所在。三种机制各有适用场景，理解它们的差异，是设计 Windows 多进程架构的关键。

### 3.3.1 使用对象句柄继承

**适用场景**：父子进程之间的句柄共享。

**机制**：

1. 父进程创建内核对象时，`SECURITY_ATTRIBUTES.bInheritHandle = TRUE`
2. 父进程调用 `CreateProcess` 创建子进程时，`bInheritHandles = TRUE`
3. 系统遍历父进程句柄表，把所有"可继承"的句柄项**复制到子进程的句柄表中相同位置**
4. 结果：同一个句柄值在父子进程中指向同一个内核对象

**限制与洞见**：

- 继承的是**句柄**，不是对象。对象本身只有一个，HandleCount 增加。
- 只有**父子关系**才能用继承。兄弟进程、祖孙进程都不行。
- 继承是"全有或全无"——所有可继承句柄都会被继承。如果需要精细控制，Windows Vista 之后可以用 `STARTUPINFOEX` + `UpdateProcThreadAttribute` 指定哪些句柄继承。
- 子进程里那个句柄值虽然在数值上与父进程相同，但它只在子进程自己的句柄表上下文里有效。

> 💡 **工业实践**：句柄继承在服务程序里常用于父服务进程把监听套接字、完成端口、同步事件传递给工作子进程。但因为"全继承"的粗粒度问题，现代代码更倾向于用下面的 `DuplicateHandle` 做精确控制。

### 3.3.2 改变句柄的标志

`SetHandleInformation` 可以动态修改句柄的继承标志（`HANDLE_FLAG_INHERIT`）和可关闭标志（`HANDLE_FLAG_PROTECT_FROM_CLOSE`）。

**关键洞见**：

- `HANDLE_FLAG_INHERIT` 让你可以在对象创建后再决定是否允许它被继承，而不必在 `CreateXxx` 时就定死
- `HANDLE_FLAG_PROTECT_FROM_CLOSE` 是一个安全护栏——防止该句柄被意外 `CloseHandle`。这在库代码中很有用：你的库创建了一个内部事件对象，不希望调用方误关它
- 这个 API 操作的是**当前进程的句柄表项**，不影响其他进程里对该对象的引用

### 3.3.3 为对象命名

**适用场景**：无血缘关系的进程之间的共享。

**机制**：

1. 进程 A：`CreateMutex(NULL, FALSE, L"MyAppMutex")`
2. 进程 B：`OpenMutex(MUTEX_ALL_ACCESS, FALSE, L"MyAppMutex")`
3. 如果两个进程在同一台机器上、且命名空间匹配，B 会拿到指向 A 创建的同一个互斥对象的句柄，`GetLastError()` 返回 `ERROR_ALREADY_EXISTS`

**深层洞见**：

- **命名对象本质是对象管理器命名空间里的"全局变量"**。对象管理器维护了一个层次化的命名空间（类似文件系统），根目录是 ``\`，下面有``\BaseNamedObjects`、`\Sessions\0...` 等
- 你可以用 Sysinternals 的 **WinObj**​ 工具浏览整个内核对象命名空间，直观看到所有命名对象
- **命名冲突的风险**：Windows 不对内核对象名做类型检查。如果你用一个名字创建了一个 Mutex，另一个进程用同一个名字创建 Event，第二个调用会失败（因为类型不匹配）。所以命名时务必加前缀，如 `Company_Product_Component_ObjectType_Name`
- **命名对象的安全**：命名对象的 ACL 在创建时确定。如果进程 A 以低权限创建了命名对象，进程 B 即使权限更高，也只能按 A 设定的 DACL 来访问

### 3.3.4 终端服务命名空间

**核心概念**：在终端服务（远程桌面服务）环境下，每个会话有自己独立的命名空间。

- **`Local` 前缀**（默认）：对象只对**同一会话**内的进程可见
- **`Global` 前缀**：对象对所有会话可见，跨会话共享

例如：`CreateMutex(NULL, FALSE, L"Local\\MySessionMutex")` 只在当前 RDP 会话内共享；`L"Global\\MyGlobalMutex"` 则对所有登录会话可见。

**工业洞见**：

- 服务程序（运行在 Session 0）和普通用户程序（运行在 Session 1+）之间共享命名对象时，**必须用 `Global` 前缀**，否则互相看不到
- 这是 Windows 服务开发中最经典的坑之一：服务创建了 `MyMutex`，用户程序 `OpenMutex("MyMutex")` 却返回 `ERROR_FILE_NOT_FOUND`，原因就是命名空间隔离
- 在 RDS（Remote Desktop Services）环境下，多个用户同时登录会产生多个会话，每个用户会话里的 `Local` 对象彼此隔离，互不干扰

### 3.3.5 专有命名空间

**解决的问题**：命名空间污染和命名冲突。

假设你的产品叫 "MyApp"，你创建了 `Global\\MyApp_Mutex`。但如果有另一个同名产品也这么做，就会冲突。**专有命名空间（Private Namespace）**​ 允许你创建一个边界，把你的所有命名对象都放进去：

```
// 创建一个边界描述符
HANDLE hBoundary = CreateBoundaryDescriptor(L"MyCompanyBoundary", 0);
// 添加 SID，定义谁可以进入这个边界（通常是当前用户或特定组）
AddSIDToBoundaryDescriptor(&hBoundary, pUserSID);
// 创建专有命名空间
HANDLE hNamespace = CreatePrivateNamespace(NULL, hBoundary, L"MyCompany");
// 在这个专有命名空间里创建对象
CreateMutex(hNamespace, FALSE, L"MyMutex");  // 实际名字是 "MyCompany\MyMutex"
```

**核心价值**：

- **隔离性**：即使另一个程序用了相同的对象名，只要它在不同的专有命名空间里，就不冲突
- **安全性**：通过 Boundary Descriptor 的 SID 列表，你可以限制哪些用户/进程能进入这个命名空间
- **工业级应用**：防命名对象抢注攻击。攻击者可能抢先创建一个与你同名的命名对象（如 `Global\\MyApp_ReadyEvent`），让你的程序误以为另一个实例已在运行。专有命名空间 + Boundary SID 可以有效防御这种"命名对象劫持"

### 3.3.6 复制对象句柄

`DuplicateHandle` 是最灵活、最强大的跨进程共享机制。

**签名要点**：

```
BOOL DuplicateHandle(
    HANDLE hSourceProcessHandle,  // 源进程句柄（需 PROCESS_DUP_HANDLE 权限）
    HANDLE hSourceHandle,         // 要复制的源句柄
    HANDLE hTargetProcessHandle,  // 目标进程句柄（需 PROCESS_DUP_HANDLE 权限）
    LPHANDLE lpTargetHandle,      // 接收新句柄值
    DWORD dwDesiredAccess,        // 新句柄的访问权限
    BOOL bInheritHandle,          // 新句柄是否可继承
    DWORD dwOptions               // DUPLICATE_CLOSE_SOURCE 或 DUPLICATE_SAME_ACCESS
);
```

**三种典型用法**：

1. **跨进程复制**：A 进程把自己拥有的句柄复制一份给 B 进程用。新句柄值在 B 进程的上下文里有效，指向同一个内核对象。
2. **降权复制**：A 进程有一个 `MUTEX_ALL_ACCESS` 的句柄，可以通过 `DuplicateHandle` 生成一个只有 `SYNCHRONIZE` 权限的新句柄，只授予 B 进程"等待"权限而不给"修改"权限。
3. **伪句柄转换**：`GetCurrentProcess()` / `GetCurrentThread()` 返回的是伪句柄（常数），不能直接传给别的进程。`DuplicateHandle` 可以把它们转换成真实的进程/线程句柄。

**与继承的对比**：

|维度|句柄继承|DuplicateHandle|
|---|---|---|
|进程关系|必须父子|任意（需 PROC_DUP_HANDLE 权限）|
|时机|只能在 CreateProcess 时|任意时刻|
|精度|全有或全无|精确控制单个句柄|
|权限|与原句柄相同|可降低权限|
|句柄值|父子相同|目标进程内新值|

> 💡 **工业实践中的经典模式**：父进程创建工作子进程时，用 `DuplicateHandle` 把需要的同步句柄、文件映射句柄等精确传递给子进程，然后通过命令行参数、环境变量或匿名管道把新句柄值告诉子进程。Stack Overflow 上关于这个话题的经典问答指出：你可以选择父进程调用 `DuplicateHandle` 把句柄复制进子进程然后 IPC 传值，也可以让子进程用 `OpenProcess` 打开父进程后再调用 `DuplicateHandle` 自己获取句柄。前者更常见。

> ⚠️ **安全警告**：`DuplicateHandle` 是双刃剑。它本身是合法的 API，但攻击者常用它来做特权提升——通过 `OpenProcess(PROCESS_DUP_HANDLE)` 拿到高权限进程句柄，再 `DuplicateHandle` 复制其令牌，最后 `SetThreadToken` 提权。防御措施：对高权限进程设置严格的 DACL，限制 `PROCESS_DUP_HANDLE` 访问权；用 Sysmon 监控 Event ID 10 的异常进程访问。

## 章节联系：句柄是 Windows 资源治理的"身份证"

把这一章串起来看，你会发现 Windows 的整个资源治理体系建立在三层抽象上：

1. **内核对象**：资源的本体，存在于内核态，受对象管理器统一管理
2. **句柄表**：进程私有的"身份证签发处"，把句柄值映射到内核对象
3. **共享机制**：跨进程边界的"身份证传递协议"——继承、命名、复制

这三层抽象对应着三个第一性原理：

- **隔离**：用户态不能直接碰内核态 → 必须通过句柄间接访问
- **管控**：每一次资源访问都要经过权限检查 → 检查发生在句柄创建时
- **生命周期**：资源不能因某个进程崩溃而泄漏 → 双计数器（HandleCount + PointerCount）确保精确回收

**与前后章节的联系**：

- 第1章讲的 `GetLastError()` 和 `ERROR_ALREADY_EXISTS`，在这一章得到了完美诠释——`CreateMutex("MyMutex")` 如果返回时 `GetLastError() == ERROR_ALREADY_EXISTS`，说明命名对象已存在，你拿到的是别人的对象的句柄。这是"成功但带附加信息"的错误码机制的经典案例。
- 第2章讲的 Unicode，在这一章也有体现——内核对象名是 Unicode 字符串，而且现代 Windows 推荐用 Unicode 命名。
- 后续章节（进程、线程、内存管理、DLL、线程同步等）讲的所有对象——进程对象、线程对象、文件映射对象、事件、互斥量、信号量、定时器——**全都是内核对象**。这一章是它们的"总纲"。理解了句柄表的机制，你才能真正理解为什么 `CreateThread` 返回的句柄不能在另一个进程里直接用；理解了使用计数，你才明白为什么父进程退出后子进程还能继续运行；理解了命名空间，你才能避开终端服务下的各种"找不到对象"的坑。

**给工业实践的五条硬建议**：

1. **所有 `HANDLE` 必须用 RAII 封装**，确保 `CloseHandle` 被调用。C++ 项目里推荐 `wil`（Windows Implementation Library）或自定义 `unique_handle`。
2. **创建内核对象时，如果可能被跨进程共享，务必命名**，且名字加上公司/产品前缀，避免冲突。
3. **服务程序和普通程序共享命名对象时，记得用 `Global` 前缀**。
4. **高安全场景下使用专有命名空间 + Boundary SID**，防御命名对象劫持攻击。
5. **用 WinObj、Process Explorer、Process Monitor 观察和调试句柄**。遇到"句柄无效"、"对象已存在"等诡异问题时，先用这些工具看一眼内核对象命名空间和句柄表，往往能秒定位问题。
