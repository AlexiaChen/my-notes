
第4章是整本书从"对象"走向"执行"的转折点。前3章我们都在讲静态的基石——错误码是状态、字符串是数据、内核对象是资源的受控入口；从第4章开始，**这些东西开始"动"起来了**：内核对象被实例化、地址空间被建立、线程被创建去执行代码。所以这一章的第一性原理是——**进程是 Windows 把"内核对象 + 地址空间 + 执行线程"三者捆绑在一起交付给开发者的"执行单元契约"**。理解了这个契约的建立过程，你才能理解后面所有的线程、内存、DLL、同步机制。

按你的目录，这一章上半部分分两大块：**4.1 进程的属性和配置**（进程"是什么、带什么配置出生"），以及 **4.2 CreateProcess 函数**（进程"怎么被生出来"）。下面逐节展开。

## 4.1 编写第一个 Windows 应用程序

这一节表面上是讲 `_tWinMain` / `_tmain` 入口函数，实则揭示了**进程启动的完整生命周期**。

### 进程的双重身份

Microsoft Learn 对进程的官方定义非常精准：每个进程提供执行程序所需的资源，包含虚拟地址空间、可执行代码、系统对象的已打开句柄、安全上下文、唯一进程标识符、环境变量、优先级类、最小/最大工作集，以及**至少一个执行线程**。

这个定义里最容易被忽视的一句话是"**至少一个执行线程**"。Richter 反复强调一个观点：**进程本身是惰性的（inert），它自己不执行任何代码，必须靠线程去执行**。这就是为什么第3章讲的内核对象使用计数如此关键——进程内核对象管理进程级资源，但真正"跑"起来的是线程内核对象。

我的第一性原理解读：**进程是"资源的容器"，线程是"执行的载体"**。这两者的解耦是 Windows 多任务架构的基石。一个进程可以有多个线程，所有线程共享该进程的虚拟地址空间和系统资源；但每个线程都有自己的异常处理、调度优先级、线程局部存储、唯一线程标识符和上下文。

### 4.1.1 进程实例句柄

`HINSTANCE` / `HMODULE` **在 Win32 里是同一个东西**——都是模块加载到进程地址空间后的基地址。这一点 Richter 讲得很清楚，但很多人学了几个月 Windows 编程都没意识到。

**工程洞见**：

- `GetModuleHandle(NULL)` 返回的是**当前执行文件**（EXE）的基地址，即使在某个 DLL 内部调用也同样返回 EXE 的 `HINSTANCE`
- `GetModuleHandle(TEXT("some.dll"))` 返回指定 DLL 的基地址
- 链接器 `/BASE` 选项可以配置模块的默认加载基址（EXE 默认 `0x400000`，DLL 默认 `0x10000000`）

为什么要关心这个？因为 `HINSTANCE` 在 Win32 里无处不在——创建窗口、加载资源、注册窗口类都要用到它。它是"模块身份"的代名词。

> 💡 **现代视角**：在 64 位 Windows 和 ASLR（地址空间布局随机化）开启的情况下，模块的"基地址"概念被弱化了——每次进程启动，系统都可能把模块加载到不同的地址。所以现代代码里，**不应该把 `HINSTANCE` 当成绝对地址来用**，而应该把它当成"模块句柄"这个抽象概念来用。这也是为什么 Richter 反复提醒：不要把 `HINSTANCE` 强转成指针去做内存操作。

### 4.1.2 进程前一个实例的句柄

这是 16 位 Windows 的历史遗留。在 16 位时代，`hPrevInstance` 用来判断"这个程序是否已经有一个实例在运行"。在 Win32 里，**这个参数永远为 `NULL`**——因为 Win32 的每个进程都有完全独立的地址空间，不存在"前一个实例"的概念。

**为什么还要保留这个参数？**​ 纯粹是为了兼容旧的源码。Richter 指出，现代 Windows 程序要做"单实例"检测，应该用第3章讲的**命名互斥量（Named Mutex）**——创建一个名为 `Global\MyCompany_MyApp_SingleInstance` 的 Mutex，如果 `GetLastError()` 返回 `ERROR_ALREADY_EXISTS`，说明已有实例。

> 💡 **工业实践洞见**：单实例检测在现代有个微妙的坑——**终端服务会话隔离**。如果你的程序既要支持单机单实例，又要支持多用户远程桌面各跑一个实例，命名要这样设计：
> 
> - 本会话内单实例：`Local\MyApp_SingleInstance`
> - 全局单实例：`Global\MyApp_SingleInstance`
> - 跨会话但按用户隔离：用 `CreatePrivateNamespace` + Boundary SID（第3章讲过）

### 4.1.3 进程的命令行

`GetCommandLine()` 返回完整命令行（包括 EXE 路径本身）。C/C++ 运行时的 `argc/argv` 是通过解析这个完整命令行得到的。

**关键工程细节**：

- `GetCommandLine()` 返回的是**指向进程环境块（PEB）中命令行副本的指针**，不要试图修改它
- 路径含空格时，命令行的解析会有歧义。比如 `"C:\Program Files\MyApp -L"` 这个字符串，系统会按空格分割依次尝试：
    - `C:\Program.exe`
    - `C:\Program Files\MyApp.exe`
    - `C:\Program Files\MyApp -L.exe`
    - ……  
        这就是经典的"**路径空格劫持**"攻击向量

**现代工业级做法**：

```
// 安全写法：显式指定 lpApplicationName，把参数单独放 lpCommandLine
CreateProcessW(
    L"C:\\Program Files\\MyApp\\app.exe",  // 明确的可执行文件
    L"\"C:\\Program Files\\MyApp\\app.exe\" -L -S",  // 完整命令行
    ...);
```

Microsoft 官方文档明确指出：**含空格的路径必须加引号或用 `lpApplicationName` 显式指定**，否则恶意用户只需在 ``C:\` 下放置一个``Program.exe` 就能劫持你的进程。

### 4.1.4 进程的环境变量

每个进程都有一个**环境块（Environment Block）**，它是一个以双 NULL 结尾的字符串数组，格式为 `Var1=Value1\0Var2=Value2\0...\0\0`。

**关键事实**（来自 Microsoft Learn）：

- 环境块**默认按字母顺序排列**（大小写不敏感的 Unicode 顺序）
- 变量名中**不能包含等号**
- 子进程**默认继承父进程环境块的副本**
- 从 Windows Vista 开始，环境块**没有硬性大小限制**（Vista 之前限制为 32767 字符）
- 但 .NET 的 `Process` 类在传 ANSI 环境块时仍有 32767 字符限制（Raymond Chen 在 Old New Thing 博客里详解过这个坑）

**环境块的操作**：

- `GetEnvironmentStrings()` 获取调用进程的环境块（只读，用完 `FreeEnvironmentStrings` 释放）
- `GetEnvironmentVariable()` 查询单个变量
- `SetEnvironmentVariable()` 修改当前进程的环境变量（不影响父进程或其他进程）
- `ExpandEnvironmentStrings()` 展开 `%USERPROFILE%` 这类引用

> 💡 **第一性原理洞见**：环境块是 Windows 进程间"配置继承"的标准机制。它的设计哲学是**不可变性 + 快照**——子进程拿到的是父进程环境块的一份拷贝，之后父子各自修改互不影响。这种"值拷贝"而非"引用共享"的设计，避免了环境变量在进程间产生意外的耦合，是 Windows 进程隔离哲学的典型体现。

**工业实践**：

- 修改子进程环境变量的**唯一方式**是在 `CreateProcess` 时传入新的环境块
- 一个进程**永远不能直接修改另一个非子进程的环境变量**
- 如果需要让子进程继承大部分父进程环境，只改几个变量：先用 `GetEnvironmentVariable` 保存原值 → 创建修改后的环境块 → `CreateProcess` → 用 `SetEnvironmentVariable` 恢复原值

### 4.1.5 进程的关联性

**关联性（Affinity）**指进程可以运行在哪些 CPU 核心上。

- 默认：进程继承父进程的关联性掩码
- 可通过 `SetProcessAffinityMask()` 设置
- 作业对象（Job Object，第5章会讲）也可以限制关联性

**现代工业视角**：

- 在 NUMA 架构服务器上，正确设置关联性可以显著提升性能——让线程访问就近的内存节点
- 游戏和实时音频软件常用关联性把关键线程绑定到特定核心，避免被系统调度打断
- **但过度使用关联性会损害系统整体调度效率**——Windows 调度器在多核间的负载均衡做得很好，除非有明确性能需求，否则不要随意绑定

### 4.1.6 进程的错误模式

`SetErrorMode()` 控制进程如何处理某些系统错误：

- `SEM_FAILCRITICALERRORS`：禁止系统弹出"硬盘未就绪"等临界错误对话框
- `SEM_NOGPFAULTERRORBOX`：禁止系统弹出"General Protection Fault"错误框
- `SEM_NOOPENFILEERRORBOX`：禁止"文件未找到"错误框

**工业洞见**：**所有服务端程序、Windows 服务、后台守护进程都应该调用 `SetErrorMode(SEM_FAILCRITICALERRORS)`**。否则，当服务试图访问一个脱机的网络驱动器时，系统会弹出一个模态对话框等待用户点击——但服务在 Session 0 里运行，没有交互用户，这个对话框永远不会被关掉，服务也就永远卡住了。这是 Windows 服务开发里最经典的死锁场景之一。

### 4.1.7 进程当前所在的驱动器和目录

这是 Windows 独有的概念——每个进程有一组"每驱动器当前目录"（Per-Drive Current Directory）。

- `GetCurrentDirectory()` 获取进程的当前目录
- `SetCurrentDirectory()` 设置
- 环境块里以 `=X:` 形式的变量存储各驱动器的当前目录（如 `=C:=C:\Users\Me`）

**关键陷阱**：当你通过 `CreateProcess` 的 `lpEnvironment` 参数传递自定义环境块时，**系统不会自动把当前目录信息传播给子进程**。你必须手动构造 `=X:` 形式的环境变量放进环境块。Microsoft 官方文档明确说明了这一点，并建议用 `GetFullPathName("X:", ...)` 来获取驱动器 X 的当前目录。

### 4.1.8 进程的当前目录

`CreateProcess` 的 `lpCurrentDirectory` 参数可以指定子进程的起始目录。如果传 `NULL`，子进程继承父进程的当前目录。

**工程最佳实践**：

- 永远**显式指定**子进程的当前目录，不要依赖继承
- 尤其是服务程序（运行在 `C:\Windows\System32` 下），如果不指定，`CreateProcess` 创建的子进程会在 System32 目录下启动，可能导致配置文件加载错乱
- 推荐做法：用 `GetModuleFileName(NULL, ...)` 获取 EXE 路径，再用 `PathRemoveFileSpec()` 提取目录，作为 `lpCurrentDirectory` 传入

### 4.1.9 系统版本

传统做法是用 `GetVersion()` / `GetVersionEx()` 判断系统版本。

**⚠️ 重要现代性提示**：这两个 API 在 Windows 8.1 之后**行为发生了变化**——它们返回的版本号可能被应用程序清单（Manifest）中的 `supportedOS` 项"冻结"在早期版本。也就是说，没有声明支持 Windows 10/11 的旧程序，调用 `GetVersionEx()` 会得到 Windows 8 的版本号，即使它运行在 Windows 11 上。

**现代工业做法**：

- 使用 `VerifyVersionInfo()` + `VersionHelpers.h` 里的 `IsWindows10OrGreater()` 等宏
- 或者直接使用**基于功能的检测**（Feature Detection）而非版本检测——与其问"我是否在 Win10 上"，不如直接尝试调用你想用的 API，看它是否成功
- 对于新的 Windows 11 专项功能，用 `IsWindows11OrGreater()`

> 💡 **洞见**：版本检测本身就是一种脆弱的工程实践。Windows 团队的官方立场已经转变为"**不要问版本，问能力**"。这与 Web 开发里的 Feature Detection 哲学完全一致——这是现代 Windows 编程的一个重要范式转移。

## 4.2 CreateProcess 函数

`CreateProcess` 是 Win32 里最复杂的 API 之一，10 个参数，每个都有深坑。Microsoft 官方文档把它描述为"创建一个独立于父进程运行的新进程"，并明确给出了**两条重要的安全提示**：

1. **`lpCommandLine` 必须是可写的字符数组**——不能是字符串字面量或 const 指针。`CreateProcessW` 可能原地修改这个缓冲区。传只读字符串会导致访问违规。
2. **`bInheritHandles` 默认为 FALSE**——除非子进程明确需要继承句柄，否则应设为 FALSE。继承的句柄（文件句柄、套接字、令牌）可能把敏感资源泄露给子进程。

### 4.2.1 pszApplicationName 和 pszCommandLine 参数

这是 `CreateProcess` 里最微妙的一对参数。

**四种组合的行为**：

|pszApplicationName|pszCommandLine|行为|
|---|---|---|
|NULL|`"app.exe arg1 arg2"`|从命令行第一个空格分隔的 token 解析出模块名|
|`"C:\\app.exe"`|NULL|用 appName 作为命令行|
|`"C:\\app.exe"`|`"arg1 arg2"`|精确控制：appName 是模块，commandLine 是参数|
|`"C:\\app.exe"`|`"C:\\app.exe arg1 arg2"`|同上一行，但命令行里重复了 EXE 名|

**模块搜索顺序**（当 `pszApplicationName` 为 NULL 且命令行里只有文件名时）：

1. 调用进程 EXE 所在目录
2. 父进程的当前目录
3. Windows 系统目录（System32）
4. 16 位 Windows 系统目录
5. Windows 目录
6. PATH 环境变量里的目录

> ⚠️ **安全红线**：**永远不要在 `pszApplicationName` 为 NULL 的情况下传含空格的未引号路径**。这是 Windows 平台上最经典的二进制劫持漏洞。正确做法是：
> 
> ```
> // 安全做法
> CreateProcessW(
>     L"C:\\Program Files\\MyApp\\app.exe",  // 明确指定
>     L"\"C:\\Program Files\\MyApp\\app.exe\" -flag",  // 命令行里也引号
>     ...);
> ```

**工业实践**：现代代码应该**总是**显式指定 `pszApplicationName`，把 `pszCommandLine` 当作纯参数。这样既安全又清晰。

### 4.2.2 psaProcess, psaThread 和 bInheritHandles 参数

`psaProcess` 和 `psaThread` 是进程/线程内核对象的安全描述符。绝大多数情况下传 `NULL`，使用默认安全描述符。

`bInheritHandles` 控制子进程是否继承父进程里标记为"可继承"的句柄。

**⚠️ 现代安全实践（非常重要）**：

Microsoft 官方文档明确指出：**`bInheritHandles=TRUE` 会导致父进程所有可继承句柄都被子进程继承**。这在多线程同时创建子进程的场景下是个问题——你可能只想让子进程 A 继承句柄 H1，让子进程 B 继承句柄 H2，但 `bInheritHandles=TRUE` 会让两个子进程都继承 H1 和 H2。

**现代解决方案**：用 `STARTUPINFOEX` + `UpdateProcThreadAttribute` + `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`，显式列出要继承的句柄列表：

```
STARTUPINFOEX siEx = { sizeof(siEx) };
SECURITY_ATTRIBUTES sa = { sizeof(sa), NULL, TRUE };  // 可继承
HANDLE hInherit = CreateEvent(&sa, FALSE, FALSE, NULL);
HANDLE hInheritList[] = { hInherit };

SIZE_T attrSize = 0;
InitializeProcThreadAttributeList(NULL, 1, 0, &attrSize);
siEx.lpAttributeList = (LPPROC_THREAD_ATTRIBUTE_LIST)HeapAlloc(
    GetProcessHeap(), 0, attrSize);
InitializeProcThreadAttributeList(siEx.lpAttributeList, 1, 0, &attrSize);
UpdateProcThreadAttribute(
    siEx.lpAttributeList, 0,
    PROC_THREAD_ATTRIBUTE_HANDLE_LIST,
    hInheritList, sizeof(hInheritList), NULL, NULL);

CreateProcess(..., FALSE, EXTENDED_STARTUPINFO_PRESENT, ..., 
    (LPSTARTUPINFO)&siEx, ...);
```

这个模式在现代 Windows 服务、Chrome 多进程架构、Node.js 子进程管理里都是标准做法。

### 4.2.3 fdwCreate 参数

创建标志，常用的有：

- **`CREATE_NO_WINDOW`**：不创建控制台窗口（适合后台子进程）
- **`CREATE_NEW_CONSOLE`**：子进程有独立的新控制台
- **`CREATE_NEW_PROCESS_GROUP`**：创建新进程组（用于 `GenerateConsoleCtrlEvent` 批量发送 Ctrl+C）
- **`CREATE_SUSPENDED`**：主线程创建后即挂起，直到 `ResumeThread` 被调用
- **`CREATE_UNICODE_ENVIRONMENT`**：`lpEnvironment` 指向的是 Unicode 环境块
- **`DEBUG_PROCESS` / `DEBUG_ONLY_THIS_PROCESS`**：父进程作为调试器
- **`DETACHED_PROCESS`**：不继承父进程控制台
- **`NORMAL_PRIORITY_CLASS` / `HIGH_PRIORITY_CLASS` / `REALTIME_PRIORITY_CLASS`**：优先级类

**`CREATE_SUSPENDED` 的工业价值**：

- 在 Resume 之前，你可以安全地修改子进程的内存（写入配置）、设置线程亲和性、注入代码
- Chrome 浏览器就是用这个标志创建渲染进程，然后在 Resume 前完成沙箱策略的应用
- 游戏引擎常用它来创建 Worker 进程并预先设置 CPU 关联性

**`CREATE_NEW_PROCESS_GROUP` 的洞见**：这个标志隐含调用了 `SetConsoleCtrlHandler(NULL, TRUE)`——也就是说，新进程**默认屏蔽了 Ctrl+C**，但 Ctrl+Break 仍然有效。这是shell程序的标准做法，让父 shell 可以自己处理 Ctrl+C 并选择性地转发给子进程。

### 4.2.4 pvEnvironment 参数

指向环境块的指针。

**关键规则**：

- 传 `NULL`：子进程继承父进程环境块的副本
- 传自定义环境块：必须自己构造 `Var=Value\0` 格式的块，以双 NULL 结尾，**并且按变量名排序**
- 如果环境块是 Unicode 的，**必须**配合 `CREATE_UNICODE_ENVIRONMENT` 标志
- 如果不传 `CREATE_UNICODE_ENVIRONITY` 且环境块是 Unicode 的，系统会尝试转换为 ANSI，可能丢字符

**构造环境块的工业级代码**：

```
#define MAX_ENV_BLOCK 4096
TCHAR envBlock[MAX_ENV_BLOCK];
LPTSTR p = envBlock;
// 必须按字母顺序：先 MySetting，再 MyVersion
StringCchCopy(p, MAX_ENV_BLOCK, TEXT("MySetting=A"));
p += lstrlen(p) + 1;
StringCchCopy(p, MAX_ENV_BLOCK - (p - envBlock), TEXT("MyVersion=2"));
p += lstrlen(p) + 1;
*p = TEXT('\0');  // 双 NULL 结尾

CreateProcess(..., CREATE_UNICODE_ENVIRONMENT, envBlock, ...);
```

### 4.2.5 pszCurDir 参数

子进程的当前驱动器和目录。

**工程铁律**：

- **永远显式传这个参数**，不要依赖默认值
- 服务程序尤其要注意——默认会继承 `C:\Windows\System32`，这通常不是你想要的
- 推荐用 `GetModuleFileName(NULL, ...)` + 提取目录的方式来设置

```
TCHAR exePath[MAX_PATH];
GetModuleFileName(NULL, exePath, MAX_PATH);
PathRemoveFileSpec(exePath);  // 去掉文件名，保留目录
CreateProcess(..., exePath, ...);  // 子进程在当前 EXE 所在目录启动
```

### 4.2.6 psiStartInfo 参数

指向 `STARTUPINFO` 结构体的指针，控制新进程的窗口外观、标准句柄、桌面等。

**关键字段**：

- `cb`：**必须**设为 `sizeof(STARTUPINFO)`，否则 `CreateProcess` 失败
- `dwFlags`：控制哪些字段有效
- `hStdInput` / `hStdOutput` / `hStdError`：标准输入输出的重定向句柄
- `wShowWindow`：窗口初始显示状态（`SW_HIDE`, `SW_SHOW`, etc.）
- `lpDesktop`：指定桌面（用于创建在屏保桌面、Winlogon 桌面等）

**现代工业实践**：

1. **总是用 `STARTUPINFOEX` 而非 `STARTUPINFO`**：
    
    ```
    STARTUPINFOEX si = { sizeof(si) };
    // 可以用 UpdateProcThreadAttribute 扩展功能
    ```
    
      
    即使不用扩展属性，用 `STARTUPINFOEX` 也是面向未来的做法。
2. **标准输出重定向的经典模式**（父子进程通过管道通信）：
    
    ```
    HANDLE hReadPipe, hWritePipe;
    CreatePipe(&hReadPipe, &hWritePipe, NULL, 0);
    SetHandleInformation(hWritePipe, HANDLE_FLAG_INHERIT, HANDLE_FLAG_INHERIT);
    
    STARTUPINFO si = { sizeof(si) };
    si.hStdOutput = hWritePipe;
    si.hStdError = hWritePipe;
    si.dwFlags = STARTF_USESTDHANDLES;
    
    CreateProcess(..., TRUE, ..., &si, ...);  // bInheritHandles=TRUE
    // 父进程从 hReadPipe 读取子进程的输出
    ```
    
3. **`wShowWindow=SW_HIDE` + `CREATE_NO_WINDOW`**：后台守护进程的标准配置

### 4.2.7 ppiProcInfo 参数

`PROCESS_INFORMATION` 结构体，输出新进程和主线程的句柄与 ID：

```
typedef struct _PROCESS_INFORMATION {
    HANDLE hProcess;    // 进程句柄（完全访问权限）
    HANDLE hThread;     // 主线程句柄（完全访问权限）
    DWORD  dwProcessId; // 进程 ID
    DWORD  dwThreadId;  // 主线程 ID
} PROCESS_INFORMATION;
```

**关键工程洞见**：

1. **`hProcess` 和 `hThread` 是"完全访问"的句柄**——即使你通过安全描述符限制了访问，这两个句柄在创建者进程里仍然是 `PROCESS_ALL_ACCESS` 和 `THREAD_ALL_ACCESS`。这是因为创建者进程天然对新进程拥有完全控制权。
2. **句柄必须关闭**：
    
    ```
    WaitForSingleObject(pi.hProcess, INFINITE);  // 等进程结束
    GetExitCodeProcess(pi.hProcess, &exitCode); // 取退出码
    CloseHandle(pi.hProcess);
    CloseHandle(pi.hThread);  // 别忘了关线程句柄！
    ```
    
      
    **最常见的资源泄露**：只关 `hProcess` 忘了关 `hThread`。
3. **`dwProcessId` 和 `dwThreadId` 是可重用的**——进程/线程退出后，它们的 ID 可能被系统分配给新的进程/线程。所以不要长期缓存 PID 并在后续操作中假定它指向同一个进程。
4. **`CreateProcess` 返回 `TRUE` 不等于子进程初始化成功**：
    - `CreateProcess` 返回时，系统只是创建了进程内核对象 + 地址空间 + 主线程内核对象
    - 主线程还没开始执行，EXE 的依赖 DLL 还没加载
    - 如果 EXE 的依赖 DLL 缺失，进程会终止，但 `CreateProcess` 仍然返回 `TRUE`
    - 要确认子进程真正"活"了，需要 `WaitForInputIdle()` 或等进程退出后检查退出码

> 💡 **工业级最佳实践**：现代 C++ 代码应该把 `PROCESS_INFORMATION` 封装成 RAII 类型：
> 
> ```
> class ProcessHandle {
>     PROCESS_INFORMATION pi_;
> public:
>     ~ProcessHandle() {
>         if (pi_.hThread) CloseHandle(pi_.hThread);
>         if (pi_.hProcess) CloseHandle(pi_.hProcess);
>     }
>     // ... 移动语义，禁止拷贝
> };
> ```
> 
> Windows Implementation Library (WIL) 和 Chromium 的 `base::Process` 都采用了这种模式。

## 章节联系：进程创建是一场"契约建立仪式"

把 4.1 和 4.2 合起来看，`CreateProcess` 的本质是**父进程和 Windows 系统之间的一场契约建立仪式**——父进程通过 10 个参数，精确地规定子进程"出生时的所有初始条件"：

- **我是谁**（pszApplicationName）→ 决定加载哪个 EXE
- **我带什么参数**（pszCommandLine）→ 决定命令行
- **我有什么权限**（psaProcess/psaThread）→ 决定安全上下文
- **我继承什么**（bInheritHandles）→ 决定句柄传递
- **我是什么状态**（fdwCreate）→ 决定优先级、窗口、调试等
- **我处在什么环境**（pvEnvironment）→ 决定环境变量块
- **我在哪里落地**（pszCurDir）→ 决定当前目录
- **我长什么样**（psiStartInfo）→ 决定窗口、标准句柄、桌面
- **我怎么被识别**（ppiProcInfo）→ 输出句柄和 ID

这 10 个参数，每一个都对应着 4.1 节讲过的"进程属性"。**4.1 是"进程有哪些属性"，4.2 是"如何在创建时设置这些属性"**——这就是这两节的内在联系。

**与前3章的联系**：

- 第1章的 `GetLastError()`：`CreateProcess` 失败时返回 `FALSE`，具体原因通过 `GetLastError()` 获取（`ERROR_FILE_NOT_FOUND`, `ERROR_PATH_NOT_FOUND`, `ERROR_ACCESS_DENIED` 等）
- 第2章的 Unicode：现代代码**必须**用 `CreateProcessW`，环境块必须配 `CREATE_UNICODE_ENVIRONMENT`
- 第3章的内核对象：`CreateProcess` 内部创建了两个内核对象——进程内核对象和线程内核对象，并把它们的句柄通过 `PROCESS_INFORMATION` 返回给调用者；这两个内核对象的使用计数机制保证了即使父进程忘记关句柄，进程退出后资源最终也会被回收

**与现代工业实践的衔接**：

1. **服务化架构**：Windows 服务（Service）创建子进程时，必须小心处理 Session 0 隔离——用 `CreateProcessAsUser` 或 `CreateProcessWithTokenW` 在指定用户会话里创建进程
2. **容器与沙箱**：Windows Container 和 AppContainer 沙箱里，`CreateProcess` 受到 Job Object 和 Silo 的限制，子进程自动继承父进程的沙箱边界
3. **多进程应用架构**：Chrome、Electron、VS Code 等现代桌面应用都采用"多进程 + IPC"架构，每个子进程通过 `CreateProcess` 创建并配 `CREATE_SUSPENDED`，在 Resume 前完成沙箱策略应用
4. **.NET 与现代语言**：C# 的 `System.Diagnostics.Process`、Python 的 `subprocess`、Node.js 的 `child_process` 本质上都是 `CreateProcess` 的封装，但隐藏了大量细节——理解 `CreateProcess` 的原生行为，才能在高层封装出问题时快速定位

> ⚠️ **一个常被忽视的现代议题**：在 Windows 11 24H2 及后续版本中，Microsoft 正在推进 **"sudo for Windows"**​ 和 **App Execution Aliases**​ 等新机制，这些机制在底层仍然调用 `CreateProcess` 或其变体（`CreateProcessAsUser`），但增加了包标识（Package Identity）和 AppX 部署的考量。这意味着未来的 Windows 进程创建，会越来越强调"应用身份"而非单纯的"EXE 路径"——这是 Richter 写书时（2007 年）完全无法预见的演进方向。


继续。上半部分我们讲完了"进程怎么生"，下半部分讲的是"进程怎么死"以及"进程以什么身份活"。这两件事在工程上的重要性，不亚于进程的创建——甚至更甚，因为**进程的退出方式直接决定了系统资源是否干净回收，而进程的权限上下文直接决定了它能做什么、不能做什么**。

## 4.3 终止进程

### 第一性原理视角

进程终止的本质是：**内核对象使用计数归零 + 地址空间被销毁 + 所有线程被强制结束**。但"怎么到达这个终态"有四条不同的路径，它们的"优雅程度"天差地别。

### 4.3.1 主线程的入口点函数返回

这是**唯一正确的进程退出方式**。

当主线程的入口函数（`_tWinMain` / `main`）返回时，C/C++ 运行时会依次执行以下操作：

1. 调用所有已注册的 `atexit` / `onexit` 函数
2. 调用所有全局/静态 C++ 对象的析构函数
3. 调用 `ExitProcess`，传入 `main` 的返回值作为进程退出码

**为什么这是唯一正确的方式？**​ 因为只有这样，C++ 对象的析构函数才会被调用、栈上的 RAII 资源才会被正确释放、文件缓冲区才会被 flush。其他方式都是在"拔电源"。

**工程洞见**：

- 如果你的 `main` 函数里直接调用了 `ExitProcess`，全局对象的析构函数**不会**被调用。这在大多数情况下不是问题（因为进程马上就死了），但如果有全局对象持有锁、写了日志、flush 了文件，你就会遇到诡异的数据损坏
- 在 DLL 里**永远不要**调用 `ExitProcess`——这会强制终止整个进程，包括其他还在正常运行的模块

### 4.3.2 ExitProcess 函数

`ExitProcess` 是进程自行了断的"硬方式"。

```
VOID ExitProcess(UINT uExitCode);
```

调用后，系统会：

1. 终止进程中的所有线程
2. 释放进程地址空间中的所有内存
3. 关闭所有内核对象句柄
4. 将退出码设为 `uExitCode`

**关键洞见**：`ExitProcess` 是"进程级自杀"。它会**强制结束同一进程内的所有其他线程**——不管那些线程在干什么。如果一个工作线程正持有临界区、正在写文件、正在做网络请求，调用 `ExitProcess` 会导致：

- 临界区永远不被释放（但内核会强制回收，所以不会死锁其他进程）
- 文件数据可能只写了一半
- 网络请求被中断，服务器可能处于不一致状态

> ⚠️ **工业实践**：现代代码里，`ExitProcess` 应该只出现在两种场景：(1) 程序检测到致命的、不可恢复的错误（如内存损坏），需要立即终止；(2) 作为 `main` 返回后的最后一步（由 CRT 自动调用）。**正常业务逻辑中，永远让 `main` 返回，不要手动调 `ExitProcess`**。

### 4.3.3 TerminateProcess 函数

`TerminateProcess` 是"他杀"。

```
BOOL TerminateProcess(HANDLE hProcess, UINT uExitCode);
```

与 `ExitProcess` 的关键区别：

- `ExitProcess` 只杀自己，`TerminateProcess` 可以杀任何有 `PROCESS_TERMINATE` 权限的进程
- `TerminateProcess` 是**异步的**——它只是通知系统"请终止这个进程"，函数返回时进程可能还没死
- `TerminateProcess` **不会**调用任何 DLL 的 `DllMain`、不会调用任何析构函数、不会 flush 任何缓冲区

**为什么这东西存在？**​ 因为它是"最后手段"。当进程已经失控、卡死、进入死循环时，你别无选择，只能 `TerminateProcess`。

> 🚨 **绝对规则：永远不要在你的程序正常逻辑中调用 `TerminateProcess`**。Raymond Chen（Microsoft 资深工程师，The Old New Thing 博客作者）反复强调过这一点——`TerminateProcess` 是"核选项"，它会留下各种资源泄漏的烂摊子。比如：
> 
> - 内核对象句柄会被关闭，但如果目标进程正持有一个命名互斥量，`TerminateProcess` 后互斥量会被废弃，其他等待该互斥量的进程会收到 `WAIT_ABANDONED`——这意味着数据可能处于不一致状态
> - 如果目标进程正持有文件锁，文件锁会被释放，但文件内容可能不完整
> - 如果目标进程是服务，服务控制管理器（SCM）会认为服务崩溃，可能触发恢复动作

**工业实践中的正确做法**：

- 需要优雅关闭另一个进程时，先发 `WM_CLOSE` 或 `GenerateConsoleCtrlEvent`（Ctrl+C），给它机会自己清理
- 等待一个超时时间
- 超时后如果进程仍然存活，才考虑 `TerminateProcess`

```
// 优雅关闭的工业级模式
BOOL GracefulTerminate(HANDLE hProcess, DWORD timeoutMs) {
    DWORD pid = GetProcessId(hProcess);
    HWND hwnd = GetTopWindow(NULL);
    // 1. 尝试找到进程的主窗口，发 WM_CLOSE
    EnumWindows([](HWND hwnd, LPARAM lParam) -> BOOL {
        DWORD pid;
        GetWindowThreadProcessId(hwnd, &pid);
        if (pid == (DWORD)lParam && GetWindow(hwnd, GW_OWNER) == NULL) {
            PostMessage(hwnd, WM_CLOSE, 0, 0);
            return FALSE;  // 停止枚举
        }
        return TRUE;
    }, (LPARAM)pid);
    
    // 2. 等待进程自行退出
    if (WaitForSingleObject(hProcess, timeoutMs) == WAIT_OBJECT_0) {
        return TRUE;  // 进程已优雅退出
    }
    
    // 3. 超时，强制终止
    TerminateProcess(hProcess, 1);
    WaitForSingleObject(hProcess, INFINITE);
    return FALSE;  // 告知调用者这是强制终止
}
```

### 4.3.4 当进程中的所有线程终止时

这是一个容易被误解的机制：**当进程中的所有线程都终止时，操作系统会自动终止该进程**。

这意味着你不需要显式调用 `ExitProcess`——当最后一个线程的入口函数返回时，进程自然消亡。但前提是**所有线程都正常退出**。如果有一个线程进入了死循环或者卡在阻塞调用上，进程就不会退出。

**工程洞见**：

- 这是"僵尸进程"的一种成因——主线程退出了，但某个后台线程还活着（比如忘了关的定时器线程、忘了 join 的工作线程）
- 调试这种问题时，`Process Explorer` 可以显示进程的线程列表，看看哪个线程还活着
- C++11 的 `std::thread` 如果 `detach` 了，主线程退出时该线程可能还在跑——这是跨平台代码里常见的进程无法退出的原因

### 4.3.5 当进程终止运行时

无论通过哪种方式终止，进程最终死亡时系统会做以下事情：

1. **所有线程被终止**（如果还没终止的话）
2. **进程分配的所有用户态内存被释放**（堆、栈、代码段）
3. **所有内核对象句柄被关闭**——如果这是某个内核对象的最后一个句柄，`HandleCount` 归零；如果 `PointerCount` 也归零，对象被销毁
4. **进程的退出码被设置**（通过 `GetExitCodeProcess` 可以获取）
5. **进程内核对象的状态变为"已触发"（signaled）**——这意味着任何等待该进程句柄的 `WaitForSingleObject` 调用会返回

**关键洞见**：第5步是进程同步的基石。父进程可以 `WaitForSingleObject(pi.hProcess, INFINITE)` 来等待子进程结束，这就是这么工作的——进程内核对象在进程活着时是"未触发"的，进程一死就变成"已触发"。

> 💡 **一个精妙的细节**：进程退出后，它的内核对象并不会立即消失——只要还有人持有该进程的句柄，内核对象就继续存在。这就是为什么你可以在进程退出后仍然调用 `GetExitCodeProcess`——内核对象还在，只是里面的数据变成了"退出码"而已。一旦最后一个句柄被关闭，内核对象才真正被销毁。

## 4.4 子进程

这一节的核心问题是：**父进程如何管理和与子进程交互？**

**关键模式**：

1. **创建子进程**​ → 拿到 `PROCESS_INFORMATION`
2. **等待子进程结束**​ → `WaitForSingleObject(pi.hProcess, ...)`
3. **获取退出码**​ → `GetExitCodeProcess(pi.hProcess, &exitCode)`
4. **关闭句柄**​ → `CloseHandle(pi.hProcess); CloseHandle(pi.hThread);`

**子进程继承的"遗产"**：

- 环境变量（如果 `bInheritHandles` 相关且环境块未自定义）
- 可继承的句柄（如果 `bInheritHandles=TRUE` 或显式指定了句柄列表）
- 当前目录（如果 `lpCurrentDirectory=NULL`）
- 进程优先级类（默认继承父进程）

**工业实践洞见**：

- **子进程管理是现代多进程架构的核心**。Chrome 的每个渲染进程、Node.js 的每个 worker、VS Code 的每个扩展宿主进程，都是通过这种方式管理的
- **作业对象（Job Object，第5章）是管理子进程的更好方式**——它可以限制子进程的资源使用、在父进程退出时自动终止所有子进程（通过 `SetInformationJobObject` + `JOB_OBJECT_LIMIT_BREAKAWAY_OK` 等标志）
- **僵尸子进程问题**：如果父进程不调用 `WaitForSingleObject` 也不关闭子进程句柄，子进程退出后内核对象会一直存在（因为父进程还持有句柄），造成内核对象泄露。这就是 Windows 版的"僵尸进程"

> 💡 **一个工程模式**：父进程创建子进程后，如果不需要等待它结束，至少应该 `CloseHandle(pi.hProcess)` 和 `CloseHandle(pi.hThread)`。如果需要后续查询退出码，那就保持句柄打开，但要记得最终关闭。

## 4.5 管理员以标准用户权限运行时

这是 Vista 引入 UAC（User Account Control）之后的核心话题。Richter 写书时 Vista 刚出，UAC 还是新鲜事物；今天（2026 年）UAC 已经是 Windows 安全模型的基石。

### 第一性原理视角

UAC 的本质是：**即使你是管理员，你的进程默认也只运行在标准用户权限下**。管理员权限不是"你有就有"，而是"你需要时显式请求"。

这是 Windows 安全模型的一次范式转移——从"管理员进程一直拥有全部权限"变成"权限按需提升，默认最小权限"。

### 4.5.1 自动提升进程的权限

**触发条件**：当 EXE 的清单文件（Manifest）中包含：

```
<requestedExecutionLevel level="requireAdministrator" uiAccess="false" />
```

或者系统通过启发式检测到程序可能需要管理员权限（如文件名包含 "setup", "install", "update" 等），会弹出 UAC 提权对话框。

**自动提升的流程**：

1. Shell 检测到需要提升
2. 弹出 UAC 对话框（在 Secure Desktop 上，防止伪造）
3. 用户确认后，通过 `AppInfo` 服务（AIS）创建新进程，新进程运行在**高完整性级别**（High IL），令牌中包含管理员组的完整权限
4. 原进程（标准用户权限）和新进程（管理员权限）是**两个完全不同的进程**，有不同的 PID、不同的令牌、不同的安全上下文

> 💡 **洞见**：自动提升不是"给现有进程加权限"，而是"创建一个权限更高的新进程"。这是关键区别——进程创建后，其令牌是**不可变的**。你不能把一个正在运行的标准用户进程"升级"为管理员进程。

### 4.5.2 手动提升进程的权限

通过 `ShellExecute` 或 `ShellExecuteEx` 以 `runas` 动词启动：

```
ShellExecute(
    NULL,
    L"runas",           // 动词：请求提升
    L"C:\\Windows\\System32\\cmd.exe",
    NULL,
    NULL,
    SW_SHOW
);
```

或者用 `ShellExecuteEx` 获取新进程的句柄：

```
SHELLEXECUTEINFO sei = { sizeof(sei) };
sei.lpVerb = L"runas";
sei.lpFile = L"C:\\Path\\To\\AdminApp.exe";
sei.nShow = SW_SHOW;
ShellExecuteEx(&sei);
// sei.hProcess 包含新进程的句柄
```

**与 `CreateProcess` 的区别**：

- `CreateProcess` **不能**提升权限——它创建的子进程继承父进程的令牌
- 要创建提升的子进程，必须用 `ShellExecute(Ex)` 的 `runas`，或者用 `CreateProcessAsUser` + 获取提升后的令牌（需要 `SeAssignPrimaryTokenPrivilege`）
- `runas` 走的是 `AppInfo` 服务，它会处理 UAC 提示

**工业实践**：

- 现代应用程序的推荐架构是**分离模式**：主程序以标准用户权限运行，只在需要执行管理操作时，通过 `runas` 启动一个小的辅助进程来执行提权操作，操作完成后辅助进程退出
- 这就是 Windows 设置应用、设备管理器等的做法

### 4.5.3 何为当前权限上下文

**关键概念**：每个进程运行在特定的**完整性级别（Integrity Level）**上：

|完整性级别|典型场景|
|---|---|
|System (0x4000)|系统服务、内核驱动|
|High (0x3000)|管理员提权后的进程|
|Medium (0x2000)|标准用户进程（大多数程序）|
|Low (0x1000)|沙箱进程（IE 保护模式、AppContainer）|

**权限上下文 = 令牌 + 完整性级别 + 特权（Privileges）**。

**关键事实**：

- 进程的完整性级别决定了它能写入哪些对象。High IL 进程可以写入 Medium IL 进程的文件，但反过来不行（强制完整性控制，MIC）
- 即使你是管理员，默认进程的 IL 是 Medium。只有提权后才是 High
- 特权（如 `SeDebugPrivilege`, `SeShutdownPrivilege`）在管理员令牌中是"默认禁用"的，即使提权后也需要显式启用

```
// 检查当前进程是否以管理员身份运行
BOOL IsRunningAsAdmin() {
    BOOL fIsAdmin = FALSE;
    PSID pAdminGroup = NULL;
    SID_IDENTIFIER_AUTHORITY NtAuthority = SECURITY_NT_AUTHORITY;
    if (AllocateAndInitializeSid(&NtAuthority, 2,
            SECURITY_BUILTIN_DOMAIN_RID, DOMAIN_ALIAS_RID_ADMINS,
            0, 0, 0, 0, 0, 0, &pAdminGroup)) {
        CheckTokenMembership(NULL, pAdminGroup, &fIsAdmin);
        FreeSid(pAdminGroup);
    }
    return fIsAdmin;
}
```

> 💡 **工业洞见**：很多程序在启动时检查是否管理员，如果不是就提示用户"请以管理员身份运行"。但更好的 UX 是：**自动用 `runas` 重新启动自己**。这就是很多安装程序的做法——双击后检测到需要提权，自动重新以管理员身份启动。

### 4.5.4 枚举系统中正在运行的进程

`Process32First` / `Process32Next` 通过快照机制枚举进程：

```
HANDLE hSnapshot = CreateToolhelp32Snapshot(TH32CS_SNAPPROCESS, 0);
PROCESSENTRY32 pe = { sizeof(pe) };
Process32First(hSnapshot, &pe);
do {
    wprintf(L"PID=%u, Name=%s\n", pe.th32ProcessID, pe.szExeFile);
} while (Process32Next(hSnapshot, &pe));
CloseHandle(hSnapshot);
```

**关键细节**：

- `CreateToolhelp32Snapshot` 创建的是**某一时刻的快照**，不是实时视图。枚举期间进程可能已退出
- `szExeFile` 只是 EXE 文件名，不是完整路径。要获取完整路径，需要用 `OpenProcess` + `QueryFullProcessImageName`
- 打开其他进程需要 `PROCESS_QUERY_INFORMATION` 权限。对受保护进程（如 Antimalware、PPL）可能失败

**现代替代方案**：

- `WTSEnumerateProcesses`：终端服务环境下枚举进程（能看到会话 ID）
- `EnumProcesses`（Psapi.h）：更简单但信息更少
- PowerShell：`Get-Process` 底层也是这些 API

### 4.5.5 Process Information 示例程序

这个示例程序展示了如何获取进程的详细信息：

- 用 `OpenProcess` 打开目标进程
- 用 `GetProcessTimes` 获取创建时间、用户态/内核态 CPU 时间
- 用 `GetProcessMemoryInfo` (PSAPI) 获取内存使用信息
- 用 `GetProcessIoCounters` 获取 I/O 统计

**工业实践延伸**：

现代进程监控工具（如 Process Explorer、任务管理器）使用的更底层 API：

- `NtQuerySystemInformation`：获取系统级进程信息（未文档化的原生 API，但被广泛使用）
- `QueryFullProcessImageName`：获取进程完整映像路径（Vista+）
- `GetProcessIntegrityLevel`：通过 `GetTokenInformation` 获取进程的完整性级别
- `EnumProcessModulesEx`：枚举进程加载的模块（包括 32 位/64 位混合）

> 💡 **一个工程经验**：写进程管理工具时，`OpenProcess` 失败不一定意味着"进程不存在"——可能是权限不够。高完整性级别的进程不能打开低完整性级别进程的某些句柄（实际上反过来是可以的，但受限于 DACL）。正确的做法是用 `PROCESS_QUERY_LIMITED_INFORMATION` 代替 `PROCESS_QUERY_INFORMATION`，前者需要的权限更低。

## 章节联系：进程的"生老病死"全图景

把 4.1~4.5 全部串起来，我们得到了 Windows 进程的完整生命周期：

```
创建配置(4.1) → CreateProcess(4.2) → 运行 → 终止(4.3)
                                          ↓
                                    子进程管理(4.4)
                                          ↓
                                    权限上下文(4.5)
```

**核心第一性原理**：

1. **进程是契约，不是实体**。CreateProcess 的 10 个参数就是契约条款，进程的一生都受这些条款约束
2. **优雅退出是工程美德**。主线程返回 > ExitProcess > TerminateProcess，优先级递减。永远追求第一种
3. **权限是创建时决定的，不是运行时改变的**。UAC 不是给进程"加权限"，而是创建"另一个更高权限的进程"
4. **进程隔离是 Windows 安全的基础**。即使你是管理员，默认也不给你管理员权限——这是"最小权限原则"的体现

**与前后章节的联系**：

- 第3章的内核对象：进程本身就是一个内核对象，`CreateProcess` 创建它，`TerminateProcess` 强制销毁它，`WaitForSingleObject` 等待它——所有操作都通过句柄
- 第5章（预告）：作业对象（Job Object）是"进程的容器"——可以把多个进程放进一个作业，统一限制它们的资源使用。这是 4.4 节子进程管理的升级版
- 第6章（预告）：线程是进程内的执行单元。4.3.1 讲的主线程返回触发进程终止，反过来理解就是——线程才是真正干活的，进程只是"装着线程的盒子"

**给工业实践的硬建议**：

1. **永远让 main 返回，不要手动 ExitProcess**
2. **永远不要在正常逻辑中 TerminateProcess 别的进程**——先发 WM_CLOSE，等超时，最后才考虑强制
3. **创建子进程时显式指定 lpCurrentDirectory 和 STARTUPINFO**——不要依赖继承
4. **UAC 时代，程序默认以标准用户运行**——需要管理员权限的操作，用 runas 启动辅助进程
5. **用 RAII 管理 PROCESS_INFORMATION**——别忘了关 hThread
6. **枚举进程时用 PROCESS_QUERY_LIMITED_INFORMATION**——兼容性更好，权限要求更低
7. **服务程序创建进程时，注意 Session 0 隔离**——用 `CreateProcessAsUser` 或 `WTSQueryUserToken` + `CreateProcessAsUser`

> ⚠️ **现代延伸（2026 视角）**：Windows 11 的"应用执行别名"（App Execution Aliases）和 Microsoft Store 应用的"稀疏包"（Sparse Package）机制，让进程的创建和权限管理又多了一层抽象——进程不仅有令牌和完整性级别，还有"包身份"（Package Identity）。这影响文件系统重定向（VFS）、注册表虚拟化、能力（Capabilities）等。这是 Richter 时代完全没有的东西，但在今天的 Windows 应用开发中越来越重要。
