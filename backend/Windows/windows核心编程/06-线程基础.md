
第6章是整本书从"资源"走向"执行"的核心转折点。前5章我们讲了错误码（状态）、字符串（数据）、内核对象（资源的受控入口）、进程（资源的容器）、作业（容器的容器）。现在终于到了真正"干活"的东西——**线程**。

**第一性原理视角**：进程是"资源的容器"，线程是"执行的载体"。这句话在第4章提过，但只有到了第6章你才会真正理解它的重量——**线程是 Windows 调度器唯一看得见的东西**。进程不执行代码，作业不执行代码，只有线程在执行代码。一个进程可以没有线程（刚 `CreateProcess` 但主线程还没 Resume），但一个线程不能没有进程（它的所有资源——地址空间、句柄表、堆——都住在进程里）。所以线程的本质是：**在已有的进程地址空间内，分配一块栈内存，设置一个 CPU 上下文，让 CPU 开始从指定的函数取指执行**。

## 6.1 何时创建线程

### 原书核心观点

Richter 列举了典型的线程使用场景：

- 处理长时间运行的任务，同时保持 UI 响应
- 并行计算，利用多核 CPU
- 异步 I/O 操作
- 监听网络端口、消息队列等阻塞等待

### 第一性原理洞见

**线程存在的唯一理由是"并发"和"响应性"**。

从 CPU 调度器的视角看，单核机器上"多线程"并不是真正的并行，只是快速切换造成的幻觉。但即使如此，它解决了两个根本问题：

1. **响应性**：UI 线程不能被阻塞。如果主线程去算一个 10 秒的矩阵乘法，窗口就会"未响应"。把计算丢给工作线程，UI 线程就能继续处理消息泵。
2. **阻塞等待的重叠**：当线程 A 在等 I/O（磁盘、网络）时，CPU 是空闲的。线程 B 可以利用这个空闲时间片做计算。

**但线程不是免费的**。创建线程的代价包括：

- 线程内核对象的分配（第3章讲过，有 HandleCount 和 PointerCount）
- 栈内存的分配（默认 1MB）
- 上下文切换的 CPU 开销（保存/恢复寄存器、TLB 刷新、CPU 缓存失效）

### 现代工业实践

2026 年的视角下，**手动调用 `CreateThread` 创建线程已经不是最佳实践**。现代工业级应用更倾向于：

- **线程池（Thread Pool）**：Windows 提供了系统线程池 API（`CreateThreadpoolWork`、`SubmitThreadpoolWork` 等），.NET 有 `ThreadPool`，C++ 有任务并行库。线程池的核心思想是**复用线程**，避免频繁创建/销毁的开销
- **异步 I/O + 完成端口（IOCP）**：对于 I/O 密集型应用，用少量线程 + 异步 I/O 就能处理大量并发连接（这就是 Nginx、Node.js、Redis 的高并发模型）
- **C++20 协程**：协程在用户态实现"协作式多任务"，避免了内核态上下文切换的开销，是"轻量级线程"的现代演进

> 💡 **洞见**：判断"何时创建线程"的现代答案变成了——**几乎永远不要手动创建线程，用线程池或异步模型**。手动 `CreateThread` 只应该在写底层框架、驱动封装、或者学习操作系统原理时使用。

## 6.2 何时不应该创建线程

### 原书核心观点

Richter 明确指出了以下情况不应该创建线程：

- 不应该为每个微小的任务都创建一个线程（线程创建/销毁的开销可能超过任务本身）
- 不应该在单 CPU 机器上创建大量线程（上下文切换会拖垮性能）
- 不应该用线程来处理可以快速完成的操作（直接同步执行更快）
- 不应该用线程来替代异步 I/O（I/O 完成端口更高效）

### 第一性原理洞见

**线程是"重"的并发原语**。每个线程默认分配 1MB 栈空间（32 位默认 1MB，64 位也是默认 1MB 但地址空间充裕得多），加上内核对象、上下文切换的缓存污染，线程的"体重"决定了它不适合细粒度并发。

**上下文切换的隐性成本**：

- 保存当前线程的 CPU 寄存器到线程内核对象
- 将新线程的寄存器从内核对象加载到 CPU
- TLB（Translation Lookaside Buffer）可能部分失效，导致内存访问变慢
- L1/L2 缓存中的热数据可能失效，因为新线程访问的是不同的内存区域

Raymond Chen（The Old New Thing）曾举例说明：一个进程有 2000 个线程，即使每个线程都只做一点点事，光是上下文切换就能让 CPU 忙得不可开交——这就是"惊群效应"的一种。

### 现代工业实践

- **线程池的线程数调优**：工业级应用通常把线程池大小设为 `CPU核心数 * 2` 或 `CPU核心数 + 1`，而不是无限增长
- **避免过度线程化**：Chrome 浏览器早期版本曾因每个标签页一个进程（后来改为每个站点一个进程）导致内存暴涨，后来引入了"服务进程"和"渲染进程"的精细划分
- **用任务（Task）替代线程**：C# 的 `Task`、`std::async`、Java 的 `CompletableFuture` 都是"逻辑任务"抽象，底层由线程池调度，避免了直接管理线程的复杂性

> ⚠️ **一个常见误区**：很多人以为"线程越多，程序越快"。实际上，线程数超过 CPU 核心数后，性能反而会下降——因为上下文切换的开销开始超过并行收益。这就是 Amdahl 定律在多线程场景的体现。

## 6.3 编写第一个线程函数

### 原书核心观点

线程函数的签名必须是：

```
DWORD WINAPI ThreadFunc(PVOID pvParam);
```

- 必须是 `__stdcall` 调用约定（WINAPI 宏展开为 `__stdcall`）
- 参数是一个 `void*`，可以指向任何数据结构
- 返回值 `DWORD` 是线程的退出码

### 第一性原理洞见

**线程函数是线程的"main 函数"**。它和进程的 `main`/`WinMain` 扮演完全相同的角色——是线程执行的起点，也是终点。线程函数返回，线程就结束了（和 `main` 返回进程就结束一样）。

**为什么必须是 `__stdcall`？**​ 这是 Windows API 的历史约定。`__stdcall` 规定被调用者清理栈，这样内核在启动线程时不需要知道线程函数需要多少栈空间。而 C 默认的 `__cdecl` 是调用者清理栈，不适合作为线程入口。

**`pvParam` 的设计哲学**：`void*` 是 C/C++ 里的"万能指针"，它让线程函数可以接收任何类型的参数。这是一种**类型擦除**——调用者知道传的是什么，线程函数内部需要强制转换回来。现代 C++ 里，这种模式被 `std::function`、`lambda` 捕获列表所取代，但底层原理不变。

### 现代工业实践

```
// 现代 C++ 风格：用 lambda + std::thread（底层还是 _beginthreadex）
std::thread t([] {
    // 线程逻辑
});
t.join();
```

但如果是原生 Win32 编程：

```
struct ThreadParams {
    HANDLE hEvent;
    int nIterations;
};

DWORD WINAPI WorkerThread(PVOID pvParam) {
    ThreadParams* p = static_cast<ThreadParams*>(pvParam);
    for (int i = 0; i < p->nIterations; ++i) {
        // 工作逻辑
    }
    SetEvent(p->hEvent);
    return 0;
}
```

> 💡 **工程洞见**：线程函数的参数**绝不能**是栈上的局部变量（除非你确定线程在局部变量销毁前已经用完），因为线程启动是异步的，父函数可能在线程读取参数前就返回了。参数应该来自堆分配、全局变量、或 `std::shared_ptr`。

## 6.4 CreateThread 函数

`CreateThread` 是创建线程的内核级 API。它的完整签名：

```
HANDLE CreateThread(
    PSECURITY_ATTRIBUTES   psa,
    SIZE_T                 cbStackSize,
    LPTHREAD_START_ROUTINE pfnStartAddr,
    PVOID                  pvParam,
    DWORD                  dwCreateFlags,
    PDWORD                 pdwThreadID
);
```

**核心流程**：

1. 创建线程内核对象（HandleCount=1, PointerCount=2——因为线程本身和创建者各持有一个引用）
2. 分配栈内存（保留 1MB 虚拟地址空间，提交初始页面）
3. 初始化上下文（Context），设置指令指针指向 `pfnStartAddr`，栈指针指向栈顶
4. 线程进入"就绪"状态，等待调度器分配 CPU 时间片

### 6.4.1 psa 参数

`psa` 是线程内核对象的安全描述符。和进程一样，控制谁能访问这个线程内核对象。

**关键洞见**：

- 线程内核对象的安全描述符决定了谁能 `TerminateThread`、`SuspendThread`、`GetThreadContext` 等
- 大多数应用程序传 `NULL`，使用默认安全描述符（继承父进程的令牌）
- 在沙箱场景（如作业对象内），可能需要设置严格的 DACL，防止其他进程操作你的线程

### 6.4.2 cbStackSize 参数

指定线程栈的**保留大小**（reserve size）。传 0 表示使用 EXE 头中指定的默认大小（通常是 1MB）。

**栈的内存布局**：

- 保留（Reserve）：1MB 虚拟地址空间
- 提交（Commit）：初始只提交 1 个页面（4KB 或 8KB，取决于系统），加上一个"防护页"（Guard Page）
- 当栈增长触及防护页时，触发 `STATUS_GUARD_PAGE_VIOLATION` 异常，内核捕获后提交下一个页面，并移动防护页
- 如果栈增长超过 1MB，触发栈溢出异常（`STATUS_STACK_OVERFLOW`）

> ⚠️ **工程警告**：栈溢出是 C/C++ 程序最常见的崩溃原因之一。递归过深、大型局部数组（如 `char buffer[1024 * 1024]`）都会导致栈溢出。现代编译器会警告大型栈分配，建议改用堆（`std::vector`、`malloc`）。

**现代视角**：64 位进程的地址空间极大（128TB 用户态），所以栈大小不再是稀缺资源。但栈的大小仍然影响内存提交量——如果创建 1000 个线程，每个默认 1MB 栈，那就是 1GB 的虚拟内存（虽然大部分是保留未提交的）。

### 6.4.3 pfnStartAddr 和 pvParam 参数

`pfnStartAddr` 是线程函数的入口地址。`pvParam` 是传给线程函数的参数。

**关键陷阱**：

- `pfnStartAddr` 必须是 `__stdcall` 函数。如果你传了一个 `__cdecl` 函数，栈会不平衡，导致未定义行为
- `pvParam` 的生命周期必须覆盖线程的整个执行期。最常见的错误：

```
// 错误示例！
void StartThread() {
    int x = 42;
    CreateThread(NULL, 0, ThreadFunc, &x, 0, NULL);  // x 在栈上！
}  // 函数返回后 x 被销毁，线程访问的是悬垂指针
```

**正确做法**：

```
// 正确：堆分配
int* px = new int(42);
CreateThread(NULL, 0, ThreadFunc, px, 0, NULL);
// 线程函数内 delete px
```

### 6.4.4 dwCreateFlags 参数

常用的值：

- `0`：线程创建后立即就绪，等待调度
- `CREATE_SUSPENDED`：线程创建后挂起（暂停状态），直到 `ResumeThread` 被调用

**`CREATE_SUSPENDED` 的工业价值**：

- 在 Resume 之前，你可以安全地修改线程的优先级、设置线程亲和性、甚至修改上下文（`SetThreadContext`）
- 第5章讲作业对象时提到的"三段式"：`CREATE_SUSPENDED` + `AssignProcessToJobObject` + `ResumeThread`——这里同样适用于线程：创建挂起的线程 → 加入作业 → 设置优先级 → Resume

### 6.4.5 pdwThreadID 参数

返回线程 ID（TID）。TID 和 PID 一样是**可重用的**——线程退出后，TID 可能被分配给新的线程。

**关键事实**：

- TID 在整个系统范围内唯一（同一时刻）
- 线程 ID 不等于线程内核对象的句柄。句柄是进程私有的索引，TID 是系统级的标识符
- 可以用 `OpenThread` 通过 TID 打开线程句柄（需要相应权限）

## 6.5 终止运行线程

### 6.5.1 线程函数返回

这是**唯一正确的线程退出方式**。

当线程函数返回时：

1. 线程函数中创建的所有 C++ 局部对象（在栈上）的析构函数被调用
2. 线程的栈内存被释放（虚拟地址空间被回收）
3. 线程内核对象的 `ExitCode` 被设为返回值
4. 线程内核对象的 `PointerCount` 减 1（如果归零，内核对象被销毁）
5. 递减该线程所属进程的 `HandleCount`（在作业统计中可见）

**洞见**：线程函数返回和进程的主线程返回（`main` 返回）是对称的。它们都是"优雅退出"的典范——资源被自动清理，没有遗留问题。

### 6.5.2 ExitThread 函数

```
VOID ExitThread(DWORD dwExitCode);
```

这是线程的"自杀"函数，类似于进程的 `ExitProcess`。

**为什么不应该用**：

- `ExitThread` 会**立即终止线程**，不会调用栈上 C++ 对象的析构函数
- 不会返回到调用者，所以 `finally` 块（SEH）也不会执行
- 如果线程是主线程，调用 `ExitThread` 会导致进程中的所有线程继续运行——进程不会退出，但主线程没了，这可能导致资源泄露

**与 `_endthreadex` 的区别**：

- `ExitThread` 是 Windows API，不清理 C 运行时（CRT）的状态
- `_endthreadex` 是 CRT 函数，会调用 CRT 的清理逻辑（如释放 TLS 等）
- 如果用 `_beginthreadex` 创建的线程，应该用 `_endthreadex` 或让线程函数返回；如果用 `CreateThread` 创建的线程，应该用 `ExitThread` 或让线程函数返回

> 🚨 **工业实践铁律**：**永远让线程函数返回，不要手动调用 `ExitThread` 或 `_endthreadex`**。这和"永远让 main 返回，不要手动 ExitProcess"是同一个道理。

## 章节联系：线程是 Windows 并发模型的"原子"

把第6章上半部分放到整本书的脉络里：

**与第3章（内核对象）的联系**：

- 线程本身就是一个内核对象，具有使用计数、安全描述符、句柄表项
- 线程内核对象的 `PointerCount` 和 `HandleCount` 机制和第3章讲的一模一样

**与第4章（进程）的联系**：

- 进程是线程的"容器"。`CreateProcess` 创建进程内核对象 + 主线程内核对象
- 主线程的入口函数是 `main`/`WinMain`，工作线程的入口函数是 `ThreadFunc`
- 进程退出时，所有线程被强制终止（第4章讲过）

**与第5章（作业）的联系**：

- 作业可以限制作业内所有线程的 CPU 时间、优先级类
- `CREATE_SUSPENDED` + 作业 + `ResumeThread` 是沙箱的标准模式

**与后续章节的预告**：

- 第7章（线程调度）：线程的优先级、时间片、调度算法
- 第8章（线程同步）：多个线程访问共享资源时的同步问题（互斥量、信号量、事件等）
- 第9章（线程局部存储）：每个线程独有的数据

**第一性原理的升华**：

线程回答了"如何让一个进程同时做多件事"的问题。但它的代价是——**并发带来了不确定性**。两个线程同时写同一个变量，结果是什么？这就是后续章节要解决的同步问题。线程是强大的工具，但也是 bug 的温床。理解线程的创建和终止，是理解并发编程的第一步。

### 工业实践的硬建议

1. **永远让线程函数返回，不要调用 `ExitThread`**
2. **不要手动 `CreateThread` 来做简单任务，用线程池**
3. **线程参数必须用堆分配或全局变量，绝不能用栈上的局部变量**
4. **创建线程时考虑用 `CREATE_SUSPENDED`，在 Resume 前完成所有初始化**
5. **线程函数签名必须是 `__stdcall`，返回 `DWORD`**
6. **永远不要忽略线程的退出码**——通过 `GetExitCodeThread` 检查线程是否正常结束
7. **C++ 项目用 `std::thread` 或 `std::jthread`**（C++20），它们底层封装了 `_beginthreadex`，自动处理 CRT 初始化和清理

> ⚠️ **现代延伸（2026 视角）**：C++20 引入了协程（`std::coroutine`），它允许在用户态实现"协作式多任务"，避免了内核态上下文切换的开销。在 Windows 上，协程可以和 I/O 完成端口结合，实现高并发的网络服务器。这是 Richter 写书时（2007 年）无法预见的技术，但今天已经成为 C++ 并发编程的前沿。理解 `CreateThread` 的底层机制，是理解协程为什么"轻量"的前提——因为协程不需要内核对象、不需要栈切换、不需要上下文切换。


下半部分接上半部分，讲的是线程的"死法"、线程在内核里到底是什么、以及 C/C++ 运行库和线程的隐秘契约。这三块内容表面上零散，但贯穿着同一个第一性原理：**线程不是孤立的执行流，它是进程内全局状态的参与者**。你杀一个线程，可能影响整个进程；你创建一个线程，就默认签下了 CRT 的契约；你拿到一个"线程句柄"，还得搞清楚它是真的还是伪的。

## 6.5.3 TerminateThread 函数

这是整个 Windows API 里最危险的函数之一，没有之一。Microsoft Learn 的官方文档开篇明义：

> "TerminateThread 是一个危险的函数，只能在最极端的情况下使用。仅当确切地知道目标线程正在执行的操作，并且控制目标线程可能在终止时运行的所有代码时，才应调用 TerminateThread。"

### 为什么这么危险：四个致命后果

Microsoft 官方列出了调用 `TerminateThread` 可能导致的具体灾难 ：

1. **临界区永不释放**：如果目标线程正持有临界区（Critical Section），它不会被释放。这意味着其他任何等待该临界区的线程都会永久死锁。
2. **堆锁永不释放**：如果目标线程正在从堆分配内存，堆锁不会被释放。整个进程的堆管理陷入不一致——后续所有 `malloc/new` 都可能挂死。
3. **Kernel32 状态不一致**：如果目标线程在被终止时正在执行某些 kernel32 调用，该线程所在进程的 kernel32 状态可能不一致。这会导致后续所有调用 kernel32 的线程行为异常。
4. **共享 DLL 的全局状态被毁**：如果目标线程正在操作共享 DLL 的全局状态，DLL 的状态可能被破坏，影响该 DLL 的其他所有使用者。

更可怕的是官方文档里这句话："**目标线程没有机会执行任何用户模式代码。附加到线程的 DLL 不会收到线程正在终止的通知。**" ——这意味着 `DLL_THREAD_DETACH` 不会被调用，线程局部存储（TLS）的析构函数不会被执行，C++ 局部对象的析构函数也不会被调用。

> 🚨 **历史坑**：Windows Server 2003 和 Windows XP 上，被 `TerminateThread` 终止的线程，其初始栈不会被释放，导致资源泄露 。虽然现代 Windows 会释放初始栈 ，但其他资源泄露问题依然存在。

### 线程无法自我保护

官方文档明确指出一个残酷的事实 ：

> "线程无法保护自身免受 TerminateThread 的侵害，只能通过控制对其句柄的访问。`CreateThread` 和 `CreateProcess` 函数返回的线程句柄具有 `THREAD_TERMINATE` 访问权限，因此任何持有这些句柄之一的调用方都可以终止你的线程。"

这意味着：**只要你把线程句柄泄露出去（比如通过句柄继承、DuplicateHandle、或者句柄表攻击），别人就能随时杀掉你的线程**。SEI CERT 安全编码标准（WIN01-C）明确把"强制终止线程"列为高危操作，要求用协作式退出替代 。

### 工业级替代方案：协作式终止

正确做法是让目标线程"自己退出"：

```
// 全局标志，用 Interlocked 操作保证线程安全
volatile LONG g_fShouldExit = 0;

// 目标线程的主循环
DWORD WINAPI WorkerThread(PVOID pvParam) {
    while (InterlockedCompareExchange(&g_fShouldExit, 0, 0) == 0) {
        // 做工作，定期检查退出标志
        DoSomeWork();
        // 关键：用 WaitForSingleObject 等待事件时，设置超时，
        // 这样即使被等待的对象一直不触发，也能定期检查退出标志
        if (WaitForSingleObject(hWorkEvent, 100) == WAIT_TIMEOUT) {
            continue;  // 超时返回，重新检查退出标志
        }
    }
    return 0;  // 优雅退出，所有清理自动执行
}

// 请求线程退出的代码
InterlockedExchange(&g_fShouldExit, 1);
SetEvent(hWorkEvent);  // 唤醒可能阻塞的线程
WaitForSingleObject(hWorkerThread, INFINITE);  // 等待真正退出
```

**现代 C++ 的最佳实践**：用 `std::atomic<bool>` 替代 `volatile LONG`，用 `std::condition_variable` 替代事件等待，用 `std::jthread`（C++20）自动在析构时请求退出并 join 。

> ⚠️ **绝对规则**：`TerminateThread` 只应该在"目标线程已经失控、且你完全清楚它在做什么"的极端场景下使用（比如超时强制清理一个卡死的第三方库调用）。正常的线程终止，永远让线程函数返回。

## 6.5.4 进程终止运行时

进程终止时，系统会做以下事情 ：

1. **所有剩余线程被标记终止**——注意是"标记"，不是立即杀死。如果某个线程正在等待内核对象，它不会被立即终止，要等等待完成后才能被终止。这可能导致应用程序停止响应
2. **进程分配的所有资源被释放**
3. **所有内核对象句柄被关闭**——但对象本身在所有句柄都关闭后才真正销毁（第3章讲过的使用计数机制）
4. **进程代码从内存中移除**
5. **进程退出码被设置**
6. **进程对象变为 signaled 状态**，释放所有等待该进程退出的线程

### 四种进程终止方式的对比

|方式|是否调用 DLL 的 `DLL_PROCESS_DETACH`|是否干净|
|---|---|---|
|主线程入口函数返回|✅ 是（通过 CRT 转发）|最干净|
|调用 `ExitProcess`|✅ 是|较干净，但不执行 C++ 全局对象析构|
|调用 `TerminateProcess`|❌ 否|最脏|
|最后一个线程终止|✅ 是|干净|

Microsoft 官方明确指出 ：

> "如果进程因 `TerminateProcess` 而终止，该进程的所有线程会立即终止，没有机会运行额外代码。这意味着线程不执行终止处理程序块中的代码。此外，附加的 DLL 不会收到进程正在分离的通知。"

这就是为什么第4章强调"永远让主线程返回"——只有这种方式，C++ 全局对象的析构函数才会被调用、DLL 的 `DLL_PROCESS_DETACH` 才会被触发、`atexit` 注册的函数才会被执行。

### 一个关键细节：子进程不被自动终止

> "系统在终止进程时，不会终止该进程创建的任何子进程。"

这意味着如果你用 `TerminateProcess` 杀掉一个父进程，它的子进程会变成"孤儿进程"继续运行。这正是第5章作业对象的价值所在——`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` 可以确保父进程退出时整个作业树被清理。

## 6.5.5 线程终止运行时

线程终止时，系统会 ：

1. **线程拥有的资源（如窗口和挂钩）被释放**
2. **线程退出码被设置**
3. **线程对象变为 signaled**，释放所有等待该线程退出的线程
4. **如果这是进程中最后一个活动线程，进程将终止**
5. **线程对象在所有句柄关闭前不会释放**

### 线程终止的五种方式

1. 线程函数返回（✅ 推荐）
2. 线程调用 `ExitThread`（⚠️ 不推荐，但比被强制终止好）
3. 进程中的任何线程调用 `ExitProcess`（⚠️ 不建议主动调用）
4. 其他线程用线程句柄调用 `TerminateThread`（🚨 危险）
5. 其他线程用进程句柄调用 `TerminateProcess`（🚨 危险，连带杀死所有线程）

### 关键洞见

`GetExitCodeThread` 返回 `STILL_ACTIVE` 表示线程仍在运行；线程终止后，退出码从 `STILL_ACTIVE` 变为线程函数返回值或 `TerminateThread`/`ExitThread` 指定的值 。

> 💡 **工程经验**：很多程序员错误地用"轮询 `GetExitCodeThread` 是否等于 `STILL_ACTIVE`"来判断线程是否还活着。正确做法是 `WaitForSingleObject(hThread, 0)` 检查线程对象是否 signaled——这利用了"线程终止时对象变为 signaled"的机制，效率更高且不依赖退出码约定。

## 6.6 线程内幕

这一节 Richter 讲了线程在内核里的真实数据结构。结合现代 Windows 内核架构，线程在内核中由三个核心数据结构描述 ：

```
┌─────────────────────────────────────────┐
│              ETHREAD                      │ ← 执行体线程块（Executive Thread Block）
│  ┌─────────────────────────────────────┐  │
│  │            KTHREAD                   │  │ ← 内核线程块（Kernel Thread Block）
│  │  • 调度信息（优先级、状态、量子）    │  │
│  │  • 同步数据                          │  │
│  │  • 内核栈                            │  │
│  │  • TEB 指针                          │  │
│  │  • CPU 上下文（寄存器）              │  │
│  └─────────────────────────────────────┘  │
│  • 所属进程指针                            │
│  • 线程起始例程地址                        │
│  • 线程 ID                                 │
└─────────────────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────┐
│               TEB                         │ ← 线程环境块（Thread Environment Block）
│  • 线程 ID                                │
│  • 用户态栈指针                           │
│  • 线程局部存储（TLS）数组                │
│  • LastError 值（这就是第1章讲的线程局部错误码！）│
└─────────────────────────────────────────┘
```

**三个结构的分工**：

- **ETHREAD**：Executive 层，包含线程的大部分信息（ID、所属进程、I/O 请求列表等）
- **KTHREAD**：调度器真正关心的部分，包含纯粹的调度信息（优先级、状态、栈指针、CPU 寄存器上下文）
- **TEB**：用户态可访问的数据结构，包含线程 ID、用户栈、TLS 数组

### 第一性原理：Windows 调度线程，不调度进程

Microsoft 内核开发者的讲义明确写道 ：

> "Windows schedules threads, not processes. Scheduling is preemptive, priority-based, and round-robin at the highest-priority."

这句话是整个 Windows 调度哲学的浓缩：

- **抢占式**：高优先级线程可以立即抢占低优先级线程
- **基于优先级**：32 级优先级（0-31），0 保留给零页线程，1-15 是动态优先级，16-31 是实时优先级
- **同优先级轮转**：同优先级线程轮流执行（Round-Robin）

### 上下文切换的成本

当线程被切换出去时，它的 CPU 寄存器状态被保存到 KTHREAD 中。下次该线程被调度时，寄存器从 KTHREAD 恢复。这就是为什么上下文切换有成本——不光是寄存器保存/恢复，还包括：

- TLB 刷新（因为地址空间可能切换——不过 Windows 优化了，同一进程的线程切换不刷 TLB）
- CPU 缓存失效（新线程访问的是不同的内存区域）
- 分支预测器状态失效

> 💡 **洞见**：理解了 KTHREAD 里保存 CPU 上下文，你就理解了为什么线程创建时要指定栈大小、为什么 `CreateThread` 的第一个参数 `psa` 控制线程内核对象的安全性——因为这些都直接映射到 KTHREAD/ETHREAD 里的字段。

### 工业实践延伸

现代 Windows 调度器还引入了 ：

- **CPU 集合（CPU Sets）**：`SetThreadSelectedCpuSets` 允许精确控制线程能跑在哪些 CPU 核心上
- **理想处理器（Ideal Processor）**：`SetThreadIdealProcessor` 指定首选处理器，减少缓存失效
- **NUMA 感知调度**：调度器尝试让线程在其本地内存节点上运行
- **优先级提升/衰减**：GUI 前台线程、等待事件的线程会得到临时优先级提升；CPU 密集型线程的优先级会衰减

## 6.7 C/C++ 运行库注意事项

这是整个第6章最容易被人忽视、但坑最深的一节。

### 6.7.1 用 `_beginthreadex` 而不要用 `CreateThread` 创建线程

**核心问题**：`CreateThread` 是纯 Win32 API，它创建的是一个"裸"线程——不初始化 C 运行库（CRT）的线程局部状态。而 `_beginthreadex` 是 CRT 提供的函数，它在内部调用 `CreateThread`，但**额外做了关键的初始化工作**。

**具体差异**：

|维度|`CreateThread`|`_beginthreadex`|
|---|---|---|
|CRT 资源初始化|无|自动分配 `_tiddata` 结构|
|线程函数签名|`DWORD WINAPI`|`unsigned __stdcall`|
|资源清理|需手动调用 `ExitThread`|自动调用 `_endthreadex`|
|`errno`、`strtok`、`rand` 等|❌ 数据竞争/崩溃|✅ 线程安全|
|TLS 析构|❌ 不执行|✅ 自动执行|
|安全性|高风险（内存泄漏/崩溃）|安全（CRT 兼容）|

**底层机制**：`_beginthreadex` 在创建线程前会调用 `_initptd()` 初始化线程的 `_tiddata` 结构，这个结构包含了该线程专属的 `errno`、locale、堆句柄、浮点环境等 CRT 状态。线程函数返回时，`_endthreadex` 会自动清理这个结构 。

**灾难场景**：如果你用 `CreateThread` 创建线程，然后在该线程里调用 `printf`、`malloc`、`strtok`、`errno` 等任何 CRT 函数 ：

- `strtok` 会尝试访问当前线程的 `_tiddata`。由于 `CreateThread` 没有分配该结构，CRT 只能分配一个临时的、未初始化的内存块
- 多线程下，CRT 内部全局/静态变量被多个线程竞争修改，导致数据错乱
- 线程退出时，`_endthreadex` 不会被调用，导致 `_tiddata` 内存永远无法释放——**隐形内存泄漏**
- 在 DLL 中使用 `CreateThread` 且 DLL 卸载时线程尚未结束，CRT 的清理逻辑无法执行，导致进程在退出时挂起或崩溃

> ⚠️ **微软的明确建议**："凡使用 CRT 或 C++ 标准库的线程，必须用 `_beginthreadex` 而非 `CreateThread`"。

**现代 C++ 的最佳实践**：

```
// 传统 CRT 方式（仍广泛使用）
uintptr_t hThread = _beginthreadex(
    NULL, 0, 
    [](void* pvParam) -> unsigned {
        // 线程逻辑，可以使用 printf/malloc/strtok 等
        int* pData = static_cast<int*>(pvParam);
        // ...
        return 0;  // 自动调用 _endthreadex
    },
    pData, 0, NULL);
CloseHandle((HANDLE)hThread);

// 现代 C++ 方式（推荐）
#include <thread>
#include <iostream>
#include <memory>

void Worker(std::shared_ptr<WorkItem> item) {
    // 完整 CRT 支持，自动资源管理
    std::cout << "Processing " << item->id << std::endl;
}

std::thread t(Worker, std::make_shared<WorkItem>(42));
t.join();  // 或者 t.detach()
```

`std::thread` 底层也是用 `_beginthreadex`（在 Windows 上），但它提供了 RAII 语义——析构时自动 join 或 detach（取决于 `std::jthread` 或 `std::thread` 的使用方式），避免了忘记关闭句柄的资源泄露。

### 6.7.2 绝对不应该调用的 C/C++ 运行库函数

Richter 在这一节明确指出：**绝对不应该在 Windows 线程里调用 `ExitThread`**。

原因：

1. `ExitThread` 是 Windows API，不清理 C 运行时（CRT）的状态
2. 如果你用 `_beginthreadex` 创建了线程，必须让线程函数返回，这样 CRT 才能自动调用 `_endthreadex` 清理 `_tiddata`
3. 如果在 `_beginthreadex` 创建的线程里调用 `ExitThread`，`_tiddata` 结构永远不会被释放，造成内存泄露
4. 同理，C++ 的全局/静态对象析构函数也不会被调用

**对应的规则**：

- 用 `CreateThread` 创建的线程 → 可以让线程函数返回，或调用 `ExitThread`
- 用 `_beginthreadex` 创建的线程 → **必须**让线程函数返回（自动调用 `_endthreadex`），**绝不能**手动调用 `ExitThread`
- 用 `std::thread` 创建的线程 → 让可调用对象返回即可

> 💡 **一个简单的记忆法则**：线程函数返回 = 优雅退出。任何"手动终止线程"的函数（`ExitThread`、`TerminateThread`、`_endthreadex`）都应该避免，除非你在写底层框架。

## 6.8 了解自己的身份

### 6.8.1 将伪句柄转换为真正的句柄

Windows 提供了两个"伪句柄"函数：

- `GetCurrentProcess()` 返回 `0xFFFFFFFF`（即 -1，常量 `CURRENT_PROCESS`）
- `GetCurrentThread()` 返回 `0xFFFFFFFE`（即 -2，常量 `CURRENT_PROCESS`）

**为什么需要伪句柄？**​ 获取真实句柄需要遍历句柄表、增加引用计数，有性能开销。伪句柄是"自指"的语法糖——当你把这个伪句柄传给需要 HANDLE 参数的函数时，内核知道"哦，这是调用者自己"。

**伪句柄的局限**：

1. **伪句柄不能被其他进程使用**。你把 `GetCurrentThread()` 的返回值通过 IPC 传给另一个进程，那个进程用它调 `WaitForSingleObject`，等待的不是你的线程，而是它自己的线程。
2. **伪句柄不能被 DuplicateHandle 正确复制**。如果你调用 `DuplicateHandle(GetCurrentThread(), ...)`，目标进程拿到的句柄**仍然指向原进程中的当前线程**——这不是你想要的"真实句柄"。
3. **伪句柄不增加内核对象的引用计数**。这意味着伪句柄不会阻止线程对象被销毁。

**转换为真实句柄**：

```
// 把伪句柄转换为真实句柄
HANDLE hRealThread = NULL;
DuplicateHandle(
    GetCurrentProcess(),   // 源进程 = 当前进程
    GetCurrentThread(),    // 源句柄 = 伪线程句柄
    GetCurrentProcess(),   // 目标进程 = 当前进程
    &hRealThread,          // 输出真实句柄
    0,                     // 继承访问权
    FALSE,                 // 不可继承
    DUPLICATE_SAME_ACCESS  // 相同访问权
);
// 现在 hRealThread 是一个真实的线程句柄
// 可以把它传给其他线程/进程使用
// 用完后必须 CloseHandle(hRealThread)
```

**为什么需要真实句柄？**​ 典型场景：

1. **跨线程/进程传递**：你想让另一个线程等待你的线程结束，或者你想把线程句柄传给另一个进程
2. **句柄继承**：你想让子进程继承你的线程句柄（用 `CreateProcess` 的 `bInheritHandles=TRUE`）
3. **引用计数管理**：你想确保线程对象在你使用期间不被销毁
4. **设置线程属性**：某些线程操作需要真实句柄

> 💡 **工业实践洞见**：在多线程架构中，主线程经常需要把"自己的工作线程的真实句柄"传递给监控线程或 IPC 通道。这时就必须用 `DuplicateHandle` 转换。一个常见错误是程序员直接把 `GetCurrentThread()` 的返回值塞进共享内存传给其他线程——结果其他线程拿到的"真实线程句柄"实际上是它自己的伪句柄解释，完全不是预期行为。

**进程伪句柄同理**：

```
HANDLE hRealProcess = NULL;
DuplicateHandle(
    GetCurrentProcess(),
    GetCurrentProcess(),
    GetCurrentProcess(),
    &hRealProcess,
    0, FALSE, DUPLICATE_SAME_ACCESS);
// hRealProcess 现在是一个真实进程句柄
// 可以传给子进程、其他线程，或调用 DuplicateHandle 复制到其他进程
```

## 章节联系：线程是 Windows 并发模型的"原子"

把第6章上下半部分合起来，我们得到了 Windows 线程的完整图景：

```
创建(CreateThread/_beginthreadex) → 运行 → 终止(返回/ExitThread/TerminateThread)
   ↓                                        ↓
内核数据结构(ETHREAD/KTHREAD/TEB)      清理(CRT状态/DLL通知/资源释放)
   ↓                                        ↓
调度器(抢占式/优先级/轮转)             进程终止(所有线程被标记终止)
```

**与前面章节的联系**：

- **第3章（内核对象）**：线程本身就是一个内核对象，具有使用计数、安全描述符、句柄表项。`DuplicateHandle` 转换伪句柄的机制，正是第3章讲的内核对象句柄表的实践应用
- **第4章（进程）**：进程是线程的容器。`CreateProcess` 创建进程内核对象 + 主线程内核对象。进程终止时，所有线程被标记终止
- **第5章（作业）**：作业可以限制作业内所有线程的 CPU 时间、优先级类。线程的调度受作业约束

**与后续章节的联系**：

- **第7章（线程调度）**：6.6 节讲的 KTHREAD 里的优先级、量子、状态，就是第7章要展开讲的调度算法的数据结构基础
- **第8章（线程同步）**：6.5.3 讲的"临界区不释放"问题，正是线程同步要解决的——如何用互斥量、信号量、事件等机制，确保线程在退出前释放所有锁
- **第9章（线程局部存储）**：6.6 节讲的 TEB 里的 TLS 数组，就是 TLS 的存储位置；6.7 节讲的 `_tiddata` 结构，本质上也是 TLS 的一个应用

**第一性原理的升华**：

线程回答了"如何让一个进程同时做多件事"。但线程的引入带来了一个根本性的复杂化：**不确定性**。两个线程同时访问共享资源，结果取决于调度器的时序——这是竞态条件（Race Condition）的根源。Richter 在前6章铺垫的所有机制——错误码、字符串、内核对象、进程、作业、线程——都是单线程视角下的静态结构；从第8章开始，我们将进入多线程的动态世界，那里的第一性原理变成了"**任何共享状态都必须被同步保护**"。

### 工业实践的硬建议

1. **永远用 `_beginthreadex` 或 `std::thread` 创建线程**，绝不用裸 `CreateThread`（除非你 100% 确定线程函数不调用任何 CRT 函数）
2. **永远让线程函数返回**，不要调用 `ExitThread`、`_endthreadex`、`TerminateThread`
3. **需要终止其他线程时，用协作式退出**——设置退出标志 + 唤醒机制 + 等待线程真正退出
4. **`TerminateThread` 是核武器**，只能在"线程完全失控"的极端场景下使用，且要做好进程状态可能不一致的心理准备
5. **伪句柄不能跨线程/跨进程使用**，需要传递线程身份时，用 `DuplicateHandle` 转换为真实句柄
6. **用 RAII 管理线程句柄**：C++ 项目用 `std::thread`/`std::jthread`，它们底层处理了 CRT 初始化、句柄关闭等所有细节
7. **理解 ETHREAD/KTHREAD/TEB 的三层结构**，这有助于理解为什么线程创建有开销、为什么上下文切换有成本、为什么 TLS 访问很快

> ⚠️ **2026 年现代延伸**：C++20 引入了 `std::jthread`，它在 `std::thread` 的基础上增加了自动协作式退出——析构时自动调用 `request_stop()` 并 join。结合 C++20 的 `std::stop_token`，这是现代 C++ 多线程编程的推荐模式。在 Windows 上，`std::jthread` 底层仍然使用 `_beginthreadex`，但提供了更符合现代 C++ 语义的接口。理解第6章讲的 CRT 契约和线程终止机制，是理解为什么 `std::jthread` 这样设计的基础——它本质上是在 `_beginthreadex` + 协作退出标志 + RAII 之上的现代封装。
