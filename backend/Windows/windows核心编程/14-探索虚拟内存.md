## 14.1 系统信息

### 第一性原理：永远不要硬编码系统相关参数

Richter 在书中开篇就强调一个核心原则：**操作系统有许多值是由运行主机决定的**——如页面大小和分配粒度。**不应该将这些参数写死（硬编码到代码中），而是应该在进程初始化时取得这些值，然后在代码中使用**。

为什么这条原则如此重要？因为：

- 页面大小(page size)：x86/x64 上通常是 4KB，但并非所有架构都是
- 分配粒度(allocation granularity)：通常是 64KB，但理论上系统可以调整
- 处理器数量：直接决定线程池大小、并行度
- 处理器类型：x86/x64/ARM——影响指令集、对齐要求
- 内存分页大小：可能有大页(Large Page, 2MB/1GB)支持

**硬编码这些值 = 把程序绑死在特定硬件上**——换一台机器就可能崩溃或性能劣化。

### 核心 API：GetSystemInfo

```
VOID GetSystemInfo(LPSYSTEM_INFO lpSystemInfo);
```

`SYSTEM_INFO` 结构的关键字段：

|字段|含义|工业意义|
|---|---|---|
|`dwPageSize`|页面大小（字节）|VirtualAlloc 提交的最小单位|
|`dwAllocationGranularity`|分配粒度|VirtualAlloc 预订地址的对齐边界|
|`dwNumberOfProcessors`|逻辑处理器数|线程池大小、并行度|
|`dwProcessorType`|处理器类型|指令集选择|
|`wProcessorArchitecture`|处理器架构|x86/x64/ARM 分支判断|
|`dwActiveProcessorMask`|活动处理器掩码|亲和性设置|

### 系统信息示例程序

Richter 在书中提供了一个系统信息示例程序（14.1 节配套），它会调用 `GetSystemInfo` 并打印所有字段。这个程序的价值在于：**它是每个 Windows 系统程序员工具箱里的"hello world"**——在写任何内存相关代码前，先跑一遍看看目标机器的参数。

### 现代延伸：GetNativeSystemInfo 与 GetSystemInfo 的差异

在 WOW64（32 位程序运行在 64 位 Windows 上）环境中，这两个函数返回不同结果：

- `GetSystemInfo`：返回 32 位视图（处理器数可能被限制、架构显示为 x86）
- `GetNativeSystemInfo`：返回真实的 64 位系统信息

> 💡 **工业洞见**：现代安装包、大型应用（如 Chrome、Visual Studio）在安装或启动时会调用 `GetNativeSystemInfo` 判断真实系统架构，从而决定加载 x86 还是 x64 的 DLL。这是 WOW64 环境下"正确感知系统"的标准做法。

### 工业实践

**1. 动态计算分配参数**：

```
SYSTEM_INFO si;
GetSystemInfo(&si);
// 预订时向上对齐到分配粒度
SIZE_T alignedSize = (size + si.dwAllocationGranularity - 1) 
                    & ~(si.dwAllocationGranularity - 1);
// 提交时向上对齐到页面大小
SIZE_T committedSize = (size + si.dwPageSize - 1) & ~(si.dwPageSize - 1);
```

**2. 线程池大小决策**：

```
// 工作线程数 = 逻辑处理器数（IOCP 默认行为）
int workerCount = si.dwNumberOfProcessors;
```

**3. 大页(Large Page)支持检测**：

- 通过 `GetSystemInfo` 无法直接检测大页支持
- 需要用 `GetPerformanceInfo` 或检查 `SeLockMemoryPrivilege` 权限

## 14.2 虚拟内存状态

### 第一性原理：系统内存是动态的、全局的、瞬时快照

如果说 `GetSystemInfo` 返回的是"静态配置"，那 `GlobalMemoryStatusEx` 返回的就是"动态状态"——它在调用的那一瞬间，告诉你系统内存的真实使用情况。

微软官方文档明确警告：**"The information returned by the GlobalMemoryStatusEx function is volatile. There is no guarantee that two sequential calls to this function will return the same information."**——两次连续调用可能返回不同结果，因为系统内存状态时刻在变。

### 核心 API：GlobalMemoryStatusEx

```
BOOL GlobalMemoryStatusEx(LPMEMORYSTATUSEX lpBuffer);
```

`MEMORYSTATUSEX` 结构的字段解析 ：

|字段|含义|工业意义|
|---|---|---|
|`dwMemoryLoad`|物理内存使用百分比(0-100)|快速判断系统内存压力|
|`ullTotalPhys`|物理内存总量(字节)|硬件配置感知|
|`ullAvailPhys`|可用物理内存|**可立即重用，无需换页**——包括 standby/free/zero 列表之和|
|`ullTotalPageFile`|系统或当前进程的提交上限(较小者)|提交内存的天花板|
|`ullAvailPageFile`|当前进程可提交的**最大**内存|决定进程能"承诺"多少内存|
|`ullTotalVirtual`|进程用户模式虚拟地址空间大小|32 位进程约 2GB/3GB，64 位进程约 128TB|
|`ullAvailVirtual`|用户模式中未预订未提交的虚拟地址空间|决定还能 VirtualAlloc 多少|
|`ullAvailExtendedVirtual`|扩展虚拟内存(保留，恒为 0)|仅特定架构的 VLM 使用|

### 关键语义深度解析

**1. `ullAvailPhys` 的精确定义**​ ：

> "This is the amount of physical memory that can be immediately reused without having to write its contents to disk first. It is the sum of the size of the standby, free, and zero lists."

这意味着"可用物理内存"= standby 列表 + free 列表 + zero 列表的总和。其中：

- **free**：完全未使用的页
- **zero**：已清零、可直接分配的页
- **standby**：曾被分配但已"软释放"的页，内容还在，可快速回收

**2. `ullTotalPageFile` 的真实含义**​ ：

> "The current committed memory limit for the system or the current process, whichever is smaller"

这个值**不是页文件大小**！它是"系统-wide 的提交上限"与"当前进程的提交上限"中的较小者。这就是第13章讲的"提交记账"——系统在物理内存和页文件总额度中记账。

**3. `ullAvailPageFile` 的应用价值**​ ：

> "The maximum amount of memory the current process can commit"

这是判断"我的进程还能再提交多少内存"的权威指标。工业级程序在分配大块内存前，应先检查这个值。

### 虚拟内存状态示例程序

Richter 在 14.2 节配套的"VMStat"示例程序，调用 `GlobalMemoryStatusEx` 并显示所有字段。这个程序的意义：

- **诊断工具**：当程序报"内存不足"时，先用 VMStat 看系统整体状态
- **容量规划**：服务器部署前，评估可用资源
- **监控基准**：长期运行的服务可以定期采样这些指标，绘制内存使用趋势图

### 工业实践

**1. 内存分配前的"安全检查"**：

```
MEMORYSTATUSEX statex;
statex.dwLength = sizeof(statex);
GlobalMemoryStatusEx(&statex);

// 我想分配 500MB，先检查是否可行
if (500 * 1024 * 1024 < statex.ullAvailPageFile) {
    // 可以安全提交
    PVOID p = VirtualAlloc(NULL, 500 * 1024 * 1024, 
                            MEM_RESERVE | MEM_COMMIT, PAGE_READWRITE);
}
```

**2. 自适应资源池大小**：

```
// 根据可用物理内存动态调整缓存大小
SIZE_T cacheSize = statex.ullAvailPhys / 4;  // 用 25% 可用物理内存做缓存
```

**3. 内存压力感知**：

```
// dwMemoryLoad > 80% 时触发清理
if (statex.dwMemoryLoad > 80) {
    FlushCache();  // 主动释放缓存
}
```

> ⚠️ **陷阱**：`GlobalMemoryStatusEx` 返回的是**瞬时快照**。微软明确说连续两次调用可能返回不同结果。因此：
> 
> - 不要基于单次调用做长期决策
> - 不要假设"刚才查询可用 1GB，现在就一定还能分配 1GB"
> - 工业级程序应该**总是处理分配失败**（VirtualAlloc 返回 NULL），而不是依赖预查询

### 现代延伸：更精细的内存查询

`GlobalMemoryStatusEx` 提供的是"粗粒度"全局视图。如果需要更精细的信息：

- **`GetPerformanceInfo`**：系统级性能数据（提交总数、提交上限等）
- **`QueryWorkingSet` / `QueryWorkingSetEx`**：查询进程工作集细节
- **`GetProcessMemoryInfo`**：进程私有工作集、峰值工作集等

## 14.3 NUMA机器中的内存管理

### 第一性原理：NUMA 是"内存访问不均匀"的现实

微软官方文档对 NUMA 的定义非常清晰 ：

> "The architecture is non-uniform because each processor is close to some parts of memory and farther from other parts of memory. The processor quickly gains access to the memory it is close to, while it can take longer to gain access to memory that is farther away."

**SMP（对称多处理器）的局限**：

- 所有处理器平等访问所有内存和 I/O
- 处理器总线成为性能瓶颈——处理器越多，总线越拥挤

**NUMA（非一致内存访问）的突破**：

- CPU 被分成多个**节点(node)**，每个节点有自己的处理器和本地内存
- 节点间通过 cache-coherent interconnect bus 连接
- 访问本地内存快，访问远程内存慢

```
┌─────────────┐         ┌─────────────┐
        │  Node 0     │         │  Node 1     │
        │ ┌─────────┐ │         │ ┌─────────┐ │
        │ │ CPU 0-7 │ │←──总线──→│ │ CPU 8-15│ │
        │ ├─────────┤ │         │ ├─────────┤ │
        │ │ Local   │ │         │ │ Local   │ │
        │ │ Memory  │ │         │ │ Memory  │ │
        │ └─────────┘ │         │ └─────────┘ │
        └─────────────┘         └─────────────┘
          快速访问                  快速访问
          慢速访问↔慢速访问
```

### 关键语义（微软官方文档精确说明）

**1. 系统的调度优化**​ ：

> "The system attempts to improve performance by scheduling threads on processors that are in the same node as the memory being used. It attempts to satisfy memory-allocation requests from within the node, but will allocate memory from other nodes if necessary."

Windows 内存管理器会**自动**尝试：

- 把线程调度到与所用内存同节点的处理器上
- 优先从同节点分配内存
- 同节点内存不足时，从其他节点分配（性能下降）

**2. `VirtualAllocExNuma` 的"软偏好"语义**​ ：

> "VirtualAllocExNuma does not allocate any physical pages, so it will succeed whether or not the pages are available on that node or elsewhere in the system. The physical pages are allocated on demand. If the preferred node runs out of pages, the memory manager will use pages from other nodes."

这意味着：

- 你可以**指定首选 NUMA 节点**，但不是强制
- 函数调用时并不分配物理页（与 `VirtualAlloc` 的 `MEM_COMMIT` 语义一致——只是记账）
- 物理页在首次访问时才分配，优先从首选节点分配

### 核心 NUMA API

```
// 1. 获取最高节点号
GetNumaHighestNodeNumber(&highestNode);

// 2. 获取处理器亲和性掩码
GetProcessAffinityMask(GetCurrentProcess(), &procMask, &sysMask);

// 3. 查询处理器所属节点
GetNumaProcessorNode(processorNumber, &nodeNumber);

// 4. 获取节点中的处理器掩码
GetNumaNodeProcessorMask(nodeNumber, &processorMask);

// 5. 查询节点可用内存
GetNumaAvailableMemoryNode(nodeNumber, &availableBytes);

// 6. 指定 NUMA 节点分配内存（核心 API）
PVOID VirtualAllocExNuma(
    HANDLE hProcess,
    PVOID lpAddress,
    SIZE_T dwSize,
    DWORD flAllocationType,  // MEM_RESERVE | MEM_COMMIT
    DWORD flProtect,
    DWORD nndPreferred       // 首选 NUMA 节点
);
```

### 示例程序：NUMA 内存分配

微软文档提供了一个完整的 NUMA 内存分配示例 ：遍历每个处理器，查询其所属 NUMA 节点，然后用 `VirtualAllocExNuma` 从该节点分配内存，最后用 `QueryWorkingSetEx` 验证物理页实际分配在哪个节点。

这个示例揭示了 NUMA 编程的三个关键步骤：

1. **拓扑发现**：用 `GetNumaHighestNodeNumber` + `GetNumaProcessorNode` 搞清楚"哪个 CPU 属于哪个节点"
2. **亲和性优化**：用 `SetProcessAffinityMask` 把线程绑定到同节点 CPU
3. **本地内存分配**：用 `VirtualAllocExNuma` 指定首选节点

### 工业实践

**1. 数据库服务器（SQL Server）**：

- 每个 NUMA 节点运行独立的调度器
- 线程绑定到节点内的 CPU
- 内存从本地节点分配，减少跨节点访问
- 这是 SQL Server 在 64 路以上服务器上保持线性扩展的关键

**2. 低延迟交易系统**：

- 交易线程绑定到特定 NUMA 节点
- 市场数据缓存从同节点分配
- 跨节点访问的额外延迟（100-200ns）在高频交易中不可接受

**3. 现代 CPU 的"NUMA 隐形化"**：

- AMD Zen 架构、Intel 新一代 Xeon 都采用 chiplet/NUMA 设计
- 即使是桌面级 CPU（如 AMD Ryzen 9 7950X），也是多 NUMA 节点
- 这意味着 NUMA 优化不再是"服务器专属"——高端桌面应用也需要考虑

> 💡 **2026 年洞见**：随着 AMD 3D V-Cache、Intel 的 tiles 架构普及，**NUMA 已经成为桌面 CPU 的常态**。Windows 11 24H2 对 NUMA 调度做了进一步优化——当线程在其首选节点外运行时，内核会主动将其迁移到本地节点。应用程序如果主动使用 `VirtualAllocExNuma` + `SetThreadAffinityMask`，可以进一步降低内存访问延迟 20-40%。

### 超过 64 个逻辑处理器的 NUMA

微软文档特别说明 ：在超过 64 个逻辑处理器的系统上，节点被分配到处理器组中（processor groups）。这是 Windows 应对"CPU 数量爆炸"的抽象层——应用程序通过 processor group 机制感知大系统。

## 14.4 确定地址空间的状态

### 第一性原理：把进程的虚拟地址空间"可视化"

前几节我们看的是"系统级"信息。这一节降到"进程级"——**如何查看当前进程虚拟地址空间中每一块区域的具体状态**？

为什么需要这个能力？

- **调试内存泄漏**：遍历地址空间，找出所有已提交区域
- **内存分析工具**：Process Explorer、VMMap 等工具的底层原理
- **自定义内存管理器**：需要精确知道哪些区域已被预订/提交
- **安全审计**：检测可疑的内存区域（如注入的代码页）

### 核心 API：VirtualQuery

```
SIZE_T VirtualQuery(
    LPCVOID lpAddress,                    // 要查询的地址
    PMEMORY_BASIC_INFORMATION lpBuffer,   // 输出结构
    SIZE_T dwLength                       // 结构大小
);
```

`MEMORY_BASIC_INFORMATION` 结构 ：

|字段|含义|
|---|---|
|`BaseAddress`|区域基址（向下舍入到页边界）|
|`AllocationBase`|整个分配区域的基址（VirtualAlloc 的起始地址）|
|`AllocationProtect`|初始分配时的保护属性|
|`RegionSize`|从 BaseAddress 开始、具有相同属性的**连续区域大小**​|
|`State`|状态：`MEM_FREE` / `MEM_RESERVED` / `MEM_COMMIT`|
|`Protect`|当前保护属性|
|`Type`|类型：`MEM_PRIVATE` / `MEM_MAPPED` / `MEM_IMAGE`|

### 关键语义

**1. 区域(Region)的定义**​ ：

> "The size of the region beginning at the base address in which all pages have identical attributes"

`RegionSize` 返回的是"从查询地址开始，所有页面属性都相同的连续区域大小"。这意味着你可以从地址 0 开始，不断查询并累加 `RegionSize`，**遍历整个用户模式地址空间**。

**2. 三种状态**​ ：

- `MEM_FREE`：空闲页，可供分配。此时 `AllocationBase`、`Protect` 等字段未定义
- `MEM_RESERVE`：已预订但未提交。物理存储未分配
- `MEM_COMMIT`：已提交，物理存储已分配（在内存或页文件中）

**3. 区域类型**​ ：

- `MEM_IMAGE`：映射的可执行文件映像（.exe、.dll）
- `MEM_MAPPED`：内存映射文件（第17章的主题）
- `MEM_PRIVATE`：进程的私有内存（堆、栈、VirtualAlloc 分配等）

### 14.4.1 VMQuery 函数

Richter 在书中封装了一个更高级的函数 `VMQuery`——它多次调用 `VirtualQuery`，聚合信息，返回一个更友好的结构。这是对 `VirtualQuery` 的"工业级封装"。

**VMQuery 相比于裸 VirtualQuery 的优势**：

1. **聚合信息**：一次调用返回区域的完整信息
2. **类型安全**：明确区分映像/映射/私有内存
3. **块(block)信息**：区分"区域(region)"和"块(block)"——一个分配区域可能包含多个块，每个块有不同的保护属性
4. **便于遍历**：返回的 `RegionSize` 可以直接用于下一次查询的地址增量

**VMQuery 的典型用法**：

```
// 遍历整个用户模式地址空间
PBYTE pb = (PBYTE)0;  // 从地址 0 开始
while (pb < (PBYTE)0x7FFFFFFF) {  // 32位进程的用户空间上限
    VMQUERY_INFO info;
    if (VMQuery(pb, &info)) {
        // 打印/分析这块区域
        printf("Base: %p, Size: %llx, State: %s, Type: %s\n",
               info.pvRgnBaseAddress,
               info.dwRgnSize,
               info.State == MEM_COMMIT ? "COMMIT" : 
               info.State == MEM_RESERVE ? "RESERVE" : "FREE",
               info.Type == MEM_IMAGE ? "IMAGE" :
               info.Type == MEM_MAPPED ? "MAPPED" : "PRIVATE");
        
        // 移动到下一个区域
        pb += info.dwRgnSize;
    } else {
        break;
    }
}
```

### 14.4.2 示例程序：虚拟内存映射

Richter 在书中提供的"虚拟内存映射"示例程序（VMMap 的雏形），调用 `VMQuery` 遍历整个地址空间，打印出每块区域的状态、保护属性、类型。

**这个程序的价值**：

- **学习工具**：直观理解"进程的虚拟地址空间到底长什么样"
- **调试工具**：定位内存泄漏、异常的内存区域
- **性能分析**：查看堆、栈、映射文件、映像的分布

**典型输出示例**（64位进程）：

```
0x0000000000010000  RESERVE  PRIVATE   64KB   (空指针赋值分区之上)
0x0000000000010000  COMMIT   IMAGE     4KB    (可执行文件映像)
0x0000000000011000  COMMIT   IMAGE     4KB    (.text 代码段)
0x0000000000012000  COMMIT   IMAGE     4KB    (.rdata 只读数据)
0x0000000000013000  COMMIT   IMAGE     4KB    (.data 可读写数据)
0x0000000000020000  COMMIT   PRIVATE   1MB    (线程栈)
0x0000000000030000  COMMIT   PRIVATE   4KB    (堆)
0x0000000000040000  RESERVE  PRIVATE   1GB    (VirtualAlloc 预订的大区域)
0x0000000040000000  COMMIT   MAPPED    64KB   (内存映射文件)
...
```

### 工业级工具

现代 Windows 上有更强大的工具，其底层原理与 VMQuery 相同：

- **Process Explorer**：SysInternals 工具，显示进程的内存映射
- **VMMap**：SysInternals 专用内存分析工具，可视化进程的虚拟地址空间
- **Process Hacker**：开源替代品，功能类似
- **WinDbg 的 `!vad` 命令**：内核调试器中查看虚拟地址描述符(VAD)树

> 💡 **洞见**：所有内存分析工具的底层都是 `VirtualQuery`（用户态）或 `ZwQueryVirtualMemory`（内核态）。理解 VMQuery 的原理，你就掌握了这些工具的"源代码级认知"。

### 现代延伸：查询更多信息

`VirtualQuery` 提供的信息相对基础。如果需要更深入的分析：

- **`QueryWorkingSetEx`**：查询哪些页在当前工作集中、哪些被锁定、NUMA 节点
- **`GetMappedFileName`**：获取内存映射文件对应的文件路径
- **`EnumProcessModules` + `GetModuleInformation`**：枚举 DLL 及其在地址空间中的位置

## 章节联系：第14章是"看清内存"的工具箱

**与第13章（Windows 内存体系结构）的联系**：

- 14.1 的 `GetSystemInfo` 返回的是第13章讲过的"页面大小、分配粒度"等系统参数
- 14.2 的 `GlobalMemoryStatusEx` 返回的是第13章讲过的"物理内存、页文件、虚拟地址空间"的动态状态
- 14.3 的 NUMA 是第13章"物理存储器和页交换文件"在多节点系统中的具体化
- 14.4 的 `VirtualQuery` 让你看到第13章讲过的"地址空间分区、预订/提交状态、保护属性"在当前进程中的具象化

**与第15章（在应用程序中使用虚拟内存）的联系**：

- 14.4 的 `VirtualQuery` + `VMQuery` 是 15 章"自己使用虚拟内存"的**诊断工具**
- 当你用 `VirtualAlloc` 预订/提交内存后，用 `VMQuery` 验证操作是否成功
- 调试自定义内存管理器时，`VMQuery` 是不可或缺的探针

**与第12章（纤程）的联系**：

- 每个纤程的 1MB 栈在地址空间中表现为 `MEM_COMMIT` + `MEM_PRIVATE` + `PAGE_READWRITE` 区域
- 用 `VMQuery` 可以看到纤程栈的分布，包括栈底的 `PAGE_GUARD` 守护页面

**与第11章（线程池）的联系**：

- 线程池 worker 线程的栈同样可以在 `VMQuery` 输出中看到
- NUMA 优化线程池：用 14.3 的 `VirtualAllocExNuma` + `SetThreadAffinityMask`，把 worker 线程绑定到节点

**与第10章（异步设备 I/O）的联系**：

- 异步 I/O 的 `OVERLAPPED` 缓冲区和 I/O 完成端口的内部结构，都可以通过 `VMQuery` 观察到
- `CreateFileMapping` + `MapViewOfFile`（第17章）创建的内存映射区域，类型为 `MEM_MAPPED`

**与第7章（线程调度）的联系**：

- NUMA 节点与处理器组的调度密切相关
- `SetThreadAffinityMask` 绑定线程到 NUMA 节点，直接影响第7章讲的线程调度行为

**第一性原理的升华**：

第14章回答了系统编程的一个核心问题：**如何在运行时"看见"内存的真实状态？**

四个层次的"看见"：

|层次|API|看见什么|
|---|---|---|
|系统配置|`GetSystemInfo`|静态参数：页面大小、处理器数、架构|
|系统状态|`GlobalMemoryStatusEx`|动态状态：物理内存使用率、可用虚拟地址|
|NUMA 拓扑|`GetNumaProcessorNode` 等|多节点系统的拓扑结构|
|进程地址空间|`VirtualQuery` / `VMQuery`|每一块区域的状态、保护、类型|

**这套工具箱的工业价值**：

1. **诊断**：程序"内存不足"时，先用 `GlobalMemoryStatusEx` 看系统，再用 `VMQuery` 看进程
2. **优化**：NUMA 系统上用 `VirtualAllocExNuma` 分配本地内存
3. **验证**：自定义内存管理器用 `VMQuery` 验证分配是否正确
4. **监控**：长期运行的服务定期采样这些指标，绘制趋势图
5. **调试**：内存泄漏、非法访问的检测利器

> 💡 **我的洞见**：第14章表面上是讲"几个查询 API"，实质上是在教你**建立对内存的"可观测性"(Observability)**。现代系统编程的核心挑战不是"能不能分配内存"，而是"看清内存用在哪儿、为什么用、能不能优化"。Richter 在 2007 年给出的这套工具，到 2026 年依然是 Windows 系统编程的"显微镜"——Process Explorer、VMMap、WinDbg 等现代工具的底层，都是这些 API 的组合与延伸。理解第14章，你就拥有了"透视"任何 Windows 进程内存布局的能力。

### 工业实践的硬建议

1. **进程启动时调用一次 `GetSystemInfo`**，缓存页面大小和分配粒度——后续所有内存操作都基于这两个值计算
2. **大内存分配前调用 `GlobalMemoryStatusEx`**，检查 `ullAvailPageFile` 是否足够——但不要把它当作"一定会成功"的保证，永远处理分配失败
3. **NUMA 系统上的高性能程序必须用 `VirtualAllocExNuma`**——指定首选节点，配合 `SetThreadAffinityMask` 把线程绑定到同节点
4. **调试内存问题时用 `VMQuery` 遍历地址空间**——比猜更快定位问题
5. **`GlobalMemoryStatusEx` 的结果是易失的**——不要缓存太久，每次关键分配前重新查询
6. **32 位程序的 `ullAvailVirtual` 极其珍贵**——2GB/3GB 的用户空间很容易碎片化，定期用 `VMQuery` 检查地址空间碎片
7. **64 位程序也不能忽视 `ullAvailPageFile`**——128TB 的虚拟地址空间虽大，但"提交上限"仍受物理内存+页文件大小约束
8. **WOW64 环境下用 `GetNativeSystemInfo`**——看到真实的系统架构，而非 32 位视图
9. **超过 64 个逻辑处理器的系统用 processor groups**——NUMA 节点被分配到处理器组中，需用 `GetNumaHighestNodeNumber` + processor group API 全面感知
10. **自定义内存管理器的必备诊断工具**——`VMQuery` 是验证"我的分配器是否正确管理了虚拟地址空间"的唯一权威手段

> ⚠️ **2026 年现代延伸**：
> 
> - **Windows 11 24H2 的 NUMA 优化**：微软在新版 Windows 中对 NUMA 调度做了进一步优化——当线程跨节点访问内存时，内核会主动将其迁移到本地节点。但应用程序主动使用 `VirtualAllocExNuma` 仍可进一步降低延迟。
> - **AMD 3D V-Cache 与 NUMA**：AMD Ryzen 9 7950X3D 等 CPU 采用 chiplet 设计，L3 缓存大的 chiplet 与内存控制器的距离更近——这本质上是"缓存级 NUMA"。Windows 11 24H2 专门优化了对这种架构的感知，游戏线程会被调度到有大缓存的 core 上。
> - **Intel 的 P-core/E-core 异构架构**：Intel 12 代+ 的 P-core（性能核）和 E-core（能效核）在内存延迟上也有细微差异。Windows 11 的调度器会考虑这一点，但应用程序用 `SetThreadAffinityMask` 精确控制仍有价值。
> - **Rust 的 `sysinfo` crate**：跨平台系统信息库，在 Windows 上底层使用 `GetSystemInfo` + `GlobalMemoryStatusEx`。这证明了 Richter 在 2007 年讲解的这些 API 到今天仍是系统信息查询的工业标准。
> - **.NET 9 的 `GC.GetGCMemoryInfo`**：.NET 运行时暴露的 GC 内存信息，在 Windows 上底层使用 `GlobalMemoryStatusEx` + `GetPerformanceInfo`。ASP.NET Core 应用可以用这个信息做自适应资源调度。
> - **eBPF on Windows**：Windows 上的 eBPF 实现可以实时跟踪 `VirtualAlloc`/`VirtualFree` 调用，绘制内存分配的时间序列——这是对第14章"内存可观测性"思想的现代延伸，从"快照查询"进化到"流式监控"。
> - **AI/ML 工作负载的 NUMA 优化**：大型语言模型推理（如 GPT 服务）在 NUMA 服务器上运行时，必须精心规划——模型权重放在哪个节点的内存、推理线程绑定到哪个节点，直接影响推理延迟。NVIDIA Triton、TensorRT-LLM 等推理框架在 Windows 上都深度使用 `VirtualAllocExNuma` + `SetThreadAffinityMask`。
