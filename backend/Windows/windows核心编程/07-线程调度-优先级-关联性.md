
第7章是 Windows 线程模型真正"活起来"的一章。前6章我们讲的是线程的静态结构——什么是线程、怎么创建、怎么终止、内核里长什么样。第7章讲的是线程在时间维度上的动态行为：**CPU 时间片如何在多个线程之间分配？高优先级线程凭什么抢占低优先级线程？Sleep 真的只是"睡一会儿"吗？为什么你几乎不应该手动调 SetThreadPriority？**

## 7.1 线程的挂起和恢复

### 核心机制：挂起计数(Suspend Count)

每个线程内核对象内部维护一个**挂起计数**(suspend count)。`CreateThread` 或 `CreateProcess` 创建线程时，挂起计数初始化为 1——这阻止了线程被调度到 CPU 上，因为线程还需要时间初始化，你不希望它在完全就绪前就开始执行代码。

- `SuspendThread(hThread)`：挂起计数 **+1**，返回之前的挂起计数。线程停止执行用户态代码
- `ResumeThread(hThread)`：挂起计数 **-1**，返回之前的挂起计数。只有当挂起计数递减到 0 时，线程才真正恢复执行

挂起计数的最大值为 `MAXIMUM_SUSPEND_COUNT`（定义为 127）。这意味着一个线程最多可以被挂起 127 次，也必须被恢复 127 次才能真正运行。

### 第一性原理洞见

**挂起计数是"引用计数"思想在调度层面的应用**——它让"挂起"这个动作可叠加、可嵌套。调试器就是利用这个机制实现"单步调试"的：报告调试事件时，进程内所有线程都被冻结，调试器通过 SuspendThread/ResumeThread 精确控制"哪个线程可以跑"。

### 🚨 关键警告：SuspendThread 不是同步原语

Microsoft 官方文档明确写道：

> "This function is primarily designed for use by debuggers. It is not intended to be used for thread synchronization."

为什么？如果被挂起的线程正持有临界区(Critical Section)、互斥量或其他同步对象，挂起它可能导致死锁——其他线程永远拿不到这个锁。这是一个**确定性的定时炸弹**。

### 现代工业实践

- **调试器**：WinDbg、Visual Studio Debugger 使用 SuspendThread 冻结目标进程的所有线程，以便检查状态
- **注入/DLL 劫持场景**：某些安全软件在 SuspendThread 后注入 DLL，再 ResumeThread
- **生产代码**：永远不要用 SuspendThread 做线程同步。需要暂停工作线程时，用"退出标志 + 事件通知"的协作式模式（参见第6章 6.5.3 的工业替代方案）

> 💡 **洞见**：挂起计数的存在揭示了一个底层事实——**线程调度的最小可控单位是"是否进入就绪队列"，而不是"在 CPU 上跑多久"**。SuspendThread 直接操纵这个开关，绕过调度器的所有策略判断。这也是它危险的原因：你绕过了系统的自我保护机制。

## 7.2 进程的挂起和恢复

Richter 在书中指出，Windows 没有原生的 `SuspendProcess` 函数。要挂起一个进程的所有线程，必须：

1. 用 `CreateToolhelp32Snapshot` 枚举进程的所有线程
2. 对每个线程调用 `OpenThread` 获取句柄
3. 对每个线程调用 `SuspendThread`

但这里有个**竞态条件的陷阱**（这是 Richter 没充分展开、但现代多线程程序必须警惕的）：

- 枚举过程中，目标进程可能创建新线程或销毁旧线程
- 新创建的线程可能不会被挂起
- 更糟的是：枚举线程 ID 时，一个现有线程可能被销毁，同时一个新线程被创建，两者恰好复用了同一个 TID——此时 SuspendThread 会挂起错误的线程

### 工业实践

- **调试器 attach**：VS Debugger 在附加到进程时，会用 `SuspendProcess` 的内部变体冻结所有线程，但这是调试子系统内部的特权操作
- **进程快照/沙箱**：Windows Sandbox、容器运行时在冻结容器内所有进程时，使用内核级机制而非逐个挂起线程
- **生产环境**：几乎不需要挂起整个进程。如果必须做，考虑用 Job Object 的 `TerminateJobObject` 或向进程发 `WM_CLOSE` 让其优雅退出

> ⚠️ **2026 年视角**：现代 Windows 提供了 `SuspendThread` 的 WOW64 版本 `Wow64SuspendThread`，以及针对 ARM64 的 `Arm64SuspendThread`，用于跨架构挂起线程。这反映了 Windows 现在需要在 x86/x64/ARM64 三种架构间互操作，而 Richter 时代只有 x86/x64。

## 7.3 睡眠(Sleep)

`Sleep(DWORD dwMilliseconds)` 让调用线程主动放弃剩余时间片，进入等待状态。

### 关键语义

- `Sleep(n)`：线程至少睡眠 n 毫秒。系统只保证"不小于 n 毫秒"，实际可能更长（取决于系统时钟分辨率，默认 ~15.6ms）
- `Sleep(0)`：放弃剩余时间片，立即重新进入就绪队列。如果存在同优先级或更高优先级的就绪线程，它们会被调度；否则当前线程继续执行
- `Sleep(INFINITE)`：线程永远不被调度。这相当于自杀——不如直接退出线程

### 第一性原理洞见

**Sleep 的本质是"自愿放弃 CPU"**。它与抢占不同——抢占是高优先级线程强行夺取 CPU，而 Sleep 是当前线程主动让出。这种"主动性"让 Sleep 成为线程协作的基石。

### 现代工业实践

`Sleep(0)` 在自旋锁、忙等待中有重要作用。但现代 Intel 优化手册指出：在超线程 CPU 上，**长时间的自旋等待会严重影响同核另一线程的性能**。更好的做法是：

```
// 旧模式：Sleep(0) 自旋
while (!ready) Sleep(0);

// 现代模式：pause 指令 + SwitchToThread
for (int i = 0; i < 5000; i++) {
    _mm_pause();  // 告诉 CPU 这是自旋，让它优化资源分配
}
SwitchToThread();  // 让出当前时间片
```

FastMM4（Delphi 的内存管理器）的早期版本因在锁竞争时滥用 `Sleep(0)` 和 `Sleep(1)`，在多核 NUMA 系统上性能严重下降。后来改为 `pause + SwitchToThread` 模式，性能显著提升。

## 7.4 切换到另一个线程(SwitchToThread)

`SwitchToThread()` 与 `Sleep(0)` 类似，但有微妙差别：

|行为|Sleep(0)|SwitchToThread|
|---|---|---|
|让权范围|所有处理器上的同优先级或更高优先级线程|仅当前处理器上的任意线程|
|是否允许切换到低优先级线程|是（Win2K 后）|是|
|是否有上下文切换开销|是|是|
|跨处理器切换|是|**否**​|

### 第一性原理洞见

`SwitchToThread` 是一个**"礼貌性的让权"**——它告诉调度器"我用完了当前时间片，如果有其他线程想用这颗 CPU，请让它用"。但它**不保证**一定会切换——如果没有其他就绪线程，调用立即返回，当前线程继续执行。

相比之下，`Sleep(0)` 是"强制性让权"——它总是放弃剩余时间片，让调度器重新评估（尽管如果只有当前线程就绪，它又会立即被调度回来）。

### 工业实践

现代 C++ 并发编程中：

- **短时间自旋**：用 `_mm_pause()`（Intel）或 `__yield()`（ARM64）+ `SwitchToThread`
- **锁竞争**：用临界区(Critical Section)或 SRWLock，它们内部已经实现了最优的"自旋 + 让权"策略
- **任务调度器**：用 `std::this_thread::yield()`，在 Windows 上映射到 `SwitchToThread`

## 7.5 在超线程 CPU 上切换到另一个线程

这是 Richter 时代的前瞻性内容，今天已经成为主流。Intel 的超线程(Hyper-Threading)技术让一个物理核心上运行两个逻辑处理器，共享执行单元、L2/L3 缓存、分支预测器等资源，但各有独立的寄存器文件和指令指针。

### 关键问题：资源争抢

当两个逻辑线程都需要某个执行单元（如浮点运算单元）时，其中一个必须停顿。这意味着**超线程的性能 ≠ 两个物理核心**。在最好的情况下（线程使用不同资源），性能提升约 30%；在最坏情况下（线程激烈争抢同一资源），性能反而下降。

### YieldProcessor 宏

在自旋循环中，应该调用 `YieldProcessor()` 宏（在 x86 上展开为 `_mm_pause()` 指令），它告诉 CPU："我正在自旋，请让出执行资源给同核的另一个逻辑线程"。这避免了"一个线程自旋占用所有资源，导致同核另一线程饿死"的问题。

### 现代延伸：混合架构(P-core/E-core)

Intel 12 代及以后的 CPU 采用 **P-core（性能核）+ E-core（能效核）**​ 的混合架构。这给线程调度带来了新挑战：

> ⚠️ **重要发现**：如果使用 `SetThreadAffinityMask` 强制将线程绑定到特定核心类型，操作系统将无法利用 **Intel Thread Director**​ 的功耗/性能优化。

**现代最佳实践**（2026 年视角）：

- **优先使用 CPU Sets API**（`SetThreadSelectedCpuSets`、`GetSystemCpuSetInformation`）而非传统的亲和性掩码
- **避免在运行时频繁更改亲和性掩码**，这会触发强制上下文切换
- **只在初始化时设置亲和性**，且尽量用"逻辑处理器集群"而非"单核绑定"
- **让操作系统调度器自主决策**，只在极端性能敏感场景（如高频交易、实时音频处理）才考虑强亲和性

## 7.6 线程的执行时间

`GetThreadTimes` 可以获取线程的用户态时间和内核态时间。这是性能分析、资源监控的基础。

### 工业实践

- **性能剖析器**：Visual Studio Profiler、Intel VTune、JetBrains dotTrace 都基于线程执行时间做采样
- **资源配额**：Job Object 的 `JobObjectBasicAccountingInformation` 就是基于线程执行时间的累加
- **调度决策**：游戏引擎、音频处理软件用线程执行时间判断是否出现"卡顿"(glitch)

> 💡 **洞见**：理解"用户态时间"和"内核态时间"的区分，是理解为什么有时候 CPU 使用率是 100% 但程序依然响应缓慢的关键——大量的内核态时间可能意味着频繁的上下文切换、系统调用或 I/O 等待。

## 7.7 在实际上下文中谈 CONTEXT 结构

`CONTEXT` 结构是线程的"寄存器快照"——它包含了线程在某一刻的所有 CPU 寄存器值：通用寄存器、段寄存器、控制寄存器、调试寄存器、浮点寄存器等。

### 关键约束

Microsoft 官方文档明确指出：

> "You cannot get a valid context for a running thread. Use the `SuspendThread` function to suspend the thread before calling `GetThreadContext`. If you call `GetThreadContext` for the current thread, the function returns successfully; however, the returned context is invalid."

也就是说：

1. **不能获取运行中线程的有效 CONTEXT**——必须先 SuspendThread
2. **即使对自身线程调用 GetThreadContext，返回的上下文也是无效的**
3. **CONTEXT 结构是高度处理器特定的**——x86、x64、ARM64 各有不同的定义，详见 `WinNT.h`

### 第一性原理洞见

CONTEXT 是**线程在内核中被切换出去时保存的那份 CPU 状态**。第6章 6.6 节讲的 KTHREAD 里就包含了 CONTEXT。当你调用 `GetThreadContext` 时，你拿到的是这份保存状态的副本。

这就是为什么必须在 SuspendThread 之后调用——只有线程被挂起，它的 CONTEXT 才是"稳定的"。如果线程正在运行，它的寄存器每纳秒都在变，你拿到的快照毫无意义。

### 工业实践

- **调试器**：WinDbg 用 GetThreadContext 读取线程的寄存器状态，显示调用栈
- **反调试检测**：某些安全软件检查调试寄存器(DR0-DR3)来检测是否有调试器附加
- **协程/纤程**：某些用户态协程库用 CONTEXT 保存/恢复协程的执行状态
- **崩溃 dump 分析**：MiniDump 文件里就包含了每个线程的 CONTEXT

## 7.8 线程优先级

这是整个第7章的核心。Windows 调度器用 0-31 的优先级数值决定下一个该运行哪个线程。

### 优先级的计算模型

线程的**基础优先级(Base Priority)**​ = 进程优先级类 + 线程相对优先级

**进程优先级类**（6 种）：

- `IDLE_PRIORITY_CLASS` (4)
- `BELOW_NORMAL_PRIORITY_CLASS` (6)
- `NORMAL_PRIORITY_CLASS` (8)
- `ABOVE_NORMAL_PRIORITY_CLASS` (10)
- `HIGH_PRIORITY_CLASS` (13)
- `REALTIME_PRIORITY_CLASS` (24)

**线程相对优先级**（7 种）：

- `THREAD_PRIORITY_IDLE` (-15)
- `THREAD_PRIORITY_LOWEST` (-2)
- `THREAD_PRIORITY_BELOW_NORMAL` (-1)
- `THREAD_PRIORITY_NORMAL` (0)
- `THREAD_PRIORITY_ABOVE_NORMAL` (+1)
- `THREAD_PRIORITY_HIGHEST` (+2)
- `THREAD_PRIORITY_TIME_CRITICAL` (+15)

**基础优先级 = 进程类基准 + 线程相对值**（具体映射见表，例如 `NORMAL_PRIORITY_CLASS` + `THREAD_PRIORITY_HIGHEST` = 8 + 2 = 10）

### 调度算法（第一性原理）

Microsoft 官方描述：

> "Threads are scheduled to run based on their scheduling priority. Each thread is assigned a scheduling priority. The priority levels range from zero (lowest priority) to 31 (highest priority)... The system assigns time slices in a round-robin fashion to all threads with the highest priority. If none of these threads are ready to run, the system assigns time slices in a round-robin fashion to all threads with the next highest priority. If a higher-priority thread becomes available to run, the system ceases to execute the lower-priority thread... and assigns a full time slice to the higher-priority thread."

**三个核心规则**：

1. **优先级抢占**：高优先级线程就绪时，立即抢占低优先级线程（不等待时间片用完）
2. **同优先级轮转**：同优先级的多个线程按 Round-Robin 分配时间片
3. **0 优先级特殊**：只有"零页线程"(zero-page thread)能用优先级 0，它负责在系统空闲时将空闲页面清零

### 进程优先级类的使用哲学

> 💡 **Microsoft 的明确建议**：
> 
> - **几乎永远不要用 `REALTIME_PRIORITY_CLASS`**——它会中断管理鼠标、键盘、后台磁盘刷新的系统线程
> - **谨慎使用 `HIGH_PRIORITY_CLASS`**——如果长时间运行，系统中其他线程都将得不到 CPU 时间
> - **`IDLE_PRIORITY_CLASS` 适合屏幕保护、周期性显示更新等"不紧急"的任务**
> - **正确模式**：如果某段时间需要高优先级，用 `SetPriorityClass` 临时提升，完成后立即降回 `NORMAL_PRIORITY_CLASS`

## 7.9 从抽象角度看优先级

这一节 Richter 讲的是"优先级不是绝对值，而是相对概念"。我补充现代视角：

### 优先级的相对性

- 线程的绝对优先级(0-31)只有在**同一时刻与其他线程比较**才有意义
- 在现代 32 线程甚至 64 线程的 CPU 上，"同优先级轮转"意味着你可能要和几十个线程共享时间片
- 优先级提升（7.10.1 节）会让你的线程优先级**临时**升高，但这只是调度器的一个"小动作"

### 工业实践的真相

**高优先级 ≠ 高性能**。在很多场景下，提升优先级反而降低整体吞吐量：

- 高优先级线程会频繁抢占低优先级线程，导致后者"饿死"
- 如果高优先级线程长时间运行，系统响应性反而下降（因为鼠标、键盘线程优先级不够高）
- 实时优先级(16-31)线程会屏蔽系统线程，可能导致磁盘缓存无法刷新、网络栈停滞

> ⚠️ **游戏引擎的经验**：游戏主线程通常用 `HIGH_PRIORITY_CLASS` + `THREAD_PRIORITY_ABOVE_NORMAL`，但渲染线程、物理线程、音频线程各有不同优先级。音频线程通常需要 `THREAD_PRIORITY_TIME_CRITICAL`，因为音频缓冲区的填充延迟会直接导致爆音(glitch)。但即便是游戏，也**绝不使用 `REALTIME_PRIORITY_CLASS`**。

## 7.10 优先级编程

### 7.10.1 动态提升线程优先级

这是 Windows 调度器最精妙的设计之一。每个线程有一个**动态优先级**，调度器用它来决定下一个运行哪个线程。

**动态优先级提升规则**：

- 将进程切换到前台时，前台窗口所属进程的优先级类被提升
- 窗口接收输入（鼠标、键盘、定时器消息）时，拥有该窗口的线程优先级被提升
- 线程的等待条件被满足时（如 I/O 完成），线程优先级被提升
- **只对基础优先级在 0-15 之间的线程提升**；16-31 的实时优先级线程不享受动态提升
- 提升后，每次时间片用完，优先级递减一级，直到回到基础优先级
- 动态优先级**永远不会低于**基础优先级

**禁用动态提升**：

```
SetThreadPriorityBoost(hThread, TRUE);   // 禁用线程的动态提升
SetProcessPriorityBoost(hProcess, TRUE); // 禁用进程内所有线程的动态提升
```

### 第一性原理洞见

动态提升是解决"优先级反转"(Priority Inversion)问题的关键机制。经典的优先级反转场景：低优先级线程持有锁 → 中优先级线程抢占 → 高优先级线程等待锁但拿不到（因为低优先级线程被中优先级线程挡着）。Windows 调度器通过**随机提升就绪线程的优先级**（包括低优先级锁持有者）来打破死锁——低优先级线程获得足够 CPU 时间释放锁，高优先级线程接着运行。

### 工业实践

- **音频/视频处理**：这些线程需要稳定的调度延迟，通常**禁用动态提升**，并固定在高优先级，避免被临时提升的其他线程抢占
- **游戏主线程**：通常**启用动态提升**，确保用户输入得到快速响应
- **后台任务**：如 Windows Indexing Service、Defender 扫描，运行在 `IDLE_PRIORITY_CLASS` 或 `BELOW_NORMAL_PRIORITY_CLASS`，且禁用动态提升，确保不影响前台应用

### 7.10.2 为前台进程微调调度程序

当进程被带到前台时，Windows 会提升其优先级类，使其 ≥ 任何后台进程的优先级类。当进程离开前台时，优先级类恢复原值。

这是 Windows 桌面响应性的核心机制——它确保了"用户在看的窗口总是最快的"。

### 7.10.3 调度 I/O 请求优先级

这是 Richter 时代还没有的机制（Windows Vista 引入）。Windows I/O 管理器内部支持 **5 级 I/O 优先级**：

|I/O 优先级|用途|
|---|---|
|**Critical**​|内存管理器（写出脏数据）|
|**High**​|未使用|
|**Normal**​|普通应用程序 I/O|
|**Low**​|未使用|
|**Very Low**​|计划任务、SuperFetch、碎片整理、内容索引、后台活动|

**两种调度策略**：

1. **层级优先级**(Hierarchy Prioritization)：Critical > High > Normal > Low，按优先级从高到低处理
2. **空闲优先级**(Idle Prioritization)：Very Low 的 I/O 进入单独的队列，系统用定时器保证至少每 0.5 秒处理一个空闲 I/O，避免饿死

**用户态设置 I/O 优先级的方式**：

- `SetPriorityClass` / `SetThreadPriority`：为进程/线程的所有 I/O 设置优先级
- `SetFileInformationByHandle`：为特定文件对象设置 I/O 优先级
- 驱动程序可以用 `IoSetIoPriorityHint` 直接设置 IRP 的 I/O 优先级

> 💡 **工业实践**：
> 
> - **Windows Task Scheduler**​ 将默认任务优先级的 I/O 设为 Very Low
> - **Windows Defender 扫描、桌面搜索索引**使用 Very Low I/O 优先级
> - **流式多媒体播放**使用带宽预留(Bandwidth Reservation)策略，确保稳定的磁盘吞吐
> - **关键洞察**：I/O 优先级只是一个"hint"——存储栈中的各个驱动程序可以选择忽略它

### 7.10.4 Scheduling Lab 示例程序

Richter 随书提供的实验程序，允许交互式地调整进程优先级类、线程优先级、观察动态提升的效果。

如果用现代 API 重写，应该增加：

- **CPU 使用率实时图表**：显示不同优先级线程的 CPU 占用
- **I/O 优先级可视化**：显示不同 I/O 优先级对磁盘吞吐的影响
- **NUMA 感知**：显示线程在 NUMA 节点间的分布
- **混合架构感知**：在 P-core/E-core 系统上，显示线程被调度到哪种核心

## 7.11 关联性(Affinity)

线程亲和性(Thread Affinity)强制线程运行在特定子集的处理器上。

### 设置亲和性的 API

- `SetThreadAffinityMask(hThread, dwThreadAffinityMask)`：用位掩码指定线程能在哪些逻辑处理器上运行
- `SetProcessAffinityMask(hProcess, dwProcessAffinityMask)`：为进程的所有线程设置
- `SetThreadIdealProcessor(hThread, dwIdealProcessor)`：指定**首选**处理器（只是提示，不保证）
- 超过 64 个处理器时，需要使用处理器组(Processor Groups)和 `SetThreadGroupAffinity`

### 第一性原理洞见

Microsoft 官方明确警告：

> "Setting thread affinity should generally be avoided, because it can interfere with the scheduler's ability to schedule threads effectively across processors. This can decrease the performance gains produced by parallel processing."

**为什么强亲和性有害？**

1. **缓存失效**：如果线程被强制绑定到一个核心，它无法利用其他核心的空闲时间
2. **调度器受限**：调度器的优化空间被压缩
3. **NUMA 误判**：线程可能被绑定到远离其内存节点的 CPU，导致远程内存访问延迟
4. **混合架构失效**：在 P-core/E-core 系统上，强亲和性屏蔽了 Intel Thread Director 的优化

### 工业实践

**适合使用强亲和性的场景**：

- 测试每个处理器的性能
- 实时系统（如高频交易）要求确定的执行延迟
- 某些 HPC 应用（如 Intel MKL 的 LAPACK 例程）通过亲和性避免线程迁移，提升缓存命中率

**现代推荐做法**（2026 年视角）：

- **优先使用 CPU Sets API**：`SetThreadSelectedCpuSets` 让操作系统在指定的 CPU 集合内自主调度
- **使用理想处理器而非硬亲和性**：`SetThreadIdealProcessor` 是提示性的，调度器仍有自由度
- **NUMA 感知**：用 `GetNumaProcessorNode` 等 API 了解线程的内存拓扑
- **避免在运行时更改亲和性**：强制上下文切换的开销很大

### 混合架构时代的特殊处理

Intel 12 代+ CPU 的 P-core/E-core 架构下，正确的线程拓扑设计：

```
┌─────────────────────────────────────────────┐
│          逻辑处理器集群设计                      │
├──────────────────────┬──────────────────────┤
│   P-core 集群         │   E-core 集群         │
│  (性能敏感线程)       │  (后台/低优先级线程)   │
│  • 游戏主线程         │  • 垃圾回收           │
│  • 音频处理           │  • 日志写入           │
│  • 物理模拟           │  • 文件索引           │
└──────────────────────┴──────────────────────┘
```

但要记住：**强亲和性会屏蔽 Intel Thread Director 的优化**。更好的做法是让操作系统自主调度，只在极端场景使用 CPU Sets。

## 章节联系：线程调度是 Windows 并发模型的"心跳"

把第7章放到整本书的脉络里：

**与第6章（线程基础）的联系**：

- 6.6 节讲的 KTHREAD 里的优先级、时间片、状态字段，就是本章调度算法的操作对象
- 6.4.4 节的 `CREATE_SUSPENDED` 标志，本质是让线程以"挂起计数=1"出生，等待 7.1 节的 ResumeThread
- 6.5.3 的 TerminateThread 是调度器眼中最粗暴的线程死亡方式——它绕过所有优雅退出路径

**与第5章（作业）的联系**：

- 作业对象的 `JOB_OBJECT_LIMIT_PRIORITY_CLASS` 可以限制作业内所有进程的优先级类
- 作业的 CPU 速率控制（CPU Rate Control）在调度器层面限制作业内所有线程的 CPU 时间
- 作业的 `ActiveProcessLimit` 限制了作业内的进程数，间接影响调度器的线程池规模

**与后续章节的联系**：

- **第8章（线程同步）**：7.8 节的优先级反转问题，正是线程同步要解决的。互斥量、信号量的"优先级继承"协议就是为了对抗优先级反转
- **第9章（线程局部存储）**：TLS 访问速度极快，因为它基于 7.7 节讲的 TEB(Thread Environment Block)——而 TEB 的指针就藏在 CONTEXT 的段寄存器里
- **第10章起（用户态调度、纤程）**：现代 Windows 提供了用户态调度(UMS)机制，允许应用程序自己实现调度策略，这是对内核调度器的补充

**第一性原理的升华**：

线程调度回答了"多个线程如何共享有限的 CPU 资源"这个问题。Windows 的答案是一个**三层模型**：

1. **优先级驱动的抢占式调度**：高优先级线程随时可以打断低优先级线程
2. **同优先级轮转**：确保公平性
3. **动态优先级提升**：打破死锁、提升响应性

但这个模型不是完美的。它假设"优先级高的线程就是重要的线程"——这在桌面场景下成立（用户输入确实重要），但在服务器场景下未必（每个 HTTP 请求都同等重要）。这就是为什么现代 Windows 服务器应用倾向于：

- 用**线程池**而非手动优先级管理
- 用**I/O 完成端口(IOCP)**而非多线程阻塞
- 用**Job Object 的 CPU 速率控制**而非优先级来控制资源使用

### 工业实践的硬建议

1. **永远不要随意提升线程优先级**。默认 `NORMAL_PRIORITY_CLASS` + `THREAD_PRIORITY_NORMAL` 适合 95% 的场景
2. **音频、实时数据处理用 `THREAD_PRIORITY_TIME_CRITICAL`，但要短暂运行**
3. **后台任务用 `IDLE_PRIORITY_CLASS` 或 `SetThreadPriority` 的 `THREAD_MODE_BACKGROUND_BEGIN`**
4. **I/O 密集型后台任务用 Very Low I/O 优先级**（通过 `SetPriorityClass` 的 `PROCESS_MODE_BACKGROUND_BEGIN`）
5. **避免用 `REALTIME_PRIORITY_CLASS`**，除非你直接与硬件对话且明白后果
6. **不要用 `SuspendThread` 做线程同步**——这是调试器的特权，不是应用程序的工具
7. **不要用 `Sleep(0)` 做自旋等待**——用 `_mm_pause()` + `SwitchToThread()`
8. **避免在运行时设置线程亲和性**——用 CPU Sets 或理想处理器替代
9. **在混合架构 CPU 上，让操作系统调度器自主工作**，只在极端性能场景使用强亲和性
10. **理解动态优先级提升**，它既是朋友（打破死锁、提升响应性）也是敌人（可能导致优先级膨胀）

> ⚠️ **2026 年现代延伸**：Windows 11 和 Windows Server 2022 开始，在超过 64 个处理器的系统上，进程和线程亲和性默认跨越所有处理器组和所有处理器。这意味着传统的 64 位亲和性掩码已经不够用，必须使用处理器组(Processor Groups)或 CPU Sets API。如果你的程序还在用 `SetThreadAffinityMask` 且假设系统不超过 64 核，在现代服务器上会出现"看不到所有 CPU"的 bug。这是 Richter 时代完全无法预见、但今天必须面对的现实。
