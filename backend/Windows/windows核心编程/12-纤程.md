
第12章是整个线程系列的"旁支"——前面从第5章到第11章，我们一直在内核线程的世界里打转：内核调度线程、线程池管理线程、IOCP 在线程间分发 I/O 完成。第12章突然话锋一转，介绍了一个**内核根本不知道存在**的执行单元——纤程(Fiber)。

为什么要有纤程？Richter 在书中开宗明义：微软加这个特性主要是为了**方便把 UNIX 服务器应用迁移到 Windows**。UNIX 世界早就有用户态协作式调度的传统，而 Windows 内核只认抢占式的线程。为了让那些"自己调度自己"的 UNIX 服务器代码能在 Windows 上跑起来，微软在 Windows NT 4.0 引入了纤程。

但纤程的意义远不止于移植——它是理解"用户态调度"与"内核态调度"分野的最佳教材，也是现代协程(Coroutine)思想的鼻祖之一。

## 12.1 使用纤程

### 第一性原理：纤程是什么

微软官方文档的定义非常精确："A fiber is a unit of execution that must be manually scheduled by the application. Fibers run in the context of the threads that schedule them. Each thread can schedule multiple fibers."

翻译成第一性原理的语言：

- **纤程是用户态的执行单元**——内核不知道纤程的存在，它只调度线程
- **纤程必须由应用程序手动调度**——通过 `SwitchToFiber` 显式切换
- **纤程运行在调度它的线程上下文中**——从系统视角看，纤程做的操作就是线程做的
- **一个线程可以容纳多个纤程**——但它们是**协作式**的，一次只能有一个在运行

微软文档进一步阐明了调度语义："Fibers are not preemptively scheduled. You schedule a fiber by switching to it from another fiber. The system still schedules threads to run. When a thread running fibers is preempted, its currently running fiber is preempted but remains selected."

这句话揭示了纤程与线程的嵌套关系：

```
内核调度线程（抢占式）
  └─ 线程内手动切换纤程（协作式）
       ├─ 纤程 A
       ├─ 纤程 B
       └─ 纤程 C
```

**关键点**：

- 内核抢占线程时，当前运行的纤程也被抢占——但它**保持选中状态**(remains selected)
- 线程重新被调度时，同一个纤程继续运行
- 纤程之间的切换完全是用户态行为，不需要内核介入

> 💡 **洞见**：纤程本质上是"线程内的线程"——但它把调度权从内核手里夺回来交给了应用程序。这是一种**权力的转移**：内核不再决定"下一个执行的是谁"，应用程序自己决定。代价是应用程序必须承担调度的全部责任。

### 纤程与线程的根本差异

|维度|线程|纤程|
|---|---|---|
|调度者|内核（抢占式）|应用程序（协作式）|
|上下文切换|内核态切换，开销大|用户态切换，开销小|
|栈|默认 1MB|默认 1MB（与线程相同！）|
|数量上限|受内存和内核限制|理论上只受内存限制|
|并发性|多核可真并行|同一线程内的纤程只能并发不能并行|
|抢占|可被内核随时抢占|不会被抢占，必须主动让出|
|TLS 访问|正常|访问的是宿主线程的 TLS|

### 核心 API 四部曲

#### 第一步：将线程转换为纤程——`ConvertThreadToFiber`

```
PVOID ConvertThreadToFiber(PVOID pvParam);
```

任何一个想要运行纤程的线程，**必须先把自己转换为纤程**。这个函数：

- 为纤程分配执行上下文（约 200 字节）- 微软文档描述它"create an area to save fiber state information"
- 将调用线程变为"当前正在执行的纤程"
- `pvParam` 作为纤程数据，可通过 `GetFiberData` 宏获取

> ⚠️ **关键语义**：转换后，这个线程本身就成了一个纤程。它既有线程的身份（内核知道），又有纤程的身份（用户态知道）。这是纤程模型的起点。

#### 第二步：创建新纤程——`CreateFiber`

```
PVOID CreateFiber(
    DWORD dwStackSize,                    // 栈大小，0 = 默认 1MB
    PFIBER_START_ROUTINE lpStartAddress,  // 纤程函数
    PVOID lpParameter                     // 参数
);
```

`CreateFiber` 做三件事：

1. 分配栈空间（默认 1MB，初始提交 2 页）
2. 分配纤程执行上下文结构
3. 初始化上下文——保存参数、栈顶/栈底地址、纤程函数地址

**但 `CreateFiber` 不会调度这个纤程！**​ 微软文档明确说："This function does not schedule the fiber." 新纤程处于"就绪但未运行"状态，必须等别人切过来。

纤程函数的签名：

```
VOID WINAPI FiberFunc(PVOID lpParameter);
```

> ⚠️ **致命规则**：纤程函数**不应该返回**！微软文档警告："If your fiber function returns, the thread running the fiber exits." 如果纤程函数返回，整个线程（包括上面所有纤程）都会被销毁。

#### 第三步：切换纤程——`SwitchToFiber`

```
VOID SwitchToFiber(PVOID lpFiber);
```

这是纤程模型的灵魂——手动调度。

`SwitchToFiber` 的内部操作（来自 Richter 书中的应用层描述）：

1. 将当前 CPU 寄存器（包括指令指针、栈指针）保存到当前纤程的执行上下文中
2. 从目标纤程的执行上下文中加载之前保存的寄存器到 CPU
3. 目标纤程从上次离开的地方继续执行

```
// 主纤程中创建并切换到新纤程
PVOID pMainFiber = ConvertThreadToFiber(NULL);
PVOID pFiber1 = CreateFiber(0, FiberFunc1, (PVOID)1);
PVOID pFiber2 = CreateFiber(0, FiberFunc2, (PVOID)2);

// 切到 Fiber1
SwitchToFiber(pFiber1);  // 当前纤程（主纤程）被挂起，Fiber1 开始运行

// 在 Fiber1 中，可以再切到 Fiber2
SwitchToFiber(pFiber2);

// 在 Fiber2 中，可以切回主纤程
SwitchToFiber(pMainFiber);
```

> 💡 **洞见**：`SwitchToFiber` 是"手动版"的上下文切换。它和内核的线程切换在机制上几乎一样（保存/恢复寄存器），但**发生在用户态，不涉及内核**——这就是为什么纤程切换比线程切换快得多。但快是有代价的：应用程序必须自己保证"公平调度"，否则某个纤程可能饿死其他纤程。

#### 第四步：销毁纤程——`DeleteFiber`

```
VOID DeleteFiber(PVOID lpFiber);
```

清理纤程的栈、寄存器子集和纤程数据。

> ⚠️ **微软文档的两个严重警告**：
> 
> 1. "If you call DeleteFiber for a fiber created by another thread, you can cause the other thread to terminate abnormally." —— 如果你删除其他线程创建的纤程，可能导致那个线程异常终止，因为纤程栈已被释放。
> 2. "If DeleteFiber is called from the currently running fiber, its thread calls ExitThread." —— 如果当前正在运行的纤程调用 `DeleteFiber` 删除自己，它的线程会调用 `ExitThread` 终止。

这两条规则揭示了纤程生命周期管理的复杂性——**纤程不能随便删，尤其是不能跨线程删**。

### 跨线程切换纤程：理论可行，实践危险

微软文档提到："You can call SwitchToFiber with the address of a fiber created by a different thread. To do this, you must have the address returned to the other thread when it called CreateFiber and you must use proper synchronization."

理论上，你可以把纤程 A 从线程 1 切到线程 2 上运行——只要线程 2 也是纤程，并且有正确的同步。但 Richters 警告这种做法**极其危险**：

- 纤程的栈可能在另一个线程的地址空间中
- TLS（线程局部存储）会"穿越"——纤程访问的是当前宿主线程的 TLS，而不是创建它的线程的 TLS
- 同步原语（关键段、互斥量）与线程绑定，跨线程切纤程会导致死锁或状态不一致

> 🚨 **工业忠告**：微软官方明确指出纤程不提供比多线程更好的优势，并且使用纤程会让几乎所有依赖 TLS 的代码（包括 C 运行库、Win32 API 的大部分）失效。除非你在写 SQL Server 这种级别的自研系统，否则**不要尝试跨线程切纤程**。

### 纤程局部存储(FLS)

这是纤程版的 TLS。由于纤程不拥有完整的线程状态，微软提供了 FLS 函数来为每个纤程创建独立变量副本：

```
DWORD FlsAlloc(PFLS_CALLBACK_FUNCTION lpCallback);  // 分配 FLS 槽
BOOL FlsFree(DWORD dwFlsIndex);                     // 释放
PVOID FlsGetValue(DWORD dwFlsIndex);                // 获取当前纤程的值
BOOL FlsSetValue(DWORD dwFlsIndex, PVOID lpValue);  // 设置当前纤程的值
```

微软文档说明："A fiber can use fiber local storage (FLS) to create a unique copy of a variable for each fiber. If no fiber switching occurs, FLS acts exactly the same as thread local storage. The FLS functions manipulate the FLS associated with the current thread. If the thread is executing a fiber and the fiber is switched, the FLS is also switched."

**关键语义**：FLS 是与"当前线程中的当前纤程"关联的。当纤程切换时，FLS 也会跟着切换。这使得每个纤程可以有自己的"局部变量副本"——这是构建纤程化库（如纤程化的 TLS 模拟层）的基础。

### 纤程与异步 I/O 的配合

这是纤程最强大的应用场景——**用同步代码写异步逻辑**。

回忆第10章的异步 I/O：你必须用 `OVERLAPPED` + 完成通知（事件/IOCP/可提醒 I/O）来处理。代码被切成"发起 I/O"和"处理完成"两部分，逻辑支离破碎。

纤程可以让这段代码"看起来是同步的"：

```
// 纤程函数：用同步风格写异步 I/O
VOID WINAPI FiberWithAsyncIO(PVOID pv) {
    HANDLE hFile = (HANDLE)pv;
    OVERLAPPED ov = {0};
    ov.hEvent = CreateEvent(NULL, TRUE, FALSE, NULL);
    
    BYTE buffer[4096];
    
    // "同步"读文件——但底层是异步的
    ReadFileAsync(hFile, buffer, 4096, &ov);
    
    // 这里可以切到其他纤程去做别的事
    SwitchToFiber(pOtherFiber);
    
    // 当 I/O 完成时，事件被信号化，我们被切回来
    // 此时数据已就绪
    ProcessData(buffer);
}

// 辅助函数：发起异步读后，等待事件时让出纤程
VOID ReadFileAsync(HANDLE hFile, BYTE* buffer, DWORD size, OVERLAPPED* ov) {
    ReadFile(hFile, buffer, size, NULL, ov);  // 发起异步 I/O
    // 等待 I/O 完成事件时让出
    while (true) {
        if (WaitForSingleObject(ov->hEvent, 0) == WAIT_OBJECT_0) {
            break;  // I/O 完成
        }
        SwitchToFiber(pSchedulerFiber);  // 让出，等下次被切回来再检查
    }
}
```

这种模式的核心是：**I/O 等待期间，纤程主动让出 CPU，让同线程的其他纤程运行**。当 I/O 完成时，事件被信号化，调度器纤程切回这个纤程。

> 💡 **洞见**：这就是现代"协程 + 异步 I/O"的雏形。C# 的 `async/await`、C++20 协程、Rust 的 `async/.await`，本质上都是纤程思想的现代演绎——**用同步的代码风格表达异步的逻辑**。区别在于：现代协程由编译器/运行时管理栈和状态，而纤程由程序员手动管理。

### 工业实践：微软为什么不推荐用纤程

微软的一篇官方博客文章"When does it make sense to use Win32 Fibers?"说得很直白：

> "For most apps, the most important expense of threads is the physical address space consumed by the stack. Fibers don't fix this; they carry just as much stack as a thread."

"Fibers don't solve that problem. However, reducing the number of threads introduces a new problem: you've still got the same amount of work to do, and now it's up to you to multiplex all that work onto just a few threads. What fibers actually do (try to) solve is the problem of manually multiplexing lots of work onto a few threads."

"By going with fibers, you're taking a lot of matters into your own hands... you also can't write managed code. And you'll never be able to call out to 3rd party code."

"For something like Microsoft SQL Server, which is one of the most highly-optimized apps on the planet, and which pretty much lives in its own world where memory is 'cheap' and library code is suspect anyway, it probably made sense to go with fibers... For almost literally everyone else, it just doesn't make sense."

**核心结论**：

1. **纤程不省内存**——每个纤程默认还是要 1MB 栈
2. **纤程不解决线程抢占开销问题**——真正的问题是线程太多，纤程只是把"多线程"换成"手动调度的多纤程"，复杂度反而更高
3. **纤程破坏了生态**——任何依赖 TLS 的代码（几乎包括所有 C 运行库、Win32 API）在纤程环境下都会出问题
4. **纤程只适合 SQL Server 这种极度自研的系统**——它有自己的一套内存管理、自己的调度逻辑、不依赖外部库

### 现代替代方案

2025 年的工业实践中，纤程的角色已经被更现代的抽象取代：

|现代方案|优势|典型场景|
|---|---|---|
|**C++20 协程**​|编译器自动管理状态，栈可动态增长，类型安全|异步 I/O、生成器、惰性计算|
|**.NET async/await**​|语言级支持，与线程池无缝集成|Web 服务、UI 应用|
|**Boost.Coroutine/Fiber**​|跨平台，提供纤程抽象|用户态调度库|
|**libuv 事件循环**​|异步 I/O + 回调，跨平台|Node.js 底层|
|**Rust tokio/async-std**​|零成本抽象，所有权安全|高性能网络服务|

CSDN 2025 年的文章明确指出："对于协程/轻量任务，优先考虑语言/运行时的 coroutine（C++20 coroutine、.NET async/await、boost::asio 协程等）。如果需要用户态调度库，可考虑成熟的库（Boost.Context/Coroutine、libuv/libuv 的事件循环、专门的 fibers 库），而不是直接用 Win32 fibers（因为可移植性与互操作性问题）。"

## 12.2 Counter 示例应用程序

Richter 在书中用 Counter 示例演示了纤程的基本用法——两个纤程协作计数，通过 `SwitchToFiber` 手动让出执行权。

### 示例的核心逻辑

```
主线程 → ConvertThreadToFiber → 成为主纤程
主纤程 → CreateFiber 创建 Counter1 纤程
主纤程 → CreateFiber 创建 Counter2 纤程
主纤程 → SwitchToFiber(Counter1)  // 切到 Counter1
    Counter1: 计数到某值 → SwitchToFiber(Counter2)  // 让给 Counter2
        Counter2: 计数到某值 → SwitchToFiber(Counter1)  // 让回 Counter1
        ... 如此往复
```

### 伪代码结构

```
// 纤程间共享的调度器
PVOID g_SchedulerFiber = NULL;

// Counter 纤程函数
VOID WINAPI CounterFiber(PVOID pv) {
    int id = (int)pv;
    for (int i = 0; i < 5; i++) {
        printf("Fiber %d: count = %d\n", id, i);
        // 让出执行权给其他纤程
        SwitchToFiber(g_SchedulerFiber);
    }
    // 完成，切回调度器
    SwitchToFiber(g_SchedulerFiber);
}

// 主纤程（调度器）
VOID WINAPI SchedulerFiber(PVOID pv) {
    PVOID fiber1 = CreateFiber(0, CounterFiber, (PVOID)1);
    PVOID fiber2 = CreateFiber(0, CounterFiber, (PVOID)2);
    
    // 交替调度两个计数器纤程
    for (int round = 0; round < 5; round++) {
        SwitchToFiber(fiber1);  // 运行 fiber1 一轮
        SwitchToFiber(fiber2);  // 运行 fiber2 一轮
    }
    
    // 清理
    DeleteFiber(fiber1);
    DeleteFiber(fiber2);
    
    // 切回主线程（退出纤程）
    SwitchToFiber(pv);  // pv 是主线程的原始纤程
}

// 程序入口
int main() {
    // 将主线程转换为纤程
    PVOID mainFiber = ConvertThreadToFiber(NULL);
    
    // 创建调度器纤程
    g_SchedulerFiber = mainFiber;  // 调度器就是主纤程
    PVOID scheduler = CreateFiber(0, SchedulerFiber, mainFiber);
    
    // 切到调度器
    SwitchToFiber(scheduler);
    
    // 调度器完成后回到这里
    DeleteFiber(scheduler);
    return 0;
}
```

### 示例揭示的纤程编程模式

**1. 协作式调度**：每个纤程在合适的时机主动调用 `SwitchToFiber` 让出 CPU。如果没有纤程让出，其他纤程永远得不到执行——这是协作式调度的本质。

**2. 调度器模式**：通常需要一个"调度器纤程"来协调多个工作纤程。调度器决定下一个运行谁，工作纤程完成一段工作后让回调度器。

**3. 生命周期管理**：纤程的创建(`CreateFiber`)和销毁(`DeleteFiber`)必须由程序员精确控制。忘记 `DeleteFiber` 会内存泄漏；错误地在运行中删除当前纤程会导致线程退出。

**4. 栈隔离**：每个纤程有独立的栈（默认 1MB）。Counter1 和 Counter2 的局部变量互不干扰——这是纤程相比"状态机"实现方式的优势。

> ⚠️ **Counter 示例的工业启示**：
> 
> - 看似简单的"两个纤程交替计数"，实际上展示了**用户态协作式多任务**的完整生命周期
> - 这种模式在游戏引擎中仍有应用——游戏逻辑、渲染、物理模拟可以作为不同纤程，在主循环的驱动下协作执行
> - 但在大多数业务应用中，这种模式过于底层——现代语言用 `async/await` 或 `goroutine` 提供了更安全、更自动化的抽象

### 纤程与协程的对照

用现代视角重新审视 Counter 示例：

```
// C++20 协程版本（伪代码）
task Counter(int id) {
    for (int i = 0; i < 5; i++) {
        printf("Fiber %d: count = %d\n", id, i);
        co_yield;  // 让出，等价于 SwitchToFiber
    }
}

task Scheduler() {
    auto c1 = Counter(1);
    auto c2 = Counter(2);
    for (int round = 0; round < 5; round++) {
        co_await c1;  // 恢复 c1，等价于 SwitchToFiber(c1)
        co_await c2;  // 恢复 c2
    }
}
```

C++20 协程的优势：

- **编译器自动管理栈帧**——不需要手动分配 1MB 栈，协程帧按需分配在堆上
- **类型安全的恢复点**——`co_yield`/`co_await` 是语言关键字，编译器保证正确性
- **自动生命周期管理**——协程对象销毁时自动清理资源
- **跨平台**——不依赖 Win32 特定 API

这就是为什么 2026 年的工业开发中，纤程主要作为**底层基础设施**（如 Boost.Context 的底层实现）存在，而应用程序开发者使用更高级的抽象。

## 章节联系：第12章是线程模型的"哲学反思"

**与第5章（线程基础）的联系**：

- 第5章讲内核线程——抢占式、内核调度、开销大
- 第12章讲纤程——协作式、用户态调度、开销小
- 两者是"调度权归属"这一维度的两端：内核 vs 应用程序

**与第6章（线程调度、优先级和亲和性）的联系**：

- 第6章的抢占式调度对纤程**透明**——内核抢占线程时，纤程也被抢占
- 纤程没有优先级概念——调度完全由应用程序控制
- 亲和性绑定在线程上，纤程跟随宿主线程的亲和性

**与第7章（用户模式同步）的联系**：

- 第7章的关键段、SRW 锁与**线程**绑定——纤程切换不会导致关键段释放
- 这意味着：如果一个纤程持有关键段后调用 `SwitchToFiber` 切到其他纤程，关键段**仍然被持有**——这可能导致死锁
- 因此，在纤程环境中使用传统同步原语是**危险的**——必须在切换纤程前释放所有锁

**与第8章（内核对象同步）的联系**：

- 内核对象是线程安全的——但纤程切换时，线程不切换，所以内核对象的"线程亲和性"语义在纤程环境下会失真
- 例如：一个纤程等待互斥量，切换到另一个纤程，而另一个纤程也尝试获取同一个互斥量——这会导致死锁，因为互斥量的"所有者"是线程，不是纤程

**与第10章（异步设备 I/O）的联系**：

- 纤程可以与异步 I/O 完美配合——这是纤程最有价值的工业场景
- 异步 I/O 发起后，纤程主动让出，I/O 完成时通过事件/IOCP 唤醒调度器，切回纤程
- 这种模式实现了"用同步代码写异步逻辑"——是 C# `async/await` 的底层思路

**与第11章（Windows 线程池）的联系**：

- 线程池是内核线程的高级抽象——自动管理线程生命周期
- 纤程是用户态执行单元的底层抽象——手动管理调度
- 两者是正交的：你可以在线程池的 worker 线程中使用纤程，但微软不建议这样做——因为线程池的回调环境假设是普通的线程上下文

**第一性原理的升华**：

第12章回答了一个根本性问题：**调度权应该属于内核，还是应用程序？**

|维度|内核调度（线程）|用户态调度（纤程）|
|---|---|---|
|调度决策|内核根据优先级、时间片|应用程序根据业务逻辑|
|切换开销|高（内核态切换）|低（用户态切换）|
|并行性|多核真并行|单线程内并发|
|生态兼容|完全兼容|破坏 TLS、CRT、第三方库|
|适用场景|通用计算|极度自研的高性能系统|

**纤程的真正价值不在于性能，而在于"控制力"**。微软博客说得很透彻："fibers aren't about performance at all, but about making manual context-switching easier." 纤程让应用程序能够以一种"看似同步"的方式编写协作式多任务代码——这在移植 UNIX 服务器、实现协程库、构建游戏引擎时很有价值。

但代价是巨大的：你必须接管调度、管理生命周期、处理 TLS 失效、避免使用大部分 Win32 API 和 C 运行库。**这是一场与整个 Windows 生态系统的博弈**——除非你的系统像 SQL Server 那样高度自研、不依赖外部生态，否则这场博弈你赢不了。

### 工业实践的硬建议

1. **新项目不要用 Win32 纤程**——优先用 C++20 协程、.NET async/await、Rust async 等现代抽象
2. **移植 UNIX 服务器到 Windows 时可以考虑纤程**——这是微软引入纤程的初衷
3. **游戏引擎可以使用纤程**——游戏逻辑、AI、物理模拟作为独立纤程，在主循环驱动下协作执行
4. **绝不能跨线程切换纤程**——微软明确警告这会导致线程异常终止
5. **纤程函数中不能调用 `ExitThread`**——这会导致整个线程退出
6. **纤程函数不能返回**——返回会导致线程及其所有纤程被销毁
7. **在 `SwitchToFiber` 前必须释放所有锁**——关键段、互斥量与线程绑定，纤程切换不会导致锁释放
8. **用 FLS 替代 TLS**——FLS 在纤程切换时会自动切换，TLS 不会
9. **`DeleteFiber` 必须小心**——删除其他线程创建的纤程会导致那个线程崩溃
10. **纤程 + 异步 I/O 是经典组合**——但现代代码应该用 IOCP + 协程，而非裸纤程

> ⚠️ **2026 年现代延伸**：
> 
> - **C++20 协程已成为主流**：在 Windows 上，C++20 协程可以通过 `windows::overlapped` 等库与 IOCP 集成，实现"同步风格写异步代码"的现代版本。Boost.Asio、cppcoro 等库已经成熟。
> - **.NET 的 Fiber 支持**：.NET 运行时内部使用纤程来实现某些高级特性（如 `ExecutionContext` 的流动），但对应用程序开发者透明。
> - **Rust 的 async 在 Windows 上的实现**：Rust 的 `tokio` 等异步运行时在 Windows 上使用 IOCP，但其任务调度模型本质上是纤程思想的现代化——每个 async 任务是一个轻量级执行单元，由运行时调度。
> - **WebAssembly 与纤程**：WASM 的"栈切换"提案（Stack Switching）引入了类似纤程的原语，允许在 WASM 模块内进行用户态上下文切换——这是纤程思想在 Web 平台的复兴。
> - **Windows 11 的内核改进**：虽然纤程仍然是用户态机制，但 Windows 11 的内核调度器对"线程内协作式多任务"有了更好的支持——例如，当一个线程内的纤程主动让出时，内核可以更快地调度其他线程，减少空转。

Richter 在 2007 年写下第12章时，纤程还是一个"前沿话题"。到 2026 年，纤程本身已经退居幕后，但它的思想——**用户态调度、协作式多任务、用同步风格写异步逻辑**——已经通过协程、async/await、goroutine 等形式成为现代编程的主流范式。理解纤程，就是理解所有这些现代抽象的历史根源和设计哲学。
