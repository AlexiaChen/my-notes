
这两章表面看一个是"错误"，一个是"字符串"，但它们其实在讲同一件事：**Windows 是一个要运行几十年、跨无数硬件与文化环境的系统，所以"跨边界的状态"必须显式化、可诊断、可失败**。错误码是函数边界上的状态显式化，字符串编码是文化边界上的状态显式化。理解了这一点，你就拿到了这两章的第一性原理，后面 20 多章的内核对象、内存管理、DLL、线程等等，本质上都是在不同的边界上重复这个套路。

## 第1章 错误处理

### 1.1 定义自己的错误代码

Richter 在书里讲得很透：Win32 错误码是一个 32 位整数，按位切分了 Severity、Microsoft/customer 标志、Facility code、Exception code 几个字段。其中最关键的一条规矩是 **bit 29**：微软自己定义的错误码这一位永远是 0，你自定义的错误码必须把这一位设成 1，这样就永远不和现在或未来的系统错误码冲突。

这是这一节的洞见所在：**错误码不是给你一个人看的，是给整个 Windows 生态看的**。你在写一个 DLL、一个中间件、一个供他人调用的库时，错误码就是你和系统、和你下游调用者之间的"契约"。如果你随便返回一个 `return 42`，那 42 在 WinError.h 里可能已经代表 `ERROR_WRONG_DISK`，调试器一解出来就是误导。

**我的理解与创新延伸**：

1. **把错误码当 API 设计来做**。错误码的三要素——消息 ID（宏）、消息文本、数值——本质上就是你对外公布的"故障词典"。写库的时候，应该建立自己的 `MyLibError.h`，仿照 WinError.h 的风格，用 `// MessageId:` 注释块来定义，这样 Visual Studio 调试器的 `$err,hr` 监视技巧也能用上。
2. **客户位的深意**：bit 29 这个设计，体现了 Windows 生态"去中心化但有序"的哲学——微软不给你分配错误码，但给你留了一个不会冲突的命名空间。今天你在 COM、驱动、WinRT 里看到的 HRESULT，也是类似的思路（0x8 开头的高位区隔）。
3. **现代延伸**：在今天的工业实践中，纯 Win32 错误码常和 **HRESULT**​ 配合使用。COM 世界用 HRESULT，`S_OK`(0)、`S_FALSE`(1) 都是成功码，**必须用 `SUCCEEDED()` / `FAILED()` 宏判断，而不能写 `hr != S_OK`**——这是新手最常踩的坑。如果你的现代 C++ 项目混合了 Win32 API 和 COM（比如用了 DirectX、WRL、WinRT），需要设计一个统一的错误映射层：把 `GetLastError()` 的值通过 `HRESULT_FROM_WIN32()` 宏转成 HRESULT，让整个代码库用一套错误传播语义。

> 💡 一个工程经验：在大型 Windows 客户端项目里，错误码的数值本身不重要，**重要的是它在日志里能被 `FormatMessage` 还原成人类可读的文本**。所以自定义错误码时，别忘了对 `FormatMessage` 的 `FORMAT_MESSAGE_FROM_HMODULE` 提供支持——把你的错误码资源编译进 DLL，这样别人拿到一个错误数值，也能通过你的 DLL 拿到文本。

### 1.2 ErrorShow 示例程序

ErrorShow 这个示例的本质，是把调试器 Watch 窗口 `$err,hr` 干的事儿，做成一个独立的小工具。它的核心只有一句：`FormatMessage` + `GetLastError`。

Microsoft Learn 上给的现代标准写法非常清晰：

```
DWORD dw = GetLastError();
FormatMessage(
    FORMAT_MESSAGE_ALLOCATE_BUFFER | 
    FORMAT_MESSAGE_FROM_SYSTEM | 
    FORMAT_MESSAGE_IGNORE_INSERTS,
    NULL, dw,
    MAKELANGID(LANG_NEUTRAL, SUBLANG_DEFAULT),
    (LPTSTR)&lpMsgBuf, 0, NULL);
// ... 用 lpMsgBuf ...
LocalFree(lpMsgBuf);
```

**我的理解与工业实践延伸**：

1. **`FormatMessage` 是全公司级的"错误码→文本"基础设施**。它不只是查一张表那么简单——`FORMAT_MESSAGE_FROM_SYSTEM` 让它去系统资源里找，`FORMAT_MESSAGE_FROM_HMODULE` 让它去指定 DLL 的资源段找，`FORMAT_MESSAGE_IGNORE_INSERTS` 避免 `%1` 这种插入符被误解。ErrorShow 这个小工具，其实就是 Visual Studio "Error Lookup" 工具和调试器 Watch 窗口背后的原理。
2. **现代工业级封装**：今天实际项目里，没人会裸写 `FormatMessage`。常见的做法是封装成 RAII 风格：

```
std::wstring GetErrorMessage(DWORD errorCode) {
    LPWSTR msgBuf = nullptr;
    DWORD size = FormatMessageW(
        FORMAT_MESSAGE_ALLOCATE_BUFFER | 
        FORMAT_MESSAGE_FROM_SYSTEM | 
        FORMAT_MESSAGE_IGNORE_INSERTS,
        NULL, errorCode,
        MAKELANGID(LANG_NEUTRAL, SUBLANG_DEFAULT),
        (LPWSTR)&msgBuf, 0, NULL);
    if (size == 0) return L"Unknown error";
    std::wstring result(msgBuf, size);
    LocalFree(msgBuf);
    return result;
}
```

配合 C++ 的 `std::system_error` + `std::system_category()`，可以把 Win32 错误无缝接入现代 C++ 的异常体系。

1. **一个容易忽略的细节**：ErrorShow 里输入错误号时，**要先调用 `GetLastError` 马上存下来**——因为后续任何一个 Windows API 调用都可能覆盖这个线程局部的错误码。这是 Win32 错误处理的"黄金法则"：错误码是线程局部的、易失的。现代封装时必须第一时间捕获，不能先打日志、先 `OutputDebugString`、先弹 MessageBox 之后再去取。

## 第2章 字符和字符串处理

这一章是 Windows 编程里"历史包袱"最重、但也最能体现"ABI 稳定性优先"哲学的一章。

### 2.1 字符编码

**第一性原理视角**：字符编码本质上是在回答一个问题——"字节怎么变成人能读的字符"。ANSI 代码页的答案依赖于运行时环境（当前系统代码页），Unicode 的答案自包含。所以 ANSI 字符串不是"错误"，而是"携带了环境依赖"；Unicode 字符串才是自描述的。

工业界现在的共识是：**UTF-8 作为内部存储，UTF-16 作为 Windows API 边界**。这是一个 2026 年的视角，Richter 写书那会儿还没这么明确，但他"为何要用 Unicode"那一节的论证方向，和今天是一致的。

### 2.2 ANSI 字符和 Unicode 字符与字符串数据类型

Windows 上的关键事实：

- `CHAR` = `char`（8 位）
- `WCHAR` = `wchar_t`（16 位，UTF-16 代码单元）
- `TCHAR` 是个宏，根据 `UNICODE` 宏在两者间切换

**关键洞见（很多书没讲透的）**：`WCHAR` 严格来说不代表"一个 Unicode 字符"，而是代表"一个 UTF-16 代码单元"。补充字符（supplementary characters，如 emoji、部分汉字）需要**两个**​ `WCHAR`，也就是代理对（surrogate pair）。所以写字符串处理代码时，"字符数 ≠ WCHAR 数"。这是个现代应用里特别容易踩的坑——你截取前 N 个 `WCHAR` 想截断字符串，结果把一个代理对拆开，字符串就废了。

### 2.3 Windows 中的 Unicode 函数和 ANSI 函数

这是 Windows API 设计里最经典的"双轨制"：

```
#ifdef UNICODE
  #define SetWindowText SetWindowTextW
#else
  #define SetWindowText SetWindowTextA
#endif
```

ANSI 版本（`SetWindowTextA`）在内核里其实是先把 ANSI 字符串转成 Unicode，再调用 W 版本。这意味着 **ANSI 版本不仅功能受限（不支持全部 Unicode 字符），而且性能更差**——每次调用都要做一次代码页转换。

> ⚠️ 书里那个年代，"ANSI 版本更快"的认知是错的。在今天 NT 内核上，A 版本纯粹是用户态的兼容胶水，W 版本才是直通内核的路径。

**我的现代解读**：

- 新项目直接用 `W` 版本，显式写 `SetWindowTextW`，别依赖宏
- `TCHAR` 宏在新项目里**已经不推荐**了——Microsoft Learn 明确说："The TEXT and TCHAR macros are less useful today, because all applications should use Unicode"
- 一些新 API（如 `LCIDToLocaleName`）**只有 W 版本**，根本没有提供 A 版本

### 2.4 C 运行库中的 Unicode 函数和 ANSI 函数

C 运行库这边走的是另一条路：用 `_UNICODE` 宏（注意带下划线）控制。`_tcslen` 在 `_UNICODE` 定义时展开为 `wcslen`，否则为 `strlen`。

**关键陷阱**：Windows 头文件用的是 `UNICODE`（无下划线），C 运行库头文件用的是 `_UNICODE`（有下划线）。两者必须**同时定义或同时不定义**，否则字符串函数和 Windows API 之间会出现类型不匹配。Visual Studio 新建项目时默认两者都定义，但如果你手动改编译选项，要特别小心。

### 2.5 C 运行库中的安全字符串函数

这是整个 C/C++ 工业界安全实践的转折点。2002 年微软 Security Push 之后推出了 `strsafe.h`，后来又有了 Safe CRT（`_s` 后缀函数）。

#### 2.5.1 初识新的安全字符串函数

`strsafe.h` 的设计哲学四条：

1. 始终 NULL 结尾
2. 始终传入目标缓冲区大小
3. 始终返回一致的 `HRESULT`
4. 支持 32/64 位

对比一下传统写法和新写法：

```
// 危险的传统写法
void UnsafeFunc(LPTSTR szPath, DWORD cchPath) {
    TCHAR szCWD[MAX_PATH];
    GetCurrentDirectory(ARRAYSIZE(szCWD), szCWD);
    strncpy(szPath, szCWD, cchPath);  // bug: cchPath 应该是剩余空间
    strncat(szPath, TEXT("\\"), cchPath);  // bug: 同上
    strncat(szPath, TEXT("desktop.ini"), cchPath);
}

// 安全的 strsafe 写法
bool SaferFunc(LPTSTR szPath, DWORD cchPath) {
    TCHAR szCWD[MAX_PATH];
    if (GetCurrentDirectory(ARRAYSIZE(szCWD), szCWD) &&
        SUCCEEDED(StringCchCopy(szPath, cchPath, szCWD)) &&
        SUCCEEDED(StringCchCopy(szPath, cchPath, TEXT("\\"))) &&
        SUCCEEDED(StringCchCat(szPath, cchPath, TEXT("desktop.ini")))) {
        return true;
    }
    return false;
}
```

`StringCchCopy` 里的 **Cch**​ = count of characters，**Ccb**​ = count of bytes。这是 strsafe 的两套函数体系。

#### 2.5.2 在处理字符串时如何获得更多控制

`StringCchXxxEx` 系列提供了扩展控制：知道目标缓冲区末尾在哪、剩余多少空间、失败时是否填充特定字符、是否置 NULL 等。

**工业实践洞见**：

- Microsoft SDL（Security Development Lifecycle）已经把 `strcpy`、`strcat`、`sprintf` 等列为 **banned function calls**
- 替换策略：选 `strsafe.h` 还是 Safe CRT（`strcpy_s` 等）？strsafe 返回 `HRESULT`、可用于内核模式、专注缓冲区溢出；Safe CRT 返回 `errno_t`、集成在 CRT 里、覆盖范围更广
- 我的建议：**用户态应用优先用 Safe CRT（`_s` 后缀）**，因为它和 C 标准库衔接更自然；做驱动或系统底层时用 `strsafe.h`

#### 2.5.3 Windows 字符串函数

`lstrcat`、`lstrcpy` 这些 Kernel32 里的老函数，**书里明确建议不要用**。它们既不接受缓冲区大小参数，也没有安全版本。现代代码应该用 `StringCchXxx` 或 `*_s` 函数替代。

### 2.6 为何要用 Unicode

Richter 列的理由：全球化、代码页地狱、NT 内核原生 Unicode。

**我的第一性原理解读**：Unicode 不是"一种编码方案"，而是**把"字符语义"从"字节表示"中解耦出来**。ANSI 世界里，同一个字节 `0x80` 在中文 Windows 上是"€"，在日文 Windows 上是另一个字符——字符的语义取决于运行时环境。这是软件里最隐蔽的 bug 来源：你无法在源代码层面保证字符串的含义。

**2026 年的延伸视角**：

- **内部存储用 UTF-8**：跨平台、网络传输、JSON/XML 配置、第三方库接口，UTF-8 是事实标准
- **Windows API 边界用 UTF-16**：因为 Win32 API 的 W 版本接受的就是 UTF-16
- **架构模式**：

```
内部业务逻辑: std::string (UTF-8)
    ↓ MultiByteToWideChar(CP_UTF8)
Win32 API 调用: std::wstring / WCHAR* (UTF-16)
    ↓ WideCharToMultiByte(CP_UTF8)
内部业务逻辑: std::string (UTF-8)
```

### 2.7 推荐的字符和字符串处理方式

把书里的推荐和 2026 年的实践做一个对照：

|书里的推荐（2007 视角）|2026 年现代实践|
|---|---|
|用 `TCHAR`/`PTSTR`|新项目直接用 `wchar_t`/`WCHAR*`；跨平台层用 `char*`(UTF-8)|
|定义 `UNICODE` 和 `_UNICODE`|同上，但更推荐直接调用 `W` 函数|
|用 `_T("...")` / `TEXT("...")`|直接用 `L"..."`|
|用 `StringCchXxx` 或 `_s` 函数|同左，外加 C++ 标准库的 `std::wstring`、`std::string_view`|
|避免 `printf` 家族的 `%s`/`%S` 转换|同左，显式用 `MultiByteToWideChar`|
|用 `CompareStringOrdinal` 比较编程字符串|同左|

**程序字符串 vs 用户字符串的区分**是这一节最容易被忽视的洞见：

- **编程字符串**（文件名、路径、注册表键、XML 标签）：用 `CompareStringOrdinal`，快、不受 locale 影响、全球一致
- **用户字符串**（UI 文本）：用 `CompareString(Ex)`，考虑 locale

这个区分在今天的云服务、跨数据中心部署里尤为重要——你的文件名比较逻辑不能因为服务器部署在哪个国家就改变行为。

### 2.8 Unicode 与 ANSI 字符串转换

#### 2.8.1 导出 ANSI 和 Unicode DLL 函数

**核心工程决策**：当你写一个 DLL 对外暴露字符串相关的 API 时，有两种策略：

1. **双导出**（兼容老代码）：同时导出 `MyFuncA` 和 `MyFuncW`，内部 `MyFuncA` 调用 `MultiByteToWideChar` 转成 Unicode 后调 `MyFuncW`。这是 Windows API 自己的做法。
2. **只导出 W 版本**（现代做法）：只提供 `MyFuncW`，强制调用方处理 Unicode。新 API（如前面提到的 `LCIDToLocaleName`）都是这么干的。

**我的建议**：如果是面向现代 Windows 的库，直接只导出 W 版本，**别给自己留 ANSI 的历史包袱**。如果是维护老库或需要兼容旧调用方，采用双导出，但内部实现统一走 Unicode。

#### 2.8.2 判断文本是 ANSI 还是 Unicode

这是实际工程里经常遇到的硬骨头：给你一段字节流，怎么判断它是 ANSI 还是 UTF-16？

**工业级判断流程**：

1. **先看 BOM（字节顺序标记）**：
    - `FF FE` → UTF-16 LE
    - `FE FF` → UTF-16 BE
    - `EF BB BF` → UTF-8
2. **没有 BOM 时**，用启发式：
    - 扫描 WCHAR 流，如果发现合法的代理对、或者大量高位字节非零，倾向 UTF-16
    - 用 `IsTextUnicode()` API（Windows 提供）做统计启发式判断
    - 或者尝试 `MultiByteToWideChar(CP_UTF8, MB_ERR_INVALID_CHARS, ...)`，如果失败说明不是合法 UTF-8
3. **最靠谱的做法**：**别让文本"自带歧义"**。文件格式、协议、配置都应该显式声明编码。HTML 有 `<meta charset>`，XML 有 `encoding=` 属性，HTTP 有 `Content-Type` 头——这都是因为"猜编码"在工程上是个无解问题。

> 💡 **真正的洞见**：判断文本编码这个问题本身，就是 ANSI 时代留下的债。如果你的系统从端到端都用 Unicode（UTF-8 或 UTF-16），根本不需要"判断"这一步。这也是为什么现代软件架构强调"内部统一编码"。

`MultiByteToWideChar` 和 `WideCharToMultiByte` 的正确用法（这是面试和实际项目里最高频的考点）：

```
// 多字节 → 宽字符（UTF-8 → UTF-16）
int needed = MultiByteToWideChar(
    CP_UTF8, MB_ERR_INVALID_CHARS,
    utf8Str, -1,  // -1 表示 null 结尾
    NULL, 0);     // 第一次调用，获取所需大小
if (needed == 0) { /* 处理错误，GetLastError() */ }
std::wstring wstr(needed, L'\0');
MultiByteToWideChar(
    CP_UTF8, MB_ERR_INVALID_CHARS,
    utf8Str, -1,
    &wstr[0], needed);

// 宽字符 → 多字节（UTF-16 → UTF-8）
int needed = WideCharToMultiByte(
    CP_UTF8, WC_ERR_INVALID_CHARS,
    wstr.c_str(), -1,
    NULL, 0, NULL, NULL);
// ... 第二次调用执行转换
```

**关键细节**：

- 永远用 `CP_UTF8` 而不是 `CP_ACP`。`CP_ACP` 是当前系统 ANSI 代码页，在不同语言环境的机器上行为不一致
- `MB_ERR_INVALID_CHARS` / `WC_ERR_INVALID_CHARS` 标志让非法序列直接报错，而不是静默替换——这对安全敏感场景至关重要
- Windows Vista 之后，如果不加严格标志，非法序列会被替换成 U+FFFD，行为更健壮

## 两章的联系：边界即一切

回到开头说的第一性原理，这两章放在一起看，有一条暗线：

**第1章讲的是"函数边界的状态传递"**——调用者和被调用者之间通过线程局部的错误码沟通"发生了什么"。

**第2章讲的是"文化边界的数据表示"**——不同语言、不同代码页的世界，通过 Unicode 这个"通用语"来沟通。

它们的共同点：

1. **都是隐式状态显式化**：错误码把"失败原因"从"你猜"变成"我告诉你一个数字"；Unicode 把"字符含义"从"看运行环境"变成"自描述"。
2. **都为了 ABI 稳定性服务**：错误码的 32 位布局、字符串的 A/W 双轨，都是为了让老二进制在新系统上还能跑。
3. **现代实践都在"收敛"**：错误码向 HRESULT 体系收敛，字符串向 Unicode 收敛，TCHAR 这种过渡方案正在退出历史舞台。

**给实际工程的几条硬建议**：

1. **新项目模板**：直接 `#define UNICODE` 和 `#define _UNICODE`，用 `wchar_t` 和 `WCHAR*`，调用显式的 `W` 函数
2. **错误处理的现代封装**：用 `HRESULT` 作为统一的错误返回类型，`GetLastError()` 的值通过 `HRESULT_FROM_WIN32()` 转换；配合 `SUCCEEDED`/`FAILED` 宏
3. **字符串生命周期管理**：在 C++ 现代代码里，用 `std::wstring` 管理 UTF-16 字符串，`std::string` 管理 UTF-8 字符串；调用 Win32 API 的瞬间才做转换；绝不裸写 `WCHAR[]` 数组
4. **安全函数不是可选项**：SDL 已经把 `strcpy`/`strcat`/`sprintf` 列为 banned，新代码里看到这些函数就是 code smell
5. **日志与诊断**：错误码一定要能通过 `FormatMessage` 还原成文本再写日志；自定义错误码也要建自己的消息资源

> ⚠️ **一个常见误区**：很多人以为"我用 `std::string` 存 UTF-8，调用 Win32 API 时临时转成 `std::wstring`"是多此一举，想直接用 `CreateWindowA` 传 UTF-8。这是**未定义行为**——`CreateWindowA` 是按 `CP_ACP` 解释的，不是按 UTF-8。正确做法就是老老实实转 UTF-16 调 `CreateWindowW`。
