
第16章是内存管理三部曲（13原理 → 14探测 → 15使用）之后的**聚焦章**——把镜头从"整个进程的虚拟地址空间"拉到"其中一块特殊区域：线程栈"。每个线程（包括纤程）都有自己的栈，这块栈从第13章讲的"用户模式分区"中分配，用第15章讲的 `VirtualAlloc` 预订+提交机制实现，并通过一种特殊的页面保护属性——`PAGE_GUARD`——实现**按需自动增长**。

Richter 在这一章的核心命题：**线程栈不是一块静态分配的内存，而是一个"预订大、按需提交、靠保护页自动扩张"的动态结构**。理解了这个机制，你就能解释：为什么默认栈只有 1MB 却能在运行时"长大"？为什么有时候程序会栈溢出崩溃？为什么大局部变量会导致奇怪的崩溃？C/C++ 运行库的栈检查函数又是如何与这个机制协作的？

## 16.1 C/C++ 运行库的栈检查函数

### 第一性原理：保护页机制如何让栈"按需增长"

微软官方文档对线程栈的定义非常精准 ：

> "Each new thread or fiber receives its own stack space consisting of both reserved and initially committed memory. The reserved memory size represents the total stack allocation in virtual memory... The system commits additional pages from the reserved stack memory as they are needed, until either the stack reaches the reserved size minus one page (which is used as a guard page to prevent stack overflow)"

这段话揭示了线程栈的三个核心事实：

**1. 栈 = 预订区域 + 初始提交页面**

- 默认情况下，链接器为线程栈预订 **1MB**​ 虚拟地址空间
- 但**初始只提交 2 个页面（8KB）**——一个作为正常使用，第二个作为保护页
- 其余 1MB - 8KB 处于"已预订但未提交"状态

**2. 栈的增长靠保护页(Guard Page)触发**

- 在已提交区域的"下方"（低地址方向），系统放置一个特殊的**保护页**
- 保护页带有 `PAGE_GUARD` 属性——任何对该页面的访问都会触发 `STATUS_GUARD_PAGE_VIOLATION` 异常

**3. 保护页的工作流程**（Raymond Chen 的精确描述 ）：

```
初始状态：
   高地址 ──→ 低地址
   [已提交][已提交][保护页][保留][保留][保留]
                     ↑栈指针

当栈指针移入保护页时：
   ① 系统捕获 STATUS_GUARD_PAGE_VIOLATION 异常
   ② 移除该页的 PAGE_GUARD 标志 → 变成普通已提交页
   ③ 在下一页（保留区域）上设置新的保护页
   ④ 恢复执行被中断的指令

结果：
   [已提交][已提交][已提交][保护页][保留][保留]
                                        ↑新的栈边界
```

这个过程**完全在内核模式**下完成，对应用程序透明。栈就这样一页一页地"自动"长大了。

### 大栈帧的危机：跳过保护页

保护页机制有一个**隐含假设**：栈以**不超过一页**的步长增长 。但如果有这样的函数：

```
void BigFrame() {
    char buffer[8192];  // 8KB 局部变量，超过一页(4KB)
    buffer[0] = 0;      // 首次访问的是 buffer 的最低地址
}
```

编译器为这个函数生成的代码会做：

```
sub esp, 8192        // 栈指针一次性下移 8KB
mov [esp], 0         // 访问最低地址处的 buffer[0]
```

**问题来了**：`sub esp, 8192` 让栈指针**直接跳过了保护页**，落到了"保留但未提交"的区域。此时访问 `[esp]` 不会触发 `STATUS_GUARD_PAGE_VIOLATION`（因为没踩到保护页），而是直接触发 `STATUS_ACCESS_VIOLATION`——进程崩溃！

> ⚠️ **这就是 C/C++ 运行库栈检查函数要解决的问题**。

### __chkstk：编译器的"栈探查"卫士

微软的 MSVC 编译器在遇到"函数需要的栈空间超过一页"时，会**自动在函数序言(prologue)中插入对 `__chkstk` 的调用**​ 。

**`__chkstk` 的工作原理**（基于 Stack Overflow 上分析的 CRT 源码 ）：

```
; __chkstk - check stack upon procedure entry
; Entry: EAX = size of local frame
; Exit:  ESP = new stackframe, if successful
_chkstk proc
    push ecx
    lea ecx, [esp] + 8 - 4    ; TOS before entering function + size for ret value
    sub ecx, eax              ; new TOS
    ; Handle allocation size that results in wraparound.
    sbb eax, eax
    not eax
    and ecx, eax
    mov eax, esp
    and eax, not (_PAGESIZE_ - 1)    ; Round down to current page boundary
cs10:
    cmp ecx, eax                    ; Is new TOS in probed page?
    jb short cs20                   ; yes.
    mov eax, ecx                    ; else, move to next page
    sub eax, _PAGESIZE_             ; and probe it
    test dword ptr [eax], eax       ; touch it (THIS triggers guard page!)
    jmp short cs10
cs20:
    pop ecx
    ret
```

**核心思想**：`__chkstk` 从当前栈指针开始，**按 4KB 页面粒度，逐页向下"触碰"内存**，直到覆盖函数需要的全部栈空间。每一次"触碰"都会精确踩到当前的保护页，触发内核的栈增长机制，让保护页逐级下移。这样就不会有任何一次访问"跳过"保护页。

Raymond Chen 在 2026 年 3 月的最新文章中确认了这个机制的现代实现 ：

> "The job of this function is to touch all of the pages spanned by the desired stack allocation, in order, so that guard pages can be converted to committed memory... You have to make sure that the first access outside the stack limit is to wherever the guard page is."

**x86 版本的关键代码逻辑**​ ：

```
_chkstk:
    push ecx
    lea ecx, [esp][4]      ; ecx = original stack pointer - 4
    sub ecx, eax           ; ecx = new stack pointer - 4
    sbb eax, eax           ; clamp ecx to zero if underflow
    not eax
    and ecx, eax
    mov eax, esp
    and eax, -PAGE_SIZE     ; round current stack pointer to page boundary
check:
    cmp ecx, eax           ; done probing?
    jb probe               ; N: keep probing
    ; ... restore and return
probe:
    sub eax, PAGE_SIZE     ; move to next page
    test [eax], eax        ; probe it (touch the page)
    jmp check
```

**x64 版本（amd64）**​ ：

```
; on entry, rax is the number of bytes to allocate
chkstk:
    sub rsp, 16
    mov [rsp], r10
    mov [rsp][8], r11
    xor r11, r11
    lea r10, [rsp][16][8]    ; r10 = caller's rsp
    sub r10, rax             ; r10 = desired new stack pointer
    cmovb r10, r11           ; clamp underflow to zero
    mov r11, gs:[StackLimit] ; user mode stack limit
    cmp r10, r11             ; are we inside the limit?
    jae done                 ; Y: nothing to do
    and r10w, #-PAGE_SIZE    ; round down to page start
probe:
    lea r11, [r11][-PAGE_SIZE]  ; move to previous page
    test [r11], r11b            ; probe it
    cmp r10, r11                ; finished probing?
    jb probe                    ; N: keep going
done:
    mov r10, [rsp]
    mov r11, [rsp][8]
    add rsp, 16
    ret
```

### /Gs 编译器开关：控制栈检查阈值

MSVC 提供 `/Gs` 开关控制栈检查的插入时机：

> "堆栈探查是编译器在函式呼叫开头插入的程式代码序列...根据预设，编译器产生的程式码会在函式需要超过一页的堆叠空间时，起始堆栈探查。此预设值相当于 x86、x64、ARM 和 ARM64 平台的 /Gs4096 编译器选项。"

**关键默认值**：

- **x86/x64/ARM/ARM64 上默认 `/Gs4096`**——即函数栈帧超过 4KB 时插入 `__chkstk` 调用
- 这个默认值**允许应用程序和 Windows 内存管理员在运行时正确地动态增加栈内存**​
- 微软明确建议：**"We recommend that you do not change the default value unless you truly know why you must change it."**​

> 💡 **工业洞见**：`/Gs4096` 的默认值不是偶然的——它与 x86/x64 的页面大小（4KB）精确对齐。这意味着只要函数栈帧不超过 4KB，编译器就不插入 `__chkstk`，因为单次 `sub esp, xxx` 不会跳过保护页；一旦超过 4KB，就必须插入 `__chkstk` 来确保逐页触碰。

### 现代延伸：CET/影子栈对 __chkstk 的挑战

Raymond Chen 在 2026 年 3 月的文章中披露了一个**重要的现代变化**​ ：

> "Since we perform a ret instruction on a return address that was not placed there by a matching call instruction, this code is not compatible with shadow stacks (which Intel calls Control-Flow Enforcement Technology, or CET). The chkstk function's wacky call convention makes it incompatible with shadow stacks."

**背景**：Intel CET（Control-flow Enforcement Technology）引入了影子栈——返回地址同时存储在普通栈和影子栈中，必须严格匹配。传统的 `__chkstk` 通过改变 `esp`/`rsp` 并直接 `ret` 的方式"跳过"返回地址，与影子栈机制不兼容。

**现代 __chkstk 的演进**：

- **旧版本**：`__chkstk` 直接修改栈指针并 `ret`——快但不兼容 CET
- **新版本（ucrtbase 中的实现）**：`__chkstk` **只负责验证栈是否可扩展，不修改栈指针**，由调用者在返回后自己执行 `sub rsp, rax`

```
; 现代 amd64 版本
mov eax, #17328        ; desired stack frame size
call chkstk            ; validate that there is enough stack
sub rsp, rax           ; allocate it (caller does this now)
```

> 💡 **洞见**：这是"安全性与兼容性驱动底层机制演进"的典型案例。CET 硬件安全特性的引入，迫使 MSVC 团队重新设计 `__chkstk` 的调用约定——从"函数自己调整栈指针"演变为"函数只验证，调用者调整"。这个变化对应用程序员透明（编译器自动处理），但它揭示了现代系统编程中"安全特性反向塑造底层 ABI"的趋势。

### 工业实践

**1. 大栈帧的隐患**：

```
// 危险：8KB 局部数组
void Dangerous() {
    char buffer[8192];  // 触发 __chkstk 调用
    // ...
}

// 更安全：用堆代替大栈帧
void Safer() {
    char* buffer = new char[8192];  // 在堆上分配
    // ...
    delete[] buffer;
}

// C++11 推荐：用 std::vector 或 std::array
void Modern() {
    std::vector<char> buffer(8192);  // 堆分配，栈上只有少量开销
    // ...
}
```

**2. 递归深度与栈溢出**：

```
// 危险：深度递归可能耗尽 1MB 栈
int Recursive(int n) {
    int arr[1024];  // 每次递归 4KB
    if (n <= 0) return 0;
    return arr[0] + Recursive(n - 1);  // 250 次递归就栈溢出
}

// 更安全：改为迭代或用显式栈
int Iterative(int n) {
    std::stack<int> s;
    // 用堆上的栈替代递归
}
```

**3. 栈溢出后的恢复**：

微软提供了 `_resetstkoflw` 函数 ：

```
__try {
    RecursiveDeep();
}
__except (EXCEPTION_EXECUTE_HANDLER) {
    if (_resetstkoflw()) {
        // 恢复成功，可以继续执行
        // 但必须注意：栈已损坏，只能做最小限度的清理后退出
    } else {
        // 恢复失败，进程终止
    }
}
```

> ⚠️ **`_resetstkoflw` 的严格限制**​ ：
> 
> - 不能在过滤器表达式(filter expression)中调用
> - 不能在过滤器函数中调用
> - 不能在 catch 块中调用（栈溢出是结构化异常，不是 C++ 异常）
> - 不能在 `__finally` 块中调用
> - 必须在栈帧尚未完全展开时调用

### 现代线程栈大小的工业配置

微软文档详细说明了如何配置线程栈大小 ：

|方法|适用场景|说明|
|---|---|---|
|PE 文件头中的默认值|全局默认|链接器默认 1MB|
|`.def` 文件中的 `STACKSIZE` 语句|为所有线程指定默认栈大小||
|`CreateThread` 的 `dwStackSize`|单个线程的初始提交大小|向上舍入到页大小|
|`CreateThread` + `STACK_SIZE_PARAM_IS_A_RESERVATION`|单个线程的预订大小|设置栈的硬上限|
|`CreateFiberEx` 的 `dwStackReserveSize` / `dwStackCommitSize`|纤程的栈大小|分别控制预订和提交|

> 💡 **工业建议**：对于已知需要大栈的线程（如递归算法、大型科学计算），应该用 `CreateThread` + `STACK_SIZE_PARAM_IS_A_RESERVATION` 显式设置较大的栈预订大小。默认的 1MB 在现代应用中经常不够用——特别是：
> 
> - 深度递归的算法（如快速排序、树遍历）
> - 包含大局部数组的函数
> - 使用 `alloca` 或变长数组(VLA)的函数
> - 某些第三方库的内部函数

## 16.2 Summation 示例程序

### 示例的本质：在栈上做大规模求和

虽然原书配套的 Summation 示例程序的具体代码未在搜索材料中直接出现，但基于 Richter 的写作风格和本章主题，这个示例的核心目的是**演示线程栈的分配、使用和增长机制**。我们可以推断它大致是这样的结构：

```
// 主线程创建 Summation 线程，在栈上进行大量计算
DWORD WINAPI Summation(LPVOID lpParam) {
    // 大量局部变量占用栈空间
    int partialSum[1024];  // 4KB 局部数组
    
    // 递归或迭代求和
    for (int i = 0; i < 1000000; i++) {
        partialSum[i % 1024] += i;
    }
    
    // 返回结果
    return partialSum[0];
}

int main() {
    // 创建线程，指定栈大小
    HANDLE hThread = CreateThread(
        NULL,           // 默认安全属性
        0,              // 使用 PE 文件头中的默认栈大小(1MB)
        Summation,      // 线程函数
        NULL,           // 参数
        0,              // 默认创建标志
        NULL            // 不需要线程 ID
    );
    
    WaitForSingleObject(hThread, INFINITE);
    CloseHandle(hThread);
    return 0;
}
```

### 示例揭示的线程栈机制

**1. 每个线程独立的栈**：

- 主线程有自己 1MB 的栈
- Summation 线程有自己独立的 1MB 栈
- 两个栈在各自的虚拟地址空间中（可能相邻，但完全隔离）

**2. 栈的初始状态**：

- 线程创建时，系统预订 1MB 虚拟地址空间
- 初始提交 2 个页面（8KB）
- 第二个页面是保护页（`PAGE_GUARD`）

**3. 栈的动态增长**：

- 当 `partialSum` 数组（4KB）被访问时，`__chkstk` 被调用
- 保护页被逐页触发，栈从 8KB 增长到 12KB、16KB……
- 增长过程对程序员完全透明

**4. 栈的边界**：

- 栈的最大大小是预订的 1MB 减去一页（保护页）
- 当栈指针试图超过这个边界时，系统触发 `EXCEPTION_STACK_OVERFLOW`

### 工业级 Summation 的演进版本

现代工业代码中，类似的"大规模求和"应该用更安全的模式：

```
// 现代版本：用堆代替大栈帧
DWORD WINAPI SafeSummation(LPVOID lpParam) {
    const int ARRAY_SIZE = 1024;
    // 用 vector 在堆上分配，栈上只有少量开销
    std::vector<int> partialSum(ARRAY_SIZE, 0);
    
    // 或者直接传参数
    LONGLONG total = 0;
    for (int i = 0; i < 1000000; i++) {
        total += i;
    }
    
    // 通过参数返回结果
    *(LONGLONG*)lpParam = total;
    return 0;
}

// 更好的版本：用 IOCP 线程池并行求和
class ParallelSummation {
    std::atomic<LONGLONG> total_{0};
    
public:
    void AddRange(int start, int end) {
        LONGLONG local = 0;
        for (int i = start; i < end; i++) {
            local += i;
        }
        total_ += local;
    }
};
```

### 栈溢出异常的工业处理

如果 Summation 真的触发栈溢出，正确的处理方式是 ：

```
DWORD WINAPI SafeSummation(LPVOID lpParam) {
    __try {
        // 可能栈溢出的代码
        LargeRecursiveSummation();
    }
    __except (EXCEPTION_EXECUTE_HANDLER) {
        // 栈溢出是结构化异常，不是 C++ 异常
        DWORD code = GetExceptionCode();
        if (code == EXCEPTION_STACK_OVERFLOW) {
            // 必须调用 _resetstkoflw 恢复保护页
            if (_resetstkoflw()) {
                // 恢复成功，但栈已损坏
                // 只能做最小限度的清理，然后退出线程
                return ERROR_STACK_OVERFLOW;
            }
        }
        return GetLastError();
    }
    return 0;
}
```

> ⚠️ **关键警告**：栈溢出后的恢复极其危险。微软文档明确指出 ：
> 
> - 栈溢出异常发生时，线程的栈已处于损坏状态
> - **必须在 `__except` 块主体内调用 `_resetstkoflw`**（不能在过滤器表达式中调用）
> - 恢复后只能做最小限度的操作，然后尽快退出线程
> - 不正确的恢复会导致下次栈溢出时"没有任何异常，进程静默终止"

### 工业实践

**1. 避免大栈帧——用堆代替**：

```
// 不好：8KB 栈帧
void BadPractice() {
    char buffer[8192];
    // ...
}

// 好：用 std::vector 在堆上分配
void GoodPractice() {
    std::vector<char> buffer(8192);
```

**2. 递归转迭代**：

```

int Factorial(int n) {
    if (n <= 1) return 1;
    return n * Factorial(n - 1);  // 深度递归
}

// 好：迭代版本
int FactorialIterative(int n) {
    int result = 1;
    for (int i = 2; i <= n; i++) {
        result *= i;
    }
    return result;
}
```

**3. 显式设置大栈线程**：

```
    NULL,
    0,
    NULL
);

// 正确写法：用 STACK_SIZE_PARAM_IS_A_RESERVATION 设置预订大小

```

**4. 监控栈使用**：

```
// 在关键函数中检查栈剩余空间
void CheckStackUsage() {
    NT_TIB* tib = (NT_TIB*)NtCurrentTeb();
    PBYTE stackBase = (PBYTE)tib->StackBase;
    PBYTE stackLimit = (PBYTE)tib->StackLimit;
    
    SIZE_T used = stackBase - (PBYTE)_AddressOfReturnAddress();
    SIZE_T total = stackBase - stackLimit;
    
    if (used > total * 0.8) {
        // 栈使用超过 80%，发出警告
        fprintf(stderr, "Warning: Stack usage at %zu%%\n", 
                used * 100 / total);
    }
}
```

### 现代延伸

**1. .NET 的栈管理**：

- .NET 线程默认栈大小 1MB（与 Win32 相同）
- 但 .NET 的 ASP.NET Core 等框架会创建具有更大栈的线程
- Kestrel 服务器的工作线程栈大小通常为 2-4MB

**2. Rust 的栈管理**：

- Rust 在 Windows 上默认线程栈 2MB（比 C++ 的 1MB 大）
- 这是因为 Rust 的 `Vec`、`String` 等类型在栈上持有少量元数据，但大数据在堆上
- Rust 的 `std::thread::Builder` 允许显式设置栈大小

**3. Go 的 goroutine 栈**：

- Go 的 goroutine 初始栈只有 2KB（极小！）
- 但 Go 的运行时会在栈增长时自动分配新栈并复制内容
- 这是"栈拷贝"策略，与 Windows 的"保护页"策略完全不同
- Go 在 Windows 上的实现底层仍使用 Windows 线程栈，但 goroutine 栈是 Go 运行时自己管理的

**4. C++20 协程的栈**：

- C++20 协程的栈帧分配在堆上（通过编译器生成的代码）
- 协程挂起时，栈帧作为对象保存在堆上
- 这与传统函数的"栈上分配"完全不同，避免了栈溢出风险

**5. Windows 11 的栈优化**：

- Windows 11 24H2 对栈的保护页机制做了细微优化
- 当检测到栈快速增长时，系统会预提交多个页面，减少页错误次数
- 这对深度递归和大型科学计算程序有明显性能提升

## 章节联系：第16章是"虚拟内存机制在栈上的具象化"

**与第13章（Windows 内存体系结构）的联系**：

- 线程栈是"用户模式分区"中的一块特殊区域
- 栈的预订+提交机制是第13章讲的"虚拟地址空间分区"的具体实例
- `PAGE_GUARD` 保护属性是第13章讲的"页面保护属性"的特殊应用

**与第14章（探索虚拟内存）的联系**：

- 用 `VMQuery`（14.4.1）可以观察线程栈的状态：预订 1MB，已提交若干页面，保护页带有 `PAGE_GUARD` 属性
- 用 `GlobalMemoryStatusEx`（14.2）可以看到栈的提交会影响系统的"提交限额"
- 用 `GetSystemInfo`（14.1）获取的页面大小（4KB）决定了栈增长的粒度

**与第15章（在应用程序中使用虚拟内存）的联系**：

- 线程栈的分配本质上是系统调用 `VirtualAlloc` 预订+提交
- 栈的增长本质上是系统对 `PAGE_GUARD` 页面的异常处理（15.6 节的保护属性改变）
- 栈的释放本质上是 `VirtualFree` 带 `MEM_RELEASE`（15.5 节）
- 但这一切对程序员**透明**——你不需要手动调用这些 API，CRT 和 Windows 内核帮你完成

**与第12章（纤程）的联系**：

- 纤程的 1MB 栈通过 `CreateFiberEx` 的 `dwStackReserveSize` 和 `dwStackCommitSize` 参数配置
- 纤程切换的本质是切换栈指针——栈指针指向的就是这块虚拟内存
- 每个纤程有独立的栈，切换纤程就是切换栈

**与第7章（线程调度）的联系**：

- 线程切换时，CPU 寄存器（包括栈指针 ESP/RSP）被保存到线程上下文中
- 新线程恢复时，栈指针从自己的栈中加载
- 这就是为什么每个线程必须有独立栈——否则栈指针会混乱

**与第5章（线程基础）的联系**：

- `CreateThread` 的 `dwStackSize` 参数直接控制线程栈的初始提交大小
- 线程栈是线程创建时分配的关键资源
- 线程退出时栈被释放——这是 16 章讲的关键规则

**第一性原理的升华**：

第16章回答了系统编程中的一个核心问题：**函数的局部变量、参数、返回地址到底存在哪里？它们是如何被管理的？**

三层核心机制的协同：

|机制|解决的问题|核心思想|
|---|---|---|
|**预订大、提交小**​|节省物理内存|1MB 预订，初始只提交 8KB|
|**保护页自动增长**​|栈的动态扩展|`PAGE_GUARD` + 异常处理|
|**`__chkstk` 栈探查**​|大栈帧不跳过保护页|按页逐次触碰|

**线程栈设计的第一性原理可以归纳为**：

1. **空间换时间**：预订 1MB 虚拟地址空间（几乎零成本），但只提交实际需要的页面
2. **惰性求值**：栈页面在首次访问时才被提交——这是第15章"按需提交"思想在线程栈上的应用
3. **异常驱动**：用 `PAGE_GUARD` 异常触发栈增长，避免了显式的"检查边界"逻辑
4. **编译器与运行时协作**：`__chkstk` 确保大栈帧不会破坏保护页机制
5. **隔离性**：每个线程独立栈，切换线程就是切换栈指针

> 💡 **我的洞见**：线程栈是 Windows 虚拟内存机制最优雅的应用之一。它把第13章讲的"虚拟地址空间分区"、第14章讲的"地址空间状态查询"、第15章讲的"`VirtualAlloc`/`VirtualFree`/`PAGE_GUARD`"全部**封装成对程序员透明的自动化机制**。你写 `int x = 5;` 时，根本不需要知道这背后有预订、有提交、有保护页、有 `__chkstk` 调用。但这种"透明"是有代价的——当栈溢出发生时，你往往措手不及。理解第16章，就是理解"透明的代价"：知道栈是如何工作的，你才能写出不会栈溢出的代码；知道 `__chkstk` 是如何与保护页协作的，你才能理解为什么有时候大局部变量会导致诡异崩溃；知道如何配置线程栈大小，你才能在深度递归、大型科学计算等场景下游刃有余。

### 工业实践的硬建议

1. **默认 1MB 栈在现代应用中经常不够**——对于深度递归、大局部数组、使用 `alloca` 的场景，用 `CreateThread` + `STACK_SIZE_PARAM_IS_A_RESERVATION` 显式设置更大的栈（如 4MB-8MB）
2. **避免大栈帧**——用 `std::vector`、`std::unique_ptr` 等 RAII 类型把大数据放到堆上，栈上只保留元数据和少量开销
3. **递归深度超过 1000 就要警惕**——考虑改写为迭代，或用显式栈（堆上的 `std::stack`）模拟递归
4. **`/Gs4096` 的默认值不要改**——微软明确建议除非你知道为什么，否则保持默认 。改小会导致每个函数都插入 `__chkstk`（性能下降），改大可能导致大栈帧跳过保护页（崩溃风险）
5. **栈溢出是结构化异常，不是 C++ 异常**——不能用 `try/catch` 捕获，必须用 `__try/__except`
6. **栈溢出恢复极其危险**——`_resetstkoflw` 必须在 `__except` 块主体内调用，且恢复后只能做最小清理然后退出线程
7. **纤程栈大小用 `CreateFiberEx` 精确控制**——`dwStackReserveSize` 和 `dwStackCommitSize` 分别控制预订和提交
8. **跨平台代码的栈大小意识**——Windows 默认 1MB，Linux 默认 8MB，macOS 默认 8MB。跨平台库要注意栈使用量
9. **`alloca` 和 VLA 是栈溢出的高危来源**——它们在栈上动态分配，无法被 `__chkstk` 保护（因为是运行时大小）。尽量避免使用，改用 `std::vector` 或 `_malloca`/`_freea`
10. **监控关键线程的栈使用**——在长期运行的服务中，定期检查栈使用率，超过 80% 时发出警告

> ⚠️ **2026 年现代延伸**：
> 
> - **CET 影子栈与 `__chkstk` 的演进**：Intel CET 硬件安全特性迫使 MSVC 重新设计 `__chkstk` 的调用约定——从"函数自己调整栈指针"演变为"函数只验证，调用者调整" 。这是硬件安全特性反向塑造底层 ABI 的典型案例。在 Windows 11 24H2+ 上，启用 CET 的程序必须使用新版本的 `__chkstk`。
> - **Windows 11 24H2 的栈增长优化**：当系统检测到栈快速增长（如深度递归）时，会预提交多个页面，减少页错误次数。这对递归算法、大型科学计算有明显性能提升。
> - **Rust 在 Windows 上的栈管理**：Rust 默认线程栈 2MB（比 C++ 的 1MB 大），且 Rust 的借用检查器在编译期就防止了许多栈相关问题。但 Rust 的 `std::thread::Builder` 仍允许显式设置栈大小，底层调用 `CreateThread`。
> - **.NET 9 的栈优化**：.NET 9 的 JIT 编译器在 Windows 上对 `__chkstk` 的调用做了优化——对于已知的栈帧大小，JIT 直接生成栈探查代码，避免函数调用开销。这是托管运行时与底层机制深度集成的例子。
> - **Go 1.22+ 在 Windows 上的 goroutine 栈**：Go 的 goroutine 初始栈仅 2KB，但 Go 运行时会在 Windows 上监听栈溢出异常，自动分配新栈并复制内容。这与 Windows 原生的"保护页"策略互补——goroutine 栈用"栈拷贝"策略，Windows 系统线程栈用"保护页"策略。
> - **AI/ML 工作负载的栈管理**：现代 AI 框架（如 PyTorch、TensorFlow）在 Windows 上运行时，其底层线程池（如 Intel OpenMP、Microsoft SEAL）会创建具有大栈的线程（通常 4-8MB），因为深度学习算子常有大局部数组。这些框架在内部显式设置 `STACK_SIZE_PARAM_IS_A_RESERVATION`。
> - **WSL2 的栈行为**：WSL2 的 Linux 程序在 Windows 上通过 Hyper-V 虚拟机运行，其栈管理由 Linux 内核处理（默认 8MB），但与 Windows 宿主的栈机制完全隔离。这证明了虚拟内存机制的"虚拟化"能力——Windows 的线程栈机制和 Linux 的线程栈机制可以在同一物理机上共存于不同虚拟化层中。
