
## 第1章 读书笔记：什么是基础设施设计模式

> 💡 这一章表面上在"下定义"，实际上是在回答一个更尖锐的问题：**为什么基础设施项目总是在实施阶段或更晚的时候"爆雷"？**​ 作者的答案是——因为前面需求没定义清楚，后面所有"设计"都是在补窟窿。这是整本书的方法论基石，后面的119个模式+8种类型，本质上都是"需求 → 模式"的映射表。

---

### 1.1 什么是基础设施

原书把"基础设施"放到 IT 系统整体里定位：它不直接交付业务功能，而是为业务功能提供"稳定运行的底座"。我的理解是，可以从**第一性原理**来简化这个概念：

```
业务功能层  ──── "系统做什么" (Functional)
    │
    ▼
基础设施层  ──── "系统怎样持续地做" (Non-functional)
    │
    ▼
物理资源层  ──── 计算 / 存储 / 网络 / 机房
```

**洞见**：基础设施的本质不是"服务器+网络"，而是一种**承诺（commitment）**——向应用层承诺"无论发生什么，我都能持续提供计算、存储、网络连接能力"。这种承诺的货币不是硬件，而是**非功能性属性**：可用性、性能、安全、可扩展、可观测。

英文世界对基础设施的界定与此高度一致：infrastructure requirements describe the nonfunctional features of the underlying computational infrastructure。换句话说，**基础设施 = 非功能属性的物理化**。这一视角非常关键，因为它直接引出 1.4、1.5 节的核心论点。

---

### 1.2 基础设施故障引发的后果

原书这一节会举若干故障案例。结合工业实践，我们可以把故障后果建模为一个**连锁放大链**：

```
单次故障（单机宕机 / 网络抖动）
   │
   ▼
服务降级（响应变慢 / 部分不可用）
   │
   ▼
业务中断（订单丢失 / 交易失败）
   │
   ▼
经济损损（营收 ↓ / SLA 罚款）
   │
   ▼
信任危机（客户流失 / 品牌受损）
   │
   ▼
组织代价（复盘 / 重构 / 人员变动）
```

**工业事实锚定**：

- 可用性从 99.9% 提升到 99.99%，年停机时间从 8.77 小时压缩到 52.6 分钟，但架构复杂度与成本呈非线性上升
- 真实案例：某电商平台 Black Friday 流量达预期 10 倍，因未做容量规划，购物车超时导致超 800 万美元销售损失
- 某医疗系统因安全是"afterthought"，SQL 注入导致 50 万患者记录泄露，合规处罚+整改超 1500 万美元

**我的创新解读**：故障的代价不是"停机时长 × 单位营收"那么简单，而是**故障暴露了需求定义阶段的欠账**。每一次生产事故，回头看都是 1.4 节需求定义没做到位的延迟变现。所以这一节与 1.4 节存在因果呼应——作者把"故障后果"放在"需求定义"前面讲，是有意为之的**恐吓营销**：让你痛了，才会重视需求。

### 1.3 基础设施构建中哪个阶段最重要

原书的答案很明确：**需求定义阶段最重要**，而非设计、实施或运维阶段。

我用一张 ASCII 图来表达各阶段的影响力分布（类似"缺陷修复成本曲线"）：

```
影响力 / 成本
   │
   │   ● 需求定义
   │   |‾\\
   │   |  ● 设计
   │   |    |‾\\
   │   |    |  ● 实施
   │   |    |    |‾\\
   │   |    |    |  ● 运维
   │   |    |    |    |
   ▼   ▼    ▼    ▼    ▼
     需求  设计  实施  运维

   ←── 变更成本 exponentially 递增 ──→
```

**第一性原理推导**：

1. 基础设施的所有非功能属性（可用性、性能、安全…）都源于需求
2. 一旦需求定错，后续每个阶段都在"精确地建造错误的东西"
3. 越往后修正，要推翻的"已成事实"越多——机房已经建好、网络拓扑已固定、应用已耦合

**工业佐证**：微软 Azure Well-Architected 可靠性原则明确指出——"Design isn't guesswork based on undefined or vague outcomes"，必须在设计前与业务方对齐"可接受的用户体验、设计约束、成功如何度量"。AWS 六大支柱（Operational Excellence / Security / Reliability / Performance Efficiency / Cost Optimization / Sustainability） 本质上也是一套**需求维度的检查单**，而不是实施维度的。

**洞见**：很多团队把"需求定义"理解为写文档、签字、归档——这是错的。NTT DATA 把基础设施设计模式本身定位为"PM 支持工具，将过往案例和专家知识模式化"，意味着**需求定义阶段就需要模式语言参与**——用模式反推需求是否完整、是否冲突、是否可验证。

### 1.4 需求定义的重要性与难点

这一节是原书的方法论核心。为什么需求定义既重要又难？

#### 重要性（Why it matters）

- 应用的许多非功能属性**由基础设施交付**：建立在充满单点故障的基础设施上的应用，无论代码写得多好都达不到高可用
- 反过来，基础设施设计得再 HA，应用层写烂了，端到端依然不可靠
- 大部分基础设施预算，其实都花在满足那些**未被清晰定义的非功能需求**上

#### 难点（Why it's hard）

```
┌─────────────────────────────────────────────┐
│  难点1：隐含性                                │
│  客户/终端用户"想当然"的东西，设计者未必知道   │
│  "系统 obviously 要与现有系统无缝协作"         │
├─────────────────────────────────────────────┤
│  难点2：冲突性                                │
│  安全 vs 易用性                               │
│  性能 vs 成本                                 │
│  可用性 vs 运维复杂度                          │
├─────────────────────────────────────────────┤
│  难点3：量化难                                 │
│  "高可用" ≠ "99.99%"                          │
│  "高性能" ≠ "p99 < 200ms"                      │
│  未量化的需求 = 无法验证的需求                  │
├─────────────────────────────────────────────┤
│  难点4：利益相关方众多                         │
│  业务方 / 应用开发 / 系统管理 / 安全合规        │
│  每方都有自己的非功能诉求                       │
└─────────────────────────────────────────────┘
```

**英文文献的直接印证**：

> "It is the IT architect or requirements engineer's job to find implicit requirements on non-functional attributes... what is obvious or taken for granted by the customers or end users of a system is not always obvious to the designers and builders of the system"

> "A large part of the budget for building an infrastructure is usually spent in fulfilling non-functional requirements that are not always clearly defined"

**我的创新解读**：需求定义的真正难点不在于"问不出问题"，而在于**跨语境翻译**——

- 业务方说的是"业务语言"（"不能丢单"）
- 架构师需要翻译成"非功能语言"（"可用性 99.95%，RPO=0，RTO<5min"）
- 实施方需要翻译成"技术语言"（"多 AZ 部署 + 同步复制 + 自动故障转移"）

这个翻译链条上任何一环失真，都会导致"业务以为要了 A，技术建了 B"的经典悲剧。基础设施设计模式的价值，正是**为中间这环提供一套标准词汇表**——让"99.95% 可用性"这种需求能直接映射到一组可复用的模式组合。

### 1.5 非功能性需求等级 & 克服非功能性需求定义困难的工具

这一节原书给出了 NFR 的"等级"概念，并介绍辅助工具。结合英文文献，我们可以把 NFR 的层级看得更清楚：

#### NFR 的三层模型（英文文献佐证）

```
┌─────────────────────────────────────────┐
│  Level 1: User-level NFR                 │
│  用户级：用户如何与系统交互                  │
│  e.g. 响应时间感知、易用性                   │
├─────────────────────────────────────────┤
│  Level 2: Architecture-level NFR          │
│  架构级：系统设计应遵循的原则                │
│  e.g. 模块化、松耦合、可演进                  │
├─────────────────────────────────────────┤
│  Level 3: Infrastructure-level NFR        │
│  基础设施级：底层计算设施的非功能特性          │
│  e.g. 可用性 / 性能 / 安全 / 可扩展          │
└─────────────────────────────────────────┘
```

（来源：）

**本书重点关注的是 Level 3**，但必须意识到：**三个层级是垂直贯通的**。用户级的"页面加载不能超过 3 秒" → 架构级的"需要 CDN + 缓存" → 基础设施级的"多区域部署 + 边缘节点"。

#### 克服 NFR 定义困难的具体工具（我的整合）

原书提到的工具结合工业实践，可以归纳为以下几类：

**① 量化工具——把形容词变成数字**

- "高可用" → "99.95% 可用性，月停机 ≤ 21.9 分钟"
- "高性能" → "p99 < 200ms，吞吐 ≥ 5000 TPS"
- "安全" → "ISO 27001 合规 + 传输/静态加密 + 最小权限"

微软 Azure 框架强调：**针对每个关键用户流定义可靠性目标，而不是笼统的"站点总是不宕机"**——这是把量化落到"用户旅程"颗粒度上的最佳实践。

**② 权衡矩阵——直面冲突**

|需求 A|需求 B|冲突点|典型取舍|
|---|---|---|---|
|强安全|易用性|认证步骤|智能卡 vs 密码|
|高性能|低成本|硬件投入|更多更快的硬件 ↑ 成本 ↑|
|高可用|低成本|冗余度|多 AZ 双活 ↑ 成本 ↑|

**③ 框架化工具——用成熟框架兜底**

- **AWS Well-Architected 6 大支柱**：运维卓越 / 安全 / 可靠性 / 性能效率 / 成本优化 / 可持续性
- **Azure Well-Architected 可靠性原则**：为业务需求而设计、聚焦关键用户流、按时间维度锚定
- **SRE 黄金信号**：延迟、流量、错误、饱和度——把 NFR 变成可监控指标

**④ 模式语言工具——本书自身的贡献**

NTT DATA 把 127 个设计模式作为"需求 → 设计"的映射词典。当业务方说"不能丢数据"，架构师可以直接翻到"数据持久性"相关模式组，而不是从零开始设计。

**⑤ 早期原型与压测**

- 在类生产环境做负载测试
- 用 Chaos Engineering / Game Day 主动注入故障
- 这解决了"unvalidated assumptions on cloud scalability"的问题

**工业实践洞见**：Netflix 在 AWS 三个可用区部署相同服务，单区故障用户无感；Uber 用数百个无状态容器 + 自动扩缩容应对峰值。这些都是 NFR 被**正确定义 → 映射到模式 → 落地验证**的成功范例。

### 1.6 基础设施设计模式：研究能够满足需求的设计方式的工具

这一节是整本书的"书名释义"环节。原书定义：

> 基础设施设计模式是指将基础设施技术者们创造出的设计方式概念化、抽象化，同时给其命名（模式名），总结其特点与注意事项而形成的集合体。目的是防止在基础设施开发中发生问题，提高基础设施的开发效率以及培养基础设施开发人才。

#### 我对"设计模式"的第一性原理解读

```
传统做法：
  需求 ──→ 架构师大脑 ──→ 设计（依赖个人经验，不可复用）

模式化做法：
  需求 ──→ 模式词典 ──→ 匹配模式组合 ──→ 设计
              ↑
              沉淀自数百个项目经验
```

**设计模式本质上是一种"压缩算法"**：

- 输入：非功能需求（多 AZ？低延迟？合规？）
- 处理：模式匹配（从 127 个模式中挑选组合）
- 输出：经过验证的基础设施设计方案

NTT DATA 在 2011 年的论文中就披露，这些模式最初是作为 PM 支持工具开发的，把过往案例和专家知识模式化，在集团内部广泛复用。但论文也坦诚——**下载了模式集不等于用得好**，他们通过用户访谈发现了 4 个问题，并提出 3 个假设来改进"易用性"。

这给了我们一个非常真实的洞见：

> 💡 **模式不是银弹**。模式集的价值取决于"如何被嵌入需求定义流程"。如果架构师只是把它当"参考书偶尔翻翻"，那和没有模式没区别。模式必须成为**需求定义阶段的主动检查单**——"这个需求对应的模式有哪些？各自权衡是什么？我们选哪个？为什么？"

#### 模式与 NFR 的对应关系（预览后续章节）

```
NFR 维度               →  设计模式组（119+8）
────────────────────────────────────────────────
可用性 / 可靠性        →  冗余、故障转移、自愈、配额、熔断器
性能 / 延迟            →  缓存、CDN、读写分离、异步化
安全性                 →  零信任、加密、最小权限、审计
可扩展性               →  无状态化、水平扩展、共享无架构
成本优化               →  Right-sizing、预留实例、Spot、Tag 成本分配
可观测性               →  指标/日志/链路追踪的标准化接入
运维卓越               →  IaC、GitOps、漂移检测、滚动发布
可持续性               →  高利用率、托管服务、ARM 实例
```

注：上述映射是我基于英文工业实践对原书 127 个模式的"预分类"，帮助你在后续逐章阅读时建立索引感。

#### 工业落地：IaC 让模式"可执行"

原书出版于 2015 年，当时 IaC 还没完全主流。但 NTT DATA 自身已经在用 Terraform + Ansible + Serverspec 把设计文档参数自动同步到 IaC 代码，解决"设计文档与实际服务器参数漂移"的问题。

这揭示了一个**重要演化**：

- 2015 年的"设计模式" = 图纸（给人看的）
- 2026 年的"设计模式" = 代码模块（给机器执行的）

现代 IaC 最佳实践把模式固化成了可复用模块：

- **Module registry**：模式的可复用代码化
- **Policy-as-code**：模式的合规性自动校验
- **Drift detection**：模式意图与实际状态的持续比对
- **GitOps**：模式变更的审计追踪与回滚

> 💡 **跨越时空的洞见**：原书 127 个模式的价值，在今天不应该只是"图画在书上"，而应该**沉淀为组织的 Terraform Module Registry / Helm Chart / 内部平台工程脚手架**。这样"模式"才真正从"知识"变成"能力"。

## 我的三点创新性洞见（超越原书视角）

**① 模式不是"设计工具"，而是"需求对话工具"**

原书把模式定位为"满足需求的设计方式"。但我认为模式的更大价值在**上游**——当业务方说出模糊诉求时，架构师可以拿模式反问："你要的是'零数据丢失'还是'秒级恢复'？这两种对应不同的模式组合和不同的成本。" 模式让需求对话**结构化**。

**② NFR 的"层级穿透"是原书隐含但未明说的核心**

用户级 → 架构级 → 基础设施级，这三层必须**同时定义、同时验证**。很多项目的失败不是某一层没做好，而是层与层之间脱节——业务说"高可用"，架构师理解成"双机热备"，实施方做成"冷备"。模式语言的价值恰恰是**打通这三个层级的词汇表**。

**③ 2015 年的模式，需要在 2026 年被"代码化"才有生命力**

原书的 127 个模式是**图画+文字**。但在云原生时代，真正的"模式复用"必须是**代码模块+策略即代码+GitOps 流水线**。建议你在读书时，每看到一个模式，就思考："这个模式如果用 Terraform/Helm/Istio 怎么表达？"——这样书就读"活"了。
