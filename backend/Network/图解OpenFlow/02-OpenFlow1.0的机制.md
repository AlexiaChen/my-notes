
# 第2章 OpenFlow 1.0的机制 — 读书笔记

如果说第1章解决的是"为什么要分离控制与转发"，那第2章解决的就是"分离之后，两边到底怎么对话"。OpenFlow 1.0 是整套协议的"原初形态"——它极简、极优雅，但也极受限于当时的硬件现实。读这一章的正确姿势是：**一边学 1.0 的具体机制，一边追问"为什么后来 1.1+ 要把它改掉"**。这样你学到的不只是协议细节，而是协议演进背后的硬件经济学和工程权衡。

---

## 2.1 OpenFlow 1.0中的流表和流表项

OpenFlow 1.0 的核心抽象极其干净：**每台交换机只有一张流表，表里是一堆流表项，每个表项由"匹配域 + 计数器 + 动作"三段组成**。

```
┌────────────────────────────────────────────┐
         │              Flow Table (单张)               │
         │                                              │
         │  ┌──────────────────────────────────────┐  │
         │  │  Match Fields (12元组, 可通配)        │  │
         │  │  Counters (包数/字节数/时长)          │  │
         │  │  Actions (转发/丢弃/入队/改字段)      │  │
         │  ├──────────────────────────────────────┤  │
         │  │  Match Fields                         │  │
         │  │  Counters                             │  │
         │  │  Actions                              │  │
         │  ├──────────────────────────────────────┤  │
         │  │  ...                                  │  │
         │  └──────────────────────────────────────┘  │
         └────────────────────────────────────────────┘
```

**为什么只有一张表？**​ Princeton 的研究说得很直白：1.0 选择单表是因为它是多厂商硬件的**"最大公约数"接口**——当时 Broadcom、Intel 等芯片厂商能用最小的改动支持它。这是一种刻意的"削足适履"：为了快速落地，牺牲了表达力。

> 💡 **我的洞见**：单流表看似简单，实则埋下了 OpenFlow 1.0 在工业界落地的根本瓶颈。Open vSwitch 团队在复盘时指出：**单表 + 通配符匹配会导致"叉乘问题"（cross-product problem）——**​ 若要按字段 A 的 n₁ 种取值和字段 B 的 n₂ 种取值分别处理，哪怕 A、B 的动作互相独立，你也得安装 n₁ × n₂ 条流表项。这直接引爆了 TCAM 容量危机。

## 2.2 流表项

### 2.2.1 头字段（Header Fields）

OpenFlow 1.0 定义了经典的 **"12 元组"匹配字段**：

```
┌─────────────┬──────────────────────────────────────────┐
│ 层级         │ 12 个匹配字段                              │
├─────────────┼──────────────────────────────────────────┤
│ L1 物理     │ 入端口 (Ingress Port)                      │
│ L2 以太网   │ 源MAC / 目的MAC / EtherType                │
│ L2 VLAN     │ VLAN ID / VLAN Priority                   │
│ L3 IP       │ 源IP / 目的IP / IP协议 / IP ToS            │
│ L4 传输     │ TCP/UDP 源端口 / TCP/UDP 目的端口           │
└─────────────┴──────────────────────────────────────────┘
```

**关键机制——通配符匹配**：每个字段都可以用位掩码（bitmask）通配，IP 字段还支持子网掩码。这意味着你可以写"匹配整个 192.168.0.0/16 网段"这样的规则。

**匹配顺序的微妙之处**：流表项按顺序匹配，**命中第一条就停止**，后续表项即使也能匹配也不会被执行。这带来一个重要推论——**流表项的安装顺序就是优先级**。但这在大规模规则下极易出错，所以 1.0 后期和 1.1+ 引入了显式的 priority 字段。

> ⚠️ **工业现实**：ONF 在 1.0.1 一致性测试里干脆把支持度分成三档：
> 
> - **Full Conformance**：12 个字段全支持
> - **Layer 3 Conformance**：只支持入端口、EtherType、源IP、目的IP
> - **Layer 2 Conformance**：只支持入端口、源MAC、目的MAC、EtherType、VLAN ID
> 
> 这说明**"OpenFlow 1.0 交换机"在工业界是个频谱，不是个点**。买设备时看到"支持 OpenFlow 1.0"别高兴太早，要问清是哪一档。

### 2.2.2 计数器（Counters）

计数器的设计体现了"可观测性第一"的 SDN 哲学：

```
计数器作用域:
├── Per Table:   活跃表项数 / 查表次数 / 匹配次数
├── Per Flow:    收包数 / 收字节数 / 持续时间
├── Per Port:    收发包数 / 收发字节数 / 丢包 / 错包 / CRC错误 ...
└── Per Queue:   发送包数 / 发送字节数 / 溢出错误
```

大部分是 64 位计数器，**溢出时静默回绕，不通知控制器**——这是个工程上需要警惕的细节，长时间运行的网络要做计数器轮询，否则可能看到"包数突然变小"。

### 2.2.3 行动（Actions）

每个流表项关联一组动作，**按顺序执行**。动作集为空 = 丢弃（这是默认行为）。

## 2.3 行动

OpenFlow 1.0 定义了 4 种行动，其中 2 种必备、2 种可选：

```
┌──────────────────────────────────────────────────────┐
│  Forward  (必备)     → 转发到物理端口 / 虚拟端口       │
│  Drop      (必备)     → 静默丢弃                       │
│  Enqueue   (可选)     → 入队，用于 QoS                 │
│  Modify-Field (可选)  → 改写报文头字段                  │
└──────────────────────────────────────────────────────┘
```

### 2.3.1 Forward 行动

最基础的转发。除了物理端口，1.0 还定义了 6 个**特殊虚拟端口**：

|虚拟端口|含义|工业用途|
|---|---|---|
|**ALL**​|除入端口外所有端口|广播|
|**CONTROLLER**​|封装后发往控制器|Reactive 模式触发|
|**LOCAL**​|发往交换机本地协议栈|本机管理流量|
|**TABLE**​|重新执行流表匹配|1.0 里的"伪多级"技巧|
|**IN_PORT**​|原路返回|探测、诊断|
|**NORMAL**​|走传统以太网转发|**混合模式关键**，让非 OF 流量走传统 ASIC|
|**FLOOD**​|沿生成树泛洪（除入端口）|传统 L2 泛洪语义|

> 💡 **我的洞见**：`NORMAL` 和 `TABLE` 这两个虚拟端口是 1.0 时代的"逃生舱"。`NORMAL` 让纯 OpenFlow 交换机能在现网"棕色地带"中存活——把常规流量甩给传统 ASIC；`TABLE` 则是 OVS 等软件交换机在 1.0 时代模拟多级流表的 hack（OVS 称之为 `resubmit` 扩展）。这俩端口的存在，本身就证明了**单流表是不够用的**。

### 2.3.2 Drop 行动

没有动作的流表项 = 丢弃。这是实现防火墙 Deny 规则的天然原语。

### 2.3.3 Enqueue 行动（可选）

把包放入指定端口的指定队列，**这是 1.0 里唯一的 QoS 机制**。工业交换机如果不实现这个行动，就无法做基于队列的流量整形。

### 2.3.4 Modify-Field 行动（可选）

可以改写报文的 10 个字段（除入端口外均可改）：

```
可改写字段:
├── L2:  VLAN ID / VLAN Priority / 剥离VLAN标签 / 源MAC / 目的MAC
├── L3:  源IP / 目的IP / IP ToS
└── L4:  源端口 / 目的端口
```

**这就是 NAT、报文重写、隧道封装的底层原语**。设置 VLAN ID/优先级时若报文无标签会自动加上；剥离 VLAN 标签则移除之——这套语义让 OpenFlow 1.0 已经能表达 VLAN 交换机、NAT 网关的功能。

## 2.4 控制器和交换机之间的消息

### 2.4.1 安全通道的建立

控制器与交换机之间是一条 **TCP 连接（生产用 TLS 加密）**。关键细节：**由交换机主动发起连接到控制器**。这意味着：

- 交换机出厂需预置控制器 IP/DNS
- 控制器必须先行启动并监听
- 控制器故障恢复后，交换机会重连

### 2.4.2 消息格式

所有 OpenFlow 消息都遵循统一的 TLV 风格头部：`Version | Type | Length | Transaction ID (XID)`。XID 用于请求/响应配对，是异步协议里匹配"谁回应了谁"的关键。

### 2.4.3 安全通道的建立和初始设置

```
交换机                                        控制器
  │                                              │
  │──────── TCP 连接发起 ──────────────────────→│
  │                                              │
  │←─── TLS 握手 (若启用) ─────────────────────│
  │                                              │
  │─── Feature Request ────────────────────────→│
  │←── Feature Reply (端口/能力/交换机ID) ──────│
  │                                              │
  │─── Set Config / Get Config ────────────────→│
  │←── Set Config / Get Config Reply ──────────│
  │                                              │
  │  通道就绪，等待 Flow-Mod 下发                 │
```

### 2.4.4 握手

握手阶段控制器要搞清楚三件事：**"你是谁"（Switch ID）、"你有哪些端口"、"你能干什么"（Capabilities）**。

Capabilities 位图告诉控制器这台交换机支持哪些可选特性——比如是否支持 `Enqueue`、是否支持 `Modify-Field`、是否支持 IP 分片重组等。这直接决定了控制器后续能下发什么动作。

> ⚠️ **1.0.1 Errata 的重要澄清**：关于"表未命中（table-miss）时的默认行为"，1.0.0 规范虽然多处提及"未匹配就发往控制器"，但在实现和互操作测试中发现大量歧义。1.0.1 明确：table-miss 时**唯一**的标准行为就是通过 Packet-In 上送控制器。这个澄清对互操作性至关重要。

### 2.4.5 Flow-Mod 消息

**这是控制器操控交换机的"核心武器"**——增、删、改流表项。

```
Flow-Mod 消息结构:
├── Command: ADD / MODIFY / MODIFY_STRICT / DELETE / DELETE_STRICT
├── Match:   12元组匹配域
├── Cookie:  控制器私有的 64 位标识（交换机不透传，只用于批量操作）
├── Idle Timeout:  空闲超时（秒）—— 多久无包匹配则删除
├── Hard Timeout:  硬超时（秒）—— 不管有无流量到点就删
├── Priority:      优先级（1.0 后期加入，解决安装顺序依赖）
├── Buffer ID:     若包已被缓冲，关联此 ID 直接处理缓冲包
└── Actions:       动作列表
```

**Idle Timeout vs Hard Timeout 的工业智慧**：

- **Idle Timeout**​ 让"短暂流"自动清理——适合 Reactive 模式下海量短连接（如 HTTP 请求）
- **Hard Timeout**​ 保证"长期流"不会永久占用 TCAM——适合需要定期刷新的策略
- 两者可同时设置，**任一到期即删除**

> 💡 **洞见**：Timeout 机制本质上是用"软件层的遗忘"来弥补"硬件层的昂贵"。TCAM 容量极小（早期 Trident+ 只有 4K 条目），不允许流表项永久堆积。这是一个被很多初学者忽略、但工业界天天都在 tuning 的参数。

### 2.4.6 Packet-In 消息

交换机在两种情况下会触发 Packet-In：

1. **Table-miss**：流表里没有匹配项
2. **流表项动作显式指定**：动作里包含 "Output to CONTROLLER"

消息里携带：

- 缓冲区 ID（若交换机有能力缓冲）
- 入端口
- 原始报文头（默认 128 字节，足够控制器做决策）
- 完整报文（若交换机不支持缓冲）

```
Reactive 模式下的 Packet-In 时序:

Host A ──→ [Switch]
              │
              ├── 查流表: MISS
              │
              ▼ Packet-In (头128字节 + Buffer ID)
          [Controller]
              │ 计算路径
              ▼ Flow-Mod (Buffer ID 关联)
          [Switch]
              │ 匹配 + 执行动作
              ▼ 从缓冲区取出原包转发
            Host B
```

### 2.4.7 Packet-Out 消息

控制器主动让交换机发送一个报文。两种用途：

- **指定 Buffer ID**：让交换机把之前 Packet-In 缓冲的那个包按指定动作发出去
- **不带 Buffer ID**：携带完整报文内容，让交换机"代发"

典型场景：控制器收到 Packet-In 后，不下 Flow-Mod，而是直接发 Packet-Out 让交换机转发这一个包（适用于**只此一包、无需建流**的场景，如 ARP 请求）。

### 2.4.8 Port-Status 消息

交换机端口状态变化时（UP/DOWN、配置变更）主动上报控制器。这是 SDN 实现**网络状态实时感知**的关键——控制器能第一时间知道"某条链路断了"，从而触发重路由。

### 2.4.9 Flow-Removed 消息

流表项因超时被删除、或被控制器主动删除时，交换机上报 Flow-Removed 通知控制器。**这对流量工程和计费至关重要**——控制器借此获知一条流的完整生命周期统计。

### 2.4.10 Error 消息

交换机在执行控制器指令出错时回报。1.0 定义了丰富的错误类型层次：

```
Hello Failed:       握手失败 (Incompatible / Permission Denied)
Bad Request:        版本不符 / 类型未知 / 长度错误 ...
Bad Action:         动作类型未知 / 参数错误 / 端口无效 ...
Flow Mod Failed:    所有表满 / 重叠 / 权限不足 / 不支持 ...
Port Mod Failed:    端口不存在 / MAC 地址错误 ...
Queue Op Failed:    队列操作失败 ...
```

> 💡 **工程经验**：在分布式控制器架构里，Error 消息是调试"控制器-交换机不一致"的首选线索。成熟的 SDN 运维平台会把 Error 消息分类聚合，形成"协议层告警"。

### 2.4.11 Barrier 消息

**这是 1.0 里保证"消息顺序"的关键机制**。

控制器下发 Flow-Mod 是异步的——发完就走，不等交换机确认。但如果控制器要：

1. 先下发一条 Flow-Mod
2. **确保这条 Flow-Mod 生效后再发 Packet-Out**

就需要插入 Barrier 消息。交换机保证：**Barrier 之前的所有消息都处理完毕后，才会处理 Barrier 之后的消息**，并向控制器回复 Barrier Reply。

```
不带 Barrier (危险):
Controller ──Flow-Mod──→ Switch
Controller ──Packet-Out─→ Switch  (可能此时 Flow-Mod 还没生效!)

带 Barrier (安全):
Controller ──Flow-Mod──→ Switch
Controller ──Barrier───→ Switch
Controller ←─Barrier Reply─ Switch  (确认 Flow-Mod 已完成)
Controller ──Packet-Out─→ Switch  (此时 Flow-Mod 已生效)
```

### 2.4.12 Echo 消息

Echo Request / Echo Reply 用于：

- **保活（Keepalive）**：检测控制器-交换机连接是否存活
- **测量延迟**：RTT 估算
- **连通性测试**：类似 TCP ping

工业部署中，Echo 间隔通常是秒级（如 5-10 秒），超时阈值配合多次重试——这是 SDN 控制通道可靠性的最后一道防线。

## 2.5 OpenFlow Switch Errata Version 1.0.1

**这一节是整章里最具"工业视角"的一节**。1.0.1 不是新版本，而是 ONF 在 2012 年 6 月发布的**勘误集（Errata）**，目的是修正 1.0.0 在实现和互操作测试中暴露的问题，且**刻意最小化规范变更以保持向后兼容**。

主要修正三类问题：

**1. 常见实现误区（Informative）**

- Table-miss 默认行为：明确唯一标准是上送控制器

**2. 规范歧义澄清**

- **端口号 0 的处理**：明确语义
- **错误消息无填充**：消除实现分歧
- **无 VLAN 头的报文匹配**：明确当匹配条件包含 VLAN 字段时如何处理无 VLAN 标签的报文
- **忽略 Match 中的某些字段**：规范澄清
- **Flow-Removed 消息的生成时机**

**3. 规范变更**

- **控制器生成报文的源端口**
- **畸形报文（Malformed packets）的处理**
- **控制器连接失败行为**：明确交换机在失去所有控制器连接时的行为

> ⚠️ **关键工程启示**：1.0.1 的存在本身说明了一件事——**OpenFlow 1.0.0 的规范文本有歧义，不同厂商的实现会出现互操作问题**。所以今天你在工业界看到的"支持 OpenFlow 1.0"的设备，实际指的是"支持 1.0.1 Errata"。买设备、选控制器时务必对齐到 1.0.1 这个基线。

### 一个真实的互操作坑

Aruba 的 AOS-S 交换机文档明确列出：对 OpenFlow 1.0.0 的支持有差异——不支持 TABLE 动作、不支持 Enqueue 行动、IP 分片处理不完整、Emergency Flow Cache 不实现。这意味着**即使两台设备都宣称"支持 OpenFlow 1.0"，它们之间的行为细节也可能不同**。这是工业 SDN 部署中最大的隐性成本。

## 2.6 新规范变化很大，需要注意

这一节是作者给读者的"预警"：OpenFlow 从 1.0 到 1.1+ 发生了**质变**，不是量变。

### 单流表的"原罪"

回看 1.0 的设计，它的简洁性背后藏着三个致命约束：

**约束一：叉乘问题（Cross-product Problem）**

```
单表下，若:
  - 字段 A 有 n₁ 种处理
  - 字段 B 有 n₂ 种处理
  - A 和 B 的动作相互独立

那么流表项数量 = n₁ × n₂  (最坏情况)
```

OVS 团队的实测：在数据中心场景，若用 Reactive 模式为每一个微流（microflow）安装精确匹配表项，由于单个微流有约 275 bits 的匹配信息，朴素实现需要 2^275 个表项——显然不可能。这就是为什么工业界必须从 Reactive 转向 **Proactive + 通配符**​ 模式。

**约束二：TCAM 容量墙**

```
早期 Broadcom Trident+ ASIC:
  - L2 表 (SRAM): ~100K 条目
  - 转发表 (TCAM): ~4K 条目  ← OpenFlow 1.0 主要用这里
```

TCAM 昂贵、耗电、容量小。而 OpenFlow 1.0 的流表项匹配域长达 252 比特，比传统 IPv4 路由 TCAM 的 60-80 比特开销增加 3 倍以上。**TCAM 成本占线卡 20-30%，功耗占比巨大**。

> 💡 **工业数据**：早期 OpenFlow 1.0-1.2 由于只能使用 TCAM，流表规模被限制在 **1,000-2,000 条**。这对数据中心 ToR 交换机是远远不够的（现代数据中心单交换机需要 10K-100K 条流）。

**约束三：匹配字段的固定 12 元组**

1.0 只支持 MAC、VLAN、IPv4、TCP/UDP 端口——**没有 IPv6、没有 MPLS、没有 QinQ、没有 SCTP、没有光电路**。在 2012 年之后这些已成为运营商和数据中心的刚需。

### 1.1+ 的"质变"方向

```
1.0  →  单表 + 12元组 + TCAM only
1.1  →  多级流表 + Group Table + 流水线处理
1.2  →  可扩展匹配 + IPv6 + 多控制器
1.3  →  Meter Table + 辅助连接 + Tunnel ID (工业主流)
1.4+ →  光端口 + 同步表 + Bundle 消息
```

**多级流表（1.1+）是质变核心**。它把 1.0 单表里"挤在一起"的功能拆分到流水线上的不同表：

```
1.0 单表 (所有规则混在一起):
┌─────────────────────────────────────────┐
│ 匹配: 入端口+MAC+IP+端口 → 动作          │
│ 匹配: 入端口+MAC+IP+端口 → 动作          │
│ ... (n₁ × n₂ 条)                         │
└─────────────────────────────────────────┘

1.1+ 多级流表 (功能解耦):
┌────────────┐   ┌────────────┐   ┌────────────┐
│ Table 0    │   │ Table 1    │   │ Table 2    │
│ 分类       │→  │ ACL 安全   │→  │ 路由转发   │
│ (n₁ 条)    │   │ (公共规则) │   │ (n₂ 条)    │
└────────────┘   └────────────┘   └────────────┘
    总表项 ≈ n₁ + n₂  (而非 n₁ × n₂)
```

> 💡 **洞见**：多级流表不只是"多了几张表"，它是把网络功能**模块化**的关键。这与软件工程里的"关注点分离"（Separation of Concerns）完全是同一个第一性原理——**把独立的决策维度拆到不同的处理阶段，表项数量从乘法变加法**。

### 为什么本书以 1.0 开篇，却以 1.1+ 为主？

作者的编排很有深意：

1. **1.0 是"第一性原理的最简表达"**——单表、12 元组、四个动作，让你在最少的认知负担下理解 SDN 的核心机制
2. **1.0 的局限性是理解后续版本"为什么这样改"的钥匙**
3. **1.1+ 才是今天工业界真正在用的版本**（特别是 1.3）

读这一章时，建议你养成习惯：**每学一个 1.0 的机制，就反问"它在 1.1+ 里会怎么演化"**。这样当你读到后面章节时，会发现一切改动都有迹可循。

## 贯穿第2章的核心洞见

```
OpenFlow 1.0 的本质:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
"用最小公约数接口，撬动现有交换机硬件"

       单表 + 12元组 + 4动作
              │
              ▼
   极简 → 易实现 → 快速落地
              │
              ▼
   但也带来 → 叉乘问题 + TCAM 墙 + 字段固定
              │
              ▼
   工业现实 → 必须 Proactive + 通配符
            → 必须混合部署 (NORMAL 端口)
            → 必须接受 1.0.1 勘误
              │
              ▼
   催生演进 → 1.1 多级流表
            → 1.3 工业主流
            → TTP 访问更多 ASIC 资源
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

**给工程师的三条实战建议**（这是书本之外，从工业部署中总结的）：

1. **Timeout 不是默认值，是架构决策**：Idle/Hard Timeout 的设置直接决定 TCAM 利用率和控制器负载。Reactive 模式下 Idle Timeout 通常设 5-60 秒，Proactive 模式下 Hard Timeout 可能设数小时。
2. **Barrier 是你的朋友**：凡是"先建流、再发包"的场景，Flow-Mod 和 Packet-Out 之间必加 Barrier。否则你会遇到诡异的"偶发丢包"——因为 Packet-Out 跑得比 Flow-Mod 快。
3. **监控 Table-Miss 率**：Table-Miss 率高 = 要么 Proactive 下流不充分，要么攻击流量在探测。这是 SDN 网络安全告警的核心指标之一。

**最后一点批判性思考**：OpenFlow 1.0 常被诟病"生不逢时"——它想用统一的流抽象表达所有网络功能，但硬件现实是**多表、多内存类型（SRAM/TCAM/DRAM）的异构集合**。这种"协议理想"与"硬件现实"的错位，正是后来 P4 等数据面可编程方案崛起的根本原因。但 1.0 的价值不可磨灭：它用最简单的抽象证明了"控制与转发分离"在工程上是可行的，为整个 SDN 时代奠定了基础。
