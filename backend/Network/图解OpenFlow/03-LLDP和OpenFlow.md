
# 第3章 LLDP 和 OpenFlow — 读书笔记

如果说第1章讲"为什么分离"，第2章讲"分离后两边怎么对话"，那么第3章讲的就是**"控制器如何看见网络"**。这是 SDN 从"能通信"走向"能路由"的关键一跃：**一个看不见拓扑的控制器，不可能做任何路径决策**。而 OpenFlow 1.0 本身并没有定义拓扑发现机制——这个空缺，由 LLDP 来填补。本章的精妙之处在于：它展示了如何用上一章学的 Packet-Out / Packet-In 这对消息，把原本运行在交换机本地的 LLDP，"劫持"到控制器集中执行，从而构建全局拓扑视图。

---

## 3.1 LLDP 和 OpenFlow

**核心命题**：LLDP 本是 IEEE 802.1AB 定义的、运行在交换机本地的二层邻居发现协议；但在 OpenFlow 网络里，交换机已经"退化"成纯粹的转发单元，没有能力自己运行 LLDP。怎么办？

答案是——**让控制器"代行" LLDP 的职责**。

```
传统网络中的 LLDP:
┌─────────┐         LLDP 协商          ┌─────────┐
│ Switch A│←━━━━━━━━━━━━━━━━━━━━━━━━━→│ Switch B│
│ (自己发) │                           │ (自己发) │
└─────────┘                           └─────────┘
  每台交换机各自维护邻居表

OpenFlow 网络中的 LLDP:
┌─────────┐                           ┌─────────┐
│ Switch A│                           │ Switch B│
└────┬────┘                           └────▲────┘
     │ Packet-Out (带 LLDP)                 │ Packet-In (带 LLDP)
     │                                     │
     ▼                                     │
┌──────────────────────────────────────────────────┐
│                  Controller                       │
│         (LLDP 的"大脑"跑到这里来了)               │
└──────────────────────────────────────────────────┘
   控制器统一构造、统一解析、统一建拓扑
```

> 💡 **第一性原理视角**：LLDP 在 SDN 中的角色转换，本质上是"控制面集中化"这一根本思想在"邻居发现"这个具体功能上的投影。传统网络里，每个节点都跑一份 LLDP 实例，各自维护局部邻居表；SDN 把这份"实例"抽上来，变成控制器里的一个全局服务——**Link Discovery Service (LDS)**。业界把这个适配了 SDN 的 LLDP 称为 **OFDP（OpenFlow Discovery Protocol）**。

**为什么不用别的办法？**​ 有人可能会问：控制器既然能通过 Features Reply 拿到每台交换机的端口信息，能不能直接"问"出拓扑？不能。因为 Features Reply 只告诉你"这台交换机有哪些端口"，**不告诉你"端口另一头连的是谁"**。物理连线信息，本质上只能通过"从一端发一个探针、看另一端收到谁发的"这种方式来获得——这正是 LLDP 干的事。

## 3.2 LLDP 的机制

### 3.2.1 在 LLDP 中使用的目标以太网地址

LLDP 帧的目的 MAC 是**固定的组播地址 `01:80:C2:00:00:0E`**，对应 IEEE 802.1AB 规定的 "Nearest Bridge" 地址。

```
LLDP 以太网帧结构:
┌──────────┬──────────┬──────────┬──────────┬─────┐
│  DMAC    │  SMAC    │ EtherType│  LLDPDU  │ FCS │
│ 6 Bytes  │ 6 Bytes  │ 2 Bytes  │ ~1500B   │4B   │
└──────────┴──────────┴──────────┴──────────┴─────┘
  01:80:C2    发送端口    0x88CC   TLV 序列
  00:00:0E   的 MAC
```

**为什么是这个地址？**​ `01:80:C2:00:00:0E` 是 IEEE 802.1 定义的"最近的桥"组播地址——**任何二层桥接设备收到这个地址的帧都不会转发，只在本链路内传递**。这保证了 LLDP 的"一跳语义"：它只用来发现直连邻居，不会泄露到整个网络。

> 💡 **工业洞见**：这个地址的选择绝非偶然，而是 LLDP 设计哲学的体现——**"我只关心和我手牵手的那个邻居"**。这种"一跳即弃"的语义，恰好是构建全局拓扑的最小原子操作：控制器只要知道所有"一手牵手"关系，就能拼出整张网络图。

### 3.2.2 LLDP 中使用的 3 种组播以太网地址

IEEE 802.1AB 实际上定义了**一组**组播地址，分别对应不同"传播边界"：

|目的 MAC|名称|传播范围|
|---|---|---|
|`01:80:C2:00:00:0E`|Nearest Bridge|不被任何桥转发，**仅限本链路**​|
|`01:80:C2:00:00:03`|Nearest non-TPMR Bridge|可被 TPMR 转发，但不被其他桥转发|
|`01:80:C2:00:00:00`|Nearest Customer Bridge|仅在 Customer Bridge 之间传播|

```
01:80:C2:00:00:0E  ← LLDP 默认用这个，最严格的一跳限制
       │
       ▼
   ┌─────────┐         ┌─────────┐
   │ Switch A│━━━━━━━━━│ Switch B│
   └─────────┘  仅此一跳 └─────────┘
       × 帧到了 B 就不会再被 B 转发给 C
```

> ⚠️ **工程提醒**：在 SDN 环境中，控制器用 Packet-Out 发出的 LLDP 帧，目的 MAC 必须是 `01:80:C2:00:00:0E`。如果误设为其他组播地址，可能导致 LLDP 帧被对端交换机意外转发，污染拓扑发现结果。这是初学者在写自定义控制器时常见的 bug。

### 3.2.3 LLDPDU 格式

LLDPDU 是 LLDP 的载荷，由一系列 **TLV（Type-Length-Value）**​ 组成：

```
┌──────────────────────────────────────────────────────┐
│  Mandatory TLVs (必选)                                │
├──────────────────────────────────────────────────────┤
│  TLV: Chassis ID       → 交换机标识 (通常是 MAC/DPID) │
│  TLV: Port ID           → 端口标识 (端口号/端口名)     │
│  TLV: TTL               → 存活时间                     │
├──────────────────────────────────────────────────────┤
│  Optional TLVs (可选)                                 │
├──────────────────────────────────────────────────────┤
│  TLV: Port Description   → 端口描述                   │
│  TLV: System Name        → 系统名                     │
│  TLV: System Description → 系统描述                   │
│  TLV: System Capabilities→ 系统能力                   │
│  TLV: Management Address → 管理地址                   │
├──────────────────────────────────────────────────────┤
│  End TLV (Type=0, Length=0)                          │
└──────────────────────────────────────────────────────┘
```

**在 OpenFlow 场景中，控制器主要利用前两个 TLV**：

- **Chassis ID TLV**：填入**发送方交换机的 Datapath ID（DPID）**——相当于交换机的"身份证"
- **Port ID TLV**：填入**发送方交换机的具体端口号**

这两个 TLV 组合起来，就是一句完整的"自报家门"：**"我是交换机 X 的端口 Y 发出的这个帧"**。

```
TLV 示例 (控制器构造 LLDPDU 时):
┌─────────────────────────────────────────┐
│ Chassis ID TLV:                          │
│   Type=1, Length=7                       │
│   Value= 00:00:00:00:00:01 (DPID of S1)  │
├─────────────────────────────────────────┤
│ Port ID TLV:                             │
│   Type=2, Length=4                       │
│   Value= 2 (Port 2 of S1)                │
├─────────────────────────────────────────┤
│ TTL TLV:                                 │
│   Type=3, Length=2                       │
│   Value= 120 (秒)                        │
├─────────────────────────────────────────┤
│ End TLV:                                 │
│   Type=0, Length=0                       │
└─────────────────────────────────────────┘
```

> 💡 **洞见**：TLV 的设计是 LLDP 最优雅的地方——**可扩展**。这也是为什么后来工业界能在 LLDP 里塞入 QoS TLV、业务属性 TLV 等自定义信息，使 LLDP 从"拓扑探针"升级为"拓扑+性能探针"。论文 _The Top-K QoS-aware Paths Discovery for Source Routing in SDN_ 正是利用这个扩展性，把时延、带宽等 QoS 信息封装进 LLDP 的自定义 TLV，让 LLDP 不仅报告"谁连着谁"，还报告"这条链路质量如何"。

## 3.3 OpenFlow 中有效使用 LLDP 的方法示例

这一节是整章的"实战核心"。作者展示了一个完整的 LLDP 拓扑发现流程。我们结合工业实践把它拆得更细。

### 3.3.1 事先准备

在发送第一个 LLDP 帧之前，控制器必须完成两件事：

**第一步：与交换机握手，获取 DPID 和端口信息**

```
Controller ──Features Request──→ Switch
Controller ←─Features Reply──── Switch
              (包含: DPID, 端口列表, 端口状态)
```

**第二步：下发流表项，让交换机"见到 LLDP 就上送"**

控制器需要在每台交换机上安装一条"捕获规则"：

```
Match: EtherType == 0x88CC   (即 LLDP 帧)
Action: Output to CONTROLLER  (上送控制器)
```

这条规则的作用是：**让交换机自己不要处理 LLDP 帧，而是统一交给控制器**。这印证了那句关键的话——"OpenFlow 交换机不识别 LLDP，只当普通报文处理"。

> ⚠️ **注意**：有些资料描述的流程是"控制器先下发流表要求针对 LLDP 执行上送动作"，随后再通过 Packet-Out 封装 LLDP 报文。在实际的控制器（如 Floodlight）实现中，也确实是先确保交换机能够匹配并上送 LLDP 帧，然后再由控制器主动发送 LLDP 探测。

### 3.3.2 通过 Packet-Out 消息发送 LLDP 帧

控制器为交换机的**每一个活跃端口**构造一个 LLDP 帧，并用 Packet-Out 消息指示交换机从该端口发出去。

```
以 S1 为例，它有 3 个端口 (port1, port2, port3):

Controller 构造 LLDP #1:
  Chassis ID = S1 的 DPID
  Port ID = 1
  封装进 Packet-Out:
    Action: Output to port 1
  ──Packet-Out──→ S1 ──从 port1 发出 LLDP──→ 链路

Controller 构造 LLDP #2:
  Chassis ID = S1 的 DPID
  Port ID = 2
  封装进 Packet-Out:
    Action: Output to port 2
  ──Packet-Out──→ S1 ──从 port2 发出 LLDP──→ 链路

Controller 构造 LLDP #3:
  Chassis ID = S1 的 DPID
  Port ID = 3
  封装进 Packet-Out:
    Action: Output to port 3
  ──Packet-Out──→ S1 ──从 port3 发出 LLDP──→ 链路
```

**时序图（单向链路发现 S1:port2 → S2:port1）**：

```
Controller          Switch 1          链路          Switch 2
    │                  │                            │
    │── Packet-Out ──→ │                            │
    │   (LLDP:         │                            │
    │    Chassis=S1    │                            │
    │    Port=2)       │                            │
    │   Action:        │                            │
    │   out port2      │                            │
    │                  │── LLDP 帧从 port2 发出 ──→│
    │                  │                            │
    │                  │                   收到 LLDP 帧
    │                  │                            │
    │                  │                   匹配流表: EtherType=0x88CC
    │                  │                   动作: 上送控制器
    │                  │                            │
    │                  │                   封装 Packet-In
    │                  │←── Packet-In ────────────│
    │                  │   (LLDP 载荷 + 入端口=port1)
    │                  │
    │ 解析 Packet-In:
    │   发送方: S1 (从 LLDP Chassis ID)
    │   发送端口: 2 (从 LLDP Port ID)
    │   接收方: S2 (从 Packet-In 来源)
    │   接收端口: 1 (从 Packet-In 入端口)
    │
    │ ★ 推断: S1:port2 ←→ S2:port1 直连
```

### 3.3.3 通过 Packet-In 消息将 LLDP 帧发送至 OpenFlow 控制器

对端交换机 S2 收到 LLDP 帧后的处理逻辑（关键点）：

```
S2 收到 LLDP 帧:
  ① 查流表: 匹配 EtherType == 0x88CC
  ② 执行动作: Output to CONTROLLER
  ③ 构造 Packet-In 消息:
     - 载荷: 原始 LLDP 帧 (包含 S1 的 Chassis ID 和 Port ID)
     - 元数据: 入端口 = port1
     - 元数据: 发送方 DPID = S2 的 DPID
  ④ 通过 OpenFlow 通道发送给控制器
```

**控制器收到 Packet-In 后做的事**：

```
Packet-In 解析:
┌──────────────────────────────────────────────┐
│  LLDP 载荷解析:                               │
│    Chassis ID = S1 的 DPID  → 发送方交换机     │
│    Port ID = 2              → 发送方端口       │
├──────────────────────────────────────────────┤
│  Packet-In 元数据:                             │
│    来源交换机 = S2 的 DPID     → 接收方交换机   │
│    入端口 = 1                 → 接收方端口     │
└──────────────────────────────────────────────┘
         ↓
  推断: S1 的 port2 与 S2 的 port1 直连
         ↓
  更新拓扑数据库:
    Link(S1:port2, S2:port1)  ← 单向链路
```

**获取双向链路**：上述过程只发现了 S1→S2 的单向链路。要确认双向连通，控制器还需要反向再来一次——从 S2 的 port1 发 LLDP，让 S1 上送 Packet-In。两次结合，确认 **S1:port2 ↔ S2:port1**​ 是双向直连链路。

**全网拓扑发现**：控制器对所有交换机、所有端口重复这个过程，就能拼出完整的网络拓扑图：

```
S1
             /  \
       (p2) /    \ (p3)
           /      \
         S2        S3
          \       /
       (p1)\     /(p1)
            \   /
             S4

控制器维护的拓扑数据库:
  Nodes: {S1, S2, S3, S4}
  Links: {
    (S1:p2, S2:p1),
    (S1:p3, S3:p1),
    (S2:p1, S4:p1),
    (S3:p1, S4:p2)
  }
```

> 💡 **工业视角**：LLDP 在实际部署中通常**每 10 秒发送一次**（这是许多控制器如 Floodlight 的默认配置），以平衡拓扑新鲜度和控制通道开销。链路超时时间一般设为 LLDP 发送间隔的数倍（如 30-60 秒），超过这个时间没收到对端 LLDP，就认为链路断开。

> ⚠️ **安全警示（书本之外的工业现实）**：LLDP 拓扑发现存在一个严重的安全隐患——**拓扑投毒攻击（Topology Poisoning Attack）**。因为 Packet-In 里的 LLDP 载荷是明文且可伪造的，攻击者可以构造假的 LLDP 帧发往交换机，让交换机上送伪造的 Packet-In，从而欺骗控制器"看到"不存在的链路。IEEE 论文 LINK-GUARD 专门研究了这个问题，提出用端口指纹、加密签名等机制防护。**这是一个在教科书里很少提、但在生产环境必须考虑的议题**。

## 3.4 基于迪杰斯特拉算法的路径计算

拓扑发现只是手段，**路径计算才是目的**。控制器拿到全局拓扑图后，就可以用图论算法计算任意两点间的最优路径。Dijkstra 算法是当之无愧的主角。

### 从拓扑图到加权图

控制器把 LLDP 发现的拓扑转化为一个**加权有向图**：

```
拓扑图 (LLDP 发现):              加权图 (Dijkstra 输入):
                                 
    S1                               S1
   /  \                             /  \
 2/    \3                          2/    \1
 /      \                          /      \
S2      S3                     S2          S3
  \     /                        \         /
  1\   /2                        1\       /4
    \ /                            \     /
     S4                              S4

节点 = 交换机                        边权 = 链路代价
边权可根据: 跳数、时延、带宽、负载等计算
```

### 链路代价函数

工业界常用的代价函数（引自 IIETA 期刊论文）：

```
C(i,j) = L(i,j) + B(i,j) + H(i,j)

其中:
  L(i,j) = 链路时延
  B(i,j) = 1/可用带宽 (带宽越小代价越大)
  H(i,j) = 跳数
```

更精细的如 EIGRP 复合度量：

```
Cost = 256 × (K1·Bw + K2·Bw/(256-Load) + K3·Delay×K5/(Rl+K4))
默认 K1=K3=1, K2=K4=K5=0 → Cost = 256 × (Bw + Delay)
```

### Dijkstra 在控制器中的执行流程

```
输入: 加权图 G=(V, E), 源节点 s, 目的节点 t
输出: 最短路径 P = [v1, v2, ..., vk]

算法核心思想 (优先队列实现):
┌────────────────────────────────────────────┐
│ 1. dist[s] = 0, dist[v] = ∞ (∀v≠s)         │
│ 2. 优先队列 PQ = {s}                        │
│ 3. while PQ 非空:                           │
│ 4.   u = PQ.extract_min()                  │
│ 5.   for each 邻居 v of u:                 │
│ 6.     if dist[u] + w(u,v) < dist[v]:      │
│ 7.       dist[v] = dist[u] + w(u,v)        │
│ 8.       prev[v] = u                       │
│ 9.       PQ.decrease_key(v, dist[v])       │
│10. 回溯 prev[] 得到路径                      │
└────────────────────────────────────────────┘
```

### 工业实战：Floodlight 控制器的 OSPF-like 路由循环

以工业界广泛使用的 Floodlight 控制器为例，它的 30 秒控制循环是这么跑的：

```
┌──────────────────────────────────────────────────────┐
│  Every 30 seconds:                                   │
│                                                      │
│  1. Topology Discovery:                              │
│     通过 LLDP 更新图 G=(V,E)                          │
│                                                      │
│  2. for each link e in E:                            │
│     计算 EIGRP 代价 w(e) = 256 × (Bw + Delay)        │
│     归一化度量; 劣化链路施加大惩罚                     │
│                                                      │
│  3. for each VLAN:                                   │
│     构建策略约束子图 Gs                               │
│     添加虚拟超级源点 (zero-cost edges)                │
│     从超级源点多源 Dijkstra:                          │
│       使用二叉堆优先队列                              │
│       平局打破: 先比跳数少, 再比字典序(DPID,port)     │
│                                                      │
│  4. 提取下一跳路径                                    │
│     通过 REST 静态流表推送器安装对称 OF1.3 流表项      │
│                                                      │
│  5. 版本化标记, 稳定性保障                            │
└──────────────────────────────────────────────────────┘
```

### Dijkstra 与多路径

标准 Dijkstra 只给出一条最短路。工业界往往需要**多条路径**做负载均衡：

- **K Shortest Paths (KSP)**：Dijkstra 的变种，计算前 K 条最短路
- **Widest-Shortest Path**：在保证最短路的前提下，选择带宽最大的路径——适合大象流（elephant flow）

```
示例: Host → Server 有多条路径

        ┌── S2 ──┐
        │   10G  │
Host ── S1       S4 ── Server
        │   1G   │
        └── S3 ──┘

Dijkstra (按跳数): 两条路径都是 2 跳 → 无法区分
Dijkstra (按带宽): S1→S2→S4 路径最小带宽 10G
                   S1→S3→S4 路径最小带宽 1G
                   → 大象流选 S1→S2→S4
```

> 💡 **洞见**：LLDP 提供的只是**静态拓扑**（谁连着谁），但 Dijkstra 需要的是**动态加权图**（每条链路的实时代价）。这意味着控制器必须在 LLDP 之外，通过主动测量（active probing）或被动统计（从 Flow Stats 获取）来持续更新链路时延、可用带宽等动态指标。SDN 路由方法的研究指出："LLDP 善于收集静态链路状态数据，但在动态场景下，路由需要的不止是静态测量。控制器必须不断监控这些动态特性，以确保正确的网络状态信息（NSI）。" 这正是现代 SDN 控制器（如 Floodlight、ONOS）在做的事——**LLDP 负责骨架，动态测量负责血肉**。

### 从路径到流表：闭环完成

Dijkstra 算出路径后，控制器必须把"路径"翻译成"流表项"：

```
Dijkstra 输出: S1 → S2 → S4 (Host 到 Server 的路径)

翻译为流表项:
┌──────────────────────────────────────────────────┐
│ 在 S1 安装:                                       │
│   Match: 源IP=Host, 目的IP=Server                 │
│   Action: Output to S1-S2 链路端口                │
├──────────────────────────────────────────────────┤
│ 在 S2 安装:                                       │
│   Match: 源IP=Host, 目的IP=Server                 │
│   Action: Output to S2-S4 链路端口                │
├──────────────────────────────────────────────────┤
│ 在 S4 安装:                                       │
│   Match: 源IP=Host, 目的IP=Server                 │
│   Action: Output to Server 所在端口               │
└──────────────────────────────────────────────────┘

(如果是双向通信, 还需安装对称的反向流表项)
```

至此，**"LLDP 发现拓扑 → Dijkstra 计算路径 → Flow-Mod 下发流表"**​ 的完整闭环打通。这就是 SDN 路由的根本机制。

**五个工程层面的关键认知**：

**1. LLDP 是 SDN 的"眼睛"，但眼睛有盲区**

LLDP 只能发现**静态拓扑**（谁连着谁），看不到动态状态（时延、带宽、丢包）。工业控制器必须配合主动测量（如 Ping、BW probe）才能做出高质量路由决策。

**2. LLDP 发送频率是权衡的艺术**

- 太快 → 控制通道开销大，交换机 CPU 压力大
- 太慢 → 拓扑变化感知迟滞，可能导致临时黑洞
- 工业默认：**10 秒一次 LLDP 发送，30-60 秒链路超时**

**3. 单向链路发现必须做双向确认**

从 S1 发 LLDP 被 S2 收到，只能证明 S1→S2 单向连通。必须反向再发一次，才能确认双向链路。这对网络测量至关重要。

**4. Dijkstra 的权重函数决定路由质量**

- 按跳数 → 最少跳路由
- 按时延 → 最低时延路由
- 按带宽倒数 → 最大带宽路由
- 复合度量 → 多约束 QoS 路由

**5. 拓扑发现的安全威胁是生产环境必须面对的**

LLDP 拓扑投毒攻击（LFA）可以让控制器"看到"虚假链路，从而把流量引向攻击者。工业部署需要 LINK-GUARD 这类防护机制。

> ⚠️ **批判性思考**：LLDP + Dijkstra 这套组合虽然是 SDN 路由的经典范式，但它有固有的**反应式延迟**——拓扑变化 → LLDP 超时检测到 → 控制器重算 → Flow-Mod 下发，这一链条在大型网络中可能需要数十秒。这也是为什么现代 SDN 控制器（如 Google B4 的控制器）会采用**​ proactive + 预计算**策略：提前算好所有候选路径，链路故障时秒级切换。理解了这个局限，你就能理解为什么 2015 年后业界开始探索 **P4 + 智能网卡**​ 等更激进的数据面可编程方案——它们试图把"路径计算"的部分能力下沉到交换机本地，减少反应式延迟。

但无论如何演进，**"集中式拓扑发现 + 全局路径计算"这一第一性原理不变**。第3章教的不是 LLDP 这个具体协议，而是**"如何让控制面获得全局视野"**​ 这一根本方法论。掌握了这个方法论，无论未来协议怎么变（从 LLDP 到 BFD，从 Dijkstra 到约束最短路径），你都能一眼看清本质。
