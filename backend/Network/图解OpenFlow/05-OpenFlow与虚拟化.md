
# 第5章 OpenFlow 与虚拟化 — 读书笔记

如果说前四章讲的是"如何用 OpenFlow 造单台交换机"，那么这一章讲的是"如何用 OpenFlow 造一整个虚拟网络世界"。作者的编排逻辑非常清晰：**服务器虚拟化逼出了网络虚拟化，而 OpenFlow 恰好是网络虚拟化最自然的载体，FlowVisor 则是把这个载体变成"多租户、多控制器共存"的关键一层**。

这一章的真正价值在于：它让你看清 **"虚拟化"不是一个功能，而是一种架构立场**——把原来固化在硬件里的"网络身份"（VLAN、IP、端口、策略）全部抽出来，变成控制器里可编程、可迁移、可隔离的软件对象。

---

## 5.1 服务器虚拟化和网络虚拟化

### 5.1.1 服务器虚拟化

服务器虚拟化的本质，是用 Hypervisor 在 x86 硬件和 Guest OS 之间插入一个**抽象层**：

```
传统物理服务器:
┌────────────────────────────┐
│  App                       │
│  OS                        │
│  Hardware (CPU/RAM/NIC)    │
└────────────────────────────┘

虚拟化后:
┌─────────────────────────────────────────┐
│  App1       App2       App3              │
│  OS1        OS2        OS3               │
├─────────────────────────────────────────┤
│  Hypervisor (VMware/Xen/KVM)             │
│  ↑ 抽象层: CPU/内存/IO 虚拟化             │
├─────────────────────────────────────────┤
│  Hardware (CPU/RAM/NIC)                 │
└─────────────────────────────────────────┘
```

> 💡 **第一性原理**：Hypervisor 做的事情，是**把"硬件资源"与"操作系统看到的资源"解耦**。Guest OS 以为自己在独占硬件，实际上看到的是 Hypervisor 虚拟出来的 vCPU、vRAM、vNIC。这种"欺骗"是虚拟化的核心技艺。

### 5.1.2 动态迁移（Live Migration）

服务器虚拟化最杀手锏的功能是 **vMotion / Live Migration**——虚拟机在物理服务器之间迁移时，业务不中断。

```
迁移前:
┌────────────┐              ┌────────────┐
│ Server A   │              │ Server B   │
│ ┌────────┐ │              │            │
│ │ VM1     │ │─────────────│→ VM1      │
│ │ (running)│ │ 内存页增量同步│ (running) │
│ └────────┘ │              │            │
└────────────┘              └────────────┘
     VM 在网络中的"位置"变了
```

**这就给网络出了个难题**：VM1 的 IP 和 MAC 不变，但它的接入端口从 Server A 的 NIC 变成了 Server B 的 NIC。传统网络中，这需要管理员手动改交换机配置、刷新 MAC 表、调整 VLAN 归属——**完全跟不上迁移的速度**。

> ⚠️ **工业现实**：在 VMware vSphere 集群中，一次 vMotion 通常在秒级完成。如果网络收敛时间超过这个窗口，就会出现**短暂的业务中断或丢包**。这就是为什么 2008 年之后"网络必须跟上计算虚拟化"成为行业刚需。

### 5.1.3 多租户（Multi-tenancy）

云计算把多租户推到了极致：

```
┌─────────────────────────┐
                    │      Cloud Provider      │
                    └─────────────────────────┘
                         ↓ 物理资源池
        ┌────────────────────────────────────────┐
        │  Tenant A │ Tenant B │ Tenant C        │
        │  App/OS   │ App/OS   │ App/OS          │
        │  vNet A   │ vNet B   │ vNet C          │
        │  (10.0/16)│ (172.16/12)│ (192.168/16)  │
        └────────────────────────────────────────┘
        
        关键: 租户 A/B/C 的网络完全隔离
              但可以共享同一套物理交换机/链路
```

**网络面临的挑战**：

- IP 地址空间可以重叠（A 和 B 都用 10.0.0.0/16）
- 广播域必须隔离
- QoS 必须保证
- 安全策略必须独立

传统 VLAN 只能提供 **4094 个隔离域**——对大规模公有云远远不够。而且 VLAN 是**交换机本地配置**，无法在控制器层面全局编排。

### 5.1.4 网络虚拟化

**网络虚拟化 = 把 Hypervisor 的思想搬到网络上**。

```
类比:
┌────────────────────────────────────────────┐
│ 服务器虚拟化                     网络虚拟化   │
├────────────────────────────────────────────┤
│ Hypervisor ↔ FlowVisor/SDN Controller      │
│ x86 指令集   ↔ OpenFlow 协议               │
│ CPU/RAM/IO  ↔ 带宽/拓扑/转发表/设备CPU      │
│ VM           ↔ 虚拟网络切片 (vSDN)           │
│ Guest OS     ↔ 租户控制器                   │
└────────────────────────────────────────────┘
```

正如资料中指出的："FlowVisor 就是位于硬件结构元件和软件之间的网络虚拟层"，它"将物理网络分成多个逻辑网络，从而允许多个控制器同时控制一台 OpenFlow 交换机"。

> 💡 **洞见**：网络虚拟化的第一性原理与服务器虚拟化完全相同——**插入抽象层，让上层"以为"自己独占资源，实际上底层是多路复用**。区别在于：
> 
> - 服务器虚拟化的抽象对象是 **x86 指令集**
> - 网络虚拟化的抽象对象是 **OpenFlow 协议**
> 
> 这个类比不是修辞，而是架构同源。理解了这一点，你就能理解为什么 FlowVisor 的设计者会自然地把它类比为"网络界的 Hypervisor"。

## 5.2 基于 OpenFlow 的网络虚拟化的实现方法示例

OpenFlow 实现网络虚拟化有多种思路，每种都有其适用场景和局限。

### 5.2.1 使用 VLAN ID 的方法

**最简单直接的虚拟化方式**：用 VLAN ID 作为租户隔离的维度。

```
租户 A → VLAN 10
租户 B → VLAN 20
租户 C → VLAN 30

OpenFlow 流表项 (Switch 视角):
┌──────────────────────────────────────────┐
│ Match: dl_vlan=10 → Action: 租户A的转发逻辑 │
│ Match: dl_vlan=20 → Action: 租户B的转发逻辑 │
│ Match: dl_vlan=30 → Action: 租户C的转发逻辑 │
└──────────────────────────────────────────┘
```

**优点**：

- 简单、直观、与现有 VLAN 基础设施兼容
- 交换机硬件 NATIVELY 支持 VLAN 标签处理

**缺点**：

- VLAN 空间只有 12 bit = 4094 个——大规模多租户不够用
- **VLAN 只能隔离流量，不能控制转发面**——租户无法自定义路由逻辑
- 无法处理重叠 IP 地址空间

> ⚠️ **关键认知**：VLAN 是"弱虚拟化"——它解决了 L2 隔离，但没有解决"控制面虚拟化"。租户 A 的控制器无法独立定义"VLAN 10 的包应该怎么路由"，因为路由决策仍由物理交换机（或单一控制器）统一做出。

### 5.2.2 使用物理端口/逻辑端口的方法

**第二种思路**：用端口来划分租户。

```
物理端口划分:
┌──────────────────────────────────────────┐
│ Switch                                   │
│ ┌──────────────────────────────────────┐ │
│ │ port1-4  → 租户 A 专属               │ │
│ │ port5-8  → 租户 B 专属               │ │
│ │ port9-12 → 租户 C 专属               │ │
│ └──────────────────────────────────────┘ │
└──────────────────────────────────────────┘

逻辑端口划分 (基于隧道):
┌──────────────────────────────────────────┐
│ 租户 A: GRE/VXLAN 隧道 → 逻辑端口 "A"    │
│ 租户 B: GRE/VXLAN 隧道 → 逻辑端口 "B"    │
│ 租户 C: GRE/VXLAN 隧道 → 逻辑端口 "C"    │
└──────────────────────────────────────────┘
```

**优点**：

- 隔离性最强——物理端口完全独占
- 逻辑端口通过隧道实现，跨物理节点透明

**缺点**：

- 物理端口划分浪费端口资源
- 逻辑端口需要隧道封装开销
- 扩展性差——端口数量是硬限制

### 5.2.3 OpenFlow 控制器的实现要点

无论采用哪种虚拟化维度，控制器的设计都必须面对以下核心问题：

**① 流空间（FlowSpace）的划分**

FlowVisor 论文里提出的"流空间"概念是核心抽象：把数据包头的 12 元组（256 bit）看作一个 256 维空间，每个切片占据这个空间的一个子集。

```
256-bit 包头空间:
┌────────────────────────────────────────────┐
│ 切片 A: src_ip=10.0.0.0/8, dst_port=80     │
│ 切片 B: src_ip=172.16.0.0/12              │
│ 切片 C: vlan=30                           │
│ 剩余空间: 默认切片 / 拒绝                  │
└────────────────────────────────────────────┘
```

**② 资源隔离的五个维度**

FlowVisor 把网络资源切片重点放在 5 项：

- **带宽隔离**：通过 QoS 队列（基于 VLAN PCP / IP ToS / OF QoS 分类）
- **拓扑发现**：每个切片看到独立的拓扑子集
- **流量工程**：切片独立的路径计算
- **设备 CPU 监测**：限制每个切片的慢路径包上送速率
- **转发表控制**：追踪哪些流表项属于哪个切片

**③ 切片策略语言**

每个切片由文本配置文件定义，包含 allow / read-only / deny 规则，按照类似防火墙规则的有序列表解析。

### 5.2.4 其他方法

除了 VLAN 和端口，工业界还探索了：

- **基于隧道标签（如 VXLAN VNI）**：24 bit 空间，支持 1600 万隔离域
- **基于 MPLS 标签**：运营商级虚拟化
- **基于 FlowVisor 的流空间划分**：最灵活，但最复杂
- **基于 OpenVirteX (OVX) 的网络嵌入**：给用户分配独立租户 ID，支持自定义拓扑

> 💡 **洞见**：虚拟化的本质是"命名空间的多路复用"。VLAN 用 12 bit 命名空间，VXLAN 用 24 bit，FlowVisor 流空间用 256 bit 包头空间。命名空间越大，虚拟化越灵活，但控制面复杂度也越高。这是"灵活性 vs 简洁性"的根本权衡。

## 5.3 FlowVisor

### 5.3.1 FlowVisor 概要

FlowVisor 是**最早的、也是最具影响力的 SDN 网络虚拟化平台**，2009 年始于斯坦福大学，用 Java 编写。

它的核心定位：**"一个特殊的 OpenFlow 控制器"**——对上层控制器而言它看起来像交换机，对下层交换机而言它看起来像控制器。

```
传统 OpenFlow 架构:
Controller ←———→ Switch

引入 FlowVisor 后:
Controller A ←→ FlowVisor ←→ Switch 1
Controller B ←→ FlowVisor ←→ Switch 2
Controller C ←→ FlowVisor ←→ Switch 3
                    │
                    └→ Switch 4, 5, ...
```

FlowVisor 将物理网络分成多个逻辑网络（称为**切片 slice**），每个切片由一个上层控制器负责管理。

### 5.3.2 FlowVisor 和 OpenFlow 控制器之间的 OpenFlow 通道

FlowVisor 与控制器、交换机之间都建立标准的 OpenFlow 通道，且**对两端完全透明**：

```
┌──────────────────────┐
                    │     FlowVisor        │
                    │  ┌────────────────┐  │
                    │  │ FVClassifier   │  │ ← 与交换机建立通道
                    │  ├────────────────┤  │
                    │  │ FVSlicer       │  │ ← 与控制器建立通道
                    │  ├────────────────┤  │
                    │  │ FlowSpace DB   │  │ ← 切片策略存储
                    │  └────────────────┘  │
                    └──────────────────────┘
                         ↑ 透明代理
         Controller A ───┘ │ └─── Switch 1
         Controller B ─────┘ └─── Switch 2
         Controller C ───────┘ └─── Switch 3
```

**消息处理流程**（当控制器发送命令给交换机时）：

```
1. 控制器 A 发送 Flow-Mod 给 FlowVisor
2. FlowVisor 的 FVSlicer 拦截消息
3. 分片器根据 FlowSpace 规则验证: 这条命令是否属于切片 A 的流空间?
4. 若符合: 修改命令（如重写匹配域），使其只对切片 A 的流生效
5. FVClassifier 将修改后的命令转发给对应的物理交换机
6. 交换机执行命令，但只影响切片 A 的流量
```

**关键设计原则**：

- **(a) 透明性**：控制器和交换机都感知不到 FlowVisor 的存在
- **(b) 隔离性**：各虚网之间流量必须完全隔离，即使广播也如此
- **(c) 可扩展性**：切片策略必须灵活、模块化、可扩展

### 5.3.3 FlowVisor 的串联

FlowVisor 支持**层次化串联**——一个 FlowVisor 实例可以虚拟化另一个 FlowVisor 实例创建的虚拟网络：

```
┌──────────────────────────────────────────────────┐
│  Controller A   Controller B   Controller C       │
└───────────────┬───────────────┬───────────────┘
                │               │
                ▼               ▼
            FlowVisor 1     FlowVisor 1
                │               │
                │ 递归分片       │
                ▼               ▼
            FlowVisor 2     FlowVisor 3
                │               │
                ▼               ▼
        ┌──────────────────────────────┐
        │  Switch 1  Switch 2  Switch 3  │
        │  Switch 4                     │
        └──────────────────────────────┘
```

这种层次化结构允许：

- **FlowVisor 2**​ 并行虚拟化多个物理交换机
- **FlowVisor 1**​ 在 FlowVisor 2/3 创建的虚拟网络上再次分片
- 每一层都可以有独立的租户控制器

> 💡 **洞见**：FlowVisor 串联的本质是"虚拟化的嵌套"——就像虚拟机里再跑 Hypervisor 创建嵌套虚拟机。但这种嵌套是有代价的：每层都会增加 OpenFlow 消息的处理延迟，且流空间会被多层切片进一步细分。

### 5.3.4 FlowVisor 和虚拟网络

FlowVisor 创建的每个虚拟网络（切片）具有以下特征：

- **独立的控制器**：每个切片由租户自己的控制器管理
- **独立的流空间**：基于包头 12 元组的通配符匹配
- **独立的资源配额**：带宽、CPU、流表项数量
- **逻辑上独立的拓扑**：切片看到的交换机和链路，是物理拓扑的子集

**工业部署实例**：GENI 试验床使用 FlowVisor 让不同研究者共享同一套物理 OpenFlow 网络，每人用自己的控制器控制自己的切片。

**北邮 SDN 校园网创新环境**的实践：通过 FlowVisor 切片 + VLAN + OVS QoS 实现虚网隔离，并演示了"用户在不同虚网间动态切换"的透明加速实验。

### 5.3.5 设置 FlowVisor 时的注意事项

这是工业部署中最关键的认知——**FlowVisor 有其架构限制**：

> ⚠️ **限制 1：流空间无法被完全利用**
> 
> FlowVisor 需要利用一部分分组头字段空间来区分不同的网络切片，因此无法利用全部的流空间地址。

> ⚠️ **限制 2：切片流空间不允许重叠**
> 
> 不同切片的流空间必须互不重叠。这意味着：
> 
> - 切片 A 占用了 `src_ip=10.0.0.0/8`，切片 B 就不能再用这个地址空间
> - 这导致"地址空间不能按需分配"——大规模多租户场景下会成为瓶颈

> ⚠️ **限制 3：不支持 vSDN 拓扑自定义**
> 
> FlowVisor 只能给用户提供物理拓扑的子集，**不支持自定义虚拟拓扑**。这意味着租户不能"虚构"一个物理网络中存在拓扑。

> ⚠️ **限制 4：逻辑隔离而非强隔离**
> 
> FlowVisor 目前只能在逻辑上隔离不同虚网的流量，**不能处理多个虚网在共享的物理设备上转发决策不同而引起的冲突**。因此工业部署通常需要：
> 
> - 为每个虚拟网络划分 VLAN
> - 借助 OVS 的 QoS 功能将不同虚网上的流量隔离

> ⚠️ **限制 5：性能开销**
> 
> FlowVisor 作为 OpenFlow 消息的拦截/修改/转发代理，会增加网络设备的负担。每一层 FlowVisor 都会增加控制通道的延迟。

**FlowVisor vs OpenVirteX 的演进**：

```
FlowVisor 的局限催生了 OVX (OpenVirteX):
- FlowVisor: 基于流空间 (FlowSpace) 划分 → 灵活但复杂，地址空间不重叠
- OVX:       基于租户 ID 划分 → 给每个切片分配独立租户 ID，
             虽欠缺灵活性，但更具实际意义
```

```
第5章的本质:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
"网络虚拟化 = 控制面的 Hypervisor"

驱动力:
  服务器虚拟化 (VM 动态迁移)
       ↓
  网络必须跟上计算的节奏
       ↓
  传统 VLAN 不够用 (4094 上限 + 无法控制转发面)
       ↓
  SDN 控制面集中化 → 天然适合做虚拟化
       ↓
  OpenFlow 作为抽象接口
       ↓
  FlowVisor 作为"网络 Hypervisor"
       ↓
  多租户、多控制器、多切片共存

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
虚拟化方法的演进:
  VLAN ID     → 弱虚拟化 (仅 L2 隔离)
  物理/逻辑端口 → 中虚拟化 (资源独占)
  FlowVisor   → 强虚拟化 (控制面完全切片)
  OVX         → 实用虚拟化 (租户 ID 嵌入)

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
FlowVisor 的架构位置:
  类比 Hypervisor 位于 x86 硬件和 Guest OS 之间
  FlowVisor 位于 OpenFlow 交换机和控制器之间
  
  五个资源切片维度:
  ├── 带宽隔离 (QoS 队列)
  ├── 拓扑发现 (独立拓扑视图)
  ├── 流量工程 (独立路径计算)
  ├── 设备 CPU (限制慢路径上送)
  └── 转发表 (追踪流表项归属)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

**六个工程层面的关键认知**：

**1. VLAN 是"乞丐版"虚拟化**

VLAN 解决了 L2 隔离，但**不能控制转发面**——租户无法独立定义路由逻辑。这正是 FlowVisor 等 SDN 虚拟化平台出现的根本原因。

**2. FlowVisor 的"透明代理"是架构杰作**

它对控制器和交换机都透明，这意味着：

- 现有 OpenFlow 控制器无需修改即可运行在 FlowVisor 之上
- 现有 OpenFlow 交换机无需修改即可被 FlowVisor 管理
- 虚拟化层与控制器、交换机独立演进

**3. 流空间是 FlowVisor 的核心抽象**

把 256-bit 包头看作高维空间，切片是这个空间的子集。这个抽象的优雅之处在于：**它可以表达任意粒度的虚拟化**——从"整个 VLAN"到"某个特定 TCP 端口的 HTTP 流量"。

**4. FlowVisor 的局限也是它的宿命**

流空间不重叠、不支持自定义拓扑、逻辑隔离而非强隔离——这些不是 Bug，而是"用 OpenFlow 1.0 的 12 元组做虚拟化"的必然结果。要突破这些限制，要么升级到 OpenFlow 1.3+ 的多级流表，要么换用 OVX 等新一代虚拟化平台。

**5. 工业部署必须"FlowVisor + VLAN + QoS"组合**

单一 FlowVisor 不足以提供生产级的隔离性。北邮 SDN 校园网的实践是典型范例：FlowVisor 做控制面切片 + VLAN 做 L2 隔离 + OVS QoS 做带宽保障。

**6. 虚拟化平台的演进方向**

FlowVisor → OVX → 现代云网络（如 AWS VPC、Azure vNet）：

- FlowVisor：基于流空间，灵活但复杂
- OVX：基于租户 ID，实用但欠灵活
- 现代云网络：完全软件定义，租户可自定义任意虚拟拓扑

> 💡 **批判性思考**：FlowVisor 是 SDN 虚拟化史上的里程碑，但它本质上是**"用 OpenFlow 1.0 的 12 元组硬凑出来的虚拟化"**。它的流空间不重叠限制、不支持自定义拓扑等缺陷，根源在于 OpenFlow 1.0 的表达力不足。这也是为什么 OpenFlow 1.3 引入多级流表、组表、计量表后，虚拟化平台可以更优雅地实现——例如用 Table 0 做租户分类，Table 1+ 做租户内部转发，从而在单台交换机上实现真正的多租户隔离而无需 FlowVisor 拦截。

**但 FlowVisor 的思想遗产不可磨灭**：它证明了"**控制面虚拟化**"的可行性——把控制器与交换机之间的 OpenFlow 通道拦截、改写、多路复用，从而在一套物理网络上跑多个逻辑网络。今天你在 AWS VPC、Google Andromeda、Azure vNet 中看到的网络虚拟化架构，骨子里都是 FlowVisor 思想的工业级实现。

**给工程师的实践建议**：

1. **想理解网络虚拟化，先动手装一次 FlowVisor**
    
    ```
    # 典型架构: Floodlight/Antony 控制器 × N + FlowVisor + OVS
    # 体验"一个控制器只看到自己的切片"的奇妙感觉
    ```
    
2. **用 Mininet + FlowVisor 做多控制器实验**
    - 切片 1: 运行 Spanning Tree 控制器
    - 切片 2: 运行 Shortest Path 控制器
    - 观察两个控制器如何"和平共处"在同一台 OVS 上
3. **理解"流空间"这个抽象**
    - 它是网络虚拟化的"x86 指令集"
    - 掌握它，你就掌握了 SDN 虚拟化的第一性原理
4. **关注现代虚拟化平台的演进**
    - OVX: 租户 ID 嵌入方式
    - OpenDaylight VTN: 基于 YANG 模型的虚拟化
    - 云厂商 VPC: 完全软件定义的虚拟化
