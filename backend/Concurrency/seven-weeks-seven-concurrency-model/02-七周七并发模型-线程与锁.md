
# 第2章 线程与锁：一切并发模型的"坐标原点"

> 💡 这一章表面讲的是 Java 的 `synchronized`、`ReentrantLock`、`volatile`、线程池。但作者真正的用意是：**让你亲手踩一遍线程与锁的坑，从而理解为什么后续六章要发明那么多新模型**。线程与锁是"对底层硬件运行过程的形式化"——这既是它的最大优点（简单、直接、效率高），也是最大缺点（把硬件级别的所有复杂性直接暴露给程序员）。

---

## 2.1 简单粗暴：线程与锁的本质定位

作者开宗明义：线程与锁模型有很多众所周知的不足，但仍是其他模型的技术基础，也是很多并发软件的首选。

🎯 **为什么"形式化硬件"既是优点又是缺点**

线程与锁之所以"简单粗暴"，是因为它几乎是对 CPU 执行过程的一比一映射：

- CPU 有多个核心 → 多个线程
- 核心间共享内存 → 线程间共享堆
- 核心访问内存需要总线仲裁 → 锁（mutex）
    
这种"贴近硬件"的特性带来两个后果：

1. **优点的根源**：几乎所有编程语言都提供支持，且不限制使用方式，如果正确使用，效率极高，能解决从小到大不同粒度的问题
2. **缺点的根源**：硬件层面的所有"反直觉"特性——缓存不可见、指令重排、乱序执行——**全部原封不动地透传给了程序员**
    
> ⚠️ 关键判断：线程与锁模型仅支持共享内存模型，**这是它最大的天花板**——它无法应用于分布式内存模型。后面 Actor 模型之所以重要，就是因为它打破了这个天花板。

## 2.2 Day 1 — 互斥与内存模型：三大危害的底层根源

这是本章最核心的一天。作者指出线程与锁有三个主要危害：**竞态条件、死锁、内存可见性**。我们要理解这三个危害不是孤立的 bug，而是**共享可变状态 + 硬件优化**这两个底层事实的必然产物。

### 🔍 危害一：竞态条件（Race Condition）

**本质**：计算的正确性依赖于多个线程操作的时序。

最经典的例子 `count++`：

```
读取 count → 加 1 → 写回 count
```

这是**三个独立的 CPU 指令**。两个线程同时执行时，可能都读到 100，都写到 101，一次递增就丢失了。

**底层根源**：

- **原子性问题**：`count++` 在源码层面看起来是一条语句，但在 CPU 层面是读-改-写三步
- **可见性问题**：线程 A 的写入可能还停留在自己的缓存/寄存器中，线程 B 读到的仍是旧值
    
### 🔍 危害二：内存可见性（Visibility）

**本质**：一个线程修改了变量，另一个线程可能永远看不到。

**底层根源**（这是最重要的洞见）：

|优化层级|具体行为|后果|
|---|---|---|
|编译器静态优化|打乱代码执行顺序|写操作可能被延迟|
|JVM 动态优化|JIT 把变量缓存到寄存器|其他线程读不到新值|
|硬件优化|CPU 乱序执行 + 每个核心独立的 L1/L2 缓存|写操作停在 Store Buffer，未刷入主存|

作者在这里引出了 **Java 内存模型（JMM）**​ 的 **happens-before**​ 关系：

- 解锁操作 happens-before 后续对同一锁的加锁
- 对 volatile 变量的写 happens-before 后续对该变量的读
    
**没有 happens-before 关系，就没有可见性保证**。这就是为什么即便 `count++` 用 volatile 修饰也**不够**——volatile 只解决可见性，不解决原子性，必须配合锁。

> 💡 **洞见**：竞态条件和内存可见性看似两个问题，本质是一个问题的两面——**原子性 + 可见性**。synchronized 同时解决两者，volatile 只解决后者。

### 🔍 危害三：死锁（Deadlock）

**本质**：四个必要条件同时满足时必然发生：

1. **互斥**：锁一次只能被一个线程持有
2. **占有并等待**：线程拿着锁 A 去申请锁 B
3. **不可剥夺**：线程 A 持有的锁，其他线程不能强行抢走
4. **循环等待**：A 等 B 的锁，B 等 A 的锁，形成闭环
    
**经典案例**：哲学家就餐问题——五个哲学家同时拿起左手的筷子，都在等右手的筷子，系统死锁。

### 🛡️ 作者给出的五条安全准则

这是 Day 1 最实用的产出：

1. **对共享变量的所有访问都需要同步化**
2. **读线程和写线程都需要同步化**（很多人以为只读不用锁，大错特错）
3. **按照约定的全局顺序来获得多把锁**（破坏死锁的"循环等待"条件）
4. **当持有锁时避免调用外星方法**（你不知道外部方法会不会尝试获取其他锁）
5. **持有锁的时间尽可能短**（减少竞争窗口）

## 2.3 Day 2 — 超越内置锁：内置锁的三大局限

作者指出 `synchronized` 作为内置锁有三个硬伤：

|局限|后果|解决方案|
|---|---|---|
|等待内置锁的线程无法被中断|一旦死锁，线程永远卡住|`ReentrantLock.lockInterruptibly()`|
|获取内置锁无法设置超时|无限等待|`ReentrantLock.tryLock(timeout)`|
|必须在 synchronized 块中获取/释放|灵活性差|`ReentrantLock` 显式 lock/unlock|

**交替锁（hand-over-hand locking）**​ 是这一节的精华思想：在链表插入节点时，不必锁住整个链表，而是**只锁当前节点和下一个节点**，允许不涉及被锁部分的其他线程继续自由访问链表。这是"锁粒度"思想的经典体现。

**条件变量（Condition）**​ 解决的是"等待某个条件成立"的问题，比 `Object.wait/notify` 更灵活——一个 `ReentrantLock` 可以创建多个 Condition。

> ⚠️ **活锁警示**：`tryLock` 超时机制如果设计不当，可能导致所有线程同时超时、同时重试、再次同时超时——这就是**活锁**，线程没有阻塞但系统毫无进展。

**原子变量（`java.util.concurrent.atomic`）**​ 是无锁非阻塞的利器，底层依赖 CAS（Compare-And-Swap）CPU 指令。这是从"锁思维"迈向"无锁思维"的第一步，也为第 4 章 Clojure 的原子变量埋下伏笔。

## 2.4 Day 3 — 站在巨人肩上：高层并发工具

这一天的核心思想是：**产品代码不应该直接使用 `Thread` 类等底层服务**。

作者给出了几条工程实践：

- **线程池代替裸线程**：CPU 密集型任务，线程池大小接近核数；IO 密集型可以更大。最佳方式是在真实环境压测。
- **`CopyOnWriteArrayList`**：监听器场景的神器——读不加锁，写时复制，读操作完全无竞争
- **`ArrayBlockingQueue`**：生产者-消费者模式的高效实现，内部已处理好所有同步细节
- **`ConcurrentHashMap`**：分段锁技术，提供更好的并发访问
    
> 📌 **这一天的隐藏信息**：所有这些"高层工具"，本质上都是在**替你管理锁的复杂性**。它们的存在本身就证明了一件事——**手写锁是反模式（anti-pattern）**。

## 🔗 全局观：线程与锁在七大模型中的坐标

如果我们把线程与锁的"三大危害"作为靶子，会发现后续每一章都在用不同策略打这个靶：

```
线程与锁的三大危害
├── 竞态条件 + 内存可见性（根源：共享可变状态）
│   ├── 第3章 函数式编程：消灭可变状态 → 问题消失
│   ├── 第4章 Clojure：分离标识与状态 → 用持久化数据结构避开
│   └── 第5章 Actor / 第6章 CSP：状态私有化 + 消息传递 → 不存在共享
│
├── 死锁（根源：多锁循环等待）
│   ├── 第5章 Actor：每个 Actor 一次处理一条消息，无锁
│   └── 第6章 CSP：channel 作为一等公民，避免多锁
│
└── 天花板：仅支持共享内存
    ├── 第5章 Actor：跨到分布式内存
    └── 第8章 Lambda 架构：彻底走向分布式
```

**这条演进链揭示的底层规律**：

> 💡 所有后续模型，都是在回答同一个问题——**"能不能不让程序员直接接触共享可变状态？"**
> 
> - 函数式：**不让它有**（消灭可变状态）
> - Clojure：**让它是不可变的**（持久化数据结构）
> - Actor/CSP：**让它不被共享**（状态封装在实体内部）
> - 数据并行：**让它变成数据阵列**（SIMD 天然无共享）
> - Lambda：**让它分散到集群**（MapReduce 思维）
>

## 💡 实际应用的几条铁律

基于本章内容，可以提炼出工程实践中**永远不会过时**的原则：

1. **最小化共享**：能用局部变量就不要用共享变量，能不共享就不共享——不共享就没有并发问题
2. **优先不可变**：String、Integer、final 字段、不可变对象天然线程安全
3. **优先高层工具**：ConcurrentHashMap、AtomicInteger、线程池——不要手写锁
4. **必须共享时，按序加锁**：所有线程按固定顺序获取多把锁，破坏循环等待
5. **锁内不做慢操作**：网络/IO/sleep 移到锁外，减少持锁时间
6. **volatile 只解决可见性**：`count++` 这种复合操作必须用锁或原子变量

## 📝 第二章读书笔记要点

如果只能记住三句话：

1. **线程与锁是对硬件的形式化**——所以高效，但也把缓存、重排、乱序执行的所有复杂性直接交给程序员
2. **三大危害（竞态、死锁、可见性）的根源是"共享可变状态 + 硬件优化"**——理解了这个根源，才能理解为什么后续模型要"消灭/隔离/分散"状态
3. **手写锁是 anti-pattern**——产品代码应该用线程池、并发容器、原子变量这些"站在巨人肩上"的工具
    
### 衔接下一章的思考锚点

第 3 章"函数式编程"会给出一个激进的答案：**既然共享可变状态是万恶之源，那就消灭它**。函数式编程通过消除可变状态，让竞态条件和内存可见性问题从根本层面消失——但代价是什么？当现实世界真的需要"状态变化"（比如银行账户余额）时，函数式如何应对？这就是第 4 章 Clojure "分离标识与状态"要解决的矛盾。
