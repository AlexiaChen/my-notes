
# 第3章 函数式编程：用"消灭可变状态"一劳永逸地解决并发

> 💡 如果说第2章线程与锁是"把硬件的复杂性原封不动交给程序员"，那么第3章给出的是一个激进但优雅的回答：**既然共享可变状态是万恶之源，那就消灭它**。函数式编程不是某种语言特性，而是一种世界观——把计算看作数学表达式的求值，而非"改变状态的一系列语句"。当状态不可变，线程与锁的三大危害（竞态、死锁、可见性）在第3章的核心计算中就**从源头消失**了。

---

## 3.1 若不爽，就另辟蹊径：函数式编程的出发点

作者用了一句很有态度的开场：**"若不爽，就另辟蹊径"**。这是对第2章的直白回应——既然线程与锁把竞态、死锁、可见性这三大危害硬塞给程序员，那我们换条路走 。

本书选用 **Clojure**​ 作为函数式编程的载体（Clojure 运行在 JVM 上，Lisp 家族，语法极简）。

🎯 **底层洞见：函数式编程不是"禁用了变量"，而是重新定义了"变化"**

命令式编程的思维方式：

```
accumulator = 0
for n in numbers:
    accumulator += n   // accumulator 是可变的
return accumulator
```

函数式编程的思维方式（Clojure 三种写法层层递进）：

```
;; 方式一：递归
(defn recursive-sum [numbers]
  (if (empty? numbers)
    0
    (+ (first numbers) (recursive-sum (rest numbers)))))

;; 方式二：reduce
(defn reduce-sum [numbers]
  (reduce (fn [acc x] (+ acc x)) 0 numbers))

;; 方式三：极致简洁
(defn sum [numbers]
  (reduce + numbers))
```

**关键差异**：方式三中的 `+` 是一个**函数**，`(reduce + numbers)` 表示"用 + 把 numbers 折叠起来"。这里没有"累加器变量"被反复修改，每一次 `+` 都产生一个新的值 。

> 💡 **这就是函数式编程的灵魂**：所谓"状态变化"，不再是修改旧值，而是**产生新值**。旧值依然存在、未被破坏。这种思维方式的转换，是整个第3章乃至后续 Clojure 章节的基石。

## 3.2 Day 1 — 抛弃可变状态：隐藏与逃逸的两类风险

这一天的核心是：**命令式代码中"可变状态"比你想的更隐蔽**，而函数式通过消除可变状态，从根本上规避了这些风险 。

### 🔍 风险一：隐藏的可变状态

作者举了 Java 中经典的 `SimpleDateFormat` 例子——它**看起来**是一个无状态工具类，但内部其实持有可变状态。多线程共用同一个 `SimpleDateFormat` 实例时，会抛出诡异的异常 。

> ⚠️ 这就是为什么"只读对象就不需要同步"是一个致命误解——你以为在读，其实在改；你以为无状态，其实内部在偷偷记录。

### 🔍 风险二：逃逸的可变状态

两个方法都加了 `synchronized`，一个返回迭代器，另一个往 List 里 add——单独看都没问题，但迭代器**逃逸**到了同步块之外，此时另一个线程调用 add，就会触发 `ConcurrentModificationException` 。

**"逃逸"的本质**：锁的保护范围有限，但可变状态的可见范围超出了锁的保护范围。

### 🛡️ 函数式的根本性解法

函数式编程没有可变状态，**所以不会遇到由共享可变状态带来的种种问题**。具体来说：

|线程与锁的危害|函数式编程如何应对|
|---|---|
|竞态条件|数据不可变，"读-改-写"三步中的"改"变成了"产生新值"，不存在中间态|
|内存可见性|不可变对象一旦发布，永远是一致的，不需要 happens-before 来保障|
|死锁|不需要锁，自然没有多锁循环等待|

🎯 **深层洞见**：

> 📌 使用线程和锁的模型中，大多数潜在的竞态条件**并不是来源于问题本身的不确定性，而是隐藏于解决方案的细节中**​ 。

这句话太重要了。举个例子：`0 加到 10000`、`统计某个页面的词频`——这些问题**本身是完全确定的**，但用线程与锁实现时，竞态条件就冒出来了。也就是说，**不确定性是"解决方案"引入的，不是"问题"本身具有的**。

函数式编程之所以优雅，是因为它**不让解决方案引入额外的不确定性**。纯函数具有**引用透明性**（referential transparency）——在任何调用函数的地方，都可以用函数运行的结果来替换函数的调用，而不会对程序产生副作用 。

举例：`(+ (+ 1 2) (+ 3 4))`，先计算 `1+2` 还是先计算 `3+4`，对结果没有任何影响。这种"求值顺序无关性"正是并行化的天然土壤。

## 3.3 Day 2 — 函数式并行：让 fold 自动利用多核

这一天作者展示了函数式编程最迷人的能力：**把串行代码改成并行，往往只需要换一个函数**。

### 🚀 从串行到并行的"一行切换"

```
;; 串行版本
(defn sum [numbers]
  (reduce + numbers))

;; 并行版本
(require '[clojure.core.reducers :as r])
(defn parallel-sum [numbers]
  (r/fold + numbers))
```

`r/fold` 的背后是 **Fork/Join 分而治之**的思想 ：把集合递归地一分为二，分别并行计算，最后合并结果。

### 🔍 为什么 fold 能安全并行？

关键原因在于 **reducer 的惰性**：

- 一个化简器（reducer）并不代表函数返回的结果，而是代表**如何产生结果的描述**
- 在被传给 `reduce` 或 `fold` 之前，化简器并不会进行求值
- 这样做有两个好处：
    1. 嵌套函数返回化简器比返回懒惰序列效率更高（不用构造中间状态的序列）
    2. 对整个嵌套链的集合操作，可以使用 `fold` 进行并行化
        
**更深层的洞见**：并行化的安全性来自不可变性。当 `fold` 把数组分成两半给两个线程计算时，每个线程处理的数据片段**不会被另一个线程修改**——因为没有"修改"这回事，只有"产生新值"。合并阶段也只是把两个结果用 `+` 组合，而 `+` 是纯函数。

### 📊 性能真相

|维度|函数式并行|线程与锁|
|---|---|---|
|编程复杂度|极低（换函数即可）|极高（手动管理锁）|
|正确性保障|由不可变性保证|由程序员小心维护|
|适用场景|数据可分解、操作可结合|任意场景|
|性能上限|受限于不可变数据结构开销|理论上更高，但易出错|

> 💡 **务实的判断**：函数式并行的性能**未必**比精心调优的线程锁更高（不可变数据结构有复制成本），但它的**开发效率和正确性保障**是线程锁远远不及的。这就是为什么 Spark、Hadoop 等大数据框架的核心理念都是函数式——`map`、`filter`、`reduce` 这些操作天然支持并行和分布式计算 。

### 🛠️ 不可变性的性能之谜：结构共享

有人会问：每次"变化"都产生新值，岂不是疯狂拷贝内存？

这就是**持久化数据结构（Persistent Data Structures）**和**结构共享（Structural Sharing）**要解决的问题 ：

- 新版本与旧版本**共享大部分结构**，而不是在每次更改时完整复制
- 例如 Clojure 的向量（Vector），修改一个元素时，只有从根到该元素的路径会被复制，其他分支完全共享
- 这使得不可变操作的复杂度从 O(n) 降到接近 O(log n)
    
**这也是 React/Redux 前端状态管理、Docker 快照、Copy-on-Write 文件系统的底层原理**​ ——不可变不是"浪费"，而是用结构共享让"保留历史状态"变得廉价。

## 3.4 Day 3 — 函数式并发：future 与 promise 的数据流思维

这一天从"并行"（让计算更快）切换到"并发"（处理多件独立的事），展示了函数式编程如何处理**时间维度**上的并发。

### 🔍 引用透明性的时间维度延伸

纯函数不仅空间上可并行（Day 2），时间上也可灵活调度：**利用这一特性可以让代码在其依赖的数据准备好时才运行，这也被称为数据流式编程**​ 。

Clojure 提供两种机制：

- **future**：把一个计算丢到后台线程执行，返回一个句柄，需要时再来取结果
- **promise**：创建一个占位符，未来某个时刻被某个线程"兑现"（deliver），其他等待这个 promise 的代码在兑现后才继续执行
    
### 🎯 底层洞见：从"控制流"到"数据流"

传统并发是**控制流驱动**的——你显式地创建线程、加锁、等待。函数式并发是**数据流驱动**的——你描述计算之间的依赖关系，运行时在依赖满足时自动执行。

举个直觉例子：

```
计算 A 需要数据 X 和 Y
X 由线程 1 生产，Y 由线程 2 生产
A 不需要关心 X 和 Y 谁先就绪，它只在两者都就绪时执行
```

这种"数据就绪驱动执行"的模型，比显式锁更自然地表达了并发问题的本质——**并发不是"多线程"，而是"多个计算之间的依赖关系"**。

> 💡 这个思想直接预示了后续两章：Actor 模型（第5章）和 CSP（第6章）都是在用"消息/通道"来表达这种依赖关系，只是换了一种语法形式。

### ⚖️ 函数式编程的边界

作者没有回避函数式编程的局限：

- **Clojure 不纯粹**：Clojure 是一门不纯粹的函数式编程语言（例如不支持尾调用消除），现实世界总有 IO、状态、副作用
- **性能代价**：为了保证没有副作用，所有的值都必须是不可变的，这会带来性能开销
- **副作用不可避免**：与外部世界交互（IO、UI、网络）必然有副作用，强行纯粹化会导致代码冗长
    
**务实的工程方案**——"函数核心，命令式外壳"：

- 将所有带有副作用的操作推到程序的边缘
- 核心业务逻辑由纯函数构成
- 这种架构下，纯函数的可并行性、可测试性、可推理性得到充分发挥

## 🔗 全局观：函数式编程在七大模型中的坐标

把第3章放回全书的谱系中看：

```
第2章 线程与锁：共享可变状态 → 三大危害
   │
   ▼ 激进解法：消灭可变状态
第3章 函数式编程：纯函数 + 不可变数据
   │  ├── 优点：竞态/死锁/可见性从源头消失，并行化几乎免费
   │  └── 缺点：现实世界需要状态变化，强行纯粹化不现实
   │
   ▼ 务实折中：承认需要可变状态，但用新机制管理它
第4章 Clojure：原子变量 + 代理 + 软件事务内存
   │
   ▼ 另一方向：不消灭状态，而是隔离状态
第5章 Actor：状态私有化 + 消息传递
第6章 CSP：通道作为一等公民
```

**这条演进链揭示的底层规律**：

> 📌 函数式编程给出了"理想答案"——彻底消灭可变状态。但它过于理想，Clojure 之道（第4章）就是在函数式的纯粹和命令式的现实之间找平衡。**整个第4章到第6章，都是在回答"既然不能完全消灭状态，那怎么管理状态才安全？"**

具体策略分化：

- **Clojure**：保留可变状态，但用原子变量、代理、STM 让状态的变更受控
- **Actor**：状态封装在 Actor 内部，外部只能通过消息间接影响
- **CSP**：状态通过通道传递，发送方和接收方不直接共享

## 💡 实际应用：函数式思维的六个落地场景

1. **大数据处理**：Spark、Hadoop 的 map/filter/reduce 天然并行——这是函数式编程最成功的应用领域
2. **前端状态管理**：React/Redux 用不可变状态让 UI 变化可预测、可回溯
3. **微服务**：无状态服务实例可被任意替换而不影响系统行为，与函数式完美契合
4. **高并发系统**：没有共享可变状态，天然规避锁、死锁、竞争条件
5. **协作工具/联机游戏**：中心状态的并发修改，用不可变快照安全保存
6. **日常代码**：即便在 Java/Python/JS 中，也可以"函数核心，命令式外壳"——把业务逻辑写成纯函数
    
### 工程实践的几条铁律

- **优先纯函数**：给定相同输入永远返回相同输出，无副作用
- **优先不可变数据**：用 `final`、不可变集合、值对象
- **隔离副作用**：IO、数据库、网络调用推到系统边缘
- **用高阶函数代替循环**：`map`、`filter`、`reduce`、`fold` 比 for 循环更容易并行化
- **警惕"隐藏的可变状态"**：`SimpleDateFormat`、迭代器逃逸等都是经典陷阱

## 📝 第三章读书笔记要点

如果只能记住三句话：

1. **线程与锁的三大危害，根源是"共享可变状态"；函数式编程通过消灭可变状态，让这些危害从源头消失**——这不是修 bug，而是让 bug 无从产生
2. **函数式并行的本质是利用引用透明性**——`(+ (+ 1 2) (+ 3 4))` 先算哪边都一样，这种"求值顺序无关性"让 `fold` 可以安全地分而治之地并行
3. **函数式编程不是银弹**——Clojure 不纯粹、性能有开销、副作用不可避免。务实的做法是"函数核心，命令式外壳"：纯函数构成业务核心，副作用推到边缘
    
### 衔接下一章的思考锚点

第3章证明了"消灭可变状态"的美好，但留下了一个尖锐的矛盾：**现实世界真的有状态变化**——银行账户余额、游戏角色位置、网页点击次数——这些都是真真切切的"可变状态"。如果强行用函数式表达，要么性能垮掉，要么代码扭曲。

第4章"Clojure 之道——分离标识与状态"给出的答案是：**不要把"状态"和"标识"捆绑在一起**。一个银行账户的"标识"（这是账户 #12345）是不变的，但它的"状态"（余额是 100 还是 200）是可变的。把这两者分离，用持久化数据结构表达状态变迁，用原子变量/代理/STM 管理变更——这就是 Clojure 在纯粹函数式和现实命令式之间的精妙折中。
