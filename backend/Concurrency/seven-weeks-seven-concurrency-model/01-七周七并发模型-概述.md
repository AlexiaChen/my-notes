
# 第1章 概述：并发编程的"地图与判据"

> 💡 这一章不直接教你任何一种并发模型，而是给你两张东西：一张**硬件与现实世界的地图**（为什么我们需要并发），一套**评判模型的判据**（后面七章每个模型都按这套判据来打分）。读懂这一章，后面六章（除线程与锁外）本质上都是在回答同一个问题：**线程与锁哪里不够好，我们用什么新结构来补？**

---

## 1.1 并发还是并行：被混淆的两个维度

这是全书最容易被跳过、却最关键的概念基石。作者借 Rob Pike 的经典定义：

- **并发**是问题域的概念——同一时间**应对**（dealing with）多件事的能力
- **并行**是方法域的概念——同一时间**动手做**（doing）多件事的能力
    
更精确的表述是：并发程序含有多个逻辑上独立的执行块，它们可以并行执行，也可以串行执行；并行程序则是通过同时执行任务的多个部分来加速 。

🎯 **为什么这个区分是"底层不变"的**

传统"线程与锁"模型并不直接支持并行——你想用线程锁利用多核，唯一办法是先写一个并发程序，再把它扔到多核上跑 。这就导致一个长期被忽视的事实：

> ⚠️ **并发程序天然不确定**（结果随时序变化而变化）；**并行程序可以是确定的**（例如把数组翻倍，分两半给两个核算，结果是确定的）。

这一句话其实是后面七种模型的"判分尺"：

- 线程与锁 → 写出来的是并发，不确定性随之而来（竞态、死锁、内存可见性）
- 函数式编程 → 消除可变状态，让并行程序重新变得确定
- 数据级并行 → 本来就是确定并行的典型场景
- Lambda 架构 → 批处理层是确定的并行，加速层处理不确定
    
**洞见**：很多人学并发，一上来就钻进 `synchronized` 和 `volatile`，却没意识到他们真正想要的是"并行"（让程序更快），而线程锁给的却是"并发"（处理多件事）——这两个目标的不匹配，正是后续所有新模型诞生的根本原因 。

## 1.2 并行架构：硬件层面的四个层级

作者提醒：**并行 ≠ 多核**。即便在单核时代，计算机也在靠并行变得越来越快。并行发生在四个层级 ：

|层级|机制|现实例子|
|---|---|---|
|**位级**​|加宽数据通路|32 位机一步完成 32 位数加法，8 位机要做 4 次|
|**指令级**​|流水线、乱序执行、推测执行|现代 CPU 看起来串行，内部早已高度并行|
|**数据级**​|SIMD，同一操作施加于大量数据|GPU 处理图像：给每个像素加亮度|
|**任务级**​|多处理器协同|共享内存 / 分布式内存多处理器|

🎯 **为什么任务级并行最重要**

前三个层级对程序员基本透明（编译器/硬件帮你做了）。**任务级并行才是软件工程师真正要设计的**，而它又分出两条路线 ：

- **共享内存模型**：所有处理器能访问任意内存地址，处理器间通过内存通信 → 编程简单，但超过一定处理器数量后内存成为瓶颈
- **分布式内存模型**：每个处理器有自己的本地内存，主要通过网络通信 → 难写，但能突破规模瓶颈、提供容错性
    
**这本书的隐藏主线就藏在这里**：后面七种模型，本质上是在共享内存和分布式内存这两端之间寻找不同的平衡点。

- 线程与锁、函数式、Clojure、Actor、CSP、数据并行 → 主要解决**共享内存**下的任务级并行
- Actor（分布式形态）、Lambda 架构 → 走向**分布式内存**
    
> 💡 理解了这张硬件地图，你会明白：为什么 GPU 编程（数据并行）和 MapReduce（Lambda）看起来和"并发"关系不大，却被作者收进这本书——因为它们都是任务级并行的具体形态，只是处在并行架构的不同层级。

## 1.3 并发：不只是多核

这一节把视角从硬件抬到现实世界，给出使用并发的**四个深层动机**​ ：

1. **并发的世界 → 并发的软件**：现实世界本质是并发的（多个用户、多个事件、多个传感器同时发生）。软件的结构如果与问题结构匹配，就会简单很多——不需要用一个复杂线程去处理多个任务，而是用多个简单线程分别处理不同任务 。
2. **分布式的世界 → 分布式的软件**：地理分布的必然选择。
3. **不可预测的世界 → 容错性强的软件**：并发代码的关键是**独立性 + 故障检测**——故障任务不影响其他任务，且能被检测到并交由专门处理故障的任务 。
4. **复杂的世界 → 简单的软件**：并发提供了一种分解复杂度的结构化手段。
    
🎯 **洞见**：多数教材把"多核"当作学并发的唯一理由，作者却在此埋下伏笔——**即使永远只有单核，我们依然需要并发**，因为并发是一种**​ structuring mechanism（结构化的机制）**，而不仅仅是优化的手段。这一点直接预示了 Actor 和 CSP 的存在价值：它们不是为了快，而是为了让并发系统的结构更清晰、容错更强。

## 1.4 七个模型：全书的路线图

作者列出并贯穿后续章节的七个模型 ：

1. **线程与锁**​ — 最传统的基础模型，是其他模型的技术基础，也是很多并发软件的首选，但有三害：竞态条件、死锁、内存可见性
2. **函数式编程**​ — 消除可变状态，从根本上线程安全，易于并行
3. **Clojure 之道——分离标识与状态**​ — 指令式与函数式的混搭，在两者之间微妙平衡
4. **Actor**​ — 适用性极广，共享内存和分布式内存皆可，容错性强
5. **通信顺序进程（CSP）**​ — 与 Actor 都基于消息传递，但 CSP 侧重**通道（channel）**，Actor 侧重**通道两端的实体**
6. **数据级并行**​ — 挖掘 GPU 中的超级计算机，适合大规模数值计算
7. **Lambda 架构**​ — 综合 MapReduce 和流式处理，处理 TB 级数据
    
🎯 **这七个模型不是并列的，而是有"谱系"的**

如果把它们按"解决线程与锁的什么问题"连起来看，会得到一条非常清晰的演进脉络：

```
线程与锁（共享可变状态 → 不确定性、死锁、可见性）
   │
   ├─► 函数式编程：干脆消灭可变状态
   │       │
   │       └─► Clojure：在可变与不可变之间取平衡（分离标识与状态）
   │
   ├─► Actor：不共享状态，改用消息传递 + 邮箱，获得容错与分布式能力
   │
   ├─► CSP：同样是消息传递，但把"通道"作为一等公民
   │
   ├─► 数据级并行：跳出"任务"思维，转向"数据"思维（GPU/SIMD）
   │
   └─► Lambda 架构：跳出单机，走向分布式批处理 + 流处理
```

**这条脉络揭示了一个底层不变的规律**：

> 📌 并发模型的演进，本质是**围绕"状态"做文章**——
> 
> - 要么消灭状态（函数式）
> - 要么隔离状态（Actor、CSP）
> - 要么分离状态的"身份"与"值"（Clojure）
> - 要么把状态外推到数据阵列（数据并行）
> - 要么把状态分散到集群（Lambda）
>     
线程与锁之所以"声名狼藉"，不是因为它错了，而是因为它**把状态的读写权完全摊开在多个执行流面前**，所有复杂性由此而生。后续六种模型，都是在用不同的抽象把这个复杂性重新封装起来。

## 📝 读书笔记：第一章的全局观

如果你只想从第一章带走三句话：

1. **并发是结构设计，并行是执行加速**。线程与锁只给你并发，不保证并行——这是所有痛苦的根源 。
2. **多核危机结束了"免费午餐"**：过去靠提升主频就能让代码变快，现在必须主动用软件挖掘并行 。而并行不止于多核，它从位级一路延伸到分布式内存的任务级 。
3. **七个模型构成一个谱系**，共同回答"如何在共享可变状态之外组织并发"。理解了这个谱系，你在后续每一章都应该问自己：这个模型**对状态的假设是什么？它牺牲了什么换来了什么？它适合共享内存还是分布式内存？**
    
### 后续章节的连接锚点

- **第 2 章 线程与锁**：作为基线，它的三害（竞态、死锁、可见性）就是后面所有模型试图解决的靶子
- **第 3 章 函数式编程**：用"无可变状态"彻底消灭三害中的竞态和可见性
- **第 4 章 Clojure**：承认现实需要可变状态，于是把"标识"和"状态"分开管理
- **第 5 章 Actor**​ 与 **第 6 章 CSP**：不消灭状态，而是让状态私有化，通过消息传递协作——Actor 和 CSP 的区别仅在"以实体为中心"还是"以通道为中心"
- **第 7 章 数据并行**：切换到数据视角，状态变成可并行变换的数据阵列
- **第 8 章 Lambda 架构**：切换到集群视角，状态分散到批处理层和加速层
    
> ⚠️ 写后续章节笔记时的建议：每一章都回到 1.1 和 1.4 的判据——这个模型是偏并发还是偏并行？它假设共享内存还是分布式内存？它如何处理"状态"？把这三个问题回答清楚，读书笔记就有骨架了。
