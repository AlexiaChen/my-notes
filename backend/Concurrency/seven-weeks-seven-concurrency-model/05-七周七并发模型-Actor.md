
# 第5章 Actor 模型：把"状态私有化"，用消息重构并发与分布式

> 💡 第4章 Clojure 之道用"分离标识与状态"在同进程内优雅地解决了共享可变状态的问题，但它有明确的天花板——**不支持分布式，也无法直接提供容错性**。《七周七并发模型》的作者用一句很妙的比喻开启本章："使用 actor 就像租车——我们如果需要，可以快速便捷地租到一辆；如果车辆发生故障，也不需要自己修理，直接打电话给租车公司更换另外一辆即可" 。Actor 模型是一种适用性非常好的通用并发编程模型，它既可用于共享内存架构，也可用于分布式内存架构，适合解决地理分布型的问题，同时还能提供很好的容错性 。本章用 Elixir（运行在 Erlang 虚拟机 BEAM 上）来介绍 Actor 模型 。

---

## 5.1 更加面向对象：Actor 对"对象"的真正还原

作者在这一节抛出一个反直觉的观点：**Actor 模型比传统的面向对象更"面向对象"**​ 。

🎯 **为什么这么说？看传统 OO 的"消息传递"是假的**

在 Java/C++ 这类 OO 语言中，我们常说"对象之间通过消息传递通信"——但实质上这只是**调用一个方法**。方法调用是：

- **同步的**：调用方阻塞，直到方法返回
- **共享的**：直接操作对象内部状态（通过 this 指针）
- **紧耦合的**：调用方必须持有被调用方的直接引用
    
而 Actor 之间的消息传递是**真实地在传递消息**​ ——消息异步发送、放入邮箱、接收方在自己节奏里处理。Actor 类似于面向对象编程中的对象——其封装了状态，并通过消息与其他 Actor 通信，但**两者同时运行，且消息传递是真实的**​ 。

**Actor 模型的三个核心公理**​ ：

1. **所有的计算都是在 Actor 中执行的**
2. **Actor 之间只能通过消息进行通信交流**
3. **为了响应消息，Actor 可以进行下列操作**：更改状态或行为、发消息给其他 Actor、创建有限数量的子 Actor
    
> 💡 **底层洞见**：Actor 模型实际上是"顺序进程（Sequential Processes）+ 函数式数据变换（Functions transforming data values）"的结合体 。它既保留了可变状态（每个 Actor 私有），又通过"不共享"规避了可变状态带来的问题——这是它与第4章 Clojure 之道的关键差异：
> 
> - **Clojure 之道**：保留可变状态，但通过 CAS/事务让变更受控
> - **Actor 模型**：保留可变状态，但**根本不共享**——每个 Actor 的状态只有自己能看到
>     
### Day 1 — 消息与邮箱：把并发复杂度压到边界

第一天的学习目标是 Actor 模型的基础——如何创建 Actor、发送消息和接收消息 。

#### 🔍 邮箱（Mailbox）是 Actor 模型的精髓

消息并非直接发送给 Actor，而是**异步地放入邮箱队列**​ ：

- **解耦**：Actors 相互独立运行，发送消息时不阻塞
- **顺序处理**：一个 Actor 与其他 Actor 并发运行，但对邮箱中的消息**按顺序串行处理**
- **并发边界收缩**："我们只需在发送消息时关注并发" ——处理消息的内部逻辑是串行的，无需考虑锁
    
**这正是 Actor 模型最优雅的地方**：把"共享可变状态导致的并发复杂性"压缩到了**消息边界**这一处。在 Actor 内部，你写的是普通的串行代码；跨 Actor 的并发，通过异步消息来表达。

#### 🎯 为什么邮箱队列是革命性的设计

|维度|线程与锁|Actor 模型|
|---|---|---|
|状态访问|多线程共享，需要锁保护|单线程私有，天然安全|
|线程通信|共享内存 + 锁|异步消息 + 邮箱|
|死锁风险|高（多锁循环等待）|低（但仍可能存在）|
|并发推理|需要考虑所有交错时序|只需考虑消息流|

每个 Actor 是"**单线程 + 消息队列**"的组合 ：每次只处理一个消息，处理完再取下一个；不同 Actor 可并发执行；同一 Actor 内部逻辑是串行的。Actor 之间只通过异步消息通信。

**数学模型**：`Actor = 函数 + 状态 + 信箱 + 调度器`，用数学表达式表示为 `Actor(a) = Behavior: Message × State → (NewState, NewMessages, NewActors)` 。这意味着每个 Actor 处理消息的过程可以视为一个纯函数，每次消息处理都是幂等的，无全局状态，可推理、可分布。

> 📌 **洞见**：Actor 模型的强大不在于"它消除了并发"，而在于"它把并发限制在消息传递这一处，让 Actor 内部回归串行编程的简单性"。这是它相比线程与锁最大的可推理性优势。

### Day 2 — 错误处理与韧性："任其崩溃"哲学

第二天学习 Actor 模型的容错性关键：失败检测和"任其崩溃"的哲学 。这是 Actor 模型（尤其是 Erlang/Elixir）最独特的贡献。

#### 🔍 传统容错 vs "任其崩溃"

传统编程中，我们写大量**防御性代码**：

```
if (input == null) return;
if (input.length() > MAX) throw new ValidationException(...);
try {
    process(input);
} catch (Exception e) {
    log.error("处理失败", e);
    // 各种兜底...
}
```

这些代码与业务逻辑混杂，让程序变得复杂难懂 。

**Erlang 的哲学截然不同——"任其崩溃"（Let It Crash）**​ ：

- 不做防御性逻辑
- 让 Actor 的管理者（监督者）去处理异常
- 因为 Actor 之间相互独立、不共享状态，一个 Actor 崩溃不太可能影响其他 Actor
- 没有防御性代码，业务逻辑更简洁
    
#### 🛡️ 监督树（Supervision Tree）与错误内核模式

"任其崩溃"不是放任自流，而是有一套精密的监督机制 ：

**监督者（Supervisor）**：系统进程，监控一个或多个工作进程，在它们失败时采取适当行动。

**错误内核模式（Error Kernel Pattern）**​ ：

- 软件的"错误内核"是"如果系统要正确运行，就必须正确的部分"
- 写得好的程序会让错误内核**尽可能小、尽可能简单**
- 这导致了**错误内核的层级结构**——风险操作被下推到较低级别的 Actor


```
System Supervisor（最高级，必须正确）
           │
           ├── Worker Pool Supervisor
           │      │
           │      ├── Worker 1（风险操作下推到这里）
           │      ├── Worker 2
           │      └── Worker 3
           │
           └── Database Supervisor
                  │
                  └── DB Connection（崩溃了重启即可）
```

**监督者的四种重启策略**​ ：

1. **恢复（Resume）**：保持已有内部状态，忽略导致故障的消息
2. **重启（Restart）**：重置 Actor 到初始状态
3. **停止（Stop）**：永久停止该 Actor
4. **升级（Escalate）**：把故障上报给上一级监督者
    
#### 🎯 "任其崩溃"的多重收益

> 💡 Actor 程序倾向于避免防御性编程，奉行"任其崩溃"哲学，这带来了多重好处 ：
> 
> - 代码更简单易懂，"正常路径"代码与容错代码清晰分离
> - Actor 彼此独立、不共享状态，一个 Actor 的失败几乎不可能对另一个产生不利影响
> - 特别重要的是——**一个失败 Actor 的监督者不会因为被监督 Actor 的崩溃而崩溃**
> - 监督者在修复错误的同时还可以记录日志，让我们意识到问题并采取补救措施，而不是把问题扫到地毯下
>     
**这就是为什么 Erlang 系统能在电信领域达到"九个九"（99.9999999%）的可用性**​ ——轻量级进程 + 监督树 + 热代码加载的组合 。

#### ⚠️ Actor 模型的代价

作者没有回避 Actor 的局限 ：

- **仍会遇到死锁**这一类共性问题
- **信箱溢出**等 Actor 模型独有的问题
- **对并行没有直接支持**：需要通过并发技术来构造并行方案，这会引入不确定性

### Day 3 — 分布式：位置透明带来的自然延展

第三天学习如何通过 Actor 模型编写分布式程序，将计算扩展到多台计算机，并能从一台或多台计算机的崩溃中恢复过来 。

#### 🔍 位置透明（Location Transparency）

Actor 模型最迷人的特性：**发送消息给另一台机器上的 Actor，与发送给本地 Actor 一样简单**​ 。

这是怎么做到的？

- 系统使用工厂构建 Actor 实例，并返回其引用（ActorRef）
- 由于位置无关紧要，Actor 实例可以启动、停止、移动和重启，以进行扩容/缩容或从意外故障中恢复
- 调用方只持有 ActorRef，不关心背后是本地进程还是远程节点
    
**位置透明的工程意义**：

- **横向扩展**：计算可以从单机扩展到集群，代码无需重写
- **容错恢复**：某台机器崩溃，Actor 可以在另一台机器上重启
- **地理分布式**：不同部分可部署在不同地理位置

#### 🎯 Actor 模型在分布式场景的独特定位

把 Actor 模型放回全书谱系中看：

|模型|共享内存|分布式内存|容错性|
|---|---|---|---|
|线程与锁|✅|❌|❌|
|函数式编程|✅|❌|间接（无状态）|
|Clojure 之道|✅|❌|❌|
|**Actor 模型**​|✅|✅|✅（监督树 + 任其崩溃）|
|CSP|✅|部分|间接|

> 📌 Actor 模型是本书第一个**同时支持共享内存和分布式内存架构**的模型 ，这也是为什么它"适用性非常好"，几乎可以解决任何规模的问题 。

## 🔗 全局观：Actor 模型在七大模型中的坐标

把第5章放回全书的演进谱系：

```
第2章 线程与锁：共享可变状态 → 三大危害
   │
   ▼ 激进解法：消灭可变状态
第3章 函数式编程：纯函数 + 不可变数据
   │
   ▼ 务实折中：承认需要状态，但重新设计"状态"概念
第4章 Clojure 之道：分离标识与状态（同进程内）
   │  └── 局限：不支持分布式，无法直接提供容错性
   │
   ▼ 边界突破：不共享状态 + 消息传递 + 监督树
第5章 Actor 模型：状态私有化 + 异步消息 + 位置透明
   │  ├── 优点：分布式、容错、"任其崩溃"哲学
   │  └── 缺点：信箱溢出、死锁仍可能发生、对并行无直接支持
   │
   ▼ 下一章：CSP 用"通道"作为一等公民，在共享内存场景下
   │          提供更轻量的消息传递（与 Actor 形成对照）
   ▼ 后续：数据级并行跳出"任务"思维；Lambda 架构走向集群
```

**这条演进链揭示的底层规律**：

> 💡 并发模型的演进，本质是关于"**如何在时间维度上协调对状态的观察与变更**"的探索，而 Actor 给出了一个极具洞察力的答案：
> 
> **不要把状态共享出去，而是把状态封装在独立实体中，让实体之间通过消息协作**。
> 
> 这个看似简单的设计决策，带来了一连串深远的后果：
> 
> 1. **并发边界收缩**：Actor 内部回归串行编程，并发复杂性被压缩到消息边界
> 2. **容错性内生**：因为状态隔离，一个 Actor 崩溃不会影响其他 Actor；监督树让"任其崩溃"成为可能
> 3. **分布式自然**：因为不共享内存，Actor 可以轻松跨越机器边界；位置透明让分布式编程与本地编程同构
> 4. **可推理性**：每个 Actor 可以单独测试，当测试覆盖了某个 Actor 的消息类型和消息顺序时，就可以确定这个 Actor 非常可靠
>     

**Actor 模型与前面模型的本质差异**：

- **vs 线程与锁**：线程锁把状态的读写权摊开在所有执行流面前 → Actor 把状态封装在私有实体中
- **vs 函数式编程**：函数式消灭状态 → Actor 保留状态，但不共享
- **vs Clojure 之道**：Clojure 用 CAS/事务让共享状态的变更受控 → Actor 根本不共享状态，用消息传递替代共享内存

## 💡 实际应用的场景与启示

### 场景一：电信/金融等高可用系统

Erlang/Elixir 在电信交换机、WhatsApp 后端等场景中证明了 Actor 模型的威力——**九个九的可用性**不是靠"不崩溃"，而是靠"崩溃了能自动恢复" 。

### 场景二：游戏服务器

Actor 模型在游戏服务端编程中广泛应用 ：每个玩家、每个 NPC、每个房间都可以是一个 Actor，通过消息协作。位置透明让游戏逻辑可以无缝扩展到多台服务器。

### 场景三：微服务架构

Actor 模型与微服务理念天然契合：

- 每个服务是一个 Actor（或 Actor 集群）
- 服务间通过异步消息通信
- 监督树实现服务熔断、降级、重启
- Akka Cluster、Orleans 是 JVM 和 .NET 生态的主流选择
    
### 场景四：物联网（IoT）与边缘计算

海量设备连接、设备随时上下线、网络不可靠——Actor 的"任其崩溃"哲学和监督树机制是天然匹配。

### 工程实践的几条铁律

1. **默认不共享**：把状态封装在 Actor 内部，外部只能通过消息间接影响
2. **消息即接口**：精心设计消息协议，消息是不可变对象
3. **监督策略显式化**：明确每个 Actor 的监督者是谁、崩溃时如何处理（恢复/重启/停止/升级）
4. **错误内核最小化**：把必须正确的核心逻辑放在高层监督者，把风险操作下推到低层 Actor
5. **避免防御性代码**：相信监督树，让"任其崩溃"哲学简化业务代码
6. **警惕信箱溢出**：失控的消息生产速度会导致信箱无限增长，需要背压（backpressure）机制

## 📝 第五章读书笔记要点

如果只能记住三句话：

1. **Actor 模型保留了可变状态，只是不进行共享**——每个 Actor 封装自己的状态，通过异步消息与其他 Actor 通信，把并发复杂性压缩到消息边界这一处
2. **"任其崩溃"哲学 + 监督树 = 内生的容错性**：不做防御性编程，让监督者在 Actor 崩溃时恢复/重启/停止/升级；错误内核模式让必须正确的核心逻辑最小化
3. **位置透明让分布式编程与本地编程同构**：发送消息给另一台机器上的 Actor 与发送给本地 Actor 一样简单，这是 Actor 模型能"解决几乎任何规模问题"的根本原因
    
### 衔接下一章的思考锚点

Actor 模型虽然强大，但作者指出了它的局限：仍可能死锁、信箱可能溢出、对并行没有直接支持 。更重要的是，Actor 模型在**共享内存场景下显得有些"重"**——为了跨分布式而设计的异步消息机制，在同进程内使用时会有不必要的开销。

第6章 CSP（通信顺序进程）给出另一个方向的答案：**同样基于消息传递，但把"通道（Channel）"作为一等公民**。CSP 与 Actor 的区别在于重心不同：

- **Actor 模型以"通道两端的实体"为中心**：Actor 是主角，邮箱是附属品
- **CSP 以"通道"为中心**：Channel 是主角，goroutine 是附属品
    
这个微妙的差别，让 CSP 在共享内存场景下（如 Go 语言的 goroutine + channel）提供了更轻量、更结构化的并发原语。但同时，CSP 通常没有 Actor 那样原生强大的分布式和容错机制——这也是为什么在实际工程中，我们常常看到 Actor（Akka）和 CSP（Go）被用于不同规模的问题。

> 📌 **全书隐藏主线愈发清晰**：每一种新模型都在重新定义"状态"——
> 
> - 线程与锁：状态是共享的可变内存 → 需要锁保护
>     
> - 函数式：状态不存在（只有值变换） → 从源头消除问题
>     
> - Clojure：状态是不可变值的时间序列 → 用 CAS/事务受控变更
>     
> - **Actor：状态封装在私有实体中，通过消息间接变更 → 不共享，所以无需锁**
>     
> - CSP：状态通过通道传递 → 以通道为中心的消息传递
>     
> - 数据并行：状态是数据阵列 → 通过 SIMD 并行变换
>     
> - Lambda：状态分散到集群 → 批处理层 + 加速层
>
