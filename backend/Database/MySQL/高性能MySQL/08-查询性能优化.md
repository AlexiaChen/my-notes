
# 第 8 章　查询性能优化——读书笔记

> 💡 这一章的本质，不是教你"哪里慢就改哪里"，而是建立一个**第一性原理**：查询的响应时间 = 所有子任务耗时之和。优化查询，本质上就是**消除子任务、减少子任务的执行次数、或让子任务跑得更快**。而绝大多数慢查询，都可以回溯到同一个病根——**访问了过多的数据**。
> 
> 正如 Silvia Botros 和 Jeremy Tinley 在开篇强调的："查询优化、索引优化和数据库表结构优化需要齐头并进，缺一不可"。本章是第 6 章（Schema 设计）和第 7 章（索引）的自然延伸——**没有好的 Schema 和索引，再精巧的查询改写也无米下炊；但没有好的查询，再优秀的 Schema 和索引也无法发挥价值**。

---

## 🎯 本章核心脉络

作者在这一章埋下了一条主线——**查询优化必须从"响应时间"反推，而非从"SQL 写法"正推**：

1. **响应时间是第一指标**——查询是任务，由子任务组成，每个子任务消耗时间
2. **慢的根因几乎都是"访问了过多数据"**——要么请求了不需要的数据，要么扫描了额外的记录
3. **重构查询往往比调参更有效**——一个复杂查询拆成多个简单查询、切分查询、分解联接
4. **理解 MySQL 的执行过程**——通信协议、查询状态、优化器、执行引擎、结果返回
5. **认清优化器的局限性**——UNION 限制、等值传递、并行执行、同表更新查询
6. **针对特定查询模式优化**——COUNT、JOIN、GROUP BY、LIMIT/OFFSET、UNION

MySQL 8.4 官方文档明确：**"为了加快 SELECT ... WHERE 的查询速度，在 WHERE 子句中使用的列上设置索引，对于 join 不同表的查询，索引尤其重要；避免查询时函数的使用；尽量减少全表扫描次数"**。这是 2026 年工业界查询优化的根本出发点。

## 为什么查询速度会慢

### 第一性原理视角

书中开宗明义：**响应时间 = 服务时间 + 排队时间**。

- **服务时间**：数据库真正处理查询的时间
- **排队时间**：等待 I/O、等待行锁、等待互斥量等资源的时间

📌 **洞见**：优化的本质，是对"子任务"动手：

1. **消除子任务**——不查不需要的列、不扫不需要的行
2. **减少子任务执行次数**——用索引避免全表扫描、用 LIMIT 提前终止
3. **让子任务跑得更快**——用覆盖索引避免回表、用内存临时表替代磁盘临时表

查询生命周期大致为：客户端 → 服务器 → 解析 → 生成执行计划 → 执行 → 返回结果。其中"执行"阶段最重要，包含大量对存储引擎的调用以及调用后的数据处理（排序、分组等）。

> ⚠️ **关键认知**：在大多数高性能查询场景中，时间都花在了"从底层存储引擎检索数据的调用操作"上——这些调用消耗在内存操作、CPU 操作和因内存不足导致的 I/O 操作上。这意味着：**减少存储引擎的数据访问次数，是查询优化最锋利的刀**。

## 慢查询基础：优化数据访问

### 是否向数据库请求了不需要的数据

书中指出低效查询的两个典型信号：**访问了太多行，或者访问了太多列**。

**反模式 1：请求了不必要的记录**

```
-- ❌ 反模式：取出所有列，应用层只用到其中 3 个
SELECT * FROM orders WHERE customer_id = 100;

-- ✅ 正确：只取需要的列
SELECT order_id, order_date, total_amount 
FROM orders 
WHERE customer_id = 100;
```

📌 **洞见**：`SELECT *` 在宽表上会造成 **2-5 倍的性能下降**——它强制回表、膨胀网络传输、挤占 buffer pool。更糟的是，如果查询本可以是覆盖索引，但 `SELECT *` 让覆盖索引失效，必须回表。

**反模式 2：多表关联时返回所有列**

```
-- ❌ 反模式
SELECT * FROM orders o JOIN customers c ON o.customer_id = c.id;

-- ✅ 正确：显式列出所需列
SELECT o.order_id, o.total_amount, c.customer_name 
FROM orders o JOIN customers c ON o.customer_id = c.id;
```

**反模式 3：重复查询相同数据**

📌 **洞见**：MySQL 8.0 已经移除了查询缓存，这意味着应用层必须自己承担缓存职责。2026 年工业界的做法是：

- 用 Redis 或应用层缓存热点数据
- 列表接口设 30-300 秒 TTL，可减少 60% 的数据库负载
- 每用户数据用 `user_id` 作缓存键，TTL 15 秒，可减少 30% QPS

### MySQL 是否在扫描额外的记录

书中给出了衡量查询开销的三个最简单指标：**响应时间、扫描行数、返回行数**。

**1. 响应时间的构成**

响应时间分为服务时间和排队时间。排队时间往往难以在应用层观测，但可以通过 `SHOW PROCESSLIST` 观察线程状态来间接判断。

**2. 扫描行数与访问类型**

EXPLAIN 的 `type` 列反映了访问类型，从慢到快依次是：

|type|含义|性能|
|---|---|---|
|ALL|全表扫描|最差|
|index|全索引扫描|差|
|range|范围扫描|中|
|ref|索引查找（非唯一）|良|
|eq_ref|唯一索引查找|优|
|const/system|常量引用|最优|

📌 **洞见**：**扫描行数与返回行数的比率**是衡量索引有效性的黄金指标。如果比率超过 100:1，通常意味着需要改进索引。例如 `LIMIT 20 OFFSET 10000`，返回 20 行但可能扫描了 10020 行——这就是典型的"小返回、大扫描"。

**3. EXTRA 列的红旗**

EXPLAIN 的 Extra 列出现以下字样时需警惕：

- **Using filesort**：需要额外排序，未能利用索引顺序
- **Using temporary**：使用了临时表（GROUP BY 或 ORDER BY 不匹配索引时）
- **Using where**：在服务器层过滤（存储引擎返回了多余行）

**2026 年工业界的诊断工作流**：

```
-- 1. 开启慢查询日志
SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 1;
SET GLOBAL log_queries_not_using_indexes = 'ON';

-- 2. 用 EXPLAIN 看执行计划
EXPLAIN SELECT * FROM orders WHERE customer_id = 100;

-- 3. 用 EXPLAIN ANALYZE 看实际执行（MySQL 8.0.18+）
EXPLAIN ANALYZE SELECT * FROM orders WHERE customer_id = 100;

-- 4. 用 pt-query-digest 分析慢日志
pt-query-digest /var/log/mysql/slow-query.log
```

> 💡 **EXPLAIN vs EXPLAIN ANALYZE**：传统 EXPLAIN 只显示**估计**的行数和成本；EXPLAIN ANALYZE 真正**执行**查询，显示实际行数和耗时。"估计值"和"实际值"的不匹配，往往揭示了过期的统计信息——这时需要 `ANALYZE TABLE`。

## 重构查询的方式

这是本章最具"第一性原理"色彩的一节——**有时候，改写查询比调索引更能带来质的飞跃**。

### 一个复杂查询还是多个简单查询

书中的核心观点：**在 MySQL 中，将一个复杂查询拆分为多个简单查询，往往能提升性能**。

📌 **洞见**：这与传统"尽量减少数据库交互"的观念相悖，但在 MySQL 语境下成立，原因有三：

1. **MySQL 优化器对复杂查询的优化能力有限**——多个简单查询让优化器每次面对的都是简单问题
2. **应用层可以做哈希关联**——避免了 MySQL 嵌套循环联接的某些缺陷
3. **减少锁竞争**——拆分的查询持有锁的时间更短

```
-- 反模式：一个巨型查询
SELECT ... FROM a JOIN b JOIN c JOIN d 
WHERE a.x = ? AND b.y = ? AND c.z = ? 
ORDER BY a.created_at DESC LIMIT 100;

-- 重构：应用层分步查询 + 哈希关联
SELECT ... FROM a WHERE a.x = ?;  -- 得到 100 个 id
SELECT ... FROM b WHERE b.id IN (...);  -- 用 id 列表查询
-- 应用层组装
```

> ⚠️ **权衡**：这种方法在网络往返成本高（高延迟）时不适用。局域网内单毫秒延迟，拆查是好选择；跨地域 50ms 延迟，就要慎重。

### 切分查询

书中提出：**大查询拆分为小查询，分而治之**。

典型场景：删除 1000 万行旧日志。

```
-- ❌ 反模式：单次大事务
DELETE FROM logs WHERE created_at < '2020-01-01';

-- ✅ 正确：分批删除
DELETE FROM logs WHERE created_at < '2020-01-01' LIMIT 10000;
-- 循环执行，每次之间 sleep 一小段时间
```

📌 **洞见**：切分查询的价值不在"更快"，而在"更平滑"——避免长事务锁表、避免主从复制延迟、避免 buffer pool 被大量脏页冲击。这是 SRE 视角下的查询优化：**宁可慢一点，不可堵一片**。

### 分解联接查询

书中指出：**将联接查询分解为应用层的多次单表查询，往往能提升性能并减少锁竞争**。

📌 **工业界场景**：

- **缓存友好**：单表查询结果更容易被缓存
- **减少锁竞争**：单次查询锁持有时间短
- **哈希关联**：应用层用哈希表做关联，避免 MySQL 嵌套循环的某些缺陷
- **跨分片查询**：在分库分表架构下，联接必须在应用层完成

```
-- 传统联接
SELECT u.name, o.total 
FROM users u JOIN orders o ON u.id = o.user_id 
WHERE u.account_type = 'premium';

-- 分解联接
SELECT id, name FROM users WHERE account_type = 'premium';  -- 得到 id 列表
SELECT user_id, total FROM orders WHERE user_id IN (...);  -- 单表查询
-- 应用层哈希关联
```

## 查询执行的基础

### MySQL 客户端/服务器通信协议

书中揭示了一个反直觉的事实：**MySQL 客户端与服务器之间的通信协议是"半双工"的**。

📌 **洞见**：半双工意味着——

- 任一时刻，要么是服务器向客户端发数据，要么是客户端向服务器发数据
- 客户端发送查询后，只能等待结果，**不能取消**正在执行的查询（直到 MySQL 8.0.20+ 支持 `KILL QUERY` 或 CTRL-C）
- 服务器开始响应后，客户端**必须完整接收整个结果集**——不能只取前 10 行就断开

**工程启示**：

1. **`max_allowed_packet` 限制单包大小**——超大查询会抛异常
2. **LIMIT 不只是语义需求，更是协议需求**——避免产生超出客户端处理能力的结果集
3. **流式处理**：客户端应逐行消费结果，而非一次性加载到内存

### 查询状态

书中列举了关键的线程状态，`SHOW FULL PROCESSLIST` 可以观测：

|状态|含义|
|---|---|
|Sleep|等待客户端新请求|
|Query|正在执行查询或发送结果|
|Locked|等待表锁（服务器层）|
|Analyzing and statistics|收集存储引擎统计信息，生成执行计划|
|Copying to tmp table|复制结果集到临时表（GROUP BY / filesort / UNION）|
|Sorting result|正在排序结果集|
|Sending data|在状态间传输数据、生成结果集、返回数据给客户端|

📌 **洞见**：**"Sending data" 是停留时间最长、也最容易被误解的状态**。它不代表"正在发送给客户端"，而是代表线程在多个状态间传输数据、生成结果集——这个阶段包含了存储引擎的数据访问、WHERE 过滤、GROUP BY 等几乎所有重活。看到长时间停留的"Sending data"，不要以为是网络慢，而要怀疑是存储引擎扫描了过多数据。

### 查询优化处理

这是本章的技术核心。MySQL 的查询优化器经历以下阶段：

1. **语法解析与预处理**：验证 SQL 语法、检查表和列是否存在
2. **查询重写**：应用代数等价变换
3. **成本估算**：基于统计信息估算不同执行计划的成本
4. **执行计划生成**：选择成本最低的计划

**MySQL 8.4 官方文档明确的优化器能力**：

**1. 常量折叠（Constant-Folding）**

```
-- 优化器自动识别常量比较
SELECT * FROM t WHERE c >= 255;  -- 若 c 是 TINYINT UNSIGNED
-- 优化器转换为：SELECT * FROM t WHERE 1=0（空集）
```

**2. 去除不必要的括号和常量条件**

```
((a AND b) AND c OR (((a AND b) AND (c AND d)))) 
→ (a AND b AND c) OR (a AND b AND c AND d)
```

**3. 索引上的常量表达式只计算一次**

**4. COUNT/MIN/MAX 的索引树优化**

```
SELECT COUNT(*) FROM tbl_name;  -- MyISAM 直接从表信息获取
SELECT MIN(key_part1) FROM tbl_name;  -- 利用 B+tree 最左叶
SELECT MAX(key_part2) FROM tbl_name WHERE key_part1 = constant;
```

**5. 提前终止**

- LIMIT 让排序提前停止
- 检测到不可能的条件立即返回空集
- HAVING 在没有 GROUP BY 时与 WHERE 合并

**6. 索引合并（Index Merge）**

📌 **洞见**：这是书中可能未充分展开的现代优化器能力。MySQL 可以用多个单列索引检索行，然后合并结果：

```
-- 可能触发 Index Merge Union
SELECT * FROM tbl_name WHERE key1 = 10 OR key2 = 20;

-- 可能触发 Index Merge Intersection
SELECT * FROM tbl_name WHERE key1 = 10 AND key2 = 20;
```

> ⚠️ **索引合并的局限**：
> 
> - 不适用于全文索引
> - 复杂 WHERE 子句（深层 AND/OR 嵌套）可能让优化器选不到最优计划
> - 此时需要手动重写查询：`(x AND y) OR z => (x OR z) AND (y OR z)`

**7. 联接顺序重排**

📌 **洞见**：MySQL 不按 SQL 中表的书写顺序联接，而是由优化器基于成本估算选择最优顺序。这就是为什么"小表驱动大表"在 MySQL 中不是绝对规则——优化器会自己决定。

**8. 哈希联接（Hash Join）**

MySQL 8.0.20+ 引入了哈希联接，对某些场景比嵌套循环联接快一个数量级。

**9. EXPLAIN FORMAT=TREE 与 EXPLAIN ANALYZE**

MySQL 8.0.16+ 支持 `EXPLAIN FORMAT=TREE`，8.0.18+ 支持 `EXPLAIN ANALYZE`：

```
-- 查看实际执行时间与估计值的差异
EXPLAIN ANALYZE 
SELECT * FROM orders o JOIN customers c ON o.customer_id = c.id 
WHERE o.total_amount > 1000;
```

### 查询执行引擎

书中讲到，MySQL 的执行引擎基于**迭代器模型**——每个操作符（扫描、过滤、联接、聚合）都是一个迭代器，上层调用下层的 `Next()` 获取下一行。

📌 **洞见**：这种"火山模型"（Volcano Model）的意义在于：**数据是一行一行向上流动的，每一层都可以提前终止**。这就是为什么：

- LIMIT 可以让排序提前停止
- 找到不满足条件的行可以立即丢弃
- 联接操作可以在找到匹配后立即继续

### 将结果返回给客户端

书中强调：**服务器一旦生成第一条结果，就开始向客户端发送数据**。

📌 **洞见**：这意味着——

- 客户端可以边接收边处理（流式）
- 但客户端必须完整接收结果集（半双工协议的限制）
- **`SQL_BUFFER_RESULT` 提示**可强制结果放入临时表，尽早释放表锁

## MySQL 查询优化器的局限性

这是本章最具洞察力的一节——**认清优化器不能做什么，比认清它能做什么更重要**。

### UNION 的限制

📌 **洞见**：UNION 的每个子查询可能无法充分利用外层 WHERE 条件。

```
-- 外层条件无法推入每个 UNION 分支
SELECT * FROM (
    SELECT id, name FROM users WHERE type = 'A'
    UNION ALL
    SELECT id, name FROM users WHERE type = 'B'
) AS t 
WHERE t.id > 1000;  -- 这个条件无法推入内层查询
```

**解决方案**：将外层条件手动推入每个子查询：

```
SELECT id, name FROM users WHERE type = 'A' AND id > 1000
UNION ALL
SELECT id, name FROM users WHERE type = 'B' AND id > 1000;
```

### 等值传递

📌 **洞见**：优化器能识别 `a = b AND b = c` 推导出 `a = c`（等值传递），但并非所有场景都能完美处理。对于复杂的多表联接，等值传递可能失效，需要手动添加冗余条件帮助优化器。

### 并行执行

📌 **洞见**：**MySQL 在查询级别不支持并行执行**——一个查询不会利用多个 CPU 核心并行扫描同一张表。这是 MySQL 与 Oracle、PostgreSQL 的重要差异。

**2026 年的现实**：

- InnoDB 在 8.0.14+ 支持**并行读取**（通过 `innodb_parallel_read_threads`）
- 但这是存储引擎层的扫描并行，不是查询执行并行
- 真正的"并行查询"需要应用层分片查询，或用 `/*+ SET_VAR(innodb_parallel_read_threads=4) */` 提示

### 在同一个表中查询和更新

📌 **洞见**：这是 MySQL 的经典限制——**不能在一条 SQL 中同时查询和更新的同一张表**。

```
-- ❌ 报错：不能 SELECT 的同时 UPDATE 同一张表
UPDATE orders SET status = 'processed' 
WHERE id IN (SELECT id FROM orders WHERE status = 'pending');
```

**解决方案**：

```
-- 方案 1：用临时表中转
CREATE TEMPORARY TABLE tmp_ids SELECT id FROM orders WHERE status = 'pending';
UPDATE orders SET status = 'processed' WHERE id IN (SELECT id FROM tmp_ids);
DROP TEMPORARY TABLE tmp_ids;

-- 方案 2：用多表 UPDATE
UPDATE orders o JOIN (SELECT id FROM orders WHERE status = 'pending') t 
ON o.id = t.id 
SET o.status = 'processed';
```

## 优化特定类型的查询

### 优化 COUNT() 查询

书中指出：__COUNT(_) 与 COUNT(column) 语义不同_*——前者计数行数，后者计数非 NULL 的列值。

📌 __洞见 1：COUNT(_) 的最优路径_*

MySQL 官方明确：对于 MyISAM 和 MEMORY 表，`COUNT(*)` 不带 WHERE 时直接从表元信息获取。对于 InnoDB，8.0+ 通过聚簇索引统计，但仍是近似优化。

**精确 COUNT 与近似 COUNT 的取舍**：

- 仪表盘、统计页：用 `EXPLAIN` 的 `rows` 估算值（近似）
- 精确业务计数：必须真实 COUNT，但可以用汇总表缓存

📌 **洞见 2：汇总表模式**

```
-- 实时 COUNT 在大表上很慢
SELECT COUNT(*) FROM orders WHERE created_at >= '2026-01-01';  -- 可能扫 100 万行

-- 用汇总表
CREATE TABLE daily_order_counts (
    order_date DATE PRIMARY KEY,
    order_count INT NOT NULL
);
-- 异步任务每分钟更新
-- 查询变成：SELECT SUM(order_count) FROM daily_order_counts 
--           WHERE order_date >= '2026-01-01';  -- 扫 30 行
```

### 优化联接查询

书中给出关键建议：**在 ON 和 USING 子句的列上建索引**。

📌 **洞见**：MySQL 8.0.20 前后，联接算法发生了重大变化：

- **8.0.20 之前**：主要用嵌套循环联接（Nested Loop Join）
- **8.0.20 之后**：引入哈希联接（Hash Join），对大表联接性能提升显著

**联接优化的现代实践**：

```
-- 1. 确保联接列有索引
CREATE INDEX idx_customer_id ON orders(customer_id);

-- 2. 用小表驱动大表（在哈希联接下不再绝对，但仍有参考价值）
-- 3. 用 STRAIGHT_JOIN 强制联接顺序（当优化器选错时）
SELECT * FROM users u STRAIGHT_JOIN orders o ON u.id = o.user_id;

-- 4. 用优化器提示
SELECT /*+ JOIN_ORDER(u, o) */ u.name, o.total 
FROM users u JOIN orders o ON u.id = o.user_id;
```

### 使用 WITH ROLLUP 优化 GROUP BY

📌 **洞见**：`WITH ROLLUP` 让 MySQL 在一次查询中同时计算明细和小计/总计，避免多次查询。

```
-- 一次查询得到按地区、按国家的销售明细 + 各地区小计 + 总计
SELECT region, country, SUM(sales) 
FROM sales 
GROUP BY region, country WITH ROLLUP;
```

**注意**：`WITH ROLLUP` 会影响索引的使用方式，对于大表可能不如"多次查询 + 应用层汇总"高效。需要根据数据量权衡。

### 优化 LIMIT 和 OFFSET 子句

这是 2026 年工业界踩坑最多的场景。

**MySQL 官方文档明确指出 LIMIT 的优化行为**：

- LIMIT 与 ORDER BY 配合时，找到前 N 行后停止排序
- 如果有索引支持 ORDER BY，这非常快
- 如果需要 filesort，必须先排序所有匹配行，再取前 N 行

📌 **洞见 1：深分页的性能悬崖**

```
-- 看似无害，实则灾难
SELECT * FROM orders ORDER BY created_at DESC LIMIT 10000, 20;
```

**问题**：MySQL 必须扫描并丢弃前 10000 行，只返回第 10001-10020 行。OFFSET 越大，扫描成本越高。

**官方文档证实**：社区版 MySQL 中，LIMIT 和 OFFSET 在 SQL 层处理，存储引擎至少返回 10020 行，然后 SQL 层丢弃前 10000 行。

📌 **洞见 2：Keyset 分页（游标分页）是 2026 年的标准答案**

```
-- ❌ Offset 分页：越翻越慢
SELECT id, name, price FROM products ORDER BY id LIMIT 20 OFFSET 10000;

-- ✅ Keyset 分页：恒定时间
SELECT id, name, price FROM products 
WHERE id > 10000  -- 上一页最后一条的 id
ORDER BY id LIMIT 20;
```

**优势**：

- 利用索引查找，时间复杂度 O(log N) 而非 O(N)
- 不受偏移量影响，第 1 页和第 1000 页一样快
- 结果集稳定（不会因新数据插入而重复/遗漏）

> 💡 **工业界补充**：火山引擎 RDS for MySQL 等云厂商已经实现了 **LIMIT/OFFSET 下推优化**——将 LIMIT 和 OFFSET 直接下推到存储引擎，减少 SQL 层与存储引擎的交互。但这需要特定的内核版本（MySQL 8.4.7_20260415+），**社区版 MySQL 默认不具备此优化**。所以 Keyset 分页仍然是通用最佳实践。

📌 **洞见 3：ORDER BY 与 LIMIT 的组合陷阱**

MySQL 官方警告：**带 LIMIT 和不带 LIMIT 的 ORDER BY 查询可能返回不同顺序的行**。这是因为 LIMIT 可能导致优化器选择不同的执行计划。如果业务依赖稳定的排序，必须在 ORDER BY 中包含唯一列：

```
-- 不稳定：同分情况下顺序不确定
SELECT * FROM products ORDER BY price DESC LIMIT 10;

-- 稳定：加入唯一列
SELECT * FROM products ORDER BY price DESC, id DESC LIMIT 10;
```

### 优化 SQL_CALC_FOUND_ROWS

📌 **洞见**：**SQL_CALC_FOUND_ROWS 在 MySQL 8.0.17 中已弃用，未来版本将移除**。

```
-- ❌ 已弃用的写法
SELECT SQL_CALC_FOUND_ROWS id, name FROM products LIMIT 3 OFFSET 0;
SELECT FOUND_ROWS() AS total;

-- ✅ 现代替代方案：独立的 COUNT(*) 查询
SELECT COUNT(*) AS total FROM products;  -- 总数
SELECT id, name FROM products LIMIT 3 OFFSET 0;  -- 页数据
```

**为什么弃用**：SQL_CALC_FOUND_ROWS 强制 MySQL 计算所有匹配行数，无法利用 LIMIT 的提前终止优化。独立的 COUNT(*) 查询可以由汇总表优化，或由 `EXPLAIN` 的 rows 估算近似。

### 优化 UNION 查询

书中指出：**UNION 比 UNION ALL 多了一个去重步骤**。

📌 **洞见**：

```
-- ❌ 不必要的去重开销
SELECT id FROM table1 WHERE type = 'A'
UNION
SELECT id FROM table2 WHERE type = 'B';

-- ✅ 如果业务允许重复，用 UNION ALL
SELECT id FROM table1 WHERE type = 'A'
UNION ALL
SELECT id FROM table2 WHERE type = 'B';
```

**UNION ALL 的优势**：

- 不需要临时表去重
- 不需要排序
- 可以并行执行子查询

**对于大结果集的 UNION，务必使用 UNION ALL**，除非确实需要去重。

## 2026 年工业界查询优化的最新补充

结合国外英文资料和工业实践，以下是书里可能未充分覆盖的现代视角：

### 1. MySQL 8.4 的查询优化新现实

- **查询缓存已完全移除**：缓存必须在应用层（Redis）或 ORM 层实现
- **不可见索引**：测试索引删除效果而不真正删除
    
    ```
    ALTER TABLE t1 ALTER INDEX i1 INVISIBLE;
    ```
    
- **降序索引**：避免 ORDER BY DESC 的 filesort
- **直方图自动更新**：8.4 中 `ANALYZE TABLE AUTO UPDATE` 可自动更新直方图
- **EXPLAIN ANALYZE**：8.0.18+ 可用，显示实际执行时间

### 2. 查询优化的现代工作流

OneUptime 等工业界团队推荐的方法论：

```
1. 开启慢查询日志（long_query_time = 1）
2. 用 pt-query-digest 分析慢日志，找出 TOP 20 慢查询
3. 对每个慢查询执行 EXPLAIN，识别：
   - type: ALL（全表扫描）
   - rows: 高估算行数
   - Extra: Using filesort / Using temporary
4. EXPLAIN ANALYZE 对比估计与实际
5. 检查 WHERE 子句是否 sargable（可索引）
6. 设计/调整索引
7. 重写查询（分解联接、切分查询、Keyset 分页）
8. 验证：EXPLAIN 确认索引被使用
9. 监控：部署后观察响应时间
```

### 3. Sargability（可索引性）原则

📌 **洞见**：WHERE 子句中的列必须是"sargable"的，索引才能生效。

```
-- ❌ 不可索引：函数包裹了索引列
SELECT * FROM payments WHERE YEAR(created_at) = 2026;

-- ✅ 可索引：范围条件
SELECT * FROM payments 
WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01';

-- ❌ 不可索引：隐式类型转换
SELECT * FROM users WHERE phone_number = 01012345678;  -- phone_number 是 VARCHAR

-- ✅ 可索引：类型匹配
SELECT * FROM users WHERE phone_number = '01012345678';
```

### 4. 索引条件下推（ICP）

MySQL 5.6+ 支持 Index Condition Pushdown——将 WHERE 条件中涉及索引列的判断下推到存储引擎层，减少回表次数。这是现代 MySQL 的默认行为，但 DBA 应该知道它的存在。

### 5. 覆盖索引的极致追求

2026 年工业界共识：宽表查询如果无法做成覆盖索引，性能天花板很低：

```
-- 覆盖索引让 40ms 的查询降至 8ms
CREATE INDEX idx_posts_cover 
ON posts (author_id, created_at, id, title);

-- 列表页只查 4 个列，完全从索引获取数据
SELECT id, title, created_at, author_id 
FROM posts 
WHERE author_id = ? 
ORDER BY created_at DESC 
LIMIT 20;
```

### 6. 选择性规则

工业界经验值：**热过滤列的选择性应高于 1:1000**——即一个过滤值应返回不超过 0.1% 的行。如果某列只有 5 个可能值，单独索引它会返回 20% 的行，效果不佳，必须与高基数列组合成复合索引。

### 7. 查询优化的边界

📌 **洞见**：不是所有慢查询都能通过 SQL 改写解决。当单表数据量超过亿级，以下手段可能比查询优化更有效：

- **分库分表**（Sharding）
- **读写分离**（Read Replica）
- **列式存储**（ClickHouse 等）
- **缓存层**（Redis、Memcached）
- **预处理汇总表**

## 小结

这一章表面讲的是"怎么优化查询"，深层传递的是**SRE 视角的查询哲学**：

**1. 响应时间是第一指标**

查询由子任务组成，优化就是消除子任务、减少执行次数、让子任务更快。所有优化技术都服务于这个目标。

**2. 慢的根因几乎都是"访问了过多数据"**

- 向数据库请求了不需要的数据（太多列、太多行、重复查询）
- MySQL 扫描了额外的记录（全表扫描、文件排序、临时表）

**3. 重构查询往往比调参更有效**

- 复杂查询拆分成多个简单查询
- 大查询切分成批次
- 联接查询分解到应用层做哈希关联

**4. 理解执行过程是优化的前提**

- 半双工协议决定了客户端必须完整接收结果
- "Sending data" 状态隐藏了大部分工作量
- 优化器基于成本估算选择执行计划，但可能选错

**5. 认清优化器的局限性**

- UNION 子查询难以利用外层条件
- 等值传递并非万能
- MySQL 不支持查询级并行执行
- 同表查询和更新不能共存于一条 SQL

**6. 特定查询模式的优化套路**

- COUNT：用汇总表缓存，区分精确与近似
- 联接：确保联接列有索引，利用哈希联接
- LIMIT/OFFSET：深分页改用 Keyset 游标分页
- SQL_CALC_FOUND_ROWS：已弃用，改用独立 COUNT(*)
- UNION：能用 UNION ALL 就不用 UNION

**7. MySQL 8.4 的现代现实**

- 查询缓存已移除，缓存必须在应用层
- EXPLAIN ANALYZE 提供实际执行时间
- 直方图自动更新让统计信息更准确
- 不可见索引让索引治理更安全

> 💡 **贯穿全章的洞见**：查询优化的本质，是用"减少数据访问"这一杠杆，撬动响应时间的下降。每一次全表扫描、每一次回表、每一次文件排序、每一次临时表创建，都是对响应时间的征税。优秀的查询优化者，像一个精明的税务筹划师——**合法地、巧妙地规避每一个不必要的数据访问税**。
> 
> 一个真实工业级查询优化工作流：
> 
> 1. **收集证据**：慢查询日志 + Performance Schema + EXPLAIN ANALYZE
> 2. **定位瓶颈**：识别全表扫描、高扫描行数、Using filesort、Using temporary
> 3. **检查 sargability**：WHERE 子句是否可利用索引
> 4. **设计索引**：基于查询模式设计复合索引、覆盖索引
> 5. **重写查询**：分解联接、切分查询、Keyset 分页
> 6. **验证效果**：EXPLAIN 确认索引被使用，响应时间下降
> 7. **持续监控**：部署后观察，防止回归
> 
> 这套方法论，让查询优化从"DBA 的黑魔法"变成了"工程的科学"——这正是本书 SRE 视角的精髓：**用数据驱动决策，用可观测性闭环反馈**。
> 
> 正如书中所言："查询优化、索引优化和数据库表结构优化需要齐头并进，缺一不可"。第 6 章的 Schema、第 7 章的索引、第 8 章的查询，三者构成了一个**性能优化的铁三角**——任何一方的短板，都会成为整个系统的瓶颈。理解这三章的内在联系，比理解任何单章的技巧都重要。

📌 **给读者的实践清单**：

- ✅ 永远不用 `SELECT *`，显式列出所需列
- ✅ 用 EXPLAIN 和 EXPLAIN ANALYZE 验证每个慢查询
- ✅ 确保 WHERE、JOIN、ORDER BY 列都是 sargable 的
- ✅ 深分页用 Keyset 游标分页，禁用大 OFFSET
- ✅ 用 UNION ALL 替代 UNION（除非必须去重）
- ✅ 联接列必须有索引
- ✅ 大批量操作切分为小批次
- ✅ 复杂联接考虑分解到应用层做哈希关联
- ✅ 用汇总表缓存 COUNT 等聚合结果
- ✅ 不在 WHERE 子句中对索引列使用函数
- ❌ 不要用 SQL_CALC_FOUND_ROWS（已弃用）
- ❌ 不要依赖 MySQL 查询缓存（8.0 已移除）
- ❌ 不要在同一 SQL 中查询和更新同一张表
- ❌ 不要让单查询扫描超过 1000 行却只返回 10 行

**查询是数据库与客户端的契约，契约的条款（SQL 写法）决定了履行的代价（响应时间）。一个优秀的查询，是用最少的子任务、最短的路径、最少的资源，换取准确的结果——这正是为什么本章把"查询性能优化"放在 Schema 和索引之后的第一性原理：Schema 和索引是静态的基础设施，而查询是动态的、每秒钟都在发生的资源消费行为。没有高效的查询，再完美的 Schema 和索引也只是沉默的潜力；而没有清晰的 Schema 和索引，再精巧的查询优化也只是无米之炊。三者合一，方能成就真正高性能的 MySQL。**
