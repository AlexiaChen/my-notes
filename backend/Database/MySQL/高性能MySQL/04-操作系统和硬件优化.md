
# 第 4 章　操作系统和硬件优化——读书笔记

> 💡 这一章的本质，不是给你一张"最优参数清单"，而是建立一个**第一性原理**：MySQL 的性能上限由它最弱的硬件/OS 环节决定，而操作系统和硬件的共同使命，是给 MySQL 提供一个**稳定、可预测、低延迟的资源底座**。任何调优，都应该从"瓶颈在哪"出发，而不是从"别人配了什么"出发。

---

## 🎯 本章核心脉络

书里这一章的隐藏主线其实是**一个诊断循环**：

1. **定位瓶颈**——是 CPU、内存、I/O 还是网络？
2. **理解资源关系**——尤其是"内存是用来避免磁盘 I/O 的"这一核心命题
3. **按工作负载选型**——OLTP 看重单核高频和低延迟存储；OLAP 看重多核和内存带宽
4. **OS 层消除反模式**——swap、错误调度器、文件系统元数据写、NUMA 跨节点访问
5. **用工具验证**——iostat、perf、fio 等

📌 **我的洞见**：很多 DBA 把这一章当成"参数手册"来读，这是误解。Silvia Botros 和 Jeremy Tinley 作为 SRE 背景的作者，真正想传达的是——**在云原生和 NVMe 时代，操作系统调优的角色已经从"主要性能杠杆"退化为"消除明显反模式的卫生措施"**。Oracle 的 MySQL 团队在 2026 年的官方博客里把这个优先级说得非常清楚：**先确保 OS 不拖累数据库（不 swap、THP 处理得当、文件描述符足够、存储栈合理），然后才是 MySQL 变量调优，最后才是 SQL 和索引——而最大的性能收益往往藏在第三步**。

这意味着：与其死记硬背 `vm.swappiness=1`，不如建立"**测量 → 识别瓶颈 → 针对性消除**"的工程方法论。

## 什么限制了 MySQL 的性能

书里开宗明义：最常见的瓶颈是 **CPU 耗尽**——要么并行查询太多，要么少量查询在 CPU 上跑太久。I/O 饱和也会发生，但因为 SSD 的普及，频率远低于 CPU 耗尽。内存耗尽通常发生在给 MySQL 分配过多内存时。

📌 **洞见**：这个判断在 2026 年依然成立，但需要加一个**云环境修正案**——在云上跑 MySQL，瓶颈经常既不是 CPU 也不是本地磁盘，而是**网络存储的 IOPS 限制和延迟**。Arm 官方 MySQL 调优指南明确指出："本地挂载的 SSD 通常性能最佳，但基于网络的存储系统也可能表现良好，需要在你的环境中测试"。所以"瓶颈是什么"这个问题，在云时代的答案是**动态的、与环境强相关的**——这也是为什么本章最后的"其他有用的工具"小节如此重要。

**第一性原理视角**：MySQL 的瓶颈本质是"某一时刻，对某个资源的需求 > 该资源的供给能力"。识别瓶颈的正确工具链是：

- `top` / `mpstat` ——CPU
- `iostat -x 1` ——磁盘 I/O 饱和度
- `pidstat -d 1` ——进程级 I/O 行为
- `perf` ——内核级瓶颈（后面"其他有用的工具"会展开）

## 如何为 MySQL 选择 CPU

书的核心观点：**低延迟（高时钟频率）比多核心更重要**。原因是 MySQL 8.0 的查询执行引擎仍然是单线程导向的——除了少数内部操作（如并行查询、InnoDB 的 I/O 线程），**一条查询通常只能用一个 CPU 核心**。

Percona 的 Vadim Tkachenko 在设计写密集型 MySQL 部署时的选择印证了这一点：他们选了 **双路 Intel Xeon E5-2643v2（6 核 × 3.5GHz）**，明确说"Many MySQL functions are not parallel... so we're going for CPU with faster cores rather than larger amount of cores"。

📌 **洞见**：这里要分场景看，不能一刀切：

|工作负载|CPU 策略|原因|
|---|---|---|
|OLTP（高并发小查询）|**高主频优先**，8-32 核|单查询延迟敏感，多核用于并发|
|OLAP（复杂分析查询）|**多核优先**，32 核以上|MySQL 8.0 的并行查询能利用多核|
|写密集 + 压缩（如 TokuDB/MyRocks）|高主频 + 多核|压缩是 CPU hungry|
|混合负载|平衡频率和核心数|中高主频的多核 CPU|

> 💡 一个 2026 年视角的补充：随着 MySQL 8.0 对多核支持的持续优化（特别是并行查询、并行 DDL、InnoDB 多实例 buffer pool），**"多核无用论"已经过时**。但"单条查询的瓶颈仍在单核"这一事实没变。所以现代选型是：**主频不低于 3.0GHz，核心数根据并发量给到 16-64 核**。

**NUMA 陷阱**（书里提到但值得展开）：在多路 CPU 服务器上，内存访问有"本地/远程"之分。如果 MySQL 进程运行在 NUMA 节点 0，却大量访问节点 1 的内存，性能会下降 20-30%。工业界两种做法：

- **方案 A**：`numactl --interleave=all mysqld` 让内存交错分配
- **方案 B**：把 MySQL 绑定到单一 NUMA 节点（适合内存需求小于单节点容量的情况）

## 平衡内存和磁盘资源

这是全章最深刻的一节，也是第一性原理的体现。

### 缓存、读取和写入

书里讲透了一个本质：**内存的存在是为了"避免磁盘访问"**。

- **读取**：如果在内存中，最快，完全不碰磁盘
- **写入**：可以通过批量合并多个更新来大幅降低磁盘负载

📌 **洞见**：这里有个反直觉的洞见——**配置大内存的主要目的，不是为了"在内存中保存数据"，而是为了"避免磁盘 I/O"**。这两句话说起来相似，但思维模型完全不同：

- 前者让你想着"我的数据集 200GB，所以要 256GB 内存"
- 后者让你想着"我的**工作集**（活跃数据）是 80GB，所以 128GB 内存就够，剩下的留给 OS 缓存和连接内存"

MySQL 官方文档对 `innodb_buffer_pool_size` 的建议是**物理内存的 50%-75%**。工业界的更精细做法是：

```
buffer pool = 工作集大小 × 1.2（留出增长余量）
但不超过物理内存的 75%
且为 OS、连接、InnoDB 字典等预留至少 2-4GB
```

### 你的工作集是什么

📌 **这是本节最容易被跳过、但最关键的概念**。工作集 = 被频繁访问的"热数据"+ 索引。它通常远小于总数据量。

一个真实案例：某电商数据库总数据量 2TB，但 95% 的查询只访问最近 90 天的数据 + 核心维度表，实际工作集约 120GB。给他们配 256GB 内存（buffer pool 约 180GB），buffer pool 命中率 99.9%。如果误以为"要装下所有数据"，就会错误地追求 2TB+ 内存，纯属浪费。

**如何测量工作集**：

```
-- 利用 InnoDB 的 buffer pool 使用率
SELECT 
  (SELECT COUNT(*) FROM information_schema.INNODB_BUFFER_PAGE 
   WHERE COMPRESSED_SIZE = 0) AS hot_pages,
  (SELECT COUNT(*) FROM information_schema.INNODB_BUFFER_PAGE 
   WHERE COMPRESSED_SIZE > 0) AS compressed_pages;
```

或者用更简单的代理指标：监控 `Innodb_buffer_pool_read_requests` vs `Innodb_buffer_pool_reads`，**命中率低于 99% 就说明 buffer pool 不够大，或者工作集在增长**。

## 固态存储

### 闪存概述

SSD 相比 HDD 的优势不是简单的"快 10-20 倍"（书里的数字），而是在随机 I/O 上的**质的飞跃**——HDD 的随机 I/O 受限于磁头寻道（~10ms），而 SSD 的随机访问延迟在微秒级。对于 MySQL 这种随机访问频繁的负载，SSD 带来的差异是决定性的。

现代工业视角：

- **SATA SSD**：随机 IOPS 约 10K-80K
- **NVMe SSD**：随机 IOPS 可达 300K-500K+
- **企业级 NVMe**：具备断电保护电容，保证写入持久性

### 垃圾收集

📌 **洞见**：SSD 的写入放大和垃圾收集（GC）是工业界容易踩的坑。SSD 写入前必须先擦除整个 block（几百 KB 到几 MB），所以：

- **写密集负载下，低质量 MLC SSD 可能在数周内磨损殆尽**
- 企业级 SSD 的 endurance 评级是关键采购指标——HGST FlashMax II 的企业级 endurance 是 10PBW（随机写）

**对 MySQL 的启示**：

- 写密集场景（如 binlog、redo log、TokuDB/MyRocks 压缩写入）必须选用企业级 SSD
- 消费级 NVMe（如三星 980 Pro）**绝对不能**用于生产数据库主存储
- 监控 SSD 的磨损指标（SMART 属性中的 `Percentage Used`）

📌 **2026 年 NVMe 调优洞见**：默认 MySQL 参数（为 HDD 时代设计）会浪费 NVMe 的性能。关键调整：

```
innodb_io_capacity = 5000-20000  # 默认 200，远低于 NVMe 能力
innodb_io_capacity_max = 10000-40000
innodb_flush_neighbors = 0  # NVMe 下相邻页刷新无意义，反而耗 CPU
innodb_flush_method = O_DIRECT  # 避免 buffer pool 和 OS page cache 双重缓存
```

## RAID 性能优化

书里的结论非常明确：**RAID 10 是 MySQL 的最优解**，RAID 5 因重建时性能暴跌和写惩罚而不推荐。

|RAID 级别|读性能|写性能|冗余|MySQL 适用性|
|---|---|---|---|---|
|RAID 0|最高|最高|无|仅临时数据、非关键数据|
|RAID 1|高|中|高|binlog、关键数据|
|RAID 5|高|**低**（写惩罚）|中|不推荐|
|RAID 10|高|高|高|**生产首选**​|

📌 **洞见**：Percona 的写密集架构里，主存储用 **PCIe SSD（HGST FlashMax II 4.8TB）**，而 OS 和日志用 **RAID 1 over 2× 3TB HDD**。这个设计很有启发性：

- **热数据 / 主存储**​ → 企业级 NVMe/PCIe SSD（性能优先）
- **OS / 日志 / binlog**​ → RAID 1 的机械盘或中端 SSD（持久性 + 成本平衡）

**RAID 控制器缓存的关键规则**：

- ✅ 带 BBU（电池备份单元）的写缓存 → 可以安全开启
- ❌ 不带 BBU 的写缓存 → **必须禁用**，否则断电丢失数据
- 现代 RAID 卡普遍采用 **电容备份（supercap）**而非电池，维护更简单

> ⚠️ **RAID 不等于备份**。RAID 解决的是"单盘故障不停机"，不解决"人为 DELETE 误删"、"文件系统损坏"、"机房级灾难"。这点在书里特别强调，工业界也反复踩坑。

### RAID 故障、恢复和监控

关键实践：

- **监控 RAID 卡电池/BBU 状态**：BBU 失效时，许多 RAID 卡会自动禁用写缓存，性能断崖式下跌
- **监控重建进度**：RAID 10 重建相对快，RAID 5 重建期间性能极差且二次故障风险高
- **定期巡检**：`megacli -PDList -aAll` 或通过 `smartctl` 检查每块盘的健康

### RAID 配置和缓存

📌 **洞见**：RAID 控制器缓存的策略配置是个精细活：

- **WriteBack + BBU**​ → 写入先入控制器缓存，性能极佳，断电由 BBU 保护
- **WriteThrough**​ → 写入直落磁盘，安全但慢
- **Cached 读**​ → 通常开启，因为 OS 和 MySQL 自身有更大的缓存，控制器读缓存意义有限

工业界最佳实践：**WriteBack + 强制 WriteBack 策略 + BBU 健康监控**。一旦 BBU 进入学习周期或失效，立即切换为 WriteThrough 避免数据风险。

## 网络配置

书里点到两个关键点：

1. **MySQL 对网络延迟敏感**——因为每次查询都是往返延迟
2. **反向 DNS 查找是常见陷阱**​ → 启用 `skip_name_resolve` 消除该延迟

📌 **洞见**：在现代云环境，网络配置的复杂性远超书里描述：

**高并发连接的端口耗尽问题**：

```
# 扩大本地端口范围
echo "1024 65535" > /proc/sys/net/ipv4/ip_local_port_range
# 启用 TIME_WAIT 复用
echo 1 > /proc/sys/net/ipv4/tcp_tw_reuse
```

**网卡中断亲和性**（多队列网卡场景）：

- 禁用 `irqbalance`，将网卡中断手动绑定到专用核心
- 避免网卡中断和业务线程争抢同一个 CPU

**RDMA / 高性能网络**：对于跨节点数据同步（如 Group Replication、InnoDB Cluster），**25Gbps+ 网络 + RDMA**​ 能显著降低复制延迟。

**云环境特别提示**：云上 MySQL 的网络性能受实例类型限制。比如 AWS RDS 的"突发网络性能"机制可能导致网络带宽骤降——选型时必须确认**基线网络带宽**，而不是峰值。

## 选择文件系统

书里的结论：**XFS 是大容量、大规模数据库的强推荐；ext4 对中大规模也够用；ZFS/Btrfs 因内存消耗大不推荐用于 MySQL**。

MySQL 官方文档和 Arm 调优指南都确认：**XFS 是一个好的起点，ext4 是另一个不错的选择**。

📌 **洞见**：2026 年的工业实践细化：

|文件系统|适用场景|挂载选项|
|---|---|---|
|**XFS**​|生产默认选择，特别是 > 500GB 数据|`noatime,nodiratime`|
|**ext4**​|中小规模（< 500GB），或内核兼容性要求|`noatime,data=writeback`|
|**ZFS**​|需要快照/压缩/去重，且有充足内存|需精心调校 ARC|
|**Btrfs**​|不推荐生产 MySQL|——|

**通用挂载优化**：

```
# /etc/fstab 示例
/dev/nvme0n1p1 /var/lib/mysql xfs defaults,noatime,nodiratime 0 2
```

`noatime` 的作用：消除每次读操作都更新文件访问时间带来的元数据写。对于数据库这种"读多写少"的场景，这个优化能减少 5-10% 的不必要 I/O。

> 💡 **ZFS 的争议**：书里说不推荐，但现代工业界有不同声音。ZFS 的 ARC 缓存、透明压缩、快照能力对 MySQL 备份非常友好。如果你的服务器有充足内存（1TB+），ZFS + 调小 ARC 上限（`zfs_arc_max`）是个可行方案。但对于常规生产环境，**XFS 仍是风险最低的选择**。

## 选择磁盘队列调度器

这是本章最容易"过时"的小节，必须结合 2026 年的现状来讲。

书里针对 HDD 时代的建议是：**用 noop 或 deadline，绝不要用 CFQ**。

📌 **2026 年更新视角**：

|存储设备|推荐调度器|原因|
|---|---|---|
|**HDD（旋转盘）**​|`mq-deadline`|需要调度器优化寻道|
|**SATA SSD**​|`mq-deadline` 或 `none`|SSD 自带并行能力|
|**NVMe SSD**​|`none`（即 noop）|硬件自身做队列管理，软件调度反而增加延迟|
|**云块存储**​|通常默认即可|云端调度器影响被虚拟化层屏蔽|

**检查和设置**：

```
# 查看当前调度器
cat /sys/block/nvme0n1/queue/scheduler
# 输出示例：[none] mq-deadline kyber bfq

# 临时切换到 none（NVMe）
echo none > /sys/block/nvme0n1/queue/scheduler

# 永久生效（udev 规则）
cat > /etc/udev/rules.d/60-io-scheduler.rules <<'EOF'
ACTION=="add|change", KERNEL=="nvme[0-9]*n[0-9]*", ATTR{queue/scheduler}="none"
ACTION=="add|change", KERNEL=="sd[a-z]", ATTR{queue/scheduler}="mq-deadline"
EOF
```

📌 **洞见**：Arm 官方指南明确指出——"在云环境运行 MySQL 时，磁盘调度算法通常设置为 noop 或类似的极简调度器，这通常是好的设置，无需调整"。这意味着**在云上，你大概率不需要动调度器**。调度器调优是**物理机 + 本地 SSD/NVMe**​ 场景下的杠杆。

## 内存和交换

这一节是生产环境的"生死线"。

### 核心问题：swap 必须尽可能避免

书里讲得非常透彻：**MySQL 被设计为"几乎所有处理都在内存中完成"**。一旦发生 swap：

- 页面无法载入 buffer pool
- 脏页刷新增加
- redo log 拥塞
- **所有处理都变成磁盘速度 → 实质上是服务失败**

内存和磁盘的速度差距是**数千到数万倍**——这个差距意味着哪怕只有少量 swap，MySQL 的延迟也会从微秒级飙到毫秒级甚至秒级。

### 工业级配置

```
# 1. 降低 swappiness（CentOS/RHEL 7+, Ubuntu 18.04+）
vm.swappiness = 1  # 范围 0-100，1 是 MySQL 生产的标准值

# 2. 禁用透明大页（THP）—— 这是 2026 年工业界共识
echo never > /sys/kernel/mm/transparent_hugepage/enabled
echo never > /sys/kernel/mm/transparent_hugepage/defrag

# 3. 提高文件描述符限制
# /etc/security/limits.conf
mysql soft nofile 65535
mysql hard nofile 65535

# 4. 增加最大进程数
mysql soft nproc 65535
```

📌 **关于 vm.swappiness=1 的洞见**：

- `swappiness=0` 在旧内核意味着"尽量不 swap"，但内存紧张时仍会 swap
- `swappiness=1` 是现代内核（3.x+）的推荐值——保留极少量的 swap 意愿，避免 OOM Killer 激进杀进程
- 某些极端场景下，DBA 会完全禁用 swap（`swapoff -a`），但这有 OOM 风险，**不推荐**

### 透明大页（THP）必须禁用

📌 **这是书里没充分展开、但 2026 年工业界视为"铁律"的配置**。THP 会导致 MySQL 在运行时出现周期性的、难以解释的延迟 spike——因为内核在后台做 2MB 大页的 compact。Apress 的一个真实案例：MySQL NDB 集群出现超过 1 分钟的停顿，最终 root cause 是 Linux 内存碎片化触发了 memory compaction，而 THP 加剧了碎片化。

**正确的做法**：

```
# 持久化禁用（推荐用 tuned 或 systemd 服务）
echo never > /sys/kernel/mm/transparent_hugepage/enabled
echo never > /sys/kernel/mm/transparent_hugepage/defrag
```

但**显式使用 hugetlbfs 大页**（非 THP）对 InnoDB buffer pool 是有益的——它能减少 TLB miss。Arm 官方文档证实："MySQL 可以从使用大内存页中受益，特别是当 InnoDB buffer pool 很大时"。

### 内存分配器

书里提到：**用 tcmalloc 或 jemalloc 替换 glibc 内置的 malloc 是提升内存访问速度的最佳方法之一**。2026 年 Percona Server 8.0 已经内置了 jemalloc 内存分配性能分析功能，说明这个实践已经被主流 MySQL 分支采纳。

## 操作系统状态

这一节书里讲的是监控和预防。核心是"用工具看清系统正在发生什么"。

### 关键监控维度

1. **CPU 状态**：`top`、`mpstat -P ALL 1`
2. **内存和 swap**：`free -m`、`vmstat 1`、`sar -r 1`
3. **磁盘 I/O**：`iostat -x 1`（看 `%util`、`await`、`svctm`）
4. **进程级 I/O**：`pidstat -d 1`
5. **网络**：`sar -n DEV 1`、`netstat -an | grep :3306 | wc -l`
6. **内核级瓶颈**：`perf top`、`perf record`

### 关键阈值

📌 **洞见**：监控的真正价值不在于"看数字"，而在于**建立基线 + 设置报警**：

- `iowait > 20%` → I/O 瓶颈信号
- `si/so` (swap in/out) > 0 → 内存压力信号
- `load average` 持续 > CPU 核心数 × 2 → CPU 饱和
- `Innodb_buffer_pool_wait_free` > 0 → buffer pool 不够或 flush 跟不上

### NUMA 状态检查

```
numactl --hardware  # 查看 NUMA 节点分布
numactl --show      # 查看当前进程的 NUMA 策略
```

### 透明大页状态

```
cat /sys/kernel/mm/transparent_hugepage/enabled
# 必须是 [never]，否则有延迟 spike 风险
```

## 小结

这一章表面讲的是"硬件和 OS 怎么选"，深层传递的是**可靠性工程的第一性原理**：

**1. 瓶颈驱动，而非配置驱动**

不要抄"最优参数清单"。先测量，识别瓶颈在 CPU、内存、I/O 还是网络，再针对性优化。Oracle 的官方建议优先级非常清晰：**OS 卫生 → MySQL 变量 → SQL/索引**。

**2. 内存是用来消除 I/O 的，不是用来装数据的**

这个思维转换决定了你怎么看待 `innodb_buffer_pool_size`——它的目标是覆盖**工作集**，而不是总数据量。测量工作集、监控 buffer pool 命中率，比死记"50-75% 内存"更有用。

**3. 2026 年的硬件现实**

- **NVMe 时代**：默认的 `innodb_io_capacity=200` 是浪费钱，必须调到 5000-20000
- **云环境**：调度器通常不用调，网络带宽和 IOPS 配额才是真瓶颈
- **多核时代**：MySQL 8.0 对多核的支持已显著增强，但仍要重视单核主频

**4. 操作系统调优的本质是"消除反模式"**

- ❌ swap → ✅ `vm.swappiness=1`
- ❌ THP → ✅ `transparent_hugepage=never`
- ❌ CFQ 调度器 → ✅ `none` (NVMe) 或 `mq-deadline` (SATA SSD)
- ❌ atime 更新 → ✅ `noatime` 挂载选项
- ❌ DNS 反向解析 → ✅ `skip_name_resolve`

**5. RAID 10 + 企业级 SSD + BBU 写缓存**​ 仍是写密集 MySQL 的黄金组合。但云上要调整为：**本地 NVMe + 多副本持久化**（如 EBS io2 + 多 AZ 部署）。

**6. 监控是调优的闭环**

没有 `iostat`、`perf`、`fio`、Prometheus 的反馈，所有调优都是盲人摸象。Percona 的参考架构里，LVM 快照备份 + 监控是标配——这提醒我们：**调优不是一次性工作，而是持续循环**。

> 💡 **贯穿全章的洞见**：操作系统和硬件优化，本质上是**为 MySQL 创造一个"可预测的延迟环境"**。CPU 要快且稳、内存要足且不 swap、I/O 设备要低延迟高 IOPS、网络要不丢包低抖动。当这个底座稳固了，MySQL 自身参数调优（第 5 章）和 SQL/索引优化（后续章节）才能发挥真正威力。**底座不稳，再精妙的 MySQL 调优都是空中楼阁**——这正是为什么本书把"操作系统和硬件优化"放在"服务器性能调优"章节之前的第一性原理。

📌 **给读者的实践建议**：

1. 在新服务器上线前，用 `fio` 测 IOPS、用 `sysbench` 测基线 QPS
2. 部署时固化 OS 层配置（swappiness、THP、调度器、文件描述符）
3. 配置 Prometheus + Grafana 监控栈，建立性能基线
4. 每次变更只改一个变量，用基准测试验证效果
5. 定期（季度）回顾性能趋势，预防式扩容

这就是"SRE 视角"的硬件和 OS 优化——不是应付故障的补丁，而是**构建可持续、可预测、可观测的数据库基础设施**的系统工程。
