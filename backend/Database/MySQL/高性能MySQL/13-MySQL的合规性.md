
# 第 13 章　MySQL 的合规性——读书笔记

> 💡 这一章的本质，不是带你逐条背诵 SOX、PCI DSS、HIPAA 的法条，而是建立一个**第一性原理**：合规性不是一套"合规功能清单"，而是一种**可证明的控制体系**——你能向审计方证明"谁、在什么时间、对什么数据、做了什么、为什么有权限做"的完整证据链。Silvia Botros 和 Jeremy Tinley 在开篇就点明：DBA 的工作不只是让数据跑得快，更要"帮助企业保护数据，并使数据符合法律要求，或获得对企业至关重要的监管认证"。
> 
> 正如书中强调的——**"合规性的构建是一个持续的过程，在需要的时候不容易'添加'"**。这句话揭示了合规工程的全部哲学：合规是架构的基因，不是上线前的补丁。2026 年工业界的现实进一步验证了这一点：SOC 2 Type II 审计周期通常为 6-12 个月，重点验证系统可用性（SLA≥99.95%）、数据完整性（通过 Checksum 校验）及隐私保护（符合 GDPR 要求）——这意味着你必须在日常运维的每一天都活得像在审计中，而非审计前突击。

---

## 🎯 本章核心脉络

这一章埋下了一条主线——**合规性 = 技术控制 + 流程纪律 + 证据留存**：

1. **合规的本质是 GRC**——治理（Governance）、风险管理（Risk management）、合规性（Compliance）三位一体
2. **主要合规框架各有侧重**——SOC 2 看整体控制、SOX 看财务、PCI DSS 看卡数据、HIPAA 看健康数据、FedRAMP 看政府、GDPR/Schrems II 看欧盟个人数据主权
3. **机密信息管理是地基**——密钥、凭据、敏感字段的存储与轮换
4. **角色与数据分离是核心控制**——基于角色的访问控制（RBAC）+ 基于风险的数据库隔离
5. **跟踪变更是合规的命脉**——审计日志 + Schema 版本控制 + 用户生命周期管理
6. **备份恢复过程必须可证明**——加密备份、跨区域容灾、定期恢复演练
7. **云平台的合规认证不能替代你的合规责任**——这是 2026 年最容易被误解的一点

## 什么是合规性

### 第一性原理视角

书中将合规性置于 **GRC（Governance、Risk management、Compliance）**​ 框架下理解：它们是"一些原则、流程和法律，用于指导企业如何评估和优先考虑其资产的风险，以及如何遵守个人或健康数据处理和传输的法律法规"。

📌 **洞见 1：合规是"可证明的控制"，不是"功能的堆砌"**

常见的认知误区：以为"开启了 SSL、装了审计插件、配置了 RBAC"就等于合规。但审计方真正审查的是：

- 这些控制是否**持续生效**（而非上线当天）
- 是否有**证据链**（日志、审批、演练记录）
- 是否有人**定期复核**（权限回收、账号清理）
- 是否有**异常响应**（告警、处置、复盘）

📌 **洞见 2：合规控制必须"内置"而非"外挂"**

书中明确指出："合规性的构建是一个持续的过程，在需要的时候不容易'添加'"。这意味着：

- 数据库设计阶段就要考虑数据分类与隔离
- 账号体系设计阶段就要考虑角色与职责分离
- CI/CD 流水线设计阶段就要考虑凭据扫描与审计
- 备份策略设计阶段就要考虑加密与异地容灾

**事后补合规的代价**：

- Schema 重构以隔离敏感数据
- 应用代码改造以支持字段级加密
- 历史数据迁移以满足"被遗忘权"
- 审计日志缺失导致无法证明历史操作

📌 **洞见 3：合规是持续的，而非项目制的**

SOC 2 Type II 要求审计周期通常为 6-12 个月——这意味着你的控制体系必须在这 6-12 个月中持续有效，而非审计前突击。这要求：

- 自动化控制（策略即代码）
- 持续监控与告警
- 定期的渗透测试与漏洞扫描
- 季度的访问复核与账号清理

## 服务组织控制类型 2（SOC 2 Type II）

SOC 2 是一组合规性控制要求，服务组织可以使用这些控制来报告其与**安全性、可用性、处理完整性、机密性和隐私性**相关的实践。

📌 **洞见：SOC 2 Type II 对数据库工程师的具体要求**

书中明确指出，希望获得 SOC 2 认证的组织中的数据库工程师需要在以下方面具有良好的实践经验：

- **数据库变更管理**
- **备份和恢复过程**
- **管理对数据库实例的访问**

**工业界 SOC 2 Type II 的数据库控制要点**：

- 审计周期通常为 6-12 个月
- 重点验证系统可用性（SLA≥99.95%）
- 数据完整性通过 Checksum 校验
- 隐私保护需符合 GDPR 要求

> 💡 **关键认知**：SOC 2 Type II 不仅看"你有什么控制"，更看"这些控制在长时间内是否持续有效"。这是它与 SOC 2 Type I（仅看某一时点）的根本区别。

## 萨班斯-奥克斯利法案（SOX）

2002 年发布的 SOX 法案针对上市公司，要求：

- 记录所有影响财务报表的操作
- 审计范围：财务相关的数据库操作
- 保留期限：**7 年**

📌 **洞见：SOX 对 MySQL 的具体落地**

- **审计日志保留 7 年**：要求 MySQL 审计日志必须归档到长期存储（如 S3 Glacier、对象存储冷归档）
- **权限变更追踪**：所有 GRANT/REVOKE 操作必须可追溯到具体审批
- **Schema 变更版本化**：财务相关表的 DDL 变更必须有代码审查和审批记录
- **职责分离**：DBA 不能同时拥有应用代码的部署权限（防止"自己改自己审"）

> ⚠️ **金融行业的特殊要求**：JR/T 0072-2012 金融行业信息系统信息安全等级保护测评指南，对金融行业数据库提出更细化的合规要求。

## 支付卡行业数据安全标准（PCI DSS）

PCI DSS 是针对支付卡数据的合规标准：

- 要求：记录所有对 cardholder data 的访问
- 审计范围：**所有数据库操作**
- 保留期限：**至少 1 年**
- 仅允许必要端口开放（如 3306 仅对内网 IP 开放）

📌 **洞见 1：PCI DSS 下的 MySQL 表设计范式**

```
-- 符合 PCI DSS 的支付表设计
CREATE TABLE payment_transactions (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  card_number VARBINARY(255) NOT NULL COMMENT 'AES加密存储',
  expiration_date VARBINARY(255) NOT NULL,
  cvv VARBINARY(255) NOT NULL,
  merchant_id INT UNSIGNED NOT NULL,
  amount DECIMAL(12,2) NOT NULL,
  transaction_time DATETIME(6) NOT NULL,
  INDEX idx_merchant (merchant_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='符合 PCI DSS 要求的支付交易表';
```

**关键原则**：

- 敏感数据使用 VARBINARY + **应用层加密**
- CVV 等最敏感字段**绝不在数据库中存储明文**
- 金额数据用 DECIMAL 而非 FLOAT（避免精度丢失）

📌 **洞见 2：PCI DSS v4.0 的纵深防御**

"通过 SSL 保传输、TDE 保静态、应用加密保内容、KMS 保管钥"的纵深防御策略：

- **传输层**：强制 TLS 1.2+
- **存储层**：TDE（透明数据加密）
- **应用层**：敏感字段 AES 加密
- **密钥层**：KMS/Vault 集中管理，绝不硬编码

> ⚠️ **常见误区**：
> 
> - ❌ 误以为 `PASSWORD()` 函数可用于业务数据加密（它只是弱哈希，仅用于账户认证）
> - ❌ 误以为 TDE 能防止 SQL 注入（TDE 只保护磁盘数据）
> - ❌ 误以为加密后就无需访问控制（加密是最后一道防线）

## 健康保险可携带性和责任法案（HIPAA）

1996 年发布的 HIPAA 针对受保护健康信息（PHI）：

- 强制数据库启用透明数据加密（TDE）
- 限制 PHI 数据出口至授权 API
- 要求记录个人数据的访问和处理

📌 **洞见：HIPAA 下的 MySQL 合规要点**

- **TDE 是强制要求**：使用 InnoDB 表空间加密（`ENCRYPTION='Y'`）
- **传输加密**：强制 TLS
- **访问审计**：所有 PHI 表的访问必须记录
- **最小权限**：基于角色精细授权，业务账号绝不该有 `information_schema` 或 `mysql` 库权限
- **数据脱敏**：对敏感字段做实时脱敏，防止广泛读取权限导致 PHI 暴露

## 联邦风险和授权管理计划（FedRAMP）

FedRAMP 是美国联邦政府的云安全授权计划：

- AWS 提供 FedRAMP 等 20+ 认证包
- 用户可通过 AWS Artifact 获取合规报告
- 要求云数据库通过 ISO 27001、SOC 2 等认证

📌 **洞见：FedRAMP 对云 MySQL 的特殊要求**

- 云平台必须通过 FedRAMP 授权
- 数据必须存储在美国境内
- 加密密钥必须由美国实体管理
- 所有访问必须可审计并留存

## 通用数据保护条例（GDPR）

GDPR 是欧盟 2016 年推出的个人数据保护条例：

- 要求：记录个人数据的访问和处理
- 保留期限：根据数据处理目的确定
- 核心权利：**被遗忘权**（用户数据可删除）、**数据可移植权**

📌 **洞见 1：GDPR 对 MySQL 架构的深远影响**

1. **数据分类与标记**：必须能识别哪些表/列包含欧盟公民个人数据
2. **被遗忘权的技术实现**："加密 + 密钥销毁"是实现"删除"的有效技术手段——销毁特定用户的加密密钥，等价于删除其数据
3. **数据主权**：欧盟公民数据必须存储在欧盟境内
4. **访问审计**：涉及个人数据的操作必须记录

📌 **洞见 2：GDPR 与 Schrems II 的数据主权挑战**

## Schrems II

2020 年，欧盟司法法院裁决了欧盟和 Facebook 爱尔兰分部之间的一桩案件，这项通常被称为 Schrems II 的裁决对数据跨境传输产生了深远影响。

📌 **洞见：Schrems II 判决的核心冲击**

- **背景**：Schrems II 判决质疑了欧盟-美国之间的数据跨境传输机制（Privacy Shield）
- **影响**：欧盟公民的个人数据若要传输到美国，必须确保美国接收方提供与欧盟等同的保护水平
- **对 MySQL 架构的含义**：
    - 欧盟用户数据 → 必须存储在欧盟区域的数据库实例
    - 跨大西洋复制 → 需要评估接收方的法律保护水平
    - 美国云厂商的欧洲区域 → 需通过 EU Data Boundary 等机制确保数据不出境
    - **区域可用性的战略意义**：出于合规性原因进行分片，按数据主权边界分片部署

> 💡 **工业实践**：全球性 SaaS 企业现在通常采用"数据主权分片"策略——按用户地理区域分片，确保每个区域的数据物理存储在对应司法管辖区内。Vitess 等工具的分片能力在此场景下发挥关键作用。

## 建立合规控制体系

### 机密信息管理

这是合规控制体系的技术地基。书中给出的核心原则：

📌 **洞见 1：机密信息的生命周期管理**

**1. 不要跨服务共享数据库凭据**

"不要共享用户"——不要跨服务共享数据库凭据。每个应用程序组件都应创建为此独立创建的、权限被严格约束的专属账户。

**2. 不要在代码仓库中提交生产数据库凭据**

"不要在代码仓库中提交生产数据库凭据"——一种常见的做法是在合并一个 pull 请求之前，扫描代码库寻找潜在的机密字符串（GitHub 等代码仓库托管服务可以实现）。

**3. 确保密码始终以加密方式而不是以明文形式存储**

"确保密码始终以加密方式而不是以明文形式存储"——机密信息的长度做了限制，如果想存储比数据库的用户和密码对更长的内容，可能会导致意外。

**4. 密钥管理的工程化**

2026 年工业界的标准做法：

- 使用 AWS KMS 或 HashiCorp Vault 集中管理加密密钥
- 密钥由 KMS/Vault 管理，严禁硬编码于配置文件或代码中
- 建立自动化的密钥轮换机制（如每 90 天轮换）
- 密钥与数据分离存储

```
-- MySQL 8.0+ 的密钥环插件配置
INSTALL PLUGIN keyring_file SONAME 'keyring_file.so';
SET GLOBAL keyring_file_data = '/secure/path/keyring';
```

**5. 传输层与静态数据加密**

"数据传输与静态数据加密：保障数据全生命周期机密"：

- **传输中**：在 MySQL 服务器端配置 TLS/SSL，使用有效证书，并强制所有客户端连接启用加密
- **静态**：为数据库所使用的云硬盘启用服务端静态加密，对于备份文件也必须启用其服务端加密选项

> ⚠️ **纵深防御的层级**：
> 
> - SSL 保传输
> - TDE 保静态
> - 应用加密保内容
> - KMS 保管钥

### 角色与数据分离

📌 **洞见 1：基于角色的访问控制（RBAC）是合规的核心**

"权限管理不应直接针对用户，而应通过角色进行中转"：

```
-- 创建角色
CREATE ROLE 'data_reader', 'data_writer', 'data_admin';

-- 为角色授权
GRANT SELECT ON app_db.* TO 'data_reader';
GRANT INSERT, UPDATE, DELETE ON app_db.* TO 'data_writer';
GRANT ALL PRIVILEGES ON app_db.* TO 'data_admin';

-- 将角色授予用户
GRANT 'data_reader' TO 'app_web'@'10.20.%';
GRANT 'data_writer' TO 'app_worker'@'10.20.%';
```

**Azure 等现代云数据库的最佳实践**：

- 为每个应用程序组件创建专用数据库用户账户
- 使用 GRANT 语句仅为特定数据库和表分配必要的权限
- 为读密集的 Web 层查询、写密集的后台处理和管理任务定义单独账户
- 定期审查和审计权限分配，删除未使用的账户
- 限制服务器管理员的使用为"break-glass"场景（紧急打破玻璃）

📌 **洞见 2：基于风险的数据库隔离**

"基于数据泄露将给企业或客户带来的风险等级对数据进行分离"：

- **出于合规性原因进行分片**：按合规要求隔离数据
- 高风险数据（PCI、PHI、PII）存储在独立数据库实例
- 独立实例拥有更严格的控制：更强的加密、更细的审计、更频繁的访问复核

📌 **洞见 3：独立的数据库用户**

每个服务、每个组件、每个运维人员都应有独立账户：

- 应用服务 → 专用应用账号（如 `app_web`、`app_worker`）
- 监控 → 专用只读账号（如 `monitor`）
- 备份 → 专用备份账号（如 `backup`）
- DBA 运维 → 个人账号 + 紧急 `break-glass` 账号

> 💡 **账号清理策略**：建议设置"删除六个月内未连接过数据库的用户"的策略，定期清理僵尸账号。

### 跟踪变更

"很多合规性法规都附带了跟踪变更的控制措施"——这是合规审计中最核心的证据链。

📌 **洞见 1：审计日志的工程化落地**

**MySQL 审计能力的现状**：

- MySQL 社区版默认无合规审计能力，需手动安装 `server_audit.so` 插件
- MySQL 企业版用 `audit_log`
- 社区版可选 MariaDB Audit Plugin 或 Percona Audit Log Plugin

**生产级审计配置**：

```
-- 企业版审计插件配置
SET GLOBAL audit_log_policy = ALL;
SET GLOBAL audit_log_format = NEW;
SET GLOBAL audit_log_rotate_on_size = 1073741824;  -- 1GB 轮转
SET GLOBAL audit_log_rotations = 365;  -- 保留 1 年
SET GLOBAL audit_log_strategy = ASYNCHRONOUS;  -- 异步写入，降低性能影响
```

**审计日志的合规要求**：

|合规标准|审计要求|保留期限|
|---|---|---|
|PCI DSS|记录所有对 cardholder data 的访问|至少 1 年|
|SOX|记录所有影响财务报表的操作|7 年|
|GDPR|记录个人数据的访问和处理|根据数据处理目的确定|

📌 **洞见 2：审计日志的防篡改与长期归档**

审计日志必须满足"**能回溯、不可删、防篡改**"：

1. **独立存储**：日志路径不能在 datadir 下，避免 MySQL 重启时被清空
2. **防篡改**：对审计日志文件启用 `chattr +a`（append-only）
3. **集中化**：实时流式传输至独立的日志分析平台（如 SIEM），以防攻击者篡改本地日志
4. **三级存储策略**：
    - 热存储：最近 7 天日志保留在本地磁盘
    - 温存储：30 天内日志存储在 NAS 或对象存储
    - 冷存储：6 个月以上日志归档到专用备份系统
5. **完整性校验**：定期 `sha256sum` 审计日志并归档哈希值

**AWS RDS 的云原生审计方案**：

- 启用 RDS Advanced Auditing（基于 MariaDB Audit Plugin）
- 审计日志自动发布到 Amazon CloudWatch Logs
- `SERVER_AUDIT` 选项被设置为 `FORCE_PLUS_PERMANENT`——插件会被强制加载且无法运行时卸载
- 可配置 CloudWatch Logs 的数据保留策略，或导出到 S3 进行低成本长期存储

📌 **洞见 3：Schema 变更的版本控制**

"Schema 变更的版本控制"是合规控制的关键环节：

- 所有 DDL 变更必须经由版本控制系统（如 Git）
- 使用 Flyway、Liquibase 等数据库迁移工具
- 每次变更有代码审查、审批记录、执行日志
- 可回溯到任意历史版本

📌 **洞见 4：用户与权限变更追踪**

MySQL 自身不记录权限变更历史，但需实时抓快照：

```
-- 查账号拥有的全部权限
SHOW GRANTS FOR 'app_user'@'10.20.%';
-- 注意输出里有没有 WITH GRANT OPTION，有就是权限传染源

-- 查全局权限残留
SELECT * FROM mysql.user WHERE User='app_user' AND Host='10.20.%'\G;
-- 重点看 Super_priv、Shutdown_priv、File_priv 是否为 N

-- 查库/表级权限是否冗余
SELECT * FROM mysql.db WHERE User='app_user' AND Db='information_schema';
-- 业务账号绝不该有 information_schema 或 mysql 库权限
```

**权限审计的最佳实践**：

- 定期审查权限分配
- 移除未使用的账户
- 限制服务器管理员的使用为"break-glass"程序
- 删除六个月未连接的用户

---

### 备份和恢复过程

备份与恢复是合规体系中"最后一道防线"的可证明性。

📌 **洞见 1：合规级备份的四大要求**

1. **加密备份**：无论是存储在对象存储中的逻辑备份还是快照，都必须启用服务端加密选项
2. **跨区域容灾**：备份文件复制到异地对象存储，保留周期根据合规要求设定
3. **定期恢复演练**：季度性恢复演练，证明备份的可恢复性
4. **备份保留策略**：
    - 热备 7 天（快速恢复）
    - 温备 30 天（短期审计）
    - 冷备 1 年+（长期合规，SOX 要求 7 年）

📌 **洞见 2：备份的合规陷阱**

> ⚠️ **关键风险点**：
> 
> - 备份未加密 → 违反 GDPR/HIPAA/PCI DSS
> - 备份密钥与备份数据同址存储 → 密钥泄露等于数据泄露
> - 备份保留期不足 → 无法满足 SOX 7 年要求
> - 从未恢复演练 → 备份的有效性无法证明

📌 **洞见 3：云平台的合规责任共享**

**重要认知**：云平台通过 ISO 27001、SOC 2、FedRAMP 等认证，**但这不能替代应用层的合规责任**。

腾讯云等云厂商的信息安全说明明确指出：云数据库通过 ISO 27001、ISO 20000、可信云服务认证、信息安全等级保护（三级）等认证——但"本文档不作为国家或行业信息安全相关标准、要求参考文档"。

这意味着：

- **云厂商的责任**：物理安全、网络基础设施、托管服务的高可用
- **你的责任**：数据分类、账号管理、访问控制、审计配置、备份策略、应用层加密

> 💡 **Azure Well-Architected Framework 的最佳实践**：
> 
> - 创建专用数据库用户账户，按组件分离
> - 使用 Microsoft Entra ID 令牌认证替代密码认证
> - 消除公网暴露，使用私有端点
> - 设置 TLS 1.3 并强制 `require_secure_transport`
> - 使用 Key Vault 管理密钥，启用密钥托管与审计
> - 审计日志路由到 Azure Monitor / Log Analytics

## 小结

这一章表面讲的是"MySQL 如何满足合规"，深层传递的是**合规工程的第一性原理**：

**1. 合规是可证明的控制体系，不是功能清单**

合规性的构建是一个持续的过程，在需要的时候不容易"添加"。它要求：

- 技术控制（加密、审计、访问控制）
- 流程纪律（变更管理、账号生命周期、定期复核）
- 证据留存（日志归档、审批记录、演练报告）

**2. 主要合规框架的 MySQL 落地要点**

|框架|核心要求|MySQL 落地|
|---|---|---|
|SOC 2 Type II|安全、可用、完整、机密、隐私|变更管理 + 备份恢复 + 访问控制|
|SOX|财务数据操作可追溯|审计日志保留 7 年 + 权限变更追踪|
|PCI DSS|卡数据保护|字段级加密 + 审计日志保留 1 年 + 端口限制|
|HIPAA|PHI 保护|TDE 强制 + 传输加密 + 访问审计|
|FedRAMP|联邦云安全|美国境内存储 + 密钥美国管理|
|GDPR|个人数据保护|数据分类 + 被遗忘权（密钥销毁）+ 数据主权|
|Schrems II|跨境传输限制|数据主权分片 + 区域隔离|

**3. 机密信息管理的工程化**

- 每个服务独立账户，不共享凭据
- 凭据不入代码仓库（PR 合并前扫描）
- 密码加密存储，密钥由 KMS/Vault 管理
- 传输层强制 TLS，静态数据 TDE 加密
- 自动化密钥轮换

**4. 角色与数据分离**

- 基于角色的访问控制（RBAC）：角色中转，不直接授权用户
- 基于风险的数据库隔离：高风险数据独立实例
- 独立数据库用户：应用、监控、备份、运维各自独立
- 定期清理僵尸账号（如 6 个月未连接）

**5. 跟踪变更的完整证据链**

- 审计插件必须启用（企业版 audit_log 或社区版 server_audit）
- 审计日志防篡改（chattr +a）、集中化（SIEM）、三级存储
- Schema 变更版本化（Git + 迁移工具）
- 权限变更可回溯（快照抓取 + 定期审查）

**6. 备份恢复的可证明性**

- 加密备份 + 跨区域容灾
- 保留策略匹配合规要求（SOX 7 年、PCI 1 年）
- 季度性恢复演练
- 备份密钥与备份数据分离存储

**7. 云平台的合规责任共享**

> 💡 **贯穿全章的洞见**：云平台通过 SOC 2、ISO 27001 等认证，**但这不能替代你的合规责任**。云厂商负责物理安全和基础设施，你负责数据分类、账号管理、访问控制、审计配置、备份策略。合规的"最后一公里"永远在你自己手里。

2026 年工业界的合规工程趋势：

- **策略即代码**：用 Terraform、Ansible 将合规控制编码化
- **零信任架构**：Entra ID 令牌认证替代密码
- **数据主权分片**：按司法管辖区物理隔离数据
- **AI 驱动的异常检测**：Gemini Cloud Assist、DevOps Guru 等
- **机密信息管理标准化**：Vault、KMS、Secret Manager 成为标配

正如书中所强调的——DBA 的工作"不仅要为性能和业务的在线时间进行规划，还要为基础设施成本、灾难恢复和各种合规性需求做规划"。合规不是 DBA 的"额外工作"，而是 DBA 角色的核心内涵。优秀的合规架构，始于对适用法规的清晰识别（你的行业、位置、数据类型决定哪些法规适用），终于对技术控制、流程纪律、证据留存三者的精准落地——既不过度合规（浪费资源），也不欠合规（法律风险）。

📌 **给读者的实践清单**：

- ✅ 识别适用的合规框架（行业 + 位置 + 数据类型）
- ✅ 建立数据分类体系，标记敏感数据
- ✅ 启用 RBAC，通过角色授权，定期审查权限
- ✅ 每个服务使用独立数据库账户，杜绝共享凭据
- ✅ 凭据存入 KMS/Vault，绝不硬编码，自动化轮换
- ✅ 强制传输层 TLS 1.2+，静态数据 TDE 加密
- ✅ 启用审计插件（企业版 audit_log 或社区版 server_audit）
- ✅ 审计日志独立存储、防篡改（chattr +a）、集中化、长期归档
- ✅ 审计日志保留期匹配合规要求（SOX 7 年、PCI 1 年）
- ✅ Schema 变更版本化（Git + Flyway/Liquibase）
- ✅ 建立账号生命周期管理：入职/离职自动回收，6 个月未连接清理
- ✅ 备份加密 + 跨区域容灾 + 季度性恢复演练
- ✅ 备份保留策略：热备 7 天、温备 30 天、冷备 1 年+
- ✅ 数据主权分片：按司法管辖区物理隔离（GDPR/Schrems II）
- ✅ 高敏感字段应用层加密（AES）+ 数据库层 TDE 双重保护
- ✅ 利用云厂商合规认证（SOC 2、ISO 27001）但不能替代自身控制
- ❌ 不要以为"开启了 SSL + 装了审计插件"就等于合规
- ❌ 不要把审计日志存储在 datadir 下
- ❌ 不要使用 `PASSWORD()` 函数加密业务数据
- ❌ 不要将备份密钥与备份数据同址存储
- ❌ 不要跨服务共享数据库凭据
- ❌ 不要在代码中硬编码生产数据库凭据
- ❌ 不要忽视数据主权要求（欧盟数据必须存储在欧盟）

**合规是 MySQL 工程师生涯的必修课，课业精通，系统才能在审计面前从容不迫。一个优秀的合规架构，是用数据分类确定保护范围、用 RBAC 实现最小权限、用审计日志构建证据链、用加密与备份确保数据主权和可恢复性——这四者的精妙平衡，正是本章"MySQL 的合规性"的灵魂所在。理解了合规的本质，你就理解了为什么现代数据库合规工程（Vault 密钥管理 + server_audit 审计 + RBAC 角色控制 + TDE 透明加密 + 跨区域加密备份）全都围绕"可证明的控制"这一核心：因为合规不是技术问题，而是法律问题；不是功能清单，而是证据链。这正是为什么本章把"合规性"放在全书的倒数第二章——没有合规的数据架构，性能再高、扩展再强、云上部署再优雅，也只是在法律的刀尖上跳舞。合规是数据库工程的"安全带"，平时觉得累赘，事故时才知珍贵。两者合一，方能成就真正企业级的 MySQL 架构。**
