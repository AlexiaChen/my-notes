
# 第 5 章　优化服务器设置——读书笔记

> 💡 这一章的本质，不是给你一份"最优 my.cnf"，而是建立**第一性原理**：MySQL 的每个配置变量，本质上都是你对"这台服务器的资源禀赋、工作负载特征、可用性/一致性要求"所做的**​ Explicit Assumption（显式假设）**。配置的错误，从来不是"值填错了"，而是"假设错了"——你假设工作集能放进 buffer pool，但实际放不进；你假设存储能扛 5000 IOPS，但实际只能扛 2000；你假设 max_connections=5000 能抗高并发，但实际上它先把内存压垮了。
> 
> 所以本章真正的主题只有一个：**如何让配置与假设保持一致，并保持可验证、可回滚**。

---

## 🎯 本章核心脉络

Silvia Botros 和 Jeremy Tinley 作为 SRE 背景的作者，在这章埋了一条主线——**配置是可靠性工程的一部分，不是 DBA 的个人艺术**：

1. **理解配置的工作机制**（作用域、动态性、持久化）——这是"配置的语言"
2. **最小化配置**——只改你理解且有证据要改的变量
3. **按资源预算分配内存**（OS / 连接 / buffer pool / 其他）——这是数学，不是艺术
4. **按存储能力配置 I/O**（io_capacity、flush_method、redo log）——让 InnoDB 知道"磁盘有多快"
5. **按负载特征配置并发**（max_connections、thread_cache、innodb_thread_concurrency）
6. **安全与高级 InnoDB**——durability 与性能的权衡

Arm 的 MySQL 调优官方指南开篇就给出了 2026 年工业界的最强共识：**"In general, leave most MySQL settings at their defaults and change them only when you have a workload requirement, test result, profile, or observed bottleneck that supports the change."**​ 这句话应该贴在每位 DBA 的显示器上。

## MySQL 的配置是如何工作的

### 语法、作用域和动态性

MySQL 的系统变量有三个维度的属性，理解这三个维度是正确配置的前提：

**1. 作用域（Scope）**

- **GLOBAL**：影响整个服务器，新连接继承该值，已有连接不受影响
- **SESSION**：仅影响当前会话
- **两者皆有**：GLOBAL 设默认值，SESSION 可覆盖

**2. 动态性（Dynamic）**

- **动态变量**：可在运行时通过 `SET` 修改，立即生效
- **只读变量**：只能在启动时通过配置文件修改，需重启生效

**3. 持久化（Persistence）**——这是 MySQL 8.0 带来的范式转变

MySQL 8.0 引入了 `SET PERSIST` 和 `SET PERSIST_ONLY`：

```
SET PERSIST max_connections = 1000;  -- 立即生效 + 写入 mysqld-auto.cnf
SET PERSIST_ONLY innodb_log_files_in_group = 3;  -- 只写入文件，重启后生效
RESET PERSIST max_connections;  -- 从 mysqld-auto.cnf 移除
```

📌 **洞见**：`mysqld-auto.cnf` 是一个 JSON 格式文件，位于数据目录下，记录了每次持久化变更的**值、时间戳、操作用户、来源主机**——这意味着 MySQL 8.0 之后，配置变更是**可审计**的。这在合规要求严格的企业环境里是重大进步。

**配置优先级**（后面的覆盖前面的）：

```
编译默认值 → my.cnf → mysqld-auto.cnf (SET PERSIST) → 命令行参数
```

> ⚠️ **这个优先级关系是反直觉的陷阱**：`SET PERSIST` 的值会覆盖 `my.cnf` 里的值。如果你在 my.cnf 里写了 `max_connections=500`，但某人曾经 `SET PERSIST max_connections=2000`，那么重启后生效的是 2000 而非 500。排查"为什么我的配置不生效"时，**第一件事就是查 `SELECT * FROM performance_schema.persisted_variables`**。

### 持久化系统变量

📌 **洞见**：`SET PERSIST` 解决了 DBA 运维中的一个经典痛点——**配置漂移（configuration drift）**。在 8.0 之前，DBA 要做两件事：① `SET GLOBAL` 让变更立即生效 ② 手动编辑 my.cnf 让变更持久化。这两步经常不一致——要么忘了改 my.cnf 导致重启后回滚，要么 my.cnf 改错了导致重启失败。

8.0 之后，**`SET PERSIST` 是单一事实源**。但它也带来了新的运维纪律要求：

- my.cnf 应该作为"基线配置"纳入版本控制（Git）
- `mysqld-auto.cnf` 是运行时变更的累积记录
- 定期审查 `persisted_variables`，把经过验证的变更合并回 my.cnf，然后 `RESET PERSIST` 清理

### 设置变量的副作用

📌 **这是本章最容易被忽视、但工业界踩坑最多的一点**。修改一个变量，可能产生你没预料到的连锁反应：

- **修改 `innodb_buffer_pool_size`**：8.0 虽然支持在线调整，但调整过程涉及内存重新分配，大 buffer pool 的 resize 可能造成毫秒到秒级的停顿
- **修改 `innodb_io_capacity`**：会让 InnoDB 重新评估刷脏页速率，可能导致短期内 I/O 陡增
- **修改 `max_connections`**：每个连接预分配 `thread_stack`（默认 1MB）+ 潜在的各种 per-thread buffer，盲目调大可能直接 OOM
- **开启 `performance_schema` 的全部插桩**：可能引入 5-10% 的性能开销

> 💡 **SRE 视角的铁律**：任何生产环境的配置变更，必须遵循**"单次单变量 + 可观测 + 可回滚"**三原则。一次改 10 个变量，出问题时你不知道是哪个变量的副作用。

### 规划变量的更改

Oracle 的官方建议非常明确：配置变更应该有明确的触发条件——

- **workload requirement**（工作负载需求变化）
- **test result**（测试结果驱动）
- **profile data**（性能剖析数据）
- **observed bottleneck**（观测到的瓶颈）

这意味着：**不要"预防性调优"**。在没有证据的情况下改配置，本质是赌博。

## 什么不该做

书里这一节讲的就是配置的反模式。结合 2026 年的工业实践，我把它提炼为**五条禁忌**：

**❌ 禁忌一：盲目抄"优化 my.cnf"**

网上流传的各种"终极 my.cnf 优化模板"大多是毒药。Percona 的 2026 基准测试配置明确标注了"Tier-specific"（分等级），因为不同规格的机器需要不同的配置。盲目套用 256GB 内存机器的配置到 8GB 的机器上，必然崩盘。

**❌ 禁忌二：盲目调大 max_connections**

Oracle 工程师明确警告：**"Raising it blindly can cause memory pressure and make overload worse rather than better"**。每个连接都会消耗内存，max_connections 从 500 调到 5000，不是性能优化，是自杀。正确做法是配合 ProxySQL 或应用层连接池，让 5000 个应用连接收敛到 500 个 MySQL 连接。

**❌ 禁忌三：过度配置每连接缓冲区**

`sort_buffer_size`、`join_buffer_size`、`read_buffer_size` 都是**每连接分配**的。把它们从 256KB 调到 4MB，如果有 1000 个并发连接，内存消耗就从 256MB 飙升到 4GB。

**❌ 禁忌四：在云环境套用物理机配置**

云盘的 IOPS 是有配额限制的，`innodb_io_capacity` 设得比云盘实际能力高，只会导致 InnoDB 频繁尝试刷盘失败重试，反而降低性能。

**❌ 禁忌五：同时改多个变量**

违反"单次单变量"原则，出问题无法定位根因。

## 创建 MySQL 配置文件

### 最小化配置

📌 **这是本章最重要的洞见，没有之一**。

Arm 官方指南的原话："**In general, leave most MySQL settings at their defaults and change them only when you have a workload requirement, test result, profile, or observed bottleneck that supports the change.**"

MySQL 8.0+ 的默认值经过了 Oracle 工程团队在大量真实负载下的调优，**对绝大多数场景是合理且安全的**。最小化配置的核心思想是：

```
[mysqld]
# 只写你必须写的——基于证据才写的
datadir = /var/lib/mysql
socket = /var/lib/mysql/mysql.sock

# 如果服务器专用于 MySQL，让 InnoDB 自动配置关键参数
innodb_dedicated_server = ON

# 字符集（8.0 默认已是 utf8mb4，但显式声明更安全）
character_set_server = utf8mb4
collation_server = utf8mb4_0900_ai_ci

# 持久化 binlog（如果用作主库或需要 PITR）
log_bin = mysql-bin
binlog_format = ROW
sync_binlog = 1

# 显式指定数据目录和 socket
```

📌 **关于 `innodb_dedicated_server=ON` 的洞见**：

这是 MySQL 8.0 引入的"半自动调优"开关。开启后，InnoDB 会自动配置：

- `innodb_buffer_pool_size`：在内存 > 4GB 的机器上，自动设为**物理内存的 75%**
- `innodb_redo_log_capacity`：8.0.30+ 自动设为 4GB（8.4+ 也是自动配置）
- `innodb_flush_method`：根据存储类型自动选择

> ⚠️ 但要注意：**`innodb_dedicated_server` 的行为在不同 MySQL 版本间可能变化**。在 8.4+ 中它会自动配置 `innodb_buffer_pool_size` 和 `innodb_redo_log_capacity`。如果你显式设置了其中某个变量，MySQL 会打印警告"Option innodb_dedicated_server is ignored for xxx"——这是预期行为，不是错误。

**最小化配置的工程价值**：

1. **可审计**：my.cnf 里只有 20 行，DBA 一眼看懂
2. **可移植**：换机器、换版本，配置基本不用改
3. **可维护**：升级 MySQL 大版本时，最小化配置几乎不会与新默认值冲突
4. **安全**：避免了"过度配置"带来的隐性风险

## 检查 MySQL 服务器的状态变量

📌 **洞见**：状态变量（Status Variables）是配置决策的**唯一可靠依据**。在你打算修改任何配置前，先看状态变量告诉了你什么：

```
-- 连接相关
SHOW GLOBAL STATUS LIKE 'Threads_created';
SHOW GLOBAL STATUS LIKE 'Connections';
SHOW GLOBAL STATUS LIKE 'Threads_running';

-- Buffer Pool 效率
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read_requests';
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_reads';
-- 命中率 = 1 - (reads / read_requests)，应 > 99%

-- 刷脏页压力
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_wait_free';
-- > 0 表示 buffer pool 不够或 io_capacity 太低

-- 临时表落盘
SHOW GLOBAL STATUS LIKE 'Created_tmp_disk_tables';
SHOW GLOBAL STATUS LIKE 'Created_tmp_tables';
-- 比例过高说明 sort/join buffer 太小或 SQL 写法差
```

**第一性原理**：配置变更应该是"观察状态变量 → 形成假设 → 修改配置 → 验证假设 → 观察状态变量"这个闭环中的一环，而不是起点。

## 配置内存使用

### 每个连接的内存需求

这是最容易被低估的内存消耗源。每个 MySQL 连接会分配：

|缓冲区|默认值|说明|
|---|---|---|
|`thread_stack`|1MB|线程栈|
|`sort_buffer_size`|256KB-4MB|排序缓冲区|
|`join_buffer_size`|256KB-4MB|JOIN 缓冲区|
|`read_buffer_size`|128KB|顺序读|
|`read_rnd_buffer_size`|256KB|随机读|
|`tmp_table_size` / `max_heap_table_size`|16MB|内存临时表上限|

📌 **内存预算公式**：

```
总内存预算 = OS 预留 + 连接内存 + Buffer Pool + InnoDB 其他 + 全局缓存

其中：
- OS 预留：2-4GB 或物理内存的 5%（取较大值）
- 连接内存 = max_connections × (per-thread buffers 总和)
- Buffer Pool：剩余内存的 75-80%（专用机）
```

**反例计算**：如果 `max_connections=1000`，且每个连接的 per-thread buffer 总计 2MB，那么连接层就要吃掉 **2GB 内存**。这就是为什么"盲调 max_connections"是危险操作。

### 为操作系统保留内存

书里强调的黄金法则：**永远不要榨干物理内存**。OS 需要内存来：

- 文件系统缓存（即使你用了 O_DIRECT，OS 仍需缓存 InnoDB 文件描述符等元数据）
- 进程内存（mysqld 本身、监控系统、SSH 等）
- 内核数据结构
- **避免 swap**（详见第 4 章）

经验值：

- ≤ 8GB 物理内存：OS 预留 2GB 或 20%
- 8-64GB 物理内存：OS 预留 4GB 或 10%
- > 64GB 物理内存：OS 预留 4-8GB 或 5%
    

### InnoDB 缓冲池

`innodb_buffer_pool_size` 是**最重要的单个配置变量**，没有之一。它缓存数据页和索引页，目标就是第 4 章讲的"工作集"。

**配置策略**：

```
# 方案 A：专用机 + innodb_dedicated_server（推荐）
innodb_dedicated_server = ON
# 8.4+ 会自动将 buffer pool 设为物理内存的 75%

# 方案 B：手动指定（需要精细控制时）
# 例如 128GB 物理内存的专用机
innodb_buffer_pool_size = 96G  # 物理内存的 75%
```

**Buffer Pool 实例数**：当 buffer pool ≥ 1GB 时，应该分成多个实例以减少锁竞争：

```
innodb_buffer_pool_instances = 8  # 经验值：每 1GB buffer pool 一个实例，最多 64
```

每个实例至少 1GB，否则实例化的意义不大。Percona 的监控面板明确指出："**Higher values allow to reduce contention but also increase overhead**"——实例数不是越多越好。

📌 **洞见**：buffer pool 大小的真正判据不是"物理内存的 80%"，而是**"工作集大小 × 1.2，且不超过物理内存的 75%"**。回到第 4 章的"工作集"概念：

- 如果你的工作集是 60GB，物理内存是 128GB，那么 96GB 的 buffer pool 是浪费
- 如果你的工作集是 100GB，物理内存是 128GB，那么 96GB 的 buffer pool 会导致 ~4% 的读要落盘
- **正确做法**：监控 `Innodb_buffer_pool_read_requests` vs `Innodb_buffer_pool_reads`，让命中率 ≥ 99%

**NUMA 考量**：在多 NUMA 节点的服务器上，可以考虑通过 `numactl --interleave=all` 启动 mysqld，让 buffer pool 内存在各 NUMA 节点间交错分配，避免跨节点访问的延迟。

### 线程缓存

`thread_cache_size` 控制 MySQL 复用线程的数量，避免频繁创建/销毁线程的开销。

```
-- 判断是否需要增大 thread_cache_size
SHOW GLOBAL STATUS LIKE 'Threads_created';
SHOW GLOBAL STATUS LIKE 'Connections';
-- 如果 Threads_created / Connections > 1%，说明线程缓存命中率低
```

Oracle 官方文档指出："**It is useful for workloads with frequent short-lived connections**"。对于短连接频繁的应用（如 PHP-FPM 传统模式），`thread_cache_size=100` 是合理的；对于使用连接池的长连接应用（如 Java/HikariCP），线程缓存的意义就不大了。

## 配置 MySQL 的 I/O 行为

这是 8.0 时代变化最大的领域，也是书里内容最需要更新的部分。

### InnoDB 事务日志

**8.0.30 之前**：通过 `innodb_log_file_size` × `innodb_log_files_in_group` 控制 redo log 总大小。

**8.0.30 及以后**：引入 `innodb_redo_log_capacity`，**统一了 redo log 的容量管理**：

```
# 8.0.30+ 推荐写法
innodb_redo_log_capacity = 4G  # 写密集负载可设为 8G-32G

# 如果开启了 innodb_dedicated_server=ON，会自动配置为 4GB
# 写密集场景可以显式覆盖：
innodb_dedicated_server = ON
innodb_redo_log_capacity = 32G  # 显式覆盖，其他参数仍自动配置
```

📌 **洞见**：redo log 容量的本质是**"在 checkpoint 之间，InnoDB 能承受多少写"**。 redo log 越大：

- ✅ 减少 checkpoint 频率 → 减少写放大
- ✅ 写密集负载吞吐更高
- ❌ 崩溃恢复时间更长
- ❌ 占用更多磁盘空间

**经验法则**：

- 读多写少：4GB 足够
- 均衡 OLTP：8GB
- 写密集（如 IoT 数据接入、订单流）：16-32GB

### 日志缓冲区

`innodb_log_buffer_size` 控制 redo log 写入磁盘前的缓冲区大小。Percona 的 2026 基准配置设为 **64M**：

```
innodb_log_buffer_size = 64M
```

对于写密集事务（如批量 INSERT），较大的 log buffer 可以减少 redo log 的刷盘次数。但注意：只要 `innodb_flush_log_at_trx_commit=1`（全 ACID），每个事务提交仍然要刷盘，log buffer 大主要是减少**内部碎片**和**批量事务**的 I/O 次数。

### InnoDB 表空间

`innodb_file_per_table` 控制每个表是否使用独立的表空间文件（.ibd）：

```
innodb_file_per_table = 1  # 8.0 默认开启
```

📌 **洞见**：这个变量在 SSD 时代的重要性下降了，但仍然建议开启，原因有三：

1. **DROP TABLE 时能真正回收磁盘空间**（共享表空间 Drop 表后空间不释放）
2. **可以针对单个表做文件系统级操作**（如冷备份、迁移）
3. **TRUNCATE TABLE 性能更好**

但有一个例外：**海量小表场景**（如上万个表），使用独立表空间会导致文件系统 inode 耗尽和打开文件数暴增。这种场景可以考虑部分表使用共享表空间。

**表空间相关的重要变量**：

```
innodb_data_file_path = ibdata1:12M:autoextend  # 系统表空间
innodb_autoextend_increment = 64  # 自动扩展步长（MB）
```

### 其他 I/O 配置选项

这是 8.0 时代最重要的更新区域：

**1. `innodb_io_capacity` 和 `innodb_io_capacity_max`**

```
# NVMe SSD 的典型配置（Percona 2026 基准）
innodb_io_capacity = 2500        # 常规后台 I/O 速率
innodb_io_capacity_max = 5000    # 突发 I/O 上限
```

Oracle 官方解释："`innodb_io_capacity` tells InnoDB how much background I/O it may assume is available"，而 "`innodb_io_capacity_max` acts as the upper burst limit for background I/O"。

📌 **洞见**：这两个值的设定应该**基于你存储设备的实测 IOPS**，而非拍脑袋：

- HDD：200 / 400
- SATA SSD：2000 / 4000
- NVMe SSD：5000-10000 / 10000-20000
- 云盘：按云厂商承诺的 IOPS 配额 × 0.8（留余量）

**2. `innodb_flush_method`**

```
innodb_flush_method = O_DIRECT  # 绕过 OS 页缓存，避免双缓存
```

Percona 2026 基准明确使用 `O_DIRECT`。它的作用是让 InnoDB 直接 I/O 到存储设备，不经过 OS 的 page cache——因为 buffer pool 本身就是 InnoDB 的"页缓存"，OS 再缓存一次就是浪费内存。

**3. `innodb_flush_neighbors`**

```
innodb_flush_neighbors = 0  # SSD/NVMe 必设，HDD 可设为 1
```

HDD 时代，相邻页刷新有意义（减少寻道）；SSD 时代，随机写和顺序写性能差异不大，相邻页刷新反而浪费 CPU 和 I/O 带宽。

**4. `innodb_read_io_threads` 和 `innodb_write_io_threads`**

```
innodb_read_io_threads = 8
innodb_write_io_threads = 8
```

默认 4，对于现代多核服务器，8 是合理的起点。但 Oracle 工程师提醒："**MySQL 5.5 has async IO so very high values might not be needed**"——在支持 Native AIO 的平台上，这两个值不用设得过高。

**5. Doublewrite Buffer**

```
innodb_doublewrite = 1  # 必须开启，防止 partial page write
```

Percona 2026 基准明确标注："**Data corruption prevention**"。这是不可妥协的安全设置。

## 配置 MySQL 并发

并发配置是"盲调重灾区"。Oracle 工程师特别警告：**max_connections 并不直接提升性能**。

### 正确配置并发的哲学

**1. 用连接池收敛连接数**

```
max_connections = 500  # 后端 MySQL 的真实连接上限
wait_timeout = 300  # 5 分钟无活动则关闭
interactive_timeout = 300
connect_timeout = 10
```

然后在应用和 MySQL 之间加 **ProxySQL**​ 或 **MySQL Router**，让应用侧的 5000 个连接收敛到 MySQL 侧的 500 个连接。这是工业界标准做法。

**2. 线程池（Enterprise / Percona Server）**

如果用的是 MySQL Enterprise Edition 或 Percona Server，可以启用线程池：

```
# Percona Server
thread_handling = pool-of-threads
thread_pool_size = 16  # 等于 CPU 核心数
thread_pool_stall_limit = 200  # ms

# MySQL Enterprise
plugin-load-add = thread_pool.so
thread_pool_size = 16
```

线程池的作用是**用少量线程服务大量连接**，避免"线程爆炸"导致的上下文切换开销。

**3. `innodb_thread_concurrency`**

```
innodb_thread_concurrency = 0  # 0 表示不限，让 InnoDB 自己决定
```

在 5.5+ 版本中，设为 0 让 InnoDB 内部的调度器自己管理并发度，通常是最优解。

### 高并发下的内存陷阱

📌 **洞见**：高并发配置的关键矛盾是——**连接数 × per-thread buffer = 内存炸弹**。

解决之道：

1. 减小 per-thread buffer（但要监控 `Created_tmp_disk_tables` 比例）
2. 用连接池限制真实连接数
3. 用线程池减少线程数

## 安全设置

书里这一节涵盖了认证、加密、审计等安全相关变量。结合 2026 年的工业实践：

**1. 传输加密**

```
require_secure_transport = ON  # 强制使用 SSL/TLS 连接
```

**2. 敏感变量持久化的安全增强**

MySQL 8.0 引入了**持久化受限变量**的概念：某些敏感变量（如 `default_password_lifetime`）的持久化需要：

- `SYSTEM_VARIABLES_ADMIN` + `PERSIST_RO_VARIABLES_ADMIN` 权限
- **加密连接**
- 提供 `persist_only_admin_x509_subject` 指定的 SSL 证书

这是为了防止中间人攻击篡改持久化配置。

**3. 二进制日志安全**

```
binlog_format = ROW  # 行格式，最安全
binlog_row_image = MINIMAL  # 只记录变更的列 + 主键
sync_binlog = 1  # 每次事务提交都刷盘，防止 binlog 丢失
```

Percona 2026 基准明确使用这组配置，理由是"**Full ACID compliance**"。

**4. 文件权限**

```
secure_file_priv = /var/lib/mysql-files/  # 限制 LOAD DATA / SELECT ... INTO OUTFILE 的路径
local_infile = 0  # 禁用 LOCAL INFILE，防止攻击者读取客户端文件
```

## 高级 InnoDB 设置

这一节书里涵盖了一些进阶变量，结合 2026 年的工业实践：

### 1. 自适应哈希索引（AHI）

```
innodb_adaptive_hash_index = ON  # 默认开启
```

AHI 对**等值查询**（如主键查找、唯一索引查找）有显著加速。但在某些高并发写入场景，AHI 的维护会成为瓶颈。Percona Server 允许对 AHI 分区（`innodb_adaptive_hash_index_partitions`）来减少锁竞争。

### 2. 变更缓冲（Change Buffer）

```
innodb_change_buffering = all  # 默认，缓冲所有操作
```

变更缓冲对**非唯一二级索引**的更新有显著加速——把随机 I/O 转化为顺序 I/O。但在写密集且二级索引多的场景，change buffer 膨胀可能成为问题。

### 3. 刷脏页调优

```
innodb_max_dirty_pages_pct = 90  # 脏页比例上限
innodb_max_dirty_pages_pct_lwm = 10  # 低水位线，低于此值开始预刷
innodb_lru_scan_depth = 4000  # 每个 buffer pool 实例的 LRU 扫描深度
```

Percona 的测试显示，`innodb_lru_scan_depth=4000` 配合较大的 buffer pool，能有效减少 free list miss。

### 4. Purge 线程

```
innodb_purge_threads = 4  # 8.0 默认 4，可增加到 8
```

Purge 线程负责清理 undo log。在写密集且长事务频繁的场景，undo log 堆积会撑爆系统表空间，需要更多 purge 线程。

### 5. 重做日志写入线程

MySQL 8.4 起，`innodb_log_writer_threads` 默认开启（当 CPU ≥ 32 核时）。这个变量控制是否使用**专用的 redo log 写入线程**：

```
SHOW VARIABLES LIKE 'innodb_log_writer_threads';
```

在高写负载的多核服务器上，专用日志写入线程可以显著提升吞吐量。

### 6. 性能模式（Performance Schema）

```
performance_schema = ON
# 按需开启插桩，不要全开
performance_schema_instrument = 'statement/%=ON'
performance_schema_consumer_events_statements_history = ON
```

## 小结

这一章表面讲的是"服务器参数怎么配"，深层传递的是**SRE 视角的配置哲学**：

**1. 配置即假设，而非配方**

每个变量的设置，背后都是你对"工作集大小、存储 IOPS、并发连接数、一致性要求"的显式假设。配置出错的本质是假设出错。**最小化配置**的核心是——只对你理解且有证据要改的变量做显式设置，其余信任 MySQL 8.0 的合理默认值。

**2. 持久化机制改变了配置管理范式**

MySQL 8.0 的 `SET PERSIST` 让配置具备了**运行时可变性 + 跨重启持久性 + 可审计性**。现代运维流程应该是：

- my.cnf 作为基线，纳入 Git 版本控制
- 运行时通过 `SET PERSIST` 做的变更，定期审查并合并回 my.cnf
- 用 `performance_schema.persisted_variables` 做配置审计

**3. 内存预算是数学，不是艺术**

```
总内存 = OS 预留 + 连接内存 + Buffer Pool + InnoDB 开销
```

盲调 `max_connections` 或 `sort_buffer_size` 都是对这条公式的无知。

**4. I/O 配置必须与存储能力匹配**

`innodb_io_capacity` 不是"越大越好"，而是"等于你存储的真实 IOPS 能力"。在 NVMe 时代，`innodb_io_capacity=200` 的默认值是在浪费硬件；但在云盘环境，设得比配额高只会适得其反。

**5. 并发配置的核心是"收敛"而非"放大"**

`max_connections` 不直接提升性能，盲调只会引发内存危机。**正确做法是：连接池 + 线程池 + 合理的超时设置**，让 5000 个应用连接收敛到 500 个 MySQL 连接。

**6. 8.0.30+ 的新范式：让 InnoDB 自动配置**

`innodb_dedicated_server=ON` 让 InnoDB 自动配置 buffer pool（75% RAM）、redo log capacity、flush method。**在专用服务器上，这个开关 + 显式覆盖少数几个变量（如写密集时的 redo log capacity），是当前最优的配置策略**。

> 💡 **贯穿全章的洞见**：配置优化的第一性原理是——**测量，而非猜测**。状态变量（`SHOW GLOBAL STATUS`）告诉你瓶颈在哪，性能模式（第 3 章）告诉你时间花在哪，操作系统工具（第 4 章）告诉你资源瓶颈在哪。这三者的数据，才是配置变更的唯一合法依据。
> 
> 一个真实的工业级配置工作流：
> 
> 1. 新服务器上线 → `innodb_dedicated_server=ON` + 最小配置
> 2. 跑基准测试（sysbench）建立性能基线
> 3. 上线后监控状态变量和 Performance Schema
> 4. 发现瓶颈（如 buffer pool 命中率 < 99%）→ 针对性调整（如增大 buffer pool）
> 5. `SET PERSIST` 立即生效 + 持久化
> 6. 季度审查，把验证过的变更合并回 my.cnf
> 
> 这套方法论，把"配置"从"DBA 的艺术"变成了"工程的科学"——这正是本书 SRE 视角的精髓所在。

📌 **给读者的实践清单**：

- ✅ 专用机必开 `innodb_dedicated_server=ON`
- ✅ 8.0.30+ 用 `innodb_redo_log_capacity` 替代旧的 log file 参数
- ✅ `innodb_flush_method=O_DIRECT` + `innodb_flush_neighbors=0`（SSD/NVMe）
- ✅ `innodb_io_capacity` 按存储实测 IOPS 设定，不是拍脑袋
- ✅ `max_connections` 配合连接池，不要盲调
- ✅ 所有配置变更走 `SET PERSIST`，并定期审查 `persisted_variables`
- ✅ 变更前先查状态变量，变更后验证假设
- ❌ 不要抄网上的"万能优化配置"
- ❌ 不要一次性改多个变量
- ❌ 不要在不知晓副作用的情况下改只读变量

**配置的本质，是用声明式的变量去描述你对系统的理解。当你不再"调优"，而是"表达对系统的认知"时，你就从 DBA 进阶为了 SRE——这正是本书第 2 章所铺垫的可靠性工程理念，在第 5 章的具体落地。**
