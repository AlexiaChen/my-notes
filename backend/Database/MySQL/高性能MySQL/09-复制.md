
# 第 9 章　复制——读书笔记

> 💡 这一章的本质，不是教你"怎么搭主从"，而是建立一个**第一性原理**：MySQL 复制默认是异步的、基于二进制日志的逻辑复制——源库提交事务后写入 binlog，副本 IO 线程拉取 binlog 写入中继日志，SQL 线程回放中继日志。这条链路上**每一个环节都可能成为瓶颈，每一个环节也都对应着一种"用某种代价换取某种保证"的权衡**。
> 
> 正如 MySQL 8.4 官方文档开篇明义：复制默认是异步的（asynchronous by default），副本不需要永久连接到源来接收更新；它支持两种复制方式——传统的基于二进制日志文件位置的复制，以及基于全局事务标识符（GTID）的事务性复制。而如果需要同步复制，应该使用 NDB Cluster，而非基础复制。

---

## 🎯 本章核心脉络

Silvia Botros 和 Jeremy Tinley 在这一章埋下了一条主线——**复制是一致性、可用性、写入延迟、运维复杂度四方的持续博弈**：

1. **复制默认异步**——这意味着副本可能落后，意味着源库宕机可能丢数据，意味着所有"高级复制特性"都是在给异步复制"打补丁"
2. **GTID 是现代复制的基石**——它用事务性标识符替代文件位置，极大简化了故障切换
3. **复制格式默认 ROW**——MySQL 8.0.34 起 `binlog_format` 已弃用，未来版本将只支持 ROW
4. **多线程复制、半同步复制、延迟复制**——分别是为了解决"应用慢"、"丢数据"、"误操作"三大问题
5. **拓扑越简单越好**——主动/被动、主动/只读池是工业界主力，双主、环形、多源等复杂拓扑弊大于利
6. **复制监控与治理**——`Seconds_Behind_Source` 只是估算值，真正的延迟要用 pt-heartbeat 或 Performance Schema 观测

## 复制概述

### 第一性原理视角

MySQL 复制解决四个核心问题：

- **Scale-out**：把读负载分散到多个副本，提升整体读性能
- **数据安全**：副本可以暂停复制进程，在不影响源库的情况下运行备份
- **分析隔离**：在副本上做分析查询，不影响源的写入性能
- **异地分发**：为远程站点创建本地数据副本

📌 **洞见 1：复制不是备份**。这是本章最重要的认知锚点。复制提供的是**冗余（redundancy）**，而非**备份（backup）**：

- 源库执行 `DELETE FROM orders WHERE ...` 误操作——副本会忠实地重放这条删除
- 源库磁盘损坏且 binlog 也丢失——副本可能因为同样的数据损坏而不可用
- 真正的数据安全需要**备份（物理备份 + binlog 归档）**​ + **复制（冗余）**​ 双重保障

📌 **洞见 2：默认异步复制决定了所有架构权衡的边界**。因为源库提交事务后**不等待副本确认**，所以：

- 副本一定存在不同程度的延迟
- 源库宕机可能丢失尚未同步到任何副本的事务
- 所有"高级复制特性"（半同步、GTID、多线程）都是在异步复制的基础上做权衡

## 复制如何工作

### 复制原理

书中详细描述了复制的三线程模型。结合 MySQL 8.4 官方文档：

**源库端（Source）**：

- 客户端执行 DML/DDL 并提交
- MySQL 将事务以事件形式持久化到 binlog
- **Binary Log Dump 线程**：为每个连接的副本创建一个 dump 线程，发送 binlog 内容

**副本端（Replica）**：

- **IO 线程（Receiver）**：连接源库，拉取 binlog 事件，写入本地中继日志（relay log）
- **SQL 线程（Applier）**：读取中继日志，在副本库上重放事件

📌 **洞见**：IO 线程和 SQL 线程的解耦是复制架构的核心设计——**网络接收与本地应用解耦**。这意味着：

- 网络慢 → IO 线程阻塞 → 但 SQL 线程可以继续应用已收到的中继日志
- 本地应用慢 → SQL 线程阻塞 → 但 IO 线程可以继续接收 binlog
- 这种解耦让"网络瓶颈"和"应用瓶颈"可以独立优化

> ⚠️ **AWS 2025 年文档的重要补充**：无论单线程复制还是多线程复制，IO 线程**始终是一个**——它很少成为复制瓶颈。真正的瓶颈在 SQL 线程的应用速度上。

### 选择复制格式

书中讨论了 STATEMENT、ROW、MIXED 三种格式。但 2026 年的现实已经完全不同：

**MySQL 8.0.34 起 `binlog_format` 已弃用**，未来版本将移除该参数，**只支持 ROW 格式**。MySQL 8.4 中 ROW 是默认格式。

|格式|工作原理|优点|缺点|
|---|---|---|---|
|STATEMENT|记录 SQL 语句|binlog 最小、最快|非确定性函数（NOW()、UUID()、RAND()）可能导致主从不一致|
|ROW|记录每行数据的变化|最强一致性、无歧义|binlog 最大（特别是批量操作）|
|MIXED|默认 STATEMENT，特定场景自动切换 ROW|平衡性能与一致性|边界情况下引擎可能误判|

📌 **洞见**：对于新部署的 MySQL 复制，**无条件使用 ROW 格式**：

- 8.0.34+ 已弃用 `binlog_format`，未来只支持 ROW
- ROW 格式下，AWS DMS、零 ETL 集成等都要求 ROW
- 蓝绿部署推荐 ROW 以确保强一致性
- ROW 格式要求**所有表都有主键**——没有主键的表在 ROW 格式下会导致副本全表扫描，引发严重延迟

> 💡 **ROW 格式的 binlog 优化**：设置 `binlog_row_image = MINIMAL` 可以减少 binlog 大小，同时保持正确性。这对于批量 UPDATE/DELETE 操作尤为有效。

### 全局事务标识符（GTID）

GTID 是 MySQL 5.6 引入、5.7+ 成熟、8.0+ 成为现代复制标准的核心机制。

**GTID 格式**：`source_uuid:transaction_id`，例如 `3E11FA47-71CA-11E1-9E33-C80AA9429562:23`

📌 **洞见**：GTID 的本质是用"事务 ID"替代"binlog 文件 + 偏移量"的坐标系。这带来的革命性变化：

**1. 故障切换的确定性**

```
-- 传统方式：必须知道确切的 binlog 文件和位置
CHANGE MASTER TO 
    MASTER_LOG_FILE='mysql-bin.000003', 
    MASTER_LOG_POS=471632;

-- GTID 方式：AUTO_POSITION 自动协商
CHANGE REPLICATION SOURCE TO 
    SOURCE_AUTO_POSITION=1;
```

**2. 副本自动定位同步点**

副本告诉源库"我已经应用了哪些 GTID"，源库自动计算出从哪个事务开始发送。这彻底消除了"找坐标"的错误可能。

**3. 副本提升（Promotion）变得简单**

旧主宕机后，任意副本都可以被提升为新主——GTID 保证了事务集合的一致性。

**GTID 的配置要点**：

```
[mysqld]
gtid_mode = ON
enforce_gtid_consistency = ON
```

**启用 GTID 的在线过渡（不停机）**：

```
SET @@GLOBAL.enforce_gtid_consistency = WARN;  -- 先 WARN 观察
SET @@GLOBAL.enforce_gtid_consistency = ON;
SET @@GLOBAL.gtid_mode = OFF_PERMISSIVE;
SET @@GLOBAL.gtid_mode = ON_PERMISSIVE;
-- 确认无匿名事务：SHOW STATUS LIKE 'Ongoing_anonymous_transaction_count';
SET @@GLOBAL.gtid_mode = ON;
```

📌 **2026 年工业实践补充**：MySQL 8.4 中，**CLONE 插件 + GTID 自动定位**已经成为搭建新副本的标准做法。CLONE 插件把源库的 `gtid_executed` 集合带到副本，并设置 `gtid_purged`——副本启动后通过 `SOURCE_AUTO_POSITION=1` 自动从正确的位置开始同步，**整个过程无需手动计算坐标**。

### 崩溃后的复制安全

书中讨论了崩溃安全复制的配置。在 MySQL 8.4 中，**崩溃安全复制已经是默认行为**——不再需要配置 `master_info_repository` 和 `relay_log_info_repository`（这些参数在 8.4 中已移除）。

📌 **洞见**：8.4 中保证复制崩溃安全的关键配置：

```
[mysqld]
gtid_mode = ON                    # 启用 GTID
enforce_gtid_consistency = ON     # 强制 GTID 一致性
sync_binlog = 1                   # 每次提交刷盘 binlog
innodb_flush_log_at_trx_commit = 1  # 每次提交刷盘 InnoDB redo log
relay_log_recovery = ON           # 副本崩溃后恢复中继日志
```

这组配置保证了：源库宕机后，已提交的事务不会丢失；副本崩溃后，已接收但未应用的事务可以从中继日志安全恢复。

### 延迟复制

MySQL 8.4 原生支持延迟复制——副本故意落后于源库指定的时间量。

📌 **洞见**：延迟复制的核心价值是**误操作防护**：

- 源库执行 `DROP TABLE` 误操作
- 如果延迟副本落后 1 小时，你可以在 1 小时内从延迟副本恢复数据
- 这是"自助式备份"——比从物理备份恢复快几个数量级

**配置延迟复制**：

```
CHANGE REPLICATION SOURCE TO 
    SOURCE_DELAY = 3600;  # 延迟 3600 秒（1 小时）
START REPLICA;
```

**工业界典型配置**：

- 防误操作：延迟 1-4 小时
- 防批量错误：延迟 1 天
- 关键业务表：延迟副本 + 常规副本混合部署

> ⚠️ **注意事项**：延迟副本在延迟窗口内如果发生源库宕机，会丢失延迟窗口内的事务。它防护的是"误操作"，不是"源库宕机"。

### 多线程复制

这是现代高吞吐量数据库的必备特性。AWS 2025 年的官方博客给出了最权威的解释：

**多线程复制的线程模型**：

```
IO 线程（1 个，每通道）          ← 始终单线程
Coordinator 线程（1 个，每通道）  ← 读取中继日志，分析依赖，分配任务
Worker 线程（N 个，每通道）       ← 实际并行应用事务
```

当 `replica_parallel_workers > 1` 时，SQL 线程分为协调线程和多个工作线程。

📌 **洞见 1：并行度的决定因素是"事务依赖关系"**

MySQL 提供两种依赖跟踪方式：

**COMMIT_ORDER（提交顺序）**：

- 基于源库组提交的时序
- 同一组提交的事务可以在副本并行应用
- 并行度受限于源库组提交的频率

**WRITESET（写入集）**：

- 基于事务修改的行集合（writeset）
- 只要两个事务修改的行不冲突，就可以并行
- 并行度远高于 COMMIT_ORDER

📌 **洞见 2：MySQL 8.4 默认开启多线程复制**

- `replica_parallel_workers` 默认为 4（8.4 之前默认为 0）
- `binlog_transaction_dependency_tracking` 默认为 WRITESET（8.4 中该变量已弃用）
- `replica_preserve_commit_order` 默认为 ON（保证副本提交顺序与源库一致）

**配置多线程复制**：

```
[mysqld]
replica_parallel_workers = 8          # 根据 CPU 核心数调整
replica_parallel_type = LOGICAL_CLOCK  # 使用逻辑时钟（WRITESET 的基础）
```

**监控多线程复制**：

```
-- 查看工作线程状态
SELECT * FROM performance_schema.replication_applier_status_by_worker;

-- 查看协调线程状态
SELECT * FROM performance_schema.replication_applier_status_by_coordinator;
```

> 💡 **AWS 最佳实践**：`replica_parallel_workers` 的设置应该基于副本的 CPU 核心数。一般设置为 CPU 核心数的 1/2 到 2/3，留出足够的资源给查询。

📌 **洞见 3：多线程复制不是银弹**

- 单事务内的多行修改无法进一步并行
- 大事务（如批量 UPDATE 100 万行）会阻塞并行应用
- 副本的并行度受限于源库的事务并发度
- 如果源库是串行写入，副本多线程也无法并行

### 半同步复制

书中介绍了半同步复制的概念。MySQL 8.4 官方支持半同步复制：

**半同步复制的工作机制**：

- 源库提交事务时，**阻塞等待**至少一个副本确认已接收并记录了该事务的 binlog 事件
- 如果在 `rpl_semi_sync_source_timeout` 时间内未收到确认，自动降级为异步复制

📌 **洞见 1：半同步复制用写入延迟换取数据安全性**

```
-- 源库启用半同步
INSTALL PLUGIN rpl_semi_sync_source SONAME 'semisync_source.so';
SET GLOBAL rpl_semi_sync_source_enabled = 1;
SET GLOBAL rpl_semi_sync_source_timeout = 1000;  # 1秒超时后降级为异步

-- 副本启用半同步
INSTALL PLUGIN rpl_semi_sync_replica SONAME 'semisync_replica.so';
SET GLOBAL rpl_semi_sync_replica_enabled = 1;
```

**半同步复制的权衡**：

- ✅ 源库宕机时，已确认的事务至少在一个副本上存在
- ✅ 大大减少了"已提交事务丢失"的窗口
- ❌ 写入延迟增加（必须等待网络往返 + 副本刷盘）
- ❌ 超时降级后行为与异步复制相同

📌 **洞见 2：半同步复制的"至少一个"语义**

"至少一个副本确认"不等于"所有副本确认"：

- 如果有 3 个副本，源库只需等待最快的那个确认
- 这保证了"至少有一个副本有数据"，但不保证"多数副本有数据"
- 如果需要更强的一致性，需要"组复制（Group Replication）"或 NDB Cluster

📌 **洞见 3：半同步 + GTID 是金融级部署的标准组合**

金融、支付、订单等核心业务的标准配置：

- GTID 确保事务追踪
- 半同步确保数据不丢失
- `sync_binlog=1` + `innodb_flush_log_at_trx_commit=1` 确保源库持久性

### 复制过滤器

书中讨论了复制过滤器的使用。MySQL 8.4 支持：

- 库级别的过滤：`binlog-do-db`、`binlog-ignore-db`（源端）
- 表级别的过滤：`replicate-do-table`、`replicate-ignore-table`（副本端）

📌 **洞见**：复制过滤器是"看似有用实则危险"的特性：

> ⚠️ **复制过滤器的主要风险**：
> 
> 1. **GTID 一致性破坏**：过滤后的副本 `gtid_executed` 集合与源库不一致，故障切换时可能出现事务遗漏或重复
> 2. **跨库事务问题**：一个事务修改多个库时，过滤器可能导致部分修改被应用、部分被忽略
> 3. **故障切换复杂**：过滤副本不能作为完整源库的故障切换目标

**工业界最佳实践**：

- 尽量避免使用复制过滤器
- 如果必须过滤，使用**单独的实例**而非过滤器——即源库只写需要复制的库
- 如果必须使用过滤器，确保过滤规则不会破坏事务完整性

## 复制切换

### 计划内切换

计划内切换（Planned Switchover）通常发生在：

- 源库硬件维护
- 源库 MySQL 版本升级
- 源库迁移到更强硬件

📌 **洞见**：计划内切换的标准流程（基于 GTID）：

```
-- 1. 在源库上设置只读（停止写入）
SET GLOBAL read_only = ON;
SET GLOBAL super_read_only = ON;

-- 2. 等待副本追上源库（GTID 完全同步）
-- 监控：SELECT GTID_SUBTRACT(@@global.gtid_executed, '源库GTID');

-- 3. 在候选副本上提升为新源
STOP REPLICA;
RESET BINARY LOGS AND GTIDS;
SET GLOBAL read_only = OFF;
SET GLOBAL super_read_only = OFF;

-- 4. 其他副本指向新源
STOP REPLICA;
CHANGE REPLICATION SOURCE TO SOURCE_HOST='新源地址', SOURCE_AUTO_POSITION=1;
START REPLICA;

-- 5. 应用层切换到新源
```

### 计划外切换

计划外切换（Unplanned Failover）发生在源库突发宕机时。这是最危险的场景：

📌 **洞见**：计划外切换的核心难题是**"数据丢失窗口"的不确定性**：

- 异步复制：可能丢失源库上已提交但未同步到任何副本的事务
- 半同步复制：可能丢失超时降级后到宕机之间的事务
- GTID 自动定位：简化了切换流程，但不消除数据丢失

**计划外切换的决策框架**：

```
1. 确认源库确实不可达（网络、硬件、MySQL 进程）
2. 选择数据最新的副本（对比 GTID_EXECUTED）
3. 在新主上执行：STOP REPLICA; RESET BINARY LOGS AND GTIDS;
4. 其他副本指向新主：CHANGE REPLICATION SOURCE TO SOURCE_AUTO_POSITION=1
5. 应用层切换
6. 原主恢复后，作为副本重新加入（避免数据冲突）
```

> ⚠️ **原主"脑裂"风险**：如果原主实际上并未宕机而是网络分区，它可能在应用层切换后继续接受写入，导致"双主"数据分歧。这就是为什么**生产环境必须用 Orchestrator、MHA、或 Group Replication 等工具来管理故障切换**——它们通过多种机制（如 STONITH、租约机制）确保原主真正下线。

### 切换时的权衡

📌 **洞见**：切换的本质是在"数据一致性"与"可用性"之间做选择：

|策略|数据安全性|切换速度|运维复杂度|
|---|---|---|---|
|等待原主恢复|最高（无数据丢失）|最慢|低|
|半同步 + 自动切换|高（丢失窗口极小）|快（秒级）|高|
|异步 + 自动切换|低（可能丢失事务）|最快|中|

**2026 年工业界的主流选择**：

- **中小规模**：Orchestrator + GTID + 半同步
- **大规模**：Group Replication（MGR）+ 多主或单主模式
- **云环境**：RDS/Aurora 托管服务（自动故障切换）

## 复制拓扑

### 主动/被动模式

**架构**：单一源库处理所有写入和读取，副本不参与正常流量。

📌 **洞见**：这是最简单的拓扑，适用于：

- 写入负载不高，读负载也不高的场景
- 需要避免"写后立即读"的一致性问题
- 重视简单性和可维护性

**配置要点**：

- 源库和副本的 CPU/内存配置对等（副本随时准备接管）
- 物理环境：n+2 冗余（至少 3 台服务器）
- 云环境：n+1 可能足够，但取决于数据量和副本构建速度

**优势**：

- 简单，故障切换直接
- 避免读副本的延迟导致"写后立即读"不一致

**劣势**：

- 读容量受限于单台服务器
- 资源利用率低

### 主动/只读池模式

**架构**：源库处理写入，读取分散到源库和一组副本。

📌 **洞见**：这是工业界最常用的拓扑，因为**读扩展是大多数应用的刚需**。

**关键设计考量**：

**1. 读副本池的管理**

- 池中至少保留 1-2 个与源库等配的副本作为故障切换候选
- 异构配置时，通过流量权重调整
- 必须实现"高延迟节点自动摘除"机制

**2. 读写分离的路由**

- 应用层路由：根据事务只读性选择数据源
    
    ```
    // Spring 的 AbstractRoutingDataSource
    @Transactional(readOnly = true)  // → 路由到副本
    public List<Report> generateReport() { ... }
    
    @Transactional  // → 路由到源库
    public void createOrder(Order o) { ... }
    ```
    

**3. 读副本的延迟容忍**

- 必须明确：哪些读可以容忍延迟（如报表、历史数据）
- 哪些读必须强一致（如余额查询、订单状态）
- 关键读可以"写后读源库"——通过 `WAIT_FOR_EXECUTED_GTID_SET()` 实现会话一致性

**4. 源库复制负载**

- 副本越多，源库的 Binary Log Dump 线程压力越大
- 复制风暴：1 个源库 + 10 个副本，源库不堪重负
- **解决方案**：级联复制——源库只复制给 1 个副本，其他副本从这一级副本复制

> ⚠️ **读副本池的运维挑战**：
> 
> - 节点越多，打补丁等运维任务越多
> - 必须自动化"摘池→维护→入池"流程
> - 副本之间的延迟差异可能导致"同一个查询在不同副本上返回不同结果"

### 不推荐的一些拓扑架构

书中明确列出了几种不推荐的拓扑。结合 2026 年的工业实践：

**1. 双源主动/主动（Active-Active Bidirectional）**

❌ **强烈不推荐**：

- 路由复杂：必须确保同一行数据只在单边写入
- 延迟导致不一致：双边写入可能因延迟产生冲突
- 容量规划困难：一边故障时，另一边必须承担全部负载
- Buffer pool 抖动：工作集变化导致缓存效率下降

**2. 双源主动/被动（Dual-Source Active/Passive）**

❌ **不推荐**：

- 看似优雅，但局限于两节点配置
- 故障时灵活性差
- 复制设置可以自动化，无需预先固定

**3. 环形复制（Ring/Circular Replication）**

❌ **绝对避免**：

- 任何一个节点宕机，更新链条断裂
- 没有优势，只增加复杂性
- 故障切换极其痛苦

**4. 多源复制（Multi-Source Replication）**

⚠️ **谨慎使用**：

- 8.4 支持多源复制（一个副本从多个源复制）
- 仅适用于**临时数据聚合**场景（如 BI 汇总）
- **不应作为永久拓扑**：单副本不能为同一源设置多个多源配置

**5. 级联复制的隐患**

- 级联复制可以解决复制风暴，但引入了"链式延迟"
- 中间节点宕机影响所有下游副本
- 必须监控整条复制链的延迟

## 复制管理和维护

### 复制监控

📌 **洞见 1：`SHOW REPLICA STATUS` 的关键字段**

```
SHOW REPLICA STATUS\G
```

重点关注：

- **Replica_IO_Running**：IO 线程状态（YES/NO）
- **Replica_SQL_Running**：SQL 线程状态（YES/NO）
- **Seconds_Behind_Source**：副本落后源库的秒数（**只是估算值**）
- **Retrieved_Gtid_Set vs Executed_Gtid_Set**：GTID 差异比秒数更可靠
- **SQL_Delay**：是否配置了延迟复制

📌 **洞见 2：`Seconds_Behind_Source` 的欺骗性**

Percona 明确指出：`Seconds_Behind_Source` 可能受长运行命令影响而返回错误值。例如：

- 源库执行了一个运行 1 小时的 UPDATE
- 副本的 SQL 线程也在执行这个 UPDATE
- 在此期间，`Seconds_Behind_Source` 可能显示为 NULL 或严重失真

**正确的延迟观测方法**：

**1. 使用 pt-heartbeat（Percona Toolkit）**

```
# 源库持续写入心跳
pt-heartbeat --daemonize --update --user=root --password=xxx \
  --host=master-ip --interval=1

# 副本读取延迟
pt-heartbeat --monitor --user=root --password=xxx \
  --host=slave-ip --master-server-id=1
```

**2. 使用 Performance Schema（MySQL 8.0+）**

```
-- 查看各应用线程状态
SELECT * FROM performance_schema.replication_applier_status_by_worker;

-- 计算真实 GTID 延迟
SELECT 
    SUBSTRING_INDEX(SUBSTRING_INDEX(@@global.GTID_EXECUTED,':',-1),'-',-1) 
    AS last_executed;
```

**3. 监控关键指标**

- 副本 I/O 线程状态
- 副本 SQL 线程状态
- 中继日志增长速率
- 二进制日志增长速率
- 磁盘空间（binlog + relay log）

### 观测复制延迟

📌 **洞见**：复制延迟的观测必须分层：

**第一层：网络传输延迟**

- IO 线程是否及时拉取 binlog？
- 监控 `Read_Source_Log_Pos` vs `Exec_Source_Log_Pos`

**第二层：中继日志应用延迟**

- SQL 线程是否及时应用中继日志？
- 监控 GTID 差异：Retrieved_Gtid_Set - Executed_Gtid_Set

**第三层：端到端业务延迟**

- 用 pt-heartbeat 测量真实业务延迟
- 这是最可靠的指标

**第四层：多线程复制的 worker 均衡**

```
-- 查看各 worker 的应用进度
SELECT worker_id, 
       (APPLYING_TRANSACTION_ORIGINAL_COMMIT_TIMESTAMP) AS start_time,
       APPLYING_TRANSACTION_END_APPLY_TIMESTAMP AS end_time
FROM performance_schema.replication_applier_status_by_worker;
```

### 确定副本数据的一致性

📌 **洞见**：副本数据一致性校验是复制运维的"定期体检"：

**1. Percona Toolkit 的 pt-table-checksum**

```
pt-table-checksum --user=root --password=xxx --host=master-ip
```

它在源库上计算每块数据的校验和，副本重放后比对校验和差异。

**2. pt-table-sync 修复不一致**

```
pt-table-sync --user=root --password=xxx \
  --host=master-ip --tables=db.table \
  --sync-to-master
```

**3. GTID 一致性验证**

```
-- 在副本上检查
SELECT GTID_SUBTRACT(@@global.gtid_executed, '源库GTID集合');
-- 结果为空表示完全一致
```

> ⚠️ **一致性校验的代价**：pt-table-checksum 会在源库上产生大量读取，可能冲击生产负载。必须在低峰期执行，并控制并发度。

## 复制问题和解决方案

### 源端二进制日志损坏

📌 **症状**：副本 IO 线程报 binlog 格式错误。

**解决方案**：

- 如果 GTID 已启用，可以在源库上执行 `PURGE BINARY LOGS` 清理损坏的 binlog
- 副本会通过 GTID 自动定位到下一个有效的 binlog
- 如果无法恢复，需要重建副本（CLONE 插件或物理备份恢复）

### 非唯一的服务器 ID

📌 **洞见**：`server_id` 必须全局唯一——这是 GTID 的 `server_uuid` 生成基础。

**后果**：

- GTID 冲突
- 复制拓扑混乱
- 故障切换数据丢失

**解决方案**：

```
-- 检查 server_id
SELECT @@server_id;
SELECT @@server_uuid;

-- 修改为唯一值
SET GLOBAL server_id = 2;
-- 并在配置文件中持久化
```

### 未配置服务器 ID

📌 **症状**：MySQL 无法启动复制，报错"server_id must be set"。

**解决方案**：

```
[mysqld]
server_id = 2  # 每台服务器唯一
```

### 临时表丢失

📌 **洞见**：这是一个经典陷阱。临时表在源库上创建，但：

- ROW 格式下，临时表**不会**写入 binlog
- 副本 SQL 线程重放时找不到临时表
- 源库重启后，临时表丢失，但副本可能仍在尝试使用

**解决方案**：

- 避免使用临时表进行跨语句操作
- 如果必须使用，用 `binlog_format = STATEMENT` 确保临时表被记录（但 8.4 已弃用 STATEMENT）
- 更好的方案：使用物理表 + 会话 ID 替代临时表

### 没有复制所有变更

📌 **常见原因**：

- 复制过滤器配置错误
- 源库使用了 `binlog-do-db` 但副本期望复制所有库
- `binlog_format` 与复制过滤器不兼容

**解决方案**：

- 审查复制过滤规则
- 使用 GTID 后可以更容易地诊断：对比源库和副本的 `gtid_executed` 集合

### 复制延迟过大

📌 **洞见**：复制延迟过大的根因分析框架：

**1. 源库侧原因**

- 大事务（批量 UPDATE/DELETE/INSERT...SELECT）
- 高并发写入超出副本应用能力
- `binlog_transaction_dependency_tracking = COMMIT_ORDER`（并行度低）

**2. 网络侧原因**

- 源库与副本之间的网络带宽不足
- 网络延迟高

**3. 副本侧原因**

- `replica_parallel_workers` 设置过低
- 副本硬件性能不足
- 副本上运行了重查询，争抢 IO/CPU
- 表缺少主键（ROW 格式下全表扫描）
- 副本的 buffer pool 太小

**解决方案矩阵**：

|原因|解决方案|
|---|---|
|大事务|拆分事务，分批执行|
|并行度低|`replica_parallel_workers = 8`，`replica_parallel_type = LOGICAL_CLOCK`|
|表缺主键|为所有表添加主键|
|副本硬件弱|升级副本硬件，或调整权重|
|副本查询争抢|将分析查询路由到其他专用副本|
|网络瓶颈|使用级联复制，减少源库 dump 线程压力|

> 💡 **AWS 2025 年最佳实践**：对于高吞吐量数据库，多线程复制是必选项。但必须配合 `binlog_transaction_dependency_tracking = WRITESET`（8.4 默认）才能发挥最大并行度。

### 来自源服务器的超大数据包

📌 **症状**：副本 IO 线程报 `Got packet bigger than 'max_allowed_packet'` 错误。

**解决方案**：

```
[mysqld]
max_allowed_packet = 256M  # 源库和副本都要设置
```

### 磁盘空间耗尽

📌 **洞见**：这是生产环境最常见的复制故障之一：

**源库 binlog 占满磁盘**：

- 设置合理的 `binlog_expire_logs_seconds`（如 7 天 = 604800 秒）
- 监控 binlog 增长速度
- 8.4 默认自动清理（`binlog_expire_logs_auto_purge = ON`）

**副本中继日志占满磁盘**：

- 设置 `relay_log_space_limit`
- 监控中继日志大小
- 确保 SQL 线程及时应用

**预防措施**：

```
-- 监控 binlog 大小
SHOW BINARY LOGS;

-- 监控中继日志
SHOW REPLICA STATUS\G  -- 查看 Relay_Log_File 和 Relay_Log_Space
```

### 复制的限制

📌 **洞见**：MySQL 基础复制的硬性限制：

1. **默认异步**：源库宕机可能丢数据
2. **不支持查询级并行**：单个大事务无法在副本上并行应用
3. **复制过滤器破坏 GTID 一致性**
4. **N 级级联复制的链式延迟**
5. **源库是单点**：所有写入集中在一台服务器

**突破限制的现代方案**：

|限制|解决方案|
|---|---|
|数据丢失窗口|半同步复制、Group Replication|
|源库单点|多主复制（MGR）、Orchestrator 自动故障切换|
|同步复制需求|NDB Cluster|
|全球分布|异步复制 + 冲突解决机制|

## 小结

这一章表面讲的是"怎么配置复制"，深层传递的是**SRE 视角的复制哲学**：

**1. 复制默认异步，这是所有权衡的起点**

异步复制决定了副本一定有延迟、源库宕机可能丢数据。所有"高级特性"都是在异步基础上做一致性、性能、复杂度的权衡。

**2. GTID 是现代复制的基石**

- 用事务 ID 替代文件位置，简化故障切换
- 8.4 中配合 CLONE 插件可以实现"零坐标"副本搭建
- `enforce_gtid_consistency = ON` 是生产环境强制要求

**3. ROW 格式是唯一未来**

- 8.0.34 起 `binlog_format` 已弃用
- 未来版本只支持 ROW
- 所有表必须有主键（ROW 格式要求）

**4. 多线程复制是性能关键**

- 8.4 默认 `replica_parallel_workers = 4`
- WRITESET 依赖跟踪提供最高并行度
- IO 线程始终单线程，瓶颈在 SQL 应用端

**5. 半同步复制用延迟换安全**

- 写入延迟增加，但数据丢失窗口极大缩小
- 金融、支付等核心业务的标配
- 超时后自动降级为异步

**6. 拓扑越简单越好**

- 主动/被动：简单，适用于低负载
- 主动/只读池：工业界主流，读写分离
- 双主、环形、多源：弊大于利，应该避免

**7. 复制监控必须深入**

- `Seconds_Behind_Source` 只是估算值，可能严重失真
- pt-heartbeat 提供业务级真实延迟
- Performance Schema 提供 GTID 级精确延迟
- 定期检查副本数据一致性（pt-table-checksum）

**8. 复制不是备份**

- 复制提供冗余，不提供时间点恢复
- 必须配合物理备份 + binlog 归档
- 延迟复制是"误操作防护"的补充手段

> 💡 **贯穿全章的洞见**：复制设计的本质，是在一致性、可用性、写入延迟、运维复杂度这四个维度上做持续的权衡。没有"完美"的复制架构，只有"适合你业务"的复制架构。优秀的复制架构设计，始于对你业务的一致性要求和延迟容忍度的清晰认知，终于对 GTID、多线程、半同步、拓扑、监控的精细打磨。
> 
> 一个真实工业级复制架构工作流：
> 
> 1. **明确需求**：写入 QPS？读取 QPS？延迟容忍？一致性要求？
> 2. **选择拓扑**：主动/被动 还是 主动/只读池？
> 3. **基础配置**：GTID + ROW + 多线程 + 半同步
> 4. **高可用**：Orchestrator 或 MGR 管理故障切换
> 5. **监控体系**：pt-heartbeat + Performance Schema + PMM
> 6. **定期演练**：季度性故障切换演练
> 7. **备份策略**：物理备份 + binlog 归档 + 延迟副本
> 
> 这套方法论，让复制架构从"DBA 的手艺"变成了"工程的科学"——这正是本书 SRE 视角的精髓：**用数据驱动决策，用自动化保障安全，用演练验证可靠性**。
> 
> 正如 MySQL 官方文档所强调的——"Replication is asynchronous by default"——这句话揭示了 MySQL 复制的全部设计哲学：**它优先保证源的写入性能和可用性，副本的一致性是"最终一致"而非"强一致"**。理解这一点，你就能理解为什么 GTID、半同步、多线程复制、Orchestrator 等所有现代复制工具都在做同一件事：**在异步复制的基础上，尽可能地逼近同步复制的安全性和一致性，同时最小化对写入性能的影响**。这才是第 9 章"复制"的真正内核。

📌 **给读者的实践清单**：

- ✅ 新部署无条件使用 GTID + ROW 格式
- ✅ `enforce_gtid_consistency = ON`（强制）
- ✅ 8.4 中多线程复制默认开启，根据 CPU 核心数调整 `replica_parallel_workers`
- ✅ 核心业务使用半同步复制，`rpl_semi_sync_source_timeout = 1000`
- ✅ 所有表必须有主键（ROW 格式要求）
- ✅ 配置延迟副本（1-4 小时）防护误操作
- ✅ 使用 pt-heartbeat 监控真实复制延迟
- ✅ 定期用 pt-table-checksum 校验副本一致性
- ✅ 设置合理的 `binlog_expire_logs_seconds`（建议 7 天以上）
- ✅ 副本设置 `read_only = ON` 和 `super_read_only = ON`
- ✅ 用 Orchestrator 或 MGR 管理故障切换，不要手动切换
- ✅ 季度性故障切换演练
- ✅ 复制 + 备份双重保障（复制不是备份）
- ❌ 不要使用复制过滤器（破坏 GTID 一致性）
- ❌ 不要部署双主、环形、复杂多源拓扑
- ❌ 不要在 ROW 格式下使用无主键的表
- ❌ 不要依赖 `Seconds_Behind_Source` 作为唯一延迟指标
- ❌ 不要让单个源库挂载过多副本（避免复制风暴）

**复制是 MySQL 高可用的血脉，血脉畅通，系统才能在高负载下持续跳动。一个优秀的复制架构，是用 GTID 确保事务追踪、用多线程复制确保应用性能、用半同步确保数据安全、用简单拓扑确保可运维性——这四者的精妙平衡，正是本章"复制"的灵魂所在。理解了复制的本质，你就理解了为什么现代 MySQL 高可用方案（Orchestrator、MGR、RDS/Aurora）全都建立在 GTID + ROW + 多线程复制的基石之上：因为这就是 MySQL 复制在 2026 年的最优解。**
