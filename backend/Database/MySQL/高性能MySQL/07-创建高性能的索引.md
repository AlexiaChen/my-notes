
# 第 7 章　创建高性能的索引——读书笔记

> 💡 这一章的本质，不是教你"哪里慢就给哪里建索引"，而是建立一个**第一性原理**：索引是一种**用写入成本、存储成本和维护复杂度，去交换"定位数据路径变短"**的权衡结构。B+tree 的有序性、最左前缀、聚簇索引对行物理顺序的决定权、回表成本、排序能否借索引完成——这五条物理事实，推导出书里所有的索引策略。任何脱离这五条物理事实的"索引最佳实践"，都是无源之水。
> 
> 正如《高性能 MySQL（第 4 版）》在本章开篇强调的："小型、负载轻的数据库通常即使没有适当的索引也能表现良好，但随着数据集的增长，性能可能会迅速下降。索引优化可能是提高查询性能的最有效方法，最佳索引有时可以比仅仅'好'的索引提高大约两个数量级的性能"。**索引是把双刃剑——它能在读侧带来数量级的提升，同时也在写侧、存储侧、内存侧收取同等量级的开销**。

MySQL 8.4 官方文档明确：InnoDB 是默认存储引擎，每张 InnoDB 表都有一个称为**聚簇索引的主键索引，该索引对数据进行组织以最小化主键查找的 I/O**。这是 2026 年工业界索引设计的根本出发点。

## 索引基础

### 索引的物理本质

书中用"书的索引"做类比：要查找特定主题，先看索引，它告诉你该术语出现的页码。

📌 **洞见**：这个类比精妙但不够——书的索引和正文是分离的，而 InnoDB 的**聚簇索引把"索引"和"数据"合二为一**。这意味着：

- **聚簇索引（主键）的叶子节点 = 完整行数据**
- **二级索引的叶子节点 = 主键值**（不是行指针）

这个区别决定了 InnoDB 索引设计的全部游戏规则。当通过二级索引查询时，MySQL 要先扫描二级索引拿到主键，再去聚簇索引拿完整行——这就是**回表**（bookmark lookup）。

### B+tree 结构的关键性质

书中详细讲了 B+tree 的存储方式。MySQL 8.4 的 InnoDB 使用 B+tree 实现[：

- **非叶子节点**只存"边界值和指向下层的指针"
- **叶子节点**存"键 + 完整数据（聚簇索引）或 键 + 主键值（二级索引）"
- **叶子节点之间有双向链表**——这让范围扫描和顺序读取极为高效

📌 **洞见**：B+tree 的有序性带来了三个核心能力，这也是索引所有"优点"的物理根源：

1. **点查找快**：从根到叶的树高通常为 3-4 层，意味着一次主键查找只需 3-4 次 I/O
2. **范围扫描快**：叶子节点的链表让 `WHERE id BETWEEN 100 AND 200` 变成顺序读
3. **排序快**：如果索引顺序与 ORDER BY 一致，可以免去 filesort

## 索引的类型

### B-tree 索引（主流）

书中指出：B-tree 索引不仅支持点查找，还支持前缀匹配和范围搜索。如果索引顺序与查询需求匹配，还可以用于加速 ORDER BY。

📌 **B+tree 能有效服务的查询模式**（假设从复合索引最左列开始使用）：

- 包含前导列的完全匹配
- 前导列的前缀匹配
- 前导列的范围条件
- 前导列匹配 + 下一列范围条件
- 当查询所需的所有列都包含在索引中时（覆盖索引），"仅从索引返回"的查询

**B-tree 的典型约束**：

- 不从最左列开始的条件下很难生效（例如，只有第二列、后缀匹配等）
- 不能跳过索引列（如果不指定前导列，基本上只能使用前一导列）
- 如果前导侧出现范围条件，则其右侧的列很难用于索引访问优化（例如，前缀匹配 `LIKE 'J%'` 之后的列）

### 自适应哈希索引（Adaptive Hash Index, AHI）

书中提到 InnoDB 有 AHI 机制，基于频繁访问的数据在内存中自动创建哈希。

📌 **2026 年重要更新**：MySQL 8.4 中，**InnoDB 自适应哈希索引默认为 OFF**，以便针对特定工作负载进行调优。这是 8.4 与早期版本的一个显著差异——Oracle 工程团队认为 AHI 在某些高并发写入场景下反而成为瓶颈（AHI 的维护需要全局锁），所以改为默认关闭，让 DBA 根据实际工作负载显式开启。

### 全文索引（FULLTEXT）

书中指出：FULLTEXT 是用于在文本中发现关键词的特殊索引类型，专用于 `MATCH ... AGAINST`，区别于标准的 WHERE 比较。MySQL 5.6 及以后版本支持 FULLTEXT 索引。

📌 **洞见**：FULLTEXT 索引的存在**并不消除对同一列建立 B-tree 索引的需要**。两者服务完全不同的查询模式。

### 其他索引类型

- **空间索引（R-tree）**：用于 GIS 数据，MySQL 5.7+ 支持
- **倒排索引**：用于 JSON 数组的多值索引（8.0.17+）

## 使用索引的优点

书中总结了索引的三大核心优点：

1. **减少服务器需要检查的数据量**——加快过滤
2. **避免排序和临时表**——利用已有的排序顺序
3. **将随机磁盘读取转换为顺序磁盘读取**——范围顺序读取的能力非常强大

📌 **洞见**：这三大优点的本质是**用"索引的有序性"替你做本该由"全表扫描 + filesort + 临时表"来做的事**。当你理解这一点，就能推导出所有高性能索引策略：

- 想要"减少检查数据量" → 让索引的前导列匹配 WHERE 子句，且选择性越高越好
- 想要"避免排序" → 让索引的列顺序匹配 ORDER BY
- 想要"顺序读" → 让索引支持范围条件，避免回表

## 高性能的索引策略

这是全章最核心的部分。我用"物理事实 → 推导 → 实践"的三段式重写。

### 前缀索引和索引的选择性

**选择性（Selectivity）**​ = 不同值的数量 / 总行数。选择性越接近 1，索引过滤效果越好。

书中强调：对于字符串列，应该考虑使用更短的键。

📌 **洞见**：前缀索引是一门"用最小字符数达到接近全列选择性"的艺术。测算方法：

```
-- 全列选择性（理论上限）
SELECT COUNT(DISTINCT email) / COUNT(*) FROM customers;

-- 测试不同前缀长度的选择性
SELECT 
    COUNT(DISTINCT LEFT(email, 7)) / COUNT(*) AS sel_7,
    COUNT(DISTINCT LEFT(email, 10)) / COUNT(*) AS sel_10,
    COUNT(DISTINCT LEFT(email, 12)) / COUNT(*) AS sel_12
FROM customers;
```

如果 `sel_10` 达到 0.98、`sel_12` 达到 0.99，则选 N=10——牺牲 1% 选择性换取 60%+ 的索引空间节省，是非常划算的交易。

**前缀索引的三个硬限制**（书里没充分展开，但工业界踩坑很多）：

> ⚠️ **致命限制 1**：前缀索引**不能用于 ORDER BY 和 GROUP BY**。因为索引只包含部分数据，不足以确定精确顺序，MySQL 被迫使用 filesort。
> 
> ⚠️ **致命限制 2**：utf8mb4 字符集下，每个字符最多占 4 字节。`email(10)` 实际可能消耗 40 字节。
> 
> ⚠️ **致命限制 3**：选择性过低时，MySQL 优化器可能直接放弃使用索引而选择全表扫描。

**前缀索引的工业级替代方案**：

```
-- 哈希衍生列 + 普通索引（解决长字符串选择性问题）
ALTER TABLE users 
    ADD name_crc INT UNSIGNED AS (CRC32(name)) PERSISTENT,
    ADD INDEX idx_name_crc (name_crc);
```

这种方案比前缀索引更灵活——哈希列的选择性接近 1，且哈希索引可以用于排序。

### 多列索引

书中给出了一个极具颠覆性的观点：**在多个列上分别建单列索引，通常不如一个设计良好的复合索引**。

📌 **洞见**：这是反直觉的。直觉告诉我们"WHERE a=1 AND b=2"应该在 a 和 b 上各建一个索引。但实际上：

- 5.0 之前的 MySQL 只能用一个索引，另一个条件要在内存里过滤
- 5.0+ 的 MySQL 有 Index Merge 能力，但优化器往往选择不佳
- **真正的解决方案是复合索引 `(a, b)`**——它一次性服务了 `a=1 AND b=2` 的查询，且能服务 `a=1` 的单列查询（最左前缀）

**复合索引的服务能力**（以 `(a, b, c)` 为例）：

```
✅ WHERE a = ?                      -- 使用索引列 a
✅ WHERE a = ? AND b = ?            -- 使用索引列 a, b
✅ WHERE a = ? AND b = ? AND c = ?  -- 使用索引列 a, b, c
✅ WHERE a = ? AND b = ? AND c > ?  -- 使用索引列 a, b 做查找，c 做范围
❌ WHERE b = ?                      -- 无法使用索引（跳过最左列）
❌ WHERE a = ? AND c = ?            -- 只能使用索引列 a，c 在内存过滤
❌ WHERE a = ? AND b > ? AND c = ?  -- 只能使用 a, b，c 无法用于查找
```

### 选择合适的索引列顺序

这是索引设计里**最微妙、最容易被机械处理**的环节。

**传统教条**：把选择性最高的列放在最左边。

📌 **洞见**：这个教条**只对了一半**。在《高性能 MySQL》中给出的观点是，在复合索引中，列顺序很重要，通常只有"最左前缀匹配"才能被高效使用。

但除了选择性，还需要考虑以下因素：

**1. 范围条件终止最左前缀**

如果前一导侧出现范围条件，则其右侧的列很难用于索引访问优化。

**2. 等值条件列优先于范围条件列**

根据复合索引最佳实践：将等值条件列放在范围条件列之前，在等值条件列中，优先选择能最好匹配查询模式并具有最高前缀复用性的顺序。

**3. ORDER BY 列的巧妙放置**

如果查询是 `WHERE status = 'shipped' ORDER BY created_at DESC`，那么索引 `(status, created_at DESC)` 可以同时服务过滤和排序。

**工业界决策框架**：

```
Step 1: 列出所有等值条件列 → 按查询模式匹配度和前缀复用性排序
Step 2: 加入第一个范围条件列
Step 3: 如果 ORDER BY 与索引前缀匹配，加入排序列
Step 4: 考虑覆盖索引，把 SELECT 中的列加到末尾
```

### 聚簇索引

这是本章最深邃的一节，也是 InnoDB 索引设计的"第一性原理"。

**InnoDB 聚簇索引的物理事实**：

- 聚簇索引的叶子节点包含**完整行数据**
- 行按主键顺序**物理存储**在磁盘上
- 每个 InnoDB 表**有且只有**一个聚簇索引

**InnoDB 如何选择聚簇索引**：

1. 显式定义的 PRIMARY KEY
2. 第一个 UNIQUE NOT NULL 键
3. 如果没有合适的键，InnoDB 自动生成隐藏的 6 字节 row ID

📌 **洞见 1：主键选择决定了整张表的物理布局**

聚簇索引的 B+tree 结构意味着，行数据按主键顺序存储在叶子节点上。这带来两个深远后果：

**后果 A：主键插入模式决定写入性能**

- **顺序主键（如 AUTO_INCREMENT）**：新行总是追加到 B+tree 的最右，几乎无页分裂 → 写入高效
- **随机主键（如 UUIDv4）**：新行插入到 B+tree 的随机位置 → 频繁页分裂 → 碎片化 → 写入性能急剧下降

**后果 B：主键大小决定所有二级索引的大小**

因为二级索引的叶子节点存储主键值，所以主键越大，每个二级索引条目越大。这就是为什么第 6 章强调"用 BIGINT 而非 CHAR(36) 做主键"——它直接影响所有二级索引的存储和内存效率。

> 💡 **2026 年的现代补充**：MySQL 8.0.30 引入了 **Generated Invisible Primary Key (GIPK)**​ 特性。当 `sql_generate_invisible_primary_key = ON` 时，创建无主键表会自动添加一个不可见的 `my_row_id` BIGINT 列作为主键。这解决了"无主键表在 Group Replication 中不被支持"的问题，也为聚簇索引提供了可控的、顺序的主键。

📌 **洞见 2：聚簇索引的"最左前缀"陷阱**

由于行数据物理上按主键聚簇，这意味着：

- **主键范围查询极快**：`WHERE id BETWEEN 100 AND 200` 是纯顺序 I/O
- **主键点查极快**：3-4 次 I/O 直达行数据
- **但二级索引访问总是需要回表**：除非是覆盖索引

📌 **洞见 3：主键更新的灾难性后果**

聚簇索引的一个隐蔽陷阱：**更新主键 = 整行数据物理移动**。因为行数据存储在主键 B+tree 的叶子节点，修改主键值意味着在 B+tree 中删除旧位置、插入新位置。这就是为什么"主键永远不变"是第 6 章强调的标识符设计铁律。

### 覆盖索引

**定义**：一个包含所有查询所需列的索引，使得查询可以完全从索引中获取数据，而无需访问表数据。

📌 **洞见**：覆盖索引是 InnoDB 索引设计的"终极形态"——它让二级索引**绕过了回表**。因为二级索引的叶子节点本来就有主键值，如果我们把查询需要的所有列都放进索引，那么：

```
-- 宽表
CREATE TABLE customers (
    id INT PRIMARY KEY,
    first_name VARCHAR(20),
    last_name VARCHAR(20),
    age INT,
    email VARCHAR(100),
    -- ... 很多其他列
) ENGINE=InnoDB;

-- 覆盖索引：包含查询所需的所有列
CREATE INDEX idx_lastname_covering ON customers(last_name, first_name, age);

-- 这个查询完全从索引获取数据，无需回表
SELECT first_name, last_name, age 
FROM customers 
WHERE last_name = 'Smith';
```

**验证覆盖索引**：在 EXPLAIN 的 Extra 列中出现 **"Using index"**​ 即表示覆盖索引生效。

> 💡 AWS RDS 团队的 2026 年性能优化指南明确指出：对于宽表，"Using index"的出现意味着查询完全从索引结构返回数据，节省了磁盘 I/O 操作——这对宽表尤为重要，因为每行包含的数据远多于查询所需。

📌 **覆盖索引的工业级设计模式**：

把 SELECT 中的列"追加"到复合索引末尾，是一种强大的优化技巧：

```
-- 原始查询需要回表
SELECT id, customer_id, total_amount, created_at 
FROM orders 
WHERE status = 'shipped' 
  AND total_amount > 500 
  AND created_at > DATE_SUB(NOW(), INTERVAL 30 DAY) 
ORDER BY created_at DESC 
LIMIT 100;

-- 覆盖索引设计
CREATE INDEX idx_status_date_covering 
ON orders(status, created_at DESC, id, customer_id, total_amount);
```

**权衡**：覆盖索引虽然消除了回表，但增加了索引宽度 → 占用更多存储 → 写入更慢。所以覆盖索引的设计是一门"读性能 vs 写性能"的精细权衡。

### 使用索引扫描来做排序

书中指出：如果索引顺序与查询要求匹配，它也可以用于加速 ORDER BY。

📌 **洞见**：这是索引最容易被忽视的超能力——**索引本身是有序的，如果索引顺序恰好匹配 ORDER BY，就可以免去 filesort**。

**索引能服务排序的条件**：

1. 索引的列顺序与 ORDER BY 完全一致（含 ASC/DESC）
2. 所有排序列都来自同一个索引
3. 如果有 WHERE 条件，必须满足最左前缀

```
-- 索引：(status, created_at DESC)
-- ✅ 可以利用索引排序
SELECT * FROM orders 
WHERE status = 'shipped' 
ORDER BY created_at DESC;

-- ❌ 无法利用索引排序（排序列与索引顺序不一致）
SELECT * FROM orders 
WHERE status = 'shipped' 
ORDER BY created_at ASC;  -- 索引是 DESC
```

**2026 年新特性**：MySQL 8.4 支持**降序索引**（DESC index），可以消除 `ORDER BY col DESC` 的 filesort：

```
CREATE INDEX idx_price_desc ON products(price DESC);
-- 理想用于 "top sales" 查询，避免在 DESC 排序中使用 filesort
```

### 冗余和重复索引

书中指出：有时会在不经意间创建这些索引，它们不仅增加更新时的开销，还会导致有用的索引信息被从内存中驱逐。

📌 **洞见**：冗余索引是索引治理里最隐蔽的成本。常见形式：

```
-- 冗余索引示例
CREATE INDEX idx_a ON t(a);           -- 单列索引
CREATE INDEX idx_ab ON t(a, b);        -- 复合索引，前缀包含 a
-- idx_a 是完全冗余的，因为 idx_ab 已经能服务 WHERE a = ? 的查询
```

**冗余索引的危害**：

- 写入时需要维护更多索引 → 写入变慢
- 占用更多磁盘和内存 → buffer pool 压力增大
- 优化器选择变复杂 → 可能选错索引

**识别方法**：

```
-- 通过 sys 库识别冗余索引
SELECT * FROM sys.schema_redundant_indexes;
```

> ⚠️ **陷阱**：有时候"看似冗余"的索引其实不冗余。例如 `(a, b)` 和 `(b, a)` 不是冗余的——它们服务不同的查询模式。判断冗余必须结合查询模式。

### 未使用的索引

书中提到：有时会在不经意间创建未使用的索引。

📌 **洞见**：未使用索引是生产环境的常态——它们往往是：

- 早期版本查询遗留下来的
- A/B 测试创建的
- 过度防御性设计的产物

**识别未使用索引的工业级方法**：

```
-- 方法 1：使用 sys.schema_unused_indexes
SELECT * FROM sys.schema_unused_indexes;

-- 方法 2：使用 Performance Schema（更精细）
SELECT 
    OBJECT_SCHEMA, OBJECT_NAME, INDEX_NAME
FROM performance_schema.table_io_waits_summary_by_index_usage
WHERE INDEX_NAME IS NOT NULL 
  AND COUNT_STAR = 0 
  AND OBJECT_SCHEMA NOT IN ('mysql', 'performance_schema', 'sys')
ORDER BY OBJECT_SCHEMA, OBJECT_NAME;
```

> 💡 **AWS RDS 2026 年性能优化指南的重要提醒**：`sys.schema_unused_indexes` 在启用 Performance Schema 或重启后会为空——它需要时间收集有意义的使用统计。**此外，必须考虑季节性工作负载**——某个索引在正常运营期间可能看似未使用，但对于月末报告等周期性流程可能至关重要。

**删除未使用索引的收益**：

- 提升写入性能（减少索引维护）
- 减少存储占用
- 减轻 buffer pool 压力
- 简化优化器的决策空间

### 维护索引和表

索引不是"建完就忘"的对象。随着 DML 操作，索引会产生碎片、统计信息会过期、甚至可能发生损坏。

#### 找到并修复损坏的表

书中提到：有时会需要找到并修复损坏的表。

📌 **洞见**：InnoDB 表损坏在现代 MySQL 中已经罕见（得益于 ACID 和 crash recovery），但仍可能因硬件故障、kill -9、磁盘错误而发生。现代修复流程：

```
-- 1. 检查表
CHECK TABLE my_table;

-- 2. InnoDB 表损坏通常用 innochecksum 工具
-- 3. 严重损坏时，从备份恢复是最佳选择
```

#### 更新索引统计信息

📌 **洞见**：MySQL 优化器的决策完全依赖于索引统计信息（基数、数据分布等）。统计信息过期会导致优化器选择错误的执行计划。

```
-- 更新统计信息
ANALYZE TABLE my_table;

-- 对于大表，建议在以下时机执行：
-- 1. 大量数据变更（>10%）后
-- 2. 新索引创建后
-- 3. 定期（如每周）维护性执行
```

**8.4 的自动统计信息更新**：InnoDB 默认在表数据显著变化时自动更新统计信息，但显式 ANALYZE TABLE 仍是 DBA 工具箱的重要工具。

#### 减少索引和数据的碎片

书中提到：需要减少索引和数据的碎片。

📌 **洞见**：InnoDB 表的碎片来自：

- 大量的 DELETE → 留下半满的页
- 随机主键插入 → 页分裂
- 变长列的 UPDATE → 行溢出

**碎片整理方法**：

```
-- 方法 1：OPTIMIZE TABLE（InnoDB 下等价于 ALTER TABLE ... FORCE）
OPTIMIZE TABLE my_table;

-- 方法 2：显式重建
ALTER TABLE my_table ENGINE=InnoDB;

-- 方法 3：在线 DDL 工具（大表）
-- 使用 pt-online-schema-change 或 gh-ost
```

> ⚠️ **大表警示**：对于 GB 级大表，OPTIMIZE TABLE 会锁表并消耗大量 I/O。生产环境应在低峰期执行，或使用 pt-osc/gh-ost 做在线重建。

## 索引策略的第一性原理总结

把本章所有策略回溯到物理事实，我们得到一条**索引设计的推导链**：

```
B+tree 有序性 
  → 最左前缀原则 
  → 复合索引列顺序：等值条件优先，范围条件靠后
  
聚簇索引存储完整行数据 
  → 主键选择决定物理布局 
  → 顺序主键优于随机主键 
  → 主键越小，二级索引越紧凑
  
二级索引叶子节点存储主键值 
  → 回表成本 
  → 覆盖索引消除回表 
  
索引有序性可被 ORDER BY 借用 
  → 索引列顺序匹配 ORDER BY 
  → 降序索引消除 filesort
  
索引需要维护 
  → 写入成本 
  → 冗余/未使用索引治理
  → 碎片整理
```

📌 **洞见**：所有"索引最佳实践"都不是教条，而是从上述物理事实推导出的**情境化决策**。这就是为什么《高性能 MySQL》反复强调——**最佳索引设计需要你重写查询**，索引策略和查询优化是不可分割的整体（本书第 7 章和第 8 章必须对照阅读）。

## 工业界 2026 年索引实践的最新补充

结合国外英文资料和工业实践，以下是书里可能未充分覆盖的现代视角：

### 1. MySQL 8.4 的索引新特性

- **不可见索引（Invisible Indexes）**：测试索引删除效果而不真正删除
    
    ```
    CREATE INDEX idx_test ON table(column) INVISIBLE;
    ALTER TABLE table ALTER INDEX idx_test VISIBLE;  -- 或 INVISIBLE 隐藏
    ```
    
      
    查询会忽略不可见索引，让你在生产环境安全测试"如果这个索引不存在会怎样"
- **降序索引（Descending Indexes）**：避免 ORDER BY DESC 的 filesort
    
    ```
    CREATE INDEX idx_price_desc ON products(price DESC);
    ```
    
- **函数索引（Functional Index）**：对表达式建索引
    
    ```
    CREATE INDEX idx_fullname ON users ((CONCAT(first_name, ' ', last_name)));
    ```
    
- **GIPK（Generated Invisible Primary Key）**：8.0.30+ 自动为无主键表生成不可见主键
- **自适应哈希索引默认 OFF**：8.4 中 InnoDB AHI 默认为 OFF，由 DBA 按工作负载显式开启

### 2. 索引数量的现代共识

2026 年工业界建议：**单表索引数控制在 5-10 个**。过度索引会让存储膨胀 2-3 倍，并显著拖慢写入。

### 3. 索引设计的现代工作流

OneUptime 等工业界团队推荐的方法论：

```
1. 分析慢查询（EXPLAIN SELECT ... 识别 "ALL" 或高扫描行数）
2. 识别高选择性列（高基数，如 email 优于 gender）
3. 按查询模式设计复合索引（等值优先，范围靠后）
4. 考虑覆盖索引
5. EXPLAIN 验证，寻找 "Using index" 且无 "Using filesort"
6. 用不可见索引测试后再删除旧索引
7. 定期用 sys.schema_unused_indexes 审查和清理
```

### 4. 云环境（Amazon RDS）的索引治理

AWS 2026 年指南特别强调：

> 💡 **季节性工作负载陷阱**：`sys.schema_unused_indexes` 在启用 Performance Schema 或重启后会为空，且需要时间收集有意义的统计信息。**某个索引在正常运营期间可能看似未使用，但对于月末报告等周期性流程可能至关重要**——删除前必须评估季节性查询模式。

### 5. 用 Performance Schema 识别缺失的索引

```
-- 查找全表扫描的查询（新建索引的候选）
SELECT DIGEST_TEXT, COUNT_STAR AS exec_count, 
       SUM_ROWS_EXAMINED AS total_rows_examined,
       SUM_ROWS_EXAMINED / COUNT_STAR AS avg_rows_examined
FROM performance_schema.events_statements_summary_by_digest 
WHERE SUM_ROWS_EXAMINED > 1000 
ORDER BY SUM_ROWS_EXAMINED DESC 
LIMIT 20;
```

## 小结

这一章表面讲的是"怎么建索引"，深层传递的是**SRE 视角的索引哲学**：

**1. 索引是权衡，不是免费午餐**

索引用写入成本、存储成本、内存成本换取读性能。优秀的索引设计是"在正确的列上建正确的索引，在错误的列上不建索引"。

**2. 聚簇索引是 InnoDB 的物理秩序**

主键选择决定了整张表的物理布局。顺序主键（AUTO_INCREMENT 或雪花 ID）→ 写入高效；随机主键（UUIDv4）→ 碎片化灾难。主键越小，所有二级索引越紧凑。

**3. 最左前缀原则是一切复合索引设计的根源**

等值条件列在前，范围条件列在后；高选择性列优先；ORDER BY 列巧妙放置；覆盖索引追加 SELECT 列。

**4. 覆盖索引是性能的圣杯**

"Using index" 的出现意味着查询完全从索引获取数据，省去回表——这对宽表是高数量级的性能提升。

**5. 索引治理与索引创建同等重要**

- 冗余索引 → 用 `sys.schema_redundant_indexes` 识别
- 未使用索引 → 用 `sys.schema_unused_indexes` 或 Performance Schema 识别
- 碎片 → 用 OPTIMIZE TABLE 或在线 DDL 工具整理
- 统计信息 → 用 ANALYZE TABLE 更新

**6. MySQL 8.4 的现代索引工具箱**

- 不可见索引：安全测试索引删除
- 降序索引：消除 ORDER BY DESC 的 filesort
- 函数索引：对表达式建索引
- GIPK：自动为无主键表生成不可见主键
- AHI 默认 OFF：按工作负载显式调优

**7. 索引策略必须与查询优化协同**

正如《高性能 MySQL》所强调的——**创建真正最佳的索引通常需要你重写查询**。第 7 章和第 8 章是不可分割的整体：索引是查询优化的物理基础，查询重写是索引设计的目标导向。

> 💡 **贯穿全章的洞见**：索引设计的本质，是用 B+tree 的物理事实去**塑造数据的访问路径**。优秀的索引设计不是"哪里慢建哪里"的反应式修补，而是**从真实查询模式出发，反推应该建立的索引结构**。当索引结构与查询模式完美契合时，查询性能是数量级的提升；当索引结构与查询模式错位时，索引不仅是摆设，更是拖累写入和内存的累赘。
> 
> 一个真实工业级索引设计工作流：
> 
> 1. **收集查询模式**：从慢查询日志、Performance Schema 提取 TOP 20 高频且慢的查询
> 2. **分析访问路径**：对每个查询做 EXPLAIN，识别全表扫描、filesort、临时表
> 3. **设计复合索引**：按"等值 → 范围 → 排序 → 覆盖"的顺序设计列
> 4. **验证效果**：EXPLAIN 确认索引被使用，关注 "Using index" 和消除 "Using filesort"
> 5. **治理存量**：定期审查冗余索引和未使用索引
> 6. **持续迭代**：随着查询模式演化，索引结构也必须演化
> 
> 这套方法论，让索引设计从"DBA 的艺术"变成了"工程的科学"——这正是本书 SRE 视角的精髓：**用数据驱动决策，用可观测性闭环反馈，用自动化保障安全**。
> 
> 正如书中所言："最佳索引有时可以比仅仅'好'的索引提高大约两个数量级的性能"——这一个数量级的差距，就是"理解索引物理事实"与"机械套用索引建议"之间的差距。

📌 **给读者的实践清单**：

- ✅ 显式定义主键，使用顺序的 BIGINT（雪花 ID 或 AUTO_INCREMENT）
- ✅ 复合索引列顺序：等值条件 → 范围条件 → ORDER BY 列 → 覆盖列
- ✅ 用 `COUNT(DISTINCT LEFT(col, N))/COUNT(*)` 测算前缀索引选择性
- ✅ 追求覆盖索引，用 EXPLAIN 的 "Using index" 验证
- ✅ 定期审查 `sys.schema_unused_indexes` 和 `sys.schema_redundant_indexes`
- ✅ 大表 DDL 使用 gh-ost 或 pt-online-schema-change
- ✅ 删除索引前先用 INVISIBLE 索引测试
- ✅ 数据变更 >10% 后执行 ANALYZE TABLE
- ❌ 不要在长字符串上建全字段索引，用前缀索引或哈希列
- ❌ 不要建冗余索引（如同时有 (a,b) 和 (a)）
- ❌ 不要用 UUIDv4 字符串作主键
- ❌ 不要在索引列上使用函数（除非用函数索引）
- ❌ 不要盲目追求索引数量，单表控制在 5-10 个

**索引是数据库的导航系统，导航系统精准，数据访问就高效；导航系统冗余或错乱，数据库就在迷宫中徘徊。一个优秀的索引设计，是后续所有查询优化的物理基础——没有好的索引，再精巧的 SQL 重写都是空中楼阁。这正是为什么本书把"创建高性能的索引"放在"查询性能优化"（第 8 章）之前的第一性原理：先有好的索引结构，再有好的查询执行计划。**
