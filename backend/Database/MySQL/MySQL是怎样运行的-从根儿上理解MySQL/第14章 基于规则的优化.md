# 第14章 基于规则的优化（内含子查询优化二三事）

## 本章主线

成本优化回答多个等价计划谁更便宜，规则优化先回答这条表达式能否改写得更简单。它不需要知道数据大小，就可以删除不可能条件、传播常量、合并谓词、消除不必要的外连接。

规则优化的底线是语义等价，尤其要尊重 NULL、三值逻辑、外连接补 NULL 和子查询多行行为。

## 14.1 条件化简

### 14.1.1 移除不必要的括号

解析器把括号转换成表达式树；优化器可以根据 AND/OR 优先级删除不影响结果的括号。可读性上的括号仍值得保留，物理改写不等于建议用户把 SQL 写得难懂。

### 14.1.2 常量传递

如果条件推出 a=b 且 b=10，优化器可以把常量传播到 a。连接条件也可能让某一表列得到更窄的范围：

$$
a=b,\ b=c,\ c=10\Rightarrow a=10
$$

### 14.1.3 移除没用的条件

TRUE 条件可以删除；FALSE 条件可以提前得到空结果；矛盾范围可以在访问表前结束。需要注意 NULL 使很多看似简单的代数变形不成立。

### 14.1.4 表达式计算

与列无关的常量表达式可以在优化阶段计算，而不是每行重复计算。列上函数则可能影响索引可用性，不能把两者混为一谈。

### 14.1.5 HAVING 子句和 WHERE 子句的合并

若 HAVING 条件只依赖分组前的列，优化器可能把它下推到 WHERE，先过滤输入行，减少分组工作。依赖聚合结果的条件不能这样移动。

### 14.1.6 常量表检测

主键/唯一键等值条件使表最多返回一行，优化器可以先把它当作常量表，给后续连接提供常量值。这正是 const 访问方法与规则推理相遇的地方。

## 14.2 外连接消除

若左外连接后的 WHERE 条件要求右表某列非 NULL，而右表没有匹配时该列必为 NULL，那么未匹配行必然被过滤，左外连接可以改成内连接。

这种改写能让优化器自由调整连接顺序，但必须识别 NULL-rejected 条件。不要手工把所有 LEFT JOIN 改成 JOIN；业务可能确实需要保留未匹配左表行。

## 14.3 子查询优化

### 14.3.1 子查询语法

常见子查询包括标量子查询、行子查询、表子查询、IN/NOT IN、EXISTS/NOT EXISTS 和相关子查询：

```sql
SELECT *
FROM orders
WHERE amount > (SELECT AVG(amount) FROM orders);

SELECT c.id
FROM customers AS c
WHERE EXISTS (
  SELECT 1
  FROM orders AS o
  WHERE o.customer_id = c.id
);
```

标量子查询必须最多返回一行；NOT IN 遇到 NULL 时有特殊 UNKNOWN 结果，这是重写时最容易出错的地方。

### 14.3.2 子查询在 MySQL 中是怎么执行的

优化器可能选择把 IN/EXISTS 改写成半连接；物化子查询结果到临时结构；使用 EXISTS 策略按外层行查找；合并或物化派生表、视图和 CTE；或对相关条件做谓词下推。

官方文档列出的子查询策略包括 semijoin、materialization 和 EXISTS；派生表则可能 merge 或 materialize（[Optimizing Subqueries](https://dev.mysql.com/doc/refman/8.4/en/subquery-optimization.html)）。

手写 SQL 时应优先表达真实业务语义，再用 EXPLAIN 检查是否发生半连接、物化或重复执行。

## 14.4 总结

- 规则优化先把表达式变简单，再把候选计划交给成本模型；
- 常量传播、矛盾消除和条件下推可以减少数据流；
- 外连接消除必须尊重 NULL 补齐语义；
- 子查询可以被半连接、物化、EXISTS 或合并/物化派生表处理；
- NULL 和相关子查询是语义与性能的高风险交叉点。
