# 第7章 B+ 树索引的使用

## 本章主线

上一章回答索引是什么，本章回答什么时候真的有用。核心不是让索引存在，而是让优化器把查询条件翻译成连续的索引扫描区间，并尽量避免回表、排序和额外分组。

## 7.1 B+ 树索引示意图的简化

分析执行计划时可以把复杂树简化成：

```text
根页 → 中间页 → 叶子页 → 索引记录 → 可能的聚簇索引回表
```

简化图只用于回答访问路径，不代表真实页数量。实际树高、页填充率、分裂和缓存命中率要结合表大小和索引统计信息。

## 7.2 索引的代价

索引的总成本可以拆成：

$$
\text{index cost}
=\text{storage}
\,+\text{write amplification}
\,+\text{maintenance}
\,+\text{read complexity}
$$

每次插入、删除和更新都可能维护多个 B+ 树；二级索引越多，写放大越大。索引还会占用 Buffer Pool，挤出真正热的数据页。

因此给所有 WHERE 列都建索引是反模式。索引价值取决于过滤后剩余行数、访问列、查询频率、写入频率和数据分布。

## 7.3 应用 B+ 树索引

### 7.3.1 扫描区间和边界条件

B+ 树最擅长把条件变成有序区间。单列索引 x 上的 x = 10 是点区间，x BETWEEN 10 AND 20 是范围区间。

复合索引 (a,b,c) 可粗略理解为先用 a 定位，再在相同 a 的范围内用 b；一旦某列变成宽范围，后续列往往难以继续缩小物理扫描区间。

让索引列可搜索的关键是保持列本身可比较：

```sql
WHERE created_at >= '2026-01-01';

-- 可能让索引失去直接定位能力
WHERE DATE(created_at) = '2026-01-01';
```

第二种需求可以改写为半开区间，或使用合适的函数索引/生成列。隐式类型转换、对列做函数、前导通配符和不匹配的 collation 都可能扩大扫描。

### 7.3.2 索引用于排序

如果过滤和排序方向与索引顺序一致，叶子链可以直接产生有序结果，减少额外排序。复合索引中，等值条件固定前缀后，后续列更容易用于排序。

不能看到 ORDER BY 就盲目加索引，要比较待排序行数、现有索引扫描范围、回表数量、内存/磁盘排序和写入维护成本。MySQL 8.0 起支持降序索引语义，但具体计划仍由优化器决定。

### 7.3.3 索引用于分组

GROUP BY 如果能沿索引顺序产生同组数据，可以减少排序或临时表。分组列通常应在组合索引前部，但还要考虑过滤、聚合函数、NULL 语义和是否回表。

## 7.4 回表的代价

二级索引命中后，若叶子没有覆盖查询所需列，就要根据主键访问聚簇索引。若二级索引扫描出 M 行：

$$
\text{cost}
\approx
\text{secondary scan}
+M\times\text{clustered lookup}
$$

M 很小时回表通常值得；M 很大时，回表可能变成大量随机 I/O，优化器会考虑全表扫描。

## 7.5 更好地创建和使用索引

### 7.5.1 只为用于搜索、排序或分组的列创建索引

从真实 SQL、慢查询和访问模式反推索引，而不是从表结构机械生成。

### 7.5.2 考虑索引列中不重复值的个数

选择性可粗略表示为：

$$
\text{selectivity}
=\frac{\text{distinct values}}{\text{total rows}}
$$

高选择性更适合定位少量记录；低选择性列仍可能在组合索引、排序、覆盖查询或数据倾斜场景中有价值。

### 7.5.3 索引列的类型尽量小

索引键越短，页里能放的键越多，树扇出越大，缓存命中越有利。类型小必须建立在值域安全之上，不能为省字节让 ID 溢出。

### 7.5.4 为列前缀建立索引

长字符串可以只索引前缀：

```sql
CREATE INDEX idx_email_prefix ON users(email(32));
```

前缀过短会降低选择性；前缀索引通常不能完整承担排序或覆盖查询。应先用样本估计不同前缀长度的 distinct 数，再压测。

### 7.5.5 覆盖索引

若索引包含查询所需全部列，查询可以只扫描二级索引，不必回表。这是用更宽索引换更少随机访问，但会增加写成本和缓存占用。

### 7.5.6 让索引列以列名的形式在搜索条件中单独出现

可搜索条件尽量写成列与常量或参数比较，避免对列做函数、算术、隐式转换。表达式固定时，可考虑生成列或函数索引，并用 EXPLAIN 检查。

### 7.5.7 新插入记录时主键大小对效率的影响

递增主键通常把新记录集中插入树的右侧，页分裂较少；随机主键把写入分散到不同叶子页，增加页访问和分裂。随机 ID 不是绝对错误，但要用时间有序 ID、批量写入或页填充策略减轻代价。

### 7.5.8 冗余和重复索引

索引 a,b 通常已覆盖只以 a 为前缀的用途；完全相同的索引几乎总是冗余。删除前要检查约束、排序方向、覆盖列、在线变更和历史 SQL。

## 7.6 总结

- 索引优化的本质是把条件变成小而连续的扫描区间；
- 复合索引列顺序决定能否定位、排序和分组；
- 回表把二级索引收益和随机 I/O 联系起来；
- 选择性、键宽、覆盖能力和写放大必须同时权衡；
- 最终证据是 EXPLAIN、实际行数和真实延迟。
