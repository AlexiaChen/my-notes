# 第3章 字符集和比较规则

## 本章主线

字符串问题常被误认为“显示乱码”，其实至少包含三个问题：字符如何编码成字节；字节如何解码回字符；两个字符串如何判断相等、大小和排序。字符集回答编码问题，比较规则回答排序和相等问题，连接变量决定客户端和服务器如何交换字节。

```mermaid
flowchart LR
    A[应用中的 Unicode 字符] --> B[客户端编码]
    B -->|character_set_client| C[服务器解析 SQL]
    C -->|character_set_connection| D[字面量/表达式比较]
    D --> E[列的字符集与 collation]
    E -->|character_set_results| F[结果编码]
    F --> G[应用解码]
```

## 3.1 字符集和比较规则简介

### 3.1.1 字符集简介

字符集可以看成一个映射：

$$
\text{character} \longleftrightarrow \text{code point}
\longleftrightarrow \text{encoded bytes}
$$

Unicode 规定字符对应的码点，UTF-8 规定如何把码点编码成一到四个字节。数据库保存的是字节，客户端和服务器必须对字节的解释达成一致。

第一性原理是：**乱码不是字符消失，而是同一组字节被不同规则解释**。修乱码必须定位哪一段的编码假设错了。

### 3.1.2 比较规则简介

比较规则定义排序和相等关系，例如是否忽略大小写、重音，以及字符排序权重。它影响 WHERE 是否命中、唯一索引是否允许插入、GROUP BY 如何分组、LIKE 如何解释和索引能否利用。

### 3.1.3 一些重要的字符集

- latin1：单字节、范围有限，历史系统常见；
- utf8：MySQL 的历史别名，最多 3 字节，不覆盖全部 Unicode；
- utf8mb4：最多 4 字节，覆盖完整 Unicode，现代应用优先；
- binary：按字节比较，不做语言学层面的折叠。

选择 utf8mb4 后仍要选择与业务排序语义一致的 collation。用户名、自然语言标题、邮箱地址和版本号，可能需要不同规则。

## 3.2 MySQL 中支持的字符集和比较规则

### 3.2.1 MySQL 中的 utf8 和 utf8mb4

MySQL 的 utf8 不是完整 UTF-8；使用 emoji 或某些扩展汉字时可能出现 Incorrect string value。新建表和连接配置通常应使用 utf8mb4：

```sql
CREATE DATABASE app
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_0900_ai_ci;
```

升级旧库还要检查表、列、连接驱动、索引长度、排序语义和已有数据。字符集变宽会增加索引字节数，可能触发索引长度约束或降低页密度。

### 3.2.2 字符集的查看

```sql
SHOW CHARACTER SET;
SELECT * FROM information_schema.CHARACTER_SETS;
SELECT @@character_set_server, @@character_set_database;
```

排查要从服务器一路查到列：

```sql
SELECT TABLE_SCHEMA, TABLE_NAME, COLUMN_NAME,
       CHARACTER_SET_NAME, COLLATION_NAME
FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA = 'app'
  AND DATA_TYPE IN ('char','varchar','text');
```

### 3.2.3 比较规则的查看

```sql
SHOW COLLATION LIKE 'utf8mb4%';
SELECT @@collation_server, @@collation_connection;
```

名称中的 ci 通常表示不区分大小写，cs 表示区分大小写，bin 表示按编码值或字节比较。名称只是线索，最终语义要以版本文档和实际测试为准。

## 3.3 字符集和比较规则的应用

### 3.3.1 各级别的字符集和比较规则

MySQL 有多级默认值：

```text
服务器 → 数据库 → 表 → 列 → 表达式/字符串字面量
```

下一级没有显式指定时继承上一级。建议在数据库和关键列上显式指定：

```sql
CREATE TABLE users (
  id BIGINT PRIMARY KEY,
  login_name VARCHAR(128)
    CHARACTER SET utf8mb4
    COLLATE utf8mb4_bin NOT NULL,
  display_name VARCHAR(128)
    CHARACTER SET utf8mb4
    COLLATE utf8mb4_0900_ai_ci NOT NULL
);
```

登录名需要精确、稳定的唯一性；展示名更接近自然语言搜索。不要让所有列共享一种比较规则。

### 3.3.2 客户端和服务器通信过程中使用的字符集

连接变量可以这样理解：

- character_set_client：服务器如何解释客户端发来的 SQL 字节；
- character_set_connection：服务器如何解释未加 introducer 的字面量和表达式；
- character_set_results：结果返回客户端时使用的字符集。

查看当前连接：

```sql
SHOW VARIABLES LIKE 'character_set%';
SHOW VARIABLES LIKE 'collation%';
```

应用应在连接建立时显式设置字符集，而不是依赖服务器默认值。驱动 DSN 参数或 SET NAMES utf8mb4 都是在建立契约；SET NAMES 不改变列定义。

常见故障链是：

```text
应用 UTF-8 → 客户端按 latin1 发出 → 服务器按 latin1 解读
→ 数据库存入错误字节 → 结果再转回 UTF-8
```

存储层已被污染时，单纯改变连接字符集可能让显示变化，却不会修复数据。

### 3.3.3 比较规则的应用

比较规则会改变查询逻辑：

```sql
SELECT *
FROM users
WHERE login_name COLLATE utf8mb4_bin = 'Alice';
```

对列做函数或显式转换可能使索引难以使用，优先把正确 collation 固化在列定义上。唯一索引也受到 collation 影响：不区分大小写的规则可能把 Alice 和 alice 看成同一个键。

MySQL 8.4 默认服务器字符集是 utf8mb4，默认 collation 是 utf8mb4_0900_ai_ci，但旧版本和迁移环境可能不同（[Server Character Set and Collation](https://dev.mysql.com/doc/refman/8.4/en/charset-server.html)）。迁移前要比较 SHOW CREATE TABLE，而不是只看应用配置。

## 3.4 总结

- 字符集解决字节代表什么字符；
- collation 解决两个字符串是否相等、如何排序；
- 连接字符集解决客户端和服务器如何交换字节；
- 库、表、列的显式定义解决默认值漂移；
- utf8mb4 是现代起点，但业务仍要选择合适的排序和唯一性语义。
