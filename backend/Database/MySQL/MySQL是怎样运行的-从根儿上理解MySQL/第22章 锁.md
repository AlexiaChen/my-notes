# 第22章 工作面试老大难——锁

## 本章主线

事务隔离的两条路是：让读看到合适的旧版本，或让并发操作互相等待。锁解决的是谁可以同时修改/读取某个资源，MVCC 解决的是读者是否必须等待写者。

```mermaid
flowchart LR
    A[事务 T1 持有锁] --> B[事务 T2 请求不兼容锁]
    B --> C[等待队列]
    C --> D{是否形成环?}
    D -->|否| E[等待持有者提交/回滚]
    D -->|是| F[死锁检测]
    F --> G[选择一个事务回滚]
```

## 22.1 解决并发事务带来问题的两种基本方式

第一种方式是锁：让冲突操作排队；第二种方式是 MVCC：让普通读读取一个可见旧版本。工程上的关键不是锁越少越好，而是只在业务不变量需要的时候锁定正确的范围。

### 22.1.1 写-写情况

两个事务修改同一记录时，不能都把自己的值当成最终值。InnoDB 通常让第一个获得排他锁，第二个等待；若第一个回滚，第二个继续，若提交，第二个重新判断条件。

应用仍要处理死锁和锁等待超时，不能假设数据库会永远替它重试。

### 22.1.2 读-写或写-读情况

普通一致性读可以读旧版本，减少读写互相阻塞；锁定读则要求读取当前版本并加锁，适合读出后马上依据它修改的场景。

### 22.1.3 一致性读

普通 SELECT 在 InnoDB 中通常是非锁定一致性读，根据事务隔离级别和 ReadView 读取可见版本。它不等于读取最新物理记录，也不等于对结果加锁。

### 22.1.4 锁定读

锁定读读取当前版本并申请锁：

```sql
SELECT * FROM account WHERE id = 1 FOR UPDATE;
SELECT * FROM account WHERE id = 1 FOR SHARE;
```

FOR UPDATE 适合准备修改，FOR SHARE 适合保护读取到的行。MySQL 8.0 还支持 NOWAIT、SKIP LOCKED 等选项，适合队列和低等待场景，但会改变应用处理语义。

### 22.1.5 写操作

UPDATE、DELETE 和 INSERT 都需要当前读和锁。写操作的 WHERE 条件不仅决定改哪些行，也决定扫描和加锁哪些索引记录或间隙。

因此写 SQL 的索引设计具有双重作用：减少执行成本，也减少锁覆盖范围。没有合适索引的 UPDATE 可能扫描并锁住大量记录。

## 22.2 多粒度锁

多粒度锁允许在表、页、行等不同粒度上加锁。粗粒度锁管理简单但并发低，细粒度锁并发高但管理成本大。

意向锁是表级声明：事务准备在某些行上加共享或排他锁。它让另一个事务在请求表级锁时可以快速判断是否与行锁冲突，而不必扫描所有行锁。

## 22.3 MySQL 中的行锁和表锁

### 22.3.1 其他存储引擎中的锁

不同引擎可以采用表级锁、行级锁或其他并发机制。MyISAM 以表级锁为主，读写冲突时影响范围更大；MEMORY 等引擎也不自动获得 InnoDB 的事务与 MVCC 语义。

### 22.3.2 InnoDB 存储引擎中的锁

InnoDB 常见锁概念：

| 锁 | 保护对象 | 直觉 |
| --- | --- | --- |
| record lock | 索引记录 | 锁住一个已存在的索引键 |
| gap lock | 索引间隙 | 阻止范围内插入 |
| next-key lock | 记录及其前间隙 | 记录锁与间隙锁的组合 |
| insert intention lock | 插入意图 | 多个事务表达准备插入不同位置 |
| AUTO-INC lock | 自增值分配 | 保护特定自增分配策略 |
| intention lock | 表级意向 | 声明将要锁行 |

锁加在索引上，而不是抽象的行上。没有合适索引时，扫描的索引路径和锁范围可能远超业务以为的几行。

唯一索引的唯一等值搜索通常能缩小为记录锁；范围搜索可能覆盖间隙，尤其在 REPEATABLE READ 和锁定读/写操作中。READ COMMITTED 会改变部分间隙锁行为，但外键和唯一性检查仍有特殊例外。

### 22.3.3 InnoDB 锁的内存结构

锁对象通常关联事务、表/索引、页或记录位置、锁模式和等待状态。多个事务请求同一资源时形成队列；兼容请求可以并存，不兼容请求进入等待。

锁的内存结构是并发控制元数据，不是把整行复制一份。锁数量过多会增加内存和死锁检测成本，长事务会让队列长期存在。

## 22.4 语句加锁分析

分析一条语句的锁，要固定五个条件：存储引擎、隔离级别、自动提交、索引和实际数据范围。

### 22.4.1 普通的 SELECT 语句

在 InnoDB 的常见隔离级别下，普通 SELECT 使用一致性读，不主动给读取记录加排他锁，也通常不阻塞正在写的事务。SERIALIZABLE 等级会改变普通读行为。

```sql
START TRANSACTION;
SELECT * FROM account WHERE id = 1;
```

如果业务下一步要依据余额更新，普通 SELECT 不足以保护读到的值，应考虑锁定读或原子 UPDATE。

### 22.4.2 锁定读的语句

FOR UPDATE 和 FOR SHARE 读取当前版本并加相应锁。锁定范围取决于索引：

- 主键/唯一索引的唯一等值条件通常锁定匹配记录；
- 非唯一索引或范围条件可能锁定扫描到的记录和间隙；
- 没有索引时，扫描路径可能导致很大范围的锁竞争。

示例：

```sql
START TRANSACTION;
SELECT id, balance
FROM account
WHERE id = 1
FOR UPDATE;
UPDATE account SET balance = balance - 10 WHERE id = 1;
COMMIT;
```

### 22.4.3 半一致性读的语句

在某些 UPDATE 场景，若扫描到的记录已被其他事务锁住，InnoDB 可能把最新已提交版本交给 MySQL 层判断 WHERE 条件；若不匹配，就避免等待；若匹配，再等待锁并读取当前版本。这种机制常称为 semi-consistent read。

它优化的是被锁记录最终不符合条件的情况，不是取消写锁冲突，也不保证所有隔离级别和语句都有同样行为。实际以版本文档、隔离级别和锁监控为准。

### 22.4.4 INSERT 语句

INSERT 需要检查唯一键、外键并保护新记录位置。它可能使用插入意向锁与间隙锁协作；两个事务插入不同键值通常可以并行，但插入相同唯一键会发生冲突。

批量 INSERT 还会影响自增锁、redo、undo、页分裂和锁持有时间。大批量事务不一定更快，可能造成更大的回滚和复制延迟。

## 22.5 查看事务加锁情况

### 22.5.1 使用 information_schema 数据库中的表获取锁信息

活跃事务可以从 information_schema.INNODB_TRX 观察：

```sql
SELECT trx_id, trx_state, trx_started,
       trx_wait_started, trx_mysql_thread_id,
       trx_query
FROM information_schema.INNODB_TRX;
```

锁的现代接口主要在 Performance Schema：

```sql
SELECT * FROM performance_schema.data_locks;
SELECT * FROM performance_schema.data_lock_waits;
```

旧版本常见的 information_schema.INNODB_LOCKS 等接口可能不存在或已被替代。用 data_lock_waits 连接请求锁与阻塞锁，再连接线程、事务和 SQL 文本，才能得到完整等待链。

### 22.5.2 使用 SHOW ENGINE INNODB STATUS 获取锁信息

```sql
SHOW ENGINE INNODB STATUS;
```

它提供最近死锁、事务、锁等待、文件 I/O、Buffer Pool 和日志状态的文本快照。快照可能被后续事件覆盖，生产环境应同时采集 Performance Schema 和错误日志。

## 22.6 死锁

死锁是等待图中的环：

$$
T_1\rightarrow T_2\rightarrow\cdots\rightarrow T_1
$$

例子：

```text
T1 先锁 A，再请求 B
T2 先锁 B，再请求 A
```

InnoDB 通常检测到环后选择一个事务作为牺牲者回滚。应用必须捕获 deadlock 错误并重试整个事务，而不是只重试最后一条 SQL。

降低死锁概率的工程做法：

- 多行、多表更新采用一致的访问顺序；
- 事务尽量短，避免用户交互期间持锁；
- WHERE 和连接列建立合适索引，减少扫描和锁范围；
- 降低不必要的 FOR UPDATE；
- 对队列场景评估 NOWAIT 或 SKIP LOCKED；
- 记录死锁日志，分析真正的锁图，而不是只调大超时时间。

官方文档也建议保持一致操作顺序、缩短事务、为锁定读和更新条件建立索引，并在应用层处理重试（[Minimize and Handle Deadlocks](https://dev.mysql.com/doc/refman/8.4/en/innodb-deadlocks-handling.html)）。

## 22.7 总结

- 锁解决冲突排队，MVCC 解决普通读不必等待写；
- 锁的真实对象是索引记录和间隙，不是模糊的行；
- 索引既决定查询速度，也决定扫描和加锁范围；
- 普通 SELECT、锁定读、UPDATE 和 INSERT 的锁语义不同；
- 通过 data_locks、data_lock_waits、INNODB_TRX 和 INNODB STATUS 建立等待图；
- 死锁是并发系统的正常可能性，正确做法是缩小冲突并重试事务。
