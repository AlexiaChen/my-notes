
# 《Redis设计与实现》读书笔记 · 第4章～第6章

这三章是 Redis "数据结构与对象" 部分的硬核三重奏：**字典是 Redis 的骨架，跳跃表是有序集合的灵魂，整数集合是小数据集合的极致压缩**。如果说上一章的 SDS 和 adlist 是"构件"，那么这三章的结构就是"构件如何被组合成对外可见的、有语义保证的数据结构"。

> 💡 先说一个版本提醒：黄健宏的书基于 Redis 3.x 前后的源码。而今天的 Redis 7.x/8.x 在这些结构上已经有了**实质性演进**——字典从 `dictht ht[2]` 变为 `dictEntry **ht_table[2]` + `ht_used[2]` + `ht_size_exp[2]` 的新布局；哈希函数从 MurmurHash 换成了 **SipHash-1-2**（防御哈希洪泛攻击）；ziplist 全面退役，被 listpack 取代。所以下面我会**以书的结构为主线，用现代源码校正细节**。

## 第4章 字典

### 4.1 字典的实现

字典（`dict`）是 Redis 的**绝对核心**——不仅是 Hash/Set 类型的底层，更是**整个数据库的 key space 本身**。`redisDb` 里就内嵌了一个 `dict` 来存储 "key → redisObject" 的映射；此外，命令表（command name → handler）、Pub/Sub 订阅关系、Hash 类型的 hashtable 编码、Set 类型的 hashtable 编码，全都是 `dict`。

现代 Redis 的 dict 结构（简化自 `src/dict.h`）：

```
typedef struct dict {
    dictType *type;               // 函数指针集合：hash、dup、free、match
    dictEntry **ht_table[2];      // 两张哈希表，ht[0] 主用，ht[1] rehash 时用
    unsigned long ht_used[2];     // 每张表的已用节点数
    long rehashidx;               // rehash 进度，-1 表示未进行
    int16_t pauserehash;          // >0 时暂停 rehash
    signed char ht_size_exp[2];    // 每张表的大小的指数：size = 1 << exp
} dict;

typedef struct dictEntry {
    void *key;
    union { void *val; uint64_t u64; int64_t s64; double d; } v;
    struct dictEntry *next;       // 拉链法解决冲突
} dictEntry;
```

注意书里老版本的 `dictht` 结构（含 `table/size/sizemask/used` 四个字段）在现代版本里被**打散**了——`table` 直接提到 `ht_table[2]`，`size` 用指数 `ht_size_exp[2]` 表示（省内存），`used` 变成 `ht_used[2]`，`sizemask` 因为 size 永远是 2 的幂，可以直接用 `size - 1` 算出来，不必存储 。

> 📌 **第一性原理洞见**：dict 的设计本质上回答了三个问题——**"值怎么比较/复制/释放"**（交给 `dictType` 函数指针，实现多态）、**"数据怎么分布"**（2 的幂大小的桶数组 + 位与取模）、**"怎么在不停机的情况下扩容"**（双表 + rehashidx 进度指针）。这三个问题的解法共同构成了 Redis 能"边服务边迁移"的工程基础。

### 4.2 哈希算法

书里讲的 Redis 3.x 用的是 **MurmurHash2**（Austin Appleby 开发，分布均匀、速度快）。但从 **Redis 4.0 开始，默认哈希函数改为 SipHash-1-2**​ ：

```
uint64_t dictGenHashFunction(const void *key, size_t len) {
    return siphash(key, len, dict_hash_function_seed);
}
```

**为什么要换？**​ 因为 MurmurHash 不是加密哈希，攻击者可以构造大量哈希冲突的 key，让 Redis 的某个桶退化成单链表，从而打垮服务（这就是著名的**哈希洪泛攻击 / Hash Flooding**）。SipHash 带 per-process 随机种子，且是密钥化的伪随机函数，使得攻击者**无法预测 key 的哈希值**，从根本上杜绝了这种攻击 。

> ⚠️ 工业启示：凡是"用户可控制 key 的哈希表"，都应该用带随机种子的 SipHash 或类似算法。这是 2010 年后所有主流语言（Python、Ruby、Rust、Go 等）的标准做法，Redis 4.0 的这次更换是这个行业共识的一部分。

另外，对于命令名这类**大小写不敏感**的场景，Redis 单独用 `dictGenCaseHashFunction` 。

### 4.3 解决键冲突

Redis 用**拉链法**（chaining）：同一个桶里的多个 key 用 `dictEntry` 的 `next` 指针串成单向链表 。

新节点**头插法**入链：

```
de->next = d->ht[1].table[h];
d->ht[1].table[h] = de;
```

为什么头插？**假设最近插入的 key 更可能被马上访问**（局部性原理），头插让新 key 在链表查找时优先被命中，是 O(1) 操作 。

但拉链法的隐患是：如果哈希函数质量差或负载因子过高，某个桶的链表会很长，查找退化到 O(N)。这就是为什么必须有 rehash——**rehash 的本质就是用"重分布"换"链长回归短小"**。

### 4.4 rehash

**触发时机**（负载因子 = used / size）：

|场景|触发条件|
|---|---|
|正常情况|负载因子 ≥ 1，扩容|
|有 BGSAVE/BGREWRITEAOF 子进程|负载因子 ≥ 5 才扩容（避免 COW 页错误风暴）|
|负载因子 < 0.1|缩容|

**扩容大小**：`_dictNextPower` 保证新表大小是"**大于等于所需容量的最小 2 的幂**"（如所需 5 → 实际 8），保证位与取模可用 。

**rehash 的完整流程**：

1. 为 `ht[1]` 分配空间（是 `ht[0]` 的 2 倍或 1/2）
2. `rehashidx = 0`，标志 rehash 开始
3. 每次字典操作**顺带迁移 `rehashidx` 指向的桶**里的所有 entry 到 `ht[1]`
4. `rehashidx++`，直到 `ht[0]` 全空
5. `ht[0] = ht[1]`，`ht[1]` 清空，`rehashidx = -1`

### 4.5 渐进式 rehash

这是本章**最精妙的设计**，也是 Redis 能保持低延迟的关键。

**核心思想**：不一次性迁移所有数据（那会阻塞服务），而是**把迁移成本摊销到每一次字典操作上**。

**触发迁移的函数**：`_dictRehashStep()` 在 `dictAddRaw`、`dictGenericDelete`、`dictFind`、`dictGetRandomKey`、`dictGetSomeKeys` 这 5 个函数里被调用，每次迁移 1 个桶 ：

```
static void _dictRehashStep(dict *d) {
    if (d->pauserehash == 0) dictRehash(d, 1);
}
```

此外，`serverCron` 定时任务也会调用 `dictRehashMilliseconds()`，**每次最多花 1ms 批量迁移 100 个桶**，确保在没有客户端请求时 rehash 也能推进 。

**rehash 期间的查找/插入语义**：

- **查找**：先查 `ht[0]`，没命中再查 `ht[1]`
- **插入**：**永远只插入 `ht[1]`**​ ——这保证了 `ht[0]` 的 entry 数量只减不增，rehash 必然能收敛
- **删除/更新**：同理，两个表都可能是目标

> 💡 **第一性原理洞见**：渐进式 rehash 的本质是**把"一次性大停顿"拆解为"可摊销的微小成本"**。这是计算机科学里"摊还分析"（amortized analysis）思想的工程典范——单次操作多花 O(1) 时间做一点迁移，但换来了"永远不对用户请求造成毫秒级阻塞"的保证。这种思想在工业系统里无处不在：Go 语言的 map 扩容、Linux 内核的 RCU 机制、甚至 GC 里的增量标记，都是同一思路的变种。
> 
> 更深的洞见是：**rehash 期间查找要查两张表，理论上慢一倍**。但 Redis 选择接受这个"暂时的双倍成本"，换取"绝不被 rehash 卡住"。这是一个典型的工程取舍——**用均摊的小代价换确定性的低延迟**。

**现代版本的补充**：Redis 7.x 引入了 `pauserehash` 计数器，在有迭代器活跃或执行 `DICT_FLAG_NO_REHASH` 操作时暂停 rehash，避免迁移导致迭代器漏项或重复 。此外还有专门的 `dictScan()` 算法，用**反向位序游标**实现无状态游标扫描，即使在 rehash 过程中也能保证不漏不重 。

### 4.6 字典 API

按职能分类：

**生命周期**

- `dictCreate(type, privDataPtr)`：创建字典
- `dictRelease(dict)`：释放（逐 entry 调 free）

**增删改查**

- `dictAdd(dict, key, val)`：添加（key 不存在时）
- `dictReplace(dict, key, val)`：添加或替换
- `dictDelete(dict, key)` / `dictUnlink(dict, key)`：删除
- `dictFind(dict, key)`：查找，返回 `dictEntry*`
- `dictFetchValue(dict, key)`：查找并取值

**rehash 相关**

- `dictExpand(dict, size)`：主动扩容到指定 size
- `_dictRehashStep(dict)`：推进一步（内部）
- `dictRehashMilliseconds(dict, ms)`：限时批量迁移

**遍历**

- `dictGetIterator(dict)` / `dictGetSafeIterator(dict)`：安全/非安全迭代器
- `dictNext(iter)`：取下一项
- `dictScan(dict, cursor, fn, data)`：无状态游标扫描（用于 `SCAN` 命令）

**特殊操作**

- `dictGetRandomKey(dict)`：随机取一个 key（用于 `RANDOMKEY`）
- `dictGetSomeKeys(dict, dest, count)`：取多个随机 key

> ⚠️ **安全 vs 非安全迭代器**：安全迭代器会递增 dict 的 `iterators` 计数器，**阻止 rehash 发生**（防止条目在迭代期间被迁移导致重复或遗漏）；非安全迭代器则允许 rehash，但要求在迭代期间只能调 `dictNext()`，不能做修改操作 。这是 Redis 内部遍历机制的重要细节，书里讲得比较简略，现代源码里这块逻辑很关键。

### 4.7 重点回顾

按第一性原理提炼：

1. **dict 是 Redis 的底座**——数据库、Hash、Set、命令表全建筑在它之上
2. **双表结构 + rehashidx 进度指针**让扩容/缩容可以渐进完成，不阻塞服务
3. **哈希函数从 MurmurHash 升级到 SipHash**，根因是防御哈希洪泛攻击
4. **负载因子阈值 1（正常）/ 5（有子进程）**​ 是内存与性能的精妙平衡
5. **新节点只插 ht[1]**​ 保证 rehash 必然收敛
6. **摊还分析思想**：用每次操作的一点点开销，换来确定性的低延迟

## 第5章 跳跃表

### 5.1 跳跃表的实现

跳跃表（skip list）是 William Pugh 1989 年提出的**概率性平衡结构**，用多层链表实现 O(log N) 的查找/插入/删除，**实现复杂度远低于 AVL 树或红黑树**。

Redis 的 zset 在超过 `zset-max-listpack-entries`（默认 128）或 `zset-max-listpack-value`（默认 64 字节）阈值时，从 listpack 编码转换为 **skiplist 编码**​ 。但这个"skiplist 编码"并非单纯的跳跃表，而是**"dict + skiplist" 的组合**：

```
typedef struct zset {
    dict *dict;        // member → score 的 O(1) 映射
    zskiplist *zsl;    // 按 score 排序的跳跃表
} zset;
```

为什么需要两个结构？因为有序集合有两种高频操作：

- **按 member 查 score**（`ZSCORE`）：dict 提供 O(1)
- **按 score 范围查 member**（`ZRANGEBYSCORE`、`ZRANK`）：skiplist 提供 O(log N)

**单独用哪个都不行**：只用 dict 无法做范围查询；只用 skiplist 做 `ZSCORE` 要 O(log N)。两者结合，member 的 SDS 字符串在两个结构间**共享**，不重复存储，兼顾了性能和内存 。

**跳跃表节点结构**：

```
typedef struct zskiplistNode {
    sds ele;                        // 成员（共享自 dict）
    double score;                   // 分值
    struct zskiplistNode *backward; // 后退指针（仅 level 0）
    struct zskiplistLevel {
        struct zskiplistNode *forward;
        unsigned long span;         // 这一跳跨过了多少个 level 0 节点
    } level[];                      // 柔性数组，长度 = 节点层数
} zskiplistNode;

typedef struct zskiplist {
    struct zskiplistNode *header, *tail;
    unsigned long length;
    int level;
} zskiplist;
```

**三个关键设计点**：

1. **层数是随机的**：`zslRandomLevel()` 用 `ZSKIPLIST_P = 0.25` 的概率决定晋升——平均每节点 1.33 层，最大 32 层（可高效存 2^64 个元素）
2. **span 字段**：每个 forward 指针记录"跨过多少个 level 0 节点"。这是 Redis 相对 Pugh 原始算法的**关键改造**——让 `ZRANK` 从 O(N) 变成 O(log N)
3. **backward 指针只在 level 0**：支持从尾到头的反向遍历（用于 `ZREVRANGE`）

Redis 源码注释里明确写了相对原始算法的**三处改造**​ ：

> a) 允许 score 重复
> 
> b) 比较不仅看 score，还要看 member（satellite data）
> 
> c) 增加了 backward 指针，使 level 0 成为双向链表，支持反向遍历

**节点插入的核心逻辑**（`zslInsertNode`）：

```
// 从最高层往下找，记录每层的"前驱节点"到 update[]
// 同时用 rank[] 记录累积 span，用于后续更新
x = zsl->header;
for (i = zsl->level-1; i >= 0; i--) {
    rank[i] = (i == zsl->level-1) ? 0 : rank[i+1];
    while (x->level[i].forward &&
           x->level[i].forward->score <= score) {
        rank[i] += x->level[i].span;
        x = x->level[i].forward;
    }
    update[i] = x;
}
// 创建新节点，随机层数
level = zslRandomLevel();
node = zslCreateNode(level, score, ele);
//  spliced 进每层，并更新 span
for (i = 0; i < level; i++) {
    node->level[i].forward = update[i]->level[i].forward;
    update[i]->level[i].forward = node;
    // 调整 span，让 rank 查询保持准确
    node->level[i].span = update[i]->level[i].span - (rank[0] - rank[i]);
    update[i]->level[i].span = (rank[0] - rank[i]) + 1;
}
```

> 💡 **第一性原理洞见**：跳跃表相比红黑树的核心优势不是性能（两者都是 O(log N)），而是**工程简洁性 + 范围查询友好 + 实现无锁化的可能性**。
> 
> 具体来说：
> 
> - **红黑树需要复杂的旋转操作**来维持平衡，代码量大、容易出 bug；跳跃表靠概率自平衡，插入逻辑只有"找位置 + 头插"，几十行搞定
> - **跳跃表的范围查询是天然的**——找到起点后顺着 level 0 的链表往后扫即可；红黑树做范围查询要做中序遍历，且需要栈或递归
> - **缓存局部性更好**：跳跃表的节点在内存里是连续分配的（一次 `zmalloc` 分配 node + level 数组），而红黑树的每个节点单独分配，指针跳转多
> - **易于实现无锁并发**：LevelDB / RocksDB 的 MemTable 都用跳跃表，原因之一就是它比平衡树更容易做并发控制
> 
> Redis 选择跳跃表而不是红黑树，是工业界"**用概率换简洁，用空间换时间**"的经典案例。这个选择在 2009 年 antirez 写出来时并不常见，但今天已经被业界广泛验证——RocksDB、Lucene、Java 的 ConcurrentSkipListMap 都选择了跳跃表。

### 5.2 跳跃表 API

**创建与销毁**

- `zslCreate()`：创建空跳跃表（header 节点 32 层，score = 0）
- `zslFree(zsl)` / `zslFreeNode(node)`：释放

**核心操作**

- `zslInsert(zsl, score, ele)`：插入节点，返回新节点指针
- `zslDelete(zsl, score, ele, nodep)`：删除指定节点
- `zslUpdateScore(zsl, curscore, curEle, newscore)`：更新分值（内部是先删后插）
- `zslRandomLevel()`：按 0.25 概率随机层数

**查找类**

- `zslFirstInRange(zsl, range)` / `zslLastInRange(zsl, range)`：找范围内首尾节点
- `zslGetElementByRank(zsl, rank)`：按下标取节点（O(log N)，靠 span 累积）
- `zslLexValueGteMin` / `zslLexValueLteMax`：Lex 范围查询辅助

**工具类**

- `zslParseLexRange` / `zslFreeLexRange`：解析 `ZRANGEBYLEX` 的 Lex 范围
- `zslIsInLexRange` / `zslIsInRange`：判断范围是否有效

### 5.3 重点回顾

1. **zset 的 skiplist 编码 = dict + skiplist 组合**，member 的 SDS 共享，兼顾 O(1) 查分和 O(log N) 范围查询
2. **节点层数随机**，晋升概率 0.25，平均 1.33 层，最大 32 层
3. **span 字段是 Redis 的关键改造**，让 `ZRANK` / `ZRANGE` 从 O(N) 变为 O(log N)
4. **backward 指针只在 level 0**，支持 `ZREVRANGE` 反向遍历
5. **跳跃表 vs 红黑树**：牺牲了确定性平衡，换取了实现简洁、范围查询友好、缓存局部性好

> 📌 **工业应用**：跳跃表是**排行榜系统的天然数据结构**。`ZADD` 更新分数、`ZREVRANGE` 取 Top N、`ZRANK` 查排名，全是 O(log N)。这也是为什么几乎所有"实时排行榜"（游戏积分榜、热度榜、销量榜）都首选 Redis Sorted Set。另一个经典场景是**延时队列**——用时间戳做 score，`ZRANGEBYSCORE` 取出到期的元素进行处理。

## 第6章 整数集合

### 6.1 整数集合的实现

整数集合（intset）是 Redis 为了**节省内存**而设计的紧凑结构，专门用于存储**整数值**的集合（Set 类型在小数据量时的底层编码）。

```
typedef struct intset {
    uint32_t encoding;       // 当前编码：INTSET_ENC_INT16/32/64
    uint32_t length;         // 元素个数
    int8_t contents[];       // 柔性数组，按 encoding 解释
} intset;
```

**三个编码级别**：

|编码|字节宽度|数值范围|
|---|---|---|
|`INTSET_ENC_INT16`|2|[-32768, 32767]|
|`INTSET_ENC_INT32`|4|[-2147483648, 2147483647]|
|`INTSET_ENC_INT64`|8|[-2^63, 2^63-1]|

`contents` 是一个**紧密排列的、按值排序的**整数数组，没有任何指针开销、没有任何 per-element header。正是这种"裸数组"让 intset 在小集合场景下比 hashtable 编码**节省一个数量级的存储空间**。

查找用 `intsetSearch`——直接在数组上做**二分查找**，O(log N)，无额外内存分配 。

### 6.2 升级

intset 最核心的机制是**升级（upgrade）**：当插入一个新值，其类型超出了当前 `encoding` 所能表示的范围时，整个集合的编码会被提升，所有已有元素都被**重新编码**为新宽度。

源码核心逻辑（`intsetUpgradeAndAdd`）：

```
static intset *intsetUpgradeAndAdd(intset *is, int64_t value) {
    uint8_t curenc = intrev32ifbe(is->encoding);
    uint8_t newenc = _intsetValueEncoding(value);
    int length = intrev32ifbe(is->length);
    int prepend = value < 0;   // 负数放数组头部，正数放尾部

    is->encoding = intrev32ifbe(newenc);
    is = intsetResize(is, intrev32ifbe(is->length) + 1);

    // 关键：从后往前升级，避免覆盖尚未处理的源数据
    while (length--)
        _intsetSet(is, length + prepend,
                   _intsetGetEncoded(is, length, curenc));

    // 把新值放到头部或尾部
    if (prepend) _intsetSet(is, 0, value);
    else _intsetSet(is, intrev32ifbe(is->length), value);

    is->length = intrev32ifbe(intrev32ifbe(is->length) + 1);
    return is;
}
```

**为什么要从后往前升级？**​ 因为升级后每个元素的宽度变大，如果从前往后复制，新位置会覆盖还没读取的旧位置数据。**从后往前**保证了读取源数据时它还没被改写 。如果新值是负数（小于所有现有元素），它会占据 index 0，此时所有原有元素都要后移一位（`prepend = 1`）；如果是正数，则追加到尾部（`prepend = 0`）。

> 💡 这是一个非常经典的"数组扩容 + 宽度升级"的算法细节，体现了 C 语言底层编程里"内存布局意识"的重要性。

### 6.3 升级的好处

intset 通过"只升不降"的策略，获得了两个核心收益：

**① 节省内存**

如果一开始就按 INT64 分配，存储 1000 个小于 128 的小整数会浪费大量空间。intset 让集合**始终保持最小够用的编码**，在小整数场景下内存占用仅为 hashtable 编码的 **1/10 甚至更少**。

**② 避免降级开销**

intset **不支持降级**——一旦升级到 INT64，即使后来所有元素都变小了，编码也不会回退。为什么？因为要判断"是否可以降级"，必须遍历整个集合检查所有元素是否都在更小编码的范围内，**这个 O(N) 操作的成本在平时是不必要的**。Redis 选择"忍受"偶尔的内存冗余，换取"永远不在热路径上做降级检查" 。

> 📌 **第一性原理洞见**：intset 的"只升不降"是一个**用空间换时间、用偶发重写换常态紧凑**的典型权衡。
> 
> 更深一层的思考是：**intset 假设了"集合里的整数大多数时候是同一量级的"**。这是一个基于现实工作负载的经验假设——比如用户 ID、状态码、枚举值，通常不会在短时间内横跨 int16 到 int64 的巨大范围。在这个假设下，"升级是罕见事件"，所以即使升级要重写整个数组，摊销成本依然极低。
> 
> 这个设计哲学与 SDS 的"预分配"异曲同工——**都为"罕见事件"预付成本，换取"常见路径"的极致效率**。

**工业视角**：Set 类型在元素全是整数且数量 ≤ `set-max-intset-entries`（默认 512）时使用 intset 编码；一旦插入非整数或超出阈值，立即转换为 hashtable 编码，**且不可逆**​ 。这意味着：如果你有一个 Set 一开始存整数，后来又加入了字符串，它会永久变成 hashtable 编码，即使后来字符串又被删掉了——编码不会回退。这是运维时需要知道的细节。

### 6.4 降级

**intset 不支持降级**。

书里 6.4 节标题虽是"降级"，但实际内容是解释"为什么不实现降级"。核心原因：

1. **降级需要全集合遍历检查**，O(N) 成本会出现在热路径上
2. **即使能降级，收益也不确定**——万一很快又插入一个大整数，又会触发升级，来回震荡
3. **intset 的使用场景是"小集合"**，即使编码是 INT64，绝对值也不大（512 个元素 × 8 字节 = 4KB），内存浪费可接受

> ⚠️ 这是工程上"**不做**"比"做"更需要勇气的决策。很多年轻工程师会本能地认为"能优化就要优化"，但资深工程师知道：**每一个特性都有维护成本、测试成本、出现 bug 的成本**。intset 的"不降级"告诉我们——**有时候，故意保留一点不完美，系统反而更简单、更可靠**。

### 6.5 整数集合 API

- `intsetNew()`：创建空 intset（默认 INT16 编码）
- `intsetAdd(is, value, &success)`：插入，必要时升级编码
- `intsetRemove(is, value, &success)`：删除（O(N) 移动尾部元素覆盖）
- `intsetFind(is, value)`：查找（二分）
- `intsetRandom(is)`：随机返回一个元素
- `intsetGet(is, pos, &value)`：按下标取
- `intsetLen(is)` / `intsetBlobLen(is)`：长度 / 字节大小
- `intsetUpgradeAndAdd(is, value)`：内部使用，升级编码并插入

### 6.6 重点回顾

1. intset 是**紧密排列的、按值排序的整数数组**，无指针开销
2. 三种编码 INT16/32/64，**只升不降**
3. 升级时**从后往前**重写，避免覆盖源数据
4. 查找用二分，O(log N)
5. "不降级"是刻意的设计选择——用偶发的编码冗余，换取热路径的简洁

## 第4～6章的横向串联

把这三章放在一起看，你会发现 Redis 底层设计的一条**隐藏主线**：

```
┌─ dict：通用的键值映射，渐进式 rehash 保证低延迟
Redis 底层构件 ─┤─ skiplist：有序集合的"有序"部分，span 让排名 O(log N)
                └─ intset：整数集合的极致压缩，升级策略平衡内存与性能
```

**它们共同的基因**：

1. **都用"元数据 + 数组/链表"的封装**——dict 有 `ht_size_exp` 和 `ht_table`；skiplist 有 `length` 和 `level`；intset 有 `encoding` 和 `length`。元数据让操作从 O(N) 变 O(1) 或 O(log N)
2. **都体现"摊还思想"**——dict 的渐进式 rehash、intset 的升级，都是在"罕见事件"上付成本，让"常见路径"保持最快
3. **都拒绝"过度优化"**——dict 不去做完美的哈希函数（用 SipHash 足够）、skiplist 不追求确定性平衡（概率就够了）、intset 不做降级（空间换简洁）
4. **都服务于"内存 + 速度"的双重目标**——Redis 是内存数据库，每一个字节、每一次 realloc、每一次指针跳转都算计到了极致

> 💡 **工业落地的三条具体建议**：
> 
> 1. **警惕 big key 引发的 rehash 风暴**：当一个 dict 里有几百万个 key 时，扩容触发的渐进式 rehash 会持续很久，期间每次操作都要多查一张表。监控 `INFO stats` 里的 `rehash` 相关指标，必要时手动 `DEBUG RELOAD` 强制 rehash
> 2. **zset 的 `ZRANGE` 类操作要小心**：虽然查找是 O(log N)，但**返回 M 个元素就是 O(log N + M)**。如果 M 很大（比如 `ZRANGE key 0 -1`），会一次性返回海量数据阻塞网络，生产环境务必分页
> 3. **intset 的"只升不降"提醒我们**：如果你的 Set 曾经插入过大整数，即使后来删除了，它也会永久停留在 hashtable 编码。对于内存敏感的 Sorted Set / Set 场景，尽量保证元素类型统一
