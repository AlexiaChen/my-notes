
# 《Redis设计与实现》读书笔记 · 第20章 Lua脚本 + 第21章 排序

这两章表面上一个是"服务端可编程"，一个是"查询算子"，但放到一起看，它们揭示的是同一个 Redis 设计哲学的深化——**用"计算下推"替代"数据上拉"**。

- 没有 Lua 之前，复杂逻辑必须在客户端拼装多条命令，面临网络往返、竞态条件、WATCH 冲突重试等问题
- 没有 SORT 之前，要对 List/Set 排序只能把数据拉到客户端排，浪费带宽且无法在服务端原子完成

Lua 脚本把"计算"下推到了数据所在的位置；SORT 把"排序+关联+分页+投影"这一整套查询能力下推到了数据所在的位置。**这两者都是"在数据近端完成工作"思想的具体化**——这也是分布式系统"Move computation to data"第一性原理在 Redis 中的体现。

> ⚠️ 版本提醒：黄健宏的书基于 Redis 3.0 时代的脚本实现。现代 Redis 在脚本复制、函数（Functions）等方面已有重大演进——**Redis 5.0 起脚本效果复制（effects replication）成为默认模式；Redis 7.0 起不再支持逐字复制（verbatim replication）；Redis 7.0 引入了 Functions 作为 EVAL 的现代替代品**​ 。下面以书的结构为主线，用现代 Redis 官方文档校正细节。

# 第20章 Lua脚本

## 20.1 创建并修改Lua环境

Redis 选择 **Lua 5.1**​ 作为嵌入式脚本语言，这是一个值得深究的决策 。

**为什么是 Lua 而非 JavaScript/Python/Starlark？**

|考量维度|Lua 5.1|其他语言|
|---|---|---|
|嵌入体积|~200KB，极轻量|Python ~10MB+|
|启动速度|毫秒级|较慢|
|沙箱能力|天然支持，可剥夺 IO 库|需要大量改造|
|语法简洁度|极简，易于限制|各有特点|
|与 C 的互操作|极好（Lua C API 是业界标杆）|一般|

**Redis 启动时的 Lua 环境初始化**：

Redis 服务器启动时调用 `scriptingInit()` 完成以下工作 ：

1. **创建 Lua 状态机**：`luaL_newstate()` 创建一个全局的 `lua_State`，整个服务器生命周期内复用
2. **加载标准库**：只加载 `base`、`table`、`string`、`math`、`debug` 等**纯计算库**
3. **剥夺危险库**：**不加载**​ `io`、`os`（除 `os.clock` 和 `os.time` 受控外）、`package` 等——这保证了脚本无法直接访问文件系统、网络、加载外部模块
4. **注入 Redis 专用全局表**：
    - `redis.call()` / `redis.pcall()`：执行 Redis 命令
    - `redis.error_reply()` / `redis.status_reply()`：构造返回值
    - `redis.log()`：写 Redis 日志
    - `redis.replicate_commands()`：启用效果复制（现代 Redis 默认开启）
    - `redis.sha1hex()`：计算 SHA1
5. **注册全局表 `KEYS` 和 `ARGV`**：执行脚本时填充
6. **设置随机数种子**：在非确定性的效果复制模式下，每次调用重新随机播种

> 💡 **洞见：Lua 环境的"减法设计"**
> 
> Redis 对 Lua 环境做的是**"减法"而非"加法"**——不是给 Lua 增加一堆 Redis 专属 API，而是**剥掉**​ Lua 中所有可能破坏沙箱安全的库（io、os、package），只保留纯计算能力，然后**精准注入**​ Redis 需要的几个桥接函数。
> 
> 这种"最小权限原则"（Principle of Least Privilege）在安全设计中至关重要。如果 Lua 脚本能 `os.execute("rm -rf /")`，那 Redis 就成了 RCE（远程代码执行）的载体。**沙箱的本质不是"提供什么"，而是"剥夺什么"**。
> 
> 更深层的洞见是：**Redis 的 Lua 环境是一个"受控的计算沙箱"，而非"通用的编程语言环境"**。它被刻意设计为"图灵完备但资源受限"——你可以写循环、条件、函数，但不能做 IO、不能加载模块、不能使用未受控的随机数。这种"图灵完备 + 资源受限"的组合，恰好是"服务端可编程"的理想形态。

### 工业应用：原子化限流器

```
-- 滑动窗口限流
local current = redis.call('INCR', KEYS[1])
if tonumber(current) == 1 then
    redis.call('EXPIRE', KEYS[1], ARGV[1])
end
local ttl = redis.call('TTL', KEYS[1])
if tonumber(current) > tonumber(ARGV[2]) then
    return {current, ttl, 0}  -- 超限
end
return {current, ttl, 1}  -- 通过
```

整个限流逻辑在服务端原子完成，避免了"先 INCR 再判断 再 EXPIRE"的多命令竞态。


## 20.2 Lua环境协作组件（续）

> ⚠️ **关键限制：为什么 SCRIPT KILL 只能杀"只读脚本"？**
> 
> 这是一个深刻的工程决策。如果脚本已经修改了数据集（写了 key），此时中断它，数据集就会停留在"半修改"状态——这破坏了 Redis 的原子性保证。因此 Redis 的选择是：**只读脚本可以杀（因为没副作用），写脚本不能杀（因为杀了数据不一致）**。对于"写脚本死循环"的场景，唯一的解药是 `SHUTDOWN NOSAVE`——手动重启且放弃内存数据 。
> 
> 这个限制的工业启示：**永远不要让 Lua 脚本进入不可控的长循环**。在写脚本时必须自评：最坏情况下脚本执行多久？如果涉及循环，循环次数是否有限？是否可能被恶意输入触发死循环？

### 工业应用：批量操作原子化

```
-- 原子化转账（补全上轮截断处）
local from = KEYS[1]
local to = KEYS[2]
local amount = tonumber(ARGV[1])

local from_balance = tonumber(redis.call('GET', from))
if from_balance < amount then
    return {err = "insufficient funds"}
end

-- 所有操作在脚本内原子执行，外部客户端看不到中间状态
redis.call('DECRBY', from, amount)
redis.call('INCRBY', to, amount)

-- 可选：记录流水
local txid = redis.call('INCR', 'txn:counter')
redis.call('HSET', 'txn:' .. txid, 'from', from, 'to', to, 
           'amount', amount, 'ts', redis.call('TIME')[1])

return {ok = "transferred"}
```

整个转账逻辑（余额校验 + 扣款 + 入账 + 流水）在服务端一次性原子完成。对比不用脚本的方案：

```
# 不用脚本的"朴素方案"
WATCH account:A
GET account:A                    # RTT 1
# 客户端判断余额...
MULTI
DECRBY account:A 100             # RTT 2
INCRBY account:B 100
EXEC
# 如果 EXEC 返回 nil，整个流程重试
# 涉及 2-3 次 RTT + WATCH 冲突重试开销
```

**脚本方案的优势**：

- **1 次 RTT**：所有逻辑打包发送
- **无竞态**：脚本执行期间整个 Redis 实例阻塞，不存在 WATCH 冲突
- **无重试风暴**：不会因为高并发下的 WATCH 冲突导致大量重试
- **逻辑封装**：业务规则（如余额校验、流水记录）封装在服务端，客户端代码极简

> 💡 **洞见：Lua 脚本的本质是"存储过程"（Stored Procedure）**
> 
> 如果你用过 Oracle/PostgreSQL 的 PL/SQL、T-SQL，会发现 Lua 脚本在 Redis 中的角色如出一辙——**把业务逻辑下推到数据所在的位置执行**。这是数据库领域"存储过程"思想的 Redis 版实现。
> 
> 但这里有个关键差异：传统关系型数据库的存储过程是**持久化的、有名字的、可版本管理的**；而 Redis 2.6~6.2 的 EVAL 脚本是**临时的、无名字的、每次都要传脚本体的**。这就导致了著名的"EVAL 反模式"：
> 
> ```
> # 反模式：每次调用都传不同脚本体
> EVAL "return 'Hello'" 0
> EVAL "return 'Scripting!'" 0
> ```
> 
> 这两个脚本在 Redis 的脚本缓存中是两条不同的记录，浪费内存且破坏缓存复用 。正确的做法是用 `SCRIPT LOAD` 预加载，然后用 `EVALSHA` 调用；或者更好的——**用 Redis 7.0+ 的 Functions**。

### Redis 7.0+ 的现代方案：Functions

Redis 7.0 引入了 **Functions**——这是 EVAL 脚本的"正统升级版" ：

```
#!lua name=banking
redis.register_function('transfer', function(keys, args)
    local from = keys[1]
    local to = keys[2]
    local amount = tonumber(args[1])
    
    local balance = tonumber(redis.call('GET', from) or '0')
    if balance < amount then
        return {err = "insufficient funds"}
    end
    
    redis.call('DECRBY', from, amount)
    redis.call('INCRBY', to, amount)
    return {ok = "transferred"}
end)
```

```
# 加载一次（管理员操作，类似加载模块）
FUNCTION LOAD "#!lua name=banking
redis.register_function('transfer', function(keys, args)
    ...
end)"

# 之后任何客户端按名字调用
FCALL transfer 2 account:A account:B 100
```

**EVAL 脚本 vs Functions 的本质差异**​ ：

|维度|EVAL 脚本|Functions|
|---|---|---|
|持久化|不持久化，重启后丢失|持久化在 RDB/AOF 中|
|复制|作为命令复制（效果复制）|作为数据集的一部分自动复制|
|命名|无名字，只有 SHA1 哈希|有人类可读的名字|
|版本管理|无|库级别，支持 `FUNCTION LOAD ... REPLACE`|
|调用方式|EVAL/EVALSHA + 脚本体或 SHA|FCALL + 函数名|
|部署模型|客户端应用的一部分|服务端扩展，独立于应用|

> 📌 **工业建议**：**Redis 7.0+ 的新项目直接用 Functions，不要用 EVAL**。Functions 是"一等公民"——它持久化、自动复制、按名调用、支持库级别版本管理，彻底解决了 EVAL 脚本"每次传脚本体 / SHA 缓存易失 / 重启后要重新加载"的痛点 。这标志着 Redis 的"服务端可编程"从"临时脚本"演进为"存储过程"。

## 20.3 EVAL命令的实现

**命令签名**：`EVAL script numkeys [key [key ...]] [arg [arg ...]]`

**numkeys 参数的深层含义**：

`numkeys` 指明后续参数中有多少个是 **key 名**。这个看似简单的设计，背后是 Redis Cluster 正确性的基石：

- KEYS 表中的 key 用于**路由决策**——Cluster 根据 KEYS[1] 的哈希槽决定脚本在哪个节点执行
- 如果脚本内部访问了未在 KEYS 中声明的 key，在 Cluster 环境下会导致**跨槽错误**或**路由错误**​
- 因此 Redis 的约定是：**脚本要访问的所有 key 必须显式声明在 KEYS 中，且必须全部在同一个哈希槽**

```
-- ✅ 正确：所有 key 显式声明
EVAL "redis.call('SET', KEYS[1], ARGV[1])" 1 mykey "value"

-- ❌ 错误：key 硬编码在脚本内，Cluster 无法路由
EVAL "redis.call('SET', 'mykey', ARGV[1])" 0 "value"
```

**EVAL 的执行流程**（基于源码分析 ）：

```
① 脚本编译: luaL_loadbuffer() 编译 Lua 源码 → 得到 Lua 函数
   ↓
② 脚本缓存: 计算 SHA1，存入 server.scripts 字典
   ↓
③ 构造执行环境:
   - 设置 KEYS 全局表（1-indexed）
   - 设置 ARGV 全局表（1-indexed）
   - 设置全局变量保护（防止脚本污染全局环境）
   ↓
④ 执行脚本: lua_pcall() 调用编译后的函数
   ↓
⑤ 类型转换: 将 Lua 返回值转为 RESP 协议返回客户端
   ↓
⑥ 清理: 重置 Lua 环境状态（全局变量保护生效）
```

**类型转换的细节**（这是工业应用中最容易踩坑的点）：

|Lua 值|RESP 转换|说明|
|---|---|---|
|`nil`|nil bulk|空值|
|`false`|nil bulk|注意：false 也转成 nil！|
|`true`|integer 1||
|Number|Integer|**截断为整数**，小数部分丢失！|
|String|Bulk String||
|Table（数组）|Multi-bulk|递归转换每个元素|
|Table `{err = "..."}`|Error|构造错误回复|
|Table `{ok = "..."}`|Status|构造状态回复|

> ⚠️ **工业警示**：Lua 的 Number 转 RESP 时被**截断为整数**——`return 3.14` 会变成 `3`。如果业务需要浮点数返回，必须转成 String：`return tostring(3.14)`。这是无数 Redis Lua 脚本 bug 的根源 。

**确定性要求**：

Redis 早期版本严格要求脚本是"确定性的"——因为旧版复制是"逐字复制"（将 EVAL 命令本身传播给副本）。如果主库脚本里用了 `TIME`、`RANDOMKEY`、`SRANDMEMBER` 等非确定性命令，副本重放时会产生不同结果，导致主从数据不一致。

现代 Redis（5.0+）改为**效果复制（effects replication）**——主库执行脚本后，将脚本产生的**写命令效果**传播给副本，而非脚本本身 。这放宽了确定性要求，但**最佳实践仍然是编写确定性脚本**——不依赖 `TIME`、不使用 `math.random()`（除非显式播种）、不访问未声明的 key。

## 20.4 EVALSHA 命令的实现

**命令签名**：`EVALSHA sha1 numkeys [key ...] [arg ...]`

**核心思想**：用 `SCRIPT LOAD` 预加载脚本，获得 SHA1 哈希，之后用 `EVALSHA` 调用，避免每次传输完整脚本体。

```
SCRIPT LOAD "redis.call('SET', KEYS[1], ARGV[1])"
→ "a42059b5113a3f5f2c6c5b7e8e6e6e6e6e6e6e6e"  (SHA1)

EVALSHA a42059b5113a3f5f2c6c5b7e8e6e6e6e6e6e6e6e 1 mykey "value"
```

**NOSCRIPT 错误与重试**：

如果副本或服务端重启后脚本缓存丢失，`EVALSHA` 会返回 `NOSCRIPT` 错误。工业级客户端的标准处理模式：

```
def eval_script(script_sha, keys, args):
    try:
        return redis.evalsha(script_sha, keys, args)
    except NoScriptError:
        # 重新加载脚本
        script_sha = redis.script_load(original_script)
        return redis.evalsha(script_sha, keys, args)
```

**EVALSHA 的工业价值**：

- **带宽节省**：脚本体可能几百字节到几 KB，SHA1 只有 40 字符
- **CPU 节省**：避免每次重新编译 Lua 源码
- **缓存命中**：热门脚本常驻服务端脚本缓存

> 💡 **洞见：EVALSHA 是"内容寻址"（Content Addressing）思想的应用**
> 
> SHA1 哈希是脚本内容的指纹——相同的脚本内容永远产生相同的 SHA1，不同的脚本内容几乎不可能碰撞。这种"用内容哈希作为标识符"的模式在现代系统中无处不在：
> 
> - Git 用 SHA1 标识 commit、tree、blob
> - Docker 用 SHA256 标识 image layer
> - IPFS 用 SHA256 标识文件
> - Redis 用 SHA1 标识脚本
> 
> **内容寻址的本质是"去重"**——相同内容只存储一份，用哈希引用。EVALSHA 让 Redis 脚本获得了这种能力：脚本体只需传输一次，之后用 40 字符的 SHA1 引用。这是"空间换时间"的反面——**"时间换空间"**：用首次的传输开销，换来后续所有调用的带宽节省。

### Redis 7.0+ 的更优解：FCALL

Functions 彻底消灭了 EVALSHA 的复杂度——函数通过 `FUNCTION LOAD` 加载一次后，持久化在 RDB/AOF 中，自动复制到所有副本，客户端只需 `FCALL function_name` 调用 。不再有 SHA1 管理、不再有 NOSCRIPT 错误、不再有重启后重新加载的烦恼。

## 20.5 脚本管理命令的实现

Redis 提供了一组脚本管理命令：

|命令|作用|实现要点|
|---|---|---|
|`SCRIPT LOAD script`|加载脚本，返回 SHA1|编译并存入 `server.scripts` 字典|
|`SCRIPT EXISTS sha1 [sha1 ...]`|检查脚本是否存在于缓存|查 `server.scripts` 字典|
|`SCRIPT FLUSH`|清空脚本缓存|释放所有脚本的 Lua 函数|
|`SCRIPT KILL`|终止正在运行的脚本|仅当脚本未执行写操作时有效|
|`FUNCTION LOAD`|加载函数库（Redis 7.0+）|存入 `server.functions` 字典，持久化|
|`FUNCTION DUMP`|导出所有函数库|用于迁移|
|`FUNCTION RESTORE`|导入函数库|用于恢复|

**SCRIPT KILL 的实现机制**：

Redis 的 Lua 解释器每执行 100,000 条指令，触发一次超时钩子检查 。如果脚本执行时间超过了 `lua-time-limit`（默认 5000ms），Redis 进入"BUSY 状态"：

- 其他客户端的所有命令都回复 `-BUSY` 错误
- 脚本本身继续运行（因为 Lua 没有安全的中断机制）
- 管理员可以执行 `SCRIPT KILL`：

```
if 脚本是只读的:
    SCRIPT KILL 成功，脚本被终止，服务器恢复正常
else:
    SCRIPT KILL 失败，提示只能用 SHUTDOWN NOSAVE
```

> ⚠️ **生产环境灾难场景**：一个写了数据的 Lua 脚本进入死循环。
> 
> - `SCRIPT KILL` 拒绝执行（因为会破坏原子性）
> - 唯一恢复手段：`SHUTDOWN NOSAVE`（丢弃上次持久化以来的所有数据）
> - 这是**灾难性的生产事故**
> 
> **预防措施**：
> 
> - 脚本中禁止无限循环，循环必须有明确的退出条件
> - 对大集合的操作使用游标式迭代（如 `SCAN`），单次处理有限数量的元素
> - 合理设置 `lua-time-limit`（默认 5 秒）
> - 优先使用只读脚本变体 `EVAL_RO` / `EVALSHA_RO` / `FCALL_RO`——它们可以随时被 `SCRIPT KILL` 终止

### 工业应用：脚本版本管理

```
# 开发环境：加载函数库
FUNCTION LOAD "#!lua name=session_mgr
redis.register_function('create_session', function(keys, args)
    ...
end)
redis.register_function('destroy_session', function(keys, args)
    ...
end)"

# 升级：使用 REPLACE 标志覆盖
FUNCTION LOAD REPLACE "#!lua name=session_mgr
redis.register_function('create_session', function(keys, args)
    ... -- 新逻辑
end)
..."
```

函数库的"库级别版本管理"让 Redis 服务端逻辑可以像应用代码一样进行 CI/CD 部署 。

## 20.6 脚本复制

这是 Redis 脚本机制中演进最剧烈的部分。

**Redis 3.0 时代（黄健宏书所述）：逐字复制（Verbatim Replication）**

```
主库执行: EVAL "redis.call('SET', 'foo', 'bar')" 0
    ↓
传播给副本: EVAL "redis.call('SET', 'foo', 'bar')" 0
    ↓
副本执行同样的脚本
```

**问题**：

1. **非确定性脚本会导致主从不一致**：脚本中如果使用 `TIME`、`RANDOMKEY` 等，副本执行时会产生不同结果
2. **脚本必须确定性**：限制了脚本的表达能力
3. **带宽浪费**：每次都要传播完整脚本体

**Redis 5.0+：效果复制（Effects Replication）**

```
主库执行: EVAL "redis.call('SET', 'foo', 'bar')" 0
    ↓
主库产生写效果: SET foo bar
    ↓
传播给副本: SET foo bar  (只是写命令，而非脚本本身)
    ↓
副本执行 SET 命令
```

**优势**：

1. **放宽了确定性要求**：脚本可以使用非确定性命令，因为传播的是效果而非脚本
2. **带宽节省**：传播的是实际写命令，而非脚本体
3. **副本执行简单**：无需 Lua 解释器参与

**Redis 7.0+ Functions 的复制**：

Functions 作为"数据集的一部分"被复制——函数库本身通过 `FUNCTION LOAD` 的复制传播到所有副本，之后 `FCALL` 调用通过效果复制传播 。这意味着：

- 函数定义本身在副本上持久存在
- 函数调用产生的写效果传播到副本
- 副本重启后函数仍在（因为持久化在 RDB/AOF 中）

> 💡 **洞见：脚本复制的演进揭示了分布式系统的核心难题——"计算"还是"结果"？**
> 
> 当主节点执行了一段计算（脚本），如何让从节点达到相同状态？两条路：
> 
> **路径 A：传播计算（逐字复制）**
> 
> - 优点：从节点独立执行，逻辑透明
> - 缺点：必须保证计算是确定性的；带宽开销大
> 
> **路径 B：传播结果（效果复制）**
> 
> - 优点：从节点无需重算；放宽确定性要求；带宽小
> - 缺点：丢失了"计算过程"的信息；调试困难
> 
> Redis 从 A 演进到 B，反映了工业界的一个普遍趋势——**在"计算"和"结果"之间，分布式系统越来越倾向于传播"结果"**。类似的演进也发生在：
> 
> - 数据库：物理复制（Physical Replication）优于逻辑复制（Logical Replication）
> - 流式系统：Chandy-Lamport 快照算法传播状态而非事件
> - 状态机复制：Raft 的日志复制本质上是"结果"（已提交的日志条目）的传播
> 
> **根本原因**：在大规模分布式系统中，"结果"比"计算"更紧凑、更可靠、更容易保证一致性。计算的确定性是脆弱的（依赖时钟、随机数、外部环境），而结果是确定的（已经发生了）。

---

## 20.7 重点回顾

1. **Lua 5.1 被嵌入 Redis**，剥夺了 io/os/package 等危险库，形成沙箱环境
2. **脚本执行原子性来自单线程**：执行期间整个 Redis 实例阻塞，所有其他客户端等待
3. **redis.call() 与 redis.pcall()**：前者遇错中止脚本，后者返回错误供处理
4. **类型转换陷阱**：Lua Number 转 RESP 时截断为整数；false 转成 nil
5. **KEYS 声明是 Cluster 正确性的基石**：所有访问的 key 必须在 KEYS 中声明且同槽
6. **EVALSHA 用 SHA1 内容寻址**避免重复传输脚本体；NOSCRIPT 错误需客户端重试加载
7. **SCRIPT KILL 只能杀只读脚本**；写脚本死循环只能 `SHUTDOWN NOSAVE`
8. **脚本复制从"逐字复制"演进为"效果复制"**（Redis 5.0+），放宽了确定性要求
9. **Redis 7.0+ 的 Functions 是 EVAL 的现代替代品**：持久化、自动复制、按名调用、库级别版本管理
10. **只读脚本变体**：EVAL_RO/EVALSHA_RO/FCALL_RO 可随时被 SCRIPT KILL 终止

# 第21章 排序

SORT 是 Redis 中最被低估的命令——它是 Redis 唯一的内置"查询处理器"，具备排序、关联、投影、分页、结果持久化等完整的 SQL-ish 能力。理解 SORT，就理解了"如何在 Redis 这种 K/V 存储之上构建查询能力"。

> ⚠️ **版本提醒**：SORT 命令在 Redis 7.4 之前不支持 Cluster 模式下的跨节点外部键访问 。这意味着 `SORT mylist BY weight_*` 这种依赖外部键的排序，在 Cluster 环境下要求所有相关 key 必须在同一个哈希槽（使用 Hash Tag 强制同槽）。Redis 7.4 开始部分放宽了这个限制，但仍需谨慎。

## 21.1 SORT \<key\> 命令的实现

**基本形式**：`SORT key [BY pattern] [LIMIT offset count] [GET pattern [GET pattern ...]] [ASC|DESC] [ALPHA] [STORE destination]`

**时间复杂度**：O(N+M*log(M))，N 是待排序元素数量，M 是返回的元素数量 。

**默认行为**：

```
# 数值排序（默认）
SORT mylist
# 等价于: SELECT * FROM mylist ORDER BY value+0 ASC

# 字符串排序
SORT mylist ALPHA
# 等价于: SELECT * FROM mylist ORDER BY value ASC

# 降序
SORT mylist DESC
SORT mylist ALPHA DESC
```

**底层实现流程**：

```
① 获取待排序集合: 从 List/Set/Sorted Set 中取出所有元素
    ↓
② 排序: 根据 ALPHA/ASC/DESC/BY 选项排序
    ↓
③ 限制: 根据 LIMIT 选项裁剪结果集
    ↓
④ 关联: 根据 GET 选项获取外部键的值
    ↓
⑤ 持久化: 根据 STORE 选项保存结果集
    ↓
⑥ 返回: 向客户端返回结果
```

> 💡 **洞见：SORT 是 Redis 的"查询处理器"原型**
> 
> SORT 命令几乎具备了一个简化版 SQL SELECT 的所有核心子句：
> 
> - **FROM**：要排序的 key（List/Set/Sorted Set）
> - **ORDER BY**：BY 选项（外部键权重）或元素本身
> - **ASC/DESC**：排序方向
> - **LIMIT**：分页
> - **GET**：投影（获取外部键的值）
> - **STORE**：结果物化（物化视图）
> 
> 这是 Redis 在"K/V 存储"之上构建"查询能力"的一次大胆尝试。它证明了——**即使是最简单的 K/V 存储，只要提供合适的算子（排序、关联、投影），就能表达相当复杂的查询语义**。
> 
> 但 SORT 也是 Redis 设计哲学的"异类"——它是 Redis 中**最复杂、最慢、最耗内存**的命令之一。这暗示了一个真理：**在 K/V 存储之上硬塞关系型查询能力，是有代价的**。这也解释了为什么 Redis 后来推出了 **Search 模块（RediSearch）**​ 来承担真正的查询需求，而 SORT 更适合轻量级的、偶发的排序需求。

---

## 21.2 ALPHA 选项的实现

**作用**：将排序元素作为**字符串**进行字典序排序，而非默认的数值排序。

```
# 默认数值排序
RPUSH numbers 1 10 2 20 3
SORT numbers
→ 1) "1" 2) "2" 3) "3" 4) "10" 5) "20"   (数值: 1<2<3<10<20)

# ALPHA 字符串排序
SORT numbers ALPHA
→ 1) "1" 2) "10" 3) "2" 4) "20" 5) "3"   (字典序: "1"<"10"<"2"<"20"<"3")
```

**实现细节**：

- 不带 ALPHA 时，Redis 尝试将元素解析为 double 精度浮点数，按数值比较
- 带 ALPHA 时，Redis 按字符串的字节序比较（UTF-8 感知，取决于 `LC_COLLATE` 环境变量）
- ALPHA 排序比数值排序慢（字符串比较开销更大）

> ⚠️ **工业警示**：如果不加 ALPHA 对字符串排序，Redis 会尝试将字符串解析为数字，解析失败的元素会被当作 0 处理，导致排序结果不符合预期。

---

## 21.3 ASC 选项和 DESC 选项的实现

**作用**：指定排序方向。ASC 是默认值。

```
SORT mylist ASC    # 升序（默认）
SORT mylist DESC   # 降序
```

**底层实现**：Redis 使用 `qsort()` 或类似快速排序算法，比较函数根据 ASC/DESC 决定比较结果的符号。

**与 ALPHA 的组合**：

```
SORT mylist ALPHA DESC   # 字符串降序
SORT mylist DESC ALPHA   # 等价写法，选项顺序无关
```

SORT 命令的选项**摆放顺序不影响执行逻辑**——Redis 内部按固定顺序处理各选项（详见 21.9 节）。

---

## 21.4 BY 选项的实现

**BY 选项是 SORT 命令最强大的特性**——它允许用**外部键的值**作为排序权重，而非元素本身。

```
# 准备数据
RPUSH user_ids 1 2 3
SET user_age_1 25
SET user_age_2 30
SET user_age_3 20

# 按外部键 user_age_* 排序
SORT user_ids BY user_age_*
→ 1) "3" 2) "1" 3) "2"   (年龄: 20 < 25 < 30)
```

**模式匹配机制**：

`BY user_age_*` 中的 `*` 是占位符，Redis 将其替换为每个元素的值，构造出实际的 key 名：

- 元素 `1` → key `user_age_1` → 值 `25`
- 元素 `2` → key `user_age_2` → 值 `30`
- 元素 `3` → key `user_age_3` → 值 `20`

然后根据这些外部键的值进行排序。

**Hash 字段作为权重**：

```
# 用 Hash 的字段作为权重
HSET user:1 age 25 name "Alice"
HSET user:2 age 30 name "Bob"
HSET user:3 age 20 name "Charlie"

SORT user_ids BY user:*->age
→ 1) "3" 2) "1" 3) "2"
```

`user:*->age` 表示：key 为 `user:{元素值}`，字段为 `age`。

**跳过排序的优化**：

```
# BY 一个不存在的 key，跳过排序
SORT user_ids BY nosort
```

`nosort` 是 Redis 的特殊关键字——它告诉 Redis 不进行排序，直接按原顺序返回。这在配合 GET 选项获取外部数据时非常有用，可以避免不必要的排序开销 。

> 💡 **洞见：BY 选项本质上实现了"索引扫描"**
> 
> 在关系型数据库中，我们会建索引来加速 ORDER BY。Redis 没有索引的概念，但 BY 选项提供了一种"手动索引"机制——**将排序权重存储在与元素 ID 相关联的外部键中，然后按这些外部键的值排序**。
> 
> 这种模式在 Redis 数据建模中极为常见：
> 
> - `user:{id}:score` 作为排序权重
> - `product:{id}:price` 作为排序权重
> - `article:{id}:publish_time` 作为排序权重
> 
> 它体现了"**用键名模式匹配模拟索引**"的思想——这是 K/V 存储中构建查询能力的通用范式。代价是：每次 SORT BY 都要访问 N 个外部键，时间复杂度 O(N)，且这些 key 必须与源 key 同槽（Cluster 环境）。

---

## 21.5 带有 ALPHA 选项的 BY 选项的实现

当 BY 选项引用的外部键值是**字符串**而非数值时，必须配合 ALPHA 选项：

```
# 外部键值是字符串
SET user_name_1 "Alice"
SET user_name_2 "Bob"
SET user_name_3 "Charlie"

# 字符串排序必须加 ALPHA
SORT user_ids BY user_name_* ALPHA
→ 1) "1" 2) "3" 3) "2"   (字典序: Alice < Charlie < Bob)
```

如果不加 ALPHA，Redis 会尝试将字符串解析为数值，解析失败默认为 0，导致排序结果错误。

**实现细节**：

BY 选项与 ALPHA 选项的组合在排序阶段协作：

1. 先从外部键获取权重值
2. 根据 ALPHA 标志决定按字符串还是数值比较
3. 执行排序

---

## 21.6 LIMIT 选项的实现

**作用**：对排序结果进行分页，类似 SQL 的 `LIMIT offset, count`。

```
SORT mylist LIMIT 0 10     # 返回前 10 个
SORT mylist LIMIT 10 5     # 跳过前 10 个，返回接下来的 5 个
```

**实现细节**：

LIMIT 在排序完成后、返回结果前执行。Redis 内部维护一个结果数组，LIMIT 操作就是对该数组进行切片。

**时间复杂度优化**：

理论上，LIMIT offset count 仍然需要完整排序 O(N_log(N))，然后跳过 offset 个元素。但 Redis 的实现做了优化——__如果只需要前 M 个元素，可以使用部分排序算法（如堆排序的变体），将复杂度降至 O(N_log(M))**​ 。

> 💡 **工业应用：分页查询**
> 
> ```
> # 第一页
> SORT articles BY article:*->publish_time LIMIT 0 20 ALPHA DESC
> 
> # 第二页
> SORT articles BY article:*->publish_time LIMIT 20 20 ALPHA DESC
> ```
> 
> 这是 Redis 中实现"按权重分页"的标准模式。但要注意——**SORT 每次都从头排序**，LIMIT 只裁剪结果，不优化排序本身。对于大数据集，每次分页都要 O(N*log(N)) 排序，性能较差。
> 
> **优化方案**：如果排序权重是固定的（如发布时间），可以考虑使用 **Sorted Set**​ 存储 `(元素, 权重)` 对，然后用 `ZRANGE`/`ZREVRANGE` 实现 O(log(N)+M) 的分页——这远比 SORT+LIMIT 高效。

---

## 21.7 GET 选项的实现

**作用**：根据排序后的元素，获取外部键的值，实现"关联查询"。

```
# 准备数据
RPUSH article_ids 1 2 3
HSET article:1 title "Redis 入门" author "Alice" publish_time 100
HSET article:2 title "Redis 进阶" author "Bob" publish_time 200
HSET article:3 title "Redis 实战" author "Charlie" publish_time 150

# 按发布时间排序，并获取标题
SORT article_ids BY article:*->publish_time GET article:*->title
→ 1) "Redis 入门" 2) "Redis 实战" 3) "Redis 进阶"
```

**GET 的特殊模式**：

- `GET #`：返回元素本身
- `GET article:*->field`：返回 Hash 字段值
- 可指定多个 GET：`GET article:*->title GET article:*->author`

**GET 的执行时机**：

GET 选项在 LIMIT 之后执行——只对 LIMIT 裁剪后的结果集获取外部键 。这很关键：它意味着 GET 操作的数量与最终返回的元素数量成正比，而非与全集大小成正比。

```
# 完整示例：排序 + 分页 + 关联 + 返回元素本身
SORT article_ids 
    BY article:*->publish_time 
    LIMIT 0 2 
    GET article:*->title 
    GET article:*->author 
    GET #
→ 1) "Redis 入门"      (title of article 1)
   2) "Alice"          (author of article 1)
   3) "1"              (element itself)
   4) "Redis 实战"     (title of article 3)
   5) "Charlie"        (author of article 3)
   6) "3"              (element itself)
```

**多个 GET 的返回顺序**：

如果指定多个 GET 选项，**返回结果按 GET 的声明顺序排列**​ 。因此调整 GET 选项的顺序会改变返回结果的结构——这是 SORT 命令中**唯一对选项摆放顺序敏感的环节**。

> 💡 **洞见：GET 选项实现了"JOIN"语义**
> 
> 在关系型数据库中，JOIN 是多表查询的核心。Redis 没有 JOIN，但 GET 选项提供了一种"手动 JOIN"机制：
> 
> - `SORT article_ids` 相当于 FROM 子句
> - `BY article:*->publish_time` 相当于 ORDER BY 子句
> - `GET article:*->title` 相当于 JOIN article 表并 SELECT title 字段
> 
> 这是 K/V 存储模拟关系查询的典型手法。但代价明显：
> 
> - **每个 GET 都要访问外部 key**：M 个结果 × K 个 GET = M×K 次 key 访问
> - **Cluster 环境限制**：所有相关 key 必须同槽
> - **性能随数据量线性下降**
> 
> 这再次印证了"在 K/V 存储上硬塞关系语义是有代价的"。对于复杂的关联查询，应该考虑：
> 
> - **数据冗余**：将常用字段冗余到主 key 中（如 Hash 中同时存 title 和 publish_time）
> - **使用 Sorted Set**：如果排序权重固定，用 ZSET 存储 (元素, 权重)，避免 BY 选项的外部键访问
> - **使用 RediSearch**：真正的搜索引擎，支持复杂查询

---

## 21.8 STORE 选项的实现

**作用**：将排序结果保存到目标 key 中，目标 key 的类型为 List。

```
SORT article_ids BY article:*->publish_time STORE sorted_articles
→ (integer) 3   # 返回结果集大小

LRANGE sorted_articles 0 -1
→ 1) "1" 2) "3" 3) "2"
```

**实现细节**：

1. 执行排序，得到结果集
2. 如果目标 key 已存在，**先删除旧值**（无论原类型是什么）
3. 将结果集作为 List 存入目标 key
4. 返回结果集的元素数量

**STORE 的工业价值**：

- **物化视图**：将频繁执行的排序结果缓存起来
- **预处理**：将排序结果存储，供后续 LIMIT 分页使用
- **解耦**：生产者执行 SORT+STORE，消费者只需 LRANGE

```
# 生产者：定时任务执行排序并存储
SORT hot_articles BY article:*->views STORE hot_articles_cache

# 消费者：直接读取缓存
LRANGE hot_articles_cache 0 9   # 热门文章 Top 10
```

> ⚠️ **工业警示**：STORE 会**覆盖目标 key 的原值**，不论原类型。如果目标 key 原本是个 Hash 或 Sorted Set，执行 STORE 后它会变成一个 List。这在生产环境中可能引发隐蔽的 bug——务必使用专用的 key 作为 STORE 目标。

---

## 21.9 多个选项的执行顺序

这是 SORT 命令最精妙的设计——**无论用户在命令行中以什么顺序书写选项，Redis 内部都以固定顺序执行**​ 。

**固定执行顺序**：

```
① 排序阶段: 使用 ALPHA / ASC / DESC / BY 选项
   ↓
② 限制阶段: 使用 LIMIT 选项裁剪结果集
   ↓
③ 关联阶段: 使用 GET 选项获取外部键
   ↓
④ 持久化阶段: 使用 STORE 选项保存结果
   ↓
⑤ 返回阶段: 向客户端返回结果
```

**关键特性**：

1. **选项书写顺序无关**：以下三种写法完全等价
    
    ```
    SORT mylist ALPHA DESC BY weight_* LIMIT 0 10 GET object_* STORE result
    SORT mylist LIMIT 0 10 BY weight_* ALPHA GET object_* STORE result DESC
    SORT mylist STORE result DESC BY weight_* GET object_* ALPHA LIMIT 0 10
    ```
    
      
    都产生完全相同的排序结果集。
2. **GET 选项的顺序敏感**：如果指定多个 GET，返回结果的结构取决于 GET 的声明顺序 。
3. **BY 选项的特殊性**：`BY nosort` 可以跳过排序阶段，直接进入限制阶段 。

**为什么这样设计？**

> 💡 **洞见：SORT 的固定执行顺序是"管道（Pipeline）"思想的体现**
> 
> SORT 命令的每个选项对应管道中的一个"算子"：
> 
> - 排序算子（BY/ALPHA/ASC/DESC）
> - 限制算子（LIMIT）
> - 投影算子（GET）
> - 物化算子（STORE）
> 
> 这些算子按**数据流的方向**排列：先排序（产生有序全集）→ 再限制（裁剪子集）→ 再投影（获取外部数据）→ 最后物化（存储结果）。这种顺序不是随意的，而是符合"数据处理的自然流向"：
> 
> 1. 必须先有完整的排序结果，才能正确地 LIMIT
> 2. 必须先 LIMIT 裁剪，才能对最终结果集 GET（避免对丢弃的元素做无用功）
> 3. 必须先 GET 完所有数据，才能 STORE 完整的结果集
> 
> 这正是数据库查询处理器中"Query Plan"的核心思想——**将查询分解为多个算子，按最优顺序执行**。Redis 的 SORT 命令虽然简单，但其内部执行顺序与 PostgreSQL/MySQL 的查询计划器遵循相同的原则：
> 
> - **尽早过滤**（LIMIT 尽早裁剪数据量）
> - **投影下推**（GET 在 LIMIT 之后执行，减少外部键访问次数）
> - **物化最后**（STORE 在所有计算完成后执行）
> 
> 理解这一点，你就能理解为什么 SORT 命令的选项"书写顺序无关"——因为 Redis 内部会**重新排列**这些选项到最优执行顺序。这是对用户的极大便利：用户无需关心选项顺序，Redis 自动优化。

### SORT 命令的工业应用总结

```
# 场景：电商商品列表，按销量降序分页，返回商品名称和价格

# 数据模型
RPUSH products 1 2 3 4 5
HSET product:1 name "iPhone" price 9999 sales 1000
HSET product:2 name "MacBook" price 19999 sales 500
HSET product:3 name "iPad" price 5999 sales 800
HSET product:4 name "AirPods" price 1999 sales 2000
HSET product:5 name "Watch" price 2999 sales 1200

# 查询：销量 Top 3，返回名称和价格
SORT products 
    BY product:*->sales 
    DESC 
    LIMIT 0 3 
    GET product:*->name 
    GET product:*->price
→ 1) "AirPods" 2) "9999" 3) "iPhone" 4) "1999" 5) "Watch" 6) "2999"
```

**这个查询等价于 SQL**：

```
SELECT p.name, p.price 
FROM products p 
ORDER BY p.sales DESC 
LIMIT 3;
```

但 SORT 的性能特征是 O(N_log(N) + M_K)，N 是商品总数，M 是返回数量（3），K 是 GET 数量（2）。当 N 很大时，每次查询都要全量排序，性能堪忧。

**工业优化建议**：

1. **小规模数据（N < 1000）**：SORT 完全够用，简单直观
2. **中大规模数据**：使用 Sorted Set 存储 `(商品ID, 销量)`，用 `ZREVRANGE` 分页，复杂度 O(log(N)+M)
3. **复杂查询需求**：使用 RediSearch 模块，支持真正的二级索引和复杂查询
4. **Cluster 环境**：所有相关 key 必须用 Hash Tag 强制同槽，否则 BY/GET 会报 CROSSSLOT 错误

## 21.10 重点回顾

1. **SORT 是 Redis 内置的查询处理器**，支持排序、关联、投影、分页、物化
2. **默认数值排序**，ALPHA 选项启用字符串字典序排序
3. **ASC/DESC 控制排序方向**，ASC 为默认
4. **BY 选项实现"索引排序"**：用外部键的值作为排序权重，是 SORT 最强大的特性
5. **GET 选项实现"JOIN"语义**：根据排序结果获取外部键的值，支持多个 GET
6. **LIMIT 选项实现分页**，在排序完成后裁剪结果集
7. **STORE 选项将结果物化为 List**，覆盖目标 key 的原值
8. **多选项执行顺序固定**：排序 → 限制 → 关联 → 物化 → 返回；书写顺序无关（GET 顺序除外）
9. **性能特征**：O(N+M*log(M))，N 为元素总数，M 为返回数量
10. **Cluster 限制**：BY/GET 引用的外部键必须与源 key 同槽（Redis 7.4 前严格限制）

## 第20~21章的深层洞见：Redis 的"计算下推"哲学

把 Lua 脚本和 SORT 命令放在一起看，一个共同的设计哲学浮现出来——**"Move Computation to Data"（计算下推到数据）**。

### 洞见一：服务端可编程性的演进路径

Redis 的服务端计算能力沿着一条清晰的演进路径发展：

```
Redis 1.0: 仅命令                        （客户端拼装逻辑）
    ↓
Redis 2.6: EVAL + Lua                    （脚本下推，原子执行）
    ↓
Redis 5.0: 效果复制                      （脚本复制优化）
    ↓
Redis 7.0: Functions                     （脚本持久化、命名、版本化）
    ↓
未来: 多语言 Functions（JavaScript 等）     （打破 Lua 5.1 限制）
```

这条路径揭示了一个真理——**"计算下推"是 K/V 存储的必然演进方向**。单纯的 GET/SET 无法满足复杂业务需求，必须把计算能力带到数据所在的位置。



### 洞见二：SORT 是"查询处理器"的雏形，但不是终点

SORT 命令用 BY/GET/LIMIT/STORE/ALPHA/ASC/DESC 七个选项，构建了一个**简化版的 SQL SELECT 处理器**。它证明了在 K/V 存储之上，用"算子组合"的方式可以表达出强大的查询语义。

但它的根本局限在于——**查询时全量计算，无索引、无优化、阻塞实例**。这促使 Redis 生态沿着两条路径演进：

**路径 A：预计算下沉（Sorted Set）**

- 将"排序"从查询时下沉到写入时
- ZADD 时 O(log N) 维护顺序
- ZRANGE 时 O(log N + M) 读取，不阻塞
- 适用：排行榜、Top N、范围查询

**路径 B：专门引擎（RediSearch）**

- 写入时构建倒排索引、数值树、GEO 索引
- 查询时走索引，O(log N + M)
- 支持全文检索、聚合、向量相似度
- 从 Redis 8 起内置于核心

这两条路径的共同启示是——**"通用算子"解决 80% 的简单问题，"专门引擎"解决 20% 的复杂问题**。Redis 不试图用 SORT 一个命令解决所有查询需求，而是提供层次化的能力：

- **简单排序**​ → SORT（灵活但慢）
- **固定权重排序**​ → Sorted Set（快但权重固定）
- **复杂查询**​ → RediSearch（功能完整但引入模块依赖）

### 洞见三：Lua 脚本与 SORT 是"计算下推"的两种范式

|维度|Lua 脚本（第20章）|SORT 命令（第21章）|
|---|---|---|
|计算模型|图灵完备的程序|固定的查询算子组合|
|灵活性|极高（可写任意逻辑）|有限（仅排序+关联+投影+分页）|
|原子性|整个脚本原子执行，阻塞实例|整个命令原子执行，阻塞实例|
|适用场景|复杂业务逻辑、原子操作|轻量级排序查询|
|性能特征|取决于脚本逻辑|O(N+M*log(M))|
|集群限制|所有 KEY 必须同槽|BY/GET 外部键必须同槽（7.4+）|
|演进方向|→ Functions（持久化、命名）|→ RediSearch（专门引擎）|

这两种范式体现了 Redis 对"计算下推"的两种不同回答：

- **Lua 脚本**：给用户一个"通用的计算沙箱"，用户自己决定下推什么计算
- **SORT**：给用户一个"专用的查询算子"，Redis 替用户决定如何下推排序计算

它们的共同点：**都是为了避免"数据上拉"**——如果不在服务端做这些计算，客户端就必须把数据拉到本地处理，在网络带宽受限的环境下这是不可接受的。

### 洞见四：Redis 的"模块进化"策略

从 SORT → Sorted Set → RediSearch 的演进，揭示了 Redis 的一个核心策略——**"核心简单，模块扩展"**：

```
Redis 核心: 5 种数据结构 + 原子命令 + Lua 脚本
    ↓
模块层: RediSearch（查询引擎）
       RedisJSON（文档存储）
       RedisTimeSeries（时序数据）
       RedisBloom（概率数据结构）
       RedisGraph（图数据库）
    ↓
Redis 8: 主流模块内置于核心
```

这种"核心 + 模块"的架构带来了三个关键优势：

1. **核心保持稳定**：5 种数据结构 + 单线程模型十几年不变，保证了 Redis 的简洁性和可预测性
2. **模块独立演进**：RediSearch、RedisJSON 等模块可以按照自己的节奏迭代，不受核心版本限制
3. **按需加载**：用户只加载需要的模块，避免核心膨胀

但"模块进化"的最终归宿是**内化**——当某个模块足够成熟、使用足够广泛时，它会被吸入核心。RediSearch 在 Redis 8 中内置就是最新的例证 。这预示着一个趋势：**Redis 正在从一个"数据结构服务器"演进为一个"多模型数据库平台"**，而这一切都建立在"核心简单 + 模块扩展 + 成熟内化"的策略之上。

### 洞见五：第一性原理视角——为什么 Redis 能做这么多事？

如果我们追溯 Redis 能够不断扩展出 Pub/Sub、事务、Lua 脚本、SORT、Cluster、RediSearch 等能力的根本原因，会发现它源自一个简单的第一性原理：

> **"在单线程、内存、键值存储的基础之上，任何计算都可以被表达为'对数据结构的操作序列'"**。

这个原理的力量在于：

- **单线程**​ → 天然的原子性，无需锁机制
- **内存**​ → 微秒级延迟，计算下推的成本极低
- **键值存储**​ → 数据寻址简单，O(1) 访问
- **数据结构丰富**​ → 5 种基础结构覆盖了绝大多数数据建模需求

从这四条公理出发，可以推导出 Redis 的所有能力：

- 想要"消息广播"？→ 用 List + 阻塞操作 → Pub/Sub
- 想要"原子批处理"？→ 用命令队列 + 执行窗口 → 事务
- 想要"复杂逻辑"？→ 嵌入 Lua 解释器 → 脚本
- 想要"排序查询"？→ 用排序算子组合 → SORT
- 想要"数据分片"？→ 用哈希槽抽象 → Cluster
- 想要"全文检索"？→ 构建倒排索引 → RediSearch

**这就是第一性原理的力量**——从最基础的几条公理出发，通过"最小原语 + 巧妙组合"，演化出一个完整的能力谱系。Redis 的成功，本质上是"第一性原理驱动设计"的成功。

## 工业落地建议（第20~21章）

### Lua 脚本的最佳实践

1. **脚本要短小精悍**：执行时间控制在 `lua-time-limit`（默认 5 秒）以内
2. **避免无限循环**：循环必须有明确的退出条件，大集合操作用 SCAN 游标
3. **优先使用只读脚本变体**：`EVAL_RO` / `EVALSHA_RO` / `FCALL_RO`，可被 SCRIPT KILL 随时终止
4. **Redis 7.0+ 直接用 Functions**：持久化、命名、版本管理，告别 EVALSHA 的 SHA1 管理噩梦
5. **KEYS 声明规范**：所有访问的 key 必须在 KEYS 参数中显式声明，且 Cluster 环境下必须同槽
6. **类型转换陷阱**：Lua Number 返回时截断为整数，浮点数必须 tostring() 后返回
7. **效果复制（Redis 5.0+ 默认）**：脚本可以使用非确定性命令，但最佳实践仍是编写确定性脚本

### SORT 命令的工业准则

1. **数据规模 < 1000 元素**：SORT 完全够用
2. **数据规模 1000~10000**：配合 LIMIT 裁剪，且仅用于低频查询
3. **数据规模 > 10000**：改用 Sorted Set 预排序，或 RediSearch
4. **Cluster 环境（Redis 7.4+）**：BY/GET 模式必须用 hash tag 强制同槽
5. **Redis 7.0+ ACL 环境**：执行用户必须有完整键读权限（`%R~*`）
6. **高频查询**：用 STORE 选项物化结果，避免重复排序
7. **替代方案优先级**：Sorted Set > RediSearch > SORT

### 现代 Redis（7.0+）的技术选型

|需求场景|推荐方案|
|---|---|
|原子批处理、简单 CAS|Functions（FCALL）|
|复杂业务逻辑、多步操作|Functions（Lua 或未来的 JS）|
|排行榜、Top N、范围查询|Sorted Set（ZADD/ZRANGE）|
|轻量级排序（N < 1000）|SORT 命令|
|全文检索、复杂查询|RediSearch（Redis 8 内置）|
|文档存储、嵌套结构|RedisJSON（Redis 8 内置）|
|时序数据|RedisTimeSeries|
|向量相似度搜索|RediSearch 的 VECTOR 字段|

> 📌 **核心建议**：Redis 8 已经将 RediSearch、RedisJSON、RedisTimeSeries 等主流模块内置到核心 。新项目应直接使用 Redis 8，享受"核心简单 + 模块内化"的双重优势——既保持 Redis 的高性能，又获得丰富的查询能力。
