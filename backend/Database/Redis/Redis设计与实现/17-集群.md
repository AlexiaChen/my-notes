
# 《Redis设计与实现》读书笔记 · 第17章 集群

如果说第15章复制和第16章 Sentinel 解决的是"单机 Redis 如何高可用"的问题，那么第17章集群解决的就是**"数据多到一台机器装不下怎么办"**的问题。这是 Redis 从"单机/主从"走向"分布式系统"的关键一跃。Redis Cluster 的设计目标非常明确：**高性能、线性扩展到 1000 节点、无代理、异步复制、不合并值**​ 。

> ⚠️ 版本提醒：黄健宏的书基于 Redis 3.0 时代的集群实现。现代 Redis Cluster 在术语上已经演进——官方文档现在使用 **primary/replica**​ 而非 master/slave ，但核心机制（哈希槽、Gossip、故障检测、故障转移）保持稳定。下面以书的结构为主线，用官方集群规范 校正细节。

---

## 17.1 节点

Redis Cluster 是一个**去中心化的分布式系统**——集群中的每个节点都是平等的，都持有数据、都参与集群状态管理 。

**节点的两个 TCP 端口**（这是书上可能没有重点强调但工业部署极易踩坑的点）：

|端口|用途|防火墙要求|
|---|---|---|
|`6379`（客户端端口）|服务客户端命令、键迁移|对客户端和所有节点开放|
|`16379`（集群总线端口 = 客户端端口 + 10000）|节点间通信（Gossip、故障检测、配置同步）|**只对集群其他节点开放**​|

> ⚠️ **工业警示**：如果只开放了 6379 而忘了开放 16379，集群节点之间无法通信，集群永远无法形成。这是 Redis Cluster 部署最常见的"翻车点"。在云环境（如 AWS Security Group、阿里云安全组）中必须同时放行这两个端口。

**节点身份标识**：

每个节点在第一次创建时生成一个 **160 位的伪随机 Node ID**​ ，这个 ID 在整个节点生命周期内保持不变，即使节点重启、IP 改变、角色变更，Node ID 也不变。这是集群识别"谁是誰"的唯一依据。

**节点发现与握手**：

```
节点 A 执行: CLUSTER MEET <B_IP> <B_PORT>
    ↓
A 与 B 建立集群总线连接
    ↓
通过 Gossip 协议互相交换已知的节点信息
    ↓
B 的信息传播到整个集群，所有节点最终都认识 B
```

**关键认知**：Redis Cluster 是**全网状连接（full mesh）**——每个节点都与集群中所有其他节点建立 TCP 连接 。这意味着集群节点数 N 的连接数是 O(N²)。官方文档明确指出，**集群设计目标是"最多 1000 节点"**​ ，因为超过这个规模，Gossip 的消息量会变得不可接受。

**节点状态机**：

每个节点为每个已知节点维护一组标志位：

- `CLUSTER_NODE_MASTER` / `CLUSTER_NODE_SLAVE`：主或从
- `CLUSTER_NODE_PFAIL`：可能失效（Probable FAIL）
- `CLUSTER_NODE_FAIL`：确认失效
- `CLUSTER_NODE_MYSELF`：自己
- `CLUSTER_NODE_HANDFAKE`：握手状态

> 💡 **第一性原理洞见**：节点设计的精髓在于——**每个节点都是集群状态的"完整副本"**。任意节点都能回答"集群现在是什么拓扑"、"槽 X 由谁负责"、"节点 Y 是否存活"。这种"全节点对等 + 全状态复制"的设计，使得客户端可以连接任意一个节点就能获得集群的完整视图。代价是存储和通信的开销与集群规模平方级增长——这是 Redis Cluster "最多 1000 节点" 限制的根本原因。如果需要更大规模，应该使用 **Redis Cluster 的联邦部署**（多个 Cluster 集群通过客户端分片）或 **Twemproxy/Codis 等代理方案**。

## 17.2 槽指派

这是 Redis Cluster 区别于一致性哈希（Consistent Hashing）的核心设计。

**16384 个哈希槽（hash slot）**：

```
key → CRC16(key) mod 16384 → [0, 16383] 区间的某个槽
```

**为什么是 16384（16K）而不是 65536（64K）或更大？**

官方规范的解释 ：

1. **心跳包优化**：节点在心跳包中用 bitmap 表示自己负责的槽，16384 个槽只需要 **2KB**​ 的 bitmap（`16384 / 8 = 2048 bytes`）。如果用 65536 个槽，bitmap 会变成 8KB，在频繁的心跳包中开销显著
2. **集群规模上限**：Redis Cluster 设计目标是 1000 节点，平均每个节点负责 16 个槽。16384 这个数量级在"槽迁移粒度"和"bitmap 大小"之间取得了最佳平衡
3. **历史原因**：早期 Redis Cluster 的 prototype 使用的是 4096 个槽，后来调整为 16384

**槽指派操作**：

```
CLUSTER ADDSLOTS 0 1 2 ... 1000    # 将槽 0~1000 指派给当前节点
CLUSTER DELSLOTS ...               # 撤销槽指派
CLUSTER SETSLOT <slot> NODE <node_id>  # 将槽指派给指定节点
```

**集群上线的条件**：

**只有当所有 16384 个槽都被指派给节点时，集群才进入 `cluster_state:ok` 状态，开始对外服务**​ 。如果有任何一个槽未被指派，集群处于 `fail` 状态，拒绝执行命令（除非设置 `cluster-require-full-coverage no`）。

**3 主节点集群的典型槽分配**：

```
Node A: [0, 5460]        → 5461 个槽
Node B: [5461, 10922]    → 5462 个槽
Node C: [10923, 16383]   → 5461 个槽
```

**为什么不用一致性哈希？**

一致性哈希的虚拟节点机制虽然也能分片，但 Redis Cluster 选择固定 16384 槽的原因 ：

1. **迁移粒度可控**：槽是数据迁移的最小单位。16384 个槽意味着迁移粒度足够细（平均每个槽的数据量不大），又能避免过细导致的管理开销
2. **配置传播简单**：槽位映射关系可以通过 bitmap 紧凑表示并在节点间传播
3. **多键操作支持**：通过 **Hash Tag**（如 `{user1000}.name`、`{user1000}.age` 用花括号强制哈希到同一槽），可以保证相关键在同一个槽中，从而支持多键操作（如 MSET、SINTER）
4. **故障转移单元清晰**：以槽为单位进行主从切换，比以"一致性哈希环的一段"为单位更清晰

> 💡 **洞见**：槽（slot）是 Redis Cluster 的"第一公民"——它是数据分片的单元、迁移的单元、故障转移的单元、配置传播的单元。把"数据分片"从"节点"抽象到"槽"这一中间层，是 Redis Cluster 设计上最关键的决策。**槽解耦了"数据"与"节点"的直接绑定**：数据属于槽，槽属于节点。当节点变化时，只需要重新分配槽，而不需要重新哈希所有 key。这是"间接层"思想的经典应用——**用一层抽象吸收变化**。

**Hash Tag 的工业用法**：

```
# 不加 Hash Tag: user:1000:name 和 user:1000:age 可能在不同的槽
# 无法在一个 MULTI 事务中操作这两个 key

# 加 Hash Tag: {user:1000}:name 和 {user:1000}:age 一定在同一个槽
# 可以安全地执行 MULTI / EXEC、MSET、SINTER 等多键操作
```

但要注意：**过度使用 Hash Tag 会导致数据倾斜**——如果所有 key 都用同一个 tag，它们会全部落到同一个槽，进而压垮单个节点。这是工业实践中需要警惕的"便利陷阱"。

## 17.3 在集群中执行命令

客户端向集群发送命令的完整流程：

```
① 客户端计算 key 的槽: slot = CRC16(key) mod 16384
    ↓
② 查本地槽映射缓存: slot → node_address
    ↓
③ 如果缓存命中: 直接发送命令到对应节点
   如果缓存未命中: 发送命令到任意节点（如从 CLUSTER SLOTS 获取的一个节点）
    ↓
④ 节点检查: 这个槽是我负责的吗？
    ├─ YES → 执行命令，返回结果
    └─ NO  → 返回 MOVED 错误: -MOVED <slot> <correct_node_ip>:<port>
    ↓
⑤ 客户端收到 MOVED:
    - 更新本地槽映射缓存
    - 重新向正确节点发送命令
```

**智能客户端 vs. 简单客户端**：

|客户端类型|行为|例子|
|---|---|---|
|智能客户端（Smart Client）|缓存槽映射，直接路由到正确节点|redis-py-cluster、Lettuce、JedisCluster|
|简单客户端|连接任意节点，靠 MOVED 重定向|普通 redis-cli、早期客户端|

现代生产环境**必须使用智能客户端**——否则每次命令都可能经历一次 MOVED 重定向，延迟翻倍。

**获取槽映射**：

```
CLUSTER SLOTS
# 返回槽范围 → 节点地址的映射
# 例: [0, 5460] → 127.0.0.1:7000 (主) + 127.0.0.1:7003 (从)
#      [5461, 10922] → 127.0.0.1:7001 (主) + 127.0.0.1:7004 (从)
#      [10923, 16383] → 127.0.0.1:7002 (主) + 127.0.0.1:7005 (从)
```

客户端在以下时机刷新槽映射 ：

- **启动时**：通过 `CLUSTER SLOTS` 获取初始映射
- **收到 MOVED 错误时**：重新执行 `CLUSTER SLOTS` 获取完整映射（而非只更新单个槽，因为一次拓扑变化通常涉及多个槽）

**多键操作的限制**：

Redis Cluster **只允许操作同一个槽内的多个 key**​ 。如果命令涉及多个 key，且这些 key 不在同一个槽，命令会被拒绝：

```
(error) CROSSSLOT Keys in request don't hash to the same slot
```

解决方法：使用 Hash Tag 强制相关 key 进入同一槽。

**只读副本与读负载均衡**：

客户端可以通过 `READONLY` 命令将会话标记为只读模式，之后该连接上的读命令会被路由到副本节点 ：

```
READONLY
GET user:1000:name    # 可能被路由到副本
READWRITE             # 取消只读模式
```

> ⚠️ **工业实践**：`READONLY` 模式在槽迁移期间可能收到 MOVED 重定向，客户端需要处理这种情况。此外，副本的数据可能滞后于主节点（异步复制），因此 `READONLY` 只适用于"允许读到旧数据"的场景（如展示用户画像、历史记录等）。

## 17.4 重新分片

重新分片（resharding）是 Redis Cluster 最核心也最复杂的操作——它让集群可以在线扩缩容，不影响服务可用性。

**重新分片的本质**：将某些槽从源节点迁移到目标节点，同时保证迁移期间集群继续服务。

**迁移流程**（以迁移单个槽为例） ：

```
① 在目标节点执行:
   CLUSTER SETSLOT <slot> IMPORTING <source_node_id>
   # 目标节点进入 IMPORTING 状态：允许接收该槽的数据，但只接受带 ASKING 的命令

② 在源节点执行:
   CLUSTER SETSLOT <slot> MIGRATING <target_node_id>
   # 源节点进入 MIGRATING 状态：如果 key 还在本地，正常处理；如果 key 不在，返回 ASK 重定向

③ 迁移 key（循环直到槽为空）:
   在源节点执行: CLUSTER GETKEYSINSLOT <slot> <count>
   # 获取槽中最多 count 个 key
   对每个 key 执行: MIGRATE <target_ip> <target_port> <key> 0 <timeout>
   # 原子性地将 key 从源节点传输到目标节点

④ 当槽中所有 key 迁移完毕:
   在目标节点执行: CLUSTER SETSLOT <slot> NODE <target_node_id>
   # 目标节点正式接管该槽，清除 IMPORTING 状态，生成新的 configEpoch
```

**关键命令 `MIGRATE` 的原子性**：

`MIGRATE` 命令在源节点上执行时是**原子的**——它在源节点上删除 key，同时通过 RESTORE 命令在目标节点上创建相同的 key，整个过程在源节点上是一个阻塞操作（但通常只阻塞毫秒级，因为单个 key 的传输很快）。

**在线迁移的工业工具**：

生产环境绝不会手动执行上述命令，而是使用 `redis-cli --cluster` 工具：

```
# 将 1000 个槽从节点 A 迁移到节点 B
redis-cli --cluster reshard <any_node_ip>:<port> \
  --cluster-from <node_A_id> \
  --cluster-to <node_B_id> \
  --cluster-slots 1000 \
  --cluster-yes
```

该工具自动完成上述 ①②③④ 所有步骤。

**迁移过程中的数据一致性保证**：

迁移期间，槽处于"分裂"状态——源节点和目标节点都声称"拥有"这个槽，但通过 MIGRATING/IMPORTING 标记和 ASKING 命令协作：

- **已迁移的 key**：源节点返回 ASK 重定向，客户端去目标节点执行（带 ASKING）
- **未迁移的 key**：源节点正常处理
- **新写入的 key**：直接在目标节点创建（因为源节点对不存在的 key 返回 ASK）

这保证了：**迁移期间不会有 key 丢失，也不会有 key 冲突**。

> 💡 **第一性原理洞见**：重新分片的设计展现了一个深刻的分布式系统智慧——**用"状态机 + 临时状态"实现"在线数据迁移"**。MIGRATING 和 IMPORTING 是槽的两个临时状态，它们把"槽的所有权转移"这个本质上的离散事件，分解成了一个连续的、可中断、可恢复的过程。这与数据库领域的"在线 schema 变更"思路异曲同工——**不在"旧状态"和"新状态"之间一刀切，而是引入中间状态让系统在两个状态间平滑过渡**。
> 
> 更深层的是：**ASK 重定向是这种"中间状态"在客户端视角的投影**。MOVED 说"槽永久属于 B"，ASK 说"这次请求去 B 试试，但槽的归属还没定"。这背后是一个更普适的真理——**分布式系统中的"瞬时状态"需要用"瞬时重定向"来表达，而"永久状态"需要用"永久重定向"来表达**。Redis Cluster 用两种重定向（MOVED/ASK）干净地分离了这两个语义。

## 17.5 ASK错误

ASK 错误是 Redis Cluster 中最容易被误解的机制。它与 MOVED 错误看起来相似，但语义截然不同。

**MOVED vs ASK**​ ：

|维度|MOVED|ASK|
|---|---|---|
|含义|槽**永久**归属于另一个节点|槽正在迁移，**临时**重定向本次请求|
|客户端动作|更新本地槽映射缓存|**不更新**缓存，仅本次请求发往目标节点|
|触发时机|槽归属已变更（稳定状态）|槽正在迁移中（中间状态）|
|后续请求|直接发往新节点|仍发往原节点，直到收到 MOVED|

**ASK 错误处理的完整客户端逻辑**​ ：

```
收到 ASK <slot> <target_ip>:<target_port> 错误
    ↓
① 向目标节点发送 ASKING 命令（设置一次性标志）
    ↓
② 立即向目标节点重新发送原始命令
    ↓
③ 目标节点因为 ASKING 标志，接受对 IMPORTING 状态槽的命令
    ↓
④ 命令执行，返回结果
    ↓
⑤ 客户端不更新本地槽映射（因为迁移可能尚未完成）
    ↓
⑥ 后续对该槽的请求仍发往原节点
    ↓
⑦ 当迁移完成时，原节点返回 MOVED，客户端才永久更新映射
```

**为什么需要 ASKING 命令？**

目标节点在 IMPORTING 状态下，默认会拒绝对该槽的命令（返回 MOVED 说"槽不归我管"）。`ASKING` 命令在目标节点上设置一个**一次性的客户端标志**，告诉目标节点："这次命令例外，即使槽还在 IMPORTING 状态也执行它" 。

如果不使用 ASKING，会发生：

- 客户端收到 ASK，发往目标节点
- 目标节点发现槽在 IMPORTING 状态，返回 MOVED 回原节点
- 原节点发现 key 已迁移，又返回 ASK
- **死循环！**

`ASKING` 打破了这个循环。

**为什么 ASK 不更新客户端缓存？**

因为迁移可能随时回滚或暂停。如果客户端在收到 ASK 时就更新缓存，而迁移实际上并未完成（比如管理员中止了 reshard 操作），客户端的缓存就会处于错误状态。通过"不更新缓存 + 继续向原节点发请求"，客户端能够自适应迁移的真实进度——**只有收到 MOVED 时，才意味着迁移真正完成**。

> 💡 **洞见**：ASK 错误的设计体现了"客户端与服务器职责分离"的精妙——
> 
> - **服务器**只负责告知"这次请求该去哪"（ASK）和"以后都去哪"（MOVED）
> - **客户端**负责决定"是否相信这个信息"（ASK 不信，MOVED 才信）
> 
> 这种"保守的客户端"策略，使得集群在迁移过程中即使发生异常（如迁移中断、源节点崩溃），也能保持数据一致性。客户端始终以"原节点"为真相源，直到服务器明确说"MOVE"（永久变更）。这是分布式系统中"悲观收敛"思想的体现——**不轻易相信临时状态，只相信经过共识的永久状态**。

## 17.6 复制与故障转移

Redis Cluster 的故障转移机制是 Sentinel 逻辑的"内置化"——**集群节点自己完成故障检测、选举和切换，不需要外部 Sentinel**。

### 故障检测：PFAIL → FAIL

**PFAIL（Possible FAIL，可能下线）**​ ：

- 节点 A 在 `cluster-node-timeout`（默认 15 秒）时间内未收到节点 B 的有效 PING 回复
- A 将 B 标记为 PFAIL
- **PFAIL 只是 A 的单方面判断**，还不是集群共识

**FAIL（确认下线）**​ ：

- 节点 A 通过 Gossip 消息收集其他节点对 B 的看法
- 如果**多数派主节点**都在 `NODE_TIMEOUT * FAIL_REPORT_VALIDITY_MULT`（当前实现为 2 倍 NODE_TIMEOUT）时间内认为 B 是 PFAIL 或 FAIL
- A 将 B 标记为 FAIL
- A 向所有可达节点广播 FAIL 消息

**关键规则**：**只有主节点（primary）的投票才算数**。从节点的判断不参与"多数派"计算。这是为了防止"从节点视角"导致的误判——毕竟从节点本身就不处理写请求，网络隔离的可能性不同。

### 副本选举：类 Raft 的领导者选举

当主节点被标记为 FAIL 后，其副本发起选举 ：

**① 选举延迟**：

```
DELAY = 500ms + random(0~500ms) + SLAVE_RANK * 1000ms
```

- **固定 500ms**：等待 FAIL 状态传播到整个集群，否则主节点们还不知道 FAIL，会拒绝投票
- **随机 0~500ms**：让多个副本错开发起选举，避免同时竞争
- **SLAVE_RANK * 1000ms**：副本排名越靠前（复制偏移越大、数据越新），延迟越小，越先发起选举

**副本排名（SLAVE_RANK）**：

- 与主节点复制偏移最大的副本 → rank 0（最先尝试选举）
- 偏移第二大的副本 → rank 1
- 以此类推

**② 发起选举**：

- 副本将自己的 `currentEpoch + 1` 作为新的选举纪元
- 向所有主节点发送 `FAILOVER_AUTH_REQUEST`

**③ 主节点投票**：

- 每个主节点在**每个纪元内只能投一票**
- 主节点只对"其主节点被标记为 FAIL"的副本投票
- 主节点优先投票给 rank 较小的副本（数据较新）
- 投票结果通过 `FAILOVER_AUTH_ACK` 回复

**④ 选举胜出**：

- 副本获得**多数派主节点**的投票 → 当选
- 如果在一个选举周期内（2 倍 NODE_TIMEOUT，至少 2 秒）未获多数派，选举中止
- 等待 `NODE_TIMEOUT * 4`（至少 4 秒）后发起新一轮选举

**⑤ 接管**：

- 当选副本执行 `REPLICAOF NO ONE` 成为新主
- 获得一个**比集群中所有现有节点都高的 `configEpoch`**​
- 向全集群广播 PONG 消息，声明自己是新主，接管原主的槽
- 其他节点收到 PONG 后，检测到更高的 configEpoch，更新本地配置
- 原主的其余副本自动改为从属于新主

**configEpoch 的关键作用**：

`configEpoch` 是集群中解决"配置冲突"的版本号。当多个节点声称"我拥有槽 X"时，**configEpoch 较大的胜出**。这保证了：

- 新主一定使用比旧主更高的 configEpoch
- 即使网络分区导致"双主"，分区恢复后 configEpoch 较大的配置会胜出
- 避免了"脑裂"导致的数据不一致

### 手工故障转移：CLUSTER FAILOVER

除了自动故障转移，管理员可以手动触发 ：

```
CLUSTER FAILOVER          # 优雅故障转移：与原主协调，确保数据不丢
CLUSTER FAILOVER FORCE    # 强制故障转移：原主不可达时使用
CLUSTER FAILOVER TAKEOVER # 完全绕过集群共识，单方面接管
```

**三种模式的区别**：

|模式|与原主协调|需要多数派授权|使用场景|
|---|---|---|---|
|默认|✅ 是|✅ 是|计划内维护，原主健康|
|FORCE|❌ 否|✅ 是|原主不可达|
|TAKEOVER|❌ 否|❌ 否|数据中心切换，原主全部不可达|

> ⚠️ **工业警示**：`TAKEOVER` 模式是危险的——它**绕过集群共识**，单方面提升副本为主。如果在网络分区场景下使用，可能导致"双主"和数据分歧。仅在"原主所在数据中心完全不可用，需要将副本提升为新主"的灾难恢复场景中使用。

### 故障转移期间的可用性

**关键事实**：在故障检测和故障转移完成之间的窗口期（通常 5-30 秒），**失效主节点负责的槽不可用**​ 。

```
T=0s    主节点停止响应
T=15s   cluster-node-timeout 到期，节点标记 PFAIL
T=15-16s  FAIL 共识达成
T=16-18s 副本选举完成
T=18s   新主开始接受写入
```

**如果设置 `cluster-require-full-coverage yes`（默认）**：在故障转移窗口期内，对整个集群的**任何写操作**都会失败（因为集群状态不是 `ok`）。

**如果设置 `cluster-require-full-coverage no`**：只有涉及失效主节点槽的写操作失败，其他槽仍可正常服务。

> 📌 **工业建议**：对于"部分槽不可用也要继续服务"的场景（如缓存），设置 `cluster-require-full-coverage no`。对于"数据强一致优先"的场景（如订单），保持默认的 `yes`。

### 副本迁移（Replica Migration）

Redis Cluster 有一个精妙的特性——**副本迁移**​ ：当某个主节点没有副本时，集群会自动从"有多余副本的主节点"调配一个副本过来。这确保了"每个主节点至少有一个副本"，从而提高了集群整体的可用性。

## 17.7 消息

Redis Cluster 节点间通过**集群总线（Cluster Bus）**通信，使用二进制协议（而非 RESP 文本协议），因为二进制协议更节省带宽和处理时间 。

**五种核心消息类型**：

**① PING / PONG**​ ：

- 节点间每秒发送 PING
- 接收方回复 PONG
- 消息内容包括：
    - **公共头**：Node ID、currentEpoch、configEpoch、节点标志位、负责的槽 bitmap、TCP 端口、集群端口、集群状态、主节点 ID（如果是副本）
    - **Gossip 段**：随机选取的几个已知节点的信息（Node ID、IP、端口、标志位）

**Gossip 段的精妙设计**：

- 每个 PING/PONG 只包含**随机几个**节点的信息，而非全部
- Gossip 段的大小与集群规模成比例
- 通过持续的随机交换，每个节点最终都能获得全集群的视图
- 官方文档的计算：100 个节点的集群，每个节点每秒发送 3.3 个 PING，总共 330 pings/秒，分摊到 100 个节点，每个节点约 3.3 pings/秒 ——完全可接受

**② MEET**：

- 用于节点握手，加入集群

**③ FAIL**​ ：

- 当节点 A 将节点 B 标记为 FAIL 时，向所有可达节点广播 FAIL 消息
- 其他节点收到后，立即将 B 标记为 FAIL（无需等待 Gossip 传播）

**④ PUBLISH**：

- 在集群中传播 Pub/Sub 消息
- 确保发布到任意节点的消息能到达所有节点的订阅者

**⑤ FAILOVER_AUTH_REQUEST / FAILOVER_AUTH_ACK**​ ：

- 副本选举过程中，副本向主节点发送投票请求
- 主节点回复投票结果

**⑥ UPDATE**：

- 当节点检测到其他节点的配置信息过时，发送 UPDATE 消息强制更新

**心跳包的双重作用**：

```
PING/PONG 消息同时承担两个职责：
  ① 故障检测：通过是否及时收到 PONG 判断节点存活
  ② 信息传播：通过 Gossip 段交换集群状态
```

这种"一举两得"的设计极大降低了协议复杂度——不需要单独的"故障检测协议"和"状态同步协议"。

> 💡 **第一性原理洞见**：Redis Cluster 的消息设计体现了 Gossip 协议的精髓——**"用不可靠的、随机的、增量的信息交换，最终达成一致"**。每个节点只与随机几个节点交换随机几个节点的信息，但通过持续的交互，整个集群的状态最终会收敛。这种"涌现式一致性"比"全节点广播"更节省资源，比"中心化协调"更鲁棒。
> 
> 但 Gossip 也有代价：
> 
> - **收敛速度慢**：信息需要多轮传播才能到达所有节点
> - **FAIL 状态需要显式广播**：为了加速故障检测，Redis 在 Gossip 之外增加了 FAIL 消息的显式广播
> 
> 这是工程上的典型权衡——**日常状态用 Gossip 增量传播（省带宽），紧急状态用广播即时通知（保速度）**。

**configEpoch 的传播**：

每个节点的 currentEpoch 和 configEpoch 都通过 PING/PONG 的公共头传播 。当节点收到更高的 configEpoch 时，会更新本地配置。这保证了：

- 新主的 configEpoch 高于旧主 → 新配置胜出
- 网络分区恢复后，configEpoch 较大的配置会覆盖较小的
- 避免了"脑裂"导致的数据永久分歧

## 17.8 重点回顾

1. **Redis Cluster 是无代理、全网状连接的分布式系统**，每个节点都持有完整的集群状态
2. **16384 个哈希槽**是数据分片、迁移、故障转移的基本单元，CRC16(key) mod 16384 计算槽号
3. **槽解耦了数据与节点**：数据属于槽，槽属于节点，使在线扩缩容成为可能
4. **MOVED 是永久重定向**（客户端更新缓存），**ASK 是临时重定向**（客户端不更新缓存，先发 ASKING）
5. **重新分片通过 MIGRATING/IMPORTING 状态**实现在线迁移，迁移期间集群持续可用
6. **故障检测：PFAIL（单节点判断）→ FAIL（多数派主节点共识）**
7. **副本选举：类 Raft 算法**，按复制偏移排名，多数派主节点投票，胜出者获得更高 configEpoch
8. **configEpoch 是解决配置冲突的版本号**，较大的 configEpoch 配置胜出
9. **Gossip 协议通过 PING/PONG 传播集群状态**，每个消息包含随机几个节点的信息
10. **Redis Cluster 只支持 database 0**，SELECT 命令不可用
11. **集群设计目标：最多 1000 节点**，超过此规模 Gossip 开销不可接受

## 第17章的深层洞见：Redis Cluster 的分布式系统哲学

### 洞见一：槽（Slot）是 Redis Cluster 的"第一公民"

```
数据 (key) → 槽 (slot) → 节点 (node)
```

这个三层映射是 Redis Cluster 最关键的架构决策。它带来了三个核心优势：

1. **迁移粒度可控**：以槽为单位迁移，16384 个槽提供了足够细的粒度
2. **配置传播高效**：槽映射可以用 2KB 的 bitmap 表示
3. **故障转移清晰**：以槽为单位进行主从切换

这与一致性哈希形成鲜明对比——一致性哈希直接将 key 映射到节点，缺少"槽"这个中间层，导致：

- 节点变化时，大量 key 需要重新映射
- 数据迁移粒度不可控
- 配置传播开销大

**"间接层"是计算机科学中最强大的思想之一**——Redis Cluster 用槽这一间接层，吸收了"节点变化"的冲击，让数据和节点解耦。

### 洞见二：用"临时状态"实现"在线数据迁移"

MIGRATING 和 IMPORTING 是槽的两个临时状态，它们把"槽所有权转移"这个离散事件，分解为连续的、可中断、可恢复的过程。

```
稳定状态: 槽 X 属于节点 A
    ↓ [CLUSTER SETSLOT X MIGRATING A] + [CLUSTER SETSLOT X IMPORTING B]
中间状态: 槽 X 同时属于 A (MIGRATING) 和 B (IMPORTING)
    ↓ [MIGRATE key by key]
迁移中:   部分 key 在 A，部分 key 在 B
    ↓ [CLUSTER SETSLOT X NODE B]
稳定状态: 槽 X 属于节点 B
```

这种"状态机 + 中间状态"的思路，是分布式系统中实现"在线操作"的通用范式：

- 数据库在线 schema 变更
- 一致性哈希的虚拟节点再平衡
- Raft 的日志复制状态机

**核心思想：不在两个稳定状态之间"一刀切"，而是引入中间状态让系统平滑过渡**。

### 洞见三：两种重定向（MOVED/ASK）分离了"永久"与"临时"

|语义|重定向类型|客户端行为|
|---|---|---|
|槽归属永久变更|MOVED|更新缓存|
|槽正在迁移中|ASK|不更新缓存，单次请求发往目标|

这种分离反映了分布式系统的一个普遍真理——**"瞬时状态"和"永久状态"需要不同的处理机制**。客户端对 ASK 的"保守"处理（不更新缓存），使得系统能够自适应迁移的真实进度，即使在迁移中断或回滚的情况下也能保持一致性。

### 洞见四：类 Raft 的故障转移，但更简单

Redis Cluster 的副本选举算法与 Raft 有许多相似之处：

- 都用 epoch（任期）防止旧消息干扰
- 都需要多数派投票
- 都按"数据最新程度"排序候选者

但 Redis Cluster 做了简化：

- **没有完整的日志复制**：依赖 Redis 的异步复制
- **没有严格的 leader 概念**：每个主节点都是"平等"的，都可以投票
- **configEpoch 解决冲突**：用版本号而非"领导者权威"来解决配置分歧

这种"Raft 风格的简化版"在 Redis Cluster 的场景下工作良好——**它不需要 Raft 的全部严谨性，因为 Redis Cluster 的故障转移不涉及"日志一致性"，只涉及"槽所有权变更"**。

### 洞见五：Gossip 是"涌现式一致性"的经典实践

Redis Cluster 用 Gossip 协议实现集群状态传播，体现了"涌现式一致性"的思想：

- 每个节点只与随机几个节点交换随机几个节点的信息
- 通过持续交互，全集群状态最终收敛
- 不需要中心协调者，没有单点故障

但 Redis Cluster 也对纯 Gossip 做了工程优化：

- **FAIL 状态显式广播**：加速故障检测
- **configEpoch 显式比较**：加速配置更新
- **UPDATE 消息强制同步**：处理"信息过时"的节点

> 💡 **创新联想**：Redis Cluster 的 Gossip 实现，可以看作"纯 Gossip"与"显式广播"的混合体——日常状态用 Gossip（省带宽），紧急状态用广播（保速度）。这种"分层通信"的思想，在未来的分布式系统设计中仍有重要价值。

### 洞见六：Redis Cluster 的一致性取舍

Redis Cluster 的官方规范明确承认 ：

> **"Acceptable degree of write safety: the system tries (in a best-effort way) to retain all the writes... Usually there are small windows where acknowledged writes can be lost."**

Redis Cluster 使用的是**异步复制**，这意味着：

- 主节点执行写命令后立即返回客户端
- 写命令随后异步传播到副本
- 主节点宕机时，最近一批未传播的写命令会丢失

**丢失窗口的大小**：

```
丢失窗口 ≈ 主节点到副本的复制延迟 + 故障转移耗时
```

**与 Sentinel 方案的对比**：

|维度|Sentinel + 复制|Redis Cluster|
|---|---|---|
|分片|不支持（单机容量上限）|支持（16384 槽分片）|
|故障检测|Sentinel 监控|集群节点互相监控|
|故障转移|Sentinel 选举 Leader 执行|副本自动选举|
|写安全性|异步复制，有丢失窗口|异步复制，有丢失窗口|
|扩展性|垂直扩展为主|水平扩展，1000 节点上限|
|客户端复杂度|低（通过 Sentinel 发现主库）|高（需要智能客户端 + 槽路由）|

> ⚠️ **工业现实**：Redis Cluster **不是"银弹"**。它解决了"数据分片"的问题，但代价是：
> 
> - 客户端必须实现智能路由（槽映射缓存、MOVED/ASK 处理）
> - 多键操作受限（必须同槽，或用 Hash Tag）
> - 只支持 database 0
> - 事务和 Lua 脚本必须操作同一槽的 key
> - 运维复杂度显著增加（重新分片、槽迁移、Gossip 调试）
> 
> 对于数据量在单机容量范围内（如 < 100GB）且要求简单部署的场景，**Sentinel + 复制**​ 仍是更优选择。Redis Cluster 的真正价值在**数据规模超过单机容量**或**需要线性扩展写吞吐**的场景下才显现。

## 工业落地建议（第17章）

### 1. 集群规划

**节点数量**：

- **最少 3 主 3 从**（共 6 节点）：生产环境最小部署
- **推荐 3 主，每主 1-2 从**：共 6-9 节点，平衡可用性和资源成本
- **大规模场景**：主节点数控制在 100 以内（Gossip 开销考虑）

**槽分配**：

- 每个主节点负责约 `16384 / 主节点数` 个槽
- 使用 `redis-cli --cluster create` 自动均匀分配

```
# 创建 3 主 3 从集群
redis-cli --cluster create \
  10.0.0.1:6379 10.0.0.2:6379 10.0.0.3:6379 \
  10.0.0.4:6379 10.0.0.5:6379 10.0.0.6:6379 \
  --cluster-replicas 1
```

### 2. 关键配置

```
# redis.conf 所有节点
cluster-enabled yes
cluster-config-file nodes.conf
cluster-node-timeout 15000          # 故障检测时间，默认 15 秒
cluster-require-full-coverage no    # 允许部分槽不可用时继续服务
cluster-replica-validity-factor 10  # 副本有效性因子
cluster-migration-barrier 1         # 副本迁移屏障
```

**`cluster-node-timeout` 的调优**：

- 太小（如 2-5 秒）：网络抖动可能触发误故障转移
- 太大（如 30-60 秒）：故障转移慢，RTO 大
- **推荐 10-15 秒**：平衡故障检测速度和误判率

### 3. 客户端选型

**必须使用智能客户端**：

|语言|推荐客户端|
|---|---|
|Java|Lettuce、JedisCluster|
|Python|redis-py-cluster|
|Go|go-redis/redis|
|Node.js|ioredis|
|C#|StackExchange.Redis|

**客户端配置要点**：

```
# Python redis-py-cluster 示例
from redis.cluster import RedisCluster

rc = RedisCluster(
    host='10.0.0.1',
    port=6379,
    # 关键参数
    max_connections=50,           # 连接池大小
    retry_on_timeout=True,        # 超时重试
    cluster_error_retry_attempts=3, # 集群错误重试次数
    read_from_replicas=True,      # 从副本读取（允许读到旧数据）
)
```

### 4. 在线扩缩容

```
# 扩容：添加新主节点并迁移槽
redis-cli --cluster add-node 10.0.0.7:6379 10.0.0.1:6379
redis-cli --cluster reshard 10.0.0.1:6379 \
  --cluster-from <existing_master_id> \
  --cluster-to <new_master_id> \
  --cluster-slots 1000 \
  --cluster-yes

# 为新主添加副本
redis-cli --cluster add-node 10.0.0.8:6379 10.0.0.1:6379 \
  --cluster-slave --cluster-master-id <new_master_id>

# 缩容：先迁移槽，再删除节点
redis-cli --cluster reshard 10.0.0.1:6379 \
  --cluster-from <leaving_master_id> \
  --cluster-to <target_master_id> \
  --cluster-slots 1000 \
  --cluster-yes
redis-cli --cluster del-node 10.0.0.1:6379 <leaving_master_id>
```

**迁移期间的监控**：

```
# 监控迁移进度
redis-cli -c -h 10.0.0.1 -p 6379 CLUSTER NODES | grep migrating
redis-cli -c -h 10.0.0.1 -p 6379 CLUSTER NODES | grep importing

# 监控集群状态
redis-cli -c -h 10.0.0.1 -p 6379 CLUSTER INFO
# cluster_state:ok
# cluster_slots_assigned:16384
# cluster_slots_ok:16384
# cluster_known_nodes:6
# cluster_size:3
```

### 5. 故障处理

**自动故障转移验证**：

```
# 模拟主节点故障
redis-cli -h 10.0.0.1 -p 6379 DEBUG SEGFAULT

# 观察故障转移
redis-cli -c -h 10.0.0.2 -p 6379 CLUSTER NODES
# 观察副本提升为新主，cluster_state 从 fail 恢复为 ok

# 原主恢复后自动成为副本
redis-server /path/to/redis.conf
redis-cli -c -h 10.0.0.1 -p 6379 CLUSTER NODES
# 原主现在显示为 replica
```

**关键监控指标**：

```
CLUSTER INFO
# 关注:
# cluster_state: ok/fail  ← 必须为 ok
# cluster_slots_fail: 0   ← 必须为 0
# cluster_known_nodes: 6  ← 节点总数
# cluster_size: 3         ← 主节点数

CLUSTER NODES
# 关注:
# 每个主节点的 connected_slots 范围
# 副本的 master_id 是否正确
# 是否有节点标记为 fail
```

### 6. 避坑指南

**① 防火墙必须开放两个端口**：

```
6379 (客户端端口) + 16379 (集群总线端口)
```

**② Hash Tag 要慎用**：

```
✅ 合理: {user:1000}:name, {user:1000}:age  ← 相关 key 同槽
❌ 危险: {all}:counter1, {all}:counter2     ← 所有 key 落到同一槽，数据倾斜
```

**③ 多键操作必须同槽**：

```
# ❌ 错误: 不同槽的 key
MSET user:1:name "Alice" user:2:name "Bob"
# (error) CROSSSLOT Keys in request don't hash to the same slot

# ✅ 正确: 使用 Hash Tag
MSET {user:1}:name "Alice" {user:1}:age 30
```

**④ 避免大 key**：

大 key（如包含百万个 field 的 Hash）在迁移时会导致 `MIGRATE` 命令长时间阻塞，影响集群性能。**单个 key 的大小建议控制在 10MB 以内**。

**⑤ `cluster-require-full-coverage` 的设置**：

```
# 缓存场景: 部分槽不可用也要继续服务
cluster-require-full-coverage no

# 数据一致性场景: 严格要求全部槽可用
cluster-require-full-coverage yes  # 默认
```
