
# 《Redis设计与实现》读书笔记 · 第11章～第14章

这四章把第一部分"数据结构与对象"和第二部分"单机数据库的实现"彻底打通：**第11章 AOF 是 RDB 时点快照的补充，用"命令日志"把数据丢失窗口压到秒级**；**第12章事件是 Redis 单线程不阻塞的灵魂**；**第13章客户端是网络上"每一个连接"在服务端的投影**；**第14章服务器把前面所有构件装配起来，让 Redis 真正跑起来**。

> ⚠️ 版本提醒：黄健宏的书基于 Redis 3.x，其中 AOF 还是"单一文件 + 重写缓冲"模型。而 **Redis 7.0 起 AOF 改为 multi-part 结构**（base + incr + manifest），这是 AOF 机制自诞生以来最大的一次架构升级 。下面以书的结构为主线，用现代资料校正细节。

## 第11章 AOF持久化

### 11.1 AOF持久化的实现

AOF（Append Only File）的设计哲学与 RDB 截然相反：**RDB 记录"数据是什么"，AOF 记录"数据怎么变成这样的"**。

每当 Redis 执行一个写命令，命令会以 RESP 协议格式**追加到 AOF 缓冲区 `server.aof_buf`**​ 。然后由 `flushAppendOnlyFile` 函数在**每个事件循环迭代结束时**将缓冲区刷到磁盘 ：

```
客户端 SET key value
    ↓
命令执行，修改内存中的 dict
    ↓
feedAppendOnlyFile() → 命令序列化追加到 aof_buf
    ↓
事件循环一轮结束前 → flushAppendOnlyFile()
    ↓
根据 appendfsync 策略决定是否 fsync
    ↓
写入 appendonly.aof 文件
```

**三种 fsync 策略**（这是 AOF 最核心的权衡）：

|策略|调用时机|耐久性|性能|
|---|---|---|---|
|`always`|每个写命令都 fsync|不丢数据|极慢（磁盘 IOPS 上限）|
|`everysec`|每秒 fsync 一次|最多丢 1 秒数据|快（默认推荐）|
|`no`|交给操作系统（通常 30 秒）|最多丢 30 秒|最快|

> 💡 **第一性原理视角**：AOF 的本质是 **WAL（Write-Ahead Log）思想在 Redis 里的应用**——任何数据修改前先写日志，保证崩溃后可重放。但 Redis 的 AOF 做了一个关键简化：**它不阻止命令执行，只在后台异步刷盘**。这意味着 `always` 以外的策略都存在"命令已执行但还未落盘"的理论窗口。这是 Redis 在"内存数据库的性能"和"持久化的强保证"之间做的明确妥协——**默认 `everysec` 策略下，Redis 选择"最多丢 1 秒"来换取近内存级的写入吞吐**。

官方文档明确：AOF 记录的是"与 Redis 协议本身相同格式"的命令 ，这意味着 AOF 文件人眼可读、可被 `redis-check-aof` 修复、甚至可以被脚本分析——这是 AOF 相对 RDB 二进制的巨大优势。

### 11.2 AOF文件的载入与数据还原

AOF 载入过程：

1. 创建一个**伪客户端**（fake client，无 socket 连接）
2. 从 AOF 文件逐条读取命令
3. 用伪客户端执行每条命令（走正常的命令执行路径）
4. 直到所有命令执行完毕

**为什么用伪客户端？**​ 因为 AOF 重放和实际客户端发命令在"服务端视角"完全一致——都是 `读取命令 → 解析 → 查找命令实现 → 执行 → 写回复`。用伪客户端可以**复用整个命令执行管线**，不需要为 AOF 重放写特殊逻辑。

**AOF 文件可能出现损坏的两种情况**：

- **尾部不完整**（如 `kill -9` 导致）：Redis 7 之前用 `aof-load-truncated yes` 忽略尾部；Redis 7 之后因为有多部分结构 + manifest，可以更精确地定位有效边界
- **中间损坏**：必须用 `redis-check-aof --fix` 修复，它会扫描文件，截断到最后一个完整命令

> ⚠️ **工业警示**：AOF 重放是**单线程顺序执行**的，速度远慢于 RDB 的二进制加载。一个 100GB 的 AOF 可能需要**数十分钟**才能重放完毕。这就是为什么 Redis 4.0 引入了 **RDB-AOF 混合持久化**——AOF 重写时在文件头部写入 RDB 格式的全量快照，尾部追加增量 AOF 命令 。这样重启时先快速加载 RDB 部分（秒级），再重放少量 AOF 增量，兼顾了速度与耐久性。

### 11.3 AOF重写

AOF 重写是 AOF 机制里**最精妙也最容易被误读**的部分。核心矛盾：**AOF 文件会无限增长**（比如对一个 key 做 10000 次 `INCR`，AOF 里就有 10000 条命令，但实际状态只是一个整数）。

**重写的本质**：**不是对原 AOF 文件做压缩，而是遍历当前内存中的数据，生成"能重建相同状态的最小命令集"**。

**Redis 3.x/6.x 的经典重写流程**：

```
┌──────────────────────┐
                    │   Redis 父进程        │
                    │   (主事件循环)        │
                    └──────────┬───────────┘
                               │ fork()
                ┌──────────────┴──────────────┐
                ▼                              ▼
        ┌──────────────┐            ┌──────────────────────┐
        │ 父进程继续服务 │            │ 子进程遍历内存         │
        │ 新命令双写：   │            │ 写入临时 AOF 文件      │
        │ → aof_buf    │            │ (最小命令集)           │
        │ → aof_rewrite│            └──────────┬───────────┘
        │   _buf      │                       │ 完成，通知父进程
        └──────────────┘                      ▼
                               父进程将 aof_rewrite_buf 内容
                               追加到临时文件末尾
                               rename 临时文件 → 正式 AOF
```

**经典模型的痛点**（Redis 7 之前）：

- **双写开销**：重写期间每个新命令都要写两份（正常 AOF + 重写缓冲）
- **内存翻倍风险**：`aof_rewrite_buf` 可能增长到很大
- **末尾阻塞**：子进程完成后，父进程要将重写缓冲刷盘并 fsync，这一步会短暂阻塞

**Redis 7.0 的 Multi-Part AOF 重写**（革命性改进）：

Redis 7 把单一 AOF 文件拆成三部分 ：

```
appendonlydir/
├── appendonly.aof.1.base.rdb   ← BASE：重写时的全量快照（RDB 或 AOF 格式）
├── appendonly.aof.1.incr.aof   ← INCR：BASE 之后的增量命令日志
└── appendonly.aof.manifest     ← MANIFEST：记录当前活跃的 BASE 和 INCR 文件
```

**重写时的流程变化**：

- 重写一开始，立即创建一个新的 INCR 文件
- 新写入的命令**直接写到新的 INCR 文件**，不再需要独立的"重写缓冲"
- 子进程在后台生成新的 BASE 文件
- BASE 生成完毕后，**原子更新 manifest**​ 指向新的 BASE + 新的 INCR 对
- 旧的 BASE 和 INCR 文件被标记为 HISTORY 并异步删除

> 💡 **第一性原理洞见**：Multi-Part AOF 的本质是把"单一文件 + 原地替换"的模型，升级为"不可变文件 + 元数据索引"的模型——这和现代存储系统（如 Kafka 的 segment、RocksDB 的 SSTable、Git 的对象存储）的设计哲学完全一致：**用"追加 + 索引"代替"原地修改"**。
> 
> 这个设计解决了经典 AOF 的三个根本问题：
> 
> 1. **消除双写**：新命令只写一次到新 INCR 文件
> 2. **消除重写缓冲的内存开销**：不需要在内存里累积重写期间的命令
> 3. **消除末尾阻塞**：manifest 的更新是 O(1) 的原子操作
> 
> 更深层的洞见是：**当一个机制的"临界区"成为瓶颈时，不要试图优化临界区，而要消除临界区的存在**。经典 AOF 的临界区是"重写完成那一刻的缓冲刷盘 + 文件替换"；Multi-Part AOF 通过"持续写入新 INCR + 后台准备新 BASE + 原子切换 manifest"彻底绕开了这个临界区。这是分布式系统里"分段（segmentation）+ 元数据切换"思想的经典应用。

**自动重写触发条件**：

```
auto-aof-rewrite-percentage 100   # 当前 AOF 比上次重写后增长 100%
auto-aof-rewrite-min-size 64mb    # 且 AOF 文件至少 64MB
```

两个条件**同时满足**才会触发 `BGREWRITEAOF`。

### 11.4 重点回顾

1. **AOF 记录命令而非数据**，用 RESP 协议格式，人眼可读
2. **三种 fsync 策略**：`always`（不丢）/ `everysec`（丢 1 秒，默认）/ `no`（丢 30 秒）
3. **AOF 载入用伪客户端重放命令**，复用命令执行管线
4. **AOF 重写是遍历内存生成最小命令集**，不是压缩原文件
5. **Redis 7 Multi-Part AOF**：BASE + INCR + MANIFEST，消除双写和重写缓冲
6. **RDB-AOF 混合持久化**（Redis 4.0+）：AOF 头部写 RDB 快照，兼顾加载速度和耐久性

## 第12章 事件

### 12.1 文件事件

Redis 是**事件驱动**的单线程服务器。antirez 在早期文档里明确说：Redis 不用 libevent/libev，而是**自己实现了一套事件库 `ae.c`**​ 。

事件库的核心是 `aeEventLoop` 结构 ：

```
typedef struct aeEventLoop {
    int maxfd;
    long long timeEventNextId;
    aeFileEvent events[AE_SETSIZE];  // 注册的文件事件
    aeFiredEvent fired[AE_SETSIZE]; // 已触发的文件事件
    aeTimeEvent *timeEventHead;     // 时间事件链表
    int stop;
    void *apidata;                  // 后端特定的数据（epfd/kqfd 等）
    aeBeforeSleepProc *beforesleep;
} aeEventLoop;
```

**文件事件**是 Redis 处理网络 I/O 的核心机制。每个客户端连接对应一个 socket fd，Redis 通过 `aeCreateFileEvent` 在这个 fd 上注册感兴趣的事件：

- **AE_READABLE**：fd 可读（客户端发了命令 / 新连接到达）
- **AE_WRITABLE**：fd 可写（可以向客户端发回复）

**文件事件的处理器（handler）**：

- 监听 socket 的 AE_READABLE → `acceptHandler`（接受新连接）
- 客户端 socket 的 AE_READABLE → `readQueryFromClient`（读命令）
- 客户端 socket 的 AE_WRITABLE → `sendReplyToClient`（发回复）

**I/O 多路复用的后端抽象**：

```
#ifdef HAVE_EVPORT
#include "ae_evport.c"    // Solaris
#else
    #ifdef HAVE_EPOLL
    #include "ae_epoll.c" // Linux
    #else
        #ifdef HAVE_KQUEUE
        #include "ae_kqueue.c" // BSD/macOS
        #else
        #include "ae_select.c" // 兼容后备
        #endif
    #endif
#endif
```

Redis 在编译时根据操作系统自动选择最高效的后端：**Linux 用 epoll，BSD/macOS 用 kqueue，Solaris 用 event ports，其他用 select**​ 。

> 💡 **洞见**：这种"根据平台选择最优后端"的抽象，是 Redis 能在各种 OS 上都保持高性能的关键。`ae.c` 提供统一接口，`ae_epoll.c`/`ae_kqueue.c` 等提供平台实现——这是典型的"策略模式 + 编译时多态"。值得一提的是，Redis 6.0 引入的 I/O 多线程，并没有改变文件事件的本质，只是在 `readQueryFromClient` 和 `sendReplyToClient` 这两个耗时的网络读写环节引入了多线程并行处理 ，事件循环的调度本身仍然是单线程的。

### 12.2 时间事件

时间事件是在**指定时间后执行**的回调。Redis 的时间事件存储在 `aeEventLoop` 的**单向链表**里（按 `when_ms` 排序）。

**最核心的时间事件是 `serverCron`**——它在 `initServer` 时通过 `aeCreateTimeEvent` 注册，初始延迟 1ms，之后**周期性自我重新调度**：

```
aeCreateTimeEvent(server.el, 1, serverCron, NULL, NULL);
```

`serverCron` 的执行频率由 `hz` 参数控制：

- 默认 `hz 10`：每秒 10 次，即每 **100ms**​ 执行一次
- `hz` 最大可设 500
- `dynamic-hz yes`（Redis 5.0+ 默认开启）：当客户端连接数很高时，自动提升 `hz` 到 500，让每次 cron 的工作量更小，避免延迟毛刺

**时间事件的典型应用**：

- `serverCron`：服务器周期性任务的总入口
- 客户端的超时检查
- 复制心跳
- 集群 periodic 任务
- 模块自定义的定时器

> 📌 **洞见**：时间事件用"链表"而非"优先队列"存储，看起来 O(N) 的扫描似乎低效。但 Redis 的设计者很清楚：**时间事件的数量极少**（通常只有个位数），链表扫描的成本可以忽略。这又是一个"按实际工作负载选数据结构"的范例——不要盲目追求理论最优，要看实际规模。

### 12.3 事件的调度与执行

事件循环的主函数是 `aeMain`，它调用 `aeProcessEvents` 在一个 `while` 循环里不断处理事件：

```
def redis_main():
    init_server()
    while server_is_not_shutdown():
        # 找到最近的时间事件
        te = get_nearest_time_event(server.time_event_linked_list)
        timeout_ms = te.when - now_in_ms()

        # 根据 timeout_ms 决定 poll 的阻塞时长
        if timeout_ms <= 0:
            poll(timeout=None)  # 已有时间事件到期，不阻塞
        else:
            poll(timeout=timeout_ms)  # 阻塞直到最近的事件到期

        # 先处理文件事件（客户端命令）
        process_file_events()

        # 再处理时间事件（serverCron 等）
        process_time_event()
```

**调度优先级的关键规则**：

1. **poll 的超时时间 = 最近的时间事件距离现在的毫秒数**。这保证了时间事件一定能按时被处理，且文件事件不会因为无限阻塞而饿死
2. **文件事件优先于时间事件**：`aeProcessEvents` 先处理所有已就绪的文件事件，再处理到期的时间事件
3. **同一 fd 的读事件优先于写事件**：避免因为写事件阻塞而导致读事件饿死

> ⚠️ **重要细节**：因为文件事件优先，如果某一轮有大量客户端请求涌入，`serverCron` 可能会被推迟执行。这就是为什么 `hz` 参数的调高有意义——它缩短了时间事件之间的间隔，减少了被文件事件"挤压"的程度。

**`beforeSleep` 钩子**：在每次 `aeApiPoll` 返回前、`process_file_events` 前调用，做一系列"睡前准备" ：

- 运行 lazy-free 队列
- 将 pending 的回复刷到输出缓冲区
- **flush AOF 缓冲区**（这就是为什么 AOF 的 `flushAppendOnlyFile` 在"事件循环每次迭代结束时"被调用）
- 发送集群总线包
- 传播 keyspace 事件

这是 Redis "**单线程 + 事件循环**" 模型最优雅的地方——**所有后台任务都被巧妙地嵌入到了事件循环的间隙中**，既没有额外的线程，又没有牺牲响应性。

### 12.4 重点回顾

1. **Redis 自己实现事件库 `ae.c`**，不用 libevent/libev
2. **文件事件**基于 I/O 多路复用：Linux 用 epoll、BSD 用 kqueue、Solaris 用 event ports
3. **时间事件**存储在链表里，核心是 `serverCron`
4. **调度规则**：文件事件优先于时间事件；poll 超时 = 最近时间事件的剩余时间
5. **`beforeSleep` 钩子**在每轮事件处理前做 AOF flush、回复发送等准备工作
6. **`dynamic-hz`**​ 让 `serverCron` 频率自适应客户端数量

## 第13章 客户端

### 13.1 客户端属性

每个连接到 Redis 的客户端，在服务端都对应一个 `client` 结构体（Redis 3.x 及之前叫 `redisClient`）。这个结构体是**网络上"连接"在服务端的完整投影**，包含了从 socket 到命令执行所需的全部状态。

按功能分类：

**① 通用属性**

- `id`：客户端唯一 ID
- `db`：当前指向的 `redisDb`（SELECT 的结果）
- `name`：客户端名称（由 `CLIENT SETNAME` 设置）
- `flags`：客户端状态标志（如 `CLIENT_MASTER`、`CLIENT_SLAVE`、`CLIENT_MONITOR`、`CLIENT_BLOCKED` 等）
- `fd`：客户端 socket 文件描述符（伪客户端为 -1）
- `createTime`、`lastInteractionTime`：创建时间和最后交互时间（用于超时判断）

**② 输入缓冲区**

- `querybuf`：动态 SDS，存储从 socket 读取的**原始协议数据**
- `querybuf_peak`：querybuf 的历史峰值（用于监控）

> ⚠️ **工业警示**：`querybuf` 的大小不受 `client-output-buffer-limit` 控制，但 Redis 会检查其大小，如果超过 `proto-max-bulk-len`（默认 512MB），客户端会被强制断开。这是防御"巨型命令攻击"的机制。

**③ 命令解析与执行状态**

- `argc` / `argv`：解析后的命令参数个数和参数数组
- `cmd`：指向命令表的指针（`redisCommand` 结构）
- `reqtype`：请求类型（内联命令 / RESP 协议）

**④ 输出缓冲区**（关键！有两个缓冲区）

Redis 为每个客户端维护**两个输出缓冲区**，这是书上可能没有重点强调但工业上极其重要的设计：

- **固定大小缓冲区 `buf[16KB]`**：用于存放**小回复**（如简单的 OK、整数、短字符串）。使用固定数组避免内存分配
- **可变大小缓冲区 `reply`**（一个 `list` 的 SDS 链表）：当回复超过 16KB 时，溢出部分存入这个链表

为什么两个缓冲区？**用固定数组处理 90% 的常见小回复，避免内存分配和碎片；用链表处理大回复，避免固定数组的 16KB 上限成为瓶颈**。

**输出缓冲区的限制**（生产环境必配）：

```
client-output-buffer-limit normal 0 0 0
client-output-buffer-limit replica 256mb 64mb 60
client-output-buffer-limit pubsub 32mb 8mb 60
```

格式：`<class> <hard limit> <soft limit> <soft seconds>`。当客户端输出缓冲区超过 hard limit 立即断开；超过 soft limit 持续 soft seconds 也断开。这是**防止"慢客户端"拖垮 Redis**​ 的关键机制——如果一个 pub/sub 订阅者消费速度跟不上，它的输出缓冲区会无限增长，最终吃光服务器内存，所以必须限制。

**⑤ 身份验证与多路复用**

- `authenticated`：是否已认证
- `user`：（Redis 6.0+ ACL）指向 `user` 结构的指针

**⑥ 阻塞与事务状态**

- `blocking_state`：BLPOP 等阻塞命令的状态
- `watch_keys`：WATCH 的事务键
- `transactions`：MULTI/EXEC 事务累积的命令

**⑦ 时间事件与定时任务**

- 客户端级别的超时检查由 `serverCron` 调用 `clientsCron` 统一处理

> 💡 **洞见**：`client` 结构体的设计体现了 Redis 对"连接"这一概念的完整建模——**一个 socket 连接不仅仅是 fd，它是 db 指针、输入输出缓冲、命令解析状态、事务状态、认证状态、阻塞状态的总和**。理解 client 结构，就理解了 Redis 如何处理"多路复用"——成百上千个客户端共享一个事件循环，但每个客户端都有自己独立的状态机。这就是为什么 Redis 能在单线程下支撑数万并发连接：它没有为每个连接开线程，而是把每个连接的状态都结构化地保存在 `client` 对象里，由事件循环统一驱动。

### 13.2 客户端的创建与关闭

**创建**：

1. 客户端 A 通过 `connect()` 连接 Redis 的监听 socket
2. 事件循环触发 AE_READABLE 事件 → `acceptHandler`
3. `acceptHandler` 调用 `accept()` 接受连接，创建新的 `client` 对象
4. 为新 socket 注册 AE_READABLE 事件，handler 为 `readQueryFromClient`
5. 新客户端进入 `server.clients` 链表（这是一个 `adlist`）

**关闭的多种场景**：

|场景|触发条件|处理方式|
|---|---|---|
|正常关闭|客户端发送 QUIT 或 TCP 连接正常关闭|优雅清理|
|超时关闭|`clientCron` 检测到 `now - lastInteraction > timeout`|强制断开|
|输出缓冲区超限|超过 `client-output-buffer-limit`|强制断开|
|输入缓冲区超限|超过 `proto-max-bulk-len`|强制断开|
|服务器关闭|收到 SIGTERM 且 `shutdown` 命令|所有客户端断开|
|主从复制断开|副本失去连接|副本客户端被清理|

**`clientCron` 的清理逻辑**（在 `serverCron` 中被调用）：

- 遍历 `server.clients`
- 检查超时：如果 `timeout` 配置 > 0 且 `now - client->lastInteractionTime > timeout`，关闭客户端
- 检查缓冲区：如果输出缓冲区超限，关闭客户端
- 批量处理（每轮 `serverCron` 检查一部分客户端，避免单次遍历所有客户端造成延迟毛刺）

> 📌 **工业经验**：生产环境中，**"超时关闭"是 Redis 对抗"僵尸连接"的主要武器**。一个配置不当的客户端（如忘记关闭连接池）可能留下成千上万个 idle 连接，每个都占用 `client` 结构体和输入/输出缓冲区。设置合理的 `timeout`（如 300 秒）可以自动清理这些连接。但注意：对于使用 `BLPOP` 等阻塞命令的客户端，`timeout` 不生效（因为从 Redis 视角它们"在等待"，不算是 idle）。

### 13.3 重点回顾

1. **`client` 结构体是连接的完整投影**：db 指针、输入输出缓冲、命令状态、事务状态、认证状态
2. **双输出缓冲区设计**：16KB 固定数组 + 可变 SDS 链表，兼顾常见小回复和大回复
3. **输出缓冲区限制是防御"慢客户端"的关键**：`client-output-buffer-limit` 必须按业务场景配置
4. **客户端创建**：accept → 创建 client → 注册文件事件
5. **客户端关闭**：正常关闭 / 超时 / 缓冲区超限 / 服务器关闭
6. **`clientCron` 批量清理**：避免遍历所有客户端造成延迟

## 第14章 服务器

### 14.1 命令请求的执行过程

这是 Redis 单机架构的"主线剧情"——一个命令从客户端发到 Redis 到回复返回，经历了什么？

**完整流程**：

**① 读取命令**

- 客户端 socket 触发 AE_READABLE 事件
- `readQueryFromClient` 被调用
- 从 socket 读取数据到 `client->querybuf`（SDS 动态扩展）
- 解析 RESP 协议，提取 `argc` 和 `argv`

**② 查找命令**

- 在命令表 `server.commands` 中根据 `argv[0]` 查找对应的 `redisCommand` 结构
- 命令表是一个 `dict`，key 是命令名字符串，value 是 `redisCommand` 结构指针
- 找不到命令 → 返回错误 `(error) ERR unknown command`

**③ 执行预备操作**

- 检查命令参数个数是否正确
- 检查客户端是否已认证（如果命令需要认证）
- 如果 `server.aof_state == AOF_ON` 且命令会修改数据，准备 AOF 传播
- 如果客户端处于订阅模式，某些命令会被拒绝
- 如果服务器正在加载数据，大部分命令会被拒绝

**④ 调用命令实现函数**

- 通过 `client->cmd->proc(client)` 调用具体命令实现
- 例如 `SET` 命令 → `setCommand`
- 命令实现修改内存中的数据结构，并通过 `addReply` 将回复写入客户端的输出缓冲区

**⑤ 执行后续工作**

- 如果命令修改了数据：
    - 传播到 AOF（追加到 `server.aof_buf`）
    - 传播到所有副本（`propagate`）
    - 标记脏数据（dirty），用于触发 RDB 自动保存
- 记录慢查询日志（如果命令执行时间超过 `slowlog-log-slower-than`）
- 记录命令统计信息

**⑥ 发送回复**

- `addReply` 将回复写入客户端的输出缓冲区
- 为客户端 socket 注册 AE_WRITABLE 事件，handler 为 `sendReplyToClient`
- 当 socket 可写时，`sendReplyToClient` 被调用，将输出缓冲区的内容发送到网络
- 发送完成后，如果输出缓冲区为空，注销 AE_WRITABLE 事件

> 💡 **第一性原理洞见**：命令执行流程揭示了 Redis 单线程模型的精髓——**整个流程是"非阻塞、事件驱动、状态机驱动"的**。任何一个命令的执行都不会长时间阻塞事件循环（除非命令本身是 O(N) 且 N 很大，这是 Redis 使用者要避免的）。客户端的状态（输入缓冲、输出缓冲、命令解析状态）被完整保存在 `client` 对象里，使得事件循环可以在多个客户端之间无缝切换——这正是"单线程 + 事件循环"能支撑高并发的根本原因。

**一个常被忽视的细节**：`addReply` 并不直接写 socket，而是**写输出缓冲区 + 注册写事件**。这是因为网络 I/O 是异步的——即使你调用 `write()`，内核 socket 缓冲区可能已满，必须等待可写事件。Redis 把这个"等待"交给了事件循环，自己继续处理下一个客户端。这种"绝不阻塞等待 I/O"的纪律，是 Redis 单线程模型高性能的根本保证。

### 14.2 serverCron函数

`serverCron` 是 Redis 的"心跳"，默认每 100ms 执行一次（由 `hz` 控制）。它负责所有"后台周期性任务"：

**① 更新时间缓存**

- 更新 `server.unixtime` 和 `server.mstime`（秒级和毫秒级时间戳）
- 这两个值是**缓存值**，精度只有 100ms，用于日志、LRU 计算、uptime 等对时间精度要求不高的场景
- 对于需要高精度时间的场景（如 `PEXPIRE`），直接调用 `gettimeofday()`

**② 更新 LRU 时钟**

- 每 10 秒更新一次 `server.lruclock`
- 用于计算键的空转时长：`idle = lruclock - redisObject.lru`

**③ 更新服务器统计信息**

- 每秒命令执行数（`ops_sec`）：通过抽样估算
- 内存使用峰值（`stat_peak_memory`）
- 网络连接数、命令数等

**④ 处理过期键**

- 调用 `activeExpireCycle` 主动清理过期键
- 这是第9章讲过的"主动删除"策略在 serverCron 中的具体执行点

**⑤ 客户端与数据库资源管理**

- 调用 `clientsCron`：检查客户端超时、清理无效客户端、释放过大的输出缓冲区
- 调用 `databasesCron`：对字典进行收缩（resize/rehash）、清理过期键

**⑥ 持久化协调**

- 检查 BGSAVE / BGREWRITEAOF 子进程状态
- 如果子进程完成，执行后续收尾（如替换 RDB 文件、更新 manifest）
- 将 AOF 缓冲区内容写入 AOF 文件（`flushAppendOnlyFile`）
- 检查是否需要触发自动 BGREWRITEAOF

**⑦ 复制与集群**

- 如果是主库：向副本发送心跳、积压缓冲区数据
- 如果是副本：检查与主库的连接、处理全量/部分重同步
- 集群模式：定期发送 Gossip 消息、检查故障转移

**⑧ 触发 AOF 重写**

- 根据 `auto-aof-rewrite-percentage` 和 `auto-aof-rewrite-min-size` 判断是否触发

**⑨ 内存淘汰**

- 如果设置了 `maxmemory`，调用 `performEvictions` 执行内存淘汰

**⑩ 处理 SIGTERM 信号**

- 如果收到关闭信号，设置 `server.shutdown_asap = 1`
- 下一次 `serverCron` 执行时，调用 `prepareForShutdown` 优雅关闭

> 📌 **洞见**：`serverCron` 是 Redis 单机版的"操作系统"——它负责任务调度、资源管理、垃圾回收、持久化协调、复制心跳。理解 `serverCron` 做什么，就理解了 Redis 作为一个"长期运行的服务进程"如何自我维持。**它的设计哲学是"把一切都变成周期性的、增量的、可分摊的工作"**：过期键清理是增量的、字典收缩是增量的、AOF 刷盘是增量的、内存淘汰是增量的。没有任何一项工作是"一次性大停顿"完成的——这正是 Redis 能保持低延迟的根本原因。

### 14.3 初始化服务器

Redis 服务器的启动流程（`main()` → `initServer()` → `aeMain()`）：

**① 设置信号处理器**

- SIGTERM：优雅关闭
- SIGSEGV/SIGBUS/SIGFPE/SIGILL：生成崩溃报告
- SIGHUP：忽略

**② 初始化配置**

- 加载默认配置 `initServerConfig()`
- 解析命令行参数和配置文件
- 应用配置到 `server` 结构体

**③ initServer() —— 核心初始化**

- 创建事件循环 `aeCreateEventLoop()`
- 创建数据库 `server.db = zmalloc(sizeof(redisDb) * server.dbnum)`
- 为每个 db 初始化 `dict` 和 `expires` 字典
- 创建监听 socket：`anetTcpServer()` 绑定 6379 端口
- 为监听 socket 注册 AE_READABLE 事件，handler 为 `acceptHandler`
- 创建共享对象（0~9999 的整数对象、OK 回复等）
- 初始化 `server.clients` 链表
- 初始化 `server.slaves` 链表
- 注册 `serverCron` 时间事件：`aeCreateTimeEvent(server.el, 1, serverCron, ...)`
- 如果启用了 AOF：打开 AOF 文件
- 如果配置了 RDB：尝试加载 RDB 文件（**这一步会阻塞直到加载完成**）
- 初始化后台线程（I/O 线程、lazy-free 线程、AOF fsync 线程等）

**④ 进入事件循环**

- `aeMain(server.el)`：开始处理事件
- 服务器正式对外服务

> ⚠️ **工业要点**：Redis 启动时的 **RDB/AOF 加载是同步阻塞的**——在这个阶段，Redis 不接受任何客户端连接。`redis-cli` 等客户端在连接时会做 "ready check"（发送 INFO 命令检查服务器是否已完成加载）。对于大数据集，这个加载过程可能持续数十分钟，在此期间 Redis 不可用。这就是为什么生产环境要**谨慎控制数据集大小**，或者使用 Redis 7 的 Multi-Part AOF（加载速度远快于纯 AOF 重放）。

**初始化的关键顺序**：

1. 先创建事件循环（因为后面要注册事件）
2. 再创建数据库（因为命令执行需要 db）
3. 再创建监听 socket 并注册 accept 事件（因为要接受连接）
4. 再注册 `serverCron` 时间事件（因为要周期性任务）
5. 最后加载持久化文件（因为要恢复数据）

这个顺序体现了**依赖关系的拓扑排序**——被依赖的先初始化，依赖别人的后初始化。这是任何复杂系统初始化的通用原则。

### 14.4 重点回顾

1. **命令执行全流程**：读取 → 解析 → 查命令 → 预备检查 → 执行 → 后续传播 → 回复
2. **`addReply` 不直接写 socket**，而是写输出缓冲 + 注册写事件，保持非阻塞
3. **`serverCron` 是 Redis 的心跳**：每 100ms 执行一次，负责过期清理、统计更新、持久化协调、复制心跳等
4. **"一切皆增量"**：serverCron 把所有后台任务都做成增量的、可分摊的，避免大停顿
5. **初始化顺序遵循依赖拓扑**：事件循环 → 数据库 → 监听 socket → serverCron → 加载持久化文件
6. **RDB/AOF 加载是启动时的同步阻塞点**，生产环境需谨慎

**第一性原理的深层洞察**：

**1. "单线程 + 事件循环"不是缺陷，而是 Redis 的核心竞争力**

很多人初看 Redis 会质疑："为什么不用多线程？单线程岂不是浪费多核？"但看完这四章你会明白：**Redis 的单线程模型是一个深思熟虑的架构选择，而非技术限制**。

- **无锁化**：单线程意味着没有任何竞态条件，不需要 mutex、不需要 CAS、不需要担心死锁。所有数据结构都可以放心地假设"我在独占访问"
- **可预测性**：每个命令的执行时间是确定的、可计算的。没有"上下文切换"、没有"锁竞争"、没有"线程调度"的不可预测性
- **简单性**：代码极其简洁。你看 `serverCron` 的代码，没有任何锁保护——因为它知道自己是唯一在跑的
- **实际瓶颈在内存和网络，不在 CPU**：对于 O(1) 或 O(log N) 的命令，CPU 从来不是瓶颈。Redis 的瓶颈通常是网络 I/O 和内存带宽

Redis 6.0 引入的多线程**只用于网络读写**（`readQueryFromClient` 和 `sendReplyToClient`），命令执行本身依然是单线程的 。这是对"单线程核心"的坚守——多线程是为了**并行化网络 I/O 这种"与逻辑无关"的工作**，而不是为了并行化命令执行。

**2. AOF 与 RDB 的本质差异：数据的"时间观"**

- **RDB 是"横切面"**：它在某一时刻对内存数据做一个快照，记录的是"数据在某个时间点的状态"
- **AOF 是"纵切面"**：它记录所有修改数据的命令，记录的是"数据如何随时间演变成当前状态"

这两种"时间观"对应了两种不同的工程哲学：

- RDB 适合**备份和灾难恢复**——一个紧凑的文件，可以归档、可以传输到异地
- AOF 适合**数据耐久性**——最大限度减少数据丢失

Redis 7 的 Multi-Part AOF 巧妙地将两者结合：**BASE 文件用 RDB 格式（紧凑、加载快），INCR 文件用 AOF 格式（追加、耐久）**。这是"横切面"和"纵切面"的完美融合。

**3. 事件循环是 Redis 的"操作系统"**

如果把 Redis 服务器比作一台计算机，那么：

- **事件循环 = 调度器**（决定下一步执行什么）
- **文件事件 = 中断**（网络 I/O 就绪）
- **时间事件 = 定时器**（周期性任务）
- **client 对象 = 进程控制块**（每个连接的完整状态）
- **serverCron = 内核线程**（后台周期性任务）

理解了这个类比，你就能理解为什么 Redis 能在单线程下做到如此高的并发——**它实现了一个用户态的、"极简版的操作系统"**，专门为"内存数据库"这个特定工作负载优化。没有通用操作系统的进程调度开销，没有上下文切换，没有锁——一切都是为速度而生。

**4. "增量主义"是 Redis 性能的工程信条**

纵观这四章，你会发现一个反复出现的模式——**Redis 拒绝任何"一次性大工作"**：

- 过期键清理：渐进式 rehash + 随机抽样，而非一次性扫描全部 key
- AOF 重写：fork 子进程后台进行，父进程继续服务
- 字典 rehash：分摊到每次字典操作，而非一次性完成
- `serverCron`：每 100ms 做一次少量工作，而非累积后做一次大量工作
- 内存淘汰：每次 `serverCron` 淘汰一小批，而非 OOM 时一次性淘汰

这种"增量主义"的哲学，保证了 Redis 在任何时刻的延迟都是可预测的、可控的。**这是 Redis 能作为"低延迟数据库"服务于广告竞价、实时风控、秒杀等高要求场景的根本原因**。

## 工业落地建议

把第11～14章的知识应用到生产环境，有以下具体建议：

**1. AOF 配置的最佳实践**

```
appendonly yes
appendfsync everysec
no-appendfsync-on-rewrite yes
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb
aof-use-rdb-preamble yes  # Redis 4.0+ 混合持久化
```

- `everysec` 是性能与耐久性的最佳平衡点
- `no-appendfsync-on-rewrite yes` 避免重写期间 fsync 竞争
- 大内存实例可适当提高 `auto-aof-rewrite-min-size` 到 128mb 或 256mb，减少重写频率

**2. 监控 AOF 相关指标**

```
INFO persistence
# 关注：aof_enabled, aof_rewrite_in_progress, aof_last_rewrite_time_sec
# aof_current_rewrite_time_sec 如果长时间 > 0，说明重写卡住了
```

**3. `hz` 参数的调优**

- 默认 `hz 10` 适用于大多数场景
- 高并发场景（> 10万 QPS）建议 `hz 100` + `dynamic-hz yes`，让 `serverCron` 更频繁地执行小批量工作
- 但 `hz` 过高会增加 CPU 开销，需在测试环境验证

**4. 客户端资源管理**

```
timeout 300  # 5分钟无活动自动断开
tcp-keepalive 60  # TCP keepalive
client-output-buffer-limit normal 0 0 0
client-output-buffer-limit replica 512mb 128mb 60
client-output-buffer-limit pubsub 64mb 16mb 60
```


格式为 `<class> <hard_limit> <soft_limit> <soft_seconds>`：

- **normal**：普通客户端。默认 `0 0 0` 即**不限制**——因为普通客户端是"请求-响应"模式，不读数据就不会有输出堆积
- **replica**：主从复制中的副本客户端。硬限制 256MB，软限制 64MB 持续 60 秒
- **pubsub**：发布订阅客户端。硬限制 32MB，软限制 8MB 持续 60 秒——因为订阅者是"push"模式，发布者速度快于订阅者消费速度时，缓冲区会暴涨

> 📌 **为什么普通客户端默认不限？**​ Redis 配置文件的原话解释得很清楚：普通客户端不会"被动"接收数据，只有发起请求后才会收到响应，因此只有异步客户端（如 pubsub、replica）才会出现"数据生产速度快于消费速度"的场景 。但对 pubsub 和 replica，必须限制——否则一个慢订阅者就能拖垮整个服务。

**排查缓冲区溢出的实战命令**：

```
# 查看当前限制
redis-cli CONFIG GET client-output-buffer-limit

# 找出输出缓冲区异常的客户端
redis-cli CLIENT LIST | grep -v "omem=0" | sort -t= -k15 -rn | head -20
```

`CLIENT LIST` 输出中关键字段 ：

- `omem`：该客户端的输出内存使用量（字节）
- `oll`：输出链表长度（output list length）
- `qbuf` / `qbuf-free`：查询缓冲区已用 / 剩余

当日志中出现 `scheduled to be closed ASAP for overcoming of output buffer limits` 时 ，说明该客户端因为缓冲区超限被标记为待关闭。

**生产环境调优建议**：

```
# Pub/Sub 场景：发布者可能瞬间推送大量消息
client-output-buffer-limit pubsub 128mb 32mb 120

# 高写入场景下的副本：全量同步时副本接收 RDB 可能很慢
client-output-buffer-limit replica 512mb 128mb 120

# 如果业务确实有"大响应"需求（如 SCAN 大范围、LRANGE 深分页）
client-output-buffer-limit normal 256mb 64mb 60
```

> ⚠️ **重要提醒**：`replica` 的限制**不能低于 `repl-backlog-size`**，否则配置会被忽略（Redis 会使用 repl-backlog-size 的大小）。因为副本客户端会共享 backlog 缓冲区的内存 。

**根因治理胜于参数调优**：缓冲区溢出往往是"慢消费者"的表象。常见的慢消费者包括 ：

- Pub/Sub 订阅者消费速度跟不上发布者
- 执行 `MONITOR` 命令的客户端（输出量极大）
- 应用层接收到 `KEYS *` 或超大 `LRANGE` 的结果后处理缓慢

根治方案是**替换危险命令**：

```
# 危险：一次性返回所有 key，阻塞且输出巨大
KEYS *

# 安全：分批迭代
SCAN 0 COUNT 100

# 危险：深分页可能返回海量数据
LRANGE mylist 0 -1

# 安全：分页读取
LRANGE mylist 0 99
LRANGE mylist 100 199
```

### 5. 启动加载与可用性

Redis 启动时如果启用了持久化，会进入 `LOADING` 状态，期间**所有数据命令都返回错误**​ ：

```
(error) LOADING Redis is loading the dataset in memory
```

**加载优先级**​ ：

1. 如果启用了 AOF（`appendonly yes`）→ 优先加载 AOF（含 RDB preamble 则先加载 RDB 部分）
2. 否则如果存在 RDB 文件 → 加载 RDB
3. 否则 → 空数据库

**加载耗时参考**​ ：

- 10GB RDB 在 SSD 上约 30-60 秒
- 机械硬盘可能需要数分钟
- 纯 AOF 重放比 RDB 加载慢 5-10 倍

**监控加载进度**（即使在 LOADING 状态，`INFO` 命令仍可执行）：

```
redis-cli INFO persistence | grep -E "loading|rdb|aof"
# loading:1
# loading_loaded_perc:20.00
# loading_eta_seconds:120
```

> 💡 **工业启示**：Redis 重启期间的 LOADING 状态是生产环境的"黑暗时刻"——所有依赖 Redis 的服务都不可用。缓解策略：
> 
> - 使用 **Redis 7 的 Multi-Part AOF**：BASE 文件是 RDB 格式，加载速度远快于纯 AOF 重放
> - 启用 **`aof-use-rdb-preamble yes`**：AOF 头部写 RDB 快照
> - 主从架构下，**先重启副本**让其完成加载并成为新主库，再重启原主库
> - 使用 **Redis Sentinel 或 Cluster**​ 实现故障转移，将单点重启转化为滚动重启

### 6. hz 参数的精细调优

`hz` 参数控制 `serverCron` 的执行频率，默认 10（即每 100ms 一次）。

**不同工作负载的推荐值**​ ：

|工作负载|推荐 hz|说明|
|---|---|---|
|通用场景|10|默认，平衡 CPU 与响应性|
|限速器、短 TTL|20-50|加快过期键清理|
|极高键周转率|50-100|主动过期更激进|
|低流量、省 CPU|5|降低后台任务开销|
|实时过期要求|100|最大化过期及时性|

**`dynamic-hz` 的自适应机制**（Redis 5.0+ 默认开启）：

当客户端数量激增时，Redis 会自动提升 `hz`（上限 500），保证每个 `serverCron` tick 处理的客户端数不超过阈值 ：

```
while (listLength(server.clients) / server.hz > MAX_CLIENTS_PER_CLOCK_TICK) {
    server.hz *= 2;
    if (server.hz > CONFIG_MAX_HZ) {
        server.hz = CONFIG_MAX_HZ;
        break;
    }
}
```

这意味着**连接数越多，`serverCron` 越频繁执行**，但每次执行的工作量更小——避免了"大批量客户端检查"造成的延迟毛刺。

> 📌 **调优经验**：`hz` 每提升 100，CPU 开销约增加 1-2% 。需要在测试环境用真实业务流量验证，监控 `INFO stats` 中的 `expired_keys` 速率和 `INFO cpu` 的 CPU 占用，找到最佳平衡点。

### 7. AOF 配置的现代最佳实践

基于 Redis 7 的 Multi-Part AOF，推荐的 `redis.conf` 配置 ：

```
# 启用 AOF（默认启用 multi-part 格式）
appendonly yes
appenddirname "appendonlydir"
appendfilename "appendonly.aof"

# fsync 策略：everysec 是最佳平衡
appendfsync everysec

# 重写期间禁止 fsync，避免与 AOF 写入竞争
no-appendfsync-on-rewrite yes

# 自动重写触发条件
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb

# 使用 RDB 格式作为 BASE 文件（更快的加载速度）
aof-use-rdb-preamble yes

# 允许加载截断的 AOF（容错）
aof-load-truncated yes

# 启用 AOF 时间戳（用于时间点恢复）
aof-timestamp-enabled yes
```

**监控 AOF 状态**：

```
redis-cli INFO persistence | grep aof
# aof_enabled:1
# aof_rewrite_in_progress:0
# aof_rewrite_scheduled:0
# aof_last_rewrite_time_sec:2
# aof_current_rewrite_time_sec:-1
# aof_base_size:10240000
```

**AOF 目录结构**（Redis 7+）：

```
appendonlydir/
├── appendonly.aof.1.base.rdb   # BASE：RDB 格式快照
├── appendonly.aof.2.incr.aof   # INCR：增量命令日志
└── appendonly.aof.manifest     # MANIFEST：跟踪当前活跃文件
```

查看 manifest 内容：

```
cat /var/lib/redis/appendonlydir/appendonly.aof.manifest
# file appendonly.aof.1.base.rdb seq 1 type b
# file appendonly.aof.2.incr.aof seq 2 type i
```

> 💡 **洞见**：Multi-Part AOF 的 manifest 文件是整个设计的"点睛之笔"——它是**唯一需要在重写完成时原子更新的文件**，而 manifest 本身只有几百字节 。这意味着重写完成的"临界区"从"追加数百 MB 的重写缓冲 + rename 大文件"，缩小为"写入一个 tiny manifest + 原子 rename"。这是用"元数据与数据分离"的思想消除性能瓶颈的经典案例。

## 第11~14章的深层串联：Redis 单机版的"第一性原理"

把 AOF 持久化、事件驱动、客户端管理、服务器初始化这四章放在一起，我们可以看到 Redis 作为一个"内存数据库服务器"的**完整工程哲学**。

### 洞见一：Redis 是"用户态操作系统"

如果把 Redis 与操作系统做类比：

|操作系统概念|Redis 对应实现|
|---|---|
|进程调度器|事件循环 `aeMain`|
|中断|文件事件（socket 可读可写）|
|定时器|时间事件（`serverCron`）|
|进程控制块|`client` 结构体|
|虚拟文件系统|键空间 `db->dict`|
|页缓存 / SWAP|持久化（RDB/AOF）|
|内核线程|I/O 线程、lazy-free 线程、AOF fsync 线程|

**Redis 自己实现了一个"极简操作系统"**，专门为"内存数据库"这个特定工作负载优化 。它抛弃了通用操作系统的进程调度、虚拟内存、文件系统等功能，用几千行 C 代码实现了事件循环、内存管理、持久化的核心。

这种"用户态操作系统"架构的优势：

- **无上下文切换**：单线程执行命令，没有进程/线程切换开销
- **无锁**：单线程意味着不需要任何锁机制
- **可预测性**：每个操作的延迟可精确计算
- **极简**：代码量少，bug 面小，易于维护

### 洞见二："增量主义"是 Redis 性能的工程信条

纵观这四章，Redis 拒绝任何"一次性大工作"：

- **过期键清理**：随机抽样 + 基数树 hint，渐进式清理
- **AOF 重写**：fork 子进程后台进行，父进程继续服务
- **字典 rehash**：分摊到每次字典操作
- **`serverCron`**：每 100ms 做一次小批量工作
- **内存淘汰**：每次 `serverCron` 淘汰一小批
- **Multi-Part AOF**：用"持续写入新 INCR + 后台准备新 BASE + 原子切换 manifest"消除重写临界区

这种"增量主义"的哲学保证了 Redis 在任何时刻的延迟都是可预测的、可控的。**这是 Redis 能作为"低延迟数据库"服务于广告竞价、实时风控、秒杀等高要求场景的根本原因**。

### 洞见三：AOF 与 RDB 的本质差异——"时间观"

- **RDB 是"横切面"**：记录数据在某个时间点的状态
- **AOF 是"纵切面"**：记录数据如何随时间演变成当前状态

Redis 7 的 Multi-Part AOF 巧妙地将两者结合：

- **BASE 文件用 RDB 格式**：紧凑、加载快（横切面的优势）
- **INCR 文件用 AOF 格式**：追加、耐久（纵切面的优势）
- **MANIFEST 文件做元数据管理**：原子切换（消除临界区）

这是对"时间观"的工程调和——**既不是纯横切面（RDB 丢数据），也不是纯纵切面（AOF 加载慢），而是两者的融合**。

### 洞见四：事件循环是 Redis 单线程模型的灵魂

事件循环的核心调度逻辑 ：

```
def ae_process_events():
    # 1. 计算最近的时间事件，作为 poll 的超时时间
    timeout = nearest_time_event().when - now()
    
    # 2. 阻塞等待文件事件，最多等 timeout 毫秒
    fired_events = ae_api_poll(timeout)
    
    # 3. 先处理文件事件（客户端命令）
    for event in fired_events:
        event.handler()
    
    # 4. 再处理到期的时间事件（serverCron 等）
    process_due_time_events()
```

**关键规则**：

- **文件事件优先于时间事件**：确保客户端请求得到及时响应
- **poll 超时 = 最近时间事件的剩余时间**：确保时间事件按时执行，同时文件事件不会饿死
- **`beforeSleep` 钩子在每轮 poll 前执行**：做 AOF flush、回复发送等准备工作

这套调度机制保证了：

- **低延迟**：文件事件优先，客户端命令不被时间事件阻塞
- **高时效**：时间事件通过 poll 超时机制保证按时执行
- **无饥饿**：poll 超时机制确保时间事件最终一定会被处理

### 洞见五：客户端是"网络上连接"的完备投影

每个 `client` 结构体保存了该连接的**全部状态**：

- 当前数据库指针 `db`
- 输入输出缓冲区
- 命令解析状态 `argc` / `argv` / `cmd`
- 事务状态、WATCH 状态
- 认证状态、ACL 用户
- 阻塞状态（如 BLPOP）

**这是 Redis 单线程支撑数万并发连接的秘密**：它没有为每个连接开线程，而是把每个连接的状态结构化地保存在 `client` 对象里，由事件循环统一驱动 。当某个客户端 socket 就绪时，事件循环取出对应的 `client` 对象，恢复其状态机，继续执行。

这种模式与 Node.js 的"事件驱动 + 单线程"、Nginx 的"worker + epoll"、Go 的"goroutine + netpoller"本质上是同一个思想——**用"状态机 + 事件循环"代替"线程 + 阻塞 I/O"**。

第11~14章完成了从"数据结构与对象"到"单机数据库实现"的跃迁。至此，Redis 的全部核心机制已经呈现在你面前：

**Redis 设计的五个第一性原理**：

1. **内存为王**：一切设计围绕"内存访问的高效性"展开——SDS 的预分配、intset 的紧凑编码、ziplist/listpack 的连续内存、embstr 的一次分配
2. **单线程的纯粹性**：用"事件循环 + 状态机"代替"多线程 + 锁"，获得无锁化、可预测性、极简性
3. **增量主义**：任何"大工作"都分解为"可分摊的小工作"——rehash、过期清理、AOF 重写、serverCron
4. **按需付费**：特性不免费提供，只有在使用时才付出成本——TTL 用独立字典、紧凑编码只在小数据时使用
5. **工程务实**：不追求理论最优，而追求"在实际工作负载下够用且高效"——跳跃表而非红黑树、SipHash 而非加密哈希、Multi-Part AOF 而非分布式一致性协议
