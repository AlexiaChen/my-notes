
# 《Redis设计与实现》读书笔记 · 第9章～第10章

这两章标志着全书从"数据结构与对象"部分正式跨入"单机数据库的实现"部分。**第9章回答的是"Redis 如何像一个数据库一样工作"——键存哪里、库怎么切换、TTL 怎么管理；第10章回答的是"Redis 如何假装自己是一个持久化数据库"——通过 RDB 快照在内存与磁盘之间架桥**。

> ⚠️ 版本提醒：黄健宏的书基于 Redis 3.x。而在现代 Redis 中，过期算法在 Redis 6 经历了一次重要重写（引入基数树加速），RDB 格式也从书里的版本演进到 **RDB v11**；Redis 7.0 之后 AOF 改为 multi-part 结构，8.0 引入了 Hash 字段级过期。下面以书的结构为主线，用现代源码校正细节。

## 第9章 数据库

### 9.1 服务器中的数据库

Redis 服务器将所有数据组织为 **多个逻辑数据库**，由 `redisServer` 中的 `redisDb db[16]` 数组管理，默认 16 个库（可由 `databases 64` 配置修改）。

每个 `redisDb` 的核心结构：

```
typedef struct redisDb {
    dict *dict;         // 键空间：key → redisObject
    dict *expires;      // 过期字典：key → 绝对过期时间戳（毫秒）
    dict *blocking_keys;// BLPOP 等阻塞键
    dict *ready_keys;   // 解除阻塞的键
    dict *watched_keys; // WATCH 的事务键
    int id;             // 数据库编号
    // ... 聚类、跳过列表等统计结构
} redisDb;
```

**两个核心字典的设计哲学**：键空间和过期字典是**分离的**。官方文档明确解释了这个选择的动机——"我们不在 key 上保存 TTL 值，因为在不需要过期的情况下（尤其是 Redis 不作为缓存使用时）会产生内存开销。因此，易失键的 TTL 存储在通常比主字典更小的**辅助哈希表**中" 。

> 💡 **第一性原理洞见**：这个"双字典"设计体现了 Redis 一贯的"按需付费"哲学——TTL 是可选功能，不应该让所有 key 都承担它的成本。更进一步，因为 `expires` 字典只收录"有 TTL 的 key"，**主动过期清理时只需要抽样这个子集，而不用遍历整个键空间**​ 。如果只有 10% 的 key 设有 TTL，主动过期就只走 10% 的数据——这是用"空间上的分离"换"时间上的高效"。

在 Redis 8.0 中，这个结构进一步演进为 `kvstore` 抽象 ，为后续的字段级过期（Hash Field Expiration，Redis 7.4 引入）打好了基础。

### 9.2 切换数据库

客户端通过 `SELECT n` 命令切换当前操作的数据库，本质是修改 `client->db` 指针指向 `server.db[n]`。

**几个关键事实**：

- 所有对数据的操作（GET/SET/HSET 等）都隐含"在当前 client->db 上操作"
- 不同库之间的 key 是完全隔离的，但 `FLUSHALL` 会清空所有库
- `MOVE key db` 命令可以将 key 在库之间移动
- 集群模式下只能用 0 号库（cluster 要求所有 key 在同一空间）

> 📌 **工业经验**：多库（select 0~15）在生产环境其实是个"反模式"。因为：
> 
> 1. 多库间没有权限隔离，一个 `FLUSHALL` 全部完蛋
> 2. 集群模式不支持多库，迁移时会痛苦
> 3. 现代实践推荐**用 key 前缀模拟多租户**（如 `user:1000:name`、`order:2001:status`），而不是用 `SELECT` 切库。Redis 官方在 Cluster 模式下强制单库，已经表明了态度。

### 9.3 数据库键空间

键空间（keyspace）就是 `db->dict` 这个哈希表，key 是 SDS 字符串，value 是 `redisObject` 指针。

**对键空间的所有操作都是对 dict 的操作**：

- `SET key value` → `dictAdd(db->dict, key, robj)`
- `GET key` → `dictFetchValue(db->dict, key)` 再检查过期
- `DEL key` → 从 `dict` 和 `expires` 同时删除
- `RANDOMKEY` → `dictGetRandomKey(db->dict)`

**键空间通知**（9.8 节会详述）：Redis 通过 `__keyspace@<db>__:<key>` 和 `__keyevent@<db>__:<event>` 两个频道，用 pub/sub 广播键空间事件 。这意味着你可以订阅 `SET`/`DEL`/`EXPIRE` 等操作，实现"数据变更触发外部动作"的模式。

**键空间的维护操作**：

- `SCAN` 命令：基于 dict 的游标遍历，不阻塞服务
- 读写比率统计：`INFO stats` 中的 `total_connections_received`、`total_commands_processed` 等
- 键空间命中率：`INFO stats` 中的 `keyspace_hits` / `keyspace_misses`

> 💡 **洞见**：键空间不只是一个 dict，它是**整个 Redis 数据模型的载体**。`db->dict` 是"数据在哪里"，`db->expires` 是"数据何时死"，`blocking_keys` 是"谁在等数据"，`watched_keys` 是"事务在看谁"。**一个 `redisDb` 结构把"数据存储"、"生命周期"、"阻塞语义"、"事务语义"全部编码进去了**——这是 Redis 作为"单线程事件驱动服务器"的必然性：所有状态必须集中、可预测、无锁。

### 9.4 设置键的生存时间或过期时间

四个核心命令：

|命令|语义|精度|
|---|---|---|
|`EXPIRE key seconds`|相对时间，秒|秒|
|`PEXPIRE key ms`|相对时间，毫秒|毫秒|
|`EXPIREAT key ts`|绝对 Unix 时间戳，秒|秒|
|`PEXPIREAT key ms-ts`|绝对 Unix 时间戳，毫秒|毫秒|

**底层统一为 `pexpireGenericCommand`**：四个命令最终都转化为 `PEXPIREAT`，即在 `db->expires` 中写入 `key → 绝对毫秒时间戳` 。

其它相关命令：

- `TTL key` / `PTTL key`：查询剩余时间（返回 -1 表示无 TTL，返回 -2 表示 key 不存在）
- `PERSIST key`：从 `expires` 字典中删除条目，取消过期
- `SET key value EX/PX/EXAT/PXAT/KEEPTTL`：创建带过期时间的 key

> ⚠️ **工业要点**：TTL 的**分辨率始终是 1 毫秒**​ ，即使你用 `EXPIRE` 设秒级精度，内部也是毫秒存储。另外，**过期时间在磁盘上是持久化的**——Redis 重启后，过期时间依然有效，时间会"真实流逝" 。这意味着：如果你用 Redis 做分布式锁，依赖 TTL 自动释放，那么 Redis 重启不会让你的锁"假死"。

**一个反直觉的细节**：`EXPIRE` 命令是 O(1) 的，**它与 value 的大小无关**——因为 TTL 是存在独立的 `expires` 字典里的，修改 TTL 不触碰 value 本身 。

### 9.5 过期键删除策略

理论上有三种经典删除策略：

**① 定时删除（Timer-based）**

- 思路：为每个 key 设置一个定时器，TTL 到达时立即删除
- 优点：最及时，内存友好
- 缺点：**不可扩展**——如果有 100 万个带 TTL 的 key，就要注册 100 万个定时器。即使高效的定时器轮（timer wheel）也会消耗大量 CPU 周期来管理

**② 惰性删除（Lazy / Passive）**

- 思路：key 被访问时才检查是否过期
- 优点：对 CPU 极其友好，只在必要时付出代价
- 缺点：如果 key 永不被访问，会一直占用内存——内存泄漏

**③ 定期删除（Active / Periodic）**

- 思路：每隔一段时间，扫描一部分 key，删除过期的
- 优点：平衡 CPU 和内存
- 缺点：难以调参——频率高了费 CPU，频率低了内存回收不及时

> 📌 **洞见**：Redis 的选择是**惰性删除 + 定期删除的组合**，刻意避开了定时删除。这是一个工程上极其清醒的决策：**"精确"是有成本的，而"概率性及时"在大多数场景下够用了**。对于缓存场景，少量 key 多活几秒完全可以接受；对于需要严格过期的场景，应该用 `PX` 精确控制或使用 Redis 8.0+ 的字段级过期。

### 9.6 Redis的过期键删除策略

Redis 的具体实现：

**惰性删除**：在 `lookupKey` / `expireIfNeeded` 函数中，每次 key 被访问时：

```
int expireIfNeeded(redisDb *db, robj *key) {
    long long when = getExpire(db, key);
    if (when < 0) return 0;  // 无 TTL
    if (when > mstime()) return 0;  // 未过期
    // 已过期：删除 key 并传播 DEL 命令
    deleteExpiredKeyAndPropagate(db, key);
    return 1;
}
```

**主动删除**：由 `serverCron` 周期性调用 `activeExpireCycle`，默认每秒 10 次（`hz 10`）：

```
对每个 db：
  重复：
    从 expires 字典随机抽 20 个 key
    删除其中已过期的
    如果过期比例 > 25%：继续循环（这一轮多扫）
    否则：跳出（这一轮结束）
  直到 CPU 时间预算耗尽（默认 tick 的 25%）
```

**Redis 6 的重大改进**：引入了**基数树（radix tree）`expires_cursor`**​ 作为辅助结构 。工作原理：

- 主动过期时，抽样 `expires` 哈希表
- 如果抽到的 key 已过期 → 立即删除
- 如果抽到的 key "即将过期" → 放入基数树作为 Hint
- 下一次循环从基数树开始（而不是盲目抽样）

这样**把"即将过期"的信息资本化**，显著降低了"hidden memory"（已逻辑过期但仍占用内存的 key）。在 Redis 6 之前，最坏情况下可能有 25% 的 key 逻辑过期但仍占用内存；Redis 6 之后这个比例大幅下降 。

**可调参数**：

- `hz`：主动过期频率，默认 10，最大 500。提高 `hz` 让过期更及时但更费 CPU
- `dynamic-hz yes`：根据客户端连接数自适应调整 `hz`（Redis 5.0+ 默认开启）
- `active-expire-effort`：主动过期的努力程度，1~10，越大回收越积极但越费 CPU

> 💡 **第一性原理洞见**：Redis 6 的这次重写揭示了一个深刻的工程真理——**当你的随机采样效率下降时，不是去调采样数量，而是去改变采样的"形状"**。原来是在哈希表里"盲抽"，现在是用基数树"记住"那些快要过期的 key，让下次采样有方向。这类似于缓存预取（prefetching）的思想：用一次发现的"即将过期"信息，降低未来采样的盲目性。
> 
> 更深层的洞见是：**概率性算法的"概率"部分可以被学习**。"随机采样"是最朴素的概率算法，而"基数树 + 随机采样"是"学习增强的概率算法"——系统从过去的采样中积累知识，让未来的采样更聪明。这是机器学习思想在系统编程中的一个微缩体现。

### 9.7 AOF、RDB和复制功能对过期键的处理

这是 Redis 一致性保证的关键环节。

**RDB 对过期键的处理**：

- 生成 RDB 时：已过期的 key **不会被保存**到 RDB 文件
- 载入 RDB 时：如果服务器是主库，会检查 key 的过期时间，已过期则忽略；如果是副本库，则保留所有 key（包括已过期的），等待主库同步删除命令

**AOF 对过期键的处理**：

- 当 key 因过期被删除时，Redis 会**追加一条 DEL 命令**到 AOF 文件
- AOF 重写时：已过期的 key 不会被写入新 AOF 文件

**复制对过期键的处理**（关键点！）：

- **只有主库执行过期删除**（无论是惰性还是主动）
- 主库删除 key 时，会**向所有副本传播 DEL 命令**
- 副本**永远不会主动删除过期 key**（即使是 READONLY 命令访问到过期 key，也是返回旧值，然后等待主库的 DEL 到达）

> ⚠️ **工业警示**：这个"主库驱动过期"的设计意味着——**如果主库和副本之间的网络中断，副本上的 key 可能会"超期服役"**。在断网期间，副本会返回本应已过期的 key 的值。这不是 bug，而是 CAP 定理下的一致性取舍：Redis 选择"在网络分区时，副本继续提供旧数据"，而不是"拒绝服务"。对于强一致性要求的场景，需要在应用层做补偿。

**Redis 8.0 的字段级过期**：Hash 的 field 也可以单独设 TTL（`HEXPIRE`），这是对"键级过期"的 finer-grained 扩展 。这意味着未来"过期删除"的概念会从 `db->expires` 字典扩展到 `hash->field_expires` 结构。

### 9.8 数据库通知

Redis 通过 pub/sub 提供两类键空间通知：

**键空间通知**（关注"哪个 key 发生了什么"）：

- 频道：`__keyspace@<db>__:<key>`
- 消息：事件名（如 `set`、`del`、`expire`）
- 例：对 `SET mykey hello` 的响应，`__keyspace@0__:mykey` 频道收到消息 `"set"`

**键事件通知**（关注"某个事件发生在哪些 key 上"）：

- 频道：`__keyevent@<db>__:<event>`
- 消息：key 名
- 例：对 `SET mykey hello` 的响应，`__keyevent@0__:set` 频道收到消息 `"mykey"`

**启用方式**：`notify-keyspace-events` 配置项，由字母组合控制：

- `K`：键空间事件，`E`：键事件
- `g`：通用命令（DEL、EXPIRE 等）
- `$`：字符串命令
- `h`：Hash 命令
- `s`：Set 命令
- `z`：Sorted Set 命令
- `x`：过期事件（expired）
- `e`：驱逐事件（evicted）

> 💡 **工业应用**：键空间通知是实现"数据变更触发器"的强大工具。典型场景：
> 
> - **缓存失效联动**：订阅 `del` 事件，触发下游缓存清理
> - **审计日志**：订阅所有写事件，异步记录审计 trail
> - **实时分析**：订阅 `set`/`hset` 事件，实时更新统计
> - **分布式协调**：监听 `expired` 事件，实现简单的分布式锁超时通知
> 
> 但要注意：通知是**fire-and-forget**的，不保证送达。如果消费者离线，错过的事件不会重放。对于关键业务，应该配合其他机制（如事务日志、CDC）使用。

### 9.9 重点回顾

按第一性原理提炼：

1. **redisDb 是 Redis 单机状态的载体**：`dict` 存数据，`expires` 存 TTL，两者分离是"按需付费"哲学的体现
2. **TTL 存绝对毫秒时间戳**，四个 EXPIRE 命令殊途同归到 PEXPIREAT
3. **惰性删除 + 主动抽样**是 Redis 的选择，回避了不可扩展的"定时删除"
4. **Redis 6 引入基数树加速主动过期**，把"概率采样"升级为"学习增强的概率采样"
5. **过期删除只有主库执行**，通过 DEL 命令传播到副本，保证最终一致性
6. **键空间通知**基于 pub/sub，是"数据变更触发器"的利器

## 第10章 RDB持久化

### 10.1 RDB 文件的创建与载入

RDB 是 Redis 的**时间点快照（point-in-time snapshot）**持久化机制。

**三种触发方式**：

|命令/配置|执行方式|使用场景|
|---|---|---|
|`SAVE`|主线程同步执行，**阻塞服务**​|几乎不用，调试时偶尔用|
|`BGSAVE`|fork 子进程，子进程写盘|生产环境标准方式|
|自动保存（`save` 配置）|`serverCron` 检查触发 BGSAVE|周期性自动快照|

**BGSAVE 的核心是 fork + Copy-On-Write**：

- 父进程调用 `fork()` 创建子进程
- 子进程继承父进程的内存空间（**不复制物理内存**，靠页表共享）
- 子进程遍历键空间，序列化到 `dump.rdb`
- 父进程继续服务客户端请求，对内存的修改触发 COW，被修改的页才真正复制

**fork 的成本**：与进程 RSS（常驻内存集）成正比，大约 **10µs/GB**​ 。这意味着一个 100GB 的 Redis 实例 fork 只需约 1ms——这就是 Redis 能支撑大内存实例的关键。

**载入过程**：

- 服务器启动时，检测到 RDB 文件存在，自动载入
- `rdbLoad()` 在主线程执行（无法并行，因为要重建内存结构）
- 先读 REDIS 魔数校验文件合法性
- 依次读 AUX 字段、每个数据库的 SELECT_DB、RESIZEDB、键值对
- 最后校验 CRC64

> 💡 **洞见**：RDB 的"载入"是**纯顺序读**——没有随机 I/O，没有命令解析，就是一块内存的二进制反序列化。这就是为什么 RDB 恢复速度极快：100GB 的 RDB 文件在现代 SSD 上 30-90 秒就能载入完成 。相比之下，AOF 要逐条重放命令，慢 5-10 倍。这是"空间换时间"的另一面——**用紧凑的二进制格式换极速恢复**。

### 10.2 自动间隔性保存

`redis.conf` 中的 `save` 配置：

```
save 3600 1       # 3600秒内至少1个key变更
save 300 100      # 300秒内至少100个key变更
save 60 10000     # 60秒内至少10000个key变更
```

**实现机制**：

- `dirty` 计数器：记录自上次 SAVE/BGSAVE 以来的修改次数
- `lastsave` 时间戳：上次成功保存的时间
- `serverCron` 每秒检查一次：遍历所有 `save` 条件，满足任一则触发 BGSAVE

**现代默认值**（Redis 5+ 的 redis.conf）：

```
save 3600 1
save 300 100
save 60 10000
```

> ⚠️ **工业经验**：默认的 `save 60 10000` 意味着如果 60 秒内有 1 万次写入，就会触发一次 BGSAVE。对于高写入负载的实例，这可能导致**频繁 fork**，引发：
> 
> - CPU 尖刺（fork 本身 + 子进程序列化）
> - 内存压力（COW 导致脏页复制）
> - 延迟毛刺（特别是云环境，fork 可能因内存带宽饱和而变慢）
> 
> 建议根据业务容忍度调整：对数据安全性要求高的场景，可以改为 `save 60 1000` 或更激进；对纯缓存场景，可以完全禁用 `save ""`，改用 AOF。

### 10.3 RDB 文件结构

现代 RDB 文件（v11）的整体布局 ：

```
+-----------+------------+-------------+------------+-----+---------+
|  "REDIS"  | 版本号"0011"|  AUX 字段    | 数据库数据  | ... | EOF+CRC |
+-----------+------------+-------------+------------+-----+---------+
   5字节        4字节      变长          变长              1字节+8字节
```

**详细结构**：

**① 文件头（9 字节）**

- 魔数 `"REDIS"`（5 字节）
- 版本号 `"0011"`（4 字节 ASCII，当前是 RDB v11）

**② AUX 字段**（RDB v7+ 引入 ）

- `redis-ver`：生成 RDB 的 Redis 版本
- `redis-bits`：64 或 32（指针宽度）
- `ctime`：文件创建时间
- `used-mem`：生成时的内存使用量
- `aof-preamble`：是否有 AOF 前缀
- `repl-stream-db` / `repl-id` / `repl-offset`：复制信息

**③ 数据库数据**（可以有多个库）

- `0xFE` + 1 字节 db id：SELECT_DB 操作码
- `0xFB` + key 数量 + expire 数量：RESIZEDB 提示（让加载器预分配哈希表）
- 键值对序列：
    - `[0xFD/0xFC] + 过期时间`：可选，秒/毫秒精度
    - `[类型字节]`：RDB_TYPE_STRING / RDB_TYPE_LIST / RDB_TYPE_HASH 等
    - `[key]`：长度前缀字符串
    - `[value]`：类型特定的二进制编码

**④ 结束标记**

- `0xFF`：EOF 操作码
- `CRC64`（8 字节）：全文件校验和

**长度编码**（变长，极其紧凑）：

```
00xxxxxx          → 6位长度（0-63）
01xxxxxx xxxxxxxx → 14位长度（0-16383）
10000000 + 4字节  → 32位长度
10000001 + 8字节  → 64位长度
11xxxxxx          → 特殊编码
```

**各种数据类型的编码**：

- 字符串：int 编码（1/2/4/8 字节整数）、LZF 压缩字符串、原始字符串
- List：quicklist（Redis 3.2+），节点内是 ziplist/listpack
- Hash：ziplist（老）/ listpack（Redis 7.0+）
- Set：intset 或 hashtable 编码
- ZSet：ziplist（老）/ listpack（Redis 7.0+）或 skiplist+dict
- Stream：Radix Tree 编码（Redis 5.0+）

> 💡 **第一性原理洞见**：RDB 格式的精髓在于**"内存布局的直接序列化"**。许多编码（如 intset、listpack）在内存中是什么样，写入 RDB 就是什么样——加载时直接 `memcpy` 到内存，不需要重新构建。这使得 RDB 既紧凑又快速。这与 Protobuf/Thrift 等"跨平台中立"的序列化框架形成鲜明对比：RDB 牺牲了跨语言兼容性，换取了极致的 Redis 内部效率。这是符合"第一性原理"的——**Redis 的持久化只需要服务 Redis 自己**，没必要为不存在的"跨语言读取"需求付出代价。

> - **内存异常排查**：哪个 key 占了多少内存？用 `rdbtools` 生成内存报告

> - **容量规划**：基于 RDB 分析数据增长趋势

### 10.5 重点回顾

1. **RDB 是时间点快照**，通过 fork + COW 实现不阻塞的服务端持久化
2. **fork 成本约 10µs/GB RSS**，这是 Redis 能支撑大内存实例的关键
3. **RDB 文件结构**：REDIS 魔数 + 版本 + AUX 字段 + 数据库数据 + EOF + CRC64
4. **当前 RDB 版本为 v11**，AUX 字段让文件自描述
5. **RDB 是紧凑的二进制格式**，恢复速度远快于 AOF 重放（5-10倍差距）
6. **RDB 不记录命令，只记录状态**——这是它与 AOF 的本质区别

## 第9～10章的横向串联：从"内存数据库"到"持久化数据库"的跨越

这两章共同回答了 Redis 最核心的身份问题：**"Redis 究竟是不是数据库？"**

```
┌─ 键空间（db->dict）：数据的家
第9章    ├─ 过期字典（db->expires）：数据的死亡时钟
         ├─ 惰性删除 + 主动抽样：死亡的执行者
         └─ 主从复制下的过期传播：一致性的保证

         ┌─ RDB 快照：某一刻的内存镜像
第10章   ├─ fork + COW：不阻塞的快照魔法
         ├─ 紧凑二进制格式：极速恢复的基础
         └─ AUX 字段 + CRC64：自描述与完整性
```

**第一性原理的深层洞察**：

1. **Redis 是"假装"持久化的内存数据库**。这句话不是贬义，而是精确描述：RDB 是定期的、概率性的持久化，不是 WAL（Write-Ahead Log）那种逐条持久化。这意味着**Redis 在"性能"和"持久性"之间明确选择了性能**——RDB 默认配置下可能丢失最近几分钟的数据。这是符合第一性原理的：Redis 的定位是"高速缓存 + 轻量数据库"，不是"强一致事务数据库"。如果你需要不丢数据，应该用 AOF 的 `appendfsync always`，或者直接用 MySQL/PostgreSQL。
2. **过期删除与持久化是正交的两套机制，但必须协同工作**。RDB 保存的是"某一刻的快照"——那一刻已过期的 key 不会进 RDB，未过期的 key 会带着过期时间戳进 RDB。载入时，过期时间被还原，key 在后续访问或主动过期中被清理。**这套协同机制的精妙之处在于：它让"时间"本身成为了数据的一部分**——RDB 不仅保存了"数据是什么"，还保存了"数据能活到什么时候"。
3. **fork + COW 是 Redis 持久化的基石，也是 Redis 单线程模型的必然选择**。因为 Redis 是单线程处理命令，不能在主线程做 I/O 密集的序列化；fork 让子进程继承内存，子进程去写盘，父进程继续服务。**这是 Redis "单线程 + 多进程" 混合架构的精华**——命令执行单线程（无锁、无竞争），持久化多进程（fork 子进程）。理解了这个，你才能理解为什么 Redis 7.0 之后的 AOF 改为 multi-part（base + increment）结构，为什么 Redis 6 引入 threaded I/O——**Redis 一直在"单线程优势"和"多核利用率"之间寻找平衡**。
4. **RDB 的"紧凑"是双刃剑**。紧凑意味着恢复快，但也意味着**RDB 是不可读的二进制格式**——你不能像 AOF 那样直接 `cat` 出来看。这迫使 Redis 生态发展出 `redis-check-rdb`、`rdbtools` 等工具链。工业界的一个趋势是：**用 RDB 做基线快照 + AOF 做增量日志**（Redis 4.0+ 的 `aof-use-rdb-preamble yes`），既享受 RDB 的快速恢复，又享受 AOF 的秒级数据安全保障。

## 工业落地建议

把这两章的知识用到生产环境，有六条具体可操作的建议：

1. **监控过期键的"hidden memory"**：定期查看 `INFO stats` 中的 `expired_keys`，结合 `INFO memory` 的 `used_memory` 观察趋势。如果发现 `used_memory` 居高不下但 `expired_keys` 持续增长，可能是主动过期跟不上——适当调高 `hz` 或 `active-expire-effort`
2. **短 TTL 场景的特殊调优**：如果你的业务有大量亚秒级 TTL 的 key（如限流器、临时令牌），默认 `hz 10` 可能不够激进。考虑：
    
    ```
    hz 100
    active-expire-effort 10
    ```
    
      
    但这会增加 CPU 开销，需在测试环境验证
3. **RDB 与 AOF 的混合策略**（Redis 4.0+ 强烈推荐）：
    
    ```
    save 3600 1
    save 300 100
    save 60 10000
    appendonly yes
    appendfsync everysec
    aof-use-rdb-preamble yes
    ```
    
      
    这样既保留了 RDB 的快速恢复能力，又将崩溃时的数据丢失窗口限制在 1 秒内
4. **大内存实例的 fork 优化**：
    - 使用 **jemalloc**（Redis 默认内存分配器），它对 COW 友好
    - 避免在云环境的突发性能实例（如 AWS t3/t4）上跑大内存 Redis，因为 CPU 积分耗尽时 fork 会变慢
    - 监控 `INFO stats` 中的 `latest_fork_usec`，正常情况下应 < 1秒/GB
5. **RDB 文件的安全管理**：
    - 定期 `redis-check-rdb` 校验 RDB 文件完整性
    - RDB 文件包含**明文数据**，务必做好文件权限（600）和传输加密
    - 对 RDB 做异地备份时，注意 AUX 字段里的 `repl-id` 和 `repl-offset` 可能与目标实例冲突
6. **键空间通知的生产使用**：
    - 不要依赖键空间通知做"强一致"的业务逻辑，它是 fire-and-forget 的
    - 对于 `expired` 事件，注意主从架构下**只有主库会发出**这个通知
    - 消费者离线期间的事件会丢失，关键场景需要配合其他机制
