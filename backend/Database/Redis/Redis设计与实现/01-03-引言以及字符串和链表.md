
# 《Redis设计与实现》读书笔记 · 第1章～第3章

黄健宏这本书的妙处在于：它不是单纯讲"Redis 怎么用"，而是沿着源码一路往里剥，告诉你"为什么这样设计"。但正如你所说，中文译本在某些术语和推理链条上偏干涩，而且 Redis 本身迭代极快——书里基于的版本（大致 3.x 前后）与今天 7.x/8.x 的源码已经有了明显分叉。所以这份笔记我会**以书的目录结构为主线**，把书里的结论、现代 Redis 源码的演变、以及工业场景中的真实取舍揉在一起写，争取让你看到的不是"复述"，而是"站在作者肩膀上再看一眼"。

## 第1章 引言

### 1.1 Redis版本说明

书里标注的版本是阅读基准线，但你心里要清楚一条时间线：

- **Redis 3.2 之前**：List 的底层是 `ziplist + adlist` 双实现，根据元素个数/大小切换
- **Redis 3.2**：引入 `quicklist`（ziplist 的双向链表），取代单纯的 adlist 作为 List 主力
- **Redis 6.x 之后**：SDS 的头部从单一的 `sdshdr` 演化为 `sdshdr5/8/16/32/64` 五种规格 ，String 的 `embstr` 阈值定为 **44 字节**​
- **Redis 7.0+**：ziplist 彻底退役，由 `listpack` 接班

> 💡 **第一性原理视角**：版本号背后其实是两条纠缠的主线——**性能的可预测性**和**内存占用的极致压榨**。每一次底层结构更替，都不是"重写"，而是在这两者之间重新找平衡点。

### 1.2 章节编排

书的整体布局分两大部分：**数据结构与对象**​ → **单机数据库的实现**。这个编排顺序本身就是一种设计哲学的表达：

1. 先讲**底层构件**（SDS、链表、字典、跳跃表、整数集合、压缩列表）——这些是"原子的、无业务含义的"
2. 再讲**对象系统**（对象、字符串、哈希、列表、集合、有序集合）——把底层构件组合成对外可见的 Type
3. 最后讲**数据库运转**（数据库、RDB、AOF、事件、客户端、服务器）——让对象系统在单机环境下跑起来

这种"自底向上"的路径，恰好对应了 Redis 源码 `src/` 目录下的文件组织方式：`sds.c`、`adlist.c`、`dict.c` 是基础，`object.c`、`t_string.c` 是中层，`server.c`、`networking.c` 是上层。

> 📌 **我的洞见**：读 Redis 源码最大的误区是想"从 `main()` 开始顺流而下"。正确姿势恰恰相反——**从最底层的数据结构往上爬**。因为上层的 server 逻辑全是建立在这些底层构件的语义保证之上的。如果你不理解 SDS 为什么是二进制安全的，你就无法理解为什么 Redis 的 key 可以是任何字节序列；如果你不理解 adlist 的 `dup/free/match` 函数指针，你就看不懂客户端链表是怎么被统一管理的。

### 1.3 推荐的阅读方法

作者建议"带着问题读"+"对照源码读"。我补充三条更具体的：

- **对照英文一手资料**：Redis 内部文档（redis.io/docs 的 internals 章节）是 antirez 本人写的，比如 SDS 那篇 。遇到中文译本讲不清楚的地方，直接回溯源码 `src/sds.h`、`src/adlist.h`。
- **画"结构 → 操作 → 复杂度"三栏表**：每个数据结构都问自己三个问题：内存怎么排？增删改查怎么走？复杂度是多少？
- **关注"为什么不用现成的"**：Redis 几乎每个数据结构都是自己造轮子（SDS 不用 C 原生字符串、adlist 不用 C++ STL、dict 不用现成哈希表）。每做一次"重复造轮子"，背后都有一段工程权衡。这是本书最值得嚼的部分。

### 1.4 行文规则

作者在前言里交代了命名习惯：`sds` 既是库名也是类型名、`listNode`/`list` 区分节点与容器。这条规则在读源码时至关重要——Redis 的 C 代码没有命名空间，靠前缀区分模块：`sds*` 是字符串、`list*` 是链表、`dict*` 是字典。

> ⚠️ 提醒：书里很多函数签名是基于老版本写的。比如老版 `sdshdr` 是 `{ long len; long free; char buf[]; }` ，而现代版本 `sdsMakeRoomFor` 采用"小于 1MB 翻倍，大于 1MB 每次只加 1MB"的策略 。看书时要把"书的结论"和"当前版本的细节"分开记。

### 1.5 配套网站

书的配套站点（redisbook.com）主要放勘误和补充图示。但更值得逛的是：

- Redis 官方 GitHub 的 `src/` 目录（最新源码）
- antirez 的 GitHub 上独立的 `sds` 库（[https://github.com/antirez/sds](https://github.com/antirez/sds)），它已经被抽出来作为独立项目维护

## 第2章 简单动态字符串（SDS）

### 2.1 SDS的定义

SDS 全称 Simple Dynamic String。**它本质上是"带元数据的字节数组"**：在 C 字符串（`char buf[]`）的基础上，在前面塞了一个 header 记录长度和空闲空间。

老版本 header 长这样 ：

```
struct sdshdr {
    long len;   // 已使用字节数
    long free;  // 未使用字节数
    char buf[]; // 实际数据
};
```

现代版本则按字符串长度分成 5 种规格的 header ，以节省小字符串的元数据开销：

|Header|适用长度|Header 大小|
|---|---|---|
|sdshdr5|< 32 bytes|1 byte|
|sdshdr8|< 256 bytes|3 bytes|
|sdshdr16|< 65536 bytes|5 bytes|
|sdshdr32|< 4 GiB|9 bytes|
|sdshdr64|< 16 EiB|17 bytes|

**关键 trick**：`sds` 类型本身是 `char *`，指向 `buf` 而非 header 的起点 。这样 SDS 对上层看起来就是普通 C 字符串，能用 `printf("%s", s)` 直接打印；但只要你往前偏移几个字节，就能拿到 header 里的 `len`。

> 💡 **第一性原理视角**：SDS 的本质是用**极小的固定开销（1~17 字节）**去购买三样东西——O(1) 长度、二进制安全、写入安全。这是一种典型的"空间换时间 + 空间换正确性"的双重交易。在内存以 GB 计的今天，这点元数据开销可以忽略；但它换来的工程收益是巨大的。

### 2.2 SDS与C字符串的区别

这是本章的核心，也是面试高频题。我把它重建成一张"四维对比"：

**① 长度获取：O(N) → O(1)**

C 字符串靠 `\0` 定位结尾，`strlen()` 必须遍历；SDS 直接读 `len` 字段 。

**② 二进制安全：否 → 是**

C 字符串不能有 `\0`，否则被截断，所以存不了图片、音频、序列化对象 ；SDS 靠 `len` 界定边界，`buf` 里可以有任意字节 。

**③ 缓冲区溢出：有风险 → 自动防护**

C 字符串 `strcat` 不检查空间，极易溢出 ；SDS 的 API 在修改前先调 `sdsMakeRoomFor` 确保容量，不够就自动扩容 。

**④ 内存重分配次数：每次修改都可能 → 摊销 O(1)**

靠两个策略 ：

- **空间预分配**：扩容时额外多分配一些（<1MB 翻倍，≥1MB 加 1MB）
- **惰性释放**：缩短字符串时不立即回收，而是记在 `free` 里以备后用

**追补一层工业视角**：

String 类型在 Redis 内部还有**三种编码**自动切换 ：

- `int`：值能放进 `long` 范围的整数，直接存在 `redisObject` 的 `ptr` 字段里，零额外分配
- `embstr`：≤44 字节的字符串，`redisObject` 和 SDS **一次性分配**，减少碎片
- `raw`：>44 字节，两者分开分配

`embstr` 实际上是只读的——一旦对它做 `APPEND` 之类的修改，会**不可逆地升级为 `raw`**​ 。这个设计背后的考虑是：短字符串追求的是"分配效率"，长字符串追求的是"修改灵活度"，二者不可兼得。

> 📌 **我的洞见**：SDS 不是"更好的 C 字符串"，它是**为 Redis 的工作负载量身定做的字符串**。Redis 是内存数据库，字符串是最常见的 value 载体，也是 key 的载体，还是输入/输出缓冲区的载体 。它面临的工作负载特征是：长度变化频繁、需要存二进制、对延迟极度敏感。SDS 的所有设计——O(1) 长度、预分配、二进制安全——都是冲着这三个特征去的。脱离这个上下文去看 SDS，会觉得"至于吗，搞这么复杂"；放回上下文，才明白**每一个字节、每一次 realloc 都算计到了**。

### 2.3 SDS API

书里列了主要 API，我从"职能分组"的角度重新归类，方便记忆：

**创建类**

- `sdsnewlen(init, len)`：核心构造函数，从任意二进制数据创建
- `sdsnew(init)`：从 C 字符串创建
- `sdsempty()`：创建空串

**查询类**

- `sdslen(s)`：O(1) 取长度
- `sdsavail(s)`：取剩余空间

**修改类**

- `sdscatlen / sdscat / sdscatsds`：追加
- `sdscpylen / sdscpy`：覆盖
- `sdsMakeRoomFor`：确保容量（内部调用）
- `sdsgrowzero`：补零增长到指定长度

**工具类**

- `sdstrim`：两端修剪
- `sdsrange`：截取子串
- `sdssplitlen / sdssplitargs`：分割（CONFIG 解析、命令行解析用）
- `sdscatprintf / sdscatfmt`：格式化拼接（`sdscatfmt` 比 `printf` 快，但占位符受限）

> ⚠️ 注意 `sdscatfmt` 这个函数——它是 Redis 自己实现的一个轻量 formatter，专门服务于协议拼接这种"频繁但格式简单"的场景。这又是一个"不用现成、自己造"的例子：C 的 `printf` 太通用、太慢，Redis 宁可牺牲通用性换性能。

### 2.4 重点回顾

按"第一性原理"重新提炼这一章的内核：

1. **SDS = C 字符串 + 长度前缀 + 空闲空间**，用 `char *` 对外伪装成 C 字符串
2. **五个现代 header 规格**是为了让小字符串的元数据开销最小化
3. **O(1) 长度、二进制安全、防溢出**是 SDS 的三大硬保障
4. **预分配 + 惰性释放**让频繁修改的摊销成本降到 O(1)
5. **String 的三编码（int/embstr/raw）**是与 SDS 正交的另一层抽象，解决"值如何存"的问题

## 第3章 链表

### 3.1 链表和链表节点的实现

Redis 的链表实现叫 `adlist`，我猜是 "a doubly linked list" 的缩写 。它由三个结构组成：

**listNode —— 单个节点**：

```
typedef struct listNode {
    struct listNode *prev;
    struct listNode *next;
    void *value;   // 万能指针，可存任意类型
} listNode;
```

**list —— 链表容器**：

```
typedef struct list {
    listNode *head;
    listNode *tail;
    void *(*dup)(void *ptr);     // 值复制函数
    void (*free)(void *ptr);     // 值释放函数
    int (*match)(void *ptr, void *key); // 值比对函数
    unsigned long len;           // 节点数，O(1) 获取长度
} list;
```

**listIter —— 迭代器**：

```
typedef struct listIter {
    listNode *next;
    int direction;  // AL_START_HEAD 或 AL_START_TAIL
} listIter;
```

几个关键设计点：

- **双端**：`head`/`tail` 都维护，头尾插入都是 O(1)
- **无环**：`head->prev = NULL`、`tail->next = NULL`
- **多态**：`value` 是 `void *`，配合三个函数指针，让同一个 adlist 能装任意类型的数据
- **O(1) 长度**：`len` 字段常驻

> 💡 **第一性原理视角**：为什么 `list` 结构里要放 `dup/free/match` 三个函数指针？因为 `value` 是 `void *`，链表本身不知道怎么复制、释放、比较节点值。**把"值该怎么管"交给使用者注入**，链表就成了一个真正通用的容器。这是 C 语言里模拟"泛型 + 多态"的经典手法，Linux 内核的链表也是同一思路。代价是：每次操作值都要走一次指针间接调用；收益是：一套链表代码服务全 Redis。

### 3.2 链表和链表节点的API

按操作类型分组：

**生命周期**

- `listCreate()`：建空链表
- `listRelease(list)`：释放整个链表，若设置了 `free` 则逐个释放节点值

**节点增删**

- `listAddNodeHead(list, value)`：头插，O(1)
- `listAddNodeTail(list, value)`：尾插，O(1)
- `listInsertNode(list, old_node, value, after)`：在指定节点前后插
- `listDelNode(list, node)`：删除节点

**遍历**

- `listGetIterator(list, direction)`：取迭代器
- `listNext(iter)`：取下一项
- `listReleaseIterator(iter)`：释放迭代器
- `listRewind(list, li)` / `listRewindTail(list, li)`：重置迭代器到头/尾

**查找与访问**

- `listSearchKey(list, key)`：按值查找（用 `match` 指针）
- `listIndex(list, index)`：按下标取节点，支持负数（-1 是尾节点）

**其他**

- `listDup(orig)`：深拷贝整个链表
- `listRotate(list)`：把尾节点移到头部（用在数据库轮换等场景）

### 3.3 重点回顾与工业视角

书里这一章表面讲的是"链表怎么实现"，但**在工业语境下，adlist 的角色已经发生了演变**：

**早期（Redis 3.2 前）**：adlist 是 List 类型的底层实现之一，当元素较多或元素较大时，从 ziplist 切换到 adlist 。

**现代（Redis 3.2+）**：List 类型统一由 `quicklist` 实现（ziplist 的双向链表），adlist 退居二线，**专职服务 Redis 的内部模块**​ ：

- **客户端管理**：`server.clients` 就是一个 adlist，维护所有连上来的 client
- **事务模块**：MULTI/EXEC 期间，命令队列用 adlist 按顺序保存
- **事件模块**：时间事件（time event）用 adlist 串起来
- **发布/订阅**：订阅了某个 channel 的客户端用 adlist 维护
- **慢日志、监视器**等也依赖 adlist

> 📌 **我的洞见**：adlist 的命运变迁其实是 Redis 工程演进的缩影。作为"对外数据结构"的 List，Redis 必须考虑**内存效率**——adlist 每个节点有 `prev/next/value` 三个指针，64 位系统下光指针就 24 字节，加上 `listNode` 本身的内存分配开销，小数据量时浪费惊人 。所以 Redis 用 `quicklist`（链表 + 压缩列表/ listpack）替代它，在"链表的可扩展性"和"连续内存的紧凑性"之间取折中 。

但作为"对内基础设施"，adlist 的**通用性、O(1) 头尾操作、函数指针注入**这些特质无可替代。客户端要增删、事务命令要保序、时间事件要遍历——这些场景对内存没那么敏感，对正确性和灵活性敏感，adlist 刚好。

**这给工业设计的启示**：

1. 同一个数据结构，在对内和对外场景中，评价标准完全不同——对外要抠内存，对内要抠灵活性和正确性的边际成本
2. "通用容器 + 函数指针回调"是 C 语言写可复用组件的经典范式，值得在自研系统里借鉴
3. 没有"最好的数据结构"，只有"在特定工作负载下最合适的数据结构"。quicklist 取代 adlist 不是因为 adlist 差，而是因为 List 的工作负载变了

## 第2章 + 第3章的横向串联

读完这两章，你应该能在脑子里建立起 Redis 底层构件的第一张地图：

```
┌─ SDS：二进制安全、O(1) 长度、防溢出 ──┐
Redis 基础构件 ├─ adlist：通用双端链表，函数指针多态 ─┤
              ├─ dict（下一章）：哈希表，渐进式 rehash
              ├─ ziplist/listpack：紧凑线性存储
              └─ ...
```

**SDS 和 adlist 的共同基因**：它们都是"在 C 语言的原始构件上，加一层元数据 + 一层 API 封装"，把"裸指针操作"变成"有语义保障的操作"。SDS 加的是 `len/free`，adlist 加的是 `len/dup/free/match`。**这种"元数据 + API"的封装哲学，贯穿整个 Redis 源码**——你在后面读 dict、跳表、整数集合时，会一而再再而三地看到同样的套路。

> ⚠️ 一个容易被译本带偏的点：书里基于的老版本 SDS 只有单一 header，而现代版本有 5 种 。如果你直接对着书看 7.x 源码，会在 `sds.h` 里看到 `SDS_TYPE_5/8/16/32/64` 等宏，不要慌，本质没变，只是"元数据本身也做了按需精简"。

## 工业落地小贴士

把这两章的知识用到实际系统里，有几条具体可操作的建议：

1. **key 和短 value 尽量控制在 44 字节以内**​ —— 触发 `embstr` 编码，少一次内存分配
2. **大 value 别硬塞 String**​ —— 超过 44 字节就是 `raw`，再大考虑分片或用 Hash 的 `field` 拆分（Redis 的 Hash 在元素 <512 且 value <64 字节时用 `listpack`，更省内存）
3. **SDS 的预分配策略意味着"反复 append 小段"比"一次性写好"更划算**​ —— 因为摊销 O(1)；但如果你知道最终长度，用 `sdsnewlen` 一次到位更省
4. **在自己的 C/C++ 项目里**如果需要字符串容器，SDS 的独立库（antirez/sds）是可以直接抄作业的——它比 `std::string` 更轻，二进制安全，且 API 简洁
5. **看到 Redis 的 List 别默认它就是"链表"**​ —— 现代版本是 quicklist，它的性能特征和纯 adlist 不一样：头尾操作仍是 O(1)，但中间插入会触发节点分裂
