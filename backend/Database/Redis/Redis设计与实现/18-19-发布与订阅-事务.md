
# 《Redis设计与实现》读书笔记 · 第18章 发布与订阅 + 第19章 事务

这两章表面上看是"两个独立功能"——一个做消息广播，一个做原子操作。但如果站在"Redis 如何在不破坏单线程简洁性的前提下，向外扩展出分布式系统原语"这个视角看，它们其实是**同一设计哲学的两面**：**用最小的概念扩展，换取最大的表达能力**。Pub/Sub 用"频道"这一个概念就实现了发布者与订阅者的完全解耦；事务用"命令队列 + 单线程执行窗口"这一个机制就实现了原子性，再用 WATCH 这一个原语实现了乐观并发控制。

> ⚠️ 版本提醒：黄健宏的书基于 Redis 3.0 左右的实现。现代 Redis 在 Pub/Sub 上已经有了重要演进——**Redis 7.0 引入了 Sharded Pub/Sub（分片发布订阅）**，通过 `SSUBSCRIBE`/`SPUBLISH`/`SUNSUBSCRIBE` 命令，将消息限定在哈希槽所在的节点，从而在 Cluster 环境下大幅降低带宽消耗 。这反映了 Redis 在"简单"与"规模"之间的持续权衡。下面以书的结构为主线，用现代 Redis 官方文档校正细节。

# 第18章 发布与订阅

## 18.1 频道的订阅与退订

**核心命令**：`SUBSCRIBE channel [channel ...]` / `UNSUBSCRIBE [channel ...]`

当一个客户端执行 SUBSCRIBE 后，它就进入了一种**特殊的"订阅态"**——这个连接从此只能执行 `SUBSCRIBE`、`PSUBSCRIBE`、`UNSUBSCRIBE`、`PUNSUBSCRIBE`、`PING`、`QUIT` 这六个命令，不能再执行 SET/GET 这类常规命令 。

**这个设计的第一性原理是什么？**

Redis 是单线程事件循环。如果一个连接一边订阅频道等待消息推送，一边又发出常规的读写命令，那么"消息何时推送"就变成了一个调度问题——是命令先执行？还是消息先推送？为了避免这种复杂性，Redis 选择了**最简单的方案：把连接切成两种互斥模式**——

```
普通模式: 可以执行任何命令，但不会有消息推送下来
订阅模式: 只能执行订阅相关命令，但会持续收到推送的消息
```

这是一种"用限制换简洁"的典型 Redis 风格取舍。代价是订阅客户端不能同时做数据读写（要读写就得另开连接）；收益是服务端实现极其简单——订阅态连接的事件处理路径完全独立。

**订阅确认的协议设计**：

SUBSCRIBE 命令的回复不是一个简单的 OK，而是一系列推送消息：

```
*3          ← 数组类型，3个元素
$9          ← 接下来字符串长度9
subscribe   ← 消息类型
$5          ← 频道名长度5
first       ← 频道名
:1          ← 当前客户端订阅的频道总数
```

这种"以消息形式确认订阅"的设计，使得客户端可以**在一个统一的流上读取所有类型的消息**——订阅确认、退订确认、实际消息推送，全是同一种格式 。客户端无需为"执行命令"和"接收消息"维护两套读取逻辑。

**退订的精妙之处**：

`UNSUBSCRIBE` 不带参数时，退订所有频道。当最后一个频道也被退订后，客户端**自动从订阅模式退出，恢复为普通模式**​ ——第三个元素（剩余订阅数）变为 0 就是这个信号。

> 💡 **洞见：SUBSCRIBE 的本质是"连接维度的状态变更"**
> 
> 书的实现细节讲得很清楚——服务器为每个客户端维护一个 `pubsub_channels` 字典，记录该客户端订阅的所有频道；同时每个频道也维护一个订阅者链表。这是一个**双向索引**结构：
> 
> - 从客户端查"我订阅了哪些频道" → O(1) 查客户端结构
> - 从频道查"有哪些订阅者" → O(1) 查频道结构
> 
> 这种双向索引在 Pub/Sub 场景下是必须的：SUBSCRIBE 时要更新两端，PUBLISH 时要遍历频道下的订阅者链表推送消息，UNSUBSCRIBE 时要从两端清理。如果用单向索引，退订时就需要遍历所有频道去找"哪个频道包含这个客户端"，复杂度从 O(1) 退化到 O(N)。
> 
> **这就是"空间换时间"思想在 Pub/Sub 中的直接应用**——用额外的客户端→频道索引，换取 O(1) 的退订操作。

### 工业应用：实时通知系统

Pub/Sub 最适合的场景是"fire-and-forget"式的实时广播 ——消息发出去就不管了，没接到就丢了，这种语义对于通知、聊天、实时比分更新等场景恰到好处。

```
# 订单状态变更通知
PUBLISH order:updates "order-12345:shipped"

# 客户端订阅
SUBSCRIBE order:updates
# 收到: message order:updates "order-12345:shipped"
```

**工业实践要点**：

- 订阅客户端必须是**常驻长连接**，短暂连接会错过消息
- 生产环境通常使用独立的 Redis 连接池专门服务于 Pub/Sub，不与常规命令混用
- 如果需要"消息持久化、离线可重放"，**不要用 Pub/Sub，改用 Redis Streams**​

## 18.2 模式的订阅与退订

**核心命令**：`PSUBSCRIBE pattern [pattern ...]` / `PUNSUBSCRIBE [pattern ...]`

模式订阅使用 glob 风格的通配符：

- `*` 匹配任意字符序列
- `?` 匹配单个字符
- `[abc]` 匹配括号内任一字符

例如 `PSUBSCRIBE news.*` 可以匹配 `news.art.figurative`、`news.music.jazz` 等所有以 `news.` 开头的频道 。

**模式订阅收到的消息格式不同于精确订阅**：

```
*4              ← 4个元素
$8              ← 长度8
pmessage        ← 消息类型: pmessage
$5              ← 匹配的模式长度
news.*          ← 原始模式
$9              ← 实际频道长度
news.sports     ← 实际频道名
$5              ← 消息体长度
Hello           ← 消息内容
```

注意 pmessage 比 message **多了一个字段**——匹配的模式。这是因为同一个消息可能匹配客户端的多个模式，客户端需要知道是哪个模式匹配上的。

**一个客户端可能收到多次同一条消息**：

```
SUBSCRIBE foo
PSUBSCRIBE f*
# 此时向 foo 发布消息，客户端会收到两条:
#   一条 message 类型 (来自精确订阅)
#   一条 pmessage 类型 (来自模式订阅)
```

这是 Redis Pub/Sub 的**有意设计**——它不做去重。原因是去重需要服务端维护"每个客户端对每个消息的接收状态"，这会破坏 Pub/Sub 的无状态、fire-and-forget 本性。书里也明确提到了这一点 。

> 💡 **洞见：模式订阅的本质是"动态的频道集合"**
> 
> 精确订阅是"订阅一个具体频道"，模式订阅是"订阅一个频道集合"——这个集合是**动态的**：即使现在还没有 `news.sports` 这个频道，订阅 `news.*` 的客户端未来也能自动收到发往 `news.sports` 的消息。
> 
> 这在工业上有巨大价值——**发布者可以自由地创建新的频道**（如 `user:{uid}:notifications`），而无需事先通知订阅者。订阅者只需用一个模式就能覆盖未来所有可能的频道：
> 
> ```
> PSUBSCRIBE user:*:notifications    # 接收所有用户的通知
> PSUBSCRIBE cache:invalidate:*      # 接收所有缓存失效事件
> ```

**底层实现**：每个客户端除了 `pubsub_channels` 字典，还有一个 `pubsub_patterns` 链表。PUBLISH 命令执行时，除了向精确订阅者推送，还会遍历所有客户端的 `pubsub_patterns` 链表，匹配模式后推送 。

> ⚠️ **工业警示**：模式订阅虽强大，但要警惕**模式过于宽泛**导致某个客户端收到海量消息。例如 `PSUBSCRIBE *` 会订阅所有频道，在生产环境是灾难性的——一个高吞吐的频道会把该客户端撑爆。

## 18.3 发送消息

**核心命令**：`PUBLISH channel message`

**复杂度**：O(N + M)，其中 N 是频道精确订阅者数量，M 是所有客户端订阅的模式总数 。

**返回值**：收到消息的订阅者数量。

**PUBLISH 的执行流程**：

```
① 查频道精确订阅者链表 → 逐个推送
② 遍历所有客户端的 pubsub_patterns → 匹配模式 → 逐个推送
③ 返回推送成功的总人数
```

**关键特性：消息不持久化**：

> 📌 Redis Pub/Sub 是纯粹的 fire-and-forget ——
> 
> - 消息不会被写入任何存储
> - 如果没有订阅者在线，消息**彻底丢失**
> - 订阅者断开连接期间错过的消息**无法补收**
> - 没有 ACK 机制，发布者不知道订阅者是否真的处理了消息

这是 Pub/Sub 与消息队列（如 Kafka、RabbitMQ）的根本区别。Kafka 把消息持久化到磁盘，允许消费者从任意 offset 重放；Redis Pub/Sub 则是"过了这个村就没这个店"。

**Pub/Sub 与键空间完全独立**：

Redis 官方文档明确指出——**Pub/Sub 与键空间没有任何关系，它故意不和键空间产生任何交互，包括数据库编号**​ 。也就是说，`PUBLISH` 在 db 10 上发布消息，db 1 上的订阅者也能收到。这是为了保持 Pub/Sub 的纯粹性——它是一个**独立的消息总线**，不依附于任何数据存储逻辑。

> 💡 **第一性原理洞见：为什么 Pub/Sub 不持久化？**
> 
> 这要从 Redis 的定位说起。Redis 是**内存数据库**，设计目标是**低延迟、高吞吐**。如果 Pub/Sub 要持久化消息，就必须：
> 
> - 写磁盘（破坏内存速度优势）
> - 维护每个订阅者的消费位点（引入大量状态）
> - 处理消息堆积、背压、重放（变成消息队列）
> 
> 这些都不是 Redis 想要的复杂度。因此 Redis 的选择是——**把"实时广播"和"可靠消息队列"分成两个独立的功能**：Pub/Sub 做前者（快、简单、不持久化），Streams 做后者（持久化、可重放、有消费者组）。
> 
> 这是"单一职责原则"在 Redis 功能设计上的体现——**一个功能只解决一类问题，做到极致，而不是试图做一个大而全的"消息中间件"**。

## 18.4 查看订阅信息

**核心命令**：`PUBSUB CHANNELS [pattern]` / `PUBSUB NUMSUB [channel ...]` / `PUBSUB NUMPAT`

|命令|作用|复杂度|
|---|---|---|
|`PUBSUB CHANNELS [pattern]`|列出当前活跃的频道（有订阅者的频道）|O(N)|
|`PUBSUB NUMSUB channel [channel ...]`|查询指定频道的订阅者数量|O(N)|
|`PUBSUB NUMPAT`|查询全局模式订阅的总数|O(1)|

**活跃频道的定义**：至少有一個订阅者的频道。`PUBSUB CHANNELS` 返回的就是这些频道，可选 pattern 参数做过滤 。

**工业监控用法**：

```
# 监控热点频道
PUBSUB CHANNELS cache:invalidate:*

# 监控订阅者规模
PUBSUB NUMSUB order:updates user:1001:notifications

# 监控模式订阅规模
PUBSUB NUMPAT
```

> 💡 **洞见： introspection 命令的存在，反映了 Redis "可观测性优先" 的工程文化**
> 
> Redis 几乎所有功能都配套了 introspection 命令——INFO、PUBSUB、CLUSTER NODES、SLOWLOG 等等。这体现了 Redis 的设计理念：**不仅要功能能用，还要让运维能看清功能的运行状态**。Pub/Sub 作为一个"消息黑洞"（消息发完即焚），如果没有 introspection 命令，运维将完全无法知道"现在有多少客户端在听"、"哪些频道是热的"——这是不可接受的。因此 `PUBSUB` 子命令的提供，是 Pub/Sub 能用于生产环境的必要条件。

## 18.5 重点回顾

1. **SUBSCRIBE 将连接切入订阅模式**，订阅模式下只能执行 SUBSCRIBE/UNSUBSCRIBE/PSUBSCRIBE/PUNSUBSCRIBE/PING/QUIT 六个命令
2. **订阅/退订的确认本身就是一种消息**，客户端在统一的流上读取所有消息类型
3. **PSUBSCRIBE 使用 glob 模式**，`*`、`?`、`[]` 通配符均支持
4. **精确订阅和模式订阅可能重复接收同一条消息**，服务端不去重
5. **PUBLISH 复杂度 O(N+M)**，N 是精确订阅者数，M 是模式订阅总数
6. **Pub/Sub 与键空间完全独立**，不持久化，fire-and-forget
7. **Pub/Sub 适合实时广播，不适合可靠消息队列**；需要持久化和重放请用 Streams
8. **Redis 7.0+ 引入 Sharded Pub/Sub**，通过 `SSUBSCRIBE`/`SPUBLISH` 在 Cluster 环境下降低带宽

# 第19章 事务

## 19.1 事务的实现

**核心命令**：`MULTI` → `...` (命令入队) → `EXEC` / `DISCARD`

**事务的三个阶段**：

```
① 开启: MULTI
   ↓
② 命令入队: SET k v / INCR counter / HSET ...
   ↓ (注意: 命令不执行，只返回 QUEUED)
③ 执行: EXEC (原子执行所有入队命令) 或 DISCARD (放弃)
```

**底层实现机制**：

Redis 服务器为每个客户端维护一个事务状态 `client.mstate`，其中包含一个命令队列 。当客户端处于 `CLIENT_MULTI` 状态时：

1. 所有常规命令**不立即执行**，而是经过语法和 ACL 校验后放入 `client.mstate.commands` 队列
2. 服务器对每个入队的命令回复 `+QUEUED`
3. 如果入队命令有语法错误（未知命令、参数个数错误等），事务被标记为 `CLIENT_DIRTY_EXEC`，后续 EXEC 会直接失败（返回 EXECABORT）
4. 收到 EXEC 时，服务器**在单线程内按顺序**执行队列中的所有命令，期间不被其他客户端打断
5. 执行完毕后，清空队列，客户端退出事务状态

**原子性的真正来源**：

Redis 事务的原子性**不是**靠"回滚机制"实现的（实际上 Redis 根本没有回滚），而是靠**单线程执行窗口**——EXEC 开始执行到执行结束的这段时间内，Redis 事件循环不会切换去处理其他客户端的命令 。

> ⚠️ **关键事实：Redis 事务不支持回滚**
> 
> 这是 Redis 事务与 MySQL 等传统数据库事务最根本的区别。如果在 EXEC 执行过程中，某条命令出现**运行期错误**（如对字符串执行 INCR），**错误会被包含在返回数组中，后续命令继续执行**​ 。
> 
> ```
> MULTI
> SET foo "bar"        → QUEUED
> INCR foo             → QUEUED  (运行时会报错: foo 是字符串)
> SET baz "qux"        → QUEUED
> EXEC
> → [OK, (error), OK]  ← 第一条和第三条都执行成功了！
> ```
> 
> Redis 官方解释：不支持回滚是为了保持 Redis 的**简单性和高性能**​ 。如果加入回滚机制，不仅需要记录 undo log，还要在命令执行失败时回溯状态——这会显著增加实现复杂度和性能开销。

**Redis 事务原子性的两个层次**：

|层次|保证|说明|
|---|---|---|
|语法层原子性|✅ 强保证|如果入队时有语法错误，EXEC 直接拒绝执行整个事务|
|执行层原子性|⚠️ 弱保证|运行期错误不会中止事务，已执行的命令不回滚|

**EXEC 执行期间的无敌时间**：

由于 Redis 是单线程的，EXEC 执行队列命令的过程中，其他客户端的所有命令都必须等待。这意味着：

> 📌 **事务执行期间，Redis 实际上是"停摆"的**——其他所有客户端都被阻塞，直到 EXEC 完成。

这就是为什么 Redis 官方和工业实践都强调——**事务要短小精悍，命令数量要少**。一个包含 10000 条命令的事务会让整个 Redis 实例卡住数秒甚至更久。

> 💡 **洞见：Redis 事务的本质是"命令批处理 + 执行窗口锁定"**
> 
> 很多人误以为 Redis 事务和数据库事务是同类东西，其实不然。Redis 事务**没有 BEGIN/COMMIT 的语义，没有回滚，没有隔离级别，没有 undo log**。它做的事情非常简单：
> 
> - **MULTI**：开启一个"命令收集器"
> - **入队**：把命令存起来，不执行
> - **EXEC**：一次性、不间断地执行所有收集的命令
> 
> 这种设计的本质是**"网络往返优化 + 执行原子性"**：
> 
> - 网络往返优化：原本 N 条命令需要 N 次 RTT，事务只需 2 次 RTT（MULTI+命令入队可流水线化，EXEC 一次性触发）
> - 执行原子性：EXEC 执行期间不被打断，保证了"这组命令要么都执行，要么都不执行（在语法正确前提下）"
> 
> **但它不是数据库意义上的事务**——它不提供回滚、不提供隔离级别、不跨数据库。理解了这一点，才能真正用好 Redis 事务。

### 工业应用：库存扣减

```
WATCH inventory:item:1001
val = GET inventory:item:1001
if val <= 0:
    UNWATCH
    return "out of stock"

MULTI
DECR inventory:item:1001
EXEC
# 如果返回 nil，说明库存被其他客户端改了，重试
```

## 19.2 WATCH 命令的实现

**核心命令**：`WATCH key [key ...]` / `UNWATCH`

**WATCH 解决的问题**：MULTI/EXEC 本身不处理并发——如果客户端 A 和 B 同时读取了某个 key 的旧值并基于旧值构造事务，EXEC 时会产生竞态条件 。

**WATCH 的乐观锁机制**：

```
WATCH mykey
val = GET mykey
val = val + 1
MULTI
SET mykey $val
EXEC
# 如果 WATCH 和 EXEC 之间 mykey 被其他客户端修改
# EXEC 返回 nil，事务中止，客户端需重试
```

**底层实现**：

1. `WATCH key` 将 key 注册到 `client.watched_keys` 链表，同时也加入到 `db->watched_keys` 字典（key → 监听该 key 的客户端列表）
2. 任何**修改性命令**（如 SET/DEL/INCR）执行时，都会调用 `signalModifiedKey(c, db, key)`
3. `signalModifiedKey` 遍历 `db->watched_keys[key]`，对所有监听该 key 的客户端设置 `CLIENT_DIRTY_CAS` 标志
4. `EXEC` 执行时，检查客户端是否有 `CLIENT_DIRTY_CAS` 标志——如果有，事务中止，返回 nil reply
5. `EXEC`/`DISCARD`/`UNWATCH`/客户端断开连接 都会自动清除 WATCH 状态

**WATCH 的语义细节**（官方文档明确说明）：

- WATCH 的键被**任何客户端修改**都会触发中止，包括 WATCH 自己的客户端
- 事务队列中的命令**不会**触发 WATCH 条件（因为它们只是入队，还未执行）
- 键过期也算"修改"——但在 Redis 6.0.9 之前，过期不会触发事务中止（这是个 bug，已修复）
- 6.0.9 之前，过期键不会导致事务中止；6.0.9 及以后，过期也会触发 WATCH 中止

**乐观锁 vs 悲观锁**：

|维度|乐观锁 (WATCH)|悲观锁 (SETNX)|
|---|---|---|
|核心思想|假设冲突很少，提交时检查|假设冲突很多，操作前先加锁|
|实现方式|WATCH + MULTI/EXEC + 重试|SETNX + EXPIRE 分布式锁|
|冲突处理|事务中止，客户端重试|获取锁失败，等待或放弃|
|性能|无锁，高并发友好|有锁开销，可能死锁|
|适用场景|冲突率低（如计数器递增）|冲突率高（如秒杀抢购）|

> 💡 **洞见：WATCH 是"CAS（Compare-And-Swap）"在 Redis 中的实现**
> 
> WATCH 提供的就是分布式系统经典的 CAS 语义——"比较并交换"。它让 Redis 事务具备了**条件执行**的能力：只有当被 WATCH 的键没有被修改时，事务才执行。
> 
> 这是 Redis 在"单线程 + 无锁"哲学下的精妙设计：
> 
> - **不加锁**：避免了死锁、锁竞争、锁超时等复杂性
> - **不阻塞**：WATCH 本身不阻塞任何其他操作
> - **可重试**：事务中止后客户端只需重新 WATCH + 重读 + 重执行
> - **代价**：高冲突场景下，大量事务会中止并重试，造成"活锁"效应
> 
> 这正是乐观锁的经典权衡——**在低冲突场景下性能极佳，在高冲突场景下反而不如悲观锁**。
> 
> Redis 8.4+ 进一步优化：提供了 `SET` 命令的 `IFEQUAL`/`IFNOTEQUAL` 等选项，以及 `DELEX` 命令，可以用**单条命令**完成 CAS 操作，比 WATCH + MULTI + EXEC 更简单更快 。这说明 Redis 在持续演进——WATCH 是通用方案，而新的 CAS 命令是针对 string 键的特定优化。

### 工业应用：余额转账

```
WATCH account:A account:B
balance_A = GET account:A
balance_B = GET account:B

if balance_A < transfer_amount:
    UNWATCH
    return "insufficient funds"

MULTI
DECRBY account:A transfer_amount
INCRBY account:B transfer_amount
EXEC
# 返回 nil 则重试
```

## 19.3 事务的 ACID 性质

这是 Redis 事务最容易被误解的部分。我们逐一分析：

### Atomicity（原子性）—— ⚠️ 部分保证

- **语法层**：如果入队命令有语法错误，EXEC 拒绝执行整个事务 → **强原子性**
- **执行层**：运行期错误不会中止事务，已执行的命令不回滚 → **弱原子性**

Redis 官方明确表态：**不支持回滚，因为回滚会显著影响 Redis 的简洁性和性能**​ 。

**结论**：Redis 事务的原子性是"残血的"——它保证"要么全执行，要么全不执行（语法正确时）"，但不保证"执行出错时回到事务前状态"。

### Consistency（一致性）—— ✅ 保证

Redis 单线程执行模型天然保证了事务执行期间没有其他命令穿插，因此不会出现"部分更新导致数据不一致"的情况。但要注意——如果事务中某条命令运行失败（如对字符串 INCR），数据会停留在"部分修改"的状态，这需要业务层处理。

### Isolation（隔离性）—— ✅ 保证

单线程执行窗口保证了 EXEC 执行期间，其他客户端命令完全不会执行 。从这个意义上，Redis 事务具有完全的隔离性——比其他数据库的"可串行化"隔离级别还要严格。

### Durability（持久性）—— ⚠️ 依赖配置

- **纯内存模式**：不持久化，Redis 重启后事务结果丢失
- **RDB 模式**：只有 RDB 快照时点之后的事务结果可能丢失
- **AOF 模式 + appendfsync always**：每次写都 fsync，**此时事务具有强持久性**​
- **AOF 模式 + appendfsync everysec**：最多丢失 1 秒的事务结果

> 📌 **综合评估**：Redis 事务**不完全满足 ACID**。它具备隔离性和一致性，但原子性是"残血版"（无回滚），持久性依赖配置。这与传统关系型数据库的事务有本质区别。

**为什么 Redis 选择这样做？**

Redis 官方文档的解释一针见血——**支持回滚会显著影响 Redis 的简洁性和性能**​ 。Redis 的设计哲学是：

1. **性能优先**：单线程 + 内存操作，追求极致速度
2. **简洁优先**：不支持回滚、undo log、隔离级别等复杂机制
3. **实用优先**：大部分 Redis 使用场景是"缓存 + 简单数据结构操作"，不需要完整的 ACID

> 💡 **洞见：Redis 事务的"不完整性"是其优势，而非缺陷**
> 
> 很多人批评 Redis 事务"不是真正的事务"。但从第一性原理看，这是 Redis 的**主动取舍**：
> 
> - 如果 Redis 要实现完整 ACID，就必须引入 undo log、回滚机制、隔离级别判断等——这将使 Redis 变成一个"内存版的关系型数据库"，丧失其"简单、快速"的核心竞争力
> - Redis 的选择是：提供**够用的原子性**（命令批处理 + 执行窗口锁定）+ **可选的持久性**（AOF always）+ **乐观并发控制**（WATCH），让用户在"性能"和"一致性"之间自己权衡
> - 对于需要强 ACID 的场景，Redis 官方推荐**使用 Lua 脚本**——EVAL 脚本在服务端原子执行，且支持复杂逻辑（条件、循环），比 MULTI/EXEC 更强大

### 事务 vs Lua 脚本

|维度|MULTI/EXEC 事务|Lua 脚本 (EVAL)|
|---|---|---|
|原子性|命令队列 + 执行窗口锁定|脚本整体原子执行|
|逻辑复杂度|仅支持简单命令队列|支持条件、循环、复杂逻辑|
|错误处理|运行错误不中止，无回滚|脚本出错即停止，所有操作无效|
|网络开销|2 次 RTT（MULTI + EXEC）|1 次 RTT|
|集群限制|所有 key 必须同槽|所有 key 必须同槽|

> 📌 **工业建议**：对于**复杂业务逻辑**，优先使用 Lua 脚本而非 MULTI/EXEC。Lua 脚本在 Redis 服务端原子执行，且支持完整的编程逻辑，是 Redis 中实现"分布式原子操作"的最佳实践。

> ⚠️ **集群环境限制**：在 Redis Cluster 中，事务（和 Lua 脚本）的**所有 key 必须位于同一个哈希槽**​ ，否则返回 CROSSSLOT 错误。这是 Redis Cluster 数据分片模型的硬约束。

## 19.4 重点回顾

1. **事务三阶段**：MULTI 开启 → 命令入队（返回 QUEUED）→ EXEC 原子执行或 DISCARD 放弃
2. **原子性来自单线程执行窗口**：EXEC 执行期间，其他客户端命令完全阻塞
3. **Redis 事务不支持回滚**：运行期错误不会中止事务，已执行命令不回滚
4. **WATCH 实现乐观锁（CAS）**：被 WATCH 的键在 EXEC 前被修改，事务中止返回 nil
5. **WATCH 底层机制**：`signalModifiedKey` 在键被修改时标记监听客户端为 `CLIENT_DIRTY_CAS`
6. **ACID 评估**：具备隔离性和一致性；原子性为"残血版"；持久性依赖 AOF 配置
7. **集群限制**：事务所有 key 必须同槽，否则 CROSSSLOT 错误
8. **Lua 脚本优于事务**：复杂逻辑优先用 EVAL，原子执行且支持编程逻辑
9. **Redis 8.4+ 新 CAS 命令**：`SET ... IFEQ/IFNE` 和 `DELEX` 提供单命令 CAS

## 第18~19章的深层洞见：Redis 的"最小原语"哲学

把这两章放在一起看，一个贯穿始终的设计哲学浮现出来——**Redis 倾向于用"最小的原语"扩展出"最大的表达能力"**。

### Pub/Sub 的最小原语：频道

只用"频道"这一个概念，就实现了：

- 点对点消息（一个发布者，一个订阅者）
- 广播（一个发布者，多个订阅者）
- 模式匹配（glob 通配符）
- 动态频道发现（订阅者无需预知频道存在）

**代价**：不持久化、不可靠、无 ACK。但 Redis 用 Streams 补足了"可靠消息队列"的场景，保持了 Pub/Sub 的纯粹。

### 事务的最小原语：命令队列 + WATCH

只用"命令队列" + "执行窗口锁定" + "WATCH 乐观锁"这三个原语，就实现了：

- 原子批处理（MULTI/EXEC）
- 乐观并发控制（WATCH）
- Check-And-Set 语义

**代价**：无回滚、不完整 ACID、集群环境 key 必须同槽。但 Redis 用 Lua 脚本补足了复杂原子操作的场景。

### 这种哲学的深层逻辑

Redis 的创始人 antirez 在设计 Redis 时，始终秉持一个信念——**"简单的数据结构 + 巧妙的组合 = 强大的功能"**。

- String、List、Hash、Set、ZSet —— 5 种基础数据结构
- 在这 5 种结构上叠加：过期、持久化、复制、Pub/Sub、事务、Cluster
- 每一种新功能都尽量**复用已有机制**，而非引入全新的复杂度

Pub/Sub 复用了 Redis 的事件循环和客户端连接模型；事务复用了单线程执行窗口和命令队列。这种"**最小原语 + 巧妙组合**"的设计，使得 Redis 在保持核心简洁的同时，能够不断向外扩展出新功能。

> 💡 **创新洞见：为什么这种"最小原语"哲学在工业实践中如此成功？**
> 
> 1. **可预测的性能**：因为每个功能都建立在相同的底层机制上，性能特征可预测
> 2. **可组合的抽象**：Pub/Sub + 事务 + 数据结构可以组合出无穷的用法
> 3. **可演进的架构**：新增功能不需要推翻原有设计，只需在已有原语上叠加
> 4. **可理解的源码**：Redis 源码之所以被称为"艺术品"，正是因为这种简洁性
> 
> 对比那些试图"一开始就设计完备"的系统（如支持完整 ACID 的 NewSQL 数据库），Redis 选择了"渐进式演进"——先用最小原语解决 80% 的问题，剩下的 20% 用新原语（如 Lua 脚本、Streams、Redis 8.4 的 CAS 命令）逐步补足。这种"实用主义演进"路径，正是 Redis 能够在工业界获得巨大成功的核心原因。

### 工业落地的核心建议

**Pub/Sub 的使用准则**：

1. ✅ 适合：实时通知、聊天室、直播弹幕、股票价格推送、缓存失效广播
2. ❌ 不适合：可靠消息队列、任务分发、事件溯源
3. ⚠️ 注意：订阅客户端必须是长连接；生产环境用独立连接池
4. 💡 替代：需要持久化和消费者组时，使用 Redis Streams

**事务的使用准则**：

1. ✅ 适合：简单原子操作（计数器、库存扣减）、配合 WATCH 实现 CAS
2. ❌ 不适合：复杂业务逻辑、跨 Slot 操作、需要回滚的场景
3. ⚠️ 注意：事务要短小精悍（命令数 < 100），避免阻塞整个实例
4. 💡 替代：复杂逻辑用 Lua 脚本；分布式锁用 Redlock 或 Redisson

**Redis 8.4+ 的新选择**：

对于 string 键的 CAS 操作，直接使用新命令：

```
SET mykey $newval IFEQ $oldval    # 仅当 mykey 当前值等于 oldval 时才设置
DELEX mykey IFEQ $oldval          # 仅当 mykey 当前值等于 oldval 时才删除
```

这比 WATCH + MULTI + EXEC 更简单、更快 。
