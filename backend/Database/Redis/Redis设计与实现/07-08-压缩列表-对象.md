## 第7章 压缩列表（ziplist）

### 7.1 压缩列表的构成

ziplist 是 Redis 为了**节省内存**而设计的**连续内存紧凑列表**——它用一块完整的内存存储所有元素，元素之间通过记录长度来"隐式寻址"，没有任何指针开销。

整体布局：

```
+---------+---------+--------+--------+--------+------+-------+
| zlbytes | zltail  | zllen  | entry1 | entry2 | ...  | zlend |
+---------+---------+--------+--------+--------+------+-------+
  4B        4B        2B     变长      变长           1B
```

- **zlbytes**：整个 ziplist 的总字节数
- **zltail**：尾节点距离起始地址的偏移量（用于 O(1) 定位尾部）
- **zllen**：节点个数（最多记录 65535，超过需要遍历）
- **entry**：实际节点
- **zlend**：固定 0xFF，标记结尾

> 💡 **第一性原理视角**：ziplist 的本质是**用"计算"换"内存"**——传统链表每个节点要存 `prev/next` 两个指针（64 位下 16 字节），而 ziplist 通过"记录长度 + 偏移计算"来模拟双向链表，**彻底消灭了指针开销**。这是嵌入式系统和内存数据库的经典套路：内存紧张时，宁可多用 CPU 做地址运算，也要把每一个字节榨干。

但这种设计的**阿喀琉斯之踵**就在"记录长度"这四个字上——为了反向遍历，每个 entry 都要记录"前一个 entry 有多长"（即 `prevlen` 字段），而这个字段的宽度取决于前一项的实际长度……这正是 7.3 节"连锁更新"的根源。

### 7.2 压缩列表节点的构成

每个 entry 的结构：

```
+--------+--------+--------+
| prevlen| encoding| data  |
+--------+--------+--------+
  变长     变长    变长
```

**prevlen 字段**（关键！）：

- 如果前一个 entry 长度 **< 254 字节**：prevlen 占 **1 字节**
- 如果前一个 entry 长度 **≥ 254 字节**：prevlen 占 **5 字节**（0xFE + 4 字节长度）

**encoding 字段**：标识 data 的类型与长度，支持整数和字符串两种：

- 字符串：根据长度分 1/2/5 字节三种编码
- 整数：支持 int16/int32/int64/24bit/8bit 等多种编码

**data 字段**：实际数据。

> 📌 注意一个细节：ziplist 的 entry **既能存字符串也能存整数**，且整数会以"整数"形式原生存储，不做字符串转换。这让 ziplist 在存储小整数时极其节省内存。

**为什么叫"压缩"列表？**​ 因为它不是对数据进行压缩算法处理，而是通过**紧凑的变长编码 + 消除指针开销**来实现"压缩效果"。这个名字容易让人误解，但理解了它的内存布局后就清楚了。

### 7.3 连锁更新

这是 ziplist **最致命的设计缺陷**，也是 Redis 7.0 决心用 listpack 取代它的根本原因。

**触发场景**（经典例子）：

假设 ziplist 中有 N 个 entry，每个长度都是 253 字节（prevlen 占 1 字节）。现在在头部插入一个 254 字节的新 entry，会发生什么？

```
插入前（所有 prevlen 都是 1 字节）：
[新254B] [253B] [253B] [253B] ... [253B]

插入后第一个 253B entry 的 prevlen 需要 5 字节
→ 第一个 253B entry 膨胀为 257B（253+4）
→ 第二个 253B entry 的 prevlen 也变为 5 字节
→ 第二个 253B entry 膨胀为 257B
→ 第三个... → 连锁反应，所有后续 entry 都要更新！
```

**最坏情况时间复杂度：O(N²)**——插入一个节点，可能导致后续所有节点都要重写 。

更严重的是，这个问题不仅出现在插入，也出现在删除——删除一个节点可能导致后续节点的 prevlen 从 5 字节收缩到 1 字节，同样引发连锁的内存重分配。

> ⚠️ 历史上 ziplist 的 prevlen 解析错误还引发过内存越界漏洞（如 CVE-2018-11213），这是 ziplist 设计缺陷带来的**安全性代价**​ 。

### 7.4 压缩列表 API

ziplist 的核心操作（均在 `ziplist.c`）：

**创建与销毁**

- `ziplistNew()`：创建空 ziplist
- `ziplistFree(zl)`：释放

**增删改查**

- `ziplistPush(zl, s, slen, where)`：头插或尾插
- `ziplistIndex(zl, index)`：按索引定位（O(N) 遍历）
- `ziplistNext(zl, p)` / `ziplistPrev(zl, p)`：前后移动指针
- `ziplistInsert(zl, p, s, slen)`：在指定位置插入
- `ziplistDelete(zl, &p)`：删除指定节点
- `ziplistFind(zl, p, s, slen, skip)`：查找（用于 Hash/Set 的成员查找）

### 7.5 重点回顾与 listpack 的登场

ziplist 的五点核心：

1. **连续内存、变长编码、无指针开销**——极致节省内存
2. **prevlen + encoding + data**​ 三段式节点结构
3. **prevlen 的 1/5 字节二态设计**埋下了连锁更新的隐患
4. **连锁更新最坏 O(N²)**，且在并发写入时会导致性能剧烈抖动
5. **Redis 7.0 起 ziplist 退役**，被 listpack 全面取代

**listpack：工业界的答案**

listpack 的核心改造只有一个——**去掉 prevlen，改为在每个 entry 的尾部存储"当前 entry 自身的总长度"（`element-tot-len`）**​ ：

```
listpack entry:
+----------+----------+-------------------+
| encoding | data     | element-tot-len   |
+----------+----------+-------------------+
  变长      变长         变长（1~5字节）
```

**为什么这样就消除了连锁更新？**​ 因为插入新节点时，**后续节点的长度信息描述的是"自己"，不依赖于前一个节点**。新节点插入后，后续节点不需要修改自己的 `element-tot-len`，自然就不会触发级联重写 。

**向前遍历怎么办？**​ 读者从当前 entry 尾部的 `element-tot-len` 读出本 entry 总长度，然后"向前跳"这个长度，就到了上一个 entry 的尾部，再读它的 `element-tot-len` 继续向前。虽然比 ziplist 的 prevlen 多了一步"读取上一个节点尾部"，但换来了**彻底消灭连锁更新的安全性**​ 。

**listpack 与 ziplist 的关键差异**：

|维度|ziplist|listpack|
|---|---|---|
|前向依赖|依赖 prevlen（前驱长度）|自包含（自身长度）|
|连锁更新|存在，最坏 O(N²)|**完全不存在**​|
|内存占用|较低（但有 prevlen 冗余）|与 ziplist 接近，甚至更优|
|安全性|曾有内存越界漏洞|长度自包含，更安全|
|并发适应性|差（任意修改可能影响相邻字节）|好（每个元素独立边界）|

> 💡 **第一性原理洞见**：ziplist 的失败给了我们一个深刻教训——**"局部性"和"独立性"是互斥的**。ziplist 追求极致的局部性（连续内存、零指针），就必须让每个节点携带"关于邻居的信息"（prevlen），而这恰恰破坏了节点的独立性，导致一处修改波及全身。
> 
> listpack 的设计哲学是：**宁可牺牲一点点局部性（多了一步"向前跳"的操作），也要保全每个节点的独立性**。这是一个典型的"解耦"思想——把"我是谁"和"我前驱是谁"这两件事拆开，让每个 entry 只对自己负责。这种"自描述"的设计在计算机系统里无处不在：TCP 报文段的头部长度字段、UTF-8 编码的前缀位、Protobuf 的 varint……都是同一个思路。
> 
> 更深层的启示：**当你发现一个数据结构在"理论上很优"但"实践中总是出 bug 或性能抖动"时，往往不是实现问题，而是模型问题**。ziplist 的 prevlen 设计在纸面上没问题，但在真实工作负载下，连锁更新的长尾延迟是致命的。Redis 团队选择"推倒重来"而不是"修补"，这是工程成熟的标志。

## 第8章 对象

### 8.1 对象的类型与编码

Redis 在底层数据结构（SDS、adlist、dict、skiplist、intset、ziplist/listpack）之上，抽象出了**对象系统**。每个对象用 `redisObject` 结构表示：

```
typedef struct redisObject {
    unsigned type:4;        // 类型：String/List/Hash/Set/ZSet
    unsigned encoding:4;    // 编码：raw/int/embstr/linkedlist/ziplist/hashtable/skiplist/intset/quicklist/listpack
    unsigned lru:LRU_BITS; // LRU 时钟或 LFU 计数
    int refcount;           // 引用计数
    void *ptr;              // 指向底层数据结构的指针
} robj;
```

**这是 Redis 架构最精妙的一层抽象**：`type` 是用户视角的类型（5 种），`encoding` 是内部实现（随版本演进，目前有 11 种以上）。**同一种 type 可以对应多种 encoding**——这就是 Redis 的"编码多态" 。

官方文档明确列出了各类型的编码 ：

- **Strings**：`int`、`embstr`、`raw`
- **Lists**：`quicklist`（Redis 7.0+ 中 quicklist 节点为 `listpack`）
- **Hashes**：`listpack`（Redis 7.0+，原为 `ziplist`）、`hashtable`
- **Sets**：`intset`、`hashtable`、`listpack`（Redis 7.2+）
- **Sorted Sets**：`listpack`（Redis 7.0+，原为 `ziplist`）、`skiplist`

> 📌 **第一性原理视角**：对象系统的本质是**"策略模式" + "自动降级/升级"**。Redis 在用户无感知的情况下，根据数据特征（类型、大小、数量）动态选择最合适的底层结构。小数据用紧凑编码省内存，大数据用通用结构保性能——这是**用空间换时间、用时间换空间的动态平衡**。

这种设计带来三大好处：

1. **对用户透明**：用户只看到 "String/List/Hash/Set/ZSet" 五种类型，不用关心底层
2. **对内存友好**：小数据极致压缩
3. **对性能友好**：大数据自动切换到 O(1) 或 O(log N) 结构

### 8.2 字符串对象

String 是 Redis 最基础的类型，但底层有**三种编码**：

**① int 编码**

- 条件：值能表示为 64 位有符号整数
- 存储：整数直接存在 `ptr` 指针位置（不是指向，就是它本身），**零额外内存分配**
- 示例：`SET counter 12345`

**② embstr 编码**

- 条件：字符串长度 ≤ **44 字节**
- 存储：`redisObject` 和 SDS **一块连续内存**分配，共 64 字节（jemalloc 的分配单元）
- 优势：一次分配、缓存友好、减少内存碎片
- 示例：`SET name "John Doe"`

**③ raw 编码**

- 条件：字符串长度 > 44 字节
- 存储：`redisObject` 和 SDS **两块分离的内存**
- 示例：`SET essay "长文本..."`

**44 字节阈值的由来**：64 字节（jemalloc 最小分配单元）- 16 字节（redisObject）- 3 字节（SDS header）- 1 字节（结尾 \0）= 44 字节 。

**编码转换规则**：

- `int` → `raw`：对整数值执行 APPEND 等字符串操作后，不可逆转为 int
- `embstr` → `raw`：embstr 是**只读的**，任何修改操作都会升级为 raw，且**不可逆**​

> 💡 **洞见**：embstr 的"只读性"是个反直觉但极其聪明的设计。embstr 的价值在于"一次性分配连续内存"，但连续内存的缺点是**修改时要整体重分配**。所以 Redis 规定 embstr 只能读，一旦要写就升级为 raw——把"短字符串的高频读"和"长字符串的频繁写"清晰地分开了。这是用"不可变性"换取"分配效率"的经典权衡，和 Java 的字符串不可变、Go 的字符串不可变是同一个思路。

### 8.3 列表对象

List 的底层演化是 Redis 历史上变动最频繁的：

**Redis < 3.2**：`ziplist`（小数据）↔ `linkedlist`（大数据）双实现切换

**Redis 3.2 ~ 6.x**：统一为 `quicklist`（ziplist 的双向链表）

**Redis 7.0+**：`quicklist` 节点从 ziplist 换成 `listpack`

**quicklist 结构**：

```
head ↔ [listpack] ↔ [listpack] ↔ [listpack] ↔ tail
        8KB以内      8KB以内      8KB以内
```

- 每个 quicklist 节点是一个 listpack（默认上限 8KB，由 `list-max-listpack-size` 控制）
- 头尾操作 O(1)，中间插入 O(N)
- 兼顾了"链表的灵活性"和"紧凑结构的内存效率"

> 📌 **工业视角**：List 是 Redis 实现**消息队列**的核心结构。`LPUSH` + `BRPOP` 是典型的任务队列模式。但要注意：**如果单个 list 元素过多（百万级），即使 quicklist 也会让 `LINDEX`/`LINSERT` 等按索引操作变慢**，因为要遍历定位。生产环境建议用 `LTRIM` 限制队列长度，或直接使用 Stream 类型。

### 8.4 哈希对象

Hash 的编码：

**① listpack 编码**（Redis 7.0+，原为 ziplist）

- 条件：元素数 < `hash-max-listpack-entries`（默认 128）**且**​ 每个 entry < `hash-max-listpack-value`（默认 64 字节）
- 存储：field 和 value 交替存储在 listpack 中
- 查找：O(N) 遍历

**② hashtable 编码**

- 触发：超过上述任一阈值，不可逆转换
- 查找：O(1)

**典型场景**：Hash 是存储"对象"的最佳结构——比如用户信息：`HSET user:1000 name "Alice" age 30 email "alice@example.com"`。

> ⚠️ **工业经验**：Hash 的编码升级是不可逆的。一旦某个 Hash 因为某个 field 的 value 超过 64 字节而从 listpack 升级到 hashtable，即使后来把这个大 value 删除了，编码也不会回退。所以在设计 Key 结构时，要预估 field 的大小，避免偶发的大 value 触发永久升级。

### 8.5 集合对象

Set 的编码：

**① intset 编码**

- 条件：所有元素都是整数 **且**​ 元素数 ≤ `set-max-intset-entries`（默认 512）
- 存储：有序整数数组，二分查找 O(log N)

**② listpack 编码**（Redis 7.2+）

- 条件：小集合且元素为非整数

**③ hashtable 编码**

- 触发：插入非整数元素 **或**​ 元素数 > 512
- 不可逆

**典型场景**：Set 是存储"标签"、"好友关系"、"点赞用户"的理想结构。`SADD`、`SISMEMBER`、`SINTER`（交集）都是 O(1) 或 O(N)。

> 💡 **洞见**：Set 的 intset 编码和 Hash 的 listpack 编码体现了同一个设计哲学——**"整数"和"小数据"是特殊的，值得用专用结构优化**。这是因为在实际业务中，大量 Set 确实是"小范围整数集合"（比如用户的标签 ID、商品的分类 ID）。针对这种常见模式做优化，收益巨大。

### 8.6 有序集合对象

ZSet 的编码：

**① listpack 编码**（Redis 7.0+，原为 ziplist）

- 条件：元素数 < `zset-max-listpack-entries`（默认 128）**且**​ 每个 member < `zset-max-listpack-value`（默认 64 字节）
- 存储：member 和 score 交替存储，按 score 排序
- 查找：O(N) 遍历

**② skiplist + dict 组合编码**

- 触发：超过任一阈值
- skiplist：按 score 排序，支持范围查询 O(log N)
- dict：member → score 的 O(1) 映射
- member 的 SDS 字符串在两个结构间共享

**典型场景**：ZSet 是**排行榜**的天然结构：

```
ZADD leaderboard 100 "player1"
ZADD leaderboard 200 "player2"
ZREVRANGE leaderboard 0 9 WITHSCORES  // Top 10
ZRANK leaderboard "player1"           // 查排名
```

> 📌 **工业提醒**：ZSet 的 `ZRANGE`/`ZREVRANGE` 操作复杂度是 O(log N + M)，其中 M 是返回元素数。如果 M 很大（比如 `ZRANGE key 0 -1`），会一次性返回海量数据阻塞网络。生产环境务必分页，或使用 `ZRANGEBYSCORE` 加 LIMIT。

### 8.7 类型检查与命令多态

Redis 的命令分为两类：

**① 通用命令**（任何类型都可执行）：`DEL`、`EXPIRE`、`TTL`、`OBJECT`、`TYPE`、`DEBUG OBJECT`

**② 类型特定命令**：每种类型有自己的专属命令

- String：`SET`、`GET`、`APPEND`、`INCR`...
- List：`LPUSH`、`RPUSH`、`LPOP`、`RPOP`...
- Hash：`HSET`、`HGET`、`HDEL`...
- Set：`SADD`、`SREM`、`SISMEMBER`...
- ZSet：`ZADD`、`ZRANGE`、`ZSCORE`...

**类型检查的两种方式**：

- **编译期**：命令分发表 `redisCommandTable` 里每个命令都有 `arity` 和 `type` 约束
- **运行期**：命令执行前调用 `typeCheck()` 检查 key 的 `type` 字段是否匹配

**命令多态**：同一种底层编码结构，可能服务多种类型。比如 `ziplist/listpack` 同时服务 Hash 和 ZSet；`dict` 同时服务 Set 和 Hash 的 hashtable 编码。Redis 通过一个 `redisObject` 的 `type` 字段来区分**同一个底层结构在不同语境下的语义**。

> 💡 **洞见**：这是面向对象编程中"多态"思想在 C 语言里的实现——**没有继承、没有虚函数表，靠 `type` 字段 + switch/函数指针分发**。Redis 源码里到处是这样的模式：一个底层结构（如 listpack）通过不同的"解释器"（Hash 的 `hsetCommand` vs ZSet 的 `zaddCommand`）呈现出完全不同的行为。这是 C 语言写大型系统的必备技巧。

### 8.8 内存回收

Redis 使用 **引用计数（reference counting）**​ 实现内存回收：

```
#define decrRefCount(o) \
    if (--(o)->refcount == 0) freeObject(o)
```

每个 `redisObject` 有 `refcount` 字段：

- 创建对象：refcount = 1
- 对象被新变量引用：`incrRefCount(o)`
- 对象不再被引用：`decrRefCount(o)`，归零则释放

**对象共享**：Redis 在启动时预创建 0~9999 的整数对象（由 `OBJ_SHARED_INTEGERS` 控制），所有对这个范围内的整数的引用都指向同一个共享对象，refcount 递增 。这极大节省了小整数 String 的内存——想象一下一个热点 key 被百万次引用，如果每次都新建对象，内存会爆炸；共享对象让 refcount 只增加一次。

> ⚠️ **注意**：对象共享**只对 int 编码的 String 开放**。原因：共享对象在释放时必须遍历所有引用者，对于包含字符串内容的对象，比较相等性本身就需要 O(N) 时间，得不偿失。只有整数可以用 O(1) 判断是否相等，所以只有 int 编码值得共享。

### 8.9 对象共享

除了上述的整数共享，Redis 还共享以下对象：

- **空字符串**（用于返回空值的场景）
- **常见命令的 reply 对象**（如 OK、错误信息等）
- **特殊值**：`shared.crlf`、`shared.colon` 等

> 💡 **洞见**：对象共享是"以空间换时间"的反向操作——**以时间（refcount 管理）换空间（避免重复分配）**。但 Redis 团队极其克制：只对"创建频率极高、比较成本极低"的对象做共享。这种克制体现了工业级系统的成熟度——**优化要有数据支撑，不能凭感觉**。

### 8.10 对象的空转时长

每个 `redisObject` 有 `lru` 字段，记录对象**最后一次被访问的时间**（精度为秒）。Redis 的两种淘汰策略依赖它：

**LRU（Least Recently Used）**：

- `maxmemory-policy allkeys-lru` 或 `volatile-lru`
- 近似 LRU：随机采样 N 个 key（由 `maxmemory-samples` 控制，默认 5），淘汰最久未使用的

**LFU（Least Frequently Used）**（Redis 4.0+）：

- `maxmemory-policy allkeys-lfu` 或 `volatile-lfu`
- `lru` 字段的 24 位被拆分为：16 位计数器 + 8 位衰减时间
- 用计数器近似记录访问频率，访问越多计数越高；随时间衰减

用户可以通过 `OBJECT IDLETIME key` 命令查看对象的空转时长（不更新 LRU 时间）。

> 📌 **工业应用**：`OBJECT IDLETIME` 是排查"冷 key"的利器。如果发现某个 key 的 idletime 非常大但一直未被淘汰，说明它可能是一个"长生命周期但低频访问"的 key，应该考虑是否要设置更短的 TTL，或者用 `volatile-lfu` 策略让它优先被淘汰。

### 8.11 重点回顾

按第一性原理提炼第8章内核：

1. **redisObject 是 Redis 的统一抽象层**：type（用户视角）+ encoding（实现视角）+ refcount + lru
2. **编码多态**：同种 type 对应多种 encoding，根据数据特征自动选择
3. **String 三编码**：int（零分配）、embstr（≤44B 连续内存）、raw（>44B 分离）
4. **Hash/ZSet 的 listpack ↔ hashtable/skiplist 自动切换**：小数据省内存，大数据保性能
5. **Set 的 intset ↔ hashtable 切换**：全整数且 ≤512 用 intset
6. **List 的 quicklist**：ziplist/listpack 的双向链表，兼顾灵活与紧凑
7. **引用计数 + 对象共享**：int 编码的 0~9999 整数全局共享
8. **LRU/LFU 淘汰**：基于 `lru` 字段的近似算法

## 第7～8章的横向串联：从"构件"到"对象"的跃迁

读完这两章，你应该能在脑子里建立起 Redis 完整的"双层架构"：

```
┌─────────────────────────────────────────────────────┐
│                  对象系统（第8章）                      │
│   String    List     Hash     Set      ZSet          │
│     ↓         ↓        ↓        ↓        ↓           │
│   int/      quick    list     int      list          │
│   emb/      list     pack     set      pack          │
│   raw       (list    /hash    /hash    /skip         │
│             pack)    table    table    list+          │
│                     /list    /list    dict           │
│                     pack     pack                    │
├─────────────────────────────────────────────────────┤
│              底层数据结构（第2~7章）                     │
│   SDS    adlist    dict    skiplist   intset   ziplist/listpack │
└─────────────────────────────────────────────────────┘
```

**这条架构线的第一性原理**：

1. **"小数据用紧凑结构，大数据用通用结构"**​ 是整个对象系统的核心策略。listpack/intset 解决"内存放大"，hashtable/skiplist 解决"操作复杂度"——两者的切换点是工程经验的结晶（128/64/512 这些阈值不是拍脑袋定的，是 benchmark 出来的）。
2. **ziplist 的退役是 Redis 工程成熟度的里程碑**。它告诉我们：**当一个设计的根本缺陷（连锁更新）在实践中造成不可忽视的长尾延迟时，"修补"不如"重做"**。listpack 用"自描述长度"这一个改变，彻底消灭了 O(N²) 的隐患，同时为未来的多线程/并发 Redis 铺平了道路（每个元素独立边界，便于分段锁）。
3. **对象系统的"编码路由"思想值得借鉴到自研系统**。如果你在设计一个多租户缓存系统，可以学 Redis：对外暴露统一的类型接口，对内根据数据特征动态选择存储引擎（内存/SSD/远程）、编码格式（紧凑/通用）、索引结构（哈希/树/跳表）。用户在绝大多数情况下感受不到差异，但在极端场景下系统能自动"做正确的事"。
4. **embstr 的"不可变性"、intset 的"只升不降"、ziplist→listpack 的"推倒重来"**——这三个决策的背后是同一个工程哲学：**用约束换效率，用不可逆换简洁**。这不是偷懒，而是经过深思熟虑的权衡：在 99% 的场景下，这些约束都不构成问题，但换来的性能/内存收益是巨大的。

## 工业落地建议

把这两章的知识用到生产环境，有五条具体可操作的建议：

1. **监控 key 的编码状态**：定期用 `OBJECT ENCODING key` 巡检，关注是否有预期之外的编码升级。特别是 Hash/Set/ZSet，如果某个 key 意外从 listpack 变成了 hashtable/skiplist，往往意味着数据规模超出了紧凑编码的阈值，需要评估内存影响。
2. **Hash/Set/ZSet 的"小数据"设计准则**：尽量让单个 Hash 的 field 数 < 128、单个 value < 64 字节。如果你的业务模型天然是大 Hash（比如存储用户的所有属性），可以考虑**按 field 范围分片**成多个小 Hash，例如 `user:1000:base`、`user:1000:prefs`、`user:1000:stats`。
3. **String 的 44 字节红线**：短字符串（如 session token、短 URL、状态码）尽量控制在 44 字节以内，享受 embstr 的一次分配红利。超过这个长度，考虑是否能拆分或用 Hash 存储。
4. **List 作为消息队列的容量管控**：quicklist 虽然高效，但单个 list 元素过多仍会导致 `LINDEX`、`LINSERT` 变慢。生产环境务必用 `LTRIM` 限制队列长度，或直接使用 Stream 类型（Redis 5.0+）。
5. **警惕 big key 引发的连锁反应**：一个 10MB 的 Hash 或 Set，在编码升级、持久化、主从同步、集群迁移时都会成为性能瓶颈。用 `redis-cli --bigkeys` 定期扫描，对超过阈值（如 Hash 字段数 > 5000、String 长度 > 10KB）的 key 做拆分或 TTL 管控。
