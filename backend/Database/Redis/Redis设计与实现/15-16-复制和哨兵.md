
# 《Redis设计与实现》读书笔记 · 第15章～第16章

这两章标志着全书从"单机数据库的实现"跨入"多机数据库的实现"——**第15章复制回答的是"如何让数据在多台机器上保持一致"；第16章 Sentinel 回答的是"当主库挂了，谁来自动顶上"**。这两章是 Redis 走向生产可用的关键一跃，也是后续 Redis Cluster（第17章）的基础。

> ⚠️ 版本提醒：黄健宏的书基于 Redis 3.x，其中只讲到 PSYNC1（Redis 2.8 引入）。而在 **Redis 4.0 中，PSYNC 升级到了 PSYNC2**，引入了双复制 ID（replid + replid2）机制，使得**故障转移后其他副本也能对新主进行部分重同步**——这是书上没有的新版核心机制 。下面以书的结构为主线，用现代资料校正细节。

## 第15章 复制

### 15.1 旧版复制功能的实现

Redis 2.8 之前，复制功能只有一种同步命令：**SYNC**。

旧版 SYNC 的工作流程极其粗暴 ：

```
从服务器 SLAVEOF master_ip master_port
    ↓
与主服务器建立 socket 连接
    ↓
发送 SYNC 命令
    ↓
主服务器收到 SYNC：
  1. BGSAVE 生成 RDB（fork 子进程，阻塞主进程）
  2. 将 RDB 文件发送给从服务器
  3. 将 BGSAVE 期间的写命令缓冲
  4. RDB 发送完毕后，发送缓冲的写命令
    ↓
从服务器：
  5. 接收并载入 RDB
  6. 执行缓冲的写命令
    ↓
进入"命令传播"阶段：主服务器每执行一个写命令就发送给从服务器
```

**旧版 SYNC 的本质问题**：它是一个"全有或全无"的同步——要么全量同步，要么什么都不做。**每次从服务器（重新）连接主服务器，无论断开时间多短，都必须来一次完整的 RDB 传输**​ 。

> 💡 **第一性原理视角**：旧版 SYNC 的设计隐含了一个假设——"从服务器重启/断线是一个罕见事件，值得为之付出一次全量同步的代价"。但在生产环境中，**网络抖动、超时、主从切换是常态而非例外**。在容器化、云原生环境中，网络闪断可能每秒都在发生。用"全量同步"来应对"1 秒的网络闪断"，就像为了修复一个错别字而重印整本书——粒度太粗，成本太高。

### 15.2 旧版复制功能的缺陷

旧版 SYNC 的缺陷可以从三个维度剖析：

**① 效率缺陷：断线重连必全量**

从服务器在以下场景都会触发全量同步 ：

- 从服务器重启
- 网络闪断超过 `repl-timeout`（默认 60 秒）
- 主服务器重启（run id 改变）
- 主从切换（Sentinel 故障转移）

对于 TB 级数据集，一次全量同步意味着：

- 主服务器 fork 子进程生成 RDB（可能占用大量内存和 CPU）
- 网络传输整个 RDB 文件（可能持续数分钟）
- 从服务器载入 RDB（阻塞，期间不提供服务）
- 主服务器缓冲区溢出可能导致同步失败循环

**② 资源缺陷：fork 风暴**

当多个从服务器同时连接或重连主服务器时，如果它们的 SYNC 请求落到不同时间点，主服务器可能**连续多次 fork**​ 生成 RDB。虽然 Redis 会复用正在进行中的 BGSAVE ，但如果时机错位，仍然会造成"fork 风暴"——CPU 尖刺、内存压力、延迟毛刺接踵而至。

**③ 一致性缺陷：异步复制的"丢失窗口"**

Redis 复制是**异步的**——主服务器执行写命令后立即返回客户端，然后才将命令传播给从服务器 。这意味着：

- 主服务器宕机时，**最近一批尚未传播的写命令会永久丢失**
- 在"主服务器挂掉 → Sentinel 提升从服务器为新主"的窗口期，数据不一致不可避免

> ⚠️ **工业现实**：旧版 SYNC 的这些缺陷在高可用架构中是致命的。一个网络抖动就让TB级数据重新全量同步一次，这种"脆弱性"使得 Redis 在 2.8 之前很难被用于严肃的生产环境。这也是为什么 antirez 在 Redis 2.8 中紧急推出 PSYNC——它不是锦上添花，而是 Redis 走向"生产级高可用"的必补之课。

### 15.3 新版复制功能的实现

Redis 2.8 引入 **PSYNC 命令**，核心思想是**"能增量就增量，不能增量才全量"**。

PSYNC 依赖三个核心数据结构（书上有详细讲解，这里结合现代源码校正）：

**① 复制 ID（Replication ID / replid）**

一个 40 字符的十六进制字符串，标识"一段数据集历史" 。每个 Redis 实例在以下时机生成新的复制 ID ：

- 作为主服务器首次启动
- 从服务器被提升为主服务器（故障转移）
- 主服务器重启

**关键：Redis 4.0+ 引入了双复制 ID 机制**​ ：

- `replid`：当前主服务器的复制 ID
- `replid2`：上一代主服务器的复制 ID（仅在新主上任后保留一段时间）

为什么需要两个？**为了支持故障转移后的部分重同步**。当 Sentinel 把一个从服务器提升为新主时，这个新主保留旧主的 replid 作为 replid2，这样其他从服务器就可以拿着旧主的 replid 来请求部分重同步 。

**② 复制偏移（Replication Offset）**

主从服务器各自维护一个偏移量：

- 主服务器每向复制流写入 N 字节数据，`master_repl_offset += N`
- 从服务器每从主服务器接收 N 字节数据，`slave_repl_offset = N`

**偏移量的精妙之处**：它是一个**逻辑时钟**——`(replid, offset)` 这个二元组唯一定位了数据集的一个精确版本 。两个实例若有相同的 replid 和 offset，则它们拥有完全相同的数据。

**③ 复制积压缓冲区（Replication Backlog）**

主服务器维护的一个**环形缓冲区**（默认 1MB），记录最近传播的写命令 。

```
repl_backlog
    ┌──────────────────────────────────────┐
    │  ...  | cmd_K | cmd_K+1 | ... | cmd_N │
    │       ↑                              ↑
    │    offset_first                 master_repl_offset
    └──────────────────────────────────────┘
         │                              │
         │                              └── 新命令从这里追加
         └── 最早可用的偏移量（若从服务器请求的 offset < 此值，必须全量同步）
```

**部分重同步的判定逻辑**（来自 `masterTryPartialResynchronization` ）：

```
// 检查复制 ID 是否匹配（replid 或 replid2）
if (strcasecmp(master_replid, server.replid) &&
    (strcasecmp(master_replid, server.replid2) ||
     psync_offset > server.second_replid_offset)) {
    goto need_full_resync;
}

// 检查 offset 是否在积压缓冲区内
if (!server.repl_backlog ||
    psync_offset < server.repl_backlog->offset ||
    psync_offset > (server.repl_backlog->offset + server.repl_backlog->histlen)) {
    goto need_full_resync;
}

// 部分重同步：从 offset 开始发送积压缓冲区的内容
c->flags |= CLIENT_SLAVE;
c->replstate = SLAVE_STATE_ONLINE;
buflen = snprintf(buf,sizeof(buf),"+CONTINUE %s\r\n", server.replid);
connWrite(c->conn,buf,buflen);
psync_len = addReplyReplicationBacklog(c,psync_offset);
```

### 15.4 部分重同步的实现

部分重同步的完整流程 ：

```
从服务器断线重连
    ↓
发送：PSYNC <replid> <offset>
    ↓
主服务器判定：
    ┌─ replid 匹配 且 offset 在积压缓冲区内？
    │     ├─ YES → +CONTINUE：仅发送 [offset, master_repl_offset] 之间的命令
    │     └─ NO  → +FULLRESYNC <new_replid> <new_offset>：全量同步
    ↓
从服务器：
    ├─ +CONTINUE → 接收增量命令，继续执行
    └─ +FULLRESYNC → 丢弃本地数据，载入新 RDB，再接收增量
```

**部分重同步的成本分析**：

- 主服务器无需 fork（不像全量同步）
- 网络只需传输缺失的部分命令（通常是 KB~MB 级，而非 GB 级）
- 从服务器无需重新载入 RDB
- **整个过程通常在毫秒到秒级完成**

**积压缓冲区大小的调优公式**​ ：

```
repl-backlog-size = 峰值写入速率(B/s) × 可接受断线时长(s)
```

例如：写入速率 10MB/s，希望容忍 60 秒断线：

```
repl-backlog-size = 10MB × 60 = 600MB
```

建议设置为计算值的 2-3 倍，以应对突发写入 。

**积压缓冲区的另一个参数**：

```
repl-backlog-ttl 3600  # 当没有从服务器连接时，积压缓冲区保留的秒数
```

默认 3600 秒。如果在 TTL 内没有从服务器重连，积压缓冲区会被释放以节省内存。

> 💡 **第一性原理洞见**：部分重同步的本质是**用"空间换时间"的经典权衡**——主服务器在内存中保留一段"历史命令"（积压缓冲区），换取从服务器重连时的快速恢复。这背后是一个更深的洞察：**网络闪断期间主服务器积累的写命令，往往远小于整个数据集**。保留"最近 N 字节的写流"比保留"整个数据集的快照"成本低得多。
> 
> 双复制 ID（replid + replid2）的引入则将这种"增量思维"从"主从关系"延伸到了"故障转移"场景——**即使主服务器换了，只要新主还记得旧主的 ID，其他从服务器仍然可以尝试部分重同步，而非被迫全量同步**。这是 PSYNC2 相较 PSYNC1 的最大突破，也是 Redis 4.0 在"高可用"方向上迈出的关键一步 。

### 15.5 PSYNC 命令的实现

PSYNC 命令的语法 ：

```
PSYNC <replication_id> <offset>
```

**两种调用场景**：

**① 首次同步**（从服务器从未同步过或 replid 未知）：

```
PSYNC ? -1
```

主服务器必定回应 `+FULLRESYNC <replid> <offset>`，触发全量同步。

**② 重连尝试部分同步**：

```
PSYNC <last_replid> <last_offset>
```

主服务器根据判定逻辑回应 `+CONTINUE` 或 `+FULLRESYNC`。

**现代 PSYNC2 的握手流程**​ （Redis 4.0+）：

```
1. Replica → Primary: PING
   Primary → Replica: +PONG
   
2. Replica → Primary: AUTH <password>  (如果主库设置了 requirepass)
   Primary → Replica: +OK
   
3. Replica → Primary: REPLCONF listening-port <port>
   Primary → Replica: +OK
   
4. Replica → Primary: REPLCONF capa eof capa psync2
   Primary → Replica: +OK
   # capa psync2: 声明支持 PSYNC2 协议
   # capa eof: 支持无盘复制（RDB 以 EOF 标记的流形式传输）
   
5. Replica → Primary: PSYNC <replid> <offset>
   
6. Primary → Replica: +FULLRESYNC <new_replid> <new_offset>
                        或 +CONTINUE <replid>
   
7. 如果是 FULLRESYNC：
   Primary: BGSAVE → 传输 RDB → 传输缓冲的写命令
   如果是 CONTINUE：
   Primary: 直接从积压缓冲区发送 [offset, master_repl_offset] 的命令
```

**PSYNC1 vs PSYNC2 的关键差异**​ ：

|维度|PSYNC1 (Redis 2.8-3.x)|PSYNC2 (Redis 4.0+)|
|---|---|---|
|复制 ID|单一 replid|双 ID：replid + replid2|
|故障转移后部分同步|❌ 不支持|✅ 支持|
|级联复制场景|每次切换都全量|可部分同步|
|协议协商|无|`REPLCONF capa psync2`|

> 📌 **工业意义**：PSYNC2 的双 ID 机制看似简单，却解决了 Redis 复制的"阿喀琉斯之踵"——**故障转移后的连锁全量同步**。在没有 PSYNC2 的时代，Sentinel 提升一个新主后，所有其他从服务器都会因为"replid 不匹配"而被迫全量同步，这在大规模部署中会造成"同步风暴"。PSYNC2 让"故障转移"这个本来就充满压力的时刻，不再雪上加霜。

### 15.6 复制的实现

**完整复制流程图**​ ：

```
┌──────────────────────────────────────────────────────────────────┐
│                          主服务器                                  │
│                                                                    │
│  ┌──────────────┐   ① PSYNC ? -1    ┌──────────────────────────┐  │
│  │              │◄──────────────────│                          │  │
│  │  事件循环     │                   │      从服务器             │  │
│  │              │                   │                          │  │
│  └──────┬───────┘                   └──────────────────────────┘  │
│         │ ② +FULLRESYNC replid offset                             │
│         ▼                                                          │
│  ┌──────────────────────────────────────────────────────────────┐ │
│  │ BGSAVE: fork 子进程生成 RDB                                   │ │
│  │ 同时：新写命令 → 积压缓冲区 + 从服务器输出缓冲区               │ │
│  └──────────────────────────────────────────────────────────────┘ │
│         │                                                          │
│         ▼                                                          │
│  ┌──────────────────────────────────────────────────────────────┐ │
│  │ 传输 RDB 文件到从服务器                                       │ │
│  │ （磁盘模式：写盘后传输；无盘模式：管道直传）                   │ │
│  └──────────────────────────────────────────────────────────────┘ │
│         │                                                          │
│         ▼                                                          │
│  ┌──────────────────────────────────────────────────────────────┐ │
│  │ 传输 BGSAVE 期间缓冲的写命令                                   │ │
│  └──────────────────────────────────────────────────────────────┘ │
│         │                                                          │
│         ▼                                                          │
│  ┌──────────────────────────────────────────────────────────────┐ │
│  │ 进入"命令传播"阶段：                                           │ │
│  │ 每执行一个写命令，立即发送给所有从服务器                        │ │
│  └──────────────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────────┘
```

**命令传播阶段的细节**：

主服务器在 `call()` 函数（命令执行的最后一步）中调用 `propagate()` ：

```
void propagate(struct redisCommand *cmd, redisDb *db, robj **argv, int argc) {
    // 传播到 AOF
    if (server.aof_state != AOF_OFF)
        feedAppendOnlyFile(cmd, db, argv, argc);
    
    // 传播到所有从服务器
    replicationFeedReplicas(server.slaves, db, argv, argc);
}
```

`replicationFeedReplicas` 将命令序列化为 RESP 协议格式，写入每个从服务器的输出缓冲区 。

**全量同步的三种传输模式**​ ：

1. **磁盘模式（Disk-backed）**：主服务器 fork 子进程写 RDB 到磁盘，然后从磁盘读取并发送给从服务器
2. **无盘模式（Diskless）**：`repl-diskless-sync yes`，fork 的子进程直接将 RDB 写入 socket，不落盘
3. **RDB 通道模式（rdbchannel）**：2024 年引入，主服务器使用两条 TCP 连接——一条传 RDB，一条传实时命令流 ，从服务器可以在载入 RDB 的同时继续应用实时命令，缩小复制滞后窗口

**无盘复制的权衡**​ ：

- 优点：避免磁盘 I/O，对 SSD 不友好的环境特别有用
- 缺点：如果某个从服务器在 RDB 传输中途断开，它必须从下一次 BGSAVE 重新开始；而磁盘模式下多个从服务器可以各按各的节奏读取同一个 RDB 文件
- `repl-diskless-sync-delay`：等待更多从服务器加入同一波无盘同步的窗口期（默认 5 秒）

**级联复制**（Cascading Replication）：

Redis 支持"从服务器的从服务器"——一个从服务器可以同时是另一个从服务器的主服务器。这在大规模部署中用于减轻主服务器的带宽压力 ：

```
Master
       /   |   \
     Replica1 Replica2 Replica3
                 |      |
            Replica1a Replica3a
```

级联复制下，部分重同步的判断逻辑不变——只要 replid 和 offset 匹配且在积压缓冲区内，就可以部分同步。

### 15.7 心跳检测

心跳是复制健康的关键保障。Redis 复制的心跳机制包含**双向心跳**：

**① 从服务器 → 主服务器：REPLCONF ACK**

从服务器每秒发送一次 ：

```
REPLCONF ACK <slave_replication_offset>
```

这个心跳有三个作用：

1. **汇报从服务器的复制偏移**：让主服务器知道从服务器追赶到了哪里
2. **检测从服务器是否存活**：主服务器在 `repl-timeout`（默认 60 秒）内未收到 ACK，判定从服务器死亡，关闭连接
3. **辅助积压缓冲区的清理**：主服务器知道最慢的从服务器 offset，可以据此决定积压缓冲区的保留范围

**② 主服务器 → 从服务器：PING**

主服务器每隔 `repl-ping-replica-period`（默认 10 秒）向从服务器发送 PING 命令 ，检测从服务器是否存活。

**心跳相关的关键配置**​ ：

```
repl-ping-replica-period 10   # 主 → 从 PING 间隔（秒）
repl-timeout 60               # 心跳超时时间（秒）
                             # 从服务器 60 秒内未发送 REPLCONF ACK 
                             # 或主服务器 60 秒内未收到从服务器任何数据，
                             # 判定连接断开
```

> ⚠️ **工业警示**：`repl-timeout` 的设置需要特别小心：
> 
> - 太小：网络微抖就会导致复制断开，触发全量同步
> - 太大：主服务器要等很久才能发现从服务器真的死了，期间会持续累积积压缓冲区
> 
> 对于跨数据中心、网络质量不稳定的场景，建议适当调大 `repl-timeout` 到 120 或 180 秒，避免"超时 → 全量同步 → 超时"的恶性循环。

**心跳对积压缓冲区的影响**：

主服务器会根据最慢从服务器的 offset 来决定积压缓冲区的"有效起点"。如果某个从服务器落后太多（offset 已经滚出积压缓冲区），主服务器实际上已经无法为它提供部分重同步——它必须全量同步。这就是为什么 **`repl-backlog-size` 的配置必须基于"最慢从服务器的写入速率 × 最大可接受滞后时间"来计算**​ 。

### 15.8 重点回顾

1. **旧版 SYNC 的致命缺陷**：断线重连必全量，TB 级数据集代价惨重
2. **PSYNC 的三驾马车**：复制 ID（replid）+ 复制偏移（offset）+ 复制积压缓冲区（backlog）
3. **`(replid, offset)` 二元组唯一定位数据集版本**——这是 Redis 复制的"逻辑时钟"
4. **PSYNC2（Redis 4.0+）引入双复制 ID**：replid + replid2，支持故障转移后的部分重同步
5. **积压缓冲区是环形缓冲**：默认 1MB，大小 = 写入速率 × 可接受断线时长
6. **全量同步的三种传输模式**：磁盘模式、无盘模式、RDB 通道模式（2024 新增）
7. **双向心跳**：从→主 REPLCONF ACK（每秒），主→从 PING（每 10 秒）
8. **Redis 复制是异步的**：主服务器执行写命令后立即返回客户端，存在"丢失窗口"

## 第16章 Sentinel

### 16.1 启动并初始化 Sentinel

Sentinel 是 Redis 的高可用组件，但它**不是一个独立的外围系统，而是一个运行在特殊模式下的 Redis 实例**——启动时使用 `--sentinel` 参数，载入 `sentinel.conf` 配置 。

**启动流程**：

```
redis-server /path/to/sentinel.conf --sentinel
    ↓
① 初始化 Sentinel 状态结构（sentinelState）
    ↓
② 载入配置文件，解析 sentinel monitor 指令
    ↓
③ 为每个被监控的主服务器创建 sentinelRedisInstance 结构
    ↓
④ 创建与被监控主服务器的网络连接
    ↓
⑤ 向主服务器发送 SUBSCRIBE 订阅频道
    ↓
⑥ 进入事件循环，开始 PING / INFO / PUBLISH 的周期性工作
```

**Sentinel 配置示例**​ ：

```
port 26379
sentinel monitor mymaster 127.0.0.1 6379 2
sentinel down-after-milliseconds mymaster 5000
sentinel failover-timeout mymaster 60000
sentinel parallel-syncs mymaster 1
sentinel auth-pass mymaster yourpassword
```

**关键配置项解析**​ ：

|配置项|含义|推荐值|
|---|---|---|
|`sentinel monitor <name> <ip> <port> <quorum>`|监控主服务器，quorum 是判定下线的哨兵数|生产环境 quorum=2|
|`down-after-milliseconds`|多久无响应判定为 SDOWN|5000-30000ms|
|`failover-timeout`|故障转移超时时间|60000-180000ms|
|`parallel-syncs`|故障转移后同时对新主同步的从服务器数|1|

> 💡 **第一性原理洞见**：Sentinel 最反直觉的设计是——**它本身就是一个分布式系统**。一个 Sentinel 是不够的（单点故障），三个 Sentinel 才是最小生产部署 。而三个 Sentinel 之间如何达成共识？答案是 **quorum 机制 + Raft 风格的领导者选举**​ 。
> 
> 这揭示了一个深刻的分布式系统真理：**"高可用"不能用一个单点来实现，必须用多个节点来互相监督**。Sentinel 的本质不是"监控 Redis 的程序"，而是"通过多个 Sentinel 互相监控 Redis 和彼此，从而在 Redis 主库失败时达成'该故障转移了'的共识"。

**Sentinel 是分布式的三个理由**​ ：

1. **降低误判**：单个 Sentinel 可能因为自身网络问题误判主库下线，多个 Sentinel 共同判定可以避免误报
2. **避免 Sentinel 自身单点故障**：如果只有 1 个 Sentinel，它挂了整个系统就没有高可用了
3. **故障转移的权威性**：故障转移必须由"多数派 Sentinel 选举出的领导者"执行，避免多个 Sentinel 同时执行冲突的故障转移

### 16.2 获取主服务器信息

Sentinel 通过**周期性地向主服务器发送 INFO 命令**来获取主服务器的信息 ：

```
每 10 秒（默认）：
    Sentinel → 主服务器: INFO
    主服务器 → Sentinel: 回复包含所有从服务器列表的 INFO 输出
```

INFO 命令的回复中包含了关键信息：

```
# Replication
role:master
connected_slaves:2
slave0:ip=127.0.0.1,port=6380,state=online,offset=12345,lag=1
slave1:ip=127.0.0.1,port=6381,state=online,offset=12345,lag=1
```

**Sentinel 从 INFO 中提取**：

- 主服务器的 `role`（确认它仍然是主服务器）
- 所有从服务器的 IP、端口、状态、复制偏移
- 主服务器的复制偏移

**为什么是每 10 秒一次？**​ 这是一个工程权衡：

- 太频繁：增加主服务器负担（INFO 命令本身有一定开销）
- 太稀疏：从服务器列表更新不及时，影响故障转移时的从服务器选择

Sentinel 发现新的从服务器后，会**立即与之建立连接**，并开始向从服务器也发送 INFO 命令（每 10 秒一次）和 PING 命令（每 1 秒一次）。

### 16.3 获取从服务器信息

Sentinel 向从服务器发送 INFO 命令（每 10 秒一次），获取 ：

```
# Replication
role:slave
master_host:127.0.0.1
master_port:6379
master_link_status:up
slave_repl_offset:12345
slave_priority:100
```

**Sentinel 关注的关键指标**：

- `master_link_status`：从服务器与主服务器的连接状态（up/down）
- `slave_repl_offset`：从服务器的复制偏移——**这是故障转移时选择"最优从服务器"的核心依据**
- `slave_priority`：从服务器优先级（故障转移时优先级数值小的优先被选为新主）

**故障转移时的从服务器排序逻辑**​ ：

1. 排除 `slave_priority = 0` 的从服务器（标记为永不提升）
2. 选择 `slave_priority` 最小的从服务器
3. 在优先级相同时，选择 `slave_repl_offset` 最大的从服务器（数据最新）
4. 在 offset 也相同时，选择 run id 字典序最小的从服务器

> 💡 **洞见**：这个排序逻辑体现了 Sentinel 的核心价值观——**"数据最新"优于"优先级最高"**。因为如果选择了一个数据落后的从服务器作为新主，会导致大量数据丢失。Sentinel 宁可选择一个优先级较低但数据最新的从服务器，也不会选择一个优先级高但数据落后的从服务器。

### 16.4 向主服务器和从服务器发送信息

Sentinel 在 **`_PUBSUB_CHANNEL_`**​ 频道（默认频道名为 `__sentinel__:hello`）上**每 5 秒发布一次自己的信息**​ ：

```
PUBLISH __sentinel__:hello "<sentinel_ip>,<sentinel_port>,<sentinel_runid>,<sentinel_epoch>,<master_name>,<master_ip>,<master_port>,<master_epoch>"
```

**这条 PUBLISH 消息的作用**：

1. **Sentinel 互相发现**：其他 Sentinel 订阅同一个频道，收到这条消息后就知道了彼此的存在
2. **配置传播**：新加入的 Sentinel 通过频道消息了解当前主服务器的地址
3. **Epoch 同步**：通过 `sentinel_epoch` 和 `master_epoch` 来协调配置纪元

**频道消息的精妙之处**：

- Sentinel 既 **PUBLISH**​ 也 **SUBSCRIBE**​ 同一个频道
- 自己发的消息自己也会收到（用于确认消息发送成功）
- 其他 Sentinel 收到消息后，如果发现了未知的 Sentinel，就与之建立连接

**为什么用 Pub/Sub 而不是专门的协议？**​ 这是一个工程上的巧思——**复用 Redis 自身的 Pub/Sub 机制来实现 Sentinel 之间的通信**，避免了重新发明轮子。Sentinel 本质上是一个"Redis 客户端"，它用 Redis 的原语（PING、INFO、PUBLISH、SUBSCRIBE）来完成所有工作。

### 16.5 接收来自主服务器和从服务器的频道信息

Sentinel 通过 SUBSCRIBE 监听 `__sentinel__:hello` 频道，当收到其他 Sentinel 的消息时：

```
收到消息 → 解析 Sentinel 信息 → 检查是否已知
    ↓
    ├─ 未知 Sentinel → 创建 Sentinel 实例，建立连接
    ├─ 已知 Sentinel → 更新最后通信时间、epoch 等信息
    └─ 主服务器配置变更 → 更新本地配置
```

**纪元（Epoch）的概念**：

Sentinel 使用两个 epoch ：

- **Sentinel 配置纪元（sentinel_epoch）**：每次 Sentinel 启动时递增
- **主服务器配置纪元（master_epoch）**：每次故障转移完成时递增

**Epoch 的作用是解决"脑裂"问题**：当网络分区发生时，可能出现"两个 Sentinel 都认为自己是领导者并尝试故障转移"的情况。通过 epoch 的比较，可以确保只有"最新纪元"的故障转移生效，旧纪元的故障转移被忽略。

**Sentinel 之间的其他通信**：

- **PING**：每 1 秒一次，检测其他 Sentinel 是否存活
- **SENTINEL is-master-down-by-addr**：用于询问其他 Sentinel "你认为这个主服务器下线了吗？"——这是客观下线判定的核心机制
- **SENTINEL get-master-addr-by-name**：查询当前主服务器地址

### 16.6 检测主观下线状态

**主观下线（Subjectively Down, SDOWN）**：单个 Sentinel 认为主服务器已下线 。

判定逻辑 ：

```
Sentinel 每 1 秒向主服务器发送 PING
    ↓
在 down-after-milliseconds 时间内未收到有效回复
（有效回复包括：+PONG、+LOADING、-MASTERDOWN）
    ↓
该 Sentinel 将此主服务器标记为主观下线（SDOWN）
```

**为什么需要"主观下线"这个概念？**​ 因为：

- 单个 Sentinel 的判断可能是错误的（它自己的网络有问题）
- 必须等待多个 Sentinel 达成共识才能采取动作
- SDOWN 是 ODOWN 的前提条件

**`down-after-milliseconds` 的配置权衡**​ ：

- 太小（如 1000ms）：网络微抖就触发 SDOWN，可能导致不必要的故障转移
- 太大（如 60000ms）：主服务器真的挂了也要等很久才开始故障转移，RTO 变大

生产环境推荐值：**5000-30000ms**，具体取决于网络的稳定性。

**主观下线的状态转换**：

```
PING 无响应超过 down-after-milliseconds
    ┌──────────────────────────────────────────────────┐
    │                                                  ▼
[正常状态] ────────────────────────────────────────→ [SDOWN]
    ▲                                                  │
    │                                                  │ PING 恢复响应
    └──────────────────────────────────────────────────┘
```

### 16.7 检查客观下线状态

**客观下线（Objectively Down, ODOWN）**：**quorum 个 Sentinel 都认定主服务器 SDOWN**​ 。

判定流程 ：

```
Sentinel A 判定主服务器 SDOWN
    ↓
Sentinel A 向其他 Sentinel 发送：
    SENTINEL is-master-down-by-addr <master_ip> <master_port> <current_epoch> <runid>
    ↓
其他 Sentinel 回复：
    <is_down> <leader_runid> <leader_epoch>
    （is_down: 1 表示也认为下线；leader_runid: 如果已经投过票，填被投票者的 runid）
    ↓
Sentinel A 统计同意"下线"的 Sentinel 数量
    ↓
如果数量 ≥ quorum：
    标记主服务器为 ODOWN
    进入"选举领头 Sentinel"阶段
```

**quorum 的含义与配置**​ ：

`sentinel monitor mymaster 127.0.0.1 6379 2` 中的 `2` 就是 quorum。

- quorum **只用于判定下线**，不用于执行故障转移
- 要实际执行故障转移，需要**多数派 Sentinel 选举出一个领导者**
- 对于 3 个 Sentinel，quorum=2 意味着：至少 2 个 Sentinel 认为主库下线，才能进入故障转移流程；但要实际执行故障转移，还需要在 3 个 Sentinel 中获得多数派（≥2）的投票选出领导者

**quorum 的工程权衡**​ ：

- **quorum 太小**（如 1）：容易误判，网络抖动就可能触发故障转移
- **quorum 太大**（如等于 Sentinel 总数）：任何一个 Sentinel 挂了都无法触发故障转移，可用性降低
- **推荐**：quorum = floor(Sentinel总数 / 2) + 1，即"多数派"

```
3 个 Sentinel → quorum = 2
5 个 Sentinel → quorum = 3
7 个 Sentinel → quorum = 4
```

> ⚠️ **重要细节**：quorum 和"领导者选举的多数派"是两个不同的概念。quorum 用于判定"是否下线"，多数派用于"是否授权故障转移"。Sentinel 的设计确保了：**只有在多数派 Sentinel 都可达时，故障转移才会发生**——这避免了"少数派分区"中的 Sentinel 错误地执行故障转移，从而导致"脑裂"（split-brain）。

### 16.8 选举领头 Sentinel

当主服务器被判定为 ODOWN 后，Sentinel 们需要选举出一个**领头 Sentinel（Leader Sentinel）**来执行故障转移。

**选举算法：Raft 风格的领导者选举**​ ：

```
每个判定主服务器 ODOWN 的 Sentinel 都进入"候选者"状态
    ↓
候选 Sentinel 增加自己的 epoch，向其他 Sentinel 发送：
    SENTINEL is-master-down-by-addr <ip> <port> <new_epoch> <self_runid>
    ↓
其他 Sentinel 收到请求后：
    ├─ 如果还没有投过票（本轮 epoch）：投票给第一个请求的候选者
    │   回复：<is_down> <candidate_runid> <candidate_epoch>
    └─ 如果已经投过票：回复已投票的候选者信息
    ↓
候选 Sentinel 统计获得的票数
    ↓
如果获得 >= 多数派票（floor(N/2)+1）：
    成为领头 Sentinel，开始执行故障转移
    ↓
否则：等待 failover-timeout，重新发起选举
```

**选举的核心规则**：

1. **先到先得**：每个 Sentinel 在当前 epoch 内只能投一票，投给第一个向它请求的候选者
2. **epoch 递增**：每轮选举 epoch 都会增加，确保旧选举的结果不会影响新选举
3. **多数派获胜**：获得多数派选票的候选者成为领导者
4. **随机退避**：如果选举失败（没有候选者获得多数派），Sentinel 会等待一个随机时间后重新发起选举，避免"选举风暴"

> 💡 **洞见**：Sentinel 的领导者选举本质上是 **Raft 共识算法的简化版**。Raft 是分布式系统中最经典的共识算法之一，其核心思想就是通过"任期（term/epoch）+ 多数派投票"来选举领导者。Sentinel 巧妙地借用了这一思想，使得"多个 Sentinel 在分布式环境下对'谁来执行故障转移'达成共识"。
> 
> 这个设计的深刻之处在于：**它把"故障转移"这个动作本身也变成了需要共识的事情**。不是"谁先发现主库下线谁就执行故障转移"，而是"必须经过多数派 Sentinel 授权，才能执行故障转移"。这从根本上避免了脑裂——在网络分区的情况下，少数派分区的 Sentinel 无法获得多数派投票，因此不会执行故障转移，从而避免了"双主"的出现。

### 16.9 故障转移

领头 Sentinel 被选出后，开始执行故障转移。完整流程 ：

**① 选择最优从服务器**

按照 16.3 节描述的排序逻辑：

1. 排除 `slave_priority = 0` 的从服务器
2. 选择 `slave_priority` 最小的
3. 优先级相同时，选择 `slave_repl_offset` 最大的（数据最新）
4. offset 相同时，选择 run id 字典序最小的

**② 提升从服务器为新主**

向选中的从服务器发送 ：

```
REPLICAOF NO ONE
```

使其停止复制，成为独立的主服务器。

**③ 让其他从服务器复制新主**

向所有其他从服务器发送 ：

```
REPLICAOF <new_master_ip> <new_master_port>
```

它们会向新主发送 PSYNC 命令，根据 15.5 节的逻辑，如果新主的 replid2 匹配且 offset 在积压缓冲区内，将进行**部分重同步**——这正是 PSYNC2 双复制 ID 机制的用武之地 。

**④ 更新配置**

领头 Sentinel 将新主的地址更新到所有 Sentinel 的本地配置，并通过 Pub/Sub 频道 `__sentinel__:hello` 广播配置变更 。

**⑤ 旧主的处理**

如果旧主重新上线，Sentinel 会向它发送 `REPLICAOF` 命令，使其成为新主的从服务器。**旧主上的数据会被新主的 RDB 全覆盖**——这意味着旧主在"失联期间"接收到的任何写命令都会丢失。

**`parallel-syncs` 参数**：

```
sentinel parallel-syncs mymaster 1
```

控制故障转移后**同时**向新主同步的从服务器数量：

- 设为 1：从服务器逐个同步，对主服务器压力小，但总耗时长
- 设为更大值：同步快，但可能压垮新主的网络和 CPU

生产环境推荐值：**1**（保守）或 **2**（平衡）。

**故障转移的完整时序图**​ ：

```
时间轴 →
                                                       
Sentinel A: ──PING──► ──PING──► [SDOWN] ──is-master-down─► 
                                                      │
Sentinel B: ──PING──► ──PING──► [SDOWN] ◄──is-master-down─┤
                                                      │
Sentinel C: ──PING──► ──PING──► [SDOWN]               │
                                                      │
                                           [ODOWN, quorum reached]
                                                      │
                                          ┌───────────┴───────────┐
                                          ▼                       ▼
                                Sentinel A 发起选举       Sentinel B/C 投票
                                          │                       │
                                          ▼                       │
                                Sentinel A 获得多数派票           │
                                          │                       │
                                          ▼                       │
                                Sentinel A 成为 Leader            │
                                          │                       │
                                          ▼                       │
                                选择最优从服务器（Replica2）       │
                                          │                       │
                                          ▼                       │
                                REPLICAOF NO ONE → Replica2       │
                                          │                       │
                                          ▼                       │
                                REPLICAOF new_master → 其他从服务器│
                                          │                       │
                                          ▼                       │
                                更新所有 Sentinel 的配置          │
                                          │                       │
                                          ▼                       │
                                客户端通过 SENTINEL get-master-addr-by-name
                                获取新主地址，重新连接
```

> ⚠️ **工业警示**：故障转移期间的"数据丢失窗口"
> 
> 由于 Redis 复制是异步的，主服务器在挂掉之前可能已经执行了一些写命令但尚未传播到从服务器。这些命令在故障转移后会**永久丢失**。丢失的数据量取决于：
> 
> - 主服务器挂掉前瞬间写入的速率
> - 从服务器的复制延迟
> - 故障转移的总耗时（通常 5-30 秒）
> 
> 如果需要更强的数据安全性，可以使用：
> 
> ```
> min-replicas-to-write 2
> min-replicas-max-lag 10
> ```
> 
> 这样主服务器只有在"至少有 2 个从服务器，且复制延迟不超过 10 秒"时才接受写命令。这实质上是用"可用性"换"一致性"——主服务器在从服务器跟不上时会拒绝写入，避免数据丢失。

### 16.10 重点回顾

1. **Sentinel 是一个运行在特殊模式下的 Redis 实例**，通过 `--sentinel` 参数启动
2. **Sentinel 是分布式的**：至少需要 3 个 Sentinel 实例才能生产部署
3. **双层下线判定**：SDOWN（单 Sentinel 判定）→ ODOWN（quorum 个 Sentinel 共同判定）
4. **quorum 只用于判定下线，故障转移需要多数派 Sentinel 选举领头 Sentinel**
5. **领头 Sentinel 选举采用 Raft 风格算法**：epoch + 多数派投票 + 先到先得
6. **故障转移流程**：选择最优从服务器 → REPLICAOF NO ONE → 其他从服务器复制新主 → 更新配置
7. **PSYNC2 让故障转移更高效**：其他从服务器可以通过 replid2 对新主进行部分重同步
8. **Sentinel 是客户端的服务发现源**：客户端通过 `SENTINEL get-master-addr-by-name` 获取当前主服务器地址
9. **Redis 复制是异步的，故障转移存在数据丢失窗口**

### 洞见一：复制的本质是"状态机复制"的简化版

分布式系统中"让多台机器状态一致"的经典方案是 **State Machine Replication**：所有节点从同一个初始状态出发，按相同顺序执行相同的命令序列，最终状态必然一致 。Redis 复制正是这个思想的应用：

- **初始状态**：从库通过 RDB 全量同步获得主库的快照（初始状态）
- **命令序列**：主库执行的每个写命令通过 RESP 协议传播给从库
- **执行顺序**：从库按接收顺序执行命令，保证与主库一致

**但 Redis 复制是"异步的状态机复制"**——主库执行命令后立即返回客户端，之后再传播给从库。这与 **Raft/Paxos 等强一致协议**形成鲜明对比：

|维度|Redis 复制|Raft/Paxos|
|---|---|---|
|一致性模型|最终一致（异步）|强一致（同步多数派）|
|写入延迟|极低（只写主库）|较高（需等待多数派 ack）|
|故障转移数据丢失|可能丢失（丢失窗口 = 复制延迟）|不丢失（已提交的不丢）|
|吞吐量|极高|受限于网络 RTT|
|适用场景|缓存、会话、排行榜|金融交易、账本|

> 💡 **第一性原理洞见**：Redis 选择"异步复制"而非"同步强一致"，是**在 CAP 定理框架下的一次明确取舍**——**优先保证 A（可用性）和 P（分区容忍），牺牲 C（强一致性）**。这不是 Redis 做不到强一致，而是 Redis 的定位是"高速缓存 + 轻量数据库"，它的用户愿意用"少量数据丢失"换取"毫秒级响应"和"极高吞吐"。
> 
> 更深层的洞见是：**分布式系统的"一致性"不是非黑即白的，而是一个谱系**。Redis 通过 `min-replicas-to-write` / `min-replicas-max-lag` 提供了"可调一致性"——你可以让主库在"至少有 N 个从库在 M 秒内跟上"时才接受写入，从而在"可用性"和"一致性"之间滑动调节。这是工程务实主义的体现：**不给用户一个死板的"一致/不一致"开关，而是给一个旋钮，让用户根据自己的业务场景调节**。

### 洞见二：PSYNC2 的双复制 ID 是"时间线分支"的优雅建模

PSYNC2 引入 `replid + replid2` 的动机，本质上是在解决一个分布式系统中的经典难题：**"当主库切换后，从库如何证明自己曾经和旧主库处于同一时间线上？"**

类比 Git 的分支模型：

- 每次主库切换 = 创建一个新分支（新 replid）
- 旧分支的 ID 被保留为 replid2（就像 Git 的 `HEAD@{1}` 记录上一次 HEAD）
- 从库拿着旧分支的 ID 来请求同步 = "我之前在旧分支上，现在想加入新分支"

**Git 的 reflog 和 Redis 的 replid2 是同一个思想**：保留"上一个时间线的标识"，让"曾经一致"的节点在新时间线上仍能找到共同点，从而避免全量同步 。

> 💡 **创新联想**：如果把这套思想进一步推广，Redis 的复制 ID 完全可以演化为一个**有向无环图（DAG）**——每个从库在部分同步时不仅发送自己的 replid，还发送一个"已知 replid 集合"。主库在这个集合中寻找与自己的 replid/replid2 的交集，从而支持更复杂的拓扑（如多主合并、双向复制）。虽然 Redis 目前没有走向这条路线（它坚持单主模型），但 PSYNC2 的双 ID 机制已经为这种演化埋下了伏笔。这是"最小可行设计"的智慧——**只为解决当前问题引入最小的概念（两个 ID），但留下扩展空间**。

### 洞见三：Sentinel 是"用 Redis 原语实现的分布式共识系统"

Sentinel 最精妙的地方在于——**它几乎不引入任何新协议，全部复用 Redis 已有的原语**：

|Sentinel 功能|复用的 Redis 原语|
|---|---|
|发现其他 Sentinel|Pub/Sub（`__sentinel__:hello` 频道）|
|检测节点存活|PING 命令|
|获取主/从信息|INFO 命令|
|传播配置变更|PUBLISH 命令|
|客户端服务发现|`SENTINEL get-master-addr-by-name` 命令|
|领导者选举|`SENTINEL is-master-down-by-addr` 命令 + epoch|

**这意味着 Sentinel 本身就是一个"Redis 客户端"**——它用 Redis 的命令和数据结构完成了分布式共识、故障检测、配置管理的一切工作。这种设计带来的好处是：

1. **极简实现**：不需要引入 ZooKeeper、etcd 等外部协调服务
2. **运维简单**：Sentinel 就是 Redis 进程，运维团队已经熟悉
3. **自包含**：Redis 集群的高可用不依赖任何外部系统

> ⚠️ **但这也是 Sentinel 的局限所在**：因为 Sentinel 复用 Redis 的单线程事件循环模型，当 Sentinel 数量增多、监控的 Redis 实例增多时，Sentinel 本身的 PING/INFO/PUBLISH 开销会增大。在超大规模部署（数百个 Redis 实例）中，Sentinel 的"全连接网格"（每个 Sentinel 与其他所有 Sentinel 都建立连接）会带来 O(N²) 的连接数增长，这时往往需要转向 **Redis Cluster + 外部编排（如 Kubernetes Operator）**​ 的方案。

### 洞见四："故障转移"的本质是"共识 + 状态机转换"

把 Sentinel 的故障转移拆解成分布式系统的标准组件：

```
故障检测 (Failure Detection)
    = 分布式系统中的"故障检测器"(Failure Detector)
    = 每个 Sentinel 运行一个本地的 Φ-Accrual 风格的检测器
    = SDOWN → ODOWN 的升级是"多数派投票"的故障判定
        ↓
领导者选举 (Leader Election)
    = Raft 风格的 epoch + 多数派投票
    = 确保"只有一个 Sentinel 执行故障转移"
        ↓
成员变更 (Membership Change)
    = 从库集合重新配置 (reconfiguration)
    = 旧主降级为从库，新主上位
    = 通过 epoch 确保配置变更的线性一致性
```

**这套流程几乎就是 Raft 协议的"浓缩版"**：Raft 用"领导人选举 + 日志复制 + 成员变更"三个子协议保证一致性；Sentinel 用"ODOWN 判定 + Leader 选举 + REPLICAOF 重配置"三个步骤实现高可用。**两者解决的是同一个问题——"分布式系统中的节点故障如何自动恢复"——只是 Raft 追求强一致，Sentinel 追求高可用**。

> 💡 **工程哲学洞见**：当你在设计一个分布式系统时，"故障检测"、"领导者选举"、"成员变更"是三个绕不开的子问题。Redis Sentinel 给出了一个"够用就好"的实现——不追求理论上的完美（比如它不保证故障转移的线性一致性，在网络分区极端情况下可能出现脑裂），但它在"绝大多数正常运营场景下"工作得足够好，且实现极其简洁。**这是工业级系统的典型特征：不追求学术上的最优，而追求"在真实工作负载下够用且可靠"**。

### 洞见五：异步复制的"丢失窗口"是 Redis 高可用的根本约束

由于 Redis 复制是异步的，主库宕机时最近一批未传播的写命令会丢失。这个"丢失窗口"的大小取决于：

```
丢失窗口 ≈ 主库到从库的复制延迟 + Sentinel 故障转移耗时
```

其中：

- **复制延迟**：取决于网络 RTT 和写入速率，通常毫秒到秒级
- **故障转移耗时**：包括 SDOWN 检测（`down-after-milliseconds`）+ ODOWN 协商 + 领导者选举 + 从库提升，通常 5-30 秒

**这意味着 Redis Sentinel 方案的 RPO（Recovery Point Objective，允许丢失的数据量）通常在秒级到十秒级**。对于缓存、会话、排行榜等场景，这是完全可以接受的；但对于金融交易、订单状态等场景，这可能不可接受。

**降低丢失窗口的工程手段**：

```
# 方案1: 提高复制的"同步性"
min-replicas-to-write 2
min-replicas-max-lag 10
# 代价: 主库在从库跟不上时会拒绝写入 (可用性下降)

# 方案2: 加快故障检测
sentinel down-after-milliseconds mymaster 5000
# 代价: 网络抖动可能触发误判

# 方案3: 减少故障转移耗时
sentinel failover-timeout mymaster 30000
sentinel parallel-syncs mymaster 2
```

> 📌 **创新联想**：如果业务要求"零丢失"，单纯的 Redis Sentinel 是不够的。业界常见的组合方案是：
> 
> - **Redis + AOF `appendfsync always`**：主库每个写命令都 fsync，最大限度保证主库数据不丢；但主库宕机后从库仍可能丢失少量未传播命令
> - **Redis Enterprise / AWS ElastiCache**：商业方案通过"多副本同步复制"实现更强的一致性
> - **改用支持强一致的存储**：如 etcd（Raft）、TiKV（Raft + 多副本同步）、或 PostgreSQL（同步复制）
> 
> **关键洞察：没有"又快又强一致又高可用"的免费午餐**。选择 Redis 就要接受它的异步复制模型，在架构层面为"可能丢失少量数据"做好准备（如重要操作同时写消息队列做补偿、客户端做重试与幂等）。

## 工业落地建议（第15~16章）

### 1. 复制拓扑的最佳实践

**推荐拓扑：星型 + 适度级联**

```
Master
       /   |   \
   Replica1 Replica2 Replica3   ← 第一层: 直连主库(用于故障转移候选)
                 |
            Replica3a            ← 第二层: 级联(减轻主库带宽)
```

- **第一层从库 2-3 个**：用于 Sentinel 故障转移的候选 + 读分担
- **读流量分散到从库**：用 `READONLY` 命令让从库处理读请求（Redis 3.0+ 从库默认只读）
- **避免过深级联**：级联超过 2 层会导致复制延迟累积

**关键配置**：

```
# redis.conf (主库)
repl-diskless-sync yes              # 无盘复制, 适合网络带宽充足场景
repl-diskless-sync-delay 5          # 等待更多从库加入同一波同步
repl-backlog-size 256mb             # 根据写入速率 × 容忍断线时长计算
repl-backlog-ttl 3600               # 无从库时保留积压缓冲区1小时
repl-disable-tcp-nodelay no         # 低延迟优先(设为 yes 可节省带宽)
min-replicas-to-write 1             # 至少1个从库跟上才接受写入(按需开启)
min-replicas-max-lag 10
```

### 2. Sentinel 部署的硬性要求

**最少 3 个 Sentinel，跨可用区部署**：

```
可用区 A: Sentinel1 + Redis Master
可用区 B: Sentinel2 + Redis Replica1
可用区 C: Sentinel3 + Redis Replica2
```

**为什么必须 3 个且跨 AZ**：

- 2 个 Sentinel 无法形成"多数派"——任何一个挂了就只剩 1 票，达不到多数派
- 跨 AZ 部署避免单个 AZ 故障导致"Sentinel 全灭 + 无法故障转移"
- 3 个 Sentinel 的 quorum 设为 2，容忍 1 个 Sentinel 故障

**Sentinel 配置模板**：

```
port 26379
daemonize yes
pidfile "/var/run/redis-sentinel.pid"
logfile "/var/log/redis/sentinel.log"

sentinel monitor mymaster 10.0.0.10 6379 2
sentinel auth-pass mymaster "strong_password"
sentinel down-after-milliseconds mymaster 5000
sentinel failover-timeout mymaster 60000
sentinel parallel-syncs mymaster 1
sentinel resolve-hostnames yes       # Redis 6.2+ 支持主机名
```

**务必设置 `requirepass` 和 `sentinel auth-pass`**：Sentinel 之间的通信和 Sentinel 对 Redis 的访问都需要认证，否则存在未授权访问风险 。

### 3. 客户端必须集成 Sentinel 感知

**反模式**：客户端硬编码主库 IP。

```
# ❌ 错误: 主库 IP 写死, 故障转移后客户端连错节点
redis = Redis(host="10.0.0.10", port=6379)
```

**正确做法**：通过 Sentinel 动态发现主库。

```
# ✅ 正确: 通过 Sentinel 获取当前主库地址
from redis.sentinel import Sentinel
sentinel = Sentinel([("sentinel1", 26379),
                     ("sentinel2", 26379),
                     ("sentinel3", 26379)], socket_timeout=0.5)
master = sentinel.master_for("mymaster", password="strong_password")
master.set("foo", "bar")  # 自动路由到当前主库
```

主流客户端库都内置了 Sentinel 支持（redis-py、Jedis、Lettuce、StackExchange.Redis 等）。**客户端在收到 `-READONLY` 错误时应自动重试获取新主地址**。

### 4. 监控复制与 Sentinel 健康

**复制健康指标**：

```
redis-cli INFO replication
# 关注:
# role:master / slave
# connected_slaves:N          ← 从库数量
# slave0:ip=...,state=online,offset=...,lag=N  ← lag 应 < 1
# master_repl_offset:12345    ← 主库当前偏移
# repl_backlog_active:1
# repl_backlog_size:268435456

redis-cli INFO stats
# 关注:
# sync_full:0          ← 全量同步次数(应接近0, 非零说明有断线重连)
# sync_partial_ok:N    ← 部分同步成功次数
# sync_partial_err:N   ← 部分同步失败次数(过高说明 backlog 太小)
```

**Sentinel 健康指标**：

```
redis-cli -p 26379 SENTINEL masters
# 查看所有监控的主库及其状态

redis-cli -p 26379 SENTINEL master mymaster
# 关注:
# num-other-sentinels:2    ← 应等于 Sentinel 总数-1
# flags:master,running     ← 不应出现 s_down 或 o_down
# quorum:2
# failover-time:0          ← 最近一次故障转移耗时

redis-cli -p 26379 SENTINEL sentinels mymaster
# 列出所有已知 Sentinel 及其状态
```

**关键告警规则**：

- `sync_partial_err` 持续增长 → `repl-backlog-size` 不足，调大
- 从库 `lag > 5` → 网络或主库写入压力过大
- Sentinel `num-other-sentinels` 低于预期 → 有 Sentinel 失联
- 主库 flags 出现 `s_down` → 单个 Sentinel 判定下线，需关注是否将升级为 `o_down`

### 5. 故障演练：定期验证高可用

**不要等到真出事才第一次跑故障转移**。定期演练：

```
# 手动触发故障转移(优雅, 不杀进程)
redis-cli -p 26379 SENTINEL failover mymaster

# 观察故障转移过程

### 6. 版本演进的工程建议

|特性|最低版本|建议|
|---|---|---|
|PSYNC1（部分重同步）|Redis 2.8|所有生产环境最低基线|
|PSYNC2（故障转移后部分同步）|Redis 4.0|**强烈建议 4.0+**，大幅减少故障转移后的全量同步|

## 这两章对全书架构的意义

第15~16章完成了从"单机数据库"到"分布式高可用数据库"的跃迁。至此，Redis 的全部核心机制已经呈现在你面前：

```
┌──────────────────────────────────────────────────────────────┐
│                     用户视角                                    │
│          SET / GET / HSET / ZADD / SENTINEL ...               │
├──────────────────────────────────────────────────────────────┤
│                   对象系统 + 数据结构                            │
│          (第2~8章: SDS/dict/skiplist/listpack/robj)           │
├──────────────────────────────────────────────────────────────┤
│                  单机数据库实现                                  │
│     (第9~14章: 键空间/过期/RDB/AOF/事件/客户端/服务器)          │
├──────────────────────────────────────────────────────────────┤
│                 多机数据库实现  ← 本篇                          │
│  ┌────────────────────────────────────────────────────────┐  │
│  │  复制 (第15章)                                          │  │
│  │  PSYNC: replid+offset+backlog → 部分重同步              │  │
│  │  异步命令传播 + 双向心跳                                 │  │
│  ├────────────────────────────────────────────────────────┤  │
│  │  Sentinel (第16章)                                      │  │
│  │  SDOWN → ODOWN → Raft风格Leader选举 → 故障转移           │  │
│  │  用 Redis 原语(PING/INFO/PUBSUB)实现分布式共识           │  │
│  └────────────────────────────────────────────────────────┘  │
├──────────────────────────────────────────────────────────────┤
│               事件驱动引擎 (第12章)                              │
│          aeEventLoop + epoll/kqueue + serverCron              │
└──────────────────────────────────────────────────────────────┘
```

**Redis 高可用设计的五个第一性原理（续前篇）**：

1. **异步优先，强一致可选**：默认异步复制追求极致性能，通过 `min-replicas-to-write` 提供"可调一致性"旋钮
2. **部分同步优于全量同步**：用"空间（backlog）换时间（恢复速度）"，PSYNC2 进一步把这套逻辑延伸到故障转移场景
3. **共识最小化**：Sentinel 只解决"该不该故障转移"和"谁来执行"两个共识问题，其余交给 Redis 原语
4. **自包含优于外部依赖**：不引入 ZooKeeper/etcd，用 Redis 自身实现高可用，降低运维复杂度
5. **演练优于侥幸**：高可用系统必须定期演练故障转移——"没演练过的故障转移方案等于没有"
