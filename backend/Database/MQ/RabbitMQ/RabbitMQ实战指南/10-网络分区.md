
第10章是 RabbitMQ 分布式本质的"照妖镜"——前面 9 章讲的集群、队列、流控，在正常网络下都不会暴露问题；**只有网络分区发生时，你才能看清 RabbitMQ 到底是不是一个真正的分布式系统**。朱忠华老师的书基于 RabbitMQ 3.x 的 Mnesia 时代，而今天（4.3.0+）Mnesia 已被彻底移除，分区处理策略也成为历史。所以这一章的读书笔记，我会用**官方最新文档校正书本的滞后口径**，帮你建立"旧版知识（3.x 及以前）→ 现代语义（4.3.0+）"的双层认知。

> 💡 **核心洞察**：网络分区的第一性原理可以归纳为一句话——**网络分区本质上是"共识的中断"**。分布式系统的所有复杂性，都源于"当网络不再可靠时，如何让一群节点对'什么是真相'达成一致"。RabbitMQ 的演进史，就是从"用运维策略修补 Mnesia 的分区弱点"到"用 Raft 共识算法从根本上解决分区问题"的历史。

## 10.1 网络分区的意义

**第一性原理视角**：在分布式系统中，网络分区不是"异常"，而是"常态"。根据 CAP 定理，当网络分区发生时（P），系统必须在一致性（C）和可用性（A）之间二选一。RabbitMQ 的不同版本、不同队列类型、不同配置，本质上都是在 C 和 A 之间做不同的权衡。

**为什么网络分区在 RabbitMQ 中特别致命**？

RabbitMQ 集群的节点间通过 Erlang Distribution 互相通信，共享元数据。当网络分区发生时：

- 分区两侧都认为对方"死了"
- 两侧独立演进——队列可以被独立创建/删除，消息独立堆积
- **如果不加处理，两侧的状态会迅速分叉（diverge）**，这就是著名的"脑裂（split-brain）"
- 当网络恢复时，两侧的状态无法自动合并——这就是网络分区最可怕的后果

**版本演进的关键事实**：

- **RabbitMQ 4.3.0 之前**（书中口径）：使用 Mnesia 作为元数据存储，提供 `ignore`、`pause_minority`、`pause_if_all_down`、`autoheal` 四种分区处理策略
- **RabbitMQ 4.3.0 及以后**（现代口径）：Mnesia 被彻底移除，元数据存储在基于 Raft 的 Khepri 中，**所有分区处理策略也被移除**——因为 Raft 本身就定义了明确的分区恢复语义，不需要也不允许配置

> 💡 **工业洞见**：网络分区不是一个"需要处理的故障"，而是一个"需要用数学保证正确性的分布式系统基本事实"。旧版 RabbitMQ 试图用运维策略（pause-minority、autoheal 等）来"修补" Mnesia 在分区下的弱点；现代 RabbitMQ 直接用 Raft 共识算法，让分区行为成为数学上可证明的——多数派继续工作，少数派不能提交，恢复时通过日志复制追上。

## 10.2 网络分区的判定

**判定机制**（官方文档明确）：

RabbitMQ 节点默认**每 60 秒**检测一次对等节点的可达性。如果一个节点在 60 秒内无法联系到另一个节点，它就认为该节点已宕机。当两个节点恢复联系时，双方都认为自己"刚才以为对方死了"——这时判定为网络分区发生。

日志中的典型判定记录：

```
2020-05-18 06:55:37.324 [error] Mnesia(rabbit@warp10): ** ERROR ** 
mnesia_event got {inconsistent_database, running_partitioned_network, rabbit@hostname2}
```

**三种发现网络分区的方式**：

1. **Server Log**：节点日志会记录分区事件和 Raft 领导者选举活动
2. **CLI 命令**：`rabbitmq-diagnostics cluster_status` 会在 `Network Partitions` 部分列出不可达节点
    
    ```
    rabbitmq-diagnostics cluster_status
    # => Network Partitions
    # => Node rabbit@node3 cannot communicate with node rabbit@node1
    # => Node rabbit@node3 cannot communicate with node rabbit@node2
    ```
    
3. **HTTP API / 管理界面**：`GET /api/nodes` 的每个节点信息中包含 `partitions` 字段；管理界面 Overview 页会显示红色警告横幅

**Raft 时代的新工具**（4.3.0+ 新增）：

```
# 查看 quorum queue 的 leader 和 followers 状态
rabbitmq-queues quorum_status

# 查看 stream 的 leader 和副本状态
rabbitmq-streams stream_status

# 检查目标节点宕机是否会让任何 quorum queue 或 stream 失去在线多数派
rabbitmq-diagnostics check_if_node_is_quorum_critical
```

> 💡 **洞见**：判定的本质不是"检测网络断了"，而是"检测共识失败了"。在 Raft 时代，除了传统的 60 秒心跳检测，**Raft 组件（Khepri、Quorum Queue、Stream）还使用自适应故障检测器（adaptive failure detector）**，它能比心跳机制更早地发现对等节点不可用，同时对延迟抖动的敏感度更低。这意味着现代 RabbitMQ 对分区的"感知"更快、更准确。

**容易被忽视的分区诱因**：

- **虚拟机挂起/恢复**：整个 OS 被挂起（如笔记本合盖、VM 迁移）时，被挂起的节点不认为自己失败，但集群其他节点认为它失败了——这种分区是**非对称的**，对 pause-minority 模式有特殊影响
- **网络抖动 vs 网络分区**：短暂的网络抖动不应触发分区处理，RabbitMQ 的 60 秒阈值就是为了过滤瞬时抖动

## 10.3 网络分区的模拟

要理解分区，必须先能模拟分区。工业界常用的几种方法：

**① 防火墙规则模拟**（最常用）：

```
# 在 node3 上阻断与 node1、node2 的通信
iptables -A INPUT -s node1-ip -j DROP
iptables -A INPUT -s node2-ip -j DROP
iptables -A OUTPUT -d node1-ip -j DROP
iptables -A OUTPUT -d node2-ip -j DROP

# 恢复网络
iptables -F
```

**② 网络命名空间（Linux Network Namespace）**：

```
# 创建网络延迟和丢包
tc qdisc add dev eth0 root netem delay 1000ms loss 100%
```

**③ 虚拟机挂起**（模拟非对称分区）：

```
# 在 hypervisor 层面挂起 VM
virsh suspend rabbitmq-node3
```

**④ 云环境的"网络 ACL"或"安全组"**：

- AWS：修改 Security Group 规则阻断节点间 25672 端口
- K8s：使用 Network Policy 阻断 Pod 间通信

**⑤ RabbitMQ 自带的测试工具**：

```
# 模拟节点不可达（不推荐生产使用）
rabbitmqctl stop_app  # 模拟节点宕机
```

> ⚠ **工业警示**：模拟分区必须在**测试环境**进行，且必须有完整的恢复预案。曾经有团队在生产环境误操作 iptables 规则，本意是模拟分区测试监控告警，结果规则写错导致整个集群 60 秒后判定分区，触发 autoheal 重启了所有节点——造成了真实的服务中断。

**模拟分区的观察清单**：

1. 管理界面是否出现红色警告横幅
2. `rabbitmqctl cluster_status` 的 `Network Partitions` 部分
3. 节点日志中的 `inconsistent_database` 错误
4. Quorum Queue 的 leader 是否发生重新选举
5. 发布者是否收到 publisher confirm 的否定应答
6. 消费者是否收到重复投递的消息

## 10.4 网络分区的影响

这是本章最关键的"后果分析"环节。影响取决于队列类型和分区处理策略。

### 10.4.1 未配置镜像（Classic Queue）

**旧版（Mnesia 时代）行为**：

在 `ignore` 策略下（默认），分区两侧独立运行：

- 队列可以在两侧独立创建/删除
- 消息在两侧独立堆积
- 消费者在两侧独立消费
- **当分区愈合时，两侧状态无法合并——一侧的状态会被丢弃**

> ⚠️ **最危险的场景**：如果分区期间两侧都在向同一个 classic queue 发布消息，愈合时**一侧的消息会静默消失**——没有错误、没有告警、没有日志记录哪些消息消失了。这是 ignore 策略最可怕的后果。

**现代（4.3.0+ Raft 时代）行为**：

Classic Queue 不进行复制，所以网络分区对 Classic Queue 的影响是**节点级别的**：

- 队列所在节点如果处于少数派分区，该队列不可用
- 队列所在节点如果处于多数派分区，该队列继续正常工作
- 没有"状态分叉"问题，因为队列数据只在单个节点上

但元数据（exchange、binding、用户、vhost 等）现在存储在 Khepri（Raft）中，遵循 Raft 语义：

- 多数派分区可以继续修改元数据
- 少数派分区的元数据修改会超时失败

### 10.4.2 已配置镜像（Mirrored Queue → Quorum Queue）

**重要版本警示**：镜像队列在 RabbitMQ 4.0 中已被完全移除，取而代之的是 Quorum Queue 和 Stream。所以这一节在现代 RabbitMQ 中实际上讲的是 **Quorum Queue 在分区下的行为**。

**Quorum Queue 的 Raft 语义**（官方文档明确）：

对于 Quorum Queue 这个 Raft 集群，网络分区有三种关键场景：

**场景 1：Leader 所在节点断开**

- Raft 集群在多数派一侧触发新的 leader 选举
- 选举期间（通常几秒），写入操作被拒绝
- 等待 publisher confirm 的消息会收到**否定应答（negative acknowledgement）**
- 客户端操作被延迟，直到新 leader 被选出来
- 新 leader 继续接受写入，向 followers 复制状态，发送 publisher confirms
- **投递给消费者但尚未 ack 的消息会被重新入队，稍后由新 leader 重新投递——消费者可能收到重复消息**

**场景 2：Follower 所在节点断开**

- 如果断开后剩余 followers 仍能形成多数派，队列继续正常工作
- 如果断开后剩余节点不足多数派，**写入被拒绝**，队列只读

**场景 3：既非 leader 也非 follower 的节点断开**

- 对 Quorum Queue 无影响

**Stream 的行为类似**：基于 Raft，多数派继续工作，少数派副本停止进展。

> 💡 **工业洞见**：Quorum Queue 在分区下的行为可以用一句话概括——**"少数派拒写，多数派继续，愈合后追平"**。这就是 Raft 共识算法的威力：它把"网络分区怎么办"这个复杂的运维问题，变成了数学上可证明的"多数派可用"问题。对比之下，旧版镜像队列在分区下的行为"难以预测，某些情况下甚至可能丢失消息"——这也是它被废弃的根本原因。

**数据安全的真相**：

- **Classic Queue**：分区期间如果节点故障且消息未复制到任何其他节点，**消息可能丢失**
- **Quorum Queue**：只要多数派节点存活，消息**不丢**；少数派节点的消息在愈合后通过 Raft 日志复制追平
- **Stream**：同 Quorum Queue，基于 Raft 复制

## 10.5 手动处理网络分区

当分区发生时（特别是使用 `ignore` 策略或 4.3.0+ 的 Raft 时代），手动恢复是必要的。

**核心原则**（官方文档明确）：**首先选择一个你最信任的分区，它将作为系统状态（schema、messages）的权威**。

**手动恢复的标准操作流程**：

1. **评估分区状态**：
    
    ```
    # 在所有节点上检查集群状态
    rabbitmqctl cluster_status
    
    # 检查 quorum queue 状态
    rabbitmq-queues quorum_status
    
    # 检查节点是否为 quorum-critical
    rabbitmq-diagnostics check_if_node_is_quorum_critical
    ```
    
2. **选择可信分区（Trusted Partition）**：通常是具有最多节点、最多消息、或最重要业务数据的那一侧
3. **停止非可信分区中的节点**：
    
    ```
    # 在非可信分区的节点上执行
    rabbitmqctl stop_app
    ```
    
4. **重置并重新加入集群**：
    
    ```
    # 警告：reset 会清除该节点所有本地数据
    rabbitmqctl reset
    rabbitmqctl join_cluster rabbit@trusted-node
    rabbitmqctl start_app
    ```
    
5. **验证集群状态**：
    
    ```
    rabbitmqctl cluster_status
    # 确认 Network Partitions 部分为 (none)
    ```
    

**4.3.0+ Raft 时代的简化恢复**：

- 少数派节点自动停止进展（不能提交元数据变更）
- 网络恢复后，少数派节点自动通过 Raft 日志复制追平状态
- **通常不需要手动 reset**，节点重连后会自动识别新 leader 并作为 follower 追平

> ⚠ **工业警示**：`rabbitmqctl reset` 是不可逆的破坏性操作。在执行前必须确认：
> 
> 1. 该节点上的 quorum queue/stream 副本在其他节点有完整副本
> 2. 该节点不是 quorum-critical 的（否则其他队列可能失去多数派）
> 3. 已选择的可信分区确实拥有最新的业务数据

**手动恢复的工业级检查清单**：

- [ ] 确认分区范围（`cluster_status`）
- [ ] 确认哪个分区是可信分区（节点数、消息量、业务重要性）
- [ ] 确认 quorum-critical 节点（`check_if_node_is_quorum_critical`）
- [ ] 停止非可信分区节点（`stop_app`）
- [ ] 重置并重新加入（`reset` + `join_cluster`）
- [ ] 验证队列状态和数据完整性
- [ ] 检查发布者和消费者连接是否恢复
- [ ] 监控后续 10-30 分钟，确保没有二次分区

## 10.6 自动处理网络分区

> ⚠️ **重要版本警示**：以下四种策略**仅适用于 RabbitMQ 4.2 及以前版本**。从 **RabbitMQ 4.3.0 开始，这些策略被完全移除**——因为 Khepri 基于 Raft，分区恢复遵循 Raft 语义，不再需要也不允许配置。本节内容作为"历史知识"和"老版本运维参考"保留。

### 10.6.1 pause-minority 模式

**机制**：RabbitMQ 自动暂停那些判定自己处于少数派（节点数 ≤ 总节点数的一半）的节点。

**CAP 取舍**：选择分区容忍（P）而非可用性（A）——这是 CP 系统的典型选择。

**行为详解**：

- 分区发生时，少数派节点自动暂停 RabbitMQ 应用（Erlang VM 不关闭，类似执行了 `rabbitmqctl stop_app`）
- 少数派节点每秒检测一次是否能连通多数派
- 网络恢复后，少数派节点自动 `start_app` 重新加入集群

**配置**：

```
cluster_partition_handling = pause_minority
```

**关键限制**：

- **2 节点集群不适合**：任何单节点故障都会导致两个节点都判定自己为少数派而被暂停，整个集群不可用
- **偶数节点集群风险**：平局时所有节点都会被暂停
- **非对称分区（VM 挂起）的特殊影响**：被挂起的节点不认为自己失败，但集群其他节点认为它失败了，可能导致不可预期的暂停行为

> 💡 **工业洞见**：pause-minority 是 3.x 时代的"最佳实践"，它的本质是"用可用性换取一致性"。在 4.3.0+ 的 Raft 时代，这种行为**已成为 Raft 算法的内置语义**——少数派不能提交，多数派继续工作。从这个角度看，Raft 时代的 RabbitMQ 天然就是 pause-minority 模式。

### 10.6.2 pause-if-all-down 模式

**机制**：只有当配置的"参考节点列表"中所有节点都不可达时，才暂停当前节点。

**与 pause-minority 的关键差异**：允许管理员**显式指定优先级**，而不是依赖节点数。

**典型场景**：

```
集群构成：机架 A 有 2 个节点，机架 B 有 2 个节点
机架间链路断开

pause-minority 模式：所有 4 个节点都被暂停（因为两侧都是 2 节点，平局）
pause-if-all-down 模式：如果管理员把机架 A 的 2 个节点列为参考节点，
                    则只有机架 B 的节点被暂停，机架 A 继续服务
```

**配置**：

```
cluster_partition_handling = pause_if_all_down
cluster_partition_handling.pause_if_all_down.nodes.1 = rabbit@rack-a-node1
cluster_partition_handling.pause_if_all_down.nodes.2 = rabbit@rack-a-node2
cluster_partition_handling.pause_if_all_down.recover = ignore
```

**附加参数 `recover`**：指示如何从分区恢复，可选 `ignore` 或 `autoheal`

> ⚠ **陷阱**：如果列出的参考节点被分割在分区的两侧，则没有节点会被暂停——这时必须依靠 `recover` 参数来决定恢复策略。

### 10.6.3 autoheal 模式

**机制**：分区发生时不做任何事；**分区愈合后**，RabbitMQ 自动决定"胜者分区"，并**重启所有不在胜者分区中的节点**。

**胜者分区的选择逻辑**：

1. 客户端连接数最多的分区获胜
2. 如果连接数平局，节点数最多的分区获胜
3. 如果仍平局，以未指定方式选择其中一个

**配置**：

```
cluster_partition_handling = autoheal
```

**CAP 取舍**：选择可用性（A）而非一致性（C）——分区期间两侧都继续服务，愈合后通过重启失败侧来合并状态。

**关键风险**：

- 重启节点上的**非复制消息会丢失**（classic queue 中未同步到其他节点的消息）
- 整个集群在 autoheal 瞬间会有短暂不可用
- 在 2 节点集群中表现相对较好（一个重启，一个继续）

> 💡 **工业洞见**：autoheal 的本质是"用数据一致性换取分区期间的可用性"。它适合这种场景：分区期间业务必须持续运行，且消息丢失的代价可以接受。但要注意——**如果使用 Quorum Queue，autoheal 的数据丢失风险大大降低**，因为 Quorum Queue 的消息本身就是 Raft 复制的，重启节点会通过 Raft 日志追平。

### 10.6.4 挑选哪种模式

**3.x 时代的选型矩阵**：

|策略|分区期间可用性|数据安全性|适用场景|
|---|---|---|---|
|ignore|两侧都可用|**最差**（状态分叉）|从不用于生产|
|pause-minority|多数派可用|最好|**3+ 节点集群的生产首选**​|
|pause-if-all-down|取决于配置|好|跨机架/跨 AZ 部署，需要显式控制优先级|
|autoheal|两侧都可用|差（非复制消息丢失）|2 节点集群，或可用性优先于一致性|

**4.3.0+ 时代的现状**：

- 所有分区处理策略配置项**不再起作用**
- RabbitMQ 强制使用基于 Raft 的多数派共识
- 集群只在多数派节点在线时保持可用
- 元数据、Quorum Queue、Stream 都遵循相同的 Raft 语义

**现代工业建议**：

1. **使用 3/5/7 奇数节点集群**——确保任何单节点故障都不会导致集群失去多数派
2. **业务关键消息一律使用 Quorum Queue**——获得 Raft 复制的可靠性
3. **瞬时/非关键消息使用 Classic Queue**——但要接受"节点故障可能丢消息"的现实
4. **跨 AZ 部署时，确保每个 AZ 的节点数不超过总节点数的一半**——避免"平局"导致整个集群不可用
5. **监控 `rabbitmq-diagnostics check_if_node_is_quorum_critical`**——在节点维护/升级前必查

> 💡 **第一性原理总结**：无论哪个版本、哪种策略，网络分区的处理本质都是在回答一个问题——**"当网络不可靠时，谁有权决定真相？"**
> 
> - ignore：每个人都可以（灾难）
> - pause-minority：多数派可以（CP 系统）
> - autoheal：连接最多的可以（AP 系统）
> - Raft（4.3.0+）：数学上的多数派可以（CP 系统，但更严格、更可证明）

## 10.7 案例：多分区情形

多分区（3 个或更多分区）是网络分区中最复杂的场景，尤其在网状网络拓扑中。

**典型多分区场景**：

```
3 节点集群：node1、node2、node3
网络故障导致：
  - node1 与 node2、node3 隔离
  - node2 与 node3 仍可通信

结果：形成两个分区
  分区 A：node1（孤立）
  分区 B：node2 + node3（多数派）
```

**在 3.x pause-minority 模式下**：

- node1 检测到自己无法连通多数派（≤1/3），自动暂停
- node2 和 node3 继续正常工作
- 网络恢复后，node1 自动重新加入

**在 4.3.0+ Raft 时代**：

- node1 上的 Khepri 元数据修改超时（无法获得多数派确认）
- node1 上的 Quorum Queue 如果是 leader 在 node1，则触发 leader 选举，node2 或 node3 成为新 leader
- node1 上的 Quorum Queue 如果是 follower，则停止进展（多数派不可达）
- 网络恢复后，node1 通过 Raft 日志复制自动追平

**更复杂的三分区场景**：

```
5 节点集群跨 3 个 AZ：
  AZ1: node1, node2
  AZ2: node3, node4
  AZ3: node5

网络故障：AZ1 与 AZ2、AZ3 隔离；AZ2 与 AZ3 隔离

形成三个分区：
  分区 A：node1 + node2（2 节点）
  分区 B：node3 + node4（2 节点）
  分区 C：node5（1 节点）
```

**在 Raft 时代的行为**：

- 没有任何分区拥有多数派（需要 ≥3 节点）
- **整个集群不可用**——所有 Quorum Queue 都无法提交写入
- 所有 Khepri 元数据修改都超时
- 这是 Raft 系统的"正确行为"——宁可完全不可用，也不能冒数据不一致的风险

**工业级应对策略**：

1. **预防胜于治疗**：网络架构设计时必须确保"多数派分区"的存在性
2. **跨 AZ 部署的节点分配**：3 个 AZ 各部署 1 个节点（共 3 节点）优于 2+2+1（共 5 节点），因为前者任何单 AZ 故障都不会导致失去多数派
3. **网络冗余**：使用多条网络路径，避免单点网络故障
4. **监控和告警**：`check_if_node_is_quorum_critical` 应该在任何节点维护前执行
5. **快速网络恢复**：多分区的危害在于持续时间，网络恢复越快，影响越小

> ⚠ **血的教训**：某金融企业使用 2+2+1 的 5 节点跨 3 AZ 部署，认为这样"高可用"。结果一次网络故障导致 AZ1 与 AZ2/AZ3 隔离，同时 AZ2 与 AZ3 之间也出现问题——形成了 2+2+1 三个分区，没有任何分区拥有多数派（需要 3 节点），**整个集群完全不可用长达 40 分钟**，直到网络修复。正确做法是使用 1+1+1 的 3 节点部署，任何单 AZ 故障后仍保留 2 节点多数派。

## 10.8 小结

第10章表面是"网络故障处理"，实质是**RabbitMQ 分布式本质的终极考验——当网络不再可靠时，系统如何选择"一致性"还是"可用性"**：

```
┌──────────────────────────────────────────────────────────┐
│  RabbitMQ 4.2 及以前（Mnesia 时代）                         │
│  ├── ignore：默认，两侧独立运行，状态分叉（最危险）          │
│  ├── pause-minority：少数派暂停，CP 系统（生产推荐）         │
│  ├── pause-if-all-down：管理员控制优先级                    │
│  └── autoheal：愈合后重启失败侧，AP 系统                    │
├──────────────────────────────────────────────────────────┤
│  RabbitMQ 4.3.0+（Khepri/Raft 时代）                       │
│  ├── 分区处理策略被完全移除                                 │
│  ├── 元数据（Khepri）、Quorum Queue、Stream 都基于 Raft     │
│  ├── 多数派继续工作，少数派不能提交                         │
│  └── 恢复通过 Raft 日志复制自动完成                         │
└──────────────────────────────────────────────────────────┘
```

**本章最重要的三个第一性原理洞察**：

**1. 网络分区不是"异常"，而是分布式系统的"常态"**。根据 CAP 定理，当 P（分区）发生时，必须在 C（一致性）和 A（可用性）之间选择。RabbitMQ 的演进史，本质上是从"用运维策略在 C 和 A 之间打补丁"（Mnesia 时代的 4 种策略）到"用数学保证 C"（Raft 时代的 Khepri）的进化。理解了这一点，你就能明白为什么 4.3.0 要彻底移除分区处理策略——**因为 Raft 已经给出了唯一正确的分区语义，配置项反而会成为误导**。

**2. "ignore 策略"是生产环境的定时炸弹**。在 ignore 模式下，分区两侧独立运行，消息在两侧独立堆积。当分区愈合时，一侧的消息会**静默消失**——没有错误、没有告警、没有日志。这是整个 RabbitMQ 运维史上最危险的行为。4.3.0+ 的 Raft 时代从根本上消除了这个风险：少数派不能提交，所以不存在"状态分叉"的可能。

**3. 集群节点数必须是奇数，且要避免"平局"**。这是 Raft 系统的基本常识，但也是最常被违反的规则：

- **2 节点集群是反模式**：任何单节点故障都会导致失去多数派，整个集群不可用
- **跨 AZ 部署不要使用 2+2+1**：应该使用 1+1+1（3 节点）或 1+1+1+1+1（5 节点）
- **每个 AZ 的节点数不能超过总节点数的一半**：避免"平局"导致整个集群不可用
- **业务关键消息必须使用 Quorum Queue**：获得 Raft 复制的可靠性，分区期间少数派拒写，多数派继续，愈合后自动追平
