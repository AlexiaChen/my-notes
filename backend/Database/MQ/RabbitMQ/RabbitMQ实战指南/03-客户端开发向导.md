## 3.1 连接 RabbitMQ

### 核心机制

客户端通过 `ConnectionFactory` 设置主机、端口、虚拟主机、用户名密码等参数，调用 `newConnection()` 建立一条 TCP 连接；再通过 `conn.createChannel()` 在连接上开辟 Channel。

**默认参数速查**：用户名/密码 `guest/guest`（仅限本机）、虚拟主机 `/`、主机 `localhost`、端口 `5672`（TLS 用 `5671`）。

### 第一性原理洞察：为什么是"连接 + 信道"两层？

这是 AMQP 设计里最精妙也最容易被忽视的一点。

- **Connection 是 TCP 连接**：建立/断开成本很高（三次握手、TLS 协商等）。
- **Channel 是虚拟连接**：复用同一条 TCP，默认最多 2047 个，是所有 AMQP 命令的实际载体。

> 💡 **工业洞见**：Channel 是**非线程安全的**——RabbitMQ 官方明确警告不要在多线程间共享同一个 Channel 实例，并发发布会导致帧交错、双重确认甚至连接级异常。所以工业实践的心智模型是：
> 
> - **常规场景**：1 个 Connection + 每线程 1 个 Channel
> - **高吞吐场景**：多个 Connection（建议 ≤ CPU 核数 × 2）+ 每个 Connection 多个 Channel
> - **Connection 带宽利用率保持在 70% 以下**

另一个生产级细节：**给连接命名**。`factory.setClientProvidedName("order-service-prod")` 这类自定义名称会显示在 broker 日志和管理界面中——在拥有几十个微服务的生产环境里，这是排障时快速定位"这条连接是谁"的关键。

虚拟主机（vhost）这一层也值得单独点出：它是 broker 内部的**逻辑隔离单元**，不同 vhost 的 exchange/queue 不能互相绑定。默认 vhost 是 `/`。工业上建议**按业务域划分 vhost**（如 `/orders`、`/payments`），既保证安全隔离，又避免命名冲突。

## 3.2 使用交换器和队列

这一节是本章的重中之重。AMQP 的哲学是"**声明即幂等**"——declare 一个已存在的同名实体时，如果属性完全一致则是 no-op；如果不一致则抛出 channel 级异常。理解这一点，你才不会在生产环境因为"重复声明"而踩坑。

### 3.2.1 exchangeDeclare 方法详解

最完整的方法签名：

```
Exchange.DeclareOk exchangeDeclare(
    String exchange,     // 交换器名称
    String type,         // direct / fanout / topic / headers
    boolean durable,     // 是否持久化
    boolean autoDelete,  // 是否自动删除
    boolean internal,    // 是否内置（客户端不能直接发消息给它）
    Map arguments        // 扩展参数，如 alternate-exchange
)
```

**关键参数语义**（结合官方文档深化）：

- **durable**：持久化交换器在 broker 重启后依然存在。RabbitMQ 官方明确指出，**transient（非持久化）交换器在实践中极少使用**，从 4.x 系列开始随着 Khepri 成为唯一元数据存储，对非持久化实体的支持将被移除。**工业洞见：生产环境一律 `durable=true`**，没有例外。
- **autoDelete**：当最后一个绑定被解除时，交换器自动删除。注意前提是"至少有一个绑定曾经存在过"——不是"所有客户端断开就删除"，这是和 queue 的 autoDelete 语义不同的地方。
- **internal**：内置交换器。客户端无法直接 `basicPublish` 到它，只能通过 exchange-to-exchange binding 让它接收消息。这是 RabbitMQ 路由能力的高级玩法，用于构建复杂的路由拓扑。
- **arguments**：最著名的就是 `alternate-exchange`（AE）。当消息无法路由到任何队列时，broker 会把消息转发到 AE，而不是静默丢弃。

**关于 alternate-exchange 的工业级补充**：

RabbitMQ 官方推荐**用 Policy 配置 AE，而不是在客户端 declare 时传 arguments**。原因是 Policy 可以在不修改代码的情况下动态调整，对运维更友好：

```
rabbitmqctl set_policy AE "^my-direct$" '{"alternate-exchange":"my-ae"}' --apply-to exchanges
```

AE 可以形成链——如果 AE 自己也路由不了，会继续转发到它配置的 AE，直到路由成功或链条结束。这是构建"消息兜底"机制的利器。

> 💡 **洞见**：朱忠华老师在书里讲 AE 讲得比较简略。但从第一性原理看，AE 解决的是"**路由失败**"这个边界场景——它和后面的"死信队列（DLX）"形成互补：AE 处理"exchange → queue"这段路的失败，DLX 处理"queue → consumer"这段路的失败。理解了这个分工，你在设计可靠消息系统时就有了完整的兜底思路。

### 3.2.2 queueDeclare 方法详解

最完整签名：

```
Queue.DeclareOk queueDeclare(
    String queue,        // 队列名，空则 broker 自动生成
    boolean durable,     // 是否持久化
    boolean exclusive,   // 是否排他
    boolean autoDelete,  // 是否自动删除
    Map arguments        // 扩展参数（TTL、长度限制、死信等）
)
```

**无参 `queueDeclare()` 的默认行为**：创建一个 broker 命名的、**排他、自动删除、非持久化**的队列。这种队列常用于 RPC 模式的回调队列。

**参数深解**：

- **durable**：队列元数据持久化。但要注意——**队列持久化 ≠ 消息持久化**。消息还需要设置 `deliveryMode=2`（PERSISTENT_TEXT_PLAIN）才能真正落盘。而且即便如此，RabbitMQ 也不对每个消息做 `fsync`，存在极小窗口期的丢失风险，要更强保证需启用 Publisher Confirms。
- **exclusive**：排他队列**仅对创建它的 Connection 可见**，连接断开自动删除。**RabbitMQ 官方特别强调：exclusive 队列几乎总是应该用 broker 自动生成的名字**。如果你给排他队列取了个静态名字，当客户端断开重连时，会有一个竞态：broker 在删、客户端在重建，极易导致连接恢复失败。
- **autoDelete**：曾有消费者连接过、且最后一个消费者断开后，队列自动删除。
- **arguments**：这是 RabbitMQ 高级特性的入口，常用的有：
    - `x-message-ttl`：消息存活时间
    - `x-max-length`：队列最大长度
    - `x-dead-letter-exchange`：死信交换器
    - `x-queue-type`：队列类型（classic / quorum / stream）

> ⚠️ **工业避坑**：不是所有属性组合都有意义。比如 exclusive + 静态命名就是反模式；durable=false + autoDelete=false 的组合在重启后会丢队列但消息还在内存中——这些边界情况在书本里很少展开，但在生产环境真会发生。

### 3.2.3 queueBind 方法详解

`queueBind(queue, exchange, routingKey, arguments)`——建立队列到交换器的绑定。

**第一性原理视角**：Binding 是 RabbitMQ 路由模型的"**连接边**"。Exchange 和 Queue 本身不产生联系，全靠 Binding 把它们编织成拓扑网。Binding 本身也有持久化属性——**Binding 的持久化继承自其源（exchange）和目的（queue）**。也就是说，如果两边都是 durable，binding 就是 fully durable；如果有一边是 transient，就是 semi-durable 或 fully transient。

> 💡 **洞见**：RabbitMQ 官方文档透露了一个未来变化——**semi-durable 和 fully transient 的 binding 在 4.x 系列将被废弃**。这意味着未来所有 binding 都必须是 fully durable 的。所以**从现在开始，工业项目里 exchange 和 queue 一律声明为 durable**，不要给自己埋雷。

### 3.2.4 exchangeBind 方法详解

`exchangeBind(destination, source, routingKey, arguments)`——交换器到交换器（E2E）的绑定。

这是 RabbitMQ 区别于其他 MQ 的一个独特能力：**交换器不仅可以路由到队列，还可以路由到另一个交换器**。这样就形成了"交换器链路"，消息可以经过多级交换器的过滤和转发。

**工业应用场景**：

- **多租户路由**：第一级 exchange 按租户 ID 路由到第二级 exchange，第二级再按业务类型路由到具体队列
- **与 internal exchange 配合**：将前端 exchange 设为 internal，所有消息必须先经过一个或多个"网关 exchange"转发，实现路由逻辑的封装

### 3.2.5 何时创建

这是一个看似简单但工业界争议很大的问题。有两种主流范式：

**范式 A：生产者/消费者各自声明所需拓扑**

- 优点：去中心化，每个服务自包含
- 缺点：容易因属性不一致导致 declare 冲突

**范式 B：独立的基础设施服务/运维脚本统一声明**

- 优点：拓扑集中管理，避免冲突
- 缺点：服务部署顺序有依赖

RabbitMQ 官方推荐的折中方案是：**使用 Policy 来统一管理 exchange 的扩展属性（如 AE），而队列和绑定的声明则由各服务自行负责**。

> 💡 **工业最佳实践**：
> 
> 1. **Declare 是幂等的**——放心地在生产者和消费者两端都声明，属性一致就没问题
> 2. **用被动声明（passive declare）做健康检查**：`queueDeclarePassive("queue-name")` 只检查队列是否存在，不存在则抛异常。这在服务启动期验证依赖很管用
> 3. **避免在运行时高频 declare/unbind**——如果拓扑变更频繁，使用 `queueDeclareNoWait` 提升性能，但它依赖心跳检测失败，安全性较低

## 3.3 发送消息

`basicPublish(exchange, routingKey, mandatory, props, body)`

**关键参数洞察**：

- **mandatory**：当消息无法路由到任何队列时，如果 `mandatory=true`，broker 会通过 `Basic.Return` 把消息返回给生产者；如果 `false`，消息直接丢弃。**这是配合 AE 的另一个兜底手段**——AE 是"转发到另一个 exchange"，mandatory 是"退回给生产者自己处理"。
- **props（BasicProperties）**：消息的元数据载体。常用字段：
    - `deliveryMode=2`：持久化消息
    - `contentType`：内容类型
    - `priority`：优先级
    - `correlationId` / `replyTo`：RPC 模式用
    - `expiration`：单条消息的 TTL
    - `headers`：headers exchange 的匹配依据

```
channel.basicPublish(
    exchangeName, 
    routingKey, 
    MessageProperties.PERSISTENT_TEXT_PLAIN,  // deliveryMode=2
    messageBodyBytes
);
```

> ⚠️ **工业陷阱**：`basicPublish` 默认是"发完就忘"——消息进入 broker 的 socket 缓冲区即返回，不保证 broker 真的收到。要强保证，必须启用 **Publisher Confirms**（下章会详述）。这是很多初级开发者踩过的坑：以为 `basicPublish` 返回了就等于消息安全入库，实际上网络抖动时消息可能静默丢失。

## 3.4 消费消息

RabbitMQ 提供两种消费模式，这是 AMQP 协议层面的根本差异。

### 3.4.1 推模式（Push）

`basicConsume(queue, autoAck, consumerTag, consumer)`——向 broker 注册一个消费者，broker 主动把消息推过来。

**这是工业生产的绝对主流模式**。关键配套机制：

**① QoS Prefetch**——`channel.basicQos(prefetchCount)`

限制 broker 向该消费者**单次推送的未确认消息数量**。这是实现消费端流控的核心手段。

RabbitMQ 官方 Work Queue 教程里有个经典案例：两个 worker，奇数消息重、偶数消息轻，如果不用 prefetch，broker 会盲目轮询导致一个 worker 忙死、另一个闲死。**设置 `prefetchCount=1` 后，broker 只在消费者 ack 后才推下一条**。

工业调优经验：

- **prefetch=1~2**：最安全但吞吐低，每条消息必须处理完才能拿下一条
- **prefetch=10~50**：良好起点，平衡吞吐与内存压力
- **prefetch=1000+**：高风险，消费者处理慢时内存暴涨

**② 公平调度（Fair Dispatch）**：prefetch + 手动 ack 配合使用，才能实现真正的"能者多劳"。

### 3.4.2 拉模式（Pull）

`basicGet(queue, autoAck)`——消费者主动从队列拉一条消息。

> ⚠️ **工业警示**：拉模式**绝不能在循环里代替推模式**！每次 `basicGet` 都要走完整的 AMQP 命令往返，性能极差。RabbitMQ 官方明确：pull 只适合"按需捞一条"的场景，常态消费必须用 push。

**选型第一性原理**：

- 需要实时处理、持续消费 → **Push 模式**
- 定时任务、按需处理、低频捞取 → **Pull 模式**

## 3.5 消费端的确认与拒绝

这是**生产环境可靠性的命脉**，也是本章最需要深挖的环节。

### 自动确认 vs 手动确认

|模式|autoAck 参数|行为|适用场景|
|---|---|---|---|
|自动确认|`true`|消息发出即视为确认，立即从队列删除|日志、指标等非关键数据|
|手动确认|`false`|消费者显式调用 `basicAck` 后才删除|**所有生产工作负载**​|

RabbitMQ 官方把自动确认描述为"**fire-and-forget**"模式——它用降低安全性换取更高吞吐。如果消费者在 ack 前崩溃或 TCP 连接断开，消息**直接丢失**。**因此自动确认不适合任何需要可靠处理的业务场景**。

更重要的是，自动确认模式下**没有 prefetch 限制**，消费者可能被消息淹没导致 OOM。

### 三种确认/拒绝指令

**① `basicAck(deliveryTag, multiple)`**——正向确认

- `multiple=true`：批量确认所有 deliveryTag ≤ 当前值的未确认消息
- 这是最常用、最推荐的指令

**② `basicReject(deliveryTag, requeue)`**——单条否定确认

- `requeue=true`：消息重新入队
- `requeue=false`：消息丢弃（若配置了 DLX 则进入死信队列）

**③ `basicNack(deliveryTag, multiple, requeue)`**——批量否定确认

- RabbitMQ 对 AMQP 协议的扩展，支持 `multiple` 批量操作
- **语义差异**：`basicReject` 表示"消息处理失败"，会递增消息的 `delivery-count`；`basicNack` 表示"消费者未处理该消息"，**不递增 delivery-count**
- 这个差异对**quorum 队列**至关重要——quorum 队列支持毒消息处理：当 `delivery-count` 超过阈值（默认 20 次）时自动死信化

> 💡 **工业洞见**：对于 quorum 队列 + 毒消息处理场景，**优先用 `basicReject` 而非 `basicNack`**，因为它的"失败计数"语义才能让 quorum 队列的 `delivery-limit` 机制生效。这是书本里很难看到的细节。

### 生产环境可靠性闭环

把 3.3 ~ 3.5 串起来，工业级可靠消息系统的标准配置：

1. **生产端**：`basicPublish` 配合 `mandatory=true` + Publisher Confirms
2. **Broker 端**：durable exchange + durable queue + 消息 `deliveryMode=2`
3. **消费端**：`autoAck=false` + `basicQos(prefetchCount)` + 业务处理后 `basicAck`
4. **异常处理**：处理失败时 `basicReject(requeue=false)` 进入死信队列，避免无限重投循环
5. **兜底机制**：exchange 配置 `alternate-exchange`，queue 配置 `x-dead-letter-exchange`

> ⚠️ **最常见的生产事故**：`requeue=true` 的无限循环——消息处理始终失败，被反复重新入队，耗尽 CPU 且阻塞其他消息。**正确做法是设置重试上限，超过后 `requeue=false` 转入死信队列**。

## 3.6 关闭连接

`channel.close()` → `connection.close()`。

**工业最佳实践**：

- 使用 try-with-resources（Java 7+）确保连接和信道无论成功失败都能关闭
- 关闭顺序：**先关 Channel，再关 Connection**
- 生产环境中，连接关闭会触发：该连接上所有 exclusive 队列被删除、所有未 ack 的消息重新入队给其他消费者
- 客户端应实现**连接恢复机制**（Connection Recovery）——RabbitMQ Java 客户端原生支持自动恢复

> 💡 **洞见**：优雅关闭在生产环境至关重要。如果强行 kill 进程而不关闭连接，broker 侧会等到 heartbeat 超时（默认 60 秒）才判定连接失效，这段时间内该连接持有的 exclusive 队列、未 ack 消息都处于"悬挂"状态。所以**务必在应用 shutdown hook 里显式关闭 connection**。

## 3.7 小结

第3章表面是 API 手册，实质是**客户端与 broker 建立"拓扑契约"的完整生命周期**：

```
建立连接（Connection/Channel）
   ↓
声明拓扑（exchangeDeclare / queueDeclare / queueBind / exchangeBind）
   ↓
生产消息（basicPublish + mandatory + Publisher Confirms）
   ↓
消费消息（basicConsume + prefetch + 手动 ack）
   ↓
拒绝/重投（basicReject / basicNack + 死信兜底）
   ↓
优雅关闭（channel.close → connection.close）
```

**本章最核心的三个第一性原理洞察**：

1. **声明即契约，契约必须等价**：declare 是幂等的，但属性必须前后一致，否则抛异常。所以从 4.x 开始 RabbitMQ 强制走向"全 durable"时代，现在就养成 durable=true 的肌肉记忆。
2. **手动 ack + prefetch 是消费端可靠性的双支柱**：没有 prefetch 的手动 ack 会撑爆内存，没有手动 ack 的 prefetch 毫无意义。二者必须配合。
3. **RabbitMQ 的可靠性是"层层兜底"的**：
    
    - 路由层兜底：alternate-exchange
    - 队列层兜底：dead-letter-exchange
    - 消费层兜底：reject + requeue=false
    - 发布层兜底：mandatory + Publisher Confirms
    
    每一层都不是银弹，但**组合起来就是工业级的可靠消息系统**。
