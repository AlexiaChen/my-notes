
# 《Unix内核源码剖析》读书笔记 · 第8章 块设备驱动

> 第7章我们把"缓冲区缓存"这层中继层建好了——getblk/bread/bwrite 等接口已经能让上层以"块号"为单位读写数据。但缓冲区里的数据最终必须落到物理磁盘上，这个"最后一公里"就是第8章的主题：**块设备驱动**。
> 
> **第一性洞见**：块设备驱动的本质，是**把"统一的块 I/O 请求"翻译成"具体硬件的操作序列"**。操作系统核心代码（bio.c）只认识 `buf` 结构体——里面是设备号、块号、数据地址、标志位；但它**不认识**​ RK11 磁盘控制器的寄存器。反过来，RK11 硬件只认识寄存器写入序列，它不认识什么是"文件系统"。**bdevsw 这张函数指针表，就是连接这两个世界的"外交使馆"**——上层通过 `bdevsw[major(dev)].d_strategy(buf)` 调用驱动，驱动内部把 buf 翻译成寄存器操作。
> 
> 正如 V6 源码 conf.h 中 bdevsw 结构体的注释所说："_Each entry (row) is the only link between the main unix code and the driver_" ——**bdevsw 的每一行，是 UNIX 主代码和驱动之间唯一的链接**。这句话精准地概括了驱动架构的第一性原理：**用一张函数指针表实现"策略与机制分离"**，让内核核心永远不需要 `#ifdef RK_DISK` 这样的硬件条件编译。

## 8.1 什么是块设备驱动

### 块设备驱动表

V6 中块设备驱动通过 **`bdevsw` 表**接入内核。该表在 `conf.h` 中定义 ：

```
struct bdevsw {
    int (*d_open)();      // 打开设备
    int (*d_close)();     // 关闭设备
    int (*d_strategy)();  // I/O 策略例程（核心！）
    int *d_tab;           // 指向该设备的 devtab 结构体
} bdevsw[];
```

V6 的 conf.c 中 `bdevsw[]` 的实际初始化（由 `mkconf` 工具自动生成） ：

```
int (*bdevsw[])() {
    &nulldev, &nulldev, &rkstrategy, &rktab,   /* rk */
    &nodev,   &nodev,   &nodev,      0,        /* rp */
    &nodev,   &nodev,   &nodev,      0,        /* rf */
    &nodev,   &nodev,   &nodev,      0,        /* tm */
    &nodev,   &nodev,   &nodev,      0,        /* tc */
    &nodev,   &nodev,   &nodev,      0,        /* hs */
    &nodev,   &nodev,   &nodev,      0,        /* hp */
    &nodev,   &nodev,   &nodev,      0,        /* ht */
    0
};
```

**关键认知**：

1. **主设备号就是 bdevsw 表的索引**。V6 的 conf.c 中 rk 排在第 2 项（从 0 开始），所以 rk 的主设备号是 2；rp 排第 3 项，主设备号是 3，以此类推 。
    
2. **`d_strategy` 是块设备区别于字符设备的根本**——块设备必须有 strategy 例程，字符设备用 `d_read`/`d_write` 。
    
3. **`d_tab` 指向驱动的 `devtab` 结构体**，内含设备队列和设备状态。
    
4. conf.c 是 `mkconf` 工具根据系统配置**自动生成**的——这意味着**驱动的安装就是"在配置文件中加一行"**​ 。
    

> 💡 **洞见**：bdevsw 的设计是操作系统史上**最早的"插件架构"之一**。内核核心代码（bio.c 的 bread/bwrite）完全不知道底层是 RK05 还是 RP04 还是磁带机——它只做一件事：`(*bdevsw[major(dev)].d_strategy)(bp)`。新增一种块设备，只需要：
> 
> 1. 写一个新的 `xxstrategy()` 函数
>     
> 2. 在 conf.c 的 bdevsw[] 中加一行
>     
> 3. 重新编译内核
>     
> 
> **核心代码零修改**。这就是"开闭原则"（对扩展开放，对修改封闭）在 1975 年的实践。

### 设备处理队列

每个块设备驱动维护一个 **`devtab` 结构体**，管理该设备的 I/O 请求队列 ：

```
struct devtab {
    char d_active;        // 设备是否正在执行 I/O
    char d_errcnt;        // 错误计数
    struct buf *b_forw;   // 队列前向指针
    struct buf *b_back;   // 队列后向指针
    struct buf *d_actf;   // 队首（下一个要执行的请求）
    struct buf *d_actl;   // 队尾（最后一个请求）
};
```

RK 驱动的 devtab 实例是 `rktab`：

```
struct devtab rktab = {0, 0, 0, 0, 0, 0};
```

**队列的核心语义**：

- **d_actf**（active front）：指向当前正在执行或下一个要执行的 buf
    
- **d_active**：设备忙标志，防止重入启动
    
- **b_forw/b_back**：buf 结构体自身的队列指针（注意：buf 结构体里**已经有**​ b_forw/b_back 字段，所以队列是直接链在 buf 上的，不需要额外的队列节点）
    

> 📌 **洞见**：devtab 队列是"**生产者-消费者**"模型的硬件版。生产者是上层的 `xxstrategy()` 调用者（bio.c 的 bread/bwrite），消费者是**设备中断**——每次 I/O 完成，中断处理函数从队列取下一个请求启动。这个模型在现代块设备中演化为：
> 
> - Linux 的 `request_queue` + `blk_mq_hw_ctx`
>     
> - NVMe 的 Submission Queue / Completion Queue
>     
> - 现代 HBA 的 I/O 队列
>     
> 
> **第一性原理完全一致**：用队列解耦"提交 I/O"和"完成 I/O"两个异步事件。

### 处理流程

块设备驱动的标准处理流程（以 RK 为例）：

```
上层调用 bread()/bwrite()
    ↓
bio.c: (*bdevsw[major].d_strategy)(bp)
    ↓
rkstrategy(bp):
    1. 校验块号合法性
    2. 将 bp 加入 rktab 队列
    3. 如果设备空闲，调用 rkstart() 启动
    ↓
rkstart():
    4. 从 rktab.d_actf 取下一个 buf
    5. 设置 d_active = 1
    6. 通过 rkaddr() 计算物理磁盘地址（柱面/磁道/扇区）
    7. 通过 devstart() 写 RK11-D 寄存器，启动 I/O
    ↓
    [磁盘硬件执行 I/O，CPU 继续干别的]
    ↓
    [I/O 完成，RK11-D 触发 BR5 中断]
    ↓
rkintr():
    8. 检查 d_active，确认不是假中断
    9. 清除 d_active
    10. 调用 iodone(bp) —— 设置 B_DONE，唤醒等待进程
    11. 调用 rkstart() 启动队列中的下一个请求
```

> ⚠️ **这是 V6 块设备驱动最关键的认知**：**strategy 函数不等待 I/O 完成**。它只是把请求入队，如果设备空闲就启动第一个，然后立即返回。真正的 I/O 完成是在**中断上下文**中处理的。这种"异步提交 + 中断完成"的模型，是块设备驱动的第一性原理。

**工业联系**：

- **Linux 的块层**：bio 提交 → `make_request_fn` → 驱动 `queue_rq` → 硬件 DMA → 中断 `blk_mq_complete_request`。与 V6 的流程一一对应 。
    
- **现代磁盘控制器的队列化**：RK11-D 是"单队列、同步启动"的原始形态；今天的 NCQ（SATA）、NVMe 队列则是"多队列、异步完成"的演化形态。但**生产-消费队列模型没变**。
    
- **中断下半部（bottom half）**：V6 的 `rkintr()` 在中断上下文里调用 `rkstart()` 启动下一个 I/O，这其实就是现代 Linux "中断上半部 + 下半部"思想的雏形——中断处理要尽量快，后续工作可以延后或继续。

## 8.2 RK-11 磁盘驱动

RK11-D 是 DEC 的 RK05 磁盘控制器，是 PDP-11/40 上最常见的块设备。V6 选择它作为"参考驱动"来展示块设备驱动的标准写法。

### RK11-D

RK05 磁盘的关键参数 ：

- 单块大小：512 字节
    
- 每块有 12 个扇区（sectors per track）
    
- 每个柱面有多个磁道
    
- 块号到物理地址的换算：`cyl = blkno / 12`，`sector = blkno % 12`
    

RK11-D 控制器通过 UNIBUS 与 PDP-11 连接，寄存器被内存映射（在 V6 源码中通过 `RKADDR` 指针访问）。

### 特殊文件

RK 磁盘在 V6 中对应的特殊文件 ：

- `/dev/rk0` - 原始（裸）RK 设备
    
- `/dev/rk0d` - 块设备，d 分区
    
- `/dev/rrk0` - 裸 I/O 版本
    

通过 `mknod` 创建：

```
/etc/mknod /dev/rk0 b 2 0   # 主设备号 2（RK），次设备号 0
```

### 设定 bdevsw[]

RK 驱动在 conf.c 中的 bdevsw 表项是 ：

```
&nulldev, &nulldev, &rkstrategy, &rktab,   /* rk */
```

含义：

- `d_open` = `nulldev`：RK 不需要特殊的 open 处理
    
- `d_close` = `nulldev`：RK 不需要特殊的 close 处理
    
- `d_strategy` = `rkstrategy`：核心 I/O 策略函数
    
- `d_tab` = `&rktab`：RK 的设备队列
    

**对比其他设备**：rp、rf、tm、tc、hs、hp、ht 等设备在 V6 标准配置中都设为 `nodev`（即 `xxstrategy` 都是 `nodev`）——因为标准 V6 发行版主要针对 RK05 配置，其他磁盘类型需要用户自己配置 。

> 💡 **洞见**：`nulldev` 和 `nodev` 这两个"空函数"的存在，本身就是一种设计智慧——**用统一的空实现填充未使用的槽位**，避免了大量的 `#ifdef` 条件编译。今天 Linux 内核中的 `noop_llseek`、`null_fops` 等空操作函数，与 V6 的 `nulldev` 思想同源。

### 中断处理函数

RK11-D 在 I/O 完成时触发 **BR5 中断**（向量地址 220 八进制）。V6 在汇编跳板中将其绑定到 `rkintr()` 函数。

中断处理函数的核心职责 ：

1. **防假中断**：检查 `rktab.d_active` 是否置位，未置位说明是异常中断，直接返回
    
2. **完成当前 I/O**：清除 `d_active`，调用 `iodone(bp)` 标记缓冲区完成
    
3. **启动下一个 I/O**：调用 `rkstart()` 从队列取下一个请求
    

### RK11-D 的寄存器

RK11-D 控制器通过一组内存映射寄存器与 CPU 通信。根据 DEC 手册，RK11-D 的寄存器基地址是 `0177400`（八进制），包括 ：

- **rkds**（Disk Status）：磁盘状态寄存器
    
- **rker**（Error Register）：错误寄存器
    
- **rkcs**（Control Status）：控制状态寄存器——写入命令字启动 I/O
    
- **rkwc**（Word Count）：字计数寄存器——指定传输字数（负值）
    
- **rkba**（Bus Address）：总线地址寄存器——指定内存缓冲区地址
    
- **rkda**（Disk Address）：磁盘地址寄存器——指定柱面/磁道/扇区
    

V6 源码中通过以下方式定义寄存器指针 ：

```
#define RKADDR ((struct device *)0177400)

struct device {
    int rkds;
    int rker;
    int rkcs;
    int rkwc;
    caddr_t rkba;
    int rkda;
};
```

**洞见**：这个 `struct device` 的定义，是**"用 C 结构体映射硬件寄存器"**的经典范例。Ritchie 把 6 个连续的 16 位寄存器定义为一个结构体，然后通过 `RKADDR->rkcs` 这样的指针访问来读写寄存器。**这是 C 语言"贴近硬件"能力的极致展现**——今天你在 Linux 内核中看到的 `readl()/writel()` 宏、MMIO 映射，其精神始祖就是 V6 的这个 `struct device`。

### rkstrategy()

`rkstrategy(bp)` 是 RK 驱动对外的 strategy 接口，由 bio.c 通过 `bdevsw[major].d_strategy` 调用 ：

```
rkstrategy(abp) {
    // 1. 检查块号是否超出 RK 磁盘最大块号
    if (abp->b_blkno >= RKMAX) {
        abp->b_error = ENXIO;
        abp->b_flags |= B_ERROR;
        iodone(abp);
        return;
    }
    
    // 2. 将 buf 插入 rktab 设备队列
    abp->b_forw = 0;
    if (rktab.d_actf == NULL) {
        rktab.d_actf = abp;
    } else {
        rktab.d_actl->b_forw = abp;
    }
    rktab.d_actl = abp;
    
    // 3. 如果设备空闲，启动 I/O
    if (rktab.d_active == 0) {
        rkstart();
    }
}
```

**关键设计**：

1. **校验先行**：块号越界立即报错，避免无效 I/O
    
2. **入队**：buf 通过自身的 `b_forw` 指针链入 rktab 队列
    
3. **启动条件**：只有当设备空闲（`d_active == 0`）时才立即启动，否则等待当前 I/O 完成后由 `rkintr()` 调用 `rkstart()` 启动
    

> ⚠️ **这是生产-消费者模型的生产者侧**：`rkstrategy` 只负责"生产"I/O 请求（入队），不负责"消费"（实际 I/O 由 `rkintr` 驱动）。这种**完全异步**的设计，让上层调用者（bio.c 的 bread/bwrite）永远不会阻塞在 strategy 调用上——真正的阻塞发生在 `iowait(bp)` 中（在 bread/bwrite 内部）。

### rkstart()

`rkstart()` 从队列取一个 buf，启动实际 I/O ：

```
rkstart() {
    register struct buf *bp;
    
    // 1. 取队首 buf
    if ((bp = rktab.d_actf) == NULL) {
        rktab.d_active = 0;
        return;
    }
    
    // 2. 标记设备忙
    rktab.d_active = 1;
    
    // 3. 计算物理磁盘地址
    RKADDR->rkda = rkaddr(bp);
    
    // 4. 设置内存地址和字计数
    RKADDR->rkba = bp->b_addr;
    RKADDR->rkwc = -(bp->b_bcount >> 1);  // 字节数转字数，负值
    
    // 5. 写控制状态寄存器启动 I/O
    int com = (bp->b_xmem & 3) << 8;
    if (bp->b_flags & B_READ)
        com |= RCOM;        // 读命令
    else
        com |= WCOM;        // 写命令
    RKADDR->rkcs = com;     // 启动 I/O！
}
```

**关键细节**：

1. **d_active 置位**：防止 `rkstrategy` 重入启动
    
2. **rkaddr() 换算物理地址**：把线性块号转换为柱面/磁道/扇区
    
3. **rkwc 是负数**：PDP-11 的 RK11-D 规定字计数寄存器必须写负值，硬件在每次传输后递增，到 0 时触发中断
    
4. **写入 rkcs 启动 I/O**：这是"扣动扳机"的动作——一旦写入 rkcs，硬件就开始 DMA 传输
    

> 💡 **洞见**：`rkstart()` 的最后一行 `RKADDR->rkcs = com` 是**整个驱动中"最危险"的一行**——它把 CPU 的控制权暂时交给了磁盘控制器。从这一刻起，到 `rkintr()` 被调用，CPU 可以去执行任何其他进程。这种"发射后不管"的异步模型，是块设备驱动的第一性原理。

### rkaddr()

`rkaddr(bp)` 把线性块号换算为 RK11-D 的物理磁盘地址：

```
rkaddr(bp) {
    int blkno = bp->b_blkno;
    int minor = minor(bp->b_dev);
    int cyl = blkno / 12;        // 每块 12 个扇区
    int sector = blkno % 12;
    return ((minor & 07) << 12) | (cyl << 4) | sector;
}
```

**换算逻辑**：

- **高 3 位**：驱动器号（次设备号的低 3 位，支持 8 个 RK05 驱动器）
    
- **中间位**：柱面号
    
- **低 4 位**：扇区号
    

> 📌 **工业联系**：现代磁盘的 LBA（Logical Block Addressing）把"柱面-磁头-扇区"的三维地址扁平化为一维块号，但**在驱动内部仍然需要换算回 CHS**——SATA 的 NCQ 命令、NVMe 的 LBA 命令，本质上都在做 rkaddr() 做的事。**第一性原理：线性块号 ↔ 物理地址的换算，是块设备驱动永恒的职责**。

### devstart()

`devstart()` 是 `rkstart()` 的内部辅助函数，负责实际写寄存器启动 I/O。在 V6 的 RK 驱动中，`devstart()` 通常被 `rkstart()` 直接内联调用，核心就是写 `RKADDR->rkcs` 寄存器。

### rkintr()

`rkintr()` 是 RK11-D 的中断处理函数，由硬件 BR5 中断触发 ：

```
rkintr() {
    register struct buf *bp;
    
    // 1. 防假中断
    if (rktab.d_active == 0)
        return;
    
    // 2. 取出当前完成的 buf
    bp = rktab.d_actf;
    rktab.d_active = 0;  // 清除忙标志
    
    // 3. 检查错误
    if (RKADDR->rkcs & RKERR) {
        bp->b_error = RKADDR->rker;
        bp->b_flags |= B_ERROR;
        rktab.d_errcnt++;
    }
    
    // 4. 完成 I/O，唤醒等待进程
    iodone(bp);
    
    // 5. 从队列移除已完成的 buf
    rktab.d_actf = bp->b_forw;
    if (rktab.d_actf == NULL)
        rktab.d_actl = NULL;
    
    // 6. 启动队列中的下一个 I/O
    rkstart();
}
```

**关键流程**：

1. **防假中断**：RK11-D 可能发送"假中断"（设备未被启动但中断线被触发），必须检查 `d_active`
    
2. **清除忙标志**：允许后续 strategy 调用启动新 I/O
    
3. **错误处理**：检查 rkcs 的错误位，设置 buf 的 B_ERROR 标志
    
4. **iodone(bp)**：标记 B_DONE 并唤醒在 bp 上睡眠的进程（这是 bread/bwrite 中 iowait 的唤醒源）
    
5. **队列推进**：把已完成的 buf 从队首移除
    
6. **启动下一个**：调用 rkstart() 继续处理队列
    

> ⚠️ **核心认知**：`rkintr()` 是**设备队列的消费驱动**。每次 I/O 完成，中断处理函数做三件事：**完成当前、出队、启动下一个**。这个"中断驱动队列"的模型，是现代块设备"中断 + 队列"架构的鼻祖。

**iodone() 的作用**​ ：

```
iodone(bp) {
    bp->b_flags |= B_DONE;     // 标记 I/O 完成
    wakeup(bp);                // 唤醒等待的进程
}
```

这正好对应第3章讲的 sleep/wakeup 机制——`bread()` 中的 `iowait(bp)` 让进程在 bp 上睡眠，`iodone(bp)` 在中断上下文中唤醒它。**I/O 的同步语义，是用 sleep/wakeup 实现的**。

### RAW 输入输出

RK 驱动也支持裸 I/O（Raw I/O），对应 `/dev/rrk*` 设备文件。裸 I/O 绕过缓冲区缓存，直接通过 `physio()` 在用户内存和磁盘之间传输数据（详见第7章的 physio 分析）。

RK 驱动的裸 I/O 入口通常是 `rkraw()` 函数，它调用 `physio(rkstrategy, ...)` 实现裸传输。

## 8.3 小结

第8章完成了块设备驱动的完整剖析。把所有机制串起来看：

```
上层（bio.c）
    ↓
bdevsw[major].d_strategy(bp)
    ↓
驱动 strategy 函数（rkstrategy）
    ↓
    1. 校验块号
    2. 入队 rktab
    3. 若设备空闲 → rkstart()
    ↓
rkstart()
    ↓
    4. 取队首 buf
    5. rkaddr() 换算物理地址
    6. 写 RK11-D 寄存器启动 DMA
    ↓
    [硬件执行 I/O，CPU 切换其他进程]
    ↓
    [I/O 完成，BR5 中断]
    ↓
rkintr()
    ↓
    7. 防假中断
    8. iodone(bp) —— 唤醒等待进程
    9. 出队
    10. rkstart() —— 启动下一个
```

**第一性原理总结**：

1. **bdevsw 是"策略与机制分离"的典范**：内核核心只认识 `buf` 结构体，通过函数指针调用驱动，永不直接操作硬件。新增设备只需在 bdevsw[] 中加一项 。
    
2. **devtab 队列是"生产者-消费者"模型**：strategy 函数是生产者（入队），中断处理函数是消费者（出队+启动下一个）。这种异步队列模型解耦了"提交 I/O"和"完成 I/O" 。
    
3. **strategy 不等待 I/O 完成**：rkstrategy 立即返回，真正的同步等待发生在上层的 iowait(bp) 中。这是"异步提交 + 中断完成"模型的精髓 。
    
4. **中断处理函数驱动队列**：rkintr 在中断上下文完成当前请求、出队、启动下一个。这是现代"中断上半部"思想的雏形 。
    
5. **C 结构体映射硬件寄存器**：`struct device` 直接映射到 RK11-D 的内存映射寄存器，是 C 语言贴近硬件能力的极致展现 。
    
6. **物理地址换算**：rkaddr() 把线性块号换算为柱面/磁道/扇区，是块设备驱动永恒的职责 。
    

**跨章节联系**：

- 第7章的 `buf` 结构体：驱动操作的唯一数据单元
    
- 第7章的 `bread/bwrite`：通过 `bdevsw[].d_strategy` 调用驱动
    
- 第7章的 `iowait/iodone`：驱动中断通过 `iodone()` 唤醒睡眠进程
    
- 第3章的 `sleep/wakeup`：I/O 同步的底层原语
    
- 第5章的"中断优先级"：RK11-D 使用 BR5 中断，与时钟（BR6）、TTY（BR4）形成优先级层次
    
- 下一章（第9章）文件系统：通过 `bread/bwrite` 读写 inode、数据块——驱动是文件系统的"腿"
    

**工业落地的五点启示**：

1. **函数指针表是"插件化架构"的鼻祖**：bdevsw 告诉我们——**用一张函数指针表，可以让核心代码与硬件驱动完全解耦**。今天的所有"插件架构"——Linux 的 `file_operations`、Windows 的 COM、Java 的 SPI、Go 的接口——都是这一思想的演化。V6 在 1975 年就证明：好的架构不是"写得更抽象"，而是"用表驱动代替条件编译"。
    
2. **设备队列是"异步 I/O"的第一性原理**：strategy 入队 + 中断出队的模型，是现代块设备队列的始祖。今天的演化：
    
    - Linux 的 `blk_mq`：多队列、每队列一个硬件上下文
        
    - NVMe 的 SQ/CQ：提交队列/完成队列，与 RK 的 devtab 队列一一对应
        
    - 现代 HBA 的 I/O 队列
        
        **第一性原理没变：用队列解耦生产和消费**。
        
    
3. **中断处理要"快进快出"**：rkintr 只做三件事——完成、出队、启动下一个。它**绝不**在中断上下文做复杂处理。这是现代"中断上半部/下半部"模型的雏形。今天的演化：
    
    - Linux 的 `tasklet`、`workqueue`、`softirq`
        
    - Windows 的 DPC（Deferred Procedure Call）
        
    - 实时操作系统的"中断线程化"
        
        **核心思想：中断处理要短平快，重活儿延后做**。
        
    
4. **C 结构体映射硬件寄存器是"硬件编程"的基础范式**：V6 的 `struct device` 映射 RK11-D 寄存器，开启了"用 C 结构体描述硬件"的传统。今天：
    
    - Linux 的 `readl()/writel()` + `ioremap()`
        
    - 嵌入式开发中的 `volatile struct GPIO_REGS *`
        
    - 设备树（Device Tree）的 `reg` 属性
        
        **V6 的 `RKADDR->rkcs = com` 是这一切的起点**。
        
    
5. **"裸 I/O"是性能敏感应用的逃生舱**：RK 驱动支持 `/dev/rrk*` 裸设备，让应用绕过缓冲区缓存。今天的演化：
    
    - Linux 的 `O_DIRECT` 标志
        
    - 数据库的直接 I/O
        
    - NVMe 的"无缓存访问"
        
        **核心思想：当应用比内核更懂 I/O 模式时，让应用绕过内核缓存**——这一思想从 V6 一直延续到今天的 NVMe 存储栈。

## 英文补充资料与跨时代对照

### 1. V6 源码原典 conf.h 和 conf.c

V6 源码中 bdevsw 结构体的定义和 conf.c 的初始化是理解驱动架构的**一手资料**："_Each entry (row) is the only link between the main unix code and the driver_" ——这句话是驱动架构设计哲学的最精确表达 。

### 2. NetBSD 驱动文档（Writing Drivers for NetBSD）

NetBSD 文档明确指出："_Both these tables [bdevsw and cdevsw] have been available under the same name in UNIX V6 since 1976_" ——这证明了 bdevsw/cdevsw 的设计从 V6 一路延续到今天的 BSD 系统 。NetBSD 的 `rf_bdevsw = { rfopen, rfclose, rfstrategy, rfioctl, rfdump, rfsize, D_DISK }` 与 V6 的 bdevsw 条目结构**惊人地一致**。

### 3.莱昂氏 UNIX V6 源代码分析（Lions Commentary）

Lions 对 rkstrategy (5389)、rkaddr (5420)、devstart (5096)、rkintr (5451)、iodone (5018) 等函数有逐行注释 。特别是 rkintr 中的 `iodone(bp)` 调用和队列推进逻辑，Lions 作了精辟分析。

### 4. PDP-11/40 和 RK11-D 硬件手册

DEC 的《PDP-11 Peripherals Handbook》详细描述了 RK11-D 的寄存器布局（基地址 0777400）和命令字格式。这是理解 `rkstart()` 中寄存器操作的硬件依据。

### 5. decuser/lions-laboratory（GitHub）

一个完整的 OpenSIMH 实验室环境，配置了 PDP-11/40 + RK11-D/RK05，用于实际运行和研究 V6 内核 。学习驱动的最佳方式是：修改 rk.c → 重新编译内核 → 在模拟器中观察行为变化。

### 6. 现代对照表

|V6 概念|现代 Linux 对应|演进|
|---|---|---|
|bdevsw[] 函数指针表|`struct block_device_operations`|增加了 ioctl、compat_ioctl 等|
|d_strategy(bp)|`queue_rq()` / `make_request_fn`|多队列、每队列硬件上下文|
|devtab 队列|`struct request_queue`|支持 NCQ、TCQ 等多命令队列|
|rkstrategy() 入队|`blk_mq_submit_bio()`|多队列提交|
|rkstart() 启动 I/O|`queue_rq` 调用驱动 `queue_rq`|硬件队列管理|
|rkintr() 中断处理|中断服务程序 + `blk_mq_complete_request()`|上半部/下半部分离|
|iodone(bp)|`bio_endio()`|完成回调|
|rkaddr() 块号换算|LBA → CHS 换算（HDD）/ LBA 直通（SSD）|逻辑块寻址|
|RK11-D 寄存器映射|`ioremap()` + `readl/writel`|内存映射 I/O|
|RAW I/O (`/dev/rrk*`)|`O_DIRECT` 标志|绕过 page cache|
|conf.c 自动生成|`Kconfig` + `Makefile` + 模块化|支持动态加载|

> 💡 **跨时代洞见**：从 V6 的 RK 驱动到今天的 NVMe 驱动，块设备驱动的**第一性原理没变**：
> 
> - **接口统一**：bdevsw → block_device_operations
>     
> - **队列异步**：devtab → request_queue → blk_mq_hw_ctx
>     
> - **中断驱动**：rkintr → 中断服务程序 + 完成队列
>     
> - **寄存器映射**：struct device → ioremap
>     
> 
> 变的是**规模**和**并行度**——从单队列到多队列，从单 CPU 到多 CPU，从机械磁盘到 SSD。但**骨架完全一致**。理解 V6 的 RK 驱动，你就拿到了理解现代块设备驱动的"源代码"。

## 给读者的学习建议

1. **在 OpenSIMH 中修改 RK 驱动**：使用 decuser/lions-laboratory 环境 ，尝试：
    
    - 在 `rkintr()` 中添加 `printf` 输出，观察每次 I/O 完成时打印的信息
        
    - 修改 `rkstrategy()` 让它故意丢弃某些请求，观察文件系统行为
        
    - 重新编译内核并在模拟器中启动，记录实验结果
        
    
    这是"看见"驱动工作的最佳方式。
    
2. **画出 RK 驱动的时序图**：
    
    ```
    进程 A: bread() → iowait(bp_A) → 睡眠
                                    ↓
    进程 B: bread() → iowait(bp_B) → 睡眠
                                    ↓
    [rkstrategy: bp_A 入队, rkstart 启动 bp_A]
                                    ↓
    [磁盘 I/O 进行中...]
                                    ↓
    [RK 中断: rkintr → iodone(bp_A) → 唤醒进程 A]
                                    ↓
    [rkintr: rkstart 启动 bp_B]
                                    ↓
    [磁盘 I/O 进行中...]
                                    ↓
    [RK 中断: rkintr → iodone(bp_B) → 唤醒进程 B]
    ```
    
    理解这个时序，你就理解了"异步 I/O + 中断完成"的精髓。
    
3. **对照 Linux 的 RK 等价物**：虽然 Linux 早已不支持 RK05，但你可以研究 Linux 的 `drivers/block/` 目录下的简单驱动（如 `brd.c` 内存磁盘驱动、`loop.c` 回环设备驱动），观察现代驱动如何沿用 V6 的 bdevsw 思想。
    
4. **思考设计问题**：如果让你为现代 NVMe SSD 写一个"V6 风格"的驱动，你会：
    
    - 保留单队列还是用多队列？
        
    - 中断处理如何划分上半部/下半部？
        
    - 如何处理 NVMe 的异步完成队列？
        
    - 如何用 C 结构体映射 NVMe 的寄存器？
        
    
    这个练习会让你深刻理解——**V6 的驱动架构在今天的约束下该如何演化**。
