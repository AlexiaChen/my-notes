
# 《Unix内核源码剖析》读书笔记 · 第7章 块设备子系统

> 前六章我们讲的是"进程"——它如何生、如何切换、如何收发信号。但进程总得**读写点什么**，否则操作系统就只是进程互相空转的玩具。第7章开始，我们进入 UNIX 第二大支柱：**I/O 与文件系统**。而块设备子系统，是文件系统的"地基"。
> 
> **第一性洞见**：块设备子系统的本质，是**用内存缓冲区消解慢速块设备的异步时延**。磁盘的寻址速度相对内存来说十分低下——"如果是内核直接操作磁盘，那么就好比博尔特和乌龟接力"。所以在文件系统和设备驱动之间，必须插入一层"高速缓冲（buffer cache）" 。这一层缓存的设计哲学极其深刻：
> 
> - **预读（read-ahead）**：如果能预测下一次要读的盘块，就预先读入
>     
> - **延迟写（delayed write）**：数据先写入高速缓冲，期待很快会有对同一块的再次写入
>     
> - **LRU 淘汰**：av-list 按"最近最少使用"顺序管理空闲缓冲区
>     
> 
> 正如 V6 源码 `buf.h` 中的注释所说："_Each buffer in the pool is usually doubly linked into 2 lists: the device with which it is currently associated (always) and also on a list of blocks available for allocation for other use (usually)_" ——每个缓冲区通常双重链接到两条链：一是它当前关联的设备链（b-list），二是空闲可分配链（av-list）。这两条链的设计，是 V6 块设备子系统最优雅的部分。

## 7.1 设备的基础

### 设备的种类

UNIX 把设备分为两大类（这个分类从 V6 一直沿用到今天）：

- **块设备（Block Device）**：以"块"为单位进行 I/O 的设备——磁盘、磁带等。块设备**可以**被挂载为文件系统
    
- **字符设备（Character Device）**：以"字符流"为单位进行 I/O 的设备——终端、打印机、鼠标等。字符设备**不能**被挂载为文件系统，但不一定是字符导向的
    

> 💡 **洞见**：这个二分法的本质，是**"是否有随机访问能力"**。块设备支持 seek，所以可以做缓冲区缓存、可以做文件系统；字符设备是流式顺序的，必须"随到随处理"。今天 Linux 的 `blockdev` 命令、`/sys/block/` 目录，仍然是这个分类的延续。

V6 支持的块设备（来自 `bdevsw` 表）包括 ：

|设备名|主设备号|说明|
|---|---|---|
|rf|0|RS 固定头磁盘|
|tc|1|TU56 DECtape|
|rk|2|RK03/RK05 移动头磁盘|
|tm|3|TU10/TU16 磁带|
|rp|4|RP 移动头磁盘|
|hs|5|RS03/RS04 固定头磁盘|
|hp|6|RP04 移动头磁盘|

### 设备驱动

每个设备驱动通过两张分派表接入内核 ：

- **`bdevsw`**（块设备分派表）：每项包含 open/close/strategy/dump 等函数指针
    
- **`cdevsw`**（字符设备分派表）：每项包含 open/close/read/write/ioctl 等函数指针
    

**主设备号（Major Device Number）**​ 就是这张表的**索引**——"_The major device number is selected by counting the line number (from zero) of the device's entry in the block configuration table. Thus the first entry in the table bdevsw would be major device zero._"

**次设备号（Minor Device Number）**​ 由驱动自行解释，通常表示：驱动器号、单元号、分区号等

### 类别和设备编号

V6 用 **16 位数**​ 表示设备号：

- **高 8 位**：主设备号（设备类型）
    
- **低 8 位**：次设备号（同类型的哪个具体设备）
    

这种"主+次"的设备号编码方式，从 V6 一直沿用到今天的 Linux——你在 `/dev/` 目录下看到的 `brw-rw---- 1 root disk 8, 1` 中的 `8, 1`，就是主设备号 8（SCSI 磁盘）、次设备号 1（第一个分区）。**50 年前 V6 定下的设备号编码，今天仍在每个 Linux 系统的 `/dev` 中鲜活存在**。

### 特殊文件

UNIX 的另一个天才设计：**"一切皆文件"**——设备也被表示为文件系统中的特殊文件（special file）。

通过 `mknod` 命令创建设备文件 ：

```
/etc/mknod /dev/NAME b MAJOR MINOR   # 块设备
/etc/mknod /dev/NAME c MAJOR MINOR   # 字符设备
```

在 inode 中，通过 **i_mode 字段的 2 位文件类型**​ 来区分 ：

- `020000`：字符型特殊文件
    
- `060000`：块型特殊文件
    

对于特殊文件，**i_addr 的第一个字的第一个字节指定设备类型（主设备号），第二个字节指定该类型的某个设备（次设备号）**​ 。

> 📌 **洞见**：特殊文件的设计让"打开设备"和"打开文件"使用完全相同的 API——`open()`、`read()`、`write()`、`close()`。用户程序不需要知道它在操作的是磁盘上的文件，还是/dev/rk0 这块物理磁盘。这是 UNIX "一切皆文件"哲学的**最硬核体现**——不是一句口号，而是 inode 结构中的 2 位标志位。

**工业联系**：今天你在 Linux 上：

- `ls -la /dev/sda1` 看到 `brw-rw---- 1 root disk 8, 1`——块设备，主 8 次 1
    
- `ls -la /dev/tty0` 看到 `crw--w---- 1 root tty 4, 0`——字符设备，主 4 次 0
    
- `mknod /dev/mydev c 240 0`——创建设备文件
    

**这些命令的行为与 V6 的 mknod 完全一致**。设备文件的"主/次设备号"编码，是操作系统史上最成功的 ABI 之一。

## 7.2 块设备子系统

### 缓冲区

块设备子系统最核心的数据结构是 **`buf` 结构体**（`buf.h`）：

```
struct buf {
    int b_flags;        // 标志位（B_BUSY, B_DONE, B_DELWRI 等）
    struct buf *b_forw; // 设备链的向前指针
    struct buf *b_back; // 设备链的向后指针
    struct buf *av_forw;// 空闲链的向前指针
    struct buf *av_back;// 空闲链的向后指针
    int b_dev;          // 主+次设备号
    int b_wcount;       // 传输字数
    char *b_addr;       // 核心地址（数据缓冲区指针）
    char b_xmem;        // 高位核心地址
    char b_blkno;       // 设备上的块号
    char b_error;       // I/O 错误码
    char b_resid;       // 出错时未传输的字数
};
```

**关键事实**：

- 缓冲区大小：**512 字节**（一个磁盘块）
    
- 缓冲区数量：NBUF 个（典型配置约 50-100 个）
    
- 每个 buf 由两部分组成：**缓冲数据区**（存放磁盘数据）+ **缓冲首部**（描述特性）
    

### b-list 和 av-list

这是 V6 缓冲区管理最精妙的设计 ：

**b-list（设备缓冲区队列）**：

- 每个设备维护一条 b-list，包含所有当前与该设备关联的缓冲区
    
- 通过 `b_forw` / `b_back` 双向链接
    
- 缓冲区在 b-list 上时，一定设置了 **B_BUSY**​ 标志
    

**av-list（空闲缓冲区队列）**：

- 全局唯一的空闲缓冲区队列
    
- 通过 `av_forw` / `av_back` 双向链接
    
- 按 **LRU（最近最少使用）顺序**排列——新释放的缓冲区插入队尾，分配时从队首取
    
- 缓冲区在 av-list 上时，**B_BUSY 标志为 0**
    

**核心规则**（来自 buf.h 注释）：

> "_A buffer is on the available list, and is liable to be reassigned to another disk block, if and only if it is not marked BUSY. When a buffer is busy, the available-list pointers can be used for other purposes. Most drivers use the forward ptr as a link in their I/O active queue._"

翻译过来就是：

1. 一个缓冲区**只有在非 BUSY 时**才会留在 av-list 上，可能被重新分配给其他磁盘块
    
2. 当缓冲区 BUSY 时，它的 av 指针可以被"挪作他用"——大多数驱动用 `av_forw` 作为 I/O 活动队列的链接
    

> 💡 **第一性原理洞见**：b-list 和 av-list 的"双链"设计，本质上是**用一套 buf 结构体同时维护两种索引**：
> 
> - b-list 按"设备 + 块号"索引（哈希链）——为了快速查找"我要的块是否已在内存"
>     
> - av-list 按"LRU 顺序"索引——为了快速找到"最久未用的缓冲区用于淘汰"
>     
> 
> 这种"一个数据结构，两套链表"的技巧，是早期 C 语言"零开销抽象"的典范——没有额外的 hash table，没有额外的 LRU 链表，就是 buf 结构体里多两个指针。**内存中的每一个 buf 同时挂在两条链上，查找效率和淘汰效率兼得**。

**工业联系**：

- **4.3BSD 的演化**：引入了更精细的多链表——"最近使用列表（LRU list）"、"非最近使用列表（AGE list）"、"空缓冲区列表（EMPTY list）"，并增加了按设备号和块号哈希的散列表
    
- **Linux 的 page cache**：用 `address_space` 的 radix tree（现在是 xarray）按 inode+offset 索引，用 LRU 链表做淘汰——**思想与 V6 完全一致，只是粒度从 512 字节块变成了 4KB 页面**
    
- **现代存储栈**：V6 的 b-list/av-list 思想，在今天的 Linux 块层中演化为 **bio 结构体 + request queue**——bio 是"缓冲区"，request queue 是"设备 I/O 队列"，对应关系惊人地一致
    

### RAW 输入输出

裸 I/O（Raw I/O）绕过缓冲区缓存，直接在用户内存和设备之间传输数据。适用于 ：

- 磁带等需要大块顺序传输的设备
    
- 文件系统检查工具（fsck）直接访问块设备
    
- 数据库等需要自己管理缓存的应用
    

裸设备文件的命名规则：**在对应的块设备文件名前加 `r`**。例如 `/dev/rk0` 是 `/dev/k0` 的裸版本，`/dev/rmt0` 是 `/dev/mt0` 的裸版本 。

## 7.3 缓冲区的初始化

### binit()

`binit()` 在系统启动时调用，初始化整个缓冲区池：

1. 把所有 NBUF 个 buf 结构体串成一条 **av-list**
    
2. 设置 `bfreelist`（空闲列表头）
    
3. 调用 `clrbuf()` 清空每个缓冲区
    

**关键细节**：av-list 初始化时是**空的**（只有 bfreelist 头节点），真正的 buf 是通过循环链接上去的。初始状态下，所有缓冲区都在 av-list 上，没有分配到任何设备。

### clrbuf()

`clrbuf()` 清空缓冲区内容——把 `b_addr` 指向的数据区清零。在 `binit()` 中，每个缓冲区都被清零，确保没有遗留数据。

## 7.4 缓冲区的获取和释放

这是块设备子系统的算法核心。三个关键函数：`getblk()`、`notavail()`、`brelse()`。

### getblk()

`getblk(dev, blkno)` 是缓冲区分配的核心函数，逻辑分为 5 种情况 ：

**情况 1：设备 b-list 上找到目标块且空闲**

- 在该设备的 b-list 上搜索 (dev, blkno) 组合
    
- 找到对应的块，且该块空闲（B_BUSY=0）
    
- 标记 B_BUSY=1，从 av-list 摘除，返回该缓冲区
    

**情况 2：设备 b-list 上找到目标块但正忙**

- 设置 B_WANTED 标志，表示有进程正在等待使用它
    
- 睡眠等待，直到缓冲区被释放
    

**情况 3：av-list 非空**

- 从 av-list 队首取一个缓冲区（LRU 算法——最久未用的）
    
- 如果该缓冲区有 B_DELWRI 标志（延迟写），先调用 `bwrite()` 把它写出
    
- 从原设备的 b-list 摘除，分配到新设备，返回
    

**情况 4：av-list 为空但有待写缓冲区**

- 遍历寻找有 B_DELWRI 标志的缓冲区
    
- 写出后分配
    

**情况 5：彻底没有可用缓冲区**

- 睡眠等待，直到有缓冲区被释放
    

> ⚠️ **洞见**：getblk() 的"情况 3"体现了 V6 延迟写的核心机制——**当我们需要一个新缓冲区时，如果 LRU 缓冲区上有延迟写数据，立即写出，然后重用这个缓冲区**。这保证了：
> 
> - 延迟写数据最终会被刷到磁盘
>     
> - 缓冲区分配不会死锁
>     
> - 写操作是"按需触发"的，而非定时批量
>     

### notavail()

`notavail(bp)` 把一个缓冲区标记为不可用（设置 B_BUSY），并将其从 av-list 中摘除。这是 getblk() 的内部辅助函数，用于在找到合适缓冲区后"锁定"它。

### brelse()

`brelse(bp)` 释放缓冲区，是 getblk() 的逆操作：

1. 清除 B_BUSY 标志
    
2. 如果有进程在等待这个缓冲区（B_WANTED），唤醒它们
    
3. 把缓冲区插回 av-list 的**队尾**（LRU——最近使用过的放到最后）
    

**关键细节**：brelse() 并不把缓冲区从 b-list 上摘除——它仍然与该设备关联。这样下次 getblk() 在同一个设备上查找块时，可以直接在 b-list 上命中。**b-list 是"设备缓存"，av-list 是"全局 LRU"——双重索引的精妙之处在此体现**。

> 💡 **洞见**：brelse() 把缓冲区插回 av-list **队尾**而非队首，这是一个极其重要的设计决策。它实现了精确的 **LRU（最近最少使用）算法**——最早释放的缓冲区在队首，最先被重用；最近释放的在队尾，最后被重用。整个 LRU 算法**不需要额外的时间戳或计数器**，仅仅依靠"插入队尾"这个动作就实现了。

**工业联系**：

- **Linux 的 LRU 链表**：active_list 和 inactive_list 双链表，页面在链表中移动实现 LRU——与 V6 的 av-list 思想同源
    
- **4.3BSD 的 AGE list**：引入了"年龄"概念，把 av-list 进一步分为 LRU list 和 AGE list ——这是 V6 单一 av-list 的细化
    
- **现代缓存算法**：CLOCK、ARC、LFU 等——都是 V6 的 LRU 思想在不同约束下的演化

## 7.5 读取

### 读取的种类

V6 提供三种读操作 ：

1. **bread()**：同步读——读取指定块，等待 I/O 完成
    
2. **breada()**：预读——同步读当前块，**异步**读下一个预测块
    
3. **incore()**：检查块是否在缓存中（不触发 I/O）
    

### bread()

`bread(dev, blkno)` 的流程 ：

```
bread(dev, blkno) {
    bp = getblk(dev, blkno);     // 获取缓冲区
    if (!(bp->b_flags & B_DONE)) {  // 如果数据不是最新的
        bp->b_flags |= B_READ;      // 设置为读操作
        (*bdevsw[major(dev)].d_strategy)(bp);  // 调用设备策略例程
        iowait(bp);                 // 睡眠等待 I/O 完成
    }
    return(bp);
}
```

**关键流程**：

1. `getblk()` 获取缓冲区——可能在缓存中命中（B_DONE 已设置），也可能需要从磁盘读
    
2. 如果缓存未命中，调用设备驱动的策略例程（strategy）启动磁盘 I/O
    
3. `iowait(bp)` 让进程在 bp 上睡眠，等待中断处理程序唤醒
    
4. 磁盘 I/O 完成后，中断处理程序调用 `iodone(bp)` 唤醒进程
    
5. 返回装满数据的缓冲区指针
    

### iowait()

`iowait(bp)` 让当前进程在缓冲区 bp 上睡眠，直到 I/O 完成。这是同步 I/O 的核心——进程阻塞等待磁盘操作。

### iodone()

`iodone(bp)` 由设备中断处理程序调用，标记缓冲区为 B_DONE 并唤醒等待的进程。例如 RK 磁盘驱动的中断处理程序 `rkintr()` 就会调用 `iodone()` 。

> 💡 **洞见**：iowait/iodone 是 V6 的"I/O 同步原语"，与第3章讲的 sleep/wakeup 是同一机制的不同应用。I/O 操作的本质是：**进程在缓冲区上 sleep，磁盘中断在缓冲区上 wakeup**。这种"用缓冲区作为同步事件通道"的设计，让 I/O 操作和进程调度完美融合。

### geterror()

`geterror(bp)` 检查缓冲区是否有错误标志（B_ERROR），如果有，设置 `u.u_error` 并返回错误码。这是 I/O 错误处理的标准路径。

### breada()

`breada(dev, blkno, rablkno)` 实现**预读**​ ：

```
breada(dev, blkno, rablkno) {
    bp = getblk(dev, blkno);
    if (!(bp->b_flags & B_DONE)) {
        bp->b_flags |= B_READ;
        (*bdevsw[major(dev)].d_strategy)(bp);  // 同步读主块
        iowait(bp);
    }
    if (rablkno) {
        rabp = getblk(dev, rablkno);
        if (!(rabp->b_flags & B_DONE)) {
            rabp->b_flags |= B_READ | B_ASYNC;  // 异步读预测块
            (*bdevsw[major(dev)].d_strategy)(rabp);
            // 不调用 iowait，直接返回
        }
    }
    return(bp);
}
```

**洞见**：breada() 的精妙之处在于——**同步读当前块，异步读预测块**。当前块是进程立即需要的，所以必须等；预测块是"可能下次会用到"的，所以用 B_ASYNC 标志启动 I/O 后立即返回，不阻塞进程。当进程下次真的需要预测块时，它已经在缓存中了。

**工业联系**：

- **Linux 的预读**：`do_generic_file_read()` 中实现 readahead，按 128KB 窗口预读
    
- **数据库系统的预读**：InnoDB 的线性预读、MySQL 的范围预读
    
- **现代 SSD 的预读**：控制器级别的预读机制
    

**从 V6 的 breada() 到今天的 readahead，第一性原理完全一致：用异步 I/O 隐藏磁盘延迟**。

### incore()

`incore(dev, blkno)` 检查指定块是否已在缓存中，**不触发 I/O**。它只是在该设备的 b-list 上查找，如果找到返回缓冲区指针，否则返回 NULL。这是文件系统代码判断"块是否已缓存"的快速路径。

## 7.6 写入

### 写入的种类

V6 提供三种写操作 ：

1. **bwrite()**：同步写——立即启动 I/O，等待完成
    
2. **bawrite()**：异步写——启动 I/O 但不等待（B_ASYNC）
    
3. **bdwrite()**：延迟写——标记 B_DELWRI，不立即启动 I/O
    

### bwrite()

`bwrite(bp)` 同步写 ：

```
bwrite(bp) {
    bp->b_flags &= ~(B_READ | B_DONE | B_ERROR);
    bp->b_flags |= B_WRITE;
    (*bdevsw[major(bp->b_dev)].d_strategy)(bp);  // 启动 I/O
    iowait(bp);                                   // 等待完成
    brelse(bp);                                   // 释放缓冲区
}
```

**特点**：进程阻塞直到写 I/O 完成。用于必须确保数据落盘的场景（如文件系统元数据更新）。

### bawrite()

`bawrite(bp)` 异步写 ：

```
bawrite(bp) {
    bp->b_flags |= B_ASYNC;  // 设置异步标志
    bwrite(bp);              // 启动 I/O 但不等待
}
```

**特点**：启动 I/O 后立即返回，进程不阻塞。当 I/O 完成时，`iodone()` 会自动调用 `brelse()` 释放缓冲区。

### bdwrite()

`bdwrite(bp)` 延迟写 ：

```
bdwrite(bp) {
    bp->b_flags |= B_DELWRI;  // 标记延迟写
    brelse(bp);               // 立即释放回 av-list
}
```

**特点**：数据**不立即写盘**，只在缓冲区上标记 B_DELWRI 标志，然后释放回 av-list。真正的写操作推迟到：

- 该缓冲区被 getblk() 选中需要重用时（情况 3）
    
- 系统调用 `bflush()` 强制刷新时
    
- 定期同步（sync 命令）
    

> 💡 **深度洞见**：延迟写是 V6 块设备子系统最优雅的优化之一。它基于一个观察：**对同一块的多次写入是常见模式**。例如：
> 
> - 文件系统的元数据更新（如 inode 的 mtime）
>     
> - 日志文件追加写入
>     
> - 数据库的 WAL（Write-Ahead Log）
>     
> 
> 如果用同步写，每次都要等磁盘 I/O；用延迟写，多次写入可以合并成一次物理 I/O。**延迟写本质上是"写合并"**——这是现代存储栈中 everywhere 的优化：
> 
> - Linux 的 pdflush / writeback 线程
>     
> - 文件系统的 journal 提交
>     
> - 磁盘控制器的写缓存
>     
> - SSD 的 FTL 层写入合并
>     
> 
> **V6 的 bdwrite() 是这一切的祖先**。

### bflush()

`bflush(dev)` 强制刷新指定设备上的所有延迟写缓冲区 ：

```
bflush(dev) {
    // 遍历该设备的 b-list
    // 对每个有 B_DELWRI 标志的缓冲区调用 bwrite()
}
```

**调用时机**：

- `sync()` 系统调用
    
- `umount()` 卸载文件系统
    
- 定期（V6 中约 30 秒一次，由 update 进程触发）
    

**工业联系**：现代 Linux 的 `pdflush` / `writeback` 线程、Windows 的 Lazy Writer、数据库的检查点机制——都是 bflush() 思想的现代演化。V6 的 bflush 是存储栈"后台刷盘"模式的鼻祖。

## 7.7 RAW 输入输出

### physio()

`physio(strategy, uio, dev, flags, mincnt)` 实现裸 I/O ：

```
physio(strategy, uio, dev, flags, mincnt) {
    // 1. 验证用户缓冲区的合法性
    //    - 地址对齐检查
    //    - 在进程内存边界内
    //    - 不与代码段重叠
    // 2. 构造一个临时 buf 结构体
    // 3. 设置 b_addr 指向用户缓冲区
    // 4. 调用设备策略例程启动 I/O
    // 5. iowait() 等待完成
}
```

**physio() 的关键特征**：

- **绕过缓冲区缓存**：数据直接在用户内存和设备间传输
    
- **用户缓冲区要求**：必须正确对齐、在进程内存边界内、不与代码段重叠
    
- **用于大块传输**：磁带等顺序设备的高效 I/O 路径
    

> ⚠️ **洞见**：physio() 的存在揭示了缓冲区的"两面性"：
> 
> - 对于普通文件 I/O：缓冲区缓存是**必要的抽象层**——提供预读、延迟写、共享缓存
>     
> - 对于裸设备 I/O：缓冲区缓存是**不必要的开销**——应用（如数据库）自己管理缓存，内核缓存只会拖累性能
>     
> 
> 这是"**给应用选择权**"的设计哲学。今天 Linux 的 `O_DIRECT` 标志、`raw` 设备、NVMe 的"无缓存 I/O"——都是 physio() 思想的延续。**第一性原理：当应用比内核更懂 I/O 模式时，应该允许应用绕过内核缓存**。

### swap()

`swap(blkno, coreaddr, count, direction)` 是交换空间的裸 I/O 接口 ：

```
swap(blkno, coreaddr, count, direction) {
    // 构造 buf 结构体
    // b_dev = swapdev（交换设备）
    // b_blkno = blkno（交换区块号）
    // b_addr = coreaddr（核心内存地址）
    // 调用 physio 执行 I/O
}
```

**关键作用**：第4章讲的交换处理（sched/xswap）最终调用 `swap()` 在内存和交换设备间传输进程映像。这是 V6 虚拟内存的"后端存储"路径。

**工业联系**：现代 Linux 的 `swap` 分区读写、zRAM 的压缩交换、Windows 的 pagefile.sys——都对应 V6 的 `swap()` 函数。NVMe SSD 上的 swap 分区，其 I/O 路径的思想与 V6 的 swap() 完全一致：**用裸 I/O 在内存和块设备间传输页/段**。

## 7.8 小结

第7章完成了块设备子系统的完整剖析。把所有机制串起来看：

```
用户进程 read()/write()
    ↓
文件系统层（下一章讲）
    ↓
块设备子系统
    ↓
    ├─ getblk()：分配/查找缓冲区
    │   ├─ 缓存命中 → 直接返回
    │   └─ 缓存未命中 → 从 av-list 取 LRU 缓冲区
    │       └─ 如有 B_DELWRI → bwrite() 写出
    │
    ├─ 读路径：bread() → strategy() → iowait() → 中断 → iodone()
    │          breada() 实现预读
    │
    ├─ 写路径：bwrite() 同步 / bawrite() 异步 / bdwrite() 延迟
    │          bflush() 强制刷新
    │
    └─ 裸 I/O：physio() → 绕过缓存 → 直接设备传输
                swap() 用于交换处理
    ↓
设备驱动（RK/RP/HP/RF/HT）
    ↓
物理磁盘/磁带
```

**第一性原理总结**：

1. **缓冲区缓存是"时间-空间权衡"的典范**：用内存空间换取 I/O 时间。512 字节的缓冲区、LRU 淘汰、预读、延迟写——所有机制都服务于"减少物理 I/O 次数" 。
    
2. **b-list 和 av-list 的双链设计**：一套 buf 结构体同时维护"设备索引"和"LRU 顺序"，零开销抽象 。这是早期 C 语言"极致性能"哲学的典范。
    
3. **缓冲区状态机的精妙**：B_BUSY / B_DONE / B_DELWRI / B_ASYNC / B_WANTED / B_ERROR 六个标志位，完整描述了缓冲区的生命周期 。每个标志位都是一个"状态维度"。
    
4. **同步与异步的统一**：bread/bwrite 是同步的（iowait 阻塞），bawrite/breada 是异步的（B_ASYNC 不等待）。**同一套机制支持两种 I/O 模式**。
    
5. **延迟写是"写合并"的祖先**：bdwrite 标记 B_DELWRI，真正的写操作推迟到缓冲区重用时或 bflush 强制刷新 。这是现代存储栈"writeback"机制的鼻祖。
    
6. **裸 I/O 提供"绕过缓存"的路径**：physio/swap 让应用可以直接访问设备，内核缓存不成为瓶颈 。这是现代 O_DIRECT 的祖先。
    

**跨章节联系**：

- 第3章的 `sleep()/wakeup()`：iowait/iodone 是其特化版本——在缓冲区上睡眠/唤醒
    
- 第4章的 `sched/xswap`：最终调用 `swap()` 做裸 I/O
    
- 第5章的 `clock()`：约 30 秒一次的 `sync` 更新进程调用 `bflush()`
    
- 下一章（第8章）文件系统：bread/bwrite 是文件系统读写块设备的唯一接口
    
- 下一章（第9章）字符设备：与块设备共享"主/次设备号 + 特殊文件"的抽象，但无缓冲区缓存
    

**工业落地的六点启示**：

1. **缓存是 I/O 性能的第一杠杆**：V6 用 50-100 个 512 字节缓冲区，就实现了"博尔特与乌龟接力"中博尔特的部分。今天任何涉及 I/O 的系统——数据库、Web 服务器、分布式存储——都需要精心设计的缓存层。**V6 告诉我们：缓存的有效性不在于大小，而在于策略**（LRU + 预读 + 延迟写）。
    
2. **双链表实现多维索引**：b-list 按设备+块号索引，av-list 按 LRU 顺序索引，共用同一套 buf 结构体。这种"一个数据结构，多套链表"的技巧，在今天仍然极具价值——例如 Linux 的 page 结构体同时挂在 LRU 链表、mapping 的 radix tree、进程的页表中。
    
3. **延迟写是写优化的第一性原理**：V6 的 bdwrite 告诉我们——**写操作不一定要立即落盘**。现代演化：
    
    - Linux 的 writeback 线程定期刷盘
        
    - 文件系统的 journal 提交
        
    - 数据库的 WAL 和检查点
        
    - SSD 的 FTL 写入合并
        
    - 分布式存储的 quorum write
        
        **所有这些，都是 bdwrite 思想的放大**。
        
    
4. **预读是隐藏延迟的关键**：breada 的同步读当前块 + 异步读预测块，是"用带宽换延迟"的经典模式。今天的演化：
    
    - Linux 的 readahead 窗口（默认 128KB）
        
    - 数据库的 sequential prefetch
        
    - 存储阵列的预读
        
    - CPU 的 L1/L2/L3 缓存预取
        
        **第一性原理：如果预测准确率 > 0，预读就一定划算**。
        
    
5. **裸 I/O 是性能敏感应用的逃生舱**：physio 绕过缓存，让数据库等应用自己管理 I/O。今天的演化：
    
    - Linux 的 O_DIRECT 标志
        
    - NVMe 的"无缓存 I/O"
        
    - DPDK 的用户态网卡驱动
        
    - SPDK 的用户态 NVMe 驱动
        
        **核心思想：当应用比内核更懂数据访问模式时，让应用绕过内核**。
        
    
6. **设备驱动的分派表模式**：bdevsw/cdevsw 两张表，主设备号索引，是"插件化架构"的早期典范。今天的演化：
    
    - Linux 的 `file_operations` 结构体
        
    - Windows 的 WDM/WDF 驱动框架
        
    - 微服务架构的"插件注册表"
        
        **第一性原理：用一张函数指针表实现"策略与机制分离"**。

对 V6 块 I/O 子系统的现代化梳理，清晰列出了 bread/breada/bwrite/bawrite/bdwrite/brelse/getblk 的核心行为，以及各磁盘驱动（RK/RP/HP/RF）的策略例程和电梯调度算法 。

原始手册页，明确说明了 `mknod name b|c major minor` 的用法，以及主设备号对应 `bdevsw/cdevsw` 表索引的语义 。

说明了各块设备的命名规则和主设备号分配："_The major device number is selected by counting the line number (from zero) of the device's entry in the block configuration table_" 。

John Lions 对 binit(5055)、clrbuf(5038)、getblk(4921)、brelse(4869)、bread(4754)、breada(4773)、bwrite(4809)、bawrite(4856)、bdwrite(4836)、bflush(5229)、physio(5259) 等函数的逐行注释 。

展示了 V6 缓冲区缓存思想在 4.3BSD 中的演化——引入了 LRU list、AGE list、EMPTY list 三链表结构，缓冲区大小可变（最大 8KB），并按设备号和块号哈希 。这是理解"V6 → 现代"演化路径的最佳资料。

### 7. IBM AIX 文档的 buf 结构体

现代 AIX 操作系统的 buf 结构体文档，展示了 B_BUSY/B_DONE/B_DELWRI/B_ASYNC/B_ERROR/B_WANTED 等标志位的延续 ，可作为"V6 思想在现代大型机 OS 中的存活证据"。

### 8. 现代对照表

|V6 概念|现代 Linux 对应|演进|
|---|---|---|
|buf 结构体|`struct bio` + `struct buffer_head`|缓冲区头部分离|
|b-list（设备链）|每设备 request_queue|设备 I/O 队列|
|av-list（空闲链）|LRU 链表（active/inactive）|双链表 + 反引用|
|getblk()|`__find_get_block()` + `alloc_page_buffers()`|增加了哈希查找|
|bread()|`__bread()`|增加了 endio 回调|
|breada()|`do_generic_file_read()` 中的 readahead|窗口化预读|
|bwrite()|`__block_write_full_page()`|同步写|
|bawrite()|`submit_bh()` 异步提交|BIO 异步|
|bdwrite()|`mark_buffer_dirty()`|延迟写 + writeback|
|bflush()|`writeback_thread`|后台定时刷盘|
|physio()|`O_DIRECT` I/O|绕过 page cache|
|swap()|`swap_readpage()` / `swap_writepage()`|交换页 I/O|
|512 字节块|4KB 页（可配置）|粒度变大|
|50-100 个缓冲区|占物理内存 10-20% 的 page cache|规模剧增|

## 给读者的学习建议

1. **在 PDP-11 模拟器上观察缓冲区行为**：用 simh 运行 V6，执行一系列文件操作，用调试器观察 buf 结构体的 b-list 和 av-list 变化。特别关注：
    
    - 连续读同一文件时，bread() 如何从缓存命中
        
    - 写文件时，bdwrite() 如何标记 B_DELWRI
        
    - 执行 `sync` 命令时，bflush() 如何刷盘
        
    
2. **画出 getblk() 的状态机**：把 5 种情况画成流程图，你会深刻理解"缓存未命中时如何分配缓冲区"的完整逻辑。特别注意"情况 3"中 B_DELWRI 的处理——这是延迟写与 LRU 淘汰的交汇点。
    
3. **对照 Linux 的块层**：在 Linux 上跟踪一次文件读操作：
    
    ```
    # 用 blktrace 观察块层 I/O
    sudo blktrace -d /dev/sda -o trace
    # 用 ftrace 跟踪 writeback
    sudo trace-cmd record -p function -l mark_buffer_dirty
    ```
    
    观察现代 Linux 的 I/O 路径，你会发现——**V6 的影子无处不在**。
    
4. **思考设计问题**：如果让你在现代 NVMe SSD 上重新设计 V6 的块设备子系统，你会：
    
    - 保留 512 字节块还是改成 4KB？
        
    - 保留 LRU 还是用 ARC/LFU？
        
    - 如何支持多队列（multi-queue）？
        
    - 如何支持 NVMe 的异步 I/O 队列？
        
    
    这个练习会让你深刻理解——**V6 的设计在今天的约束下该如何演化**。
