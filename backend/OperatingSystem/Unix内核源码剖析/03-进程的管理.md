
# 《Unix内核源码剖析》读书笔记 · 第3章 进程的管理I

> 第2章把"进程是什么"钉死了——proc 常驻、user 可换出、地址空间由 PDP-11 的 MMU 段寄存器定义。第3章则回答"进程怎么活起来、怎么切换、怎么死掉"。青柳隆宏在这一章铺开的是 UNIX 进程模型的**第一组系统调用原语**：fork / exec / wait / exit / break。
> 
> **第一性洞见**：UNIX 之所以伟大，不是因为它做了多少事，而是因为它用**极少的原语组合出了无限可能**。"创建进程"和"执行程序"在 V6 里是**两个独立系统调用**（fork 和 exec），而不是合并成一个"spawn"。这个看似绕弯的设计，恰恰是 UNIX 哲学"每个程序只做一件事"在内核里的体现——fork 只复制，exec 只替换，两者的正交组合赋予了 shell 流水线、重定向、后台任务等无穷威力。
> 
> 正如 UNIX 进程管理相关资料所指出，进程是"一个地址空间 + 一个执行线程"的组合，V6 提供的进程管理服务包括 fork、wait、exec、exit、kill、getpid、brk、nice、sleep 等。这一章我们逐个拆解。

## 3.1 进程的生命周期

V6 中进程从生到死经历一条明确的链路：

```
fork() → 创建子进程（复制父进程映像）
   ↓
exec() → 子进程替换为新程序
   ↓
运行 → 在 SRUN/SWAIT/SSLEEP 等状态间迁移
   ↓
exit() → 进程自我终止，进入 SZOMB（僵尸态）
   ↓
wait() → 父进程回收子进程，释放 proc 槽位
```

**关键认知**：一个进程要"彻底消失"，必须满足两个条件：(1) 进程已调用 exit 终止（或因 kill 被杀）；(2) 父进程已调用 wait 回收。如果进程已 exit 但父进程尚未 wait，它就进入**僵尸态（SZOMB）**——占据 proc 表项但不占内存。

> 💡 **洞见**：僵尸态的存在是一个**容错设计**——父进程需要子进程的退出状态（exit status）和资源使用统计（utime、stime 等），所以内核不能在 exit 时立即销毁进程的全部痕迹，必须把这些信息"挂起来"等父进程来取。这个机制从 V6 一路延续到今天的 Linux：你在 `ps aux` 里看到的 `<defunct>` 进程，就是 1975 年的设计在 2024 年的回响。

**工业联系**：如果父进程先于子进程死掉怎么办？V6 的解法是——**孤儿进程被 reparent 到 proc[1]（init 进程）**，由 init 来 wait 它们。这个"init 收养孤儿"的机制是现代 systemd、Docker init 进程的直系祖先。今天你在 Linux 容器里看到的 PID 1 进程承担的"收割僵尸子进程"职责，正是 V6 init 的当代化身。

## 3.2 创建进程

### 进程的复制

fork() 的本质是**复制**。当父进程调用 fork()，内核：

1. 在 proc[] 表中找一个空槽
    
2. 调用 `newproc()` 初始化新的 proc 和 user 结构体
    
3. 复制父进程的地址空间（代码段、数据段、栈）
    
4. 复制父进程打开的文件描述符表
    
5. 返回时，父子进程在 fork() 调用点**分别返回**——父进程拿到子进程 PID，子进程拿到 0
    

**洞见**：fork 的"全量复制"在今天看来效率低下（想想 fork 一个占用 2GB 内存的进程），但在 V6 时代这是合理的——因为：

- PDP-11 上进程内存通常很小（几十 KB）
    
- 更重要的是，**fork 之后几乎总是紧跟 exec**，复制的数据马上就被丢弃
    

这就引出了 UNIX 史上最精妙的设计之一：**fork/exec 分离**。shell 启动程序的经典代码：

```
while (1) {
    printf("$");
    readcommand(command, args);
    if ((pid = fork()) == 0) {
        exec(command, args, 0);
    } else if (pid > 0) {
        wait(pid);
    }
}
```

fork 只复制，exec 才替换——两者正交。这种"组合优于集成"的思想，是现代管道（`cmd1 | cmd2`）、重定向（`cmd > file`）、后台任务（`cmd &`）能够实现的基石。如果 UNIX 当初选择把"创建并加载"合并成一个 spawn 系统调用（像 Windows 的 CreateProcess），那么 shell 的这些优雅语法就不可能如此简单地实现。

> 📌 **创新视角**：fork/exec 的分离体现了**第一性原理式的极简**——把"进程创建"和"程序加载"两个关注点解耦，让每个原语都最简单。这种"正交原语组合"的设计哲学，比任何"一体化"设计都更具扩展性。今天我们在微服务架构中提倡的"单一职责 + 组合"，早在 1975 年的内核里就已经是基本原则。

### 父进程和子进程

fork 之后，父子进程的**关键差异**：

|字段|父进程|子进程|
|---|---|---|
|p_pid|原有 PID|新分配 PID|
|p_ppid|不变|设为父进程 PID|
|返回值|子进程 PID|0|
|文件描述符|共享同一组文件表项|复制 fd 表，但指向相同的 file 结构|
|地址空间|独立|独立（复制父进程）|

注意"文件描述符共享"这一点——父子共享 file 结构意味着共享文件偏移量。这是 UNIX 管道能够工作的基础：父进程 fork 后关闭不需要的 fd 端，子进程也关闭不需要的端，剩下的一对 fd 就构成了单向管道。

### 系统调用 fork

fork 的入口在 `sys1.c`，核心是调用 `newproc()`。fork 本身的代码很短，大部分工作在 newproc() 里完成。

### newproc()

这是第3章最硬核的函数之一。`newproc()` 的职责：

1. **分配 proc 槽位**：遍历 proc[]，找 p_stat == NULL 的空槽
    
2. **复制 proc 结构体**：从父进程复制大部分字段到子进程，但调整：
    
    - p_pid：分配新 PID
        
    - p_ppid：设为父进程 PID
        
    - p_stat：设为 SIDL（创建中间态）
        
    
3. **复制 user 结构体**：把父进程的 user 区完整复制到为子进程分配的新 user 区
    
4. **复制地址空间**：
    
    - 代码段：如果可共享，增加引用计数；否则分配新代码段
        
    - 数据段 + 栈：物理内存复制
        
    
5. **子进程上下文设置**：
    
    - 在子进程的 user 结构体中设置内核栈，使得 swtch() 切到子进程时，子进程从 fork() 返回 0
        
    - 关键技巧：在子进程的 u_rsav 中伪造现场，让 swtch() 返回时就像从 fork() 返回一样
        
    

> ⚠️ **难点提示**：newproc() 里最精妙的部分是"让子进程从 fork() 返回 0"。这是通过在子进程的保存现场中**修改返回地址的返回值**实现的——父进程在 fork 返回点得到子进程 PID，子进程在同一返回点得到 0，但两者的代码执行路径完全相同。这种"一次调用，两次返回"的魔法，是 UNIX 学习者必须跨越的认知门槛。

### panic()

panic() 是内核的"临终遗言"函数。当内核遇到不可恢复的错误时调用，打印错误信息后进入死循环或重启。

**何时会 panic**？在 newproc() 中，如果 proc 表已满（NPROC=50）无法分配新槽位，如果内存不足无法复制地址空间——这些都可能导致 panic 或相关错误处理。

**工业联系**：现代 Linux 内核仍然有 `panic()` 函数，行为类似：打印内核 oops、dump 堆栈、根据 `kernel.panic` 参数决定是重启还是停住。V6 的 panic 是现代内核崩溃机制的鼻祖。今天你在 Linux 生产环境看到的 kernel panic 日志，其精神血脉可以直接追溯到 V6。

## 3.3 切换执行进程

这是第3章的第二个硬核小节，涉及调度器的核心：`swtch()`。正如有关 V6 调度代码的著名分析所指出的：**整个 swtch() 函数大约只有一页代码**——这是操作系统史上最令人震撼的"极小化"成就。

### 中断执行进程

PDP-11 通过时钟中断（约每 60Hz 一次）周期性剥夺当前进程的 CPU。时钟中断处理程序：

1. 进入内核态
    
2. 调用 `setpri()` 动态调整当前进程优先级
    
3. 如果需要抢占，调用 `swtch()` 切换进程
    

### 进程的执行状态

回顾第2章的 6 个状态，在调度场景下最相关的是：

- **SRUN**：可运行（在内存中或在交换区等待换入）
    
- **SWAIT / SSLEEP**：睡眠中，等待某事件
    
- **SZOMB**：僵尸态
    

调度器只关心 `p_stat == SRUN && (p_flag & SLOAD)` 的进程——即可运行**且**在内存中的进程。

### 选择执行进程的算法

swtch() 的调度算法极度简单——**全局扫描 proc[]，选出 p_pri 值最小的（优先级最高的）SRUN 且 SLOAD 的进程**：

```
i = NPROC;
do {
    rp++;
    if (rp >= &proc[NPROC]) rp = &proc[0];
    if (rp->p_stat == SRUN && (rp->p_flag & SLOAD) != 0) {
        if (rp->p_pri < n) {  // n 是当前最小优先级
            n = rp->p_pri;
            p = rp;
        }
    }
} while (--i);
```

**洞见**：这是 O(N) 的线性扫描，N=50。在今天看来低效至极，但在 V6 的时代——50 个进程、几 MHz 的 CPU——这是最务实的选择。**不要盲目崇拜"高效算法"，要匹配硬件规模**。今天 Linux 的 O(1) 调度器、CFS 的红黑树，都是因为进程数量爆炸式增长（现代系统动辄上千进程）才成为必要。如果 V6 也用红黑树，那就是过度设计。

优先级是**动态调整**的：

- 时钟中断处理程序中调用 `setpri()` 根据进程最近使用的 CPU 时间调整 p_pri
    
- CPU 密集型进程优先级逐渐降低（p_pri 值增大）
    
- I/O 密集型/交互型进程优先级升高
    
- 这是**最简单的公平调度思想**——给 I/O bound 进程更高优先级，系统响应性更好
    

### 上下文切换

`swtch()` 是 V6 最神秘的函数，也是 Lions 注释本里最有名的一段。它的三步曲：

**第一步：保存当前进程现场**

```
savu(u.u_rsav);  // 保存 r5, sp 到 user 结构体的 u_rsav
```

savu 是汇编宏，把当前栈指针和 r5 保存到指定位置。

**第二步：借用 proc[0] 的中转**

swtch() 先把地址空间切到 proc[0]（调度进程），然后在 proc[0] 的上下文中执行调度算法，选出下一个进程。

**第三步：恢复新进程现场**

```
retu(p->p_addr);  // 切换地址空间到新进程
aretu(p->p_rsav); // 恢复新进程的 r5, sp
```

> 📌 **著名的"你不该理解这个"注释**：在 swtch() 的第 2238 行，Dennis Ritchie 留下了操作系统史上最著名的代码注释——"You are not expected to understand this." 这是因为 savu/retu/aretu 对栈指针和程序计数器的复杂操作，在没有深刻 PDP-11 汇编和内核内存管理知识的情况下几乎无法理解。

**洞见**：为什么需要 proc[0] 作为"调度进程中转站"？因为上下文切换的本质矛盾是——**你要切换掉当前进程的地址空间，但切换代码本身必须有一个稳定的执行环境**。proc[0] 提供了一个"中立的、永远在内存中的"内核地址空间，让 swtch() 能安全地完成"杀死自己、复活别人"的操作。

**工业联系**：现代 Linux 的 `context_switch()` 做着完全相同的事——保存 prev 进程现场、切换 mm 和栈、恢复 next 进程现场。区别在于：

- 现代 CPU 有硬件上下文切换支持（x86 的 TSS）
    
- 现代调度器用运行队列（rq）而非全局扫描
    
- 但有意思的是，**xv6（MIT 的教学 OS）几乎原封不动地复刻了 V6 的 swtch() 思想**——用汇编保存/恢复寄存器，用调度线程作为中转。这证明 V6 的上下文切换设计是"第一性正确"的。
    

### 系统调用 wait

wait() 让父进程阻塞，直到有一个子进程退出。它的实现：

1. 遍历 proc[]，找 p_ppid == 当前进程 PID 的子进程
    
2. 如果找到 SZOMB 状态的子进程，立即回收，返回其 PID 和退出状态
    
3. 如果没有子进程退出，调用 `sleep()` 让自己睡在 `&proc[1]` 事件上
    
4. 当某个子进程 exit 时，会 wakeup 父进程
    

### sleep()

`sleep(chan, pri)` 是 V6 最基本的同步原语：

```
sleep(chan, pri) {
    // 当前进程在 chan 事件上睡眠
    proc->p_wchan = chan;
    proc->p_pri = pri;
    proc->p_stat = SSLEEP;  // 或 SWAIT
    swtch();  // 让出 CPU
    // 被 wakeup 后从这里返回
}
```

**核心思想**：sleep 释放处理器（通过 swtch），wakeup 使线程再次可运行，以便 swtch 在未来的某个时刻选择它运行。

> 💡 **洞见**：sleep/wakeup 是 V6 的"信号量雏形"。它没有现代 semaphores 的计数语义，但提供了**基于事件通道（chan）的等待/通知机制**。多个进程可以睡在同一个 chan 上，wakeup(chan) 会唤醒所有这些进程。这是最简单的"多生产者-多消费者"同步模型。

**工业联系**：xv6 的 sleep/wakeup 几乎逐行复刻了 V6，但加了一把锁（proc_table_lock）来解决"丢失唤醒"问题：

```
void sleep(void *chan, struct spinlock *lk) {
    // 必须持锁进入，保证不会错过 wakeup
    acquire(&proc_table_lock);
    release(lk);
    cp->chan = chan;
    cp->state = SLEEPING;
    sched();
    // 醒来后重新获取原锁
}
```

Linux 内核的 `wait_event()` / `wake_up()` 宏族是 sleep/wakeup 的现代演化，本质机制完全一致。

### swtch() 的返回位置

这是 V6 最烧脑的部分。一个进程调用 swtch() 让出 CPU 后，**未来某个时刻会被别的进程通过 swtch() 切回来**，从当年让出 CPU 的那条 swtch() 调用之后继续往下执行。

关键认知：

- swtch() 不是"调用一次返回一次"的普通函数
    
- 它是"调用一次，未来在某个不确定的时间点返回"的神奇函数
    
- 一个进程的 swtch() 返回，必定对应另一个进程的 swtch() 调用
    

这种"协程式"的切换模型，和现代线程库的 `swapcontext()` 是同一种思想。

### setpri()

`setpri()` 在时钟中断中被调用，根据进程最近的 CPU 使用情况动态调整 p_pri：

```
setpri(pp) {
    pp->p_pri = (pp->p_cpu/4) + 2*pp->p_nice + 2*BASE;
    if (pp->p_pri > 127) pp->p_pri = 127;
    pp->p_cpu >>= 1;  // CPU 使用率衰减
}
```

**洞见**：这是**最简单的反馈控制系统**——CPU 用得越多，优先级越低；随着时间推移，p_cpu 衰减，优先级回升。整个算法不到 10 行代码，却实现了"惩罚 CPU 密集型进程、奖励 I/O 密集型进程"的公平调度策略。现代 CFS（Completely Fair Scheduler）的"虚拟运行时间"思想，在 V6 这里已经有了雏形。

### wakeup()

`wakeup(chan)` 遍历 proc[]，把所有睡在 chan 上的进程状态改为 SRUN，使它们下次 swtch() 时可能被选中：

```
wakeup(chan) {
    for (rp = &proc[0]; rp < &proc[NPROC]; rp++) {
        if (rp->p_wchan == chan && rp->p_stat == SSLEEP) {
            rp->p_stat = SRUN;
            rp->p_wchan = 0;
            setpri(rp);  // 重置优先级
        }
    }
}
```

### setrun()

`setrun()` 是把进程标记为可运行的辅助函数，通常在进程从交换区换入后调用，设置 p_stat = SRUN 并可能触发调度。

## 3.4 执行程序

### 程序执行文件的格式

V6 的 exec() 支持三种 a.out 格式，由文件头部的魔数区分：

- **0407**：非纯文本（impure）——代码段和数据段混合在一个段里
    
- **0410**：纯文本（pure text）——代码段独立、只读、可共享
    
- **0411**：纯文本 + 分离的指令/数据空间（PDP-11 的 I/D 分离模式）
    

格式头部还包含：

- 代码段长度（tsize）
    
- 数据段长度（dsize）
    
- 符号表信息
    
- 程序入口点
    

> 💡 **洞见**：区分"纯文本"和"非纯文本"是 V6 支持**代码段共享**的关键。多个进程 exec 同一个程序（如 `/bin/ls`）时，如果该程序是 pure text 格式，它们的代码段可以共享同一块物理内存——这是对 PDP-11 极小内存的极致优化。

### 系统调用 exec

exec() 的流程（以 0410 纯文本格式为例）：

1. **读取并验证 a.out 头部**
    
2. **建立新地址空间**：
    
    - 调用 `xalloc()` 分配/查找代码段
        
    - 分配数据段和栈段
        
    - 调用 `estabur()` 设置用户地址空间寄存器
        
    
3. **加载程序**：
    
    - 把代码段从文件读入（如果是 pure text，可能已在交换区有备份）
        
    - 把数据段从文件读入
        
    - 设置用户栈，压入 argv 和 envp
        
    
4. **设置寄存器现场**：
    
    - 设置 PC 指向程序入口点
        
    - 设置 SP 指向栈顶
        
    - 设置用户寄存器初始值
        
    
5. **返回用户态**：从 trap 返回，进程开始执行新程序
    

**关键挑战**（正如课程讲义所指出的）：如何建立地址空间并设置带有参数的栈。exec() 要在用户地址空间中布局新程序，并把 argc/argv 压到用户栈上，这样新程序从 main(argc, argv) 启动时才能正确取到参数。

> ⚠️ **exec 不改变 PID**：exec 是"替换进程映像"，PID、父进程关系、打开的文件描述符都保持不变。这正是 fork/exec 组合能够工作的关键——shell fork 出子进程（继承 shell 的文件描述符），然后子进程 exec 新程序（继承文件描述符，所以标准输入输出重定向能够生效）。

### estabur()

`estabur()` 设置 PDP-11 的用户地址空间寄存器（PAR/PDR），定义进程的虚拟地址空间布局：

```
estabur(tsize, dsize, ssize, sep, xrw) {
    // 设置代码段寄存器
    // 设置数据段寄存器
    // 设置栈段寄存器
    // 检查总大小是否超过限位
}
```

参数：

- tsize：代码段大小
    
- dsize：数据段大小
    
- ssize：栈段大小
    
- sep：是否 I/D 分离
    
- xrw：执行/读/写权限
    

### sureg()

`sureg()` 把 user 结构体中保存的地址空间原型（`u_uisa[]` 和 `u_uisd[]`）加载到硬件 MMU 寄存器。每次进程被切换进来时调用。

### expand()

`expand()` 调整进程数据段（+栈段）的大小，是 `break()` 系统调用的底层实现。它的挑战在于：

- 扩大时：需要分配新的物理内存，可能需要先换出其他进程腾出空间
    
- 缩小时：释放物理内存
    
- 整个过程可能涉及**自身被换出**——这是 V6 中最微妙的场景之一
    

> 📌 **洞见**：正如 UNIX V6 内部分析所指出的，当进程在 expand() 等操作中被换出时，调用栈可能包含各种中间状态。V6 的解法是——**不尝试恢复复杂的调用栈，而是直接丢弃**，让进程回到被换出前的那个点重新执行。这种"要么全有要么全无"的事务性思想，是早期操作系统处理复杂资源分配时的常见策略。

---

## 3.5 进程的终止

### 系统调用 exit

exit() 执行进程的自我清理：

1. **释放资源**：
    
    - 关闭所有打开的文件描述符
        
    - 释放数据段和栈段内存
        
    - 释放代码段（如果引用计数归零）
        
    
2. **通知父进程**：
    
    - 向父进程发送信号（SIGCHLD 的雏形）
        
    - wakeup 父进程（如果父进程正在 wait 上睡眠）
        
    
3. **进入僵尸态**：
    
    - 设置 p_stat = SZOMB
        
    - 保存退出状态到 proc 结构体
        
    - 保存资源使用统计（utime, stime）
        
    
4. **调用 swtch()**：让出 CPU，永不返回
    

**洞见**：exit() 之后进程永远不会"自己"再运行——它要么被父进程 wait 回收（proc 槽位释放），要么永远以僵尸态存在直到父进程死亡后被 init 收养。

### 系统调用 wait

wait() 的完整语义：

1. 遍历 proc[] 找自己的子进程
    
2. 如果找到 SZOMB 子进程：
    
    - 取回退出状态和资源统计
        
    - 释放子进程的 proc 槽位
        
    - 返回子进程 PID
        
    
3. 如果没有 SZOMB 子进程但有其他子进程在运行：
    
    - sleep 在 `&proc[1]` 事件上
        
    - 被子进程 exit 时的 wakeup 唤醒后重试
        
    
4. 如果没有任何子进程：
    
    - 返回错误（ECHILD）
        
    

> 💡 **工业联系**：今天 Linux 的 `wait()`, `waitpid()`, `wait4()` 系统调用，语义与 V6 完全一致。Java 的 `Process.waitFor()`、Python 的 `subprocess.wait()`、Go 的 `cmd.Wait()`——所有这些用户态 API 的底层，都是 V6 在 1975 年定义的 wait 语义。

## 3.6 数据区域的扩展

### 系统调用 break

`break()`（在 V6 系统调用表中编号为 17，对应 sbreak）用于调整进程数据段的末尾（break point）。它调用 `expand()` 来实际调整数据段大小。

**用途**：

- malloc 的实现底层依赖 sbrk/brk 来调整堆大小
    
- 程序初始化时设置数据段大小
    

**洞见**：V6 的 break 系统调用是**堆内存管理的最底层接口**。今天你在 Linux 上调用 malloc()，最终会通过 brk 或 mmap 系统调用向内核申请内存——而这个 brk 系统调用的语义，与 V6 的 sbreak 几乎完全相同。45 年了，这个接口的核心契约没变过。

## 3.7 管理内存和交换空间

这是第3章最优雅的一小节——V6 用**同一个极简数据结构**管理两类资源：主存（coremap）和交换区（swapmap）。

### map 结构体

```
struct map {
    char *m_size;  // 块数（连续单元的数量）
    char *m_addr;  // 空白区域起始地址
};
```

这是一个**极简的资源映射表**——每个表项描述一段连续的空闲区域（大小和起始地址）。表以 m_size == 0 的项结尾。

**关键事实**：

- coremap 的单位是 64 字节
    
- swapmap 的单位是 512 字节
    
- coremap 和 swapmap 都是 `int[100]` 数组，但被 reinterpret 为 `struct map` 使用
    

> 💡 **洞见**：这种"int 数组 + struct map reinterpret"的技巧，是早期 C 语言"弱类型"特性的典型应用。作者们知道 int 是 16 位、char* 也是 16 位，所以直接把 int[100] 当作 struct map[50] 来用。**这种"类型双关（type punning）"在现代 C 中是不安全的，但在 V6 的时代是家常便饭**——它反映了早期系统编程"程序员完全清楚内存布局"的文化。

### 获取未使用区域

`malloc(map *mp, int size)` 实现 first-fit 分配算法：

```
malloc(mp, size) {
    for (bp = mp; bp->m_size; bp++) {
        if (bp->m_size >= size) {
            a = bp->m_addr;
            bp->m_addr += size;
            if ((bp->m_size -= size) == 0) {
                // 当前块被分配完，后面的块前移
                do {
                    bp++;
                    (bp-1)->m_addr = bp->m_addr;
                    (bp-1)->m_size = bp->m_size;
                } while ((bp-1)->m_size > 0);
            }
            return(a);
        }
    }
    return(0);  // 分配失败
}
```

**洞见**：整个分配器只有 15 行代码。它用的是最简单的 **first-fit 算法**——遍历空闲块链表，找到第一个够大的块就分配。没有 btree、没有 segregated free list、没有 buddy system。为什么？因为 V6 管理的内存通常很小（coremap 最多管理 256K 字），first-fit 的 O(n) 复杂度完全可接受。

**工业联系**：有趣的是，first-fit 今天在某些场景下仍然是合理选择——比如内核的某些早期启动阶段内存分配器、实时系统中可预测性比速度更重要的场景。但主流用户态 malloc（ptmalloc、jemalloc、tcmalloc）早已转向更复杂的算法，因为：

- 内存规模从 KB 级变成 GB 级
    
- 碎片化问题变得严重
    
- 多核并发要求无锁分配
    

但 V6 的 map 结构思想并未消失——**Linux 内核的 buddy allocator 仍然用"按阶管理的空闲块链表"**，本质上就是 map 结构体的多维扩展。

### 释放区域

`mfree(map *mp, int size, int aa)` 释放内存：

```
mfree(mp, size, aa) {
    // 遍历找到合适位置插入
    // 与相邻空闲块合并（coalescing）
}
```

**关键操作**：释放时要检查前后是否有相邻的空闲块，如果有则**合并**成一个更大的块。这是防止碎片化的基本手段。

> ⚠️ **注意**：V6 的 mfree 在合并时有个隐含假设——调用者保证不会重复释放同一块内存。没有现代分配器的"double free 检测"。这反映了早期操作系统的设计哲学：**内核信任自身代码，不浪费指令做防御性检查**。

## 3.8 小结

第3章完成了进程管理第一组原语的完整剖析。把它们串起来看：

```
fork ──→ 复制进程映像（newproc）
   ↓
exec ──→ 替换进程映像（estabur, sureg, expand）
   ↓
[运行] ──→ 调度切换（swtch, sleep, wakeup, setpri）
   ↓
exit ──→ 自我终止，进入僵尸态
   ↓
wait ──→ 父进程回收子进程
```

**第一性原理总结**：

1. **fork/exec 的正交分解**：创建与加载解耦，赋予 shell 无穷的组合能力。这是 UNIX 哲学在内核层面的第一个胜利。
    
2. **swtch 的三步曲**：保存现场 → proc[0] 中转选优 → 恢复新现场。这个"通过调度进程中转"的模式，是上下文切换的第一性原理——你总得有个"不被切换掉的稳定执行环境"。
    
3. **sleep/wakeup 的事件模型**：用 `chan` 作为事件通道，多对多的等待/通知。这是同步原语的极简起点。
    
4. **map 结构的统一资源管理**：用同一个 first-fit 分配器管理主存和交换区。极简数据结构的力量。
    
5. **动态优先级反馈**：CPU 用得越多优先级越低，10 行代码实现公平调度。
    

**跨章节联系**：

- 第2章的 proc/user 结构体，在本章被 newproc() 实际填充和使用
    
- 第2章的 PDP-11 MMU 段寄存器，在本章被 estabur()/sureg() 实际操作
    
- 本章的 expand() 和内存管理，为第4章"交换处理"埋下伏笔——当 expand 失败、内存不足时，sched() 会介入换出进程
    
- 本章的 sleep/wakeup，将在第5章"中断与陷入"中与硬件中断处理深度结合
    

**工业落地的五点启示**：

1. **正交原语 > 一体化接口**：fork/exec 分离的设计，比 Windows 的 CreateProcess 更灵活。今天我们在设计 API 时也应追求"最小正交原语集"。
    
2. **调度算法的复杂度要匹配规模**：V6 的 O(N) 扫描在 N=50 时完美，在 N=5000 时必须升级。不要过度设计，也不要低估规模增长。
    
3. **上下文切换必须有"中立中转站"**：无论是 V6 的 proc[0]，还是现代 OS 的 idle 线程/swapper 线程，这个"永远在内存中的调度执行环境"是必需的。
    
4. **资源管理用 first-fit 起步**：当你设计一个新的资源管理系统时，先用 first-fit 跑起来，再根据实际情况优化。V6 证明了 first-fit 在适当规模下的生命力。
    
5. **僵尸态是"信息交接"的必要代价**：父进程需要子进程的退出信息，所以子进程不能完全消失。理解这一点，你就能理解为什么现代分布式系统中的"孤儿任务回收"、容器编排中的"僵尸容器清理"都是同样的问题。
