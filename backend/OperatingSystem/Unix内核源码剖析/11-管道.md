
# 《Unix内核源码剖析》读书笔记 · 第11章 管道

> 前几章我们建立了完整的"文件处理"框架——fd → file → inode → 数据块。用户程序用 `open/read/write/close` 这套统一接口操作普通文件、设备文件、目录。但有一个关键的 IPC（进程间通信）场景没解决：**两个进程如何交换数据？**
> 
> V6 之前的答案是**临时文件**——`progA > temp; progB < temp; rm temp`。能用，但笨拙：浪费磁盘 I/O、需要清理、速度慢。
> 
> **第一性洞见**：管道的本质，是**用"文件抽象"承载"内存字节流"**。V6 的 pipe() 系统调用只做了几件事——在内存中分配一个 inode 作为缓冲区，创建两个 file 结构体（一个读端、一个写端），让它们指向同一个 inode，返回两个 fd 。就这样，**"文件"不再是磁盘上的数据，而是内存中的字节流**；**"读写文件"不再是磁盘 I/O，而是 sleep/wakeup 协调的进程间通信**。
> 
> 正如 V6 源码 pipe.c 中的注释所说——"_Allocate an inode on the root device. Allocate 2 file structures. Put it all together with flags._" ——管道就是用"临时 inode + 两个 file"拼出来的 。这种"**用已有抽象解决新问题**"的设计，是 UNIX 哲学的最高体现：**不发明新机制，而是用现有机制的新组合**。

---

## 11.1 什么是管道

管道（pipe）是 UNIX 的进程间通信原语，提供一个**单向的字节流**通道：

- **写端**：进程向管道写入数据
    
- **读端**：另一个进程从管道读取数据
    
- **内核缓冲区**：数据写在内存中，不落盘
    
- **fd 接口**：管道的两端是两个文件描述符，可用 `read()/write()` 系统调用操作
    

### 使用管道的优点

相比"临时文件"方案，管道的革命性优势 ：

1. **零磁盘 I/O**：数据完全在内存中缓冲（V6 中 PIPSIZ = 4096 字节）
    
2. **自动清理**：管道的生命周期由 fd 的引用计数管理，进程退出时自动释放
    
3. **同步语义**：管道满时写进程阻塞，管道空时读进程阻塞——内核自动协调生产者和消费者
    
4. **统一接口**：管道用与普通文件完全相同的 `read()/write()/close()` 接口，shell 不需要特殊语法
    
5. **组合能力**：`ls | grep | wc` 这样的流水线，本质是多个进程通过管道串联
    

> 💡 **洞见**：管道"零磁盘 I/O + 自动清理"的优势，揭示了它的第一性原理——**用内核缓冲区替代临时文件，把"进程间通信"伪装成"文件读写"**。这是 UNIX "一切皆文件"哲学的巅峰之作：管道在用户态看起来就是两个 fd，在内核态就是一个 inode + 一块内存缓冲区。

**工业联系**：今天你在 Linux 上运行的每一个 shell 流水线（`ls | grep | awk | sort | uniq`），其底层机制与 V6 的管道**字节级兼容**。1975 年写的 shell 脚本，今天在 Linux 6.x 上仍然能跑——这是 UNIX 哲学"保持简单"的最大回报 。

## 11.2 开始管道通信

### 系统调用 pipe

V6 的 `pipe()` 系统调用源码 ：

```
pipe() {
    register *ip, *rf, *wf;
    int r;
    
    // 1. 在根设备分配一个 inode（作为管道的缓冲区）
    ip = ialloc(rootdev);
    if (ip == NULL) return;
    
    // 2. 分配读端的 file 和 fd
    rf = falloc();
    if (rf == NULL) {
        iput(ip);
        return;
    }
    r = u.u_ar0[R0];  // 保存读端 fd
    
    // 3. 分配写端的 file 和 fd
    wf = falloc();
    if (wf == NULL) {
        rf->f_count = 0;
        u.u_ofile[r] = NULL;
        iput(ip);
        return;
    }
    
    // 4. 在 R0/R1 中返回两个 fd（传统 UNIX 做法：两个 fd 都在寄存器中返回）
    u.u_ar0[R1] = u.u_ar0[R0];  // R1 = 写端 fd
    u.u_ar0[R0] = r;            // R0 = 读端 fd
    
    // 5. 设置写端 file：FWRITE|FPIPE，指向 ip
    wf->f_flag = FWRITE|FPIPE;
    wf->f_inode = ip;
    
    // 6. 设置读端 file：FREAD|FPIPE，指向 ip
    rf->f_flag = FREAD|FPIPE;
    rf->f_inode = ip;
    
    // 7. 关键：inode 引用计数设为 2（读端和写端各一个引用）
    ip->i_count = 2;
    ip->i_flag = IACC|IUPD;
    ip->i_mode = IALLOC;
}
```

**pipe() 的四个关键设计**：

1. **inode 作为缓冲区**：管道的数据存储在 inode 指向的内存块中，PIPSIZ = 4096 字节
    
2. **两个 file 指向同一个 inode**：读端 file 的 f_inode 和写端 file 的 f_inode 都指向 ip
    
3. **FPIPE 标志**：标记这是管道而非普通文件，使 read/write 分派到 readp/writep
    
4. **i_count = 2**：读端和写端各持有一个引用，只有当两端都关闭时，inode 才会被释放
    

> ⚠️ **关键认知**：V6 的 pipe() 在 R0 和 R1 两个寄存器中返回两个 fd 。这是"传统 UNIX 做法"——现代 Linux 的 pipe() 系统调用改为将 fd 写入用户态数组 `pipe(fd[2])`，但 V6 时代 R0/R1 双寄存器返回是惯例 。

**洞见**：pipe() 用"临时 inode"实现管道，这个 inode 的 i_mode 被设为 IALLOC（已分配）且标记 FPIPE。有趣的是，**如果 PIPSIZ 大于 4096，管道会退化为使用 LARG 文件（大文件间接寻址）——但 Ken Thompson 明确说过不建议这样做**​ 。这揭示了管道设计的一个隐含约束：**管道应该是"小缓冲、高吞吐"的，不应该被当作大容量存储**。

## 11.3 收发数据

管道的读写通过 `writep()` 和 `readp()` 实现，它们是 `writei()` 和 `readi()` 的管道特化版本。

### writep()

`writep(fp)` 向管道写入数据 ：

```
writep(fp) {
    register *rp, *ip, c;
    rp = fp;
    ip = rp->f_inode;
    c = u.u_count;  // 需要写的剩余字节数
    
loop:
    plock(ip);  // 锁定管道 inode
    
    // 1. 写完所有数据，返回
    if (c == 0) {
        prele(ip);
        u.u_count = 0;
        return;
    }
    
    // 2. 检查管道两端是否都打开
    //    ip->i_count < 2 意味着某一端已关闭
    if (ip->i_count < 2) {
        prele(ip);
        u.u_error = EPIPE;           // Broken pipe 错误
        psignal(u.u_procp, SIGPIPE); // 发送 SIGPIPE 信号
        return;
    }
    
    // 3. 管道已满（i_size1 >= PIPSIZ），写进程睡眠
    if (ip->i_size1 == PIPSIZ) {
        ip->i_mode |= IWRITE;  // 标记有写进程在等待
        prele(ip);
        sleep(ip+1, PPIPE);    // 睡在 ip+1 通道上
        goto loop;             // 被唤醒后重试
    }
    
    // 4. 有空间，写入数据
    u.u_offset[0] = 0;
    u.u_offset[1] = ip->i_size1;  // 从当前数据末尾开始写
    u.u_count = min(c, PIPSIZ - u.u_offset[1]);
    c = -u.u_count;  // 更新剩余字节数
    writei(ip);      // 调用 writei 实际写入（通过 i_addr 指向的内存缓冲）
    prele(ip);
    
    // 5. 唤醒等待读的进程
    if (ip->i_mode & IREAD) {
        ip->i_mode &= ~IREAD;
        wakeup(ip+2);  // 唤醒睡在 ip+2 通道上的读进程
    }
    
    goto loop;  // 继续写剩余数据
}
```

**writep() 的核心机制**：

1. **plock/prele 锁定**：用管道的 inode 作为锁对象，保证读写操作的原子性
    
2. **EPIPE 检测**：`i_count < 2` 意味着读端已关闭，写端收到 EPIPE 错误 + SIGPIPE 信号
    
3. **满管道阻塞**：管道数据达到 PIPSIZ 时，写进程在 `ip+1` 通道上睡眠
    
4. **部分写入循环**：一次系统调用可能无法写完所有数据（管道满了），writep 循环写入直到完成
    
5. **唤醒读进程**：写入数据后，如果有读进程在等待，立即唤醒
    

### readp()

`readp(fp)` 从管道读取数据 ：

```
readp(fp) {
    register *rp, *ip;
    rp = fp;
    ip = rp->f_inode;
    
loop:
    plock(ip);  // 保守锁定
    
    // 1. 读偏移追上写偏移（管道为空）
    if (rp->f_offset[1] == ip->i_size1) {
        if (rp->f_offset[1] != 0) {
            // 重置读写偏移为 0（循环缓冲区的"折叠"）
            rp->f_offset[1] = 0;
            ip->i_size1 = 0;
            // 唤醒等待写的进程
            if (ip->i_mode & IWRITE) {
                ip->i_mode &= ~IWRITE;
                wakeup(ip+1);
            }
        }
        
        // 2. 检查管道两端是否都打开
        prele(ip);
        if (ip->i_count < 2) {
            // 写端已关闭，返回 EOF（u.u_count 保持原值，表示 0 字节读取）
            return;
        }
        
        // 3. 管道为空，读进程睡眠
        ip->i_mode |= IREAD;
        sleep(ip+2, PPIPE);  // 睡在 ip+2 通道上
        goto loop;
    }
    
    // 4. 有数据，读取
    u.u_offset[0] = 0;
    u.u_offset[1] = rp->f_offset[1];
    readi(ip);
    rp->f_offset[1] = u.u_offset[1];
    prele(ip);
}
```

**readp() 的核心机制**：

1. **空管道检测**：读偏移 == 写偏移（i_size1）意味着管道为空
    
2. **EOF 语义**：写端关闭（`i_count < 2`）且管道为空时，read 返回 0 字节（EOF）
    
3. **阻塞读**：管道为空且写端仍打开时，读进程在 `ip+2` 通道上睡眠
    
4. **循环缓冲区**：当读写偏移相等且非 0 时，重置两者为 0——实现环形缓冲区的"折叠"
    
5. **唤醒写进程**：读走数据后，如果有写进程在等待，立即唤醒
    

### plock() 和 prele()

`plock(ip)` 和 `prele(ip)` 是管道的锁机制 ：

```
plock(ip) {
    register *rp;
    rp = ip;
    while (rp->i_flag & ILOCK) {
        rp->i_flag |= IWANT;
        sleep(rp, PPIPE);
    }
    rp->i_flag |= ILOCK;  // 设置锁
}

prele(ip) {
    register *rp;
    rp = ip;
    rp->i_flag &= ~ILOCK;  // 清除锁
    if (rp->i_flag & IWANT) {
        rp->i_flag &= ~IWANT;
        wakeup(rp);  // 唤醒等待锁的进程
    }
}
```

**关键设计**：

1. **plock/prele 是 inode 级别的锁**——管道的 inode 充当互斥锁
    
2. **ILOCK 标志**：表示 inode 已被锁定
    
3. **IWANT 标志**：表示有进程在等待锁
    
4. **sleep/wakeup 协调**：plock 在锁被占用时睡眠，prele 释放锁时唤醒等待者
    

> 💡 **洞见**：plock/prele 是 V6 的"自旋锁 + 睡眠锁"混合体——它先用忙等检查锁（while 循环），如果锁被占用则睡眠。这是单 CPU 时代的典型锁实现：因为只有一个 CPU，睡眠后锁的持有者肯定能运行并释放锁。**多核时代这种做法不再安全**，现代 Linux 用 spinlock + mutex 替代——但 V6 的 plock/prele 是第一代"内核对象锁"的雏形。

**writep 和 readp 的协同**：

```
写进程                        读进程
──────                        ──────
writep():
  plock(ip)
  检查 i_count >= 2
  检查管道有空间
  writei() 写入数据
  wakeup(ip+2)  ←── 唤醒 ──→  readp():
  prele(ip)                   plock(ip)
                                读数据
                                wakeup(ip+1)  ←── 唤醒 ──→  回到 writep 的 loop:
                                                            plock(ip)
                                                            继续写剩余数据
```

**这是生产-消费者模型的经典实现**——writep 是生产者，readp 是消费者，管道缓冲区是有限容量的队列，plock/prele 是互斥锁，sleep/wakeup 是条件变量。**今天你在任何编程语言中看到的"线程安全的阻塞队列"，其第一性原理与 V6 的 writep/readp 完全一致**。

## 11.4 结束管道通信

### closef()

管道的关闭通过第10章讲的 `closef()` 函数实现。当管道的某一端被关闭时：

1. **递减 file.f_count**：如果 f_count 归零，释放 file 结构体
    
2. **调用 closei()**：递减 inode.i_count
    
3. **关键**：对于管道（FPIPE 标志），closei() 会**唤醒对端**：
    
    - 关闭写端 → 唤醒睡在 `ip+2` 上的读进程（让读进程感知到 EOF）
        
    - 关闭读端 → 唤醒睡在 `ip+1` 上的写进程（让写进程收到 EPIPE）
        
    

> ⚠️ **关键语义**：管道的生命周期由**两端的引用计数**共同决定：
> 
> - 只有当**两端都关闭**（`i_count == 0`）时，管道的 inode 才被真正释放
>     
> - 如果只关闭一端，管道仍然存在，另一端继续工作
>     
> - 写端关闭后，读端继续读取剩余数据，然后收到 EOF（read 返回 0）
>     
> - 读端关闭后，写端继续写入会收到 SIGPIPE 信号 + EPIPE 错误
>     

**工业联系**：这就是今天你在 Linux 上看到的"Broken pipe"错误的来源——**1975 年 V6 的第一性原理，在 2024 年的 Linux 上仍然成立**。

## 11.5 建立管道通信的流程

### 建立父子进程间的通信

管道最常用的场景是**父子进程通信**。典型流程：

```
父进程：
1. pipe(fd[2])  → 创建管道，fd[0]=读端, fd[1]=写端
2. fork()       → 创建子进程
3. if (子进程) {
       close(fd[1]);        // 子进程关闭写端
       dup2(fd[0], 0);      // 将读端复制到 stdin
       exec("wc");          // 执行 wc，从 stdin 读取
   } else {
       close(fd[0]);        // 父进程关闭读端
       dup2(fd[1], 1);      // 将写端复制到 stdout
       exec("ls");          // 执行 ls，向 stdout 写入
   }
```

**关键机制**：

1. **fork 继承管道**：子进程继承父进程的 fd 表，所以父子共享同一个管道的两个 file 结构体（f_count 递增）
    
2. **关闭不需要的端**：父子各自关闭不用的端，确保 `i_count` 正确反映活跃端点数
    
3. **dup2 重定向**：用 dup2 将管道的读/写端复制到 stdin/stdout，使得子进程执行的程序**完全不知道**自己在和管道通信——它以为自己在读写终端
    
4. **exec 保持 fd**：exec 不关闭 fd（除非设置了 CLOSE_ON_EXEC 标志），所以管道在 exec 后仍有效
    

> 💡 **洞见**：这就是 `ls | wc` 的底层实现机制。shell 作为父进程：
> 
> - 创建管道
>     
> - fork 出两个子进程
>     
> - 将管道写端 dup 到第一个子进程的 stdout
>     
> - 将管道读端 dup 到第二个子进程的 stdin
>     
> - 两个子进程分别 exec ls 和 wc
>     
> 
> **ls 和 wc 完全不知道管道的存在**——它们只是读写 fd 1 和 fd 0。这就是 UNIX "组合优于集成"哲学的终极体现：**shell 用 pipe + fork + dup2 + exec 这四个原语，构建出任意复杂的流水线**。

### 系统调用 dup

`dup(fd)` 复制文件描述符——创建一个新 fd，指向与 fd 相同的 file 结构体：

```
dup() {
    // 1. 获取原 fd 对应的 file
    fp = getf(u.u_arg[0]);
    if (fp == NULL) return;
    
    // 2. 分配新 fd
    newfd = ufalloc();
    if (newfd < 0) return;
    
    // 3. 新 fd 指向同一个 file，递增引用计数
    u.u_ofile[newfd] = fp;
    fp->f_count++;
    
    // 4. 返回新 fd
    u.u_ar0[R0] = newfd;
}
```

**dup 在管道中的关键作用**：

- **dup2(fd, 0)**：将 fd 复制到 stdin，使得后续 exec 的程序从管道读取
    
- **dup2(fd, 1)**：将 fd 复制到 stdout，使得后续 exec 的程序向管道写入
    
- **管道共享**：dup 递增 file.f_count，使得多个 fd 指向同一个 file 结构体
    

> 📌 **洞见**：dup 是管道实现 shell 流水线的"胶水"。没有 dup，fork 出的子进程就无法将管道的读/写端重定向到 stdin/stdout。dup 的本质是**"让多个 fd 指向同一个打开文件描述"**——今天 Linux 的 `dup/dup2/dup3` 系统调用，与 V6 的 dup 机制完全一致。

## 11.6 小结

第11章完成了 V6 管道的完整剖析。把所有机制串起来看：

```
pipe() 系统调用
    ↓
    ├─ ialloc() 分配 inode（管道缓冲区，PIPSIZ=4096）
    ├─ falloc() × 2 分配两个 file 结构体
    ├─ 读端 file: FREAD|FPIPE，f_inode = ip
    ├─ 写端 file: FWRITE|FPIPE，f_inode = ip
    ├─ ip->i_count = 2（读端+写端）
    └─ 返回两个 fd（R0=读端, R1=写端）
    ↓
fork() + dup2() + exec()
    ↓
父子进程通过管道通信
    ↓
write() → writep():
    ├─ plock(ip) 加锁
    ├─ 检查 i_count >= 2（管道两端都打开）
    ├─ 管道满？sleep(ip+1) 阻塞
    ├─ writei() 写入数据
    ├─ wakeup(ip+2) 唤醒读进程
    └─ prele(ip) 解锁
    ↓
read() → readp():
    ├─ plock(ip) 加锁
    ├─ 管道空？sleep(ip+2) 阻塞
    ├─ readi() 读取数据
    ├─ wakeup(ip+1) 唤醒写进程
    └─ prele(ip) 解锁
    ↓
close() → closef():
    ├─ file.f_count--
    ├─ 若 f_count 归零：closei() → iput()
    ├─ 若 i_count 归零：释放 inode 和数据块
    └─ 唤醒对端（让对端感知 EOF 或 EPIPE）
```

**第一性原理总结**：

1. **管道 = "文件抽象" + "内存缓冲区"**：pipe() 用 ialloc 分配 inode 作为缓冲区，用 falloc 创建两个 file 结构体。管道在用户态表现为两个 fd，在内核态表现为一个 inode + 一块内存 。
    
2. **FPIPE 标志实现"多态"**：file.f_flag 的 FPIPE 位使得 read/write 系统调用分派到 readp/writep 而非普通的 readi/writei。这是 V6 "统一接口 + 内部多态"哲学在 IPC 领域的应用。
    
3. **i_count = 2 是管道的"心跳"**：读端和写端各持有一个引用，i_count 反映管道两端的活跃状态。i_count < 2 意味着某一端已关闭，触发 EOF 或 EPIPE 语义 。
    
4. **plock/prele 是管道的锁**：用 inode 的 ILOCK 标志实现互斥，保证 writep/readp 的原子性。这是 V6 单 CPU 时代的"睡眠锁"实现。
    
5. **sleep/wakeup 实现同步**：writep 在 `ip+1` 通道上睡眠（管道满），readp 在 `ip+2` 通道上睡眠（管道空）。匹配的 wakeup 调用实现生产-消费者协调 。
    
6. **循环缓冲区**：管道的 i_size1（写偏移）和 file.f_offset（读偏移）实现环形缓冲区语义。当读写偏移相等且非 0 时，readp 重置两者为 0（"折叠"） 。
    
7. **EPIPE/SIGPIPE 是"写向虚空"的回应**：当写端尝试写入但读端已关闭时，V6 返回 EPIPE 错误并发送 SIGPIPE 信号 。这是 6th Edition UNIX 首次引入的语义 。
    

**跨章节联系**：

- **第2章的 proc/user 结构体**：u_ofile[NOFILE] 是管道的 fd 载体
    
- **第3章的 fork**：fork 复制 u_ofile 数组，父子共享管道 file 结构体（f_count 递增）
    
- **第3章的 sleep/wakeup**：writep/readp 的阻塞机制完全依赖 sleep/wakeup
    
- **第5章的中断与陷入**：wakeup 在内核上下文执行，最终由调度器切换进程
    
- **第6章的信号**：EPIPE 时 psignal 发送 SIGPIPE
    
- **第9章的文件系统**：pipe() 用 ialloc 分配 inode，用 iget/iput 管理生命周期
    
- **第10章的文件处理**：read/write/close/dup 系统调用是管道的用户态接口
    

**工业落地的五点启示**：

### 1. **"用已有抽象解决新问题"是最高效的设计**

V6 的管道没有发明任何新机制——它复用了 inode、file、fd、sleep/wakeup、ialloc、falloc 等所有已有构件。这种"**组合优于集成**"的设计哲学，使得管道的代码量极小（pipe.c 总共只有约 100 行 ），却实现了强大的 IPC 能力。今天的设计启示：

- Docker 容器网络用"veth pair + bridge"组合，而非发明新虚拟设备
    
- Kubernetes 的 Service 用"iptables/ipvs + ClusterIP"组合，而非修改内核
    
- Web 框架的中间件用"装饰器 + 责任链"组合，而非重写 HTTP 处理
    

### 2. **fd 是整数句柄的极致威力**

管道的威力完全建立在"fd 是整数"这一事实上——因为 fd 是整数，所以：

- 可以用 `dup2(fd, 0/1)` 重定向
    
- 可以用 `fork()` 继承
    
- 可以用 `close()` 关闭
    
- shell 可以用 `cmd1 | cmd2 | cmd3` 语法构建任意长度的流水线
    

今天 Linux 的 **io_uring**、**eventfd**、**timerfd**、**signalfd**​ 等都是这一思想的延续——**任何内核对象，只要能用 fd 表示，就能享受 fd 的所有操作**。

### 3. **生产-消费者模型的第一性原理**

writep/readp 是生产-消费者模型的经典实现：

- **互斥**：plock/prele（相当于今天的 mutex）
    
- **条件变量**：sleep/ip+1/ip+2（相当于今天的 condition variable）
    
- **有限缓冲区**：PIPSIZ = 4096 字节（相当于今天的 bounded queue）
    

今天你在任何语言中看到的"线程安全阻塞队列"（Java 的 `ArrayBlockingQueue`、Python 的 `queue.Queue`、Go 的 `chan`），其第一性原理与 V6 的管道**完全一致**。

### 4. **引用计数管理 IPC 资源生命周期**

管道的 inode 生命周期由两个引用计数共同决定：

- **file.f_count**：每个 fd 的引用
    
- **inode.i_count**：管道两端的引用
    

只有当所有引用都释放时，资源才被回收。这是今天**智能指针（shared_ptr）、RAII、垃圾回收**共同的第一性原理。V6 用 C 语言手动实现了自动资源管理——比 C++ 的智能指针早 20 年。

### 5. **管道语义的稳定性是 UNIX 的最大遗产**

从 V6（1975）到 Linux 6.x（2024），管道的**核心语义 50 年未变**​ ：

- 单向字节流
    
- 两个 fd（读端/写端）
    
- 阻塞读写
    
- EOF 语义（写端关闭后读端收到 EOF）
    
- EPIPE/SIGPIPE 语义（读端关闭后写端收到错误）
    

所有的演化都是**加法式**的 ：

- **POSIX.1-1988**：正式标准化，PIPE_BUF 最小 512 字节
    
- **Linux 2.6.11**：默认管道容量从 4096 增至 65536 字节（16 页）
    
- **Linux 2.6.17**：引入 splice(2)/tee(2)/vmsplice(2) 实现零拷贝
    
- **Linux 2.6.27**：pipe2() 支持 O_CLOEXEC/O_NONBLOCK
    
- **Linux 2.6.35**：F_SETPIPE_SZ/F_GETPIPE_SZ 支持动态调整管道容量
    
- **Linux 3.4**：O_DIRECT 标志支持包模式
    
- **Linux 5.8**：O_NOTIFICATION_PIPE 支持内核事件通知
    

**工业联系**：

- **现代 Linux 管道实现**（fs/pipe.c）：用 `pipe_inode_info` 结构体管理环形缓冲区，包含 `pipe_buffer` 数组、锁、等待队列等
    
- **splice/tee 零拷贝**：允许数据完全在内核空间传递，避免用户态-内核态拷贝
    
- **io_uring + pipe**：现代高性能网络框架用 io_uring 的 pipe 支持，实现异步、零拷贝的数据流处理
    
- **Docker/K8s 的日志管道**：容器运行时（containerd、CRI-O）用管道将容器标准输出转发到日志收集系统
    
- **Shell 流水线**：`ps aux | grep nginx | awk '{print $2}' | xargs kill`——这条命令在 V6 上能跑，在 Linux 6.x 上也能跑

## 英文补充资料与跨时代对照

### 1. V6 管道源码原典（pipe.c）

最权威的资料——V6 源码中 pipe()、readp()、writep()、plock()、prele() 的完整实现 。特别是：

- pipe() 中的注释："_Allocate an inode on the root device. Allocate 2 file structures. Put it all together with flags._"
    
- writep() 中的 EPIPE 检测："_If there are not both read and write sides of the pipe active, return error and signal too._"
    
- PIPSIZ 定义："_Max allowable buffering per pipe. This is also the max size of the file created to implement the pipe. If this size is bigger than 4096, pipes will be implemented in LARG files, which is probably not good._"
    

### 2. "Two File Descriptors and a Revolution: The Birth of Pipes in UNIX"

这篇文章精彩地总结了管道的革命性意义 ："_Before pipes, programs lived alone. If you wanted one program's output to be consumed by another, you had to use temporary files._" 并详细分析了 pipe() 源码的每一行。

### 3. "How are Unix pipes implemented?"

深度分析了 writep/readp 的协同机制 ："_On entry, we want to write u.u_count bytes into the pipe... The real magic happens in sleep() and wakeup()_"，并指出了 6th Edition 是 EPIPE 错误码和 SIGPIPE 信号首次引入的版本 。

### 4. xv6 的管道实现（现代教学对照）

xv6 是 V6 的现代 RISC-V 重写，管道实现演化为 ：

```
struct pipe {
    char data[PIPESIZE];  // PIPESIZE = 512
    uint nread;           // 读取指针
    uint nwrite;          // 写入指针
    int readopen;         // 读端是否打开
    int writeopen;        // 写端是否打开
};
```

xv6 用独立的 `struct pipe` 替代 V6 的"inode 复用"——这是架构上的清晰化，但**第一性原理完全一致**：两个 file 指向同一个 pipe 对象，一个可读一个可写 。

### 5. "Pipe Mechanics" 演化时间线

详细记录了管道从 1973 年至今的演化 ：

- 1973: V3 首次引入 pipe，缓冲区 504 字节
    
- 1974: V4 用 C 语言重写，缓冲区增至 4096 字节（PIPSIZ）
    
- 1975: V6 完善 EPIPE/SIGPIPE 语义
    
- 1988: POSIX.1 标准化 pipe()
    
- 2005: Linux 2.6.11 管道容量 4096 → 65536
    
- 2006: Linux 2.6.17 splice/tee/vmsplice 零拷贝
    
- 2008: Linux 2.6.27 pipe2() 支持 O_CLOEXEC/O_NONBLOCK
    
- 2010: Linux 2.6.35 F_SETPIPE_SZ 动态调整容量
    

### 6. 现代对照表

|V6 概念|现代 Linux 对应|演化|
|---|---|---|
|pipe() 分配 inode|`do_pipe()` → `create_pipe_inode()` → `pipe_inode_info`|从"复用 inode"到"独立 pipe_inode_info 结构体"|
|PIPSIZ = 4096|默认管道容量 65536（16 页）|容量增加 16 倍|
|i_count = 2|`pipe_inode_info.readers/writers` 计数|从单一计数到读写端独立计数|
|FPIPE 标志|`file->f_op = &pipefifo_fops`|从标志位判断到函数指针表分派|
|plock/prele（ILOCK 睡眠锁）|`pipe->mutex` + `spinlock`|从单 CPU 睡眠锁到多核 mutex + spinlock|
|sleep(ip+1)/wakeup(ip+1)|`wait_event()` / `wake_up()`|从简单 sleep/wakeup 到等待队列|
|sleep(ip+2)/wakeup(ip+2)|`wait_event()` / `wake_up()`|同上|
|i_size1 写偏移|`pipe_buffer.head/tail` + 环形缓冲区|从线性偏移到真正的环形缓冲区|
|f_offset[1] 读偏移|`pipe_buffer.head/tail`|同上|
|EPIPE + SIGPIPE|EPIPE + SIGPIPE|语义 50 年未变|
|`pipe(fd[2])` 用户数组|`pipe2(fd[2], flags)`|增加 flags 参数（O_CLOEXEC/O_NONBLOCK）|
|无 splice/tee|`splice(2)` / `tee(2)` / `vmsplice(2)`|零拷贝数据移动|
|固定 4096 容量|`fcntl(fd, F_SETPIPE_SZ, size)`|动态调整容量|
|无包模式|`O_DIRECT` 包模式|数据报语义|
|无 epoll 集成|`epoll_ctl(fd, EPOLL_CTL_ADD, ...)`|管道 fd 可被 epoll 监听|
|无 eventfd/timerfd|`eventfd(2)` / `timerfd_create(2)`|新型"管道类"fd|
|io_uring 不支持|`io_uring` 异步 I/O 支持 pipe|管道纳入现代异步 I/O 框架|

> 💡 **跨时代洞见**：从 V6 到现代 Linux，管道的**第一性原理完全一致**：
> 
> - **两个 fd**：一个读端、一个写端
>     
> - **单向字节流**：数据从写端流向读端
>     
> - **内核缓冲区**：数据在内存中缓冲，不落盘
>     
> - **阻塞语义**：空管道阻塞读、满管道阻塞写
>     
> - **EOF 语义**：写端关闭后读端收到 EOF
>     
> - **EPIPE 语义**：读端关闭后写端收到 EPIPE + SIGPIPE
>     
> - **引用计数管理生命周期**：i_count/file.f_count 决定资源释放
>     
> 
> 变的是**规模**（4096 → 65536 字节）、**并行度**（单 CPU 睡眠锁 → 多核 mutex + spinlock）、**能力**（增加了 splice 零拷贝、pipe2 标志、动态调整容量、io_uring 异步支持）。但**骨架——pipe() 创建两个 fd 指向共享缓冲区——50 年没变**。
> 
> 正如 "Pipe Mechanics" 文章所总结的 ："_The design is remarkably stable. The core semantics of pipe() — unidirectional byte stream between two file descriptors — have not changed since 1973. Every addition has been strictly additive, preserving backward compatibility. Code written for V7 Unix pipes in 1979 still works unmodified on Linux 6.x._"
> 
> 理解 V6 的管道，你就拿到了理解现代 Linux 管道、shell 流水线、Docker 日志管道、io_uring 异步管道的"源代码"。

## 给读者的学习建议

1. **在 Linux 上观察管道的现代演化**：
    
    ```
    # 观察管道容量
    mkfifo test_pipe
    cat /proc/sys/fs/pipe-max-size  # 查看最大管道容量
    
    # 观察 splice 零拷贝
    cat /proc/sys/fs/pipe-user-pages-soft  # 查看每用户管道页软限制
    
    # 用 strace 跟踪 shell 流水线
    strace -f -e trace=pipe,dup2,execve sh -c "ls | wc -l"
    # 你会看到：pipe() → fork() → dup2() → execve() 的精确序列
    ```
    
2. **画出 writep/readp 的状态机**：
    
    ```
    管道状态：空 → 部分填充 → 满 → 部分填充 → 空
    
    写进程：
      plock → 检查 i_count → 检查满？
        满 → sleep(ip+1) → 被 readp 的 wakeup(ip+1) 唤醒 → 重试
        不满 → writei → wakeup(ip+2) → 继续写
    
    读进程：
      plock → 检查空？
        空 → 检查 i_count < 2？
            是 → 返回 EOF
            否 → sleep(ip+2) → 被 writep 的 wakeup(ip+2) 唤醒 → 重试
        不空 → readi → wakeup(ip+1) → 继续读
    ```
    
    理解这个状态机，你就理解了生产-消费者模型的精髓。
    
3. **对照 xv6 学习现代演化**：
    
    - V6：管道复用 inode，用 i_size1/f_offset 表示读写偏移
        
    - xv6：管道用独立的 `struct pipe`，用 nread/nwrite 环形缓冲区
        
    - Linux：管道用 `pipe_inode_info` + `pipe_buffer[]` 数组，支持多页缓冲
        
    
    观察这一演化路径，你会看到"**从复用现有结构到独立专用结构**"的架构清晰化过程。
    
4. **思考设计问题**：如果让你为现代 100 核 CPU + NVMe 的服务器重新设计 V6 的管道，你会：
    
    - 保留"两个 fd"模型吗？还是改用更现代的接口？
        
    - 如何处理 100 核同时读写同一管道的锁竞争？（提示：Linux 用 mutex + spinlock + 每 CPU 变量）
        
    - 如何支持零拷贝？（提示：splice/tee）
        
    - 如何支持异步 I/O？（提示：io_uring）
        
    
    这个练习会让你深刻理解——**V6 的管道架构在今天的约束下该如何演化**。答案就在现代 Linux 的 fs/pipe.c：它保留了 V6 的核心语义（两个 fd、单向字节流、阻塞读写），但在每一层都做了多核优化和零拷贝扩展。
