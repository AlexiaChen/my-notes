
# 《Unix内核源码剖析》读书笔记 · 第14章 启动系统

> 前13章我们逐一剖析了 V6 的各个子系统——进程管理、内存管理、中断与系统调用、块设备、缓冲区高速缓存、文件系统、文件处理、管道、字符设备、终端。但这些子系统"是谁启动的"？内核从 PDP-11 加电的那一刻起，到多用户登录提示符出现的那一刻止，中间经历了什么？第14章回答的就是这个"操作系统生命周期的起点"问题。
> 
> **第一性洞见**：V6 的启动流程是一条**"硬件引导 → 汇编建栈 → C 的 main() 初始化 → 手工制造进程 0 → fork 出进程 1 执行 /etc/init → 进入调度循环"**​ 的单线链路。整条链路最精妙的地方在于——**"进程 0"不是 fork 出来的，而是内核用手工方式"捏"出来的；进程 1 也不是 fork 出来的普通进程，而是通过"内核内置的一段 icode 机器码 + exec(/etc/init)"凭空生成的**。正如 TUHS 邮件列表中所总结的 ："_After the usual initialization, the '0th' process ... is hand-crafted; it then forks into two, using the standard UNIX fork() system call ... The second process then runs a tiny program (the binary for which is built into the kernel) which does an exec() system call, to read in and run /etc/init._"
> 
> 这就是 UNIX "**用一个进程孵化所有进程**"哲学的最早实践——今天你在 Linux 上看到的 `systemd`（PID 1）的祖先，可以追溯到 V6 的这个手工制造的进程 0 和 exec 出来的 `/etc/init`。

---

## 14.1 启动的流程

V6 的启动是一个**多级引导**过程，每一级都只做"加载下一级并跳转"这一件事：

### 第一级：硬件引导（ROM Bootstrap）

Lions 注释本详细记录了操作员在 PDP-11 控制台的动作 ：

1. 将 "enable/halt" 开关拨到 "halt"，停止处理器
    
2. 在开关寄存器中设置硬件引导加载程序（bootstrap loader）的地址
    
3. 按下并释放 "load address" 开关
    
4. 将 "enable/halt" 开关拨到 "enable"
    
5. 按下并释放 "start" 开关
    

这激活了**永久记录在处理器 ROM 中的引导程序**。ROM 引导程序从系统盘的 **0 号块**加载一个更大的引导程序，这个更大的引导程序负责寻找并加载名为 **`/unix`**​ 的文件到内存低地址处，然后将控制权转移到地址 0 处的指令 。

> 💡 **洞见**：`/unix` 是操作系统内核的目标代码文件。它由一组源文件（如我们研究的这些）正常编译并链接在一起，形成单一的目标程序文件，存储在根目录中 。这意味着 V6 的内核是**静态链接**的单一映像——没有模块、没有动态加载、没有 initramfs。这与现代 Linux 形成鲜明对比：现代 Linux 内核通常是压缩映像（bzImage）+ initramfs 的两段式加载。但**第一性原理一致**：引导程序找到内核映像 → 载入内存 → 跳转执行。

### 第二级：start()（汇编入口）

地址 0 处是一条分支指令，跳转到 000040 处的跳转指令，再跳转到 `m40.s` 文件中标记为 `start` 的指令（第 0612 行）。`start()` 是**用汇编语言写的**，它的任务是**建立最基本的执行环境**——在 C 语言的 main() 能够运行之前，必须有栈和段表 。

Lions 对 `start()` 的剖析 ：

1. **0613**: 测试内存管理状态寄存器 SR0 的 "enabled" 位。如果已设置，处理器将永远停留在一个两条指令的循环中。这通常是因为操作员在启动系统前激活了控制台上的 "clear" 按钮来清除该位。这个循环的原因可能是：在双总线超时错误的情况下，处理器会分支到地址 0，此时不应允许它继续往下执行。
    
2. **0615**: 执行 `reset`，清除并初始化所有外围设备的控制和状态寄存器。此时系统运行在**内核模式且内存管理禁用**的状态下。
    
3. **0619**: 初始化内核段寄存器。`KISA0` 和 `KISD0` 是前一对内核模式段寄存器的核心地址。前 6 个内核描述符寄存器被初始化为 `077406`（描述一个完整的 4K 字、读写段）。前 6 个内核地址寄存器分别初始化为 0, 0200, 0400, 0600, 01000, 01200。结果，前 6 个内核段被初始化为指向物理内存的前 6 个 4K 字段。**"内核到物理地址"的转换对于 0 到 0137777 范围内的内核地址是平凡的**。
    
4. **0632**: `end` 是一个加载器伪变量，定义了程序代码和数据区的范围。这个值向上舍入到 64 字节的倍数，存储在第七段（段 #6）的地址寄存器中。注意这个寄存器的地址存储在 `ka6` 中，因此该寄存器的内容可作为 `*ka6` 访问。
    
5. **0634**: 相应的描述符寄存器被加载一个值（因为 `USIZE` 等于 16）描述的是一个读写段，长度为 16 × 32 = 512 字。值 `007406` 是通过将八进制值 017 左移 8 位，然后与值 6 进行"或"运算得到的。
    

**start() 的核心使命**：

> **用最少的汇编指令，建立起 C 语言运行所需的最小环境——内核段表（KISA/KISD）、栈指针、内存管理状态**。在 start() 执行完毕时，内核仍然运行在"内存管理禁用"状态，但已经拥有了正确的段寄存器布局，使得 C 函数可以开始执行。

> ⚠️ **关键认知**：V6 的 `start()` 与现代 Linux 的 `head.S` / `boot/compressed/head.S` 是同一角色——都是"汇编编写的、内核第一条 C 代码前的最后一步"。现代 Linux 启动流程：`BIOS → GRUB → head.S（建立页表）→ startup_64() → start_kernel()`；V6 启动流程：`ROM → block 0 loader → /unix 载入 → start()（建立段表）→ main()`。架构骨架高度一致。

### 第三级：main()（C 语言初始化）

`main()` 是 V6 的 C 语言入口点，源码在 `sys/main.c` 第 01879 行 。Lions 注释本给出了完整源码 ：

```
/*
 * Initialization code.
 * Called from cold start routine as
 * soon as a stack and segmentation
 * have been established.
 * Functions:
 * clear and free user core
 * turn on clock
 * hand craft 0th process
 * call all initialization routines
 * fork - process 0 to schedule
 * - process 1 execute bootstrap
 *
 * loop at low address in user mode -- /etc/init
 * cannot be executed.
 */
main()
{
    startup();

    /*
     * set up system process
     */
    proc[0].p_addr = ka6->r[0];
    proc[0].p_size = USIZE;
    proc[0].p_stat = SRUN;
    proc[0].p_flag |= SLOAD|SSYS;
    proc[0].p_nice = NZERO;
    u.u_procp = &proc[0];
    u.u_cmask = CMASK;

    /*
     * Initialize devices and
     * set up 'known' i-nodes
     */
    clkstart();
    cinit();
    binit();
    iinit();
    rootdir = iget(rootdev, (ino_t)ROOTINO);
    rootdir->i_flag &= ~ILOCK;
    u.u_cdir = iget(rootdev, (ino_t)ROOTINO);
    u.u_cdir->i_flag &= ~ILOCK;
    u.u_rdir = NULL;

    /*
     * make init process
     * enter scheduling loop
     * with system process
     */
    if(newproc()){
        expand(USIZE + (int)btoc(szicode));
        estabur((unsigned)0, btoc(szicode), (unsigned)0, 0, RO);
        copyout((caddr_t)icode, (caddr_t)0, szicode);
        /*
         * Return goes to loc. 0 of user init
         * code just copied out.
         */
        return;
    }
    sched();
}
```

**main() 的执行可分为四个阶段**：

#### 阶段一：startup()——前置初始化

调用 `startup()` 完成一些汇编/C 边界的清理工作——清除和释放用户内存空间。

#### 阶段二：手工制造进程 0（"hand craft 0th process"）

```
proc[0].p_addr = ka6->r[0];  // 进程 0 的内存地址 = 当前内核栈地址
proc[0].p_size = USIZE;      // 进程大小 = USIZE（16 块）
proc[0].p_stat = SRUN;       // 状态：可运行
proc[0].p_flag |= SLOAD|SSYS; // 标志：已加载 + 系统进程
proc[0].p_nice = NZERO;      // 优先级：默认
u.u_procp = &proc[0];        // 当前 user 结构体的 u_procp 指向进程 0
u.u_cmask = CMASK;           // 文件创建掩码
```

**这是 V6 最精妙的设计之一**——进程 0 不是 fork 出来的（因为此时还没有任何进程可以 fork），而是内核**直接用赋值语句"捏"出来的**：

- `p_addr` 指向当前内核栈（因为 main() 当前就运行在这个栈上）
    
- `p_stat = SRUN` 标记为可运行
    
- `p_flag` 的 `SSYS` 位标记它是**系统进程**（不会出现在用户进程列表中）
    
- `u.u_procp` 指向 proc[0]，使得后续代码可以"假装"自己就是进程 0
    

Lions 注释本指出 ："_`sched` is executed by process #0, which after completing its initial tasks, spends its time in a double role: openly as the scheduler i.e. a normal kernel process; and surreptitiously as the intermediate process of `swtch`_"。也就是说，**进程 0 永不终止**——它永远作为调度器运行，并且在 `swtch()` 上下文切换中扮演"中间进程"的角色 。

#### 阶段三：初始化所有子系统

```
clkstart();   // 启动时钟
cinit();      // 初始化字符设备缓冲区池
binit();      // 初始化块设备缓冲区池
iinit();      // 初始化 inode 表
rootdir = iget(rootdev, (ino_t)ROOTINO);  // 获取根目录 inode
rootdir->i_flag &= ~ILOCK;                // 清除锁
u.u_cdir = iget(rootdev, (ino_t)ROOTINO); // 设置当前工作目录
u.u_cdir->i_flag &= ~ILOCK;
u.u_rdir = NULL;                          // 无根目录（chroot 尚未实现）
```

**这是 V6 所有子系统的"总开关"**：

- `clkstart()`：启动时钟中断，这是**多任务调度的时间基准**
    
- `cinit()`：第12章讲的字符设备缓冲区池初始化
    
- `binit()`：第7章讲的块设备缓冲区池初始化
    
- `iinit()`：第9章讲的 inode 表初始化
    
- `iget(rootdev, ROOTINO)`：获取根目录的 inode，建立 `u.u_cdir`
    

> 💡 **洞见**：`main()` 中这几行初始化调用，是**全书前13章所有子系统的"集结号"**。在你读到第14章时回头看：
> 
> - `clkstart()` 对应第5章的时钟中断
>     
> - `cinit()` 对应第12/13章的字符设备
>     
> - `binit()` 对应第7章的缓冲区高速缓存
>     
> - `iinit()` 对应第9章的文件系统
>     
> - `iget(ROOTINO)` 对应第9/10章的 iget 和 u.u_cdir
>     
> 
> **main() 把前13章的所有独立子系统"焊接"成一个完整的操作系统**。

#### 阶段四：fork 出进程 1，执行 /etc/init

```
if(newproc()){
    // 这里是子进程（进程 1）的执行路径
    expand(USIZE + (int)btoc(szicode));
    estabur((unsigned)0, btoc(szicode), (unsigned)0, 0, RO);
    copyout((caddr_t)icode, (caddr_t)0, szicode);
    return;  // 返回到刚刚拷贝到地址 0 的 icode 代码
}
sched();  // 父进程（进程 0）进入调度循环
```

**这是 V6 启动最神奇的部分**：

1. **`newproc()`**：调用标准的 fork 系统调用内部函数，创建进程 0 的一个副本——进程 1。此时进程 1 几乎是进程 0 的完全克隆。
    
2. **`expand()` + `estabur()` + `copyout()`**：在进程 1 的用户空间地址 0 处，**拷贝一段内核内置的机器码 `icode`**。这段 icode 是一个**极小的程序**，它的唯一功能就是执行 `exec("/etc/init")` 系统调用 。
    
3. **`return`**：当进程 1 从 main() 返回时，由于用户空间地址 0 已经被 icode 占据，CPU 会"返回"到 icode 的入口点——也就是开始执行 icode。
    
4. **icode 执行 `exec("/etc/init")`**：将 `/etc/init` 程序加载到进程 1 的用户空间，替换掉 icode。此时进程 1 变成了 `/etc/init` 进程（PID 1）。
    
5. **`sched()`**：进程 0（父进程）调用 `sched()` 进入**永久调度循环**。如 TUHS 邮件所总结的 ："_The '0th' process (which in V6 has the task of swapping processes in and out) is hand-crafted; it then forks into two_"。进程 0 从此成为**交换守护进程 + 调度器**。
    

**洞见**：这段代码的精妙之处在于——**它用"标准 UNIX 工具"（fork + exec）完成了"创建第一个用户进程"这个非凡任务**。没有任何特殊的"创建用户进程"系统调用，纯粹是用 fork 克隆自己 + 用 exec 替换成 /etc/init。这是 UNIX "组合优于集成"哲学的最高体现：

- 不用为"启动 init"发明新机制
    
- 复用 fork（创建进程副本）
    
- 复用 exec（替换进程映像）
    
- 复用 icode（内核内置的微型引导程序）
    

今天你在 Linux 上看到的启动过程——`kernel_init()` 线程 fork 出 `/sbin/init`（或 systemd）——其第一性原理与 V6 的这段 `newproc() + icode + exec("/etc/init")` **完全一致**。

### 第四级：/etc/init

`/etc/init` 是 V6 的 **PID 1 进程**——所有用户进程的祖先。它的源码逻辑非常简单 ：

1. **系统初始化**：init 首先执行 `/etc/rc` 脚本，进行系统级的初始化（挂载文件系统、启动守护进程等）
    
2. **fork 子进程执行 shell**：init 为每个终端（/dev/tty0, /dev/tty1, ...）fork 出一个子进程，子进程执行 `/bin/sh` 提供登录提示符
    
3. **等待子进程退出**：当用户从 shell 退出时，init 检测到子进程死亡，重新 fork 一个新的 shell——这样用户登出后又能立即登录
    
4. **孤儿进程收养**：任何父进程先于子进程退出的"孤儿进程"，都会被 init 收养（p_ppid 改为 1）
    

正如 TUHS 邮件所总结的 ："_That process/command then does another fork(), and the child process from that exec's the shell (command interpreter, in /bin/sh)_"。

**/etc/init 的核心使命**：

> **成为所有用户进程的祖先 + 维护终端登录会话的生命周期**。

init 的精妙之处在于它的"永生性"——它永远不会退出（如果 init 退出，内核会发生 panic）。它是用户态的"根进程"，与内核态的"进程 0（调度器）"形成镜像：**进程 0 是内核所有进程的祖先，init 是用户所有进程的祖先**。

> ⚠️ **跨时代联系**：今天 Linux 上的 `systemd`（PID 1）就是 V6 `/etc/init` 的直接后裔。虽然 systemd 的功能极大扩展（服务管理、socket 激活、cgroup、日志），但其核心语义——**"PID 1、所有用户进程的祖先、系统初始化的起点"**——与 V6 的 `/etc/init` **完全一致**。甚至 systemd 的"孤儿进程收养"机制，都可以追溯到 V6 init 的这一职责。

## 14.2 小结

第14章完成了 V6 启动流程的完整剖析。把所有机制串起来看：

```
PDP-11 加电
  ↓
ROM 中的引导程序执行
  ↓
从系统盘 0 号块加载更大的引导程序
  ↓
引导程序加载 /unix 到内存地址 0
  ↓
跳转到地址 0 → 分支到 start()
  ↓
start()（汇编）:
  - 检查内存管理状态寄存器
  - reset 所有外设
  - 初始化内核段寄存器（KISA/KISD）
  - 建立栈和段表
  ↓
跳转到 main()（C 语言）
  ↓
main():
  ├─ startup()  // 前置清理
  ├─ 手工制造进程 0:
  │   proc[0].p_addr = ka6->r[0]
  │   proc[0].p_stat = SRUN
  │   proc[0].p_flag |= SLOAD|SSYS
  │   u.u_procp = &proc[0]
  ├─ 初始化所有子系统:
  │   clkstart()  // 时钟
  │   cinit()     // 字符设备缓冲池
  │   binit()     // 块设备缓冲区池
  │   iinit()     // inode 表
  │   iget(ROOTINO) → u.u_cdir  // 根目录
  ├─ if (newproc()) {  // 进程 1 的路径
  │     expand() + estabur() + copyout(icode)
  │     return → 执行 icode
  │   }
  └─ sched()  // 进程 0 进入调度循环
  ↓
进程 1 执行 icode:
  ├─ icode 调用 exec("/etc/init")
  ├─ /etc/init 加载到进程 1 的用户空间
  ↓
/etc/init（PID 1）:
  ├─ 执行 /etc/rc 系统初始化
  ├─ 为每个终端 fork 子进程执行 /bin/sh
  ├─ 等待子进程退出 → 重新 fork
  └─ 收养所有孤儿进程
  ↓
用户登录 → shell → 执行命令 → fork/exec 新进程
  ↓
V6 多用户分时系统完全启动
```

**第一性原理总结**：

1. **"多级引导"是计算机启动的通用范式**：ROM → 引导块 → 内核映像 → start() → main() → init。每一级只做"加载下一级并跳转"，职责单一 。今天从 BIOS/UEFI → GRUB → vmlinuz → head.S → start_kernel → kernel_init 的流程，与 V6 的引导链**架构一致**。
    
2. **汇编与 C 的分工**：`start()` 用汇编建立"最小执行环境"（段表、栈、内存管理状态），`main()` 用 C 完成"所有子系统初始化" 。这种"汇编做底层、C 做上层"的分工，是所有操作系统内核的通用模式。
    
3. **进程 0 是"手工捏造"的**：它不是 fork 出来的（因为没有父进程），而是内核直接用赋值语句构造的 。进程 0 的 `SSYS` 标志标记它为系统进程，它永不终止，永远作为调度器和交换守护进程 。今天 Linux 的 `kthreadd`（PID 2）和 `swapper`（PID 0）就是这一角色的演化。
    
4. **fork + exec 创建第一个用户进程**：V6 没有为"启动 init"发明特殊机制，而是复用标准的 fork（克隆进程 0）+ exec（替换映像为 /etc/init）。这是 UNIX "组合优于集成"哲学的巅峰体现 。
    
5. **/etc/init 是所有用户进程的祖先**：PID 1 进程负责系统初始化、终端登录管理、孤儿进程收养 。它的"永生性"（退出会导致内核 panic）确立了它在用户态的根地位。今天 Linux 的 systemd 继承了这一角色。
    
6. **sched() 是调度器的入口**：进程 0 调用 `sched()` 进入永久调度循环 。Lions 注释本指出，进程 0 在 `sched` 和 `swtch` 中扮演双重角色 。今天 Linux 的调度器入口是 `schedule()`，由 `kthreadd` 或 `swapper` 进程调用——与 V6 的 `sched()` 是同一思想的演化。
    

**跨章节联系**：

- **第2章的 proc/user 结构体**：`proc[0]` 的手工构造直接操作 `proc` 结构体；`u.u_procp = &proc[0]` 建立 user 与 proc 的关联
    
- **第3章的 fork/newproc**：`main()` 中用 `newproc()` 创建进程 1，正是第3章讲的 fork 机制
    
- **第4章的 exec**：`icode` 执行 `exec("/etc/init")`，正是第4章讲的 exec 机制
    
- **第5章的时钟中断**：`clkstart()` 启动时钟，为后续调度提供时间基准
    
- **第6章的信号**：init 用信号管理终端会话；orphan 进程收养涉及 `p_ppid` 重设
    
- **第7章的缓冲区缓存**：`binit()` 初始化缓冲区池
    
- **第8章的块设备驱动**：`binit()` 初始化块设备子系统
    
- **第9章的文件系统**：`iinit()` 初始化 inode 表；`iget(ROOTINO)` 获取根目录
    
- **第10章的文件处理**：`u.u_cdir` 的设置为后续所有文件操作奠定基础
    
- **第11/12/13章的字符设备**：`cinit()` 初始化字符设备缓冲区池；终端驱动的 `klopen` 等在 init fork shell 时被调用
    

**工业落地的五点启示**：

### 1. **"静态链接内核 + 多级引导"是操作系统的标准启动范式**

V6 的 `/unix` 是静态链接的单一映像，由 ROM 引导程序从磁盘 0 号块加载 。这一范式延续至今：

- **Linux**：`vmlinuz` 是压缩的内核映像，由 GRUB 从 `/boot` 加载；但内核内部仍是静态链接（模块是运行时动态加载的）
    
- **Windows**：`ntoskrnl.exe` 是静态链接的内核，由 `winload.exe` 加载
    
- **macOS**：`kernelcache` 是静态链接的内核缓存，由 BootX 加载
    

**第一性原理：内核必须是"自包含的静态映像"**，因为它运行时没有别的程序可以依赖。引导程序只需要做一件事——把内核映像从存储介质搬到内存，然后跳转。V6 的 ROM 引导 → block 0 引导 → /unix 加载，与今天的 UEFI → GRUB → vmlinuz 加载，是同一范式的 50 年演化。

### 2. **"汇编建栈 + C 做初始化"是内核入口的标准分工**

V6 的 `start()`（汇编）建立段表和栈，`main()`（C）初始化所有子系统 。这一分工在所有现代内核中完好保留：

- **Linux**：`head.S`（汇编）建立页表 → `start_kernel()`（C）初始化
    
- **Windows**：`KiSystemStartup`（汇编）→ `Phase1Initialization`（C）
    
- **xv6**：`entry.S` → `start.c` → `main.c`
    

**洞见**：为什么必须先用汇编写入口？因为 C 语言运行时需要栈和内存管理单元（MMU）的正确配置。在 PDP-11 上，start() 需要手动设置 KISA/KISD 段寄存器 ；在 x86 上，head.S 需要手动设置 CR3 页表寄存器 。**汇编是"打开 C 语言之门"的唯一钥匙**。

### 3. **"进程 0 手工制造"是内核线程的起源**

V6 手工构造 proc[0]，标记 SSYS 为系统进程，让它永久运行 sched() 。这是今天所有操作系统"内核线程"的始祖：

- **Linux**：`kthreadd`（PID 2）是所有内核线程的父进程
    
- **Windows**：`System` 进程（PID 4）是所有系统线程的父进程
    
- **macOS**：`kernel_task` 是所有内核线程的父进程
    

**第一性原理：内核需要一个"永远不会退出的系统进程"作为调度器和内核线程的祖先**。V6 的进程 0 就是这个角色；现代操作系统用 `kthreadd`/`System`/`kernel_task` 继承了这一设计。

### 4. **"fork + exec"创建第一个用户进程是 UNIX 的天才设计**

V6 用标准的 fork + exec 创建 /etc/init，没有发明任何特殊机制 。这一设计的深远影响：

- **今天 Linux 的 `kernel_init()`**：内核线程调用 `kernel_execve("/sbin/init")` 启动 PID 1
    
- **容器运行时（Docker/K8s）**：`runc` 用 clone + execve 启动容器内的 init 进程
    
- **Android 的 `zygote`**：用 fork 孵化应用进程，每个应用进程都是 zygote 的副本
    

**洞见**：V6 证明了——**如果一个操作系统正确地实现了 fork 和 exec，那么它就不需要任何"特殊机制"来启动第一个用户进程**。这种"用通用机制解决特殊问题"的设计哲学，是 UNIX 简洁性的根源。今天你在 Linux 上用 `fork()` + `exec()` 创建任何进程，其第一性原理与 V6 `main()` 中的 `newproc()` + `exec("/etc/init")` 完全一致。

### 5. **"PID 1 永生"是用户态系统初始化的基石**

V6 的 /etc/init 永远不会退出（退出会导致内核 panic），它是所有用户进程的祖先 。这一设计演化为：

- **Linux 的 systemd/PID 1**：如果 systemd 崩溃，内核会 panic
    
- **容器中的 init**：Docker 容器的 PID 1 如果退出，容器就会停止
    
- **Kubernetes Pod**：infra 容器（pause 进程）作为 PID 1，永生不退出
    

**工业联系**：

- **孤儿进程收养**：V6 init 收养所有孤儿进程 ，今天 Linux 的 systemd 仍然承担这一职责
    
- **终端登录管理**：V6 init 为每个终端 fork shell ，今天 Linux 的 `getty` + `login` + `bash` 是这一机制的演化
    
- **系统初始化脚本**：V6 的 `/etc/rc` ，今天演化为 systemd 的 service 单元、SysV init 的 `/etc/init.d/` 脚本
    
- **服务监控**：V6 init 检测 shell 退出并重生 ，今天 systemd 的 `Restart=always` 是这一机制的延续

### 2. TUHS 邮件列表："Bootstrapping UNIX - how was it done"

TUHS 社区对 V6 启动过程的权威总结 ：

> "_UNIX kernels consists of a number of smallish relocatable binary modules which are statically linked into a large object code image; during booting, that image is loaded into memory and started. After the usual initialization, the '0th' process (which in V6 has the task of swapping processes in and out) is hand-crafted; it then forks into two, using the standard UNIX fork() system call... The second process then runs a tiny program (the binary for which is built into the kernel) which does an exec() system call, to read in and run /etc/init. That process/command then does another fork(), and the child process from that exec's the shell (command interpreter, in /bin/sh)._"

这段话是理解 V6 启动流程最精炼的英文描述。

### 3. V6 main.c 源码（sys/main.c 第 01879 行）

完整的 main() 源码 ，包括：

- `startup()` 调用
    
- 进程 0 的手工构造（proc[0].p_addr / p_size / p_stat / p_flag / p_nice）
    
- 子系统初始化（clkstart/cinit/binit/iinit/iget）
    
- `newproc()` + `expand()` + `estabur()` + `copyout(icode)` 创建进程 1

源码中的注释本身就是最好的文档：

```
* Functions:
* clear and free user core
* turn on clock
* hand craft 0th process
* call all initialization routines
* fork - process 0 to schedule
* - process 1 execute bootstrap
*
* loop at low address in user mode -- /etc/init
* cannot be executed.
```

### 4. "Installing UNIX Sixth Edition"（gunkies.org）

详细记录了 V6 引导块（block 0）的工作原理 ：引导块中的小程序能够"从文件系统中的任何位置加载普通的 UNIX 格式二进制文件并启动"。这揭示了 V6 引导程序的精妙——它不是简单的"加载固定位置"，而是能够解析文件系统、找到 `/unix` 文件并加载。

### 5. xv6 的启动流程（现代教学对照）

xv6 是 V6 的现代 RISC-V 重写，启动流程与 V6 高度一致 ：

```
BIOS → Bootloader → entry.S → start.c → main.c
                                          ↓
                                    userinit() 创建第一个用户进程
                                          ↓
                                    mpmain() 进入调度循环
```

xv6 的 `userinit()` 对应 V6 的 `newproc()` + `copyout(icode)`；xv6 的 `mpmain()` 对应 V6 的 `sched()`。架构骨架完全一致。

### 6. 现代对照表

|V6 概念|现代 Linux 对应|演化|
|---|---|---|
|ROM 引导程序|UEFI/BIOS|从 ROM → Flash/EEPROM|
|磁盘 0 号块的引导程序|GRUB stage 1/2|从 512 字节引导块 → 多阶段引导加载器|
|`/unix` 静态链接内核|`vmlinuz` 压缩内核 + `initramfs`|从单一静态映像 → 压缩映像 + 临时根文件系统|
|`start()`（汇编）|`head.S` / `early_startup()`|从 PDP-11 段寄存器 → x86_64 页表|
|`main()`（C）|`start_kernel()`|函数名和复杂度都演化了|
|手工构造 proc[0]|`sched_init()` 创建 `swapper` (PID 0) + `kthreadd` (PID 2)|从单一系统进程 → 多个内核线程|
|`proc[0].p_flag|= SSYS`|`PF_KTHREAD` 标志|
|`clkstart()` 启动时钟|`tick_init()` + `init_timers()`|机制一致，精度更高|
|`cinit()` 字符设备缓冲池|`chardev_init()`|机制一致|
|`binit()` 块设备缓冲池|`buffer_init()` → 页缓存|从缓冲区池演化到页缓存|
|`iinit()` inode 表|`inode_init()` + `dentry_cache_init()`|从简单 inode 表 → inode + dentry 双层缓存|
|`iget(ROOTINO)`|`dget(sb->s_root)`|从单 inode → dentry + inode|
|`newproc()` 创建进程 1|`kernel_thread(kernel_init)`|从 fork 演化到专门的 `kernel_thread`|
|内核内置 `icode` + `exec("/etc/init")`|`kernel_execve("/sbin/init")`|从 icode 机器码 → 直接调用 execve 系统调用|
|`/etc/init`（PID 1）|`systemd` / `init`|从简单初始化脚本 → 服务管理器|
|`/etc/rc` 系统初始化脚本|`systemd.service` 单元 / SysV init 脚本|从 shell 脚本 → 声明式服务单元|
|`sched()` 调度循环|`schedule()` 由 `kthreadd` 调用|从进程 0 的函数调用 → 内核线程的调度循环|
|`swtch()` 上下文切换|`context_switch()`|从 PDP-11 的 savu/retu/aretu → 现代上下文切换|

> 💡 **跨时代洞见**：从 V6 到现代 Linux，启动流程的**第一性原理完全一致**：
> 
> - **多级引导**：ROM → 引导块 → 内核映像 → 汇编入口 → C 的 main → init
>     
> - **汇编建栈 + C 做初始化**：start()/head.S 建立执行环境，main()/start_kernel() 初始化子系统
>     
> - **进程 0 手工制造**：内核需要一个永不退出的系统进程作为调度器
>     
> - **fork + exec 创建第一个用户进程**：复用通用机制，不发明特殊机制
>     
> - **/etc/init 是所有用户进程的祖先**：PID 1 永生，负责系统初始化
>     
> - **sched() 进入调度循环**：进程 0 成为调度器
>     
> 
> 变的是**规模**（单一静态映像 → 压缩内核 + initramfs）、**硬件复杂度**（单 CPU PDP-11 → 多核 x86_64/ARM64）、**能力**（从简单 init 脚本 → systemd 服务管理）、**引导安全性**（从无条件引导 → UEFI Secure Boot）。但**骨架——"硬件引导 → start → main → 手工进程 0 → fork/exec init → 调度循环"——50 年没变**。
> 
> 正如 Lions 注释本所揭示的 ，V6 的启动流程之所以经典，不是因为它复杂，而是因为它**用最少的代码完成了最关键的使命**——把一堆独立的子系统"焊接"成一个完整的、可运行的、多用户的操作系统。理解 V6 的启动流程，你就拿到了理解现代 Linux 启动（从 GRUB 到 systemd）的"源代码"。
> 
> TUHS 邮件中的一句话最能概括 V6 启动的哲学 ："_Which was all very simple, compared to some contemporary operating systems._"——与同时代的 Multics 等操作系统相比，V6 的启动流程"非常简单"。但这种"简单"背后，是 UNIX 设计者深刻的洞察：**用通用机制（fork/exec）解决特殊问题（启动 init），用最少的新概念完成最多的功能**。

## 给读者的学习建议

1. **在 Linux 上观察启动流程的现代演化**：
    
    ```
    # 观察内核启动参数
    cat /proc/cmdline
    
    # 观察 PID 1（systemd 或 init）
    ps -p 1 -o pid,comm,args
    
    # 观察内核线程（对应 V6 的进程 0）
    ps -p 2 -o pid,comm,args  # kthreadd
    
    # 跟踪内核启动日志
    dmesg | head -50
    
    # 阅读 Linux 内核启动源码
    # init/main.c 中的 start_kernel()
    # kernel/fork.c 中的 kernel_thread()
    # init/do_mounts.c 中的 prepare_namespace()
    ```
    
    你会发现——**V6 的 main() 思想在现代 Linux 的 start_kernel() 中完好延续**。
    
2. **画出 V6 启动的完整状态机**：
    
    ```
    ROM 引导 → block 0 引导 → 加载 /unix → start()（汇编）
      → main()（C）
        ├─ startup()
        ├─ 手工构造 proc[0]
        ├─ clkstart/cinit/binit/iinit/iget
        ├─ if newproc():
        │    进程 1: expand + estabur + copyout(icode) → return → 执行 icode
        │    icode: exec("/etc/init") → /etc/init 成为 PID 1
        │    /etc/init: 执行 /etc/rc → 为每个终端 fork shell
        └─ else:
             进程 0: sched() → 永久调度循环
    ```
    
    理解这个状态机，你就理解了操作系统"从无到有"的全过程。
    
3. **对照 xv6 学习现代演化**：
    
    - V6 的 `start()` → xv6 的 `entry.S` + `start.c`
        
    - V6 的 `main()` → xv6 的 `main.c`
        
    - V6 的 `newproc()` + `copyout(icode)` → xv6 的 `userinit()`
        
    - V6 的 `sched()` → xv6 的 `mpmain()` → `scheduler()`
        
    - V6 的 `/etc/init` → xv6 的 `initcode.S` + `user/init.c`
        
    
    阅读 xv6 的 `kernel/main.c` 和 `kernel/proc.c` 中的 `userinit()`，你会看到 V6 启动思想在 50 年后的延续。
    
4. **思考设计问题**：如果让你为现代多核 x86_64 系统重新设计 V6 的启动流程，你会：
    
    - 如何处理 SMP（对称多处理）？第一个 CPU 启动后如何唤醒其他 CPU？（提示：Linux 的 `smp_init()` + APIC IPI）
        
    - 如何处理 KASLR（内核地址空间布局随机化）？（提示：现代内核在 head.S 中重定位）
        
    - 如何支持 initramfs？（提示：Linux 的 `populate_rootfs()` + `default_rootfs()`）
        
    - 如何用 `kthreadd` 替代单一的进程 0？（提示：Linux 的 `rest_init()` 中 `kernel_thread(kthreadd)`）
        
    
    这个练习会让你深刻理解——**V6 的启动架构在今天的约束下该如何演化**。答案就在现代 Linux 的 `init/main.c`：它保留了 V6 的核心语义（汇编入口、C 的 main、手工创建第一个系统进程、fork+exec 创建 init、进入调度循环），但在每一层都做了多核、虚拟化、安全性的扩展。
