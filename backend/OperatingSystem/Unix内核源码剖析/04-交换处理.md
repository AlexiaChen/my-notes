
# 《Unix内核源码剖析》读书笔记 · 第4章 交换处理

> 第3章把"进程怎么生、怎么切、怎么死"讲完了，但留下了一个悬而未决的问题：**当内存装不下所有进程时怎么办？**​ 第4章回答的就是这个问题——交换处理（swapping）。
> 
> **第一性洞见**：V6 选择"整体交换"而非"分页"，不是因为设计者不知道分页，而是因为 PDP-11 没有硬件分页支持。正如 ETH Zürich 关于 V6 交换处理的讲义所明确指出的：**swapping 是"无硬件支持"时代的必然选择**——whole process 粒度的换出换入，对应的是"Process Size ≤ Memory"的约束；而 paging 才需要 MMU 的硬件支撑。V6 跑在 PDP-11/40 上，物理地址 18 位（最大 256K 字）、虚拟地址 16 位（64K 字）、无分页但有一些分段支持——在这种硬件上，"进程级交换"是唯一合理的虚拟化方案。
> 
> 这一章的精妙之处在于：**交换机制不只是"内存不够时的逃生舱"，它是 V6 进程模型的有机组成部分**。fork 出来的新进程如果内存装不下，要 swap 出去；exec 加载新程序时需要分配正文段，可能涉及交换；进程被调度器选中运行时需要从交换区换入。sched 这个"进程 0"在 V6 中扮演着唯一常驻且永不阻塞的守护进程角色，是全章的真正主角。

---

## 4.1 什么是交换处理

### 代码段和数据段

要理解交换，先要理解 V6 中"换出"到底换了什么。根据 UNIX V6 内存布局的资料：

- **代码段（Text）**：纯代码（pure text）是只读的、可共享的。两个进程运行同一个程序时，共享主存中的同一份代码段
    
- **数据段 + 栈 + user 结构体（PPDA）**：这三块在主存中**连续存放**，并且**总是作为一个整体被换出/换入**
    

> 📌 **关键事实**：数据段、栈、user 块三者"always swapped as a unit"——这是一个刻意的设计简化。正如 V6 内存布局文档指出的："_The two data blocks are always stored contiguously in main memory, along with the 'user' block, and all three are always swapped as a unit; this simplifies physical memory allocation and swapping code._" 把三块绑在一起换，物理内存分配和交换代码都大幅简化。

**工业联系**：这种"绑定换出"的思想，在现代操作系统中演化为：

- **Linux 的 swap 机制**：匿名页（堆、栈、匿名映射）整体换出，但文件页可通过 page cache 机制单独处理
    
- **容器环境的 memory cgroup**：当 cgroup 内存超限时，内核触发的 OOM Killer 本质上是在做"比交换更激进"的资源回收
    
- **iOS 的 Jetsam**：基于内存压力的进程级杀死，是"整体交换"思想在闪存时代的极端演化——直接杀进程而非换出
    

### sched()

`sched` 是进程 0 的实体函数，是 V6 中**唯一常驻且永不阻塞的守护进程（daemon process）**，承担着全局资源仲裁者的角色。它大部分时间在睡眠，被以下事件唤醒：

- **runout**：没有已换出的进程就绪可运行（需要新进程换出触发）
    
- **runin**：有进程已换出且就绪可运行，但还没满足条件（换出不满 3 秒 或 内存中进程都不够"老"）
    

sched 的核心循环逻辑（根据 Lions 讲义）：

1. **找换入对象**：在已换出且 SRUN 的进程中，选**换出时间最久**的那个
    
2. **检查 runin 条件**：该进程换出必须 > 3 秒，且内存中必须有进程已经驻留 > 2 秒 或处于非活跃状态
    
3. **分配内存**：调用 `malloc(coremap, size)` 尝试分配
    
4. **如果内存不够**：
    
    - 在内存中找 SWAIT/SSTOP 状态且未被锁定的进程
        
    - 调用 `xswap()` 把它换出
        
    - 释放的内存用来换入目标进程
        
    
5. **执行换入**：调用 `swap(addr_in_swap, mm_addr, size, B_READ)` 从交换区读入
    
6. **释放交换区**：`mfree(swapmap, size, old_swap_addr)`
    
7. **标记进程可运行**：设置 SLOAD 标志，重置 p_time
    

> 💡 **洞见**：sched 的算法体现了**极简的"贪心策略"**——换入"等最久的"，换出"最不活跃的"。没有复杂的预测，没有 LRU 链表，就是两个简单的启发式：
> 
> - 换入：换出时间最长的（公平性）
>     
> - 换出：内存中驻留最久且不活跃的（最小化对系统响应性的影响）
>     
> 
> 这种策略在进程数量少（NPROC=50）、内存小（最大 256K 字）的时代是合理的。今天的 Linux 内核有数十种内存回收策略（kswapd、NUMA balancing、memory compaction、THP），但**根本目标与 sched 完全一致**：在内存压力下，决定谁走、谁留。

**sched 的五个核心标号**（来自 Lions 讲义）：

- `sloop`：顶层循环
    
- `loop`：选择调入/调出进程
    
- `found1`：执行换出处理
    
- `found2`：执行换入处理
    
- `swaper`：swap I/O 错误处理（panic）
    

### xswap()

`xswap(p, ff, os)` 负责把进程**换出**到交换区，三个参数：

- `p`：指向目标进程的 proc 结构体
    
- `ff`：free flag，如果非 0，换出后释放主存
    
- `os`：old size，要换出的数据段长度
    

源码逻辑（根据 UNIX V6 源码分析笔记）：

```
xswap(p, ff, os) {
    if (os == 0) os = rp->p_size;  // 如果 os 为 0，换出整个数据段
    a = malloc(swapmap, (rp->p_size+7)/8);  // 分配交换区空间
    if (a == NULL) panic("out of swap space");
    xccdec(rp->p_textp);  // 递减代码段引用计数
    rp->p_flag |= SLOCK;  // 设置调度锁
    if (swap(a, rp->p_addr, os, 0)) panic("swap error");  // 执行换出
    if (ff) mfree(coremap, os, rp->p_addr);  // 如果 ff，释放主存
    rp->p_addr = a;  // 数据段地址改为交换区地址
    rp->p_flag &= ~(SLOAD|SLOCK);  // 清除 SLOAD 和 SLOCK
    rp->p_time = 0;  // 重置驻留时间
    if (runout) { runout = 0; wakeup(&runout); }  // 唤醒 sched
}
```

**关键细节**：`os` 参数的精妙之处——当进程调用 `expand()` 扩大数据段失败时，p_size 已经更新为新尺寸，但实际主存中的数据仍是旧尺寸。此时 xswap 按新尺寸分配交换区，但只写入旧尺寸的数据。这是 V6 对"expand 中途失败"场景的优雅处理。

> ⚠️ **注意**：xswap 换出的**只是数据段**，不包括代码段。代码段是共享的、由 text 数组管理的，换出代码段需要特殊处理（详见 4.2）。

## 4.2 共享代码段的处理

这是第4章最具"工程美感"的一节。V6 怎么做到多个进程运行 `/bin/ls` 时只占用一份代码段内存？

### 核心数据结构：text 数组

内核维护一个全局的 `text` 结构体数组，每个元素描述一个已加载的正文段：

```
struct text {
    int x_daddr;   // 交换区中的磁盘地址
    int x_size;    // 正文段大小
    int x_iptr;    // 指向文件 inode 的指针
    int x_count;   // 引用该正文段的进程数
    int x_ccount;  // 在主存中的引用计数
    int x_flag;    // 标志位（如 XWRIT 表示正被换出）
};
```

**四个关键函数**：

### xalloc()

`xalloc(ip)` 在 exec() 中被调用，负责为新程序分配或链接到正文段。根据原始 V6 设计文档，有四种场景：

1. **程序没有纯代码段**：xalloc 直接返回，什么都不做
    
2. **代码段正被其他进程使用且在主存中**：递增 x_count 和 x_ccount，把 text 指针放入 proc 结构体
    
3. **代码段被使用但不在主存中**：先从交换区换入，再递增计数
    
4. **没有任何进程使用该代码段**（交换区中也没有）：调用 `expand()` 分配空间 → 从文件读入代码 → 换出到交换区 → 调用 `xswap()` 换回主存并设置标志
    

> 💡 **洞见**：场景 4 是整个 xalloc 里最微妙的逻辑——"先换出再换入"。为什么？因为 V6 的正文段管理策略是：**正文段在交换区中必须有一份副本**。这样当所有引用该代码段的进程都被换出时，正文段占用的主存可以被释放，但交换区中的副本仍在。下次有进程需要这个代码段时，直接从交换区换入即可，不必再从文件系统读。

**这是 V6 的"代码段缓存"机制**——交换区不仅是进程数据段的临时存放地，也是共享代码段的"二级缓存"。

### xfree()

`xfree()` 在 exit() 中被调用，进程终止时释放对正文段的引用：

1. 递减 x_count
    
2. 如果 x_count 归零，放弃交换区中的正文段副本（不标记保存）
    

### xccdec()

`xccdec()` 递减**主存中**的引用计数（x_ccount）。当 x_ccdec 被调用且 x_ccount 归零时：

- 正文段占用的主存被释放回 coremap
    
- 但交换区中的副本保留（因为 x_count 可能仍 > 0）
    

`xccdec()` 在三个地方被调用：

- `xswap()` 中（进程换出时）
    
- `xfree()` 中（进程退出时）
    
- 其他地方进程放弃代码段引用时
    

> 📌 **深度理解**：x_count 和 x_ccount 是两个不同维度的引用计数：
> 
> - **x_count**：有多少进程引用这个正文段（无论在主存还是交换区）
>     
> - **x_ccount**：有多少进程在主存中引用这个正文段
>     
> 
> 当 x_ccount 归零但 x_count > 0 时，正文段可以释放主存但保留交换区副本；当 x_count 归零时，交换区副本也可以释放了。

**工业联系**：这种"双计数"的共享内存管理思想，在现代操作系统中演化为：

- **Linux 的 page cache**：文件页在主存中缓存，引用计数跟踪有多少个 VMA 映射了该页
    
- **Linux 的 KSM（Kernel Same-page Merging）**：合并相同内容的匿名页，用引用计数跟踪
    
- **容器的镜像分层**：Docker 的 overlayfs 中，只读层（镜像）被多个容器共享，引用计数管理生命周期
    
- **共享库**：现代 OS 的 .so/.dll 文件在内存中只加载一份，多个进程共享——这正是 V6 正文段共享思想的现代延续

## 4.3 小结

第4章完成了 V6 交换处理的全貌。把核心机制串起来：

```
内存压力出现
    ↓
sched 被唤醒
    ↓
选择换出时间最长的就绪进程
    ↓
xswap() 换出数据段到交换区
    ↓
xccdec() 递减正文段主存引用计数
    ↓
（如果 x_ccount==0）释放正文段主存
    ↓
malloc(coremap) 分配内存
    ↓
swap() 从交换区换入目标进程
    ↓
mfree(swapmap) 释放交换区
    ↓
进程标记为 SLOAD，可被调度
```

**第一性原理总结**：

1. **交换是硬件约束的产物**：PDP-11 无分页 → 只能进程级交换 → sched 作为常驻仲裁者
    
2. **数据段/栈/user 三者绑定交换**：简化物理内存分配，这是"用空间换简单性"的典型权衡
    
3. **正文段单独管理**：通过 text 数组 + 双引用计数（x_count/x_ccount）实现代码共享，这是 V6 在极小内存下支持多用户多进程的关键优化
    
4. **sched 的贪心策略**：换入"等最久的"、换出"最不活跃的"——极简但有效的启发式
    
5. **交换区是"二级存储"**：既存进程数据段，也缓存共享正文段
    

**跨章节联系**：

- 第3章的 `expand()` 失败 → 触发 `xswap()` 换出 → 本章核心机制
    
- 第3章的 `exec()` → 调用 `xalloc()` 分配正文段 → 本章 4.2 节
    
- 第3章的 `exit()` → 调用 `xfree()` 释放正文段 → 本章 4.2 节
    
- 第2章的 proc 结构体 p_addr 字段 → 在交换时从"主存地址"变为"交换区地址"
    
- 第2章的 SLOAD 标志 → sched 设置和清除的核心标志
    

**工业落地的四点启示**：

1. **约束驱动架构**：V6 的交换机制完全是被 PDP-11 的硬件约束"塑形"的。今天我们在设计系统时，也应该主动识别硬件/平台约束，让架构从约束中自然涌现，而非照搬"最佳实践"。
    
2. **共享只读数据的引用计数**：V6 的 text 数组 + 双引用计数，是现代共享库、容器镜像层、page cache 的共同祖先。**"只读数据单独管理 + 引用计数"**​ 是多进程环境下节省内存的第一性原理。
    
3. **贪心策略在小规模下的有效性**：sched 的 O(N) 扫描 + 简单启发式，在 N=50 时完全够用。这提醒我们——**不要过度设计调度/分配算法**，先用量级估算，再决定是否需要复杂数据结构。Linux 早期版本也是 O(N) 扫描，直到进程数量爆炸才引入 O(1) 调度器和红黑树。
    
4. **"交换区作为缓存"的思想**：V6 把交换区用作共享正文段的缓存，这是现代 page cache、buffer cache 的思想雏形。**存储层级中每一层都可以是下一层的缓存**——这个思想从 V6 一路延伸到今天的 NVMe SSD 缓存、Redis 缓存、CDN 缓存。

## 英文补充资料与跨时代对照

### 1. Lions 原典

John Lions 的《A Commentary on the Sixth Edition UNIX Operating System》第 14-15 章专门讲程序交换，是本章的必读原典。Lions 在书中不仅逐行注释 sched、xswap、xalloc、xfree、xccdec，还讨论了潜在的竞态条件（Race Conditions）。

### 2. ETH Zürich 的交换处理讲义

Urs Fässler 的讲义《Process Swapping in UNIX V6》清晰地对比了 swapping vs paging：

- **Swapping**：older、easy、whole process、proc size ≤ memory
    
- **Paging**：modern、complicated、parts of memory、arbitrary proc size、needs MMU
    

讲义中还把 sched 的 100 行代码重构为 9 个独立函数，对比了现代编码风格与 V6 原始风格的差异——这是理解"代码演进"的绝佳材料。

### 3. xv6 的现代对照

xv6（MIT 的教学 OS）在 RISC-V 上重新实现了 V6 的思想，但有几处关键演进：

- **sleep/wakeup 加锁**：V6 在单 CPU 上通过关中断避免丢失唤醒（lost wakeup）；xv6 运行在多处理器上，必须显式加锁
    
- **调度器**：xv6 的 scheduler() 实现简单的 round-robin，而 V6 的 sched 实现了基于优先级的交换决策
    
- **正文段共享**：xv6 简化了这一机制，没有完整复刻 V6 的 text 数组管理
    

正如 xv6 指南中所指出的："_The original Unix kernel's sleep simply disabled interrupts, which sufficed because Unix ran on a single-CPU system. Because xv6 runs on multiprocessors, it adds an explicit lock to sleep._" 这句话精准地概括了从 V6 到现代的演进本质——**单核到多核，是从"关中断"到"显式锁"的范式转换**。

### 4. 现代演变对照表

|V6 概念|现代 Linux 对应|演进原因|
|---|---|---|
|sched (进程0)|kswapd + migration 线程|多核并行回收|
|进程级交换|按需分页 (demand paging)|MMU 硬件支持|
|xswap (整体换出数据段)|匿名页换出 (try_to_free_pages)|更细粒度|
|text 数组 (共享正文段)|共享库 + page cache|机制相同，粒度更细|
|swapmap (交换区管理)|swap 分区 + zram + zswap|多层交换设备|
|coremap (主存管理)|伙伴系统 (buddy allocator)|多核 + NUMA|
|x_count/x_ccount|page._refcount/page._mapcount|同样的双计数思想|

> 💡 **跨时代洞见**：从 V6 到现代 Linux，内存管理的**第一性原理没变**——在内存压力下，决定谁走谁留；对共享只读数据用引用计数管理。变的是**粒度**（进程 → 页 → 大页）和**并行度**（单核关中断 → 多核细粒度锁）。理解 V6，你就拿到了理解现代内存管理的"源代码"。
