
# 《Unix内核源码剖析》读书笔记 · 第12章 字符设备

> 第8章讲了块设备——硬盘、磁带这类"以块为单位、可随机寻址、走缓冲区高速缓存"的设备；第10/11章讲了文件处理和管道——用"fd → file → inode"的统一抽象对用户态暴露 I/O 能力。但还有一类设备既不适合走块设备的缓冲区缓存（它们是字节流，不是数据块），也不适合走普通文件的 inode 数据块——**字符设备**：终端、打印机、串口、鼠标、声卡。
> 
> **第一性洞见**：字符设备的本质是**"用一个整数（设备号）反向查表，找到一组函数指针，把 read/write 系统调用直接分派到驱动代码"**。V6 用 `cdevsw[]` 这张"字符设备开关表"统一了所有字符设备的接入方式——表里每一行是一个设备驱动，每一列是一个操作（open/close/read/write/sgtty）。当用户执行 `write(fd, buf, n)`，而 fd 指向的是字符设备文件时，V6 走的是 ：
> 
> ```
> if ((ip->i_mode&IFMT) == IFCHR) {
>     (*cdevsw[ip->i_addr[0].d_major].d_write)(ip->i_addr[0]);
>     return;
> }
> ```
> 
> 这一行代码就是 UNIX "一切皆文件"哲学在字符设备上的最终落地——**用户看到的仍然是 `write()` 系统调用，但内核内部已经跳转到了具体硬件的驱动函数**。今天你在 Linux 上看到的 `struct cdev` + `struct file_operations`，与 V6 的 `cdevsw[]` 是同一思想的现代演化 。

## 12.1 字符设备驱动

V6 的字符设备开关表定义 ：

```
struct cdevsw {
    int (*d_open)();
    int (*d_close)();
    int (*d_read)();
    int (*d_write)();
    int (*d_sgtty)();
} cdevsw[];
```

System III 的官方文档对这五个函数给出了精确语义 ：

- **d_open(dev, flag)**：每次文件被 open 时调用，`dev` 是完整设备号，`flag` 非零表示以写方式打开
    
- **d_close(dev, flag)**：仅当最后一个持有该文件的进程关闭时才调用——这意味着**驱动无法自己维护引用计数**
    
- **d_read(dev)**：从设备读取字符，通过 `u.u_count` / `u.u_base` / `u.u_segflg` 与用户空间交互
    
- **d_write(dev)**：向设备写入字符，`u.u_count` 初始为待写字节数，驱动每写出一个字符就递减 `u.u_count`，通常用 `cpass()` 逐个取字符；如果要批量拷贝，可用 `iomove()`
    
- **d_sgtty(dev, cmd, addr)**：实现 `ioctl` 系统调用，用于设备的特殊控制（主要是终端的 `stty`/`gtty`）
    

V6 的配置表里注册了若干字符设备 ：

```
int (*cdevsw[])() {
    &klopen, &klclose, &klread, &klwrite, &klsgtty,  /* console (KL11/DL11) */
    &pcopen, &pcclose, &pcread, &pcwrite, &nodev,    /* pc */
    &lpopen, &lpclose, &lpread, &lpwrite, &nodev,    /* lp (LP11 行式打印机) */
    &nulldev, &nulldev, &mmread, &mmwrite, &nodev,   /* mem */
    &nulldev, &nulldev, &rkread, &rkwrite, &nodev,   /* rk (磁盘原始 I/O) */
    // ... 后续更多槽位，多为 nodev/nulldev
    0
};
```

**关键设计**：

1. **nulldev**：表示该操作可以忽略（如某些设备的 open 不需要任何设置）
    
2. **nodev**：表示该操作是错误（如只读设备上的 write）
    
3. **第5种"设备"其实是 RK 磁盘**：通过"原始 I/O"函数 `rkread/rkwrite` 访问，行为上变成字符设备——这是"块设备也可以字符流方式访问"的早期实践，今天 Linux 的 `/dev/sda`（块）与 `/dev/sda1`（分区）并列，以及 `/dev/raw/` 原始设备接口，都是这一思想的延续
    

> 💡 **洞见**：`cdevsw[]` 是一张**"主设备号 → 驱动函数指针表"**的映射表。当用户执行 `mknod /dev/lp c 2 0` 创建设备文件时，"c" 表示字符设备，"2" 是主设备号（即 `cdevsw[]` 的下标），"0" 是次设备号（传递给驱动，用于区分同类型的多个物理设备）。`echo hello > /dev/lp` 的执行路径是 ：
> 
> ```
> echo 进程 write(1, "hello", 5)
>   → rdwr() 权限检查
>   → writei() 发现是字符设备 (IFCHR)
>   → cdevsw[2].d_write(次设备号 0)  // 即 lpwrite(0)
>   → lpcanon() → lpoutput() → 写入 LP11 硬件
> ```
> 
> **整个路径中没有缓冲区高速缓存、没有 bmap、没有块设备子系统——数据直接从用户空间流向硬件**。这就是字符设备与块设备的本质区别。

### 字符设备缓冲区

块设备有统一的缓冲区高速缓存（第7章的 `buf[]` 池），但字符设备没有——它们的数据是字节流，不按块组织。然而，**字符设备驱动内部通常需要自己的缓冲区**，原因是：

1. **速率不匹配**：CPU 向设备写数据速度 >> 设备消费数据速度（如 LP11 打印机每秒只能打几十到几百字符）
    
2. **中断驱动**：设备完成一个字符的输出后会发中断，驱动在中断处理程序中取下一个字符——这需要缓冲区暂存
    
3. **流控制**：当缓冲区满时，写进程应该睡眠；当缓冲区空时，设备应该停止输出
    

V6 用 **clist（字符列表）**​ 作为字符设备的标准缓冲区结构 。clist 是一个**字符环形队列**，由 `getc()` / `putc()` 操作，是字符设备驱动的核心数据结构。

### 对缓冲区的操作

clist 的核心操作 ：

- **putc(c, clist)**：向缓冲区放入一个字符；如果缓冲区满，调用者需要睡眠
    
- **getc(clist)**：从缓冲区取一个字符；如果缓冲区空，返回 -1
    
- **cpass()**：从用户空间逐个取字符（用于 write 路径），内部处理 `u.u_segflg` 和 `u.u_count` 的更新——System III 文档明确说"_For most drivers, which work one character at a time, the routine cpass() is used to pick up characters from the user's buffer_"
    
- **iomove(buf, offset, count, B_WRITE)**：批量拷贝，比 cpass 快，用于需要转移大量字符的场景
    

**clist 的设计哲学**：

> 字符设备缓冲区要解决的核心问题是**"生产-消费者"速率匹配**。写进程是生产者（通过 write → cpass → putc），设备中断是消费者（通过 lpint → getc）。clist 就是它们之间的**有界环形队列**。

### 初始化缓冲区池

V6 在系统启动时调用 `cinit()` 初始化字符缓冲区池——分配一块内存作为 clist 的存储后端，建立空闲字符块链表。这与第7章 `buf[]` 缓冲区池的初始化（`binit()`）是平行的：

- **块设备缓冲区池**：`binit()` 初始化 `buf[]` 数组，每个 buf 512 字节
    
- **字符设备缓冲区池**：`cinit()` 初始化 clist 池，每个单元 1 字节
    

> 📌 **洞见**：V6 用**两套独立的缓冲区池**分别服务块设备和字符设备，这揭示了 I/O 子系统的第一性原理——**"数据组织形式决定缓冲区策略"**：
> 
> - 块设备：数据以 512 字节块为单位，随机寻址 → 用 `buf[]` 池 + bmap + 块设备高速缓存
>     
> - 字符设备：数据以字节流为单位，顺序访问 → 用 clist 池 + cpass + 驱动内部环形队列
>     
> 
> 今天 Linux 的区分更加明显：**块设备走页缓存（page cache）**，参与 VFS 的地址空间管理；**字符设备完全不走页缓存**，I/O 直接到达驱动 。这是 1975 年 V6 双缓冲池设计的现代演化。

## 12.2 LP11 设备驱动

### 什么是 LP11

LP11 是 DEC PDP-11 的**行式打印机接口**。它连接行式打印机（line printer），特点是 ：

- **慢速设备**：打印速度通常为每秒 10-300 字符，远低于 CPU
    
- **字符流输出**：数据以字符流形式发送给打印机
    
- **中断驱动**：每输出完一个字符，LP11 发出中断，驱动在中断处理程序中发送下一个字符
    
- **状态寄存器**：LPADDR->lpsr，第 15 位是出错标志（电源未开、缺纸、温度过高等），第 8 位（DONE）表示"可以接收下一个字符"
    
- **数据寄存器**：LPADDR->lpbuf，写入要打印的字符
    

LP11 的物理地址是 0177514（八进制），寄存器定义 ：

```
#define LPADDR 0177514
struct {
    int lpsr;   // 状态寄存器
    int lpbuf;  // 数据缓冲寄存器
};
```

### LP11 设备驱动的功能

LP11 驱动的核心功能是**"把用户 write() 的字节流，可靠地、按设备速率地送到打印机"**。它需要解决三个问题：

1. **速率匹配**：用户 write 很快，打印机很慢 → 需要输出缓冲区（clist）
    
2. **中断驱动**：打印机每完成一个字符就中断 → 中断处理程序从缓冲区取下一个字符
    
3. **字符转换**：某些打印机需要把小写转大写、把 `\n` 转成回车+换行等 → `lpcanon()` 做规范化
    

### lpopen()

`lpopen(dev, flag)` 的源码 ：

```
lpopen(dev, flag) {
    register unit;
    register struct lp *lp;
    
    unit = dev & 07;  // 取低 3 位作为次设备号
    if (unit >= lp_cnt || unit >= LPMAX || (lp = &lp_dt[unit])->flag || lp_addr[unit]->lpsr)
        return;  // 设备不存在/已打开/硬件错误 → 失败
    
    lp_addr[unit]->lpcsr = (dev & 077) | OPEN;
    lp->ind = 4;   // 缩进 4 列
    lp->col = 80;  // 当前列号（80 表示行尾）
    lp->line = 66; // 每页行数
    lp_addr[unit]->lpcsr |= IENABLE;  // 开启中断
    lpoutput(unit, FORM);  // 输出换页符，开始新的一页
}
```

**关键设计**：

1. **次设备号提取**：`dev & 07` 取低 3 位，支持最多 8 台打印机
    
2. **硬件状态检查**：`lp_addr[unit]->lpsr` 非零表示设备有错误（如缺纸）
    
3. **OPEN 标志**：标记设备已打开，防止重复打开
    
4. **IENABLE**：开启设备中断，使能中断驱动的输出
    
5. **lpoutput(unit, FORM)**：输出换页符（FORM = 014），让打印机走到下一页顶部
    

### lpwrite()

`lpwrite(dev)` 的源码 ：

```
lpwrite(dev) {
    register c;
    while ((c = cpass()) >= 0)  // 从用户缓冲区逐个取字符
        lpcanon(dev & 07, c);  // 规范化后送入输出缓冲
}
```

**关键设计**：

- **cpass() 逐个取字符**：System III 文档明确指出 `cpass()` 负责从用户空间取字符并更新 `u.u_count`
    
- **lpcanon() 做规范化**：每个字符经过 `lpcanon()` 处理后，再进入输出缓冲
    
- **write 不直接操作硬件**：write 只是把数据"推"入驱动内部缓冲区，真正的硬件输出由 `lpstart()` 在中端上下文中完成
    

### lpcanon()

`lpcanon(c)` 是 LP11 的**字符规范化函数**——它对每个要打印的字符做转换 ：

```
lpcanon(c) {
    register c1, c2;
    c1 = c;
    
    // 1. 大写转换：如果开启了 CAP 标志，小写转大写
    if (lp11.flag & CAP) {
        if (c1 >= 'a' && c1 <= 'z')
            c1 = c1 - 'a' + 'A';
    }
    
    // 2. 特殊字符处理：\n 转换成 \r\n（回车+换行）
    //    制表符转换成空格序列
    //    等等
    
    // 3. 调用 lpoutput 输出转换后的字符
    lpoutput(c1);
}
```

**关键设计**：

1. **大写转换**：LP11 连接的某些行式打印机只支持大写，所以 `lpcanon()` 在小写字母时转为大写
    
2. **换行规范化**：把 `\n` 展开为 `\r\n`（回车+换行）——这是早期 UNIX 文本惯例的来源，今天 Windows 的 `\r\n` 与 UNIX 的 `\n` 分歧，根源就在 `lpcanon()` 这类规范化函数
    
3. **制表符展开**：把 `\t` 展开为适当数量的空格，对齐到制表位
    
4. **可扩展**：`lpcanon()` 是字符设备的"数据处理层"，终端驱动中的 `ttyinput()`/`ttyoutput()` 也是类似的设计
    

> 💡 **洞见**：`lpcanon()` 揭示了字符设备驱动的分层设计——
> 
> ```
> write() 系统调用
>   → lpwrite()      // 驱动入口
>   → lpcanon()      // 字符规范化（数据处理层）
>   → lpoutput()     // 缓冲区管理（缓冲层）
>   → lpstart()      // 硬件启动（寄存器操作层）
>   → lpint()        // 中断处理（硬件完成通知）
> ```
> 
> **每一层职责单一**：write 负责与系统调用对接，canon 负责字符转换，output 负责缓冲，start 负责硬件操作，int 负责中断响应。这种"分层 + 单向数据流"的模式，是今天所有驱动框架（Linux 的 tty 层、网络协议栈、USB 驱动栈）的共同祖先。

### lpoutput()

`lpoutput(c)` 是**缓冲区管理层**​ ：

```
lpoutput(c) {
    if (lp11.cc >= LPHWAT)        // 缓冲区字符数 >= 高水位
        sleep(&lp11, LPPRI);      // 睡眠等待中断处理程序唤醒
    putc(c, &lp11);               // 字符放入 clist 缓冲区
    spl4();                       // 提升中断优先级
    lpstart();                    // 尝试启动硬件输出
    spl0();                       // 恢复中断优先级
}
```

**关键设计**：

1. **LPHWAT（高水位）= 100**：当缓冲区字符数达到 100 时，写进程睡眠
    
2. **putc(c, &lp11)**：字符放入 clist 环形队列
    
3. **spl4()/spl0()**：提升/恢复中断优先级，保护 lpstart() 不被中断打断
    
4. **lpstart()**：尝试启动硬件——如果设备就绪（DONE 位置位），立即输出一个字符
    

### lpstart()

`lpstart()` 是**硬件操作层**​ ：

```
lpstart() {
    register int c;
    while (LPADDR->lpsr & DONE && (c = getc(&lp11)) >= 0)
        LPADDR->lpbuf = c;  // 写入数据寄存器，启动字符输出
}
```

**关键设计**：

1. **DONE 位检查**：`LPADDR->lpsr & DONE` 为真表示设备就绪，可以接收下一个字符
    
2. **getc(&lp11)**：从 clist 缓冲区取一个字符
    
3. **LPADDR->lpbuf = c**：写入数据寄存器，**这一赋值触发硬件开始输出字符**
    
4. **循环输出**：只要设备就绪且缓冲区有数据，就连续输出——这加速了批量打印
    

### lpint()

`lpint()` 是**中断处理程序**​ ：

```
lpint() {
    register int c;
    lpstart();  // 继续输出下一个字符
    if (lp11.cc == LPLWAT || lp11.cc == 0)  // 达到低水位或缓冲区空
        wakeup(&lp11);  // 唤醒睡眠的写进程
}
```

**关键设计**：

1. **LPLWAT（低水位）= 50**：当缓冲区字符数降到 50 或 0 时，唤醒等待的写进程
    
2. **lpstart()**：中断处理程序中继续输出——因为当前字符输出完成，设备 DONE 位置位，可以发送下一个
    
3. **wakeup(&lp11)**：唤醒因缓冲区满而睡眠的写进程——这是生产-消费者模型的"消费者唤醒生产者"
    

### lpclose()

`lpclose(dev, flag)` 的源码 ：

```
lpclose(dev, flag) {
    lpcanon(FORM);  // 输出换页符，结束当前页
    lp11.flag = 0;  // 清除 OPEN 标志
}
```

**关键设计**：

1. **lpcanon(FORM)**：输出换页符，让打印机走到下一页——这样打印纸会走到页与页的边界，方便撕纸
    
2. **清除 OPEN 标志**：允许设备再次被打开
    
3. **注意**：lpclose 并不立即刷新所有缓冲数据——换页符之后的数据可能仍在缓冲区中，等待中断逐步输出
    

> ⚠️ **关键语义**：V6 文档明确说"_The close routine is called only when the file is closed for the last time_" ——这意味着**驱动无法自己维护用户计数**。如果多个进程打开同一个 LP11 设备，只有最后一个进程关闭时 lpclose 才会被调用。这是一个重要的限制——驱动必须假设"随时可能有多个用户"，用其他方式（如 OPEN 标志）做互斥。

## 12.3 小结

第12章完成了 V6 字符设备驱动的完整剖析。把所有机制串起来看：

```
用户程序：
  fd = open("/dev/lp0", O_WRONLY)
  write(fd, "Hello\n", 6)
  close(fd)

内核路径：
  open() → openi() → cdevsw[2].d_open(0) → lpopen(0)
  write() → writei() → 发现 IFCHR → cdevsw[2].d_write(0) → lpwrite(0)
  close() → closei() → cdevsw[2].d_close(0) → lpclose(0)

lpwrite(0) 内部：
  while (c = cpass()) >= 0
    → lpcanon(c)
      → lpoutput(c)
        → if (lp11.cc >= LPHWAT) sleep(&lp11, LPPRI)  // 缓冲区满则睡眠
        → putc(c, &lp11)                              // 字符入 clist 缓冲
        → spl4(); lpstart(); spl0()                  // 尝试启动硬件
          → lpstart():
              while (LPADDR->lpsr & DONE && (c = getc(&lp11)) >= 0)
                LPADDR->lpbuf = c                    // 写寄存器，触发硬件输出

硬件中断：
  LP11 完成一个字符输出 → 发中断 → lpint()
    → lpstart()                                        // 继续输出下一个
    → if (lp11.cc == LPLWAT || lp11.cc == 0)
        wakeup(&lp11)                                  // 唤醒睡眠的写进程
```

**第一性原理总结**：

1. **"主设备号 → 函数指针表"是字符设备的接入方式**：`cdevsw[major].d_write(minor)` 这一行代码，把"文件抽象"与"硬件驱动"彻底解耦 。今天 Linux 的 `struct cdev` + `struct file_operations` 是同一思想的演化 。
    
2. **字符设备不走页缓存，I/O 直达驱动**：与块设备的"write → 页缓存 → 写回"不同，字符设备的 write 直接到达驱动 。这是字符设备"字节流、顺序访问"本质决定的。
    
3. **驱动内部分层**：lpwrite → lpcanon → lpoutput → lpstart → lpint，每一层职责单一 。这种"分层 + 单向数据流"的模式，是今天所有驱动框架（tty 层、网络协议栈、USB 驱动栈）的共同祖先。
    
4. **clist 是字符设备的缓冲区**：clist 是一个字符环形队列，通过 putc/getc 操作，解决生产-消费者速率匹配问题。LPHWAT（100）是高水位，LPLWAT（50）是低水位——这是"水位线"流控算法的早期实践。
    
5. **中断驱动是字符设备的灵魂**：lpstart 启动硬件输出第一个字符，lpint 在中断中继续输出后续字符 。整个输出过程是中断驱动的、异步的——write 系统调用只是把数据推入缓冲区就返回，真正的硬件输出在中断上下文中逐步完成。
    
6. **spl4()/spl0() 保护临界区**：在 lpoutput 中，spl4() 提升中断优先级，防止 lpstart 执行期间被 LP11 中断打断（否则可能导致竞态）。这是单 CPU 时代的"关中断保护"模式。
    

**跨章节联系**：

- **第2章的 user 结构体**：`u.u_count`、`u.u_base`、`u.u_segflg` 是字符设备 write/read 的核心参数
    
- **第5章的中断与陷入**：lpint 是中断处理程序，通过硬件中断向量表调用
    
- **第6章的信号**：字符设备驱动可以发送信号（如终端的 SIGINT）
    
- **第8章的块设备驱动**：与字符设备驱动平行，但块设备走缓冲区高速缓存，字符设备走 clist
    
- **第10章的文件处理**：open/write/close 系统调用是字符设备的用户态接口
    
- **第11章的管道**：管道也是一种"字符流"抽象，但管道的数据在内存中，字符设备的数据在硬件上
    

**工业落地的五点启示**：

### 1. **"主设备号 + 函数指针表"是设备驱动的标准架构**

从 V6 的 `cdevsw[]` 到 Linux 2.4 的 `register_chrdev()`，再到 Linux 2.6+ 的 `struct cdev` + `struct file_operations` ，**核心架构 50 年未变**：

- 主设备号标识驱动
    
- 次设备号标识具体设备实例
    
- 驱动通过函数指针表注册 open/release/read/write/ioctl/mmap 等操作
    
- 用户态用 `mknod` 创建设备文件，用 open/read/write 操作设备
    

**第一性原理：用"整数标识 + 函数指针表"解耦"用户态接口"与"硬件实现"**。今天你在 Linux 上写任何字符设备驱动，都遵循这一范式：

```
// Linux 2.6+ 字符设备驱动骨架
static struct file_operations my_fops = {
    .open = my_open,
    .read = my_read,
    .write = my_write,
    .release = my_release,
};
static struct cdev my_cdev;
cdev_init(&my_cdev, &my_fops);
alloc_chrdev_region(&devt, 0, 1, "mydev");
cdev_add(&my_cdev, devt, 1);
```

**这段代码的祖先就是 V6 的 `lpopen/lpwrite/lpclose` 注册到 `cdevsw[]`**。

### 2. **字符设备"不走页缓存"是性能与语义的双重选择**

V6 的字符设备 write 直达驱动 ；现代 Linux 的字符设备同样**不参与页缓存**​ 。这是字符设备的本质决定的：

- **字节流语义**：字符设备是顺序字节流，没有"块"的概念，页缓存的"块对齐"优化无用武之地
    
- **实时性要求**：终端、串口等字符设备通常需要"写即达"，不能延迟
    
- **硬件速率限制**：驱动内部的 clist 已经做了速率匹配，不需要再在 VFS 层缓存
    

**工业联系**：

- 今天你在 Linux 上写串口驱动、GPIO 驱动、I2C 驱动、USB 字符设备驱动，都遵循"write 直达驱动"的语义
    
- 某些字符设备（如 framebuffer、GPU）通过 `mmap` 直接映射硬件内存到用户空间，绕过 write 系统调用
    
- 块设备的"原始 I/O"接口（`/dev/sda` 的 O_DIRECT）借鉴了字符设备的"无缓存"语义
    

### 3. **"水位线"流控是生产-消费者模型的经典算法**

LP11 驱动用 LPHWAT=100（高水位）和 LPLWAT=50（低水位）实现流控 ：

- 缓冲区字符数 >= 100 → 写进程睡眠
    
- 缓冲区字符数降到 50 或 0 → 唤醒写进程
    

这是"**高低水位线（high/low watermark）**"流控算法的早期实践。今天：

- TCP 套接字的 `SO_SNDBUF` / `SO_RCVBUF` 用类似的水位线机制
    
- 网络设备的 TX/RX 队列用水位线做流控
    
- 声卡的 ALSA 缓冲区用水位线触发回调
    
- 任何"生产者-消费者"系统（线程池、消息队列、管道）都用这一算法
    

### 4. **中断驱动是 I/O 设备的主流模型**

LP11 的"write 推入缓冲区 → lpstart 启动 → lpint 中断中继续"模式 ，是中断驱动 I/O 的经典范式：

- **write 是非阻塞的**：把数据推入缓冲区立即返回
    
- **硬件是异步的**：设备在自有速率下消费数据
    
- **中断是完成通知**：每完成一个字符，中断触发下一个字符的输出
    
- **sleep/wakeup 做同步**：缓冲区满时写进程睡，中断处理程序中唤醒
    

今天所有高性能 I/O 设备都遵循这一模型：

- **网卡**：NAPI 中断 + 轮询混合驱动
    
- **磁盘**：NVMe 的完成队列中断
    
- **USB**：URB 完成回调
    
- **声卡**：PCM 数据消费中断
    

### 5. **字符规范化（canonicalization）是终端处理的核心**

`lpcanon()` 做的字符转换（小写转大写、`\n` 展开为 `\r\n`、制表符展开） ，是终端"规范模式（canonical mode）"的雏形。今天：

- Linux 终端的 `ICANON` 模式：缓冲行、处理 ERASE/KILL、展开 `\n` 为 `\r\n`
    
- 串口的 `termios` 设置：INLCR、ICRNL、ONLCR、OPOST 等标志位
    
- 文本的 `\n` vs `\r\n` 分歧：根源就在 `lpcanon()` 这类规范化函数
    

> 💡 **Windows 与 UNIX 的文本换行分歧溯源**：UNIX 用 `\n`（LF），Windows 用 `\r\n`（CRLF）。这是因为早期 UNIX 的终端和打印机驱动（如 `lpcanon()`）**在输出时自动把 `\n` 展开为 `\r\n`**——所以用户态只需写 `\n`，驱动负责展开。而 DOS/Windows 选择在用户态显式写 `\r\n`。这一设计选择的不同，造就了今天跨平台文本处理的永恒痛点。

## 英文补充资料与跨时代对照

### 1. V6 设备开关表定义（原典）

V6 源码 `conf.c` 中的 `cdevsw[]` 定义 ，以及 `lp.c` 中 LP11 驱动的完整实现 ，特别是：

- `lpopen()` 的设备状态检查和中断使能
    
- `lpwrite()` 通过 `cpass()` 逐个取字符
    
- `lpcanon()` 的字符规范化
    
- `lpoutput()` 的水位线流控（LPHWAT=100）
    
- `lpstart()` 的 DONE 位检查
    
- `lpint()` 的中断处理和低水位唤醒（LPLWAT=50）
    

### 2. System III 的 `u_iosys` 文档

TUHS 保存的 System III 文档精确描述了字符设备驱动的接口契约 ：

- "_The cdevsw table specifies the interface routines present for character devices. Each device provides five routines: open, close, read, write, and special-function_"
    
- "_The open routine is called each time the file is opened... The close routine is called only when the file is closed for the last time_"
    
- "_For most drivers, which work one character at a time, the routine cpass() is used to pick up characters from the user's buffer_"
    
- "_Write routines which want to transfer a probably large number of characters into an internal buffer may also use the routine iomove(buffer, offset, count, flag)_"
    

这份文档虽然是 System III（1980），但它描述的接口契约与 V6（1975）**完全一致**，是理解字符设备驱动语义的最权威英文资料。

### 3. "Writing a device driver for Unix V6"

这篇文章手把手展示了如何为 V6 编写一个字符设备驱动 ：

- 定义 `mbwrite()` 函数，通过 `cpass()` 循环取字符
    
- 在 `cdevsw[]` 表中注册驱动：`&nulldev, &nulldev, &nodev, &mbwrite, &nodev`
    
- 用 `mknod /dev/mb c 16 0` 创建设备文件
    
- 展示 `echo Hello > /dev/mb` 的执行路径：`write → rdwr → writei → cdevsw[16].d_write → mbwrite`
    
- 揭示了 V6 虚拟内存映射的细节：`0177340` 在用户态对应 `177340`（内核态高位地址映射）
    

### 4. Linux 字符设备驱动的演化（现代对照）

Linux Kernel Labs 的资料清晰说明了 UNIX 字符设备模型在 Linux 中的延续 ：

- "_In UNIX, hardware devices are accessed by the user through special device files in /dev_"
    
- "_system calls open, read, write, close, lseek, mmap etc. are redirected by the operating system to the device driver_"
    
- "_For character devices system calls go directly to device drivers, in case of block devices, the drivers do not work directly with system calls_"
    
- "_The identifier consists of two parts: major and minor. The first part identifies the device type, and the second one identifies the device_"
    

kernel-internals.org 的资料给出了 Linux 2.6+ 的 `struct cdev` 和 `struct file_operations` 完整定义 ，明确展示了现代字符设备驱动框架：

- `alloc_chrdev_region()` / `cdev_add()` 替代 `register_chrdev()`
    
- `struct file_operations` 包含 `.open/.read/.write/.unlocked_ioctl/.mmap/.release` 等函数指针
    
- `container_of` 宏从 `inode->i_cdev` 反查驱动私有数据
    

### 5. 现代对照表

|V6 概念|现代 Linux 对应|演化|
|---|---|---|
|`cdevsw[]` 设备开关表|`struct cdev` + `struct file_operations`|从全局数组 → 每个设备一个 cdev 对象|
|`cdevsw[major].d_open`|`file_operations.open`|函数指针语义一致|
|`cdevsw[major].d_close`|`file_operations.release`|注意：Linux 改名为 release|
|`cdevsw[major].d_read`|`file_operations.read` / `read_iter`|增加了 `read_iter`（异步 I/O）|
|`cdevsw[major].d_write`|`file_operations.write` / `write_iter`|增加了 `write_iter`|
|`cdevsw[major].d_sgtty`|`file_operations.unlocked_ioctl`|ioctl 从 sgtty 演化|
|`mknod /dev/lp c 2 0`|`mknod /dev/lp c 2 0` + udev 自动创建|用户态命令完全一致，udev 自动化|
|主设备号静态分配|`alloc_chrdev_region()` 动态分配|避免主设备号冲突|
|`cpass()` 逐个取字符|`copy_from_user()` + 循环|机制一致，接口演化|
|`iomove()` 批量拷贝|`copy_from_user()` / `iov_iter`|支持分散/聚集 I/O|
|clist 字符缓冲区|`struct circ_buf` / `kfifo`|内核提供通用环形缓冲区|
|`putc()` / `getc()`|`kfifo_put()` / `kfifo_get()`|通用环形缓冲区操作|
|LPHWAT/LPLWAT 水位线|`SO_SNDBUF` / `SO_RCVBUF` 水位线|TCP 套接字流控|
|`spl4()` / `spl0()`|`local_irq_save()` / `local_irq_restore()`|从 PDP-11 中断优先级 → CPU 中断控制|
|`sleep(&lp11, LPPRI)`|`wait_event()` / `schedule()`|从简单 sleep → 等待队列|
|`wakeup(&lp11)`|`wake_up()`|等待队列唤醒|
|`lpint()` 中断处理|`request_irq()` 注册的中断处理程序|中断注册机制演化|
|`lpcanon()` 字符规范化|`termios` 的 `OPOST` 标志|终端规范模式|
|`lp_addr[unit]->lpsr` 寄存器访问|`ioremap()` 映射后读写|从物理地址直接访问 → ioremap 映射|
|`&nulldev` / `&nodev`|`NULL` 函数指针|用 NULL 表示不支持的操作|
|无 `mmap`|`file_operations.mmap`|现代字符设备支持内存映射|
|无 `poll`|`file_operations.poll`|现代字符设备支持多路复用|
|无异步 I/O|`file_operations.read_iter` / `io_uring`|现代异步 I/O 框架|

> 💡 **跨时代洞见**：从 V6 到现代 Linux，字符设备驱动的**第一性原理完全一致**：
> 
> - **主设备号 + 次设备号**：标识驱动和设备实例
>     
> - **函数指针表**：open/close/read/write/ioctl 的驱动实现
>     
> - **write 直达驱动**：不经过页缓存
>     
> - **中断驱动**：硬件异步消费数据，中断处理程序继续输出
>     
> - **clist 缓冲区**：解决生产-消费者速率匹配
>     
> - **水位线流控**：LPHWAT/LPLWAT → SO_SNDBUF/SO_RCVBUF
>     
> - **mknod 创建设备文件**：用户态命令 50 年未变
>     
> 
> 变的是**规模**（主设备号从 8 位扩展到 12+ 位）、**并行度**（从单 CPU 关中断 → 多核 spinlock + 每 CPU 变量）、**能力**（增加了 mmap、poll、异步 I/O、ioctl 扩展）、**自动化**（udev 自动创建设备节点）。但**骨架——"主设备号查表 → 函数指针分派 → 驱动内部中断驱动 I/O"——50 年没变**。
> 
> 正如 Linux Kernel Labs 文档所总结的 ："_In UNIX, hardware devices are accessed by the user through special device files. These files are grouped into the /dev directory, and system calls open, read, write, close, lseek, mmap etc. are redirected by the operating system to the device driver associated with the physical device._" —— 这段描述对 V6 和现代 Linux **同时成立**。

## 给读者的学习建议

1. **在 Linux 上观察字符设备驱动的现代演化**：
    
    ```
    # 查看已注册的字符设备
    cat /proc/devices
    
    # 查看设备文件的主/次设备号
    ls -la /dev/ttyS0 /dev/lp0 /dev/null /dev/zero
    
    # 用 strace 跟踪字符设备操作
    strace -e trace=open,read,write mknod /tmp/mydev c 240 0
    
    # 阅读一个真实字符设备驱动源码
    # Linux 内核中的 drivers/char/mem.c（/dev/null, /dev/zero 的实现）
    # drivers/tty/serial/8250/8250_core.c（串口驱动）
    ```
    
    你会发现——**V6 的 `cdevsw[]` 思想在现代 Linux 中完好延续**。
    
2. **画出 LP11 驱动的完整状态机**：
    
    ```
    用户 write:
      lpwrite → cpass 取字符 → lpcanon 转换
        → lpoutput:
            if cc >= 100: sleep
            putc → clist
            lpstart: while DONE && getc: lpbuf = c
    
    硬件中断:
      lpint:
        lpstart（继续输出）
        if cc == 50 or 0: wakeup
    
    用户 close:
      lpclose → lpcanon(FORM) → 清 OPEN 标志
    ```
    
    理解这个状态机，你就理解了中断驱动 I/O 的精髓。
    
3. **对照 Linux 现代字符设备驱动**：
    
    - V6 的 `lp.c` → Linux 的 `drivers/char/lp.c`（现代并口打印机驱动）
        
    - V6 的 `cdevsw[]` → Linux 的 `struct cdev`
        
    - V6 的 `lpwrite` → Linux 的 `lp_write`
        
    - V6 的 `lpint` → Linux 的 `lp_interrupt`
        
    
    阅读 Linux 的 `drivers/char/lp.c`，你会看到 V6 的 LP11 驱动思想在 50 年后的延续。
    
4. **思考设计问题**：如果让你为现代 PCIe 设备编写字符设备驱动，你会：
    
    - 如何处理多核并发？（提示：Linux 用 mutex、spinlock、per-CPU 变量）
        
    - 如何支持异步 I/O？（提示：`read_iter` / `io_uring`）
        
    - 如何支持 mmap？（提示：`file_operations.mmap` + `remap_pfn_range`）
        
    - 如何处理设备热插拔？（提示：Linux 设备模型 + udev）
        
    
    这个练习会让你深刻理解——**V6 的字符设备架构在今天的约束下该如何演化**。答案就在 Linux 的字符设备框架中：它保留了 V6 的核心语义（主/次设备号、函数指针表、write 直达驱动），但在每一层都做了多核优化和能力扩展。
