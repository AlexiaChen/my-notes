
# 《Unix内核源码剖析》读书笔记 · 第9章 文件系统

> 第7章我们把"块设备缓冲区"建好了——内核可以用 `bread/bwrite` 按"设备号+块号"读写 512 字节的块；第8章我们把"块设备驱动"打通了——RK11-D 把"块号"翻译成"柱面/磁道/扇区"。但用户要的不是"块"，是"/home/ken/hello.c"这样的**文件路径**。第9章回答的就是这个核心问题：**如何把"人类可读的路径名"转换为"磁盘上的数据块"？**
> 
> **第一性洞见**：UNIX 文件系统的本质是**"三权分立"**——
> 
> - **文件名**​ 与 **文件内容**​ 完全分离（目录只存"名字→inode号"的映射）
>     
> - **inode**​ 是文件的"身份证"（存元数据+数据块索引，不含文件名）
>     
> - **数据块**​ 是文件的"身体"（纯二进制内容）
>     
> 
> 正如斯坦福 CS111 讲义所指出的："_The Unix v6 filesystem stores inodes on disk together in a fixed-size inode table... The inode table starts at block 2... Inodes are 32 bytes big, and 1 block = 1 sector = 512 bytes, so 16 inodes/block_" 。这种"文件名- inode - 数据块"的三级分离，是 UNIX "一切皆文件"哲学得以成立的**架构基础**——因为文件名与内容解耦，所以同一个文件可以有多个名字（硬链接）；因为 inode 与数据块分离，所以文件可以动态增长；因为这一切都通过 inode 统一抽象，所以普通文件、目录、设备特殊文件、管道才能用同一套机制管理。

## 9.1 什么是文件系统

### inode

inode（索引节点）是 V6 文件系统的核心抽象。磁盘上的 inode 结构体（32 字节） ：

```
struct inode {
    int16_t i_mode;     // 文件类型和权限位
    uint8_t i_nlink;    // 硬链接数
    uint8_t i_uid;      // 所有者用户 ID
    uint8_t i_gid;      // 所有者组 ID
    uint8_t i_size0;    // 文件大小高字节
    int16_t i_size1;    // 文件大小低 16 位（共 24 位）
    int16_t i_addr[8];  // 8 个块地址/索引
    int16_t i_atime[2]; // 最后访问时间
    int16_t i_mtime[2]; // 最后修改时间
};
```

**关键字段解读**：

- **i_mode**：高 4 位表示文件类型（普通文件、目录、字符设备、块设备），低 12 位是权限（755 等）
    
- **i_nlink**：硬链接计数。只有当 i_nlink 降为 0 时，文件数据块才被释放
    
- **i_addr[8]**：这是文件系统的"寻址引擎"——8 个 16 位块号，实现直接索引+间接索引
    
- **i_size**：24 位文件大小，最大 16MB（但实际上受 i_addr 寻址能力限制）
    

**inode 在磁盘上的布局**：

> 📌 重要事实：inode 从 block 2 开始连续存储，每个块存 16 个 inode（512/32=16），i-number 从 1 开始编号，i-number 1 永远是根目录 。

计算 inode N 的磁盘位置：

- 所在块号：`2 + (N-1)/16`
    
- 块内偏移：`(N-1) % 16 * 32`
    

### 树状结构的命名空间

UNIX 文件系统是一个**树状命名空间**，根是 `/`（i-number 1）。树的每个节点都是一个目录文件，目录的内容是**目录项（directory entry）**序列 ：

```
struct direct {
    char d_name[14];    // 14 字节文件名
    int16_t d_ino;      // 2 字节 inode 号
};
```

每个目录项固定 16 字节——14 字节文件名 + 2 字节 i-number。因为 16 字节恰好是 512 字节块的 1/32，所以**一个目录项绝不会跨块边界**——这是一个精妙的尺寸选择 。

> 💡 **洞见**：目录也是文件，只是它的内容是"名字→inode 号"的映射表。这意味着：
> 
> - `mkdir` 就是创建一个新文件 + 在其中写 `.` 和 `..` 两个目录项
>     
> - `ln` 硬链接就是在一个目录里增加一个目录项，指向已有的 inode，并递增 i_nlink
>     
> - `unlink` 删除文件就是删除一个目录项，并递减 i_nlink
>     
> - 文件的实际数据块，直到 i_nlink 归零才会被释放
>     
> 
> **"文件"与"名字"的彻底解耦**，是 UNIX 文件系统最优雅的设计——它让硬链接、符号链接、挂载、管道、设备文件，全都成为"inode + 目录项"的自然推论。

### 挂载

挂载（mount）是 UNIX 文件系统的"命名空间拼接"机制——把一个文件系统的根目录"嫁接"到另一个文件系统的某个目录节点上 。

**挂载的核心思想**：

```
挂载前：
/ (root fs i-num 1)
├── bin/
├── home/
│   └── ken/
└── dev/

执行：mount /dev/rk1 /home/ken/data

挂载后：
/ (root fs i-num 1)
├── bin/
├── home/
│   └── ken/
│       └── data/  ← 这个目录现在是 rk1 文件系统的根
│           ├── file1
│           └── file2
```

挂载的实现机制（来自 MIT 6.828 讲义）：_"mount /dev/rk0 /mnt/ will create an inode with IMOUNT for /mnt, which will point to the inode for /dev/rk"_ ——挂载点的 inode 被标记为 IMOUNT 标志，并指向被挂载设备的根 inode。当 `namei()` 解析路径时，遇到 IMOUNT 标记的 inode，就会"跳转"到被挂载文件系统的命名空间继续解析 。

> ⚠️ **洞见**：挂载的本质是**命名空间的递归拼接**。V6 用"挂载点 inode 带 IMOUNT 标志 + 指向被挂载设备根 inode"这种极简方式，实现了无限层级的文件系统树。今天你在 Linux 上看到的 `/proc`、`/sys`、`/dev`、`/run`、`/var/lib/docker` 等挂载点，其机制与 V6 完全相同——**挂载是命名空间的"超链接"**。

### 访问权限

V6 的权限模型极其简单但完备 ：

- **i_mode 低 9 位**：owner/group/other 的 rwx 权限
    
- **i_uid / i_gid**：文件所有者
    
- **访问检查**：`access(ip, mode)` 函数根据当前进程的 uid/gid 与 i_uid/i_gid 匹配，检查请求的权限位
    

**特殊权限**：

- **SUID**（V6 中通过 i_mode 高位标志）：执行时进程 euid 设为文件所有者的 uid
    
- **目录的 x 权限**：表示"可进入"（search permission）
    

> 📌 **工业联系**：今天 Linux 的 `ls -l` 输出的 `drwxr-xr-x`、`-rwsr-xr-x`（SUID）等权限位，与 V6 的 i_mode 编码**完全一致**。50 年没变的 ABI。

### 根磁盘

根磁盘（root disk）是系统启动时挂载到 `/` 的文件系统。V6 在 `iinit()` 中初始化根文件系统：

```
iinit() {
    // 挂载根设备（通常是 RK0）
    mountroot(...);
    // 读取根 inode（i-num 1）
    rootdir = iget(rootdev, 1);
    // 设置当前目录为根
    u.u_cdir = rootdir;
}
```

## 9.2 块设备的区域

V6 文件系统把整个块设备划分为四个区域 ：

```
Block 0:   引导块（Boot Block）—— 存放 bootstrap 程序
Block 1:   超级块（Superblock）—— 文件系统元信息
Block 2
  ↓
Block 2+s_isize-1:  inode 区（i-list）—— 所有 inode 连续存储
Block 2+s_isize
  ↓
Block s_fsize-1:  数据区（Data Blocks）—— 文件数据 + 间接块
```

### 用于启动的区域

**Block 0**​ 是引导块，存放 bootstrap 程序，与文件系统结构无关——它被 PDP-11 的 ROM 固件加载到内存执行，启动整个系统 。

### 超级块

**Block 1**​ 是超级块，结构体 `filsys` ：

```
struct filsys {
    int16_t s_isize;       // inode 区占用的块数
    int16_t s_fsize;       // 文件系统总块数
    int16_t s_nfree;       // 空闲块缓存数量
    int16_t s_free[100];   // 空闲块号缓存
    int16_t s_ninode;      // 空闲 inode 缓存数量
    int16_t s_inode[100];  // 空闲 inode 号缓存
    char    s_flock;       // 空闲块锁
    char    s_ilock;       // 空闲 inode 锁
    char    s_fmod;        // 超级块修改标志（脏标志）
    int16_t s_time[2];     // 最后修改时间
};
```

**关键字段解读**：

- **s_isize**：inode 区占用多少块。从 block 2 开始，到 `2+s_isize-1` 结束
    
- **s_fsize**：文件系统总块数
    
- **s_free[100]**：空闲块号的**成组链接缓存**——这是 V6 空闲块管理的核心数据结构
    
- **s_inode[100]**：空闲 inode 号的缓存
    
- **s_fmod**：脏标志。如果为 1，表示超级块已被修改，需要在 `update()` 时写回磁盘
    

> 💡 **洞见**：超级块是文件系统的"控制中心"。它记录了两个关键资源（空闲块、空闲 inode）的分配状态。但 V6 的设计极其巧妙——**超级块不保存完整的空闲块列表，而是只缓存 100 个空闲块号**。当需要更多时，从磁盘上的"空闲块链"中批量加载。这是"内存缓存 + 磁盘持久化"的经典模式。

### inode 区域

**Block 2 到 Block 2+s_isize-1**​ 是 inode 区，所有 inode 连续存储 ：

- 每个 inode 32 字节
    
- 每个 512 字节块存 16 个 inode
    
- i-number 从 1 开始（i-number 0 保留不用，因为 iget 错误时返回 0）
    
- i-number 1 永远是根目录
    

**i-number 到磁盘位置的换算**：

```
block = 2 + (i_number - 1) / 16
offset = ((i_number - 1) % 16) * 32
```

### 存储区域

**Block 2+s_isize 到 Block s_fsize-1**​ 是数据区，存放：

- 普通文件的数据块
    
- 目录文件的数据块（目录项序列）
    
- 大文件的间接索引块
    

数据块的分配通过 `alloc()` 函数实现，释放通过 `free()` 函数实现。

## 9.3 挂载

### mount 结构体

每个挂载点对应一个 `mount` 结构体（在内存中）：

```
struct mount {
    int16_t m_dev;        // 设备号
    struct buf *m_bufp;   // 指向超级块的缓冲区
    struct inode *m_inodp; // 指向挂载点目录的 inode
};
```

系统维护一个 `mount[NMNT]` 数组，记录所有已挂载的文件系统 。

### 系统调用 mount

`mount(dev, dir, rwflag)` 系统调用的流程：

1. **权限检查**：只有超级用户（uid=0）可以执行 mount
    
2. **获取挂载点 inode**：`iget(dir)` 获取目标目录的 inode
    
3. **检查挂载点**：
    
    - 必须是目录
        
    - 不能被其他文件系统挂载（不能有 IMOUNT 标志）
        
    - 必须是本文件系统内的节点（防止跨文件系统挂载）
        
    
4. **读取超级块**：`bread(dev, 1)` 读取被挂载设备的超级块
    
5. **设置 IMOUNT 标志**：在挂载点 inode 上设置 IMOUNT 标志
    
6. **建立 mount 结构体**：记录设备号、超级块缓冲区、挂载点 inode
    
7. **加入 mount 数组**
    

> ⚠️ **关键设计**：挂载点的 inode 被标记为 IMOUNT，并且"记住"了被挂载设备的根 inode。当 `namei()` 解析路径走到这个目录时，检测到 IMOUNT 标志，就会"跳转"到被挂载设备的命名空间继续解析 。

### getmdev()

`getmdev(ip)` 函数的作用是：给定一个 inode，返回它所属的文件系统设备号。如果 inode 是挂载点（IMOUNT 标志），则返回被挂载设备的设备号；否则返回 inode 自己的设备号。

这是 `namei()` 实现挂载点"跳转"的关键辅助函数。

### 系统调用 umount

`umount(dev)` 系统调用的流程：

1. **权限检查**：只有超级用户
    
2. **查找 mount 结构体**：在 mount 数组中找到对应 dev 的挂载项
    
3. **检查是否繁忙**：如果被挂载文件系统上还有进程打开文件，拒绝 umount
    
4. **清除 IMOUNT 标志**：清除挂载点 inode 的 IMOUNT 标志
    
5. **释放资源**：释放挂载点 inode、超级块缓冲区，从 mount 数组移除
    

> 💡 **洞见**：umount 的"繁忙检查"是文件系统一致性的关键保障——V6 不允许卸载一个仍有文件被打开的文件系统，否则那些打开文件的 inode 就会"悬挂"。这揭示了**挂载是命名空间的"硬连接"**——一旦建立，就不能随意断开。

## 9.4 inode 的获取和释放

这是文件系统最核心的两个函数：`iget()` 和 `iput()`。

### inode[] 数组

系统在内存中维护一个固定大小的 inode 数组 `inode[NINODE]`，作为**inode 缓存**：

```
struct inode inode[NINODE];  // 通常 NINODE = 100
```

每个内存 inode 是磁盘 inode 的**内存映像**，加上一些控制字段：

```
struct inode {
    // 磁盘 inode 的所有字段（i_mode, i_nlink, i_uid, ...）
    // 加上：
    int16_t i_flag;         // 标志：ILOCK, IUPD, IMOD, etc.
    int16_t i_count;        // 引用计数（多少个进程/文件句柄引用）
    int16_t i_dev;          // 所属设备
    int16_t i_number;       // i-number
    struct inode *i_forw;   // 哈希链前向指针
    struct inode *i_back;   // 哈希链后向指针
    struct inode *i_freef;  // 空闲链前向指针
    struct inode *i_freeb;  // 空闲链后向指针
};
```

### iget()

`iget(dev, ino)` 获取一个 inode 的内存映像 ：

```
iget(dev, ino) {
    // 1. 在内存 inode 表中查找
    for (ip = inode; ip < inode+NINODE; ip++) {
        if (ip->i_dev == dev && ip->i_number == ino) {
            // 找到！增加引用计数
            if ((ip->i_flag & ILOCK) == 0) {
                ip->i_count++;
                return(ip);  // 直接返回，无需读盘
            }
            // 已被锁定，等待解锁
            sleep(ip, PIN);
            goto loop;  // 重试
        }
    }
    
    // 2. 未在内存中，找一个空闲 inode 槽位
    for (ip = inode; ip < inode+NINODE; ip++) {
        if (ip->i_count == 0 && (ip->i_flag & ILOCK) == 0) {
            // 清空并复用
            ip->i_dev = dev;
            ip->i_number = ino;
            ip->i_count = 1;
            ip->i_flag = ILOCK;  // 加锁
            
            // 3. 从磁盘读取 inode
            block = 2 + (ino-1)/16;
            offset = ((ino-1)%16)*32;
            bp = bread(dev, block);
            // 复制磁盘 inode 到内存 inode
            bcopy(bp->b_addr + offset, ip, 32);
            brelse(bp);
            
            return(ip);
        }
    }
    
    // 内存 inode 表已满
    panic("iget: no inodes");
}
```

**iget() 的关键设计**：

1. **内存缓存优先**：先查内存 inode 表，命中则直接返回，**零磁盘 I/O**
    
2. **引用计数**：`i_count` 记录有多少个用户引用这个 inode
    
3. **ILOCK 标志**：iget 返回的 inode 是**加锁**的，防止并发修改
    
4. **未命中读盘**：计算磁盘位置 → bread() 读块 → 复制 32 字节 → brelse()
    

> ⚠️ **洞见**：iget() 的设计体现了**"缓存 + 引用计数 + 锁"**三位一体的资源管理范式。这个范式从 V6 一直延续到今天：
> 
> - Linux 的 `iget_locked()` / `iput()` 几乎就是 V6 iget/iput 的翻版
>     
> - 现代对象池、连接池、缓存系统都是同一思想
>     
> - 引用计数是自动资源管理的鼻祖——比 C++ 的智能指针早了 20 年
>     

### iput()

`iput(ip)` 释放一个 inode 的引用 ：

```
iput(ip) {
    // 1. 递减引用计数
    ip->i_count--;
    
    // 2. 如果还有其他引用，直接返回
    if (ip->i_count > 0)
        return;
    
    // 3. 如果 i_nlink 为 0，文件已被 unlink
    if (ip->i_nlink <= 0) {
        // 释放文件的所有数据块
        itrunc(ip);
        // 释放 inode 本身
        ifree(ip->i_dev, ip->i_number);
    }
    
    // 4. 如果 inode 被修改过，写回磁盘
    if (ip->i_flag & IUPD) {
        iupdat(ip, ...);
    }
    
    // 5. 解锁并标记为可回收
    ip->i_flag &= ~ILOCK;
    ip->i_flag |= IFLUSH;
}
```

**iput() 的关键语义**：

- **引用计数归零 ≠ 释放资源**：只有当 `i_nlink` 也为 0 时，文件数据才被真正释放
    
- **延迟写回**：inode 的修改通过 i_flag 的 IUPD 标志标记，在 iput 时或 update 时写回磁盘
    
- **itrunc + ifree**：当文件被最后 unlink 时，递归释放所有数据块，然后释放 inode
    

> 💡 **洞见**：iput() 揭示了 UNIX 文件系统的**"最后一个关闭者负责清理"**模型。这种"引用计数 + 延迟释放"的机制，是现代 RAII（Resource Acquisition Is Initialization）、智能指针、垃圾回收的**共同祖先**。V6 用 C 语言手动实现了自动资源管理——这是它对计算机科学最伟大的贡献之一。

### iupdat()

`iupdat(ip, ta, tm)` 将内存 inode 的修改写回磁盘：

```
iupdat(ip, ta, tm) {
    // 如果 inode 被修改
    if (ip->i_flag & (IUPD|IACC)) {
        // 计算磁盘位置
        block = 2 + (ip->i_number-1)/16;
        offset = ((ip->i_number-1)%16)*32;
        bp = bread(ip->i_dev, block);
        // 复制内存 inode 到磁盘 inode 位置
        bcopy(ip, bp->b_addr + offset, 32);
        // 延迟写
        bdwrite(bp);
        // 清除修改标志
        ip->i_flag &= ~(IUPD|IACC);
    }
}
```

**关键设计**：使用 `bdwrite()` **延迟写**——不立即刷盘，而是标记 B_DELWRI，等待 bflush 或 update 时批量写入。这是第7章延迟写思想在文件系统层的应用。

## 9.5 inode 与存储区域的对应关系

这是文件系统最核心的算法——**如何通过 inode 找到文件的数据块**。

### bmap()

`bmap(ip, bn, rwflag)` 将文件的**逻辑块号**转换为**物理设备块号**​ ：

V6 的寻址结构是 **"8 直接 + 间接"**​ 的三级结构 ：

```
小文件（≤ 8 块，4KB）：
    i_addr[0..7] 直接指向数据块

大文件（≤ 7×256+8 块，约 896KB）：
    i_addr[0..6] 指向 7 个一级间接块
    i_addr[7] 保留（在 V6 中不用于二级间接）

巨型文件（V6 理论上支持但通过 i_addr[7] 实现二级间接）：
    i_addr[0..6] 指向 7 个一级间接块
    i_addr[7] 指向一个二级间接块，该块包含 256 个一级间接块指针
```

**bmap() 的逻辑**（以一级间接为例）：

```
bmap(ip, bn, rwflag) {
    // 1. 直接块
    if (bn < 8) {
        if (rwflag && ip->i_addr[bn] == 0) {
            // 写时分配
            ip->i_addr[bn] = alloc(ip->i_dev);
        }
        return(ip->i_addr[bn]);
    }
    
    // 2. 一级间接块
    bn -= 8;
    if (bn < 256 * 7) {
        indir_idx = bn / 256;
        offset = bn % 256;
        
        // 获取/分配一级间接块
        if (ip->i_addr[indir_idx] == 0) {
            if (!rwflag) return(0);  // 读且不存在
            ip->i_addr[indir_idx] = alloc(ip->i_dev);
        }
        
        // 读取一级间接块
        bp = bread(ip->i_dev, ip->i_addr[indir_idx]);
        // 获取其中的物理块号
        phys = bp->b_addr[offset];
        if (phys == 0 && rwflag) {
            phys = alloc(ip->i_dev);
            bp->b_addr[offset] = phys;
            bawrite(bp);
        } else {
            brelse(bp);
        }
        return(phys);
    }
    
    // 3. 二级间接（通过 i_addr[7]）
    // 类似逻辑，多一次间接
}
```

**bmap() 的精妙之处**：

1. **按需分配**：只有在 rwflag 为写且块不存在时，才调用 alloc() 分配新块
    
2. **读时短路**：如果是读操作且块不存在，直接返回 0（不分配）
    
3. **透明间接**：调用者无需知道文件是大文件还是小文件——bmap() 自动处理间接层级
    

> 📌 **洞见**：bmap() 是 UNIX 文件系统**"一切皆文件"**​ 承诺的技术基石。无论是普通文件、目录、设备文件、管道，只要它们有数据块，都通过 bmap() 统一寻址。特别是**设备文件**——它的 i_addr 存储的不是数据块号，而是设备号（主+次），所以 bmap() 对设备文件"短路"，直接返回设备号。这种**统一抽象 + 特例短路**的设计，是现代面向对象编程"多态"思想的 C 语言前身。

**文件大小限制**：

|文件类型|寻址方式|最大大小|
|---|---|---|
|小文件|8 直接|8 × 512 = 4KB|
|大文件|7 × 256 直接 + 8|7 × 256 × 512 ≈ 896KB|
|巨型文件|7 × 256 + 1 × (256×256)|约 16.06MB|

注：不同资料对 V6 最大文件尺寸的口径略有差异，但**机制是一致的**——8 个 i_addr 项，前 7 个可做一级间接，第 8 个可做二级间接 。

### itrunc()

`itrunc(ip)` 截断文件——释放文件的所有数据块，将文件大小置为 0：

```
itrunc(ip) {
    // 1. 释放 8 个直接块
    for (i = 0; i < 8; i++) {
        if (ip->i_addr[i]) {
            free(ip->i_dev, ip->i_addr[i]);
            ip->i_addr[i] = 0;
        }
    }
    
    // 2. 释放一级间接块
    // 读取每个一级间接块，释放其中的所有数据块
    // 然后释放一级间接块本身
    
    // 3. 释放二级间接块（如果适用）
    // 读取二级间接块 → 读取每个一级间接块 → 释放数据块
    
    // 4. 文件大小清零
    ip->i_size = 0;
    ip->i_flag |= IUPD;
}
```

**itrunc() 的递归释放**：从直接块到一级间接到二级间接，层层释放。这是文件系统"垃圾回收"的最原始形态。

## 9.6 分配块设备中的块

文件系统的两个核心资源：数据块和 inode。它们的分配/释放算法是文件系统的"内存分配器"。

### ialloc()

`ialloc(dev)` 分配一个新的 inode ：

```
ialloc(dev) {
    // 1. 检查超级块缓存
    if (s->s_inode[0] == 0) {
        // 缓存为空，从磁盘加载一批
        bp = bread(dev, 1);  // 读超级块
        // 从磁盘的 inode 空闲链加载 100 个
        // ...
    }
    
    // 2. 从缓存中取一个
    ino = s->s_inode[--s->s_ninode];
    s->s_fmod = 1;  // 标记超级块脏
    
    // 3. 读取磁盘 inode，清零
    block = 2 + (ino-1)/16;
    bp = bread(dev, block);
    ip = bp->b_addr + ((ino-1)%16)*32;
    // 清零 32 字节
    for (i = 0; i < 16; i++) ip->i_daddr[i] = 0;
    bdwrite(bp);  // 延迟写
    
    // 4. 返回 i-number
    return(ino);
}
```

**ialloc() 的关键设计**：

- **批量缓存**：超级块缓存 100 个空闲 inode 号，避免每次分配都读盘
    
- **成组链接**：磁盘上的空闲 inode 用"成组链接"方式组织——每个块存 100 个 inode 号，最后一个指向下一个空闲块
    
- **延迟写**：清零后的 inode 用 bdwrite() 延迟写回
    

### ifree()

`ifree(dev, ino)` 释放一个 inode ：

```
ifree(dev, ino) {
    // 1. 如果超级块缓存未满，直接加入缓存
    if (s->s_ninode < 100) {
        s->s_inode[s->s_ninode++] = ino;
        s->s_fmod = 1;
        return;
    }
    
    // 缓存已满，写回磁盘
    bp = bread(dev, 1);  // 读超级块
    // 将缓存的 100 个 inode 号写入新的空闲块
    // ...
}
```

### alloc()

`alloc(dev)` 分配一个数据块 ：

```
alloc(dev) {
    // 1. 检查超级块缓存
    if (s->s_nfree <= 0) {
        panic("alloc: no blocks");  // 磁盘满
    }
    
    // 2. 从缓存取一个空闲块号
    bno = s->s_free[--s->s_nfree];
    
    // 3. 如果缓存空了，从磁盘加载下一组
    if (s->s_nfree <= 0) {
        bp = bread(dev, bno);  // 读取空闲块链块
        s->s_nfree = bp->b_addr[0];  // 该块的第一个字是下一组的数量
        // 复制接下来的 100 个字到 s_free
        for (i = 0; i < 100; i++)
            s->s_free[i] = bp->b_addr[i+1];
        brelse(bp);
    }
    
    // 4. 返回块号
    return(bno);
}
```

**alloc() 的"成组链接"算法**：

V6 的空闲块管理采用**成组链接法**​ ：

```
超级块缓存：s_free[0..99]，s_nfree 个有效

磁盘上的空闲块链：
  Block A: [next_group_block, free1, free2, ..., free99]
  Block B: [next_group_block, free100, ..., free199]
  ...
```

- 每个"空闲块链块"的第一个字存储下一组的块号
    
- 接下来的 100 个字存储实际的空闲块号
    
- 超级块缓存 100 个空闲块号，用尽时从磁盘加载下一组
    

> 💡 **洞见**：成组链接法是 V6 文件系统的**天才设计**——它把"空闲块管理"和"空闲块本身"统一起来。空闲块链块本身就是空闲块，但它的内容是"更多空闲块的指针"。这种"自引用"的设计，让文件系统在**不占用额外元数据空间**的情况下，管理任意数量的空闲块。今天你在 Linux 的 ext2/ext3 中看到的"块位图（block bitmap）"，就是成组链接法的演化——从"链式"到"位图"，本质相同：**用最紧凑的方式记录空闲资源**。

### free()

`free(dev, bno)` 释放一个数据块 ：

```
free(dev, bno) {
    // 1. 如果超级块缓存未满，直接加入
    if (s->s_nfree < 100) {
        s->s_free[s->s_nfree++] = bno;
        s->s_fmod = 1;
        return;
    }
    
    // 2. 缓存已满，将 bno 作为新的链块头
    bp = getblk(dev, bno);
    bp->b_addr[0] = s->s_nfree;  // 当前缓存数量
    // 将超级块缓存的 100 个块号复制到新块
    for (i = 0; i < 100; i++)
        bp->b_addr[i+1] = s->s_free[i];
    bwrite(bp);  // 同步写
    
    // 3. 重置超级块缓存
    s->s_nfree = 0;
    s->s_fmod = 1;
}
```

### getfs()

`getfs(dev)` 获取指定设备的超级块：

```
getfs(dev) {
    // 从 mount 数组中找到对应设备的 mount 结构体
    // 返回 m_bufp->b_addr（超级块的内存映像）
}
```

### badblock()

`badblock(bp, dev, bno)` 处理坏块：

```
badblock(bp, dev, bno) {
    // 打印诊断信息到控制台
    printf("bad block %d on dev %d\n", bno, dev);
    // 清空空闲列表，防止从损坏的空闲列表中分配
    s->s_nfree = 0;
    // 触发 panic 或标记文件系统为只读
}
```

> ⚠️ **洞见**：badblock() 的处理策略反映了 V6 对"数据完整性"的朴素态度——**发现坏块就清空空闲列表，宁可停止分配也不使用可能损坏的块**。这是"fail-stop"原则的早期实践。现代文件系统的理念类似但更复杂：ext4 有"坏块 inode"专门记录坏块；ZFS 和 Btrfs 使用校验和 + 数据冗余来自动检测和修复损坏。

## 9.7 将路径变为 inode

这是文件系统对用户最直接的接口——`namei()` 函数。

### 目录的内容

目录文件的内容是**目录项序列**，每个目录项 16 字节 ：

```
struct direct {
    char d_name[14];    // 文件名
    int16_t d_ino;      // i-number
};
```

目录项的特点：

- **固定 16 字节**：14 + 2，不跨块边界
    
- **文件名最长 14 字节**：超过则截断
    
- **i-number 为 0 表示空目录项**：可复用
    
- **`.`（i-number 指向自身）和 `..`（i-number 指向父目录）**：每个目录必须包含这两个特殊项
    

### namei()

`namei()` 是文件系统的"路径解析器"——把 `/usr/ken/hello.c` 这样的路径名转换为对应的内存 inode 指针 。

```
namei() {
    // 1. 确定起始目录
    if (path[0] == '/') {
        // 绝对路径：从根目录开始
        ip = rootdir;
    } else {
        // 相对路径：从当前目录开始
        ip = u.u_cdir;
    }
    iget(ip->i_dev, ip->i_number);  // 确保 ip 在内存中
    
    // 2. 逐段解析路径
    while (1) {
        // 跳过 '/'
        while (*path == '/') path++;
        if (*path == '\0') break;  // 路径结束
        
        // 提取当前段名
        for (i = 0; i < 14 && *path != '/'; i++)
            name[i] = *path++;
        name[i] = '\0';
        
        // 3. 在当前目录中查找该名字
        // 遍历目录的数据块
        for (bn = 0; bn < (ip->i_size>>9); bn++) {
            bp = bread(ip->i_dev, bmap(ip, bn));
            // 在每个目录项中查找
            for (i = 0; i < 512/16; i++) {
                dp = bp->b_addr + i*16;
                if (dp->d_ino == 0) continue;  // 空项
                if (match(dp->d_name, name)) {
                    // 找到！获取下一级 inode
                    next_ino = dp->d_ino;
                    brelse(bp);
                    
                    // 4. 处理挂载点
                    iput(ip);  // 释放当前目录 inode
                    ip = iget(ip->i_dev, next_ino);
                    
                    // 检查 IMOUNT 标志
                    if (ip->i_flag & IMOUNT) {
                        // 跳转到被挂载文件系统的根
                        iput(ip);
                        ip = iget(ip->i_mounted_dev, 1);
                    }
                    
                    goto next_segment;
                }
            }
            brelse(bp);
        }
        
        // 未找到
        u.u_error = ENOENT;
        return(NULL);
        
    next_segment:
        // 继续下一段
    }
    
    return(ip);
}
```

**namei() 的关键设计**：

1. **绝对路径 vs 相对路径**：根据路径首字符决定起始目录
    
2. **逐段解析**：每次处理一个路径段（如 `usr`、`ken`、`hello.c`）
    
3. **目录项搜索**：遍历目录文件的数据块，逐个比较目录项的 d_name
    
4. **挂载点跳转**：遇到 IMOUNT 标志的 inode，跳转到被挂载设备的根
    
5. **符号链接处理**：V6 不直接支持符号链接（V7 才引入），但 namei 的逻辑为后续扩展预留了空间
    

> ⚠️ **洞见**：namei() 是文件系统**"路径→inode"转换的核心算法**。它的每一次迭代都是一次 `iget()` + `bmap()` + `bread()` 的组合。这个过程揭示了文件系统的性能特征：
> 
> - 路径越深，需要遍历的目录越多
>     
> - 每次目录查找都可能触发磁盘 I/O
>     
> - 这就是为什么深层目录结构会导致性能下降
>     
> 
> **现代文件系统的优化方向**（ext4 的 extent、XFS 的 B+ 树、Btrfs 的 extent tree），本质上都是在优化 namei() 的核心循环——减少目录查找的 I/O 次数。

### access()

`access(ip, mode)` 检查访问权限 ：

```
access(ip, mode) {
    // 1. 超级用户拥有所有权限
    if (u.u_uid == 0) return(1);
    
    // 2. 所有者权限
    if (u.u_uid == ip->i_uid) {
        if (mode & (ip->i_mode >> 6)) return(1);
    }
    
    // 3. 组权限
    if (u.u_gid == ip->i_gid) {
        if (mode & (ip->i_mode >> 3)) return(1);
    }
    
    // 4. 其他人权限
    if (mode & ip->i_mode) return(1);
    
    return(0);  // 权限不足
}
```

**access() 的权限检查顺序**：超级用户 → 所有者 → 组 → 其他。这是 UNIX 权限模型的经典实现。

## 9.8 初始化与同步

### iinit()

`iinit()` 在系统启动时调用，初始化根文件系统 ：

```
iinit() {
    // 1. 挂载根设备
    mountroot();
    
    // 2. 读取根 inode（i-number 1）
    rootdir = iget(rootdev, 1);
    
    // 3. 设置当前目录为根
    u.u_cdir = rootdir;
    rootdir->i_count++;  // 增加引用计数
}
```

### update()

`update()` 是文件系统的"同步守护进程"——定期将脏数据写回磁盘：

```
update() {
    while (1) {
        // 1. 睡眠约 30 秒
        sleep(&lbolt, 0);  // 每秒被 clock() 唤醒一次
        if (lbolt % 30 != 0) continue;  // 每 30 秒执行一次
        
        // 2. 遍历所有挂载的文件系统
        for (mp = mount; mp < &mount[NMNT]; mp++) {
            if (mp->m_bufp == NULL) continue;
            
            // 3. 同步超级块
            if (mp->m_bufp->b_flags & B_DIRTY) {
                bwrite(mp->m_bufp);  // 写回超级块
            }
            
            // 4. 同步所有脏 inode
            for (ip = inode; ip < &inode[NINODE]; ip++) {
                if (ip->i_count && (ip->i_flag & IUPD)) {
                    iupdat(ip, ...);
                }
            }
            
            // 5. 刷新所有延迟写缓冲区
            bflush(mp->m_dev);
        }
    }
}
```

**update() 的关键作用**：

- **定期刷盘**：每 30 秒将脏超级块、脏 inode、延迟写缓冲区写回磁盘
    
- **崩溃恢复**：如果系统崩溃，最多丢失 30 秒的数据
    
- **fmod 标志**：超级块的 fmod 标志记录是否被修改，update 只写回被修改的超级块
    

> 💡 **洞见**：update 是 V6 的"后台写回"机制，与第7章讲的延迟写（bdwrite）完美配合：
> 
> - bdwrite 标记缓冲区为 B_DELWRI，不立即写盘
>     
> - update 每 30 秒触发 bflush，将所有 B_DELWRI 缓冲区写回
>     
> - 这种"延迟写 + 定期刷盘"的策略，是现代文件系统 writeback 机制的鼻祖
>     
> 
> **工业联系**：
> 
> - Linux 的 `pdflush` / `writeback` 线程：定期将脏页写回磁盘
>     
> - Linux 的 `sync` 命令：强制立即刷盘（对应 V6 的 update 立即执行）
>     
> - 数据库的 WAL（Write-Ahead Log）+ Checkpoint：类似的"延迟写 + 定期持久化"策略
>     
> - 现代文件系统的 journal 提交：ext4 的 `commit=30` 参数与 V6 的 30 秒间隔惊人地一致
>

## 9.9 小结

第9章完成了 V6 文件系统的完整剖析。把所有机制串起来看：

```
路径名 "/usr/ken/hello.c"
    ↓
namei() 逐段解析
    ↓
    ├─ 每段：在目录文件中搜索目录项
    │   └─ bread() + bmap() 读取目录数据块
    ├─ 找到匹配项 → iget() 获取下一级 inode
    └─ 遇到 IMOUNT → 跳转到被挂载文件系统
    ↓
目标文件的 inode（内存映像）
    ↓
文件操作（read/write）
    ↓
bmap() 逻辑块号 → 物理块号
    ↓
bread()/bwrite() 缓冲区 I/O
    ↓
rkstrategy() 块设备驱动
    ↓
RK11-D 磁盘控制器
```

**第一性原理总结**：

1. **"文件名 - inode - 数据块"三级分离**：文件名与内容解耦，inode 统一抽象所有文件类型，数据块纯粹存储二进制内容。这是 UNIX "一切皆文件"的哲学基础 。
    
2. **inode 是文件的"身份证"**：32 字节定长结构，存储元数据 + 8 个块地址。i-number 从 1 开始，i-number 1 永远是根目录 。
    
3. **iget/iput 实现 inode 生命周期管理**：内存缓存 + 引用计数 + 锁的三位一体。这是现代对象池、智能指针、**RAII 资源管理、gc 垃圾回收的鼻祖**。V6 用 C 语言手动实现了"引用计数 + 延迟释放"的自动资源管理范式——这比 C++ 的智能指针早了整整 20 年，比 Java 的垃圾回收早了 25 年。今天你在任何现代语言中看到的"引用计数"（Swift 的 ARC、Python 的 refcount、Rust 的 Rc/Arc），其思想血脉都可以追溯到 V6 的 iget/iput 。

### 4. **bmap 是"一切皆文件"的技术基石**

bmap() 将文件的逻辑块号统一转换为物理块号，无论是普通文件、目录、设备文件还是管道，都通过 bmap 统一寻址 。特别是**设备文件**——它的 i_addr 存储的不是数据块号，而是设备号，所以 bmap 对设备文件"短路"，直接返回设备号。这种**统一抽象 + 特例短路**的设计，是现代面向对象"多态"思想的 C 语言前身。V6 的小文件用 8 个直接指针，大文件通过 i_addr[0..6] 做一级间接、i_addr[7] 做二级间接，文件最大可达约 16MB 。

### 5. **成组链接法是空闲资源管理的天才设计**

V6 用"成组链接"管理空闲块——超级块缓存 100 个空闲块号，磁盘上的空闲块链块第一个字存储下一组的块号，接下来的 100 个字存储实际的空闲块号 。这种"自引用"的设计让文件系统在**不占用额外元数据空间**的情况下，管理任意数量的空闲块。今天 Linux ext2/ext3 的块位图（block bitmap）、现代存储系统的空闲空间管理，都是成组链接法的演化。

### 6. **namei 是路径解析的核心算法**

namei() 把 `/usr/ken/hello.c` 这样的路径名逐段解析为 inode 指针，每次迭代都是一次 iget() + bmap() + bread() 的组合，遇到 IMOUNT 标志的 inode 就跳转到被挂载文件系统 。这个过程揭示了文件系统的性能特征——路径越深，需要遍历的目录越多，每次目录查找都可能触发磁盘 I/O。现代文件系统的 extent、B+ 树、Btrfs 的 extent tree 等优化，本质上都是在优化 namei() 的核心循环。

### 7. **延迟写 + 定期刷盘是 crash consistency 的朴素方案**

update() 每 30 秒将脏超级块、脏 inode、延迟写缓冲区写回磁盘 。如果系统崩溃，最多丢失 30 秒的数据。fmod 标志位在崩溃后指导 fsck 工具判断文件系统一致性 。这是现代文件系统 writeback 机制的鼻祖——Linux 的 `pdflush`、`sync` 命令、`commit=30` 参数，与 V6 的 update 机制惊人地一致。

## 跨章节联系

第9章文件系统把前面所有章节的设施**汇聚到同一个目标**——让用户用路径名访问数据：

- **第2章的 proc/user 结构体**：`u.u_cdir` 保存当前工作目录的 inode 指针；`u.u_error` 记录文件操作错误
    
- **第3章的 fork/exec**：fork 复制文件描述符表（每个 fd 指向一个 file 结构体，file 结构体指向 inode）；exec 继承文件描述符
    
- **第5章的中断与陷入**：文件 I/O 最终触发第8章的块设备中断，`iodone()` 唤醒等待进程
    
- **第6章的信号**：`core()` 函数用文件系统接口创建 core 文件
    
- **第7章的块设备子系统**：bread/bwrite 是文件系统读写磁盘块的**唯一接口**
    
- **第8章的块设备驱动**：文件系统通过 `bdevsw[major].d_strategy` 调用驱动，完全不感知底层硬件
    

**关键认知**：文件系统是 V6 的"集大成者"——它站在第7章缓冲区缓存的肩上，通过第8章的驱动访问磁盘，用第2章的 user 结构体保存进程的文件状态，被第3章的进程管理机制调度，由第5章的中断机制驱动 I/O 完成。理解文件系统，就是理解 V6 所有子系统如何**协同工作**。

## 工业落地的七点启示

### 1. **"文件名 - inode - 数据块"三级分离是文件系统的第一性原理**

V6 把文件名（目录项）、文件元数据（inode）、文件内容（数据块）三者彻底解耦。这种分离带来了：

- **硬链接**：多个文件名指向同一个 inode（i_nlink 计数）
    
- **软链接**（V7 引入）：文件名指向另一个文件名
    
- **挂载**：一个文件系统的根嫁接为另一个文件系统的目录
    
- **设备文件**：inode 不指向数据块而指向设备号
    
- **管道**：inode 指向内存缓冲区而非磁盘块
    

今天任何现代文件系统（ext4、XFS、Btrfs、ZFS、APFS）都遵循这一分离模型。**第一性原理：文件名是"人类接口"，inode 是"系统接口"，数据块是"存储接口"——三者解耦才能最大化灵活性**。

### 2. **引用计数是自动资源管理的鼻祖**

iget/iput 的 `i_count` 引用计数机制，是今天所有自动资源管理方案的祖先：

- **C++ 智能指针**：`shared_ptr` 的引用计数与 `i_count` 机制完全一致
    
- **Swift/Objective-C ARC**：自动引用计数
    
- **Python 对象模型**：每个对象的 `ob_refcnt`
    
- **Rust Rc/Arc**：编译期保证的引用计数
    
- **Linux 内核**：`kref`、`fget/fput`、`iget/iput` 本身就是这一思想的现代延续
    

V6 告诉我们：**资源的生命周期管理，本质是引用计数的增减**。理解 V6 的 iget/iput，你就理解了现代所有资源管理方案的设计哲学。

### 3. **"获取"与"加锁"分离避免死锁**

xv6 的演化清晰地展示了这一点——iget() 返回未锁定的 inode，ilock() 才真正加锁 。这种分离：

- 允许多个进程持有同一个 inode 的指针（通过 iget 增加 ref）
    
- 但只有一个进程能锁定 inode（通过 ilock）
    
- 避免了路径解析过程中的死锁（如 `/a/b/c` 需要同时锁定 a、b、c 三个 inode）
    

**这是现代并发编程的核心范式**——"引用获取"与"互斥访问"分离。今天的 `std::shared_ptr` + `std::mutex`、Java 的 `Reference` + `synchronized`、Go 的 `sync.Once`，都是同一思想。

### 4. **延迟写是文件系统性能的杠杆**

V6 的 bdwrite（延迟写）+ update（定期刷盘，30 秒间隔）机制 ，是今天所有文件系统 writeback 的鼻祖：

- **Linux ext4**：`commit=30` 参数（默认 30 秒刷盘）
    
- **Linux 的 pdflush/writeback 线程**：定期将脏页写回
    
- **数据库的 WAL + Checkpoint**：预写日志 + 定期检查点
    
- **ZFS/Btrfs 的 COW**：写时复制 + 事务提交
    

**第一性原理：用"延迟写 + 定期刷盘"在性能和持久性之间取得平衡**。V6 在 1975 年就找到了这个平衡点，30 秒的默认值惊人地合理——今天 Linux 的 `dirty_expire_centisecs=3000`（30 秒）与 V6 完全一致。

### 5. **成组链接法是"自描述元数据"的早期实践**

V6 的空闲块成组链接 ，让空闲块本身承载空闲块链信息，不占用额外的元数据空间。这种"自描述"思想在今天演化为：

- **ext2/ext3 的块位图**：用位图紧凑记录空闲块
    
- **XFS 的 B+ 树**：用树结构管理空闲空间
    
- **Btrfs 的 extent tree**：用 extent 管理连续空闲空间
    
- **ZFS 的 metaslab**：用空间映射管理存储池
    

**核心思想：元数据应该"自描述"且"紧凑"**。V6 的成组链接法在 512 字节块的限制下做到了极致——100 个空闲块号 + 1 个链指针 = 101 个 16 位字 = 101 * 2 = 202 字节，小于 512 字节块，完美适配。

### 6. **namei 的路径解析是"解释器"的雏形**

namei() 把路径名当作一种"微型语言"来解释执行——逐字符解析，遇到 `/` 分段，每段在目录中查找，遇到挂载点跳转 。这种"解释器模式"在今天演化为：

- **Shell 的路径解析**：`/usr/bin/gcc` 的查找过程
    
- **动态链接器的库搜索**：`LD_LIBRARY_PATH` 中的路径遍历
    
- **Web 服务器的 URL 路由**：`/api/v1/users` 的路由匹配
    
- **Kubernetes 的资源路径**：`/api/v1/namespaces/default/pods`
    

**第一性原理：任何层级命名空间都需要"路径→资源"的解析器**。V6 的 namei 是这一模式的鼻祖。

### 7. **超级块的 fmod 标志是"脏数据追踪"的鼻祖**

V6 超级块的 `fmod` 标志记录文件系统是否被修改 ，update 只写回被修改的超级块。这种"脏标志 + 定期刷盘"的模式，今天演化为：

- **Linux 的 `dirty` 标志**：页缓存脏页标记
    
- **数据库的 `dirty page`**：缓冲池脏页管理
    
- **SSD 的 FTL 脏块管理**：闪存转换层的脏块追踪
    
- **分布式系统的 `dirty flag`**：副本一致性协议中的脏数据标记
    

**核心思想：用脏标志避免无意义的写操作**。V6 在 1975 年就实践了这一优化。

## 英文补充资料与跨时代对照

### 1. V6 文件系统手册（fs(5)）—— 一手资料

TUHS 保存的 V6 `fs.5` 手册页明确规定了文件系统的磁盘布局 ：

- Block 0：引导块
    
- Block 1：超级块，结构体 `filsys` 包含 `s_isize`、`s_fsize`、`s_nfree`、`s_free[100]`、`s_ninode`、`s_inode[100]`、`s_flock`、`s_ilock`、`s_fmod`、`s_time`
    
- Block 2 起：inode 区，i-number 从 1 开始，inode 32 字节，16 个/块
    
- 成组链接法管理空闲块："_The free list for each volume is maintained as follows... The first word in each free-chain block is the number of free-block numbers listed in the next 100 words_"
    

### 2. Lions 注释本第 19 章

John Lions 对 iget (7285)、namei (7531)、bmap (6415)、ialloc、alloc、free、ifree 等函数有逐行注释。特别是 iget 中 7292-7297 行处理挂载文件系统的逻辑，以及 7316 行对多处理器锁的局限性讨论（"does this lock work on multiprocessors? Answer: no"） 。

### 3. Stanford CS347 讲义

讲义清晰总结了 V6 文件系统的关键设计 ：

- "_disk inodes are 32 bytes big, and 1 block = 1 sector = 512 bytes, so 16 inodes/block_"
    
- "_Small files have 8 direct pointers; in large files the eight pointers are pointers to a block of pointers_"
    
- "_Files are limited to 2^15 blocks_"
    
- 指出了 V6 的性能策略："_It overlaps computation and I/O, but doesn't do any disk scheduling. It cheats on semantics_"
    

### 4. xv6 源码与文档（现代演化对照）

xv6 几乎逐行复刻了 V6 的文件系统，但针对多处理器做了改进 ：

- **iget/iput**：与 V6 语义一致，但增加了 icache.lock 自旋锁
    
- **ilock/iunlock**：xv6 把 iget 与 ilock 分离，避免多处理器死锁
    
- **ialloc/balloc**：用位图替代成组链接法（因为 xv6 运行在简单的 ide 磁盘上）
    
- **bmap**：支持直接块、一级间接、二级间接
    

xv6 的 `fs.c` 是理解 V6 文件系统思想在现代演化的**最佳对照材料**​ 。

### 5. 现代对照表

|V6 概念|现代 Linux 对应|演化|
|---|---|---|
|iget/iput + i_count|`iget_locked`/`iput` + `i_count`|增加了 `i_lock` 自旋锁|
|ilock/iunlock|`inode_lock`/`inode_unlock`|读写锁替代睡眠锁|
|成组链接法|块位图（block bitmap）|从链式到位图|
|bmap 8 直接 + 间接|extent 树|从块指针到 extent|
|超级块 filsys|`struct ext4_super_block`|字段极大扩展|
|s_free[100] 缓存|内存中的块分配器|slab 分配器|
|update 30 秒刷盘|`pdflush` + `dirty_expire_centisecs=3000`|机制一致，参数可调|
|fmod 脏标志|`sb->s_dirt`|脏标志机制一致|
|namei 路径解析|`path_lookup()`|增加了 RCU、LOOKUP 标志|
|挂载 IMOUNT 标志|`MNT_` 挂载标志|挂载选项极大丰富|
|14 字节文件名|255 字节文件名（ext4）|文件名长度扩展|
|512 字节块|4KB 块（可配置）|块大小增大 8 倍|
|最大文件 16MB|最大文件 16TB（ext4）|容量指数级增长|

> 💡 **跨时代洞见**：从 V6 到现代 Linux 文件系统，**第一性原理完全一致**：
> 
> - **"文件名 - inode - 数据块"三级分离**
>     
> - **引用计数管理 inode 生命周期**
>     
> - **延迟写 + 定期刷盘平衡性能与持久性**
>     
> - **路径解析的逐段查找**
>     
> - **挂载实现命名空间拼接**
>     
> 
> 变的是**规模**（块大小、文件名长度、最大文件容量）、**并行度**（单核到多核）、**数据结构**（成组链接到位图、从块指针到 extent）。但骨架——iget/iput/bmap/namei/alloc/free——**50 年没变**。理解 V6 的文件系统，你就拿到了理解现代文件系统的"源代码"。

    ```
    进程 A: fopen("/file") → iget(inode_X) → i_count=1
    进程 B: fopen("/file") → iget(inode_X) → i_count=2
    进程 A: fclose → iput → i_count=1
    进程 B: unlink("/file") → i_nlink=0
    进程 B: fclose → iput → i_count=0 & i_nlink=0 → itrunc + ifree
    ```
    
    理解这个状态机，你就理解了引用计数的精髓。

    - iget 如何与 ilock 分离（避免多处理器死锁）
        
    - icache.lock 自旋锁如何保护 inode 缓存
        
    - 位图替代成组链接法的实现

    这个练习会让你深刻理解——**V6 的文件系统在今天的约束下该如何演化**。
