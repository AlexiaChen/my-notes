
# 《Unix内核源码剖析》读书笔记 · 第5章 中断与陷入

> 前四章我们把"进程"这个实体建起来了：它怎么生（fork）、怎么切换（swtch）、怎么换入换出（sched/xswap）、怎么死（exit/wait）。但有一个根本问题没回答——**谁在驱动这一切？**
> 
> 答案是：**中断与陷入**。它们是"用户态/外部世界"与"内核"之间的**唯一入口**。正如 V6 文档所述，陷入和硬件中断造成了 CPU 正常指令执行序列的突然切换，提供了一种处理在 CPU 控制外产生的特殊条件的机制；而这种设施也用作"系统调用"机制的一部分——用户程序执行一条 trap 指令以故意造成一次陷入，从而取得操作系统的注意和帮助。
> 
> **第一性洞见**：中断与陷入的本质，是**硬件提供给软件的"控制权转让"原语**。CPU 正常运行时完全按计划执行指令流；但当"外部事件"（中断）或"异常条件"（陷入）发生时，硬件强行打断当前流，把控制权交给内核预设的处理入口。这是计算机系统中"异步性"与"同步性"的统一入口——**所有"非顺序发生"的事情，都从这里进来**。理解这一章，你就拿到了理解"内核如何响应世界"的钥匙。

---

## 5.1 什么是中断与陷入

### 什么是中断

**中断（Interrupt）**​ 是 CPU 外部硬件设备发起的控制权转让请求。

PDP-11 上的关键硬件事实 ：

- CPU 的 PSW（程序状态字）中有 3 位记录当前处理器优先级（IPL，Interrupt Priority Level），值为 0-7
    
- 外部设备通过 UNIBUS 的 4 条中断请求线 **BR4、BR5、BR6、BR7**​ 发起中断，数字越大优先级越高
    
- 当设备的中断优先级 **高于**​ CPU 当前的 IPL 时，CPU 才会响应
    
- 把 IPL 设为 7，就可以屏蔽所有硬件中断——V6 内核代码中有大量这样的临界区保护
    

> 💡 **洞见**：中断优先级的本质，是**紧急程度的硬件表达**。磁盘中断优先级高（BR5），因为如果不及时把数据从磁盘缓冲区读走，扇区可能旋转过去导致重读；打印机中断优先级低（BR4），因为打印机可以无限期等待。PDP-11 用"数字大小"表达了"数据丢失的紧迫性"——这是一个用硬件位数编码"时间敏感性"的绝佳设计。

不同中断源的优先级（PDP-11/40）：

|中断源|优先级|向量地址（八进制）|
|---|---|---|
|线性时钟|6|100|
|实时时钟|6|104|
|磁盘|5|220|
|KL-11/DL-11（串口/TTY）|4|60|
|供电异常|陷入|240（向量地址）|

### 什么是陷入

**陷入（Trap）**​ 是 CPU **内部**产生的"异常事件"，**无优先级，必须立刻处理**。

PDP-11 上的陷入源 ：

- **总线错误**（Bus Error）：访问不存在的内存
    
- **非法指令**：执行未定义的指令
    
- **段违例**（Segmentation Violation）：违反内存管理规则
    
- **断点/跟踪陷阱**：调试用
    
- **IOT 陷阱**：I/O 陷入
    
- **浮点异常**：浮点运算出错
    
- **系统调用**：用户执行 `trap` 指令故意触发
    

> ⚠️ **关键认知**：陷入和中断的本质区别——正如相关资料指出的：**"陷入可以认为是'第8级中断'"**，因为 PSW 寄存器中的中断屏蔽位并不能屏蔽陷入的产生，哪怕它的值是 7。这意味着**陷入比任何硬件中断都紧急**——即使内核关了所有中断，用户程序执行 trap 指令仍然能切入内核。这是系统调用能够工作的硬件基础。

**工业联系**：现代 x86 的 IDT（中断描述符表）中，中断和异常的向量号也是分开的——0-31 留给异常（陷入），32-255 留给外部中断。Intel SDM 明确指出：**异常（Exception）是 CPU 同步执行的、与指令执行直接相关的中断**；而**中断（Interrupt）是 CPU 异步执行的、与外部硬件相关的中断**。这个区分从 PDP-11 一直精确到今天的 x86-64。**50 年过去了，中断与陷入的二元划分依然是计算机体系结构的基石**。

## 5.2 优先级与向量（Vector）

### 中断优先级和处理器优先级

PDP-11 用 PSW 的 bit 7-5 记录当前处理器优先级（共 8 级 0-7）：

- **IPL 0**：最低优先级，所有中断都可响应
    
- **IPL 7**：最高优先级，屏蔽所有硬件中断（但陷入仍可触发）
    

**中断处理中的优先级提升**：当 CPU 进入一个优先级为 N 的中断处理程序时，硬件会自动把 IPL 设为 N。这样做的效果是——同级或更低级的中断被屏蔽，但更高级的中断仍能抢占。这保证了**高优先级中断可以嵌套低优先级中断**，形成中断嵌套链 。

> 💡 **洞见**：这种"优先级即屏蔽"的设计，是**无锁临界区的最原始形态**。在内核中，当你需要保护一段数据结构不被并发修改时，最简单的办法不是加锁，而是把 IPL 提升到足够高——这样任何可能修改该数据的中断都被屏蔽。V6 内核中大量使用这种技术。这是"关中断"保护的源头，也是今天 Spin Lock 的"禁用本地中断"变体的祖先。

### 中断和陷入向量

**向量表（Vector Table）**​ 是 PDP-11 的中断/陷入分发机制：

- 向量表固定在内存地址 **0**​ 开始的位置
    
- 每个向量占 **两个字（4 字节）**：第一个字是新的 PC（处理程序入口），第二个字是新的 PSW（含优先级）
    
- 当中断/陷入发生时，硬件自动：
    
    1. 把当前 PSW 和 PC 压入**当前栈**（用户态陷入压用户栈，内核态中断压内核栈）
        
    2. 从中断向量表中取出对应的新 PC 和新 PSW
        
    3. 装入新 PC 和新 PSW，跳转到处理程序
        
    

**向量号计算**：向量号 × 4 = 向量在内存中的地址。例如：

- 总线错误：向量号 1 → 地址 4
    
- 系统调用（trap）：向量号 7 → 地址 28（八进制 34）
    
- 断点：向量号 3 → 地址 12（八进制 14）
    

V6 在 `l.s` 中定义了完整的向量表，把每个向量指向对应的汇编处理程序（如 `trap`、`call` 等）。

> 📌 **深度理解**：向量表是**硬件与内核之间的契约**——硬件只知道"出问题了，去地址 X 取处理程序入口"；内核负责在地址 X 处放置正确的跳转指令。这种"硬件查表 + 软件跳板"的两级分发，是现代 IDT、ARM 的异常向量表、RISC-V 的 mtvec 的共同祖先。**向量表的存在，让"无限种类的异常"能够被"统一机制"处理**。

## 5.3 中断和陷入的处理流程

### 发生中断或陷入

无论是中断还是陷入，PDP-11 硬件都执行相同的序列 ：

1. **比较优先级**（仅中断）：如果中断优先级 ≤ 当前 IPL，忽略；陷入无条件执行
    
2. **保存现场**：把当前 PSW 和 PC 压入**当前栈**（用户态陷入压用户栈，内核态中断压内核栈）
    
3. **查向量表**：根据向量号从地址 0 开始的向量表中取出新 PC 和新 PSW
    
4. **装载新值**：新 PSW → PSW 寄存器，新 PC → PC 寄存器
    
5. **跳转执行**：CPU 从新 PC 开始执行——通常是 V6 的汇编跳板程序 `trap` 或 `call`
    

**用户栈 vs 内核栈的关键区分**：

|场景|栈选择|原因|
|---|---|---|
|用户程序执行 trap 指令|压入**用户栈**​|陷入前是用户态|
|用户程序执行时发生硬件中断|压入**用户栈**​|中断前是用户态|
|内核执行时发生硬件中断|压入**内核栈**​|中断前是内核态|

这意味着——**同一个中断/陷入处理程序，在不同上下文中被调用时，栈的位置完全不同**。这是 V6 中很多"魔法"的根源，也是 Lions 注释本里反复强调的难点。

### 执行 call 和 trap

V6 在汇编层（`l.s`）准备了两个关键跳板：

- **`trap`**（地址 0755 附近）：陷入处理跳板。所有陷入（包括系统调用）都先跳到这里
    
- **`call`**（地址 0776 附近）：中断处理跳板。所有硬件中断都先跳到这里
    

这两个跳板的职责 ：

1. **建立 C 函数调用环境**：PDP-11 的硬件在进入中断/陷入时，只保存了 PSW 和 PC，但没有建立 C 函数预期的栈帧。跳板程序负责"搭台子"——设置 R5（帧指针）、保存寄存器、构造参数
    
2. **调用 C 函数**：`trap` 跳板最终调用 C 函数 `trap()`；`call` 跳板调用具体的中断处理程序（如 `clock()`）
    
3. **返回准备**：C 函数返回后，跳板清理栈，用 `rtt` 指令恢复原来的 PSW 和 PC
    

**`trap` 指令的细节**（系统调用的入口）：

- PDP-11 的 `trap` 指令的 icode 范围是 **0104400 到 0104777**（八进制）
    
- 后 8 位是系统调用号。例如 `trap 013` 表示第 11 号系统调用 `exec`
    
- 指令执行时，CPU 切换到内核态（PS ← 020），PC 跳转到向量 34（系统调用陷入入口）
    

> ⚠️ **难点揭示**：V6 源码里有**三个同名 `trap`**，初学者最容易混淆 ：
> 
> 1. **汇编指令 `trap`**：用户程序执行的机器指令
>     
> 2. **汇编代码 `trap`**：0755 行的跳板程序，给 C 函数 `trap()` 搭建环境
>     
> 3. **C 函数 `trap`**：trap.c 中 2693 行的主体处理函数
>     
> 
> 记住这个区分，是你读懂第5章的关键。

**工业联系**：现代 x86 的 `syscall`/`sysenter` 指令，本质上就是 PDP-11 `trap` 指令的演化版本——用一条指令完成"切到内核态 + 跳转到预设入口"。但现代 CPU 用 MSR 寄存器存入口地址（x86 的 IA32_LSTAR），而不是像 PDP-11 那样固定从地址 34 取向量。这是"固定向量表"到"可配置入口"的演进，但**第一性原理没变：用一条指令让 CPU 从用户态安全地进入内核态**。

## 5.4 时钟中断处理函数

### 时钟设备的规格

PDP-11 的时钟硬件（如 KC-11 线性时钟）：

- 以**线路频率**产生中断——50Hz 电源对应每 20ms 一次，60Hz 电源对应每 16.67ms 一次
    
- V6 源码中 `#define HZ 60`——即每秒 60 次时钟中断
    
- 时钟中断优先级为 **6**（BR6）
    

### 时钟中断处理函数的内容

时钟中断是 V6 的"心跳"——它是**驱动调度器和交换处理的节拍器**。正如 Stack Overflow 上对 V6 源码的讨论所指出的：**"基本的同步是在 runin 标志上进行的，该标志是休眠的，由时钟例程每秒设置一次。因此，核心洗牌每秒钟进行一次。"**​ 这意味着 sched 的换入换出决策，是以**每秒 1 次的频率**触发的，而时钟中断本身是每秒 60 次。

### clock()

`clock()` 是时钟中断的 C 处理函数（slp.c 中），其核心职责：

1. **时间统计**：
    
    - 递增 `lbolt`（系统心跳计数）
        
    - 递增当前进程的 `p_time`（进程已运行时间）
        
    - 递增 `u.u_utime`（用户态 CPU 时间）
        
    
2. **调度决策**：
    
    - 递减 `curproc->p_pri`（动态调整优先级）
        
    - 每隔 1 秒（HZ 次中断），设置 `runrun` 标志，触发调度器考虑切换进程
        
    - 更新所有 RUN 状态进程的 `p_cpu`，重算 `p_pri`
        
    
3. **交换触发**：
    
    - 每隔 1 秒检查 `runin` 和 `runout` 条件
        
    - 如果满足交换条件，唤醒进程 0（sched）
        
    
4. **偶发事务**：
    
    - 处理 `time` 系统时间
        
    - 处理 `tout`（超时）
        
    - 处理 `procp->p_cpu` 衰减
        
    

> 💡 **洞见**：clock() 是 V6 的"心脏起搏器"。它每秒跳 60 次，但**真正的调度决策每秒只做 1 次**——这是"高频中断 + 低频决策"的经典模式。今天的操作系统（包括 Linux）仍然沿用这个模式：时钟中断高频触发，但 CFS 调度器的抢占检查是另一个频率。这种设计避免了"每次中断都做完整调度"的开销。

**工业联系**：

- **Linux 的 `tick_periodic()` / `scheduler_tick()`**：现代 Linux 在 tick 中做时间统计、RCU 推进、调度器周期性决策，与 V6 的 clock() 职责高度一致
    
- **实时操作系统的 tick**：RTOS（如 FreeRTOS、Zephyr）的 tick 中断处理，与 V6 的 clock() 几乎是同一个模板
    
- **性能数据**：正如 UNIX V6 源码分析所指出的，在系统负载较高时，V6 的 O(n) 优先级重计算遍历操作会占用约 **3% 的 CPU 时间**。这解释了为什么现代调度器都改用 O(1) 算法——规模上来后，再简单的数据结构和算法也会成为瓶颈

## 5.5 陷入处理函数

### trap()

`trap()` 是 V6 陷入处理的"总控中心"（trap.c 中 2693 行），它根据陷入类型和来源进行分发：

**1. 硬件故障陷入**（如总线错误、非法指令、段违例）：

- 向当前进程发送对应的**信号**（Signal）
    
- 例如：总线错误 → `SIGBUS`，非法指令 → `SIGINS`，段违例 → `SIGSEGV`
    

根据 V6 文档 ：_"The PDP-11 hardware detects a number of program faults... Such faults cause the processor to trap to a system routine. When an illegal action is caught, unless other arrangements have been made, the system terminates the process and writes the user's image on file core in the current directory."_

**2. 系统调用陷入**（trap 指令触发）：

- 从用户寄存器 R0 取出系统调用号
    
- 通过 `sysent` 表分发到具体的系统调用处理函数
    
- 这部分的详细流程在 5.6 节展开
    

**3. 栈溢出处理**（段违例的特殊情况）：

- 当用户栈向下增长超过栈段边界时，触发段违例
    
- trap() 调用 `grow()` 尝试扩大栈段
    
- 如果扩大失败，发送 `SIGSEGV`
    

**trap() 的关键代码片段**​ ：

```
case 8+USER:  // 浮点异常
    i = SIGFPT;
    break;
case 9+USER:  // 段违例
    a = sp;
    if (backup(u.u_ar0) == 0)
        if (grow(a)) goto out;
    i = SIGSEG;
    break;
```

> ⚠️ **难点提示**：PDP-11/40 的一个硬件限制——它**不能重启半执行的指令**。这意味着当 `cmp -(sp),(sp)` 这样的指令引发段违例时，V6 无法"回退"到指令执行前的状态来重试。`backup()` 函数试图在软件层面模拟这种回退，但在某些情况下会失败。这是 PDP-11/40 与 PDP-11/45、PDP-11/70 的重要差异。

### grow()

`grow()` 负责在用户栈溢出时**自动扩展栈段**：

1. 计算需要的新栈大小
    
2. 调用 `expand()` 调整数据段+栈段的总大小
    
3. 如果成功，返回 1；失败则返回 0，trap() 会向进程发送 `SIGSEGV`
    

**洞见**：grow() 体现了 V6 的"**自动栈增长**"机制——用户程序不需要预先声明栈大小，内核在栈溢出时自动扩展。这是现代 OS"栈自动增长"思想的源头。今天你在 Linux 上运行一个递归程序直到栈溢出时看到的 `SIGSEGV`，其处理流程与 V6 的 grow() 是一脉相承的。

## 5.6 系统调用的处理流程

这是第5章最实用的一节——它回答了"用户程序怎么调用内核功能"。

### 传递参数的方法

V6 系统调用的参数传递约定（PDP-11 ABI）：

- **R0-R5 寄存器**：承载前 6 个参数
    
- **用户栈**：如果需要更多参数，从用户栈上传递
    
- **R0 和 R1**：用于返回值
    

当用户执行 `trap` 指令时，硬件自动把 R0 等寄存器的值保存在用户栈上（因为 trap 陷入时，PSW 和 PC 被压栈，但通用寄存器需要软件保存）。V6 的 `trap` 汇编跳板负责把用户寄存器的值复制到内核栈上的 `u.u_ar0` 数组中，供 C 函数 `trap()` 访问。

### sysent 结构体

`sysent` 是**系统调用分发表**——这是 V6 最具现代意义的表格之一：

```
struct sysent {
    int (*sy_call)();    // 系统调用处理函数指针
    short sy_narg;       // 参数个数
    short sy_size;       // 参数总大小
} sysent[NSYS];
```

每个系统调用在表中占据一项，例如：

|索引|系统调用|处理函数|参数个数|
|---|---|---|---|
|1|exit|sys_exit|1|
|2|fork|sys_fork|0|
|3|read|sys_read|3|
|4|write|sys_write|3|
|5|open|sys_open|3|
|7|wait|sys_wait|0|
|11|exec|sys_exec|2|

> 💡 **洞见**：sysent 表是**"表驱动编程"的教科书案例**。它把"系统调用号 → 处理函数"的映射集中在一张表里，新增系统调用只需在表中加一项，不需要修改 trap() 的分发逻辑。这种"数据驱动的架构"在现代操作系统中无处不在——Linux 的 `sys_call_table`、Windows 的 `KeServiceDescriptorTable`、macOS 的 `sysent` 都是同一思想。

**工业联系**：Linux 的 `sys_call_table` 与 V6 的 `sysent` 几乎一模一样——都是"系统调用号索引的函数指针数组"。区别在于：

- Linux 有 300+ 系统调用，V6 只有约 43 个
    
- Linux 用 `syscall` 指令触发，V6 用 `trap` 指令
    
- 但**第一性原理完全相同**：用一张表把"用户请求"映射到"内核函数"
    

### trap() 中的系统调用分发

C 函数 `trap()` 处理系统调用的流程：

1. **取系统调用号**：从 `u.u_ar0[R0]` 取出（R0 的低字节是系统调用号）
    
2. **查 sysent 表**：`sysent[callnum]` 取得处理函数指针和参数个数
    
3. **参数校验**：检查参数个数是否合法
    
4. **调用 trap1()**：通过 `trap1(sysent[callnum].sy_call)` 执行实际处理函数
    

**trap1() 的关键作用**：

```
trap1(f) {
    u.u_intflg = 1;        // 标记正在处理系统调用
    savu(u.u_qsav);       // 保存 R5, R6 到 u.u_qsav
    (f)();                // 执行系统调用
    u.u_intflg = 0;       // 清除标记
}
```

为什么需要 `savu(u.u_qsav)` 这个"神奇"的调用？

**因为系统调用执行过程中可能被信号打断**。如果系统调用在 `sleep()` 上阻塞时被信号唤醒，内核需要**模拟一个从 trap1() 内的"异常返回"**——直接恢复到 trap1() 调用前的现场，让 trap() 重新检查信号。如果没有 `savu(u.u_qsav)`，这种异常返回就无法正确清理栈帧 。

> ⚠️ **深度理解**：trap1() 的设计是 V6 中最微妙的部分之一。它解决了一个根本性问题：**系统调用不是原子操作**——它可能睡眠、可能被信号中断、可能需要重试。savu(u.u_qsav) 保存的现场，就是这个"可中断点"。这与现代 Linux 的 `EINTR`（系统调用被信号中断）错误处理，是同一个问题的不同时代解法。

**工业联系**：

- **Linux 的 `EINTR`**：当系统调用被信号中断时，返回 `EINTR` 错误码，用户程序需要决定是否重试
    
- **Linux 的 `SA_RESTART`**：signal 的标志位，告诉内核自动重启被中断的系统调用
    
- **现代 Windows 的 `IOCP`**：异步 I/O 模型，从根本上避免了"系统调用阻塞被信号打断"的问题
    

V6 的 trap1() 用 `savu/u_qsav` 机制手动处理这个问题，现代 OS 用错误码和标志位处理——**机制演进了，但问题本质没变**。

## 5.7 小结

第5章完成了 V6 控制流入口的完整剖析。把所有机制串起来看：

```
外部事件/内部异常
    ↓
[硬件] 比较优先级、保存 PSW/PC、查向量表
    ↓
[汇编跳板] trap/call 建立 C 环境
    ↓
[C 函数] trap() 统一分发
    ↓
    ├─ 硬件故障 → 发信号 (SIGSEGV 等)
    ├─ 时钟中断 → clock() 更新统计、触发调度
    └─ 系统调用 → trap1() → sysent[callnum] → 具体 sys_xxx()
    ↓
[返回] rtt 恢复 PSW/PC，回到原执行流
```

**第一性原理总结**：

1. **中断与陷入是内核的唯一入口**：所有"非顺序控制流转移"都必须经过这里。这是操作系统"控制反转"的根本机制。
    
2. **硬件与内核的契约是向量表**：硬件只认"地址 0 开始的向量表"，内核负责填充正确的处理程序入口。这种"硬件查表 + 软件跳板"的两级分发，是计算机系统的通用模式。
    
3. **优先级即屏蔽**：PDP-11 用 PSW 的 3 位优先级实现"关中断"保护，这是无锁编程的源头。现代自旋锁的"禁用本地中断"变体，本质相同。
    
4. **系统调用是"故意的陷入"**：用户程序用 trap 指令"故意"触发陷入，把自己的意图安全传递给内核。sysent 表把"调用号"映射到"处理函数"，是表驱动架构的经典案例。
    
5. **时钟中断是心跳**：clock() 每秒 60 次触发，但调度决策每秒只做 1 次。高频中断 + 低频决策的分离，是现代操作系统的通用模式。
    
6. **系统调用不是原子操作**：trap1() 中的 savu(u.u_qsav) 机制，解决了"系统调用可能被信号中断"的根本问题。这是现代 `EINTR` 错误的祖先。
    

**跨章节联系**：

- 第3章的 `swtch()`：在 clock() 设置 `runrun` 标志后被调用，完成进程切换
    
- 第4章的 `sched`：每秒被 clock() 唤醒一次，检查 runin/runout 条件，决定换入换出
    
- 第3章的 `sleep()/wakeup()`：陷入处理中发送信号（如 SIGKILL）会调用 `psignal()`，进而 `wakeup()` 目标进程
    
- 第2章的 user 结构体：`u.u_ar0` 数组保存用户寄存器现场，是 trap() 访问用户参数的桥梁
    
- 下一章（第6章）的信号：trap() 处理硬件故障陷入时，核心操作就是"向进程发送信号"
    

**工业落地的五点启示**：

1. **向量表是硬件与软件的接口契约**：在设计任何"硬件事件 → 软件处理"的系统时，用向量表作为分发机制。今天的中断控制器（APIC）、ARM 的异常向量表，都是这一思想的延续。
    
2. **优先级编码紧急程度**：用数字优先级表达"时间敏感性"，让硬件自动做"该不该打断当前执行"的决策。这在实时系统中尤为重要——RTOS 的任务优先级、Linux 的 RT 调度策略，都是这一思想的演化。
    
3. **表驱动优于 switch-case**：sysent 表告诉我们——把"请求类型 → 处理函数"的映射数据化，比写一长串 if-else 或 switch 更灵活、更易扩展。今天的所有 RPC 框架、API 网关路由，本质都是 sysent 表的放大版。
    
4. **系统调用的参数传递需要 ABI 约定**：R0-R5 寄存器 + 用户栈的混合传递，是 PDP-11 的 ABI 选择。今天的 x86-64 System V ABI 用 RDI/RSI/RDX/RCX/R8/R9 传前 6 个参数——**机制相同，寄存器不同**。理解 V6 的 ABI，你就能理解为什么今天的系统调用要用特定的寄存器传参。
    
5. **可中断性是系统调用的本质属性**：trap1() 用 savu 处理"系统调用被信号打断"，揭示了"阻塞操作必须可中断"的第一性原理。今天的异步 I/O、Future/Promise、协程，都是在更高层次上解决同一个问题——**如何让"等待"不阻塞整个执行流**。

## 英文补充资料与跨时代对照

### 1. PDP-11 官方手册（Digital Equipment Corporation）

《PDP-11 Series Handbook》中明确记载："When an interrupt or trap occurs, the current PSW and PC are preserved... The new contents of the PC and the PSW are fetched from two consecutive memory words called a vector." 这是理解 V6 中断/陷入硬件基础的**一手资料**。

### 2. MIT 6.828 课程材料

《Lecture 7 homework: Entering the Unix v6 Kernel on the PDP-11》通过 PDP-11 模拟器逐步跟踪了第一次系统调用陷入的全过程——从用户态执行 `TRAP 13` 到进入 C 函数 `trap()`。这是**实操理解 trap 流程的最佳材料**。

### 3. University of Toronto 的 Interrupts 讲义

清晰解释了 PDP-11 的中断优先级模型："greater numbers are greater priorities... When an interrupt occurs, the hardware compares the priority of the interrupt to the CPU priority stored in the PSW, and interrupts if and only if the CPU priority is lower." 配有声音中断 vs 键盘中断的实例。

### 4. V6 源码原典（TUHS）

`trap.c`、`clock.c`、`l.s`、`m40.s` 等原始文件，可在 TUHS（The Unix Heritage Society）网站获取。特别是 `trap.c` 中 2693-2824 行的 `trap()` 函数，以及 2841 行的 `trap1()` 函数，是本章的"圣物"。

### 5. Lions 注释本第 9 章

John Lions 对 V6 中断/陷入处理的逐行注释，特别是对 `trap` 汇编跳板和 `trap()` C 函数的对照讲解，是理解"同名 trap 三个实体"的最佳资料。

### 6. 现代对照

|V6 概念|现代 Linux 对应|演进|
|---|---|---|
|trap 指令|syscall/sysenter 指令|专用指令替代通用陷入|
|向量表（地址 0）|IDT（中断描述符表）|可配置位置|
|PSW 的 IPL 3 位|EFLAGS 的 IF + 优先级|扩展为更多位|
|sysent 表|sys_call_table|300+ 系统调用|
|trap1() 的 savu|EINTR + SA_RESTART|错误码 + 标志位|
|clock() 每秒 60 次|tick_periodic() 或 tick_sched()|HZ 可配置（通常 250/1000）|
|信号发送给进程|send_sig()|信号语义保持一致|
