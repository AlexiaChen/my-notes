
# 《Unix内核源码剖析》读书笔记 · 第6章 信号

> 前五章我们把进程的"身体"建好了——它有 proc 和 user 结构体、有地址空间、能被 fork/exec、能在时钟中断驱动下被 swtch 切换、能在内存不足时被 sched 换入换出。但进程还缺一个东西：**对外部事件的响应能力**。第5章讲了陷入和中断是"进入内核"的入口；第6章则讲——**内核进入后，怎么把"事件"交付给进程？**
> 
> 答案是：**信号（Signal）**。
> 
> **第一性洞见**：信号的本质是**"异步事件在受控检查点的受控交付"**。说它异步，是因为信号随时可能产生（硬件异常、kill 系统调用、时钟）；说它受控，是因为 V6 **不会**在信号到达的瞬间打断进程去执行 handler，而是等到进程在**特定的检查点**（即将睡眠、从 trap 返回、时钟中断每秒检查时）才去"看一眼"自己有没有待处理信号。这种"延迟交付"不是偷懒，而是**硬件约束下的必然**——因为目标进程的 user 结构体（保存着用户栈和寄存器现场）可能已经被换出到磁盘，只有等调度器把它换入内存，才能安全地构造信号处理现场 。
> 
> 正如英文讲义所指出的："_The Sender sets a flag in the receiver's proc structure and increase the priority of the receiver. The Receiver checks the flag, and deliver the signal. Why does the receiver deliver the signal instead of the sender? (Answer: The receiver's stack may be swapped out; thus, we must give the scheduler a chance first to load the receiver.)_" ——这句话是理解 V6 信号设计的第一性原理。

## 6.1 什么是信号

### 信号的发送方法

V6 中信号的发送极其简单——**在目标进程的 proc 结构体中设置一个标志位**：

```
// proc 结构体中的关键字段
struct proc {
    // ...
    char p_sig;        // 发送给该进程的信号编号
    // ...
};
```

`kill()` 系统调用是用户态发送信号的主要入口。根据 V6 手册 ，kill 的语义是：

- 向 r0 中指定的 PID 进程发送信号
    
- 发送者和接收者必须有相同的有效用户 ID，否则只有超级用户能做
    
- **PID = 0 的特殊语义**：信号发送给所有与发送者共享同一个控制终端和用户 ID 的进程
    
- 进程不能给自己发信号
    

> 💡 **洞见**：PID=0 的语义是 V6 对"终端前台进程组"概念的朴素表达——你在 shell 里按 Ctrl+C，其实是 init 或 shell 向整个进程组广播 SIGINT。这个"进程组"概念在 V6 中还很原始（通过 p_ttyp 控制终端字段关联），但**思想已经完备**——今天你在 Linux 上 `kill -9 -PGID`（注意负号）做的事，V6 用 `kill(0, SIGKIL)` 就能做。

**关键限制（V6 信号的"不可靠"根源）**：根据英文讲义 ，"_if the destination process has a signal pending, overwrite it with this one. Thus, the signals in v6 may be lost_"。也就是说——**p_sig 是个单槽位字段，只能存一个待处理信号**。如果进程已经有待处理信号，新来的信号会**覆盖**它。这就是著名的"信号可能丢失"问题的源头。

> ⚠️ **重要例外**：SIGKIL（信号 9）**不可被覆盖**——即使目标进程已有待处理信号，SIGKIL 也能强行设置。这是 SIGKIL "必杀"语义的内核级保证。

### 确认接收信号

信号不是"发送即送达"，而是"**发送方设置标志，接收方在检查点确认**"。V6 中接收方在以下三个检查点确认信号 ：

1. **即将进入休眠时**（`sleep()` 函数中调用 `issig()`）
    
2. **从 trap 返回用户态时**（`trap()` 函数中调用 `issig()`）
    
3. **时钟中断每秒检查时**（`clock()` 函数中调用 `issig()`）
    

为什么是这三个点？因为它们是**"内核即将把控制权交还用户态"的天然边界**。在用户态执行指令流时被信号打断是不可能的（PDP-11 没有硬件支持），所以只能在"内核 → 用户态"的切换瞬间插入信号检查。

`issig()` 的逻辑极简：

```
issig() {
    if (u.u_procp->p_sig != 0) {
        // 有待处理信号
        return(u.u_procp->p_sig);
    }
    return(0);
}
```

返回非零值表示信号编号，返回 0 表示没有信号。

### 信号的种类

V6 定义了 **NSIG = 20**（最多支持 20 种信号），但实际只用了 **13 种**​ ：

|编号|名称|含义|默认行为|
|---|---|---|---|
|1|SIGHUP|终端挂断|终止|
|2|SIGINT|中断（Ctrl+C/Rubout）|终止|
|3|SIGQIT|退出（Ctrl+\）|终止 + Core|
|4|SIGINS|非法指令|终止 + Core|
|5|SIGTRC|跟踪/断点|终止 + Core|
|6|SIGIOT|IOT 指令|终止 + Core|
|7|SIGEMT|EMT 指令|终止 + Core|
|8|SIGFPT|浮点异常|终止 + Core|
|9|SIGKIL|强制终止|**终止（不可捕获）**​|
|10|SIGBUS|总线错误|终止 + Core|
|11|SIGSEG|段违例|终止 + Core|
|12|SIGSYS|系统调用错误|终止 + Core|
|13|SIGPIPE|管道断裂|终止|

> 📌 **历史注脚**：这些信号名字大多来自 PDP-11 的硬件特性——SIGIOT 来自 PDP-11 的 IOT 指令，SIGTRC 来自 PDP-11 的跟踪陷阱，SIGEMT 来自 PDP-11 的 EMT 指令。今天你在 Linux 上看到的 SIGABRT（6）、SIGFPE（8）、SIGKILL（9）、SIGSEGV（11）等，编号和 V6 完全一致——**这是 1975 年定下的契约，50 年来没变过**。

### 信号的处理方式

V6 中每个进程通过 `user.u_signal[NSIG]` 数组定义对每个信号的处理方式 ：

- **值为 0**：执行默认动作（通常是终止进程）
    
- **值为奇数**：忽略该信号
    
- **值为偶数**：执行该值对应的用户态函数作为信号处理程序
    

**关键设计**：SIGKIL（9）既不能忽略也不能自定义 handler——任何试图 `ssig(SIGKIL, ...)` 的操作都会返回 EINVAL 错误。这是"管理员最后手段"语义的内核保证。

### ssig()

`ssig()` 是 `signal()` 系统调用的内核实现，负责修改 `u.u_signal[]` 数组 ：

```
ssig() {
    register a;
    a = u.u_arg[0];  // 信号编号
    if (a >= NSIG || a == SIGKIL) {
        u.u_error = EINVAL;
        return;
    }
    u.u_ar0[R0] = u.u_signal[a];  // 返回旧的处理方式
    u.u_signal[a] = u.u_arg[1];  // 设置新的处理方式
    if (u.u_procp->p_sig == a)
        u.u_procp->p_sig = 0;    // 如果当前有待处理信号，清除它
}
```

**洞见**：ssig 的返回值设计——返回**旧的信号处理方式**。这让用户可以"保存旧 handler，设置新 handler，处理完后恢复原 handler"。这是 V6 信号编程的标准惯用法。

### kill()

`kill()` 系统调用的内核实现，核心是调用 `psignal()`：

```
kill() {
    register a;
    a = u.u_arg[0];  // 目标 PID
    if (a == 0) {
        // 向所有共享终端和用户 ID 的进程发信号
        for (所有 proc) {
            if (proc->p_ttyp == u.u_ttyp && proc->p_uid == u.u_uid)
                psignal(proc, u.u_arg[1]);
        }
    } else {
        // 找到指定 PID 的进程
        for (所有 proc) {
            if (proc->p_pid == a) {
                // 权限检查
                if (proc->p_uid != u.u_uid && !suser())
                    u.u_error = EPERM;
                else
                    psignal(proc, u.u_arg[1]);
                return;
            }
        }
        u.u_error = ESRCH;  // 进程不存在
    }
}
```

### signal()

`signal()` 是用户态 API，对应内核的 `ssig()`。它就是 V6 版的 `signal(2)` 系统调用。

### psignal()

`psignal(p, sig)` 是**信号发送的核心函数**——它在目标进程的 proc 结构体中设置 p_sig 标志 ：

```
psignal(p, sig) {
    p->p_sig = sig;
    // 应该提升目标进程优先级，但代码有个 bug：用了 p_stat 而非 p_pri
    if (p->p_stat == SSLEEP) {
        // 如果目标进程在睡眠，唤醒它
        setrun(p);
    }
}
```

> ⚠️ **著名的 V6 Bug**：英文讲义明确指出："_should raise priority of destination process, but code contains a bug (it uses p_stat instead of p_prio)_"。psignal 本应提升目标进程的优先级确保它能尽快被调度并检查信号，但 Ritchie 的代码错把 `p_stat` 当成了 `p_pri`——这是个真实的 bug，存在于 V6 源代码中。Lions 注释本里专门讨论了这个问题。

**洞见**：psignal 只做两件事——(1) 设置 p_sig 标志；(2) 如果目标进程在睡，唤醒它。它**不**直接执行 handler，因为目标进程的 user 结构体可能不在内存中。**这就是"发送方设置标志，接收方延迟交付"模型的硬件根源**。

### issig()

如前所述，`issig()` 在三个检查点被调用，返回待处理信号编号或 0。

### psig()

`psig()` 是**信号交付的核心函数**——它在用户态构造信号处理的执行现场 。这是 V6 中最精妙的函数之一：

```
psig() {
    register a, *ip, *fp;
    // 1. 取出信号编号
    a = u.u_procp->p_sig;
    u.u_procp->p_sig = 0;  // 清除待处理标志
    
    // 2. 检查用户自定义处理方式
    if ((a &= 037) == 0) goto out;  // 默认终止
    
    // 3. 如果是奇数，忽略信号
    if (u.u_signal[a] & 1) goto out;
    
    // 4. 执行用户 handler（偶数）
    // 修改用户栈，构造执行现场：
    // - 把 trap/中断现场的 PC 压到用户栈
    // - 把 trap/中断现场的 PSW 压到用户栈
    // - 把用户 handler 地址设置到 PC
    // - 用 rtt 指令返回用户态时，先执行 handler
    
    // 5. 关键：设置 u_signal[0] = 0，防止 handler 被递归中断
    u.u_signal[0] = 0;
    
    // 6. 返回用户态，执行 handler
out:
    // 默认动作：终止进程
}
```

**psig() 的精髓**（英文讲义的精彩分析 ）：

> "_The code modifies the user stack so that after the signal handler runs, it returns to the saved pc in the trap/interrupt frame; this pc corresponds to the next instruction that must be executed after the signal handler has completed. The code also modifies the user stack to save the saved PSW, because the signal handler is likely to modify the condition codes in PSW; thus, PSW needs to be restored to its saved value when the signal handler completes._"

换句话说，psig() **手工构造了一个用户栈帧**，使得：

1. 信号 handler 执行完毕后，`rtt` 指令会从栈上弹出 PC 和 PSW
    
2. PC 指向**原来被打断的下一条指令**
    
3. PSW 恢复为原来的处理器状态
    

这样，信号 handler 就像"插队执行"的一段代码，执行完后会**无缝回到原来被中断的位置继续执行**。

> 💡 **第一性原理洞见**：psig() 做的事情，本质上是**"用户态的上下文切换"**——它在同一个进程的地址空间内，从一个执行流（被中断的指令流）切换到另一个执行流（信号 handler），然后再切回来。这和内核的 `swtch()` 在思想上完全一致，只不过 swtch 切换的是**进程**，psig 切换的是**同一进程内的执行流**。
> 
> 更深刻的洞见是：**psig 必须"伪造"一个返回地址**。 handler 函数看起来像是"被调用"的，但实际上它不是被 call 指令调用的，而是 psig 手工在栈上构造了调用现场。这就是为什么 handler 执行完 `return` 时能正确回到原执行点——因为栈上早就准备好了对应的返回地址。

**信号重入问题**：psig 设置 `u.u_signal[0] = 0` 是为了防止 handler 被另一个信号递归中断。这意味着：

- **handler 执行期间，该信号被重置为默认动作**（通常是终止）
    
- 如果 handler 想持续捕获该信号，**必须在 handler 内部重新调用 signal() 注册自己**
    
- 如果在重新注册之前又来了同一个信号，**进程会终止**！
    

这就是 V6 信号臭名昭著的"不可靠信号"问题的根源。现代 UNIX 用 `sigaction()` 解决了这个问题——handler 执行期间自动阻塞同类信号。

### core()

`core()` 函数负责**生成 core dump 文件**——当信号默认动作是"终止 + Core"时调用：

1. 在当前目录下创建名为 `core` 的文件
    
2. 把进程的整个地址空间（代码段、数据段、栈、user 结构体）写入文件
    
3. 终止进程
    

> 📌 **工业联系**：今天你在 Linux 上看到的 `core` 文件，其机制与 V6 完全相同。区别在于：
> 
> - 现代 Linux 用 `ulimit -c` 控制 core 文件大小
>     
> - 现代 core 文件名可配置（`/proc/sys/kernel/core_pattern`），可以包含 PID、时间戳、可执行文件名等
>     
> - 4.3+BSD 引入了 `core.prog` 命名方式（prog 是可执行文件前 6 字符）
>     
> 
> 但**第一性原理没变**：进程崩溃时，把内存映像持久化到磁盘，供 debugger 事后分析。gdb 的 `bt`（backtrace）、`info registers` 等命令，读的就是 core 文件里的这些信息。

### 在系统调用处理中处理信号

这是 V6 信号最微妙的部分。回顾第5章讲过的 `trap1()` 函数——系统调用处理函数执行期间，可能被信号中断（比如进程在 `read()` 上睡眠时被 SIGKILL 唤醒）。

处理流程：

1. 系统调用在 `sleep()` 上阻塞
    
2. 信号到达，`psignal()` 唤醒进程
    
3. 进程被调度，从 `swtch()` 返回到 `sleep()` 之后的代码
    
4. `sleep()` 返回，回到 `trap1()`
    
5. `trap1()` 返回，回到 `trap()`
    
6. `trap()` 在返回用户态之前调用 `issig()` 检查信号
    
7. 如果有信号，`psig()` 构造 handler 现场
    
8. `rtt` 指令返回用户态，**先执行信号 handler**
    
9. handler 执行完，`rtt` 再次返回，**这次才真正回到系统调用后的那条指令**
    

> ⚠️ **关键认知**：V6 的信号**不会**中断正在内核态执行的系统调用。信号只能在"内核即将返回用户态"的检查点被交付。这意味着——如果一个系统调用永远不睡眠、永远不返回（理论上不可能，但长时间运行的系统调用确实存在），信号就会被延迟很久才交付。这是 V6 信号延迟的本质原因。

## 6.2 跟踪功能

### 什么是跟踪

跟踪（Tracing）是 V6 提供的**父进程控制子进程执行**的机制，主要用于实现**断点调试器**（如早期的 db 调试器）。

**核心思想**：父进程通过 `ptrace()` 系统调用，可以：

- 读写子进程的内存和寄存器
    
- 单步执行子进程
    
- 让子进程继续执行或终止
    
- 拦截子进程收到的信号
    

### ipc 结构体

`ipc`（Inter-Process Communication）结构体是父子进程在跟踪过程中的"信箱"：

```
struct ipc {
    int ip_lock;   // 锁（通常是子进程 PID）
    int ip_data;   // 数据（读写的值）
    int ip_addr;   // 地址（内存地址或寄存器偏移）
    int ip_req;    // 请求类型
};
```

父进程把请求写入 ipc，唤醒子进程；子进程在 `stop()` 中被唤醒后，通过 `procxmt()` 响应请求，把结果写回 ipc，然后重新睡眠等待下一个请求。

### 跟踪的处理流程

根据 V6 源码分析 ，跟踪的完整流程如下：

**子进程侧**：

1. 子进程调用 `ptrace(0, ...)` 声明自己将被父进程跟踪（设置 STRC 标志）
    
2. 子进程执行过程中遇到信号（无论是硬件异常还是外部 kill）
    
3. 进入 `stop()` 函数：
    
    ```
    stop() {
    loop:
        cp = u.u_procp;
        if (cp->p_ppid != 1)
            for (pp = &proc[0]; pp < &proc[NPROC]; pp++)
                if (pp->p_pid == cp->p_ppid) {
                    wakeup(pp);              // 唤醒父进程
                    cp->p_stat = SSTOP;      // 进入停止状态
                    swtch();                  // 让出 CPU
                    if ((cp->p_flag&STRC)==0 || procxmt())
                        return;              // 继续执行
                    goto loop;
                }
    }
    ```
    
4. `procxmt()` 执行父进程的具体请求（读内存、写内存、设置寄存器、继续等）
    

**父进程侧**：

1. 调用 `ptrace(request, pid, addr, data)`
    
2. 找到子进程（必须是自己的直接子进程）
    
3. 填写 ipc 结构体
    
4. 调用 `setrun(p)` 唤醒子进程
    
5. 父进程在 `&ipc` 上 `sleep()`，等待子进程处理完请求
    
6. 子进程处理完后 `wakeup(&ipc)`，父进程被唤醒，读取结果
    

### stop()

`stop()` 是子进程进入"被跟踪停止"状态的入口。它的核心是：

- **唤醒父进程**（通过 `wakeup(pp)`）
    
- **自身进入 SSTOP 状态**
    
- **调用 swtch() 让出 CPU**
    
- 被父进程的 `setrun()` 唤醒后，调用 `procxmt()` 处理请求
    
- 如果 `procxmt()` 返回 1，子进程继续执行；返回 0，继续停在 stop 循环中
    

### ptrace()

根据 V6 手册 ，ptrace 有 8 种请求：

|请求|功能|
|---|---|
|0|子进程声明自己将被跟踪|
|1, 2|读子进程数据空间/指令空间的一个字|
|3|读子进程的 user 结构体（寄存器等信息）|
|4, 5|写子进程数据空间/指令空间的一个字|
|6|写子进程的 user 结构体（寄存器）|
|7|让子进程继续执行，可指定忽略/传递某个信号|
|8|终止被跟踪的子进程|

> 💡 **洞见**：ptrace 的请求 7 是调试器的核心——它让子进程"带着信号继续执行"。如果信号是 0，表示忽略导致停止的那个信号；如果是其他值，表示子进程继续执行时"假装"收到了那个信号。这是 gdb 的 `continue` 命令、`stepi` 命令的底层机制。

**工业联系**：今天的 `gdb`、`strace`、`ltrace`、`perf` 等调试/跟踪工具，底层都依赖 ptrace（或现代的 `ptrace` + `seccomp` + `eBPF` 组合）。gdb 设置断点的原理是：

1. 用 ptrace 读写子进程内存，把目标地址的指令替换为 `trap` 指令（PDP-11 上是 0104400 系列）
    
2. 子进程执行到该地址时触发 trap，陷入内核
    
3. 内核发现子进程被跟踪，调用 `stop()` 进入停止状态
    
4. 父进程（gdb）被 `wakeup`，通过 ptrace 读取子进程状态、修改寄存器、恢复原始指令
    
5. 父进程用 ptrace 请求 7 让子进程单步执行一条指令
    
6. 重复上述过程
    

**这个流程从 V6 到今天的 gdb，核心机制 50 年没变**。

### procxmt()

`procxmt()` 是子进程响应父进程 ptrace 请求的"执行器"。它是一个大的 switch 语句，根据 `ipc.ip_req` 的值执行相应操作：

- 请求 1, 2：从 `ipc.ip_addr` 读取子进程内存的一个字，放入 `ipc.ip_data`
    
- 请求 3：从 user 结构体读取寄存器值
    
- 请求 4, 5：把 `ipc.ip_data` 写入子进程内存的 `ipc.ip_addr` 处
    
- 请求 6：修改 user 结构体中的寄存器值
    
- 请求 7：设置"继续执行"标志，返回 1 让 `stop()` 退出循环
    
- 请求 8：调用 `exit()` 终止子进程
    

### wait()

父进程通过 `wait()` 系统调用感知子进程的状态变化：

- 子进程正常退出 → wait 返回子进程 PID 和退出状态
    
- 子进程被信号终止 → wait 返回子进程 PID 和信号编号
    
- **子进程被跟踪停止**​ → wait 返回一个特殊值（0177），表示"子进程已停止而非终止"
    

> 📌 **洞见**：`wait()` 的"停止"返回值是调试器的关键——gdb 通过 wait 得知子进程遇到了断点，然后用 ptrace 去检查/修改子进程状态。V6 用 0177 这个特殊的"终止状态"值来区分"真的死了"和"停下来了"，这是现代 `WIFSTOPPED()` 宏的鼻祖。

## 6.3 小结

第6章完成了 V6 信号与跟踪机制的完整剖析。把所有机制串起来看：

```
事件源（硬件异常/ kill 系统调用/ 时钟）
    ↓
psignal()：在目标 proc.p_sig 设置标志
    ↓
（延迟交付——等待接收方到达检查点）
    ↓
issig()：在 sleep/trap/clock 检查点确认信号
    ↓
psig()：构造用户栈现场，执行 handler
    ↓
（handler 执行完，rtt 返回原执行点）
```

**跟踪机制的流程**：

```
父进程 ptrace(request) → 填 ipc → setrun(子进程) → sleep(&ipc)
                                              ↓
子进程遇到信号 → stop() → wakeup(父) → SSTOP → swtch()
                                              ↓
                                      被父进程唤醒
                                              ↓
                                    procxmt() 处理请求
                                              ↓
                                    返回结果到 ipc
                                              ↓
                                    wakeup(&ipc) → 父进程唤醒
```

**第一性原理总结**：

1. **信号是"异步事件 + 受控交付"**：发送方只设置标志，接收方在检查点确认并交付。这是硬件约束（user 结构体可能换出）下的必然设计。
    
2. **p_sig 是单槽位邮箱**：V6 的信号不可靠——新信号覆盖旧信号。这是"信号可能丢失"问题的根源，也是现代 `sigaction()` 要解决的问题。
    
3. **psig() 是"用户态上下文切换"**：它在同一个进程内构造执行流切换，思想和内核的 swtch() 一致，但操作的是用户栈。
    
4. **信号 handler 必须重新注册**：V6 的 `u.u_signal[0] = 0` 设计导致 handler 执行期间该信号被重置为默认动作。这是"不可靠信号"的另一面。
    
5. **跟踪是父进程对子进程的"完全控制"**：通过 ipc 信箱 + stop/procxmt 协作，父进程可以读写子进程内存、单步执行、拦截信号。这是 gdb 等调试器的鼻祖。
    
6. **wait() 统一回收子进程**：无论是正常退出、信号终止、还是被跟踪停止，父进程都通过 wait() 感知。0177 特殊返回值区分"停止"和"终止"。
    

**跨章节联系**：

- 第2章的 proc 结构体：`p_sig` 字段是本征章的核心数据结构
    
- 第3章的 `sleep()/wakeup()`：信号交付依赖 sleep 中的 issig() 检查
    
- 第4章的 sched：psignal 唤醒目标进程后，需要 sched 把它换入内存才能构造 handler 现场
    
- 第5章的 trap：trap 返回用户态前的 issig() 检查，是信号交付的主要检查点
    
- 下一章（第7章）的"文件与 I/O"：core 文件的生成依赖文件系统接口
    

**工业落地的六点启示**：

1. **不可靠信号的教训**：V6 的 p_sig 单槽位设计告诉我们——**异步事件的传递必须有队列**。现代操作系统的"信号队列"（pending signal queue）正是对 V6 缺陷的修正。今天设计任何异步通知机制（消息队列、事件总线、Webhook）时，都应该用队列而非单槽位。
    
2. **延迟交付的普适性**：V6 的"在检查点交付信号"思想，在现代操作系统中演化为"**在抢占点检查**"——Linux 的 `schedule()` 前检查 `TIF_SIGPENDING` 标志、Java 的线程中断在"安全点（safepoint）"检查、Go 的 goroutine 抢占在"函数序言"检查。**第一性原理相同：异步事件不能在任意点打断执行流，必须在受控检查点交付**。
    
3. **用户态上下文切换的通用性**：psig() 构造用户栈现场的思想，在现代演化为：
    
    - **协程（coroutine）**：切换执行流时保存/恢复寄存器现场
        
    - **C 语言的 `setjmp/longjmp`**：保存/恢复栈帧
        
    - **异步编程的 continuation**：把"剩下的工作"封装成闭包
        
    
    这些技术的共同祖先，都可以追溯到 psig() 的"伪造返回地址"。
    
4. **ptrace 调试模型的持久生命力**：从 V6 的 ptrace 到今天的 gdb、strace、ltrace、perf、eBPF，调试器的基本模型没变——**父进程通过内核提供的接口，观察和控制子进程的执行**。eBPF 是这一思想在现代的最新演化：不再需要 ptrace 的"停止-检查-继续"开销，而是用内核中的 BPF 程序直接观察。但**第一性原理相同：观测者通过内核中介观察被观测者**。
    
5. **SIGKILL 的"不可捕获"语义**：V6 设定 SIGKIL 不可被忽略或捕获，这个语义延续到今天。它告诉我们——**系统必须保留一个"管理员最后手段"**，即使进程故意忽略所有其他信号，管理员仍能强制终止它。今天容器编排系统（Kubernetes）的 `kubectl delete pod --force --grace-period=0` 正是这一思想的现代体现。
    
6. **core dump 是调试的基石**：V6 的 core() 函数生成的 core 文件，是现代 post-mortem debugging 的起点。今天的生产环境调试流程：
    
    - 进程崩溃 → 生成 core 文件
        
    - 用 gdb 加载 core 文件 → 查看 backtrace、局部变量、寄存器
        
    - 定位 bug
        
    
    这一流程的每个环节，都能在 V6 中找到对应。

## 英文补充资料与跨时代对照

### 1. MIT 6.828 课程讲义（Interprocess Communication）

讲义中明确指出："_The Sender sets a flag in the receiver's proc structure and increase the priority of the receiver. The Receiver checks the flag, and deliver the signal._" 并深入分析了为什么是接收方而不是发送方交付信号（因为接收方的栈可能已被换出）。讲义还逐行讲解了 psig() 如何修改用户栈以实现 handler 执行。

### 2. V6 信号类型定义

V6 源码中 `NSIG = 20`，实际定义了 13 种信号。今天 Linux 的 signal.h 中，SIGKILL=9、SIGSEGV=11 等编号与 V6 完全一致——**这是操作系统史上最稳定的 ABI 之一**。

### 3. V6 ptrace 手册（Section 2）

手册清晰定义了 ptrace 的 8 个请求："_Ptrace provides a means by which a parent process may control the execution of a child process, and examine and change its core image. Its primary use is for the implementation of breakpoint debugging._"

### 4. Lions 注释本第 13 章

John Lions 对 ssig (3614)、kill (3630)、signal (3949)、psignal (3963)、issig (3991)、psig (4043)、core (4094)、stop (4016)、ptrace (4164)、procxmt (4204) 等函数有逐行注释。特别是 psig() 中 4055-4061 行"修改用户栈"的代码，Lions 称之为"信号的精髓"。

### 5. 现代对照

|V6 概念|现代 Linux 对应|演进|
|---|---|---|
|p_sig（单槽位）|pending signal queue|信号不再丢失|
|ssig()/signal()|sigaction()|handler 执行期间自动阻塞同类信号|
|psig() 构造用户栈|setup_frame()/setup_rt_frame()|机制相同，支持 sa_siginfo|
|SIGKIL 不可捕获|SIGKILL/SIGSTOP 不可捕获|语义一致|
|core() 生成 core 文件|core dump + core_pattern|支持命名模板|
|ptrace() 8 种请求|ptrace() + eBPF|eBPF 替代部分调试场景|
|stop()/procxmt()|ptrace 的 STOP/CONT|机制一致|
|wait() 返回 0177|WIFSTOPPED(status)|宏封装|

> 💡 **跨时代洞见**：从 V6 到现代 Linux，信号机制的**第一性原理没变**——异步事件在受控检查点交付。变的是：
> 
> - **可靠性**：从单槽位到队列，信号不再丢失
>     
> - **安全性**：SIGKILL/SIGSTOP 不可捕获的语义被严格保持
>     
> - **灵活性**：sigaction 支持 sa_siginfo、sa_mask 等高级特性
>     
> - **调试能力**：ptrace 从"停止-检查-继续"模式演化为支持 eBPF 的"内核内观测"
>     
> 
> 理解 V6 的信号，你就拿到了理解现代信号机制的"源代码"。

## 给读者的学习建议

1. **在 PDP-11 模拟器上观察信号交付**：用 simh 运行 V6，写一个用户程序注册 SIGINT handler，然后从另一个终端 `kill -2 <pid>`，用调试器观察 psig() 如何构造用户栈。这是"看见" psig() 工作的最佳方式。
    
2. **画出 psig() 的用户栈变化图**：
    
    ```
    信号到达前：                 信号 handler 执行时：
    +------------------+         +------------------+
    | 原 PSW           | ← rtt   | 原 PC            |
    | 原 PC            |         | 原 PSW           |
    | ...用户栈...      |         | ...用户栈...      |
    +------------------+         | handler 地址     | ← PC
                                +------------------+
    ```
    
    理解这个栈帧的构造，你就理解了"信号处理"的本质。
    
3. **对比现代 sigaction**：在 Linux 上写一个程序用 `sigaction()` 注册信号处理函数，观察 handler 执行期间同类信号是否被阻塞。对比 V6 的 `signal()`，体会"可靠信号"与"不可靠信号"的区别。
    
4. **用 strace 观察现代调试**：在 Linux 上 `strace -f -e trace=signal,ptrace gdb ./test`，观察 gdb 如何通过 ptrace 控制子进程。你会发现——**50 年前的机制今天还在运行**。
