## 第II部分 进程 · 第2章 前置背景

在正式进入第1章之前，必须先建立的一个认知是：**UNIX V6 不是一个抽象的操作系统，它是 PDP-11 的"孪生兄弟"**。V6 于 1975 年发布，约 9000 行 C + 2000 行汇编，首次被广泛授权给大学，是 BSD 家族的起点，也是 John Lions 那本传奇注释本的剖析对象。它运行在 PDP-11 系列机上，而 PDP-11 是 16 位处理器、18 位物理地址空间（如 11/40 支持 56K–228K 字内存）、无分页但支持分段、带 UNIBUS 内存映射 I/O。

> 💡 **第一性原理视角**：V6 的全部"简洁"都不是为了简洁而简洁，而是因为硬件只允许它简洁。当我们今天惊叹于"43 个系统调用就能跑起一个完整操作系统"时，要意识到这背后是 PDP-11 那可怜的内存容量在强制约束。**约束是设计的母亲**——这句话在 V6 上体现得淋漓尽致。

## 第1章 UNIX V6的全貌

### 1.1 什么是UNIX V6

UNIX V6 是贝尔实验室 1975 年发布的第六版 UNIX，第一个被广泛授权给大学之外机构的版本。它的历史定位非常特殊：

- **代码规模极小**：约 9000 行 C + 2000 行汇编，一个学期就能读完
    
- **完全用 C 编写**：这是第一个带可移植 C 编译器的 UNIX，意味着内核不再是汇编的奴隶
    
- **伴随 Lions 注释本**：John Lions 写的逐行注释本，尽管 AT&T 曾试图封禁，但在 1990 年代后成为操作系统课程的"地下圣经"
    
- **现代系统的直系祖先**：BSD 家族直接从 V6 衍生；Minix 受它启发；Linux 的设计哲学也能追溯到这里
    

> 📌 **读书笔记洞见**：V6 之所以到今天还在被读，不是因为它"古老"，而是因为它**把操作系统的本质概念压缩到了人脑可一次性消化的规模**。现代 Linux 内核有几千万行代码，你永远无法"读完"它；但 V6 你可以，读完之后你对操作系统的认知会完成一次"第一性原理"的重构——你会发现现代内核里那些复杂的子系统（调度器、内存管理、文件系统），在 V6 里都是用几百行代码直白实现的。**复杂是积累出来的，不是本质需要的**。

### 1.2 UNIX的历史

UNIX 的诞生是对 MULTICS 的"反动"——MULTICS 太复杂、太庞大，Ken Thompson 和 Dennis Ritchie 想要一个"简单的、能做完的"系统。这条主线你必须抓住：

1. **1969 年**：Thompson 在 PDP-7 上写出第一个 UNIX 原型
    
2. **1971-1973 年**：搬到 PDP-11，用 C 重写（这是最关键的一步——用高级语言写操作系统）
    
3. **1975 年**：V6 发布，广泛授权给大学
    
4. **1979 年**：V7 发布，取代 V6；V7 后来被微软买去改名叫 Xenix 卖了几年
    
5. **学术移植潮**：Wollongong 大学移植到 Interdata 7/32（1976）、Princeton 移植到 IBM PC（1978）、Toronto 移植到 LSI-11——这些移植证明了 C 语言可移植性的巨大价值
    

> 💡 **我的理解**：UNIX 历史的真正转折点是"用 C 写内核"这个决定。在 V6 之前，操作系统基本都是汇编写的；V6 之后，OS 进入了"高级语言时代"。**这个决定的深远影响远超技术本身**——它让操作系统知识可以被"传授"而不只是被"悟"，让 Lions 注释本成为可能，让一代代计算机学生能够通过读代码来学习操作系统。

### 1.3 UNIX V6内核

V6 内核是一个**宏内核（monolithic kernel）**，所有核心功能（进程管理、内存管理、文件系统、设备驱动、系统调用）都在同一个地址空间里。但它的"宏"是相对于今天的尺度而言的——实际上代码高度模块化：

- **进程管理**：`proc.c`、`slp.c`（sleep/wakeup）、`swtch.s`（上下文切换）
    
- **系统调用分发**：`sys.c`、`trap.c`
    
- **文件系统**：`filsys.c`、`iget.c`、`namei.c`
    
- **内存管理**：`malloc.c`、`swap.c`
    

整个内核小于 9000 行 C，**两个程序员（Ritchie 和 Thompson）就能维护**。

**工业联系**：今天的 Linux 宏内核在哲学上与 V6 一脉相承——所有核心功能在同一地址空间。但 Linux 引入了可加载内核模块（LKM）、微内核化的一些尝试（如 eBPF）。**V6 告诉我们：在资源受限时，宏内核是最务实的选择**。这也是为什么嵌入式系统、RTOS 至今仍偏好宏内核架构。

### 1.4 构成UNIX V6运行环境的硬件：PDP-11

这一节是整本书的"硬骨头"——不理解 PDP-11，你就不可能真正理解 V6 的进程模型。

**PDP-11 的关键特性**：

|特性|具体参数|对 V6 的影响|
|---|---|---|
|字长|16 位|指针只能是 16 位，限制地址空间|
|物理地址|18 位（11/40）|最大 256K 字内存|
|内存管理|无分页，有分段|V6 用"交换(swapping)"而非"分页(paging)"|
|I/O 架构|UNIBUS 内存映射|设备寄存器就是内存地址|
|寄存器|8 个通用寄存器 r0-r7|C 调用约定、上下文切换的基础|
|运行速度|< 1 MIPS，寄存器间传输 0.9μs|一切设计必须极度精简|

**PDP-11 的内存管理单元（MMU）**​ 是理解后续进程模型的关键：它提供 8 组段寄存器（PAR/PDR），每组描述一个 8K 字的分段。这就是 V6 实现"每个进程独立地址空间"的硬件基础——**没有 MMU 的 PDP-11 型号（如 11/20）根本跑不了 V6**。

> ⚠️ **关键认知**：V6 的"交换(swapping)"机制不是设计者的首选，而是 PDP-11 没有硬件分页支持下的妥协方案。**当硬件不支持页面级调度时，操作系统只能以"整个进程"为粒度在内存和磁盘间移动**。这就是为什么 V6 需要 proc（常驻）和 user（可换出）的分离——这个分离的本质原因是硬件约束。

**工业联系**：现代 CPU 都有 MMU 和分页支持，所以现代 OS 都用"按需分页(demand paging)"而非"交换"。但**交换的思想从未消失**——Linux 的 swap 机制、Android 的 LMK(Low Memory Killer)、iOS 的 Jetsam 都是"当内存不够时，把整个进程或进程的部分换出/杀死"思想的现代演化。理解 V6 的交换，你就理解了现代内存压力管理的"基因"。

### 1.5 代码

V6 的代码组织：

- **内核代码**：`/usr/sys` 目录下，约 44 个文件
    
- **头文件**：`proc.h`、`user.h`、`param.h` 等
    
- **汇编部分**：`m40.s`（PDP-11/40 专用）、`l.s`（通用底层）
    
- **C 部分**：进程管理、文件系统、系统调用等
    

代码风格极其朴素——没有复杂的抽象层，没有面向对象，就是**结构体 + 函数**的直接表达。这种"裸"的风格恰恰是它适合学习的原因。

### 1.6 手册

V6 手册首次采用"分章节编号"的格式（如 `1. 命令`、`2. 系统调用`），这套传统一直延续到今天的 UNIX 手册（`man 1` 到 `man 8`）。手册不仅告诉你怎么用，更是**内核接口的规格说明**。

> 💡 读书建议：配合 Lions 注释本一起读。Lions 的书是原典级资料，逐行解释 V6 内核，1996 年后解禁，现在可以在 TUHS (The Unix Heritage Society) 网站上自由获取。

### 1.7 小结

第1章的核心信息可以浓缩为一句话：**UNIX V6 是一个被硬件约束塑形的、极简的、用 C 语言写的、跑在 PDP-11 上的分时操作系统**。它的所有"优雅"都源于"简陋"——因为硬件简陋，所以软件必须聪明；因为代码量少，所以每个学生都能读完。

## 第II部分 进程 · 第2章 进程

### 2.1 进程的概要

#### 什么是进程

在 V6 中，**进程 = 一个正在执行的程序实例 + 它的执行状态 + 它的地址空间 + 它的资源上下文**。这不是抽象定义，而是具体的：当你在 shell 里敲下 `ls`，内核就创建一个进程——分配一个 proc 结构体、加载 ls 的可执行文件到内存、建立地址空间、开始执行。

**我的洞见**：进程的"第一性原理"是**"执行现场的可移植性"**——操作系统需要一种机制，能把"一个程序的运行状态"完整地保存下来、移动到别处、恢复执行。V6 用 proc + user + 地址空间 这三个东西的组合来实现这种"可移植性"。**现代操作系统的进程/线程/协程，本质上都是在解决"执行现场如何保存和恢复"这个问题，区别只在于粒度**。

#### 进程的并行执行

PDP-11 是单处理器，所以"并行"是**伪并行**——通过快速切换制造多个进程"同时运行"的假象。V6 用时间片 + 优先级调度来实现：

- 时钟中断周期性触发
    
- 调度器选择下一个进程
    
- 通过 `swtch()` 完成上下文切换
    

**工业联系**：今天的 CPU 多是多核的，真正的并行执行成为可能。但**调度器的核心思想没变**——时间片、优先级、就绪队列、等待队列，这些概念从 V6 一路传承到 Linux 的 CFS（Completely Fair Scheduler）。V6 的调度器只有几十行代码，Linux 的 CFS 有几千行，但**本质问题相同：如何在多个竞争执行单元之间公平且高效地分配 CPU**。

#### 进程的执行状态

V6 中进程有 6 种状态（定义在 proc.h 中）：

- `SSLEEP` (1)：在高优先级事件上睡眠
    
- `SWAIT` (2)：在低优先级事件上睡眠
    
- `SRUN` (3)：可运行
    
- `SIDL` (4)：进程创建中间态
    
- `SZOMB` (5)：进程终止中间态（僵尸进程）
    
- `SSTOP` (6)：被追踪停止
    

> 💡 **洞见**：注意 V6 只有 6 个状态，而现代 Linux 有 `TASK_RUNNING`、`TASK_INTERRUPTIBLE`、`TASK_UNINTERRUPTIBLE`、`TASK_STOPPED`、`TASK_TRACED`、`EXIT_ZOMBIE`、`EXIT_DEAD` 等十几种。**状态机的膨胀反映了操作系统复杂度的增加**——但 V6 的 6 态模型已经抓住了进程生命周期的本质：创建 → 就绪 → 运行 → 阻塞 → 终止。理解 V6 的 6 态，你就能理解现代 OS 状态机的"根"。

特别是 `SZOMB`（僵尸态）——进程已经退出但父进程还没调用 `wait()` 回收，此时进程占据 proc 表项但不占内存。这是 V6 的一个精妙设计：**让僵尸进程"轻量化"存在，直到父进程来收尸**。这个机制一直延续到现代 UNIX/Linux。

#### 用户模式和内核模式

PDP-11 通过 PSW（程序状态字）的某一位来区分两种模式：

- **用户模式**：只能访问自己的地址空间，不能执行特权指令
    
- **内核模式**：可以执行特权指令，可以访问所有内存
    

**切换时机**：

1. 系统调用（trap 指令）
    
2. 中断（时钟、I/O）
    
3. 异常（段错误等）
    

切换时，**CPU 特权级别改变，同时地址空间也切换**——MMU 重新加载段寄存器，指向内核空间或用户空间。

**关键设计**：每个进程有**两个栈**——

- **用户栈**：在用户模式下使用
    
- **内核栈**：在内核模式下使用，保存在 user 结构体中
    

为什么要两个栈？因为如果只用用户栈，一旦用户栈损坏，内核就无法执行；分离后，**即使用户栈崩了，内核仍能正常运行**。这是 V6 的一个容错设计，现代 OS 完全继承了这一思想。

> 💡 **工业联系**：xv6（MIT 用于教学的现代简化 OS）明确写道："A process's kernel stack is separate (and protected from user code) so that the kernel can execute even if a process has wrecked its user stack"——这句话几乎就是 V6 设计的现代复述。Linux 的 `task_struct` 里也有 `stack` 成员指向内核栈。**从 V6 到 Linux，40 多年过去了，这个设计没变过**。

#### 交换处理

因为 PDP-11 没有分页，当内存不足时，V6 只能把**整个进程**换出到磁盘交换区。这就是"交换(swapping)"。

- **换出**：把进程的 user 结构体 + 内核栈 + 数据段 + 用户栈 整体写到交换设备
    
- **换入**：当进程需要运行时，整体读回内存
    
- **swapper**：进程 0（调度器）负责交换决策
    

交换的粒度是"整个进程"——这是那个时代硬件限制下的必然选择。

**工业联系**：现代 OS 用"按需分页"替代了整体交换，但交换的思想仍在：

- Linux 的 `swap` 分区/文件：内存紧张时，把匿名页换出
    
- Android 的 LMK：内存不足时直接杀进程（比换出更激进）
    
- iOS 的 Jetsam：类似的机制
    

**我的理解**：从"整体交换"到"按需分页"再到"主动杀死进程"，**这是一条从硬件约束到用户体验优化的演进路线**。V6 教给我们的是这条路线的起点——理解起点，才能理解为什么现代 OS 要做那些复杂的优化。

### 2.2 proc结构体和user结构体

这是第2章最核心的内容，也是 V6 进程模型的精华所在。

#### proc结构体

`proc` 是每个进程的**常驻内存**的控制块。即使进程被换出到磁盘，它的 proc 结构体仍然留在内存中，因为调度器需要它来做决策。

```
struct proc{
    char p_stat;     // 进程状态
    char p_flag;     // 进程标志
    char p_pri;      // 优先级（负数高优先级）
    char p_sig;      // 收到的信号
    char p_uid;      // 用户id
    char p_time;     // 驻留时间（调度用）
    char p_cpu;      // CPU使用率（调度用）
    char p_nice;     // nice值（调度用）
    int  p_ttyp;     // 控制终端
    int  p_pid;      // 进程id
    int  p_ppid;     // 父进程id
    int  p_addr;     // 可交换映像地址
    int  p_size;     // 可交换映像大小（*64字节）
    int  p_wchan;    // 等待的事件
    int  *p_textp;   // 指向text结构体的指针
} proc[NPROC];
```

关键点：

- `NPROC` 定义为 50，即**系统最多 50 个进程**
    
- proc 数组是**静态大小**的
    
- **字段都是调度相关的**——状态、优先级、PID、父PID、内存位置等
    

> 💡 **第一性原理洞见**：为什么 proc 要常驻？因为**调度器需要随时能访问到所有进程的状态**，如果 proc 也被换出，调度器就无法工作了。所以 proc 里只放"调度所必需的最小信息集"。这是一种**极致的信息分类**——把"必须常驻的信息"和"可以换出的信息"彻底分开。

**这种分类思想在工业界的延续**：

- Linux 的 `task_struct` 相当于 proc + user 的组合，但内部仍然区分"调度相关字段"和"内存相关字段"
    
- 现代 OS 的"轻量级进程(LWP)"概念，本质是 proc 结构体的进化——把线程的控制块做得更小、切换更快
    

#### user结构体

`user` 是进程的**可交换部分**，包含进程的全部上下文信息。它**只在进程处于内核态时才被访问**，并且系统中同时只有一个 user 结构体可被 CPU 访问（通过全局变量 `_u` 指向当前进程的 user）。

```
struct user{
    int u_rsav[2];       // 切换时保存 r5, r6
    int u_fsav[25];      // 保存浮点寄存器
    char u_segflg;       // I/O标志：用户或内核空间
    char u_error;        // 错误码
    char u_uid;          // 有效用户id
    char u_gid;          // 有效组id
    char u_ruid;         // 真实用户id
    char u_rgid;         // 真实组id
    int  u_procp;        // 指向对应proc结构体的指针
    char u_base;         // I/O基址
    char u_count;        // I/O剩余字节数
    char u_offset[2];    // 文件偏移
    int  u_cdir;         // 当前目录inode
    int  u_ofile[NOFILE];// 打开文件表
    int  u_arg[5];       // 系统调用参数
    int  u_tsize;        // 代码段大小(*64)
    int  u_dsize;        // 数据段大小(*64)
    int  u_ssize;        // 栈段大小(*64)
    int  u_sep;          // I/D分离标志
    int  u_signal[NSIG]; // 信号处理
    int  u_utime;        // 用户态CPU时间
    int  u_stime;        // 内核态CPU时间
    int  u_ar0;          // 用户寄存器R0的地址
    // ... 还有更多字段
};
```

user 结构体的关键信息：

- 包含**当前进程的完整内核上下文**
    
- 与**内核栈共享同一块物理内存**（PDP-11 的 S6 段，大小为 USIZE*64=1K 字）
    
- 这部分叫做 **PPDA (Per Process Data Area)**
    

> 📌 **深度洞见**：proc 和 user 的分离，本质上是**"调度视角的进程"与"执行视角的进程"的分离**。
> 
> - proc 是给调度器看的：轻量、常驻、只包含决策所需信息
>     
> - user 是给执行体看的：完整、可换出、包含全部上下文
>     
> 
> **这是一个极具现代意义的架构决策**。今天的 Linux 虽然把两者合并为 `task_struct`，但在内部实现上依然遵循同样的逻辑——调度器只看 `task_struct` 中的调度字段，而进程切换时才加载完整的上下文。**V6 用"两个结构体"做到了现代 OS 用一个结构体分层做到的同一件事**。

**工业联系**：

- **Linux 的 `task_struct`**：约 1000 行结构定义，包含了 V6 的 proc + user 的所有信息，但增加了线程、命名空间、cgroup 等现代概念
    
- **Windows 的 `EPROCESS`/`ETHREAD`**：类似地分离了"进程控制块"和"线程控制块"
    
- **Solaris 的 `proc`/`user`**：几乎就是 V6 设计的直系继承
    

### 2.3 为进程分配的内存

#### 代码段

代码段（text segment）存放程序的机器指令，**只读、可共享**。多个进程运行同一个程序（如 `/bin/ls`）时，共享同一个代码段——这是 V6 的一个重要优化，节省内存。

在 proc 结构体中，`p_textp` 指向一个 `text` 结构体，记录：

- 有多少进程正在共享这个代码段
    
- 代码段在交换设备上的位置
    

#### 数据段

数据段（data segment）存放：

- 已初始化的全局变量
    
- 未初始化的全局变量（BSS）
    
- 堆（通过 `brk()`/`sbrk()` 扩展）
    

数据段是**私有的**——每个进程有自己的副本。

#### 虚拟地址空间

在 PDP-11 上，每个进程的虚拟地址空间由 MMU 的 8 组段寄存器定义。典型的布局（从低地址到高地址）：

```
低地址
├── 代码段 (Text)   - 只读，可共享
├── 数据段 (Data)   - 可读写，私有
├── 堆 (Heap)       - 向上增长
├── ... 空闲 ...
├── 用户栈 (Stack)  - 向下增长
高地址
```

内核空间位于虚拟地址空间的高部，用户程序无法直接访问。

> 💡 **洞见**：V6 的虚拟地址空间布局和现代 UNIX/Linux 几乎一样——代码段在低地址、栈在高地址、堆向上增长、栈向下增长。**这个布局不是 V6 发明的，但它通过 V6 固化成了 UNIX 系统的标准**。今天你用 `cat /proc/<pid>/maps` 看到的布局，和 1975 年 V6 进程的布局是同一个"物种"。

#### 变换地址

这是 V6 中非常硬件相关的一块。PDP-11 的 MMU 通过 **PAR (Page Address Register)**​ 和 **PDR (Page Description Register)**​ 来实现地址转换：

- PAR：指定该段在物理内存中的起始地址
    
- PDR：指定该段的长度和访问权限（读/写/执行）
    

在 V6 中，`user` 结构体里的 `u_uisa[16]` 和 `u_uisd[16]` 分别保存用户 PAR 和 PDR 的原型值。当进程被切换进来时，内核把这些值加载到 MMU 寄存器中。

**关键函数**：

- `estabur()`：设置用户地址空间寄存器
    
- `sureg()`：把 user 中的值加载到硬件寄存器
    

> 📌 **工业联系**：PAR/PDR 就是现代页表的"史前版本"。现代 CPU 用多级页表（x86 的 CR3 指向页表根），PDP-11 用 8 组段寄存器——**机制不同，目的相同：把虚拟地址翻译成物理地址**。理解 V6 的 PAR/PDR，你就能更好地理解现代 MMU 的设计哲学——它们都在解决同一个问题：**如何让每个进程看到自己独立的、连续的内存空间**。

### 2.4 小结

第2章的核心可以总结为三个递进的认知：

**第一层：进程是什么**

进程 = 执行现场 + 地址空间 + 资源上下文。在 V6 中，这三样东西分别由 proc 结构体（常驻）、user 结构体（可换出）、以及 PDP-11 的 MMU 段寄存器（定义地址空间）共同承载。

**第二层：为什么这么设计**

因为 PDP-11 的硬件限制：

- 内存小 → 必须能换出 → proc/user 分离
    
- 无分页 → 只能整体交换 → 进程是交换的基本单位
    
- 16 位地址 → 必须分段 → MMU 用 PAR/PDR
    

**第三层：这种设计的影响**

- **proc/user 的分离思想**​ → 现代 OS 的 PCB 分层设计
    
- **用户栈/内核栈分离**​ → 现代 OS 的容错基础
    
- **代码段共享**​ → 现代 OS 的动态链接、共享库
    
- **虚拟地址空间布局**​ → 今天所有 UNIX 系统的标准
    

> ⚠️ **给读者的特别提醒**：青柳隆宏的书在讲解 proc/user 时，非常注重"为什么这个信息放在 proc 而不是 user"的讨论。这才是读这本书的正确姿势——**不要只记字段，要问"为什么"**。每个字段的位置都是一次设计决策，每个决策背后都是硬件约束或性能考量。

## 跨章节的全局洞见

把第1章和第2章连起来看，会发现一条清晰的"设计约束链"：

```
PDP-11 硬件限制
    ↓
V6 的内核架构决策
    ↓
proc/user 结构体的划分
    ↓
进程模型的建立
    ↓
现代操作系统的基因
```

**这条链的第一性原理是：软件架构是硬件约束的函数**。V6 之所以是今天的样子，不是因为设计者聪明（他们当然聪明），而是因为 PDP-11 只允许它这么做。

当我们今天学习 V6 时，真正有价值的不只是"V6 是怎么做的"，更是"**V6 为什么必须这么做**"。前者让你了解历史，后者让你获得设计操作系统直觉。

**工业落地的三点启示**：

1. **约束催生优雅**：V6 的极简不是目标，而是约束的产物。今天我们在设计系统时（无论是 OS、数据库还是分布式系统），也应该主动给自己设约束——"如果内存只有 256K，我会怎么设计？"这种思维训练能帮你剔除伪需求。
    
2. **信息分类是架构的核心**：proc/user 的分离告诉我们，**把"常驻信息"和"可交换信息"分开，是管理有限资源的关键手段**。这个思想在现代缓存设计、内存分级管理中无处不在。
    
3. **硬件意识不可丢失**：今天很多系统程序员不熟悉硬件了，但 V6 告诉我们——**不懂硬件，就懂不了操作系统的本质**。MMU、寄存器、中断控制器，这些是操作系统的"物理定律"，绕不开。
