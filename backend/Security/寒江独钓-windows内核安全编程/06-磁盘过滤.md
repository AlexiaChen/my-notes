## 6.1 磁盘过滤驱动的概念

### 6.1.1 设备过滤和类过滤

**📌 书中的世界**

Windows 的存储栈支持两种过滤驱动：

- **设备过滤驱动（Device Filter）**：挂到特定设备对象上，只过滤该设备的 I/O
- **类过滤驱动（Class Filter）**：挂到整个设备类上，过滤该类所有设备的 I/O

对于磁盘，类过滤驱动通过在注册表 `HKLM\SYSTEM\CurrentControlSet\Control\Class\{4D36E967-E325-11CE-BFC1-08002BE10318}` 下的 `UpperFilters` 或 `LowerFilters` 值来加载——这正是磁盘类的 GUID。

**🔍 第一性原理视角：过滤的"作用域"决定了工程的复杂度**

- 设备过滤：作用域窄、影响小、调试容易，但需要对每个设备单独安装
- 类过滤：作用域广、一劳永逸，但一旦有 bug，全盘受影响——甚至可能导致系统无法启动

微软的 `addfilter` 示例明确警告：如果在启动盘上添加无效的过滤驱动然后重启，系统可能出现 **INACCESSIBLE_BOOT_DEVICE**​ 错误，必须用"最后一次正确配置"才能恢复。

> ⚠️ **工业级教训**：还原驱动通常选择**卷设备过滤**（挂在 `Volume` 类上），而不是磁盘设备过滤。为什么？因为卷是"分区"的抽象，挂在这里可以做到"只还原 C 盘而不动 D 盘"的精细化控制。

### 6.1.2 磁盘设备和磁盘卷设备过滤驱动

**📌 书中的世界**

Windows 存储栈是一个典型的分层架构。微软官方文档明确描述了这种分层：

- **存储端口驱动（Port Driver）**：如 `storport.sys`、`atapi.sys`，把 SRB 转换成总线特定命令发给 HBA
- **存储类驱动（Class Driver）**：如 `disk.sys`，把标准 IRP 翻译成带 CDB 的 SRB
- **存储过滤驱动（Filter Driver）**：上下层过滤驱动都可以存在，监控并修改 SRB/IRP

**🔍 第一性原理视角：在存储栈的哪一层挂过滤，决定了你能看到什么**

```
[用户态/内核态组件]
    ↓
[文件系统驱动 ntfs.sys / fastfat.sys]
    ↓
[卷设备对象 Volume]
    ↓  ← 挂在这里：看到的是"卷层面的扇区 I/O"
[磁盘类驱动 disk.sys]
    ↓  ← 挂在这里：看到的是"整块物理磁盘的扇区 I/O"
[存储端口驱动 storport.sys / atapi.sys]
    ↓
[物理硬件]
```

**关键认知**：不管挂在哪一层，磁盘过滤驱动看到的都是**扇区级别的读写**，不是文件。文件路径、文件名称、文件属性这些信息在文件系统层（ntfs.sys）才被解析。所以还原驱动在卷层过滤时：

- 能看到：哪个扇区被读/写、写了多少字节、写到哪个偏移
- 看不到：这个扇区属于哪个文件、文件名是什么

> 💡 **洞见**：这就是为什么"磁盘还原"和"文件防篡改"是两个不同的工程——前者在卷/磁盘层做扇区重定向，后者必须在文件系统层做。现代工业界做防勒索、文件审计、DLP，用的都是**文件系统微过滤驱动（Minifilter）**，而不是磁盘过滤驱动。

### 6.1.3 注册表和磁盘卷设备过滤驱动

**📌 书中的世界**

书中详细介绍了通过注册表安装磁盘卷过滤驱动的机制：

- 在 `Control\Class\{71A27CDD-812A-11D0-BEC7-08002BE2092F}`（卷类 GUID）下添加 `UpperFilters` 值
- 系统在启动时自动加载该过滤驱动，并调用其 `AddDevice`

**🏭 现代工业实践**

微软官方文档对注册表安装过滤驱动的描述非常清晰：类过滤驱动通过在类注册表项下设置 `UpperFilters` 或 `LowerFilters` 多字符串值来加载。这种方式至今仍是磁盘/卷过滤驱动的标准安装方法。

> ⚠️ **生产环境硬约束**：
> 
> - 过滤驱动必须签名（EV 证书 + WHQL）
> - `UpperFilters` 值写错一个字母，相关设备就可能消失
> - 错误的过滤驱动挂在启动卷上 = 系统无法启动
> - 这也是为什么现代还原软件（如 冰点/Deep Freeze、Shadow Defender）的安装程序极度谨慎——它们知道自己在玩火

## 6.2 具有还原功能的磁盘卷过滤驱动

### 6.2.1 简介

**📌 书中的世界**

本章要实现的目标：一个磁盘卷上层过滤驱动，挂载后对所有写入卷的扇区做"重定向"，使得原始扇区数据不被修改；重启后，所有写入丢失，卷恢复到初始状态。这就是"还原卡"的内核核心。

**🔍 第一性原理视角：还原的本质是"写时复制（Copy-on-Write）"**

这和操作系统内存管理的 CoW、虚拟机的快照技术、Docker 的 overlay 文件系统，是**同一个第一性原理**：

- 读取时：如果扇区未被修改，返回原始数据；如果已被修改，返回重定向数据
- 写入时：不直接写原始位置，而是写到"差异区域"，并记录"该扇区已修改"

**🏭 现代工业实践**

"还原"技术在工业界有多种实现层级：

|实现层级|技术方案|典型产品|
|---|---|---|
|磁盘卷过滤驱动|扇区级 CoW|早期还原卡|
|文件系统微过滤|文件级 CoW|Volume Shadow Copy|
|存储栈虚拟化|块级 CoW|VHDX diff disk|
|虚拟机快照|整机 CoW|VMware Snapshot|
|用户态 overlay|文件级 overlay|Docker overlayfs|

### 6.2.2 基本思想

**📌 书中的世界**

核心算法伪代码：

```
写请求(Sector X):
    if (Bitmap[X] == 0) {  // 该扇区尚未被重定向
        Bitmap[X] = 1;     // 标记为已修改
        分配差异区域的一块空间 DiffY;
        SectorMap[X] = DiffY;  // 记录映射关系
    }
    实际写入到 DiffY;  // 而不是 Sector X

读请求(Sector X):
    if (Bitmap[X] == 1) {
        从 DiffY (= SectorMap[X]) 读取;
    } else {
        从原始 Sector X 读取;
    }
```

**🔍 第一性原理视角：还原 = 状态机 + 重定向 + 查表**

这三个要素缺一不可：

1. **状态机（Bitmap）**：记录每个扇区是否被修改
2. **重定向（Diff Area）**：实际写入隐藏的差异存储区
3. **查表（Sector Map）**：维护"原始扇区 ↔ 差异扇区"的映射

> 💡 **洞见**：这套思想几乎是所有"快照/还原/差异存储"技术的通用模板。理解了这个模板，你就能看懂 VHDX 的 differencing disk、ZFS 的 snapshot、Git 的对象存储、Docker 的 layer——它们都是这个思想的变体。

## 6.3 驱动分析

### 6.3.1 DriverEntry 函数

**📌 书中的世界**

WDM 过滤驱动的 `DriverEntry` 要做的事：

1. 设置 `DriverObject->DriverExtension->AddDevice = AddDevice`
2. 设置 `DriverUnload`（如果需要支持动态卸载）
3. 填写 `MajorFunction` 数组——**过滤驱动必须为所有可能的 IRP 类型提供派遣函数**

**🔍 第一性原理视角：为什么过滤驱动要"全量填写"MajorFunction？**

普通功能驱动只需要处理它关心的 IRP 类型。但过滤驱动不同——微软 WDM 编程指南明确指出：

> "A filter driver has to support all the same IRP types that the driver immediately underneath it supports. If a filter were to leave a particular MajorFunction table entry in its default state, IRPs of that type would get failed with STATUS_INVALID_DEVICE_REQUEST."

换句话说：**过滤驱动是"透明中间件"**——它不处理的 IRP 也必须"透传"下去，而不是让 I/O 管理器用默认的 `STATUS_INVALID_DEVICE_REQUEST` 完成。所以 `DriverEntry` 中通常这样做：

```
for (int i = 0; i < ARRAYSIZE(DriverObject->MajorFunction); i++) {
    DriverObject->MajorFunction[i] = DispatchPassThrough;  // 默认透传
}
DriverObject->MajorFunction[IRP_MJ_PNP] = DispatchPnp;
DriverObject->MajorFunction[IRP_MJ_POWER] = DispatchPower;
DriverObject->MajorFunction[IRP_MJ_READ] = DispatchRead;
DriverObject->MajorFunction[IRP_MJ_WRITE] = DispatchWrite;
DriverObject->MajorFunction[IRP_MJ_DEVICE_CONTROL] = DispatchDeviceControl;
```

**🏭 现代工业实践**

现代还原驱动仍遵循这一模式，但需要额外注意：

- Windows 10 1607+ 可以注册表禁用遗留文件系统过滤驱动
- 虽然磁盘卷过滤驱动不属于"文件系统过滤驱动"，但微软趋势是**推动所有过滤驱动走向更规范的模型**
- 新的存储过滤驱动应考虑使用 **WDF 存储过滤框架**简化开发

### 6.3.2 AddDevice 函数

**📌 书中的世界**

`AddDevice` 是过滤驱动"附着"到目标设备栈的核心：

```
NTSTATUS AddDevice(
    PDRIVER_OBJECT DriverObject,
    PDEVICE_OBJECT PhysicalDeviceObject)  // 注意：这里是 PDO
{
    // 1. 创建无名过滤设备对象
    IoCreateDevice(DriverObject, sizeof(DEVICE_EXTENSION),
        NULL,  // 过滤设备对象必须无名！
        PhysicalDeviceObject->DeviceType,  // 必须与下层设备类型一致
        0, FALSE, &filterDeviceObject);
    
    // 2. 附着到设备栈
    PDEVICE_OBJECT lowerDevice = 
        IoAttachDeviceToDeviceStack(filterDeviceObject, PhysicalDeviceObject);
    
    // 3. 复制下层设备的标志
    filterDeviceObject->Flags |= 
        lowerDevice->Flags & (DO_DIRECT_IO | DO_BUFFERED_IO | DO_POWER_PAGABLE);
    
    // 4. 初始化设备扩展
    deviceExtension->LowerDevice = lowerDevice;
    deviceExtension->PhysicalDevice = PhysicalDeviceObject;
    
    // 5. 初始化移除锁
    IoInitializeRemoveLock(&deviceExtension->RemoveLock, ...);
    
    // 6. 清除 DO_DEVICE_INITIALIZING 标志
    filterDeviceObject->Flags &= ~DO_DEVICE_INITIALIZING;
}
```

**🔍 第一性原理视角：AddDevice 的五件事**

微软官方文档明确列出了 WDM 过滤驱动 `AddDevice` 的标准步骤：

1. **IoCreateDevice 创建无名过滤设备**——过滤设备对象永远不能有名字，否则会造成安全漏洞
2. **IoAttachDeviceToDeviceStack 附着**——把自己插入到设备栈中
3. **复制下层设备的 DeviceType 和 Flags**——保证 I/O 管理器和下层行为一致
4. **存储 PDO 指针到设备扩展**——后续 PnP 操作要用
5. **初始化移除锁（IO_REMOVE_LOCK）**——防止设备在被移除时还有未完成的 IRP

> 💡 **洞见**：`IoAttachDeviceToDeviceStack` 这个函数名其实有点误导——它并不是"附着到设备栈"，而是"附着到 PDO 所在设备栈的最顶层"。调用后，你的过滤设备就位于设备栈顶部，所有发往该设备栈的 IRP 都会先经过你的派遣函数。

**🏭 现代工业实践**

现代过滤驱动开发的最佳实践：

- 使用 **WDF 框架**的 `WdfFdoInitBindToIoQueue` 等 API 简化附着逻辑
- 使用 **WDF 移除锁**（`WDF_REMOVE_LOCK`）替代裸的 `IO_REMOVE_LOCK`
- 设备扩展中的状态信息需要考虑 **多核同步**（自旋锁或 WDF 自旋锁）

### 6.3.3 PnP 请求的处理

**📌 书中的世界**

PnP IRP 的处理是过滤驱动最棘手的部分。还原驱动需要正确处理以下 PnP 次功能码：

- `IRP_MN_START_DEVICE`：启用设备接口
- `IRP_MN_QUERY_STOP_DEVICE` / `IRP_MN_STOP_DEVICE`：处理设备暂停/停止
- `IRP_MN_QUERY_REMOVE_DEVICE` / `IRP_MN_REMOVE_DEVICE`：处理设备移除
- `IRP_MN_SURPRISE_REMOVAL`：处理意外移除

**🔍 第一性原理视角：PnP 处理的"黄金法则"**

过滤驱动对 PnP IRP 的处理原则是：

1. **先下发，后完成**——大多数 PnP IRP 需要先 `IoSkipCurrentIrpStackLocation` + `IoCallDriver` 下发，等下层处理完，再在上层的完成例程中做自己的清理
2. **REMOVE_DEVICE 时必须等待所有 IRP 完成**——通过移除锁 `IoReleaseRemoveLockAndWait` 实现
3. **不能阻止设备移除**——过滤驱动没有权利拒绝 PnP 管理器的移除请求

**关键代码片段**：

```
case IRP_MN_REMOVE_DEVICE:
    // 1. 先下发，让下层先处理
    IoSkipCurrentIrpStackLocation(Irp);
    status = IoCallDriver(devExt->LowerDevice, Irp);
    
    // 2. 等待所有 IRP 完成
    IoReleaseRemoveLockAndWait(&devExt->RemoveLock, Irp);
    
    // 3. 清理资源
    IoDetachDevice(devExt->LowerDevice);
    IoDeleteDevice(DeviceObject);
    return status;
```

> ⚠️ **工业级陷阱**：如果在 `IRP_MN_REMOVE_DEVICE` 时还有未完成的读写 IRP，直接 `IoDeleteDevice` 会导致系统崩溃。这就是为什么必须使用 `IoReleaseRemoveLockAndWait`——它阻塞直到所有持有移除锁的 IRP 都释放。

**🏭 现代工业实践**

WDF 框架把 PnP 处理大幅简化了：

- 通过 `WDF_PNPPOWER_EVENT_CALLBACKS` 结构注册回调
- `EvtDevicePrepareHardware`、`EvtDeviceD0Entry`、`EvtDeviceD0Exit` 等事件回调
- 框架自动处理 PnP 状态机，驱动作者只需关注业务逻辑

但作为安全研究者，理解 WDM 的 PnP 机制仍然是必要的——因为：

- 你需要能够读懂任何第三方驱动的行为
- Rootkit 常常利用 PnP 回调做"隐身"或"持久化"
- EDR 需要监控 PnP 事件来检测可疑设备活动

### 6.3.4 Power 请求的处理

**📌 书中的世界**

电源 IRP 的处理相对简单——过滤驱动通常只需要"透传"：

```
NTSTATUS DispatchPower(PDEVICE_OBJECT DeviceObject, PIRP Irp) {
    // 直接透传，不关心电源状态变化
    IoSkipCurrentIrpStackLocation(Irp);
    return IoCallDriver(devExt->LowerDevice, Irp);
}
```

**🔍 第一性原理视角：为什么电源 IRP 通常透传？**

电源管理是"设备功能"的一部分，过滤驱动一般不改变设备的电源行为。但要注意：

- 如果过滤驱动分配了非分页内存或其他硬件资源，可能需要在 `IRP_MN_SET_POWER` 时做相应处理
- 还原驱动的差异区域如果在休眠/睡眠时需要特殊处理，就要拦截 `IRP_MN_QUERY_POWER` 和 `IRP_MN_SET_POWER`

> 💡 **洞见**：电源 IRP 看似简单，但它揭示了驱动开发的哲学——**"你知道得越少越好"**。过滤驱动尽量不介入它不理解的领域，只做自己职责范围内的事。

### 6.3.5 DeviceIoControl 请求的处理

**📌 书中的世界**

`IRP_MJ_DEVICE_CONTROL` 是用户态程序与内核驱动"对话"的主要通道。还原驱动需要定义私有 IOCTL 来实现：

- 启用/禁用还原
- 查询差异区域使用情况
- 强制提交（把差异写入原始位置）
- 强制还原（丢弃所有差异）
- 查询某个扇区是否被修改

**🔍 第一性原理视角：IOCTL 是"控制平面"，读写 IRP 是"数据平面"**

这是网络工程中"控制平面与数据平面分离"思想在内核驱动中的体现：

- **数据平面**（READ/WRITE IRP）：高速、频繁、需要极致性能
- **控制平面**（DeviceIoControl）：低频、需要严格的权限和参数校验

**IOCTL 处理的安全要点**：

```
NTSTATUS DispatchDeviceControl(PDEVICE_OBJECT DeviceObject, PIRP Irp) {
    PIO_STACK_LOCATION irpSp = IoGetCurrentIrpStackLocation(Irp);
    ULONG controlCode = irpSp->Parameters.DeviceIoControl.IoControlCode;
    ULONG inputLen = irpSp->Parameters.DeviceIoControl.InputBufferLength;
    ULONG outputLen = irpSp->Parameters.DeviceIoControl.OutputBufferLength;
    
    switch (controlCode) {
    case IOCTL_ENABLE_RESTORE:
        // 严格校验：inputLen >= sizeof(ENABLE_PARAMS)
        // 权限检查：是否管理员
        // 参数合法性：卷是否合法
        break;
    case IOCTL_COMMIT_CHANGES:
        // 危险操作！需要二次确认
        break;
    // ...
    }
}
```

> ⚠️ **工业级安全约束**：
> 
> - 所有来自用户态的输入都是**不可信的**——必须严格验证长度、地址、权限
> - 私有 IOCTL 的调用者必须是可信的用户态服务
> - 危险操作（如强制提交/还原）需要多重确认机制
> - 任何整数运算都可能溢出——使用 `RTL_NUMBER_OF` 等安全宏

**🏭 现代工业实践**

现代还原/安全产品的控制通道架构：

```
用户态服务（GUI/CLI）
    ↓ DeviceIoControl
内核过滤驱动
    ↓ 共享内存 / 事件
内核数据平面（READ/WRITE 拦截）
```

这种"控制平面与数据平面分离"的架构使得：

- 高频的读写拦截走"快速路径"（直接在内核完成）
- 低频的策略控制走"慢速路径"（通过 IOCTL 下发）
- 用户态服务可以做复杂的策略决策（与云端通信、UI 交互）

### 6.3.6 bitmap 的作用和分析

**📌 书中的世界**

Bitmap 是还原驱动的"核心状态机"——每一位对应卷中的一个扇区（或一块），记录该扇区是否被修改过。

**数据结构设计**：

```
#define SECTOR_SIZE 512
#define BITMAP_BITS_PER_BYTE 8

// 假设卷大小为 volumeSize 字节
// 需要 volumeSize / SECTOR_SIZE 位来记录所有扇区
// 即 volumeSize / SECTOR_SIZE / 8 字节的 bitmap

struct _DEVICE_EXTENSION {
    PUCHAR Bitmap;           // 位图，每位对应一个扇区
    ULONG BitmapSize;        // 位图大小（字节）
    ULONG SectorsPerBitmapBit;  // 一个 bit 对应几个扇区（可调整粒度）
    PVOID DiffArea;          // 差异区域（隐藏的存储区）
    ULONG DiffAreaSize;      // 差异区域大小
    // ...
};
```

**🔍 第一性原理视角：Bitmap 是"空间换时间"的经典权衡**

- **时间复杂度**：O(1) 查询任意扇区是否被修改
- **空间开销**：每 GB 卷需要 256KB 位图（如果每 bit 对应 1 个 512 字节扇区）
- **粒度选择**：粗粒度（1 bit = 多个扇区）省内存但浪费差异空间；细粒度（1 bit = 1 扇区）精确但耗内存

**Bitmap 操作的原子性挑战**：

```
// 在 DISPATCH_LEVEL 设置 bit 必须原子操作
InterlockedBitTestAndSet((LONG*)Bitmap, sectorIndex);
```

> 💡 **洞见**：Bitmap 的设计揭示了系统工程的一个普适真理——**没有"完美的数据结构"，只有"适合场景的数据结构"**。还原驱动选择 Bitmap，是因为：
> 
> - 查询频率极高（每次读写都要查）
> - 内存预算有限（Bitmap 必须常驻非分页内存）
> - 更新操作简单（置位/清零）
> 
> 这与 Redis 的 Bitmap 类型、Bloom Filter、Linux 的页表脏位跟踪，是同一个工程哲学的不同表现。

**🏭 现代工业实践**

现代还原/快照系统的元数据管理更加复杂：

- **B+ 树或 Radix Tree**：替代简单 Bitmap，支持稀疏表示（大部分扇区未被修改时不占内存）
- **持久化 Bitmap**：Bitmap 本身需要持久化到磁盘，重启后恢复还原状态
- **增量快照链**：不仅记录"是否与原始不同"，还记录"与上一快照的差异"
- **COW 元数据**：Bitmap 本身的更新也采用 CoW，避免 Bitmap 损坏导致整个还原系统失效

GitHub 上的 `difi` 项目（Windows 磁盘过滤驱动 PoC）展示了类似的思路：它拦截读写，把写入重定向到磁盘上的隐藏区域，并为重定向的扇区创建映射表。这正是书中还原驱动的"现代开源版本"——只不过 `difi` 用的是 extent 映射而非简单 Bitmap。

### 6.3.7 boot 驱动完成回调函数和稀疏文件

**📌 书中的世界**

"boot 驱动完成回调"指的是：在系统启动过程中，还原驱动需要在某个关键时刻执行初始化——比如分配差异区域、加载 Bitmap、建立扇区映射表。由于还原驱动通常在启动早期就需要生效（否则启动过程中的写入就无法被拦截），它往往作为**启动启动驱动（Boot Start Driver）**，并在 `DriverEntry` 或某个 PnP 回调中完成关键初始化。

"稀疏文件"则是差异区域的理想存储形式——在 NTFS 上，稀疏文件允许"逻辑上很大但实际占用很小"的文件。未被写入的部分不占磁盘空间，只有实际写入的块才分配物理簇。

**🔍 第一性原理视角：稀疏文件是"惰性分配"的典范**

```
差异区域（稀疏文件，逻辑大小 = 卷大小）
    ↓
[未写入区域] → 不占物理空间
[已写入区域] → 分配实际簇，存入重定向数据
```

稀疏文件的优势：

- **空间效率**：只有被实际修改的扇区才占用差异空间
- **时间效率**：预分配差异区域时不需要真的写满整个区域
- **与 Bitmap 天然配合**：Bitmap 中未置位的扇区，对应的稀疏文件区域就是"空洞"

**稀疏文件的实现**：

```
// 用户态服务通过 DeviceIoControl 告诉驱动差异区域信息
// 驱动在内部维护：
// - Bitmap（哪些扇区被修改）
// - 稀疏文件句柄（实际存储重定向数据）
// - 扇区映射表（原始扇区 → 稀疏文件偏移）
```

**🏭 现代工业实践**

现代还原系统的差异存储管理：

- **NTFS 稀疏文件**：利用 `FSCTL_SET_SPARSE` 创建稀疏文件
- **ReFS 块克隆**：Windows Server 2016+ 的 ReFS 支持块级去重和克隆
- **VHDX 差异磁盘**：把差异区域做成一个 VHDX diff disk，由 Hyper-V 的 VHD 服务提供者管理
- **持久化策略**：Bitmap 和扇区映射表本身也需要持久化——通常存储在卷的保留区域或单独的隐藏文件

### 6.3.8 读/写请求的处理

**📌 书中的世界**

这是还原驱动的"心脏"——所有读写 IRP 都在这里被拦截和重定向。

**写请求处理**：

```
NTSTATUS DispatchWrite(PDEVICE_OBJECT DeviceObject, PIRP Irp) {
    PDEVICE_EXTENSION devExt = ...;
    PIO_STACK_LOCATION irpSp = IoGetCurrentIrpStackLocation(Irp);
    
    LARGE_INTEGER offset = irpSp->Parameters.Write.ByteOffset;
    ULONG length = irpSp->Parameters.Write.Length;
    ULONG startSector = offset.QuadPart / SECTOR_SIZE;
    ULONG sectorCount = length / SECTOR_SIZE;
    
    // 1. 为每个扇区做重定向
    for (ULONG i = 0; i < sectorCount; i++) {
        ULONG sector = startSector + i;
        
        // 2. 检查 Bitmap
        if (!IsSectorModified(devExt, sector)) {
            // 3. 分配差异区域
            ULONG diffOffset = AllocateDiffSector(devExt);
            
            // 4. 更新 Bitmap 和映射表
            SetSectorModified(devExt, sector);
            devExt->SectorMap[sector] = diffOffset;
        }
        
        // 5. 修改 IRP 的写入目标为差异区域
        // 这需要构造新的 IRP 或使用 IRP 完成例程
    }
    
    // 6. 下发修改后的 IRP
    IoSkipCurrentIrpStackLocation(Irp);
    return IoCallDriver(devExt->LowerDevice, Irp);
}
```

**读请求处理**：

```
NTSTATUS DispatchRead(PDEVICE_OBJECT DeviceObject, PIRP Irp) {
    PDEVICE_EXTENSION devExt = ...;
    PIO_STACK_LOCATION irpSp = IoGetCurrentIrpStackLocation(Irp);
    
    LARGE_INTEGER offset = irpSp->Parameters.Read.ByteOffset;
    ULONG length = irpSp->Parameters.Read.Length;
    ULONG startSector = offset.QuadPart / SECTOR_SIZE;
    ULONG sectorCount = length / SECTOR_SIZE;
    
    // 1. 设置完成例程
    IoSetCompletionRoutine(Irp, ReadCompletionRoutine, 
        devExt, TRUE, TRUE, TRUE);
    
    // 2. 下发 IRP
    return IoCallDriver(devExt->LowerDevice, Irp);
}

NTSTATUS ReadCompletionRoutine(
    PDEVICE_OBJECT DeviceObject, PIRP Irp, PVOID Context) 
{
    PDEVICE_EXTENSION devExt = Context;
    
    if (Irp->PendingReturned)
        IoMarkIrpPending(Irp);
    
    // 3. 在完成例程中检查：哪些扇区被重定向？
    // 如果被读取的扇区中有被修改过的，需要从差异区域读取数据
    // 并替换 SystemBuffer 中的对应部分
    
    // 4. 对于被修改的扇区，构造新的 IRP 从差异区域读取
    // 或用 KeStallExecutionProcessor 暂停处理器直接拷贝
    
    // 5. 或者直接在当前完成例程中修改 Irp->AssociatedIrp.SystemBuffer
    // 把被重定向扇区的数据替换为差异区域的数据
    
    return STATUS_SUCCESS;  // 或 STATUS_MORE_PROCESSING_REQUIRED
}
```

**🔍 第一性原理视角：读写重定向的三个技术难题**

**难题一：写重定向的"原子性"**

一个 WRITE IRP 可能跨越多个扇区。如果只重定向了其中一部分，系统崩溃了怎么办？

- 解决方案：使用 Bitmap 的"预置位"策略——先置位所有相关 bit，再执行重定向写入。如果崩溃发生在置位后、写入前，重启后该扇区被视为"已修改"，从差异区域读取（差异区域此时可能是垃圾数据）
- 更好的方案：使用日志（Journaling）——先写日志，再改 Bitmap，最后做重定向

**难题二：读完成时的"数据拼装"**

一个 READ IRP 读取的数据可能混合了"原始扇区"和"重定向扇区"。完成例程中需要：

- 检查每个扇区是否在 Bitmap 中标记为已修改
- 对已修改的扇区，从差异区域读取正确数据
- 拼装成完整的读取缓冲区返回给用户

微软的存储过滤驱动文档明确指出：存储过滤驱动的 I/O 完成例程可以使用 `STATUS_MORE_PROCESSING_REQUIRED` 来阻止完成处理，或者保留原始 IRP 以便驱动在重用 IRP 之前进行处理。这意味着在读完成例程中，我们可以安全地修改数据。

**难题三：IRQL 与内存约束**

- 读写分发函数在 `PASSIVE_LEVEL` 或 `APC_LEVEL` 调用（对于卷设备）
- 完成例程可能在 `DISPATCH_LEVEL` 调用
- 因此：所有数据结构（Bitmap、SectorMap、DiffArea 指针）必须位于**非分页内存**
- 任何在完成例程中访问的数据都不能被分页

> ⚠️ **工业级陷阱**：
> 
> - 不要在完成例程中调用 `IoDeleteDevice`——必须在 `PASSIVE_LEVEL`
> - 不要在完成例程中访问分页内存
> - 不要在完成例程中做复杂计算——会影响系统性能
> - 注意递归 I/O：如果在完成例程中发起新的 I/O，可能形成无限循环

**🏭 现代工业实践**

现代还原/CoW 系统在读写处理上的优化：

|优化方向|技术手段|
|---|---|
|减少 Bitmap 查询开销|使用 64-bit 原子操作批量处理|
|加速扇区映射|使用 Radix Tree 替代线性数组|
|减少内存占用|稀疏 Bitmap + 按需加载|
|提高 I/O 性能|批量重定向 + I/O 合并|
|保证崩溃一致性|日志结构 + 检查点|

微软存储过滤驱动的 I/O 完成例程文档指出，存储过滤驱动（SFD）的 I/O 完成例程在较低层驱动调用 `IoCompleteRequest` 时被调用。这意味着我们可以在 I/O 完成例程中做数据转换和处理。

## 🎯 本章核心洞见总结

读完第6章，我希望你带走的不只是"怎么写一个还原过滤驱动"，而是这四个**第一性原理**：

**1. 还原的本质是"写时复制"，这是跨层级的通用原理**

从 CPU 内存管理（fork 的 CoW）、到文件系统（VHDX diff disk）、到容器（Docker overlay）、到磁盘卷过滤（本章还原驱动）——**"首次写入时重定向，读取时查表返回"**​ 这个思想贯穿了整个计算技术栈。理解了这个思想，你就能理解一大类"快照/还原/差异"技术。

**2. 在存储栈的哪一层做过滤，决定了你能看到什么**

```
应用层（文件路径、文件名）
    ↓  ← 文件系统微过滤驱动（Minifilter）在这里工作
文件系统（ntfs.sys）
    ↓
卷设备（Volume）← 本章的磁盘卷过滤驱动在这里工作
    ↓  ← 看到的是"扇区级 I/O"
磁盘类驱动（disk.sys）
    ↓  ← 看到的是"整块磁盘的扇区级 I/O"
存储端口驱动（storport.sys）
    ↓
硬件
```

**关键认知**：如果你要做"文件防篡改/防勒索/DLP"——用**文件系统微过滤驱动（Minifilter）**，因为它能看到文件路径。如果你要做"磁盘还原/快照"——用**磁盘卷过滤驱动**，因为它工作在更底层，能拦截所有写入（包括绕过文件系统的直接扇区写入）。

**3. 现代工业界的选择：Minifilter > Legacy Filter**

微软官方明确建议：新的文件系统过滤驱动应该使用 Minifilter 模型，而不是 Legacy 过滤驱动。从 Windows 10 1607 开始，管理员甚至可以通过注册表设置**阻止遗留文件系统过滤驱动加载**。

这意味着：

- 书中这种 Legacy 风格的磁盘卷过滤驱动，在现代 Windows 上**仍然有效**（因为它过滤的是卷设备，不是文件系统）
- 但如果要做文件级安全产品，必须用 Minifilter
- 还原驱动这种"卷级 CoW"场景，Legacy 模型仍然适用，但现代实现会考虑用 WDF 框架简化开发

**4. 过滤驱动的"透明性原则"**

过滤驱动的核心职业道德是"透明"：

- 不处理的 IRP 必须透传
- 不能改变 IRP 的语义（除非这是驱动的目的，如还原驱动）
- 不能阻止设备的正常 PnP/电源操作
- 不能在完成例程中做危险操作

还原驱动是过滤驱动中的"异类"——它的目的就是**改变语义**（把写入重定向）。这种"有意的不透明"必须非常小心地实现，否则一个 bug 就会导致数据损坏或系统崩溃。

### 从书中环境到现代工业环境的迁移清单

|书中技术 (Win7/Vista 时代)|现代工业做法 (Win10/11)|说明|
|---|---|---|
|Legacy 磁盘卷过滤驱动|WDF 存储过滤驱动|更安全、更易维护|
