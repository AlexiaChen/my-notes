## 3.1 过滤的概念

### 3.1.1 设备绑定的内核 API 之一

**📌 书中的世界**

书中第一个介绍的绑定 API 是 `IoAttachDevice()`。它接受三个参数：我们自己创建的过滤设备对象（SourceDevice）、目标设备的名字（TargetDevice，是个 `UNICODE_STRING`）、以及输出参数 AttachedDevice（返回绑定后的设备栈顶端）。

**🔍 第一性原理视角：绑定 = 在设备栈顶端"插队"**

"过滤"这个词在安全领域容易被误解为"Hook"或"Patch"——但 Windows 的过滤驱动走的是完全合法的路线：**I/O 管理器本来就支持设备栈，你的过滤设备对象只要挂到栈顶，后续的 IRP 就会先经过你**。

`IoAttachDevice` 的语义是：

1. 根据名字找到目标设备对象
2. 把你的过滤设备对象插入到这个目标设备的设备栈**最顶端**
3. 返回"你挂上去之后，你下方那个设备对象"的指针（也就是原来的栈顶）

这样，任何发往原设备的 IRP，都会先到达你的过滤设备，再由你决定是放过、修改、还是拒绝。

**🏭 现代工业实践**

`IoAttachDevice` 是较早期的 API，现代微软官方推荐使用的是 **`IoAttachDeviceToDeviceStackSafe`**——它在绑定过程中做了更好的安全检查，尤其是在目标设备正在卸载的情况下，比老的 `IoAttachDevice` 和 `IoAttachDeviceToDeviceStack` 都更安全。CSDN 上的驱动开发笔记也明确指出：「官方建议使用 `IoAttachDeviceToDeviceStackSafe`，因为兼容性更高，更安全」。

> 💡 **洞见**：从 `IoAttachDevice` → `IoAttachDeviceToDeviceStack` → `IoAttachDeviceToDeviceStackSafe`，这个演进路径反映了微软对"过滤驱动稳定性"的持续加固。老的 API 没有充分考虑"目标设备正在卸载时绑定"这种竞态，新的 Safe 版本则在内部加了锁和保护。

### 3.1.2 设备绑定的内核 API 之二

**📌 书中的世界**

书中第二个 API 是 `IoAttachDeviceToDeviceStack()`。它与 `IoAttachDevice` 的区别在于：**不再接受设备名字，而是直接接受目标设备对象指针（PDEVICE_OBJECT）**。

微软官方文档对 `IoAttachDeviceToDeviceStack` 的定义非常清晰：

> 该例程将调用方的设备对象附加到链中**当前最高的设备对象**，并返回指向以前最高的设备对象的指针。如果 TargetDevice 之上还有其他分层的驱动程序，则返回的设备对象指针可能与 TargetDevice 不同。

**🔍 第一性原理视角：为什么需要"直接传设备对象"的版本？**

`IoAttachDevice` 需要走一次"名字 → 对象"的解析；而 `IoAttachDeviceToDeviceStack` 跳过了这一步，直接操作设备对象。这在两种场景下至关重要：

1. **你已经通过某种方式拿到了设备对象指针**（比如遍历设备栈）
2. **避免 TOCTOU 竞态**：从"按名字查设备对象"到"绑定"之间，设备可能被卸载。直接传指针的版本避免了这个时间窗口

微软文档特别强调了一个**关键语义**：

> `IoAttachDeviceToDeviceStack` 将 SourceDevice 附加到链中**当前分层的最高设备对象**，并且**无法确定驱动程序是否按正确的顺序分层**。

这句话的意思是：Windows 不会帮你保证过滤驱动的顺序——如果你的过滤驱动必须位于某个特定驱动之下，你必须在那个驱动之上分层之前调用此例程。

> ⚠️ **这是过滤驱动开发中最容易忽视的坑**：设备栈上可能有多个过滤驱动，绑定顺序直接影响谁先看到 IRP。在串口过滤这种简单场景里无所谓，但在文件系统过滤、网络过滤等复杂场景下，顺序就是一切。

### 3.1.3 生成过滤设备并绑定

**📌 书中的世界**

完整的绑定流程是：

1. `IoCreateDevice()` 创建一个过滤设备对象
2. 设置 `DeviceType` 与目标设备一致（通过 `IoGetDeviceObjectPointer` 获取目标设备的类型）
3. 调用 `IoAttachDevice()` 或 `IoAttachDeviceToDeviceStack()` 完成绑定
4. 保存返回的设备对象指针（即"下层设备"），供后续 `IoCallDriver` 使用

**🔍 第一性原理视角：过滤设备对象 = "镜子"**

过滤设备对象有几个反直觉的特性：

- **它没有名字**（或可以不暴露名字）——用户态不需要直接打开它
- **它的 DeviceType 必须与目标设备一致**——否则 I/O 管理器不会把 IRP 发给它
- **它的 StackSize 必须比下层设备大 1**——`IoAttachDeviceToDeviceStack` 会自动帮你设置好
- **它的 AlignmentRequirement 要与下层对齐**——同样由绑定函数自动设置

这意味着：**过滤设备对象是目标设备的一面"镜子"**——它模仿目标设备的所有外在特征，只是在 IRP 流经时插了一脚。

**🏭 现代工业实践**

现代 WDF/KMDF 驱动中，过滤设备的创建和绑定被框架封装了：

- 用 `WdfDeviceCreate` 创建设备对象
- 用 `WdfFdoInitSetFilter` 声明这是一个过滤驱动
- 框架自动处理 StackSize、DeviceType 继承、绑定顺序等问题

但在 WDM 层（本书的语境），这些细节必须手动处理——这也是为什么学安全编程要先学 WDM：**框架替你做的事，正是你需要理解的事**。

### 3.1.4 从名字获得设备对象

**📌 书中的世界**

书中介绍了两种方法：

1. **`IoGetDeviceObjectPointer()`**：文档化 API，通过设备名获取设备对象指针 + 文件对象指针
2. **`ObReferenceObjectByName()`**：未文档化 API，可以直接通过名字拿到设备对象/Driver 对象指针

**🔍 第一性原理视角：为什么需要"按名字找对象"？**

Windows 内核是一个对象管理器（Object Manager）的世界——所有内核对象（设备、驱动、进程、线程、事件、互斥体等）都生活在对象目录树中，路径形如 `\Device\Serial0`、`\Driver\Serial`。要从内核代码里拿到这些对象的指针，就必须"按名字解析"。

**`IoGetDeviceObjectPointer` 的语义**（微软官方文档）：

- 输入：设备名（`\Device\RawDisk` 这种格式）、期望访问权限
- 输出：设备对象指针 + 文件对象指针
- **关键陷阱**：返回的文件对象指针会增加设备对象的引用计数。如果你不需要文件对象，必须调用 `ObDereferenceObject(fileObject)` 来释放——但要注意，**这同时也会减少设备对象的引用计数**。如果你后续还要用设备对象指针，必须先对它再调用 `ObReferenceObject` 增加引用

**`ObReferenceObjectByName` 的语义**：

- 这是未文档化 API，但功能强大：它可以直接按名字拿到 Driver 对象（`*IoDriverObjectType`）或 Device 对象（`IoDeviceObjectType`）
- 它会**增加对象的引用计数**，所以用完必须配对调用 `ObDereferenceObject`
- 只能在 **PASSIVE_LEVEL**​ 调用
- 微软不在 WDK 中文档化它，意味着它可能在未来 Windows 版本中改变行为或签名

> ⚠️ **2026 年的现实**：随着 Windows 11 25H2（build 26100+）和 Server 2025 的内核演进，未文档化 API 的稳定性风险比 XP/Vista 时代更大。微软的 Driver Verifier 从 Windows 7 开始就会标记可疑的对象句柄使用。工业界的最佳实践是：**能用 `IoGetDeviceObjectPointer` 就不用 `ObReferenceObjectByName`**。

**🏭 现代工业实践**

- 优先使用 `IoGetDeviceObjectPointer`（文档化、稳定）
- 如果需要遍历某个 Driver 创建的所有 Device 对象，可以用 `ObReferenceObjectByName` 拿到 Driver 对象，然后通过 `DriverObject->DeviceObject` 和 `DeviceObject->NextDevice` 链表遍历——但这是研究/审计场景的做法，不应出现在生产驱动中
- 使用未文档化 API 时，**必须**配对调用 `ObDereferenceObject`，否则会造成对象引用计数泄漏

### 3.1.5 绑定所有串口

**📌 书中的世界**

书中演示了如何枚举并绑定所有串口（COM1-COM256）。方法是构造 `\Device\Serial0`、`\Device\Serial1`... 这样的名字，循环调用 `IoGetDeviceObjectPointer` + `IoAttachDeviceToDeviceStack`。

**🔍 第一性原理视角：枚举的艺术**

"绑定所有串口"看似简单，但藏着几个工程问题：

1. **串口数量不确定**——可能是 1 个，也可能是几十个（通过端口扩展器）
2. **某些串口名可能不存在**——`IoGetDeviceObjectPointer` 会返回 `STATUS_OBJECT_NAME_NOT_FOUND`，必须优雅处理
3. **绑定顺序**——如果系统已经有其他串口过滤驱动，你的位置在哪里？

书中的做法（构造 `Serial0`、`Serial1`... 循环尝试）是一种"暴力枚举"策略，简单有效，但不是最优解。更严谨的做法是通过 `ObReferenceObjectByName` 拿到 `\Driver\Serial` 这个 Driver 对象，然后遍历它的 `DeviceObject` 链表——这样可以**精确枚举所有串口设备对象，不漏不重**。

> 💡 **洞见**：这两种枚举方式反映了两种不同的工程哲学：
> 
> - **字符串猜测枚举**（书中做法）：简单、直观，但可能漏掉动态创建的串口
> - **对象树遍历**（工业做法）：精确、完整，但依赖未文档化 API
> 
> 在安全研究领域，后者更有价值——因为你不想漏掉任何一个被隐藏的串口设备（Rootkit 可能故意让你枚举不到）。

## 3.2 获得实际数据

### 3.2.1 请求的区分

**📌 书中的世界**

过滤驱动的核心是分发函数（Dispatch Routine）。串口过滤主要关心两类 IRP：

- **`IRP_MJ_WRITE`**：数据从用户态发往串口（你想监控"写了什么"）
- **`IRP_MJ_READ`**：数据从串口发往用户态（你想监控"读了什么"）
- 其他 IRP（`IRP_MJ_CREATE`、`IRP_MJ_CLOSE`、`IRP_MJ_DEVICE_CONTROL` 等）直接向下转发

**🔍 第一性原理视角：IRP 的分发是"路由决策"**

每一个到达你过滤设备的 IRP，你都要做三个决策：

1. **关心吗？**​ —— 只拦截你感兴趣的 IRP 类型（WRITE/READ）
2. **怎么处理？**​ —— 监视（拷贝数据后放行）/ 修改（篡改数据后放行）/ 阻断（直接完成 IRP 返回错误）
3. **何时拿数据？**​ —— 在分发函数里拿"下发前"的数据；在完成例程里拿"完成后"的数据

这正是过滤驱动区别于其他内核编程的核心：**你不是"处理"请求，你是"观察/干预"请求**。

### 3.2.2 请求的结局

**📌 书中的世界**

IRP 的"结局"有三种：

1. **向下转发**：调用 `IoCallDriver()` 把 IRP 传给下层设备
2. **自己完成**：调用 `IoCompleteRequest()` 直接结束 IRP
3. **挂起**：返回 `STATUS_PENDING`，稍后完成

**🔍 第一性原理视角：过滤驱动必须"对下透明"**

过滤驱动最大的工程约束是：**你的存在对下层驱动和用户态程序都应该是"透明"的**——除非你有意为之。这意味着：

- 你不能改变 IRP 的语义（除非做安全干预）
- 你必须正确传递 IRP 的状态码和 Information 字段
- 你设置的完成例程必须正确"冒泡" `PendingReturned` 标记

微软的完成例程文档明确指出：

> 任何将 IRP 向下传递的驱动程序，都可以在调用 `IoCallDriver` 之前通过调用 `IoSetCompletionRoutine` 为 IRP 可选地注册一个完成例程。完成例程在 **IRQL <= DISPATCH_LEVEL**​ 的**任意线程上下文**中被调用。因为它们可能在 DISPATCH_LEVEL 被调用，所以完成例程不能调用必须在较低 IRQL 调用的内核模式例程，例如 `IoDeleteDevice`。出于同样的原因，完成例程中使用的任何数据结构都必须从**非分页内存**中分配。

这段话是过滤驱动开发的"金科玉律"——它告诉你完成例程里能做什么、不能做什么。

**🏭 现代工业实践**

完成例程的常见模式（参考微软过滤驱动示例代码）：

```
// 通用完成例程：检查下层是否标记了 Pending，如果是则冒泡
NTSTATUS GenericCompletion(
    IN PDEVICE_OBJECT pDevObj,
    IN PIRP pIrp,
    IN PVOID pContext) 
{
    if (pIrp->PendingReturned)
        IoMarkIrpPending(pIrp);
    return STATUS_SUCCESS;
}
```

这个 `GenericCompletion` 是几乎所有过滤驱动的"标配"——它确保 `Pending` 状态正确向上传递。

### 3.2.3 写请求的数据

**📌 书中的世界**

这是本章最精彩的部分——如何拿到 WRITE IRP 中用户态写入串口的实际数据。书中核心要点：

- 串口设备通常使用 `DO_BUFFERED_IO` 或 `DO_DIRECT_IO`
- 如果是 `DO_BUFFERED_IO`：数据在 `Irp->AssociatedIrp.SystemBuffer`
- 如果是 `DO_DIRECT_IO`：数据在 `Irp->MdlAddress` 描述的 MDL 中，需要通过 `MmGetSystemAddressForMdl` 映射到内核地址
- 数据长度在 `IoGetCurrentIrpStackLocation(Irp)->Parameters.Write.Length`

**🔍 第一性原理视角：数据在哪取决于"I/O 方式"**

这是第2章讲的"数据类型"和"I/O 方式"的实战应用。WRITE IRP 的数据位置完全由**目标设备对象的 Flags**​ 决定：

|设备对象 Flags|数据位置|访问方式|
|---|---|---|
|`DO_BUFFERED_IO`|`Irp->AssociatedIrp.SystemBuffer`|直接访问（内核空间的非分页缓冲）|
|`DO_DIRECT_IO`|`Irp->MdlAddress`（MDL）|`MmGetSystemAddressForMdl` 映射后访问|
|两者都未设置|`Irp->UserBuffer`|必须用 `ProbeForRead` + `try/except` 访问|

微软的 IRP_MJ_WRITE 文档给出了权威说明：

> 如果设备对象的 Flags 中设置了 `DO_BUFFERED_IO` 标志，则 `Irp->AssociatedIrp.SystemBuffer` 指向系统提供的中间缓冲区。否则，此成员设置为 NULL。`Irp->MdlAddress` 是描述要写入数据的页面的 MDL 地址。

> 💡 **洞见**：过滤驱动拿数据的难点不在于"读内存"，而在于"知道数据在哪"。这需要你在绑定设备时检查目标设备对象的 Flags，确定它的 I/O 方式，然后在分发函数里用对应的方式取数据。**错误的访问方式 = 立刻 BSOD**。

**🏭 现代工业实践：串口过滤的真实数据获取**

一个工业级的串口过滤驱动，在 WRITE 分发函数中应该这样做：

```
NTSTATUS SerialFilterWrite(
    PDEVICE_OBJECT DeviceObject,
    PIRP Irp)
{
    PDEVICE_EXTENSION devExt = DeviceObject->DeviceExtension;
    PIO_STACK_LOCATION irpSp = IoGetCurrentIrpStackLocation(Irp);
    
    // 1. 设置完成例程，以便在 IRP 完成后还能检查状态
    IoCopyCurrentIrpStackLocationToNext(Irp);
    IoSetCompletionRoutine(Irp, SerialFilterWriteCompletion,
        NULL, TRUE, TRUE, TRUE);
    
    // 2. 如果是缓冲 I/O，现在就可以拿到数据
    if (DeviceObject->Flags & DO_BUFFERED_IO) {
        PVOID buffer = Irp->AssociatedIrp.SystemBuffer;
        ULONG length = irpSp->Parameters.Write.Length;
        // 这里可以监控/记录/修改 buffer 中的数据
        DbgPrint("WRITE %d bytes: %.*s\n", length, length, (char*)buffer);
    }
    // 如果是 DIRECT I/O，数据在下层完成后的 Completion 里拿更稳妥
    
    // 3. 向下转发
    return IoCallDriver(devExt->LowerDeviceObject, Irp);
}
```

**关键工程细节**：

- 在 WRITE 分发函数中，**数据还未被下层处理**，此时如果你修改 `SystemBuffer` 中的数据，下层写出去的就是修改后的数据——这就是"中间人篡改"
- 如果你想拿到"实际写入了多少字节"或"写入是否成功"，必须在**完成例程**中检查 `Irp->IoStatus.Information` 和 `Irp->IoStatus.Status`
- 如果设备使用 `DO_DIRECT_IO`，在完成例程中通过 `MmGetSystemAddressForMdlSafe` 映射 MDL 拿到数据指针

## 3.3 完整的代码

### 3.3.1 完整的分发函数

**📌 书中的世界**

书中给出了完整的分发函数模板：

- `IRP_MJ_CREATE` / `IRP_MJ_CLOSE` → 直接转发
- `IRP_MJ_READ` → 设置完成例程后转发（在完成例程中拿数据）
- `IRP_MJ_WRITE` → 设置完成例程后转发（在完成例程中拿数据）
- `IRP_MJ_DEVICE_CONTROL` → 直接转发或选择性拦截
- 其他 → 直接转发

**🔍 第一性原理视角：分发函数是过滤驱动的"总路由器"**

完整的分发函数体现了过滤驱动的**三大职责**：

1. **分类（Classify）**：根据 `MajorFunction` 决定关心与否
2. **前置处理（Pre-process）**：对关心的 IRP，在向下转发前做监视/修改
3. **后置处理（Post-process）**：通过完成例程，在 IRP 完成后做记录/通知

这三个职责构成了过滤驱动的"生命周期钩子"——类似于用户态的 AOP（面向切面编程）。

**🏭 现代工业实践：分发函数的最佳实践**

- 用 `IoSkipCurrentIrpStackLocation` + `IoCallDriver` 直接转发不关心的 IRP（效率最高）
- 用 `IoCopyCurrentIrpStackLocationToNext` + `IoSetCompletionRoutine` + `IoCallDriver` 处理关心的 IRP
- 在完成例程中，如果需要"暂停"完成流程（比如异步处理数据），返回 `STATUS_MORE_PROCESSING_REQUIRED`；否则返回 `STATUS_SUCCESS` 让 I/O 管理器继续完成流程
- 微软文档明确：`STATUS_MORE_PROCESSING_REQUIRED` 会暂停 IRP 的完成处理，之后可以通过对同一 IRP 调用 `IoCompleteRequest` 来恢复

### 3.3.2 如何动态卸载

**📌 书中的世界**

动态卸载是过滤驱动最容易出错的部分。正确的卸载顺序是：

1. **`IoDetachDevice()`**：从设备栈分离过滤设备
2. **`IoDeleteDevice()`**：删除过滤设备对象
3. 释放所有资源（自旋锁、内存池等）

**🔍 第一性原理视角：卸载顺序 = 资源释放顺序的反转**

这是一个通用的系统编程原则——**资源释放顺序必须是申请顺序的反转**：

```
申请顺序：IoCreateDevice → IoAttachDevice → 分配资源
释放顺序：释放资源 → IoDetachDevice → IoDeleteDevice
```

如果顺序错了，比如先 `IoDeleteDevice` 再 `IoDetachDevice`，那么分离时引用的设备对象已经是野指针——立刻 BSOD。

> ⚠️ **关键约束**：`IoDeleteDevice` 不能在完成例程中调用，因为完成例程运行在 IRQL <= DISPATCH_LEVEL 的任意线程上下文，而 `IoDeleteDevice` 必须在 PASSIVE_LEVEL 调用。这也是为什么卸载必须等到所有 IRP 都完成（或取消）之后才能进行。

**🏭 现代工业实践**

- 现代 WDF 驱动中，卸载逻辑由框架自动处理——你只需在 `EvtCleanupCallback` / `EvtDestroyCallback` 中释放你分配的资源，框架负责剩下的事
- WDM 过滤驱动必须手动实现 `DriverUnload` 例程，且必须：
    1. 遍历所有已绑定的过滤设备
    2. 对每个设备调用 `IoDetachDevice`
    3. 然后调用 `IoDeleteDevice`
    4. 最后释放 DeviceExtension 中的资源
- 如果驱动正在处理 IRP 时被卸载，必须**等待所有 IRP 完成**——这通常通过一个计数器 + 自旋锁实现，或者使用 `IoAcquireRemoveLock` / `IoReleaseRemoveLock`（现代 WDM 推荐做法）

### 3.3.3 完整的代码

**📌 书中的世界**

书中给出了完整可编译的串口过滤驱动代码，包含：

- `DriverEntry`：创建过滤设备、绑定所有串口
- 各 MajorFunction 分发函数
- 完成例程
- `DriverUnload`：动态卸载

**🔍 第一性原理视角：这份代码是"过滤驱动的最小完备集"**

这份代码的价值不在于"可以拿去用"（串口过滤在现代 Windows 上几乎没人这么写了），而在于它展示了**过滤驱动的全部骨架**：

```
DriverEntry
  ├─ 遍历目标设备（串口）
  │   ├─ IoCreateDevice（创建过滤设备）
  │   └─ IoAttachDeviceToDeviceStack（绑定）
  └─ 填写 MajorFunction 派发表

DispatchXxx
  ├─ 设置完成例程
  ├─ IoCallDriver（向下转发）
  └─ 返回状态

CompletionRoutine
  ├─ 检查 PendingReturned
  ├─ 拿数据/记录日志
  └─ 返回 STATUS_SUCCESS 或 STATUS_MORE_PROCESSING_REQUIRED

DriverUnload
  ├─ 遍历过滤设备
  │   ├─ IoDetachDevice
  │   └─ IoDeleteDevice
  └─ 释放资源
```

> 💡 **洞见**：这个骨架是所有 Windows 过滤驱动的"基因"——无论是串口过滤、键盘过滤、文件系统过滤（legacy filter）、网络过滤（TDI/NDIS filter），还是现代的文件系统微过滤（Minifilter）、WFP 网络过滤，它们的骨架都与这个串口过滤驱动同构。**学会这一个，等于学会了所有过滤驱动**。

**🏭 现代工业实践：从 Legacy 过滤到现代过滤框架**

串口过滤在现代 Windows 上的工业实践已经完全演化：

|过滤类型|Legacy 做法（书中）|现代做法|
|---|---|---|
|串口/设备过滤|WDM 过滤驱动 + `IoAttachDeviceToDeviceStack`|KMDF 过滤驱动 + `WdfFdoInitSetFilter`|
|文件系统过滤|Legacy FS Filter（本书第7章）|**Minifilter**（微软官方推荐）|
|网络过滤|TDI 过滤（已废弃）|**WFP**（Windows Filtering Platform）|
|注册表过滤|`CmRegisterCallback`|同上（依然是最佳实践）|

微软官方明确建议：

> 为了最佳的可靠性和性能，请使用带 Filter Manager 支持的**文件系统 Minifilter 驱动**，而不是 Legacy 文件系统过滤驱动。

这个建议的精神适用于所有过滤场景：**框架化的过滤模型优于 Legacy 的手工过滤**。原因是：

1. 框架处理了绑定顺序、IRQL、引用计数等易错细节
2. 框架提供了标准化的通信机制（用户态 ↔ 内核态）
3. 框架通过了 WHQL 认证的兼容性测试

但本书坚持讲 WDM Legacy 过滤的价值在于：**你必须先理解"框架之下发生了什么"，才能真正理解框架**。当你日后调试一个 Minifilter 的诡异问题时，如果你懂 `IoAttachDeviceToDeviceStack` 的语义、懂完成例程的 IRQL 约束、懂 `STATUS_MORE_PROCESSING_REQUIRED` 的含义——你就能看穿框架的抽象，直击问题本质。

## 🎯 本章核心洞见总结

读完第3章，我希望你带走的不只是"怎么写串口过滤驱动"，而是这三个**第一性原理**：

**1. 过滤的本质是"设备栈插入"，不是"Hook"**

Windows 的 I/O 框架天然支持过滤——你只需把自己的设备对象挂到目标设备栈顶端。这种方式：

- 不需要 patch 任何内核代码
- 不需要 Hook 任何函数指针
- 不会被 PatchGuard 触发
- 是微软"支持"的过滤机制

理解这一点，你就能理解为什么 Windows 上的安全软件（杀毒、EDR、防火墙、加密软件）全都采用过滤驱动模型——这是唯一稳定、合法、可认证的内核扩展方式。

**2. IRP 是过滤驱动的"血液"**

IRP 在设备栈中向下流动、向上完成。过滤驱动的工作就是在 IRP 流经自己这一层时：

- **向下之前**：可以监视或修改 IRP 的输入数据
- **向上完成**：通过完成例程监视或修改 IRP 的输出数据和状态

完成例程的约束（IRQL <= DISPATCH_LEVEL、任意线程上下文、非分页内存）是过滤驱动开发中**最容易引发 BSOD 的地方**。

**3. 数据在哪取决于 I/O 方式**

`DO_BUFFERED_IO` → `SystemBuffer`；`DO_DIRECT_IO` → `MdlAddress`；两者皆非 → `UserBuffer`。这是过滤驱动"拿数据"的根本依据。**判断错 I/O 方式 = 立刻 BSOD**。

### 从书中环境到现代工业环境的迁移清单

|书中做法 (XP/Vista 时代)|现代工业做法 (Win10/11)|
|---|---|
|`IoAttachDevice`|`IoAttachDeviceToDeviceStackSafe`|
|`ObReferenceObjectByName` 枚举串口|优先 `IoGetDeviceObjectPointer`；研究场景才用未文档化 API|
|手工遍历 `Serial0`~`SerialN`|通过 `\Driver\Serial` 的 DeviceObject 链表遍历|
|WDM 过滤设备 + 手动绑定|KMDF `WdfFdoInitSetFilter`|
|手工管理绑定/分离顺序|WDF 框架自动管理生命周期|
|手工完成例程 + `STATUS_MORE_PROCESSING_REQUIRED`|WDF `EvtIoXxx` 回调 + 框架托管的完成机制|
|无符号加载|DSE + EV 签名 + WHQL 认证|
|在 DISPATCH_LEVEL 完成例程中调用 `IoDeleteDevice`（错误！）|确保卸载路径在 PASSIVE_LEVEL 执行|

> 📌 **最后一句话**：第3章的串口过滤驱动，是内核安全编程的"Hello World"——它简单到可以在一个下午跑通，却完整包含了过滤驱动的所有核心要素：设备绑定、IRP 截获、完成例程、动态卸载。**把这份代码亲手编译、加载、用 WinDbg 单步跟踪一遍，你就算真正"入门"了 Windows 内核过滤**。后面章节的键盘过滤、文件系统过滤、网络过滤、注册表过滤，全都是这个骨架的"换皮"——变的只是关心的 IRP 类型和拿数据的方式，不变的是"设备栈插入 + IRP 截获"这一核心范式。
