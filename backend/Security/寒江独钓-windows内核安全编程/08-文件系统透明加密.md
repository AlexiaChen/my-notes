
第8章"文件系统透明加密"是全书**最接近商用安全产品**的一章——企业 DLP（数据防泄漏）、透明加密软件（如 Symantec Endpoint Encryption、Microsoft BitLocker 的某些模式、各国内联 DLP 厂商的产品）的内核核心，就是这一章讲的东西。书中以 sfilter 框架为基础，构建一个叫 `crypt_file` 的透明加密过滤驱动：机密进程看到明文，普通进程看到密文；文件在磁盘上永远是密文，在内存中才是明文。

## 8.1 文件透明加密的应用

### 8.1.1 防止企业信息泄密

**📌 书中的世界**

企业信息泄密的路径主要有：邮件外发、U 盘拷贝、网盘上传、截图外传、打印。透明加密的目标是：**让机密文件在离开企业受控环境时"自动变成乱码"**——即使文件被窃取，没有对应的解密密钥和授权进程也打不开。

**🔍 第一性原理视角：透明加密的本质是"绑定数据解密权到受控进程"**

这不是传统的"加密 = 保密"，而是"加密 = 把解密能力与进程身份绑定"。第一性原理可以归纳为：

> **数据的解密视图只对"授信进程"可见；非授信进程看到的永远是密文。**

这个原理决定了透明加密系统的三个核心要素：

1. **进程身份验证**：如何可靠地识别"谁是授信进程"
2. **加密边界管理**：哪些文件需要加密、加密标识如何存储
3. **视图隔离**：如何确保非授信进程无法通过各种"后门"（缓存、内存映射）看到明文

### 8.1.2 文件透明加密防止企业信息泄密

**📌 书中的世界**

书中强调"透明"二字的含义：用户和应用程序无感知——Word 打开 .docx 文件时看到的是明文，保存时自动加密落盘；文件在硬盘上始终是密文。

**🔍 第一性原理视角：透明性 = 拦截点的"无感嵌入"**

百度百科对驱动层加密的定义非常精准：**"文件在存储时为密文，在内存中使用时为明文，用户操作过程无感知"**。这个定义的精髓在于**双视图**：

- **持久化视图（磁盘）**：密文
- **运行时视图（内存）**：明文

过滤驱动的职责就是在这两个视图之间做"实时转换"——写时加密、读时解密。

**🏭 现代工业实践**

现代透明加密产品（如金纬、安在、Foxtrot 等）的架构：

```
应用程序（Word/Excel/CAD）
    ↓ 文件 I/O
Minifilter 驱动（Pre/Post 回调）
    ↓ 判断进程信任 + 文件策略
    ↓ 写时加密 / 读时解密
文件系统（NTFS/ReFS）
    ↓
磁盘（密文存储）
```

### 8.1.3 文件透明加密软件的例子

**📌 书中的世界**

书中提到了若干市面上的透明加密软件作为参考。

**🏭 现代工业实践**

2026 年的主流透明加密/DLP 产品：

- **Microsoft BitLocker**：扇区级全盘加密，不区分进程，但提供完整的磁盘加密服务
- **Symantec Endpoint Encryption**：企业级，支持文件级透明加密
- **Trend Micro Endpoint Encryption**：文件级 + 全盘加密
- **国内厂商**：金纬科技、安在软件、亿赛通等，主打"进程级透明加密"
- **Foxtrot 双缓冲 Minifilter**：开源原型，AES-128 加密，双缓冲机制实现进程级视图隔离

> 💡 **洞见**：观察这些产品的架构演变会发现一个共同趋势——**从"文件级加密"走向"进程级视图隔离"**。早期的透明加密只做"文件写时加密、读时解密"；现代的透明加密（如 TDE）更进一步：**同一个文件，授信进程看到明文视图，非授信进程看到密文视图**。这是透明加密技术的"第二代"演进。

## 8.2 区分进程

### 8.2.1 机密进程与普通进程

**📌 书中的世界**

透明加密的核心是"进程区分"——必须明确回答："当前发起文件 I/O 的进程，是授信进程还是非授信进程？"

**🔍 第一性原理视角：进程身份是透明加密的"信任根"**

整个加密体系的信任链始于"进程身份的可靠识别"。如果进程识别被绕过，加密体系就崩塌。所以进程识别必须是：

- **可靠的**：不能被伪造（如进程名 spoofing）
- **细粒度的**：能区分到具体进程（甚至具体到进程签名）
- **实时的**：每个 I/O 请求都要重新验证

### 8.2.2 找到进程名字的位置

**📌 书中的世界**

在 legacy 过滤驱动中，通过 `PsGetCurrentProcess()` 获取当前进程对象，然后通过 `EPROCESS` 结构中的 `ImageFileName` 字段获取进程名。

**🔍 第一性原理视角：进程名的"可靠性层级"**

进程识别的可靠性从低到高：

1. **进程名（ImageFileName）**：最不可靠——同名进程、改名进程都能绕过
2. **进程 ID（PID）**：稍可靠，但 PID 会复用
3. **进程路径（Full Image Path）**：较可靠
4. **进程签名（Authenticode）**：最可靠——需要验签，成本高但安全性最高
5. **进程 token + ACL**：系统级信任

**🏭 现代工业实践**

Minifilter 提供了更干净的 API 来获取进程上下文：

```
// 获取请求者进程对象
PEPROCESS process = FltGetRequestorProcess(Data);
// 获取请求者进程 ID
HANDLE pid = FltGetRequestorProcessId(Data);  // 或 FltGetRequestorProcessIdEx
// 注意：不要长期持有 PEPROCESS 引用，避免悬垂指针
```

现代 DLP 产品的进程信任判定：

```
// 伪代码：TDE 的进程白名单判定
FLT_PREOP_CALLBACK_STATUS TdePreRead(...) {
    PFLT_FILE_NAME_INFORMATION nameInfo;
    FltGetFileNameInformation(Data, ..., &nameInfo);
    
    UNICODE_STRING processName = GetCurrentProcessName();
    if (!IsInWhitelist(processName)) {
        // 非授信进程：返回密文或拒绝访问
        Data->IoStatus.Status = STATUS_ACCESS_DENIED;
        return FLT_PREOP_COMPLETE;
    }
    // 授信进程：透明解密
    return FLT_PREOP_SUCCESS_WITH_CALLBACK;
}
```

### 8.2.3 得到当前进程的名字

**📌 书中的世界**

书中给出了从 `EPROCESS` 中提取进程名的代码，以及处理不同 Windows 版本 `EPROCESS` 结构偏移差异的技巧。

**🔍 第一性原理视角：硬编码偏移是"脆弱的艺术"**

不同 Windows 版本中 `EPROCESS` 结构的字段偏移可能变化。书中用特征码搜索或版本判断来定位 `ImageFileName`——这种做法在现代 Windows 上极其脆弱：

- Windows 10 1909 的偏移 ≠ Windows 11 24H2 的偏移
- 任何 Windows 补丁都可能微调结构

**🏭 现代工业实践**

现代驱动**绝不**硬编码 `EPROCESS` 偏移，而是：

- 使用微软文档化的 API（如 `FltGetRequestorProcess`）
- 使用 `PsReferencePrimaryToken` + `SeQueryInformationToken` 获取 token 信息
- 使用 `ZwQueryInformationProcess` 获取进程完整路径
- 在用户态服务中做进程验签（Authenticode），然后通过通信端口传递给内核

> ⚠️ **工业级教训**：进程识别的可靠性直接决定加密体系的强度。仅靠进程名识别的透明加密产品，在面对"进程名 spoofing"或" DLL 注入到授信进程"攻击时形同虚设。现代产品普遍采用"进程名 + 路径 + 签名 + token"的多因子鉴定。

## 8.3 内存映射与文件缓冲

### 8.3.1 记事本的内存映射文件

**📌 书中的世界**

书中揭示了一个关键事实：**像记事本这样的程序，打开文件时用的是内存映射（Memory-Mapped File），而不是普通的 ReadFile/WriteFile**。这意味着文件内容通过缺页中断从磁盘载入进程地址空间，而**过滤驱动拦截不到这种"内存访问"**。

**🔍 第一性原理视角：这是透明加密的"阿喀琉斯之踵"**

Windows 的文件访问有四条路径：

1. **普通 IRP 读写**（ReadFile/WriteFile）→ 过滤驱动能拦截
2. **Fast I/O 读写**（缓存命中）→ 过滤驱动能拦截（如果实现了 Fast I/O 例程）
3. **内存映射文件**（MapViewOfFile）→ 过滤驱动**拦截不到内存访问本身**
4. **缓存管理器分页 I/O**（延迟写、预读）→ 过滤驱动能拦截分页 IRP，但时机微妙

对于内存映射文件，应用程序直接访问映射到文件的虚拟内存页。当页面不在物理内存时，触发缺页中断，内存管理器发送分页 I/O 请求（IRP_MJ_READ）从磁盘读取——**这个 IRP 过滤驱动能拦截到**。但当页面已在物理内存时，应用程序的读写直接操作内存页，**不经过任何 IRP**——过滤驱动完全看不到。

### 8.3.2 Windows 的文件缓冲

**📌 书中的世界**

Windows 的缓存管理器（Cache Manager）会缓存文件数据以提高性能：

- **预读（Read-ahead）**：文件还没被读取时，explorer.exe 可能已经把它读入缓存
- **延迟写（Lazy write）**：写入的数据先留在缓存，由系统线程定期刷盘
- **写回缓存**：修改后的页面在"脏"状态下驻留内存

**🔍 第一性原理视角：缓存是"明文泄漏"的温床**

对于透明加密，缓存管理器带来两个致命问题：

**问题一：预读导致非授信进程"偷看"明文**

如果授信进程（如 Word）打开过一个加密文件，明文可能残留在缓存中。当非授信进程（如恶意程序）随后打开同一文件时，如果过滤驱动不强制重新从磁盘读取密文，**非授信进程就能通过缓存"看到"明文**。

**问题二：延迟写导致密文不一致**

应用程序写入的明文停留在缓存中，延迟写线程负责刷盘。如果在刷盘前过滤驱动不拦截这个分页写 IRP 做加密，**密文文件会被写入明文数据**。

> ⚠️ **工业现实**：CSDN 上的技术分析指出，第二代透明加密技术"为了防止非授信进程访问文件系统缓存的文件明文，每次打开和关闭文件时都要清理文件缓存。这对相当于屏蔽了系统文件缓存带来的性能优化，对大文件的操作影响尤其明显。损坏文件的原因主要是对于延迟写入的缓冲文件...很多情况下都会造成文件数据丢失或文件格式损坏"。

### 8.3.3 文件缓冲：明文还是密文的选择

**📌 书中的世界**

书中给出了一个关键设计决策：**文件缓冲中存放明文**。理由是：

- 内存中的明文便于应用程序编辑
- 只需处理分页读/写请求来做加解密
- 普通进程（非授信）看到的是密文——因为普通进程访问时，过滤驱动从磁盘读取密文，解密后给普通进程？不对——

等等，这里需要仔细辨析书中的逻辑。实际上正确的理解是：

- **对于授信进程**：过滤驱动在 post-read 中解密，在 pre-write 中加密。缓存中存的是**明文**（因为分页 I/O 的读/写也会被过滤驱动拦截并加解密）
- **对于非授信进程**：过滤驱动**不进行解密**——非授信进程从缓存或磁盘读取到的都是密文

但问题来了：缓存是全局的，不区分进程。如果一个加密文件被授信进程打开过，缓存中就有了明文；此时非授信进程打开同一文件，**会直接从缓存读取明文**——这就泄漏了！

**🔍 第一性原理视角：缓存的"进程间隔离缺失"是核心难题**

书中给出的解决方案是：**在文件打开/关闭时清除缓冲**。具体策略：

- 当非授信进程打开加密文件时，强制清除该文件的缓存
- 当文件关闭时（CLEANUP/CLOSE），清除缓存中该文件的明文

**🏭 现代工业实践：双缓冲机制**

现代透明加密产品（如 Foxtrot）采用更优雅的方案——**双缓冲**：

```
每个受保护文件维护两套缓存视图：
- 明文缓冲区：供授信进程访问
- 密文缓冲区：供非授信进程或底层存储使用
```

当 IRP 进入时，驱动根据进程信任度动态决定使用哪个缓冲，并通过 `FltSetCallbackDataDirty` 标记脏页确保 Cache 一致性。

这是比"清除缓冲"更高效的方案——它保留了缓存的性能优势，同时实现了进程间的视图隔离。

### 8.3.4 清除文件缓冲

**📌 书中的世界**

书中详细介绍了在 `IRP_MJ_CLEANUP` 或 `IRP_MJ_CLOSE` 中清除文件缓冲的技术：

- 下发 `IRP_MJ_FLUSH_BUFFERS` 或 `IRP_MJ_SHUTDOWN` 类型的控制请求
- 使用 `CcFlushCache` + `CcPurgeCacheSection` 清除缓存管理器中的缓存
- 必须小心处理 IRQL——缓存操作在 `PASSIVE_LEVEL` 进行

**🔍 第一性原理视角：清除缓冲是"安全与性能"的权衡**

- **清除得太频繁**：性能急剧下降（失去缓存意义）
- **清除得不及时**：明文泄漏风险
- **清除的时机**：文件关闭时（CLEANUP）是关键窗口

**🏭 现代工业实践**

现代 Minifilter 的缓冲管理：

```
// 在 PostCleanup 中清除缓存
FLT_POSTOP_CALLBACK_STATUS PostCleanup(...) {
    // 1. 刷新该文件的缓存
    CcFlushCache(...);
    // 2. 清除该文件的缓存段
    CcPurgeCacheSection(...);
    // 3. 确保后续的读请求从磁盘读取密文
}
```

> ⚠️ **工业级陷阱**：清除缓冲必须非常小心，否则会导致系统 BSOD。特别是：
> 
> - 不能在 IRQL > PASSIVE_LEVEL 调用 `CcPurgeCacheSection`
> - 必须确保没有其他进程正在使用该文件的缓存
> - 延迟写线程可能正在刷盘，需要同步等待

## 8.4 加密标识

### 8.4.1 保存在文件外、文件头还是文件尾

**📌 书中的世界**

加密文件需要一个"标识"来表明"我是加密文件"。三种存储位置各有优劣：

|位置|优点|缺点|
|---|---|---|
|**文件外**（如 NTFS 扩展属性、影子文件）|不修改文件内容；原有文件结构完整|管理复杂；影子文件需要隐藏；易丢失|
|**文件头**（Header）|自包含；随文件移动；易识别|偏移所有数据；读时必须跳过 header；加密文件大小 ≠ 原始大小|
|**文件尾**（Footer）|不偏移数据；文件头保持原样|追加数据需要修改 footer 位置；某些文件格式（如 JPEG）尾部有特定结构|

**🔍 第一性原理视角：加密标识的"位置博弈"**

书中选择**文件头**存储加密标识，理由：

1. **自包含性**：文件复制/移动到任何地方，标识跟着文件走
2. **识别效率**：打开文件时读前几个字节即可判断
3. **实现简单**：不需要额外的影子文件管理

但文件头方案有个**致命问题**：**偏移**。如果加密标识占 128 字节，那么原始文件的第 0 字节，在加密文件中位于第 128 字节。这意味着：

- 所有读请求的偏移都要 +128
- 所有写请求的偏移都要 +128
- 文件大小要 +128

### 8.4.2 隐藏文件头的大小

**📌 书中的世界**

书中定义 `HIDDEN_HEADER_SIZE`（如 128 字节或 256 字节），包含：

- 魔数（Magic Number）：标识这是一个加密文件
- 版本号
- 算法标识（AES/SM4/3DES 等）
- 密钥 ID（指向密钥管理系统的索引）
- IV（初始化向量）
- 原始文件大小

**🔍 第一性原理视角：加密文件头是"元数据的容器"**

文件头中存储的不仅是"标识"，更是"解密所需的一切信息"：

- **密钥 ID**：驱动拿着它去密钥管理服务查询实际密钥（密钥本身不应硬编码在驱动中）
- **IV**：保证相同明文加密后产生不同密文（抗重放攻击）
- **算法标识**：支持算法升级

> 💡 **洞见**：现代加密文件头的设计借鉴了 LUKS（Linux Unified Key Setup）的格式——魔数 + 版本 + 加密参数 + 密钥槽。这种"自描述"的头部格式是工业标准做法。

### 8.4.3 隐藏文件头的设置偏移

**📌 书中的世界**

由于隐藏文件头的存在，所有针对加密文件的读/写偏移都要做转换：

```
// 读请求：用户想读偏移 X 的数据
// 实际从磁盘读取偏移 X + HIDDEN_HEADER_SIZE 处的数据

// 写请求：用户想写偏移 Y 的数据
// 实际写入磁盘偏移 Y + HIDDEN_HEADER_SIZE 处
```

**🔍 第一性原理视角：偏移转换是透明加密的"数学约束"**

这是透明加密驱动中最容易出 bug 的地方。每一个读/写 IRP 的 `ByteOffset` 都必须经过转换，而且必须保证：

- 转换后不越界
- 转换是可逆的（读和写的转换必须对称）
- 分页 I/O 的偏移也要同样转换

### 8.4.4 隐藏文件头的读/写偏移

**📌 书中的世界**

书中给出了读/写偏移转换的具体实现，并强调了在以下场景必须正确处理偏移：

- 普通 IRP 读/写
- 分页 I/O 读/写（来自缓存管理器）
- Fast I/O 读/写
- 文件大小查询（需要减去头部大小）

**🏭 现代工业实践**

现代 Minifilter 透明加密驱动在偏移处理上更加系统化：

```
// 伪代码：Minifilter 中的偏移转换
FLT_PREOP_CALLBACK_STATUS PreRead(...) {
    // 检查是否为加密文件（通过 StreamContext）
    if (streamCtx->IsEncrypted) {
        // 偏移 + HIDDEN_HEADER_SIZE
        Data->Iopb->Parameters.Read.ByteOffset.QuadPart 
            += HIDDEN_HEADER_SIZE;
    }
    return FLT_PREOP_SUCCESS_WITH_CALLBACK;
}

FLT_POSTOP_CALLBACK_STATUS PostRead(...) {
    if (streamCtx->IsEncrypted && NT_SUCCESS(Data->IoStatus.Status)) {
        // 解密读取的数据
        DecryptBuffer(Data->Iopb->Parameters.Read.Length, 
                     Data->Iopb->Parameters.Read.DataBuffer);
    }
    return FLT_POSTOP_FINISHED_PROCESSING;
}
```

> ⚠️ **工业级细节**：偏移转换不仅要处理 `ByteOffset`，还要注意：
> 
> - `IRP_MJ_QUERY_INFORMATION` 中返回的文件大小要减去头部大小
> - `IRP_MJ_SET_INFORMATION` 中 `EndOfFile` 设置要加上头部大小
> - 文件锁（`IRP_MJ_LOCK_CONTROL`）的偏移也要转换

## 8.5 文件加密表

### 8.5.1 何时进行加密操作

**📌 书中的世界**

书中提出一个关键问题：加密驱动怎么知道"哪些文件需要加密"？答案是**文件加密表**——一个内核中的数据结构，记录所有"需要加密的文件"及其状态。

**🔍 第一性原理视角：加密表是"策略与状态的分离"**

- **策略**：哪些文件需要加密（基于路径、扩展名、目录规则）
- **状态**：文件当前是否加密、密钥 ID、加密参数

加密表将这两个维度统一在一个数据结构中，供所有 I/O 回调查询。

### 8.5.2 文件控制块与文件对象

**📌 书中的世界**

Windows 文件系统中：

- **FCB（File Control Block）**：文件系统内部的数据结构，每个打开的文件有一个 FCB
- **FILE_OBJECT**：每个 `CreateFile` 调用创建一个 FILE_OBJECT，关联到 FCB

**🔍 第一性原理视角：FCB 是"文件级状态"的自然载体**

由于 FCB 的生命周期与文件本身绑定（与打开次数无关），它是存储"文件加密状态"的理想位置。但 legacy 过滤驱动无法直接访问 FCB——所以书中用**文件加密表**模拟这个功能。

**🏭 现代工业实践**

Minifilter 提供了完美的解决方案——**Stream Context**：

```
// Stream Context 直接链接到文件（FCB），与打开的 FILE_OBJECT 数量无关
typedef struct _STREAM_CONTEXT {
    BOOLEAN IsEncrypted;
    ULONG KeyId;
    ULONGLONG OriginalFileSize;
    // ...
} STREAM_CONTEXT, *PSTREAM_CONTEXT;

// 在 PreCreate 中创建并关联到流
FltAllocateContext(FltObjects->Filter, FLT_STREAM_CONTEXT, 
    sizeof(STREAM_CONTEXT), NonPagedPool, &streamCtx);
FltSetStreamContext(FltObjects->Instance, FltObjects->FileObject,
    FLT_SET_CONTEXT_KEEP_IF_EXISTS, streamCtx, NULL);
```

Stream Context 的优势：

- **自动生命周期管理**：最后一个 FILE_OBJECT 关闭时，FltMgr 自动清理
- **跨 FILE_OBJECT 共享**：同一个文件的所有打开共享同一个 Stream Context
- **与 FCB 一一对应**：等同于书中想实现的"文件加密表"功能，但由 FltMgr 托管

### 8.5.3 文件加密表的数据结构与初始化

**📌 书中的世界**

书中定义文件加密表的数据结构：

```
typedef struct _ENCRYPT_FILE_ENTRY {
    LIST_ENTRY ListEntry;          // 链表节点
    UNICODE_STRING FileName;       // 文件名
    BOOLEAN IsEncrypted;           // 是否加密
    ULONG KeyId;                   // 密钥 ID
    FAST_MUTEX Lock;               // 保护锁
} ENCRYPT_FILE_ENTRY, *PENCRYPT_FILE_ENTRY;
```

**🔍 第一性原理视角：内核中的"状态数据库"**

这个数据结构本质上是一个**内核态的"文件加密状态数据库"**：

- 查询：O(1) 或 O(log n) 查找
- 插入：新文件打开时
- 删除：文件关闭且最后一个引用消失时

**🏭 现代工业实践**

现代 Minifilter 使用 FltMgr 提供的 Context 机制替代手动链表：

- **Stream Context**：文件级状态（是否加密、密钥 ID）
- **Stream Handle Context**：FILE_OBJECT 级状态（进程信任度、明文/密文视图）
- **Volume Context**：卷级策略（该卷是否启用加密、加密算法）

这种分层 Context 架构比单一的"文件加密表"更灵活、更不容易出错。

### 8.5.4-8.5.6 文件加密表的操作：查询/添加/删除

**📌 书中的世界**

书中给出了加密表的查询、添加、删除操作，强调了多核同步（自旋锁或快速互斥锁）的重要性。

**🔍 第一性原理视角：内核数据结构的"并发安全"**

所有内核数据结构都必须考虑多核并发：

- 查询操作可能与其他核上的添加操作并发
- 删除操作必须确保没有正在进行的 I/O 引用该条目
- 使用引用计数管理生命周期

**🏭 现代工业实践**

Minifilter 的 Context 机制自动处理了并发：

- `FltGetStreamContext` 增加引用计数
- `FltReleaseContext` 减少引用计数
- 最后一个引用释放时自动清理

开发者不需要手动管理锁和生命周期——这是 Minifilter 相比 legacy 模型的最大工程优势之一。

## 8.6 文件打开处理

### 8.6.1 直接发送 IRP 进行查询与设置操作

**📌 书中的世界**

在文件打开处理中，过滤驱动需要：

- 查询文件属性（是否加密、头部信息）
- 设置文件属性（标记为加密）
- 这些操作通过直接构造和下发 IRP 来完成

**🔍 第一性原理视角：过滤驱动中的"IRP 重入"问题**

在 legacy 过滤驱动中直接下发 IRP 到下层的文件系统，看似简单，实则暗藏陷阱：

- 下发的 IRP 可能再次被本过滤驱动拦截（如果过滤驱动在设备栈的更高位置）
- 造成无限递归

> ⚠️ **工业级陷阱**：这就是"重入"问题。书中 8.6.3 节专门讲"文件的非重入打开"——通过设置标志位或使用特殊参数，确保下发的 IRP 不会再次被本驱动处理。

**🏭 现代工业实践**

Minifilter 提供了 `FltCreateFile` 等 API 替代 `ZwCreateFile`——`FltCreateFile` 明确设计为在 Minifilter 环境中使用，避免重入问题。微软文档建议：__Minifilter 中不建议使用 Zw_ 函数，而是使用 Flt_ 函数，避免重入（死循环）**。

### 8.6.2 直接发送 IRP 进行读/写操作

**📌 书中的世界**

在打开文件时，过滤驱动可能需要直接读取文件头部来判断是否加密：

1. 构造 READ IRP
2. 下发到下层文件系统
3. 在完成例程中解析头部
4. 根据解析结果设置文件加密状态

**🔍 第一性原理视角：这是"带外 I/O"**

过滤驱动在正常的 I/O 流之外，自己发起 I/O 来读取元数据。这种"带外 I/O"必须小心：

- 不能在 Dispatch 函数中同步等待（会导致死锁）
- 必须使用完成例程异步处理
- 必须防止重入

### 8.6.3 文件的非重入打开

**📌 书中的世界**

书中给出了避免重入的关键技术：

- 在设备扩展中设置"正在处理"标志
- 下发 IRP 时设置特定的标志位
- 在完成例程中检查标志位，避免递归处理

**🔍 第一性原理视角：重入是过滤驱动的"经典死锁场景"**

```
过滤驱动下发 IRP 读取文件头部
    ↓
IRP 到达设备栈顶部
    ↓
又被本过滤驱动的 DispatchRead 拦截
    ↓
再次下发 IRP 读取头部
    ↓
无限递归 → 栈溢出 → BSOD
```

**解决方案**：

1. 使用 `DO_DEVICE_INITIALIZING` 之外的标志位标记"当前 IRP 是本驱动自己下发的"
2. 在完成例程中检查这个标志，如果是自己下发的，跳过过滤逻辑直接完成
3. 或者使用 `IoSetCompletionRoutine` 的"忽略"标志

### 8.6.4 文件的打开预处理

**📌 书中的世界**

在 `IRP_MJ_CREATE` 的 pre-create 回调中：

1. 获取文件名
2. 查询文件加密表，判断文件是否需要加密
3. 如果是加密文件，读取文件头部，解析加密参数
4. 设置 Stream Context（或文件加密表条目）
5. 决定是否放行

**🔍 第一性原理视角：CREATE 是"策略决策的黄金点"**

`IRP_MJ_CREATE` 是文件 I/O 的"起点"，在这里做决策成本最低：

- 进程信任判定
- 文件加密状态判定
- 密钥获取
- 偏移转换初始化

所有后续 I/O 都可以依赖 CREATE 阶段建立的"上下文"来做快速决策。

**🏭 现代工业实践**

Minifilter 的 PreCreate 回调是现代透明加密产品的核心决策点：

```
FLT_PREOP_CALLBACK_STATUS PreCreate(...) {
    // 1. 获取文件名
    FltGetFileNameInformation(Data, ..., &nameInfo);
    
    // 2. 获取请求者进程
    PEPROCESS process = FltGetRequestorProcess(Data);
    
    // 3. 判断进程信任度
    BOOLEAN isTrusted = IsProcessTrusted(process, nameInfo);
    
    // 4. 判断文件是否需要加密（基于策略）
    BOOLEAN needEncrypt = IsFilePolicyMatch(nameInfo);
    
    // 5. 创建 Stream Context 并记录状态
    PSTREAM_CONTEXT ctx;
    FltAllocateContext(..., &ctx);
    ctx->IsEncrypted = needEncrypt;
    ctx->IsTrustedProcess = isTrusted;
    FltSetStreamContext(..., ctx, ...);
    FltReleaseContext(ctx);
    
    return FLT_PREOP_SUCCESS_WITH_CALLBACK;
}
```

## 8.7 读写加密/解密

### 8.7.1 在读取时进行解密

**📌 书中的世界**

读请求的解密流程：

1. Pre-read：转换偏移（+HIDDEN_HEADER_SIZE）
2. 下发 IRP 到下层
3. Post-read 完成例程：从下层获取密文数据
4. 解密数据，替换回用户缓冲区
5. 如果是非授信进程，不解密（保持密文）

**🔍 第一性原理视角：解密是"完成例程中的原地操作"**

关键技术点：

- 解密必须在 post-read 完成例程中进行（因为 pre-read 时数据还没从磁盘读取）
- 解密是"原地"的——直接修改 `Irp->AssociatedIrp.SystemBuffer` 或 MDL 映射的缓冲区
- 解密算法必须是"流式的"——支持任意偏移的解密（不能假设每次都从文件开头解密）

**🏭 现代工业实践**

现代 Minifilter 的解密流程：

```
FLT_POSTOP_CALLBACK_STATUS PostRead(...) {
    PSTREAM_CONTEXT ctx;
    FltGetStreamContext(FltObjects->Instance, 
        FltObjects->FileObject, &ctx);
    
    if (ctx->IsEncrypted && ctx->IsTrustedProcess) {
        // 授信进程：解密
        PUCHAR buffer = Data->Iopb->Parameters.Read.DataBuffer;
        ULONG length = Data->Iopb->Parameters.Read.Length;
        
        // 流式解密：根据 ByteOffset 计算 CBC/AES 块的起始位置
        DecryptStream(buffer, length, 
            Data->Iopb->Parameters.Read.ByteOffset.QuadPart 
            - HIDDEN_HEADER_SIZE,
            ctx->KeyId, ctx->IV);
    }
    // 非授信进程：保持密文，不解密
    
    FltReleaseContext(ctx);
    return FLT_POSTOP_FINISHED_PROCESSING;
}
```

### 8.7.2 分配与释放 MDL

**📌 书中的世界**

当文件使用 `DO_DIRECT_IO` 时，用户缓冲区通过 MDL 描述。解密操作需要：

1. 通过 `MmGetSystemAddressForMdlSafe` 获取 MDL 映射的内核虚拟地址
2. 在该地址上进行解密操作
3. 操作后不需要显式释放映射（由 I/O 管理器在 IRP 完成时处理）

**🔍 第一性原理视角：MDL 是"用户缓冲区的内核视图"**

解密操作本质上是"修改内核中的明文"——这个明文要么在 `SystemBuffer`（Buffered I/O），要么在 MDL 映射的地址（Direct I/O），要么在用户地址本身（Neither I/O，极少见）。

**🏭 现代工业实践**

Minifilter 通过 `Data->Iopb->Parameters.Read.DataBuffer` 统一提供数据缓冲区指针，FltMgr 已经处理了 MDL 映射的细节。开发者不需要手动调用 `MmGetSystemAddressForMdlSafe`——这是 Minifilter 相比 legacy 模型的又一简化。

### 8.7.3 写请求加密

**📌 书中的世界**

写请求的加密流程：

1. Pre-write：转换偏移（+HIDDEN_HEADER_SIZE）
2. 加密用户缓冲区中的数据
3. 下发 IRP 到下层（此时数据是密文）
4. 下层写入磁盘的是密文

**🔍 第一性原理视角：加密是"下发前的原地操作"**

与读解密不同，写加密在 **pre-write**​ 中完成（而不是 post-write），因为：

- 加密后的数据需要下发到下层写入磁盘
- 如果在 post-write 中加密，下层已经写入了明文

**关键挑战**：加密必须是"流式的"——支持从任意偏移开始加密。AES-CBC 模式需要处理"前一块"的密文作为 CBC 链接的输入，这意味着：

- 如果写入不是"块对齐"的，需要读取前一块的密文
- 这又引入了"带外 I/O"（读取前一块），再次面临重入问题

**🏭 现代工业实践**

现代透明加密产品采用以下策略解决"流式加密"难题：

1. **块对齐写入**：强制写入偏移和长度为加密块大小（如 16 字节 AES 块）的整数倍
2. **Cipher Feedback 模式**：CFB 模式支持流式加密，不需要块对齐
3. **XTS-AES 模式**：专为磁盘加密设计，支持扇区级加密（BitLocker 使用 XTS-AES）
4. **双缓冲机制**：维护明文和密文两套缓冲，通过 `FltSetCallbackDataDirty` 标记脏页

> 💡 **洞见**：现代透明加密已经从传统的"CBC + 块对齐"演进到"XTS-AES + 流式处理"。XTS-AES 是 IEEE 1619 标准，专为存储设备加密设计，支持对任意偏移的数据进行独立加密——这正是透明加密需要的特性。

## 8.8 crypt_file 的组装

### 8.8.1 crypt_file 的初始化

**📌 书中的世界**

`crypt_file` 驱动的初始化：

1. `DriverEntry` 中注册派遣函数
2. 初始化文件加密表（自旋锁 + 链表）
3. 注册文件系统变动回调
4. 绑定文件系统 CDO，等待卷挂载
5. 绑定 VDO，开始过滤文件 I/O

**🔍 第一性原理视角：这是 sfilter 框架 + 加密逻辑的"组装"**

`crypt_file` = sfilter 框架（第7章）+ 加密表（8.5 节）+ 读写加解密（8.7 节）+ 缓冲管理（8.3 节）。

### 8.8.2 crypt_file 的 IRP 预处理

**📌 书中的世界**

在 pre-create/pre-read/pre-write 中：

1. 查询文件加密表，判断文件是否加密
2. 判断进程是否授信
3. 如果是加密文件 + 授信进程：准备解密/加密
4. 转换偏移
5. 下发 IRP 到下层

**🏭 现代工业实践**

Minifilter 版本的 crypt_file 预处理：

```
CONST FLT_OPERATION_REGISTRATION Callbacks[] = {
    { IRP_MJ_CREATE, 0, PreCreate, PostCreate },
    { IRP_MJ_READ, 0, PreRead, PostRead },
    { IRP_MJ_WRITE, 0, PreWrite, PostWrite },
    { IRP_MJ_CLEANUP, 0, PreCleanup, PostCleanup },
    { IRP_MJ_OPERATION_END }
};
```

Altitude 设置：`360000-389999` 范围（文件系统加密层）：

- 防病毒层：320000-329999（在加密层之上）
- **加密层：140000-149999 或 360000-389999**（在防病毒之下）
- 这样确保：防病毒看到的是明文（加密前），加密驱动看到的是原始数据

### 8.8.3 crypt_file 的 IRP 后处理

**📌 书中的世界**

在 post-read 完成例程中：

1. 检查 IRP 状态是否成功
2. 如果是加密文件 + 授信进程：解密数据
3. 如果是加密文件 + 非授信进程：不解密（保持密文）
4. 在 post-write 中：可能需要在写入完成后更新加密表状态

**🔍 第一性原理视角：后处理是"数据转换的最后机会"**

post 回调是修改 I/O 数据的最后窗口。在这里：

- 可以修改读取的数据（解密）
- 可以检查写入的结果（成功/失败）
- 可以更新文件状态（如文件大小变化）

**🏭 现代工业实践**

Minifilter 的 Post 回调架构：

```
FLT_POSTOP_CALLBACK_STATUS PostRead(...) {
    // 1. 检查 IRP 是否成功
    if (!NT_SUCCESS(Data->IoStatus.Status))
        return FLT_POSTOP_FINISHED_PROCESSING;
    
    // 2. 获取 Stream Context
    PSTREAM_CONTEXT ctx;
    FltGetStreamContext(..., &ctx);
    
    // 3. 如果是加密文件且授信进程：解密
    if (ctx->IsEncrypted && ctx->IsTrustedProcess) {
        DecryptData(Data->Iopb->Parameters.Read.DataBuffer,
                    Data->Iopb->Parameters.Read.Length,
                    Data->Iopb->Parameters.Read.ByteOffset.QuadPart);
    }
    
    FltReleaseContext(ctx);
    return FLT_POSTOP_FINISHED_PROCESSING;
}
```

## 🎯 本章核心洞见总结

读完第8章，我希望你带走的不只是"怎么写一个透明加密过滤驱动"，而是这四个**第一性原理**：

**1. 透明加密的本质是"视图隔离"，而非简单的"加解密"**

```
磁盘视图：密文（持久化）
    ↑ 加密/解密转换
内存视图：明文（运行时）
    ↑ 进程级视图隔离
授信进程：看到明文
非授信进程：看到密文
```

这个模型的核心是**两个转换 + 一个隔离**：

- 写转换：明文 → 密文（落盘前）
- 读转换：密文 → 明文（读取后）
- 进程隔离：确保非授信进程无法通过任何途径（IRP、缓存、内存映射）看到明文

**2. 缓存与内存映射是透明加密的"阿喀琉斯之踵"**

这是本章最重要的技术洞察。Windows 的缓存管理器和内存映射机制会让过滤驱动"看不见"某些数据访问：

- 预读导致非授信进程可能从缓存读取明文
- 延迟写导致密文不一致
- 内存映射文件让过滤驱动完全拦截不到数据访问

解决方案的演进：

- **第一代**：清除缓冲（简单但性能差，易导致文件损坏）
- **第二代**：双缓冲机制（明文缓冲 + 密文缓冲，按进程隔离）
- **第三代**：自定义文件系统驱动 + Minifilter 组合（最彻底但最复杂）

**3. 进程信任是加密体系的"信任根"**

整个加密体系的安全性依赖于"进程身份识别的可靠性"。从弱到强的识别方式：

- 进程名（最弱）
- 进程路径
- 进程签名（Authenticode）
- 进程 token + ACL

现代 DLP 产品普遍采用"进程名 + 路径 + 签名"的多因子鉴定，并在用户态服务中做进程验签，通过通信端口传递给内核。

**4. Legacy → Minifilter 是透明加密的必然演进**

书中基于 sfilter 的 legacy 实现，在现代 Windows 上应当迁移到 Minifilter：

|书中技术（Legacy sfilter）|现代做法（Minifilter）|优势|
|---|---|---|
|手动文件加密表（链表+锁）|Stream Context（FltMgr 托管）|自动生命周期管理|
|手动重入处理|`FltCreateFile`（无重入）|避免死循环|
|手动偏移转换 + 完成例程|Pre/Post 回调 + `Data->Iopb`|框架托管 IRP 生命周期|
|手动 Fast I/O 分发表|FltMgr 自动路由|无需关心 IRP/Fast I/O 差异|
|无确定性排序|Altitude 机制（加密层 140000-149999）|加密在防病毒之下，确定性强|
|无法动态卸载|`FltUnregisterFilter`|运行时动态加载/卸载|
|硬编码 EPROCESS 偏移|`FltGetRequestorProcess`|版本无关，文档化 API|

> 📌 **关键认知**：微软自 Windows Vista 起就强烈推荐 Minifilter 替代 Legacy Filter。2026 年的现代透明加密产品**几乎全部基于 Minifilter**。

**5. 工业产品的"第二代"演进：从文件加密到进程级视图隔离**

观察现代透明加密产品（如 TDE、Foxtrot）的架构，可以发现一个清晰的演进路径：

```
第一代：文件级加密
  - 写时加密、读时解密
  - 不区分进程
  - 问题：非授信进程可通过缓存/内存映射看到明文

第二代：进程级视图隔离
  - 同一个文件，授信进程看到明文视图，非授信进程看到密文视图
  - 双缓冲机制
  - 按进程粒度实施访问控制
  - 这是 2026 年企业 DLP 的主流方案
```
