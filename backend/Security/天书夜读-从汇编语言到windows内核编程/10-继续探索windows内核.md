
# 第 10 章 继续探索 Windows 内核

## 第一性原理：探索未知内核调用的本质是"恢复三件套"——ABI、数据结构、符号

当你面对一个 Windows 内核里"未文档化"或"文档不全"的函数调用时，本质上是在做三件事：

1. **恢复调用约定（ABI）**：参数怎么传？几个参数？谁清理栈？
2. **恢复数据结构**：参数指向什么内存布局？结构体字段是什么类型？
3. **恢复符号信息**：函数叫什么名字？属于哪个模块？它的语义是什么？

原书 2009 年写这一章时，微软公共符号服务器虽已存在但远不如今天完善，很多内核内部调用只能靠"反汇编 + 黑盒测试 + 数据结构对照"来还原。15 年后的今天，微软公共符号服务器已经能提供 ntoskrnl.exe、win32k.sys 等核心模块的丰富符号信息 ，但**探索未文档化调用的第一性原理没变**——你依然需要理解 ABI、数据结构和符号这三者的关系。

## 10.1 探索 Windows 已有内核调用

**原书意图**：教读者如何利用 WinDbg 的 `x` 命令枚举模块导出函数、用 `uf` 反汇编、用 `dt` 查看数据结构，从而理解一个已知名称的内核函数是如何工作的。

**现代工业标准做法**：

**第一步：找到目标函数**

```
# 枚举 nt 模块中所有以 "Io" 开头的函数
x nt!Io*

# 枚举所有以 "Nt" 开头的系统调用
x nt!Nt*

# 枚举特定驱动的导出函数
x kbdclass!*
x diskperf!*
```

**第二步：查看函数原型和数据结构**

```
# 查看函数反汇编
uf nt!IoCallDriver

# 查看数据结构定义
dt nt!_IRP
dt nt!_IO_STACK_LOCATION
dt nt!_KEVENT
```

**第三步：理解 WDM 公开接口**

微软在 `wdm.h` 头文件中声明了大量内核调用接口 。例如 `IoCallDriver` 的官方原型 ：

```
NTSTATUS IoCallDriver(
    IN PDEVICE_OBJECT DeviceObject,
    IN OUT PIRP Irp
);
```

- 调用前必须设置 IRP 中目标驱动的 I/O 栈位
- `IoCallDriver` 将 `DeviceObject` 参数赋给被调用驱动的 `IO_STACK_LOCATION` 结构的 `DeviceObject` 成员
- 调用后除非设置了 `IoCompletion` 例程，否则上层驱动无法再访问该 IRP
- IRQL 约束：`IRQL <= DISPATCH_LEVEL`

同理，`IoAllocateIrp` 用于在给定 I/O 栈位数量的情况下分配一个 IRP ；`IoAllocateWorkItem` 用于分配一个工作项 。

**第四步：动态追踪**

```
# 下断点
bp nt!IoCallDriver

# 查看调用栈
k

# 查看 IRP 内容
!irp <IRP地址>

# 查看设备对象
!devobj <DeviceObject地址>
```

> 💡 **洞见**：探索"已有内核调用"的第一性原理是——**从"名字"到"语义"的映射**。微软文档告诉你 `IoCallDriver` 的原型和 IRQL 约束 ，但文档不会告诉你：
> 
> - 它在什么场景下被调用（需要看调用栈 `k`）
> - 它的参数实际指向什么数据（需要 `dt` 查看结构体）
> - 它的返回值如何影响后续流程（需要 `!irp` 查看 IRP 状态）
> 
> 这就是为什么原书要把"探索已有调用"作为本章的开篇——**它训练的是"用调试器重建函数语义"的能力**。光看文档你只知道"what"，用 WinDbg 动态追踪你才知道"how"和"why"。

## 10.2 自己实现 XP 的新调用

### 第一性原理：实现未知调用 = 逆向工程 + 数据结构还原 + C 语言重写

原书 2009 年讲这一节时，面临的核心问题是：Windows XP 的某些内核内部调用没有公开文档，但驱动开发又需要用到它们。怎么办？答案是——**自己从反汇编中还原它的 C 语言原型**。

### 10.2.1 对照调试结果和数据结构

**原书意图**：通过在 WinDbg 中观察未知函数的调用现场（寄存器、栈、内存），推断它的参数个数、参数类型和返回值。

**具体方法**：

**1. 在目标函数上下断点，观察调用现场**

```
# 下断点
bp nt!UnknownFunction

# 触发调用后，查看寄存器
r

# 查看栈
k

# 查看栈上的参数
dd rsp
```

**2. 根据 x86 调用约定推断参数**

在 32 位 Windows 上，主流调用约定是 `__stdcall`：

- 参数从右到左压栈
- 被调用者清理栈（`ret n`）
- 返回值在 `EAX`

观察反汇编时：

```
; 调用前
push [esp+12]    ; 第 3 个参数
push [esp+8]     ; 第 2 个参数  
push [esp+4]     ; 第 1 个参数
call UnknownFunction
; 调用后
; EAX 包含返回值
```

**3. 识别数据结构**

通过观察函数内部如何访问参数指向的内存，推断结构体布局：

```
; 假设 [ebp+8] 是第一个参数（指针）
mov eax, [ebp+8]     ; eax = 参数1（指针）
mov ecx, [eax]       ; ecx = *(参数1) → 第一个字段
mov edx, [eax+4]     ; edx = *(参数1+4) → 第二个字段
```

由此推断：

```
typedef struct _UNKNOWN_STRUCT {
    ULONG Field1;    // 偏移 0
    ULONG Field2;    // 偏移 4
    // ... 更多字段
} UNKNOWN_STRUCT, *PUNKNOWN_STRUCT;
```

**4. 对照已知数据结构**

Windows 内核有很多"家族化"的数据结构模式。通过观察字段的用途，往往能猜出它属于哪一类：

- 如果第一个字段是 `Type` 和 `Size` → 可能是对象头（`_OBJECT_HEADER`）
- 如果包含 `ListEntry` → 可能是链表节点
- 如果包含 `SpinLock` → 可能是多线程共享结构

### 10.2.2 写出 C 语言的对应代码

**原书意图**：把反汇编分析结果写成可编译的 C 语言声明和封装函数。

**标准做法**：

```
// 1. 声明函数原型
typedef NTSTATUS (*PFN_UnknownFunction)(
    PUNKNOWN_STRUCT Param1,
    ULONG Param2,
    PVOID Param3
);

// 2. 获取函数地址
UNICODE_STRING funcName;
RtlInitUnicodeString(&funcName, L"UnknownFunction");
PFN_UnknownFunction UnknownFunction = 
    (PFN_UnknownFunction)MmGetSystemRoutineAddress(&funcName);

// 3. 调用
if (UnknownFunction) {
    NTSTATUS status = UnknownFunction(myStruct, 0x100, buffer);
}
```

**工业界最佳实践**：

- **永远用 `MmGetSystemRoutineAddress` 获取未文档化函数地址**——它会在运行时查找符号，避免硬编码地址
- **用 `typedef` 定义函数指针类型**——提高代码可读性
- **做好版本兼容**——未文档化函数在不同 Windows 版本中可能变化，需要运行时检测
- **封装成 C++ 类**（参考第 9 章）——用 RAII 管理资源

> ⚠️ **现代警示**：
> 
> 原书 2009 年鼓励"自己实现 XP 的新调用"，但在 2026 年的今天：
> 
> - 微软对未文档化接口的使用有**严格的合规性审查**
> - Windows 10/11 引入了 **PatchGuard（内核补丁保护）**​ 和 **HVCI（基于虚拟化的代码完整性）**，阻止内核被随意挂钩和修改
> - **Driver Verifier**​ 会检测对未文档化接口的异常使用
> - 微软官方强烈建议**只使用 WDK 文档化的 DDI 接口**
> 
> 今天的工业实践中，"自己实现未文档化调用"主要用于：
> 
> - **安全研究**（漏洞挖掘、rootkit 分析）
> - **兼容性层**（让老驱动在新系统上运行）
> - **性能优化**（访问未文档化的内部接口获取性能优势）
> 
> 但**生产环境驱动应尽量使用文档化接口**。

## 10.3 没有符号表的情况

**原书意图**：讲当 WinDbg 没有符号时，如何纯靠反汇编和调试器命令理解内核代码。

**这是原书时代的常态**——2009 年微软公共符号服务器虽有，但符号覆盖率远不如今天。很多内核内部函数没有符号，驱动开发者必须学会"盲调"。

**现代视角下的符号获取**：

今天微软公共符号服务器已经非常完善 ：

```
# 使用 .symfix 快速配置符号路径
.symfix C:\MyCache

# 或手动设置
set _NT_SYMBOL_PATH=srv*C:\MyCache*https://msdl.microsoft.com/download/symbols
```

配置后，WinDbg 会自动从微软服务器下载所需符号并缓存到本地 。这意味着：

- `ntoskrnl.exe`、`hal.dll`、`win32k.sys` 等核心模块**有完整符号**
- 大多数系统驱动**有公共符号**
- 第三方驱动**需要自己提供 .pdb**

**但"无符号"场景依然存在**：

- 第三方闭源驱动
- 恶意驱动/rootkit（故意剥离符号）
- 某些未文档化的内核内部函数
- 自己写的驱动忘记加载 .pdb

**无符号下的探索方法**：

**1. 利用调用约定推断参数**

```
; x86 __stdcall 示例
push eax            ; 参数3
push ebx            ; 参数2
push ecx            ; 参数1
call unknown_func
; 返回值在 EAX
```

从 `push` 指令个数和类型推断参数个数和大致类型。

**2. 利用相邻符号推断**

```

# 通过 known_func 的调用约定和上下文，推断 unknown_func 的用途
```

**3. 利用字符串引用推断**

```
# 在函数中搜索字符串引用
# 字符串往往揭示函数的功能
```

**4. 利用池标签（Pool Tag）推断**

```
# 函数中如果调用 ExAllocatePoolWithTag，池标签会揭示模块身份
# 如 'nbk' 标签 → 键盘类驱动（kbdclass）
```

**5. 利用 Driver Verifier 的增强诊断**

```

# 通过内存分配模式推断函数的内存使用习惯
```

> 💡 **洞见**：无符号调试的第一性原理是——**"代码即文档"**。当符号缺失时，反汇编代码本身就是最权威的信息源。原书 2009 年这一节训练的核心能力，在今天依然有价值：
> 
> - 看懂调用约定 → 推断参数
> - 看懂内存访问模式 → 推断数据结构
> - 看懂字符串和常量 → 推断功能语义
> - 看懂调用关系 → 推断模块归属
> 
> 现代工业界的安全研究员、恶意代码分析师，每天都在做这件事——因为恶意驱动必然是"无符号"的。掌握无符号调试能力，是内核安全研究的硬功夫。

## 10.4 64 位操作系统下的情况

### 第一性原理：x64 不是"32 位加宽"，而是一套全新的 ABI

原书 2009 年写这一章时，Windows XP x64 刚起步，主流还是 32 位系统。但今天 Windows 11 时代，**x64 是唯一主流**——ARM64 虽然兴起但市场份额仍小。理解 x64 调用约定，是现代 Windows 内核开发的**必修课**。

### 10.4.1 分析 64 位操作系统的调用

**x64 调用约定的核心规则**（微软官方文档 ）：

**1. 参数传递：寄存器优先**

- 第 1-4 个整型参数：`RCX`, `RDX`, `R8`, `R9`
- 第 5 个及以后的参数：栈上传递
- 浮点参数：`XMM0`-`XMM3`

**2. 影子空间（Shadow Space）**

- 调用方必须在栈上分配 **32 字节（4 个 qword）**​ 的影子空间
- 即使被调用函数不用，调用方也必须分配
- 影子空间允许被调用函数将寄存器参数转储到栈上

**3. 栈对齐**

- 调用前 `RSP` 必须 **16 字节对齐**
- 函数入口处 `[RSP]` 是返回地址

**4. 寄存器易失性**

- **易失寄存器**（调用方保存）：RAX, RCX, RDX, R8-R11, XMM0-XMM5
- **非易失寄存器**（被调用方保存）：RBX, RBP, RDI, RSI, R12-R15, XMM6-XMM15

**实例分析**：

假设有一个 x64 内核函数：

```
NTSTATUS UnknownFunc(PDEVICE_OBJECT DeviceObject, PIRP Irp, 
                     ULONG ControlCode, PVOID InputBuffer);
```

调用时的汇编模式：

```
; 参数准备
mov rcx, rax                    ; RCX = DeviceObject（参数1）
mov rdx, rbx                    ; RDX = Irp（参数2）
mov r8d, ecx                    ; R8 = ControlCode（参数3）
mov r9, input_buffer            ; R9 = InputBuffer（参数4）

; 分配影子空间
sub rsp, 32                     ; 32 字节影子空间

; 调用
call UnknownFunc

; 清理影子空间
add rsp, 32

; 返回值在 RAX
```

**反汇编识别技巧**：

```
; 看到这种模式，就知道是函数调用：
; 1. 设置 RCX/RDX/R8/R9
; 2. sub rsp, 20h（分配 32 字节影子空间）
; 3. call xxx
; 4. add rsp, 20h（清理影子空间）
```

**系统调用的特殊约定**：

在 x64 Windows 上，用户态通过 `syscall` 指令进入内核 （：

- **RAX**​ = 系统调用号
- **RCX**​ = 第 1 个参数
- **RDX**​ = 第 2 个参数
- **R8**​ = 第 3 个参数
- **R9**​ = 第 4 个参数
- 返回值在 **RAX**

> ⚠️ **注意**：由于 `syscall` 指令会破坏 `RCX`，`ntdll.dll` 的存根会先把原始的第一个参数复制到 `R10`，内核从 `R10` 读取第一个参数。

### 10.4.2 深入了解 64 位内核调用参数传递

**原书意图**：深入分析 x64 下参数传递的细节，特别是复杂数据类型（结构体、浮点数、聚合类型）的传递方式。

**微软官方文档的详细规则**​ ：

**1. 整型参数**

```
func1(int a, int b, int c, int d, int e, int f);
; a in RCX, b in RDX, c in R8, d in R9
; e 和 f 在栈上（e 在高地址，f 在低地址）
```

**2. 浮点参数**

```
func2(float a, double b, float c, double d, float e, float f);
; a in XMM0, b in XMM1, c in XMM2, d in XMM3
; e 和 f 在栈上
```

**3. 混合参数**

```
func3(int a, double b, int c, float d, int e, float f);
; a in RCX, b in XMM1, c in R8, d in XMM3
; e 和 f 在栈上
```

**4. 聚合类型（结构体）**

- 大小为 8/16/32/64 位的结构体：作为整型传递
- 其他大小的结构体：**作为指针传递**（调用方分配内存，传递指针）
- `__m128`：**作为指针传递**

**对内核编程的意义**：

**1. 结构体作为参数**：

```
// 小结构体（≤ 64 位）直接传值
typedef struct _SMALL_STRUCT {
    ULONG Field1;
    ULONG Field2;
} SMALL_STRUCT;  // 64 位，通过 RCX/RDX 等寄存器传递

// 大结构体通过指针传递
typedef struct _LARGE_STRUCT {
    ULONG Field1;
    ULONG Field2;
    ULONG Field3;
    ULONG Field4;
    ULONG Field5;
} LARGE_STRUCT;  // 160 位，通过指针传递
```

**2. 内核函数调用示例**：

```
// IoCallDriver 的 x64 调用约定
// RCX = DeviceObject（参数1）
// RDX = Irp（参数2）
// 返回值在 RAX
mov rcx, device_object
mov rdx, irp
sub rsp, 32                    ; 影子空间
call nt!IoCallDriver
add rsp, 32
; RAX = NTSTATUS 返回值
```

**3. 反汇编实战**：

从 C++ 汇编/反汇编的角度分析 ：

假设我们反汇编 `IoCallDriver` 的调用者：

```
sub_fffff800`00123456 proc near
    ; 函数序言
    push rbp
    mov rbp, rsp
    sub rsp, 40h
    
    ; 调用 IoCallDriver
    mov rcx, [rbp+10h]        ; RCX = DeviceObject
    mov rdx, [rbp+18h]        ; RDX = Irp
    call qword ptr [IoCallDriver]  ; 间接调用
    
    ; 返回值在 RAX
    mov [rbp-8], rax           ; 保存 NTSTATUS
    
    ; 函数尾声
    add rsp, 40h
    pop rbp
    ret
sub_fffff800`00123456 endp
```

通过反汇编，我们可以确认：

- 参数通过 `RCX` 和 `RDX` 传递（符合 x64 调用约定）
- 返回值通过 `RAX` 获取
- 函数使用了 32 字节的影子空间（包含在 `sub rsp, 40h` 中）

**4. 与 x86 的关键差异**：

|维度|x86 (__stdcall)|x64 (Microsoft x64)|
|---|---|---|
|参数传递|栈（右到左）|寄存器 RCX/RDX/R8/R9 + 栈|
|栈清理|被调用者 (`ret n`)|调用者（清理影子空间+参数）|
|返回值|EAX|RAX|
|栈对齐|4 字节|16 字节|
|this 指针|ECX（thiscall）|RCX（第一个参数）|
|调用约定种类|**stdcall/**cdecl/__fastcall/thiscall|**唯一一种**​|

> 💡 **洞见**：x64 调用约定的第一性原理是——**"寄存器优先 + 影子空间兜底"**。微软在设计 x64 ABI 时做了一个关键决策：**用寄存器传递前 4 个参数**（性能优化），同时**强制分配 32 字节影子空间**（正确性保障）。这个设计的精妙之处在于：
> 
> 1. **性能**：80% 的函数调用不超过 4 个参数，寄存器传递避免了内存访问
> 2. **正确性**：影子空间保证了即使被调用函数需要，也能将寄存器参数转储到已知位置
> 3. **统一性**：消除了 x86 时代 **stdcall/**cdecl/__fastcall 的混乱，只有一种调用约定
> 4. **调试友好**：统一的约定让反汇编和调试变得可预测
> 
> 原书 2009 年讲 32 位调用约定时，重点是"识别 __stdcall 的 `ret n` 模式"；今天讲 x64，重点是"识别 RCX/RDX/R8/R9 + `sub rsp, 20h` 的模式"。**模式的载体变了，但"通过调用约定反推参数"的方法论没变**。
> 
> 这就是为什么理解 x64 调用约定对内核安全研究至关重要：
> 
> - **逆向工程**：看到 `RCX` 被设置，就知道这是第一个参数
> - **漏洞挖掘**：参数验证不严 → 从 `RCX`/`RDX`/`R8`/`R9` 传入的用户态数据可能导致提权
> - **Rootkit 分析**：挂钩内核函数时，必须正确保存和恢复 RCX/RDX/R8/R9
> - **驱动开发**：调用约定错误 → 参数错位 → 系统崩溃

**现代工业实践——x64 内核开发的最佳实践**：

**1. 使用 `/kernel` 模式编译**：

```
cl /kernel /GS /W4 /WX /Zi /Od ...
```

**2. 遵循 IRQL 约束**：

- 大部分内核 API 要求在 `IRQL <= DISPATCH_LEVEL` 调用
- 使用 `PAGED_CODE()` 宏标记分页代码

**3. 使用 WDF 框架**：


# 第 10 章的知识地图与前后联系

把这一章放进全书脉络：

```
第 8 章：环境与调试（工具链闭环）
第 9 章：用 C++ 编写内核程序（C++ 语法子集）
                ↓
第 10 章：继续探索 Windows 内核（ABI + 数据结构 + 符号）← 你在这里
                ↓
第 11+ 章：过滤驱动实战（键盘/磁盘/文件系统/网络过滤）
```

**为什么"继续探索 Windows 内核"是过滤驱动实战的前置技能？**

因为后面所有过滤驱动实战的本质，都是**拦截并理解内核中的未知调用**：

- **键盘过滤**：需要理解 `KbdClass` 驱动如何处理按键数据——通过 `dt kbdclass!_KEYBOARD_INPUT_DATA` 查看数据结构
- **磁盘过滤**：需要理解 `DiskPerf` 等驱动如何拦截磁盘 I/O——通过 `uf diskperf!xxx` 反汇编分析
- **文件系统过滤**：需要理解 `fltmgr.sys` 的 Minifilter 回调机制——通过符号和文档结合分析
- **网络过滤**：需要理解 `tcpip.sys` 的 WFP 调用流程——通过 `x tcpip!*Wfp*` 枚举相关函数

**没有第 10 章的"探索未知内核调用"的能力，后面所有过滤驱动实战都是"盲人摸象"**——你不知道要拦截的函数长什么样、参数怎么传、数据结构是什么布局。

**2009 → 2026 的演进主线**：

|维度|原书时代（2009）|今天（2026）|
|---|---|---|
|主流架构|32 位 x86 为主|64 位 x64 为主，ARM64 兴起|
|调用约定|**stdcall/**cdecl/__fastcall 多种|**x64 唯一调用约定**（RCX/RDX/R8/R9）|
|符号获取|公共符号服务器初步可用|**公共符号服务器完善**​ ，自动下载+本地缓存|
|未文档化接口|常用，微软审查较松|严格受限，PatchGuard/HVCI 阻止滥用|
|探索工具|WinDbg 基础命令|WinDbg + 静态分析（IDA Pro/Ghidra）+ 符号服务器|
|系统调用机制|`int 0x2e` 或 `sysenter`|**`syscall` 指令**​|
|服务表|SSDT 直接存函数指针|SSDT 存编码偏移（需解码）|
|工业实践|大量使用未文档化接口|**优先使用文档化 DDI**，未文档化仅用于研究|

> 📌 **终极洞见**：第 10 章教给你的不是"怎么调用一个未知函数"，而是**Windows 内核探索的方法论**——**"ABI 识别 → 数据结构还原 → 符号辅助 → 动态验证"的四步法**。
> 
> 这个方法论的第一性原理是：
> 
> 1. **ABI 是固定的**：x86 的 `__stdcall` 规则、x64 的 RCX/RDX/R8/R9 规则，都是**编译器和操作系统共同遵守的契约**
> 2. **数据结构是可推断的**：通过内存访问模式、池标签、字符串引用，可以反推结构体的字段布局
> 3. **符号是桥梁**：微软公共符号服务器让"已知调用"的探索变得轻松，但"未知调用"仍需黑盒分析
> 4. **动态验证是真理**：无论静态分析多么完美，最终都要通过 WinDbg 动态追踪验证
> 
> 原书 2009 年讲这一章时，处于"32 位为主、符号不完善、未文档化接口盛行"的时代。15 年后的今天：
> 
> - **x64 成为绝对主流**，调用约定统一化让逆向分析更可预测
> - **符号服务器完善**，已知接口的探索效率大幅提升
> - **PatchGuard/HVCI 的引入**，让未文档化接口的滥用变得极其危险
> - **静态分析工具（IDA Pro 8.x/Ghidra）成熟**，让无符号分析能力大幅提升
> 
> **这就是为什么这一章在今天依然具有不可替代的价值**：
> 
> - 方法论文档化：它教你在"没有文档"的情况下如何工作
> - 安全研究刚需：恶意驱动必然是"无符号"的，必须掌握黑盒分析能力
> - 兼容性层必需：让老驱动在新 Windows 上运行，必须理解内部接口
> - 内核深入理解：只使用文档化接口无法理解 Windows 内核的全貌
> 
> **工业界今天的真实做法**：
> 
> - **已知接口**：通过 WDK 文档 + 公共符号服务器 + WinDbg 动态追踪
> - **未文档化接口**：仅用于安全研究和兼容性层，生产驱动必须使用文档化 DDI
> - **x64 逆向**：掌握 RCX/RDX/R8/R9 + 影子空间的识别模式
> - **无符号调试**：IDA Pro/Ghidra + WinDbg 组合，配合池标签和字符串引用推断
> - **系统调用分析**：理解 `syscall` 指令 + `RAX` 系统调用号 + `KiServiceTable` 编码偏移
> - **防御性编程**：使用 Driver Verifier 的 DDI Compliance Checking 检测违规调用
> - **现代框架**：优先使用 KMDF/UMDF，框架已经封装了大部分底层调用约定细节
> 
> 原书 2009 年的"自己实现 XP 的新调用"在今天看来可能"过时"，但其背后的**探索精神和方法论**——面对未知时不退缩，通过系统化分析还原真相——这正是内核安全研究的核心素养。15 年过去了，Windows 内核的表面积扩大了百倍，但"探索未知"的方法论依然是内核程序员的立身之本。
