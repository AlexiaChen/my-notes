# 第 4 章 内核字符串与内存

## 4.1 字符串的处理

### 第一性原理：内核里的"字符串"不是字符串，是"带边界的字节序列描述"

用户态 C 程序员习惯 `char*` + `\0` 终止符。但**内核不能信任任何来自用户态的"字符串"**——它没有边界、可以被截断、可以跨特权边界、可以在你读取途中被另一线程改写。所以 Windows 内核设计了一个**自描述结构**​ `UNICODE_STRING`：

```
typedef struct _UNICODE_STRING {
    USHORT Length;         // 当前字符串的字节数，不含结尾 \0
    USHORT MaximumLength;  // Buffer 的总字节容量
    PWSTR  Buffer;         // 指向宽字符缓冲区的指针
} UNICODE_STRING, *PUNICODE_STRING;
```

微软官方文档明确三点 ：

- `Length` 是**已使用字节数**，不含结尾 `\0`（如果存在）
- `MaximumLength` 是 `Buffer` 的容量上限，转换类例程（如 `RtlAnsiStringToUnicodeString`）靠它保证不越界
- 初始化必须用 `RtlUnicodeStringInit` 或 `RtlUnicodeStringInitEx`，老式的 `RtlInitUnicodeString` 仍在广泛使用

> 💡 **我的洞见**：`UNICODE_STRING` 的本质是**"能力（capability）+ 长度（length）+ 数据（data）"三位一体的安全契约**。这是内核编程的第一性原理之一——**任何跨越信任边界的数据，都必须自带边界描述**。用户态的 `\0` 终止符模型在内核里是**不安全**的，因为：
> 
> 1. 遍历找 `\0` 是 O(n)，内核要求可预测的执行时间
> 2. 用户态缓冲区可能不含 `\0`，遍历会越界到内核地址空间
> 3. 用户态可以在内核读取中途改变缓冲区内容（TOCTOU 竞态）
> 
> 所以 `Length` 字段的存在，不是为了"优化 strlen"，而是为了**把字符串变成一种"内核可安全消费"的不变量**。这是原书 2009 年可能不会明说、但今天在做安全驱动时必须刻进骨子里的认知。

### 4.1.1 使用字符串结构

**原书意图**：告诉你内核里不要用 `wchar_t*`，要用 `UNICODE_STRING`。

**现代延伸**：

- `UNICODE_STRING` 在 ntdef.h / wdm.h / ntddk.h 中定义 ，是**整个 Windows 内核的通用语**——对象名、注册表键、文件路径、设备名，全都是它
- 与之配套的还有 `ANSI_STRING` 和 `OEM_STRING`，但**现代驱动开发强烈建议只用 `UNICODE_STRING`**，ANSI 版本仅用于遗留兼容
- 在 WDF（Windows Driver Framework）里，`UNICODE_STRING` 依然是核心类型，WDF 的对象属性、名称、ID 全靠它承载

**工业实践**：今天写 KMDF 驱动时，`UNICODE_STRING` 常配合 `WDFSTRING` 对象使用，由 WDF 接管生命周期，避免原书时代手动管理 Buffer 导致的泄密/越界。

### 4.1.2 字符串的初始化

**原书可能讲两种方式**：

1. `RtlInitUnicodeString(&str, L"hello")` —— 栈上/只读数据段的字符串，Buffer 指向源字符串，**不拷贝**
2. 自己 `ExAllocatePool` 分配 Buffer，再 `RtlCopyUnicodeString` —— 可变字符串

**⚠️ 关键陷阱**（原书可能提及但未充分强调）：

- `RtlInitUnicodeString` 初始化的字符串，**Buffer 指向的是源字符串常量**。如果你把这个 `UNICODE_STRING` 传给某个会修改 Buffer 的内核 API，会触发**写入只读段异常**（Bug Check 0xBE: ATTEMPTED_WRITE_TO_READONLY_MEMORY）
- 微软现在推荐 `RtlUnicodeStringInit` 系列，因为它会**做边界检查并返回状态码**，而 `RtlInitUnicodeString` 不返回状态，出错时直接崩

**现代最佳实践**：

```
// 旧式（原书风格）
UNICODE_STRING str;
RtlInitUnicodeString(&str, L"my_driver");

// 新式（推荐）
UNICODE_STRING str;
NTSTATUS status = RtlUnicodeStringInit(&str, L"my_driver");
if (!NT_SUCCESS(status)) {
    // 处理错误：源字符串太长或 NULL
}
```

### 4.1.3 字符串的拷贝

**原书意图**：讲 `RtlCopyUnicodeString`、`RtlAppendUnicodeStringToString` 等。

**第一性原理**：字符串拷贝在内核里不是"便利操作"，而是**资源分配决策**——

- 目标 Buffer 谁分配？
- 目标 Buffer 多大？
- 拷贝发生在哪个 IRQL？
- 源字符串来自用户态还是内核态？（涉及 `ProbeForRead` 探针）

**现代延伸**：

- `RtlCopyUnicodeString` 要求目标 `UNICODE_STRING` 的 `Buffer` 已经分配好，且 `MaximumLength` 足够
- 如果要从 `ANSI_STRING` 转换到 `UNICODE_STRING`，用 `RtlAnsiStringToUnicodeString`，这个函数**内部会分配内存**，调用者必须配对调用 `RtlFreeUnicodeString` 释放 ——这是内核内存泄漏的高发点
- 工业界驱动静态分析工具（如 PREfast/SDV）会专门检查 `RtlAnsiStringToUnicodeString` 与 `RtlFreeUnicodeString` 的配对

> 💡 **洞见**：字符串拷贝在内核里本质是"跨信任边界的数据搬运"。每一次拷贝都是一次潜在的**信息泄露面**（忘记清零的池内存）或**拒绝服务面**（用户传入超长字符串耗尽非分页池）。这也是为什么 Windows 10 2004 之后引入的新池分配 API 默认**清零内存**——直接消灭一类信息泄露 Bug。

### 4.1.4 字符串的连接

**原书意图**：`RtlAppendUnicodeStringToString`、`RtlAppendUnicodeToString`。

**工业现实**：

- 连接操作最大的坑是**目标缓冲区溢出**。原书时代可能靠程序员自觉检查 `MaximumLength`，今天这套做法在静态分析器里会被标记为高风险
- 现代 WDF 驱动倾向于使用 **WDFSTRING 对象**​ + `WdfStringCreate` / `WdfStringGetUnicodeString`，由框架托管缓冲区生命周期
- 对于路径拼接等场景，微软推荐使用 `IoGetDosDevicePath` 等专用 API，而非手工拼字符串

### 4.1.5 字符串的打印

**原书意图**：`DbgPrint` / `KdPrint` 配合 `%wZ` 格式符打印 `UNICODE_STRING`。

**关键知识点**：

- `%wZ` 是内核专属格式符，对应 `UNICODE_STRING*`
- `%Z` 对应 `ANSI_STRING*`
- 普通 `%ws` 期望的是 `wchar_t*`，**不是**​ `UNICODE_STRING`——混用会崩

**现代延伸**：

- `DbgPrint` 在生产驱动里应该**完全移除或用 `DbgPrintEx` 配合过滤等级**，否则会泄露敏感信息且影响性能
- Windows 10 之后推荐 `DbgPrintEx` + `DPFLTR` 掩码，配合注册表 `Debug Print Filter` 控制输出
- 工业级驱动还会集成 **ETW（Event Tracing for Windows）**​ 做结构化日志，远比 `DbgPrint` 强大

## 4.2 内存与链表

### 4.2.1 内存的分配与释放

这是**原书与当今差异最大的一节**，必须重点展开。

**原书可能讲**：`ExAllocatePoolWithTag(PoolType, Size, Tag)`。

**🚨 重大变更**：`ExAllocatePoolWithTag` 已在 **Windows 10 版本 2004 被弃用**，微软官方明确替换为 `ExAllocatePool2` 和 `ExAllocatePool3` 。

**为什么弃用？第一性原理视角**：

旧 API 分配的内存**不自动清零**。驱动作者必须手动调用 `RtlZeroMemory`，但很多人忘记这么做——导致**内核池内存信息泄露**（用户态程序通过 IOCTL 读到内核残留的其他驱动/进程的敏感数据）。这是过去十年 Windows 内核漏洞的高频来源之一。新 API `ExAllocatePool2` **默认把分配的内存清零**​ ，从 API 层面消灭了这类 Bug。

**对照代码**：

```
// 旧式（原书风格，现已弃用）
PVOID buf = ExAllocatePoolWithTag(NonPagedPool, 100, 'dcba');
if (buf) RtlZeroMemory(buf, 100);

// 新式（Windows 10 2004+ 推荐）
PVOID buf = ExAllocatePool2(POOL_FLAG_NON_PAGED, 100, 'dcba');

// 高级分配（带优先级、配额等）
POOL_EXTENDED_PARAMETER params = {0};
params.Type = PoolExtendedParameterPriority;
params.Priority = HighPoolPriority;
PVOID buf = ExAllocatePool3(POOL_FLAG_NON_PAGED, 100, 'dcba', &params, 1);
```

**池类型与 IRQL 的硬约束**（原书讲了，但今天仍绝对适用）：

- `IRQL <= APC_LEVEL`：可以用 `PagedPool`（分页池）
- `IRQL <= DISPATCH_LEVEL`：只能用 `NonPagedPool`（非分页池），因为在 DISPATCH_LEVEL 及以上时**页面调度被禁用**，访问分页池会直接蓝屏
- 64 位系统上，池分配按 **16 字节边界对齐**；32 位系统按 8 字节对齐
- `NumberOfBytes >= PAGE_SIZE` 时分配页对齐的缓冲区

**池标签（Pool Tag）的工程意义**：

- 标签是 1-4 个 ASCII 字符，通常用反向写法如 `'1gaT'`
- 每个分配代码路径应用**唯一标签**，WinDbg 的 `!pool` 命令和 `poolmon` 工具可以按标签统计内存用量
- 这是排查内核内存泄漏的**首要武器**——原书时代就这么强调，今天依然是工业界标配

> 💡 **我的洞见**：内核内存分配的第一性原理是——**内存不是"资源"，而是"责任"**。每次 `ExAllocatePoolX` 都意味着：
> 
> 1. 你承诺在某个明确的时刻 `ExFreePool` 释放它
> 2. 你承诺在分配的 IRQL 下使用它（分页/非分页）
> 3. 你承诺不让它越界（否则池头部损坏，系统崩潰）
> 4. 你承诺不让它泄露敏感数据（否则新 API 默认清零）
> 
> 现代驱动框架（WDF）把这些"承诺"封装成了对象生命周期——WDF 对象销毁时自动释放关联的内存。这背后的哲学转变是：**能用 RAII/对象模型解决的，就不要让程序员手动管**。原书 2009 年基于 WDM 的裸写风格，今天在 KMDF 里大部分已被框架接管。但**理解底层 `ExAllocatePoolX` 的语义，依然是调试 WDF 驱动、排查池损坏 Bug 的必备功力**——框架帮你省事，但不会替你理解。

### 4.2.2 使用 LIST_ENTRY

**原书意图**：讲 Windows 内核里如何用 `LIST_ENTRY` 实现双向链表。

**LIST_ENTRY 结构**（微软官方定义 ）：

```
typedef struct _LIST_ENTRY {
    struct _LIST_ENTRY *Flink;  // 前向指针
    struct _LIST_ENTRY *Blink;  // 后向指针
} LIST_ENTRY, *PLIST_ENTRY;
```

**第一性原理视角**：Windows 内核链表的精妙之处在于——**链表节点与数据解耦**。`LIST_ENTRY` 本身不带任何 payload，它被**嵌入**到你自己的数据结构里：

```
typedef struct _MY_DATA {
    LIST_ENTRY ListEntry;   // 嵌入链表节点
    ULONG Key;
    PVOID Data;
} MY_DATA, *PMY_DATA;
```

这样设计的好处（这是原书可能讲了但值得深度展开的）：

1. **同一数据结构可以同时属于多个链表**——只要嵌入多个 `LIST_ENTRY` 成员
2. **链表操作代码完全泛型化**——系统提供的 `InsertHeadList`/`RemoveEntryList` 等例程只认 `LIST_ENTRY`，不认你的数据结构
3. **遍历时通过 `CONTAINING_RECORD` 宏反向拿到宿主结构**：
    
    ```
    PMY_DATA data = CONTAINING_RECORD(listEntry, MY_DATA, ListEntry);
    ```
    

**关键规则**：

- 链表头必须调用 `InitializeListHead` 初始化
- Windows 的 `LIST_ENTRY` 链表是**循环双向链表**——空表时头的 Flink/Blink 都指向自己
- **不要手动改 Flink/Blink**，必须用系统例程（`InsertHeadList`、`InsertTailList`、`RemoveEntryList` 等）
- 在 SMP 环境下操作链表，必须用 **`ExInterlockedXxx` 系列**（`ExInterlockedInsertHeadList`、`ExInterlockedRemoveHeadList` 等），它们内部加自旋锁

**工业界现状**：

- 活跃进程列表（`PsActiveProcessHead`）、线程列表、PEB 里的模块加载列表——**整个 Windows 内核到处都是 `LIST_ENTRY`**​
- 调试时 `!list` 命令可以直接遍历
- 现代驱动开发中，WDF 提供了更高级的集合抽象（WDFCOLLECTION），但底层关键数据结构（如 EPROCESS 的 `ActiveProcessLinks`）依然是 `LIST_ENTRY`

> 💡 **洞见**：`LIST_ENTRY` 的设计体现了 Windows 内核架构的一个核心思想——**用统一的元语构建整个系统**。一个小小的两个指针的结构，撑起了从进程管理到内存管理到设备栈的整套基础设施。理解 `LIST_ENTRY` + `CONTAINING_RECORD` 这对组合，等于拿到了"看懂 Windows 内核数据结构"的钥匙。原书把它放在第 4 章讲，正是因为它后面每一章（键盘过滤、磁盘过滤、文件系统过滤）都会反复用到。

### 4.2.3 使用长长整型数据

**原书意图**：讲 `LARGE_INTEGER` / `ULARGE_INTEGER`——64 位整数的内核表示。

**结构定义**：

```
typedef union _LARGE_INTEGER {
    struct {
        ULONG LowPart;
        LONG HighPart;
    } u;
    LONGLONG QuadPart;
} LARGE_INTEGER, *PLARGE_INTEGER;
```

**为什么需要它？第一性原理**：

- 32 位系统上，`LONGLONG` 不是原子类型——对它赋值/读取可能需要多条指令
- 文件偏移、文件大小、性能计数器、时间戳都需要 64 位表示
- `LARGE_INTEGER` 用 union 同时提供"高低 32 位分别访问"和"整体 64 位访问"两种视角

**现代延伸**：

- 原书 2009 年主要面向 32 位系统，那时 `LARGE_INTEGER` 的高低拆分访问很有必要
- 今天 x64 系统上 `LONGLONG` 是原生原子操作，但**为了 ABI 兼容性**，`LARGE_INTEGER` 这个类型依然在所有内核 API 里出现（如 `ZwReadFile` 的 `ByteOffset` 参数）
- 工业界代码中，**优先用 `QuadPart` 成员**访问，除非你需要兼容极老的 32 位环境
- WDF 驱动里，`LARGE_INTEGER` 依然频繁出现在 `WDFMEMORY` 描述符、`WDF_REQUEST_PARAMETERS` 等结构里

> 💡 **洞见**：`LARGE_INTEGER` 是"ABI 稳定性压倒语言便利性"的典型案例。C 语言早在 C99 就有了 `long long`，但 Windows 内核 API 为了不破坏 1990 年代以来的二进制兼容性，至今坚持用这个 union 结构。读懂这一点，你就能理解为什么 Windows 内核编程里有那么多"看起来很怪"的类型——**它们都是历史演化的活化石，每一个都有它存在的工程理由**。

### 4.2.4 使用自旋锁

**原书意图**：讲 `KSPIN_LOCK` + `KeAcquireSpinLock` / `KeReleaseSpinLock`。

**自旋锁的本质**（第一性原理）：

自旋锁不是"互斥锁"。它是**"关调度 + 总线原子操作"的组合拳**：

1. `KeAcquireSpinLock` 第一步：**把当前 CPU 的 IRQL 提升到 DISPATCH_LEVEL**——这意味着该 CPU 上不会再发生线程切换，也不会再响应低于 DISPATCH_LEVEL 的中断
2. 第二步：在锁上做原子测试-置位（test-and-set），如果锁已被其他 CPU 持有，则**忙等（自旋）**直到锁释放
3. `KeReleaseSpinLock` 必须传入获取锁时保存的 `OldIrql`，用来**恢复原来的 IRQL**​

**微软官方文档强调的硬规则**​ ：

- ⚠️ 持锁期间代码**不可分页**——不能引用任何可分页数据
- ⚠️ 持锁期间**不能调用**可能访问可分页数据或产生异常的外部函数
- ⚠️ **不能递归获取**自旋锁——保证死锁
- ⚠️ 必须**尽快释放**——因为调度被禁用，系统实时性受影响
- ⚠️ 只能在 `IRQL <= DISPATCH_LEVEL` 调用 `KeAcquireSpinLock`
- ⚠️ 不能用同一个 `OldIrql` 变量保存两个不同锁的旧 IRQL，否则竞态

**与 LIST_ENTRY 的配合**：

```
KSPIN_LOCK ListLock;
LIST_ENTRY MyList;

// 初始化
KeInitializeSpinLock(&ListLock);
InitializeListHead(&MyList);

// 插入（原子操作 + 自旋锁保护）
ExInterlockedInsertHeadList(&MyList, &entry->ListEntry, &ListLock);
```

`ExInterlockedXxxList` 系列例程内部会获取指定的自旋锁，操作完成后释放 。**关键约束**：用于 `ExInterlockedXxxList` 的自旋锁**不能用于其他目的**——它专门服务于这些原子链表操作 。

**现代工业实践的演进**：

1. **排队自旋锁（Queued Spin Lock）**：`KeAcquireInStackQueuedSpinLock` 系列，在多 CPU 竞争激烈时性能优于传统自旋锁，避免了"缓存行 bouncing"
2. **WDF 框架的自旋锁**：`WdfSpinLockCreate` + `WdfSpinLockAcquire` / `WdfSpinLockRelease`，由框架管理生命周期
3. **更细粒度的同步原语**：
    - 短期临界区用**互锁操作**（`InterlockedIncrement` 等）
    - 长期持有用**推锁（Push Lock）**——共享/独占混合模式，读多写少场景性能极佳
    - 被动级别（PASSIVE_LEVEL）用**快速互斥体（Fast Mutex）**或 **ERESOURCE**
4. **Driver Verifier**​ 会检测自旋锁的滥用——持锁时间过长、在错误 IRQL 获取、递归获取等

> 💡 **我的洞见**：自旋锁是内核同步里"最锋利的刀"——用得好，它是多处理器安全的基石；用不好，它就是系统挂起的元凶。原书 2009 年讲自旋锁时，系统大多是双核、四核；今天服务器 64 核、128 核已是常态，**自旋锁的"忙等"成本被指数级放大**——一个 CPU 在 DISPATCH_LEVEL 自旋 1 毫秒，意味着该 CPU 上所有线程都被冻结 1 毫秒。这就是为什么现代驱动开发强烈建议：
> 
> - **能不用自旋锁就不用**——优先考虑 WDF 框架提供的更高级同步对象
> - **必须用时，临界区代码控制在几十条指令以内**
> - **读多写少场景用 Push Lock 替代自旋锁**
> - **永远不要在自旋锁保护的临界区里调用外部函数**——这条铁律 15 年来从未改变，未来也不会改变

```
第 5+ 章：键盘过滤、磁盘过滤、文件系统过滤、网络过滤（"内核对象与请求"的实战）
```

**第 4 章的核心地位**：它是从"通用 C 编程"过渡到"Windows 内核编程"的桥梁。前面三章讲的是"任何 C 程序都适用的底层知识"，从第 4 章开始，你接触的每一个概念都是**Windows 内核特有的**：

- `UNICODE_STRING` → 后面每一章的设备名、对象名、文件路径都用它
- `ExAllocatePoolX` → 后面每一章的驱动对象、设备扩展、请求上下文都靠它分配
- `LIST_ENTRY` → 后面键盘过滤的键值队列、磁盘过滤的请求跟踪、文件系统的上下文管理，全都用它
- `KSPIN_LOCK` → 后面所有涉及多处理器安全的场景都用它

**2009 → 2025 的演进主线**（这是读这一章时最该建立的认知）：

|维度|原书时代（2009）|今天（2025-2026）|
|---|---|---|
|字符串|`RtlInitUnicodeString` 为主|`RtlUnicodeStringInit` + WDFSTRING 对象|
|内存分配|`ExAllocatePoolWithTag`（不自动清零）|`ExAllocatePool2/3`（默认清零，防信息泄露）|
|链表|`LIST_ENTRY` + 手动自旋锁|`LIST_ENTRY` + `ExInterlockedXxx` + WDF 集合抽象|
|同步|自旋锁为主|自旋锁 + 排队自旋锁 + Push Lock + WDF 同步对象|
|开发模型|纯 WDM 裸写|WDF/KMDF 框架为主，WDM 原语为辅|

> 📌 **终极洞见**：第 4 章教给你的不是"几个 API 怎么用"，而是**内核编程的世界观**——在内核里，每一个字符串都有边界，每一块内存都有 IRQL 归属，每一个链表节点都与数据解耦，每一把锁都以"关调度"为代价。这套世界观一旦建立，你看后续章节的键盘过滤、磁盘过滤、文件系统过滤时，会自然地把"字符串处理 → 内存分配 → 链表管理 → 锁保护"这套四件套套到每个场景上——这就是原书作者把这章放在"过滤驱动实战"之前的深意。

**工业界今天的真实做法**：微软官方推荐新驱动一律用 **KMDF（Kernel-Mode Driver Framework）**——它在 WDM 之上封装了对象生命周期、自动内存管理、内置同步机制。一个 KMDF 驱动里你可能**根本不会直接调用 `ExAllocatePoolX` 或 `KeAcquireSpinLock`**，这些都被框架接管了。但**理解这些底层原语仍是 KMDF 驱动开发者的必修课**——因为：

1. 调试 KMDF 驱动时，你看到的是底层 WDM 结构
2. 阅读 Windows 内核源码/逆向分析时，满眼都是 `UNICODE_STRING`、`LIST_ENTRY`、`KSPIN_LOCK`
3. 遇到框架没覆盖的边缘场景，你必须下沉到 WDM 原语
4. 安全研究/恶意驱动分析，对方用的就是这些原语

所以这一章的价值，**不在于让你照着写 WDM 驱动，而在于给你一套"读懂 Windows 内核"的词汇表**。配合现代 KMDF 框架的使用，你既能享受框架的安全便利，又能在需要时下沉到底层——这才是 2025 年 Windows 内核安全编程的正确姿势。
