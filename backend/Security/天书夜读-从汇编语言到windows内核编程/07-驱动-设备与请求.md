# 第 7 章 驱动、设备与请求

## 7.1 驱动与设备

### 第一性原理：驱动对象不是"功能实体"，是"I/O 管理器的注册表项"

用户态程序员理解"驱动"往往是 `*.sys` 文件本身。但**内核里没有"驱动"这个活体对象**——只有 I/O 管理器为每个已加载驱动创建的 `DRIVER_OBJECT`，它本质是**一张"分发函数指针表 + 驱动元数据"的载体**。

微软官方文档明确 ：I/O 管理器为已安装和加载的每个驱动程序创建驱动程序对象，结构是 `DRIVER_OBJECT`；当 I/O 管理器调用驱动的 `DriverEntry` 例程时，它会提供驱动程序对象的地址；**驱动程序负责填写这些入口点**。

> 💡 **我的洞见**：`DRIVER_OBJECT` 的第一性原理是——**它是驱动与 I/O 管理器之间的"契约载体"**。I/O 管理器不关心你的驱动内部怎么实现，它只认 `DRIVER_OBJECT` 里那张 `MajorFunction[IRP_MJ_MAXIMUM_FUNCTION + 1]` 函数指针数组 。每一次用户态或上层驱动发起 I/O，I/O 管理器就是拿着这个 `MajorFunction` 数组做分发：**`MajorFunction[IRP_MJ_XXX]` 数组的指针对应于在 I/O 堆栈位置中传递的主要函数代码（IRP_MJ_XXX）**​ 。
> 
> 所以原书把"驱动入口与驱动对象"放在 7.1.1 作为开篇第一小节，深意在于：**理解驱动的第一步，是理解"驱动把自己能处理的请求类型登记到 `MajorFunction` 表里"这件事**。没有这张表，I/O 管理器不知道把 `IRP_MJ_READ` 发给谁。

### 7.1.1 驱动入口与驱动对象

**原书意图**：讲 `DriverEntry` 是内核加载驱动后调用的第一个函数，原型为：

```
NTSTATUS DriverEntry(PDRIVER_OBJECT DriverObject, PUNICODE_STRING RegistryPath);
```

**DRIVER_OBJECT 结构的关键字段**（微软官方 ）：

```
typedef struct _DRIVER_OBJECT {
    CSHORT Type;
    CSHORT Size;
    PDEVICE_OBJECT DeviceObject;       // 本驱动创建的设备对象链表头
    ULONG Flags;
    PVOID DriverStart;
    ULONG DriverSize;
    PVOID DriverSection;
    PDRIVER_EXTENSION DriverExtension; // AddDevice 例程挂在 DriverExtension->AddDevice
    UNICODE_STRING DriverName;         // 形如 \Driver\DriverName
    PUNICODE_STRING HardwareDatabase;
    PFAST_IO_DISPATCH FastIoDispatch;
    PDRIVER_INITIALIZE DriverInit;
    PDRIVER_STARTIO DriverStartIo;
    PDRIVER_UNLOAD DriverUnload;       // 卸载函数指针
    PDRIVER_DISPATCH MajorFunction[IRP_MJ_MAXIMUM_FUNCTION + 1]; // 分发函数表
} DRIVER_OBJECT, *PDRIVER_OBJECT;
```

**DriverEntry 必须完成的三件事**（原书一定会强调）：

1. **填充 `MajorFunction` 数组**：把驱动要处理的 `IRP_MJ_XXX` 对应的分发函数指针填进去
2. **设置 `DriverUnload`**：可卸载驱动必须设置卸载例程
3. **设置 `DriverExtension->AddDevice`**（PnP 驱动必需）：PnP 管理器调用 `AddDevice` 时创建设备对象

**Talos Intel 的安全分析视角**（2024 年最新 ）：现代恶意驱动分析时发现，`DriverEntry` 里最常见的三个动作正是——初始化 `DRIVER_OBJECT`、调用 `IoCreateDevice` 创建设备对象、调用 `IoCreateSymbolicLink` 创建符号链接。**理解正常驱动的 `DriverEntry` 结构，是识别恶意驱动的基础**——因为恶意驱动在这个标准骨架上做"最小偏离"：不设置 `DriverUnload`（防止卸载）、在 `MajorFunction[IRP_MJ_DEVICE_CONTROL]` 里藏后门 IOCTL 处理逻辑等。

**现代工业实践——KMDF 的对应物**：

今天微软官方推荐用 KMDF 框架写驱动，`DriverEntry` 退化成"一行框架初始化" ：

```
NTSTATUS DriverEntry(PDRIVER_OBJECT DriverObject, PUNICODE_STRING RegistryPath) {
    WDF_DRIVER_CONFIG config;
    WDF_DRIVER_CONFIG_INIT(&config, EvtDriverDeviceAdd);
    return WdfDriverCreate(DriverObject, RegistryPath, 
                           WDF_NO_OBJECT_ATTRIBUTES, &config, WDF_NO_HANDLE);
}
```

KMDF 框架内部**依然创建 `DRIVER_OBJECT`**，但把 `MajorFunction` 表的填充、PnP/电源管理的接入全部封装了 。驱动作者只需要实现 `EvtDriverDeviceAdd` 等事件回调。**底层还是 WDM，只是 KMDF 替你把样板代码写了**。

> ⚠️ **关键认知**：原书 2009 年基于纯 WDM 讲 `DriverEntry`，今天 95% 以上的新驱动用 KMDF。但**理解 `DRIVER_OBJECT` 仍是刚需**——因为：
> 
> 1. 调试驱动时，WinDbg 里 `dt nt!_DRIVER_OBJECT` 看到的还是这个结构
> 2. 逆向分析第三方/恶意驱动时，对方用的就是 WDM 原语
> 3. KMDF 框架自身也是构建在 `DRIVER_OBJECT` 之上的

### 7.1.2 分发函数和卸载函数

**原书意图**：讲如何编写 `DispatchXxx` 函数处理各类 IRP，以及如何编写 `DriverUnload` 做清理。

**分发函数的本质**：

```
NTSTATUS DispatchCreate(PDEVICE_OBJECT DeviceObject, PIRP Irp) {
    // 处理 IRP_MJ_CREATE
    Irp->IoStatus.Status = STATUS_SUCCESS;
    Irp->IoStatus.Information = 0;
    IoCompleteRequest(Irp, IO_NO_INCREMENT);
    return STATUS_SUCCESS;
}
```

微软官方文档图解 ：驱动程序对象中的调度入口点（DDDispatchXxx）对应于在 I/O 堆栈位置中传递的主要函数代码（IRP_MJ_XXX）。I/O 管理器首先将每个 IRP 路由到驱动程序提供的调度例程。

**必处理的几个 `IRP_MJ_XXX`**（Talos Intel 2024 文章明确 ）：

|主功能码|含义|是否必须处理|
|---|---|---|
|`IRP_MJ_CREATE`|打开设备对象（如 `CreateFile` 触发）|**必须**（即便空实现也要 `IoCompleteRequest`）|
|`IRP_MJ_CLOSE`|关闭设备对象|**必须**​|
|`IRP_MJ_READ`|从设备读数据|按需|
|`IRP_MJ_WRITE`|向设备写数据|按需|
|`IRP_MJ_DEVICE_CONTROL`|设备 I/O 控制（IOCTL）|按需，安全驱动核心|
|`IRP_MJ_POWER`|电源管理|PnP 驱动必须|
|`IRP_MJ_PNP`|即插即用|PnP 驱动必须|

**卸载函数的本质**：

```
VOID DriverUnload(PDRIVER_OBJECT DriverObject) {
    PDEVICE_OBJECT devObj = DriverObject->DeviceObject;
    while (devObj) {
        PDEVICE_OBJECT next = devObj->NextDevice;
        IoDeleteDevice(devObj);  // 删除设备对象
        devObj = next;
    }
    // 删除符号链接、释放资源等
}
```

**关键规则**：`DriverObject->DeviceObject` 是所有本驱动创建的设备的链表头，`NextDevice` 字段把同驱动的所有设备串起来 。卸载时必须遍历这个链表，逐个删除设备对象——漏删任何一个都会导致系统崩溃。

> 💡 **洞见**：分发函数与卸载函数的第一性原理是——**它们是 `DRIVER_OBJECT` 生命周期的两个端点**。`DriverEntry` 是"出生登记"，`DriverUnload` 是"死亡清理"，中间的 `DispatchXxx` 是"活着时的职责"。原书把 7.1.2 放在 7.1.1 之后，正是因为这三者是一个有机整体：`DriverEntry` 里填 `MajorFunction` 表 → I/O 管理器按表分发到 `DispatchXxx` → 驱动卸载时 `DriverUnload` 清理 `DriverEntry` 里创建的一切。
> 
> **安全驱动的工业实践**：现代安全驱动（杀毒、EDR、过滤驱动）的分发函数里，**`IRP_MJ_DEVICE_CONTROL` 是最高危的入口**——用户态通过 `DeviceIoControl` 发送 IOCTL 与驱动通信，任何输入验证不严都会导致特权提升漏洞。2024 年 Talos Intel 披露的多个恶意驱动，攻击载体都是 `IRP_MJ_DEVICE_CONTROL` 的 IOCTL 处理中存在任意读写漏洞 。这也是为什么微软驱动安全指南反复强调：**IOCTL 处理中必须对输入缓冲区做严格的 `ProbeForRead`/`ProbeForWrite` 和长度校验**。

### 7.1.3 设备与符号链接

**原书意图**：讲 `IoCreateDevice` 创建设备对象，`IoCreateSymbolicLink` 创建符号链接让用户态可见。

**设备对象的本质**（Talos Intel 2024 ）：

> "A device object can be thought of as an interface for requests between a client and a driver. Instead of sending a request directly to a driver, a device object acts as the communication point for a client."

设备对象（`DEVICE_OBJECT`）是客户端与驱动之间请求的**通信端点**。用户态不直接发请求给驱动，而是通过设备对象这个"信箱"。

**标准创建设备对象代码**：

```
UNICODE_STRING deviceName;
RtlInitUnicodeString(&deviceName, L"\\Device\\MyDriver");

PDEVICE_OBJECT deviceObject;
NTSTATUS status = IoCreateDevice(
    DriverObject,           // 所属驱动对象
    sizeof(DEVICE_EXTENSION), // 设备扩展大小
    &deviceName,            // 设备名（内核命名空间）
    FILE_DEVICE_UNKNOWN,    // 设备类型
    0,                      // 设备特征
    FALSE,                  // 是否独占
    &deviceObject
);
```

**创建符号链接**：

```
UNICODE_STRING symbolicLink;
RtlInitUnicodeString(&symbolicLink, L"\\DosDevices\\MyDriver");

// 把 \DosDevices\MyDriver 链接到 \Device\MyDriver
IoCreateSymbolicLink(&symbolicLink, &deviceName);
```

**为什么需要符号链接？第一性原理**：

- 设备对象名在 `\Device` 命名空间下，**用户态不可直接访问**
- 符号链接把 `\DosDevices\MyDriver` 映射到 `\Device\MyDriver`，用户态就可以用 `CreateFile("\\\\.\\MyDriver", ...)` 打开设备
- `\\\\.\\` 在用户态等价于 `\DosDevices`，这是 Win32 命名空间到内核命名空间的桥梁

> 💡 **我的洞见**：设备对象 + 符号链接这套机制，体现了 Windows 内核架构的核心思想——**命名空间隔离 + 符号链接桥接**。内核命名空间（``\Device\`、``\Driver`、``\Registry\`）和用户态命名空间（``\DosDevices` 映射为 `\.`）是两套独立的世界，符号链接是它们之间的"大使馆"。这种设计的安全价值在于：
> 
> 1. 用户态不能直接操纵内核命名空间里的对象
> 2. 驱动作者**显式**决定是否创建符号链接——不创建 = 用户态不可见 = 天然封闭
> 3. 恶意驱动如果要与用户态通信，必然要创建符号链接——这给了安全软件一个检测锚点

### 7.1.4 设备的安全创建

**原书意图**：讲 `IoCreateDeviceSecure` + `IoCreateSymbolicLink` 配合 SDDL（Security Descriptor Definition Language）字符串控制设备对象的访问控制。

**这是原书 2009 年就会强调、但今天更关键的一节**——因为过去 15 年大量驱动漏洞源于"设备对象创建时未正确限制访问权限"，导致低权限用户态进程能与高权限驱动通信，触发特权提升。

**安全创建设备对象的标准做法**：

```
UNICODE_STRING deviceName;
RtlInitUnicodeString(&deviceName, L"\\Device\\MySecureDriver");

// SDDL 字符串：只允许管理员和系统访问
UNICODE_STRING sddlString;
RtlInitUnicodeString(&sddlString, L"D:P(A;;GA;;;BA)(A;;GA;;;SY)");

PDEVICE_OBJECT deviceObject;
NTSTATUS status = IoCreateDeviceSecure(
    DriverObject,
    sizeof(DEVICE_EXTENSION),
    &deviceName,
    FILE_DEVICE_UNKNOWN,
    FILE_DEVICE_SECURE_OPEN,
    FALSE,
    &sddlString,           // SDDL 安全描述符
    NULL,                  // 设备类 GUID
    &deviceObject
);
```

**SDDL 字符串的工业标准写法**：

- `D:P(A;;GA;;;BA)(A;;GA;;;SY)` → 仅管理员（Built-in Administrators）和系统（SYSTEM）有完全访问权
- `D:P(A;;GA;;;AU)` → 已认证用户（Authenticated Users）可访问
- `D:P(A;;GA;;;WD)` → 所有人（World）可访问——**高危！仅用于无害设备**

**FILE_DEVICE_SECURE_OPEN 标志的关键作用**：

> ⚠️ 这个标志告诉 I/O 管理器：对设备的**所有打开操作**（包括通过符号链接打开）都必须进行安全描述符检查。如果不设置这个标志，攻击者可能通过某些路径绕过 SDDL 限制直接打开设备对象。

**现代工业实践——KMDF 的安全设备创建**：

```
// KMDF 中通过 INF 文件声明安全描述符
// INF 的 [MyDriver_Device.NT] 段：
// HKR,,Security,,"D:P(A;;GA;;;BA)(A;;GA;;;SY)"
```

KMDF 框架把 SDDL 字符串的指定从代码移到了 INF 文件，实现"安全策略与代码分离"——这是现代驱动安全的最佳实践。

**微软驱动安全指南的核心要点**​ ：

1. 设备对象**默认不应**对用户态可见——不创建符号链接 = 天然安全
2. 如果必须创建符号链接，**必须**用 `IoCreateDeviceSecure` + 严格的 SDDL
3. `IRP_MJ_DEVICE_CONTROL` 的 IOCTL 处理中，**必须**验证输入缓冲区
4. 使用 **Driver Verifier**​ 的 `I/O Verification` 检测设备对象滥用

> 💡 **洞见**：设备安全创建的第一性原理是——**"默认拒绝"优于"默认开放"**。原书 2009 年讲 `IoCreateDeviceSecure` 时，驱动生态的安全意识还不如今天。15 年后的今天，随着 Bring Your Own Vulnerable Driver (BYOVD) 攻击的泛滥，微软在 Windows 10/11 上引入了 **Vulnerable Driver Blocklist**——已知的有漏洞驱动会被系统直接阻止加载 。这倒逼现代驱动开发必须把"安全创建设备"作为**第一铁律**，而非"可选项"。

### 7.1.5 设备与符号链接的用户相关性

**原书意图**：讲符号链接的"用户相关性"——同一个符号链接在不同用户会话中指向不同的设备对象。

**核心概念**：Windows 是多用户、多会话系统。符号链接 `\DosDevices\MyDriver` 在**每个登录会话中有独立的命名空间**。这意味着：

- 用户 A 登录会话中创建的 `\DosDevices\MyDriver` 符号链接
- 与用户 B 登录会话中的同名符号链接**互不干扰**
- 这是通过 *_\Sessions\0\DosDevices*_​ 这种每会话命名空间实现的

**全局符号链接 vs 会话局部符号链接**：

```
// 全局符号链接（所有会话可见）
IoCreateSymbolicLink(L"\\DosDevices\\Global\\MyDriver", &deviceName);

// 会话局部符号链接（仅当前会话可见）
IoCreateSymbolicLink(L"\\DosDevices\\MyDriver", &deviceName);
```

**`\DosDevices\Global` 前缀的作用**：

- 不加 `Global`：符号链接只对**创建它的那个会话**可见
- 加 `Global`：符号链接对**所有会话**可见
- 服务（运行在 Session 0）创建的符号链接默认在 Session 0 的命名空间，用户会话无法直接访问——必须显式用 `\DosDevices\Global` 前缀

> ⚠️ **工业界经典 Bug**：驱动服务在 Session 0 创建了 `\DosDevices\MyDriver` 符号链接，用户态程序在 Session 1 调用 `CreateFile("\\\\.\\MyDriver")` 失败——因为该符号链接只在 Session 0 可见。修复方法是驱动里用 `\DosDevices\Global\MyDriver`。

**现代延伸**：

- 服务与服务之间、服务与用户态程序之间的通信，符号链接的"用户相关性"是关键考量
- 安全软件（杀毒、EDR）的驱动**通常创建全局符号链接**，以便用户态服务能与之通信
- 恶意驱动可能故意创建**会话局部**符号链接，规避基于全局命名空间扫描的检测

## 7.2 请求处理

### 第一性原理：IRP 是"跨驱动的责任链令牌"，I/O 栈位是"每个驱动的责任区"

用户态 `ReadFile`/`WriteFile`/`DeviceIoControl` 的一次调用，在内核里被封装成一个 **IRP（I/O Request Packet）**。但这个 IRP **不是给一个驱动独享的**——它是整条设备栈（device stack）**共享的责任链令牌**。

微软官方文档明确 ：I/O 管理器为分层驱动链中的每个驱动在 IRP 中分配**一个 I/O 栈位（I/O Stack Location）**，每个 I/O 栈位由一个 `IO_STACK_LOCATION` 结构组成。I/O 管理器为每个 IRP 创建 I/O 栈位数组，数组元素与分层驱动链中的每个驱动对应。

> 💡 **我的洞见**：IRP + I/O 栈位的第一性原理是——**"请求"与"处理上下文"分离**。IRP 是请求的载体（数据、状态、完成例程），I/O 栈位是每个驱动的处理上下文（参数、目标设备对象、文件对象）。这种设计让 Windows 能构建任意深度的驱动栈：
> 
> ```
> 用户态 CreateFile
>     ↓
> I/O 管理器创建 IRP，分配 N 个 I/O 栈位
>     ↓
> 驱动 A 的 DispatchCreate 被调用，使用 I/O 栈位[0]
>     ↓
> 驱动 A 调用 IoCallDriver 下发，驱动 B 使用 I/O 栈位[1]
>     ↓
> ... 直到最底层驱动完成 IRP
>     ↓
> IoCompleteRequest 向上回卷，每层驱动有机会在 CompletionRoutine 里处理
> ```
> 
> 原书把"IRP 与 IO_STACK_LOCATION"作为 7.2.1 的第一小节，正是因为它**是整个 Windows I/O 系统的基石**——不理解这个责任链模型，就无法理解后面章节的键盘过滤、磁盘过滤、文件系统过滤、网络过滤。过滤驱动的本质，就是**插到这条 IRP 责任链的中间，拦截并可能修改 IRP**。

### 7.2.1 IRP 与 IO_STACK_LOCATION

**IRP 结构要点**（微软官方文档隐含）：

- IRP 是 I/O 管理器分配的**不透明结构**
- 包含：I/O 栈位数组、`IoStatus`（完成状态）、`MdlAddress`（内存描述符列表）等
- 驱动通过 `IoGetCurrentIrpStackLocation(Irp)` 获取自己的 I/O 栈位

**IO_STACK_LOCATION 结构的核心字段**（微软官方 ）：

```
typedef struct _IO_STACK_LOCATION {
    UCHAR MajorFunction;       // IRP_MJ_XXX
    UCHAR MinorFunction;       // IRP_MN_XXX（某些主功能有子功能）
    UCHAR Flags;
    UCHAR Control;
    union {
        // 针对不同 MajorFunction 的参数联合体
        struct { ... } Create;      // IRP_MJ_CREATE 参数
        struct { ... } Read;       // IRP_MJ_READ 参数
        struct { ... } Write;      // IRP_MJ_WRITE 参数
        struct { ... } DeviceIoControl; // IRP_MJ_DEVICE_CONTROL 参数
        // ...
    } Parameters;
    PDEVICE_OBJECT DeviceObject;   // 本层驱动的目标设备对象
    PFILE_OBJECT FileObject;       // 打开的文件对象
    PIO_COMPLETION_ROUTINE CompletionRoutine; // 完成例程
    PVOID Context;                 // 上下文
} IO_STACK_LOCATION, *PIO_STACK_LOCATION;
```

**I/O 栈位的工业级认知**：

- **每个驱动只碰自己的 I/O 栈位**：通过 `IoGetCurrentIrpStackLocation` 获取
- **下发到下层驱动时必须设置下一层栈位**：通过 `IoGetNextIrpStackLocation` + 填充
- **I/O 栈位数 = 设备栈深度**：I/O 管理器根据设备栈的 `StackSize` 字段决定分配多少个栈位
- **过滤驱动的标准手法**：在自己的 I/O 栈位里记录上下文，设置 `CompletionRoutine`，然后调用 `IoCallDriver` 下发

**现代工业实践——KMDF 对 IRP 的封装**：

KMDF 框架把 IRP 完全封装成 `WDFREQUEST` 对象 。I/O 管理器发送 I/O 请求到驱动时：

1. 框架为请求创建 `WDFREQUEST` 对象
2. 将请求对象放入 I/O 队列
3. 调用驱动注册的请求处理器

```
// KMDF 请求处理回调
VOID EvtIoDeviceControl(WDFQUEUE Queue, WDFREQUEST Request, 
                        size_t OutputBufferLength, size_t InputBufferLength,
                        ULONG IoControlCode) {
    // 框架已经从 IRP 中提取了所有参数，驱动无需直接接触 IRP
    // 通过 WdfRequestRetrieveInputBuffer / WdfRequestRetrieveOutputBuffer 获取缓冲区
    // ...
    WdfRequestComplete(Request, STATUS_SUCCESS);
}
```

**关键约束**（微软官方 ）：

> ⚠️ 调用 `WdfRequestComplete` 之后，**驱动不能再访问 WDFREQUEST 对象或其关联的底层 WDM IRP 结构**——即使调用了 `WdfObjectReference` 增加引用计数也不行。这是 KMDF 框架的硬规则，违反会导致 Bug Check。

> 💡 **洞见**：从 WDM 的裸 IRP 操作到 KMDF 的 `WDFREQUEST` 封装，体现了驱动开发 15 年来的最大演进——**"让驱动作者远离 IRP 的内部细节"**。但理解 IRP 与 I/O 栈位的机制仍是不可替代的：
> 
> 1. 调试 KMDF 驱动时，WinDbg 里看到的还是 IRP
> 2. 过滤驱动（特别是文件系统 Minifilter、WFP 网络过滤）仍需直接操作 IRP
> 3. 逆向分析、漏洞挖掘时，对方用的就是裸 IRP
> 4. KMDF 框架自身的实现，就是构建在 IRP 机制之上的

### 7.2.2 打开与关闭请求的处理

**原书意图**：讲 `IRP_MJ_CREATE` 和 `IRP_MJ_CLOSE` 的分发函数实现。

**这两个请求的特殊性**：

- **每个驱动都必须处理**——即使用户态从不打开设备，I/O 管理器在加载驱动时也会发一个内部的 `IRP_MJ_CREATE`
- 对应**用户态的 `CreateFile` 和 `CloseHandle`**
- 在过滤驱动中，`IRP_MJ_CREATE` 是**注入过滤逻辑的关键切入点**

**标准实现**：

```
NTSTATUS DispatchCreate(PDEVICE_OBJECT DeviceObject, PIRP Irp) {
    // 获取当前 I/O 栈位
    PIO_STACK_LOCATION stack = IoGetCurrentIrpStackLocation(Irp);
    
    // 可以在这里做：
    // 1. 权限检查
    // 2. 记录打开者进程信息（PsGetCurrentProcess）
    // 3. 初始化设备扩展中的每文件上下文
    // 4. 拒绝非法打开请求
    
    Irp->IoStatus.Status = STATUS_SUCCESS;
    Irp->IoStatus.Information = 0;
    IoCompleteRequest(Irp, IO_NO_INCREMENT);
    return STATUS_SUCCESS;
}

NTSTATUS DispatchClose(PDEVICE_OBJECT DeviceObject, PIRP Irp) {
    // 清理 DispatchCreate 中分配的资源
    Irp->IoStatus.Status = STATUS_SUCCESS;
    IoCompleteRequest(Irp, IO_NO_INCREMENT);
    return STATUS_SUCCESS;
}
```

**工业级安全实践**：

- **在 `IRP_MJ_CREATE` 里做进程鉴权**：通过 `PsGetCurrentProcessId()` + `PsLookupProcessByProcessId` 获取打开者的进程信息，判断是否在白名单内
- **过滤驱动的核心挂钩点**：文件系统过滤驱动（Minifilter）在 `PostCreate` 回调里检查文件打开操作，网络过滤驱动（WFP）在 `FltPostOperation` 里检查连接建立
- **EDR 产品的基础**：现代终端检测与响应产品，几乎都在 `IRP_MJ_CREATE` 路径上挂钩，监控敏感进程对敏感设备的打开行为

### 7.2.3 应用层信息传入

**原书意图**：讲用户态如何通过 `DeviceIoControl` 发送 IOCTL 把信息传给驱动。

**IOCTL 的本质**：

```
// 用户态
BOOL DeviceIoControl(
    HANDLE hDevice,      // CreateFile 返回的设备句柄
    DWORD dwIoControlCode, // IOCTL 控制码
    LPVOID lpInBuffer,   // 输入缓冲区
    DWORD nInBufferSize,
    LPVOID lpOutBuffer,  // 输出缓冲区
    DWORD nOutBufferSize,
    LPDWORD lpBytesReturned,
    LPOVERLAPPED lpOverlapped
);
```

**IOCTL 控制码的编码规则**（CTL_CODE 宏）：

```
CTL_CODE(DeviceType, Function, Method, Access)
```

- **Method**：`METHOD_BUFFERED`（系统复制缓冲区）、`METHOD_IN_DIRECT`（输入缓冲，输出 MDL）、`METHOD_OUT_DIRECT`（输出缓冲，输入 MDL）、`METHOD_NEITHER`（直接使用用户态地址）
- **Access**：`FILE_ANY_ACCESS`、`FILE_READ_ACCESS`、`FILE_WRITE_ACCESS`

**驱动侧处理**：

```
NTSTATUS DispatchDeviceControl(PDEVICE_OBJECT DeviceObject, PIRP Irp) {
    PIO_STACK_LOCATION stack = IoGetCurrentIrpStackLocation(Irp);
    ULONG ioctl = stack->Parameters.DeviceIoControl.IoControlCode;
    ULONG inputLen = stack->Parameters.DeviceIoControl.InputBufferLength;
    ULONG outputLen = stack->Parameters.DeviceIoControl.OutputBufferLength;
    
    // 获取缓冲区（METHOD_BUFFERED 方式）
    PVOID buffer = Irp->AssociatedIrp.SystemBuffer;
    
    switch (ioctl) {
        case IOCTL_MYDRIVER_DO_X:
            // 必须做：
            // 1. ProbeForRead/Write（如果在用户态地址）
            // 2. 验证输入长度
            // 3. 验证输入数据的合法性
            // 4. 执行操作
            break;
        default:
            Irp->IoStatus.Status = STATUS_INVALID_DEVICE_REQUEST;
    }
    
    IoCompleteRequest(Irp, IO_NO_INCREMENT);
    return Irp->IoStatus.Status;
}
```

> ⚠️ **工业界血泪教训**：IOCTL 处理是驱动漏洞的**头号来源**。过去 15 年披露的 Windows 内核提权漏洞，70% 以上源于 IOCTL 处理不当：
> 
> - 输入缓冲区未做 `ProbeForRead` 验证 → 内核访问无效用户态地址 → 任意读/写
> - 输入长度未校验 → 缓冲区溢出
> - `METHOD_NEITHER` 使用不当 → TOCTOU 竞态
> - IOCTL 权限未限制 → 低权限用户触发高权限操作

**现代工业实践——KMDF 的安全 IOCTL 处理**：

```
VOID EvtIoDeviceControl(WDFQUEUE Queue, WDFREQUEST Request,
                        size_t OutputBufferLength, size_t InputBufferLength,
                        ULONG IoControlCode) {
    // KMDF 框架自动处理缓冲区验证
    PVOID inputBuffer;
    size_t inputBufferLength;
    WdfRequestRetrieveInputBuffer(Request, InputBufferLength,
                                  &inputBuffer, &inputBufferLength);
    // 框架已经做了 ProbeForRead 和长度校验
    // 驱动作者只需关注业务逻辑
    WdfRequestComplete(Request, STATUS_SUCCESS);
}
```

KMDF 框架的 `WdfRequestRetrieveInputBuffer` 等方法**内部做了缓冲区验证**，从根本上消灭了一大类漏洞。

### 7.2.4 驱动层信息传出

**原书意图**：讲驱动如何把处理结果/状态信息传回用户态。

**四种主要方式**：

**1. IOCTL 输出缓冲区**（同步）：

```
// METHOD_BUFFERED 方式
PVOID outputBuffer = Irp->AssociatedIrp.SystemBuffer;
*(PULONG)outputBuffer = result;
Irp->IoStatus.Information = sizeof(ULONG);  // 返回数据长度
Irp->IoStatus.Status = STATUS_SUCCESS;
IoCompleteRequest(Irp, IO_NO_INCREMENT);
```

**2. 事件通知 + 共享内存**（异步高性能）：

```
// 驱动创建共享内存，用户态映射
// 驱动用 KeSetEvent 通知用户态有新数据
```

**3. 回调函数（高难度）**：

```
// 用户态通过 IOCTL 注册回调函数的用户态地址
// 驱动在适当时机调用该函数
// ⚠️ 极度危险，现代驱动几乎不用
```

**4. 文件日志**（持久化）：

```
// 驱动把信息写入文件（参考第 5 章）
// 用户态后续读取文件获取信息
```

**现代工业实践——WDF 框架的对应物**：

```
// KMDF 中完成请求并传出数据
WdfRequestCompleteWithInformation(Request, STATUS_SUCCESS, bytesWritten);
```

**工业级架构模式**：

- **EDR 产品**：驱动层捕获事件 → 通过 IOCTL 输出缓冲区或共享内存传给用户态服务 → 用户态服务做深度分析
- **防火墙**：驱动层（WFP 过滤引擎）拦截数据包 → 通过共享内存环形缓冲区高速传给用户态分析引擎
- **沙箱/虚拟化**：驱动层拦截系统调用 → 通过事件+共享内存机制通知用户态监控程序

> 💡 **我的洞见**：驱动层信息传出的第一性原理是——**"内核态到用户态的信息流必须受控"**。这不是技术限制，而是安全架构的必然要求：
> 
> 1. 内核态数据可能包含敏感信息（密码、密钥、其他进程内存）
> 2. 用户态程序不可信，传出机制必须防止信息泄露
> 3. 性能考量：频繁的内核-用户态切换代价高昂，需要共享内存等高效机制
> 
> 原书 2009 年讲这部分时，主流模式是"IOCTL 同步请求-响应"。今天的工业级安全产品（EDR、XDR、下一代防火墙）已经演进到**"内核采集 + 共享内存环形缓冲 + 用户态异步消费"**的高性能架构——驱动层只负责高速采集和写入环形缓冲，用户态服务批量消费。这种架构的核心优势：
> 
> - 内核态零阻塞：写入环形缓冲是 O(1) 操作
> - 用户态批处理：减少上下文切换
> - 内存拷贝最小化：共享内存避免数据复制
> 
> 理解这个演进，你就理解了为什么现代 Windows 驱动开发必须把"信息传出"作为一个独立架构议题来对待，而非简单的"IOCTL 返回数据"。

# 第 7 章的知识地图与前后联系

把这一章放进全书脉络：

```
第 1-3 章：C ↔ 汇编 ↔ 反汇编（机器视角）
第 4 章：字符串 + 内存 + 链表 + 锁（内核原语）
第 5 章：文件 + 注册表（持久化状态）
第 6 章：时间 + 线程 + 事件（并发与时序）
                ↓
第 7 章：驱动 + 设备 + IRP（驱动骨架与 I/O 模型）← 你在这里
                ↓
第 8+ 章：过滤驱动实战（键盘/磁盘/文件系统/网络过滤）
```

**为什么"驱动、设备与请求"是过滤驱动实战的总纲？**

因为后面每一章的过滤驱动，本质上都是在做同一件事——**把自己的驱动对象插入到目标设备栈中，让 IRP 流经时经过自己的分发函数**：

- **键盘过滤**：Attach 到 `\Device\KeyboardClass0` 设备栈，拦截 `IRP_MJ_READ` 获取按键
- **磁盘过滤**：Attach 到磁盘设备栈，拦截 `IRP_MJ_READ/WRITE` 做加密/解密
- **文件系统过滤**：Minifilter 注册到 FltMgr，拦截文件 I/O 的各类回调
- **网络过滤**：WFP 注册 callout，拦截 TCP/IP 栈的数据包

**没有第 7 章的"DRIVER_OBJECT + DEVICE_OBJECT + IRP + I/O 栈位"这套骨架知识，后面所有过滤驱动实战都是空中楼阁**——你不知道 IRP 怎么流，就不知道在哪拦截；你不知道设备栈怎么构建，就不知道怎么 Attach；你不知道分发函数怎么写，就不知道拦截后怎么处理。

**2009 → 2025 的演进主线**：

|维度|原书时代（2009，纯 WDM）|今天（2025-2026，KMDF 为主）|
|---|---|---|
|驱动入口|`DriverEntry` 手动填 `MajorFunction` 表|`DriverEntry` 调用 `WdfDriverCreate`，框架自动管理|
|设备创建|`IoCreateDevice` + 手动符号链接|`WdfDeviceCreate` + INF 声明|
|设备安全|`IoCreateDeviceSecure` + SDDL 代码硬编码|INF 文件声明 SDDL，策略与代码分离|
|请求处理|裸 IRP + `IoGetCurrentIrpStackLocation`|`WDFREQUEST` 封装，框架提取参数|
|请求完成|`IoCompleteRequest`|`WdfRequestComplete`（完成后 IRP 不可访问）|
|符号链接用户相关性|``\DosDevices\` vs``\DosDevices\Global`|同上，KMDF 提供 `WdfDeviceCreateSymbolicLink` 等 API|
|安全实践|手动 `ProbeForRead/Write` + 长度校验|框架 API 内部自动验证，从源头消灭漏洞|
|恶意驱动防护|无系统级防护|Windows 10/11 引入 Vulnerable Driver Blocklist|

> 📌 **终极洞见**：第 7 章教给你的不是"怎么写一个 WDM 驱动"，而是**Windows I/O 系统的第一性原理**——**"一切 I/O 皆 IRP，一切 IRP 皆流经设备栈，每一层驱动在自己的 I/O 栈位上承担有限责任"**。
> 
> 这条原理 15 年未变，是 Windows 内核最稳定的设计之一。KMDF 框架的出现并没有改变它，只是**把这套原理封装成了更易用、更安全的对象模型**：
> 
> - `DRIVER_OBJECT` → `WDFDRIVER`（根对象）
> - `DEVICE_OBJECT` → `WDFDEVICE`（子对象）
> - `IRP` → `WDFREQUEST`（I/O 请求对象）
> - `I/O 栈位` → `WDFREQUEST` 的参数提取 API
> - `IoCompleteRequest` → `WdfRequestComplete`
> 
> 原书 2009 年基于纯 WDM 讲这一章，让你直面 IRP 的内部机制——这是"知其所以然"。今天工业界用 KMDF 写驱动，让你远离 IRP 的细节——这是"知其然并安全用之"。**两者的关系是互补而非替代**：KMDF 让你快速构建安全的生产驱动，但理解 WDM 原语让你能调试 KMDF 驱动、能逆向分析第三方驱动、能做内核安全研究。
> 
> **这就是为什么这本书 15 年后仍有价值**——它教你的是"Windows I/O 系统的骨架"，而非"某个框架的 API 用法"。框架会变（WDM → KMDF → 未来的某种新框架），但骨架不变。掌握骨架，你就能在任何框架下游刃有余；只学框架，框架一换你就得从头再来。
> 
> **工业界今天的真实做法**：
> 
> - 新驱动一律用 **KMDF**（内核态）或 **UMDF v2**（用户态）
> - 必须直接操作 IRP 的场景（如文件系统 Minifilter、WFP 网络过滤、特定硬件驱动），在 KMDF 框架内使用 `WdfRequestXxx` 系列 API 间接操作，或使用 `WdfRequestWdmIrpGet` 获取底层 IRP 进行精细控制
> - 设备安全创建：INF 文件声明 SDDL，遵循"默认拒绝"原则
> - IOCTL 处理：使用 `METHOD_BUFFERED` 优先，避免 `METHOD_NEITHER`
> - 配合 **Driver Verifier**​ 的 `I/O Verification` 和 `Deadlock detection` 进行全面验证
> - 防御 **BYOVD 攻击**：驱动需通过 HVCI/HVCI+ 兼容测试，避免被 Windows 漏洞驱动黑名单拦截
