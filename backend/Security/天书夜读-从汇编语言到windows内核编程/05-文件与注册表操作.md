# 第 5 章 文件与注册表操作

## 5.1 文件操作

### 第一性原理：内核里的"文件"不是文件，是"对象管理器命名空间中的一个对象"

用户态程序员眼里的"文件"是 `fopen` 返回的一个 `FILE*`，背后是 CRT 封装的句柄。但**内核里没有"文件"这个概念**——只有"对象管理器（Object Manager）命名空间中的一个对象"，文件对象（`FILE_OBJECT`）只是其中一种对象类型。你要访问 `C:\Windows\example.txt`，实际路径在内核里是：

```
\DosDevices\C:\Windows\example.txt
```

或更底层的：

```
\SystemRoot\example.txt    （映射到操作系统安装目录，如 C:\Windows）
```

微软官方文档明确：内核态驱动通过**对象名**引用文件，这个名字被封装进 `OBJECT_ATTRIBUTES` 结构，再传给 `ZwCreateFile`。

> 💡 **我的洞见**：这一节的第一性原理是——**内核访问文件 = 在对象管理器命名空间中解析一个名字 + 获得一个内核句柄**。这条路径上有三个不可省略的环节：
> 
> 1. **名字解析**：`\DosDevices\C:` 这样的名字在对象管理器里逐级解析，可能跨越**符号链接**（如 `C:` 是指向 `\Device\HarddiskVolumeN` 的符号链接）
> 2. **句柄创建**：`ZwCreateFile` 在对象管理器里创建一个**句柄**，这个句柄属于"内核句柄"还是"当前进程句柄"，由 `OBJ_KERNEL_HANDLE` 标志决定
> 3. **权限检查**：`DesiredAccess` 参数触发的不是"文件权限"，而是**对象管理器的访问检查**——这是内核安全模型的核心
> 
> 原书 2009 年讲这部分时，可能没强调一个关键点：**如果驱动不在系统线程上下文里运行，必须设置 `OBJ_KERNEL_HANDLE` 标志**，否则创建的句柄属于"当前进程"，可能被该进程任意访问甚至关闭——这是内核句柄泄露/滥用的经典源头。

### 5.1.1 使用 OBJECT_ATTRIBUTES

**原书意图**：教读者用 `InitializeObjectAttributes` 宏初始化这个结构，然后传给 `ZwCreateFile` / `ZwOpenKey`。

**结构定义**（微软官方 ）：

```
typedef struct _OBJECT_ATTRIBUTES {
    ULONG Length;                       // 结构大小，InitializeObjectAttributes 自动设置
    HANDLE RootDirectory;               // 根目录句柄（NULL = ObjectName 是绝对路径）
    PUNICODE_STRING ObjectName;         // 对象名（UNICODE_STRING）
    ULONG Attributes;                   // 属性标志位掩码
    PVOID SecurityDescriptor;           // 安全描述符（创建对象时用，打开时忽略）
    PVOID SecurityQualityOfService;     // 服务质量（InitializeObjectAttributes 设为 NULL）
} OBJECT_ATTRIBUTES;
```

**关键标志位**（这是原书可能讲了但值得深度展开的）：

|标志|含义与工程意义|
|---|---|
|`OBJ_CASE_INSENSITIVE`|对象名比较时不区分大小写。文件名/注册表键名**几乎总是用这个**​|
|`OBJ_KERNEL_HANDLE`|句柄在内核模式创建，**只能被内核访问**。不在系统线程上下文时必须设置|
|`OBJ_FORCE_ACCESS_CHECK`|即使内核模式打开句柄，也强制做完整访问检查。安全敏感场景用|
|`OBJ_DONT_REPARSE`|不跟随重解析点（reparse point）。**安全软件防重定向绕过的利器**​|
|`OBJ_OPENLINK`|打开符号链接对象本身，而非它指向的目标|

**标准初始化代码**：

```
UNICODE_STRING uniName;
OBJECT_ATTRIBUTES objAttr;
RtlInitUnicodeString(&uniName, L"\\DosDevices\\C:\\Windows\\example.txt");
// 或 L"\\SystemRoot\\example.txt"
InitializeObjectAttributes(&objAttr, &uniName,
    OBJ_CASE_INSENSITIVE | OBJ_KERNEL_HANDLE, NULL, NULL);
```

> ⚠️ **关键陷阱**：`\DosDevices` 命名空间在驱动加载早期可能还不存在（盘符尚未暴露）。这时唯一保证可用的是 `\SystemRoot` 命名空间，它映射到操作系统安装目录（如 `C:\Windows`） 。原书 2009 年基于 XP 环境，那时启动顺序与今日 Win10/11 不同，这条限制今天依然存在，做启动驱动（boot-start driver）时尤其要注意。

**`RootDirectory` 的相对路径玩法**：

如果 `RootDirectory` 非 NULL，`ObjectName` 就是相对于该目录的**相对路径**。这是注册表操作中极其常见的模式——先打开 `HKLM\SYSTEM\CurrentControlSet\Services\MyDriver` 作为根，再用相对名字打开其子键。

### 5.1.2 打开和关闭文件

**原书意图**：讲 `ZwCreateFile` 的复杂参数列表，以及如何用 `ZwClose` 关闭句柄。

**ZwCreateFile 的 11 个参数**（微软官方 ）——这是 Windows 内核 API 里参数最多的几个之一，本身就说明了"打开文件"在内核里是个复杂操作：

```
NTSTATUS ZwCreateFile(
    PHANDLE FileHandle,               // 输出的文件句柄
    ACCESS_MASK DesiredAccess,        // 请求的访问权限
    POBJECT_ATTRIBUTES ObjectAttributes, // 上一节讲的 OBJECT_ATTRIBUTES
    PIO_STATUS_BLOCK IoStatusBlock,   // I/O 状态块
    PLARGE_INTEGER AllocationSize,    // 分配大小（创建新文件时用）
    ULONG FileAttributes,             // 文件属性
    ULONG ShareAccess,                // 共享访问
    ULONG CreateDisposition,          // 创建处置（存在/不存在时怎么办）
    ULONG CreateOptions,              // 创建选项
    PVOID EaBuffer,                   // 扩展属性（驱动一般用不到）
    ULONG EaLength                    // EA 长度
);
```

**CreateDisposition 的六种情况**（这是原书一定会强调的 ）：

|标志|文件存在时|文件不存在时|
|---|---|---|
|`FILE_CREATE`|返回错误|创建文件|
|`FILE_OPEN`|打开文件|返回错误|
|`FILE_OPEN_IF`|打开文件|创建文件|
|`FILE_OVERWRITE`|打开并覆盖|返回错误|
|`FILE_OVERWRITE_IF`|打开并覆盖|创建文件|
|`FILE_SUPERSEDE`|替换文件|创建文件|

**CreateOptions 的关键标志**：

- `FILE_SYNCHRONOUS_IO_NONALERT` / `FILE_SYNCHRONOUS_IO_ALERT`：**让 I/O 管理器维护当前文件位置指针**，后续 `ZwReadFile`/`ZwWriteFile` 可以传 `ByteOffset = NULL` 顺序读写
- `FILE_NO_INTERMEDIATE_BUFFERING`：不开缓存，常用于设备直接 I/O
- `FILE_WRITE_THROUGH`：写操作直达介质，不留在缓存
- `FILE_DELETE_ON_CLOSE`：关闭句柄时删除文件（配合 `DELETE` 访问权）

**IRQL 硬约束**（原书讲了但今天依然绝对适用）：

> ⚠️ 文件操作**只能在 `IRQL = PASSIVE_LEVEL` 进行**。如果在 `DISPATCH_LEVEL` 或更高 IRQL 调用 `ZwCreateFile`/`ZwReadFile`/`ZwWriteFile`，系统会直接 Bug Check。
> 
> 工业界做法是：在 `DISPATCH_LEVEL` 上收到请求时，用 **`IoQueueWorkItem`**​ 或 **系统工作线程（System Worker Thread）**​ 把文件操作降级到 `PASSIVE_LEVEL` 的工作项中执行。

**关闭文件**：`ZwClose(FileHandle)`。微软文档明确，`ZwClose` 是释放已打开对象句柄的通用例程——它递减句柄的对象引用计数，使句柄失效 。

> 💡 **我的洞见**：`ZwCreateFile` 的 11 个参数反映了一个深层事实——**"打开文件"在内核里本质上是一次"对象管理器 + 安全子系统 + I/O 子系统 + 文件系统驱动"四方的协同握手**。原书可能把它当成"内核版 fopen"来讲，但第一性原理告诉我们：每一次 `ZwCreateFile` 调用，都是在触发一次跨子系统的事务。这就是为什么它不能在 `DISPATCH_LEVEL` 上调——因为它可能需要等待页面调度、可能需要做安全检查、可能需要与文件系统驱动交互，这些都要求线程上下文和可调度性。

### 5.1.3 文件读/写操作

**原书意图**：讲 `ZwReadFile` / `ZwWriteFile` 的用法。

**官方文档要点**​ ：

`ZwReadFile` / `ZwWriteFile` 的参数高度对称：

```
NTSTATUS ZwReadFile(
    HANDLE FileHandle,                  // 5.1.2 中获得的句柄
    HANDLE Event,                       // 事件对象（异步完成用，驱动一般设 NULL）
    PIO_APC_ROUTINE ApcRoutine,         // APC 例程（驱动设 NULL）
    PVOID ApcContext,                   // APC 上下文（设 NULL）
    PIO_STATUS_BLOCK IoStatusBlock,     // I/O 状态块
    PVOID Buffer,                       // 数据缓冲区
    ULONG Length,                       // 缓冲区长度
    PLARGE_INTEGER ByteOffset,          // 文件偏移
    PULONG Key                          // 保留，设 NULL
);
```

**三种偏移指定方式**（这是原书可能没讲透的关键点）：

1. **显式偏移**：`ByteOffset` 指向一个 `LARGE_INTEGER`，指定绝对偏移
2. **当前位置**：如果 `ZwCreateFile` 时指定了 `FILE_SYNCHRONOUS_IO_NONALERT`，I/O 管理器维护当前文件位置，`ByteOffset` 可传 `NULL`
3. **追加模式**：用 `FILE_APPEND_DATA` 访问权打开句柄，`ByteOffset` 被忽略，数据总是写到文件末尾

**读取注册表值的标准"两步走"模式**（微软官方示例 ）：

```
// 写文件
ntstatus = ZwCreateFile(&handle, GENERIC_WRITE, &objAttr, &ioStatusBlock,
    NULL, FILE_ATTRIBUTE_NORMAL, 0, FILE_OVERWRITE_IF,
    FILE_SYNCHRONOUS_IO_NONALERT, NULL, 0);
if (NT_SUCCESS(ntstatus)) {
    ZwWriteFile(handle, NULL, NULL, NULL, &ioStatusBlock,
                buffer, cb, NULL, NULL);
    ZwClose(handle);
}

// 读文件
LARGE_INTEGER byteOffset;
ntstatus = ZwCreateFile(&handle, GENERIC_READ, &objAttr, &ioStatusBlock,
    NULL, FILE_ATTRIBUTE_NORMAL, 0, FILE_OPEN,
    FILE_SYNCHRONOUS_IO_NONALERT, NULL, 0);
if (NT_SUCCESS(ntstatus)) {
    byteOffset.LowPart = byteOffset.HighPart = 0;
    ZwReadFile(handle, NULL, NULL, NULL, &ioStatusBlock,
               buffer, BUFFER_SIZE, &byteOffset, NULL);
    ZwClose(handle);
}
```

> ⚠️ **工业界血泪教训**：
> 
> 1. `ZwWriteFile` 的 `Buffer` **必须是内核模式地址**，且缓冲区不能位于分页内存（如果 IRQL 可能升高）
> 2. 写操作返回的 `IoStatusBlock.Information` 才是**实际写入的字节数**——必须检查，因为磁盘满、配额超限等都会导致部分写入
> 3. 文件 I/O 是**耗时操作**（可能涉及磁盘调度、缓存管理器、文件系统驱动），绝不能在内核关键路径（如中断服务例程 ISR）中调用
> 4. 现代驱动框架（KMDF）提供了 `WdfFileObject` 等抽象，但底层依然是这套 `ZwXxx` 接口

**与现代文件操作的衔接**：

- 微软在 Win10 1803 引入了 **`IoGetDriverDirectory`**​ 和 **`IoGetDeviceDirectory`**​ API，让驱动有了一个"官方认可"的持久化文件目录（类似用户态的 `ProgramData`），避免在 `C:` 根目录随意写文件
- 这个目录通过符号链接 `\DriverData` 在内核中访问，用户态通过环境变量 `%DriverData%` 访问

## 5.2 注册表操作

### 第一性原理：注册表是内核的"配置数据库"，但访问它依然是"对象管理器命名空间解析"

注册表键在内核眼里**不是注册表**，而是对象管理器命名空间里的另一种对象，路径形如：

```
\Registry\Machine\SYSTEM\CurrentControlSet\Services\MyDriver
```

微软官方文档明确：打开注册表键是一个**两步过程**​ ——

1. 调用 `InitializeObjectAttributes` 初始化 `OBJECT_ATTRIBUTES`，`ObjectName` 必须是 `\Registry` 开头的完整路径（如果 `RootDirectory` 为 NULL）
2. 调用 `ZwCreateKey` 或 `ZwOpenKey` 传入这个结构

> 💡 **我的洞见**：注册表和文件在内核里走的是**同一套对象管理器基础设施**——`OBJECT_ATTRIBUTES` + `ZwCreateXxx` + `ZwClose` 这套范式对两者完全一致。这不是巧合，而是 Windows 内核架构的统一性体现：**对象管理器是统一命名空间，文件、注册表键、事件、互斥体、信号量……全是这个命名空间里的对象**。理解这一点，你对整个 Windows 内核的"对象世界观"就打通了。

### 5.2.1 注册表键的打开

**原书意图**：讲 `ZwCreateKey`（创建或打开）和 `ZwOpenKey`（仅打开已存在的键）。

**ZwOpenKey 函数签名**（微软官方 ）：

```
NTSTATUS ZwOpenKey(
    PHANDLE KeyHandle,                 // 输出的键句柄
    ACCESS_MASK DesiredAccess,          // 请求的访问权限
    POBJECT_ATTRIBUTES ObjectAttributes // 键的路径与属性
);
```

**关键规则**：

- 如果键不存在，`ZwOpenKey` 返回错误，**不会创建键**​
- 不在系统线程上下文调用时，必须设置 `OBJ_KERNEL_HANDLE`
- `ZwOpenKey` **忽略**​ `ObjectAttributes` 中的安全描述符
- 用完后必须 `ZwClose(KeyHandle)`

**DesiredAccess 与操作的对应关系**（微软官方文档 ）：

|操作|所需访问权|
|---|---|
|读注册表值|`KEY_QUERY_VALUE` 或 `KEY_READ`|
|写注册表值|`KEY_SET_VALUE` 或 `KEY_WRITE`|
|枚举子键|`KEY_ENUMERATE_SUB_KEYS` 或 `KEY_READ`|
|创建子键|`KEY_CREATE_SUB_KEY` 或 `KEY_WRITE`|
|删除键|`DELETE`|

**标准代码**（参考官方文档）：

```
UNICODE_STRING keyName;
OBJECT_ATTRIBUTES objAttr;
HANDLE keyHandle;

RtlInitUnicodeString(&keyName, L"\\Registry\\Machine\\SYSTEM\\CurrentControlSet\\Services\\MyDriver");
InitializeObjectAttributes(&objAttr, &keyName,
    OBJ_CASE_INSENSITIVE | OBJ_KERNEL_HANDLE, NULL, NULL);

NTSTATUS status = ZwOpenKey(&keyHandle, KEY_READ, &objAttr);
if (NT_SUCCESS(status)) {
    // 操作键...
    ZwClose(keyHandle);
}
```

**相对打开的高级玩法**：

```
// 先打开父键
ZwOpenKey(&parentHandle, KEY_READ, &parentObjAttr);
// 再用相对路径打开子键
UNICODE_STRING subKeyName;
RtlInitUnicodeString(&subKeyName, L"Parameters");
InitializeObjectAttributes(&subObjAttr, &subKeyName,
    OBJ_CASE_INSENSITIVE | OBJ_KERNEL_HANDLE, parentHandle, NULL);
ZwOpenKey(&subHandle, KEY_READ, &subObjAttr);
```

**现代工业实践——WDF 框架的注册表抽象**：

今天写 KMDF 驱动，微软推荐用 **WDF 框架的注册表对象**而非裸 `ZwXxx` 调用 ：

- `WdfDeviceOpenRegistryKey`：打开设备的硬件键或驱动的软件键
- `WdfDriverOpenParametersRegistryKey`：打开驱动的 Parameters 子键
- `WdfRegistryQueryULong` / `WdfRegistryAssignULong`：类型安全的读/写
- `WdfRegistryClose`：关闭（但通常由 WDF 对象生命周期自动管理）

```
// 现代 KMDF 风格
WDFKEY key;
NTSTATUS status = WdfDeviceOpenRegistryKey(
    device,
    PLUGPLAY_REGKEY_DRIVER,
    KEY_READ,
    WDF_NO_OBJECT_ATTRIBUTES,
    &key
);
if (NT_SUCCESS(status)) {
    ULONG value;
    status = WdfRegistryQueryULong(key, &valueName, &value);
    // key 的生命周期由 WDF 对象框架管理
}
```

> 💡 **洞见**：WDF 的注册表抽象不只是"语法糖"，它解决了三个工程痛点：
> 
> 1. **生命周期管理**：WDFKEY 对象绑定到父对象（如 WDFDEVICE），父对象销毁时自动关闭键句柄——消灭句柄泄漏
> 2. **类型安全**：`WdfRegistryQueryULong` 等强类型 API 消除了 `ZwQueryValueKey` 的"两步走"缓冲区猜测游戏
> 3. **跨 UMDF/KMDF 统一**：同一套 API 在用户态驱动（UMDF）和内核态驱动（KMDF）中都可用

### 5.2.2 注册表值的读

**原书意图**：讲 `ZwQueryValueKey` 的用法。

**这是注册表操作里最"反人性"的一个 API**——因为它要求"两步走"：

```
// 第一步：探测大小
ULONG resultLength;
status = ZwQueryValueKey(
    keyHandle,
    &valueName,
    KeyValuePartialInformation,
    NULL,                   // 缓冲区为 NULL
    0,                      // 长度为 0
    &resultLength           // 返回所需大小
);
// status == STATUS_BUFFER_TOO_SMALL，resultLength 为所需大小

// 第二步：分配缓冲区并真正读取
PVOID buffer = ExAllocatePool2(POOL_FLAG_PAGED, resultLength, TAG);
if (buffer) {
    status = ZwQueryValueKey(
        keyHandle,
        &valueName,
        KeyValuePartialInformation,
        buffer,
        resultLength,
        &resultLength
    );
    if (NT_SUCCESS(status)) {
        // buffer 前 4 字节是类型，然后是数据
        ULONG type = *(ULONG*)buffer;
        PVOID data = (PUCHAR)buffer + 4;
        // 使用数据...
    }
    ExFreePool(buffer);
}
```

**ZwQueryValueKey 参数要点**​ ：

- `KeyValueInformationClass`：常用 `KeyValuePartialInformation`（返回类型和值数据，不含名字）
- 读取的数据类型由 `Type` 字段决定：`REG_DWORD`、`REG_SZ`、`REG_BINARY`、`REG_MULTI_SZ` 等

**工业界更现代的读法**——使用 `RtlQueryRegistryValues`：

这个 RTL 例程允许一次性查询多个值，且由系统处理缓冲区分配，大大简化了代码。但它依然要求调用者在 `PASSIVE_LEVEL`。

**WDF 框架的现代化读法**：

```
ULONG timeout;
NTSTATUS status = WdfRegistryQueryULong(key, &valueName, &timeout);
// 一行搞定，无需两步走，无需手动分配
```

### 5.2.3 注册表值的写

**原书意图**：讲 `ZwSetValueKey` 的用法。

**函数签名**（微软官方 ）：

```
NTSTATUS ZwSetValueKey(
    HANDLE KeyHandle,            // 5.2.1 中打开的键句柄
    PUNICODE_STRING ValueName,   // 值名（可为 NULL 表示"(默认)"值）
    ULONG TitleIndex,            // 保留，驱动必须设 0
    ULONG Type,                  // 数据类型
    PVOID Data,                  // 数据缓冲区
    ULONG DataSize               // 数据大小
);
```

**关键语义**：

- 值名不存在 → **创建**新值
- 值名已存在 → **覆盖**原有值
- `KeyHandle` 必须有 `KEY_SET_VALUE` 访问权

**标准写法**：

```
UNICODE_STRING valueName;
RtlInitUnicodeString(&valueName, L"Timeout");

ULONG timeout = 5000;  // 5 seconds
ZwSetValueKey(keyHandle, &valueName, 0, REG_DWORD, &timeout, sizeof(timeout));

// 写字符串值
UNICODE_STRING valueData;
RtlInitUnicodeString(&valueData, L"MyDriverState");
ZwSetValueKey(keyHandle, &valueName, 0, REG_SZ, valueData.Buffer, valueData.Length);
```

**工业界注册表使用的最佳实践**（2025 年微软与 OSR 联合推荐 ）：

|做什么|怎么做|
|---|---|
|避免硬编码路径|用 `WdfDriverOpenParametersRegistryKey` 打开 Parameters 键|
|设备特定配置|用 `WdfDeviceOpenRegistryKey` 打开设备硬件键|
|运行时状态持久化|用 `WdfDriverOpenPersistentStateRegistryKey`|
|文件持久化|用 `IoGetDriverDirectory` 获取 `\DriverData\<Company>\<App>` 路径|
|日志/崩溃转储|写入 `%DriverData%\<Company>\Logs`|
|验证用户输入|所有从注册表读到的值**必须验证范围和语义**​|

> 💡 **我的洞见**：注册表在内核编程里的角色，2009 年和 2025 年发生了根本性变化：
> 
> - **2009 年（原书时代）**：注册表是驱动存储配置的**唯一正规途径**，驱动在 `DriverEntry` 里直接 `ZwOpenKey(\Registry\Machine\SYSTEM\CurrentControlSet\Services\MyDriver\Parameters)` 读配置
> - **2025 年**：微软明确划分了**配置的三类位置**——
>     1. **INF 提供的只读参数**：放在 Service 的 `Parameters` 子键，运行时只读
>     2. **运行时持久化状态**：放在专门的 PersistentState 位置
>     3. **设备特定状态**：放在设备的硬件键下
> 
> 这种划分的第一性原理是：**配置的可变性决定了它的存放位置**。只读配置（如默认超时）和可变状态（如当前连接数）混在同一个键里，是导致驱动升级/回滚时出现"脏状态"问题的根源。现代驱动框架强制这种分离，是 15 年来无数注册表相关 Bug 换来的工程智慧。

# 第 5 章的知识地图与前后联系

把这一章放进全书脉络：

```
第 1-3 章：C ↔ 汇编 ↔ 反汇编（机器视角）
第 4 章：字符串 + 内存 + 链表 + 锁（内核原语）
                ↓
第 5 章：文件 + 注册表（内核持久化状态）← 你在这里
                ↓
第 6+ 章：磁盘过滤 / 文件系统过滤 / 网络过滤（实战）
```

**为什么文件与注册表要放在过滤驱动实战之前？**

因为过滤驱动的核心工作模式是——**拦截请求 + 查配置 + 写日志/状态**：

- **配置查询**：过滤驱动从注册表读规则（如"哪些进程可以访问哪些文件"）→ 5.2 节
- **状态持久化**：过滤驱动把审计日志写入文件 → 5.1 节
- **策略存储**：加密驱动把密钥/策略存注册表 → 5.2 节
- **黑白名单**：防毒引擎把病毒特征库从文件读入内核内存 → 5.1 节

没有第 5 章的基础，第 6 章（磁盘过滤）、第 7 章（文件系统过滤）根本无从下手——你拦截了 IRP 却不知道"该不该放行"，因为规则还没地方读。

**2009 → 2025 的演进主线**：

|维度|原书时代（2009）|今天（2025-2026）|
|---|---|---|
|文件访问|`ZwCreateFile` + `\DosDevices\C:`|优先 `\SystemRoot`；持久化文件用 `\DriverData`|
|注册表访问|裸 `ZwOpenKey` + 硬编码 `\Registry\Machine\...`|WDF 框架的 `WdfXxxRegistryXxx` 抽象|
|句柄管理|手动 `ZwClose`|WDF 对象生命周期自动管理|
|IRQL 约束|强调 `PASSIVE_LEVEL`|依然 `PASSIVE_LEVEL`，但 WDF 工作项框架更成熟|
|配置与状态分离|不区分|强制分离：Parameters（只读）/ PersistentState（读写）/ Device Key（设备特定）|
|安全访问|可选 `OBJ_KERNEL_HANDLE`|非系统线程上下文**必须**​ `OBJ_KERNEL_HANDLE`；敏感场景加 `OBJ_FORCE_ACCESS_CHECK`|

> 📌 **终极洞见**：第 5 章教给你的不是"怎么读写文件/注册表"，而是**内核里"持久化状态"的两种范式**：
> 
> - **文件**​ = 大量、流式、非结构化或半结构化数据（日志、特征库、缓存）
> - **注册表**​ = 少量、离散、结构化配置（开关、超时、路径、策略）
> 
> 这两种范式的共同点是：**它们都是对象管理器命名空间里的对象**，访问它们必须遵守同一套规则——`OBJECT_ATTRIBUTES` 描述"我是谁、我要什么"，`OBJ_KERNEL_HANDLE` 保证"句柄不被用户态进程滥用"，`PASSIVE_LEVEL` 保证"访问时可调度"，`ZwClose` 保证"资源不泄漏"。
> 
> 原书 2009 年讲这套 API 时，系统多是单核/双核、XP/ Vista 主导、驱动模型以 WDM 为主。今天 128 核 CPU、Win11 24H2、KMDF 成为主流——但**对象管理器的这套核心范式 15 年未变**。这就是 Windows 内核设计的优雅之处：**底层原语稳定，上层框架演进**。你掌握了 `OBJECT_ATTRIBUTES` + `ZwCreateXxx` + `ZwClose` 这套三角关系，就等于拿到了打开整个 Windows 内核对象世界的万能钥匙——无论是文件、注册表、事件、互斥体、信号量，还是后面章节要讲的驱动对象、设备对象、文件对象，全都是这套范式。

**工业界今天的真实做法**：

- 新驱动一律用 **KMDF**，文件操作用 `WdfFileObject` 相关 API，注册表操作用 `WdfXxxRegistryXxx` 系列
- 持久化文件写入 `\DriverData<Company><Product>` 目录（Win10 1803+）
- 配置严格分离：INF 设置的参数（只读） vs 运行时状态（读写） vs 设备特定配置
- 所有注册表/文件操作封装在 `PASSIVE_LEVEL` 的工作项中，绝不在 `DISPATCH_LEVEL` 直接调用 `ZwXxx`
- 配合 **Driver Verifier**​ 的 `Deadlock detection` 和 `I/O Verification` 检测注册表/文件操作的误用
