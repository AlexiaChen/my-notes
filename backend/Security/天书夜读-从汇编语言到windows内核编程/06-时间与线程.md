# 第 6 章 时间与线程

## 6.1 时间与定时器

### 第一性原理：内核里"时间"不是钟表，是"调度决策的度量标尺"

用户态程序员眼里的"时间"是 `GetTickCount()` 返回的毫秒数、是 `time()` 返回的秒数——它们是给人看的。但**内核里的时间是为调度器服务的**：

- 线程要阻塞多久？→ 用相对时间
- 定时器什么时候到期？→ 用绝对时间
- 两个事件之间过了多久？→ 用滴答计数
- 日志里写的是什么钟点？→ 用系统时间

微软内核里至少有**三套并行的时间体系**，原书 2009 年可能没讲透，但今天必须分清：

|时间体系|代表 API|单位|更新频率|用途|
|---|---|---|---|---|
|滴答计数（Tick Count）|`KeQueryTickCount`|滴答数（tick）|每个时钟中断 +1|相对计时、时间戳、性能分析|
|系统时间（System Time）|`KeQuerySystemTime`|100 纳秒|约每 10 毫秒更新|日志时间戳、文件时间|
|性能计数器（Performance Counter）|`KeQueryPerformanceCounter`|高精度|硬件依赖|微秒级精确测量|

> 💡 **我的洞见**：理解这三套时间体系的第一性原理是——**它们服务于不同的"客户"**。`KeQueryTickCount` 服务于调度器（它只关心"又过了一个时钟中断"）；`KeQuerySystemTime` 服务于人类（它要给出"现在几点"）；`KeQueryPerformanceCounter` 服务于测量（它要给出尽可能细的粒度）。原书把"获得当前滴答数"和"获得当前系统时间"并列成两小节，本质上就是在教读者区分**"给调度器看的时间"**和**"给人看的时间"**——这是内核编程最容易被忽视的基础认知。

### 6.1.1 获得当前滴答数

**原书意图**：教读者用 `KeQueryTickCount` 获取系统启动以来的时钟中断次数。

**微软官方文档**明确 ：

```
VOID KeQueryTickCount(PLARGE_INTEGER CurrentCount);
```

- 返回的是**自系统启动以来间隔定时器中断的次数**
- 系统运行时，**每次间隔定时器中断 TickCount 加 1**
- 可在**任意 IRQL**​ 调用
- 最小支持 Windows 2000

**🚨 最关键的一点（原书可能讲了但今天必须反复强调）**：

> ⚠️ **你不应该对"一个 tick 的长度"做任何假设**——它会因硬件和其他因素而变化。

要获得真实的经过时间，必须配合 `KeQueryTimeIncrement`：

```
LARGE_INTEGER tickCount;
ULONG increment;  // 每个 tick 的 100 纳秒单位数

KeQueryTickCount(&tickCount);
increment = KeQueryTimeIncrement();

// 计算自启动以来的毫秒数
// 公式：毫秒 = (tickCount × increment) / 10000
// 因为 1 毫秒 = 10000 个 100 纳秒单位
```

现代系统上 `increment` 常见值为 **156250（15.625 毫秒）**​ 或 **390625（39.0625 毫秒）**——这意味着 `KeQueryTickCount` 的原始值**不是毫秒**，直接拿它当毫秒用会差 156 倍。

**为什么是 64 位？**​ 原书时代可能用 32 位的 `GetTickCount()`，49.7 天就会回绕（wrap around）。`KeQueryTickCount` 返回 64 位 `LARGE_INTEGER`，**理论上千年才会回绕**——这是内核级 API 与用户态 API 的一个典型差异：内核要求"绝对不回绕"的时间戳。

**工业界实际用法**：

- **性能分析**：记录函数入口和出口的 tick 差值，乘以 increment 得到耗时
- **随机数种子**：用 tick 数作为伪随机算法的初始熵
- **超时判断**：`if (current_tick - start_tick) * increment / 10000 > TIMEOUT_MS`
- **相对调度**：给定时器设置相对到期时间时，内核内部就用 tick 计数

> 💡 **洞见**：`KeQueryTickCount` + `KeQueryTimeIncrement` 这套组合，体现了内核时间度量的第一性原理——**"计数"与"换算"分离**。Tick 计数是调度器的母语（它只在乎"过了几个中断"），而"每个 tick 等于多少时间"是硬件相关的换算系数。这种分离让 Windows 能跑在从 10MHz 到 5GHz 跨度极大的硬件上，而调度逻辑本身不需改动。**这是抽象的力量**——原书教 API 用法，但真正的工程智慧是理解"为什么这么设计"。

### 6.1.2 获得当前系统时间

**原书意图**：教读者用 `KeQuerySystemTime` 获取当前的"墙钟时间"。

**微软官方文档**​ ：

```
VOID KeQuerySystemTime(PLARGE_INTEGER CurrentTime);
```

- 系统时间是**自 1601 年 1 月 1 日以来的 100 纳秒间隔计数**
- 通常在**大约每 10 毫秒更新一次**
- 这个值按 **GMT 时区**计算
- 调用 `ExSystemTimeToLocalTime` 转换为本地时区
- 可在**任意 IRQL**​ 调用

**关键认知**：

1. **1601-01-01 基准**：这是 Windows FILETIME 的基准，也是 `UNICODE_STRING` 时间戳、`CreateFile` 时间等的统一基准
2. **~10ms 更新频率**：系统时间精度只有 10ms 左右——如果你需要更高精度（微秒级），必须改用 `KeQueryPerformanceCounter`
3. **GMT 基准**：直接拿到的是 UTC 时间，要显示给用户看必须转本地时区

**标准转换流程**：

```
LARGE_INTEGER systemTime, localTime;
TIME_FIELDS timeFields;

KeQuerySystemTime(&systemTime);              // UTC 时间
ExSystemTimeToLocalTime(&systemTime, &localTime);  // 转本地时区
RtlTimeToTimeFields(&localTime, &timeFields);      // 拆成年/月/日/时/分/秒/毫秒

KdPrint(("当前时间: %04d-%02d-%02d %02d:%02d:%02d.%03d\n",
    timeFields.Year, timeFields.Month, timeFields.Day,
    timeFields.Hour, timeFields.Minute, timeFields.Second,
    timeFields.Milliseconds));
```

**工业界实际用法**：

- **日志时间戳**：驱动写日志时标注时间
- **文件时间**：与 `ZwCreateFile` 的文件属性时间字段对接
- **证书/许可证验证**：检查有效期
- **审计追踪**：安全驱动记录"何时发生了什么"

> ⚠️ **常见陷阱**：
> 
> - 不要拿 `KeQuerySystemTime` 做微秒级性能测量（精度不够）
> - 不要假设两次调用之间系统时间一定单调递增（NTP 校时可能回拨）
> - 系统时间可被管理员手动修改，不能用作安全敏感的单调计数

**与现代高精度时间的对比**：

|需求|推荐 API|
|---|---|
|日志时间戳（10ms 精度够用）|`KeQuerySystemTime`|
|性能测量（微秒级）|`KeQueryPerformanceCounter`|
|调度超时（tick 级）|`KeQueryTickCount`|
|定时器到期|`KeSetTimer` 的 `DueTime`（100ns 单位）|

### 6.1.3 使用定时器

**原书意图**：讲 `KTIMER` 对象 + `KeInitializeTimer` + `KeSetTimer` 的用法。

**微软官方文档**明确 ：从 Windows 2000 起，`KeXxxTimer` 系列例程管理基于 `KTIMER` 结构的定时器对象。

**核心 API 三步曲**：

1. **分配并初始化定时器**：

```
KTIMER timer;
KeInitializeTimer(&timer);  
// 默认创建"通知定时器"（Notification Timer）
// 或用 KeInitializeTimerEx(&timer, SynchronizationTimer/NotificationTimer)
```

1. **设置到期时间**：

```
LARGE_INTEGER dueTime;
dueTime.QuadPart = -10000 * 500;  // 相对 500 毫秒（负值=相对时间，单位 100ns）
// 正值 = 绝对时间（1601-01-01 起的 100ns 计数）

BOOLEAN pending = KeSetTimer(&timer, dueTime, NULL);
// KeSetTimer 只设置单次定时器
// KeSetTimerEx(&timer, dueTime, Period, Dpc) 可设置周期定时器
```

1. **可选：关联 DPC 例程**：

```
KDPC dpc;
KeInitializeDpc(&dpc, CustomTimerDpc, Context);
KeSetTimer(&timer, dueTime, &dpc);
// 定时器到期时，CustomTimerDpc 在 DISPATCH_LEVEL 执行
```

**通知定时器 vs 同步定时器**（这是原书可能讲了但值得深度展开的）：

|类型|到期行为|典型用途|
|---|---|---|
|**通知定时器**​ (Notification Timer)|变为 Signaled 后**保持**​ Signaled，直到显式重置|多个线程等待同一个定时器|
|**同步定时器**​ (Synchronization Timer)|变为 Signaled 后**自动重置**为 Not-Signaled，当一个等待线程被释放后|单次超时通知|

**微软官方图解的标准模式**​ ：

```
线程上下文（PASSIVE_LEVEL）：
1. KeInitializeTimer 初始化定时器
2. KeSetTimer(&timer, dueTime, NULL)  // 不关联 DPC
3. KeWaitForSingleObject(&timer, ...)  // 线程阻塞等待
4. 定时器到期 → 内核将定时器从队列移除并设为 Signaled → 线程变为 Ready
```

**IRQL 约束与 DPC 的角色**：

> ⚠️ **关键规则**：`KeSetTimer` 可在 `DISPATCH_LEVEL` 调用，但**只有当 `DueTime` 为负值（相对时间）时**；在 `DISPATCH_LEVEL` 或更高 IRQL 运行的驱动例程**必须**通过将定时器对象与关联的 DPC 对象结合使用，以便在超时发生时排队执行驱动程序提供的 `CustomTimerDpc` 例程。

**工业界最佳实践**：

1. **单次超时 vs 周期定时器**：

```
// 单次超时（常用）
KeSetTimer(&timer, dueTime, NULL);

// 周期定时器（每隔 1 秒触发一次 DPC）
#define PERIOD_MS 1000
LARGE_INTEGER period;
period.QuadPart = -10000 * PERIOD_MS;  // 首次到期：1 秒后
KeSetTimerEx(&timer, period, PERIOD_MS, &dpc);  // Period 参数单位是毫秒
```

1. **取消定时器**：

```
KeCancelTimer(&timer);  // 返回 BOOLEAN，TRUE 表示定时器在队列中并被取消
```

1. **WORKER THREAD 模式**（现代推荐）：

```
// 在系统线程中等待定时器
PsCreateSystemThread(&hThread, ..., TimerThreadProc, &timer);

VOID TimerThreadProc(PVOID Context) {
    PKTIMER timer = (PKTIMER)Context;
    while (!bShouldExit) {
        KeWaitForSingleObject(timer, Executive, KernelMode, FALSE, NULL);
        // 定时器到期，做实际工作（在 PASSIVE_LEVEL）
        DoPeriodicWork();
    }
    PsTerminateSystemThread(STATUS_SUCCESS);
}
```

> 💡 **我的洞见**：定时器在内核里扮演的角色，2009 年和 2025 年有了重要的架构演进：
> 
> - **2009 年（原书时代）**：`KTIMER` + `CustomTimerDpc` 是主流模式，DPC 里做大量工作（受限于 DISPATCH_LEVEL 约束）
> - **2025 年**：微软明确推荐**将定时器到期与系统工作线程结合**——定时器 DPC 只做"唤醒工作线程"这一件事，实际工作在 `PASSIVE_LEVEL` 的系统线程里完成。这是因为：
>     1. DISPATCH_LEVEL 上不能访问分页数据、不能等待、不能做复杂操作
>     2. 现代系统多核化，长时间占住 DPC 会影响整个 CPU 的调度延迟
>     3. 工作线程模型更符合"关注点分离"——定时逻辑与业务处理逻辑解耦
> 
> 这个演进的第一性原理是：**DPC 是"紧急但不重要"的执行上下文，系统线程是"重要但不紧急"的执行上下文**。定时器到期是"紧急"事件（必须准时响应），但具体工作往往"不重要到需要在 DISPATCH_LEVEL 立刻完成"——所以现代驱动的标准做法是：DPC 唤醒 → 工作线程处理。

**现代 KMDF 框架的对应物**：

- `WdfTimerCreate` + `WdfTimerStart` / `WdfTimerStop`
- 定时器到期回调在 `PASSIVE_LEVEL` 或 `DISPATCH_LEVEL` 可配置
- 由框架管理定时器对象生命周期，卸载时自动停止并等待回调完成

## 6.2 线程与事件

### 第一性原理：内核线程是"内核里的执行流"，事件是"执行流之间的握手信号"

用户态程序里，线程是 `CreateThread` 创建的，由操作系统调度；事件是什么 `CreateEvent` 创建的内核对象句柄。但**在内核态，线程和事件都是"分发对象"（Dispatcher Object）**——它们是对象管理器命名空间里的一类特殊对象，可以被 `KeWaitForSingleObject` 等待。

微软内核文档明确 ：`PsCreateSystemThread` 创建与给定进程对象或默认系统进程关联的内核模式线程；`KeInitializeEvent` 将事件对象初始化为同步（单个服务员）或通知（多个服务员）类型事件。

### 6.2.1 使用系统线程

**原书意图**：讲 `PsCreateSystemThread` 创建内核线程。

**微软官方文档要点**​ ：

**为什么需要系统线程？**

> 速度较慢的设备或你很少使用的设备（例如 CD/DVD 光驱）的驱动程序，可以通过建立设备专用的系统线程来解决许多"等待"问题。此外，大部分的文件系统驱动程序都会使用系统后台工作线程。

**标准创建代码**：

```
HANDLE hThread;
NTSTATUS status = PsCreateSystemThread(
    &hThread,          // 输出的线程句柄
    0,                 // DesiredAccess
    NULL,              // ObjectAttributes
    NULL,              // ProcessHandle（NULL = 系统线程，属于 System 进程 PID=4）
    NULL,              // ClientId
    ThreadStartRoutine,// 线程函数
    Context            // 传给线程函数的参数
);

// 线程函数签名
VOID ThreadStartRoutine(IN PVOID Context);
```

**🚨 关键工程要点（微软官方文档强调）**​ ：

1. **线程函数必须调用 `PsTerminateSystemThread` 自我终止**：

```
VOID MyThreadProc(IN PVOID Context) {
    // ... 做工作 ...
    PsTerminateSystemThread(STATUS_SUCCESS);
    // 注意：这行之后不会执行
}
```

1. **获取线程对象指针**（用于等待线程退出）：

```
HANDLE hThread;
PsCreateSystemThread(&hThread, ...);

PETHREAD pThread;
ObReferenceObjectByHandle(hThread, THREAD_ALL_ACCESS, NULL,
                          KernelMode, &pThread, NULL);
ZwClose(hThread);  // 关闭句柄，但对象指针仍有效

// 等待线程退出
KeWaitForSingleObject(pThread, Executive, KernelMode, FALSE, NULL);

// 线程退出后
ObDereferenceObject(pThread);  // 释放对象引用
```

1. **优先级设置**（避免优先级反转）：

```
KeSetBasePriorityThread(PsGetCurrentThread(), LOW_REALTIME_PRIORITY);
```

> ⚠️ 微软明确警告 ：将驱动程序建立线程的基底优先级设定得太高，可能会在提交该驱动程序 I/O 要求的较低优先级线程时造成延迟（优先级反转问题）。

**IRQL 约束**：

- `PsCreateSystemThread` 必须在 **`PASSIVE_LEVEL`**​ 调用
- 系统线程本身运行在 **`PASSIVE_LEVEL`**
- 这意味着系统线程可以做任何 `PASSIVE_LEVEL` 允许的操作：文件 I/O、注册表访问、分页内存分配等

**工业界实际使用模式**：

**模式一：专用设备线程**（经典模式）

```
// 驱动设备扩展里保存线程对象指针
typedef struct _DEVICE_EXTENSION {
    KEVENT StartEvent;      // 通知线程开始工作
    KEVENT ExitEvent;       // 通知主线程线程已退出
    PETHREAD ThreadObject;  // 线程对象指针
    BOOLEAN ShouldExit;     // 退出标志
} DEVICE_EXTENSION;

// 创建设备专用线程
PsCreateSystemThread(&hThread, 0, NULL, NULL, NULL, 
                     DeviceThreadProc, deviceExtension);
ObReferenceObjectByHandle(hThread, ..., &devExt->ThreadObject, ...);
ZwClose(hThread);

// 线程函数
VOID DeviceThreadProc(IN PVOID Context) {
    PDEVICE_EXTENSION devExt = (PDEVICE_EXTENSION)Context;
    KeSetBasePriorityThread(PsGetCurrentThread(), LOW_REALTIME_PRIORITY);
    
    while (!devExt->ShouldExit) {
        // 等待"开始工作"事件或 1 秒超时
        LARGE_INTEGER timeout;
        timeout.QuadPart = -10000 * 1000;  // 1 秒
        NTSTATUS status = KeWaitForSingleObject(
            &devExt->StartEvent, Executive, KernelMode, FALSE, &timeout);
        
        if (status == STATUS_TIMEOUT) {
            // 超时：做周期性任务
            DoPeriodicTask();
        } else {
            // 被事件唤醒：处理具体工作
            ProcessWorkItem();
        }
    }
    
    // 通知主线程：我要退出了
    KeSetEvent(&devExt->ExitEvent, 0, FALSE);
    PsTerminateSystemThread(STATUS_SUCCESS);
}

// 卸载时
devExt->ShouldExit = TRUE;
KeSetEvent(&devExt->StartEvent, 0, FALSE);  // 唤醒线程
KeWaitForSingleObject(devExt->ThreadObject, Executive, KernelMode, FALSE, NULL);
ObDereferenceObject(devExt->ThreadObject);
```

**模式二：工作线程池**（现代文件系统驱动常用）

> 微软文档指出 ："大部分的文件系统驱动程序都会使用系统后台工作线程，并提供后台工作线程回调例程。"

**模式三：WDF 工作项**（现代 KMDF 推荐）

```
WDF_WORKITEM_CONFIG config;
WDF_WORKITEM_CONFIG_INIT(&config, MyWorkItemHandler);
WDFWORKITEM workItem;
WdfWorkItemCreate(&config, WDF_NO_OBJECT_ATTRIBUTES, &workItem);
WdfWorkItemEnqueue(workItem);  // 由系统线程池执行
```

**优势**：无需手动管理线程生命周期，框架自动使用系统线程池

### 6.2.2 在线程中睡眠

**原书意图**：讲如何让内核线程"睡一段时间"。

**核心 API：`KeDelayExecutionThread`**

```
NTSTATUS KeDelayExecutionThread(
    KPROCESSOR_MODE WaitMode,       // KernelMode 或 UserMode
    BOOLEAN Alertable,              // 是否可告警
    PLARGE_INTEGER Interval         // 睡眠时间（负=相对时间，单位 100ns）
);
```

**标准用法**：

```
// 睡眠 500 毫秒
LARGE_INTEGER delay;
delay.QuadPart = -10000 * 500;  // 负值表示相对时间
KeDelayExecutionThread(KernelMode, FALSE, &delay);
```

**关键规则**：

> ⚠️ **`KeDelayExecutionThread` 只能在 `PASSIVE_LEVEL` 调用**——它本质上是调用 `KeWaitForSingleObject` 等待一个内部定时器对象。如果在 `DISPATCH_LEVEL` 或更高 IRQL 调用，系统直接 Bug Check。

**替代方案：用定时器 + 等待**（适用于任何 IRQL 的"睡眠"模拟）：

```
// 在 DISPATCH_LEVEL 不能"睡眠"，但可以设置定时器并在 DPC 中做工作
KTIMER timer;
KDPC dpc;
KeInitializeTimer(&timer);
KeInitializeDpc(&dpc, TimerDpcProc, Context);
KeSetTimer(&timer, dueTime, &dpc);
// 当前代码路径继续执行，DPC 在定时器到期时触发
```

**工业界最佳实践**：

1. **避免在驱动关键路径上睡眠**：睡眠会阻塞当前线程，如果是处理 IRP 的线程，会阻塞整个 I/O 请求链
2. **用工作线程睡眠**：如果需要周期性任务，创建工作线程，在线程里 `KeDelayExecutionThread`
3. **用定时器替代长睡眠**：如果是"N 秒后做某事"，用 `KeSetTimer` + DPC，而非"睡眠 N 秒后继续"

```
// 不好的做法：在 IRP 处理中睡眠
// 好的做法：队列工作项，在工作项里睡眠
WdfWorkItemEnqueue(workItem);

VOID MyWorkItemHandler(WDFWORKITEM WorkItem) {
    // 这里运行在系统线程上下文（PASSIVE_LEVEL）
    LARGE_INTEGER delay;
    delay.QuadPart = -10000 * 1000;  // 睡眠 1 秒
    KeDelayExecutionThread(KernelMode, FALSE, &delay);
    // 继续处理
}
```

> 💡 **洞见**：内核线程的"睡眠"本质不是真的"睡"，而是**主动放弃 CPU 并让自己进入 Wait 状态**，直到定时器对象 Signaled 才被唤醒。这与用户态 `Sleep()` 的原理完全一致——都是线程调度器的"等待-唤醒"机制。原书可能把"睡眠"当作独立概念讲，但它的第一性原理是**"定时器和等待的合体"**：`KeDelayExecutionThread` 内部就是创建一个一次性定时器，然后 `KeWaitForSingleObject` 它。理解这一点，你就明白为什么"睡眠"只能在 `PASSIVE_LEVEL`——因为它本质是等待。

### 6.2.3 使用同步事件

**原书意图**：讲 `KEVENT` + `KeInitializeEvent` + `KeSetEvent` + `KeWaitForSingleObject` 实现线程间同步。

**微软官方文档**​ ：`KeInitializeEvent` 将事件对象初始化为同步（单个服务员）或通知（多个服务员）类型事件并设置其初始状态。

**事件的两大类型**（这是原书一定会强调的核心知识点）：

|类型|参数|行为特征|典型用途|
|---|---|---|---|
|**同步事件**​ (SynchronizationEvent)|`SynchronizationEvent`|当事件为激发态时，遇到 `KeWaitForXxx` 等内核函数，**事件对象会自动变回到未激发态**​|一对一的生产者-消费者|
|**通知事件**​ (NotificationEvent)|`NotificationEvent`|当事件变为激发态时，**需要手动将其改回未激发态**​|一对多的广播通知|

**标准用法**：

```
// 1. 初始化同步事件（初始未激发）
KEVENT event;
KeInitializeEvent(&event, SynchronizationEvent, FALSE);

// 2. 生产者线程：设置事件（唤醒一个等待者）
KeSetEvent(&event, 0, FALSE);

// 3. 消费者线程：等待事件
NTSTATUS status = KeWaitForSingleObject(
    &event,              // 等待的事件对象
    Executive,           // 等待模式
    KernelMode,          // 处理器模式
    FALSE,               // 不可告警
    NULL                 // 无超时（永久等待）
);
// 返回 STATUS_SUCCESS 表示事件被激发
// 因为是同步事件，返回时事件自动重置为未激发态
```

**KeWaitForSingleObject 的超时用法**：

```
LARGE_INTEGER timeout;
timeout.QuadPart = -10000 * 5000;  // 5 秒超时

NTSTATUS status = KeWaitForSingleObject(
    &event, Executive, KernelMode, FALSE, &timeout);

if (status == STATUS_TIMEOUT) {
    // 5 秒内事件未被激发
} else if (NT_SUCCESS(status)) {
    // 事件被激发
}
```

**多对象等待**：`KeWaitForMultipleObjects` 可同时等待多个事件/对象，支持"任一对象激发"或"所有对象激发"两种模式。

**🚨 关键工程要点**：

1. **事件对象的内存生命周期**：

> ⚠️ `KEVENT` 必须是**非分页内存**，且**在等待它的所有线程退出前不能被释放**。最常见 Bug：驱动卸载时事件还在被等待，导致 Bug Check 0x50 或 0xC4。

2. **IRQL 约束**：

> ⚠️ `KeWaitForSingleObject` 只能在 **`PASSIVE_LEVEL`**​ 调用（当指定超时或非零绝对时间时）。在 `DISPATCH_LEVEL` 只能做"零超时"的轮询式等待，或者直接用自旋锁。

3. **Alertable 参数**：

> - `FALSE`：等待不可被 APC 打断
> - `TRUE`：等待可被 APC 打断，返回 `STATUS_ALERTED`

**工业界经典模式：生产者-消费者队列**

```
// 设备扩展
typedef struct _DEVICE_EXTENSION {
    KEVENT ItemAvailable;     // 同步事件：队列中有项可处理
    KEVENT ExitThread;        // 通知事件：线程应退出
    KSPIN_LOCK QueueLock;     // 保护队列的自旋锁
    LIST_ENTRY WorkQueue;     // 工作项队列
    PETHREAD WorkerThread;    // 工作线程对象指针
} DEVICE_EXTENSION;

// 初始化
KeInitializeEvent(&devExt->ItemAvailable, SynchronizationEvent, FALSE);
KeInitializeEvent(&devExt->ExitThread, NotificationEvent, FALSE);
KeInitializeSpinLock(&devExt->QueueLock);
InitializeListHead(&devExt->WorkQueue);

// 生产者（可能在 DISPATCH_LEVEL，如 DPC 中）
VOID ProduceWorkItem(PDEVICE_EXTENSION devExt, PWORK_ITEM item) {
    KIRQL irql;
    KeAcquireSpinLock(&devExt->QueueLock, &irql);
    InsertTailList(&devExt->WorkQueue, &item->ListEntry);
    KeReleaseSpinLock(&devExt->QueueLock, irql);
    
    // 唤醒工作线程
    KeSetEvent(&devExt->ItemAvailable, 0, FALSE);
}

// 消费者线程（运行在 PASSIVE_LEVEL）
VOID ConsumerThreadProc(IN PVOID Context) {
    PDEVICE_EXTENSION devExt = (PDEVICE_EXTENSION)Context;
    KeSetBasePriorityThread(PsGetCurrentThread(), LOW_REALTIME_PRIORITY);
    
    while (TRUE) {
        // 等待"有工作项"或"退出信号"
        PVOID objects[] = { &devExt->ItemAvailable, &devExt->ExitThread };
        NTSTATUS status = KeWaitForMultipleObjects(
            2, objects, WaitAny, Executive, KernelMode, FALSE, NULL, NULL);
        
        if (status == STATUS_WAIT_0 + 1) {
            // ExitThread 事件被激发，退出线程
            break;
        }
        
        // 处理队列中的所有工作项
        while (TRUE) {
            KIRQL irql;
            KeAcquireSpinLock(&devExt->QueueLock, &irql);
            if (IsListEmpty(&devExt->WorkQueue)) {
                KeReleaseSpinLock(&devExt->QueueLock, irql);
                break;
            }
            PLIST_ENTRY entry = RemoveHeadList(&devExt->WorkQueue);
            KeReleaseSpinLock(&devExt->QueueLock, irql);
            
            PWORK_ITEM item = CONTAINING_RECORD(entry, WORK_ITEM, ListEntry);
            ProcessWorkItem(item);  // 在 PASSIVE_LEVEL 处理
        }
    }
    
    PsTerminateSystemThread(STATUS_SUCCESS);
}
```

> 💡 **我的洞见**：事件同步的第一性原理是——**它是"执行流之间最轻量级的握手信号"**。相比于自旋锁（忙等、消耗 CPU）、相比于信号灯（Semaphore，可计数的复杂同步），事件是最简单的"二进制信号"——要么有信号，要么没信号。原书把"同步事件"作为 6.2.3 单独一节，正是因为它与"通知事件"有着本质的行为差异：
> 
> - **同步事件**​ = "自动重置" = 一对一通知（如生产者唤醒消费者）
> - **通知事件**​ = "手动重置" = 一对多广播（如告诉所有等待线程"可以退出了"）
> 
> 工业界的最佳实践是：**同步事件用于"任务分发"，通知事件用于"状态广播"**。上面的生产者-消费者代码就是典型案例——`ItemAvailable` 用同步事件（每次只唤醒一个消费者处理一个任务），`ExitThread` 用通知事件（广播给所有可能的等待者"该退出了"）。

**现代工业界的演进**：

- **WDF 框架的同步事件**：`WdfWaitLockCreate` / `WdfSpinLockCreate` 提供了更高级的抽象
- **WDF 工作项替代手写线程**：多数场景不需要 `PsCreateSystemThread`，用 `WdfWorkItemCreate` + `WdfWorkItemEnqueue` 即可
- **推锁（Push Lock）**：读多写少场景用 `EX_PUSH_LOCK` 替代事件+自旋锁组合
- **UEFI 与 SM 安全**：现代 Windows 驱动（特别是 Secure Core PC 上的驱动）对事件对象的内存保护有更严格要求，需用 `MmProtectDriverSection` 等 API 保护包含同步对象的数据段

```
                ↓

```

**为什么"时间与线程"要放在过滤驱动实战之前？**

因为过滤驱动的核心工作模式是——**拦截请求 → 查配置（可能要等待/睡眠） → 做处理（可能要开工作线程） → 记日志（可能要计时）**：

- **键盘过滤**：拦截按键 → 可能需要存储按键序列 → 定时回传（定时器 + 系统线程）
- **磁盘过滤**：拦截 IRP → 可能需要延迟处理 → 工作线程 + 事件同步
- **文件系统过滤**：Minifilter 回调 → 可能需要做耗时扫描 → 工作队列 + 睡眠
- **网络过滤**：拦截数据包 → 可能需要做深度检测 → 系统线程池处理

没有第 6 章的"时间度量 + 线程管理 + 事件同步"这套并发原语，第 7 章起的过滤驱动实战根本无从下手——你拦截了请求却不知道"如何在不阻塞 IRP 完成的情况下做耗时处理"，因为答案就在本章：用系统线程 + 事件通知 + 定时器超时。

**2009 → 2025 的演进主线**：

|维度|原书时代（2009）|今天（2025-2026）|
|---|---|---|
|获取时间|`KeQueryTickCount` + `KeQuerySystemTime`|同上，但新增 `KeQueryPerformanceCounter`（高精度）的广泛使用|
|定时器|`KTIMER` + `CustomTimerDpc`（DPC 里做大量工作）|`KTIMER` + DPC 仅唤醒工作线程，实际工作在 `PASSIVE_LEVEL` 系统线程完成|
|系统线程|`PsCreateSystemThread` 手写线程管理|优先用 WDF 工作项（`WdfWorkItemCreate`）；必须用手写线程时，微软仍推荐 `PsCreateSystemThread` + 事件通知模式|
|线程睡眠|`KeDelayExecutionThread`|同上，但明确限制在 `PASSIVE_LEVEL`；长睡眠优先用定时器|
|事件同步|`KEVENT` + `KeInitializeEvent`|同上；现代框架提供 `WdfWaitLock` 等高级抽象|
|优先级管理|未强调|微软明确警告避免优先级反转，推荐 `LOW_REALTIME_PRIORITY`|
|多核考虑|双核/四核为主|多核普及，自旋锁成本放大，事件+工作线程模型成为主流|

> 📌 **终极洞见**：第 6 章教给你的不是"几个 API 怎么用"，而是**内核并发模型的世界观**——在内核里，"时间"是调度的度量标尺，"线程"是执行的载体，"事件"是执行流之间的握手信号。这三者的关系构成了内核并发的第一性原理：
> 
> **执行流（线程）通过等待事件进入阻塞状态，调度器根据时间度量决定是否唤醒它**。
> 
> 原书 2009 年讲这套 API 时，系统多是单核/双核、XP/Vista 主导、调度器相对简单。今天 128 核 CPU、Win11 24H2、调度器高度复杂——但**这套"线程-事件-时间"的三角关系 15 年未变**。这就是 Windows 内核设计的优雅之处：**底层原语稳定，上层框架演进**。你掌握了 `PsCreateSystemThread` + `KEVENT` + `KeSetTimer` 这套三角关系，就等于拿到了构建任何内核并发场景的万能工具集——无论是过滤驱动的请求队列、文件系统驱动的延迟写入、还是网络驱动的数据包处理流水线，全都是这套原语的组合。
> 
> **工业界今天的真实做法**：
> 
> - 新驱动优先用 **KMDF 工作项**（`WdfWorkItemCreate`）而非手写系统线程
> - 必须用手写线程时，严格遵循微软官方模式 ：`PsCreateSystemThread` → `ObReferenceObjectByHandle` 获取线程对象指针 → 事件通知退出 → `KeWaitForSingleObject` 等待线程终止 → `ObDereferenceObject` 释放
> - 定时器 DPC 只做"唤醒"工作，实际业务逻辑在工作线程里完成
> - 配合 **Driver Verifier**​ 的 `Deadlock detection` 检测事件/线程的死锁
> - 在 SMP 系统中特别注意**优先级反转**问题，系统线程优先级不要设得过高
