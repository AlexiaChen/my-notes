
# 第 10 章 数据结构（Data Structures）

> 这一章是全书前半部分（第 2~9 章）所有机制的**集大成之战**——Paul 把"分割、数据所有权、锁、延后处理（RCU/引用计数/危险指针）"这些武器全部拿出来，用来构建**真正可扩展的并行数据结构**。而他选择的"练兵场"是**哈希表**——这个看似简单、却在工业界无处不在的数据结构（内核 dcache、inode cache、路由表、连接表、futex 哈希表、TCP 连接哈希表……）。
> 
> 为什么是哈希表？Paul 的理由很充分 ：
> 
> - 它是"读多写少"的典型（read-mostly）
>     
> - 它的"可分区性"谱系的演进路径。
>     
> - 它是并行数据结构设计的"麻雀"——解剖它就能掌握所有并行数据结构的设计哲学
>     
> 
> 全章的演进路径是一条**从"完全可分区"到"读侧重"到"不可分区但可扩展"的递进光谱**：
> 
> |演进阶段|核心技术|读者开销|写者开销|可扩展性|
> |---|---|---|---|---|
> |10.2 可分割哈希表|每桶锁（数据锁）|低（无竞争时）|中（桶锁）|随桶数线性|
> |10.3 读侧重 RCU 哈希表|RCU + 每桶锁|**零或近零**​|中（桶锁 + 宽限期）|读者近乎线性|
> |10.4 可扩展 RCU 哈希表|RCU + 双指针集 + 间接层|**零或近零**​|高（resize 成本）|读者线性 + 可动态扩缩|
> 
> 这条演进路径的本质是：**用越来越精巧的"延后处理 + 多版本共存"机制，把"写者/resize 的成本"与"读者的性能"彻底解耦**。

## 10.1 从例子入手（Choosing an Example）

**原文骨架**：Paul 明确选择哈希表作为贯穿全章的运行示例，并给出理由 ：

- 它是读多写少的典型
    
- 它在工业界广泛应用
    
- 它的并行化路径能展现从"简单锁"到"RCU"的完整演进
    

**第一性解读**：

这一节是 Paul 的"教学宣言"——**通过一个具体数据结构，把前面所有抽象机制落地**。哈希表的精妙之处在于：它的"可分区性"不是二元的（可分区/不可分区），而是**连续的谱系**：

- **固定大小哈希表**：完全可分区（每桶独立锁）
    
- **受 RCU 保护的固定大小哈希表**：读者无锁，写者仍按桶同步
    
- **可调整大小的哈希表**：部分可分区——查找可按桶分区，但 resize 操作需要全局协调
    

**🎯 第一性洞见**：Paul 选择哈希表，是因为哈希表的"可分区性谱系"恰好映射了全书的核心主题——**分割是并行的第一性原理，但当数据结构需要"动态调整"时，纯粹的分割不再够用，必须引入"延后处理"（RCU）来达成并发**。

## 10.2 可分割的数据结构（Partitionable Data Structures）

### 10.2.1 哈希表的设计（Hash-Table Design）

**原文骨架**：固定大小哈希表是**完全可分区**的数据结构——每个桶（bucket）有独立的锁，不同桶的操作完全并行 。

**设计要点**：

- 哈希函数将 key 映射到桶索引
    
- 每个桶维护一个链表（或其他冲突解决结构）
    
- 每个桶有独立的 `spinlock_t` 保护
    
- 查找/插入/删除首先定位桶，然后获取该桶的锁
    

**第一性解读**：

这是第 6.3.3 节"数据锁"思想在哈希表上的直接应用——**把全局锁拆分为 N 个桶锁**。理想情况下（哈希函数均匀、key 分布均匀），不同线程操作不同桶的概率极高，锁争用接近于零。

**🎯 关键认知**：桶锁哈希表的可扩展性上限由**桶数**决定。桶数越多，锁争用越低，但每个桶的链表越长，查找时间越长。**桶数与链表长度是零和博弈**——这是哈希表设计的核心权衡。

### 10.2.2 哈希表的实现（Hash-Table Implementation）

**原文骨架**：Paul 给出了基于每桶锁的哈希表实现 ：

```
struct hash_bucket {
    spinlock_t lock;
    struct ht_elem *head;
};

struct hash_table {
    unsigned long nbuckets;
    struct hash_bucket *buckets;
};

// 查找：定位桶 → 获取桶锁 → 遍历链表 → 释放锁
struct ht_elem* hash_search(struct hash_table *ht, void *key) {
    long b = hash(ht, key);
    spin_lock(&ht->buckets[b].lock);
    // 遍历 ht->buckets[b].head 链表
    spin_unlock(&ht->buckets[b].lock);
    return elem;
}
```

**第一性解读**：

实现的核心特征：

1. **桶锁保护**：每个桶独立加锁，不同桶的操作并行
    
2. **查找路径短**：哈希计算 + 一次加锁 + 链表遍历
    
3. **插入/删除**：同样按桶加锁，修改链表
    

**工业映射**：

- **Java `ConcurrentHashMap`（JDK 7 及之前）**：分段锁（Segment Lock）——把哈希表分成 16 个 Segment，每个 Segment 是一把桶锁
    
- **Java `ConcurrentHashMap`（JDK 8+）**：进一步优化——桶头节点用 `synchronized`，链表转红黑树时用 `synchronized` + CAS，实质上仍是"数据锁"思想
    
- **Linux 内核 `hlist`**：`include/linux/list.h` 中的哈希链表实现，配合每桶锁使用
    
- **futex 哈希表**：早期 Linux 内核 futex 哈希表只有 256 个桶，缺乏 NUMA 感知，导致大系统上严重冲突和伪共享。后来的补丁将其扩展到 `256 * ncpus`，并利用 `alloc_large_system_hash()` 实现 NUMA 感知分配 ——这是工业界对"桶数不足 + 伪共享"问题的经典修复
    

### 10.2.3 哈希表的性能（Hash-Table Performance）

**原文骨架**：Paul 给出了每桶锁哈希表在不同 CPU 数下的性能数据 。

**第一性解读**：

性能曲线的关键特征：

- **低 CPU 数**：每桶锁哈希表表现优异——几乎线性加速
    
- **高 CPU 数**：性能趋于平缓——桶锁的争用开始显现
    
- **桶数固定时**：随着 CPU 数增加，多个 CPU 竞争同一个桶锁的概率上升
    

**🎯 第一性洞见**：每桶锁哈希表的可扩展性受限于**桶数**。当 `CPU数 >> 桶数` 时，桶锁成为瓶颈。解决方案只有两个：

1. **增加桶数**（但固定大小哈希表无法动态扩容）
    
2. **消除桶锁**（用 RCU 让读者无锁）
    

**工业洞见**：

- **桶数选择**：工业实践中，桶数通常设为 `2 * CPU数` 或 `4 * CPU数`，以平衡锁争用和内存占用
    
- **NUMA 感知分配**：Linux 内核的 `alloc_large_system_hash()` 会将哈希表分布到各个 NUMA 节点，避免所有桶集中在单一节点的内存上 ——这是哈希表在 NUMA 系统上的关键优化
    
- **自适应哈希表缩放**：Linux 内核后来引入 `HASH_ADAPT` 标志，让 dcache 和 inode 哈希表在大内存机器上以更慢的节奏增长（内存每翻 4 倍，哈希表仅翻倍而非翻 4 倍）——避免大内存机器上哈希表占用过多内存

## 10.3 读侧重的数据结构（Read-Mostly Data Structures）

### 10.3.1 受 RCU 保护的哈希表的实现（RCU-Protected Hash Table Implementation）

**原文骨架**：在每桶锁哈希表基础上引入 RCU——**读者侧完全无锁**，写者侧仍按桶加锁但配合 RCU 宽限期回收 。

**核心模式**：

```
// 读者侧（零开销）
void hash_search_rcu(struct hash_table *ht, void *key) {
    rcu_read_lock();
    long b = hash(ht, key);
    // 通过 rcu_dereference() 安全遍历桶链表
    hlist_for_each_entry_rcu(elem, &ht->buckets[b].head, hte_next) {
        if (cmp(elem, key)) break;
    }
    rcu_read_unlock();
    return elem;
}

// 写者侧（按桶加锁 + RCU 延后回收）
void hash_delete_rcu(struct hash_table *ht, struct ht_elem *elem, long b) {
    spin_lock(&ht->buckets[b].lock);
    hlist_del_rcu(&elem->hte_next);  // RCU 安全删除
    spin_unlock(&ht->buckets[b].lock);
    // 宽限期后安全释放
    call_rcu(&elem->rcu_head, safe_free);
    // 或使用 synchronize_rcu() 同步等待
}
```

**第一性解读**：

RCU 保护的哈希表**保留了每桶锁**，但桶锁的作用范围被大幅缩小：

- **读者**：完全绕过桶锁，通过 RCU 机制安全遍历
    
- **写者**：仍需获取桶锁以保护链表修改，但**删除的元素通过 `call_rcu()` / `synchronize_rcu()` 延后释放**
    

**🎯 第一性洞见**：RCU + 每桶锁的组合是**"读者极致优化"与"写者合理开销"的平衡**：

- 读者路径：零锁、零原子操作、仅禁用抢占（非抢占内核中开销为零）
    
- 写者路径：桶锁 + 宽限期等待，但写者之间仍需桶锁互斥
    

这是为什么 RCU 保护的哈希表在**读多写少**场景下表现极其优异——读者的开销被压到了物理极限。

### 10.3.2 受 RCU 保护的哈希表的性能（RCU-Protected Hash Table Performance）

**原文骨架**：Paul 给出的性能数据显示——**RCU 保护的哈希表在相同 CPU 数下，查找吞吐量比每桶锁哈希表高出一个数量级以上**​ 。

**第一性解读**：

性能跃升的根本原因：

- 每桶锁哈希表的读者必须获取桶锁（即使是读也要加锁）
    
- RCU 哈希表的读者完全无锁——零 Cache 一致性流量、零原子操作
    

**工业映射**：

- **Linux 内核 dcache**：目录项缓存使用 RCU 保护，查找路径（`rcu-walk` 模式）完全无锁
    
- **Linux 内核 inode 哈希表**：同样使用 RCU
    
- **Josh Triplett 等人的 USENIX ATC'11 论文**​ 证明：可扩展 RCU 哈希表的查找扩展性比读写锁**提升 125 倍**，比当时的 Linux 最佳实践提升 56%，且 resize 期间查找性能无退化
    

### 10.3.3 对受 RCU 保护的哈希表的讨论（RCU-Protected Hash Table Discussion）

**原文骨架**：Paul 总结了 RCU 哈希表的优势与局限 ：

**优势**：

- 读者零开销
    
- 查找可线性扩展
    
- 与每桶锁结合，写者间仍保持合理的并发度
    

**局限**：

- **固定大小**：桶数固定，无法动态扩容——当元素数量增长时，链表变长，查找性能退化
    
- **写者仍需桶锁**：高频更新场景下，桶锁仍可能成为瓶颈
    
- **内存占用**：RCU 宽限期内的多版本共存导致内存无界（除非节流更新）
    

**🎯 第一性洞见**：RCU 保护的固定大小哈希表是"读多写少 + 元素数量相对稳定"场景的最优解。但当元素数量动态变化时，固定大小成为硬约束——这就引出了 10.4 节的"可扩展哈希表"。

## 10.4 不可分割的数据结构（Non-Partitionable Data Structures）

> ⚠️ **结构说明**：你目录中的"不可分割的数据结构"对应原书英文版的"Non-Partitionable Data Structures" 。但 Paul 在书中明确指出——**可调整大小的哈希表并非完全不可分割，而是"部分可分区"**：查找、插入、删除可以按桶分区，但 resize 操作需要全局协调 。这一节的核心正是：**如何让"不可分区"的 resize 操作与"可分区"的常规操作并发执行**。

### 10.4.1 可扩展哈希表的设计（Resizable Hash Table Design）

**原文骨架**：Paul 给出了三种可扩展 RCU 哈希表的设计思路，第一种（也是书中实现的一种）基于 **Herbert Xu 的双指针集（pointer-pair）方案**​ ：

**核心思想**：

- **每个数据元素维护两套链表指针**（`hte_next[0]` 和 `hte_next[1]`）——一套供当前哈希表使用，另一套供 resize 过程中的新哈希表使用
    
- **哈希表结构 `ht` 增加一个间接层**——`ht_cur` 指针指向当前活动的哈希表
    
- **Resize 操作**：
    
    1. 分配新哈希表（更大或更小）
        
    2. 设置 `htp->ht_new = htp_new`
        
    3. `synchronize_rcu()` 等待宽限期
        
    4. 遍历旧表每个桶，将元素通过**第二套指针**链接到新表的对应桶
        
    5. `rcu_assign_pointer(htp_master->ht_cur, htp_new)` 发布新表
        
    6. 再次 `synchronize_rcu()` 后释放旧表
        
    

**第一性解读**：

双指针集方案的精妙之处在于——**查找、插入、删除可以与 resize 完全并发**：

- 读者通过 `ht_cur` 访问当前表，使用 `hte_next[ht_idx]` 指针集遍历
    
- Resize 线程使用另一套指针集 `hte_next[!ht_idx]` 构建新表
    
- 两套指针集互不干扰，读者始终看到一致的数据
    

**🎯 第一性洞见**：双指针集是"多版本共存"思想在数据结构层面的极致体现——**不是维护数据的多个版本，而是维护"链接关系的多个版本"**。这允许 resize 在不阻塞任何其他操作的情况下，渐进式地将数据迁移到新表。

**其他两种可扩展哈希表方案**​ ：

1. **Josh Triplett 的指针解压缩（pointer-unzip）方案**：内存占用更小，但 resize 需要等待多个 RCU 宽限期，resize 本身较慢
    
2. **Mathieu Desnoyers 的 RCU 化 split-ordered list**：所有操作都是无阻塞（non-blocking）的，对过载系统友好，但实现复杂
    

### 10.4.2 可扩展哈希表的实现（Resizable Hash Table Implementation）

**原文骨架**：Paul 在 `hash_resize.c` 中给出了完整实现，核心 resize 函数逻辑如下 ：

```
int hashtab_resize(struct hashtab *htp_master, unsigned long nbuckets, ...) {
    // 1. 尝试获取全局 resize 锁（非阻塞，避免与更新者长时间互斥）
    if (!spin_trylock(&htp_master->ht_lock))
        return -EBUSY;
    
    // 2. 分配新哈希表
    htp = htp_master->ht_cur;
    htp_new = ht_alloc(nbuckets, ...);
    
    // 3. 关联新表到旧表，发布"resize 进行中"信号
    htp->ht_new = htp_new;
    synchronize_rcu();  // 等待宽限期，确保所有读者看到 ht_new
    
    // 4. 渐进式迁移：遍历旧表每个桶
    htp_new->ht_idx = !htp->ht_idx;  // 切换指针集
    for (i = 0; i < htp->ht_nbuckets; i++) {
        htbp = &htp->ht_bkt[i];
        spin_lock(&htbp->htb_lock);
        htp->ht_resize_cur = i;
        
        // 将该桶所有元素通过另一套指针链入新表
        cds_list_for_each_entry(htep, &htbp->htb_head, hte_next[idx]) {
            htbp_new = ht_get_bucket_single(htp_new, htp_new->ht_getkey(htep), &b);
            spin_lock(&htbp_new->htb_lock);
            cds_list_add_rcu(&htep->hte_next[!idx], &htbp_new->htb_head);
            spin_unlock(&htbp_new->htb_lock);
        }
        spin_unlock(&htbp->htb_lock);
    }
    
    // 5. 发布新表
    rcu_assign_pointer(htp_master->ht_cur, htp_new);
    synchronize_rcu();
    
    // 6. 释放旧表
    spin_unlock(&htp_master->ht_lock);
    free(htp);
    return 0;
}
```

**第一性解读**：

实现的关键工程细节：

1. **`spin_trylock` 而非 `spin_lock`**：resize 线程不阻塞等待——如果其他线程正在 resize，直接返回 `-EBUSY`。这避免了 resize 操作之间的相互阻塞。
    
2. **两次 `synchronize_rcu()`**：
    
    - 第一次：确保所有读者看到 `ht_new` 指针，开始使用新指针集
        
    - 第二次：确保所有"在 resize 开始前进入临界区"的读者已完成，可以安全释放旧表
        
    
3. **桶级渐进迁移**：resize 线程逐个桶迁移，每迁移一个桶就释放该桶的锁——**这意味着更新者只会被阻塞"一个桶的迁移时间"**，而非整个 resize 过程 。
    
4. **双指针集切换**：`ht_idx` 在 0 和 1 之间切换，决定当前使用哪套指针。读者通过 `rcu_dereference(htp_master->ht_cur)` 获取当前表，再用 `hte_next[htp->ht_idx]` 遍历。
    

**Paul 在 2019 年的简化**​ ：后续 Paul 进一步简化了 `hashtab_lookup()`——因为 resize 期间旧表保持不变，且读者在 RCU 读侧临界区内（防止第二个 resize 开始），所以查找**只需在旧表中搜索**，无需检查 resize 状态。这提升了常见路径（无 resize）的性能。

**🎯 第一性洞见**：可扩展 RCU 哈希表的实现揭示了并行数据结构设计的一个核心真理——**"不可分割"的操作可以通过"分解为多个可并发的步骤 + 多版本共存"来实现并发**。resize 看似是全局操作，但通过双指针集和渐进式迁移，它被分解为了"可与查找/插入/删除并发的细粒度步骤"。

### 10.4.3 可扩展哈希表的讨论（Resizable Hash Table Discussion）

**原文骨架**：Paul 给出了可扩展哈希表与固定大小哈希表的性能对比 。

**核心性能发现**：

1. **短链表场景**（2048 元素）：resize 开销主导——因为正常查找开销极低，resize 的缓存未命中成本显得突出。**1 毫秒的 resize 间隔太短**，resize 开销侵蚀了性能。
    
2. **中等链表场景**（16384 元素）：可扩展哈希表与过小固定哈希表的性能差异很小——因为链表变长后，查找开销本身成为主导，resize 开销相对不重要。
    
3. **长链表场景**（131072 元素）：所有方案性能都比 2048 元素场景差一个数量级以上——**最佳策略是一次性大幅扩容（如 64 倍）**，而非渐进式小幅扩容。
    

**🎯 第一性洞见（这是 10.4 全节最关键的工程启示）**：

> **哈希表 resize 的策略应该是"大幅扩容 + 迟滞（hysteresis）防止频繁 resize"。**​ 具体原则：
> 
> - **扩容时激进**：内存充足环境下，哈希表大小应该"大幅增加"而非小幅调整
>     
> - **缩容时保守**：内存充足环境下，哈希表大小的增加应该远比减少更激进
>     
> - **迟滞防抖**：避免在小幅度波动时频繁触发 resize，否则 resize 的开销会侵蚀掉哈希表本身的性能优势
>     

**工业洞见**：

- **Linux 内核 dcache 自适应哈希表**：`HASH_ADAPT` 标志让哈希表在大内存机器上以亚线性节奏增长 ——正是"激进扩容 + 亚线性缩放"思想的体现
    
- **Josh Triplett 等人的内核实现**​ ：可扩展 RCU 哈希表已在 Linux 内核中实现和测试，查找可 wait-free、线性可扩展，resize 期间查找性能无退化
    

### 10.4.4 其他可扩展的哈希表（Other Resizable Hash Tables）

**原文骨架**：Paul 讨论了双指针集方案的替代品 ：

**三种方案的权衡**：

|方案|内存开销|Resize 速度|并发度|实现复杂度|
|---|---|---|---|---|
|**双指针集（pointer-pair）**​|高（每元素两套指针）|快|高|简单|
|**指针解压缩（pointer-unzip）**​|低（单套指针）|慢（需多宽限期）|高|中等|
|**RCU 化 split-ordered list**​|低|中等|**无阻塞**​|复杂|

**🎯 第一性洞见**：这三种方案再次印证了第 2 章的"铁三角"——**内存开销、resize 速度、实现复杂度不可兼得**。双指针集用内存换简单性和速度；pointer-unzip 用 resize 速度换内存；split-ordered list 用实现复杂度换无阻塞特性。

**工业映射**：

- **内存敏感场景**：选择 pointer-unzip 或 split-ordered list
    
- **性能敏感场景**：选择双指针集
    
- **云环境过载机器**：split-ordered list 的无阻塞特性至关重要

## 10.5 其他数据结构（Other Data Structures）

**原文骨架**：Paul 简要讨论了其他并行数据结构的设计原则。

**我的洞见（基于全章脉络）**：

哈希表是"读多写少 + 可分区"的完美载体，但其他数据结构有不同的特征：

|数据结构|主要并行化策略|工业实现|
|---|---|---|
|**链表**​|RCU 保护遍历 + 每节点锁保护修改|Linux 内核 `hlist` + RCU|
|**树（平衡树/B+树）**​|层次锁（内部节点粗粒度、叶子节点细粒度）+ RCU|Linux 内核 radix tree/xarray|
|**队列**​|每生产者/每消费者私有队列 + 偶尔共享|DPDK ring、Disruptor|
|**Skip List**​|RCU 保护 + 细粒度锁|部分 KV 存储|
|**基数树（Radix Tree）**​|RCU + 层次锁|Linux 内核 page cache 索引|

**🎯 核心原则**：无论哪种数据结构，设计哲学都是一致的——

1. **先分割**（数据所有权/分区）
    
2. **再选择延后处理机制**（RCU 用于读多写少、危险指针用于内存敏感、引用计数用于通用生命周期）
    
3. **最后考虑锁**（仅用于写者间的互斥）

## 10.6 微优化（Micro-Optimization）

这一节 Paul 讨论了并行数据结构的底层优化技巧——这些技巧看似微小，但在高性能路径上积累起来就是数量级的差异。

### 10.6.1 实例化（Specialization）

**原文骨架**：针对特定访问模式定制数据结构，而非使用通用数据结构。

**第一性洞见**：第 2 章 YAGNI 原则的具体落地——**通用性是一把双刃剑**。一个"通用哈希表"为了处理所有情况，必然在每种具体情况上都次优。针对特定访问模式（key 类型、哈希函数、读写比、元素数量级）定制的哈希表，往往能比通用哈希表快数倍。

**工业洞见**：

- **Google 的 `dense_hash_map`**：针对"小 key、已知 value 类型"优化的哈希表，比 `std::unordered_map` 快数倍
    
- **Facebook 的 `folly::F14`**：针对现代 CPU 缓存特性优化的哈希表
    
- **我的判断**：今天写 C++ 高性能服务的工程师，**不应该默认使用 `std::unordered_map`**——它在工业基准测试中 consistently 表现不佳。应选择 `folly::F14`、`google::dense_hash_map`、或 `tsl::hopscotch_map` 等现代替代品。
    

### 10.6.2 比特与字节（Bits and Bytes）

**原文骨架**：在数据结构布局上精打细算——字节对齐、位域、紧凑布局。

**关键优化**：

- **Cache Line 对齐**：热点数据与锁分配到不同 Cache Line，避免伪共享（呼应第 3 章）
    
- **位域压缩**：将多个布尔/小整数状态压缩到一个机器字中
    
- **指针压缩**：64 位系统中，如果虚拟地址空间有限，可用 32 位偏移替代 64 位指针
    

**工业洞见**：

- **Java `@Contended`**：JVM 提供的 Cache Line 对齐注解，消除伪共享
    
- **C++ `alignas(64)`**：Cache Line 对齐
    
- **Linux `__cacheline_aligned`**：内核宏
    

### 10.6.3 硬件层面的考虑（Hardware Considerations）

**原文骨架**：数据结构设计必须顺应硬件习性（呼应第 3 章）。

**关键考量**：

- **NUMA 感知**：内存分配应考虑 NUMA 节点亲和性
    
- **Cache 局部性**：数据布局应优化空间局部性
    
- **Prefetching**：对规律性访问模式，硬件/软件预取能隐藏内存延迟
    
- **SIMD 友好**：数据布局应支持向量化访问
    

**工业映射**：

- **Linux `alloc_large_system_hash()`**：NUMA 感知的大哈希表分配器 ——这是内核工业实践中"硬件层面考虑"的典范
    
- **futex 哈希表优化补丁**​ ：将 256 个固定桶扩展到 `256 * ncpus`，并利用 `alloc_large_system_hash()` 实现 NUMA 感知分配，解决了大系统上的冲突和伪共享问题
    
- **我的判断**：今天设计高性能并行数据结构时，**NUMA 亲和性是必须考虑的因素**。在 128 核双路服务器上，一个"所有桶集中在 Node 0 内存"的哈希表，其跨节点访问延迟会彻底摧毁性能。正确的做法是用 `numactl` 或 `libnuma` 将桶分布到各节点的本地内存。

## 10.7 总结（Summary）

**Paul 的全章收束**：

1. **分割是第一步**：per-bucket lock 的哈希表在单 socket 上表现优异，是并发编程的基础工具。
    
2. **RCU 是读侧重场景的利器**：当数据结构读多写少时，RCU + 每桶锁的组合能让读者零开销，性能提升数量级。
    
3. **可扩展 RCU 哈希表突破了"固定大小"的限制**：通过双指针集 + 渐进式迁移，resize 可以与查找/插入/删除完全并发。
    
4. **resize 策略至关重要**：大幅扩容 + 迟滞防抖，避免频繁 resize 侵蚀性能。
    
5. **微优化决定最后一公里**：实例化、比特/字节布局、硬件层面考量（NUMA/Cache/Prefetching），这些"微小"优化在高性能路径上积累出数量级差异。

## 本章总览：贯穿全章的第一性原理总结

读完第 10 章，我认为 Paul 真正想建立的认知框架可以压缩为**三句话**：

1. **并行数据结构的设计本质是"分割 + 延后处理"的组合艺术**。从每桶锁（纯分割）到 RCU + 每桶锁（分割 + 延后回收）到可扩展 RCU 哈希表（分割 + 多版本共存 + 渐进式协调），每一步演进都在用更精巧的机制把"读者的性能"与"写者/resize 的成本"进一步解耦。
    
2. **"不可分割"的操作可以通过"分解为可并发步骤 + 多版本共存"来实现并发**。可扩展哈希表的双指针集方案是这一思想的最高体现——resize 看似全局不可分割，但通过维护两套指针集和渐进式迁移，它被分解成了与查找/插入/删除完全并发的细粒度步骤。
    
3. **没有"最佳"并行数据结构，只有"最匹配访问模式"的数据结构**。固定大小 RCU 哈希表适合"元素数量稳定"的场景；可扩展 RCU 哈希表适合"元素数量动态变化"的场景；双指针集、pointer-unzip、split-ordered list 在内存开销、resize 速度、无阻塞特性上各有权衡——选择取决于你的具体约束。
    

> 📌 **给工程师的个人判断（2026 年视角）**：
> 
> 第 10 章是全书**最具工业即战力**的章节。今天主流系统软件中的并行哈希表实现，几乎都能在 Paul 这一章里找到对应：
> 
> - **Linux 内核 dcache/inode 哈希表**：RCU 保护 + 每桶锁 + 自适应缩放（HASH_ADAPT）
>     
> - **Linux 内核 rhashtable**：可扩展 RCU 哈希表的工业级实现
>     
> - **Linux futex 哈希表**：`256 * ncpus` 桶数 + NUMA 感知分配
>     
> - **Java `ConcurrentHashMap`**：JDK 8+ 的 `synchronized` + CAS + 链表/红黑树
>     
> - **C++ `folly::F14`、`google::dense_hash_map`**：针对现代 CPU 优化的哈希表
>     
> - **Josh Triplett 等人的可扩展 RCU 哈希表**（USENIX ATC'11）：查找扩展性比读写锁提升 **125 倍**，比当时 Linux 最佳实践提升 **56%**，resize 期间查找性能无退化
>     
> 
> **我的核心建议**：
> 
> 1. **遇到"读多写少"的并行数据结构，第一选择是 RCU + 每桶锁**，而非传统的读写锁——这是 Linux 内核 20 年验证的最佳实践
>     
> 2. **需要动态扩缩容时，使用可扩展 RCU 哈希表**——双指针集方案简单且高性能，pointer-unzip/split-ordered list 在内存敏感/无阻塞需求时选用
>     
> 3. **resize 策略：大幅扩容 + 迟滞防抖**——避免频繁 resize 侵蚀性能，这是 Paul 通过性能数据得出的铁律
>

>     
> 6. **微优化决定最后一公里**：Cache Line 对齐消除伪共享、NUMA 亲和性避免跨节点访问、数据布局优化 Cache 局部性——这些"微小"优化积累出数量级差异
>     
> 
> Paul 在 2025 年 Kernel Recipes 演讲中强调的"先分割数据和选择复制"——第 10 章就是这一哲学在数据结构层面的完整落地。**哈希表从"每桶锁"到"RCU 保护"到"可扩展 RCU"的演进路径，展现了并行数据结构设计的完整光谱**：
> 
> **纯分割（每桶锁）→ 分割 + 延后处理（RCU 哈希表）→ 分割 + 多版本共存 + 渐进式协调（可扩展 RCU 哈希表）**
>

> 
> **分割数据 → 用 RCU/危险指针/引用计数管理生命周期 → 必要时用锁保护写者间互斥 → 微优化顺应硬件习性**
