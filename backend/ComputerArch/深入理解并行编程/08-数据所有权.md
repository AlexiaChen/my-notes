
# 第 8 章 数据所有权（Data Ownership）

> 这一章的开场白是 Paul 借《魔戒》咕噜姆的台词做出的戏仿："**It is mine, I tell you. My own. My precious.**"（它是我的，我告诉你。我自己的。我的宝贝。）
> 
> 这句玩笑背后是全书最深刻的一个设计哲学：**避免锁带来的同步开销的最简单方式之一，就是在线程（或 CPU）之间封装数据，以便让数据仅被一个线程访问或修改**​ 。Paul 更进一步指出，数据所有权其实是覆盖了"三大并行设计技术"的集大成者——它**分割了线程、它批处理了所有本地操作、它把"弱化同步"推向了逻辑极致（直接消除同步）**​ 。
> 
> 正因为如此，数据所有权被广泛且重度地使用，**它甚至是一种新手凭借本能也会使用的应用模式**​ 。但恰恰是这种"太简单"，让它成了**被严重低估的同步机制**​ ——它的简单性反而让它在业界的受尊重程度受损。这一章就是要为数据所有权"正名"，并系统化它的几种主要形态。

## 8.1 多进程（Multiple Processes）

**原文骨架**：回顾第 4.1 节的 shell 并行示例 ：

```
compute_it 1 > compute_it.1.out &
compute_it 2 > compute_it.2.out &
wait
cat compute_it.1.out
cat compute_it.2.out
```

两个 `compute_it` 实例作为**独立进程**并行运行，**不共享内存**。因此给定进程中的所有数据都由该进程拥有，**上述示例中的几乎全部数据都是被拥有的**​ 。这种方式**几乎完全消除了同步开销**​ 。

**第一性解读**：

多进程是数据所有权的**逻辑极致（logical extreme）**——每个线程（进程）拥有自己的私有地址空间 。在这种极端下：

- **零同步开销**：因为没有共享内存，所以不需要锁、不需要原子操作、不需要内存屏障
    
- **极致简单**：进程间自然隔离，程序员不需要任何并行编程技巧
    
- **最佳性能**：消除了所有 Cache 一致性流量、伪共享、锁争用
    

**Quick Quiz 8.2/8.3 的思考**​ ：

- _剩余什么同步？_ 进程间的同步仅剩"父进程 wait 子进程"这种极粗粒度的协调，以及通过文件/管道/Socket 的通信
    
- _有任何共享数据吗？_ 严格来说没有——即使通过文件通信，也是"写完后读"，而非"同时读写同一块内存"
    

**🎯 第一性洞见**：多进程模式揭示了数据所有权的本质力量——**当数据不被共享时，同步问题从根本上消失了**。这不是"用某种巧妙的锁协议解决了同步"，而是"重新定义了问题边界，让同步根本不必要"。

**工业洞见**：

- **Shell 并行 + GNU Parallel**：数据工程师最常用的"零成本并行"模式
    
- **Nginx/Apache 多 worker 进程**：每个 worker 独立处理请求，通过共享监听 socket + 内核负载均衡实现并行，几乎不需要应用层锁
    
- **MapReduce / Hadoop / Spark**：本质就是"多进程 + 消息传递"的分布式版——每个 task 是独立进程，通过 HDFS/Shuffle 传递数据
    
- **我的判断**：多进程是工业界"并行普惠化"的基石。今天 90% 的"高并发服务"本质上是多进程架构（Kubernetes 多 Pod、微服务多副本），而非真正的共享内存并行。

## 8.2 部分数据所有权和 pthread 线程库（Partial Data Ownership and pthreads）

**原文骨架**：第 5 章"计数"大量使用了数据所有权，但做了一个关键改变 ：

> **不允许线程修改其他线程拥有的数据，但允许线程读取这些数据。**

换言之，共享内存允许**更细粒度的所有权和访问权限概念**​ 。

**典型例子**：每线程统计计数器（第 5 章图 5.9）

```
// 每线程独立计数器，通过 __thread 或 per-CPU 数组实现
__thread unsigned long counter;

void inc_count(void) {
    counter++;  // 只写自己的副本，无锁
}

long read_count(void) {
    long sum = 0;
    for (each thread t) sum += counter[t];  // 读所有线程的副本
    return sum;
}
```

这里 `inc_count()` 只更新对应线程的 `counter` 实例，而 `read_count()` 访问（但不修改）所有线程的 `counter` 实例 。

**第一性解读**：

部分数据所有权是**"写所有权独占 + 读权限共享"**的优雅折中：

- **写路径**：完全无锁、无同步——每个线程只写自己的 Cache Line（通过 `aligned(CACHE_LINE_SIZE)` 避免伪共享）
    
- **读路径**：需要遍历所有线程的副本，读到的是"最终一致"的近似结果
    
- **零锁零原子零屏障**：`inc_count()` 的机器码就是一条普通的 `inc` 指令
    

**Quick Quiz 8.4 的思考**​ ：_是否存在"每个线程只读自己的 per-thread 变量实例，但写其他线程的实例"的部分所有权？_ —— Paul 抛出这个问题让读者思考"所有权不对称"的边界。实际上这种反向模式很少见，因为"写他人数据"打破了所有权的核心好处（消除同步）。

**纯数据所有权的补充**：第 6.4.3 节的**每线程内存分配器缓存**是纯数据所有权的典范——每个线程的缓存完全归该线程私有 。分配/释放都在本地缓存上进行，零同步开销；只有当本地缓存溢出/欠载时才回到全局分配器（此时才需要锁）。

**工业洞见**：

|部分所有权模式|工业实现|
|---|---|
|每线程统计计数器|Java `LongAdder`、Prometheus client 分片计数|
|每线程内存分配器缓存|glibc malloc 的 per-thread arena、jemalloc tcache、SLUB per-CPU|
|部分所有权 + pthreads|Thread-Local Storage (TLS)、`__thread`、`thread_local`|

> 💡 **我的洞见**：部分数据所有权是"共享内存并行编程中极难避免的一种所有权形式"——Quick Quiz 8.1 的答案正是如此 。只要你用 C/C++ 写 pthreads 程序，几乎必然会用到 per-thread 变量。这是为什么理解部分所有权至关重要：**它不是可选项，而是共享内存并行的默认范式**。

## 8.3 函数输送（Function Shipping）

**原文骨架**：前面几节描述了一种"弱形式的数据所有权"——线程**伸手**去访问其他线程的数据。这可以被认为是**把数据带到需要它的函数那里**。

**另一种替代方案是：把函数发送到数据所在的地方**​ 。

**典型例子**：第 5.4.3 节的 Signal-Theft 上限计数器

```
// flush_local_count_sig() 是信号处理函数，扮演"被输送的函数"
// pthread_kill() 在 flush_local_count() 中发送信号——即"输送函数"
// 然后等待被输送的函数执行完毕

void flush_local_count(void) {
    pthread_kill(tid, SIGUSR1);  // 输送函数到目标线程
    // 等待 flush_local_count_sig() 完成
    while (!signal_handled) { /* 等待 */ }
}

void flush_local_count_sig(int sig) {
    // 这个函数运行在"数据拥有者"的线程上下文中
    // 读取该线程的 thread_counter 并写回全局变量
    global_count += thread_counter;
    signal_handled = 1;
}
```

**第一性解读**：

函数输送的核心思想是**"把计算移到数据旁边，而非把数据移到计算旁边"**​ ：

- **数据拥有者线程**：独占访问自己的数据，无需任何同步
    
- **外部请求者**：不直接访问数据，而是通过信号/消息/"输送一个函数"到拥有者线程
    
- **拥有者线程执行该函数**：因为它本来就拥有数据，所以执行时无同步开销
    
- **代价**：引入了消息传递开销 + 需要处理并发交互（输送的函数可能与拥有者线程正在执行的 `add_count()`/`sub_count()` 并发）
    

**Quick Quiz 8.5 的思考**​ ：_除了 POSIX 信号，还有什么机制可用于函数输送？_ 答案是丰富的——**任何"让目标线程执行某段代码"的机制都可以**：

- 消息队列（Actor 模型）
    
- 管道（Pipe）+ 命令协议
    
- 异步任务队列（如 `boost::asio` 的 `post`）
    
- Remote Procedure Call (RPC)
    
- **Go 的 goroutine + channel**：把"要执行的函数"作为消息发送到拥有数据的 goroutine
    

**工业洞见**：

|函数输送机制|工业对应|
|---|---|
|POSIX 信号|Signal-Theft 计数器、部分内核机制|
|消息队列/Actor|Erlang Actor Model、Akka、Orleans|
|Channel|Go `chan func()`、Rust `crossbeam` 通道|
|任务队列|Tokio 的 `tokio::task`、`rayon::spawn`|
|RPC|gRPC、Thrift、Cap'n Proto|

> 🎯 **我的洞见**：函数输送是**"消息传递并发模型"的微观版**。Erlang "processes communicate only via message passing" 的哲学，本质就是函数输送的极致化——数据永远不被共享，所有跨进程操作都通过"发送消息（函数）到数据拥有者"完成。这也是为什么 Erlang 在并发正确性和可维护性上远超共享内存模型。

## 8.4 指派线程（Designated Thread）

**原文骨架**：前面几节描述了"允许每个线程保留自己的数据副本或部分副本"的方式。与之相对，**本节描述一种功能分解（functional decomposition）方法**——特定的**指派线程（designated thread）拥有完成其工作所需数据的权限**​ 。

**典型例子**：第 5.2.3 节的最终一致计数器

```
// eventual() 函数由一个指派线程运行
void eventual(void) {
    while (1) {
        sleep(interval);
        // 周期性地将每线程计数拉入全局计数器
        for (each thread t) {
            global_count += counter[t];
            counter[t] = 0;
        }
    }
}
```

`eventual()` 线程周期性地将每线程 counts 拉入全局计数器，使得对全局计数器的访问**最终收敛于实际值**​ 。

**Quick Quiz 8.6 的思考**​ ：_`eventual()` 函数中的数据实际上__没有被 `eventual()` 线程拥有__！这怎么能算数据所有权？_ —— Paul 的回答揭示了指派线程的本质：**这个线程拥有"执行汇聚操作的权利"**，而非拥有所有数据。它通过"拉取"动作获得临时访问权，完成汇聚后数据仍归原线程所有。

**第一性解读**：

指派线程是**"功能所有权"而非"数据所有权"**——它拥有的是"对特定数据的特定操作权"：

- **每个线程有明确角色**：I/O 线程拥有 I/O 数据结构、监控线程拥有统计结构、allocator 线程拥有内存池
    
- **跨角色访问通过通信**：需要访问其他角色数据时，通过消息/函数输送请求该角色的指派线程代为执行
    
- **典型模式**：
    
    - **Pipeline 阶段**：每个阶段有指定的 per-stage 线程
        
    - **生产者-消费者**：生产者线程拥有输出队列，消费者线程拥有输入队列
        
    - **监控线程**：拥有统计结构
        
    - **内存池分配器线程**：拥有全局内存池
        
    

**工业洞见**：

|指派线程模式|工业对应|
|---|---|
|I/O 子系统专用 I/O 线程|Redis 主线程事件循环、Node.js 事件循环|
|数据库式事务处理器|每个连接一个线程（Thread-per-Connection）|
|GUI 事件循环|主线程独占 UI 事件队列|
|网络包处理管道|DPDK 的每端口 RX/TX 线程|
|内存池专用分配器线程|jemalloc 的 arena 管理线程|

> 💡 **我的洞见**：指派线程是**现代高性能系统软件的隐性主干**。当你研究 Redis、Node.js、Nginx、Envoy、Tokio 等系统的架构时，会发现它们几乎都在用"指派线程 + 消息传递"的模式——**一个线程负责一件事，这事的数据就归它私有**。这种模式在 Paul 看来是数据所有权在函数维度的延伸，它兼具"零同步开销"和"清晰的职责分离"双重优势。

## 8.5 私有化（Privatization）

**原文骨架**：对于共享内存的并行程序，**一种提升性能和可扩展性的方式是将共享数据转换成由特定线程拥有的私有数据**​ 。

**经典例子**：用私有化解决哲学家就餐问题

原问题：5 个哲学家围圆桌，每两人间 1 支叉子（共 5 支），最多只允许 2 人同时就餐。

私有化方案：**给每个哲学家配备额外的 5 支叉子，使每个哲学家都有自己的私有成对叉子**。

结果：**所有 5 个哲学家可以同时就餐**，且提供了对特定类型疾病的传播大幅减少的额外好处 ——这个幽默的补充暗示了私有化不仅提升性能，还消除了"共享资源导致的隐性耦合"。

**第一性解读**：

私有化是一种**反向工具（reverse tool）**——当发现性能瓶颈在于某个共享数据结构时，考虑能否把它私有化（哪怕只是部分私有化），往往能得到意外的性能提升 。

**但私有化并非免费**，Paul 以简单上限计数器为例说明其代价 ：

- 原算法允许线程读取彼此的数据，但只允许更新自己的数据
    
- 跨线程访问仅存在于 `read_count()` 的求和循环中
    
- 如果消除这个循环 → 移动到更高效的纯数据所有权，但代价是 `read_count()` 返回的结果精确度降低
    

**Quick Quiz 8.7 的思考**​ ：_是否可能在保持每线程数据完全私有的同时，获得更高的精确度？_ ——答案是可行的，方法是引入更复杂的协调协议（如定期聚合、层次化聚合），但代价是实现复杂性。

**🎯 第一性洞见**：私有化揭示了并行设计中一个核心权衡——

> **共享数据的"精确度/一致性"与"私有化的性能收益"之间存在物理性的张力。**​ 完全私有化 = 零同步 + 零精确度保证；部分共享 = 有同步 + 有精确度。工程师的艺术在于找到这个张力的甜蜜点。

**工业洞见（GPU 计算的绝佳例证）**：

ScienceDirect 的研究表明，在 GPU 大规模并行系统中，**原子更新常常成为瓶颈**——即使更新均匀分布，由于 histogram 的 bin 数远少于 GPU 核心数，冲突不可避免。**典型解决方案是私有化**：为每个线程（或一小簇线程 warp）创建 histogram 的独立副本，线程间无冲突，最后再将各副本合并到全局副本 。

这就是 GPU 高性能计算的标准范式——**私有化是 GPU 并行效率的重要来源**​ 。

> 📌 **我的判断**：私有化是今天工业界最被低估的优化手段之一。许多工程师遇到共享数据结构瓶颈时，第一反应是"细化锁粒度"或"改用无锁结构"，却忽略了**最根本的解决方案——能否把这个数据结构私有化？**​ 如果可以，性能提升往往是数量级的，而非百分比。

## 8.6 数据所有权的其他用途（Other Uses for Data Ownership）

**原文骨架**：当数据可以被分割、跨线程访问或更新需求很少或没有时，数据所有权最为有效。幸运的是，**这种情况很常见，并且在各种并行编程环境中广泛存在**​ 。

**Paul 列举的环境**​ ：

|环境|数据所有权形态|
|---|---|
|**MPI**​|消息传递环境中的自然所有权|
|**MapReduce**​|每个 map/reduce task 拥有独立数据分片|
|**Shared-Nothing 数据库**​|每个节点拥有独立数据分区|
|**客户端-服务器 / RPC / Web 服务**​|每个连接/会话拥有独立上下文|
|**Erlang**​|语言层面强制数据所有权，消息传递是唯一通信方式|
|**GPGPU 计算**​|每个 GPU 线程处理数据的一个独立分区，同步开销接近零|
|**Fork-Join**​|独立进程地址空间|
|**C 语言栈上的 auto 变量**​|每个线程/函数调用拥有独立副本|
|**并行线性代数**​|数据按矩阵块分区|
|**网络内核（IX OS）**​|每连接一个线程，大多数操作无需跨线程同步|

**第一性解读**：

这一节揭示了数据所有权的**普适性**——它不仅是共享内存并行的一种技巧，更是**几乎所有并行编程环境的底层范式**：

- **从语言层**：Erlang 从语法层面强制数据所有权
    
- **从系统层**：MPI、MapReduce、Shared-Nothing DB 都是数据所有权的分布式版
    
- **从硬件层**：GPU 的每个线程处理独立数据分区，是数据所有权在 SIMT 模型上的极致体现
    
- **从应用层**：Web 服务的每连接一线程、每请求一上下文，本质都是数据所有权
    

**DeepWiki 的精炼总结**​ ：

> 数据所有权模式在以下场景最有效：
> 
> - 数据自然分割（如哈希表按桶）
>     
> - 每线程状态（如统计计数器）
>     
> - 生产者-消费者模式（如工作队列）
>     
> - 流水线架构（如网络协议栈）
>     

**🎯 第一性洞见**：数据所有权是**并行编程的"第一性原理"级别的设计模式**。它不是"众多同步技巧之一"，而是"让同步根本不必要"的终极手段。所有其他同步机制（锁、原子操作、RCU、无锁结构）都是"在无法使用数据所有权时的次优解"。

> 💡 **我的判断**：这一节是全书最具"哲学高度"的一节。Paul 在暗示——**如果你发现自己在使用复杂的锁协议或无锁结构，第一反应应该是问："能不能用数据所有权避免这个问题？"**​ 如果能，你获得的不仅是更好的性能，更是更简单的代码、更少的正确性问题、更强的可扩展性。数据所有权常常被低估，**恰恰是因为它太简单**​ 。

## 本章总览：贯穿全章的第一性原理总结

读完第 8 章，我认为 Paul 真正想建立的认知框架可以压缩为**三句话**：

1. **数据所有权是"消除同步"而非"管理同步"的极致手段。**​ 锁、原子操作、RCU 都是在"共享数据"的前提下做同步管理；而数据所有权通过"分割数据到独占所有者"，从根本上消除了同步的必要。这是为什么它被重度使用，甚至是新手本能使用的模式 。
    
2. **数据所有权有四个主要形态，构成从"完全隔离"到"精细权限"的光谱**​ ：
    
    |形态|数据位置|跨线程访问|同步需求|
    |---|---|---|---|
    |**多进程**​|各自地址空间|无|几乎零|
    |**完全数据所有权**​|共享内存|无|零|
    |**部分数据所有权**​|共享内存|只读|轻量|
    |**函数输送**​|共享内存|通过消息|消息传递开销|
    |**指派线程**​|共享内存|通过指定线程|消息传递开销|
    
3. **数据所有权常被低估，恰恰是因为它太简单**​ 。但它的三大优势——**简洁（无锁/无原子/无屏障）、性能（无同步开销，缓存局部性好）、可扩展性（随 CPU/线程数线性扩展）**——让它成为并行设计的第一选择。
    

> 📌 **给工程师的个人判断（2026 年视角）**：
> 
> 第 8 章是全书**最具"工程即战力"的章节之一**，但也是最被忽视的——因为工程师们往往被"锁、原子操作、无锁结构、RCU"这些"看起来很酷"的机制吸引，而忽略了"数据所有权"这种"看起来太平凡"的机制。
> 
> 今天主流的高性能系统的核心架构决策，几乎都能在数据所有权的光谱上找到对应：
> 
> - **多进程**：Kubernetes Pod、微服务多副本、Nginx 多 worker
>     
> - **完全数据所有权**：per-CPU 变量、Thread-Local Storage、GPU 每线程私有数据
>     
> - **部分数据所有权**：Java `LongAdder`、每线程内存分配器缓存（tcmalloc/jemalloc/SLUB）
>     
> - **函数输送**：Erlang Actor Model、Go channel、Tokio task、gRPC
>     
> - **指派线程**：Redis 单线程事件循环、Node.js 事件循环、DPDK 每端口线程、IX OS 每连接线程
>     
> - **私有化**：GPU histogram 私有化、MapReduce 数据本地化、Shared-Nothing 数据库分片
>     
> 
> **我的核心建议**：
> 
> 1. **遇到并行设计问题时，第一问永远是"这段数据真的需要跨线程共享吗？"**​ —— 这是 Paul 在 2025 年 Kernel Recipes 演讲中强调的"先分割数据和选择复制"的具体落地
>     
> 2. **如果不需要共享 → 数据所有权，零同步**​
>     
> 3. **如果偶尔需要读 → 部分所有权，轻量同步**​
>     
> 4. **如果需要跨线程操作 → 函数输送或指派线程**​
>     
> 5. **如果必须全局共享 → 才考虑锁、RCU 等机制**（第 7、9、10 章的主题）
>     
> 6. **当发现性能瓶颈时，考虑能否私有化**​ —— 这是反向工具，但效果常超预期
>     
> 
> 数据所有权是并行编程的"第一性原理"级别的设计模式。当你掌握了它，你会发现**大多数"并行难"的问题，本质都是"不必要的数据共享"制造的假问题**。消除不必要的共享，你就消除了 90% 的并行难题。
> 
> 这也解释了为什么 Paul 把数据所有权放在"锁"之后、"延迟处理（RCU）"之前——**数据所有权是锁的"大哥"**（更简单、更高效、更可扩展），而 RCU 是数据所有权在"时间维度"的延伸（第 9 章会讲"安全地将公共数据结构临时私有化"就是 RCU 的思想）。理解了这个递进关系，你就理解了全书的设计哲学：
> 
> **数据所有权（空间维度的分割）→ RCU（时间维度的分割）→ 锁（最后的兜底）**
> 
> 这个顺序不可颠倒。很多工程师一上来就用锁，是颠倒了这个顺序——他们本可以先用数据所有权消除 90% 的同步需求，剩下的 10% 用 RCU，最后实在无法分割的 1% 才用锁。
