## 13.1 计数难题（Counter Conundrums）

这一节 Paul 用第 5 章（计数）+ 第 7 章（锁）+ 第 9 章（RCU/引用计数）的工具箱，解决两个具体的计数难题——**对更新进行计数**和**对查找进行计数**。这两个问题看似相似，但最优解完全不同，揭示了并行计数设计的核心第一性原理。

### 13.1.1 对更新进行计数（Counting Updates）

**原文骨架**：假设 Schrödinger（第 10 章运行示例的主人公）想要统计每只动物的**更新次数**，且这些更新已经被**每数据元素锁（per-data-element lock）**保护 。

**🎯 第一性洞见：最优解是"反直觉的简单"**​

Paul 的答案令人意外地简单 ：

> **"Just place a counter in each data element, and increment it under the protection of that element's lock!"**
> 
> （只需在每个数据元素内部放置一个计数器，并在持有该元素锁时递增它！）

**为什么这是最优解？**​ 三个深层原因：

1. **锁已经提供了内存序和原子性保证**：每数据元素锁的持有者已经独占了该数据元素，因此在锁内递增计数器**不需要任何额外的原子操作或内存屏障**——锁的获取/释放已经隐式地提供了所需的顺序保证。
    
2. **零额外同步开销**：计数器与数据元素共存于同一缓存行（如果布局得当），递增计数器就是一条普通的 `inc` 指令，无原子 RMW、无 Cache 一致性流量。
    
3. **读者无锁访问**：如果读者需要无锁读取该计数器，更新者应使用 `WRITE_ONCE()`，读者应使用 `READ_ONCE()`，以防止编译器优化导致的数据竞争 。
    

**工业映射**：

- **Linux 内核 `struct inode` 中的 `i_count`**：虽然 `i_count` 是引用计数（语义不同），但"在锁内递增统计计数器"的模式在内核中无处不在——如 `dcache` 中每个 `dentry` 的访问计数，在 `d_lock` 保护下递增。
    
- **Java 并发类中的 `stamp` 字段**：`StampedLock` 在写锁保护下递增 stamp 字段，模式完全相同。
    
- **我的判断**：今天写业务代码的工程师，遇到"统计某对象的操作次数"时，**第一反应应该不是"用 `AtomicLong`"**，而是"这个对象是否已经被某把锁保护？如果是，直接在锁内用普通 `long` 递增"。这是 Paul 这一节最重要的工程启示——**不要盲目使用原子操作，先看是否已经有锁提供了所需的保证**。
    

### 13.1.2 对查找进行计数（Counting Lookups）

**原文骨架**：现在 Schrödinger 还想统计每只动物的**查找次数**，但**查找是由 RCU 保护的**​ 。这是比"更新计数"难得多的问题。

**为什么难？**​ 三个核心挑战：

1. **RCU 查找路径必须保持无锁**：如果在 RCU 读侧临界区内获取每元素锁来递增计数器，会**破坏 RCU 的可扩展性优势**​ ——大系统上所有查找线程竞争同一把锁，RCU 的读者零开销优势荡然无存。
    
2. **不能使用简单的全局原子计数器**：第 5 章已经证明，全局原子计数器在多核上是可扩展性杀手（Cache Line 弹跳）。
    
3. **内存占用约束**：使用第 5 章的统计计数器（每线程/每 CPU 分片），**所需计数器数量 = 数据元素数 × 线程数**​ ——对于百万级数据元素 × 百级线程，内存开销不可接受。
    

**Paul 给出的四级方案阶梯**​ ：

**方案零：Just Say No（完全不计数）**

> 如果可能，完全避免计数——效仿 Linux 的 `noatime` 挂载选项（不更新文件访问时间）。
> 
> **这是最优方案**：毕竟，"什么都不做"比任何方案都快 。在业务语义允许的情况下，不计数就是最佳计数。

**方案一级：每数据元素统计计数器**

沿用第 5 章的统计计数器思想，但**每个数据元素维护自己的 per-CPU/per-thread 计数器阵列**。

**代价**：内存开销 = 数据元素数 × CPU 数。对于百万级元素 × 64 CPU，需要 **6400 万个计数器**——内存爆炸。

**方案二级：每 Socket 计数器（而非每 CPU）**

> 如果内存开销过度，可以保留 per-socket 计数器而非 per-CPU 计数器，同时关注哈希表性能 。

**🎯 第一性洞见**：这是第 5 章"统计计数器"思想与第 3 章"NUMA/硬件体系结构"的结合——**在 NUMA 系统中，per-CPU 计数器可能导致跨节点访问**。改为 per-socket 计数器，虽然精度略降（同一 socket 内多 CPU 共享一个计数器），但内存开销降为 1/CPU数-per-socket，且消除了跨节点访问。

**方案三级：RCU 友好计数器**

结合 RCU 的发布-订阅机制，让读者通过 `rcu_dereference()` 安全读取计数器快照，写者通过 `WRITE_ONCE()` 更新，避免数据竞争。

**我的洞见**：13.1.2 节揭示了并行计数设计的**核心第一性原理**——

> **计数的最优方案不是"选哪种计数器"，而是"能否根本不计数"。如果必须计数，则按"内存开销 vs 精度 vs 性能"的三角权衡，从方案零逐级下降到方案三级。每一级的下降都是为了换取某种资源的节省。**

**工业映射**：

- **Linux 内核 `noatime` 挂载选项**：完全不更新访问时间，是"方案零"的工业典范
    
- **Linux 内核统计计数器**：如 `/proc` 中的各种统计，使用 per-CPU 计数器 + 读取时汇总（方案一级的变体）
    
- **Java `LongAdder`**：高并发计数器的工业标准实现，本质是方案一级的"每线程分片"
    
- **我的判断**：今天写高并发服务的工程师，遇到"统计查找次数/请求次数"需求时，**决策流程应该是**：
    
    1. 业务能否接受不计数？（方案零）→ 最优
        
    2. 内存是否充裕？（方案一级 per-CPU）→ 用 `LongAdder`
        
    3. 内存敏感 + NUMA 系统？（方案二级 per-socket）→ 自定义 per-socket 计数器
        
    4. 需要 RCU 读侧无锁访问？（方案三级）→ 结合 `WRITE_ONCE`/`READ_ONCE`

## 13.2 使用 RCU 拯救并行软件性能（RCU Rescues）

这一节是**全章最精彩的工业设计集锦**——Paul 展示了 RCU 如何"拯救"那些被锁拖垮的并行软件。四个真实场景构成 RCU 应用的完整光谱。

### 13.2.1 RCU 和基于每 CPU 变量的统计计数（RCU and Per-Thread-Variable-Based Statistical Counters）

**原文骨架**：回到第 5 章的统计计数器——**用 RCU 保护 per-thread 计数器的注册表**，使得线程的动态创建/销毁不会导致读者访问已释放的计数器数组 。

**核心机制**：

- 每个线程创建时，将自己的计数器指针通过 `rcu_assign_pointer()` 注册到全局数组
    
- 读者通过 `rcu_dereference()` 安全遍历全局数组，汇总各线程计数器
    
- 线程退出时，通过 `call_rcu()` / `synchronize_rcu()` **延迟回收**该线程的计数器内存
    
- 保证：宽限期内所有读者都能看到一致的计数器快照
    

**🎯 第一性洞见**：这一节展示了 RCU 与第 5 章统计计数器的**完美结合**——

- **每线程计数器**（数据所有权思想）消除了写路径的同步开销
    
- **RCU 保护注册表**消除了读者与"线程退出"之间的竞争
    
- **延迟回收**保证了宽限期内读者的安全访问
    

这是"数据所有权 + RCU"组合模式的第一个工业级范例。

**工业映射**：

- **Linux 内核 `percpu_counter`**：基于 per-CPU 计数器 + RCU 保护
    
- **Java `LongAdder` 的内部实现**：类似思想，但用 CAS + 分片而非 RCU
    
- **我的判断**：今天实现"高并发统计计数器"的工程师，在 Linux 内核态应使用 `percpu_counter` + RCU；在用户态 Java 应使用 `LongAdder`；在用户态 C++ 应参考 `liburcu` 的 `per-thread` 计数器模式。
    

### 13.2.2 RCU 及可插拔 I/O 设备的计数器（RCU and Counters for Removable I/O Devices）

**🎯 这是全节最具工业价值的应用场景。**

**问题背景**：统计**可移除 I/O 设备**的访问次数。基线实现使用**读写锁**——I/O 发起的快速路径需要获取读锁，设备移除时需要获取写锁 。

**核心矛盾**：读写锁在 I/O 发起的**快速路径（fastpath）**上造成了**高昂开销**​ 。每次 I/O 发起都要获取读锁，高并发下锁争用严重。

**RCU 救援方案**​ ：

- **I/O 操作**：使用 RCU 读侧临界区（`rcu_read_lock()` / `rcu_read_unlock()`）保护，读者零开销
    
- **设备移除**：调用 `synchronize_rcu()` 等待所有在途 I/O 完成
    
- **保证**：`synchronize_rcu()` 返回后，剩余的计数器值准确反映**仅有在途 I/O**
    

**为什么这个方案优雅？**​ 三个深层原因：

1. **快速路径零开销**：I/O 发起不再获取任何锁，RCU 读者开销极低（非抢占内核中为零）
    
2. **慢速路径（设备移除）合理开销**：`synchronize_rcu()` 等待宽限期，但设备移除是**罕见操作**，开销可接受
    
3. **计数准确性**：`synchronize_rcu()` 确保宽限期后，所有在途 I/O 已完成，计数器值准确
    

**🎯 第一性洞见**：这是"并行快速路径（Fastpath）"模式（第 6.4 节）与 RCU 的完美结合——

- **热路径（I/O 发起）**：RCU 读侧临界区，零开销
    
- **冷路径（设备移除）**：`synchronize_rcu()`，合理开销
    

再次印证了全书的主题——**用"分割数据 + 弱化同步 + 延后处理"把热路径的开销压到物理极限**。

**工业映射**：

- **Linux 内核 USB 子系统**：可热插拔 USB 设备的访问统计使用 RCU 模式
    
- **Linux 内核网络设备**：`dev_get_by_name()` 等网络接口查询使用 RCU 保护
    
- **我的判断**：今天写设备驱动或 I/O 子系统的工程师，遇到"可移除设备的并发访问统计"时，**RCU + `synchronize_rcu()` 是最优解**，而非读写锁。这是 Linux 内核 20 年验证的最佳实践。
    

### 13.2.3 数组及长度（Array and Length）

**原文骨架**：考虑如下结构 ：

```
struct foo {
    int length;
    char a[16];
};
struct foo *fa;
```

**问题**：CPU 0 读取 `length`（得到 16），同时 CPU 1 **收缩数组到 8 并分配新指针**。CPU 0 用旧 `length`（16）配合新指针（指向 8 字符数组）访问 → **SEGV 或内存损坏**​ 。

**🎯 第一性洞见：长度和数组必须"原子地"一起更新。**

**RCU 救援方案**：将 `length` 和 `a[]` **嵌入同一个 RCU 保护的结构中**​ ：

```
struct foo {
    int length;
    char a[16];  // 与 length 同处一个 RCU 保护结构
};
struct foo __rcu *fa;

// 更新：分配新结构，填充新 length 和新 a[]
struct foo *new_foo = kmalloc(...);
new_foo->length = 8;
// ... 复制数据到 new_foo->a ...
rcu_assign_pointer(fa, new_foo);  // 原子发布新结构
// 宽限期后释放旧结构
```

**为什么有效？**​ 当 CPU 0 通过 `rcu_dereference(fa)` 获取指针时，它得到的是**包含匹配的 length 和 a[] 的同一结构**。即使 CPU 1 发布了新的、更小的 `foo_a` 结构，CPU 0 仍继续使用具有一致 length 和数据的旧结构 。

**工业映射**：

- **Linux 内核 `struct iovec` 数组**：长度与数据指针通过 RCU 保护
    
- **我的判断**：这一节揭示了 RCU 应用的一个**通用原则**——**任何需要"原子地"更新的多字段组合，都应该通过"间接指针 + RCU 发布新结构"来实现**。这是 RCU 模式的核心思想之一。
    

### 13.2.4 相关联的字段（Correlated Fields）

**🎯 这是 RCU 应用中最微妙、最强大的模式。**

**问题**：考虑 Schrödinger 的动物测量结构 ：

```
struct animal {
    char photo[10000];  // 大字段
    int meas_1;
    int meas_2;
    int meas_3;
};
```

**需求**：测量值 `meas_1/2/3` 必须**原子地**一起更新——读者要么看到旧的三元组，要么看到新的三元组，**绝不能看到混合版本**（如旧的 `meas_1` + 新的 `meas_2`）。

**方案一级（朴素）**：分配新 `animal` 结构，复制整个结构（包括 10000 字节的 `photo[]`），更新 `meas_1/2/3`，然后替换指针。

**代价**：复制 10000 字节的 `photo[]` 开销不可接受 。

**🎯 RCU 救援方案：间接层（Indirection）**​

```
struct measurement {
    int meas_1;
    int meas_2;
    int meas_3;
};
struct animal {
    char photo[10000];
    struct measurement __rcu *mp;  // 间接指针
};

// 更新：
struct measurement *new_meas = kmalloc(sizeof(*new_meas));
new_meas->meas_1 = new_val1;
new_meas->meas_2 = new_val2;
new_meas->meas_3 = new_meas3;
rcu_assign_pointer(animal->mp, new_meas);  // 原子发布新测量
// 宽限期后释放旧测量
```

**读者通过 `rcu_dereference(animal->mp)` 看到的是测量值的三元组原子快照**​ 。

**缓存优化（Cache-Friendly Optimization）**​ ：

间接层增加了一次缓存未命中（dereference `mp`）。Paul 给出的优化方案 ：

1. **正常情况**：`mp` 指向 `animal` 结构内嵌的 `measurement` 嵌入实例（无额外缓存未命中）
    
2. **更新时**：分配临时 `measurement`，`mp` 指向临时实例（读者在此期间承受一次缓存未命中）
    
3. **宽限期后**：将临时 `measurement` 复制回嵌入实例
    
4. **第二次宽限期后**：`mp` 指回嵌入实例，释放临时实例
    

**🎯 第一性洞见**：相关联字段模式揭示了 RCU 的**深层哲学**——

> **"原子性"不是通过锁来实现的，而是通过"发布新版本的指针"来实现的。**​ 读者看到的是指针发布时刻的一致性快照，而非通过锁"冻结"整个结构。

这是 RCU 区别于所有其他同步机制的核心特征——**它不阻止并发更新，而是让更新者发布新版本，读者访问旧版本，两者真正并行无冲突**。

**工业映射**：

- **Linux 内核 `struct task_struct` 的 `mm` 字段**：内存描述符通过 RCU 保护，让读者看到一致的内存映射快照
    
- **配置热更新**：新配置作为新版本发布，RCU 读者在宽限期内仍使用旧配置
    
- **我的判断**：今天写"需要原子更新多个字段"的并发数据结构的工程师，**首选方案应该是"间接指针 + RCU 发布新结构"**，而非"用锁保护多字段更新"。这是 Linux 内核中 `seqlock` 的 RCU 化替代方案，性能更优。
    

**Paul 邮件中的关键洞见**​ ：

> _"Read-only code paths should remain read-only: Spurious synchronization writes to shared memory kill performance and scalability."_
> 
> （只读代码路径应保持只读：对共享内存的伪同步写会毁掉性能和可扩展性。）

这句话精准概括了 RCU 救援的核心价值——**它让只读路径真正只读，零同步写**，从而获得了极致的可扩展性。

## 13.3 散列难题（Hashing Hassles）

这一节 Paul 探讨了哈希表（及其他搜索结构）中的两个微妙问题——**相关联的数据元素**和**更新友好的哈希表遍历**。这两个问题揭示了并行哈希表设计的深层挑战。

### 13.3.1 相关联的数据元素（Correlated Data Elements）

**原文骨架**：考虑 Schrödinger 将家人加入内存数据库的场景 。他绝对不希望数据库显示"新娘已结婚，但新郎未结婚"——即**关联数据元素必须原子地一起更新**​ 。

**问题本质**：这与 13.2.4 的"相关联的字段"是**同一问题的两个尺度**：

- **13.2.4**：同一结构内的多字段原子更新 → 用间接指针 + RCU
    
- **13.3.1**：跨多个哈希表元素的原子更新 → 需要更精巧的机制
    

**🎯 第一性洞见：跨元素的原子更新是并行哈希表的"圣杯问题"。**

**Paul 给出的方案**：

**方案一级：将关联元素合并为单一结构**

如果语义允许，将"丈夫"和"妻子"合并为一个 `family` 结构，用一把锁或 RCU 保护整个结构。这是最简单的方案，但限制了灵活性。

**方案二级：两阶段提交协议**

1. 更新者获取两个元素的锁（按固定顺序避免死锁）
    
2. 更新第一个元素
    
3. 更新第二个元素
    
4. 释放锁
    

**代价**：读者可能看到中间状态（丈夫已更新，妻子未更新）。

**方案三级：间接层 + RCU（推荐方案）**

每个哈希表元素指向一个"数据对象"，**关联元素共享同一个数据对象**​ ：

```
struct family_data {
    bool husband_married;
    bool wife_married;
    // ... 其他关联字段
};
struct family_data __rcu *family_data_ptr;

// 更新：分配新 family_data，填充一致性状态，RCU 发布
struct family_data *new_data = kmalloc(sizeof(*new_data));
new_data->husband_married = true;
new_data->wife_married = true;  // 原子地同时设置
rcu_assign_pointer(family_data_ptr, new_data);
// 宽限期后释放旧数据
```

**读者通过 `rcu_dereference(family_data_ptr)` 看到的是一致的婚姻状态**​ 。

**工业映射**：

- **Linux 内核的 `struct inode` 与 `struct dentry`**：通过 RCU 保护，确保读者看到一致的文件系统状态
    
- **我的判断**：跨元素的原子更新问题在分布式系统中更为突出（如分布式事务）。但在单机并行哈希表中，间接层 + RCU 是最优雅的解决方案。
    

### 13.3.2 更新友好的哈希表遍历（Update-Friendly Hash-Table Traversal）

**原文骨架**：考虑对哈希表进行**统计扫描**（如计算平均长度-权重比），同时**更新操作（添加/删除元素）并发进行**​ 。

**问题**：传统遍历（如在锁保护下遍历）会阻塞所有更新，造成系统停顿。对于大型哈希表，全表遍历可能需要较长时间，期间的更新停滞不可接受。

**🎯 RCU 救援方案：更新友好遍历**​

```
// 统计扫描
rcu_read_lock();
hash_for_each(table, bucket, element) {
    // 在 RCU 读侧临界区内遍历
    // 更新操作可并发进行，不阻塞遍历
    accumulate_stats(element);
}
rcu_read_unlock();
```

**RCU 保证**：遍历期间元素不会被释放（宽限期未到），即使元素被删除也只是从链表中断开，遍历仍能安全访问 。

**可接受的不精确性**：由于遍历和更新并发进行，**统计结果可能有轻微误差**（某些元素被计入两次，或某些元素未被计入）。但对于统计扫描场景，**轻微误差是可接受的**​ 。

**🎯 第一性洞见：更新友好遍历揭示了 RCU 的"最终一致性"哲学——**

> **不是所有操作都需要强一致性。对于统计、监控、聚合等场景，"近似一致 + 零阻塞"远比"强一致 + 全表锁"更有价值。**

**可扩展哈希表的挑战**​ ：

- 在**可调整大小的哈希表**中，resize 操作期间，旧表和新表都不包含所有元素
    
- 解决方案：
    
    1. 获取哈希表的 resize 锁
        
    2. 遍历旧表和新表（确保覆盖所有元素）
        
    3. 释放 resize 锁
        
    
- 代价：遍历期间 resize 被阻塞，但 resize 是罕见操作
    

**工业映射**：

- **Linux 内核 `rhashtable` 的遍历**：使用 RCU 实现更新友好遍历
    
- **Java `ConcurrentHashMap` 的 `forEach`**：类似思想，但使用 `volatile` + CAS 而非 RCU
    
- **我的判断**：今天写"需要对大型并发哈希表做统计扫描"的工程师，**RCU 包裹的遍历是最佳方案**。它允许统计与更新真正并发，系统吞吐量不受影响。这是 RCU 在"读多写少 + 需要遍历"场景下的杀手锏应用。

## 本章总览：贯穿全章的第一性原理总结

读完第 13 章，我认为 Paul 真正想建立的认知框架可以压缩为**三句话**：

1. **并行设计的第一性原理是"先问能否不做"**。"对查找进行计数"的最优解是"完全不计数"（如 `noatime`）；"跨元素原子更新"的最优解是"将关联元素合并为单一结构"。**在并行世界里，"不做"往往比"聪明地做"更优**。
    
2. **RCU 是"读侧重"场景的终极救援工具**。它通过四个工业级模式拯救被锁拖垮的并行软件：
    
    - **每线程计数器 + RCU 保护注册表**：消除线程动态创建/销毁与读者之间的竞争
        
    - **RCU 读侧临界区替代读写锁**：I/O 快速路径零开销（可插拔设备计数）
        
    - **长度与数据嵌入同一 RCU 结构**：消除"长度-数据"错位
        
    - **间接指针 + RCU 发布新结构**：相关联字段的原子更新
        
    
3. **"原子性"在 RCU 世界通过"发布新版本"实现，而非"锁住旧版本"**。读者看到的是指针发布时刻的一致性快照，更新者发布新版本——两者真正并行无冲突。这是 RCU 区别于所有其他同步机制的核心哲学。
