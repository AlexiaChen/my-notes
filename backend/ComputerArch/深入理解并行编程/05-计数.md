
# 第 5 章 计数（Counting）


---

## 5.1 为什么并发计数不可小看（Why Concurrent Counting Matters）

**原文骨架**：计数器看似简单——一个整数加一而已——但一旦成为**多核共享的热点**，它就会暴露并行编程几乎所有核心难题：原子性、内存序、Cache 一致性、伪共享、可扩展性瓶颈。Paul 在这一节用实测说明：一个朴素全局计数器的性能，会**随 CPU 核数增加而急剧恶化**，甚至比单线程还慢。

**第一性解读**：

为什么一个 `++` 能拖垮多核？回到第 3 章的物理真相：

> 🎯 **每一次 `g_counter++` 都是一次"读-修改-写"原子操作（CAS 或 `LOCK XADD`），它必须把承载计数器的 Cache Line 拉到当前核的 Modified 状态，使其他核上同一 Line 失效。**​ 当 N 个核同时计数，这个 Cache Line 就在 N 个核间疯狂"弹来弹去"（MESI 状态在 M/S 间震荡），产生海量 Cache 一致性流量。**计数器的争用成本 ≈ 第 3 章表里的"CAS + Cache Miss"≈ 500+ 时钟周期/次**，而非直觉的"几次加法"。

**这就是"并发计数不可小看"的硬件根源**：它不是算法复杂，而是**共享写入的物理成本被多核放大到了不可接受**。这一节的真正价值，是**用一个极简例子，把抽象的"硬件习性"变成了可感知的性能悬崖**——为后面 5.2~5.4 的所有计数器变体提供了"为什么要这样设计"的动机。

**工业洞见**：

- 全局 QPS 计数器、连接数统计、请求计数器等**看似无害的全局变量**，在高并发服务里常是隐形的可扩展性杀手。很多"莫名其妙的多核不 scale"根因，就是某个全局计数器。
    
- 这也解释了为什么 Linux 内核大量使用**每 CPU 计数器**（`per_cpu` 变量）——不是内核开发者闲，而是全局计数器在多核上真的不 work。

## 5.2 统计计数器（Statistical Counters）

**原文骨架**：统计计数器（statistical counter）是"只增不减、最终读取汇总"的计数器，用于统计事件次数（如数据包接收数、函数调用次数）。本节给出**四种演进实现**，构成一条清晰的设计优化链：**全局原子计数器 → 数组计数器 → 最终一致计数器 → 每线程/每 CPU 计数器**。

### 5.2.1 设计（Design）

**第一性解读**：

设计统计计数器的核心矛盾是**"计数写入的热路径"与"读取汇总的冷路径"的不对称**：

- **写（计数）极频繁**：每次事件都要 `++`，是性能敏感的热路径，必须廉价。
    
- **读（汇总）极少**：通常只在监控/采样时读取一次，可以接受稍贵。
    

> 💡 **关键洞察**：利用这种"写多读少 + 允许读取略滞后"的不对称性，可以把热路径的开销压到极致——这正是统计计数器多种优化变体的共同出发点。

### 5.2.2 基于数组的实现（Array-Based Implementation）

**原文骨架**：把全局计数器拆成一个**数组**，每个数组元素对应一个 CPU 核/线程，各核只更新自己对应的元素（无共享写入），读取时遍历数组求和。

**第一性解读**：

这是**"数据分割 + 复制"思想在计数器上的第一次落地**（呼应第 2 章 Paul 的设计原则和第 3 章"共享是成本源头"）。

- 每个核写自己独占的数组槽位 → **零 Cache 一致性流量**（槽位分属不同 Cache Line，无伪共享）。
    
- 读取时加总 N 个槽位 → 得到近似/最终总数。
    

**伪代码（我的整理）**：

```
#define NR_CPUS 64
long __cacheline_aligned counter[NR_CPUS];  // 每元素独立 Cache Line

// 热路径：每 CPU 写自己槽位，无竞争
void inc_count(void) {
    counter[smp_processor_id()]++;
}
// 冷路径：遍历求和
long read_count(void) {
    long sum = 0;
    for (int i = 0; i < NR_CPUS; i++) sum += counter[i];
    return sum;
}
```

**工业洞见**：

- Linux 内核的 `/proc/stat`、`/proc/vmstat` 等统计信息就是**每 CPU 计数器 + 读取时汇总**的典型——`per_cpu` 变量 + `for_each_online_cpu` 求和。
    
- **代价**：读取不是原子的全局快照——求和过程中各槽位仍在被并发修改，读到的是"近似一致"的值。对统计场景（监控、采样）这完全可接受。
    

### 5.2.3 最终结果一致的实现（Eventually Consistent Implementation）

**原文骨架**：在数组计数器基础上，引入**版本号/序列机制**，让读取端能检测到"汇总期间是否有并发更新"，必要时重试，从而获得一个"最终结果一致"（而非实时一致）的读数。

**第一性解读**：

这是对 5.2.2 的**一致性增强**：数组计数器读到的是"某一时刻各槽位的拼接"，可能因求和跨时隙而不完全自洽。最终一致版本通过**轻量级协调机制**（如读取前后各取一次版本号，比对一致则接受）让读数"在某个时刻点是自洽的"。

> 🎯 **核心洞见**：这里体现了并行设计的一条通用原则——**不追求"实时全局一致"，而追求"最终一致 + 可验证"**。实时全局一致需要全局同步（昂贵），最终一致只需本地协调（廉价）。对 99% 的统计场景，后者足够且快得多。

**工业映射**：

- 分布式系统的"最终一致性"（如 DNS TTL、Cassandra 的读写一致性级别）与这里的思路同源——**用"允许短暂不一致"换取"极高可用性和可扩展性"**。
    
- 内核 `per_cpu` 计数器的读取语义本身就是"最终一致"的：你读到的 vmstat 数字是"各 CPU 最近一次更新"的拼接，不保证是一个原子瞬间快照。
    

### 5.2.4 基于每线程变量的实现（Per-Thread Variable Implementation）

**原文骨架**：把计数器进一步从"每 CPU"细化为"每线程（per-thread）"——每个线程有自己独立的计数变量（Thread-Local Storage / `__thread` / `thread_local`），彻底消除线程间共享写入。

**第一性解读**：

这是数组计数器的**自然进化**：5.2.2 按 CPU 分（粒度 = CPU），5.2.4 按线程分（粒度 = 线程）。在线程数 ≈ CPU 数时二者等价；在线程数远多于 CPU 数（或线程动态创建销毁）时，每线程变量更灵活。

**三种实现路径（我的整理）**：

|方式|机制|优劣|
|---|---|---|
|**`__thread` / `thread_local`**​|编译器为每个线程生成独立副本|零开销访问；但线程退出后数据需另行汇总回收|
|**每线程指针数组**​|全局数组存各线程的计数指针，新线程注册|读取时可遍历汇总；需协调线程生命周期|
|**RCU 保护的不定长数组**​|用 RCU 管理线程注册表，读侧无锁遍历|读侧极致快；写侧（线程创建/销毁）走 RCU 回收|

**工业洞见**：

- **Thread-Local Storage（TLS）**​ 是现代高并发库的标配：Redis、Nginx、JVM（Thread-Local Allocation Buffer, TLAB）都用 TLS/线程局部数据消除共享写入。
    
- **JVM `LongAdder`**：Java 8 引入的 `LongAdder`/`LongAccumulator` 正是"每线程（Striped）计数器"思想的工业级落地——内部维护一组 `Cell`（按线程哈希分散到不同 Cell），`add()` 只更新本线程对应 Cell，`sum()` 遍历求和。**在高争用下 `LongAdder` 显著优于 `AtomicLong`**，这正是 5.2.4 思想在标准库的直接体现。
    
- **我的判断**：今天写 Java/Go/C++ 的工程师，遇到"高并发计数"需求，**首选应该是语言/库提供的 striped/per-thread 计数器（`LongAdder`、C++ `tbb::atomic` 聚合、Go `sync/atomic` + per-P 分片），而非自己手撸全局 `atomic<int>`**。这正是 Paul 这一节思想的现代工业化成果。
    

### 5.2.5 本节讨论（Discussion）

**第一性总结（5.2 全节）**：

统计计数器的四种实现构成了一条**"用分割换可扩展性"的清晰演进链**：

> **全局原子计数器（不可扩展）**
> 
> → **数组计数器（每 CPU，消除伪共享）**
> 
> → **最终一致计数器（可验证的近似读数）**
> 
> → **每线程变量（最细粒度分割 + TLS）**

这条链的**第一性原理**是：**把"一个被所有人争抢的共享变量"，重构成"每人写自己的副本、读取时汇总"**。它把第 3 章"共享是成本源头、复制是免费优化"和第 2 章"先分割数据再考虑访问控制"的设计原则，在一个极简例子上完整兑现了。

> ⚠️ **适用边界**：统计计数器方案**只适用于"只增不减、允许读数略滞后"的场景**（事件统计、QPS 计数）。一旦需要"有上限的计数"（如资源配额、连接数限制），统计计数器就不够了——这正是 5.3/5.4 节要解决的问题。

## 5.3 近似上限计数器（Approximate Upward Counters）

**原文骨架**：上限计数器（upward counter with limit）在统计计数器基础上增加一个**上限约束**——计数不能超过某阈值（如最大并发连接数、资源池配额）。本节先给出一个**简单上限计数实现**，再演进到**近似上限计数器**（允许偶尔略超上限，换取极高性能和可扩展性）。

### 5.3.1 设计（Design）

**第一性解读**：

上限计数器比统计计数器的核心难点在于：**"是否超过上限"的判断必须是实时且正确的**——统计计数器允许读数滞后，但"是否还能再接一个连接"这个判断不能错（否则资源被用超，可能 OOM/崩溃）。

> 💡 **关键洞察**：这里再次出现"一致性 vs 性能"的取舍。若要求**严格不超过上限**，判断必须全局同步（昂贵）；若允许**偶尔略超上限**（对很多场景可接受），则可大幅放宽同步、获得近统计计数器的可扩展性。**这就是"近似上限计数器"存在的理由——用"偶尔略超"换"极致性能"。**

### 5.3.2 简单的上限计数实现（Simple Limit Counter）

**原文骨架**：用一把全局锁或全局原子变量保护计数和上限判断——每次 `increment` 先获取锁/原子读，判断 `count < limit`，是则 `count++`，否则拒绝。

**第一性解读**：

这是最直观的实现，但**它正是 5.1 节"不可扩展"的那个朴素全局计数器**——所有线程争抢同一把锁/同一个原子变量，Cache Line 弹跳，性能随核数急剧恶化。

**伪代码（我的整理）**：

```
long count = 0, limit = MAX_CONN;
pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;

int inc_limit(void) {
    pthread_mutex_lock(&m);
    if (count >= limit) { pthread_mutex_unlock(&m); return -EBUSY; }
    count++; pthread_mutex_unlock(&m); return 0;
}
```

**工业洞见**：这种实现**只适合低争用/少核场景**。在高并发网关、连接池里，它会立刻成为瓶颈。这也是为什么工业级连接池/限流器很少用"全局锁 + 精确计数"。

### 5.3.3 关于简单上限计数的讨论（Discussion）

**我的补充**：简单上限计数的价值在于**正确性和实现简单性**——它严格保证"不超过上限"，适合对资源超用零容忍的场景（如内存池配额）。但**它不可扩展**，是多核下的性能反例。这一节和 5.3.4 形成对照：**要可扩展性，就得放松"严格不超上限"的约束。**

### 5.3.4 近似上限计数器的实现（Approximate Limit Counter）

**原文骨架**：借鉴 5.2 的统计计数器思想——把计数按 CPU/线程分片，每片独立计数，全局只维护一个**近似汇总**。判断是否超上限时，用近似汇总做快速决策，允许偶尔略超。

**第一性解读**：

近似上限计数器的核心技巧是**两阶段判断**：

1. **快路径（本地分片）**：线程只更新自己的本地分片计数，几乎无竞争。
    
2. **慢路径（全局近似汇总）**：定期/按需把各分片汇总，与上限比较；由于汇总本身是近似的（各分片仍在变），判断结果也是近似的——**可能偶尔放过一次"实际已超上限"的请求**。
    

> 🎯 **核心洞见**：这里把"精确判断"降级为"概率性判断"，换来了**接近统计计数器的可扩展性**。它再次印证全书主线——**在并行世界里，"近似正确 + 极快"常常比"精确正确 + 极慢"更有实用价值。**

### 5.3.5 关于近似上限计数器的讨论（Discussion）

**适用场景与边界（我的判断）**：

- ✅ **适用**：限流（rate limiting）、近似配额、负载均衡决策——这些场景"偶尔多放一个请求"的后果轻微（最多略微增加后端压力），而高并发下的性能收益巨大。工业级限流器（如令牌桶、滑动窗口计数）普遍采用分片/近似思路。
    
- ❌ **不适用**：硬资源配额（如"最多分配 1024MB 内存，超了就 OOM"）、安全相关计数——这类场景**不允许任何超用**，必须选 5.4 的精确上限计数器。
    

> 💡 **工程准则**：**先问"超上限的后果多严重"**。后果轻微 → 近似上限计数器（快）；后果严重 → 精确上限计数器（慢但正确）。这是把"业务语义"纳入并行选型决策的典型例子。

## 5.4 精确上限计数（Exact Upward Counters）

**原文骨架**：当"不允许超上限"是硬约束时，必须采用**精确上限计数器**。本节给出两种实现：**原子上限计数（atomic limit counter）**​ 和更精巧的 **Signal-Theft 上限计数**，后者用信号/协调协议在保持精确的同时大幅提升可扩展性。

### 5.4.1 原子上限计数的实现（Atomic Limit Counter）

**原文骨架**：用原子变量（`atomic_long_t` / `std::atomic<long>`）保护计数和上限判断，依靠原子操作的"读-修改-写"语义保证判断与递增的原子性。

**第一性解读**：

原子上限计数是"简单锁实现"的**无锁化升级**——把 `mutex_lock`/`unlock` 替换为 CAS/`fetch_add`，消除了上下文切换开销，但仍**共享同一个原子变量**，因此 Cache Line 弹跳的可扩展性问题**依旧存在**（只是比锁轻量一些）。

**伪代码（我的整理）**：

```
std::atomic<long> count{0};
const long limit = MAX_CONN;

int inc_limit() {
    long old = count.fetch_add(1, std::memory_order_acq_rel);
    if (old >= limit) { count.fetch_sub(1, std::memory_order_relaxed); return -EBUSY; }
    return 0;
}
```

**工业洞见**：

- 原子上限计数适合**中等争用**场景。低争用下它接近无开销；高争用下仍会因 Cache Line 弹跳而恶化。
    
- **内存序选型**：计数本身用 `acq_rel`（建立同步关系），回滚的 `fetch_sub` 用 `relaxed`（纯计数修正，无依赖链）即可——这是第 4 章"选对内存序"原则的直接应用。
    

### 5.4.2 关于原子上限计数的讨论（Discussion）

**我的补充**：原子上限计数是"正确性 + 可接受性能"的折中。它的价值在于**语义清晰、实现简洁、无死锁风险**。但在**核数很多 + 争用很高**（如 64 核服务器上统计全局连接数）时，它仍会成为瓶颈。**要突破这个瓶颈，就需要更精巧的协议——Signal-Theft。**

### 5.4.3 Signal-Theft 上限计数的设计（Signal-Theft Limit Counter Design）

**原文骨架**：Signal-Theft 是一种**分布式协调机制**——把计数分片到各 CPU/线程（类似 5.2 的统计计数器），但为保证"精确不超上限"，引入**信号（signal）与窃取（theft）**​ 协议：当某分片计数接近上限时，通过信号通知其他分片"减速/停止"，必要时"窃取"其他分片的配额余量，从而在**保持精确上限**的同时实现**接近线性的可扩展性**。

**第一性解读（这是全章技术密度最高的一节）**：

Signal-Theft 的思想可以类比**分布式资源调度**：

> 🎯 **把"全局硬约束（上限）"分解为"各分片本地软约束 + 分片间协调信号"。**​ 正常情况下各分片独立计数（无共享、快）；当全局总量逼近上限时，协调协议介入（慢，但罕见），保证精确不超。

这和第 2 章"铁三角"、第 3 章"硬件习性"的关系在于：**Signal-Theft 用"偶尔的跨分片协调（贵）"换"常态下的零共享（快）"**，把昂贵的全局同步从"每次计数都发生"降级为"只在接近上限时发生"——**这是"热路径极致优化"思想的巅峰体现**。

### 5.4.4 Signal-Theft 上限计数的实现（Implementation）

**原文骨架**：Paul 在书中给出了 Signal-Theft 的详细代码（含每 CPU 计数数组、`theft` 函数、`signal` 机制、上限判断逻辑）。核心是：

- 每 CPU 维护本地计数和本地上限（总额按 CPU 数分片）；
    
- `increment` 先尝试本地分片，本地未满则成功（快路径）；
    
- 本地已满/竞争时，通过 signal 请求其他分片"让出配额"（theft），从富余分片"窃取"余量完成本次计数；
    
- 全局上限通过各分片上限之和精确维持。
    

**实现要点（我的整理，非逐行抄书）**：

```
// 每 CPU 分片：本地计数 + 本地上限
struct cpu_count {
    long local_count;
    long local_limit;   // 初始 = global_limit / NR_CPUS
} __cacheline_aligned per_cpu_cnt[NR_CPUS];

// 快路径：本地分片计数
int inc_limit(int cpu) {
    if (per_cpu_cnt[cpu].local_count < per_cpu_cnt[cpu].local_limit) {
        per_cpu_cnt[cpu].local_count++; return 0;  // 无共享，极快
    }
    return signal_theft(cpu);  // 慢路径：协调/窃取
}
```

**工业洞见**：

- Signal-Theft 是**"分片 + 协调"范式**的经典范例。它的价值不只在于计数——**任何"带全局硬约束的分布式资源分配"问题**（如分布式限流、配额管理、连接池分配）都可以借鉴这套思想。
    
- Linux 内核的 **cgroup v2 资源控制**（`cpu.max`、`memory.max`）在底层就使用了类似"分片配额 + 跨 CPU/跨 cgroup 协调"的机制来在保证硬上限的同时保持可扩展性。
    

### 5.4.5 关于 Signal-Theft 上限计数的讨论（Discussion）

**我的判断**：

Signal-Theft 是"精确上限 + 高可扩展性"的**最优解**，但它的代价是**实现复杂度极高**（远超前面所有变体）。工程选型时要清醒权衡：

- ✅ **值得用**：核数多（≥16）+ 争用高 + 硬上限不可违反（如内核级资源配额、硬限流）。此时 Signal-Theft 带来的可扩展性收益远超实现成本。
    
- ❌ **过度设计**：核数少 / 争用低 / 上限可近似 → 直接用原子上限计数甚至简单锁实现即可，**不要为了"理论上更优"而引入 Signal-Theft 的复杂度**。
    

> 📌 **这印证了第 2 章的 YAGNI 原则**：通用性/极致性能是一把双刃剑，过度追求就是"朝自己脚开枪"。Signal-Theft 是"必要时才出鞘"的利器，非常规武器。

## 5.5 特殊场合的并行计数（Parallel Counting for Special Cases）

**原文骨架**：Paul 在这一节讨论了**针对特定访问模式优化的计数器**——如"只增、偶尔清零""读多写少""需要支持 decrement"等特殊语义下的定制计数器。

**第一性解读**：

这一节的主旨是**"计数器设计必须贴合访问模式"**——没有一种计数器能通吃所有场景。几种典型特殊场合：

|特殊场合|优化思路|工业对应|
|---|---|---|
|只增、定期清零（如每秒 QPS）|分片计数 + 定期整体重置|监控系统指标采集（Prometheus counter）|
|读多写少|读写锁 / RCU 保护计数器|配置引用计数、路由表版本号|
|需支持增减（可正可负）|分片 + 本地增减 + 汇总|连接数（accept 增、close 减）|
|需要精确快照|全局版本号 + 两阶段读|分布式一致性协议中的 epoch/term|

**工业洞见**：

- **Prometheus `Counter` / `Gauge`**：Prometheus 客户端库在进程内就用"每线程分片 + 抓取时汇总"实现高并发下的指标采集——正是 5.2 思想的直接工业化。
    
- **我的判断**：这一节的价值在于**培养"先刻画访问模式，再选/设计计数器"的工程习惯**，而非提供万能模板。

## 5.6 关于并行计数的讨论（Discussion）

这是全章收束。Paul 从"性能""专门化""学到了什么"三个维度总结并行计数。

### 5.6.1 并行计数的性能（Performance）

**第一性总结**：计数器性能的天花板由**共享写入的 Cache 一致性成本**决定（第 3 章物理真相）。所有优化变体的本质都是**把"每次计数都共享写入"重构为"常态下无共享写入"**：

- 全局原子/锁 → 每次都共享（最慢，不可扩展）；
    
- 数组/每 CPU/每线程 → 常态无共享（快，近线性扩展）；
    
- 近似上限 → 常态无共享 + 偶尔协调（快，允许略超）；
    
- Signal-Theft → 常态无共享 + 罕见精确协调（快 + 精确，但复杂）。
    

**工业洞见**：评测计数器方案时，**不要只看平均吞吐，要看随核数增加的扩展性曲线（throughput vs core count）**。一个"平均吞吐高但在 16 核后不再增长"的全局计数器，实际价值远低于"吞吐随核数近线性增长"的分片计数器。

### 5.6.2 并行计数的专门化（Specialization）

**第一性总结**：**不存在"通用最优计数器"**。统计计数、近似上限、精确上限、特殊场合，各自对应不同的访问模式和一致性需求。计数器设计的专门化，是"第 2 章铁三角中通用性与性能不可兼得"这一守恒律在微型问题上的具象化——**追求通用（一套计数器通吃）就会牺牲性能；追求性能（贴合特定模式定制）就会牺牲通用性。**

### 5.6.3 从并行计数中学到什么（Lessons Learned）

这是全章**最有价值的收束**。我把 Paul 的教训与我自己的洞见融合，提炼为**五条跨场景可迁移的第一性原理**：

1. **共享写入是并行的成本之源**：一个全局计数器的灾难，不在算法，而在"所有核争抢同一 Cache Line"。**任何并行数据结构，先问"有没有共享写入热点"，再谈算法优化。**
    
2. **分割 + 复制是免费的优化**：把共享变量拆成"每 CPU/每线程副本 + 读取时汇总"，几乎是"无本万利"的可扩展性提升——前提是访问模式允许（写多读少、允许读数滞后/近似）。
    
3. **一致性是有梯度的，不是二元的**：实时精确一致（贵）↔ 最终一致（廉）↔ 近似一致（更廉）。**把一致性要求降到"业务可接受的最低档"，往往能换来数量级性能提升。**​ 这是并行设计最被低估的杠杆。
    
4. **简单性优先，复杂度是最后手段**：全局锁 → 原子变量 → 分片计数 → Signal-Theft，复杂度递增。**先用手头最简单的方案验证瓶颈，确有需要再升级**——不要用 Signal-Theft 去解决 4 核机器上的计数问题（YAGNI）。
    
5. **用硬件真相解释软件现象**：计数器为什么慢？不是"锁慢"，而是"Cache Line 在多核间弹跳"。**养成用第 3 章硬件习性（Cache、NUMA、原子开销、内存屏障）解释并行性能现象的习惯**，你就能从"抄并行模板"进阶为"设计并行系统"。

## 本章总览：贯穿全章的第一性原理总结

读完第 5 章，我认为 Paul 真正想建立的认知框架可以压缩为**三句话**：

1. **计数器是并行编程的"hello world"，也是硬件习性的"压力测试"。**​ 一个 `++` 能把 Cache 一致性、伪共享、原子开销全部暴露出来——搞懂计数器，就搞懂了并行性能问题的物理根源。
    
2. **所有计数器优化的本质，都是"把共享写入重构为私有副本 + 按需协调"。**​ 从全局原子到每线程分片，再到 Signal-Theft，是一条"用分割换可扩展性"的清晰演进链，其思想可迁移到几乎所有并行数据结构设计。
    
3. **一致性是有成本的连续谱，工程的艺术在于把一致性降到业务可接受的最低档。**​ 统计计数（最终一致）→ 近似上限（概率正确）→ 精确上限（Signal-Theft），对应不同的业务语义和成本。选错档位（过度精确或过度近似）要么牺牲性能，要么引入风险。
    

> 📌 **给工程师的个人判断（2026 年视角）**：今天写业务代码的工程师，**绝大多数计数需求应直接使用语言/库提供的分片/per-thread 计数器**——Java 用 `LongAdder`、C++ 用 TBB 原子聚合或自研 striped counter、Go 用 `sync/atomic` + per-P 分片、指标采集用 Prometheus client 内置分片。**不要自己手撸全局 `atomic<int>` 去扛高并发计数**——那是 5.1 节的反面教材。而当你需要做"硬上限资源配额"这类对正确性零容忍的需求时，才值得借鉴 5.4 的精确上限/Signal-Theft 思想，或直接使用内核/cgroup 提供的资源控制机制。
> 
> 更重要的是：**第 5 章的真正价值超出"计数"本身**。它用计数器这个极简载体，把全书前四章（并行难的根因 → 硬件习性 → 工具 → 第一个模式）串成了一条完整的设计思维链。学会用"分割数据、规避共享、按需协调、按业务语义定一致性档位"这套思维去审视**任何**并行数据结构（队列、哈希表、链表、内存分配器），你才算真正读懂了 Paul 这一章——也才算真正入门了并行编程的设计之道。
