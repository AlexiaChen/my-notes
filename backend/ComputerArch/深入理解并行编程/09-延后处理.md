
# 第 9 章 延后处理（Deferred Processing）

> 这一章的开场白是全书极具颠覆性的一句话——**"在并行编程中，'懒惰'往往比'勤劳'表现更好、扩展性更强。"**​
> 
> "延后处理"（Deferred Processing）的本质是：**把某些操作推迟到更合适的时机执行，从而降低同步开销，提升性能和可扩展性**​ 。这种策略在有记录的历史黎明之前就已存在，偶尔被贬称为拖延症，甚至是纯粹的懒惰——但过去几十年的研究表明，它在简化和优化并行算法方面具有重大价值 。
> 
> 本章用一个贯穿始终的运行示例——**Pre-BSD 路由表**（一个简化的包路由算法，本质是"地址→网络接口"的映射链表）来承载所有讨论 。选择这个示例是因为：路由表是"读多写少"的典型，正好能凸显四种延后处理技术的差异。
> 
> 四种核心技术 ：
> 
> |技术|核心思路|
> | --- |---|
> | **引用计数（Reference Counting）** ​|用计数器跟踪对象引用数，计数为零时释放|
> |**危险指针（Hazard Pointers）**​|每个线程发布正在使用的指针，阻止其被释放|
> |**顺序锁（Sequence Locking）**​|读者检测写者操作并重试，无需持锁|
> |**RCU（Read-Copy-Update）**​|读者无锁访问，写者更新后等待旧读者完成再释放|
> 
> 这四种技术不是互相替代的关系，而是构成了一个**"延后处理光谱"**——从"简单但慢"到"复杂但极致快"，从"自动回收"到"手动延后"。理解这个光谱，是读懂本章的关键。

---

## 9.1 引用计数（Reference Counting）

### 9.1.1 各种引用计数的实现

**原文骨架**：引用计数通过跟踪指向对象的引用数量来防止对象被过早释放。但 Paul 指出——**"Although this is a conceptually simple technique, there are a great many variants adapted to different situations"**（虽然这是一个概念上简单的技术，但存在大量适应不同情况的变体）。

**第一性解读**：

Paul 在 IBM 的论文《Overview of Linux-Kernel Reference Counting》中给出了**引用计数的六种变体分类**​ ，这是我见过最清晰的框架：

|类别|原子操作|内存屏障|典型场景|
|---|---|---|---|
|**Simple counting**（`-`）|无|无|单线程或已有锁保护|
|**Atomic counting**（`A`）|有|无|简单计数，无依赖链|
|**Atomic with release barrier**（`AM`）|有|仅释放端|获取后立刻使用，释放时需屏障|
|**Checked atomic with release barrier**（`CAM`）|有|仅释放端|获取时需检查（如 `kref_get_unless_zero`）|
|**Checked atomic**（`CA`）|有|无|获取时检查但无需屏障|
|**Checked atomic with acquire barrier**（`MCA`）|有|获取端+释放端|最强保证|

**🎯 第一性洞见**：引用计数绝不是"一个 `atomic_inc` + 一个 `atomic_dec`"那么简单。它的**正确性取决于"获取引用"和"释放引用"两端的原子操作与内存屏障的正确配对**。这就是为什么 Linux 内核里有 `kref`、`refcount_t`（带溢出保护）等多种引用计数原语——它们在安全性、性能、内存屏障开销上各有权衡 。

**经典陷阱（Pre-BSD 路由表中的 bug）**​ ：

```
// 错误写法：获取指针和增加引用非原子
p = route_table_head;
p->ref_count++;  // BUG! 在 p 和 p->ref_count 之间，另一个线程可能 free(p)

// 正确写法：用 CAS 或 kref_get_unless_zero 原子性地"获取引用"
p = route_table_head;
while (!kref_get_unless_zero(&p->refcount)) {
    p = route_table_head;  // 重试
}
```

**工业洞见**：

- **C++ `std::shared_ptr`**：引用计数的工业标准实现，但注意——`shared_ptr` 的引用计数是**原子操作 + 内存屏障**的 `MCA` 变体，开销不低。在性能敏感路径上，`shared_ptr` 的引用计数可能成为瓶颈。
    
- **Linux `kref`**：`kref_get()` / `kref_put()`，常用于内核对象生命周期管理。
    
- **Linux `refcount_t`**：`refcount_inc()` / `refcount_dec_and_test()`，带溢出保护，防引用计数回绕攻击。
    

> ⚠️ **关键认知**：引用计数在 perfbook 的 Pre-BSD 路由表示例中，**性能垫底**​ ——原因就在于"每次查找都要原子增/减引用计数"，产生了大量的 Cache 一致性流量。这印证了第 3 章的硬件真相——**原子操作不是免费午餐**。

### 9.1.2 危险指针（Hazard Pointers）

**原文骨架**：危险指针是 Maged Michael 2004 年提出的**安全内存回收（Safe Memory Reclamation, SMR）**技术 。它的核心思想是——**与其用一个整数计数器，不如让每个线程把自己正在使用的指针"发布"到一个 per-CPU/per-thread 的槽位（hazard pointer slot）中**。

**第一性解读（这是全章技术密度最高的一节）**：

危险指针的工作机制 ：

**读者侧**：

1. 读取目标指针的值
    
2. 将该值存储到自己的 hazard pointer slot 中
    
3. 执行全序内存屏障（`smp_mb()`）
    
4. 重新读取原始指针，若值改变则清空 slot 并重试
    
5. 否则，目标对象的存在性得到保证
    

**更新者侧**：

1. 取消发布目标对象（如将指针设为 NULL）
    
2. 执行全序内存屏障
    
3. 扫描所有 hazard pointer slot
    
4. 如果没有 slot 引用该对象 → 立即释放
    
5. 如果有 slot 引用 → 延迟释放，下次扫描再判断
    

**🎯 第一性洞见**：危险指针本质上是**"不计数的引用计数"**​ 。它和引用计数的根本区别在于：

- **引用计数**：在被引用对象内部维护一个计数器，每次获取/释放都要原子修改这个计数器 → **Cache 一致性流量大**
    
- **危险指针**：引用信息维护在**读者本地的 slot**​ 中，读者侧**不需要写被遍历的数据结构**​ → **Cache 友好，读者可扩展**
    

这正是危险指针的最大优势——**读者侧无写操作，因此 CPU cache 可以做资源复制，从而弱化并行访问控制机制，提升性能和可扩展性**​ 。

**但危险指针有代价**​ ：

- 获取引用可能**失败**（slot 被占用或对象已被取消发布），失败时**必须从遍历起点重新开始**（对于嵌套数据结构，必须从最外层重新开始）
    
- 需要仔细管理 per-thread 状态和重试逻辑
    
- 每次 `acquire` 都需要内存屏障，开销不低
    

**工业映射**：

- **C++26 `std::hazard_pointer`**：危险指针已进入 C++26 标准，头文件 `<hazard_pointer>`，被保护对象需继承 `std::hazard_ptr_obj_base`
    
- **Linux 内核正在引入 hazard pointers**：2024 年 9 月 Boqun Feng 等人提交 RFC 补丁，Paul McKenney 和 Neeraj Upadhyay 参与 co-develop ，2026 年 7 月 LWN 报道了 Mathieu Desnoyers 和 Paul McKenney 的新实现
    

**性能数据（来自 Paul 的演讲）**​ ：

|nreaders|atomic refcount|percpu_ref|RCU|hazptr|
|---|---|---|---|---|
|0|10|7|2|9|
|5|150|7|3|9|
|10|250|10|2|9|
|15|400|8|2|9|
|20|500|8|2|9|
|25|600|9|2|9|
|30|700|9|2|9|
|32|750|9|2|9|

> 💡 **关键观察**：随着读者数增加，atomic refcount 的开销**线性恶化**（10 → 750），而 hazard pointer 和 RCU 保持平稳（~9）。这再次印证——**引用计数的原子操作是多核扩展性的杀手**。

### 9.1.3 支持引用计数的 Linux 原语

**原文骨架**：Linux 内核提供了多种引用计数原语，每种对应 9.1.1 中的不同变体 。

**核心原语**​ ：

- **`kref`**：经典引用计数，`kref_get()` / `kref_put()`
    
- **`refcount_t`**：带溢出保护的引用计数，`refcount_inc()` / `refcount_dec_and_test()`
    
- **`percpu_ref`**：每 CPU 引用计数，读者侧无原子操作（类似第 5 章统计计数器的思想），适用于**读多写少且计数值近似**的场景
    
- **`atomic_t` / `atomic_long_t`**：底层原子整数，可手动构建引用计数
    

**🎯 第一性洞见**：`percpu_ref` 是引用计数与第 5 章"统计计数器"思想的完美结合——**读者侧零原子操作（写本地 per-CPU 副本），写者侧/汇总时才原子化**。这再次印证了全书的主题——**"分割数据 + 复制"是消除同步成本的根本手段**。

**工业洞见**：

- **`percpu_ref` 的性能数据**（上表）：在 32 个读者时仅开销 9，与 RCU 持平，远优于 atomic refcount 的 750——这就是"per-CPU 化"的威力。
    
- **代价**：`percpu_ref` 的计数值是**最终一致的近似值**，不支持精确的 `dec_and_test()` 语义（除非切换到原子模式）。因此**它适用于"引用计数用于生命周期管理"而非"引用计数用于精确判断"**的场景。
    

### 9.1.4 计数优化

**原文骨架**：汇总引用计数的优化方向——**per-CPU 化、批量更新、选择合适的屏障语义**。

**我的洞见**：这一节是 9.1 全节的收束——引用计数的优化路径与第 5 章计数器的优化路径**完全一致**：

- 全局原子计数 → 慢，不可扩展
    
- per-CPU 分片 + 定期汇总 → 快，可扩展（如 `percpu_ref`）
    
- 危险指针 → 读者侧零写，更极致的优化
    

**工程准则**：**当你发现引用计数成为瓶颈时，不要盲目优化原子操作本身，而要问"能否 per-CPU 化"或"能否用危险指针/RCU 替代"**。

## 9.2 顺序锁（Sequence Locking）

**原文骨架**：顺序锁（seqlock）的核心思想是——**写者独占，读者无锁但需检测写者操作并重试**。

**工作机制**：

```
// 写者
write_seqlock(&seqlock);
// ... 修改数据 ...
write_sequnlock(&seqlock);

// 读者
unsigned seq;
do {
    seq = read_seqbegin(&seqlock);  // 读取序列号
    // ... 读取数据 ...
} while (read_seqretry(&seqlock, seq));  // 若期间有写者，则重试
```

**第一性解读**：

顺序锁的本质是**"乐观读"**——读者假设"读期间不会有写者"，通过序列号检测假设是否成立，不成立则重试。

**🎯 顺序锁的四大局限**（perfbook 明确指出）：

1. **限制更新**：顺序锁不适合频繁更新的场景——写者独占，读者重试风暴会拖垮系统。
    
2. **不允许遍历可能被释放的指针**：顺序锁保护的是"小且静态的数据"（如配置参数、时间戳），**不保护指针引用**——因为如果写者替换了指针指向的对象并释放旧对象，读者重试前可能访问已释放内存 。
    
3. **写者可能饿读者**：顺序锁允许写者延后读者，但反之不行。在写密集型负载下，读者可能饿死 。
    
4. **需要与 RCU/危险指针配合使用**：顺序锁检测并发更新，但安全引用获取需要 RCU 或危险指针的配合 。
    

**工业映射**：

- **Linux 内核 `seqlock_t`**：`write_seqlock()` / `read_seqbegin()` / `read_seqretry()`
    
- **典型用例**：`jiffies`（系统时钟滴答）、系统时间、`gettimeofday()` 的实现——这些是"小、静态、读多写少且写者极少"的数据，完美适配顺序锁
    
- **Linux 内核 `ktime_get()`**：使用 seqlock 保护时钟数据
    

**第一性洞见**：顺序锁是**"小数据、极高频读、极少写"场景的专属武器**。它的reader 开销极低（仅两次序列号读取 + 内存屏障），但代价是"不允许保护指针遍历"和"写者可能饿读者"。**它是 RCU 的"轻量版前身"**——RCU 解决了顺序锁的指针安全问题，但代价是内存占用无界。

## 9.3 读-复制-更新（RCU）

这是全章的**技术巅峰**，也是 Paul McKenney 本人主导设计并持续维护的同步机制。RCU 于 2002 年 10 月加入 Linux 内核 。

### 9.3.1 RCU 介绍

**原文骨架**：RCU 是一种同步机制，专为**读多写少（read-mostly）**的数据结构设计，目的是实现高性能和可扩展的低开销读取 。

**第一性解读**：

RCU 的核心特性 ：

- **读者零开销或近乎零开销**：在某些实现中（非抢占内核），RCU 读者侧原语的开销为零
    
- **延后回收**：内存或资源在**所有先存读者完成**后才回收
    
- **多版本共存**：更新者可能维护数据的多个版本，确保读者始终看到一致的视图
    

**🎯 第一性洞见**：RCU 的本质是**"在数据所有权（第 8 章）的基础上引入时间维度"**——通过"复制新版本 + 保留旧版本直到宽限期结束"，让读者和写者真正并发执行。这是为什么 Paul 说 RCU 是"数据所有权在时间维度的延伸"。

**RCU vs 其他技术的核心差异**（perfbook 表 9.5 精华）：

|维度|引用计数|危险指针|顺序锁|RCU|
|---|---|---|---|---|
|存在性保证|是|是|否|是|
|读者开销|高（原子 RMW）|无（但有重试）|两次屏障|**零或近零**​|
|内存占用|有界|有界|有界|**无界**（除非节流更新）|
|读者前进保证|无锁|无锁|阻塞|有界等待自由|
|引用获取|可能失败|可能失败|不安全|**不会失败**​|
|自动回收|是|否|N/A|否|
|代码行数|94|79|79|73|

**这张表是全章最具决策价值的内容**——它告诉你：没有"最佳"技术，只有"最适合当前工作负载"的技术。

### 9.3.2 RCU 基础（RCU Fundamentals）

**原文骨架**：RCU 由**三大基础机制**构成 ：

#### 机制一：发布-订阅（Publish-Subscribe）—— 用于插入

**核心原语**：`rcu_assign_pointer()`

```
// 不安全写法：编译器和 CPU 可能重排初始化与指针赋值
p->a = 1;
p->b = 2;
p->c = 3;
gp = p;  // 并发读者可能看到未初始化的 gp->a/b/c

// 安全写法：rcu_assign_pointer 封装了内存屏障
p->a = 1;
p->b = 2;
p->c = 3;
rcu_assign_pointer(gp, p);  // 保证: 指针发布前，数据已完全初始化
```

**第一性解读**：`rcu_assign_pointer()` 的核心是**release 语义的内存屏障**——确保在指针发布之前，所有数据初始化已完成且对其他 CPU 可见。这呼应了第 3 章的内存屏障知识。

#### 机制二：等待先存读者（Wait for Pre-Existing Readers）—— 用于删除

**核心原语**：`synchronize_rcu()`

```
// 删除流程
list_del(&old->list);           // 1. 从链表摘除
synchronize_rcu();              // 2. 等待所有先存读者完成（宽限期）
kfree(old);                     // 3. 安全释放
```

**第一性解读**：`synchronize_rcu()` 等待一个"宽限期（Grace Period）"——即**所有在 `synchronize_rcu()` 调用前开始的 RCU 读者都已完成**。这是 RCU 的"魔法"所在。

**宽限期检测的核心机制——静止状态（Quiescent State）**：

- 在非抢占内核中，一个简单的静止状态是"上下文切换"——因为 RCU 读者必须禁用抢占，所以当 CPU 发生上下文切换时，可以确定该 CPU 上**没有 RCU 读者正在运行**​
    
- **QSBR（Quiescent-State-Based Reclamation）**：基于静止状态的回收机制
    

#### 机制三：维护多版本（Maintain Multiple Versions）—— 支持并发插入和删除

**核心思想**：更新者保留旧版本数据，直到宽限期结束后才回收。这使得读者在宽限期内仍能访问旧版本，与写者的新版本并发存在。

**🎯 第一性洞见**：RCU 的三大机制构成了一个**完整的"时间维度分割"方案**：

- **空间维度分割**（第 8 章数据所有权）：不同线程拥有不同数据 → 零同步
    
- **时间维度分割**（RCU）：同一数据在不同时间点有多个版本 → 读者访问旧版本，写者创建新版本，两者并发无冲突
    

**RCU 读者侧原语**：

```
rcu_read_lock();           // 进入 RCU 读侧临界区（通常仅禁用抢占）
p = rcu_dereference(gp);   // 安全订阅：获取 RCU 保护的指针
// ... 使用 p ...
rcu_read_unlock();         // 退出 RCU 读侧临界区
```

**关键认知**：在非抢占内核中，`rcu_read_lock()` / `rcu_read_unlock()` 的开销**为零**——它们只是禁用/启用抢占，不产生任何原子操作或内存屏障 。这就是为什么 RCU 读者的性能可以"与单线程代码执行相同的指令" 。

### 9.3.3 RCU 用法

**原文骨架**：RCU 在 Linux 内核中广泛应用于各种读多写少的数据结构。

**典型用例**：

1. **路由表 / 网络过滤规则**：读多写少，查找频繁，更新罕见
    
2. **系统调用表**：极少修改，高频调用
    
3. **模块列表**：模块加载/卸载罕见，遍历频繁
    
4. **inode 缓存**：文件访问读多写少
    
5. **设备树**：硬件枚举后基本静态
    

**🎯 第一性洞见**：RCU 的适用条件是严格的——**读多写少 + 读者临界区短 + 可接受延后回收**。违反任何一个条件，RCU 的优势都会大打折扣：

- 写多 → 宽限期频繁，内存占用膨胀
    
- 读者临界区长 → 宽限期拉长，内存占用无界
    
- 不能延后回收 → RCU 的基本前提被破坏
    

**RCU 与引用计数的组合使用**（perfbook 的重要洞见）：

> "这种内存占用和获取失败之间的张力，有时通过在 Linux 内核中组合使用 RCU 和引用计数器来解决。RCU 用于短生命周期的引用，这意味着 RCU 读侧临界区可以很短。这些短的 RCU 读侧临界区反过来意味着相应的 RCU 宽限期也可以很短，从而限制内存占用。对于少数需要更长生命周期引用的数据元素，使用引用计数。"

**这是工业界最重要的 RCU 使用模式**——**RCU 处理"短引用"（查找、遍历），引用计数处理"长引用"（跨函数、跨线程传递对象）**。两者的组合既获得了 RCU 的读者零开销，又避免了 RCU 的内存无界问题。

**工业映射**：

- **Linux 内核**：RCU 保护的数据结构数量已超过所有其他锁的总和
    
- **C++ 用户态 RCU**：`liburcu` 库提供了用户态 RCU 实现
    
- **我的判断**：今天写 C++ 高性能服务的工程师，遇到"读多写少"的数据结构（配置管理、路由表、规则引擎、缓存元数据），**首选方案应是"RCU + 引用计数"组合**，而非传统的读写锁。
    

### 9.3.4 Linux 内核中的 RCU API

**原文骨架**：RCU 提供了一系列 API，每种针对不同的使用场景 。

**核心 API 总表**​ ：

|API|用途|
|---|---|
|`rcu_read_lock()`|开始 RCU 读侧临界区|
|`rcu_read_unlock()`|结束 RCU 读侧临界区|
|`rcu_dereference()`|安全加载 RCU 保护的指针|
|`rcu_assign_pointer()`|安全更新 RCU 保护的指针|
|`synchronize_rcu()`|等待所有先存 RCU 读者完成（宽限期）|
|`call_rcu()`|宽限期后调用指定回调函数|

**RCU 的多种"风味"（Flavors）**：

|Flavor|特点|用途|
|---|---|---|
|**RCU（经典）**​|读者禁用抢占|内核核心数据结构|
|**SRCU（Sleepable RCU）**​|读者可休眠|读者需要调用可能休眠的函数|
|**Tasks RCU**​|等待任务切换|特定内核子系统|
|**QSBR**​|用户态静止状态回收|用户态 RCU 实现|

**第一性洞见**：RCU 的"风味"多样性反映了**"不存在通用最优 RCU"**——不同场景需要不同的宽限期检测机制和读者侧语义。这是第 2 章"铁三角"在 RCU 层面的体现：性能、生产率、通用性不可兼得，因此 RCU 提供多种变体让使用者按需选择。

### 9.3.5 "玩具式"的 RCU 实现（"Toy" RCU Implementation）

**原文骨架**：Paul 在书中给出了一个**简化版的 RCU 实现**，用于教学目的，帮助读者理解 RCU 的核心机制。

**核心组成**：

1. **读者侧**：`rcu_read_lock()` / `rcu_read_unlock()` 通过禁用/启用抢占实现
    
2. **宽限期检测**：基于"静止状态"——当所有 CPU 都发生了上下文切换，即可确定宽限期结束
    
3. **`synchronize_rcu()`**：等待所有 CPU 经历至少一个静止状态
    
4. **`call_rcu()`**：将回调函数排入队列，在宽限期结束后调用
    

**🎯 第一性洞见**：玩具式 RCU 实现的价值在于——**它揭示了 RCU 的"魔法"本质上是"等待所有 CPU 确认没有读者"**。这个"确认"机制可以是：

- 上下文切换（非抢占内核）
    
- 静止状态报告（QSBR）
    
- 显式静止状态标记（如 `rcu_quiescent_state()`）
    

理解玩具实现，就理解了 RCU 的"灵魂"——**宽限期检测是所有 RCU 实现的核心难点**，也是不同 RCU 风味之间最大的差异点。

### 9.3.6 RCU 练习

**原文骨架**：Paul 在书中提供了多个 RCU 练习，帮助读者巩固理解。这些练习涵盖了：

- RCU 链表的基本操作（插入、删除、遍历）
    
- RCU 与引用计数的组合使用
    
- RCU 在嵌套数据结构中的应用
    
- RCU 宽限期的理解
    

**我的洞见**：这一节的存在本身就说明了 RCU 的学习曲线——**RCU 看似简单（读者零开销），但正确使用需要深入理解宽限期、内存屏障、多版本共存等概念**。这也是为什么很多工程师"听说过 RCU 但用不对 RCU"。

## 9.4 如何选择？（Which to Choose?）

**原文骨架**：perfbook 表 9.5 给出了四种技术的系统对比 。

**我的决策框架（基于表 9.5 + 工业经验）**：

### 决策树

**第一问：数据结构是否"读多写少"？**

- 否 → RCU、危险指针、顺序锁都不适合，回到锁（第 7 章）或数据所有权（第 8 章）
    
- 是 → 进入下一问
    

**第二问：读者侧开销是否是瓶颈？**

- 否（读者少或并发度低）→ **原子引用计数**即可，简单且自动回收
    
- 是（高并发读者）→ 进入下一问
    

**第三问：内存占用是否敏感？（能否容忍无界内存占用）**

- 是（内存受限环境）→ **危险指针**：有界内存占用，读者侧无写
    
- 否（内存充足）→ 进入下一问
    

**第四问：数据是否"小且静态"？是否只需要保护值而非指针？**

- 是 → **顺序锁**：读者开销极低，但写者可能饿读者
    
- 否（需要保护指针引用）→ 进入下一问
    

**第五问：能否接受延后回收？读者临界区是否短？**

- 是 → **RCU**：读者零开销，但需要管理宽限期和内存占用
    
- 否（需要立即回收或长读者临界区）→ **危险指针**或**RCU + 引用计数组合**
    

### 工业经验法则

|场景|推荐方案|
|---|---|
|通用对象生命周期管理|引用计数（`kref` / `refcount_t`）|
|高并发读多写少 + 内存敏感|危险指针（C++26 `std::hazard_pointer`）|
|小静态数据（配置、时间戳）|顺序锁（`seqlock_t`）|
|路由表、规则表、缓存元数据|RCU + 引用计数组合|
|极致性能 + 内存充足|RCU（经典或 SRCU）|

> 💡 **核心洞察**：Linux 内核的真实实践是**"RCU 处理短引用 + 引用计数处理长引用"**——这是经过 20 年工业验证的最佳组合模式。它既获得了 RCU 的读者零开销，又用引用计数解决了 RCU 的内存无界问题。

## 9.5 更新端怎么办（What About Updates?）

**原文骨架**：延后处理技术最直接适用于**读多写少**的场景。这引出一个自然的问题——**"更新端怎么办？"**​ 毕竟，提升读者的性能和可扩展性固然好，但我们也希望写者同样具备高性能和可扩展性 。

**第一性解读**：

这一节是 Paul 对"延后处理技术偏袒读者"的诚实反思：

> ⚠️ **RCU、危险指针、顺序锁都是以"读者极致优化"为代价，将复杂性推给更新端**。这意味着：
> 
> - RCU 写者需要等待宽限期（延迟回收）
>     
> - 危险指针写者需要扫描所有 hazard pointer slot
>     
> - 顺序锁写者需要独占且可能饿读者
>     

**更新端的优化策略**：

1. **批处理更新**：将多个更新操作合并，减少宽限期/扫描的次数
    
2. **读者-写者角色分离**：某些 CPU/线程专门做更新，其他专门做读取（数据所有权思想的应用）
    
3. **RCU 组合其他机制**：对于需要高并发更新的数据结构，可以结合使用 RCU 和其他同步机制（如每 CPU 缓存、读写锁等）
    
4. **更新端的"玩具式"实现**：理解 RCU 更新端的核心——`synchronize_rcu()` 等待宽限期，`call_rcu()` 延后回调
    

**🎯 第一性洞见**：这一节揭示了延后处理技术的**根本权衡**——**读者和写者之间的性能权衡是不对称的**。你不能既要读者零开销，又要写者零延迟。工业实践中：

- **读者极致优化**​ → RCU（代价：写者延迟回收）
    
- **平衡读写**​ → 读写锁（代价：读者间不完全并发）
    
- **写者极致优化**​ → 数据所有权 + 消息传递（代价：架构复杂）
    

**工业映射**：

- **Linux 内核路由表更新**：使用 RCU 保护，更新端通过 `call_rcu()` 延后释放，批处理多个路由更新
    
- **配置热更新**：使用 RCU 发布新配置，旧配置在所有读者退出后回收
    
- **我的判断**：当更新端成为瓶颈时，正确的做法**不是放弃 RCU**，而是**结合数据所有权思想**——让更新操作本身也并行化（如多个更新线程各负责一部分数据），或引入批处理机制。这是 9.5 节的真正启示。

## 本章总览：贯穿全章的第一性原理总结

读完第 9 章，我认为 Paul 真正想建立的认知框架可以压缩为**三句话**：

1. **延后处理的本质是"用时间换空间/用空间换时间/用重试换无锁"**。四种技术构成了一个完整的光谱：
    
    - **引用计数**：用原子操作换自动回收（简单但慢）
        
    - **危险指针**：用重试换无锁读者（复杂但可扩展、内存有界）
        
    - **顺序锁**：用乐观读换读者零开销（极快但局限多）
        
    - **RCU**：用延后回收换读者零开销（极致快但内存无界）
        
    
2. **RCU 是"数据所有权在时间维度的延伸"**。第 8 章的数据所有权消除了"空间维度的共享"，RCU 通过"多版本共存 + 宽限期回收"消除了"时间维度的共享"——读者访问旧版本，写者创建新版本，两者真正并发。这是为什么 RCU 读者可以做到零开销。
    
3. **没有"最佳"延后处理技术，只有"最匹配工作负载"的技术**。perfbook 表 9.5 的决策矩阵告诉我们：**读者开销、内存占用、是否存在性保证、是否自动回收——这四维的权衡决定了技术选型**。工业界的最佳实践是**"RCU 处理短引用 + 引用计数处理长引用"的组合**——这是经过 Linux 内核 20 年验证的黄金组合。
    

> 📌 **给工程师的个人判断（2026 年视角）**：
> 
> 第 9 章是全书**最具工业即战力**的章节之一。今天的主流系统软件中，你能看到的延后处理技术应用：
> 
> - **Linux 内核**：RCU 保护的数据结构数量已超过所有其他锁的总和；危险指针正在被引入内核（2024 RFC 补丁，2026 LWN 报道）
>     
> - **C++26 标准**：`std::hazard_pointer` 正式进入标准库
>     
> - **用户态 RCU**：`liburcu` 库成熟可用
>     
> - **高性能服务**：路由表、规则引擎、配置管理、缓存元数据——这些"读多写少"场景的首选应是 RCU + 引用计数组合
>     
> 
> **我的核心建议**：
> 
> 1. **遇到"读多写少"的数据结构，第一选择是 RCU + 引用计数组合**，而非传统的读写锁
>     
> 2. **读者侧追求极致性能 → RCU**；**内存敏感或需要无锁更新 → 危险指针**（C++26 `std::hazard_pointer`）
>     
> 3. **小且静态的数据（配置、时间戳、版本号）→ 顺序锁**
>     
> 4. **通用对象生命周期管理 → 引用计数**（`kref` / `refcount_t` / `std::shared_ptr`）
>     
> 5. **理解 RCU 的三大机制**（发布-订阅、宽限期、多版本）比记忆 API 更重要——理解了机制，你就能在任何环境下正确使用 RCU
>     
> 6. **RCU 不是银弹**：它的代价是"写者延迟回收"和"内存可能无界"。当更新端成为瓶颈时，需要结合数据所有权思想或使用 RCU + 引用计数组合
>     
> 
> Paul 在 2025 年 Kernel Recipes 演讲中强调的"先分割数据和选择复制"——延后处理技术正是这一哲学在"时间维度"的体现。**引用计数是"即时回收"，危险指针是"按需回收"，顺序锁是"乐观读 + 重试"，RCU 是"延后到宽限期后回收"**——这四种回收策略，本质上都是在回答同一个问题：**"何时可以安全释放一个正在被并发访问的对象？"**
> 
> 理解了这个统一问题，你就理解了第 9 章的真正价值——它不仅仅是教你四种技术，而是教你**用"时间"作为并行设计的新维度**。当你掌握了这个维度，很多之前看似无解的并行问题（"如何在高并发读的同时安全删除？"），都会变得清晰可控。
