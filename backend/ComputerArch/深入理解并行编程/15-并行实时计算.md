
# 第 15 章 并行实时计算（Parallel Real-Time Computing）

> 这一章的开场白是 Paul 对"实时"二字最冷静的祛魅——**"实时"并不意味着"快"，它意味着"可预测"。**​ 一个系统可以在 1 微秒内完成 99.99% 的请求，但如果剩下 0.01% 的请求需要 10 秒，那它就不是一个实时系统。反之，一个系统平均响应 100 毫秒、但最坏情况也绝不超过 105 毫秒，那它就是合格的实时系统。
> 
> Paul 在开篇引用了 Derek Will 的定义 ：
> 
> **"A real-time system is one in which the correctness of the system depends not only on the logical result of computations, but also on the time at which those results are produced."**
> 
> （实时系统是这样一种系统：其正确性不仅取决于计算的逻辑结果，还取决于这些结果被产生出来的时间。）
> 
> 这一章的核心命题——**并行与实时看似矛盾（并行追求吞吐，实时追求确定性延迟），但现代多核系统（特别是 Linux 通过 PREEMPT_RT 补丁集提供的硬实时能力）正在让"并行实时计算"成为现实**。Paul 作为 Linux 内核 RCU 子系统的维护者，同时也是实时 Linux（PREEMPT_RT）的关键贡献者，在这一章里把他 20 年的实时内核实战经验倾囊相授。

## 15.1 什么是实时计算（What is Real-Time Computing?）

### 15.1.1 软实时（Soft Real-Time）

**原文骨架**：软实时系统**尽力**在截止时间前完成任务，但偶尔错过截止时间是可接受的——系统不会崩溃，只是服务质量下降。

**典型例子**：

- 多媒体播放：错过一帧会导致画面卡顿，但不会系统崩溃
    
- 网络包转发：偶尔的包延迟会导致吞吐波动，但连接不会断
    
- 游戏物理引擎：偶尔的帧率下降影响体验，但不影响正确性
    

**第一性解读**：

软实时的核心是**统计意义上的时间保证**——"99.9% 的请求在 10ms 内完成"。它关注的是**尾延迟（tail latency）的分布**，而非最坏情况。

**🎯 第一性洞见**：软实时与"高性能"高度相关。一个高吞吐的并行系统，如果尾延迟可控，就能很好地服务于软实时场景。**这正是为什么第 5~10 章的并行优化（消除锁争用、使用 RCU 让读者零开销、per-CPU 计数器）直接服务于软实时**——它们压低了尾延迟。

**工业映射**：

- **CDN 边缘节点**：99 分位延迟 < 50ms 是软实时指标
    
- **在线广告竞价**：100ms 内必须返回结果，否则放弃
    
- **我的判断**：今天 90% 的"实时"业务需求其实是"软实时"——他们要的是"快且稳定"，而非"绝对可预测"。这类需求用标准的并行优化手段（RCU、无锁队列、per-CPU 缓存）就能很好满足。
    

### 15.1.2 硬实时（Hard Real-Time）

**原文骨架**：硬实时系统中，**任何一次**错过截止时间都是**系统故障**——可能导致物理损坏、人员伤亡或任务彻底失败。

**典型例子**：

- 汽车电子：刹车系统的控制循环必须在固定周期内完成，否则刹车失灵
    
- 飞行控制：飞机姿态控制必须在毫秒级完成，否则失控
    
- 工业机器人：机械臂运动控制错过截止时间会导致碰撞
    
- 医疗设备：心脏起搏器的刺激脉冲必须在精确时刻发出
    

**第一性解读**：

硬实时要求**最坏情况执行时间（WCET, Worst-Case Execution Time）的可证明上界**。这不是"测试出来"的，而是**通过分析证明的**——因为测试无法覆盖所有调度可能性和所有中断组合。

**🎯 第一性洞见**：硬实时与"并行"存在结构性张力——

- 并行追求**吞吐**（单位时间内完成更多任务）
    
- 硬实时追求**确定性**（最坏情况有可证明上界）
    
- **多核并行引入了不确定性**：缓存一致性流量、NUMA 跨节点延迟、锁争用的不可预测性，都会让 WCET 分析变得极其困难
    

这正是为什么硬实时系统传统上用**单核 + 静态调度**，而非多核并行。但现代需求（自动驾驶、无人机）既需要实时又需要算力，推动了"并行实时"的发展。

**工业映射**：

- **AUTOSAR Adaptive Platform**：汽车行业的硬实时标准，基于 POSIX + 实时扩展
    
- **NASA JPL 飞行软件**：火星探测器使用 VxWorks（硬实时 RTOS）+ 形式化验证
    
- **Linux PREEMPT_RT**：将 Linux 内核转化为硬实时操作系统（见 15.4.1）
    

### 15.1.3 现实世界的实时（Real-World Real-Time）

**原文骨架**：Paul 指出——**现实世界的实时系统是软硬混合的**。很少有系统纯粹是"硬实时"或"软实时"，而是存在一个**关键性谱系**。

**关键性谱系（Criticality Spectrum）**​ ：

|关键性级别|错过截止时间的后果|典型系统|
|---|---|---|
|**安全关键（Safety-Critical）**​|人员伤亡/物理损坏|刹车、飞行控制、起搏器|
|**任务关键（Mission-Critical）**​|任务彻底失败|卫星通信、金融交易|
|**业务关键（Business-Critical）**​|重大经济损失|支付系统、广告竞价|
|**质量关键（Quality-Critical）**​|用户体验下降|视频流、社交 feed|
|**尽力而为（Best-Effort）**​|几乎无影响|后台批处理、日志归档|

**第一性解读**：

现实世界的系统往往是**混合关键性（Mixed-Criticality）**的——同一个系统里，刹车控制是安全关键（硬实时），仪表盘渲染是质量关键（软实时），日志记录是尽力而为。

**🎯 第一性洞见**：混合关键性系统改变了"实时"的设计范式——

- 不能对所有任务用同一套实时策略（太保守则浪费算力，太激进则风险）
    
- 需要**关键性感知的调度**：高关键性任务优先、低关键性任务可牺牲
    
- **这正是多核并行的用武之地**：将不同关键性的任务隔离到不同 CPU 核，避免低关键性任务干扰高关键性任务
    

**工业映射**：

- **ARM Big.LITTLE / DynamIQ**：大核跑高关键性任务，小核跑低关键性任务
    
- **Linux `SCHED_DEADLINE`**：基于 Earliest Deadline First（EDF）的调度策略，支持任务截止时间保证
    
- **我的判断**：今天自动驾驶、机器人、无人机等系统的核心架构挑战，本质是"混合关键性调度"。Linux PREEMPT_RT + `SCHED_DEADLINE` + CPU 亲和性隔离，是当前工业界最主流的方案。

## 15.2 谁需要实时计算（Who Needs Real-Time Computing?）

**原文骨架**：Paul 列举了需要实时计算的主要领域 。

**核心领域**：

1. **工业控制**：PLC、SCADA 系统、机器人控制
    
2. **汽车电子**：发动机控制、刹车、转向、自动驾驶
    
3. **航空航天**：飞控、卫星、航天器
    
4. **医疗设备**：起搏器、输液泵、手术机器人
    
5. **通信基础设施**：5G 基站、交换机、路由器
    
6. **金融交易**：高频交易（HFT）的订单处理
    
7. **多媒体**：音频/视频处理、直播编码
    
8. **游戏**：物理引擎、网络同步
    

**第一性解读**：

这些领域的共同特征是——**"结果正确但来得太晚"等于"结果错误"**。一个正确但迟到的刹车信号，和一个错误的刹车信号，后果一样严重。

**🎯 第一性洞见**：实时计算的需求正在从"传统嵌入式"向"通用计算"扩散——

- 5G 基站需要 μs 级定时（实时）
    
- 高频交易需要 ns 级时间戳（实时）
    
- 自动驾驶需要 ms 级控制循环（实时）
    
- 即使是 Web 服务，用户也期望"快速且稳定"（软实时）
    

**我的判断**：今天"实时"已经不是嵌入式工程师的专属领域。**任何写服务端代码的工程师，都应该理解软实时的基本概念**——因为"尾延迟优化"本质上是软实时工程。

## 15.3 谁需要并行实时计算（Who Needs Parallel Real-Time Computing?）

**原文骨架**：并行实时计算的需求来自**算力需求与实时约束的叠加**​ 。

**典型场景**：

1. **自动驾驶**：需要实时处理摄像头/激光雷达数据（实时）+ 运行深度学习推理（高算力）
    
2. **无人机**：需要实时飞控（实时）+ 运行视觉 SLAM（高算力）
    
3. **工业机器人**：需要实时运动控制（实时）+ 运行路径规划（高算力）
    
4. **5G 基站**：需要实时调度（实时）+ 运行信号处理（高算力）
    

**第一性解读**：

这些场景的共同点是——**单核算力不足以完成实时任务**。例如，自动驾驶的视觉处理需要 GPU/NPU 级别的算力，但这些算力又必须在严格的实时约束内交付结果。

**🎯 第一性洞见**：并行实时计算的核心挑战是——**在多核/众核系统上，如何同时保证确定性和吞吐量**。这需要从三个层面协同设计：

- **操作系统层面**：实时调度（`SCHED_DEADLINE`、优先级调度）
    
- **并行编程层面**：可预测的同步原语（RCU、无锁队列）
    
- **硬件层面**：CPU 亲和性、NUMA 隔离、中断亲和性

## 15.4 实现并行实时系统（Implementing Parallel Real-Time Systems）

这是全章的**技术核心**。Paul 从操作系统和应用两个层面展开。

### 15.4.1 实现并行实时操作系统（Implementing a Parallel Real-Time Operating System）

**原文骨架**：Paul 深入 Linux PREEMPT_RT 补丁集——它将 Linux 内核转化为硬实时操作系统 。

**Linux 实时化的核心挑战**：

标准 Linux 内核中有大量**不可抢占的代码段**（自旋锁保护的临界区、中断处理程序、软中断），这些代码段的最坏执行时间不可预测，破坏了实时性。

**PREEMPT_RT 的四大关键技术**​ ：

**技术一：可抢占自旋锁（PREEMPT_RT Spinlocks）**

标准内核的自旋锁（`spinlock_t`）在持有期间**禁止内核抢占**。PREEMPT_RT 将自旋锁改为**可抢占的互斥锁**（底层用 `rt_mutex`），使得持有锁的临界区可以被高优先级任务抢占。

**代价**：`rt_mutex` 的获取可能涉及休眠，因此不能用于中断上下文——PREEMPT_RT 通过"线程化中断处理程序"解决（见技术三）。

**技术二：优先级继承（Priority Inheritance）**

当低优先级任务持有高优先级任务所需的锁时，低优先级任务**临时继承**高优先级任务的优先级，防止"优先级反转"导致高优先级任务无限等待。

**经典案例**：1997 年火星探路者（Mars Pathfinder）的优先级反转 bug——启用优先级继承后解决 。

**技术三：线程化中断处理程序（Threaded Interrupt Handlers）**

标准内核的中断处理程序运行在中断上下文中，**不可被调度**。PREEMPT_RT 将大部分中断处理程序改为**内核线程**，使其可以被实时调度器调度。

**收益**：中断处理程序不再"霸占 CPU 直到完成"，而是作为普通任务参与优先级调度。

**技术四：延迟操作（Deferrable Operations）**

将不可抢占的操作（如 `rcu_read_lock()` 临界区、softirq）延迟到**可抢占的上下文**中执行，减少不可抢占代码段的长度。

**🎯 第一性洞见：PREEMPT_RT 的核心哲学是——"让内核中所有代码都可被高优先级实时任务抢占"。**​ 这通过将自旋锁改为互斥锁、线程化中断、延迟不可抢占操作来实现。

**RCU 在实时内核中的特殊处理**​ ：

Paul 作为 RCU 维护者，特别讨论了 RCU 对实时性的影响：

- **`synchronize_rcu()` 可能休眠**：在 PREEMPT_RT 中，`synchronize_rcu()` 内部使用 `wait_for_completion()`，可能休眠——这对实时任务可能是问题
    
- **RCU 宽限期延迟**：RCU 读者可能长时间不退出临界区（虽然罕见），延迟宽限期，间接影响内存回收
    
- **实时 RCU 变体**：Paul 引入了 `rcu_read_lock_rt()` 等实时友好变体，限制 RCU 读侧临界区的最长持续时间
    

**工业映射**：

- **Linux PREEMPT_RT 补丁集**：自 2.6 时代起维护，2024 年起部分功能逐步合入 mainline（如 `PREEMPT_DYNAMIC`）
    
- **RTAI / Xenomai**：Linux 上的硬实时扩展（双内核方案，与 PREEMPT_RT 的单内核方案不同）
    
- **我的判断**：今天需要硬实时 Linux 的工程师，**首选是 PREEMPT_RT**（单内核，与 mainline 兼容性好），其次是 Xenomai（双内核，实时性更强但兼容性差）。
    

**实时调度策略**​ ：

Linux 提供三种实时调度策略：

- **`SCHED_FIFO`**：先进先出实时调度，高优先级任务绝对优先
    
- **`SCHED_RR`**：轮转实时调度，同优先级任务轮转
    
- **`SCHED_DEADLINE`**：基于 EDF（Earliest Deadline First），任务声明周期和截止时间，内核保证可调度性
    

**🎯 第一性洞见**：`SCHED_DEADLINE` 是 Linux 实时调度的现代标准——它基于**可调度性分析**（schedulability analysis），能数学证明一组实时任务是否能在截止时间前全部完成。这是从"经验调优"到"数学保证"的跨越。

**CPU 亲和性与隔离**​ ：

实时系统的关键配置：

```
# 将 CPU 0 隔离给实时任务，不让普通进程和中断使用
isolcpus=0
nohz_full=0
rcu_nocbs=0
```

- **`isolcpus`**：将 CPU 从通用调度器中隔离
    
- **`nohz_full`**：减少隔离 CPU 上的定时器 tick 干扰
    
- **`rcu_nocbs`**：将 RCU 回调 offload 到其他 CPU，减少隔离 CPU 上的 RCU 处理
    

**工业映射**：

- **工业控制计算机**：实时任务绑定到隔离 CPU，中断绑定到其他 CPU
    
- **高频交易**：交易引擎绑定到隔离 CPU，避免 OS 抖动
    
- **我的判断**：今天配置实时 Linux 系统的工程师，**CPU 隔离 + 中断亲和性是必做项**，而非可选项。这是 Paul 在书中反复强调的实践。
    

### 15.4.2 实现并行实时应用（Implementing a Parallel Real-Time Application）

**原文骨架**：Paul 从应用层面讨论了如何编写实时友好的并行程序。

**核心原则**：

**原则一：避免优先级反转**

- 使用优先级继承的锁（`PTHREAD_PRIO_INHERIT`）
    
- 避免在持有锁时执行长耗时操作
    

**原则二：使用实时友好的同步原语**

- **RCU**：读者侧零开销、wait-free，是实时应用的理想选择
    
- **无锁队列**：SPSC（单生产者单消费者）无锁队列是实时应用的标准模式
    
- **避免全局锁**：全局锁的最坏等待时间不可预测
    

**原则三：控制内存分配延迟**

- 实时任务中**禁止动态内存分配**（`malloc`/`free` 可能触发页面错误、锁竞争）
    
- 预分配内存池，实时任务从池中获取
    

**原则四：避免页面错误（Page Fault）**

- 实时任务启动前，`mlockall(MCL_CURRENT | MCL_FUTURE)` 锁定所有内存页
    
- 防止运行时因缺页中断导致的不可预测延迟
    

**原则五：使用 CPU 亲和性**

- 实时任务绑定到隔离 CPU（`sched_setaffinity()`）
    
- 中断亲和性配置（`/proc/irq/N/smp_affinity`）
    

**🎯 第一性洞见：实时应用的本质是"消除一切不可预测的延迟源"。**​ 这包括：

- 锁争用 → 用 RCU/无锁结构消除
    
- 内存分配 → 预分配 + 内存池
    
- 页面错误 → `mlockall` 锁定内存
    
- 中断干扰 → CPU 隔离 + 中断亲和性
    
- OS 调度抖动 → `SCHED_DEADLINE` + 实时优先级
    

**工业映射**：

- **高频交易引擎**：C++ 实现，绑定隔离 CPU，`mlockall` 锁定内存，无锁 SPSC 队列传递市场数据
    
- **自动驾驶中间件**（ROS 2 / Cyber RT）：实时调度 + DDS 通信 + 无锁队列
    
- **我的判断**：今天写实时应用的工程师，**最大的误区是"只关注算法复杂度，不关注延迟源"**。一个 O(1) 的算法如果触发了 `malloc` 或页面错误，其尾延迟可能比 O(n) 的算法更差。实时编程的第一原则是"可预测性优于平均性能"。

## 15.5 实时 VS. 快速：如何选择（Real-Time vs. Fast: How to Choose）

**原文骨架**：Paul 给出了实时与快速（高吞吐）的对比决策框架 。

**核心对比**：

|维度|实时（Real-Time）|快速（Fast/High-Throughput）|
|---|---|---|
|优化目标|最坏情况延迟（WCET）|平均吞吐/平均延迟|
|关键指标|尾延迟（p99.9/p99.99）|吞吐量（ops/sec）|
|可接受偶尔慢|**否**​|是|
|同步原语选择|RCU、无锁、优先级继承锁|普通锁、原子操作|
|内存管理|预分配、内存池、`mlockall`|动态分配可接受|
|调度策略|`SCHED_DEADLINE`/`SCHED_FIFO`|`SCHED_OTHER`（CFS）|
|适用场景|刹车、飞控、起搏器|Web 服务、批处理、数据分析|

**🎯 第一性洞见：实时与快速不是"二选一"的对立，而是"优化目标"的不同。**

- **软实时 ≈ 快速 + 尾延迟控制**：大多数 Web/服务端场景属于此类——既要快，又要稳定
    
- **硬实时 = 确定性 >> 吞吐**：安全关键场景，宁可牺牲 50% 吞吐也要保证截止时间
    

**决策树（我的整理）**：

1. **错过截止时间会导致人员伤亡/物理损坏？**
    
    - 是 → **硬实时**：PREEMPT_RT + `SCHED_DEADLINE` + CPU 隔离 + 内存锁定
        
    - 否 → 进入下一问
        
    
2. **业务对尾延迟敏感（用户可感知卡顿/超时）？**
    
    - 是 → **软实时**：RCU + 无锁队列 + per-CPU 缓存 + 监控 p99.9 延迟
        
    - 否 → 进入下一问
        
    
3. **只需高吞吐，延迟分布不重要？**
    
    - 是 → **快速**：标准并行优化（线程池 + 工作队列 + 普通锁）
        
    - 否 → 重新审视需求
        
    

**工业映射**：

- **硬实时案例**：汽车刹车 ECU（AUTOSAR + OSEK/VDX RTOS）
    
- **软实时案例**：CDN 边缘节点（Nginx + `SCHED_FIFO` + CPU 亲和性）
    
- **快速案例**：Hadoop/Spark 批处理（CFS 调度 + 大线程池）
    

**我的洞见**：这一节是全章的收束，也是 Paul 对"实时"二字的最终祛魅——

> **"实时"不是"快"的同义词。一个系统可以非常快（平均 1μs 响应）但不是实时的（最坏情况 10s）。一个系统可以非常实时（最坏 105ms 且可证明）但不是特别快（平均 100ms）。**
> 
> **选择"实时"还是"快速"，本质是选择"优化尾延迟"还是"优化平均吞吐"。**​ 这个选择应该由业务后果决定，而非技术偏好。

**Paul 的邮件补充**​ ：

Paul 在 LKML 中强调——**"实时 Linux 的目标不是让所有代码都实时，而是让关键任务可预测。"**​ 这与第 6.4 节的"并行快速路径"思想一脉相承——**热路径（关键任务）用激进的实时策略，冷路径（非关键任务）用普通策略**。

## 本章总览：贯穿全章的第一性原理总结

读完第 15 章，我认为 Paul 真正想建立的认知框架可以压缩为**三句话**：

1. **"实时"意味着"可预测"，而非"快"。**​ 实时系统的正确性取决于"结果在何时产生"，而非"结果是否正确"。硬实时要求 WCET 的可证明上界（任何一次超时都是故障），软实时只要求统计意义上的尾延迟控制（偶尔超时可接受）。
    
2. **并行与实时存在结构性张力，但可通过协同设计化解。**​ 多核并行引入的不确定性（缓存一致性流量、NUMA 延迟、锁争用）是实时性的天敌。但通过 CPU 隔离、中断亲和性、RCU/无锁同步、内存预分配等手段，可以在多核系统上实现可预测的实时性。Linux PREEMPT_RT 是这一协同设计的工业级典范。
    
3. **实时应用的第一原则是"消除一切不可预测的延迟源"，而非"优化平均性能"。**​ 锁争用、动态内存分配、页面错误、中断干扰、OS 调度抖动——这些"偶尔发生但代价巨大"的事件，是实时系统的最大敌人。实时编程要求工程师从"关注平均"转向"关注尾延迟"。
    

> 📌 **给工程师的个人判断（2026 年视角）**：
> 
> 第 15 章是全书**最具"现实落点"的章节**——它把前 14 章的所有机制（RCU、数据所有权、无锁结构、CPU 亲和性、内存屏障）统一到了"实时性"这一目标下，告诉你这些机制在实时场景中的真实价值。
> 
> 今天工业界对"实时"的需求正在从传统嵌入式向通用计算扩散：
> 
> |实时类型|典型场景|推荐技术栈|Paul 本章对应|
> |---|---|---|---|
> |**硬实时**​|汽车 ECU、飞控、起搏器|AUTOSAR + 静态调度 / PREEMPT_RT + `SCHED_DEADLINE`|15.4.1|
> |**软实时**​|CDN、高频交易、自动驾驶中间件|RCU + 无锁队列 + per-CPU 缓存 + CPU 隔离|15.4.2|
> |**快速（高吞吐）**​|Web 服务、批处理、数据分析|线程池 + 工作队列 + 普通锁|15.5|
> 
> **我的核心建议**：
> 
> 1. **先判断"实时还是快速"**：用 15.5 节的决策树——安全后果决定硬实时 vs 软实时 vs 快速
>     
> 2. **软实时场景（绝大多数服务端）**：重点优化尾延迟——使用 RCU（读者零开销、wait-free）、无锁 SPSC 队列、per-CPU 计数器。这些正是前 14 章的核心机制在实时场景的应用
>     
> 3. **硬实时场景**：使用 Linux PREEMPT_RT + `SCHED_DEADLINE` + CPU 隔离 + `mlockall` + 内存池。不要自己实现实时调度，使用内核提供的机制
>     
> 4. **实时任务禁止动态内存分配**：预分配内存池，避免 `malloc`/`free` 的不可预测延迟
>     
> 5. **实时任务锁定内存**：`mlockall(MCL_CURRENT | MCL_FUTURE)` 防止页面错误
>     
> 6. **CPU 隔离是必做项**：`isolcpus` + `nohz_full` + `rcu_nocbs`，将实时任务与 OS 干扰隔离
>     
> 7. **理解 RCU 的实时影响**：`synchronize_rcu()` 可能休眠，实时任务应使用 `call_rcu()` 或实时友好的 RCU 变体
>     
> 8. **优先级继承是必须的**：使用 `PTHREAD_PRIO_INHERIT` 属性的锁，防止优先级反转
>     
> 
> Paul 在 2025 年 Kernel Recipes 演讲中强调的"先分割数据和选择复制"——这一章告诉我们：**实时性是"分割"思想的终极应用场景**。将高关键性任务隔离到独立 CPU（空间分割），将实时任务的关键路径与非关键路径分离（时间分割），正是"分割"哲学在实时系统中的体现。而 RCU 的读者 wait-free 特性，使其成为实时应用最理想的同步机制——**这正是 Paul 作为 RCU 维护者 20 年的核心洞见**。
> 
> 这也解释了为什么 Paul 把"实时计算"放在全书靠后的位置——**实时性是对并行系统的最高要求，它需要前 14 章所有机制的综合运用**。没有对锁、RCU、数据所有权、内存屏障、NBS 的深入理解，就无法正确设计并行实时系统。第 15 章不是"新增一个机制"，而是"用前 14 章的机制解决实时这个最高难度的并行问题"。
> 
> 这一章留给工程师的最宝贵财富是——**"快"与"实时"是两个不同的优化目标，选择哪个应该由业务后果决定，而非技术偏好**。当你下次面对"要不要做实时优化"的决策时，先问自己：**"如果这次操作慢了 100ms，会发生什么？"**​ 答案会告诉你一切。
