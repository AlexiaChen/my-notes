## 数据复制

## 一、本章在全书知识地图中的坐标

如果第3章解决了"数据落在单台机器的磁盘上长什么样"，那么**第5章解决的是"同一份数据落在多台机器的磁盘上，如何保持合理的一致"**。

这是一个分水岭章节。从前两章（数据模型、存储引擎）开始，我们一直在讨论**单机**视角；从第5章开始，我们正式进入**分布式**视角——网络会出现分区、节点会失效、时钟会漂移、消息会乱序。**复制是分布式系统"可靠性"的工程实现**，也是后续所有章节（分区 Ch6、事务 Ch7、分布式事务 Ch9）的物理基础。

本章与全书的因果链：

- **↩️ 第1章 R-S-M 三角**：复制直接服务于**可靠性**（容错、高可用）和**可扩展性**（读吞吐扩展、就近低延迟）；但复制也引入了**可维护性**挑战（运维复杂度、冲突处理）
    
- **↩️ 第3章 存储引擎**：复制的底层就是 WAL/binlog 的传输——这正是第3章 B-Tree 中 WAL 的另一个身份
    
- **↩️ 第4章 编码与演化**：复制的数据流中，编码格式必须向前向后兼容，否则滚动升级会变成灾难
    
- **➡️ 第6章 分区**：复制与分区是正交的两个维度——"复制=相同数据的多副本，分区=不同数据的多子集"，真实的大规模系统通常是两者的组合
    
- **➡️ 第7、9章 事务与共识**：复制本质上是"多副本状态机"问题，而状态机的正确性最终要靠共识算法（Raft/Paxos）来保证

## 二、第一性原理：为什么需要复制？

Kleppmann 开宗明义——复制（Replication）的定义是"在多台机器上保存相同数据的副本"，它服务于三个核心目标：

|目标|物理动机|
|---|---|
|**高可用性（Availability）**​|单节点故障不应导致全系统停止|
|**读吞吐扩展（Read Throughput）**​|多个副本分担读请求|
|**延迟优化（Reduced Latency）**​|数据放到离用户地理位置更近的地方|

**第一性原理洞见**：复制的本质是用**空间（多份存储）换时间（可用性+性能）**。但天下没有免费的午餐——多份副本意味着"写操作必须传播到多个节点"，而传播过程受限于网络物理约束（延迟、丢包、分区）。

> 🔥 **我的理解**：复制的根本难题可以用一句话概括——**"如何在不可靠的网络上，维持多份副本之间'足够一致'的状态"**。这个"足够"二字，是整个分布式系统的灵魂拷问：强一致会牺牲可用性，最终一致会牺牲用户体验。本章的全部内容，都是在"一致性光谱"上寻找不同业务场景下的最优落点。

## 三、三种复制范式：从集权到无政府

Kleppmann 将复制分为三种范式，它们之间不是并列关系，而是**"一致性 vs 可用性 vs 复杂度"这个三角上的不同落点**：

```
强一致 + 简单
            │
            ▼
     ┌──────────┐
     │ 单主复制  │ ← 集权：一个leader说了算
     └──────────┘
          │
          │ 牺牲强一致，换取写可用性
          ▼
     ┌──────────┐
     │ 多主复制  │ ← 民主：多个leader，冲突需解决
     └──────────┘
          │
          │ 牺牲简单性，换取极致可用性
          ▼
     ┌──────────┐
     │ 无主复制  │ ← 无政府：任意节点可写，quorum+冲突合并
     └──────────┘
        最终一致 + 高可用
```

### 3.1 单主复制（Single-Leader）：集权模式

**核心规则**：一个节点被指定为 leader，所有写请求必须经过它；其他节点是 follower，通过复制日志（replication log）按顺序应用 leader 的写入。

**为什么单主复制是工业界默认选择？**​ 因为它把"分布式系统的根本难题——写入顺序"中央集权化了：leader 决定写入顺序，follower 按相同顺序应用。这消除了并发写入的冲突问题。

#### 同步 vs 异步 vs 半同步

这是单主复制中第一个关键权衡：

|模式|行为|优势|代价|
|---|---|---|---|
|**同步（Synchronous）**​|Leader 等待 follower 确认后才返回客户端|数据零丢失，follower 与 leader 强一致|任一 follower 故障 → 整个写阻塞|
|**异步（Asynchronous）**​|Leader 立即返回，后台传播|写入永不被 follower 拖慢|Leader 崩溃可能丢失未复制的写入|
|**半同步（Semi-synchronous）**​|至少一个 follower 同步确认，其余异步|平衡点：保证至少2副本有数据|配置复杂|

**工业现实**：完全同步在工业界几乎不可用（任何一个 follower 抖动都会导致全系统停写）；完全异步在 leader 故障时有数据丢失风险；**半同步是主流选择**——如 MySQL 的 `rpl_semi_sync`。

#### 复制日志的三种实现（呼应第3、4章）

|实现方式|机制|优缺|
|---|---|---|
|**基于语句（Statement-based）**​|主节点把 SQL 语句发送给从节点执行|简单，但 `NOW()`、`AUTO_INCREMENT` 等非确定性函数会导致不一致|
|**基于 WAL（预写日志）**​|物理复制磁盘页的变化|与存储引擎紧耦合，版本升级困难（呼应第3章 WAL 机制）|
|**基于行（Row-based / 逻辑日志）**​|复制"对某行的插入/更新/删除"逻辑记录|与存储引擎解耦，是逻辑日志（呼应第4章编码演化）|

**🔥 洞见**：现代工业系统（MySQL binlog row format、PostgreSQL logical replication、MongoDB oplog）普遍选择**基于行的逻辑日志**——因为它既避免了语句复制的非确定性问题，又解耦了存储引擎（可以独立升级主从版本的存储格式）。这正是第4章"编码与演化"理念在复制层的落地。

#### 新 follower 的上线：不停机追赶

设置新 follower 不能简单拷贝文件——因为数据库在持续写入。标准流程：

1. 对 leader 数据库做**一致性快照**（不需要锁全库）
    
2. 将快照拷贝到新 follower
    
3. follower 连接 leader，**请求快照时间点之后的所有变更**（通过复制日志的精确位置）
    
4. 应用完积压日志后，follower 追平，开始正常接收新写入
    

这个过程正是**CDC（第4章工业实践）的核心机制**——也是 Kafka、Debezium 等系统的底层原理。

#### 节点失效处理

- **Follower 失效**：容易处理。Follower 本地记录已应用的日志位点，恢复后从该位点继续追赶
    
- **Leader 失效**：需要**故障转移（Failover）**：
    
    1. 检测失效（通常通过超时机制）
        
    2. 选举新 leader（某个 follower 被提升）
        
    3. 重新配置系统使所有写入路由到新 leader
        
    

> ⚠️ **脑裂风险（Split Brain）**：如果旧 leader 并未真正死亡（如网络分区），新旧 leader 同时接受写入会导致数据分叉。**这是单主复制最危险的边缘情况**，通常需要 consensus 算法（Ch9 的主题）来避免。

### 3.2 复制滞后：单主复制的阿喀琉斯之踵

异步复制下，follower 必然会滞后于 leader。Kleppmann 指出了三种由于复制滞后导致的异常：

#### 问题1：读己之写（Read-After-Write Consistency）

用户提交数据后立刻刷新页面，请求路由到了尚未追上最新写入的 follower，导致用户"看不到自己刚提交的内容"——**这是最经典、最让用户困惑的异常**。

**解决方案**：

- **关键内容路由到 leader**：如果用户访问的是自己可能修改过的内容，强制从 leader 读；否则从 follower 读
    
- **时间窗口法**：记录用户上次写入时间，在写入后的一段时间内（如1分钟）总是读 leader
    
- **客户端打标法**：客户端在写操作后拿到一个时间戳/版本号，读请求携带该标记，系统确保读到的副本至少包含该标记之后的所有写入
    

#### 问题2：单调读（Monotonic Reads）

用户多次读取，先看到了新值，然后又看到了旧值——产生"时光倒流"的错觉。例如：用户在 follower A 上看到了最新的推文，然后负载均衡器把请求路由到滞后的 follower B，用户看到了旧的推文列表。

**解决方案**：**确保每个用户的请求都路由到固定的副本**（如按用户 ID 哈希到固定 follower）。这样单个用户不会在不同副本间跳跃，单调读自然成立。

#### 问题3：前缀一致读（Consistent Prefix Reads）

因果相关的写入可能以错误顺序到达 follower。例如：用户先发了一条评论，然后回复了某条评论（依赖第一条的存在）。如果这两个写入因为网络原因乱序到达 follower，follower 上会出现"回复了一个不存在的评论"的荒谬状态。

**解决方案**：

- 将因果相关的写入路由到同一个分区/节点（避免跨分片的因果乱序）
    
- 使用**版本向量（Version Vector）**追踪因果依赖（见 3.4 节）
    

> 💡 **洞见**：这三种异常的本质，都是"复制滞后"在不同维度的投影。**它们共同揭示了一个真理：在异步复制的世界里，"一致性"不是系统的默认属性，而是需要应用层精心设计才能获得的奢侈品**。这也是为什么单主复制虽然简单，但在跨区域、高写入并发场景下力不从心——催生了多主复制。

### 3.3 多主复制（Multi-Leader）：民主模式

**核心规则**：允许多个节点同时接受写请求，每个节点既是 leader 又是其他节点的 follower。

#### 适用场景

多主复制不是为了"更酷"，而是为了解决单主复制在特定场景下的力不从心：

1. **多数据中心部署**：每个数据中心有一个 leader，本地写入低延迟，跨数据中心异步复制
    
2. **离线客户端**：如手机 App，用户在没有网络时也能写入本地，联网后同步到服务端
    
3. **协同编辑**：如 Google Docs，每个用户的光标位置是一个"写入"，需要合并
    

#### 写冲突：多主复制的原罪

当两个不同的 leader 同时修改同一份数据时，冲突不可避免。Kleppmann 提出了几种收敛策略：

|策略|机制|代价|
|---|---|---|
|**最后写入者获胜（LWW）**​|基于时间戳，后者覆盖前者|**可能丢数据**——如果时钟漂移，一个"更晚的逻辑写入"可能被错误判定为"更早"|
|**副本 ID 优先级**​|给每个副本分配唯一 ID，ID 大的胜出|同样丢数据|
|**值合并**​|把两个值合并（如 "B/C"）|仅适用于可合并的数据类型|
|**自定义冲突解决**​|应用层逻辑决定如何合并|复杂度最高，但最灵活|
|**CRDT（无冲突复制数据类型）**​|数学上保证可自动合并|仅适用于特定数据类型（计数器、集合等）|
|**OT（可执行的转换）**​|协同编辑算法（如 Google Docs 使用）|仅适用于文本/操作序列|

#### 多主复制拓扑

多个 leader 之间如何传播写入？常见拓扑：

|拓扑|结构|问题|
|---|---|---|
|**环形（Circular）**​|A→B→C→A|单点故障阻断整个环；需要标识符防止循环|
|**星形（Star）**​|中心节点转发|中心节点是瓶颈|
|**全连接（All-to-All）**​|每个 leader 直接与其他所有 leader 通信|日志覆盖问题：网络速度不同导致顺序不一致|

**全连接拓扑的日志覆盖问题**是经典坑：客户端 X 的 insert 操作先到达 B leader，客户端 Y 基于该值做了 update 操作也发到 B，但 C leader 接收顺序可能是 update 先到、insert 后到——导致 C 上的 update 找不到目标。**版本向量（Version Vector）是解决这个问题的关键**（见 3.4 节）。

> 🔥 **我的洞见**：多主复制的本质是一场**"写可用性 vs 一致性复杂度"的交易**。它用应用层的冲突解决复杂度，换来了跨区域/离线场景下的写可用性。**但绝大多数业务并不需要多主复制**——它们需要的是"单主复制 + 合理的读写一致性保证"。多主复制是特种兵，不是常规部队。工业界真正广泛采用多主的场景，主要是多数据中心部署（如 Gmail、Salesforce），且通常配合复杂的冲突解决框架。

### 3.4 无主复制（Leaderless）：无政府模式

**核心规则**：放弃 leader 概念，任何副本都可以直接接受写请求。Dynamo、Cassandra、Riak、Voldemort 都属于这一类。

#### Quorum 机制：w + r > n

这是无主复制的数学魔法：

- **n**​ = 副本总数
    
- **w**​ = 写操作需要确认的节点数
    
- **r**​ = 读操作需要查询的节点数
    

**当 w + r > n 时**，读操作查询的节点集合与最近一次成功写入的节点集合**必然重叠**（鸽笼原理）。那个重叠的节点握有最新值，客户端通过版本号就能识别出它。

**常见配置**：n=3, w=2, r=2——容忍 1 个节点不可用，仍能读写。

**可调优**以适应工作负载：

- 写少读多 → w=n, r=1（读极快，但写脆弱）
    
- 写多读少 → w=1, r=n（写极快，但读脆弱）
    
- 均衡 → w=2, r=2（n=3）
    

#### 节点失效与恢复

**写入时失效**：客户端并行写多个副本，只要 w 个成功即可认为写入成功。失效的副本暂时被跳过。

**恢复时的两种修补机制**：

1. **读修复（Read Repair）**：客户端读 r 个节点，发现某些节点返回旧值，则将新值异步写回这些落后节点。适用于读频繁的数据。
    
2. **反熵（Anti-entropy）**：后台进程定期比对副本差异（如通过 Merkle Tree），将缺失的更新补齐。**不保证以特定顺序修复**，但能保证最终一致**。
    

#### 工业深度：Dynamo 风格的完整机制

Amazon Dynamo（以及受其启发的 Cassandra、Riak）的精妙之处远不止 quorum：

|机制|作用|
|---|---|
|**一致性哈希环**​|每个节点负责 key 空间的一段范围，扩缩容只需调整环映射|
|**Hinted Handoff（提示移交）**​|目标副本不可达时，临时写到下一个可用节点，并标记"本应属于 X"；X 恢复后再转发|
|**Sloppy Quorum（宽松 quorum）**​|在节点失效时，w/r 个确认可以来自"临时替补"节点——提升可用性，但**破坏了 w+r>n 的严格保证**​|
|**Vector Clock（版本向量）**​|每个副本和每个主键维护一个版本号向量 `(node_id, counter)`，用于检测并发写入|
|**Merkle Tree**​|用于高效比对副本间的 key 范围差异，反熵时只传输不同部分|

#### 并发写检测与冲突解决

无主复制中没有 leader 来序列化写入，并发冲突是常态。Dynamo 的方案：

1. **Vector Clock 检测并发**：如果两个 vector clock 互不为因果（即无法判断谁先于谁），则为并发写入，需要冲突解决
    
2. **LWW（Last Write Wins）**：基于时间戳，但**时钟漂移可能导致静默丢数据**
    
3. **应用层合并**：如购物车场景，可以将两个并发写入的商品列表合并，而非丢失任何一方
    

> ⚠️ **关键提醒**：w + r > n **不能保证强一致性**：
> 
> - 使用 sloppy quorum 时，w 个写入与 r 个读取可能落在完全不同的节点集合上
>     
> - 两个并发写入先后无法判定，LWW 可能因时钟偏差丢数据
>     
> - 要真正的线性一致性，需要共识算法（Ch9 的主题），而非 quorum
>     

> 🔥 **我的洞见**：无主复制的本质是**"把一致性问题从写入时推迟到读取时"**——写入时不做全局协调（所以写永远成功，只要 w 个节点可达），读取时通过版本号和 quorum 来"拼凑"出最新状态。这种设计的哲学是：**"写可用性"比"强一致性"更重要**。这适用于购物车、点赞、浏览计数等"偶尔冲突合并不会造成灾难"的场景。但对于金融交易、库存扣减等"绝对不能丢写"的场景，无主复制是危险的——这也是为什么银行核心系统至今仍以单主复制为主。

## 四、工业实践：三种范式在真实系统的落地

### 4.1 单主复制的工业王者：MySQL + 半同步复制

MySQL 是全球最广泛使用的单主复制数据库。其典型配置：

- **binlog format = ROW**（基于行的逻辑日志，与存储引擎解耦）
    
- **rpl_semi_sync_master_enabled = ON**（半同步复制）
    
- **一主多从**：主库承担所有写入，从库1同步确认，从库2/3异步，承担读流量
    

**典型应用场景**：电商订单系统、金融交易系统、ERP 等需要强一致性的核心业务。

### 4.2 多主复制的工业代表：Salesforce、Gmail

Salesforce 的多数据中心部署采用多主复制——每个地理区域有一个可写的 leader，区域间异步复制。用户无论身处何地，都能低延迟写入；冲突通过"最后写入者获胜 + 业务层审计"解决。

**关键经验**：多主复制的冲突解决**必须在业务语义层面设计**，而非依赖数据库通用机制。Salesforce 的做法是为每种对象类型定制冲突解决逻辑。

### 4.3 无主复制的工业标杆：Amazon Dynamo 与 Cassandra

Amazon 的购物车服务是 Dynamo 风格无主复制的经典案例：

- **N=3, R=2, W=2**​ 的 quorum 配置
    
- Vector Clock 解决并发写冲突
    
- 购物车合并语义：两个并发添加商品的写入可以合并（"B 和 C 都在购物车里"），而非互相覆盖
    
- **设计哲学**："偶尔的合并冲突，比系统停机更便宜"
    

**携程的工业实践**：受 Dynamo 启发，携程酒店开发了 Hare（多存储介质预定库）和 InfoKeeper（高可用动态信息存储），在国产互联网场景中落地了无主复制。这证明 Dynamo 风格并非 Amazon 专属，而是具有普适工程价值。

### 4.4 现代云数据库的复制演进

值得注意的是，现代云数据库正在模糊三种范式的边界：

- **Amazon DynamoDB**：表面是无主复制，但每个 partition 内部是"1 leader + 2 follower"的单主复制——这是**混合范式**的典型
    
- **Google Spanner**：单主复制 + TrueTime 共识，实现全球强一致
    
- **CockroachDB**：多主复制 + Raft 共识，每个 range 内部是单主，跨 range 是多主
    

> 💡 **洞见**：工业界的发展趋势不是"选一种范式"，而是**"按场景混合多种范式"**。这正是 Kleppmann 全书思想的体现——架构师的核心能力是理解每种范式的权衡，并在系统中组合使用。

## 五、跨章联系：复制是分布式系统的物理基础

回到全书的因果链，复制这一章承上启下：

- **↩️ 第1章 R-S-M**：
    
    - **可靠性**​ ← 复制是容错的核心手段（部分节点故障，系统继续运行）
        
    - **可扩展性**​ ← 读副本分担读流量，地理副本降低延迟
        
    - **可维护性**​ ← 复制引入的复杂度（冲突处理、监控复制滞后、故障转移）是可维护性的重大挑战
        
    
- **↩️ 第3章 存储引擎**：
    
    - 复制的底层是 WAL/binlog 的传输——单主复制的"复制日志"正是 B-Tree WAL 的另一个用途
        
    - LSM-Tree 的 SSTable 文件天然适合复制（不可变文件，易于同步）
        
    
- **↩️ 第4章 编码与演化**：
    
    - 复制的数据流中，编码格式必须向前向后兼容
        
    - 逻辑日志（基于行的复制）与存储引擎解耦，正是编码抽象的胜利
        
    
- **➡️ 第6章 分区**：
    
    - 复制与分区是正交的——真实系统通常是"先分区，再在每分区内复制"
        
    - 分区 + 单主复制 = 每个分区有一个 leader
        
    - 分区 + 无主复制 = Dynamo 风格
        
    
- **➡️ 第7章 事务与第9章 共识**：
    
    - 单主复制的"故障转移"需要共识算法避免脑裂
        
    - 多主复制的"冲突解决"本质上是分布式事务问题
        
    - 无主复制的"quorum + vector clock"是最终一致性的工程实现，但要线性一致性仍需共识

## 六、我的整合洞见：复制范式的第一性原理选择框架

综合全章，我提炼出**复制范式选型的第一性原理决策树**：

```
你的系统首要目标是什么？

├── 强一致性 + 简单性（绝大多数业务）
│     └── 单主复制（半同步）
│         例：订单、支付、用户账户
│
├── 跨区域写可用性 + 可接受冲突
│     └── 多主复制 + 应用层冲突解决
│         例：CRM、邮件、协同编辑
│
└── 极致写可用性 + 冲突可合并
      └── 无主复制（Dynamo 风格）
          例：购物车、点赞、浏览计数
```

**更深层的洞见**：复制范式的选择，本质上是**对"网络分区时该怎么办"的回答**：

|网络分区时的选择|对应范式|CAP 取向|
|---|---|---|
|停止写入，保一致性|单主复制（同步）|CP|
|继续写入，接受冲突|多主/无主复制|AP|

而 **PACELC 定理**比 CAP 更精确地描述了这种权衡：在分区（P）时，选择可用性（A）还是一致性（C）；**即便没有分区（E），仍要在延迟（L）和一致性（C）之间选择**。单主异步复制 = PA/EC（分区时保可用，平时牺牲一致性换低延迟）；单主同步复制 = PC/EC（无论何时都保一致，牺牲延迟）。

> 🔥 **我的核心观点**：**复制不是为了"让数据多一份"，而是为了在"不可靠的网络"和"可靠的系统"之间架桥**。每一种复制范式，都是这座桥的一种设计方案——单主是吊桥（简单但有一根主缆）、多主是斜拉桥（复杂但有多个受力点）、无主是悬浮桥（极致可用但晃动）。**优秀的架构师不是"选最好的桥"，而是"为这条河选最合适的桥"**——河流的宽度（数据量）、水流的速度（写入频率）、通行的负载（一致性要求），决定了桥梁的形态。

## 七、本章小结

### 核心命题回顾

|命题|第一性原理解读|
|---|---|
|复制 = 用空间换时间|多副本换可用性+性能，代价是写入传播的复杂度|
|单主复制是默认选择|中央集权化写入顺序，消除并发冲突，但 leader 是瓶颈|
|异步复制的三种异常|读己之写、单调读、前缀一致读——都是"复制滞后"的投影|
|多主复制解决写可用性|代价是冲突解决复杂度，需要应用层语义参与|
|无主复制的 quorum 魔法|w+r>n 保证读写集合相交，但不保证线性一致性|
|Sloppy quorum 的代价|提升可用性，但破坏 w+r>n 的严格保证|
|Vector Clock 检测并发|每个副本维护版本向量，识别因果依赖|
|三种范式不是互斥而是光谱|工业系统趋向混合范式（如 DynamoDB 的 partition 内单主）|

### 关键术语速查

- **Replication Lag（复制滞后）**：Follower 落后 Leader 的程度，通常用"延迟的写操作数"或"时间差"衡量
    
- **Semi-synchronous Replication（半同步复制）**：至少一个 Follower 同步确认，其余异步
    
- **Read-After-Write Consistency（读写一致性）**：用户总能看到自己的最新写入
    
- **Monotonic Reads（单调读）**：用户不会看到"时光倒流"的旧值
    
- **Consistent Prefix Reads（前缀一致读）**：因果相关的写入按正确顺序被读取
    
- **Quorum（法定人数）**：w+r>n 时读写集合必然重叠
    
- **Hinted Handoff（提示移交）**：目标副本不可达时临时写到替补节点
    
- **Read Repair（读修复）**：读取时发现旧值，异步写回新值
    
- **Anti-entropy（反熵）**：后台进程比对副本差异并修补
    
- **Vector Clock（版本向量）**：`(node_id, counter)` 集合，用于检测并发写
    
- **LWW（Last Write Wins）**：基于时间戳的冲突解决，可能静默丢数据
    
- **CRDT（无冲突复制数据类型）**：数学上保证可自动合并的数据结构

## 八、写给读者的话

第5章最深刻的启示，**不是"三种复制范式有什么区别"，而是一种"分布式思维的觉醒"**。

在单机世界里，"写入"意味着"数据已经安全存储"——这是一个原子操作，要么成功要么失败。但在分布式世界里，"写入"是一个**跨越不可靠网络的传播过程**——你永远无法确切知道"此刻，所有副本是否已经收到了我的写入"。

**这就是分布式系统的根本困境，也是复制这一章的全部意义。**

Kleppmann 通过三种范式告诉我们：**没有"完美的复制"，只有"针对特定业务场景最优的复制"**。单主复制用"中心化"换来了简单性和强一致性；多主复制用"应用层冲突解决"换来了跨区域写可用性；无主复制用"最终一致性"换来了极致可用性。

**优秀的架构师，是那个能在"一致性、可用性、复杂度"这个三角中找到最优平衡点的人**。他理解：

- 对于支付系统，"强一致性"是不可妥协的底线 → 单主复制 + 半同步
    
- 对于购物车，"写可用性"比"强一致性"更重要 → 无主复制 + 合并语义
    
- 对于全球部署的 SaaS，"本地低延迟写入"是核心竞争力 → 多主复制 + 业务层冲突解决
    

> _"Replication is not about having multiple copies of data; it's about making a system reliable despite unreliable networks."_
> 
> 复制不是为了拥有多份数据，而是为了在不确定的网络上构建可靠的系统。

**而这，正是分布式系统设计的灵魂。**
