
# 《数据密集型应用系统设计》第3章 读书笔记

## 一、本章在全书知识地图中的坐标

如果说第2章解决了"数据长什么样"（数据模型），那么**第3章解决的是"数据落在存储介质上时长什么样"**——这是从逻辑世界下沉到物理世界的决定性一步。

Kleppmann 在本章开篇用一个极简数据库（append-only log + 内存哈希表）告诉我们：**一个能用的数据库，核心不过是"顺序写日志 + 内存索引"**。所有复杂的存储引擎，都是在这个朴素原型上的工程演进。

本章与前面的呼应：

- **↩️ 第1章 R-S-M 三角**：存储引擎的选择直接决定可靠性（崩溃恢复机制）、可扩展性（写入吞吐）和可维护性（运维复杂度）
    
- **↩️ 第2章 数据模型**：关系模型的底层是 B-Tree，文档模型的底层是 LSM-Tree，图模型的底层往往是原生图存储或 KV 存储——**数据模型是存储引擎的"上层抽象"**
    
- **↩️ 第4章 编码演化**：SSTable、B-Tree 页、列存块，本质都是"编码后的字节"在磁盘上的组织方式
    

而本章内部有一条清晰的**演进主线**——这是全章最值得品味的"第一性原理"：

> **追加日志 → 哈希索引 → SSTable/LSM-Tree → B-Tree → 列存/OLAP**

每一步演进，都是在解决前一步的某个致命局限。理解这条链，就理解了整个存储引擎设计史的"为什么"。

## 二、第一性原理：存储引擎设计的物理约束

在展开具体数据结构之前，必须先建立两个不可回避的物理事实：

|物理约束|数值量级|设计含义|
|---|---|---|
|顺序磁盘 I/O|比随机 I/O **快几个数量级**​|写优化引擎必须追求顺序写|
|内存访问|比磁盘 **快几个数量级**​|热数据必须留内存，索引结构要紧凑|

**这两个事实，就是存储引擎一切权衡的根源**。LSM-Tree 是为了"把随机写变成顺序写"而生；B-Tree 是为了"用最少的磁盘 I/O 次数定位到数据"而生；列存是为了"分析查询只读取需要的列"而生。

> 💡 **洞见**：评价一个存储引擎，不要看它"是什么结构"，而要看它**在哪个物理约束上做了优化**。所有的"快"和"慢"，都可以在这两个物理事实上找到解释。

## 三、演进主线：从极简数据库到工业级存储引擎

### 3.1 起点：追加日志 + 哈希索引（Bitcask 模型）

最简单的数据库就是**一个只能追加（append-only）的日志文件**。写入 = 追加一行；读取 = 从后往前扫描找最新值。

**问题**：读取太慢——O(n) 全表扫描。

**改进**：在内存里维护一个哈希表，key → 字节偏移量。写入时追加到日志并更新哈希表；读取时通过哈希表直接 seek 到位置。

**这就是 Riak 的 Bitcask 引擎的核心**。

**两个致命局限**：

1. **所有 key 必须能放进内存**（磁盘哈希表不实用）
    
2. **无法做范围查询**（哈希表是无序的）
    

这两个局限，引出了后续的演进。

### 3.2 第一次跃迁：SSTable——让数据"有序"

**核心改变**：段文件中的键值对**按键排序**。这一个改变解锁了三个巨大优势：

1. **合并效率极高**：多个段合并类似归并排序，O(n) 时间完成，且同 key 只保留最新值
    
2. **内存索引可以稀疏**：不需要为每个 key 建索引，每隔几千个 key 记一个偏移量即可，查询时在块内小范围扫描
    
3. **可压缩**：相邻记录分组压缩，减少 I/O
    

**写入流程**（LSM-Tree 的核心）：

```
写入 → 内存 memtable（红黑树/跳表，保持有序）
       ↓ memtable 达到阈值
   刷盘为 SSTable 文件（不可变）
       ↓
   后台 compaction 合并多个 SSTable
```

**读取流程**：先查 memtable，再按从新到旧的顺序查 SSTable，直到命中。

**代表实现**：LevelDB、RocksDB、Cassandra、HBase、Bigtable、InfluxDB。

**🔥 工业级优化：布隆过滤器**

当查询一个**不存在的 key**​ 时，理论上要遍历所有 SSTable 才能确认"没有"。布隆过滤器用概率性数据结构解决这个问题——**"若判断不存在则一定不存在；若判断存在则可能不存在"**，从而避免无意义的磁盘 I/O。

**🔥 两种 Compaction 策略**（这是 LSM 工程实践的精华）：

|策略|机制|适用场景|代表|
|---|---|---|---|
|**Size-Tiered**​|新的小 SSTable 合并到旧的大 SSTable|写吞吐优先|Cassandra 默认、HBase|
|**Leveled**​|按 key 范围拆分成多层，每层比上一层大 10 倍|读性能优先、空间放大低|LevelDB、RocksDB、Cassandra 可选|

### 3.3 第二次跃迁：B-Tree——关系数据库的基石

**核心思想**：将数据库分解为固定大小的**页（page，通常 4KB）**，页之间通过地址引用形成树状结构。

**结构特征**：

- 根页包含 key 和对子页的引用
    
- 每个子页负责一段连续 key 范围
    
- 分支因子通常为几百，**3-4 层就能支撑数十亿行**（4 层 × 4KB × 500 分支因子 = 256 TB）
    
- 查找复杂度 O(log n)
    

**写入时的页分裂**：当页满时，分裂成两个半满页，并更新父页——这保证了树的平衡性。

**崩溃安全机制——预写式日志（WAL）**：

> ⚠️ 页分裂是危险操作：如果在只写了一部分页时崩溃，索引就会损坏。

**解决方案**：所有修改**先追加到 WAL**，再应用到 B-Tree 页。崩溃恢复时重放 WAL。这正是第4章"编码与演化"中 WAL/binlog 的源头——**WAL 是存储引擎的基石，而非存储结构本身**。

**代表实现**：PostgreSQL、MySQL (InnoDB)、Oracle、SQL Server、SQLite——几乎所有关系数据库。

### 3.4 LSM-Tree vs B-Tree：本质权衡

这是本章**最关键的工程决策点**。我把材料中的对比提炼为一张"决策全景图"：

|维度|LSM-Tree|B-Tree|
|---|---|---|
|**写入模式**​|顺序写（memtable 刷盘 + compaction）|原地更新（随机 I/O + 页分裂）|
|**读取模式**​|可能查多次（memtable + 多个 SSTable）|单次树遍历，O(log n)|
|**写放大**​|高（compaction 可能重写数据 5-20 次）|低（但 WAL + 页写至少 2 次）|
|**读放大**​|高（需查多个 SSTable）|低（单条路径）|
|**空间放大**​|较高（多副本并存）|较低（但有碎片）|
|**范围查询**​|好（SSTable 有序）|优秀（原生支持）|
|**事务语义**​|较弱（key 可能在多处）|强（每个 key 唯一位置）|
|**延迟稳定性**​|compaction 可能引起毛刺|稳定|
|**典型场景**​|写密集：时序、日志、事件流|读写均衡：OLTP、范围查询|

**🔥 我的洞见：写放大与读放大的物理权衡**

LSM 的"快写"不是免费的——它把代价转移到了两个地方：

1. **写放大**：同一份数据在 lifetime 内被物理写入磁盘 5-20 次（compaction 重写）
    
2. **读放大**：查询可能要查 memtable + 多层 SSTable
    

这意味着**LSM 对 SSD 寿命的压力更大**（写入次数多），且在某些读场景下延迟不如 B-Tree 稳定。这就是为什么**"高写入"本身不足以成为选择 LSM 的理由**——还要看读模式（点查还是扫描？）、一致性要求（是否需要强事务？）、硬件约束（SSD 耐用性？）。

> 💡 **选型决策树**：
> 
> - 需要 SQL + JOIN + 事务 + 中等写入 → PostgreSQL / MySQL（B-Tree）
>     
> - 写入吞吐是瓶颈（百万级/秒）+ 简单查询 → Cassandra / Scylla（LSM）
>     
> - 嵌入式 KV + 可预测延迟 → RocksDB / LevelDB（LSM）
>     
> - 时间序列 + 低成本保留 → 专用 TSDB（底层 LSM）
>     

### 3.5 其他索引结构：主键之外

除了主键索引，工业系统还需要：

- **二级索引**：支持按非主键列查询
    
- **聚集索引（Clustered Index）**：数据行直接存在索引中（MySQL InnoDB 的主键索引）
    
- **非聚集索引**：索引存储指向数据行的引用或主键值（需要"回表"）
    
- **多列索引（Concatenated Index）**：多列组合成一个 key
    
- **覆盖索引（Covering Index）**：索引本身包含查询所需的所有列，无需回表

## 四、事务处理与分析处理：工作负载决定一切

### 4.1 根本分歧：两类工作负载

Kleppmann 在本章后半段引入了**数据存储的第二个根本性分类**——按工作负载性质划分：

|维度|OLTP（联机事务处理）|OLAP（联机分析处理）|
|---|---|---|
|**目的**​|实时事务管理（销售、更新）|复杂数据分析与报告|
|**数据来源**​|实时当前运营数据|来自 OLTP 的聚合历史数据|
|**数据模型**​|规范化（3NF）|星型/雪花型模式或反规范化|
|**数据量**​|GB 到 TB|TB 到 PB|
|**查询类型**​|简单，带主键或索引过滤|复杂 SELECT，带聚合和 JOIN|
|**操作**​|频繁短时更新|批处理写入，历史数据少改|
|**响应时间**​|毫秒级|秒级到小时级（现代趋近亚秒）|
|**存储布局**​|**行存**（Row-oriented）|**列存**（Column-oriented）|
|**一致性**​|ACID 强一致|最终一致可接受|
|**代表系统**​|Postgres、MySQL、Oracle|ClickHouse、Snowflake、Hive|

### 4.2 行存 vs 列存：布局决定命运

这是 OLTP 与 OLAP 分道扬镳的物理根源。

**行存（Row Store）的逻辑**：

- 一条记录的**所有字段连续存储**
    
- 适合"取完整对象"的场景：读取用户信息、更新订单状态
    
- B-Tree 索引让点查毫秒级返回
    

**列存（Column Store）的革命性**：

- **同一列的所有值连续存储**
    
- 分析查询通常只涉及少数几列（如 `SELECT SUM(order_value) GROUP BY country`），列存只需读取相关列文件
    
- 列内数据类型一致 → **压缩比 5-20×**（delta、dictionary、ZSTD 等编码）
    
- 向量化执行（SIMD）让单核每秒处理数千万行
    

**ClickHouse 官方基准**：ClickBench 42 个分析查询，列存引擎在单节点上 **1-10 秒**完成。如果用 Postgres 跑同样查询？可能需要分钟级甚至更长。

**🔥 工业案例**：LangChain 联合创始人 Ankush Gola 明确表示，他们在 Postgres 上遇到了"高吞吐摄取 + 面向用户的低延迟分析查询"的双重需求，这**自然导向了 OLAP/实时分析数据库**。这正是现代数据架构的典型演进路径——**OLTP 和 OLAP 必须用不同引擎**。

### 4.3 为什么不能用一个数据库同时做 OLTP 和 OLAP？

理论上可以，但实际上：

1. **资源竞争**：长时间运行的分析查询会吃满 CPU/内存/IO，拖垮 OLTP 的实时事务
    
2. **优化方向矛盾**：行存优化点查，列存优化扫描，鱼与熊掌不可兼得
    
3. **数据量级差异**：OLTP 是 GB-TB，OLAP 是 TB-PB，架构设计完全不同
    

这就是为什么现代数据架构普遍采用**"OLTP 主库 + CDC + OLAP 数仓"**的分离架构（这正是第4章 CDC 模式的工业落地）。

### 4.4 数据仓库与星型模式

OLAP 系统的数据建模通常采用：

- **星型模式（Star Schema）**：一个事实表（Fact Table）+ 多个维度表（Dimension Table）
    
- **雪花模式（Snowflake Schema）**：维度表进一步规范化
    

这与第2章"数据模型"形成呼应——**分析场景下的数据模型，是为"聚合查询"优化的，而非为"关系完整性"优化**。

### 4.5 HTAP：试图统一两者的努力

近年来出现了 **HTAP（Hybrid Transactional/Analytical Processing）**​ 产品，试图在一个系统内同时服务 OLTP 和 OLAP：

- **TiDB**：OLTP 侧用行存 + LSM，OLAP 侧用列存 + 向量化
    
- **OceanBase**：LSM 底层的行列混合
    
- **Oracle、SQL Server**：传统强者，兼具两端能力
    

**🔥 我的洞见**：HTAP 不是"消灭了 OLTP/OLAP 的区分"，而是通过**同一份数据的多种物理表示**来同时满足两类需求。这恰恰是本章核心思想的延伸——**存储布局决定性能，所以要用不同的布局服务不同的查询**。HTAP 的本质是"一份逻辑数据，多种物理编码"，这与第4章"编码与演化"的理念一脉相承。

## 六、跨章联系：第3章是"物理层"的奠基

回到全书的因果链：

- **↩️ 第1章 R-S-M**：
    
    - **可靠性**​ ← WAL 机制、compaction 的崩溃恢复
        
    - **可扩展性**​ ← LSM 的写吞吐优势，B-Tree 的读吞吐优势
        
    - **可维护性**​ ← 存储引擎的运维复杂度（compaction 风暴、页分裂、索引膨胀）
        
    
- **↩️ 第2章 数据模型**：
    
    - 关系模型 → B-Tree 为主
        
    - 文档模型 → LSM 为主（但也有 B-Tree，如 MongoDB）
        
    - 图模型 → 原生图存储或 KV 存储（RocksDB 作为嵌入式引擎）
        
    
- **↩️ 第4章 编码与演化**：
    
    - SSTable 中的键值对、B-Tree 页、列存块——都是"编码后的字节"
        
    - WAL 正是 CDC 的数据源（详见第4章笔记）
        
    - 存储格式的演化能力，决定了系统的长期可维护性
        
    
- **➡️ 第5-7章 的伏笔**：
    
    - **复制**：主从复制的底层就是 WAL/binlog 的传输
        
    - **分区**：LSM 的 key 范围分区、B-Tree 的页分裂，都与分区策略深度相关
        
    - **事务**：B-Tree 的"每个 key 唯一位置"天然适合事务；LSM 的"key 多副本"让事务实现更复杂

## 七、我的整合洞见：存储引擎选型的第一性原理

综合全章，我提炼出**存储引擎选型的三个第一性原理**：

### 原理一：物理约束不可违抗

顺序 I/O 永远比随机 I/O 快，内存永远比磁盘快。**任何存储引擎的"快"，都是在某个物理约束上做了极致优化**：

- LSM 优化了"写入是顺序的" → 牺牲了读放大和写放大
    
- B-Tree 优化了"树遍历深度最小" → 牺牲了写入的随机 I/O
    
- 列存优化了"只读相关列" → 牺牲了点查性能
    

### 原理二：工作负载决定架构

没有"最好的存储引擎"，只有"最适合工作负载的存储引擎"。选型时必须问：

1. **读写比例**？写密集 → LSM；读写均衡 → B-Tree
    
2. **查询模式**？点查为主 → B-Tree/Hash；范围扫描 → LSM/B-Tree；聚合分析 → 列存
    
3. **一致性要求**？强事务 → B-Tree；最终一致可接受 → LSM
    
4. **数据量级**？GB-TB → OLTP；TB-PB → OLAP
    

### 原理三：写放大与读放大是零和博弈

LSM 用"后台 compaction"把写放大转移到了后台，但付出了读放大和延迟不稳定性的代价。B-Tree 用"原地更新"保持了读的稳定性，但付出了写路径上随机 I/O 的代价。**这是物理约束下的零和博弈，不存在"既要又要"的银弹**。

> 🔥 **更深层的洞见**：现代存储引擎正在走向**"混合"**——
> 
> - **B-Tree + 自适应哈希索引**：MySQL 8.0 的 AHI 监控热点等值查询，自动建立内存哈希表，某电商实测 QPS 从 8000 提升到 22000
>     
> - **LSM + 布隆过滤器 + 多级 compaction**：Cassandra/Scylla 的标准配置
>     
> - **行列混合（HTAP）**：TiDB、OceanBase
>     
> - **LSM 底层 + 列存上层**：时序数据库、实时数仓
>     

**这种"混合"趋势恰恰是 Kleppmann 全书思想的体现——没有一种技术能解决所有问题，优秀的架构师懂得"按场景组合多种技术"。**

## 八、本章小结

### 核心命题回顾

|命题|第一性原理解读|
|---|---|
|索引是"用写开销换读性能"|每个索引都是一次写放大，所以"过度索引"和"索引不足"一样危险|
|追加日志 → 哈希索引 → SSTable → B-Tree → 列存|每一步都是为了解决前一步的物理局限，是"约束驱动演化"的经典范例|
|LSM 树优化顺序写，B-Tree 优化树遍历|物理约束下的零和博弈：写放大 vs 读放大|
|OLTP 用行存 + B-Tree，OLAP 用列存|工作负载的物理特征（点查 vs 扫描）决定存储布局|
|列存的压缩比 5-20×|同列数据类型一致 → 编码效率极高|
|HTAP 不是消灭区分，而是多物理表示|一份逻辑数据，多种物理编码——与"编码与演化"理念一致|

### 关键术语速查

- **SSTable**：Sorted String Table，键值对按键排序的不可变文件
    
- **Memtable**：内存中的有序结构（红黑树/跳表），LSM 的写入缓冲
    
- **Compaction**：后台合并 SSTable，丢弃过期/删除的值
    
- **Bloom Filter**：概率性数据结构，避免对不存在 key 的无意义磁盘查询
    
- **WAL（Write-Ahead Log）**：预写式日志，B-Tree 崩溃恢复的基石
    
- **Page Split**：B-Tree 页满时的分裂操作，保证树平衡
    
- **Write Amplification**：一次逻辑写入导致多次物理写入（LSM compaction 的典型代价）
    
- **Read Amplification**：一次查询需要多次物理读取（LSM 多 SSTable 查询的典型代价）
    
- **Clustered Index**：聚集索引，数据行直接存在索引中（InnoDB 主键索引）
    
- **Star Schema**：星型模式，OLAP 数仓的标准建模方式

## 九、写给读者的话

第3章最深刻的启示，**不是让你记住 LSM 和 B-Tree 的区别，而是让你建立"物理约束意识"**。

当你面对任何一个存储相关的技术决策时，不要问"哪个更快"，而要问：

1. **这个系统的物理瓶颈在哪里？**（顺序 I/O？随机 I/O？内存容量？网络带宽？）
    
2. **这个存储引擎在哪个物理约束上做了优化？**
    
3. **我的工作负载的物理特征是什么？**
    
4. **两者的匹配度如何？**
    

**优秀的架构师，是那个能在"物理约束"和"工作负载"之间看到本质映射的人**。这也是为什么 Kleppmann 把存储引擎放在"数据模型"之后、"复制与分区"之前——**理解了数据如何落在磁盘上，才能真正理解数据如何在网络中复制和分区**。

> _"Every storage engine is a bet on which physical constraint matters most for your workload."_
> 
> 每个存储引擎，都是一次关于"哪种物理约束对你的工作负载最关键"的押注。

**而你，就是那个下注的人。**
