## 一、本章在全书知识地图中的坐标

如果第5章（复制）和第6章（分区）解决了"数据在分布式环境下的**空间分布**"问题，那么**第7章解决的是"数据在并发与故障环境下的**时间一致性**"问题**。

这是一个分水岭章节。从前两章我们学会了把数据复制到多机、切分到多机；但一旦多个操作并发执行、一旦操作可能中途失败，**"系统状态绝不应该停留在中间状态"**这一朴素诉求变得极其困难。事务，就是数据库系统给出的答案。

本章与全书的因果链：

- **↩️ 第1章 R-S-M 三角**：事务直接服务于**可靠性**（原子性保障部分失败不产生脏数据），但也**损害可扩展性**（强隔离级别降低并发度）和**可维护性**（长事务、死锁、隔离级别误用都是运维噩梦）
    
- **↩️ 第3章 存储引擎**：事务的持久性依赖 WAL（预写日志）；事务的隔离性依赖锁/MVCC/SSI
    
- **↩️ 第5章 复制**：单主复制下事务相对简单；多主/无主复制下，"全局事务"变成分布式事务，需要 2PC 等协议
    
- **↩️ 第6章 分区**：单分区事务是本地事务；**跨分区事务是分布式事务**——这是 SAGA、TCC、2PC 等模式的由来
    
- **➡️ 第9章 共识**：可串行化的极致实现（如 SSI）和分布式事务的正确性，最终都要靠共识算法兜底

## 二、第一性原理：事务到底解决了什么问题？

### 2.1 事务的定义与本质

Kleppmann 给出定义：**事务是将多个读写操作捆绑成一个逻辑单元的机制——要么全部成功提交，要么全部失败中止（abort/rollback）**。

**第一性原理洞见**：事务的本质是**"把并发与故障的复杂性，封装成一个可推理的抽象"**。没有事务时，应用开发者必须自己处理：

- 操作做到一半系统崩溃怎么办？
    
- 两个用户同时修改同一条数据怎么办？
    
- 我读到的数据，在我使用它做决定的瞬间，是不是已经被别人改了？
    

事务把这些"边缘情况"包装起来，让应用层可以**假装**只有一个用户在操作、且操作永远不会中途失败。**这是一种"认知减负"**——事务是数据库送给应用开发者的"单线程幻觉"。

### 2.2 ACID 的真正含义（及一个被误解的字母）

|特性|含义|谁的责任|
|---|---|---|
|**A - 原子性（Atomicity）**​|故障发生时中止事务，丢弃所有已做写入，保证"全有或全无"|数据库|
|**C - 一致性（Consistency）**​|事务前后数据满足应用定义的"不变量"（如转账前后总金额不变）|**应用层**（数据库仅通过 A、I 辅助实现）|
|**I - 隔离性（Isolation）**​|并发事务互不干扰，效果等价于串行执行|数据库|
|**D - 持久性（Durability）**​|事务提交后数据不会因故障丢失|数据库（单节点靠 WAL+刷盘，分布式靠复制）|

> 🔥 **关键洞见**：业界常把 ACID 并列，但 **C（一致性）与其他三个有本质区别**——A、I、D 是数据库自身的机制属性，而 C 是**应用层的责任**。数据库提供的原子性、隔离性、持久性，只是帮助应用达成一致性的工具。换句话说：**一致性不是一个数据库特性，而是一个应用不变量**——"A 有 100 元，B 有 50 元，转账后总和仍为 150 元"这个约束，是业务逻辑，不是数据库自动保证的。

这也是为什么 Kleppmann 在第1章 R-S-M 三角中强调的"可靠性"，在事务层面被拆解为 A、I、D 三个可工程化的子目标——而 C 必须靠开发者自己维护。

### 2.3 单对象事务与多对象事务

事务按涉及对象数量分两类：

- **单对象事务**：单个记录的原子写入（如 Cassandra 的单行原子性）
    
- **多对象事务**：跨多条记录、多个表、多个分区的原子操作
    

**多对象事务才是真正的难点**。外键约束、文档间引用、二级索引——这些都需要"多对象事务防止数据不同步"。

**分布式系统的残酷现实**：许多分布式数据存储系统不支持多对象事务，主要是因为**当数据跨分区时，多对象事务难以正确实现**。这正是第6章分区与本章事务的根本张力——**分区提升了可扩展性，但以牺牲跨分区事务为代价**。

## 三、并发异常：弱隔离级别要防范的"幽灵"

多个事务并发执行时，如果不加限制，会出现一系列异常。Kleppmann 系统化地梳理了这些异常：

### 3.1 脏写与脏读

|异常|描述|发生原因|
|---|---|---|
|**脏写**​|一个事务覆盖了另一个未提交事务的写入|两个并发事务写同一行，后者未等前者提交就覆盖|
|**脏读**​|读到另一个未提交事务写入的数据|事务 A 修改数据但未提交，事务 B 读到了这个"幽灵值"，随后 A 回滚|

**脏读的危害**：如果业务基于脏读数据做了决策（如"看到余额 100 元，决定支出 80 元"），而那个"100 元"是别的事务未提交的临时值且随后回滚，决策就是建立在谎言之上。

### 3.2 不可重复读（Read Skew）

**经典案例**（Kleppmann 书中的 Alice 转账例子）：

- Alice 有两个账户各 500 元
    
- 她从账户 1 转 100 元到账户 2
    
- 转账事务发生在 Alice 的两次余额查询之间
    
- 结果：第一次查账户 1 看到 500 元，第二次查账户 2 看到 400 元
    
- **合计：900 元！**​ 100 元"蒸发"了
    

这种异常对**备份、数据分析、报表生成**是致命的——你在导出数据的过程中，数据被并发修改，导出的快照是不一致的。

### 3.3 更新丢失（Lost Update）

**最常见的并发 bug**：两个事务同时执行"读-修改-写回"循环。

```
事务1: 读计数器=42 → 计算43 → 写回43
事务2: 读计数器=42 → 计算43 → 写回43
结果：计数器应该是44，但实际是43——一次更新丢失了
```

这发生在**并发"读取-修改-写入"导致覆盖**的场景。典型场景：

- 计数器递增
    
- 多人同时编辑 wiki 页面
    
- 仓库库存扣减
    

### 3.4 写偏斜（Write Skew）

**这是最微妙、最危险的异常**。Kleppmann 给出的经典例子：

> 医院要求**至少一名医生**值班。Alice 和 Bob 两名医生同时查看值班表，都看到"有两名医生值班"，于是都提交"我要下班"的请求。结果两人都下班了——**违反了"至少一名医生值班"的不变量**。

写偏斜的本质：**两个事务都基于相同的"前提"做出决策，但各自的写入都不冲突（修改的是不同行），然而组合起来破坏了应用不变量**。

写偏斜在工业界的具体表现：

- **用户名注册**：检查"用户名不存在"→ 插入用户。并发时可能导致重名
    
- **双重支出**：检查"余额 > 0"→ 插入支出记录。并发时可能导致超支
    
- **会议室预订**：检查"时段空闲"→ 预订。并发时可能导致双重预订
    

> ⚠️ **关键警告**：在快照隔离（Repeatable Read）级别下，数据库**不会自动检测写偏斜**。如果你依赖"先查后写"的逻辑来维持数据约束，必须非常小心。

### 3.5 幻读（Phantom Read）

一个事务按条件查询出结果集后，另一个并发事务**插入/删除了**满足该条件的新记录并提交，原事务再次查询时行数变了。

```
事务1: SELECT * FROM users WHERE age > 20;  -- 返回10行
事务2: INSERT INTO users VALUES ('Bob', 25); COMMIT;
事务1: SELECT * FROM users WHERE age > 20;  -- 返回11行
```

幻读的本质是：**WHERE 条件匹配的"行集合"本身在事务过程中发生了变化**。

## 四、隔离级别：正确性 vs 性能的连续光谱

SQL 标准定义了四级隔离级别，本质上是在"正确性"与"并发性能"之间做权衡：

|隔离级别|脏读|不可重复读|幻读|写偏斜|性能|典型默认|
|---|---|---|---|---|---|---|
|**Read Uncommitted**​|❌ 允许|✅|✅|✅|最高|几乎不用|
|**Read Committed**​|❌ 禁止|✅ 允许|✅ 允许|✅ 允许|较高|**Oracle、PostgreSQL、SQL Server**​|
|**Repeatable Read (Snapshot Isolation)**​|❌|❌ 禁止|⚠️ 视实现|✅ 允许|中等|**MySQL InnoDB**​|
|**Serializable**​|❌|❌|❌ 禁止|❌ 禁止|最低|金融核心|

> 💡 **重要澄清**：上表是 SQL 标准定义。但**工业实现往往在标准的边界上游走**，这点 PostgreSQL 官方文档说得很清楚：
> 
> - PostgreSQL 的 Read Uncommitted 模式**实际行为等同于 Read Committed**（因为 PG 的 MVCC 架构下这是唯一合理的映射）
>     
> - PostgreSQL 的 Repeatable Read 实现**不允许幻读**（标准只要求"不允许不可重复读"，PG 提供了更高的保证，这符合标准因为"更高保证是可接受的"）
>     
> - MySQL InnoDB 的 Repeatable Read 通过 **MVCC + Next-Key Lock（间隙锁+行锁）**​ 在很大程度上解决了幻读问题
>     

**这说明：不要死记"标准定义"，要理解"你的数据库实际怎么做"**。这也是为什么 Kleppmann 强调——**隔离级别名称相同，不同数据库的行为可能不同**。

### 4.1 Read Committed：防脏读脏写，代价最小

**实现机制**：

- **防脏写**：行级排他锁。事务要修改一行，必须先获得该行的写锁，提交或中止后才释放
    
- **防脏读**：多版本。数据库为正在被修改的对象维护旧值和新值两个版本。事务提交前，其他读操作读到旧值；提交后，新值才对其他人可见
    

**Read Committed 只防脏读脏写，不防不可重复读、更新丢失、写偏斜、幻读**。它是 Oracle、PostgreSQL、SQL Server 的默认级别，适用于"大部分互联网场景（如新闻、论坛）"。

### 4.2 Snapshot Isolation / Repeatable Read：MVCC 的杰作

**核心思想**：每个事务开始时，拿到数据库在那一瞬间的**一致性快照**。整个事务期间，所有读操作都从这个快照读取——**读不阻塞写，写不阻塞读**。

**实现机制：多版本并发控制（MVCC）**：

- 每行数据有多个版本，每个版本带有创建它的事务 ID
    
- 读操作只访问"创建事务 ID 早于当前事务 ID"的最新版本
    
- 写操作创建新版本，旧版本保留供旧事务读取
    
- 这实现了"读不加锁、写不阻塞读"
    

**MVCC 解决不可重复读**：Alice 的两次余额查询都从同一个快照读取，账户 2 在快照中仍是 500 元，不会出现"900 元"的诡异现象。

**MVCC 的精妙之处**：Read Committed 也可以说是多版本，不过只需要两个版本（旧值和新值），所以它是对**请求级别**的快照；而 Snapshot Isolation 是每个事务都有一个版本，因此是对**事务级别**的快照。

> 🔥 **洞见**：MVCC 的本质是**"用空间（多版本）换时间（读写不阻塞）"**。这是与第3章 LSM-Tree "用写放大换读性能" 如出一辙的工程哲学——**所有性能优化，本质上都是某种物理资源的置换**。

### 4.3 Serializable：正确性的终极堡垒

Serializable 是最严格隔离级别，保证事务效果**等价于**按某种顺序串行执行。

**关键认知**：**可串行化 ≠ 串行执行**。现代数据库通过智能调度算法，在保证"等价于串行"的同时实现高性能并发。Kleppmann 详细讨论了三种实现方式：

#### 方式一：Serial Execution（真串行执行）

**反直觉的思路**：既然锁的开销那么大，不如干脆**不要并发**——用单线程串行执行所有事务！

**代表系统**：VoltDB、Redis

**适用条件**：

- 内存数据库（数据集可放入内存）
    
- 事务逻辑非常短（不能有磁盘 I/O、不能有网络交互）
    
- 高冲突场景
    

**优势**：避开了锁竞争和上下文切换的开销，反而比多线程更快

**劣势**：适用场景受限，单 CPU 核成为吞吐量天花板

#### 方式二：Two-Phase Locking（2PL，两阶段锁）

**经典悲观策略**：事务分两个阶段

- **扩展阶段（Growing Phase）**：只获锁，不放锁
    
- **收缩阶段（Shrinking Phase）**：只放锁，不获锁
    

读用共享锁，写用排他锁。只要遵循 2PL，就能在数学上保证可串行化。

**工业现实**：2PL 是"悲观的恐龙"

- 读锁阻塞写锁，写锁阻塞读锁
    
- 并发度急剧下降
    
- 死锁成为家常便饭
    
- 延迟极不稳定（一个长事务持锁，所有相关事务排队）
    

**这就是"除非万不得已，别用 Serializable"的工程共识由来**。

#### 方式三：Serializable Snapshot Isolation（SSI，可串行化快照隔离）

**这是 Kleppmann 最推崇的技术，也是现代数据库的演进方向**。

**核心思想**：基于快照隔离（提供高性能的读），但在**提交时**增加冲突检测——如果发现事务执行期间发生了写偏斜的条件，则中止并重试。

**SSI 检测两种危险结构**：

1. **读取了过时的 MVCC 版本**：事务读到的数据，在它提交前被其他事务修改了（"读之前有未提交的写"）
    
2. **读取后数据被修改**：事务读到的数据，在它读取之后、提交之前，被其他事务修改了（"读之后有提交的写"）
    

**SSI 是一种乐观并发控制（OCC）**：假设冲突罕见，先执行操作，提交时检查冲突，冲突则中止重试。

**工业落地**：PostgreSQL 9.1+ 实现了 SSI，性能接近快照隔离，但能提供完整的 Serializable 保证。

> 🔥 **我的洞见**：SSI 代表了事务隔离设计的**范式转移**——从"悲观预防"（2PL：假设冲突必然发生，提前加锁阻塞）到"乐观检测"（SSI：假设冲突罕见，执行后检测，冲突则重试）。这种转移之所以可能，是因为现代硬件条件下**冲突概率远低于传统假设**——大多数事务操作不同的数据行。SSI 的本质是**把"冲突检测"从"执行时"推迟到"提交时"**，从而大幅降低了读写之间的阻塞。这是与无主复制中"把一致性问题从写入时推迟到读取时"异曲同工的设计哲学。

## 五、工业实践：隔离级别的真实选择

### 5.1 主流数据库的默认隔离级别

|数据库|默认隔离级别|选择逻辑|
|---|---|---|
|**Oracle**​|Read Committed|防脏读即可，性能优先|
|**PostgreSQL**​|Read Committed|同上，且 PG 的 MVCC 架构天然支持快照|
|**SQL Server**​|Read Committed|同上|
|**MySQL InnoDB**​|Repeatable Read|通过 MVCC + Next-Key Lock 防幻读|
|**CockroachDB**​|Serializable|分布式数据库，默认最强隔离|

### 5.2 金融系统的分层锁策略

某支付平台的工业实践极具代表性：

- **账户余额更新**：行级排他锁（保证强一致性）
    
- **交易记录插入**：表级意向共享锁（批量操作优化）
    
- **日终对账**：快照读（无锁，利用 MVCC）
    

这套方案既保证了交易一致性，又满足了高并发需求，**峰值 TPS 达 10 万+**。这正是"按操作类型选择隔离策略"的工程典范。

### 5.3 写偏斜的工业解决方案

当业务依赖"先查后写"逻辑时，在 Snapshot Isolation 下有写偏斜风险。三种解决方案：

|方案|机制|适用场景|
|---|---|---|
|**SELECT ... FOR UPDATE**​|显式加排他锁，强制串行化|冲突频繁的场景|
|**升级到 Serializable**​|使用 SSI 或 2PL|正确性要求极高|
|**物化冲突（Materializing Conflicts）**​|预先生成所有可能冲突的行，强迫事务锁住这些行|冲突结构可预知的场景（如会议室预订）|

### 5.4 分布式事务：2PC 与 SAGA

当数据跨多个分区/节点时，单机事务升级为分布式事务。主流方案：

**两阶段提交（2PC）**：

- **准备阶段**：协调者询问所有参与者"能否提交"
    
- **提交阶段**：若全票通过则提交，否则全部回滚
    
- **问题**：协调者单点故障、同步阻塞、网络分区下可能阻塞
    

**SAGA 模式**：

- 将长事务拆分为一系列本地事务
    
- 每个本地事务有对应的补偿事务
    
- 任一失败则按逆序执行补偿
    
- **适用场景**：微服务架构、长事务

## 六、跨章联系：事务是分布式数据系统的"正确性基石"

回到全书的因果链：

- **↩️ 第1章 R-S-M**：
    
    - **可靠性**​ ← 原子性 + 持久性保证部分失败不产生脏数据
        
    - **可扩展性**​ ← 强隔离级别（Serializable）显著降低并发度
        
    - **可维护性**​ ← 长事务、死锁、隔离级别误用是运维噩梦
        
    
- **↩️ 第3章 存储引擎**：
    
    - 持久性依赖 WAL（呼应第3章 B-Tree 的 WAL 机制）
        
    - 隔离性依赖锁/MVCC——MVCC 的多版本与 LSM-Tree 的 SSTable 不可变文件天然契合
        
    
- **↩️ 第5章 复制**：
    
    - 单主复制下，事务由 leader 串行化处理，相对简单
        
    - 多主/无主复制下，"全局事务"变成分布式事务，需要 2PC 或 SAGA
        
    - 异步复制下的"读己之写"、"单调读"等问题，本质是弱隔离级别在分布式环境的投射
        
    
- **↩️ 第6章 分区**：
    
    - 单分区事务是本地事务
        
    - **跨分区事务是分布式事务**——这是 SAGA、TCC、2PC 的由来
        
    - 分区键的选择直接影响事务是否需要跨分区
        
    
- **➡️ 第9章 共识**：
    
    - 2PC 的协调者故障需要共识算法恢复
        
    - SSI 的冲突检测在分布式环境下需要全局时钟或版本向量
        
    - 真正的线性一致性需要 Paxos/Raft 兜底

## 七、我的整合洞见：事务设计的第一性原理

综合全章，我提炼出**事务设计的第一性原理框架**：

### 原理一：事务的本质是"认知抽象"

事务不是在"解决问题"，而是在"封装问题"——把并发与故障的复杂性隐藏起来，让应用开发者可以**假装**世界是单线程的、故障是不会发生的。**这种抽象的价值，不在于它消除了复杂性，而在于它把复杂性集中到了数据库内核，让应用层不必每次都重新发明轮子**。

### 原理二：隔离级别是"正确性-性能"光谱上的主动选择

没有"最好的隔离级别"，只有"针对你的业务最优的隔离级别"：

- **Read Committed**：互联网场景的主流选择，防脏读脏写即可
    
- **Repeatable Read / Snapshot Isolation**：需要一致性快照的场景（备份、报表、财务对账）
    
- **Serializable**：金融核心、强一致性要求的场景
    

### 原理三：弱隔离的陷阱是"隐式依赖"

写偏斜等异常的危险之处在于——**代码看起来是对的，但在并发下会悄悄破坏数据不变量**。开发者必须主动识别业务中的"先查后写"模式，并显式选择防御措施（FOR UPDATE、Serializable、物化冲突）。

> ⚠️ **经验法则**：如果你的业务逻辑包含"检查某条件 → 基于检查结果做写入"，那么在 Snapshot Isolation 级别下，你必须假设这个条件在你写入时可能已经不成立。

### 原理四：SSI 是隔离级别设计的未来

SSI 代表了从事务隔离设计**从"悲观预防"到"乐观检测"的范式转移**。随着硬件性能提升和冲突概率降低，乐观策略（执行后检测，冲突则重试）在大多数场景下优于悲观策略（执行时加锁，冲突则阻塞）。

**这是与无主复制中"把一致性问题从写入时推迟到读取时"异曲同工的设计哲学——能推迟的决策尽量推迟，因为推迟给了系统更多信息来做最优选择**。

### 原理五：分布式事务的本质是两难选择

跨分区/跨节点的分布式事务，本质上是在做选择：

- **2PC**：强一致性，但同步阻塞、协调者单点
    
- **SAGA**：高可用，但最终一致性，需要补偿逻辑
    
- **放弃分布式事务**：通过应用层设计避免跨节点事务（如按聚合根分区）
    

**这是 CAP 定理在事务层面的具体投射**。

## 八、关键术语速查

- **ACID**：原子性、一致性、隔离性、持久性——但 C 是应用层责任，A/I/D 是数据库机制
    
- **脏读（Dirty Read）**：读到未提交的数据
    
- **不可重复读（Non-Repeatable Read）**：同一事务内两次读同一行，结果不同
    
- **幻读（Phantom Read）**：同一事务内同一查询条件的行数变化
    
- **写偏斜（Write Skew）**：两个事务基于相同前提做决策，各自写入不冲突，但组合起来破坏不变量
    
- **更新丢失（Lost Update）**：并发"读-修改-写回"导致覆盖
    
- **MVCC（多版本并发控制）**：维护数据多版本，读不加锁、写不阻塞读
    
- **2PL（两阶段锁）**：扩展阶段只获锁、收缩阶段只放锁，保证可串行化的经典算法
    
- **SSI（可串行化快照隔离）**：乐观并发控制，事务基于快照执行，提交时检测写偏斜
    
- **2PC（两阶段提交）**：分布式事务的协调协议——准备阶段 + 提交阶段
    
- **SAGA**：将长事务拆分为本地事务序列，失败时执行补偿
    
- **Next-Key Lock**：间隙锁+行锁，InnoDB 在 Repeatable Read 下防幻读的机制

## 九、写给读者的话

第7章最深刻的启示，**不是"事务有哪几种隔离级别"，而是一种"正确性工程的觉醒"**。

在单机、低并发的世界里，事务是一个理所当然的抽象——"要么全做，要么全不做"。但在分布式、高并发的现代系统里，**事务变成了一个充满权衡的复杂决策**：

- 选 Serializable？一致性最强，但吞吐量断崖式下跌
    
- 选 Read Committed？性能好，但写偏斜可能悄悄破坏数据
    
- 跨分区事务？2PC 还是 SAGA？强一致还是高可用？
    

**Kleppmann 通过这一章告诉我们：事务不是银弹，而是一把双刃剑**。它赋予了应用开发者"单线程幻觉"的便利，但也带来了性能损耗、死锁风险、分布式复杂性。

**优秀的架构师，是那个能在"正确性"和"性能"之间看到业务本质的人**。他理解：

- 对于支付系统，"强一致性"是不可妥协的底线 → Serializable 或 SSI
    
- 对于社交媒体，"最终一致性"可以接受 → Read Committed + 应用层冲突处理
    
- 对于库存系统，"写偏斜"是隐形杀手 → FOR UPDATE 或 Serializable
    
- 对于跨微服务的长事务 → SAGA + 补偿
    

> _"Transactions are not a feature; they are a contract between the application and the database about how to handle concurrency and failures."_
> 
> 事务不是一项功能，而是应用与数据库之间关于"如何处理并发与故障"的契约。

**而这，正是分布式数据系统设计的深层智慧——用显式的契约，换取隐式的复杂性封装。**
