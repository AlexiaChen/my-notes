
# 第7章 可靠的数据传递 · 读书笔记

> 💡 这一章表面是"如何配置 Kafka 做到不丢消息"，实质是在回答：**在一个分布式日志系统中，"可靠"不是一个开关，而是生产者、broker、消费者三方共同遵守的一份契约**。书里第2版写于 ZooKeeper 时代，但 Kafka 3.0 之后幂等生产者已成默认，3.3+ KRaft 全面取代 ZK，4.x 又引入了 ELR（Eligible Leader Replicas）来细化"不彻底首领选举"。所以这份笔记的做法是：**以原书目录为骨架，用最新的官方文档和工业实践重新讲述"可靠性契约"**，让你看到的不是一串配置项，而是一套自洽的端到端保证。

---

## 7.1 可靠性保证

Kafka 官方给出的承诺非常精确：**只要至少有一个同步副本（ISR）存活，已提交的消息就不会丢失**。这句话拆开来看有三个关键词：

- **"已提交的"**：指消息已经被 ISR 中所有成员复制，且 HW（High Watermark）已推进到该消息之后
- **"消息不会丢失"**：消费者永远看不到可能丢失的消息——它们只能读到 HW 以下的消息
- **"至少一个 ISR 存活"**：这是可靠性的前提，也是 `min.insync.replicas` 要守护的底线

Kafka 的可靠性不是绝对的"永不丢失"，而是**在特定故障域内**的保证。官方设计文档说得很坦白：Kafka 只处理"节点突然失效后恢复"的 fail/recover 模型，不处理拜占庭故障。这是一个工程上的诚实——它把"可靠性"定义为"在预期故障模式下不丢数据"，而不是"在所有可能故障下都不丢数据"。

### 洞见：可靠性是"概率性保证"而非"绝对保证"

回到第一性原理——分布式系统的 CAP 定理告诉我们，在网络分区（P）必然存在的前提下，一致性和可用性不可兼得。Kafka 的选择是：**默认偏向一致性（C），通过配置可以在两者间滑动**。

这条滑动的杠杆就是：

|杠杆|偏向一致性（不丢）|偏向可用性（不停服）|
|---|---|---|
|`unclean.leader.election.enable`|false（默认）|true|
|`min.insync.replicas`|高（如 2）|低（如 1）|
|`acks`|all|0 或 1|

> 💡 工业界 99% 的生产环境选择"偏向一致性"——因为"不可用"是可以被感知、被告警、被处理的，而"静默丢数据"是灾难性的、不可恢复的。

## 7.2 复制

复制是可靠性的物理基础。Kafka 的每个分区都是一个复制日志（replicated log），官方设计文档把复制的本质讲得很清楚：**用一个 leader 来决定写入顺序，follower 只需要复制 leader 选定的值和顺序**。

核心机制回顾（详见第6章）：

- **ISR 动态伸缩**：follower 在 `replica.lag.time.max.ms`（默认 30s）内没追上 leader → 被移出 ISR
- **HW 界定可见性**：消费者只能读到 HW 以下的消息
- **Leader Epoch 防幽灵数据**：旧 leader 重新加入时，新 leader 用 epoch 告诉它截断未提交部分

但有一个微妙之处值得展开——**acks=all 并不意味着"所有副本都确认"**：

> ⚠️ 官方文档明确："acknowledgement by all replicas" does not guarantee that the full set of assigned replicas have received the message. 当 acks=all 时，确认发生在"当前 ISR 中所有成员"都收到消息的那一刻。

这意味着：如果 RF=3 但 ISR 退化到 {leader, follower1}，acks=all 只等 2 个确认。此时如果 leader 和 follower1 同时挂掉，那些"已确认"的消息就会丢失。**这就是为什么 `min.insync.replicas` 是可靠性的地板**。

### 洞见：复制是"信任链"，不是"副本数"

很多人误解"RF=3 就意味着可以容忍 3 个故障"——错。准确的表述是：**RF=3 + min.insync.replicas=2 + acks=all 意味着可以容忍 1 个 broker 永久故障而不丢数据**。

信任链是这样的：

```
acks=all ──要求──> ISR 中所有成员确认
min.insync.replicas=2 ──要求──> ISR 至少有 2 个成员
RF=3 ──提供──> ISR 最大可能有 3 个成员

∴ 当 1 个 broker 挂掉：ISR 从 3 退化到 2，仍满足 min.insync.replicas=2，写入继续
  当 2 个 broker 同时挂掉：ISR 退化到 1，不满足 min.insync.replicas=2，写入被拒绝（返回 NotEnoughReplicasException）
```

**被拒绝的写入不会丢数据——它们会失败，应用层可以重试或向上报错**。这就是"偏向一致性"的含义：宁可停服，不可丢数据。

## 7.3 broker 配置

### 7.3.1 复制系数（replication.factor）

默认值是 1——这是 Kafka 最大的"可靠性陷阱"。**生产环境必须显式设置为 3**。

Red Hat 的官方调优文档给出的生产基线非常清晰：

```
default.replication.factor=3
min.insync.replicas=2
```

这三个配置的组合效果：

|可用同步副本数|Leader 行为|
|---|---|
|2（leader + 1 follower）|等待 1 个 follower 确认，**允许写入**​|
|1（仅 leader）|ISR 低于 min.insync.replicas，**拒绝写入**​|
|0|不可能（leader 自己总在 ISR 中）|

> ⚠️ **默认配置的致命陷阱**：Kafka 3.0+ 虽然 acks 默认为 all，但 `min.insync.replicas` 仍默认为 1，`default.replication.factor` 也默认为 1。这意味着开箱即用的 Kafka 实际上是**零可靠性的**——leader 单独写入就算 ack=all 成功。任何生产 topic 都必须显式覆盖这两个值。

### 7.3.2 不彻底的首领选举（unclean.leader.election.enable）

这是可用性 vs 一致性博弈的最前线。

**当整个 ISR 都挂掉时**：

- `unclean.leader.election.enable=false`（默认）：分区不可用，拒绝读写，直到 ISR 成员恢复
- `unclean.leader.election.enable=true`：允许从 OSR（out-of-sync replica）中选 leader，**可能丢数据**——因为 OSR 上的消息可能比 ISR 旧

官方设计文档的态度很明确：**从 0.11.0.0 开始，Kafka 默认选择"等待一致性副本"的策略**。

**KRaft + ELR：4.x 的现代解法**

Kafka 4.1 引入了 ELR（Eligible Leader Replicas），把原来的"ISR vs OSR"二元划分变成了三元：

- **ISR**：完全同步的副本，HW 只在所有 ISR 成员写入后才推进
- **ELR**：曾经在 ISR 中、但因 ISR 跌破 min.insync.replicas 而被移出的副本。它们虽然不在 ISR 中，但仍然持有到 HW 为止的数据
- **Out of ISR/ELR**：滞后太多、选举为 leader 会丢数据的副本

有了 ELR，首领选举的优先级变成：

```
1. ISR 成员（最优，零数据丢失）
2. ELR 成员（安全，数据不丢失，HW 不会倒退）
3. 最后一个已知 leader
4. Out-of-sync 副本（仅当 unclean.leader.election.enable=true）
5. 分区离线（unclean 禁用时）
```

> 💡 **工业视角**：ELR 是 KIP-966 的成果，目标是"当只有 min.ISR-1 个副本经历不彻底关闭时，能够选举 leader 而不丢数据或让 HW 倒退"。这是 Kafka 可靠性演化的一个重要里程碑——它让"不彻底选举"从"必然丢数据"变成了"可控的安全降级"。

### 7.3.3 最少同步副本（min.insync.replicas）

这是与 acks=all 配合使用的"地板配置"。官方文档说得很直白：

> 这个设置只在生产者使用 acks=all 时生效，保证消息至少被这么多同步副本确认。

典型配置：`min.insync.replicas=2`，配合 `replication.factor=3`。这样：

- 允许 1 个 broker 故障，写入继续
- 如果 2 个 broker 同时故障，写入被拒绝（但数据不丢）

### 7.3.4 保持副本同步

这是运维层面的关注点。关键指标：

- **Under-Replicated Partitions**：ISR 大小 < 分配副本数的分区数。正常值应为 0
- **Replica Lag**：follower 落后 leader 的消息数
- **副本放置策略**：跨机架、跨可用区分布，避免相关故障

监控到 Under-Replicated Partitions > 0 时，说明有 follower 跟不上或被移出 ISR，需要排查：网络、磁盘 IO、GC 停顿、broker 过载。

### 7.3.5 持久化到磁盘

很多人误解"Kafka 是纯内存系统"——错。Kafka 的依赖是 OS 页缓存 + 顺序刷盘：

- 生产者发送的消息先到 leader 的页缓存
- Follower 通过 Fetch 协议拉取，也写入自己的页缓存
- **何时 fsync 到磁盘由 `flush.messages` 和 `flush.ms` 控制**（现代 Kafka 通常依赖 OS 后台刷盘，而非显式 fsync）
- 即使进程崩溃，OS 页缓存中的数据不会丢（除非操作系统崩溃或断电）

> 💡 工业界最佳实践：**不要让 Kafka 做同步 fsync**。依赖副本机制（RF=3）来保证持久性，比频繁 fsync 的单机持久性更可靠，且吞吐量高出几个数量级。

### 洞见：broker 配置的"第一性原理"

所有 broker 可靠性配置都在守护一件事：**让 ISR 的成员数永远不低于 min.insync.replicas**。

```
replication.factor=3        → 提供 ISR 的上限
min.insync.replicas=2       → 设定 ISR 的下限
unclean.leader.election.enable=false → 当 ISR 跌破下限时，选择停服而非丢数据
replica.lag.time.max.ms=30s → 定义"什么算跟不上"
```

这四个配置构成一个**闭环的可靠性契约**。任何一环缺失，契约就破裂。

## 7.4 在可靠的系统中使用生产者

### 7.4.1 发送确认（acks）

三个级别：

|acks|语义|持久性|延迟|适用场景|
|---|---|---|---|---|
|0|发完即忘|最低|最低|指标、日志，可接受丢失|
|1|leader 写入即确认|中等|中等|平衡场景|
|**all**​|ISR 中所有成员写入才确认|最高|最高|金融、订单、任何不可丢数据|

**生产环境铁律：必须 acks=all**。但光 acks=all 不够——它必须与 `min.insync.replicas>=2` 配合使用才有意义。

### 7.4.2 配置生产者的重试参数

Kafka 3.0+ 的重大变化：**enable.idempotence 默认为 true**。启用幂等时：

- `retries` 自动设为 `Integer.MAX_VALUE`
- `acks` 自动设为 `all`
- `max.in.flight.requests.per.connection` 自动设为 5

幂等生产者的工作机制：

```
每个生产者实例获得唯一 Producer ID (PID)
每条消息附带序列号（per topic-partition）
Broker 端按 PID + 序列号去重：
  - 序列号匹配预期 → 正常写入
  - 序列号小于预期 → 重复，丢弃并返回成功
  - 序列号大于预期 → 乱序，抛出 OutOfOrderSequenceException
```

**关键限制**：

> ⚠️ 幂等性只在"单个生产者会话内"有效。如果生产者应用重启，它会获得新的 PID，跨会话的去重上下文丢失——可能产生重复。

### 7.4.3 额外的错误处理

Confluent 的官方建议：

- **避免应用层重发**：如果启用了幂等，应用层不要再自己做重试，否则无法去重
- **处理不可恢复异常**：`OutOfOrderSequenceException`、`UnknownProducerIdException` 出现时，应关闭生产者并创建新实例
- **delivery.timeout.ms**：控制最大重试时间，默认 120000ms（2分钟）

工业界生产基线配置：

```
Properties props = new Properties();
props.put("bootstrap.servers", "kafka:9092");
props.put("acks", "all");
props.put("enable.idempotence", "true");  // Kafka 3.0+ 默认开启
props.put("retries", Integer.MAX_VALUE);
props.put("max.in.flight.requests.per.connection", "5");
props.put("delivery.timeout.ms", "300000");  // 5分钟
props.put("compression.type", "snappy");
props.put("transactional.id", "order-processor-1");  // 如需跨分区原子性
```

### 洞见：生产者的"可靠性契约"

生产者的可靠性不是"配置出来的"，而是"设计出来的"：

```
acks=all + min.insync.replicas=2 + RF=3  → broker 端不丢数据
enable.idempotence=true                  → 重试不产生重复
keyed messages + 单分区                  → 有序性保证
```

这三条组合起来，Confluent 称之为"端到端顺序保证"：**特定 key 的消息总是以发送顺序落到特定分区，消费者总是以完全相同顺序读取**。

> 💡 如果需要跨分区的原子性（如"扣款"和"记账"必须同时成功或同时失败），则需要**事务生产者**——设置 `transactional.id`，用 `beginTransaction()` / `commitTransaction()` 包裹发送。但事务的性能开销显著，仅在真正需要时使用。

## 7.5 在可靠的系统中使用消费者

### 7.5.1 消费者的可靠性配置

消费者端的可靠性核心就一句话：**先处理，再提交**。

关键配置：

```
props.put("enable.auto.commit", "false");  // 禁用自动提交
props.put("auto.offset.reset", "earliest");  // 或 latest，取决于业务
props.put("max.poll.interval.ms", "600000");  // 防止处理过慢被踢出组
props.put("max.poll.records", "100");  // 控制单次 poll 的消息数
```

### 7.5.2 手动提交偏移量

这是消费者可靠性的命脉。**自动提交是"静默数据丢失"的头号原因**：

```
典型故障场景：
1. Consumer 调用 poll()，收到消息 100-199
2. 自动提交触发，offset 提交为 200
3. Consumer 在处理消息 150 时崩溃
4. Consumer 重启，从 offset 200 继续
5. 消息 150-199 永久丢失！
```

**正确的手动提交模式**：

```
while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
    try {
        for (ConsumerRecord<String, String> record : records) {
            processOrder(record);  // 先处理
        }
        consumer.commitSync();  // 处理后提交
    } catch (Exception e) {
        // 处理失败，不提交 offset，消息将在重启后重新投递
        log.error("Processing failed", e);
        // 可选择：发送到死信队列、告警、人工介入
    }
}
```

**CommitFailedException 的处理**：

```
原因：消费者在两次 poll() 之间花了太长时间，Kafka 认为它已死，触发了 rebalance
解决：
  - 增大 max.poll.interval.ms
  - 减少 max.poll.records
  - 更频繁地提交 offset
```

**混合提交策略**（工业界推荐）：

```
// 热路径：异步提交，不阻塞
consumer.commitAsync((offsets, exception) -> {
    if (exception != null) {
        log.error("Async commit failed", exception);
    }
});

// 关闭时：同步提交，确保最后位置被刷入
Runtime.getRuntime().addShutdownHook(new Thread(() -> {
    try {
        consumer.commitSync();  // 阻塞直到成功
    } finally {
        consumer.close();
    }
}));
```

### 洞见：消费者可靠性的"第一性原理"

消费者端的可靠性可以归结为三个语义级别：

|语义|实现方式|后果|
|---|---|---|
|**At most once**​|获取消息后立即提交 offset|可能丢消息，但不会重复|
|**At least once**​|处理完成后提交 offset|可能重复，但不会丢消息|
|**Exactly once**​|配合事务或幂等生产者|复杂，性能开销大|

工业界 99% 的场景选择 **At least once**——因为"重复"可以通过业务层幂等来处理，而"丢失"是不可恢复的。

**业务幂等的三板斧**：

1. **数据库唯一键**：利用唯一约束防止重复插入
2. **幂等更新**：UPDATE ... WHERE version = expected_version
3. **去重表**：在处理前检查"消息指纹"是否已处理

> 📌 **关键认知**：Kafka 的 offset 提交机制只保证"at least once"。真正的 exactly-once 需要业务层配合——Kafka 提供的是"不丢消息 + 可检测重复"的基础设施，业务层负责"处理重复"。

## 7.6 验证系统可靠性

### 7.6.1 验证配置

配置可靠性不是"设了就行"，必须验证。验证清单：

```
□ replication.factor >= 3（所有生产 topic）
□ min.insync.replicas >= 2
□ unclean.leader.election.enable = false
□ enable.idempotence = true（Kafka 3.0+ 默认）
□ acks = all
□ enable.auto.commit = false
□ offsets.retention.minutes 调整到业务可接受的值（默认 7 天太短）
```

**为什么 offsets.retention.minutes 默认 7 天是个坑**：

> ⚠️ 消费者组停用超过 7 天后，其 offset 会被 Kafka 静默删除。下次启动时，按照 auto.offset.reset 策略重新开始——如果是 latest，则停机期间的消息全部丢失（静默数据丢失）；如果是 earliest，则从 retention 边界开始重放（产生大量重复）。

工业界建议：`offsets.retention.minutes=43200`（30天）或更长。

### 7.6.2 验证应用程序

**故障注入测试**：

1. **Broker 杀进程**：kill -9 一个 broker，观察 ISR 变化、leader 切换时间、生产者重试行为
2. **网络分区**：用 iptables 阻断 broker 间通信，观察 unclean 选举是否被触发
3. **消费者杀死**：在 poll() 和处理之间 kill -9 消费者，验证消息不丢
4. **磁盘满**：填满 broker 磁盘，观察生产者行为
5. **Controller 故障**：杀掉 controller，观察新 controller 选举时间

**端到端验证**：

- 生产者发送 N 条消息，每条带唯一 ID
- 消费者处理后写入数据库（带唯一键）
- 验证数据库中恰好有 N 条记录（无丢失、无重复）

### 7.6.3 在生产环境中监控可靠性

核心监控指标：

|指标|警告阈值|严重阈值|含义|
|---|---|---|---|
|**Consumer Lag**​|> 10,000|> 100,000|消费滞后消息数|
|**Under-Replicated Partitions**​|> 0|持续 > 0|ISR 缩小|
|**Replica Lag**​|持续增长|超过 replica.lag.time.max.ms|follower 跟不上|
|**Offset Commit 失败率**​|> 2%|> 5%|协调者不稳定|
|**Commit Latency**​|> 100ms|> 500ms|提交性能问题|
|**Rebalance 频率**​|每小时多次|每分钟多次|消费者组不稳定|
|**Offset Reset 事件**​|发生即告警|-|静默数据丢失的信号|

**监控工具栈**：

- **Burrow**：专门监控 consumer lag 和 offset 提交健康度
- **Prometheus + Kafka Exporter**：采集 JMX 指标
- **Confluent Control Center / Conduktor**：商业监控平台
- **kafka-consumer-groups.sh**：命令行诊断

```
# 查看消费滞后
kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --describe --group my-group

# 输出示例：
# TOPIC    PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
# orders   0          5000            5500            500
```

### 洞见：可靠性验证的"第一性原理"

可靠性不是"配置出来的"，而是"验证出来的"。**没有经过故障注入测试的可靠性配置，只是纸面可靠性**。

工业界成熟的做法是建立"混沌工程"常态化：

- 每周自动 kill 一个 broker
- 每月模拟一次网络分区
- 每季度做一次全链路故障演练

只有在真实故障中活下来的配置，才是真正的可靠配置。

## 7.7 小结

把全章串起来，Kafka 的可靠性是一个**三方契约**：

```
┌─────────────────────────────────────────────────────┐
│ 生产者端                                              │
│  acks=all + enable.idempotence=true                  │
│  → 保证：消息不丢、不重复、有序                        │
└──────────────────────┬──────────────────────────────┘
                       │ 发送
                       ↓
┌─────────────────────────────────────────────────────┐
│ Broker 端                                             │
│  RF=3 + min.insync.replicas=2                        │
│  + unclean.leader.election.enable=false               │
│  → 保证：已提交消息在 ISR 存活时不丢                   │
│  → ISR 跌破 min.insync.replicas 时拒绝写入（停服保数据）│
└──────────────────────┬──────────────────────────────┘
                       │ 复制
                       ↓
┌─────────────────────────────────────────────────────┐
│ 消费者端                                              │
│  enable.auto.commit=false + 处理后 commitSync()       │
│  + 业务层幂等处理                                     │
│  → 保证：at-least-once 语义，重复可由业务去重           │
└─────────────────────────────────────────────────────┘
```

### 工业界可靠性黄金基线

```
# ===== Broker/Topic 级别 =====
default.replication.factor=3
min.insync.replicas=2
unclean.leader.election.enable=false
offsets.retention.minutes=43200  # 30天

# ===== Producer 级别 =====
acks=all
enable.idempotence=true
retries=2147483647
max.in.flight.requests.per.connection=5
delivery.timeout.ms=300000

# ===== Consumer 级别 =====
enable.auto.commit=false
auto.offset.reset=earliest  # 或 latest，取决于业务
max.poll.interval.ms=600000
max.poll.records=100
```

### 给读者的"可靠性心智模型"

> 📌 **全章最核心的一句话**：Kafka 的可靠性不是来自某个神奇的配置项，而是来自**生产者、broker、消费者三方共同遵守的一份契约**——生产者承诺"用 acks=all 等待 ISR 确认"，broker 承诺"在 ISR 存活时不丢已提交消息，在 ISR 跌破底线时宁可停服"，消费者承诺"先处理再提交，并对重复消息做幂等处理"。**任何一方的违约，都会让整个可靠性契约崩塌**。

**这条契约的三个支柱**：

1. **写入端不丢**：acks=all + 幂等 + 重试
2. **存储端不丢**：RF=3 + min.insync.replicas=2 + unclean 选举禁用
3. **读取端不丢**：手动提交 + 业务幂等

**而验证这份契约的唯一方式**，是主动注入故障——kill broker、阻断网络、杀死消费者——在真实的混沌中确认：消息真的不丢、不重复、有序。

> ⚠️ **最后的警示**：Kafka 3.0+ 虽然幂等生产者默认开启，但 `min.insync.replicas` 仍默认为 1，`default.replication.factor` 仍默认为 1。**这意味着"开箱即用"的 Kafka 实际上零可靠性**——你必须显式配置才能激活可靠性契约。这是每一个 Kafka 运维者必须刻进肌肉记忆的事实。
