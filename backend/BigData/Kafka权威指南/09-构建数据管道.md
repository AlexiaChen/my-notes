
# 第9章 构建数据管道 · 读书笔记

> 💡 这一章表面是"如何用 Kafka Connect 搭建数据管道"，实质是在回答：**当一个组织要把几十上百个外部系统（数据库、对象存储、搜索引擎、数据仓库、SaaS API）的数据流动起来时，应该用什么抽象来组织这种"系统间的数据搬运"？**​ 答案不是"写一堆 Producer/Consumer 客户端"——那是意大利面架构。答案是 **Kafka Connect：把"数据进出 Kafka"这件事本身框架化、插件化、运维化**。这一章的真正价值，是帮你建立"数据管道"作为一种独立工程学科的心智模型：它有自己要考虑的维度（及时性、可靠性、吞吐量、格式、转换、安全、故障处理、耦合性），也有自己最适合的工具（Connect API 优于裸客户端 API 的大多数场景）。

---

## 9.1 构建数据管道时需要考虑的问题

这是全章的"维度框架"——八个维度构成了评估任何数据管道方案的坐标系。

### 9.1.1 及时性（Timeliness）

及时性问的是"数据从产生到可被消费，延迟是多少"。

Kafka 本身的端到端延迟可以做到毫秒级——Confluent 的官方优化指南指出，生产者默认 `linger.ms=0`，消息一就绪就发送，端到端延迟极短。但管道的及时性不只取决于 Kafka：

- **Source 端**：CDC 类连接器（如 Debezium）可以亚秒级捕获数据库变更；而基于 SQL 轮询的连接器可能受 `poll.interval.ms` 限制，延迟在秒到分钟级
- **Sink 端**：Elasticsearch 批量写入有 refresh_interval（默认 1s），HDFS/S3 连接器通常按文件滚动策略（如 10 分钟或 1GB），延迟可能是分钟到小时级
- **转换层**：SMT 是逐条处理，开销小；但如果管道中嵌入了 Kafka Streams/Flink 做复杂转换，窗口聚合的延迟通常在秒到分钟级

> 💡 **工业决策**：及时性要求决定了技术选型。实时风控要求毫秒到秒级 → 必须 CDC + 直接写入；离线分析允许小时级延迟 → 可以用 S3/HDFS 批导出。不要为"天级延迟就可接受"的场景上 CDC，反之亦然。

### 9.1.2 可靠性（Reliability）

可靠性在这里的含义比第7、8章更宽——它不只是"Kafka 不丢消息"，而是"端到端不丢、不重、有序"。

管道可靠性的三个层次：

**第一层：传输可靠性**

- Source → Kafka：依赖生产者的 acks=all、幂等、EOS
- Kafka → Sink：依赖消费者的手动提交、幂等 sink

**第二层：偏移管理可靠性**

- Source 连接器必须把"从外部系统读到的位置"持久化，才能在故障重启后不丢不重
- Kafka Connect 框架提供了 offset 存储机制（offset.storage.topic）

**第三层：外部系统可靠性**

- 目标系统（如数据库）是否支持幂等写入？是否支持事务？
- 这是 EOS 的真正边界——Kafka 事务能保证"Kafka 内部原子性"，但**跨系统原子性需要目标系统配合**

> ⚠️ **关键认知**：Kafka Connect 的精确一次语义（EOS）是**连接器相关的**——即使你在 worker 级别配置了所有正确的属性，如果连接器本身不支持或不利用 Kafka Connect 框架的能力，精确一次仍然不可能实现。

### 9.1.3 高吞吐量和动态吞吐量

吞吐量考量有两个维度：

**峰值吞吐量**：管道必须能扛住业务峰值。Kafka Connect 通过并行任务（tasks）实现横向扩展——增加 `tasks.max` 可以提高吞吐量，但也会增加资源消耗。

**动态吞吐量**：业务量会增长。Connect 的优势在于：可以动态增加 worker 节点，框架自动重新平衡任务；可以增加分区数来提高 sink 的并行度。

> 💡 **反模式**：用单个大连接器实例处理所有表。正确做法是按业务域拆分连接器，每个连接器独立扩缩容。

### 9.1.4 数据格式

数据格式是管道中最容易被低估、却最能决定项目生死的维度。

**序列化格式选择**：

|格式|优点|缺点|适用场景|
|---|---|---|---|
|**Avro**​|紧凑、Schema Registry 管理、向前向后兼容|需要 Schema Registry|企业级生产环境首选|
|**Protobuf**​|紧凑、强类型、gRPC 生态|需要 protoc 编译|已有 Protobuf 定义的系统|
|**JSON**​|人类可读、无依赖|无 schema 约束、体积大|开发环境、简单场景|
|**JSON Schema**​|JSON + schema 约束|体积比 Avro 大|需要 JSON 兼容性的场景|

**Converters 的角色**：Kafka Connect 的 converter 负责在 Connect 内部数据表示和 Kafka 的字节格式之间转换。对于 source 连接器，converter 把数据序列化为写入 topic 的格式；对于 sink 连接器，converter 把 topic 中的字节反序列化为 Connect 内部格式。

> 📌 **工业铁律**：生产环境用 Avro + Schema Registry。Schema 是"管道上下游组件之间的 API 契约"，Schema Registry 让这个契约可版本化、可演进、可兼容检查。没有 Schema Registry 的 Kafka 管道，等于没有版本管理的微服务 API。

### 9.1.5 转换

转换分为两类，必须分清边界：

**SMT（Single Message Transform，单消息转换）**：

- 逐条处理，轻量级
- 常见操作：字段重命名、添加时间戳、路由到不同 topic、掩码敏感字段
- 链式组合：可以串联多个 SMT

**流式处理框架（Kafka Streams / Flink）**：

- 有状态操作、聚合、join、窗口
- 重转换应该下沉到这里

> ⚠️ Confluent 的生产指南明确警告：**复杂的或大量的 SMT 会引入显著的延迟。如果它们成为瓶颈，考虑将繁重的转换卸载到专用的流处理框架（如 Flink 或 Kafka Streams）**。

**经验法则**：

- 字段级映射、简单路由 → SMT
- 跨消息聚合、多流 join、状态ful 计算 → Kafka Streams/Flink

### 9.1.6 安全性

数据管道的安全性是分层的：

**传输层**：

- TLS 加密 worker 与 broker、worker 与外部系统之间的所有通信
- SASL/SSL 认证（SCRAM、Kerberos、mTLS）

**授权层**：

- Kafka ACL：worker 只拥有它需要的最小权限（读写特定 topic）
- 精确一次源连接器需要特定的 ACL：Write/Describe 权限在 TransactionalId 资源上，以及 IdempotentWrite 集群权限

**凭据管理**：

- 绝不在连接器配置中硬编码密码
- 使用 Kafka Connect Secret Providers：配置中用占位符 `${vault:secret/prod/db_password}`，运行时从外部 secrets manager 解析
- 支持凭据轮换而无需重启连接器

**插件安全**：

- 每个连接器插件都是在 worker JVM 中运行的第三方代码
- 在多租户环境中需要隔离和加固

### 9.1.7 故障处理

这是区分"玩具管道"和"生产管道"的关键。

**背压（Backpressure）处理**：

- 降低 sink 连接器的 `max.poll.records`
- 监控 consumer lag，设置告警
- 根本解决方案：扩展目标系统容量

**错误隔离与 DLQ（Dead Letter Queue）**：

```
errors.tolerance = 'all'
errors.deadletterqueue.topic.name = dlq-topic
errors.deadletterqueue.context.headers.enable = true
```

这套配置确保：

- 单条"毒消息"不会导致整个任务停止
- 失败消息进入 DLQ 主题，附加上下文（堆栈、原始 topic）
- 主数据流不中断

**重试与幂等**：

```
errors.retry.timeout = 300000
errors.retry.delay.max.ms = 10000
```

- 临时性错误（网络抖动）自动重试
- Sink 必须实现幂等写入，避免重试导致重复

**Worker 故障**：

- 分布式模式下，worker 失败，其任务自动重新分配到活跃 worker
- 这是 Connect 相比"裸客户端脚本"的核心优势之一

### 9.1.8 耦合性和灵活性

这是架构层面的考量，决定了你的管道是"刚性"还是"柔性"。

**松耦合原则**：

- Source 系统不需要知道数据最终去哪里
- Sink 系统不需要知道数据从哪里来
- Kafka 作为中央枢纽解耦所有系统

**灵活性体现**：

- 新增 Sink：只需部署新的 sink 连接器，Source 无感知
- 替换 Source：只需部署新的 source 连接器，Sink 无感知
- 多消费者模式：一个 Source 的数据可以被 N 个 Sink 同时消费

> 💡 **这是 Kafka 作为"数据中枢"架构的核心价值**：相比点对点的 ETL（A→B 直接连接），以 Kafka 为中心的架构让每个系统只需与 Kafka 对话，系统间两两解耦。100 个系统的集成，从点对点的 4950 条连接，简化为与 Kafka 的 200 条连接。

### 洞见：八个维度的"第一性原理"

把九个考量维度抽象到底层，其实是回答三个问题：

1. **数据怎么流动？**​ → 及时性、吞吐量（时间与速率维度）
2. **数据是什么？**​ → 数据格式、转换（语义维度）
3. **数据流动得可靠吗？**​ → 可靠性、故障处理、安全性（信任维度）
4. **系统间如何组织？**​ → 耦合性和灵活性（架构维度）

这四个问题构成了数据管道工程的"第一性原理框架"。任何管道方案，无论技术栈如何，都必须在这四个维度上给出答案。

## 9.2 何时使用 Connect API 或客户端 API

这是工程师最常问的问题。答案的路径依赖清晰：

**使用 Kafka Connect 的场景**：

- 数据集成的"管道"性质明显：从 A 系统搬到 B 系统
- 需要利用现成的连接器（数据库 CDC、S3、ES、HDFS 等）
- 需要框架级的可靠性保证（offset 管理、任务重启、横向扩展）
- 团队不想维护大量 Producer/Consumer 代码
- 需要 DLQ、SMT、Schema Registry 集成等开箱即用能力

**使用客户端 API（Producer/Consumer）的场景**：

- 应用本身就在产生/消费事件（如微服务）
- 需要精细控制消息的 key、partition 路由
- 业务逻辑与数据生产/消费紧密耦合
- 需要事务性语义与应用业务逻辑深度集成
- 实时流处理（Kafka Streams）而非简单的数据搬运

> 💡 **经验法则**：如果是"系统集成"（system integration）→ Connect；如果是"应用开发"（application development）→ 客户端 API。两者的边界在于：你的代码核心是"搬运数据"还是"处理业务逻辑"。

## 9.3 Kafka Connect

### 9.3.1 运行 Connect

Connect 有两种部署模式：

**Standalone 模式**：

- 单进程运行
- offset 存储在本地文件
- 适用于开发、小数据量场景

**Distributed 模式**：

- 多 worker 组成集群
- 三个内部 topic：
    - `config.storage.topic`：存储连接器配置
    - `status.storage.topic`：存储连接器状态
    - `offset.storage.topic`：存储 source 连接器的偏移量
- Worker 故障自动重新平衡任务
- 生产环境唯一选择

**核心架构**：

```
┌──────────────────────────────────────────────┐
│ Kafka Connect Cluster                         │
│  ┌────────────┐  ┌────────────┐  ┌─────────┐ │
│  │  Worker 1  │  │  Worker 2  │  │ Worker 3│ │
│  │ ┌────────┐ │  │ ┌────────┐ │  │ ┌─────┐ │ │
│  │ │Task 1  │ │  │ │Task 2  │ │  │ │Task3│ │ │
│  │ │(Source)│ │  │ │(Sink)  │ │  │ └─────┘ │ │
│  │ └────────┘ │  │ └────────┘ │  │         │ │
│  └────────────┘  └────────────┘  └─────────┘ │
└──────────────────────────────────────────────┘
        │                            │
        ↓                            ↓
   External Source              External Sink
   (Database, etc.)            (ES, S3, etc.)
```

**REST API 是管理入口**：

```
# 创建连接器
curl -X POST http://connect:8083/connectors \
  -H "Content-Type: application/json" \
  -d @mysql-source.json

# 查看连接器状态
curl http://connect:8083/connectors/mysql-source/status

# 暂停/恢复
curl -X PUT http://connect:8083/connectors/mysql-source/pause
curl -X PUT http://connect:8083/connectors/mysql-source/resume

# 删除
curl -X DELETE http://connect:8083/connectors/mysql-source
```

### 9.3.2 连接器示例：文件数据源和文件数据池

这是 Kafka Connect 自带的示例连接器，用于演示：

**FileStreamSourceConnector**：

- 从 worker 文件系统读取文件
- 每行转换为一条记录发送到 Kafka topic

**FileStreamSinkConnector**：

- 从 Kafka topic 读取消息
- 每条消息写入一行到输出文件

配置示例：

```
{
  "name": "file-source",
  "config": {
    "connector.class": "org.apache.kafka.connect.file.FileStreamSourceConnector",
    "tasks.max": "1",
    "file": "/var/log/app.log",
    "topic": "app-logs",
    "value.converter": "org.apache.kafka.connect.json.JsonConverter",
    "value.converter.schemas.enable": "false"
  }
}
```

> 💡 虽然这是个教学示例，但它揭示了 Connect 的核心模式：**连接器只负责"与外部系统的协议对接"，框架负责"与 Kafka 的读写"**。这种设计让连接器插件可以专注于外部系统的特殊性，而不必关心 Kafka 的细节。

### 9.3.3 连接器示例：从 MySQL 到 ElasticSearch

这是工业界最常见的 CDC 场景。

**整体架构**：

```
MySQL (binlog) 
   ↓ Debezium MySQL Source Connector
Kafka topic: mysql.inventory.products
   ↓ ES Sink Connector  
Elasticsearch index: products
```

**Debezium Source 配置**：

```
{
  "name": "mysql-cdc-source",
  "config": {
    "connector.class": "io.debezium.connector.mysql.MySqlConnector",
    "tasks.max": "1",
    "database.hostname": "mysql.example.com",
    "database.port": "3306",
    "database.user": "${vault:mysql/user}",
    "database.password": "${vault:mysql/password}",
    "database.server.id": "184054",
    "database.server.name": "mysql-prod",
    "database.include.list": "inventory",
    "table.include.list": "inventory.products,inventory.orders",
    "database.history.kafka.bootstrap.servers": "kafka:9092",
    "database.history.kafka.topic": "schema-changes.inventory",
    
    "key.converter": "io.confluent.connect.avro.AvroConverter",
    "key.converter.schema.registry.url": "http://schema-registry:8081",
    "value.converter": "io.confluent.connect.avro.AvroConverter",
    "value.converter.schema.registry.url": "http://schema-registry:8081",
    
    "transforms": "unwrap,route",
    "transforms.unwrap.type": "io.debezium.transforms.ExtractNewRecordState",
    "transforms.route.type": "org.apache.kafka.connect.transforms.RegexRouter",
    "transforms.route.regex": "([^.]+)\\.([^.]+)\\.([^.]+)",
    "transforms.route.replacement": "$2-$3",
    
    "errors.tolerance": "all",
    "errors.deadletterqueue.topic.name": "dlq-mysql-cdc",
    "errors.deadletterqueue.context.headers.enable": true
  }
}
```

**ES Sink 配置**：

```
{
  "name": "es-sink-products",
  "config": {
    "connector.class": "io.confluent.connect.elasticsearch.ElasticsearchSinkConnector",
    "tasks.max": "3",
    "topics": "products",
    "connection.url": "https://elasticsearch:9200",
    "connection.username": "${vault:es/username}",
    "connection.password": "${vault:es/password}",
    "type.name": "_doc",
    "key.ignore": "true",
    "schema.ignore": "true",
    "topic.key.ignore": "products:true",
    "transforms": "keyfromid",
    "transforms.keyfromid.type": "org.apache.kafka.connect.transforms.ExtractField$Key",
    "transforms.keyfromid.field": "id",
    
    "consumer.isolation.level": "read_committed",
    
    "errors.tolerance": "all",
    "errors.deadletterqueue.topic.name": "dlq-es-sink",
    "errors.deadletterqueue.context.headers.enable": true,
    
    "max.batch.size": "2000",
    "linger.ms": "500",
    "flush.timeout.ms": "10000"
  }
}
```

**关键技术要点**：

1. **Debezium 通过 binlog 捕获变更**，保证捕获所有 INSERT/UPDATE/DELETE
2. **SMT `ExtractNewRecordState`**​ 把 Debezium 的变更封装"展开"为干净的记录
3. **ES Sink 用记录的 key 作为文档 ID**，实现 upsert 语义——天然幂等
4. **`consumer.isolation.level=read_committed`**：确保 sink 只读取已提交的事务消息
5. **DLQ 配置**：任何无法写入 ES 的记录进入 DLQ，主流程不中断

> 💡 **为什么这个管道是"生产级"的**：
> 
> - Source 端：CDC 保证不丢不失
> - 传输：Kafka 的 RF=3 + acks=all 保证可靠
> - Sink 端：ES 的文档 ID upsert 保证幂等
> - 故障：DLQ 隔离毒消息，offset 机制保证重启续传
> - 安全：Vault 管理凭据，TLS 加密传输

### 9.3.4 单一消息转换（SMT）

SMT 是 Connect 的"轻量级转换层"，在消息从连接器传递到 converter 之前（source）或之后（sink）执行。

**内置 SMT 示例**：

|SMT|功能|
|---|---|
|`ExtractField`|提取嵌套字段|
|`ReplaceField`|重命名/删除/添加字段|
|`MaskField`|掩码敏感字段|
|`RegexRouter`|基于正则重路由 topic|
|`TimestampRouter`|基于时间戳路由 topic|
|`Filter`|基于谓词过滤消息|
|`InsertHeader` / `InsertField`|插入头部/字段|
|`Debezium ExtractNewRecordState`|展开 Debezium 变更封装|

**链式组合**：

```
"transforms": "addTS,maskPII,route",
"transforms.addTS.type": "org.apache.kafka.connect.transforms.InsertField$Value",
"transforms.addTS.timestamp.field": "extracted_at",
"transforms.maskPII.type": "com.example.MaskPIITransform",
"transforms.maskPII.fields": "credit_card,ssn",
"transforms.route.type": "org.apache.kafka.connect.transforms.RegexRouter",
"transforms.route.regex": "(.*)",
"transforms.route.replacement": "processed-$1"
```

**谓词（Predicates）**：

```
"predicates": "isPII",
"predicates.isPII.type": "org.apache.kafka.connect.transforms.predicates.TopicNameMatches",
"predicates.isPII.pattern": ".*-pii",
"transforms.maskPII.predicate": "isPII"
```

> ⚠️ **SMT 的边界**：SMT 是"逐条、无状态"的转换。如果你需要跨消息的状态（如"计算滑动窗口平均"），SMT 做不到——这时候必须用 Kafka Streams 或 Flink。把 SMT 当"数据清洗层"，把流处理当"数据计算层"，职责分离。

### 9.3.5 深入理解 Connect

**任务调度与再平衡**：

Connect 使用类似消费者组的再平衡协议。当 worker 加入/离开、连接器配置变更、任务数变更时，触发再平衡：

1. 所有 worker 重新分配连接器及其任务
2. 再平衡期间管道短暂暂停
3. 再平衡完成后恢复

**Offset 管理**：

- Source 连接器通过 `OffsetStorageWriter` 报告从外部系统读取的位置
- 框架定期持久化 offset 到 `offset.storage.topic`
- 故障重启后，从最后持久化的 offset 恢复

**Exactly-Once Source 支持**（Kafka 3.3+）：

KIP-618 引入了对 source 连接器精确一次的支持：

- Worker 配置 `exactly.once.source.support=enabled`
- 框架为每批 source task 返回的记录创建并提交 Kafka 事务
- 偏移量提交与消息生产在同一个事务中
- 崩溃恢复时，未完成的事务回滚——既不丢也不重

**连接器定义的边界**：

```
public class MySourceConnector extends SourceConnector {
    @Override
    public ExactlyOnceSupport exactlyOnceSupport(Map<String, String> props) {
        // 连接器声明是否支持 EOS
        return ExactlyOnceSupport.SUPPORTED;
    }
    
    @Override
    public ConnectorTransactionBoundaries canDefineTransactionBoundaries(Map<String, String> props) {
        // 连接器是否可以自定义事务边界
        return ConnectorTransactionBoundaries.SUPPORTED;
    }
}
```

**事务边界控制**：

默认情况下，框架为每个 `poll()` 返回的记录批次创建一个事务。但连接器可以自定义：

```
private int recordsSent;

@Override
public List<SourceRecord> poll() {
    List<SourceRecord> records = fetchRecords();
    for (SourceRecord record : records) {
        if (++this.recordsSent % 10 == 0) {
            this.context.transactionContext().commitTransaction(record);
        }
    }
    return records;
}
```

> 💡 **为什么需要自定义事务边界**：当一个源文件/对象被拆分为多条记录、但应该原子性投递时，自定义边界确保"要么全部投递成功，要么全部回滚"。

### 洞见：Connect 的"第一性原理"

Connect 的本质是：**把"数据进出 Kafka"这件事本身，建模为一个分布式的、可插拔的、有状态管理的框架**。

四个核心抽象各司其职：

- **Connector**：定义"从哪到哪"（逻辑作业）
- **Task**：定义"怎么并行搬"（物理执行单元）
- **Worker**：定义"在哪跑"（运行时容器）
- **Converter + Transform**：定义"数据长什么样、要不要改"

这种"逻辑/物理/运行时/数据"的四层分离，是 Connect 能够支撑大规模数据管道的根本原因。它让：

- **开发者**只需实现连接器插件（关注外部系统协议）
- **运维者**只需部署 worker 集群、配置连接器实例
- **架构师**只需组合连接器构建管道

而框架本身处理了所有"脏活"：offset 管理、任务调度、故障转移、再平衡、DLQ、Schema Registry 集成、EOS……

> 📌 **这正是"框架"与"库"的区别**：裸 Producer/Consumer 是库——你得自己处理 offset、重试、故障转移；Connect 是框架——这些都被框架吸收，你只需声明"意图"。

## 9.4 Connect 之外的选择

Connect 不是唯一答案。工业界还有其他选择：

### 9.4.1 其他数据存储系统的数据摄入框架

- **Apache NiFi**：基于 Web 的、可视化的数据流管理工具，强调数据血缘和回溯
- **Apache Airflow**：以 DAG 定义管道，适合批处理调度
- **云厂商托管服务**：AWS DMS、GCP Dataflow、Azure Data Factory

适用场景对比：

|工具|优势|劣势|
|---|---|---|
|Kafka Connect|Kafka 原生、实时、框架级可靠性|只擅长 Kafka↔外部系统|
|NiFi|可视化、数据血缘、协议丰富|学习曲线陡、Kafka 集成需额外配置|
|Airflow|复杂的 DAG 编排、调度能力强|批处理导向，实时性弱|

### 9.4.2 基于图形界面的 ETL 工具

- **Talend、Informatica、Matillion**​ 等传统 ETL 工具
- **优势**：业务分析师可用、丰富的连接器生态
- **劣势**：实时性弱、与 Kafka 的流模型不匹配、成本高

> 💡 这类工具正在被"Kafka Connect + dbt + 流处理"的现代数据栈替代。ETL 中的"T"（转换）正在向"ELT"演变——先入 Kafka（E+L），再用流处理/Kafka Streams 做转换（T）。

### 9.4.3 流式处理框架

- **Kafka Streams**：轻量级、Kafka 原生、Java/Scala API
- **Apache Flink**：重量级、exactly-once 状态管理、SQL 支持
- **Apache Spark Structured Streaming**：微批处理模型

**关键区分**：

```
Connect 负责：系统间数据搬运（无状态或简单状态）
流处理框架负责：数据计算与转换（有状态、跨消息）
```

> 💡 **现代数据管道的标准架构**：
> 
> ```
> Source System → [Connect Source] → Kafka → [Stream Processing] → Kafka → [Connect Sink] → Sink System
> ```
> 
> Connect 做"边界"，流处理做"内核"。

### 洞见：为什么 Connect 在大多数场景下是正确答案

回到第一性原理——数据管道的本质是"外部系统的状态变化 ↔ Kafka 日志流的双向映射"。

这种映射有几个固有特征：

1. **协议多样性**：每个外部系统有自己的协议（JDBC、binlog、REST、S3 API…）
2. **可靠性要求**：不能丢、不能重、故障可恢复
3. **水平扩展性**：数据量会增长
4. **运维可见性**：状态、监控、告警、DLQ

裸写 Producer/Consumer 客户端要自己处理所有这些——相当于每个管道都在重新发明轮子。Connect 的价值在于：**它把这些共性抽象为框架能力，让"与外部系统对接"变成"配置一个连接器"**。

但 Connect 并非银弹：

- **延迟极度敏感的场景**：如高频交易，可能需要裸客户端微调
- **复杂事件处理**：Connect SMT 能力不足，必须配合流处理
- **非 Kafka 中心的架构**：如果管道不涉及 Kafka，Connect 无意义

### 给读者的"数据管道心智模型"

> 📌 **全章最核心的一句话**：数据管道的本质是"外部系统的状态变化与 Kafka 日志流之间的双向可靠映射"——Kafka Connect 之所以成为这个领域的事实标准，是因为它把"映射"这件事框架化：Connector 定义端点、Task 提供并行、Worker 提供运行时、Converter 处理格式、Transform 处理轻量转换、框架本身提供 offset 管理、故障转移、EOS 和 DLQ。当你用 Connect 而非裸客户端构建管道时，你买的不是"一个工具"，而是"一整套数据集成的最佳实践"。

**三个必须刻进肌肉记忆的认知**：

1. **Connect 解决"边界"，流处理解决"内核"**：数据进出 Kafka 用 Connect，数据在 Kafka 内部的计算用 Kafka Streams/Flink。两者职责分明，组合使用。
2. **EOS 是有条件的**：Kafka 3.3+ 支持 source 连接器的精确一次，但需要 worker 启用 `exactly.once.source.support`，且连接器本身声明支持；sink 端的精确一次则依赖目标系统的幂等或事务能力。配置 `isolation.level=read_committed` 是 sink 端的必要但不充分条件。
3. **Schema Registry 不是可选项**：生产环境的管道必须用 Avro/Protobuf + Schema Registry。Schema 是"管道上下游之间的 API 契约"——没有版本化契约的数据管道，注定在第一次 schema 变更时崩溃。

**工业界真相**：

> 大多数"数据管道项目失败"的根源，不是技术选型错误，而是忽视了这八个维度中的某一个。最常见的两个坑：一是用 JSON 裸奔不带 schema，导致三个月后 schema 变更引发全链路故障；二是用 SMT 做重度转换，导致 Connect worker CPU 打满、管道延迟飙升。避免这两个坑，你的管道就超越了 80% 的行业实践。
