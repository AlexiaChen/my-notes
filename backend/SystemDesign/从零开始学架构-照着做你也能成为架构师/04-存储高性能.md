# 《从零开始学架构》读书笔记 · 第4章 存储高性能

> **一句话定位第4章**：当第1～3章告诉你"架构要解决复杂度"，第4章就聚焦其中最硬核、最高频的一个复杂度——**数据量大了、并发高了，存储怎么撑住**。它给出三条递进的技术路线：**关系数据库的"拆而用之"（读写分离/分库分表）→ NoSQL 的"换合适的引擎"→ 缓存的"空间换时间"**。三者不是并列，而是**由浅入深、由改造到替换、由数据库内到数据库外**的解决思路。

---

## 4.1 关系数据库——"能不改存储引擎，就先在 MySQL 内做文章"

关系数据库（MySQL/Oracle）仍是绝大多数系统的"主存储"，因为它提供 ACID 事务、SQL 表达能力、成熟运维体系。第4章的第一性原理是：**在不动存储引擎的前提下，先用"读写分离"分散读压力，再用"分库分表"分散写/存储压力**，把单实例的能力榨干，实在不够再考虑 NoSQL。

### 4.1.1 读写分离——"写主读从，把读流量分流"

**核心原理（工业实现）**：基于 MySQL **主从复制**（binlog → 从库 I/O 线程拉取写 Relay Log → SQL 线程回放）。主库负责所有写（INSERT/UPDATE/DELETE）和强一致读，多个从库承担 SELECT，从而突破单实例的 IO/CPU 瓶颈。

**关键工程要点（书里不会细说、但工业必踩的坑）**：

- **主从延迟是读写分离的"原罪"**：从库串行回放（5.6+ 支持并行复制但仍存在延迟），刚写入主库的数据从库可能"还没到"。**解法**：核心业务（支付、登录、注册后立即读）强制走主库；非核心读走从库。
    
- **复制模式选型**：异步（默认，性能好、可能丢数据）/ 半同步（主库等至少一个从库 ACK，降低丢失风险）/ MGR 组复制（Paxos 多副本强一致，8.0 推荐）。**按业务容忍度选，而非无脑追强一致**。
    
- **路由实现方式对比**：
    

|实现方式|代表|优点|缺点|适用|
|---|---|---|---|---|
|应用层路由|注解+动态数据源|灵活、无中间件损耗|侵入代码、事务处理复杂|简单项目|
|JDBC 驱动层|ShardingSphere-JDBC|配置简单、支持负载均衡|仅 Java、事务控制有限|Java 项目（推荐）|
|代理中间件|MyCat / ProxySQL / ShardingSphere-Proxy|对应用透明、支持多语言|额外网络开销、可能成瓶颈|异构语言/中大型|

**工业实践**：淘宝/美团等大厂读多写少场景普遍"一主多从 + ShardingSphere/MyCat 路由"；**高可用叠加 MHA/Orchestrator + 双主双从**。

**我的洞见（第一性原理）**：读写分离的底层逻辑是**"读多写少"场景下，用"数据冗余"换"读吞吐"**——这和"高可用靠冗余"同源，但目的不同（此处为扩展读能力）。**它解决的是"读瓶颈"，不是"写瓶颈"**；一旦写成瓶颈，就必须走向分库分表。判断该不该做读写分离，先看读写比——读远大于写时才划算。

### 4.1.2 分库分表——"单实例扛不住时，把数据拆到多个实例"

**何时必须分（经验阈值）**：单表数据量 **500万～1000万+**、单表写入 TPS 打满/锁竞争严重、单库连接数被打满、慢查询暴增。**原则：能不分就不分，能垂直就不水平，水平拆分是最后手段**。

**两类拆分（维度完全不同）**：

|类型|拆分依据|解决什么|结构|生产优先级|
|---|---|---|---|---|
|**垂直分表**​|按列/字段|大字段、宽表 IO 差|表变多、结构不同|优先做（成本最低）|
|**垂直分库**​|按业务模块|业务耦合、单库压力|库变多（user_db/order_db…）|其次做（契合微服务）|
|**水平分表**​|按行（分片键）|单表数据量过大|表变多、结构相同|最后手段|
|**水平分库分表**​|按行 + 拆库|高并发+大数据终极方案|库表都变多|高并发写入标配|

**水平拆分的核心三要素**：

1. **分片键（Sharding Key）**：必须高基数、查询频繁、尽量不变更（如 user_id/order_id），一旦选定**很难改**。
    
2. **分片算法**：取模（`user_id % N`，均匀但扩容需迁移）/ 范围（按时间，适合冷热分离）/ 一致性哈希（方便扩缩容）。
    
3. **全局唯一 ID**：不能用自增主键，需用 **Snowflake / UUID**（推荐 Snowflake，有序且全局唯一）。
    

**分库分表带来的"新复杂度"（务必提前预案）**：

- 跨库 JOIN → 数据冗余 / 应用层聚合 / 全局表；
    
- 分布式事务 → 最终一致性（MQ+本地消息）/ TCC / Saga / Seata(2PC)；
    
- 分页/排序/count 变复杂 → 中间件聚合或应用层归并；
    
- 扩容需数据迁移 → 初期按 2 的幂次方规划分片数（如 4/8/16）。
    

**我的洞见**：分库分表的本质是**用"分布式"解决"单机容量与并发上限"，代价是把关系数据库的"强一致/易 JOIN"优势部分让渡出去**。这是一个**主动放弃部分关系型便利、换取横向扩展能力**的权衡。因此第2章"合适原则"在此尤为重要——**团队/业务没到那个量级，千万别为了"看起来先进"而提前分库分表**，否则运维复杂度会反噬。

### 4.1.3 实现方法——"客户端分片 vs 中间件分片"

|实现方式|原理|优点|缺点|
|---|---|---|---|
|**应用层（客户端）分片**​|代码内按分片规则路由|无中间件损耗、灵活|侵入代码、跨库 JOIN/事务需自处理、多语言支持差|
|**代理层（中间件）分片**​|代理拦截 SQL 透明路由|对应用透明、支持多语言、含分布式事务|额外网络开销、中间件可能成瓶颈|

**代表中间件**：ShardingSphere（功能全面，Java 中大型首选）、MyCat（MySQL 协议兼容）、ProxySQL（读多写少/查询路由缓存）。**工业建议：Java 项目优先 ShardingSphere-JDBC 或 Proxy；多语言环境用 MyCat/ProxySQL**。

**我的洞见**：实现方式的选择，本质是**"性能/灵活性"与"透明度/运维成本"的取舍**。小团队、强技术能力 → 客户端分片可控；快速上线、标准化、异构语言 → 中间件分片更省心。

## 4.2 NoSQL——"关系型解决不了的，换一个数据模型来解决"

关系数据库的短板：行存储导致列查询 IO 高、Schema 变更需 DDL 锁、全文检索弱、复杂关系查询弱。NoSQL = **Not Only SQL**（而非"No SQL"），定位是**关系型的补充**，按数据模型专精不同场景。

### 四类 NoSQL 与选型（核心对比）

|类型|核心索引/结构|定位|优势|短板|典型代表|适用场景|
|---|---|---|---|---|---|---|
|**K-V 存储**​|哈希表 / Key→黑盒 Value|内存高速缓存|亚毫秒、百万 QPS|仅精确 Key 查、无事务|Redis、Memcached|缓存、会话、计数器、排行榜|
|**文档数据库**​|B 树 / JSON 嵌套文档|灵活结构化持久存储|动态 Schema、嵌套结构免 JOIN|文档≤16MB、JOIN 弱、内存高|MongoDB、Couchbase|CMS、用户画像、产品目录|
|**列式数据库**​|列族 / 按列连续存储|大数据高 IO 分析|高压缩(8:1~30:1)、高写入吞吐、时序友好|不适合点查、无 JOIN、学习陡|HBase、Cassandra、Bigtable|IoT 时序、离线大数据分析、监控|
|**全文搜索引擎**​|倒排索引（+列式正排）|文本检索+聚合|分词/打分/高亮、海量文本检索碾压 RDBMS|非主存储、写性能有限、不保强一致|Elasticsearch、Solr|电商搜索、内容检索、日志 ELK|

**选型口诀（来自工业总结）**：

- 管理/事务型系统（运营、库存、交易、记账）→ **首选关系型 + 缓存 + 一致性**；
    
- 大流量前台（电商单品页）→ 后台关系型 + 前台内存型(KV)；
    
- 日志型 → 原始数据用列式，搜索日志用搜索引擎型；
    
- 搜索型系统 → 前台搜索引擎型（ES），后台关系型；
    
- 离线/实时分析 → 列式（Cassandra/HBase）+ Spark。
    

**我的洞见（第一性原理 + 创新视角）**：

1. **NoSQL 的本质不是"反对 SQL"，而是"按访问模式选存储结构"**——KV 面向"按主键极速取"，文档面向"嵌套对象整体读写"，列式面向"按列聚合扫描"，搜索引擎面向"文本倒排检索"。**数据结构决定它能高效支撑的查询模式**，选错模型，再强的硬件也白搭。
    
2. **"ES 能否替代 MySQL"是经典误区**——不能。ES 是**搜索加速层/辅存储**，不保证强一致、无 JOIN。正确姿势是 **MySQL 作主存储 + ES 作搜索索引**（双写或 CDC 同步），各司其职。
    
3. **现代架构的趋势是"多存储混合栈"（Polyglot Persistence）**：一个系统同时用关系库+Redis+ES+对象存储，按数据访问模式匹配引擎，而非试图让一个数据库解决所有问题。这正是第2章"合适原则"在存储层的落地。

## 4.3 缓存——"用空间换时间，把热点数据放在离 CPU 更近的地方"

缓存是提升存储高性能**成本最低、见效最快**的手段（Redis/Memcached），但其三大经典问题若不加防护，反而会成为系统雪崩的导火索。

### 三大问题与防御方案对比

|问题|核心特征|典型触发|首选解决方案|
|---|---|---|---|
|**缓存穿透**​|查**不存在**的数据，缓存/DB 都没有|恶意攻击(id=-1)、参数非法、数据已删|① 布隆过滤器前置拦截 ② 缓存空值(短 TTL) ③ 接口参数校验|
|**缓存击穿**​|**单个热点 Key**​ 过期瞬间，并发打到 DB|秒杀商品、热搜文章、爆款视频|① 互斥锁(SETNX，单线程回源) ② 逻辑过期/热点 Key 永不过期 ③ 拆分热点 Key|
|**缓存雪崩**​|**大量 Key 同时过期**​ / Redis 集群宕机|批量导入设相同 TTL、集群故障|① TTL 随机化(3600±600s) ② 多级缓存 ③ 熔断降级(Sentinel/Hystrix) ④ Redis 高可用集群|

**关键方案原理解读**：

- **布隆过滤器**：空间效率极高的概率数据结构，O(k) 查询，**"一定不存在"则直接拦截，"可能存在"才放行**；有误判率（可调 0.1%~1%）但无"假阴性"，非常适合黑名单/鉴权/穿透拦截。某电商实践：布隆过滤器拦截 99% 穿透请求，CPU 仅增 3%。
    
- **互斥锁防击穿**：缓存 miss 时 SETNX 抢锁，仅一个线程查 DB 并回写缓存，其余等待重试。
    
- **TTL 随机化防雪崩**：基准过期时间 + 随机偏移，把集中失效打散到时间窗口。
    
- **多级缓存架构（工业标配）**：**本地缓存(Caffeine，ms 级) + 分布式缓存(Redis Cluster，全量)**，层层拦截。Netflix 用 EVCache+本地缓存将读延迟从 10ms 降至 1ms；某社交平台据此使穿透请求减少 80%、DB 压力降 60%。
    

**我的洞见（第一性原理）**：

1. **缓存三大问题的本质都是"缓存未命中时 DB 被击穿"**，区别只在"未命中的原因"——数据不存在(穿透) / 单 Key 过期(击穿) / 批量过期(雪崩)。**防护思路统一为"前置拦截 + 限流回源 + 冗余兜底"**三层防线。
    
2. **缓存不是"加了就快"，而是"加了且命中率高才快"**。必须配合监控命中率、动态调整 TTL、异步回源、缓存预热（系统启动/低峰期提前加载热点数据）。
    
3. **缓存与 DB 一致性是另一大课题**（书中未展开但工业必做）：推荐 **"先更新 DB，再删除缓存"**（Cache Aside）+ 延时双删/异步补偿，避免脏数据。

## 4.4 本章小结 + 三章技术路线串联

**本章核心脉络（由浅入深的解决思路）**：

```
存储高性能的三级递进方案
┌─────────────────────────────────────────────────┐
│ 第1级：关系数据库内优化（不动引擎）              │
│   读写分离 ──► 解决"读瓶颈"（读多写少）         │
│   分库分表 ──► 解决"写/容量瓶颈"（横向扩展）    │
├─────────────────────────────────────────────────┤
│ 第2级：换合适的存储引擎（NoSQL）                 │
│   KV / 文档 / 列式 / 搜索引擎 ──► 按数据模型选型 │
│   原则：NoSQL 是 SQL 的补充，多存储混合栈        │
├─────────────────────────────────────────────────┤
│ 第3级：缓存（空间换时间，数据库外加速）          │
│   Redis + 多级缓存 ──► 防穿透/击穿/雪崩          │
└─────────────────────────────────────────────────┘
```

**贯穿全章的第一性原理**：存储高性能的本质是 **"把对的数据放在对的引擎里，把热的数据放在离 CPU 更近的地方"**——即**按数据的访问模式（读多/写多/点查/扫描/全文检索/热点）匹配最合适的存储结构与位置**，而非盲目堆硬件或追新技术。

**与前面章节的联系**：

- 第1章"复杂度来源"中的**高性能**、第3章"识别复杂度→设计备选方案"的流程，在本章落地为**具体可执行的存储架构模式**；
    
- 第2章"合适原则"在本章体现得淋漓尽致——**能读写分离就不分库分表，能关系型解决就不上 NoSQL，能加缓存就不改存储引擎**；每一步"升级"都意味着复杂度的增加，务必"在当前约束下选最合适的那一级"。
