# 《从零开始学架构》读书笔记 · 第8章 存储高可用

> **一句话定位第8章**：第7章用 FMEA 教会我们"如何发现存储单点故障的隐患"，第8章则给出**消除这些隐患、让存储"不中断服务"的具体架构模式**。全书脉络在此清晰浮现——第4章"存储高性能"（分库分表/NoSQL/缓存）解决"存得快"，第8章"存储高可用"解决"存得稳（不丢、不断）"。二者常需**同时达成**，却又在资源投入上存在天然张力（加机器：高性能为"扩展"、高可用为"冗余"），这正是架构师持续要做取舍的地方。

## 8.1 主备复制——"备胎式"最简高可用

### 8.1.1 基本实现

- **结构**：一主一备（或一主多备）。**主机承担所有读写**，备机平时**不参与业务读写**，仅通过 binlog/oplog 实时同步主机数据，处于待命状态；主机宕机后**人工**将备机提升为主机。
    
- **同步方式**：MySQL 异步复制（默认，性能好、可能丢数据）/ 半同步（至少一从确认，RPO 接近 0，写性能下降约 7-12%）/ 全同步（所有从确认，最安全、性能最低）。
    

### 8.1.2 优缺点分析

- **优点**：① 架构**最简单**，客户端无需感知备机存在，故障恢复后只需改连接地址；② 主机/备机仅需数据复制，无需状态判断与自动切换逻辑。
    
- **缺点**：① 备机长期闲置，**硬件利用率仅约 50%，成本浪费**；② 故障后**需人工干预**，恢复慢且易出错。
    
- **适用**：传统企业内部小规模系统、对成本不敏感但要求绝对简单的场景。
    

**我的洞见（第一性原理）**：主备复制的本质是**"用 100% 的硬件冗余，换取主机故障时的可恢复性"**——它解决的是"数据不丢、能恢复"，而非"服务不中断"。备机不扛流量，因此**对"读吞吐"毫无帮助**，这也是它与下一节"主从复制"的根本分水岭。理解这一点，就不会在"需要读扩展"的场景误选主备。

## 8.2 主从复制——"读写分离"兼顾性能与高可用

### 8.2.1 基本实现

- **结构**：主机负责**写**（增删改），**从机负责读**（查询），主机通过 binlog 将变更同步给从机。
    
- **核心机制**：三个线程——Binlog Dump Thread（主库读 binlog 发送）、IO Thread（从库接收写 relay log）、SQL Thread（从库回放 relay log）。
    

### 8.2.2 优缺点分析

- **优点**：① 主机故障时**读业务可继续由从机承担**，可用性优于主备；② 从机分担读流量，**发挥硬件性能、提升整体吞吐**。
    
- **缺点**：① 客户端需**感知主从关系**，应用架构要做读写分离，**复杂度高于主备**；② **主从延迟**导致从机可能读到旧数据（最终一致性问题）；③ 故障时仍需**人工干预**。
    
- **适用**：**写少读多**的业务（论坛/BBS/新闻网站，读是写的 10～100 倍以上）。
    

**我的洞见（创新视角）**：主从复制是**"一份冗余，两种收益"**的典范——同一份数据副本，既用于**读扩展（高性能）**，又用于**故障兜底（高可用）**。这恰好印证了第4章与第8章的内在联系：**主从复制同时是"高性能手段"（读分流）和"高可用手段"（读业务容灾）**。但也正因从机扛读流量，**主从延迟**成了它绕不开的"原罪"（见 8.1/4.1.1 的应对：核心读走主库、监控 Seconds_Behind_Master）。

## 8.3 主备倒换与主从倒换——"让切换自动化"

主备/主从的致命短板是"需人工切换"。**主备倒换/主从倒换**就是引入**自动故障转移（Failover）机制**，把"人肉切换"变成"自动切换"。

### 8.3.1 设计关键

- **状态判断（心跳+多源确认）**：监控节点定期心跳探测；为避免"监控节点自身网络抖动导致误切换/脑裂"，**主库连不上时需让从库也确认**（多方验证确诊）。
    
- **数据补偿（尽力少丢）**：确诊后，Manager 尝试通过 SSH 登录原主库磁盘，**强行拷贝未传出的 binlog 补发给从库**；若主库彻底断电，则以**数据最新（Relay Log 最多/GTID 最靠前）的从库为基准**切换（结合半同步可保证数据不丢）。
    
- **VIP 漂移**：切换后通过脚本/arping/Keepalived 将**虚拟 IP 从老主解绑、绑定到新主**，应用闪断重连，**10～30 秒内业务恢复**，对应用透明。
    

### 8.3.2 常见架构（工业主流方案对比）

|方案|原理|优点|缺点|适用|
|---|---|---|---|---|
|**MHA**（Master High Availability）|Manager-Agent 架构；心跳监控→多方确诊→选数据最全从库→binlog 补全→VIP 漂移|支持 GTID/传统复制；binlog 抢救机制，**数据丢失量低于普通切换**；对应用透明|开源版已停维护、对 MySQL 8.0 新特性适配弱；Manager 有单点风险需热备|传统金融外围、中大型网站后台|
|**Orchestrator + Consul/ProxySQL**​|GitHub 开源；定期嗅探构建拓扑、GTID 跟踪；通过 **Raft 共识**实现自身高可用，不会成为单点|可视化拓扑+REST API；支持 Hook 对接 VIP/DNS 自定义操作；可纳入自动化运维|需额外部署 etcd/Consul 等 DCS 实现自身 HA，组件多、运维复杂度高于 MHA|有运维能力的中大规模企业、云原生/多区域部署|
|**Group Replication / InnoDB Cluster**​|MySQL 官方；基于 **Paxos 协议**实现多主+自动选主+强一致|数据强一致（多数派确认）、自动故障切换、多主写入|节点越多协商越慢、对网络延迟要求高（易脑裂）|需强一致+自动切换的场景|

**工业实践印证**：美团 2015 年前用 MMM（踩坑多），2015 年起全面切到 **MHA**，并做了防脑裂优化（如主库未完全挂时先加全局读锁再切换）。

**我的洞见（第一性原理）**：

1. **倒换机制的本质是"用一致性协议/协调机制，把人工决策自动化"**——MHA 用 Manager+SSH 做中心化决策，Orchestrator 用 Raft 做分布式决策，MGR 用 Paxos 做组内共识。**选哪种，本质是"用什么样的协调机制来避免误切换和脑裂"的取舍**。
    
2. **主备倒换 vs 主从倒换**：主备倒换是"备机原不参与业务、切换后接管全部读写"；主从倒换是"从机原本就扛读、切换后只读从机升为主、其余从机重定向新主"。**后者切换更平滑（读能力不中断），但架构更复杂**——这再次体现"合适原则"：能主备解决的别上主从倒换。

## 8.4 主主复制——"双活写入"，收益与风险并存

- **基本实现**：两个 MySQL **互为主从**（双向复制），**两者均可处理读写**，数据双向同步。
    
- **优点**：① 任一主故障，另一主**继续服务，几乎无停机**；② 两主分担读写负载，**写 TPS 理论上可翻倍**。
    
- **致命缺点——冲突处理**：双向复制极易**数据冲突**（两主同时更新同一行、自增 ID 重复），需额外机制解决。
    
- **工业必备规避手段**：
    
    - 设置 `auto_increment_increment` + `auto_increment_offset`（如两主分别 offset=1/2、increment=2），**避免自增 ID 冲突**；
        
    - **应用层写入路由控制**（如按用户 ID 哈希/奇偶拆分写范围），避免两主写同一行；
        
    - 启用 GTID 复制 + 半同步，配合 MHA/Orchestrator 做自动故障转移。
        
    

**我的洞见（创新视角）**：主主复制是**"用复杂度换写入高可用/写扩展"**的权衡。**它的价值不在"两主同时随便写"，而在"双活容灾 + 可控的写入拆分"**——生产环境几乎都要通过业务拆分把写入"分片"到两个主，否则冲突解决的成本会吞噬双写的收益。正如 MySQL 权威实践所言："允许向两台主库写入所带来的麻烦，远远大于其带来的好处"，**主主能不用则不用，要用则必须配齐冲突规避全套方案**。这与第2章"简单原则"高度呼应。

## 8.5 数据集群——"多副本协同，从集中到分散"

当数据量/并发超过主从架构上限，需走向**集群**：多节点协同，通过副本保证高可用、通过分片保证可扩展。

### 8.5.1 数据集中集群

- **特征**：数据**集中存储**（不分片），多节点通过**副本**保证高可用，客户端视角像访问一个整体。
    
- **典型**：MySQL Group Replication / InnoDB Cluster（多主、Paxos 共识、强一致）、MySQL Cluster（NDB，天然多主但非双向复制模型）。
    
- **适用**：需要**强一致+自动故障切换**、数据量尚未到必须分片程度的场景。
    

### 8.5.2 数据分散集群

- **特征**：数据**按分片分布到多个节点**（每个节点存部分数据），每个分片配主从副本保证高可用。
    
- **典型**：
    
    - **Redis Cluster**：16384 个哈希槽分片，每个主节点负责部分槽、配从节点备份；故障时节**点通过类 Raft 投票选举新主**；无中心节点，用 **Gossip 协议**传播状态、达到**最终一致**。
        
    - **Cassandra**：一致性哈希分片 + 多主复制，可调一致性级别（ONE/QUORUM/ALL），**AP 倾向、高可用优先**。
        
    - **TiDB（TiKV）**：Range 分片 + **Raft 协议**（每个 Region 是一个 Raft 组），既支持范围查询又保证强一致。
        
    - **HBase**：按 RowKey 范围分片（Region），Region 分裂后按范围重新分配。
        
    

### 8.5.3 分布式事务算法

分散集群跨分片写需保证事务语义，常见方案：**2PC（两阶段提交，强一致但协调者单点、阻塞）**、**TCC（Try-Confirm-Cancel，业务层补偿）**、**Saga（长事务、事件驱动补偿）**、**本地消息表/事务消息（基于 MQ 的最终一致）**——与第6章 BASE/最终一致哲学一脉相承。

### 8.5.4 分布式一致性算法

集群节点间"选主 + 日志复制 + 数据一致"的基石算法：

|算法|核心机制|复杂度|典型应用|适用场景|
|---|---|---|---|---|
|**Raft**​|领导者选举+日志复制+任期机制，多数派确认|低（易实现）|etcd、Consul、TiDB PD、Redis Cluster（变种）、Kafka KRaft、RocketMQ、Nacos|配置中心、分布式锁、库存一致性|
|**Paxos**​|提案-批准机制（Prepare/Accept）|高|Chubby、Google Spanner、MySQL Group Replication|复杂分布式存储、电信级|
|**ZAB**​|基于 Raft 改进，领导者固定任期+数据广播|中|ZooKeeper|服务注册中心、分布式协调|
|**Gossip**​|去中心化，节点随机扩散同步，**最终一致**​|低|Redis Cluster、Cassandra|非核心数据同步、状态传播|

**关键认知**：强一致系统（etcd/ZooKeeper/TiDB）选 Raft/Paxos/ZAB；高可用优先、可接受最终一致的系统（Cassandra/Redis Cluster 状态同步）用 Gossip+Raft 混合。

**我的洞见（第一性原理 + 创新视角）**：

1. **数据集中集群 vs 分散集群的根本区别，是"数据是否分片"**——集中集群靠"副本冗余"保高可用（不分片），分散集群靠"分片+副本"同时保**可扩展（分片）**与**高可用（副本）**。前者简单、强一致易保证；后者扩展性强，但引入跨分片事务与一致性难题。
    
2. **一致性算法的选择，本质是"一致性强弱"与"可用性/扩展性"的取舍（呼应第6章 CAP）**：Raft/Paxos→CP/强一致；Gossip→AP/最终一致。**没有"最好"的算法，只有"与业务一致性要求匹配"的算法**——这正是"合适原则"在集群层的落地。
    
3. **现代趋势是"混合协议"**：如 TiDB 用 Raft 保强一致、Redis Cluster 用 Gossip+Raft 混合、TDengine 混合范围+哈希分片。**单一协议难以兼顾一致性与扩展性，按场景组合才是工程正解**。

## 8.6 数据分区——"把海量数据切分到多节点"

分区（Sharding）是分散集群"数据怎么切、怎么分布、怎么冗余"的具体策略。

### 8.6.1 数据量（为什么要分区）

单节点存储/IO 有上限，**数据量超过单机容量或写入吞吐打满时，必须水平分区**把数据分布到多节点，突破单机瓶颈。

### 8.6.2 分区规则（数据怎么切）

|策略|原理|优点|缺点|适用|
|---|---|---|---|---|
|**哈希分片**​|对分片键哈希取模（如 `user_id % N`）|数据均匀分布、避免热点、天然支持水平扩展|范围查询效率低、扩容需大量迁移|用户数据、无需范围查询|
|**范围分片**​|按字段值区间划分（如时间/ID 范围）|适合有序数据、范围查询高效|易产生**热点区间**（最新时间段访问集中）|时序数据、IoT、时间序列|
|**一致性哈希**​|哈希环+虚拟节点（如 Cassandra/Redis 16384 槽）|节点增减**仅影响相邻数据**，迁移量降至 1/N（3→4 节点仅迁 25%，传统哈希需迁 75%）|实现较复杂|频繁扩缩容环境|
|**混合分片**​|范围+哈希结合（如 TDengine：时间窗口+设备 ID 哈希）|兼顾范围查询与负载均衡、避免热点|策略设计复杂|物联网时序等复合场景|

**工业实践**：电商订单按 `user_id` 哈希分片；IoT 时序数据按时间窗口自动分片+设备 ID 哈希（TDengine 管理 10 万台设备日均 8.64 亿条数据）；Redis Cluster 用 16384 虚拟槽+CRC16 哈希。

### 8.6.3 复制规则（分片怎么冗余）

- **副本分布策略**：为保证容错，副本需**跨机架、跨可用区（AZ）分布**——如 HDFS 默认 3 副本存不同机架；ZooKeeper 多数派跨物理位置。
    
- **复制模式选型**（呼应第6章 CAP）：
    
    - **同步复制**：主写入后立即同步从节点，**强一致、数据安全**，但写性能下降（金融交易）；
        
    - **异步复制**：主写入立即返回、异步同步从节点，**高吞吐**，但可能丢数据（吞吐量优先场景）；
        
    - **半同步**：折中，至少一从确认（金融外围/订单系统）。
        
    

**我的洞见（创新视角）**：

1. **分区规则的选择，本质是"按查询模式匹配数据分布"**——点查为主选哈希，范围查询为主选范围，频繁扩缩容选一致性哈希，复合场景选混合。**选错分片键，再强的硬件也白搭**（如用时序范围分片做用户点查会全集群扫描）。
    
2. **分片键的选取是"一锤定音"的决策**——一旦选定很难更改，必须高基数、查询频繁、尽量不变更（同 4.1.2）。**分片键选错，是分区架构最昂贵的失误**。
    
3. **复制规则是"CAP 取舍在分区层的落地"**：要强一致（CP）选同步复制，要高吞吐/高可用（AP）选异步复制。**分区解决"数据放得下/写得快"，复制解决"数据不丢/服务不断"，二者共同构成分散集群的完整高可用方案**。

## 8.7 本章小结 + 全章脉络与联系

**本章核心脉络（由简到繁、由双机到集群/分区）**：

```
存储高可用架构（消除存储单点，保数据不丢、服务不断）
├─ 8.1 主备复制：主机读写、备机待命（冷备）→ 最简单，硬件浪费50%，人工切换
├─ 8.2 主从复制：主机写、从机读（读写分离）→ 读扩展+读容灾，受主从延迟困扰
├─ 8.3 主备/主从倒换：引入自动 Failover
│     MHA（GTID+binlog补全+VIP漂移）/ Orchestrator（Raft自身HA+可视化）/
│     Group Replication（Paxos+强一致+多主）
├─ 8.4 主主复制：双主双向复制 → 写高可用/写扩展，但冲突处理复杂，需业务拆分规避
├─ 8.5 数据集群
│     集中集群（不分片，副本冗余：MGR/InnoDB Cluster）
│     分散集群（分片+副本：Redis Cluster/Cassandra/TiDB/HBase）
│     分布式事务（2PC/TCC/Saga/本地消息表）
│     分布式一致性算法（Raft/Paxos/ZAB/Gossip）
└─ 8.6 数据分区
     分区规则：哈希/范围/一致性哈希/混合
     复制规则：同步(CP)/异步(AP)/半同步 + 跨机架/AZ 分布
```

**贯穿全章的第一性原理**：存储高可用的本质是 **"用冗余（副本）消除单点 + 用分片突破单机容量/吞吐上限 + 用一致性协议（Raft/Paxos/Gossip）协调多副本"**。所有双机/集群/分区方案，都是这句话在具体约束（数据量、读写比、一致性要求、运维能力）下的展开。

**与前面章节的联系**：

- 第1章"复杂度来源"中的**高可用**，在第6章获得理论化表达（CAP），在第7章获得分析方法（FMEA），在本章获得**可落地的架构模式**（主备→主从→倒换→集群→分区）。
    
- 第4章"存储高性能"（分库分表/NoSQL/缓存）与本章"存储高可用"**紧密交织**：主从复制同时是"读扩展（高性能）"和"读容灾（高可用）"手段；加机器既为"扩展"（高性能）也为"冗余"（高可用），目的不同却共用机制。
    
- 第6章 CAP 在本章"实例化"：**同步复制→CP（金融核心）**，**异步复制→AP（互联网前台）**；一致性算法 Raft→CP，Gossip→AP。
    
- 第2章"合适原则"贯穿：**能主备解决的别上主从，能主从解决的别上主主/集群**；主主能不用则不用（复杂度高）；一致性算法/复制模式按业务一致性要求匹配，而非追"最强"。
