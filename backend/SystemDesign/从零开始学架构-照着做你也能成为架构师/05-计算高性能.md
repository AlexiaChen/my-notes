# 《从零开始学架构》读书笔记 · 第5章 计算高性能

> **一句话定位第5章**：第4章解决"数据怎么存得快"，第5章解决"请求怎么处理得快"。它分两条主线——**单服务器高性能（一台机器内，用合适的并发模型把 CPU/IO 吃满）**​ 和 **集群高性能（一台不够就多台，用负载均衡把流量合理分派）**。前者是"向内挖潜"，后者是"向外扩展"，共同构成计算高性能的完整解法。

---

## 5.1 单服务器高性能——"一台机器内，选对并发模型"

单服务器高性能的关键不在"堆硬件"，而在**并发模型**——即如何把海量连接/请求映射到有限的 CPU 与线程/进程上。并发模型又由操作系统的 **I/O 模型（阻塞/非阻塞/多路复用/异步）**​ 与 **进程模型（进程/线程）**​ 共同决定。本章按"由简到复杂、由同步到异步"的顺序，给出六种经典模型。

### 5.1.1 PPC（Process Per Connection）

- **做法**：每来一个新连接，`fork` 一个子进程专门处理该连接。世界上第一个 Web 服务器 CERN httpd 即采用此模式。
    
- **优点**：实现极简；进程间隔离，单个连接异常不影响其他连接。
    
- **缺点**：① `fork` 代价高（复制内存映像、分配内核资源）；② 父子进程通信需用 IPC，复杂；③ 并发连接数受限于进程调度，通常**仅几百**。
    

### 5.1.2 prefork（预先创建进程）

- **做法**：系统启动时**预先 `fork` 好一批子进程**，accept 同一 socket，新连接到来时由内核保证仅一个进程 accept 成功，省去连接时 fork 的开销。Linux 2.6+ 已解决 accept 惊群问题。
    
- **优点**：减少连接建立时延，响应更快。
    
- **缺点**：仍继承 PPC 的"进程间通信复杂、并发数有限"问题。
    
- **工业案例**：Apache MPM **prefork**​ 模式，默认最大支持 **256**​ 并发连接，适合需兼容非线程安全库或追求进程隔离稳定性的场景。
    

### 5.1.3 TPC（Thread Per Connection）

- **做法**：每来一个新连接，**新建一个线程**处理。
    
- **优点**：线程比进程轻量，创建代价低；线程共享进程内存，**通信比 IPC 简单**。
    
- **缺点**：① 高并发（每秒上万连接）时创建线程仍有性能瓶颈；② 线程互斥/共享引入复杂度，易死锁；③ 某线程内存越界可能导致**整个进程退出**。
    

### 5.1.4 prethread（预先创建线程）

- **做法**：启动时预先创建线程池，连接到来时从池中取线程处理，避免连接时创建线程的开销。
    
- **优点**：并发量比 TPC 更高。
    
- **缺点**：继承 TPC 的线程安全风险。
    
- **工业案例**：Apache MPM **worker**​ 模式（多进程 + prethread 变种），默认 16 进程 × 25 线程 = **400**​ 并发处理线程。
    

> **PPC vs TPC 的取舍（书的洞见）**：并发几百的场景，**反而更多用 PPC**——因为 PPC 无死锁风险、进程互不干扰，**稳定性更高**。这也印证了第2章"合适/简单原则"：并发不高时，稳定性和实现简单优先于"更轻量"。

### 5.1.5 Reactor（反应器）——**目前 Linux 高性能服务器的绝对主流**

- **核心思想**：**同步 I/O 多路复用 + 事件分发**。主线程（Reactor）用 `epoll`/`select`/`poll` 监听 fd 事件，事件就绪后分发给对应 Handler，**由 Handler 主动调用 `read`/`write` 完成实际 I/O 与业务处理**。
    
- **通俗比喻**：快递到小区，快递员打电话**通知你"来取"**，你需要自己下楼取（应用主动 read）——这是"事件就绪时通知你，你去读"。
    
- **三种演进形态**：
    
    - **单 Reactor 单进程/线程**：acceptor 接收 + handler 处理，逻辑清晰但 handler 耗时会长阻塞事件循环。
        
    - **单 Reactor 多线程**：Reactor 负责 IO 事件分发，耗时业务交给独立工作线程池，IO 与业务解耦。
        
    - **主从 Reactor 多进程/线程**：主 Reactor 仅 accept 新连接，分发给从 Reactor；从 Reactor 负责已建连接的读写事件。**Nginx、Netty 的主从 Reactor 模型**即典型应用。
        
    
- **优点**：编程模型相对简单，充分利用非阻塞 I/O，避免每连接一线程。
    
- **缺点**：实际 I/O 仍是同步的，单个 Handler 读写耗时过长会阻塞事件循环。
    

### 5.1.6 Proactor（前摄器）——"内核帮你把数据读好"

- **核心思想**：**真正的异步 I/O**。应用发起 `aio_read` 并传入缓冲区地址后立即返回；**内核全程负责把数据读入用户缓冲区**，完成后通知应用"数据已就绪，请处理"。
    
- **通俗比喻**：快递员**直接把快递送到你门口**，再通知你"门口拿了即可"。
    
- **代表实现**：Windows **IOCP**（经典 Proactor）；Linux `aio`/较新的 `io_uring` 提供异步支持。
    
- **优点**：I/O 全交给内核，减少用户态/内核态上下文切换，高负载下更省 CPU，支持耗时长的并发任务。
    
- **缺点**：编程模型复杂、内存管理麻烦（缓冲区在异步期间须保持有效）；**Linux 原生异步 I/O 支持长期不完善**，故 Linux 服务器主流仍是 epoll + Reactor。
    

**我的洞见（第一性原理 + 创新视角）**：

1. **六种模型的演进，本质是"减少连接建立开销"与"减少线程/进程数量"两条主线交织的结果**：PPC→prefork、TPC→prethread 是"预创建"解决 fork/创建开销；PPC/TPC→Reactor/Proactor 是"用事件驱动替代每连接一执行单元"解决 C10K/C10M 问题。理解这条主线，就理解了为何现代高并发服务器（Nginx/Redis/Netty）几乎全数站在 Reactor 肩上。
    
2. **Reactor vs Proactor 的根本区别，一句话**：Reactor 感知"**待完成**的 I/O 事件"（就绪通知），Proactor 感知"**已完成**的 I/O 事件"（完成通知）。前者是"你来读"，后者是"我读好给你"。
    
3. **选型建议（贴合工业）**：Linux 环境下，**epoll + Reactor 是事实标准**，成熟、稳定、生态完善；Windows 环境或内核级异步需求可考虑 IOCP/Proactor。不要为了"看起来更先进"强行上 Proactor——**第2章的"合适原则"在此再次生效**：主流成熟方案往往是最合适的方案。

## 5.2 集群高性能——"一台不够就多台，用负载均衡分派"

当单机性能到顶（CPU/内存/IO 瓶颈），解法不是继续堆单机，而是**增加服务器构成集群**，把请求合理分配到多台机器。这就是**负载均衡（Load Balancing）**——本质是"任务分配器"，目标是让计算资源被充分利用、避免单点故障、实现水平扩展。

### 5.2.1 负载均衡分类——"按作用层级分三类，且可组合"

|分类|作用层级|典型实现|优点|缺点|适用|
|---|---|---|---|---|---|
|**DNS 负载均衡**​|地域级|DNS 轮询 / GeoDNS|简单、成本低、就近访问提速|缓存导致更新不及时、分配策略简单、无法感知后端状态|全球/跨区域分布、CDN 加速|
|**硬件负载均衡**​|集群级|F5 BIG-IP、A10、Citrix NetScaler|功能强、性能强（百万级并发）、稳定、带防火墙/防 DDoS|价格昂贵（数十万～数百万）、扩展性差|金融/电信/大型企业|
|**软件负载均衡**​|机器级|Nginx、HAProxy（L7）；LVS（L4）|简单、便宜（普通 Linux 服务器即可）、灵活可定制|单 Nginx 约 5 万并发，功能/安全不如硬件|互联网应用、微服务集群内部|

**组合使用原则（工业标准架构）**：**DNS 负责地域级 → 硬件负责集群级 → 软件负责机器级**。例如：用户就近接入（DNS）→ 进入某 IDC 集群（F5/A10）→ 集群内分发到具体服务节点（Nginx/LVS）。云时代还衍生出**云负载均衡**（AWS ALB、阿里云 SLB、Azure LB），按需付费、集成自动伸缩与健康检查，进一步降低运维复杂度。

### 5.2.2 负载均衡架构——"按 OSI 层级分 L4 / L7"

- **四层负载均衡（传输层，L4）**：基于 **IP + 端口**（TCP/UDP）转发，性能高、开销小，适合数据库、游戏、长连接等场景。代表：LVS、F5、云 LB。
    
- **七层负载均衡（应用层，L7）**：基于 **URL、Cookie、Header、HTTP 方法**等应用层信息路由，可感知业务语义（如按 URL 分流到不同服务），灵活但性能略低于 L4。代表：Nginx、HAProxy、AWS ALB。
    

**我的洞见**：L4/L7 不是"谁更好"，而是**按需求分层选用**——对延迟敏感、协议单一的用 L4；需要按业务语义智能路由（灰度发布、按租户分流、WAF）用 L7。现代架构常 **L4 做入口 + L7 做业务路由**​ 双层叠加。

### 5.2.3 负载均衡算法——"按什么规则把请求分给谁"

按算法目的可分为四类：

|算法|原理|优点|缺点|适用场景|
|---|---|---|---|---|
|**轮询（Round Robin）**​|按顺序依次分配|简单、公平|不感知服务器负载/性能差异|服务器配置相近|
|**加权轮询（Weighted RR）**​|按权重比例分配|解决异构集群（高性能机多分）|权重需手动设定|服务器性能不同|
|**最少连接（Least Connections）**​|分配给当前连接数最少的节点|动态均衡，避免"分配到忙节点"|需维护连接状态表，不感知连接时长|长连接业务|
|**源地址哈希（Source IP Hash）**​|按源 IP/Cookie/SessionID 哈希|同一用户固定到同一节点，**会话保持**​|节点增减/权重变化会打破映射，负载可能不均|需 Session 亲和场景|
|**最小响应时间（Least Response Time）**​|优先分配给响应最快的节点|用户体验好，自适应负载|实现复杂，需实时监控|对延迟敏感|

**我的洞见（第一性原理）**：

1. **算法没有"最优"，只有"最合适"**——选算法的本质是**回答"你希望按什么维度均衡"**：均匀分（轮询）、按能力分（加权）、按当前压力分（最少连接/响应时间）、按用户粘性分（哈希）。这再次呼应第2章"合适原则"。
    
2. **工业实战口诀**：短连接 + 同构节点 → 轮询；异构节点 → 加权轮询；长连接 → 最少连接；需 Session 保持 → 源 IP 哈希（或更好：把 Session 外移到 Redis，彻底解耦会话与节点亲和）。
    
3. **负载均衡本身也要高可用**：硬件 LB 常做主备/双活，软件 LB（如 Nginx/HAProxy）可用 Keepalived + VRRP 做 VIP 漂移，避免 LB 自身成为单点。

## 5.3 本章小结 + 全章脉络与联系

**本章核心脉络（向内挖潜 → 向外扩展）**：

```
计算高性能的两大路径
┌──────────────────────────────────────────────────────┐
│ 路径一：单服务器高性能（向内挖潜）                   │
│   PPC / prefork ──► 每连接一进程（稳定，并发低）    │
│   TPC / prethread ──► 每连接一线程（轻量，并发中等）│
│   Reactor  ──► epoll + 事件分发（Linux 主流，C10K） │
│   Proactor ──► 异步 I/O（Windows IOCP/Linux io_uring）│
├──────────────────────────────────────────────────────┤
│ 路径二：集群高性能（向外扩展）                       │
│   负载均衡分类：DNS(地域) + 硬件(集群) + 软件(机器) │
│   负载均衡架构：L4(IP+端口) / L7(URL/Cookie)         │
│   负载均衡算法：轮询/加权/最少连接/哈希/响应时间     │
└──────────────────────────────────────────────────────┘
```

**贯穿全章的第一性原理**：计算高性能的本质是 **"让有限的 CPU/IO 资源，以最合适的并发模型被充分利用（单机），再把超出单机能力的负载，按合理规则分派到多机（集群）"**。所有模型与算法，都是这句话在具体约束下的展开。

**与前面章节的联系**：

- 第1章"高性能"作为核心复杂度来源之一，在本章落地为**可执行的并发模型 + 集群方案**；
    
- 第2章"合适原则"贯穿始终——**并发不高用 PPC（稳定简单），高并发用 Reactor（主流成熟），Linux 不必强上 Proactor；选 LB 算法看业务维度而非追"最智能"**；
    
- 第3章"识别复杂度→设计备选方案→评估选择"的流程，在本章体现为：**先判断瓶颈在"单机并发"还是"总量不足"，再针对性选模型/上集群**。
