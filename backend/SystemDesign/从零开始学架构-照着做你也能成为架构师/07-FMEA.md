# 《从零开始学架构》读书笔记 · 第7章 FMEA

> **一句话定位第7章**：第6章从理论层面建立了"高可用 vs 一致性"的取舍框架（CAP），第7章给出**把"高可用"真正落地为高可用架构的具体分析方法**——FMEA（故障模式与影响分析）。它不是一个设计工具，而是一个**"架构设计完成后，系统性排查可用性隐患"的复盘/评审工具**。本章是全书从"认知高可用"走向"构造高可用架构（第8章起）"的**桥梁与方法论支点**。

---

## 7.1 FMEA 介绍——"先搞清楚：FMEA 是干什么的、不是干什么的"

**FMEA 是什么**：FMEA（Failure Mode and Effects Analysis，故障模式与影响分析）是一种在各行各业广泛应用的**可用性分析方法**，通过对系统范围内**潜在的故障模式**加以分析，并按严重程度分类，以确定失效对系统的最终影响。

**出身与跨界能力**：FMEA 最早源于美国军方（20 世纪 40 年代后期美国空军正式采用），后广泛应用于汽车（福特等）、航空航天（NASA 阿波罗计划）、半导体、医疗、软件等行业。它能在差异巨大的领域通用，**根本原因在于 FMEA 是一套"分析和思考的方法"，而不是某个领域的专属技能或工具**——这也是它能无缝迁移到软件架构领域的底层逻辑。

**⚠️ 最关键的定位澄清（本书核心观点）**：

> **FMEA 并不能指导我们"如何做架构设计"，而是当我们"设计出一个架构后"，再用 FMEA 对这个架构进行分析，看看架构是否还存在某些可用性的隐患。**

**我的洞见（第一性原理）**：这一定位极其重要，却最易被误解。很多人把 FMEA 当成"设计工具"，其实它是**"事后评审/风险扫描工具"**——它不告诉你架构该怎么画，而是对着你已经画好的架构图，**逐个部件假设它故障，倒逼你发现"原来这里没做冗余/没做降级/没做监控"**。理解这一定位，才不会用错工具、也不会指望 FMEA 替你做设计。

## 7.2 FMEA 方法——"四步流程 + 一张分析表"

### 四步分析法（本书给出的架构领域具体做法）

1. **给出初始的架构设计图**（作为分析对象）；
    
2. **假设架构中某个部件发生故障**；
    
3. **分析此故障对系统功能造成的影响**；
    
4. **根据分析结果，判断架构是否需要进行优化**。
    

### FMEA 分析表（核心产出）

FMEA 的载体就是一张表。常见表格包含以下字段（本书/业界通用版本）：

|字段|含义与填写要点|
|---|---|
|**① 功能点**​|从**用户角度**看的功能（如"登录""下单"），**不是**系统内部模块划分|
|**② 故障模式**​|部件"怎样故障"（如"MySQL 读取超时 5s"），**尽量精确、量化描述**，避免泛化|
|**③ 故障影响**​|对用户/功能的具体影响（如"60% 用户响应超过 5s""登录不可用"）|
|**④ 严重程度**​|业务视角分级：**致命/高/中/低/无**（5 级）|
|**⑤ 故障原因**​|故障的具体根因（如"慢查询""磁盘满""低版本 Bug"）|
|**⑥ 故障概率**​|发生可能性：**高/中/低**（硬件故障概率低、开源系统中等、自研系统偏高）|
|**⑦ 风险程度**​|综合严重程度 × 故障概率，通常分 **高/中/低**​|
|**⑧ 已有措施**​|当前已有的应对（自动告警、容错/自动切换副本、自动恢复）|
|**⑨ 规避措施**​|技术手段+管理手段（数据备份、网络双入口、定时自动重启）|
|**⑩ 解决措施**​|针对性技术手段（如引入读写分离、加缓存、限流降级）|
|**⑪ 后续规划**​|还缺哪些应对，按优先级排序形成后续计划|

### 量化评分体系（工业标准：RPN）

业界（AIAG FMEA 手册）对关键维度采用 **1～10 分**评分，并计算**风险优先数 RPN**：

RPN=严重度(S)×频度(O)×探测度(D)

|维度|含义|评分倾向|
|---|---|---|
|**严重度 S**​|失效对用户的危害程度|1=无影响；9-10=核心业务完全不可用/安全事故|
|**频度 O**​|失效原因发生的概率|1=几乎不可能；10=几乎必然|
|**探测度 D**​|现有手段下故障被发现/定位的速度|1=极易探测（防错）；10=根本无法检测|

- RPN 范围 1～1000，**RPN 越大，改善的必要性越高**。
    
- **重要原则**：S≥9（安全/法规/核心功能丧失）的项，**无论 O、D 分值如何，均列为最高优先改善项**。
    

**我的洞见（创新视角）**：本书给出的 5 级（致命/高/中/低/无）是"简化版 FMEA"，适合架构评审快速使用；工业标准的 S/O/D 十分制 + RPN 是"完整版"，适合需要量化排期的严谨场景。**二者不是替代关系，而是"场景匹配"关系**——架构方案评审用 5 级简化版（高效、易共识）；重大系统/安全敏感系统用十分制 + RPN（可量化排期、可追溯）。这也是"合适原则"在 FMEA 用法上的体现。

## 7.3 FMEA 实战——"对着架构图，逐部件做'故障推演'"

### 实战要点（如何把 FMEA 真正用起来）

1. **以"功能"而非"模块"为分析单元**：功能点要从用户视角定义（"用户能登录""订单能支付"），这样故障影响才能映射到真实业务损失。
    
2. **一个功能点可对应多种故障模式**：例如"登录"功能，可能对应"MySQL 超时""Redis 缓存击穿""Nginx 转发失败"等多种故障模式，需逐条列出分别分析。
    
3. **故障模式要"精确+量化"**：写"MySQL 读取耗时特别大"不如写"MySQL 读取超时 5 秒"；进一步追问"是磁盘 IO、内存、还是慢查询导致"，才能落到可执行的解决措施。
    
4. **系统化思维，考虑级联故障**：分析时不能只看单点，要从整体出发，考虑部件间的依赖与**雪崩/级联效应**（如一个缓存集群宕机 → 大量请求打到 DB → DB 被打垮）。
    
5. **FMEA 是"活文档"，需定期评审更新**：应随架构演进、故障复盘、新技术引入而**定期评审更新**，保持其有效性。
    

### 实战案例示意（用户管理系统——登录功能）

|功能点|故障模式|故障影响|严重程度|故障原因|故障概率|风险程度|已有措施|解决措施|
|---|---|---|---|---|---|---|---|---|
|登录|MySQL 读取超时 5s|60% 用户响应>5s，登录变慢|高|慢查询/索引缺失|高|高|慢查询监控|加索引、读写分离、登录态缓存|

### 工业实践印证

- **互联网大厂**：在架构评审（Design Review）中把 FMEA 作为**高可用方案的前置关卡**——新系统上线前必须产出 FMEA 表，RPN 高的项必须有对应解决措施才能上线。
    
- **SRE/云原生场景**：FMEA 与 **SLO/SLI 设计、监控告警、混沌工程（Chaos Engineering）**​ 联动——FMEA 识别高风险项 → 为其建设监控与 SLO → 用混沌工程主动注入故障验证韧性。
    
- **参与人员**：理想情况下由系统 Owner、项目 Leader、架构师（领域专家）、相关开发与测试共同参与；时间受限时可用"简化版流程 + 表格"由核心成员完成。
    

**我的洞见（第一性原理 + 创新视角）**：

1. **FMEA 的本质是"预演故障"，把"事后救火"前移到"事前排雷"**。它强迫架构师主动问："如果这个部件挂了，会怎样？"——这种**反向思维（从故障反推架构缺陷）**​ 是提升可用性的核心心法。与其说 FMEA 是表格，不如说它是一种**"假设故障"的工程师思维习惯**。
    
2. **FMEA 与第6章 CAP 的关系**：CAP 告诉你"分布式下一致性与可用性存在理论张力"，FMEA 则把这种张力**落到具体部件的故障场景**——例如"假设 MySQL 主库宕机（分区），当前架构是 CP 还是 AP？用户能否登录？"**CAP 是理论框架，FMEA 是把它"实例化、场景化"的分析工具**。二者结合，才构成"高可用架构"从理论到排查的完整闭环。
    
3. **FMEA 的局限要正视**：它是"已知未知"的分析，对"未知未知"（完全未预想到的 emergent 故障）无能为力。因此需配合**混沌工程（主动注入未知故障）**​ 与**完善的故障复盘机制**，让 FMEA 表随真实故障不断迭代补全——**FMEA 不是一次性的文档，而是随系统演进持续更新的"活的风险台账"**。

## 7.4 本章小结 + 全章脉络与联系

**本章核心脉络（定位 → 方法 → 实战）**：

```
FMEA（故障模式与影响分析）
├─ 7.1 介绍：一套"分析思考方法"而非设计工具
│   定位：架构设计完成后，用于排查可用性隐患（非指导设计）
│
├─ 7.2 方法：四步法 + 分析表
│   四步：出架构图 → 假设某部件故障 → 分析影响 → 判断是否需要优化
│   表格：功能点/故障模式/影响/严重程度/原因/概率/风险程度/措施…
│   量化：RPN = S(严重度) × O(频度) × D(探测度)
│
└─ 7.3 实战：以"用户视角功能"为单元，逐部件做故障推演
    要点：功能>模块、精确量化、考虑级联故障、FMEA 是活文档需持续更新
    联动：与 SLO/监控/混沌工程/SRE 实践结合，形成闭环
```

**贯穿全章的第一性原理**：FMEA 的本质是 **"用'假设故障'的反向思维，把高可用从一句口号变成一张可评审、可排期、可追溯的风险台账"**。它不创造架构，但能让已有架构的可用性隐患**显性化、可量化、可治理**。

**与前面章节的联系**：

- 第1章"复杂度来源"中的**高可用**，在第6章获得理论化表达（CAP），在本章获得**可操作的分析方法**（FMEA）——三者形成"目标(高可用) → 理论(CAP) → 方法(FMEA)"的完整链条。
    
- 第2章"合适原则"再次生效：**FMEA 用 5 级简化版还是十分制+RPN，取决于系统重要度与团队资源**，不必对所有系统都套完整量化流程。
    
- 第3章"识别复杂度→评估备选方案"的流程，与 FMEA 天然契合：**FMEA 就是对"高可用"这一复杂度做专项识别与评估的工具**。
    
- 第4～5章的存储/计算高性能方案（主从、集群、负载均衡），正是 FMEA 表中"解决措施/已有措施"最常指向的**高可用落地手段**——FMEA 识别隐患，第8章起的高可用架构模式（主备/主从/多副本）提供解法。
