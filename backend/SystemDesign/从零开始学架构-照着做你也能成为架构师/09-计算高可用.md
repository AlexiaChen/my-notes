# 《从零开始学架构》读书笔记 · 第9章 计算高可用

> **一句话定位第9章**：第8章解决"存储怎么高可用"（数据不丢、不断），第9章转向**"计算/服务怎么高可用"（请求处理不中断）**。二者是"高可用体系"的两大支柱——存储高可用保"数据"，计算高可用保"服务"。本章给出计算层从"双机"到"集群"的四种经典架构模式，并与第8章形成"存储—计算"高可用的完整拼图。

---

## 9.1 主备——"计算层最简高可用，备机冷待命"

### 基本实现

- **结构**：一主一备。**主机承担所有业务请求**，备机平时**不处理业务、处于待命**，仅通过心跳/健康检查被监控；主机宕机后**人工**将流量切到备机。
    
- 与第8.1 存储主备同源：都是"主机干活、备机冷备"，区别在**这里是应用/服务进程**，而非数据库。
    

### 优缺点分析

- **优点**：① 架构**最简单**，客户端无需感知备机；② 无状态服务的备机可随时接管，切换成本低。
    
- **缺点**：① 备机长期闲置，**硬件利用率仅约 50%，资源浪费**；② 故障后**需人工干预**，恢复慢。
    
- **适用**：内部管理系统、对成本不敏感、业务量小且可接受短时人工切换的场景。
    

**我的洞见（第一性原理）**：计算主备的本质是**"用 100% 硬件冗余，换取主机故障时的可恢复性"**——与存储主备（8.1）逻辑完全一致，只是冗余对象从"数据库"变成"应用服务"。它的价值在"简单可靠"，局限在"资源浪费+人工切换慢"。**当业务量增长、不能接受人工切换时，就该考虑主从或集群方案**。

---

## 9.2 主从——"备机也干活，兼顾负载与容灾"

### 基本实现

- **结构**：主机负责**部分业务**（如写入型/核心请求），从机负责**另一部分业务**（如只读/非核心请求），两者**同时对外提供服务**，通过健康检查互相感知。
    
- 与第8.2 存储主从的区别：存储主从是"主机写、从机读（读写分离）"；**计算主从是"按业务维度拆分到主从机分别承载"**，更强调"两台都干活、各管一块"。
    

### 优缺点分析

- **优点**：① 两台**都承担业务，硬件利用率高**（无闲置）；② 一台故障，**另一台可接管其业务**（配合负载均衡/网关路由），可用性优于主备。
    
- **缺点**：① 客户端/网关需**感知主从关系并按规则路由**，架构复杂度高于主备；② 业务拆分需合理，**拆分不当会导致某台过载**。
    
- **适用**：业务可清晰拆分为两类（如"写服务"与"读服务"、"核心交易"与"查询报表"），且希望**资源充分利用**的场景。
    

**我的洞见（创新视角）**：计算主从的精髓是**"让备机也产生价值"**——把"冷备"变成"分担负载的从机"，一举两得：**资源利用率↑ + 故障时有同伴可接管**。它与存储主从（读写分离）的思路同源却不同形：**存储主从按"读写操作"拆分，计算主从按"业务模块"拆分**。理解这一差异，就不会把两种"主从"混为一谈。

## 9.3 对称集群——"多节点对等，无中心、可水平扩展"

### 基本实现

- **结构**：**所有节点角色对称、对等**，无主从无中心，每个节点都能处理**相同类型**的业务请求；前端通过**负载均衡（Nginx/LVS/SLB）**​ 将请求分发到任意节点。
    
- 典型形态：**无状态服务集群**（Spring Boot 微服务多实例、Node.js 集群、Go 微服务），节点无状态，session/上下文外移到 Redis。
    

### 优缺点分析

- **优点**：① **天然高可用**——任意节点故障，负载均衡自动剔除，流量切到其他节点，**对业务透明**；② **水平扩展能力强**——加节点即可扩容，突破单机瓶颈；③ 无中心、无主从切换逻辑，**架构简洁**。
    
- **缺点**：① 要求服务**无状态**（或有外部分布式状态存储），**有状态服务改造成本高**；② 负载均衡本身需**高可用**（Keepalived/VRRP 或云 LB 多 AZ），否则 LB 成新单点。
    
- **适用**：**无状态 Web/API 服务**（互联网前台、微服务接口），这是**互联网最主流的计算高可用形态**。
    

**工业实践印证**：Netflix/美团/阿里的微服务架构，核心思路就是"**无状态服务 + 对称集群 + 负载均衡 + 自动扩缩容**"，配合 Kubernetes 的 Deployment/Service 实现节点故障时自动重启与流量摘除。

**我的洞见（第一性原理）**：

1. **对称集群的本质是"用负载均衡 + 无状态 + 多副本，把单点变成多点冗余"**——它把"主备/主从"的"主从切换"逻辑**彻底取消**，改为"任意节点对等、故障即剔除"。这是计算高可用**最成熟、最主流**的方案。
    
2. **"无状态"是对称集群的先决条件**（创新视角）：正因为服务无状态（session 外移 Redis、文件外移对象存储），任意节点都能处理任意请求，**节点才真正"对称"**。因此，把有状态服务改造成无状态，是迈向对称集群的关键一步——这也是第4章"缓存(Redis)"在第9章"计算高可用"中的隐性支撑作用。

## 9.4 非对称集群——"多节点角色不同，各司其职+自动故障转移"

### 基本实现

- **结构**：集群内节点**角色不对称**——分为**主节点（Master）**​ 与**工作节点（Worker/Slave）**；Master 负责**协调/调度/状态管理**，Worker 负责**实际业务处理**；Master 通过**选举算法（Raft/Paxos/ZAB）**​ 保证自身高可用。
    
- 典型形态：**有状态/需协调的分布式系统**——ZooKeeper（Leader/Follower）、etcd（Leader/Follower）、Kafka（Controller Broker）、Elasticsearch（Master/Data 节点）、Hadoop YARN（RM/NM）。
    

### 优缺点分析

- **优点**：① 适合**有状态、需强一致协调**的场景（分布式锁、选主、配置管理）；② Master 通过**选举自动故障转移**，无需人工干预；③ 角色分离，**职责清晰、可控性强**。
    
- **缺点**：① 架构**最复杂**，需引入一致性协议与选举机制；② Master 选举/切换期间**可能有短暂不可用窗口**；③ 运维成本高（需监控选举健康、脑裂风险）。
    
- **适用**：**分布式协调/有状态中间件**（注册中心、配置中心、消息队列、分布式存储的协调节点）。
    

**工业实践印证**：

- **ZooKeeper/etcd**：Leader 处理所有写请求并保证 ZAB/Raft 强一致，Follower 分担读；Leader 故障后自动选举新 Leader（秒级），是 K8s/微服务注册发现的基石。
    
- **Elasticsearch**：Master 节点负责集群元数据/分片分配，Data 节点负责数据存储与查询；Master 通过 Zen Discovery/选举保证高可用。
    

**我的洞见（创新视角 + 第一性原理）**：

1. **非对称集群是"为有状态/需协调的系统量身定制的高可用方案"**——当系统**必须有中心协调者**（如分布式锁、选主、元数据管理）时，无法用"对称集群"（无中心）解决，只能引入 Master+选举，形成非对称结构。
    
2. **对称 vs 非对称的根本分水岭，是"系统是否有状态/是否需要中心协调"**：无状态/无需协调 → 对称集群（简单、主流）；有状态/需协调 → 非对称集群（复杂、但必要）。**这再次印证第2章"合适原则"——没有"非对称一定优于对称"，只有"与系统状态特性匹配"**。
    
3. **非对称集群的"选举协议"与第8.5.4 存储一致性算法（Raft/Paxos/ZAB）完全同源**——计算层的 Master 选举与存储层的副本共识，用的是同一套分布式一致性理论。这正是全书"存储—计算"高可用体系在理论层面的统一点。

## 9.5 本章小结 + 全章脉络与联系

**本章核心脉络（由简到繁、由双机到集群）**：

```
计算高可用架构（服务/请求处理不中断）
├─ 9.1 主备：主机干活、备机冷待命 → 最简单，资源浪费50%，人工切换
├─ 9.2 主从：主机与从机按"业务维度"各管一块、都干活 → 资源利用率高，需按业务拆分路由
├─ 9.3 对称集群：多节点对等、无中心、无状态 + 负载均衡 → 最主流，天然高可用、可水平扩展
└─ 9.4 非对称集群：Master(协调)+Worker(处理)，Raft/Paxos/ZAB 选举 → 适合有状态/需协调的分布式系统
```

**四种模式对比一览**：

|模式|节点关系|是否需状态外移|自动切换|复杂度|适用场景|
|---|---|---|---|---|---|
|主备|主干活/备冷待命|否|人工|★☆☆☆☆|内部系统、量小、可接受人工切换|
|主从|主从按业务各管一块|否|半自动|★★☆☆☆|业务可拆两类、需资源充分利用|
|对称集群|节点对等、无中心|**是（无状态化）**​|自动（LB剔除）|★★☆☆☆|无状态 Web/API/微服务（主流）|
|非对称集群|Master+Worker 角色不对称|是（协调状态）|自动（选举）|★★★★☆|有状态/需协调的中间件（ZK/etcd/ES/Kafka）|

**贯穿全章的第一性原理**：计算高可用的本质是 **"用冗余（多副本/多节点）+ 负载均衡/选举协议，消除计算单点；并按系统'有无状态/是否需协调'匹配对应的集群形态"**。所有四种模式，都是这句话在具体业务约束下的展开。

**与前面章节的联系**：

- 第1章"复杂度来源"中的**高可用**，在第6章（CAP）、第7章（FMEA）、第8章（存储高可用）层层落地后，在本章完成**"计算/服务高可用"的最后一块拼图**——至此，"存储高可用 + 计算高可用"构成完整的高可用体系。
    
- 第5章"集群高性能"中的**负载均衡**（5.2），在本章成为对称集群的**核心组件**（Nginx/LVS 分发请求、自动剔除故障节点）——**负载均衡同时是高性能手段（5章）和高可用手段（9章对称集群）**，目的不同却共用机制。
    
- 第8章"存储高可用"与本章"计算高可用"**高度对称**：存储层有主备/主从/集群/分区，计算层也有主备/主从/对称集群/非对称集群，**两套体系用相同的"冗余+协调"思想，分别解决"数据不丢"和"服务不断"**。
    
- 第8.5.4 的**一致性算法（Raft/Paxos/ZAB）**​ 在本章"非对称集群"中再次出场——计算层 Master 选举与存储层副本共识**共用同一套分布式一致性理论**，是全章乃至全书"存储—计算"高可用体系的理论统一点。
    
- 第2章"合适原则"贯穿：**能主备解决的别上主从，能对称集群解决的别上非对称集群**；非对称集群复杂度最高，只在"系统必须有中心协调"时才选用。
