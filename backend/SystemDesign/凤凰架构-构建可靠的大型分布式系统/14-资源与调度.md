
# 《凤凰架构》第14章 · 资源与调度 —— 读书笔记

> **一句话立住**：前13章把"拆、通、一致、扛流量、保安全、达共识、做路由、治流量、建信任、可观测、容器化、容器网络、持久化存储"全部解决后，本章直面一个最朴素也最致命的问题——**节点上的 CPU、内存、磁盘都是有限的，但 Pod 是动态的、贪婪的、会超发的**。周志明的核心命题是：**Kubernetes 资源调度的本质，是用"声明式资源边界"把"无限的 Pod 欲望"与"有限的节点容量"对齐——Request 决定"Pod 去哪儿"，Limit 决定"Pod 能用多少"，QoS 决定"Pressure 时谁先死"，调度器决定"集群资源如何被最优分配"**。这也是本章最值得刻进脑子的一句话：**资源调度不是"把 Pod 放到节点上"这么简单，而是"在四个维度上同时做权衡"——放置正确性（Predicate）、放置最优性（Priority）、运行时安全性（Limit/QoS）、节点稳定性（Eviction）**。

## 一、先把全章骨架搭起来（四层机制、一条主线）

本章按"资源模型 → 服务质量 → 驱逐机制 → 默认调度器"四层递进：

|层级|回答的问题|关键机制|
|---|---|---|
|**资源模型（14.1）**​|Pod 到底需要多少资源？|Request（调度依据+预留）/ Limit（运行时上限）|
|**服务质量与优先级（14.2）**​|Pressure 时谁先死？|QoS（Guaranteed/Burstable/BestEffort）+ PriorityClass|
|**驱逐机制（14.3）**​|节点快死了怎么自救？|kubelet 主动驱逐（Eviction）vs 内核 OOMKill|
|**默认调度器（14.4）**​|Pod 该去哪个节点？|Predicate（过滤）+ Priority（打分）两阶段|

**一条贯穿始终的主线（我的第一性原理提炼）**：**资源调度的全部复杂度，源于一个根本矛盾——"Pod 的资源欲望是无限的、动态的"与"节点的资源容量是有限的、静态的"的冲突**。Kubernetes 用四层机制层层设防：

1. **资源模型**：让 Pod "声明"自己需要多少（Request）和最多能用到多少（Limit）
    
2. **QoS/优先级**：让系统知道"谁的命更值钱"
    
3. **驱逐机制**：节点快死时"弃车保帅"
    
4. **调度器**：新 Pod 到来时"放到最合适的地方"
    

**这四层机制不是孤立的，而是"声明→决策→执行→自救"的完整闭环**——理解这一点，你就能看懂 K8s 资源调度的全部设计哲学。

## 二、逐节脉络 + 我的理解与洞见

### 14.1 资源模型 —— "Request 与 Limit" 的双生契约

#### 核心原理：Request 与 Limit 的根本差异

- **Request（请求）**：调度器视角——决定 Pod 能被调度到哪个节点（节点可分配资源 - 已分配 Request 之和 ≥ Pod Request）；kubelet 视角——为容器预留 Request 量的资源
    
- **Limit（限制）**：kubelet 和容器运行时视角——容器运行时资源使用的硬上限，最终由 Linux 内核 cgroups 强制执行
    

#### 内核执行机制（最硬核的部分）

Kubernetes 的资源声明，最终都翻译成 Linux 内核的 cgroups 控制：

- **CPU Request**​ → cgroups 的 `cpu.weight`（CFS 完全公平调度器的相对权重）
    
    - 1 CPU = 1024 shares，K8s 中 1000m = 1024 shares
        
    - 含义：节点 CPU 竞争时，按 Request 比例分配 CPU 时间
        
    
- **CPU Limit**​ → cgroups 的 `cpu.max`（CFS 配额）
    
    - 含义：每 100ms 周期内最多使用 Limit 指定的 CPU 时间
        
    - **超限行为：CPU 节流（Throttling）**——容器不被杀，但被限流
        
    
- **Memory Request**​ → 调度器提示 + kubelet 预留（**不影响运行时强制执行**）
    
- **Memory Limit**​ → cgroups 的 `memory.max`
    
    - **超限行为：OOM Kill**——内核直接杀容器进程
        
    

> **💡 第一性原理洞见**：CPU 是"可压缩资源"，内存是"不可压缩资源"——这个本质差异决定了 K8s 对二者的执行策略截然不同：
> 
> - **CPU 超限**​ → 节流（Throttling），容器继续运行但变慢——因为 CPU 可以"挤一挤"
>     
> - **内存超限**​ → 杀进程（OOM Kill），因为内存"挤不了"，要么给、要么杀
>     
> 
> 这就是为什么"CPU Limit 设太低会导致延迟毛刺，而 Memory Limit 设太低会导致容器反复重启"——**两者的故障模式根本不同**。工业界的一个热门辩论正是："要不要给 CPU 设 Limit？"反对者的核心论点是：CPU 是可压缩的，Request 已经保证了公平调度，Limit 只会在节点有空闲 CPU 时仍节流容器，造成无谓的延迟。

#### 为什么需要 Request？

Request 是 K8s 调度器的"决策依据"。调度器确保：**节点上所有 Pod 的 Request 之和 ≤ 节点可分配资源**。这带来两个关键特性：

1. **可超卖（Overcommit）**：Limit 之和可以超过节点容量——因为假设"不是所有 Pod 同时打满 Limit"
    
2. **低 Request 的危险**：如果 Pod 实际需要 512Mi 但只 Request 64Mi，调度器可能把 8 个这样的 Pod 装到同一节点，然后 8 个同时 spike 时节点 OOM
    

> **💡 工业惨案**：生产环境中最常见的一类故障——"不设置 CPU Request 或将 Request 设得过低，导致节点 CPU 满载、业务延迟暴增，机器软死锁"；以及"Java 应用的 JVM Xmx 大于 Pod Memory Request，导致 JVM 启动时就被 OOM Kill，Pod 不断重启"。**这揭示了一个朴素真理：Request 不是"Hint"，而是"契约"——你对 K8s 撒谎，K8s 就用 OOM 教训你**。

### 14.2 服务质量与优先级 —— "Pressure 时谁先死"的数学

#### QoS 三类的判据与含义

K8s 基于每个容器的 Request 和 Limit 关系，自动为 Pod 分配 QoS 类：

|QoS 类|判据|驱逐顺序|适用场景|
|---|---|---|---|
|**Guaranteed**​|所有容器 CPU/Memory 的 Request == Limit，且都 > 0|最后被驱逐|核心业务、数据库、延迟敏感|
|**Burstable**​|至少一个容器设了 Request 或 Limit，但不满足 Guaranteed|中间被驱逐|绝大多数普通应用|
|**BestEffort**​|所有容器都没设 Request/Limit|最先被驱逐|离线任务、批处理|

**Guaranteed 的严苛判据**：

- Pod 中每个容器的 CPU/Memory Request 和 Limit 都必须 > 0
    
- **且 CPU Request == CPU Limit**
    
- **且 Memory Request == Memory Limit**
    

> **💡 洞见**：QoS 的本质，是"资源声明的严格程度"决定"生存优先级"。**Guaranteed 之所以最后死，不是因为 K8s 偏爱它，而是因为"Request == Limit"意味着这个 Pod 既不能超用（Request 就是它的天花板），又不能少给（Request 是它的最低保障）——它是一个"老实公民"，系统没理由先杀它**。反之，BestEffort 是"不声明、不预留、不负责"的 Pod，节点 Pressure 时自然第一个被牺牲。

#### PriorityClass —— 调度抢占比 QoS 更高阶

PriorityClass 是集群级的优先级定义，值域 0 到 1,000,000,000（更大的数保留给系统关键 Pod）：

- **system-node-critical**：永远不应被驱逐的节点关键 Pod
    
- **system-cluster-critical**：集群关键 Pod
    

**调度抢占逻辑**：

1. 高优先级 Pod 无法调度时，调度器尝试从某节点驱逐低优先级 Pod 为其腾出空间
    
2. 抢占时选择"优先级最低的 Pod 集合"，若受 PodDisruptionBudget 保护则考虑更高优先级
    
3. **关键认知**：调度器的抢占逻辑**只考虑 Pod 优先级，不考虑 QoS**
    

> **💡 本章思想高地**：**QoS 与 PriorityClass 是正交的两套机制**：
> 
> - **调度抢占（Preemption）**：由 kube-scheduler 触发，**只看 PriorityClass**
>     
> - **节点压力驱逐（Eviction）**：由 kubelet 触发，**综合考虑 QoS + Priority + 资源超用比例**
>     
> 
> kubelet 驱逐 Pod 的排序依据：
> 
> 1. 资源使用是否超过 Request
>     
> 2. Pod 优先级
>     
> 3. 资源使用量相对于 Request 的比例
>     
> 
> **这意味着网上流传的"驱逐先看 Priority 再看 QoS"是不准确的**——官方口径是：kubelet 用 QoS 类来"估算 Pod 最有可能被驱逐的顺序"，但具体排序是 QoS + Priority + 超用比例的综合结果。一个 BestEffort 但高优先级的 Pod，可能比 Burstable 低优先级的 Pod 活得更久——但这不意味着 Priority 绝对压过 QoS，而是二者在不同维度共同作用。

#### 工业配置法则

- **核心业务（数据库、API 网关、支付核心）**：Guaranteed QoS + 高 PriorityClass——双保险
    
- **普通微服务**：Burstable QoS + 中 PriorityClass
    
- **批处理/测试/日志收集**：BestEffort QoS + 低 PriorityClass——节点压力时自动清理
    

### 14.3 驱逐机制 —— "保节点、弃 Pod" 的节点自救

#### Eviction 与 OOM Kill 的本质区别

|维度|Eviction（驱逐）|OOM Kill|
|---|---|---|
|触发者|kubelet|Linux 内核|
|触发时机|节点资源将至阈值以下（如 `memory.available<1Gi`）|容器内存超过 Limit 或节点内存彻底耗尽|
|可预测性|可配置阈值，可预测|不可预测，瞬间发生|
|是否按 QoS 排序|是|是（间接，通过 oom_score_adj）|
|目标|恢复节点稳定性|内核强制资源上限|

**驱逐的本质目标只有一个：保住 Node，牺牲 Pod**。

#### 驱逐触发条件

kubelet 监控四类节点压力信号：

- **MemoryPressure**：内存可用量低于阈值
    
- **DiskPressure**：磁盘空间/inode 不足
    
- **PIDPressure**：PID 数量耗尽
    

#### 驱逐排序的完整逻辑

当节点出现 MemoryPressure 时，kubelet 的驱逐顺序：

1. **BestEffort Pod 全部考虑驱逐**（因为它们没有 Request，永远"超用"）
    
2. 驱逐 BestEffort 后压力仍在 → 按 PriorityClass 驱逐，同优先级按"资源使用/Request 比例"降序
    
3. 仍不足 → 考虑驱逐 Guaranteed 和未超用 Request 的 Burstable Pod，按 PriorityClass 排序
    

**关键原则**：**kubelet 不会驱逐"使用量未超过 Request"的 Pod**——即使它的优先级很低。这意味着：一个低优先级但严格守规矩（使用 ≤ Request）的 Pod，比一个高优先级但严重超用（使用 >> Request）的 Pod 更安全。

> **💡 我的核心洞见**：驱逐机制的深层哲学是**"惩罚超用者，保护守规矩者"**。这不是简单的"优先级高的活下来"，而是"对资源契约的遵守程度"决定生死。**一个 BestEffort Pod 由于根本没签契约，天然就是"超用者"，所以第一个死；一个 Guaranteed Pod 由于严格签了契约（Request==Limit），它不可能超用，所以永远不会因为 Eviction 而死（只会被更高优先级的 Pod 抢占）**。这再次印证了全书的核心哲学：**在分布式系统里，"契约"比"身份"更根本**。

### 14.4 默认调度器 —— "过滤 + 打分"的两阶段决策

Kubernetes 调度器的算法分为两个清晰的阶段：

#### 第一阶段：Predicate（过滤）

对所有节点执行**硬约束检查**，过滤掉不满足条件的节点。核心 Predicate：

- **PodFitsResources**：节点空闲资源（Capacity - 所有 Pod Limit 之和）≥ Pod Request
    
- **PodFitsPorts**：HostPort 不冲突
    
- **PodFitsHost**：Pod 指定了 NodeName 时匹配
    
- **PodSelectorMatches**：匹配 nodeSelector
    
- **NoDiskConflict**：Volume 不冲突
    
- **NodeAffinity**：节点亲和性匹配
    
- **PodAffinity/PodAntiAffinity**：Pod 间亲和/反亲和
    
- **TaintToleration**：污点容忍
    

**并发执行**：调度器启动 16 个 Goroutine 并发为所有节点计算 Predicate。

#### 第二阶段：Priority（打分）

对过滤后的节点打分（0-10 分），加权求和后选最高分：

```
finalScore = Σ(weight_i × priorityFunc_i)
```

核心 Priority 函数：

- **LeastRequestedPriority**：选择 CPU/内存剩余最多的节点——**效果是让 Pod 在集群中分散**
    
    ```
    score = (cpu((capacity - sum(requests)) * 10 / capacity) 
           + memory((capacity - sum(requests)) * 10 / capacity)) / 2
    ```
    
- **BalancedResourceAllocation**：选择 CPU/内存分配最均衡的节点——避免"CPU 用满、内存空闲"的倾斜
    
- **NodeAffinityPriority**：节点亲和性权重
    
- **TaintTolerationPriority**：容忍度权重
    
- **SelectorSpreadPriority**：让同一 Service 的 Pod 跨节点分散——提高可用性
    
- **InterPodAffinityPriority**：Pod 间亲和性权重
    
- **ImageLocalityPriority**：镜像本地缓存优先——减少拉取时间
    

#### 两阶段设计的哲学

> **💡 本章最核心的洞见**：调度器的两阶段设计，本质是"正确性"与"最优性"的解耦：
> 
> - **Predicate 解决"能不能放"**（硬约束，必须 100% 满足）
>     
> - **Priority 解决"放哪里最好"**（软约束，在满足条件的节点中选最优）
>     
> 
> 这种"先过滤、后打分"的模式，与第 8 章"流量治理"中"先限流、后容错"的防御纵深如出一辙——**都是把"必须满足的硬规则"与"希望满足的软偏好"分层处理**。工业界几乎所有资源调度系统（YARN、Mesos、Borg）都采用类似的两阶段模型，因为它是"NP-hard 装箱问题"在工程上的最优近似解。

#### LeastRequestedPriority 的隐性效果

LeastRequestedPriority 表面是"选最空闲节点"，但其**全局效果是 Pod 在集群中均匀分布**——这提高了：

- **容错性**：同一服务的多个副本分散在不同节点，单节点故障只影响部分副本
    
- **资源利用率**：避免"热点节点"与"冷点节点"并存
    
- **弹性**：新 Pod 总有空间可放
    

但 LeastRequestedPriority 也有盲区——它不考虑"节点资源分配均衡性"，可能导致"CPU 用满但内存空闲"的倾斜节点。**这就是为什么 BalancedResourceAllocation 作为补充 Priority 函数被引入**——两者配合，既有"分散"又有"均衡"。

## 三、把全章"串起来"的三条洞见（我的原创综合）

### 洞见一：资源调度的本质是"四层契约"

K8s 资源调度是四层契约的叠加：

1. **Pod → 系统**：Request/Limit 契约（"我至少要这么多，最多用这么多"）
    
2. **Pod ↔ Pod**：QoS/Priority 契约（"Pressure 时谁先死"）
    
3. **kubelet → 节点**：Eviction 契约（"节点快死时我有权杀 Pod"）
    
4. **调度器 → 集群**：Predicate/Priority 契约（"新 Pod 去哪儿最合适"）
    

**这四层契约共同构成了 K8s "声明式资源调度"的完整闭环**。缺任何一层，系统都会在"资源争抢"这个分布式系统永恒的主题上失守。

### 洞见二：CPU 与内存的本质差异，决定了完全不同的故障模式

- **CPU 可压缩**​ → Request 保证公平份额，Limit 导致节流（性能下降但不崩溃）
    
- **内存不可压缩**​ → Request 保证预留，Limit 超限直接 OOM Kill（崩溃重启）
    

**工业界的关键决策**：

- **CPU Limit**：慎设。Request 已保证公平调度，Limit 只会在节点有空闲 CPU 时仍节流容器，造成无谓的延迟毛刺。Google SRE 和许多大型互联网公司选择"只设 Request、不设 CPU Limit"
    
- **Memory Limit**：必设。内存是不可压缩资源，不设 Limit 等于"允许 Pod 吃掉整个节点内存，触发内核 OOM 杀进程，且被杀顺序不可控"
    
- **Memory Request**：必须 ≥ JVM Xmx / 应用实际启动需求，否则应用启动即被 OOM Kill
    

### 洞见三：调度的本质是"在多个合理的选择中做最优决策"

Predicate 阶段回答"哪些节点可行"，Priority 阶段回答"哪个节点最好"。**这两阶段的分离，反映了工程问题的普遍真理——"正确性"与"最优性"必须分层处理**：

- 把软偏好混入硬约束 → 可能导致"无节点可调度"
    
- 把硬约束混入软偏好 → 可能导致"放到不满足需求的节点上"
    

**K8s 调度器的两阶段模型，是 NP-hard 资源调度问题在工程上的优雅近似**——它在"计算效率"与"调度质量"之间取得了极佳平衡。这也是为什么从 Borg 到 Kubernetes，两阶段调度模型被沿用了二十年。

## 四、工业落地的方法论（我的原创综合）

把本章思想落到工程实践，我提炼出 **"K8s 资源调度五条军规"**：

**军规一：核心业务必须 Guaranteed + 高 Priority**

```
resources:
  requests:
    cpu: "2"
    memory: "4Gi"
  limits:
    cpu: "2"        # Request == Limit
    memory: "4Gi"   # Request == Limit
priorityClassName: system-cluster-critical
```

数据库、API 网关、支付核心等关键服务——双保险确保它们在节点 Pressure 时最后死。

**军规二：普通服务用 Burstable，但 Request 必须"诚实"**

```
resources:
  requests:
    cpu: "500m"     # 诚实评估：应用正常运行所需的最小 CPU
    memory: "1Gi"   # 必须 ≥ JVM Xmx + Metaspace + 系统开销
  limits:
    cpu: "2"        # 允许突发到 2 核
    memory: "2Gi"   # 内存 Limit 必设，防节点 OOM
```

**Request 不是"越小越好"**——低 Request 导致调度器把过多 Pod 装到同一节点，节点 CPU 软死锁、内存 OOM 连锁。

**军规三：CPU Limit 慎设，Memory Limit 必设**

- **CPU**：只对延迟不敏感的服务设 Limit；核心服务"只设 Request、不设 CPU Limit"，让节点空闲 CPU 可被充分利用
    
- **Memory**：所有 Pod 必须设 Limit，且 Limit ≥ Request（否则自动降级为 Guaranteed 导致无法突发）
    

**军规四：驱逐阈值必须显式配置**

```
# kubelet 启动参数
--eviction-hard=memory.available<1Gi,nodefs.available<10%,nodefs.inodesFree<5%
--eviction-soft=memory.available<2Gi,nodefs.available<15%
--eviction-soft-grace-period=memory.available=2m,nodefs.available=2m
--eviction-max-pod-grace-period=30
```

**软驱逐 + 硬驱逐组合**，给 Pod 优雅退出的时间，避免硬杀导致数据损坏。

**军规五：用 PriorityClass 保护关键路径**

```
# 为核心业务创建高优先级
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: critical-business
value: 100000
globalDefault: false
description: "核心业务优先级"
```

  name: api-pdb

  minAvailable: 3

      app: api

## 五、与全书脉络的呼应

把第14章放回全书的逻辑链中看，它是第四部分"不可变基础设施"的收官之作：

- **第11章**：容器化——让"应用"变成不可变的、可重建的
    
- **第12章**：容器网络——让"通信"在动态环境中始终连通
    
- **第13章**：持久化存储——让"数据"在易逝的容器中永恒存活
    
- **第14章**：资源与调度——让"有限的节点资源"在无限的 Pod 欲望中被最优分配
    

**这四章共同回答了"不可变基础设施"的核心命题：应用不可变、通信动态化、数据持久化、资源最优化**。

更进一步，把第14章与全书主线串联：

- **第8章"流量治理"**：HPA 基于 CPU/内存指标自动扩缩容 → 本章的 Request/Limit 是 HPA 的决策依据
    
- **第9章"可靠通信"**：Zero Trust 网络策略 → 本章的 PriorityClass 保护关键服务不被驱逐
    
- **第10章"可观测性"**：Metrics 监控 → 本章的 Resource 使用率是核心监控指标
    
- **第6章"分布式共识"**：etcd 的 QoS 必须是 Guaranteed + 最高 Priority → 否则 etcd 被驱逐 = 集群脑裂
    

**资源调度不是某一章的主题，而是贯穿全书的一种"底层纪律"——它让分布式系统的所有其他能力"在资源约束下仍能正确、最优地运行"**。这也与全书"凤凰"意象呼应——**分布式系统的可靠性，建立在"用 Request/Limit 约束欲望、用 QoS/Priority 区分贵贱、用 Eviction 做节点自救、用调度器做最优放置"这一资源调度第一性原理之上，而 K8s 的四层资源契约，正是这一原理在云原生时代的最强表达**。

---

> **收尾一句**：本章教给你的，不是"Request/Limit 怎么配、调度器怎么调"，而是一把更锋利的尺子——**当有人再向你推销"K8s 资源调度最佳实践"时，先问：它在"资源模型→QoS/优先级→驱逐→调度"的四层契约中工作在哪一层？它是否尊重了"CPU 可压缩 vs 内存不可压缩"的本质差异？它是否理解了"QoS 与 PriorityClass 是正交机制"？它的调度策略是"先过滤后打分"的两阶段模型吗？**​ 能回答这四问，你就不再会被"调度调优名词"裹挟，而能做出有依据、有洞见、贴合业务实际的资源调度决策。这也与全书"凤凰"意象呼应——**分布式系统的可靠性，建立在"用四层资源契约把无限的 Pod 欲望约束在有限的节点容量之内"这一第一性原理之上，而 Request 的调度依据、Limit 的运行时上限、QoS 的生存优先级、Eviction 的节点自救、调度器的过滤打分，正是这一原理在"资源与调度"维度上的五重跃迁**。
