
# 《凤凰架构》第3章 · 事务处理 —— 读书笔记

> **一句话立住**：前三章是一条完整的逻辑链——第1章解决"系统为什么要拆"，第2章解决"拆开之后怎么通信"，本章解决"拆开之后怎么保证数据不丢不乱"。周志明的核心命题是：**分布式事务的本质，是"在放弃强一致性的代价下，用工程手段逼近一致性"**。这里的"逼近"二字是关键——你永远得不到绝对的一致性，只能得到"足够好的一致性"。理解这一点，你就不会再执着于"有没有一种分布式事务能像本地事务一样简单可靠"，而会学会**按业务对一致性的真实需求，选最划算的折中方案**。这也是本章最值得刻进脑子的一句话。

---

## 一、先把全章骨架搭起来（四类事务、一条主线）

本章按"**服务数量 × 数据源数量**"把事务分成四类，并围绕"一致性代价"逐级推进：

|类型|服务数|数据源数|核心机制|一致性|一句话定位|
|---|---|---|---|---|---|
|本地事务（3.1）|单|单|数据库 ACID 原生能力|强|一切事务的"基准参照系"|
|全局事务（3.2）|单|多|XA / 2PC（两阶段提交）|强|单服务跨库，靠协调者投票|
|共享事务（3.3）|多|单|多服务共用一个数据源|强（理论）|理论可行、生产罕见|
|分布式事务（3.4）|多|多|CAP 权衡 + 柔性事务|最终|微服务主战场，本章重头戏|

**一条贯穿始终的主线**：**随着"服务×数据源"从 1×1 走向多×多，强一致性（ACID）的代价呈指数级上升，最终被迫退到"最终一致性"（BASE）**。这不是技术的失败，而是**分布式系统的物理本质——网络不可靠、节点会挂、消息会丢会重——决定的必然妥协**。本章的思想含量，全在"如何聪明地妥协"这六个字里。

---

## 二、逐节脉络 + 我的理解与洞见

### 3.1 本地事务 —— 一切事务的"基准参照系"

#### 3.1.1 实现原子性和持久性

- **脉络**：本地事务是"仅操作单一事务资源、不需要全局事务管理器协调"的事务，直接依赖数据源（如数据库）原生提供的 ACID 能力。应用层最多对事务接口做一层标准化包装（如 JDBC），**不能深入参与事务运作过程**——这与后面靠应用代码实现的 XA/TCC/SAGA 形成鲜明对比。为保证原子性（Atomic）和持久性（Durability），数据库在崩溃后靠"崩溃恢复（Crash Recovery）"补救，主流手段有三种：
    
    - **Commit Logging（提交日志）**：把"改什么数据、改成什么值"顺序追加到日志（最高效的写入方式），日志安全落盘后数据库才改数据，改完追加"结束记录"。简单可靠，但**先天缺陷是"绝不允许事务提交前修改磁盘数据"**。
        
    - **Shadow Paging（影子分页）**：不动原数据，复制一份修改，最后把指针从原数据指向副本（指针切换被视为原子操作）。比 Commit Logging 简单，但涉及隔离性和并发锁时并发能力有限，高性能数据库中应用不多。
        
    - **Write-Ahead Logging / WAL（提前写入日志）**：**现代数据库的主流选择**。引入 **Undo Log（回滚日志）**——记录"改了哪个位置、从什么值改成什么值"，用于事务回滚或崩溃恢复时"擦除"提前写入的数据变动；以及 **Redo Log（重做日志）**——记录已提交的事务变动，崩溃后重演以保证持久化。**简单说：Undo 负责"撤销未提交的"，Redo 负责"重做已提交的"。**
        
    
- **洞见（第一性原理）**：这一节最该记住的一句话是——**"本地事务的 ACID，本质是数据库内核用日志换来的"**。原子性和持久性不是"免费"的，它们是用"先写日志、再改数据"的额外写入代价换来的。**理解 WAL，你就理解了为什么数据库"写性能"总会有一个由日志落盘速度决定的上限**，也理解了为什么后面所有分布式事务方案都要额外付出"协调开销"——因为分布式事务本质上是在多个 WAL 之间再协调出一个"全局的先后秩序"。
    

#### 3.1.2 实现隔离性

- **脉络**：隔离性靠**锁机制**（悲观锁：行锁/表锁阻塞并发；乐观锁：基于版本号/时间戳检测冲突，如 MVCC）和 **MVCC（多版本并发控制）**——保存数据历史版本，让读不阻塞写，解决脏读、不可重复读，但可能产生幻读。四种经典隔离级别：读未提交 → 读已提交 → 可重复读 → 可串行化，分别对应不同的锁策略（读锁/写锁/范围锁）。
    

|隔离级别|加锁策略|能防的问题|遗留问题|
|---|---|---|---|
|读未提交|几乎不加读锁|—|脏读、不可重复读、幻读|
|读已提交|读锁用完即放|脏读|不可重复读、幻读|
|可重复读|读锁贯穿事务|脏读、不可重复读|幻读（无范围锁，可插入新行）|
|可串行化|读锁+写锁+范围锁全加|全部|性能最低|

- **洞见**：**隔离级别是"并发性能 vs 数据异常"的权衡滑杆**——级别越高越安全但越慢。这里藏着一个常被忽视的洞见：**"可重复读"挡住了已有数据的修改，却挡不住"别人插入新行"，所以仍会幻读**——这个细节解释了为什么很多数据库的默认隔离级别停在"读已提交"而非最高级。**工程上的一条铁律：不要盲目追求最高隔离级别，先问"我的业务到底怕哪种异常"，再选级别**——这正是"按痛点选方案"思想在事务里的第一次亮相。
    

### 3.2 全局事务 —— 单服务跨库的"强一致"尝试

- **脉络**：全局事务适用于"**单服务 + 多数据源**"场景，核心是 **XA（eXtended Architecture）接口**——在事务管理器（Transaction Manager，协调全局）和资源管理器（Resource Manager，驱动本地事务）之间形成双向通信桥梁，把多个数据源的一致动作统一提交/回滚。XA 把提交拆成两阶段，即 **2PC（两阶段提交）**：
    
    - **准备阶段（投票）**：协调者询问所有参与者是否准备好提交，参与者若就绪回复 Prepared，否则回复 Non-Prepared。
        
    - **提交阶段（执行）**：若全部 Prepared，协调者先本地持久化事务状态为 Commit，再向所有参与者发 Commit 指令，参与者立即提交；否则（任一 Non-Prepared 或超时），协调者持久化为 Abort 并向全体发 Abort，参与者立即回滚。
        
    
- **2PC 的三大顽疾**：① **同步阻塞**——参与者锁定资源期间，其他事务必须等待；② **单点故障**——协调者宕机可能让事务悬挂（participants 不知道该提交还是回滚）；③ **数据不一致**——网络分区时可能部分提交、部分回滚。为缓解阻塞，衍生出 **3PC（三阶段提交）**：新增 CanCommit（询问能否提交）→ PreCommit（预提交）→ DoCommit（最终提交），并引入双向超时机制，降低阻塞风险。**但 3PC 仍无法在网络分区下保证绝对一致，且多一轮通信增加延迟**——它只是"把 2PC 的痛点减轻"，而非"根治"。
    
- **洞见（本章思想高地之一）**：**2PC/3PC 的悲剧，不在于设计得不好，而在于它们试图用"额外一轮通信 + 一个协调者"来伪造一个"分布式里的本地事务"**。这恰恰违背了分布式的物理本质——网络会分区、协调者会挂。**所以 2PC 的真正定位是"数据库中间件层（如 ShardingSphere）自动处理的跨分片事务"，而不是"微服务间事务的主流方案"**。理解这一点，你就不会在微服务里盲目上 2PC，而会把 2PC 的适用边界牢牢框在"单服务跨库、且能容忍性能损耗"的场景里。这也是周志明把全局事务和分布式事务分开讲的深意——**二者虽然都"跨多个数据源"，但微服务引入的"多服务"维度，让问题性质发生了根本变化**。
    

### 3.3 共享事务 —— 一个"理论可行、生产罕见"的边界案例

- **脉络**：共享事务是"**多服务 + 单数据源**"——多个服务共享同一个数据库。这在理论上可行（多服务通过同一数据源的事务接口协调），但**周志明明确指出它是"伪需求"**：现实中几乎只有 ProxySQL、MaxScale 这样"对多个数据库实例做负载均衡"的数据库代理，而几乎没有"代理一个数据库为多个应用提供事务协调"的交易服务代理。
    
- **洞见**：这一节的价值在"纠偏"。**它提醒我们：架构方案不能只看"理论上能不能跑通"，还要看"是否顺应生产系统的压力方向"**。多服务共享单库，意味着数据库成为压力最大、又最难伸缩的瓶颈——这与微服务"去中心化、独立伸缩"的初衷背道而驰。**所以共享事务的正确结论不是"如何实现它"，而是"应该避免它"**：每个微服务拥有自己的数据库，才是微服务数据管理的正道。这一节用"反面教材"的方式，再次强化了全章"按实际生产压力做权衡"的主线。
    

### 3.4 分布式事务 —— 本章重头戏，微服务的"一致性战场"

#### 3.4.1 CAP 与 ACID —— 为什么强一致不得不让步

- **脉络**：分布式事务特指"**多服务 + 多数据源**"的事务处理机制（注意与 DTP 模型里的"分布式事务"区分）。CAP 定理指出：分布式系统中，**一致性（C，任何时刻任何节点看到的数据都符合预期）、可用性（A，系统不间断提供服务）、分区容忍性（P，网络分区时系统仍能正确服务）三者最多同时满足两个**。周志明给出了一个极其锋利的论证，解释为什么**今天主流分布式系统几乎都选 AP（牺牲 C）**：
    
    1. **P 是分布式的天然属性**——只要用网络共享数据，分区就始终可能存在，无法在设计层面彻底避免。
        
    2. **A 是建设分布式系统的根本目的**——如果可用性随节点增多反而降低，分布式就失去了价值（除非是银行/证券这类"宁可中断也不能出错"的场景）。
        
    
- **从 ACID 到 BASE**：既然 C 被牺牲，人们重新定义一致性——把 ACID 里的 C 称为"**强一致性/线性一致性**"，把 AP 系统"尽可能获得正确结果"的追求称为"**弱一致性**"，并在二者之间总结出"**最终一致性**"：如果数据一段时间内不被其他操作更改，它最终会达到与强一致相同的结果，面向最终一致性的算法也叫"**乐观复制算法**"。由此衍生 **BASE 理论**：Basically Available（基本可用）+ Soft state（软状态）+ Eventually consistent（最终一致）。**相应地，用 ACID 的事务叫"刚性事务"，本章后续几种分布式事务方案统称"柔性事务"**。
    
- **洞见（全章最核心的洞见）**：**CAP 不是"三选二"的菜单，而是"在 P 必然存在的前提下，C 与 A 的权衡滑杆"**。很多人误读 CAP 为"我可以任意选两个"，这是错的——**P 没得选，真正要选的是"在网络分区时，我要一致性还是要可用性"**。对绝大多数互联网业务（电商、社交、内容平台），答案是"要可用，接受最终一致"；对金融核心（转账、清算），答案是"要一致，宁可暂时不可用"。**这个"业务属性决定一致性选型"的判断，是本章给架构师最重要的一把尺子**——后面所有柔性事务方案（可靠事件队列/TCC/SAGA），本质都是在"如何以更低的代价逼近最终一致"这道题上各显神通。
    

#### 3.4.2 可靠事件队列 —— 最简单、最主流的柔性事务

- **脉络**：可靠事件队列（也叫"本地消息表"/"事务性发件箱 Outbox 模式"）是**用消息队列连接多个本地事务，靠消息的可靠投递保证最终一致**。其核心做法是 **Best-Effort 1PC（最大努力一次提交）**：把"最有可能出错、优先级最高"的业务以本地事务方式完成，同时把后续操作记录为事件/消息一并写入本地数据库的消息表（保证"业务落库"与"消息落库"的原子性），再由后台任务/中继进程异步投递到 MQ（如 RocketMQ/Kafka/RabbitMQ），下游服务消费并执行本地事务。**它的铁律是：第一步业务一旦提交成功，后续就没有"失败回滚"的概念，只许成功、不许失败——靠不断重试（最大努力交付）直至成功或人工介入**。为避免重复投递/消费，所有消费操作必须**幂等**。
    
- **典型顺序安排**（电商下单）：账号扣款（最易出错、优先级最高）→ 仓库出库 → 商家收款。账号扣款成功则"开弓没有回头箭"，后续步骤尽全力推进。
    
- **洞见**：**可靠事件队列的高明之处，在于它把"分布式事务"这个难题，转化成了"保证消息不丢 + 保证消费幂等"这两个已经被 MQ 生态解决得很好的子问题**。它不追求强一致，而是用"异步 + 重试 + 幂等"三件套，以极低的性能代价换取最终一致。**这是工业界落地最广泛、性价比最高的柔性事务方案**——但也正因"不锁定资源、不保证隔离"，它**无法解决"超售"这类需要强隔离的场景**（两个人同时买同一商品，各自检查都不超售，加起来却超售了）。这个短板，恰恰引出了下一节 TCC 的存在理由。
    

> **工业实际**：阿里 RocketMQ 的"事务消息"（半消息→本地事务→确认投递）是此模式的工业级实现，广泛用于电商下单、支付通知；每日亿级订单场景下，配合"本地消息表 + 定时补发 + 死信队列 + 人工干预通道"，能做到"消息零丢失、消费幂等、最终一致"。Seata 框架的 AT 模式（对业务几乎无侵入）底层也走"先记录 undo log、再异步推进"的思路，是可靠事件队列思想的框架化落地。

#### 3.4.3 TCC 事务 —— 用"业务侵入"换"强隔离 + 高性能"

- **脉络**：TCC（Try-Confirm-Cancel）由数据库专家 Pat Helland 在 2007 年论文《Life beyond Distributed Transactions: An Apostate's Opinion》中提出，是**业务侵入式较强的事务方案**，要求把业务处理拆成"预留资源"和"确认/释放资源"两个子过程：
    
    - **Try**：尝试执行——完成所有业务可执行性检查（保障一致性），并预留（冻结）全部需用到的业务资源（保障隔离性，如冻结库存、预扣金额）。
        
    - **Confirm**：确认执行——不做任何业务检查，直接使用 Try 阶段准备好的资源完成业务。**Confirm 可能重复执行，必须幂等**。
        
    - **Cancel**：取消执行——释放 Try 阶段预留的资源。**Cancel 也可能重复执行，必须幂等**。
        
    
    TCC 类似两阶段提交：先对所有参与方执行 Try（任一失败则全部 Cancel），再统一执行 Confirm（任一失败则最大努力重试 Confirm 直至成功）。
    
- **洞见（第一性原理）**：**TCC 的本质，是把"数据库层面的锁"上移到"业务层面的资源冻结"**——用"冻结库存/预扣金额"这种业务语义，代替数据库的行锁/表锁，从而**避免了数据库长事务锁定，提升了吞吐量，同时获得了可靠事件队列所没有的隔离性（解决超售）**。但它的代价极其明确：**业务侵入性极强——每个参与服务都要写 3 套接口（Try/Confirm/Cancel），开发量大；且要求"技术可控性"高，能改造所有参与方的接口**。这就决定了 TCC 的适用边界：**高并发、对隔离性要求高、且你能控制所有参与方代码的场景**（如电商库存扣减、金融支付）。一旦涉及"无法改造的第三方系统"（如直连银行 U 盾/扫码支付），TCC 的 Try 阶段就无从实施——这个限制，自然引出了下一节 SAGA。
    

> **工业实际**：蚂蚁金服/支付宝的核心支付链路、大型电商的库存预扣减，普遍采用 TCC 或其变体（如阿里 Seata 的 TCC 模式），在"双 11"级高并发下既保证不超售、又避免数据库长事务拖垮系统。**这印证了：TCC 是"用开发工作量换取高性能 + 强隔离"的典型权衡**。

#### 3.4.4 SAGA 事务 —— 长事务 + 跨第三方的最终一致方案

- **脉络**：SAGA 源于 1987 年普林斯顿大学 Hector Garcia-Molina 和 Kenneth Salem 在 ACM SIGMOD 发表的论文《SAGAS》——**比微服务早了约 30 年**，原本用于解决"长时间事务（Long-Lived Transactions）"占用锁过久的问题。其核心是**把一个大事务 T 拆成一系列可交错运行的本地子事务 T1→T2→…→Tn（每个 Ti 具备原子性），并为每个 Ti 设计对应的补偿动作 Ci**：
    
    - **Ti 与 Ci 必须满足**：二者都幂等；Ti 与 Ci 满足交换律（先执行 Ti 还是先执行 Ci 效果一样）；Ci 必须能成功提交（失败则持续重试直至成功或人工介入）。
        
    - **失败恢复两种策略**：① **正向恢复（Forward Recovery）**——Ti 失败则一直重试 Ti 直至成功（适用于"已经扣款就一定要发货"这类必须完成的场景）；② **逆向恢复（Backward Recovery）**——Ti 失败则按逆序执行已成功步骤的补偿 C(i-1)→…→C1，把系统带回一致状态。
        
    - **两种实现风格**：**编排式（Orchestration）**——由中央协调器（Saga Execution Coordinator）控制流程；**协同式（Choreography）**——无中心协调器，服务间通过事件/消息直接触发，各自监听并触发下一步。
        
    
- **洞见（本章收官 + 与 TCC 的辩证）**：**SAGA 与 TCC 的根本分野在于"是否冻结资源 + 是否要求业务可控"**：
    
    - TCC 用"冻结/预留"换"隔离性"，但要求你能改造所有参与方接口——**适合你能掌控全部参与方的内部高并发场景**。
        
    - SAGA 不做资源冻结、不要求接口三态化，每个子事务直接提交，**对"无法控制的外部系统"（如第三方银行支付、酒店/机票供应商）更友好**——这正是 TCC 做不到、而 SAGA 存在的核心理由。**代价是 SAGA 没有隔离性**（与可靠事件队列类似），且补偿是"语义层面的反向操作"（扣款的补偿是退款，发货的补偿是召回包裹），不是简单的"数据库回滚"。
        
    
    **我的综合洞见**：把 TCC 和 SAGA 看成"同一道题的两种答案"——题面是"如何在微服务间保证最终一致"。**TCC 答："我冻结资源、分步确认，换隔离性和高性能，但你要让我改所有参与方的代码"；SAGA 答："我不冻结、直接提交、失败时语义补偿，换对第三方的友好，但你接受无隔离 + 补偿逻辑复杂"**。**二者互补而非替代**——这正是本章"没有银弹、因地制宜"主旨的最高体现。
    

> **工业实际**：旅行预订平台（同时订机票+酒店+租车，涉及多个第三方供应商）是 SAGA 的教科书级场景——各供应商接口不可改造、流程长、每步都有明确逆操作（取消机票/退订酒店），天然契合 SAGA。**阿里 Seata 的 SAGA 模式**已在金融核心等场景落地，支持"状态机编排 + 正向/补偿服务"的可视化编排。**这印证了：凡是"长流程 + 跨第三方 + 每步有明确反向操作"的业务，SAGA 往往是比 TCC 更务实的选择**。

## 三、把全章"串起来"的三条洞见（我的原创综合）

1. **一条主线（一致性的代价递增）**：从"本地事务（1×1，强一致、零协调开销）"→"全局事务（1×多，XA/2PC 强一致但同步阻塞、单点故障）"→"共享事务（多×1，理论可行、生产应避免）"→"分布式事务（多×多，CAP 迫使退到最终一致，靠柔性事务逼近）"，**强一致性的代价随"服务×数据源"指数级上升，最终不得不在 P 必然存在的前提下，于 C 与 A 之间做权衡**。这是全章的"第一性原理骨架"。
    
2. **一个核心判断（没有银弹，只有权衡）**：**分布式事务里没有"包治百病"的方案，只有"按业务属性选最划算折中"的智慧**。选型的决策逻辑应是——
    
    - 单服务单库 → 本地事务（JDBC 事务，零额外成本）；
        
    - 单服务跨库 → XA/2PC（能容忍性能损耗时）；
        
    - 多服务多库、异步/高吞吐/能接受最终一致 → **可靠事件队列 / MQ 事务消息（工业首选，性价比最高）**；
        
    - 多服务多库、需强隔离（防超售）、能改造所有参与方 → **TCC（用开发量换高性能+隔离）**；
        
    - 多服务多库、长流程、涉及不可改造的第三方 → **SAGA（用无隔离+补偿复杂换对第三方友好）**。
        
    
3. **一种方法论（从"题眼"出发而非"从框架出发"）**：**不要先问"我用 Seata 还是 RocketMQ"，而要先问三个业务问题——① 我的业务能接受最终一致吗？（能→柔性事务；不能→2PC/TCC）② 我需要防超售/强隔离吗？（需要→TCC；不需要→可靠事件队列/SAGA）③ 参与方我能全部改造吗？（能→TCC；不能→SAGA）**。能回答这三问，选型自然清晰——这正是"理解创新 + 第一性原理"在本章最实在的落脚点：**用"业务痛点"而不是"技术潮流"驱动架构决策**。
    

> **收尾一句**：本章教给你的，不是"哪种分布式事务最先进"，而是一把更锋利的尺子——**当有人再向你推销"下一代分布式事务框架"时，先问：我的业务要强一致还是最终一致？要隔离还是吞吐？参与方能改造吗？**​ 能回答这三问，你就不再会被框架潮流裹挟，而能做出有依据、有洞见、贴合业务实际的选型决策。这也与全书"凤凰"意象呼应——**系统的可靠性不靠"永不出错"，而靠"在必然出错的分布式世界里，用聪明的折中，让整体最终回到一致"**。
