
# 《凤凰架构》第13章 · 持久化存储 —— 读书笔记

> **一句话立住**：前12章把"拆、通、一致、扛流量、保安全、达共识、做路由、治流量、建信任、可观测、容器化、容器网络"全部解决后，本章直面一个有哲学意味的矛盾——**容器是"易逝的、不可变的、随时重建的"，但数据必须"持久的、可变的、跨生命周期存活的"**。周志明的核心命题是：**Kubernetes 存储设计的本质，是用"抽象层叠抽象层"把"易逝的 Pod"与"持久的数据"解耦——Volume 解决临时共享，PV/PVC 解耦供给与消费，StorageClass 实现按需自动供给，CSI 把存储驱动从 K8s 源码中彻底外移**。这也是本章最值得刻进脑子的一句话：**容器可以死，数据不能死；而让数据在容器的生生死死中活下来，需要的是一整套"声明式存储抽象"，而非一块"挂载的硬盘"**。

---

## 一、先把全章骨架搭起来（两层抽象、一条主线）

本章按"K8s 存储设计 → 容器存储生态"两步走，但背后的逻辑是**抽象层不断叠加**的过程：

|抽象层|解决什么问题|关键机制|
|---|---|---|
|**Volume（卷）**​|容器间文件共享、临时数据|emptyDir / hostPath / configMap / secret|
|**PV / PVC**​|解耦"存储供给"与"存储消费"|管理员创建 PV，用户创建 PVC，控制平面绑定|
|**StorageClass**​|解耦"静态预置"与"动态供给"|声明 Provisioner，PVC 引用 SC 自动创建 PV|
|**CSI**​|解耦"K8s 核心代码"与"存储驱动实现"|标准 gRPC 接口，第三方驱动以容器形式部署|

**一条贯穿始终的主线（我的第一性原理提炼）**：**持久化存储的全部复杂度，源于一个根本矛盾——"容器的易逝性"与"数据的永恒性"的冲突**。解决这个矛盾的工具箱只有一样：**抽象**。每一层抽象都在用"上一层的复杂性"换取"下一层用户的简洁性"：

- **Volume 抽象**：让 Pod 不关心"文件存在哪里"（内存？宿主机？网络存储？）
    
- **PV/PVC 抽象**：让用户不关心"存储是怎么来的"，让管理员不关心"存储是被谁消费的"
    
- **StorageClass 抽象**：让"存储供给"变成"声明即所得"，无需人工预置
    
- **CSI 抽象**：让 K8s 不关心"后端是 EBS 还是 Ceph 还是 NFS"，让存储厂商不关心"K8s 的内部实现"
    

**这四次抽象，正是全书"关注点分离"哲学在存储维度上的四次递进展现**——与第 7 章"从类库到服务"、第 11 章"Operator 把运维知识编码为 CRD"、第 12 章"CNI 把网络从 K8s 中解耦"完全一脉相承。

## 二、逐节脉络 + 我的理解与洞见

### 13.1 Kubernetes 存储设计 —— 四次抽象的哲学

#### 13.1.1 Mount 和 Volume

- **脉络**：容器中的文件在磁盘上是临时存放的，这给容器中运行的较重要的应用程序带来两个问题：① 当容器重建时，容器中的文件将会丢失；② 当在一个 Pod 中同时运行多个容器时，容器间需要共享文件。Kubernetes 抽象出了 Volume 来解决以上两个问题。
    
- **Volume 的本质**：Volume 的生命周期与挂载它的 Pod 相同——Pod 被删除时 Volume 也一起被删除（但 Volume 里的文件可能在 Volume 消失后仍然存在，这取决于 Volume 的类型）。
    
- **Volume 的主要类型**：
    
    - **emptyDir**：Pod 生命周期内的临时存储，Pod 删除则数据丢失。适用于容器间共享、临时数据处理。
        
    - **hostPath**：直接使用宿主机路径，灵活性高，开发调试常用。
        
    - **configMap / secret**：把配置/密钥以文件形式注入容器。
        
    - **PV/PVC**：持久化存储（本章主角）。
        
    
- **💡 我的洞见（第一性原理层）**：**Volume 的引入，标志着 K8s 承认了一个事实——"容器文件系统是易逝的，但应用需求是多样的"**。emptyDir 解决"同 Pod 多容器共享"，hostPath 解决"开发调试要访问宿主文件"，configMap/secret 解决"配置注入"——这些是"易逝"场景下的权宜之计。**真正需要"跨越 Pod 生命周期"的持久数据，必须上升到 PV/PVC 抽象**——这正是下一节的议题。
    

#### 13.1.2 静态存储分配

- **脉络**：静态分配是"管理员预置"模式：
    
    1. 管理员手动创建 PV（指定容量、访问模式、后端存储类型）
        
    2. PV 进入 Available 状态
        
    3. 用户创建 PVC（指定容量、访问模式）
        
    4. PV Controller 扫描现有 PV，找到第一个满足 PVC 要求的 PV
        
    5. 绑定（Bound），PVC 与 PV 一对一映射
        
    
- **局限性**（DeepWiki 文档明确指出）：
    
    - 每个新 PV 都需要手动干预，无法扩展到大规模集群
        
    - 不适应当 Pod 自动扩缩的场景
        
    - **容量浪费**：一个请求 3 GiB 的 PVC 可能绑定到 5 GiB 的 PV，浪费 2 GiB
        
    
- **💡 我的洞见**：**静态分配的本质问题，是"人"成为了存储供给的瓶颈**。在虚拟机时代，管理员手动分配存储卷是合理的——因为虚拟机本身数量有限、生命周期长。但在 K8s 时代，Pod 可能秒级生灭、集群规模上千节点，**"人肉预置 PV"在速度和规模上都不可行**。这正是"静态分配"在工业界迅速被"动态分配"取代的根本原因——**不是静态分配错了，而是它的扩展模型与 K8s 的弹性哲学不兼容**。
    

#### 13.1.3 动态存储分配

- **脉络**：Kubernetes 1.6 引入动态分配，流程变为：
    
    1. 管理员预先创建 StorageClass（定义 Provisioner + 参数）
        
    2. 用户创建 PVC，引用 StorageClass
        
    3. PersistentVolume Controller 监听 PVC，通过 CSI 接口调用外部 Provisioner
        
    4. Provisioner 调用底层存储系统 API（EBS/GCE PD/Ceph 等）实际创建存储卷
        
    5. Provisioner 在 K8s API Server 中创建对应的 PV 对象
        
    6. PV 与 PVC 自动绑定
        
    
- **StorageClass 的关键字段**：
    
    - `provisioner`：标识负责供给的外部供应器（如 `ebs.csi.aws.com`）
        
    - `parameters`：传递给供应器的参数（如磁盘类型、IOPS）
        
    - `reclaimPolicy`：Retain（保留数据）/ Delete（自动删除，动态分配的默认值）
        
    - `volumeBindingMode`：Immediate（立即绑定）/ WaitForFirstConsumer（等待 Pod 调度后再绑定，解决跨 AZ 问题）
        
    
- **💡 本章最核心的洞见**：**动态分配的本质，是把"存储供给"从"管理员的手"转移到了"声明式 API"**。StorageClass 就像一个"存储模板"——它声明了"如果我需要一块 100Gi 的 SSD，就去调用 EBS API 创建一块 gp3 卷"。**用户不再想"存储从哪来"，只想"我要什么"；K8s 不再等"管理员创建好 PV"，而是"按需自动创建"**。这是"基础设施即代码"哲学在存储领域的极致体现——**存储不再是"被管理的资源"，而是"被声明的状态"**。
    
- **工业实践**：StatefulSet 配合动态分配，每个数据库副本都会自动获得独立的持久化存储卷。云厂商托管集群（EKS/GKE/AKS）默认提供基于 CSI 的动态分配，用户只需声明 PVC 即可获得云盘。
    

#### 13.1 小节总结：四次抽象的哲学递进

|抽象层|谁不关心什么|代价|收益|
|---|---|---|---|
|**Volume**​|Pod 不关心文件存哪里|临时性，Pod 删除则数据丢失|容器间共享、配置注入|
|**PV/PVC**​|用户不关心存储怎么来；管理员不关心被谁消费|需要管理员预置 PV|供给与消费解耦|
|**StorageClass**​|用户不关心供给细节；系统自动创建 PV|需要预先定义 StorageClass|按需自动供给，无限扩展|
|**CSI**​|K8s 不关心后端存储类型；存储厂商不关心 K8s 内部|需要部署 CSI 驱动|存储生态繁荣，驱动独立演进|

**这四次抽象，每一次都在用"声明式"替代"命令式"，用"解耦"替代"耦合"**。这正是云原生哲学的核心——**让复杂的事情变得声明即所得**。

### 13.2 容器存储与生态 —— 从 In-Tree 到 CSI 的范式革命

#### 13.2.1 Kubernetes 存储架构

- **核心组件**：
    
    - **PV Controller**：管理卷的整个生命周期，控制 PVC 和 PV 进行绑定，执行卷的 Provision 或 Delete 操作
        
    - **AD Controller（Attach/Detach Controller）**：执行卷的 Attach 或 Detach，将卷挂接到目标节点
        
    - **Volume Manager（kubelet 内）**：执行卷的 Mount 或 Unmount，以及共享目录挂载、卷格式化等操作
        
    
- **存储生命周期三阶段**：
    
    1. **Provision/Delete**：创建/删除存储卷（PV Controller 调用 CSI 驱动）
        
    2. **Attach/Detach**：将卷挂接到目标节点（AD Controller 调用 CSI 驱动）
        
    3. **Mount/Unmount**：在节点上将卷挂载到指定目录（Volume Manager 调用 CSI 驱动）
        
    
- **💡 洞见**：K8s 存储架构的本质，是**把"存储生命周期"分解为三个独立的控制循环**——供给、挂载、使用。**每个控制循环都是"声明式调和"**：PV Controller 调和"PVC 期望"与"PV 实际"，AD Controller 调和"Pod 调度"与"卷连接状态"，Volume Manager 调和"挂载意图"与"实际挂载状态"。**这与第 6 章"分布式共识"、第 11 章"K8s 声明式控制循环"的哲学完全一致——K8s 不是"执行命令"，而是"调和状态"**。
    

#### 13.2.2 FlexVolume 与 CSI

- **In-Tree 模式的痛点**（K8s 源码内集成驱动）：
    
    - 存储驱动与 K8s 核心代码强耦合
        
    - 新增存储系统需修改 K8s 代码库
        
    - 版本迭代受限于 K8s 发布周期
        
    
- **FlexVolume（K8s 1.2+，GA 1.8，已弃用）**：
    
    - 可执行文件模型，放置在节点的 `/usr/libexec/kubernetes/kubelet-plugins/volume/exec/` 路径
        
    - 局限性：
        
        - **不支持 Provision/Delete**，动态供给必须依赖额外的 External Provisioner
            
        - 必须在每个节点手动安装驱动二进制
            
        - 跨调用无状态，状态必须存储在临时文件中
            
        
    
- **CSI（Container Storage Interface）**：
    
    - K8s 1.9 引入，1.13 GA，已成为标准
        
    - 定义 gRPC 接口规范（约 2704 行，相比 FlexVolume 的 155 行更为完备）
        
    - **Kubernetes 侧组件**（Sidecar 模式部署）：
        
        - **Node Driver Registrar**：向 kubelet 注册 CSI 插件
            
        - **External Provisioner**：监听 PVC，调用插件 CreateVolume/DeleteVolume
            
        - **External Attacher**：监听 VolumeAttachment，调用插件 Attach/Detach
            
        - **External Resizer**：处理卷扩容
            
        - **External Snapshotter**：处理快照
            
        
    - **存储厂商侧组件**（gRPC 服务）：
        
        - **CSI Identity**：描述插件能力
            
        - **CSI Controller**：实现 CreateVolume/DeleteVolume/Attach/Detach 等
            
        - **CSI Node**：实现 NodePublish/NodeUnpublish 等节点侧操作
            
        
    
- **💡 本章思想高地**：**CSI 的胜利，不是技术细节的胜利，而是"架构哲学"的胜利**。FlexVolume 试图用"可执行文件"解耦，但仍有诸多限制；CSI 用"gRPC 服务 + Sidecar 模式"彻底解耦——**存储驱动不再是一个文件，而是一个容器化的微服务**。这带来三大革命性优势：
    
    1. **无需重启集群即可升级存储驱动**（Sidecar 滚动更新）
        
    2. **存储厂商与 K8s 社区完全解耦**（独立开发、独立发布）
        
    3. **支持完整的存储生命周期**（Provision/Attach/Mount/Snapshot/Resize/Monitor）
        
    

#### 13.2.3 从 In-Tree 到 Out-of-Tree

- **CSIMigration 计划**（K8s 1.17）：
    
    - 各大云厂商的 In-Tree 驱动（AWS EBS、GCE PD、vSphere 等）逐步迁移到 CSI
        
    - 通过 CSI Migration 特性，Out-of-Tree 驱动可以伪装成 In-Tree 等效驱动，保持向后兼容
        
    - 用户无需修改现有 YAML，底层自动切换到 CSI 实现
        
    
- **当前状态**：
    
    - In-Tree 驱动：已冻结，不再接受新的 In-Tree 卷类型
        
    - FlexVolume：已弃用（K8s 1.23 标记 deprecated）
        
    - CSI：活跃开发，推荐方案
        
    
- **💡 我的洞见**：**In-Tree → CSI 的迁移，是 K8s"减肥"战略的缩影**。早期的 K8s 试图"什么都自己实现"——In-Tree 存储驱动、In-Tree 网络插件（CNI 之前）、In-Tree 容器运行时（CRI 之前）。但随着生态爆发，K8s 社区意识到：**"平台应该定义接口，而非实现接口"**。于是有了三大解耦：
    
    - **CRI**（容器运行时接口）：解耦 Docker/runc/containerd
        
    - **CNI**（容器网络接口）：解耦 Flannel/Calico/Cilium（第 12 章）
        
    - **CSI**（容器存储接口）：解耦 EBS/Ceph/NFS
        
    
    **这三次解耦的共同哲学是：K8s 收缩为"声明式控制平面"，把"如何实现"交给生态**。这正是"不可变基础设施"这一编名的精髓——**K8s 不再是"大而全的虚拟机编排器"，而是"声明式控制的薄层"**。
    

#### 13.2.4 容器存储插件生态

今天的 CSI 生态三分天下：

**1. 云厂商托管 CSI（首选路径）**

- **AWS EBS CSI / EFS CSI**：gp3 卷可配置 IOPS，RWO 访问；EFS 提供 RWX 但延迟不适合数据库
    
- **GCE PD CSI**：pd-ssd / pd-balanced / Hyperdisk 多档性能
    
- **Azure Disk/File CSI**：Disk 为 RWO 且区域本地化，File 为 RWX
    
- **适用场景**：托管 K8s 集群（EKS/GKE/AKS），追求"零存储运维"
    

**2. 私有云/自建 CSI**

- **Rook + Ceph**：CNCF 毕业项目，把 Ceph 的块存储（RBD）、文件存储（CephFS）、对象存储（RGW）统一编排
    
    - RBD 适合 RWO，CephFS 允许 RWX
        
    - 通过 CRUSH 映射实现机架感知，3 副本机制
        
    - 运维较重，需要 SSD 日志盘、至少 3 个 Monitor
        
    
- **Longhorn**：Rancher 出品，轻量级分布式块存储
    
    - 简单部署，内置 UI、快照、备份到 S3
        
    - 仅块存储（RWO），复制在卷层进行
        
    - 适合中小集群、边缘场景
        
    
- **OpenEBS**：多引擎（Mayastor/cStor/Jiva），灵活但各引擎运维模式不同
    
- **TopoLVM**：基于 LVM 的本地存储，极致性能（无网络开销），但无数据冗余
    

**3. 对象存储与数据保护**

- **MinIO**：K8s 原生 S3 兼容对象存储，适合 AI/数据分析
    
- **Velero**：备份/容灾/迁移，保护集群对象和 PV 数据
    

|维度|AWS EBS CSI|Rook+Ceph|Longhorn|OpenEBS|
|---|---|---|---|---|
|部署环境|公有云|私有云/混合|任意 K8s|任意 K8s|
|存储类型|块（RWO）|块+文件+对象|块（RWO）|块（取决于引擎）|
|动态供给|✅|✅|✅|✅|
|RWX 支持|❌（需 EFS）|✅（CephFS）|❌|❌|
|数据冗余|云厂商托管|3 副本/EC|副本|取决于后端|
|运维复杂度|低|高|中|中|
|性能|高（云盘）|高（全闪）|中（网络复制）|中|

- **💡 我的工业选型判断**：
    
    - **托管 K8s + 无状态/标准数据库**​ → 云厂商 CSI（EBS/PD/Disk），享受零运维
        
    - **私有云 + 需要统一存储平台**​ → Rook + Ceph，一块集群提供块/文件/对象
        
    - **边缘/中小集群 + 简单块存储**​ → Longhorn，一键部署+UI 运维
        
    - **高 IOPS 本地存储**​ → TopoLVM + 节点本地 SSD
        
    - **AI/大数据分析**​ → MinIO（S3 兼容对象存储）
        
    
- **访问模式的关键认知**：
    
    - **RWO（ReadWriteOnce）**：单节点读写，云盘默认模式，适合数据库
        
    - **ROX（ReadOnlyMany）**：多节点只读，适合配置分发
        
    - **RWX（ReadWriteMany）**：多节点读写，只有文件存储（CephFS/NFS/EFS）支持，**块存储（EBS/RBD）无法实现**——这是选型时的硬性约束
        
    - **RWOP（ReadWriteOncePod）**：K8s 1.22+ 引入，单 Pod 独占，更强隔离
        
    

> **⚠️ 一个常被忽视的工程真相**：**数据库（PostgreSQL/MySQL）不能用 RWX 文件存储**。分布式文件系统（NFS/EFS/CephFS）的网络延迟和一致性模型，无法满足数据库的 IO 预期。数据库必须用 RWO 块存储（EBS/RBD/Longhorn Volume）。**这是存储选型的第一铁律**。

## 三、把全章"串起来"的三条洞见（我的原创综合）

### 洞见一：持久化存储的本质，是"用抽象对抗易逝"

容器是易逝的——Pod 可以随时重建、节点可以随时下线、调度器可以随时驱逐。**但数据必须跨越这些生生死死存活下来**。K8s 的解决方案不是"让容器不死"，而是"用抽象层把数据与容器解耦"：

- **Volume**：让 Pod 内的容器共享临时数据
    
- **PV/PVC**：让数据拥有独立于 Pod 的生命周期
    
- **StorageClass**：让存储供给自动化、声明化
    
- **CSI**：让存储后端可插拔、可演进
    

**这四次抽象，每一次都在用"声明式状态"替代"命令式操作"**——这正是 K8s 作为"声明式控制平面"哲学在存储维度的一致体现。

### 洞见二：CSI 的胜利 = "平台定义接口，生态实现接口"

CSI 战胜 In-Tree 和 FlexVolume，不是技术细节的胜负，而是架构哲学的胜利：

- **In-Tree**：K8s 什么都自己实现 → 扩展受制于 K8s 发布周期
    
- **FlexVolume**：用可执行文件解耦 → 仍有诸多限制、需节点安装
    
- **CSI**：用 gRPC 服务 + Sidecar 模式 → 存储驱动容器化、独立演进、热插拔
    

**CSI 与 CRI（容器运行时）、CNI（网络）并列，构成 K8s"三大接口解耦"**。这标志着 K8s 从一个"大而全的编排器"演变为一个"声明式控制的薄层"——**K8s 定义"想要什么"，生态决定"怎么实现"**。这正是"不可变基础设施"这一编名的精髓。

### 洞见三：存储选型 = "访问模式 × 性能 × 运维成本"的三维权衡

没有"最好的存储方案"，只有"最贴合业务需求的方案"：

- **访问模式**：数据库必须 RWO 块存储；共享文件可用 RWX 文件存储
    
- **性能需求**：高 IOPS 本地 SSD（TopoLVM）> 全闪 Ceph RBD > 云盘 EBS > 网络复制 Longhorn > NFS
    
- **运维成本**：云厂商 CSI（零运维）> Longhorn（轻运维）> Rook+Ceph（重运维）
    

**工业界的最佳实践**：

- 托管 K8s → 直接用云厂商 CSI
    
- 私有云/混合云 → Rook+Ceph 统一存储平台
    
- 边缘/中小集群 → Longhorn 轻量级块存储
    
- 跨云可移植 → Rook+Ceph 或 MinIO（对象存储）

## 四、工业落地的方法论（我的原创综合）

把本章思想落到工程实践，我提炼出 **"K8s 持久化存储五层模型"**：

**第一层：存储抽象（必选）**

- 所有持久化数据必须通过 PVC 消费，禁止 Pod 直接使用 hostPath/emptyDir 存重要数据
    
- 明确定义访问模式：数据库用 RWO，共享文件用 RWX
    
- 设置合理的 Reclaim Policy：生产数据用 Retain（防止误删），临时数据用 Delete
    

**第二层：动态供给（必选）**

- 定义 StorageClass，配置 Provisioner + 参数
    
- 云环境：使用云厂商 CSI 驱动（EBS/PD/Disk）
    
- 私有环境：Rook+Ceph 或 Longhorn
    
- 设置 `volumeBindingMode: WaitForFirstConsumer` 解决跨 AZ 调度问题
    

**第三层：CSI 驱动部署（必选）**

- 云托管 K8s：启用云厂商 CSI 插件
    
- 自建 K8s：部署 Rook 或 Longhorn 的 CSI 驱动
    
- 确保 external-provisioner、node-driver-registrar 等 Sidecar 正常运行
    

**第四层：数据保护（生产必需）**

- 定期快照：使用 CSI Snapshotter + Velero
    
- 备份到对象存储：Velero 备份到 S3/MinIO
    
- 跨 AZ 复制：Ceph 3 副本跨机架/可用区
    
- 关键业务配置跨 AZ 数据复制
    

**第五层：监控与调优（生产必需）**

- 监控 PV 容量使用率、IOPS、吞吐量
    
- 使用本地 SSD 加速 IO 密集型负载
    
- 调整文件系统参数（ext4/xfs）
    
- 拓扑感知调度：VolumeZonePredicate 保证 Pod 与 PV 同 AZ
    

**五层合力，构成"从抽象到保护的完整存储体系"**——这正是《凤凰架构》"凤凰"意象在本章的体现：**系统的可靠性不靠"容器不死"，而靠"用 PV/PVC/StorageClass/CSI 的四层抽象，让数据在容器的生生死死中，像凤凰一样浴火重生、永恒存活"**。
