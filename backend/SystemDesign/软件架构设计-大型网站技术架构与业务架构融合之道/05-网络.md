## 5.1–5.2 HTTP/1.0 → HTTP/1.1：在文本协议上打补丁

### 📖 原著脉络

HTTP/1.0 的核心问题是**短连接**——每个请求都要新建一个 TCP 连接，三次握手 + 慢启动的开销被重复支付。HTTP/1.1 给出了一系列补丁：

- **Keep-Alive（持久连接）**：默认复用 TCP 连接，`Connection: keep-alive` 管理生命周期
    
- **Chunked Transfer（分块传输）**：`Transfer-Encoding: chunked` 让服务器在未知 `Content-Length` 时也能流式返回
    
- **Pipeline（管道化）**：允许客户端在收到前一个响应之前就连续发下一个请求
    
- **断点续传**：`Range` 头支持部分内容请求
    

### 💡 我的理解与洞见

**1. HTTP/1.1 的"补丁哲学"：在不可打破的兼容性约束下做局部优化。**

HTTP/1.1 的所有改进都是**增量式**的——它不能改变 HTTP/1.0 的文本语义（否则存量互联网会崩塌）。这种"戴着镣铐跳舞"的演进策略，恰恰是工业界协议设计的常态：**向后兼容的权重，常常高于技术上的优雅**。

**2. Pipeline 为什么失败了？——队头阻塞（Head-of-Line Blocking）是第一性原理层面的硬伤。**

HTTP/1.1 管道化允许连续发请求，但**响应必须按请求顺序返回**。这意味着：如果第一个请求处理慢（比如一个耗时的数据库查询），后面所有请求的响应即使已经就绪，也**必须排队等第一个返回**。

> **洞见**：队头阻塞的本质是——**"顺序"与"并发"在单一通道上发生了冲突**。HTTP/1.1 试图用 Pipeline 在"单一 TCP 连接"这个顺序通道上强行叠加并发语义，但 TCP 本身是保证字节流有序的，于是应用层的并发诉求被传输层的顺序性"绞杀"了。
> 
> 这也是为什么工业界最终选择的不是 Pipeline，而是**"域名分片 + 多连接并行"**——既然一个通道有队头阻塞，那就开 6 个通道（浏览器对每个域名的连接数限制约为 6）。这是一种"用空间换并发"的妥协，但带来了连接数膨胀的新问题。

**3. "一来多回"问题：HTTP/1.1 的又一个隐性瓶颈。**

作者提出的"一来多回"（一个请求触发服务器多个响应，如 SSE、长轮询）在 HTTP/1.1 的"一问一答"语义下表达力不足，这也成为后来 HTTP/2 流（Stream）概念的伏笔。

> **工业视角**：今天我们在微服务中用 gRPC 做双向流、用 WebSocket 做长连接推送、用 SSE 做服务端事件推送——这些需求在 HTTP/1.1 时代都需要"hack"（如长轮询）。**这些 hack 的本质，都是在文本协议上模拟"多路复用"**。理解了这一点，你就能明白为什么 HTTP/2 的 Stream 是范式跃迁，而不只是优化。

## 5.3 HTTP/2：二进制分帧 + 多路复用 + HPACK

### 📖 原著脉络

HTTP/2（2015 年，RFC 7540）做了三件核心的事：

1. **二进制分帧（Binary Framing）**：把所有消息拆成二进制帧（HEADERS 帧、DATA 帧等），不再是人类可读的文本
    
2. **多路复用（Multiplexing）**：在单一 TCP 连接上并行交错传输多个流（Stream），每个流有唯一 ID
    
3. **头部压缩（HPACK）**：用静态表 + 动态表 + Huffman 编码，把每次重复发送的头部压成索引号
    

### 💡 我的理解与洞见

**1. HTTP/2 的真正革命：把"通道"和"流"分离。**

HTTP/1.1 的一个 TCP 连接 = 一个请求/响应序列；HTTP/2 的一个 TCP 连接 = **一个传输通道，N 个逻辑流**。这是"通道"与"流"的第一次清晰分离。

> **洞见（第一性原理）**：HTTP/2 解决队头阻塞的思路是——**在单一通道上构造多个逻辑子通道（Stream），让子通道之间互不阻塞**。这本质上是操作系统"虚拟内存"思想的协议层投影：正如虚拟内存让每个进程都以为自己独占内存，HTTP/2 的 Stream 让每个请求都以为自己独占连接。

**2. HPACK 的智慧：用"状态"换"带宽"。**

HTTP/1.x 每次请求都重复发送 `Cookie`、`User-Agent`、`Accept` 等几乎不变的头部，是纯粹的带宽浪费。HPACK 的做法是：

- **静态表**：把常用头部（`GET`、`POST`、`:method`、`:path` 等）硬编码为索引号
    
- **动态表**：把本次连接中出现的头部字段加入动态表，后续用索引引用
    
- **Huffman 编码**：对字符串字面量再做一次压缩
    

> **洞见**：HPACK 揭示了协议设计的一条普适原则——**"冗余即机会"**。任何在多次交互中重复出现的信息，都值得被"提升"为状态（无论是客户端的表、还是服务端的缓存）。这条原则同样适用于 RPC 框架（如 gRPC 的 ProtoBuf 字段编号）、数据库协议（预处理语句）、甚至 CPU 的流水线设计（指令缓存）。

**3. HTTP/2 的"阿喀琉斯之踵"：TCP 层的队头阻塞并未解决。**

这是一个**关键认知**，很多读书笔记会忽略：

> HTTP/2 解决了**应用层**的队头阻塞，但**TCP 层**的队头阻塞依然存在。如果某个 Stream 的 TCP 包丢失，整个 TCP 连接都要等这个包重传成功，连接上**所有 Stream 都被阻塞**。

这在低丢包率的有线网络里问题不大，但在**移动网络（WiFi↔4G 切换、地铁、电梯）**这种丢包率较高的弱网环境下，HTTP/2 的多路复用优势会被 TCP 的队头阻塞完全抵消，甚至不如 HTTP/1.1 开多个独立 TCP 连接（一个连接丢包不影响其他连接）。

> **工业数据**：Google 测试显示，HTTP/3 在弱网环境下比 HTTP/2 降低 30%+ 的延迟。**这正是 HTTP/3/QUIC 诞生的根本动机**——不是 HTTP/2 设计得不好，而是 TCP 这个传输层"底盘"在弱网下的局限性，已经无法通过应用层补丁来弥补。

**4. 服务器推送（Server Push）为何逐渐淡出？**

HTTP/2 的 Server Push 允许服务器主动推送客户端可能需要的资源（如 HTML 引用的 CSS/JS）。但实践中问题很多：推送了客户端已经缓存的资源、推送时机难以精确判断、与 HTTP 缓存语义冲突。**现代前端构建工具（如 Vite）反而鼓励"拆小文件"+ HTTP/2 多路复用**，让客户端自己去并发请求——这比服务器"猜你需要什么"更精准。

> **洞见**：Server Push 的衰落印证了一个架构原则——**"服务端预测"往往不如"客户端按需请求 + 协议层并发"**。中心化的智能预测听起来美好，但分布式的按需拉取在绝大多数场景下更鲁棒。这条原则在微服务架构中同样适用：与其让 API Gateway 做复杂的编排预测，不如让客户端/BFF 层按需并发调用。

## 5.4–5.5 SSL/TLS 与 HTTPS：在不信任的网络上建立信任

### 📖 原著脉络

作者从背景出发，依次讲了：

- **对称加密的问题**：密钥如何安全分发？
    
- **双向非对称加密**：用公钥加密、私钥解密，解决密钥分发，但无法确认对方身份
    
- **单向非对称加密**：客户端用服务器公钥加密，只有服务器能解密
    
- **中间人攻击（MITM）**：攻击者截获并替换公钥
    
- **数字证书与 CA**：用可信第三方的私钥对服务器公钥签名，证明"这个公钥确实属于 example.com"
    
- **根证书与信任链**：根 CA → 中间 CA → 终端证书的层级信任传递
    
- **SSL/TLS 四次握手**：以 TLS 1.2 为典型
    

### 🔍 网络佐证：TLS 1.3 的现代握手

阿里云开发者社区的图解清晰地展示了现代 TLS 1.3 的握手流程：

1. **ClientHello**：客户端发送随机数 A + 支持的密码套件 + 客户端临时公钥（ECDHE）
    
2. **ServerHello**：服务器选定套件，返回随机数 B + 服务器临时公钥
    
3. **证书链 + 证书校验**：服务器发送证书链，客户端逐级验证签名、有效期、域名匹配、吊销状态
    
4. **密钥协商**：双方用 ECDHE 算法计算共享密钥，结合随机数派生出对称的会话密钥
    
5. **Finished**：双方互发握手消息的 HMAC 摘要，确认握手未被篡改
    

TLS 1.3 相比 TLS 1.2 的关键优化：

|维度|TLS 1.2|TLS 1.3|
|---|---|---|
|握手延迟|2-RTT|**1-RTT**（0-RTT 可选）|
|密钥交换|RSA/静态 DH|**仅 ECDHE**（强制前向保密）|
|加密算法|支持弱算法（RC4 等）|**仅强算法**（AES-GCM 等）|
|握手数据量|5-7 KB|**2-3 KB**​|

### 💡 我的理解与洞见

**1. TLS 的本质：用"非对称加密"解决"对称密钥的安全分发"，用"证书链"解决"公钥的身份归属"。**

这两句话是理解整个 TLS 的钥匙。很多人背"TLS 握手流程"背得很熟，但说不清**为什么需要两套加密体系**。答案就在上面——

- **对称加密**快但不能安全分发密钥；
    
- **非对称加密**能安全分发但太慢，不适合加密大量数据；
    
- 所以现实方案是：**用非对称加密安全地协商出一个对称密钥，然后用对称密钥加密后续所有数据**。这就是 TLS 的"混合加密"思想。
    

**2. 证书信任链的精妙：用"少数根"信任"多数叶"。**

互联网上有数以亿计的网站，不可能每个都让用户手动信任。CA 体系的智慧在于：

```
根 CA（自签名，私钥离线保存，预装于操作系统/浏览器）
  ↓ 用根 CA 私钥签名
中间 CA（由根 CA 授权，代为签发终端证书）
  ↓ 用中间 CA 私钥签名
终端证书（绑定 example.com 等具体域名）
```

客户端验证时**自底向上**追溯：用中间 CA 的公钥验证终端证书签名 → 用根 CA 的公钥验证中间证书签名 → 追溯到本地预装的根证书 → 信任链成立。

> **洞见**：证书链的层级设计体现了经典的**"信任委托"**模式——根 CA 绝不下场直接签终端证书（避免私钥泄露的灾难性后果），而是把权力"委托"给中间 CA。这跟现实社会的公证体系、区块链的共识节点选举、甚至 Kubernetes 的 RBAC 角色继承，是同一个"信任分层"思想的不同投影。
> 
> **架构启示**：在设计分布式系统的信任体系时（如 Service Mesh 中的 mTLS、零信任架构），**"根证书离线 + 中间证书代理签发"**​ 是当前工业界验证过的最佳实践。Istio、Linkerd 等服务网格的证书体系，本质就是这套思想的落地。

**3. 前向保密（Forward Secrecy）：TLS 1.3 的强制要求，架构师必须理解的安全底线。**

TLS 1.2 支持 RSA 密钥交换——服务器证书里的 RSA 公钥直接加密预主密钥。问题在于：**如果服务器的 RSA 私钥日后泄露，攻击者就能解密之前截获的所有会话**。

TLS 1.3 强制使用 **ECDHE**（椭圆曲线迪菲-赫尔曼临时密钥交换）——每次握手都生成临时的密钥对，会话结束后临时私钥即丢弃。**即使服务器长期私钥泄露，历史会话也无法被解密**。

> **工业视角**：今天部署 HTTPS，**必须启用 TLS 1.3，禁用 TLS 1.2 及以下的 RSA 密钥交换**。这是金融、电商、政务系统的安全合规底线。Nginx 配置示例：`ssl_protocols TLSv1.3;`，并配合 `ssl_ecdh_curve X25519:prime256v1;` 使用现代椭圆曲线。

**4. 0-RTT 的双刃剑：性能与重放攻击的权衡。**

TLS 1.3 的 0-RTT 模式允许客户端在握手的同时就发送加密的应用数据，把延迟压到极致。但代价是：

> **0-RTT 数据存在重放攻击风险**——攻击者截获 0-RTT 数据包后，可以原样重放到服务器（如重放一笔支付请求）。

因此工业界的做法是：**仅对幂等操作（GET 请求）启用 0-RTT**，对 POST/PUT/DELETE 等状态变更操作坚持 1-RTT。这是"性能 vs 安全"权衡的经典案例——**不是所有请求都配得上 0-RTT 的性能红利**。

**5. HTTPS 的"隐性成本"：架构师必须算的账。**

很多人以为"上了 HTTPS 就安全了"，但实际部署时有一笔账要算：

- **握手延迟**：首次连接 1-RTT（TLS 1.3）+ TCP 三次握手 1-RTT = 至少 2-RTT 才能开始传数据
    
- **证书管理**：90 天有效期的 Let's Encrypt 证书需要自动化续期（Cert-Manager、acme.sh）
    
- **CPU 开销**：ECDHE 密钥交换、AES-GCM 对称加密都有计算成本，高并发下需要 TLS 卸载（如 Nginx 做 TLS termination，或用 Intel QAT 硬件加速）
    
- **0-RTT 重放风险**：如前所述，需要业务层配合
    

> **洞见**：HTTPS 不是"免费的安全"，而是一组**需要主动管理的工程权衡**。现代工业界的做法是——**TLS termination 放在边缘（CDN/负载均衡器），内部服务间用 mTLS（Service Mesh）或明文（可信网络）**。这既享受了边缘 HTTPS 的安全红利，又避免了内部海量短连接 TLS 握手的性能损耗。

## 5.6 TCP/UDP：可靠与不可靠的辩证

### 📖 原著脉络

- **可靠与不可靠**：TCP 提供可靠传输（序号、确认、重传、流量控制、拥塞控制），UDP 提供不可靠但极简的传输
    
- **TCP 的"假"连接（状态机）**：TCP 是"面向连接"的，但这个连接是**逻辑上的**——本质是两端维护的状态机，而非物理电路
    
- **三次握手与"两军问题"**：用三次握手建立双向可信的连接
    
- **四次挥手**：全双工特性的必然结果
    

### 🔍 网络佐证

**三次握手（SYN → SYN+ACK → ACK）**：

1. 客户端发 SYN（seq=x）——证明客户端发送能力正常
    
2. 服务器回 SYN+ACK（seq=y, ack=x+1）——证明服务器收发能力正常
    
3. 客户端发 ACK（seq=x+1, ack=y+1）——证明客户端接收能力正常
    

**为什么不是两次？**​ 如果只有两次握手，服务器无法确认客户端是否收到了自己的响应。假设一个延迟的旧 SYN 报文到达服务器，服务器会误以为是新连接请求并回复 SYN+ACK、分配资源进入连接状态；但客户端实际上并未请求，不会发送数据——**服务器资源被无效占用**。

**两军问题（Two Generals Problem）**：在不可靠网络上，不存在"绝对可靠"的协议——无论多少次握手，理论上都无法 100% 确认对方收到了最后一条消息。TCP 选择**三次**是因为：三次已经达到"非常可观的可信率"，再增加握手次数，可靠性提升边际效益骤减，而延迟和开销线性增加——这是对数对曲线式的权衡。

**四次挥手**：TCP 是全双工的，每个方向的数据流必须独立关闭。被动方收到 FIN 后，可能还有数据要发送，所以**不能把 ACK 和自己的 FIN 合并发送**（这与握手时 SYN+ACK 可以合并形成对比）。因此挥手必须是 4 次：FIN → ACK → FIN → ACK。最后的 TIME_WAIT 状态持续 2MSL，确保最后一个 ACK 可达，并让网络中残留的旧报文自然消亡。

### 💡 我的理解与洞见

**1. TCP 三次握手的"第一性原理"：用最小的往返次数，确认双向的收发能力 + 同步初始序号。**

很多人背"三次握手防止死锁"，但更深层的洞察是：

> **三次是"可靠性/开销"曲线上的最优拐点。**​ 一次不够（单向），两次不够（服务器无法确认客户端接收能力），三次刚好（双向确认完成），四次及以上边际效益骤降。

这再次印证了第2章"道术合一"的思想——具体的握手次数是"术"，**"在不可靠网络上用最小代价建立双向可信"才是"道"**。QUIC 后来把握手压缩到 1-RTT（首次）/0-RTT（恢复），并不是推翻了这个道，而是在道的基础上引入了 TLS 1.3 的密钥协商机制，把"传输层握手"和"加密层握手"合并了——这是另一层次的优化。

**2. TCP "面向连接"的真相：连接是"状态"，不是"电路"。**

作者特意强调 TCP 是"假"连接，这个点非常犀利。很多初学者把 TCP 连接想象成一根"管子"，实际上它只是**两端各自维护的一组状态变量**（序号、窗口、缓冲区）。中间路由器对 TCP 连接一无所知，它只看到一个个独立的 IP 包。

> **洞见**：理解 TCP 连接是"状态"而非"电路"，是理解现代网络架构的关键。正因为连接是状态——
> 
> - **四元组（源IP、源端口、目的IP、目的端口）**才能唯一标识一个连接
>     
> - **NAT 设备**才能在公网上让多台内网机器共享一个公网 IP（通过改写四元组 + 维护映射表）
>     
> - **QUIC 的连接迁移**才能用 Connection ID 替代四元组，实现 WiFi↔4G 无缝切换（见 5.7）
>     

**3. UDP 的"不可靠"恰恰是其优势。**

TCP 的可靠性是有代价的：三次握手延迟、重传导致的队头阻塞、拥塞控制导致的吞吐量受限。在某些场景下，"不可靠"反而是更好的选择：

- **实时音视频**（WebRTC）：丢一个包重传过来已经晚了，不如直接丢帧
    
- **DNS 查询**：一个 512 字节的查询，TCP 三次握手的开销比数据本身还大
    
- **QUIC/HTTP/3**：在 UDP 之上自己实现"选择性可靠"——需要可靠的用可靠流，不需要可靠的直接发
    

> **工业视角**：现代网络编程的趋势是**"TCP 做兜底，UDP 做优化"**。QUIC 就是在 UDP 上重新实现了 TCP 的可靠性精华（序号、重传、拥塞控制），同时规避了 TCP 的队头阻塞和握手延迟。这预示着——**未来越来越多的应用层协议会选择 UDP 作为传输底座**。

## 5.7 QUIC/HTTP/3：下一代传输协议的范式跃迁

### 📖 原著脉络

- **不丢包（Raid5 算法和 Raid6 算法）**：QUIC 在 UDP 之上实现可靠传输，借鉴 RAID 的思想做冗余与纠错
    
- **更少的 RTT**：QUIC 握手合并了传输层与加密层，首次连接 1-RTT，恢复连接 0-RTT
    
- **连接迁移**：用 Connection ID 替代四元组，WiFi↔4G 切换不断连
    

### 🔍 网络佐证

HTTP/3 的本质是 HTTP-over-QUIC：

**1. 更少的 RTT**：

- QUIC 内部集成了 TLS 1.3，握手时**同时**完成传输层连接建立与加密密钥协商
    
- 首次连接：1-RTT
    
- 会话恢复：0-RTT（客户端缓存服务器公钥，首包即发送加密应用数据）
    

**2. 彻底解决队头阻塞**：

- HTTP/2 的 TCP 层队头阻塞：一个包丢失 → 整个 TCP 连接等待重传 → 所有 Stream 阻塞
    
- QUIC 的每个 Stream 有独立的包编号和重传逻辑：**单个 Stream 丢包只影响自己，其他 Stream 正常处理**
    

**3. 连接迁移（Connection Migration）**：

- TCP 用四元组标识连接，IP 变化 → 连接必断
    
- QUIC 用 64 位随机 Connection ID 标识连接，IP 变化时只需在新路径上发送带有相同 ID 的数据包 → 连接无缝迁移
    
- **Google 实测：连接迁移成功率接近 100%**
    

**4. 灵活的拥塞控制**：

- TCP 的拥塞控制实现在内核里，更新算法需要升级操作系统
    
- QUIC 的拥塞控制在用户态，可以像更新 App 一样快速迭代
    

**工业部署现状**：

- Nginx 1.25+ 支持 HTTP/3
    
- Cloudflare 全量支持
    
- Facebook 75%+ 流量使用 HTTP/3
    
- 阿里巴巴双十一大规模应用
    
- Google 测试：弱网下比 HTTP/2 降低 30%+ 延迟
    

### 💡 我的理解与洞见

**1. QUIC 的本质：把 TCP 从内核"解救"到用户态。**

这是 QUIC 最深刻的架构意义。TCP 实现在内核里，意味着：

> **任何 TCP 协议的改进（如修复队头阻塞、优化拥塞控制），都需要操作系统内核升级——这个周期以"年"计。**

而 QUIC 跑在 UDP 之上、实现在用户态，**协议迭代速度从"内核发布周期"缩短到"应用发布周期"**。这看似是个实现细节，实则是**软件架构演进速度的范式跃迁**——把"慢变的底座"用"快变的抽象"包裹起来，是计算机工业反复验证的真理（正如虚拟机把硬件抽象出来、容器把操作系统抽象出来）。

**2. QUIC 连接迁移：移动互联时代的"杀手锏"。**

这是 QUIC 最具商业价值的特性。在 5G/WiFi 6 时代，移动设备的网络切换是高频事件（电梯、地铁、高铁、WiFi↔4G）。传统 TCP 下，每一次 IP 变化都意味着连接重建（1-2 RTT 的闪断），对实时音视频、在线游戏、移动支付的体验是致命的。

> **洞见**：Connection ID 替代四元组，本质上是**把"连接的身份"与"连接的路由"解耦**。这跟微服务架构中"服务标识（Service Name）与实例地址（IP:Port）解耦"是同一个思想——Kubernetes 的 Service、Consul 的服务发现、Istio 的 Virtual Service，都是用稳定的逻辑标识遮蔽不稳定的物理地址。**QUIC 把这个思想做到了传输层**。

**3. HTTP 协议选型的决策树（工业实践指南）。**

基于以上分析，给出架构师视角的选型建议：

```
是否需要支持 IE11 / 老旧系统？
├─ 是 → HTTP/1.1 + 域名分片（≤6 个）+ 资源打包合并
└─ 否 → 是否主要用户为移动端/弱网？
        ├─ 是 → 优先 HTTP/3 (QUIC)，降级到 HTTP/2
        └─ 否 → HTTP/2 足够
                └─ 关注 TCP 队头阻塞（丢包率 < 0.5% 时可忽略）
```

> **现实约束**：HTTP/3 基于 UDP，企业防火墙/运营商可能对 UDP 做 QoS 降速甚至拦截。因此**工业部署的最佳实践是"HTTP/3 为主、HTTP/2 兜底"**——客户端优先尝试 HTTP/3，失败则透明降级到 HTTP/2。Cloudflare、Nginx 1.25+ 都已支持这种 Alt-Svc 降级机制。

**4. QUIC 的"RAID 思想"：用冗余对抗丢包。**

作者在 5.7.1 提到 QUIC 借鉴 RAID 5/6 算法，这是一个极有洞察力的视角。RAID 5 用奇偶校验、RAID 6 用双重校验，允许 1-2 块磁盘损坏而不丢数据。QUIC 在 UDP 之上实现可靠传输时，也采用了类似的**前向纠错（FEC）**思想——发送数据包时附带冗余校验包，接收方即使丢失个别包，也能通过校验包恢复数据，避免重传的 RTT 惩罚。

> **洞见**：这是"存储领域的冗余思想"向"网络领域的迁移"。**跨域的概念迁移，是架构师最高级的能力之一**——能从 RAID 想到 QUIC 的 FEC，从操作系统的虚拟内存想到 HTTP/2 的 Stream，从数据库的 WAL 想到消息队列的 Commit Log（Kafka 正是这么设计的）。**余春龙在本书中反复强调的"业务架构与技术架构融合"，本质上就是这种跨域概念迁移的能力。**

## 🧭 全章串联：一条主线穿起七个小节

回看第5章的全部内容，它们围绕一条主线展开：

```
HTTP/1.0/1.1 ──(补丁式优化: Keep-Alive/Pipeline/Chunked)──┐
                                                          │
HTTP/2 ────────(范式跃迁: 二进制分帧/多路复用/HPACK)─────┤
                                                          ├── 应用层：减少往返、消除冗余、隔离故障
QUIC/HTTP/3 ───(底层重构: UDP+用户态可靠传输/0-RTT/连接迁移)┘

TLS/HTTPS ─────(混合加密+证书链+前向保密)─────────────────── 安全层：在不信任的网络上建立信任

TCP/UDP ───────(三次握手/四次挥手/可靠vs不可靠)───────────── 传输层：在不可靠的物理网络上构建可靠传输
```

**这条主线的底层逻辑，正是第2章"道术合一"在网络协议的具体展开：**

|第一性原理|HTTP/1.1|HTTP/2|HTTP/3/QUIC|
|---|---|---|---|
|**减少 RTT**​|Keep-Alive 复用连接|多路复用减少连接数|1-RTT/0-RTT 握手|
|**消除冗余**​|-|HPACK 头部压缩|头部压缩 + QPACK|
|**隔离故障**​|域名分片（多连接）|Stream 级隔离（但受限于 TCP）|Stream 级完全隔离|
|**确认身份/可靠**​|-|TLS（依赖 TCP）|内置 TLS 1.3 + Connection ID|

> **谁只背得下"HTTP/2 比 HTTP/1.1 快""HTTP/3 用 QUIC"——那是停留在术；谁能说出"协议演进的底层逻辑，是在 RTT、冗余、故障隔离、安全信任这四个维度上持续做权衡"——谁才真正读通了本章的道。**
