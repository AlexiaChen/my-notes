
# 《软件架构设计》读书笔记 · 第8章 高并发问题

> 第4-7章把架构师的"底层功底"依次夯实——操作系统管本机 I/O、网络管跨机传输、数据库管持久化与一致性、框架/中间件管复杂度封装。**从第8章起，本书进入"技术架构之道"**，开始回答架构师每天都要面对的真问题："高并发来了，怎么办？"
> 
> 余春龙在这一章的处理非常高明——他没有罗列"加缓存、加机器、加 CDN"这种术级清单，而是**先把高并发问题按"读/写"这两个最根本的操作分类，再从每一类问题的本质出发推导策略**。这种"从第一性原理出发"的写法，正是本章最值得深挖的宝藏。
> 
> 本章的第一性原理主线可以提炼为一句话：
> 
> **高并发的本质，是把"读"和"写"这两类操作的压力，用一切可能的手段（缓存、并行、预处理、分片、异步、批量）降到系统可承受的阈值之下。读优化的核心是"让数据离消费者更近"，写优化的核心是"把写入的压力拆开、推迟、合并"。**

## 8.1 问题分类：先识别"敌人"的长相

### 📖 原著脉络

作者把高并发系统分为三类，因为**不同类型的系统，应对策略截然不同**：

- **侧重高并发读**：搜索引擎、电商商品搜索、商品描述/图片/价格——读的量级、频率、响应时间要求都极高
    
- **侧重高并发写**：广告扣费系统——用户的每次浏览/点击都要实时扣减广告主余额，写密集且要求实时
    
- **读写都高**：电商库存/秒杀、支付/红包、IM/微博/朋友圈——读和写都面临巨大压力
    

### 💡 我的理解与洞见

**1. 分类的本质：识别"瓶颈在哪一侧"。**

很多架构师一上来就"加缓存、上 MQ、分库分表"全套招呼，这是懒政。**高并发问题的第一性原理是——先问"瓶颈在读还是在写"**，因为二者的优化方向几乎是镜像的：

|维度|高并发读|高并发写|
|---|---|---|
|核心矛盾|数据离消费者太远|写入压力超过单机承载|
|优化方向|让数据**靠近**消费者|把压力**拆开/推迟/合并**​|
|典型策略|缓存、并发读、重写轻读|分片、异步、批量|
|一致性代价|缓存与 DB 的一致性|分布式事务/最终一致性|

> **洞见**：分类不是学术游戏，而是**决策分支的起点**。识别错了类型，策略就会南辕北辙——对一个写密集系统猛加 Redis 缓存，不仅没用，还引入了缓存一致性这个新包袱。

**2. "读写都高"的系统为什么最难？——因为读优化和写优化经常打架。**

秒杀系统就是典型案例：写侧要"扣库存"（高并发写），读侧要"查商品详情/库存余量"（高并发读）。**缓存对读是福音，对写却是负担**——每次写都要同步更新/失效缓存，引入了一致性问题。

> **工业解法**：秒杀这类极端场景，工业界的解法是"**写用 Redis 原子递减 + 异步落库**"——Redis 单线程天然串行化写操作，DECR 命令原子扣减库存，异步 MQ 把扣减结果落库。读商品详情走 CDN + Redis 多级缓存。**这就是"读写都用最适合的技术分别处理"的 CQRS 思想在秒杀场景的极致应用**。

## 8.2 高并发读：让数据离消费者更近

### 📖 原著脉络

作者给出三个递进策略：

**策略1：加缓存**——本质是"空间换时间"

- 本地缓存 / Memcached / Redis 集中式缓存
    
- MySQL Master/Slave（用 Slave 分担读）
    
- CDN 静态文件加速（动静分离）
    
- 必须面对缓存雪崩、缓存穿透、缓存击穿三大问题
    

**策略2：并发读**——串行改并行

- 异步 RPC：无依赖的多个调用并行执行，耗时从 T1+T2+T3 降为 Max(T1,T2,T3)
    
- 冗余请求（对冲请求）：Google 做法，先发一个请求，超时未响应则向多台服务器发同样请求，取最快响应
    

**策略3：重写轻读**——计算从读端移到写端

- 微博 Feeds 流：写时把微博推送到粉丝的收件箱（写扩散），读时直接读自己的收件箱
    
- 推拉结合：粉丝少的用户用推，粉丝多的用户（大 V）用拉，读时聚合
    
- 宽表 / 搜索引擎：提前把多表 join 的结果做成宽表或 ES 文档
    

**总结：CQRS 架构**——读写分离，读写两侧用不同的数据结构

### 💡 我的理解与洞见（本章重点）

**1. 三个策略的统一原理：让"慢路径"变成"快路径"。**

这是我对高并发读的第一性原理抽象。所谓"慢路径"，是指：

- 跨网络访问 DB（网络 I/O + 磁盘 I/O）
    
- 多表 Join + 聚合计算（CPU 密集）
    
- 串行调用多个服务（延迟累加）
    

三个策略分别从不同角度消除慢路径：

|策略|消除慢路径的方式|第一性原理|
|---|---|---|
|**加缓存**​|把数据复制到离消费者更近的地方（本地内存/Redis/CDN）|**空间换时间**​|
|**并发读**​|把串行慢路径改成并行慢路径|**用并行掩盖延迟**​|
|**重写轻读**​|把"读时的计算"提前到"写时完成"，读时直接取结果|**计算时间位移**（写时多干，读时少干）|

> **洞见**：这三种策略不是并列关系，而是**递进关系**——能用缓存解决的，绝不用并发读；能用重写轻读的，绝不在读时实时聚合。**越往前，性价比越高；越往后，代价越大。**​ 这是架构师选型的第一性原则。

**2. 缓存：最锋利的剑，也是最容易伤自己的剑。**

缓存是"空间换时间"最直白的实现，但它引入了三个经典问题：

- **缓存雪崩**：大量 key 同时过期 → 所有请求穿透到 DB → DB 被打垮。**解法**：TTL 加随机抖动，避免同时失效
    
- **缓存穿透**：查询不存在的数据 → 缓存和 DB 都没有 → 每次都打 DB。**解法**：布隆过滤器拦截非法 key，或缓存空值（短 TTL）
    
- **缓存击穿**：热点 key 过期瞬间 → 大量请求同时穿透到 DB。**解法**：互斥锁（只有一个请求去加载，其余等待）+ 逻辑过期（返回旧值+异步刷新）
    

> **工业深度实践**：对于"缓存击穿"这种单热点 key 失效引发的惊群效应，现代工业界还有更精巧的解法：
> 
> - **请求合并（Request Coalescing）**：多个线程同时发现缓存 miss 时，只有一个去加载 DB，其余等待结果
>     
> - **提前刷新（Probabilistic Early Expiration）**：在 key 即将过期前，以小概率触发异步刷新，把刷新压力平摊
>     
> - **Stale-While-Revalidate**：直接返回旧值，后台异步刷新，用户无感
>     

**3. 并发读：对冲请求是降低长尾延迟的利器。**

作者提到的 Google "冗余请求"策略，是一个被严重低估的高并发读优化：

> 分布式系统中，单节点延迟率可能只有 1%，但当请求涉及 100 个节点时，整体延迟率高达 63.4%（1 - 0.99^100）。Google 的对冲请求方案：**先发一个请求，等待内部服务 95% 请求的响应时间，未收到响应则向另一台服务器发同样请求，取最先返回的结果**。仅用 2% 额外请求量，就把 99.9% 请求的响应时间从 1800ms 降低到 74ms。

> **洞见**：这是对"尾延迟（Tail Latency）"的精准打击。平均值好看没用，**P99/P999 才是用户体验的真实映射**——一个 1000 次请求中 1 次慢到 2 秒的系统，远比 1000 次都稳定在 200ms 的系统体验差。
> 
> **工业应用**：对冲请求在 Google 的 Stuppa、Facebook 的 「Hedged Request」、微服务框架的 Retry 中都广泛应用。它揭示了一条普适原则——**在分布式系统中，用少量冗余成本换取长尾延迟的大幅降低，往往比优化单请求性能更划算**。

**4. 重写轻读：CQRS 思想的朴素表达。**

微博 Feeds 流的例子是重写轻读的教科书案例：

- **原始方案**：读时实时查询"关注列表" + "每人发的微博" + 按时间排序聚合——关注 500 人就要查 500 次 + 内存排序，高并发下必死
    
- **重写轻读**：每个用户有一个"收件箱"，别人发微博时异步推送到粉丝收件箱（写扩散），读时直接读自己的收件箱
    
- **推拉结合**：大 V（粉丝百万）不发写扩散（否则写爆），改用拉；普通用户用推；读时聚合推和拉的结果
    

> **洞见**：重写轻读的本质是**"计算时间位移"**——把计算成本从"每次读"转移到"每次写"，并用**异步化**解耦写扩散的耗时。这跟第6章讲的数据仓库"物化视图"、第7章讲的 CQRS 是**同一个思想**：
> 
> - 物化视图：提前计算聚合结果，查询直接命中
>     
> - CQRS：写模型保持规范化和强一致，读模型通过事件/CDC 投影成反范式宽表
>     
> - 重写轻读：写时扩散，读时直接取
>     
> 
> **三者是同一个第一性原理在不同层级的应用：用"写时的计算成本"换"读时的极致性能"。**

**5. CQRS：高并发读的集大成架构。**

作者把三个策略总结为 CQRS（Command Query Responsibility Segregation），但 CQRS 远不止"读写分离"：

|维度|简单读写分离|完整 CQRS|
|---|---|---|
|存储|同库（主从）|异库异构|
|数据模型|同一套表结构|写模型规范化 + 读模型反范式化|
|同步机制|主从复制（Binlog）|事件驱动 / CDC / MQ|
|一致性|准实时（秒级延迟）|最终一致性|
|适用场景|中小型系统|大型高并发系统|

**工业案例**：淘宝订单搜索、京东订单中心、美团交易系统都采用完整 CQRS——写入 MySQL（命令侧，保证 ACID），通过 Binlog/Canal 同步到 Elasticsearch（查询侧，支持多维搜索）。

> **洞见**：CQRS 的真正威力，是**让"写"和"读"可以按照各自的访问模式独立优化**——写侧用规范化模型保证一致性，读侧用反范式宽表/ES/Redis 保证查询性能。**这是"业务架构与技术架构融合"的典范**：业务上"下单"和"查单"是两个不同的用例，技术上就用两套不同的存储模型来服务。

## 8.3 高并发写：把写入压力拆开、推迟、合并

### 📖 原著脉络

作者给出五个递进策略：

1. **数据分片**：把数据分成 N 份并行处理——分库分表、ConcurrentHashMap、Kafka Partition、ES 分布式索引
    
2. **任务分片**：对处理程序本身分片——Map/Reduce 思想，把大任务拆成小任务并行执行
    
3. **异步化**：接口异步、JDK 异步、业务异步——短信验证码丢进 MQ 异步发送，应用服务器立即返回
    
4. **批量**：汇总多次写操作为一次批量——MySQL 批量插入、Kafka 批量写入
    
5. **串行化 + 多进程单线程 + 异步 I/O**：Redis 模式——多进程避免锁竞争，单线程避免上下文切换，异步 I/O 避免阻塞
    

### 💡 我的理解与洞见（本章另一重点）

**1. 五个策略的统一原理：降低"单次写入的有效开销"。**

这是我对高并发写的第一性原理抽象：

|策略|降低开销的方式|第一性原理|
|---|---|---|
|**数据分片**​|把单机写入压力分摊到多机|**分而治之**（Divide & Conquer）|
|**任务分片**​|把单任务拆成多子任务并行|**分而治之**（在程序层）|
|**异步化**​|把同步等待变成异步处理|**解耦时间依赖**​|
|**批量**​|把 N 次小写入合并为 1 次大写入|**用顺序写替代随机写**（呼应第6章 WAL）|
|**串行化+多进程单线程+异步 I/O**​|消除锁竞争和上下文切换|**消除并发开销本身**​|

> **洞见**：五个策略不是平等的，而是**按"代价从小到大"排列的**——能用批量的绝不用异步化，能用异步化的绝不用分片，能分片的绝不用重构为串行化模型。**越往后的策略，架构改造代价越大，但收益也越根本。**

**2. 批量：被严重低估的性能利器。**

批量写入是高并发写里**性价比最高**的策略，因为它的本质是"用顺序写替代随机写"——这正是第6章 Redo Log WAL 思想在工业界的再次体现。

工业数据：

- 单线程单条 INSERT：QPS ≈ 2000
    
- 16 线程并发 + 批量写入（rewriteBatchedStatements=true）：QPS 提升至 **3.2 万**，延迟降低 80%
    
- 批量大小为 100 时，吞吐量可达单条的 **8 倍以上**
    

> **洞见**：Kafka 为什么写入速度那么快？三个原因——Partition 分片、磁盘顺序写入、**批量**。其中"批量"是关键——Producer 端累积一批消息一次性发给 Broker，Broker 端累积一批消息一次性落盘。**批量的本质，是把"网络 I/O 的固定开销"和"磁盘 I/O 的固定开销"用"聚合"摊薄到每条消息上。**
> 
> 这跟第4章"缓冲 I/O"是同一个思想：缓冲 I/O 用缓冲区聚合多次小 I/O 为少量大 I/O，批量写用批量聚合多次小写为少量大写。**跨越操作系统、数据库、消息队列、分布式系统，顶级的写优化都在做同一件事——聚合降次。**

**3. 异步化：不仅是"解耦"，更是"削峰"。**

异步化的工业范本——短信验证码：

- **同步做法**：应用服务器调用短信平台 API（耗时 2-3 秒）→ 阻塞等待 → 返回用户。并发高时 Tomcat 线程池耗尽，整个服务雪崩
    
- **异步做法**：应用服务器把"发短信"请求丢进 MQ → 立即返回 → 后台 Consumer 慢慢消费，调用短信平台
    

> **洞见**：异步化的真正价值不只是"解耦"，更是**"削峰"**——把瞬时高峰的写入请求，变成 MQ 中平滑消费的任务流。MQ 充当了"蓄水池"：洪水来时先蓄住，下游按自己的节奏处理。
> 
> 这正是秒杀、抢购、红包等场景的核心架构：**前端请求 → 校验 → 写 MQ → 立即返回"排队中" → 异步Worker 消费 MQ 落库**。用户感知的是"已提交"，系统获得的是"流量整形"。

**4. Redis 模式：串行化 + 多进程单线程 + 异步 I/O 的哲学。**

作者提到的第五个策略，是 Redis 的核心架构哲学，也是最反直觉的一个：

- **多进程**：启动多个 Redis 实例（或利用多核），避免单进程无法利用多核
    
- **单线程**：每个 Redis 实例内部单线程处理命令——**消除锁竞争和上下文切换**
    
- **异步 I/O**：用 epoll 等非阻塞 I/O 处理网络读写——**避免 I/O 阻塞**
    

> **洞见**：这个模式的精髓是——**用"单线程串行化"消除并发开销（锁、上下文切换），用"多进程"利用多核，用"异步 I/O"避免阻塞**。它揭示了一个反直觉的真理：
> 
> **有时候，"串行化"比"并发化"性能更高。**
> 
> 为什么？因为并发化的隐性成本是锁竞争、上下文切换、缓存一致性流量——当这些成本超过并发带来的收益时，单线程反而更快。Redis 的单线程模型能够轻松支撑 10万+ QPS，正是因为避免了这些并发开销。
> 
> **工业延伸**：这个思想在现代系统中广泛存在——
> 
> - Node.js 的事件循环（单线程 + 异步 I/O）
>     
> - Nginx 的 Worker 模型（多进程 + 单线程事件驱动）
>     
> - Go 的 GMP（协程轻量级，上下文切换成本极低）
>     
> - Actor 模型（Erlang/Elixir，每个 Actor 串行处理消息）
>     
> 
> **第一性原理**：**并发不是目的，吞吐才是目的。当"串行化 + 异步 I/O"能达到更高吞吐时，放弃并发是合理的 architectural trade-off。**

**5. 数据分片：高并发写的"终局方案"。**

当缓存、异步、批量都用尽了，单机的写入能力还是不够时，**唯一的出路是数据分片**——把数据按某个维度（如 user_id 哈希、时间范围）拆分到多个数据库实例：

- 某电商订单系统优化案例：单库写入 QPS 1.2 万（已达 MySQL 极限）→ 按 user_id 哈希拆 4 库 32 表 → 单分片写入降至 3000 QPS → 配合批量写入，整体提升至 **8 万 QPS**
    

> **洞见**：数据分片是"分而治之"思想在数据库层的终极应用。它呼应了第6章"分库分表"的内容——**分片键的选择决定了系统的天花板**。分片键选错（如按 order_id 分片但高频查询是按 user_id），分片不仅没用，反而引入跨分片查询的新瓶颈。
> 
> **这再次印证了本书的主题——业务架构与技术架构必须融合**：技术上的"怎么分"取决于业务上的"按什么维度查"。

## 8.4 容量规划：用数据说话，而非拍脑袋

### 📖 原著脉络

作者强调两个核心：

- **吞吐量、响应时间、并发数的关系**
    
- **压力测试与容量评估**
    

### 🔍 网络佐证

**三者的核心关系（Little's Law）**：

```
吞吐量（TPS/QPS）≈ 并发数 / 平均响应时间
```

**关键认知**：

- **并发数增加，吞吐量未必线性增加**——存在最佳并发点，超过后增加并发反而有害
    
- **典型曲线**：轻负载区（线性增长）→ 负载区（增速放缓）→ 饱和区（达到峰值）→ 过载区（下降）
    
- **容量规划的核心**：找到"最佳并发区间"——吞吐量最大、响应时间可接受
    

**压力测试的方法论**：

1. **单接口基准**：1 用户多次迭代，获取单用户 RT 与 TPS 基线
    
2. **阶梯/爬坡**：从低并发起步，按 20% 增量逐级增压，每级稳定运行 3-5 分钟
    
3. **拐点判定**：
    
    - 吞吐量拐点：TPS 增幅低于并发增幅的 50%
        
    - 延迟拐点：P99 响应时间突破业务容忍阈值
        
    - 错误拐点：错误率 > 0.1%
        
    
4. **容量计算**：理论最大并发 = 稳定 RPS × 平均响应时间；生产环境预留 1.5 倍冗余
    

### 💡 我的理解与洞见

**1. 容量规划的第一性原理：找到"拐点"，而非追求"最大值"。**

很多团队压测时追求"系统能撑多少 QPS"，这是错误的。正确的做法是——**找到吞吐量开始下降、响应时间开始飙升的"拐点"，并以拐点为容量规划的基准**。

> **生动比喻（高速公路收费站）**：
> 
> - 并发数 = 同时到达收费站的车
>     
> - 吞吐量 = 单位时间通过的车流量
>     
> - 上升区：多开几个窗口，车越多通行车流越大
>     
> - 峰值区：窗口全开，车流达到最大设计容量
>     
> - **过载区**：车远超窗口处理能力，车辆排长队（响应时间飙升），单位时间内通过的车反而减少
>     

**2. 压测必须观察 P99，而非平均值。**

这是工业界血的教训：

- **平均值**容易被极端值稀释，看起来"健康"——比如平均 RT 200ms，但 1% 的请求 2 秒
    
- **P95/P99**才是用户体验的真实映射——它代表了"绝大多数用户实际感受到的延迟"
    
- **错误率**是最易忽视却最关键的指标，错误率 > 1% 就必须停止压测
    

> **洞见**：一个"平均 RT 200ms"但"P99 2秒"的系统，比"平均 RT 500ms"但"P99 600ms"的系统体验更差。架构师看压测报告，**第一眼看 P99，第二眼看错误率，平均值仅供参考**。

**3. 容量规划的工业公式。**

基于 Little's Law，给出实用的容量规划公式：

```
并发数 ≈ 吞吐量（QPS）× 平均响应时间（秒）
```

**实例**：目标峰值 QPS = 1500，平均 RT = 120ms = 0.12s

→ 系统内平均并发 ≈ 1500 × 0.12 = 180

→ Tomcat maxThreads 至少不低于 180

→ 下游 DB 连接池、Redis 连接池都不能远小于 180，否则形成硬阻塞

**扩容决策**：

- 若单机在目标并发下 RT/错误率超标 → 按"峰值并发 / 单机可承载并发"向上取整扩容
    
- 生产环境必须预留 **1.5 倍冗余**
    
- 网关/应用设置限流阈值 = 目标峰值 TPS × 安全余量
    

> **洞见**：容量规划不是"算出来的"，而是"测出来的"。公式只是给出初始估算，**真正的拐点必须通过阶梯压测获得**。这也是为什么工业界强调"全链路压测"——只有用接近生产的流量模型去压，才能得到可信的容量基线。

**4. 容量规划的本质：为"不确定性"预留空间。**

容量规划的最终目的，不是"精确算出需要多少台机器"，而是**"为业务的增长和流量的突发预留缓冲"**。双十一、秒杀、突发新闻事件——这些场景的流量往往是日常的 10-100 倍。**没有冗余的容量规划，就是一颗定时炸弹。**

> **工业实践**：
> 
> - 日常容量预留 30-50% 冗余
>     
> - 大促前通过压测重新评估，扩容到峰值的 1.5-2 倍
>     
> - 配合弹性伸缩（K8s HPA）应对突发流量
>     
> - 限流、熔断、降级作为容量的最后一道防线
>

## 🧭 全章串联：一条主线穿起四个小节

回看第8章的全部内容，它们围绕"高并发"这一核心命题，从识别问题到解决读、解决写、再到验证容量，形成完整闭环：

```
8.1 问题分类：识别瓶颈在读还是写
        ↓
8.2 高并发读：让数据离消费者更近
    ├─ 加缓存（空间换时间）
    ├─ 并发读（并行掩盖延迟）
    └─ 重写轻读（计算时间位移）
        ↓ 总结为 CQRS
8.3 高并发写：把写入压力拆开、推迟、合并
    ├─ 数据分片（分而治之）
    ├─ 任务分片（分而治之在程序层）
    ├─ 异步化（解耦时间依赖）
    ├─ 批量（聚合降次，顺序写替代随机写）
    └─ 串行化+多进程单线程+异步I/O（消除并发开销）
        ↓
8.4 容量规划：用数据验证上述策略的有效性
    └─ 吞吐量、响应时间、并发数的三角关系 + 阶梯压测找拐点
```

**这条主线的底层逻辑，正是第2章"道术合一"在高并发领域的具体展开：**

|第一性原理|本章对应（术）|底层思想（道）|
|---|---|---|
|空间换时间|缓存、CDN、重写轻读|用冗余/预处理消除慢路径|
|分而治之|数据分片、任务分片|大瓶颈拆成小瓶颈|
|聚合降次|批量、缓冲写|用顺序写替代随机写|
|解耦时间依赖|异步化、MQ|用空间（队列）换时间解耦|
|消除并发开销|串行化+单线程+异步I/O|有时串行比并发更快|
|用数据说话|容量规划、阶梯压测|找到拐点，而非追求极值|

> **谁只背得下"高并发读用缓存、高并发写用分库分表"——那是停留在术；谁能说出"读优化的核心是让数据离消费者更近（空间换时间/并行/计算时间位移），写优化的核心是降低单次写入的有效开销（分治/解耦/聚合/消除并发开销），且所有策略都必须通过容量规划验证"——谁才真正读通了本章的道。**
