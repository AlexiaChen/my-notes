
这两章是全书的高潮——第21章"尖叫的架构"给出了一个**反直觉的美学判断**：评价一个架构的好坏，先看它的顶层目录"喊"出来的是什么；第22章"整洁架构"则把这个美学判断**收敛为一个几何模型**——同心圆 + 依赖规则。两章合在一起，实际上是 Bob 对前21章所有纪律的**最终可视化**：SOLID 是类级纪律，组件原则是组件级纪律，第15-20章是策略与边界，而第21-22章是这一切的"形状"。这一章的真正智慧在于：Bob 没有发明新的原则，他只是把前面所有的原则**画成了一个图**——这个图之所以有力，是因为它让"保持可选项"从一句哲学口号变成了一个可以贴在墙上的几何约束。

# 第21章 尖叫的软件架构

## 架构设计的主题

Bob 开篇用了一个建筑蓝图的比喻，这个比喻看似朴素，但极其锋利：

> 当你看一栋建筑的蓝图时，你会立刻知道这是一栋住宅、一个图书馆，还是一座教堂。架构在"尖叫"——它在喊出这座建筑的用途。

然后他抛出了全章最关键的问题：

> **那么，你的应用架构"尖叫"出来的是什么？**​ 当你看顶级目录结构和最高层包中的源文件时，它们是在尖叫"医疗系统"、"会计系统"、"库存管理系统"？还是在尖叫"Rails"、"Spring/Hibernate"、"ASP"？

这个答案几乎决定了架构的成败。

Bob 回溯到 Ivar Jacobson 的 seminal work《Object-Oriented Software Engineering》，指出其副标题就是"A use case driven approach"——Jacobson 早就点明：**软件架构是支撑系统用例的结构**。正如住宅和图书馆的平面图尖叫着它们的用例，软件应用的架构也应该尖叫着它的用例。

> 💡 **第一性原理解读**：第21章"尖叫"的第一性原理是**"认知的经济学"**。任何系统的第一消费者不是最终用户，而是**开发者**——尤其是那些还不熟悉系统、需要快速理解"这个系统做什么"的开发者。顶层目录结构是开发者对系统的**第一认知界面**。如果这个界面尖叫的是"Spring/Hibernate"，那么开发者建立的第一个心智模型就是技术模型——他们会围绕 Controller、Service、Repository 去思考；如果这个界面尖叫的是"Patient/Appointment/Billing"，那么开发者建立的第一个心智模型就是业务模型——他们会围绕业务能力和用例去思考。
> 
> 这两种心智模型导致了完全不同的系统演化路径：
> 
> - **技术模型主导**​ → 所有变更都从"框架允许我怎么做"出发，业务规则被框架约束扭曲
> - **业务模型主导**​ → 所有变更都从"业务需要什么"出发，框架作为插件服务于业务
> 
> 所以"尖叫"不是一个美学问题，而是一个**认知经济学问题**——它决定了 HR 成本在系统全生命周期中的走向。技术导向的目录结构，会把每一行业务代码的修改都变成一个"框架对抗"的过程，HR 成本指数级上升。

### 工业对照：按业务能力组织的现代实践

2024-2026 年的工业实践完全验证了 Bob 的洞察。现代"尖叫架构"的组织方式：

```
❌ 技术导向（尖叫"我是 Rails/Spring"）
src/
├── controllers/
├── services/
├── repositories/
└── models/

✅ 业务导向（尖叫"我是医疗系统"）
src/
├── patients/
│   ├── Patient.java              # 实体
│   ├── RegisterPatientUseCase.java
│   ├── PatientController.java     # 适配器
│   └── PatientRepositoryImpl.java
├── appointments/
│   ├── Appointment.java
│   ├── ScheduleAppointmentUseCase.java
│   └── AppointmentController.java
└── billing/
    ├── Invoice.java
    ├── GenerateInvoiceUseCase.java
    └── BillingController.java
```

2023 年那篇著名的反思文章《Uncle Bob, We've Failed You!》尖锐地指出：过去十年业界虽然接受了"同心圆"图表，但把"Use Case"悄悄替换成了"Service"，结果**Service 让我们关注数据而不是用例**——这正是违背了"尖叫"的本意。

> 📌 **创新洞见**：Bob 2017 年说"架构应该尖叫业务意图"时，主要对立面是 MVC 的技术分层。今天，我们需要把"尖叫"的对立面扩展到更多现代形态：
> 
> - ❌ "尖叫微服务"：`order-service/`、`payment-service/`、`user-service/` —— 这是在尖叫"我的部署拓扑"，不是业务意图
> - ❌ "尖叫 DDD"：`interfaces/`、`application/`、`domain/`、`infrastructure/` —— 这是在尖叫"我的 DDD 分层"，业务意图被埋在第3层
> - ❌ "尖叫框架"：`@RestController`、`@Entity`、`@Service` —— 注解本身就是框架噪声
> - ✅ "尖叫业务"：`patients/`、`appointments/`、`billing/` —— 每个目录内再分 entity/usecase/adapter
> 
> 真正"尖叫"的架构，是让一个新开发者在**不读一行代码、只看目录**的情况下，就能回答"这个系统是用来做什么的"。这是 Bob 原书精神的现代兑现。

## 架构设计的核心目标

Bob 在这一节给出了"尖叫架构"的深层目的：

> 优秀架构以用例为中心，是为了让架构师能够**安全地描述支撑这些用例的结构，而不必承诺于框架、工具和环境**。再次考虑房屋的规划——建筑师的首要关切是确保房屋可用，而不是确保房屋由砖块制成。

这段话揭示了架构设计的核心目标：**最大化"未做的决策"数量**。

具体做法是：

- 架构师**首先**确保用例被满足
- 至于用砖块、石头还是雪松——房主可以晚些决定
- 好的软件架构让关于框架、数据库、Web 服务器和其他环境问题的决策**被推迟、被延迟**
- 好的架构让**改变这些决策变得容易**
- 好的架构**强调用例**，并将它们与周边关注点解耦

2024 年 Adesso 的文章精准地引用了 Bob 的这句金句：

> "A good architect maximizes the number of decisions not made."

> 💡 **第一性原理解读**：这一节的第一性原理是**"决策期权经济学"**（延续第15章"保持可选项"）。每一个早期决策都在消耗系统的"决策期权"。架构设计的核心目标不是"做出正确的决策"，而是**"尽可能长时间地不做出决策"**——因为：
> 
> - 早期做出的决策基于最不完整的信息
> - 早期做出的决策关闭了最多的选项
> - 早期做出的决策如果错误，修正成本最高
> 
> 所以**"最大化未做决策的数量"**​ 不是拖延，而是一种精密的期权管理策略。当架构让用例与框架、数据库、Web 服务器解耦时，这些细节决策就被"期权化"了——你可以在信息最充分的时刻"行权"，而不是在信息最匮乏的 Day 1 被迫行权。
> 
> 这就是为什么 Bob 说"好的架构让改变这些决策变得容易"——**架构质量 = 决策的可逆性**。一个让"从 MySQL 切换到 PostgreSQL"需要重写业务规则的架构，是糟糕的架构；一个让这个切换只需替换一个适配器的架构，是整洁的架构。

## 那 Web 呢

这是全章最反直觉、也最解放思想的一节。

Bob 的回答干脆利落：

> **Web 是一种交付机制，你的应用架构应该如此对待它。你的应用通过互联网交付这一事实，是一个细节，不应支配你的系统结构**。

更进一步：

> 你的系统架构应该对"如何交付"尽可能无知。**你应该能够把它交付为控制台应用、Web 应用、胖客户端应用，甚至是 Web 服务应用，而不会对基础架构造成不当的复杂化或变更**。

### 为什么这一点至关重要

大多数团队的致命错误是：**从 Day 1 就把"Web 应用"等同于"系统本身"**。他们：

- 用 Spring Boot / Rails / Django 的脚手架启动项目
- 在 Controller 里写业务逻辑
- 用 `@Entity` 注解渗透领域模型
- 把 HTTP Request/Response 对象传递到业务核心

结果：**Web 框架成为了架构的主干**，业务规则被迫适应框架的生命周期、线程模型、依赖注入容器。

Bob 的解药是：**Web 只是一个插件**。系统核心是业务规则，Web 是通过边界"插入"到业务规则上的一个交付机制。

> 💡 **第一性原理解读**：这一节的第一性原理是**"交付机制与业务本质的分离"**。Web 在 1990 年代之前根本不存在，在未来也可能被语音、AR/VR、脑机接口等新交付机制取代。但业务本质——"下单"、"计息"、"盘点"——几十年来基本不变。
> 
> 如果一个系统的架构让 Web 成为了"主干"，那么当交付机制从 Web 演进到移动 App、再到语音助手时，业务规则就需要重写。反之，如果 Web 只是一个插件，那么业务规则可以"插入"到任意新的交付机制上——**业务规则的生命周期得以脱离交付机制的代际更替**。
> 
> 这就是为什么银行的核心计息逻辑可以运行几十年——它被正确地与交付机制隔离了。每一次交付技术的更替，都只是"换了一个插件"，核心业务规则稳如泰山。

### 工业对照：Backend for Frontend 与多交付机制

2024-2026 年的工业实践：

**1. 同一核心，多种交付**：

```
┌── Web BFF → Use Cases → Domain
Mobile App ───────→├── Mobile BFF → Use Cases → Domain
CLI ──────────────→├── CLI Adapter → Use Cases → Domain
API Gateway ──────→└── API Adapter → Use Cases → Domain
```

每个交付机制都是独立适配器，共享同一个业务核心。

**2. Serverless 中的"Web 无关性"**：

2024-2026 年，AWS Lambda 等 Serverless 平台让"Web 是插件"成为默认实践：

```
// Lambda Handler（Web 适配器，与业务核心完全解耦）
export const handler = async (event: APIGatewayProxyEvent) => {
  const request = mapToCreateOrderRequest(event);
  const useCase = container.resolve<CreateOrderUseCase>();
  const result = await useCase.execute(request);
  return mapToApiGatewayResponse(result);
};

// 同一业务核心可以"插入"到不同的触发器
export const onSQSEvent = async (event: SQSEvent) => {
  // 完全相同的 Use Case，不同的适配器
};
```

业务核心对"是否通过 Web 调用"一无所知。

## 框架是工具而不是生活信条

这一节是 Bob 对"框架迷信"的当头棒喝。

他坦率地指出框架作者的心理：

> 框架作者通常相信他们的框架。他们写的示例，是从一个真正信徒的视角讲述的。其他写框架的人也往往是这种真正信仰的信徒。他们向你展示使用框架的方式，通常是一种包罗万象的、无所不在的、"让框架做一切"的姿态。但这**不是你想要采取的姿态**。

Bob 的建议极其犀利：

> **用厌世的眼光看待每个框架。怀疑地审视它。是的，它可能有帮助，但代价是什么？我应该如何用它，又应该如何保护自己免受其害？我如何保持架构对用例的强调？**

### 框架的真正位置

Bob 的逻辑非常清晰：

- 框架是工具，不是生活方式
- 框架可以非常强大、非常有用
- 但框架应该被**封装在系统中**，确保它们不能支配系统的结构
- 架构应该是**围绕用例和业务关注点**组织的

> ⚠️ **批判性思考**：Bob 2017 年警告"框架是工具不是信条"时，主要对立面是 Rails 的"全栈框架"哲学和 Spring 的"全家桶"倾向。今天，框架迷信不仅没有消失，反而以新的形式愈演愈烈：
> 
> - **前端框架迷信**：React/Vue/Angular 的目录结构（components/、hooks/、store/）经常渗透进业务核心
> - **云厂商框架迷信**：直接调用 AWS SDK / Azure SDK，让业务核心与云厂商锁定
> - **ORM 迷信**：`@Entity` 注解直接写在领域实体上，让 JPA/Hibernate 渗透业务核心
> - **LLM 框架迷信**：LangChain/LlamaIndex 的链式调用直接写在业务规则中，让 LLM 提供商锁定
> - **微服务框架迷信**：Spring Cloud / Istio 的注解和配置渗透业务核心
> 
> 2026 年 Cubic 的文章明确指出：当 AI 辅助编程成为主流时，**依赖规则必须由静态分析工具守护**——因为 AI 生成的代码倾向于"过度耦合"（因为它看不到全貌，会直接写 `database.query()` 在业务逻辑中）。
> 
> 这意味着 Bob "框架是工具"的告诫在 AI 时代变得更加尖锐：**框架不是信条，而且框架的诱惑力在 AI 时代被放大了**——因为 AI 默认会生成"框架中心化"的代码。架构师的工作从"教育人类开发者抵制框架诱惑"升级为"用工具强制 AI 抵制框架诱惑"。

### 工业对照：架构适应度函数守护边界

2024-2026 年的现代实践：

```
// ArchUnit 测试：强制"框架是工具"
class ArchitectureTest {
    @Test
    void domain_should_not_depend_on_frameworks() {
        assertThat(domainClasses())
            .should().notDependOnClassesThat()
            .resideInAPackage("..springframework..")
            .or().resideInAPackage("..hibernate..")
            .or().resideInAPackage("..jpa..");
    }
    
    @Test
    void use_cases_should_not_know_about_web() {
        assertThat(useCaseClasses())
            .should().notDependOnClassesThat()
            .haveNameMatching(".*Controller")
            .or().haveNameMatching(".*RestController");
    }
    
    @Test
    void entities_should_not_have_framework_annotations() {
        assertThat(entityClasses())
            .should().notBeAnnotatedWith(Entity.class)
            .andShould().notBeAnnotatedWith(Service.class);
    }
}
```

这样，Bob "框架是工具"的哲学就变成了 CI 中的**硬约束**——任何违反"尖叫业务意图"的代码都无法合并。

## 可测试的架构设计

这一节是"尖叫架构"的自然推论，也是 Bob 给出的**可操作检验标准**：

> 好的架构应该独立于框架、**无需 UI 即可测试**、**无需数据库即可测试**、独立于任何外部机构。

具体含义：

- **无需 UI 即可测试**：业务规则可以在没有浏览器、没有 HTTP 服务器的情况下进行测试
- **无需数据库即可测试**：业务规则可以在内存中实现 Repository 接口，不需要真实的数据库连接
- **独立于任何外部机构**：业务规则不依赖 Web 服务、第三方 API、消息队列

### 为什么可测试性是架构质量的试金石

Bob 的逻辑链条非常严密：

1. 如果业务规则可以独立于 UI 测试 → 说明业务规则不依赖 UI
2. 如果业务规则可以独立于数据库测试 → 说明业务规则不依赖数据库
3. 如果业务规则可以独立于外部服务测试 → 说明业务规则不依赖外部机构
4. 因此，**可测试性 = 解耦性的直接证据**

反过来也成立：**如果一个架构难以测试，那么它一定是紧耦合的**。测试的难度直接反映了耦合的程度。

> 💡 **第一性原理解读**：可测试性的第一性原理是**"依赖的可观测性"**。不可见的依赖是最危险的依赖——它们在代码中不明显，但在运行时致命。测试是暴露这些隐藏依赖的唯一可靠手段：
> 
> - 当你尝试脱离数据库测试业务规则时，你会发现所有偷偷 import 了 JPA 的地方
> - 当你尝试脱离 UI 测试业务规则时，你会发现所有偷偷依赖了 HttpSession 的地方
> - 当你尝试脱离外部服务测试业务规则时，你会发现所有偷偷调用了第三方 SDK 的地方
> 
> 所以**"可测试架构"不是一个附加属性，而是"解耦架构"的必然结果和唯一证明**。一个声称"解耦"但难以测试的架构，是虚假的解耦。

### 工业对照：毫秒级测试的架构

2024-2026 年的工业标准：

```
// 业务规则测试：毫秒级，无 Spring、无数据库、无 Web 服务器
class CreateOrderUseCaseTest {
    @Test
    void should_create_order_successfully() {
        // 1. Mock 端口（简单的 in-memory 实现）
        OrderRepository mockRepo = new InMemoryOrderRepository();
        EmailService mockEmail = new FakeEmailService();
        
        // 2. 实例化用例
        CreateOrderUseCase useCase = new CreateOrderUseCase(mockRepo, mockEmail);
        
        // 3. 执行
        Order order = useCase.execute(new CreateOrderRequest(customerId, items));
        
        // 4. 断言
        assertThat(order.getStatus()).isEqualTo(OrderStatus.CREATED);
    }
}
```

Insper 的 2026 年教学材料明确指出：

> "业务规则在用例层可以用纯 JUnit 进行单元测试——没有 Spring 上下文、没有数据库、没有 Web 服务器。Mock Repository 接口，在毫秒内测试 Service。"

**测试金字塔的现代实践**：

```
/\
       /E2E\          ← 少量（依赖真实基础设施）
      /────\/
     /Integration\    ← 适量（测试适配器与端口的连接）
    /────────\/
   /  Unit     \      ← 大量（业务规则，毫秒级）
  /────────────\/
```

当架构"尖叫业务意图"时，**单元测试层可以达到 80%+ 的覆盖率**，因为业务规则完全独立于基础设施。

## 本章小结

第21章的真正贡献，是给出了一个**反技术中心化的美学与经济学判据**：

|维度|技术中心化架构|尖叫业务意图的架构|
|---|---|---|
|**顶层目录**​|controllers/、services/、repositories/|patients/、appointments/、billing/|
|**框架地位**​|框架是架构的主干|框架是插件|
|**Web 地位**​|Web 是系统本身|Web 是交付机制|
|**决策时机**​|Day 1 选定所有框架/数据库|尽可能推迟细节决策|
|**可测试性**​|需要 UI + 数据库 + Web 服务器|毫秒级纯单元测试|
|**新开发者认知**​|"这是一个 Spring 应用"|"这是一个医疗系统"|

### 三个核心定律

**定律一：架构应该尖叫业务意图，而不是技术栈**

顶级目录结构应该让你立刻知道系统做什么，而不是用什么框架。

**定律二：框架是工具，不是信条**

用厌世的眼光看待框架。怀疑地审视它。保护业务核心免受框架侵蚀。

**定律三：可测试性 = 解耦性的试金石**

如果业务规则可以脱离 UI、数据库、外部服务进行测试，那么这个架构就是解耦的。

### 现代工业的批判性补充

> ⚠️ **三个需要更新的视角**：
> 
> **1. "尖叫"在现代微服务架构中的误用**
> 
> 现代团队经常把"尖叫架构"误解为"按微服务命名"——`order-service/`、`payment-service/`、`user-service/`。这是在尖叫"我的部署拓扑"，不是业务意图。正确的"尖叫"应该是每个微服务**内部**依然按业务能力组织：
> 
> ```
> order-service/
> ├── orders/           ← 尖叫"订单业务能力"
> │   ├── Order.java
> │   ├── PlaceOrderUseCase.java
> │   └── OrderController.java
> └── shipments/        ← 尖叫"配送业务能力"
>     ├── Shipment.java
>     └── ScheduleShipmentUseCase.java
> ```
> 
> **2. AI 时代"尖叫"的新挑战**
> 
> 2024-2026 年，AI 辅助编程对"尖叫架构"提出了新挑战：
> 
> - AI 生成的代码倾向于"技术中心化"（默认生成 Controller/Service/Repository）
> - 必须通过架构适应度函数在 CI 中**强制**"尖叫业务意图"
> - 工具：ArchUnit、Spring Modulith、Custom Linting Rules
> 
> **3. "尖叫"不等于"过度细分"**
> 
> 按业务能力组织时，必须警惕"过度细分"——不是每个名词都需要一个顶级目录。应该按**业务能力的聚合边界**（即 DDD 的 Bounded Context）来组织，而不是按每个实体组织。

# 第22章 整洁架构

第22章把前21章的所有纪律**收敛为一个几何模型**——同心圆。这是全书的"图腾"。

## 依赖关系规则

### 同心圆的四层结构

Bob 给出的整洁架构模型是四层同心圆：

```
┌──────────────────────────────────────────────┐
│  Frameworks & Drivers                         │
│  (Web, UI, External APIs, DB)                 │
├──────────────────────────────────────────────┤
│  Interface Adapters                           │
│  (Controllers, Presenters, Gateways)          │
├──────────────────────────────────────────────┤
│  Use Cases                                    │
│  (Application-Specific Business Rules)        │
├──────────────────────────────────────────────┤
│  Entities                                     │
│  (Enterprise Business Rules)                  │
└──────────────────────────────────────────────┘
```

**从内到外**：

1. **Entities（实体层）**：企业级业务规则。最通用、最稳定、最不可能变更。如 `Order`、`Customer`、`Invoice`
2. **Use Cases（用例层）**：应用特定业务规则。编排实体，定义应用支持的操作。如 `PlaceOrderUseCase`、`CancelOrderUseCase`
3. **Interface Adapters（接口适配器层）**：将数据从最便于用例和实体的格式，转换为最便于外部机构（如数据库或 Web）的格式。包含 Presenters、Controllers、Gateways、Repository 实现
4. **Frameworks & Drivers（框架与驱动器层）**：最外层，包含 Web 框架、数据库、UI、外部设备。这一层全是细节，应该易于替换

### 依赖规则（The Dependency Rule）

这是全章、乃至全书的**核心定律**：

> **源码依赖只能指向内。内圈中的任何东西都不能知道外圈中的任何东西。**​ 这意味着：Web 框架 import Controller，而不是反过来；数据库 import Repository 接口，而不是反过来；UI import Presenter，而不是反过来。

用更严格的话说：

> 内圈中声明的任何东西的名字——函数、类、变量或任何其他命名软件实体——都**不得**被外圈代码提及。

### 跨边界的数据：简单数据结构

Bob 补充了依赖规则的一个关键细节：

> 在每个层边界，数据以简单结构（DTO）的形式跨边界流动，以防止实现细节泄漏。

Insper 的教学材料给出了更严格的约束：

> **跨边界的数据必须是简单数据结构——普通对象或记录——绝不可以是框架类型。`@Entity` 注解或 `HttpServletRequest` 绝不能出现在 Use Case 或 Entity 类中**。

### 为什么依赖必须向内

Bob 的逻辑基于**稳定性与抽象性的对应**：

- **内层 = 高层策略**​ = 稳定 + 抽象（业务规则几十年不变）
- **外层 = 低层细节**​ = 易变 + 具体（框架每年都在换）

依赖应该**从易变指向稳定**——这是 SDP（稳定依赖原则）的直接应用。

如果反过来（依赖向外），那么：

- 框架的一个小升级会迫使业务规则重新编译
- 数据库 Schema 的一个调整会迫使用例层修改
- UI 的一个重构会迫使实体层变更

这正是大多数"大泥球"系统的病变机制。

> 💡 **第一性原理解读**：依赖规则的第一性原理是**"变更成本的不对称性"**。内层业务规则的变更成本极高（影响整个系统、需要完整的回归测试、可能涉及业务方审批），外层细节的变更成本极低（替换一个适配器、升级一个框架版本）。
> 
> 依赖方向决定了"变更的传播方向"：
> 
> - 依赖向内 → 外层的变更被隔离（适配器修改不影响业务核心）
> - 依赖向外 → 外层的变更传播到内层（框架升级迫使业务规则重写）
> 
> 所以依赖规则本质上是一个**变更成本的防火墙**——它确保高成本的变更（业务规则）不会被低成本的变更（细节）所波及。这是 HR 成本最小化在依赖层面的直接落地。
> 
> 更深一层：依赖向内不是"自然"的，它需要**主动的多态反转**（DIP）。在大多数人的直觉中，业务规则需要调用数据库，所以业务规则依赖数据库——这是直觉的、但错误的方向。正确的方向是：业务规则**定义**它需要什么样的数据库能力（端口），数据库**实现**这个端口（适配器），源码依赖通过多态反转，从数据库指向业务规则。
> 
> 这是软件架构中最违反直觉、但也最深刻的一个设计决策：**运行时的控制流向外，编译时的源码依赖向内**。

### 工业对照：现代整洁架构的实现

**1. 推荐的包结构**（Insper 2026 教学材料）：

```
com.example.product/
├── domain/                    ← Entities 层
│   ├── Product.java           # 领域对象（无框架注解）
│   └── ProductRepository.java # Repository 接口（端口）
├── application/               ← Use Cases 层
│   ├── ProductService.java    # 业务逻辑
│   └── ProductDTO.java        # 跨边界数据
└── adapter/                   ← Interface Adapters 层
    ├── in/
    │   ├── ProductController.java
    │   ├── ProductRecordIn.java
    │   └── ProductRecordOut.java
    └── out/
        ├── ProductJpaAdapter.java  # 实现 ProductRepository
        ├── ProductTable.java       # @Entity 类（仅在此层）
        └── ProductMapper.java
```

**关键约束**：

- `@Entity` 注解**只能**出现在 `adapter/out/ProductTable.java` 中，绝不能出现在 `domain/Product.java` 中
- `ProductService`（用例层）只依赖 `ProductRepository` 接口，从不依赖 JPA、Spring Data 或任何持久化细节
- `ProductController`（适配器层）调用 `ProductService`，但 `ProductService` 不知道 `ProductController` 的存在

**2. 依赖规则的工具守护**（Cubic 2026）：

```
@Test
void enforce_dependency_rule() {
    // 内层不能依赖外层
    assertThat(classes().that().resideInAPackage("..domain.."))
        .should().notDependOnClassesThat()
        .resideInAnyPackage("..adapter..", "..application..");
    
    // 用例层不能依赖框架
    assertThat(classes().that().resideInAPackage("..application.."))
        .should().notDependOnClassesThat()
        .resideInAPackage("..frameworks..");
    
    // 实体不能有 ORM 注解
    assertThat(classes().annotatedWith(Entity.class))
        .should().resideInAPackage("..adapter.out..");
}
```

Cubic 的文章明确指出：**当依赖规则不被执行时，系统就会慢慢腐烂**——数据库查询进入 Controller，业务逻辑泄漏到 UI，基础设施代码直达领域层。在 AI 辅助编程时代，这种守护从"最佳实践"升级为"必需品"。

## 一个常见的应用场景

Bob 在这一节给出了整洁架构的一个具体应用场景。基于搜索材料，我们可以用现代工业中一个标准的"创建用户"场景来展开：

### 场景：CreateUserUseCase

**1. 最内层：实体（Entities）**

```
// 纯业务对象，无任何框架依赖
public class User {
    private UserId id;
    private Email email;
    private UserStatus status;
    
    public User(UserId id, Email email) {
        this.id = id;
        this.email = email;
        this.status = UserStatus.PENDING;
    }
    
    public void activate() {
        this.status = UserStatus.ACTIVE;
    }
    
    public boolean isActive() {
        return status == UserStatus.ACTIVE;
    }
}
```

**2. 第二层：用例（Use Cases）**

```
// 用例定义端口（接口）
public interface UserRepository {
    Optional<User> findByEmail(Email email);
    void save(User user);
}

public interface EmailService {
    void sendWelcomeEmail(Email email);
}

// 用例实现
public class CreateUserUseCase {
    private final UserRepository userRepository;  // 依赖向内
    private final EmailService emailService;      // 依赖向内
    
    public CreateUserUseCase(UserRepository userRepository, 
                            EmailService emailService) {
        this.userRepository = userRepository;
        this.emailService = emailService;
    }
    
    public User execute(CreateUserCommand command) {
        // 1. 业务校验
        if (userRepository.findByEmail(command.getEmail()).isPresent()) {
            throw new UserAlreadyExistsException(command.getEmail());
        }
        
        // 2. 创建实体
        User user = new User(UserId.generate(), command.getEmail());
        
        // 3. 持久化
        userRepository.save(user);
        
        // 4. 发送邮件
        emailService.sendWelcomeEmail(user.getEmail());
        
        return user;
    }
}
```

**3. 第三层：接口适配器（Interface Adapters）**

```
// 入站适配器：REST Controller
@RestController
public class UserController {
    private final CreateUserUseCase createUserUseCase;
    
    @PostMapping("/users")
    public ResponseEntity<UserResponse> createUser(@RequestBody CreateUserRequest request) {
        CreateUserCommand command = request.toCommand();
        User user = createUserUseCase.execute(command);
        return ResponseEntity.ok(UserResponse.from(user));
    }
}

// 出站适配器：PostgreSQL Repository
@Repository
public class PostgresUserRepository implements UserRepository {
    private final JdbcTemplate jdbcTemplate;
    
    @Override
    public Optional<User> findByEmail(Email email) {
        // 数据库访问细节
    }
    
    @Override
    public void save(User user) {
        // 数据库访问细节
    }
}

// 出站适配器：邮件服务
@Component
public class SendGridEmailService implements EmailService {
    @Override
    public void sendWelcomeEmail(Email email) {
        // SendGrid API 调用
    }
}
```

**4. 第四层：框架与驱动器（Frameworks & Drivers）**

```
// Composition Root（main 方法或 Spring 配置）
@Configuration
public class AppConfig {
    @Bean
    public CreateUserUseCase createUserUseCase(
        UserRepository userRepository,
        EmailService emailService
    ) {
        return new CreateUserUseCase(userRepository, emailService);
    }
    
    @Bean
    public UserRepository userRepository(DataSource dataSource) {
        return new PostgresUserRepository(dataSource);
    }
    
    @Bean
    public EmailService emailService(SendGridClient client) {
        return new SendGridEmailService(client);
    }
}
```

### 这个场景揭示了什么

**1. 源码依赖严格向内**：

```
Frameworks & Drivers → Interface Adapters → Use Cases → Entities
(PostgresUserRepository)   (UserController)    (CreateUserUseCase)  (User)
```

`CreateUserUseCase` 从未 import `PostgresUserRepository`、`UserController`、`SendGridEmailService`——它只知道接口。

**2. 控制流向外**：

运行时：`UserController` → `CreateUserUseCase` → `PostgresUserRepository`

**3. 跨边界数据是简单结构**：

`CreateUserRequest`、`CreateUserCommand`、`UserResponse` 都是简单 DTO，不含任何框架类型。

**4. 可替换性**：

- 从 PostgreSQL 切换到 MongoDB：只需替换 `PostgresUserRepository` 为 `MongoUserRepository`
- 从 SendGrid 切换到 AWS SES：只需替换 `SendGridEmailService` 为 `SesEmailService`
- 从 REST 切换到 gRPC：只需替换 `UserController` 为 `UserGrpcController`
- **业务核心（`User`、`CreateUserUseCase`）零修改**

> 📌 **创新洞见**：Bob 2017 年给出的"常见应用场景"主要是单体的整洁架构。今天，这个场景在微服务、Serverless、AI 系统中展现出更强大的生命力：
> 
> **AI 时代的扩展**：
> 
> ```
> // 在 CreateUserUseCase 中添加 LLM 调用
> public class CreateUserUseCase {
>     private final UserRepository userRepository;
>     private final EmailService emailService;
>     private final LLMProvider llmProvider;  // 新增端口
>     
>     public User execute(CreateUserCommand command) {
>         // ... 原有逻辑
>         
>         // 新增：用 LLM 生成个性化欢迎消息
>         String welcomeMessage = llmProvider.generate(
>             "Generate a welcome message for user: " + command.getEmail()
>         );
>         emailService.sendPersonalizedWelcome(user.getEmail(), welcomeMessage);
>         
>         return user;
>     }
> }
> 
> // LLM 提供商是框架层插件
> @Component
> public class OpenAIAdapter implements LLMProvider {  // 源码依赖向内
>     // 调用 OpenAI API
> }
> 
> @Component
> public class ClaudeAdapter implements LLMProvider {  // 可替换
>     // 调用 Claude API
> }
> ```
> 
> 当从 GPT-4 切换到 Claude 3 时，`CreateUserUseCase` **一行代码都不用改**——只需在 Composition Root 中替换 Bean 实现。这正是整洁架构在 AI 时代的兑现：**LLM 提供商是最外层的细节，业务核心对它一无所知**。

### 工业对照：整洁架构在现代技术栈中的落地

**1. 前端（React）中的整洁架构**：

```
// domain/（实体层）
export class User {
  constructor(public id: string, public email: string) {}
}

// application/（用例层）
export class CreateUserUseCase {
  constructor(private userRepository: UserRepository) {}
  
  async execute(command: CreateUserCommand): Promise<User> {
    // 业务逻辑
  }
}

// adapter/in/（入站适配器：React Hook）
export function useCreateUser() {
  const repository = useContext(UserRepositoryContext);
  const useCase = new CreateUserUseCase(repository);
  
  return async (email: string) => {
    return await useCase.execute(new CreateUserCommand(email));
  };
}

// adapter/out/（出站适配器：REST API）
export class RestUserRepository implements UserRepository {
  async save(user: User): Promise<void> {
    await fetch('/api/users', {
      method: 'POST',
      body: JSON.stringify({ email: user.email })
    });
  }
}
```

React 组件（最外层框架）调用 Hook（入站适配器），Hook 调用 UseCase（用例层），UseCase 调用 Repository 接口（端口），RestUserRepository（出站适配器）实现接口。依赖严格向内。

**2. 整洁架构在微服务内部的强制**：

2026 年的工业共识是：**每个微服务内部都应该是整洁架构的**。微服务解决了"部署独立性"，但微服务内部依然需要整洁架构来解决"代码组织"问题。一个典型的微服务内部结构：

```
order-service/
├── domain/           # Entities
│   ├── Order.java
│   └── OrderRepository.java  # 端口
├── application/      # Use Cases
│   ├── PlaceOrderUseCase.java
│   └── CancelOrderUseCase.java
├── adapter/
│   ├── in/           # Controllers
│   └── out/          # Repository 实现、外部服务客户端
└── config/           # Composition Root
```

**3. 架构适应度函数：自动化守护依赖规则**：

2026 年 Cubic 的文章强调：整洁架构的依赖规则**不能只停留在文档上**，必须在 CI 中用工具强制：

- **ArchUnit**（Java）：在 JUnit 测试中断言包依赖方向
- **Dependency Cruiser**（JavaScript/TypeScript）：在构建时检查模块依赖图
- **Spring Modulith**：在模块级别强制执行边界
- **AI-powered code review**：自动捕获 Pull Request 中的依赖违规

这样，当 AI 生成代码或初级开发者写出"Service 直接调用数据库"的代码时，CI 会**自动阻断合并**。

### 现代工业的批判性补充

> ⚠️ **三个需要更新的视角**：
> 
> **1. 整洁架构不是"必须四层"**
> 
> Bob 的四层模型是一个**参考实现**，不是教条。现代工业实践表明：
> 
> - 小型项目可能只需要 Entities + Use Cases 两层
> - 复杂项目可能在 Use Cases 和 Interface Adapters 之间加入"Application Services"层
> - 关键是**依赖规则**，不是层数
> 
> 2023 年那篇《Uncle Bob, We've Failed You!》的反思很有代表性：业界接受了同心圆，但把"Use Case"悄悄替换成了"Service"，结果失去了"用例驱动"的本意。**问题在于不是四层模型本身，而是是否真正围绕用例组织**。
>

> 2024-2026 年，AI 辅助编程成为主流，AI 生成的代码倾向于"技术中心化"。Cubic 的文章明确指出：**依赖规则必须用静态分析工具守护**：
> 
> - ArchUnit、NDepend、Dependency Cruiser
> - AI-powered code review platforms
> - 在 Pull Request 中自动捕获依赖违规
> 
> 整洁架构从"工程师的纪律"升级为"工具的强制"。
> 
> **3. 整洁架构与服务边界的正交性**
> 
> 整洁架构的同心圆是**源码层次**的边界，与**部署层次**的服务边界是正交的：
> 
> - 一个微服务内部依然应该是整洁架构的
> - 微服务之间的边界是服务层次的边界
> - 两者互补，不冲突
> 
> 2026 年的工业共识："以模块化单体起步，如果扩展需要，再将适配器抽取为独立的微服务，且无需触及领域核心"。这正是整洁架构在边界谱系上的灵活应用。
