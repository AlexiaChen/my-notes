
第19章和第20章是全书"整洁架构模型"的真正奠基——第19章给出了一个颠覆性的度量标准：**层次 = 与 I/O 的距离**；第20章把这套度量落到业务逻辑上：**业务实体处于最高层，用例处于较低层，请求/响应模型是它们之间的简单数据结构**。这两章合在一起，实际上是给出了一个可以精确操作的"整洁架构同心圆"的几何定义。Bob 的天才之处在于：他没有用"高层/低层"这种模糊的直觉词，而是用**"距输入输出的距离"**这个可度量的定义，把 SRP、CCP、DIP、SDP、SAP 全部统一到了一个坐标系里。

# 第19章 策略与层次

## 层次（Level）

### 软件的本质：策略的集合

Bob 开篇给出了一个极其简洁、但极深刻的定义：

> 软件系统本质上是一系列处理策略的集合。计算机程序核心上就是这样——它详尽地描述了将输入转化为输出的策略。

这个定义看似平淡，实则颠覆了大多数人对软件的直觉认知。我们习惯说"软件是代码"、"软件是系统"、"软件是产品"——但 Bob 说**软件是策略**。

为什么这个定义重要？因为它直接告诉我们**架构要管理的是什么**——不是代码行、不是模块、不是服务，而是**策略**。

在非小型系统中，整体策略会被细分为众多更细粒度的策略声明：

- 一部分描述业务规则如何计算
- 一部分描述报表如何格式化
- 一部分描述输入数据如何校验

### 架构的艺术：按变更方式重组策略

Bob 紧接着给出了架构工作的本质：

> 架构开发的艺术之一，就是仔细地将这些策略彼此分离，并根据它们的变更方式进行重新分组。

具体做法是：

1. **因相同原因、在相同时间变更的策略，处于同一层次，应该放在同一个组件中**（这是 SRP 和 CCP 的直接应用）
2. **因不同原因、在不同时间变更的策略，处于不同层次，应该分离到不同组件中**
3. 将这些重组后的组件组织成一个**有向无环图（DAG）**——节点是包含同层次策略的组件，有向边是组件间的依赖关系，连接不同层次的组件

> 💡 **第一性原理解读**：第19章"层次"的第一性原理是**"变更轴的几何化"**。第13章 CCP 说"按变更原因分组"——但 CCP 没有告诉你在多个变更轴同时存在时如何排序。Bob 在这里给出了答案：**用"距 I/O 的距离"作为层次的度量坐标**。
> 
> 这个度量之所以深刻，是因为它与变更频率高度相关：
> 
> - **距 I/O 越远**（高层策略）→ 变更频率越低、变更原因越重要（业务本质、核心算法）
> - **距 I/O 越近**（低层策略）→ 变更频率越高、变更原因越琐碎（UI 框架升级、数据库迁移、I/O 设备更换）
> 
> 加密程序的例子完美说明了这一点：加密算法本身（距 I/O 远）极难变更，且变更原因重大（安全性突破）；而 I/O 设备（距 I/O 近）经常变更，且变更原因琐碎（换一个终端、换一种传输方式）。
> 
> 所以"层次"不是一个人为的分类，而是**变更动力学在几何上的自然投影**。架构师的工作，就是识别这个几何结构，并让源码依赖顺着这个几何结构——从低层指向高层。

### 层次的严格定义：与输入输出的距离

Bob 给出了全章最重要的一句话：

> **"层次"的严格定义是"与输入和输出之间的距离"。一条策略距离系统的输入/输出越远，它所隶属的层次就越高。相反，直接管理输入和输出的策略，其在系统中的层次是最低的。**

这个定义有三个革命性含义：

**1. 层次是可度量的**

不是"我觉得这是高层"或"我觉得这是底层"——而是**数一数这条策略与 I/O 之间隔了多少层**。隔得越多，层次越高。

**2. 层次与重要性正相关**

高层策略（距 I/O 远）通常：

- 变更更少
- 变更原因更重要（业务本质、核心算法、关键规则）
- 价值更高（直接关乎赚钱/省钱）

低层策略（距 I/O 近）通常：

- 变更频繁
- 变更原因更琐碎（框架升级、设备更换、格式调整）
- 价值更低（细节实现）

**3. 源码依赖方向必须与层次绑定**

> 在优秀的架构中，这些依赖的方向是基于它们所连接的组件的层次而决定的。在任何情况下，低层组件都被设计为依赖于高层组件。

这是 DIP（依赖反转原则）和 SDP（稳定依赖原则）在高层次的直接应用：**稳定（高层）的东西不应该被易变（低层）的东西依赖，反过来才对**。

### 加密程序：控制流与源码依赖的反向

Bob 用了一个经典的加密程序例子来说明"层次"与"控制流"的解耦：

**错误写法**：

```
function encrypt() {
    while (true) 
        writeChar(translate(readChar()));
}
```

这段代码的问题：`encrypt`（高层策略）直接依赖 `readChar` 和 `writeChar`（低层 I/O 策略）。**控制流和源码依赖方向一致，都从高层指向低层**——这违反了"源码依赖应该指向高层"的原则。后果是：I/O 设备的任何变更（换终端、换传输方式）都会迫使 `encrypt` 重新编译。

**正确写法**：

```
┌─────────────────────────────────────────┐
│  Encrypt (高层)                          │
│  ┌───────────────────────────────────┐   │
│  │ CharReader 接口                   │   │
│  │ CharWriter 接口                   │   │
│  └───────────────────────────────────┘   │
└──────────↑──────────────────↑────────────┘
           │                  │
           │                  │
    ┌──────↓──────┐   ┌──────↓──────┐
    │ConsoleReader│   │ConsoleWriter│
    │(低层)       │   │(低层)       │
    └─────────────┘   └─────────────┘
```

- `Encrypt` 类定义 `CharReader` 和 `CharWriter` 接口（端口）
- `ConsoleReader` 和 `ConsoleWriter` 实现这些接口（适配器）
- **运行时控制流**：`Encrypt` → `ConsoleReader.readChar()` → `Encrypt.translate()` → `ConsoleWriter.writeChar()`（向外）
- **编译时源码依赖**：`ConsoleReader` → `CharReader` 接口 → `Encrypt`（向内）

> 加密程序的核心洞察：**源码依赖与控制流解耦，并与层次耦合**。控制流可以任意方向流动（因为运行时调用是动态的），但源码依赖必须始终指向高层。

**结果**：I/O 设备、传输方式等低层更改几乎不会影响高层加密策略。加密策略可以在广泛的上下文中被复用——文件、网络、内存、UI，任何 I/O 形态都可以"插入"到 `Encrypt` 上。

> 💡 **创新洞见**：Bob 2017 年用"加密程序"作为例子，今天我们需要把这个例子升级为**"AI 推理程序"**：
> 
> ```
> // 高层策略（距 I/O 最远）
> class ContentModerator {
>   constructor(private llm: LLMProvider) {}  // 端口
>   
>   moderate(text: string): ModerationResult {
>     const prompt = this.buildPrompt(text);
>     const completion = this.llm.complete(prompt);  // 控制流向外
>     return this.parseResult(completion);
>   }
> }
> 
> // 低层策略（距 I/O 最近）
> class OpenAIAdapter implements LLMProvider {  // 源码依赖向内
>   complete(prompt: string): Completion {
>     // 调用 OpenAI API
>   }
> }
> 
> class ClaudeAdapter implements LLMProvider {  // 源码依赖向内
>   complete(prompt: string): Completion {
>     // 调用 Claude API
>   }
> }
> ```
> 
> 当 OpenAI 涨价或停服时，`ContentModerator`（高层策略）**一行代码都不用改**——只需在 Composition Root 中将 `OpenAIAdapter` 替换为 `ClaudeAdapter`。这正是 Bob "层次"理论在 AI 时代的完美兑现：**LLM 提供商距 I/O 最近（网络调用），所以是低层；内容审核策略距 I/O 最远（核心业务），所以是高层；源码依赖必须从 LLM 适配器指向内容审核策略**。

### 工业对照：层次理论在现代架构中的体现

**1. 六边形架构的层次映射**：

Alistair Cockburn 的六边形架构（2005）与 Bob 的层次理论完全吻合。2024 年的权威资料明确指出：

- **从核心域逻辑开始**：独立于数据库、API 或用户界面实现核心业务逻辑和实体
- **设计端口（接口）**：定义入站端口（处理外部请求）和出站端口（与外部系统通信）
- **实现适配器**：入站适配器处理 HTTP 请求或消息队列，出站适配器处理数据库或外部 API
- **利用依赖注入**：通过接口而非直接实现连接适配器与核心系统

这正是"源码依赖指向高层（核心域）"的现代工程化表达。

**2. 微服务内部的层次**：

Chris Richardson 在《Microservice Patterns》中明确：每个微服务的**内部架构通常应该是六边形的**。这意味着即使在微服务（最强边界）内部，依然要遵循层次规则——源码依赖指向领域核心。

**3. Serverless 函数的层次**：

2024 年 Cockburn 的六边形架构新书指出：Serverless 架构特别受益于六边形结构，因为 Lambda 函数经常将业务逻辑与基础设施代码混在一起。六边形架构强制分离，使每个函数可独立测试，其逻辑可在不同触发器（API Gateway、SQS、EventBridge）之间复用。

**4. 模块化单体先行**：

现代工业最佳实践明确指出："以模块化单体起步，如果扩展需要，再将适配器抽取为独立的微服务，且无需触及领域核心"。这正是 Bob 层次理论在操作层面的推论——**先按层次划分组件（源码层次），再根据需要扩展边界（部署/服务层次）**。

## 本章小结

第19章的真正贡献，是给出了一个**可度量的层次定义**，将前15章的所有原则统一到一个坐标系中：

|原则|在第19章中的体现|
|---|---|
|**SRP**​|因相同原因变更的策略归为同一层次、同一组件|
|**CCP**​|因相同原因、同时变更的策略 belong together|
|**OCP**​|高层策略（稳定）不因低层策略（易变）的变更而修改|
|**DIP**​|源码依赖由低层指向高层，与控制流解耦|
|**SDP**​|低层（易变）依赖高层（稳定）|
|**SAP**​|高层（抽象）被低层（具体）实现|

### 层次的三个可操作推论

**推论一：源码依赖方向 = 层次方向**

```
高层 ←── 源码依赖 ── 低层
（距 I/O 远）          （距 I/O 近）
```

**推论二：控制流方向 ≠ 源码依赖方向**

控制流可以任意方向（运行时动态），但源码依赖必须指向高层。这是通过多态（DIP）实现的。

**推论三：隔离强度与层次正相关**

越高的层次，应该越稳定、越抽象、越难变更。越低的层次，应该越易变、越具体、越容易替换。

> 💡 **最终洞见**：第19章的"层次"不是一种"架构风格"，而是**架构的万有引力定律**——无论你用单体、模块化单体、微服务、Serverless、事件驱动，只要你希望系统是"软"的（可被廉价改变），你就必须遵守这条定律：
> 
> **源码依赖必须指向距 I/O 更远的高层策略**。
> 
> 这就是为什么 Bob 说"一个计算机程序就是将输入转化为输出的策略的详细描述"——一旦你接受这个定义，那么"如何组织这些策略"就有了客观标准：按变更方式分组，按距 I/O 的距离排序，让依赖指向高层。
> 
> 在 AI 驱动开发的时代，这个定律变得更加关键：当 LLM 调用、向量数据库、事件总线等新型 I/O 密集组件涌入系统时，**只有严格遵守"源码依赖指向高层"的层次纪律，业务核心才能不被这些易变的细节所污染**。一个 2025 年的真实案例：某金融科技公司在核心风控引擎外包裹了 LLM 端口，当从 GPT-4 切换到 Claude 3 时，风控引擎代码零修改——这正是第19章层次理论在 AI 时代的兑现。

# 第20章 业务逻辑

第20章把第19章的"层次"理论**落到业务逻辑上**——这是整洁架构同心圆最核心的内两层。

## 业务实体

### 业务实体 = 关键业务逻辑 + 关键业务数据

Bob 给出了一个极其精准的定义：

> **业务逻辑**是程序中那些真正用于赚钱或省钱的业务逻辑与过程，也称为"关键业务逻辑"。关键业务逻辑通常需要处理一些数据，这些数据称为"关键业务数据"。关键业务逻辑和关键业务数据是紧密相关的，所以它们很适合被放在同一个对象中处理。我们将这种对象称为"**业务实体（Entity）**"。

这个定义有三个关键点：

**1. 业务实体是"赚钱/省钱"的载体**

业务逻辑不是泛指所有代码逻辑——它是**直接创造商业价值的逻辑**。订单计算、利率计算、库存盘点、风险评估——这些是业务实体应该承载的。而那些"不赚钱"的逻辑（格式化、校验、持久化、传输）不是业务实体，它们是低层的细节。

**2. 业务逻辑与业务数据是孪生的**

关键业务逻辑和关键业务数据是**不可分离的**——它们共同构成了业务实体。一个 `Order` 实体既有 `calculateTotal()` 这样的业务行为，也有 `items`、`status` 这样的业务数据。把它们分开（贫血模型）是对业务实体的背叛。

**3. 业务实体是最高层的策略**

按照第19章的层次定义，业务实体**距 I/O 最远**——它不依赖数据库、不依赖 UI、不依赖框架。因此业务实体是系统中**层次最高的组件**。

### 业务实体的特征

基于材料，业务实体具有以下特征：

- 将软件中具体实现了该关键业务的部分聚合在一起
- 将其与自动化系统中我们所构建的其他部分隔离区分
- 业务实体这个概念只要求我们将关键业务数据和关键业务逻辑绑定在一个独立的软件模块内

> 💡 **第一性原理解读**：业务实体的第一性原理是**"业务本质的封装"**。业务实体回答的问题是："如果这个系统完全没有计算机、完全没有自动化，这段业务逻辑和数据还存在吗？"
> 
> - 如果存在（如"订单"、"利率"、"库存"）——它就是业务实体
> - 如果不存在（如"HTTP 请求"、"数据库行"、"JSON 文档"）——它不是业务实体
> 
> 这是区分业务实体与技术细节的根本标准。一个 `Order` 业务实体，无论系统是运行在大型机、PC、Web、移动端还是 Serverless 上，它都存在——因为它的本质是"订单"这个业务概念，与技术无关。
> 
> 2024 年六边形架构资料明确指出：**核心域逻辑应该独立于数据库、API 或用户界面实现**。这正是业务实体的工业级表达——它是系统的"不变内核"，所有技术细节都是围绕它旋转的插件。

### 工业对照：业务实体的现代实现

**1. 富领域模型（Rich Domain Model）**：

```
// 业务实体：Order
public class Order {
    private final OrderId id;
    private final CustomerId customerId;
    private final List<OrderLine> orderLines;
    private OrderStatus status;
    
    public Order(OrderId id, CustomerId customerId) {
        this.id = id;
        this.customerId = customerId;
        this.orderLines = new ArrayList<>();
        this.status = OrderStatus.DRAFT;
    }
    
    public void addOrderLine(Product product, int quantity) {
        if (status != OrderStatus.DRAFT) {
            throw new IllegalStateException("Cannot modify non-draft order");
        }
        orderLines.add(new OrderLine(product, quantity));
    }
    
    public Money calculateTotal() {
        return orderLines.stream()
            .map(OrderLine::subtotal)
            .reduce(Money.ZERO, Money::add);
    }
    
    public void validate() {
        if (orderLines.isEmpty()) {
            throw new DomainException("Order must have at least one item");
        }
    }
}
```

**2. 业务实体的纯净性约束**：

现代工业对业务实体的纯净性有严格要求：

- **无框架导入**：不 import 任何 ORM、Web 框架、JSON 库
- **无 ORM 注解**：不在实体类上使用 `@Entity`、`@Column` 等注解
- **无 JSON 序列化逻辑**：实体不关心如何被序列化
- **纯语言构造**：只使用编程语言本身的特性

Cockburn 在 2024 年的六边形架构新书中明确："**保持领域纯净**——领域中不导入任何外部内容，没有 ORM 注解，没有框架装饰器，没有 JSON 序列化逻辑，只用纯语言构造。"

**3. 业务实体的可测试性**：

因为业务实体不依赖任何外部细节，它可以在**毫秒级**完成单元测试，不需要数据库、不需要 Web 服务器、不需要任何 I/O。

```
@Test
void should_calculate_total_correctly() {
    // 无需任何 mock，纯内存测试
    Order order = new Order(new OrderId(), new CustomerId());
    order.addOrderLine(new Product("Book", Money.of(10)), 2);
    order.addOrderLine(new Product("Pen", Money.of(5)), 1);
    
    assertEquals(Money.of(25), order.calculateTotal());
}
```

## 用例

### 用例 = 特定场景下的应用业务规则

Bob 的精确定义：

> **用例**是关于如何操作一个自动化系统的描述，它定义了用户需要提供的输入数据、用户应该得到的输出信息以及产生输出所应该采取的处理步骤。用例中包含了对如何调用业务实体中的关键业务逻辑的定义。用例控制着业务实体之间的交互方式。

关键区分：

**业务实体 vs 用例**：

|维度|业务实体|用例|
|---|---|---|
|抽象级别|通用业务规则|特定场景下的业务规则|
|距 I/O 距离|最远（最高层）|较近（较低层）|
|是否依赖对方|不依赖用例|依赖业务实体|
|示例|`Order`（订单）|`CreateOrderUseCase`（创建订单）|

### 为什么用例层次低于业务实体？

这是第19章"层次"理论的直接应用：

- **业务实体**描述的是"订单是什么、订单能做什么"——这是业务本质，距 I/O 最远，层次最高
- **用例**描述的是"用户如何创建订单"——这是特定场景下的操作流程，距 I/O 较近（需要处理用户输入、产生输出），层次较低

因此：**用例依赖业务实体，业务实体不依赖用例**。

> 💡 **第一性原理解读**：用例的第一性原理是**"业务实体的编排"**。业务实体是"名词"（订单、客户、产品），用例是"动词"（创建订单、取消订单、计算折扣）。动词依赖名词（"创建订单"必须先有"订单"这个概念），但名词不依赖动词（"订单"这个概念独立于"如何创建订单"存在）。
> 
> 这就是为什么业务实体层次高于用例——**名词比动词更根本**。一个业务系统可以没有"创建订单"这个用例（也许通过其他方式创建），但不能没有"订单"这个业务实体。

### 用例的关键特征

基于材料：

- 用例是**应用特定业务规则**，不是通用业务规则
- 用例**依赖于业务实体**，但业务实体**不依赖于用例**
- 用例**不描述系统与用户之间的接口**，只描述特定场景下的业务逻辑
- 用例**与数据流入/流出系统的方式无关**
- 一个 API 接口可以有多个用例

### 工业对照：用例的现代实现

**1. 用例即应用服务**：

```
// 用例：CreateOrderUseCase
public class CreateOrderUseCase {
    private final OrderRepository orderRepository;
    private final CustomerRepository customerRepository;
    
    public CreateOrderUseCase(
        OrderRepository orderRepository,
        CustomerRepository customerRepository
    ) {
        this.orderRepository = orderRepository;
        this.customerRepository = customerRepository;
    }
    
    public Order execute(CreateOrderRequest request) {
        // 1. 验证输入（应用级校验）
        if (!customerRepository.exists(request.getCustomerId())) {
            throw new CustomerNotFoundException(request.getCustomerId());
        }
        
        // 2. 创建业务实体
        Order order = new Order(new OrderId(), request.getCustomerId());
        request.getOrderLines().forEach(line -> 
            order.addOrderLine(line.getProduct(), line.getQuantity())
        );
        
        // 3. 业务实体自校验
        order.validate();
        
        // 4. 持久化
        return orderRepository.save(order);
    }
}
```

**2. 端口与适配器中的用例**：

在现代六边形架构中，用例通过**输入端口**和**输出端口**与外界通信：

```
// 输入端口（定义在用例层）
public interface CreateOrderPort {
    Order createOrder(CreateOrderRequest request);
}

// 输出端口（定义在用例层）
public interface OrderRepositoryPort {
    Order save(Order order);
    Optional<Order> findById(OrderId id);
}

// 用例实现
public class CreateOrderUseCase implements CreateOrderPort {
    private final OrderRepositoryPort orderRepository;
    
    public CreateOrderUseCase(OrderRepositoryPort orderRepository) {
        this.orderRepository = orderRepository;
    }
    
    @Override
    public Order createOrder(CreateOrderRequest request) {
        // 业务逻辑...
    }
}
```

**3. 用例的隔离性**：

现代工业强调用例的**完全隔离**：

- 用例**不知道**自己是被 HTTP 调用、CLI 调用还是消息队列调用
- 用例**不知道**数据如何持久化（通过 `OrderRepositoryPort` 端口）
- 用例**不知道**结果如何展示（通过 `OrderPresenter` 输出端口）
- 用例**可以在毫秒级**完成单元测试，所有端口都用 mock 实现

## 请求和响应模型

### 跨边界数据必须是简单数据结构

Bob 在这一节给出了全章最具操作性、也最容易被违反的规则：

> 用例会接收输入数据，并产生输出数据。但在一个设计良好的架构中，用例对象通常不应该知道数据展现给用户或者其他组件的方式。

具体要求：

**1. 请求模型（Request Model）**：

- 用例接收的输入应该是**简单的数据结构**
- 不包含任何业务规则
- 不派生任何 HTTP 接口或 UI 细节
- 通常是 DTO（Data Transfer Object）、记录、或值对象

**2. 响应模型（Response Model）**：

- 用例产生的输出应该是**简单的数据结构**
- 不包含任何展示逻辑
- 不派生任何 HTTP 接口或 UI 细节
- 通常是 DTO、记录、或值对象

**3. 关键禁忌**：

> ⚠️ **避免引用业务实体**，即使二者有很多相同的数据。因为两个对象会以不同原因和速率发生变更，会违反共同闭包原则（CCP）和单一职责原则（SRP）。

### 为什么请求/响应模型不能是业务实体？

这是第19章"层次"理论的直接应用：

- **业务实体**：距 I/O 最远，变更频率低，变更原因重要
- **请求/响应模型**：距 I/O 较近（它们是 I/O 与用例之间的数据结构），变更频率高，变更原因琐碎（API 契约调整、UI 字段增减）

如果让用例直接接收/返回业务实体：

1. **API 契约变更会影响业务实体**——违反了层次规则
2. **业务实体被迫携带 I/O 细节**——破坏了业务实体的纯净性
3. **真重复伪装成假重复**——表面上都是"订单数据"，但变更原因完全不同

### 工业对照：请求/响应模型的现代实践

**1. 三层模型分离**：

现代工业明确采用**独立的领域模型、持久化模型、API 模型**：

```
# 领域模型（业务实体）
@dataclass
class User:
    id: UUID
    name: str
    email: str
    
    def change_name(self, new_name: str) -> None:
        if not new_name.strip():
            raise ValueError("Name cannot be empty")
        self.name = new_name

# 持久化模型（数据库实体）
class UserEntity(Base):
    __tablename__ = "users"
    id = mapped_column(UUID, primary_key=True)
    name = mapped_column(String(200))
    email = mapped_column(String(255), unique=True, index=True)

# API 模型（请求/响应 DTO）
class CreateUserRequest(BaseModel):
    name: str
    email: EmailStr

class UserResponse(BaseModel):
    id: UUID
    name: str
    email: EmailStr
```

**2. 映射代码的经济学**：

2026 年 Milan Jovanović 的文章给出了极其务实的指导：

> "大多数映射代码不该存在。当 API 契约与内部模型不同时、当想隐藏内部实现细节时、当领域实体暴露了不该序列化的行为时、当需要返回计算或聚合数据时才映射。当源和目标结构完全相同时，**1:1 映射是仪式，不是架构**。"

这是对 Bob "请求/响应模型"规则的现代补充——**不要为了架构而架构**。如果 `CreateUserRequest` 和 `CreateUserCommand` 字段完全相同，那么 1:1 映射就是无价值的仪式。正确的判断是：

- **结构不同**​ → 映射（有价值的转换）
- **结构相同**​ → 跳过映射（直接使用）

**3. CQRS 中的查询处理**：

对于读操作，现代工业倾向于**完全跳过映射**：

```
public class GetOrderByIdQueryHandler implements IQueryHandler<OrderResponse> {
    private final IApplicationDbContext _dbContext;
    
    public async Task<Result<OrderResponse>> Handle(
        GetOrderByIdQuery query, 
        CancellationToken cancellationToken
    ) {
        var order = await _dbContext.Orders
            .Where(o => o.Id == query.OrderId)
            .Select(o => new OrderResponse(  // 直接投影到响应模型
                o.Id, 
                o.Customer.Name, 
                o.TotalAmount.Amount, 
                o.Status.Name, 
                o.CreatedAt
            ))
            .FirstOrDefaultAsync(cancellationToken);
        
        // 无需加载领域实体，无需映射
    }
}
```

这是 CQRS 模式在读侧的极致应用——**查询直接投影到响应模型，完全绕过业务实体**。这符合 Bob 的精神：请求/响应模型是简单数据结构，不必通过业务实体中转。

**4. 跨边界数据的硬约束**：

现代工业对跨边界数据结构的约束：

- **绝不能是框架对象**：不允许 `@Entity`、`HttpServletRequest`、ORM 对象跨边界
- **绝不能是复杂对象**：不允许携带依赖、行为、副作用
- **必须是值对象或 DTO**：纯数据，不可变优先
- **必须使用依赖注入**：在组合根（Composition Root）中装配，领域代码不实例化适配器

> 📌 **创新洞见**：Bob 2017 年说"请求/响应模型是简单数据结构"时，主要考虑的是 HTTP/UI 场景。今天，我们需要把这个规则扩展到所有现代 I/O 形态：
> 
> |I/O 形态|请求模型|响应模型|
> |---|---|---|
> |HTTP API|`CreateOrderRequest` (Pydantic/Record)|`OrderResponse` (Pydantic/Record)|
> |消息队列|`OrderPlacedEvent` (Avro/Protobuf)|无（事件驱动）|
> |Serverless 触发器|`APIGatewayEvent` → `CreateOrderRequest`|`OrderResponse` → `APIGatewayProxyResponse`|
> |LLM 调用|`SummarizeTextRequest`|`SummaryResult`|
> |gRPC|`CreateOrderProto`|`OrderProto`|
> 
> 2025 年的一个真实案例：某 AI 创业公司将 LLM 提示词构建逻辑封装在 `ContentModerationUseCase` 内部，对外暴露的请求模型是简单的 `ModerateTextRequest { text: string }`，响应模型是 `ModerationResult { isToxic: boolean, score: number }`。当从 GPT-4 切换到 Claude 3 时，请求/响应模型完全不变——**业务核心对 LLM 提供商的变化零感知**。这正是 Bob "请求/响应模型是简单数据结构"规则在 AI 时代的兑现。

## 本章小结

第20章把第19章的"层次"理论**落到业务逻辑上**，给出了整洁架构同心圆最内两层的精确定义：

|组件|层次|距 I/O 距离|职责|依赖方向|
|---|---|---|---|---|
|**业务实体**​|最高层|最远|关键业务逻辑 + 关键业务数据|不依赖任何外部|
|**用例**​|次高层|较远|特定场景下的应用业务规则|依赖业务实体|
|**请求模型**​|较低层|较近|简单的输入数据结构|由 Controller 创建并传入|
|**响应模型**​|较低层|较近|简单的输出数据结构|由用例创建并传出|

### 三个核心定律

**定律一：业务实体是最高层的策略**

业务实体距 I/O 最远，变更最少、原因最重要。它是系统的"不变内核"。

**定律二：用例依赖业务实体，反之不成立**

这是第19章层次规则的直接应用——低层依赖高层。

**定律三：跨边界数据必须是简单数据结构**

请求模型和响应模型不能引用业务实体，即使数据相似。因为它们变更原因不同，强行共享会违反 CCP 和 SRP。

### 贯穿全书的位置

第20章是"整洁架构模型"的**内圈奠基**：

- **第19章**：层次的度量标准——距 I/O 的距离
- **第20章**​ ← **本章**：业务逻辑的内圈结构——业务实体（最高层）+ 用例（次高层）
- **第21章**（后续）：尖叫的架构——让架构"喊出"业务意图
- **第22章**（后续）：整洁架构——同心圆模型的最终呈现

**本章的核心金句**：

> 业务逻辑是一个软件系统存在的意义，属于核心功能，是系统用来赚钱或省钱的那一部分代码。这些业务逻辑应该保持纯净，不要掺杂用户界面和数据库相关的东西。其他低层次的概念应该以插件形式接入到系统中。

这句话实际上是**整个整洁架构模型的浓缩**——后续章节的同心圆、依赖规则、端口与适配器，都是从这句话展开的。

### 现代工业的批判性补充

> ⚠️ **三个需要更新的视角**：
> 
> **1. 业务实体的"纯度"在现代语言中更具挑战**
> 
> Bob 2017 年讨论业务实体时，主要以 Java/C# 的 OO 语言为背景。今天：
> 
> - **函数式语言**（Haskell、Elixir）：业务实体可能是纯函数 + 不可变数据
> - **动态语言**（Python、Ruby）：业务实体的"纯度"需要工具守护（ArchUnit、类型检查）
> - **AI 驱动开发**：AI 生成的代码倾向于把 ORM 注解、JSON 序列化逻辑直接写在实体上——必须通过架构适应度函数（Architecture Fitness Functions）在 CI 中强制"实体纯净性"
> 
> **2. 用例的粒度需要审慎评估**
> 
> Bob 原书暗示"一个用例 = 一个类"。现代工业实践发现：
> 
> - **过细的用例**（每个字段操作一个用例）导致类爆炸
> - **过粗的用例**（一个用例涵盖整个用户旅程）导致上帝类
> - **正确的粒度**：一个用例 = 一个完整的业务操作（如 `CreateOrder`、`CancelOrder`、`ApproveExpenseClaim`）
> 
> 2025 年的真实案例：某 FinTech 公司最初为每个字段验证创建一个用例，导致 200+ 个用例类；重构后合并为 20 个业务操作级用例，代码量减少 60%，可维护性显著提升。
> 
> **3. 请求/响应模型的"映射经济学"**
> 
> Bob 强调"请求/响应模型是简单数据结构"是正确的，但现代工业补充了**映射的经济学判断**：
> 
> - **结构不同**​ → 映射有价值（防御性转换、隐藏内部细节）
> - **结构相同**​ → 1:1 映射是无价值的仪式，应该消除
> - **CQRS 读操作**​ → 直接投影到响应模型，完全绕过业务实体和映射
> 
> 这是 Bob 原书未能充分展开、但今天必须纳入的现代实践——**架构不应为了"看起来整洁"而增加无价值的映射层**。

## 第19-20章在全书中的位置

第19章和第20章是**"整洁架构模型"的真正奠基**。如果说：

- **第15章**回答了"为什么"——保持可选项
- **第16章**回答了"战术"——通过对用例的解耦、对分层的解耦获得独立性
- **第17章**回答了"在哪里画边界"——在变更轴处，依赖指向核心
- **第18章**回答了"边界跨越时发生了什么"——源码依赖、控制流、数据结构、通信代价
- **第19章**​ ← **本章**：回答了"如何度量层次"——距 I/O 的距离
- **第20章**​ ← **本章**：回答了"业务逻辑如何分层"——业务实体（最高层）+ 用例（次高层）

后续章节将展开：

- **第21章 尖叫的架构**：让架构"喊出"业务意图——这是层次理论的业务导向
- **第22章 整洁架构**：同心圆模型——这是层次理论的最终可视化

**第19-20章的核心洞察值得铭记**：

> 软件系统是一系列策略的集合。策略的层次由"距 I/O 的距离"度量。距 I/O 最远的是业务实体（最高层），其次是用例（次高层）。源码依赖必须始终指向高层。跨边界数据必须是简单数据结构。

当你下次设计系统业务逻辑时，问自己三个问题：

1. **这个策略距 I/O 有多远？**（度量层次）
2. **源码依赖指向高层了吗？**（验证依赖方向）
3. **跨边界数据是简单的吗？**（验证数据结构）

这三个问题构成了"整洁架构"在业务逻辑层面的**完整性检验**。无论技术栈如何演变，只要你希望系统是"软"的（可被廉价改变），你就必须遵守这三个约束。

> 💡 **最终洞见**：第19-20章的"策略与层次"+"业务逻辑"，不是一种"架构风格"，而是**架构的几何学**——它给出了一个客观的坐标系，让"高层/低层"这种模糊直觉变成了可度量的几何属性。
> 
> 这就是为什么 2024-2026 年的工业实践——六边形架构、模块化单体、Serverless、微服务内部架构、AI 系统架构——都自觉或不自觉地遵循了这两章的原则：
> 
> - **六边形架构**：核心域（业务实体）距 I/O 最远，适配器（低层）依赖核心
> - **模块化单体**：在源码层次强制业务实体与用例的边界
> - **Serverless**：Lambda 函数内部依然是"业务实体 + 用例 + 端口"的结构
> - **AI 系统**：LLM 提供商作为最低层插件，内容审核策略作为最高层业务实体
> 
> Bob 在 2017 年建立的坐标系，今天在云原生、AI 驱动开发、多端交付的时代不仅没有过时，反而成为了架构设计的"万有引力定律"——**无论技术细节如何变化，业务实体始终是系统的最高层，源码依赖始终指向它**。
> 
> 当你评估任何一种架构风格、任何一种框架、任何一种技术选型时，回到 Bob 的两个问题：
> 
> 1. **它是否让业务实体保持了最高层的地位？**
> 2. **源码依赖是否始终指向业务实体？**
> 
> 如果答案是"是"，那么无论它看起来多么时髦或多么古老，它都是正确的架构。如果答案是"否"，那么无论它多么流行，它都在违背整洁架构的第一定律。
