# 产品

## 视频销售网站的业务全景

Bob 在书中描述的系统是一个线上收费视频网站，业务规则如下 ：

- **个人用户**：支付一个价格可流式观看视频；支付更高的价格可下载视频并永久拥有
- **企业用户**：仅限流式播放（不能下载）；批量购买可享受数量折扣；且**购买者与观看者通常不是同一人**
- **视频作者**：需要提供视频文件、文字描述，以及附带习题、问题、解答、源代码等辅助材料
- **管理员**：需要新增视频系列、向系列中添加/删除视频、为各种授权类型设定价格

## 产品的架构意义

> 💡 **第一性原理解读**：这个产品描述看似平常，但蕴含着架构第一性原理的关键线索——**变更源头**。
> 
> 当我们剥离所有的技术细节（Web、数据库、框架），回到产品本身，会发现一个本质事实：**系统不是为了"运行"而存在，而是为了"响应变更"而存在**。
> 
> 视频销售网站的"存在理由"不是"它能跑在服务器上"，而是：
> 
> - 个人用户的购买偏好会改变（想要新的授权模式）
> - 企业用户的批量折扣规则会改变（季节性促销）
> - 视频作者上传的辅助材料类型会扩展（增加交互式测验）
> - 管理员的定价策略会演化（动态定价、订阅制）
> 
> **这四类人就是系统未来的四类变更源头**。架构的第一性原理告诉我们：必须识别变更源头，并将它们隔离在独立的物理边界中，使得"为个人用户做的变更"不会影响"为企业用户做的变更"。
> 
> 这正是单一职责原则（SRP）在架构尺度的应用——**一个组件不应该有两个变更原因；如果有，就拆开**。

### 工业对照：2026 年"产品驱动架构"的现代实践

2026 年的工业实践验证了这种"从产品反向推导架构"的方法论：

**1. 用例作为架构的一等公民**

Insper 的 MLOps 课程资料明确指出，在现代整洁架构落地中：

> 判断一个类属于哪一层的实用启发式：如果它随业务变化而变化 → Entity 或 Use Case；如果它随接口变化而变化（REST → gRPC）→ Interface Adapter；如果它随库升级而变化（Spring Boot 版本、JPA dialect）→ Frameworks & Drivers 。

这与 Bob 的"产品 → 用例 → 组件"推导链完全吻合——**业务变化是架构分层的第一推动力**。

**2. 电商平台的整洁架构验证**

CS Topics 的资料给出了一个直接相关的工业案例：

> 电商平台（如大型市场）：整洁架构将动态定价、库存分配和结账规则与 UI 渲染和支付网关集成隔离开来；当支付提供商变更时，只有适配器代码需要修改 。

这正是视频销售网站案例的现代工业翻版——定价规则（企业批量折扣、个人下载溢价）是业务核心，支付网关是可替换的适配器。

# 用例分析

## 四个角色与用例图谱

Bob 通过用例分析识别出**四个主要角色（Actor）**​ ：

|角色|核心关注点|典型用例|
|---|---|---|
|**Viewer（观看者）**​|浏览和观看视频|View Catalog as Viewer、Watch Video|
|**Purchaser（购买者）**​|购买授权|View Catalog as Purchaser、Purchase Video License、Upgrade License|
|**Administrator（管理员）**​|管理内容和定价|Add Video、Set Pricing、Manage Series|
|**Video Author（视频作者）**​|提供内容|Upload Video、Supply Metadata|

根据单一职责原则，**这四个角色将成为系统变更的主要驱动力**。每当新增或修改功能时，都是在为这四个角色中的某一个服务。因此，我们希望将系统分区，使得针对一个角色的变更不会影响其他角色 。

## 抽象用例的设计洞察

Bob 在用例图中使用了一个精妙的抽象：

> 注意图 33.1 中央的虚线用例。它们是**抽象用例（abstract use cases）**。抽象用例设定通用策略，由其他用例具体化。正如你所见，"View Catalog as Viewer"和"View Catalog as Purchaser"两个用例都继承自"View Catalog"抽象用例 。

Bob 坦诚地指出：

> 一方面，创建这个抽象并非严格必要——如果把抽象用例从图中去掉，整体产品的功能也不会受损。另一方面，这两个用例如此相似，我认为明智的做法是及早识别这种相似性，并找到统一的方式 。

## 刻意的简化

Bob 明确说明：

> 图 33.1 中显示的用例并非完整列表。例如，你找不到登录或登出用例。省略的原因仅仅是为了控制本书中问题的规模 。

> ⚠️ **批判性洞见**：这是本章最容易误导读者的地方。读者可能误以为"一个真实的视频销售网站只需要这几个用例"。**错**。Bob 的省略是教学性的简化，不是工程性的完整建模。在真实的 cleancoders.com 中，登录/登出、支付集成、邮件通知、许可证校验、反盗版 DRM 等都是核心用例。

这意味着我们在学习此案例时，应该：

- **学习推导方法**，而非记住具体用例清单
- **理解抽象用例的取舍**——它不是免费的，会增加组件层级的复杂度（后面"组件架构"一节会看到 Catalog View 和 Catalog Presenter 这两个特殊组件就是为这个抽象服务的）
- **认识到架构推导是迭代的**——第一轮的用例分析永远不会是最终版

### 工业对照：2026 年用例建模的现代实践

**1. 用例即端口（Use Case as Port）**

2025 年 DeepWiki 的资料给出了视频销售案例的现代实现映射：

> 用例层组件：Viewer Use Cases、Purchaser Use Cases、Admin Use Cases、VideoAuthor Use Cases

每个角色的用例被组织为独立的用例组件，这与 Bob 的"按角色分区"完全一致。

**2. 用例接口的现代形态**

```
// Use Case (application layer)
interface CreateOrderUseCase {
    execute(input: CreateOrderInput): Promise<CreateOrderOutput>
}

// Input/Output ports (defined by use case)
interface CreateOrderInput {
    userId: string
    items: OrderItem[]
}
interface CreateOrderOutput {
    orderId: string
    status: string
}
```

tessl.io 的资料给出了这一现代模板 ：用例通过输入端口和输出端口与外界通信，**用例本身包含单一职责（单一工作流）、依赖抽象（端口）而非具体实现、编排实体和网关、不包含展示逻辑（格式化、HTTP、UI）**。

**3. AI 时代用例建模的延伸**

在 2026 年的 LLM 驱动应用中，"Upload Video"用例可能进一步拆分为：

- `UploadVideoUseCase`（业务编排）
- `TranscribeVideoUseCase`（调用 AI 转录）
- `GenerateMetadataUseCase`（调用 LLM 生成元数据）

每个都是独立的用例组件，共享同一个 `VideoRepository` 端口。这验证了 Bob 的预见——**用例分析是应对业务复杂化的核心工具**。

# 组件架构

## 从用例到物理组件的推导

Bob 给出了初步的组件架构（图 33.2）：

> 图中的双线代表架构边界（一如既往）。你可以看到典型的 Views、Presenters、Interactors、Controllers 分区。你还看到我按对应的角色对每个类别进行了拆分。图 33.2 中的每个组件都代表一个潜在的 .jar 文件或 .dll 文件。每个组件将包含分配给它的 Views、Presenters、Interactors 和 Controllers 。

关键设计决策：

**1. 按角色 × 按技术层级 的二维切分**

```
角色维度 →    Viewer    Purchaser    Admin    VideoAuthor
技术层级 ↓
Views          ✓          ✓          ✓          ✓
Presenters     ✓          ✓          ✓          ✓
Interactors    ✓          ✓          ✓          ✓
Controllers    ✓          ✓          ✓          ✓
```

**2. 抽象用例的物理映射**

> 注意 Catalog View 和 Catalog Presenter 这两个特殊组件。这就是我处理抽象 View Catalog 用例的方式。我假设这些 Views 和 Presenters 将被编写为这些组件中的抽象类，而继承组件将包含从这些抽象类继承的 View 和 Presenter 类 。

**3. 组件与部署单元的分离**

Bob 提出了一个极具洞察力的问题：

> 我真的会把系统拆分成这么多组件，并作为 .jar 或 .dll 文件交付吗？

他的回答是"是，也不是"：

> 我们会按照组件将编译和构建环境分开，以便单独构建对应组件。但是我们仍然可以将组件组合在一起进行交付。比如，我们可以将其交付为 5 个 .jar 文件，按照视图、展示器、交互器、控制器、工具类，按照这种分类进行组合一起交付 。

## 组件切分的深层原理

> 💡 **第一性原理解读**：组件架构这一节揭示了整洁架构的"物理维度"——**组件是部署的最小单元，是变更的原子单位**。
> 
> 前面章节讲的是"逻辑分层"（Entities → Use Cases → Interface Adapters → Frameworks），本章讲的是"物理切分"（哪些类应该编译进同一个 .jar/.dll）。
> 
> Bob 在这里兑现了第 12-16 章的组件原则：
> 
> - **REP（复用/发布等同原则）**：组件的颗粒度应该与复用/发布的颗粒度一致
> - **CCP（共同闭包原则）**：因相同原因而变更的类应该在同一个组件中
> - **CRP（共同复用原则）**：总是一起复用的类应该在同一个组件中
> 
> 按角色切分组件，是因为**同一角色的用例因相同业务原因而变更**（CCP）；将 View/Presenter/Interactor/Controller 放在一起，是因为**它们共同实现一个用例**（CRP）。
> 
> 但 Bob 的"是，也不是"回答更为精妙——**组件是"潜在"的部署单元，不是"必然"的部署单元**。在系统早期，你可以将所有组件打包成单一的 .jar 交付；当某个组件（比如企业采购用例）需要独立部署或独立扩展时，你可以将它拆分为独立的 .jar。这种"保持可选项"的思想，正是第 15 章的核心原则在组件尺度的应用。

### 工业对照：2026 年组件组织的四种流派

现代工业实践在"如何组织组件/包"上有四种主流方式 ：

**1. Package by Layer（按技术层分包）**

```
com.videosales/
├── web/          # Controllers
├── business/     # Use Cases
└── persistence/  # Repositories
```

- **优点**：简单易懂，技术分离清晰
- **缺点**：不体现业务领域；业务功能的变更往往横跨多个层；容易破坏架构边界

**2. Package by Feature（按业务功能分包）**

```
com.videosales/
├── viewer/       # View Catalog, Watch Video
├── purchaser/    # Purchase License, Upgrade License
├── admin/        # Add Video, Set Pricing
└── author/       # Upload Video, Supply Metadata
```

这是 Bob 在本章案例中隐含推荐的方式——**顶层包"喊出"了业务领域**。

**3. Ports and Adapters（端口与适配器）**

```
com.videosales/
├── domain/          # Entities + Use Cases + Ports
└── infrastructure/  # Adapters (Web, DB, Frameworks)
```

**4. Package by Component（按组件分包）**

Simon Brown 推荐的方式，与 Ports and Adapters 类似，但将后端基础设施与领域打包在一起，作为拆分微服务的准备。

> 💡 **创新洞见**：Bob 在 2017 年的案例实际上超越了单纯的"Package by Feature"——他是**按"角色 × 技术层级"的矩阵切分**。这种矩阵切分的现代意义在 2026 年愈发凸显：
> 
> 当视频销售网站需要支持新的交付渠道（如移动 App、智能 TV App、AI Voice Assistant）时：
> 
> - **按角色切分**保证"Viewer 用例的变更"不影响"Purchaser 用例"
> - **按技术层级切分**保证"UI 技术变更"不影响"业务规则"
> - **矩阵切分**保证两者同时满足
> 
> 2026 年的实践（如 Insper MLOps 课程资料）推荐的包结构正是这种思想的兑现 ：
> 
> ```
> com.example.product/
> ├── domain/                    # Entities layer
> │   ├── Product.java
> │   └── ProductRepository.java # Port
> ├── application/               # Use Cases layer
> │   ├── ProductService.java
> │   └── ProductDTO.java
> └── adapter/                   # Interface Adapters layer
>     ├── in/
>     │   ├── ProductController.java
>     │   └── ProductRecordIn.java
>     └── out/
>         ├── ProductJpaAdapter.java
>         └── ProductMapper.java
> ```
> 
> 这种结构让"业务领域在顶层包中喊出来"（domain/application 是业务概念），同时保持技术层级的隔离。

# 依赖关系管理

## 依赖规则的兑现

Bob 在这一节明确了依赖管理的核心纪律：

> 所有依赖都单向穿越边界线，且始终指向包含更高层级策略的组件 。

具体到视频销售网站的组件架构：

```
依赖方向（严格向内）：
Entities ← Use Cases ← Interface Adapters ← Frameworks & Drivers
              ↑                                      ↑
              └── Viewer/Purchaser/Admin/Author     └── Web/DB Frameworks
                   Use Cases
```

**控制流与依赖流的反向性**：

> 控制流从左到右，但大多数依赖箭头指向左侧——符合依赖规则：所有依赖都指向包含更高层级策略的组件 。

这是一个关键洞察：**控制流**和**依赖流**可以相反方向流动。例如：

1. **控制流**：Viewer Controller → View Catalog Interactor → Catalog Presenter → Catalog View
2. **依赖流**：Catalog View → Catalog Presenter → View Catalog Interactor → Viewer Controller

控制流向右，依赖流向左——这是依赖反转原则（DIP）在架构尺度的体现。

## 依赖管理的工业级纪律

2026 年的工业实践将 Bob 的依赖规则进一步具体化为可执行的纪律 ：

**纪律一：依赖永远向内**

```
❌ 违反：Entity 导入基础设施层的 ORM 装饰器
✅ 正确：Entity 是普通对象；在 Repository（适配器层）中映射到 ORM
```

**纪律二：实体保持纯净**

```
❌ 违反：Entity 使用 @Entity 装饰器（来自 TypeORM）
✅ 正确：Entity 是纯 TypeScript/Java 对象；Repository 在基础设施层处理框架映射
```

**纪律三：框架代码置于边缘**

```
❌ 违反：在 Use Case 中实例化具体的 PostgresRepository
✅ 正确：Use Case 依赖 IRepository 接口；DI 在组合根提供具体实现
```

**纪律四：用编译器强制依赖规则**

> 许多团队说"我们通过良好的纪律和代码审查来强制这一原则，因为我们信任开发人员。"这很好，但在预算和截止日期面前从未被尊重。
> 
> 有些团队使用静态分析工具在构建时检查和自动强制架构违规。但我个人希望在可能的情况下使用编译器来强制我的架构 。

这是 2026 年依赖管理的最新前沿——**用编译器和包可见性强制架构规则**，而非依赖"工程师的自律"：

- **Java**：使用 Java 9+ 的 Module System 强制封装
- **Kotlin**：使用 internal 可见性修饰符
- **Rust**：使用 crate 和 mod 系统
- **静态分析**：ArchUnit（Java）、NetArchTest（.NET）、dependency-cruiser（JS/TS）

### 工业对照：2026 年依赖管理的现代工具链

**1. ArchUnit 强制架构规则**

```
@AnalyzeClasses(packages = "com.videosales")
class ArchitectureTest {
    @ArchTest
    static final ArchRule domain_should_not_depend_on_infrastructure =
        noClasses().that().resideInAPackage("..domain..")
            .should().dependOnClassesThat()
            .resideInAPackage("..infrastructure..");
}
```

**2. 包可见性强制封装**

```
com.videosales/
├── domain/           # 公开 Entity 和 Repository 接口
│   ├── Product.java  # public
│   └── ProductRepository.java  # public（端口）
├── application/      # 公开 Use Case 接口
│   └── ProductService.java  # public
└── adapter/          # 内部实现，包私有
    ├── in/
    │   └── ProductController.java  # public（框架入口）
    └── out/
        ├── ProductJpaAdapter.java  # package-private
        └── ProductMapper.java      # package-private
```

ProductJpaAdapter 和 ProductMapper 使用包私有可见性，确保它们不能被 domain 或 application 层反向依赖 。

**3. 视频销售案例的现代依赖映射**

DeepWiki 给出的视频销售案例组件依赖图 ：

```
Database Components → Entity Components → Use Case Components → Presentation Components
   (最低策略)           (企业规则)         (应用规则)           (最外圈细节)
   
依赖方向：Presentation → Use Cases → Entities → Database
控制流向：Presentation ← Use Cases ← Entities ← Database
```

注意：Database Components 在最左侧，但依赖箭头指向它——这意味着 Use Case Components 依赖 Database 的**接口**（端口），而 Database 的具体实现在 Frameworks & Drivers 层。这正是依赖反转的兑现。

> 💡 **创新洞见**：Bob 在 2017 年提出的"依赖单向穿越边界"原则，在 2026 年已经从"设计纪律"进化为"编译器强制的工程实践"。
> 
> 这一进化的第一性原理是：**依赖规则是架构的"物理定律"，应该用物理手段（编译器）强制，而非社会手段（代码审查）强制**。
> 
> 正如 vranec 的阅读笔记所指出的：
> 
> > "所有四种打包方式在依赖流上都是相同的。但组件的可见性可能不同。如果某些组件在同一个包中，那么我们可以使用 Java 中的默认可见性。Brown 先生建议使用编译器（而不仅仅是纪律）来强制依赖规则。"
> 
> 这意味着 2026 年的架构师不仅有"设计架构"的责任，还有"用工具和语言特性强制架构"的责任。当一个 Entity 意外地导入了 ORM 框架类时，构建应该**失败**，而不是等到代码审查或生产事故时才发现。

第33章的真正贡献，是**将全书的所有原则组装成了一个可运行的架构**——从产品到用例，从用例到组件，从组件到依赖。

## 两个维度的分离

Bob 在小结中明确了架构的两个分离维度 ：

**维度一：基于 SRP 的角色分离**

- 四个角色（Viewer、Purchaser、Admin、Video Author）是四个独立的变更源头
- 每个角色的用例应该被隔离在独立的组件中
- 目标是"因不同原因而变更"的组件相互分离

**维度二：基于依赖规则的策略层级分离**

- 不同层级的策略（企业规则 vs 应用规则 vs 接口适配 vs 框架细节）
- 依赖永远指向更高层级的策略
- 目标是"以不同速率变更"的组件相互分离

> 两个维度的共同目标：**将因不同原因、以不同速率变更的组件相互分离**​ 。

## 案例的工业定位

|维度|视频销售网站案例|现代工业对照|
|---|---|---|
|**产品建模**​|4 个角色、抽象用例 View Catalog|电商平台：动态定价、库存分配、结账规则与 UI/支付隔离|
|**用例分析**​|按角色识别用例，抽象公共策略|Use Case 即 Port，定义输入/输出端口|
|**组件架构**​|角色 × 技术层级的矩阵切分|Package by Feature + 端口适配器|
|**依赖管理**​|依赖单向穿越边界，指向高层策略|编译器强制依赖规则，包可见性封装|

第33章是**整洁架构原则的第一次完整组装**：

- **第 1-5 章**：编程范式与 SOLID 原则（逻辑纪律）
- **第 6-15 章**：组件原则（物理纪律）
- **第 16-21 章**：整洁架构的边界与依赖规则（架构纪律）
- **第 22-29 章**：服务、测试、嵌入式架构等具体场景

- **第 33 章**​ ← **本章**：将所有原则应用于真实案例

> 💡 **最终洞见**：第33章的第一性原理是**"架构是从产品反向推导的物理结构"**。
> 
> 大多数架构师的错误思维是"技术正向推导"：
> 
> - ❌ "我们用 Spring Boot，所以 Controller/Service/Repository 三层架构"
> - ❌ "我们用 React，所以前端用组件化架构"
> - ❌ "我们用微服务，所以按服务拆分"
> 
> Bob 演示的正确思维是"产品反向推导"：
> 
> - ✅ "我们有四类用户，他们是独立的变更源头，所以按角色分区"
> - ✅ "View Catalog 对 Viewer 和 Purchaser 有共性，所以提取抽象用例"
> - ✅ "控制流从 Controller 到 Interactor 到 Presenter 到 View，依赖流反向"
> - ✅ "组件是潜在的部署单元，可以按需拆分"
> 
> 2025-2026 年的工业实践完全验证了这一推导链：
> 
> - **产品驱动**：电商平台的动态定价、库存分配、结账规则被隔离为业务核心，UI 和支付网关是可替换适配器
> - **用例即端口**：每个用例通过输入/输出端口与外界通信，不依赖具体框架
> - **编译器强制**：依赖规则不再是"工程师的自律"，而是编译器和包可见性强制的物理定律
> - **组件灵活性**：组件是潜在的部署单元，可以按需打包为单一 .jar 或多个 .jar
> 
> 对于正在读《架构整洁之道》的你，第33章应该成为你面对任何新系统时的"架构推导模板"：
> 
> 1. **第一步**：列出所有 Actor（角色）——他们是变更源头
> 2. **第二步**：为每个 Actor 识别 Use Cases——抽象公共策略
> 3. **第三步**：按"角色 × 技术层级"切分组件——应用 CCP 和 CRP
> 4. **第四步**：强制依赖单向向内——用编译器而非纪律来保证
> 5. **第五步**：组件作为潜在部署单元——保持"按需拆分"的可选项
> 
> 正如 vranec 的阅读笔记所坦言："我记得对这一章感到失望。对于案例研究来说太短了。而且这个架构并没有向我'喊出'视频销售，因为我首先看到的是技术边界。"
> 
> 这个批评是公正的——Bob 的案例确实"技术边界先于业务领域"。但这是教学性的妥协：在单章篇幅内，Bob 必须优先演示"原则如何组装"，而非"领域如何表达"。**真正的"领域 scream"需要结合第 34 章"缺失的一章"中的 Package by Feature 思想**——这正是下一章的内容。
> 
> 带着这个认识去读第 34 章，你会看到 Bob（实际上是 Simon Brown）如何补齐最后一块拼图：**如何让顶层包结构"喊出"业务领域，而不仅仅是技术分层**。这将与前文所有原则结合，形成整洁架构的完整工业落地范式。
