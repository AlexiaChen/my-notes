
第34章是全书的"补天之章"——由 Simon Brown 撰写，讨论一个被前文忽略但极其致命的问题：**即使你有完美的类设计、组件边界、依赖规则，如果在"实现细节"上处理不当，整个架构依然会崩坏**。这一章用"在线书店的订单查询功能"这一个微小用例，展示了四种代码组织方式（按层封装、按功能封装、端口和适配器、按组件封装），并揭示了一个令人震惊的事实——**如果访问权限修饰符没有被严格使用，这四种看似截然不同的封装方式，最终会劣化成完全相同的东西**。

这一章的真正价值在于：它将整洁架构从"逻辑设计"拉回到"物理落地"——**架构不只是画图，更是访问修饰符、包结构、编译器强制**。

# 按层封装

## 传统的水平分层

Simon Brown 以一个在线书店的"查看订单状态"用例为例，展示了第一种也是最经典的组织方式——按层封装（Package by Layer）：

```
com.company.myapp/
├── web/
│   └── OrdersController.java          // 处理 HTTP 请求
├── service/
│   ├── OrdersService.java             // 业务逻辑接口
│   └── OrdersServiceImpl.java         // 业务逻辑实现
└── repository/
    ├── OrdersRepository.java          // 数据访问接口
    └── JdbcOrdersRepository.java      // JDBC 实现
```

核心特征：

- **水平切片**：代码按技术角色切分（Web、Service、Repository）
- **严格分层**：每一层只能依赖相邻的下层
- **依赖向下**：OrdersController → OrdersService → OrdersRepository

Martin Fowler 在《Presentation Domain Data Layering》中也指出，采用这种分层架构是入门的好方法。许多书籍、教程、培训课程和示例代码都会引导你走上创建分层架构的道路。

## 按层封装的三大优势

1. **简单快速**：非常适合项目的早期阶段，无需大量复杂性即可启动并运行
2. **技术关注点分离清晰**：web、业务逻辑、持久化各居其位
3. **开发者熟悉**：大多数开发者都熟悉这种 MVC 启发式的方法

## 按层封装的三大缺陷

> ⚠️ **第一性原理批判**：按层封装的根本问题在于——**它优化的不是业务变更，而是技术关注点**。

**缺陷一：无法反映业务领域**

分层架构不"喊出"任何关于业务领域的信息。把两个来自完全不同业务领域的分层架构并排放在一起，它们看起来惊人地相似：都是 web、services、repositories。正如前文中所述，正如 Uncle Bob 所说，分层架构并没有"喊出"业务领域。

**缺陷二：规模扩展失灵**

一旦软件规模和复杂性增长，你会发现仅有三个大代码桶是不够的，需要进一步思考模块化。

**缺陷三：跨层调用的诱惑（最致命）**

```
// 常见的错误：跨层调用
public class OrdersController {
    @Autowired
    private OrdersRepository repository;  // 直接依赖 Repository 层，跳过 Service 层
}
```

这是按层封装最隐蔽的陷阱——**Web 控制器可以直接访问数据层，绕过业务逻辑层**。这在"业务逻辑层要控制权限"的场景下尤其不合理。

### 工业对照：2026 年按层封装的定位

2026 年的工业实践对按层封装给出了精确的定位：

**ByteLedger 2026 年的判断**：

> 按层封装（controllers/、models/、services/）在项目超过约 10 个功能后就会崩溃——一个功能变更需要在六个文件夹中进行"霰弹式手术"（shotgun surgery）。

**JavaThinking 2026 年的建议**：

> 按层封装最适合小型项目、范围聚焦的微服务，或刚接触模块化设计的团队。对于中型到大型项目，应该迁移到按功能封装或 DDD。

**2026 年的具体建议**：

```
❌ 脆弱的按层结构（>10 个功能后崩溃）
controllers/ user.js order.js
models/ user.js order.js
services/ user.js order.js

✅ 可扩展的功能优先结构
features/
├── user/ controller.js model.js service.js user.test.js
└── order/ controller.js model.js service.js order.test.js
```

# 按功能封装

## 垂直切分：让业务领域"喊出来"

按功能封装（Package by Feature）是第二种组织方式——垂直切分，根据相关的功能、业务概念或聚合根（领域驱动设计术语）来切分：

```
com.company.myapp/
├── orders/
│   ├── OrdersController.java           // 所有订单相关的类
│   ├── OrdersService.java              // 都放在同一个包中
│   ├── OrdersServiceImpl.java
│   ├── OrdersRepository.java
│   └── JdbcOrdersRepository.java
└── users/
    ├── UsersController.java            // 所有用户相关的类
    ├── UsersService.java               // 都放在同一个包中
    └── UsersRepository.java
```

核心特征：

- **垂直切片**：代码按业务功能切分
- **高内聚**：包内的所有类型都执行与领域相关的功能
- **业务领域可见**：包名直接反映业务概念

## 按功能封装的优势

**优势一：业务领域自我表达**

系统的主要目的可以从代码结构中被推断出来。

**优势二：高内聚、低耦合**

正如 David Stech Tips 的资料指出的：

> 在按功能封装风格中，我们理想情况下只在一个包中更改类——与我们正在开发的功能相关的那个包，因此内聚性高；而且包之间的依赖很少，因此耦合性低。

**优势三：代码定位容易**

相关代码都在一起，而不是分散在不同的包中。Java Practices 的经典论断是：

> 维护程序员需要进行大量搜索来找到所需项——在按功能封装中，由于给定任务所需的所有项通常在同一目录中，因此极大地减少了在目录之间导航的需要。

**优势四：可删除性测试**

> 一个有趣的测试：如果删除一个功能可以简化为单次操作——删除一个目录，那么这个项就具有最大模块化。

## 按功能封装的局限

> 💡 **批判性洞见**：按功能封装并非银弹。

**局限一：功能粒度模糊**

对于"功能"的理解没有清晰指引——一个功能包应该多大？多大算过小？多大算过大？

**局限二：基础设施代码可能绕过领域**

> 基础设施代码可能绕过领域调用应用程序的另一部分代码。

**局限三：跨层跳跃的可能性**

> 有可能作弊并跳过层级。

### 工业对照：2026 年按功能封装的主流化

**ByteLedger 2026 年明确**：

> 同变更的文件应该放在一起，而不是按类型分散。功能文件夹具有可扩展性；层文件夹不具有。

**JavaThinking 2026 年推荐**：

> 对于具有不同业务功能的中大型项目，按功能封装是最佳选择。功能自包含，更容易让新开发人员上手（例如"在 payment 包上工作"），减少跨层依赖。

**2026 年的现代形态**（以 Node/TypeScript API 为例）：

```
src/
├── features/
│   ├── auth/
│   ├── orders/
│   └── users/
├── shared/              # 纯工具，无功能导入
│   ├── db.ts
│   ├── logger.ts
│   └── errors.ts
├── app.ts               # express/fastify 设置
└── server.ts            # 入口点
```

每个功能文件夹包含该功能的所有相关代码，shared/ 只包含真正的跨功能原语（错误、日志、配置加载器等），没有循环导入。

> 💡 **创新洞见**：2026 年的工业实践将"按功能封装"进一步发展为"**同变更文件共置（colocation）**"原则。这不仅是包组织方式，更是一种**架构哲学**——代码的组织应该映射业务的变更模式，而非技术的分类模式。
> 
> 这一原则的底层逻辑是：
> 
> - **变更是软件的唯一常量**——功能会变，技术栈也会变，但功能的变更频率远高于技术栈
> - **按层封装优化技术关注点**（Web 技术会变、持久化技术会变）
> - **按功能封装优化业务关注点**（订单功能会变、用户功能会变）
> - 因为业务变更频率 >> 技术变更频率，所以按功能封装更具可持续性

# 端口和适配器

## 内外分离：领域与实现细节的隔离

第三种组织方式——端口和适配器（Ports and Adapters），也称为六边形架构：

```
com.company.myapp/
├── domain/                    # 内部区域（领域）
│   ├── OrdersService.java     # 业务逻辑
│   ├── Order.java             # 领域实体
│   └── OrdersRepository.java  # 端口（接口）
└── infrastructure/            # 外部区域（基础设施）
    ├── OrdersController.java  # 适配器（Web）
    └── JdbcOrdersRepository.java  # 适配器（数据库）
```

核心规则：

> 只有外部代码能依赖内部代码，反之则不能。即细节依赖核心，核心不能依赖细节。

## 端口和适配器的本质

Simon Brown 明确指出：

> 正如 Uncle Bob 所说，诸如"端口和适配器""六边形架构""边界、控制器、实体"等方法，旨在创建业务/领域聚焦的代码与技术实现细节（如框架和数据库）独立且分离的架构。

这一架构的关键洞察：

- **内部区域**：包含了所有的领域概念（业务规则、实体、端口接口）
- **外部区域**：包含了与外界交互的部分（UI、数据库、第三方集成）
- **依赖方向**：只有外部代码能依赖内部代码，反之则不能

## 端口和适配器的优势

**优势一：业务核心完全独立**

领域代码不依赖任何框架、数据库、Web 技术。这使得：

- 业务核心可以被独立测试
- 业务核心可以被独立部署
- 适配器可以被独立替换（如从 SQL 切换到 NoSQL 而不改变业务逻辑）

**优势二：测试性极强**

可以隔离测试应用程序的核心，而不必担心适配器。

**优势三：模块化程度高**

可以独立开发和部署核心与适配器，这使其更易于管理和扩展。

### 工业对照：2026 年端口和适配器的现代实践

**TheLinuxCode 2026 年给出的"Feature Core + Ports"模式**：

```
com.acme.inventory/
├── core/          # 领域模型和业务规则
├── ports/         # 外部依赖的接口（数据库、队列、HTTP API）
├── adapters/      # 端口的实现
└── api/           # 暴露入站端点
```

这种包结构使得**在不撕裂核心的情况下交换外部依赖变得容易**。

**TheLinuxCode 进一步给出的"API + Internal"分割模式**：

```
com.acme.payments/
├── api/           # 外部 API
├── internal/      # 内部实现
│   ├── model/
│   └── ...
└── model/         # 共享领域类型
```

> 我把它们放在一个 internal 子包中，并阻止模块导出它。这使新类应该位于哪个包中变得显而易见。它也阻止人们"仅仅因为类在那里"就导入内部类。

**2026 年的编译器强制**：

Java 9+ 的 Module System 允许使用 `module-info.java` 文件声明公共 API 并隐藏内部包：

```
module com.company.app.user {
    exports com.company.app.user.api;
    // internal 包不被导出，对外部不可见
}
```

正如第33章所述，**强烈建议利用编译器来维护架构设计原理，而不要依赖个人自律和编译过程之后的工具**。

> 💡 **创新洞见**：端口和适配器在 2026 年已经从"架构风格"进化为"**编译器强制的物理边界**"。
> 
> 2017 年 Simon Brown 写这一章时，端口和适配器主要靠"包结构和纪律"来维持。2026 年的工业实践将其进一步硬化：
> 
> - **Java 9+ Modules**：用 `module-info.java` 强制封装
> - **包私有可见性**：internal 子包不导出
> - **路径别名**：TypeScript 的 `@/features/auth` 让 IDE 原生解析
> - **静态分析**：ArchUnit 在构建时检查架构违规
> 
> 这意味着端口和适配器不再只是"逻辑架构"，而是**编译器可以理解并强制的物理架构**。这是 Bob 在全书反复强调的原则——"用编译器执法，而非依赖自律"——在包组织尺度上的兑现。

# 按组件封装

## 面向服务的视角：粗粒度组件

第四种组织方式——按组件封装（Package by Component）：

> 按组件封装，目标是将一个粗粒度组件相关的所有类放入一个 Java 包中。

```
com.company.myapp/
└── orderscomponent/              # 订单组件（粗粒度）
    ├── OrdersController.java      // UI 层
    ├── OrdersService.java         // 业务逻辑
    ├── OrdersServiceImpl.java
    ├── OrdersRepository.java      // 数据访问接口
    ├── JdbcOrdersRepository.java  // 数据访问实现
    └── Order.java                 // 领域实体
```

核心定义：

> 组件定义：在一个执行环境（应用程序）中的、一个干净、良好的接口背后的一系列相关功能的集合。

## 按组件封装的本质

按组件封装可以看作是**前三种方式的混合**——它以一种面向服务的视角来构建软件系统，与微服务架构类似：

- 像端口和适配器模式将 Web 视为一种交付手段一样，"按组件封装"将 UI 与粗粒度组件分离
- 业务逻辑与持久化代码合并在一起，称为"组件"
- **组件是部署单元**——系统中能够部署的最小单位（在 Java 里就是 jar 文件）

## 按组件封装的关键纪律

**纪律一：public 类型越少，潜在的依赖关系就越少**

在按层封装中，`OrderService` 与 `OrderRepository` 需要 public 修饰符，因为包外的类需要依赖它们。但在按组件封装中，它们都在同一个包内，可以使用包私有（package-private）可见性。

**纪律二：组件内部关注点分离**

> 在组件中，需要关注重点隔离原则，这是组件内部的问题，使用者不需要关心。

**纪律三：最小化公开接口**

```
// 组件对外只暴露一个干净的接口
public interface OrdersComponent {
    OrderStatus getOrderStatus(OrderId orderId);
}

// 组件内部的所有类都可以是包私有的
class OrdersController { ... }        // package-private
class OrdersServiceImpl { ... }       // package-private
class JdbcOrdersRepository { ... }    // package-private
class Order { ... }                   // package-private
```

## 按组件封装的优势

**优势一：变更局部化**

> 如果我们需要编写和订单有关的代码，只有一个位置需要修改——OrdersComponent。

**优势二：面向服务**

提供了一种面向服务的视角，与微服务架构类似。

**优势三：微服务化的前提**

> 单体程序中的一个良好定义的组件，是微服务化架构的一个前提条件。

**优势四：综合了前三种方式的优点**

正如 Code Decoupling 的比较所示：按组件封装是"所有先前方式的混合方法，最小化了它们的缺陷"。

### 工业对照：2026 年按组件封装的现代意义

**Sngular 2024 年的总结**：

> 按组件封装可以看作是前两种方式的混合，因为每个组件可以有自己的内部分层或功能结构。代码被组织成自包含的组件，这些组件代表应用程序中可重用的子系统或模块。

**2026 年的现代组件化**：

```
src/
├── components/                      # 粗粒度业务组件
│   ├── orders/                      # 订单组件
│   │   ├── api/                     # 对外接口（public）
│   │   ├── internal/                # 内部实现（包私有）
│   │   │   ├── controller/
│   │   │   ├── service/
│   │   │   └── repository/
│   │   └── index.ts                 # 显式的公开接口
│   └── payments/                    # 支付组件
└── shared/                          # 跨组件共享
```

**组件是微服务的前提**：

单体程序中的一个良好定义的组件，是微服务化架构的一个前提条件。当你需要将订单组件独立部署时，它已经具备了清晰边界和最小化公开接口——只需将其打包为独立的服务即可。

> 💡 **创新洞见**：按组件封装在 2026 年的真正价值在于**它是"架构演进的期权"**。
> 
> 单体应用中的一个良好定义的组件，是微服务化架构的一个前提条件。这意味着：
> 
> - **Day 1**：你可以将所有组件打包成单一的 .jar 交付（如第33章所述）
> - **Year 1**：当订单组件需要独立扩展时，将其拆分为独立的微服务
> - **组件边界早已定义好**，拆分成本极低
> 
> 这正是 Bob 在全书中反复强调的"保持可选项"原则在组件尺度的兑现。按组件封装不是"微服务"，但它是"微服务的预备役"——**当你需要微服务时，组件边界让拆分成为单行操作，而非架构重构**。
> 
> 2026 年的工业实践验证了这一点：单体程序中的一个良好定义的组件，是微服务化架构的一个前提条件。

# 具体实现细节中的陷阱

## 陷阱一：访问权限修饰符的失效

这是本章最震撼的洞察——如果访问权限修饰符没有被严格使用，那么前面讨论的所有四种封装方式**最终会劣化成完全相同的东西**。

> 如果所有属性和方法都是 public，那么这四种模式将完全一样！完全一样，只是由于我们没有严格地使用访问权限修饰符！

具体表现：

- **按层封装中**：OrdersController 可以直接依赖 OrdersRepository（跳过 OrdersService），因为所有类都是 public
- **按功能封装中**：orders 包中的类可以直接依赖 users 包中的内部类，因为所有类都是 public
- **端口和适配器中**：基础设施层可以反向依赖领域层的内部细节，因为所有类都是 public
- **按组件封装中**：组件外部可以直接访问组件内部的 Service 和 Repository，因为所有类都是 public

## 陷阱二：跨层调用的诱惑

> 在按层封装结构中，OrdersController 可以在某些情况下绕过了 OrderService 类，直接调用 OrdersRepository，绕过业务逻辑层是不合理的，尤其是在业务逻辑层要控制权限的情况下。

这是一个具体的实现陷阱——即使你在架构图上画了三层，如果 OrdersController 和 OrdersRepository 都是 public，开发者会在截止日期压力下"抄近道"。

## 陷阱三：依赖方向的隐性倒置

> 一个主要的规则：只有外部代码能依赖内部代码，反之则不能。即细节依赖核心，核心不能依赖细节。

但如果内部代码（领域层）意外地导入了外部代码（框架/数据库）的 public 类，依赖规则就被悄无声息地破坏了。

## 解决方案：用编译器执法

> 采用静态分析工具约束不大持久，作者个人更倾向选择能够让编译器执法的做法。

具体手段：

1. **严格的访问修饰符**：默认使用最小可见性（包私有、private），仅在必要时升级为 public
2. **Java 9+ Module System**：用 `module-info.java` 强制封装
3. **静态分析工具**：ArchUnit、NetArchTest、dependency-cruiser 在构建时检查架构违规
4. **包结构强制**：利用编译器的包可见性规则

> ⚠️ **第一性原理解读**：这一节的真正洞见是——**架构不是画出来的，是编译器强制出来的**。
> 
> "我们依赖良好的纪律和代码审查来强制这一原则，因为我们信任开发人员。"这很好，但在预算和截止日期面前从未被尊重。
> 
> 许多团队说"我们通过良好的纪律和代码审查来强制这一原则，因为我们信任开发人员。"这很好，但在预算和截止日期面前从未被尊重。
> 
> 有些团队使用静态分析工具在构建时检查和自动强制架构违规。但我个人希望在可能的情况下使用编译器来强制我的架构。

### 工业对照：2026 年编译器执法的工业标准

**TheLinuxCode 2026 年明确**：

> 对于任何将被其他团队使用的库或服务，我将包拆分为外部 API 和内部实现。我避免暴露内部类，即使它们是 public。相反，我将它们放在 internal 子包中，并阻止模块导出它。

**ByteLedger 2026 年强调**：

> 用工具强制执行结构——lint 规则和路径别名胜过部落知识。

**2026 年的具体工具链**：

|语言|编译器强制手段|
|---|---|
|Java|Java 9+ Modules (`module-info.java`)、包私有可见性|
|Kotlin|`internal` 可见性修饰符|
|Rust|`crate` 和 `mod` 系统|
|TypeScript|路径别名 (`@/features/auth`)、`private` 字段|
|Go|`internal/` 包约定|

# 组织形式与封装的区别

## 组织形式 ≠ 封装

这是本章最微妙也最深刻的区分：

- **组织形式**（Organization Form）：代码在文件系统中的物理排列方式（按层、按功能、按组件）
- **封装**（Encapsulation）：代码对外部隐藏内部实现细节的程度（通过访问修饰符）

**关键洞察**：组织形式是"外在的骨架"，封装是"内在的纪律"。**没有封装的组织形式只是"看起来不错"，而非"真正的解耦"**。

## 四种组织形式的封装潜力

|组织形式|封装潜力|关键纪律|
|---|---|---|
|按层封装|低（跨层调用容易）|严格限制 public 类|
|按功能封装|中（包内高内聚）|使用包私有可见性|
|端口和适配器|高（内外分离）|内部包不导出|
|按组件封装|最高（最小公开接口）|组件外只暴露接口|

## 封装的第一定律

> public 类型越少，潜在的依赖关系就越少。

这意味着：

- 默认使用**最小可见性**
- 每个类、每个方法、每个字段都应该使用能满足需求的最小访问级别
- public 是一种"承诺"——一旦公开，就不能轻易改变

### 工业对照：2026 年封装的现代实践

**TheLinuxCode 2026 年的"API + Internal"模式**：

```
com.acme.payments/
├── api/           # 外部 API（公开）
├── internal/     # 内部实现（隐藏）
│   ├── model/
│   └── ...
└── model/        # 共享领域类型
```

> 这使新类应该位于哪个包中变得显而易见。它也阻止人们"仅仅因为类在那里"就导入内部类。

**JavaThinking 2026 年的建议**：

> 即使在良好的结构下，包也可能泄漏内部细节。使用这些技术强制执行边界：Java 9+ 模块：使用 module-info.java 文件声明公共 API 并隐藏内部包。

> 💡 **创新洞见**：组织形式与封装的区别，本质上揭示了**架构的"双重性"**：
> 
> - **逻辑架构**（Logical Architecture）：依赖规则、边界、同心圆——这是"设计意图"
> - **物理架构**（Physical Architecture）：包结构、访问修饰符、编译器强制——这是"设计落地"
> 
> 大多数架构师只关注逻辑架构（画图、定义边界），而忽视了物理架构（访问修饰符、编译器强制）。这就是"设计图纸很美好，代码实现很糟糕"的根本原因。
> 
> 2026 年的工业实践正在弥补这一鸿沟：
> 
> - **编译器强制**：Java 9+ Modules、Kotlin internal、Rust crate 系统
> - **静态分析**：ArchUnit 在构建时检查架构违规
> - **路径别名**：TypeScript 的 `@/features/auth` 让 IDE 原生解析
> - **Lint 规则**：ESLint、Checkstyle 强制包依赖规则
> 
> 正如 Simon Brown 所言：**我们的每一项设计决策都必须为未来的变化敞开大门。让我们现在编写的代码不对未来的代码产生阻碍是一项非常重要的技能，通常需要花费多年时间才能掌握。**

# 其他的解耦合模式

## 超越包组织的解耦手段

除了前述四种包组织方式，Simon Brown 还讨论了其他解耦模式：

**1. 静态分析工具**

> 使用静态分析工具（NDepend、Structure101、Checkstyle、JArchitect 等）。

**2. 编译器强制**

> 使用编译器。（更可取）始终建议尽可能依赖编译器来遵守这些方法。

**3. 模块系统**

Java 9+ 的 Module System 允许用 `module-info.java` 精确控制包的可见性：

```
module com.company.app.orders {
    exports com.company.app.orders.api;  // 只导出 API 包
    // internal 包不被导出，对外不可见
}
```

**4. 路径别名与 Lint 规则**

2026 年的现代实践中，路径别名和 lint 规则胜过部落知识：

```
// tsconfig.json
{
  "compilerOptions": {
    "paths": {
      "@/features/*": ["./src/features/*"],
      "@/shared/*": ["./src/shared/*"]
    }
  }
}
```

## 解耦模式的工业级选择

根据 Code Decoupling 的综合比较：

|模式|适用场景|主要优势|主要弱点|
|---|---|---|---|
|按层封装|小型或早期项目|简单、快速启动|难以扩展|
|按功能封装|中型到大型项目|业务领域可见、代码易定位|基础设施可能绕过领域|
|端口和适配器|需要技术解耦的系统|业务核心独立、可测试性强|可能引入 undesirable 依赖|
|按组件封装|面向服务/微服务等|综合前三者优点、最小化缺陷|需要谨慎管理公开接口|

### 工业对照：2026 年解耦模式的现代工具箱

**ByteLedger 2026 年的完整工具箱**：

1. **共置原则**（Colocation）：同变更文件放一起
2. **功能文件夹**（Feature Folders）：优于层文件夹
3. **路径别名**（Path Aliases）：`@/features/auth`
4. **Lint 规则**：强制结构
5. **单一 README**：每个可运行单元一个
6. **Monorepo 工具**：Turborepo、Nx、Bazel（但小团队不应过早采用）

**JavaThinking 2026 年的演进路径**：

> 小项目从按层或按功能封装起步。随着项目和团队成熟，迁移到 DDD 组织方式。

**定律一：包组织方式映射变更模式**

默认使用最小可见性。每个类、方法、字段都应该使用能满足需求的最小访问级别。

**定律四：用编译器执法，而非依赖自律**

> 强烈建议利用编译器来维护架构设计原理，而不要依赖个人自律和编译过程之后的工具。
