
这两章是 Bob 把"架构边界"这把刀，刺入两个被长期误以为"特殊到不适用整洁架构"的领域：**测试**和**嵌入式**。第28章的结论极具颠覆性——**测试不是系统的"外人"，而是最外圈的那个组件**，它必须遵守依赖规则，否则就会反噬系统本身（脆弱测试→系统僵化）。第29章则把嵌入式系统的"硬件诅咒"破解了：**固件会过时，硬件会报废，唯有与硬件解耦的软件逻辑可以长生**。两章合在一起，实际上是整洁架构的"极限压力测试"——如果连测试和嵌入式这种"最不像是能画边界"的场景都能用同心圆模型驯服，那么整洁架构就是真正普适的。

# 第28章 测试边界

## 测试也是一种系统组件

### 一个被长期混淆的问题

Bob 开篇就搁置了测试领域的无尽争论：

> 从架构的角度来看，所有测试都是相同的。无论是 TDD 创建的小型测试，还是大型的 FitNesse、Cucumber、SpecFlow 或 JBehave 测试，它们在架构上都是等价的。

无论你是单元测试、集成测试、验收测试、功能测试、Cucumber 测试、TDD 测试、BDD 测试、组件测试……**从架构视角看，它们等价于同一个东西：系统最外圈的组件**。

### 测试组件的四个架构特征

**1. 遵循依赖规则**

测试在本质上是非常细节化、非常具体的，它们始终向内依赖于被测试的代码。在架构圆环中，**你可以把测试看作最外圈**——系统内没有任何组件依赖于测试，测试始终向内依赖于系统的组件。

**2. 最孤立的组件**

测试也是可以独立部署的。事实上，大多数时候它们被部署在测试系统中，而非生产系统中。因此，即使在通常不需要独立部署的系统中，测试依然会被独立部署。测试是系统中最孤立的组件。

**3. 不参与系统运行**

系统的正常运行并不需要用到测试组件，没有用户依赖于它。它的角色是支持开发，而不是支持运行。

**4. 是所有其他组件的模范**

然而，测试仍然是系统中不可或缺的组件。事实上，它在许多方面都反映了系统中其他组件所应遵循的设计模型。

> 💡 **第一性原理解读**：这一节的第一性原理是**"测试是依赖图的叶子节点，也是架构纪律的探针"**。在源码依赖图中：
> 
> ```
> 生产代码 → 向内 → 业务核心
> 测试代码 → 向内 → 生产代码 → 向内 → 业务核心
> ```
> 
> 测试是依赖链的末端——它只依赖生产代码，不被任何生产代码依赖。这让它成为系统中**最自由、最孤立**的组件。但也正因为它"最自由"，开发者才会误以为"测试可以随便写"——这是 Bob 要击碎的第一个错觉。
> 
> 更深层的原理是：**测试代码的质量是生产代码架构质量的探针**。如果测试只能透过 GUI 才能验证业务规则，那么这暴露了生产代码的一个架构缺陷——业务规则被 GUI 绑架了。如果测试与每个生产类一一对应，那么这暴露了生产代码的结构性僵化。测试组件之所以"反映其他组件应遵循的设计模型"，是因为**测试代码的痛苦程度，与生产代码的架构质量成反比**。

### 工业对照：测试作为"架构适应度函数"

2025-2026 年，测试的现代角色进一步演化为**"架构适应度函数"（Architectural Fitness Function）**：

```
// ArchUnit 测试：既是测试，又是架构守卫
@Test
void domain_should_not_depend_on_infrastructure() {
    // 这个测试本身就是"系统组件"
    // 它向内依赖生产代码，验证其架构合规性
    assertThat(classes().that().resideInAPackage("..domain.."))
        .should().notDependOnClassesThat()
        .resideInAnyPackage("..jpa..", "..http..", "..stripe..");
}
```

这种测试既是"测试组件"（可被独立部署、不参与生产运行），又是"架构纪律的执行者"。它印证了 Bob 的判断——**测试是系统中最孤立的组件，但也是最关键的组件**。

## 可测试性设计

### 脆弱测试问题（The Fragile Tests Problem）

Bob 指出了一个"灾难性的观点"：

> 测试的极端孤立性，加上它们通常不参与部署，常常让开发者认为测试不属于系统设计的一部分。这是一个灾难性的观点。没有被良好集成到系统设计中的测试往往是脆弱的，它们使系统变得死板且难以更改。

具体机制：

- 测试与系统强耦合 → 系统的轻微变更导致大量测试失败
- 修改一个常见组件 → 成百上千个测试破裂
- 开发者意识到"简单修改会导致大规模测试失败" → **抵制修改**
- 系统变得死板、难以演变

Bob 给出了一个生动的对话场景：

> 想象开发团队和营销团队之间的对话——营销团队要求对导航结构做一个简单的更改，但这将导致 1000 个测试中断。

### 软件设计的第一规则

> 软件设计的第一规则（无论是可测试性还是其他原因）始终是：不要依赖于易变的东西。

GUI 是易变的。透过 GUI 操作系统来验证业务规则的测试套件必然是脆弱的。因此，设计系统和测试的目标是——**业务规则可以脱离 GUI 被测试**。

### 脆弱测试的三个根源

**1. GUI 耦合**：测试通过点击界面验证业务规则，界面一变测试全崩

**2. 结构性耦合（Structural Coupling）**：测试套件对每个生产类都有一个测试类，对每个生产方法都有一套测试方法。这样的测试套件与应用程序结构深度耦合

**3. 资源耦合**：测试依赖昂贵的资源（数据库、网络、第三方服务），导致测试缓慢、不稳定

> ⚠️ **批判性洞见**：结构性耦合是"最强、最阴险"的测试耦合形式。想象一个测试套件，它对每个生产类都有一个测试类，对每个生产方法都有一套测试方法——这种"一对一映射"看起来很"完整"，实际上是架构灾难。当生产方法或类发生变更时，大量测试必须跟着变更。这导致测试脆弱，并使生产代码变得死板。
> 
> 这是一个反直觉的洞察：**"测试覆盖率 100%"和"测试脆弱性"可能是一枚硬币的两面**。当你追求"每个类都有测试类"时，你可能正在创造结构性耦合。真正的解药不是"测试更多"，而是"测试在正确的边界上"。

### 工业对照：现代测试金字塔的架构基础

2026 年的测试实践明确了测试的结构性原则：

|测试类型|对应架构边界|是否允许结构性耦合|
|---|---|---|
|单元测试|类/函数内部|✅ 允许（但要小心）|
|组件测试|组件边界|❌ 禁止穿透组件内部结构|
|集成测试|服务/适配器边界|❌ 禁止依赖具体实现|
|端到端测试|系统最外圈|❌ 禁止依赖 GUI 细节|

**关键纪律**：

- **单元测试**可以（但不必须）与类结构对应——它们是测试组件中最内层的
- **组件测试以上**必须通过测试专用 API 进行，**禁止结构性耦合**
- **端到端测试**必须透过稳定的 UI 契约（如 DOM 选择器、可访问性 ID）而非像素坐标或 DOM 结构

这正是 Bob "可测试性设计"在现代的兑现——**测试边界必须与架构边界对齐**。

## 测试专用 API

### 测试专用 API 的设计原则

Bob 给出了解决方案：

> 实现这一目标的方法是创建一个特定的 API，测试可以使用它来验证所有的业务规则。这个 API 应该具有超级能力，允许测试避开安全约束，绕过那些成本高昂的资源（例如数据库），强制将系统设置为某种可测试的状态。该 API 将是用户界面所用到的交互器和接口适配器的一个超集。

具体特征：

**1. 超级权限（Superpowers）**：

- 避开安全约束
- 绕过昂贵资源（数据库、网络、第三方服务）
- 强制系统进入特定的可测试状态

**2. 是 UI 使用的交互器和接口适配器的超集**：

- UI 使用的 API ⊂ 测试专用 API
- 测试专用 API 暴露更多"后门"能力

**3. 解耦测试与应用程序结构**：

- 不仅仅是把测试从 UI 解耦
- 目标是**把测试的结构与应用程序的结构解耦**

### 测试专用 API 的真正目的

> 测试 API 的目的是将测试与应用程序解耦。这种解耦不仅仅包括从 UI 中分离测试：目标是将测试的结构与应用程序的结构分离。

这意味着：

- ❌ 错误做法：为每个生产类写一个测试类（结构性耦合）
- ✅ 正确做法：通过测试专用 API，隐藏应用程序结构，让生产代码可以以不影响测试的方式重构和演进

### 安全性考量

> 这种具有超级权限的测试专用 API 是非常危险的，所以我们应当将它放置在一个独立的、可单独部署的组件中。

关键纪律：

- **独立部署**：测试专用 API 必须在独立的组件中
- **不进入生产**：绝对不能随生产系统部署
- **权限隔离**：超级权限只能在测试环境中激活

### 工业对照：现代测试专用 API 的实现模式

**1. 测试门面（Test Facade）模式**：

    }

**3. 现代工业的"测试双"模式**：

2026 年的测试实践进一步明确：

- **测试专用 API 必须独立部署**：放在独立的测试组件中，绝不进入生产镜像
- **超级权限必须环境隔离**：通过 `@Profile("test")` 或构建变体控制
- **测试 API 是 UI API 的超集**：UI 能做的测试 API 都能做，UI 不能做的（强制状态、绕过支付）测试 API 也能做

### 工业对照：AI 时代的测试边界新挑战

2025-2026 年，AI 辅助编程对测试边界提出了新挑战：

**1. AI 生成的测试往往是结构性耦合的**：

AI 倾向于"为每个生产类生成一个测试类"——这正是 Bob 警告的"结构性耦合"模式。当 AI 生成 1000 个测试类，每个对应一个生产类时，系统的脆弱性会指数级上升。

**2. AI 辅助生成测试的解决方案**：

```
架构纪律（ArchUnit 测试）→ AI 生成测试 → 架构适应度函数验证
                                        ↓
                              不符合纪律 → 拒绝合并
```

**3. LLM 应用的测试边界**：

测试 LLM 应用时，测试专用 API 必须能够：

- 强制 LLM 返回特定响应（Mock LLM 端口）
- 绕过 Token 计费和速率限制
- 注入特定的上下文状态

```
# 测试专用 API：LLM 应用的超集接口
class LLMTestApi:

        """超级权限：强制 LLM 返回特定响应，绕过真实 LLM 调用"""
        mock_llm = MockLLMProvider(forced_response)
        return self.use_case.moderate(content, llm_provider=mock_llm)
```

## 本章小结

第28章的真正贡献，是把**测试从"系统的外人"重新定位为"最外圈的架构组件"**。

### 三个核心定律

**定律一：测试是系统组件，遵循依赖规则**

测试在架构圆环的最外圈，始终向内依赖生产代码，不被任何生产代码依赖。测试是系统中最孤立的组件，但也是不可或缺的组件。

**定律二：脆弱测试源于耦合，尤其是结构性耦合**

- GUI 耦合：测试透过 GUI 验证业务规则
- 结构性耦合：测试与生产类一一对应
- 资源耦合：测试依赖昂贵资源

这三类耦合使测试脆弱，进而使系统僵化——开发者因为害怕破坏测试而抵制修改。

**定律三：测试专用 API 是解耦的关键**

测试专用 API 必须具有超级权限（绕过安全、绕过昂贵资源、强制可测状态），是 UI 所用交互器和接口适配器的超集。其目的是**将测试的结构与应用程序的结构解耦**，而不仅仅是把测试从 UI 解耦。

# 第29章 整洁的嵌入式架构

第29章是整洁架构在**最不友好环境**中的压力测试——嵌入式系统。这里有严格的资源约束（有限的 CPU、内存、存储空间）、有实时性要求、有直接与硬件寄存器打交道的需求。许多人认为"整洁架构是企业级 Java 的奢侈品，嵌入式系统玩不起"——Bob 用这一章证明：**恰恰相反，嵌入式系统最需要整洁架构，因为硬件迭代最快、过时最早**。

## “程序适用测试”测试

### 嵌入式系统的本质挑战

嵌入式系统的独特性：

> 嵌入式系统受到硬件资源的限制，并且与硬件功能紧密耦合。

具体挑战：

- **硬件约束**：CPU、内存和存储受限
- **紧耦合**：嵌入式系统经常直接与传感器、执行器或微控制器等硬件组件交互
- **实时性要求**：时序约束至关重要，系统必须在严格的截止时间内响应事件
- **测试困难**：测试往往依赖于硬件，难以隔离软件逻辑

James Grenning 的名言被 Bob 引用：

> "尽管软件不会磨损，但固件和硬件会变得过时，从而需要对软件进行修改。"
> 
> "尽管软件不会磨损，但它可能被对固件和硬件的未管理依赖从内部摧毁。"——James Grenning

### “程序适用测试”的哲学

这一节的核心思想是：**嵌入式系统的软件部分应该能在宿主机（开发者的 PC）上被测试，而不需要目标硬件**。

换句话说，如果你的嵌入式代码**必须刷到板子上才能测试**，那么你的架构有问题。

### 工业对照：宿主机测试的现代实践

2026 年 EurthTech 的文章明确指出：

> 应用层绝不应该直接触碰硬件寄存器。它应该调用 BSP 或中间件。测试方法：你的应用层能在 PC（x86）上编译并在模拟器中运行吗？如果可以，你就拥有了整洁架构。如果不行（因为它试图 #include "stm32f4xx.h"），你的层次就在泄露。

专业固件的分层结构：

```
┌─────────────────────────────────────────┐
│  Application Layer（业务逻辑）              │ ← 可在 PC 上编译测试
│  "如果温度>50°C 且电池>20%，开启风扇"      │
├─────────────────────────────────────────┤
│  Middleware（中间件）                      │ ← 硬件无关
│  RTOS、文件系统、通信协议栈                 │
├─────────────────────────────────────────┤
│  BSP（板级支持包）                         │ ← 知道"引脚5连接了什么"
│  bsp_led_red_on(), bsp_get_battery()     │
├─────────────────────────────────────────┤
│  HAL（硬件抽象层）                         │ ← 知道"如何翻转引脚"
│  gpio_write_pin(PORT_A, PIN_3, HIGH)    │
└─────────────────────────────────────────┘
```

**关键测试**：应用层能否在 x86 上编译并运行？如果应用层代码试图 `#include "stm32f4xx.h"`，那么层次就在泄露。

> 💡 **第一性原理解读**：这一节的第一性原理是**"硬件依赖的局部化"**。嵌入式系统中真正与硬件交互的代码只占约 10%（HAL、驱动），而约 90% 是逻辑、协议、状态机。但许多团队把所有代码都与 MCU 紧耦合，导致：
> 
> - 无法在宿主机测试（必须刷板子）
> - 无法在不同芯片间移植（从 AVR 切换到 STM32 要重写一切）
> - 无法并行开发（硬件团队和软件团队互相等待）
> 
> 解决这个问题的第一性原理是：**把约 10% 的硬件交互代码隔离在清晰的接口背后，让约 90% 的逻辑代码保持平台无关**。这样，90% 的代码可以在 PC 上用 mock 实现进行测试，只有 10% 的硬件抽象层需要在目标硬件上验证。

### 工业对照：Hoomanely 的三层固件契约

2025 年 Hoomanely 的工程实践给出了现代工业的验证：

**第一层：硬件访问层（HAL）**——拥有物理

- 寄存器访问、引脚配置、总线事务、时序约束、电源时序
- 每个硬件变体一个实现
- 无产品逻辑
- 确定性行为
- 可独立测试

当传感器从 I²C 改为 SPI，或 GPIO 更换引脚时，**HAL 吸收变化，上层代码完全不受影响**。

**第二层：设备和服务抽象**——拥有行为

- 传感器暴露校准后的测量值，而非寄存器
- 电力系统暴露状态、限制和转换
- 通信栈暴露消息，而非帧

这一层允许**预验证**——核心固件逻辑可以在最终硬件锁定前很久，使用遵守相同接口的 mock 实现进行验证。

**第三层：产品逻辑**——拥有意图

- 何时捕获数据
- 如何做出决策
- 状态如何转换
- 错误如何处理

这一层：

- 无寄存器知识
- 无时序假设
- 无硬件依赖
- 仅通过服务和设备的术语表达

> 📌 **关键洞见**：Hoomanely 的实践证明，当接口契约稳定时：
> 
> - 硬件团队可以迭代布局密度、电源完整性、连接器对齐、机械适配
> - 固件团队可以迭代功能行为、数据流、电源策略、通信流
> - **双方互不等待**
> 
> 这就是 Bob "程序适用测试"思想在 2025 年的工业兑现——**固件应该以不同于硬件的速度移动，而不破坏两者之间的对齐**。

这解锁的业务价值：

## 目标硬件瓶颈

### 硬件瓶颈的本质

Bob 在这一节深入讨论了嵌入式系统开发中的"目标硬件瓶颈"问题。

**核心问题**：如果嵌入式团队没有硬件就无法运行测试，那么你就有一个架构问题。

2026 年 Denys Suprunenko 直截了当地指出：

> 如果你的嵌入式团队不能脱离硬件运行测试——你就有了一个架构问题。
> 
> 让我们直接一点。如果你的固件需要真实硬件来验证逻辑，你正在付出代价：
> 
> - ⏳ 更慢的开发周期
> - 🧪 有限的测试覆盖率
> - ⚠️ 脆弱的发布
> 
> 这不是工具问题。这是一个架构决策。

### 典型嵌入式系统的现实

> 在一个典型的嵌入式系统中：
> 
> - ~10% 是硬件交互（HAL、驱动）
> - ~90% 是逻辑、协议、状态机
> 
> 然而许多团队把所有东西都与 MCU 紧耦合。结果？👉 没有刷板子，你什么都测试不了。

### 高性能团队的做法

> 高性能团队的不同做法：他们将固件视为软件，而不是"运行在芯片上的代码"。他们：
> 
> - 🧩 将硬件隔离在清晰的接口背后
> - 🧼 保持核心逻辑的平台无关性
> - 🔁 在每次提交时在 PC 上运行测试——没有板子，没有实验室，没有借口

### 嵌入式系统的反模式与解决方案

|反模式|问题|解决方案|
|---|---|---|
|**与框架结婚**​|对特定框架的依赖使代码难以更改|将框架作为插件使用，在边界处隔离|
|**暴露硬件细节**​|向上层暴露硬件细节造成紧耦合|使用隐藏实现细节的抽象|
|**直接硬件访问**​|业务逻辑直接访问硬件寄存器|创建具有有意义名称的适当抽象|
|**散布的条件编译**​|代码中散布的 #ifdef 指令|使用多态和构建系统替代|
|**非标准类型**​|使用处理器特定类型|使用标准类型（stdint.h）|
|**单体文件**​|在单个文件中混合多个关注点|按职责分离（业务逻辑 vs 硬件访问）|

### 条件编译的 DRY 问题

许多嵌入式系统严重依赖条件编译（#ifdef）来处理硬件变体，这会造成可维护性问题：

> 在代码中散布像 #ifdef BOARD_V2 这样的条件编译指令违反了 DRY（Don't Repeat Yourself）原则，并创建脆弱的代码。

**糟糕的实现**：消息处理器和 UART 硬件访问在同一个文件中，硬件细节（波特率、寄存器）对业务逻辑可见，只能在目标硬件上测试。

**整洁的实现**：消息处理器通过硬件抽象接口工作，UART 细节隔离在固件层，消息处理器可以用 mock 串行接口测试。

### 工业对照：宿主机测试的具体技术

**1. 硬件抽象层（HAL）的接口设计**：

```
// 硬件接口：用头文件作为接口定义
typedef struct {
    int (*readTemperature)();
} TemperatureSensor;

// 特定硬件的实现
int hardwareReadTemperature() {
    // 硬件特定代码读取温度
    return analogRead(TEMP_PIN);
}

TemperatureSensor sensor = { .readTemperature = hardwareReadTemperature };
```

**2. 依赖注入在嵌入式中的应用**：

```
// 在运行时将硬件依赖注入核心逻辑
void monitorTemperature(TemperatureSensor* sensor, FanController* fan, int threshold) {
    int temp = sensor->readTemperature();
    if (temp > threshold) {
        fan->turnOn();
    }
}

// Main 组件：依赖解析的场所
int main() {
    TemperatureSensor sensor = { .readTemperature = hardwareReadTemperature };
    FanController fan = { .turnOn = hardwareTurnOnFan, .turnOff = hardwareTurnOffFan };
    
    while (1) {
        monitorTemperature(&sensor, &fan, 25);
    }
}
```

**3. 宿主机测试**：

```
// 在宿主机上测试核心逻辑
void testShouldTurnOnFan() {
    assert(shouldTurnOnFan(30, 25) == 1);
    assert(shouldTurnOnFan(20, 25) == 0);
}

void testMonitorTemperature() {
    TemperatureSensor mockSensor = { .readTemperature = mockReadTemperature };
    FanController mockFan = { .turnOn = mockTurnOnFan, .turnOff = mockTurnOffFan };
    
    monitorTemperature(&mockSensor, &mockFan, 25);
    // 验证风扇状态变化
}
```

**4. 现代嵌入式测试工具链**：

- **Unity + CMock**（ThrowTheSwitch）：嵌入式单元测试框架
- **Zephyr ztest**：Zephyr RTOS 内置测试框架
- **Cppcheck / PC-lint**：静态分析工具，捕捉缓冲区溢出、类型不匹配等

**5. RTOS 集成的分层模型**：

```
┌─────────────────────────────────────────┐
│  Application Tasks（应用层任务）           │ ← 业务逻辑任务
│  Sensor Task, Comm Task, UI Task        │
├─────────────────────────────────────────┤
│  Queues & Semaphores（队列和信号量）       │ ← 任务间通信
├─────────────────────────────────────────┤
│  RTOS（FreeRTOS, Zephyr）                │ ← 调度器
├─────────────────────────────────────────┤
│  Device Abstractions（设备抽象）           │
├─────────────────────────────────────────┤
│  HAL（硬件抽象层）                         │ ← 寄存器访问
└─────────────────────────────────────────┘
```

2026 年 Hubble 的文章明确指出：

> 分层架构使得宿主机测试成为可能。如果你的应用层不 #include "stm32f4xx.h"，你可以在笔记本上编译它，用 mock HAL 函数测试它。

**6. 硬件在环（HIL）测试的准确定位**：

> 对于驱动级验证——真实的硬件行为很重要（时序、信号完整性、中断处理）——你需要真实的目标硬件。HIL 设置自动化刷写和验证。但它们是另一个话题。
> 
> 关键洞察：前面的分层架构正是使得离目标测试成为可能的原因。如果你跳过了架构，你就跳过了高效测试的能力。它们是同一个决策。

### 三个核心定律

**定律一：硬件迭代不可逃逸，软件必须与之解耦**

> "尽管软件不会磨损，但固件和硬件会变得过时，从而需要对软件进行修改。"——James Grenning

硬件和固件会过时，这是物理必然。但软件不应该因此被迫重写。**通过硬件抽象层（HAL）和操作系统抽象层（OSAL），将硬件和操作系统作为实现细节，软件核心逻辑可以获得长寿命**。

**定律二：目标硬件瓶颈是架构问题，不是工具问题**

如果嵌入式团队没有硬件就无法运行测试，那是架构决策的错误，而非工具限制。约 10% 的硬件交互代码应该隔离在清晰接口背后，约 90% 的逻辑代码应该保持平台无关，可在宿主机测试。

**定律三：嵌入式整洁架构的分层契约**

```
Application Layer（产品逻辑，拥有意图）
    ↓ 依赖
Device & Service Abstractions（设备与服务抽象，拥有行为）
    ↓ 依赖
HAL（硬件访问层，拥有物理）
    ↓ 依赖
Hardware（电气现实）
```

依赖方向严格从外向内——应用层不知道寄存器、时序或硬件细节，只通过服务和设备的术语表达。

> 4. **目标硬件瓶颈是架构问题，不是物理必然**
> 
> Bob 在 2017 年建立的这套体系，今天在 IoT、汽车电子、工业控制等领域不仅没有过时，反而成为了**嵌入式架构师的"生存工具箱"**。当你下次面对嵌入式项目时，记住 Hoomanely 的洞见：**固件应该以不同于硬件的速度移动，而不破坏两者之间的对齐**。这正是整洁架构在嵌入式世界中的兑现——它不是企业级 Java 的奢侈品，而是对抗硬件过时的必需品。

2. **边界强度按梯度选择**（第24章）
3. **架构边界穿透所有物理边界**（第27章）
4. **测试是最外圈的架构组件**（第28章）
5. **硬件和操作系统是实现细节**（第29章）
