
这一章最容易被误读的地方是：读者往往记住了"按业务能力拆"和"按子域拆"这两个名词，却没抓住 Richardson 真正想表达的**第一性原理——拆分不是在切代码，而是在切"业务边界 + 数据所有权 + 团队所有权"这三件绑在一起的事**。下面我按"原理 → 章节脉络 → 工业洞见"三层展开。

## 一、第一性原理：拆分的本质是"寻找认知边界"

要理解这一章，先要回答一个问题：**为什么"切"这件事这么难？**

答案藏在软件架构的根本矛盾里：人类大脑的"工作记忆"有限，单个开发者能同时理解的代码规模是有上限的（业界经验值大约是 1-2 万行具备完整心智模型）。当系统超过这个规模，就必须用"边界"把认知负荷切碎。单体内的"逻辑模块"是软边界——靠自觉维护，必然腐化；微服务做的是用进程边界把软边界硬化。

但硬化边界有个隐藏前提：**你必须切对**。切错了，比不切还糟——这就是工业界常说的"分布式单体"（Distributed Monolith）。Martin Fowler 早在 2015 年就警告过"微服务溢价"：微服务架构只有在系统规模和复杂度达到临界点时才有正收益，否则你付出的分布式复杂度远超收益。

所以拆分的本质问题不是"怎么切"，而是**"业务的认知边界在哪里？"**​ Richardson 给出的答案是：去业务本身找，不要去技术层找。

> 💡 我的洞见：很多人以为"按业务能力拆分"和"按子域拆分"是两种并列的方法，其实它们是**同一个动作的两个视角**——业务能力是"组织对外呈现的功能"（外向视角），子域是"领域内部的知识边界"（内向视角）。DDD 的限界上下文（Bounded Context）恰好是这两个视角的交汇点：一个限界上下文对外是一个业务能力，对内是一个统一的领域模型。所以 Richardson 在书中把这两种方法并列，不是让你二选一，而是告诉你**从两个方向互相校验**。

## 二、章节脉络：Richardson 的三步法

### 第一步：识别系统操作（2.2.1）

这是最容易被跳过的步骤，但 Richardson 坚持要从这里开始。所谓"系统操作"，是指系统对外呈现的、**抽象的、与具体实现无关的**操作集合。分为两类：

- **命令型**：创建、修改、删除数据（如 `createOrder`、`cancelOrder`）
    
- **查询型**：读取和查询数据（如 `findOrder`、`getRestaurantMenu`）
    

识别技巧：在分析用户故事和业务场景时，**找频繁出现的动词**。"用户下单"、"餐厅接单"、"骑手更新位置"——这些动词短语就是系统操作的候选。

每个系统操作还要定义：

- **命令规范**：参数、返回值、涉及的领域模型类
    
- **行为规范**：前置条件（什么情况下能执行）、后置条件（执行后系统变成什么样）
    

> ⚠️ 这一步的价值常被低估。系统操作列表本质上就是**用例层面的"需求契约"**——它让你在动手切服务之前，先对"系统到底要做什么"达成共识。没有这份契约，后面的服务拆分就是空中楼阁。

### 第二步：识别服务（2.2.2 - 2.2.4）

这是本章的核心，Richardson 给出了两条主路径 + 一组指导原则。

**路径一：按业务能力拆分**

业务能力是"组织为了达成目标而做的事情"——订单管理、客户管理、账单、库存、配送。每个业务能力对应一个服务，服务拥有自己的数据和业务逻辑。

这种方法的优点是**稳定**——业务能力不会轻易变。十年前 FTGO 有"订单管理"，十年后还是有"订单管理"，但它的技术栈、数据模型可能换了 N 代。业务能力的稳定性让它成为天然的拆分锚点。

**路径二：按子域拆分（DDD 视角）**

这是路径一的深化版本。DDD 的核心概念：

- **领域**：你要解决的整个业务问题
    
- **子域**：领域的子集。DDD 区分三种子域——核心域（核心竞争力）、支撑子域（必要但非差异化）、通用子域（行业通用，可买可不建）
    
- **限界上下文**：领域模型的边界，每个限界上下文内部有一套"通用语言"（Ubiquitous Language），同一个词在不同上下文里含义不同
    

FTGO 的子域划分：订单获取、订单管理、餐馆管理、送餐、会计。每个子域映射到一个服务。

**关键洞察**：DDD 的"限界上下文"几乎是微服务边界的完美映射。每个限界上下文 = 一个服务 = 一个团队 = 一份数据库。这就是为什么 Richardson 会在书中说"按子域拆分"是"按业务能力拆分"的精细化版本。

**拆分的指导原则**（Richardson 借用了面向对象设计的两大原则）：

1. **单一职责原则（SRP）**：一个类/服务只应有一个引起它变化的原因。微服务化后：每个服务应该是内聚的、小的、只承担单一职责。
    
2. **闭包原则（CCP）**：如果出于某种原因，两个类的修改必须耦合先后发生，那么就应该把它们放在同一个包（服务）内。微服务化后：因相同原因变更的服务应该放在一起，这样一次需求变更只影响一个团队、一个服务。
    

这两条原则合起来就是一句话：**让"经常一起变的东西"待在一起，"不一起变的东西"分开**。这是判断边界是否正确的根本标准。

### 第三步：定义服务 API（2.2.6）

有了系统操作清单和服务清单，最后一步是把系统操作分配给服务，并定义服务间的协作接口。

分配原则：

- 大部分系统操作完全由一个服务处理（理想情况）
    
- 有些操作需要跨服务协作（如 `createOrder` 可能涉及订单服务、餐厅服务、账户服务）
    
- 跨服务协作需要的接口，就是服务 API 的"协作操作"部分
    

分配时会有**边界模糊**的情况。Richardson 举的例子很经典：`noteUpdatedLocation`（更新送餐员位置）这个操作——一方面它与送餐员有关，应该分配给 Courier Service；另一方面它需要送餐地点，属于 Delivery Service 的职责。这种"左右为难"恰恰是边界没切干净的信号，需要回到第二步重新审视。

## 三、拆分的五大难点（2.2.5）：理论遇到现实的五道坎

这是本章最有"工业味"的一节，也是 Richardson 诚实地告诉你"微服务不是免费的午餐"的地方。

**难点一：网络延迟**

特定的拆分可能导致两个服务之间大量往返调用。比如"获取用户及其订单"需要：调用 UserService → 调用 Orders Service → 对每个订单调用 Product Service……一个查询变成 4N+2 次网络调用。

- **解决**：把多个相关服务组合在一起（合并过细的服务）；或者实施批处理 API，一次往返获取多个对象；或者改用异步事件驱动。
    

**难点二：同步 IPC 导致可用性降低**

REST 同步调用会把服务可用性串联起来：A 调 B 调 C，B 挂了 A 也挂了。三个 99.9% 可用的服务串联，整体可用性降到 99.7%。

- **解决**：参考第 3 章的异步消息模式。
    

**难点三：跨服务数据一致性**

一个系统操作需要修改多个服务的数据时，原来的 ACID 事务不复存在。

- **解决**：参考第 4 章的 Saga 模式。
    

**难点四：无法跨服务获取真正一致的数据视图**

分布式环境下，没有全局快照。

- **解决**：实践中很少带来真正的问题，接受最终一致性。
    

**难点五：上帝类阻碍拆分（God Class）**

这是最阴险的难点。`Order` 类在 FTGO 中贯穿订单处理、餐馆订单管理、送餐、付款等所有环节，拥有复杂的状态模型和海量字段。它是整个应用的"心脏"，也是拆分的"绊脚石"。

Richardson 给出了三种处理方式，并明确指出**第三种是推荐方案**：

1. 把 Order 类打包成库 + 中央 Order 数据库（违反松耦合，退化成共享数据库反模式）
    
2. 把 Order 数据库封装在 Order Service 中，其他服务调用它（结果是贫血模型，Order Service 变成纯数据服务）
    
3. **应用 DDD，将每个服务视为具有自己领域模型的单独子域**——订单处理服务有自己的 Order 模型，送餐服务有自己的 Order 模型版本，它们通过 API 或事件通信，各自的模型只在自己的上下文内有意义
    

> 📌 第三种方案的精髓：承认"Order"在不同上下文里**本就是不同的东西**。订单处理上下文里的 Order 关注的是生命周期状态；送餐上下文里的 Order 关注的是地理位置和配送进度。强行统一成一个 Order 类，就是上帝类的根源。

## 四、工业实践视角：这些年我们交过的学费

如果 Richardson 写书时（2018年）的工业界还在热情拥抱微服务，那么 2024-2026 年的工业界已经在冷静反思。这一章的理论在工业落地时，有几个必须知道的真相：

### 1. 错误边界 = 分布式单体

工业界总结了微服务失败的五大反模式：

- **共享数据库**：Order Service、Product Service、User Service 共用一个 schema。任何一个表的变更都需要跨团队协调，数据层根本不独立。
    
- **同步调用链**：API 请求 → A → B → C → D，任何一环慢了或挂了，整个请求失败。
    
- **过于健谈的服务**：一个查询需要 4N+2 次网络调用。
    
- **按技术层拆分**：FrontendService、BackendService、DatabaseService——三个"服务"每次改需求都要一起改、一起部署。这是违反康威定律的典型。
    
- **过早拆分 / Nano-services**：服务切得太细，通信开销和管理成本反而超过业务价值。
    

### 2. 康威定律：架构是组织的镜像

Melvin Conway 1967 年的观察："任何组织在设计系统时，都会不可避免地复制该组织的沟通结构。"这意味着：

- 如果你的组织是 Frontend 团队、Backend 团队、DBA 团队三足鼎立，你切出来的必然是 FrontendService、BackendService 和共享数据库——不管你技术上有多想切对。
    
- **逆向康威 manoeuvre**：要想得到松耦合的微服务架构，必须先调整团队结构——建立小的、自治的、跨职能的"两披萨团队"，每个团队端到端拥有一个业务能力或限界上下文。
    

Spotify 的"squad"模式、Sam Newman 的"stream-aligned teams"、Amazon 的"you build it, you run it"——都是这个原理的实践。

> ⚠️ 这是绝大多数微服务转型失败的根本原因：试图在不改组织结构的前提下做微服务。结果就是"分布式单体"——部署拓扑是分布式的，但协调开销还是单体的。

### 3. Uber 的教训：2,200 个微服务之后的回归

Uber 在规模化过程中激进拆分，最终运行着 **2,200 个关键微服务**。每个服务独立拥有、独立部署。但问题来了：

- 一个新功能可能需要跨数十个上下游服务协调变更
    
- 没有任何明确的契约来约束服务如何演化
    
- 工程师无法从整体上理解系统
    
- 入职新领域可能需要理解数百个服务交互
    

Uber 的应对方案是 **DOMA（Domain-Oriented Microservice Architecture）**：把 2,200 个服务归类为 70 个领域，引入领域网关为每个领域暴露单一稳定接口，建立领域层之间的严格依赖规则。结果：新平台入职时间缩短 25-50%，平台支持成本下降一个数量级。

这个案例的洞见是：**无约束的拆分本身就是一种架构债务**。当服务数量爆炸时，必须在服务之上引入"领域"这一层抽象来重新收编。

### 4. 务实的拆分决策框架

综合这两年的工业实践，我给你一个判断"该不该拆、怎么拆"的框架：

**先问组织约束**：

- 工程师 < 10 人 → 单体
    
- 10-50 人 → 模块化单体
    
- 50-100 人 → 选择性服务化（只抽热点）
    
- 100+ 人 → 微服务（但也要警惕过度拆分）
    

**再问数据约束**：

- 这个边界内的数据能容忍"暂时不一致"吗？
    
- 如果不能（如账户余额、支付状态），这些数据应该待在同一个服务里
    
- 跨服务的数据一致性要用 Saga 或最终一致性
    

**再问部署约束**：

- 你提出的服务能独立部署吗？不能 → 分布式单体
    
- 独立部署是微服务唯一不可被模块化单体替代的收益
    

**最后问运维预算**：

- 你有成熟的 CI/CD、容器编排、分布式追踪、集中日志吗？
    
- 没有 → 过早拆分会让你寸步难行
    

### 5. 正确的迁移路径：绞杀者模式

Martin Fowler 提出的"绞杀者模式"（Strangler Fig Pattern）是从单体迁微服务的行业标准做法：

1. 在单体前面放一个 API 网关/外观层
    
2. 识别第一个要抽取的能力（选孤立、边界清晰的，如认证、通知）
    
3. 构建新服务，拥有自己的数据库和 API 契约
    
4. 通过网关把相关流量逐步路由到新服务
    
5. 验证稳定后，删除单体中对应的代码
    
6. 重复，直到单体被"绞杀"殆尽
    

Stripe 用 5 年时间从 Ruby 单体迁到微服务，从 API 网关 → 支付处理 → 商户入驻逐步抽取，每一步都验证后再走下一步。Shopify 则选择了"模块化单体"路线——在单体内部强制模块边界，获得了微服务 80% 的收益（团队自治、清晰边界），却避免了运维复杂度的飙升。

## 五、本章的核心洞见（我自己的提炼）

读完这一章，我认为 Richardson 真正想传递的不是"两种拆分方法"，而是四个更深层的认知：

**第一，拆分是一个"发现"过程，不是"设计"过程。**​ 业务能力、子域、限界上下文——这些都是业务本身就有的结构，架构师的任务是**发现**它们，而不是**发明**它们。这也是为什么 DDD 的事件风暴（Event Storming）、上下文映射（Context Mapping）等技术这么重要——它们是"发现"边界的工具，而不是"创造"边界的工具。

**第二，服务边界的正确性由"变更传播"来验证。**​ 单一职责原则和闭包原则合起来的判据是：**当你改一个需求时，需要改几个服务？**​ 如果需要改 3 个服务才能实现一个小功能，你的边界就是错的。正确的边界应该让 80% 以上的需求变更只落在一个服务内。

**第三，"上帝类"问题揭示了单体和微服务的根本差异。**​ 单体里的一个类，在微服务里会变成 N 个上下文里的 N 个类，它们通过 API 或事件协作。这不是"重复"，而是"每个上下文都有自己的真理"。接受这一点，是接受微服务思维的分水岭。

**第四，拆分难点的本质是"分布式系统的物理定律"。**​ 网络延迟、可用性串联、数据一致性——这些不是 Richardson 的书的缺陷，而是分布式系统的物理定律。微服务架构把这些定律**从隐性变成显性**，迫使你在架构层面面对它们。第 3 章（IPC）、第 4 章（Saga）、第 7 章（CQRS）都是在给你应对这些物理定律的工具。

> 💡 一个反直觉的洞见：很多时候，**"先别拆"才是正确的架构决策**。如果你现在的痛点主要是"部署慢"或"团队互相等待"，那么"模块化单体 + 强制模块边界 + 独立数据库 schema"可能就能解决 80% 的问题，而不必承担微服务的运维复杂度。Amazon、Facebook、Etsy 都是用单体 + 良好的模块化做到了持续交付。微服务不是目标，独立部署和团队自治才是目标——微服务只是达到这些目标的手段之一。
