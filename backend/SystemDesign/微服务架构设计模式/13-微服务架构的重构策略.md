
这一章最容易被误读的地方是：读者往往把绞杀者模式当成一个"技术套路"——加个 API Gateway、抽几个服务、删点旧代码，似乎就大功告成。其实 Richardson 真正想表达的是**第一性原理——遗留系统重构的本质矛盾是"在高速行驶的列车上更换引擎"**：你既不能停业务（Big Bang 重写风险太大），又不能永远带着旧代码（单体地狱持续折磨团队）。绞杀者模式的精髓在于**它把"重构"从一个"项目"变成了一个"持续的过程"**，让每一次小步提取都立即产生业务价值，同时把风险控制在最小爆炸半径内。

下面我按"原理 → 章节脉络 → 工业洞见"三层展开。

## 一、第一性原理：为什么"推倒重写"在微服务重构中是死路

要理解这一章，先回到 Richardson 在书中开篇给出的核心判断：**不要做"一步到位，推倒重来"式的改造**。Martin Fowler 的名言在这里被 Richardson 反复引用——**"推倒重写的唯一保证，就是彻底搞砸一切"**。

为什么 Big Bang 重写必然失败？三个深层原因：

**原因一：遗留系统的真实需求是"未知的"**

原需求可能已丢失，系统里实现了大量"不再需要的功能"。现代化过程本质上是一个**发现过程**——你必须在重构中持续学习哪些功能真正有价值 。

**原因二：Big Bang 是在追逐移动靶**

当你从头重写时，旧单体仍在生产环境运行、仍在持续演进。等你写完，旧系统已经又往前走了两年。你追的永远是移动靶 。

**原因三：价值交付被推迟到终点**

Big Bang 在"到位"之前不会带来任何业务价值。而软件项目最大的风险就是"时间"——时间越长，成本和失败概率越高 。

> 💡 我的洞见：绞杀者模式本质上是一种**"风险与时间的解耦"策略**。它承认"完全微服务化"这个目标可能需要数年 ，但通过让第一个服务尽早上线、尽早产生价值，把"多年后的大收益"转换成"每季度的小收益"。更重要的是，它强制你在生产环境的熔炉中验证微服务架构决策 ——如果你的技术选型有误（比如错误使用共享库），在抽取几个服务后就能发现并纠正，而不是等"烘焙"到几百个服务后才被迫重构。

## 二、章节脉络：从"为什么重构"到"三种策略"到"集成胶水"

### 第一部分：重构到微服务需要考虑的问题（13.1）

**13.1.1 为什么要重构单体应用**

Richardson 明确给出了"单体地狱"的三类业务症状 ：

- **交付缓慢**：团队被单体的复杂性拖垮
    
- **充满故障的软件交付**：每次部署都心惊胆战
    
- **可扩展性差**：无法针对热点模块独立扩展
    

但在动手之前，Richardson 强调了一个常被忽略的前提：**先尝试改善软件开发流程（如引入自动化测试）、优化 CI/CD、提升团队自主性**。如果这些"单体内部优化"能解决问题，就不必微服务化 。Amazon 花了数年时间重构它的单体 ，这说明微服务化是一个战略决策，不是战术应急。

**13.1.2 绞杀单体应用**

绞杀者模式（Strangler Fig Pattern）的生物学隐喻来自热带雨林的绞杀榕 ：它从宿主树的树冠开始生长，根系向下延伸，最终包围并"窒息"宿主树，使其死亡，只留下绞杀榕本身。

**三个核心原则**​ ：

1. **尽早且频繁地体现价值**：第一个服务上线就开始获益，且随着服务数量增长，收益稳步增加
    
2. **尽可能少对单体做出修改**：修改遗留代码耗时、昂贵、风险高
    
3. **不需要过多的基础设施投资**：在重构前期只做最小投资，等服务数量增多再升级部署基础设施
    

**绞杀者模式的弊端（Richardson 诚实地指出）**​ ：

- 与 Big Bang 不同，绞杀者模式通常需要修改遗留应用
    
- 为了从单体中提取服务，必须先将它与单体其他部分解耦
    
- 还需要修改遗留应用以调用新服务或处理来自新服务的请求
    
- 如果遗留应用使用古老技术，这些修改会非常困难
    

### 第二部分：将单体应用重构为微服务的若干策略（13.2）

这是本章的核心，Richardson 给出了**三种递进策略**：

#### 策略一：将新功能实现为服务（13.2.1）——最低风险的起点

**核心思想**：在单体旁边新建一个服务来实现新功能，通过 API Gateway 将新功能请求路由到新服务，遗留请求仍路由到单体。

**为什么这是最佳起点**：

- 不需要修改单体（降低风险）
    
- 新服务可以使用现代技术栈、DDD、现代开发实践
    
- 立即获得微服务的好处（独立部署、独立扩展）
    
- 降低单体的增长速度——新功能不再加剧单体的膨胀
    

**集成胶水（Integration Glue）**：新服务需要与单体协作，胶水代码由两个方向的适配器组成 ：

- **服务访问单体数据**：通过单体的查询 API 检索数据，或订阅单体发布的领域事件来更新本地副本
    
- **服务调用单体功能**：通过异步消息或同步 API 调用单体
    

**如果新功能无法作为服务实现**：解决方案是**先在单体中实现功能，随后将功能及其他相关功能一并提取到自己的服务中**​ ——这就是策略三的雏形。

#### 策略二：隔离表现层与后端（13.2.2）——为后续提取铺路

**核心思想**：将单体的表现层（处理 HTTP 请求、生成 HTML 的模块）与业务逻辑层、数据访问层分开。

**价值**：

- 表现层和后端可以独立部署
    
- 后端业务逻辑层暴露 API，为后续服务化提供清晰边界
    
- 这是"提取业务能力"之前的必要准备
    

#### 策略三：提取业务能力到服务中（13.2.3）——垂直切片的提取

这是最核心、也最具挑战的策略。你要提取的是**对单体应用自上而下的一个"垂直切片"**​ ，包含：

- 实现 API 端点的入站适配器
    
- 领域逻辑
    
- 出站适配器（如数据库访问逻辑）
    
- 单体的数据库模式（这部分最棘手）
    

**提取的迭代方法**：

- 首次提取可以保留命令和查询等公开 API，只提取算法的核心部分
    
- 后续迭代再逐步提取数据访问层
    
- 最终把数据库模式也拆分出去
    

### 第三部分：设计服务与单体的协作方式（13.3）——本章最硬核的部分

这是 Richardson 写作的精华，也是工业界落地绞杀者模式时最容易翻车的地方。

**13.3.1 设计集成胶水**

当新服务的领域模型与单体的领域模型不同时（几乎是必然的），必须实现 **反腐蚀层（Anti-Corruption Layer, ACL）**​ 。

**ACL 的本质**​ ：一种在不同领域模型之间进行转换的软件层，旨在防止一个模型的概念"污染"另一个模型。

**为什么 ACL 不可避免？**​ Richardson 以 FTGO 为例 ：单体有一个职责过载的 `Order` 实体，而新的 Delayed Delivery Service 有一个职责单一的 `Delivery` 实体。类名、字段名、字段值都不同。如果不做翻译，单体的糟糕模型会"腐蚀"新服务的干净模型。

**ACL 的双向性**：

- **服务调用单体**：服务通过 ACL 接口（如 `CustomerContactInfoRepository`）定义自己的领域语言，实现类负责调用单体并翻译响应
    
- **服务订阅单体事件**：单体发布的领域事件使用单体的领域语言，服务的事件处理器必须翻译事件到自己的领域模型
    
- **单体调用服务**：单体也需要 ACL 来调用服务——例如 FTGO 单体通过 `DeliveryService` 接口发送通知消息，实现类将参数翻译为 Delivery Service 能理解的消息
    

> 📌 ACL 是微服务重构中**最重要的架构决策之一**。它决定了新服务能否保持"干净"，还是会被单体的技术债拖垮。

**13.3.2 在服务和单体之间维持数据一致性**

这是重构期最棘手的问题。当更新请求需要同时修改服务和单体的数据时，必须保持跨系统的一致性。

**解决方案**​ ：使用**事务性消息（Transactional Messaging）**，由框架（如 Eventuate Tram）实现。

- **简单场景**：请求方发送通知消息或发布事件来触发更新
    
- **复杂场景**：请求方必须使用 **Saga**​ 来维护数据一致性
    

**单体如何发布领域事件？**​ 这是关键挑战 ：

- **方法一**：在单体中所有修改特定实体的地方，插入对事件发布 API 的调用
    
- **方法二**：使用 CDC（Change Data Capture，如 Debezium）捕获数据库变更日志，转换为领域事件
    
- 一旦单体能够发布事件，新服务就可以订阅这些事件来维护自己的数据副本
    

**查询的处理**：

- 服务可以通过**单体的查询 API 检索数据**
    
- 或者通过**订阅单体事件维护副本**（CQRS 思想，见第7章）
    

**13.3.3 处理身份验证和访问授权**

遗留单体通常有自己的身份认证机制（可能是老旧的 session 或自定义 token）。新服务需要使用现代认证机制（如 OAuth2 + JWT，见第11章）。

**集成方案**：

- API Gateway 负责验证客户端身份并颁发 JWT
    
- JWT 同时传递给单体和微服务
    
- 单体需要改造以验证 JWT（这是"修改单体"的典型场景）
    
- 微服务使用 JWT 获取主体身份和角色
    

### 第四部分：两个完整案例（13.4-13.5）

**13.4 将新功能实现为服务：处理错误配送订单**

- **Delayed Delivery Service 的设计**：一个全新的、职责单一的服务
    
- **集成胶水设计**：通过 ACL 调用单体的查询 API 获取客户联系信息，通过事件订阅获取订单状态变更
    

**13.5 从单体中提取送餐管理功能**

- **现有送餐管理功能分析**：单体中职责过载的 Order 实体包含了送餐逻辑
    
- **Delivery Service 概览**：全新的送餐服务，拥有自己的数据库
    
- **领域模型设计**：干净的 `Delivery` 聚合，与单体的 `Order` 彻底解耦
    
- **集成胶水设计**：ACL 双向翻译，单体通过 ACL 调用 Delivery Service，Delivery Service 订阅单体的 Order 事件
    
- **修改 FTGO 单体**：这是最痛苦的部分——需要在单体中插入 ACL 代码，让其调用新服务
    

## 三、工业实践视角：绞杀者模式在 2024-2026 年的真实样貌

综合工业界最新实践，我给你一个完整的"单体到微服务"迁移框架：

### 1. 提取顺序的决策矩阵

**🎯 优先提取的模块**（高 ROI）：

- **高频变更的模块**：业务变化快的模块，微服务化后立即提升交付速度
    
- **造成扩展性/可靠性问题的模块**：如支付模块需要独立扩展
    
- **边界清晰的模块**：如认证、通知、文件服务
    
- **边缘模块**：依赖少、被调用多
    

**❌ 暂缓提取的模块**：

- 接近生命周期末期的模块
    
- 极少变更的遗留模块（每年改一次，提取 ROI 太低）
    
- 领域边界模糊的模块（先通过 DDD 事件风暴理清边界）
    

Shopify 的工程实践印证了这一点 ：在 280 万行 Ruby 代码的单体中，他们没有贸然提取，而是先**强制执行内部边界**（使用模块可见性规则和显式接口），在分布之前先有纪律。

### 2. 数据迁移的三阶段策略

这是 2026 年工业界的共识 ：

**Phase 1：共享数据库（过渡期）**

- 新服务和旧单体连接同一个数据库
    
- 优点：不需要数据同步
    
- 缺点：schema 变更需双边同步
    
- **关键认知**：不要急着分库！先拆进程再分库
    

**Phase 2：API 代理**

- 新服务有自己的数据库
    
- 迁移期间通过 API 访问旧数据库的数据
    
- 开始建立数据边界
    

**Phase 3：完全分离**

- 每个服务有自己的数据库
    
- 服务间通过事件同步数据
    
- 使用双写（Dual-Write）+ 数据核对（Reconciliation）确保一致性
    
- 验证无误后才切割数据源
    

**Wonder Cement 案例**​ ：一家印度水泥厂的厂内物流系统，通过 Azure 微服务架构，分两个阶段、三个月时间、零运营中断完成迁移。他们使用 **Service Bus 做事件驱动通信**、**Blob Storage 做文档存储**、**Cache 做低延迟访问**。关键是：**每次只提取一个能力，双写+核对+验证后才切割数据**。

### 3. 并行运行模式（Parallel Run）

对于关键功能，工业界使用**并行运行模式**​ ：

- 单体和微服务同时处理相同请求
    
- 初期只返回单体的响应给用户
    
- 微服务的响应与单体响应进行比对验证
    
- 置信度足够后，逐步将流量切到微服务
    

这是降低关键功能迁移风险的有效手段。

### 4. 绞杀者模式的工业反模式

**反模式一：过早分库**

很多团队急于"每个服务自己的数据库"，结果跨服务查询从 JOIN 变成 API 调用，数据一致性从事务变成事件同步，运维负担陡增。**正确做法：共用 DB 撑好几个月再分**​ 。

**反模式二：功能冻结**

"等新服务写好了再加功能"——结果新服务写了 6 个月还没好，旧系统 6 个月没更新，客户跑了。**正确做法：迁移和功能开发并行，这正是绞杀者模式的设计初衷**​ 。

**反模式三：按技术层而非业务能力提取**

按 UI、业务逻辑、数据层提取，必然制造分布式单体。**正确做法：提取完整的垂直切片（业务能力强）**​ 。

**反模式四：忽略"最后 10%"**

最难、耦合最紧的服务留到最后，往往成为"永远提取不完"的尾巴。**正确做法：接受某些代码永远不会被迁移——每年只改一次的遗留模块，提取的 ROI 太低，可以让它继续在单体中运行**​ 。

**反模式五：过早退役单体**

单体是你的安全网，在服务稳定前就关闭它，等于撤掉救生圈。**正确做法：让单体自然萎缩，直到它小到可以"无声退役"**​ 。

### 5. 绞杀者模式不适用的场景

工业界 2026 年的诚实判断 ：

> ⚠️ 绞杀者模式并非免费——它增加了路由门面、反腐蚀层，以及在一段时间内故意并行运行两个系统。

**不适用场景**：

- **小型或简单应用**：门面+提取机制的成本可能超过干净重写
    
- **接近生命周期末期**：即将退役的系统，增量现代化是浪费
    
- **领域边界完全未知**：无法识别限界上下文，就无法沿着边界提取。先通过事件风暴等方法做领域分解
    

## 四、本章的核心洞见（我自己的提炼）

读完这一章，我认为 Richardson 真正想传递的不是"绞杀者模式怎么用"，而是四个更深层的认知：

**第一，微服务重构的本质是"用时间换安全"。**​ Big Bang 重写试图"用空间换时间"——一次性投入大量资源，期望在某个未来时间点一次性收获。绞杀者模式反其道而行之——接受重构是一个**长达数年的持续过程**​ ，但通过让第一个服务尽早上线、尽早产生价值，把"多年后的大收益"转换成"每季度的小收益+持续学习"。这种"风险与时间的解耦"，是微服务重构的第一性原理。

**第二，反腐蚀层（ACL）是微服务重构的"免疫系统"。**​ 新服务的领域模型是干净的、现代的；单体的领域模型是腐化的、过载的。如果不做 ACL，单体的技术债会像病毒一样感染新服务，让你的微服务架构从出生起就带着单体的病。**ACL 的本质是"翻译+隔离"——它让新服务能够用自己纯净的领域语言思考，同时在边界处与单体对话**。这是 Richardson 在第13章最具工程深度的贡献。

**第三，数据一致性是重构期最深的坑，事务性消息是唯一出路。**​ 当更新请求需要同时修改服务和单体的数据时，传统分布式事务（2PC）在遗留系统中往往不可用。**使用框架（如 Eventuate Tram）实现的事务性消息，配合 Saga，是跨系统数据一致性的标准答案**——这正是第3章事务性发件箱和第4章 Saga 在重构场景下的实战应用。

**第四，绞杀者模式不是"银弹"，它有明确的适用边界。**​ Richardson 诚实地指出了它的弊端：需要修改遗留代码、古老技术栈下修改困难 。工业界 2026 年进一步明确了不适用场景：小系统、近退役系统、领域边界未知的系统 。**很多时候，"不重构"比"重构"更明智**——如果你的单体还能通过内部模块化、CI/CD 优化、团队自主性提升来解决问题，那么微服务化可能只是用"分布的复杂度"替换"单体的复杂度"，净收益为负。Amazon Prime Video 在 2023 年的微服务回退案例，以及 Segment 从微服务回归单体的案例，都说明**微服务不是终极答案，而是特定上下文下的权衡选择**。

> 💡 一个反直觉的洞见：**很多时候，"不提取某些模块"比"提取所有模块"更需要智慧**。Industrial 数据表明，遗留系统中约有 20-30% 的模块每年只变更一次甚至更少——这些模块的提取 ROI 太低，让它们继续在单体中运行反而是最优决策 。绞杀者模式的真正目标不是"消灭单体"，而是"让单体萎缩到无足轻重的程度"。当单体只剩下每年改一次的遗留代码时，它已经不构成"单体地狱"，你可以选择保持现状，或者低成本地将其整体废弃。**这种"接受部分遗留"的务实态度，才是 Richardson 绞杀者模式在 2026 年工业界最成熟的诠释**。
