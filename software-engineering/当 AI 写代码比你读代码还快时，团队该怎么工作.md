## 一、现状：Code Review这个制度已经跟不上了

现在的 AI 编程工具（Agent）写一个下午代码，比一个团队一周仔细读完的代码量还要大。这不是夸张，是已经发生的事。

过去几十年，代码审查（Code Review）能成立，靠的是一个隐含的前提：**写代码的速度和读代码的速度差不多**，至少在同一个数量级。一个人写一段代码，另一个人花差不多的时间读完，给出意见。这个前提现在不成立了。

于是团队面临两个选择，两个都不好：

- **死守审查流程**：每一行代码都认真读、认真评。结果就是你自己成了整个团队的瓶颈——所有人的工作都卡在你读代码这一步。
- **直接放行**：不认真看了，点个 Approve 完事。代码审查变成了一个橡皮图章，走个形式流程。
    
现实中，大多数团队选了第二个。大家心照不宣地继续走审批流程，但实际上已经不怎么看了。

这带来的最大问题不是 bug 漏过了——bug 上线了可以修。最大的问题是**虚假的安全感**：流程还在走，章还在盖，大家感觉"代码被审过了"，于是放心地发布了。这种信任是假的，但它确实让人敢把代码发到线上去。

但话说回来，代码审查从来就不是目的本身。你真正需要的不是"有人读了一遍代码"，而是两件事：**你能掌控这个项目，并且对它有足够的信心，知道发布出去的东西不会出大问题**。读代码只是达到这两个目的的一种手段，而且是很弱的一种。手段被误当成了目的。

## 二、为什么人现在读不懂 Agent 写的代码了

要理解为什么旧的审查方式不行了，先看一个基本事实：**人做代码审查之所以有价值，不是因为人"仔细"，而是因为人对代码库有足够的了解。**

一个好的审查者，手上正经写过这个项目里的代码，脑子里装着系统是怎么运作的、各个模块之间怎么交互的。这种对系统的了解才是审查质量的来源，阅读代码只是把这种了解用出来的过程。如果一个人对项目不了解，那他的眼睛虽然在动、在读代码，实际上什么都没看出来——就像让一个不懂建筑的人翻图纸，字都认得，但看不出哪里有问题。

Agent 时代把人从这个位置上推开了，原因很简单：**人和 Agent 写代码的"成本结构"完全不同。**

### 速度层面

Agent 生成一个代码改动的成本几乎为零——它不需要思考半天，不需要查文档，不需要休息。而一个人手写代码，在 Agent 旁边就成了整个流程里最慢的一环。理性的做法是让 Agent 放手去跑，你别拦着。但问题是，一旦你停下来不亲手写代码了，你对项目的了解就开始退化。你不再每天泡在代码里，慢慢地，你就不了解最新的实现了。

### 代码风格层面

即使一个人速度快到能跟上 Agent 的产出，还有一个更深的问题。一个项目的代码库，本质上是无数个小决策积累起来的：这个地方要不要抽成公共函数？日志打到什么粒度合适？模块边界画在哪？这些问题没有标准答案，取决于写代码的人对项目的理解和取舍。

Agent 写代码时，遵循的是它自己的逻辑一致性——它不会像人一样因为赶工期就偷懒少写测试，也不会因为觉得麻烦就跳过重构。这听起来是好事，但也意味着 Agent 产出的代码有一种统一的"质地"。如果一个人在中间插手，用手工的方式写几段代码进去，这段代码的"质地"就跟 Agent 写的不一样——取舍标准不同、抽象层次不同、边界处理方式不同。两种不同风格混在同一个项目里，整个系统的可读性反而会下降。

综合起来就是：**在一个大量使用 Agent 的项目里，人既跟不上 Agent 的产出速度，写出来的代码也跟 Agent 的风格不兼容**​ 结果是，人对代码库的实时了解越来越弱，到了一定程度，再做代码审查就变成了在看自己已经理解不了的东西。

这也解释了为什么有些团队引入了 Agent 却没有提速——瓶颈往往就是那个还在坚持亲手写代码、亲手审代码的人。不是他不努力，而是他还在用旧的工作方式。

## 三、其实 senior 工程师早就这么干了

上面说的这些，听起来像是 Agent 时代的新问题，但其实不是。

你回想一下，你认识的最资深的那几个系统工程师或者首席架构师，他们最后一次逐行读完自己负责的全部代码是什么时候？大概率是很久以前的事了。一个有经验的系统工程师带一个大项目，靠的不是自己逐行读所有代码，而是两件事：一是信任下面干活的人，二是了解系统的整体架构。没人会觉得这种管理方式"不负责任"。

逐行读代码这件事，本来就是基层开发者才消费得起的——项目小、代码量少的时候才能做到。后来大家把"我能逐行读"等同于"我对项目有把握"，其实是个误会。Agent 时代的到来，只是把所有级别的工程师都推到了 senior 原本就在的位置上：你不可能读完所有代码，你得找到别的办法来建立信心。

那 senior 工程师的信心从哪来？具体来说，来自这些东西：

- 跟某个同事合作久了，知道他写出来的东西靠谱
- 测试套件在历次发布中都扛住了
- 系统上线后跑了很久，没出过大问题
- 灰度发布期间用户反馈正常
- 监控面板上几个版本的指标都很平稳
    
这些都是信号，不是某一个Pull Request diff/ Merge Request diff 能告诉你的。代码审查在这些信号里反而是最弱的一个。它一直在假装回答一个问题："系统整体还好不好？"但它其实答不上来，因为它只看得到PR一小块改动。

## 四、核心问题：系统的可预测性在下降

随着一个项目不断被修改、功能不断增加，它会自然地变得越来越复杂。这是软件工程里很早就被记录的现象：一个正在被使用的系统，如果不持续投入精力去整理和维护，它的复杂度只会越来越高。

在 Agent 出现之前，人类写代码和读代码的速度本身就起到了一定的限速作用——人写得慢，所以系统变化得也慢，复杂度的增长速度相对可控。Agent 出现之后，这个限速器没了。一个可用的产品可以在一小时内搭出来，也可以在一夜之间变得没人看得懂。

这种变化带来的直接后果是：**你越来越难预测自己的系统了**​ 改了 A 模块的一个参数，你不再能说清楚 B 模块会不会受影响、会怎么受影响。

所谓"对系统的信任"，本质上就是这种预测能力。不是一种感觉，不是 CI 全绿，而是你有把握说"我改了这个，系统会在那几个方面做出什么样的反应"。这个能力不是读一个 diff 能给的，因为预测是整个系统的属性，不是某一次改动的属性。

所以问题不应该问"这个 diff 对不对"，而应该问"系统的整体状态是在变好还是在变差"。这个问题的答案不需要打开任何 diff 就能找到。

## 五、替代方案：读系统，不读 diff

既然 diff 给不了你想要的答案，那就别读 diff 了。去读系统本身。

一个运行中的系统会持续向外发送信号，告诉你它现在的状态。你不需要打开代码文件，只需要观察这些信号。以下是几个最有效的方式：

### 1. Bug 列表的分布

Bug 不是均匀分布的。某些模块反复出 bug，某些接口每个月都冒出新的边界情况——这些地方就是系统"漏水"的地方。

Agent 犯的错误尤其有参考价值。人类开发者遇到模糊的接口或不完整的规格时，往往会凭经验猜一个合理的做法，把问题盖住。Agent 不会猜，它会严格按照字面意思执行，然后出错。所以 Agent 犯的错通常会精准地指向一个不干净的输入：要么是接口定义模糊，要么是规格说明漏了某个情况。

### 2. 变异测试的结果

变异测试的做法是：故意改坏一段正确的代码（比如把一个大于号改成小于号，或者删掉一个分支），然后跑测试，看有没有测试失败。如果测试还是全绿，说明你的测试套件没有覆盖到这个行为——它以为自己保护了这个功能，其实没有。

每一个"没被检测出来的改动"就是一个潜在的 bug 藏身之处。

### 3. 代码结构分析

有些代码特征直接关联着风险：

- 一个函数里分支特别多，说明它处理的状态组合比规格需要的更复杂
- 同一份数据被存在两个地方，意味着将来一定有人改了一个忘了改另一个
- 两个 Agent 反复修改同一个接口边界，说明这个边界划分本身有问题
    
### 4. 线上监控数据

系统上线后的错误率、延迟分布、资源消耗等指标，是最真实的信号。一个安静的监控面板比一百个通过的 diff 更有说服力——前提是这个监控确实是有效的（有时候"没报警"只是因为没人触发那个功能）。

## 六、怎么用这些信号来改进系统

光看信号不够，关键是要形成闭环。流程是这样的：

**观察到问题 → 找到导致问题的根源 → 从源头上收紧条件**

举个例子：

- Bug 列表显示某个模块反复出问题 → 去看这个模块的接口定义 → 发现接口语义模糊，Agent 每次理解得都不一样 → 把这个接口重构成语义明确的版本，同时补上针对性的测试用例
- 变异测试发现某个核心逻辑没有测试覆盖 → 补上测试，要求测试用真实的输入数据、断言真实的行为，而不是只检查返回值的类型
- 两个 Agent 反复在同一个地方产生冲突 → 说明这个模块的边界划分不合理 → 重新设计边界，让职责划分清晰到 Agent 不会再误解
    
这里的核心心态转变是：**Agent 犯错不是 Agent 的能力问题，而是你的输入条件不够好**​ 它暴露出来的每一个错误，都是在告诉你"这里有一个你没清理干净的地方"。你应该把这些错误当成改进系统的线索，而不是简单地认为"模型不行，换个写法再试一次"。

## 七、关于测试质量的重要提醒

上面多次提到测试，这里需要说清楚什么样的测试是有价值的。

一个测试有价值，必须满足两个条件：

1. **它验证的是真实行为，不是代码结构**​ 比如一个测试只检查"这个函数返回了一个对象，对象里有这几个字段"，但没有验证这些字段的值在实际业务场景下是否正确。这种测试通过了也没意义。
2. **它的断言(Assert)够严格**​ 如果代码真的出了回归问题，这个测试必须会变红。如果一个测试永远都是绿的——不管你改了什么——那它就是在骗你。
    
同样的逻辑适用于所有信号：一个信号只有在你确认过它能正常触发的时候，才值得信任。如果监控系统从来没报过警，你得先确认它不是因为配置错误而沉默。

## 八、一个重要的区分

不是所有的"系统复杂度高"都是坏事。比如一个插件系统允许一百种不同的扩展实现同一个接口，从"有多少种不同的实现方式"这个角度看，它的熵非常高。但这是设计目标，不是系统腐化。

信号能告诉你复杂度在哪，但不能自动告诉你这种复杂度是不是合理的。这个判断需要人来下。

另外，上面提到的所有信号（Bug 列表、变异测试结果、结构分析）都是**事后**的——它们告诉你问题已经发生了或者存在了。它们能帮你发现和修复问题，但不能在问题产生之前阻止它。要真正做到预防，需要把注意力放到更上游的地方：写好规格说明、设计清晰的接口、搭建完善的各种自动化测试基础设施。

---

## 九、总结

把上面所有的内容浓缩成一句话：

**别再试图当守门人了。开始观察系统发出的信号，找到问题根源，然后一轮一轮地收紧输入条件。**

具体来说，新的工作方式是这样的：

| 旧方式            | 新方式                 |
| -------------- | ------------------- |
| 逐行读 diff，找 bug | 看 Bug 列表的分布，找系统性弱点  |
| 靠审查来保证质量       | 靠测试硬度、类型系统、监控来保证质量  |
| 出了问题怪写代码的人/模型  | 出了问题追溯输入条件哪里不干净     |
| 信任来自"我读过这段代码"  | 信任来自系统持续表现稳定、信号持续正常 |

在这个新方式里，人的工作不再是"读代码、挑毛病"，而是**定义清楚系统应该是什么样子的，搭建好验证和监控的基础设施，然后根据系统反馈的信号持续调整**。写代码这件事本身，越来越多地交给 Agent 去做。人负责的是更高层面的事情：定方向、划边界、建机制、看信号。

这也是为什么文章最后留了一个问题：如果人不写代码了、不读代码了，那人的工作到底是什么？这个问题值得单独讨论，但至少现在已经清楚的是——**守在门口逐行检查的日子结束了。**
