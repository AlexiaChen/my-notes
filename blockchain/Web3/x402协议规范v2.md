
# X402 协议规范v2

## 文档范围

本规范定义了 x402 互联网原生支付的核心协议。它涵盖：

- **协议基础**：支付要求格式、支付负载结构和核心消息模式
- **促进者接口**：用于支付验证和结算的标准 API
- **支付方案**：可扩展的支付方式（目前支持 "exact" 方案）
- **安全考虑**：重放攻击预防和最小化信任

**不在范围内**：本规范不包括：

- 特定传输的实现（在传输规范中涵盖）
- 特定实现模式（在应用说明中涵盖）
- 特定框架的集成
- 客户端预算管理
- 会话处理机制

---

## 架构

x402 由三个核心组件组成：

1. **类型**：独立于传输机制和支付方案的核心数据结构（例如，`PaymentRequirements`、`PaymentPayload`、`SettlementResponse`）
2. **逻辑**：依赖于支付方案（例如，exact、deferred）和网络（例如，evm、solana 等）的支付形成和验证逻辑
3. **表示**：支付数据的传输和信令方式，取决于传输机制（例如，HTTP、MCP、A2A）

---

## 1. 概述

x402 是一个开放支付标准，使客户端能够为外部资源付费。该协议定义了可在各种传输层上实现的标准化消息格式和支付流程，为不同支付方案、网络和传输层之间的支付提供了标准化机制。

本规范基于 [Coinbase x402 仓库](https://github.com/coinbase/x402) 中可用的 x402 协议实现和文档。它旨在为 x402 协议提供全面且与实现无关的规范。

---

## 2. 核心支付流程

x402 协议遵循带支付集成的标准请求-响应周期：

1. **客户端请求**：客户端向资源服务器发起请求
2. **需要付款响应**：如果没有附加有效付款，服务器以需要付款信号和支付要求响应
3. **付款授权请求**：客户端在后续请求中提交签名的付款授权
4. **结算响应**：服务器验证付款授权并启动区块链结算

---

## 3. 协议组件

x402 协议涉及三个主要组件：

- **资源服务器**：需要付费才能访问受保护资源（API、内容、数据等）的服务
- **客户端**：请求访问受保护资源的任何应用程序或智能体
- **促进者**：处理支付验证和区块链结算的服务

---

## 4. 响应类型

x402 协议定义了具有特定语义的标准响应类型：

- **成功**：请求成功，支付已验证并结算
- **需要付款**：需要付款才能访问资源
- **无效请求**：无效的付款负载或支付要求
- **服务器错误**：支付处理期间的服务器错误

特定传输的实现将这些响应类型映射到适当的传输机制（例如，HTTP 状态码、JSON-RPC 错误码等）。

---

## 5. 类型

本节定义了 x402 协议中使用的核心数据结构。这些结构完全独立于传输机制和支付方案。所有传输和方案都使用这些完全相同的数据结构，区别仅在于它们的表示方式（传输层）和应用的验证/结算逻辑（方案层）。

### 5.1 PaymentRequired 模式

#### 5.1.1 JSON 负载

当资源服务器需要付款时，它以需要付款信号和包含支付要求的 JSON 负载响应。示例：

```json
{
  "x402Version": 2,
  "error": "PAYMENT-SIGNATURE header is required",
  "resource": {
    "url": "https://api.example.com/premium-data",
    "description": "Access to premium market data",
    "mimeType": "application/json"
  },
  "accepts": [
    {
      "scheme": "exact",
      "network": "eip155:84532",
      "amount": "10000",
      "asset": "0x036CbD53842c5426634e7929541eC2318f3dCF7e",
      "payTo": "0x209693Bc6afc0C5328bA36FaF03C514EF312287C",
      "maxTimeoutSeconds": 60,
      "extra": {
        "name": "USDC",
        "version": "2"
      }
    }
  ],
  "extensions": {}
}
```

#### 5.1.2 字段说明

`PaymentRequired` 模式包含以下字段：

| 字段名 | 类型 | 必需 | 描述 |
|--------|------|------|------|
| `x402Version` | `number` | 必需 | 协议版本标识符（必须为 2） |
| `error` | `string` | 可选 | 解释为什么需要付款的人类可读错误消息 |
| `resource` | `object` | 必需 | 描述受保护资源的 ResourceInfo 对象 |
| `accepts` | `array` | 必需 | 定义可接受付款方式的支付要求对象数组 |
| `extensions` | `object` | 可选 | 协议扩展数据 |

`accepts` 数组中的每个 `PaymentRequirements` 对象包含：

| 字段名 | 类型 | 必需 | 描述 |
|--------|------|------|------|
| `scheme` | `string` | 必需 | 支付方案标识符（例如，"exact"） |
| `network` | `string` | 必需 | CAIP-2 格式的区块链网络标识符（例如，"eip155:84532"） |
| `amount` | `string` | 必需 | 以原子代币单位为单位的所需付款金额 |
| `asset` | `string` | 必需 | 代币合约地址或法币的 ISO 4217 货币代码 |
| `payTo` | `string` | 必需 | 接收方钱包地址或角色常量（例如，"merchant"） |
| `maxTimeoutSeconds` | `number` | 必需 | 付款完成允许的最长时间 |
| `extra` | `object` | 可选 | 方案特定的附加信息 |

`ResourceInfo` 对象包含：

| 字段名 | 类型 | 必需 | 描述 |
|--------|------|------|------|
| `url` | `string` | 必需 | 受保护资源的 URL |
| `description` | `string` | 可选 | 资源的人类可读描述 |
| `mimeType` | `string` | 可选 | 预期响应的 MIME 类型 |

`Extensions` 对象是一个键值映射，其中每个键是扩展标识符，每个值遵循标准化结构：

| 字段名 | 类型 | 必需 | 描述 |
|--------|------|------|------|
| `info` | `object` | 必需 | 服务器提供的扩展特定数据 |
| `schema` | `object` | 必需 | 定义 `info` 预期结构的 JSON 模式 |

扩展启用了核心支付机制之外的模块化可选功能。服务器在 `PaymentRequired` 中通告支持的扩展，客户端在 `PaymentPayload` 中回显它们。客户端必须至少包含收到的信息；它可能会附加其他信息，但不能删除或覆盖现有信息。

### 5.2 PaymentPayload 模式

#### 5.2.1 JSON 结构

客户端在支付负载字段中包含支付授权为 JSON：

```json
{
  "x402Version": 2,
  "resource": {
    "url": "https://api.example.com/premium-data",
    "description": "Access to premium market data",
    "mimeType": "application/json"
  },
  "accepted": {
    "scheme": "exact",
    "network": "eip155:84532",
    "amount": "10000",
    "asset": "0x036CbD53842c5426634e7929541eC2318f3dCF7e",
    "payTo": "0x209693Bc6afc0C5328bA36FaF03C514EF312287C",
    "maxTimeoutSeconds": 60,
    "extra": {
      "name": "USDC",
      "version": "2"
    }
  },
  "payload": {
    "signature": "0x2d6a7588d6acca505cbf0d9a4a227e0c52c6c34008c8e8986a1283259764173608a2ce6496642e377d6da8dbbf5836e9bd15092f9ecab05ded3d6293af148b571c",
    "authorization": {
      "from": "0x857b06519E91e3A54538791bDbb0E22373e36b66",
      "to": "0x209693Bc6afc0C5328bA36FaF03C514EF312287C",
      "value": "10000",
      "validAfter": "1740672089",
      "validBefore": "1740672154",
      "nonce": "0xf3746613c2d920b5fdabc0856f2aeb2d4f88ee6037b8cc5d04a71a4462f13480"
    }
  },
  "extensions": {}
}
```

#### 5.2.2 字段说明

`PaymentPayload` 模式包含以下字段：

| 字段名 | 类型 | 必需 | 描述 |
|--------|------|------|------|
| `x402Version` | `number` | 必需 | 协议版本标识符 |
| `resource` | `object` | 可选 | 描述正在访问的资源的 ResourceInfo 对象 |
| `accepted` | `object` | 必需 | 指示选择的付款方式的 PaymentRequirements 对象 |
| `payload` | `object` | 必需 | 方案特定的支付数据 |
| `extensions` | `object` | 可选 | 协议扩展数据 |

`accepted` 字段包含 `PaymentRequirements` 对象（见第 5.1.2 节）。

`payload` 字段包含方案特定的数据。例如，对于 exact EVM 方案，这包括：

| 字段名 | 类型 | 必需 | 描述 |
|--------|------|------|------|
| `signature` | `string` | 必需 | 用于授权的 EIP-712 签名 |
| `authorization` | `object` | 必需 | EIP-3009 授权参数 |

`Authorization` 对象包含以下字段：

| 字段名 | 类型 | 必需 | 描述 |
|--------|------|------|------|
| `from` | `string` | 必需 | 付款方的钱包地址 |
| `to` | `string` | 必需 | 接收方的钱包地址 |
| `value` | `string` | 必需 | 以原子单位为单位的付款金额 |
| `validAfter` | `string` | 必需 | 授权生效的 Unix 时间戳 |
| `validBefore` | `string` | 必需 | 授权过期的 Unix 时间戳 |
| `nonce` | `string` | 必需 | 32 字节随机数，用于防止重放攻击 |

---

### 5.3 SettlementResponse 模式

#### 5.3.1 JSON 结构

支付结算后，服务器在支付响应字段中包含交易详情为 JSON：

```json
{
  "success": true,
  "transaction": "0x1234567890abcdef1234567890abcdef1234567890abcdef1234567890abcdef",
  "network": "eip155:84532",
  "payer": "0x857b06519E91e3A54538791bDbb0E22373e36b66"
}
```

#### 5.3.2 字段说明

`SettleResponse` 模式包含以下字段：

| 字段名 | 类型 | 必需 | 描述 |
|--------|------|------|------|
| `success` | `boolean` | 必需 | 指示支付结算是否成功 |
| `errorReason` | `string` | 可选 | 结算失败时的错误原因（成功时省略） |
| `payer` | `string` | 可选 | 付款方钱包的地址 |
| `transaction` | `string` | 必需 | 区块链交易哈希（结算失败时为空字符串） |
| `network` | `string` | 必需 | CAIP-2 格式的区块链网络标识符 |
| `extensions` | `object` | 可选 | 协议扩展数据 |

---

### 5.4 VerifyResponse 模式

#### 5.4.2 字段说明

`VerifyResponse` 模式包含以下字段：

| 字段名 | 类型 | 必需 | 描述 |
|--------|------|------|------|
| `isValid` | `boolean` | 必需 | 指示付款授权是否有效 |
| `invalidReason` | `string` | 可选 | 无效的原因（有效时省略） |
| `payer` | `string` | 可选 | 付款方钱包的地址 |

## 6. 支付方案（逻辑）

本节描述 x402 协议支持的支付方案。支付方案定义了支付如何在特定支付网络上形成、验证和结算。方案独立于底层传输机制。

每个方案定义：

- 如何在 `PaymentPayload` 内构造 `payload` 字段
- 结算和验证程序
- `PaymentRequirements` 的 `extra` 字段中的方案特定要求

### 6.1 Exact 方案（EVM 概述）

"exact" 方案使用 EIP-3009（带授权的转账）来实现 ERC-20 代币特定金额的安全、无 gas 转账。

#### 6.1.1 EIP-3009 授权

授权遵循 EIP-3009 `transferWithAuthorization` 标准：

```javascript
const authorizationTypes = {
  TransferWithAuthorization: [
    { name: "from", type: "address" },
    { name: "to", type: "address" },
    { name: "value", type: "uint256" },
    { name: "validAfter", type: "uint256" },
    { name: "validBefore", type: "uint256" },
    { name: "nonce", type: "bytes32" },
  ],
};
```

#### 6.1.2 验证步骤

促进者执行以下验证步骤：

1. **签名验证**：验证 EIP-712 签名有效且由付款方正确签名
2. **余额验证**：确认付款方有足够的代币余额进行转账
3. **金额验证**：确保付款金额满足或超过所需金额
4. **时间窗口检查**：验证授权在其有效时间范围内
5. **参数匹配**：确认授权参数与原始支付要求匹配
6. **交易模拟**：模拟 `transferWithAuthorization` 交易以确保它会成功

#### 6.1.3 结算

结算通过在 ERC-20 合约上调用 `transferWithAuthorization` 函数并使用支付负载中提供的签名和授权参数来执行。

---

### 6.2 Exact 方案（SVM 概述）

对于 Solana (SVM)，`exact` 方案使用 `TransferChecked` 实现 SPL 代币。关键验证要求包括：

- 强制执行严格的指令布局（计算单元限制、计算单元价格、TransferChecked）
- 确保促进者费用支付者不出现在任何指令账户中，并且不是转账 `authority` 或 `source`
- 限制计算单元价格以减轻 gas 滥用
- 验证目标 ATA 与 `payTo`/`asset` PDA 和账户存在规则匹配
- 要求转账 `amount` 完全等于 PaymentRequirements 中指定的 `amount`

完整的 SVM 细节在 `specs/schemes/exact/scheme_exact_svm.md` 中指定。

## 7. 促进者接口

促进者提供用于支付验证和结算的 HTTP REST API。这使资源服务器能够将区块链操作委托给可信的第三方或自己托管端点。请注意，虽然核心 x402 协议是传输无关的，但促进者 API 目前标准化为 HTTP 端点。

### 7.1 POST /verify

在不执行区块链交易的情况下验证付款授权。

**请求（Exact 方案）：**

```json
{
  "paymentPayload": {
    /* PaymentPayload 模式 */
  },
  "paymentRequirements": {
    /* PaymentRequirements 模式 */
  }
}
```

包含实际数据的示例：

```json
{
  "paymentPayload": {
    "x402Version": 2,
    "resource": {
      "url": "https://api.example.com/premium-data",
      "description": "Access to premium market data",
      "mimeType": "application/json"
    },
    "accepted": {
      "scheme": "exact",
      "network": "eip155:84532",
      "amount": "10000",
      "asset": "0x036CbD53842c5426634e7929541eC2318f3dCF7e",
      "payTo": "0x209693Bc6afc0C5328bA36FaF03C514EF312287C",
      "maxTimeoutSeconds": 60,
      "extra": {
        "name": "USDC",
        "version": "2"
      }
    },
    "payload": {
      "signature": "0x...",
      "authorization": {
        "from": "0x...",
        "to": "0x...",
        "value": "10000",
        "validAfter": "1740672089",
        "validBefore": "1740672154",
        "nonce": "0x..."
      }
    }
  },
  "paymentRequirements": {
    "scheme": "exact",
    "network": "eip155:84532",
    "amount": "10000",
    "asset": "0x036CbD53842c5426634e7929541eC2318f3dCF7e",
    "payTo": "0x209693Bc6afc0C5328bA36FaF03C514EF312287C",
    "maxTimeoutSeconds": 60,
    "extra": {
      "name": "USDC",
      "version": "2"
    }
  }
}
```

**成功响应：**

```json
{
  "isValid": true,
  "payer": "0x857b06519E91e3A54538791bDbb0E22373e36b66"
}
```

**错误响应：**

```json
{
  "isValid": false,
  "invalidReason": "insufficient_funds",
  "payer": "0x857b06519E91e3A54538791bDbb0E22373e36b66"
}
```

| `extra` | `object` | 可选 | 附加的方案特定配置 |

## 8. 发现 API

x402 协议包含一个发现机制，允许客户端查找和探索可用的启用 x402 的资源。这使创建市场（称为"Bazaars"）成为可能，用户可以在其中发现和访问变现的 API 和数字服务。

发现目前实现为 HTTP REST API，尽管发现的资源可以使用任何 x402 支持的传输。

### 8.1 GET /discovery/resources

从 Bazaar 列出可发现的 x402 资源。

**请求参数：**

| 参数 | 类型 | 必需 | 描述 | 默认值 |
|------|------|------|------|--------|
| `type` | `string` | 可选 | 按资源类型过滤（例如，"http"） | - |
| `limit` | `number` | 可选 | 返回的最大结果数（1-100） | 20 |
| `offset` | `number` | 可选 | 分页要跳过的结果数 | 0 |

**响应：**

```json
{
  "x402Version": 2,

    {

      "type": "http",

  "pagination": {
    "limit": 10,
    "offset": 0,
    "total": 1
  }
}
```

### 8.2 发现的资源字段

| 字段名 | 类型 | 必需 | 描述 |
|--------|------|------|------|
| `resource` | `string` | 必需 | 正在变现的资源 URL 或标识符 |
| `type` | `string` | 必需 | 资源类型（目前 HTTP 端点为 "http"） |
| `x402Version` | `number` | 必需 | 资源支持的协议版本 |
| `accepts` | `array` | 必需 | 指定付款方式的 PaymentRequirements 对象数组 |
| `lastUpdated` | `number` | 必需 | 资源最后更新的 Unix 时间戳 |
| `metadata` | `object` | 可选 | 附加元数据（类别、提供商等） |

### 8.3 Bazaar 概念

Bazaar 是一个市场生态系统，可以在其中发现和访问启用 x402 的资源。主要功能：

- **资源发现**：按类别、提供商或付款要求查找 API 和服务
- **付款透明度**：预先查看定价和付款方式
- **提供商信息**：了解服务提供商及其产品
- **动态更新**：资源可以动态添加、更新或删除

### 8.4 示例用法

```bash
# 发现金融数据 API
GET /discovery/resources?type=http&limit=10

# 搜索特定提供商
GET /discovery/resources?metadata[provider]=Coinbase
```

## 9. 错误处理

x402 协议定义了促进者或资源服务器可能返回的标准错误代码。这些错误代码帮助客户端了解付款失败的原因并采取适当的行动。

- **`insufficient_funds`**：客户端没有足够的代币来完成付款
- **`invalid_exact_evm_payload_authorization_valid_after`**：付款授权尚未有效（在 validAfter 时间戳之前）
- **`invalid_exact_evm_payload_authorization_valid_before`**：付款授权已过期（在 validBefore 时间戳之后）
- **`invalid_exact_evm_payload_authorization_value`**：付款金额不足以支付所需的付款
- **`invalid_exact_evm_payload_signature`**：付款授权签名无效或签名不正确
- **`invalid_exact_evm_payload_recipient_mismatch`**：接收方地址与付款要求不匹配
- **`invalid_network`**：指定的区块链网络不受支持
- **`invalid_payload`**：付款负载格式错误或包含无效数据
- **`invalid_payment_requirements`**：付款要求对象无效或格式错误
- **`invalid_scheme`**：指定的支付方案不受支持
- **`unsupported_scheme`**：促进者不支持该支付方案
- **`invalid_x402_version`**：协议版本不受支持
- **`invalid_transaction_state`**：区块链交易失败或被拒绝
- **`unexpected_verify_error`**：付款验证期间发生意外错误
- **`unexpected_settle_error`**：付款结算期间发生意外错误

## 10. 安全考虑

### 10.1 重放攻击预防

x402 协议实现了多层保护以防止重放攻击：

- **EIP-3009 Nonce**：每个授权包含一个唯一的 32 字节随机数以防止重放攻击
- **区块链保护**：EIP-3009 合约在智能合约级别本质上防止随机数重用
- **时间限制**：授权具有明确的有效时间窗口以限制其生命周期
- **签名验证**：所有授权都由付款方加密签名

### 10.2 认证集成

该协议支持与认证系统集成（例如，Sign-In with Ethereum - SIWE），以实现经过认证的定价模型，其中经过验证的用户获得折扣率或特殊访问条款。

## 11. 实现说明

### 11.1 网络标识符

x402 v2 中的网络使用 CAIP-2（链无关改进提案）格式：`namespace:reference`。

**格式**：`{namespace}:{reference}`（例如，Base 主网的 `eip155:8453`）

鼓励非区块链网络遵循 CAIP-2 格式（例如，`ach:us`、`sepa:eu`）。

参考实现同时支持 EVM 和 Solana 网络，例如：

- **`eip155:84532`**：Base Sepolia 测试网
- **`eip155:8453`**：Base 主网
- **`eip155:43113`**：Avalanche Fuji 测试网
- **`eip155:43114`**：Avalanche 主网
- **`solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp`**：Solana 主网
- **`solana:EtWTRABZaYq6iMfeYKouRu166VU2xqa1`**：Solana 开发网

### 11.2 支持的资产

代币支持因网络而异：

**EVM 网络：**
- 实现 EIP-3009（带授权的转账）的 ERC-20 代币
- 示例：USDC

**Solana：**
- 任何 SPL 代币
- Token2022 程序代币

代币可用性取决于促进者服务功能和特定于网络的部署。

## 12. 用例和应用

x402 协议在互联网上实现了多样化的变现场景。虽然核心协议是 HTTP 原生且与链无关的，但特定实现可以根据用例要求而变化。

### 12.1 AI 智能体集成

AI 智能体可以使用 x402 自主为资源和服务付费。该协议支持：

- 资源访问的**自动付款处理**
- 通过促进者服务的**资源发现**
- **预算管理**和支出控制（特定于实现）
- 用于操作分组的**关联跟踪**（特定于实现）
- **多传输支持**，允许智能体跨 HTTP API、MCP 工具和其他协议层工作

### 12.2 人类用户应用程序

应用程序可以实现 x402 用于：

- **基于会话的访问**（限时订阅）
- **按需付费内容**（文章、视频、下载、工具）
- 具有每次调用定价的**资源变现**
- **基于认证的定价**（经过验证的用户的折扣率）
- 支持 Web、桌面和 AI 应用程序的**跨协议支付**

### 12.3 传输支持

x402 集成到多个传输层：

- **HTTP**：Web API、REST 服务、服务器框架（Express.js、FastAPI、Next.js 等）
- **MCP（模型上下文协议）**：AI 智能体工具和资源
- **A2A（智能体对智能体协议）**：直接的智能体对智能体付款
- **自定义协议**：任何基于请求-响应的系统都可以实现 x402 支付流程

### 12.4 服务器框架

x402 与流行框架集成：

- **Express.js**：`require_payment()` 中间件
- **FastAPI/Flask**：特定于框架的中间件
- **Hono**：边缘运行时支持
- **Next.js**：全栈集成
- **ai/agents**：AI 智能体和 MCP 框架

### 12.5 客户端库

不同传输的客户端可以通过 x402 支付能力增强：

- **HTTP 客户端**：axios/fetch（浏览器）、httpx/requests（Python）、curl（CLI）
- **MCP 客户端**：ai/agents MCP 客户端
- **A2A**：x402_a2a (python)
- **自定义集成**：特定于应用程序的付款处理

### 12.6 高级模式

该协议实现了复杂的变现策略：

- 基于用户认证或使用模式的**动态定价**
- 用于基于时间的访问控制的**会话管理**
- 用于多次资源访问的**批量付款**
- 建立在微支付基础上的**订阅模式**

_注意：特定模式的实现细节（如预算管理、关联跟踪或会话处理）可在应用说明和实现指南中找到。特定于传输的实现细节在传输规范文档中涵盖。_
