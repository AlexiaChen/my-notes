
# x402

x402 是一个面向互联网原生支付的开放标准。它旨在支持所有网络（包括加密货币和法定货币）和所有形式的价值（稳定币、代币、法定货币）。

```typescript
app.use(
  paymentMiddleware(
    {

        description: "天气数据",        // 您的端点功能
      },
    },
  ),
);
// 就这么简单！详见 examples/ 获取完整详情
```

## 原则

- **开放标准**：x402 是一个开放标准，任何人都可以自由访问和使用。它永远不会强迫依赖单一方。
- **HTTP / 传输原生**：x402 旨在无缝补充现有的数据传输。只要有可能，它不应要求在典型客户端/服务器流程范围之外进行额外的请求。
- **网络、代币和货币无关**：我们欢迎为新的网络（包括加密货币和法定货币）、签名标准或方案添加支持的贡献，只要它们符合我们在 [CONTRIBUTING.md](https://github.com/coinbase/x402/blob/main/CONTRIBUTING.md) 中提出的接受标准。x402 可以扩展对基于法定货币的网络的支持，但永远不会为了法定货币支付而降低链上支付的优先级。
- **向后兼容**：x402 不会弃用对任何现有网络的支持，除非出于标准安全性的考虑认为这种移除是必要的。
- **最小化信任**：所有支付方案绝不允许促进者或资源服务器在不符合客户端意图的情况下转移资金。
- **易于使用**：x402 需要比现有互联网支付方式好 10 倍。这意味着将尽可能多的加密细节从客户端和资源服务器抽象出来，放入促进者中。这意味着客户端/服务器不需要考虑 gas、rpc 等问题。

## 术语：

- **`resource`（资源）**：互联网上的某种东西。这可以是网页、文件服务器、RPC 服务、API，或任何接受 HTTP/HTTPS 请求的互联网资源。
- **`client`（客户端）**：想要为资源付费的实体。
- **`facilitator`（促进者）**：为一个或多个网络促进支付验证和执行的服务器。
- **`resource server`（资源服务器）**：为客户端提供 API 或其他资源的 HTTP 服务器。

---

## 技术目标：

- 对客户端、服务器和促进者来说是无需许可且安全的
- 对客户端和资源服务器的采用摩擦最小化
- 资源服务器和客户端的最小集成（服务器 1 行代码，客户端 1 个函数）
- 能够权衡响应速度与支付保证
- 可扩展到不同的支付流程和网络

### 典型的 x402 流程

x402 支付通常遵循以下流程，但服务器有很大的灵活性。参见 `examples/` 中的 `advanced` 文件夹。

![[Pasted image 20260205103520.png]]


以下概述了使用 `x402` 协议进行支付的流程。请注意，如果客户端已经知道资源接受的付款详细信息，则步骤 (1) 和 (2) 是可选的。

1. **`Client`（客户端）** 向 **`resource server`（资源服务器）** 发起 HTTP 请求。

2. **`Resource server`（资源服务器）** 以 `402 Payment Required`（需要付款）状态响应，并将 `PaymentRequired` b64 对象作为 `PAYMENT-REQUIRED` 标头返回。

3. **`Client`（客户端）** 选择服务器响应返回的 `PaymentRequirements` 之一，并根据他们选择的 `PaymentRequirements` 的 `scheme`（方案）和 `network`（网络）创建 `PaymentPayload`。

4. **`Client`（客户端）** 向资源服务器发送包含 `PaymentPayload` 的 `PAYMENT-SIGNATURE` 标头的 HTTP 请求。

5. **`Resource server`（资源服务器）** 通过本地验证或将 `PaymentPayload` 和 `PaymentRequirements` POST 到 `facilitator`（促进者）的 `/verify` 端点来验证 `PaymentPayload` 是否有效。

6. **`Facilitator`（促进者）** 根据 `PaymentPayload` 的 `scheme` 和 `network` 对对象进行验证，并返回 `Verification Response`（验证响应）。

7. 如果 `Verification Response`（验证响应）有效，资源服务器执行工作以满足请求。如果 `Verification Response`（验证响应）无效，资源服务器返回 `402 Payment Required`（需要付款）状态，并在响应正文中返回 `Payment Required Response` JSON 对象。

8. **`Resource server`（资源服务器）** 通过直接与区块链交互，或将 `Payment Payload` 和 `Payment PaymentRequirements` POST 到 `facilitator server`（促进者服务器）的 `/settle` 端点来结算支付。

9. **`Facilitator server`（促进者服务器）** 根据 `Payment Payload` 的 `scheme` 和 `network` 向区块链提交支付。

10. **`Facilitator server`（促进者服务器）** 等待支付在区块链上确认。

11. **`Facilitator server`（促进者服务器）** 向资源服务器返回 `Payment Execution Response`（支付执行响应）。

12. **`Resource server`（资源服务器）** 向 `Client`（客户端）返回 `200 OK` 响应，将他们请求的资源作为 HTTP 响应的主体，如果支付成功执行，则包含一个 `PAYMENT-RESPONSE` 标头，其中包含作为 Base64 编码 JSON 的 `Settlement Response`（结算响应）。

### 方案（Schemes）

方案是一种移动资金的逻辑方式。

区块链允许大量灵活的资金移动方式。为了帮助促进日益增长的支付用例，`x402` 协议通过其 `scheme` 字段可扩展到不同的支付结算方式。

每种支付方案可能具有不同的操作功能，具体取决于完成支付所需的操作。

例如，`exact`（精确支付）是作为协议一部分发布的第一个方案，其行为与 `upto`（最高支付）不同。`exact` 转账特定金额（例如：支付 1 美元阅读文章），而理论上的 `upto` 会根据请求期间消耗的资源转账最多到一定金额（例如：从 LLM 生成代币）。

参见 `specs/schemes` 了解有关方案的更多详细信息，并参见 `specs/schemes/exact/scheme_exact_evm.md` 查看在 EVM 链上进行精确支付的第一个提议方案。

---

### 方案 vs 网络

因为方案是一种移动资金的逻辑方式，所以方案的实现方式对于不同的区块链可能有所不同（例如：在以太坊上实现 `exact` 的方式与在 Solana 上实现 `exact` 的方式非常不同）。

客户端和促进者必须明确支持不同的 `(scheme, network)` 对，才能创建正确的负载并验证/结算支付。
