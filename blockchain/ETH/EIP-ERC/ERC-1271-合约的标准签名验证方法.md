## 摘要

外部拥有账户 (EOA) 可以使用其关联的私钥对消息进行签名，但目前合约不能。我们提出了一个标准方法，使任何合约能够验证代表给定合约的签名是否有效。这可以通过在签名合约上实现 `isValidSignature(hash, signature)` 函数来实现，该函数可以被调用来验证签名。

## 动机

有许多（并且将有更多）合约希望利用签名消息来验证移动资产的权利或其他目的。为了使这些合约能够支持非外部拥有账户（即合约所有者），我们需要一个标准机制，通过该机制合约可以指示给定签名是否代表其有效。

一个需要提供签名消息的应用程序示例是具有链下订单簿的去中心化交易所，其中买卖订单是签名消息。在这些应用程序中，EOA 对订单进行签名，表示其买卖给定资产的愿望，并授予交易所智能合约通过签名完成交易的明确权限。对于合约而言，常规签名是不可能的，因为合约不拥有私钥，因此有了这个提案。

## 规范

本文档中的关键词 "MUST"、"MUST NOT"、"REQUIRED"、"SHALL"、"SHALL NOT"、"SHOULD"、"SHOULD NOT"、"RECOMMENDED"、"MAY" 和 "OPTIONAL" 应按照 RFC 2119 中的描述进行解释。

```solidity
pragma solidity ^0.5.0;

contract ERC1271 {

  // bytes4(keccak256("isValidSignature(bytes32,bytes)"))
  bytes4 constant internal MAGICVALUE = 0x1626ba7e;

  /**
   * @dev Should return whether the signature provided is valid for the provided hash
   * @param _hash      Hash of the data to be signed
   * @param _signature Signature byte array associated with _hash
   *
   * MUST return the bytes4 magic value 0x1626ba7e when function passes.
   * MUST NOT modify state (using STATICCALL for solc < 0.5, view modifier for solc > 0.5)
   * MUST allow external calls
   */
  function isValidSignature(
    bytes32 _hash,
    bytes memory _signature)
    public
    view
    returns (bytes4 magicValue);
}
```

`isValidSignature` 可以调用任意方法来验证给定签名，这可能是上下文相关的（例如基于时间或基于状态）、EOA 相关的（例如智能钱包内签名者的授权级别）、签名方案相关的（例如 ECDSA、多签、BLS）等。

此函数应由希望签名消息的合约实现（例如智能合约钱包、DAO、多签名钱包等）。希望支持合约签名的应用程序应在签名者是合约时调用此方法。

## 基本原理

我们认为提议函数的名称是适当的，因为**授权的**签名者为给定数据提供适当的签名将看到其签名被签名合约视为"有效"。因此，签名操作消息只有在签名者被授权代表智能钱包执行给定操作时才有效。

提供了两个参数以简化将签名的哈希与签名分开。使用 `bytes32` 哈希而不是未哈希的消息是为了简化，因为合约可能期望非标准的特定哈希函数，例如 EIP-712。

`isValidSignature()` 不应该能够修改状态，以防止 `GasToken` 铸造或类似的攻击向量。同样，这是为了简化函数的实现表面以实现更好的标准化，并允许链下合约查询。

期望返回特定的返回值而不是布尔值，以便对签名进行更严格和更简单的验证。

## 向后兼容性

此 EIP 与以前的签名验证工作向后兼容，因为此方法特定于基于合约的签名，而不是 EOA 签名。

## 参考实现

签名合约的示例实现：

```solidity
/**
 * @notice Verifies that the signer is the owner of the signing contract.
 */
function isValidSignature(
  bytes32 _hash,
  bytes calldata _signature
) external override view returns (bytes4) {
  // Validate signatures
  if (recoverSigner(_hash, _signature) == owner) {
    return 0x1626ba7e;
  } else {
    return 0xffffffff;
  }
}

/**
 * @notice Recover the signer of hash, assuming it's an EOA account
 * @dev Only for EthSign signatures
 * @param _hash       Hash of message that was signed
 * @param _signature  Signature encoded as (bytes32 r, bytes32 s, uint8 v)
 */
function recoverSigner(
  bytes32 _hash,
  bytes memory _signature
) internal pure returns (address signer) {
  require(_signature.length == 65, "SignatureValidator#recoverSigner: invalid signature length");

  // Variables are not scoped in Solidity.
  uint8 v = uint8(_signature[64]);
  bytes32 r = _signature.readBytes32(0);
  bytes32 s = _signature.readBytes32(32);

  // EIP-2 still allows signature malleability for ecrecover(). Remove this possibility and make the signature
  // unique. Appendix F in the Ethereum Yellow paper (https://ethereum.github.io/yellowpaper/paper.pdf), defines
  // the valid range for s in (281): 0 < s < secp256k1n ÷ 2 + 1, and for v in (282): v ∈ {27, 28}. Most
  // signatures from current libraries generate a unique signature with an s-value in the lower half order.
  //
  // If your library generates malleable signatures, such as s-values in the upper range, calculate a new s-value
  // with 0xFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFEBAAEDCE6AF48A03BBFD25E8CD0364141 - s1 and flip v from 27 to 28 or
  // vice versa. If your library also generates signatures with 0/1 for v instead 27/28, add 27 to v to accept
  // these malleable signatures as well.
  //
  // Source OpenZeppelin
  // https://github.com/OpenZeppelin/openzeppelin-contracts/blob/master/contracts/cryptography/ECDSA.sol

  if (uint256(s) > 0x7FFFFFFFFFFFFFFFFFFFFFFFFFFFFFFF5D576E7357A4501DDFE92F46681B20A0) {
    revert("SignatureValidator#recoverSigner: invalid signature 's' value");
  }

  if (v != 27 && v != 28) {
    revert("SignatureValidator#recoverSigner: invalid signature 'v' value");
  }

  // Recover ECDSA signer
  signer = ecrecover(_hash, v, r, s);

  // Prevent signer from being 0x0
  require(
    signer != address(0x0),
    "SignatureValidator#recoverSigner: INVALID_SIGNER"
  );

  return signer;
}
```

在外部签名合约上调用 isValidSignature() 函数的合约示例：

```solidity
function callERC1271IsValidSignature(
  address _addr,
  bytes32 _hash,
  bytes calldata _signature
) external view {
  bytes4 result = IERC1271Wallet(_addr).isValidSignature(_hash, _signature);
  require(result == 0x1626ba7e, "INVALID_SIGNATURE");
}
```

## 安全考虑

由于调用 isValidSignature() 函数没有预期的 gas 限制，因此某些实现可能会消耗大量的 gas。因此，在外部合约上调用此方法时不硬编码发送的 gas 量很重要，因为它可能会阻止某些签名的验证。

还要注意，实现此方法的每个合约都负责确保传递的签名确实是有效的，否则预期会有灾难性的结果。
