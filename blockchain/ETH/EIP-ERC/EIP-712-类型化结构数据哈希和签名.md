## 摘要

这是一个用于类型化结构数据哈希和签名的标准，而不仅仅是字节字符串。它包括：

- 编码函数正确性的理论框架
- 与 Solidity 结构体类似且兼容的结构数据规范
- 这些结构实例的安全哈希算法
- 这些实例在可签名消息集合中的安全包含
- 域分离的可扩展机制
- 新的 RPC 调用 `eth_signTypedData`
- EVM 中哈希算法的优化实现

它不包括重放保护。

## 动机

如果我们只关心字节字符串，签名数据是一个已解决的问题。不幸的是，在现实世界中，我们关心复杂的有意义消息。哈希结构化数据并非易事，错误会导致系统安全属性的丧失。

因此，"不要自己设计加密算法"这个格言适用。相反，应该使用经过同行评审和充分测试的标准方法。本 EIP 旨在成为该标准。

本 EIP 旨在改进链下消息签名在链上使用的可用性。我们看到链下消息签名的采用率不断增长，因为它节省 gas 并减少了区块链上的交易数量。目前，签名消息是向用户显示的不透明十六进制字符串，几乎没有关于组成消息的项目的上下文。

在这里，我们概述了一种将数据与其结构一起编码的方案，允许在签名时向用户显示以供验证。以下是用户根据本提案签名消息时可以看到的内容示例。

## 规范

可签名消息集从交易和字节字符串 `𝕋 ∪ 𝔹⁸ⁿ` 扩展到还包括结构化数据 `𝕊`。新的可签名消息集为 `𝕋 ∪ 𝔹⁸ⁿ ∪ 𝕊`。它们被编码为适合哈希和签名的字节字符串，如下所示：

- `encode(transaction : 𝕋) = RLP_encode(transaction)`
- `encode(message : 𝔹⁸ⁿ) = "\x19Ethereum Signed Message:\n" ‖ len(message) ‖ message`，其中 `len(message)` 是 `message` 中字节数量的**非零填充**的 ASCII 十进制编码。
- `encode(domainSeparator : 𝔹²⁵⁶, message : 𝕊) = "\x19\x01" ‖ domainSeparator ‖ hashStruct(message)`，其中 `domainSeparator` 和 `hashStruct(message)` 定义如下。

此编码是确定性的，因为各个组件是确定性的。编码是单射的，因为三种情况在第一个字节上总是不同。（`RLP_encode(transaction)` 不以 `\x19` 开头。）

编码符合 ERC-191。"版本字节"固定为 `0x01`，"版本特定数据"是 32 字节的域分隔符 `domainSeparator`，"要签名的数据"是 32 字节的 `hashStruct(message)`。

### 类型化结构数据 `𝕊` 的定义

为了定义所有结构化数据的集合，我们从定义可接受的类型开始。与 ABIv2 一样，这些类型与 Solidity 类型密切相关。采用 Solidity 符号来解释定义是说明性的。该标准特定于以太坊虚拟机，但旨在对高级语言不可知。例如：

```
struct Mail {
    address from;
    address to;
    string contents;
}
```

**定义**：**结构体类型**具有有效的标识符作为名称，并包含零个或多个成员变量。成员变量具有成员类型和名称。

**定义**：**成员类型**可以是原子类型、动态类型或引用类型。

**定义**：**原子类型**是 `bytes1` 到 `bytes32`、`uint8` 到 `uint256`、`int8` 到 `int256`、`bool` 和 `address`。这些对应于它们在 Solidity 中的定义。注意没有别名 `uint` 和 `int`。注意合约地址始终是纯 `address`。该标准不支持定点数。本标准的未来版本可能会添加新的原子类型。

**定义**：**动态类型**是 `bytes` 和 `string`。这些在类型声明方面类似于原子类型，但它们在编码中的处理方式不同。

**定义**：**引用类型**是数组和结构体。数组要么是固定大小的，要么是动态的，分别用 `Type[n]` 或 `Type[]` 表示。结构体是通过名称对其他结构体的引用。该标准支持递归结构体类型。

**定义**：结构化类型数据集合 `𝕊` 包含所有结构体类型的所有实例。

### `hashStruct` 的定义

`hashStruct` 函数定义为：

- `hashStruct(s : 𝕊) = keccak256(typeHash ‖ encodeData(s))`，其中 `typeHash = keccak256(encodeType(typeOf(s)))`

**注意**：`typeHash` 对于给定的结构体类型是常量，不需要在运行时计算。

### `encodeType` 的定义

结构体的类型编码为 `name ‖ "(" ‖ member₁ ‖ "," ‖ member₂ ‖ "," ‖ … ‖ memberₙ ")"`，其中每个成员写成 `type ‖ " " ‖ name`。例如，上面的 `Mail` 结构体编码为 `Mail(address from,address to,string contents)`。

如果结构体类型引用其他结构体类型（而这些结构体又引用更多结构体类型），则收集被引用的结构体类型集合，按名称排序并附加到编码。一个示例编码是 `Transaction(Person from,Person to,Asset tx)Asset(address token,uint256 amount)Person(address wallet,string name)`。

### `encodeData` 的定义

结构体实例的编码是 `enc(value₁) ‖ enc(value₂) ‖ … ‖ enc(valueₙ)`，即按照它们在类型中出现的顺序连接编码的成员值。每个编码的成员值正好是 32 字节长。

原子值编码如下：布尔值 `false` 和 `true` 分别编码为 `uint256` 值 `0` 和 `1`。地址编码为 `uint160`。整数值符号扩展到 256 位，并以大端顺序编码。`bytes1` 到 `bytes31` 是具有开头（索引 `0`）和结尾（索引 `length - 1`）的数组，它们在末尾零填充到 `bytes32` 并按从头到尾的顺序编码。这对应于它们在 ABI v1 和 v2 中的编码。

动态值 `bytes` 和 `string` 编译为其内容的 `keccak256` 哈希。

数组值编译为其内容的连接 `encodeData` 的 `keccak256` 哈希（即 `SomeType[5]` 的编码与包含五个 `SomeType` 类型成员的结构体的编码相同）。

结构体值递归编码为 `hashStruct(value)`。这对于循环数据是未定义的。

### `domainSeparator` 的定义

```
domainSeparator = hashStruct(eip712Domain)
```

其中 `eip712Domain` 的类型是一个名为 `EIP712Domain` 的结构体，具有以下一个或多个字段。协议设计者只需要包含对其签名域有意义的字段。未使用的字段从结构体类型中省略。

- `string name` 签名域的用户可读名称，即 DApp 或协议的名称。
- `string version` 签名域的当前主要版本。来自不同版本的签名不兼容。
- `uint256 chainId` EIP-155 链 ID。如果与当前活动的链不匹配，用户代理**应该**拒绝签名。
- `address verifyingContract` 将验证签名的合约地址。用户代理**可能**进行特定于合约的钓鱼预防。
- `bytes32 salt` 协议的消歧盐。这可以用作最后手段的域分隔符。

本标准的未来扩展可以添加具有新用户代理行为约束的新字段。用户代理可以自由地使用提供的信息来通知/警告用户或拒绝签名。Dapp 实现者不应添加私有字段，新字段应通过 EIP 流程提出。

`EIP712Domain` 字段应按上述顺序排列，跳过任何不存在的字段。未来的字段添加必须按字母顺序排列，并位于上述字段之后。用户代理应接受 `EIP712Domain` 类型指定的任何顺序的字段。

### `eth_signTypedData` JSON RPC 的规范

方法 `eth_signTypedData` 被添加到以太坊 JSON-RPC。该方法与 `eth_sign` 并行。

#### eth_signTypedData

签名方法使用以下方法计算以太坊特定的签名：`sign(keccak256("\x19\x01" ‖ domainSeparator ‖ hashStruct(message)))`，如上定义。

**注意**：要签名的地址必须已解锁。

##### 参数

1. `Address` - 20 字节 - 将签名消息的账户地址。
2. `TypedData` - 要签名的类型化结构化数据。

类型化数据是一个包含类型信息、域分隔符参数和消息对象的 JSON 对象。以下是 `TypedData` 参数的 json-schema 定义。

```
{
  type: 'object',
  properties: {
    types: {
      type: 'object',
      properties: {
        EIP712Domain: {type: 'array'},
      },
      additionalProperties: {
        type: 'array',
        items: {
          type: 'object',
          properties: {
            name: {type: 'string'},
            type: {type: 'string'}
          },
          required: ['name', 'type']
        }
      },
      required: ['EIP712Domain']
    },
    primaryType: {type: 'string'},
    domain: {type: 'object'},
    message: {type: 'object'}
  },
  required: ['types', 'primaryType', 'domain', 'message']
}
```

##### 返回

`DATA`：签名。与 `eth_sign` 一样，它是一个以 `0x` 开头的十六进制编码的 65 字节数组。它以大端格式编码黄皮书附录 F 中的 `r`、`s` 和 `v` 参数。字节 0…32 包含 `r` 参数，字节 32…64 包含 `s` 参数，最后一个字节包含 `v` 参数。注意 `v` 参数包含 EIP-155 中指定的链 ID。

##### 示例

请求：

## 基本原理

`encode` 函数为新类型扩展了一个新情况。编码的第一个字节区分这些情况。出于同样的原因，立即以域分隔符或 `typeHash` 开始是不安全的。虽然困难，但可能构造一个 `typeHash`，它也恰好是有效 RLP 编码交易的前缀。

域分隔符防止否则相同的结构冲突。可能两个 DApp 提出了相同的结构，如 `Transfer(address from,address to,uint256 amount)`，但它们不应该兼容。通过引入域分隔符，DApp 开发人员可以保证没有签名冲突。

域分隔符还允许在给定 DApp 内的同一结构体实例上使用多个不同的签名用例。在前面的示例中，可能需要 `from` 和 `to` 的签名。通过提供两个不同的域分隔符，这些签名可以彼此区分。

**替代方案 1**：使用目标合约地址作为域分隔符。这解决了第一个问题，即合约提出相同的类型，但没有解决第二个用例。该标准确实建议实现者在适当的地方使用目标合约地址。

函数 `hashStruct` 以 `typeHash` 开头来分隔类型。通过给不同的类型不同的前缀，`encodeData` 函数只需要在给定类型内是单射的。只要 `typeOf(a)` 不是 `typeOf(b)`，`encodeData(a)` 等于 `encodeData(b)` 就可以。

### `typeHash` 的基本原理

`typeHash` 旨在在 Solidity 中变为编译时常量。例如：

```
bytes32 constant MAIL_TYPEHASH = keccak256(
  "Mail(address from,address to,string contents)");
```

对于类型哈希，考虑了几种替代方案并因以下原因被拒绝：

**替代方案 2**：使用 ABIv2 函数签名。`bytes4` 不足以抗冲突。与函数签名不同，使用更长的哈希产生的运行时成本可以忽略不计。

**替代方案 3**：修改为 256 位的 ABIv2 函数签名。虽然这捕获了类型信息，但没有捕获除函数之外的任何语义。这已经在 ERC-20 和 ERC-721 的 `transfer(address,uint256)` 之间造成了实际的冲突，在前者中 `uint256` 指的是金额，而在后者中指的是唯一 ID。通常，ABIv2 偏好兼容性，而哈希标准应该偏好不兼容性。

**替代方案 4**：扩展了参数名称和结构体名称的 256 位 ABIv2 签名。上面的 `Mail` 示例将编码为 `Mail(Person(string name,address wallet) from,Person(string name,address wallet) to,string contents)`。这比提出的解决方案更长。实际上，字符串的长度可能以输入长度的指数增长（考虑 `struct A{B a;B b;}; struct B {C a;C b;}; …`）。它也不允许递归结构体类型（考虑 `struct List {uint256 value; List next;}`）。

**替代方案 5**：包括 natspec 文档。这将在 schemaHash 中包含更多语义信息，并进一步减少冲突的机会。它使扩展和修改文档成为破坏性更改，这与常见假设相矛盾。它还使 schemaHash 机制非常冗长。

### `encodeData` 的基本原理

`encodeData` 旨在允许在 Solidity 中轻松实现 `hashStruct`：

```
function hashStruct(Mail memory mail) pure returns (bytes32 hash) {
    return keccak256(abi.encode(
        MAIL_TYPEHASH,
        mail.from,
        mail.to,
        keccak256(mail.contents)
    ));
}
```

它还允许在 EVM 中进行高效的原地实现

```
function hashStruct(Mail memory mail) pure returns (bytes32 hash) {

    // Compute sub-hashes
    bytes32 typeHash = MAIL_TYPEHASH;
    bytes32 contentsHash = keccak256(mail.contents);

    assembly {
        // Back up select memory
        let temp1 := mload(sub(mail, 32))
        let temp2 := mload(add(mail, 128))

        // Write typeHash and sub-hashes
        mstore(sub(mail, 32), typeHash)
        mstore(add(mail, 64), contentsHash)

        // Compute hash
        hash := keccak256(sub(mail, 32), 128)

        // Restore memory
        mstore(sub(mail, 32), temp1)
        mstore(add(mail, 64), temp2)
    }
}
```

原地实现对结构体在内存中的内存布局做出了强有力但合理的假设。具体来说，它假设结构体不是分配在地址 32 以下，成员按顺序存储，所有值填充到 32 字节边界，动态和引用类型存储为 32 字节指针。

**替代方案 6**：紧密打包。这是在 Solidity 中使用多个参数调用 `keccak256` 时的默认行为。它最小化了要哈希的字节数，但需要在 EVM 中使用复杂的打包指令。它不允许原地计算。

**替代方案 7**：ABIv2 编码。特别是随着即将到来的 `abi.encode`，应该容易使用 `abi.encode` 作为 `encodeData` 函数。ABIv2 标准本身不符合确定性安全标准。同一数据有多种有效的 ABIv2 编码。ABIv2 不允许原地计算。

**替代方案 8**：将 `typeHash` 从 `hashStruct` 中省略，而是将其与域分隔符组合。这更有效，但 Solidity `keccak256` 哈希函数的语义不是单射的。

**替代方案 9**：支持循环数据结构。当前标准针对类树数据结构进行了优化，对于循环数据结构未定义。为了支持循环数据，需要维护包含到当前节点路径的堆栈，并在检测到循环时替换堆栈偏移量。这使得规范和实现更加复杂。它还破坏了组合性，其中成员值的哈希用于构造结构体的哈希（成员值的哈希将取决于路径）。可以以兼容的方式扩展标准以定义循环数据的哈希。

同样，直接实现对于有向无环图是次优的。通过成员的简单递归可能会两次访问同一节点。记忆化可以优化这一点。

### `domainSeparator` 的基本原理

由于不同的域有不同的需求，因此使用了可扩展方案，其中 DApp 指定 `EIP712Domain` 结构体类型和实例 `eip712Domain`，然后将其传递给用户代理。然后，用户代理可以根据存在的字段应用不同的验证措施。

## 向后兼容性

RPC 调用、web3 方法和 `SomeStruct.typeHash` 参数当前未定义。定义它们不应影响现有 DApp 的行为。

对于结构体类型 `SomeStruct` 的实例 `someInstance`，Solidity 表达式 `keccak256(someInstance)` 是有效语法。它当前计算为实例内存地址的 `keccak256` 哈希。此行为应被认为是危险的。在某些情况下，它看起来会正常工作，但在其他情况下，它将无法通过确定性和/或单射性。依赖当前行为的 DApp 应被认为是危险地损坏的。

## 安全考虑

### 重放攻击

本标准仅关于签名消息和验证签名。在许多实际应用中，签名消息用于授权操作，例如代币交换。**非常重要**的是，实现者确保应用程序在两次看到相同的签名消息时行为正确。例如，应拒绝重复的消息或授权的操作应该是幂等的。如何实现是特定于应用程序的，超出了本标准的范围。

### 抢先交易攻击

可靠广播签名的机制是特定于应用程序的，超出了本标准的范围。当签名广播到区块链以在合约中使用时，应用程序必须能够抵御抢先交易攻击。在这种攻击中，攻击者拦截签名并在原始预期用途发生之前将其提交给合约。当攻击者首先提交签名时，应用程序应该正确行为，例如通过拒绝它或简单地产生与签名者预期的完全相同的效果。
