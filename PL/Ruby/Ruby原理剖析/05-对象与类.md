
# 第5章 读书笔记：对象与类

> 💡 这一章回答的核心问题是：**Ruby 说"一切皆对象"，那对象在内存里到底是什么样子？类又是什么？**
> 
> 从第一性原理看，Ruby 的对象模型解决的是一个根本性的职责划分问题：**对象只负责"我是谁 + 我有什么状态"，类负责"我是什么类型 + 我能做什么行为"**。这种职责分离不是美学选择，而是工程必然——因为同一个类的成千上万个实例，必须共享同一套方法定义，而不能各自复制一份。

📌 **时代注记**：原书基于 Ruby 2.0，本章提到的 `ivptr` 数组、`RClass` 结构在今天（Ruby 3.x/4.x）依然成立，但有了重要演进——特别是 Ruby 3.3+ 引入的 **RVARGC（Variable Width RValue GC）**​ 和 **Object Shapes**​ 技术，让实例变量的存储更高效。我们会在对应小节指出这些演进 。

## 5 对象与类

承接第4章——我们已经看到 `send` 指令如何在方法表中查找方法。但方法表存在于哪里？对象又如何找到自己的类？这一章揭开谜底。

原书作者 Pat Shaughnessy 在章节导言中点明：本章要回答两个内部结构的疑问——**"Inside a Ruby Object"**​ 和 **"What's Inside the RClass Structure?"**​ 。这两个结构构成了 Ruby 对象模型的基石。

---

## 5.1 Ruby 对象内部

原书从一个简单的实验切入 ：

```
class Mathematician
  attr_accessor :first_name
  attr_accessor :last_name
end

euler = Mathematician.new
euler.first_name = 'Leonhard'
euler.last_name = 'Euler'

euclid = Mathematician.new
euclid.first_name = 'Euclid'
```

当我们 `puts euler`，会看到 `#<Mathematician:0x007fbd738608c0>`——那个十六进制数就是对象在内存中的 `VALUE` 指针地址 。

**Ruby 对象在 C 层面的真相**：每个 Ruby 对象都是一个 **`RObject` 结构体**，它包含：

- **`RBasic` 头部**：所有 Ruby 值都有的公共部分，含 `flags`（标记对象是否 frozen、是否为单件类等）和 `klass`（指向所属类的指针）
    
- **实例变量存储**：`numiv`（实例变量数量）+ `ivptr`（指向实例变量值数组的指针）
    

🎯 **我的洞见（本节最核心的认知）**：

> **Ruby 对象 = 一个类指针 + 一组实例变量值**。
> 
> 注意——对象内部**没有方法**。方法不在对象上，而在类上。对象只"响应"方法，但不"拥有"方法。

这是 Ruby 对象模型的第一性原理：**行为与状态分离**。对象持状态（`@first_name = 'Leonhard'`），类持行为（`def first_name; @first_name; end`）。当我们调用 `euler.first_name`，Ruby 顺着 `euler` 的 `klass` 指针找到 `Mathematician` 类，在类的方法表里查到 `first_name` 方法，然后在 `euler` 的上下文中执行。

### 5.1.1 检验 klass 和 ivptr

`klass` 指针和 `ivptr` 指针是 `RObject` 的两个核心字段 。

以 `euler` 和 `euclid` 为例：

```
euler (RObject)                    euclid (RObject)
├── RBasic                         ├── RBasic
│   ├── flags                      │   ├── flags
│   └── klass ───────────────┐     │   └── klass ───────────────┐
│                            │     │                            │
├── numiv = 2                │     ├── numiv = 1                │
├── ivptr ──────┐            │     ├── ivptr ──────┐            │
                ▼            │                     ▼            │
        [ #<VALUE>, ]    │             [ #<VALUE> ]       │
          "Leonhard"     │               "Euclid"         │
          "Euler"        │                                  │
                          ▼                                  ▼
                    Mathematician (RClass)            Mathematician (RClass)
                    （同一个 RClass 实例）          （同一个 RClass 实例）
```

🎯 **我的洞见**：注意 `euler` 和 `euclid` 的 `klass` 指针**指向同一个 `Mathematician` RClass 结构**。这说明——**类对象是单例的，它是所有同类实例共享的"蓝图"**。这回答了"为什么 Ruby 不用为每个对象复制方法"——方法只存在类里，所有实例通过 `klass` 指针共享。

### 5.1.2 观察同一个类的两个实例

原书通过实验展示了 `euler` 和 `euclid` 的内部状态 ：

- `euler`：`numiv = 2`，`ivptr` 指向 `["Leonhard", "Euler"]`
    
- `euclid`：`numiv = 1`，`ivptr` 指向 `["Euclid"]`
    

**关键发现：即使两个对象是同一个类的实例，它们的 `numiv` 和 `ivptr` 也可以不同**。

这是因为 Ruby 允许**动态添加实例变量**——你可以在运行时给某个对象单独添加 `@age`，而其他同类的对象可能没有这个变量。

🎯 **我的洞见**：这里隐藏着一个重要设计——**实例变量的"名字→索引"映射存在类里，而"值"存在对象里**。

`iv_index_tbl` 是类里的一张表，映射：

```
@first_name → 0
@last_name  → 1
```

而每个对象的 `ivptr` 数组按这个索引存值：

```
euler.ivptr = ["Leonhard", "Euler"]  # 索引 0 是 first_name 的值
euclid.ivptr = ["Euclid"]            # 只有 first_name，没有 last_name
```

为什么这么设计？**因为实例变量名对所有同类实例是相同的，但值是每个实例私有的**。把"名字→索引"映射放在类里共享，避免了每个对象都存一份变量名字典——这节省了海量内存。原书明确指出："instance variable names are saved in the object's class instead, because they're the same for all instances of a class" 。

💡 **现代演进**：Ruby 3.3 引入的 **Object Shapes**​ 技术进一步优化了这一点——把"属性形状"（即实例变量集合）抽象为 Shape 对象，相同形状的对象共享 Shape，Shape 里记录属性索引信息。这让属性访问从"查表"变成"直接偏移"，是近年来 Ruby 性能提升的关键 。

### 5.1.3 基本类型对象

`String`、`Array`、`Hash`、`Regexp` 等基本类型，MRI 不用通用的 `RObject`，而是用**特化的结构体**​ ：

- `RString`：字符串
    
- `RArray`：数组
    
- `RHash`：哈希
    
- `RRegexp`：正则表达式
    

这些结构体同样以 `RBasic` 开头（保证有 `flags` 和 `klass`），但后面跟着针对该类型优化的字段。

🎯 **我的洞见**：特化结构体的本质动机是**性能与内存**。通用 `RObject` 的 `ivptr` 数组访问有间接层，而 `RString` 可以直接在结构体内嵌字符数据、`RArray` 可以直接内嵌元素指针数组。这种"为常用类型定制结构体"的思路，和 Java 的 `Integer` vs `Object`、Go 的 `int` vs `interface{}` 是同一类工程权衡。

### 5.1.4 简单立即值完全不需要结构体

`Fixnum`（Ruby 2.0 及以前）、`Symbol`、`nil`、`true`、`false` 这些**简单值，根本不存在对应的 C 结构体**​ 。

它们的 VALUE 指针**本身编码了值**——也就是说，VALUE 不是一个指向堆上结构体的指针，而是把值直接塞进了指针的位里。

🎯 **我的洞见（本节最震撼的认知）**：

> **小整数是"假装成指针的值"**。
> 
> 在 64 位系统上，指针的低 2-3 位通常是对齐填充（因为内存对齐，指针地址的低位是 0）。Ruby 利用这一点——如果 VALUE 的最低位是 1，Ruby 就知道"这是个 Fixnum，值在高 63 位里"，而不去解引用它。
> 
> 这就是为什么 Ruby 2.0 时代 `Fixnum` 运算极快——**不加不减不分配，值直接在寄存器里**。

⚠️ **重要演进**：Ruby 2.4 起，`Fixnum` 和 `Bignum` 合并为统一的 `Integer` 类 。但"小整数用 VALUE 直接编码"的优化思想依然保留——现代 Ruby 的 `Integer` 在内部仍然区分"立即值整数"和"堆分配大整数"。原书基于 Ruby 2.0 的讨论，其第一性原理在今天依然正确。

### 5.1.5 基本类型对象有实例变量吗

原书提出了一个有趣的问题：**像 `1`、`:foo`、`nil` 这样的简单立即值，能有实例变量吗？**

答案是——**可以有，但它们不存立即值结构体里**。

Ruby 提供了一个特殊的全局哈希表 `generic_iv_tbl`，专门用来给这些"没有 RObject 结构体"的对象存实例变量 。

🎯 **我的洞见**：这是一个**优雅的逃生舱设计**。

Ruby 的哲学是"一切皆对象"，理论上你可以给任何对象（包括 `1`、`nil`）添加实例变量。但为了不让 `1` 这样一个被编码在 VALUE 里的立即值，被迫分配一个完整的 `RObject` 结构体（那会让所有小整数运算都变慢），Ruby 选择用一张全局哈希表 `generic_iv_tbl` 来"额外"记录：

```
generic_iv_tbl = {
  1 (VALUE) => { :@custom_var => "value" },
  :foo (VALUE) => { :@another => 42 }
}
```

这完美体现了工程上的**分层设计**：

- 99% 的情况，对象用 RObject，实例变量存在 `ivptr` 里（快）
    
- 1% 的情况，有人给立即值加实例变量，用 `generic_iv_tbl` 兜底（慢但能工作）
    

### 5.1.6 基本类型对象的实例变量保存在哪里

承接上节——`generic_iv_tbl` 是一张**两级哈希表**​ ：

1. 第一级：key 是对象的 VALUE，value 是指向第二级哈希的指针
    
2. 第二级：key 是实例变量名，value 是实例变量值
    

原书作者做了一个有趣的实验——测量给对象添加实例变量的耗时 。结果发现一个奇怪的现象：添加第 8 个实例变量时，耗时突然跳高；添加第 9、10 个时，耗时又下降。

**原因**：Ruby 1.9+ 的 `ivptr` 是一个**简单数组**（不再是 Ruby 1.8 的哈希表）。当你添加新实例变量时：

- 前 7 个变量：数组预先分配了空间
    
- 第 8 个变量：数组空间不足，Ruby 扩容（一次性分配 3 个额外槽位），所以这次特别慢
    
- 第 9、10 个变量：空间已够，所以又快了
    

🎯 **我的洞见**：这个实验揭示了 Ruby 对象模型的**性能特征**：

- **实例变量访问是 O(1)**——通过类的 `iv_index_tbl` 拿到索引，直接从 `ivptr` 数组取
    
- **但动态添加实例变量可能触发数组扩容**，带来偶发开销
    
- 这就是为什么**在 `initialize` 里一次性设置所有实例变量**比"运行时零散添加"性能更好——前者让数组一次性分配到位，后者可能多次扩容
    

💡 **工业应用**：

- **领域模型设计**：在 `initialize` 中初始化所有实例变量，让对象"形状"尽早稳定，配合 Ruby 3.3+ 的 Object Shapes 获得最佳性能
    
- **避免给 `Symbol`、`nil`、`true` 添加实例变量**——它们走 `generic_iv_tbl` 全局哈希，不仅慢，还会增加全局锁竞争
    
- **性能敏感的循环内**，避免动态添加实例变量

## 5.2 RClass 结构体内部有什么

原书通过反推得出 RClass 应该包含的信息 ：

> 一个 Ruby 类，就是一个方法定义的集合。

因此 `RClass` 至少应该有：**方法表（m_tbl）**。但作者进一步指出，类还需要：

- **super 指针**：指向父类，用于继承链查找
    
- **iv_index_tbl**：实例变量的名字→索引映射（供该类所有实例共享）
    
- **iv_tbl**：类级别的实例变量（如 `@@class_level` 这种类实例变量）
    
- **const_tbl**：常量表
    

现代 Ruby 源码中，`RClass` 的真实结构是这样的 ：

```
struct RClass {
    struct RBasic basic;
    VALUE super;
    struct rb_id_table *m_tbl;
};

struct rb_classext_struct {
    struct st_table iv_tbl;                    // 类级别实例变量 + 类变量
    struct rb_id_table *m_tbl;                 // 方法表
    struct rb_id_table *const_tbl;             // 常量表
    struct rb_id_table *callable_m_tbl;        // 可调用的缓存方法
    struct rb_id_table *cc_tbl;                // 调用缓存表
    struct rb_id_table *cvc_tbl;               // 类变量表
    size_t superclass_depth;
    VALUE *superclasses;                       // 缓存的扁平化父类链
    struct rb_subclass_entry subclasses;       // 子类链
    struct rb_subclass_entry subclass_entry;
    const VALUE origin_;                       // 用于 Module#prepend
    const VALUE refined_class;                 // 用于 refinements
    rb_alloc_func_t allocator;                 // 为新实例分配内存
    const VALUE includer;
    // ... 其他字段
};
```

🎯 **我的洞见**：注意 `RClass` 本身极简——只有 `RBasic` + `super` + `m_tbl`。**真正的复杂数据在 `rb_classext_struct` 里**，通过指针关联。这是 C 语言里的"桥接模式"——保持 `RClass` 小巧（因为它在 hot path 上频繁访问），把不常用的数据放到扩展结构里。

### 5.2.1 继承

`super` 指针是继承的实现基础 。

```
class Animal
  def breathe; "breathing"; end
end

class Dog < Animal
  def bark; "woof"; end
end

Dog.new.breathe  # => "breathing"
```

内存中的结构：

```
Dog (RClass)                    Animal (RClass)
├── RBasic                      ├── RBasic
├── super ───────────────────►  ├── super ──────────► BasicObject
├── m_tbl: { bark: ... }        ├── m_tbl: { breathe: ... }
└── ...                         └── ...
```

当调用 `Dog.new.breathe` 时，Ruby：

1. 在 `Dog` 的 `m_tbl` 里找 `breathe`——没找到
    
2. 顺着 `super` 指针到 `Animal`
    
3. 在 `Animal` 的 `m_tbl` 里找 `breathe`——找到了！
    

这就是 Ruby 方法查找的基本算法（第6章会详述）。`super` 指针形成了一条**继承链**。

🎯 **我的洞见**：继承的本质是**方法表的链式查找**。子类不复制父类的方法，只是通过一个指针"指向"父类。这符合第一性原理——**共享优于复制**。

### 5.2.2 类实例变量 vs 类变量

这是 Ruby 最容易被误解的特性之一。原书专门用一节来区分 ：

```
class SuperClass
  @class_instance_var = "I'm a class instance variable"
  @@class_var = "I'm a class variable"
end

class SubClass < SuperClass
end

SuperClass.instance_variables  # => [:@class_instance_var]
SubClass.instance_variables    # => []
```

**类实例变量（`@class_instance_var`）**：

- 存在类的 `iv_tbl` 里
    
- **不被子类继承**
    
- 每个类有自己的副本
    

**类变量（`@@class_var`）**：

- 存在类的 `iv_tbl` 里，但通过特殊算法查找
    
- **沿 super 链向上查找**
    
- 子类"看到"父类的类变量
    

🎯 **我的洞见（本节最核心的认知）**：

> **类实例变量和类变量，在存储上是一样的（都在 `iv_tbl` 里），但查找算法完全不同。**
> 
> - 访问 `@class_instance_var`：只在**当前类**的 `iv_tbl` 里找
>     
> - 访问 `@@class_var`：**从当前类开始，沿 super 链向上找**，找到第一个就返回
>     

这就是为什么 `SubClass.class_variable_get(:@@class_var)` 能拿到父类的类变量，但 `SubClass.instance_variable_get(:@class_instance_var)` 拿不到。

⚠️ **工业现实**：类变量的"沿 super 链向上查找"语义，经常导致意外行为：

```
class A
  @@value = "from A"
end

class B < A
  @@value = "from B"
end

A.class_variable_get(:@@value)  # => "from B"  ❗️
```

`B` 修改了 `@@value`，结果 `A` 的 `@@value` 也变了！因为类变量的查找是"向上找第一个"，`B` 的赋值实际上修改了 `A` 的类变量（因为 `A` 才是第一个定义的）。

**这就是为什么现代 Ruby 社区强烈不建议使用类变量**——它的语义违反直觉。改用**类实例变量 + 显式的 `class << self` 方法**才是正道：

```
class A
  class << self
    attr_accessor :value
  end
end

class B < A
end

A.value = "from A"
B.value = "from B"
A.value  # => "from A"  ✅
B.value  # => "from B"  ✅
```

### 5.2.3 存取类变量

原书详细讨论了类变量的查找算法 。

类变量的存取通过 `cvc_tbl`（`rb_id_table`）进行。查找算法伪代码：

```
def lookup_class_variable(cls, var_name):
    while cls != nil:
        if cls.iv_tbl contains var_name:
            return cls.iv_tbl[var_name]
        cls = cls.super
    raise "uninitialized class variable"
```

🎯 **我的洞见**：注意这个算法的两个特征：

1. **向上查找，不向下**：子类能看到父类的类变量，但父类看不到子类的
    
2. **找到第一个就返回**：这导致"子类赋值类变量"会"穿透"到父类
    

这就是为什么 Rails 等框架**完全避免使用 `@@` 类变量**，转而使用 `mattr_accessor` 或 `class_attribute`——它们在语义上更可控。

### 5.2.4 常量

常量存在 `const_tbl` 里 。

```
class Math
  PI = 3.14159
end

Math::PI  # => 3.14159
```

常量的查找与类变量类似——**沿 super 链向上查找**。但常量查找还有额外的"嵌套作用域"维度：

```
class Outer
  CONST = "outer"
  
  class Inner
    CONST = "inner"
    
    def show
      CONST          # => "inner"（当前类先找）
      Outer::CONST   # => "outer"（显式指定）
    end
  end
end
```

🎯 **我的洞见**：常量查找是 Ruby 作用域模型的重要部分。它结合了：

1. **词法作用域**：当前类/模块及其嵌套外层
    
2. **继承链**：沿 super 向上
    

这使得 Ruby 的常量既能表达"命名空间"（如 `Net::HTTP`），又能表达"继承共享"（子类能看到父类的常量）。

💡 **工业应用**：

- Rails 的 `Routes`、`ApplicationController` 等都是常量，通过常量查找机制实现命名空间
    
- 大型应用中，常量的命名空间组织直接影响查找性能
    
- Ruby 3.x 对常量查找做了缓存优化（第6章会讲内联方法缓存，常量也有类似机制）
    

### 5.2.5 真实的 RClass 结构体

综合前述，现代 Ruby 的 `RClass` 完整结构如下 ：

```
RClass
├── RBasic
│   ├── flags
│   └── klass → 指向 Class 类（因为类也是对象）
├── super → 父类 RClass 指针
└── m_tbl → 方法表 (ID → rb_method_entry_t)

rb_classext_struct（通过指针关联，现代 Ruby 中与 RClass 连续分配）
├── iv_tbl → 类实例变量 + 类变量
├── const_tbl → 常量表
├── callable_m_tbl → 可调用方法缓存
├── cc_tbl → 调用缓存表
├── cvc_tbl → 类变量表
├── superclasses → 缓存的扁平化父类链
├── subclasses → 子类链表
├── origin_ → Module#prepend 使用的 origin 指针
├── refined_class → Refinement 使用的指针
├── allocator → 为该类的新实例分配内存的函数
└── includer → include 关系中的"被包含者"
```

🎯 **我的洞见（贯穿 5.2 的核心认知）**：

> **RClass 是一个"元对象"——它既是对象（因为有 klass 指针，类本身也是 Class 的实例），又是类型的载体（因为有 m_tbl、const_tbl、super）**。
> 
> 这种双重身份揭示了 Ruby 对象模型的优雅：**类也是对象，所以类可以有类方法（存在类的单件类的 m_tbl 里）、可以有实例变量（存在 iv_tbl 里）、可以被当作参数传递**。
> 
> 这就是 Ruby "一切皆对象"的真正含义——**不是修辞，而是 C 层面的事实**。

⚠️ **重要补充**：现代 Ruby 的 `RClass` 经历了多次演进：

- Ruby 3.3+ 的 **Object Shapes**​ 技术：把实例变量的"形状"抽象出来，相同形状的对象共享 Shape ，极大加速了属性访问
    
- **RVARGC**：可变宽度的 RValue，让对象大小更灵活
    
- **调用缓存表（cc_tbl）**：缓存方法查找结果，加速 `send`

## 5.3 总结

本章我们从第一性原理梳理了 Ruby 对象与类的内部表示：

1. **Ruby 对象 = 类指针（klass）+ 实例变量值数组（ivptr）**。对象内部没有方法，方法在类里。对象只持状态，类持行为——这是行为与状态分离的第一性原理 。
    
2. **实例变量的存储优化**：Ruby 1.9+ 用数组 `ivptr` 存值，用类的 `iv_index_tbl` 存"名字→索引"映射 。这避免了每个对象都复制变量名字典，节省海量内存。现代 Ruby 进一步引入 Object Shapes 优化 。
    
3. **基本类型对象的特化**：`RString`、`RArray`、`RRegexp` 等用特化结构体，以 `RBasic` 开头，后面跟针对该类型的优化字段 。
    
4. **简单立即值（Fixnum/Symbol/nil/true/false）没有 C 结构体**——值直接编码在 VALUE 指针里。这是 Ruby 小整数运算极快的根本原因 。
    
5. **立即值的实例变量存在全局 `generic_iv_tbl` 里**——这是一个优雅的逃生舱设计，保证了"一切皆对象"的语义完整性，同时不拖累热路径性能 。
    
6. **RClass 结构**：极简的 `RClass`（RBasic + super + m_tbl）+ 丰富的 `rb_classext_struct`（iv_tbl、const_tbl、cvc_tbl、superclasses 缓存、origin、refined_class、allocator 等）。类本身也是对象，体现了"一切皆对象" 。
    
7. **继承通过 super 指针链实现**——子类不复制父类方法，只是通过指针链接。方法查找沿 super 链向上 。
    
8. **类实例变量 vs 类变量**：
    
    - 类实例变量（`@foo`）：只在当前类的 `iv_tbl` 查找，不继承
        
    - 类变量（`@@foo`）：沿 super 链向上查找，子类"看到"父类的类变量，且赋值会穿透到父类
        
    
9. **常量存在 const_tbl 里**，查找结合词法作用域和继承链 。
    

🔑 **贯穿全章的核心洞见**：

> **Ruby 对象模型的本质是"引用 + 共享"。**
> 
> - 对象通过 `klass` 指针**引用**类，共享类的方法
>     
> - 同类实例通过类的 `iv_index_tbl` **共享**属性名映射，各自持有值
>     
> - 子类通过 `super` 指针**引用**父类，共享父类的方法
>     
> - 类变量通过 super 链**向上共享**
>     
> 
> 这种设计的第一性原理是——**共享优于复制**。它让 Ruby 在保持动态灵活性的同时，内存占用保持在合理范围。

- **第6章"方法查找与常量查找"**：本章埋下了 super 指针和方法表 m_tbl，下一章将详细讲解 Ruby 如何遍历祖先链查找方法、Module#include 如何工作、全局方法缓存和内联方法缓存如何加速查找
    
- **类变量的陷阱**：本章揭示的类变量"穿透"行为，是 Ruby 元编程中著名的坑。理解它在 C 层面的实现（沿 super 链向上找第一个），你就不会再被它绊倒
    
- **Object Shapes 技术**：Ruby 3.3+ 引入的这项技术，把"对象形状"抽象为独立实体，让同类同形状的对象共享 Shape 对象。这是基于本章讲的 `iv_index_tbl` 机制的进一步演进

📌 **工业实践建议**：

当你在设计 Ruby 领域模型时：

1. **在 `initialize` 中一次性设置所有实例变量**——让对象形状尽早稳定，配合 Object Shapes 获得最佳性能
    
2. **避免使用类变量 `@@`**——改用 `class << self; attr_accessor :foo; end` 模式，语义更清晰，不会意外穿透
    
3. **理解"对象只持状态，类持行为"**——这意味着为对象添加方法（通过 `define_method`）会改变类的 m_tbl，影响所有实例
    
4. **警惕给 Symbol/nil/true/false 添加实例变量**——它们走 `generic_iv_tbl` 全局哈希，性能差且有锁竞争
    
5. **利用"类也是对象"**——类可以作为参数传递、可以动态创建（匿名类）、可以在运行时修改，这是 Ruby 元编程威力的根源
