
# 第6章 读书笔记：方法查找和常量查找

> 💡 这一章回答的核心问题是：**当写下 `obj.foo` 时，Ruby 如何知道要执行哪段代码？当写下 `CONST` 时，Ruby 如何知道它指向哪个常量？**
> 
> 从第一性原理看，这是两个本质不同的查找问题：**方法查找是"沿着祖先链做线性探针"**，而**常量查找是"先在词法作用域里找，找不到再去继承链找"**。前者由"接收者的类"驱动，后者由"代码书写位置的嵌套结构"驱动——这个差别是 Ruby 语义最精妙、也最容易被误解的地方。

📌 **时代注记**：原书基于 Ruby 2.0。今天（Ruby 3.x/4.x）的方法缓存已从"全局状态版本号"演进为更细粒度的机制（见 Ruby Issue #16614），但**祖先链查找算法、include/prepend 的语义、常量查找的两阶段规则，至今未变**——本章的知识对现代 Ruby 完全适用 。

---

## 6 方法查找和常量查找

承接第5章——我们已经知道每个对象通过 `klass` 指针找到自己的类，类里有 `m_tbl` 方法表。但 Ruby 支持 `include` 模块、`prepend` 模块、多层继承、单件方法、refinement……这些方法定义分散在不同的类/模块里。**"查找"的本质，就是沿着一张"扁平化的祖先链"从左到右扫描，找到第一个匹配的方法名**。

🎯 **我的洞见**：Ruby 的方法查找之所以让人觉得"魔法"，是因为它在 C 层面极其朴素——就是一个 while 循环：

```
klass = recv->klass;
while (klass) {
    if ((me = m_tbl_lookup(klass->m_tbl, mid))) return me;
    klass = RCLASS_SUPER(klass);
}
```

但这个朴素的循环之上，Ruby 构建了一整套**动态改写祖先链**的机制：`include` 往 `super` 链里插节点、`prepend` 在类前面插节点、单件类悄悄插入到对象和类之间、refinement 在词法作用域内临时改链。所有这些"魔法"在查找那一刻都消失了——查找看到的只是一张**已经扁平化好的线性链表**​ 。

## 6.1 Ruby 如何实现模块

### 6.1.1 模块是类

Ruby 内部，`Module` 和 `Class` 的关系比表面上更紧密——**`Class` 的父类就是 `Module`**​ ：

```
Class.superclass    # => Module
Module.superclass   # => Object
```

在 C 层面，`RClass` 结构体既用于表示类，也用于表示模块 。模块和类的唯一实质区别是：

- **类可以被实例化**（`allocate` 分配对象），有 `allocator` 函数
    
- **模块不能被实例化**，但可以被 `include`/`prepend` 到其他类或模块中
    

🎯 **我的洞见**：**"模块"在内部就是一个"没有 allocator 的 RClass"**。这个设计的第一性原理是**复用**——模块和类共享同一套内部结构（方法表、常量表、super 指针、iv_index_tbl），区别仅在于"能否 new"。这让 `include` 模块变得极其自然：把模块的 RClass 插入到类的 super 链里，模块的方法就"像"是类自己的方法了。

### 6.1.2 将模块 include 到类中

这是 Ruby 混入（mixin）的核心机制。原书详细描述了 include 时发生了什么 ：

当 `class C; include M; end` 执行时，Ruby 内部：

1. **复制模块 M**：Ruby 不会直接把 M 的 RClass 挂到 C 的 super 链上，而是创建一个 **iclass（include class）节点**——它是一个代理 RClass，指向 M 的方法表，但没有自己的名字
    
2. **插入 super 链**：把这个 iclass 插入到 C 原本的 super（即 C.superclass）**之前**
    

```
include 前：
C → super → Object → ...

include M 后：
C → super → iclass(M) → super → Object → ...
```

🎯 **我的洞见（本节最核心的认知）**：

> **include 的本质是"在 super 链里插入一个代理节点"，而不是"把模块的方法复制到类里"。**
> 
> 这就是为什么：
> 
> - 模块 M 后来新增的方法，会自动出现在所有 include M 的类里（因为它们共享同一个方法表）
>     
> - 多个类 include 同一个 M，它们看到的方法定义始终一致
>     
> - include 不会让类的方法表膨胀
>     

原书 6.2.11 和 6.2.12 专门验证了这一点——**在已被 include 的模块中增加方法，或者在已被 include 的模块中再 include 其他模块，这些变更会即时反映到所有 include 它的类中**​ 。这证实了"共享方法表"而非"复制方法表"的实现本质。

⚠️ **关键细节**：原书 6.2.13 进一步指出——**"被 include 的类"与原始模块共享方法表**。这意味着：

```
module M
  def foo; "foo from M"; end
end

class C
  include M
end

M.instance_method(:foo) == C.instance_method(:foo)  # => true（共享同一个 method entry）
```

这在元编程中意义重大——你修改 `M` 的方法，所有 include `M` 的类的行为都会改变。

## 6.2 Ruby 的方法查找算法

原书给出官方算法：**从接收者类 R 开始，依次检查 R 的 prepend 模块（逆序）、R 自身、R 的 include 模块（逆序）；如果 R 有 superclass，则对 superclass 重复上述过程，直到找到方法**​ 。

但 Noel Rappin 在 2025 年的文章中给出了一个更简洁、更准确的现代表述 ：

> **Ruby 取 `receiver.singleton_class.ancestors` 这张列表，从左到右扫描，第一个包含该方法的类/模块即为所求。**

这个表述把"prepend 模块、类自身、include 模块、superclass 链、单件类"全都统一了——因为它们**都已经扁平化在这张 ancestors 列表里**。

### 6.2.1 方法查找示例

```
module Pre
  def say; "prepend"; end
end

class Kla
  prepend Pre
  def say; "class"; end
end

r = Kla.new
r.singleton_class.ancestors
# => [#<Class:#<Kla>>, Pre, Kla, Object, JSON::Ext::Generator::GeneratorMethods::Object, PP::ObjectMixin, Kernel, BasicObject]

r.say  # => "prepend"（Pre 在 Kla 之前，所以先找到 Pre#say）
```

如果执行 `def r.say; "banana"; end`，那么 `r.singleton_class` 里就有了 `say` 方法，查找在第一站就停止，`r.say` 返回 `"banana"` 。

### 6.2.2 方法查找算法实践

完整的 MRO（方法解析顺序）示例 ：

```
module M1; end
module M2; end
module M3; end

class Base
  include M1
end

class Child < Base
  prepend M2
  include M3
end

Child.ancestors
# => [M2, Child, M3, Base, M1, Object, Kernel, BasicObject]
```

规则总结 ：

1. **prepend 的模块在类自身之前**，且后 prepend 的在前
    
2. **类自身**
    
3. **include 的模块在类自身之后**，且后 include 的在前
    
4. **superclass 链**，对 superclass 重复 1-3
    

🎯 **我的洞见**：这套规则的本质是**"越具体越靠前"**——

- 单件方法（只对某一个对象生效）→ 最具体 → 最前面
    
- prepend 模块（包装类的行为）→ 很具体 → 类前面
    
- 类自身 → 基础
    
- include 模块（为类添加能力）→ 类后面
    
- superclass → 更泛化 → 更后面
    

这是面向对象设计"具体化优先"原则在查找顺序上的直接体现。

### 6.2.3 Ruby 中的多继承

Ruby 没有经典意义上的多继承（一个类直接继承多个类），但通过 `include` 实现了**类似多继承的能力**​ 。

🎯 **我的洞见**：原书 6.1.1 节明确指出——**"Essentially, there is no difference between including a module and specifying a superclass"**（include 一个模块和指定一个 superclass 本质上没有区别）。Ruby 内部维护的依然是**单链 super 继承**——模块通过 iclass 节点插入到这条单链中，让方法查找看起来像是"多继承"。

这正是 Ruby 的优雅之处：**用单继承的底层结构，模拟出多继承的表达力**。每个类只有一条 super 链，但链上可以穿插多个模块的 iclass 节点。

### 6.2.4 全局方法缓存

方法查找虽然是简单的链表遍历，但**在深层继承链上，每次调用都要走多个节点**——这对热点方法来说是巨大的开销。

Ruby 的解决方案是**全局方法缓存（Global Method Cache）**​ ：

- 一张全局哈希表，key 是 `klass#method`，value 是 `defined_class#method`
    
- 默认 **2048 个条目**，可通过环境变量 `RUBY_GLOBAL_METHOD_CACHE_SIZE` 调整（必须是 2 的幂）
    
- Shopify 工程师发现，即使是超大型 Rails 应用，2048 条目也能达到 90%+ 的命中率
    
- 每条缓存条目 40 字节，默认占用约 80KB；调到 128K 条目约占用 2.5MB
    

示例缓存内容 ：

|klass|defined_class|
|---|---|
|`Fixnum#times`|`Integer#times`|
|`Object#puts`|`BasicObject#puts`|

### 6.2.5 内联方法缓存

全局方法缓存是"备用方案"。**真正的第一道防线是内联方法缓存（Inline Method Cache）**​ ：

- 内联缓存在**特定的调用点（call site）**
    
- 它是"inline"的，因为缓存就存储在 Ruby 代码的 YARV 指令中，紧挨着 `send` 指令
    

```
# 原始 YARV
putobject 10
send

# 缓存结果后
putobject 10
send <Integer#times>    # 缓存的方法查找结果直接附在 send 指令上
```

🎯 **我的洞见（本节最核心的认知）**：

> **内联方法缓存的 key 是两个值：全局方法状态（global_method_state）+ 类序列号（class_serial）**​ 。
> 
> - `global_method_state`：全局串行号，每当某些类发生变异（例如 monkey patching）时递增
>     
> - `class_serial`：接收者类的序列号，每个类都有，对类做某些操作（如重开类）时会递增
>     
> 
> 缓存的值是：要调用的方法。

当内联缓存命中时，`send` 指令直接取出缓存的方法执行，**完全跳过祖先链查找**。Tenderlove 的实验显示，仅仅给 `Kernel` 增加一个方法，就会改变 `global_method_state`——而**改变这个值在运行时有很坏的影响，因为它会使所有的调用缓存失效**（因为调用缓存的 key 就是"类序列号"和"全局方法状态"）。

### 6.2.6 清空 Ruby 的方法缓存

James Golick 的文章揭示了 Ruby 方法缓存失效的残酷真相 ：

> **MRI 的缓存失效策略是全局的——任何时候你对任何类做任何修改，整个 VM 的方法缓存会同时被清空。**

Charlie Somerville 整理了完整的"缓存破坏"操作清单 ：

- `create` 或 `remove`（undef）一个方法
    
- `include` 一个模块到类中
    
- `refinements`
    
- 其他可能的元编程技术
    

结果是——**clearing the cache happens quite frequently in Ruby. The global and inline method caches might remain valid for only a short time**。

James Golick 在他们生产环境的测量：**每个请求至少 20 次缓存失效，约 10% 的请求时间花在方法解析上**，平均每次方法解析约 1 微秒，每个请求至少 8000 次缓存未命中，总计 8ms 以上 。

🎯 **我的洞见**：这就是为什么你经常听到"调用 `Object#extend` 是坏的"这类说法——**它不仅仅是 Object#extend 本身，而是它背后的全局缓存失效**。任何元编程操作（如 Rails 中 ActiveRecord 的某些动态行为、OpenStruct 的实例化）都会在背后触发缓存失效。

⚠️ **重要演进**：Ruby Issue #16614 提出了全新的方法缓存机制 ：

- **Disposable IMC**：把 CC 做成 RVALUE（GC 对象），miss 时分配新的 CC
    
- **per-Class Method Cache（pCMC）**：替代固定大小的全局缓存，允许灵活的缓存大小
    
- **基于 method entry 失效**：不再用 class serial，而是给 method entry 设"invalidated"标志
    

这意味着现代 Ruby 正在从"粗粒度全局失效"走向"细粒度精准失效"——**修改一个方法，只让指向该方法的缓存失效，而不是让所有缓存失效**。

### 6.2.7 在同一个类中 include 两个模块

```
module A
  def foo; "A"; end
end

module B
  def foo; "B"; end
end

class C
  include A
  include B
end

C.new.foo  # => "B"
```

**后 include 的模块在祖先链中更靠前**（逆序插入）。

```
include A 后：C → iclass(A) → Object
include B 后：C → iclass(B) → iclass(A) → Object
```

所以 `B#foo` 先被找到 。

### 6.2.8 在模块中 include 模块

模块也可以 include 其他模块。查找时，被包含模块的 iclass 节点会**嵌套**在包含它的模块的 iclass 之前 ：

```
module C
  def c; "c"; end
end

module A
  include C
  def a; "a"; end
end

class B
  include A
end

B.new.c  # => "c"
B.ancestors
# => [B, A, C, Object, Kernel, BasicObject]
```

**注意 `A` 在 `C` 之前**——因为 `A` 自身的方法（如 `a`）应该优先于它 include 的 `C` 的方法（如 `c`）。

### 6.2.9 Module#prepend 示例

`prepend` 与 `include` 方向相反——**prepend 插入的模块在类自身之前**：

```
module Logging
  def call
    puts "before"
    super
  end
end

class Service
  prepend Logging
  
  def call
    puts "service"
  end
end

Service.new.call
# 输出：
# before
# service

Service.ancestors
# => [Logging, Service, Object, Kernel, BasicObject]
# 注意：不是 [Service, Logging, Object]
```

这就是为什么 `Logging#call` 先执行，且 `super` 能正确委托给原始的 `Service#call`。

### 6.2.10 Ruby 如何实现 Module#prepend

这是原书最精彩的部分之一——**prepend 的内部实现比 include 复杂得多**​ 。

`prepend` 不是简单地在 super 链前面插一个 iclass。MRI 的做法是：

**prepend 前的结构**：

```
Service (方法表中有 call) → super → Object
```

**prepend 后的结构**：

```
Service (方法表为空) → super → iclass(Logging) → super → Service_origin (原始方法) → super → Object
```

具体步骤 ：

1. **复制 Service 为 Service_origin**：把 Service 的原始方法表移到 Service_origin 中
    
2. **清空 Service 的方法表**：Service 本身变成"空壳"
    
3. **插入 Logging 的 iclass**：在 Service 的 super 链上、Service_origin 之前插入 Logging 的 iclass
    
4. **Service 的 origin 指针指向 Service_origin**
    

🎯 **我的洞见（本节最震撼的认知）**：

> **prepend 的本质是"把类自己拆成两层"——外层是空壳 Service，内层是 Service_origin 持有原始方法。prepend 的模块插在这两层之间。**
> 
> 为什么要这么复杂？因为要保证 `super` 的正确性：
> 
> - 当 `Logging#call` 调用 `super` 时，查找从 Logging 的 super（即 Service_origin）继续
>     
> - Service_origin 里有原始的 `call` 方法
>     
> - 所以 `super` 正确委托给了原始的 Service#call
>     

这是 MRI 中最聪明的工程设计之一——**用"拆分类"的技巧，让 prepend 模块的 `super` 调用能穿越"类自身"这一层，找到原始实现**。

💡 **工业应用**：prepend 是现代 Ruby 切面编程（AOP）的首选机制：

- **Rails 的 `ActiveSupport::Callbacks`**：在方法前后织入回调
    
- **计量和日志**：包裹业务方法，记录执行时间
    
- **授权检查**：在控制器动作前验证权限
    
- **相比 `include` + `alias_method_chain` 的老方案**，`prepend` 更干净、不会有别名链断裂的问题
    

### 6.2.11 在已被 include 的模块中增加方法

原书验证了：动态给已 include 的模块添加方法，会即时反映到所有 include 该模块的类 。

```
module A
  def a; puts 'a'; end
end

class B
  include A
end

B.new.a  # => "a"

module C
  def c; puts 'c'; end
end

module A
  include C
end

B.new.c  # => "c"  ✅ 立即可用
```

这证实了 6.1.2 节的结论——**iclass 节点与原始模块共享方法表**。

### 6.2.12 在已被 include 的模块中 include 其他模块

与上节同理，模块的方法表是实时共享的。

### 6.2.13 "被 include 的类"与原始模块共享方法表

原书强调：**include 时创建的 iclass 节点，与原始模块共享同一个方法表（m_tbl）**。

这意味着：

```
module M
  def foo; "foo"; end
end

class C
  include M
end

M.instance_method(:foo).object_id == C.instance_method(:foo).object_id  # => true
```

**它们指向内存中同一个 method entry**。这就是为什么修改模块会即时影响所有 include 它的类。

## 6.3 常量查找

常量查找与方法查找有着根本性的不同。原书指出——**常量的解析方式和方法大不相同**​ 。

### 6.3.1 在超类中查找常量

最简单的场景：

```
class SuperClass
  CONST = "from SuperClass"
end

class SubClass < SuperClass
end

SubClass::CONST  # => "from SuperClass"
```

### 6.3.2 Ruby 如何在父级命名空间中查找常量

这是 Ruby 常量查找最独特的一面——**词法作用域优先**：

```
module A
  CONST = "A"
  
  module B
    def self.show
      CONST  # => "A"（在词法外层 A 中找到）
    end
  end
end
```

`Module.nesting` 揭示了查找顺序 ：

```
module A
  module C
    module D
      Module.nesting  # => [A::C::D, A::C, A]
    end
  end
end
```

Ruby 按 `Module.nesting` 的顺序查找常量——先看 `A::C::D`，再看 `A::C`，再看 `A`。

🎯 **我的洞见**：**常量查找与方法查找的根本区别在于"起点"**：

- **方法查找的起点是 `self.class`**（接收者的类）
    
- **常量查找的起点是 `Module.nesting`**（代码书写位置的词法嵌套）
    

这就是为什么在方法内部访问常量时，常量的查找不依赖于 `self`：

```
class A
  CONST = "A's constant"
end

class B < A
  def get_const
    CONST  # 查找的是 B 的词法作用域，不是 self.class
  end
end

B.new.get_const  # => "A's constant"
# 但如果 self 是 B 的实例，且 B 没有 CONST，则会沿着 B 的祖先链找到 A::CONST
```

## 6.4 Ruby 中的词法作用域

Ruby 常量查找的完整算法是 ：

1. **词法作用域查找**：在 `Module.nesting` 列出的类/模块中依次查找
    
2. **继承层次查找**：在"当前打开的类/模块"的 `ancestors` 中查找
    
3. **顶级常量查找**：在 `Object` 的常量中查找
    
4. **const_missing**：调用当前类/模块的 `const_missing` 方法（如果有）
    

### 6.4.1 为新类或模块创建常量

```
module A
  B = Class.new do
    VALUE = 1
  end
  
  C = Class.new do
    VALUE = 2
  end
end

A::B::VALUE  # => 未初始化常量错误！
A::VALUE     # => 2（意外地在 A 上定义了 VALUE）
```

⚠️ **关键陷阱**：`Class.new` 和 `Module.new` **不会影响 Module.nesting**！所以用 `Class.new` 动态创建的类，其词法作用域不是预期的嵌套结构。这就是为什么 RSpec 的 `describe` 块内定义常量往往是全局的——除非显式指定 `self::CONST`。

### 6.4.2 在父命名空间中使用词法作用域查找常量

```
module A
  CONST = 1
  
  def A.method1
    Module.nesting  # => [A]
    CONST + 1       # => 2（在 A 中找到）
  end
end

module A::Inner
  def (A::Inner).method2
    Module.nesting  # => [A::Inner]（注意：没有 A！）
    CONST + " scope" # => "outer scope"（A 不在 nesting 中，所以去顶级找）
  end
end
```

**关键认知**：`module A::Inner` 这种"跳过式"定义，**不会把 A 加入 Module.nesting**。必须用嵌套形式：

```
module A
  module Inner
    def (A::Inner).method2
      Module.nesting  # => [A::Inner, A] ✅
      CONST.to_s + " scope"  # => "1 scope"
    end
  end
end
```

这就是为什么 Ruby 风格指南推荐用嵌套形式而非 `::` 形式定义模块 。

### 6.4.3 Ruby 的常量查找算法

综合上述，完整算法 ：

```
1. 词法作用域查找（Module.nesting）：
   - 依次检查 nesting 中的每个类/模块是否定义了该常量
   - 找到则返回

2. 继承层次查找：
   - 取"当前打开的类/模块"（innermost class/module statement）
   - 检查其 ancestors 列表中是否定义了该常量
   - 找到则返回

3. 顶级常量查找：
   - 检查 Object 的常量（几乎所有类都继承自 Object）
   - 找到则返回

4. const_missing：
   - 调用当前类/模块的 const_missing 方法
   - 如果没有，则抛出 NameError
```

### 6.4.4 Ruby 真实的常量查找算法

🎯 **我的洞见（本章最核心的认知）**：

> **方法查找和常量查找是两套平行的体系，它们在"起点"上根本不同：**
> 
> |维度|方法查找|常量查找|
> |---|---|---|
> |起点|`self.singleton_class.ancestors`|`Module.nesting` → 当前类的 `ancestors` → `Object`|
> |驱动|接收者对象|代码书写位置|
> |是否受 self 影响|是|**否**​|
> |词法作用域|不参与|**第一优先级**​|
> 
> 这就是为什么在 `class << self` 内部访问常量时会有意外行为 ：
> 
> ```
> class SuperExample
>   A_CONSTANT = "super example constant"
> end
> 
> class SubExample < SuperExample
>   class << self
>     def print_constant_fails
>       A_CONSTANT  # NameError! 
>     end
>   end
> end
> ```
> 
> 因为 `class << self` 的作用域是 `#Class:SubExample`，它的 `Module.nesting` 是 `[#Class:SubExample, SubExample]`。在第二项 `SubExample` 中查找时，会沿 `SubExample.ancestors` 找到 `SuperExample`——等等，这应该能找到啊？
> 
> 不，关键在于：**`class << self` 里的代码，其"当前打开的类"是 `#Class:SubExample`（即 SubExample 的单件类），而不是 SubExample 本身**。`#Class:SubExample` 的 ancestors 是 `[#Class:SubExample, #Class:SuperExample, #Class:Object, ...]`，这里面**没有 SuperExample 这个类**——只有它的单件类 `#Class:SuperExample`。所以 `A_CONSTANT` 找不到。

这个例子完美展示了"常量查找由词法作用域驱动，而非 self"这一原则。

## 6.5 总结

本章我们从第一性原理梳理了 Ruby 的方法查找与常量查找：

1. **模块是类**：`Class` 的父类是 `Module`，模块在内部就是一个没有 allocator 的 RClass 。
    
2. **include 的实现**：创建一个 **iclass 代理节点**，插入到类的 super 链中、原 superclass 之前。iclass 与原始模块**共享方法表**​ 。
    
3. **方法查找算法**：沿着 `receiver.singleton_class.ancestors` 线性扫描，第一个包含该方法的类/模块即为所求。顺序规则：单件类 → prepend 模块（逆序）→ 类自身 → include 模块（逆序）→ superclass 链 。
    
4. **prepend 的实现**：把类"拆成两层"——外层空壳 + 内层 origin 持有原始方法，prepend 的模块插在两层之间。这保证了 `super` 能正确穿越到原始实现 。
    
5. **方法缓存**：
    
    - **内联方法缓存**：存储在 `send` 指令旁，key 是 `global_method_state` + `class_serial`，value 是要调用的方法
        
    - **全局方法缓存**：默认 2048 条目，key 是 `klass#method`，value 是 `defined_class#method`
        
    - **失效机制**：Ruby 2.0 时代是**全局粗粒度失效**——任何类变异都会清空所有缓存
        
    - **现代演进**：Ruby 正在转向 per-Class 方法缓存 + 基于 method entry 的细粒度失效
        
    
6. **常量查找算法**：**词法作用域优先，继承层次其次，顶级常量最后**​ 。
    
    - 第一步：`Module.nesting` 中的类/模块
        
    - 第二步：当前打开类/模块的 `ancestors`
        
    - 第三步：`Object` 的常量
        
    - 第四步：`const_missing`
        
    
7. **词法作用域的关键性**：`module A::B` 这种"跳过式"定义**不会把 A 加入 Module.nesting**，导致 A 的常量不可见。必须用嵌套形式 。
    
8. **方法查找 vs 常量查找的根本差异**：方法查找由 `self` 驱动，常量查找由代码书写位置驱动。
    

🔑 **贯穿全章的核心洞见**：

> **Ruby 的查找系统，本质上是在"动态性"和"性能"之间取得平衡的艺术。**
> 
> - **方法查找**：用扁平化的祖先链 + 双层缓存（内联 + 全局），把动态的混入机制"伪装"成静态的快速查找
>     
> - **常量查找**：用词法嵌套 + 继承链的两阶段查找，把"代码书写位置"的语义与"面向对象继承"的语义统一起来
>     
> 
> 两者都体现了同一个第一性原理——**用预处理（扁平化祖先链、Module.nesting）把动态结构转换为静态结构，然后用缓存加速静态结构的查找**。

⚠️ **给后续章节的铺垫**：

- **第7章"哈希表"**：方法表和常量表内部都是哈希表。本章我们看到了方法查找的算法，下一章将深入这些方法表和常量表在内部是如何用哈希表数据结构实现的，以及哈希冲突如何处理
    
- **方法缓存与现代 Ruby**：Ruby 3.x 的 MJIT/RJIT 正是基于方法缓存的有效性做优化的——稳定的调用点可以被 JIT 编译，而频繁的缓存失效会让 JIT 代码失效
    
- **Zeitwerk**：现代 Rails 用 `const_missing` 实现自动加载，这正是常量查找算法的第四步工程应用
    
- **prepend 与 AOP**：prepend 的这种"拆分类"实现，是 Ruby 切面编程的基础。理解它，你就能看懂 Rails 的 `ActiveSupport::Callbacks`、`PaperTrail` 的版本追踪等库的底层机制
    

📌 **工业实践建议**：

1. **减少运行期的元编程**：避免在热点路径上 `define_method`、`include`、`extend`——每次都会触发全局方法缓存失效
    
2. **prepend 优于 alias_method_chain**：现代 Ruby 切面编程首选 prepend，语义清晰且不破坏方法链
    
3. **用嵌套形式定义模块**：`module A; module B; ...; end; end` 而非 `module A::B; ...; end`，确保词法作用域正确
    
4. **警惕 `Class.new` 动态创建类**：它不影响 Module.nesting，容易导致常量查找意外
    
5. **顶级常量用 `::` 明确引用**：在嵌套深的模块中，用 `::String` 而非 `String` 避免遮蔽
    
6. **调整全局方法缓存大小**：对于大型 Rails 应用，适当调大 `RUBY_GLOBAL_METHOD_CACHE_SIZE`（如设为 4096 或 8192）可减少缓存失效
    
7. **理解 `const_missing` 的性能成本**：它是常量查找的最后一道防线，频繁触发意味着常量定义有问题
