
# 第1章 读书笔记：分词与语法解析

> 💡 这一章的本质，是回答一个问题：**一段自由的 Ruby 文本，是如何被机器"读懂"的？**
> 
> 从第一性原理看，它解决的是"字符 → 有意义的单词 → 符合语法的结构 → 树形的语义表示"这一连串信息转换。Ruby 并不是"直接执行代码"，而是先把你写的自由文本，逐级翻译成它自己能处理的严谨数据结构。

---

## 1 分词与语法解析

Ruby 在执行你的代码之前，会把源码经历**三次变换**（character → token → AST → YARV bytecode）。本章聚焦前两步：

- **分词（Tokenization）**：把字符流切成"单词"（token）
    
- **语法解析（Parsing）**：按语法规则把 token 流组织成抽象语法树（AST）
    

这两步在 Ruby 里**不是先后串行，而是同时发生**——解析器在需要一个新 token 时，才会驱动词法器往后切下一个词 。这一点很关键：很多人误以为"先全量分词、再全量解析"，但 MRI 的实现是**边解析边要词**，解析器的状态和词法器的状态相互咬合。

🎯 **我的洞见**：这种"按需分词"不是偶然设计，而是 Ruby 语法的**上下文敏感性**决定的。Ruby 中同一个字符 `/` 可能是除法运算符，也可能是正则字面量的开头；同一个 `do` 可能是块的开头，也可能是循环体的开头。词法器必须知道"解析器现在期望什么"，才能正确地切出 token。换句话说，**Ruby 的词法分析是有状态的（stateful），而不是纯粹的正则切分**。这也是为什么 Ruby 没有用 Lex 那种传统词法生成器，而是**手写词法器**​ 。

---

## 1.1 词条：构成 Ruby 语言的单词

词条（token）是 Ruby 语言的最小有意义单元：关键字（`def`、`end`、`if`）、标识符、操作符、数字、字符串等。

### 用 Ripper 观察词条

Ruby 1.9 起内置了 **Ripper**​ 标准库，它复用了 MRI 自身的分词和解析代码，让我们可以"窥探"Ruby 内部是怎么看待我们的代码的 。

```
require 'ripper'
require 'pp'

pp Ripper.lex("def m(a) nil end")
# => [[[1, 0], :on_kw, "def"],
#     [[1, 3], :on_sp, " "],
#     [[1, 4], :on_ident, "m"],
#     [[1, 5], :on_lparen, "("],
#     ...
```

每个词条是一个四元组：`[行号, 列号]`、词条类型（如 `:on_kw`、`:on_ident`）、原始文本、以及词法器当时的状态 。

🎯 **我的洞见**：注意最后那个"词法器状态"字段（如 `EXPR_BEG`、`EXPR_ARG`、`EXPR_END`）。这是 Ruby 词法器**最有特色的设计**——它是一个有限状态机，用大约 20 个状态来记录"我现在处在表达的什么位置" 。比如：

- 在 `EXPR_BEG`（表达式开头）遇到 `*` → 它是 splat 操作符
    
- 在 `EXPR_END`（表达式结尾）遇到 `*` → 它是乘法操作符
    
- 在 `EXPR_BEG` 遇到 `&` → 它是 block 参数的前缀
    
- 在 `EXPR_END` 遇到 `&` → 它是按位与
    

**这就是 Ruby 语法"看似随意实则严谨"的根本原因**。词法器不是孤立地看一个字符，而是带着"上下文"去解释它。

⚠️ **重要认知**：词法器**不做语法正确性检查**。你给它完全非法的 Ruby 代码，它照样能切出 token 来 ：

```
Ripper.tokenize("1var @= /foobar`")
# => ["1", "var"]
```

语法对错是下一步解析器的职责。**职责分离**是这一步设计的第一性原理：**词法器只回答"这是什么词"，解析器才回答"这些词排在一起合不合法"**。

### 工业实际应用

理解词条切割，在工程上有非常具体的用途：

- **SyntaxTree**​ 等工具直接基于 CRuby 的内部解析器生成语法树，提供代码格式化、检查、模式匹配能力，可用于统一的编码规范检查
    
- **RubySonar**​ 这类深静态分析器（Sourcegraph 的底层技术之一）通过解析 Ruby 代码做类型推断和跨过程分析，为 IDE 和代码搜索提供支撑
    
- 编辑器中的语法高亮、括号匹配、增量解析，本质上都是在 Token 级别或 AST 级别做文章

## 1.2 语法解析：Ruby 如何理解代码

分词解决了"单词"问题，解析要解决"造句"问题：把线性排列的 token 流，组织成一棵**抽象语法树（AST）**。

### Ruby 的真实做法

Ruby 使用一个叫 **Bison**​ 的 LALR 解析器生成器。但注意——**Ruby 不是在运行时调用 Bison**，而是在**构建 Ruby 本身的时候**，用 Bison 读取语法规则文件 `parse.y`，生成解析器代码 `parse.c` 。

流程是这样的：

```
构建期：parse.y ──(Bison/Lrama)──> parse.c（生成的解析器）
运行期：parse.c 解析词法器输出的 token 流 ──> AST（NODE 树）
```

`parse.y` 这个文件非常庞大——约 520KB、超过 13000 行，是 Ruby 源码树中最复杂的单一文件 。它里面**同时包含**：

- 语法规则（Bison 部分）
    
- 词法器代码（手写的 `yylex` 函数）
    
- 语义动作（规约时创建 NODE 节点的 C 代码）
    

🎯 **我的洞见**：这里有个非常巧妙的工程 trick——`parse.y` 通过条件编译，让同一个语法文件**既服务于 Ruby 自身（构建 NODE 树），又服务于 Ripper（产生事件流）**​ 。用注释分隔：

- `/*%%%*/ ... /*%` 之间的代码 → 编译进 Ruby 本体，负责创建 NODE
    
- `/%* ... %*/` 之间的代码 → 只编译进 Ripper，负责派发事件
    

这就是为什么 Ripper 能用和 Ruby 完全一致的语法规则去"模拟"解析——它们本来就是同一份 `parse.y` 的不同编译产物。

### 1.2.1 理解 LALR 解析算法

LALR = **Look-Ahead Left-to-right Rightmost derivation in reverse**，即"带向前看的、从左到右扫描的、最右推导的逆过程" 。

拆开理解：

- **L（Left-to-right）**：从左到右扫描 token 流
    
- **R（Reversed rightmost derivation）**：采用**自底向上**策略，通过**移进-归约（Shift-Reduce）**技术寻找匹配的语法规则
    
- **LA（Look-Ahead）**：必要时向前看一个 token，决定该怎么规约
    

#### 移进-归约机制

解析器维护一个栈，对输入 token 流执行两种操作 ：

1. **Shift（移进）**：把当前 token 压入栈，从输入流取下一个 token
    
2. **Reduce（归约）**：当栈顶的若干个元素正好匹配某条语法规则的右部时，把它们弹出，替换为该规则的左部（非终结符）
    

举个例子，假设语法规则是 `VerbAndObject : le gusta` 和 `SpanishPhrase : VerbAndObject el ruby`。解析 `le gusta el ruby` 时：

```
栈: []              输入: le gusta el ruby
→ Shift le          栈: [le]           输入: gusta el ruby
→ Shift gusta       栈: [le, gusta]    输入: el ruby
→ Reduce(VerbAndObject)  栈: [VerbAndObject]  输入: el ruby
→ Shift el          栈: [VerbAndObject, el]   输入: ruby
→ Shift ruby        栈: [VerbAndObject, el, ruby]  输入: ∅
→ Reduce(SpanishPhrase)  栈: [SpanishPhrase]  输入: ∅
→ Accept
```

解析器用一个**状态机**来管理这个过程。每个状态对应"当前已经看到了语法规则的哪一部分"。状态转移表由 Bison 在构建期根据 `parse.y` 算好 。

🎯 **我的洞见**：LALR 是一种**工程权衡的产物**。Knuth 提出的完整 LR(1) 解析器理论上最强大，但状态数爆炸；LALR 通过合并"核心相同、只是向前看集合不同"的状态，大幅压缩状态表，代价是偶尔会引入 LR(1) 中没有的归约-归约冲突 。**实测超过 90% 的编程语言语法都能用 LALR(1) 无冲突地解析**​ ——这就是它被 Yacc/Bison 选为默认算法的根本原因：在"能力"和"表格大小"之间取得了最佳平衡。

Ruby 的 `parse.y` 就是 LALR(1) 语法，用 `%token`、`%type`、`%left/%right/%nonassoc` 等指令声明终结符、非终结符和优先级 。你可以运行 `ruby -y your_script.rb` 看到解析器在状态之间跳转的调试信息 。

#### 为什么 Ruby 选择 LALR 而不是其他算法？

- **省内存**：LALR 的状态数和 SLR 相同，远小于 LR(1)
    
- **生态成熟**：Yacc/Bison 自 1975 年起就是工业级工具
    
- **错误恢复**：LALR 解析器能给出带行号列号的有用错误信息
    

### 1.2.2 真实的 Ruby 语法规则

`parse.y` 里的规则长这样 ：

```
symbol : tSYMBEG sym { $$ = $2; }

sym : fname | tIVAR | tGVAR | tCVAR ;

block_arg : tAMPER arg_value { $$ = NEW_BLOCK_PASS($2); }
```

- `%token` 声明终结符（terminal），如 `tIDENTIFIER`、`tFID`、`tGVAR`、`tIVAR`、`tCONSTANT`、`tCVAR`、`tLABEL`
    
- `%type` 声明非终结符（nonterminal），如 `expr_value`、`arg_value`、`primary_value`、`fcall`
    
- `$$` 代表当前规则的返回值，`$1`、`$2`... 代表子规则的返回值
    
- 语义动作里调用 `NEW_CALL`、`NEW_BLOCK_PASS` 等宏，**创建 NODE 节点**——这些节点最终组成 AST
    

#### AST 的形态

解析的产物是一棵由 **NODE**​ 组成的树。`NODE` 是一个 tagged union 结构，约有 150 种节点类型，每种 Ruby 语言构造都对应一种或多种节点 。

用 Ripper 可以直接看到 AST 的 S-表达式形式：

```
require 'ripper'
require 'pp'

pp Ripper.sexp('def hello(world) "Hello, #{world}!"; end')
# => [:program,
#     [[:def,
#       [:@ident, "hello", [1, 4]],
#       [:paren, [:params, [[:@ident, "world", [1, 10]]], nil, nil, nil, nil, nil, nil]],
#       [:bodystmt,
#        [[:string_literal,
#          [:string_content,
#           [:@tstring_content, "Hello, ", [1, 18]],
#           [:string_embexpr, [[:var_ref, [:@ident, "world", [1, 27]]]]],
#           [:@tstring_content, "!", [1, 33]]]]],
#         nil, nil, nil]]]]
```

从 `:program` 根节点出发，能看到 `:def` → `:paren`/`:params` → `:bodystmt` → `:string_literal` 这样的层级 。Ruby 2.6+ 还可以用 `RubyVM::AbstractSyntaxTree` 直接拿到内部 NODE 树 。

🎯 **我的洞见（这一节最关键的认知）**：

Ruby 语法之所以"感觉灵活"，是因为 `parse.y` 里大量使用**上下文相关的歧义消解**。几个典型例子：

1. **`/` 的歧义**：除法还是正则？词法器根据当前 lex state 决定。在 `EXPR_BEG` 状态下 `/` 是正则开头，在 `EXPR_END` 状态下是除法。
    
2. **`do` 块的歧义**：`while x do ... end` 是循环体，`foo x do ... end` 是块。解析器通过 bitstack 跟踪嵌套层级和命令参数上下文来区分 。
    
3. **heredoc 和字符串**：词法器用 `lex.strterm` 管理多行字符串边界 。
    
4. **`{` 的歧义**：是哈希字面量还是块？取决于它在方法调用参数中的位置。
    

这些都印证了前面说的——**Ruby 的词法器和解析器是深度耦合的，不是两个独立阶段**。理解这一点，你才能真正理解为什么 Ruby 的语法"看起来那么自由，却又那么严谨"。

📌 **现代演进**：Ruby 3.3 起引入了 **Prism**​ 作为新一代解析器，使用 Pratt 解析算法而非 LALR，提供更好的错误恢复和容错能力，目标是服务 IDE、静态分析等场景 。目前 `parse.y` 和 Prism 并存，可通过 `--parser=` 切换 。这是一个重要信号：**LALR 在"完整程序解析"上表现出色，但在"编辑器里的增量/容错解析"场景下力不从心**——这正是下一代工具的方向。

#### 工业实际应用

- **tree-sitter-ruby**：基于 Tree-sitter 的 Ruby 解析器，支持**增量解析**——用户连续输入时只重解析变更区域，响应延迟稳定在毫秒级，已深度集成到 Neovim、VS Code、GitHub Codespaces 等环境，支撑语义跳转、符号查找、重命名重构、智能补全等 LSP 能力
    
- **Rubysonar**：深静态分析器，做过程间类型推断，为代码搜索和 IDE 提供底层支撑
    
- **rsense-server**：基于 JRuby/Java 的 Ruby 静态分析服务器，处理 `method_missing`、`define_method`、`eval` 等动态特性，提供跨平台语义服务
    
- **SyntaxTree**：基于 CRuby 内部解析器，提供代码格式化、AST 遍历、模式匹配，可直接用于编码规范检查

## 1.3 总结

本章我们从第一性原理梳理了 Ruby 把源码"读懂"的全过程：

1. **分词**把字符流切成带上下文状态的词条。Ruby **手写词法器**（不用 Lex），用一个约 20 状态的有限状态机记录 `EXPR_BEG`/`EXPR_END`/`EXPR_ARG` 等上下文，从而消歧义（如 `/`、`*`、`&`、`do` 的多义性）。词法器只回答"这是什么词"，**不做语法检查**。
    
2. **语法解析**用 **LALR(1) 算法**（通过 Bison/Lrama 从 `parse.y` 生成 `parse.c`）把 token 流自底向上地**移进-归约**成一棵 **NODE 构成的 AST**。LALR 是"解析能力"和"状态表大小"之间的最佳工程折衷。
    
3. **Ruby 的真实语法规则**写在 `parse.y` 里——这个 13000+ 行的文件同时包含词法器、`%token`/`%type` 声明的语法规则、以及创建 NODE 的语义动作。同一份 `parse.y` 通过条件编译，既服务 Ruby 本体（产 NODE 树），又服务 Ripper（产事件流）。
    
4. **工业价值**：理解词条和 AST，是构建静态分析器（Rubysonar）、IDE 语义服务（rsense、tree-sitter-ruby）、代码格式化工具（SyntaxTree）、以及下一代容错解析器（Prism）的基础。
    

🔑 **贯穿全章的一个核心洞见**：

> Ruby 的"灵活语法"不是魔法，而是**词法器和解析器深度协作**的结果。词法器带着"解析器现在期望什么"的上下文去切词；解析器带着 LALR 状态机和向前看能力去消歧义。两者通过 `parse.y` 这一个"单一事实来源"紧密咬合。
> 
> 这也是为什么 Ruby 没有用常规的 Lex+Yacc 组合，而是**手写词法器 + Bison 生成解析器**——因为 Ruby 语法的上下文敏感性，远超常规 Lex 正则切分的能力边界。

⚠️ **给后续章节的铺垫**：

解析产出的 AST（NODE 树），下一章就要进入**编译阶段**——YARV 如何把这棵树编译成字节码。届时你会看到，`NODE_CALL`、`NODE_BLOCK_PASS` 这些我们在 `parse.y` 语义动作里创建的节点，会一一对应到 YARV 的指令。

另外值得持续关注的是：**Prism 解析器**正在改变 Ruby 工具链的格局 。它用 Pratt 解析而非 LALR，主打容错和可移植，目标是让 IDE、静态分析、跨平台工具都能共享同一个高质量解析器。理解本章的 LALR 思路，再去对照 Prism 的 Pratt 思路，你会发现**解析器设计的取舍本质上是"为哪种使用场景优化"的问题**——LALR 为"完整程序的一次性解析"优化，Pratt 为"编辑器里的增量/容错解析"优化。
