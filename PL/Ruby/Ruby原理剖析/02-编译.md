
# 第2章 读书笔记：编译

> 💡 这一章回答的核心问题是：**AST 已经建好了，Ruby 怎么把它变成能快速执行的东西？**
> 
> 从第一性原理看，"编译"的本质是**把树形的、递归的、带有大量间接性的 AST，重排成线性的、顺序的、适合栈式虚拟机快速分发的指令流**。这不是为了时髦，而是为了打破 Ruby 1.8 "每次执行都要重新理解 AST" 的性能天花板。

---

## 2.1 Ruby 1.8 没有编译器

Ruby 1.8 的执行路径只有两步：

```
源码 → 字符流 → 词条 → AST → 直接遍历 AST 节点执行
```

也就是说，1.8 的 MRI（Matz's Ruby Interpreter）在 parse.y 生成 AST 之后，**立刻开始递归遍历这棵树，边遍历边执行每个 NODE 代表的动作**——没有中间字节码 。

🎯 **我的洞见**：这种"树遍历解释器（tree-walking interpreter）"最大的问题在于——**AST 是递归结构，执行时也是递归调用**。每执行一个节点，就要做一次 C 函数调用、一次 switch/分支判断、一次子树递归。在热点循环里，这种开销会被放大多次。Python 之所以在 1.8 时代就比 Ruby 快，根本原因之一就是 Python 早就把 AST 编译成了线性字节码，让一个高度优化的栈式虚拟机去跑，而 Ruby 还在"每次都重新理解树" 。

用原书 Figure 2-1 的话说：**在 1.8 里，你的代码永远不会被完整编译成机器语言；如果你去反汇编 CPU 真正运行的机器码，你看到的不是映射到你 Ruby 代码的指令，而是实现 Ruby 解释器本身的 C 代码**​ 。

⚠️ **关键认知**：1.8 不是"没编译"，而是**编译到了 AST 这一层就停了**。AST 本身就是一种"中间表示"，但它不是为"快速执行"优化的，而是为"忠实表达语法结构"优化的。这两者有着根本不同的设计目标。

---

## 2.2 Ruby 1.9 和 Ruby 2.0 引入了编译器

Koichi Sasada（笹田耕一）在 Ruby 1.9 中引入了 **YARV（Yet Another Ruby Virtual Machine）**，执行路径变成了三步：

```
源码 → 词条 → AST → YARV 字节码 → YARV 解释器执行
```

这一步引入了真正的**编译器**：它把 AST 节点遍历一遍，生成一串低级的 YARV 指令 。

🎯 **我的洞见**：YARV 和 JVM 的思路同源，但有两点刻意保持不同 ：

|维度|JVM|YARV|
|---|---|---|
|编译器是否对用户暴露|是（`javac` 独立工具）|**否**，完全在内部自动完成|
|是否会 JIT 到机器码|是（HotSpot JIT）|**否**，只解释字节码|

**这两点"不做"都是有意为之的工程决策**：

1. **不暴露编译器**：Ruby 的哲学是"开发者只关心代码本身"。让用户手动调 `rubyc` 编译，违背了 Ruby 的流畅体验。所以编译被做成**运行时自动的、透明的**一步。
    
2. **不做 JIT**：Ruby 1.9 时代引入 JIT 的复杂度远超收益。YARV 先用"direct threaded code"技术解释字节码——执行完一条指令后直接跳到下一条指令对应的 C 函数，避免中央 switch 分发，减少 CPU 分支预测失败 。这种方式让 Ruby 1.9 比 1.8 **快约 1 倍**​ ，但没有 JIT 的复杂度。
    

📌 **历史注记**：真正的 JIT 要到 Ruby 2.6 的 MJIT、Ruby 3.0 的 MJIT/RJIT 才逐步落地。所以本书写于 2.0 时代，"YARV 只是解释器"是符合当时现实的——**YARV 是个更快的解释器，但不是 JIT 编译器**​ 。

💡 **性能直觉**：Fibonacci(30) 这种纯计算基准，Ruby 1.8 约 5.5 秒，1.9 降到约 3.0 秒，2.6+MJIT 进一步降到 1.5 秒，3.0 达到约 1.0 秒 。**第一步巨大飞跃（1.8→1.9）就来自"AST→字节码"这一章讲的事**。

## 2.3 Ruby 如何编译简单脚本

以 `puts 2+2` 为例，编译过程大致是：

1. 解析器生成 AST，根节点是 `NODE_SCOPE`，内含一个 `NODE_FCALL`（`puts` 调用），参数是一个 `NODE_ADD`（`2+2`）
    
2. 编译器从 `RubyVM::InstructionSequence.compile` 进入，核心函数是 **`iseq_compile_each`**——它**遍历 AST，对每个节点类型生成对应的 YARV 指令**​
    
3. 最终产物是一段 YARV 指令，类似：
    

```
0000 putobject 2
0002 putobject 2
0004 opt_plus
0005 opt_send_without_block :puts, 1
0008 leave
```

🎯 **我的洞见**：`iseq_compile_each` 这个函数名透露了关键信息——**编译就是"对每个 AST 节点，编译生成对应指令"**。这是一种**树的后序遍历**：先编译子节点（压栈操作数），再编译父节点（发出消费操作数的指令）。

观察上面这段指令，你能看到一个**栈式虚拟机的本质特征**：

- `putobject 2` 把整数 2 压栈
    
- 再来一个 `putobject 2` 压栈
    
- `opt_plus` 弹栈两个操作数、相加、把结果压栈
    
- `opt_send_without_block` 消耗栈顶的参数并调用 `puts`
    

**数据流向完全靠栈隐式传递，指令本身不带操作数地址**——这让字节码非常紧凑 。

你可以自己实验——用 Ruby 自带工具直接看编译产物 ：

```
RubyVM::InstructionSequence.compile("puts 2+2").disasm
```

📌 **工业应用**：这个能力在今天演变成了强大的工具链基础：

- **`RubyVM::InstructionSequence`**​ 让我们能反汇编任何 Ruby 代码，是理解性能瓶颈的第一抓手
    
- **SyntaxTree**​ 等现代 gem 直接基于指令序列做代码分析、格式化、模式匹配
    
- **MJIT/RJIT**​ 正是在指令序列的基础上，识别热点指令序列并将其 JIT 到机器码

## 2.4 编译块调用

块（block）是 Ruby 最具标志性的特性：`each { |x| ... }`、`map { |x| ... }` 中的 `{...}` 部分。

🎯 **我的洞见**：块调用的编译有一个**精妙的设计**——**块本身被编译成一个独立的指令序列（ISEQ）**，嵌在调用方的指令流中。

具体来说：

1. 调用方在调用 `each` 等方法时，YARV 会生成一条 `send` 类指令
    
2. 同时，块体内的代码被编译成**独立的 ISEQ**，作为常量池的一部分存储
    
3. 调用时，这个块的 ISEQ 作为"隐藏参数"传递给被调用的方法
    
4. 当方法内部执行 `yield` 时，YARV 通过 `invokeblock` 指令**找到调用方帧中的块 ISEQ 并执行**​
    

`invokeblock` 的工作机制很有意思：它会**沿着帧栈向上爬，直到找到一个方法帧，然后执行当初调用该方法时附带的块 ISEQ**，结果压回栈 。

💡 **为什么这个设计是第一性的？**

块的本质是"**附属于方法调用的一段可执行代码**"。把它编译成独立 ISEQ 有几个好处：

- **生命周期清晰**：块的 ISEQ 在方法调用时绑定，调用结束自然释放
    
- **闭包捕获明确**：块可以访问定义处的局部变量，这些变量通过"环境指针（env pointer）"链在帧之间传递（下一章会详述）
    
- **性能可控**：块的字节码只编译一次，可重复执行
    

⚠️ **工业现实**：块调用的编译复杂度，正是 Ruby 性能优化的重点战场。在 MJIT/RJIT 中，**块调用的内联（inlining）**​ 是关键优化手段——把热点块的指令直接内联到调用方，消除 `invokeblock` 的帧切换开销。

## 2.5 本地表（Local Table）

每个作用域（方法体、块体、类体）在编译时都会建立一个**本地表**，记录该作用域内的所有局部变量和参数的位置。

🎯 **我的洞见**：本地表的存在揭示了一个关键事实——**Ruby 的局部变量在编译期就确定了内存布局（栈偏移量）**。

```
def calculate(x, y)
  sum = x + y
  product = x * y
  sum + product
end
```

对应的本地表大致是：

```
0: x       (参数)
1: y       (参数)
2: sum     (局部变量)
3: product (局部变量)
```

编译后的指令通过偏移量访问：

```
0000 getlocal 0, 0    # 加载 x
0002 getlocal 1, 0    # 加载 y
0004 opt_plus         # x + y
0005 setlocal 2, 0    # sum = ...
...
```

`getlocal 0` 不是去查"名为 x 的变量"，而是直接去**栈帧的第 0 个槽位**取值 。**这种"编译期确定偏移、运行期直接寻址"的方式，是 YARV 快于 1.8 树遍历的核心原因之一**。

📌 **ISEQ 的完整结构**：一个指令序列除了字节码和本地表，还包含 ：

- **调用计数器**（供 JIT 判断热点）
    
- **JIT 入口点**
    
- **参数元数据**（必需参数、可选参数、rest、关键字、block 等）
    
- **常量池**
    
- **源码位置信息**（行号、列号，供调试和 TracePoint）
    
- **捕获表**（异常处理）
    

你可以用 `RubyVM::InstructionSequence` 直接观察本地表 ：

```
puts RubyVM::InstructionSequence.compile(<<~RUBY).disasm
  def foo(a, b=1, *c, d:, e: 2, **f, &g)
  end
RUBY
# 会显示完整的本地表和参数元数据
```

### 2.5.1 编译可选参数

可选参数（如 `def m(a, b=2)`）的编译策略是——**在方法入口插入"默认值检查"指令**。

编译后的逻辑大致是：

1. 如果调用方传了 `b`，使用传入值
    
2. 如果没传，执行默认表达式 `2`，并将结果存入本地表的 `b` 槽位
    

这通过在 ISEQ 的参数元数据里标记 `opts: 1`（1 个可选参数）来实现 。调用设置代码（method call setup code）负责确保栈与参数声明对齐 。

🎯 **我的洞见**：可选参数的默认值**不是编译期常量折叠**，而是**运行期每次都可能重新求值**。这意味着：

```
def m(b = Time.now)
  b
end
```

每次调用 `m()` 不带参数时，`Time.now` 都会被重新执行。这看似显然，但从编译视角看——**默认值表达式是作为 AST 子节点被编译进 ISEQ 的，它会在"参数未提供"的分支中被求值**。这是一个运行时分支，不是编译期替换。

### 2.5.2 编译关键字参数

Ruby 2.0 引入的关键字参数，在 YARV 层面有一个**非常巧妙的实现技巧**——**关键字参数被实现为一个隐藏的哈希参数**​ 。

看这段代码的编译产物 ：

```
def add_two(a:, b:)
  a + b
end
```

本地表会出现三个条目：

```
[2] ?    <- 隐藏的哈希参数！
[3] b
[4] a
```

那个神秘的 `[2] ?` 就是调用方传来的关键字哈希。编译出的指令会：

1. 用 `getlocal 2, 0` 取出这个哈希
    
2. 用 `dup` 复制
    
3. `putobject :a` 把键 `:a` 压栈
    
4. `opt_send_simple` 调用 `Hash#[]` 取出值
    
5. `setlocal 4, 0` 存入本地表的 `a` 槽位
    
6. 同理处理 `:b`
    
7. 如果调用方传了未声明的关键字（如 `c:`），抛出 `ArgumentError: unknown keyword: c`
    

🎯 **我的洞见（本节最核心的认知）**：

> **关键字参数在字节码层面 = 一个隐藏的哈希参数 + 一系列哈希取值指令 + 参数校验指令**。

这揭示了几件事：

1. **关键字参数不是"原生"的**——它们是建立在哈希之上的语法糖。这就是为什么早期 Ruby 性能测试中，关键字参数比位置参数慢
    
2. **`**kwrest` 参数**（收集未声明的关键字）在本地表中表现为 `kwrest: 0`，表明它在参数列表的索引 0 位置
    
3. **`checkkeyword` 指令**用于检查某个关键字是否在调用方传入的哈希中 ，返回布尔值压栈
    
4. 参数校验完全由编译器生成的指令序列负责，而不是由虚拟机的某条特殊指令负责——这体现了**"编译器做语义检查，虚拟机只做机械执行"的职责分离**
    

💡 **工业应用**：理解关键字参数的编译实现，对性能敏感场景有直接指导意义：

- 热点方法中，**位置参数比关键字参数快**（少了哈希分配和查找）
    
- 但关键字参数带来 API 可用性提升——这是典型的工程权衡
    
- 现代 Ruby 通过 `kwarg` 专用指令和优化过的哈希实现，不断缩小两者的性能差距

## 2.6 总结

本章我们从第一性原理梳理了 Ruby 编译器的演进与工作机制：

1. **Ruby 1.8 没有编译器**：解析出 AST 后直接递归遍历执行。树遍历解释器的固有缺陷——每次执行都要重新理解树结构——导致性能瓶颈 。
    
2. **Ruby 1.9/2.0 引入 YARV 编译器**：Koichi Sasada 引入了 Yet Another Ruby Virtual Machine，AST 被编译成 YARV 字节码后再解释执行。Ruby 刻意做到两点：编译器对用户透明（不暴露为独立工具）、不 JIT 到机器码（直到 2.6 的 MJIT 才改变） 。
    
3. **简单脚本的编译**：核心是 `iseq_compile_each` 函数，后序遍历 AST，对每个节点类型生成对应的栈式指令。栈式虚拟机靠栈隐式传递数据，字节码紧凑高效 。
    
4. **块调用的编译**：块被编译成独立的 ISEQ，作为隐藏参数传递给被调用方法；`yield` 时通过 `invokeblock` 指令沿帧栈找到块 ISEQ 并执行 。
    
5. **本地表**：每个作用域编译期就确定局部变量的栈偏移量，运行期直接寻址，这是 YARV 快于 1.8 的关键 。
    
6. **可选参数的编译**：在方法入口插入默认值检查分支，默认值表达式是运行期求值的 AST 子节点 。
    
7. **关键字参数的编译**：**被实现为一个隐藏的哈希参数**，加上一系列哈希取值和校验指令。这揭示了关键字参数"建立在哈希之上"的本质 。
    

🔑 **贯穿全章的核心洞见**：

> **编译的本质，是把"为语法忠实性优化的树形 AST"，重排成"为执行效率优化的线性字节码"。**
> 
> 这一转换带来了三重解耦：
> 
> - **编译期与运行期解耦**：编译做一次，执行做多次
>     
> - **语义与分发解耦**：编译器负责语义检查（如关键字校验），虚拟机只做机械的指令分发
>     
> - **代码与数据解耦**：ISEQ 是代码（指令），栈帧是数据（局部变量），两者通过本地表的偏移量关联
>     

⚠️ **给后续章节的铺垫**：

编译产生的 ISEQ，下一章就要进入 **YARV 的执行阶段**——虚拟机如何使用内部栈、如何管理调用栈帧、如何通过环境指针链实现闭包变量访问。届时你会看到：

- 本章讲的 `getlocal`/`setlocal` 指令，如何通过栈帧偏移量实际操作内存
    
- 块调用时，`invokeblock` 如何沿着环境指针 ladder 爬帧
    
- 本地表不只是"变量名→偏移"的映射，更是**实现 Ruby 动态变量访问（如 `binding.local_variable_get`）的基础**
    

另外值得注意的是：**MJIT/RJIT 正是基于本章讲的 ISEQ 结构做 JIT 优化的**​ 。理解 ISEQ 的完整结构（字节码、本地表、参数元数据、常量池、捕获表），是理解现代 Ruby 性能优化的钥匙。当你下次看到"Ruby 3.0 达到 3x 性能"这种说法时，要知道——**那颗种子，就是在 1.9 引入 YARV 编译器这一刻种下的**。
