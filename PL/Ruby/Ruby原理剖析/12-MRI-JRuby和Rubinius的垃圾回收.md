
# 第12章 读书笔记：MRI、JRuby、Rubinius 垃圾回收

> 💡 这一章回答的核心问题是：**当 Ruby 对象不再被使用时，谁来回收内存？不同 Ruby 实现给出了截然不同的答案。**
> 
> 从第一性原理看，垃圾回收解决的是三个根本问题：**哪些对象是活的？如何回收死对象的内存？如何让回收过程不拖垮程序性能？**​ MRI 选择"标记-清除"这条朴素路径，JRuby 直接借用 JVM 几十年积累的工业级收集器，Rubinius 则借鉴 Smalltalk-80 架构用"复制+分代"重新设计。三种答案，三种哲学，但都服务于同一个目标——让 Ruby 程序员不必手动管理内存。

📌 **时代注记（极重要）**：原书基于 Ruby 2.0 时代的 MRI——那个时候的 MRI 还是**纯粹的标记-清除收集器，没有分代、没有增量标记、没有压缩**。但今天的 MRI（Ruby 3.x）已经演变为 **RGenGC（受限分代 GC）+ 增量标记 + 延迟清除 + 压缩（GC.compact）**​ 的现代收集器 。本章的读书笔记将采取"双视角"：先用原书 Ruby 2.0 的视角讲清第一性原理，再指出现代 Ruby 的演进——这样你既能读懂原书，又能理解今天的 Ruby 源码。

---

## 12 垃圾回收：GC 解决三个问题

原书开宗明义：所有垃圾收集器都必须解决三个问题 ：

1. **如何识别垃圾对象？**——遍历对象图，从根对象（roots）出发，跟随引用找到所有活对象，剩下的就是垃圾
    
2. **如何回收内存？**——把死对象占用的内存归还给系统，供后续分配使用
    
3. **如何减少回收对程序的中断？**——GC 执行时是否必须暂停程序（Stop-The-World）？暂停多久？能否并发执行？
    

🎯 **我的洞见**：这三个问题对应了 GC 设计的三元权衡——**吞吐量（throughput）vs 暂停时间（pause time）vs 内存开销（memory overhead）**。没有任何一种 GC 算法能同时最优地解决这三个问题，所有收集器都是在三元组中做工程取舍：

- **MRI 的传统标记-清除**：牺牲暂停时间（全程 STW），换取简单性和内存效率
    
- **JVM 的分代+并发收集器**：牺牲实现复杂性，换取极短的暂停时间和高吞吐量
    
- **Rubinius 的复制+分代**：牺牲内存空间（需要 To-Space），换取压缩性和年轻对象的高回收率
    

理解这一点，你就能看懂为什么不同 Ruby 实现的 GC 行为如此不同——它们优化的是不同的目标函数。

## 12.2 MRI 中的垃圾回收：标记与清除

### 12.2.1 空闲列表（Free List）

MRI 管理 Ruby 对象的核心数据结构是 **RVALUE**——每个 Ruby 对象在堆上都由一个 RVALUE 结构表示（约 40 字节） 。这些 RVALUE 结构组织在"页（page）"中，每页约 16KB，可容纳约 408 个 RVALUE 槽位 。

**空闲列表**是一个链表，链接所有未被使用的 RVALUE 槽位。分配新对象时：

1. 检查当前堆的空闲列表是否有空槽
    
2. 如果有，从空闲列表取下一块，初始化为 new object
    
3. 如果没有，触发 GC 或分配新页
    

🎯 **我的洞见**：空闲列表的本质是**用链表管理"已分配但可回收"的内存槽**。这是最经典的分配器设计——简单、O(1) 分配、无外部碎片（因为槽位大小固定）。但它有一个隐藏代价：**无法分配超过 RVALUE 大小的对象**（40 字节）。这就是为什么 MRI 对大对象（如长字符串、大数组）使用特殊的内存分配策略——它们不放在 RVALUE 槽位里，而是 RVALUE 结构里只存一个指针，指向堆外分配的实际数据 。

### 12.2.2 标记（Marking）

标记阶段从**根对象（roots）**开始遍历对象图：

- **根对象**包括：全局变量、当前调用栈上的局部变量、寄存器中的对象引用等
    
- **遍历算法**：从根出发，递归跟随对象间的引用指针，标记所有可达对象
    
- **标记表示**：被访问到的对象标记为"活"，未被访问的为"垃圾"
    

原书 Figure 12-4 清晰地展示了这个过程——从左边的灰色根对象出发，箭头代表引用，MRI 沿着箭头遍历整个对象图，标记每个遇到的对象 。

### 12.2.3 MRI 如何标记存活对象

这是 MRI GC 最精妙的设计之一——**位图标记（Bitmap Marking）**​ 。

**Ruby 1.8 及更早版本**：标记位直接存在每个 RVALUE 结构内部（用 `FL_MARK` 标志位）。

**问题**：当 Ruby 进程 fork 出子进程时，Unix 的 **Copy-on-Write（COW）**​ 机制允许父子进程共享相同的内存页。但一旦 GC 在子进程中运行，它会修改几乎所有 RVALUE 的 `FL_MARK` 位——这导致 COW 失效，操作系统不得不复制整个内存页，fork 节省内存的优势荡然无存 。

**Ruby 2.0 的解决方案**：引入**位图标记**——把标记位从 RVALUE 结构中移出，存到一个独立的"空闲位图（free bitmap）"数据结构中 。

```
传统方式（Ruby 1.8）：
[RVALUE][RVALUE][RVALUE]...  ← 标记位在每个 RVALUE 内部
GC 运行时修改所有 RVALUE → COW 失效

位图标记（Ruby 2.0+）：
[RVALUE][RVALUE][RVALUE]...  ← 对象数据
[Bitmap ][Bitmap ][Bitmap ]...  ← 标记位集中存储
GC 运行时只修改 Bitmap → 大部分 RVALUE 内存页保持不变 → COW 依然有效
```

🎯 **我的洞见（本节最核心的认知）**：

> **位图标记是"为 Unix fork + COW 优化"的典范设计。**
> 
> 它解决了一个极其实际的工程问题：Rails 应用经常用 `fork` 预加载应用代码，然后让子进程处理请求。如果 GC 破坏 COW，每个子进程都会复制整个内存堆，fork 的内存优势完全丧失。
> 
> 通过把标记位集中存储，MRI 最大化了"在进程间共享相同值的内存页数量"——只有 Bitmap 页会在 GC 时被修改，RVALUE 页保持不变，COW 依然有效 。

这是 MRI GC 演进史上最重要的一次优化——它不仅是一个算法改进，更是对 Unix 进程模型的深度适配。

### 12.2.4 清除（Sweeping）

标记完成后，堆中包含标记（活）和未标记（垃圾）两种对象。清除阶段 ：

1. 遍历所有堆页的每个 RVALUE 槽位
    
2. 如果对象被标记 → 取消标记（为下次 GC 重置）
    
3. 如果对象未标记 → 将其 RVALUE 结构重新链接到空闲列表
    

**关键点**：清除阶段**不实际复制对象**，只是调整 RVALUE 结构中的 `next` 指针，把死对象的槽位串入空闲链表 。这就是为什么清除通常很快。

### 12.2.5 延迟清除（Lazy Sweeping）

**Ruby 1.9.3 引入的重要优化**​ 。

传统清除：标记完成后，GC 暂停程序，一次性清除所有死对象，然后才恢复程序执行。这会导致较长的 STW 暂停。

延迟清除的核心思想 ：

> **不一次性清除所有垃圾，而是"按需清除"——只清除足够让程序继续分配新对象的少量垃圾，然后立即恢复程序执行。**

具体算法 ：

- 当程序需要分配新对象但空闲列表为空时，GC 执行一个"清除步（sweep step）"，清除一个堆页中的死对象（约 2048 个槽位）
    
- 清除完这个堆页后，程序继续运行
    
- 下次再需要内存时，重复上述过程
    
- 这样把总的清除工作量**分摊（amortize）**到多次小的 GC 暂停中
    

🎯 **我的洞见**：延迟清除是一个典型的"时间换时间"优化——

- **不减少总的清除工作量**：该清除的死对象还是要清除
    
- **但把工作量分摊到多个短时间暂停中**：每次只清除一个堆页，程序暂停时间从"O(总堆大小)"降到"O(单个堆页)"
    
- **代价**：清除的总时间可能略增（因为需要多次启动/停止清除过程），但程序的响应性显著提升
    

原书 Experiment 12-1 通过 GC 分析报告验证了这一行为——你可以看到 MRI 执行"延迟清除"而非"全回收" 。

### 12.2.6 标记-清除的缺点

原书总结了传统标记-清除的三大缺点 ：

1. **STW 暂停**：标记阶段必须完全停止程序执行（"Stop-The-World"）。在大型应用中，这可能造成几十到几百毫秒的卡顿
    
2. **内存碎片**：清除后堆中出现大量不连续的空闲槽位。虽然 MRI 用固定大小的 RVALUE 槽位缓解了内部碎片，但当对象被提升到老年代或堆页的存活率很高时，碎片化依然严重
    
3. **全堆扫描**：每次 GC 都要遍历整个堆——无论对象是新是旧。这违反了"弱代假说"（见 12.5.1）
    

⚠ **工业现实**：在 Ruby 1.8 时代，这些问题导致了严重的生产事故——

- Rails 应用处理请求时突发 GC 停顿，用户看到"卡一下"
    
- 长时间运行后堆碎片化，内存占用只增不减
    
- 大堆场景下 GC 时间线性增长
    

这就是为什么 Ruby 2.1 引入了 RGenGC（分代 GC），2.2 引入了增量标记，2.7 引入了压缩（GC.compact）——逐步解决这些问题 。

### 12.2.7 观察 MRI 执行延迟清除

原书 Experiment 12-1 引导我们实际观察 MRI 的延迟清除行为 ：

```
require 'gc_tracer'  # 或设置环境

# 强制触发 GC 并观察日志
GC.start
```

通过分析 GC 分析报告（GC.stat 和 GC::Profiler），你可以看到：

- **延迟清除的特征**：GC 报告中出现多个短时间的清除事件，而非一次长时间的清除
    
- **清除步长**：每次清除约 2048 个槽位（Ruby 2.0+ 的默认值）
    

🎯 **我的洞见**：这个实验的价值在于——**让你"看见"GC 的内部行为**。当你理解了延迟清除的机制，就能解释为什么：

- 内存分配在 GC 后瞬间变快（空闲列表刚刚被填充）
    
- 随着程序继续运行，分配逐渐变慢（空闲列表耗尽，每次分配触发一个小清除步）
    
- 这种"锯齿状"的性能特征，正是延迟清除的典型表现
    

### 12.2.8 观察 MRI 执行全回收

通过 `GC.start`（或 `GC.start(full_mark: true)`），你可以强制触发一次完整的全堆回收 ：

```
GC.start(full_mark: true)
```

全回收的特征：

- 标记阶段遍历整个对象图（包括老年代）
    
- 清除阶段一次性清除所有死对象
    
- STW 暂停时间较长（与堆大小线性相关）
    
- 但回收后堆最紧凑，空闲列表最充足
    

### 12.2.9 解读 GC 分析报告

Ruby 提供了 `GC.stat` 和 `GC::Profiler` 来观察 GC 行为 ：

```
GC::Profiler.enable
# ... 运行你的程序 ...
report = GC::Profiler.report
GC::Profiler.disable

# 或者用 GC.stat 获取实时统计
GC.stat
# => {
#   :count=>123,              # GC 触发次数
#   :heap_used=>75,           # 使用的堆页数
#   :heap_length=>75,         # 堆页总数
#   :heap_increment=>0,       # 上次 GC 增加的堆页数
#   :heap_live_slots=>29633,  # 存活对象数
#   :heap_free_slots=>419,    # 空闲槽位数
#   :heap_final_slots=>0,     # 待最终化的槽位
#   :heap_marked_slots=>29633,# 标记的槽位
#   :total_allocated_object=>1234567,  # 累计分配对象数
#   :total_freed_object=>1204934,      # 累计释放对象数
#   ...
# }
```

原书给出了 GC 报告的关键指标解读 ：

|指标|含义|
|---|---|
|**Invoke time**​|GC 启动的时间点（从程序开始执行算起）|
|**Use size**​|GC 结束后，存活对象占用的堆内存|
|**Total size**​|GC 结束后，存活对象 + 空闲列表占用的总堆内存|
|**Total object**​|存活对象 + 空闲列表中的所有对象个数|
|**GC Time**​|本次 GC 的耗时|

🎯 **我的洞见（本节最核心的认知）**：

> **GC 报告揭示了 Ruby 内存使用的"指数增长规律"**​ 。
> 
> 随着存活对象增加，Ruby 会倍增 Total size（因为 GC 是在空闲列表满时触发的）。这导致：
> 
> - 下次 GC 的启动间隔呈指数增长
>     
> - Invoke time、Use size、Total size、Total object、GC Time 都成倍增长
>     
> - GC 时间随堆大小线性增长
>     
> 
> 这就是为什么在内存压力大的应用中，你会观察到 GC 时间逐渐变长——这不是 bug，是标记-清除算法的数学性质。

💡 **工业应用**：

```
# 在 Rails 应用中监控 GC 行为
GC::Profiler.enable

# 在请求处理前后观察
before_action do
  @gc_count_before = GC.stat[:count]
end

after_action do
  @gc_count_after = GC.stat[:count]
  if @gc_count_after > @gc_count_before
    Rails.logger.warn "GC triggered during request: #{
      GC::Profiler.report
    }"
  end
end
```

通过监控 GC 触发频率和耗时，你可以识别内存热点，优化对象分配模式。

## 12.3 JRuby 和 Rubinius 中的垃圾回收

原书指出，JRuby 和 Rubinius 都不使用 MRI 的"空闲列表 + 标记-清除"策略，而是采用了三种更先进的算法 ：

1. **复制垃圾回收（Copying GC）**
    
2. **分代垃圾回收（Generational GC）**
    
3. **并发垃圾回收（Concurrent GC）**
    

这三种算法往往是组合使用的——JRuby 通过 JVM 获得全部三种能力，Rubinius 则自行实现了分代+复制的组合。

🎯 **我的洞见**：为什么 JRuby 和 Rubinius 都选择了这三条路径？

- **MRI 的标记-清除是"非移动（non-moving）"策略**——对象在内存中的位置固定不变。这简化了与 C 扩展的交互，但导致了碎片化
    
- **复制 GC 是"移动（moving）"策略**——对象在内存中会被移动和紧凑化。这消除了碎片，但需要更新所有指向该对象的引用
    
- **JRuby 没有 C 扩展兼容性负担**（Java 生态的对象引用由 JVM 统一管理），Rubinius 则从一开始就设计为精确 GC（precise GC）——两者都能安全地移动对象
    

这就是为什么 MRI 长期停留在标记-清除，而 JRuby/Rubinius 能直接采用更先进的算法。

## 12.4 复制垃圾回收

### 12.4.1 碰撞分配（Bump Allocation）

复制 GC 的基础是**碰撞分配**——在一个连续的大内存区块中分配对象 ：

```
分配指针
   ↓
[obj1][obj2][obj3][............ 空闲空间 ............]
                    ↑
                分配指针移动到这里
```

每次分配只需：

1. 检查分配指针 + 对象大小是否超出堆尾
    
2. 如果没有，在分配指针处写入对象
    
3. 分配指针 += 对象大小
    
4. 返回新对象的地址
    

🎯 **我的洞见**：碰撞分配是**最简单、最快的分配策略**——O(1) 时间，无链表遍历，无空闲列表维护。更重要的是，它**具有极佳的内存局部性（locality）**——连续分配的对象在内存中也连续，CPU 缓存命中率高 。

相比之下，MRI 的空闲列表分配需要遍历链表找到合适大小的槽位，且分配的对象散布在堆的各处，缓存命中率低。

### 12.4.2 半空间算法（Semi-Space Algorithm）

当初始堆填满并触发 GC 时，复制 GC 的真正威力显现 。

**半空间算法**使用两个堆：

- **From-Space**：当前活动的堆，新对象通过碰撞分配在这里创建
    
- **To-Space**：初始为空的堆
    

GC 过程 ：

1. 从根对象出发遍历对象图，识别所有存活对象
    
2. 将所有存活对象**从 From-Space 复制到 To-Space**，紧凑排列
    
3. 复制完成后，**交换 From-Space 和 To-Space**​ 的角色
    
4. 新的 From-Space 成为活动堆，To-Space 等待下次 GC
    

```
GC 前：
From-Space:  [A][B][dead][C][dead][D][dead]
To-Space:    [..............................]

GC 中（复制存活对象）：
From-Space:  [A][B][dead][C][dead][D][dead]
To-Space:    [A][B][C][D]..................

GC 后（交换角色）：
From-Space:  [A][B][C][D]..................  ← 新对象从这里分配
To-Space:    [..............................]
```

🎯 **我的洞见（本节最核心的认知）**：

> **半空间算法用"空间换时间"——它需要 2 倍的内存（两个堆），但换来了三个巨大优势**：
> 
> 1. **分配极快**：碰撞分配，O(1)
>     
> 2. **自动压缩**：存活对象被紧凑排列，无碎片
>     
> 3. **清除极快**：死对象不需要单独清除——它们留在旧 From-Space 里，随空间交换被整体废弃
>     
> 
> 代价是：
> 
> - 内存开销：实际需要 2 倍堆空间
>     
> - 实现复杂：移动对象时必须更新所有指向它的引用（使用"转发指针 forwarding pointer"技术）
>     

Rubinius 的年轻代就使用了 **Baker 复制收集器**——半空间算法的经典实现 。

### 12.4.3 伊甸堆（Eden Heap）

实际上，Rubinius 和 JVM 都使用了半空间算法的变体，引入了第三个堆区域——**伊甸堆（Eden Heap）**​ ：

```
┌─────────────────────────────────────────────┐
│  Eden Heap (伊甸堆)                          │
│  ┌───────────────────────────────────────┐  │
│  │ 新对象通过碰撞分配在这里创建              │  │
│  └───────────────────────────────────────┘  │
├─────────────────────────────────────────────┤
│  From-Space (源空间)                         │
├─────────────────────────────────────────────┤
│  To-Space (目标空间)                         │
└─────────────────────────────────────────────┘
```

**工作流程**：

1. 新对象在 Eden 中通过碰撞分配创建
    
2. 当 Eden 填满时，触发 Minor GC
    
3. Minor GC 将 Eden 中存活的对象复制到 From-Space（或晋升到老年代）
    
4. 多次 Minor GC 后，From-Space 中的存活对象被复制到 To-Space（半空间交换）
    
5. 多次生存的对象被晋升到老年代
    

🎯 **我的洞见**：伊甸堆的引入是基于"弱代假说"的工程优化——大多数对象在分配后极短时间内死亡，根本熬不过第一次 Minor GC。把新对象集中放在 Eden 中，可以让 Minor GC 极其高效地回收它们（大部分直接废弃，只有少数需要复制）。

## 12.5 分代垃圾回收

### 12.5.1 弱代假说（Weak Generational Hypothesis）

分代 GC 的理论基础是计算机科学中观察到的经验规律 ：

> **大多数对象在分配后极短时间内就变成垃圾。**

统计数据显示：

- 约 **85% 的对象在分配后几秒内变为不可达**​
    
- 在 Rails 请求处理中，每次请求创建成千上万个对象（字符串、哈希、数组包装器等），但 **99% 在响应发送的那一刻就毫无用处**​
    
- 只有少数对象（会话数据、缓存、类定义等）能长期存活
    

🎯 **我的洞见**：弱代假说是整个分代 GC 的理论基石。它告诉我们——**与其每次都扫描整个堆，不如把"年轻对象"和"老年对象"分开处理**：

- **年轻代**：频繁 GC，因为这里垃圾最多
    
- **老年代**：很少 GC，因为这里的对象大多长期存活
    

这种"抓大放小"的策略，让 GC 的整体效率大幅提升。

### 12.5.2 为新生代使用半空间算法

基于弱代假说，新生代（Young Generation）使用半空间算法极其合适 ：

- 新生代的对象大多很快死亡
    
- 复制收集器在 Minor GC 时，只需复制少数存活对象到 Survivor 空间或老年代
    
- **典型 Minor GC 可回收约 80% 的新生代内存**​
    

🎯 **我的洞见**：新生代 + 半空间算法是"天作之合"——

- 半空间算法的缺点是"复制存活对象的开销"
    
- 但在新生代，存活对象极少（<20%），复制开销极小
    
- 同时获得了碰撞分配的速度和自动压缩的好处
    

这就是为什么所有现代 GC（JVM、Rubinius、现代 MRI 的 RGenGC）都在新生代使用复制算法。

### 12.5.3 晋升对象（Promoting Objects）

对象在新生代中每存活一次 Minor GC，年龄（age）就加 1。当年龄达到阈值时，对象被**晋升（promote）**到老年代 ：

- **Rubinius**：对象在新生代存活 **7 次**​ GC 后晋升到老年代
    
- **MRI RGenGC**：对象存活 **3 次**​ GC 后晋升（RVALUE_OLD_AGE = 3）
    
- **JVM**：晋升阈值动态计算，取决于 Survivor 空间的大小和对象年龄分布
    

🎯 **我的洞见**：晋升阈值的设定是一个精妙的工程权衡——

- **阈值太低**：对象过早晋升到老年代，老年代迅速填满，导致频繁的 Major GC
    
- **阈值太高**：对象在新生代来回复制，浪费 CPU
    
- **Rubinius 选择 7 次，MRI 选择 3 次**——反映了不同的性能模型和调优哲学
    

Rubinius 的 Evan Phoenix 曾说："The trick has been tuning how long an object exists before it is promoted to the old object space. We've only tuned it a little." ——调优晋升阈值是 GC 工程中最微妙的平衡点。

### 12.5.4 成熟代对象垃圾回收

老年代使用什么算法？三种实现的答案不同：

|实现|老年代算法|说明|
|---|---|---|
|**MRI RGenGC**​|标记-清除（改进版）|受限分代：只有受写屏障保护的（WB-protected）对象才能晋升到老年代|
|**JVM**​|多种选择（CMS、G1、ZGC、Shenandoah）|取决于选择的收集器|
|**Rubinius**​|标记-清除|与年轻代的复制收集器配对|

**分代 GC 的核心难题：跨代引用**​ 。

如果老年代对象引用了新生代对象，那么在 Minor GC 时，如果不扫描老年代，就会漏标这个新生代对象，错误地将其回收。

**解决方案：写屏障（Write Barrier）+ 记忆集（Remembered Set）**​ ：

```
当程序执行 `old_obj.field = young_obj` 时：
1. 写屏障检测到：源对象 old_obj 是老年代，目标 young_obj 是新生代
2. 把 old_obj 加入 Remembered Set
3. 下次 Minor GC 时，除了扫描根，还要扫描 Remembered Set 中的所有老年代对象
```

🎯 **我的洞见（本节最核心的认知）**：

> **写屏障是分代 GC 能够正确工作的关键技术。**
> 
> Ruby 2.1 引入 RGenGC 时，最大的挑战就是写屏障 ：
> 
> - Ruby 对象分为两类：**受写屏障保护的（WB-protected）**​ 和 **不受保护的（WB-unprotected）**
>     
> - 只有 WB-protected 对象才能晋升到老年代
>     
> - WB-unprotected 对象（如 Proc、Ruby::Env）即使存活也无法晋升，但如果被老年代引用，会被加入 Remembered Set
>     
> - 这就是为什么 RGenGC 被称为"受限（Restricted）分代 GC"——它通过限制晋升对象的范围，简化了写屏障的实现
>     
> 
> 在 C 扩展中实现写屏障极其困难，这也是 RGenGC 花了 3 年多才完成的原因 。

## 12.6 并发垃圾回收

### 12.6.1 当对象图改变时进行标记

传统的标记-清除是 **Stop-The-World（STW）**​ 的——标记期间程序完全暂停。但程序越大，标记时间越长，用户体验越差。

**并发标记**的目标：让 GC 标记与程序执行同时进行。但这带来了一个根本性问题 ：

> **如果在标记过程中，程序修改了对象图（比如新建对象、删除引用、添加引用），怎么办？**

考虑这种情况：

```
1. GC 标记线程：标记了对象 A（A 是灰色的）
2. 程序线程：执行 `A.next = new_object`
3. GC 标记线程：完成了对 A 的标记，将 A 变黑
4. 问题：new_object 从未被标记，但它被 A 引用——它会被错误回收！
```

### 12.6.2 三色标记（Tricolor Marking）

解决并发标记问题的经典算法是**三色标记**​ ：

- **白色（White）**：尚未被访问的对象（潜在垃圾）
    
- **灰色（Gray）**：已被标记，但其引用的对象还未完全扫描
    
- **黑色（Black）**：已被标记，且其所有引用都已扫描
    

**算法流程**：

```
初始：所有对象为白色
从根开始：
1. 将根直接引用的对象标记为灰色
2. 从灰色集合中取出一个对象：
   - 将它引用的所有白色对象标记为灰色
   - 将该对象标记为黑色
3. 重复步骤 2，直到灰色集合为空
4. 剩余白色对象 = 垃圾
```

**并发场景下的正确性保证**：

使用**写屏障**监控对象图的改变 ：

- 当黑色对象引用白色对象时（`black_obj.field = white_obj`），写屏障将白色对象重新标记为灰色
    
- 这保证了"黑色对象不会指向未被标记的白色对象"这一不变式
    
- 标记完成时，所有从灰色可达的白色对象都会被正确标记
    

🎯 **我的洞见**：三色标记 + 写屏障，是并发 GC 的理论基石。Ruby 2.2 引入的**增量标记（Incremental Marking）**正是基于这一原理 ——把标记过程分成多个小步，与程序执行交替进行，每次只标记一定数量的槽位，从而显著减少 STW 暂停。

### 12.6.3 JVM 中的三种垃圾收集器

JVM 提供了多种 GC 实现，适应不同的应用场景 ：

|收集器|特点|适用场景|
|---|---|---|
|**Serial（串行）**​|单线程 STW|小型应用、客户端|
|**Parallel（并行）**​|多线程 STW，年轻代并行回收|吞吐优先的批处理|
|**Concurrent Mark-Sweep（CMS）**​|年轻代 STW，老年代并发|低延迟服务|
|**G1（Garbage-First）**​|将堆划分为区域，增量并发回收|大堆、可预测暂停|
|**ZGC**​|亚毫秒级暂停，全并发|超大堆、实时系统|
|**Shenandoah**​|极低暂停，并发压缩|高吞吐、低延迟|

JRuby 演讲中明确指出 OpenJDK 提供的收集器 ：

- **Parallel Collector**：多线程 STW，尽快完成 GC
    
- **Concurrent Collector**：年轻代 STW，老年代并发
    
- **G1**：年轻代和老年代都并发
    
- **Serial**：单线程 STW，最大吞吐量
    

🎯 **我的洞见（本节最核心的认知）**：

> **JRuby 的最大优势之一——"One GC to rule them all"**​ 。
> 
> 在 JRuby 中，**所有对象（Ruby 对象、Java 对象、C 扩展、库）都表达为 JVM 对象，共享同一个 GC**​ 。这意味着：
> 
> - 没有"Ruby 对象用 Ruby GC 管理，Java 对象用 JVM GC 管理"的分裂
>     
> - 没有内存模型的不一致
>     
> - 可以利用 JVM 几十年来积累的 GC 研究成果
>     
> 
> Charles Nutter（JRuby 核心开发者）在 RubyConf 2012 上说："these really are the best gc's in the world... it's all there and available for free if you run on top of JRuby" ——JVM 的 GC 是过去 10 年 GC 研究 90% 的成果承载者，而 JRuby 用户可以免费获得。

这就是为什么 JRuby 在长时间运行的服务端应用中表现出色——**ZGC 可以提供亚毫秒级的 GC 暂停，G1 可以在 TB 级堆上稳定运行**​ 。

### 12.6.4 触发主收集（Major Collection）

Major GC（Full GC）的触发条件 ：

- 老年代对象数超过阈值（`old_objects_limit`）
    
- 不受写屏障保护的对象数超过阈值
    
- malloc 内存压力达到阈值
    
- 显式调用 `GC.start(full_mark: true)`
    

🎯 **我的洞见**：Major GC 是"昂贵的操作"——它需要扫描整个堆（包括老年代），STW 暂停时间长。现代 GC 通过各种技术避免频繁 Major GC：

- **增量标记**：把标记过程分散到多个小步
    
- **并发标记**：标记与程序执行同时进行
    
- **并发清除**：清除与程序执行同时进行
    
- **记忆集**：Minor GC 时只扫描 Remembered Set，而非整个老年代
    

JRuby 的 Experiment 12-2 演示了如何使用 `-J-verbose:gc` 观察 JVM 的 GC 行为 。

## 12.8 总结

本章我们从第一性原理梳理了 Ruby 三种实现的垃圾回收机制：

### 1. MRI 的演进之路

|版本|GC 算法|关键特性|
|---|---|---|
|**Ruby 1.8**​|简单标记-清除|全程 STW，标记位在 RVALUE 内部|
|**Ruby 1.9.3**​|标记-清除 + 延迟清除|清除工作分摊到多次小暂停|
|**Ruby 2.0**​|位图标记|标记位移到独立 Bitmap，优化 COW|
|**Ruby 2.1**​|RGenGC（受限分代）|引入年轻/老年代，写屏障，Minor/Major GC|
|**Ruby 2.2**​|RGenGC + 增量标记|标记过程分步进行，减少 STW|
|**Ruby 2.7+**​|RGenGC + 增量标记 + 压缩|`GC.compact` 消除碎片|

### 2. 三种 GC 算法的本质区别

|算法|核心思想|代表实现|
|---|---|---|
|**标记-清除**​|标记活对象，清除死对象，不移动对象|MRI（老年代）、Rubinius（老年代）|
|**复制收集**​|把存活对象复制到新空间，自动压缩|Rubinius（年轻代 Baker 收集器）、JVM（年轻代）|
|**分代收集**​|基于弱代假说，年轻代频繁 GC，老年代很少 GC|RGenGC、JVM、Rubinius|
|**并发收集**​|GC 与程序并发执行，三色标记 + 写屏障|JVM 的 CMS/G1/ZGC/Shenandoah|

### 3. 三种 Ruby 实现的 GC 对比

|维度|MRI|JRuby|Rubinius|
|---|---|---|---|
|**底层机制**​|自研 C 代码|JVM 的 GC|自研 C++ 代码|
|**年轻代**​|标记-清除（RGenGC）|复制收集（半空间）|Baker 复制收集器|
|**老年代**​|标记-清除|标记-清除（CMS）或并发收集（G1/ZGC）|标记-清除|
|**分代**​|RGenGC（Ruby 2.1+）|是|是|
|**并发**​|增量标记（Ruby 2.2+）|多种并发收集器|否（STW）|
|**压缩**​|GC.compact（Ruby 2.7+）|JVM 自动压缩（G1/ZGC/Shenandoah）|年轻代自动压缩|
|**写屏障**​|是（RGenGC 受限）|JVM 自动处理|是|
|**C 扩展影响**​|大（C 扩展绕过写屏障）|无（Java 生态统一）|小（精确 GC）|

🔑 **贯穿全章的核心洞见**：

> **垃圾回收的本质，是"在吞吐量、暂停时间、内存开销"这个三元组中做工程权衡。**
> 
> - **MRI 的传统路径**：用简单的标记-清除，逐步演进到 RGenGC + 增量标记 + 压缩。每一步都是"在不破坏 C 扩展兼容性的前提下"的小步改进。这是"兼容性优先"的哲学。
>     
> - **JRuby 的路径**：直接借用 JVM 几十年的 GC 研究成果，免费获得分代、并发、压缩等全部现代特性。这是"站在巨人肩膀上"的哲学——代价是放弃 C 扩展生态。
>     
> - **Rubinius 的路径**：借鉴 Smalltalk-80 架构，自研年轻代复制 + 老年代标记-清除的分代 GC。这是"精确 GC + 对象移动"的哲学——代价是实现复杂，但获得了压缩性和缓存友好性。
>     
> 
> 三条路径，一个目标——让 Ruby 程序员不必手动管理内存。但每种路径都反映了不同的工程价值观和约束条件。

⚠ **给全书总结的升华**：

通过前 12 章的探索，我们从 Ruby 源码的字符开始，一路走到了 GC 的内存回收——完整地走过了 Ruby 内部实现的全部旅程：

```
字符 → 词条 → AST → YARV 字节码 → 执行 → 对象与类 → 
方法查找 → 哈希表 → 闭包 → 元编程 → JRuby/JVM → Rubinius → GC
```

**Ruby 这门语言的美学，在底层实现中得到了完美的呼应**：

- **词法分析器**：手写的、有状态的——呼应 Ruby 语法的上下文敏感性
    
- **YARV 虚拟机**：双栈架构——呼应 Ruby 的"表达式 + 调用 + 作用域"三维语义
    
- **对象模型**：klass 指针 + ivptr——呼应"行为/状态分离"的第一性原理
    
- **方法查找**：扁平化祖先链 + 双层缓存——呼应 Ruby 动态性的性能需求
    
- **散列表**：开放寻址 + 紧凑数组——呼应 Ruby 内部"一切皆散列表"的现实
    
- **闭包**：rb_block_t + rb_env_t——呼应 1975 年 Sussman/Steele 的闭包理论
    
- **元编程**：单例类 + 词法作用域 + refinement——呼应"一切皆对象"的彻底一致性
    
- **GC**：标记-清除 → 分代 → 并发 → 压缩——呼应 Ruby 对象生命周期的管理需求
    

**Ruby 不仅是"程序员快乐"的语言，更是"实现者优雅"的语言**。Matz 的设计哲学贯穿始终——"Ruby 优化了程序员的快乐"，而这种快乐，从最底层的 GC 位图标记，到最高层的 `instance_eval` 混合作用域，都被精心地设计和实现。

📌 **工业实践建议**：

1. **监控 GC 行为**：用 `GC::Profiler` 和 `GC.stat` 在生产环境监控 GC 频率和耗时
    
2. **理解 GC 触发条件**：避免频繁创建短命大对象，减少 Minor GC 压力
    
3. **JRuby 应用调优**：用 `-J-XX:+UseG1GC` 或 `-J-XX:+UseZGC` 选择适合的收集器，用 `-J-Xlog:gc*` 监控 GC 行为
    
4. **MRI 应用调优**：Ruby 2.7+ 可使用 `GC.compact` 主动压缩堆，减少碎片
    
5. **C 扩展注意**：C 扩展中的裸指针会阻碍对象移动（pinning），在压缩 GC 中需要特别处理
    
6. **写屏障意识**：在 C 扩展中修改对象引用时，要注意 RGenGC 的写屏障要求
    
7. **内存泄露排查**：用 `ObjectSpace` 统计对象数量，识别未释放的对象引用
