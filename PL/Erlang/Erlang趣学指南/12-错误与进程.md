
# 第十二章「错误与进程」读书笔记：当崩溃跨过进程边界

第十一章你学到了如何把"玩具进程"升级为"生产级进程"——状态封装、协议抽象、超时控制、邮箱管理。但你一定注意到一个尴尬：**如果进程 A 依赖进程 B，B 崩溃了，A 怎么知道？A 应该跟着死还是继续活？如果 A 要继续活，它怎么知道 B 死了并决定要不要重启 B？**

第七章讲的"let it crash"在单进程维度是清晰的——进程崩溃，监督树重启。但监督树还没教，而且**崩溃如何跨进程传播**这个底层机制完全没展开。

第十二章"Errors and Processes"要解决的根本问题是——

> **当一个进程崩溃时，整个系统如何"感知"到这个崩溃，并作出正确的响应？**

Fred 本章围绕三个核心机制展开：**Links（链接）→ Trapping Exits（捕获退出信号）→ Monitors（监视）**。我会按内在逻辑串，但主线始终是——**本章是"let it crash"哲学在多进程维度的落地，是第十七章监督树的底层支点**。

---

## 💀 小节一：Links —— "自杀协定"是可靠的默认

### 链接的本质

Fred 开宗明义：link 是两个进程之间的一种特殊关系。一旦建立，如果其中一方因 `throw`/`error`/`exit`（非正常原因）死亡，**另一方也会死**。

建立链接：

```
link(Pid).           %% 在当前进程与 Pid 之间建立双向链接
unlink(Pid).         %% 移除链接
spawn_link(Fun).     %% 原子性：创建进程 + 建立链接
```

Fred 用 `myproc()` 演示——`myproc` 睡 5 秒后调用 `exit(reason)` 自杀。实验结果：

```
1> spawn(fun linkmon:myproc/0).           %% 没链接
<0.52.0>                                 %% 5 秒后 shell 安然无恙

2> link(spawn(fun linkmon:myproc/0)).     %% 建立了链接
true
** exception error: reason                %% 5 秒后 shell 跟着崩了
```

📌 **洞见一："自杀协定"是最安全的默认**

为什么 Erlang 选择"链接进程一起死"作为默认行为？Cosmiclearn 的分析一针见血：

> **"这听起来很残酷，但它是最安全的默认：如果你依赖的组件没了，你大概也应该消失，以避免不一致的状态。"**​

想象一个场景：进程 A 负责处理用户请求，它依赖进程 B 提供数据库连接。如果 B 崩溃了：

- **选项一：A 继续活着**——但 A 现在拿着一个死的 B 的 Pid，每次请求都会失败/超时/永久阻塞
- **选项二：A 跟着 B 一起死**——整组进程死亡，由监督者统一重启整组
    
Erlang 选择**选项二**。理由深刻：

1. **状态一致性**：A 可能持有部分状态（"已扣款但未发货"），让它继续活下去会积累更多不一致
2. **故障隔离**：让 A 死，故障就被限制在 A+B 这组内，不会扩散到不相关的进程
3. **重启整组**：监督者重启时，A 和 B 都以干净的初始状态重新建立——这比"修补 A 的状态"可靠得多
    
> 💡 **这就是"let it crash"在多进程维度的表达**：不是"防止 B 崩溃"，而是"B 崩溃时，让依赖 B 的一切都死，然后整体重启"。

### exit 信号的传播机制

当进程 A 死亡时，BEAM 内部发生了什么？ 给出了精确的生命周期：

```
1. 终止：进程 A 死
2. 信号生成：VM 查看 A 的链接集（link set，存储在 PCB 里）
3. 传播：VM 向链接集中每个进程发送 exit 信号 {'EXIT', A, Reason}
4. 反应：接收进程检查 Reason：
   - normal → 忽略（优雅退出）
   - 其他 → 以相同 Reason 立即崩溃
   - kill → 不可捕获的硬杀
```

Fred 用 `chain/1` 函数展示了连锁崩溃：

```
chain(0) ->
    receive _ -> ok
    after 2000 -> exit("chain dies here")
    end;
chain(N) when N > 0 ->
    spawn_link(fun() -> chain(N-1) end),
    receive _ -> ok
    after 2000 -> exit("chain dies here")
    end.
```

如果我们在 shell 里 `spawn_link(fun() -> chain(3) end)`，会形成链：`shell <-> [3] <-> [2] <-> [1] <-> [0]`。

2 秒后 `[0]` 因超时调用 `exit("chain dies here")` 自杀，然后：

```
[0] 死 → [1] 收到 {'EXIT', [0], "chain dies here"} → [1] 以相同原因死
     → [2] 收到 {'EXIT', [1], "chain dies here"} → [2] 以相同原因死
     → [3] 收到 {'EXIT', [2], "chain dies here"} → [3] 以相同原因死
     → shell 收到 {'EXIT', [3], "chain dies here"} → shell 以相同原因死
```

**整条链像多米诺骨牌一样倒下**。这正是"自杀协定"的威力——一个崩溃，整组清洁地死亡。

### exit 信号的三种 Reason

|Reason|含义|链接进程的反应|
|---|---|---|
|`normal`|进程自然结束或 `exit(normal)`|**忽略**，链接进程继续活|
|其他（如 `error`、`boom`、`"chain dies here"`）|异常终止|**以相同 Reason 崩溃**​|
|`kill`|不可捕获的硬杀|**立即死**，trap_exit 也救不了|

📌 **洞见二：normal 是"优雅退出"的协议**

`exit(normal)` 或进程自然结束后，`{'EXIT', Pid, normal}` 信号会被链接进程**忽略**——这意味着"正常退出不传播"。这是极其重要的设计：

- 监督者重启子进程时，子进程正常退出 → 监督者不跟着死
- 系统关闭时，进程正常退出 → 不触发连锁崩溃
- **只有"异常退出"才传播**——这正是我们想要的
    
> 💡 **工程含义**：你应该在"主动关闭"时使用 `exit(normal)`，在"出错"时使用 `exit(Reason)` 或让错误自然发生。这个区别决定了故障是否传播。

## 🛡️ 小节二：Trapping Exits —— 监督者的雏形

### 问题：如果所有进程都"自杀"，谁来重启？

链接机制解决了"快速失败、整组死亡"的问题，但没有解决"重启"的问题。Fred 在章节里明确指出：

> **"链接擅长'杀'，但缺了'重启'的一半。"**​

要重启进程，必须有人**知道进程死了但不跟着死**。这个人就是"系统进程"（system process）。

### trap_exit 机制

调用 `process_flag(trap_exit, true)` 可以把当前进程变成系统进程：

```
1> process_flag(trap_exit, true).
true
2> spawn_link(fun() -> linkmon:chain(3) end).
<0.49.0>
3> receive X -> X end.
{'EXIT',<0.49.0>,"chain dies here"}
```

**奇迹出现了**：这次 shell 没有崩溃！它收到了一条普通消息 `{'EXIT',<0.49.0>,"chain dies here"}`。

发生了什么？ 解释得很清楚：

> **"当进程设置 trap_exit 后，到来的 exit 信号不再致命。相反，BEAM 把信号转换成标准的 Erlang 消息，丢进进程的邮箱。消息格式永远是三元组：{'EXIT', FromPid, Reason}。"**

### 系统进程的工作机制

Fred 重做了 `chain` 的例子，这次在 shell 里先 `trap_exit`：

```
[shell] == [3] == [2] == [1] == [0]     （建立链接链）
[shell] == [3] == [2] == [1] == *dead*  （[0] 超时自杀）
[shell] == [3] == [2] == *dead*         （[1] 收到信号，但因 shell 在 trap_exit，[1] 的链接集中有 shell 这个系统进程）
[shell] == [3] == *dead*                （[2] 同理）
[shell] <-- {'EXIT',[3],"chain dies here"}  （[3] 死，向 shell 发信号）
[shell] <-- still alive!                （shell 把信号转为消息，自己不死）
```

📌 **洞见三：trap_exit 是监督者的雏形**

这正是第十七章监督树的工作机制：

```
%% 监督者的伪代码
supervisor() ->
    process_flag(trap_exit, true),  %% 关键！监督者不跟着子进程死
    Pid = spawn_link(worker),       %% 原子性创建并链接子进程
    supervisor_loop(Pid).

supervisor_loop(ChildPid) ->
    receive
        {'EXIT', ChildPid, Reason} ->
            %% 监督者收到消息而非崩溃，可以决定：
            %% - 记录日志
            %% - 按策略重启子进程
            %% - 或自己也退出
            log(Reason),
            NewPid = restart_child(),
            supervisor_loop(NewPid)
    end.
```

**监督者的本质 = `spawn_link` + `trap_exit` + `receive {'EXIT', ...}` + 尾递归**。这些都是第十二章的原语。

> 💡 **Fred 在第十二章其实已经带你写了"迷你 supervisor"**——你只是还没意识到。第十七章的 OTP `supervisor` behaviour，就是把这些原语工程化为可配置的监督策略（one_for_one、one_for_all、rest_for_one）。

### 不同异常在 trap_exit 下的行为

Fred 在章节里详细展示了 `throw`、`error`、`exit` 在邻居进程 trap_exit 时的不同表现：

|异常源（在子进程中）|未捕获时（子进程崩溃）|父进程 trap_exit 后收到的消息|
|---|---|---|
|`throw(Reason)`|子进程崩溃，Reason|`{'EXIT', ChildPid, {{nocatch, Reason}, StackTrace}}`|
|`error(Reason)`|子进程崩溃，Reason|`{'EXIT', ChildPid, {Reason, StackTrace}}`|
|`exit(Reason)`|子进程退出，Reason|`{'EXIT', ChildPid, Reason}`|
|正常结束（`exit(normal)`）|子进程正常终止|`{'EXIT', ChildPid, normal}`|

📌 **洞见四：trap_exit 下的 Reason 是"故障分类"的依据**

监督者收到 `{'EXIT', ChildPid, Reason}` 后，根据 Reason 决定重启策略：

- `normal` → 不重启（子进程是主动退出的）
- `shutdown` 或 `{shutdown, Term}` → 不重启（子进程是被要求关闭的）
- 其他 → 重启（这才是真正的"异常"）
    
这正是 OTP 监督策略的核心逻辑。**Reason 不仅仅是一个字符串，它是故障的"语义分类"**。

### kill 信号的特殊性

有一个例外必须强调：`exit(Pid, kill)` 发送的 `kill` 信号**不可被 trap_exit 捕获**：

```
1> process_flag(trap_exit, true).
true
2> exit(self(), kill).
** exception exit: killed
```

为什么需要"不可捕获的 kill"？因为在某些场景下，你必须**强制**杀死一个进程，无论它是否设置了 trap_exit。例如：

- 监督者要关闭整个应用
- 系统要强制关闭一个失控的进程
- 防止"僵尸进程"通过设置 trap_exit 来逃避杀死
    
> ⚠️ **`kill` 是 Erlang 的"终极武器"**——它绕过 trap_exit，直接终止进程。但正因为太强，正常情况下不应该用，只在系统关闭或强制清理时使用。

## 🔭 小节三：Monitors —— 单向的、轻量的观察者

### link 的局限

link 有三个限制：

1. **双向的**：A link B 意味着 B 也 link A，双方都会因对方崩溃而死（除非 trap_exit）
2. **唯一的**：两个进程之间只能有一个链接，重复调用 `link/1` 无效
3. **对称的**：无法表达"我只想观察你，但不想和你一起死"
    
这些限制在某些场景下是束缚。比如：你想观察一个进程是否还活着，但不想和它建立生死与共的关系；或者你想同时观察多个进程，但 link 的唯一性限制了你。

### monitor 的登场

Erlang 提供 monitor 作为 link 的替代：

```
Ref = erlang:monitor(process, Pid).
%% 返回唯一引用 Ref
```

当被监视的进程终止时，监视者收到消息：

```
{'DOWN', Ref, process, Pid, Reason}
```

📌 **洞见五：monitor vs link 的本质差异**

|维度|link|monitor|
|---|---|---|
|方向性|双向|**单向**​|
|数量|两进程间唯一|**可建立多个**​|
|崩溃时|默认跟着死（除非 trap_exit）|**监视者不死**，只收到消息|
|信号类型|exit 信号（特殊）|普通消息 `{'DOWN', ...}`|
|移除|`unlink(Pid)`|`demonitor(Ref)`|
|典型用途|建立"生死与共"的进程组|观察进程状态、临时监控|

### monitor 的典型场景

**场景一：RPC 调用超时控制**

```
rpc_call(Pid, Request, Timeout) ->
    Ref = erlang:monitor(process, Pid),
    Pid ! {self(), Ref, Request},
    receive
        {Ref, Reply} ->
            erlang:demonitor(Ref),
            receive {'DOWN', Ref, process, Pid, _} -> ok after 0 -> ok end,
            {ok, Reply};
        {'DOWN', Ref, process, Pid, Reason} ->
            {error, {process_down, Reason}}
    after Timeout ->
        erlang:demonitor(Ref),
        receive {'DOWN', Ref, process, Pid, _} -> ok after 0 -> ok end,
        {error, timeout}
    end.
```

**场景二：监督者观察子进程**

实际上，OTP 的 `supervisor` 在某些策略下就是用 monitor 而非 link——因为 monitor 单向、可建立多个，更适合精细控制。

📌 **洞见六：monitor 是"松耦合"的故障观察**

link 表达的是"我们是一组的，同生共死"；monitor 表达的是"我在看着你，但你死不死跟我没关系"。

这种语义差异决定了：

- **link + trap_exit**​ → 用于监督者-子进程关系（强耦合，监督者需要知道子进程死讯且不跟着死）
- **monitor**​ → 用于观察者-目标关系（松耦合，观察者只是想知道目标是否还活着）
    
> 💡 **有趣的是**：`spawn_monitor/1` 也是原子操作，它一次性完成"创建进程 + 建立 monitor"，并返回 `{Pid, Ref}`。这是许多 OTP 内部机制的基石。

### link 与 monitor 的组合

实际系统中，link 和 monitor 经常组合使用：

```
%% 监督者可能同时用 link 和 monitor
supervisor() ->
    process_flag(trap_exit, true),
    {Pid, Ref} = spawn_monitor(worker),
    supervisor_loop(Pid, Ref).

supervisor_loop(Pid, Ref) ->
    receive
        {'EXIT', Pid, Reason} ->
            %% link 传播的信号（如果监督者没 trap_exit 就会死，但这里 trap 了）
            handle_child_death(Reason, Pid, Ref);
        {'DOWN', Ref, process, Pid, Reason} ->
            %% monitor 的消息
            handle_child_death(Reason, Pid, Ref)
    end.
```

这种组合让监督者既能"双向感知"（link）又能"精确识别"（monitor 的 Ref）子进程的死亡。

### 与前十一章的深度连接

**与第七章（错误和异常）的连接**：

|维度|第七章（单进程）|第十二章（多进程）|
|---|---|---|
|机制|try...catch|link + trap_exit + monitor|
|谁处理|当前进程|链接/监视进程|
|崩溃传播|不传播（异常在当前进程内处理）|跨进程传播 exit 信号|
|哲学|处理可预期错误|让进程死，让别的进程修复|

第七章的 try/catch 是"在当前进程内修复"；第十二章的 link/trap_exit 是"让别的进程修复"。**两套机制互补，构成 Erlang 完整的容错体系**。

**与第十章（并发原语）的连接**：

- 第十章学了 spawn + ! + receive
    
- 第十二章学的是 spawn 的"容错变体"：spawn_link、spawn_monitor
    
- **spawn_link = spawn + link 的原子组合**——消除"spawn 后立即崩溃"的竞态
    

**与第十一章（深入多重处理）的连接**：

|维度|第十一章|第十二章|
|---|---|---|
|失败视角|调用方视角（超时）|进程拓扑视角（信号）|
|机制|receive...after Timeout|link + exit 信号|
|检测对象|对方进程是否响应|对方进程是否还活着|
|响应|timeout，调用方决定怎么办|exit 信号，接收方默认跟着死（除非 trap_exit）|

**第十一章的超时是"调用方主动探测"，第十二章的 link 是"VM 自动通知"**。两者结合，构成完整的故障检测：

- 超时处理"慢"或"假死"（进程活着但不响应）
    
- link/monitor 处理"真死"（进程已终止）
    

> 💡 **这就是为什么 OTP 的 gen_server:call/2 既有超时（默认 5 秒）又有 link/monitor——双保险**。

### 与后续章节的直接连接

**第十三章**会用 link/trap_exit 设计一个完整的事件服务器，包含：

- 用 spawn_link 创建事件处理进程
    
- 用 trap_exit 实现监督者
    
- 用 monitor 实现更精细的故障观察
    
- 热代码升级
    

**第十四章 gen_server**​ 的内部机制：

- `gen_server:start_link/4` 内部调用 `spawn_link`
    
- 监督者与 gen_server 之间建立 link
    
- gen_server 崩溃 → 监督者（trap_exit）收到 `{'EXIT', Pid, Reason}` → 按策略重启
    

**第十七章 Supervisors**​ 的本质：

```
%% OTP supervisor 的伪代码
init(ChildSpecs) ->
    {ok, {#{strategy => one_for_one, intensity => 3, period => 10}, ChildSpecs}}.

start_link() ->
    spawn_link(fun() -> init_and_loop() end).  %% 监督者自己也被更高层监督

loop(State) ->
    process_flag(trap_exit, true),  %% 关键！
    receive
        {'EXIT', ChildPid, Reason} ->
            case Reason of
                normal -> ok;  %% 不重启
                shutdown -> ok;  %% 不重启
                _ -> restart_child(ChildPid, State)  %% 重启
            end,
            loop(State);
        {'DOWN', Ref, process, ChildPid, Reason} ->
            %% monitor 方式
            handle_child_down(Ref, ChildPid, Reason, State),
            loop(State)
    end.
```

**监督树 = 本章所有原语的工程化组合**：

- `spawn_link` 创建子进程
- `process_flag(trap_exit, true)` 让监督者不跟着死
- `receive {'EXIT', Pid, Reason}` 感知子进程死亡
- 根据 Reason 决定重启策略
- 尾递归 loop 保持监督者永生
    
### 与工业级系统的连接

WhatsApp 的架构是本章理念的真实写照：

- **每个用户连接 = 一个 gen_server 进程**
- **连接进程与用户会话管理进程建立 link**——用户断开时，整组进程一起死，统一重启
- **监督者用 trap_exit 感知子进程死亡**——35 人团队能管理 9 亿用户，靠的就是这种自动故障恢复
- **监控进程用 monitor**——观察依赖服务（如数据库）是否还活着
- **kill 信号用于系统关闭**——部署新版本时，强制关闭旧版本进程
    
**这就是第十二章三件套（link + trap_exit + monitor）在生产系统的样子**。

## ✍️ 读书笔记的核心收获

1. **link 是"自杀协定"**：两个进程建立链接后，一方非正常死亡，另一方默认跟着死
    
2. **这是最安全的默认**：依赖组件消失时，让依赖者一起死，避免不一致状态，整组重启
    
3. **exit 信号的传播机制**：进程死亡 → VM 查链接集 → 向每个链接进程发 `{'EXIT', Pid, Reason}`
    
4. **三种 Reason 的语义**：
    
    - `normal` → 链接进程忽略，不传播
        
    - 其他 → 链接进程以相同 Reason 崩溃
        
    - `kill` → 不可捕获的硬杀，trap_exit 也救不了
        
    
5. **`spawn_link` 是原子操作**：消除"spawn 后立即崩溃"的竞态窗口
    
6. **trap_exit 让进程变成"系统进程"**：`process_flag(trap_exit, true)` 后，exit 信号被转换为普通消息 `{'EXIT', FromPid, Reason}` 投入邮箱
    
7. **trap_exit 是监督者的雏形**：监督者 = `spawn_link` + `trap_exit` + `receive {'EXIT', ...}` + 尾递归
    
8. **不同异常的 trap_exit 表现**：
    
    - `throw(Reason)` → `{'EXIT', Pid, {{nocatch, Reason}, ST}}`
        
    - `error(Reason)` → `{'EXIT', Pid, {Reason, ST}}`
        
    - `exit(Reason)` → `{'EXIT', Pid, Reason}`
        
    
9. **Reason 是故障分类的依据**：监督者根据 Reason 决定重启策略（normal/shutdown 不重启，其他重启）
    
10. **link 的三个限制**：双向、唯一、对称
    
11. **monitor 是单向观察者**：
    
    - `erlang:monitor(process, Pid)` 返回唯一 Ref
        
    - 目标进程死亡时收到 `{'DOWN', Ref, process, Pid, Reason}`
        
    - 监视者**不会**跟着死
        
    
12. **monitor vs link 的本质差异**：
    
    |维度|link|monitor|
    |---|---|---|
    |方向|双向|单向|
    |数量|唯一|多个|
    |崩溃时|默认同死（除非 trap_exit）|监视者不死，只收消息|
    |用途|生死与共的进程组|松耦合观察|
    
13. **`spawn_monitor/1` 原子操作**：创建进程 + 建立 monitor，返回 `{Pid, Ref}`
    
14. **link + monitor 组合使用**：监督者既能"双向感知"又能"精确识别"子进程死亡
    
15. **kill 信号的特殊性**：`exit(Pid, kill)` 绕过 trap_exit，强制终止——用于系统关闭或强制清理
    
16. **超时（第十一章）与 link（第十二章）互补**：
    
    - 超时处理"慢"或"假死"（进程活着但不响应）
        
    - link/monitor 处理"真死"（进程已终止）
        
    

> 💡 **贯穿全书的隐喻再进化**：Erlang 的多进程容错可以总结为——
> 
> **"让崩溃在进程边界内发生，让崩溃通过信号跨边界传播，让专门的进程捕获信号并重启。"**
> 
> - **link**​ 建立了"故障传播通道"——一个进程崩溃，依赖它的进程通过 exit 信号感知
>     
> - **trap_exit**​ 把"信号"转为"消息"——让监督者能感知崩溃而不跟着死
>     
> - **monitor**​ 提供"松耦合观察"——在不建立生死关系的前提下感知进程状态
>     
> - **Reason**​ 是故障的"语义分类"——normal/shutdown 不重启，其他重启
>     
> 
> **这三个机制，构成了 Erlang "let it crash" 哲学在多进程维度的完整落地**：
> 
> 1. 进程因 bug 崩溃（第七章的 error）
>     
> 2. 崩溃通过 link 传播 exit 信号（本章）
>     
> 3. 监督者 trap_exit 捕获信号（本章）
>     
> 4. 监督者根据 Reason 决定重启策略（第十七章）
>     
> 5. 系统恢复正常运行
>     
> 
> 这就是为什么 WhatsApp 能用 35 人支撑 9 亿用户——不是因为他们写出了无 bug 的代码，而是因为：
> 
> - **每个用户连接是一个独立的 gen_server 进程**（进程隔离）
>     
> - **进程崩溃被 link 自动传播**（故障感知）
>     
> - **监督者 trap_exit 捕获崩溃并重启**（自动恢复）
>     
> - **monitor 观察依赖服务**（松耦合健康检查）
>     
> 
> **第十二章是"let it crash"从单进程到多进程的关键跃迁**。当你读到第十七章监督树时，你会发现——**OTP supervisor 不是魔法，是 link + trap_exit + monitor + 尾递归的工程化封装**。
> 
> 正如 Fred 在章节里展示的 `chain(3)` 例子：一个进程崩溃，整条链倒下；但如果链的头部是 trap_exit 的系统进程，整条链倒下后，头部会收到 `{'EXIT', Pid, Reason}` 消息，然后可以重启整条链。**这就是监督树的微型原型，这就是 Erlang 容错哲学的精髓**。
