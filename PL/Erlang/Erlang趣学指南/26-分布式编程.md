
# 第二十六章「分布式编程」读书笔记：当"进程模型"跨越网络

前二十五章你走完了 Erlang/OTP 的完整抽象链——但所有抽象都建立在一个隐含前提上：**进程在同一台机器的 BEAM 里**。第二十六章"Distributed Programming"要打破这个前提。Fred 开篇就抛出了 Erlang 最激进的主张：

> **"在 Erlang 中，你写代码的方式对于单机八核，和对于跨全球数据中心八十台机器，几乎是一样的。"**​

这就是 Erlang 的**位置透明性（Location Transparency）**——它不是一个库、不是一个框架，是 BEAM 虚拟机的**根本属性**​ 。

第二十六章要解决的根本问题是——

> **如何让"spawn + ! + receive"这套进程原语，从单机透明扩展到跨机器集群？节点、Cookie、EPMD、RPC 各自扮演什么角色？全联通网络的代价是什么？**

---

## 🌐 小节一：The Philosophy of Location Transparency —— 分布式的"魔法"本质

### 为什么 Erlang 的分布式"特殊"？

在大多数语言中，调用远程函数意味着：

```
序列化（JSON/Protobuf）→ 网络协议 → Socket 管理 → 重试逻辑 → 反序列化
```

而在 Erlang 中 ：

```
%% 本地调用
Pid ! {do_something, Args}.

%% 远程调用——语法完全一样！
RemotePid ! {do_something, Args}.
```

**BEAM 自动处理**：Erlang 项的二进制序列化、通过 TCP/IP 或 TLS socket 传输、在远端重建消息 。

📌 **洞见一：消息是唯一的原语**

Erlang 并发模型的核心是"进程不共享内存，只通过消息通信" 。正因为如此：

- **Process A 和 Process B 在同一内存空间**​ → 消息是内存拷贝
    
- **Process A 和 Process B 相隔千里**​ → 消息是网络传输
    

**对 BEAM 来说，这两种情况的处理逻辑几乎相同**——它作为"透明路由器"为所有消息选择正确路径 。

### 官方定义：什么是分布式 Erlang

Erlang 官方文档明确 ：

> **"A distributed Erlang system consists of a number of Erlang runtime systems communicating with each other. Each such runtime system is called a node."**

**关键点**：

- 分布式 Erlang 系统 = 多个 Erlang 运行时系统互相通信
    
- 每个运行时系统称为一个**节点（Node）**
    
- **不同节点间的消息传递、链接、监视，在使用 pid 时是透明的**
    
- **注册名则是每个节点本地的**——发送消息时必须同时指定节点名
    

> ⚠️ **这个细节至关重要**：pid 是位置透明的（你不需要知道它属于哪个节点），但**注册名不是**——`{logger, 'node2@localhost'}` 才是跨节点发送注册进程消息的正确语法 。

## 🏷️ 小节二：Nodes and Names —— 节点的命名艺术

### 两种命名方式

Fred 在章节里详细讨论了节点命名的两种方式 ：

**1. 短名（-sname）**

```
$ erl -sname node1
(node1@localhost)1> node().
node1@localhost
```

- 用于**同一局域网**内的节点
    
- 假设一个公共域
    
- 主机名只用第一部分（如 `localhost`）
    

**2. 长名（-name）**

```
$ erl -name node1@server.example.com
(node1@server.example.com)1> node().
'node1@server.example.com'
```

- 用于**完全限定域名（FQDN）**
    
- 生产环境跨网络的标准选择
    
- 主机名是完整的
    

📌 **洞见二：长名节点不能与短名节点通信**

这是 Erlang 分布式的硬约束 ：

> **"A node with a long node name cannot communicate with a node with a short node name."**​

**工程启示**：生产集群必须统一命名策略——要么全是 `-sname`，要么全是 `-name`。

### 节点名的格式

节点名是一个原子，格式为 `name@host` ：

- `name`：用户指定的名称，可包含字母数字、`-`、`_`、`.`
    
- `host`：长名用完整主机名，短名用主机名的第一部分
    

```
%% 运行时启动分布式节点
1> node().
nonode@nohost    %% 非分布式模式

2> net_kernel:start([dilbert, shortnames]).
{ok,<0.102.0>}

(dilbert@uab)3> node().
dilbert@uab
```

### 非分布式节点的默认名

```
1> node().
nonode@nohost
```

这就是"未以分布式模式启动"的 BEAM 的默认节点名 。

## 🍪 小节三：The Magic Cookie —— 第一道防线（但不是安全）

### Cookie 的三重设置方式

Fred 在章节里明确了 Cookie 的设置 ：

**1. 命令行参数**

```
$ erl -sname node1 -setcookie my_secret_key
```

**2. 文件方式**

```
$ cat ~/.erlang.cookie
my_secret_key
```

Erlang 会在用户主目录查找 `.erlang.cookie` 文件。

**3. 运行时设置**

```
1> erlang:set_cookie(node(), 'my_secret_key').
```

📌 **洞见三：Cookie 是"共享密钥"，不是"加密"**

官方文档严肃警告 ：

> **"Starting a distributed node without also specifying -proto_dist inet_tls will expose the node to attacks that may give the attacker complete access to the node and by extension the cluster."**

**关键认知**：

- Cookie 只是一个**明文令牌（plain-text token）**
    
- 它的作用是**防止同一网络上的不同集群意外连接**​
    
- **它不是防火墙的替代品，也不是 TLS 的替代品**​
    
- 生产环境必须通过 TLS 隧道或 VPN 传输分布式流量
    

> ⚠️ **这是 Erlang 分布式最容易被误用的地方**——很多开发者以为"设置了 Cookie 就安全了"，实际上 Cookie 只是集群隔离机制，不是安全机制。真正的生产安全需要 `-proto_dist inet_tls` 。

## 📞 小节四：Node Connections & EPMD —— 集群的"电话簿"

### 连接的建立

Fred 在章节里展示了经典的 ping 操作 ：

```
%% 在 beta 节点上
(beta@localhost)1> net_adm:ping(alpha@localhost).
pong
```

**连接建立的过程**（这是 EPMD 的核心价值）：

```
1. NodeA 想与 NodeB 通信
2. NodeA 询问 NodeB 所在主机的 EPMD（端口 4369）："NodeB 在哪个端口？"
3. EPMD 回复："NodeB 在端口 51234"
4. NodeA 直接连接 NodeB 的 51234 端口
```

### EPMD：Erlang 端口映射守护进程

官方文档明确 ：

> **"epmd is automatically started at every host where an Erlang node is started. It is responsible for mapping the symbolic node names to machine addresses."**

**EPMD 的关键特性**：

- 在每个运行 Erlang 节点的主机上**自动启动**
    
- 默认监听 **4369 端口**
    
- 维护"节点名 → TCP 端口"的映射表
    
- 节点启动时向 EPMD 注册自己
    
- 节点停止时从 EPMD 注销
    

**查看 EPMD 注册信息**：

```
$ epmd -names
epmd: up and running on port 4369 with data:
name alpha at port 54321
```

📌 **洞见四：EPMD 是"主机级的 DNS"**

```
┌──────────────────────────────────────────┐
│  Host Machine                              │
│                                            │
│  ┌──────────────┐    ┌──────────────────┐ │
│  │   EPMD        │    │  Erlang Nodes     │ │
│  │   (port 4369) │    │                   │ │
│  │              │    │  alpha (port 54321)│ │
│  │  alpha→54321 │    │  beta  (port 54322)│ │
│  │  beta →54322 │    │  gamma (port 54323)│ │
│  └──────────────┘    └──────────────────┘ │
└──────────────────────────────────────────┘
```

> 💡 **EPMD 的持久性**：即使某个 Erlang 节点崩溃，EPMD 仍然运行——它是 OS 级守护进程，确保主机上节点"地图"的持续可用性 。

### 全联通网络（Full Mesh）

这是 Erlang 分布式最反直觉的特性 ：

> **"Connections are by default transitive. If a node A connects to node B, and node B has a connection to node C, then node A also tries to connect to node C."**​

```
%% Node A 连接 Node B
A> net_kernel:connect_node('B@host').
true

%% Node B 已经连接 Node C
%% 现在 Node A 自动尝试连接 Node C！
A> nodes().
['B@host', 'C@host']    %% A 现在能看到 B 和 C
```

📌 **洞见五：全联通是默认行为，但可以关闭**

```
$ erl -name node1 -connect_all false
```

**关闭后的行为**：

- 节点只连接你显式指定的节点
    
- 不会自动传播连接
    
- 适合大型集群（避免 N² 连接爆炸）
    

**隐藏节点（Hidden Node）**：

```
$ erl -name observer_node -hidden
```

> **"A hidden node is a node started with the command-line flag -hidden. Connections between hidden nodes and other nodes are not transitive; they must be set up explicitly. Also, hidden nodes do not show up in the list of nodes returned by nodes/0."**​

**典型用途**：运维监控节点——连接集群检查状态，但不干扰集群的全联通拓扑 。

### 动态节点名

官方文档介绍了一种特殊模式 ：

> **"If the node name is set to undefined, the node will be started in a special mode to be the temporary client of another node."**​

```
$ erl -name undefined
```

**特性**：

- 节点向第一个连接的节点请求动态分配节点名
    
- 自动设置 `-dist_listen false -hidden`
    
- 如果第一个连接断开，节点失去动态名，必须重新连接获取新名
    

**典型用途**：临时客户端、动态扩容的 worker 节点。

## 📨 小节五：Communication Basics —— 远程消息与 RPC

### 发送给远程注册进程

```
%% 如果 node2 上有一个名为 logger 的注册进程
{logger, 'node2@localhost'} ! {log, "Remote event occurred"}.
```

**语法**：`{RegisteredName, NodeName} ! Message`

### 发送给远程 PID

```
%% 如果你已经从之前的消息中获取了远程 PID
RemotePid ! {data, 123}.
```

**完全透明**——BEAM 识别 PID 属于另一个节点，自动处理路由 。

### RPC：远程过程调用

虽然消息传递是 Erlang 的心脏，但 Fred 在章节里展示了 `rpc` 模块的便利 ：

**同步 RPC**：

```
%% 在 beta 上，询问 alpha 的内存使用情况
(beta@localhost)3> rpc:call(alpha@localhost, erlang, memory, [total]).
24567890
```

**多播 RPC**：

```
%% 在集群所有节点上执行命令
(beta@localhost)4> rpc:multicall(nodes(), os, cmd, ["hostname"]).
{["my-laptop\n"], []}
```

**返回值**：`{Results, BadNodes}` 元组

### 远程 Spawn

```
%% 在 Node 上创建执行 Fun 的进程
spawn(Node, Fun) -> Pid.

%% 在 Node 上创建执行 apply(Mod, Fun, Args) 的进程
spawn(Node, Mod, Fun, Args) -> Pid.
```

📌 **洞见六：远程 Spawn 的版本一致性陷阱**

CSDN 资料明确指出 ：

> **"spawn(Node, Mod, Func, ArgList) 这种形式会比 spawn(Node, Fun) 更健壮。当分布式节点上运行的模块版本不一致时 spawn(Node, Fun) 会失败。"**​

**原因**：

- `spawn(Node, Fun)` 需要把 Fun 的闭包序列化到远端——如果模块版本不一致，反序列化失败
    
- `spawn(Node, Mod, Fun, Args)` 只在远端执行 `apply(Mod, Fun, Args)`——只要远端加载了正确版本的模块即可
    

> 💡 **生产经验**：优先使用 `spawn(Node, Mod, Fun, Args)`，避免 `spawn(Node, Fun)`


### 与前二十五章的深度连接

**与第十章（并发原语）的连接**：

|维度|单机并发|分布式 Erlang|
|---|---|---|
|`spawn(Fun)`|本地进程|`spawn(Node, Fun)` 远程进程|
|`Pid ! Msg`|本地消息|`Pid ! Msg` **语法完全相同**​|
|`receive`|本地接收|远程接收**语法完全相同**​|
|`link(Pid)`|本地链接|跨节点链接透明|
|`monitor(process, Pid)`|本地监视|跨节点监视透明|

**位置透明性的真正实现**：pid 在跨节点时仍然是有效的"地址"——BEAM 自动路由 。

**与第十四章（gen_server）的连接**：

gen_server 的 `{global, Name}` 注册方式支持跨节点全局注册：

```
gen_server:start_link({global, my_service}, ?MODULE, [], []).
```

但这需要 `global` 模块——它会维护跨节点的名称注册表，并处理网络分区。

**与第二十章（分布式应用）的连接**：

第二十章我们已经学过分布式应用的 failover——一个应用在多个节点上定义，但同一时刻只有一个节点运行它。第二十六章是第二十章的"底层基础"：

```
第二十章：分布式应用（application 级别的 failover）
    │
    ▼
第二十六章：分布式 Erlang（节点、Cookie、EPMD、RPC）
    │
    ▼
第十章：并发原语（spawn + ! + receive）
```

**与第二十五章（ETS）的连接**：

⚠️ **这是关键工程认知**：

> **ETS 表是节点本地的，不跨节点共享**​ 。

```
Node A                               Node B
┌─────────────────────┐              ┌─────────────────────┐
│ ETS Table A         │              │ ETS Table B         │
│ (owned by ProcA)    │              │ (owned by ProcB)    │
│                     │              │                     │
│ 数据：{k1, v1}      │  不共享！     │ 数据：{}             │
└─────────────────────┘              └─────────────────────┘
```

**跨节点共享数据的选择**：

1. **Mnesia**：分布式、事务性、持久化（基于 ETS + DETS）
    
2. **每个节点维护 ETS 副本**：通过 RPC 或 pub/sub 同步
    
3. **一致性哈希**：数据分片到不同节点
    

### 与工业级系统的连接

**WhatsApp 的分布式架构**（推测）：

```
┌──────────────────────┐
                    │   Load Balancer       │
                    └──────────┬───────────┘
                               │
              ┌────────────────┼────────────────┐
              ▼                ▼                ▼
        ┌──────────┐    ┌──────────┐    ┌──────────┐
        │ Node A   │    │ Node B   │    │ Node C   │
        │ (BEAM)   │◄──►│ (BEAM)   │◄──►│ (BEAM)   │
        │          │    │          │    │          │
        │ ETS:     │    │ ETS:     │    │ ETS:     │
        │ ConnTbl  │    │ ConnTbl  │    │ ConnTbl  │
        └──────────┘    └──────────┘    └──────────┘
              │                │                │
              └────────────────┼────────────────┘
                               │
                    ┌──────────▼───────────┐
                    │  Mnesia (持久化层)     │
                    │  - 用户数据           │
                    │  - 消息历史           │
                    │  - 分布式事务         │
                    └──────────────────────┘
```

**关键设计**：

- **节点间全联通**：`-connect_all false` 关闭（避免 N² 连接）
    
- **Cookie 隔离集群**：生产/预生产/测试环境用不同 Cookie
    
- **TLS 传输**：`-proto_dist inet_tls` 加密节点间通信
    
- **EPMD 管理**：每个主机自动启动，监听 4369
    
- **RPC 用于运维**：`rpc:multicall(nodes(), ...)` 批量执行命令
    
- **ETS 节点本地**：连接状态等热点数据本地存储
    
- **Mnesia 跨节点**：用户数据、消息历史分布式存储
    

**35 人支撑 9 亿用户的分布式基础**：

- **位置透明**：单机八核 → 全球八十台机器，代码几乎不变
    
- **let it crash + 分布式**：节点崩溃 → 集群自动剔除 → Mnesia 副本切换
    
- **全联通 vs 网状**：大型集群用 `-connect_all false` 避免连接爆炸
    
- **网络分区处理**：`global` 模块处理脑裂（CAP 中的 P）

## ⚠️ 分布式 Erlang 的工程陷阱

### 陷阱一：网络分区（Net Split）

```
正常状态：          网络分区：
[A]◄──►[B]          [A]      [B]
  ▲      ▲            │      │
  │      │            │      │
  ▼      ▼            ▼      ▼
[C]◄──►[D]          [C]      [D]
                         
A,B,C,D 全联通     A,C 互通；B,D 互通；AC 与 BD 隔离
```

**后果**：

- `global` 模块出现"脑裂"——两侧都认为自己拥有某个全局名
    
- 分布式应用 failover 冲突
    
- 数据不一致
    

**缓解**：

- 使用 `netsplit` 检测
    
- 采用 Quorum 机制
    
- CAP 定理：Erlang 偏向 AP（可用性 + 分区容忍）
    

### 陷阱二：Cookie 不是安全

如前所述，Cookie 只是**集群隔离**机制，不是安全机制 。生产系统必须：

```
$ erl -name node1 -proto_dist inet_tls \
      -ssl_dist_optfile /path/to/ssl.conf
```

### 陷阱三：EPMD 是单点

EPMD 在主机上是单点：

- EPMD 崩溃 → 该主机上的节点无法被其他节点发现
    
- 但已有连接不受影响
    
- Erlang 会自动重启 EPMD
    

**生产建议**：

- 防火墙限制 4369 端口访问
    
- 使用 `-start_epmd false` 配合手动 EPMD 管理（高级）
    

### 陷阱四：全联通网络的 N² 问题

10 个节点的集群 = 45 条连接

100 个节点的集群 = 4950 条连接

1000 个节点的集群 = 499500 条连接

**解决方案**：

```
$ erl -name node1 -connect_all false
```

然后用显式连接管理：

```
net_kernel:connect_node('node2@host').
```

## ✍️ 读书笔记的核心收获

1. **位置透明性**：Erlang 分布式不是库，是 BEAM 的根本属性
    
2. **节点定义**：节点是带名字的 Erlang 运行时系统，名字格式 `name@host`
    
3. **两种命名**：
    
    - `-sname`：短名，同一局域网
        
    - `-name`：长名，完全限定域名，生产标准
        
    - **长名节点不能与短名节点通信**​
        
    
4. **Cookie 机制**：
    
    - 三种设置方式：命令行、`.erlang.cookie` 文件、运行时 `erlang:set_cookie/2`
        
    - **只是集群隔离，不是安全机制**​
        
    - 生产必须用 `-proto_dist inet_tls`
        
    
5. **EPMD**：
    
    - Erlang 端口映射守护进程
        
    - 默认监听 4369
        
    - 映射节点名到 TCP 端口
        
    - 主机上自动启动，OS 级持久
        
    
6. **全联通网络**：
    
    - 默认 transitive：A 连 B，B 连 C → A 自动连 C
        
    - `-connect_all false` 关闭
        
    - 隐藏节点 `-hidden`：不传播连接，不在 `nodes()` 中显示
        
    
7. **通信原语**：
    
    - 远程注册进程：`{Name, Node} ! Msg`
        
    - 远程 PID：`Pid ! Msg`（完全透明）
        
    - `rpc:call(Node, Mod, Fun, Args)`：同步 RPC
        
    - `rpc:multicall(Nodes, Mod, Fun, Args)`：多播 RPC，返回 `{Results, BadNodes}`
        
    - `spawn(Node, Mod, Fun, Args)`：远程创建进程（优于 `spawn(Node, Fun)`）
        
    
8. **节点监控**：
    
    - `monitor_node(Node, true)`：接收 `{nodeup, Node}` / `{nodedown, Node}`
        
    - `erlang:disconnect_node(Node)`：强制断开
        
    - `nodes()` / `nodes(hidden)` / `nodes(connected)`
        
    
9. **动态节点名**：`-name undefined` 启动临时客户端节点
    
10. **官方安全警告**：不使用 `-proto_dist inet_tls` 会暴露节点给完全访问攻击
    
11. **ETS 是节点本地的**：不跨节点共享，分布式数据需要 Mnesia 或其他机制
    
12. **分布式应用的底层**：第二十章的 failover 建立在第二十六章的节点连接之上
    
13. **网络分区处理**：CAP 定理中 Erlang 偏向 AP，`global` 模块处理脑裂
    
14. **工程最佳实践**：
    
    - 生产环境统一用 `-name`
        
    - 始终用 `-proto_dist inet_tls`
        
    - 大集群用 `-connect_all false`
        
    - 远程 Spawn 优先用 `spawn(Node, Mod, Fun, Args)`
        
    - ETS 用于节点本地热点数据，Mnesia 用于跨节点持久化
        
    

> 💡 **贯穿全书的隐喻再进化**：Erlang 的分布式哲学可以总结为——
> 
> **"用进程封装计算，用消息封装通信，用位置透明封装网络。"**
> 
> - **进程**​ 封装"计算单元"（第十章）
>     
> - **消息**​ 封装"通信原语"（第十章）
>     
> - **位置透明**​ 封装"网络边界"（第二十六章）← 你在这里
>     
> - **监督树**​ 封装"容错"（第十七章）
>     
> - **分布式应用**​ 封装"failover"（第二十章）
>     
> - **Mnesia**​ 封装"分布式数据"（后续章节）
>     
> 
> **第二十六章的真正价值，是让你理解"单机并发"与"分布式系统"的统一性**：
> 
> 1. **第十章**学到 `spawn + ! + receive`
>     
> 2. **第二十六章**发现——这些原语**跨节点语法完全相同**
>     
> 3. **BEAM 自动处理**：序列化、传输、路由、重建
>     
> 4. **你写的代码不变**，但系统在 80 台机器上运行
>     
> 
> **这就是 Erlang 被称为"分布式系统母语"的原因**。
> 
> 正如 Fred 在章节里展示的——**位置透明性不是特性，是哲学**：
> 
> - 进程不共享内存 → 消息传递是唯一通信方式
>     
> - 消息传递 → 本地和远程语法一致
>     
> - 语法一致 → 位置透明
>     
> - 位置透明 → 单机代码 = 分布式代码
>     
> 
> **从第一章到第二十六章，你看到了 Erlang 抽象的终极表达**：
> 
> - 不可变变量 → 函数式纯洁性
>     
> - 并发原语 → 进程模型
>     
> - 行为 → 通用/特定分离
>     
> - 监督树 → 容错骨架
>     
> - 应用 → 生命周期管理
>     
> - 发布 → 可部署单元
>     
> - 热升级 → 不停机演化
>     
> - ETS → 节点本地共享内存
>     
> - **分布式 Erlang → 跨节点位置透明**​ ← 你在这里
>     
> - Mnesia → 分布式、持久化、事务性数据（后续）
>     
> 
> **位置透明性的代价与收益**：
> 
> |维度|收益|代价|
> |---|---|---|
> |编程模型|单机=分布式|网络分区需要处理|
> |扩展性|线性扩展到多机|全联通 N² 连接问题|
> |容错|节点崩溃不影响集群|脑裂（CAP 中的 P）|
> |安全|Cookie 隔离集群|Cookie 不是真正的安全|
> |性能|BEAM 自动优化传输|网络延迟不可避免|
> 
> **WhatsApp 35 人支撑 9 亿用户的分布式基础**：
> 
> - 位置透明 → 代码无需为分布式重写
>     
> - 全联通关闭 → 避免 N² 连接爆炸
>     
> - Cookie 隔离 → 生产/预生产环境分离
>     
> - TLS 传输 → `-proto_dist inet_tls` 加密
>     
> - ETS 节点本地 → 连接状态等热点数据
>     
> - Mnesia 跨节点 → 用户数据分布式存储
>     
> - 监督树 + 分布式 → 节点崩溃自动恢复
>     
> - `global` 模块 → 处理网络分区和脑裂
>     
> 
> 正如 Erlang 官方文档的严肃警告 ：
> 
> **"Starting a distributed node without also specifying -proto_dist inet_tls will expose the node to attacks that may give the attacker complete access to the node and by extension the cluster."**
> 
> **这正是工程成熟的标志**——理解抽象的强大，也理解抽象的代价：
> 
> - 位置透明是礼物，但网络分区是必须面对的现实
>     
> - Cookie 是便利，但 TLS 是必须的
>     
> - 全联通是默认，但大集群需要 `-connect_all false`
>     
> - ETS 是节点本地，跨节点数据需要 Mnesia
>     
> 
> **第二十六章是"单机 Erlang"与"分布式 Erlang"的桥梁**：
> 
> - 它告诉你 `spawn + ! + receive` 如何跨机器工作
>     
> - 它告诉你节点、Cookie、EPMD、RPC 的协作机制
>

>     
> - 它为后续 Mnesia、分布式应用、集群运维奠定基础
>     
> 
> 正如 Fred 在章节里展示的——**当"进程模型"遇见"网络"**，Erlang 给出了与众不同的答案：
> 
> - 不是"远程过程调用框架"
>

>

>
