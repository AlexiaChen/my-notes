
# 第五章「递归」读书笔记：没有循环的真相——不可变逼出了递归，尾递归让它变成循环

前四章你陆续建立了几个认知：变量不可变（第一章）、模块是 BEAM 的代码单元（第二章）、函数头即协议且守卫做运行时准入（第三/四章）。第五章"Recursion"要处理一个乍看奇怪、实则必然的问题——

> **Erlang 没有 `for`、没有 `while`、没有任何循环关键字。那"重复做事"怎么办？**

Fred 本章的小节依次是：**Length of a List → Length of a Tail Recursion → More Tail Recursion → Tail Recursion and Stack Overflow → More Recursive Functions → Quick, Sort!**。我会按这个顺序串，但主线是——**递归不是 Erlang 的"无奈之举"，而是不可变世界观下的唯一必然选择；而尾递归，则是让这种必然选择具备工业级能力的魔法**。

---

## 🔁 小节一：Length of a List —— 递归不是语法，是数据的本质

Fred 开章就用列表长度函数点破了递归与 Erlang 数据模型的深层连接：

```
len([]) -> 0;
len([_|T]) -> 1 + len(T).
```

为什么这么写？因为**Erlang 的列表本身就是递归定义的**——`[1 | [2 | ... [n | []]]]`。一个列表要么是空的 `[]`，要么是 `[Head | Tail]`，而 Tail 自己又是一个列表。这种**递归数据结构**天然呼唤递归算法。

Fred 在课堂上展开 `len([1,2,3,4])` 的求值过程：

```
len([1,2,3,4]) = 1 + len([2,3,4])
               = 1 + 1 + len([3,4])
               = 1 + 1 + 1 + len([4])
               = 1 + 1 + 1 + 1 + len([])
               = 1 + 1 + 1 + 1 + 0
               = 4
```

📌 **洞见一：递归是"结构归纳法"的代码化**

数学里证明一个关于自然数的命题，你做"数学归纳"：证明基例成立，再证明若 n 成立则 n+1 成立。Erlang 里处理递归数据结构，你做"结构递归"：写出空列表的基例，再写出 `[H|T]` 的递归子句。**函数子句与数据的构造方式一一对应**——这正是第三章我们谈到的"构造/解构对称性"的进一步深化。

📌 **洞见二：为什么不能有循环？因为循环依赖可变状态**

`for` 循环的本质是：一个可变变量（如 `i`）从初值变到终值，每次迭代修改它：

```
# Python：total 是可变的
total = 0
for x in [1, 2, 3, 4, 5]:
    total = total + x
```

但 Erlang 的变量**绑定后不可变**（第一章）。你无法写出 `total = total + X`，因为第二次绑定会失败。**循环在语义上就不可能存在**——不是 Fred 忘了加，而是不可变世界观从根本上排除了循环。

> 💡 一句话：**循环是 mutable state 的谎言，递归才是真相**。Erlang 只是诚实地选择了真相。

📌 **洞见三：递归与模式匹配的完美合谋**

`len([_|T]) -> 1 + len(T)` 这一行同时做了三件事：

1. **解构数据**：把列表拆成头 `_` 和尾 `T`
2. **缩小问题**：原问题（列表长度）被归约为更小的子问题（尾部长度）
3. **组合结果**：`1 + len(T)`
    
这三步是**所有递归函数的模板**。Fred 在本章反复强调：**先写基例（base case），再写递归子句**——因为基例永远是最简单的输入。

## 🌀 小节二：Length of a Tail Recursion —— 从线性过程到迭代过程

Fred 在这一节提出了一个尖锐的问题：**`len([1,2,3,4])` 的展开产生了 5 个嵌套的加法**。对于 4 个元素这无所谓，但如果是**数百万个元素**呢？BEAM 要在内存里保留数百万个"待计算"的加法。

这就是所谓的"body recursion"陷阱：

```
len([a,b,c]) 需要等待 len([b,c]) 的结果才能做加法
len([b,c])   需要等待 len([c]) 的结果才能做加法
len([c])     需要等待 len([]) 的结果才能做加法
```

每一层调用都要在栈上**挂起**，等下一层返回后才能完成自己的加法。栈帧随列表长度线性增长。

### 尾递归的登场

Fred 引出尾递归（tail recursion）的核心思想：

> **尾递归把线性过程（随元素增长）转变为迭代过程（实际上不增长）。**

怎么做到？引入一个**累加器（accumulator）**作为额外参数，把"计算结果"在计算的同时累积起来，而不是等到最后才回溯：

```
tail_fac(N) -> tail_fac(N, 1).
tail_fac(0, Acc) -> Acc;
tail_fac(N, Acc) when N > 0 -> tail_fac(N-1, N*Acc).
```

Fred 展开 `tail_fac(4)`：

```
tail_fac(4) = tail_fac(4, 1)
tail_fac(4, 1) = tail_fac(3, 4)
tail_fac(3, 4) = tail_fac(2, 12)
tail_fac(2, 12) = tail_fac(1, 24)
tail_fac(1, 24) = tail_fac(0, 24)
tail_fac(0, 24) = 24
```

📌 **洞见：尾递归的本质是"尾调用"**

判别标准只有一个——**递归调用是不是函数体里最后做的事情？**

```
%% 非尾递归：递归调用返回后还要做加法
len([_|T]) -> 1 + len(T).

%% 尾递归：递归调用就是返回值，没有"待办工作"
tail_len(T, Acc) -> tail_len(T, Acc+1).
```

当递归调用处于"尾位置"时，BEAM 可以做**尾调用优化（Tail Call Optimization, TCO）**：

- **普通递归**：每次调用都压一个新的栈帧，调用完成后弹栈
- **尾递归**：BEAM 复用当前栈帧，把新参数写入，跳回函数开头——**递归在机器层面变成了 `goto` 循环**
    
结果是：**无论列表有 3 个元素还是 30 亿个，BEAM 只用同一个栈帧**。

> 💡 这就是为什么 WhatsApp 能用 Erlang 处理海量消息——尾递归让"遍历百万级列表"和"遍历 3 个元素"的内存开销完全相同。

### 尾递归与"最后调用优化"

Erlang 做的甚至比传统尾递归更彻底——**Last Call Optimization（LCO）**：

> 不仅递归调用被优化，所有处于"尾位置"的调用都被优化。这使得**互递归函数**（a 调用 b，b 调用 a...）也能被优化，而在其他语言体系中这通常很难或不可能做到。

这意味着你可以写出这样的代码而不会有栈溢出风险：

```
a(X) -> ...; b(Y) -> ...;
%% a 尾调用 b，b 尾调用 a，BEAM 都能优化
```

📌 **洞见：LCO 是 Erlang "let it crash" + 监督树的底层盟友**

长期运行的服务器进程本质上是"无限递归"：

```
server_loop(State) ->
    receive
        {msg, Data} ->
            NewState = handle(Data, State),
            server_loop(NewState);  %% 尾递归！进程永远存活
        stop -> ok
    end.
```

如果没有 LCO，这个事件循环会在几百万条消息后栈溢出。有了 LCO，**`gen_server` 的 `loop` 函数可以永远运行下去，内存占用恒定**——这是 OTP 并发模型能成立的底层前提。

## 📚 小节三：More Tail Recursion —— 累加器惯用法

Fred 在这一节通过 `duplicate/2`、`reverse/2` 等函数，巩固尾递归的"累加器模式"：

```
%% 非尾递归版本
duplicate(0, _) -> [];
duplicate(N, Term) when N > 0 -> [Term | duplicate(N-1, Term)].

%% 尾递归版本
tail_duplicate(N, Term) -> tail_duplicate(N, Term, []).
tail_duplicate(0, _, List) -> List;
tail_duplicate(N, Term, List) when N > 0 ->
    tail_duplicate(N-1, Term, [Term | List]).
```

📌 **洞见一：尾递归惯用法模板**

Fred 总结的模式非常清晰：

1. **公开 API**：定义一个 arity 较小的函数（如 `tail_duplicate/2`），初始化累加器
2. **私有 helper**：定义一个 arity 较大的函数（如 `tail_duplicate/3`），携带累加器
3. **基例**：当输入到达终止条件时，返回累加器
4. **递归子句**：更新累加器，尾调用自身
    
因为 Erlang **不允许默认参数**（不同 arity 就是不同函数），所以这种"包装函数 + 累加器 helper"的两层结构是 Erlang 尾递归的标准惯用法。

📌 **洞见二：构建列表时的"反转技巧"**

Fred 在这里埋下了一个关键洞见：**在 Erlang 里，往列表头部添加元素极快，往尾部添加极慢**。

所以当你用尾递归构建列表时，会**自然地逆序构建**。标准做法：

```
double_elements(List) -> double_elements(List, []).
double_elements([], Acc) -> lists:reverse(Acc);  %% 最后反转
double_elements([H|T], Acc) ->
    double_elements(T, [2*H | Acc]).
```

**先逆序构建，最后 `lists:reverse/1` 一次性反转**——这是 Erlang 社区的标准惯用法。`lists:reverse/1` 本身是高度优化的尾递归函数，所以整体仍然是 O(n) 且常数空间。

## ⚠️ 小节四：Tail Recursion and Stack Overflow —— 为什么 Erlang 不怕栈溢出

这一节的标题本身就是个反讽——**在 Erlang 里，正确书写的尾递归永远不会栈溢出**。

Cosmiclearn 的分析很直观：

**Body Recursion（栈增长）**：

```
sum([10,20,30])
  → 栈帧1: 等待 sum([20,30])
    → 栈帧2: 等待 sum([30])
      → 栈帧3: 等待 sum([])
        → 返回 0
      → 30+0=30
    → 20+30=50
  → 10+50=60
```

100 万个元素 = 100 万个栈帧 → 内存耗尽。

**Tail Recursion（栈恒定）**：

```
sum([10,20,30], 0)
  → 复用栈帧: sum([20,30], 10)
    → 复用栈帧: sum([30... 等等不对，应该是 sum([30], 30) 
      → 复用栈帧: sum([], 60)
        → 返回 60
```

无论多少元素，永远只用 1 个栈帧。

📌 **洞见：BEAM 的栈管理是手动的**

Erlang 的 BEAM 虚拟机与其他 VM（如 JVM）有根本差异：

> JVM 等虚拟机：进入函数时自动分配栈帧，返回时自动释放。
> 
> BEAM：栈管理是显式的——`allocate N` 指令分配大小为 N 的栈帧，`deallocate N` 做相反操作。

这意味着：**不需要栈空间的函数根本不分配任何东西**；而其他函数可以在调用最后一个函数**之前**释放自己的栈帧——这实际上就是尾调用优化。

更妙的是，BEAM 的 JIT 编译器持续优化这一机制。2019 年的一个提交优化了"BIF 在尾位置调用"的场景：

> 当 `setelement/3` 等 BIF 在尾位置被调用时，BEAM 引入 `call_bif_only` 指令，将原本的"分配栈帧→调用 BIF→释放栈帧"三条指令序列优化为单条指令。

这种持续 30 多年的底层优化，让 Erlang 的尾递归性能达到了"工业级可靠"的程度。

## 🔧 小节五：More Recursive Functions —— 递归模式的目录

Fred 在这一节给出了更多递归函数的例子，实际上是在为你建立**递归模式库**。结合衍生教程的总结，Erlang 递归的核心模式有：

### 模式一：简单列表处理（非尾递归）

```
process_list([]) -> BaseValue;
process_list([Head | Tail]) -> ProcessElement(Head, process_list(Tail)).
```

### 模式二：尾递归列表处理

```
process_list_tail([], Acc) -> Acc;
process_list_tail([Head | Tail], Acc) ->
    NewAcc = update_accumulator(Head, Acc),
    process_list_tail(Tail, NewAcc).
```

### 模式三：列表构建

```
build_list([]) -> [];
build_list([Head | Tail]) -> [transform(Head) | build_list(Tail)].
```

### 模式四：列表过滤

```
filter_list([], _) -> [];
filter_list([Head | Tail], Pred) ->
    case Pred(Head) of
        true -> [Head | filter_list(Tail, Pred)];
        false -> filter_list(Tail, Pred)
    end.
```

📌 **洞见：这些模式就是第六章高阶函数的前身**

注意**模式三（map）和模式四（filter）**——它们就是第六章你会学到的 `lists:map/2` 和 `lists:filter/2` 的内部实现。Fred 在这一节其实在为下一章埋伏笔：**递归模式一旦被发现是通用的，就可以被抽象成高阶函数**。

`map` 的递归定义：

```
map(_, []) -> [];
map(F, [H|T]) -> [F(H) | map(F, T)].
```

看清楚了吗？这就是模式三的具现化。**第六章的高阶函数不是新发明，而是第五章递归模式的参数化抽象**。

## 🚀 小节六：Quick, Sort! —— 递归的威力展示

Fred 以快速排序作为本章的收官之作，展示递归在处理复杂算法时的优雅：

```
quicksort([]) -> [];
quicksort([Pivot | Rest]) ->
    quicksort([X || X <- Rest, X < Pivot])
    ++ [Pivot] ++
    quicksort([X || X <- Rest, X >= Pivot]).
```

短短 5 行，完整实现了快排。这体现了递归的真正威力——**复杂算法用递归表达，往往比命令式循环更接近问题的数学本质**。

📌 **洞见：递归 = 数学归纳法的代码化**

快排的定义就是分治：

1. **基例**：空列表已经有序
2. **递归子句**：选一个基准 Pivot，把剩余元素分成"小于 Pivot"和"大于等于 Pivot"两组，分别排序，然后拼接
    

**算法即递归结构**。这种表达方式在 Erlang 里不是"技巧"，而是"自然语言"。

### 与不可变性的双向连接

第一章我们学到"变量不可变"，当时你可能觉得这是个限制。第五章揭示了**不可变的真正礼物**：

|命令式循环|Erlang 递归|
|---|---|
|依赖可变状态 `i++`|每次递归都是新的函数调用|
|循环变量可被意外修改|每次绑定的变量不可变|
|并发时需要加锁保护循环变量|**天然线程安全，无需锁**​|
|栈深度固定|普通递归栈深度 = 数据规模|
|—|**尾递归让栈深度 = 1**​|

不可变逼出了递归，递归（特别是尾递归）又让不可变具备了工业级性能。**这是一对完美的共生关系**。

### 与并发世界的直接连接

第十章你会学到 `spawn` 创建进程，而**每个长期运行的服务器进程，本质上都是一个尾递归函数**：

```
%% gen_server 的底层事件循环（简化版）
server_loop(State) ->
    receive
        {call, From, Request} ->
            {reply, Reply, NewState} = handle_call(Request, From, State),
            reply(From, Reply),
            server_loop(NewState);  %% 尾递归！进程永生
        {cast, Msg} ->
            NewState = handle_cast(Msg, State),
            server_loop(NewState);  %% 尾递归！
        stop ->
            terminate(State)
    end.
```

**没有尾递归 + LCO，就没有 Erlang 的轻量级进程**。每个进程的事件循环都要"永远运行下去"，如果每次处理消息都消耗栈空间，百万进程根本不可能。正是因为尾递归在 BEAM 里是常数空间，Erlang 才能 spawn 出百万级轻量进程，每个进程都是一个独立的尾递归循环。

> 💡 WhatsApp 的 200 万连接/服务器、35 人支撑 9 亿用户——这个架构的最底层支点，就是第五章你学到的尾递归。

### 与 OTP 的直接连接

第十四章 `gen_server` Behaviour 的精髓，就是这个尾递归事件循环。而监督树（第十七章）本身也是递归的：

```
supervisor 启动
  → 启动子进程1
  → 启动子进程2
  → 监听子进程退出消息
  → 如果子进程崩溃，按策略重启（递归地重新启动）
  → 监督者自身也在尾递归等待消息
```

**OTP 的整个架构，是递归思想的放大**：单个函数是递归的，单个进程是递归的（事件循环），监督树是递归的（崩溃重启），应用启动是递归的（启动子应用）。

### 与第六章高阶函数的连接

第六章你会学到 `lists:map/2`、`lists:filter/2`、`lists:foldl/3` 等高阶函数。**这些函数的内部实现，全是第五章的递归模式**：

- `map` = 模式三（列表构建）
- `filter` = 模式四（列表过滤）
- `foldl` = 尾递归 + 累加器
    
Fred 在这一章其实已经把第六章的"原材料"全部备齐了，只是还没做"参数化抽象"。等你学到第六章，会发现——**所谓高阶函数，就是把第五章的递归模式中的"具体处理逻辑"替换成"函数参数"**。

## ✍️ 读书笔记的核心收获

1. **Erlang 没有循环不是缺陷，是必然**：变量不可变从根本上排除了 `for`/`while`，递归成为唯一的重复机制
2. **列表是递归数据结构**：`[H|T]` 的定义方式天然呼唤递归算法，函数子句与数据构造一一对应
3. **递归 = 结构归纳法**：先写基例（最简单输入），再写递归子句（缩小问题+组合结果）
4. **Body recursion 的代价**：递归调用后有"待办工作"（如 `+`），导致栈帧随数据规模线性增长
5. **尾递归的本质**：递归调用处于"尾位置"，是函数最后做的事，没有"待办工作"
6. **尾调用优化（TCO）**：BEAM 复用当前栈帧而非分配新的，递归在机器层面变成 `goto` 循环
7. **Last Call Optimization**：Erlang 不只优化尾递归，还优化所有尾位置调用，使互递归也能被优化
8. **累加器惯用法**：包装函数初始化累加器 + 私有 helper 携带累加器；不同 arity 是不同的函数
9. **列表构建的反转技巧**：尾递归构建列表时自然逆序，最后用 `lists:reverse/1` 一次性反转
10. **尾递归让服务器进程永生**：`gen_server` 的事件循环是尾递归，内存恒定，可永远运行
11. **递归模式是高阶函数的前身**：map/filter/fold 的内部实现就是本章的递归模式
12. **BEAM 栈管理是手动的**：`allocate`/`deallocate` 指令让不需要栈的函数零开销，让尾调用优化自然发生
    
> 💡 **贯穿全书的隐喻再进化**：Erlang 的世界里，**递归不是"重复的语法"，而是"存在的模式"**。
> 
> - 一个列表的存在方式是递归的（`[H|T]`）
>     
> - 一个进程的存在方式是递归的（事件循环）
>     
> - 一个监督树的存在方式是递归的（崩溃重启）
>     
> - 一个应用的启动是递归的（启动子应用）
>     
> 
> 当你真正理解递归，你会发现**Erlang 不是"用递归来实现循环"，而是整个世界本来就是递归的**——Erlang 只是诚实地反映了这一点。
