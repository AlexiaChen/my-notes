
# 第七章「错误和异常」读书笔记：崩溃不是失败，是故障隔离的基本单元

前五章你建立了"不可变 + 递归 + 高阶函数"的顺序编程范式，第六章把"变化的部分"抽象成 fun。但 Fred 在这一章开篇就泼了一盆冷水——

> **"Not so fast! 现在还不能解释所有的错误处理。"**

为什么？因为你之前写的代码都是"理想情况"——假设输入永远正确、假设函数永远返回、假设世界永远正常。但 Erlang 诞生的电信交换机要求**全年停机不超过 4 分钟**，硬件会坏、网络会断、协议会演化、bug 永远存在。**Erlang 的核心洞察是：你不可能预防所有错误，那就让错误以最可控的方式发生**。

第七章"Error and Exceptions"要解决的根本问题是——

> **在"错误必然发生"的前提下，Erlang 如何把错误转化为系统的可控行为？**

Fred 本章的小节依次是：**Not So Fast! → A Compilation of Errors → No! Your Logic Is Wrong! → Runtime Errors → Raising Exceptions → Handling Errors → Errors and Processes**。 我会按这个顺序串，但主线始终是——**Erlang 的异常处理不是"防御性编程"，而是"故障隔离 + 快速失败 + 让别的进程修复"**，这正是后续 OTP 监督树（第十七章）的底层支点。

---

## 🚦 小节一：Not So Fast! —— Erlang 的双轨错误处理机制

Fred 在这一节开宗明义地揭示了一个反直觉的事实：

> **Erlang 有两条错误处理范式——函数式（顺序）的和并发的。**

这是理解本章的钥匙。在其他语言里，异常处理就是 try/catch 一把梭。但 Erlang 把错误处理分成了两层：

|层级|作用域|主要机制|哲学|
|---|---|---|---|
|**函数式/顺序**​|单个进程内部|`try...catch`、模式匹配|处理可预期的错误|
|**并发**​|跨进程|链接（link）、监控（monitor）、exit 信号|让崩溃发生，让别的进程修复|

📌 **洞见一：为什么需要两层？**

因为 Erlang 系统是由大量轻量进程组成的（第十章我们会学到 spawn）。在一个进程内部，你可以 try/catch 处理异常；但**当整个进程陷入无法恢复的状态时，正确的做法不是在当前进程内"修补"，而是让进程死掉，由监督者（supervisor）重启它**。

> 💡 这就是"let it crash"的真正含义——**不是放任 bug，而是把"修复"的责任从"出错的地方"转移到"专门设计的监督者"**。出错进程只管崩溃，监督者只管重启。职责分离，系统简洁。

Cosmiclearn 的分析一针见血：

> **"我们从小被 Java/C++ 教育'不惜一切代价防止崩溃'。但 Erlang 诞生于爱立信实验室，为电信交换机供电——这些系统根本不能停。创造者意识到一个深刻真相：你无法预防每一个错误。"**

如果强行"防止每一个错误"，代码会变成防御性编程的泥潭——每个函数开头都要检查参数、每个调用都要验证返回值、每个边界都要加锁。Erlang 选择了一条更干净的路：**让错误快速暴露，然后用架构手段隔离和恢复**。

## 🔧 小节二：A Compilation of Errors —— 编译期能挡住的，就不要留到运行时

Fred 列举了各类编译错误：

- **语法错误**：`module.beam:module name does not match file name`——第二章我们学到的"模块名=文件名"约束在这里发挥作用
- **未使用函数/变量**：`./module.erl:2: Warning: function some_function/0 is unused`
- **未导出函数被错误调用**：`./module.erl:2: function some_function/1 undefined`
- **语法错误**：`./module.erl:5: syntax error before: 'SomeCharacterOrWord'`
- **静态分析警告**：`./module.erl:5: Warning: this expression will fail with a 'badarith' exception`——编译器能推断出 `llama + 5` 必崩
- **函数头不匹配**：`./module.erl:5: head mismatch`
- **子句顺序错误**：`./module.erl:5: Warning: this clause cannot match because a previous clause at line 4 always matches`——第三章我们学到的"具体子句必须前置"规则
- **case 变量不安全**：`./module.erl:9: variable 'A' unsafe in 'case' (line 5)`
    
📌 **洞见二：编译器是你的第一道防线**

Erlang 编译器做了大量静态检查——虽然它不是静态类型系统（第四章），但它能捕获：

- 明显的算术错误（`llama + 5`）
- 不可能匹配的函数子句
- 变量作用域问题
    
**这些"免费的检查"体现了 Erlang 的工程哲学：能在编译期发现的，绝不拖到运行时**。这与第四章 Dialyzer 的成功类型分析一脉相承——多层防御，层层递进。

> ⚠️ 注意：Fred 特别提到，编译器警告`this clause cannot match because a previous clause always matches`——这直接对应第三章我们学到的"函数子句从上到下匹配，具体子句必须在前"。如果你写错了顺序，编译器会告诉你，但**不会拒绝编译**——Erlang 再次展现了它的"乐观"哲学：警告你，但尊重你的选择。

## 🧠 小节三：No! Your Logic Is Wrong! —— 逻辑错误最难抓

Fred 指出：逻辑错误（Logical errors）是"程序没有崩溃，但行为不符合预期"——比如 GUI 按钮点击没反应。

这类错误：

- 编译期查不出来
- 运行时不一定崩溃
- **只能靠测试框架、tracing 工具、调试器发现**
    
📌 **洞见三：Erlang 更关注"会崩溃的错误"**

Fred 在本节说了一句很实在的话：

> **"It's easier to focus on those that make your programs crash, won't bubble up 50 levels from now."**

翻译过来：**"更容易关注的是那些会让程序崩溃的错误，它们不会从现在起冒泡 50 层。"**

这是一个反直觉但深刻的工程洞察——**会崩溃的错误反而更好处理**，因为：

1. 崩溃立即暴露问题，错误现场清晰
2. 崩溃不会"带着脏状态继续运行"
3. 崩溃可以被监督树捕获和重启
4. 相比之下，逻辑错误会"安静地错误"——数据悄悄损坏、状态悄悄偏离，等到发现时已经传播了 50 层调用栈
    
> 💡 **这就是为什么 Erlang 选择"let it crash"而不是"防御性编程"**——崩溃是善意的提醒，逻辑错误是恶意的潜伏。

## 💥 小节四：Runtime Errors —— 三类异常的精确划分

这是本章的核心。Erlang 官方文档明确把异常分为三类：

### 1. error —— 运行时错误（Run-time Errors）

由 BEAM 虚拟机在遇到"逻辑不可能"时触发：

```
1> lists:sort(fffffff).
** exception error: no function clause matching lists:sort(fffffff)

2> case "Unexpected Value" of
2> expected_value -> ok;
2> other_expected_value -> 'also ok'
2> end.
** exception error: no case clause matching "Unexpected Value"
```

常见的 error 类型：

|错误原因|含义|
|---|---|
|`badarg`|参数类型错误或格式错误|
|`badarith`|算术表达式中的错误参数（如 `10 + "1"`）|
|`{badmatch, V}`|模式匹配失败|
|`function_clause`|找不到匹配的函数子句|
|`{case_clause, V}`|case 表达式中没有匹配的支|
|`if_clause`|if 表达式中没有 true 支|
|`undef`|调用了不存在的函数|
|`{badfun, F}`|fun F 有问题|
|`{badarity, F}`|fun 应用的参数数量错误|

你也可以手动触发：`erlang:error(Reason)`。

### 2. exit —— 进程终止通知

`exit/1` 用于进程自我终止，`exit/2` 用于让另一个进程终止：

```
exit(normal).              %% 优雅退出
exit(some_reason).         %% 异常退出，会向链接进程广播 {'EXIT', Pid, Reason}
exit(Pid, kill).           %% 强制杀死另一个进程
```

**关键点**：exit 异常与**并发**紧密相关。当进程因 exit 终止时，它会向所有链接的进程发送 exit 信号。这是第十章"links and monitors"、第十七章监督树的基础。

### 3. throw —— 程序员控制的"非局部返回"

`throw/1` 是**唯一一类设计为被常规捕获**的异常：

```
throw({not_found, UserId}).
```

throw 的典型用途：

- **非局部返回**：从深层递归中提前跳出
- **预期错误信号**：如"用户不存在"、"资源不可用"
- **控制流**：代替多层嵌套的 if/case
    
📌 **洞见四：三类异常的意图区分（这是本章最深的洞见）**

Erlang 邮件列表里 Richard Carlsson 的解释堪称经典：

> **"当你的意思是'终止进程，给 Term 作为原因（如果有进程在监视）'，用 `exit(Term)`。**
> 
> **当你的意思是'发生了崩溃错误'，即一些相当意外的事情，调用者并不真的预期要处理它，用 `erlang:error(Reason)`。**
> 
> **当你想 throw 一个调用者可能想要捕获的异常时，用 `throw(Term)`，并且要在文档中写明你的函数可能会 throw 这个异常。"**

这个区分极其重要：

|异常类|意图|谁该捕获|典型场景|
|---|---|---|---|
|**error**​|"我崩了，这是 bug"|监督树|`1/0`、`badmatch`、`undef`|
|**exit**​|"我要终止了"|链接/监控进程|正常关闭、强制杀进程|
|**throw**​|"我返回了一个特殊情况"|调用者|提前返回、预期异常|

**实践指导原则**：

- **error**：用于"调用者不应该处理"的严重错误。让监督树来重启进程
- **exit**：用于进程生命周期管理，特别是并发场景
- **throw**：用于"调用者应该处理"的预期情况，**并且要在文档中明确说明**
    
> 💡 **一个判断标准**：如果你预期调用者会处理这个"异常"，用 throw；如果你认为这是 bug、调用者无能为力，用 error；如果你要终止进程或通知其他进程，用 exit。

## 🚀 小节五：Raising Exceptions —— 主动抛出异常的艺术

Fred 展示了三种主动抛出异常的方式：

```
generate_exception(1) -> a;                           %% 正常返回
generate_exception(2) -> throw(a);                    %% throw 异常
generate_exception(3) -> exit(a);                     %% exit 异常
generate_exception(4) -> {'EXIT', a};                 %% 历史遗留语法
generate_exception(5) -> erlang:error(a).             %% error 异常
```

📌 **洞见五：选择正确的异常类是工程纪律**

这不是语法选择，是**语义选择**：

- 如果你的函数遇到了"调用者应该预期并处理"的情况（如"用户不存在"），用 `throw({user_not_found, Id})`
- 如果遇到了"这表示 bug"的情况（如"不可能到达的代码路径"），用 `erlang:error(should_not_reach_here)`
- 如果要终止当前进程，用 `exit(Reason)`
    
**常见反模式**：用 `exit/1` 来模拟 error。Richard Carlsson 明确指出：

> **"当真正的意思是'终止进程'，用 `exit(Term)`；当真正的意思是'发生了崩溃错误'，用 `erlang:error(Reason)`。因为 `error` 会贴心地用 backtrace 包装崩溃原因，而 `exit` 不会。"**

这意味着：**用 `error/1` 引发的崩溃，错误日志管理器会记录完整的栈轨迹，方便调试；用 `exit/1` 引发的"崩溃"，栈轨迹不会被包含**。所以——

> ⚠️ **真正表示 bug 的崩溃，用 `erlang:error/1` 而不是 `exit/1`**。这是 Erlang 社区的铁律。

## 🛡️ 小节六：Handling Errors —— try...catch 的正确姿势

Erlang 提供了两种异常处理机制：`catch`（遗留）和 `try...catch`（R10B 之后推荐）。

### try...catch 的完整语法

```
try Expression of
    Pattern1 [when Guard1] -> Expression1;
    Pattern2 [when Guard2] -> Expression2
catch
    Class1:Exception1:Stacktrace1 [when Guard] -> Handler1;
    Class2:Exception2:Stacktrace2 [when Guard] -> Handler2
after
    CleanupCode
end.
```

Fred 用经典的"黑骑士"例子演示：

```
black_knight(Attack) ->
    try
        talk(),
        sword(Attack)
    catch
        throw:slice -> "It is but a scratch.";
        error:cut_arm -> "I've had worse.";
        exit:cut_leg -> "Come on you pansy!";
        _:_ -> "Just a flesh wound."
    end.
```

📌 **洞见六：try...catch 的五个关键细节**

**1. `of` 子句把"成功处理"与"风险执行"分离**

`try Expr of Pattern -> ... catch ... end` 的结构精妙之处在于：

- `try` 和 `of` 之间的部分是"保护区"——这里的异常会被捕获
- `of` 和 `catch` 之间的部分是"成功处理"——**这里的异常不会被捕获**
- `catch` 之后的部分是"异常处理"

为什么要这样设计？因为如果成功处理结果时又崩溃了，这个崩溃**不应该**被同一个 try 捕获——它应该传播出去，让上层决定如何处理。

**2. `Class:Reason:Stacktrace` 三元组**

从 OTP 21 开始，你可以捕获栈轨迹：

```
try risky_call()
catch
    error:Reason:Stacktrace ->
        logger:error("Crash: ~p~nStack: ~p", [Reason, Stacktrace]),
        {error, Reason}
end.
```

**3. `after` 是"finally"**

无论是否异常，`after` 块都会执行。典型用例是资源清理：

```
try
    {ok, File} = file:open("data.txt", [read]),
    process_file(File)
catch
    error:Reason -> {error, Reason}
after
    file:close(File)  %% 确保文件关闭
end.
```

> ⚠️ **`after` 块的返回值被丢弃**——try 表达式返回的是 `of` 或 `catch` 块的值，不是 `after` 块的值。

**4. 缩写形式**

`try F catch ... end` 等价于 `try F of Val -> Val catch ... end`——成功时直接返回 F 的值。

**5. ⚠️ 致命陷阱：try 保护区不能是尾递归的**

Fred 在原文特别强调：

> **"It is important to know that the protected part of an exception can't be tail recursive."**

这是第五章我们学到的尾递归知识的深化。**当你把代码放进 `try` 的保护区时，BEAM 必须保留栈帧以便异常发生时能回溯**——这就破坏了尾递归优化。

```
%% 尾递归，但不在 try 保护区内——OK
loop(State) ->
    receive
        Msg -> loop(handle(Msg, State))
    end.

%% 尾递归，但在 try 保护区内——栈会增长！
loop_bad(State) ->
    try
        receive
            Msg -> loop_bad(handle(Msg, State))
        end
    catch
        _:_ -> ok
    end.
```

📌 **实际工程指导意义**：

- **不要在长期运行的事件循环里包 try/catch**——这会导致栈溢出
- **try/catch 应该用于"短小的、可能失败的"操作**（如文件 IO、外部调用）
- **长期运行的进程应该用"let it crash" + 监督树**，而不是在循环内 try/catch
    
**6. catch-all 要小心**

`_:_` 能捕获所有异常，但 Fred 警告：

> **"在实践中，使用 catch-all 模式要小心：尽量保护你能处理的代码，但不要超过这个范围。Erlang 有其他机制来处理剩下的事情。"**

这意味着——**只捕获你真的知道如何处理的异常**。捕获了却不妥善处理，比不捕获更危险（因为错误被"吞掉"了）。

## 🔗 小节七：Errors and Processes —— 从顺序到并发的桥

这是本章最深刻的一节，也是连接"顺序错误处理"与"并发错误处理"的桥梁。

### 进程崩溃的本质

Erlang 官方文档说得很清楚：

> **"当 Erlang 中发生异常时，执行该错误表达式的进程的执行会停止。这被称为失败（failure）。"**

也就是说——**异常终止的是"进程"，不是"整个系统"**。这是 Erlang 容错模型的基石。

### exit 信号的传播

当一个进程崩溃时，它会向所有**链接（linked）**的进程发送 exit 信号 `{'EXIT', Pid, Reason}`：

```
%% 进程 A 和 B 链接
A: spawn_link(fun() -> exit(bug) end).
%% B 会收到 {'EXIT', A_Pid, bug}
```

如果 Reason 不是 `normal`，且接收进程没有设置 `trap_exit`，那么 B 也会崩溃，并继续传播 exit 信号。这就是"连锁崩溃"——但这是**受控的连锁崩溃**，因为监督树会捕获并在适当的层级重启。

### 捕获 exit 信号

进程可以设置 `process_flag(trap_exit, true)` 来捕获 exit 信号，而不是跟着崩溃：

```
on_exit(Pid, Fun) ->
    spawn(fun() ->
        process_flag(trap_exit, true),
        link(Pid),
        receive
            {'EXIT', Pid, Why} -> Fun(Why)
        end
    end).
```

这就是监督者的雏形。

📌 **洞见七：错误处理从"进程内"上升到"进程间"**

这是本章真正的世界观转折：

|维度|顺序错误处理|并发错误处理|
|---|---|---|
|机制|try...catch|link/monitor + exit 信号|
|谁处理|当前进程|专门的监督进程|
|哲学|在当前上下文修复|让进程死，让别的进程修复|
|适用|可预期的错误|不可恢复的错误|

**两条范式不是替代关系，而是互补关系**：

- **try...catch**​ 处理"调用者应该处理的预期错误"（如文件不存在、用户输入非法）
- **link/monitor + 监督树**​ 处理"进程级不可恢复错误"（如 bug、资源耗尽、外部系统故障）
    
### "Let it crash" 的完整图景

把本章的所有概念串起来，"let it crash" 的完整工作流程是：

```
1. 进程遇到不可恢复错误
2. 进程调用 erlang:error(Reason) 或直接崩溃（badmatch、function_clause 等）
3. 异常终止当前进程的执行
4. 向所有链接进程发送 exit 信号 {'EXIT', Pid, Reason}
5. 如果 Reason 不是 normal，且接收方未 trap_exit → 接收方也崩溃
6. 监督者（设置了 trap_exit）捕获 exit 信号
7. 监督者按预定义策略重启崩溃的进程
8. 系统恢复正常
```

> 💡 **这就是 Erlang 能在 35 人团队下支撑 WhatsApp 9 亿用户的秘密**——不是因为他们写出了无 bug 的代码，而是因为他们的架构让 bug 的影响被限制在单个进程内，且能被自动恢复。

把第七章放进全书架构：

```
第一章：变量不可变 → 模式匹配失败即崩溃
第二章：模块 → 代码组织单元
第三章：函数语法 → 函数子句匹配失败即 error
第四章：类型 → 动态强类型，错误运行时暴露
第五章：递归 → 尾递归让进程事件循环永生
第六章：高阶函数 → fun 作为进程入口
第七章：Errors and Exceptions ← 你在这里
   ↓ error/exit/throw 三类异常；try...catch；进程崩溃+exit 信号
第八章：Functionally Solving Problems
   ↓ 用"let it crash"+模式匹配解决实际错误
第九章：Data Structures

第十章：Concurrency ← Erlang 的真正舞台
   ↓ spawn、send、receive、link、monitor

   ↓ 应用级生命周期管理
```

### 与前六章的深度连接

**与第一章（不可变）的连接**：

- 变量不可变 → 模式匹配失败 → 触发 `badmatch` error
- 不可变让"崩溃"绝对安全——没有"半修改"状态
    
**与第三章（函数语法）的连接**：

- `function_clause` 错误直接源于函数子句匹配失败
- `case_clause`、`if_clause` 错误直接源于模式匹配/守卫失败
- **第三章学的每个语法结构，都有对应的错误类型**
    
**与第五章（递归）的连接**：

- 尾递归让事件循环永生
- 但 try 保护区破坏尾递归→长期运行进程不能用 try 包住循环
- **这强化了"let it crash"的必要性**——进程循环不能自己处理错误，必须靠监督树
    
**与第六章（高阶函数）的连接**：

- `spawn(fun() -> ... end)`——fun 作为进程入口
- fun 内崩溃 → 进程崩溃 → exit 信号
- **高阶函数让"进程"的抽象成为可能**
    
### 与后续并发章节的直接连接

第十章你会学到：

```
Pid = spawn(fun() -> loop([]) end).
link(Pid).  %% 建立链接
monitor(Pid).  %% 建立单向监控
```

**link 和 monitor 机制，就是本章 exit 信号的工程化**。监督树（第十七章）的本质是：

```
%% 监督者伪代码
supervisor_loop(Children, Strategy) ->
    receive
        {'EXIT', ChildPid, Reason} ->
            case Reason of
                normal -> ok;  %% 正常退出，不重启
                _ -> restart_child(ChildPid, Children, Strategy)
            end,
            supervisor_loop(Children, Strategy)
    end.
```

**监督者就是一个"专门捕获 exit 信号并重启"的进程**。本章学的每一个概念——exit 信号、`trap_exit`、Reason 分类——都在监督树里被放大。

## ✍️ 读书笔记的核心收获

1. **Erlang 有双轨错误处理**：函数式（顺序）的 try/catch + 并发的 link/monitor/exit 信号
    
2. **三类异常意图分明**：
    
    - **error**：bug，调用者不预期处理，用 `erlang:error/1`，含栈轨迹
    - **exit**：进程终止通知，用于并发，用 `exit/1` 或 `exit/2`
    - **throw**：程序员可预期的异常/非局部返回，用 `throw/1`，**必须文档化**
        
3. **error 的典型类型**：`badarg`、`badarith`、`badmatch`、`function_clause`、`case_clause`、`if_clause`、`undef` 等
    
4. **try...catch 的五点精髓**：
    
    - `of` 子句分离"成功处理"与"风险执行"——成功处理区的异常不被捕获
    - `Class:Reason:Stacktrace` 三元组（OTP 21+）提供栈轨迹
    - `after` 是 finally，返回值被丢弃
    - 缩写形式 `try F catch ... end` 等价于 `try F of Val->Val catch ... end`
    - `_:_` catch-all 要谨慎使用
        
5. **⚠️ 致命陷阱：try 保护区不是尾递归的**——长期运行的事件循环不能在 try 内做尾递归，否则栈溢出
6. **编译器是第一道防线**：能静态发现的错误（如 `llama + 5`、子句顺序错误）编译器会警告
7. **逻辑错误最难抓**：不会崩溃但行为错误，只能靠测试/tracing/调试器
8. **会崩溃的错误反而更好处理**：立即暴露、现场清晰、可被监督树捕获重启
9. **进程崩溃的本质**：异常终止的是"进程"而非"系统"——这是容错模型的基石
10. **exit 信号传播**：进程崩溃时向所有链接进程发送 `{'EXIT', Pid, Reason}`，形成受控的连锁崩溃
11. **`trap_exit` 让进程捕获 exit 信号**：这是监督者的雏形
12. **两条范式互补**：
    
    - try/catch 处理"调用者应该处理的预期错误"
    - link/monitor + 监督树处理"进程级不可恢复错误"
        
13. **"let it crash" 的完整流程**：错误发生 → 进程崩溃 → exit 信号 → 监督者捕获 → 按策略重启 → 系统恢复
    
14. **error vs exit 的工程纪律**：表示 bug 用 `erlang:error/1`（含栈轨迹），终止进程用 `exit/1`
    

> 💡 **贯穿全书的隐喻再进化**：Erlang 的错误处理哲学可以总结为——
> 
> **"错误不是敌人，是不可控的错误才是敌人。"**
> 
> - 不可变 + 强类型 → 错误立即暴露，不延迟
>     
> - 三类异常 → 精确的意图表达
>     
> - try/catch → 处理可预期的错误
>     
> - 进程隔离 + exit 信号 → 不可恢复的错误被隔离在进程边界内
>     
> - 监督树（后续章节）→ 自动恢复
>     
> 
> **Erlang 不是"防止错误"，而是"驯服错误"**。它承认错误的必然性，然后用架构手段把错误转化为系统的可控行为。这就是电信级可靠性的真正秘密——不是无 bug，而是 bug 无害。
