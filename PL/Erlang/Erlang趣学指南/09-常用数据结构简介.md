
# 第九章「常用数据结构简介」读书笔记：不可变世界里的"状态方案"

前八章你建立了一个完整顺序编程范式：不可变变量、递归、尾递归、高阶函数、模式匹配、错误处理。但你一定隐隐觉得缺了点什么——**当数据规模变大、当状态变复杂、当"值"不再是简单的整数或元组时，怎么办？**

第八章的 RPN 计算器里，栈只是一个列表；最短路径问题里，状态只是几个整数。但真实的电信系统里，你需要：

- 表示一个"用户"：有 id、name、group、age……十几个字段
- 管理百万用户的会话状态：key-value 查找要快
- 处理路由表：需要有序结构
- 维护连接池：需要集合去重
- 表示网络拓扑：需要有向图
- 排队处理消息：需要队列
    
第九章"A Short Visit to Common Data Structures"就是来填这个坑的。Fred 的小节依次是：**Records → Key/Value Stores（含 Stores for Small Amounts of Data → Larger Dictionaries: Dicts and GB Trees）→ A Set of Sets → Directed Graphs → Queues**。

但本章真正的洞见不是"Erlang 有哪些数据结构"，而是——

> **在不可变世界里，"状态"不是被"修改"的，是被"替换为新版本"的。因此每一种数据结构，本质上都是一种"如何高效生成新版本"的方案。**

## 🏷️ 小节一：Records —— 编译期已知的"命名元组"

### 表象：Record 是元组的语法糖

Fred 开宗明义：record 本质是**带名字的元组**。定义一个 record：

```
-record(robot, {name, type=industrial, hobbies, details=[]}).
```

创建时：

```
first_robot() -> #robot{name="Mechatron", type=handmade, 
                        details=["Moved by a small man inside"]}.
```

在 shell 里 `rr(records)` 加载 record 定义后，打印出来是：

```
#robot{name = "Mechatron", type = handmade, 
       hobbies = undefined, 
       details = ["Moved by a small man inside"]}
```

但如果不加载 record 定义，你看到的是底层真相——**它就是一个元组**：

```
{robot, "Mechatron", handmade, undefined, ["Moved by a small man inside"]}
```

📌 **洞见一：Record 是编译期的"字段名 ↔ 位置索引"映射**

Record 在运行时**不存在**——它只是在编译阶段，把 `#robot.name` 翻译成 `element(2, Tuple)` 的一种语法糖。这意味着：

- Record 的字段在编译期必须已知
- Record 的字段数量是固定的
- Record 的访问是 O(1) 的——直接元组索引
- Record 没有运行时类型，它不参与 Dialyzer 的 per-key 类型检查
    
这与 C 语言的 `struct` 极其相似，但有一个关键差异——**Erlang 的 record 是不可变的**。更新一个 record：

```
Crusher = #robot{name="Crusher", hobbies=["Crushing people", "petting cats"]}.
Upgraded = Crusher#robot{hobbies=["Crushing people", "petting cats", "petting dogs"]}.
```

`Crusher#robot{hobbies = [...]}` **不是修改 Crusher，而是创建一个新元组**。原 Crusher 不变。

📌 **洞见二：Record 在模式匹配中是"声明式解构器"**

Record 最强大的地方在于它可以出现在模式里：

```
admin_panel(#user{name=Name, group=admin}) -> Name ++ " is allowed!";
admin_panel(#user{name=Name}) -> Name ++ " is not allowed".

adult_section(U = #user{}) when U#user.age >= 18 -> allowed;
adult_section(_) -> forbidden.
```

**这正是第三章我们学到的"函数头即协议"的延伸**——record 让函数头能以"字段名"的形式声明"我期望的数据形状"。`#user{name=Name, group=admin}` 这一行同时做了：

1. 验证输入是 user record
2. 验证 group 字段是 admin
3. 把 name 字段绑定到变量 Name
    
如果传入的不是 `#user{group=admin}`，模式匹配失败 → `function_clause` 异常 → 进程崩溃 → 监督树处理。

> 💡 Record 把"数据验证"前置到了模式匹配阶段。这是 Erlang "fail fast" 哲学在数据结构层的落地。

### Record vs Map：Fred 的后记补充

Fred 在本书后面的《Postscript: Maps》一节里给出了极其精辟的对比：

|维度|Record|Map|
|---|---|---|
|键是否编译期已知|✅ 是|❌ 否（运行时动态）|
|不可变|✅|✅|
|O(1) 直接索引|✅（编译期确定偏移）|❌（哈希查找）|
|Dialyzer per-key 类型检查|✅|❌|
|跨模块不透明|✅|✅|
|模式匹配|✅|✅|
|动态增删键|❌|✅|

📌 **洞见三：Record 是"进程内部状态"的最佳载体**

Fred 给出了一条极具工程智慧的判断：

> **"For the core of your process loop, when you know all keys that should exist, a record would be a smart choice, performance-wise."**

翻译：当你在写进程的事件循环、且你知道所有字段在编译期就确定时，**用 record 是性能最优的选择**。

为什么？因为：

- 进程状态在编译期已知（你设计 `gen_server` 时知道 State 有哪些字段）
- Record 是 O(1) 直接索引，比 map 的哈希查找快
- Record 的字段固定，Dialyzer 能做 per-key 类型检查
- 跨模块不透明，强制了"状态封装"
    
> ⚠️ **Map 不是 Record 的替代品**。Map 替代的是 dict，不是 record。用 map 替代 record，就像在 C 语言里用哈希表替代 struct——能做，但不是好主意。

📌 **洞见四：Record 的"热升级痛点"**

Record 的唯一短板：热代码升级时，record 定义变了（加了字段），老代码和新代码对同一个元组的字段索引理解不同，可能导致错位。这就是为什么 OTP 的 `code_change/3` 回调函数存在——你需要在那里手动转换状态。

**这是"编译期已知"换来的代价：灵活性降低，热升级时需要显式处理**。但相比它带来的性能、类型安全、模式匹配能力，这个代价在"进程内部状态"场景下是完全值得的。

## 🗄️ 小节二：Key/Value Stores —— 不可变世界里的"字典困境"

### 为什么需要 KV 结构？

列表查找是 O(n) 的——Erlang 的变量不可变，无法"原地修改"一个哈希表。那么问题来了：

> **在不可变语义下，如何实现高效的 key-value 查找？**

Erlang 标准库给出了**四类答案**，对应四类使用场景：

|结构|底层实现|适用场景|性能特征|
|---|---|---|---|
|**proplists**​|列表 `[{K,V}]`|小数据、配置项、函数选项|O(n) 查找|
|**orddict**​|排序列表|<75 个元素的小字典|O(log n) 查找|
|**dict**​|哈希树|通用 KV，读多写少|读 O(1) 平均|
|**gb_trees**​|平衡树|大数据，需要有序，写多|O(log n) 查找，有序|
|**maps**​|VM 优化的哈希结构|现代 Erlang 的默认 KV 选择|O(1) 平均，原生语法|

### Proplists：配置项的"方言"

`proplists` 模块处理的是 `property list`——`[{active, true}, binary]` 这样的列表，其中原子 `binary` 是 `{binary, true}` 的简写。

📌 **洞见五：Proplists 是"选项传递"的惯用法**

Erlang 标准库里大量使用 proplists 作为函数选项：

```
inet:setopts(Socket, [{active, true}, binary]).
file:open("data.txt", [read, write, append, {encoding, utf8}]).
```

为什么用 proplists 而不是 map？因为：

- **proplists 支持"原子简写"**：`binary` 等价于 `{binary, true}`
- **proplists 支持"默认值覆盖"**：后面的选项覆盖前面的
- **proplists 是列表，可以与模式匹配无缝配合**
- **proplists 的 O(n) 性能对于"配置项"场景完全可接受**——你不会在一个选项列表里放 10000 个选项

> 💡 这是 Erlang 工程哲学的精髓：**不为"可能"的性能问题买单，只为"实际"的使用场景优化**。

### Maps：现代 Erlang 的默认 KV

Fred 在《Postscript: Maps》里明确指出：

> **"Maps are a replacement for dicts, not for proper design."**

Map 的语法简洁：

```
Map = #{name => "Alice", age => 30, job => "Engineer"}.
NewMap = Map#{age := 31}.  %% 更新（键已存在用 :=）
Added = Map#{address => "123 Elm St"}.  %% 新增（用 =>）
```

📌 **洞见六：Map 是 dict 的现代替代品，不是 record 的替代品**

这是 Fred 反复强调的观点：

- **Map 替代 dict**：两者都是动态 KV，map 有 VM 级优化，语法更简洁
- **Map 不替代 record**：record 的键编译期已知，有 O(1) 直接索引、per-key 类型检查；map 的键运行时动态，性能略逊，类型检查粒度粗
    
**选型指南**（来自 Fred 的后记）：

|场景|选择|
|---|---|
|进程内部状态，字段编译期已知|**record**​|
|动态 KV，键运行时确定，跨模块传递|**map**​|
|函数选项、配置项|**proplists**​|
|大数据 KV，读多写少|**dict**​ 或 **map**​|
|需要有序遍历的 KV|**gb_trees**​|

### Dicts 和 GB Trees：当数据量变大

当 KV 数据量变大（上千、上万条目），proplists 和 orddict 就不合适了。Erlang 提供两个主力结构：

**dict**：基于哈希树实现

- 读操作极快，O(1) 平均
- 适合**读多写少**的场景
- 判断键相等用 `=:=`（严格匹配）
    
**gb_trees**：基于通用平衡树（Gustav Balstrom's trees）

- 所有操作 O(log n)
- 保持键的有序性
- 适合**需要范围查询、有序遍历、写多读少**的场景
- 与 `gb_sets` 同源

📌 **洞见七：dict 与 gb_trees 的本质差异是"哈希 vs 有序树"**

这与命令式语言里的 HashMap vs TreeMap 是同一组取舍。但 Erlang 的不可变性带来一个微妙之处：

- **dict 的"更新"是路径复制**——只复制从根到被修改叶子的路径，其他部分共享。这是持久化数据结构（Persistent Data Structure）的经典实现
- **gb_trees 的"更新"同样是路径复制**——平衡树的旋转操作会创建新节点，但大部分子树共享
    
> 💡 这就是不可变世界的精妙：**"修改"不是 in-place 改写，而是"复制被影响的路径 + 共享未受影响的部分"**。这让"旧版本"依然有效——这正是热代码升级、COW（Copy-On-Write）fork、函数式持久性的底层机制。

### 选型决策树

把 Fred 和 Erlang 社区的经验浓缩为决策树：

```
需要 key-value 存储？
├─ 数据量 < 10，且是配置/选项？
│   └─ 用 proplists
├─ 数据量 < 75？
│   └─ 用 orddict 或 map
├─ 字段编译期已知，是进程内部状态？
│   └─ 用 record（不是 KV，但常被视为"结构化状态"）
├─ 键动态，跨模块传递？
│   └─ 用 map（现代）或 dict（传统）
├─ 需要有序遍历 / 范围查询 / 写多读少？
│   └─ 用 gb_trees
└─ 读多写少的大数据 KV？
    └─ 用 dict 或 map
```

## 🎯 小节三：A Set of Sets —— 为什么有四种集合？

Erlang 提供了**四种**集合实现：ordsets、sets、gb_sets、sofs（sets of sets）。

初学者会困惑：为什么不直接给一个"最好的"？Fred 的解释是：

> **"一旦你意识到这是因为实现者一致认为没有'最佳'的构建集合的方法，这就会变得更有意义。"**

四种实现各有侧重：

|实现|底层|适用场景|特点|
|---|---|---|---|
|**ordsets**​|排序列表|小集合，需要可读表示|最慢，但表示最简单|
|**sets**​|类 dict 的哈希结构|读密集型集合操作|与 dict 类似，用 `=:=` 比较元素|
|**gb_sets**​|类 gb_trees 的平衡树|通用集合，写多读少，需要有序|与 gb_trees 类似，用 `==` 比较元素|
|**sofs**​|集合的集合|关系代数、复杂集合运算|处理"集合的集合"|

📌 **洞见八：`=:=` vs `==` 的微妙差异**

这是 sets 和 gb_sets/ordsets 的关键区别：

```
1> sets:is_element(1.0, sets:from_list([1])).
false    %% 1.0 和 1 是不同元素（=:= 严格匹配）

2> ordsets:is_element(1.0, ordsets:from_list([1])).
true     %% 1.0 和 1 是相同元素（== 值相等）

3> gb_sets:is_element(1.0, gb_sets:from_list([1])).
true     %% 同上
```

**这是一个工程陷阱**：如果你的集合里可能有 `1` 和 `1.0` 同时存在的语义需求，用 `sets`；如果认为它们应该等价，用 `gb_sets` 或 `ordsets`。

📌 **洞见九：sets 与 gb_sets 的关系 = dict 与 gb_trees 的关系**

这是一组对称的设计：

```
KV 存储：            dict    ↔  gb_trees
集合：               sets    ↔  gb_sets
底层：               哈希     ↔  平衡树
适用：               读多     ↔  写多/有序
元素比较：           =:=      ↔  ==
```

> 💡 **Bjorn Gustavsson（Wings3D 作者，OTP 团队成员）的建议**：在大多数情况下用 `gb_sets`，需要清晰可读的表示时用 `ordsets`，需要 `=:=` 语义时用 `sets`。

**为什么 gb_sets 是默认推荐？**​ 因为：

1. 平衡树的所有操作复杂度稳定 O(log n)
2. 保持元素有序，支持范围查询、前驱后继
3. 写操作性能优于 sets
4. 在 Erlang 不可变语义下，树的"路径复制"比哈希表的"路径复制"更均匀

## 🕸️ 小节四：Directed Graphs —— 数学关系的数据结构表达

Erlang 提供 `digraph` 和 `digraph_utils` 两个模块来处理有向图：

- **digraph**：构造和修改——操作顶点、边、寻找路径和环
- **digraph_utils**：图遍历（前序/后序）、环检测、树形图检测、邻居查找
    
📌 **洞见十：图是"关系的结构化表达"**

为什么 Erlang（一个主打消息传递的并发语言）要提供图结构？因为：

1. **OTP 应用依赖图**：application 启动顺序是有向无环图（DAG）
2. **监督树是树形图**：监督者-子进程的层级关系
3. **模块依赖是图**：哪些模块依赖哪些模块
4. **网络拓扑是图**：交换机、路由器、节点连接
5. **状态机是图**：状态是顶点，转移是边
    
> 💡 第八章的最短路径问题，其实就是图的单源最短路径。Fred 在本章把"手写递归"升级为"标准库图结构"——这意味着你可以在生产系统里直接构建路由表、依赖图、状态机。

**sofs 模块**更进一步：它允许在集合族和有向图之间双向转换。这是关系代数的函数式表达——你可以对图做"投影"、"选择"、"连接"等关系运算。

## 🚶 小节五：Queues —— 纯函数式 FIFO 的艺术

queue 模块实现了一个双向、先进先出（FIFO）的队列。它的底层实现极为巧妙：**用两个列表**：

```
%% 队列表示为 {RearList, FrontList}
%% RearList：新元素从这里入队（添加到头部）
%% FrontList：元素从这里出队（从头部取）
```

enqueue 操作：

```
enqueue(Element, {Rear, Front}) -> {[Element | Rear], Front}.
```

dequeue 操作：

```
dequeue({Rear, []}) -> 
    %% Front 空了，把 Rear 反转作为新的 Front
    dequeue({[], lists:reverse(Rear)});
dequeue({Rear, [Head | Front]}) -> 
    {Head, {Rear, Front}}.
```

📌 **洞见十一：两个列表的队列是"不可变 FIFO"的最优解**

为什么不用单个列表？因为在单个列表上：

- 从头部添加元素是 O(1)
- 从头部取出元素是 O(1)
- **但从尾部添加元素是 O(n)**——需要遍历整个列表
    
FIFO 队列需要"一头进、一头出"，单列表无法两头都高效。**两个列表解决这个问题**：

- 入队：添加到 Rear 的头部 O(1)
- 出队：从 Front 的头部取 O(1)
- 当 Front 为空时，把 Rear 反转后作为新的 Front（摊还 O(1)）

这是 Chris Okasaki《Purely Functional Data Structures》的经典算法。**它是为不可变语义量身定做的**——每次 enqueue/dequeue 都返回一个新队列，旧队列不变。

📌 **洞见十二：Queue 是"消息队列"的微型原型**

第十章你会学到 `receive` 语句——它从进程邮箱（一个消息队列）中取出消息。进程邮箱的底层实现，**本质上就是本章的 queue 结构**。

更深一层：Erlang 的整个并发模型建立在"消息队列"之上：

```
进程 A                                   进程 B
   │                                        │
   │  send: B ! Msg                        │  receive
   │                                        │
   ▼                                        ▼
B 的邮箱: {[Msg1, Msg2, Msg3], []}    B 的邮箱: {[Msg1, Msg2, Msg3], []}
            ▲                                 │
            │                                 ▼
            │                          取出 Msg1 处理
            │                          邮箱变为: {[Msg2, Msg3], []}
            │
            └── 新消息从 Rear 入队
```

**queue 模块就是进程邮箱的算法原型**。理解了两个列表的 queue，你就理解了 Erlang 并发的消息传递底层。

### 与不可变性的深度连接

第一章"变量不可变"在第九章结出了最丰硕的果实：

|命令式语言|Erlang|
|---|---|
|修改哈希表的一个键：`dict[key] = new_val`|创建新 dict：`NewDict = Dict#{key := new_val}`|
|原 dict 被修改|原 Dict 不变，NewDict 共享未修改的部分|
|需要锁保护并发修改|**无需锁**——数据不可变，天然线程安全|
|修改集合的一个元素：`set.add(elem)`|创建新集合：`NewSet = sets:add_element(Elem, Set)`|
|队列的 enqueue 是 in-place|队列的 enqueue 返回新队列|

**不可变逼出了"路径复制"技术**——每种数据结构都不是在原地修改，而是创建一个新版本，新旧版本共享未受影响的部分。这种"持久化数据结构"（Persistent Data Structures）是函数式编程的基石，也是 Erlang 并发模型能跑百万轻量进程的根本原因之一。

### 与第八章的直接连接

第八章你手写 RPN 计算器时，栈是一个列表，每次"压栈"是 `[Num | Stack]`——创建了一个新列表。这其实就是**最简单的"持久化栈"**。

第八章最短路径问题里，Path 累加器是一个列表，每次决策是 `[{a, A} | Path]`——也是路径复制。

**第九章的标准库数据结构，就是把第八章你手写的"递归归约 + 累加器"模式，工程化为高效的生产级实现**：

- 你手写的列表栈 → 标准库的 `queue`
- 你手写的递归查找 → 标准库的 `dict`/`gb_trees`/`maps`
- 你手写的集合操作 → 标准库的 `sets`/`gb_sets`/`ordsets`
- 你手写的图遍历 → 标准库的 `digraph`/`digraph_utils`
    
> 💡 **第八章是"发明轮子"，第九章是"使用工业级轮子"**。但理解第八章的手写实现，才能真正理解第九章标准库设计的精妙——它们都不是魔法，都是尾递归+模式匹配+不可变数据的自然延伸。

### 与后续并发章节的直接连接

第十章 `spawn` 出来的每个进程，都有一个**状态（State）**。这个 State 用什么承载？

- **简单状态**：用 record（编译期已知字段，O(1) 访问）
- **动态状态**：用 map（现代 Erlang 首选）
- **大规模 KV**：用 dict 或 gb_trees
- **进程邮箱**：queue 结构
    
第十四章 `gen_server` 的 `handle_call/3` 返回值：

```
handle_call(Request, From, State) ->
    NewState = process(Request, State),
    {reply, Reply, NewState}.
```

**`State → NewState` 的转换，就是不可变数据结构的"路径复制"**。每次处理消息，都创建一个新状态，旧状态在监督树重启时可能被引用（用于回滚）。

> 💡 WhatsApp 的每个连接是一个 `gen_server` 进程，State 是 record 或 map，存储用户会话数据。百万连接 = 百万个不可变 State，每个消息处理都创建新 State 版本。**这正是第九章数据结构在 Production 里的真实写照**。

### 与热代码升级的连接

第二十二章会讲到的 `code_change/3`：

```
code_change(OldVsn, State = #user_v1{name=Name}, Extra) ->
    %% 老版本 State 转换为新版本
    NewState = #user_v2{name=Name, nickname=undefined},
    {ok, NewState}.
```

**热升级的本质是"状态的版本迁移"**。Record 因为是编译期固定的元组结构，迁移时需要显式写 `code_change/3`；Map 因为是运行时动态的，可以逐步迁移（新老字段共存）。

> ⚠️ 这就是为什么 Fred 说"record 用于进程内部状态，map 用于跨模块传递"——热升级时，内部状态需要显式迁移，而跨模块数据可以更灵活。

## ✍️ 读书笔记的核心收获

1. **Record 是"命名元组"**：编译期已知字段，运行时就是元组，O(1) 直接索引，适合进程内部状态
2. **Record 在模式匹配中是声明式解构器**：`#user{group=admin}` 同时验证数据形状和提取字段
3. **Record vs Map 的本质差异**：编译期已知 vs 运行时动态；Record 有 per-key 类型检查，Map 没有
4. **Map 替代 dict，不替代 record**：动态 KV 用 Map，固定结构用 Record
5. **Proplists 是"选项传递"的惯用法**：`[{active, true}, binary]` 形式，O(n) 但对配置项完全可接受
6. **KV 选型决策树**：
    
    - 小数据/配置 → proplists
        
    - 编译期已知字段 → record
        
    - 动态键、跨模块 → map
        
    - 大数据、读多 → dict
        
    - 大数据、有序/写多 → gb_trees
        
    
7. **四种集合各有侧重**：ordsets（小且可读）、sets（读多，`=:=` 语义）、gb_sets（通用，`==` 语义）、sofs（集合的集合）
    
8. **`=:=` vs `==` 是 sets 与 gb_sets/ordsets 的关键区别**：`1.0` 和 `1` 在 sets 里是不同元素，在 gb_sets 里是相同元素
    
9. **gb_sets 是集合的默认推荐**：平衡树，所有操作 O(log n)，写操作优于 sets
    
10. **Queue 用两个列表实现**：`{Rear, Front}`，入队 O(1)，出队摊还 O(1)，是 Chris Okasaki 的纯函数式队列
    
11. **Queue 是进程邮箱的算法原型**：第十章 `receive` 语句的底层就是 queue 结构
    
12. **不可变逼出"路径复制"**：每种数据结构的"修改"都是创建新版本+共享未修改部分，这是持久化数据结构，也是 Erlang 并发无锁的底层原因
    
13. **有向图 digraph 是关系的形式化**：OTP 应用依赖、监督树、模块依赖、网络拓扑、状态机——都是图
    
14. **第九章 = 第八章的工业级实现**：你手写的递归归约，在标准库里被工程化为高效数据结构
    

> 💡 **贯穿全书的隐喻再进化**：Erlang 的数据结构世界可以总结为——
> 
> **"在不可变的世界里，'状态'不是被修改的，是被替换为新版本的。"**
> 
> - Record：编译期已知的固定结构，O(1) 访问，适合进程内部状态
>     
> - Map：运行时动态 KV，适合跨模块传递
>     
> - Dict/gb_trees：大规模 KV，哈希 vs 平衡树的取舍
>     
> - Sets/gb_sets：数学集合的函数式表达
>     
> - Digraph：关系的形式化表达
>     
> - Queue：纯函数式 FIFO，进程邮箱的原型
>     
> 
> **每一种数据结构，本质上都是一种"如何高效生成新版本"的方案**。当你在第十章 spawn 出第一个进程、在第十四章写出第一个 `gen_server` 时，你会发现——**进程的状态就是第九章的某种数据结构，每次消息处理就是"创建状态的新版本"**。Erlang 的并发模型，建立在不可变数据结构的路径复制之上。
> 
> 这就是为什么 WhatsApp 能用 35 人支撑 9 亿用户——每个连接是一个不可变的 `gen_server` 状态，每次消息处理产生新状态，旧状态自动被 GC。**没有锁、没有竞态、没有死锁**——因为数据根本不可变。
