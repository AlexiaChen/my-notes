
# 第二章「模块」读书笔记：从即兴表达式到生产系统的边界

第一章里你在 shell 中敲的每一行代码，都是**即兴的、一次性的、无法被其他代码复用**的。第二章"Modules"要解决的根本问题就是：**如何让代码从"shell 里的对话"变成"生产系统中的公民"**。

模块（module）这个概念表面上平淡无奇——每个 Erlang 函数都必须属于某个模块，模块对应一个 `.erl` 文件——但这个看似普通的容器，实际上是 Erlang 整套可靠系统工程的最基础组织单元。后续的应用（application）、释放（release）、热代码升级、分布式节点，全都建立在"模块"这个地基之上。

Fred 本章的小节依次是：**What Are Modules? → Creating Modules → Compiling Code → Compiler Options → Defining Macros → More About Modules（含 Metadata 与 Circular Dependencies）**。我会按这个顺序串，但主线始终是——**模块在 Erlang 世界观里到底是什么**。

---

## 🧱 小节一：What Are Modules? —— 模块是 BEAM 的代码加载单元

官方文档开宗明义："Erlang code is divided into modules. A module consists of a sequence of attributes and function declarations"。这句话看似平淡，但它揭示了一个关键事实：

> 在 Erlang 里，**不存在"游离的函数"**。所有代码都必须栖身于模块之中，而模块是 BEAM 加载、链接、版本化、替换的最小单位。

为什么必须是这样？回到第一章建立的认知：Erlang 系统是一个**永远在运行的活系统**。这样的系统要求：

- 代码可以被加载、卸载、热替换（电信系统要求"全年停机不超过 4 分钟"）
- 不同版本的代码可以在内存中共存（热升级时老版本要服务完在途请求，新版本同时接收新请求）
- 分布式场景下，代码单元要在节点间明确定位（`Module:Function(Args)` 这种调用形式天然支持跨节点）
    
如果函数是"游离"的，上述三点全都无法实现。**模块就是 BEAM 世界里代码的"身份证 + 地址 + 版本号"三位一体的载体**。

📌 **洞见**：模块不是语法层面的组织工具，它是 BEAM 虚拟机的**一等公民管理单元**。理解这一点，才能理解为什么后续 OTP 的 application 是"模块的集合"、release 是"application 的集合"——Erlang 用层层组合的方式，把"模块"这个原子单元逐步放大成一个完整的生产系统。

## 📦 小节二：Creating Modules —— `-module` 与 `-export` 构成的契约边界

创建一个模块最基本的三个要素：

```
-module(math_utils).          % 模块名，必须与文件名 math_utils.erl 相同
-export([add/2, factorial/1]). % 导出函数，决定对外可见的接口

add(A, B) -> A + B.
factorial(0) -> 1;
factorial(N) when N > 0 -> N * factorial(N - 1).
```

这里有两个**不可妥协的硬性约束**：

### 约束一：`-module` 名字必须与文件名一致

这不是语法洁癖，而是 BEAM 代码加载机制的硬性要求——"Otherwise code loading does not work as intended"。当系统在运行时需要加载 `math_utils` 模块时，它会去查找 `math_utils.beam` 文件。如果模块名和文件名不一致，加载器就找不到对应的字节码。

🎯 **实际应用**：这个约束使得**模块名在全系统范围内成为唯一寻址符**。配合 `Module:Function(Args)` 的调用惯例，你可以写出跨节点调用的代码：`rpc:call(Node, math_utils, add, [2, 3])`——模块名本身就是定位代码的坐标。

### 约束二：`-export` 是唯一的对外部接口

未导出的函数只能在模块内部调用，外部无法访问。这是一个**显式的、白名单式的契约声明**：模块作者必须刻意决定"哪些函数对外开放"。

📌 **洞见**：这种"默认封闭、显式导出"的设计，与 Erlang 整体的工程哲学完全一致——

|设计层面|默认行为|显式开启|
|---|---|---|
|函数可见性|模块内私有|`-export` 导出|
|数据类型|动态但强类型|`-spec` 静态声明（第 30 章）|
|进程状态|不共享|消息传递|
|故障处理|让进程崩溃|监督树捕获并重启|

**每一层都在贯彻"显式优于隐式、契约优于便利"**。导出列表本质上就是模块对外部世界签订的**协议契约**——这与第一章我们谈到的"tagged tuple 作为消息协议"是一脉相承的：模块导出函数是进程间协作的"公开 API"，而模块内部函数是实现细节。

> 💡 这也是为什么 WhatsApp 这类系统能在 35 人团队下支撑 9 亿用户——每个模块、每个进程都有清晰的协议边界，故障被隔离在边界内，不会横向扩散。

## ⚙️ 小节三：Compiling Code —— 从源码到 BEAM 的跃迁

shell 里可以用 `c(Module)` 编译，命令行可以用 `erlc Module.erl` 编译。编译的产物是 `.beam` 文件——BEAM 虚拟机的字节码。

但这里有一个**容易被忽略的关键机制**：编译后，BEAM 会自动生成两个函数 `module_info/0` 和 `module_info/1`。这两个函数让你在运行时反射式地查询模块的一切信息：

```
1> math_utils:module_info().
[{module, math_utils},
 {exports, [{add, 2}, {factorial, 1}, {module_info, 0}, {module_info, 1}]},
 {attributes, [{vsn, [146299772997766369192496377694713339991]}]},
 {compile, [{options, []}, {version, "X.X"}, ...]},
 ...]
```

📌 **洞见**：`module_info/1` 的存在说明——**模块在 BEAM 里不是死代码，而是带有元数据的活对象**。你可以运行时查询它的导出函数、属性、编译选项。这个能力是后续所有"动态"特性的基础：

- **热代码加载**：系统可以在运行时加载新版本的 `.beam` 文件，BEAM 会保留旧版本服务在途请求，同时让新请求路由到新版本
- **行为模式（behaviour）**：`-behaviour(gen_server)` 这种声明，让 OTP 框架能在运行时检查模块是否实现了必需的回调函数
- **文档与类型**：`-doc`、`-spec` 等属性被编译进 `.beam`，可被工具链动态检索
    
模块从"源代码文件"变成了"BEAM 里的第一类对象"——这再次印证了第一章的核心观点：**Erlang 系统是活的**。

## 🔧 小节四：Compiler Options —— 编译期的杠杆

`-compile(Options)` 属性允许在模块内嵌编译器选项，例如：

```
-compile([debug_info]).       % 包含调试信息
-compile(export_all).         % 临时导出所有函数（调试用）
-compile({nowarn_unused_vars}). % 抑制未使用变量警告
```

📌 **洞见**：`-compile(export_all)` 是一个典型的"开发期便利、生产期禁忌"。它让你在调试时不必频繁修改 `-export` 列表，但一旦进入生产就必须移除——否则模块的契约边界就被破坏了。这种"编译期开关"机制体现了 Erlang 工程文化的务实性：**提供便利，但把最终决定权交给开发者**。

更深一层：编译器选项、宏、条件编译（`-ifdef`/`-ifndef`）的组合，让同一个 `.erl` 文件可以根据 `TEST`、`DEBUG` 等不同宏定义编译出不同行为的产物。这是 Erlang 在"函数式纯代码"与"工程现实需求"之间找到的平衡点。

## 🔁 小节五：Defining Macros —— 文本层面的抽象

Erlang 的宏通过 `-define(Macro, Replacement)` 定义，通过 `?Macro` 使用：

```
-define(sub(X, Y), X - Y).
% 使用
?sub(5, 2).  % 展开为 5 - 2
```

宏是**纯文本替换**，发生在预处理阶段，不进入运行时。这与 C 语言宏类似，但 Erlang 明确把它定位为"编译期的便利工具"，而非语言核心机制。

📌 **洞见**：为什么 Erlang 不把宏做成更强大的元编程系统？因为 Erlang 的哲学是**让运行时保持简单和可预测**。宏只在编译期展开，BEAM 里不存在任何"宏的痕迹"——这意味着运行时行为是透明的、可调试的、可热升级的。对比 Lisp 那种强大的宏系统，Erlang 主动选择了"克制"：

> **宏够用到能消除重复，但绝不强到能改变语言语义。**

这种克制与函数式编程的"纯函数"理念、与 BEAM 的"简单可预测"理念完全同构。

## 🌐 小节六：More About Modules —— 元数据与环形依赖

这是本章最有"工程纵深"的一节，包含两个容易被初学者跳过但极其重要的话题。

### 元数据（Metadata）：`-vsn`、`-author`、`-behaviour` 等

模块可以携带丰富的元数据：

```
-vsn(1.0).                    % 模块版本
-behaviour(gen_server).       % 声明遵循 gen_server 行为
-moduledoc("This module ..."). % 模块文档
-doc("Adds two numbers.").    % 函数文档
```

其中 **`-vsn` 是热代码升级的关键**。如果不显式指定，BEAM 会用模块的 MD5 校验和作为默认版本号。版本号让系统能区分"当前运行的版本"和"刚加载的新版本"，从而支持第 22 章会深入讲的 `appup`/`relup` 热升级机制。

🎯 **实际应用**：在 OTP 的 release 结构里，每个模块必须有唯一名称和版本号，application 资源文件（`.app`）列出它所包含的模块及版本，release 资源文件（`.rel`）再组合多个 application。**模块 → application → release**，这是 Erlang 生产系统的三层组织结构，而模块层的 `-vsn` 是最底层的版本锚点。

### 环形依赖（Circular Dependencies）

Fred 在这一节讨论了模块间的环形依赖问题。Erlang 的解决之道很特别：**用 `-import` 谨慎使用，更推荐始终用 `Module:Function` 的完整限定形式**。

📌 **洞见**：Erlang 社区有一条不成文的铁律——**慎用 `-import`**。原因是：

1. `-import` 会让代码"看起来像本地函数"，降低可读性
2. 在大型系统里，过度使用 `-import` 容易导致模块间隐式耦合
3. `Module:Function(Args)` 的完整形式虽然冗长，但它**显式声明了依赖关系**，让模块的边界清晰可见
    
Joe Armstrong 在《Programming Erlang》里甚至警告：**"Do not under any circumstance try to make your own module called lists——if you make any mistakes in lists, you could easily seriously damage the system"**。这句话的深层含义是：在 Erlang 的"活系统"里，模块不是孤立的代码片段，而是**全局命名空间里的共享基础设施**。模块名的唯一性、接口的显式导出、调用的完整限定——所有这些"看似繁琐"的约束，都是为了在大规模并发系统中维持秩序。

> 💡 环形依赖的真正解药不是语言特性，而是**架构纪律**：模块间的依赖应该是有向无环图（DAG）。如果 Fred 告诉你环形依赖是个问题，他实际上是在教你——**好的 Erlang 系统，模块之间有清晰的层级，底层模块不依赖上层模块**。

## 🔗 全局脉络：模块在整本书中的位置

把第二章放进全书架构里看：

```
第一章：Shell + 基础类型
   ↓ 代码是"活的表达式"
第二章：Modules ← 你在这里
   ↓ 代码变成"有边界、有版本、可加载的单元"
第三章：Syntax in Functions（模式匹配、卫语句、case/if）
   ↓ 函数成为主要的控制流抽象
第四章：Types（或缺乏类型）
第五章：Hello Recursion!
第六章：Higher-Order Functions
   ↓ 函数式编程范式完备
第七章：Errors and Exceptions
第八章：Functionally Solving Problems
第九章：Data Structures
   ↓ 顺序编程能力完备
第十章：Concurrency ← Erlang 的真正舞台
   ↓
第十四章：OTP（gen_server, supervisor, application）
   ↓
第二十一章：Release
   ↓
第二十二章：热升级（appup/relup）
```

可以看到一个清晰的递进：**模块是"顺序编程"与"并发/OTP 编程"之间的桥梁**。没有模块，就没有：

- **行为模式（behaviour）**：`-behaviour(gen_server)` 让一个普通模块"变成"一个通用的服务器，这是第 14 章的核心机制
- **监督树**：supervisor 模块通过 `-behaviour(supervisor)` 声明自己遵循监督协议，这是第 17 章的基础
- **应用与释放**：application 是模块的集合，release 是 application 的集合，这是第 18-21 章的主线
- **热代码升级**：模块的版本属性 + BEAM 的双版本共存机制，让系统能在不停止的情况下升级
    
换句话说：**第二章学的每一个概念，都会在后面的章节里被反复使用并放大**。模块名与文件名的绑定 → 支持跨节点寻址；`-export` 的导出列表 → 成为进程间协议；`-vsn` 版本号 → 支撑热升级；`-behaviour` → 开启 OTP 行为模式。

## ✍️ 读书笔记的核心收获

1. **模块是 BEAM 的一等公民**：不是语法容器，而是代码加载、版本化、热替换的最小单位
2. **`-module` 名 = 文件名 = 全局唯一寻址符**：这是跨节点调用 `Node:Module:Function` 能够工作的前提
3. **`-export` 是显式契约**：默认封闭、白名单导出，与 Erlang 整体"显式优于隐式"的哲学同构
4. **`module_info/1` 让模块成为反射对象**：运行时可查询、可热加载、可行为检查——模块是"活的"
5. **宏是克制的**：只做文本替换，不进入运行时，保持 BEAM 的简单可预测
6. **慎用 `-import`**：`Module:Function` 的完整形式虽然冗长，但显式声明依赖，维护模块边界
7. **环形依赖的解药是架构纪律**：模块依赖应是有向无环图，底层不依赖上层
8. **模块 → Application → Release**：Erlang 生产系统的三层组织结构，模块是最底层锚点
    
> 💡 一个贯穿全书的隐喻：**Erlang 不是"一种语言"，而是"一套构建永不宕机系统的工程方法论"**。模块是这套方法论的第一个工程化构件——它把第一章"shell 里的即兴对话"正式升级为"生产系统中的契约公民"。
