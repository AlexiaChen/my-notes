
# 第二十三章「套接字编程」读书笔记：当"进程模型"遇见"网络字节流"

前二十二章你走完了 OTP 的完整抽象链：从 gen_server 到 supervisor，从 application 到 release，再到热升级。但 Fred 在第二十三章"Buckets of Sockets"开篇就点出一个被前面刻意回避的事实：

> **"不幸的是，本指南是关于 Erlang 的，而不是关于 TCP 和 UDP 的。"**​

换句话说——前面所有 OTP 行为（gen_server、gen_statem、gen_event）在网络应用中都被"封装"了，但**封装底下是什么？**​ 当你 `gen_server:call/2` 跨节点通信时，当 sockserv 接受 telnet 连接时，当 Process Quest 的玩家通过 socket 连入游戏时——**底层的字节是如何在网线上流动的？**

第二十三章要解决的根本问题是——

> **Erlang 的套接字编程到底是什么？TCP 与 UDP 在 BEAM 中如何被建模？"套接字"如何与"进程"无缝融合？**

Fred 本章的小节依次是：Use TCP! → UDP Sockets → TCP Sockets → 顺序与并行服务器 → 控制逻辑（主动/被动/半阻塞）→ 连接从何而来 → 套接字错误处理 → UDP 的更多细节 → 向多台机器广播。我会按这个顺序串，但主线始终是——**在 Erlang 中，套接字不是文件描述符，是"进程导向的资源"：它被进程拥有、通过消息通信、与"let it crash"哲学无缝集成**。

## 🌐 小节一：Use TCP! —— 两种协议的 Erlang 视角

### TCP 与 UDP 的本质区别

Fred 用"邮箱隐喻"阐释两者 ：

**UDP（无连接数据报）**：

> 就像往一个邮箱里塞纸条，不需要确认对方是否存在、不需要建立连接。你写好 `{127,0,0,1}:8789`，把纸条扔进去，完事。

**TCP（有状态、面向连接）**：

> 更像一次握手："嘿哥们，我是 IP 94.25.12.37，想聊吗？" → "当然，给你的消息标上序号 N，然后递增" → 从此双方可以有序地、可靠地交换纸条。

📌 **洞见一：协议选择在 Erlang 中"哲学化"**

|维度|UDP|TCP|
|---|---|---|
|连接|无连接|面向连接（握手）|
|可靠性|不保证送达、不保证顺序|保证送达、保证顺序|
|Erlang 建模|单个数据报独立|套接字是"长期关系"|
|典型应用|DNS、日志、广播|Web、数据库连接、游戏长连接|
|进程模型|一进程管理多客户端|一进程 per 连接（典型）|

> 💡 Fred 的标题"Use TCP!"暗示了——**在大多数需要可靠性的场景下，TCP 是默认选择**。UDP 的用武之地是那些"丢一两个包没关系"的场景（如日志收集、实时监控）。

## 📨 小节二：UDP Sockets —— 数据报的 Erlang 表达

### 四个基本操作

Fred 明确指出 UDP 的操作集极小 ：

> **"UDP 只有几个基本操作：设置套接字、发送消息、接收消息、关闭连接。"**

**第一步：打开套接字**

```
1> {ok, Socket} = gen_udp:open(8789, [binary, {active, true}]).
{ok, #Port}
```

📌 **洞见二：#Port 是"套接字即资源"的物证**

注意返回值——`#Port`。这不是 Pid，但是**可以像 Pid 一样被链接**：

> **"它们可以大量像 Pid 一样使用：你甚至可以设置链接，以便在崩溃时故障传播到套接字！"**​

**这是 Erlang 套接字编程最深刻的特性**——套接字在 BEAM 中不是文件描述符，是**一等公民资源**：

- 可以被链接（link）
    
- 可以参与监督树
    
- 控制进程崩溃 → 套接字自动关闭
    

**第二步：尝试重复打开（会失败）**

```
2> gen_udp:open(8789, [binary, {active, true}]).
{error, eaddrinuse}
```

端口已被占用——这正是操作系统级的"邮箱独占"。

**第三步：在第二个 shell 中打开另一个 UDP 套接字并发送**

```
%% 第二个 shell
1> {ok, Socket} = gen_udp:open(8790).
{ok, #Port}
2> gen_udp:send(Socket, {127,0,0,1}, 8789, "hey there!").
ok
```

`gen_udp:send/4` 的参数顺序 ：

- 自己的套接字
    
- 远程地址（4 元组 IPv4 / 8 元组 IPv6 / 字符串主机名）
    
- 远程端口
    
- 消息（字符串、二进制、或 IO 列表）
    

**第四步：回到第一个 shell 接收**

```
%% 第一个 shell
3> flush().
Shell got {udp, #Port<0.123>, {127,0,0,1}, 8790, "hey there!"}
ok
```

📌 **洞见三：主动模式下的消息格式**

主动模式下，控制进程收到：

```
{udp, Socket, FromIp, FromPort, Message}
```

**五个字段完整描述了"谁从哪儿发来什么"**——这正是第十一章学的消息即契约在网络层的投射。

### 套接字选项的完整图谱

`gen_udp:open/2` 的第二个参数是选项列表 ，关键选项：

|选项|含义|
|---|---|
|`binary`|数据以二进制接收（而非整数列表）|
|`{active, true}`|主动模式——数据作为消息自动推送|
|`{active, false}`|被动模式——需用 `gen_udp:recv/2,3` 拉取|
|`{active, once}`|半阻塞——只主动接收一条消息|
|`{ip, Address}`|绑定到特定 IP|
|`{port, Port}`|绑定到特定端口|
|`{broadcast, true}`|允许广播|
|`inet4` / `inet6`|IPv4 / IPv6|

📌 **洞见四：active 模式是"套接字与进程模型的融合点"**

`{active, true}` 模式下，套接字**自动向控制进程发送消息**——这正是 Erlang "万物皆进程、通信皆消息"哲学的延伸。网络字节流被透明地转换为进程间消息。

### 被动模式

Fred 演示了如何切换到被动模式 ：

```
%% 关闭并重新打开
1> gen_udp:close(Socket).
ok
2> f(Socket).
ok
3> {ok, Socket} = gen_udp:open(8789, [binary, {active, false}]).
{ok, #Port}
```

被动模式下，必须用 `gen_udp:recv/2,3` 显式拉取：

```
{ok, {Address, Port, Packet}} = gen_udp:recv(Socket, 0).
```

**主动 vs 被动的本质区别**：

- **主动**：套接字推数据给进程（进程被动接收消息）
    
- **被动**：进程拉数据从套接字（进程主动控制节奏）
    

> ⚠️ **主动模式的隐患**：恶意客户端可以洪水般发送数据报，控制进程的消息邮箱会被淹没。Fred 在 TCP 部分会详细讨论这个问题。

## 🔗 小节三：TCP Sockets —— 面向连接的"进程配对"

### TCP 的生命周期

TCP 的操作集比 UDP 丰富得多：

```
服务器端：                       客户端：
gen_tcp:listen(Port, Options)   gen_tcp:connect(Host, Port, Options)
    │                               │
    ▼                               ▼
gen_tcp:accept(ListenSocket)   （连接建立）
    │                               │
    ▼                               ▼
（获得通信 Socket）              （获得通信 Socket）
    │                               │
    ▼                               ▼
gen_tcp:send/2                   gen_tcp:send/2
gen_tcp:recv/2,3                 gen_tcp:recv/2,3
    │                               │
    ▼                               ▼
gen_tcp:close/1                  gen_tcp:close/1
```

📌 **洞见五：listen socket 与通信 socket 的分离**

TCP 服务器有两个层次的套接字：

1. **Listen Socket**：监听端口，等待连接（类似"前台接待"）
    
2. **Communication Socket**：accept 后获得的专用套接字（类似"分配给客户的专属通道"）
    

**这正是 Process Quest 中 sockserv 的底层机制**——sockserv_sup 监督的 sockserv_serv 进程调用 `gen_tcp:listen/2` 创建 listen socket，然后 `gen_tcp:accept/1` 阻塞等待连接，每个连接分配一个通信 socket。

### 一个简单的 TCP 服务器

Fred 在书中给出了经典示例 ：

```
start_nano_server() ->
    {ok, Listen} = gen_tcp:listen(2345, 
        [binary, {packet, 4}, {reuseaddr, true}, {active, true}]),
    {ok, Socket} = gen_tcp:accept(Listen),
    gen_tcp:close(Listen),
    loop(Socket).

loop(Socket) ->
    receive
        {tcp, Socket, Bin} ->
            Str = binary_to_term(Bin),
            Reply = {ok, "I got it.", Str},
            gen_tcp:send(Socket, term_to_binary(Reply)),
            loop(Socket);
        {tcp_closed, Socket} ->
            io:format("client closed~n")
    end.
```

**关键选项解析**​ ：

|选项|含义|
|---|---|
|`binary`|以二进制接收数据|
|`{packet, 4}`|每个数据包前有 4 字节长度头|
|`{reuseaddr, true}`|允许端口重用（崩溃后快速重启）|
|`{active, true}`|主动模式，数据作为消息推送|

📌 **洞见六：{packet, N} 解决了 TCP 的"粘包/拆包"问题**

TCP 是字节流协议——它不保留消息边界。如果没有 `{packet, N}`，你需要手动处理：

```
发送端：send("Hello"), send("World")
接收端可能收到："HelloWorld" 或 "He", "lloWorld"
```

**`{packet, 4}` 告诉 Erlang 驱动**：每个消息前加 4 字节长度头。驱动自动组装完整数据包后再推送给控制进程 。**这正是第十一章学的"协议设计"在网络层的工程化实现**。

### 客户端

```
nano_client:connect(Str) ->
    {ok, Socket} = gen_tcp:connect("localhost", 2345, 
        [binary, {packet, 4}]),
    ok = gen_tcp:send(Socket, term_to_binary(Str)),
    receive
        {tcp, Socket, Bin} ->
            io:format("Client received: ~p~n", [binary_to_term(Bin)]),
            gen_tcp:close(Socket)
    end.
```

**注意**：客户端不需要 `{active, true}`——它用 `receive` 表达式阻塞等待回复，这本身就是一种"被动接收"。

## 🔀 小节四：顺序与并行服务器 —— 进程模型的威力

### 顺序服务器（一次一个连接）

```
seq_server() ->
    {ok, Listen} = gen_tcp:listen(2345, [...]),
    seq_loop(Listen).

seq_loop(Listen) ->
    {ok, Socket} = gen_tcp:accept(Listen),
    loop(Socket),          %% 处理这个连接直到关闭
    seq_loop(Listen).      %% 再接受下一个
```

**问题**：处理一个连接时，其他连接必须等待。

### 并行服务器（每连接一进程）

```
start_parallel_server() ->
    {ok, Listen} = gen_tcp:listen(2345, [...]),
    spawn(fun() -> par_connect(Listen) end).

par_connect(Listen) ->
    {ok, Socket} = gen_tcp:accept(Listen),
    spawn(fun() -> par_connect(Listen) end),  %% 立即派生新 acceptor
    loop(Socket).                             %% 当前进程处理这个连接
```

📌 **洞见七：并行服务器 = "accept 进程"与"处理进程"的分离**

这是 Erlang TCP 服务器的标准范式：

```
Acceptor 进程（监督者角色）
    │
    ├─ accept 连接1 → spawn Worker1 处理
    │
    ├─ accept 连接2 → spawn Worker2 处理
    │
    ├─ accept 连接3 → spawn Worker3 处理
    │
    └─ ...
```

**这正是 sockserv_sup 监督 sockserv_serv 的微型版**——sockserv_serv 既是 acceptor 又是 worker 监督者。

### controlling_process 的妙用

Fred 在书中强调了一个关键操作 ：

```
{ok, Socket} = gen_tcp:accept(Listen),
gen_tcp:controlling_process(Socket, Pid),  %% 转移控制权
loop(Socket).
```

**为什么需要 controlling_process？**

> **"每个套接字都有一个控制进程（即创建套接字的进程）。如果控制进程死了，套接字会自动关闭。"**​

**默认情况下，accept 的进程是控制进程**。但如果直接在 accept 进程里处理连接，accept 进程就被绑死了。解决之道：

1. Acceptor 进程 accept 获得 Socket
    
2. `spawn` 一个 Worker 进程
    
3. `controlling_process(Socket, WorkerPid)` 转移所有权
    
4. Acceptor 继续 accept 下一个连接
    
5. Worker 进程拥有 Socket，它死了 Socket 自动关闭
    

📌 **洞见八：控制进程 = 套接字的"监督者"**

这与第十二章学的 link/monitor 完美契合：

- 控制进程与套接字建立隐性 link
    
- 控制进程崩溃 → 套接字自动关闭 → 客户端收到 `{tcp_closed, Socket}`
    
- 客户端崩溃 → 服务器控制进程收到 `{tcp_closed, Socket}` → 可以优雅处理
    

**"let it crash"在网络层的落地**——你不需要手动写 `try...catch` 来关闭套接字，控制进程模型自动处理。

## 🎛️ 小节五：控制逻辑 —— 主动/被动/半阻塞的三角

这是本章最微妙的部分。Fred 详细讨论了三种模式 。

### 1. 主动模式（Active True）

```
{ok, Socket} = gen_tcp:connect(Host, Port, [binary, {active, true}]).
%% 或者
inet:setopts(Socket, [{active, true}]).
```

**行为**：数据到达时，自动向控制进程发送 `{tcp, Socket, Data}` 消息。

**优点**：

- 编程模型简单——只需 `receive` 消息
    
- 与 gen_server 的 `handle_info/2` 完美契合
    

**缺点**（严重）：

> **"恶意客户端可以向系统发送成千上万的消息，而它们都会被发往控制进程。控制进程无法阻止这些消息流。"**​

**主动模式下的"数据洪流攻击"**：

```
恶意客户端                    控制进程
    │                            │
    ├─── 10000 条消息 ──►        │
    │                            ├── 消息邮箱溢出
    │                            ├── 系统崩溃或异常
    │                            │
```

**主动模式只适用于受信任的环境**（如内部网络、localhost）。

### 2. 被动模式（Active False）

```
{ok, Socket} = gen_tcp:connect(Host, Port, [binary, {active, false}]).
%% 或者
inet:setopts(Socket, [{active, false}]).
```

**行为**：必须用 `gen_tcp:recv/2,3` 显式拉取数据。

```
loop(Socket) ->
    case gen_tcp:recv(Socket, 0) of
        {ok, Data} ->
            %% 处理数据
            loop(Socket);
        {error, closed} ->
            io:format("Client disconnected~n")
    end.
```

**优点**：

- 控制进程完全掌控数据接收节奏
    
- 不会被数据洪流冲垮
    

**缺点**：

- 阻塞式——`recv` 调用会阻塞直到数据到达
    
- 难以与其他消息源交互
    
- 与 gen_server 模型不完全契合（gen_server 是消息驱动的）
    

### 3. 半阻塞模式（Active Once）—— Erlang 的独特创新

```
{ok, Socket} = gen_tcp:connect(Host, Port, [binary, {active, once}]).
%% 或者
inet:setopts(Socket, [{active, once}]).
```

**行为**：套接字在主动模式下只接收**一条**消息。收到后，必须显式调用 `inet:setopts(Socket, [{active, once}])` 重新激活才能接收下一条。

📌 **洞见九：半阻塞 = 主动与被动的完美折中**

```
控制进程 loop:
    receive
        {tcp, Socket, Data} ->
            %% 处理这条消息
            inet:setopts(Socket, [{active, once}]),  %% 重新激活
            loop(Socket);
        {tcp_closed, Socket} ->
            %% 连接关闭
            ok
    end.
```

**半阻塞模式的优势**：

1. **流量控制**：控制进程处理完一条消息后才重新激活，恶意客户端无法洪水攻击
    
2. **消息驱动**：与 gen_server 的 `handle_info/2` 完美契合
    
3. **背压天然**：处理慢 → 重新激活慢 → 客户端发送被 TCP 窗口机制节流
    

> 💡 **这正是 gen_server 处理 TCP 连接的标准模式**——Fred 在 Process Quest 的 sockserv_serv 中就用了这种模式。

### 三种模式的选择指南

|场景|推荐模式|
|---|---|
|受信任网络、简单客户端|`{active, true}`|
|需要精确流量控制、阻塞式处理|`{active, false}`|
|生产服务器、gen_server 集成|`{active, once}`（半阻塞）|
|高并发、防攻击|`{active, once}` + 监督|

## 🏗️ 小节六：连接从何而来 —— 控制进程的转移

Fred 深入讨论了"控制进程"这个概念 ：

> **"每个套接字都有一个控制进程（即创建套接字的进程）。如果控制进程死了，套接字会自动关闭。"**

### 控制进程的默认行为

```
%% Acceptor 进程
accept_loop(Listen) ->
    {ok, Socket} = gen_tcp:accept(Listen),
    %% 此时 Socket 的控制进程是 Acceptor
    WorkerPid = spawn(fun() -> worker_loop(Socket) end),
    gen_tcp:controlling_process(Socket, WorkerPid),  %% 转移！
    accept_loop(Listen).
```

📌 **洞见十：controlling_process 是"套接字所有权"的转移**

转移后：

- **Acceptor 进程崩溃**​ → Socket **不会**关闭（因为控制进程已是 Worker）
    
- **Worker 进程崩溃**​ → Socket **自动关闭**​ → 客户端收到 `{tcp_closed, Socket}`
    
- **客户端崩溃**​ → Worker 收到 `{tcp_closed, Socket}` → 可以优雅处理或崩溃
    

**这正是"let it crash"在网络层的完美落地**：

```
Worker 进程处理连接
    │
    ├── 业务错误导致崩溃
    │       │
    │       ▼
    │   Socket 自动关闭
    │       │
    │       ▼
    │   客户端收到 {tcp_closed, Socket}
    │
    └── 监督者（sockserv_sup）感知 Worker 崩溃
            │
            ▼
        决定是否重启 Worker
```

## 🛡️ 小节七：套接字错误处理 —— "什么都不用做"

Fred 给出了 Erlang 套接字编程最令人震惊的结论 ：

> **"套接字的错误处理极其简单——基本上你什么都不用做。"**​

**为什么？**

> **"如前所述，每个套接字都有一个控制进程（即创建套接字的进程）。如果控制进程死了，那么套接字将自动关闭。这意味着如果我们有一个客户端和服务器，服务器因编程错误而死，服务器拥有的套接字将自动关闭，客户端将收到 {tcp_closed, Socket} 消息。"**​

📌 **洞见十一：错误处理 = "不处理"**

|传统语言|Erlang|
|---|---|
|try-catch-finally 关闭 socket|控制进程崩溃 → socket 自动关闭|
|手动管理资源生命周期|BEAM 自动回收|
|显式错误处理代码|"let it crash" + 监督树重启|

**示例**：

```
%% 服务器因 bug 崩溃
loop(Socket) ->
    receive
        {tcp, Socket, Bin} ->
            Str = binary_to_term(Bin),
            Result = 1 / 0,  %% 抛出异常！
            loop(Socket)
    end.

%% 进程崩溃 → Socket 自动关闭 → 客户端收到 {tcp_closed, Socket}
```

**客户端代码**：

```
client_loop(Socket) ->
    receive
        {tcp, Socket, Data} ->
            %% 正常处理
            client_loop(Socket);
        {tcp_closed, Socket} ->
            %% 服务器崩溃了，但我不需要做任何清理
            %% Socket 已经被 BEAM 自动关闭
            io:format("Server died, but I'm fine~n")
    end.
```

> 💡 **这就是 Erlang 套接字编程的优雅之处**——你写的错误处理代码越少，系统越可靠。因为 BEAM 和 OTP 已经帮你处理了 99% 的错误情况。

## 📡 小节八：UDP 的更多细节 —— 数据报的陷阱

Fred 在 UDP 部分额外讨论了几个关键问题 。

### 数据报可能重复

> **"UDP 数据包可能被投递两次（这让一些人感到惊讶），所以你在编写远程过程调用代码时必须小心。可能第二个查询的回复实际上是第一个查询的重复答案。"**

**解决方案**：客户端使用 `make_ref()` 生成唯一引用：

```
client(Request) ->
    {ok, Socket} = gen_udp:open(0, [binary]),
    Ref = make_ref(),  %% 唯一引用
    ok = gen_udp:send(Socket, "localhost", 4000, 
                      term_to_binary({Ref, Request})),
    wait_for_ref(Socket, Ref).

wait_for_ref(Socket, Ref) ->
    receive
        {udp, Socket, _, _, Bin} ->
            case binary_to_term(Bin) of
                {Ref, Val} ->  %% 验证引用匹配
                    Val;
                {_OtherRef, _} ->  %% 丢弃重复/错误包
                    wait_for_ref(Socket, Ref)
            end
    end.
```

📌 **洞见十二：make_ref 是 UDP 可靠性的基石**

第十一章学的 `make_ref/0` 技巧，在 UDP RPC 场景中至关重要：

- 每个请求携带唯一 Ref
    
- 服务器回复时回显 Ref
    
- 客户端验证 Ref 匹配才接受
    
- 这防御了：重复包、乱序包、错误响应
    

**这正是 RPC 协议的最小可靠性层**——用应用层逻辑弥补 UDP 传输层的不可靠。

### 广播

UDP 支持广播（需要 `{broadcast, true}` 选项）：

```
{ok, Socket} = gen_udp:open(0, [binary, {broadcast, true}]),
gen_udp:send(Socket, {255,255,255,255}, 8789, "Hello everyone!").
```

### 与前二十二章的深度连接

**与第十章（并发原语）的连接**：

- `gen_udp:open/2` 内部调用 `spawn` 创建端口驱动进程
    
- `{udp, Socket, ...}` 消息通过 `!` 发送
    
- `receive` 接收网络消息
    
- **套接字编程是"并发原语在网络层的延伸"**
    

**与第十一章（深入多重处理）的连接**：

- `make_ref()` 用于 UDP RPC 的唯一性标识
    
- `{packet, N}` 是协议设计的分包机制
    
- 超时控制：`gen_udp:recv/3` 的第三个参数是超时
    
- 主动/被动模式是"消息接收策略"
    

**与第十四章（gen_server）的连接**：

- gen_server 的 `handle_info/2` 处理 `{tcp, Socket, Data}` 消息

**与第二十二章（Process Quest）的连接**：

Process Quest 的 sockserv 应用就是基于本章原语构建的：

```
sockserv_sup（监督者）
    │
    ▼
sockserv_serv（gen_server）
    │
    ├── gen_tcp:listen/2 创建 listen socket
    ├── gen_tcp:accept/1 接受连接
    ├── spawn worker gen_server 处理每个客户端
    ├── gen_tcp:controlling_process/2 转移 socket 所有权

```

**本章填补了第二十二章的"底层空白"**——sockserv 的黑魔法，原来是这些原语的组合。

### 与现代 OTP 的连接

**新 socket 模块（OTP 22+）**：

DeepWiki 文档指出 ：

> **"Erlang/OTP 提供双后端架构，应用可选择两种实现策略：gen_tcp/gen_udp（传统 inet 驱动）或 socket 模块（NIF 实现）。"**​

传统 `gen_tcp` 使用 `inet_drv.c` 端口驱动，新 `socket` 模块使用 NIF。通过 `{inet_backend, socket}` 选项选择 ：

```
gen_tcp:connect(Host, Port, [binary, {packet, 0}, {inet_backend, socket}]).
```

**性能对比**：

|后端|实现|性能|复杂度|
|---|---|---|---|
|`inet`|端口驱动|良好|低|
|`socket`|NIF|更高|高|

> 💡 **Fred 的书出版时（2013 年），socket 模块还未引入（OTP 22，2019 年）。但本章的原理完全适用于新模块——因为高层 API（gen_tcp/gen_udp）保持不变，只是底层实现换了**。

## ✍️ 读书笔记的核心收获

1. **Erlang 套接字是"进程导向的资源"**：被进程拥有、通过消息通信、可参与 link
    
2. **UDP 的四个基本操作**：open / send / receive / close
    
3. **#Port 是套接字的表示**：可以像 Pid 一样被链接，崩溃时故障传播
    
4. **TCP 是面向连接的**：listen → accept → send/recv → close
    
5. **Listen Socket 与 Communication Socket 分离**：前者等待连接，后者专用于已建立的连接
    
6. **{packet, N} 解决 TCP 粘包/拆包**：驱动自动组装完整数据包
    
7. **term_to_binary / binary_to_term**：Erlang 项与二进制的编解码，比 XML 快一个数量级
    
8. **三种接收模式**：
    
    - `{active, true}`：主动推送，简单但有洪水攻击风险
        
    - `{active, false}`：被动拉取，完全控制但阻塞
        
    - `{active, once}`：半阻塞，接收一条后需重新激活——生产服务器首选
        
    
9. **并行服务器范式**：accept 进程与 worker 进程分离，每连接一进程
    
10. **controlling_process 转移套接字所有权**：accept 进程 → worker 进程
    
11. **控制进程崩溃 → 套接字自动关闭**：客户端收到 `{tcp_closed, Socket}`
    
12. **"let it crash"在网络层的落地**：错误处理代码极少，BEAM 自动回收资源
    
13. **UDP 数据报可能重复**：用 `make_ref()` 生成唯一引用防御重复包
    
14. **UDP 广播**：`{broadcast, true}` 选项启用
    
15. **套接字选项全景**：
    
    - 通用：`binary`、`{active, Mode}`、`{packet, N}`、`{reuseaddr, true}`
        
    - TCP 特定：`{nodelay, true}`、`{send_timeout, T}`
        
    - UDP 特定：`{broadcast, true}`、`{multicast_ttl, TTL}`
        
    
16. **现代 socket 模块**：OTP 22+ 引入 NIF 实现，通过 `{inet_backend, socket}` 选择，性能更高
    
17. **gen_tcp/gen_udp 的双后端架构**：inet 驱动（传统）vs socket NIF（新）
