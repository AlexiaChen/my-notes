
# 第二十一章「发布」读书笔记：把"应用"打包为"可部署、可热升级"的目标系统

前二十章你完成了一次完整的抽象上升：

- 第十四章~第十六章：**行为**（gen_server / gen_statem / gen_event）
    
- 第十七章：**监督树**（容错骨架）
    
- 第十八、十九章：**应用**（把监督树包装为标准 OTP 应用）
    
- 第二十章：**应用控制器 + 分布式应用**（跨节点高可用）
    

但 Fred 在第二十一章"Release is the Word"开篇就抛出了部署维度的终极问题：

> **"当你写完一个或多个应用后，如何把'这些应用 + 一部分 Erlang/OTP 应用'打包成一个完整的系统，转移到另一台机器上运行？"**

这正是本章要解决的根本问题——

> **什么是 OTP 发布（Release）？如何用 .rel 文件定义发布？如何生成启动脚本？如何打包为自包含的目标系统？如何实现不停机热升级？**

OTP 官方文档给出了最精准的定义 ：

> **"当你写好一个或多个应用后，你可能想用这些应用和 Erlang/OTP 应用的一个子集创建一个完整的系统。这被称为一个发布（release）。为此，需要创建一个发布资源文件来定义发布中包含哪些应用。发布资源文件被用来生成启动脚本和发布包。被转移到另一站点并安装的系统被称为目标系统（target system）。"**

---

## 📦 小节一：Release 的本质 —— 从"应用"到"系统"

### 为什么需要 Release？

回顾前几章的演化：

|章节|抽象层级|交付物|
|---|---|---|
|第十四章~十六章|行为|单个 gen_server / gen_statem / gen_event 模块|
|第十七章|监督树|容错骨架|
|第十八、十九章|应用|标准 OTP 应用（.app 文件 + 监督树）|
|**第二十一章**​|**发布**​|**可部署的完整系统**​|

📌 **洞见一：Release = 应用的"集装箱集合" + 运行时**

一个 Release 包含 ：

1. **你的应用**（如 ppool、whatsapp）
    
2. **依赖的 OTP 应用**（kernel、stdlib、sasl 等）
    
3. **ERTS**（Erlang 运行时系统）——可选，用于自包含部署
    
4. **启动脚本**（.boot 文件）
    
5. **配置文件**（sys.config、vm.args）
    

**关键价值**：Release 是**自包含的**——它可以部署到一台没有安装 Erlang 的机器上，因为 ERTS 可以被打包进 release 。

> 💡 正如 Adopting Erlang 所言："Releases in Erlang are powerful—they bundle everything needed to run your application, even if Erlang isn't installed on the target system."

### Release vs 应用 vs 目标系统

OTP 官方明确了三个概念的区别 ：

|概念|含义|
|---|---|
|**Application**​|一个 OTP 应用（.app 文件 + 监督树 + 代码）|
|**Release**​|一个或多个应用 + OTP 子集 + 启动脚本|
|**Target System**​|Release 被转移到目标机器并安装后的形态|

**类比**：

- Application = 一个集装箱
    
- Release = 一艘货船（多个集装箱 + 动力系统 + 导航）
    
- Target System = 货船停靠在目的港口并准备起航

## 📝 小节二：发布资源文件（.rel 文件）—— 发布的"蓝图"

### .rel 文件的结构

OTP 官方文档给出的语法 ：

```
{release, {RelName, Vsn}, 
 {erts, EVsn}, 
 [{Application1, AppVsn1}, ... {ApplicationN, AppVsnN}]}.
```

**官方示例**（ch_rel-1.rel）：

```
{release, {"ch_rel", "A"}, 
 {erts, "14.2.5"}, 
 [{kernel, "9.2.4"}, 
  {stdlib, "5.2.3"}, 
  {sasl, "4.2.1"}, 
  {ch_app, "1"}]}.
```

### 关键约束

📌 **洞见二：.rel 文件的三条铁律**

**1. 必须包含 kernel 和 stdlib**​

> **"The minimal release based on Erlang/OTP consists of the Kernel and STDLIB applications, so these applications must be included in the list."**

**2. 如果要支持热升级，必须包含 sasl**​

> **"If the release is to be upgraded, it must also include the SASL application."**

**3. 文件命名**：`Name.rel`，其中 Name 是唯一名称

### 应用启动类型

.rel 文件中的每个应用可以指定启动类型 ：

```
{Application, AppVsn, Type}
```

|Type|行为|
|---|---|
|**permanent**​|加载并永久启动（默认）|
|**transient**​|加载并临时启动|
|**temporary**​|加载并临时启动|
|**load**​|仅加载，不启动|
|**none**​|不加载不启动，但模块代码可用|

📌 **洞见三：Type 字段控制"应用如何启动"**

这与 .app 文件的 `mod` 字段配合：

- `permanent` + 有 `mod` → 应用完全启动（构建监督树）
    
- `load` + 有 `mod` → 仅加载代码，不调用 `start/2`（库应用模式）
    
- `none` → 极端场景，仅代码可用

## 🚀 小节三：生成启动脚本 —— systools 的魔法

这是 Release 构建的核心步骤。OTP 的 `systools` 模块（SASL 应用的一部分）提供了构建工具 。

### 第一步：生成启动脚本

```
1> systools:make_script("ch_rel-1", [local]).
ok
```

**这条命令做了什么？**​

1. 读取 `ch_rel-1.rel` 文件
    
2. 读取每个应用的 `.app` 文件
    
3. 进行语法和依赖检查
    
4. 生成两个文件：
    
    - `ch_rel-1.script`：人类可读的启动脚本
        
    - `ch_rel-1.boot`：二进制启动脚本（运行时使用）
        
    

**`local` 选项的含义**​ ：

> **"local is an option that means that the directories where the applications are found are used in the boot script, instead of $ROOT/lib."**

**这是本地测试的利器**——启动脚本使用相对路径，方便开发调试。

### 第二步：启动 Release

```
% erl -boot ch_rel-1
Erlang/OTP 26 [erts-14.2.5] [64-bit] [smp:8:8] [ds:8:8:10] [async-threads:1] [jit]
Eshell V14.2.5 (press Ctrl+G to abort, type help(). for help)
1> application:which_applications().
[{ch_app,"Channel allocator","1"},
 {sasl,"SASL CXC 138 11","4.2.1"},
 {stdlib,"ERTS CXC 138 10","5.2.3"},
 {kernel,"ERTS CXC 138 10","9.2.4"}]
```

📌 **洞见四：启动脚本自动加载并启动所有应用**

`-boot ch_rel-1` 告诉 BEAM：按照 `ch_rel-1.boot` 脚本的指示，自动加载并启动所有声明的应用 。**你不需要手动 `application:start/1`**——启动脚本按正确顺序完成一切。

### 启动脚本的工作原理

Adopting Erlang 的解释极为清晰 ：

> **"Starting an Erlang release is similar to an operating system boot sequence that is followed by an init system starting services. An Erlang node starts by running instructions found in a boot file. The instructions load modules and start applications."**

**启动脚本的执行流程**：

```
1. 加载 kernel 应用（最先，因为它是基础设施）
2. 加载 stdlib 应用
3. 加载 sasl 应用（如果包含）
4. 加载你的应用 ch_app
5. 按依赖顺序启动应用：
   kernel → stdlib → sasl → ch_app
6. 每个应用的 start/2 被调用，构建监督树
7. 系统就绪
```

## 📦 小节四：创建发布包 —— 从"脚本"到"可部署单元"

### 第三步：打包为 tar 文件

```
1> systools:make_script("ch_rel-1").
ok
2> systools:make_tar("ch_rel-1").
ok
```

**生成的 `ch_rel-1.tar` 包含**​ ：

```
% tar tf ch_rel-1.tar
lib/kernel-9.2.4/ebin/kernel.app
lib/kernel-9.2.4/ebin/application.beam
...
lib/stdlib-5.2.3/ebin/stdlib.app
lib/stdlib-5.2.3/ebin/lists.beam
...
lib/sasl-4.2.1/ebin/sasl.app
...
lib/ch_app-1/ebin/ch_app.app
lib/ch_app-1/ebin/ch_app.beam
...
ch_rel-1.rel
ch_rel-1.boot  (renamed to start.boot)
```

📌 **洞见五：发布包 = 代码 + 配置 + 启动脚本**

发布包默认包含 ：

- 所有应用的 `.app` 文件
    
- 所有应用的 `.rel` 文件
    
- 所有应用的 object code（按应用目录结构组织）
    
- 二进制启动脚本（重命名为 `start.boot`）
    

**如果指定 `sys.config`，它会自动包含在发布包中**​

### 第四步：部署到目标系统

```
# 复制 tar 文件到目标机器
scp ch_rel-1.tar user@target-machine:/opt/

# 在目标机器上解压
ssh user@target-machine
cd /opt
tar xf ch_rel-1.tar

# 启动
./erts-14.2.5/bin/erl -boot ch_rel-1/start
```

**关键价值**：如果打包时包含了 ERTS（通过 `systools:make_tar/2` 的 `{erts, "/usr/local/lib/erlang"}` 选项），目标机器**不需要预装 Erlang**​

## 🔥 小节五：Release Handling —— 不停机热升级的终极武器

这是本章最震撼的部分，也是 Erlang "九个九可用性"的真正秘密。

### 热升级的整体框架

OTP 官方文档描述 ：

> **"Erlang 编程语言的一个重要特性是能够在运行时更改模块代码（代码替换）。基于此特性，OTP 应用 SASL 提供了一个框架，用于在运行时升级和降级整个 release 的不同版本。这就是我们所说的发布处理（release handling）。"**

**框架的两个组成部分**​ ：

1. **离线支持（systools）**：生成脚本、构建发布包
    
2. **在线支持（release_handler）**：解包和安装发布包
    

### 热升级的完整流程

```
开发环境                          目标系统
─────────                        ─────────
1. 修改代码
2. 更新 .app 文件版本号
3. 写新的 .rel 文件
4. 为每个改动的应用写 .appup 文件
5. 基于 .appup 生成 relup 文件
6. 创建新的发布包
7. 传输发布包到目标系统
        │
        │ scp new_release.tar
        ▼
8. release_handler:unpack_release/1
9. release_handler:install_release/1
   ├─ 评估 relup 中的指令
   ├─ 模块可能被添加、删除或重新加载
   ├─ 应用可能被启动、停止或重启
   └─ 必要时重启整个 emulator
10. 如果安装失败 → 系统重启 → 自动使用旧版本
11. 如果安装成功 → 新版本成为默认版本
```

📌 **洞见六：.appup 和 relup 是热升级的"说明书"**

**`.appup` 文件**（每个应用一个）：

```
{"2.0.0",
 "1.0.0",
 [{update, ch3, {advanced, []}, []}]}.
```

描述如何在 ch3 模块的 1.0.0 和 2.0.0 之间升级/降级。

**`relup` 文件**（整个发布一个）：

由 `systools:make_relup/3,4` 生成 ，基于所有 `.appup` 文件，描述如何在旧版本和新版本之间升级/降级。

### 热升级的安全性保证

OTP 官方文档明确 ：

> **"如果安装失败，系统可能重启。旧发布版本随后被自动使用。如果安装成功，新版本成为默认版本，在系统重启时应使用。"**

📌 **洞见七：热升级的"回滚机制"**

|阶段|行为|
|---|---|
|升级中|新代码逐渐加载，旧代码仍在运行|
|升级成功|新版本成为默认，旧版本保留作为回滚点|
|升级失败|系统重启，自动加载旧版本|
|显式回滚|`release_handler:install_release(OldVsn)`|

**这正是电信系统"全年停机不超过 4 分钟"的物理基础**——你可以升级代码，现有连接不断开，新连接用新代码，失败时自动回滚。

### 热升级的工程约束

OTP 官方警告 ：

> **"It is therefore recommended that code is changed in as small steps as possible, and always kept backwards compatible."**

**热升级的最佳实践**：

1. **小步修改**：每次升级改动尽量小
    
2. **向后兼容**：新代码必须能处理旧代码创建的状态
    
3. **避免循环依赖**：复杂的依赖关系会让升级顺序难以决定
    
4. **嵌入式启动**：必须使用嵌入式模式启动（`erl -embedded`），并启用心跳监控（`heart`）

## 🛠️ 小节六：现代工具链 —— Rebar3 与 relx

虽然 systools 是官方底层工具，但现代 Erlang 开发使用更友好的工具链。

### Rebar3 的 relx 配置

Adopting Erlang 展示了典型的 `rebar.config` ：

```
{relx, [
    {release, {service_discovery, {git, long}}, 
     [service_discovery_postgres, service_discovery, 
      service_discovery_http, service_discovery_grpc, recon]},
    {sys_config, "./config/dev_sys.config"},
    {vm_args, "./config/dev_vm.args"},
    {dev_mode, true},
    {include_erts, false},
    {extended_start_script, true}
]}.
```

### Rebar3 的发布命令

DeepWiki 总结了三个核心命令 ：

|命令|用途|
|---|---|
|`rebar3 release`|构建 release|
|`rebar3 relup --upfrom 0.0.1`|创建升级文件|
|`rebar3 tar`|打包为 tarball|

**`rebar3 release` 做了什么？**​ ：

1. 编译所有项目应用
    
2. 解析所有依赖
    
3. 根据 relx 配置生成发布文件
    
4. 创建启动脚本和相关文件
    
5. 在 `_build/<profile>/rel/` 目录下生成完整发布
    

📌 **洞见八：relx 让发布构建"简单到不再是负担"**

Adopting Erlang 的历史回顾 ：

> **"在早期 Erlang/OTP 中，只有 systools 和其从发布资源文件生成启动脚本的功能。那时，发布处理是一个手动过程，用户在其周围构建了自己的工具。然后出现了 reltool……虽然创建和安装目标系统从未在 sasl 应用之外提供示例模块。发布对许多用户来说仍然是神秘和困难的。relx 的创建目标是使发布创建和管理变得如此简单，用户不再觉得这是一个最好不去承担的负担。"**

**工具演化路径**：

```
systools（手动）→ reltool（GUI 工具）→ relx（现代化）→ rebar3 release（集成）
```

**与第十八、十九章（Application）的连接**：

|维度|Application|Release|
|---|---|---|
|交付物|.app 文件 + 监督树|.rel 文件 + 启动脚本 + 发布包|
|范围|单个应用|多个应用 + OTP 子集|

|升级|手动替换模块|通过 relup 自动热升级|

**Application 是 Release 的组成单元**。没有标准化的应用，就无法构建 release。

**与第二十章（分布式应用）的连接**：

- Release 是分布式应用部署的载体
    
- 一个 release 可以部署到多个节点

## ✍️ 读书笔记的核心收获

1. **Release 的定义**：把一个或多个应用与 Erlang/OTP 应用的一个子集打包成完整系统
    
2. **Target System**：Release 被转移到目标机器并安装后的形态
    
3. **.rel 文件的三条铁律**：
    
    - 必须包含 kernel 和 stdlib（最小发布）
        
    - 要支持热升级必须包含 sasl
        
    - 文件命名：`Name.rel`
        
    
4. **.rel 文件结构**：`{release, {Name, Vsn}, {erts, EVsn}, [{App, AppVsn}, ...]}`
    
5. **应用启动类型**：permanent / transient / temporary / load / none
    
6. **systools:make_script/1,2**：生成启动脚本（.script 可读 + .boot 二进制）
    
7. **local 选项**：使用相对路径，便于本地测试
    
8. **启动 Release**：`erl -boot ch_rel-1` 自动加载并启动所有应用
    
9. **systools:make_tar/1,2**：创建发布包（tar 文件）
    
10. **发布包内容**：.app 文件、.rel 文件、object code、start.boot
    
11. **自包含部署**：包含 ERTS 的 release 可部署到无 Erlang 的机器
    
12. **Release Handling 的两部分**：
    
    - 离线：systools 生成脚本和发布包
        
    - 在线：release_handler 解包和安装
        
    
13. **热升级流程**：
    
    - 修改代码 → 更新 .app 版本 → 写新 .rel → 写 .appup → 生成 relup → 创建新发布包 → 传输到目标 → unpack → install
        
    
14. **.appup 文件**：描述单个应用在版本间的升级/降级方式
    
15. **relup 文件**：描述整个 release 在版本间的升级/降级方式
    
16. **热升级的安全性**：
    
    - 升级失败 → 系统重启 → 自动使用旧版本
        
    - 升级成功 → 新版本成为默认
        
    - 显式回滚：`release_handler:install_release(OldVsn)`
        
    
17. **热升级的工程约束**：
    
    - 小步修改
        
    - 保持向后兼容
        
    - 嵌入式启动 + 心跳监控
        
    
18. **现代工具链**：
    
    - systools（底层官方工具）
        
    - reltool（历史 GUI 工具）
        
    - relx（现代化工具）
        
    - rebar3 release（集成 relx）
        
    
19. **Rebar3 三个核心命令**：`rebar3 release` / `rebar3 relup` / `rebar3 tar`
    
20. **启动脚本的执行流程**：类似操作系统启动——加载模块，按依赖顺序启动应用
