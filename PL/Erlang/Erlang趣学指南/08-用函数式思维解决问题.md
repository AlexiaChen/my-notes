## 🧮 小节一：逆波兰表达式计算器——"数据即协议，递归即引擎"

### 问题本质

逆波兰表达式（RPN）也叫后缀表达式：`2 3 +` 表示 `2+3`，`2 3 + 4 *` 表示 `(2+3)*4`。

命令式语言的解法是：用一个栈，遍历 token 列表，遇到数字压栈，遇到运算符弹出栈顶两个元素计算后压回。这需要**可变栈**和**循环**。

但在 Erlang 里：

- 变量不可变 → 不能用"压栈/弹栈"修改同一个栈
- 没有循环 → 必须用递归
- 列表是递归数据结构 → 天然适合递归遍历
    
### Erlang 的解法骨架

Fred 给出的核心解法是一个递归函数，参数为"剩余的 token 列表"和"当前的栈"：

```
rpn([], [Result]) -> Result;
rpn([Token | Rest], Stack) ->
    case Token of
        Op when Op =:= '+' -> 
            [B, A | RestStack] = Stack,
            rpn(Rest, [A + B | RestStack]);
        Op when Op =:= '*' -> 
            [B, A | RestStack] = Stack,
            rpn(Rest, [A * B | RestStack]);
        Num when is_number(Num) -> 
            rpn(Rest, [Num | Stack])
    end.
```

📌 **洞见一：栈不是"可变数据结构"，是"递归的第二个参数"**

这是本章第一个震撼教育：

|命令式思维|Erlang 思维|
|---|---|
|栈是可变的，`push`/`pop` 修改它|栈是不可变的，每次递归传入"新栈"|
|循环遍历 token 列表|递归遍历，每次处理一个 token|
|循环变量记录"当前位置"|递归参数 `Rest` 是"剩余未处理的 token"|
|最终结果是栈顶|最终结果是递归的归约值|

**栈在 Erlang 里不是一个"东西"，而是递归调用的一个参数**。每次"压栈"实质上是"用 `[Num | Stack]` 构造一个新列表作为下一次递归的栈参数"；每次"弹栈"实质上是"`[B, A | RestStack] = Stack` 的模式匹配解构"。

> 💡 这就是第五章我们学到的"尾递归 + 累加器"惯用法——Stack 就是累加器，Rest 就是"剩余工作"。尾递归优化保证无论表达式多长，栈空间恒定。

📌 **洞见二：模式匹配是"天然的语法分析器"**

注意 `case Token of` 这一层——

```
case Token of
    '+' -> ...;
    '*' -> ...;
    Num when is_number(Num) -> ...
end.
```

**token 的类型直接决定了分支走向**。这正是第三章我们学到的"模式匹配 + 守卫"的威力：

- `'+'` 是原子模式，匹配加法运算符
- `Num when is_number(Num)` 是变量+守卫，匹配数字
- 不匹配任何子句？→ `case_clause` 异常 → 进程崩溃 → 监督树重启

**错误输入不需要"防御性检查"**——它要么被某个子句匹配并处理，要么触发 `case_clause` 崩溃。这就是第七章"let it crash"的落地：语法错误的输入就让进程崩溃，让监督者决定如何响应。

📌 **洞见三：函数式子句可以取代 case**

Fred 在书中还展示了另一种写法——**把 case 提升为函数多子句**：

```
rpn([], [Result]) -> Result;
rpn(['+' | Rest], [B, A | Stack]) -> rpn(Rest, [A + B | Stack]);
rpn(['*' | Rest], [B, A | Stack]) -> rpn(Rest, [A * B | Stack]);
rpn([Num | Rest], Stack) when is_number(Num) -> rpn(Rest, [Num | Stack]).
```

**这是第三章"函数头即协议"理念的极致运用**：

- 函数头直接解构 token 列表：`['+' | Rest]` 匹配"头是加法运算符"
- 函数头直接解构栈：`[B, A | Stack]` 匹配"栈至少有两个元素"
- 多个子句按自上而下的顺序匹配
- 不符合任何子句的输入 → `function_clause` 异常 → 崩溃
    
> 💡 **两种写法本质相同，但第二种更 Erlang 化**：它把"语法分析"完全交给函数头的模式匹配，函数体只做"纯粹的计算"。这符合 Erlang 的哲学——**让模式匹配承担所有"分支判断"，让函数体保持纯净**。

📌 **洞见四：高阶函数的潜在抽象**

如果运算符越来越多（加减乘除、sin、cos、log...），上面的代码会出现大量重复：

```
rpn(['+' | Rest], [B, A | Stack]) -> rpn(Rest, [A + B | Stack]);
rpn(['-' | Rest], [B, A | Stack]) -> rpn(Rest, [A - B | Stack]);
rpn(['*' | Rest], [B, A | Stack]) -> rpn(Rest, [A * B | Stack]);
%% ... 每个运算符都要写一遍
```

**第六章的高阶函数思想在这里闪光**——我们可以把"运算符 → 计算函数"的映射抽出来：

```
operator_fun('+') -> fun(A, B) -> A + B end;
operator_fun('-') -> fun(A, B) -> A - B end;
operator_fun('*') -> fun(A, B) -> A * B end.

rpn([Op | Rest], [B, A | Stack]) ->
    Fun = operator_fun(Op),
    rpn(Rest, [Fun(A, B) | Stack]).
```

**这就是函数式思维的精髓**：识别重复模式，把"变化的部分"（运算符对应的计算）参数化为 fun，把"不变的部分"（解构栈、递归）留在框架里。这种抽象思维在第十四章 OTP 的 `gen_server` 里会被放大——`gen_server` 框架处理"消息接收、状态维护、递归循环"等不变的部分，用户只需提供 `handle_call/3`、`handle_cast/2` 等"变化的部分"。

## 🛣️ 小节二：希思罗机场到伦敦——递归遍历问题空间

### 问题本质

这是一道经典的最短路径题：从希思罗机场到伦敦市区，有 A、B 两条平行道路，中间有多个交叉点相连。在每个交叉点，你可以选择：

1. **继续走 A 路**（代价 A 路段）
2. **继续走 B 路**（代价 B 路段）
3. **从 A 切换到 B**（代价 切换路段）
4. **从 B 切换到 A**（代价 切换路段）

目标：找到从起点到终点的最小总代价路径。

### 问题建模：递归数据结构

Fred 的第一步是把问题**建模为递归数据结构**——这是函数式解题的关键：

```
-type road() :: {A :: integer(), B :: integer(), Cross :: integer()}.
%% 一段路：A 路段代价、B 路段代价、切换路段代价
```

一条完整的路径是 `road()` 的列表：`[{A1,B1,X1}, {A2,B2,X2}, ..., {An,Bn,Xn}]`。

📌 **洞见五：先建数据模型，再写算法**

这与命令式编程形成鲜明对比：

|命令式思维|Erlang 函数式思维|
|---|---|
|先想"循环怎么写"|先想"数据怎么表示"|
|用数组+下标遍历|用递归数据结构+模式匹配|
|变量记录"当前最优"|递归归约出最优解|

**Erlang 的解题顺序是：数据模型 → 递归结构 → 模式匹配 → 归约**。这与第一章"变量不可变"、第三章"函数头即协议"一脉相承——**数据的形状决定了函数的形状**。

### 递归解法骨架

Fred 给出的核心解法：

```
%% 主函数：从路段列表归约出最小代价
shortest_path(Roads) -> shortest_path(Roads, 0, 0, []).

%% 基础情况：路走完了，返回当前代价和路径
shortest_path([], TotalA, TotalB, Path) ->
    case TotalA < TotalB of
        true -> {TotalA, lists:reverse(Path)};
        false -> {TotalB, lists:reverse(Path)}
    end;

%% 递归情况：处理当前路段
shortest_path([{A, B, Cross} | Rest], TotalA, TotalB, Path) ->
    %% 选项1：继续在 A 路
    NewTotalA1 = TotalA + A,
    NewTotalB1 = TotalB,
    Path1 = [{a, A} | Path],
    
    %% 选项2：继续在 B 路
    NewTotalA2 = TotalA,
    NewTotalB2 = TotalB + B,
    Path2 = [{b, B} | Path],
    
    %% 选项3：从 A 切到 B
    NewTotalA3 = TotalA + Cross,
    NewTotalB3 = TotalB,
    Path3 = [{cross_a_to_b, Cross} | Path],
    
    %% 选项4：从 B 切到 A
    NewTotalA4 = TotalA,
    NewTotalB4 = TotalB + Cross,
    Path4 = [{cross_b_to_a, Cross} | Path],
    
    %% 选择最小代价，继续递归
    %% ... 比较四个选项，选最小的继续
    shortest_path(Rest, MinTotalA, MinTotalB, MinPath).
```

📌 **洞见六：穷举 + 归约 = 递归的威力**

这个问题的本质是**决策树**：在每个路段，有 4 个选项，n 个路段就有 4^n 条可能路径。朴素的穷举是指数级的。

但 Fred 的解法展示了函数式编程的一个深刻洞察——**在很多问题中，"局部最优"可以归约为"全局最优"**：

- 走到第 k 个路段时，只需要知道"在 A 路的最小代价"和"在 B 路的最小代价"
- 这两个值就是归约的状态
- 每处理一个路段，状态更新一次
- 最终状态就是答案
    
**这就是动态规划的函数式表达**：状态作为递归参数传递，每次递归"消费"一个输入、更新状态、传递下去。

📌 **洞见七：尾递归保证工业级可靠**

注意 `shortest_path/4` 是**尾递归**——递归调用是函数体最后做的事。这意味着：

- 无论道路有多长（100 个路段？10000 个路段？），栈空间恒定
- BEAM 的 LCO 优化把它变成机器层面的循环
- 这与 RPN 计算器的 `rpn/2` 是同一类模式
    
**两个例题，同一种底层机制**——尾递归 + 累加器。这不是巧合，这是 Erlang 函数式解题的标准范式：

```
输入数据（递归结构）
    ↓
递归遍历，每次处理一个元素
    ↓
更新累加器状态
    ↓
递归调用自身（尾位置）
    ↓
基例返回最终结果
```

> 💡 这个范式在第十章之后会被放大为**进程的事件循环**：`receive` 消息 → 更新状态 → 尾递归调用自身。RPN 计算器是"遍历 token 列表"，事件循环是"遍历消息队列"——**本质相同**。

📌 **洞见八：Path 的构建与反转技巧**

Fred 在构建路径时用的是 `[{a, A} | Path]`——**每次把新决策压在列表头部**。这是因为：

- 向列表头部添加元素是 O(1) 的
- 向列表尾部添加元素是 O(n) 的（需要遍历整个列表）
    
所以 Path 在递归过程中是**逆序**构建的，最后用 `lists:reverse/1` 一次性反转。这是第五章我们学到的"列表构建反转技巧"——尾递归构建列表时自然逆序，最后 `lists:reverse/1` 反转。

**这是 Erlang 函数式解题的标准惯用法**：

```
%% 标准模式
solve(List) -> solve(List, []).  %% 初始化累加器为空列表
solve([], Acc) -> lists:reverse(Acc);  %% 最后反转
solve([H | T], Acc) -> solve(T, [transform(H) | Acc]).  %% 头部构建
```

### 与前七章的深度连接

**与第一章（不可变）的连接**：

- 栈不可变 → 每次递归传入新栈
- 变量不可变 → 状态必须通过递归参数传递
- **不可变性逼出了"状态即参数"的范式**

**与第三章（函数语法）的连接**：

- RPN 计算器的 `case Token of` 是模式匹配+守卫
- 升级版的函数多子句把模式匹配提升到函数头
- **函数头解构数据 = 语法分析的代数化**
    
**与第五章（递归）的连接**：

- RPN 计算器：`rpn(Rest, [Num | Stack])` 是尾递归
- 路径问题：`shortest_path(Rest, TotalA, TotalB, Path)` 是尾递归
- **两个例题都是"尾递归 + 累加器"的标准范式**
    
**与第六章（高阶函数）的连接**：

- RPN 计算器中，`operator_fun/1` 返回 fun，抽象了"运算符→计算"
- 路径问题中，可以把"决策函数"参数化
- **高阶函数是消除重复的利器**
    
**与第七章（错误和异常）的连接**：

- RPN 计算器中，非法 token 触发 `case_clause` 或 `function_clause` → 崩溃
- 路径问题中，空输入等边界情况由基例处理
- **let it crash 不是被动接受，是主动设计错误边界**
    
### 与后续并发章节的直接连接

第十章你会学到 `spawn` 和 `receive`——**进程的事件循环就是第八章 RPN 计算器的放大版**：

```
%% RPN 计算器（顺序版）
rpn([], [Result]) -> Result;
rpn([Token | Rest], Stack) -> 
    %% 处理一个 token
    rpn(Rest, NewStack).

%% 进程事件循环（并发版）
server_loop(State) ->
    receive
        {call, From, Request} ->
            NewState = handle_call(Request, From, State),
            server_loop(NewState);  %% 尾递归！
        {cast, Msg} ->
            NewState = handle_cast(Msg, State),
            server_loop(NewState)   %% 尾递归！
    end.
```

**结构完全一致**：

|RPN 计算器|进程事件循环|
|---|---|
|输入：token 列表|输入：消息队列|
|状态：栈|状态：ServerState|
|基例：列表为空|终止条件：收到 stop 消息|
|递归：处理一个 token|递归：处理一条消息|
|尾递归：栈空间恒定|尾递归：进程永生|

> 💡 **这就是第八章最深的洞见**：函数式解题的范式与并发进程的范式**同构**。你在本章学到的"递归遍历+状态累加+尾递归"，直接迁移到第十章的"消息处理+状态更新+事件循环"。**Erlang 的函数式顺序编程，是为并发编程做准备的**。

### 与 OTP 的直接连接

第十四章 `gen_server` Behaviour 的本质，就是 RPN 计算器"框架+回调"模式的工程化：

```
%% RPN 计算器框架
rpn(Tokens) -> rpn(Tokens, []).
rpn([], [Result]) -> Result;
rpn([Token | Rest], Stack) ->
    %% "框架"处理遍历和栈管理
    %% "回调"是运算符对应的计算
    NewStack = apply_operator(Token, Stack),  %% 回调
    rpn(Rest, NewStack).

%% gen_server 框架
gen_server:start_link(CallbackModule, Args, Options) ->
    %% "框架"处理消息接收、状态维护、事件循环
    %% "回调"是 CallbackModule:init/1, handle_call/3, handle_cast/2...
    spawn(fun() -> init_and_loop(CallbackModule, Args) end).
```

**Fred 在第八章其实已经教你写了"迷你 gen_server"**——你只是还没意识到而已。RPN 计算器的"遍历框架"对应 `gen_server` 的"消息循环框架"，运算符处理对应 `handle_call/3` 回调。

## ✍️ 读书笔记的核心收获

1. **函数式解题四步法**：
    
    - **建数据模型**：用元组、列表、tagged tuple 表示问题
    - **找递归结构**：数据如何递归定义？基例是什么？
    - **写递归函数**：模式匹配解构 + 守卫验证 + 尾递归+累加器
    - **处理边界**：非法输入触发异常（let it crash），由监督树恢复
        
2. **栈不是"可变数据结构"，是"递归的第二个参数"**：RPN 计算器把栈作为递归参数传递，每次"压栈"是构造新列表
3. **模式匹配是"天然的语法分析器"**：`case Token of` 或函数多子句直接对应语法规则
4. **函数多子句优于 case**：把"语法分析"完全交给函数头的模式匹配，函数体保持纯净
5. **高阶函数消除重复**：RPN 计算器中，`operator_fun/1` 把"运算符→计算"抽象为 fun
6. **先建数据模型，再写算法**：Erlang 的解题顺序是"数据模型 → 递归结构 → 模式匹配 → 归约"
7. **尾递归 + 累加器是标准范式**：
    
    ```
    solve(List) -> solve(List, []).
    solve([], Acc) -> lists:reverse(Acc);
    solve([H | T], Acc) -> solve(T, [transform(H) | Acc]).
    ```
    
1. **Path 构建用反转技巧**：头部构建 O(1)，最后 `lists:reverse/1` 反转
2. **函数式解题与并发进程同构**：
    
    |  RPN 计算器 | 进程事件循环 |
    | --- | --- |
    |输入 token 列表|输入 消息队列|
    |状态 栈|状态 ServerState|
    |尾递归遍历|尾递归事件循环|
    
3. **第八章 = 迷你 gen_server**：RPN 计算器的"框架+回调"模式，在第十四章被工程化为 OTP Behaviour
    
4. **let it crash 在解题中的落地**：非法 token 触发 `case_clause` 或 `function_clause` → 进程崩溃 → 监督树重启。**错误边界是主动设计的，不是被动防御的**
    
5. **引用透明性的威力**：因为函数对同一输入永远返回同一输出（无副作用），所以可以放心地组合、抽象、复用。博客园的文章指出——"当一个函数的参数不变时，总是返回相同的值，这是 Erlang 的引用透明性。基于这个原则，可以把许多函数组合起来解决复杂的问题"
    

> 💡 **贯穿全书的隐喻再进化**：Erlang 的函数式解题心智可以总结为——
> 
> **"把世界看作递归的数据，把算法看作数据的归约。"**
> 
> - 数据是不可变的 → 算法只能是"从输入数据归约出输出数据"
>     
> - 数据是递归的 → 算法只能是递归的
>     
> - 函数是一等的 → 算法中可以参数化"变化的部分"
>     
> - 错误是不可避免的 → 让错误快速崩溃，由架构恢复
>     
> 
> **这种心智模型不仅是"如何写函数"，更是"如何设计系统"**。当你用函数式思维解 RPN 计算器时，你其实在练习：如何把"不变的逻辑"与"变化的数据"分离、如何把"遍历框架"与"业务回调"分离、如何用尾递归让程序永生。
> 
> 这些练习在第十章之后会显现出巨大价值——**并发进程就是"递归遍历消息队列的函数"，OTP 就是"工程化的高阶函数框架"，监督树就是"自动化的错误恢复"**。第八章是"函数式思维"与"并发架构思维"之间的桥梁。
