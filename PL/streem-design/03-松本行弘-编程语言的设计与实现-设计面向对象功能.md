
# 第3章读书笔记：设计面向对象功能

> 💡 第二章结束时，Streem 已经是一门能跑的、以管道和流为核心的函数式语言——所有数据不可变，计算靠 `产生器 | 过滤器 | 消费者` 完成。这时候抛出一个尖锐问题：**这样一门"以流为计算模型的函数型语言"，还需要面向对象吗？**​ 第三章就是 Matz 对这个问题的正面回应：不是"要不要 OOP"，而是"要哪一种 OOP，以及它如何与流模型共处"。

## 全局定位：第三章是全书的"范式调和"章

把五章串起来看，第三章处在一个微妙的转折点上：

|章节|核心命题|范式立场|
|---|---|---|
|第1章|造一门什么样的语言|设计世界观确立|
|第2章|Streem 原型落地|**函数式 + 流**（不可变、管道、emit/skip/return）|
|**第3章**​|**设计面向对象功能**​|**流 + 轻量对象模型 的调和**​|
|第4章|实现 Streem 的对象|对象表示的工程兑现|
|第5章|强化流编程|回到流，深化流|

Matz 自己说得很清楚：**"Ruby 是面向对象的语言，Streem 是以流为计算模型的函数型语言"**。这两句话放在一起，就是第三章真正的张力所在——作者本人是 OOP 语言（Ruby）的创造者，但他亲手造的新语言却主动选择了函数型范式。这不是否定 OOP，而是一次**有意识的范式降级与重构**：OOP 太重，不适合流导向；但完全丢掉对象又会让语言失去组织复杂性的能力。

第三章四个小节（3-1 各种各样的面向对象 / 3-2 Streem 的面向对象 / 3-3 再看 Streem 的语法 / 3-4 模式匹配）恰好是一条完整的思维链：**先开阔视野看 OOP 的全谱系 → 再为 Streem 选定一个轻量的对象模型 → 然后回头修正语法 → 最后用模式匹配补足函数式表达力**。

## 洞见一：OOP 不是一个东西，而是一整个光谱

3-1"各种各样的面向对象"看似是基础科普，实则是为 3-2 的 Streem 决策做"选项盘点"。Matz 在《日经Linux》连载时的真实意图，是要让读者意识到：**当人们说"面向对象"时，他们说的可能是完全不同的东西**。

从谱系上看，OOP 至少有这样几条分化轴：

- **类基础 vs 原型基础**：Java/C++ 走类路线，JavaScript/Self 走原型路线。类基础强调分类与继承层级，原型基础强调对象间的克隆与委托。
- **单一继承 vs 多重继承**：C++ 允许多重继承，Java 退回到单继承+接口，Ruby 用 mixin 模块调和。
- **消息传递 vs 方法调用**：Smalltalk 视角下"一切皆消息"，Java 视角下"一切皆方法分发"。
- **状态可变 vs 状态不可变**：传统 OOP 允许对象内部状态变更，这与并发编程从根本上冲突。
    
> 🎯 **洞见**：这一节的真正价值，是揭示了一个被业界长期模糊处理的真相——**"支持 OOP"从来不是一个二元开关，而是一组连续的设计选择**。当你说一门语言"是 OOP 的"，你必须追问：是哪一种 OOP？

这个追问在 Streem 的语境下尤为致命。因为在 GitHub 上 Streem 仓库的早期讨论中，就有人直接问 Matz："Streem 会支持 class/method/inheritance 吗？" Matz 的回答非常坦白：

> ⚠️ **"我不认为 OOP 有利于面向流编程。我原则上不反对 OOP，事实上我喜欢 Ruby，但在这个上下文里，OOP 会感觉像是生硬拼接上去的。Objects、Methods、Properties 并不适合帮助你以过滤、映射、转换这种流导向的方式思考。这就是为什么更原型化、更函数式的方案在这种情况下可能更好。"**

这话等于直接宣判：传统类基础的 OOP 在 Streem 里**不会**以 Java 那种形态出现。第三章的"设计面向对象功能"，设计的其实是**一种被流范式改造过的、轻量的、原型化的对象机制**。

## 洞见二：Streem 的 OOP 是"被流改造过的 OOP"

3-2"Streem 的面向对象"是本章的核心决策点。结合 Matz 的自述和 Streem 仓库讨论，可以还原出他的真实取向：

**为什么不用类基础的 OOP？**

- 类基础 OOP 的核心是"分类+继承"，这套思维与"数据流经管道被转换"的流模型在认知上不匹配
- 类基础 OOP 通常伴随可变状态（对象属性可改），这与 Streem 第二章确立的"所有数据不可变"铁律正面冲突
- 继承层级在流处理场景下几乎无用武之地——你不会对"流"做分类学
    
**为什么不完全抛弃对象？**

- 流本身在 Streem 里就是对象：`STDIN`、`STDOUT`、`read(path)`、`write(path)` 返回的流对象，`tcp_server(8007)` 返回的服务器端 Socket 流对象
- 数组、Map、函数表达式、Symbol——这些第二章已经引入的复合数据类型，本质上都需要对象模型来承载
- 标准库的组织、方法的调用（`ary.push(2)`、`map.get(word, 0)`），都需要某种对象机制
    
**Streem 的实际选择：轻量原型 + 函数式**

Matz 在讨论中明确倾向：**"原型化是 OOP 的一种轻量版本，你仍然可以用那种方式编程 Streem，而函数式天生适合基于列表/流的程序（看看 Lisp 和 Haskell 就知道）"**。

这意味着 Streem 的 OOP 大致是这样的形态：

- **对象存在，但没有沉重的类层级**
- **方法调用存在（`expr.method(args)`），但方法不改变对象内部状态**（因为不可变）
- **更接近原型模型而非类模型**——对象可以直接作为对象使用，而不必先声明类
- **函数式是一等公民**：`map`、`filter`、`reduce` 这类高阶函数比"对象+方法"更常用
    
> 💡 **洞见**：Streem 的 OOP 设计，本质上是一次**"OOP 的瘦身手术"**——保留对象作为组织单元的能力，去掉类层级、去掉可变状态、去掉继承带来的复杂性，让对象以一种"轻量原型"的姿态服务于流模型。
> 
> 这是对"一切皆对象"（Ruby 的哲学）的一次**刻意背离**。Matz 没有试图让 Streem 成为另一门 Ruby，而是让 Streem 成为 Ruby 的"函数式+流"兄弟——两者共享"对象作为基础数据单元"的理念，但在范式权重上完全不同：**Ruby 是 OOP 为主、函数式为辅；Streem 是函数式+流为主、轻量对象为辅**。

## 洞见三：语法是被实现倒逼着修订的

3-3"再看 Streem 的语法"是全书最具"工程真实感"的一节。从连载时间表可以看出关键线索：

|连载时间|主题|本书章节|
|---|---|---|
|2015年6月刊|AST|2-7|
|2015年8月刊|局部变量与异常处理|2-8|
|**2015年10月刊**​|**CSV**​|**5-3**​|
|**2015年11月刊**​|**基本数据结构**​|**4-2**​|
|**2015年12月刊**​|**各种各样的面向对象**​|**3-1**​|
|**2016年1月刊**​|**Streem 的面向对象**​|**3-2**​|
|**2016年8月刊**​|**再看 Streem 的语法**​|**3-3**​|
|**2016年9月刊**​|**模式匹配**​|**3-4**​|

注意一个反直觉的事实：**3-3"再看 Streem 的语法"在连载中排到第 29 期（2016年8月），而 3-1/3-2 排在 2015年12月/2016年1月**——也就是说，Matz 在 2015 年底初步确定了 Streem 的面向对象取向后，经过大半年（期间穿插了 CSV、基本数据结构、对象表示与 NaN Boxing、垃圾回收、管道编程、管道的组成要素、无锁算法、时间表示、统计基础等主题的实现），到 2016 年 8 月才"再看 Streem 的语法"。

这说明什么？

> 📌 **语法不是先于实现确定的，而是被实现过程倒逼着反复修订的**。第二章 2-7 的 AST 实现阶段暴露出的 shift/reduce conflict 等问题，到第三章才得到系统性的语法再设计。这是一种非常健康的工程节奏：**先让语言跑起来，再在真实实现中观察语法哪里别扭，然后回炉重造**。

从已知的材料可以推断，"再看 Streem 的语法"至少涉及：

- 面向对象引入后，方法调用语法、对象字面量语法如何与现有管道语法协调
- 模式匹配语法（3-4）的引入对整体语法的影响
- 可能出现的 break 语句删除、if 语句修改、右侧赋值增加等调整（这些在第二章 AST 实现时已被提及需要修正）
    
## 洞见四：模式匹配是函数式流语言的"自然补完"

3-4"模式匹配"放在第三章结尾，绝非偶然。它与 3-2 的"函数式取向"形成呼应——**模式匹配是函数式语言（ML、Haskell、Scala、Erlang）的标志性特性**，而在以流为计算模型的 Streem 里，模式匹配有着极其自然的用武之地：

- **解构流数据**：当流中的元素是复合数据结构（数组、Map、对象）时，模式匹配可以一次性提取出内部结构
- **分支处理不同形状的数据**：在过滤器 `{ |x| ... }` 中，根据 x 的形状选择不同处理逻辑
- **与不可变性天然契合**：模式匹配创建的是新绑定，不修改原数据，完美符合 Streem 的不可变约束
    
> 🎯 **洞见**：把 3-4 模式匹配与 3-2 Streem 的面向对象合起来看，Matz 的真正意图是——**用函数式的模式匹配，替代 OOP 中用多态+继承来做的"分派"**。在传统 OOP 里，你靠虚方法表+继承层级来实现"对不同类型做不同处理"；在函数式+模式匹配的范式里，你靠对数据形状的解构来做同样的事，而且更显式、更安全、更符合不可变约束。

这是第三章最深的洞见：**Streem 不是"加了 OOP 的函数式语言"，而是"用函数式手法重写了 OOP 要解决的核心问题"**。对象仍然存在（作为数据组织单元），但"对象能干嘛"不再靠类层级和方法重写，而是靠模式匹配 + 高阶函数 + 流转换来表达。

## 联系脉络：第三章 → 全书各章的暗线

把第三章放回全书架构，能看到一条非常清晰的"范式调和"主线：

```
第1章：设计世界观
   │
第2章：Streem 原型（函数式 + 流 + 不可变）
   │
第3章：设计面向对象功能 ← 你现在在这里
   │   │
   │   ├─ 3-1 各种各样的 OOP → 盘点选项，确立"OOP 是一个光谱"
   │   │
   │   ├─ 3-2 Streem 的 OOP → 选定"轻量原型 + 函数式"路线
   │   │       │
   │   │       ↓ 直接驱动
   │   │
   │   ├─ 3-3 再看 Streem 的语法 → 语法修订（衔接第2章 AST 暴露的问题）
   │   │       │
   │   │       ↓ 语法确定后，进入对象表示的实现
   │   │
   │   └─ 3-4 模式匹配 → 函数式补完（衔接第5章流处理的表达力）
   │
   ↓ 第三章做出的"轻量对象模型"决策，直接定义第四章的实现目标
   │
第4章：实现 Streem 的对象（4-2 基本数据结构 / 4-3 对象表示与 NaN Boxing / 4-4 垃圾回收 / 4-5 无锁算法）
   │   第四章要实现的"对象"，就是第三章定义的"轻量、不可变、函数式友好"的对象
   │
   ↓ 对象模型稳定后，回到流模型的深化
   │
第5章：强化流编程（管道、CSV、时间、统计、随机数、数据流图）
       第五章的流处理能写得如此简洁，正是因为第三章解决了"流中流动的数据如何被组织为对象"
```

特别值得注意的是 **第三章与第四章的因果链**：3-2 做出了"Streem 用轻量对象模型"的设计决策，4-2 到 4-5 才据此实现基本数据结构、对象表示、GC、无锁算法。**没有第三章的设计决策，第四章的实现就失去了方向**；反过来，第四章实现中遇到的工程约束（比如 NaN Boxing 对对象表示的限制），又可能倒逼第三章的语法再调整。这种"设计 ↔ 实现"的双向反馈，正是 Matz 在《日经Linux》上连载三年（2014年4月 - 2016年12月）的真实节奏。

## 一句贯穿本章的洞见

> ⚠️ **真正的大师不是"选择一种范式并坚守到底"，而是"清楚每一种范式的代价，并为特定的计算模型定制最合适的范式组合"。**
> 
> Matz 在第三章展示的，是一位语言设计者在面对"我自己创造的 Ruby 就是 OOP 语言，但现在我要造的 Streem 是以流为计算模型的函数型语言"这一身份张力时，做出的清醒抉择：**不因为自己是 OOP 之父就强行给 Streem 加类，也不因为追时髦就彻底抛弃对象**。
> 
> 他做的是一次精密的范式解剖——把 OOP 拆解为"对象作为数据单元 / 类层级 / 继承 / 方法分发 / 可变状态"等组件，然后**只保留对流模型有用的部分（对象作为数据单元、方法调用语法），丢弃不兼容的部分（类层级、继承、可变状态），并用函数式的模式匹配和高阶函数来替代被丢弃部分的功能**。
> 
> 这种"范式杂交"的能力，才是语言设计者最稀缺的素养。大多数语言要么纯 OOP（Java）、要么纯函数式（Haskell）、要么纯原型（早期 JavaScript），而 Streem 尝试的是一种更精细的范式配方——**为"流"这一特定计算模型，定制"轻量对象 + 函数式 + 模式匹配"的专属组合**。
> 
> 这正是第三章最值得记入读书笔记的洞见：**编程语言的设计，本质上不是"选哪个范式"，而是"为你的计算模型，从所有范式中萃取最匹配的组件，并让它们和谐共处"**。
