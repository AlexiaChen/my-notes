
# 第2章读书笔记：新语言 Streem 的设计与实现

> 💡 如果说第1章回答的是"创造一门什么样的语言"，那么第2章就是**把这个问题从理念层面拽到工程层面**：如何从一个抽象的并发计算模型出发，一步步搭出一个能跑的原型语言处理器。本章八个小节（2-1 抽象的并发编程 / 2-2 新语言 Streem / 2-3 首先开发语法检查器 / 2-4 事件循环 / 2-5 多线程与对象 / 2-6 缓存与符号 / 2-7 转换为抽象语法树 / 2-8 局部变量与异常处理），本质上是一条"设计意图 → 原型实现 → 迭代深化"的真实开发流水账。

## 全局定位：第二章在全书的枢纽地位

把五章串起来看，第二章是**全书最硬核的"实现篇"开篇**：

|维度|第1章|第2章|第3-5章|
|---|---|---|---|
|焦点|设计世界观|**Streem 原型落地**​|面向对象、对象表示、流编程强化|
|抽象层级|概念与架构|**原型与迭代**​|特性深化|
|关键动作|确立意图|**做出能跑的东西**​|往原型里填血肉|

Matz 在访谈里说得很直白：他不想重复造 Ruby 的轮子，于是决定**尝试新方法**——以流（Stream）为计算模型，开发专门处理数据的语言，把过去 Shell 脚本能做的事大规模开展起来，顺应多核时代的需要。第二章就是这场"尝试"的工程记录。

## 洞见一：并发不应由程序员显式管理，而应由语言模型默认提供

2-1"抽象的并发编程"是整个第二章乃至整本书的**设计原点**。Matz 观察到：随着多核 CPU 普及，Shell 脚本基于管道连接多进程的计算模型被重新认识——只要计算模型选得合适，并发执行可以非常自然地实现。

但他同时指出 Shell 的两个硬伤：

- **进程创建成本高**，大量轻量处理时性能崩盘
- **管道只能传字节流**，CSV/JSON 等结构化数据的序列化/反序列化开销不可忽视
    
由此引出 Streem 的三个设计必要条件：

1. **轻量并发**：在一个 OS 进程内预开与 CPU 核数相当的线程，让它们轮番执行"任务"（task）——相当于 Erlang 的 process、Go 的 goroutine
2. **消除竞争条件**：所有数据不可变（immutable），从根上消灭"状态变更 × 执行时机"带来的 bug
3. **高抽象度的计算模型**：借鉴 Shell 的管道模型，抽象度高 → 自由度降低 → 但**极易调试**
    
> 🎯 **洞见**：Matz 在这里做了一个非常反主流的判断——**21 世纪的并发语言不应该让程序员"手动管理线程和锁"，而应该把并发藏进计算模型里**。Streem 选择"流"作为这个模型：数据像水一样从生产者流向过滤器再流向消费者，并发是这种模型的天然副产品，而不是程序员要显式申请的东西。
> 
> 这一点直接区别于 Go（goroutine + channel 仍需显式并发原语）、Java（线程 + synchronized）、甚至 Erlang（actor 模型仍需显式 spawn）。Streem 的野心更大：**语法即并发**，`|` 符号连接的不仅是数据，更是自动并行化的执行单元。

## 洞见二：Streem 的语法是"设计意图"的直接物化

2-2"新语言 Streem"给出了语法的具体形态：

```
STDIN | STDOUT                    # 类 cat 命令
seq(100) | {|x| if x % 15 == 0 {"FizzBuzz"} else if x % 3 == 0 {"Fizz"} else if x % 5 == 0 {"Buzz"} else {x} } | STDOUT
STDIN | {|line| return *line.split } | reduce([:]) {|map, word| map.set(word, map.get(word, 0) + 1) } | STDOUT
```

这套语法里有几个**极具设计意识**的决策：

- **管道即核心**：`表达式1 | 表达式2 | ... | 表达式n`，前一个是产生器（generator），中间是过滤器（filter），最后一个是消费者（consumer）
- **不可变性贯穿始终**：`a = [1,2,3,4]; b = a.push(5)` —— `b` 是新数组，原数组不变。这与传统 OOP 语言形成尖锐对立
- **两种赋值方向**：`=` 与 `->`（反向赋值，让代码顺序与数据流向一致）
- **emit / skip / return 控制流三件套**：emit 产生多值、skip 终止当前迭代、return 退出函数
- **Block 语法糖**：`reduce(0) {|x,y| x+y }` 等价于 `reduce(0, {|x,y| x+y })`，把 Ruby 的 block 优雅地融进函数式范式
    
> 💡 **洞见**：Streem 的语法不是"好看"那么简单，每一个语法决策都在**为"流模型 + 不可变性 + 轻量并发"这组设计铁三角服务**。`->` 反向赋值是为管道数据流方向服务；不可变数据是为一劳永逸消除竞争条件服务；Block 语法糖是为让过滤器写法自然服务。
> 
> 这正是第1章 1-4/1-5"编程语言设计入门"里强调的**设计权衡**的具体兑现：你选择什么计算模型，语法就该长成什么样。

## 洞见三：语言处理器是"迭代出来"的，不是"设计出来"的

2-3 到 2-7 这一组小节，**最珍贵的价值不是技术细节，而是展示了 Matz 真实的开发节奏**——他不是一次性设计出完美架构，而是像所有优秀工程师那样，从最小可用起步，逐步迭代：

**第一步：先开发语法检查器（2-3）**

- 引入任务构成模式：生产者-消费者、轮询调度、广播、汇总、请求-应答
- 软件构成：词法分析器 + 语法定义
- 用 lex/flex 做词法分析，yacc/bison 做语法分析
- 用巴科斯范式（BNF）定义 Streem 语法
    
**第二步：开发事件循环（2-4）**

- 从 `main` 的原型开始
- 自行开发事件循环，用 `epoll` 系统调用检测 I/O 事件
- 事件队列 + 处理函数模式
    
**第三步：多线程与对象（2-5）**

- 多线程化，尝试多核化
- 带优先级的队列实现
- 并发控制、队列为空的处理
- 用结构体表示对象
- 多线程处理的调试（这是真坑）
    
**第四步：缓存与符号（2-6）**

- 用缓存高速访问数据，设置多级缓存
- 数据更新时的问题
- 对管道的再次思考："在同一个内核中运行速度更快"
- 引入 Lisp 的符号（Symbol）概念
- 符号的 GC 问题
    
**第五步：转换为抽象语法树（2-7）**

- 支持符号语法的新方法
- 语法分析动作 → 转换为 AST
- 用结构体表示语法树节点
- 直接执行语法树 / 遍历 AST
- 灵活应用递归调用
    
从实现架构看，Streem 的系统分为三个子系统：**语言前端（解析源码 → AST）+ 运行时（执行引擎 + 事件循环 + 流管理）+ 标准库**。AST 节点超过 25 种类型，涵盖字面量、控制流、函数、变量、集合、流操作等。

> ⚠️ **洞见**：这一节给读者的真实启发是——**造一门语言和你平时做项目没本质区别，都是从能跑的最小原型开始，遇到什么问题解决什么问题**。Matz 在 2-5 里承认"多线程处理的调试"是难点，在 2-6 里坦言"对管道的再次思考"导致架构调整，在 2-7 里提到"被搁置的语法分析也取得了进展"。这些"不完美"的记录，恰恰是本章最宝贵的资产：**它展示了一位语言设计大师真实的工程决策过程**，而不是事后美化的"正确架构"。

## 洞见四：局部变量与异常处理——让语言从"玩具"变"工具"

2-8 是第二章的收官，也是让 Streem 从演示原型跨越到实用语言的关键一步：

**局部变量**

- 历史回顾："回到30年前"——没有局部变量的世界
- 局部变量的引入与实现
- 局部变量的嵌套与作用域嵌套的特殊情况
- **闭包（closure）的实现**：Streem 的闭包如何捕获环境
    
**异常处理**

- 编译时检查与错误检查
- 让"异常"产生：借鉴 Swift 的 Optional
- 忽视错误的代价
- Streem 的异常处理的实现
    
从架构实现看，Streem 用 `strm_state` 结构体形成作用域的链表来管理变量环境，提供 `strm_var_set`、`strm_var_get`、`strm_var_def` 等操作。错误处理则用 `node_error` 结构体表示，区分运行时错误、return、skip 三种类型，通过 `strm_raise()` 沿调用栈传播。

> 📌 **洞见**：局部变量和异常听起来很基础，但它们是**一门语言"可用性"的分水岭**。没有闭包，Streem 的 `{ |x| ... }` 过滤器就没法捕获外部环境；没有异常处理，`seq(100) | ...` 这种长管道里一个节点出错就会导致整个流崩溃。Matz 把这一节放在第二章结尾，暗示着：**一个语言处理器原型能不能用，不光取决于酷炫的并发模型，更取决于这些"不起眼"的可用性基础设施**。

## 联系脉络：第二章 → 后续章节的暗线

把第二章放回全书，能看到一条非常清晰的演进路径：

```
第2章：做出 Streem 原型
   │
   ├─ 2-2 Streem 语法 → 第3章：设计面向对象功能（3-2 Streem的面向对象、3-3 再看Streem的语法）
   │                      为什么需要"再看"？因为 2-7 的 AST 阶段暴露了 shift/reduce conflict 等问题
   │
   ├─ 2-5 用结构体表示对象 → 第4章：实现 Streem 的对象（4-2 基本数据结构、4-3 对象表示与 NaN Boxing、4-4 垃圾回收、4-5 无锁算法）
   │                          第二章只是"用结构体表示"的起步，第四章才真正解决对象表示、GC、并发
   │
   └─ 2-4 事件循环 + 2-1 抽象的并发编程 → 第5章：强化流编程（5-1 管道编程、5-7 数据流图）
                                      第二章是事件循环的雏形，第五章把流编程模型做到生产级
```

特别值得注意的是 **3-3"再看 Streem 的语法"**​ 这个小节——它直接呼应了第二章 2-7 的 AST 实现过程中暴露的问题：shift/reduce conflict、break 语句的删除、if 语句的修改、右侧赋值的增加等。这说明**第二章的 AST 实现直接驱动了第三章的语法再设计**，两章之间是"实现 → 反馈 → 修正"的迭代关系，而非独立的章节。

## 一句贯穿本章的洞见

> 🎯 **造一门语言，始于一个尖锐的设计判断，成于一次次不完美的迭代。**
> 
> Matz 在第二章展示的，不是"如何正确地造语言"，而是"如何开始造一门语言"——从抽象的并发模型出发，用 lex/yacc 快速搭起语法检查器，用 epoll 实现事件循环，用结构体表示对象，逐步引入缓存、符号、AST、局部变量、异常。**每一步都不是完美的，但每一步都让语言更靠近"能用"**。
> 
> 这给所有读者的真正启示是：**不要等架构完美了再动手**。Streem 的第二章如果用"业界最佳实践"的标准看，处处都是临时方案——自研事件循环而非用 libuv、简单的结构体对象而非完善的 NaN Boxing、被"搁置"的语法分析。但正是这些"不完美"的快速迭代，让 Streem 在很短时间里从一个念头变成了能跑 `STDIN | STDOUT` 的真实语言。
> 
> 而 Streem 最锋利的设计判断——**把并发藏进"流"这个计算模型里，让 `|` 符号自动意味着并行**——则是全书最具启发性的洞见。它告诉我们：好的语言设计不是给程序员更多控制权，而是**给一个更聪明的默认行为**，让他们不必去思考本来就不该由他们思考的问题。
