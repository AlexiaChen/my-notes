
## 开篇：第 11 章的主线——"函数"在 CPython 中到底是什么

前几章我们建立了：

- **code object**​ 是编译期的静态产物（字节码 + 常量 + 名字表）[第 7 章]
- **frame**​ 是 code object 的运行期实例，由 `PyEval_EvalFrame` 驱动 [第 8 章]
- **控制流**​ 是条件跳转与无条件跳转的组合 [第 10 章]

第 11 章要回答一个更根本的问题：**Python 中的 "def" 语句执行时发生了什么？**​ 函数不是凭空出现的——它是 `PyCodeObject`（静态）与 `func_globals`（动态上下文）的"封装体"。

**本章双轨阅读的关键分歧点**：

- **书里（Python 2.5）**：`PyFunctionObject` 包含 `func_code` / `func_globals` / `func_defaults` / `func_closure` / `func_doc` / `func_name` / `func_dict` / `func_module` 等字段
- **现代（3.14）**：结构体通过 `COMMON_FIELDS` 宏统一定义，并新增了 `func_kwdefaults`、`func_qualname`、`func_annotations`、`func_version`、`vectorcall` 等关键字段

最显著的演化发生在**调用机制**上：

- **3.11 前**：`CALL_FUNCTION` / `CALL_FUNCTION_KW` / `CALL_METHOD` 三条指令各自为政
- **3.11 起**：拆解为 `PUSH_NULL` → `PRECALL` → `CALL` + `KW_NAMES` 的标准化调用序列，专为自适应专用化服务
- **3.13 起**：`f_locals` 变成"直写代理"（PEP 667），彻底修复了"修改 f_locals 不影响真实局部变量"的长期怪癖

## 11.1 PyFunctionObject 对象

**书里（Python 2.5）的定义**：

```
typedef struct {
    PyObject_HEAD
    PyObject *func_code;       // 对应的 PyCodeObject
    PyObject *func_globals;    // 运行时的 global 名字空间
    PyObject *func_defaults;   // 默认参数（tuple 或 NULL）
    PyObject *func_closure;    // NULL 或 cell 对象元组，用于闭包
    PyObject *func_doc;        // 文档字符串
    PyObject *func_name;       // 函数名 __name__
    PyObject *func_dict;       // __dict__ 属性
    PyObject *func_weakreflist;
    PyObject *func_module;     // __module__
} PyFunctionObject;
```

**现代（3.14）的定义**（依据 `Include/cpython/funcobject.h`）：

```
#define COMMON_FIELDS(PREFIX) \
    PyObject *PREFIX ## globals; \
    PyObject *PREFIX ## builtins; \
    PyObject *PREFIX ## name; \
    PyObject *PREFIX ## qualname; \
    PyObject *PREFIX ## code; \
    PyObject *PREFIX ## defaults;   /* NULL or a tuple */ \
    PyObject *PREFIX ## kwdefaults; /* NULL or a dict */ \
    PyObject *PREFIX ## closure;    /* NULL or a tuple of cell objects */

typedef struct {
    PyObject_HEAD
    COMMON_FIELDS(func_)
    PyObject *func_doc;
    PyObject *func_dict;
    PyObject *func_weakreflist;
    PyObject *func_module;
    PyObject *func_annotations;  // 参数和返回值注解
    vectorcallfunc vectorcall;   // 专用化的向量调用入口
    uint32_t func_version;       // 用于专用化的版本号
} PyFunctionObject;
```

**关键演化**：

- **`func_kwdefaults`**：3.11+ 单独存储仅关键字参数的默认值（字典），与 `func_defaults`（位置参数默认值元组）分离。
- **`func_qualname`**：3.11+ 加入，存储限定名（如 `OuterClass.inner_method`），对嵌套函数/类的调试和内省至关重要。
- **`func_annotations`**：从 Python 3.x 早期就存在，但 3.14 进一步强化，支持 `from __future__ import annotations` 的延迟求值。
- **`vectorcall` + `func_version`**：3.12+ 加入的高性能调用机制与版本跟踪。当 `defaults` / `kwdefaults` / `code` / `annotations` 任一变化时，`func_version` 归零，触发专用化失效。
- **结构体注释明确区分**：_"Function objects are created by the execution of the 'def' statement. They reference a code object... There is one code object per source code 'fragment', but each code object can be referenced by zero or many function objects"_——这正是书上强调的"code object 是静态的，function object 是动态的"的现代官方表述。

**第一性原理**：

- **函数对象 = 代码 + 上下文的封装**。`func_code` 指向静态编译产物，`func_globals` 指向运行时的全局名字空间——这两个字段在函数被调用时会传入新创建的 frame。
- **同一个 code object 可以被多个 function object 共享**：每次执行 `def` 语句都会创建一个新的 function object，但它们可能指向同一个 code object。这就是为什么在函数内部定义函数（工厂模式）每次调用外层函数都会得到一个新的内层函数对象。
- **`func_closure` 是闭包的载体**：当内层函数引用外层函数的变量时，这些变量会被"升级"为 cell 对象，外层函数的 code object 的 `co_cellvars` 列出这些变量名，内层函数的 `func_closure` 持有对应的 cell 元组。

**洞见——`func_version` 是 3.12+ 性能优化的关键**：

每次 `func_defaults` / `func_kwdefaults` / `func_code` / `func_annotations` 发生变化，`func_version` 就会自增。自适应解释器缓存 `CALL` 指令的专用化结果时，会记录当时的 `func_version`；下次调用时若版本匹配，直接走专用化快路径，否则重新专用化。这使得修改函数默认值（虽然罕见）能正确失效专用化。

## 11.2 无参函数调用

**书里（Python 2.5）的调用流程**：

1. 加载函数对象到栈：`LOAD_NAME func`
2. 调用：`CALL_FUNCTION 0`（参数个数为 0）
3. PVM 进入 `_PyEval_EvalFrameEx`，创建新 frame，`func_code` 和 `func_globals` 传入

**现代（3.14）的调用序列**（依据官方 `dis` 文档）：

```
def f():
    return 42

f()
```

编译出的字节码（3.11+）：

```
LOAD_GLOBAL 0 (f)     # 加载函数对象
PUSH_NULL             # 3.11+ 为方法调用统一协议，非方法调用时推入 NULL
PRECALL 0             # 前缀指令，为 CALL 专用化做准备
CALL 0                # 实际调用，0 个参数
```

**关键演化**：

- **3.11 的"调用序列革命"**：原本单一的 `CALL_FUNCTION` 被拆解为 `PUSH_NULL` → `PRECALL` → `CALL` 三段式。`PRECALL` 本身逻辑上是 no-op，但它的存在让 CALL 指令可以被自适应解释器专用化——例如 `CALL_FUNCTION` 被专用化为 `CALL_PY_EXACT_ARGS`（精确参数个数的 Python 函数调用）。
- **`vectorcall` 协议**：3.12+ 的 `PyFunctionObject` 含有 `vectorcall` 函数指针。当调用函数时，PVM 优先通过 `_PyFunction_Vectorcall` 走快速向量调用路径（参数以数组形式传递，避免栈操作开销），而非传统的"压栈-调用-弹栈"流程。
- **3.11+ 调用性能提升显著**：基准测试显示，同样是 `len(str(i))` 的循环，3.10 耗时 ~16.8ms，3.11 降至 ~10.9ms——调用序列的重构和专用化是主要贡献者之一。

**第一性原理**：

- **函数调用 = 创建新 frame + 跳转**。"调用"在 PVM 层面就是 `CALL` 指令：从栈上弹出 callable 和参数 → 创建新 frame（绑定 `func_code` + `func_globals`）→ 把参数写入新 frame 的局部变量区 → 递归进入 `_PyEval_EvalFrame`。
- **3.11+ 的三段式调用序列是"分派与执行解耦"**：`PUSH_NULL` + `PRECALL` 是"准备阶段"，`CALL` 是"执行阶段"。这种分离让 `CALL` 指令在执行过程中可以被改写为专用化版本（如 `CALL_PY_EXACT_ARGS`、`CALL_BUILTIN_CLASS`），而不必每次都重新解析调用约定。

**工业实际**：

```
import dis
import timeit

def f(): return 42

# 观察 3.14 的调用序列
dis.dis(f.__call__)  # 或直接 dis.dis(f)
# 输出：
# PUSH_NULL
# PRECALL 0
# CALL 0
# RETURN_VALUE

# 性能测试：3.11+ 的函数调用比 3.10 快约 30%
print(timeit.timeit("f()", "def f(): return 42", number=10000000))
```

**洞见**：每次函数调用都要承担"创建 frame + 绑定参数 + 建立名字空间"的固定开销。这就是为什么 Python 函数调用相对"重"——它不是 C 的栈帧压入，而是堆分配 frame 对象 + 字典/数组绑定的组合。减少不必要的函数调用（如把热循环里的小函数内联，或用 `functools.lru_cache` 缓存结果）是 Python 性能调优的基本功。

## 11.3 函数执行时的名字空间

**书里（Python 2.5）的视角**：

- 函数 frame 的三个名字空间：`f_locals`（局部）、`f_globals`（全局，来自 `func_globals`）、`f_builtins`（内建）
- 书里明确指出：`func_globals` 指向函数在定义时所在的全局名字空间，这是函数执行时关联 global 作用域的依据
- 局部变量访问通过 `f_localsplus` 数组（变长区域：局部变量 + cell + free + 栈）

**现代（3.14）的关键演化——PEP 667（3.13+）**：

**3.12 及以前的行为（有缺陷）**：

```
def f():
    x = 1
    frame = sys._getframe()
    locals()['x'] = 2     # 修改快照
    print(x)              # 仍然输出 1！修改没有生效
    frame.f_locals['x'] = 3
    print(x)              # 仍然是 1！必须调用 PyFrame_LocalsToFast()
```

`frame.f_locals` 返回的是从局部变量数组**即时构造的字典副本**；要写回必须通过 `PyFrame_LocalsToFast()` C API。这导致字典和数组可能失同步。

**3.13+ 的新行为（PEP 667）**：

- `frame.f_locals` 返回一个 **write-through proxy**（`PyFrameLocalsProxy_Type` 实例）
- 对代理的修改**实时反映**到帧的实际局部变量存储中，反之亦然
- `locals()` 内置函数**每次调用返回独立的快照**（不是代理），保证 `exec()` / `eval()` 的语义清晰

**PEP 667 的设计哲学**：

> _"frame.f_locals is always in sync with the frame because it is a view of it, not a copy of it."_

具体来说：

- `frame.f_locals` → **读写视图**（write-through proxy），所有修改立即生效
- `locals()` → **独立快照**（snapshot），每次调用都创建新的 dict 副本

这种分离让意图更清晰：调试器/追踪器用 `frame.f_locals`（需要读写同步），用户代码用 `locals()`（只需要瞬时快照）。

**第一性原理**：

- **函数 frame 的名字空间是"分层"的**：局部变量在 `f_localsplus` 数组里（最快访问），全局变量在 `func_globals` 字典里，内建变量在 `f_builtins` 字典里。
- **3.13 的 PEP 667 修复了"视图 vs 副本"的长期歧义**：之前的实现既不可靠又慢，因为帧数组和字典快照可能失同步。直写代理从根本上消除了这个问题——`f_locals` 是帧的"窗口"，不是"副本"。
- **`locals()` 返回快照而非视图是刻意为之**：这样 `exec()` 在局部作用域执行时，对局部变量的修改不会影响原帧（保持了 Python 语义的清晰性）。

**工业实际**：

```
import sys

def demo():
    x = 1
    frame = sys._getframe()
    
    # 3.13+ ：通过 f_locals 代理修改立即生效
    frame.f_locals['x'] = 100
    print(x)  # 3.13+ 输出 100（3.12 及以前仍输出 1）
    
    # locals() 始终返回快照
    snap = locals()
    snap['x'] = 200
    print(x)  # 仍然是 100，快照修改不影响真实局部变量
    
    # 调试器可以利用 f_locals 代理实时修改变量
    frame.f_locals['x'] = 999
    print(x)  # 输出 999

demo()
```

**洞见——为什么 PEP 667 对调试器/APM 工具至关重要？**

在 3.12 及以前，调试器要修改断点处的局部变量，必须调用 `PyFrame_LocalsToFast()` C API 把字典写回帧数组；如果忘记调用，修改就丢失了。3.13+ 的直写代理让这个过程自动化——任何对 `frame.f_locals` 的修改都立即生效。这对 PyCharm、VS Code Debugger、以及各类 APM 工具的 Python 探针是重大简化。

## 11.4 函数参数的实现

**书里（Python 2.5）的参数处理**：

- 位置参数：`co_varnames` 的前 N 个槽
- 默认参数：`func_defaults` 元组
- `*args` / `**kwargs`：通过特定字节码处理
- 参数绑定是函数调用时在新 frame 的 `f_localsplus` 数组中完成的

**现代（3.14）的参数语义**（依据 Python 官方文档）：

**1. 默认参数在函数定义时求值一次**：

> _"Default parameter values are evaluated from left to right when the function is defined. This means that the expression is evaluated once, when the function is defined, and that the same 'pre-computed' value is used for each call."_

这就是为什么可变默认值是经典陷阱：

```
def append_to(element, target=[]):  # target 在 def 时创建，所有调用共享
    target.append(element)
    return target

append_to(1)  # [1]
append_to(2)  # [1, 2] —— 不是 [2]！
```

**2. 三种参数形式**（Python 3.x 完整支持）：

- **位置参数**：`def f(a, b)`
- **仅位置参数（PEP 570, 3.8+）**：`def f(a, b, /)`
- **仅关键字参数**：`def f(*, a, b)`
- **可变位置参数**：`def f(*args)`
- **可变关键字参数**：`def f(**kwargs)`

**3. 参数绑定算法**（依据 CPython 文档描述）：

1. 根据形参表创建一串空闲槽
2. 如果有 N 个位置参数，放在前 N 个槽中
3. 对于每个关键字参数，用标识符检测对应槽；若槽已占用则抛 `TypeError`
4. 所有关键字参数处理后，未填充的槽用函数定义中的默认值填充
5. 如果仍有未填充的槽，抛 `TypeError`
6. 所有被填充的槽当作调用的参数表

**4. 现代字节码层面的参数处理**：

- 3.11+ 引入了 `COPY_FREE_VARS` 指令，用于闭包调用时把 free variables 从 func_closure 复制到 frame
- `CALL` 指令的 `argc` 参数指示位置参数和关键字参数的总数（不含 self）
- 关键字参数名通过 `KW_NAMES` 前缀指令从 `co_consts` 加载

**第一性原理**：

- **参数绑定 = "位置实参填入槽 + 关键字实参映射到槽 + 默认值和可变参数兜底"**。这是一个编译期确定槽布局、运行期填充槽的过程。
- **默认参数的"定义时求值"是 Python 语义的核心设计**：它使得默认参数可以是任意表达式（包括函数调用），但也带来了可变默认值的陷阱。理解这一点，就能理解为什么 `target=None` + `if target is None: target = []` 是标准写法。
- **`/` 和 `*` 不是语法糖，是 ABI 边界**：仅位置参数让函数可以安全地重命名参数而不破坏调用方；仅关键字参数让函数可以安全地添加新的位置参数而不破坏调用方。这是大型库 API 演进的关键工具。

**工业实际**：

```
import dis

# 1. 可变默认值的陷阱与修复
def bad_append(element, target=[]):
    target.append(element)
    return target

def good_append(element, target=None):
    if target is None:
        target = []
    target.append(element)
    return target

# 2. 参数形式的最佳实践
def configure(
    host,                    # 位置或关键字
    port,                    # 位置或关键字
    /,                       # 以上为仅位置参数
    timeout=30,              # 位置或关键字，有默认值
    *,                       # 以下为仅关键字参数
    retry=3,
    ssl=True
):
    pass

# 3. 观察参数绑定的字节码
dis.dis(configure)
# 会看到 LOAD_FAST 系列指令从局部变量区取参数
# 默认值通过 LOAD_CONST 从 co_consts 加载
```

**洞见——为什么 3.8 引入仅位置参数（PEP 570）？**

`/` 语法让 API 设计者可以明确"这些参数只能用位置传递"。这在两个场景下极有价值：

1. **API 稳定性**：参数名可以安全重构而不破坏用户代码
2. **C 函数兼容性**：CPython 的内建函数很多是仅位置的（如 `len(obj)` 不能写成 `len(obj=obj)`），`/` 让纯 Python 实现能与 C 实现保持一致的调用约定

## 11.5 函数中局部变量的访问

**书里（Python 2.5）的机制**：

- 局部变量不在字典里，而在 `f_localsplus` 数组的前 `co_nlocals` 个槽
- `LOAD_FAST` / `STORE_FAST` 通过下标直接访问数组
- 编译期通过符号表分析确定每个变量是否是局部的（若是，用 `LOAD_FAST`；否则用 `LOAD_GLOBAL`）

**现代（3.14）的局部变量访问指令**：

**基础指令**：

- `LOAD_FAST(var_num)`：将 `co_varnames[var_num]` 压栈
- `STORE_FAST(var_num)`：将栈顶存入 `co_varnames[var_num]`
- `DELETE_FAST(var_num)`：删除局部变量
- `LOAD_FAST_CHECK(var_num)`：3.12+ 加入，若变量未初始化则抛 `UnboundLocalError`

**3.13+ 的微指令融合**（性能优化）：

- `LOAD_FAST_LOAD_FAST(var_nums)`：一次压入两个局部变量（3.13+）
- `STORE_FAST_STORE_FAST(var_nums)`：一次存储两个局部变量（3.13+）
- `STORE_FAST_LOAD_FAST(var_nums)`：存储一个、加载另一个（3.13+）

**3.14 的借用引用优化**：

- `LOAD_FAST_BORROW(var_num)`：压入借用引用而非强引用（3.14+）
- `LOAD_FAST_BORROW_LOAD_FAST_BORROW(var_nums)`：借用版本的双加载（3.14+）

**第一性原理**：

- **局部变量访问 = 数组下标操作，不是字典查找**。这就是为什么局部变量访问比全局变量快——`LOAD_FAST 0` 是直接的内存访问，而 `LOAD_GLOBAL name` 要经历"名字 → 哈希表查找 → 对象"的多步过程。
- **编译期决定变量类别**：Python 编译器扫描整个函数体，把所有出现在赋值左侧的名字标记为局部变量（进入 `co_varnames`）。这就是为什么在函数体内任何位置赋值都会让该名字成为局部变量，即使赋值在引用之后（导致 `UnboundLocalError`）。
- **3.13+ 的指令融合是"常见模式专用化"**：`a = b + c` 这样的常见模式，原本需要 `LOAD_FAST(b); LOAD_FAST(c); BINARY_ADD; STORE_FAST(a)` 四条指令，现在可以用融合指令减少分派开销。

**工业实际**：

```
import dis

def compute(a, b, c):
    x = a + b
    y = x * c
    return y

dis.dis(compute)
# 3.14 输出示例：
# LOAD_FAST 0 (a)
# LOAD_FAST 1 (b)
# BINARY_OP 0 (+)
# STORE_FAST 3 (x)
# LOAD_FAST 3 (x)
# LOAD_FAST 2 (c)
# BINARY_OP 5 (*)
# STORE_FAST 4 (y)
# LOAD_FAST 4 (y)
# RETURN_VALUE

# 性能法则：
# 1. 热循环里把全局变量绑定到局部
import math
def slow(N):
    result = 0
    for i in range(N):
        result += math.sin(i)  # 每次都 LOAD_GLOBAL math + LOAD_ATTR sin
    return result

def fast(N):
    result = 0
    sin = math.sin  # 绑定到局部变量
    for i in range(N):
        result += sin(i)  # 每次只 LOAD_FAST sin
    return result

# fast 比 slow 快 2-3 倍
```

**洞见——为什么 `UnboundLocalError` 是 Python 最常见的"反直觉"错误？**

```
x = 1
def f():
    print(x)  # 想打印全局的 x
    x = 2     # 但这行让编译器把 x 标记为局部变量
f()  # UnboundLocalError: local variable 'x' referenced before assignment
```

编译器扫描整个函数体时发现了 `x = 2` 这行赋值，于是把 `x` 归入 `co_varnames`，`print(x)` 编译为 `LOAD_FAST 0`——但执行到 `print` 时 `x` 还没有被 `STORE_FAST` 赋值，所以报错。**修复方法**：用 `global x` 声明告诉编译器"x 是全局变量"，或者用 `nonlocal x`（如果在嵌套函数中）。

## 11.6 嵌套函数、闭包与 decorator

**书里（Python 2.5）的闭包机制**：

- 外层函数的局部变量被内层函数引用时，这些变量被"升级"为 cell 变量
- 内层函数的 `func_closure` 持有外层函数 cell 变量的元组
- 编译期通过 `co_cellvars`（外层）和 `co_freevars`（内层）协调

**现代（3.14）的闭包实现**：

**cell 对象的角色**：

- 当外层函数 `outer()` 的局部变量 `y` 被内层函数 `inner()` 引用时，Python 把 `y` 从普通局部变量"升级"为 **cell 变量**
- cell 是一个小的堆分配对象（`PyCellObject`），包装了真实的值
- 外层函数和内层函数**共享同一个 cell 对象**——外层写值、内层读值，都通过同一个 cell

**字节码层面的闭包创建**：

```
# 外层函数 outer()
MAKE_CELL 0          # 为 co_cellvars[0] 创建 cell
LOAD_CLOSURE 0       # 将 cell 压栈（用于构建闭包元组）
BUILD_TUPLE 1        # 构建闭包元组
LOAD_CONST <code>    # 加载内层函数的 code object
MAKE_FUNCTION 8      # 创建内层函数，flags=0x08 表示有闭包
```

**内层函数的自由变量访问**：

- `LOAD_DEREF(i)`：从 cell 中加载自由变量
- `STORE_DEREF(i)`：存储到 cell
- `COPY_FREE_VARS(n)`：3.11+ 新增，调用闭包时把 n 个自由变量从 `func_closure` 复制到 frame
- 3.11 起 `LOAD_DEREF` / `STORE_DEREF` 的 `i` 不再偏移 `co_varnames` 的长度，简化了索引计算

**观察闭包的内部**：

```
def outer(x):
    def inner():
        return x * 2  # x 是自由变量
    return inner

fn = outer(10)
print(fn.__code__.co_freevars)          # ('x',)
print(fn.__closure__[0].cell_contents)  # 10
print(fn.__closure__[0])                # <cell at 0x...>
```

**Decorator 的字节码实现**：

```
@deco
def func():
    pass
```

等价于：

```
def func():
    pass
func = deco(func)
```

区别在于：**原始函数从未被临时绑定到名字 `func`**——装饰器在 `MAKE_FUNCTION` 之后立即应用，再把结果绑定到名字。

字节码：

```
LOAD_NAME 0 (deco)          # 加载装饰器
LOAD_CONST 1 (<code>)       # 加载函数 code object
MAKE_FUNCTION 0             # 创建函数对象
CALL 1                      # 调用装饰器
STORE_NAME 1 (func)         # 绑定装饰结果
```

**第一性原理**：

- **闭包 = cell 对象的共享**。内层函数之所以能"记住"外层函数的变量，是因为它们共享同一个 cell 对象。外层函数返回后，其 frame 被销毁，但 cell 对象因为被内层函数的 `func_closure` 引用而继续存活。
- **`func_closure` 是闭包的"背包"**：它装着内层函数需要的所有自由变量的 cell。每次调用内层函数时，`COPY_FREE_VARS` 把这些 cell 复制到新 frame 的自由变量区。
- **Decorator 是"函数包装的语法糖"**：`@deco` 不过是 `func = deco(func)` 的语法简写。理解这一点，就能理解为什么 decorator 可以有参数（`@deco(arg)` 等价于 `func = deco(arg)(func)`）。

**工业实际**：

```
# 1. 闭包经典应用：工厂函数
def make_multiplier(factor):
    def multiplier(x):
        return x * factor  # factor 通过 cell 捕获
    return multiplier

double = make_multiplier(2)
triple = make_multiplier(3)
print(double(5), triple(5))  # 10, 15

# 2. 闭包变量修改：必须用 nonlocal
def counter():
    count = 0
    def inc():
        nonlocal count  # 声明要修改外层 cell 变量
        count += 1
        return count
    return inc

c = counter()
print(c(), c(), c())  # 1, 2, 3

# 3. Decorator 链与等价性
@f1(arg)
@f2
def func():
    pass
# 等价于：
# def func(): pass
# func = f1(arg)(f2(func))

# 4. 3.11+ COPY_FREE_VARS 的作用
import dis
def outer():
    x = 1
    def inner():
        return x
    return inner

dis.dis(outer)
# 会看到 MAKE_CELL, LOAD_CLOSURE, BUILD_TUPLE, MAKE_FUNCTION 序列
inner = outer()
dis.dis(inner)
# 会看到 LOAD_DEREF 访问自由变量 x
```

**洞见——闭包与 `__slots__` 的性能协同**：

闭包变量存储在 cell 对象中（堆分配），每个 cell 约 16 字节。如果一个类有大量实例且每个实例的方法都是闭包（常见于某些 ORM 或 RPC 客户端），内存开销会很大。这时用 `__slots__` 可以消除实例的 `__dict__`，但闭包本身的 cell 开销仍在。**真正的优化是避免在热路径上动态创建闭包**——如果需要绑定参数，优先考虑 `functools.partial` 或类方法，它们比闭包更轻量。

## 第 11 章合体总结：函数机制的完整图景

|维度|书里（2.5）|现代（3.14）|
|---|---|---|
|**PyFunctionObject**​|9 个字段|COMMON_FIELDS 宏 + func_kwdefaults/qualname/annotations/version/vectorcall 等|
|**调用指令**​|`CALL_FUNCTION` / `CALL_FUNCTION_KW` / `CALL_METHOD`|`PUSH_NULL` → `PRECALL` → `CALL` + `KW_NAMES`（3.11+）|
|**f_locals 语义**​|直接返回局部变量字典|PEP 667 直写代理（3.13+）|
|**局部变量访问**​|`LOAD_FAST` / `STORE_FAST`|基础指令 + 3.13 融合指令 + 3.14 借用引用|
|**闭包实现**​|cell 对象 + `func_closure`|同上，3.11+ 新增 `COPY_FREE_VARS`，`LOAD_DEREF` 索引简化|
|**仅位置参数**​|不支持|3.8+ PEP 570 支持 `/`|
|**调用性能**​|基线|3.11+ 快约 30%（调用序列重构 + 专用化）|

### 三个必须带走的洞见

**洞见一：函数对象 = 代码（静态）+ 上下文（动态）的封装。**

`func_code` 指向编译期产物，`func_globals` 指向定义时的全局名字空间。同一个 code object 可以被多个 function object 共享（每次执行 `def` 都创建新的 function object）。这解释了 Python 函数作为一等公民的底层机制——函数可以传递、可以返回、可以嵌套，本质上都是在操作这个封装体。

**洞见二：3.11 的调用序列革命是性能的引爆点。**

把单一的 `CALL_FUNCTION` 拆解为 `PUSH_NULL` → `PRECALL` → `CALL` 三段式，让 `CALL` 指令可以被自适应解释器专用化。`CALL_PY_EXACT_ARGS`、`CALL_BUILTIN_CLASS` 等专用化版本绕过了通用的参数绑定流程，直接走快路径。这是 3.11 函数调用性能提升 30% 的核心原因之一。

**洞见三：局部变量是"数组下标"而非"字典查找"，这是 Python 性能优化的隐藏杠杆。**

`LOAD_FAST 0` 是直接的内存访问，而 `LOAD_GLOBAL name` 要经历哈希表查找。把热路径上的全局变量绑定到局部（`sin = math.sin`），就是利用了这个差异，可以获得 2-3 倍的性能提升。3.13+ 的指令融合（`LOAD_FAST_LOAD_FAST`）和 3.14 的借用引用（`LOAD_FAST_BORROW`）进一步优化了常见访问模式。
