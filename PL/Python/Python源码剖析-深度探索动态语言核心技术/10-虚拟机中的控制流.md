
## 开篇：第 10 章的主线——"控制流"在 PVM 中是什么

前几章我们建立了三个认知：

- **code object**​ 是编译期的静态产物（字节码 + 常量 + 名字表）[上一章]
- **frame**​ 是 code object 的运行期实例（名字空间 + 求值栈 + 指令指针）[第 8 章]
- **表达式求值**​ 就是 PVM 对求值栈的操作（`LOAD_*` 压栈、`BINARY_*` 运算、`STORE_*` 出栈）[第 9 章]

第 10 章要解决的，是**这些栈操作指令如何被"串起来"形成 if/for/while/try 的控制流**。本质上，高级语言的控制流结构在 PVM 层面只有两种原语：

1. **条件跳转**：`POP_JUMP_IF_FALSE/TRUE`——根据栈顶真假决定下一条指令的位置
2. **绝对/相对跳转**：`JUMP_FORWARD/BACKWARD/ABSOLUTE`——无条件转移到某条指令

**所有**​ if/for/while/try，无论多么复杂，编译后都是这两种跳转指令的组合。这就是控制流的"第一性原理"。

延续双轨阅读法：

- **轨道一（机制，跨版本稳定）**：控制流 = 条件跳转 + 无条件跳转的组合。这一原则从 Python 1.x 到 3.14 从未改变。
- **轨道二（策略，关键演化）**：
    - **Python 3.6+**：字节码从不定长改为定长 2 字节 wordcode
    - **Python 3.11+**：零成本异常处理——用 `ExceptionTable` 取代运行时的"块栈（block stack）"
    - **Python 3.11+**：跳转指令的参数从绝对偏移改为相对 delta（`POP_JUMP_IF_FALSE` 等）
    - **Python 3.12+**：`FOR_ITER` 在迭代器耗尽时不再弹出迭代器（改由 `END_FOR` 清理）
    - **Python 3.14**：PEP 765 禁止在 `finally` 块中使用 `return`/`break`/`continue` 退出

## 10.1 Python 虚拟机中的 if 控制流

**书里（Python 2.5）的 if 编译模型**：

```
if test1:
    suite1
elif test2:
    suite2
else:
    suite3
```

编译为：

```
EVAL test1
POP_JUMP_IF_FALSE L1
suite1
JUMP_FORWARD L3
L1: EVAL test2
POP_JUMP_IF_FALSE L2
suite2
JUMP_FORWARD L3
L2: suite3
L3: ...
```

**核心指令语义**（依据官方 `dis` 文档）：

- `POP_JUMP_IF_FALSE(delta)`：弹出栈顶，若为假则向后跳转 `delta` 条指令；否则继续执行下一条。
- `POP_JUMP_IF_TRUE(delta)`：对称版本。
- `JUMP_FORWARD(delta)`：无条件向前跳转 `delta`。
- **3.11 起 `POP_JUMP_IF_*` 的参数是相对 delta 而非绝对目标地址**——这是为了配合定长 wordcode，让指令更紧凑、分派更快。

**现代（3.14）的 if 演化**：

- 跳转指令进一步细分：`POP_JUMP_IF_FALSE` / `POP_JUMP_IF_TRUE` 现在是伪指令，最终会被汇编为带方向的版本（`POP_JUMP_IF_FALSE_FORWARD` 等）。
- 短路求值 `and` / `or` 用 `JUMP_IF_FALSE_OR_POP` / `JUMP_IF_TRUE_OR_POP` 实现——若条件满足则跳转（不弹出左操作数），否则弹出左操作数继续。
- 3.13+ 增加了 `POP_JUMP_IF_NONE` / `POP_JUMP_IF_NOT_NONE`，对 `is None` 模式做专用化。

**第一性原理**：

- **if 的本质是"栈顶真假的二分"**：求值条件表达式 → 栈顶得到一个布尔值 → 根据真假跳转到不同指令位置。没有"if 指令"，只有"条件求值 + 条件跳转"。
- **elif 不是新语法，是 if-else 的嵌套平铺**：每个 `elif` 编译为"测试 + 失败跳转 + 分支 + 跳出"，与手写嵌套 if-else 产生的字节码完全一致。这就是为什么深层 elif 链性能会下降——每个 elif 都要重新求值并跳转。
- **短路求值 = 条件跳转的语法糖**：`a and b` 编译为 `LOAD a; POP_JUMP_IF_FALSE; LOAD b`——若 a 为假，直接跳到表达式结束，b 根本不被求值。这就是"短路"的字节码真相。

**洞见——为什么 `if x is None` 比 `if x == None` 快？**

3.13+ 的 `POP_JUMP_IF_NONE` 是专用化指令，直接从栈顶比较 `is None`（指针身份比较，O(1) 且无函数调用）；而 `==` 要走 `BINARY_OP` → `PyObject_RichCompare` → 可能调用 `__eq__` 方法。在热路径上，把 `== None` 改成 `is None` 不仅是风格问题，更是性能问题。

**工业实际**：

```
import dis

def classify(x):
    if x < 0:
        return "neg"
    elif x == 0:
        return "zero"
    elif x > 100:
        return "large"
    else:
        return "normal"

dis.dis(classify)
# 输出会显示三个 POP_JUMP_IF_FALSE 串联
# 每个 elif 都是一次"测试-跳转"，所以热路径上减少 elif 层数
# 或使用 match-case（3.10+）获得更紧凑的分派
```

## 10.2 Python 虚拟机中的 for 循环控制流

**书里（Python 2.5）的 for 编译模型**：

```
for i in iterable:
    suite
```

编译为：

```
SETUP_LOOP L
LOAD iterable
GET_ITER
FOR_ITER
STOR_FAST i
suite
JUMP_ABSOLUTE FOR_ITER
L: POP_BLOCK
```

**核心指令语义**：

- `GET_ITER`：把栈顶对象替换为 `iter(TOS)`——调用 `iter()` 内置函数，触发对象的 `__iter__` 方法。
- `FOR_ITER(delta)`：TOS 是迭代器。调用其 `__next__()` 方法。若产出新值，压栈（迭代器留在栈下）；若迭代器耗尽，则弹出迭代器，指令指针向后跳 `delta`。
- **3.12+ 演化**：迭代器耗尽时不再由 `FOR_ITER` 弹出，而是继续执行后续的 `END_FOR` 指令清理。这是为自适应专用化腾出空间——`FOR_ITER` 后面可以跟 cache 条目。
- 3.11+ `FOR_ITER` 的参数也是相对 delta。

**语言层面的关键语义**：

> _"The expression list is evaluated once; it should yield an iterable object. An iterator is created for the result of the expression list."_

这句官方文档的话揭示了 for 循环最重要的事实：**可迭代表达式只求值一次**。这意味着：

```
for x in get_data():  # get_data() 只调用一次
    process(x)
```

`get_data()` 在循环开始前就被调用并转换成迭代器，`for` 循环本身只是反复调用 `__next__()`。

**第一性原理**：

- **for 循环 = 迭代器协议 + 条件跳转**：`GET_ITER` 把可迭代对象转为迭代器，`FOR_ITER` 反复调用 `__next__()` 直到耗尽（抛出异常被 `FOR_ITER` 内部捕获并跳转）。**没有"for 指令"**，for 是 `GET_ITER` + `FOR_ITER` + `JUMP_BACKWARD` 的指令组合。
- **for 不是 C 风格的"下标循环"**：`for i in range(n)` 看似是下标循环，实则 `range(n)` 返回一个迭代器对象，`FOR_ITER` 每次调用其 `__next__()`。这就是为什么 Python 的 for 能遍历任何可迭代对象（list/tuple/dict/set/生成器/自定义 iterator）。
- **`else` 子句的本质**：for-else 的 else 块，编译为循环正常结束后（迭代器自然耗尽，非 break）执行的代码。break 会跳过 else，因为 break 直接跳转到循环外的下一条指令，绕过了 else 块。

**洞见——为什么在循环里修改正在迭代的 list 是危险的？**

```
lst = [1, 2, 3, 4]
for x in lst:
    lst.remove(x)  # 灾难！
```

`FOR_ITER` 持有的是 `iter(lst)` 返回的迭代器，该迭代器内部维护一个索引。当你 `remove(x)` 时，list 的长度和元素位置都变了，但迭代器的索引还在前进——导致跳过元素甚至越界。`for x in lst[:]:` 之所以安全，是因为 `lst[:]` 创建了副本，迭代器遍历的是副本，修改的是原 list。

**工业实际**：

```
import dis

def iterate(items):
    for item in items:
        process(item)

dis.dis(iterate)
# GET_ITER → FOR_ITER → ... → JUMP_BACKWARD_TO_FOR_ITER
# 注意：3.11+ 跳转指令名变化，但语义一致

# 性能建议：
# 1. 遍历 list 元素用 for-in，不用 range(len(lst)) + lst[i]
#    for x in lst:   优于   for i in range(len(lst)): x = lst[i]
#    后者多了 LOAD_FAST + LOAD_FAST + BINARY_SUBSCR 三次操作

# 2. 大数据集用生成器避免一次性加载
#    for line in file:   优于   for line in file.readlines():

# 3. 需要索引时用 enumerate
#    for i, x in enumerate(lst):   优于   for i in range(len(lst)): x = lst[i]
```

## 10.3 Python 虚拟机中的 while 循环控制结构

**书里（Python 2.5）的 while 编译模型**：

```
while test:
    suite
```

编译为：

```
SETUP_LOOP L
L1: EVAL test
POP_JUMP_IF_FALSE L
suite
JUMP_ABSOLUTE L1
L: POP_BLOCK
```

`break` 编译为 `BREAK_LOOP`（弹出块栈并跳转到循环后），`continue` 编译为 `JUMP_ABSOLUTE L1`（跳回测试）。

**现代（3.14）的 while 演化**：

- 3.11 起 `SETUP_LOOP` / `POP_BLOCK` 被移除（与控制流"零成本"化一致）。while 循环不再需要运行时块栈。
- 跳转指令使用相对 delta：`POP_JUMP_IF_FALSE_FORWARD` / `JUMP_BACKWARD`。
- **3.11 新增 `JUMP_BACKWARD_NO_INTERRUPT`**：循环回边默认用这条指令，它不检查中断（信号处理），减少热路径开销。普通 `JUMP_BACKWARD` 会检查是否有待处理的中断（如 Ctrl+C）。
- `CONTINUE_LOOP` 在现代字节码中已不存在，continue 直接编译为 `JUMP_BACKWARD` 到循环测试点。

**while-else 语义**：

> _"This repeatedly tests the expression and, if it is true, executes the first suite; if the expression is false... the suite of the else clause, if present, is executed and the loop terminates. A break statement executed in the first suite terminates the loop without executing the else clause’s suite."_

关键点：**break 跳过 else，正常条件为假时执行 else**。

**第一性原理**：

- **while = 条件跳转 + 向后跳转**：测试条件 → `POP_JUMP_IF_FALSE` 跳出 → suite → `JUMP_BACKWARD` 回到测试。与 for 的区别在于：for 的"条件"是迭代器是否耗尽（由 `FOR_ITER` 内部判定），while 的"条件"是任意布尔表达式（由 `POP_JUMP_IF_FALSE` 显式判定）。
- **break/continue 是语法糖**：break = 跳转到循环后的第一条指令；continue = 跳转到循环测试点。3.11+ 后，这两条语句直接编译为对应的 `JUMP_FORWARD` / `JUMP_BACKWARD`，不再需要 `BREAK_LOOP` 这种特殊指令。
- **while 循环的性能隐患**：因为每次迭代都要重新求值条件表达式，若条件表达式复杂（如调用函数、属性查找），会成为热路径瓶颈。优化手法：`while True:` + 内部 `if not cond: break`，把条件检查转化为循环内的单次跳转。

**洞见——while True + break 为何有时更快？**

```
# 慢：每次迭代都重新求值复杂条件
while expensive_check(x):
    x = transform(x)

# 快：条件检查在循环内，但只用一次跳转
while True:
    if not expensive_check(x):
        break
    x = transform(x)
```

前者每次迭代都要 `CALL expensive_check` + `POP_JUMP_IF_FALSE`；后者把条件检查放到循环体开头，逻辑等价但有时能让自适应解释器更好地专用化 `expensive_check` 的调用。

**工业实际**：

```
import dis

def while_loop(n):
    i = 0
    while i < n:
        i += 1
    return i

dis.dis(while_loop)
# 3.14 输出大致是：
# LOAD_FAST 0 (i)
# LOAD_FAST 1 (n)
# COMPARE_OP <
# POP_JUMP_IF_FALSE_FORWARD ...
# ... 循环体 ...
# JUMP_BACKWARD ...

# 性能法则：
# 1. 能用 for 就别用 while：for 的迭代器协议比 while 的条件求值更专
# 2. 无限循环用 while True:，不用 while 1:（后者在 3.x 已是语法错误）
# 3. 循环内避免属性查找：把 obj.attr 绑定到局部变量
```

## 10.4 Python 虚拟机中的异常控制流

**这是 3.11 性能革命的核心章节**，书的模型与现代实现差异最大，必须重点展开。

**书里（Python 2.5）的异常处理模型——"块栈"**：

```
try:
    suite1
except ExceptionType:
    suite2
finally:
    suite3
```

编译为：

```
SETUP_FINALLY L1          # 把 try 块压入运行时 block stack
suite1
POP_BLOCK                 # 离开 try 块，弹出 block stack
JUMP_FORWARD L2
L1: ...                   # 异常处理入口
suite2
L2: ...                   # finally 入口
suite3
```

**问题**：每次进入 try 块都要 `SETUP_FINALLY`（压栈），离开时都要 `POP_BLOCK`（出栈）。即使异常从未抛出，这些指令也要执行——**异常处理的成本在"正常路径"上不为零**。

**现代（3.11+）的"零成本异常处理"**：

3.11 彻底移除了运行时的块栈，`SETUP_FINALLY` 和 `POP_BLOCK` 从字节码中消失，取而代之的是 **`ExceptionTable`**——一个附加在 code object 上的静态表（`co_exceptiontable`）。

```
def f():
    try:
        g(0)
    except:
        return "fail"
```

**3.10 的字节码**（旧模型）：

```
SETUP_FINALLY 7 (to 16)
LOAD_GLOBAL 0 (g)
LOAD_CONST 1 (0)
CALL_NO_KW 1
POP_TOP
POP_BLOCK
LOAD_CONST 0 (None)
RETURN_VALUE
>> 16 POP_TOP
POP_TOP
POP_TOP
>> 22 POP_EXCEPT
LOAD_CONST 3 ('fail')
RETURN_VALUE
```

**3.11 的字节码**（新模型）：

```
RESUME 0
NOP
LOAD_GLOBAL 1 (NULL + g)
LOAD_CONST 1 (0)
PRECALL 1
CALL 1
POP_TOP
LOAD_CONST 0 (None)
RETURN_VALUE
>> 38 PUSH_EXC_INFO
POP_TOP
>> 42 POP_EXCEPT
LOAD_CONST 2 ('fail')
RETURN_VALUE
>> 48 COPY 3
POP_EXCEPT
RERAISE 1
ExceptionTable:
  4 to 32 -> 38 [0]
  38 to 40 -> 48 [1] lasti
```

**ExceptionTable 的格式**：

- 概念上是 5 元组序列：(start_offset, end_offset, target, stack_depth, push_lasti)
- start_offset 包含，end_offset 不包含
- 偏移以"指令"为单位（不是字节）
- 采用变长编码，支持二分查找，O(log n) 查询

**异常抛出时的处理流程**：

1. 用当前指令偏移在 ExceptionTable 中二分查找匹配条目
2. 若无匹配，异常向上传播给调用者
3. 若有匹配：
    - 弹出栈直到匹配条目的 stack_depth
    - 若 push_lasti 为真，把异常抛出点的偏移压栈
    - 把异常（traceback, value, type 三者）压栈
    - 跳转到 target 偏移恢复执行

**关键洞见**：

- **正常路径成本 ≈ 0**：try 块内的字节码执行时，没有任何异常处理相关的指令。`SETUP_FINALLY` / `POP_BLOCK` 完全消失。
- **异常抛出成本略增**：需要查 ExceptionTable + 栈展开，但代价很小。
- **这是典型的"以异常路径的代价换取正常路径的自由"**——符合"异常应该稀有"的工程哲学。

**3.14 的进一步演化**：

- **PEP 765**：禁止在 `finally` 块中使用 `return` / `break` / `continue` 退出。这解决了长期存在的"finally 中的 return 会覆盖 try 块中的 return"的反直觉行为。
- **ExceptionTable 持续微调**：与 3.11 相比，3.14 的字节码细节有变化（如 `CALL` 指令的演化），但 ExceptionTable 的核心机制保持不变。

**第一性原理**：

- **异常控制流 = "正常路径"与"异常路径"的分离**：3.11 之前，两条路径耦合在字节码流中（SETUP_FINALLY 污染正常路径）；3.11 之后，异常路径信息被剥离到静态表，正常路径干净如初。
- **"零成本"不是免费，是"正常路径免费"**：异常抛出时仍需查表+展开，但频率极低，所以 amortized cost 趋近零。这与第 4 章 list 的"均摊 O(1)"是同构思想——**高频路径极致优化，低频路径适度妥协**。
- **ExceptionTable 存放在 code object 上**，因此它是"静态"的——同一个函数的所有调用帧共享同一张表。这就是为什么 code object 可以被安全缓存和共享。

**洞见——为什么 3.11 的 try 块几乎零开销？**

```
import timeit

def with_try():
    try:
        x = 1 + 2
    except Exception:
        pass
    return x

def without_try():
    x = 1 + 2
    return x

# 3.10：with_try 明显慢于 without_try（SETUP_FINALLY/POP_BLOCK 开销）
# 3.11+：两者性能几乎相同（零成本异常处理）
```

这意味着在 3.11+ 中，**防御性 try/except 在热路径上几乎免费**。你可以大胆地写：

```
# 3.11+ 中这是高性能写法
try:
    value = cache[key]
except KeyError:
    value = compute(key)
    cache[key] = value
```

**工业实际**：

```
import dis

def demo():
    try:
        risky_call()
    except ValueError:
        handle_value_error()
    except TypeError:
        handle_type_error()
    finally:
        cleanup()

dis.dis(demo)
# 3.14 输出会显示 ExceptionTable 部分
# ExceptionTable:
#   4 to 32 -> 38 [0]   # try 块范围 → ValueError 处理
#   4 to 32 -> 48 [0]   # try 块范围 → TypeError 处理
#   4 to 56 -> 58 [0]   # 整个 try 块 → finally 处理

# 工程建议：
# 1. 捕获具体异常，不用裸 except:（裸 except 会捕获 KeyboardInterrupt 等）
# 2. 3.14+ 允许 except A, B: 省略括号（PEP 758）
# 3. finally 块中不要再 return/break/continue（PEP 765 禁止）
# 4. 多个异常类型用 except*（3.11+ ExceptionGroup）
```

**3.11+ 异常处理的性能实测意义**：

- **EAFP 风格（Easier to Ask for Forgiveness than Permission）成为主流**：`try: d[k] except KeyError:` 在 3.11+ 几乎与 `if k in d: d[k]` 一样快，而在 3.10 及以前前者明显慢。
- **这是 Python 并发/异步编程的福音**：asyncio 的 TaskGroup、ExceptionGroup 等依赖异常传播，零成本异常处理让大规模异步任务的异常管理开销骤降。

## 第 10 章合体总结：控制流的本质

|控制结构|书里（2.5）|现代（3.14）|核心指令|
|---|---|---|---|
|**if**​|`POP_JUMP_IF_FALSE` + `JUMP_FORWARD`|同上，参数为相对 delta|条件求值 + 条件跳转|
|**for**​|`GET_ITER` + `FOR_ITER` + `JUMP_ABSOLUTE`|`GET_ITER` + `FOR_ITER` + `JUMP_BACKWARD`，`END_FOR` 清理|迭代器协议 + 条件跳转|
|**while**​|`SETUP_LOOP` + `POP_JUMP_IF_FALSE` + `JUMP_ABSOLUTE` + `POP_BLOCK`|移除 SETUP_LOOP/POP_BLOCK，纯跳转|条件跳转 + 向后跳转|
|**异常**​|运行时块栈：`SETUP_FINALLY` / `POP_BLOCK`|零成本：`ExceptionTable` 静态表|异常抛出时查表跳转|

### 三个必须带走的洞见

**洞见一：所有控制流都是"跳转"的语法糖。**

if/for/while/try 在字节码层面只有两种原语——条件跳转（`POP_JUMP_IF_*`）和无条件跳转（`JUMP_*`）。理解这一点，你就能"编译"任何 Python 控制结构到脑中的字节码：**任何复杂的嵌套控制流，拆到底都是这两类指令的组合**。这也是为什么 `goto` 在 Python 中不需要——跳转无处不在，只是被高级语法包装了。

**洞见二：3.11 的"零成本异常处理"是控制流演化的分水岭。**

`SETUP_FINALLY` / `POP_BLOCK` 的移除，本质是**把"异常路径信息"从动态的字节码流中剥离，放到静态的 ExceptionTable 里**。这与第 7 章 pyc 缓存、第 4 章 list 的 free list 是同构思想——**高频路径（正常执行）极致优化，低频路径（异常处理）付出查表代价**。代价交换的结果是：3.11 中 try 块的正常执行路径与无 try 块几乎同速。

**洞见三：跳转指令的相对化（3.11）与循环回边的 NO_INTERRUPT 变体，是"热路径极致优化"的体现。**

`POP_JUMP_IF_FALSE` 的参数从绝对地址改为相对 delta，是为了配合定长 wordcode；`JUMP_BACKWARD_NO_INTERRUPT` 的出现，是因为循环回边不需要检查 Ctrl+C（信号处理），省下每次迭代的系统调用检查。这些微小优化累积起来，就是 3.11 相比 3.10 约 25% 的性能提升的重要组成部分。

### 立刻可做的实验

1. **对比 if 的字节码**：
    
    ```
    import dis
    dis.dis(compile("if a: x=1\nelif b: x=2\nelse: x=3", "<string>", "exec"))
    # 观察三个 POP_JUMP_IF_FALSE 的串联
    ```
    
2. **观察 for 循环的迭代器协议**：
    
    ```
    import dis
    def f(items):
        for x in items:
            process(x)
    dis.dis(f)
    # GET_ITER → FOR_ITER → ... → JUMP_BACKWARD
    ```
    
3. **见证零成本异常处理**：
    
    ```
    import dis
    def f():
        try:
            g(0)
        except:
            return "fail"
    dis.dis(f)
    # 查看 ExceptionTable 部分
    print(f.__code__.co_exceptiontable)  # 原始字节
    ```
    
4. **性能对比（3.11+）**：
    
    ```
    import timeit
    # EAFP vs LBYL 在 3.11+ 几乎同速
    timeit.timeit("try:\n d[k]\nexcept KeyError:\n pass",
                  "d={}; k='missing'", number=1000000)
    timeit.timeit("if k in d:\n d[k]",
                  "d={}; k='missing'", number=1000000)
    ```
    

### 版本差异速查

|书里（Python 2.5）|现代去哪儿找|
|---|---|
|`SETUP_FINALLY` / `POP_BLOCK` 运行时块栈|3.11+ 移除，改用 `ExceptionTable`（零成本异常处理）|
|`POP_JUMP_IF_FALSE(target)` 绝对地址|3.11+ 改为相对 delta，并细分为 `POP_JUMP_IF_FALSE_FORWARD` 等|
|`FOR_ITER` 耗尽时弹出迭代器|3.12+ 不再弹出，由后续 `END_FOR` 清理|
|`BREAK_LOOP` / `CONTINUE_LOOP`|3.11+ 直接编译为 `JUMP_FORWARD` / `JUMP_BACKWARD`|
|`SETUP_LOOP`|3.11+ 移除|
|异常表不存在|3.11+ `co_exceptiontable` 属性|
|无 `JUMP_BACKWARD_NO_INTERRUPT`|3.11+ 新增，循环回边默认使用|
|finally 中可 return/break/continue|3.14 PEP 765 禁止|
|`except A, B:` 必须括号|3.14 PEP 758 允许省略括号|
