
# 《Lua设计与实现》读书笔记 · 第7章　GC算法

> 💡 如果说前六章讲的是 Lua 如何用 C 构造出一个动态类型的"值宇宙"，那么本章讲的就是——**这个宇宙如何自动清理自己**。
> 
> **第一性原理视角**：C 语言的世界里没有自动内存管理，malloc/free 必须成对出现。但 Lua 作为一门动态语言，必须让"创建对象"和"释放对象"对脚本层透明。这就要求在 C 的手动内存世界里，架起一套自动生命期管理系统。**GC 不是 Lua 的"附加功能"，而是 Lua 作为动态语言存在于 C 世界中的"必要条件"**——没有 GC，Lua 的所有堆对象（string、table、closure、userdata、thread）都会瞬间变成悬垂指针的源头。

---

## 7.1　原理

### Lua GC 的演进：从"双色"到"三色"再到"分代"

理解 Lua 5.4 的 GC，必须先看清它走过的路——每一步演进都是为了解决前一步的痛点：

**Lua 5.0：双色标记-清除（Stop-The-World）**

早期 Lua 用最简单的黑/白两色：黑色=可达，白色=不可达。缺点是**必须一次性跑完整个 GC 周期**，中间不能打断——否则就会出现"黑对象指向白对象"的破坏。对于大程序，这一次性停顿可能长达数百毫秒。

**Lua 5.1：三色增量 GC**

引入**灰色**作为中间状态：灰色=对象已访问但其引用尚未完全扫描。三色不变式（tri-color invariant）规定：**黑色对象不能指向白色对象，除非通过写屏障干预**。这一改变让 GC 可以分步执行，把停顿打散到程序运行过程中。

**Lua 5.2：首次尝试分代 GC**

基于"大部分对象要么早死、要么长寿"的分代假说，引入 young/old/touched 三态。但实现过于粗糙——**只要活过一轮 GC 就变成 old**，导致大量本应被回收的临时对象被错误晋升。

**Lua 5.3：移除分代 GC**

因为 5.2 的分代实现效果不佳，5.3 干脆退回纯增量。

**Lua 5.4：重新设计的分代 GC（七态）**

这是本章的重点。Lua 5.4 在增量三色的基础上，重新引入了分代模式，但对象状态从 5.2 的 3 种扩展到 **7 种**：`new → survival → old-0 → old-1 → old → touched-1 → touched-2`。

> 💡 **洞见：为什么是 7 种状态？这是"经验设计"对抗"理论简洁"的胜利**
> 
> 5.2 的失败在于：它假设"活过一轮 = 长寿"，但现实中很多对象会活过一轮然后死掉。5.4 的解法是——**活过两轮才算真正变老**（new → survival → old-_）。这背后的第一性原理是__局部性原理和二八法则_*：一个对象如果被重复使用多次，它大概率会存活很长时间；如果只是偶尔活过一轮，它很可能马上就要死。
> 
> 但 7 态带来了新的复杂度——特别是"不是所有对象同时变老"，所以需要 old-0/old-1/old 三种 old 子状态来区分老化程度，配合写屏障的 back barrier 把 old 对象染成 touched 重新纳入扫描。
> 
> **复杂度在推理上，而不在代码上**——这是 Lua 作者 Roberto 的原话。换句话说，代码量增加不多，但需要严谨证明所有状态转换都保持 GC 正确性。

### 三色标记-清除的核心思想

```
白：未访问（本轮可能回收）
灰：已访问但子引用未扫描完
黑：完全扫描完毕（本轮不回收）
```

GC 循环从根集合（Root Set）出发：

- **根集合**包括：主线程（mainthread）、注册表（registry）、全局环境 `_G`、全局元表、上一轮待终化对象
    
- 从根开始，把直接可达对象由白染灰
    
- 增量地处理灰色对象：染灰其子引用，自身由灰染黑
    
- 当灰色队列清空，进入原子阶段
    
- 原子阶段后，所有仍是白色的对象都是垃圾，进入清除
    

**双白机制（Dual-White）**：Lua 用两个白色（WHITE0 和 WHITE1）交替使用。本轮的"当前白"由 `global_State.currentwhite` 记录；新创建的对象用当前白，上一轮遗留的对象用"另一白"——这样在增量过程中新创建的对象不会和待回收对象混淆。

> 💡 **洞见：双白机制是增量 GC 正确性的基石**
> 
> 如果没有双白，增量 GC 在执行过程中新创建的对象（默认白色）会和"应该被回收的旧白色对象"无法区分。双白让"本轮新对象"和"上轮遗留对象"在颜色上天然区分——这是 5.1 引入增量 GC 时最精巧的一个设计，也是为什么 Lua 的 GC 能在不打断程序的情况下保持正确性。

### 分代模式的工作原理

Lua 5.4 的分代模式**默认不开启**，需要显式通过 `collectgarbage("generational")` 切换。其工作模式：

- **Minor GC（次要收集）**：只扫描 young 对象（new + survival），速度快
    
- **Major GC（主要收集）**：当内存增长到阈值（如上轮的一倍），做一次完整的 stop-the-world 全量收集
    

根据 Lua 作者的基准测试：Conway 生命游戏基准在分代模式下比增量模式快 **35%**，内存略省；二叉树构建遍历基准快 **66%**，内存省 **25%**。且没有基准在分代模式下变慢。

> ⚠️ **重要局限**：Lua 5.4 的分代模式中，**Major GC 仍然是原子 stop-the-world 的**。这个问题要到 Lua 5.5 才会解决（允许主要收集也增量进行）。

🏭 **工业印证**：在游戏主循环中，分代 GC 的价值极大——每帧创建的大量临时对象（向量、碰撞结果、消息封装）都是"早死"的 young 对象，minor GC 能快速清理它们而不必扫描持久的游戏状态表。这就是为什么 Roblox 的 Luau、WoW 的 Lua 环境都极度依赖高效的 GC。

## 7.2　数据结构

GC 的数据结构在第2章 `CommonHeader` 的基础上进一步组织起来。回顾第2章讲过：每个 GC 对象都以 `CommonHeader` 开头，包含 `next`、`tt`、`marked` 三个字段。本章的所有魔法，都建立在 `marked` 字段的位操作上。

### marked 字段的位编码

`marked` 是一个字节，各位含义：

|位|宏|含义|
|---|---|---|
|0|WHITE0BIT|白色类型 0|
|1|WHITE1BIT|白色类型 1|
|2|BLACKBIT|黑色|
|3|FINALIZEDBIT|有终化器待执行|
|4|-|弱值标志|
|5|FIXEDBIT|固定对象（不参与 GC）|
|6|SFIXEDBIT|超级固定对象|

### global_State 中的 GC 链表

Lua 5.4 在 `global_State` 中维护**多个链表**，按对象生命周期阶段分类：

|链表|作用|
|---|---|
|**allgc**​|所有可回收对象的主链表（新对象创建后入此链）|
|**fixedgc**​|永久不回收的对象（如保留字字符串）|
|**finobj**​|带有 `__gc` 元方法的对象|
|**tobefnz**​|待执行终化器的对象|
|**gray**​|标记阶段：待扫描的灰色对象|
|**grayagain**​|原子阶段需要一次性扫描的灰色对象（线程、弱表）|
|**weak**​|弱值表|
|**allweak**​|弱键弱值表|
|**ephemeron**​|弱键表（ephemeron 语义）|
|**twups**​|开放的 upvalue 链表|

**关键认知**：对象在链表中移动反映了其 GC 状态的变化。例如带有 `__gc` 的对象在创建时**直接从 allgc 移到 finobj**；当判定为垃圾时，从 finobj 移到 tobefnz 等待终化。

### GC 状态机

`global_State.gcstate` 跟踪当前 GC 阶段，状态转换如下：

```
GCSpause          → 等待分配阈值触发
    ↓
GCSpropagate      → 增量标记（处理 gray 链表）
    ↓
GCSatomic         → 原子阶段（不可打断）
    ↓
GCSswpallgc       → 清除 allgc 中的垃圾
    ↓
GCSswpfinobj      → 清除 finobj 中的垃圾
    ↓
GCSswptobefnz     → 处理 tobefnz
    ↓
GCSswpend         → 结束清除，准备终化
    ↓
GCScallfin        → 执行终化器
    ↓
回到 GCSpause
```

> 💡 **洞见：为什么需要这么多状态？因为"增量"意味着工作必须可暂停、可恢复**
> 
> 如果 GC 是 stop-the-world 的，只需要"标记→清除"两个阶段。但增量 GC 必须把工作切成小块，每块执行完都要能安全地把控制权交还给程序。所以 Lua 把 GC 切成了 **GCSpropagate（标记）和 GCSswpallgc（清除）这两个可以增量执行的阶段**，中间用 GCSatomic 做不可打断的过渡，最后用 GCScallfin 处理终化器。
> 
> 这是一种**用状态机复杂性换取停顿时间缩短**的经典工程权衡。

## 7.3　具体流程

### 7.3.1　新创建对象

当 Lua 执行 `luaC_newobj` 创建一个新 GC 对象时：

1. 从内存池分配对象，对象头部 `CommonHeader` 的 `marked` 字段初始设为**当前白**（`currentwhite`）
    
2. 对象**立即链入 `allgc` 链表头部**
    
3. 如果对象带有 `__gc` 元方法（userdata），创建时**直接从 allgc 移到 finobj**
    

**增量 GC 下的关键问题**：新对象在 GC 周期中途被创建，它的颜色是"当前白"——这和"上一轮遗留的待回收白对象"在颜色值上是不同的（双白机制）。这保证了新对象不会被误回收。

**写屏障（Write Barrier）**：当程序在 GC 执行期间修改对象引用时，可能破坏三色不变式（黑对象指向白对象）。Lua 用写屏障修复：

- **forward barrier**：当黑对象指向白对象时，把白对象染灰（如 `luaC_barrier`）
    
- **back barrier**：当 old 对象指向 new 对象时，把 old 对象标记为 touched，纳入重新扫描
    

> 💡 **洞见：新对象的"当前白"着色 + 写屏障，是增量 GC 正确性的双保险**
> 
> 双白机制解决了"新对象和垃圾对象颜色混淆"的问题；写屏障解决了"增量过程中引用关系变化"的问题。两者缺一不可——没有双白，新对象可能被误回收；没有写屏障，黑对象引用的白对象可能在清除阶段被错误回收。

### 7.3.2　初始化阶段（GCSpause → GCSpropagate）

`restartcollection` 函数执行初始化：

1. **翻转 currentwhite**：本轮用另一个白色作为"当前白"
    
2. **清空 gray、grayagain、weak 等临时链表**
    
3. **标记根集合**：
    
    - 主线程 `g->mainthread`
        
    - 注册表 `g->l_registry`
        
    - 全局环境 `_G`
        
    - 全局元表 `markmt`
        
    - 上一轮待终化的对象 `markbeingfnz`
        
    
4. 根对象由白染灰，进入 `gray` 链表
    
5. GC 状态切换到 `GCSpropagate`
    

**根集合的选取体现了 Lua 的嵌入哲学**：`_G` 是脚本层的全局入口，registry 是 C 宿主与 Lua 交互的桥梁，主线程是主协程。从这三个根出发，理论上可以到达所有"活"的对象。

### 7.3.3　扫描标记阶段（GCSpropagate）

这是增量 GC 的核心阶段，由 `propagatemark` 函数驱动：

```
while gray 链表非空:
    取出一个灰色对象
    switch 对象类型:
        case Table:      traversetable  → 标记表中所有键值对
        case Closure:    traverseclosure → 标记 upvalue 和 Proto
        case Thread:     移入 grayagain → 原子阶段处理
        case Proto:      traverseproto → 标记常量和调试信息
        case Userdata:   直接染黑，标记元表和环境
        case String:     无需遍历（字符串无引用）
    自身由灰染黑
```

**增量控制**：每次 `singlestep` 只处理有限个灰色对象（通常一个），然后返回，把控制权交还给程序。这就是为什么增量 GC 的停顿时间短——它把"扫描整个堆"这个大任务切成了无数个小任务。

**线程和弱表的特殊处理**：thread 对象和弱表被放入 `grayagain` 链表，它们的重新扫描必须在**原子阶段**一次性完成（不可打断），因为涉及复杂的状态一致性问题。

**写屏障在标记阶段持续生效**：程序在 GC 增量执行期间修改对象引用时，写屏障确保三色不变式不被破坏。

### 7.3.4　回收阶段（GCSswpallgc → GCSswptobefnz）

当灰色链表清空，进入原子阶段 `GCSatomic`：

1. **remarkupvals**：处理开放的 upvalue
    
2. **处理 grayagain**：原子性地重新扫描线程和弱表
    
3. **处理弱表**：清除弱表中 key 或 value 为白色（不可达）的条目
    
4. **分离待终化对象**：`luaC_separateudata` 把 finobj 中不可达但有 `__gc` 的对象移到 `tobefnz`
    
5. **翻转 currentwhite**：为下一轮 GC 准备
    
6. **初始化清除指针**：`sweepgc` 指向 allgc 链表头
    

进入清除阶段 `GCSswpallgc`：

```
while sweepgc 未到链表尾:
    取当前对象
    if 对象是白色（非当前白）:
        从链表中移除
        释放内存
    else:
        重置颜色为下一轮的白色
    sweepgc 前进
```

**清除也是增量的**：`sweepgc` 指针记录当前清除位置，每次 `singlestep` 只清除有限个对象，然后返回。

**带有 `__gc` 的对象**：在 `GCSswpfinobj` 阶段，如果发现 finobj 中的对象是白色（不可达），**不立即释放**，而是移到 `tobefnz` 链表，等待终化器执行。

### 7.3.5　结束阶段（GCSswpend → GCScallfin）

**GCSswpend**：结束清除，检查内存大小，准备进入终化阶段。

**GCScallfin**：执行终化器：

1. 遍历 `tobefnz` 链表中的每个对象
    
2. 在调用 `__gc` 之前**先把对象重新标记为可达**（避免终化器执行期间对象被回收）
    
3. 调用 `__gc` 元方法，把对象作为参数传入
    
4. 终化器执行完毕后：
    
    - 清除 `FINALIZEDBIT` 标记
        
    - 把对象从 `tobefnz` 移回 `allgc` 链表
        
    - 对象将在**下一轮 GC**​ 中被正常回收
        
    

> 💡 **洞见：终化器为什么必须拆分到两轮 GC？**
> 
> 这是 Lua GC 设计中最微妙的一点。考虑以下场景：
> 
> ```
> local obj = {}
> setmetatable(obj, {__gc = function(o) 
>     -- 终化器里可能重新把 obj 赋值给某个全局变量（复活）
>     _G.resurrected = o
> end})
> obj = nil
> collectgarbage("collect")
> ```
> 
> 如果终化器在清除阶段之前执行，终化器代码可能改变引用关系（复活对象），这会破坏已经完成的标记结果。所以 Lua 的策略是：
> 
> 1. **第一轮 GC**：识别带 `__gc` 的垃圾对象 → 移到 `tobefnz` → 执行 `__gc` → 对象复活回 `allgc`
>     
> 2. **第二轮 GC**：复活的 obj 如果再次不可达，正常回收
>     
> 
> 这就是为什么**带 `__gc` 的对象至少要经历两轮 GC 才能被真正释放**。这个设计保证了终化器执行期间引用关系变化的安全性，代价是对象生命周期延长一轮。

🏭 **工业印证**：在游戏开发中，如果用 `__gc` 管理 GPU 资源句柄（纹理、缓冲区），开发者必须意识到——**资源不会在调用 `collectgarbage` 后立即释放，可能要等下一轮 GC**。这就是为什么游戏引擎通常会显式调用 `texture:release()` 而不是依赖 `__gc` 做确定性资源管理。Lua 5.4 引入的 to-be-closed 变量（`<close>` 属性）正是为了解决这个问题——提供确定性的资源释放，而不依赖 GC 的时机。

## 7.4　进度控制

Lua 5.4 的 GC 进度控制通过 `collectgarbage(opt, arg)`（Lua 层）或 `lua_gc(L, opt, arg)`（C 层）进行。

### 增量模式的三参数

|参数|含义|默认值|
|---|---|---|
|**pause**​|上一轮 GC 后，内存使用达到多少百分比时启动新一轮（以 % 计）|200（即内存翻倍才启动）|
|**stepmultiplier**​|GC 速度相对于内存分配速度的倍数|100|
|**stepsize**​|每次增量步骤分配多少字节后执行一步（对数尺度，2^n 字节）|13（≈8KB）|

**pause 参数详解**：pause=200 意味着"上一轮 GC 后内存使用量翻倍，才启动新一轮"。pause ≤ 100 表示不等待，立即启动。pause 越大，GC 越不激进，内存占用越高但 CPU 开销越低。

**stepsize 参数详解**：这是对数参数，stepsize=13 表示每次分配 2^13 = 8192 字节后执行一步。stepsize=60 相当于禁用了增量（变成 stop-the-world），因为步长太大了。

### 分代模式的两参数

|参数|含义|
|---|---|
|**minormultiplier**​|控制 minor GC 的频率|
|**majormultiplier**​|控制 major GC 的触发阈值|

分代模式下，minor GC 频繁执行（只扫描 young 对象），当内存压力达到 `majormultiplier` 阈值时，执行一次 stop-the-world 的 major GC。

### 模式切换

Lua 5.4 允许在增量和分代模式间动态切换：

- **切换到分代**：`collectgarbage("generational")`
    
- **切换回增量**：`collectgarbage("incremental")`
    

切换的触发条件基于内存增长模式：

- 如果 minor GC 后内存增长超过上轮的 1 倍 → 执行 major GC
    
- 如果 major GC 回收的内存不到增长量的一半（bad collection）→ 临时切回增量模式做一轮完整扫描
    
- 如果完整扫描后存活对象增长小于上轮的 1/8 → 切回分代模式
    

> 💡 **洞见：GC 参数调优的本质是"在停顿时间和内存占用之间找平衡点"**
> 
> 这是第一性原理在工程上的直接体现：没有任何一组 GC 参数对所有程序都是最优的。Lua 官方文档明确说"GC 行为在不同平台、不同 Lua 版本间是不可移植的，最优设置同样不可移植"。
> 
> **调优方向**：
> 
> - 实时系统（游戏帧循环、嵌入式控制）→ 降低 pause，增大 stepsize，让 GC 步子大但频率低，避免帧内卡顿
>     
> - 批处理程序（编译器、离线处理）→ 直接 `collectgarbage("stop")` 关闭 GC，程序退出时 OS 自动回收所有内存
>     
> - 长连接服务器（OpenResty、Skynet）→ 分代模式 + 适当的 minormultiplier，让 young 对象快速回收
>     

🏭 **工业最佳实践**：

**1. 游戏主循环中的 GC 控制**：

```
function game_frame()
    -- 关键渲染逻辑前，确保 GC 不捣乱
    collectgarbage("stop")  -- 关键路径禁用 GC
    
    render_scene()
    update_physics()
    
    -- 帧末允许 GC 增量执行
    collectgarbage("restart")
    collectgarbage("step", 100)  -- 手动推进 100 步
end
```

**2. OpenResty 中的 GC 调优**：

```
lua_gc_mode nginx;  # 使用分代 GC
lua_gc_minor_multiplier 20;  # 调整 minor GC 频率
```

每个请求创建的临时对象在请求结束时通过 minor GC 快速清理，避免污染 long-lived 的全局状态。

**3. 内存敏感场景的 emergency collection**：

```
local mem = collectgarbage("count")  -- 当前内存使用量(KB)
if mem > HARD_LIMIT then
    collectgarbage("collect")  -- 强制全量回收
end
```

**4. Roberto 的性能建议**：

> "Lua 的 GC 是为平均程序调优的。如果你的程序创建和释放大量内存，可以通过 `collectgarbage` 更好地调优。对于批处理程序，永远停止 GC 可能是选项——因为程序退出时所有内存都会被 OS 回收，GC 反而是浪费。"

## 贯穿第7章的核心洞见

读完本章，我想留下五条**超越书本身的认知**：

**1. GC 不是 Lua 的"附加功能"，而是"存在前提"**

在 C 的手动内存世界里，Lua 要想提供动态类型的自动内存管理，必须在堆对象上架设一套生命期系统。**GC 与 `TValue`/`GCObject` 是同一枚硬币的两面**——没有 GC，`marked` 字段毫无意义；没有 `CommonHeader`，GC 无从遍历对象。

**2. 三色标记的本质是"把原子操作拆成可中断的增量操作"**

灰色状态的存在，让"标记整个堆"这个不可打断的大操作，变成了"每次处理一个灰色对象"的可中断小操作。**写屏障 + 双白机制**是保证拆散后正确性的两大支柱。

**3. 分代 GC 的七态设计是"经验主义"对"理论简洁"的胜利**

5.2 的 3 态分代失败，是因为它用"活过一轮 = 长寿"这个过于简单的启发式。5.4 的 7 态设计承认了现实世界的复杂性——对象老化是渐进的，需要用 `new → survival → old-*` 的多步演化来逼近真实的生命周期分布。**复杂度在推理，不在代码**——这是 Lua 作者最值得品味的工程哲学。

**4. 终化器的"两轮 GC"设计是对"不确定性"的妥协与驯服**

`__gc` 元方法里的代码可能复活对象、可能改变引用关系、可能引发新的分配。Lua 选择把终化器放到 GC 流程最后，并拆分到两轮 GC 中执行——**用对象生命周期的延长，换取了引用关系一致性**。这也是为什么 Lua 5.4 要引入 to-be-closed 变量：在需要确定性资源释放的场景，不要依赖 GC 的时机。

**5. GC 调优没有银弹，只有权衡**

pause、stepmultiplier、stepsize（增量模式）或 minormultiplier、majormultiplier（分代模式）——所有参数的本质都是在**停顿时间 vs. 内存占用 vs. CPU 开销**这个三角中寻找平衡点。Lua 官方手册明确警告：GC 行为跨平台、跨版本不可移植，最优设置同样不可移植。**真正的工业级 Lua 应用，必须在目标环境下实测调优，而不是照搬任何"最佳配置"**。

---

**工业应用的统一视角**：

- **游戏行业**：分代 GC + 帧末手动 step，让 young 对象（每帧的临时向量、碰撞结果）快速回收，同时避免帧内卡顿
    
- **Web 服务器（OpenResty）**：每个请求是天然的 young 对象生成器，分代 GC 的 minor collection 完美匹配请求生命周期
    
- **嵌入式系统**：step size 调大、pause 调大，让 GC 尽量少打扰实时控制循环
    
- **批处理程序**：直接关闭 GC，依赖 OS 在进程退出时回收所有内存
    
- **资源管理**：对于需要确定性释放的资源（文件句柄、网络连接、GPU 资源），使用 to-be-closed 变量（`<close>`）而非 `__gc`——因为后者至少要两轮 GC 才能释放
