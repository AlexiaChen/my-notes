
# 第12章 终结与弱引用 —— 读书笔记

如果说前几章回答了"虚拟机如何执行、如何回收、如何跨语言互操作、如何抛出和处理异常"，那么第12章要回答的是一个让"对象清理"从"隐式"走向"显式可控"的根本问题——**当对象即将死去，虚拟机如何在"自动回收"与"资源清理"之间建立一套既精确又可编程的机制？**​ 这就是"终结（Finalization）与弱引用（Weak References）"。李晓峰在这一章实际上在讲一个被工业界反复打磨的真理——**终结是 JVM 最早的"对象临终钩子"尝试，但它因时机不确定、可能复活对象、拖慢 GC 而被现代 Java 废弃；弱引用体系（Soft/Weak/Phantom + ReferenceQueue）则是 JVM 给出的"精确可达性编程"答案，它让程序员能够细粒度地表达"对象在什么可达性状态下应该被如何处理"**。理解这一章，你才能理解为什么 Java 9 把 `finalize()` 标记为废弃、Java 18 将其标记为"弃用待移除"、为什么 `Cleaner` API 和 `PhantomReference` 成为现代资源清理的首选。

结合 `java.lang.ref` 包规范、Oracle HotSpot FAQ 对软引用的策略说明、Oracle 官方关于 finalization 内存滞留的文章，以及 JEP 421（Java 18 将 finalization 标记为 deprecated for removal）的工业演进，我来梳理这一章的脉络，并注入一些第一性原理层面的思考。

## 12.1 终结：JVM 最初的"临终钩子"及其原罪

终结机制的设计初衷是优雅的——**让对象在被 GC 回收之前，有机会释放它持有的非内存资源**（文件句柄、socket、数据库连接、堆外内存）。程序员只需重写 `Object.finalize()` 方法：

```
@Override
protected void finalize() throws Throwable {
    try {
        // 释放资源
    } finally {
        super.finalize();
    }
}
```

**HotSpot 的 FinalReference 机制**：

HotSpot 内部通过一种特殊的 `FinalReference`（它是 `WeakReference` 和 `PhantomReference` 之间的内部引用类型）来追踪需要终结的对象。当一个对象被创建且其类重写了非平凡的 `finalize()` 方法时：

1. JVM 立即为该对象创建一个 `FinalReference` 实例
    
2. 这个 `FinalReference` 被加入一个全局链表，使其对 GC 保持"finalizer-reachable"
    
3. GC 在标记阶段发现对象仅 finalizer-reachable 时，将其加入 finalize 队列
    
4. `Finalizer` 线程异步执行 `finalize()` 方法
    
5. `finalize()` 执行完毕后，该对象失去 `FinalReference` 引用，下次 GC 才能真正回收
    

> ⚠️ **洞见（本章核心判断之一）**：终结机制的原罪不是"慢"，而是**"三个不确定性"**——
> 
> **1. 时机不确定性**：GC 决定何时调用 `finalize()`，可能几秒、几分钟、甚至永远不调用（如果对象始终强可达，或 JVM 在 finalize 前就退出了）。用 finalize 管理文件句柄，可能在大流量下积累成"Too many open files"错误。
> 
> **2. 复活可能性**：`finalize()` 中执行 `this.rescue = this` 即可"复活"对象。复活后该对象在本次生命周期内不会再被 finalize（因为 finalize 最多调用一次），如果它再次变得不可达，将**没有第二次机会**做清理——资源泄漏就此发生。
> 
> **3. GC 周期不确定性**：需要终结的对象至少需要**两次 GC 周期**才能真正回收——第一次 GC 发现对象 finalizer-reachable，加入 finalize 队列；Finalizer 线程执行 finalize()；第二次 GC 才能回收。在内存紧张时，这种"额外 GC 周期"会加剧性能问题。

正是这三个不确定性，让 `finalize()` 在 Java 9 被正式废弃（deprecated），在 Java 18 被标记为"弃用待移除"（JEP 421）。Oracle 官方明确表示："The use of finalization can lead to problems with security, performance, and reliability."

## 12.2 为何需要弱引用：从"隐式钩子"到"显式可达性编程"

终结机制的失败，暴露了一个根本性问题——**对象清理不应该与对象生命周期"隐式绑定"**。程序员需要的是一种机制，能够：

1. 在不阻止对象被 GC 回收的前提下，仍然持有对该对象的"引用"
    
2. 在对象被回收的"某个时刻"，得到通知并执行清理动作
    
3. 对清理时机、顺序、复活行为有精确控制
    

这就是弱引用体系要解决的问题——**它把"引用强度"从二元的"强/无"扩展为连续的"强/软/弱/虚"光谱**，让程序员能够精确表达"我希望这个对象在什么可达性状态下存活"。

`java.lang.ref` 包规范明确定义了四种引用类型，从最强到最弱：

|引用类型|可达性定义|GC 行为|主要用途|
|---|---|---|---|
|**Strong**​|通过非引用对象可达|绝不回收|默认对象引用|
|**Soft**​|非强可达，但通过软引用可达|内存不足时回收（OOM 之前）|内存敏感缓存|
|**Weak**​|非强/软可达，但通过弱引用可达|下一次 GC 立即回收|规范化映射（如 WeakHashMap）、防止监听器泄漏|
|**Phantom**​|非强/软/弱可达，已 finalize，且被虚引用引用|随时回收，但回收后入队通知|替代 finalize 的灵活清理|

> 💡 **洞见**：弱引用体系的本质，是把"可达性"从 JVM 的内部概念**显式暴露给程序员**。在只有强引用的世界里，程序员要么"持有对象"（阻止回收），要么"不持有"（无法得到回收通知）；弱引用体系让程序员能够说——"我希望这个缓存对象在内存充足时存活，在内存紧张时被回收"（Soft）、"我希望这个监听器在它观察的主体被回收时自动解除注册"（Weak）、"我希望在这个对象死后执行清理但绝对不允许复活"（Phantom）。**这是编程语言对"对象生命周期"建模能力的一次质变**——从"二元生死"到"连续可达性光谱"。

## 12.3 对象生存期状态：可达性状态机

这是全章最具"形式化"质感的部分——JVM 规范精确定义了对象的五种可达性状态，它们反映了对象生命周期的连续演变：

```
强可达 (Strongly Reachable)
   ↓ 所有强引用消失
软可达 (Softly Reachable)
   ↓ GC 在内存压力下清除软引用
弱可达 (Weakly Reachable)
   ↓ GC 清除弱引用
    ↓（如果有 finalize 方法且未执行）
finalizer-reachable → Finalizer 线程执行 finalize()
    ↓
虚可达 (Phantom Reachable)  ← PhantomReference 指向对象
   ↓ PhantomReference 被清除或不可达
不可达 (Unreachable)  ← 真正可回收
```

**关键状态转换细节**：

1. **强 → 软 → 弱**：这是一个"引用强度递减"的过程。当对象失去更强的引用时，它"跌入"下一个较弱的可达性状态。
    
2. **弱 → finalizer-reachable**：如果一个对象仅通过弱引用可达，且它有非平凡的 `finalize()` 方法，那么清除弱引用并不直接让对象不可达——它还要经过 finalization 阶段。这就是为什么带 finalize 的对象需要两次 GC 周期。
    
3. **finalizer-reachable → 虚可达**：finalize() 执行完毕后，对象进入虚可达状态。**此时即使有 PhantomReference 指向它，对象也无法被复活**——PhantomReference.get() 永远返回 null。
    
4. **虚可达 → 不可达**：当所有 PhantomReference 被清除或自身不可达时，对象真正变为不可达，内存可被回收。
    

### 12.3.1 对象状态转换的工业实现

HotSpot 在 GC 的标记阶段处理这些状态转换。以 G1 GC 为例：

- **并发标记阶段**：标记线程遍历对象图，当遇到 SoftReference/WeakReference/PhantomReference 时，检查其 referent 是否已被标记
    
- **引用处理阶段**：对未被标记的 referent，根据引用类型执行不同动作：
    
    - SoftReference：根据 `SoftRefLRUPolicyMSPerMB` 策略决定是否清除（见 12.4 节）
        
    - WeakReference：立即清除 referent，将 WeakReference 自身加入 pending 链表
        
    - PhantomReference：将 referent 置为 null（但对象内存暂不释放），将 PhantomReference 自身加入 pending 链表
        
    
- **pending → ReferenceQueue**：ReferenceHandler 线程（MAX_PRIORITY 守护线程）从 pending 链表取出引用，enqueue 到关联的 ReferenceQueue
    

### 12.3.2 引用队列（ReferenceQueue）：可达性变化的"通知总线"

引用队列是弱引用体系的"神经系统"——**当引用指向的对象可达性发生变化时，JVM 将该引用对象本身（不是被引用对象）加入关联的队列**。

程序员通过两种方式从队列中获取引用：

- **轮询**：`referenceQueue.poll()` —— 非阻塞，队列为空时返回 null
    
- **阻塞等待**：`referenceQueue.remove()` —— 阻塞直到有引用可用
    

Oracle 官方文章给出了一个工业级模式——用后台线程持续从队列中取出引用并清理关联资源：

```
static void drainRefQueueLoop() {
    while (true) {
        NativeImage3 nativeImg = (NativeImage3) refQueue.remove();
        nativeImg.dispose();  // 释放关联的原生资源
    }
}
```

或者，如果不想引入新线程，可以在分配新资源前"有限度地"清理队列：

```
static final int MAX_ITERATIONS = 2;
static void drainRefQueueBounded() {
    for (int i = 0; i < MAX_ITERATIONS; i++) {
        NativeImage3 nativeImg = (NativeImage3) refQueue.poll();
        if (nativeImg == null) break;
        nativeImg.dispose();
    }
}
```

### 12.3.3 引用对象状态转换：Reference 类的内部状态机

每个 `Reference` 对象（SoftReference/WeakReference/PhantomReference 的实例）自身也经历一个状态机：

```
Active → Pending → Enqueued → Inactive
```

- **Active**：新创建的引用对象处于此状态。referent 字段指向被引用对象
    
- **Pending**：GC 发现 referent 不可达，将引用对象加入 pending 链表，等待 ReferenceHandler 线程处理
    
- **Enqueued**：引用对象被加入关联的 ReferenceQueue
    
- **Inactive**：从 ReferenceQueue 中取出后，引用对象永久变为 Inactive，referent 必定已被回收
    

> 💡 **洞见**：引用对象自身的状态机与被引用对象的可达性状态机是**两套并行运转的状态机**。前者追踪"引用对象在队列中的生命周期"，后者追踪"被引用对象在 GC 眼中的生死"。程序员通过 ReferenceQueue 观察到的，是引用对象从 Pending 到 Enqueued 的转换——这一转换恰好发生在被引用对象"死亡"的时刻附近。**这种"双状态机"设计，是 JVM 在"对象回收"和"程序员通知"之间建立的精确桥梁**。

## 12.4 引用对象实现：HotSpot 的 ReferenceProcessor

这一节是全章最具"HotSpot 内部视角"的部分——JVM 如何在 GC 中处理这些特殊引用？

HotSpot 中所有 GC 实现（Serial/Parallel/G1/ZGC）都遵循统一的引用处理框架——`ReferenceProcessor`。在 GC 标记阶段完成后、对象清理之前，调用 `ReferenceProcessor::process_discovered_references` 函数处理发现的特殊引用。

**处理流程**：

1. **SoftReference 处理**：根据策略决定是否清除
    
    - **AlwaysClearPolicy**：始终清除软引用（通过 `-XX:+ClearAllSoftReferences` 或 Full GC 时使用）
        
    - **LRUMaxHeapPolicy**（Server VM 默认）：基于堆空闲空间计算软引用的存活时间，公式为 `lifetime = free_heap_MB × SoftRefLRUPolicyMSPerMB`
        
    - **LRUCurrentHeapPolicy**（Client VM 默认）：基于当前堆大小计算
        
    
    Oracle HotSpot FAQ 明确指出：Server VM 使用最大可能堆大小（-Xmx）计算空闲空间，因此**倾向于扩大堆而非清除软引用**；Client VM 使用当前堆大小，因此**倾向于清除软引用而非扩大堆**。
    
2. **WeakReference 处理**：直接清除 referent，将 WeakReference 自身加入 pending 链表
    
3. **PhantomReference 处理**：将 referent 置为 null（但对象内存暂不释放），将 PhantomReference 自身加入 pending 链表
    
4. **FinalReference 处理**：将 referent 标记为存活（避免本次 GC 回收），并将 FinalReference 加入 finalize 队列，等待 Finalizer 线程执行 finalize()
    

> 💡 **洞见（本章核心判断之二）**：`ReferenceProcessor` 的设计揭示了一个深刻的工程哲学——**"特殊引用的处理，本质是 GC 算法的'插件点'"**。HotSpot 的 GC 框架在标记完成后统一调用 `process_discovered_references`，但具体如何处理每种引用，由各个引用类的语义决定。这种设计让：
> 
> - **GC 算法与引用语义解耦**：Serial/Parallel/G1/ZGC 可以共享同一套引用处理框架
>     
> - **引用类型可扩展**：JVM 内部可以引入新的引用类型（如 FinalReference），而不需要修改每个 GC 算法
>     
> - **处理顺序可优化**：GC 可以先处理弱引用（清除 referent），再处理虚引用（入队通知），最后处理 FinalReference（加入 finalize 队列）
>     
> 
> 这是"策略模式"在 GC 内核中的经典应用——**引用对象是"策略"，ReferenceProcessor 是"上下文"，GC 标记算法是"客户端"**。

## 12.5 引用对象处理顺序：一个被严重误解的细节

这是全章最微妙、也最容易被错误理解的部分——**不同类型的引用，在 GC 中的处理顺序是什么？**

Stack Overflow 上的实验给出了清晰的答案：

```
// 弱引用和虚引用指向同一个对象
WeakReference wRef = new WeakReference(obj, queue);
PhantomReference pRef = new PhantomReference(obj, queue);
obj = null;

// 第一次 GC 后：
// weak reference enqueued after 1 gc polls
// 对象开始 finalize
// phantom reference enqueued after 2 gc polls（finalize 完成后）
```

**关键发现**：

1. **WeakReference 入队时机**：在对象被真正回收之前（或恰好在 finalization 开始时）。这意味着——**如果在 finalize() 中通过弱引用"复活"对象，理论上是有可能的**（尽管这是不推荐的反模式）。
    
2. **PhantomReference 入队时机**：在对象完成 finalize() 之后。这意味着——**通过虚引用永远无法"复活"对象，因为 PhantomReference.get() 永远返回 null，且对象已经走过 finalization**。
    
3. **处理顺序的不确定性**：JVM 规范**不保证**引用入队的拓扑顺序。即使对象 A 引用对象 B，且 A、B 都变为不可达，JVM 也不保证 ref(A) 先于 ref(B) 入队。JVM 规范 2.17.7 节明确指出："The Java virtual machine imposes no ordering on finalize method calls."
    

> ⚠️ **工业现实**：这个"无顺序保证"的特性，对使用 `PhantomReference` + `ReferenceQueue` 做资源清理的程序员意义重大——**你不能假设清理动作的执行顺序与对象间的引用拓扑一致**。如果你的清理逻辑依赖于"先清理 B 再清理 A"（因为 A 依赖 B 的资源），你必须自己在清理代码中处理这种依赖关系，而不能依赖 JVM 的入队顺序。Guava 的 `FinalizableReferenceQueue` 就是为了解决这个问题而设计的——它通过在清理线程中抛出异常来主动终止清理，避免未处理的引用泄漏。

> 💡 **洞见（本章核心判断之三）**：引用处理顺序的"不确定性"，揭示了 JVM 设计的一个深层原则——**"GC 是并行的、批量处理的，而不是串行的、拓扑排序的"**。GC 在标记阶段一次性发现所有不可达对象，然后在引用处理阶段批量处理它们的特殊引用。这种"批量处理"是 GC 高性能的根本原因，但代价是放弃了"拓扑顺序保证"。程序员如果需要在资源清理中维持顺序依赖，必须自己显式管理——这是"性能与语义"的经典权衡。Oracle 官方文章坦言："total reliance on the garbage collector to identify unreachable objects so that their associated native resources can be reclaimed has a serious flaw: Memory is typically plentiful, and guarding a potentially scarce resource with a plentiful one is not a good strategy."——**用"充裕的资源（内存）"去守护"稀缺的资源（文件句柄）"本身就是错误的策略**，因为 GC 的触发时机不可预测。

## 贯穿第12章的三条暗线（承上启下）

1. **"对象清理"从"隐式钩子"演进为"显式可达性编程"**：finalize() 是原初的尝试，但因时机不确定、可能复活、拖慢 GC 而被废弃；弱引用体系（Soft/Weak/Phantom + ReferenceQueue）则是 JVM 给出的精确答案——它让程序员能够细粒度表达"对象在什么可达性状态下应该被如何处理"。这是编程语言对"对象生命周期"建模能力的一次质变。
    
2. **"双状态机"是引用体系的精髓**：被引用对象经历"强→软→弱→finalizer→虚→不可达"的可达性状态机；引用对象自身经历"Active→Pending→Enqueued→Inactive"的生命周期状态机。两套状态机并行运转，通过 ReferenceQueue 桥接，让程序员能够在"对象死亡"的精确时刻执行清理。
    
3. **"GC 是批量处理，不是拓扑排序"**：引用处理顺序的不确定，是 GC 高性能的代价。程序员若需要在资源清理中维持顺序依赖，必须自己显式管理。这揭示了"性能与语义保证"的经典权衡——JVM 选择性能，把语义保证的责任交还给程序员。
    

---

**本章最核心的一句话**：终结与弱引用的本质，是 JVM 在"自动回收"与"资源清理"之间建立的**可编程桥梁**——**finalize() 是初代尝试但因"时机不确定、可能复活、拖慢 GC"而被现代 Java 废弃（Java 9 废弃、Java 18 弃用待移除）；弱引用体系通过 Soft/Weak/Phantom 三种渐弱的引用强度 + ReferenceQueue 通知机制，让程序员能够精确表达"对象在什么可达性状态下应该被如何处理"；HotSpot 的 ReferenceProcessor 在 GC 标记后统一处理这些特殊引用；而引用处理顺序的不确定，是 GC 批量处理高性能的必然代价**。理解这套"可达性编程"模型，你就拿到了看懂现代 Java 资源清理（Cleaner API、PhantomReference）、内存敏感缓存（SoftReference）、规范化映射（WeakHashMap）设计哲学的钥匙。

> 📌 **工业实践提示**：本章知识的直接应用包括——
> 
> - **资源清理首选 `try-with-resources` + `AutoCloseable`**（确定性、异常安全）
>     
> - **最后安全网用 `Cleaner` API（Java 9+）**：注册 `PhantomReference` + `Runnable`，在对象变为虚可达后执行清理，避免复活风险
>     
> - **内存敏感缓存用 `SoftReference`**：通过 `-XX:SoftRefLRUPolicyMSPerMB` 调节存活时间
>     
> - **规范化映射/监听器用 `WeakReference`**：如 `WeakHashMap` 的 key，避免内存泄漏
>     
> - **切勿用 `finalize()` 管理稀缺资源**：时机不确定可能导致"Too many open files"
>     
> - **切勿假设引用入队顺序**：清理逻辑若有依赖，必须显式管理
>     
> - **警惕 FinalReference 的隐性开销**：任何重写了非平凡 `finalize()` 的对象，在创建时就产生 FinalReference 开销，即使对象从未被回收
