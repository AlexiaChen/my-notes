
# 第9章 垃圾回收支持 —— 读书笔记

如果说第5章回答了"有哪些 GC 算法"、第8章回答了"如何逆向遍历调用栈"，那么第9章要回答的是一个让前面所有讨论**真正落地**的问题——**当 GC 在某个 Safepoint 触发时，虚拟机如何精确地知道"此刻堆外哪些位置持有对象引用"？如何让 GC 既能准确枚举根集、又能自由移动对象，同时还不破坏正在执行本地代码的线程的正确性？**​ 这就是"垃圾回收支持（GC Support）"。李晓峰在这一章实际上在讲一个被工业界反复打磨的真理——**GC 不是孤立运行的，它需要虚拟机每一个子系统（解释器、JIT、栈展开、本地接口、同步系统）的协同配合，才能做到"精确、安全、可移动"**。这是"准确式 GC（Exact GC）"能够成立的底层支柱，也是 HotSpot 区别于早期 Classic VM 的"全 handle 设计"的关键演进。

结合 OpenJDK HotSpot 官方术语表、Oracle JNI 设计规范、OpenJDK 邮件列表中对 JNI handle 的权威澄清，以及 HotSpot Server Compiler 的 oop map 设计论文，我来梳理这一章的脉络，并注入一些第一性原理层面的思考。

## 9.1 为何需要垃圾回收支持：从"保守式"到"准确式"的必然

要理解为什么 GC 需要"全 VM 的支持"，首先要理解 GC 根枚举的两种哲学：

**保守式 GC（Conservative GC）**：不要求 VM 精确知道栈上哪些是引用。GC 从已知根位置开始扫描内存，把每个字都"猜测"为可能指向堆的指针（通过边界检查、对齐检查等启发式规则），然后递归标记。优点是实现简单——VM 无需为 GC 生成任何元数据；缺点是**无法支持对象移动**（因为无法确定某个字是真指针还是假指针，移动对象后无法安全更新"疑似指针"），且可能误标导致内存无法回收。

**准确式 GC（Exact GC）**：VM 精确知道内存中每个位置的类型——这个字是整数、是浮点数、还是对象引用。HotSpot、JRockit、J9 等现代 JVM 均采用准确式 GC。在 HotSpot 中，这个"类型映射表"叫做 **OopMap**（Ordinary Object Pointer Map）；在 JRockit 中叫 livemap；在 J9 中叫 GC map；在 Apache Harmony DRLVM 中也叫 GCMap——**本质相同，名字各异**。

> 💡 **我的洞见**：从保守式到准确式的演进，是 GC 设计的第一性原理级跃迁——**"精确性"换来了"可移动性"**。保守式 GC 因为不敢确定栈上的字是不是真引用，所以对象不能移动（移动后无法更新"疑似指针"）；准确式 GC 因为确切知道哪些位置是引用，所以可以放心移动对象（移动后只需更新已知的引用位置）。而"准确"不是 GC 自己就能做到的，它要求**解释器、JIT 编译器、栈展开机制、本地接口、同步系统**全部配合，在正确的时刻生成并维护"引用位置元数据"。这就是为什么"GC 支持"需要单独成章——它不是 GC 组件的内部事务，而是**整个虚拟机对 GC 的"共同承诺"**。

准确式 GC 要求 VM 在以下五个场景中都能精确枚举引用：

1. **Java 代码**（解释器执行 + JIT 编译代码）
    
2. **本地代码**（C/C++ native 方法）
    
3. **Java ↔ 本地转换边界**
    
4. **同步方法**（monitor 持有的对象）
    
5. **全局根集**（静态字段、JNI 全局引用等）
    

## 9.2 在 Java 代码中支持垃圾回收：OopMap 与 RegisterMap

这是全章最核心的部分——HotSpot 如何在 Java 代码执行时，让 GC 精确知道栈和寄存器中的引用位置。

### 9.2.1 GC-Map（OopMap）：JIT 编译器的"引用位置地图"

HotSpot 官方术语表明确定义：

> **GC map**：A description emitted by the JIT (C1 or C2) of the locations of oops in registers or on stack in a compiled stack frame. Each code location which might execute a safepoint has an associated GC map. The GC knows how to parse a frame from a stack, to request a GC map from a frame's nmethod, and to unpack the GC map and manage the indicated oops within the stack frame.

OopMap 的生成时机有三处：

**1. 类加载时**：HotSpot 在类加载过程中，计算该类对象内"什么偏移量上是什么类型的数据"，生成对象内的 OopMap。这样从对象向外扫描时是准确的。

**2. 解释器执行时**：解释器可以自动生成 OopMap 供 GC 使用——因为解释器的栈帧布局是高度规则的（局部变量表 + 操作数栈），引用位置可静态推导。

**3. JIT 编译时**：这是最精妙的部分。JIT (C1/C2) 在生成机器码的同时，在**每个 Safepoint**​ 处生成一个 OopMap，记录"执行到这条指令时，栈上和寄存器中哪些位置是对象引用"。

**为什么是 Safepoint 而不是每条指令？**​ 如果对每条指令都生成 OopMap，开销太大。HotSpot 采取"在 Safepoint 处生成 OopMap"的策略——Safepoint 通常位于：

- 方法返回前
    
- 循环回边
    
- 方法调用点（call 之后）
    
- 可能抛出异常的位置
    

在这些位置上，对象引用基本趋于稳定（很少产生和删除），恰好适合 GC 枚举根集。

**OopMap 的物理载体**：在 HotSpot 中，OopMap 数据存储在编译后的 `nmethod`（native method）中，与机器码、异常表、调试信息一同压缩存储。GC 在 Safepoint 时，根据当前 PC 值查找对应的 OopMap，解析出哪些栈槽/寄存器持有 oop。

JIT 编译器中 OopMap 的生成逻辑位于 `Compile::BuildOopMaps()`（源码 `buildOopMap.cpp`），在寄存器分配阶段收集每个 Safepoint 处的引用位置信息，最终打包进 `nmethod`。

### 9.2.2 带寄存器的栈展开：RegisterMap 的作用

这是全章最具"HotSpot 内部视角"的部分。当 GC 需要展开一个 JIT 编译的栈帧时，面临一个挑战——**引用可能不在栈上，而在寄存器中**。

现代 CPU 有 16-32 个通用寄存器，JIT 编译器会尽可能把热点变量（包括对象引用）分配到寄存器中，而非栈槽。当 GC 需要枚举根时，它必须知道"当前哪些寄存器持有 oop"。

**两个同名但不同物的"Register Map"**：

- **JIT 编译器内部的 RegisterMap**：是寄存器分配算法的瞬态中间数据结构（基于图着色或线性扫描），编译完成后即丢弃，**与 GC 完全无关**。开发者无法通过 JVM TI 或 JFR 观察到它。
    
- **HotSpot 运行时的 RegisterMap 类**（`registerMap.hpp`）：用于 GC 安全点扫描栈帧时**定位 oop 引用位置**，与 JIT 寄存器分配无关。
    

> ⚠️ **重要澄清**：很多资料混淆这两个 "RegisterMap"。正确理解是——JIT 编译时的寄存器分配信息**不会**以"RegisterMap"形式暴露给 GC；JIT 会在每个 Safepoint 处将"当前哪些寄存器持有 oop"编码进 OopMap。GC 在栈展开时，通过 `RegisterMap` 类（运行时结构）配合 OopMap，恢复被调用者保存的寄存器的内容——因为如果引用在某个被调用者保存寄存器中，且该寄存器的值已被 spill 到栈上，GC 必须能从栈上找到它。

**栈展开的完整流程**（GC 视角）：

```
1. 从线程栈顶帧开始
2. 读取当前帧的 OopMap（根据 PC 定位）
3. 解析 OopMap：栈上哪些槽 + 哪些寄存器持有 oop
4. 对于这些"寄存器中的 oop"，通过 RegisterMap 找到其实际存储位置
   （可能在物理寄存器中，也可能已被 spill 到栈上）
5. 标记这些 oop 为存活
6. 调用 frame::sender(RegisterMap*) 推导调用者帧
7. 重复 2-6，直至栈底
```

> 💡 **洞见**：OopMap + RegisterMap 的配合，揭示了准确式 GC 的一个精髓——**"引用位置的元数据"与"引用值的实际存储"分离**。OopMap 告诉 GC "引用在哪里"（栈槽编号 / 寄存器编号），RegisterMap 帮助 GC 在跨帧展开时"找回寄存器的值"（因为被调用者保存寄存器可能在调用者帧中被 spill）。这套机制让 HotSpot 能够在"寄存器分配自由度最大化"（JIT 可以随意将引用放入寄存器）和"GC 可精确枚举"（GC 总能找到所有引用）之间取得平衡。**这是"编译器优化"与"GC 正确性"协同设计的典范**——JIT 不为 GC 牺牲优化机会（引用照常入寄存器），GC 也不要求 JIT 让步（通过 OopMap 精确查询）。

## 9.3 在本地代码中支持垃圾回收：句柄（Handle）是生命线

这是全章最具"跨语言"挑战的部分。当线程进入 native 方法时，问题来了——**native 方法的栈帧是 C/C++ 编译器生成的，HotSpot 无法为其生成 OopMap**（因为 HotSpot 不理解 C++ 的调用约定和栈布局）。那么 GC 如何知道 native 方法中哪些位置持有对象引用？

### 9.3.1 对象引用访问：为什么不能直接暴露 oop

Oracle JNI 规范明确指出：

> The VM must keep track of all objects that have been passed to the native code, so that these objects are not freed by the garbage collector. The native code, in turn, must have a way to inform the VM that it no longer needs the objects. In addition, the garbage collector must be able to move an object referred to by the native code.

这里有三个硬性要求：

1. VM 必须跟踪所有传入本地代码的对象，防止被 GC 回收
    
2. 本地代码必须能通知 VM "我不再需要这个对象了"
    
3. **GC 必须能够移动本地代码引用的对象**（因为 HotSpot 的主流 GC 都是移动式收集器）
    

第三个要求是关键——**如果本地代码直接持有裸 oop（对象指针），GC 移动对象后，本地代码持有的指针就变成了悬垂指针**。

OpenJDK 邮件列表中的权威澄清揭示了一个常见误解：

> "Nonmovable" refers to the "local JNI reference", not the Java object instance itself. What that guarantees is that, given a jobject, the value of the jobject won't change. But that doesn't imply anything related whether or not the Java object is pinned... the actual referent object is free to move.

即：**jobject 自身不移动，但它指向的 Java 对象可以被 GC 自由移动**。

### 9.3.2 对象句柄实现：二级间接的精妙设计

HotSpot 的解决方案是**句柄（Handle）**——一个二级间接指针：

```
jobject → JNIHandle → Java object
[ oop* ] → [ oop ] → [ oopDesc ]
```

- **jobject**​ 是一个不透明指针，实际类型是 `oop*`（指向 oop 的指针）
    
- **JNIHandle**​ 是 GC 可知的根——GC 知道这个位置持有引用，且这个位置本身不移动
    
- **oop**​ 是真正的对象指针，GC 移动对象时会更新这里的 oop 值
    
- **oopDesc**​ 是堆中的对象本体
    

HotSpot 术语表对 handle 的官方定义：

> **handle**: A memory word containing an oop. The word is known to the GC, as a root reference. C/C++ code generally refers to oops indirectly via handles, to enable the GC to find and manage its root set more easily. Whenever C/C++ code blocks in a safepoint, the GC may change any oop stored in a handle. Handles are either 'local' (thread-specific, subject to a stack discipline) or global (long-lived and explicitly deallocated).

**句柄的两大类别**：

- **局部句柄（Local Handle）**：线程特定，遵循栈纪律（subject to a stack discipline），native 方法返回时自动释放
    
- **全局句柄（Global Handle）**：长生命周期，必须显式释放
    

**为什么这套设计如此关键？**​ 因为 HotSpot 的主流 GC（Serial、Parallel、G1）**都是移动式收集器**。OpenJDK 邮件明确指出：

> All garbage collectors in HotSpot, except for CMS, are moving collectors. As such, after each completed collection, Java objects will move. If you're holding raw oops that the GC isn't aware of, they won't be updated during GC, and will be left dangling afterwards.

只有 CMS 是标记-清除（非移动式），所以 CMS 时期可以"相对宽松"地讨论裸指针访问；但 G1 是移动式收集器，在 GCLocker 活跃时根本不能执行 GC。这意味着——**在 HotSpot 中，任何试图绕过 JNI handle 直接访问裸 oop 的行为，都是危险的、不可移植的**。

> ⚠️ **工业铁律**："Don't try to bypass the JNI abstractions. It'll bite back hard if you switch between different JVM implementations." 即使某个特定场景（如 CMS 老年代）下裸指针碰巧能工作，一旦切换到 G1 或其他移动式 GC，代码就会崩溃。这是 JNI 编程最危险的"未定义行为"。

### 9.3.3 GC 安全性维护：GCLocker 与临界区

当本地代码需要长期持有对象引用（如大数组），且不希望 GC 在期间移动对象时，可以使用 **JNI 临界区**（`GetPrimitiveArrayCritical` / `ReleasePrimitiveArrayCritical`）。

HotSpot 通过 **GCLocker**​ 机制实现：进入临界区时，GC 被禁用；所有临界区退出后，如果堆积的 GC 请求，会触发一次 Full GC 来执行延迟的回收。

> 💡 **洞见**：GCLocker 揭示了一个深刻的工程权衡——**"性能"与"GC 自由度"的博弈**。临界区允许本地代码以"近似裸指针"的方式访问 Java 对象（避免复制开销），代价是**这段时间内 GC 无法移动对象，甚至无法执行**。如果临界区时间过长，会导致堆空间紧张、Full GC 延迟触发。这就是为什么 JNI 临界区必须"短平快"——进入临界区、访问数据、立即退出，绝不能在其中执行长时间操作或调用其他 JNI 函数。

### 9.3.4 对象体访问：通过 JNI 函数而非裸指针

本地代码访问 Java 对象体（字段、数组元素）时，**必须**通过 JNI 函数：

- `GetIntField` / `SetIntField`：访问对象字段
    
- `GetIntArrayElements` / `ReleaseIntArrayElements`：访问数组元素
    
- `GetStringUTFChars` / `ReleaseStringUTFChars`：访问字符串
    

Oracle JNI 规范的设计概述明确指出：

> With C++, JNI functions are defined as inline member functions that expand to their C counterparts. However, the underlying mechanism is exactly the same as with C.

即无论 C 还是 C++，底层机制都是通过 `JNIEnv*` 接口指针调用 JNI 函数，**绝不直接解引用 jobject**。

### 9.3.5 对象分配：本地代码中的 `NewObject`

本地代码通过 JNI 的 `NewObject`、`NewArray` 等函数在堆上创建 Java 对象。这些对象返回为局部引用，VM 将其加入当前线程的局部句柄表——GC 在枚举根时会扫描这个句柄表，确保新对象在局部引用有效期内不会被回收。

> 💡 **洞见**：本地代码中的对象分配，本质上和 Java 代码中的 `new` 是同一个堆、同一套 GC 管理。区别仅在于——Java 代码的 `new` 由 JIT 编译为"分配 + 初始化"的机器码，而本地代码的 `NewObject` 是一次 JNI 调用，经过 `JNI_ENTRY`/`JNI_END` 的状态切换，最终落到 HotSpot 内部的对象分配器（可能涉及 TLAB 分配，见第5章）。**这套统一机制保证了"Java 对象和本地创建的对象在 GC 眼中毫无区别"**——它们都是堆中的 oop，都受同一套 GC 管理。

## 9.4 在同步方法中支持垃圾回收：Monitor 与 GC 的协作

这是全章较微妙的部分——同步方法持有 Monitor 时，GC 如何确保这个被锁保护的对象不被错误回收？

### 9.4.1 同步 Java 方法

当一个 Java 方法是 `synchronized` 时，进入方法会执行 `monitorenter`，退出时执行 `monitorexit`。在方法执行期间，该对象被当前线程"锁持有"。

**GC 视角**：锁持有的对象是强引用——GC 在标记阶段会将 Monitor Owner 持有的对象视为存活（因为它是从线程栈可达的）。但有一个微妙点——**对象的 Mark Word 在锁升级过程中会被复用**（无锁 → 偏向锁 → 轻量级锁 → 重量级锁），GC 在遍历对象图时必须能正确解析 Mark Word 中的状态，避免与锁状态位冲突。

HotSpot 的设计是——**GC 在标记对象时，会"穿透" Mark Word 的锁状态位，提取出真正的哈希码和 GC 标记位**（通过 `ObjectMonitor*` 和 mark word 的状态机协作）。这要求 GC 与 Monitor 系统深度协作。

### 9.4.2 同步本地方法

当 native 方法是 `synchronized` 时，情况更复杂：

- native wrapper 在进入 C 函数前执行 `monitorenter`（通过 JNI 的 `MonitorEnter`）
    
- 本地代码执行期间，对象被锁持有
    
- native wrapper 在 C 函数返回后执行 `monitorexit`
    

**GC 安全性**：由于 native wrapper 在 `_thread_in_native` 和 `_thread_in_java` 之间切换线程状态，GC 在 Safepoint 可以看到这个线程"正在 native 代码中持有 Monitor"——该 Monitor 关联的对象被视为强引用根。

> 💡 **洞见**：同步方法与 GC 的协作揭示了一个深层设计原则——**"锁持有"本身就是一种 GC 根**。当一个线程持有对象的 Monitor 时，这个对象对该线程而言是强可达的，GC 不能回收它。这就是为什么 HotSpot 的 `ObjectMonitor` 结构必须让 GC 可见——GC 在枚举根时，必须遍历所有被持有的 Monitor，将其关联对象加入根集。这是"同步系统"与"GC 系统"在根集定义上的深度耦合。

## 9.5 Java 与本地代码转换中的 GC 支持：边界协议

这是全章的"边界工程"总结——每次跨越 Java ↔ native 边界，都必须维护 GC 安全性。

### 9.5.1 本地到 Java

当本地代码通过 JNI 调用 Java 方法（如 `CallVoidMethod`）时：

- 参数中的 jobject 通过句柄间接引用——GC 可以移动底层对象，句柄自动更新
    
- 调用 Java 方法期间，线程状态从 `_thread_in_native` 切换到 `_thread_in_vm`
    
- 如果被调用的 Java 方法触发 GC，本地代码中持有的 jobject 仍然有效（因为句柄被 GC 更新）
    
- Java 方法返回后，线程状态切回 `_thread_in_native`
    

### 9.5.2 Java 到本地

当 Java 方法调用 native 方法时（通过 `javac` 生成的 `native` 方法）：

- 参数中的对象引用被包装为局部句柄，加入当前线程的局部句柄表
    
- native wrapper 将线程状态从 `_thread_in_java` 切换到 `_thread_in_native`
    
- 本地代码执行期间，如果 GC 发生，VMThread 会等待该线程到达 Safepoint——但 `_thread_in_native` 状态的线程被视为"已安全"（因为 C 代码不直接操作 Java 对象，只通过句柄间接引用）
    
- native 方法返回时，局部句柄自动释放（除非显式转为全局句柄）
    

### 9.5.3 本地到本地

当两个 native 方法通过 JNI 互操作时（如本地库 A 调用本地库 B 的 JNI 函数）：

- 必须通过 `JNIEnv*` 调用 JNI 函数（如 `NewObject`、`CallMethod`）
    
- 不能直接传递裸 oop 或 jobject 内部指针
    
- 这是因为本地到本地的调用也需要经过句柄管理层，确保 GC 一致性
    

> ⚠ **工业现实**：本地到本地的"绕道 JNI"看似低效，但这是 GC 安全性的强制要求。OpenJDK 邮件明确指出——"Don't try to bypass the JNI abstractions." 任何试图直接操作裸 oop 的行为，在移动式 GC 下都会导致悬垂指针。

## 9.6 全局根集：GC 根的"全景图"

这一节是全章的"汇总"——GC 的根集由哪些部分组成？

根据 HotSpot 术语表和 JVM 规范，GC root 包括：

|根集类别|具体内容|维护机制|
|---|---|---|
|**Java 栈局部变量**​|每个线程栈帧的局部变量表中的 oop|OopMap（JIT）/ 解释器规则|
|**Java 栈操作数栈**​|操作数栈中的 oop|OopMap（JIT）/ 解释器规则|
|**寄存器中的 oop**​|JIT 分配在寄存器中的引用|OopMap + RegisterMap|
|**JNI 局部引用**​|native 方法执行期间的局部句柄|线程局部句柄表|
|**JNI 全局引用**​|跨方法/跨线程的长期句柄|全局句柄表|
|**JNI 弱全局引用**​|不阻止回收的全局句柄|全局句柄表（弱引用）|
|**静态字段**​|类的 static 字段引用的对象|方法区 / 元空间|
|**常量池引用**​|类常量池中的 `CONSTANT_String`、类型引用|方法区 / 元空间|
|**Monitor 持有的对象**​|被 synchronized 锁保护的对象|ObjectMonitor 结构|
|**JVM 内部引用**​|系统类加载器、异常对象、类等|VM 内部根集|
|**本地方法栈 JNI 引用**​|JNI 参数和返回的 jobject|句柄表|

> 💡 **洞见（本章核心判断）**：全局根集的多样性揭示了一个深刻事实——**GC 不是"扫描堆"那么简单，而是"从所有堆外引用堆的入口点出发"的图遍历**。这些入口点分布在虚拟机的每一个子系统中：解释器的栈帧、JIT 的 OopMap、本地代码的句柄表、同步系统的 Monitor、类元数据中的静态字段。HotSpot 之所以能做到"准确式 GC"，是因为**每一个可能产生堆外引用的子系统，都向 GC 暴露了精确的引用位置元数据**。这种"全 VM 协同"的设计哲学，是 HotSpot 相对于早期 Classic VM（全 handle 设计，性能差）的根本进步——**Classic VM 用"统一句柄"换取简单性但牺牲性能；HotSpot 用"OopMap + 句柄"的分场景精确方案，既保证准确性又最大化性能**。

IBM 的 JNI 文档给出了一个极具教育意义的反模式示例——在循环中创建局部引用而不释放：

```
while (...) {
    jobject myObj = (*env)->NewObject(env, clz, mid, NULL);
    // 使用 myObj...
    // 如果没有 DeleteLocalRef，每次循环的 myObj 都会累积在局部句柄表中
    // 导致局部引用泄漏，直到 native 方法返回才会自动释放
    (*env)->DeleteLocalRef(env, myObj);  // 必须显式释放
}
```

这个反模式揭示了 JNI 局部引用的一个关键事实——**局部引用不是"GC 自动管理的引用"，而是"与 native 方法生命周期绑定的引用"**。它的释放时机是"native 方法返回"或"显式 DeleteLocalRef"，而非"GC 决定"。如果在长生命周期的 native 方法中循环创建局部引用而不释放，这些对象会一直被句柄表强引用，直到方法返回——造成事实上的内存泄漏。

## 贯穿第9章的三条暗线（承上启下）

1. **"准确式 GC"是虚拟机全子系统协同的结果**：OopMap（JIT 生成）、RegisterMap（栈展开恢复寄存器）、句柄表（本地代码）、Monitor（同步方法）、类元数据（静态字段）——每个子系统都在为 GC 提供"精确的引用位置元数据"。理解这一点，你才能理解为什么"GC 支持"需要单独成章，而不是 GC 组件的内部实现细节。
    
2. **"句柄"是跨语言边界 GC 安全性的基石**：jobject 是二级间接指针（jobject → handle → oop → oopDesc），GC 移动对象时只更新 handle 中的 oop 值，所有本地引用自动跟随。这套机制让 HotSpot 的移动式 GC（Serial/Parallel/G1）能够自由压缩堆，而不用担心本地代码持有悬垂指针。代价是 JNI 调用的句柄开销——这是"安全性换性能"的经典权衡。
    
3. **"分场景精确方案"优于"统一句柄方案"**：Classic VM 用统一句柄管理所有引用（简单但慢）；HotSpot 用 OopMap 处理 Java 代码（零开销、精确）、用句柄表处理本地代码（必要开销、安全）。这种"分场景优化"的哲学，与前面章节的"解释器/JIT 分层"、"GC 分代"、"锁升级"一脉相承，是 HotSpot 设计的统一思想。
    

---

**本章最核心的一句话**：垃圾回收支持的本质，是虚拟机向 GC 做出的"全子系统协同承诺"——**Java 代码通过 OopMap 精确暴露引用位置，本地代码通过句柄表间接引用对象（GC 移动对象时自动更新），同步方法通过 Monitor 向 GC 注册强引用根，全局根集汇聚所有堆外引用入口**。理解这套"精确、安全、可移动"的 GC 支持体系，你就拿到了看懂 HotSpot 准确式 GC、JNI 句柄机制、GCLocker 临界区、以及为什么"绕过 JNI 直接访问裸 oop"在移动式 GC 下必然崩溃的钥匙。

> 📌 **工业实践提示**：本章知识的直接应用包括——理解为什么 JNI 局部引用在长 native 方法中必须显式 `DeleteLocalRef`（避免局部引用泄漏）、为什么 JNI 临界区必须"短平快"（GCLocker 阻塞 GC）、为什么移动式 GC 下不能缓存裸 oop（对象移动后悬垂）、为什么全局引用必须显式 `DeleteGlobalRef`（否则内存泄漏）、以及为什么弱全局引用必须在使用前提升为强引用（避免竞态条件）。这些都是从"VM GC 支持"反推"JNI 编程最佳实践"的典型案例。
