
# 第5章 垃圾回收设计 —— 读书笔记

如果说前四章回答了"虚拟机如何加载类、如何表示对象、如何执行字节码"，那么第5章要回答的是虚拟机里最"隐形"却最致命的问题——**那些不再被使用的对象，谁来回收它们占用的内存？**​ 垃圾回收（GC）是 Java 等托管语言"内存安全"承诺的物理兑现，也是 JVM 性能调优的终极战场。李晓峰在这一章从最朴素的"对象什么时候死"出发，一路推到现代分代式、区域化收集器的精妙设计。结合 HotSpot/OpenJDK 的工业实现和英文权威资料，我来梳理这一章的脉络，并注入一些第一性原理层面的思考。

## 5.1 对象生存期：GC 的全部问题都源于"不知道对象何时死"

GC 要解决的根本问题只有一个：**判断一个对象是否还"活着"，把死对象占用的内存回收复用**。但"活着"这件事，在运行时不像在源码里那么直观——一个对象可能在某个时刻对所有线程都不可达，但虚拟机无法静态证明这一点。

这里要先厘清一个关键概念——**对象的"生存期（lifetime）"与"作用域（scope）"不是一回事**。一个在方法内 `new` 出来的对象，作用域可能随方法返回而结束，但它的生存期可能更长（被返回、被缓存、被静态字段引用）。GC 判断的是"可达性（reachability）"，而非"是否在某个词法作用域内"。

> 💡 **我的洞见**：对象生存期的多样性，是 GC 算法分野的根本原因。大量实证研究表明，Java 程序中绝大多数对象都是"朝生夕死"的——IBM 的研究发现，通常 **90% 以上的对象在创建后不久就变为不可达**（这就是著名的"弱分代假说"的经验基础）。这一观察直接催生了"分代式 GC"：把"死得快的"和"活得久的"分开管理，对前者用高效算法频繁回收，对后者用低成本方式偶尔处理。理解这一点，你就理解了现代 GC 设计的"第一性原理"——**不是所有对象都值得用同样的代价去管理**。

## 5.2 引用计数（Reference Counting, RC）：最简单也最古老的思路

引用计数是 GC 最直观的思路——**给每个对象维护一个"被引用的次数"计数器**，当计数器归零时，对象立即被回收。

**工作方式**：

- 创建一个新引用指向对象时，计数器 +1
    
- 一个引用被置空或指向别处时，计数器 -1
    
- 计数器归零 → 立即回收该对象，并递归将其引用的其他对象的计数器 -1
    

**优势**：

- 回收时机确定——对象一"无人引用"就立即回收，内存可及时复用
    
- 回收动作分散在每次赋值操作中，没有"全局停顿（Stop-The-World）"
    
- 实现简单，C++ 的 `shared_ptr`、Python 的默认 GC、Swift/Objective-C 的 ARC 都基于 RC
    

**致命缺陷——循环引用**：

```
class Node { Node next; }
Node a = new Node();
Node b = new Node();
a.next = b;
b.next = a;   // a 和 b 互相引用，计数器各为 1
a = null; b = null;  // 外部引用清零，但 a、b 互相引用，计数器仍为 1，永远无法回收！
```

> ⚠️ **洞见**：循环引用是 RC 的"阿喀琉斯之踵"。正因为这个缺陷，Java 的 JVM **没有采用引用计数作为主 GC**（早期 Classic VM 曾尝试过，因循环引用问题放弃）。但 RC 的思想并未消失——现代 JVM 的**并发标记阶段**广泛使用"引用计数"思想做局部判断；而 Objective-C/Swift 的 ARC、Rust 的引用借用检查器，则用编译期分析或运行时弱引用来规避循环引用问题。

## 5.3 对象追踪（Object Tracing）：从"根"出发的可达性分析

既然 RC 靠"引用数"判断生死有循环引用缺陷，JVM 采用了另一条路线——**对象追踪（Tracing）**，即"可达性分析（Reachability Analysis）"。

**核心思想**：从一组称为 **GC Roots**​ 的根对象出发，顺着对象引用链递归遍历，所有能被遍历到的对象是"存活"的，遍历不到的对象就是"不可达"的、可被回收的。

**哪些对象算 GC Roots？**（OpenJDK 规范）

- 虚拟机栈（栈帧中的局部变量表）中引用的对象
    
- 方法区中类静态属性引用的对象
    
- 方法区中常量（如 `String` 常量池）引用的对象
    
- 本地方法栈中 JNI 引用的对象（Native 引用）
    
- 被同步锁（`synchronized`）持有的对象
    
- Java 虚拟机内部的引用（如 Class 对象、异常对象、系统类加载器）
    

**追踪算法的抽象框架（Mark 阶段）**：

```
mark(obj):
    if obj.mark == false:
        obj.mark = true
        for child in obj.references:
            mark(child)
```

从每个 Root 调用 `mark`，标记完所有可达对象后，未被标记的对象即为垃圾。

> 💡 **我的洞见**：对象追踪的本质，是把"对象生死判断"从"局部计数"升级为"全局连通性分析"。这解决了循环引用问题——即使 a、b 互相引用，只要它们整体不从 Roots 可达，就会被一并回收。代价是：**必须暂停所有用户线程（Stop-The-World）以保证遍历期间对象图不被并发修改**，且遍历本身有 O(存活对象数) 的时间开销。JVM 选择追踪而非 RC，本质上是选择"全局精确判断 + 可控停顿"而非"局部即时回收 + 循环引用陷阱"。这条取舍，定义了后续所有 GC 算法的优化方向——**如何让这个"全局遍历"更快、更并发、更分代**。

## 5.4 RC 与对象追踪：两种哲学的根本对比

这一节是全章的"思想分水岭"。把 RC 和追踪放到一张表上对照，差异一目了然：

|维度|引用计数（RC）|对象追踪（Tracing）|
|---|---|---|
|判断依据|局部引用数量|全局可达性（从 Roots）|
|回收时机|立即（计数器归零时）|批量（GC 触发时）|
|循环引用|❌ 无法处理|✅ 天然解决|
|停顿（STW）|无（增量回收）|有（遍历对象图需 STW）|
|回收开销分布|分散在每次赋值|集中在 GC 周期|
|额外空间开销|每个对象一个计数器|标记位（bitmap 或对象头）|
|典型应用|Python、Swift/ARC、C++ shared_ptr|Java JVM、Go、.NET|

> 💡 **洞见**：RC 与追踪并非"谁取代谁"的关系，而是"确定性 vs 精确性"的取舍。RC 给你"确定性的及时回收"但牺牲循环引用的正确性；追踪给你"全局精确的可达性判断"但代价是 STW 停顿。现代工业 VM 其实在悄悄"融合"两者——**Go 的 GC 在标记阶段用三色抽象 + 写屏障（本质是追踪），但其 `runtime.SetFinalizer` 和弱引用机制借鉴了 RC 的"引用关系"思想**；而 Java 的 `PhantomReference`、弱引用（`WeakHashMap`）等，则让程序员在追踪 GC 之上手动表达"我想观察但不想强引用"的语义。理解这两种哲学的取舍，是看懂所有 GC 设计的元视角。

## 5.5 GC 安全点（GC Safepoint）："世界暂停"的精确控制

要让 GC 安全地遍历对象图，必须让所有用户线程在某个"安全"的时刻停下来——这就是 **Safepoint（安全点）**。

**什么是 Safepoint**：代码中某些特定的位置（通常是方法调用、循环回边、异常抛出点），在这些位置上，线程的栈状态和寄存器状态是"可枚举"的——即 GC 能准确知道此时栈上哪些槽位持有对象引用。

**Safepoint 的工作机制**：

1. GC 发起请求，设置一个全局的"需要进入 Safepoint"标志
    
2. 每个用户线程在**下一次执行到 Safepoint**​ 时，主动检查该标志
    
3. 若标志置位，线程暂停自己（"世界暂停"），等待 GC 完成
    
4. GC 完成后清除标志，线程恢复执行
    

HotSpot 的 Safepoint 实现有两种模式：

- **基于页面的 Safepoint（Page Poll）**：将某个内存页设置为不可读，线程访问该页时触发 SIGSEGV 信号进入 Safepoint——这是 HotSpot 的默认高效实现
    
- **基于标志位的 Safepoint**：线程在 Safepoint 处检查一个全局 volatile 标志位
    

**Safepoint 的代价**：Safepoint 不能太密集（否则每条指令都检查标志，性能崩塌），也不能太稀疏（否则 GC 等待线程到达 Safepoint 的时间过长，导致"GC 延迟尖刺"）。HotSpot 默认在**所有方法返回点和所有循环回边**放置 Safepoint——这保证了任何线程都能在"合理时间内"响应 GC 请求。

> ⚠️ **工业现实**：Safepoint 本身会成为性能问题。如果某个线程长时间执行一个**不含 Safepoint 的紧密循环**（如 JNI 调用、大数组 `System.arraycopy`），它会"错过" Safepoint 检查，导致 GC 不得不等待它，造成**"Safepoint 停顿尖刺"**——用户感知为应用"卡死"几百毫秒甚至几秒。这正是 `-XX:+UseCountedLoopSafepoints` 等调优参数的存在意义，也是 ZGC/Shenandoah 等现代收集器极力缩短 Safepoint 停顿的核心动机。

> 💡 **洞见**：Safepoint 揭示了一个深刻的工程哲学——**"全局暂停"这种粗暴操作，必须通过"协作式"而非"抢占式"来实现**。JVM 没有用信号强行暂停线程（那会导致栈状态不一致），而是让线程在"我确定自己状态安全"的时刻主动暂停。这种"协作式 Safepoint"思想，和操作系统内核的"抢占点"、分布式系统的"一致性快照（Chandy-Lamport）"异曲同工——**要让一个分布式/多线程系统在某时刻达成全局一致状态，必须让各参与者在"安全点"主动配合，而非外部强行中断**。

## 5.6 常用追踪 GC 算法：两大基础算法

对象追踪有两种最经典的实现策略——**标记-清除（Mark-Sweep）**​ 和 **追踪复制（Copying）**。它们是所有现代 GC 算法的"原子操作"。

### 5.6.1 标记-清除（Mark-Sweep）

**算法步骤**：

1. **Mark（标记）**：从 GC Roots 出发，追踪所有可达对象，在对象头/bitmap 中标记"存活"
    
2. **Sweep（清除）**：线性扫描整个堆，把未标记的对象回收，加入空闲列表（free list）
    

**优势**：

- 不移动对象——存活对象地址不变，引用无需更新
    
- 实现简单，适合"存活对象多、垃圾少"的场景
    

**劣势**：

- **内存碎片化**——回收后产生大量不连续的小空闲块，可能导致后续大对象分配失败（即使总空闲空间足够）
    
- Sweep 阶段需扫描整个堆（包括存活对象），吞吐量随堆增大而下降
    

### 5.6.2 追踪复制（Copying / Cheney's Algorithm）

**算法步骤**（经典两半区复制）：

1. 将堆分为两个大小相等的半区：From 空间和 To 空间
    
2. 对象只在 From 空间分配；当 From 空间满时触发 GC
    
3. 从 Roots 出发，把**所有可达对象**复制到 To 空间（紧凑排列）
    
4. 交换 From 和 To 的角色——原来的 To 变成新的 From
    

**优势**：

- **无碎片**——存活对象被紧凑复制到 To 空间一端，分配时只需"撞针分配（bump-the-pointer）"，O(1) 极快
    
- 只遍历存活对象，对"垃圾多、存活少"的场景效率极高
    

**劣势**：

- **空间浪费**——始终有一半堆空间处于"闲置"状态（To 空间）
    
- 需要更新所有指向被复制对象的引用（通过"转发指针 / forwarding pointer"机制）
    

> 💡 **洞见**：标记-清除和复制算法代表了 GC 设计的第一组根本取舍——**"碎片化/分配速度" vs "空间利用率"**。标记-清除不移动对象、省空间但产生碎片、分配慢；复制算法移动对象、消除碎片、分配极快但浪费一半空间。这个取舍直接决定了后续所有 GC 算法的演进方向：分代式 GC 本质是把"复制算法"用在"死得快的年轻代"（空间浪费可接受，因为年轻代本身不大），把"标记-清除/压缩"用在"活得久的老年代"（空间宝贵，不能浪费一半）。

## 5.7 常用追踪 GC 变体：从基础算法到工程杰作

这一节是全章的"工程精华"——五种变体，每一种都在解决基础算法的某个具体痛点。

### 5.7.1 标记-压缩（Mark-Compact）

**解决的问题**：标记-清除的碎片化。

**算法**：在 Mark 之后，增加"Compact（压缩）"阶段——将所有存活对象**滑动到堆的一端**，然后清理边界外的全部内存。压缩后堆空间连续，分配恢复为高效的撞针分配。

**代价**：压缩需要移动对象并更新所有引用，是 GC 中**最耗时**的操作之一。Serial Old、Parallel Old 收集器采用此算法。

### 5.7.2 滑动压缩（Sliding Compact）

标记-压缩的一个工程优化——**LISP2 算法**是经典滑动压缩实现：通过三次遍历堆（第一次计算存活对象新地址、第二次更新引用、第三次移动对象），实现原地压缩，无需额外空间。

### 5.7.3 追踪转发（Tracking Forwarding / Forwarding Pointer）

这是复制算法和分代 GC 的核心辅助机制。**当一个对象被复制到新位置后，在原位置留下一个"转发指针（forwarding pointer）"**，指向它的新地址。这样，当 GC 遍历过程中再次遇到该对象（通过不同引用路径），就能通过转发指针找到其新位置，避免重复复制。

> 💡 **洞见**：转发指针是一个"用空间换一致性"的精妙设计——它在对象头中借几位（或用一个专门的 forwarding 字）记录"我已经被搬到哪儿了"。这解决了复制过程中的"对象同一性"问题：同一个对象被多个根引用时，必须保证只复制一次、所有引用都更新到同一新地址。转发指针让"对象移动"对上层透明——这正是 GC 实现"自动内存管理"承诺的物理基础。

### 5.7.4 标记-复制（Mark-Copy）

本质就是 5.6.2 的追踪复制算法——先标记可达对象，再把它们复制到 To 空间。HotSpot 的 **Serial、Parallel Scavenge、G1 的年轻代**都采用标记-复制（更准确地说是"复制"为主，因为年轻代垃圾远多于存活对象）。

### 5.7.5 分代式 GC（Generational GC）：现代 JVM 的基石

这是全章**最重要**的一节——分代式 GC 是现代 JVM（Serial、Parallel、CMS、G1、ZGC、Shenandoah 的年轻代）的共同基石。

**核心假说（Generational Hypothesis）**：

1. **弱分代假说**：绝大多数对象都是朝生夕死的（IBM 研究：90%+ 对象短期死亡）
    
2. **强分代假说**：熬过越多次 GC 的对象，越不可能在未来死亡
    
3. **跨代引用假说**：老年代引用新生代的情况相对较少（为此引入"记忆集 / Remembered Set"优化）
    

**分代设计**：将堆分为**年轻代（Young Generation）**​ 和 **老年代（Old Generation）**：

- **年轻代**：存放新创建的对象，采用**复制算法**（Eden + 两个 Survivor 区 S0/S1），Minor GC 频繁但极快
    
- **老年代**：存放经历多次 Minor GC 仍存活的对象，采用**标记-清除/标记-压缩**，Major GC infrequent 但较慢
    

**对象在代际间的流转**：

```
新对象 → Eden 区
         │
         ▼ (Eden 满，Minor GC)
     存活对象 → Survivor S0 (年龄=1)
         │
         ▼ (每次 Minor GC 存活，年龄+1)
     Survivor S0 ⇄ S1 (复制算法在 S0/S1 间来回)
         │
         ▼ (年龄达到阈值，默认 15，即 -XX:MaxTenuringThreshold)
     晋升（Promote）到 老年代
```

**跨代引用问题**：Minor GC 时，如果仅扫描年轻代，可能漏掉"被老年代对象引用"的年轻代对象（这些对象也是存活的）。全堆扫描代价太高，解决方案是**记忆集（Remembered Set / Card Table）**——将老年代划分为若干"卡页（Card Page，通常 512 字节）"，当老年代对象写入引用时，通过**写屏障（Write Barrier）**​ 将对应卡页标记为"脏（dirty）"。Minor GC 时只需额外扫描"脏卡页"中的老年代对象，而非整个老年代。

> 💡 **洞见**：分代式 GC 是"对象生存期异质性"这一观察的直接工程兑现，也是"空间换时间"思想的集大成者。它做了三重取舍：① 把堆切成两代（空间划分成本）→ 换取 Minor GC 只扫年轻代的高效率；② 年轻代用复制算法（浪费一个 Survivor 区）→ 换取无碎片 + 撞针分配；③ 引入 Card Table + 写屏障（额外写操作开销）→ 换取 Minor GC 无需扫描整个老年代。这三重取舍的叠加，让分代式 GC 在"吞吐量"和"停顿时间"之间取得了极佳的平衡——这正是 Java 长期统治企业级服务端市场的底层原因之一。

> ⚠️ **工业演进提示**：分代式 GC 虽好，但"固定分两代"在超大堆（数十 GB 到 TB 级）场景下暴露出问题——老年代太大，Major GC / Full GC 停顿难以接受。这直接催生了 **G1（Garbage-First）**：把堆划分为约 2048 个等大小的 Region，逻辑上保留分代（年轻代 Region + 老年代 Region），但物理上不再连续划分，通过"优先回收垃圾最多的 Region"实现可预测的停顿（`-XX:MaxGCPauseMillis`）。**G1 是分代思想的"区域化进化"**——既保留分代的优势，又通过 Region 化把单次回收的堆范围可控。而 **ZGC/Shenandoah**​ 更进一步，用"染色指针 + 读屏障"实现并发压缩，把停顿压到亚毫秒级，几乎与堆大小无关。

## 5.8 移动式 GC 与非移动式 GC：物理布局的终极取舍

这一节是全章的"物理层"总结——从"对象是否移动"的角度，重新审视 GC 设计对内存分配、数据局部性、并发能力的深远影响。

### 5.8.1 数据局部性（Data Locality）

**移动式 GC**（复制、标记-压缩）会把存活对象**紧凑排列**，这带来一个关键好处——**数据局部性提升**。紧凑排列的对象在内存上相邻，CPU 访问时能更好地利用**缓存行（Cache Line，通常 64 字节）**​ 和 **预取器（Prefetcher）**，减少 TLB miss 和 cache miss。

非移动式 GC（标记-清除）产生的碎片会让对象散布在堆的各处，降低空间局部性。

> 💡 **洞见**：数据局部性是 GC 设计中"隐形"的性能杠杆。一个"存活对象紧凑排列"的堆，不仅分配快，更让程序的**访问延迟更低**——因为对象图遍历（如序列化、深拷贝、GC 标记阶段本身）会连续命中缓存。这也是为什么即便标记-清除实现简单，现代高性能 JVM 仍倾向"压缩式"收集器（G1、ZGC 都做并发压缩）——它们愿意承担"移动对象的开销"，换取长期运行下的数据局部性红利。

### 5.8.2 跳增指针分配（Bump-the-Pointer Allocation）

移动式 GC（尤其是复制算法）的最大工程红利——**撞针分配**：由于存活对象被紧凑复制到 To 空间的一端，To 空间内已用区和空闲区之间有一个清晰的边界（`top` 指针）。分配新对象只需：

```
if (top + size <= end) {
    obj = top;
    top += size;   // O(1)，无需遍历空闲列表
    return obj;
}
```

这比标记-清除的"遍历空闲列表找合适块"快几个数量级。**TLAB（Thread-Local Allocation Buffer）**​ 正是撞针分配的线程级扩展——每个线程在 Eden 区预分配一小块私有缓冲区，线程内分配对象完全无锁（仅移动自己的 TLAB 的 `top` 指针），只有 TLAB 用尽时才需要 CAS 竞争 Eden 空间。

### 5.8.3 空闲列表与分配位图（Free List & Allocation Bitmap）

非移动式 GC（标记-清除）无法用撞针分配，必须维护**空闲列表（Free List）**——将堆中未被占用的块按大小组织成链表，分配时从链表中查找合适块（First-Fit / Best-Fit / Segregated Fit）。

- **First-Fit**：找到第一个足够大的块，速度快但加剧碎片
    
- **Best-Fit**：找大小最匹配的块，碎片少但搜索慢
    
- **Segregated Free List（分离空闲列表）**：按块大小分级（如 8B、16B、32B、64B……），每级一条链表——这正是 HotSpot 的 **CMS**​ 和 **G1**​ 在老年代/Region 内使用的分配策略
    

**分配位图（Allocation Bitmap）**：用堆外的一块比特位图记录堆中每个"分配单元（如 8 字节对齐块）"是否已被占用。位图比对象头中的标记位更紧凑，适合大堆场景下的快速分配判断。

### 5.8.4 离散大小列表（Segregated Size Lists）

这是分离空闲列表的进阶——**按对象大小分级管理空闲块**。例如，专门维护 8B 块链表、16B 块链表、32B 块链表……分配时直接到对应大小的链表取块，O(1) 完成。这是 **jemalloc、tcmalloc**（C/C++ 高性能分配器）和 JVM 的 TLAB/TLAB 外分配共同采用的思想。

> 💡 **洞见**：离散大小列表揭示了一个通用工程原则——**"同类聚集"能极大提升分配/回收效率**。把大小相近的对象放在同一级链表，既减少碎片，又让分配接近 O(1)。这与 CPU 缓存的"组相联"、哈希表的"分桶"、数据库 B+ 树的"页管理"如出一辙——**"分而治之 + 同类聚集"是计算机系统中解决"查找效率"问题的通用范式**。

### 5.8.5 标记位与分配位（Mark Bit & Allocation Bit）

GC 需要两类关键的 1-bit 信息：

- **标记位（Mark Bit）**：标记对象是否存活（追踪阶段设置）
    
- **分配位（Allocation Bit）**：标记某内存单元是否已分配给对象
    

这两类位可以合并到**对象头的 Mark Word**​ 中（如 HotSpot 对象头的 GC 分代年龄位、锁状态位复用），也可以用**独立的位图（Bitmap）**​ 存储在堆外。使用独立位图的好处是：① 不污染对象头；② 位图本身紧凑（1 bit 对应 8 字节堆，1 MB 位图可管理 8 GB 堆）；③ GC 扫描位图比扫描对象头缓存更友好。

### 5.8.6 线程局部分配（Thread-Local Allocation, TLAB）

**TLAB（Thread-Local Allocation Buffer）**​ 是 JVM 对象分配的核心优化——每个线程在 Eden 区（年轻代）拥有**一小块私有内存缓冲区**（默认大小由 `-XX:TLABSize` 控制，通常几十 KB 到几 MB）。

**工作机制**：

- 线程内 `new` 对象时，优先在自家 TLAB 内用撞针分配（**完全无锁**）
    
- TLAB 用尽时，线程通过 CAS 从 Eden 区"批发"一块新的 TLAB
    
- 多线程并发分配时，仅 TLAB 申请/ refill 时需要 CAS 竞争，热点路径无锁
    

> ⚠️ **工业数据**：TLAB 让 Java 的对象分配速度**接近栈分配**——在微基准测试中，Java 的 `new Object()` 吞吐量可达每秒数亿次，与 C++ 的栈分配差距不大。这正是 Java 能"肆无忌惮"地创建大量短生命周期对象（如包装类型、Lambda 捕获对象）的底层支撑。没有 TLAB，Java 的高频对象分配会在 CAS 竞争下崩溃。

### 5.8.7 移动式 GC 与非移动式 GC 的混合：现代收集器的融合之道

这一节是全章的"现代视角"总结——现代高性能 GC 早已不是"纯移动"或"纯非移动"的二选一，而是**根据场景混合使用**：

|收集器|年轻代策略|老年代策略|混合特点|
|---|---|---|---|
|**Serial**​|复制（移动式）|标记-压缩（移动式）|纯移动式，单线程|
|**Parallel Scavenge**​|复制（移动式）|标记-压缩（移动式）|纯移动式，多线程并行|
|**CMS**​|复制（移动式）|标记-清除（非移动式）|混合：年轻代移动 + 老年代非移动（产生碎片，最终需 Full GC 压缩）|
|**G1**​|复制（移动式）|复制 + 标记-压缩（移动式）|以 Region 为单位移动，整体紧凑|
|**ZGC**​|并发复制（移动式）|并发复制（移动式）|全堆移动式，染色指针 + 读屏障实现并发移动|
|**Shenandoah**​|并发复制（移动式）|并发复制（移动式）|全堆移动式，Brooks 转发指针 + 读屏障|

> 💡 **洞见（本章核心判断）**：移动式与非移动式的取舍，本质是**"对象移动开销" vs "碎片/分配效率"**​ 的博弈。非移动式（标记-清除）不移动对象、实现简单、适合并发（无需更新引用），但产生碎片、分配慢；移动式（复制/压缩）移动对象、消除碎片、分配极快、提升数据局部性，但移动本身有开销、且并发移动需要读屏障/转发指针等复杂机制。

> 现代 GC 的演进趋势清晰可见——**从"非移动式为主"（CMS 时代）走向"移动式为主"（G1/ZGC/Shenandoah 时代）**。原因有二：① 大堆场景下碎片化的代价被放大（CMS 的碎片问题最终导致它被弃用）；② 现代 CPU 的读屏障开销已足够低（ZGC 的染色指针 + 读屏障在 x86 上仅增加约 10-15% 开销），使得"并发移动"成为可能。**这条演进路线的底层逻辑是：随着硬件变强，"移动对象的代价"在下降，而"碎片化的代价"在上升——所以移动式 GC 成为大堆时代的最优解。**

## 贯穿第5章的三条暗线（承上启下）

1. **"对象生存期异质性"是 GC 设计的元动力**：正因对象死得有快有慢，才催生了分代式 GC、Region 化 GC；正因要区分"移动/非移动"，才衍生出六种不同的算法变体。理解"对象生存期分布"，就读懂了 GC 设计的起点。
    
2. **"空间换时间"贯穿所有 GC 取舍**：复制算法浪费一半空间换无碎片、TLAB 用线程私有缓冲区换无锁分配、Card Table 用写屏障开销换 Minor GC 无需全堆扫描、分代式用代际划分换 Minor GC 高效率——每一项决策都是"用某种空间/开销，换取某种时间/效率"。
    
3. **GC 的终极战场是"停顿时间 vs 吞吐量"**：Serial/Parallel 追求吞吐量（停顿长）、CMS/G1 追求可预测停顿、ZGC/Shenandoah 追求亚毫秒级停顿（牺牲部分吞吐量）。不同业务场景（批处理 vs Web 服务 vs 实时交易）在这条频谱上选取不同平衡点。
    

---

**本章最核心的一句话**：垃圾回收设计的本质，是在"对象生死判断的准确性"与"回收过程的效率/停顿"之间做动态权衡——**RC 用局部计数换即时回收但败给循环引用，追踪算法用全局可达性分析换精确判断但需 STW，分代式用对象生存期异质性换高效率，移动式用对象移动换无碎片与数据局部性**。理解这条从"RC vs 追踪"到"分代 vs Region"再到"移动 vs 非移动"的演进频谱，你就拿到了看懂所有现代 GC（CMS/G1/ZGC/Shenandoah）设计哲学的钥匙。

> 📌 **工业实践提示**：本章知识的直接应用包括——根据业务场景选择收集器（吞吐型选 Parallel、低延迟选 G1/ZGC）、合理设置年轻代大小与 `-XX:MaxTenuringThreshold` 控制晋升、用 TLAB 调优减少 CAS 竞争、理解"GC 停顿尖刺"常由 Safepoint 等待或 Full GC 触发。这些都是从"GC 数据结构与算法"出发反推"JVM 调优"的典型案例。
