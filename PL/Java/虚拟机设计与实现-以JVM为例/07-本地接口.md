
# 第7章 本地接口 —— 读书笔记

如果说前六章回答了"虚拟机如何加载、表示、执行、回收、调度"，那么第7章要回答的是一个让"托管世界"与"非托管世界"握手的问题——**当 Java 代码需要调用 C/C++ 写的 `malloc`、需要打开操作系统文件描述符、需要调用 CUDA 核函数时，虚拟机如何在"类型安全的托管环境"与"裸露指针的非托管环境"之间架一座既安全又高效的桥？**​ 这座桥就是 JNI（Java Native Interface）。李晓峰在这一章实际上在讲一个被工业界反复打磨的真理——**本地接口的本质不是"让 Java 调 C"，而是"在托管运行时与操作系统之间建立一套受控的、可验证的、GC 友好的边界"**。JNI 不是简单的 API 集合，而是虚拟机设计哲学在"跨语言边界"这个极端场景下的集中体现。

结合 Oracle 官方 JNI 规范、OpenJDK HotSpot 的实现源码、以及工业界对 FFI（Foreign Function Interface）的现代演进，我来梳理这一章的脉络，并注入一些第一性原理层面的思考。

## 7.1 为何需要本地接口：托管世界的"必要之恶"

JVM 的设计初衷是"一次编写，到处运行"——字节码屏蔽了底层硬件和 OS 的差异。但有三个场景让"纯托管"变得不可能或不经济：

1. **操作系统交互**：文件 I/O、网络 socket、进程管理、共享内存——这些本质上是 OS 内核提供的 syscall，Java 标准库 `java.io`、`java.net` 的底层必须调用本地代码
    
2. **遗留代码复用**：企业几十年积累的 C/C++ 库（加密、图像处理、科学计算、工业控制）不可能用 Java 重写
    
3. **性能热点**：极少数对延迟/吞吐极敏感的场景（音视频编解码、高频交易、SIMD 加速），需要绕过 JVM 的托管开销
    

> 💡 **我的洞见**：本地接口的存在揭示了一个反直觉的事实——**"纯托管"的 JVM 其实从未真正"纯"过**。翻开 `java.lang.Object` 的源码，你会发现在 HotSpot 中，`getClass()`、`hashCode()`、`wait()`、`notify()`、`notifyAll()`、`clone()` 这六个方法全是 `native` 的。也就是说，**Java 对象模型的最底层、线程同步的最底层、GC 协作的最底层，全都依赖本地接口与 JVM 内部交互**。本地接口不是 JVM 的"附件"，而是 JVM 的"地基"——没有它，连 `Object.hashCode()` 都无法实现。理解这一点，你就能理解为什么 JNI 的设计如此"保守"（不直接暴露内部指针、强制通过句柄访问对象）——因为它是 JVM 正确性的最后一道防线。

## 7.2 从托管代码到本地代码的转换：跨越边界的"四次变换"

这是全章最精彩的部分。一次 `java.lang.String.getBytes()` 这样的 native 方法调用，背后发生了四层变换：

```
Java 方法 →（1）调用约定变换→ Native Wrapper →（2）参数封送→
C 函数 →（3）JNIEnv 间接调用→ JVM 内部 →（4）GC/线程状态切换→ 真实操作
```

### 7.2.1 本地方法封装：命名约定与动态链接

**默认静态注册**：遵循 `Java_<包名>_<类名>_<方法名>` 的长命名约定。例如 `pkg.Cls.f` 对应的 C 函数是 `Java_pkg_Cls_f__ILjava_lang_String_2`。JVM 在类加载时通过 `System.loadLibrary()` 加载 `.so/.dll`，首次调用 native 方法时用 `dlsym()` 按命名约定查找 C 函数地址并动态链接。

**动态注册（registerNatives）**：长命名约定在核心类中会产生大量符号查找开销。HotSpot 对 `Object`、`Thread`、`FileInputStream` 等核心类采用 `RegisterNatives` 机制——在 C 代码中显式提供一个 `JNINativeMethod` 数组，将 Java 方法名+签名直接映射到 C 函数指针：

```
static const JNINativeMethod methods[] = {
    {"hashCode", "()I", (void *)&JVM_IHashCode},
    {"wait", "(J)V", (void *)&JVM_MonitorWait},
    {"notify", "()V", (void *)&JVM_MonitorNotify},
    {"notifyAll", "()V", (void *)&JVM_MonitorNotifyAll},
    {"clone", "()Ljava/lang/Object;", (void *)&JVM_Clone},
};
```

`Object` 类在静态初始化时调用 `registerNatives()`，将这些方法直接绑定到 JVM 内部入口点（带 `JVM_` 前缀的 C 函数）。这种方式避免了运行时符号查找，是 HotSpot 对"热点 native 方法"的核心优化。

**方法绑定的底层实现**：当 `RegisterNatives` 被调用时，HotSpot 通过 `JNIHandles::resolve_non_null` 将 `jclass` 转为内部 `Klass*`，在 `SymbolTable` 中查找方法符号，最终调用 `Method::register_native` 设置 `Method` 对象的 `_native_function` 字段。此后每次调用该 native 方法，JVM 直接跳转到这个函数指针，无需再次符号解析。

> 💡 **洞见**：静态注册 vs 动态注册，揭示了 JVM 设计的一个通用哲学——**"常见的走快路径，罕见的保留通用性"**。长命名约定是 JNI 规范的通用方案，保证任何 Java 类都能用；而 `registerNatives` 是 HotSpot 对核心类的定制优化，把"运行时符号查找"提前到"类加载时一次性绑定"。这与第4章 JIT 的"解释器→C1→C2 分层"、第5章 GC 的"年轻代复制→老年代压缩"的同一条思想一脉相承：**对高频路径做特化优化，对低频路径保留通用能力**。

### 7.2.2 封装代码的 GC 支持：句柄（Handle）是生命线

这是全章**最关键**的设计决策——**为什么 JNI 不让 C 代码直接拿 Java 对象的裸指针？**

原因有两个：

1. **GC 会移动对象**：HotSpot 的复制/压缩算法会在 GC 时把对象从堆的一端搬到另一端（见第5章）。如果 C 代码持有裸指针，GC 移动对象后该指针就变成了悬垂指针
    
2. **GC 需要知道对象被引用**：如果对象被传入本地代码，GC 必须知道这个对象"有人在用"，否则会错误地回收它
    

**解决方案：JNI 句柄（JNI Handle）**。HotSpot 用 `JNIHandles` 类管理 Java 对象与本地代码之间的间接层：

- `jobject` 不是一个裸指针，而是一个**指向"句柄块"的指针**
    
- 句柄块中才存放真正的对象 `oop`（普通对象指针）
    
- GC 移动对象时，只需更新句柄块中的 `oop`，所有 `jobject` 自动"跟随"到新地址
    
- `JNIHandles::resolve(jobject)` 将 `jobject` 解析为内部 `oop`（inline 快速路径）
    

**局部引用 vs 全局引用**：JNI 将本地代码持有的对象引用分为两类：

- **局部引用（Local Reference）**：在 native 方法调用期间有效，方法返回后自动释放。VM 会在 native 方法栈帧中创建局部引用，GC 将其视为 Root Set 的一部分
    
- **全局引用（Global Reference）**：调用 `NewGlobalRef` 显式创建，必须调用 `DeleteGlobalRef` 显式释放，否则对象永不回收（内存泄漏）
    

IBM 的 JNI 诊断指南给出了一个精妙的比喻——局部引用就像 C 函数中的"隐形自动变量"，**它被创建在运行本地代码的线程的栈上，GC 从其 Root Set 中追踪到这个局部引用，因此不会回收该对象；当函数退出时，局部引用"超出作用域"，对象可能变为不可达而被回收**。

> ⚠️ **工业陷阱**：局部引用在两种场景下必须显式释放：
> 
> 1. native 方法访问了一个大型 Java 对象，创建了局部引用，但后续还要执行其他计算——这个大型对象会一直占用内存直到方法返回
>     
> 2. native 方法创建了**大量**局部引用（如在循环中反复调用 JNI 函数返回 jobject），VM 需要跟踪每个局部引用，可能耗尽内存
>     
> 
> 这两种场景都必须通过 `DeleteLocalRef` 显式释放，或使用 `PushLocalFrame`/`PopLocalFrame` 批量管理。

**数组访问的"复制 vs 钉住（Pinning）"**：访问 Java 基本类型数组（如 `int[]`）时，JNI 提供两套函数：

- `GetIntArrayElements` / `ReleaseIntArrayElements`：可能复制数组到 C 堆（如果 GC 不支持钉住，或数组布局不符合本地代码要求）
    
- `GetPrimitiveArrayCritical` / `ReleasePrimitiveArrayCritical`：尽可能"钉住"数组，让 C 代码直接访问 Java 堆（但这段时间内 GC 不能移动该数组，相当于进入临界区）
    

JNI 规范明确：**GC 算法可以对每个数组独立决策"复制还是钉住"——小对象复制，大对象钉住**。这又是一个"按场景优化"的经典案例。

> 💡 **洞见**：JNI 句柄层是"计算机科学中所有问题都可以通过加一层间接来解决"的最佳例证。但加这层间接不是免费的——每次通过 `jobject` 访问 Java 对象，都要经过 `JNIHandles::resolve` 的指针解析；每次调用 JNI 函数，都要经过 `JNI_ENTRY`/`JNI_END` 宏的状态切换（引入内存屏障和 Safepoint 检查）。这就是为什么 JNI 调用比纯 Java 调用慢 10-100 倍的根本原因。但也正是这层间接，让 JVM 能够在 GC 时自由移动对象、让本地代码无需感知 GC 的存在——**这是"抽象代价换安全性"的典型工程权衡**。

### 7.2.3 封装代码的同步支持：MonitorEnter/MonitorExit

本地代码如何参与 Java 的同步模型？JNI 提供了与 `synchronized` 块等价的原语：

```
if ((*env)->MonitorEnter(env, obj) != JNI_OK) {
    // 错误处理
}
// ... synchronized block ...
if ((*env)->MonitorExit(env, obj) != JNI_OK) {
    // 错误处理
}
```

这两个函数与第6章讲的 `monitorenter`/`monitorexit` 字节码指令底层共享同一套 `ObjectMonitor` 机制——本地代码通过 JNI 调用，最终进入 HotSpot 的 `ObjectSynchronizer::enter/exit`，与 Java 代码的 `synchronized` 完全互操作。

> ⚠️ **工业约束**：`JNIEnv` 指针**只在创建它的线程中有效**，不能跨线程传递。局部引用同样线程私有。如果本地代码要在多线程间共享 Java 对象，必须把局部引用转化为全局引用。**这是 JNI 编程最常见的 Bug 来源**——程序员误以为 `jobject` 是全局有效的，在另一个线程中使用导致 JVM 崩溃。

## 7.3 本地方法实现的绑定：从 C 函数到 JVM 内部

这一节是全章的"HotSpot 视角"——native 方法到底如何与 JVM 内部对接？

**两种绑定路径**：

1. **JNI 函数（普通 native 方法）**：C 函数通过 `JNIEnv*` 调用 `jni.cpp` 中定义的函数（如 `jni_GetArrayLength`），这些函数内部将 `jobject` 解析为 `oop`，再调用 HotSpot 内部实现
    
2. **JVM_ 入口点（核心类 native 方法）**：通过 `registerNatives` 直接绑定到 `JVM_IHashCode`、`JVM_MonitorWait` 等 JVM 内部函数，绕过 JNI 函数表，性能更高
    

**`JNI_ENTRY`/`JNI_END` 宏**：所有 `jni.cpp` 中的函数都被这对宏包裹。它们做几件关键的事：

- 线程状态切换：从 `_thread_in_native` 切换到 `_thread_in_vm`，让 GC 知道该线程正在执行 VM 代码
    
- Safepoint 检查：确保线程在 VM 操作时可以被安全暂停
    
- 异常状态保存与恢复
    
- 性能计数与诊断钩子
    

> 💡 **洞见**：`JNI_ENTRY`/`JNI_END` 宏揭示了一个深刻的工程事实——**本地代码进入 JVM 内部时，必须"向 GC 报到"**。线程状态切换确保 GC 在标记 Root Set 时能正确处理这个线程的栈；Safepoint 检查确保线程不会长时间阻塞 GC 的 STW 操作。这是 JNI 与 JVM 协作的"握手协议"——本地代码看似自由，实则在 JVM 的严密监管之下。

## 7.4 本地代码到托管代码的转换：反向跨越边界

正向跨越（Java→C）我们已经讲透；反向跨越（C→Java）同样重要。本地代码可以通过 JNI 调用 Java 方法、创建 Java 对象、访问字段：

```
// 1. 查找类
jclass cls = env->FindClass("java/lang/String");
// 2. 查找方法 ID（两步查找，缓存 ID 避免重复查找）
jmethodID mid = env->GetMethodID(cls, "f", "(ILjava/lang/String;)D");
// 3. 调用方法
jdouble result = env->CallDoubleMethod(obj, mid, 10, str);
```

**字段/方法 ID 的生命周期陷阱**：JNI 规范明确指出——**字段 ID 和方法 ID 不会阻止 VM 卸载生成该 ID 的类**。如果类被卸载，ID 变为无效。因此，如果本地代码要长时间持有 ID，必须**保持对底层类的活引用**（如创建全局引用），或在使用前重新计算 ID。

**异常处理**：JNI 函数通过两种方式报告错误：

- 返回错误码（如 `NULL`、`JNI_FALSE`）
    
- 抛出 Java 异常（通过 `Throw`、`ThrowNew`）
    

本地代码调用 Java 方法时，必须检查 `ExceptionOccurred()`——因为 Java 方法可能抛出异常，而 C 代码无法用 `try-catch` 捕获。**这是 JNI 编程的第二大 Bug 来源**——忘记检查异常导致程序在错误状态下继续执行。

**异步异常**：一个线程可能通过已废弃的 `Thread.stop()` 向另一个线程抛出异步异常。JNI 规范强烈不建议使用这种机制，因为它破坏了 Java 异常模型的"同步性"假设。

> 💡 **洞见**：反向跨越揭示了一个本质问题——**本地代码调用 Java 方法时，JVM 必须"重建"一个 Java 调用栈帧**。这个过程比正向跨越更昂贵，因为它需要：① 查找并验证类/方法；② 创建 Java 栈帧；③ 参数封送（将 C 类型转为 Java 类型）；④ 切换到 JVM 执行引擎；⑤ 处理返回值和异常。这就是为什么在性能敏感的 FFI 场景中，业界倾向于"减少跨越次数"而非"减少单次跨越开销"——**批量调用、将循环移到本地端、用 ID 缓存**是常见的优化手段。

## 7.5 本地代码到本地代码的转换：为什么要"绕道"JNI

这是全章最微妙的一节——如果两个 C 库需要互相调用，为什么不直接用 C 的调用约定，而要通过 JNI API？

### 7.5.1 通过 JNI API 的本地到本地转换

假设本地库 A 想要调用本地库 B 的函数，且 B 的函数需要操作 Java 对象（接收 `jobject`、返回 `jstring` 等）。这时 A 不能直接调用 B 的 C 函数，而必须通过 JNI API：

```
本地库 A 的 C 函数
    ↓ 调用 JNI 函数（如 NewObject、CallMethod）
    ↓ 通过 JNIEnv* 进入 JVM 内部
    ↓ JVM 执行 B 的 native 方法
    ↓ 返回到 A
```

### 7.5.2 为什么在本地到本地转换中使用 JNI API

**根本原因：本地库 B 的 native 方法签名中包含 Java 类型（jobject、jstring、jclass 等），这些类型是"受 JNI 句柄层管理的间接引用"**。如果 A 直接调用 B 的 C 函数：

1. **句柄管理缺失**：B 接收到的 `jobject` 可能没有在 JVM 的句柄表中正确注册，GC 无法识别这个引用，可能错误回收对象
    
2. **线程状态错误**：B 的 C 函数在执行时，线程状态可能不在 `_thread_in_native` 或 `_thread_in_vm`，GC 的 Safepoint 机制无法正确处理
    
3. **引用生命周期混乱**：A 创建的局部引用在跨库调用时可能无法正确传递，导致 B 访问悬垂引用
    

**通过 JNI API 的"绕道"实际上是"回家"**——让调用重新经过 JVM 的监管层，确保所有 GC 语义、线程状态、引用管理都正确无误。

> 💡 **洞见（本章核心判断）**：本地到本地的"绕道 JNI"揭示了一个深刻的工程哲学——**跨边界调用不是"函数调用"，而是"状态机转移"**。每一次跨越托管/非托管边界，都必须完成：调用约定适配、参数封送、句柄管理、线程状态切换、GC 协作、异常处理。JNI API 就是这套"状态机转移协议"的标准实现。直接 C 调用跳过了这套协议，等于在 JVM 的"免疫系统"之外操作——短期看似高效，长期必然导致 GC 错误、内存破坏、JVM 崩溃。

> ⚠️ **工业演进**：JNI 的"重边界"代价在云原生、高频 FFI 场景下越来越不可接受。业界正在推进多个替代方案：
> 
> - **Project Panama（Foreign Function & Memory API）**：JDK 22+ 正式引入 `java.lang.foreign`，提供比 JNI 更轻量、更类型安全、零复制的本地互操作
>     
> - **阿里巴巴 FFI / LLVM4JNI**：通过将 C++ API 编译为字节码，从根本上"打破 Java 方法与原生函数之间的边界"
>     
> - **GraalVM Native Image**：在 AOT 编译时直接将本地调用内联到机器码中
>     
> 
> 这些方案的共同思路是——**要么让边界更薄（Panama），要么让边界消失（LLVM4JNI、GraalVM）**。但它们都没有抛弃 JNI 的核心设计原则：**托管世界与非托管世界之间，必须有一套明确的、受控的、GC 友好的边界协议**。

## 贯穿第7章的三条暗线（承上启下）

1. **"边界即协议"——JNI 不是 API 而是状态机**：每一次托管↔非托管跨越，都必须完成调用约定适配、参数封送、句柄管理、线程状态切换、GC 协作、异常处理。理解 JNI 的这种"协议"本质，才能理解为什么 JNI 调用有固有开销，以及为什么 Project Panama 等现代方案要重新设计这套协议。
    
2. **"句柄层"是 GC 与本地代码共存的生命线**：`jobject` 不是裸指针，而是句柄；GC 移动对象时只更新句柄，所有本地引用自动跟随。局部引用/全局引用的生命周期管理，是 JNI 编程正确性的核心。
    
3. **"常见的走快路径"——registerNatives 是 HotSpot 的核心优化**：核心类的 native 方法通过 `RegisterNatives` 直接绑定到 `JVM_` 入口点，绕过 JNI 函数表的动态查找开销。这与 JIT 分层、GC 分代、锁升级的"自适应"哲学一脉相承。
    

---

**本章最核心的一句话**：本地接口的本质，是在"类型安全的托管世界"与"裸露指针的非托管世界"之间建立一套**受控的、可验证的、GC 友好的边界协议**——通过 JNI 句柄层隔离 GC 移动、通过局部/全局引用管理对象生命周期、通过 `JNI_ENTRY`/`JNI_END` 宏完成线程状态切换与 Safepoint 协作、通过 `registerNatives` 为热点 native 方法开辟快路径。**理解 JNI 的"边界协议"本质，你就拿到了看懂 HotSpot 本地互操作、GC 与本地代码协作、以及 Project Panama 等下一代 FFI 方案设计哲学的钥匙**。

> 📌 **工业实践提示**：本章知识的直接应用包括——理解为什么 JNI 调用比纯 Java 慢一个数量级（句柄解析 + 状态切换 + Safepoint 检查）、为什么 native 方法中必须谨慎管理局部引用避免内存泄漏、为什么 `JNIEnv` 不能跨线程传递、以及为什么现代 Java FFI（Project Panama）要通过 `MemorySegment` + `Linker` 重新设计边界协议以降低开销。这些都是从"VM 本地接口设计"反推"Java 本地互操作最佳实践"的典型案例。
