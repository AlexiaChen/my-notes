
# 第14章 针对吞吐量的 GC 优化 —— 读书笔记

如果说前几章回答了"GC 有哪些算法、虚拟机如何支持 GC"，那么第14章要回答的是一个让前面的所有讨论**真正服务于业务指标**的问题——**当我们的目标是"吞吐量最大化"（即应用线程运行时间占总时间的比例最大）时，虚拟机应该如何自适应地调整回收范围、分代策略、堆空间大小、分配空间布局，甚至利用大页和预取？**​ 这就是"针对吞吐量的 GC 优化"。李晓峰在这一章实际上在讲一个被工业界反复验证的真理——**吞吐优化的本质不是"让 GC 更快"，而是"让单位有用工作所承担的 GC 开销最小"**。这需要虚拟机在多个维度上做连续的适应性调整：何时做部分堆回收、何时做全堆回收、是否分代、堆该多大、年轻代（NOS）该多大、对象该分配到哪里、如何利用硬件的大页和预取能力。

结合李晓峰原书第14章框架、Oracle HotSpot GC Tuning Guide 对 Parallel Collector 的官方权威描述，以及 Dynatrace 对"分代 vs 非分代""TLH 对分配性能影响"的工业分析，我来梳理这一章的脉络，并注入一些第一性原理层面的思考。

## 14.1 部分堆回收与全堆回收之间的适应性调整：回收范围的频谱

这是全章的第一个核心抉择——**GC 应该回收整个堆，还是只回收其中一部分？**

### 部分堆回收（Partial Heap Collection）

部分堆回收是指只回收堆的一个子集——在分代式 GC 中，就是 Minor GC（只回收年轻代）。

**优势**：

- 回收范围小、速度快、对应用停顿时间短
    
- 符合"弱分代假说"——90% 以上的对象在年轻时死亡，回收年轻代性价比最高
    
- 在 Parallel Collector 中，部分堆回收可以被多线程并行执行，进一步提升吞吐量
    

**代价**：

- 无法回收老年代中的垃圾
    
- 如果对象晋升过快，老年代碎片化，最终仍需要全堆回收
    

### 全堆回收（Full Heap Collection）

全堆回收是指回收整个堆——包括年轻代和老年代。

**优势**：

- 一次性回收所有代的垃圾
    
- 可以执行压缩（Compaction），消除碎片
    
- 在 Parallel Collector 中，通过 `-XX:+UseParallelOldGC` 可以让全堆回收也并行执行
    

**代价**：

- 回收范围大、停顿时间长
    
- 在纯吞吐量场景下，单次 Full GC 可能达到几百毫秒甚至数秒
    

### 适应性调整的核心思想

Oracle 官方文档明确指出：Parallel Collector 的适应性调整逻辑是——

> "If the GC pause time is greater than the pause time goal then reduce the generations sizes... If the pause time goal is being met then consider the application's throughput goal. If the application's throughput goal is not being met, then increase the sizes of the generations..."

即：

1. **停顿时间超标**​ → 缩减代的大小（让单次回收更快）
    
2. **停顿达标但吞吐量不达标**​ → 增大代的大小（减少 GC 频率，降低总 GC 时间占比）
    
3. **两者都达标**​ → 缩减堆 footprint（节省内存）
    

> 💡 **洞见（本章核心判断之一）**：部分堆回收与全堆回收的适应性调整，本质上是在"单次停顿时长"与"GC 频率（即总 GC 时间占比）"之间寻找平衡点。Parallel Collector 的智慧在于——**它不追求"单次停顿最短"（那是 CMS/G1/ZGC 的目标），而是追求"总 GC 时间占比最小"**。这意味着：在吞吐量优先的场景下，我们宁可接受较长的单次停顿，也要减少 GC 的发生频率。这正是为什么 Parallel Collector 被称为"Throughput Collector"——它的优化目标是 `GCTimeRatio`（如 `-XX:GCTimeRatio=99` 表示允许 GC 占用总时间不超过 1%），而非 `MaxGCPauseMillis`。

> ⚠️ **工业现实**：很多工程师误以为"优化 GC 就是减少停顿"，但在纯吞吐场景下这是错误的。对于一个夜间批处理任务，一次 2 秒的 Full GC 和一百次 20 毫秒的 Minor GC，哪个吞吐量更高？后者！因为后者的总 GC 时间可能只有 2 秒，而前者虽然单次停顿长但频率极低，总 GC 时间可能只有 2 秒——但如果部分堆回收能减少 Full GC 的频率，让应用在两次 Full GC 之间有更长的连续运行时间，吞吐量反而会提升。这就是为什么 Parallel Collector 的默认行为是"让堆尽可能大、让 GC 尽可能少"——**在吞吐量世界里，"少做"比"快做"更重要**。

## 14.2 分代式与非分代式算法之间的适应性调整：是否分代的辩证

这是全章最具哲学深度的一环——**分代式 GC 一定是吞吐量最优的吗？**

### 分代式 GC 的吞吐量优势

分代式 GC 基于"弱分代假说"——绝大多数对象朝生夕死。通过把堆分为年轻代和老年代：

- **年轻代 GC（Minor GC）频繁但快速**：只扫描年轻代，使用复制算法，O(存活对象数) 时间复杂度
    
- **老年代 GC（Major GC）罕见但缓慢**：使用标记-整理，O(总对象数) 时间复杂度，但频率低
    

Oracle 官方文档证实：Parallel Collector 就是一个分代式收集器，通过多线程并行执行 Minor GC 来提升吞吐量；在 JDK 7u4+ 中，通过 `-XX:+UseParallelOldGC` 让 Major GC 也并行执行，进一步降低全堆回收的开销。

### 非分代式 GC 的吞吐量优势

但 Dynatrace 的工业分析给出了一个反直觉的事实：

> "If your application is designed for pure throughput and the number of temporary objects is relatively small, a non-generational GC has advantages. A full parallel GC has a better tradeoff in terms of CPU usage if you don't care about the response time of a single transaction."

即当满足以下条件时，非分代式 GC 可能更有优势：

1. **临时对象数量相对较少**：不满足"弱分代假说"的前提
    
2. **纯吞吐场景**：不关心单次事务的响应时间
    
3. **CPU 使用率优先**：非分代式 GC 在 CPU 使用率上有更好的权衡
    

### 适应性调整的智慧

李晓峰在这一节实际上在讲——**虚拟机应该根据应用的对象生命周期特征，动态选择分代或非分代策略**。

Dynatrace 的分析进一步指出：

> "Only a thorough performance test can determine this for sure."

即：分代还是非分代，**没有理论上的绝对答案，只有通过性能测试才能确定**。这正是适应性调整的核心——**让虚拟机根据运行时观测到的对象生命周期分布，动态选择最优策略**。

> 💡 **洞见（本章核心判断之二）**：分代 vs 非分代的适应性调整，揭示了 GC 设计的一个第一性原理——**"对象生命周期的异质性"决定分代是否有价值**。如果应用中绝大多数对象都是"朝生夕死"的（符合弱分代假说），分代式 GC 是吞吐量最优的；如果对象的生命周期分布相对均匀（临时对象少），非分代式 GC 的全并行回收可能 CPU 效率更高。现代 GC 的演进趋势——Generational ZGC（JDK 21+）的引入——正是这一适应性的兑现：ZGC 最初是非分代的（JDK 15-20），但在实践中发现分代能进一步提升吞吐量（在测试场景中减少 25-40% 的 GC CPU 开销），因此在 JDK 21 引入了分代模式。这是"适应性调整"思想在工业界的最新验证。

## 14.3 堆的空间大小的适应性调整：自适应堆管理的艺术

这是全章最具"工业质感"的部分——HotSpot 的 Parallel Collector 如何在运行时动态调整堆和代的大小？

### 14.3.1 空间大小扩展：三步适应性调整

Oracle 官方文档详细描述了 Parallel Collector 的自适应调整机制：

**每次 GC 结束后，收集器执行以下统计与调整**：

1. **统计更新**：更新平均停顿时间等统计数据
    
2. **目标检验**：按优先级检验三个目标——
    
    - 第一优先级：**最大停顿时间目标**（`-XX:MaxGCPauseMillis=`）
        
    - 第二优先级：**吞吐量目标**（`-XX:GCTimeRatio=`）
        
    - 第三优先级：**最小 footprint 目标**（`-Xmx` 指定的最大堆）
        
    
3. **代大小调整**：根据需要增大或缩减代的大小
    

**增大与缩减的速率不同**：

- 默认情况下，**代以 20% 的增量增大**（`-XX:YoungGenerationSizeIncrement=` / `-XX:TenuredGenerationSizeIncrement=` 控制）
    
- **代以 5% 的减量缩减**（`-XX:AdaptiveSizeDecrementScaleFactor=` 控制缩减速率）
    
- 增长率与缩减率的不对称设计，是为了避免堆大小震荡
    

**调整方向的智慧**：

- 如果**停顿时间目标未达标**​ → 只缩减一个代的大小（优先缩减停顿时间较长的那个代）
    
- 如果**吞吐量目标未达标**​ → 同时增大两个代的大小（按各自对总 GC 时间的贡献比例分配增量）
    
- 如果**两个目标都达标**​ → 缩减堆以最小化 footprint
    

### 14.3.2 NOS 大小：年轻代（New/Young Generation）的关键作用

在李晓峰的原书中，年轻代被称为 **NOS（New Object Space）**——新对象空间。这是分代式 GC 中**最活跃的回收区域**。

Dynatrace 的调优指南明确指出：

> "Sizing the young generation is the most important tuning step in a generational GC setup. First, it must be large enough to handle all threads of the concurrent working set without tenuring short-lived objects to the old generation. Second, we want long-lived objects tenured as quickly as possible."

即年轻代大小需要在两个极端之间找到平衡：

- **太小**​ → 短命对象过早晋升到老年代，导致老年代压力增大
    
- **太大**​ → Minor GC 时存活对象多，GC 周期变慢；同时老年代空间被压缩
    

**关键经验法则**（Dynatrace）：

- 年轻代 GC 后，两个 Survivor 空间中的一个**填充率不应超过 75%**
    
- 同时老年代不应增长
    
- 如果年轻代 GC 变得昂贵但老年代不增长 → 年轻代中存活对象过多，需要调整晋升阈值让中等寿命对象更快晋升
    

### 14.3.3-14.3.5 NOS 设计的三种变体

李晓峰原书讨论了 NOS（年轻代）的三种设计变体，这是本章最具"实现细节"的部分：

**部分转发 NOS 设计（Partial Forwarding NOS）**：

年轻代采用复制算法，但只转发（复制）存活对象，死对象占用的空间直接回收。这是标准的复制算法年轻代实现。

**半空间 NOS 设计（Semi-space NOS）**：

年轻代被划分为两个等大的半空间（From 和 To），GC 时将 From 空间的存活对象复制到 To 空间，然后交换角色。这是最经典的复制算法实现，优点是简单、无碎片，缺点是空间利用率只有 50%。

**aged-mature NOS 设计**：

在年轻代内部进一步细分年龄，让"中等寿命"对象在年轻代内有更多机会被回收，而不是过早晋升到老年代。这直接针对 Dynatrace 提到的"middle-lived objects"问题——这类对象是 GC 性能的隐形杀手。

> 💡 **洞见**：这三种 NOS 设计变体，体现了"年轻代内部管理"的三种哲学——**部分转发追求效率、半空间追求简单和无碎片、aged-mature 追求减少过早晋升**。现代 HotSpot 的年轻代实现（Eden + S0 + S1）实际上是这三种思想的混合：Eden 使用 bump-the-pointer 分配（部分转发的思想），S0/S1 是半空间复制的体现，而晋升阈值（`-XX:MaxTenuringThreshold`）和 Survivor 空间自适应调整（`-XX:TargetSurvivorRatio`）则是 aged-mature 思想的兑现。

### 14.3.6 回退回收（Fallback Collection）

当适应性调整失效时——例如年轻代 GC 后存活对象过多导致老年代无法容纳晋升——虚拟机必须触发**回退回收**，即 Full GC。

Oracle 官方文档提到：

> "Reducing the number of garbage collector threads and increasing the size of the old generation will reduce this fragmentation effect."

即在 Parallel Collector 中，由于多个 GC 线程并行执行 Minor GC，每个线程在老年代预留一部分空间作为"晋升缓冲区（promotion buffers）"，这种划分可能造成碎片化效应。**减少 GC 线程数或增大老年代，可以降低这种碎片化效应**。

> ⚠ **工业现实**：回退回收（Full GC）是吞吐量的天敌——它不仅停顿时间长，而且频率不可控。Parallel Collector 的适应性调整主要目标之一，就是**尽可能推迟回退回收的发生**。通过动态调整年轻代和老年代的比例、调整晋升阈值、优化 Survivor 空间利用率，虚拟机试图在两次 Full GC 之间最大化应用运行时间。这就是为什么在纯吞吐场景下，我们倾向于给 Parallel Collector 配置较大的堆（`-Xms` 和 `-Xmx` 设为相等的大值）——**用空间换时间，减少 Full GC 频率**。

## 14.4 分配空间之间的适应性调整：TLH 与并发分配的权衡

这是全章最具"并发视角"的部分——当多个线程同时分配对象时，如何保持高吞吐量？

### 线程局部分配缓冲区（TLH / TLAB）

Dynatrace 的工业分析指出：

> "The solution to this is thread-local allocation. Each thread receives a small, but exclusive, memory allotment where objects are allocated without the need for synchronization. This increases concurrency and the speed of application execution."

即：每个线程获得一小块独占的内存分配缓冲区（在 HotSpot 中称为 TLAB——Thread-Local Allocation Buffer），在该缓冲区内分配对象无需同步。

**适应性调整的辩证**：

Dynatrace 进一步分析：

> "A generational heap with TLH requires a larger young generation than without a TLH. The same number of objects simply uses more space. On the other hand, a non-generational heap with active TLH is likely to become more fragmented and will need more-frequent compaction."

这是一个深刻的工程权衡：

- **分代堆 + TLH**​ → 需要更大的年轻代（因为 TLH 占用空间），但碎片化可控
    
- **非分代堆 + TLH**​ → 更可能出现碎片化，需要更频繁的压缩
    

### 分配空间的适应性调整

虚拟机需要在以下维度做适应性调整：

1. **TLAB 大小**：根据线程分配速率动态调整
    
2. **TLAB refill 策略**：何时从 Eden 区重新批发 TLAB
    
3. **分配空间布局**：Eden 区 vs. TLAB 的比例
    

> 💡 **洞见（本章核心判断之三）**：分配空间的适应性调整，揭示了并发 GC 设计的一个第一性原理——**"分配速度"与"空间效率"的博弈**。TLAB 用"线程私有化"解决了分配同步瓶颈（极大提升并发分配吞吐量），但代价是空间浪费（每个线程的 TLAB 都有未使用部分）。虚拟机必须根据运行时线程数、分配速率、堆压力，动态调整 TLAB 大小和 refill 策略。这是"适应性调整"思想在"对象分配"这一最热点路径上的体现——与第4章 JIT 的分层编译、第5章 GC 的分代设计、第6章锁的升级机制一脉相承。

## 14.5 大 OS 页与预取：硬件协同的吞吐量优化

这是全章最具"硬件视角"的部分——如何利用现代 CPU 和 OS 的内存管理能力提升 GC 吞吐量？

### 大页（Large Pages / Huge Pages）

工业实践指南明确指出，在 Linux 等支持大页的操作系统上，可以通过以下参数启用大页支持：

```
-XX:+UseLargePages -XX:LargePageSizeInBytes=2m
```

**大页的吞吐量收益**：

1. **TLB（Translation Lookaside Buffer）命中率提升**：TLB 是 CPU 中缓存虚拟地址到物理地址映射的高速缓存。使用 2MB 大页替代 4KB 默认页，TLB 可覆盖的虚拟地址范围扩大 512 倍，大大减少 TLB miss
    
2. **页表遍历开销降低**：大页减少页表级数，加快地址转换
    
3. **GC 扫描效率提升**：GC 在标记阶段需要遍历大量对象，大页带来的 TLB 命中率提升直接转化为 GC 吞吐量的提升
    

> ⚠ **工业注意事项**：大页并非银弹。它需要 OS 层面的配置（如 Linux 的 `hugetlbfs`），且大页内存通常不可Swap，配置不当可能导致内存浪费或其他应用内存紧张。但在吞吐量优先的批处理、大数据场景中，大页通常能带来 5-10% 的吞吐量提升。

### 内存预取（Prefetching）

GC 在遍历对象图（标记阶段）和复制存活对象（复制算法）时，内存访问模式相对规律——顺序扫描堆空间。

现代 CPU 的**硬件预取器**可以自动识别顺序访问模式，提前将后续内存加载到缓存。但 JVM 可以通过以下方式进一步优化：

1. **GC 线程的软件预取**：在扫描大块内存前，显式插入预取指令
    
2. **对象布局优化**：通过"标记-压缩"让存活对象在内存中紧凑排列，提升缓存局部性
    
3. **GC 工作线程的 NUMA 感知**：在 NUMA 架构的多插槽服务器上，让 GC 线程优先访问本地内存节点
    

Oracle 官方文档提到的 Amdahl 定律分析揭示了一个关键事实：

> "The red line is an application spending only 1% of the time in garbage collection on a uniprocessor system. This translates to more than a 20% loss in throughput on 32 processor systems."

即：在单处理器上仅占 1% 时间的 GC，在 32 处理器系统上会导致超过 20% 的吞吐量损失！这是因为 GC 的串行部分（无法完美并行化）成为可扩展性的瓶颈。**大页和预取优化，正是通过减少 GC 的内存访问开销，缓解这一可扩展性瓶颈**。

> 💡 **洞见（本章核心判断之四）**：大页与预取优化揭示了一个深刻的工程事实——**GC 吞吐量的天花板，往往不在于算法本身，而在于内存子系统的效率**。在 TB 级堆、数十核 CPU 的现代服务器上，GC 线程的内存访问模式决定了吞吐量上限。TLB miss、cache miss、NUMA 远程访问，这些"隐性开销"可能占据 GC 总时间的 30-50%。通过大页减少 TLB miss、通过预取隐藏内存延迟、通过 NUMA 感知优化本地内存访问，这些"底层优化"在吞吐量优先的场景下，往往比"算法层面的微调"带来更显著的收益。这正是为什么现代 GC（如 ZGC）在设计时就深度考虑了 NUMA 感知（`-XX:+UseNUMA`）和大页支持——**吞吐量优化必须"软硬协同"**。

## 贯穿第14章的三条暗线（承上启下）

1. **"适应性调整"是吞吐优化的统一哲学**：无论是回收范围（部分堆 vs 全堆）、分代策略（分代 vs 非分代）、堆空间大小、年轻代大小、分配空间布局，HotSpot 的 Parallel Collector 都通过运行时统计和适应性调整，动态寻找最优配置。这与前几章的"解释器/JIT 分层"、"GC 分代"、"锁升级"、"快慢路径分离"一脉相承——**HotSpot 的设计哲学是"让虚拟机根据运行时情况自适应优化"，而非"让用户手动调参"**。
    
2. **"吞吐量优先"≠"停顿最短"**：这是本章最重要的认知纠偏。Parallel Collector 的目标是 `GCTimeRatio`（总 GC 时间占比），而非 `MaxGCPauseMillis`（单次停顿时长）。在纯吞吐场景下，我们宁可接受较长的单次停顿，也要减少 GC 频率——因为"少做"比"快做"更能提升吞吐量。
    
3. **"硬件协同"是吞吐优化的最后一公里**：大页、预取、NUMA 感知——这些"底层优化"在现代多核、大内存服务器上对 GC 吞吐量有决定性影响。GC 吞吐量的天花板往往不在于算法，而在于内存子系统的效率。
    

---

**本章最核心的一句话**：针对吞吐量的 GC 优化，本质是在"回收范围（部分堆 vs 全堆）、分代策略（分代 vs 非分代）、堆空间大小、年轻代布局、分配空间（TLAB）、硬件协同（大页/预取/NUMA）"六个维度上做**连续的适应性调整**，目标是**让单位有用工作所承担的 GC 开销最小**——而非让单次停顿最短。HotSpot 的 Parallel Collector 通过 `GCTimeRatio` 量化吞吐目标，按"停顿时间 → 吞吐量 → footprint"的优先级动态调整代大小（增长 20%/收缩 5% 的非对称速率），并根据运行时对象生命周期特征在分代与非分代之间做适应性选择。理解这套"六维适应性调整"框架，你就拿到了看懂现代 JVM 吞吐优化的钥匙。

> 📌 **工业实践提示**：本章知识的直接应用包括——
> 
> - **吞吐量场景选型**：批处理、大数据、后台计算任务首选 `-XX:+UseParallelGC`，并配合 `-XX:+UseParallelOldGC` 让全堆回收也并行
>     
> - **参数配置铁三角**：`-Xms` 和 `-Xmx` 设为相等值（避免堆动态伸缩）、`-XX:ParallelGCThreads` 设为物理核心数的 70-100%、`-XX:+UseAdaptiveSizePolicy` 开启自适应
>     
> - **量化吞吐目标**：`-XX:GCTimeRatio=99`（GC 时间占比 ≤1%）或根据业务需求调整
>     
> - **大页优化**：Linux 下 `-XX:+UseLargePages -XX:LargePageSizeInBytes=2m`
>     
> - **监控与验证**：通过 GC 日志观察 Minor GC 频率、Full GC 触发频率、Survivor 空间利用率（应 <75%）、老年代增长速率
>     
> - **避免过早晋升**：通过调整 `-XX:MaxTenuringThreshold` 和 `-XX:TargetSurvivorRatio`，防止中等寿命对象过早晋升到老年代
>     
> - **NUMA 感知**：多插槽服务器上启用 `-XX:+UseNUMA`
>
