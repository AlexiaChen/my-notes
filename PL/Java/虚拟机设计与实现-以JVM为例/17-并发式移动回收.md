
# 第17章 并发移动式回收 —— 读书笔记

如果说第14章回答了"如何让 GC 总时间占比最小"（吞吐量），第15章回答了"如何让 GC 随核数线性加速"（可扩展性），第16章回答了"如何让 STW 停顿有界"（响应性），那么第17章要回答的是 GC 设计的"圣杯问题"——**当对象必须被移动（复制/压缩）时，GC 线程与 Mutator 线程如何真正并发地完成整个移动过程，把最后的 STW 尾巴也砍掉？**​ 这就是"并发移动式回收（Concurrent Moving Collection）"。李晓峰在这一章实际上在讲一个被工业界反复验证的真理——**并发移动的本质，是在"对象同一性"与"对象地址可变性"之间建立一套不变式（Invariant）——通过让目标空间、当前副本或源空间中的某一个在并发期保持不变，用转发指针、读屏障或虚拟内存映射，让 Mutator 在对象被搬动时仍能正确访问**。

结合李晓峰原书第17章框架、Shenandoah 的 Brooks 指针转发设计 、ZGC 的染色指针与读屏障机制 ，以及复制/压缩算法的基础理论 ，我来梳理这一章的脉络，并注入一些第一性原理层面的思考。

## 17.1 并发复制："目标空间不变"——最早的并发移动不变式

这是全章的第一种不变性策略——**保证"目标空间"在并发复制期间不被 Mutator 修改**，从而让 GC 线程可以安全地把对象复制到目标空间。

### 17.1.1 基于槽位的"目标空间不变"算法

**核心思想**：目标空间被划分为固定大小的槽位（slot），每个槽位在并发复制期间只被一个 GC 线程拥有。GC 线程将存活对象复制到这些槽位中，Mutator 不访问目标空间（或者通过屏障受限访问）。

**工作流程**：

1. GC 线程遍历对象图，将存活对象复制到目标空间的预分配槽位
    
2. 在旧对象头中留下转发指针（forwarding pointer），指向新槽位
    
3. Mutator 访问旧对象时，通过读屏障发现转发指针，转发到新槽位
    
4. 复制完成后，目标空间整体激活，源空间被回收
    

**理论基础**：复制算法（Copying Collector）天然适配这种模型——将堆分为 from-space 和 to-space，所有新对象复制到 to-space，from-space 留下 forwarding pointer 。这是 Cheney 复制算法在并发场景下的自然延伸。

### 17.1.2 "目标空间不变"性

**不变式的形式化定义**：

> 在并发复制期间，目标空间中的每个槽位要么为空、要么包含一个完整复制的对象。Mutator 永远不会观察到"半复制"的对象。

**保证机制**：

- 目标空间槽位的分配是单线程的（或通过 CAS 原子分配）
    
- 对象复制是"原子可见"的——要么完全复制完成（转发指针设置），要么未开始
    
- Mutator 通过转发指针访问目标空间，永远不会直接写入目标空间
    

**优势**：

- Mutator 可以并发读取目标空间中的对象（只读）
    
- GC 线程可以安全并行复制
    

**劣势**：

- Mutator 不能并发写入目标空间——这限制了某些场景的并发度
    
- 目标空间必须是预分配的（from-space/to-space 模型），空间利用率 50%
    

### 17.1.3 对象转发

**转发指针（Forwarding Pointer）是"目标空间不变"策略的核心数据结构**​ 。

**工作原理**：

```
复制前：
  [Old Object] → 无转发指针（或指向自身的 Brooks 指针）
  
GC 线程复制：
  [Old Object] → forwarding pointer → [New Object in To-Space]
  [New Object] → 完整复制的数据
  
Mutator 访问旧对象：
  读屏障检查 → 发现转发指针 → 转发到 New Object
```

**关键保证**：转发指针的设置必须是原子的（通过 CAS 指令）。一旦转发指针设置完成，所有后续访问都通过它转发到新对象 。

### 17.1.4 基于对象的"目标空间不变"算法

这是 Shenandoah GC 的核心设计——**在每个对象头前增加一个新的字段：Brooks 指针**​ 。

**Brooks 指针的设计**​ ：

- Brooks 指针源自 Rodney A. Brooks 1984 年的论文《Trading Data Space for Reduced Time and Code Space in Real-Time Garbage Collection on Stock Hardware》
    
- Shenandoah 在每个对象的最前面（对象头之前）统一增加一个 Brooks 指针字段
    
- **正常状态**：Brooks 指针指向对象本身（类似句柄，直接指向对象实际地址）
    
- **迁移状态**：Brooks 指针指向对象的新地址（迁移完成后）
    

**工作流程**​ ：

1. GC 线程启动并发迁移，将对象从旧地址复制到新地址
    
2. 通过原子操作（CAS）将旧对象的 Brooks 指针更新为指向新地址
    
3. 应用线程访问对象时，读屏障检查 Brooks 指针：
    
    - 指向自身 → 对象未移动，直接访问
        
    - 指向新地址 → 对象已移动，通过 Brooks 指针转发
        
    
4. 后续 Shenandoah 还有并发引用更新阶段，将堆中所有指向旧对象的引用更新为新地址
    

**Shenandoah 选择 Brooks 指针的根本原因**​ ：

- **无需 remembered set**：转发指针让每个 Region 可以独立回收，不需要跟踪跨区域引用
    
- **无用户/内核态陷阱依赖**：纯软件方案
    
- **无读风暴**：不需要像某些方案那样批量更新引用
    
- **对象格式不变**：JVM 内部对象布局不变，第三方工具仍可遍历堆
    

**代价**​ ：

- **每个对象额外一个指针大小的空间开销**（在 64 位系统上是 8 字节）
    
- **并发瓶颈**：转发指针可能成为并发访问的热点
    
- **每次对象访问都需要一次额外的间接寻址**（通过 Brooks 指针）
    

> 💡 **洞见（本章核心判断之一）**："目标空间不变"+ Brooks 指针的方案，本质是用"空间换并发"——每个对象多一个指针字段，换来"GC 线程与应用线程真正并发复制"的能力。Shenandoah 的设计哲学是——**让转发指针成为对象身份的"稳定锚点"**：无论对象在内存中如何移动，通过 Brooks 指针总能找到它。这是"目标空间不变"策略在工业界最成功的兑现，也是 Shenandoah 能够实现"停顿时间与堆大小无关"的根本原因 。

### 17.1.5 基于虚拟内存的"目标空间不变"算法

这是 ZGC 的核心设计——**利用 64 位虚拟地址空间的冗余位，在指针本身存储 GC 状态（染色指针），通过多重虚拟内存映射实现"目标空间不变"**​ 。

**染色指针的设计**​ ：

- 64 位指针中，bits 0-41 存储对象真实地址（最大 4TB 堆）
    
- bits 42-45 存储元数据标记（Marked0、Marked1、Remapped、Finalizable）
    
- 高位 bits 46-63 未使用
    

**关键创新**：**ZGC 将三个不同的虚拟地址视图映射到同一块物理内存**​ ：

- Marked0 视图：指针的第 43 位为 1
    
- Marked1 视图：指针的第 44 位为 1
    
- Remapped 视图：指针的第 42 位为 1
    

**工作流程**​ ：

```
并发标记阶段：
  Mutator 读取引用 → 读屏障检查指针颜色
  如果是 Remapped → 改为 Marked0，加入标记队列
  如果是 Marked0 → 快路径通过
  
并发重定位阶段：
  GC 线程将对象从旧地址 A 复制到新地址 B
  在转发表（Forwarding Table）中记录 A → B
  Mutator 读取指向 A 的旧引用 → 读屏障检查
  发现颜色不是 Remapped → 查转发表获取 B
  原地修正指针为 B 且颜色改为 Remapped（自愈）
  后续访问全部走快路径
```

**ZGC vs Shenandoah 的对比**：

|维度|Shenandoah（Brooks 指针）|ZGC（染色指针 + 读屏障）|
|---|---|---|
|转发信息存储|对象头前的 Brooks 指针|指针本身的颜色位 + 全局转发表|
|对象布局修改|每个对象增加一个指针字段|对象布局不变|
|虚拟地址依赖|无，兼容性好|需要 64 位平台的虚拟地址冗余位|
|读屏障开销|每次访问均需间接寻址|快路径仅检查颜色位，多数情况快路径通过|
|自愈机制|后续并发引用更新阶段批量更新|读屏障首次访问时原地修正（自愈）|

> 💡 **洞见**：两种"目标空间不变"的工业实现，代表了"空间换并发"的两种哲学——**Shenandoah 把转发信息存在对象里（空间开销摊到每个对象），ZGC 把转发信息存在指针里（空间开销是固定的几位 + 全局转发表）**。ZGC 的染色指针更巧妙——它利用 64 位地址空间的"浪费位"存储 GC 状态，让每个指针自带元数据，无需 dereference 对象头即可判断对象状态 。这是硬件特性（64 位地址空间的冗余位）与软件设计（读屏障）的完美协同。

## 17.2 并发复制："当前副本不变"——应对"对象移动风暴"

这是全章的第二种不变性策略，也是最具"工程挑战"的部分。

### 17.2.1 对象移动风暴

**问题场景**：在并发复制过程中，如果 Mutator 频繁修改对象，可能导致"对象移动风暴"：

- GC 线程正在复制对象 A 到新地址 A'
    
- Mutator 修改了 A 的字段
    
- 如果 GC 线程已经复制了 A 的旧状态，修改会丢失
    
- 如果 GC 线程尚未复制 A，修改会被复制到 A'
    

**核心难题**：**"当前副本"在并发期是变化的——Mutator 在修改它，GC 在复制它**。如何让双方协作而不丢失更新？

### 17.2.2 "当前副本不变"设计

**不变式的形式化定义**：

> 在并发复制期间，"当前副本"（Mutator 正在访问的副本）保持不变。GC 线程复制的是"快照副本"，而非"当前副本"。

**实现机制**：

1. **写屏障介入**：Mutator 修改对象字段时，写屏障捕获修改
    
2. **双副本策略**：
    
    - **当前副本**（Current Copy）：Mutator 正在读写的副本
        
    - **快照副本**（Snapshot Copy）：GC 线程复制的副本，基于复制开始时的状态
        
    
3. **修改日志**：Mutator 的修改被记录在日志中，GC 线程复制完成后，将日志中的修改应用到新副本
    

**Shenandoah 的实际做法**​ ：

- 正常状态：Brooks 指针指向对象本身
    
- Mutator 修改对象字段时，通过写屏障确保修改的是"当前副本"
    
- GC 线程复制对象时：
    
    - 通过 CAS 将 Brooks 指针从"指向自身"改为"指向新副本"
        
    - 这个 CAS 操作是并发复制的关键同步点
        
    - 如果 CAS 成功 → GC 线程拥有复制权，Mutator 后续访问通过 Brooks 指针转发到新副本
        
    - 如果 CAS 失败 → 说明 Mutator 或其他 GC 线程已经启动了复制，当前线程放弃
        
    

**ZGC 的"无当前副本概念"**：

- ZGC 的染色指针模型下，不存在"当前副本不变"的问题——因为 Mutator 访问对象时，读屏障总是在"加载引用"的那一刻决定去哪个视图（Marked0/Marked1/Remapped）访问
    
- 对象的数据只有一个副本，但指针的颜色位决定了"逻辑视图"
    
- 当 GC 移动对象时，旧地址的转发表记录新地址，Mutator 的读屏障自动通过转发表找到新地址
    

### 17.2.3 并发复制与并发堆追踪的关系

**关键洞察**：并发复制通常不是独立进行的，而是与并发堆追踪（Concurrent Tracing）紧密协作。

**两种协作模式**：

**模式 A：先追踪后复制（Shenandoah 的初始设计）**

```
并发标记 → 确定存活对象
并发复制 → 将存活对象复制到新 Region
并发引用更新 → 更新所有指向旧对象的引用
```

**模式 B：追踪与复制交织（ZGC 的设计）**

```
并发标记（顺便触发自愈）
并发重定位（GC 移动对象 + Mutator 读屏障自愈）
```

**Shenandoah 的并发引用更新阶段**​ ：

- 对象复制完成后，堆中仍有大量指向旧地址的引用
    
- Shenandoah 需要并发地将这些引用更新为新地址
    
- 这是 Shenandoah 相对于 ZGC 的一个额外阶段——ZGC 通过读屏障的"自愈"机制，在 Mutator 首次访问时懒更新引用，无需独立的引用更新阶段
    

> 💡 **洞见（本章核心判断之二）**："当前副本不变"策略的本质，是**用并发协议解决"读写并发"问题**。Shenandoah 用 Brooks 指针 + CAS + 写屏障，确保 GC 线程和 Mutator 不会同时修改同一个副本；ZGC 用染色指针 + 读屏障，让"对象数据"单一副本+"指针颜色"多视图，从根本上避免了"双副本"问题。这是两种截然不同的工程哲学——**Shenandoah 选择"显式协作"（通过 Brooks 指针和 CAS 实现双方协议），ZGC 选择"隐式协作"（通过指针颜色和读屏障让 Mutator 自我调节）**。后者更优雅，但依赖 64 位虚拟地址空间的冗余位；前者更通用，但对象头开销更大 。

## 17.3 并发复制："源空间不变"——反向思维

这是全章的第三种不变性策略，也是最反直觉的一种。

### 17.3.1 "源空间不变"设计

**核心思想**：**保证源空间的数据在并发复制期间不被修改**——Mutator 所有的读写都通过转发指针重定向到目标空间的新副本。

**不变式的形式化定义**：

> 在并发复制期间，源空间中的对象数据是只读的。任何对源空间对象的写操作，都被写屏障重定向到目标空间的新副本。

**工作流程**：

1. GC 线程决定将源空间 Region 中的对象复制到目标空间
    
2. 立即为源空间 Region 设置"转发模式"——所有对该 Region 中对象的访问都通过 Brooks 指针转发
    
3. Mutator 尝试修改源空间对象时：
    
    - 写屏障检测到对象在"待复制"状态
        
    - 如果对象尚未复制 → 触发紧急复制（或让 Mutator 帮助复制）
        
    - 如果对象已复制 → 修改重定向到新副本
        
    
4. GC 线程并发复制所有存活对象到目标空间
    
5. 复制完成后，源空间 Region 整体回收
    

**与"目标空间不变"的对比**：

|维度|目标空间不变|源空间不变|
|---|---|---|
|不变的场所|目标空间（新副本）|源空间（旧副本）|
|Mutator 写入|受限（不能直接写目标空间）|受限（不能直接写源空间，必须重定向）|
|转发指针方向|旧对象 → 新对象|旧对象 → 新对象（相同）|
|并发度|GC 复制时 Mutator 可读旧对象|GC 复制时 Mutator 的写操作被重定向|
|典型应用|经典复制算法并发化|Shenandoah 的部分阶段|

### 17.3.2 部分转发"源空间不变"设计

**核心思想**：不是整个源空间 Region 都进入"源空间不变"模式，而是**对象粒度**的部分转发。

**工作流程**：

1. GC 线程复制对象时，通过 CAS 将该对象的 Brooks 指针从"指向自身"改为"指向新副本"
    
2. CAS 成功的那一刻，该对象进入"源空间不变"模式——Mutator 对该对象的访问都通过 Brooks 指针转发
    
3. 尚未被复制的对象，Mutator 可以直接访问和修改
    
4. GC 线程逐步复制所有存活对象，每个对象在复制完成的瞬间进入"源空间不变"模式
    

**Shenandoah 的实际实现**​ ：正是这种"部分转发"的"源空间不变"策略——每个对象独立地通过 Brooks 指针的 CAS 操作进入转发状态，而不是整个 Region 同时进入。

> 💡 **洞见**："源空间不变"策略的精妙之处在于——**它把"不变"的粒度从"整个空间"细化到"单个对象"**。这种细粒度让 GC 线程和 Mutator 可以真正细粒度并发：GC 线程复制对象 A 时，Mutator 可以并发修改对象 B（只要 B 尚未被复制）。这是并发度最大化的关键——**不变性的粒度越细，并发度越高**。Shenandoah 的 Brooks 指针 CAS 操作，正是这种细粒度"源空间不变"的工程兑现。

## 17.4 无 STW 的完整并发移动

这是全章最具"理想主义"色彩的部分——**能否完全没有 STW，让整个移动过程都与 Mutator 并发？**

**理论可行性**：

- 标记阶段：可与 Mutator 并发（SATB 或增量更新保证正确性）
    
- 复制阶段：可通过 Brooks 指针或染色指针与 Mutator 并发
    
- 引用更新阶段：可通过读屏障的"自愈"机制与 Mutator 并发
    

**工业现实**：

- **Shenandoah**：初始标记和最终标记需要极短的 STW（通常 <10ms，甚至亚毫秒），其余阶段完全并发
    
- **ZGC**：只有三个极短的 STW 阶段（初始标记、再标记、初始转移），且都只扫描 GC Roots，停顿时间与堆大小无关，通常在 1ms 以内
    

**"无 STW"的挑战**：

1. **Root 扫描的原子性**：GC Roots（线程栈、JNI 引用）在物理上需要 Mutator 暂停才能一致地扫描
    
2. **转发表的原子切换**：ZGC 需要在某个原子点切换"使用转发表"的状态
    
3. **极端边缘情况**：某些硬件或 OS 级别的操作可能需要极短暂的 STW
    

> ⚠ **工业现实**：真正的"零 STW"在目前的工业实现中仍未完全达成——Shenandoah 和 ZGC 都有极短的 STW 阶段（亚毫秒到几毫秒）。但这里的"无 STW"指的是——**移动（复制/压缩）这个最耗时的阶段完全并发**，STW 仅用于必须原子操作的极短根扫描。这是目前工业界的最优解，也是"响应性优化"的终极兑现。

## 17.5 并发压缩回收：当"复制"不够用时

这是全章的收官部分——**复制算法需要 2x 空间（from-space/to-space），而压缩算法（Compaction）在原地完成，空间效率更高**。但压缩的并发化比复制更难。

### 17.5.1 并发区域复制式回收

**核心思想**：**将压缩问题转化为区域复制问题**——每个 Region 独立地"复制"其存活对象到新的 Region，原 Region 被回收。

**工作流程**（类似 G1 的 Mixed GC 但完全并发化）：

1. 选择一组待回收的 Region（CSet）
    
2. 为每个 CSet Region 分配目标 Region
    
3. 并发复制：将 CSet Region 中的存活对象复制到目标 Region
    
4. 通过 Brooks 指针或染色指针，让 Mutator 并发访问被移动的对象
    
5. 复制完成后，CSet Region 整体回收
    

**Shenandoah 的并发压缩**​ ：正是这种模式——利用 Brooks 指针让每个 Region 独立回收，无需 remembered set。

**优势**：

- 空间效率高于纯复制算法（不需要整个 to-space 预分配）
    
- 可以增量进行——每次只回收部分 Region
    

**劣势**：

- 需要管理 Region 之间的引用（通常通过 Brooks 指针或 RSet）
    
- 浮动垃圾问题——标记后变为垃圾的对象在本次周期中无法回收
    

### 17.5.2 基于虚拟内存的并发压缩

**核心思想**：**利用虚拟内存映射，让"物理内存中的压缩"对 Mutator 透明**。

**ZGC 的方案**​ ：

- 利用染色指针，将同一物理内存在不同虚拟地址视图中映射
    
- 并发压缩时，GC 线程将对象从物理页面 A 复制到物理页面 B
    
- 通过修改虚拟内存映射，让"旧虚拟地址"指向"新物理页面"
    
- Mutator 通过旧虚拟地址访问时，MMU 自动映射到新物理页面
    

**关键技术**：

- **染色指针**：在指针中编码 GC 状态
    
- **多重虚拟映射**：同一物理内存对应多个虚拟地址视图
    
- **读屏障**：在 Mutator 访问时检查和修正指针状态
    

**优势**：

- 真正的"原地压缩"——物理内存中被压缩，但对 Mutator 透明
    
- 无需为每个对象存储 Brooks 指针
    
- 读屏障快路径开销极小（仅检查颜色位）
    

**代价**：

- 依赖 64 位虚拟地址空间的冗余位
    
- 需要 OS 和硬件支持虚拟内存重映射
    
- 实现复杂度高
    

> 💡 **洞见（本章核心判断之三）**：并发压缩的两种工业实现，代表了"空间换并发"的两种终极形态——**Shenandoah 用 Brooks 指针（空间开销摊到每个对象）实现区域复制式并发压缩，ZGC 用染色指针+虚拟内存映射（空间开销是固定的指针冗余位）实现基于虚拟内存的并发压缩**。ZGC 的方案更优雅——它让"压缩"对 Mutator 完全透明，物理内存中被压缩，但虚拟地址视图保持不变，Mutator 通过旧虚拟地址访问时由 MMU 自动映射到新物理位置 。这是硬件特性（虚拟内存）与软件设计（染色指针+读屏障）的巅峰协同，也是 ZGC 能够实现"亚毫秒级停顿、与堆大小无关"的根本原因。

## 贯穿第17章的三条暗线（承上启下）

1. **"不变性选择"决定并发移动算法的形态**：目标空间不变（基于槽位/对象/虚拟内存）、当前副本不变、源空间不变——三种不变性策略代表了"让并发移动正确"的三种思路。Shenandoah 选择 Brooks 指针实现"对象粒度的源空间不变"，ZGC 选择染色指针+读屏障实现"指针粒度的目标空间不变"。**不变性的粒度越细，并发度越高**。
    
2. **"转发指针"是并发移动的通用原语**：无论是 Brooks 指针（Shenandoah）还是染色指针中的转发表（ZGC），核心思想都是通过"转发信息"让 Mutator 在对象被移动时仍能正确访问。**区别仅在于转发信息的存储位置**——对象头（Brooks 指针）vs. 指针本身（染色指针）+ 全局转发表。
    
3. **"无 STW 的并发移动"是响应性优化的终极目标**：Shenandoah 和 ZGC 都实现了"移动阶段完全并发"，仅保留亚毫秒级的 STW 用于根扫描等必须原子操作的工作。这是 GC 设计二十年来"STW 时间极小化"演进的终点——**从 Serial GC 的秒级 STW，到 Parallel GC 的百毫秒级 STW，到 G1 的十毫秒级 STW，到 Shenandoah/ZGC 的亚毫秒级 STW**。
    

---

**本章最核心的一句话**：并发移动式回收的本质，是通过建立**三种不变性策略**之一——目标空间不变（复制算法并发化，Shenandoah 用 Brooks 指针、ZGC 用染色指针+读屏障）、当前副本不变（应对对象移动风暴，通过 CAS + 写屏障确保 GC 与 Mutator 不冲突）、源空间不变（细粒度到对象级别的并发复制）——让 GC 线程与 Mutator 真正并发地完成对象的复制与压缩。**Shenandoah 用 Brooks 指针让每个 Region 独立回收、无需 remembered set，实现"目标空间/源空间不变"；ZGC 用染色指针+虚拟内存多重映射+读屏障自愈，实现"指针粒度的目标空间不变"并达到亚毫秒级停顿**。理解这套"不变性策略 + 转发指针 + 读屏障"的并发移动框架，你就拿到了看懂 Shenandoah/ZGC 等现代低延迟 GC 设计哲学的钥匙，也是《虚拟机设计与实现》GC 部分的真正收官。

> 📌 **工业实践提示**：本章知识的直接应用包括——
> 
> - **Shenandoah 适用场景**：需要低延迟但不想依赖 64 位虚拟地址冗余位的硬件/OS（如 ARM64 某些配置），或需要 Region 独立回收的灵活性
>     
> - **ZGC 适用场景**：64 位平台（x86-64、ARM64 等支持虚拟地址冗余位的架构），堆大小 8MB-16TB，要求亚毫秒级停顿
>     
> - **停顿时间对比**：Shenandoah 目标 ≤10ms（实际 2-5ms），ZGC 目标 <1ms，两者都与堆大小无关
>     
> - **吞吐量权衡**：Shenandoah 的 Brooks 指针带来 <10% 吞吐量开销 ；ZGC 的读屏障带来 10-15% 吞吐量开销
>     
> - **JDK 版本选择**：Shenandoah 从 JDK 12 实验性引入 ；ZGC 从 JDK 11 引入、JDK 15 生产就绪、JDK 21 引入分代 ZGC
>     
> - **避免误用场景**：小堆（<4GB）或吞吐量极端敏感的场景，Parallel GC 仍是更优选择（见第14章）
>
