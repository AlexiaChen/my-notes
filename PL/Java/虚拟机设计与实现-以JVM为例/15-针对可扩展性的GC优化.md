
# 第15章 针对可扩展性的 GC 优化 —— 读书笔记

如果说第14章回答了"如何在吞吐量目标下自适应调整 GC"（让 GC 总时间占比最小），那么第15章要回答的是一个让前面的所有讨论**真正能利用硬件**的问题——**当服务器从单核走向 8 核、32 核、128 核，当堆从 GB 级膨胀到 TB 级时，GC 如何保持近乎线性的加速比？为什么很多时候加核不加速？**​ 这就是"针对可扩展性的 GC 优化"。李晓峰在这一章实际上在讲一个被工业界反复验证的真理——**GC 可扩展性的本质，不是"用更多线程做同一件事"，而是"把不可预测的图遍历拆解成可并行、可窃取、低同步的任务流"**。理解这一章，你才能理解为什么 Flood 等人在 2001 年的开创性论文中，8 处理器上 pMarkcompact 达到了 5.5 倍的加速比，而现代多核下 Google 数据中心通过优化工作窃取仍能获得 38% 的 GC CPU 利用率提升。

结合李晓峰本人关于并行 GC 的演讲、Flood 等人的经典论文《Parallel Garbage Collection for Shared Memory Multiprocessors》、以及工业界对 HotSpot Parallel Compaction 的实现分析，我来梳理这一章的脉络，并注入一些第一性原理层面的思考。

## 15.1 回收阶段：可扩展性的"战场地图"

GC 的可扩展性优化，必须按阶段拆开来看——因为每个阶段的并行化难度截然不同。

一个完整的移动式 GC 周期包含以下阶段：

1. **根枚举（Root Scanning）**：从 GC Roots（线程栈、全局变量、JNI 引用等）出发，标识初始存活对象集合
    
2. **对象图遍历（Object Graph Traversal）**：从根集合出发，递归标记所有可达对象——**这是 GC 中不可预测性最高的阶段**
    
3. **标记（Marking）**：在对象头或 mark bitmap 中标记存活对象
    
4. **统计/规划（Summary）**：计算每个区域/对象的存活字节数，规划压缩后的目标地址
    
5. **引用修正（Pointer Fix-up）**：将所有指向被移动对象的引用更新为新地址
    
6. **对象移动（Compaction/Evacuation）**：将存活对象从旧地址复制到新地址
    

**各阶段的可扩展性特征**：

|阶段|可预测性|并行化难度|主要瓶颈|
|---|---|---|---|
|根枚举|高（根数量有限）|低|同步开销|
|对象图遍历|**极低（图形状任意）**​|**极高**​|负载均衡|
|标记|中|中|原子操作竞争|
|统计/规划|高|低（常单线程）|串行瓶颈|
|引用修正|中|中|内存带宽|
|对象移动|中|中|内存带宽、依赖环|

> 💡 **洞见（本章核心判断之一）**：GC 可扩展性的第一性原理是——**"不可预测的图遍历"是并行化的主战场，"可预测的规划阶段"常是串行瓶颈**。Flood 等人的论文明确指出："Parallelizing GC is inherently difficult because the workload—tracing the graph of live objects—is unpredictable and cannot be perfectly divided using static partitioning alone"。这就是为什么本章 15.2 节用整整一节讲"对象图遍历的并行化"——它是可扩展性优化的核心战场。而 15.4 节的并行压缩，则是在解决另一个难题——**"依赖环"**：目标地址依赖标记统计、指针修正依赖对象已移动、移动又依赖目标区已腾出。

## 15.2 并行对象图遍历：三种负载均衡策略

这是全章最具"算法美感"的部分，也是李晓峰并行 GC 演讲的核心内容。对象图遍历的任务是"访问图中的所有节点"——但图的形状是任意的、任务粒度很小（标记一个对象就是一项 task）、且各节点的工作量不均。如何让 N 个 collector 线程均衡地分担这项工作？

### 15.2.1 任务共享（Pool Sharing）

**核心思想**：所有 collector 线程从一个**共享的任务池**中获取任务。

**工作流程**：

1. 共享池中以"task block"为单位管理任务
    
2. 每个 collector 从池中抓取一个 task block
    
3. 从 task block 中 pop 出一个 task，push 到自己的 mark stack
    
4. 以 DFS 顺序扫描 mark stack 中的对象
    
5. 如果 mark stack 满了，将其链接到另一个 mark stack，把满的那个放回池
    
6. 如果 mark stack 空了，从 task block 中取另一个 task
    

**优势**：实现直观，负载均衡通过共享池自然实现

**劣势**：**需要同步访问共享池**——block size 和 stack depth 的选择直接影响性能；多核下池访问成为锁竞争瓶颈

### 15.2.2 工作窃取（Work Stealing）

**核心思想**：每个 collector 有自己的线程局部 mark stack，空闲时从其他 collector 的栈底"窃取"任务。

**工作流程**：

1. 每个 collector 有一个线程局部的 mark stack，初始分配来自根集合的引用
    
2. collector 在本地栈上无同步地操作
    
3. 如果本地栈空了，collector 从其他 collector 栈的**底部**窃取任务
    
4. 如果栈中只剩一个条目，collector 需要同步访问
    
5. 如果栈空了且无法窃取，该 collector 进入空闲
    

**优势**：本地操作**完全无同步**，仅在窃取时需要同步

**劣势**：栈满时需要特殊处理；窃取失败率高时 collector 空等

> ⚠ **工业现实**：工作窃取在理论上是优雅的，但在实际多核环境中面临严峻挑战。CSDN 上的 JVM 优化综述指出："Parallel GC 设计了任务窃取机制来平衡 GC 线程之间的负载，当 GC 线程拿到 CPU 时间片却没有可执行 GC 任务时，就会尝试从其他 GC 线程窃取任务。但任务窃取的方式是从任意两个其他 GC 线程的本地任务队列中窃取。由于大部分 GC 线程的本地任务队列都为空，任务窃取的失败率很高，导致没有任务的 GC 线程最终只能浪费 CPU 时间片空等。" 这正是 Suo 等人优化工作的出发点——他们记录还有 GC 任务的线程作为窃取目标，将应用总执行时间降低了近 50%。

### 15.2.3 任务推送（Task Pushing）

**核心思想**：每个 collector 有一组输出任务队列（每个其他 collector 一个），主动将任务推送给空闲的 collector。

**工作流程**：

1. 每个 collector 有一个线程局部的 mark stack 用于本地操作
    
2. 每个 collector 有一组输出任务队列，每个其他 collector 对应一个
    
3. 当新任务 push 进 mark stack 时，collector 检查是否有任务队列有空位
    
4. 如果有，从 mark stack 中"滴"一个任务 enqueue 到任务队列
    
5. 当本地 mark stack 空时，collector 检查输入任务队列是否有任务，有则 dequeue
    

**优势**：任务队列**大多是无锁的**（no synchronization instruction）——通过巧妙的队列设计，push 和 pop 操作可以完全无同步

**劣势**：实现复杂度高，需要维护 N-1 个输出队列

> 💡 **洞见（本章核心判断之二）**：三种策略构成了一个"同步开销频谱"——**任务共享（池访问同步）← 工作窃取（窃取时同步）← 任务推送（大多无锁）**。李晓峰在演讲中给出的顺序，恰好是从"有同步"到"无同步"的演进：任务共享需要同步访问共享池；工作窃取仅在窃取时需要同步；任务推送通过"每个 collector 有 N-1 个输出队列"的设计，让 push/pop 操作在大多数情况下无锁。这正是可扩展性优化的核心哲学——**"用无锁设计消除同步瓶颈"**。Google 数据中心的工作也验证了这一点：Hassanein 等人对 JVM 工作窃取的优化，在 Gmail 前端服务器上实现了 **GC CPU 降低 15-20%、整体 CPU 性能提升 5%**，在约 59000 个作业样本上 GC CPU 利用率**几何平均提升 38%**。这证明：在多核时代，**负载均衡策略的微小改进，可以带来巨大的生产环境收益**。

## 15.3 并行对象标记：原子操作与位图的艺术

标记阶段的并行化相对直观——多个线程同时标记对象，但需要处理"两个线程同时标记同一个对象"的竞争。

**工业级解决方案**：

- **HotSpot Parallel Compaction**​ 使用 **ParMarkBitMap**——一个每字两位的位图覆盖整个堆，一位标记对象起始、一位标记对象结束，无需对象头即可高效计算下一个对象和区域内的存活字数
    
- 每个 worker 线程有独立的 **PSMarkTaskQueue**（溢出任务队列）
    
- 存活对象通过 **PCMarkAndPushClosure**​ 标记，调用 `ParCompactionManager::mark_and_push()`
    
- 每个区域的存活字数统计累积在线程局部的 **MarkingStatsCache**（1024 条目的线程局部缓存）中，减少对全局 `ParallelCompactData::RegionData` 的竞争
    

> 💡 **洞见**：标记阶段的并行化精髓是——**"用线程局部缓存吸收竞争"**。全局的 mark bitmap 是共享的，但直接对全局结构做原子操作会造成严重的内存竞争。HotSpot 的解法是让每个线程先在本地缓存中累积统计，再批量刷回全局——这是"分流（shifting）"思想在 GC 标记阶段的经典应用，与第14章"TLAB 线程局部分配"的哲学一脉相承。

## 15.4 并行压缩：拆解"依赖环"的工程艺术

这是全章最具挑战性的部分——压缩（Compaction）为什么难并行？因为它有三个**阶段依赖**：

```
标记阶段 → 统计存活字节数 → 计算每个对象的新地址（依赖统计）
                                    ↓
引用修正阶段 → 更新所有指向旧地址的引用（依赖新地址已计算）
                                    ↓
移动阶段 → 将对象复制到新地址（依赖目标区域已腾出空间）
```

**这个依赖环是并行压缩的核心难题**。李晓峰原书讨论了五种并行压缩算法，每种都在以不同方式拆解依赖环：

### 15.4.1 并行 LISP2 压缩器：三段式拆解

经典的 LISP2 压缩算法是串行的，包含三个阶段：

1. **安装转发指针（Forwarding Pointer Installation）**：计算每个对象的新地址
    
2. **修正指针（Fix-up Pointers）**：更新所有引用
    
3. **移动对象（Move）**：复制对象到新地址
    

**并行化策略**（Abuaiadh-Ossia-Petrank-Silbershtein 2004）：

- 堆被划分为 N 个区域（N = 压缩线程数），划分不均匀以平衡工作量
    
- **每个区域独立压缩**，因此压缩阶段不需要同步操作
    
- **区域数量决定压缩质量**——区域数与压缩质量之间存在权衡
    

**改进压缩质量**：在偶数区域向左滑动、奇数区域向右滑动——这样最终只产生 N/2 堆对象（而非 N 堆）

**IBM 的并行压缩**（Abuaiadh et al. 2004）进一步演化：

- 不同于 Sun 的方案，对象被打包到堆的底部
    
- **空间开销优化**：用较小的表替换每个对象中的转发指针
    
- **两趟堆扫描**（每趟并行执行）：移动并记录信息 → 利用信息修正指针
    

> 💡 **洞见**：并行 LISP2 的核心思想是——**"分区域独立压缩 + 奇偶滑动方向"**。通过让每个区域独立工作，消除了压缩阶段的同步；通过奇偶区域不同滑动方向，减少了最终产生的"对象堆"数量，提升了压缩质量。这是在"并行度"与"压缩质量"之间的精妙权衡。

### 15.4.2 对象依赖树：理解压缩的依赖结构

压缩的依赖结构可以建模为一棵树：

- 节点 = 对象或区域
    
- 边 = "A 必须在 B 之前移动"的依赖关系
    

**串行压缩**：深度优先遍历依赖树

**并行压缩**：尽可能并行处理无依赖关系的节点

工业实现（如 HotSpot Parallel Compaction）通过 **RegionData**​ 结构跟踪依赖：

- `_destination`：目标地址
    
- `_source_region`：源区域
    
- `_dc_and_los`：目标区域计数（destination count）——编码有多少目标区域从该源区域接收数据
    
- 压缩时目标计数原子递减，归零时该区域变为可用
    

### 15.4.3 带用于转发指针的目标表的压缩器：用表替换每对象开销

这是 IBM 并行压缩的核心创新——**用全局转发表替换每个对象中的转发指针**：

- 传统 LISP2：每个对象需要一个额外的字存储转发指针 → **空间开销 O(对象数)**
    
- 改进方案：用较小的全局表存储转发信息 → **空间开销 O(区域数)**
    

**工业演进**：ZGC 的 Compressed Forwarding Tables（CFW）进一步压缩了这个表：

- 在分代 ZGC 上实现并发压缩
    
- 支持 mutator 并发重定位对象（减少延迟）
    
- 在内存不足时支持就地压缩
    
- 与 ZGC 现有的转发表集成
    

> 💡 **洞见**：转发指针的存储方式，是并行压缩的"空间开销旋钮"。每对象一个字是最简单但最耗空间的；全局表更紧凑但有查找开销。CFW 算法在分代 ZGC 上的实践证明——**"用计算换空间"在并发场景下是值得的**：虽然每次查引用都要做一次位运算 + 一次位图统计查表，但远小于维护"每对象一份转发地址"所需的存储和访问成本。这是"时间-空间权衡"在并发 GC 中的经典体现。

### 15.4.4 基于对象节的压缩器：用"节"拆解依赖

"对象节（Object Section）"是一种将堆划分为较大粒度单元的策略：

**工作流程**：

1. 堆被划分为固定大小的单位（units）
    
2. 每个线程遍历对象，统计单位中的存活字节数
    
3. 将连续的单位合并为区域（regions）
    
4. 区域是压缩的基本单位——区域包含的对象决定了它将被复制的方向
    

**HotSpot Parallel Compaction 的工业实现**：

- 堆划分为 **64K HeapWords 的固定大小区域**
    
- **稠密前缀（Dense Prefix）**：老年代的连续前缀区域密度足够高，移动它们的内容比节省的时间更多，因此这些对象原地进行，仅需调整指针
    
- **空间分裂（Space Splitting）**：当年轻代的存活数据不能完全放入老年代时，找到溢出对象并记录 SplitInfo，让一个源区域的数据流向两个不同的目的地
    

> 💡 **洞见**：基于对象节的压缩器，本质上是**"用粗粒度分区换取并行度，用细粒度统计换取压缩质量"**。区域数越多 → 并行度越高，但压缩后产生的空闲区域越多（分配效率降低）；区域数越少 → 压缩质量越高，但并行度降低。HotSpot 选择 **64K HeapWords**​ 的区域大小，正是这个权衡的工程兑现。而"稠密前缀"的优化则进一步减少了不必要的工作——**"不压缩"有时是最好的压缩**。

### 15.4.5 单趟就地压缩器（The Compressor）：一趟扫描的极限优化

这是压缩算法演进的"圣杯"——**只用一趟堆扫描完成完整压缩**。

**Compressor 算法（Kermany & Petrank）的核心创新**：

- **首次实现单趟堆扫描**的压缩器
    
- 完全压缩堆中所有对象
    
- **保持对象顺序**（sliding compaction）
    
- **低空间开销**
    
- 有并行版本和并发版本
    

**复杂度对比**：

|算法|堆扫描趟数|标记位图|备注|
|---|---|---|---|
|Jonkers, Morris|2|0|早起单线程算法|
|SUN 2001|3|0|首个并行压缩，但产生多个稠密区|
|IBM 2004|2|1|并行，非并发|
|**The Compressor**​|**1**​|**1**​|**首次单趟压缩**​|

**代价**：

- 仍需维护标记位图和偏移向量两份辅助数据结构
    
- 偏移向量的大小只和 block 的数量成正比，而非对象数量——内存开销可控
    
- newAddress 的计算需要位运算 + 位图统计查表，比"直接读转发地址"多花一点计算
    

> 💡 **洞见（本章核心判断之三）**：单趟压缩器的价值不仅在于"少扫一遍堆"，更在于**"缓存局部性的质变"**。由于不需要像 LISP2 那样反复完整遍历堆来分别完成"算地址"、"改引用"、"搬对象"三件事，缓存利用率相应更好。在 TB 级堆上，每减少一趟完整堆扫描，就意味着减少一次对全堆内存的遍历——这是**内存带宽是现代 GC 主要瓶颈**的直接回应。Compressor 的设计哲学是——**"用计算换带宽"**：用位运算+位图查表的计算开销，替代一次完整堆扫描的内存带宽开销。在内存带宽受限的多核服务器上，这是划算的交易。

> ⚠ **工业现实**：单趟压缩虽然优雅，但并非银弹。CSDN 的 GC 手册学习笔记指出——"仍然需要维护标记位图和偏移向量这两份辅助数据结构"，且"newAddress 的计算本身不是完全免费的"。在 HotSpot 的 Parallel Compaction 中，采用的是"标记 + 总结（summary，常单线程）+ 并行压缩"的三阶段策略，而非纯粹的单趟压缩——这是工程上"并行度"与"算法优雅性"的妥协。Parallel Compaction 通过 **Shadow Regions**​ 机制进一步打破依赖环：空闲线程发现目标区域仍被占用时，原子地将其标记为 ShadowRegion，分配备用区域（shadow_region）复制数据，等真实目标可用后再拷贝过去。这是"用空间换时间"拆解依赖环的工业典范。

## 贯穿第15章的三条暗线（承上启下）

1. **"负载均衡策略"决定遍历阶段的可扩展性上限**：任务共享（池访问同步）→ 工作窃取（窃取时同步）→ 任务推送（大多无锁），构成同步开销的频谱。Google 数据中心的实践证明，优化工作窃取可在生产环境获得 38% 的 GC CPU 利用率提升——**多核时代，负载均衡的微小改进 = 巨大的生产收益**。
    
2. **"依赖环拆解"是并行压缩的核心难题**：标记 → 统计 → 计算新地址 → 修正指针 → 移动对象，这五个阶段形成依赖环。五种并行压缩算法（并行 LISP2、对象依赖树、转发指针目标表、对象节、单趟压缩）本质上都在以不同方式拆解依赖：分区域独立压缩（并行 LISP2）、用表替换每对象开销（转发指针目标表）、粗粒度分区（对象节）、单趟扫描（Compressor）、影子区域（HotSpot Parallel Compaction）。
    
3. **"时间-空间-带宽"的三方权衡贯穿所有算法**：并行 LISP2 用"区域独立"换"并行度"，代价是压缩质量；转发指针目标表用"计算"换"空间"；单趟压缩用"计算"换"内存带宽"；稠密前缀用"不压缩"换"效率"。**没有最优算法，只有最适合场景的算法**——堆大小、核数、对象生命周期分布、延迟要求，共同决定选择哪种并行压缩策略。
    

---

**本章最核心的一句话**：针对可扩展性的 GC 优化，本质是在多核硬件上**拆解两个核心瓶颈**——"不可预测的对象图遍历"通过任务共享/工作窃取/任务推送三种负载均衡策略实现可扩展的并行标记（同步开销从有锁到无锁递减），"阶段间依赖环"通过并行 LISP2（分区域独立压缩）、转发指针目标表（空间换时间）、对象节（64K 区域粒度）、单趟压缩（计算换带宽）、影子区域（空间换依赖解耦）五种算法创新实现可扩展的并行压缩。Flood 等人在 8 处理器上实现了 5.5 倍加速，Google 通过工作窃取优化在生产环境获得 38% 的 GC CPU 利用率提升——**这证明 GC 可扩展性优化的第一性原理是："把不可预测的图遍历变成可窃取的任务流，把阶段间的依赖环拆解成可并行的独立工作"**。

>
