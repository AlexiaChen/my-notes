
# 第16章 针对响应性的 GC 优化 —— 读书笔记

如果说第14章回答了"如何让 GC 总时间占比最小"（吞吐量），第15章回答了"如何让 GC 随核数线性加速"（可扩展性），那么第16章要回答的是 GC 设计的第三极——**当业务指标是"单次停顿最短、延迟可控"时（Web 服务、B/S 架构、金融交易、实时推荐），虚拟机如何把必须 Stop-The-World 的工作极小化，并把其余工作并发化？**​ 这就是"针对响应性的 GC 优化"。李晓峰在这一章实际上在讲一个被工业界反复验证的真理——**响应性优化的本质不是"让 GC 更快"，而是"让必须 STW 的工作尽可能少、让其余工作与 Mutator 并发进行"**。这需要在四个维度上协同设计：用区域式堆控制单次回收粒度、用并发追踪（三色标记 + SATB/增量更新/读屏障）解决"Mutator 并发修改对象图"的漏标问题、用并发根集枚举消除"根扫描"这个传统 STW 热点、用并发回收调度让整个 GC 周期在 Mutator 运行过程中渐进完成。

结合 G1 官方文档（Oracle）对区域式 GC、SATB、Remembered Set 的权威描述 ，学术论文对 G1 软实时目标与"高概率满足而非硬保证"的精准分析 ，以及美团技术团队对 ZGC"全并发标记-转移-重定位"的工业实践 ，我来梳理这一章的脉络，并注入一些第一性原理层面的思考。

## 16.1 区域式 GC：把"回收粒度"从"整个堆"降到"Region"

这是全章的基石。响应性优化的第一性原理是——**STW 停顿时间 ∝ 单次回收的工作量**。如果把回收单位从"整个堆"降到"堆的一个小区域"，单次停顿自然可控。

### G1 的区域式堆设计

Oracle 官方文档明确描述 ：G1 将堆划分为大量等大小的 Region（1-32MB），每个 Region 动态扮演 Eden / Survivor / Old / Humongous 角色。这种设计的革命性在于——**G1 打破了"年轻代 vs 老年代"的物理分代边界**，代之以逻辑分代。

学术研究进一步阐释了 G1 的区域式设计哲学 ：

> "A major design goal in G1GC is collecting a region on its own, without any dependencies on others. Therefore, remembered sets are associated with each region for tracking the origin of inter-regional pointers, and filled by pointer-write barriers."

即：G1 的核心设计目标是**"独立回收单个 Region，而不依赖其他 Region"**。为实现这一点，每个 Region 关联一个 Remembered Set（RSet），通过写屏障记录跨 Region 指针的来源。

### 区域式 GC 的三种收集模式

G1 的官方文档 描述了三种收集模式：

1. **Young Collection（STW）**：仅回收 Eden + Survivor Region。从根集出发追踪，利用 RSet 处理从 Old 指向 Young 的引用（避免误回收），存活对象复制到新的 Survivor 或 Old Region。
    
2. **Concurrent Marking（并发）**：当 Old + Survivor Region 占用率超过 IHOP 阈值（默认 45%）时触发。复用 Young Collection 的根集，**采用 SATB 算法**——在并发堆遍历期间，所有指针修改的旧值都被写屏障记录，作为标记的附加根。保证标记开始时可达的所有对象最终都被遍历到。
    
3. **Mixed Collection（STW）**：并发标记完成后，在后续多次 Young Collection 中**逐步回收一部分 Old Region**——优先选择垃圾占比高的 Region（Garbage First 的命名由来），将多次 Old 回收分摊到多个有界停顿中。
    

> 💡 **洞见（本章核心判断之一）**：区域式 GC 的本质，是**"用空间换停顿可控性"**。RSet 为每个 Region 维护"谁引用了我"的精确地图，让回收单个 Region 时只需扫描其 RSet，而非全堆 。这正是响应性优化的第一性原理兑现——**把"必须扫描的范围"从"整个堆"压缩到"待回收 Region 的 RSet"**。但代价是：① 写屏障开销（每次引用写入都要维护 RSet）② 空间开销（RSet 本身占用内存）③ 浮动垃圾（SATB 保守策略导致标记开始时快照中的对象，即使后续变为垃圾也不会在本次周期回收）。G1 用"双重写屏障"（SATB 的 pre-write barrier + RSet 的 post-write barrier）换取了"绝对不漏标 + 无需全堆扫描" ，这正是它取代 CMS 成为 JDK 9 默认 GC 的技术根基 。

> ⚠ **工业现实**：G1 的区域式设计提供了"高概率满足停顿目标"而非"硬实时保证" 。Oracle 文档明确指出："G1GC can meet soft real-time deadlines with a high probability. However, no actual guarantees can be determined." 学术论文也证实："User-specified pause times are sometimes exceeded significantly" 。这意味着——G1 的 `MaxGCPauseMillis` 是**目标值而非承诺值**。在极端情况下（如 Humongous 对象分配、Evacuation Failure），G1 仍会触发单线程的 Full GC，造成秒级停顿 。理解这一点，对低延迟场景的 GC 选型至关重要。

## 16.2 并发追踪：三色标记与 Mutator 协作

这是全章最具"算法美感"的部分——**如何让 GC 线程与 Mutator 线程并发遍历对象图，而不漏标存活对象？**

### 三色标记：并发追踪的理论基础

三色标记算法将对象分为三种颜色 ：

|颜色|含义|
|---|---|
|**白色**​|尚未被 GC 访问过，标记结束时仍为白色的对象被回收|
|**灰色**​|已被 GC 访问，但其子引用尚未完全扫描|
|**黑色**​|已被 GC 访问，且所有子引用都已扫描完毕|

标记循环：从根集出发将所有根对象标记为灰色 → 从灰色集合中取出对象，将其白色子引用变为灰色，自身变为黑色 → 重复直至灰色集合为空 → 剩余白色对象即为垃圾。

### 并发场景的"对象消失"问题

当 Mutator 与 GC 并发运行时，可能出现两种情况破坏三色不变式（**不允许黑→白边**）：

1. **Mutator 插入**了从黑色对象到白色对象的新引用
    
2. **Mutator 删除**了从灰色对象到该白色对象的全部引用
    

如果同时满足这两个条件，白色对象会通过黑色对象"隐式"保持可达，但 GC 不会再次扫描黑色对象 → **白色对象被错误回收**。

### 16.2.1 起始快照（SATB）：G1 的选择

**SATB（Snapshot-At-The-Beginning）**​ 的核心思想 ：在并发标记开始时对堆对象图打快照，确保"标记开始时可达的所有对象，即使 Mutator 在并发期间解除了引用，也不会被漏标"。

**实现机制**：G1 使用 **pre-write barrier**——在 Mutator 修改引用**之前**，将旧值记录到 SATB 缓冲区：

```
// 伪代码：G1 的 SATB pre-write barrier
void pre_write_barrier(oop* slot, oop new_value) {
    oop old_value = *slot;
    if (old_value != null && is_white(old_value)) {
        satb_mark_queue.push(old_value);  // 记录被覆盖的旧引用
    }
    *slot = new_value;
}
```

并发标记结束后，Final Mark 阶段（STW）会扫描 SATB 缓冲区，将其中记录的对象作为附加根重新标记。

**SATB 的语义保证**：标记开始时快照中的对象，即使 Mutator 解除了所有指向它的引用，它仍然被 SATB 记录为"曾可达"，因此不会被错误回收。代价是**浮动垃圾**——这些对象在本次 GC 周期中不会被回收，留待下次 GC 处理 。

### 16.2.2 增量更新（Incremental Update）：CMS 的选择

**增量更新**的核心思想 ：当黑色对象**新增**了对白色对象的引用时，通过 post-write barrier 将这个黑色对象**变回灰色**，强制 GC 在标记结束前重新扫描它。

```
// 伪代码：CMS 的 Incremental Update post-write barrier
void post_write_barrier(oop* slot, oop new_value) {
    oop src = get_containing_object(slot);
    if (is_black(src) && is_white(new_value)) {
        mark_gray(src);  // 将黑色对象重新变为灰色
    }
    *slot = new_value;
}
```

**SATB vs 增量更新的对比**​ ：

|维度|SATB（G1）|增量更新（CMS）|
|---|---|---|
|关注对象|被**删除**的引用|新**插入**的引用|
|处理方式|记录被放弃的白色对象，Remark 阶段重新标记|把黑色对象变回灰色，重新遍历|
|浮动垃圾|较多|较少|
|Remark 工作量|只扫描 SATB 缓冲区（短 STW）|重新扫描全部老年代（长 STW）|
|实现复杂度|低|高|
|适用场景|大堆低延迟|-|

> 💡 **洞见**：SATB 和增量更新是"漏标防护"的两种哲学——**SATB 是"保守策略：宁可多标，不可漏标"**​ ；增量更新是"精确策略：只处理真正的新增引用"。G1 选择 SATB 的根本原因：**Remark 阶段只扫描 SATB 缓冲区，STW 时间远短于 CMS 的增量更新 Remark**​ 。这是用"较多的浮动垃圾"换取"更短的 Remark 停顿"——在响应性优先的场景下，这是划算的交易。

### 16.2.3 用三色术语表示并发追踪

三色标记的工程实现关键 ：

1. **颜色存储**：不使用对象头，而使用**位图（Mark Bitmap）**——每个对象用 2 位记录颜色状态，减少内存占用
    
2. **并行标记线程**：多个 GC 线程通过**工作窃取（Work Stealing）**​ 算法平衡负载
    
3. **原子操作**：颜色的转变（白→灰→黑）通过原子操作保证线程安全
    

### 16.2.4 使用读屏障的并发追踪：ZGC 的突破

这是全章最具革命性的部分——ZGC 摒弃了传统的写屏障 SATB 方案，转而采用**读屏障（Load Barrier）+ 染色指针（Colored Pointer）**​ 。

**ZGC 的读屏障机制**​ ：当应用线程读取对象引用（`obj.field`）时，读屏障介入：

- 检查指针的"颜色位"
    
- 如果对象已被 GC 移动 → 立即修正指针地址，指向新位置
    
- 如果对象未标记 → 触发标记，压入 Mark Stack
    
- 已标记 → 直接返回值
    

**ZGC vs G1 的屏障对比**​ ：

|维度|G1|ZGC|
|---|---|---|
|屏障触发点|引用**写入前**（Pre-write）|引用**读取时**（Load-time）|
|核心语义|SATB：保全初始快照可达性|On-the-fly：按需快照+实时修正|
|STW 卡表扫描|需要（Remark 阶段扫描 RSet）|完全避免（纯并发标记）|
|停顿时间|与 Region 数量、存活对象数相关|与堆大小**无关**，亚毫秒级|

> 💡 **洞见（本章核心判断之二）**：ZGC 的读屏障 + 染色指针，是"并发追踪"思想的终极兑现——**GC 移动对象时，不需要暂停所有线程，应用线程在访问时自动"自我修正"**​ 。美团技术团队的实践数据 ：ZGC 只有三个 STW 阶段（初始标记、再标记、初始转移），且都只依赖于 GC Roots 集合大小，**停顿时间不会随着堆的大小或者活跃对象的大小而增加**——这意味着无论是 1GB 还是 1TB 的堆，ZGC 的停顿都在亚毫秒级。代价是：**每次对象读取都要执行读屏障指令，吞吐量比 G1 低 10-15%**​ 。这是"响应性 vs 吞吐量"权衡的极致体现——ZGC 把"停顿时间"压到物理极限，代价是"单位工作的 GC 开销"上升。

## 16.3 并发根集枚举：消除最后一个 STW 热点

这是全章最具"HotSpot 内部视角"的部分。传统 GC 的根集枚举（扫描线程栈、JNI 引用、静态字段）必须 STW——因为 Mutator 在运行时会不断修改栈上的引用。

### 16.3.1 并发根集枚举设计

**核心挑战**：线程栈是 Mutator 高频修改的数据结构。如果 GC 线程与 Mutator 并发扫描栈，可能漏掉 Mutator 刚压栈的引用。

**G1 的方案**​ ：

- **Initial Mark 阶段**（STW，极短）：标记 GC Roots 直接关联的对象。这个阶段通常**搭载在 Young GC 的 STW 停顿上**，避免额外停顿
    
- **Root Region Scanning 阶段**（STW，极短）：扫描 Survivor Region 中指向老年代的引用（Survivor 属于"根区域"），必须在下次 Young GC 前完成
    

### 16.3.2 在根集枚举过程中追踪堆

G1 的并发追踪巧妙地把"根集枚举"和"堆追踪"交织进行 ：

1. Initial Mark（STW）：标记 GC Roots 直接关联的对象
    
2. 并发标记阶段：GC 线程与 Mutator 并发遍历对象图，SATB 写屏障记录 Mutator 的引用修改
    
3. Final Mark（STW）：处理 SATB 缓冲区中剩余的变动
    
4. 并发存活计算：统计每个 Region 的存活占比
    

### 16.3.3 并发栈扫描

这是 ZGC 相对 G1 的进一步突破。ZGC 的初始标记和初始转移**只扫描 GC Roots**​ ，其处理时间与 GC Roots 数量成正比——而 GC Roots 数量（线程数 × 栈深度）通常远小于堆中对象总数。

> 💡 **洞见**：并发根集枚举的本质，是**"把必须 STW 的根扫描压缩到极致"**。G1 通过"Initial Mark 搭载 Young GC"消除独立的根扫描停顿；ZGC 通过"只扫描 GC Roots 而非整个堆"让初始标记停顿与时间堆大小解耦。这是响应性优化的另一个第一性原理——**"STW 工作量 ∝ 必须原子操作的数据结构大小"**。GC Roots 的大小通常可控（数百个线程 × 数千栈帧），而堆对象数量可能达数十亿——将 STW 限定在前者而非后者，是亚毫秒级停顿的根本原因。

## 16.4 并发回收调度：让整个 GC 周期在 Mutator 运行过程中渐进完成

这是全章的"调度艺术"——如何将 GC 工作分解为"必须 STW 的短暂停顿"和"与 Mutator 并发的长任务"，并按响应性目标调度。

### 16.4.1 调度并发根集枚举

G1 的调度智慧 ：

- Initial Mark **搭载在 Young GC 上**（piggyback），避免独立停顿
    
- Root Region Scanning 必须在下一次 Young GC **之前**完成——G1 通过内部调度保证这一点
    

### 16.4.2 调度并发堆追踪

并发标记阶段的调度考量 ：

- **SATB 缓冲区管理**：Mutator 在写屏障中填充 SATB 缓冲区，GC 线程并发消费。如果 Mutator 填充速度超过 GC 消费速度，缓冲区积压 → 最终在 Final Mark 阶段造成长 STW
    
- **调优参数**：`-XX:G1SATBBufferSize` 控制 SATB 缓冲区大小，并发线程数影响消费速度
    

### 16.4.3 并发回收调度

G1 的 Mixed GC 调度是响应性优化的典范 ：

- **停顿预测模型**：基于历史数据（每个 Region 的回收时间、存活对象大小）预测本次回收的总时间
    
- **CSet 选择**：用贪心算法选择"回收价值最高"的 Region 集合，累计预测时间不超过 `MaxGCPauseMillis`
    
- **多批次分摊**：老年代回收被分摊到多次 Mixed GC 中，而非一次性 Full GC
    

### 16.4.4 并发回收阶段转换

G1 的完整 GC 周期阶段转换 ：

```
Young GC → (Old 占用率 > IHOP) 
   → Initial Mark (STW, 搭载 Young GC)
   → Concurrent Marking (并发, SATB)
   → Final Mark (STW, 短)
   → Live Counting (并发)
   → Mixed GC × N (STW, 每次受 MaxGCPauseMillis 约束)
   → 回归 Young GC
```

ZGC 的阶段转换更极致 ：

```
初始标记 (STW, 极短) 
   → 并发标记
   → 再标记 (STW, <1ms, 超时则重新并发标记)
   → 初始转移 (STW, 极短)
   → 并发转移/重定位
   → 并发标记循环...
```

> 💡 **洞见（本章核心判断之三）**：并发回收调度的本质，是**"把 GC 工作分解为'必须 STW 的原子操作'和'可与 Mutator 并发的渐进任务'，并在响应性目标的约束下动态调度"**。G1 的停顿预测模型让它"高概率"满足 `MaxGCPauseMillis` ；ZGC 通过"只 STW 扫描 GC Roots"让停顿时间与堆大小解耦，实现亚毫秒级常数停顿 。但两者都付出了代价：G1 的双重写屏障带来吞吐量开销，ZGC 的读屏障带来 10-15% 的吞吐量下降 。这是"响应性优化"的永恒真理——**停顿时间的降低，必然以吞吐量为代价**。

## 贯穿第16章的三条暗线（承上启下）

1. **"STW 工作量极小化"是响应性优化的第一性原理**：区域式 GC 把单次回收范围从"整个堆"压缩到"Region + RSet"；并发根集枚举把 STW 的根扫描压缩到"GC Roots 本身"；并发追踪把对象图遍历变成与 Mutator 并发进行。这三重压缩，让 STW 停顿从"与堆大小线性相关"变为"与 Region 数量或 GC Roots 数量相关"。
    
2. **"Mutator 协作"是并发追踪正确性的基石**：三色标记 + SATB（G1）或读屏障（ZGC）解决了"Mutator 并发修改对象图"的漏标问题。SATB 是"保守策略：宁可多标不可漏标" ，用浮动垃圾换取短 Remark 停顿；ZGC 的读屏障是"按需快照+实时修正"，完全避免 STW 卡表扫描 。
    
3. **"响应性 vs 吞吐量"的权衡无处不在**：G1 的双重写屏障、ZGC 的读屏障，都用吞吐量下降换取停顿时间降低。G1 是"高概率满足停顿目标"（软实时），ZGC 是"亚毫秒级常数停顿"（近似硬实时）。这是响应性优化的核心取舍——**没有"最优"的响应性 GC，只有"最适合业务场景"的 GC**。

**本章最核心的一句话**：针对响应性的 GC 优化，本质是在"STW 工作量极小化"和"GC 与 Mutator 最大程度并发"两个方向上协同发力——**区域式 GC（G1）把回收粒度从整个堆降到 Region，用 RSet + SATB 写屏障实现"独立回收单个 Region"且保证不漏标，通过停顿预测模型将老年代回收分摊到多次受控停顿中；ZGC 进一步用染色指针 + 读屏障实现"全并发标记-转移-重定位"，将 STW 限制在仅扫描 GC Roots 的范围内，实现与堆大小无关的亚毫秒级停顿**。理解这套"区域化 + 并发化 + 屏障协作"的响应性优化框架，你就拿到了看懂 G1/ZGC/Shenandoah 等现代低延迟 GC 设计哲学的钥匙。

> 📌 **工业实践提示**：本章知识的直接应用包括——
> 
> - **响应性场景选型**：延迟要求中等（堆 4-64GB）选 G1（`-XX:+UseG1GC`，调优 `MaxGCPauseMillis` 和 `InitiatingHeapOccupancyPercent`）；延迟要求极致（堆 >32GB）选 ZGC（`-XX:+UseZGC`，JDK 15+ 生产可用，JDK 21+ 支持分代）
>     
> - **G1 调优铁三角**：`-XX:MaxGCPauseMillis`（目标停顿，非承诺）、`-XX:G1SATBBufferSize`（SATB 缓冲区）、`-XX:InitiatingHeapOccupancyPercent`（IHOP 阈值）
>     
> - **ZGC 代价认知**：读屏障带来 10-15% 吞吐量下降，需要较新 CPU 架构支持（着色指针使用 64 位地址的多余位）
>     
> - **避免 Evacuation Failure**：G1 在 Humongous 对象分配、晋升过快时可能触发单线程 Full GC（秒级停顿）——通过调大堆、提前 IHOP、减少大对象分配来避免
>     
> - **Mixed GC 监控**：通过 GC 日志观察 Mixed GC 次数（应由 `G1MixedGCCountTarget` 控制分摊）、CSet 选择是否符合停顿目标
>     
> - **屏障开销权衡**：G1 的 SATB + RSet 双重写屏障是吞吐量低于 Parallel GC 的根源；ZGC 的读屏障是吞吐量低于 G1 的根源
>
