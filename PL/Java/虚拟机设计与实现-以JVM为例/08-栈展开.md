
# 第8章 栈展开 —— 读书笔记

如果说前七章回答了"虚拟机如何加载、表示、执行、回收、调度、跨语言互操作"，那么第8章要回答的是一个让所有这些子系统能够"安全地逆向穿越调用栈"的根本问题——**当异常需要传播、当 GC 需要枚举根、当调试器需要打印栈轨迹、当线程需要到达 Safepoint 时，虚拟机如何从一个正在运行的状态出发，逆向遍历整条调用栈？**​ 这就是"栈展开（Stack Unwinding）"。李晓峰在这一章实际上在讲一个被工业界反复打磨的真理——**栈展开不是"异常机制的附属品"，而是虚拟机运行时的一等公民能力，它是异常传播、GC 根枚举、调试/诊断、Safepoint 协作的共同基石**。理解栈展开，你才能理解为什么 JVM 能在"保持 Java 类型安全"的同时，还能正确地与本地代码互操作。

结合 JVM 规范中的异常处理语义、OpenJDK HotSpot 的 `StackFrameStream`/`RegisterMap`/`StackWatermark` 源码、以及 ORP（Open Runtime Platform）论文中对"托管帧/本地帧"混合展开的工程设计，我来梳理这一章的脉络，并注入一些第一性原理层面的思考。

## 8.1 为何需要栈展开：虚拟机的"逆向望远镜"

"栈展开"字面意思是"把栈帧一个个拆开"。但它的本质远比字面深刻——**它是虚拟机在"时间反方向"上遍历调用历史的能力**。

为什么需要这种能力？因为以下五个核心场景都要求 VM 能够"从当前执行点出发，逆向走完整个调用链"：

1. **异常传播**：当 `athrow` 在当前方法找不到匹配的异常处理块时，JVM 必须"弹出当前栈帧、恢复调用者栈帧、把异常对象压入调用者操作数栈、在调用者中重新查找异常表"——这个过程逐帧向上，直到找到匹配的 `catch` 或到达线程栈顶。
    
2. **栈轨迹填充**：`Throwable.fillInStackTrace()` 在异常对象创建时，需要遍历当前线程的所有栈帧，快照成 `StackTraceElement[]`——这是一个 O(栈深度) 的操作。
    
3. **GC 根枚举**：GC 在标记阶段需要从 GC Roots 出发遍历对象图，而 GC Roots 的重要组成部分就是"所有线程栈上的局部变量"——这要求 GC 能够精确地展开每个线程的栈，找到所有存活的 `oop` 引用。
    
4. **Safepoint 协作**：当 GC 需要暂停所有线程时，必须能够展开线程栈，确定线程当前停在哪条字节码、栈上哪些槽位持有对象引用（见第6章 6.10 节）。
    
5. **调试与诊断**：`jstack`、`Thread.dumpStack()`、IDE 调试器的调用栈视图，全部依赖栈展开能力。
    

> 💡 **我的洞见**：栈展开是虚拟机"自我反思（introspection）"能力的物理兑现。一个没有栈展开能力的执行引擎，就像一个没有后视镜的汽车——它能往前开（执行），但不能回头看（诊断、恢复、回收）。从第一性原理看，**栈展开的本质是"在程序执行的时间轴上逆向遍历"**——它需要栈帧结构中保存足够的元数据（返回地址、局部变量表、操作数栈、异常表、寄存器状态），让 VM 能够从"当前帧"推导出"上一帧"的完整状态。这种设计哲学贯穿了从 C 语言调用栈到 Java 虚拟机栈的所有实现——**调用栈不仅是"执行的载体"，更是"历史的记录"**。

## 8.2 Java 方法帧的栈展开：自描述的栈结构

Java 方法帧的栈展开是"理想情况"——因为 Java 栈帧是**自描述（self-describing）**的：每一个字节码方法都携带了完整的元数据（局部变量表大小、操作数栈深度、异常表、行号表），JVM 可以仅凭栈帧本身的结构化信息完成展开。

### 8.2.1 栈展开设计：异常表驱动的帧间跳转

Java 方法栈展开的核心数据结构是**异常表（Exception Table）**。每个方法的 Code 属性中都附带一张异常表，记录了一组条目：

```
起始 PC | 结束 PC | 处理器 PC | 捕获的异常类型
```

当 `athrow` 抛出异常时，JVM 在当前方法的异常表中查找：是否存在一条条目，使得"当前 PC 落在 [起始 PC, 结束 PC) 范围内"且"抛出的异常是捕获类型的子类"？

**查找算法的关键特征**：

- **顺序匹配**：JVM 按异常表条目的书写顺序线性扫描，第一个匹配的条目胜出
    
- **这意味着 catch 块的顺序影响性能**：更具体的异常类型应该写在前面，否则可能被更通用的异常"屏蔽"
    
- **finally 的本质**：编译器会为每个 try 块生成两份异常表条目——一份对应显式 catch（指定具体异常类型），一份对应隐式 finally（type = null，匹配所有异常）
    

**栈展开的执行流程**（当当前方法无匹配处理器时）：

```
1. 检查当前方法是否为 synchronized → 是则释放监视器锁
2. 弹出当前栈帧（局部变量表、操作数栈被销毁）
3. 将同一个异常对象引用（不是副本）压入调用者操作数栈顶
4. 恢复调用者栈帧为当前帧
5. 在调用者中重复异常表查找
6. 直至找到匹配的 catch，或传播到线程最顶层（线程终止）
```

> ⚠️ **关键细节**：栈展开过程中传递的是**同一个异常对象引用**，而非副本。这就是为什么异常对象的 `stackTrace` 字段在传播过程中保持不变——它记录的是原始的抛出位置，即使异常被多层向上捕获，栈轨迹依然显示真实的源头。

### 8.2.2 栈展开实现：frame 与 RegisterMap 的协同

在 HotSpot 中，Java 方法帧的栈展开由两个核心抽象完成：**`frame`**​ 和 **`RegisterMap`**。

**`frame` 类**：代表栈上的一个物理帧，提供 `sender(RegisterMap* map)` 方法，从当前帧推导出调用者帧。这个推导依赖于：

- 当前帧的栈指针（SP）和帧指针（FP）
    
- 返回地址（当前方法执行完后应返回的调用者 PC）
    
- 调用者的寄存器状态
    

**`RegisterMap` 类**：**寄存器状态映射表**。这是栈展开中最精妙的部分——当 JVM 展开一个帧时，必须恢复调用者的寄存器状态（因为被调用者可能使用了调用者保存的寄存器）。`RegisterMap` 记录了"每个寄存器的值当前存储在哪里"（可能在物理寄存器中，也可能已被 spill 到栈上）。

**`StackFrameStream`**：HotSpot 提供的栈帧迭代器，从栈顶帧开始，自动处理 `RegisterMap` 的更新：

```
for (StackFrameStream fst(thread); !fst.is_done(); fst.next()) {
    frame* f = fst.current();
    // 处理当前帧...
}
```

每次 `fst.next()` 调用 `frame::sender(RegisterMap*)`，根据当前帧的元数据恢复调用者的寄存器状态，并计算出调用者帧的位置。

> 💡 **洞见**：HotSpot 的 `StackFrameStream` + `RegisterMap` 机制揭示了一个深刻的工程事实——**栈展开不是"删除内存"，而是"状态恢复"**。JVM 并不真的"弹出"栈帧（那是函数返回时 OS 自动完成的），而是通过一个迭代器，从当前帧的元数据中"推算"出调用者帧的完整状态。这个过程之所以可能，是因为 Java 栈帧是**自描述的**——每个方法的 Code 属性包含了局部变量表大小、操作数栈最大深度等信息，JIT 编译后的机器码也保留了"栈图（Stack Map）"信息，让 VM 能够在任意 PC 位置精确地知道栈上哪些槽位持有对象引用。这种"自描述性"是 Java 栈帧区别于 C 栈帧的根本特征，也是 GC 能够安全枚举 Java 栈上所有引用的前提。

### 现代 HotSpot 的演进：StackWatermark 与"栈处理屏障"

JDK 21 中引入了 **StackWatermark**​ 机制，这是对栈展开能力的进一步深化——它允许 VM 在"不阻塞线程"的情况下，渐进式地处理栈帧。

StackWatermark 的核心思想：

- 每个线程维护一个"水印（watermark）"——表示"栈上已经处理到哪个位置"
    
- 当需要处理栈（如 GC 根枚举、Safepoint 协作）时，VM 从栈顶开始，每次处理几个帧，更新水印
    
- 线程在执行过程中，如果向下调用方法，会经过一个"栈屏障"，检查当前栈帧是否在水印之上——如果是，说明这个帧还未被处理，线程自己触发处理
    

源码注释揭示了关键设计：

```
// Always process three frames when starting an iteration.
// The three frames corresponds to:
// 1) The callee frame
// 2) The caller frame
// This allows a callee to always be able to read state from its caller
// without needing any special barriers.
// 3) An extra frame to deal with unwinding safepointing on the way out.
```

> 💡 **洞见**：StackWatermark 是"栈展开"思想在现代并发 GC 下的进化。传统 GC 需要 STW 后一次性展开所有线程的栈；而 ZGC/Shenandoah 等并发 GC 需要"在应用运行的同时"展开栈。StackWatermark 通过"水印 + 栈屏障"实现了**并发、渐进、无阻塞的栈处理**——线程自己在向下调用方法时"顺便"处理栈帧，VM 无需强制暂停线程。这是栈展开能力与并发 GC 协作的工业典范，也是 HotSpot 在 JDK 21 中 GC 停顿压到亚毫秒级的关键技术之一。

## 8.3 本地方法帧的栈展开：跨越托管/非托管的鸿沟

这是全章**最具挑战性**的部分，也是 Java 栈展开与 C/C++ 栈展开的根本分野。

### 8.3.1 栈展开设计：混合栈的"双重身份"

当一个线程既执行 Java 方法又调用本地方法时，它的调用栈变成了**混合栈**——Java 帧和本地（C/C++）帧交替出现。问题在于：

- **Java 帧是自描述的**：JVM 知道每个 Java 帧的精确布局
    
- **本地帧是非自描述的**：C/C++ 帧的布局依赖于编译器、优化级别、调用约定（ABI），JVM 无法直接"读懂"一个 C 帧
    

这就带来了一个根本挑战：**当异常从 Java 帧传播到本地帧，或从本地帧回到 Java 帧时，JVM 如何正确地展开？**

ORP（Open Runtime Platform）论文给出了工业级的答案：

> Unwinding a thread's stack proceeds by first identifying, for each frame, whether it is managed or native. If the frame is managed, the corresponding JIT is called to unwind the frame. Otherwise, the core VM uses a **last managed frame (LMF) list**​ to find the managed frame nearest the native frame.

**核心设计——LMF（Last Managed Frame）链表**：

- 每个线程在 TLS（线程局部存储）中维护一个 LMF 链表的头指针
    
- 每当 Java 调用 native 方法时，JVM 生成一个**wrapper 帧**（Java→native 的胶水代码），并在 LMF 链表中插入一个节点
    
- LMF 节点记录了：调用 native 之前的最后一个 Java 帧的位置、被调用者保存的寄存器、返回地址等信息
    
- 当栈展开遇到 native 帧时，VM 通过 LMF 链表"跳过"native 帧，直接定位到上一个 Java 帧
    

### 8.3.2 Java 到本地封装设计：Wrapper 帧的工程细节

HotSpot 调用 native 方法时，会生成一个 **native wrapper**（本地封装帧），执行以下关键步骤：

```
1. 创建栈帧
2. 按 ABI 将参数移动到正确的寄存器/栈位置
3. 将对象引用包装为 JNI 句柄（handle）
4. 获取 JNIEnv* 和 jclass（静态方法）
5. 如果是同步方法，锁定监视器
6. 检查 native 函数是否已链接（懒链接）
7. 将线程状态从 _thread_in_java 切换为 _thread_in_native
8. 调用 native 函数
9. 检查是否需要进入 Safepoint
10. 将线程状态恢复为 _thread_in_java
11. 如果是同步方法，解锁监视器
12. 解包返回值，重置 JNI 句柄块
13. 处理 JNI 异常
14. 移除栈帧
```

**Wrapper 帧的关键作用**：

- **状态转换**：线程在 `_thread_in_java` 和 `_thread_in_native` 之间切换，让 GC 知道线程当前在执行什么类型的代码
    
- **句柄管理**：将 `oop` 包装为 JNI 句柄，确保 GC 移动对象时本地代码持有的引用依然有效（见第7章）
    
- **LMF 注册**：在 LMF 链表中插入节点，为栈展开提供"跳过 native 帧"的桥梁
    
- **异常桥接**：native 方法返回的 JNI 异常被转换为 Java 异常，继续向上展开
    

> 💡 **洞见**：Wrapper 帧是"托管世界"与"非托管世界"之间的**外交使馆**——它既是 Java 调用 native 的出口，也是 native 返回 Java 的入口，更是栈展开时穿越混合栈的"桥梁"。ORP 论文中提到，VM 会为 native 方法生成**专门化的 JNI wrapper**——针对大多数只有少量引用参数的 native 方法，使用内联指令序列直接分配和初始化 JNI 句柄，而非调用通用函数。这种"特化 wrapper"可以将 JNI 调用密集型应用的性能提升几个百分点——这又是 HotSpot "常见路径走快路径"哲学在栈展开/本地接口边界的体现。

### 8.3.3 栈展开实现：跨语言异常处理的语义

这是全章最微妙的部分——**异常如何跨越 Java/native 边界传播？**

JNI Light 的形式化模型给出了精确的语义：

> A JNI exception pending in native code does not immediately disrupt the native code execution, and only after the native code finishes execution will the JVM mechanism for exceptions start to take over.

**跨语言异常传播的精确语义**：

```
情形 1：异常在 Java 帧中抛出，展开到 native 帧
  → native 帧不立即处理异常
  → 异常被记录为 native 帧的 "pending exception"
  → native 代码继续执行（程序员必须显式检查并处理）
  → native 方法返回 Java 后，JVM 接管异常，继续向上展开

情形 2：native 代码通过 JNI 显式抛出异常（如 env->Throw）
  → 异常被记录为 native 帧的 pending exception
  → native 代码继续执行（程序员必须显式检查并处理）
  → native 方法返回 Java 后，JVM 接管异常，继续向上展开

情形 3：异常在 Java 帧中抛出，展开到上一个 Java 帧
  → 按标准 Java 异常语义处理
  → 在当前帧的异常表中查找匹配的处理器
```

> ⚠ **工业陷阱**：JNI 异常模型是"错误易发"的——native 代码调用 JNI 函数后，必须显式检查 `env->ExceptionCheck()` 或 `env->ExceptionOccurred()`，否则异常会继续潜伏，直到 native 方法返回 Java 后才爆发。这就是为什么 JNI 编程的"四大常见 Bug"中，"忘记检查 JNI 异常"位列其中（其他三个是：跨线程传递 JNIEnv、局部引用泄漏、忘记 DeleteGlobalRef）。

### 8.3.4 本地帧与 C 帧：两套栈的协奏

这里需要厘清一个常见的混淆——**"本地帧"与"C 帧"的关系**。

在 JVM 规范中，"本地方法栈（Native Method Stack）"是线程私有的运行时数据区，与"Java 虚拟机栈"并列。但实际上：

- **物理上**：在大多数 HotSpot 实现中，Java 栈和 native 栈**是同一个栈**——都是 OS 线程的调用栈。Java 方法帧和 C 函数帧交替出现在同一个连续的栈空间中。
    
- **逻辑上**：Java 帧遵守 JVM 规范的结构（局部变量表、操作数栈、动态链接、返回地址）；C 帧遵守平台 ABI（参数传递寄存器、返回地址、帧指针等）。
    

**栈展开时如何处理 C 帧**：由于 C 帧是非自描述的，HotSpot 采用以下策略：

1. **识别帧类型**：通过 PC 地址范围判断——如果 PC 落在 JVM 内部代码区间，则是 Java 帧；如果落在 native 库区间，则是 C 帧
    
2. **跳过 C 帧**：通过 LMF 链表找到最近的 Java 帧
    
3. **恢复寄存器**：LMF 节点中保存了"调用 native 方法之前的寄存器状态"，包括被调用者保存的寄存器和指令指针
    
4. **继续展开 Java 帧**：从恢复的 Java 帧出发，继续用 `StackFrameStream` 向上遍历
    

ORP 论文中的图示清晰地展示了这一点：

```
栈顶 → [Wrapper][Native][Native][Wrapper][Native][Wrapper][Managed]...[栈底]
         ↑ LMF 指针指向最近的 Wrapper
```

当栈展开遇到第一个 Wrapper 时，通过 LMF 链表找到它，然后利用 Wrapper 中保存的信息"跳过"其下方的所有 native 帧，直接定位到上一个 Managed 帧。

> 💡 **洞见（本章核心判断）**：本地方法帧的栈展开揭示了一个深刻的工程哲学——**"非自描述的世界必须用自描述的世界来锚定"**。C 帧本身是"黑暗"的（JVM 无法读懂），但 JVM 通过在 Java→native 的边界处插入"自描述的 Wrapper 帧 + LMF 链表节点"，在混合栈中建立了"灯塔"——每次展开遇到 native 区域时，都能通过最近的灯塔"跳跃"回 Java 世界。这种设计哲学与"在不可信环境中建立可信锚点"的通用工程原则一脉相承——TLS 证书链中的根证书、分布式系统中的共识节点、甚至 CPU 的"信任根（Root of Trust）"，都是同一种思想的体现。

## 贯穿第8章的三条暗线（承上启下）

1. **栈展开是虚拟机"自我反思"的物理兑现**：异常传播、GC 根枚举、Safepoint 协作、调试诊断——所有需要"逆向遍历调用栈"的能力，都建立在栈展开之上。理解栈展开，就读懂了 JVM 为什么能在保持类型安全的同时，支持复杂的异常处理、并发 GC 和跨语言互操作。
    
2. **"自描述性"是 Java 帧与 C 帧的根本分野**：Java 帧携带完整的元数据（异常表、局部变量表、操作数栈、栈图），JVM 可以独立展开；C 帧遵循平台 ABI，JVM 无法直接读懂。HotSpot 通过 Wrapper 帧 + LMF 链表，在混合栈中建立"灯塔"，让栈展开能够跨越托管/非托管的鸿沟。
    
3. **栈展开能力在现代 HotSpot 中持续进化**：从早期的"STW 时一次性展开所有线程栈"，到 JDK 21 的 StackWatermark 实现"并发、渐进、无阻塞的栈处理"——栈展开机制本身也在追求"更低的停顿、更高的并发度"。这是 HotSpot "自适应、分阶段优化"哲学在栈处理领域的延续。

**本章最核心的一句话**：栈展开的本质，是虚拟机在"时间反方向"上遍历调用历史的能力——**Java 帧凭借自描述的元数据可以独立展开，native 帧借助 Wrapper 帧与 LMF 链表的"灯塔"实现混合栈穿越，HotSpot 的 StackFrameStream/RegisterMap 提供物理帧迭代，StackWatermark 实现并发渐进式栈处理**。理解栈展开，你就拿到了看懂 JVM 异常处理、GC 根枚举、Safepoint 协作、JNI 跨语言异常传播、以及现代并发 GC 栈处理机制的钥匙。

> 📌 **工业实践提示**：本章知识的直接应用包括——理解为什么异常传播成本是 O(栈深度)（异常表查找 + fillInStackTrace 遍历）、为什么 catch 块顺序影响性能、为什么 JNI 异常必须显式检查、为什么 native 方法中"忘记 DeleteLocalRef"会导致内存泄漏（GC 无法通过栈展开枚举 native 代码持有的局部引用）、以及为什么现代 GC 能够通过 StackWatermark 实现亚毫秒级停顿。这些都是从"VM 栈展开设计"反推"Java 异常/JNI/GC 最佳实践"的典型案例。
