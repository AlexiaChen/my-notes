
# 第3章 虚拟机中的数据结构 —— 读书笔记

如果说第2章回答了"虚拟机由哪些核心组件构成"，那么第3章要回答的是一个更底层、也更本质的问题：**当 Java 代码里写下 `new Person("Alice")`、`person.sayHello()` 这样一行行语句时，虚拟机内部到底用什么样的数据结构把它们表示出来？**​ 这一章是整个 JVM 实现从"概念"走向"物理表示"的基石——对象、类、方法，这三大语言核心概念，在虚拟机内部必须被映射成具体可操作的 C++ 结构体、可被分配的堆内存、可被快速查表的跳转数组。

结合原书英文章节（Xiao-Feng Li, _Data Structures in a Virtual Machine_, CRC Press, 2017）给出的框架，以及 HotSpot VM 的工业实现细节，我来梳理这一章的三条主干，并注入一些第一性原理层面的思考。

## 3.1 对象与类：虚拟机如何看待"类型"这件事

原书开篇就给出了一个根本性的分类——JVM 字节码指令集处理两种数据类型：**基本类型（primitive types）和引用类型（reference types）**。变量若为基本类型，则直接持有值（数字、布尔、返回地址）；若为引用类型，则持有一个指向对象的指针。每个对象都是某个引用类型（类或数组）的实例。

这里有一个精微但重要的定义：**原书在本书后续部分，将"class"一词用作统称，同时涵盖 classes、arrays 和 interfaces**——虽然 interface 自身不会有实例，但会有"类实现了某接口"的实例存在。

> 💡 **我的洞见**：这个分类看似平淡，实则揭示了虚拟机类型系统的第一性原理——**虚拟机不关心"面向对象"的哲学，只关心"值在哪儿、怎么寻址"**。基本类型的值就在变量自身里；引用类型的值在别处（堆上），变量只存一个"门牌号"。这种二元划分直接决定了后续所有的内存布局、参数传递、垃圾回收策略。C++ 程序员之所以能在栈上创建对象（`Person p("Alice")`），正是因为 C++ 不让步于"一切皆引用"的抽象；而 Java 选择让所有对象实例都活在堆上、变量只持有引用，这种取舍换来了 GC 的统一管理和指针语义的简化，代价是每个对象访问都多一次间接寻址。原书的这个开场，其实是整个 Java 语言设计哲学的虚拟机层宣言。

**工业实现对照（HotSpot）**：在 HotSpot 内部，这种"类型二元论"被进一步落实为 **oop-klass 模型**——这是理解整个 JVM 对象系统的钥匙。

- **oop（Ordinary Object Pointer）**：表示对象的实例数据，本质是堆上的一个指针，所有 oop 都继承自 `oopDesc`。
    
- **klass**：表示该对象所属类型的元数据，封装了类名、方法表（vtable）、字段偏移量、继承关系等。
    

HotSpot 的设计者刻意把"对象"拆成 oop 和 klass 两部分，原因很深刻：**他们不想让每个对象实例都内嵌一张虚函数表（vtable）**。所以 oop 部分不包含任何虚函数，仅仅持有实例数据；而 klass 部分持有 vtable，负责方法分派。这是一个用空间换时间的经典工程决策——vtable 在类级别只存一份，所有该类的实例共享。

## 3.2 对象表示：一个 Java 对象在内存里到底长什么样

这是全章最具"工业质感"的一节。原书给出的是抽象视角，而 HotSpot 给出了具体的物理布局——两者对照着看，你会发现虚拟机设计的精妙。

### HotSpot 的对象内存布局

在 64 位 JVM 中（开启压缩指针时），一个普通 Java 对象在堆上的物理布局如下：

|偏移|组成部分|大小|内容|
|---|---|---|---|
|0|**Mark Word**​|8 字节|哈希码、GC 分代年龄、锁状态、偏向线程 ID 等|
|8|**Klass Pointer**​|4 字节（压缩后）|指向元空间中的 `instanceKlass`|
|12|**实例数据**​|可变|对象的字段值|
|-|**对齐填充**​|0-7 字节|保证对象总大小为 8 字节整数倍|

如果是数组对象，在 Klass Pointer 之后还会插入一个 4 字节的**数组长度字段**。

Oracle 官方的 HotSpot 性能引擎架构白皮书明确记载：HotSpot 使用**两机器字（two machine-word）的对象头**（Classic VM 是三机器字），因为平均 Java 对象很小，这一改动为典型应用节省了约 **8% 的堆空间**。第一个字存身份哈希码和 GC 状态信息；第二个字是对对象所属类的引用；只有数组才有第三个字，用于存数组长度。

### Mark Word：一个被极致压缩的"状态寄存器"

Mark Word 是对象头中最精妙的部分。64 位下它只有 8 字节，却要塞进哈希码、GC 分代年龄、锁状态、偏向线程 ID 等多类信息。HotSpot 的解决方案是：**让 Mark Word 的结构随对象状态动态复用**——

- **无锁状态（001）**：31 位身份哈希码 + 4 位 GC 年龄 + 1 位偏向标志 + 2 位锁标志
    
- **偏向锁（101）**：54 位持有锁的线程指针 + 2 位 epoch + …… + 2 位锁标志
    
- **轻量级锁（000）**：62 位指向线程栈中锁记录（lock record）的指针
    
- **重量级锁（010）**：62 位指向操作系统 Monitor 对象的指针
    
- **GC 标记（011）**：被 G1/ZGC 等收集器用于标记阶段
    

> 💡 **我的洞见**：Mark Word 的动态复用设计，是一个"用时间换空间"的微缩杰作。它本质上是一个**状态机**——同一个 64 位存储区，根据最后 2-3 位的状态标志位，被解释为完全不同的含义。这种设计哲学和 CPU 的"条件码寄存器"、网络协议的"复用字段"如出一辙。它给我们的启示是：**在内存极度敏感的底层数据结构里，"一物多用"往往是必须的妥协**。每个 Java 对象都要承担这 8 字节的固定开销——如果你在堆里有 1000 万个 `Boolean` 对象，光对象头就吃掉 120 MB 内存，而真正的布尔值数据只有 1 字节/对象。这就是为什么在高性能、低延迟的 Java 系统里，原生类型集合（如 Eclipse Collections、FastUtil）能比 `HashMap<Long, Long>` 节省数倍内存——它们避免了"对象头爆炸"。这也是 Project Valhalla 正在推进"值类型（Value Types）"的根本动机：让 Java 也能有类似 C++ 栈上对象的紧凑表示。

### Klass Pointer 与 InstanceKlass

Klass Pointer 指向元空间（Metaspace）中的一个 `instanceKlass` 对象，后者包含了该类的几乎所有元数据：

- `_name`：类名（Symbol）
    
- `_super`：父类（Klass）
    
- `_constants`：常量池
    
- `_methods`：方法数组
    
- `_fields`：字段数组
    
- `_vtable`：虚方法表（用于虚分派）
    
- `_itable`：接口方法表（用于接口分派）
    
- `_init_state`：初始化状态
    

Java 层的 `java.lang.Class<?>` 对象，本质上就是这个 `instanceKlass` 的一个"镜像封装"，供反射 API 使用。

> 💡 **我的洞见**：oop-klass 的分离，其实揭示了虚拟机设计的又一个第一性原理——**"实例数据"和"类型元数据"的访问模式完全不同，应该物理分离**。实例数据（oop）被频繁读写、被 GC 频繁移动；而类型元数据（klass）在类加载后基本不变，GC 几乎不动它。把两者分开存储，GC 在搬运对象时只需要更新 oop 的 Klass Pointer（实际上开启了压缩指针后连这个都不用改），而不用复制整个类的元数据。更进一步，这种分离让"同一个类的所有实例共享一份类型信息"成为可能——vtable、字段偏移、方法字节码都只存一份，所有 `new Person()` 出来的对象共享之。这是面向对象语言在虚拟机层"类-实例"关系的物理兑现。

### 压缩指针（Compressed Oops）的工业魔法

现代 64 位 JVM 默认开启 `-XX:+UseCompressedOops`，Klass Pointer 从 8 字节压到 4 字节，引用类型字段也从 8 字节压到 4 字节。其原理是：假设堆基址对齐到 8 字节，那么 32 位的窄指针左移 3 位即可得到真实 64 位地址，这样 4 字节指针就能寻址约 **32 GB**​ 的堆空间。

> ⚠️ **工业启示**：压缩指针是一个"用 CPU 解码换内存带宽"的经典权衡。每个对象引用访问时，JVM 都要做一次"窄指针 → 宽指针"的解码（address = heap_base + (narrow_oop << 3)），这增加了少量 CPU 开销，但换来了：① 对象头从 16 字节降到 12 字节；② 引用字段从 8 字节降到 4 字节；③ 同等物理内存下能装下更多对象，显著提升 CPU 缓存命中率。在 32 GB 堆以内的服务，开启压缩指针几乎是免费的午餐。一旦堆超过 32 GB，就必须关闭压缩指针，对象头回到 16 字节——这就是为什么很多 JVM 性能调优指南建议"堆大小控制在 32 GB 以内"。

## 3.3 方法描述：虚拟机如何实现"多态"

这是全章最具"计算机科学美感"的一节。原书指出，JVM 的核心数据结构之一是 **virtual function table（虚函数表）**。方法描述要解决的问题是：**当调用 `animal.eat()` 时，虚拟机怎么知道该跳转到 `Animal.eat()` 还是 `Dog.eat()`？**

### 字节码层面的五种调用指令

JVM 提供了 5 种方法调用指令，分别对应不同的分派语义：

|指令|调用场景|分派方式|
|---|---|---|
|`invokestatic`|静态方法|静态分派（编译期确定）|
|`invokespecial`|构造器、私有方法、父类方法|静态分派|
|`invokevirtual`|实例方法（非 final）|**动态分派**​|
|`invokeinterface`|接口方法|**动态分派**​|
|`invokedynamic`|Lambda、动态语言|**动态分派**（Java 7 引入）|

### vtable：把"查继承链"优化成"查表"

如果没有 vtable，每次虚方法调用都要从对象的实际类开始，沿继承链向上逐个比较方法签名——这是 O(n) 的线性查找，对性能是灾难。

HotSpot 的解法是：**在类加载的链接阶段，为每个类静态构建一张 vtable**。vtable 的构建规则是——

- 按继承层次"摊平"所有可重写的方法
    
- 子类继承父类的 vtable，并覆盖被重写的方法槽位
    
- 同一方法签名在不同类的 vtable 中占据**相同的索引位置**
    

举例：

```
Animal 的 vtable:
  索引 0: Animal.eat()
  索引 1: Animal.sleep()

Dog 的 vtable（继承 Animal）:
  索引 0: Dog.eat()        ← 覆盖
  索引 1: Animal.sleep()   ← 继承
  索引 2: Dog.bark()       ← 新增

Cat 的 vtable（继承 Animal）:
  索引 0: Cat.eat()        ← 覆盖
  索引 1: Animal.sleep()   ← 继承
  索引 2: Cat.meow()       ← 新增
```

当执行 `animal.eat()` 时，字节码是 `invokevirtual Animal.eat`，JVM 在编译期已经算出 `eat()` 在 vtable 中的索引（比如 0）。运行时：

```
// 伪代码
Method* method = object->klass->vtable[method_index];  // method_index = 0
(*method)(object, args...);
```

无论 `animal` 实际指向 `Dog` 还是 `Cat`，`eat()` 在各自 vtable 中的索引都是 0，所以只需一次定长表偏移寻址，就完成了多态分派——**O(1) 时间复杂度**。

### itable：接口分派的额外维度

接口方法不走 vtable，因为接口可以多实现——一个类可以实现多个接口，无法在单一的 vtable 线性结构上整齐排列。HotSpot 的解法是 **itable（接口方法表）**：每个实现类为每个它实现的接口单独维护一张映射表。

调用 `Runnable r = () -> {}; r.run();` 时，JVM 先识别目标方法是接口方法，然后在 `r` 实际类型的 itable 中定位 `Runnable.run` 对应的实现入口。itable 的查找比 vtable 略复杂，因此 `invokeinterface` 的性能通常略低于 `invokevirtual`——这是 Java 设计"单继承 + 多接口"模型在虚拟机层的必然代价。

### 哪些方法不进 vtable？

- **static 方法**：编译期绑定，用 `invokestatic` 直接定位
    
- **private 方法**：隐含 final，用 `invokespecial` 绑定
    
- **final 实例方法**：不可重写，JIT 可能直接内联
    
- **构造器**：始终用 `invokespecial`
    

> 💡 **我的洞见**：vtable/itable 机制揭示了面向对象多态在虚拟机层的"物理代价"。很多人以为多态是"免费的"——其实不然。每个对象调用虚方法都要经过一次"取 klass → 取 vtable → 按索引取方法指针 → 跳转"的四步间接寻址。这就是为什么 JIT 编译器会疯狂内联热点方法——一旦内联，`invokevirtual` 可以被优化掉，直接变成线性代码，多态的间接开销归零。换句话说，**vtable 是"冷代码路径"的高效折中，而 JIT 内联是"热代码路径"的彻底消除**。这和第1章"解释器- JIT"的双层架构、第2章执行引擎的"自适应编译"哲学一脉相承：虚拟机处处都在做"冷路径用通用机制、热路径用特化优化"的权衡。理解 vtable，你就理解了 Java 性能优化的半壁江山——为什么 `final` 方法更快、为什么小方法容易被内联、为什么"接口注入"在某些极端性能场景下会成为瓶颈。

## 贯穿第3章的三条暗线

1. **"规范"与"实现"的分离在数据结构层的具体兑现**：原书给出的是抽象视角（对象、类、方法），HotSpot 给出的是具体 C++ 结构体（oopDesc、instanceKlass、vtable）。理解这种"双层映射"，是看懂任何 JVM 源码的钥匙。
    
2. **空间与时间的永恒权衡**：对象头为了省 8% 堆空间选择两机器字而非三机器字；压缩指针用解码开销换内存带宽；vtable 用类级别的"空间换时间"让运行时分派达到 O(1)。每一项决策都是工程权衡的结晶。
    
3. **"共享"是降低开销的根本手段**：所有实例共享一份 klass 元数据、共享一张 vtable；oop 只存各实例独有的数据。这是面向对象"类-实例"语义在物理层的兑现，也是 GC、JIT、反射等所有子系统能够高效协作的基础。
    

---

**本章最核心的一句话**：虚拟机中的数据结构，本质上是把"对象、类、方法"这三大语言概念，**映射成可分配、可寻址、可分派、可回收的物理表示**——oop 负责实例数据、klass 负责类型元数据、vtable/itable 负责多态分派。这三者的分离与协作，构成了整个 JVM 运行时系统的物理基石。理解了第3章，你再去看 class 文件格式、类加载、GC、JIT 的任何细节，都会发现它们不过是在操作这三大数据结构的变体。

> 📌 **工业实践提示**：在大规模低延迟 Java 应用中，本章知识的直接应用包括——用 JOL（Java Object Layout）工具分析对象内存占用、用原生类型集合替代包装类型集合避免"对象头爆炸"、控制堆大小在 32 GB 以内以保留压缩指针收益、在热路径上避免接口调用以助 JIT 内联。这些都是从"虚拟机数据结构"出发反推"Java 代码优化"的典型案例。
