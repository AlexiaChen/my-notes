
# 第6章 线程设计 —— 读书笔记

如果说前几章回答了"虚拟机如何加载类、如何表示对象、如何执行字节码、如何回收内存"，那么第6章要回答的是让这一切真正"并发"起来的根本问题——**当多个执行流同时跑在虚拟机里，VM 如何把"线程"这个抽象概念落到操作系统上？如何在并发访问共享数据时既不丢正确性、又不丢性能？如何让 GC 这种需要"冻结世界"的操作安全地插入到运行中的线程之间？**​ 线程设计是 JVM 从"能跑"走向"能并发跑"的关键一跃。李晓峰在这一章实际上在讲一个被工业界反复打磨的真理——**线程不是虚拟机的"附属品"，而是虚拟机运行时模型的"第一公民"**，它贯穿了执行引擎、内存管理、GC、同步机制的所有子系统。

结合 OpenJDK HotSpot 的官方运行时概述、JVM 规范第 8 章（Threads and Locks）以及工业演进（特别是 Project Loom 虚拟线程的引入），我来梳理这一章的脉络，并注入一些第一性原理层面的思考。

## 6.1 什么是线程：VM 视角下的"执行流"

从操作系统角度看，线程是"CPU 调度的最小单位"——它拥有独立的程序计数器、栈、寄存器状态，但与同进程内的其他线程共享堆、方法区、文件句柄等所有地址空间资源。

但从虚拟机角度看，线程的意义更为深刻——**它是"托管运行时"的执行载体**。在 JVM 中，每个线程不仅是 OS 调度单位，更是以下事物的载体：

- 一套**私有的运行时数据区**（PC 寄存器、Java 虚拟机栈、本地方法栈）
    
- 一份**线程局部的分配缓冲区（TLAB）**
    
- 一组**同步状态**（持有的锁、等待的条件）
    
- 一个**安全点状态机**（决定 GC 能否安全暂停该线程）
    

> 💡 **我的洞见**：线程在 VM 中扮演的角色，远比在原生程序中深刻。在 C/C++ 程序里，线程是 OS 给的"执行流"；在 JVM 里，线程是 VM 把"字节码执行、内存分配、锁获取、GC 协作"等所有运行时活动**绑定到一条执行流上**的载体。这就是为什么 HotSpot 要为每一个 Java 线程创建三个相互关联的 C++ 对象——`java.lang.Thread`（Java 层可见）、`JavaThread`（VM 内部管家）、`OSThread`（平台相关包装）——**线程不是"一个东西"，而是"一组协同的对象"**。理解这一点，你才能理解为什么线程的创建/销毁在 JVM 中是一个"重量级"事件，以及为什么 Project Loom 的虚拟线程要把这种"1:1 绑定"打破。

## 6.2 内核线程与用户线程：三种映射模型的哲学分野

这是全章的"架构基石"——VM 线程如何映射到 OS 线程，决定了整个虚拟机并发模型的性格。

|模型|映射关系|调度者|典型代表|
|---|---|---|---|
|**1:1（内核线程映射）**​|一个 VM 线程 ↔ 一个 OS 内核线程|操作系统内核|HotSpot（JDK 1.2+ 至今的默认）|
|**N:1（用户线程）**​|N 个 VM 线程 ↔ 1 个 OS 内核线程|JVM 自己（用户态调度器）|早期 JVM 的"Green Threads"、 goroutine 之前的某些实现|
|**M:N（混合模型）**​|M 个 VM 线程 ↔ N 个 OS 内核线程|JVM + OS 协作|Go 的 GMP、Java 19+ 的虚拟线程|

**1:1 模型的本质**：HotSpot 采用 **1:1 内核线程映射**——每个 `java.lang.Thread` 在 `start()` 时，JVM 通过 `pthread_create`（Linux）创建一个真实的 OS 内核线程（LWP，轻量级进程），Java 线程的生命周期与这个 LWP 完全绑定。

**为什么 HotSpot 选择 1:1**：

- **利用多核并行**：每个 Java 线程可被 OS 调度到不同 CPU 核心，真正实现并行
    
- **阻塞处理简单**：一个线程因 I/O 或锁阻塞时，OS 自动挂起其对应的 LWP，不影响其他线程
    
- **实现简单**：JVM 不需要自己写线程调度器（时间片分配、优先级抢占），这些全部委托给 OS 内核
    

**1:1 的代价**：

- **线程创建/切换开销大**：每次 `pthread_create` 都需要内核参与，默认 1MB 栈空间，上下文切换需要用户态↔内核态转换
    
- **线程数量受限**：OS 能创建的 LWP 数量有限，数万线程就会导致严重的上下文切换开销
    
- **优先级映射复杂**：Java 线程优先级与 OS 线程优先级的映射因平台而异，无法保证语义一致性
    

> ⚠️ **洞见**：1:1 模型是"性能与复杂度的最佳折中"——它把调度权完全交给 OS，换取了实现简单性和多核利用率，代价是"线程很重"。这个代价在 2005 年（HotSpot 确立 1:1 模型的时代）是可接受的——那时服务器核心数有限、Java 主要用于后端长驻服务，线程数通常在几百到几千量级。但到了云计算和微服务时代，一个服务可能需要处理数十万并发连接——1:1 模型的"线程太重"问题成了 Java 的阿喀琉斯之踵。这正是 **Project Loom 虚拟线程（Java 21 正式引入）**​ 要解决的问题：它回归 M:N 混合模型，成千上万个"虚拟线程"映射到少量 OS 线程上，由 JVM 用户态调度器管理——本质上是把"Green Threads 的思想"用现代方式重新实现，同时保留 1:1 模型与本地代码互操作的兼容性。

## 6.3 VM 线程到 OS 线程的映射：HotSpot 的三层结构

这一节是全章最具"工业质感"的部分——HotSpot 如何用三个 C++ 对象把一个 Java 线程"落地"到 OS 线程。

```
┌─────────────────────────────────────────────────────────┐
│  Java 层                                                │
│  java.lang.Thread  (开发者可见的线程对象)                 │
│       │ eetop 字段持有 JavaThread 的地址                  │
│       ▼                                                 │
│  JVM 层 (C++)                                            │
│  JavaThread  (VM 内部管家)                               │
│       ├── 维护线程状态机                                  │
│       ├── 持有 HandleMark、栈锚点                        │
│       ├── 持有 TLAB（Thread-Local Allocation Buffer）     │
│       ├── 持有 Safepoint 状态                            │
│       └── 持有 OSThread 引用                             │
│       ▼                                                 │
│  OS 层 (C++)                                             │
│  OSThread  (平台相关包装器)                              │
│       └── 持有 OS 的线程句柄（如 Linux 的 pthread_t）      │
│       ▼                                                 │
│  OS 内核                                                 │
│  LWP (Light-weight Process)  ← pthread_create 创建       │
└─────────────────────────────────────────────────────────┘
```

**线程创建的调用链**（以 Linux 为例）：

1. Java 代码调用 `Thread.start()` → 触发 native 方法 `start0()`
    
2. JVM 入口 `JVM_StartThread` 创建 C++ 层的 `JavaThread` 对象
    
3. `JavaThread` 构造函数调用 `os::create_thread()`，平台相关代码最终调用 `pthread_create()`
    
4. OS 创建 LWP，分配栈空间（受 `-Xss` 控制，默认 1MB）
    
5. `JavaThread` 初始化线程局部存储、TLAB、同步对象
    
6. 新线程启动，执行 `Thread.run()` 方法
    

**线程终止**：`run()` 返回后，JVM 调用 `Thread.exit()`，依次释放 TLAB、移除 JavaThread、销毁 OSThread、LWP 由 OS 回收。

> 💡 **洞见**：这个三层结构是"关注点分离"的典范——`java.lang.Thread` 负责 Java 层语义、`JavaThread` 负责 VM 内部状态、`OSThread` 负责平台差异。这种分层让 HotSpot 能在不同 OS 上复用绝大部分线程管理逻辑，只需在 `OSThread` 层做平台适配。**更重要的是，这个结构揭示了虚拟机线程设计的本质哲学——"线程不是 OS 线程的简单包装，而是一组跨层的、协同的状态集合"**。任何需要在"线程粒度"上做的优化（如 TLAB、Safepoint、锁状态），都必须在这三层结构上协同工作。

除了用户线程，HotSpot 还创建了一系列**内部 VM 线程**，它们共同构成了 JVM 的"后台心脏"：

- **VMThread**：执行所有需要在 Safepoint 进行的 VM 操作（如 STW GC、偏向锁撤销、线程栈 dump）
    
- **GC 线程**：不同 GC 算法的回收线程（如 Parallel GC 的多线程、G1 的并发标记线程）
    
- **CompilerThread**：JIT 编译线程（C1/C2 各有独立线程）
    
- **WatcherThread**：模拟定时器中断，用于周期性操作
    
- **Signal Dispatcher**：处理 OS 信号
    

## 6.4 同步构件：并发正确性的基石

当多个线程共享堆内存时，"并发正确性"成为头等大事。JVM 提供的同步构件可以分为两大类：

**1. 互斥构件（Mutual Exclusion）**：保证同一时刻只有一个线程能进入临界区

- **Monitor（管程）**：`synchronized` 的底层实现，提供互斥 + 条件变量
    
- **原子操作**：CAS（Compare-And-Swap）等硬件原子指令的 JVM 封装
    

**2. 协调构件（Coordination）**：线程间的等待/通知机制

- **wait()/notify()/notifyAll()**：基于 Monitor 的条件变量
    
- **java.util.concurrent**​ 包：更高层的锁、信号量、屏障等
    

> 💡 **洞见**：同步构件的演进史，是"从重量级到轻量级"的演进史。JVM 规范要求每个对象都有一个 Monitor，但 HotSpot 的实现极其精巧——**锁状态被编码在对象头的 Mark Word 中**，根据竞争情况动态升级：无锁 → 偏向锁 → 轻量级锁（栈锁）→ 重量级锁（Inflated Monitor）。这种"锁升级"机制意味着——**在大多数无竞争场景下，synchronized 的性能开销接近于零**（只需在 Mark Word 中设置一位偏向锁标志）；只有在真正有竞争时，才"膨胀"为重量级 Monitor，涉及 OS 层面的互斥量（mutex）和线程阻塞。这是"自适应"思想在线程同步领域的体现，与第4章 JIT 的"自适应编译"、第5章 GC 的"分代自适应"一脉相承。

## 6.5 Monitor：JVM 同步的"万能构件"

Monitor 是 JVM 同步模型的核心——它把"互斥"和"条件变量"两个看似独立的概念，统一在一个数据结构里。这是本章最精彩的环节。

### 6.5.1 互斥：Monitor 的"独占性"

Monitor 的互斥保证基于一个简单的规则——**任一时刻，只有一个线程能成为 Monitor 的 Owner**。这个规则通过 `monitorenter` 和 `monitorexit` 字节码指令强制实施。

根据 JVM 规范：执行 `monitorenter` 时，如果 Monitor 未被任何线程持有，当前线程成为 Owner，将 Monitor 的 entry count 设为 1；如果当前线程已经是 Owner，则 entry count 递增（**可重入性**）；如果 Monitor 被其他线程持有，当前线程阻塞直到 Monitor 被释放。

### 6.5.2 条件变量：Monitor 的"协调性"

仅有互斥是不够的。经典的"生产者-消费者"问题中，消费者发现缓冲区为空时，它需要"释放锁并等待"，直到生产者填入数据后"唤醒"它。这就是条件变量的作用——**wait()/notify()/notifyAll()**。

Monitor 内部维护两个队列：

- **Entry Set（进入队列）**：等待获取锁的线程
    
- **Wait Set（等待队列）**：已获取锁但调用了 wait() 释放锁并等待的线程
    

### 6.5.3 monitorenter：进入 Monitor 的完整流程

`synchronized` 块在字节码层面被编译为 `monitorenter` 和 `monitorexit` 对。编译器甚至会为异常路径生成额外的 `monitorexit`，确保锁在任何退出路径（包括异常）都能释放。

**HotSpot 中 monitorenter 的执行路径**（快路径 vs 慢路径）：

1. **快路径（Fast Path）**：在无竞争情况下，JIT 生成的代码直接在对象头的 Mark Word 中设置偏向锁或轻量级锁，无需进入 VM 运行时——整个过程在用户态完成，极快
    
2. **慢路径（Slow Path）**：当检测到竞争（如 Mark Word 已被其他线程设置），进入 C++ 实现的慢路径，可能触发锁膨胀（Inflated），创建 ObjectMonitor 对象，将线程加入 Entry Set 并阻塞
    

**ObjectMonitor 的核心结构**：

```
ObjectMonitor {
    owner:        当前持有锁的线程
    recursions:   重入次数
    entryList:    阻塞等待锁的线程队列
    waitSet:      调用 wait() 后等待的线程队列
}
```

### 6.5.4 monitorexit：退出 Monitor 的语义

执行 `monitorexit` 时：

1. 当前线程必须是 Monitor 的 Owner，否则抛 `IllegalMonitorStateException`
    
2. entry count 递减
    
3. 若 entry count 归零，释放 Monitor，从 Entry Set 中唤醒一个线程（具体唤醒策略取决于 JVM 实现，通常是非公平的）
    

> ⚠️ **工业细节**：HotSpot 的 Monitor 唤醒策略是**非公平**的——释放锁时不保证等待时间最长的线程先获得锁。这是为了性能：公平竞争需要额外的队列管理开销。在大多数服务端场景下，非公平锁的吞吐量显著高于公平锁，代价是可能出现"线程饥饿"。如果业务需要公平性，应使用 `java.util.concurrent.locks.ReentrantLock` 的公平模式。

### 6.5.5 Object.wait()：释放锁并进入等待

`wait()` 的精确语义（JVM 规范）：

1. 当前线程必须是 Monitor 的 Owner，否则抛 `IllegalMonitorStateException`
    
2. 将当前线程加入 Wait Set
    
3. **释放 Monitor**（entry count 归零，owner 置空）
    
4. 线程阻塞，直到被 `notify()`/`notifyAll()` 唤醒或超时
    
5. 被唤醒后，线程从 Wait Set 移到 Entry Set，**重新竞争 Monitor**
    
6. 竞争成功后，线程从 `wait()` 返回——此时它再次成为 Owner
    

### 6.5.6 Object.notify()/notifyAll()：唤醒等待线程

- **notify()**：从 Wait Set 中随机选择一个线程，将其移到 Entry Set
    
- **notifyAll()**：将 Wait Set 中所有线程移到 Entry Set
    

> 💡 **洞见（本章核心判断之一）**：Monitor 统一了"互斥"与"条件变量"，这是一个被 Dijkstra 在 1970 年代提出的"管程（Monitor）"概念的 JVM 兑现。它的精妙之处在于——**把"锁"和"条件"绑定在同一个对象上**，避免了"锁和条件变量分离"带来的复杂性（如 POSIX 的 mutex + condvar 需要手动配对）。但这也带来了一个常见陷阱：程序员常常忘记 `wait()` 必须在循环中调用（`while (condition) wait()` 而非 `if (condition) wait()`），因为：
> 
> - `notify()` 只唤醒一个线程，可能有多个线程等待不同条件
>     
> - 线程被唤醒后到重新获取锁之间，条件可能被其他线程再次改变
>     
> - "虚假唤醒（spurious wakeup）"在某些平台上可能发生
>     
> 
> 这就是为什么 Joshua Bloch 在《Effective Java》中强调——**"永远在循环中使用 wait()"**。这是 Monitor 模型在实践中最重要的"防坑指南"。

## 6.6 原子：非阻塞同步的基石

Monitor 是"阻塞式同步"——获取不到锁的线程会被挂起。但在某些场景下，阻塞的代价太高（线程上下文切换开销）。这时就需要"非阻塞式同步"——**原子操作**。

JVM 通过 `sun.misc.Unsafe`（JDK 9+ 为 `java.lang.invoke.MethodHandles.Lookup`）暴露了硬件原子指令：

- **CAS（Compare-And-Swap）**：比较并交换，是现代并发算法的基石
    
- **Atomic 类族**：`AtomicInteger`、`AtomicLong`、`AtomicReference` 等
    
- **VarHandle**（JDK 9+）：类型安全、性能更好的原子操作入口
    

**CAS 的语义**：

```
CAS(addr, expected, new):
    if (*addr == expected):
        *addr = new
        return true
    else:
        return false
```

CAS 是**硬件级别的原子指令**（x86 的 `CMPXCHG`、ARM 的 `LDREX/STREX`），它允许线程在不阻塞的情况下尝试更新共享变量——如果更新成功，皆大欢喜；如果失败（说明其他线程已经修改了变量），则重试或采取其他策略。

> 💡 **洞见**：CAS 是现代并发编程的"第一性原理"——**用"乐观重试"代替"悲观加锁"**。基于 CAS 可以构建出各种无锁（Lock-Free）和非阻塞（Non-Blocking）数据结构：原子变量、无锁队列、无锁栈、甚至无锁 HashMap（如 `ConcurrentHashMap` 的分段 CAS）。但 CAS 不是银弹——它有"ABA 问题"（变量从 A 改成 B 又改回 A，CAS 误认为未修改），需要用 `AtomicStampedReference` 解决；在高竞争场景下，CAS 的"自旋重试"会导致 CPU 空转，此时反而不如 Monitor 的"直接阻塞"。

## 6.7 Monitor 与原子：阻塞与非阻塞的辩证

这一节是全章的"哲学升华"——Monitor（阻塞）和原子（非阻塞）不是替代关系，而是互补关系。

### 6.7.1 阻塞与非阻塞

- **阻塞（Blocking）**：获取不到资源时，线程被挂起，让出 CPU，直到资源可用
    
    - 优点：高竞争下 CPU 利用率高，无空转
        
    - 缺点：上下文切换开销大，延迟不可控
        
    
- **非阻塞（Non-Blocking）**：获取不到资源时，线程不挂起，而是重试或执行备选路径
    
    - 优点：无上下文切换，延迟低
        
    - 缺点：高竞争下 CPU 空转，可能导致饥饿
        
    

### 6.7.2 中央控制点

Monitor 的本质是一个"中央控制点"——所有线程必须在这里排队。这种集中化设计的优势是**语义清晰、易于推理**；劣势是**成为性能瓶颈**。

原子操作则是"去中心化"的——每个线程直接操作共享变量，通过 CAS 协调。优势是**无中心瓶颈**；劣势是**高竞争下冲突频繁**。

### 6.7.3 锁与非锁

HotSpot 的锁升级路径完美诠释了"锁与非锁"的融合：

1. **无锁**：Mark Word 中无锁标志
    
2. **偏向锁**：将 Mark Word 指向当前线程，相当于"非锁的锁"——只有当前线程访问时，零开销
    
3. **轻量级锁**：在栈帧中创建锁记录，通过 CAS 尝试获取，失败则膨胀
    
4. **重量级锁**：真正的 Monitor，涉及 OS 互斥量
    

> 💡 **洞见**：HotSpot 的锁升级机制揭示了一个深刻的工程哲学——**"能用非锁解决的，绝不用锁；能用轻锁解决的，绝不用重锁"**。这是"自适应"思想在线程同步上的终极体现。在真实应用中，绝大多数 synchronized 块都是无竞争的（线程局部性原理），所以偏向锁能让这些场景接近零开销；只有当真正出现竞争时，才逐级升级到重量级锁。这种"渐进式降级性能"的策略，让 `synchronized` 在 JDK 6 之后的性能有了质的飞跃，不再是企业应用的性能瓶颈。

### 6.7.4 非阻塞之上的阻塞

这是一个反直觉但重要的观察——**即使是"非阻塞"的原子操作，在 JVM 底层也可能构建在"阻塞"机制之上**。例如，当一个线程自旋 CAS 失败时，它可能最终选择"park"（如 `Unsafe.park()`），而这背后是 OS 的互斥量和条件变量——本质上是 Monitor 的底层实现。

反过来，Monitor 的实现也利用了原子操作——锁膨胀时创建 ObjectMonitor 需要 CAS 来避免多线程竞争。

> 💡 **洞见**：阻塞与非阻塞并非二元对立，而是**一个连续的光谱**。在最底层，原子操作提供了"非阻塞的原语"；在中间层，Monitor 利用原子操作构建了"阻塞的语义"；在高层，并发框架（如 `java.util.concurrent`）又利用 Monitor 和原子操作构建了更复杂的非阻塞算法（如 `ConcurrentLinkedQueue`）。理解这种"层级构建"关系，是看懂 Java 并发包设计的关键。

## 6.8 回收器与修改器：GC 与 Mutator 的协作

这一节引入了一个重要视角——**在 GC 发生时，应用程序线程（Mutator，即"修改器"，因为它们修改对象图）必须与回收器（Collector）协作**。

如果 GC 在遍历对象图时，Mutator 同时修改对象图（如创建一个新对象、修改一个引用字段），那么 GC 可能：

- 漏标一个本应存活的对象（导致错误回收，程序崩溃）
    
- 错标一个本应死亡的对象（保守但安全）
    

为解决这个"并发修改"问题，JVM 采用了两种策略：

1. **STW（Stop-The-World）**：GC 开始时，暂停所有 Mutator 线程，等 GC 完成关键阶段后再恢复
    
2. **并发 GC + 写屏障（Write Barrier）**：GC 与 Mutator 并发运行，但通过写屏障记录 Mutator 对对象图的修改，确保 GC 的正确性
    

> ⚠️ **洞见**：STW 是"简单但粗暴"的方案，并发 GC + 写屏障是"复杂但平滑"的方案。现代 GC（CMS、G1、ZGC、Shenandoah）都在极力减少 STW 的时间和频率，但最终仍需要某种形式的"全局暂停"来完成关键操作（如 G1 的"Root Region Scan"、ZGC 的"Pause Mark Start"）。这就是为什么 Safepoint 机制如此重要——它是 STW 的"协作式实现"。

## 6.9 线程局部数据：TLAB 与 ThreadLocal

线程局部数据是"避免共享"的终极手段——如果每个线程都有自己的数据副本，就根本不需要同步。

### ThreadLocal

`java.lang.ThreadLocal<T>` 提供线程局部变量——每个线程都有自己独立的变量副本，互不干扰。实现原理：每个 `Thread` 对象内部维护一个 `ThreadLocalMap`，key 是 `ThreadLocal` 对象，value 是线程局部值。

### TLAB（Thread-Local Allocation Buffer）

这是 HotSpot 中更重要的线程局部数据——**每个线程在 Eden 区拥有一小块私有分配缓冲区**。

**TLAB 的工作机制**：

- 线程内 `new` 对象时，优先在自家 TLAB 内用"撞针分配"（bump-the-pointer）
    
- TLAB 用尽时，线程通过 CAS 从 Eden 区"批发"一块新的 TLAB
    
- 多线程并发分配时，仅 TLAB 申请/refill 时需要 CAS 竞争，热点路径完全无锁
    

> 💡 **洞见**：TLAB 是"用空间换时间"的经典案例——它为每个线程预留了一小块堆空间（通常几十 KB 到几 MB），避免了多线程分配对象时的 CAS 竞争。代价是 TLAB 之间可能有碎片（未使用的 TLAB 空间），但相比无锁分配带来的巨大性能提升，这点浪费是值得的。**TLAB 揭示了一个通用工程原则：在高度并发的场景下，"让每个执行单元拥有私有资源"往往比"共享资源 + 同步"更高效**。这也是为什么 CPU 有 L1/L2 缓存、Why 数据库有 Buffer Pool per connection、Why Netty 有 ThreadLocal 的 EventLoop——"线程私有化"是高并发系统的通用优化范式。

## 6.10 GC 的线程暂停支持：Safepoint 与 Safe Region

这是全章的"技术高潮"——当 GC 需要"冻结世界"时，如何让运行中的线程安全地停下来？

### 6.10.1 GC 安全点（Safepoint）

**什么是 Safepoint**：代码中某些特定的位置，在这些位置上，线程的栈状态和寄存器状态是"可枚举"的——即 GC 能准确知道此时栈上哪些槽位持有对象引用。

**Safepoint 的位置选择**：

- 方法调用点
    
- 循环回边（back-edge）
    
- 异常抛出点
    
- 创建对象（需要在堆上分配内存的点）
    

HotSpot 采用**主动式中断（Voluntary Suspension）**：GC 需要暂停线程时，设置一个全局标志，各线程在执行到 Safepoint 时主动轮询这个标志，发现标志置位就自行挂起。

**高效的轮询机制**：HotSpot 使用**内存保护陷阱**实现极高效的轮询——把某个特定的内存页通过 `mprotect` 设置为不可读。JIT 编译的代码在 Safepoint 处插入一条 `test [safepoint_page], 0` 指令，当 GC 需要暂停线程时，将该内存页设为不可读，线程执行到这条指令时触发 `SIGSEGV` 信号，由 JVM 的信号处理器捕获并挂起线程。这样，轮询操作精简到只有一条汇编指令的开销。

**不同状态下的线程如何到达 Safepoint**：

- **运行解释器代码**：切换字节码分派表，强制在字节码之间检查 Safepoint
    
- **运行 JIT 编译代码**：通过内存保护陷阱（page trap）触发
    
- **运行本地（native）代码**：线程在从 native 返回 VM 时检查 Safepoint 标志
    
- **已阻塞（_thread_blocked）**：立即被视为已停止，因为阻塞状态的线程堆栈引用不会改变
    

### 6.10.2 GC 安全区域（Safe Region）

Safepoint 机制有一个盲区——**当线程处于 Sleep 或 Blocked 状态时，它无法"走到" Safepoint**。这时就需要 Safe Region。

**Safe Region 的定义**：一段代码片段中，引用关系不会发生变化。在这个区域内的任意地方开始 GC 都是安全的。可以把 Safe Region 看作"被拉伸了的安全点"。

**Safe Region 的工作流程**：

1. 线程进入 Safe Region 时，标识自己"已进入 Safe Region"
    
2. 在此期间如果 JVM 发起 GC，不用管这个线程（因为它在 Safe Region 内，引用关系不会变）
    
3. 线程准备离开 Safe Region 时，检查 GC 是否已完成
    
4. 如果 GC 已完成，线程正常离开；如果 GC 仍在进行，线程停留在 Safe Region 等待
    

> 💡 **洞见**：Safe Region 的本质是"反向 Safepoint"——Safepoint 是"线程主动跑到安全点"，Safe Region 是"线程声明自己所在区域是安全的"。这两个机制互补，覆盖了线程所有可能的状态。理解这一点，你就能理解为什么某些"长耗时且无 Safepoint 的紧密循环"会导致 GC 停顿尖刺——因为线程被困在"非 Safepoint 且非 Safe Region"的状态，GC 必须等它，造成不可预测的延迟。这也是为什么 JIT 会在所有循环回边插入 Safepoint 检查——确保任何循环都能在"合理时间"内响应 GC 请求。

### 6.10.3 基于锁的安全点

HotSpot 还有一种特殊的安全点实现——**基于锁的安全点**。当线程持有某个特定锁时，GC 可以通过这个锁来协调线程的暂停。这种机制主要用于一些特殊的 VM 操作，如"偏向锁撤销"——当 GC 需要撤销所有对象的偏向锁时，它需要确保相关线程在安全的状态下。

### 6.10.4 回收中的线程交互

当 GC 触发 STW 时，VMThread 执行以下流程：

```
1. VMThread 设置全局 Safepoint 标志
2. 各 Java 线程在下一个 Safepoint 处自行挂起
3. VMThread 等待所有 Java 线程确认已停止
4. 执行 GC 操作（标记、回收、压缩等）
5. 清除 Safepoint 标志
6. 各 Java 线程从 Safepoint 恢复执行
```

> ⚠️ **工业现实**：Safepoint 本身可能成为性能瓶颈。在极端情况下，如果某个线程长时间执行一个不包含 Safepoint 的紧密循环（如大数组的 `System.arraycopy`、长时间的 JNI 调用），它会"错过"Safepoint 检查，导致 GC 等待，产生数百毫秒甚至数秒的"GC 停顿尖刺"。这在低延迟系统（如金融交易、实时通信）中是致命的。ZGC 和 Shenandoah 等现代 GC 通过"并发压缩 + 读屏障"将 STW 停顿压到亚毫秒级，但 Safepoint 的"协作式"本质决定了——**任何需要所有线程到达一致状态的 VM 操作，都可能被某个"不听话"的线程拖慢**。这也是为什么 `-XX:+UseCountedLoopSafepoints` 等调优参数存在，以及为什么编写"GC 友好"的代码（避免在循环中做长时间无 Safepoint 的操作）在低延迟场景下至关重要。

## 贯穿第6章的三条暗线（承上启下）

1. **"线程是 VM 运行时模型的载体"而非"OS 线程的简单包装"**：HotSpot 用 `java.lang.Thread` + `JavaThread` + `OSThread` 三层结构，把字节码执行、内存分配（TLAB）、同步（Monitor）、GC 协作（Safepoint）全部绑定到线程上。理解这一点，才能理解为什么线程在 JVM 中是"重量级"的——因为它承载了太多运行时职责。
    
2. **"自适应"思想贯穿线程同步**：锁升级（无锁→偏向→轻量级→重量级）、Safepoint 的主动轮询、TLAB 的私有化分配——这些都是"根据运行时情况动态选择最优策略"的体现。这与第4章 JIT 的自适应编译、第5章 GC 的分代自适应一脉相承，是 HotSpot 设计的统一哲学。
    
3. **"阻塞与非阻塞"是连续光谱而非二元对立**：Monitor 提供阻塞语义但底层用原子操作构建；原子操作是非阻塞原语但高竞争下可能退化为阻塞。理解这种层级构建关系，是掌握 Java 并发编程（从 `synchronized` 到 `java.util.concurrent` 到虚拟线程）的钥匙。
    

---

**本章最核心的一句话**：线程设计在 JVM 中绝非"给 OS 线程加个壳"那么简单，而是一套**把"执行流、内存分配、同步互斥、GC 协作"统一绑定到线程载体上的综合工程**——1:1 映射让 JVM 复用 OS 调度能力但付出"线程重"的代价（催生虚拟线程）；Monitor 统一了互斥与条件变量但需要通过锁升级实现"自适应"性能；原子操作提供了非阻塞原语但高竞争下可能退化；Safepoint/Safe Region 让 GC 能安全地"冻结世界"但依赖线程的协作式配合。**理解这套"线程即运行时载体"的模型，你就拿到了看懂 HotSpot 并发架构、GC 协作、以及 Project Loom 虚拟线程设计哲学的钥匙**。

> 📌 **工业实践提示**：本章知识的直接应用包括——理解为什么"线程数不是越多越好"（1:1 映射 + 上下文切换开销）、为什么 `synchronized` 在现代 JVM 中性能已大幅提升（锁升级）、为什么高并发分配用 TLAB 无锁、为什么低延迟系统要警惕"Safepoint 停顿尖刺"、以及为什么 Java 21+ 的虚拟线程能颠覆传统的"线程池"模型。这些都是从"VM 线程设计"反推"Java 并发编程最佳实践"的典型案例。
