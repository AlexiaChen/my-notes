
# 第11章 异常抛出 —— 读书笔记

如果说前几章回答了"虚拟机如何执行、如何回收、如何调度线程、如何通过运行时辅助外包复杂操作"，那么第11章要回答的是一个让"控制流"在虚拟机中能够"非正常跳转"的根本问题——**当 `athrow` 指令执行、当数组越界、当空指针解引用、当 `Thread.stop()` 被调用时，虚拟机如何从"抛出异常的那一刻"出发，精确地保存上下文、跨语言边界传播、构建栈轨迹、查找异常处理器、完成控制转移？**​ 这就是"异常抛出（Exception Throwing）"。李晓峰在这一章实际上在讲一个被工业界反复打磨的真理——**异常不是简单的"goto"，而是虚拟机在"时间维度和空间维度"上的一次精密协同：它既要保存抛出点的完整上下文，又要穿越 Java/native 混合栈，还要在控制转移时精确恢复寄存器与栈状态**。理解异常抛出，你才能理解为什么 JVM 的异常处理既精确（Precise Exception）又高效，以及为什么 JNI 的异常模型是"延迟接管"而非"立即中断"。

结合 JVM 规范（Java SE 21）对异常处理的权威定义、OpenJDK 中 `java.lang.Throwable` 的 `backtrace` 字段设计、HotSpot 中 `exceptions.hpp` 的线程级 pending exception 机制，以及工业界对"同步/异步异常"的语义界定，我来梳理这一章的脉络，并注入一些第一性原理层面的思考。

## 11.1 保存异常抛出上下文：异常面前的"时空定格"

异常抛出的第一要务是**保存抛出点的完整上下文**——因为异常处理代码可能在上百层调用栈之上，VM 必须能够"定格"异常发生那一刻的所有状态。

### 11.1.1 VM 保存的上下文

JVM 规范明确规定：异常由 `Throwable` 或其子类的实例表示，**抛出异常会导致控制从抛出点立即非局部转移**。这种"非局部转移"要求 VM 在抛出瞬间保存：

- **异常对象引用**：即 `athrow` 指令从操作数栈顶弹出的 `Throwable` 实例
    
- **PC 位置**：异常发生的精确字节码偏移量（用于异常表匹配）
    
- **栈帧链**：当前线程的完整调用栈（用于栈轨迹构建和控制转移）
    
- **线程状态**：`_thread_in_java` 或 `_thread_in_native`（决定是否进入 Safepoint 协议）
    

HotSpot 的工业实现更精妙——它**不使用 C++ 异常机制**（为了避免编译器依赖和不可预测的性能），而是把异常保存在**线程对象**中：

> "Scheme: Exceptions are stored with the thread. There is never more than one pending exception per thread. All functions that can throw an exception carry a THREAD argument... Throwing an exception means setting a pending exception in the thread."

每个线程有且仅有一个 `_pending_exception` 字段（oop 类型），所有可能引发异常的函数都通过 `TRAPS` 宏携带 `THREAD` 参数，函数返回时通过 `CHECK` 宏检查是否有 pending exception。这是 HotSpot 异常传播的"血管"——它让 C++ 层面的 VM 代码能够像 Java 一样"抛出异常"，但底层是线程级状态字段而非 C++ 异常栈展开。

### 11.1.2 Linux 中 OS 保存的上下文

当异常涉及 Safepoint 或 native 方法边界时，Linux 下 HotSpot 利用 **SIGSEGV 信号机制**保存上下文：

- Safepoint 轮询页被 `mprotect` 设为不可读
    
- 线程执行到轮询指令时触发 SIGSEGV
    
- JVM 的信号处理器捕获信号，此时 OS 已将线程的完整寄存器状态（ucontext_t）保存到信号栈帧中
    
- HotSpot 从这个 ucontext 中提取 PC、SP、FP 和各寄存器值，作为异常上下文的一部分
    

### 11.1.3 Windows 中 OS 保存的上下文

Windows 下使用 **结构化异常处理（SEH）**​ 和 `RaiseException` 机制，原理类似但 API 不同。HotSpot 在 Windows 上通过 `__try/__except` 捕获异常，从 `CONTEXT` 结构中提取寄存器状态。

### 11.1.4 同步与异步异常：异常家族的"双胞胎"

这是全章最重要的概念分野——JVM 规范明确区分两类异常：

**同步异常（Synchronous Exceptions）**：

- 由当前线程的动作**直接引发**
    
- 只在执行某条特定指令**之后**同步抛出
    
- 三类来源：
    
    1. `athrow` 指令执行
        
    2. JVM 同步检测到的异常执行条件（如数组越界、类型转换失败、除零）
        
    3. 加载或链接阶段的错误
        
    

**异步异常（Asynchronous Exceptions）**：

- 可能在程序执行的**任何时刻**发生
    
- 两类来源：
    
    1. 其他线程调用 `Thread.stop()` 或 `ThreadGroup.stop()`
        
    2. JVM 内部错误（如 `OutOfMemoryError`、栈溢出）
        
    

> 💡 **洞见（本章核心判断之一）**：同步与异步异常的区分，揭示了 JVM 异常模型的"精确性承诺（Precise Exception）"——JVM 规范明确规定："Exceptions thrown by the Java Virtual Machine are precise"——当控制转移发生时，异常抛出点之前的所有指令效果必须对用户程序可见，而异常抛出点之后的指令效果必须不可见。这意味着：**即使 JIT 做了激进的乱序执行或推测执行，一旦异常发生，所有"越过"异常点的推测执行副作用必须被隐藏**。这是 JVM 对"优化与正确性"矛盾的优雅解决——优化可以自由进行，但必须对用户程序呈现"顺序执行"的语义幻象。异步异常的棘手之处在于：它可能在任意两条指令之间插入，JIT 编译器必须在"控制转移指令"（如跳转、调用、返回）处插入异步异常轮询点，以确保异步异常的延迟有界。这正是 HotSpot 在 Safepoint 处同时处理"GC 请求"和"异步异常"的根本原因——它们在机制上同源。

## 11.2 本地代码内与跨本地代码异常处理：JNI 边界的"延迟接管"

这是全章最具"跨语言"挑战的部分。当异常遇到 Java ↔ native 边界时，语义变得极其微妙。

### 11.2.1 本地代码内的异常处理

**关键事实**：native 代码（C/C++）中，JVM 异常**不会立即中断**​ native 代码的执行。

HotSpot 的设计哲学是——**native 代码必须通过 JNI 函数显式检查 pending exception**。具体语义：

- 当 Java 代码通过 JNI 调用 native 方法时，如果 Java 侧已经有一个 pending exception，JVM 会先清空它再进入 native 代码（因为 native 方法通常有 `throws` 声明，异常应该在 Java 侧处理）
    
- native 代码执行期间，如果通过 JNI 调用 Java 方法并触发异常，该异常被记录为 native 帧的 pending exception
    
- **native 代码继续执行**——JVM 不会中断它，程序员必须显式调用 `env->ExceptionCheck()` 或 `env->ExceptionOccurred()` 检查
    
- 只有 native 方法**返回到 Java 代码**时，JVM 才正式"接管"这个异常，开始栈展开
    

> ⚠️ **工业陷阱**：这是 JNI 编程最常见的 Bug 来源。程序员误以为 JNI 调用失败会像 Java 异常一样立即中断控制流，但实际上 native 代码会继续执行，可能导致：
> 
> - 在异常状态下继续使用无效的 jobject（悬垂引用）
>     
> - 资源泄漏（文件句柄、锁未释放）
>     
> - 内存破坏（对部分初始化的对象进行操作）
>     

正确的 native 代码模式是：

```
jobject result = env->CallObjectMethod(obj, mid, args);
if (env->ExceptionCheck()) {
    // 处理异常或清理资源后返回
    env->ExceptionDescribe();  // 可选：打印异常
    env->ExceptionClear();     // 清除 pending exception
    return NULL;
}
```

### 11.2.2 带异常 Java 代码返回到本地代码

这是全章最微妙的场景——**Java 方法 A 调用 native 方法 B，B 又通过 JNI 调用 Java 方法 C，C 抛出异常**。

执行流程：

```
Java 方法 A
  → native 方法 B（进入 _thread_in_native）
    → JNI 调用 Java 方法 C（切换回 _thread_in_java）
      → C 中 athrow 抛出异常
      → JVM 在 C 的异常表中查找 → 未找到匹配
      → C 栈帧弹出，异常在 B 的上下文中"重抛"
    → JNI 调用返回到 B，但此时 B 的 pending exception 被设置
  → B 继续执行（如果程序员未检查异常）
  → B 返回到 A
  → JVM 在 A 的上下文中接管异常，开始栈展开
```

**关键设计决策**：HotSpot 选择**不在 native 方法 B 中立即中断**，而是让 pending exception "潜伏"在 B 的执行期间，直到 B 返回 Java 后才正式接管。这样做的原因：

1. **C/C++ 语义兼容性**：C 代码没有"异常中断"的概念，强制中断会破坏 C 代码的资源管理
    
2. **JNI 规范合规**：JNI 规范明确要求 native 代码显式检查异常
    
3. **性能考量**：每次 JNI 调用都检查异常会带来不可接受的开销
    

### 11.2.3 带异常的本地代码返回到 Java 代码

当 native 方法返回 Java 时，JVM 执行以下步骤：

1. 检查当前线程的 `_pending_exception` 字段
    
2. 如果存在 pending exception：
    
    - native wrapper 将线程状态从 `_thread_in_native` 切换为 `_thread_in_java`
        
    - 将 pending exception 对象引用压入 Java 调用者的操作数栈
        
    - 在 Java 调用者中开始异常表查找
        
    - 如果找到匹配的 catch → 跳转到 handler
        
    - 如果未找到 → 继续向上展开
        
    
3. 如果不存在 pending exception：正常返回，将返回值压入操作数栈
    

> 💡 **洞见**：跨本地代码异常处理的"延迟接管"模型，揭示了一个深刻的工程哲学——**"当两种语言的异常模型不兼容时，让边界处的语义转换延迟到回归主导语言时进行"**。Java 有精确的异常语义，C 没有；HotSpot 选择在 Java↔native 边界处"冻结"异常状态（存为线程级 pending exception），让 native 代码继续执行（符合 C 语义），但在 native 方法返回 Java 的瞬间"解冻"异常（恢复 Java 语义）。这种"延迟解冻"机制，是 JVM 在"跨语言互操作性"和"异常语义精确性"之间取得的精妙平衡。它与第7章 JNI 的"句柄层延迟绑定"、第9章 GC 支持的"跨边界 GC 安全性"一脉相承——**HotSpot 在每一个跨语言边界处都采用"延迟到回归 Java 时再处理"的策略**，既保持 JNI 的 C 语义兼容性，又维护 JVM 的精确异常模型。

## 11.3 保存栈轨迹：异常对象的"黑匣子"

这是全章最具"HotSpot 内部视角"的部分——异常对象如何捕获调用栈？

### Throwable 的栈轨迹存储机制

`java.lang.Throwable` 类有两个关键字段：

```
private transient Object backtrace;  // Native code 保存栈轨迹指示
private StackTraceElement[] stackTrace;  // 用户可见的栈轨迹数组
```

**关键设计——延迟构建**：

- `backtrace` 字段由 native 代码填充，保存的是 VM 内部的栈帧快照（以 VM 特定格式）
    
- `stackTrace` 数组**不会在异常构造时立即构建**
    
- 只有当用户首次调用 `getStackTrace()` 或 `printStackTrace()` 时，才通过 `getOurStackTrace()` 方法从 `backtrace` 解码出 `StackTraceElement[]` 数组
    

```
private synchronized StackTraceElement[] getOurStackTrace() {
    if (stackTrace == UNASSIGNED_STACK || 
        (stackTrace == null && backtrace != null)) {
        int depth = getStackTraceDepth();
        stackTrace = new StackTraceElement[depth];
        for (int i = 0; i < depth; i++)
            stackTrace[i] = getStackTraceElement(i);
    }
    return stackTrace;
}
```

**为什么延迟构建？**

1. **性能优化**：许多异常被抛出后从未调用 `printStackTrace()`（如在框架内部被捕获并处理），立即构建完整栈轨迹数组是浪费
    
2. **内存优化**：`StackTraceElement` 对象较多，延迟构建避免不必要的内存分配
    
3. **HotSpot 优化**：`fillInStackTrace()` 是 native 方法，它遍历当前线程栈帧，但只保存"压缩格式"的 backtrace（如返回地址数组），而非展开为 Java 对象
    

> 💡 **洞见**：`backtrace` 与 `stackTrace` 的"双轨制"揭示了一个深刻的工程原则——**"原始数据"与"用户视图"分离**。VM 内部用紧凑的 native 格式保存栈轨迹（backtrace），只在用户真正需要时解码为 Java 对象数组（stackTrace）。这种设计让 `new Throwable()` 的代价极低（只捕获原始栈帧指针），而 `printStackTrace()` 的代价按需支付。**这正是"惰性求值（Lazy Evaluation）"思想在 JVM 内部的经典应用**——它让"异常抛出"这个高频操作保持轻量，同时不牺牲"栈轨迹查询"的表达力。

### 栈轨迹的构建过程

`fillInStackTrace()` 的 native 实现（HotSpot 中 `Throwable::fillInStackTrace`）：

1. 从当前线程栈顶帧开始
    
2. 使用 `StackFrameStream` 迭代器遍历所有栈帧（见第8章）
    
3. 对每个栈帧，提取：类名、方法名、字节码索引（BCI）
    
4. 将 BCI 转换为源码行号（通过行号表 LineNumberTable）
    
5. 以 VM 内部格式存储到 `backtrace` 字段
    

> ⚠ **工业现实**：栈轨迹的构建是异常机制的"隐性开销"。在性能敏感的代码中，频繁抛出和捕获异常（如在循环中用异常控制流程）会导致：
> 
> - `fillInStackTrace()` 遍历整个调用栈（O(栈深度)）
>     
> - 可能触发 Safepoint（因为要展开栈帧）
>     
> - 分配 `StackTraceElement` 对象（如果调用 `printStackTrace()`）
>     
> 
> 这就是为什么《Effective Java》强调——**"不要用异常做控制流"**。异常的正确用途是"异常情况"，而非"正常情况"。在 JDK 7+ 中，`Throwable` 的构造器增加了 `writableStackTrace` 参数，允许创建不包含栈轨迹的异常（如 `new MyException("msg", null, false, false)`），正是为了性能敏感的框架（如 Scala、Kotlin）优化异常开销。

## 11.4 找到异常处理器：异常表的"精确匹配"

这是全章最核心的算法环节——JVM 如何在当前方法中找到匹配的异常处理器？

### 异常表的结构

每个方法的 Code 属性中包含一张**异常表（Exception Table）**，每条记录有四个字段：

|字段|含义|
|---|---|
|`start_pc`|受保护代码段的起始字节码偏移量|
|`end_pc`|受保护代码段的结束字节码偏移量（左闭右开）|
|`handler_pc`|异常处理器（catch 块）的起始字节码偏移量|
|`catch_type`|捕获的异常类型（指向常量池中的类引用；0 表示 finally）|

### 匹配算法

当异常在 `athrow` 指令（PC = X）处抛出时，JVM 执行：

```
for each entry in exception_table (按表顺序):
    if (X >= entry.start_pc && X < entry.end_pc):  // 位置匹配
        if (entry.catch_type == 0 || 
            thrown_exception.isInstanceOf(entry.catch_type)):  // 类型匹配
            PC = entry.handler_pc  // 跳转到 catch 块
            return
// 未找到匹配
弹出当前栈帧
在调用者帧中重复上述查找
```

**三个关键细节**：

1. **顺序匹配**：JVM 按异常表条目在 class 文件中的**书写顺序**线性扫描，第一个匹配胜出。这意味着——catch 块的**源代码顺序影响性能**！更具体的异常类型应该写在前面，否则可能被更通用的异常"屏蔽"。
    
2. **子类匹配**：`catch_type` 匹配时，如果抛出的异常是 `catch_type` 所指类的**子类**，也算匹配。这就是为什么 `catch (Exception e)` 能捕获所有受检异常和非受检异常。
    
3. **finally 的实现**：`catch_type = 0` 的条目表示捕获所有异常（包括 `Throwable`），编译器用它实现 `finally` 语义——每个 try 块都会生成两条异常表条目：一条对应显式 catch（指定具体类型），一条对应隐式 finally（type = 0）。
    

### 跨栈帧的异常传播

如果在当前方法中未找到匹配的处理器：

1. **释放监视器锁**：如果当前方法是 `synchronized`，释放 monitor
    
2. **弹出当前栈帧**：操作数栈和局部变量表被丢弃
    
3. **异常在调用者帧中重抛**：同一个异常对象引用被压入调用者的操作数栈
    
4. **在调用者中重复查找**：从调用者的异常表开始匹配
    
5. **直至找到匹配的 catch**​ 或 **到达线程栈顶**
    

> 💡 **洞见**：异常处理器查找的"自底向上"算法，揭示了一个反直觉的事实——**异常传播的成本是 O(栈深度 × 异常表大小)**。在最坏情况下（异常一路传播到 main 方法），JVM 需要遍历整个调用栈的每个方法的异常表。这就是为什么"深层嵌套的 try-catch"会成为性能瓶颈——每次异常抛出都要付出线性扫描的代价。HotSpot 对此做了优化：对于 JIT 编译的代码，异常处理器地址通过 `nmethod::_exception_handlers` 表提供 O(1) 查找；但对于解释器代码，仍需逐帧回溯解释器栈帧。这也解释了为什么现代 JIT 编译器会尽可能内联小方法——内联不仅减少调用开销，更减少异常传播时需要遍历的栈帧数。

## 11.5 控制转移：从抛出点到处理器的"精确跳转"

这是全章最具"机器级"质感的部分——当异常处理器找到后，JVM 如何精确地跳转到 catch 块，并恢复正确的执行状态？

### 11.5.1 控制转移操作

控制转移包含以下原子操作：

1. **PC 修正**：将程序计数器设为 `handler_pc`
    
2. **栈帧调整**：确保操作数栈处于 catch 块期望的初始状态（通常是空的，异常对象引用作为隐式参数）
    
3. **寄存器恢复**：恢复被调用者保存的寄存器（如果是从 JIT 代码转移）
    
4. **监视器处理**：释放当前方法持有的所有监视器锁
    

### 11.5.2 用于控制转移的寄存器

在 JIT 编译代码中，控制转移涉及寄存器状态机：

- **调用者保存寄存器（Caller-saved）**：调用者负责保存，被调用者可以自由使用——异常发生时无需恢复
    
- **被调用者保存寄存器（Callee-saved）**：被调用者必须使用前保存，返回前恢复——异常发生时必须恢复
    
- **PC 寄存器**：直接设为 `handler_pc`
    
- **FP（帧指针）**：恢复为调用者的帧指针
    
- **SP（栈指针）**：恢复为调用者的栈指针
    

### 11.5.3 数据寄存器恢复

HotSpot 通过 **RegisterMap**（见第9章）机制恢复寄存器：

- 当异常从 JIT 代码转移到 catch 块时，VM 使用 OopMap 确定哪些寄存器持有对象引用
    
- 通过 RegisterMap 找到这些寄存器的实际存储位置（物理寄存器或栈槽）
    
- 恢复这些寄存器的值到 catch 块入口时的预期状态
    

### 11.5.4 控制寄存器修正

**关键挑战**：如果异常从 JIT 编译的深栈帧中抛出，而 catch 块在更高层的栈帧中，VM 需要"跨栈帧"修正控制寄存器。

HotSpot 的解决方案是使用 **`SharedRuntime::exception_handler_for_return_address()`**：

- 对于 JIT 编译代码：通过 `nmethod::_exception_handlers` 表 O(1) 查找目标 handler 地址
    
- 对于解释器代码：逐帧回溯解释器栈帧，解析每个 frame 的 `interpreter_frame_method()` 与 `interpreter_frame_bcp()`，比对 bcp 是否位于该方法的 `method()->exception_table()` 范围内
    

### 11.5.5 执行恢复

异常处理器找到后，执行恢复的流程：

```
1. 设置 PC = handler_pc
2. 将异常对象引用压入操作数栈顶（作为 catch 块的隐式参数）
3. 恢复调用者栈帧的寄存器状态
4. 如果是从 native 方法返回，执行 native wrapper 的逆操作：
   - 解锁 monitor（如果是 synchronized native）
   - 将线程状态从 _thread_in_native 切换为 _thread_in_java
   - 清理 JNI 局部引用
5. 跳转到 handler_pc 开始执行 catch 块
```

> ⚠ **工业细节**：控制转移的精确性要求 VM 在异常表匹配成功后，必须**精确恢复 catch 块入口处的所有机器状态**。这包括：
> 
> - 操作数栈：清空，仅保留异常对象引用
>     
> - 局部变量表：恢复为 catch 块入口时的状态（通常只有方法参数）
>     
> - 寄存器：恢复被调用者保存寄存器
>     
> - 监视器：释放当前方法持有的所有锁
>     
> 
> 任何一个状态恢复错误，都会导致 catch 块执行时出现诡异的 bug（如读取到错误的局部变量值、寄存器中的悬垂引用）。这就是为什么 HotSpot 对异常路径的测试极其严格——异常机制是 JVM 正确性的"最后一道防线"。

### 11.5.6 未捕获异常

如果异常传播到线程栈顶仍未找到匹配的处理器，JVM 执行以下流程：

```
1. 线程终止
2. 在终止前，按以下规则处理未捕获异常：
   a. 如果线程设置了 UncaughtExceptionHandler → 执行该 handler
   b. 否则 → 调用该线程的 ThreadGroup 的 uncaughtException() 方法
   c. 如果 ThreadGroup 及其父 ThreadGroup 未重写 uncaughtException()
      → 调用默认 handler 的 uncaughtException() 方法
3. 线程正式终止
```

**主线程的特殊性**：如果未捕获异常发生在主线程（main 方法），默认 handler 会：

- 打印异常堆栈到 System.err
    
- 调用 `System.exit(1)` 终止 JVM 进程
    

**虚拟线程的差异**：在 Java 21+ 的虚拟线程中，未捕获异常**不会杀死载体线程（carrier thread）**，而是触发 `UncaughtExceptionHandler` 后，该虚拟线程直接结束，载体线程继续调度其他虚拟线程任务。

> 💡 **洞见（本章核心判断）**：未捕获异常的处理机制揭示了一个深刻的工程哲学——**"异常的终点不是崩溃，而是受控的终止"**。JVM 不允许未捕获异常"静默消失"，而是通过 `UncaughtExceptionHandler` 机制给应用程序最后一次"善后"的机会（如记录日志、释放资源、通知监控系统）。这是 JVM "托管运行时"承诺的最后体现——即使程序出错，JVM 也要确保终止过程是可控的、可观测的、可定制的。从第一性原理看，这与操作系统进程的 "signal handler" 机制、分布式系统的 "circuit breaker" 模式异曲同工——**"错误必须被显式处理，不能隐式忽略"**。

## 贯穿第11章的三条暗线（承上启下）

1. **异常是"跨层控制流协议"而非简单跳转**：从 `athrow` 到 catch 块，异常经历了"上下文保存 → 跨语言边界传播 → 栈轨迹构建 → 异常表匹配 → 控制转移 → 执行恢复"的完整协议。每一步都涉及虚拟机多个子系统的协同——解释器/JIT（执行）、StackFrameStream（栈展开）、OopMap/RegisterMap（GC 支持）、JNI（本地接口）、Monitor（同步）。理解异常，就读懂了 JVM 作为一个"分布式系统"的内部协同。
    
2. **"精确异常"是 JVM 对优化与正确性的优雅调和**：JIT 可以自由做推测执行、指令重排、内联优化，但必须保证"异常点之前的效果可见、异常点之后的效果不可见"。异步异常的延迟有界性要求 JIT 在控制转移点插入轮询。这种"优化自由 + 语义精确"的双重承诺，是 JVM 异常模型区别于 C++ 异常、Python 异常的根本特征。
    
3. **"延迟接管"是跨语言异常传播的工程典范**：JNI 边界处，HotSpot 选择"冻结"异常为线程级 pending exception，让 native 代码继续执行（符合 C 语义），直到 native 方法返回 Java 时才"解冻"异常（恢复 Java 语义）。`backtrace` 与 `stackTrace` 的"双轨制"同样是"延迟构建"思想的体现。这两条"延迟"策略，与第7章 JNI 句柄的"延迟绑定"、第9章 GC 支持的"跨边界延迟处理"一脉相承——**HotSpot 在跨语言边界处普遍采用"延迟到回归 Java 时处理"的策略**，既维护了 JNI 的 C 语义兼容性，又保持了 JVM 的精确异常模型。
    

---

**本章最核心的一句话**：异常抛出的本质，是虚拟机在"时间与空间"维度上的一次精密协同协议——**VM 在抛出瞬间保存完整上下文（线程级 pending exception + PC + 栈帧链），跨 Java/native 边界时采用"延迟接管"策略（native 代码继续执行，返回 Java 时才解冻异常），栈轨迹通过 `backtrace`+`stackTrace` 双轨制延迟构建，异常处理器通过异常表的"位置+类型"顺序匹配精确查找，控制转移通过 OopMap/RegisterMap 精确恢复寄存器与栈状态，未捕获异常通过 `UncaughtExceptionHandler` 实现受控终止**。理解这套"精确、延迟、跨语言"的异常协议，你就拿到了看懂 JVM 异常处理、JNI 异常模型、以及 HotSpot 为什么能做到"Precise Exception"的钥匙。

> 📌 **工业实践提示**：本章知识的直接应用包括——理解为什么"不要用异常做控制流"（栈轨迹构建 O(栈深度) + 可能触发 Safepoint）、为什么 catch 块顺序影响性能（异常表顺序匹配）、为什么 JNI 代码中必须显式检查 `ExceptionCheck()`（native 代码不会因异常中断）、为什么 `Throwable` 子类应该避免重写 `fillInStackTrace()`（破坏栈轨迹捕获）、以及为什么 Java 21+ 虚拟线程的未捕获异常不会杀死载体线程。这些都是从"VM 异常抛出机制"反推"Java 异常处理最佳实践"的典型案例。
