
# 第18章 monitor 性能优化 —— 读书笔记

如果说前十七章回答了"虚拟机如何执行、如何回收、如何跨语言互操作、如何模块化"，那么第18章要回答的是一个让 synchronized 从"重量级阻塞"进化为"近乎无开销"的根本问题——**当 99% 的锁操作实际上没有竞争（或只有单线程反复进入）时，虚拟机如何避免动辄陷入操作系统互斥量（pthread_mutex_t）的昂贵陷阱？**​ 这就是"monitor 性能优化"。李晓峰在这一章实际上在讲一个被工业界反复验证的真理——**monitor 优化的本质，是在"无竞争 / 单线程重入 / 轻度竞争 / 重度竞争"这四种真实场景中，为锁提供一条从便宜到昂贵的"升级路径"，并且让这条路径在运行时可进可退**。理解这一章，你才能理解为什么 synchronized 在 JDK 6 之后不再是"性能毒药"，为什么偏向锁在 JDK 15 被废弃（JEP 374），以及为什么 BEA JRockit 和 IBM JVM 都实现了 Tasuki 锁来获得"胖锁可回收"的能力。

结合李晓峰原书第18章框架、IBM 研究院 1998 年"Thin Locks"论文的工业传承、HotSpot 对象头 Mark Word 的锁状态编码、以及 JEP 374 对偏向锁废弃的官方解释，我来梳理这一章的脉络，并注入一些第一性原理层面的思考。

## 18.1 惰性锁：利用"线程局部性"的零开销锁

这是全章的起点，也是 monitor 优化的"第一性原理"——**大多数 Java 锁在生命周期内只被单个线程持有**。

### 线程局部性（Thread Locality）的观察

IBM 研究院 2002 年的研究明确指出：对于一个给定的锁，如果其加锁序列中包含某个特定线程的极长重复，则称该锁具有"线程局部性"，该线程称为"主导锁线程（dominant locker）"。基于这一观察，提出了**锁保留（Lock Reservation）**技术——也称为**惰性锁（Lazy Lock）**或**偏向锁（Biased Lock）**。

### 惰性锁的核心思想

锁被"保留"给其主导线程，以至于该线程后续访问锁时几乎零开销：

1. **首次加锁**：通过一次 CAS 操作，将锁标记为"已保留给线程 T"，并记录 T 的线程 ID
    
2. **后续加锁（同一线程 T）**：只需检查"锁是否保留给我"——一次普通的内存读取比较，**无需 CAS、无需原子指令**
    
3. **解锁（同一线程 T）**：**什么都不做**——线程不真正"释放"锁，锁继续保持偏向状态
    
4. **其他线程尝试加锁**：触发"偏向撤销（Bias Revocation）"，通常在 Safepoint 进行
    

> 💡 **洞见（本章核心判断之一）**：惰性锁的本质是**"用空间换原子操作"**——它在对象头的 Mark Word 中永久记录"这个锁属于哪个线程"，从而让主导线程的加锁/解锁完全避开 CAS（在现代硬件上，CAS 意味着内存屏障和刷新内存队列，开销相当可观）。研究表明，原子操作在对称竞争场景下有效，但在锁获取不对称（某一线程占主导）的场景下并非最佳方案——而这类不对称在 JVM 自身等系统中极为常见。惰性锁通过"给主导线程优先权，将成本转移给其他线程"，正是针对这种不对称性的优化。

> ⚠ **工业现实与演进**：惰性锁（在 HotSpot 中称为偏向锁）在 JDK 6（2006 年）引入并默认开启。然而，随着硬件演进和工作负载变化，偏向锁的撤销开销（需要在 Safepoint 执行）在现代应用中经常超过其收益。JEP 374 在 **JDK 15 中将偏向锁废弃并默认禁用**，在后续版本中彻底移除。今天，HotSpot 的默认路径是：无锁 → 轻量级锁（瘦锁）→ 重量级锁（胖锁）。但理解惰性锁的思想仍然至关重要——它揭示了 monitor 优化的根本方向："**针对锁的使用模式做专门化优化**"。

## 18.2 瘦锁：CAS + 栈上锁记录的轻量级路径

这是全章最具"HotSpot 内部视角"的部分，也是现代 HotSpot 在无竞争场景下的**实际快路径**。

### Mark Word 中的瘦锁编码

在 64 位 HotSpot 中（关闭压缩指针），对象头的 Mark Word（8 字节）根据锁状态存储不同内容：

|锁状态|Mark Word 内容|标志位|
|---|---|---|
|无锁|identity hash code \| 分代年龄 \| 0|01|
|偏向锁|线程 ID \| epoch \| 分代年龄 \| 1|01|
|**瘦锁**​|**指向栈上锁记录的指针**​|**00**​|
|**胖锁**​|**指向 ObjectMonitor 的指针**​|**10**​|
|GC 标记|前向指针|11|

### 18.2.1 瘦锁锁定路径

**核心算法**（HotSpot `ObjectSynchronizer::fast_enter` 路径）：

1. **检查无锁状态**：如果 Mark Word 标志位为 01（无锁），进入瘦锁获取路径
    
2. **在当前线程栈帧创建锁记录（Lock Record）**：锁记录中存储"Displaced Mark Word"（当前对象头的拷贝）
    
3. **CAS 替换 Mark Word**：通过 `Atomic::cmpxchg_ptr` 尝试将对象头的 Mark Word 替换为"指向锁记录的指针"
    
4. **CAS 成功**​ → 线程获得瘦锁，Mark Word 标志位变为 00
    
5. **CAS 失败**​ → 检查 Mark Word 是否指向当前线程的栈帧（说明是当前线程重入）→ 如果是，重入计数 +1；如果不是，说明存在竞争，进入膨胀流程
    

```
// 伪代码：瘦锁获取的核心逻辑
LockRecord* lr = create_lock_record_on_stack();
lr->displaced_mark_word = obj->mark();  // 拷贝原 Mark Word
if (CAS(&obj->mark, lr->displaced_mark_word, ptr_to_lr)) {
    // 成功获得瘦锁
    return LOCK_ACQUIRED;
} else {
    // CAS 失败，检查是否重入或需要膨胀
    if (obj->mark() points to current thread's stack) {
        lr->displaced_mark_word = 0;  // 重入，标记为 recursive
        return LOCK_RECURSIVE;
    } else {
        inflate_and_acquire_fat_lock();  // 膨胀为胖锁
    }
}
```

**关键设计要点**：

- **锁记录在线程栈上**：利用空间局部性，减少缓存未命中
    
- **Displaced Mark Word 的保存**：解锁时需要恢复原始 Mark Word（包含 hash code、分代年龄等）
    
- **CAS 是唯一原子操作**：在无竞争场景下，一次 CAS 成功即可，开销仅为几条机器指令（20-40 纳秒）
    

### 18.2.2 瘦锁解锁路径

**核心算法**：

1. **遍历当前线程栈上的锁记录**，找到与当前对象对应的锁记录
    
2. **检查 Displaced Mark Word**：
    
    - 如果为 0 → 说明是重入锁，重入计数 -1，直接返回（不真正解锁）
        
    - 如果非 0 → 说明是最外层解锁
        
    
3. **CAS 恢复 Mark Word**：通过 CAS 将对象头的 Mark Word 从"指向锁记录的指针"恢复为 Displaced Mark Word
    
4. **CAS 成功**​ → 锁释放完成
    
5. **CAS 失败**​ → 说明在解锁过程中锁已膨胀为胖锁，需要走胖锁的解锁路径
    

```
// 伪代码：瘦锁释放的核心逻辑
LockRecord* lr = find_lock_record_for(obj);
if (lr->displaced_mark_word == 0) {
    // 重入解锁，直接返回
    return;
}
if (CAS(&obj->mark, ptr_to_lr, lr->displaced_mark_word)) {
    // 成功恢复无锁状态
    destroy_lock_record(lr);
    return;
} else {
    // 锁已膨胀，走胖锁解锁
    fat_lock_exit(obj);
}
```

### 18.2.3 竞争标志重置支持

这是瘦锁实现中的一个微妙细节——**竞争标志（Contention Bit）的管理**。

在瘦锁的 Lock Word 结构中，有一位专门的"竞争位（Contention Bit）"：

- **Contention Bit = 0**：无竞争
    
- **Contention Bit = 1**：存在竞争
    

**竞争标志的作用**：

- 当线程 CAS 失败（发现竞争）时，设置竞争位
    
- 锁的拥有者在释放锁时检查竞争位
    
- 如果竞争位被设置，拥有者知道有其他线程正在等待，需要采取相应动作（如唤醒等待线程、触发膨胀等）
    

**重置时机**：

- 在锁成功获取且无竞争时，竞争位保持为 0
    
- 在锁释放且无等待线程时，竞争位重置为 0
    
- 这个机制让锁的拥有者能够"感知"是否有线程在等待，从而做出优化的释放决策
    

> 💡 **洞见**：竞争标志的设计体现了 monitor 优化的核心哲学——**"让无竞争路径保持极简，让竞争路径承担复杂性"**。在无竞争的 99% 场景中，只需一次 CAS，不涉及竞争位的任何操作；只有在竞争发生的 1% 场景中，才涉及竞争位的设置和检查。这种"快路径极简、慢路径复杂"的设计，与第4章解释器的"快路径/慢路径分离"、第6章 GC 的"Young GC 快、Full GC 慢"一脉相承——**这是 HotSpot 贯穿所有子系统的统一设计哲学**。

## 18.3 胖锁：当竞争不可避免时的重量级方案

这是全章最具"操作系统视角"的部分——当瘦锁无法兜住竞争时，虚拟机必须求助于操作系统。

### 18.3.1 整合 monitor 数据结构

**胖锁的本质**：JVM 在堆上分配一个 `ObjectMonitor` 对象（C++ 结构），包含完整的管程数据结构：

```
class ObjectMonitor {
    Thread* _owner;           // 锁拥有者线程
    intptr_t _recursions;     // 重入计数
    ObjectWaiter* _EntryList; // 阻塞等待获取锁的线程队列
    ObjectWaiter* _WaitSet;   // 调用 wait() 的线程队列
    Thread* _Responsible;     // 负责线程（用于自适应自旋）
    int _SpinDuration;        // 自旋持续时间
    // ... 其他字段
};
```

**ObjectMonitor 的关键组件**：

- **owner**：当前持有锁的线程
    
- **EntryList**：尝试获取锁但未能成功的线程（处于 blocked 状态）
    
- **WaitSet**：调用了 `obj.wait()` 的线程（处于 waiting 状态）
    
- **recursions**：重入计数器
    

### 18.3.2 交由 OS 来支持

当锁膨胀为胖锁后，**线程阻塞与唤醒交由操作系统完成**：

- 在 Linux 上，底层使用 `pthread_mutex_t` 和 `pthread_cond_t`
    
- 线程阻塞时调用 `park()`，涉及系统调用，线程从用户态切换到内核态
    
- 线程唤醒时调用 `unpark()`，由 OS 调度器重新调度
    

**性能代价**：

- **上下文切换**：5-15 微秒（仅上下文切换本身）
    
- **缓存污染**：线程在不同核心恢复时，缓存行失效
    
- **调度延迟**：OS 调度器决定何时唤醒，存在不可预测的延迟
    

> ⚠ **工业现实**：胖锁的代价是昂贵的系统调用和上下文切换。这就是为什么 monitor 优化的目标是——**尽可能让锁停留在瘦锁状态，避免膨胀为胖锁**。但胖锁也有其不可替代的价值：在真实竞争场景下，让线程进入 OS 级别的阻塞（park），允许 CPU 去执行其他有用工作，这比忙等（busy-wait）更高效。

### 18.3.3 瘦锁膨胀为胖锁

这是 monitor 优化的关键转折点——**何时、如何膨胀**。

**膨胀触发条件**：

1. 线程 T1 持有瘦锁（Mark Word 指向 T1 栈上的锁记录）
    
2. 线程 T2 尝试 CAS 获取锁，失败（发现 T1 持有）
    
3. T2 进入膨胀流程：
    

**膨胀算法**（HotSpot `ObjectSynchronizer::inflate`）：

```
1. T2 分配一个新的 ObjectMonitor 对象
2. T2 使用 CAS 将 Mark Word 设置为 INFLATING 状态（临时状态）
3. 如果 CAS 成功：
   a. T2 读取 Displaced Mark Word（从 T1 的锁记录中）
   b. 将 Displaced Mark Word 拷贝到 ObjectMonitor 的 _header 字段
   c. 设置 ObjectMonitor 的 _owner = T1
   d. 使用 CAS 将 Mark Word 设置为指向 ObjectMonitor 的指针（标志位 10）
4. 如果 CAS 失败（其他线程已在膨胀）：
   a. 回收分配的 ObjectMonitor
   b. 重试膨胀循环
```

**INFLATING 状态的必要性**：

- 确保同一时刻只有一个线程执行膨胀
    
- 防止膨胀线程读到过期的 Displaced Mark Word
    
- 其他线程（包括锁拥有者 T1）在膨胀完成前都必须等待
    

**膨胀后的影响**：

- 一旦膨胀为胖锁，**传统 HotSpot 中是不可逆的**——即使后续竞争消失，锁也保持为胖锁
    
- 所有后续加锁/解锁都走 ObjectMonitor 的 enter/exit 路径
    
- 这是传统瘦锁模型的主要弱点之一
    

> 💡 **洞见（本章核心判断之二）**：瘦锁膨胀为胖锁的"单向不可逆性"，是传统 HotSpot monitor 设计的最大遗憾。在真实的多线程基准测试中，大多数锁竞争是**暂时性的**——某个热点时刻有竞争，但随后竞争消失。然而传统 HotSpot 一旦膨胀就永不回退，这意味着应用在长期运行后，大量本可以回到瘦锁的锁被永久固定在胖锁状态，持续付出昂贵的系统调用代价。这正是 Tasuki 锁要解决的第一个核心问题。

### 18.3.4 休眠等待被竞争瘦锁

这是胖锁膨胀前的"最后一搏"——**自适应自旋**。

**传统瘦锁模型的缺陷**：

- 当 T2 CAS 失败时，传统模型立即进入膨胀
    
- 但 T1 可能很快（几微秒内）就释放锁
    
- 立即膨胀 + 线程阻塞的代价远高于短暂自旋
    

**HotSpot 的自适应自旋优化**：

- 在膨胀前，T2 先进行自适应自旋
    
- 自旋次数根据前一次在同一锁上的自旋成功率动态调整
    
- 采用阶梯式退避策略，避免长时间空转
    
- 自旋期间适当让出 CPU（通过 yield 或短暂 park）
    

**自旋的收益与代价**：

- **收益**：如果锁持有时间极短（纳秒级），自旋可以避免昂贵的上下文切换
    
- **代价**：自旋消耗 CPU 资源，如果锁持有时间长，自旋是纯浪费
    

**工业实测数据**：

- 瘦锁 CAS 成功：20-40 纳秒
    
- 胖锁上下文切换：5-15 微秒（相差 100-1000 倍）
    

> 💡 **洞见**：自适应自旋是"用 CPU 时间换上下文切换开销"的经典权衡。它基于一个关键观察——**大多数锁的持有时间极短**。在 16 线程竞争 synchronized 计数器的基准测试中，吞吐量从单线程的 1200 万 ops/sec 下降到 300 万 ops/sec——竞争代价巨大。自适应自旋试图在这种场景下"扛过"短暂竞争，避免立即堕入胖锁的深渊。

## 18.4 Tasuki 锁：让胖锁"可回收"的革命性优化

这是全章最具"算法美感"的部分，也是 BEA JRockit 和 IBM JVM 都采用的优化。

### Tasuki 锁要解决的瘦锁模型两大弱点

1. **不可逆膨胀**：一旦瘦锁膨胀为胖锁，永不回退
    
2. **忙等（Busy-wait）**：竞争线程通过自旋等待，浪费 CPU
    

### 18.4.1 将同一个胖锁 monitor 用于竞争控制

**Tasuki 锁的核心创新之一：FLC 位（Flat-lock Bit）**

Tasuki 锁在对象头中引入了一个独立于 Lock Word 的 FLC 位（扁平锁位）：

- **为什么独立于 Lock Word**：FLC 位由竞争线程设置，而 Lock Word 仅由锁拥有者线程修改，两者需要独立以保证数据一致性
    
- **FLC 位的作用**：标记"是否有线程正在竞争该锁"
    

**Tasuki 锁的竞争处理流程**：

```
1. 线程 T2 尝试获取瘦锁，CAS 失败
2. T2 设置对象的 FLC 位
3. T2 创建一个新的胖锁（ObjectMonitor）
4. T2 将自己加入到胖锁的阻塞线程队列
5. T2 将胖锁插入到对应的查找表（lock table）
6. T2 挂起自己（suspend），开始等待
7. 锁拥有者 T1 释放锁时：
   a. 检查 FLC 位
   b. 如果 FLC 位被设置：
      - 遍历查找表找到对应的胖锁
      - 向所有阻塞线程发送信号（signal）
8. 被唤醒的线程 T2 获得锁后，按照原瘦锁模型的方式膨胀锁
```

**关键优势**：

- **消除忙等**：T2 在设置 FLC 位后立即挂起，不自旋
    
- **胖锁复用**：通过查找表，多个竞争线程可以共享同一个胖锁结构
    

> 💡 **洞见（本章核心判断之三）**：FLC 位的引入是 Tasuki 锁最精妙的设计——它用一个独立的"竞争标志位"将"竞争检测"与"锁状态"解耦。锁拥有者 T1 在释放锁时只需检查 FLC 位（一次普通的内存读取），就能知道是否有线程在等待。如果有，才去查找表找胖锁并唤醒等待线程；如果没有，释放路径就是极简的瘦锁解锁。这是"快路径极简"哲学在 Tasuki 锁中的延续。

### 18.4.2 胖锁收缩为瘦锁（Deflation）

这是 Tasuki 锁最具革命性的创新——**胖锁可逆**。

**核心思想**：如果膨胀后的胖锁没有任何阻塞或等待的线程，且被释放，那么它可以被"回缩"为普通的瘦锁。

**Deflation 算法**：

```
1. 线程 T1 持有胖锁，准备释放
2. 释放时检查：
   - EntryList 为空（无线程阻塞等待）
   - WaitSet 为空（无线程调用 wait）
3. 如果两个队列都为空：
   a. 直接将对象的 Lock Word 重置为零（即瘦锁的无锁状态）
   b. 胖锁结构被回收
4. 后续线程获取该锁时，走瘦锁路径（CAS）
```

**与传统瘦锁模型的对比**：

|维度|传统瘦锁|Tasuki 锁|
|---|---|---|
|膨胀触发|CAS 失败|CAS 失败 + 设置 FLC + 创建胖锁|
|竞争处理|自旋等待（忙等）|设置 FLC 后挂起（无忙等）|
|膨胀可逆性|**不可逆**​|**可逆（Deflation）**​|
|长期运行表现|大量锁永久停留在胖锁|竞争消退后回到瘦锁|

**工业实现差异**：

- **BEA JRockit**：实现了 Tasuki 锁机制，通过运行时采样数据动态调整权值，左右 Lock Inflation/Deflation 的过程
    
- **IBM JVM**：同样实现了 Tasuki 锁，但在启发式设计上有所不同
    

> 💡 **洞见**：Tasuki 锁的 Deflation 机制揭示了一个深刻的工程真理——**"锁的状态应该反映当前的竞争 reality，而非历史的竞争 memory"**。传统 HotSpot 的"膨胀不可逆"是基于"一旦竞争发生，未来很可能继续竞争"的假设；但工业基准测试表明，大多数锁竞争是**暂时性的**——高峰时段有竞争，低谷时段无竞争。Tasuki 锁通过 Deflation 让锁状态能够动态适应竞争的变化，这在长时间运行的企业应用中带来显著的性能提升。BEA JRockit 和 IBM JVM 都通过动态调整 Inflation/Deflation 的阈值，进一步强化了这种适应性。

## 18.5 线程局部锁：惰性锁的工程实现

这是全章的收官部分，也是把第18.1节的"惰性锁理论"落到工程实现的细节。

### 18.5.1 锁保留（Lock Reservation）

**锁保留是惰性锁的工程术语**——JVM 为每个对象维护一个"保留线程"的概念。

**工作流程**：

```
1. 首次加锁：
   a. 检查对象是否已被保留
   b. 如果未保留：
      - 通过 CAS 将锁状态设置为"已保留给当前线程"
      - 同时获取锁（CAS 成功即获得锁）
   c. 如果已保留给其他线程：
      - 暂停锁拥有者线程
      - 移除保留状态
      - 恢复拥有者线程
      - 重新尝试获取锁

2. 后续加锁（同一线程）：
   a. 检查"锁是否保留给我"
   b. 是 → 直接获得锁，无 CAS、无原子操作
   c. 否 → 触发保留转移或膨胀

3. 解锁（同一线程）：
   a. 什么都不做——锁继续保持保留状态
   b. 这是锁保留与瘦锁的关键区别：瘦锁解锁需要 CAS 恢复 Mark Word，锁保留解锁零开销
```

**HotSpot 中的实际演进**：

- **JDK 6-14**：实现了偏向锁（Biased Locking），这是锁保留的一种实现
    
    - 在对象头 Mark Word 中存储偏向线程 ID
        
    - 后续加锁只需比较线程 ID（一次内存读取）
        
    - 解锁不做任何操作
        
    - 其他线程竞争时触发偏向撤销（在 Safepoint 执行，开销昂贵）
        
    
- **JDK 15+**：偏向锁被废弃（JEP 374），原因：
    
    - 现代应用中，偏向撤销的 Safepoint 开销经常超过偏向锁的收益
        
    - 原子操作在现代硬件上已相对便宜
        
    - 维护偏向锁的复杂性超过了其带来的收益
        
    

### 18.5.2 线程亲密锁（Thread-Affinity Lock）

**线程亲密性的观察**：如果某个锁表现出强烈的线程局部性（特定线程频繁获取），则可以建立"线程与该锁的亲和关系"。

**工业实现思路**（基于学术文献）：

1. **Reservation Bit**：在 Lock Word 中设置保留位，标记锁是否被某个线程保留
    
2. **Fat Lock ID**：在 Lock Word 中存储 20 位的胖锁 ID，用于查找对应的胖锁结构
    
3. **Contention Bit**：竞争位，标记是否存在竞争
    

**Sable VM 的变体实现**：

- 将 FLC 位从对象头移到线程的内部数据结构中
    
- 原因：对象头的空间极其昂贵，即使一个位，在大量小对象场景下也会造成显著的内存开销
    
- 代价：需要一个专用的 mutex 来保证对 FLC 位的互斥访问
    
- 线程结构必须包含一个链表，保存"(锁对象, 阻塞线程)"的元组对
    

> 💡 **洞见（本章核心判断之四）**：线程局部锁（锁保留/偏向锁）的本质，是利用"锁使用模式的不对称性"做专门化优化。在传统对称竞争场景下，原子操作（CAS）是最优解；但在"某一线程占主导"的不对称场景下，给主导线程优先权、将成本转移给其他线程，能获得更高的整体性能。这是"针对工作负载特征做优化"这一计算机科学基本原理在 monitor 设计中的体现。HotSpot 在 JDK 15 废弃偏向锁，并不是因为"线程局部性"这一观察错了，而是因为：① 现代硬件上 CAS 的开销已大幅降低；② 偏向撤销需要在 Safepoint 执行，在现代复杂应用中 Safepoint 的到达时间（Safepoint Poll）可能很长；③ 维持偏向锁的复杂性（批量重偏向、撤销、epoch 管理等）超过了其收益。这是对"优化策略随硬件演进和工作负载变化而重新审视"的经典案例。

## 贯穿第18章的三条暗线（承上启下）

1. **"快路径极简、慢路径复杂"是 monitor 优化的统一哲学**：从惰性锁（零开销的偏向路径）→ 瘦锁（一次 CAS 的轻量级路径）→ 胖锁（OS mutex 的重量级路径），每一级都在"无竞争/单线程重入/轻度竞争/重度竞争"这四种真实场景中提供最优解。这与第4章解释器的"快路径/慢路径分离"、第14章 GC 的"Young GC 快、Full GC 慢"一脉相承。
    
2. **"可逆性"是 Tasuki 锁对传统瘦锁模型的根本性改进**：传统 HotSpot 的瘦锁膨胀为胖锁是单向不可逆的，导致长期运行的应用中大量锁永久停留在胖锁状态；Tasuki 锁通过 FLC 位（消除忙等）+ Deflation（胖锁可回收）两大创新，让锁状态能够动态适应竞争的变化，在 BEA JRockit 和 IBM JVM 中都获得了显著的性能提升。
    
3. **"优化策略必须随硬件演进和工作负载变化而重新审视"**：偏向锁（锁保留）在 JDK 6 引入时是巨大的性能突破，但在 JDK 15 被废弃——这不是因为"线程局部性"的观察错了，而是因为现代硬件上 CAS 开销降低、Safepoint 撤销代价相对上升、应用复杂度增加。monitor 优化的历史告诉我们——**任何"针对特定硬件特征和工作负载模式"的优化，都有其生命周期**。
    

---

**本章最核心的一句话**：monitor 性能优化的本质，是在"无竞争 / 单线程重入 / 轻度竞争 / 重度竞争"这四种真实场景中，为 synchronized 提供一条**从便宜到昂贵的升级路径**——**惰性锁（利用线程局部性，零开销偏向）/ 瘦锁（一次 CAS + 栈上锁记录）/ 胖锁（ObjectMonitor + OS mutex）三级递进**；Tasuki 锁通过 FLC 位消除忙等、通过 Deflation 让胖锁可回收，解决了传统瘦锁模型"不可逆膨胀"和"竞争时忙等"两大弱点，成为 BEA JRockit 和 IBM JVM 的共同选择；而偏向锁在 JDK 15 的废弃（JEP 374），则提醒我们——**任何针对特定硬件特征和工作负载模式的优化，都有其生命周期，必须随技术演进重新审视**。理解这套"分级升级 + 可逆优化 + 生命周期管理"的 monitor 优化框架，你就拿到了看懂 HotSpot synchronized 实现、JEP 374 决策背景、以及现代并发编程性能调优的钥匙。

> 📌 **工业实践提示**：本章知识的直接应用包括——
> 
> - **理解为什么 synchronized 不再是"性能毒药"**：JDK 6 之后的锁升级机制让无竞争场景下 synchronized 的开销极低（瘦锁 CAS 仅 20-40 纳秒）

>

>     
> - **高竞争场景的替代方案**：StampedLock、ReentrantLock、LongAdder 等 `java.util.concurrent` 工具在高竞争下表现优于 synchronized（基准测试中 16 线程 synchronized 计数器吞吐量从 1200 万 ops/sec 降到 300 万，而 StampedLock 继续线性扩展）

>     
> - **Tasuki 锁的工业价值**：在长时间运行、竞争模式动态变化的企业应用中，胖锁可回收机制（Deflation）带来显著的性能稳定性提升
