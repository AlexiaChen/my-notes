
# 《深入理解Java虚拟机（第2版）》第2章 读书笔记

## Java 内存区域与内存溢出异常 —— 读懂 JVM 的"内存地图"与"故障现场"

> 本章是全书技术含量最高、也最"硬核"的章节之一。如果说第1章是"走近 Java"的鸟瞰地图，那么第2章就是**把 JVM 这台机器的"内存电路板"拆开给你看**——哪些区域归谁管、对象怎么在里头出生、又在哪一处会"内存溢出"而猝死。它是后续所有篇章（GC、类加载、字节码执行、并发）共同的**内存地基**。

## 一、章节脉络总览（先建骨架）

第2章围绕一条主线展开：**JVM 如何划分和管理运行时内存 → 对象如何在其中诞生 → 哪几类典型场景会导致内存溢出**。全书逻辑链如下：

```
2.1 概述
  ↓ "Java 程序的内存由 JVM 自动管理，但 OOM 仍会发生"
2.2 运行时数据区域（6 大区域：PC / 栈 / 本地栈 / 堆 / 方法区 / 运行时常量池 + 直接内存）
  ↓ "内存被划分成若干区域，各有职责"
2.3 HotSpot 虚拟机对象探秘（对象的创建 / 内存布局 / 访问定位）
  ↓ "对象是如何在这些区域里被构造出来的"
2.4 实战：OutOfMemoryError 异常（堆 / 栈 / 方法区常量池 / 直接内存 四类溢出）
  ↓ "每一类区域都可能成为 OOM 的事故现场"
2.5 本章小结
```

**我的理解（第一性原理视角）**：这一章真正的"第一性原理"是——**JVM 通过"区域隔离 + 职责分离"来同时解决三个矛盾：线程隔离（PC/栈私有）vs 线程共享（堆/方法区）；自动 GC（堆）vs 手动/原生管理（直接内存/本地栈）；规范稳定（方法区存类元信息）vs 运行弹性（堆可扩展）**。理解"每个区域为什么存在、为谁服务、谁会溢出"，比死记硬背 6 个区域名称重要得多。

## 二、逐节精读与洞见

### 2.1 概述 —— 自动内存管理的"能与不能"

Java 与 C/C++ 最大的不同，是**把内存控制权交给了 JVM**：程序员只管 new 对象，不管 delete/free；内存的分配与回收由 JVM 自动完成。这带来了极高的开发效率，但也埋下隐患——**一旦内存管理失控（泄漏、配置不当、区域容量不足），程序员往往束手无策，因为控制权已不在自己手里**。

**洞见**：这一节的深层含义是——**"自动管理"不是"无需理解"**。恰恰因为控制权交给了 JVM，你才更需要理解 JVM 的内存划分与回收机制，否则一旦 OOM，你连"该调哪个参数、该查哪类泄漏"都不知道。这正是本章乃至全书存在的根本理由。

### 2.2 运行时数据区域 —— JVM 的"六块电路板"

这是全章信息密度最高的一节。下面用**一张总表 + 逐区域洞见**的方式梳理（结合书中定义与 HotSpot 现行实现补正）：

|区域|线程私有/共享|存储内容|是否可 OOM|关键参数|
|---|---|---|---|---|
|**程序计数器（PC）**​|私有|当前线程执行的字节码指令地址（native 方法时为 undefined）|**否**（唯一不会 OOM 的区域）|—|
|**Java 虚拟机栈**​|私有|方法调用的栈帧：局部变量表 / 操作数栈 / 动态链接 / 方法出口|StackOverflowError / OOM|`-Xss`|
|**本地方法栈**​|私有|为 native（JNI）方法服务|StackOverflowError / OOM|HotSpot 中与虚拟机栈**合并为同一栈**​|
|**Java 堆**​|共享|对象实例与数组（GC 主战场）|OOM: Java heap space|`-Xms` / `-Xmx`|
|**方法区**​|共享|类元信息 / 常量 / 静态变量 / JIT 编译后的代码缓存|OOM: PermGen（≤JDK7）/ Metaspace（≥JDK8）|`-XX:MaxMetaspaceSize`|
|**运行时常量池**​|共享（方法区一部分）|编译期字面量 + 符号引用|随方法区一起溢出|同上|
|**直接内存**（非 JVM 规范区域）|—|NIO 的 DirectByteBuffer 等堆外内存|OOM: Direct buffer memory|`-XX:MaxDirectMemorySize`|

**逐区域洞见（重点，带工业联系）**：

1. **程序计数器——"线程切换后能恢复执行"的基石**。它是 JVM 规范中**唯一不会抛出 OutOfMemoryError 的区域**，物理上通常借 CPU 寄存器实现，开销极小。多线程环境下，每条线程独立计数，互不干扰——这是 Java 多线程能正确切换的根本保障。
    
2. **虚拟机栈——"方法调用的内存模型"**。每个方法调用对应一个**栈帧（Stack Frame）**，栈帧含局部变量表、操作数栈、动态链接、方法出口。局部变量表里存的是**基本类型 + 对象引用（reference，不是对象本身）**；64 位类型（long/double）占两个变量槽（Slot）。
    
    - **工业联系**：JIT 会通过**逃逸分析**判断对象是否"逃出方法"——若未逃逸，可能在**栈上分配**（标量替换）而非堆上，从而随栈帧一起回收，极大减轻 GC 压力。这是"栈"与"对象分配"之间一个极有价值的优化联系。
        
    
3. **本地方法栈——HotSpot 的"合并"设计**。HotSpot 不区分虚拟机栈和本地方法栈（`-Xoss` 参数存在但**实际无效**），两者共用同一栈，`-Xss` 同时控制两者。**洞见**：这说明 HotSpot 在工程实现上追求"简化栈模型"——对 Java 方法和 native 方法一视同仁，统一用一套栈帧管理。
    
4. **Java 堆——"GC 的主战场"**。堆是 JVM 管理的最大一块内存，几乎所有对象实例和数组都在这里分配，逻辑上分为**新生代（Eden + 2 个 Survivor）和老年代**。**工业联系**：`-Xmx`/`-Xms` 是生产环境必调参数（如 8 核 16G 机器常配 `-Xmx8G`），新生代（`-Xmn`）一般占堆的 1/3~1/2。
    
5. **方法区与运行时常量池——"从 PermGen 到 Metaspace 的演进"**。这是本章**最需要与现行 JDK 对齐**的一点：
    
    - **JDK 7 及以前**：方法区用**永久代（PermGen）**实现，运行时常量池（含字符串常量池）也在其中，`-XX:PermSize`/`-XX:MaxPermSize` 控制大小。
        
    - **JDK 8 起**：**永久代被移除，由元空间（Metaspace）取代**，Metaspace 使用**本地内存（Native Memory）**，不再占用堆；`-XX:MetaspaceSize`/`-XX:MaxMetaspaceSize` 控制（**不设 Max 等于不限制，可能耗尽物理内存**）。
        
    - **字符串常量池（StringTable）在 JDK 7 后已移至堆中**，与运行时常量池分离。
        
    - **洞见（第一性原理 + 创新判断）**：从 PermGen 到 Metaspace 的演进，本质是**"把类元信息从受 GC 严格管理的堆中解放出来，交给更灵活的本地内存"**——因为类的生命周期（常驻、卸载少）与对象（短命、频繁回收）截然不同，混在一起管理只会互相拖累。这再次印证了"**按数据生命周期分离存储**"的工程哲学。**注意**：StringTable（字符串常量池）≠ 运行时常量池，前者 JDK7+ 在堆，后者在 Metaspace。
        
    
6. **直接内存——"不归 JVM 堆管的影子杀手"**。直接内存并非 JVM 规范定义的区域，但通过 NIO 的 `ByteBuffer.allocateDirect()` 大量使用，**直接向操作系统申请堆外内存**，不由 GC 直接管辖。`-XX:MaxDirectMemorySize` 控制上限（默认等于 `-Xmx`）。
    
    - **工业联系（Netty/高并发 I/O）**：Netty 等高性能网络框架重度依赖 DirectByteBuffer 做零拷贝。**典型坑**：堆监控一切正常，但物理内存被 Direct Buffer 慢慢吃光导致进程被 OS 杀掉——**这是最难排查的 OOM 类型之一**。
        
    

### 2.3 HotSpot 虚拟机对象探秘 —— 对象是如何"出生"的

这是本章最具"内部实现美感"的一节，分三块：**创建 → 内存布局 → 访问定位**。

#### 2.3.1 对象的创建（六步流水线）

遇到 `new` 指令后，HotSpot 按以下流程创建对象：

```
① 类加载检查 → ② 分配内存 → ③ 初始化零值 → ④ 设置对象头 → ⑤ 执行 <init> 构造方法
```

- **① 类加载检查**：`new` 的参数能否在常量池定位到类的符号引用？该类是否已加载/解析/初始化？若否，先执行类加载。
    
- **② 分配内存**：类加载完成后对象大小即确定。分配方式有二，取决于**堆是否规整**，而堆是否规整又取决于**收集器是否带压缩整理能力**：
    
    - **指针碰撞（Bump the Pointer）**：堆规整时用（如 Serial、ParNew 等带压缩的收集器），通过移动指针分配。
        
    - **空闲列表（Free List）**：堆不规整时用（如 CMS），维护可用内存块列表。
        
    - **并发安全**：多线程同时分配时，用 **CAS 重试**保证原子性，或为每线程在 Eden 区预分配一小块 **TLAB（Thread Local Allocation Buffer，`-XX:+UseTLAB`）**，线程私有、避免竞争。
        
    
- **③ 初始化为零值**：将分配到的内存（不含对象头）清零，保证字段不赋初值也能使用（如 int 默认 0）。
    
- **④ 设置对象头**：写入对象所属类、类元数据位置、哈希码、GC 分代年龄、锁状态等。
    
- **⑤ 执行 `<init>`**：调用构造函数按程序员意愿初始化——至此对象才真正"可用"。
    

**洞见**：创建流程里最精妙的是**"分配方式由收集器决定"这一耦合**——它揭示了 JVM 内部一个深层设计原则：**内存分配与垃圾回收是高度协同的，而非两个独立模块**。理解这一点，后面学 GC 章节时会豁然开朗。

#### 2.3.2 对象的内存布局（对象头 + 实例数据 + 对齐填充）

HotSpot 中对象在堆中的布局分三部分：

```
┌─────────────────────────────────────────────┐
│  对象头 (Object Header)                      │
│  ├─ Mark Word（标记字）                      │
│  └─ Klass Pointer（类型指针 → 类元数据）      │
├─────────────────────────────────────────────┤
│  实例数据 (Instance Data)  —— 各字段值        │
├─────────────────────────────────────────────┤
│  对齐填充 (Padding)       —— 补到 8 字节倍数 │
└─────────────────────────────────────────────┘
```

- **Mark Word**：存储对象运行时数据——哈希码、GC 分代年龄（4 位，最大 15，决定对象最多经历 15 次 Young GC 才晋升）、锁状态（偏向锁/轻量级锁/重量级锁/GC 标记）。32 位 JVM 占 4 字节，64 位占 8 字节。
    
- **Klass Pointer（类型指针）**：指向方法区/元空间中的 `InstanceKlass`（类元数据），JVM 借此在运行期获取类信息；启用**压缩指针（`-XX:+UseCompressedOops`，JDK6 后默认开启）**时为 4 字节，否则 8 字节。
    
- **实例数据**：对象的非静态属性（字段值）；引用类型同样受压缩指针影响占 4 或 8 字节。
    
- **对齐填充**：HotSpot 要求对象起始地址为 **8 字节整数倍**，大小不足则用 padding 补齐。
    

**关键数据（务必记住）**：64 位 JVM + 开启压缩指针时，**空对象占 16 字节**（8B Mark Word + 4B Klass + 4B 对齐填充）。

> 补充（前沿）：**Project Lilliput（JEP 450/519）**正在把 Klass Pointer 合并进 Mark Word，将对象基础头从 12 字节压缩到 **8 字节**——未来对象内存效率将进一步提升。

**洞见 & 工业联系（这是本节最有价值的"创新判断"）**：

1. **对象头的"隐性成本"惊人**。每个对象至少 12~16 字节头开销。若有 1000 万个 `Boolean` 包装对象，仅对象头就占约 **120MB**，而实际数据（boolean 值）仅 1 字节/对象——**有效数据被头开销淹没**。这就是为什么用 `HashMap<Boolean,...>` 存大量布尔标志极浪费，应改用 `BitSet` 或 Eclipse Collections 等**原生类型特化集合**，内存可削减 10 倍以上。**这是"理解对象布局"直接指导"工程选型"的典型案例**。
    
2. **分代年龄 4 位 = 最大 15 次**：这是对象晋升老年代的默认阈值（`-XX:MaxTenuringThreshold`，默认 15），理解它有助于后续调优 GC 晋升行为。
    

#### 2.3.3 对象的访问定位（句柄 vs 直接指针）

栈上的 `reference` 如何找到堆中的对象？《规范》未规定，HotSpot 采用**直接指针**方式：

|方式|reference 存的内容|优点|缺点|
|---|---|---|---|
|**句柄（Handle）**​|句柄池中的句柄地址，句柄再分指实例数据 + 类型数据|GC 移动对象只需改句柄，reference 不变，稳定|每次访问**两次间接寻址**，慢 12%~18%|
|**直接指针（HotSpot 默认）**​|对象在堆中的直接地址|**一次寻址**，访问快 12%~18%（数组遍历等高频场景受益显著），CPU 缓存局部性好|GC 移动对象时需更新所有指向它的 reference|

- HotSpot **自 JDK 1.3 起仅采用直接指针**；配合压缩指针（`-XX:+UseCompressedOops`）仍有效，用 32 位偏移表示 64 位地址，兼顾内存与性能。
    
- Oracle 官方白皮书明确：Classic VM 用句柄（两层级间接寻址成性能瓶颈），HotSpot 改用直接指针，"提供 C 速度级别的实例变量访问"。
    

**洞见（第一性原理）**：HotSpot 选择直接指针，本质是**"用 GC 的复杂度（移动对象时更新所有引用）换取访问路径的性能"**——因为对象访问在 Java 中**极其频繁**，积少成多，一次额外寻址的开销会非常可观。这再次体现了 JVM 设计的**权衡辩证法**：**把复杂度留给基础设施（GC），把性能留给高频路径（业务代码）**。理解这种"为高频路径牺牲低频路径"的取舍思维，比记住结论更重要。

### 2.4 实战：OutOfMemoryError 异常 —— 四类"事故现场"的复盘

这一节是"理论落地"的关键：针对 2.2 的每类区域，逐一**用代码复现 OOM 并给出诊断思路**。下面按"现象 → 复现/原因 → 诊断 → 解决"梳理（结合书中与现行 JDK 实践补正）：

#### 2.4.1 Java 堆溢出（`Java heap space`）

- **现象**：`java.lang.OutOfMemoryError: Java heap space`。
    
- **原因**：对象分配无法满足——**内存泄漏**（静态集合持有对象引用、未关闭资源、监听器未注销、ThreadLocal 未 remove）或**数据量超堆容量**（一次性查大量数据未分页）。
    
- **诊断**：`-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/var/log/heapdump.hprof` 自动生成堆转储，用 **Eclipse MAT / VisualVM / JProfiler**​ 分析泄漏嫌疑、支配树、引用链。
    
- **解决**：合理调大 `-Xmx`/`-Xms`；用 **Caffeine/Guava Cache/Redis**​ 等带过期策略的缓存替代无界 `HashMap`；数据库查询加分页（MyBatis PageHelper），大对象拆分、流式处理。
    

#### 2.4.2 虚拟机栈和本地方法栈溢出

HotSpot **不区分**虚拟机栈与本地方法栈（`-Xoss` 无效），栈容量仅由 `-Xss` 控制（64 位 Linux 默认约 1MB）。两类异常：

- **`StackOverflowError`**：线程请求栈深度超过允许值——**无限递归/递归过深**，或方法内定义超大局部变量数组使栈帧过大。有清晰错误堆栈，**易定位**。
    
- **`OutOfMemoryError: unable to create new native thread`**：创建线程时因**物理内存/ulimit/容器内存不足**无法分配栈内存。
    
- **注意**：HotSpot **不支持栈动态扩展**，故线程运行期不会因"扩展栈"而 OOM，只在**创建线程申请内存时**可能因内存不足而 OOM。
    
- **解决**：检查递归终止条件、用循环替代深递归；谨慎调大 `-Xss`（过大会减少可创建线程数）；容器/微服务场景注意 `-Xss` 与线程数的平衡。
    

#### 2.4.3 方法区和运行时常量池溢出

- **方法区溢出（`Metaspace` / 旧版 `PermGen space`）**：**动态生成大量类**——CGLIB 动态代理、ASM 字节码生成、频繁热部署、OSGi/JSP 编译等，类加载器无法回收导致元空间膨胀。现象：`java.lang.OutOfMemoryError: Metaspace`。
    
    - **诊断**：`jstat -gcmetacapacity <pid>` 监控 Metaspace 容量/使用量/峰值；`jmap -clstats <pid>` 查看已加载类数量与类加载器，定位异常类加载器。
        
    - **解决**：限制动态类生成、复用代理类；合理配置 `-XX:MetaspaceSize=128m -XX:MaxMetaspaceSize=256m`（避免无限制增长）。
        
    
- **运行时常量池溢出**：JDK 6 及以前常量池在永久代，可用 `-XX:PermSize`/`-XX:MaxPermSize` 限制并复现（如 `while` 死循环调 `String.intern()`）；**JDK 7 后字符串常量池移至堆中**，同样代码不再触发 PermGen 溢出。
    
    - **洞见**：`String.intern()` 在 JDK 6 会把首次遇到的字符串**拷贝进永久代常量池**，JDK 7+ 则只在堆中记录引用——这一行为差异是"常量池迁移"最直接的体现。
        
    

#### 2.4.4 本机直接内存溢出（`Direct buffer memory`）

- **现象**：`java.lang.OutOfMemoryError: Direct buffer memory`。
    
- **原因**：NIO/Netty 等通过 `ByteBuffer.allocateDirect()` 分配大量直接内存且未及时释放；`-XX:MaxDirectMemorySize` 设置过小或未限制。
    
- **典型坑（"影子杀手"）**：Direct Buffer 不归 JVM 堆管，**堆监控正常但物理内存被吃光**，传统堆工具难以发现。
    
- **解决**：调大 `-XX:MaxDirectMemorySize`；Netty 使用 **PooledByteBufAllocator**​ 并限制缓冲区上限；确保 DirectByteBuffer 不再被引用以便 Cleaner 回收。
    

**通用诊断工具箱（工业级排查清单）**：

- 开堆转储：`-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=...`
    
- 看 GC 日志：`-Xlog:gc*:file=gc.log:time,uptime,level,tags`（JDK9+）
    
- 监控指标：堆使用率、Full GC 频率（正常几小时一次，若每分钟多次则堆不足/老年代碎片多）、GC 耗时（Young GC <100ms、Full GC <1s 为佳）
    
- 容器化部署：用 Prometheus + Grafana 监控堆/线程数/GC 暂停，配合 Kubernetes 告警
    

### 2.5 本章小结

## 四、本章核心洞见总结（第一性原理视角，值得反复回看）

1. **区域隔离解决三大矛盾**：线程隔离 vs 共享、自动 GC vs 原生手动管理、规范稳定 vs 运行弹性——这是理解 6 大区域"为什么存在"的钥匙。
    
2. **对象头的隐性成本**：每个对象 12~16 字节头开销，海量小对象场景（如 `Boolean` 包装）头开销会淹没有效数据 → 优先用原生类型特化集合/BitSet。
    
3. **分配方式由收集器决定**：内存分配与 GC 高度协同，二者不是独立模块——这是学 GC 章节的前置认知。
    
4. **PermGen → Metaspace 的演进本质**：按数据生命周期分离存储（类元信息生命周期 ≠ 对象生命周期），把类元信息从受 GC 严格管理的堆中"解放"到本地内存。
    
5. **直接指针的选择 = 权衡辩证法**：用 GC 的复杂度（移动对象更新引用）换取高频访问路径的性能——"把复杂度留给基础设施，把性能留给业务代码"。
    
6. **直接内存是"影子杀手"**：不归堆管、堆监控正常却能吃光物理内存，NIO/Netty 高并发场景务必监控并限制。
