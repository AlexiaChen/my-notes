**我的理解（第一性原理视角）**：这一章真正的"第一性原理"是——**JMM 是一套"为并发正确性提供可证明保证"的规则体系，而不是 JVM 的物理内存划分**。它要解决的不是"数据存在哪"（那是第2章的话题），而是"当一个线程写了变量，另一个线程什么时候、以什么顺序能看到"。围绕这个问题，JMM 给出了三件事：① **抽象结构**（主内存 + 工作内存 + 8 种交互操作）；② **三大特性保障**（原子性、可见性、有序性）；③ **happens-before 原则**（判断"两个操作是否有可见性保证"的唯一法律依据）。**理解 happens-before，就拿到了判断任何并发代码正确性的"试金石"**——这正是本章最该被刻进骨子里的内容。

## 二、逐节精读与洞见

### 12.1 概述 —— 并发的瓶颈在"内存"不在"CPU"

JVM 的并发瓶颈，从来不是 CPU 算力，而是**多线程对共享内存的访问一致性**。一个线程的写入，另一个线程能否看到？以什么顺序看到？这正是 JMM 要回答的问题。

**洞见**：理解"并发问题的本质是内存可见性与有序性问题"，是进入本章的钥匙。很多开发者误以为并发问题只是"多个线程同时执行"——其实**真正麻烦的是"线程间如何通过共享内存通信"**。JMM 就是为这个通信过程制定"交通规则"。

### 12.2 硬件的效率与一致性 —— 为什么需要 JMM

这一节是 JMM 的"动机篇"。现代硬件架构有三个特征，直接导致了"内存可见性"问题：

1. **CPU 多级缓存**：每个核心有 L1/L2 缓存，多核共享 L3 和主存。线程 A 在 Core 1 上修改了变量，值先停留在 Core 1 的 L1 缓存里，线程 B 在 Core 2 上读到的仍是旧值——**这就是"内存不可见"的硬件根源**。
    
2. **写缓冲区（Store Buffer）**：CPU 写入先进写缓冲区，异步刷回缓存/主存。这提升了写入吞吐，但造成了"写操作对其他 CPU 核不可见"的时间窗。
    
3. **指令重排序**：编译器（Javac、JIT）和 CPU 都会为性能对指令重排——只要**单线程语义不变**，重排就是合法的。但多线程下，重排会打破"程序顺序"的预期。
    

**缓存一致性协议（如 MESI）**​ 解决了多核缓存一致性问题，但**无法完全消除写缓冲区的延迟**；而**指令重排序在硬件层无法被完全禁止**（否则性能崩塌）。因此，**JVM 必须在语言层面提供一套"抽象承诺"——无论底层硬件如何重排、无论缓存延迟多大，只要程序员遵守 JMM 规则，并发程序就是正确的**。这就是 JMM 存在的根本理由。

**洞见（第一性原理）**：JMM 是**"硬件复杂性的抽象屏蔽层"**——它把"CPU 缓存、写缓冲、指令重排"这些底层细节，抽象为"主内存 + 工作内存 + happens-before"这套简单模型。**程序员只需要理解 JMM，不需要理解 MESI、Store Buffer、Memory Barrier**——这是 Java "Write Once, Run Anywhere" 在并发领域的延伸：**"Correct Once, Correct Everywhere"**。

### 12.3 Java 内存模型（JMM）—— 并发正确性的"宪法"

#### 12.3.1 主内存与工作内存

**JMM 的抽象结构**（务必与第2章的"物理内存区域"严格区分）：

|维度|JMM 抽象|第2章物理内存|
|---|---|---|
|性质|逻辑模型/规则|实际内存区域|
|主内存|所有共享变量（实例字段、静态字段、数组元素）|对应 Java 堆 + 方法区|
|工作内存|线程私有，保存该线程使用的变量副本|对应 CPU 缓存 + 寄存器 + 写缓冲区（抽象）|
|线程间通信|**必须经过主内存**​|物理上通过缓存一致性协议|

**关键规则**：

- 线程对变量的所有操作（读/写）都必须在**工作内存**中进行，**不能直接读写主内存**；
    
- 不同线程之间无法直接访问对方的工作内存；
    
- 线程间通信必须经过两步：线程 A 把工作内存中修改的变量**刷新到主内存**​ → 线程 B 从**主内存读取最新值到自己的工作内存**。
    

**洞见**：JMM 的"主内存/工作内存"是**纯粹的逻辑抽象**——工作内存并不是 JVM 里某一块真实存在的内存区域，而是涵盖了 CPU 缓存、写缓冲区、寄存器的统称 。理解这一点，就不会把 JMM 和第2章的"Java 堆/栈"混淆。

#### 12.3.2 内存间交互操作 —— 8 种原子操作

JMM 定义了 8 种原子操作，完成主内存与工作内存之间的变量交互 ：

|操作|作用域|语义|
|---|---|---|
|**lock**（锁定）|主内存|把变量标识为某线程独占|
|**unlock**（解锁）|主内存|释放锁定状态的变量|
|**read**（读取）|主内存|把变量值从主内存传输到工作内存|
|**load**（载入）|工作内存|把 read 得到的值放入工作内存的变量副本|
|**use**（使用）|工作内存|把变量值传给执行引擎（执行字节码指令时）|
|**assign**（赋值）|工作内存|把执行引擎返回的值赋给工作内存的变量|
|**store**（存储）|工作内存|把工作内存的变量值传到主内存|
|**write**（写入）|主内存|把 store 传输的值写入主内存变量|

**执行规则**（核心约束）：

- read 和 load 必须**成对出现**；store 和 write 必须**成对出现**；
    
- 不允许线程无原因（无 assign）将工作内存数据同步到主内存；
    
- 一个变量同一时刻只能被一个线程 lock；lock 操作可以多次，需相同次数 unlock 才能释放；
    
- 对一个变量执行 unlock 前，**必须先 store + write**，把修改同步回主内存。
    

**洞见**：这 8 种操作是 JMM 的"汇编语言"——happens-before 原则、volatile 语义、synchronized 语义，最终都翻译为这 8 种操作的执行顺序约束。理解这 8 种操作，就看懂了 JMM 的"指令集"。

#### 12.3.3 volatile 型变量的特殊规则

`volatile` 是 JMM 提供的**最轻量级的同步机制**，具备两大语义（JSR-133 强化后）：

**① 可见性**：对一个 volatile 变量的写，立即刷新到主内存；对一个 volatile 变量的读，强制从主内存获取（使本线程工作内存中的副本失效）。

**② 有序性（通过内存屏障实现）**：JSR-133 规定了 4 类内存屏障，插入在 volatile 读写前后 ：

- **volatile 写**：写操作前插入 `StoreStore` 屏障（防止前面的写被重排到 volatile 写之后）；写操作后插入 `StoreLoad` 屏障（防止后面的读被重排到 volatile 写之前）；
    
- **volatile 读**：读操作后插入 `LoadLoad` 屏障（防止后面的普通读被重排到 volatile 读之前）；读操作后插入 `LoadStore` 屏障（防止后面的写被重排到 volatile 读之前）。
    

**③ 不保证原子性**：`volatile int i; i++;` 仍然不是原子操作——i++ 是"读-改-写"三步复合操作，volatile 只保证单次读或单次写的原子性，不保证复合操作的原子性。

**volatile 的典型适用场景**​ ：

- **状态标志位**（如 `volatile boolean shutdown`）：一个线程写、多个线程读；
    
- **安全发布不可变对象**：通过 volatile 引用发布不可变对象；
    
- **双重检查锁定（DCL）单例**：`instance` 必须声明为 volatile（JSR-133 修复了 DCL 的 bug）；
    
- **部分无锁算法**：基于 volatile + CAS 的乐观锁。
    

**洞见（第一性原理 + 工业联系）**：

1. **volatile 的本质是"轻量级 happens-before 载体"**：对一个 volatile 变量的写 happens-before 后续对该变量的读 。这意味着——volatile 写之前的**所有**普通变量写操作，都对后续 volatile 读的线程可见。**这是 volatile 能够实现"线程间通信"的根本原因**，也是 DCL 单例能被正确修复的关键。
    
2. **为什么 volatile 不能替代锁**：因为 volatile 不保证原子性。任何"读-改-写"或"检查再执行"的复合操作，仅靠 volatile 都不安全——必须用 `synchronized`、`Lock` 或 `Atomic*` 类。
    
3. **工业现实警示**：曾有金融交易平台的 `boolean shutdown` 标志未声明为 volatile，导致后台线程永远看不到主线程的修改，CPU 100% 服务假死 。这是生产环境中真实发生的、因遗漏 volatile 导致的严重故障。**任何被多线程读写的"开关型"变量，必须声明为 volatile**。
    
4. **JDK 9+ 的 VarHandle**：提供了比 volatile 更细粒度的内存语义控制（acquire/release/opaque 等模式），是高性能并发编程的新利器。
    

#### 12.3.4 long 和 double 型变量的特殊规则

**非原子协定**：JVM 规范允许把 **64 位的 long 和 double 读写操作拆分为两个 32 位操作**来执行 。这意味着在 32 位 JVM 上，一个线程可能读到"旧的高 32 位 + 新的低 32 位"这种非法中间态（术语叫"字分裂/Word Tearing"）。

**JSR-133（JDK 5）后的强化**：

- **对于任意 volatile 修饰的 long/double 变量，读写必须是原子的**；
    
- 对于非 volatile 的 long/double，JVM 实现**可以选择**是否保证原子性（绝大多数现代 JVM 实现实际上保证了原子性，但规范未强制）。
    

**工业实践**：在 32 位 JVM 环境下，若多线程共享 long/double 变量且无同步，强烈建议声明为 volatile 以确保原子性。现代 64 位 JVM 上此问题已基本消失，但作为防御性编程，共享的 long/double 仍推荐 volatile 或 synchronized。

#### 12.3.5 原子性、可见性与有序性 —— 并发三要素

这是 JMM 的"三大保障目标"：

|特性|含义|保障机制|
|---|---|---|
|**原子性**​|一个操作不可中断，要么全部执行，要么都不执行|基本类型的读写（除 long/double 非 volatile 外）天然原子；更大范围的原子性靠 `synchronized`、`Lock`、`Atomic*`|
|**可见性**​|一个线程的修改对其他线程立即可见|`volatile`、`synchronized`、`final`、`Lock`|
|**有序性**​|程序执行顺序符合预期，不被重排序破坏|`volatile`（禁止特定重排）、`synchronized`（串行化临界区）、happens-before 规则|

**关键认知**：

- **`synchronized` 是"全能选手"**：同时保证原子性、可见性、有序性——但代价是重量级（尽管 JDK 6 后做了大量锁优化，见第13章）；
    
- **`volatile` 是"轻量级专家"**：只保证可见性 + 有序性，**不保证原子性**；
    
- **`final` 字段的特殊语义**：JSR-133 规定，构造函数中对 final 字段的写入，禁止与"this 引用逃逸"重排序，从而保证对象的安全发布（构造完成前 this 不会逸出）。
    

**洞见**：理解"并发三要素"与"同步原语的保障范围"的对应关系，是正确选择并发工具的基础。**能用 volatile 解决的，绝不用 synchronized；必须用锁的，选对锁的粒度**。这是并发性能优化的第一原则。

#### 12.3.6 先行发生原则（happens-before）—— JMM 的"宪法"

**happens-before 的定义**：如果操作 A happens-before 操作 B，那么 A 的执行结果对 B **可见**，且 A 的执行顺序**排在**​ B 之前 。

**JMM 中的 8 条 happens-before 规则**：

1. **程序次序规则**：单线程内，按控制流顺序，前面的操作 happens-before 后面的操作；
    
2. **管程锁定规则**：`unlock` 操作 happens-before 后续对同一锁的 `lock` 操作；
    
3. **volatile 变量规则**：对 volatile 变量的写 happens-before 后续对该变量的读；
    
4. **线程启动规则**：`Thread.start()` 调用 happens-before 该线程的任何操作；
    
5. **线程终止规则**：线程中的所有操作 happens-before 其他线程检测到该线程终止（如 `join()` 返回）；
    
6. **线程中断规则**：`interrupt()` 调用 happens-before 被中断线程检测到中断事件；
    
7. **对象终结规则**：对象构造函数执行结束 happens-before 它的 `finalize()` 方法开始；
    
8. **传递性**：若 A happens-before B，且 B happens-before C，则 A happens-before C。
    

**happens-before 的工业价值**：**它是判断"两个操作之间是否有可见性保证"的唯一法律依据**。当我们写并发代码时，不需要记忆"volatile 插入了什么内存屏障"，只需要问——**"这两个操作之间，是否存在一条 happens-before 链？"**​ 如果存在，代码就是正确的；如果不存在，就可能有并发 bug。

**经典示例（DCL 单例）**：

```
class Singleton {
    private static volatile Singleton instance;  // 必须 volatile
    
    public static Singleton getInstance() {
        if (instance == null) {                    // 第一次检查
            synchronized (Singleton.class) {
                if (instance == null) {            // 第二次检查
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
```

**为什么 `instance` 必须 volatile？**​ 因为 `instance = new Singleton()` 在字节码层面是三步：① 分配内存；② 初始化对象；③ 将 `instance` 指向内存地址。JIT 可能重排为 ①③②。若无 volatile，线程 A 执行到 ①③ 后，`instance` 非空但未初始化，线程 B 在第一次检查时看到 `instance != null`，直接返回一个**未初始化完成的对象**​ → 灾难。volatile 的 `StoreStore` 屏障禁止了这种重排，保证了"初始化完成" happens-before "instance 被赋值"。

**洞见（第一性原理 + 创新判断）**：

1. **happens-before 是 JMM 的"宪法"**——它把复杂的"内存屏障、缓存一致性、指令重排"等底层细节，抽象为程序员可推理的"偏序关系"。**判断并发代码正确性的标准流程**：① 列出所有共享变量的读写操作；② 检查每对"写-读"操作之间是否存在 happens-before 关系；③ 若存在，则正确；若不存在，则需加 volatile/synchronized/锁。
    
2. **happens-before 不是"时间先后"，而是"可见性保证"**：两个操作在时间上 A 先于 B 发生，并不代表 A happens-before B——必须有上述 8 条规则之一作为法律依据。这是 most developers 最容易混淆的点。
    
3. **JSR-133 是 Java 并发的"里程碑"**：JDK 5 之前，JMM 定义模糊，DCL 单例、安全发布等经典模式都无法正确工作。JSR-133 通过强化 happens-before 规则和 volatile 语义，**一举奠定了现代 Java 并发编程的基石**​ 。`java.util.concurrent` 包（JDK 5 引入）正是建立在 JSR-133 的坚实基础之上。
    
4. **工业联系**：理解 happens-before，能让你读懂 `java.util.concurrent` 中任意并发工具的实现原理。例如 `CountDownLatch` 的 `countDown()` 与 `await()` 之间的可见性保证，本质就是 happens-before 规则的应用；`ConcurrentHashMap` 的分段锁、volatile 节点，都是同一原理的工程实现。
    

### 12.4 Java 与线程 —— 线程的"操作系统映射"

#### 12.4.1 线程的实现

**三种线程模型**：

|模型|映射关系|特点|代表|
|---|---|---|---|
|**用户级线程（ULT）**​|多对一（M:1）|JVM 自行调度，轻量，但无法利用多核，一个线程阻塞则整个进程挂起|JDK 1.2 之前的"绿色线程"|
|**内核级线程（KLT）**​|一对一（1:1）|每个 Java 线程对应一个 OS 线程，由 OS 调度，可利用多核，但创建/切换开销大|**现代 HotSpot（JDK 1.2+）**​|
|**混合模型**​|多对多（M:N）|用户态线程映射到少量内核线程，兼顾轻量与多核|Go goroutine、JDK 19+ 虚拟线程|

**现代 HotSpot 的 1:1 模型**：

- `new Thread()` 只是在 JVM 堆上创建一个 Java 对象，**不创建 OS 线程**；
    
- 调用 `start()` 时，通过 JNI 调用 `JVM_StartThread` → `os::create_thread()` → `pthread_create()`（Linux）或 `CreateThread()`（Windows）；
    
- HotSpot 内部用 **`JavaThread`**​ 抽象 Java 层线程（含线程状态、栈信息、中断状态），用 **`OSThread`**​ 抽象 OS 内核线程（含内核线程句柄、优先级），二者**一一对应**；
    
- 线程调度完全由 OS 内核负责，JVM 不参与调度决策。
    

**洞见（第一性原理 + 工业联系）**：

1. **1:1 模型的"双刃剑"**：优点是真正并行、可利用多核、单个线程阻塞不影响其他线程；缺点是**线程创建/销毁/切换成本高**（每次上下文切换 1-5 微秒，线程切换开销占总 CPU 的 15%-25%）。这解释了为什么"线程池"在 Java 中是必备基础设施——**线程的创建成本太高，必须复用**。
    
2. **虚拟线程（Project Loom，JDK 21 正式）**：JDK 19 引入的虚拟线程采用 M:N 混合模型——成千上万个虚拟线程映射到少量 OS 线程（carrier thread）上，由 JVM 调度。虚拟线程的创建成本极低（几 KB 栈），可以"一个任务一个线程"地编写高并发代码，而无需担心线程数量爆炸。**这是 Java 并发模型自 1.2 以来最大的革新**，标志着 Java 从"1:1 内核线程时代"迈入"M:N 虚拟线程时代"。
    
3. **工业联系**：理解 1:1 模型的局限性，是理解"为什么 Netty 要用 EventLoop + 少量线程处理上万连接"的关键——因为 OS 线程昂贵，必须用"少量线程 + 异步非阻塞"模式榨干每个线程的算力。虚拟线程的出现，将从根本上改变这种编程范式。
    

#### 12.4.2 Java 线程调度

**调度模型**：现代 HotSpot 采用**抢占式调度**（Preemptive Scheduling）——线程调度完全由 OS 内核负责，JVM 不参与决策 。

**调度机制**：

- OS 采用**时间片轮转**策略，为每个就绪线程分配 CPU 时间片；
    
- 时间片用完后触发上下文切换，CPU 切换到其他就绪线程；
    
- 线程优先级（`Thread.setPriority()`）仅作为**提示**给 OS，实际调度仍由 OS 决定——**Java 线程优先级不可靠**，不应作为并发正确性的依赖。
    

**洞见**：Java 线程调度的"黑盒性"是工业实践的重要认知——**不要依赖线程优先级来保证并发正确性**。优先级在不同 OS 上的映射不一致（Solaris 有 2^31 级优先级，Windows 只有 7 级，Linux 忽略优先级），且 OS 调度器可能完全无视它。并发正确性必须靠"同步机制"（volatile/synchronized/锁）保证，而非靠调度时序。

#### 12.4.3 状态转换 —— 6 种状态的状态机

Java 线程在整个生命周期中会处于以下 **6 种状态之一**（定义在 `Thread.State` 枚举）：

```
NEW
         │ start()
         ↓
    ┌─ RUNNABLE ─────────────────────────────┐
    │    ↑                                    │
    │    │                                    │
    │ 获得锁                              时间到/notify()
    │    │                                    │
    │    ↓                                    ↓
    │  BLOCKED                            WAITING
    │                                     │
    │                              TIMED_WAITING
    │                                     │
    └─────────────────────────────────────┘
         │ run() 结束
         ↓
     TERMINATED
```

**6 种状态的精确语义**：

|状态|触发条件|对应 OS 线程状态|
|---|---|---|
|**NEW**​|已创建 Thread 对象，未调用 start()|无对应 OS 线程|
|**RUNNABLE**​|调用 start() 后，包含"就绪"和"运行中"两种子状态|就绪或运行|
|**BLOCKED**​|等待进入 synchronized 临界区（锁竞争）|阻塞|
|**WAITING**​|调用 `Object.wait()` / `Thread.join()` / `LockSupport.park()`|阻塞|
|**TIMED_WAITING**​|调用 `Thread.sleep(long)` / `wait(long)` / `join(long)` / `parkNanos()`|阻塞|
|**TERMINATED**​|run() 执行结束|OS 线程已销毁|

**关键认知**：

- **RUNNABLE 是"复合状态"**：JVM 层面不区分"就绪"和"运行中"——从 OS 看可能是就绪队列中的等待者，也可能是正在 CPU 上执行的线程；
    
- **BLOCKED vs WAITING 的本质区别**：BLOCKED 是"被动阻塞"——等锁释放；WAITING 是"主动挂起"——等特定条件（notify/超时）；
    
- **BLOCKED 只存在于 synchronized 临界区竞争**；使用 `java.util.concurrent.Lock` 的线程在等锁时处于 WAITING/TIMED_WAITING 而非 BLOCKED。
    

**洞见（第一性原理 + 工业联系）**：

1. **线程状态是诊断并发问题的"第一现场"**：通过 `jstack <pid>` 或 `Thread.getState()` 获取线程状态，是排查死锁、活锁、线程饥饿的标准动作。一个健康的高并发应用，**BLOCKED 和 WAITING 线程不应长时间累积**——若 `jstack` 显示大量线程长时间 BLOCKED 在 synchronized 上，说明存在锁竞争热点；若大量线程 WAITING on `LockSupport.park()`，可能是线程池饱和或任务队列积压。
    
2. **工业最佳实践**：生产环境监控线程状态时，**重点关注三类异常**：① 长时间 RUNNABLE 但 CPU 不高的线程（可能在等 I/O 或锁）；② 大量 BLOCKED 线程（锁竞争）；③ 大量 WAITING 线程（线程池配置不合理或下游阻塞）。这是 APM 工具（如 Arthas、Pinpoint）线程诊断的核心逻辑。
    

### 12.5 本章小结

本章完成了四件事：**揭示了 JMM 存在的硬件根源（CPU 缓存、写缓冲、指令重排）**；**定义了 JMM 的抽象结构（主内存/工作内存 + 8 种原子操作）**；**阐明了 volatile 的语义边界（可见性+有序性，非原子）与 happens-before 八大规则**；**讲解了 Java 线程的实现（1:1 内核线程模型）、调度（OS 抢占式）与 6 种状态转换**。它是 Java 并发编程的"宪法"——后续所有并发工具类、锁优化技术、JUC 包的实现，都以 JMM 为法理基础。

## 四、本章核心洞见总结（第一性原理视角，值得反复回看）

1. **JMM 是"硬件复杂性的抽象屏蔽层"**：它把 CPU 缓存、写缓冲、指令重排这些底层细节，抽象为"主内存 + 工作内存 + happens-before"的简单模型。**JMM 是逻辑规则，不是物理内存划分**——工作内存涵盖了 CPU 缓存、写缓冲区、寄存器，并非 JVM 中真实存在的内存区域。
    
2. **并发问题的本质是"内存可见性与有序性"**：瓶颈不在 CPU 算力，而在多线程对共享内存的访问一致性。理解这一点，才能理解为什么需要 volatile、synchronized、happens-before。
    
3. **volatile 是"轻量级 happens-before 载体"**：保证可见性 + 有序性，但**不保证原子性**。"读-改-写"复合操作（如 i++）仅靠 volatile 不安全。典型适用场景：状态标志位、DCL 单例、安全发布不可变对象。
    
4. **happens-before 是 JMM 的"宪法"**：判断两个操作之间是否有可见性保证的唯一法律依据。**判断并发代码正确性的标准流程**——检查两个操作之间是否存在一条 happens-before 链；若存在则正确，若不存在则需加同步。JSR-133（JDK 5）强化了 happens-before 规则和 volatile 语义，奠定了现代 Java 并发编程的基石。
    
5. **long/double 的"非原子协定"**：JVM 规范允许 64 位变量读写拆分为两个 32 位操作；JSR-133 后，**volatile 修饰的 long/double 必须是原子操作**。32 位 JVM 环境下共享 long/double 建议声明 volatile。
    
6. **现代 HotSpot 采用 1:1 内核线程模型**：每个 Java 线程对应一个 OS 线程，调度由 OS 负责。优点是真正并行、可利用多核；缺点是线程创建/切换开销大（每次上下文切换 1-5 微秒，占总 CPU 15%-25%）。这解释了"线程池"在 Java 中为何是必备基础设施。
    
7. **虚拟线程（JDK 21+）是 Java 并发模型的自 1.2 以来最大革新**：M:N 混合模型，成千上万虚拟线程映射到少量 OS 线程，由 JVM 调度。它将从根本上改变"少量线程 + 异步非阻塞"的编程范式。
    
8. **Java 线程调度是 OS 抢占式的，JVM 不参与**：线程优先级仅作为"提示"给 OS，**不可靠**——并发正确性绝不能依赖线程优先级，必须靠同步机制保证。
    
9. **6 种线程状态是诊断并发问题的"第一现场"**：`jstack` 输出的线程状态（RUNNABLE/BLOCKED/WAITING/TIMED_WAITING）是排查死锁、锁竞争、线程池饱和的核心依据。**BLOCKED 只存在于 synchronized 竞争；使用 `java.util.concurrent.Lock` 的线程等锁时处于 WAITING/TIMED_WAITING**。
    
10. **工业最佳实践启示**：
    
    - 能用 volatile 解决的，绝不用 synchronized；
        
    - 任何被多线程读写的"开关型"变量，必须声明 volatile（真实金融故障案例：未声明 volatile 导致服务永久假死）；
        
    - 不依赖线程优先级保证并发正确性；
        
    - 监控线程状态时重点关注：长时间 RUNNABLE 但 CPU 不高（等 I/O 或锁）、大量 BLOCKED（锁竞争热点）、大量 WAITING（线程池不饱和或下游阻塞）；
        
    - 高并发场景优先考虑虚拟线程（JDK 21+）或异步非阻塞模型（Netty EventLoop）。
