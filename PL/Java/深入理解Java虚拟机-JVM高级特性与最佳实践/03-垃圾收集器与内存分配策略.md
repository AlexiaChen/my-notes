**我的理解（第一性原理视角）**：这一章真正的"第一性原理"是——**GC 的本质是一个"在程序运行的同时，安全、高效、低成本地回收无用对象"的并发问题**。它要同时解决三个子问题：① **正确性**（不回收仍被使用的对象，即"可达性分析"）；② **效率**（不能让 STW 停顿拖垮应用，即"分代 + 并发 + 区域化"）；③ **碎片化**（回收后内存要能继续分配大对象，即"复制/整理 vs 标记-清除"的取舍）。后面所有内容，都是围绕这三个子问题展开的**工程权衡**。

## 二、逐节精读与洞见

### 3.1 概述 —— GC 管什么、不管什么

GC 需要回收的内存区域主要是**堆（对象实例/数组）和方法区（废弃常量、无用类）**。其中堆是 GC 的"主战场"（对象朝生夕死、回收频繁），方法区回收频率低、条件苛刻。**例外**：栈和 PC 计数器随线程生灭、天然自动回收，无需 GC 介入。

**洞见**：理解"GC 主要管堆"这一点，后面所有"GC 调优 = 调堆大小/分代比例/收集器"的逻辑就顺理成章了。

### 3.2 对象已死吗 —— "什么是垃圾"的判定艺术

这是全章的**理论地基**，回答了 GC 最根本的问题：如何判断一个对象"已死"可以回收。

#### 3.2.1 引用计数算法（Java **不使用**）

给对象维护一个引用计数器，被引用 +1、引用失效 −1，计数为 0 即回收。**优点**：实现简单、判定高效。**致命缺陷**：**无法解决对象之间相互循环引用**的问题（A↔B 互相引用，但外部已无任何引用，计数却不为 0，永远无法回收）。这也是 Python 等语言使用、而 Java **弃用**此算法的根本原因。

#### 3.2.2 可达性分析算法（Java **真正使用**）

以**一系列"GC Roots"对象为起点**，沿引用链向下搜索，能到达的对象为**存活**，无任何引用链相连的对象为**不可达（垃圾）**。

**GC Roots 的五大来源**（务必记住）：

1. 虚拟机栈（栈帧局部变量表）中引用的对象；
    
2. 本地方法栈中 JNI（Native 方法）引用的对象；
    
3. 方法区中**类静态属性**引用的对象；
    
4. 方法区中**运行时常量池**引用的常量对象；
    
5. 被 `synchronized` 持有锁的对象。
    

**洞见（第一性原理）**：可达性分析的本质是**"从一组确定存活的根出发，做一次有向图遍历"**——它用"根的可达性"替代"引用的计数"，天然规避了循环引用问题。这也是图论思想在 JVM 中的一次经典应用。

#### 3.2.3 再谈引用（JDK 1.2 后：四种引用）

JDK 1.2 把引用细分为四种，**强度由强到弱**，决定了对象"能活多久"：

|引用类型|被回收时机|典型场景|
|---|---|---|
|**强引用**​ `Object o = new Object()`|**永不回收**（宁抛 OOM 也不回收）|普通业务对象|
|**软引用**​ `SoftReference`|**内存不足时**回收（OOM 前二次回收）|内存敏感缓存（图片/商品缓存）|
|**弱引用**​ `WeakReference`|**GC 时立即**回收（无论内存是否充足）|临时缓存、WeakHashMap、监听器自动注销|
|**虚引用**​ `PhantomReference`|不影响生命周期，**仅用于跟踪回收事件**（必须配 ReferenceQueue）|堆外内存释放哨兵（如 NIO DirectByteBuffer 的 Cleaner）|

**洞见 & 工业联系**：四种引用是**"把内存回收的主动权部分交还程序员"**的机制。经典案例：`WeakHashMap` 的 key 用弱引用，当 key 不再被强引用时，下次 GC 会自动移除对应条目——**非常适合做"无副作用的临时缓存/去重映射"**。软引用则是"内存紧张时自动让出空间"的缓存首选。

#### 3.2.4 生存还是死亡（finalize 的"一次自救"机会）

即使可达性分析判定为"不可达"，对象也**不一定立即死亡**——`finalize()` 方法给了它**最后一次"自救"机会**：

1. 第一次标记：可达性分析判定不可达 → 标记；
    
2. 筛选：若对象**覆盖了 `finalize()` 且未执行过**，放入 `F-Queue`，由 JVM 建立的**低优先级 Finalizer 线程**异步执行；
    
3. 自救窗口：在 `finalize()` 中若对象**重新与 GC Roots 建立引用链**（如把自己赋值给某个静态变量），则被移出回收队列、"复活"；
    
4. 第二次标记：若仍不可达，则**真正回收**。
    

**重要约束**：`finalize()` **最多只执行一次**；执行时机不确定、不保证执行完毕；**绝不推荐用它做资源释放**（用 `try-finally` / `AutoCloseable` 替代）。

**洞见**：`finalize()` 的"自救"机制是个**有趣的学术设计，却是工程上的反面教材**——它延迟了回收、拖慢了 GC、且行为不可控。理解它"存在但别用"，是 Java 资源管理成熟的标志。虚引用 + Cleaner 才是现代"对象回收时释放堆外资源"的正确姿势。

#### 3.2.5 回收方法区

方法区（≥JDK8 为 Metaspace）回收频率低，主要回收两类：**废弃常量**和**无用类**。

- 废弃常量：判定逻辑与普通对象类似（无引用即废弃）。
    
- **无用类卸载**需**同时满足三个苛刻条件**：① 该类**所有实例**都已被回收；② 加载该类的 **ClassLoader 已被回收**；③ 该类对应的 **`java.lang.Class` 对象没有任何引用**。
    

**工业联系**：在 **CGLIB 动态代理、频繁热部署、OSGi、JSP 编译**等"大量动态生成类"的场景下，类卸载尤为关键——若 ClassLoader 泄漏，Metaspace 会持续膨胀触发 OOM（见第2章 2.4.3）。

### 3.3 垃圾收集算法 —— 四种"扫地"原语

这是全章算法核心。注意：**前三种是基础算法，第四种"分代收集"是组合策略**。

|算法|流程|优点|缺点|适用区域|
|---|---|---|---|---|
|**标记-清除**（Mark-Sweep）|标记存活对象 → 统一清除未标记对象|实现简单；**不移动对象**（地址稳定）|效率低（两次全堆扫描）；**产生大量不连续碎片**​|老年代（思想偶尔用）|
|**复制**（Copying）|内存分两块，只用一块；GC 时把存活对象复制到另一块，原块整体清空|**无碎片、回收极快**（只复制存活对象）|**内存利用率仅 50%**；存活率高时复制成本高|**新生代**（对象朝生夕死，存活率极低）|
|**标记-整理**（Mark-Compact）|标记存活对象 → 向内存**一端紧凑移动**​ → 清理边界外内存|**无碎片、内存利用率高**​|移动对象成本高（需更新引用）|**老年代**（存活率高、常放大对象）|
|**分代收集**（Generational）|**不是独立算法，而是组合策略**：按对象生命周期分新生代/老年代，各用最合适算法|针对性强、效率高|实现复杂|HotSpot 整体策略|

**关键补正（HotSpot 对复制算法的优化）**：原生复制算法浪费 50% 内存，HotSpot 通过 **Eden:S0:S1 = 8:1:1**​ 的布局，把新生代可用空间提升到 **90%（80%+10%）**，仅 10% 被"浪费"，**完美规避了复制算法内存利用率低的短板**。

**洞见（第一性原理 + 创新判断）**：

1. **"分代"是本章最重要的工程智慧**——它建立在一个经验规律上：**绝大多数对象"朝生夕死"，熬过多次 GC 的对象更可能长期存活**。据此把堆分区、对不同区用不同算法，是"**按数据生命周期分离处理**"思想的又一次胜利（呼应第2章 PermGen→Metaspace 的演进逻辑）。
    
2. **算法没有绝对优劣，只有"对不对得起数据特征"**：新生代用复制（存活率低→复制极少、极快）、老年代用标记-整理（存活率高→复制不划算、又不能忍碎片）。**选算法 = 看数据特征，这是工程取舍的精髓**。
    

### 3.4 HotSpot 的算法实现 —— 理论如何高效落地

这是本章**最能体现 HotSpot 工程功力**的一节：可达性分析和三种算法在纸面上简单，要在"几乎不暂停应用"的前提下高效实现，需要三块精密机制。

#### 3.4.1 枚举根节点（OopMap）

可达性分析需要枚举 GC Roots。若逐个检查方法区常量、静态属性、栈帧局部变量，**方法区就有数百上千 MB，检查时延极高**；且分析期间必须 **STW（Stop-The-World，冻结所有 Java 线程）**以保证一致性。

HotSpot 用一组叫 **OopMap**​ 的数据结构解决：

- **类加载完成时**，HotSpot 计算出"对象内各偏移量上是什么类型的数据"；
    
- **JIT 即时编译过程中**，在**特定位置**记录下栈和寄存器中哪些位置是引用。
    
- GC 扫描时**直接读取 OopMap 即可定位引用**，无需遍历整个方法区/栈帧。
    

#### 3.4.2 安全点（Safepoint）

**不可能为每条指令都生成 OopMap**（空间成本无法接受），故只在**特定位置——安全点**生成。程序**只有到达安全点才能暂停**进入 GC。

- **安全点位置**（具有"让程序长时间执行"特征的指令序列复用处）：方法调用后、循环末尾、可能抛异常的位置。
    
- **安全点密度权衡**：太少→GC 等待过长、STW 延迟不可控；太多→OopMap 数据膨胀、轮询开销大。
    
- **如何让线程主动到安全点暂停**：HotSpot 采用**主动式中断**——在安全点处设置全局中断标志，线程执行中**不断轮询该标志**，为真则挂起自己；底层用**内存保护陷阱**实现（需暂停时把轮询指令所在内存页设为不可访问，线程访问即触发自陷异常，在异常处理器中挂起）。**抢先式中断**（中断所有线程、不在安全点就恢复跑到安全点）几乎无 JVM 采用。
    

#### 3.4.3 安全区域（Safe Region）

安全点解决不了**休眠/阻塞线程**（sleep/blocked/wait 状态，不占用 CPU、无法主动跑到安全点轮询标志）。

**安全区域**：一段**引用关系不会发生变化**的代码区间（如 `Object.wait()`、`Thread.sleep()`、`LockSupport.park()`、I/O 阻塞入口）。线程**进入时打上"位于安全区"标识**，GC 可忽略它们；**准备离开时检查 GC 是否完成**，未完成则等待信号、完成则正常离开。**本质**：安全区域是安全点在"静止态"下的延伸，两者共同保障所有线程在 STW 时都处于可预测、无副作用的状态。

**洞见（第一性原理）**：OopMap + 安全点 + 安全区域这三件套，共同解决了"**如何在几乎不暂停应用的前提下，快速、准确、一致地完成根枚举**"这一核心难题。**安全点/安全区域不是开发者可配置的参数，而是 HotSpot 在编译期和运行期自动注入的机制**——理解它们的存在，能帮你解释很多"诡异"现象（如线程为何在特定位置才响应 GC、为何 sleep 中的线程不影响 GC）。

### 3.5 垃圾收集器 —— HotSpot 七大收集器选型指南

这是全章**最贴近线上调优**的一节。HotSpot 提供七种收集器，**没有"万能最优"，只有"对场景最合适"**。按"新生代/老年代"两两搭配理解更清晰：

|收集器|作用代|线程模型|算法|核心特点|启用参数|
|---|---|---|---|---|---|
|**Serial**​|新生代|单线程|复制|简单高效、STW 较长；Client 模式/单 CPU/嵌入式首选|`-XX:+UseSerialGC`|
|**ParNew**​|新生代|多线程并行|复制|Serial 的多线程版；**唯一能与 CMS 配合**的新生代收集器|`-XX:+UseParNewGC`|
|**Parallel Scavenge**​|新生代|多线程并行|复制|**关注吞吐量**（吞吐 = 用户代码时间/(用户+GC时间)），可设吞吐目标|`-XX:+UseParallelGC`（JDK8 默认）|
|**Serial Old**​|老年代|单线程|标记-整理|Client 模式老年代默认；**CMS 失败时的"后备方案"（Concurrent Mode Failure）**|随 SerialGC 自动启用|
|**Parallel Old**​|老年代|多线程并行|标记-整理|Parallel Scavenge 的老年代搭档，构成"吞吐量优先"组合|`-XX:+UseParallelOldGC`|
|**CMS**​|老年代|并发（与用户线程）|标记-清除|**低延迟优先**；并发收集、响应快；**会产生内存碎片**​|`-XX:+UseConcMarkSweepGC`（JDK9 废弃、JDK14 移除）|
|**G1**​|整堆|多线程/并发|区域化复制+整理|**可预测停顿模型**；Region 化堆布局；**JDK9+ 默认收集器**​|`-XX:+UseG1GC`|

**CMS 的四阶段（理解低延迟的关键）**：

1. **初始标记**（STW，极快）：标记 GC Roots **直接引用**的对象；
    
2. **并发标记**（并发）：从根对象遍历整个对象图，与用户线程并发；
    
3. **重新标记**（STW，较短）：修正并发期间因引用变化导致的漏标（用**增量更新**写屏障，记录新增引用到 mod-union table）；
    
4. **并发清除**（并发）：清除未标记对象（**标记-清除，不整理→产生碎片**）。
    

**CMS 缺陷**：内存碎片（可能触发 Full GC）、CPU 资源敏感（并发阶段争抢 CPU）、浮动垃圾、Concurrent Mode Failure 风险（老年代填满时降级为 Serial Old 做 Full GC，停顿剧增）。**已废弃，不推荐新项目使用**。

**G1 的核心设计（Garbage-First，"垃圾优先"）**：

- **Region 化堆布局**：把堆划分为约 **2048 个大小相等的 Region**（1MB~32MB，2 的幂），每个 Region 可**动态扮演 Eden/Survivor/Old/Humongous**​ 四种角色（**无物理分代，只有逻辑分代**）；超过 Region 50% 的大对象直接分配到 **Humongous Region**。
    
- **RSet（记忆集）+ CSet（回收集合）**：RSet 记录"谁引用了我"（避免全堆扫描），CSet 是本次要回收的 Region 集合（Mixed GC 除全部 Young Region 外，还含垃圾占比最高的部分 Old Region）。
    
- **SATB（初始快照）算法**：并发标记用写屏障在引用断裂前把旧值记录到 SATB 队列，remark 阶段重新扫描"曾经被引用过的对象"，效率高于 CMS 的增量更新。
    
- **四阶段**：初始标记（STW，设 TAMS 指针确保并发期新对象不干扰标记）→ 并发标记（SATB）→ 最终标记（STW，处理 SATB 缓冲）→ 筛选回收/Evacuation（STW，按"回收价值"排序、复制整理，停顿可控）。
    

**G1 关键参数**：`-XX:MaxGCPauseMillis=200`（目标最大停顿，默认 200ms）、`-XX:InitiatingHeapOccupancyPercent=45`（触发并发标记周期的堆占用阈值，默认 45%）、`-XX:G1HeapRegionSize`（Region 大小）。

**洞见（第一性原理 + 创新判断 + 工业联系）**：

1. **收集器演进的主线是从"吞吐优先"走向"延迟可控"再走向"超大堆"**：`Serial → Parallel(吞吐) → CMS(低延迟) → G1(可预测停顿+大堆) → ZGC(染色指针+亚毫秒停顿+TB 级堆)`。这是"**硬件内存越来越大、业务对延迟越来越敏感**"驱动的必然演进。
    
2. **G1 的"Garbage First"思想是革命性的**：传统收集器"先扫哪块由分代固定决定"，G1 则"**优先扫垃圾最多的 Region，性价比最大化**"——这是把"回收决策"从"空间维度"升级到"价值维度"的一次跃迁。
    
3. **工业选型建议**：Web 服务/后端默认用 **G1**（`-XX:+UseG1GC`）；堆 > 4GB、对延迟敏感（如金融交易、实时推荐）考虑 **ZGC**（`-XX:+UseZGC`，JDK15 转正，亚毫秒停顿、支持 TB 级堆）；小内存/嵌入式用 Serial；**CMS 已过时，新项目勿用**。调优黄金原则：**先优化代码（减少对象分配速率）> 分配合适堆大小 > 再调收集器参数**。
    

#### 3.5.8 理解 GC 日志 & 3.5.9 参数总结（实用速查）

**开启 GC 日志**：

- JDK8 及更早：`-Xloggc:/path/to/gc.log -XX:+PrintGCDetails -XX:+PrintGCDateStamps`
    
- JDK9+ 推荐：`-Xlog:gc*:file=/path/to/gc.log:time,uptime,level,tags`（可加 `:filecount=10,filesize=100M` 做日志轮转）
    

**不同收集器日志标识对比**（诊断必备）：

|GC 类型|Young GC 标识|Full/Mixed GC 标识|关键字段|
|---|---|---|---|
|Serial / Parallel|`[GC`|`[Full GC`|`PSYoungGen`、`ParOldGen`、`Heap before/after GC`|
|CMS|`[GC`|`[Full GC (System)`|`CMS-initial-mark`、`CMS-concurrent-mark`|
|G1|`[GC pause (G1 Evacuation Pause) (young)`|`[Full GC` / `[GC Pause (G1 Mixed GC)`|`G1HeapRegion`、`Eden:`、`Survivor:`|
|ZGC (JDK11+)|`[Garbage Collection`|`[Garbage Collection (Full)`|`ZGC Phase`、`Relocated`|

**日志核心指标**：GC 事件类型、堆内存变化（`Heap: 1024M->256M(2048M)`）、停顿时间（`[Times: user=0.02 sys=0.00, real=0.02 secs]`）、GC 频率。**诊断口诀**：频繁 Minor GC → 新生代过小或对象分配速率过高；频繁 Full GC → 老年代不足或对象过早晋升；长时间停顿 → 考虑切换 G1/ZGC 并设 `MaxGCPauseMillis`。

### 3.6 内存分配与回收策略 —— 对象的"人生轨迹"

这一节把"堆内存如何分配"讲透，是理解 GC 日志中"对象为何晋升、何时 Full GC"的关键。

#### 3.6.1 对象优先在 Eden 分配

大多数对象在新生代 **Eden 区**分配。Eden 没有足够空间时，触发一次 **Minor GC（新生代 GC）**。Minor GC 非常频繁、回收速度较快（因新生代对象朝生夕死）。

- **TLAB（Thread Local Allocation Buffer）**：为解决多线程并发在 Eden 分配的内存竞争，JVM 为每个线程在 Eden 预分配一小块**私有缓冲区**（默认约占 Eden 的 1%，可通过 `-XX:TLABSize` 调整）。线程创建对象**优先在自己的 TLAB 无锁分配**；TLAB 用完或对象过大才走共享 Eden 的 CAS/加锁分配。**所有 OpenJDK 衍生 JVM 都提供 TLAB**（`-XX:+UseTLAB`，默认开启）。
    

**洞见**：TLAB 是"**用空间局部性换无锁并发**"的经典案例——每个线程一小块私有 Eden，把"全局竞争"降级为"线程本地操作"，极大提升分配吞吐。

#### 3.6.2 大对象直接进入老年代

超过 `-XX:PretenureSizeThreshold`（单位字节）的大对象（长字符串、大数组）**直接在老年代分配**，避免在新生代 Eden↔Survivor 之间来回复制、降低效率。**注意**：该参数**仅对 Serial 和 ParNew 有效，对 Parallel Scavenge 无效**。

**工业联系**：G1 中超过 **Region 大小 50%**​ 的对象直接分配到 **Humongous Region**（逻辑上属老年代），避免大对象在新生代反复复制触发过早 Minor GC。

#### 3.6.3 长期存活的对象将进入老年代

每个对象有**年龄计数器**（存在对象头的分代年龄字段，4 位 → **最大 15**）。Eden 出生、经历第一次 Minor GC 后仍存活并被 Survivor 容纳 → 移入 Survivor、年龄设为 1；之后**每熬过一次 Minor GC 年龄 +1**；达到 `-XX:MaxTenuringThreshold`（**默认 15**）时晋升老年代。

#### 3.6.4 动态对象年龄判定

**不必等到年龄达阈值才晋升**：若 Survivor 中**同年龄所有对象大小总和 > Survivor 空间的一半**，则**年龄 ≥ 该年龄的对象直接进入老年代**。HotSpot 按年龄从小到大累加对象大小，超过 Survivor 50% 时，把该批对象的**最大年龄作为新的晋升阈值**。

**洞见**：动态年龄判定是"**自适应**"思想的体现——JVM 根据当前 Survivor 中对象的年龄分布**动态调整晋升节奏**，避免因固定阈值导致 Survivor 溢出或对象过早/过晚晋升，更好适应程序实际内存使用模式。

#### 3.6.5 空间分配担保

Minor GC 前，JVM 会检查老年代是否有足够空间容纳可能晋升的对象：

- 若老年代**最大可用连续空间 > 新生代所有对象总空间**​ → Minor GC 安全；
    
- 若不满足，检查 `-XX:HandlePromotionFailure`（JDK7 后**已废弃、固定为允许**）：允许时继续判断老年代最大可用连续空间是否 **> 历次晋升到老年代对象的平均大小**​ → 大于则尝试（有风险的）Minor GC，小于则先 Full GC；不允许则直接 Full GC。
    

**担保失败的代价**：原本几十毫秒的 Minor GC 可能变成几百毫秒甚至秒级的 Full GC，**性能剧烈抖动**。担保机制是 JVM 的"**保险丝**"而非性能瓶颈——它保证 Minor GC 大概率安全，失败时再用 Full GC 兜底。

**通用堆参数速查**：`-Xms`/`-Xmx`（初始/最大堆，建议设为相同值避免运行时扩容）、`-Xmn`（新生代大小）、`-XX:NewRatio=2`（老年代:新生代=2:1）、`-XX:SurvivorRatio=8`（Eden:Survivor=8:1）、`-XX:MaxTenuringThreshold=15`。

## 四、本章核心洞见总结（第一性原理视角，值得反复回看）

1. **GC 的本质是"并发环境下安全、高效、低成本回收内存"**，要同时解决正确性（可达性分析）、效率（分代+并发+区域化）、碎片化（复制/整理 vs 标记-清除）三个子问题。
    
2. **可达性分析用"根的可达性"替代"引用计数"，天然规避循环引用**——图论在 JVM 中的经典应用。
    
3. **分代收集是"按数据生命周期分离处理"的胜利**：新生代用复制（存活率低→复制极少）、老年代用标记-整理（存活率高→复制不划算、又不能忍碎片）。
    
4. **HotSpot 高效落地的三件套**：OopMap（快速枚举根）+ 安全点（活跃线程可控暂停）+ 安全区域（静止态线程兜底），共同把 STW 代价压到最低。
    
5. **收集器演进主线**：吞吐（Parallel）→ 低延迟（CMS）→ 可预测停顿+大堆（G1）→ 亚毫秒+TB 堆（ZGC）；**G1 的"Garbage First"把回收决策从"空间维度"升级到"价值维度"**。
    
6. **对象晋升的五条路径**：年龄达阈值(默认15) / 动态年龄判定(Survivor 同龄对象>50%) / Survivor 空间不足 / 大对象(Humongous) / 空间分配担保失败→Full GC。**理解这五条，就读懂了 GC 日志里"对象为何晋升、何时 Full GC"**。
