**我的理解（第一性原理视角）**：这一章真正的"第一性原理"是——**Javac 的本质是一个"源码 → 抽象语法树 → 字节码"的转换器，它的核心使命是"正确性"和"语言表达力"，而不是"运行期性能"**。这意味着：

- Javac 做**大量的语义检查**（类型、控制流、可达性、异常处理），确保生成的 Class 文件是"语义合法"的；
    
- Javac 做**语法糖的"脱糖"（Desugar）**，把高级语法还原为 JVM 能理解的简单字节码；
    
- Javac **几乎不做运行期性能优化**（循环展开、寄存器分配、公共子表达式消除这些事留给 JIT）；
    
- Javac **开放了注解处理器这个"插件口子"**，让程序员可以在编译期读取/修改/生成代码。
    

**这是 Java 生态"编译期工具链"繁荣的根本原因**——Lombok、MapStruct、AutoService、Immutables、JMH 代码生成、Dagger 2 等一整套"编译期代码生成"生态，全部建立在本章所描述的机制之上。

## 二、逐节精读与洞见

### 10.1 概述 —— "编译期"是个歧义句

周志明开篇就澄清一个关键概念：**Java 世界里说的"编译期"至少有三重含义**：

|编译期类型|输入 → 输出|代表编译器|
|---|---|---|
|**前端编译**​|`.java` → `.class`|Javac、Eclipse ECJ|
|**JIT（运行期编译）**​|字节码 → 本地机器码|HotSpot C1/C2、Graal|
|**AOT（静态提前编译）**​|`.java` 或 `.class` → 本地机器码|Jaotc、GCJ、Excelsior JET|

**本章只讨论第一类——前端编译（Javac）**。

**关键论断（本章最重要的一句话）**：**Javac 对代码的运行效率几乎没有任何优化措施，但它做了许多针对 Java 语言编码过程的优化，来改善程序员的编码风格和提高编码效率**。相当多新生 Java 语法特性，都是靠编译器的"语法糖"来实现的。

**洞见**：这句话颠覆了很多人的认知——大家以为"编译器=优化器"，但 Javac 的定位其实是**"语言特性的翻译器 + 语义守门人"**。真正的性能优化在 JIT（第11章）。理解这一点，你就不会期待"换个 Javac 版本让程序跑快 30%"，而会把性能优化的目光投向 JIT 参数、GC 调优、算法改进。

### 10.2 Javac 编译器 —— 三大阶段、一颗 AST 贯穿始终

周志明把 Javac 编译过程分为**一个准备过程 + 三个处理过程**。但结合 OpenJDK 源码，更精细的内部阶段是 **7 步 Pipeline**：

```
① Parse（词法/语法分析）→ ② Enter（填充符号表）→ ③ Process（注解处理）
                                                      ↑            ↓
                                                 ⑥ Gen（字节码生成）← ⑤ Desugar（解语法糖）
                                                      ↑            ↓
                                                 ④ Attribution（标注/类型检查）←→ Flow（数据流分析）
```

**贯穿所有阶段的核心数据结构是抽象语法树（AST）**——Parse 之后，Javac 就不再碰源码字符流，所有后续操作都在 AST 上进行。

#### 10.2.2 解析与填充符号表

**① 词法分析（Lexical Analysis）**：源代码字符流 → Token 序列。单个字符是程序编写的最小单元，而 **Token 才是编译过程的最小元素**——关键字、变量名、字面量、运算符都是一个 Token。例如 `int a = b + 2` 这句代码包含 6 个 Token：`int`、`a`、`=`、`b`、`+`、`2`。

**② 语法分析（Syntax Analysis）**：根据 Token 序列构造**抽象语法树（AST）**。AST 是一种描述程序代码语法结构的树形表示，每个节点代表一个语法结构（包、类型、修饰符、运算符、接口、返回值、甚至代码注释）。

> 💡 **关键认知**：语法分析后，编译器就**不再对源码文件进行操作**，后续所有动作都建立在 AST 之上。这意味着——**AST 是 Javac 内部统一的"源代码表示"**，注解处理器、语义分析、代码生成全都在 AST 上做文章。

**③ 填充符号表（Enter 阶段）**：符号表是由一组符号地址和符号信息构成的数据结构。Enter 阶段递归扫描 AST，把所有类、接口、方法、字段的符号信息登记到符号表中。

**符号表在编译的不同阶段都要用到**：

- **语义分析阶段**：用于语义检查（如一个名字的使用与原先声明是否一致）；
    
- **中间代码生成阶段**：用于产生中间代码；
    
- **目标代码生成阶段**：当对符号名进行地址分配时，符号表是地址分配的直接依据。
    

**洞见**：符号表是编译器的"全局通讯录"——它让"前面阶段收集的信息"能够被"后面阶段"使用。理解符号表，就理解了"为什么编译器能在语义分析阶段知道某个变量是否已经声明"——因为声明阶段的 Enter 已经把它写进符号表了。

#### 10.2.3 注解处理器 —— 把编译器变成"可编程工具"

这是 Javac 最具"黑客精神"的一个阶段。

**JDK 5**​ 引入了注解，最初设计是在**运行期**通过反射发挥作用。但 JDK 6 通过 **JSR 269（Pluggable Annotation Processing API）**​ 把注解处理提前到了**编译期**：

- 插入式注解处理器可以看作是**一组编译器的插件**；
    
- 插件工作时，**允许读取、修改、添加抽象语法树中的任意元素**；
    
- 如果插件在处理注解期间**对语法树进行了修改，编译器将回到解析及填充符号表的过程重新处理，直到所有插件都没有再对语法树进行修改为止**——每一次循环称为一个"Round（轮次）"；
    
- 这个"Round 循环"机制意味着：**注解处理器可以生成新的源文件 → 触发新一轮 Parse → 再处理 → 直到稳定**。
    

**JSR 269 的核心 API**：

- 自定义注解处理器需继承 `javax.annotation.processing.AbstractProcessor`；
    
- 用 `@SupportedAnnotationTypes` 指定处理的注解类型（全类名）；
    
- 用 `@SupportedSourceVersion` 指定编译版本；
    
- 用 `@SupportedOptions` 指定编译参数；
    
- 覆写 `process(Set<? extends TypeElement>, RoundEnvironment)` 方法实现处理逻辑；
    
- 注解的保留策略必须是 `@Retention(RetentionPolicy.SOURCE)`——只在编译期可见；
    
- 注册方式：在 `META-INF/services/javax.annotation.processing.Processor` 文件中写明处理器全类名，或使用 `javac -processor` 参数指定。
    

**洞见（第一性原理 + 创新判断）**：

1. **注解处理器 = 把编译器变成"可编程工具"**。JSR 269 之前，想要在编译期修改代码，唯一的办法是"改写编译器"（如 AspectJ 的做法）；JSR 269 之后，任何程序员都可以**通过标准 API 在编译期读取/生成代码**，而不需要 fork 一个 Javac。这是 Java 生态"编译期工具链"爆发的根本性转折。
    
2. **Round 循环机制是"代码生成 → 再处理"的优雅解法**：Lombok 的 `@Data` 在 Round 1 生成 getter/setter 方法 → 这些方法成为新的源文件 → Round 2 中编译器看到完整的方法声明 → 类型检查通过。整个机制无需程序员干预，完全是 Javac 内部 Pipeline 的自然循环。
    
3. **工业现实对照**：
    
    - **Lombok**：通过非标准的 `com.sun.tools.javac.*` 内部 API 直接修改 AST，在编译期注入 getter/setter/equals/hashCode/builder 等代码；
        
    - **MapStruct**：通过注解处理器生成 DTO ↔ Entity 映射代码；
        
    - **AutoService**（Google）：自动生成 `META-INF/services` 文件；
        
    - **Immutables**：生成不可变对象实现；
        
    - **Dagger 2**：生成依赖注入代码；
        
    - **JMH**：生成微基准测试代码；
        
    - **Project Lombok 的争议**：它使用了 JDK 内部 API（`com.sun.tools.javac.*`），这些 API 不属于公开标准，可能在 JDK 版本升级时失效。这也是为什么 Lombok 经常需要紧跟 JDK 新版本做适配。
        
    

> ⚠️ **重要区分**：JSR 269 标准 API 只能**生成新文件**（如生成一个新的 `.java` 源文件），**不能直接修改已有源文件对应的 AST**——修改 AST 需要借助 JDK 内部 API（这正是 Lombok 的做法，也是它的兼容性风险所在）。

#### 10.2.4 语义分析与字节码生成

这是 Javac 做"正确性保证"的核心阶段，包含 4 个子步骤：

**① 标注检查（Attribution）**：

- 变量使用前是否已被声明；
    
- 变量与赋值之间的数据类型是否能够匹配；
    
- **常量折叠（Constant Folding）**：`int a = 1 + 2` 在 AST 上能看到字面量 1、2 和 + 操作符，但标注检查后会**直接折叠为字面量 3**——运行期不再计算；
    
- 名字解析、类型推断、重载决议。
    

**② 数据流与控制流分析（Flow）**：

- **Definite Assignment（确定性赋值）**：确保变量在使用前已被初始化；
    
- **Reachability（可达性）**：检测不可达代码（如 `return` 之后的语句）；
    
- **Exception Analysis**：确保受查异常被捕获或声明；
    
- **Final 变量赋值检查**：防止 final 变量被重复赋值；
    
- **Resource Management**：对 try-with-resources 的资源管理做检查。
    

**③ 解语法糖（Desugar / Lowering）**：

- 把高级语法糖翻译为 JVM 能直接执行的简单结构；
    
- 包括：foreach → Iterator 循环、lambda → invokedynamic、try-with-resources → try-finally、枚举 → 继承 Enum 的特殊类、自动装箱拆箱 → valueOf/xxxValue、变长参数 → 数组、桥接方法合成等；
    
- **泛型类型擦除**也在此阶段完成（见 10.3.1）；
    
- **桥接方法（Bridge Method）**：为了保持多态，在泛型子类重写父类方法时合成一个桥接方法，映射泛型签名到原始类型签名。
    

**④ 字节码生成（Gen + ClassWriter）**：

- 遍历脱糖后的 AST，生成 JVM 字节码；
    
- 把前面各步骤生成的信息（常量池、字段表、方法表、Code 属性等）写入 `.class` 文件；
    
- **少量代码添加工作**：如实例构造器 `<init>()` 和类构造器 `<clinit>()` 就是在这个阶段添加到语法树中的；
    
- 还包括：StackMapTable 生成、LineNumberTable 生成、InnerClasses 属性生成等。
    

**洞见（第一性原理）**：

1. **Javac 的"优化"集中在"减少运行期不必要的工作"**：常量折叠让 `1+2` 不在运行期计算、不可达代码消除让死代码不进字节码、类型检查让类型错误在编译期暴露。**这些都是"正确性 + 减少运行期开销"的优化，而非"提升运行期性能"的优化**——后者是 JIT 的使命。
    
2. **AST 是贯穿所有阶段的"单一事实来源"**：Parse 生成 AST → Enter 在 AST 上填符号 → Process 修改 AST → Attr 在 AST 上标类型 → Flow 在 AST 上做流分析 → Desugar 在 AST 上做转换 → Gen 从 AST 生成字节码。**理解 AST 的中心地位，就理解了为什么注解处理器能如此强大**——它拿到的是和 Javac 内部完全相同的 AST。
    
3. **泛型擦除发生在 Desugar 阶段**：这意味着 JVM 运行时根本不知道泛型信息——`List<String>` 和 `List<Integer>` 在字节码层面都是 `List`。这是 Java 泛型被称为"伪泛型"的根本原因（见 10.3.1）。
    

### 10.3 Java 语法糖的味道 —— 编译器替你写的"隐形代码"

这是全章最有趣的一节。**所谓"语法糖"，就是编译器在编译期自动替你写代码的语法**——JVM 根本不认识这些语法，全是 Javac 在脱糖阶段还原为简单结构。

#### 10.3.1 泛型与类型擦除（Java 最被误解的特性）

**核心机制**：

- Java 的泛型**只在程序源码中存在**；
    
- 编译后的字节码中，泛型被替换为**原生类型（Raw Type）**——通常是 `Object` 或泛型参数的左边界类型；
    
- 在相应位置插入**强制类型转换**代码；
    
- `List<String>` 和 `List<Integer>` 在运行期是**同一个 Class 对象**——因为泛型信息被完全擦除。
    

**示例**：

```
// 源码
Map<String, String> map = new HashMap<>();
map.put("hello", "world");
System.out.println(map.get("hello"));

// 编译后（反编译视角）
Map map = new HashMap();
map.put("hello", "world");
System.out.println((String) map.get("hello"));  // 编译器插入了强制转换
```

**类型擦除带来的限制**：

- **不能用泛型类型做方法重载**：`void method(List<String>)` 和 `void method(List<Integer>)` 是同一个方法签名（擦除后都是 `List`），无法重载；
    
- **泛型类型不能用于 `catch` 子句**：`catch (T e)` 不合法；
    
- **静态字段在泛型实例间共享**：`class Box<T> { static int count; }` 中 `Box<String>.count` 和 `Box<Integer>.count` 是同一个字段；
    
- **不能 `new T()`**：运行时不知道 T 的具体类型；
    
- **泛型数组创建受限**：`new T[10]` 不合法。
    

**桥接方法的秘密**：为了保持泛型多态，Javac 会在字节码中合成"桥接方法"。例如：

```
class Node<T> {
    public T getData() { ... }
}
class StringNode extends Node<String> {
    @Override
    public String getData() { ... }  // 擦除后签名变为 Object getData()
}
```

Javac 会为 `StringNode` 合成一个桥接方法：

```
// 合成的桥接方法
public Object getData() {
    return getData();  // 调用真实的 String getData()
}
```

这个桥接方法保证了"父类引用调用泛型方法时能正确分发到子类实现"——**它是 JVM 实现泛型多态的幕后英雄**。

**洞见（第一性原理 + 创新判断）**：

1. **Java 泛型是"编译期的谎言"**：它在源码层面给你类型安全的幻觉，但在字节码层面消失得无影无踪。**这就是为什么 Java 泛型被称为"伪泛型"**——它不改变 JVM 的任何东西，纯粹是 Javac 在编译期为程序员做的"类型安全检查 + 自动插入 cast"。
    
2. **类型擦除是"向后兼容"的必然代价**：Java 5 引入泛型时，JVM 规范已经稳定。如果采用 C# 的"真泛型"（每个泛型类型生成独立的运行时类型），就会破坏与已有字节码和 JVM 的兼容性。**类型擦除是用"运行期类型信息的丢失"换取"与 JDK 1.4 及以前字节码的 100% 兼容"**。
    
3. **工业现实对照**：
    
    - **Kotlin 的泛型**：JVM 上的 Kotlin 同样受类型擦除限制，但 Kotlin 提供了 `inline` 函数 + `reified` 类型参数来"绕过"擦除——通过内联函数在调用点展开，使类型信息在字节码中可见；
        
    - **Scala 的泛型**：同样基于 JVM 类型擦除，但通过 `@specialized` 注解可以为基本类型生成特化版本；
        
    - **Project Valhalla**：正在为 Java 引入"值类型（Value Types）+ 真泛型（Reified Generics）"——通过 `Any` 类型和泛型特化，让 `ArrayList<int>` 不再需要装箱。这将是对类型擦除的根本性修正，但要保持向后兼容的挑战巨大。
        
    

#### 10.3.2 自动装箱、拆箱与遍历循环

这三种语法糖是 Java 代码中出现频率最高的：

**① 自动装箱/拆箱**：

```
// 源码
Integer n = 66;        // 自动装箱
int i = n;             // 自动拆箱

// 编译后
Integer n = Integer.valueOf(66);
int i = n.intValue();
```

**陷阱**：Integer 缓存 `-128 ~ 127` 之间的对象（通过 `Integer.valueOf()` 返回缓存实例）：

```
Integer a = 100;
Integer b = 100;
System.out.println(a == b);  // true（同一缓存对象）

Integer c = 200;
Integer d = 200;
System.out.println(c == d);  // false（超出缓存，新建对象）
```

**这就是为什么包装类型比较必须用 `.equals()` 而非 `==`**——自动装箱返回的可能是缓存对象，也可能是新对象，行为不一致。

**② 遍历循环（foreach）**：

```
// 源码
List<Integer> list = Arrays.asList(1, 2, 3, 4);
for (int i : list) {
    sum += i;
}

// 编译后
List list = Arrays.asList(new Integer[]{
    Integer.valueOf(1), Integer.valueOf(2),
    Integer.valueOf(3), Integer.valueOf(4)
});
for (Iterator localIterator = list.iterator(); localIterator.hasNext(); ) {
    int i = ((Integer) localIterator.next()).intValue();
    sum += i;
}
```

**foreach 循环的本质**：对数组 → 编译为传统索引循环；对 `Iterable` → 编译为 `Iterator` 循环。

**③ 变长参数**：

```
// 源码
print("a", "b", "c");

// 编译后
print(new String[]{"a", "b", "c"});
```

**洞见**：

1. **foreach 循环的"隐藏成本"**：每次 foreach 都会创建一个 `Iterator` 对象（对 `Iterable` 而言）。在**极高频循环**场景下，这可能成为性能瓶颈——此时应改用传统 for 循环或手写索引。但绝大多数业务场景下，foreach 的可读性收益远大于这点开销。
    
2. **自动装箱的"隐性性能陷阱"**：在数值计算密集的循环中，自动装箱会导致大量 `Integer.valueOf()` 调用和对象分配。例如 `Integer sum = 0; for (...) sum += i;` 会在每次迭代产生一个新 Integer 对象——**这就是为什么数值计算一定要用 `int` 而非 `Integer`**。
    
3. **工业最佳实践**：阿里巴巴 Java 开发手册明确规定——**在 POJO 类中，不要用包装类型声明数据库字段对应的属性，避免自动装箱拆箱的性能损耗**；但在 RPC 接口的返回值中，推荐使用包装类型以区分"未赋值"与"值为 0"。
    

#### 10.3.3 条件编译

Java **没有预处理器**（不像 C/C++ 的 `#ifdef`），但可以用**常量折叠 + 不可达分支消除**实现等价效果：

```
// 源码
public static void main(String[] args) {
    if (true) {
        System.out.println("block 1");
    } else {
        System.out.println("block 2");
    }
}

// 编译后（反编译视角）
public static void main(String[] args) {
    System.out.println("block 1");
    // else 分支被完全消除
}
```

**机制**：`if (常量表达式)` 中，若常量表达式为 `false`，则该分支被 Javac 判定为不可达代码，在字节码生成阶段直接剔除。**这是 Java 实现"条件编译"的唯一方式**。

**洞见**：条件编译的本质是**"编译期常量折叠 + 不可达代码消除"两个优化的组合应用**。它揭示了 Javac 的一个设计哲学——**"凡是编译期能确定的事，绝不留到运行期"**。这也是为什么 `final static` 常量能在 switch-case 中直接使用，而普通变量不行。

### 10.4 实战：插入式注解处理器 —— 自己写一个 CheckGetter

这是全章最具"动手价值"的一节。周志明带读者实现了一个 `CheckGetter` 注解处理器：**检查被 `@CheckGetter` 注解的类，若其字段没有对应的 getter 方法，则编译报错**。

**核心实现思路**：

**① 定义注解**：

```
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.SOURCE)  // 只在编译期可见
public @interface CheckGetter {}
```

**② 实现注解处理器**：

```
@SupportedAnnotationTypes("annotations.CheckGetter")
@SupportedSourceVersion(SourceVersion.RELEASE_8)
public class CheckGetterProcessor extends AbstractProcessor {
    @Override
    public boolean process(Set<? extends TypeElement> annotations,
                           RoundEnvironment roundEnv) {
        // 1. 找到所有被 @CheckGetter 注解的类
        for (Element element : roundEnv.getElementsAnnotatedWith(CheckGetter.class)) {
            // 2. 遍历类的所有字段
            for (Element enclosed : element.getEnclosedElements()) {
                if (enclosed.getKind() == ElementKind.FIELD) {
                    // 3. 检查是否存在对应的 getter 方法
                    String fieldName = enclosed.getSimpleName().toString();
                    String getterName = "get" + capitalize(fieldName);
                    boolean hasGetter = element.getEnclosedElements().stream()
                        .filter(e -> e.getKind() == ElementKind.METHOD)
                        .anyMatch(e -> e.getSimpleName().toString().equals(getterName));
                    // 4. 若不存在，通过 Messager 输出编译错误
                    if (!hasGetter) {
                        processingEnv.getMessager().printMessage(
                            Diagnostic.Kind.ERROR,
                            "Class '" + element.getSimpleName() + "' is annotated as @CheckGetter, " +
                            "but field '" + fieldName + "' is without getter",
                            enclosed
                        );
                    }
                }
            }
        }
        return false;  // 返回 false 表示不独占该注解，允许其他处理器继续处理
    }
}
```

**③ 注册处理器**：在 `META-INF/services/javax.annotation.processing.Processor` 文件中写入 `CheckGetterProcessor` 的全类名。

**④ 编译时触发**：

```
javac -processor CheckGetterProcessor Foo.java
error: Class 'Foo' is annotated as @CheckGetter, but field 'a' is without getter
```

**洞见（第一性原理 + 工业联系）**：

1. **这个"玩具级"处理器，正是 Lombok、MapStruct、AutoService 的雏形**。`javax.lang.model.*` 包把 Java 语言元素（包、类型、方法、字段、变量、注解）映射为 `Element` 和 `TypeMirror` 对象——**相当于在编译期为程序员提供了一份"Java 语言本身的反射 API"**。
    
2. **`Messager` 是注解处理器与编译器沟通的"标准渠道"**：通过 `Messager.printMessage(Diagnostic.Kind.ERROR, ...)`，处理器可以输出编译错误、警告、提示——这些消息会被 Javac 统一格式化输出，与 Javac 自身的错误信息风格一致。
    
3. **工业级应用**：
    
    - **Lombok 的 `@Data`/`@Getter`/`@Setter`**：在 Round 1 通过内部 API 修改 AST，注入方法声明 → Round 2 编译器看到完整类定义；
        
    - **MapStruct 的 `@Mapper`**：生成 DTO 映射实现类；
        
    - **AutoService（Google）**：自动生成 `META-INF/services` 文件，避免手工维护；
        
    - **Immutables**：生成不可变对象实现；
        
    - **Dagger 2**：生成依赖注入代码，编译期完成 DI 图构建，运行期零反射；
        
    - **JMH 的 `@Benchmark`**：生成微基准测试的脚手架代码；
        
    - **Error Prone（Google）**：在编译期做额外的静态代码分析，捕获潜在 bug（如 `==` 比较对象、`hashCode` 与 `equals` 不一致等）。
        
    
4. **`return false` vs `return true`**：`process()` 方法返回 `true` 表示该注解被"独占"，其他处理器不再处理；返回 `false` 表示允许其他处理器继续处理。大多数情况下返回 `false`——除非你明确想要"吃掉"这个注解。
    

### 10.5 本章小结

本章完成了三件事：**拆解了 Javac 的编译过程（解析与填充符号表 → 注解处理器 → 语义分析与字节码生成）**；**揭示了 Java 语法糖的底层机制（泛型类型擦除、自动装箱拆箱、foreach 循环、条件编译）**；**通过 CheckGetter 实战演示了插入式注解处理器的威力**。它是连接"Java 语言"与"JVM 字节码"的最后一环——从此你眼中的 Java 代码，不再是"JVM 直接执行的指令"，而是"Javac 替你翻译、脱糖、检查后生成的字节码"。

## 四、本章核心洞见总结（第一性原理视角，值得反复回看）

1. **Javac 的核心使命是"正确性 + 语言表达力"，而非"运行期性能"**。真正的性能优化在 JIT（第11章）。**期待"换个 Javac 版本让程序跑快 30%"是不现实的**。
    
2. **AST 是贯穿 Javac 所有阶段的"单一事实来源"**：Parse 生成 AST → Enter 在 AST 上填符号 → Process 修改 AST → Attr 在 AST 上标类型 → Flow 在 AST 上做流分析 → Desugar 在 AST 上做转换 → Gen 从 AST 生成字节码。**理解 AST 的中心地位，就理解了为什么注解处理器如此强大**。
    
3. **Java 泛型是"编译期的谎言"**：类型擦除后用"伪泛型"换取"与 JDK 1.4 及以前字节码的 100% 兼容"。代价是运行期类型信息丢失、不能用泛型做方法重载、不能 `catch` 泛型异常。**桥接方法是 JVM 实现泛型多态的幕后英雄**。
    
4. **语法糖的本质是"编译器替你写代码"**：foreach → Iterator 循环、自动装箱 → `Integer.valueOf()`、自动拆箱 → `Integer.intValue()`、变长参数 → 数组、条件编译 → 常量折叠 + 不可达分支消除。**JVM 根本不认识这些语法，全是 Javac 在脱糖阶段还原为简单结构**。
    
5. **插入式注解处理器（JSR 269）= 把编译器变成"可编程工具"**：JDK 6 之前想要在编译期修改代码只能 fork 编译器；JSR 269 之后，任何程序员都能通过标准 API 在编译期读取/生成代码。**这是 Java 生态"编译期工具链"（Lombok、MapStruct、AutoService、Dagger 2、JMH、Error Prone）爆发的根本原因**。
    
6. **Round 循环机制**：注解处理器若生成新源文件，Javac 会回到 Parse 阶段重新处理，直到稳定。**Lombok 的 `@Data` 就是利用 Round 1 注入方法 → Round 2 编译器看到完整类定义的经典案例**。
    
7. **JSR 269 标准 API 只能生成新文件，不能直接修改已有 AST**——修改 AST 需要借助 JDK 内部 API（`com.sun.tools.javac.*`），这正是 Lombok 的做法，也是它的兼容性风险所在。**这解释了为什么 Lombok 经常需要紧跟 JDK 新版本做适配**。
    
8. **工业最佳实践启示**：
    
    - 数值计算密集场景避免使用包装类型（自动装箱拆箱的隐性开销）；
        
    - 包装类型比较必须用 `.equals()` 而非 `==`（Integer 缓存 `-128~127` 导致行为不一致）；
        
    - 极高频 foreach 循环考虑改用传统 for 循环（避免 Iterator 对象分配）；
        
    - 编译期代码生成（Lombok/MapStruct/Dagger 2）优于运行期反射/AOP——零运行期开销、类型安全、可调试。
