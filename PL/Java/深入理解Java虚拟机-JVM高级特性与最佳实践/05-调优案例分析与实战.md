## 二、5.2 案例分析 —— 七桩故障悬案逐案拆解

### 5.2.1 高性能硬件上的程序部署策略

**场景**：64 位机器、大内存（如 16G+）、多 CPU。常见误区是"堆越大越好"，把 `-Xmx` 设到 10G+，以为能减少 GC。

**核心观点（书中的重要判断）**：**大堆 ≠ 高性能**。堆过大时，单次 Full GC 的停顿时间会随堆大小近似线性增长（尤其是使用 PS/CMS 这类全堆扫描收集器时），一次 Full GC 可能停顿数秒甚至数十秒，对延迟敏感服务是灾难。

**部署策略权衡**（书里的核心洞见）：

| 策略 | 做法 | 适用场景 | 代价 |
|---|---|---|---|
| **① 64位JVM + 大堆** | 单进程 `-Xmx` 设大 | 数据处理/批处理，能容忍较长 STW | Full GC 停顿随堆增大而变长 |
| **② 64位JVM + 多进程（推荐Web服务）** | 一台机器起多个 JVM 实例（如 4×4G），前置负载均衡 | 高并发 Web/中间件 | 跨进程共享缓存需额外方案（如 Redis）|
| **③ 使用并发/低延迟收集器** | 大堆配合 CMS/G1/ZGC | 大堆 + 延迟敏感 | CMS 已废弃；G1/ZGC 是现���首选 |

**工业联系 & 洞见**：
- 今天的最佳实践是**"多实例 + 容器化 + G1/ZGC"**：Kubernetes 中把 JVM 部署为多个中等堆（如 4~8G）的 Pod，而非一个超大堆单实例——既避免单次 GC 停顿过长，又便于弹性扩缩。
- **第一性原理判断**：GC 停顿的本质是"**扫描/整理的对象越多，停顿越长**"。所以"把鸡蛋分散到多个篮子（多进程/多容器）"，比"把所有鸡蛋放一个大篮子再想办法（超大堆+超低延迟收集器）"更稳健、更可扩展。**这是"分治思想"在部署架构上的直接应用**。

### 5.2.2 集群间同步导致的内存溢出

**场景**：一个后台 RPC/同步服务，每 10 分钟加载/同步一次数据，短时间内产生大量对象，触发频繁 GC 甚至 OOM。

**根因**：集群节点间高频同步 + 同步数据被**静态集合/缓存长期持有** → 对象无法回收 → 老年代持续增长 → 最终 OOM（`Java heap space`）。本质是**"生产者-消费者速率失衡 + 无淘汰策略的缓存"**叠加。

**解决思路**（书中 + 现代补正）：
1. **异步解耦**：把同步调用改为**生产者/消费者模式的消息队列**（Kafka/RocketMQ），削峰填谷，避免瞬时大对象洪峰。
2. **缓存必须带淘汰**：将无界 `static HashMap` 替换为 **Caffeine/Guava Cache/Redis**，设置**最大容量 + TTL 过期**，从源头杜绝"只进不出"。
3. **数据库查询加分页**：避免一次性把 80 万条记录捞进内存（MyBatis PageHelper / 流式查询）。

**洞见**：这类 OOM 的表象是"内存不足"，**本质是"对象生命周期管理失控"**——缓存/静态集合成了"对象坟墓"，只进不出。记住一句排障铁律：**"静态集合 + 无淘汰 = 内存泄漏的温床"**。

### 5.2.3 堆外内存导致的溢出错误（DirectByteBuffer "暗杀案"）

**这是本章最具启发性的案例，也是生产最高频的"影子杀手"。**

**场景**：服务运行数天后突发 `OutOfMemoryError: Direct buffer memory`，但 `-Xmx` 堆使用率始终很低（如 30%），`jstat -gc` 老年代稳定，`jmap -histo` 未见大对象堆积——构成典型的**"堆内健康，进程濒死"矛盾现象**。

**根因机制**（必须理解透）：
- `ByteBuffer.allocateDirect()` 分配的**直接内存（Direct Memory）不归 JVM 堆管**，直接向操作系统申请堆外内存，受限 `-XX:MaxDirectMemorySize`（默认等于 `-Xmx`）。
- DirectByteBuffer **自身是堆内小对象（几十字节）**，但它背后指向**堆外数 MB 内存**；GC 只看见"小壳子"，看不见背后的堆外大块，**堆监控一切正常**。
- 回收依赖 **Cleaner（虚引用机制）**：DirectByteBuffer 被 GC 后，Cleaner 才会异步释放其堆外内存。若**分配速度 >> GC 回收速度**，或 `ByteBuf.release()` 漏调用（Netty），堆外内存持续堆积直至 OOM。

**诊断（破局的唯一可信信标——NMT）**：堆 dump（MAT）**看不到**直接内存，必须多维度联动：

```bash
# 1. 启用 NMT（启动参数：-XX:NativeMemoryTracking=summary）
jcmd <PID> VM.native_memory baseline          # 建立基线
jcmd <PID> VM.native_memory summary scale=MB # 查看各区域，重点看 Direct / Internal
jcmd <PID> VM.native_memory summary.diff     # 与基线对比，看增量

# 2. 统计 DirectByteBuffer 实例数（持续增长 = 泄漏风险）
jmap -histo:live <PID> | grep -i DirectByteBuffer

# 3. 查物理内存映射，找持续增长的匿名块 [anon]
pmap -x <PID> | sort -n -k3

# 4. Netty 场景：开启泄漏检测（PARANOID 级打印泄漏对象创建栈）
-Dio.netty.leakDetection.level=PARANOID
```

NMT 输出关键线索示例：

```
Category      Used (MB)   Trend
Heap          1080         → (平稳)
Direct        2348         ↑↑↑ (持续 +120MB/h)   ← 元凶
Internal       896         ↑  (与 Direct 强相关)
```

**解决（防御性编码 + 自动化防护）**：

```java
// ✅ 正确释放 MappedByteBuffer（JDK8；JDK9+ 用 Cleaner/CleanerFactory）
public static void unmap(MappedByteBuffer buffer) {
    if (buffer == null || !buffer.isDirect()) return;
    try {
        Method cleanerMethod = buffer.getClass().getMethod("cleaner");
        cleanerMethod.setAccessible(true);
        Object cleaner = cleanerMethod.invoke(buffer);
        Method cleanMethod = cleaner.getClass().getMethod("clean");
        cleanMethod.invoke(cleaner);
    } catch (Exception e) { log.warn("Failed to unmap buffer", e); }
}
```

- **显式限制**：`-XX:MaxDirectMemorySize=512m`（推荐设为堆的 1/4~1/2，避免挤占系统内存）。
- **池化复用**：Netty 用 `PooledByteBufAllocator`（默认开启），避免每次 `allocateDirect` 的系统调用开销与碎片；**必须保证 `buf.release()` 成对调用**，漏一次泄漏一块。
- **全局兜底**：`-XX:+ExplicitGCInvokesConcurrent`（让 `System.gc()` 触发并发 GC 而非 Full STW，辅助 Cleaner 回收）；**慎用 `-XX:+DisableExplicitGC`**——它会把 DirectByteBuffer 的 Cleaner 回收路径也一并禁用，加剧泄漏。
- **优先堆内**：非高频零拷贝场景（小数据 <1KB 拷贝成本高），用 `ByteBuffer.wrap(byte[])` 堆内缓冲更安全可控。

**工业联系（真实案例）**：某线上服务 NioChannel 每个连接初始化申请 4MB 堆外 buffer，连接数达 1451 时堆外内存 ≈ 5804MB 濒临 OOM；通过 `jmap -histo` 定位到 NioChannel 异常多，最终**调小 buffer + 控制连接数**解决。**现代进阶方案**：Java 21 的 **Project Panama FFM API** 允许 Java 直接访问 C 内存结构、零拷贝，从源头规避 DirectByteBuffer 的隐式依赖（JMH 压测显示堆外内存从 1.82GB 降至 280MB、吞吐提升 34%）。

**洞见（第一性原理）**：DirectByteBuffer 案例揭示了 JVM 内存管理的一个**深层边界**——**"GC 只管堆内对象，不管对象背后指向的堆外资源"**。这提醒我们：**当一个"小对象"是"大资源"的句柄时（DirectByteBuffer / 文件句柄 / 数据库连接），绝不能只靠 GC，必须配���显式的资源释放协议（try-with-resources / release() / Cleaner）**。这是"RAII/资源即对象"思想在 Java 中的对应物。

### 5.2.4 外部命令导致系统缓慢

**场景**：Java 应用频繁调用外部系统命令（`Runtime.getRuntime().exec()` / `ProcessBuilder`），系统整体变慢、CPU 飙升。

**根因**：每次 `exec()` 都会 **fork 一个子进程**（Linux 下 `fork()` + `exec()`），JVM 进程内存较大时，**fork 的写时复制（Copy-On-Write）开销巨大**；且子进程若不读取其输出流（`Process.getInputStream()`），可能因管道缓冲区满而**阻塞挂起**，反压拖垮 JVM。

**解决**：
- **避免高频 `exec`**：把"调外部命令"改为**进程内库调用**（如用 Java 原生库替代调用 `grep`/`awk` 脚本）。
- **必须读取子进程输出**：`exec()` 后**异步消费** `stdout`/`stderr`（否则管道满阻塞），并使用 `Process.waitFor()` 超时控制 + 最终 `destroy()` 回收。
- **改用线程池/异步**：批量外部调用用队列削峰，避免瞬时大量 fork。

**洞见**：这个案例的深层教训是——**"跨进程边界"的代价远高于"跨方法/跨线程边界"**。`fork` 一个进程的开销是毫秒级（COW + 上下文切换），而方法调用是纳秒级。**凡是高频路径上出现 `Runtime.exec`，几乎必然成为性能瓶颈**——这是"减少跨边界开销"原则的典型应用。

### 5.2.5 服务器 JVM 进程崩溃

**场景**：JVM 进程**直接被操作系统 OOM Killer 杀掉**（日志出现 `java.lang.OutOfMemoryError` 或进程莫名消失，`dmesg` 可见 OOM Kill 记录），而非优雅抛出堆 OOM。

**根因**：**物理内存被耗尽**——常见元凶是 ① 堆外内存（DirectByteBuffer）失控；② **大量线程**（每线程默认 1MB 栈，`-Xss`）耗尽内存；③ 容器/ cgroup 内存限制小于 JVM 实际占用（堆 + 堆外 + 栈 + Metaspace + CodeCache）。

**诊断与解决**：

```bash
# 1. 确认是否被 OS OOM Killer 杀掉
dmesg -T | grep -i "killed process" | grep java
# 2. 查线程数（过高 → 调小 -Xss 或用线程池）
ps -eLf | grep java | wc -l
ulimit -u   # 系统线程/进程上限
# 3. 容器环境：确保 -Xmx + MaxDirectMemorySize + 线程栈预留 < 容器内存 limit
```

- **控制线程数**：用 `Executors.newFixedThreadPool()` 等线程池，避免每次请求 `new Thread().start()`；`-Xss256k`（默认 1MB→256KB）可显著增加可创建线程数（过小会 StackOverflow）。
- **容器内存规划**：总内存预算 = `-Xmx` + `-XX:MaxDirectMemorySize` + `-Xss × 线程数` + `Metaspace` + `CodeCache` + 系统预留，**不超过容器 limit 的 70%~80%**。
- **开启堆转储兜底**：`-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/dump`，崩溃后可离线分析。

**洞见**：JVM 进程崩溃的本质是**"JVM 视角的资源（堆）"与"操作系统视角的资源（物理内存）"发生了错位**——堆监控正常，但进程因堆外/栈/系统内存耗尽被 OS 杀掉。**这再次印证了 5.2.3 的教训：JVM 的"内存世界"只是操作系统内存的一部分，调优时必须站在 OS 全局视角**。

### 5.2.6 不恰当数据结构导致内存占用过大

**这是本章"数据结构 × JVM 对象头"交叉视角最精彩的案例。**

**场景**：后台 RPC 服务器每 10 分钟加载约 **800MB 的 `HashMap<Entry>` 数据**，期间 Minor GC 停顿长达 500ms+。

**根因（两层）**：
1. **分配速率冲击**：800MB 数据瞬间填满 Eden，频繁触发 Minor GC；GC 时这 800MB 数据在 Eden↔Survivor 间**反复复制**，导致 Minor GC 时间长。
2. **空间效率极低（核心洞见）**：`HashMap` 存储 `Long→Long` 时，表面数据仅 2×8=16 字节，封装成 `Map.Entry` 后额外多出：对象头 16B + `next` 指针 8B + `hash` 字段 4B + 对齐 4B + 对 Entry 的引用 8B。**实际耗费约 88 字节，空间效率仅 16/88 ≈ 18%**——有效数据被对象头和 Map 内部结构"淹没"了 82%。海量小对象还会加剧 GC 压力。

**解决思路（书中 + 现代补正）**：

| 思路 | 做法 | 效果 |
|---|---|---|
| **① 大对象尽早入老年代** | 减小新生代或用 `-XX:SurvivorRatio=65536` + `-XX:MaxTenuringThreshold=0`（等价于去掉 Survivor），让大对象第一次 Minor GC 后立即进老年代，避免 Eden↔Survivor 反复复制 | 减少 Minor GC 停顿 |
| **② 优化数据结构（治本）** | 用 **FastUtil / Agrona / Eclipse Collections** 等**原生类型特化集合**（如 `Long2ObjectOpenHashMap`、`Int2DoubleOpenHashMap`），消除 Long 装箱与 Entry/桶数组开销 | 内存可降至原方案的 **6.5%**（案例：3205MB → 211MB，省约 3GB）|
| **③ 平行数组替代对象集合** | 将 `List<Point>`（每个含 long+double+对象头）改为两个平行数组 `long[] timestamps` + `double[] values` | 内存下降 40%~60%，且 CPU 缓存友好 |
| **④ 启用压缩指针** | `-XX:+UseCompressedOops`（堆 ≤32GB 自动生效），对象引用从 8B 压至 4B | 对 Map 的 Node 数组、链表 next 指针收益明显 |

**工业联系（真实案例）**：某报表导出接口查 6 万条数据用 `HashMap` 接收结果集，频繁 FGC；优化为 **JavaBean + EasyExcel 分页导出 + 限流**（Guava/Redis），并将 HashMap 改为对象封装，内存占用显著下降。**现代推荐**：高基数 Map 场景首选 **FastUtil / Agrona**，实测内存仅为 JDK HashMap 的 1/3~1/15。

**洞见（第一性原理 + 创新判断）**：
1. **"数据结构的选择，本质是对'对象头开销'和'间接引用开销'的权衡"**。JVM 中每个对象至少 12~16 字节头，当你的"有效数据"小于"头开销"时，**换数据结构（原生类型集合/平行数组）比"调 JVM 参数"有效 10 倍**。这是"理解对象布局（第2章）→ 指导工程选型（第5章）"的直接闭环。
2. **调优的优先级铁律**：**优化代码/数据结构 > 调整内存布局参数 > 更换收集器**。很多人一上来就调 GC 参数，殊不知根源是"用错了数据结构"——**参数调优治标，结构优化治本**。

### 5.2.7 由 Windows 虚拟内存导致的长时间停顿

**场景**：带心跳检测的 GUI 桌面程序，上线后**偶尔出现约 1 分钟完全无日志输出**（心跳误报），大部分 GC 在 100ms 内，但**偶尔一次接近 1 分钟的超长收集**。

**根因**：GUI 程序最小化时，Windows 会将其**工作集（Working Set）修剪、换出到磁盘页面文件（Swap）**以腾出物理内存给前台应用；当 GC 触发需要扫描堆时，**必须先把这些换出的内存页从磁盘恢复回物理内存**，导致"从准备开始 GC 到真正开始扫描之间"的等待时间极长，出现分钟级停顿。

**解决**：
- **阻止 JVM 在最小化时被修剪工作集**：添加 JVM 参数 `-Dsun.awt.keepWorkingSetOnMinimize=true`（VisualVM 等工具的启动配置就带此参数，保证恢复最小化时立即响应）。
- **Linux 服务器类比（现代补正）**：服务器虽无"最小化"概念，但 **Swap 同样是 JVM 的隐形杀手**——当 `-Xmx` 设置过高（如 8G）而宿主机 RAM 仅 4G 时，堆部分被换出到 Swap，GC 扫描需先 I/O 换回，单次 GC 耗时从毫秒飙升至秒/分钟级，形成"死亡 GC 停顿"。**服务器调优**：`-Xmx` 不超过物理内存 70%、预留空间给 OS/线程栈；调整 `vm.swappiness=10`（默认 60）让内核尽量避免 Swap；容器环境务必设内存 limit 并预留 headroom。

**洞见**：这个案例揭示了一个**跨越 OS 与 JVM 的深层真相**——**GC 停顿时间 = 扫描对象的时间 + 等待内存页就绪的时间**。当堆被换出到磁盘，GC 的"扫描"阶段会被慢速 I/O 阻塞，停顿失控。**NMT 显示的是已提交内存（committed），不反映是否被 Swap 出去**，容易误判内存压力。**这提醒我们：JVM 调优绝不能脱离操作系统——"堆大小"的上限不是 `-Xmx` 能设多大，而是"物理内存能稳定驻留多少"**。

## 三、5.3 实战：Eclipse 运行速度调优 —— 一个完整的调优闭环演示

这是本章**把方法论落地的示范**：用一个真实、可复现的 Eclipse 调优过程，演示"建立评估体系 → 发现问题 → 逐层优化 → 验证效果"的完整闭环。

### 5.3.1 调优前的程序运行状态

**建立评估体系（第一步，也是最关键的一步）**：先关闭所有项目、关闭 Eclipse，在 `eclipse.ini` 加入 GC 日志参数，建立**可量化的基线**：

```
-XX:+PrintGCTimeStamps
-XX:+PrintGCDetails
-verbose:gc
-Xloggc:gc.log
```

启动 Eclipse 并观察 `gc.log`：调优前典型现象是**启动过程中 Full GC 频繁**（因老年代/永久代容量随使用动态扩展触发扩展式 Full GC），Minor GC 次数也较多，启动耗时明显。

### 5.3.2 升级 JDK 1.6 的性能变化及兼容问题

- **升级 JRE/JDK 版本本身就能带来免费性能收益**：新 JDK 的 JIT 编译器优化更强、GC 算法改进、类加载更快。**书中实验**：把 Eclipse 运行在 JDK 1.6 上，启动速度和运行时流畅度均有可感知提升。
- **兼容性问题**：升级 JDK 后需留意插件/依赖是否兼容新版本 API（如内部 API `sun.misc.Unsafe`、废弃方法），必要时调整启动参数（如 `--add-opens` 开放模块封装，JDK9+ 模块化后尤需注意）。

### 5.3.3 编译时间和类加载时间的优化

- **跳过字节码验证**：`-Xverify:none`（JDK8 及以前），启动时可跳过类字节码验证，**加快类加载速度**（Eclipse 插件极多，类加载是启动瓶颈之一）。JDK9+ 用 `-noverify`（效果类似，模块化后验证机制变化）。
- **增大代码缓存**：`-XX:ReservedCodeCacheSize=256m`，JIT 编译后的本地代码存入 CodeCache，Eclipse 长期运行、插件多，足够 CodeCache 避免 JIT 去优化（deoptimization）。
- **Server 模式 + JIT 深度优化**：`-server`（JDK8 及以前显式指定；JDK9+ 64 位默认即 server），让 JIT 随运行时间把热点字节码更深度编译为本地码，长期运行的 Eclipse 受益明显。

### 5.3.4 调整内存设置控制垃圾收集频率（核心调优）

**核心洞察（书中关键判断）**：**把 `-Xms` 与 `-Xmx`、`-XX:PermSize` 与 `-XX:MaxPermSize` 设为相同值**——强制 JVM 在启动时就把老年代和永久代容量**固定下来**，避免运行时因内存使用增长而**动态扩展**，从而**消除"因容量扩展触发的 Full GC"**。

```ini
# eclipse.ini（书中最终优化配置，JDK6 时代）
-vm
D:/_DevSpace/jdk1.6.0_21/bin/javaw.exe
-vmargs
-Dosgi.requiredJavaVersion=1.5
-Xverify:none
-Xmx512m        # 最大堆 = 初始堆
-Xms512m        # 初始堆，避免运行时扩容
-Xmn128m        # 新生代 128MB，避免频繁 Minor GC
-XX:PermSize=96m        # 永久代初始 = 最大
-XX:MaxPermSize=96m     # 避免永久代扩展触发 Full GC
```

**效果**：在该配置下，Eclipse 启动后一分钟仅发生 **8 次 Minor GC + 4 次 Full GC，总耗时 1.928 秒**，相较调优前大幅降低。

**与现代 JDK 对齐（重要补正）**：JDK8 起**永久代（PermGen）已被 Metaspace 取代**，`-XX:PermSize`/`-XX:MaxPermSize` **不再生效**；现代 Eclipse（JDK11+）配置应改为：

```ini
-vmargs
-Dosgi.requiredJavaVersion=11
-XX:+UseG1GC                  # JDK9+ 默认 G1，可显式指定
-XX:+UseStringDeduplication   # G1 字符串去重，减少重复 String 内存
-Xms1024m
-Xmx2048m                     # 不超过物理内存 1/2
-XX:MetaspaceSize=256m        # 替代 PermSize
-XX:MaxMetaspaceSize=512m     # 替代 MaxPermSize，限制元空间上限
-XX:ReservedCodeCacheSize=256m
-Xverify:none
```

**洞见**：Eclipse 调优的核心就一句话——**"让容量一次性到位，别让 JVM 边跑边扩"**。这背后是"**消除不必要的 Full GC = 消除不必要的长时间停顿**"的工程原则。对任何一个长期运行的 Java 应用（中间件、IDE、后台服务），**`-Xms=-Xmx` + Metaspace 设上限**都是首选基线配置。

### 5.3.5 选择收集器降低延迟

- **JDK6 时代**：Parallel Scavenge（吞吐量优先）是默认新生代收集器；对 Eclipse 这类**交互式 GUI 应用**，可改用 **ParNew + CMS**（`-XX:+UseConcMarkSweepGC`）以降低延迟、减少界面卡顿。
- **现代（JDK9+）**：**G1 已是默认收集器**（`-XX:+UseG1GC`），天然适合大堆 + 低延迟，配合 `-XX:MaxGCPauseMillis=200` 设定期望最大停顿；**对延迟极敏感**（如实时推荐/金融交易）可进一步用 **ZGC**（`-XX:+UseZGC`，JDK15 转正，亚毫秒级停顿、支持 TB 级堆）。

**Eclipse 调优闭环总结**（方法论提炼）：

```
① 建立评估体系（开 GC 日志，量化基线）
   ↓
② 升级 JDK（免费获取 JIT/GC 改进）
   ↓
③ 优化类加载/编译（跳过验证、增大 CodeCache、server 模式）
   ↓
④ 调整内存布局（-Xms=-Xmx、Metaspace 上限，消除扩展式 Full GC）
   ↓
⑤ 选择匹配场景的收集器（交互型→低延迟 CMS/G1/ZGC；批处理→吞吐 Parallel）
   ↓
⑥ 验证效果（对比 GC 日志：次数↓、总耗时↓、停顿↓）
```

## 六、本章核心洞见总结（第一性原理视角，值得反复回看）

1. **调优的本质是"在约束之间做工程权衡"**，抓手永远是三条优先级：**优化代码/数据结构 > 调整内存布局 > 更换收集器**。参数调优治标，结构优化治本。
2. **"分治思想"应用于部署**：大堆 Full GC 停顿随堆增大而变长 → 优选"多实例/多容器中等堆 + 前置负载均衡"，比"单实例超大堆"更稳健可扩展。
3. **DirectByteBuffer 揭示 JVM 内存边界**：GC 只管堆内对象、不管对象背后指向的堆外资源 → 必须配显式资源释放协议（release()/Cleaner/try-with-resources）；堆 dump 看不到堆外，NMT 是破局唯一可信信标。
4. **数据结构选择 = 对"对象头开销"的权衡**：HashMap<Long,Long> 空间效率仅 18%，海量小对象场景用原生类型特化集合（FastUtil/Agrona）内存可降至 1/3~1/15——"理解对象布局→指导工程选型"的直接闭环。
5. **"跨进程边界"代价远高于"跨方法/线程边界"**：高频路径上的 `Runtime.exec`（fork）几乎必然是瓶颈，应改为进程内库调用。
6. **JVM 调优必须站在 OS 全局视角**：`-Xmx` 上限不是能设多大，而是"物理内存能稳定驻留多少"；Swap/工作集修剪会把 GC 停顿从毫秒拖到分钟级（NMT 不反映 Swap，易误判）。
7. **Eclipse 调优核心口诀**：`-Xms=-Xmx`（消除扩展式 Full GC）+ Metaspace 设上限 + 跳过验证/增大 CodeCache + 选匹配场景的收集器（交互型→G1/ZGC，批处理→Parallel）。
