## 二、逐节精读与洞见

### 9.1 概述 —— 程序员的"两个抓手"

周志明开篇点题：在 Class 文件格式、API、字节码指令这些 JVM 已经固化的部分之外，**程序能主动控制的主要是两部分**：

1. **字节码生成**（在运行时动态产生新的 Class 文件内容）；
    
2. **类加载器**（决定类如何被加载进 JVM）。
    

这两个抓手互为表里：**字节码生成解决"类的形态"，类加载器解决"类的来源"**。把它们组合，就能做到许多"违反直觉"的事——热部署、AOP、应用隔离、跨 JDK 版本兼容、运行期代码注入。

**洞见**：这"两个抓手"的开放，是 JVM 从"Java 语言的运行时"演变为"多语言、可扩展的通用平台"的关键。如果 JVM 把类加载和字节码生成都封死，Java 生态绝不会有今天的 Spring AOP、OSGi、Arthas、JaCoCo、各类 APM……**理解这两个抓手的威力，是理解整个 Java 生态"为什么这么能打"的底层逻辑**。

### 9.2.1 Tomcat：正统的类加载器架构

**背景问题**：一个 Web 服务器上可能部署多个 Web 应用，它必须同时解决四个看似矛盾的需求：

- **A. 隔离**：两个 Web 应用使用的类库相互隔离（同名类不冲突）；
    
- **B. 共享**：两个 Web 应用可以共享某些公共类库（如 Spring、日志框架）；
    
- **C. 容器隔离**：服务器本身不受 Web 应用的影响；
    
- **D. 热部署**：大多数服务器应该支持 HotSwap（热替换）功能。
    

**Tomcat 的解法：多层级的类加载器体系**

```
Bootstrap ClassLoader（JVM 核心：rt.jar）
        ↑
System ClassLoader（CLASSPATH 下的类）
        ↑
Common ClassLoader（Tomcat 基础类加载器，加载 CATALINA_HOME/lib）
        ↑
   ┌────┴────┐
Webapp1     Webapp2   ← 每个 Web 应用独立一个 WebappClassLoader
（JasperLoader 为每个 JSP 独立一个类加载器，支持 JSP 热加载）
```

**关键设计：WebappClassLoader 打破了双亲委派模型**

传统的双亲委派是"父加载器优先"；而 WebappClassLoader **默认"本地优先"**：

1. 检查 JVM 本地缓存；
    
2. 若是 JDK 核心类（`java.*`）→ 委派 Bootstrap 加载（**防篡改，这部分仍守双亲委派**）；
    
3. **先在本地 `WEB-INF/classes` 和 `WEB-INF/lib` 查找**（打破双亲委派的"反常规"动作）；
    
4. 本地找不到 → 才向上委派给 CommonClassLoader → SystemClassLoader → BootstrapClassLoader。
    

**为什么必须打破？**​ 假如 Webapp1 用了 Spring 4，Webapp2 用了 Spring 5，且都放在各自的 `WEB-INF/lib` 下。**如果严守双亲委派**，Common 类加载器先加载到其中一个 Spring 版本，另一个 Web 应用就会被"污染"。**只有让 WebappClassLoader 先查本地**，才能保证"我自己应用里的类库版本我说了算"。

> 💡 **Tomcat 配置项 `delegate="true"`**：若设置此属性，WebappClassLoader 会回归"父加载器优先"的标准双亲委派——适用于所有 Web 应用真正共享同一版本类库的场景。

**洞见（第一性原理 + 创新判断）**：

1. **Tomcat 是"正统打破双亲委派"的范本**——它不是为了炫技而打破，而是为了解决"应用隔离 vs 容器共享"这对矛盾。**打破双亲委派的真正动机，从来都是"隔离需求"与"共享需求"的拉锯**。
    
2. **JVM 认定"由不同类加载器实例加载的同名类属于完全不同的类型"**——这是 Tomcat 能做到"同名类多版本共存"的根本法理。不同 WebappClassLoader 实例加载的 `com.example.User`，在 JVM 眼里是两个毫无关系的 Class 对象，互不等价、不能强转。
    
3. **JSP 热加载的秘诀**：每个 JSP 文件对应一个独立的 JasperLoader，JSP 源码改动后，Tomcat 直接丢弃旧的 JasperLoader、创建新的 JasperLoader 重新加载——**类卸载的前提是"加载它的类加载器可被回收"**，JasperLoader 的独立化为 JSP 热替换提供了可能。
    
4. **工业现实对照**：现代微服务架构下，Tomcat 的"多应用隔离"价值在弱化（因为每个服务独立进程部署），但 **Spring Boot 内嵌 Tomcat**​ 仍然用这套类加载体系保证"应用类与框架类"的合理边界。理解 Tomcat 类加载器，对排查 `ClassNotFoundException`、`NoClassDefFoundError`、`ClassCastException（同一类被不同加载器加载）` 这三大经典类加载异常有直接指导意义。
    

### 9.2.2 OSGi：灵活的类加载器架构

**背景问题**：OSGi 要解决的是"动态模块化"——**模块（Bundle）可以热插拔、可以运行时启用/停用、可以多个版本共存**。传统的树状双亲委派模型做不到这一点：它假设类加载器层级是静态的、父子关系是固定的。

**OSGi 的解法：网状类加载器架构**

OSGi 中**每个 Bundle 都有自己的类加载器**，它们之间不是父子关系，而是**平级的协作关系**，形成一个"类加载委派网络"：

```
Bootstrap ClassLoader（java.* 包）
                 ↑
           System Bundle ClassLoader
                 ↑
    ┌────────────┼────────────┐
Bundle A      Bundle B      Bundle C
（导出 com.api）（导入 com.api，导出 com.impl）（导入 com.api 和 com.impl）
```

**类加载时，Bundle 类加载器按以下顺序查找**：

1. `java.*` 包 → 委派给父加载器；
    
2. 在 `bootdelegation` 列表中声明的包 → 委派给父加载器；
    
3. 在 `Import-Package` 中声明的包 → 委派给**声明了对应 `Export-Package` 的那个 Bundle 的类加载器**；
    
4. 在 `Require-Bundle` 中声明的 Bundle → 按清单顺序委派；
    
5. 本 Bundle 的 `Bundle-ClassPath`（私有包、内嵌 JAR）；
    
6. 动态导入 `DynamicImport-Package` → 尝试动态解析。
    

**核心突破**：类加载不再是"沿固定父子链向上"，而是**"按 Bundle 的元数据（MANIFEST.MF）动态解析依赖图"**。当 Bundle A 加载 `com.example.api.Service` 时，实际调用的是框架调度后的、来自 Bundle B 的 Class 对象。

**OSGi 的三大神奇能力**：

- **双向可见性**：Bundle A 可以看见 Bundle B 导出的包，Bundle B 也可以看见 Bundle A 导出的包（传统双亲委派是单向向上，无法实现）；
    
- **多版本共存**：Bundle A 使用 `com.lib v1`，Bundle C 使用 `com.lib v2`，两者在同一 JVM 内和平共处；
    
- **热插拔**：卸载一个 Bundle 时，框架把它从依赖图中摘除，依赖方自动重连到新的提供者，旧 Bundle 类加载器被丢弃 → 类被卸载。
    

**代价**：引入额外的复杂度，线程死锁和内存泄漏的风险（如 Bundle 间循环依赖导致类加载死锁、Listener 未注销导致 Bundle 类加载器无法回收）。

**洞见（第一性原理）**：

1. **OSGi 不是"颠覆"双亲委派，而是"绕开"它**——把"谁能加载哪个类"的决策权从"类加载器的静态继承关系"转移到了"模块元数据和运行时服务注册中心"。这是架构层面的重大抽象升级。
    
2. **OSGi 把类加载器从"树"变成了"网"**——这是软件架构中"用显式依赖图替代隐式层级"的经典案例。它带来的动态性极强，但复杂度也极高。Eclipse 插件体系就是 OSGi 最著名的应用。
    
3. **工业现实对照**：OSGi 在 2000 年代中后期风靡一时（Eclipse、GlassFish、Spring DM），但因复杂度过高，在微服务时代逐渐式微。**JDK 9 的 JPMS（Project Jigsaw）可以看作是 OSGi 理念的"官方轻量版"**——用 `module-info.java` 声明模块依赖，但类加载器仍是层级式的（PlatformClassLoader 介于 Bootstrap 和 AppClassLoader 之间），没有 OSGi 那么极致的网状灵活性。
    

### 9.2.3 字节码生成技术与动态代理的实现

**背景问题**：字节码生成是指"在运行时动态产生 Class 文件的字节码"。除了 `javac` 这种编译期生成，还有哪些场景需要运行期生成字节码？

**典型场景**：

- Web 服务器中的 JSP 编译器（把 JSP 翻译为 Servlet Class）；
    
- 编译时嵌入的 AOP 框架（如 AspectJ）；
    
- **JDK 动态代理**（最经典的运行期字节码生成）。
    

**JDK 动态代理的底层机制**：

当我们调用 `Proxy.newProxyInstance(ClassLoader loader, Class<?>[] interfaces, InvocationHandler h)` 时，JVM 内部做了这些事：

1. **生成代理类名**：形如 `com.sun.proxy.$Proxy0`、`$Proxy1`……
    
2. **调用 `ProxyGenerator.generateProxyClass()` 生成字节码**：
    
    - 遍历所有接口方法，为每个方法生成对应的 `ProxyMethod` 对象；
        
    - 额外生成 `hashCode()`、`equals()`、`toString()` 三个方法的代理；
        
    - 按 Class 文件格式规范，从零开始拼装字节码：写魔数 `0xCAFEBABE` → 次/主版本号 → 常量池 → 访问标志 → 类索引 → 父类索引（`java/lang/reflect/Proxy`）→ 接口索引集合 → 字段集合 → 方法集合；
        
    - 代理类的每个方法体都是同一套路：`super.h.invoke(this, m1, args)`——把调用转发给 `InvocationHandler`；
        
    
3. **调用 `defineClass0()`（JNI 本地方法）把字节码加载为 Class 对象**；
    
4. **用反射拿到代理类的构造器（接受 InvocationHandler 参数）并实例化**。
    

**设置 `sun.misc.ProxyGenerator.saveGeneratedFiles=true`**，可以把生成的 `$Proxy0.class` 保存到磁盘，反编译后你能看到：代理类 `extends Proxy implements 你的接口`，所有接口方法都转发给 `InvocationHandler.invoke()`。

**洞见（第一性原理 + 创新判断）**：

1. **动态代理的精髓：在"原始类和接口还未知"的时候，就确定代理行为**。代理类与原始类脱离直接联系后，就可以很灵活地应用在不同的应用场景——这是 AOP（面向切面编程）的基石。
    
2. **字节码生成 = "把 Class 文件结构倒着用"**：第6章讲"Class 文件如何被解析"，这里讲"Class 文件如何被生成"。**理解第6章的 Class 文件结构，是理解动态代理、ASM、CGLIB、JaCoCo 等所有字节码工具的前提**。
    
3. **JDK 动态代理的局限**：只能代理接口（因为代理类必须 `extends Proxy`，Java 单继承限制）。要代理类，需要用 CGLIB（通过继承 + 重写方法生成子类字节码）或 Byte Buddy 等工具。
    
4. **工业现实对照**：
    
    - **Spring AOP**：默认对接口用 JDK 动态代理，对类用 CGLIB；
        
    - **MyBatis Mapper**：Mapper 接口无实现类，MyBatis 用动态代理在运行期生成实现；
        
    - **RPC 框架（Dubbo/gRPC）**：客户端接口用动态代理生成，把方法调用转为网络请求；
        
    - **Retrofit**：Android/iOS 网络库的 Java 版，同样基于动态代理。
        
    - **现代演进**：JDK 8+ 的 Lambda 表达式、`StringConcatFactory`、VarHandle 等都通过 `invokedynamic` + `MethodHandle` 在运行期动态生成/绑定行为（见第8章 8.3.3），这是比动态代理更新一代的字节码动态化机制。
        
    

### 9.2.4 Retrotranslator：跨越 JDK 版本

**背景问题**：JDK 5 引入了泛型、自动装箱、枚举、注解、可变参数等语法特性，编译出的 Class 文件无法直接运行在 JDK 1.4/1.3 上。**Retrotranslator 的作用就是把 JDK 5 编译出的 Class 文件，"逆向移植"为可在 JDK 1.4/1.3 上部署的版本**。

**JDK 升级的功能大致分类**：

1. **编译器层面改进**：自动装拆箱、泛型（类型擦除）；
    
2. **Java API 增强**：新的类库（如 `java.util.concurrent`）；
    
3. **需要在字节码中支持的改动**：如 `enum` 编译为带 `values()`/`valueOf()` 的特殊类；
    
4. **虚拟机内部的改进**：如新的指令、新的属性。
    

**Retrotranslator 只能模拟前两类**：

- 第二类（API 增强）→ 以独立类库的方式实现（把 JDK 5 的新类库打包进去）；
    
- 第一类（编译器改进）→ 使用 **ASM 框架直接对字节码进行处理**，把 `List<String>` 擦除为 `List`、把自动装箱拆为显式 `Integer.valueOf()` 调用等。
    

**洞见（第一性原理 + 工业现实）**：

1. **Retrotranslator 的本质是"字节码层面的向后兼容编译器"**——它证明了"Class 文件格式的稳定性"使得"在字节码层面做转换"成为可能。这是 Class 文件"平台中立性"的又一例证。
    
2. **现代工业中 Retrotranslator 已无实际用途**：JDK 8 已成为绝对主流，JDK 11/17/21 是主流 LTS。今天如果需要"跨 JDK 版本兼容"，业界做法是：
    
    - **Multi-release JAR**（JEP 238）：同一个 JAR 包含多个版本的类文件，JVM 按自身版本选择合适的版本；
        
    - **构建期降级编译**：用 `maven-compiler-plugin` 的 `release` 参数，在 JDK 17 环境下编译出 JDK 8 兼容的字节码；
        
    - **直接升级 JDK**：与其费心"逆向移植"，不如统一升级到 JDK 17 LTS。
        
    
3. **Retrotranslator 的方法论遗产**：它对字节码的精细操控思想，在今天的**字节码增强工具**（APM、Chaos Mesh、各类诊断工具）中依然活着。理解 Retrotranslator，是理解"字节码工具箱"历史脉络的一环。
    

### 9.3 实战：自己动手实现远程执行功能

这是全章最具"黑客美学"的一节——**向一个运行中的 JVM 注入并执行任意临时代码，且不依赖 JDK 版本、不改变原服务器部署、不依赖第三方库、不侵入原程序**。

**三个核心子问题**：

1. **如何编译提交到服务器的 Java 代码**？→ 客户端编译上传 Class 文件（而非 Java 源码），规避服务器端编译环境依赖；
    
2. **如何执行编译后的 Java 代码**？→ 要能访问服务器其他类库、且执行完能卸载（避免类泄漏）；
    
3. **如何收集执行结果**？→ 劫持 `System.out`，把输出重定向到我们自己的缓冲区。
    

**四个关键组件**：

**① HotSwapClassLoader**：扩展 `ClassLoader`，重写 `defineClass()` 使其**支持同一个类被多次加载**（每次加载都是全新的 Class 对象）。核心代码如下：

```
public class HotSwapClassLoader extends ClassLoader {
    public HotSwapClassLoader() {
        super(Thread.currentThread().getContextClassLoader());
    }
    
    // 关键：暴露父类的 protected defineClass 为 public，且每次调用都走 loadByte → defineClass
    public Class<?> loadByte(byte[] classByte) {
        return defineClass(null, classByte, 0, classByte.length);
    }
}
```

**关键**：每次调用 `loadByte()` 都返回**新的 Class 对象**——即使类名相同，因为是由同一个 HotSwapClassLoader 的新实例加载（或同一实例多次 defineClass 同名类在某些 JVM 实现下会报 `LinkageError`，所以 HotSwapClassLoader 通常配合"每次执行创建新实例"使用）。

**② HackSystem**：替换 `java.lang.System`。直接修改 Class 文件的字节码，把常量池中 `java/lang/System` 的字符串替换为 `org/fenixsoft/classloading/execute/HackSystem`。HackSystem 提供：

- 自定义的 `out`（PrintStream 子类），把输出写到内存缓冲区；
    
- `clearBuffer()` / `getBufferString()` 用于结果提取；
    
- 其余静态方法委托给原 System，保证兼容。
    

**③ ClassModifier**：操作 `byte[]` 数组，把 Class 文件中常量池的 `CONSTANT_Utf8_info` 项里内容为 `"java/lang/System"` 的常量，替换为 `"org/fenixsoft/classloading/execute/HackSystem"`。**这是纯字节码层面的"字符串替换"**——不通过源码，直接操纵 Class 文件的二进制结构（呼应第6章常量池结构）。

**④ JavaClassExecutor**：对外提供的执行入口：

```
public class JavaClassExecutor {
    public static String execute(byte[] classByte) {
        HackSystem.clearBuffer();
        ClassModifier cm = new ClassModifier(classByte);
        byte[] modifiedBytes = cm.modifyUTF8Constant(
            "java/lang/System", 
            "org/fenixsoft/classloading/execute/HackSystem"
        );
        HotSwapClassLoader hotSwapClassLoader = new HotSwapClassLoader();
        Class<?> clazz = hotSwapClassLoader.loadByte(modifiedBytes);
        try {
            Method method = clazz.getMethod("main", new Class[]{String[].class});
            method.invoke(null, new String[]{null});
        } catch (Throwable t) {
            t.printStackTrace(HackSystem.out);
        }
        return HackSystem.getBufferString();
    }
}
```

**执行流程串联**：

```
客户端编译好的 Class 文件（byte[]）
   ↓
ClassModifier 把常量池中 System 替换为 HackSystem
   ↓
HotSwapClassLoader.loadByte() 加载为新的 Class 对象
   ↓
反射调用 main() 方法
   ↓
main() 里的 System.out.println() 实际调用 HackSystem.out
   ↓
结果写入 HackSystem 的缓冲区
   ↓
execute() 返回缓冲区的字符串 → 传回客户端
```

**洞见（第一性原理 + 工业联系）**：

1. **这个"玩具级"远程执行器，正是现代诊断工具 Arthas 的雏形**。Arthas 通过 **JDK 1.6 引入的 Attach API**​ 把自己的 Agent 附着到目标 JVM 进程，再通过类加载机制加载字节码，实现运行时类的增强与替换：
    
    - `VirtualMachine.attach(pid)` 连接到目标 JVM；
        
    - `vm.loadAgent(agentJar, args)` 加载 Agent JAR；
        
    - Agent 的 `agentmain()` 方法通过 `Instrumentation` 接口拿到 `ClassFileTransformer`，可以对已加载类做 `retransform`、对未加载类做 `transform`；
        
    - 字节码修改后通过自定义类加载器加载，实现"热替换"。
        
    
2. **这套机制的"双刃剑"性质**：同样的 Attach API + Instrumentation 能力，既可以被 Arthas 用来诊断，也可以被恶意 Agent 用来"改变认证逻辑、绕过校验、插入隐藏接口"。**这就是为什么生产环境要对 JVM 的 Attach 端口、Agent 加载权限做严格管控**。
    
3. **现代工业中的"远程执行"**：
    
    - **Arthas**：阿里开源的 Java 诊断工具，核心机制就是 9.3 实战的"加强版"；
        
    - **BTrace**：通过字节码增强，在方法入口/出口插入追踪逻辑；
        
    - **JaCoCo**：覆盖率工具，字节码插桩；
        
    - **各类 APM（SkyWalking、Pinpoint）**：字节码增强实现链路追踪；
        
    - **JVM SandBox（阿里）**：基于 Instrumentation 的"无侵入" AOP 沙箱。
        
    
4. **安全边界**：`BootstrapClassLoader` 加载的类无法被 retransform（JVM 限制），这是 JVM 给自己的"安全底线"。

## 四、本章核心洞见总结（第一性原理视角，值得反复回看）

1. **JVM 留给程序员的"两个抓手"：类加载器（决定类的来源）+ 字节码生成（决定类的形态）**。掌握这两个抓手，就能做到"运行期改变 JVM 执行的东西"。
    
2. **Tomcat 是"正统打破双亲委派"的范本**：WebappClassLoader 默认"本地优先"，是为了解决"应用隔离 vs 容器共享"的矛盾。**打破双亲委派的真正动机，从来都是"隔离需求"与"共享需求"的拉锯**。
    
3. **JVM 认定"由不同类加载器实例加载的同名类属于完全不同的类型"**——这是 Tomcat 能做到"同名类多版本共存"、OSGi 能做到"模块级热插拔"的法理基础。
    
4. **OSGi 把类加载器从"树"变成了"网"**：类加载决策权从"类加载器的静态继承关系"转移到了"模块元数据和运行时服务注册中心"。带来极致动态性的同时，也带来极高的复杂度和死锁/内存泄漏风险。
    
5. **动态代理的精髓：在"原始类和接口还未知"的时候，就确定代理行为**。ProxyGenerator 按 Class 文件格式规范从零拼装字节码，这是"把第6章的 Class 文件结构倒着用"的典范。
    
6. **Retrotranslator 证明：Class 文件格式的稳定性使得"字节码层面的向后兼容转换"成为可能**。现代工业中它已退役，但其"字节码操控"思想在 APM、诊断工具、字节码增强框架中生生不息。
    
7. **9.3 实战的"HotSwapClassLoader + HackSystem + ClassModifier"三位一体，正是 Arthas 等现代诊断工具的雏形**。JDK 6 引入的 Attach API + Instrumentation 接口，把这种"运行期字节码注入"能力产品化、标准化。
    
8. **能力越强，责任越大**：同样的字节码增强机制，既能支撑 APM 链路追踪、Arthas 诊断，也能被恶意利用来篡改业务逻辑。**生产环境必须对 JVM 的 Attach 端口、Agent 加载做严格安全管控**——这是 9.3 实战留给我们的"安全觉醒"。
