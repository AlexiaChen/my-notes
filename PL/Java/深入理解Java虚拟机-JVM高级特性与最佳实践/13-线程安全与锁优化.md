## 二、逐节精读与洞见

### 13.1 概述 —— 线程安全的定义

Brian Goetz 对"线程安全"的经典定义：**当多个线程访问一个对象时，如果不用考虑这些线程在运行时环境下的调度和交替执行，也不需要进行额外的同步，或者在调用方进行任何其他的协调操作，调用这个对象的行为都可以获得正确的结果，那这个对象是线程安全的**。

**洞见**：这一定义的关键在于"**不考虑调度和交替**"——这意味着线程安全的代码，其正确性**不依赖于线程执行的时序**。这是判断"某段代码是否线程安全"的黄金标准。

### 13.2 线程安全

#### 13.2.1 Java 语言中的线程安全（5 个等级）

按照"实现线程安全的成本"从低到高，Java 中的线程安全分为 5 个等级 ：

|等级|含义|典型代表|
|---|---|---|
|**① 不可变（Immutable）**​|对象创建后状态不可变，天生线程安全|`String`、`Integer`、`Long`、`BigInteger`、`BigDecimal`、`LocalDateTime`|
|**② 绝对线程安全**​|完全符合线程安全的严格定义，任何时序下都正确|理论存在，实践中极少见（即使是 `Vector`，其复合操作如"先 check 再 add"仍需外部同步）|
|**③ 相对线程安全**​|保证单次方法调用的原子性，但复合操作仍需外部同步|`Vector`、`Hashtable`、`ConcurrentHashMap`|
|**④ 线程兼容**​|本身非线程安全，但调用方通过外部同步可使其安全|`ArrayList`、`HashMap`、`HashSet`|
|**⑤ 线程对立**​|无论怎样同步都无法在并发中使用|`Thread.suspend()` / `Thread.resume()`（已废弃）|

**洞见（第一性原理 + 创新判断）**：

1. **"不可变"是线程安全的终极形态**——它把"并发问题"从源头消灭：没有写操作，就不存在竞争。这就是为什么 Java 并发最佳实践第一条永远是"**优先考虑不可变对象**"。函数式编程（如 Scala、Kotlin）的并发模型，本质就是把"不可变"作为默认。
    
2. **"相对线程安全"是 Java 并发包的主流形态**：`ConcurrentHashMap` 保证单次 `put/get` 是原子的，但"先 get 再 put 若 absent"这种复合操作仍需 `putIfAbsent` 等原子方法。理解这一点，能避免无数并发 bug——**不要把"线程安全容器"等同于"所有复合操作都安全"**。
    
3. **工业现实对照**：Java 8 之后的 `java.util.concurrent` 包，大量使用"不可变 + CAS + 分段锁"的组合来实现"相对线程安全"。例如 `ConcurrentHashMap` 在 Java 8 中用 `Node` 数组 + CAS + `synchronized`（锁单个桶的头节点）实现高并发。
    

#### 13.2.2 线程安全的实现方法（三条路线）

实现线程安全有三条根本路线，成本递增 ：

**路线一：互斥同步（Mutual Exclusion & Synchronization）—— 悲观策略**

- **核心思想**："只要共享数据，就一定会有竞争"——访问前先加锁，让临界区同一时刻只被一个线程执行。
    
- **Java 中的实现**：
    
    - `synchronized`：基于对象头的 **Mark Word + Monitor**​ 实现。编译后在同步块前后插入 `monitorenter` / `monitorexit` 字节码。对**同一线程可重入**，会阻塞其他线程。
        
    - `ReentrantLock`（JDK 5 引入）：基于 **AQS（AbstractQueuedSynchronizer）**​ 实现，相比 `synchronized` 增加了三项高级功能：
        
        - **等待可中断**：`lockInterruptibly()` 允许等待锁的线程响应中断；
            
        - **公平锁**：构造时可选公平模式（按申请顺序获得锁）；
            
        - **多条件绑定**：一个 `ReentrantLock` 可绑定多个 `Condition` 对象。
            
        
    
- **代价**：线程阻塞和唤醒需要陷入内核（上下文切换开销 1-5 微秒），高并发下成为瓶颈。
    

**路线二：非阻塞同步（Non-Blocking Synchronization）—— 乐观策略**

- **核心思想**："竞争很少发生"——先进行操作，如果没有争用则成功；如果有争用则冲突重试（CAS 循环）。
    
- **硬件基础**：CAS（Compare-And-Swap）指令，x86 上是 `cmpxchg`。语义："**当且仅当 V 的当前值等于预期值 A 时，才将 V 更新为 B，返回更新前的值**"——整个操作是原子的。
    
- **Java 中的实现**：`AtomicInteger`、`AtomicLong`、`AtomicReference` 等原子类，底层调用 `Unsafe.compareAndSwapInt()` 等 native 方法。
    
- **ABA 问题**：CAS 只检查"值是否变化"，不检查"值是否曾被改过又改回"。解决方案：`AtomicStampedReference` 通过版本号（时间戳）解决。
    
- **代价**：冲突严重时，CAS 循环会浪费大量 CPU；ABA 问题需额外机制处理。
    

**路线三：无同步方案（No Synchronization）—— 根治策略**

- **核心思想**：如果代码根本不涉及共享数据，就不需要任何同步。
    
- **两种典型实现**：
    
    - **可重入代码（Reentrant Code / Pure Code）**：不依赖堆上数据、不调用非可重入方法、所有状态量由参数传入——返回结果可预测。这类代码天然线程安全。
        
    - **线程本地存储（Thread Local Storage）**：通过 `ThreadLocal` 把共享数据的可见范围限制在同一个线程内，线程间不共享 → 无线程争用。典型场景：每个请求对应一个服务器线程（如数据库连接 `Connection`、事务上下文 `TransactionContext`、用户会话 `Session`）。
        
    

**三种路线的选择决策树**：

```
是否存在共享可变数据？
├─ 否 → 无同步方案（可重入代码 / ThreadLocal / 不可变对象）✅ 最优
└─ 是 → 竞争是否激烈？
        ├─ 否 → 非阻塞同步（CAS + Atomic*）✅ 优
        └─ 是 → 互斥同步（synchronized / ReentrantLock）⚠️ 必要之恶
```

**洞见（第一性原理 + 工业联系）**：

1. **"互斥是因，同步是果"**：互斥是实现同步的一种手段，同步是目的 。理解这一点，就不会再把 `synchronized` 当作"银弹"——它只是众多同步手段中的一种，且是成本较高的一种。
    
2. **`synchronized` vs `ReentrantLock` 的工业选型**：
    
    - **JDK 5 时代**：`ReentrantLock` 性能全面优于 `synchronized`（synchronized 那时还是重量级锁）；
        
    - **JDK 6 之后**：HotSpot 对 `synchronized` 做了大量锁优化（本章 13.3 的全部内容），两者性能差距收窄；
        
    - **现代实践**：需要 `ReentrantLock` 的高级功能（可中断、公平锁、多条件）时才用它；否则优先用 `synchronized`——JVM 对其的优化空间更大（锁消除、锁粗化、偏向/轻量级锁都只对 synchronized 生效，对 ReentrantLock 无效）。
        
    
3. **ThreadLocal 的双刃剑**：它是"无同步方案"的工业级利器，但**使用不当会导致内存泄漏**——ThreadLocalMap 的 Entry 对 ThreadLocal 是弱引用，若 ThreadLocal 实例被回收但 value 未清理，value 会一直驻留直到线程结束。在线程池场景下（线程长期存活），这种泄漏会累积。**这就是为什么 ThreadLocal 用完后必须 `remove()`**——这一最佳实践直接源于第3章讲的"Metaspace/堆外内存泄漏"同类问题。
    

### 13.3 锁优化 —— HotSpot 对 synchronized 的 6 项优化

这是全章最具"工程美学"的一节。HotSpot 的锁优化遵循一个统一的设计哲学：**"让锁尽量在用户态内解决，尽量避免陷入内核态的阻塞/唤醒"**。围绕这个目标，JVM 提供了 6 项优化，按照"竞争程度从低到高"的顺序依次是：

#### 13.3.1 自旋锁与自适应自旋

**问题背景**：线程拿不到锁时，传统做法是挂起（Park）→ 阻塞 → 上下文切换。但**上下文切换的开销极大**（需要消耗数千个 CPU 时钟周期，引发内核态与用户态的切换）。如果锁持有时间非常短（微秒级），让等待线程"空转几圈"反而更划算。

**自旋锁（Spin Lock）**：

- 线程获取锁失败时，**不立即挂起，而是执行一个忙循环（自旋）**，循环体内不断重试 CAS；
    
- 自旋次数由 `-XX:PreBlockSpin` 控制（JDK 7 后移除该参数）；
    
- **代价**：自旋占用 CPU 时间。如果锁持有时间长，自旋就是纯粹的 CPU 浪费。
    

**自适应自旋（Adaptive Spinning，JDK 6 引入，默认开启）**​ ：

- 自旋次数**不再是固定值**，而是由 JVM 动态调整：
    
    - 如果"在同一个锁对象上，自旋等待刚刚成功获得过锁"，且持有锁的线程正在运行中 → JVM 认为这次自旋也很可能成功，**允许自旋更长时间**；
        
    - 如果"对于某个锁，自旋很少成功获得过" → JVM 认为再自旋也是浪费，**下次获取该锁时直接省略自旋过程，立即阻塞**；
        
    
- 自适应自旋是 JVM "学习型优化"的典型——它根据历史表现动态调整策略。
    

**洞见**：自适应自旋体现了 JVM 优化的精髓——**"用机器学习式的动态调整，替代人工设定的固定阈值"**。这与 JIT 的分层编译（动态阈值）、GC 的自适应策略（如 G1 的停顿预测）是同一哲学：JVM 通过观察运行时行为，自动调优参数。

#### 13.3.2 锁消除（Lock Elimination）

**机制**：JIT 编译器在运行时，通过**逃逸分析**检测到某段同步代码**不可能存在共享数据竞争**，则将该锁完全消除 。

**经典案例**：

```
public String concatString(String s1, String s2, String s3) {
    StringBuffer sb = new StringBuffer();
    sb.append(s1);
    sb.append(s2);
    sb.append(s3);
    return sb.toString();
}
```

`sb` 是局部变量，所有引用都未逃逸出 `concatString()` 方法 → JVM 通过逃逸分析确定"sb 不会被其他线程访问" → **JIT 直接消除 StringBuffer.append() 内部的 synchronized 锁**。

**工业联系**：这就是为什么**单线程场景下用 StringBuilder 替代 StringBuffer 并非性能必需**——JIT 会自动消除 StringBuffer 的锁。但作为防御性编程和代码可读性，单线程场景仍推荐 StringBuilder（避免无谓的锁获取尝试开销，尽管微小）。

#### 13.3.3 锁粗化（Lock Coarsening）

**机制**：如果 JVM 探测到**一串零碎的操作都对同一个对象加锁**，会将加锁同步的范围**扩展（粗化）到整个操作序列的外部**，减少加锁/解锁的次数 。

**典型案例**：

```
// 源码：循环内反复加锁
for (int i = 0; i < 100; i++) {
    synchronized (lock) {
        // 小临界区
    }
}

// 锁粗化后
synchronized (lock) {
    for (int i = 0; i < 100; i++) {
        // 小临界区
    }
}
```

**洞见（工业最佳实践）**：虽然 JVM 会自动做锁粗化，但**作为防御性编程，对于"循环内反复获取同一把锁"的场景，手动将锁提到循环外是更稳妥的做法**——JVM 的锁粗化有触发条件限制，手动优化能保证在所有 JDK 版本上都生效。

#### 13.3.4 轻量级锁（Lightweight Locking）

**核心思想**：在无竞争或低竞争场景下，**避免操作系统级互斥量（Mutex）的开销**，通过 JVM 层面的 CAS 操作尝试获取锁 。

**工作机制**：

1. 代码进入同步块，对象无锁（锁标志位 01）；
    
2. 在当前线程的栈帧中创建 **Lock Record**​ 空间，拷贝对象 Mark Word（Displaced Mark Word）；
    
3. JVM 用 **CAS 操作**尝试将对象 Mark Word 更新为"指向 Lock Record 的指针"，锁标志位变为 00；
    
4. **CAS 成功**​ → 线程获得轻量级锁，进入临界区；
    
5. **CAS 失败**​ → 说明有竞争：
    
    - 若 Mark Word 已指向当前线程的栈帧 → 说明当前线程已持有该锁（重入），直接进入；
        
    - 否则 → 轻量级锁**膨胀为重量级锁**，锁标志位变为 10，Mark Word 存储指向操作系统 Mutex 的指针，后续等待线程进入阻塞。
        
    

**对象头 Mark Word 的锁状态变化**​ ：

```
无锁      : [ hashCode | 分代年龄 | 0 | 01 ]
偏向锁    : [ 线程ID | Epoch | 分代年龄 | 1 | 01 ]
轻量级锁  : [ 指向栈中锁记录的指针 ] → 00
重量级锁  : [ 指向互斥量的指针 ] → 10
GC 标记   : [ 空 ] → 11
```

**洞见（第一性原理）**：

1. **轻量级锁的本质是"以 CAS 替代 Mutex"**：CAS 是用户态操作（纳秒级），Mutex 是内核态操作（微秒级，涉及上下文切换）。**轻量级锁把"锁竞争"在用户态内解决，避免了陷入内核的开销**。
    
2. **锁升级是单向的**：无锁 → 偏向锁 → 轻量级锁 → 重量级锁，**只能升级不能降级**​ 。这是因为降级需要复杂的"反向操作"，且实际收益有限——HotSpot 团队判断"维持单向升级"是更简单且足够优的设计。
    

#### 13.3.5 偏向锁（Biased Locking）—— 一个已被时代淘汰的优化

**核心思想**：在**绝对无竞争**场景下，连 CAS 操作都省掉——偏向锁"偏心"于第一个获取它的线程，后续该线程再进入同步块时，**不做任何同步操作**（无 CAS、无 Mutex）。

**工作机制**​ ：

1. 锁对象第一次被线程获取时，JVM 将锁标志设为 01，偏向模式设为 1；
    
2. 在 Mark Word 中**记录持有锁的线程 ID**；
    
3. 之后该线程每次进入这个锁相关的同步块时，**JVM 不再进行任何同步操作**（连 CAS 都不做）；
    
4. 当另一个线程尝试获取该锁时 → **偏向锁撤销**（需要进入 Safepoint）→ 升级为轻量级锁。
    

**🚨 重大演进：JDK 15 起偏向锁被默认禁用，后续版本彻底移除**

这是本章**最关键的时效补丁**。OpenJDK JEP 374 明确指出 ：

- **JDK 15 起**：`-XX:-UseBiasedLocking` 成为默认值，偏向锁被默认禁用；
    
- **JDK 17+**：彻底移除偏向锁相关逻辑；
    
- **废弃原因**：
    
    1. **性能收益不再明显**：早期受益于偏向锁的旧式同步集合（如 `Hashtable`、`Vector`）在现代应用中已被 `HashMap`、`ArrayList`、`ConcurrentHashMap` 替代；
        
    2. **撤销代价高昂**：偏向锁撤销需要进入 Safepoint（引发 STW 停顿），在"线程池 + 工作者线程"模型下（如 Web 应用），偏向锁的撤销开销反而拖累性能；
        
    3. **维护成本极大**：偏向锁逻辑与 JVM 底层的线程调度、GC 对象移动深度交织，代码复杂且阻碍虚拟线程（Project Loom）等新特性演进。
        
    

**工业实践建议**​ ：

- **JDK 15+ 应用**：无需修改代码，synchronized 默认走"无锁 → 轻量级锁（自旋）→ 重量级锁"的路径；
    
- **存量系统在 JDK 15/16 过渡期**：若确认 95% 以上同步块由单一线程访问（如日志门面、本地计数器），可保留 `-XX:+UseBiasedLocking`，但需监控 Safepoint 次数与停顿时间；
    
- **JDK 17+ 升级**：偏向锁相关参数全部移除，synchronized 直接进入轻量级锁流程。
    

**洞见（第一性原理 + 创新判断）**：

1. **偏向锁的兴衰是 JVM 优化哲学演进的缩影**：JDK 6 引入偏向锁时，假设"大部分锁由单一线程反复获取"；JDK 15 禁用偏向锁时，假设"现代应用大多采用线程池模型，锁的竞争是常态而非例外"。**JVM 优化的方向，始终跟随应用程序的真实模式而调整**。
    
2. **"给开发者的终极建议"**​ ：
    
    - **信任 JVM，但不要依赖魔法**：JIT 的锁消除、锁粗化很聪明，但写出结构清晰的代码（如手动在循环外上锁）永远是最稳妥的；
        
    - **拥抱新版本**：JDK 17+ 移除偏向锁，说明 JVM 团队认为"轻量级锁 + 快速 CAS"是未来的方向，**不要再纠结偏向锁的参数调优**；
        
    - **理解 synchronized 的现代形态**：在 JDK 17+ 中，synchronized 的实际表现是"无竞争时轻量级锁（CAS）+ 自旋；竞争激烈时升级为重量级锁"——这个模型简洁高效，是现代 Java 并发性能的基石。
        
    

### 13.4 本章小结

本章完成了两件事：**定义了线程安全的 5 个等级（不可变→绝对安全→相对安全→线程兼容→线程对立），并给出了实现线程安全的 3 条路线（互斥同步/非阻塞同步/无同步）**；**拆解了 HotSpot 对 synchronized 的 6 项锁优化（自旋/自适应自旋/锁消除/锁粗化/轻量级锁/偏向锁）**。它是 JMM（第12章）的"工程落地篇"——JMM 告诉你"什么是对的"，本章告诉你"如何既对又快"。

## 四、本章核心洞见总结（第一性原理视角，值得反复回看）

1. **线程安全的 5 个等级是"实现成本从 0 递增到不可能"的光谱**：不可变（0 成本）→ 绝对安全（极高成本）→ 相对安全（中等成本）→ 线程兼容（调用方承担成本）→ 线程对立（不可能）。**工业实践的第一原则：优先不可变**。
    
2. **实现线程安全的 3 条路线**：互斥同步（悲观、synchronized/ReentrantLock）→ 非阻塞同步（乐观、CAS/Atomic_）→ 无同步（根治、不可变/ThreadLocal/可重入代码）。__选择顺序应该是"无同步 > 非阻塞 > 互斥"_*——成本递增，收益递减。
    
3. **synchronized vs ReentrantLock 的现代选型**：JDK 6 之后两者性能差距大幅收窄。需要 ReentrantLock 的高级功能（可中断、公平锁、多条件）时才用它；否则优先 synchronized——JVM 对其的优化空间更大（锁消除/粗化/轻量级锁都只对 synchronized 生效）。
    
4. **HotSpot 锁优化的统一哲学："让锁尽量在用户态内解决"**：自旋避免阻塞、锁消除去掉无竞争的锁、锁粗化合并细碎的锁、轻量级锁用 CAS 替代 Mutex、偏向锁消除无竞争场景的 CAS。**锁升级路径是单向的**：无锁 → 偏向锁（JDK 15 前）→ 轻量级锁 → 重量级锁。
    
5. **🔥 偏向锁在 JDK 15 起默认禁用，JDK 17+ 彻底移除**（JEP 374）：原因是现代应用多采用"线程池 + 工作者线程"模型，偏向锁的撤销开销（Safepoint STW）反而拖累性能；同时早期受益于偏向锁的旧式同步集合（Hashtable/Vector）已被 HashMap/ArrayList/ConcurrentHashMap 替代。**现代 synchronized 的实际形态是"无锁 → 轻量级锁（CAS + 自旋）→ 重量级锁"**。
    
6. **自适应自旋是 JVM "学习型优化"的典范**：自旋次数不是固定值，而是根据历史表现动态调整——上次自旋成功则这次自旋更久，上次自旋失败则这次直接阻塞。**这体现了 JVM 优化的精髓：用运行时观测数据替代人工设定的固定阈值**。
    
7. **锁消除依赖逃逸分析**：JIT 通过逃逸分析判定"锁对象未逃逸出线程"时，直接消除锁操作。**这也是为什么单线程场景下 StringBuffer 和 StringBuilder 性能差距被 JVM 抹平——JIT 会自动消除 StringBuffer 的锁**。
    
8. **工业最佳实践**：
    
    - 并发设计优先用"不可变对象 + 无共享数据 + ThreadLocal"；
        
    - 必须用锁时，优先 synchronized，需要高级功能才用 ReentrantLock；
        
    - 循环内反复获取同一把锁时，**手动将锁提到循环外**（不要完全依赖 JVM 的锁粗化）；
        
    - JDK 15+ 应用无需（也无法）调优偏向锁参数；
        
    - ThreadLocal 用完后必须 `remove()`，避免线程池场景下的内存泄漏；
        
    - CAS 操作需注意 ABA 问题，必要时用 `AtomicStampedReference`。
        
    
9. **ThreadLocal 的双刃剑**：作为"无同步方案"的工业级利器，它通过把共享数据限制在线程内来避免竞争；但线程池场景下线程长期存活，ThreadLocal 中的 value 若未 `remove()` 会累积泄漏——这与第3章讲的堆外内存/Metaspace 泄漏是同类问题。
