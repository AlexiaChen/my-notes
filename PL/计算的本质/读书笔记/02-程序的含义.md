
# 第2章　程序的含义 —— 读书笔记

## 一句话先立住这一章在全书的位置

第1章给你"刚好够用的 Ruby 实验室"，第2章则回答一个更根本的问题：**当我们说一段程序"有意义"时，我们到底在说什么？**​ 这是全书从"编程"跨入"计算理论"的门槛。Tom Stuart 选择用 Ruby 把形式语义学"做实"——不是给你数学符号，而是让你亲手写出一个能跑的解释器/语义函数，这正是这本书的第一性原理：**用可运行的代码代替抽象符号，让"含义"变成可以观察、可以实验的东西**​ 。

## 2.1 "含义"的含义 —— 为什么要先问这个问题

日常写代码时，我们默认"程序的含义"就是"它跑起来会发生什么"。但作为一门工程学科，编程语言的"含义"必须被**精确、无歧义、可论证**地定义，否则：

- 编译器作者和程序员对"同一个构造"的理解可能不一致；
    
- 无法证明"编译器优化前后程序含义不变"；
    
- 无法证明"这个程序永远不会越界/空指针解引用"。
    

所以"含义"在这里是一个**工程刚需**，而非哲学玄谈。形式语义学（formal semantics）就是给编程语言下"精确含义定义"的学科，主要分为操作语义、指称语义、公理语义三大类 。Stuart 在这一章只聚焦前两类，因为它们最容易被 Ruby 代码直观表达。

> 💡 洞见：这一节真正想建立的直觉是——**"含义"不是程序跑完后的副作用，而是"程序"到"数学对象/行为"的一个映射**。一旦你接受这个设定，后面小步/大步/指称三种语义就只是"选哪种映射方式"的不同答案。

## 2.2 语法 —— 先有结构，才有含义

语义的前提是**语法**：哪些符号串是合法程序。语法把字符流组织成**抽象语法树（AST）**——只保留与含义有关的结构，丢掉括号、分号等"书写细节"。这一步至关重要：后面所有语义都是**定义在 AST 上**的映射。

工业联系：任何真实语言的工具链都从这里开始。Ruby 自身的 `SyntaxTree`/`Ripper` 把源码解析成 AST；`Rubocop` 基于 `rubocop-ast` 的 AST 做 lint/格式化，每条规则（cop）本质是一个**访问者（Visitor）**，对特定节点类型（如 `on_def`、`on_send`）做处理 ；Shopify 的 Ruby LSP 也用 `Syntax Tree` + Visitor 模式遍历 AST 来提供编辑器智能提示 。这和第2章 2.6 实现解析器是同一件事——你手写一个 tiny 语言的 parser，正是在复刻工业语言工具的第一步。

## 2.3 操作语义 —— "程序如何执行"

操作语义的核心思想：**想象一台理想的抽象机器，为程序在这台机器上的执行定义精确规则**​ 。它回答"程序如何一步步运行"，而非"程序是什么"。Stuart 用一门叫 **SIMPLE**​ 的玩具语言贯穿本节，把推理规则写成 Ruby 类（`Number`、`Add`、`LessThan`、`Assign`、`If`、`While`……），每个节点都能 `#reduce`/`#evaluate`。

### 2.3.1 小步语义（Small-Step Semantics）

小步语义又称**结构化操作语义（SOS）**，由 Gordon Plotkin 提出 。核心：定义一组**规约规则（reduction rules）**，每次只对表达式做**一步**化简，迭代直到得到最终值 。例如 `(1+2)*3 → 3 * 3 → 9`：先规约子表达式 `1+2`，再规约乘法 。

实现上，Stuart 构造一个 `Machine`：它持有一个"当前表达式 + 环境"，反复调用 `#reduce`（一步规约），打印每一步，直到不可再约。这正是 Rust 移植版 `computation.rs` 的做法——`Machine::new(...).run()` 会逐步输出 `4 + 10 → 14` 。

小步的特点与适用场景 ：

- **粒度细**：每步可见，能观察中间状态；
    
- **能刻画非终止**：不终止 = 无限归约链（这一点到第8章讲停机问题时是关键）；
    
- **擅长并发/非确定/控制流**（异常、break、continue 等复杂控制流都能建模）；
    
- 代价是规则更多、推导树更大、语言设计者要指定更多求值顺序细节。
    

> 💡 洞见：小步语义的本质是**把"求值"变成"重写系统"**。你不是在"计算"，而是在反复对一棵 AST 做局部替换，直到它变成一个"值"。这个视角切换极其重要——它把"运行程序"降格为"按规则改写字符串/树"，为后面第7章的 tag system、图灵机（都是"按规则改写"）埋下统一伏笔：**计算 = 重写**。

### 2.3.2 大步语义（Big-Step Semantics）

大步语义又称**自然语义（Natural Semantics）**，由 Gilles Kahn 提出 。与小步相反，它**一步到位**：直接定义"表达式 e 在环境 σ 下求值为结果 v"，记作 `⟨e, σ⟩ ⇓ v` 。对复合表达式，做法是递归求值子表达式，再把子结果组合成最终结果——**它本质上就是一个递归解释器**​ 。

Stuart 的实现：`#evaluate` 方法对每个 AST 节点递归调用子节点的 `#evaluate`，组合出结果。如书中所说，大步实现"用了更多堆栈"，靠递归调用栈记住"在整体运算中的位置" 。

大步的特点与适用场景 ：

- **粒度粗**：直接给出输入输出关系，忽略中间步；
    
- **规则更少、更接近递归解释器**，对函数式语言的定义非常自然；
    
- 最著名的应用是 **Standard ML 标准定义第6章**（用大步风格解释 ML 的全部运行时行为），OCaml 也用大步补充其小步定义 ；
    
- 代价是**难以自然刻画并发、非确定、发散（不终止）和运行时错误**——这些在大步里要么表达不出来，要么要额外机制 。
    

**小步 vs 大步（一张表理清）**​ ：

|维度|小步（SOS）|大步（Natural）|
|---|---|---|
|求值粒度|每次一步|一步到位|
|中间状态|可观察|不可观察|
|实现方式|迭代/循环|递归|
|非终止|显式（无限链）|难以区分|
|擅长|并发、调试、控制流|编译器优化、类型推导、ML系语言定义|

两者关系（确定性语言下）：`C ⇓ R` 当且仅当 `C →* R`（大步可推出小步，小步可推出大步），见定理 9.1 。

> 💡 洞见：两种语义不是"谁对谁错"，而是**同一枚硬币的两面——一个盯着"过程"，一个盯着"结果"**。工业界编译器前端常用大步风格写解释器（递归求值直观），而需要调试器、并发分析、静态分析时则倾向小步（中间状态可见）。理解这一点，你就理解了为什么真实语言规范（如 ML、OCaml）常常**两套语义并存**。

## 2.4 指称语义 —— "程序是什么"

指称语义由 **Dana Scott 和 Christopher Strachey**​ 在 1960s–70s 提出 ，核心是：**把程序映射到一个数学对象（通常是函数）**，用更底层的数学语言解释程序 。它回答"程序**是**什么"，而非"程序如何执行" 。

三个基本原则 ：① 每个语法短语都有含义（denotation）；② 含义是良定义的数学对象（常为高阶函数）；③ 复合短语的含义是其直接子短语含义的数学组合——这第三条叫**组合性（compositionality）**，是指称语义的灵魂 。

实现上，Stuart 用 Ruby 写"语义函数" `[]`：把 AST 节点映射到 Ruby 对象（数字映射到 `Integer`，布尔表达式映射到 `true/false`，语句映射到"状态变换函数" `State → State`）。对 `while` 循环这类递归构造，则用**最小不动点（least fixed point）**​ 给出含义——`fix(f) = ⊔ₙ≥₀ fⁿ(⊥)`，即使循环不终止，含义也是良定义的（⊥，即"无信息/非终止"）。

指称语义的"语义域"取决于语言 ：布尔表达式→布尔值；算术表达式→整数；命令式语言→状态变换 `State→State`；SQL 查询→关系集合；甚至动画/MIDI 可分别对应声音波 。Haskell 这类纯函数式语言的指称语义尤其自然：程序 `10`、`9+1`、`2 * 5`、`sum[1..4]` 都**指称整数 10**​ ；Haskell98 标准甚至**只规定了非严格指称语义，把"如何执行"留给了实现**​ 。

> 💡 洞见（本章最重要的一条）：**操作语义和指称语义是"how"与"what"的分野**。小步/大步告诉你"怎么跑"，指称语义告诉你"它等价于哪个数学函数"。这两套视角到后面第9章"抽象解释/类型系统"会再次合流——静态分析的本质，就是**用一个"更粗糙但可计算"的指称域（如"符号+整数"）去近似真实指称语义**，从而在编译期推断程序性质。指称语义不是屠龙术，它是类型系统、抽象解释、编译器优化正确性的理论地基。

## 2.5 形式化语义实践 —— 为什么值得付出这份复杂度

### 2.5.1–2.5.3 形式化、找到含义、备选方案

这几节 Stuart 在论证：**给语言一个形式化语义是值得的**。一份好的形式语义 ：

- 比"参考实现"更精确，比"社区直觉"更可靠；
    
- 能回答"这个实现正确吗？"；
    
- 支撑语言的分析、变换、**程序性质证明**和**语言设计改进**（如组合性）。
    

工业实例（这是形式语义真正"落地"的地方）：

- **CompCert**：第一个经过机器检验证明"语义保持"的现实级优化 C 编译器（针对 ISO C 2011，生成 ARM/PowerPC/RISC-V/x86 高效代码）。它用 Coq 证明"编译后可执行代码的行为与源程序语义完全一致" ；2026 年 CompCert 更成功通过 DO-178C/DO-333/DO-330 鉴定，用于 ATR 42/72 新一代多用途计算机（MFC_NG）的适航认证 ——这意味着**形式语义直接进入了航空安全关键软件**。
    
- **ASTRÉE 静态分析器**：基于**抽象解释**，用操作语义的"具体语义"做基础，构造"符号+整数"等抽象域，对空客 A340/A380 飞控软件（数十万行 C）做运行时错误静态验证（数组越界、除零、断言违反等） 。
    
- **Java/Android 安全**：有工作为大型 Java 子集定义**小步操作语义**，作为开发"可证明正确"的静态分析与认证编译器的根基 ；也有为 Android Smali/Dalvik 字节码定义操作语义（Smali⁺），支撑恶意应用检测与安全分析 。
    
- **区块链/Cardano**：有项目用 Scala 3 的 tagless-final 风格把指称语义做成"可执行的 eDSL"，直接用于 Cardano 账本规范 ——"代码即规约"。
    

> 💡 洞见：形式语义绝不是学术摆设。它的真实价值在于**"正确性可被机器证明"**——当你要证明"编译器没引入 bug""飞控软件不会数组越界""智能合约按规约运行"时，必须先有"程序含义"的精确定义。这就是为什么航空（DO-178C）、加密库、OS 内核、区块链会用 Coq/Isabelle 做形式化验证。Stuart 用 Ruby 把这堵高墙拆低了：你写的每一个语义函数，都是这个宏大工程的"微型预演"。

## 2.6 实现语法解析器 —— 把"字符串"变成"AST"

最后一节把前面所有东西串起来：手写一个 **parser**，把程序文本解析成 AST，再交给前面写好的语义/解释器去求值。这是编译器前端的标准流程：**词法分析（lex）→ 语法分析（parse）→ AST → 语义/解释/编译**。

工业联系再次呼应：Ruby 的 `SyntaxTree`（基于内置 `Ripper`）把源码解析为 AST 并用 Visitor 模式遍历 ；`Rubocop` 的每个 lint 规则就是一个 Visitor ；你也可以用 Visitor + 递归求值器（Interpreter 模式）直接解释执行 AST 。Stuart 在这一节让你亲手实现这个链条的最小版本——**理解了它，你就理解了每一个真实语言工具（编译器、linter、格式化器、IDE）的"心脏"是怎么跳的**。

## 全章脉络与"第一性原理"总结

把第2章的逻辑主线抽出来，是这样的递进：

1. **含义需要被精确定义**（2.1）——否则无正确性可言；
    
2. **先有语法/AST，才有含义**（2.2）；
    
3. **操作语义**（2.3）：用"抽象机+规约规则"定义**如何执行**——小步（过程/重写）vs 大步（结果/递归解释器）；
    
4. **指称语义**（2.4）：用"语义函数"把程序映射到**数学对象**——组合性 + 不动点处理递归/不终止；
    
5. **形式化语义的价值**（2.5）：支撑验证、优化正确性、语言设计——并在航空/编译器/静态分析/区块链中真实落地；
    
6. **实现 parser**（2.6）：把理论闭环成"可运行的 tiny 语言"。
    

**一条贯穿全书的洞见**：这一章其实在悄悄建立"通用计算模型"的第一块砖——**程序 = AST + 语义**。无论后面第3章的有限自动机、第5章的图灵机、第6章的 λ 演算，本质都是"一串结构 + 一组重写/规约规则"。小步语义的"按规则逐步重写"尤其具有预言性：它和第7章的 tag system、图灵机的"配置迁移"是**同一种思维方式**。读懂第2章，后面所有"计算模型"都会显得不那么陌生——它们只是在换不同的"AST 形状"和"规约规则"而已。
