
# 《垃圾回收的算法与实现》读书笔记 · 第9章 RC Immix 算法

> 延续前八章建立的"第一性原理"视角：引用计数法（第3章）有三个老问题——计数器频繁增减拖累吞吐量、计数器占内存、循环引用无法回收；Immix（第5章）则用 Block+Line 的堆组织、bump-pointer 分配、按需压缩解决了标记-压缩的"全堆扫描"痛点。第9章的 RC Immix（2013 年 Rifat Shahriyar、Stephen M. Blackburn 等人在 OOPSLA 提出）做了一件极其漂亮的事——**把两者融合，让引用计数第一次在高性能赛道上追平了最快的分代追踪式收集器**。本章的目的，正如书名副标题所言：把引用计数"吞吐量低"这一最大缺点，改善到实用级别。

---

## 一、9.1 目的：引用计数为何"高性能不及格"

要理解 RC Immix 的目的，必须先看清引用计数在高性能赛道上落后的根本原因。

直到 2012 年，优化后的引用计数仍比最快的追踪式收集器慢 10% 左右——这看似不大，但对性能敏感的应用而言是"不可采用的壁垒"。进一步剖析发现，**剩余的性能差距主要来自堆组织方式，而非计数本身**：

- **传统引用计数用空闲链表（free-list）管理堆**：分配时要遍历链表找合适分块；回收时要把分块重新链回空闲链表
    
- **空闲链表分配器的缓存局部性差**：对象分散在堆中各处，mutator 访问时 cache miss 高
    
- **引用计数的"局部性优势"被空闲链表吞噬**：引用计数本是"局部操作"（只动受影响对象），但空闲链表让分配变成了"全堆搜索"
    

> 💡 **第一性原理洞察**：RC Immix 的核心洞见是——**引用计数的真正瓶颈不是"计数"，而是"堆怎么组织"**。一旦把引用计数的"对象级局部回收"能力，嫁接到 Immix 的"线/块级连续分配 + 按需压缩"的堆组织上，引用计数的局部性优势就能完全释放。这不是简单的"1+1"，而是**用 Immix 的堆组织消解了引用计数的堆管理开销，同时用引用计数替代了 Immix 的全堆 tracing 回收**——两种算法在最擅长的维度上互补。

论文原话："Our work identifies heap organization as the principal source of the remaining performance gap."（我们的工作确认，堆组织是剩余性能差距的主要来源。）RC Immix 用 Immix 的 line 和 block 堆结构，替换了引用计数传统的 free-list 堆组织。

## 二、9.2 合并型引用计数法（Coalesced Reference Counting）

### 核心思想：只关心"期初和期末"，忽略中间过程

传统引用计数法在每次指针赋值时都要做 `ref_cnt--` 和 `ref_cnt++`。但观察一个事实——**如果对同一个对象分别进行一次增量和减量操作，两者会互相抵消，最终计数器的值并没有变化**。

合并型引用计数法（Levanoni & Petrank, 2001）的核心洞察是：**选定一个时间区间，在该期间内不进行计数器的增减，只记录"发生了什么"，等区间结束（更改缓冲区满）时一次性修正**。

### 算法机制

**写入屏障**（合并型）：

```
write_barrier_coalesced_RC(obj, field, dst):
    if not obj.dirty:
        register(obj)           # 首次改动时，把 obj 注册到更改缓冲区
    obj.field = dst
```

**关键动作**：

1. 指针改动时，不直接增减计数器，而是把"发生改动的对象"注册到**更改缓冲区（Modified Buffer）**
    
2. 同时，该对象的所有子对象信息也被记录——因为 mutator 可能频繁改 obj 的多个域
    
3. 当更改缓冲区满时，触发 GC：
    
    - 先对缓冲区中记录的"当前引用的子对象"做增量
        
    - 再对"最初引用的子对象"做减量
        
    - 净效果等价于"期初和期末的差值"，中间所有抵消操作都被省略
        
    

### 为什么有效

考虑对象 X 的指针在一段时间内频繁变更：X→A→B→A→B→…

- **传统引用计数**：每次变更都要 `inc(B); dec(A)`，6 次操作
    
- **合并型引用计数**：只记录"X 发生过改动"，期末时 `inc(当前B); dec(最初A)`，2 次操作
    

**当对象间引用关系频繁变化时，合并的效果极其显著**——大部分 inc/dec 成对抵消，被彻底省略。

### 优点与代价

- ✅ **吞吐量大幅提升**：忽略了 inc 和 dec 相抵消的部分
    
- ❌ **增加了 mutator 的最大暂停时间**：更改缓冲区满时要 STW 查找缓冲区、修正计数器
    
- ❌ **需要额外内存**：更改缓冲区本身占用空间
    
- 🔧 **调优旋钮**：减小更改缓冲区 → 暂停时间缩短，但吞吐量下降。需要权衡。
    

> 💡 **洞见**：合并型引用计数体现了 GC 设计中的一个精妙范式——**"延迟批量处理"**。它和上一章增量式 GC 的思想有异曲同工之妙：都是把"频繁发生的小操作"合并为"偶尔发生的大操作"。区别在于：
> 
> - 增量式 GC 是为了打散 STW → 用写屏障+三色标记，让 GC 和 mutator 交替
>     
> - 合并型引用计数是为了消除冗余操作 → 用更改缓冲区，把多次 inc/dec 合为一次净修正
>     
> 
> 两者都在"操作频率"和"单次开销"之间做权衡，是同一种工程哲学的不同应用。

## 三、9.3 合并型引用计数法 + Immix：RC Immix 的融合之道

这是本章的高潮。融合不是简单拼接，而是**在三个维度上深度整合**：

### 维度一：双计数器体系（对象计数 + 线计数）

RC Immix 引入了**两层计数器**：

|计数器|作用域|含义|
|---|---|---|
|**对象引用计数**​|单个对象|指向该对象的引用数量|
|**线存活对象计数（line live object count）**​|一条 Line（256B）|该线内当前存活对象的数量|

**为什么需要线计数？**​ 因为 Immix 以"线"为最小回收单位——只有整条线的存活对象数为 0 时，这条线才能被回收。对象计数器告诉 GC "这个对象死没死"，线计数器告诉 GC "这条线能不能回收"。

**线的"Born Dead"优化**：新分配的线初始存活对象计数为 0（即"生而为死"）。如果一条线上的所有新对象在第一次 GC 到来前就死光了，RC Immix 根本不需要为这条线做任何计数工作——直接整线回收。这完美契合"弱分代假说"（大部分对象朝生夕灭）。

### 维度二：撤除空闲链表，拥抱 Bump-Pointer

传统引用计数的致命伤是 free-list 分配器：

- 分配时要查找链表、更新元数据
    
- 回收时要维护链表结构
    
- 缓存局部性差
    

RC Immix 完全撤除空闲链表，采用 Immix 的**线内 bump-pointer 分配**：

- 分配时只需检查线内是否有足够空间，然后移动 `free` 指针
    
- 省去了把分块重新连接到空闲链表的处理
    
- 分配本身就是 O(1) 的指针推进
    

### 维度三：机会性复制（Opportunistic Copying）—— 抗碎片

引用计数法有个固有缺陷：**它是对象局部的（object-local），不知道一个对象的所有引用在哪里，因此难以做复制压缩**。RC Immix 抓住了**两个复制时机**：

**① 被动碎片整理（Passive Defragmentation）—— 针对新对象**

- 新对象在"第一次 GC"时，所有引用关系都已经确定（要么被根或其他活对象引用，要么死）
    
- 此时可以安全地把存活的新对象复制到新的块，原块整块回收
    
- 这本质上就是"复制算法"，但因为只针对新对象，复制成本可控
    

**② 主动碎片整理（Proactive/Reactive Defragmentation）—— 针对旧对象 + 循环引用**

- 利用备份追踪（backup tracing）做周期性的循环垃圾回收
    
- 在追踪过程中，顺带把存活对象复制到新块（opportunistic copying）
    
- 当碎片率达到阈值时触发 reactive defragmentation；平时用 copy reserve 做 proactive defragmentation
    

### 循环引用的处理：备份追踪收集器

引用计数法无法处理循环引用——RC Immix 的解决方案是**集成一个备份追踪收集器（backup tracing cycle collector）**：

- 周期性地做 tracing（从根出发标记活对象）
    
- tracing 时标记活对象和对应的线，并修正线计数
    
- tracing 结束后，未标记的线被回收
    
- 这本质上就是第2章的标记-清除，但是作为"引用计数的补充"周期性运行
    

> 💡 **第一性原理洞察**：RC Immix 的融合揭示了 GC 设计的最高艺术——**"让每种机制只做自己最擅长的事"**：
> 
> - **引用计数**：负责日常回收——对象死时立即回收，局部性好，增量性强
>     
> - **线/块堆组织**：负责空间管理——bump-pointer 分配、整线/整块回收
>     
> - **机会性复制**：负责抗碎片——新对象首次 GC 时复制、备份追踪时顺带复制
>     
> - **备份追踪**：负责完备性——周期性清除循环垃圾、修正计数误差
>     
> 
> 这四者不是简单叠加，而是**形成了一条流水线**：引用计数做 99% 的回收工作，备份追踪只在必要时介入；bump-pointer 让分配极快，线计数让回收极简；机会性复制在回收的同时顺带完成压缩。每一种机制都在自己最有效的作用点上发力，互不干扰又彼此增强。

### 工业级性能数据

RC Immix 的论文给出了震撼的结果 ：

> "RC Immix closes the 10% performance gap, matching the performance of a highly tuned production generational collector."
> 
> （RC Immix 消除了这 10% 的性能差距，匹配了高度调优的生产级分代收集器的性能。）

具体而言：

- 相比传统引用计数，吞吐量**平均提升 12%**
    
- 在某些基准测试下，**甚至超过追踪型 GC**
    
- 相比生产级分代收集器（Gen Immix），总体时间快 **3%**，最坏情况慢 6%，最佳情况快 21%
    

这是引用计数法历史上**第一次**在高性能赛道上追平了最快的分代收集器。

## 四、9.4 优点和缺点：权衡清晰

### 优点

**① 吞吐量大幅改善**​

两个原因：

- **导入合并型引用计数**：不再通过写屏障频繁执行计数器增减，即使对象间引用关系频繁变化，吞吐量也不会下降太多
    
- **撤除空闲链表**：以线为单位管理分块，线内分配只需移动指针；省去了把分块重新链接到空闲链表的处理
    

**② 保持引用计数的固有优势**：

- **即时回收**：对象死时立即释放，资源型对象可及时释放
    
- **增量性**：回收动作分散在 mutator 运行过程中，最大暂停时间短
    
- **局部性**：操作只涉及受影响对象，缓存友好
    

**③ 抗碎片**：通过机会性复制，在引用计数基础上实现了压缩，消除了碎片问题

**④ 匹配生产级性能**：首次让引用计数达到高性能 GC 的实用级别

### 缺点

**① 最大暂停时间增长**​

- 合并型引用计数法本身会增加暂停时间（更改缓冲区满时需要 STW 修正计数器）
    
- 可以通过**调整更改缓冲区大小**来缩短暂停时间（但会牺牲吞吐量）
    
- RC Immix 整体的暂停时间比纯引用计数法更长
    

**② 线级内部碎片**​

- "只要线内还有一个非垃圾对象，就无法将其回收"
    
- 当线计数器为 1（线内还有一个活动对象）时，即使该活动对象只占线的极小一部分，整条线也无法回收，**大部分线空间被白白消耗**
    
- 这是"线"作为回收最小单位带来的固有代价
    

**③ 实现复杂度高**：

- 需要维护对象计数器 + 线计数器 + 更改缓冲区 + 备份追踪收集器
    
- 对象头部的位分配极其紧张（8 位中要用 2 位记录合并型引用的 dirty 状态、1 位 mark、1 位 new 标识、4 位存引用计数）
    

> ⚠️ **核心洞见**：RC Immix 的优缺点完全同源——都来自"双计数器 + 更改缓冲区 + 机会性复制"这一融合设计。
> 
> - 吞吐量的提升 ← 合并型引用计数消除了冗余 inc/dec + 撤除空闲链表
>     
> - 暂停时间的增长 ← 更改缓冲区满时的批量修正
>     
> - 抗碎片能力 ← 机会性复制（但增加了实现复杂度和备份追踪的 STW）
>     
> - 线级碎片 ← 线作为最小回收单位的代价
>     
> 
> 这再次印证了 GC 设计的"不可能五边形"：RC Immix 在"吞吐量、最大暂停时间、堆利用率、碎片、实现复杂度"五个维度上做了一次精妙的重新平衡——**大幅优化了吞吐量和碎片，代价是暂停时间略增、实现复杂度飙升**。

## 六、工业实践印证

### 1. RC Immix 的学术影响

RC Immix 论文发表于 OOPSLA 2013，被誉为"引用计数法的翻身之作"。它直接启发了一系列后续工作：

- **Sticky Immix**：把 Immix 扩展为分代式，无需复制式新生代，通过标记旧对象、限制追踪范围到新对象来实现分代回收
    
- **Fast Conservative Garbage Collection**（2015）：将 RC Immix 的思想扩展到保守式 GC 场景，证明 RC Immix 的堆组织也能为 C/C++ 等非精确式环境带来性能提升
    
- **Rust 的引用计数优化**：Rust 的 `Rc<T>` 和 `Arc<T>` 虽然是编译期确定的引用计数，但 RC Immix 的"合并型计数"思想在 Rust 的某些 runtime 优化中有借鉴
    

### 2. 与生产环境收集器的对比定位

|收集器|类型|适用场景|与 RC Immix 的关系|
|---|---|---|---|
|**RC Immix**​|引用计数 + Immix|需要确定性回收 + 高性能|本章主角|
|**JVM G1**​|分代 + 标记-整理|大堆、可预测停顿|竞争对手，RC Immix 在论文中与之性能相当|
|**JVM ZGC**​|并发 + 染色指针|超大堆、极致低延迟|另一条技术路线（并发而非引用计数）|
|**Go GC**​|并发三色标记-清除|高并发微服务|另一条技术路线|
|**CPython GC**​|引用计数 + 分代循环 GC|通用脚本语言|传统引用计数的工业代表，未采用 RC Immix 的堆组织优化|

> 💡 **工程启示**：RC Immix 证明了**引用计数法在高性能赛道并非"天生不及格"**——之前的落后是因为堆组织不当，而非计数机制本身。一旦用 Immix 的堆组织替换 free-list，引用计数就能追平分代追踪式 GC。
> 
> 这为 GC 选型提供了一个**全新的维度**：
> 
> - 需要**确定性回收**（资源及时释放）→ 引用计数路线（RC Immix 是最佳实现）
>     
> - 需要**极致低延迟**（超大堆）→ 并发路线（ZGC/Shenandoah）
>     
> - 需要**高吞吐 + 可预测停顿**​ → 分代追踪路线（G1）
>     
> 
> RC Immix 的意义，是让"引用计数"从"性能敏感的禁区"变成了"可严肃考虑的选项"。

### 3. 为什么主流工业 GC 仍未广泛采用 RC Immix

尽管 RC Immix 性能卓越，但截至 2025 年，主流工业 GC（HotSpot、Go、CoreCLR）仍未直接采用。原因包括：

- **循环引用仍需备份追踪**：RC Immix 并非纯引用计数，仍需周期性 tracing，实现复杂度高
    
- **写屏障仍是必需**：合并型引用计数需要写屏障维护更改缓冲区
    
- **对象头部位紧张**：4 位引用计数在极端场景下仍可能溢出（需用 sticky 技术 + 备份追踪修正）
    
- **生产环境的路径依赖**：HotSpot、Go 等已有成熟的追踪式 GC 实现，切换到 RC Immix 需要重写整个内存管理系统
    
- **多核扩展性**：引用计数的"局部性"在多核高并发场景下，可能成为缓存一致性的瓶颈（多个核同时修改同一对象的计数器引发 cache line bouncing）
    

但 RC Immix 的思想已被广泛吸收：

- **G1 的 Region 化**​ ← Immix 的 Block/Line 思想
    
- **ZGC 的染色指针**​ ← 类似 RC Immix 的"在指针/头部编码元数据"思想
    
- **Go 的混合写屏障**​ ← 合并型引用计数的"延迟批量处理"思想

## 七、承上启下：RC Immix 在全书算法篇的位置

至此，我们已经学完了九章内容。回顾全书算法篇的演化主线：

|章节|核心算法|解决的矛盾|遗留问题|
|---|---|---|---|
|第2章|标记-清除|自动识别垃圾|碎片、STW 长|
|第3章|引用计数|避免长 STW、即时回收|吞吐量低、循环引用|
|第4章|复制算法|消除碎片|堆利用率 50%|
|第5章|标记-压缩|无碎片 + 高堆利用率|压缩成本高|
|第6章|保守式 GC|C/C++ 等非合作环境的 GC|不能移动对象|
|第7章|分代 GC|用统计规律大幅降低 GC 成本|写屏障开销|
|第8章|增量式 GC|把长 STW 打散为短停顿|吞吐量下降|
|**第9章**​|**RC Immix**​|**引用计数的吞吐量瓶颈**​|**暂停时间略增、实现复杂**​|

**关键洞察**：RC Immix 是本书算法篇的**高潮**——它不再发明新算法，而是**把前八章几乎所有核心思想熔于一炉**：

- 用**合并型引用计数**（第3章延迟引用的进化版）解决计数器开销
    
- 用**Immix 的线/块堆组织**（第5章）解决分配速度和碎片
    
- 用**备份追踪**（第2章标记-清除 + 第3章部分标记-清除思想）解决循环引用
    
- 用**机会性复制**（第4章复制算法思想）做被动/主动碎片整理
    
- 用**"Born Dead"新对象优化**（第7章分代思想）契合弱分代假说
    

**RC Immix 证明了：GC 算法的未来不在"发明新算法"，而在"精巧地组合已有算法"**。每一种基本算法都有其擅长的场景和固有的代价，通过精心设计的堆组织、写屏障、缓冲区机制，可以让多种算法在各自最有效的维度上协同工作，达到"1+1 >> 2"的效果。

**带着这个视角进入"实现篇"（第二部分）**，你会看到：Python、Dalvik VM、Rubinius、V8 等真实语言运行时，都不是单纯使用某一种算法，而是**RC Immix 思想的工业化身**——组合多种算法、在堆组织层面优化、用写屏障连接各部分。这正是本书下半部分的精华所在。

---

📌 **本章核心收获**：

- RC Immix 的第一性原理：引用计数的真正瓶颈不是"计数"，而是"堆组织"——用 Immix 的线/块堆组织替换 free-list，引用计数就能追平最快的分代收集器
    
- 合并型引用计数法：只关心"期初和期末"，中间 inc/dec 通过更改缓冲区合并抵消，大幅提升吞吐量，代价是暂停时间增长
    
- RC Immix 的双计数器体系：对象引用计数（管对象生死）+ 线存活对象计数（管线能否回收），"Born Dead"优化让朝生夕灭的对象零成本回收
    
- 机会性复制：新对象首次 GC 时被动复制 + 备份追踪时主动复制，在引用计数基础上实现抗碎片
    
- 备份追踪收集器：周期性 tracing 解决循环引用、修正计数误差——引用计数与追踪式 GC 的深度融合
    
- 性能数据：吞吐量平均提升 12%，总体性能匹配甚至超过生产级分代收集器
    
- 缺点：暂停时间略增（可通过调整更改缓冲区权衡）、线级内部碎片（线内有一活动对象则整线不能回收）、实现复杂度高
    
- RC Immix 是全书算法篇的集大成者——熔接了前八章几乎所有核心思想，证明了"GC 的未来在于精巧组合而非新算法发明"
    
- 工业影响：启发了 Sticky Immix、Fast Conservative GC 等后续工作；其思想（Region 化、染色指针、混合写屏障）已融入 G1/ZGC/Go 等现代收集器
