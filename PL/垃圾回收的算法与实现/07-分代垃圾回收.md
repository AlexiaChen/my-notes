
# 《垃圾回收的算法与实现》读书笔记 · 第7章 分代垃圾回收

> 延续前六章建立的"第一性原理"视角：标记-清除、引用计数、复制、标记-压缩这四种基本算法，都是在"对整个堆做回收"的假设下设计的。但工程实践中发现了一个**颠覆性的统计规律**——**大部分对象在生成后马上就变成了垃圾，很少有对象能活得很久**。分代 GC 正是把这个统计规律**作为第一性原理**，重新组织了整个堆的结构。它不再是一种新的"回收算法"，而是一种**"基于对象年龄的统计分区策略"**——把四种基本算法组合使用，让每种算法只在自己最擅长的年龄区间工作。

---

## 一、7.1 分代垃圾回收：把"统计规律"作为设计基石

### 核心思想

在对象中引入**"年龄"概念**——刚生成的对象叫**新生代对象**，经过一定次数 GC 还存活的对象晋升为**老年代对象**。对不同代使用不同 GC 算法：

- 对新生代执行的 GC 叫 **新生代 GC（minor GC）**，频率高
    
- 对老年代执行的 GC 叫 **老年代 GC（major GC）**，频率低
    
- 新生代对象存活一定次数后晋升（promotion/aging）到老年代
    

### 经验假说（分代假说）

> "大部分对象在生成后马上就变成了垃圾，很少有对象能活得很久"

这是一个**经验规律而非数学定理**——它源自对真实程序运行时对象生命周期的统计观察。IBM 对面向对象系统的研究表明：**98% 的对象是朝生夕灭的**。

> 💡 **第一性原理洞察**：分代 GC 的本质，是把"回收算法"和"回收调度"解耦。它承认一个事实——**回收算法的效率，取决于它要处理的对象集合中"活对象的比例"**。在新生代，活对象比例极低（2%），因此用复制算法极度划算；在老年代，活对象比例极高（接近 100%），因此复制算法极不划算，转而用标记-清除或标记-压缩。
> 
> 更深刻的洞见是：**分代 GC 不是一种新算法，而是四种基本算法的"调度层"**。它把堆按年龄分区，每个区选用最适合该区特征的基本算法。这就是为什么工业界常说——"Generational is a partitioning strategy, not a tracing algorithm"（分代是分区策略，不是追踪算法）。

### 分代 GC 的收益公式

设新生代存活率为 sy​，新生代对象数量为 Ny​，则每次 minor GC 回收的垃圾约为 (1−sy​)⋅Ny​。**sy​ 越小，单位扫描成本的回收收益越高**——这正是"频繁、廉价的 minor GC"划算的根本原因。

## 二、7.2 Ungar 的分代垃圾回收：现代分代 GC 的鼻祖

David Ungar 1984 年在《Generation Scavenging》论文中提出这一算法，获得了 2008 年 ACM SIGSOFT Impact Paper Award，是现代分代 GC 的事实标准原型。

### 堆结构（四个空间）

Ungar 论文中对各空间大小的经典设定：

- **生成空间（New-Space / Eden）**：140KB，新对象分配于此
    
- **幸存空间（Past-Survivor / Future-Survivor）**：各 28KB，用作 From 和 To 空间
    
- **老年代空间（Old-Space）**：940KB
    

新生代 = 生成空间 + 两个幸存空间；老年代 = 老年代空间。

### 对象头结构

每个对象头包含：

- **age**：从新生代 GC 中存活下来的次数
    
- **forwarded**：已经复制完毕的标志
    
- **remembered**：已经向记录集记录完毕的标志
    
- **forwarding 指针**
    
- 对象的种类和大小
    

### 新生代 GC（minor GC）流程

当生成空间满时启动：

1. 从 GC Roots + **记录集**（见 7.5 节）出发
    
2. 将生成空间中的活动对象复制到 To 幸存空间
    
3. 同时，From 空间内的活动对象也复制到 To 幸存空间
    
4. 复制完成后，Past-Survivor 和 Future-Survivor 角色翻转（flip）
    
5. 从一定次数的新生代 GC 中存活下来的对象，被**晋升**到老年代空间
    

### 老年代 GC（major GC）

老年代空间占满后触发，使用**标记-清除算法**。

### 性能数据

Ungar 在 Sun 工作站上的 Smalltalk 实现：

> **scavenge 时间中位数 150 毫秒，每 16 秒发生一次**

这意味着 mutator 几乎感受不到 GC 的存在——分代 GC 的"无感知回收"愿景首次在工程上被证实。

> 💡 **洞见**：Ungar 的设计在 1984 年就预见了现代 JVM 的堆布局——**Eden + S0/S1 + Old 的三层结构，正是 Ungar 的 New-Space + Past-Survivor/Future-Survivor + Old-Space 的直接继承**。更惊人的是，Ungar 当时就提出了"自适应晋升策略"和"从程序执行中获取提示来改进晋升"的思想——这在当时是极具前瞻性的。

## 三、7.3 优点：为什么分代 GC 成为现代 GC 的事实标准

|优点|深层机制|
|---|---|
|**大幅缩减 GC 时间**​|minor GC 只扫新生代，而新生代活对象比例极低（~2%），扫描成本 ∝ 活对象数而非堆大小|
|**结合了复制和标记-清除的优势**​|新生代用复制（无碎片、分配快），老年代用标记-清除/压缩（适合高存活率）|
|**短停顿**​|分代小、回收快，Ungar 实现中 150ms 的停顿对交互式系统可接受|
|**自适应**​|晋升阈值可根据运行时行为动态调整|

> 💡 **工程洞见**：分代 GC 的收益不是"免费"的——它用一个统计假设（弱分代假说）换来了巨大的性能提升。**这个交换在假设成立时极度划算，在假设不成立时会适得其反**。这正是 7.4 节"缺点"的核心。

---

## 四、7.4 缺点：当统计假设失效时

分代 GC 的根本前提是"弱分代假说"成立——即大部分对象朝生夕灭。当这个假设不成立时：

**① 分代 GC 可能比非分代 GC 更慢**

如果 workload 中大量对象都能存活较长时间（如大缓存预热、对象池故意保留一切），则：

- 对象在幸存空间之间被反复复制，直到晋升
    
- 写屏障在每次指针写入时都要执行，开销陡增
    
- 但回收到的垃圾很少——**付出了复制成本，却没有获得相应的死对象回收收益**
    

这就是经典的 **"nepotism"（任人唯亲）/ premature-promotion（过早晋升）病态**：新生代充满存活对象，晋升阈值崩塌，你在为并不存在的回收收益买单。

**② 写屏障带来固有开销**

每次指针写入都要检查是否需要记录到记忆集，这是分代 GC 不可避免的税收。

**③ 跨代引用管理复杂**

必须维护记录集/卡片表，增加了实现复杂度。

> ⚠️ **核心洞见**：分代 GC 的优缺点同源——都来自"弱分代假说"。假设成立 → 优点尽显；假设不成立 → 缺点暴露。**这解释了为什么 Go 语言至今（Go 1.22）仍未引入分代 GC**——Go 团队认为，对于 Go 的目标 workload（高并发微服务、大量短命对象但内存访问模式多样），分代假说的收益不足以抵消写屏障的固有开销和实现复杂度。这是一个**经过深思熟虑的工程取舍**，而非技术债。

## 五、7.5 记录各代之间引用的方法：写屏障 + 记忆集

### 核心问题

minor GC 时，如果只从栈和全局变量这些"真根"出发扫描，会**漏掉"只被老年代对象引用"的新生代对象**——例如一个长寿命的 `CustomerList`（老年代）添加了一个新的 `Order`（新生代），如果只扫描真根，`Order` 会被错误回收。

但如果为了找这些跨代引用而**扫描整个老年代**，就回到了全堆扫描——分代 GC 的优势荡然无存。

### 解决方案：写屏障 + 记忆集（Remembered Set）

**写屏障（Write Barrier）**​ 是编译器在每次指针写入指令后自动插入的一小段代码。它监视一个特定事件：**从老对象指向年轻对象的指针写入**。

```
write_barrier(obj, field, new_obj):
    *field = new_obj
    if obj.old == TRUE and new_obj.young == TRUE:
        if obj.remembered == FALSE:
            remembered_sets[rs_index] = obj
            rs_index += 1
            obj.remembered = TRUE
```

三个判定条件：

1. 发出引用的对象是不是老年代对象
    
2. 指针更新后的引用目标对象是不是新生代对象
    
3. 发出引用的对象是否还没有被记录到记录集中
    

### 记忆集的实现：卡片表（Card Table）

最普遍的记忆集实现是**卡片表**——把老年代切成固定大小的"卡片"（如 HotSpot 中 512 字节一张），当老年代对象的指针被改写时，写屏障只把该对象所在的卡片标记为"脏"（DIRTY）。minor GC 扫描时，**只需扫描脏卡片中的对象**，寻找跨代引用。

```
老年代内存:
[Card 0][Card 1][Card 2][Card 3]...
卡片表:
[  0  ][  1  ][  0  ][  1  ]...
       ↑Dirty    ↑Dirty
```

> 💡 **第一性原理洞察**：写屏障 + 记忆集的设计，体现了 GC 中一个普适的工程哲学——**"主动记录"优于"被动扫描"**。不在 GC 时辛苦搜索跨代引用，而在 mutator 运行时廉价地记录它们。这是 O(1) 的写入开销换取 O(跨代引用数) 的扫描开销，而非 O(老年代大小)。
> 
> 更进一步：卡片表是"精确记忆集"的**空间换时间简化版**——它不记录精确的跨代引用位置，而只记录"可能包含跨代引用的卡片"，把记忆集的存储空间从 O(跨代引用数) 降到 O(老年代大小/卡片大小)。这种"用粗粒度换空间"的权衡，在 G1 的 Remember Set、ZGC 的 Colored Pointer 中都有体现。

## 六、7.6 多代垃圾回收：超越两代

### 核心思想

Ungar 的原始设计是"新生代 + 老年代"两代。但实际工程中可以扩展到更多代——**.NET CLR 就是三代结构**：

- **Gen0**：回收最频繁，类似 Ungar 的新生代
    
- **Gen1**：中等频率，类似"中间代"
    
- **Gen2**：回收最少，即老年代
    

### 多代的优势

- **更精细的年龄区分**：避免"新生代对象"一刀切地晋升到老年代
    
- **中间代吸收"中等寿命"对象**：很多对象既不是朝生夕灭，也不是长命百岁——它们在 Gen1 就被回收，永远不会晋升到 Gen2
    
- **Gen0/Gen1 的回收（ephemeral collection）很廉价**，只有 Gen2 回收才是全堆 GC
    

### 工业印证

.NET CLR 的三代结构与 JVM 的两代结构（Eden/S0/S1/Old）代表了两种不同的设计哲学：

- **JVM**：两代 + 幸存空间复制，结构简单，新生代内部用复制算法做年龄筛选
    
- **.NET**：三代，直接在代际间做晋升，更精细但实现更复杂
    

两者的骨架一致：**小且频繁的新生代回收 + 写屏障维护的记忆集 + 存活对象的晋升**。

## 七、7.7 列车垃圾回收（Train Algorithm）：老年代的增量回收

### 核心问题

即使有了分代，老年代 GC 仍然是全堆回收——当老年代填满时触发 major GC，必须 STW 扫描整个老年代。对于**大堆、低延迟**需求的系统，一次 major GC 的停顿可能是灾难性的。

### 列车算法的思想

列车算法（Train Algorithm）由 Hudson 和 Moss 提出，将老年代进一步划分为**列车（train）和车厢（car）**：

- 老年代空间被分为多个**车厢（car）**
    
- 多个车厢组成一列**列车（train）**
    
- 每个车厢维护自己的记忆集，记录从其他车厢/列车指向本车厢的引用
    
- 每次 GC 只回收一列列车（或一节车厢），实现**老年代的增量回收**
    

### 算法流程

1. 每次只选择一列列车（通常是"最老"的那列）进行回收
    
2. 从该列车的车厢出发，结合记忆集，标记可达对象
    
3. 存活对象被疏散到其他列车或晋升
    
4. 该列车被整体回收
    

### 为什么叫"列车"

形象地比喻：老年代就像编组站，对象像车厢，列车按顺序进站。每次只处理一列列车，避免长时间停顿。

> 💡 **洞见**：列车算法是"分代思想在老年代内部的递归应用"——既然分代把堆按年龄分区可以降低回收成本，那么**为什么不在老年代内部再做一次分区**？列车算法把老年代切成更小的回收单元，让 major GC 也能增量进行。这是"分而治之"思想在 GC 中的极致体现。
> 
> 更深远的意义：列车算法预示了现代 GC 的**Region 化趋势**——G1 把堆切成 2048 个等大小 Region，每次只回收"收益最高"的几个 Region，本质上就是列车算法的工业进化版。从 Ungar 的分代 → 列车算法的老年代细分 → G1 的 Region 化，我们可以看到一条清晰的演化主线：**不断细化回收的粒度，让 GC 停顿与堆大小解耦**。

```
第一性原理：弱分代假说（大部分对象朝生夕灭）

│   ├─ 新生代：复制算法（4章）

│
├─ 7.4 缺点：统计假设失效时适得其反（过早晋升病态）
│
├─ 7.5 跨代引用：写屏障 + 记忆集（卡片表）
│   └─ "主动记录"优于"被动扫描"
│
├─ 7.6 多代 GC：.NET 三代结构，更精细的年龄区分
│
└─ 7.7 列车算法：老年代内部的增量回收
    └─ 分代思想的递归应用 → 预示 G1 的 Region 化
```

**更深层的洞见**：分代 GC 在全书算法篇中占据**承上启下**的关键位置：

- **承上**：它把前面学的四种基本算法（标记-清除、引用计数、复制、标记-压缩）**组合使用**——新生代用复制，老年代用标记-清除/压缩。分代 GC 不是第五种算法，而是前四种算法的"调度层"。
    
- **启下**：它引入的两个核心机制——**写屏障**和**记忆集**——是后续所有"高级 GC"的基础组件：
    
    - 增量 GC（第8章）：需要写屏障维护三色不变式
        
    - 并发 GC（第9章）：需要写屏障保证并发正确性
        
    - G1/ZGC/Shenandoah：记忆集的工业化身（RSet、Card Table）
        
    

**理解分代 GC，你就拿到了打开现代 GC 设计的万能钥匙**。

## 九、工业实践印证

### 1. HotSpot JVM：Ungar 设计的直接继承者

HotSpot 的堆结构与 Ungar 1984 年的设计惊人地一致 ：

```
HotSpot 堆布局（与 Ungar 设计的对应关系）：
┌─────────────────────────────────────────────┐
│ 新生代 (Young Generation)                    │
│ ┌──────────────────┬──────────┬──────────┐  │
│ │  Eden (140KB*)   │ S0 (28KB*)│ S1 (28KB*)│  │  ← New-Space + PS + FS
│ └──────────────────┴──────────┴──────────┘  │
├─────────────────────────────────────────────┤
│ 老年代 (Old Generation) 940KB*               │  ← Old-Space
└─────────────────────────────────────────────┘
* 比例为 Ungar 原论文设定，HotSpot 实际大小可调
```

**HotSpot 收集器矩阵**：

|收集器|新生代算法|老年代算法|特点|
|---|---|---|---|
|**Serial**​|复制（Eden→S0/S1）|标记-整理|单线程 STW，客户端模式|
|**Parallel Scavenge**​|复制（多线程）|Parallel Old（标记-整理）|吞吐优先|
|**ParNew**​|复制（多线程）|与 CMS 配合|多线程加速 minor GC|
|**CMS**​|复制|标记-清除（并发）|低延迟，但有碎片问题|
|**G1**​|复制（Region 级疏散）|标记-整理（Region 级）|可预测停顿|

### 2. 卡片表：写屏障的工业实现

HotSpot 中卡片表的具体实现 ：

- 卡片大小：**512 字节**
    
- 写屏障：每次指针写入后，检查是否 old→young，若是则标记对应卡片为 DIRTY
    
- minor GC 时只扫描 DIRTY 卡片
    

```
// HotSpot 写屏障伪代码（cardTableBarrier）
void post_write_barrier(oop* slot, oop value) {
    *slot = value;
    if (value != NULL && in_young_gen(value)) {
        CardTable::mark_card_dirty(slot);
    }
}
```

### 3. G1：分代思想的 Region 化进化

G1（JDK 9+ 默认收集器）把分代思想推向了新的高度 ：

- 堆被切成 **2048 个等大小 Region**（可调节）
    
- 每个 Region 可以动态担任 Eden、Survivor、Old 或 Humongous 角色
    
- 通过 **Remembered Set（RSet）**​ 跟踪跨 Region 引用
    
- 根据用户设定的 `-XX:MaxGCPauseMillis=200` 目标，**优先回收"垃圾最多"的 Region**
    
- 核心哲学：**可预测的停顿**——"Garbage First"意味着先回收垃圾最多的 Region
    

G1 的本质是：**把分代 + 列车算法的思想，用 Region 化的方式重新实现**。Region 就是"细粒度的车厢"，RSet 就是"细粒度的记忆集"。

### 4. .NET CLR：三代结构

.NET CLR 采用 Gen0/Gen1/Gen2 三代结构 ：

- **Gen0**：回收最频繁，ephemeral collection 极廉价
    
- **Gen1**：中间代，吸收中等寿命对象
    
- **Gen2**：老年代，回收即全堆 GC
    
- 同样使用卡片表 + 写屏障维护 old→young 引用
    

### 5. 为什么 Go 至今没有分代 GC

Go 1.22 仍然是**非分代**的并发三色标记-清除 GC 。Go 团队的考量：

- Go 的目标 workload 中，分代假说的收益不足以抵消写屏障的固有开销
    
- Go 的 GC 目标是 **< 500μs 的停顿**，通过并发标记 + 辅助 GC 达成
    
- 引入分代需要写屏障，而 Go 当前的混合写屏障（Dijkstra + Yuasa）已经复杂
    

> 💡 **工程启示**：Go 的选择揭示了一个深刻真理——**分代 GC 不是"银弹"**。它假设 workload 符合弱分代假说，对于不符合该假说的 workload，分代 GC 反而有害。现代 GC 选型时，必须先问：**你的 workload 符合弱分代假说吗？**
> 
> - 符合（Web 服务、函数式编程、大量临时对象）→ JVM/.NET 分代 GC 极佳
>     
> - 不符合（大缓存、对象池、批处理）→ 非分代并发 GC（Go、ZGC）可能更合适
>

## 十、承上启下：分代 GC 在全书算法篇的位置

至此，我们已经学完了六种 GC 范式：

|范式|本质|关键机制|
|---|---|---|
|标记-清除|集中式、就地回收|mark + sweep|
|引用计数|分布式、即时回收|ref_cnt ±1|
|复制算法|搬迁活对象|forwarding pointer|
|标记-压缩|标记 + 就地压缩|3 次扫描 / 双指针|
|保守式 GC|不确定指针下的保守处理|三重过滤|
|**分代 GC**​|**基于年龄的统计分区策略**​|**写屏障 + 记忆集 + 晋升**​|

**关键洞察**：分代 GC 是全书算法篇的**分水岭**——

- **前五种算法**都是"对整个堆做回收"的基本算法
    
- **分代 GC**​ 是第一种"调度层算法"——它不改变基本算法的内核，而是改变**何时、对哪部分堆、用哪种基本算法**做回收
    

后续章节（第8章 增量 GC、第9章 并发 GC、第10章 GC 大统一）都是在这个"调度层"上继续创新：

- **增量 GC**：把一次 GC 打散到多个时间片执行（需要写屏障维护三色不变式）
    
- **并发 GC**：让 GC 与 mutator 同时运行（需要写屏障保证并发正确性）
    
- **GC 大统一**：把分代、增量、并发组合成现代 GC（如 G1、ZGC、Shenandoah）
    

**带着"分代 GC = 调度层 + 基本算法组合"的视角进入下一章**，你会清晰地看到：增量 GC 和并发 GC 并不是新的回收算法，而是**对分代 GC 的"调度时机"做进一步优化**——把 STW 的 minor GC 进一步打散为增量执行，或让 minor GC 与 mutator 并发执行。**写屏障和记忆集，是贯穿这三个高级主题的共同基础设施**。

---

📌 **本章核心收获**：

- 分代 GC 的第一性原理是**弱分代假说**（大部分对象朝生夕灭），它是一个**分区调度策略**，而非新算法
    
- Ungar 1984 年的设计（New-Space + S0/S1 + Old-Space + Remembered Set + Tenuring）是现代 JVM 堆结构的直接原型
    
- 分代 GC 的收益公式：minor GC 成本 ∝ 新生代活对象数（~2%），而非堆大小
    
- 写屏障 + 记忆集（卡片表）是解决跨代引用问题的关键——"主动记录"优于"被动扫描"
    
- 分代 GC 的阿喀琉斯之踵：当弱分代假说失效时（过早晋升病态），分代 GC 反而比非分代更慢——这是 Go 至今未引入分代的根本原因
    
- 多代 GC（.NET 三代）和列车算法（老年代增量回收）是分代思想的深化，预示了 G1 的 Region 化
    
- 工业印证：HotSpot（Eden+S0/S1+Old + 卡片表）、.NET CLR（Gen0/1/2）、G1（Region + RSet）都是 Ungar 设计的直系后代
    
- **分代 GC 是全书算法篇的分水岭**：前五种是基本算法，分代 GC 是第一种调度层算法，后续增量/并发/大统一都是在这个调度层上继续创新
