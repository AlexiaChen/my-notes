
# 《垃圾回收的算法与实现》读书笔记 · 第3章 引用计数法

> 延续前两章建立的"第一性原理"视角：如果说**标记-清除是"集中式、全局可达性"的判定**——从根出发一次性遍历整个对象图；那么**引用计数就是"分布式、局部、即时"的判定**——在每个对象头上维护一个计数器，mutator 每做一次指针改动，就立刻在受影响对象的计数器上 ±1，归零即回收 。
> 
> 这两种思路的根本分歧在于：**垃圾判定的职责放在哪里？**​ 标记-清除把判定集中在 GC 的一次性遍历里；引用计数把判定分散到 mutator 的每一次指针操作里。这一分歧决定了引用计数全部的优缺点，以及本章 3.4~3.7 所有改进的方向。

---

## 一、3.1 引用计数的算法：把"判定"嵌入每一次指针赋值

每个对象头里维护一个无符号整数计数器 `ref_cnt`，记录当前有多少引用指向它。算法由三个原语构成 ：

```
new_obj(size):
    obj = malloc(size)
    obj.ref_cnt = 1          # 新建对象，被创建者引用一次
    return obj

assign(*ptr, obj):           # 更新引用：先增后减，顺序不能反
    obj.ref_cnt += 1         # 先对新对象 +1，防止中途回收
    (*ptr).ref_cnt -= 1      # 再对旧对象 -1
    if (*ptr).ref_cnt == 0:
        free_obj(*ptr)
    *ptr = obj

free_obj(obj):
    for each child in obj:
        child.ref_cnt -= 1
        if child.ref_cnt == 0:
            free_obj(child)
    heap.release(obj)
```

**最关键的细节**：`assign` 必须**先递增新对象的计数器，再递减旧对象的计数器**。这个顺序不能反——如果先减后增，考虑 `a = a` 这种自赋值，旧对象计数器可能短暂归零被误回收，随后新引用指向已释放内存 。

> 💡 **第一性原理洞察**：引用计数的精妙之处在于——**它把"可达性分析"这个命题，转化成了"每个对象自我计数"的局部算术问题**。不需要从根遍历，不需要全局视图；mutator 自己每次改指针时顺手把账算清。这是一种**彻底的去中心化**——GC 不再是"某个时刻停下来做全局判定"的 centralized authority，而是"每一次指针操作都是一次微型 GC"的 decentralized protocol。
> 
> 这种去中心化带来的本质特征是：**垃圾在"变成垃圾的那一刻"就被回收，而不是"等到下次 GC 周期"**。这是引用计数区别于所有 tracing 算法的根本特征。

---

## 二、3.2 优点：去中心化带来的三大红利

|优点|深层含义|
|---|---|
|**即刻回收**​|对象在引用归零的瞬间立即释放，内存利用率实时最优 ；资源型对象（文件句柄、锁）可及时释放|
|**最大暂停时间极短**​|不需要 STW 做全局遍历，每次只处理一个对象的回收 ；RTOS、实时系统的最爱|
|**无需沿指针全局搜索**​|不依赖 GC Roots 遍历，算法局部性好，缓存友好；且天然适合**分布式 GC**（跨节点引用用引用计数，节点内用 tracing）|

> 💡 **工程洞见**：引用计数的"即刻回收"在**资源敏感场景**无可替代。Python 选择引用计数作为主力 GC ，正是因为：文件对象、网络连接、锁这类"稀缺资源"需要在引用消失时**立刻**释放，而不能等到某个不确定的 GC 周期。这是 tracing GC 难以企及的确定性。

---

## 三、3.3 缺点：去中心化的三重代价

引用计数的缺点和它的优点是硬币的两面——**正是"把判定分散到每次指针操作"这一设计，带来了所有问题**​ ：

**① 计数器增减开销大**

每次指针赋值都要 ±1，且涉及跨对象内存写入。在指针操作频繁的 workload 下，这部分开销会显著侵蚀 mutator 吞吐量。更糟的是：根引用的频繁变化（函数调用、栈帧切换）会带来大量无意义的计数器抖动 。

**② 计数器占用内存**

每个对象头都要预留计数器空间。要支持大引用数就要宽位宽，浪费内存；位宽窄又会溢出 。

**③ 循环引用无法回收（最致命）**

```
A ↔ B 互相引用
即使外部已无任何引用指向 A 或 B
A.ref_cnt ≥ 1, B.ref_cnt ≥ 1 永远成立
→ 内存泄漏
```

这是引用计数**理论上的硬伤**——任何纯引用计数方案都无法解决 。

> ⚠️ **核心洞见**：这三个缺点不是随机的，它们精确地对应了"去中心化判定"的三个代价维度——
> 
> - 缺点①是**时间代价**（每次操作都要付账）
>     
> - 缺点②是**空间代价**（每个对象都要随身带账本）
>     
> - 缺点③是**语义代价**（局部视角看不到全局环路）
>     
> 
> 本章 3.4~3.7 的四个改进，恰好一一对应修补这三个缺点（其中循环引用有两个改进方案从不同角度切入）。

## 四、3.4 延迟引用计数法：修补"计数器增减开销大"

### 改进思路

**根引用的频繁变化是计数器抖动的主因**——栈帧切换、临时变量赋值都会让根引用大规模变动。延迟引用计数法的洞察是：**与其每次根引用变化都更新计数器，不如"欠着"，把计数器为 0 的对象先塞进 ZCT（Zero Count Table），等 GC 发生时统一处理**​ 。

```
dec_ref_cnt(obj):
    obj.ref_cnt -= 1
    if obj.ref_cnt == 0:
        ZCT.add(obj)          # 不直接回收，先入表

scan_zct():                   # GC 触发时统一处理
    for r in roots:
        (*r).ref_cnt += 1     # 把根引用"反映"到计数器上
    for obj in ZCT:
        if obj.ref_cnt == 0:
            delete(obj)       # 此时仍为零，才是真垃圾
    for r in roots:
        (*r).ref_cnt -= 1
```

### 权衡

- ✅ 根引用变化时不再频繁 ±1，**大幅削减了计数器抖动的开销**​
    
- ❌ **失去了"即刻回收"这一最大优势**——垃圾要等 scan_zct 才被回收
    
- ❌ scan_zct 的最大暂停时间与 ZCT 大小成正比；ZCT 缩太小又会导致 scan_zct 调用过于频繁，反而压低吞吐量
    

> 💡 **洞见**：延迟引用计数揭示了 GC 设计中的一个普遍权衡——**"实时性"与"吞吐量"的交换**。纯引用计数的"即刻回收"是实时性的极致，但付出了吞吐量代价；延迟引用计数把实时性打折，换回了吞吐量。这是本书"不可能三角"在引用计数内部的微观重演。

## 五、3.5 Sticky 引用计数法：修补"计数器占用内存"

### 改进思路

观察事实：**绝大多数对象的引用次数很少**——大部分对象只有 1~2 个引用，能到 31 次引用的对象极少 。因此不必给每个对象分配一个完整的机器字（32/64 位）做计数器，可以大幅缩减位宽（比如 5 位，最多计数到 31）。

**溢出时的两种处理策略**​ ：

**策略 A：什么都不做**

溢出后不再更新该对象的计数器。赌的是"能溢出 31 次的对象必然是长期存活的活动对象，漏更新也不会有太大问题"。简单但有可能漏回收。

**策略 B：回退到标记-清除**

当发生溢出时，启动一次完整的标记-清除：

1. 把所有对象的计数器重置为 0
    
2. 从根遍历，对可达对象的计数器 +1（注意每个对象只标记一次）
    
3. 清除阶段遍历整个堆，回收计数器仍为 0 的对象
    

这种混合方案一举两得：**既能处理溢出对象的回收，又能顺带回收循环引用垃圾**​ 。代价是：标记-清除本身要遍历全堆，吞吐量下降。

> 💡 **洞见**：Sticky 引用计数体现了 GC 中一个极其重要的设计哲学——**"用统计规律换资源"**。它赌的是一个经验事实："引用数多的对象是少数"。这种"按概率分布优化常见情况、罕见情况降级处理"的思路，在 GC 设计中反复出现：分代 GC 赌"对象朝生夕灭"、1 位引用计数赌"对象大多不被共享"、Sticky 赌"引用数普遍很小"。**统计学假设是 GC 算法优化的隐藏发动机**。

## 六、3.6 1 位引用计数法：Sticky 的极端形态

**把计数器压缩到极致——只有 1 位**​ ：

- `0` = UNIQUE（唯一引用，引用数为 1）
    
- `1` = MULTIPLE（多重引用，引用数 ≥ 2）
    

**关键实现技巧**：利用指针对齐的闲置位。指针通常 4/8 字节对齐，低 2~3 位永远是 0，可以把这闲置的 1 位借来当计数器标签 。

**更新指针的方式也必须改变**：不再通过"指定要引用的对象"来更新（`*ptr = &obj`），而是通过"复制某个指针"来更新（`dest_ptr = src_ptr`） 。例如把 B→C 的指针复制给 A，此时 A 和 B 都指向 C，C 必然是 MULTIPLE。

**回收规则**：只有当指针标签是 UNIQUE 时才能回收——因为 MULTIPLE 意味着还有其他引用，不敢回收 。

### 优势与代价

- ✅ **几乎不会出现缓存缺失**：更新计数时不需要去读远处的对象头，只操作指针本身
    
- ✅ **节省内存**：不需要独立的计数器空间
    
- ❌ 同样面临"溢出"问题（MULTIPLE 状态下计数器信息已丢失，无法精确知道引用数）
    

> 💡 **洞见**：1 位引用计数是"把管理信息从对象头剥离、附到指针上"的极致演绎。这与上一章标记-清除中"位图标记"的思想（管理信息与对象分离）异曲同工——**GC 的进化史上，"管理信息放哪里"这个问题被反复重新回答**。1 位引用计数把这个答案推到了极致：管理信息不放对象头，不放独立位图，而是**借指针的闲置位**。

## 七、3.7 部分标记-清除算法：修补"循环引用"（最优雅的方案）

这是本章最具独创性的改进，也是工业界处理循环引用的主流思路（Python 的循环垃圾收集器正是这一思想的继承者 ）。

### 核心思想

循环引用垃圾**在实际程序中占比极小**​ 。因此**不需要对整个堆做标记-清除，只需要对"可能是循环垃圾的对象群"做标记-清除**——这就是"部分"二字的精髓 。

### 四色标记法

每个对象头用 2 位记录颜色状态 ：

|颜色|含义|
|---|---|
|**黑 BLACK**​|绝对不是垃圾（对象创建时的初始色）|
|**白 WHITE**​|绝对是垃圾|
|**灰 GRAY**​|已被搜索完毕的对象|
|**阴影 HATCH**​|可能是循环垃圾的对象|

### 算法流程

**① 引用减少时**：当某对象的计数器减 1 后仍 > 0，说明它可能处在循环引用中——将其涂成 HATCH，并加入阴影队列 。

**② 分配失败时触发 `scan_hatch_queue()`**：

- **paint_gray**：从阴影对象出发，将其涂成灰色，对其子对象计数器 -1 并递归涂灰。这一步让循环垃圾群的计数器全部归零。
    
- **scan_gray**：扫描灰色对象，计数器为 0 的涂白（是真垃圾），计数器 > 0 的涂黑并对其子对象 +1（不是垃圾，恢复计数）。
    
- **collect_white**：回收所有白色对象——循环垃圾在此被清除 。
    

### 为什么优雅

**它将标记-清除的搜索范围严格限制在"阴影对象及其子对象"这个极小集合内**，而不是全堆 。循环垃圾的搜索成本从 O(堆大小) 降到 O(可能成环的对象群大小)，而后者在实践中极小。

> 💡 **第一性原理洞察**：部分标记-清除的本质是**"引用计数为主、tracing 为辅"的混合架构**。它承认了纯引用计数的理论缺陷（循环引用），但拒绝为此付出"全堆 tracing"的代价——而是通过精妙的启发式（计数器减后仍非零 → 可能是循环）把 tracing 的范围压缩到最小。**这是 GC 设计中"扬长避短"的典范：让引用计数处理 99% 的常见情况，让 tracing 只处理那 1% 的循环引用特例**。
> 
> 更深远的意义：它打破了"引用计数 vs tracing"的二元对立，开创了**混合 GC**​ 的范式。现代 GC 几乎都是混合架构——Python（引用计数 + 分代循环 GC）、JVM G1（分代 + 并发标记）、Go（并发 tracing + 辅助 GC）……部分标记-清除是这一范式的思想源头之一。

## 八、章节脉络：四个改进如何对应三个缺点

```
引用计数法
├─ 缺点①计数器增减开销大 ──→ 3.4 延迟引用计数（ZCT 批量延迟处理）
├─ 缺点②计数器占用内存 ───→ 3.5 Sticky（缩减位宽）
│                         └→ 3.6 1位引用计数（极致压缩到指针位）
└─ 缺点③循环引用 ─────────→ 3.7 部分标记-清除（只对疑似环做 tracing）
                           └→ 3.5 Sticky 策略B（溢出时回退标记-清除）
```

**更深层的洞见**：这四个改进呈现出两条清晰的演进路径——

**路径一：让引用计数"更轻"**

延迟引用计数 → Sticky → 1 位引用计数，是一条逐步削减"去中心化判定"成本的路径。每一步都在赌一个统计假设：

- 延迟引用计数赌"根引用变化频繁但大多临时"
    
- Sticky 赌"引用数普遍很小"
    
- 1 位引用计数赌"对象大多不被共享"
    

**路径二：让引用计数"更完备"**

部分标记-清除是另一条路径——承认引用计数的理论缺陷，用 tracing 作为补充，但严格限制 tracing 的代价。**这是混合 GC 的思想起源**。

两条路径并非互斥，工业级实现往往**同时使用**：例如 Sticky + 部分标记-清除的组合，既压缩了计数器开销，又解决了循环引用。

## 九、工业实践印证

### Python：引用计数 + 循环 GC 的教科书级实现

CPython 的内存管理正是**引用计数为主 + 周期性循环 GC 为辅**的混合架构 ：

- **引用计数负责即时回收**：每个 PyObject 头部都有 `ob_refcnt` 字段，引用归零立即释放
    
- **循环 GC 专门处理循环引用**：`gc` 模块基于**分代假设**（新对象更易成垃圾），将对象分为 3 代（Gen0/1/2），阈值默认为 `(2000, 10, 10)`——Gen0 分配数超过释放数 2000 时触发回收
    
- **循环 GC 的算法本质就是部分标记-清除**：只追踪"可能形成循环的容器对象"（list、dict、class instance 等），不可变对象（int、str）不参与循环检测
    

```
# 引用计数无法处理的典型场景
class Node:
    def __init__(self):
        self.parent = None
        self.child = None

a, b = Node(), Node()
a.child = b
b.parent = a
del a, b  # a 和 b 互相引用，引用计数永不为零

import gc
gc.collect()  # 循环 GC 介入，检测出并回收这对循环垃圾
```

> 💡 **工程启示**：Python 的选择揭示了一个深刻真理——**纯引用计数或纯 tracing 都不是最优解，混合架构才是工业级 GC 的归宿**。引用计数提供确定性、即时性；tracing 提供完备性、处理循环。两者互补，缺一不可。

### 其他工业印证

|系统|引用计数的应用方式|
|---|---|
|**Objective-C / Swift ARC**​|编译器自动插入 retain/release，本质是编译期确定的引用计数 ；Swift 用 weak/unowned 引用主动打破循环|
|**C++ shared_ptr**​|引用计数的具体化，weak_ptr 对应循环引用的解决方案|
|**分布式系统 GC**​|跨节点的引用用引用计数，节点内用 tracing——引用计数的"去中心化"特质使其在分布式场景天然适配|

## 十、承上启下：引用计数在全书算法篇的位置

引用计数法与上一章的标记-清除形成了**根本性的范式对立**：

|维度|标记-清除（第2章）|引用计数（第3章）|
|---|---|---|
|判定方式|集中式、全局可达性|分布式、局部计数|
|回收时机|GC 周期触发时|引用归零的瞬间|
|循环引用|✅ 天然处理|❌ 理论硬伤|
|停顿特征|长 STW|极短、平滑|
|额外内存|1 个 mark 位/对象|计数器（多位）|
|对象移动|不移动（兼容保守式 GC）|不移动|
|工业代表|Boehm GC|CPython|

**关键洞察**：这两种算法代表了 GC 设计的两种根本哲学——

- **标记-清除哲学**："停下一切，从全局视角判定生死"——简单、完备，但付出 STW 代价
    
- **引用计数哲学**："在 mutator 的每一次操作中渐进式判定"——平滑、即时，但付出计数器开销和循环引用难题
    

后续章节的算法，本质上都是在这两个极端之间找平衡点：

- **复制算法（第4章）**：继承标记-清除的"集中式判定"，但用"对象移动"解决碎片问题
    
- **分代算法（第5章）**：两种哲学都可以套用，但核心是引入"年龄假设"大幅削减工作量
    
- **增量/并发算法（第6章往后）**：把标记-清除的"集中式判定"打散，向引用计数的"平滑"理念靠拢
    

**带着这个视角往下读，你会看到：GC 算法的演化史，就是标记-清除与引用计数这两极之间的张力史**。每一种新算法，都是在这两个极点之间寻找更适合当下硬件和工作负载的新平衡点。

---

📌 **本章核心收获**：

- 引用计数是"去中心化、即时"的垃圾判定，与标记-清除的"集中式、延迟"判定形成根本对立
    
- 三大缺点（计数器开销 / 内存占用 / 循环引用）是"去中心化"的三个代价维度
    
- 四种改进分成两个方向：让引用计数"更轻"（延迟→Sticky→1位）、让引用计数"更完备"（部分标记-清除）
    
- 部分标记-清除开创了"混合 GC"范式——引用计数为主，tracing 为辅，严格限制 tracing 范围
    
- Python 的"引用计数 + 分代循环 GC"是这一章理论的最佳工业印证
    
- 引用计数与标记-清除的对立，定义了全书算法篇的演化张力
