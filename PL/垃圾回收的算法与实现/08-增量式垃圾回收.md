
# 《垃圾回收的算法与实现》读书笔记 · 第8章 增量式垃圾回收

> 延续前七章建立的"第一性原理"视角：从第2章标记-清除开始，我们一直隐含一个前提——**GC 是一次性、原子化完成的，期间 mutator 必须 STW（Stop-The-World）**。但堆越大，STW 越长；当堆达到 GB/TB 级时，一次 Full GC 的停顿可能长达数秒——这对交互式系统、实时交易、微服务等场景是不可接受的。第8章的增量式 GC，正是打破这一前提的第一把刀：**让 GC 和 mutator 交替执行，把一次长停顿打散为多次极短停顿**。

---

## 一、8.1 什么是增量式垃圾回收：把"一次性"打散为"交替执行"

### 核心思想

传统 GC 的执行模式是：

```
[STW: 标记全部] → [STW: 清除全部] → [mutator 运行]
```

增量式 GC 的执行模式是：

```
[GC 一小步] → [mutator 运行一小段] → [GC 一小步] → [mutator 运行一小段] → ...
```

GC 和 mutator **交替执行**，每次 GC 只做"一点点工作"，从而把最大暂停时间压缩到极小 。

### 增量式 GC 与三色标记的天然契合

增量式 GC 通常用**三色标记（Tri-color Marking）**作为底层机制——把对象染成黑/灰/白三色：

- **白色**：尚未被 GC 访问的对象（可能是垃圾）
    
- **灰色**：自身被标记，但子对象还未被扫描
    
- **黑色**：自身和所有子对象都已被标记（GC 认为"完全活"）
    

增量式 GC 每次执行一小步，从标记栈弹出若干灰色对象进行处理，然后交还控制权给 mutator 。

### 根本矛盾：增量执行破坏了"原子性"

当 GC 和 mutator 交替执行时，一个致命问题出现了——**mutator 在 GC 暂停期间改变了对象引用图，可能导致活对象被错误回收**。

具体场景：A（黑）的子对象 B（灰）已被处理，A 即将变黑；此时 mutator 运行，把 A 的引用从 B 改为 C（C 是白）。如果 GC 不知道这个变化，A 变黑后，C 仍然是白色——**C 是活对象（A 引用它），但 GC 会把它当垃圾回收**。

> 💡 **第一性原理洞察**：增量式 GC 的本质矛盾是——**"GC 看到的引用图"与"mutator 实际维护的引用图"出现了不一致**。要解决这个矛盾，只有两条路：
> 
> ① **阻止不一致发生**（强三色不变式：不允许黑指向白）
> 
> ② **保留不一致发生前的快照**（弱三色不变式：允许黑指向白，但保证该白对象在 GC 开始时的快照中是可达的）
> 
> 这两条路，对应了本章 8.3 和 8.4 的两位主角——**Steele 算法走路径①，汤浅算法走路径②**。而连接这两条路的桥梁，就是**写屏障（Write Barrier）**。

## 二、8.2 优点和缺点：吞吐量与最大暂停时间的零和博弈

### 优点

- **最大暂停时间极短**：GC 工作被打散到多个时间片，每次只停顿极短时间
    

### 缺点

- **吞吐量下降**：写屏障在每次指针写入时都要执行，带来固有开销；且 GC 和 mutator 交替执行会产生缓存效应（cache thrashing）
    
- **可能产生浮动垃圾（Floating Garbage）**：在 GC 周期中变成垃圾的对象，要等到下一轮 GC 才能被回收
    

> ⚠️ **核心洞见**：增量式 GC 把"吞吐量与最大暂停时间"这对矛盾**显性化**了——你优化了一方，另一方必然恶化 。这正是本书第1章提出的"GC 不可能三角"在增量式场景下的直接体现。工业界选型时，必须明确回答：**你的系统是对最大暂停时间敏感（实时系统、交易系统），还是对吞吐量敏感（批处理、科学计算）？**
> 
> - 前者 → 增量式 GC 是救星
>     
> - 后者 → 增量式 GC 反而有害，不如用 Parallel GC 一次性干完
>

## 三、8.3 Steele 的算法：守护"强三色不变式"

### 核心思想

Steele 算法通过**写屏障**严格维持**强三色不变式**——**绝不允许黑色对象指向白色对象**​ 。

### 写屏障伪代码

```
write_barrier(obj, field, newobj):
    if $gc_phase == GC_MARK and obj.mark == TRUE and newobj.mark == FALSE:
        obj.mark = FALSE          # 把黑色对象重新染灰
        push(obj, $mark_stack)    # 重新入栈，等待再次扫描
    *field = newobj               # 更新指针
```

**关键动作**：当黑色对象（已完全扫描）要指向白色对象（未扫描）时，**把黑色对象重新染回灰色**，让它重新进入待扫描队列 。

### 与 Dijkstra 插入写屏障的对比

Dijkstra 的写屏障是"**把白色对象染灰**"：

```
write_barrier(obj, field, newobj):
    if newobj.mark == FALSE:
        newobj.mark = TRUE
        push(newobj, $mark_stack)
```

Steele 的写屏障是"**把黑色对象染灰**" ——两者的本质区别在于**染灰的对象不同**：

|维度|Dijkstra 插入屏障|Steele 混合屏障|
|---|---|---|
|染灰对象|新引用的目标（白色对象）|发出引用的对象（黑色对象）|
|不变式|强三色不变式|强三色不变式|
|重扫范围|只扫新对象及其子树|重新扫原黑色对象及其**整个**子树|
|浮动垃圾|较多（C 即使变垃圾也要等到下轮）|较少（A 重新变灰后，若 C 变垃圾则不会保留 C）|
|写屏障开销|较低|较高（条件更严格）|

### Steele 算法的精妙之处

回到上一节的场景：A（黑）的子对象 B（灰）已被处理；mutator 把 A→B 改为 A→C（C 白）。

- **Dijkstra 屏障**：把 C 染灰 → C 被保留。如果 C 很快又变成垃圾，C 必须等到下一轮 GC 才能回收（**浮动垃圾**）。
    
- **Steele 屏障**：把 A 重新染灰 → A 重新入栈。当 GC 再次扫描 A 时，如果 A 已经不再引用 C（C 变成了垃圾），**C 不会被保留**——Steele 算法通过更严格的条件，**减少了被错误保留的对象数量**​ 。
    

> 💡 **洞见**：Steele 算法体现了工程中的一个深刻权衡——**用"更严格的写屏障条件"换取"更少的浮动垃圾"**。代价是写屏障本身的开销更大（判断条件更复杂，且可能引发对原黑色对象子树的重新扫描）；收益是内存使用效率更高。这种"开销换精确度"的权衡，在 GC 设计中反复出现。
> 
> 更广义地看，Steele 属于**灰色 mutator 屏障（Grey Mutator Barrier）**家族——Dijkstra、Steele、Boehm 都是这一派 。它们的共同特征是：写屏障阻止黑→白指针的出现，但代价是**在标记结束后必须重新扫描 mutator 的根**（因为 mutator 自身可能处于"灰色"状态，某些字段指向白色对象）。这个重扫动作需要 STW，是这一类屏障的"阿喀琉斯之踵"。

## 四、8.4 汤浅的算法：快照式 GC 与"弱三色不变式"

### 核心思想

汤浅太一（Yuasa）的算法采取了完全不同的路径——**允许黑色对象指向白色对象**，但通过**快照（Snapshot-At-The-Beginning, SATB）**保证正确性 。

核心原则：**以 GC 开始时对象间的引用关系为基础执行 GC**​ 。换句话说，GC 标记的是"GC 开始那一刻的活对象集合"——即使在标记过程中某些对象变成了垃圾，只要它们在 GC 开始时是活的，本轮就不会被回收。

### 写屏障伪代码（删除屏障）

```
write_barrier(obj, field, newobj):
    oldobj = *field                  # 取出将被覆盖的旧引用
    if oldobj.mark == FALSE:         # 如果旧对象是白色
        oldobj.mark = TRUE           # 在覆盖前把它染灰
        push(oldobj, $mark_stack)    # 推入标记栈
    *field = newobj                 # 执行实际的指针更新
```

**关键动作**：在覆盖旧指针**之前**，先把旧指针指向的对象染灰 。这表示"在 GC 开始时的快照里，这个对象是被人引用的，所以它必须被视为活对象"。

### 汤浅算法如何保证正确性

回到场景：A（黑）的子对象 B（灰）已被处理；mutator 把 A→B 改为 A→C（C 白）。

- **汤浅屏障**：在覆盖 A→B 之前，先把 B 染灰 → B 被保留。即使 A 已经变黑，且 A 现在指向 C（白），但 B 在 GC 开始时的快照中是活的（A 指向 B），所以 B 被保留。
    
- 由于 B 被保留，且 B 的子对象在标记过程中会被扫描，因此**通过 B 可达的所有对象都不会被错误回收**。
    

汤浅算法允许"黑→白"指针的存在（本例中 A 黑指向 C 白），但它通过 SATB 保证了**弱三色不变式**——要么黑不指向白，要么存在一条从灰色对象到该白色对象的路径（B 灰指向 C 白） 。

### 汤浅算法的特征

- **属于黑色 mutator 屏障（Black Mutator Barrier）**家族
    
- **不需要在标记结束后重扫 mutator 根**（因为 mutator 自身已经被"染黑"——所有根字段要么指向黑、要么指向灰）
    
- **代价是"快照内的浮动垃圾"**：在 GC 周期内变成垃圾的对象（如本例中的 B，如果 mutator 后续删除了 A→B 的引用），必须等到下一轮 GC 才能回收
    
- **不需要 STW 重扫**，但需要**在 GC 周期开始时 STW 扫描所有根**（把 mutator 变为黑色）
    

> 💡 **洞见**：汤浅算法体现了另一种工程哲学——**"用空间（浮动垃圾）换时间（无重扫 STW）"**。它在 GC 开始时做一个"快照"，整个标记过程都基于这个快照进行。代价是快照之后变成垃圾的对象要等到下一轮才能回收；收益是标记结束后不需要 STW 重扫 mutator 根。
> 
> 这恰好与 Steele 算法形成镜像：
> 
> - **Steele**：写屏障条件严格 → 浮动垃圾少，但需要 STW 重扫根
>     
> - **汤浅**：写屏障记录快照 → 浮动垃圾多，但不需要 STW 重扫根
>     
> 
> 两种方案都是"用一种代价换另一种代价"，没有绝对优劣，只有适合与否。

## 五、8.5 比较各个写入屏障：三种主流方案的权衡矩阵

本章虽重点讲 Steele 和汤浅，但完整的写屏障谱系包含三种主流方案。综合对比 ：

|维度|Dijkstra 插入屏障|Steele 混合屏障|Yuasa 删除屏障（汤浅）|
|---|---|---|---|
|**所属家族**​|灰色 mutator|灰色 mutator|黑色 mutator|
|**触发时机**​|写入新指针后|写入新指针后|覆盖旧指针前|
|**染灰对象**​|新引用的目标（白→灰）|发出引用的对象（黑→灰）|被覆盖的旧目标（白→灰）|
|**维持不变式**​|强三色|强三色|弱三色（基于 SATB）|
|**浮动垃圾**​|多|少|中（基于快照）|
|**标记结束时的 STW**​|需要重扫 mutator 根|需要重扫 mutator 根|不需要重扫（但需要开始时 STW 扫根）|
|**写屏障开销**​|低|高（条件严格）|中|
|**精确度**​|弱|强|中|
|**典型应用**​|-|硬实时系统|Go 混合写屏障的组成部分、G1 SATB|

### 工业演进：Go 的混合写屏障

Go 1.8 引入了**混合写屏障（Hybrid Write Barrier）**，结合了 Dijkstra 和 Yuasa 两者的优点 ：

```
write_barrier(slot, newobj):
    shade(*slot)        # Yuasa 部分：覆盖前把旧对象染灰
    shade(newobj)       # Dijkstra 部分：写入后把新对象染灰
    *slot = newobj
```

混合写屏障的优势：**既不需要在标记结束时 STW 重扫 mutator 根，也不需要开始时 STW 扫所有根**——它同时堵住了两条漏标路径 。这是写屏障技术演化的集大成者，也是 Go 语言能够实现"低延迟并发 GC"的关键基础设施。

> 💡 **第一性原理洞察**：三种写屏障的本质区别，归结为一个问题——**"谁为'GC 与 mutator 交替执行导致的不一致'买单？"**
> 
> - Dijkstra/Steele：让**写屏障**买单（每次写入都检查，开销大但精确）
>     
> - Yuasa：让**浮动垃圾**买单（保留快照内的所有对象，内存效率低但写屏障轻）
>     
> - 混合写屏障：两者都买一点（写屏障开销适中，浮动垃圾适中，STW 极小）
>     
> 
> 这再次印证了 GC 设计的统一规律——**没有免费的午餐，每一项性能提升都要用另一种代价换取**。写屏障技术的演化史，就是"寻找最优代价组合"的探索史。

## 六、章节脉络：增量式 GC 在全书算法篇的位置

```
根本矛盾：GC 与 mutator 交替执行 → 引用图不一致 → 可能漏标活对象
│
├─ 8.1 增量式定义：交替执行，打散 STW
│   └─ 底层机制：三色标记
│
├─ 8.2 优缺点：最大暂停时间 ↓，吞吐量 ↓（零和博弈）
│
└─ 8.3~8.5 写屏障：解决"漏标"的两种路径
    │
    ├─ 路径①：阻止黑→白（强三色不变式）
    │   ├─ Dijkstra：染灰新对象（宽松）
    │   └─ Steele：染灰黑色对象（严格）
    │        └─ 代价：写屏障开销大，但浮动垃圾少
    │
    └─ 路径②：快照式 SATB（弱三色不变式）
        └─ Yuasa/汤浅：覆盖前染灰旧对象
             └─ 代价：浮动垃圾多，但无需 STW 重扫根
        
    工业演进：Go 混合写屏障 = Dijkstra + Yuasa
```

**更深层的洞见**：增量式 GC 是 GC 演化史上的**关键转折点**——它第一次系统性地回答了"如何在 GC 和 mutator 并发执行时保证正确性"。这个答案的核心是**写屏障**，而写屏障技术一旦成熟，就为下一章的"并发 GC"铺平了道路。

**增量式 GC 与并发 GC 的关系**：

- 增量式 GC：GC 和 mutator **交替执行**（GC 做一步，mutator 做一步）
    
- 并发 GC：GC 和 mutator **真正同时执行**（多核并行）
    

两者面临的**正确性挑战完全相同**——都是"GC 和 mutator 同时操作引用图"。因此，**写屏障技术既是增量式 GC 的基础，也是并发 GC 的基础**。本章学习的 Steele、Yuasa 写屏障，在下一章的并发 GC 中会原封不动地使用，只是执行环境从"交替"升级为"真正并行"。

## 七、工业实践印证

### 1. CMS：Dijkstra 插入屏障的工业应用

CMS（Concurrent Mark Sweep）是 JVM 历史上第一款真正的并发收集器，使用**写后屏障（Post-Write Barrier）实现增量更新**​ ：

```
并发标记阶段：
  mutator 把黑色对象指向白色对象
  → 写后屏障捕获该黑色对象，记录到"重扫队列"
  → 最终标记（Remark）阶段 STW，重新扫描这些黑色对象
```

**致命弱点**：Remark 阶段需要 STW 重新深度扫描这些黑色对象，**停顿时间往往较长且不可预测**——这是 CMS 被 G1 取代的核心原因 。

### 2. G1：汤浅 SATB 的工业应用

G1（JDK 9+ 默认）使用**写前屏障（Pre-Write Barrier）+ SATB**​ ：

```
pre_write_barrier(field):
    old_value = *field
    if old_value != null and $gc_phase == GC_CONCURRENT_MARK:
        $current_thread.satb_mark_queue.enqueue(old_value)
```

G1 的 SATB 队列在最终标记阶段被处理——只需把队列中的旧对象标记为存活即可，**不需要重新深度扫描**。这极大缩短了最终标记的 STW 时间，是 G1 能够提供"可预测停顿"的关键 。

### 3. Go：混合写屏障的典范

Go 1.8+ 的混合写屏障 ：

```
write_barrier(slot, newobj):
    shade(*slot)        # Yuasa 部分
    shade(newobj)       # Dijkstra 部分
    *slot = newobj
```

Go 的混合写屏障让 GC 能够**完全并发**地执行标记，不需要在标记结束时 STW 重扫 mutator 根。这是 Go 能够实现"< 500μs 停顿"的关键基础设施。

### 4. ZGC/Shenandoah：跳出"写屏障"的新流派

ZGC 完全抛弃了传统的写屏障，改用**读屏障（Load Barrier）+ 染色指针（Colored Pointers）**​ ：

```
每次从堆中加载引用时：
  if 引用颜色不对:
      触发读屏障，修正引用（"自愈"）
```

- **ZGC**：染色指针（元数据编码在 64 位指针的高位）+ 读屏障，不占对象头额外空间
    
- **Shenandoah**：Brooks Pointer（对象头中存转发指针）+ 读屏障 + 写屏障
    

> 💡 **工程启示**：ZGC/Shenandoah 代表了 GC 设计的最新前沿——**不再依赖写屏障维护三色不变式，而是用"读屏障 + 对象头/指针元数据"实现并发复制**。这是 GC 技术的"范式跃迁"：从"阻止不一致发生"（写屏障）到"让不一致发生，但在读取时修正"（读屏障 + 染色指针）。
> 
> 但值得注意的是：**ZGC/Shenandoah 的并发标记阶段，仍然需要某种形式的 SATB 或写屏障来处理"标记期间的引用变更"**。读屏障主要解决的是"并发复制阶段的引用修正"问题。所以，本章学习的写屏障知识，在理解任何现代 GC 时都不可或缺。

## 八、承上启下：增量式 GC 在全书算法篇的位置

至此，我们已经学完了八章内容，GC 算法的演化主线逐渐清晰：

|章节|核心创新|解决的矛盾|
|---|---|---|
|第2章 标记-清除|集中式可达性判定|"如何自动识别垃圾"|
|第3章 引用计数|分布式即时判定|"如何避免长 STW"|
|第4章 复制算法|对象移动|"如何消除碎片"|
|第5章 标记-压缩|原地压缩|"如何既无碎片又不浪费空间"|
|第6章 保守式 GC|不确定指针下的保守处理|"C/C++ 等非合作环境的 GC"|
|第7章 分代 GC|基于年龄的统计分区|"如何用统计规律大幅降低 GC 成本"|
|**第8章 增量式 GC**​|**GC 与 mutator 交替执行**​|**"如何把长 STW 打散为短停顿"**​|

**关键洞察**：第8章是 GC 演化史上的**第二个分水岭**（第一个是第7章分代 GC）。

- **第7章分代 GC**：在"空间维度"上优化——把堆按年龄分区，让每种基本算法在最擅长的地方工作
    
- **第8章增量式 GC**：在"时间维度"上优化——把 GC 工作打散到时间片上执行，用写屏障维护正确性
    

**增量式 GC 的真正价值，不在于它创造了新算法，而在于它提供了一套"让任何 GC 算法都能增量执行"的基础设施——写屏障**。这套基础设施一旦建立，下一章的"并发 GC"就水到渠成——把"交替执行"升级为"真正并行执行"，写屏障机制完全复用。

**带着"写屏障是 GC 与 mutator 并发执行的正确性交钥"这一视角进入下一章**，你会清晰地看到：并发 GC 不是一种新算法，而是增量式 GC 的"多核升级版"——核心机制（三色标记 + 写屏障）完全相同，只是执行环境从"单核交替"升级为"多核并行"。而现代 GC 的终极形态（G1/ZGC/Shenandoah），正是**分代（第7章）+ 增量（第8章）+ 并发（第9章）**三者深度融合的产物。

---

📌 **本章核心收获**：

- 增量式 GC 的本质：把一次长 STW 打散为多次极短停顿，GC 与 mutator 交替执行
    
- 底层机制是三色标记，根本矛盾是"GC 与 mutator 交替导致引用图不一致"
    
- 解决不一致的两条路径：
    
    - **路径①强三色不变式**：Steele 写屏障（把黑色对象染灰）——写屏障开销大，但浮动垃圾少
        
    - **路径②弱三色不变式（SATB）**：汤浅写屏障（覆盖前把旧对象染灰）——浮动垃圾多，但无需 STW 重扫根
        
    
- Dijkstra 插入屏障是 Steele 的"宽松版"——染灰新对象而非黑色对象
    
- Go 混合写屏障 = Dijkstra + Yuasa，同时堵住两条漏标路径，是写屏障演化的集大成者
    
- 工业印证：CMS 用 Dijkstra 屏障（Remark 阶段 STW 长）、G1 用汤浅 SATB（Remark 阶段极短）、Go 用混合写屏障、ZGC/Shenandoah 跳出写屏障用读屏障+染色指针/Brooks Pointer
    
- **增量式 GC 是"时间维度"的优化，与第7章分代 GC"空间维度"的优化正交**——两者结合就是现代 GC 的基石
    
- **写屏障是连接增量式 GC 与并发 GC 的核心基础设施**——下一章的并发 GC 本质上是增量式 GC 的多核升级版
