## 一、10.1 本章前言：Python GC 的"混合哲学"

Python 的 GC 设计遵循一个核心哲学——**"让最合适的机制做最合适的事"**：

- **引用计数**：负责 99% 的日常回收——对象死时立即释放，确定性、即时性
    
- **分代循环 GC**：负责那 1% 的"引用计数搞不定的事"——循环引用检测
    
- **四级内存分配器**：负责让"对象分配"这一最高频操作快到极致
    

> 💡 **第一性原理洞察**：Python GC 的本质，是把第3章引用计数法的"即时回收"优势发挥到极致，同时用第7章的分代思想 + 第2章的标记-清除来修补引用计数的致命短板（循环引用）。它不是一个新算法，而是**前九章理论的工业化组合**——这正是本书"实现篇"想要传达的核心讯息：**现代语言运行时的 GC，从来不是单一算法，而是多种算法的精密编排**。

## 二、10.2~10.7 Python 的内存分配器：四级金字塔

Python 对象分配的核心挑战是：**Python 程序创建和销毁海量小对象（整数、元组、字符串、函数参数列表）**，如果每次都直接调用系统 malloc/free，性能会被系统调用拖垮。CPython 的解法是构建**四级内存分配器金字塔**​ ：

```
┌─────────────────────────────────────────────────────────┐
│ 第3层：对象特有分配器（Per-type freelists）              │
│   tuple/list/float/frame 等内置类型的空闲列表缓存        │
├─────────────────────────────────────────────────────────┤
│ 第2层：Python 对象分配器（pymalloc）                     │
│   Arena(256KB) → Pool(4KB) → Block(8B~512B 尺寸类)       │
├─────────────────────────────────────────────────────────┤
│ 第1层：Python 低级内存分配器                             │
│   PyMem_RawMalloc / PyMem_Malloc → 调用 malloc           │
├─────────────────────────────────────────────────────────┤
│ 第0层：通用基础分配器                                    │
│   OS: mmap() / VirtualAlloc() / sbrk()                   │
└─────────────────────────────────────────────────────────┘
```

### 第0层：通用基础分配器（OS 层面）

操作系统提供的最底层接口——Linux 的 `mmap()`/`sbrk()`，Windows 的 `VirtualAlloc()`。这一层处理的是**内核页（通常 4KB）**的分配与回收。

### 第1层：Python 低级内存分配器

CPython 暴露三个"域（domain）" ：

|域|API|底层分配器|用途|
|---|---|---|---|
|**RAW**​|`PyMem_RawMalloc`|malloc|不需要 GIL 的保护域内存|
|**MEM**​|`PyMem_Malloc`|pymalloc|必须在 GIL 下分配的 Python 缓冲区|
|**OBJ**​|`PyObject_Malloc`|pymalloc|Python 对象分配|

> 💡 **洞见**：三个域的划分，体现了 CPython 对"分配场景"的精细区分。RAW 域甚至可以绕过 GIL——这对于无 GIL 构建（free-threaded build）至关重要，它直接用 mimalloc 替代 pymalloc，每个线程有独立的本地空闲列表 。

### 第2层：Python 对象分配器（pymalloc）—— 金字塔的核心

这是 CPython 性能的关键。pymalloc 的设计目标：**为 ≤512 字节的小对象提供极速分配**​ 。

**三级层次结构**​ ：

```
Arena (256KB)
└─ Pool (4KB) × 64
   └─ Block (尺寸类: 8, 16, 24, ..., 512 字节)
```

- **Arena**：256KB 大块，从 malloc 一次性申请，是**唯一真正能归还 OS 的单位**（当 arena 完全空闲时）
    
- **Pool**：4KB 页，每个 pool **只服务于单一尺寸类**（如 32 字节 pool 只分配 32 字节 block）
    
- **Block**：实际分配单元，按 8 字节倍数量化（size class）
    

**为什么这个设计极快**​ ：

1. **无系统调用开销**：对象分配在预分配的 arena 内部完成，不需要每次都 mmap
    
2. **无池内碎片**：pool 内所有 block 同尺寸，释放的 block 立即可服务下一次同尺寸分配
    
3. **缓存友好**：相似大小的对象倾向于聚集在同一个 pool，提升 CPU 缓存命中率
    
4. **>512 字节的对象直接回落 malloc**——pymalloc 不处理大对象
    

**尺寸类示例**：

|请求大小|分配 Block 大小|每 Pool 对象数|
|---|---|---|
|1-8 B|8 B|512|
|9-16 B|16 B|256|
|25-32 B|32 B|128|
|505-512 B|512 B|8|

### 第3层：对象特有分配器（Per-type Freelists）

某些内置类型维护自己的空闲列表，避免走 pymalloc 的热路径：

- **tuple**：小元组的按尺寸空闲列表
    
- **list**：空列表空闲列表
    
- **frame**：每线程栈帧空闲列表
    

> 💡 **第一性原理洞察**：四级分配器金字塔的设计，完美体现了工程中的一个核心法则——**"为最常见的情况做极致优化，罕见情况降级处理"**：
> 
> - 99% 的 Python 对象是 ≤512 字节的小对象 → pymalloc 极致优化
>     
> - 罕见的大对象 → 直接回落 malloc
>     
> - 高频的内置类型（tuple/list/frame）→ 再加速一层 freelist
>     
> - 每层都在"常见情况"上压榨性能，在"罕见情况"上保持正确
>     
> 
> 这正是我们在第3章 Sticky 引用计数、第4章 BiBOP 法中见过的同一种思维——**用统计规律优化常见情况**。Python 内存分配器的精妙，不在于发明了新算法，而在于**把"小对象高频分配"这一统计规律，用四级金字塔的结构化方式做到了极致**。

## 三、10.8~10.9 引用计数法：Python GC 的主力

### 对象头与引用计数

CPython 中每个对象都是一个 `PyObject`：

```
typedef struct _object {
    _PyObject_HEAD_EXTRA
    Py_ssize_t ob_refcnt;   // 引用计数
    PyTypeObject *ob_type;  // 类型指针
} PyObject;
```

每个对象头里都有 `ob_refcnt` 字段。引用增加时（赋值、传参、入容器）+1；引用减少时（del、离开作用域、容器移除）-1。**当 `ob_refcnt` 归零时，对象立即被释放**​ ——这是 CPython 的主力回收机制。

### 引用的所有权（Ownership）

CPython 用**"所有权"语义**管理引用计数 ：

- **"拥有"引用**：调用者负责在不再需要时 decref
    
- **"借用"引用**：调用者不增加计数，但保证在对象使用期间引用有效
    

这种精细的所有权协议，使得 C 扩展开发中引用计数的正确性可以被静态推理。

### 引用计数的工业实证

```
import sys
x = [1, 2, 3]
print(sys.getrefcount(x))  # 2（getrefcount 本身临时 +1）
y = x
print(sys.getrefcnt(x))    # 3
del y
print(sys.getrefcount(x))  # 2
x = None
# 此时 refcnt = 0 → 立即回收！
```

> 💡 **洞见**：引用计数的"即时回收"特性，使 CPython 的**内存行为具有确定性**——对象在 refcnt 归零的瞬间立即释放，内存不一定立刻归还 OS（arena 级别的归还要看整体占用），但对象的析构函数（如文件关闭、锁释放）会立即执行。这是 Python 适合编写**资源敏感型程序**（如文件处理、网络连接管理）的根本原因。

## 四、10.10 如何应对循环引用：分代循环 GC

### 循环引用的致命问题

```
class Node:
    def __init__(self):
        self.parent = None
        self.children = []

a, b = Node(), Node()
a.children.append(b)
b.parent = a
del a, b
# 即使外部引用已删除，a 和 b 互相引用
# refcnt 永远 ≥ 1，引用计数无法回收！
```

这是引用计数法的理论硬伤（第3章已详述）。Python 的解决方案是**集成一个分代循环 GC**​ ——它周期性运行，专门处理引用计数无能为力的循环垃圾。

### 分三代的架构

Python 将对象分为三代：

|代|对象特征|回收频率|
|---|---|---|
|**Gen 0**​|新创建的对象|最频繁|
|**Gen 1**​|从 Gen 0 存活晋升的对象|较低|
|**Gen 2**​|从 Gen 1 存活晋升的对象|最低|

### 触发机制：分配压力驱动，而非时间驱动

默认阈值 **(700, 10, 10)**​ ：

- **Gen 0 阈值 = 700**：当 Gen 0 中"分配数 − 释放数"的净值 ≥ 700 时，触发 Gen 0 回收
    
- **Gen 1 阈值 = 10**：Gen 0 被回收 10 次后，触发 Gen 1 回收（同时扫描 Gen 0）
    
- **Gen 2 阈值 = 10**：Gen 1 被回收 10 次后，触发 Gen 2 回收（全堆扫描）
    

> ⚠️ **关键澄清**：阈值**不是**"每代对象的总数量上限"，而是：
> 
> - `t0` 衡量 Gen 0 对象数量的**净增长**（新分配 − 已释放）
>     
> - `t1` 和 `t2` 衡量的是**前一代回收中幸存并被提升的对象数量**​
>     

这意味着：Python 的 GC 是**由分配压力触发的**，而非定时触发。这契合 Python 的工作负载特征——分配越频繁，越可能需要回收。

### 循环 GC 的算法本质：标记-清除

Python 的循环 GC 使用**标记-清除算法**（第2章）：

1. **标记阶段**：从根对象（全局变量、栈中变量等）出发，标记所有可达对象
    
2. **清除阶段**：遍历堆，回收所有未被标记的对象（即不可达的循环引用对象）
    

但 Python 做了一个精妙的优化——**只对"容器对象"做循环 GC**。因为**只有容器对象（list、dict、set、class instance 等）才能参与循环引用**，不可变对象（int、str、tuple 等）永远不会形成环。这大幅缩小了循环检测的扫描范围 。

### 分代假说的工业印证

Python 的分代设计与弱分代假说完美吻合——**大部分对象朝生夕灭**。Gen 0 被频繁扫描（每 700 次净分配），但大部分对象在 Gen 0 就被回收了，只有极少数"长寿"对象会晋升到 Gen 1 和 Gen 2，而高代的扫描频率指数级降低。

> 💡 **第一性原理洞察**：Python 的分代循环 GC，是第3章"部分标记-清除"思想的工业进化版：
> 
> - 第3章告诉我们：循环引用垃圾在实际程序中占比极小，不需要对整个堆做标记-清除，只需要对"可能成环的对象"做
>     
> - Python 的做法：只对容器对象做循环 GC（因为不可变对象不成环）+ 分三代（因为对象年龄分布符合弱分代假说）
>     
> - 两者结合：**扫描范围被双重缩小**——既按"对象类型"（容器 vs 不可变）过滤，又按"对象年龄"（Gen 0/1/2）分层
>     
> 
> 这是"统计规律优化"思想在 GC 中的极致应用——Python 用两个统计假设（"只有容器对象成环" + "弱分代假说"），把循环 GC 的成本压到了极低。

### 性能调整的工业建议

`gc` 模块提供了丰富的调优接口：

```
import gc

# 查看当前阈值
gc.get_threshold()  # (700, 10, 10)

# 手动调高阈值（减少 GC 频率，提升吞吐，但增加内存占用）
gc.set_threshold(1400, 20, 20)

# 手动调低阈值（增加 GC 频率，降低内存占用，但增加 CPU 开销）
gc.set_threshold(350, 5, 5)

# 手动触发回收
gc.collect()         # 全代回收
gc.collect(0)        # 只回收 Gen 0
```

**调优决策树**：

- 应用创建大量短命循环引用 → 降低阈值
    
- 应用性能受 GC 停顿影响、内存充裕 → 提高阈值
    
- 性能敏感的热路径 → `gc.disable()` 临时禁用，事后 `gc.enable()` + `gc.collect()`
    
- 已知父子循环引用 → 用 `weakref` 主动打破环（如树结构中 parent 用 weakref）

## 六、工业实践印证与深度洞察

### 1. 为什么 Python 选择"引用计数为主"而非"追踪式为主"

这是一个根本性设计决策，值得深入剖析：

**选择引用计数的收益**：

- **确定性回收**：对象 refcnt 归零立即释放，资源型对象（文件、锁、网络连接）可及时释放
    
- **无 STW**：引用计数的回收动作分散在 mutator 运行中，不需要 Stop-The-World
    
- **实现简单**：不需要复杂的 GC 调度器
    
- **内存实时释放**：大部分对象在不再被引用时立即释放
    

**选择引用计数的代价**​ ：

- **每次赋值/传参都有计数开销**​ → CPython 比 JVM 慢的主要原因之一
    
- **循环引用必须靠辅助 GC**​ → 周期性 tracing 带来 STW
    
- **多线程下计数器修改需要原子操作**​ → GIL 的隐性成本之一
    

**对比 JVM 的选择**：JVM 选择"追踪式 GC 为主"（从 Serial 到 G1 到 ZGC），因为：

- Java 的对象分配速率极高，引用计数的计数器开销不可接受
    
- Java 程序通常是长期运行的服务端应用，对"确定性回收"的要求低于对"吞吐量和停顿"的要求
    
- JVM 没有 GIL，多线程下引用计数的原子操作开销更加致命
    

> 💡 **工程启示**：语言运行时的 GC 选型，本质上是由**语言的语义特征**和**目标 workload**​ 共同决定的：
> 
> - Python：动态语言、单机脚本/服务端混合、重视资源确定性 → 引用计数为主
>     
> - Java：静态类型、服务端为主、重视吞吐 → 追踪式分代 GC 为主
>     
> - Go：并发微服务、重视低延迟 → 并发追踪式 GC
>     
> - Rust：编译期所有权 → 编译期引用计数（Rc/Arc）+ 无 GC
>     
> 
> **没有"最好的 GC"，只有"对这门语言最合适取舍的 GC"**。Python 的选择，是对"动态语言 + 资源敏感性"这组特征的 optimally balanced 答案。

### 2. CPython 3.14+ 的增量 GC：向"低延迟"演进

最新的 CPython 3.14 引入了**增量垃圾回收**​ ——这标志着 Python GC 正在向第8章的"增量式 GC"思想靠拢。通过把循环 GC 的标记阶段打散执行，Python 正在努力减少 GC 停顿对延迟敏感应用的影响。

这是本书理论演进在工业界的直接映射——当 Python 的应用场景从"脚本语言"扩展到"高并发服务端"（如 FastAPI、asyncio），原有的"周期性 STW 循环 GC"就成了瓶颈，增量式 GC 是自然的技术演进方向。

### 3. 内存不一定归还 OS：Arena 的生命周期

一个重要但常被忽视的细节：**Python 对象被引用计数回收后，内存通常不会立即归还 OS**​ 。

- 对象级别的回收：refcnt 归零 → 对象内存被 pymalloc 回收，block 回到 pool 的空闲列表
    
- Pool 级别的回收：当 pool 完全空闲时，可能被标记为空闲状态
    
- **Arena 级别的归还**：只有当整个 256KB arena 完全空闲时，才会通过 `munmap()` 真正归还 OS
    

这意味着：一个 Python 程序在峰值分配 1GB 内存、随后释放 900MB 后，进程的 RSS 可能仍然显示 ~1GB——因为那 900MB 分散在多个未完全空闲的 arena 中，无法归还 OS。

> 💡 **调优洞见**：这就是为什么长期运行的 Python 服务（如 Web 服务器）可能出现"内存只涨不跌"的现象——并非真正的内存泄漏，而是 arena 未能完全释放。**诊断工具**：`tracemalloc`、`objgraph`、`gc.get_objects()` 可以帮助定位哪些对象未被回收 ；`gc.set_threshold()` 可以调整回收频率。

### 4. 与其他语言运行时的横向对比

|运行时|主力算法|辅助机制|循环引用处理|
|---|---|---|---|
|**CPython**​|引用计数|分代循环 GC（标记-清除）|周期性 tracing|
|**PyPy**​|追踪式分代 GC|框架栈式 GC|集成在追踪 GC 中|
|**JVM HotSpot**​|分代追踪 GC|复制（新生代）+ 标记-整理（老年代）|追踪 GC 天然处理|
|**Go**​|并发三色标记-清除|混合写屏障|并发 tracing|
|**CoreCLR (.NET)**​|分代精确式移动 GC|复制 + 标记-压缩|追踪 GC 天然处理|
|**V8 (JavaScript)**​|分代式（Scavenge + Mark-Sweep-Compact）|增量标记 + 并发回收|追踪 GC 天然处理|

**核心观察**：CPython 是主流语言运行时中**唯一以引用计数为主力**的。这使它独树一帜——既有"确定性回收"的优势，也背负着"计数器开销 + 循环 GC 辅助"的代价。PyPy 作为 Python 的另一实现，选择了追踪式 GC 路线，证明了 Python 语义本身并不绑定于引用计数——但 CPython 为了兼容海量的 C 扩展（这些扩展依赖 `ob_refcnt` 的确定性行为），必须保留引用计数。

## 七、承上启下：Python GC 在全书"实现篇"的位置

至此，我们进入了本书的第二部分"实现篇"。Python 作为第一个案例，具有承上启下的关键作用：

**承上**：Python GC 几乎动用了算法篇的全部核心理论：

- 引用计数（第3章）—— 主力机制
    
- 标记-清除（第2章）—— 循环 GC 算法
    
- 分代 GC（第7章）—— 三代架构
    
- BiBOP（第4章）—— pymalloc 的 Pool 按尺寸类划分
    
- 部分标记-清除（第3章）—— 只对容器对象做循环检测
    
- 增量式 GC（第8章）—— Python 3.14+ 的演进方向
    

**启下**：Python GC 为后续三个工业案例提供了参照系：

- **第11章 Dalvik VM**：Android 的 ART 虚拟机，分代 + 复制 + 并发标记-清除
    
- **第12章 Rubinius**：Ruby 的 VM，也是引用计数 + 分代追踪的混合
    
- **第13章 V8**：JavaScript 引擎，分代式（Scavenge + Mark-Sweep-Compact）+ 增量 + 并发
    

**带着"Python 是以引用计数为主力"这一独特视角**，去看后续三个案例会发现：

- Dalvik/ART 和 V8 都选择了**追踪式 GC 为主力**（与 Python 相反）
    
- Rubinius 则和 Python 一样，是**引用计数 + 追踪式 GC 的混合架构**
    
- 这背后的根本差异在于：**语言的语义是否要求"确定性回收"**
    

Python 和 Ruby 作为动态脚本语言，需要确定性回收来保证资源（文件句柄、锁）的及时释放；而 Java/JavaScript/Go 作为服务端导向的语言，更重视吞吐和低延迟，可以接受"非确定性"的追踪式 GC。

---

📌 **本章核心收获**：

- Python GC = **引用计数（主力）+ 分代循环 GC（辅助）+ 四级内存分配器**，是前九章理论的工业级融合
    
- 四级分配器金字塔：第0层 OS → 第1层 PyMem → 第2层 pymalloc（Arena 256KB → Pool 4KB → Block 8B~512B 尺寸类）→ 第3层 Per-type Freelist
    
- pymalloc 的精妙：小对象（≤512B）走极速路径，**无系统调用、无池内碎片、缓存友好**；大对象直接回落 malloc
    
- 引用计数的工业实证：`ob_refcnt` 字段 + 所有权语义 → refcnt 归零立即释放 → **确定性回收**
    
- 循环引用处理：分三代（Gen 0/1/2）+ 只对容器对象做标记-清除 + 触发阈值 (700, 10, 10)
    
- 阈值 (700, 10, 10) 是**分配压力驱动**而非时间驱动：t0 衡量 Gen 0 净增长，t1/t2 衡量晋升数量
    
- Python 3.14+ 引入增量 GC，向低延迟演进——印证第8章增量式 GC 的工业趋势
    
- **Python 是主流语言运行时中唯一以引用计数为主力的**——这是对"动态语言 + 资源敏感性"这组特征的 optimally balanced 答案
    
- 内存不一定归还 OS：只有整个 256KB Arena 完全空闲时才会 munmap，这是长期运行 Python 服务"内存只涨不跌"的根本原因
    
- **调优工具箱**：`gc.get_threshold()` / `gc.set_threshold()` / `gc.collect()` / `gc.disable()` / `weakref` / `tracemalloc` / `objgraph`
