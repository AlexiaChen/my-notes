
# 《垃圾回收的算法与实现》读书笔记 · 第4章 GC 复制算法

> 延续前三章建立的"第一性原理"视角：标记-清除是"集中式、就地回收"——找到垃圾，在原地释放；引用计数是"分布式、即时回收"——每次指针操作都做一次微型判定。而**复制算法走了一条截然不同的路：与其费心找垃圾，不如把活对象全部搬走，剩下的空间整个清空**。这是一种"逆向思维"——不回收垃圾，而是**只保留活物**。

---

## 一、4.1 什么是 GC 复制算法：Semispace 模型

### 核心思想

把堆**对半切**成两个等大区域：`From` 空间（当前使用）和 `To` 空间（闲置）。当 `From` 空间满时，GC 从根集合出发遍历对象图，**把所有可达对象复制到 `To` 空间**，复制完成后 `From` 和 `To` 角色互换，`From` 空间整体变为可重新分配的空区域。

### 算法流程（Fenichel & Yochelson, 1969 的原始递归版本）

```
copying_gc():
    for r in roots:
        *r = copy(*r)           # 从根开始，递归复制
    swap(From, To)

copy(obj):
    if obj.forwarding != null:
        return obj.forwarding   # 已复制过，返回新地址
    new_obj = allocate_in_To(obj.size)
    new_obj = copy_fields(obj)  # 递归复制子对象
    obj.forwarding = new_obj    # 在原位置留下"转发表"
    return new_obj
```

**forwarding pointer（转发表）**​ 是整个算法的关键机制：对象被复制后，在 `From` 空间的旧址写入一个指向 `To` 空间新址的指针。这样当其他对象也引用它时，能通过 forwarding pointer 找到新地址，保证"同一对象只被复制一次"。

### 分配：Bump Pointer 的极致速度

因为 `To` 空间里的存活对象是**连续紧凑排列**的，分配新对象只需把 `free` 指针向后推——所谓 **bump-pointer allocation**，O(1) 时间。

> 💡 **第一性原理洞察**：复制算法的本质洞察是——**"识别垃圾"和"整理内存"可以合并为一步**。标记-清除先标记垃圾、再清除垃圾、内存仍然零散；复制算法则不关心垃圾是谁，只把活对象搬过来，垃圾自动留在 `From` 空间被整体丢弃。**垃圾不需要被单独识别，它们只是"没被搬走的那些"**。这是计算思维中典型的"与其正面解决问题，不如重新定义问题"——把 GC 问题重新定义为"活对象搬迁 + 空间压缩"问题。

---

## 二、4.2 优点：全部源自"只处理活对象 + 对象移动"

|优点|深层机制|
|---|---|
|**吞吐量优秀**​|只访问活对象，不扫垃圾；成本和**存活集大小**成正比，而非堆大小|
|**分配极快**​|bump-pointer，O(1)；无需空闲链表查找|
|**无碎片化**​|活对象紧凑排列，`From` 空间整体重用，外部碎片彻底消失|
|**缓存友好（深度优先版本）**​|有引用关系的对象在 `To` 空间里相邻，提升缓存命中率|

> 💡 **洞见**：这四条优点**有共同的源头**——"只搬活对象"这一动作同时达成了"高性能、快分配、无碎片、好局部性"。尤其是"只访问活对象"这一条，让复制算法在**高垃圾产生率**的 workload 下（如函数式语言、大量短命对象）效率极高——因为活对象少，要复制的也少。

---

## 三、4.3 缺点：同样是"对象移动"的副产品

|缺点|深层机制|
|---|---|
|**堆利用率仅 50%**​|必须预留一个等大的 `To` 空间，否则无法复制|
|**不兼容保守式 GC**​|对象地址变了，C/C++ 那种无法区分"是指针还是整数"的场景就无法使用|
|**递归实现栈开销大**​|原始 FY 算法递归复制子对象，消耗调用栈甚至栈溢出|
|**存活率高时复制成本高昂**​|如果活对象占堆的 90%，就要复制 90% 的对象——此时复制算法反而不如标记-清除|

> ⚠️ **核心洞见**：复制算法的根本矛盾是——**它用"空间换时间"**。预留 `To` 空间（空间换）、移动对象带来压缩和快分配（时间换）。但这个交换在"存活率低"时极度划算（复制少量活对象，获得整个压缩后的空间）；在"存活率高"时极度不划算（复制几乎所有对象，还占了双倍空间）。**这正是后续"分代算法"能够完美嫁接复制算法的关键**——分代把复制算法限制在"存活率极低的新生代"，让复制算法的优势被最大化，劣势被规避。

## 四、4.4 Cheney 的 GC 复制算法：把递归变迭代

C. J. Cheney 1970 年的论文《A Non-Recursive List Compacting Algorithm》给出了复制算法的**迭代实现**，这是工程上的里程碑。

### 核心机制：scan + free 双指针

```
To 空间布局：
[已被完全处理] [已被复制但未处理] [空闲]
     ↑                        ↑
   scan                    free
```

- **free 指针**：指向下一个可分配位置，复制对象时 free 后移
    
- **scan 指针**：指向"已复制但其子对象尚未处理"的对象
    

### 算法流程

```
cheney():
    for r in roots:
        *r = copy_root(*r)         # 根直接引用的对象复制到 To
    while scan != free:            # scan 追 free，追上即完成
        obj = *scan
        for each ref in obj.fields:
            ref = copy_ref(ref)    # 复制子对象（如有必要）
        scan += obj.size           # scan 前进
```

`copy_ref` 的判断逻辑利用了 forwarding pointer：**如果引用指向 `To` 空间，说明已复制；指向 `From` 空间，说明未复制**。

### 为什么这是广度优先

根对象先被复制进 `To`，scan 从 `To` 头部开始处理——先处理的根对象其子对象被复制到 free 处（即 `To` 尾部附近），scan 要等前面的都处理完才轮到它们。这就形成了一个**隐式的 FIFO 队列**，`To` 空间本身就是队列，无需额外数据结构。

> 💡 **洞见**：Cheney 算法的精妙在于**"用堆空间本身当队列"**。传统的广度优先搜索需要一个显式队列数据结构，而 Cheney 巧妙地用 `scan` 和 `free` 指针把 `To` 空间变成了队列——`free` 入队，`scan` 出队。这种"不额外消耗内存"的特性，体现了 GC 算法设计中"复用已有资源"的最高艺术。

### 代价：缓存不友好

广度优先导致有引用关系的对象在 `To` 空间里**距离较远**。例如父对象 A 在 `To` 开头，它的子对象 B/C/D 被复制到 `To` 尾部附近，A 和 B/C/D 在空间上不相邻——缓存局部性差。

---

## 五、4.5 近似深度优先搜索方法：修复缓存局部性

### Moon 算法（1970s）的初步尝试

引入第三个指针 `scan_partial`，让它指向**最近一个虚拟内存页**进行扫描。这样在同一页内的对象是深度优先复制的，跨页才是广度优先。缺点是对象可能被扫描两次。

### Wilson 等人的改进版（真正实用的近似深度优先）

引入**页面级局部扫描机制**：

- **page[]**：将堆分割为一个个页面的数组
    
- **local_scan[]**：每个页各自的扫描指针
    
- **major_scan**：指向第一个未完全搜索完的页面
    
- **free**：分配指针
    

**算法逻辑**：

1. 从根直接引用的对象复制到 `page[0]`
    
2. 对 `major_scan` 指向的当前页，用 `local_scan` 在该页内做**类深度优先**搜索
    
3. 如果复制出的新对象落到某个页，就对该页触发一次局部扫描
    
4. `major_scan` 持续指向第一个未搜索完的页，直到所有页都搜索完毕
    

**效果**：互相引用的对象**基本落在同一个内存页中**，有效利用高速缓存。

> 💡 **洞见**：近似深度优先方法揭示了一个深刻的工程真理——**完美的深度优先需要递归（栈开销大），完美的广度优先缓存不友好（Cheney）**。工程解法是"折中"：**在页内深度优先，跨页广度优先**。这本质上是把"局部性"概念显式建模为"页"——同一页内的对象大概率同时被访问，所以让它们深度优先聚集；跨页的对象访问频率相对较低，广度优先也无妨。这种"分层折中"的思维，在后续 G1 的 Region 化设计中再次登场。

## 六、4.6 多空间复制算法：缓解堆利用率低

### 核心思想

既然"只能利用半个堆"是复制算法的最大痛点，那就**不要把整个堆都切成两半**——把堆 N 等分，拿出 2 份作为 `From` 和 `To` 执行复制算法，**其余 N-2 份空间用标记-清除算法管理**。

### 工作方式

- 每次 GC 时，`From` 和 `To` 向后滚动一个等分位
    
- 在复制算法的 2 份空间里：活对象被复制、压缩、无碎片
    
- 在其余 N-2 份标记-清除空间里：用我们第2章学过的算法管理
    

### 权衡

- ✅ 堆利用率从 50% 提升到 (N-2)/N，N 越大利用率越高
    
- ❌ 标记-清除部分的空间仍然存在碎片问题
    
- ❌ 实现复杂度显著上升——两套 GC 机制并存
    

> 💡 **洞见**：多空间复制算法是"混合 GC"思想的又一次展现——**不再追求单一算法完美，而是让不同算法各司其职**。复制算法负责"需要高压缩、高分配速度"的那部分堆；标记-清除负责"存活率高、不适合复制"的那部分堆。这种"分而治之"的思想，直接预示了后续**分代 GC**​ 的设计哲学：不同特征的对象用不同算法管理。事实上，多空间复制可以看作是分代 GC 的"雏形版本"——只是分代 GC 用"对象年龄"来动态决定对象在哪个空间，而多空间复制用静态划分。

## 七、章节脉络：复制算法的"得与失"同源

```
复制算法（Semispace）
├─ 本质：只搬活对象，垃圾自动留在 From
├─ 优点（都源自"对象移动 + 只处理活对象"）
│   ├─ 吞吐高（只访问活对象）
│   ├─ 分配快（bump-pointer）
│   ├─ 无碎片（活对象紧凑排列）
│   └─ 缓存友好（深度优先版本）
├─ 缺点（也都源自"对象移动"）
│   ├─ 堆利用率 50%（必须预留 To 空间）
│   ├─ 不兼容保守式 GC（对象地址变了）
│   ├─ 递归实现栈开销大
│   └─ 存活率高时复制成本高
└─ 改进路径
    ├─ 4.4 Cheney：递归→迭代（解决栈开销）
    │   └─ 代价：广度优先→缓存不友好
    ├─ 4.5 近似深度优先：修复缓存局部性
    │   └─ 代价：实现复杂，对象可能被扫描多次
    └─ 4.6 多空间复制：缓解堆利用率低
        └─ 代价：标记-清除部分的碎片问题依然存在
```

**更深层的洞见**：复制算法的演化史，是"对象移动"这一设计决策的**利弊权衡史**。每一次改进都在"移动对象"带来的某个优势或劣势上做文章：

- Cheney 改进了"移动的方式"（递归→迭代），但意外损害了缓存局部性
    
- 近似深度优先修复了 Cheney 的缓存问题，但增加了实现复杂度
    
- 多空间复制缓解了"移动"导致的空间浪费，但引入了混合管理的复杂性
    

**这揭示了一个 GC 算法设计的普遍规律：没有任何一种改进是"免费"的**。每一个改进都在用一种新的代价，去替换原有的代价。理解这一点，你就能预判：未来任何一种新 GC 算法，必然也是在某个维度上做权衡。

## 八、工业实践印证

### JVM 新生代：复制算法的现代工业典范

HotSpot JVM 的**新生代（Young Generation）**​ 正是复制算法的工业化身：

```
新生代布局：
┌─────────┬──────────────┬──────────────┐
│  Eden   │   Survivor0   │   Survivor1   │
│ (80%)   │   (10%)       │   (10%)       │
└─────────┴──────────────┴──────────────┘
   ↓ Minor GC 时
┌─────────┬──────────────┬──────────────┐
│  Eden   │   Survivor1   │   Survivor0   │
│  清空   │  (From→To)    │   (新 To)     │
└─────────┴──────────────┴──────────────┘
```

- **Eden 空间**：新对象分配于此，占新生代 80%
    
- **Survivor0 / Survivor1**：相当于 `From` 和 `To` 空间
    
- **Minor GC**：Eden + 一个 Survivor 里的活对象，复制到另一个 Survivor
    
- **IBM 统计数据**：**98% 的对象是朝生夕灭的**——这正是复制算法最理想的应用场景
    

> 💡 **工程洞见**：JVM 选择复制算法用于新生代，完美印证了我们在 4.3 节的分析——**复制算法在"存活率低"时极度高效**。98% 的对象在 Minor GC 时已经死亡，需要复制的活对象极少，复制成本极低，却换来了 Eden 区完全的压缩和无碎片。这是"算法特征"与"workload 特征"完美匹配的典范。

### G1 GC：Cheney 复制思想的 Region 化演进

G1 把堆切成等大小的 Region，年轻代回收时采用 **Cheney 风格的复制**：

- 把 Eden 和 Survivor 里的活对象 **evacuate（疏散）**​ 到新的 Region
    
- 疏散过程本质是 Cheney 复制——scan/free 指针的 Region 版本
    
- 老年代回收时用标记-清除（或标记-整理）
    

### Appel 式 GC：复制算法 + 大堆

Appel 在 1989 年提出：**如果能提供比平均活对象体积大几倍的堆空间，复制算法可以做到任意高效**。因为堆越大，单次 GC 触发间隔越长，复制算法"只处理活对象"的优势越明显。这是"用空间换时间"的极致——**堆空间本身是复制算法的最佳加速器**。

### 函数式语言的天然伴侣

Lisp Machine（Symbolics 3600）、Smalltalk、Self 等语言早期都采用 Cheney 复制算法，因为函数式编程大量产生短命对象，复制算法的"只处理活对象"特性完美契合。

## 九、承上启下：复制算法在全书算法篇的位置

至此，我们已经学了三种基本 GC 算法，它们构成了"算法篇"的三角基石：

|算法|核心动作|根本优势|根本劣势|适用场景|
|---|---|---|---|---|
|**标记-清除**（第2章）|就地标记垃圾并释放|不移动对象、兼容保守式 GC|碎片、分配慢、STW 长|C/C++ 运行时、老年代|
|**引用计数**（第3章）|每次指针操作更新计数|即刻回收、停顿平滑|循环引用、计数器开销|Python、需要确定性回收|
|**复制算法**（第4章）|搬迁活对象到新空间|无碎片、分配快、吞吐高|堆利用率低、不兼容保守式 GC|新生代、函数式语言|

**关键洞察**：这三种算法各有一个"阿喀琉斯之踵"——

- 标记-清除：**碎片**
    
- 引用计数：**循环引用**
    
- 复制算法：**只能利用半个堆**
    

而有趣的是，**这三种劣势恰好可以被"分代"思想统一解决**：

- 分代后，复制算法只用于新生代（存活率低 → 复制成本低 → 半个堆的代价可接受）
    
- 老年代用标记-清除或标记-整理（存活率高 → 复制不划算 → 就地回收更合适）
    
- 循环引用问题在分代框架下由老年代的 tracing 统一处理
    

**这就是为什么下一章（第5章）的分代算法会成为现代 GC 的事实标准**——它不是发明了一种新算法，而是**巧妙组合了已有的三种算法，让每种算法只在自己最擅长的场景工作**。理解了这个"组合哲学"，你就拿到了打开现代 GC 设计的钥匙。

---

📌 **本章核心收获**：

- 复制算法的本质是"重新定义问题"——不找垃圾，只搬活物；垃圾自动留在原地
    
- 所有优点（高吞吐、快分配、无碎片、好局部性）和所有缺点（堆利用率低、不兼容保守式 GC、存活率高时成本高）都源自"对象移动"这一设计决策
    
- Cheney 算法用 scan/free 双指针把递归变迭代，**用堆本身当队列**——GC 算法设计的艺术典范
    
- Cheney 的广度优先带来缓存不友好，近似深度优先通过在页内深度优先、跨页广度优先来折中
    
- 多空间复制用"复制 + 标记-清除"混合，缓解堆利用率问题，是分代 GC 的雏形
    
- JVM 新生代（Eden + S0/S1）是复制算法的完美工业印证——98% 对象朝生夕灭的统计规律让复制算法优势最大化
    
- 三种基本算法的根本劣势，恰好可以被"分代"思想统一解决——这是下一章的核心命题
