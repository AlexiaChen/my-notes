
# 《垃圾回收的算法与实现》读书笔记 · 第2章 GC 标记-清除算法

> 延续上一章建立的"第一性原理"视角：GC 的本质是**可达性判定 + 空间复用**。标记-清除（Mark-Sweep）是这一本质最直白的回答——**先用标记阶段完成"判定"，再用清除阶段完成"复用"**。它是所有 tracing GC 的"源点算法"，后续复制、标记-压缩、分代、并发 GC 全是它的"补丁版本"。

---

## 一、2.1 标记-清除算法：最朴素的"两步走"

算法由**标记阶段**和**清除阶段**构成，伪代码层面的定义非常清晰：

```
Mark Phase:
  Mark(root):
    if markedBit(root) == false:
        markedBit(root) = true
        for each v referenced by root:
            Mark(v)

Sweep Phase:
  Sweep():
    for each object p in heap:
        if markedBit(p) == true:
            markedBit(p) = false   // 清标记，为下次 GC 做准备
        else:
            heap.release(p)        // 回收垃圾，链入空闲链表
```

**标记阶段**：从 GC Roots（线程栈局部变量、静态变量、JNI 引用等）出发，**深度优先**遍历对象图，给所有可达对象打上 mark 位。用 DFS 而非 BFS，是为了压低递归栈的内存占用。

**清除阶段**：线性扫描整个堆，把"未标记"的对象回收到空闲链表，把"已标记"对象的标记位清零。

> 💡 **第一性原理洞察**：标记-清除的精妙之处在于——**它把"什么是垃圾"这个哲学问题，转化成了"从根出发能否到达"这个图论问题**。这种"正向标记活对象、反向回收死对象"的二分法，是整个 tracing GC 家族的共同祖先。后续所有算法，要么改"标记"的方式（三色标记、并发标记），要么改"清除"的方式（复制、压缩、分代），但**"从根可达性判定生死"这个内核从未动摇**。

---

## 二、2.2 优点：为什么它能成为"始祖算法"

|优点|深层含义|
|---|---|
|**实现简单**​|两个函数（Mark + Sweep）即可完成，易于验证正确性|
|**天然处理循环引用**​|循环引用只要从根到达不了，照样被回收——这是引用计数做不到的|
|**不移动对象（No Relocation）**​|回收后对象地址不变，因此**与保守式 GC 兼容**——可以在 C/C++ 运行时中使用，无需编译器配合|
|**内存开销低**​|每个对象只需 1 个 mark 位，无需额外复制空间|

> 💡 **工程洞见**：**"不移动对象"是标记-清除最被低估的优势**。正因为对象不动，Boehm-Demers-Weiser GC 才能作为保守式收集器直接用于 C/C++，被 Mozilla Firefox（JavaScript 引擎）和 Mono 采用。任何需要"与现有原生代码互操作"的场景，标记-清除都是首选——这是复制算法天生做不到的。

---

## 三、2.3 缺点：四个致命短板催生了后续所有改进

标记-清除的四大缺点，恰好对应了本章 2.4~2.7 的四个改进方向：

**① 碎片化（Fragmentation）**

清除后空闲内存散布为大量不连续的小块。极端情况下，总空闲内存有 500MB，但全是大大小小的碎片，一个 100MB 的连续分配就会失败——即使总空闲远超需求。这是标记-清除**最致命的弱点**。

**② 分配速度慢**

分配时需要遍历空闲链表寻找合适分块（First-Fit / Best-Fit / Worst-Fit）。最坏情况要遍历整个链表。

**③ 与写时复制（Copy-on-Write）不兼容**

在 Linux `fork()` 场景下，父子进程本应共享内存页，只有当某一方写入时才复制该页。但标记-清除需要在**对象头**上改写 mark 位——这意味着即使 mutator 没改对象数据，GC 的标记动作也会触发 COW 页面复制，让 COW 的共享优势荡然无存。

**④ STW 停顿长**

标记阶段和清除阶段都要遍历整个堆，**停顿时间与堆大小线性相关**。对于交互式或实时系统，这是不可接受的。

> ⚠️ **核心洞见**：这四个缺点不是孤立的，它们共同指向标记-清除的"原罪"——**它是一种"就地回收"算法，既不动对象，又不整理内存，又不区分对象年龄，又把管理信息写在对象头上**。每一个"不"都换来了一个优点，但也都埋下了代价。后续所有改进，本质上都是在"打破某一个不"——这正是本章 2.4~2.7 的隐藏主线。

---

## 四、2.4 多个空闲链表：修补"分配速度慢"

### 改进思路

原本只有一个全局空闲链表，所有大小的分块混在一起，分配时必须线性遍历。改进方案是**按分块大小分组**，建立多个空闲链表：

- 分块大小为 2, 3, 4, ..., limit 的，各自建立独立链表
    
- 大于 limit 的大分块需求极为罕见，全部放入一个"大块链表"统一处理
    

### 工业印证

> 💡 **Go 语言的内存分配器就是这样做的**——按大小等级（size class）建立多个空闲链表（mspan），分配时按对象大小直接定位到对应等级的链表，避免遍历。这是标记-清除"多空闲链表"思想在现代工业中的直接继承。

**权衡**：牺牲了一定的内存灵活性（大块链表查找稍慢，但大块分配本就稀少），换来了分配速度的数量级提升。

---

## 五、2.5 BiBOP 法：修补"碎片化"

**BiBOP = Big Bag Of Pages**。思路：把堆划分为固定大小的 Page，再把若干 Page 组成 Bag，**让每个 Bag 只分配同一种固定大小的对象**。

```
Bag A (只放 2 字对象)  |  Bag B (只放 3 字对象)  |  Bag C (只放 4 字对象)
```

回收一个 2 字对象后，这块空间将来仍能分配给新的 2 字对象——Bag 内部不会出现大小不匹配的碎片。

> ⚠️ **但 BiBOP 并未真正消除碎片**：如果程序申请的 2 字对象很少，而 4 字对象很多，就会出现"2 字 Bag 空闲、4 字 Bag 溢出"的尴尬——**整体堆利用率反而下降**。Memcached 的内存分配器就采用了类似的思路。

**洞见**：BiBOP 本质是**用"空间换碎片"**——通过限制每个区域的多样性，来抑制区域内碎片；代价是跨区域的负载不均。**它是标记-清除走向"分代/分区域"管理的中间形态**，本书后续的 G1 式 Region 化思路，与此一脉相承。

---

## 六、2.6 位图标记：修补"与写时复制不兼容"

### 核心思想

既然"在对象头上改 mark 位"会破坏 COW，那就**把 mark 位从对象头抽出来，集中放到一张独立的位图（Bitmap）里**：

```
堆对象区:  [obj0][obj1][obj2]...           ← 不再修改
位图区:    [bit0][bit1][bit2]...           ← mark 操作改这里
```

每个对象（或其首地址）在位图中对应一个 bit。标记阶段改位图，清除阶段遍历位图并清零。

### 带来的两个好处

1. **与 COW 兼容**：位图表极小，即使被复制也无伤大雅；更重要的是，对象本身不被修改，不会触发无谓的页面复制。
    
2. **清除更高效**：清标记时不需要遍历整个堆的对象头，只需把位图整体清零（或遍历位图），缓存友好度大幅提升。
    

> 💡 **工程洞见**：位图标记体现了 GC 设计的一个重要范式——**"管理信息与业务数据分离"**。这个思想在后续算法中反复出现：G1 的 Remember Set、ZGC 的 Colored Pointer、Shenandoah 的 Brooks Pointer，本质上都是"把 GC 所需的元数据从对象头剥离出去"的演进。位图标记是这一范式的鼻祖。

**注意**：多个堆的情况下，对象地址不连续，无法用简单的位运算从对象地址算出位图索引，需要为每个堆配一张位图。

---

## 七、2.7 延迟清除法（Lazy Sweep）：修补"STW 过长"

### 核心思想

传统清除阶段必须一次性扫完整个堆，造成长停顿。**延迟清除的核心洞察是：mutator 分配时往往只需要"一块够用的空间"，而不是"全部空闲空间"**。因此——

> 把清除工作打散到每次分配时按需进行：分配器调用 `lazy_sweep(size)`，从堆中线性搜索，找到第一个 ≥ size 的未标记分块就立即返回；找不到才触发一次完整标记，然后继续延迟清除。

```
new_obj(size):
    chunk = lazy_sweep(size)        # 从上次位置继续扫，找到就返回
    if chunk != NULL:
        return chunk
    mark_phase()                    # 极端情况：扫完都没找到，做一次完整标记
    chunk = lazy_sweep(size)        # 再试一次
    if chunk != NULL:
        return chunk
    return NULL                     # 真 OOM
```

### 权衡与局限

- ✅ **最大暂停时间显著缩短**：单次清除只扫到"够用"为止，不再扫全堆。
    
- ⚠️ **效果不稳定**：如果上次暂停位置恰好落在"活动对象密集区"，下一次 `lazy_sweep` 可能要跳过大量活动对象才能找到垃圾，反而导致长停顿。
    
- ⚠️ **只解决了清除阶段，没解决标记阶段**：标记仍是 STW。这个问题的彻底解决要等到下一章的"增量回收"和"三色标记"。
    

> 💡 **洞见**：延迟清除是标记-清除走向"并发/增量"的第一次试探——它承认了"GC 不必一次性做完，可以穿插在 mutator 运行中"。这个思想直接开启了后续章节的**增量式 GC、三色标记、并发标记**的完整演化链。

## 八、章节脉络：四个改进如何对应四个缺点

```
标记-清除算法
├─ 缺点①碎片化 ──────────→ 2.5 BiBOP（堆布局层面修补）
├─ 缺点②分配慢 ─────────→ 2.4 多个空闲链表（分配器层面修补）
├─ 缺点③COW不兼容 ─────→ 2.6 位图标记（标记存储层面修补）
└─ 缺点④STW长 ──────────→ 2.7 延迟清除（执行时机层面修补）
```

**更深层的洞见**：这四个改进**彼此正交，可以叠加使用**。工业级 GC 往往是"多空闲链表 + 位图标记 + 延迟清除"的组合体；BiBOP 则更像是"分代/分区域"思想的雏形。每一种改进都只解决一个问题，但都不引入复制算法的"对象移动"——因为一旦移动对象，就破坏了标记-清除最大的优势（与保守式 GC 兼容、与 C/C++ 互操作）。

这就是为什么 **Boehm-Demers-Weiser GC**（C/C++ 保守式 GC）至今仍是标记-清除的纯正血脉继承者——它宁可忍受碎片和停顿，也要保住"不移动对象"的兼容性。

## 九、工业实践印证

|工业实现|与本章的对应关系|
|---|---|
|**Python 的循环垃圾收集器**​|引用计数为主，但循环引用无法处理，因此**专门用标记-清除来回收循环垃圾**——这正是标记-清除"天然处理循环引用"优势的直接应用|
|**HotSpot Serial GC（老年代）**​|使用 **Mark-Sweep-Compact**：标记-清除 + 后续压缩阶段，压缩专门解决碎片问题|
|**Dalvik / 早期 ART GC**​|以标记-清除为主，但因碎片问题导致大对象分配失败，最终催生了 ART 的 **Concurrent Copying GC**​|
|**Boehm-Demers-Weiser GC**​|纯标记-清除 + 位图标记思想的保守式 C/C++ 收集器，被 Firefox、Mono 采用|
|**Go 内存分配器**​|多空闲链表（size class + mspan）思想的现代化身|
|**Ruby GC**​|提供 `immediate_sweep: false` 参数，允许**延迟清除**（lazy sweep）|

> 💡 **架构师视角的总结**：标记-清除的四大缺点在工业界不是被"解决"的，而是被"绕开"的——
> 
> - **碎片问题**​ → 用"标记-压缩"或"复制算法"绕开（HotSpot 老年代 Mark-Sweep-Compact）
>     
> - **分配慢**​ → 用"多空闲链表 / 线程本地缓存"绕开（Go, JVM TLAB）
>     
> - **COW 不兼容**​ → 用"位图标记"绕开（Boehm GC）
>     
> - **STW 长**​ → 用"并发标记 + 增量清除"绕开（CMS, G1, ZGC）
>     
> 
> 理解了这套"缺点 → 改进 → 工业绕开"的映射，你就掌握了**阅读任何现代 GC 实现的元框架**。

## 十、承上启下：标记-清除的"遗产"与"未竟之事"

标记-清除给出了 GC 最朴素的解法，但它留下了两个**它自己解决不了、必须靠后续算法接力**的问题：

1. **对象移动的禁忌**：标记-清除为了兼容性坚持"不移动对象"，但这导致碎片无解。复制算法和标记-压缩算法将接过"整理内存"的使命——代价是放弃与保守式 GC 的兼容。
    
2. **STW 的根本矛盾**：延迟清除只缓解了清除阶段的停顿，标记阶段仍是 STW。要彻底打破，必须引入**三色标记 + 写屏障**，让标记与 mutator 并发进行——这是下一章"增量回收"和后续"并发 GC"的核心议题。
    

带着这两个未竟之问进入后续章节，你会清晰地看到：**复制算法是如何用"对象移动"换取"零碎片 + 高分配速度"的；分代算法是如何用"年龄假设"换取"大部分 GC 工作量锐减"的；并发算法是如何用"写屏障"换取"标记与 mutator 同时运行"的**。每一种新算法，都是对标记-清除某个短板的针对性补丁——这就是全书算法篇的统一叙事弧线。

---

📌 **本章核心收获**：

- 标记-清除 = **可达性标记 + 就地回收**，是所有 tracing GC 的源点
    
- 四大缺点（碎片 / 分配慢 / COW 不兼容 / STW 长）催生了四大改进
    
- 四种改进**彼此正交、可叠加**，但都不打破"不移动对象"的底线
    
- 工业界不是"解决"了这些缺点，而是**用组合拳"绕开"**了它们
    
- 标记-清除留下的两个根本矛盾（对象不可移动、标记必须 STW），将驱动后续所有算法的演化
