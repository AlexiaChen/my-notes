
# 《垃圾回收的算法与实现》读书笔记 · 第6章 保守式 GC

> 延续前五章建立的"第一性原理"视角：之前我们学的所有算法（标记-清除、引用计数、复制、标记-压缩），都隐含了一个前提——**GC 能准确知道"哪里是指针、哪里不是指针"**。但现实中，C/C++ 这种语言处理程序，**栈、寄存器、全局变量里的值，GC 根本无法区分是整数还是指针**——这时怎么办？本章回答的正是这个"元问题"：**当指针识别不可靠时，GC 该如何自处？**

---

## 一、6.1 什么是保守式 GC：在"不确定性"面前选择保守

### 核心定义

**保守式 GC（Conservative GC）**​ 指的是"不能识别指针和非指针的 GC"。

在 C/C++ 这类语言中，以下位置被称为**"不明确的根"（ambiguous roots）**：

- 寄存器
    
- 调用栈（call stack）
    
- 全局变量空间（.data 段）
    

GC 无法从编译器获得"这些位置的值是否是指针"的元数据。面对这种不确定性，保守式 GC 采取了一种"宁枉勿纵"的态度：**把所有疑似指针的值，都当作指针来处理**。

### 疑似指针的三重过滤

保守式 GC 在检查不明确的根时，会通过三个基本项目来判断一个值"是否可能是指针"：

1. **对齐检查**：值是否正确对齐？（如 64 位 CPU 下是否为 8 的倍数）
    
2. **堆范围检查**：值是否指向堆内？
    
3. **对象头检查**：值是否指向堆内某个对象的开头？
    

只有**同时满足这三个条件**，该值才被"保守地"认定为指针。

> 💡 **第一性原理洞察**：保守式 GC 的本质，是在"指针识别的不确定性"面前做出的**风险不对称选择**。
> 
> - 如果把"真指针"误判为非指针 → 活对象被错误回收 → **程序崩溃**（不可接受）
>     
> - 如果把"非指针"误判为指针 → 垃圾对象被错误保留 → **内存泄漏**（可接受）
>     
> 
> 这两种错误的代价**极度不对称**——前者是灾难，后者是可容忍的退化。因此"保守"二字不是贬义，而是一种**工程上的理性选择**：宁可错杀（保留）一千，不可放过一个（回收）。这种"风险不对称驱动设计"的思维，在系统工程里反复出现（如 Type-Safe 语言的选择、数据库的事务隔离级别）。

### 工业锚点：Boehm-Demers-Weiser GC

Hans Boehm、Alan Demers、Mark Weiser 于 1988 年提出的 **Boehm GC**，是保守式 GC 最经典的工业实现：

- 作为 C/C++ 中 `malloc()` 的 drop-in replacement
    
- 使用 tracing mark-sweep 算法
    
- 定期扫描栈、寄存器、全局变量，把所有"像指针的值"当作指针
    
- **不移动对象**——因为分不清指针与整数，就不敢改写任何字
    
- 被 gcj (Java)、Mono (C#/.NET)、Bigloo (Scheme)、MzScheme 等采用

## 二、6.2 优点：语言处理程序与 GC 的解耦

|优点|深层含义|
|---|---|
|**语言处理程序不依赖于 GC**​|不需要编译器配合，GC 可以作为独立库存在|
|**易于挂接到任何语言**​|包括 C/C++ 这种无类型安全保证的语言|
|**实现简单**​|不需要生成栈图、类型元数据，不需要改写 mutator 代码|
|**与手动内存管理共存**​|可以只给部分代码用 GC，其他代码仍用 malloc/free|

> 💡 **洞见**：保守式 GC 的最大价值，是**打破了"GC 必须与语言深度耦合"的定律**。在 C/C++ 这种"非合作环境"（uncooperative environment）中，精确式 GC 几乎无法实现——因为编译器不提供指针位置的元数据。Boehm GC 的出现，让 C/C++ 程序员也能享受到自动内存管理的好处，而无需重写语言运行时。

---

## 三、6.3 缺点：保守的代价

保守式 GC 的缺点和它的优点是硬币的两面——**正是"不要求编译器配合"这一设计，带来了所有问题**：

**① 识别指针需要成本**

对每个根做对齐检查、堆范围检查、对象头检查，本身就有开销。

**② 错误识别指针会压迫堆（False Retention）**

一个值恰好等于某个对象地址的整数，会把那个对象连同它指向的整张子图都"吊住"。在指针密集、地址空间紧张时可能很严重。

**③ 不能使用复制算法等"移动对象"的 GC 算法**

这是最致命的限制。**复制算法、标记-压缩算法都需要移动对象，移动后必须改写所有指向该对象的指针**。但在保守式 GC 中，根里的某个值可能是 false pointer（实质是整数，但长得像指针）——如果 GC 移动了"该指针指向的对象"，并尝试把这个根改写为新地址，就会**破坏原本应该是整数的数据，导致程序异常**。

> ⚠️ **核心洞见**：这第三条缺点定义了一个根本性的"可行域边界"——
> 
> **指针识别精度 → 反向决定 GC 算法可行域**
> 
> - 保守式（不能识别）→ 不敢移动对象 → **只能用标记-清除这类"不移动"的算法**
>     
> - 准确式（能识别）→ 可以安全移动对象 → **解锁复制算法、标记-压缩、分代复制**
>     
> 
> 这就是为什么 Boehm GC 虽然是 mark-sweep，但**永远不做 compaction**——移动对象意味着要改写所有引用，而保守式 GC 不敢改写疑似指针。这也直接导致 Boehm GC 存在堆碎片问题。

---

## 四、6.4 准确式 GC：保守式的对立面

**准确式 GC（Precise/Exact GC）**​ 指的是"能正确识别指针和非指针的 GC"。

### 实现方式

- 编译器为每个安全点生成**栈图（stack map）**
    
- 为每个类型生成**堆指针位图**
    
- 运行时据此准确区分指针与非指针
    

### 优缺点对比

|维度|保守式 GC|准确式 GC|
|---|---|---|
|指针识别|启发式（对齐+堆范围+对象头）|精确（编译器提供元数据）|
|能否移动对象|❌ 不能|✅ 能|
|可用算法|仅标记-清除类|全部（复制、压缩、分代均可）|
|假指针泄漏|有|无|
|语言处理程序复杂度|低（GC 独立）|高（编译器必须配合）|
|代表|Boehm GC (C/C++)|HotSpot (Java)、Go、CoreCLR (.NET)|

> 💡 **洞见**：Go 的选择很有代表性——它采用准确式 GC，要求编译器为每个安全点生成栈图。**代价**是编译器与运行时的复杂度，以及栈图带来的二进制体积；**换来**的是：没有假指针导致的泄漏，回收更彻底；并且因为确切知道每个指针的位置，**为将来的移动式回收留了门**——Go 至今不移动堆对象，但它移动栈（copystack 扩缩栈时要把栈上所有指针逐一改写到新栈），靠的正是同一套栈图。
> 
> **"精确，是这一切优化得以安全进行的前提"**——这句话道破了准确式 GC 的战略价值。

## 五、6.5 间接引用：让保守式 GC 能用复制算法

### 核心思想

既然保守式 GC 不能用复制算法的根本原因是"不敢改写根里的疑似指针"，那么**能不能让根永远不指向对象本身，而是通过一个中间层（句柄，handle）来引用？**

```
改造前（保守式 GC 不能直接用复制）：
  根 ──→ 对象A
  如果移动对象A，必须改写根，但根是"不明确的根"，不敢改

改造后（经由句柄间接引用）：
  根 ──→ 句柄 ──→ 对象A
  移动对象A时，只需改写句柄里的指针，根本身不变
```

**具体做法**：

- 根和对象之间引入**句柄（handle）**
    
- 每个对象都有一个句柄，句柄持有指向对象的指针
    
- 局部变量和全局变量这些"不明确的根"里，**只装着指向句柄的指针**，而非直接指向对象
    
- mutator 操作对象时，要通过句柄的间接引用来执行处理
    
- 移动对象时，只需修改句柄里的指针，无需改写根
    

### 优点与代价

- ✅ **保守式 GC 可以使用复制算法**（以及标记-压缩等移动对象的算法）
    
- ❌ **访问对象需要两次内存访问**（根→句柄→对象），降低了对对象内部数据的访问速度，影响整个语言处理程序的速度
    

> 💡 **洞见**：间接引用是一种"**用时间换算法自由度**"的权衡。它承认"根不能改"这一保守式 GC 的硬约束，通过引入一层中间抽象（句柄）把这个约束隔离起来——根只与句柄交互（句柄地址稳定），GC 只与句柄里的指针交互（移动对象时改写这里）。这种"**引入间接层来化解约束冲突**"的思维，是计算机科学中最强大的设计范式之一（虚拟内存、句柄表、VTable、网络代理……无一不是此思想的体现）。

## 六、6.6 MostlyCopyingGC：Bartlett 的"大部分复制"算法

Joel F. Bartlett 于 1988-1989 年提出的 **MostlyCopyingGC**，是对保守式 GC 的重大突破——**它让保守式 GC 在不使用句柄的前提下，也能运行复制算法**。

### 核心思想

**抛开不能移动的对象，对大多数对象进行复制**。具体来说：把堆分成固定大小的**页（page）**，那些"被不明确的根直接指向的对象"所在的页**不移动**，其他页里的对象**全部复制**。

### 算法前提

1. 根是不明确的根
    
2. 没有不明确的数据结构（即 GC 可以明确判断对象里的域是指针还是非指针）
    
3. 对象大小任意
    
4. CPU 是 32 位（本书以 32 位为例讲解）
    

### 堆结构与执行流程

**堆被分为一定大小的页**：

- 当正在使用的页 + 准备分配的页 >= 总页数/2 时，触发 GC
    
- GC 开始时，**把所有从根引用的页标记为"晋升"（promoted）**——这些页里的对象不移动
    
- 把其他页里的活对象复制到空白页（To 页）
    
- 复制完成后，把 current_space 的值设定为 next_space 的值
    

**Cornell 的资料给出了更精确的四阶段流程**：

- **Phase I**：扫描栈和静态区找根，晋升所有包含根的页，将晋升页里的对象入 Cheney 队列
    
- **Phase II**：在队列上执行复制收集，但**不更新对象内的指针**（所有对象仍指向 fromSpace）
    
- **Phase III**：重新扫描队列，将对未晋升页的指针替换为 forwarding pointer；收集晋升页的链表
    
- **Phase IV**：通过 forwarding pointer 把对象从新空间复制回晋升页，GC 完成
    

### 关键特征

- **根指向的页里的垃圾不会被回收**——因为这些页不移动，页内的垃圾只能留在原地
    
- 这个垃圾所引用的子对象群也**不会被回收**
    
- 如果所有页都含有根指向的对象，那么**所有的垃圾都无法被回收**——这是最坏情况
    

### 优点与代价

- ✅ 在保守式 GC 中实现了复制算法，**继承了复制算法的优点**（无碎片、分配快、吞吐高）
    
- ❌ **部分垃圾不被回收**——根所在页的垃圾被保留，拉低了内存使用效率
    
- ❌ 对象不是按顺序复制的，**无法利用缓存的局部性原理**
    

### 页大小的经验值

实验表明，**编码页大小为 512 字节比较合适**——页越小，根所在页的垃圾占比越小，内存效率越高；但页太小会增加页管理的开销。

> 💡 **第一性原理洞察**：MostlyCopyingGC 的精妙之处在于——**它重新定义了"保守"的边界**。传统保守式 GC 是"全盘保守"（所有对象都不移动）；Bartlett 观察到：**只有被根直接指向的对象不能移动，其他对象都可以安全移动**。通过"页"这个粒度，他把堆划分为"必须保守的区域"和"可以自由复制的区域"，从而**在保守的约束下，争取到了最大的复制空间**。
> 
> 这是一种典型的"**分而治之 + 最小化约束范围**"的工程思维——不去挑战"不能移动根指向的对象"这个硬约束，而是**精确识别约束的作用范围**（根指向的页），在约束之外的地方放手使用高效算法。这种思维在后续的 G1 GC（只压缩选定的 Region）、Shenandoah（并发压缩但用 Brooks Pointer 保证并发正确性）中都有体现。

## 七、6.7 黑名单：缓解假指针导致的泄漏

### 核心思想

Hans Boehm 发明的**黑名单法**，专门解决"指针错误识别导致垃圾被保留"的问题。

**黑名单记录的是什么？**

> "不明确的根内的非指针，其指向的是有可能被分配对象的地址"

具体来说：mutator 无法引用"至今未使用过的对象"——也就是说，**如果根内存在一个值，恰好等于堆内未使用对象的地址，那它肯定是非指针**（因为 mutator 不可能引用一个从未被分配出去的地址）。这种地址被**记入黑名单**。

### 黑名单如何发挥作用

当 GC 需要分配新对象时：

- 如果要分配到黑名单内的地址，**所分配的对象必须满足两个条件**：
    
    1. **小对象**
        
    2. **没有子对象的对象**（即叶子对象）
        
    

这样做的逻辑是：即使这个对象成了垃圾且因假指针未被回收，**它也不会拖住其他对象**（因为没有子对象），**损失被控制在最小范围内**。

### 为什么这样能缓解问题

指针错误识别的危害程度，取决于被错误保留的垃圾对象的**大小和子对象数量**：

- **大小**：有个巨大的对象死掉了，却被错误识别为"还活着" → 严重压迫堆
    
- **数量**：错误识别会引发连锁反应——子对象的子对象、子对象的子对象的子对象……错误像多米诺骨牌一样连续下去
    

黑名单通过将"可能被假指针误伤的地址"分配给"小且无子对象"的对象，**切断了错误识别的连锁反应**，将损失隔离在最小范围。

### 优点与代价

- ✅ 缓解保守式 GC 因错误识别对象而压迫堆的问题，**提升堆的使用效率**
    
- ❌ 需要花费时间检查黑名单
    

> 💡 **洞见**：黑名单法体现了 GC 设计中的另一种重要思维——**"风险隔离"**。它承认假指针不可避免，但通过在分配环节做文章，**把假指针可能造成的损害控制在最小范围内**。这与网络安全中的"零信任架构"、金融系统中的"限额风控"是同一类思维：**既然无法完全消除风险，就让风险的爆炸半径最小化**。
> 
> 更深远的意义：黑名单法是**"分配器与收集器协同设计"**的早期范例。它打破了"GC 只负责回收、分配器只负责分配"的传统分工，让分配器在分配时就考虑 GC 的回收效率。这种协同设计思想，在现代 GC 中反复出现：G1 的 Region 设计让分配与回收协同、ZGC 的染色指针让分配与并发回收协同。

## 八、章节脉络：保守式 GC 的"约束与突围"

```
保守式 GC（核心约束：不敢改写疑似指针）
│
├─ 6.1 定义：不明确的根 + 三重过滤（对齐/堆范围/对象头）
│   └─ 本质：风险不对称下的理性选择（宁错留，不误收）
│
├─ 6.2 优点：语言处理程序与 GC 解耦
│   └─ 工业锚点：Boehm GC 可作为 C/C++ 独立库
│
├─ 6.3 缺点：保守的代价
│   ├─ 指针识别成本
│   ├─ 假指针导致内存泄漏
│   └─ 不能用复制/压缩等移动对象的算法 ← 根本约束
│
├─ 6.4 准确式 GC：对立面
│   └─ 编译器配合生成栈图/类型元数据
│       └─ 解锁移动式回收（HotSpot/Go/CoreCLR）
│
└─ 6.5~6.7 在保守式约束下的三种突围路径
    ├─ 6.5 间接引用：引入句柄层隔离约束
    │   └─ 代价：二次内存访问，性能下降
    │
    ├─ 6.6 MostlyCopyingGC：精确识别约束作用范围
    │   └─ 根指向的页不移动，其他页复制
    │   └─ 代价：根所在页的垃圾不被回收
    │
    └─ 6.7 黑名单：风险隔离
        └─ 假指针易伤的地址只分配小且无子对象的对象
        └─ 代价：分配时需查黑名单
```

**更深层的洞见**：这三种改进路径，展现了面对"硬约束"时的三种典型工程思维：

1. **间接引用——加层隔离**：不改变约束本身，而是在约束外层包一层抽象，让约束的作用范围被隔离。这是"解耦"思维。
    
2. **MostlyCopyingGC——精确识别约束边界**：不盲目保守，而是精确分析"约束到底作用在哪些对象上"，在约束之外大胆使用高效算法。这是"精细化"思维。
    
3. **黑名单——风险隔离**：承认约束带来的风险无法消除，但通过分配策略让风险的爆炸半径最小化。这是"风控"思维。
    

**这三种思维并非互斥，工业级保守式 GC 往往三者并用**：Boehm GC 既使用黑名单技术避免假指针热点，也在特定场景下支持 MostlyCopying 的思路；而间接引用则在需要兼容复制算法的保守式环境中使用。

## 九、工业实践印证

### 1. Boehm GC：保守式 GC 的工业标杆

Hans Boehm 的 BDW GC 是保守式 GC 最成功的工业实现：

- **采用 mark-sweep 算法**，从不移动对象
    
- 支持增量式 GC（但不是硬实时）
    
- 支持分代 GC（但对象不移动）
    
- 支持多线程和多处理器
    
- 被 gcj、Mono、Bigloo Scheme、MzScheme、D 语言运行时、w3m 等采用
    
- 最新稳定版本 8.2.10（2025年10月）
    

### 2. Unity 的 Boehm GC：保守式的现实困境

Unity 引擎长期采用 Boehm GC 作为托管堆的收集器，这给了我们看到保守式 GC 缺点的绝佳窗口：

> "Unity 目前使用的是 Boehm GC，这是一种保守的、不移动的 GC。它会扫描所有线程栈（包括托管代码和本地代码），寻找要收集的托管对象，一旦分配了托管对象，该对象在内存中的位置就永远不会移动。"

**Boehm GC 在 Unity 中的具体问题**：

|问题|表现|
|---|---|
|**False Retention**​|string/byte[] 内容区被当作潜在指针扫描，二进制数据恰好"像指针"就会被误判为存活|
|**堆碎片**​|不移动对象 → 释放后留下空洞 → 新分配必须找合适大小的空洞填充|
|**线性扫描成本**​|整个堆作为单一代际，每次 GC 成本 ∝ 堆大小，100MB 活对象即使只回收 1KB 也要扫 100MB|
|**页永不归还 OS**​|一旦向 OS 申请了某块内存页，除非整个页内所有对象都被回收，否则该页永远不会归还|

### 3. Unity 向 CoreCLR 迁移：从保守式走向准确式

Unity 官方博客明确宣布正在将运行时迁移到 .NET 的 CoreCLR GC：

> "Unity 目前使用的是 Boehm GC，这是一种保守的、不移动的 GC。…… .NET 使用 CoreCLR GC，它是一种精确的移动 GC。它仅在托管代码中跟踪已分配的对象，并在内存中移动这些对象以提高性能。"

这个迁移决策，恰恰是本章理论的最佳工业印证：

- **保守式 GC**：语言运行时与 GC 解耦，但牺牲移动式回收 → 碎片、假指针泄漏
    
- **准确式 GC**：需要编译器/运行时深度配合，但解锁移动式回收 → 无碎片、高效压缩
    

Unity 选择 CoreCLR，意味着它**愿意支付"运行时与 GC 深度协同"的复杂度代价，换取"移动式回收"带来的性能提升**。这印证了我们在 6.4 节的分析：**准确式 GC 是"编译器与运行时深度协同"的体现，而精确，是这一切优化得以安全进行的前提**。

### 4. 精确式 GC 的工业现状

现代主流语言运行时都已转向准确式 GC：

- **HotSpot JVM**：通过 OopMap 实现精确式 GC，解锁分代、复制、压缩等所有算法
    
- **Go**：编译器生成栈图，准确式 GC，支持栈移动
    
- **CoreCLR (.NET)**：精确式移动 GC，正在被 Unity 采纳
    
- **Mono**：原用 Boehm GC，后引入 SGen（分代精确式 GC）作为替代
    

> 💡 **工程启示**：保守式 GC 在今天的地位，已经从"主流方案"退居为"兼容方案"——它主要用于**必须兼容 C/C++ 原生代码、无法要求编译器配合**的场景。在新的语言运行时设计中，准确式 GC 已经是事实标准。但 Boehm GC 的价值依然不可替代：它为 C/C++ 生态提供了"自动内存管理"的可能，是连接"手动管理世界"与"自动管理世界"的桥梁。

## 十、承上启下：保守式 GC 在全书算法篇的位置

至此，我们已经学完了五种基本 GC 算法/范式：

|范式|指针识别|能否移动对象|工业代表|
|---|---|---|---|
|标记-清除|准确式|否|Boehm GC|
|引用计数|准确式|否|CPython|
|复制算法|准确式|是|JVM 新生代|
|标记-压缩|准确式|是|JVM 老年代|
|**保守式 GC**​|**保守式**​|**否**​|**Boehm GC (C/C++)**​|

**关键洞察**：保守式 GC 不是"第六种算法"，而是**对所有前四种算法的"约束层"**——它定义了一个根本性的边界：

> **指针识别精度决定了 GC 算法的可行域**
> 
> - 保守式 → 只能用"不移动对象"的算法（标记-清除、引用计数）
>     
> - 准确式 → 解锁"移动对象"的算法（复制、压缩、分代复制）
>     

这就是为什么本书把保守式 GC 放在"算法篇"与"进阶算法篇"之间——它是**连接"基础算法"与"高级调度"的关键认知节点**。理解了保守式 GC 的约束，你才能真正理解：

- 为什么 JVM/Go/.NET 都选择准确式 GC（为了解锁移动式回收）
    
- 为什么分代、并发、增量这些"高级算法"都**隐含要求准确式 GC**
    
- 为什么 C/C++ 生态的 GC 化如此困难（保守式是唯一选择，而保守式封杀了最高效的算法）
    

下一章（第7章）开始，本书将进入"**分代垃圾回收**"——这是现代 GC 的基石架构。而分代 GC 有一个隐含前提：**必须是准确式 GC**。因为只有准确式 GC 才能安全移动对象，才能在对象在代际间移动时正确更新所有引用。

**带着"保守式 vs 准确式"这个根本范式对立进入下一章**，你会清晰地看到：分代 GC、增量 GC、并发 GC 这些"高级算法"，本质上都是**在准确式 GC 的基础上**，通过更精巧的调度策略，把"不可能五边形"（吞吐、停顿、空间、碎片、实现复杂度）推向更优的平衡点。而保守式 GC 因其根本约束，被永远挡在了这些高级算法的大门之外——这正是 Unity 不惜代价迁移到 CoreCLR 的根本原因。

---

📌 **本章核心收获**：

- 保守式 GC 的本质是"风险不对称下的理性选择"——宁错留，不误收
    
- 三重过滤（对齐+堆范围+对象头）是疑似指针的判定标准
    
- 保守式 GC 的根本约束：**不敢移动对象**​ → 只能用标记-清除类算法 → 无法避免碎片
    
- 准确式 GC 通过编译器配合（栈图+类型元数据）解锁移动式回收，是现代语言运行时的主流选择
    
- 三种突围路径展现了三种工程思维：间接引用（加层隔离）、MostlyCopyingGC（精确识别约束边界）、黑名单（风险隔离）
    
- 工业印证：Boehm GC 是 C/C++ 保守式 GC 的标杆；Unity 正从 Boehm 迁移到 CoreCLR，正是从保守式走向准确式的产业缩影
    
- **指针识别精度 → 反向决定 GC 算法可行域**：这是贯穿现代 GC 设计的根本法则，是进入下一章"分代 GC"的认知前提
