
# 《垃圾回收的算法与实现》读书笔记 · 第12章 Rubinius 的垃圾回收

> 延续前十章建立的"第一性原理"视角：第4章复制算法告诉我们"对象移动"能换来无碎片和快分配，但代价是堆利用率 50%；第5章标记-压缩告诉我们"原地压缩"能兼顾高堆利用率和无碎片，但代价是压缩成本高；第6章保守式 GC 告诉我们"不能精确识别指针"就只能保守处理，封杀了移动式回收；第7章分代 GC 告诉我们"按年龄分区"能让复制算法和标记-清除/压缩各司其职；第8章增量式 GC 告诉我们"写屏障"是 GC 与 mutator 并发执行的交钥。Rubinius 作为 Ruby 的高性能 VM 实现，把这些理论**熔接成了一套"准确式 + 分代 + 复制 + Immix 标记-区域 + 写屏障"的精密 GC 体系**——它是本书算法篇理论在工业界最完整的"集大成式"落地之一。

## 一、12.1 本章前言：Rubinius 的工程目标

Rubinius 是一个用 C++ 实现 VM、大量核心库用 Ruby 自身编写的 Ruby 实现，其设计哲学是"**If it can be done in Ruby, then it shouldn't be in C**" 。它在 GC 上的核心目标是 ：

- **分代（Generational）**：年轻对象用复制算法，成熟对象用标记-清除/Immix
    
- **压缩（Compacting）**：避免碎片，提升缓存局部性
    
- **并发（Concurrent）**：GC 与 mutator 并行执行
    
- **准确式（Exact/Precise）**：能精确区分指针与非指针——这是这一切的前提
    

> 💡 **第一性原理洞察**：Rubinius 的 GC 设计，本质上是把前几章我们学过的所有算法，在"准确式 GC"这个前提下做了一个**全景式编排**：
> 
> - 准确式（第6章）→ 解锁对象移动
>     
> - 分代（第7章）→ 新生代用复制、老年代用标记-区域
>     
> - 复制算法（第4章）→ 新生代 Baker 两空间复制
>     
> - Immix 标记-区域（第5章）→ 老年代压缩与回收
>     
> - 写屏障（第7/8章）→ 维护跨代引用、支持并发
>     
> 
> 这不是"选择一种算法"，而是"**让每种算法在最擅长的维度上工作**"。Rubinius 的 GC 是本书算法篇理论工业化的**范本级案例**。

## 二、12.2 Rubinius 的 GC 算法：分代 + 复制 + Immix 的三重奏

Rubinius 的 GC 架构经历了演进，但核心思想一脉相承 ：

### 早期架构（"The Reaper"时期）

```
┌──────────────────────────────────────────────┐
│ 年轻代 (Young/Nursery)：Baker 两空间复制算法    │
│  └─ 新对象分配于此，存活一定次数后晋升          │
├──────────────────────────────────────────────┤
│ 成熟代 (Mature/Old)：Mark-Sweep 或 Immix      │
│  └─ 晋升来的长寿命对象                          │
└──────────────────────────────────────────────┘
```

- **年轻代**：Baker 两空间压缩复制收集器（Baker's two-space compacting collector）
    
- **成熟代**：标记-清除收集器（Mark/Sweep collector）
    
- **跨代引用**：所有 VM 中的对象访问都通过**写屏障**，维护"引用了年轻对象的成熟对象集合"
    

### 后期架构（Immix 统一时期）

Rubinius 后期将老年代也演进为 **Immix 标记-区域算法**​ ：

```
┌──────────────────────────────────────────────┐
│ 年轻代：Baker 两空间复制算法                    │
├──────────────────────────────────────────────┤
│ 老年代：Immix 标记-区域算法                     │
│  └─ Block (32KB) → Line (128B) 层级组织         │
│  └─ 标记阶段 + 区域回收（疏散）                  │
└──────────────────────────────────────────────┘
```

Rubinius 的 Immix 实现位于 `machine/memory/immix.hpp` 和 `machine/memory/immix.cpp` 中 ：

- **Block 大小**：32KB
    
- **Line 大小**：128 字节
    
- **每块 Line 数**：256 行
    
- **Block 状态**：`cFree`（完全空闲）/ `cRecyclable`（使用中但有空闲行）/ `cUnavailable`（完全使用）/ `cEvacuate`（碎片化，适合疏散）
    

> 💡 **洞见**：Rubinius 从"年轻代复制 + 成熟代标记-清除"演进到"年轻代复制 + 老年代 Immix"，是本书第5章 Immix 算法工业价值的直接印证。Immix 的"标记-区域"混合特性，使其**在老年代这种"存活率高、不适合纯复制"的场景下，依然能通过"区域级疏散"实现压缩**——这恰好填补了"复制算法不适合老年代"的空白。

## 三、12.3 对象管理：三种堆的精细划分

Rubinius 最具创新性的设计，是把堆划分为三种逻辑堆 ：

|堆类型|引用规则|用途|
|---|---|---|
|**开放堆（Open Heap）**​|任何对象可以引用任何其他对象|类似正常的 Ruby 环境|
|**封闭堆（Closed Heap）**​|堆内对象可以引用外部对象，但外部不能引用堆内对象|提供部分隔离|
|**隔离堆（Isolated Heap）**​|完全隔离，内外互不引用|线程可以独立执行，GC 可并行|

### 隔离堆的革命性意义

隔离堆的设计让 Rubinius 实现了**真正的并行 GC**​ ：

> "Threads that use isolated heaps can execute fully independent of any other thread and only must synchronize with the process during boot, fork, and halt. The garbage collector for isolated heaps is run in that thread."

也就是说，每个隔离堆拥有自己独立的 GC 线程，**不需要全局 STW**——这直接打破了传统 GC "全局暂停"的魔咒 。

### 对象管理的工业细节

Rubinius 管理两类对象 ：

- **面向对象对象**：支持继承，有完整的对象语义
    
- **数据对象**：无面向对象概念，轻量级
    

新对象分配采用 **Bump-Pointer 分配**（指针碰撞） ：

- 维护一个指向"下次分配位置"的指针
    
- 分配时只需移动指针，O(1) 时间
    
- 对象大小可以不一致，相邻分配
    
- **优势**：分配极快、缓存局部性好（related values 在内存中相邻）
    

> 💡 **第一性原理洞察**：Rubinius 的"三种堆"设计，是 GC 理论中"分而治之"思想的极致体现。它不仅按"对象年龄"分区（分代），还按"对象引用关系"分区（开放/封闭/隔离）。**隔离堆的设计尤其精妙**——它让 GC 从"全局 STW"走向"局部并行"，是本书第8章"增量/并发 GC"思想在架构层面的升华。每个隔离堆的 GC 在自己的线程上独立运行，不需要全局暂停——这是真正意义上的"并发 GC"。

## 四、12.4 走向准确式 GC 之路：Rubinius 的根本转型

这是本章最深刻的一节。Rubinius 从 MRI（Matz Ruby Interpreter）继承而来，但 MRI 的 GC 是**保守式、非压缩、Stop-The-World 的标记-清除**​ ：

> "Ruby has had a GC since the start; it's a conservative stop-the-world all-or-nothing non-compacting mark-and-sweep garbage collector."

MRI 保守式 GC 的问题（第6章已详述）：

- 不能移动对象 → 碎片严重
    
- 假指针导致内存泄漏
    
- 必须 STW 扫描整个堆
    

### Rubinius 的准确式转型

Rubinius 选择了一条根本不同的路——**准确式 GC**​ ：

> "Rubinius has a precise GC, and so doesn't suffer from this problem, which can lead to dead objects never being collected."

准确式 GC 让 Rubinius 解锁了三大能力 ：

1. **对象可移动**​ → 压缩、复制成为可能
    
2. **无假指针**​ → 回收更彻底，无内存泄漏
    
3. **支持分代**​ → 年轻代复制 + 老年代压缩
    

### 准确式 GC 的工程实现

Rubinius 的准确式 GC 通过 LLVM JIT 编译时插入元数据实现 ：

```
// 写屏障的 LLVM IR 插入（JIT 编译时）
void write_barrier(Value* obj, Value* val) {
    Value* is_ref = check_is_reference(val);
    BasicBlock* cont = new_block("reference_obj");
    BasicBlock* run_barrier = new_block("run_barrier");
    BasicBlock* done = new_block("done");
    
    create_conditional_branch(cont, done, is_ref);
    set_block(cont);
    // 快速路径：检查是否需要写屏障
    // 慢速路径：调用运行时写屏障
    // ...
}
```

**写屏障的触发时机**：当写入一个"年轻对象引用"到"成熟对象"时，需要通过写屏障将该成熟对象记录到"引用年轻对象的成熟对象集合"中 。

> 💡 **洞见**：Rubinius 的"走向准确式 GC 之路"，本质上是本书第6章理论的工业兑现——**准确式 GC 是"精确，是这一切优化得以安全进行的前提"**。Rubinius 通过 LLVM JIT 在编译期生成栈图和类型元数据，让运行时能够精确区分指针与非指针。这一转型解锁了：
> 
> - 对象移动（压缩、复制）
>     
> - 分代 GC（需要写屏障维护记忆集）
>     
> - 并发 GC（需要精确知道引用位置）
>     
> 
> 没有准确式 GC，Rubinius 就不可能有今天的分代 + 复制 + Immix + 并发架构。这正是第6章"保守式 vs 准确式"对立在 Ruby 运行时演进中的直接映射——Rubinius 选择了准确式，MRI 后期（2.1+）也开始引入分代 GC，印证了"准确式是高级 GC 的前提"这一规律。

## 五、12.5 GC 复制算法：年轻代的 Baker 两空间复制

Rubinius 年轻代采用 **Baker 的复制算法**（1978 年 Baker 在 Minsky 1963 年复制算法基础上的改进） ：

### 半空间算法（Semi-Space）

```
From-Space                      To-Space
[对象A][对象B][对象C][...]      [初始为空]
```

当 From-Space 填满时：

1. 从 GC Roots 出发，遍历对象图
    
2. 将所有存活对象复制到 To-Space
    
3. 复制过程中，From-Space 中的对象头写入 forwarding pointer
    
4. 复制完成后，From-Space 和 To-Space 角色互换
    
5. To-Space 成为新的 From-Space，通过 bump-pointer 分配新对象
    

### Rubinius 的 Eden Heap 变体

Rubinius 和 JVM 一样，使用了半空间算法的一种变体——引入第三个堆"Eden" ：

```
┌─────────────────────────────────────────┐
│ Eden Heap（新对象分配区）                  │
├──────────────────┬──────────────────────┤
│ From-Space       │ To-Space             │
└──────────────────┴──────────────────────┘
```

- 新对象在 Eden 中分配
    
- Eden 满时，存活对象复制到 From-Space
    
- 后续 GC 在 From-Space 和 To-Space 之间复制
    
- 存活一定次数的对象晋升到老年代
    

### Baker 复制算法的工业优势

|优势|机制|
|---|---|
|**分配极快**​|Bump-pointer，O(1)|
|**无碎片**​|存活对象紧凑排列|
|**缓存友好**​|Related objects 在内存中相邻|
|**只复制存活对象**​|成本低，与存活集大小成正比|

> 💡 **洞见**：Rubinius 年轻代选择 Baker 复制算法，与 JVM 新生代选择复制算法，是同一个第一性原理的工业印证——**弱分代假说下，年轻代存活率极低（~2%），复制算法"只处理活对象"的特性使其效率极高**。Rubinius 通过 auto-tuned lifetime 机制动态调整对象晋升阈值 ，让复制算法在"对象朝生夕灭"的 Ruby workload 下发挥最大效能。

## 六、12.6 Q&A：Rubinius GC 的工程权衡

### Q1：为什么 Rubinius 的成熟代从 Mark-Sweep 演进到 Immix？

**A**：Mark-Sweep 不压缩 → 碎片严重 → 长期运行的 Ruby 应用（如 Rails 服务器）内存碎片累积 → 性能下降。Immix 的"标记-区域"混合特性，在老年代高存活率的场景下，仍能通过"区域级疏散"实现压缩，彻底解决碎片问题 。

### Q2：Rubinius 的 GC 目前是并发的吗？

**A**：**部分并发**。根据最新 Rubinius 架构 ：

- 当前实现：单线程 GC，必须 STW 同步所有 mutator 线程
    
- 未来方向：隔离堆将提供并行收集（每个隔离堆独立 GC）
    
- 写屏障已经就位，为并发 GC 奠定了基础
    

### Q3：Rubinius 相比 MRI 的 GC 优势在哪？

|维度|MRI（2.0 及以前）|Rubinius|
|---|---|---|
|GC 类型|保守式标记-清除|准确式分代|
|压缩|否|是（年轻代复制 + 老年代 Immix）|
|分代|2.1+ 才开始引入|原生支持|
|并发|否|写屏障就位，隔离堆可并行|
|碎片|严重|无（压缩）|
|Fork 友好|否（对象被标记位修改）|是（对象本身不被标记）|

> 💡 **关键洞察**：Rubinius 的"对象本身不被标记"设计（标记位存在外部位图），使其**非常 fork 友好**​ ——在 fork() 场景下，父子进程可以共享内存页，直到某一方向写入才触发 CoW。这是本书第2章"位图标记"思想的工业兑现。

### Q4：Rubinius 的写屏障如何实现？

**A**：Rubinius 的写屏障在 LLVM JIT 编译时插入 ：

- **快速路径**：检查是否需要写屏障（如：obj 是否是成熟对象且 val 是否是年轻对象）
    
- **慢速路径**：如果需要，调用运行时写屏障，将该成熟对象记录到"引用年轻对象的成熟对象集合"
    
- **跨代引用追踪**：GC 时，除了从 Roots 扫描，还要扫描这个集合中的成熟对象，以发现被成熟对象引用的年轻对象
    

这正是本书第7章"写屏障 + 记忆集"理论的工业落地。

## 八、工业实践印证与深度洞察

### 1. Rubinius vs MRI vs JRuby 的 GC 横向对比

|运行时|GC 类型|压缩|分代|并发|准确式|
|---|---|---|---|---|---|
|**MRI（传统）**​|标记-清除|否|否（2.1+ 部分引入）|否|否（保守式）|
|**MRI（2.1+）**​|标记-清除 + 分代|否|是（部分）|否|否（保守式）|
|**Rubinius**​|年轻代复制 + 老年代 Immix|是|是|写屏障就位，隔离堆可并行|是|
|**JRuby**​|JVM GC（G1/ZGC 等）|是|是|是|是|

**核心观察**：

- **MRI**​ 长期受保守式 GC 困扰——不能移动对象导致碎片严重，假指针导致内存泄漏
    
- **Rubinius**​ 通过准确式转型，一举解锁了压缩、分代、并发 — 这是 Ruby 运行时演进的关键转折
    
- **JRuby**​ 直接利用 JVM 成熟的 GC 体系，是"站在巨人肩膀上"的另一种路径
    

### 2. Rubinius 的 Immix 性能数据

学术论文指出，Immix 相比许多其他算法能**提升总应用性能 7%~25%**​ ——这正是 Rubinius 选择 Immix 作为老年代算法的根本原因。

Rubinius 的 Immix 实现进一步优化 ：

- **分代收集支持**：年轻代对象在 Immix 区域中分配，多次 GC 存活后晋升
    
- **并行收集**：利用多线程并行执行标记和回收
    
- **增量标记**：将标记工作分摊到多个时间片
    
- **写屏障优化**：高效跟踪跨代引用
    

### 3. Rubinius 的"fork 友好"特性

> "Objects themselves are not marked, making rubinius very 'fork friendly'."

Rubinius 的标记位存储在外部位图中，对象本身不被修改 ——这意味着：

- 在 Linux `fork()` 场景下，父子进程可以共享内存页
    
- 只有某一方向真正写入对象数据时，才触发 Copy-on-Write
    
- 避免了"标记位修改导致整个页面复制"的无谓开销
    

这是本书第2章"位图标记"思想（修补标记-清除与 COW 不兼容）的工业兑现 ，也是 Rubinius 在 Web 服务器场景（prefork 模型）下的关键优势。

### 4. Rubinius 的演进方向与本书理论的前沿呼应

根据最新 Rubinius 架构 ：

- **当前**：单线程 GC，STW
    
- **未来**：
    
    - 开放堆引入第二分代区
        
    - 隔离堆提供并行收集
        
    - 整体向"真正并发 GC"演进
        
    

这一演进路径，与本书第8章（增量式 GC）、第9章（RC Immix）的前沿方向完全一致——**GC 的未来在于"精确 + 分代 + 复制/压缩 + 并发"的四位一体**。Rubinius 已经在准确式、分代、复制、Immix 压缩四个方面做好了准备，只待在工程上完成"真正并发"的最后一步。

### 5. 与 Python / Dalvik VM 的对照

|维度|CPython|Dalvik VM|Rubinius|
|---|---|---|---|
|**主力算法**​|引用计数|标记-清除|分代：复制 + Immix|
|**准确式**​|是（但引用计数是对象级）|是|是|
|**压缩**​|否（但有循环 GC）|否|是（年轻代复制 + 老年代 Immix）|
|**分代**​|是（3代）|粗粒度（Zygote/Active）|是（年轻/老年）|
|**并发**​|增量（3.14+）|标记/清除并发|写屏障就位，隔离堆可并行|
|**写屏障**​|引用计数增减|Card Table 写屏障|跨代写屏障|
|**工程约束**​|动态语言语义|嵌入式设备|高性能 Ruby 运行时|

**核心观察**：

- **Python**​ 因动态语言语义选择引用计数为主力，无法完全享受移动式回收的红利
    
- **Dalvik VM**​ 因嵌入式约束选择标记-清除，不压缩
    
- **Rubinius**​ 因追求高性能，选择了"复制 + Immix"的移动式回收组合——这是现代 GC 的"黄金三角"范式
    

Rubinius 的 GC 设计，代表了本书算法篇理论在工业界**最完整的落地**——它几乎动用了前十章的所有核心理论，并且熔接成一个 coherent 的系统。

## 九、承上启下：Rubinius GC 在全书"实现篇"的位置

至此，我们分析了三个工业案例：

|案例|主力算法|核心特征|工程约束|
|---|---|---|---|
|**第10章 Python**​|引用计数 + 分代循环 GC|确定性回收|动态语言语义|
|**第11章 Dalvik VM**​|并发标记-清除|短停顿、不压缩|嵌入式设备|
|**第12章 Rubinius**​|分代：年轻代复制 + 老年代 Immix|准确式、压缩、分代|高性能 Ruby 运行时|

**关键洞察**：三个案例展示了 GC 工业实现的三种不同范式：

- **Python**：以"引用计数"为主力 → 确定性回收，但牺牲了移动式压缩
    
- **Dalvik VM**：以"标记-清除"为主力 → 短停顿，但因嵌入式约束不压缩
    
- **Rubinius**：以"复制 + Immix"为主力 → 准确式、压缩、分代、并发就绪
    

**Rubinius 代表了现代 GC 的"黄金三角"范式**——分代（第7章）+ 复制/压缩（第4/5章）+ 并发（第8章），在准确式 GC（第6章）的前提下熔接而成。它是本书算法篇理论在工业界**最完整的"集大成式"落地**。

**带着这个视角进入下一章（第13章 V8 的 GC）**，你会看到：V8 作为 JavaScript 引擎，同样选择了"分代 + 复制 + 标记-压缩 + 并发"的黄金三角范式——但 V8 面对的是不同的工程约束（前端/Node.js、JIT 编译、大对象处理），因此演化出了独特的"Scavenge + Mark-Sweep-Compact + Incremental + Concurrent"架构。**Rubinius 与 V8 的对照，将揭示"同样的 GC 理论范式，在不同的工程约束下如何演化出不同的工业形态"**——这正是本书"实现篇"想要传达的核心讯息。

📌 **本章核心收获**：

- Rubinius GC = **准确式 + 分代 + 年轻代复制(Baker) + 老年代 Immix + 写屏障**，是本书算法篇理论最完整的工业落地
    
- **准确式转型**是 Rubinius 的根本转折点（12.4）：从 MRI 的保守式 → Rubinius 的准确式，解锁了对象移动、分代、并发
    
- **三种堆**的创新设计（12.3）：开放堆 + 封闭堆 + 隔离堆 → 隔离堆实现真正的并行 GC，是并发 GC 在架构层面的升华
    
- **年轻代 Baker 复制算法**（12.5）：Semi-Space + Eden Heap 变体，Bump-Pointer 分配，auto-tuned 晋升阈值——弱分代假说的工业印证
    
- **老年代 Immix 标记-区域**：Block (32KB) + Line (128B) 层级，标记阶段 + 区域疏散，按需压缩——解决老年代高存活率场景下的碎片问题
    
- **写屏障**：LLVM JIT 编译时插入，维护跨代引用集合，为并发 GC 奠定基础
    
- **fork 友好**：标记位存储在外部位图，对象本身不被修改——第2章"位图标记"思想的工业兑现
    
- **性能数据**：Immix 相比其他算法提升总应用性能 7%~25%
    
- **与 Python/Dalvik VM 的对照**：Python 因动态语义选引用计数、Dalvik 因嵌入式约束选标记-清除、Rubinius 因高性能追求选"复制 + Immix"——三种范式各有其工程合理性
    
- **Rubinius 代表了现代 GC 的"黄金三角"范式**：分代 + 复制/压缩 + 并发，在准确式 GC 前提下熔接——这是本书算法篇理论的集大成式落地
    
- **未来演进**：单线程 STW → 隔离堆并行收集 → 真正并发 GC，与本书第8/9章前沿方向一致
