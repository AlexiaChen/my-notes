
# 《垃圾回收的算法与实现》读书笔记 · 第5章 GC 标记-压缩算法

> 延续前四章建立的"第一性原理"视角：标记-清除选择"就地回收、不移动对象"——换来了兼容性，但留下了碎片；复制算法选择"搬迁活对象"——换来了无碎片和快分配，但堆利用率只剩 50%。**标记-压缩算法走的是第三条路：先做可达性标记（继承标记-清除的"集中式判定"），再把活对象紧凑地移到堆的一端（继承复制算法的"对象移动"）**。它试图同时拿到两边的红利——既不像标记-清除那样留下碎片，也不像复制算法那样浪费一半堆空间。

---

## 一、5.1 什么是 GC 标记-压缩算法：两阶段、三遍扫描

### 核心思想

标记-压缩由 **Lisp2 算法**（也叫"标准标记-压缩"）为代表，包含两个阶段：

1. **标记阶段**：与标记-清除完全相同——从 GC Roots 出发，给所有可达对象打上 mark 位
    
2. **压缩阶段**：把活对象紧凑地移到堆的一端，消除中间的空隙
    

Lisp2 的压缩阶段需要**对整个堆进行 3 次搜索**：

|遍数|操作|目的|
|---|---|---|
|第1遍|设定 forwarding 指针|计算每个活对象压缩后的新地址，写在对象头的 forwarding 字段里|
|第2遍|更新指针|遍历所有对象，把指向旧地址的引用改写成 forwarding 指向的新地址|
|第3遍|移动对象|按 forwarding 指针把活对象搬到新地址|

### 与复制算法的本质区别

复制算法是"边遍历边复制"——`From` 空间的活对象复制到 `To` 空间，复制完 `From` 整体废弃。标记-压缩是"先算好新地址、再更新所有引用、最后才移动"——**所有动作都在同一个堆空间内完成**，不需要预留一个等大的 `To` 空间。

> 💡 **第一性原理洞察**：标记-压缩的本质，是把"垃圾回收"问题重新定义为"内存压实"问题。**它不回避对象移动，但拒绝为移动付出'半个堆闲置'的代价**。代价是什么呢？是压缩阶段必须 3 次扫描堆——计算新地址、更新引用、物理移动，每一步都要遍历。这就是为什么标记-压缩的**吞吐量低于复制算法，但堆利用率高于复制算法**。它是标记-清除和复制算法之间的"中间态"——用更高的计算成本，换来了"既无碎片、又不浪费空间"的双重收益。

---

## 二、5.2 优点：双重红利

|优点|深层机制|
|---|---|
|**有效利用堆，无碎片化**​|活对象被紧凑排列到堆的一端，彻底消除外部碎片；堆利用率接近 100%|
|**分配速度快**​|压缩后活对象连续排列，分配可用 bump-pointer，O(1)|
|**兼容保守式 GC**​|与标记-清除一样不预留 `To` 空间，但对象会被移动——这点与复制算法不同，需要 mutator 配合更新所有引用|
|**适合老年代**​|老年代对象存活率高，复制算法要复制几乎所有对象（成本高），标记-清除会留下碎片；标记-压缩在"高存活率"场景下是最优解|

> 💡 **工程洞见**：标记-压缩的"无碎片 + 高堆利用率"组合，使它成为**老年代回收的事实标准**。JVM 的 Serial Old、Parallel Old 收集器都采用标记-整理作为老年代算法；G1 的老年代回收、CMS 在碎片达到阈值时的"退化整理"阶段，本质也都是标记-压缩。

---

## 三、5.3 缺点：压缩的计算成本

标记-压缩最大的痛点是**压缩阶段必须 3 次扫描整个堆**：

- **吞吐量低于复制算法**：复制算法在遍历活对象的同时就完成了复制，相当于"遍历 + 移动"合一；而标记-压缩必须"遍历算地址 → 遍历更新指针 → 遍历移动对象"，三步割裂
    
- **停顿时间长**：压缩阶段必须 STW，堆越大停顿越长。在 TB 级堆上，一次 Full GC 的压缩可能导致**秒级甚至十秒级停顿**
    
- **对象移动必须更新所有引用**：不像复制算法有独立的 `To` 空间可以"一次性切换"，标记-压缩必须在同一空间内原地更新所有指向被移动对象的指针
    

> ⚠️ **核心洞见**：标记-压缩的根本矛盾是——**它想要"复制算法的无碎片"和"标记-清除的高堆利用率"，但两个优点背后的动作（移动对象、原地更新引用）都必须做，且无法合并**。这就是 Lisp2 算法需要 3 次扫描堆的根本原因。后续 5.4~5.6 的所有改进，本质上都是在"减少扫描次数"或"降低压缩频率"这两个方向上做文章。

## 四、5.4 Two-Finger 算法：把 3 次扫描降到 2 次

Robert A. Saunders 提出的 **Two-Finger（双指针）算法**，是标记-压缩家族中最经典的改进。

### 核心思想

**free 指针从堆头向堆尾搜索空闲空间，live 指针从堆尾向堆头搜索活对象**，两指针像两只手指一样相向移动：

```
初始状态：
[堆头] ... 活 垃 活 活 垃 活 活 ... [堆尾]
        ↑free                ↑live

第一次交换：
[堆头] ... 活 活 活 活 垃 活 活 ... [堆尾]
            ↑free            ↑live

两指针交叉 → 移动结束
```

**关键技巧**：活对象被复制到空闲空间后，**在原位置（即 live 指针原来指向的对象里）写入 forwarding 指针**——因为该对象马上要被覆盖，它的域空间可以借用。这样就不需要像 Lisp2 那样给每个对象头预留一个 forwarding 字段。

### 两步操作

1. **移动对象**：free 和 live 双指针相向搜索，把 live 指向的活对象复制到 free 指向的空闲位置，在 live 原处写 forwarding
    
2. **更新指针**：遍历堆，如果某指针指向的地址 > free 指针当前位置（说明该对象已被移动），则把指针更新为 forwarding 指向的新地址
    

### 优点与代价

- ✅ **只需 2 次扫描堆**（Lisp2 需要 3 次），吞吐量更高
    
- ✅ **不需要额外的 forwarding 空间**，内存使用效率更高
    
- ❌ **必须要求所有对象大小一致**——这是 Two-Finger 最大的制约
    
- ❌ **对象顺序被打乱**——压缩后堆中对象的排列顺序与压缩前完全不同，无法利用缓存局部性
    

> 💡 **洞见**：Two-Finger 的"对象大小必须一致"限制看似苛刻，但**上一章我们学过的 BiBOP 法（把堆按对象大小分块）恰好能与之配合**——在每个 BiBOP 块内，所有对象大小相同，可以独立应用 Two-Finger 算法。这体现了本书算法之间的"组合性"：单个算法有缺陷，但算法 A 的缺陷可以被算法 B 弥补，组合后形成实用方案。

### 与 Lisp2 的本质差异

Lisp2 是"先算全局新地址，再统一更新，最后移动"——三次扫描，但对象相对顺序保持不变。Two-Finger 是"边移动边记录 forwarding"——两次扫描，但对象顺序被打乱。**这是"扫描次数"与"顺序保持"之间的权衡**：Two-Finger 用"顺序打乱"换来了"少一次扫描"。

## 五、5.5 表格算法：在"扫描次数"与"顺序保持"间找平衡

B. K. Haddon 和 W. M. Waite 于 1967 年提出的**表格算法**，试图解决 Two-Finger "顺序打乱导致缓存不友好"的问题。

### 核心思想

观察到堆中**活对象经常是连续成群的**。与其逐个对象移动，不如**把连续的活对象群作为一个整体平移**——只需要记录每个对象群的"起始位置"和"向左移动的距离"，就能推算出群内每个对象的新地址。

**间隙表格（Break Table）**：按照一个个活动对象群记录下压缩所需信息的表格。

### 两步操作

1. **移动对象群 + 构建间隙表格**：free、live、scan 三个指针从左到右扫描——
    
    - free 遇到非活动对象停下
        
    - live 遇到活动对象停下
        
    - scan 遇到活动对象群的尾部停下
        
    - 此时 `live - free` = 向左移动的距离，`scan - live` = 对象群的大小
        
    - 把对象群整体左移，并在原位置记录到间隙表格
        
    
2. **更新指针**：遍历所有引用，查间隙表格，把指向移动对象的指针减去对应的左移距离
    

### 优点与代价

- ✅ **只需 2 次扫描堆**（与 Two-Finger 相同）
    
- ✅ **保持了活对象的相对顺序**——对象群内部顺序不变，可以利用缓存
    
- ❌ **维护间隙表格的代价很高**：每次移动对象群都要移动和更新表格；如果表格记录是乱序的，查找某对象的移动距离会变成 O(N)
    
- ❌ 表格本身要占用额外空间
    

> 💡 **洞见**：表格算法体现了 GC 设计中一个精妙的权衡——**"保持顺序"是有价的，但值得**。Two-Finger 用"顺序打乱"换了"少一次扫描 + 无额外空间"；表格算法用"维护间隙表格的复杂度"换回了"顺序保持 → 缓存友好"。这再次印证了本书贯穿始终的主题：**GC 算法没有"更好"，只有"在不同维度上做不同权衡"**。在工业实践中，表格算法因实现复杂、表格维护代价高，应用不如 Two-Finger 广泛，但它的"对象群整体平移"思想，在后续的 ImmixGC 中得到了继承和发展。

## 六、5.6 ImmixGC 算法：标记-压缩的现代工业化身（2008）

Stephen M. Blackburn 和 Kathryn S. McKinley 于 2008 年提出的 **ImmixGC**，是标记-压缩算法家族的集大成者，也是本章最具现代工程价值的算法。

### 核心思想：Block + Line 两级组织

把堆划分为两级结构：

```
堆
└─ Block（32KB 固定块）
   └─ Line（128B 固定线）
      └─ 对象分配在 Line 内
```

每个 Block 维护：

- **line[]**：该 Block 中的线
    
- **mark_table[]**：每条 Line 的标记状态（FREE / MARKED / ALLOCATED / CONSERVATIVE）
    
- **status**：整个 Block 的状态（FREE / RECYCLABLE / UNAVAILABLE）
    
- **hole_cnt**：Block 中连续空 Line 的个数
    

### 对象分类处理

ImmixGC 按对象大小分三类：

- **小型对象**（< 128B）：在 Line 内分配
    
- **中型对象**（128B ~ 8KB）：跨 Line 分配
    
- **大型对象**（≥ 8KB）：ImmixGC 不管理，交给下层收集器（如 Jikes RVM 的 MMTk）
    

### 分配：Bump-pointer + 孔（Hole）复用

使用 cursor 和 limit 两个指针指向 RECYCLABLE Block 的孔（连续空闲 Line）的开头和结尾，采用类似复制算法的分配方法。当孔空间不够时，找下一个孔；Block 无孔时标记为 UNAVAILABLE，从其他 RECYCLABLE Block 寻找。

### 三步回收

1. **选定备用的 From 块**：标记阶段开始时，选定一些 Block 作为回收目标
    
2. **搜索阶段（标记）**：从根出发标记所有可达对象，被标记对象所在的 Line 标记为 MARKED
    
3. **清除阶段（压缩）**：把 RECYCLABLE Block 中未标记的 Line 清空，使 Block 重新变为有孔状态，供后续分配使用
    

### 关键创新：按需压缩

ImmixGC 最核心的思想是——**不是每次 GC 都做全堆压缩，而是只在"孔（hole）不足"时才压缩特定的 Block**。这大幅降低了压缩的频率和成本。

> 💡 **第一性原理洞察**：ImmixGC 是标记-压缩算法演化的集大成者，它把前几章几乎所有思想都融合进来：
> 
> - **Block/Line 的层级组织**​ → 类似上一章"多空间复制"和 BiBOP 的分块思想
>     
> - **Line 级别的标记-清除**​ → 第2章标记-清除的精细化版本
>     
> - **Block 级别的压缩**​ → 本章标记-压缩的按需版本
>     
> - **Bump-pointer 分配**​ → 复制算法的分配速度
>     
> - **按需压缩**​ → 类似第2章"延迟清除"的"只在必要时做昂贵操作"思想
>     
> 
> ImmixGC 的本质是：**用"分级粒度"打破"标记-压缩必须全堆扫描"的魔咒**。Line 级做轻量级标记-清除（频繁、低成本），Block 级做重量级压缩（罕见、高成本）。这种"多级粒度、按需触发"的思想，正是现代 GC（G1 的 Region、ZGC 的 Page）的核心设计哲学。

### 工业印证

ImmixGC 最初在 Jikes RVM（现在的 Jikes Research Virtual Machine）中实现，后来其思想深刻影响了：

- **G1 GC 的 Region 化设计**：把堆分成等大小 Region，年轻代用复制、老年代用标记-压缩，按需选择 Region 进行回收
    
- **Shenandoah 的 Brooks Pointer + 并发压缩**：对象移动时通过 forwarding pointer 保持并发访问的正确性
    
- **Go 1.12+ 的混合写屏障**：部分借鉴了 ImmixGC 的"保守标记"思想

## 七、章节脉络：标记-压缩的演化主线

```
Lisp2 标记-压缩（基准）
├─ 缺点：3 次扫描堆，成本高
│
├─ 5.4 Two-Finger：减少扫描次数
│   ├─ 双指针相向搜索，2 次扫描
│   ├─ 借用对象域存 forwarding，无额外空间
│   ├─ 代价：对象必须等大 + 顺序打乱（缓存不友好）
│   └─ 配合 BiBOP 可解"对象等大"限制
│
├─ 5.5 表格算法：在"扫描次数"与"顺序保持"间平衡
│   ├─ 对象群整体平移，2 次扫描
│   ├─ 间隙表格记录移动信息
│   ├─ 保持对象相对顺序 → 缓存友好
│   └─ 代价：表格维护复杂，查表 O(N)
│
└─ 5.6 ImmixGC：现代集大成者
    ├─ Block + Line 两级组织
    ├─ Line 级标记-清除（轻量、频繁）
    ├─ Block 级按需压缩（重量、罕见）
    ├─ Bump-pointer 分配
    └─ 工业影响：G1 Region 化、Shenandoah 并发压缩
```

**更深层的洞见**：标记-压缩算法的演化史，是"如何降低压缩成本"的探索史。三条路径各有侧重：

1. **Two-Finger 路径**：承认"压缩必须做"，但让压缩更高效（少扫描、零额外空间）——代价是牺牲局部性
    
2. **表格算法路径**：承认"局部性重要"，用更复杂的机制保持顺序——代价是实现复杂
    
3. **ImmixGC 路径**：**重新定义问题**——不追求"每次 GC 都压缩"，而是"按需压缩 + 多级粒度"，把标记-清除和标记-压缩组合使用
    

**这三条路径的演进，揭示了 GC 算法设计的一个深层规律：当单一算法在某个维度上遇到瓶颈时，突破的方向往往不是"把算法做得更高效"，而是"重新定义问题"——引入新的抽象层级（Block/Line）、新的触发条件（按需压缩）、新的组合方式（标记-清除 + 标记-压缩）**。ImmixGC 之所以是现代标记-压缩的巅峰，正是因为它跳出了"Lisp2 三次扫描"的框架，用全新的视角重构了问题。

## 八、工业实践印证

### JVM 老年代：标记-整理的工业主场

HotSpot JVM 的老年代回收，主流选择都是标记-整理：

|收集器|老年代算法|特点|
|---|---|---|
|**Serial Old**​|单线程标记-整理|简单、停顿长，Client 模式默认|
|**Parallel Old**​|多线程标记-整理|吞吐优先，停顿仍长|
|**CMS**​|标记-清除为主 + 碎片达阈值时退化到标记-整理|并发低延迟，但碎片积累到一定程度必须 Full GC 整理|
|**G1**​|年轻代复制 + 老年代标记-整理（按需选择 Region）|Region 化，可预测停顿|
|**ZGC / Shenandoah**​|并发标记 + 并发压缩|染色指针 / Brooks Pointer 支持并发移动|

> 💡 **工程洞见**：CMS 选择标记-清除作为老年代主力算法，是因为老年代对象存活率高、复制成本大，不如就地收集。但标记-清除的碎片问题无法回避——当碎片达到一定程度时，CMS 必须退化到一次 Full GC 的标记-整理。这恰恰印证了本章的核心论点：**标记-清除和标记-压缩不是替代关系，而是互补关系**。CMS 的日常用标记-清除保低延迟，紧急时用标记-压缩保空间连续性——这是工业界对"不可能三角"的务实妥协。

### 为什么老年代不用复制算法

阿里巴巴中间件团队的技术文章明确指出：

> 分代式 GC 里，年老代常用 mark-sweep；或者是 mark-sweep/mark-compact 的混合方式。这是因为年老代的对象可能会长时间存活且存活率高，或者是比较大，这样拷贝起来不划算，还不如采用就地收集的方式。

各种算法的时间开销大体关系：**compaction ≥ copying > marking > sweeping**，且 **marking + sweeping > copying**。也就是说：

- 复制算法虽然也要移动对象，但"计算新地址 + 更新指针 + 移动"可以合一，所以快
    
- 标记-压缩必须先算新地址、再更新指针、最后移动，三步割裂，所以慢
    
- 但在老年代高存活率的场景下，复制算法要复制 90%+ 的对象，反而不如标记-压缩的"就地更新 + 移动"
    

### Ruby 2.7 的 GC.compact

2019 年 Ruby 引入 `GC.compact` API，允许手动触发压缩。Matz 本人认可了这一特性，并在 Ruby 2.7 中发布。这证明**标记-压缩并非"上古算法"**——现代语言运行时仍在用它解决碎片问题。Ruby 的压缩实现同样需要"Full GC → 更新指针 → 移动对象 → Full GC"的流程，与 Lisp2 的三段式思想一脉相承。

### Go 语言的演化

Go 1.12 之前只用并发标记-清除，碎片问题严重。Go 1.12+ 逐步引入**混合写屏障**，为未来的并发压缩做准备。这再次印证：纯标记-清除在长时间运行的 server 端会遭遇碎片问题，最终还是要回到标记-压缩。

## 九、承上启下：标记-压缩在全书算法篇的位置

至此，我们已经学完了四种基本 GC 算法，它们构成了完整的"算法光谱"：

|算法|移动对象？|堆利用率|碎片|停顿|适用代|
|---|---|---|---|---|---|
|**标记-清除**（第2章）|否|高|有|中|老年代、保守式 GC|
|**引用计数**（第3章）|否|高|有（但即时回收）|极短|Python、需要确定性回收|
|**复制算法**（第4章）|是|50%~90%|无|短（存活少时）|新生代|
|**标记-压缩**（第5章）|是|高|无|长|老年代|

**关键洞察**：这四种算法恰好覆盖了"移动 vs 不移动"和"空间利用率 vs 停顿时间"两个根本维度的所有可能组合：

- **不移动 + 高利用率**​ → 标记-清除（但有碎片）
    
- **不移动 + 高利用率 + 即时性**​ → 引用计数（但有循环引用）
    
- **移动 + 低利用率 + 短停顿**​ → 复制算法（但浪费空间）
    
- **移动 + 高利用率 + 长停顿**​ → 标记-压缩（但压缩成本高）
    

**没有任何一种算法能同时拿到"不移动、高利用率、无碎片、短停顿、低开销"——这就是 GC 的"不可能五边形"**。每一种新算法、每一种工业级 GC，都是在这五个顶点之间找适合自己的平衡点。

下一章（第6章）开始，本书将进入**"高级算法篇"**——增量式 GC、分代 GC、并发 GC、GC 大 unified 等。这些"高级算法"并不是第五种基本算法，而是**对前四种基本算法的"调度优化"**：

- **增量式 GC**：把标记-清除或标记-压缩的 STW 打散到 mutator 运行过程中
    
- **分代 GC**：把堆按年龄分层，新生代用复制、老年代用标记-清除或标记-压缩
    
- **并发 GC**：让 GC 与 mutator 同时运行，用写屏障保证正确性
    

带着"四种基本算法 + 不可能五边形"的框架进入下一章，你会清晰地看到：**所有"高级算法"本质都是"调度层面的创新"**——算法内核仍然是这四种之一，只是通过"分代、增量、并发"等调度手段，把停顿时间、吞吐量、空间利用率这个不可能五边形推向更优的平衡点。

---

📌 **本章核心收获**：

- 标记-压缩 = 标记-清除的"集中式判定" + 复制算法的"对象移动"，试图同时拿到两边的红利
    
- Lisp2 算法需要 3 次扫描堆（计算新地址 → 更新指针 → 移动对象），压缩成本是瓶颈
    
- **Two-Finger**：双指针相向搜索，2 次扫描，借用对象域存 forwarding，但要求对象等大、打乱顺序——可用 BiBOP 配合
    
- **表格算法**：对象群整体平移 + 间隙表格，2 次扫描且保持顺序，但表格维护复杂
    
- **ImmixGC**：Block+Line 两级组织，Line 级标记-清除 + Block 级按需压缩，是现代标记-压缩的巅峰，深刻影响 G1/ZGC/Shenandoah
    
- 工业界：JVM 老年代主流用标记-整理（Serial Old / Parallel Old），CMS 是标记-清除为主 + 碎片阈值时退化到标记-整理，Ruby 2.7 引入 GC.compact
    
- 四种基本算法构成了"不可能五边形"的所有组合——没有任何一种能同时最优，高级算法篇的"增量、分代、并发"本质都是调度层面的优化
