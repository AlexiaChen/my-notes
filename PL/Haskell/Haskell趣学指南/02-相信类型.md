
# 第2章 相信类型（Types and Typeclasses）——读书笔记

> 💡 第1章让你接受了"计算即表达式变换"；第2章则在每个表达式上贴了一张**不可伪造的身份证**——类型。这一张身份证让编译器在代码运行**之前**就能替你回答："这个值属于哪一类？这个函数能不能接这个参数？" 整本书后半段那些看似高深的抽象——高阶函数、Functor、Monad——之所以能既通用又安全，**全靠这一章铺下的两块基石：类型推断 + 类型类**。

## 🎯 全局脉络：类型系统到底在解决什么问题

命令式语言里，类型是"告诉编译器我要用什么内存布局"；Haskell 里，类型是**关于表达式的不可变事实**。这个事实有两个惊人属性：

**属性一：静态（static）—— 编译期可知**

Haskell 中每个表达式的类型在编译时就已经确定。你若写出"用布尔值除以数字"这样的代码，它**根本编不过**，更谈不上运行崩溃。错误被消灭在运行之前。

**属性二：强（strong）—— 无意义操作被拒绝**

强类型意味着"把整数当函数调用"、"把字符串传给只接受整数的函数"这类表达式会被系统直接拒绝。类型不是文档，是**数学证明**——它证明你的程序里不存在某一类结构性错误。

**属性三：可推断（inferred）—— 你不必处处标注**

Haskell 有类型推断。写个 `a = 5 + 4`，编译器自己知道 `a :: Int`，你无需手写类型声明。这让 Haskell 兼具静态类型的安全与动态语言的简洁。

> 📌 **三属性合一的洞见**：静态给你安全，强类型给你证明力，推断给你 ergonomics（人机工效）。三者结合，使得 Haskell 能在**不牺牲抽象能力**的前提下，**把大量 bug 推到编译期**。这是后面所有"在类型层面编程"玩法的入场券。

## 🔍 逐节洞见

### 3.1 Believe the Type —— `::` 读作 "has type of"

用 `:t` 在 GHCi 里查类型，是每个 Haskell 程序员的日常仪式：

```
ghci> :t 'a'
'a' :: Char
ghci> :t "HELLO!"
"HELLO!" :: [Char]     -- 即 String
ghci> :t (True, 'a')
(True, 'a') :: (Bool, Char)
```

几个关键认知：

**① 显式类型首字母大写**。`Char`、`Bool`、`Int`、`IO` 都是大写开头。这是一个视觉约定，让你一眼区分"类型"和"值/变量"。

**② 函数也有类型，且参数与返回值用同一个箭头 `->` 连接**：

```
removeNonUppercase :: [Char] -> [Char]
addThree :: Int -> Int -> Int -> Int
```

注意 `addThree` 的类型——**没有"参数列表"和"返回值"的语法区分**，全是 `->`。这暗示了一个深刻事实：Haskell 里所有函数本质上都是**单参数函数**，"多参函数"只是单参函数返回另一个单参函数的语法糖。这一手直接通向第5章的**柯里化（currying）**与部分应用。

**③ 列表与元组的类型不对称**：

- `[Char]` 是一个类型（"字符的列表"）
    
- 但 `(Bool, Char)` 与 `(Char, Char, Char)` 是**两个不同的类型**
    

> 📌 洞见：元组的长度是其类型的一部分。这就是第一章讲过的"元组是异构固定结构"在类型层面的回声——编译器在类型里就锁死了"这个对子有两个元素、各是什么类型"。

**④ 常见基础类型一览**：`Int`（有界整数）、`Integer`（任意精度整数）、`Float`、`Double`、`Bool`、`Char`。其中 `Int` vs `Integer` 的区分本身就是 Haskell "类型即语义"哲学的体现——要不要溢出语义，由类型决定，不由运行时决定。

> ⚠️ 工程提醒：默认情况下字面量 `5` 的类型是 `Num a => a`——它是一个"待定数字"，可被实例化为 `Int`、`Integer`、`Double` 等。这是 3.3 类型类的伏笔。

### 3.2 Type Variables —— 多态不是泛型，是"类型级函数"

看 `fst` 的类型：

```
fst :: (a, b) -> a
```

`a`、`b` 就是**类型变量**——它们代表"任意类型"。这类似于其他语言的泛型，但在 Haskell 里它来得更自然：因为类型推断的存在，你几乎从不需要显式写出类型参数。

**为什么类型变量是革命性的？**

回到第1章的 `head`：`head :: [a] -> a`。这一个签名就覆盖了"取任意类型列表的头"——整数列表、字符串列表、元组列表……**一份代码，全类型适用**。

> 📌 洞见：类型变量让"高阶函数"成为可能。第5章的 `map :: (a -> b) -> [a] -> [b]`、`foldl :: (b -> a -> b) -> b -> [a] -> b`，它们的通用性完全建立在类型变量之上。**没有类型变量，就没有 `map` 的"对任意列表做任意变换"**；没有类型变量，Haskell 就退化成一个"类型安全的 ML"。

类型变量的另一层深意：**它不是逃逸舱口，而是约束**。当你写 `fst :: (a, b) -> a`，你向编译器承诺"我只返回第一个元素，绝不碰第二个"——编译器可以据此做优化与证明。多态在 Haskell 里是**受控的多态**（parametric polymorphism），受"参数性定理"（parametricity）约束：一个多态函数的行为可以由其类型签名唯一确定到极大程度。这是 Haskell 程序员能做"靠类型签名猜函数实现"游戏的根本原因。

### 3.3 Typeclasses 101 —— 类型类不是类，是"能力证书"

这是全章最深的一节，也是通往全书后半段的咽喉。

**类型类解决什么问题？**

类型变量 `a` 代表"任意类型"，但有时候你需要的不是"任意"，而是"**支持某组操作的任意类型**"。比如 `+` 号：

```
(+) :: Num a => a -> a -> a
```

`Num a =>` 就是**类型类约束**：要求类型变量 `a` 必须是 `Num` 类型类的实例。换句话说：`a` 可以是任意类型，**只要那个类型"会做加法"**。

**Haskell 里几个核心类型类**：

|类型类|能力（必须有）|典型实例|
|---|---|---|
|`Eq`|`==`, `/=`|所有可比较相等的类型|
|`Ord`|`<`, `>`, `<=`, `>=`|可排序类型|
|`Show`|`show` → 字符串|可打印类型|
|`Read`|`read` ← 字符串|可从字符串解析|
|`Num`|`+`, `-`, `*` 等|`Int`, `Integer`, `Float`, `Double`|
|`Integral`|整数运算|`Int`, `Integer`|
|`Floating`|浮点运算|`Float`, `Double`|

**类型类的本质洞见**：

> 💡 类型类不是 OOP 里的"类"。**它是一种介于"接口"（Java）和"概念"（C++）之间的机制**——它定义了一组函数签名，任何想要加入这个类的类型都必须提供这些函数的实现。

与 OOP 接口的关键区别：

- **OOP**：值是对象，对象携带其类信息；方法是"发给对象的消息"
- **Haskell**：类型是被动的标签；类型类约束是**函数签名上的前置条件**；`show :: Show a => a -> String` 在编译期就被特化为具体类型的 `show`
    

**一个常被忽略的细节**：

旧版 LYAH 写道"要成为 `Num` 的实例，类型必须先是 `Eq` 和 `Show` 的实例"。但 **GHC 7.4.1 之后 `Num` 不再有 `Eq`/`Show` 超类约束**。所以下面这段代码在现代 GHC 中会报错：

```
foo :: Num x => x -> String
foo x = show x ++ "!"        -- 错误！需要 (Show x) 约束
```

必须写成：

```
foo :: (Num x, Show x) => x -> String
```

> ⚠️ 读书提醒：LYAH 作为经典教材仍有少量过时细节。遇到类型类约束问题时，以你用的 GHC 版本实际行为为准。**类型类之间的超类关系是可以演变的，但"类型类 = 能力集合"这一核心思想不变**。

**为什么类型类是 Haskell 的灵魂？**

因为它让"**重载**"（overloading）不再是语言内建的特殊机制，而是**普通的、用户可扩展的机制**。你想让自定义类型支持 `==`？写一个 `Eq` 实例。想让它支持 `map`？写一个 `Functor` 实例。想让它支持 `>>=`？写一个 `Monad` 实例。

> 📌 **这一节是第8章（自定义类型类）、第11章（Functor/Applicative/Monoid）、第12章（Monad）的总开关**。当你读到第12章 `Monad` 类型类时，回头看这一节——你会发现 Monad 不过是一个"稍微复杂点的类型类"，和 `Eq` 在机制上没有任何不同。

## 🛠 实际工程启示

**1. 类型签名是你的第一道 API 文档**

Haskell 社区的最佳实践：**即使有类型推断，也鼓励给顶层函数写显式类型签名**。为什么？因为类型签名就是最准确的文档——它告诉你函数"吃什么、拉什么"，且永远不会过期（编译器会强制它与实际实现一致）。

**2. 多态签名是约束，也是承诺**

当你写 `head :: [a] -> a`，你向调用者承诺"我返回的东西一定是列表里的某个元素，我不会凭空捏造"。这种"自由定理"（free theorem）让你**仅靠类型就能推理代码行为**——这是 Haskell 能在不运行的情况下做大量优化的基础。

**3. 类型类让你写出"零成本抽象"**

`sum :: Num a => [a] -> a` 在编译期就会被特化为 `sum :: [Int] -> Int` 或 `sum :: [Double] -> Double`，**没有虚函数表、没有运行时分派**。类型类在编译期就被解析为具体函数指针——性能与手写 C 循环无异。

**4. 类型类约束是"最小权限原则"的类型级版本**

写 `replicate' :: (Num i, Ord i) => i -> a -> [a]` 比写 `replicate' :: Int -> a -> [a]` 更通用——前者可与任何支持数值和比较的类型配合。**养成习惯：能用类型类约束就别写死具体类型**，你的函数会立刻变得更通用、更可复用。

**5. 警惕"类型类实例的法则"**

`Num` 的实例必须满足 `+` 的结合律等定律；`Functor` 的实例必须满足 `fmap id = id`。这些**法则是类型类契约的一部分**，编译器不检查，但违反它们会让依赖这些法则的抽象（如 `fold`、`traverse`）产生诡异 bug。**写实例时，心里要有法则**。

## 一句话收束

> 第2章不是在教你"如何标注类型"，而是在揭示 Haskell 的核心信念：**类型不是束缚表达的枷锁，而是让编译器替你证明程序正确性的语言**。类型变量让"一次编写、全类型适用"成为可能，类型类让"能力即约束"成为可扩展的机制——这两者合力，使得 Haskell 能在不损失抽象能力的前提下，把 bug 消灭在编译期。当你读到第13章的 `State Monad`、`IO Monad` 时，请记得回头看这一章：它们与你今天看到的 `Eq`、`Num` 在机制上毫无二致，只是能力更高级而已。
