## 🎯 全局脉络：为什么 Haskell 把"数据"和"行为"劈成两半

OOP 的信条是"数据和行为打包在一起"——类里既有字段又有方法。Haskell 故意反其道而行之：

- **数据**用 ADT 定义，只描述"值有哪些形状"
    
- **行为**用类型类定义，只描述"某种类型能做什么"
    
- 二者通过 `instance` 声明连接
    

为什么要这么设计？答案藏在编程语言理论的一个经典难题里——**表达式问题（Expression Problem）**：

|扩展维度|代数数据类型（ADT）|OOP 类继承|
|---|---|---|
|**加新操作**（如给 `Shape` 加 `area`）|✅ 便宜：直接写新函数，旧代码不受影响|❌ 昂贵：要改接口，所有子类都得补新方法|
|**加新数据类型**（如给 `Expr` 加 `Minus`）|❌ 昂贵：要改 ADT 定义，所有模式匹配的函数都得更新|✅ 便宜：新增子类，旧代码不受影响|

> 📌 **洞见**：ADT 是"封闭"的——一旦定义 `data Maybe a = Nothing | Just a`，你就不能在外面再加第三个构造器。这看似是限制，实则是**特性的来源**：
> 
> - 编译器能**静态证明模式匹配穷尽**——消除一整类"忘记处理某分支"的 bug
>     
> - 可以轻松写出**总函数**（total function）——对类型的所有可能值都有定义
>     
> - 加新操作是"零成本"的——你只需定义新函数，不需要动旧代码一根毫毛
>     

而类型类解决了另一半问题：当**多种不同类型需要共享同一种行为**时（如 `Int`、`Float`、`Double` 都能做加法），用类型类定义一次接口，各类型分别提供实例。

> 💡 **Haskell 的终极答案**：**ADT 负责"枚举数据变体"，类型类负责"跨类型的共享行为"**。二者正交、互补。这是 Haskell 对"表达式问题"的独特解法——不像 OOP 把数据和行为捆绑（导致加操作昂贵），也不像单纯的函数库（导致跨类型抽象困难）。

这一章的所有内容，都是在教你**用这对组合拳建模真实世界**。

### 8.1 代数数据类型入门 —— 值构造子就是函数

最经典的起点：`Bool` 的定义：

```
data Bool = False | True
```

`data` 引入新类型，`=` 左边是**类型构造子**（Type Constructor）`Bool`，右边是**值构造子**（Value Constructor）`False` 和 `True`，`|` 读作"或"。

**值构造子本质上是函数**：

```
ghci> :t Circle
Circle :: Float -> Float -> Float -> Shape
ghci> :t Rectangle  
Rectangle :: Float -> Float -> Float -> Float -> Shape
```

`Circle` 不是一个值，而是一个"接受三个 `Float`、返回一个 `Shape`"的函数。这一认识至关重要——**它把第1章"函数是一等公民"的思想延伸到了类型系统**：值构造子就是普通函数，可以部分应用、可以传入高阶函数。

**形状建模的完整例子**：

```
data Shape = Circle Float Float Float 
           | Rectangle Float Float Float Float

surface :: Shape -> Float
surface (Circle _ _ r) = pi * r ^ 2
surface (Rectangle x1 y1 x2 y2) = (abs $ x2 - x1) * (abs $ y2 - y1)
```

注意 `surface` 的函数体——**两个模式对应两个构造子**，这正是第3章学的"模式匹配"，也是第4章学的"结构递归"的孪生兄弟：**ADT 的构造子数量，决定了处理该类型的函数需要多少个方程**。

> 📌 **洞见**：ADT 的"代数"二字不是装饰。`data Shape = Circle ... | Rectangle ...` 在代数上就是"Circle 的形状 + Rectangle 的形状"——`|` 对应**和类型（Sum Type）**。`data Car = Car String String Int` 中 `Car` 构造子后面的字段是"乘积"关系——对应**积类型（Product Type）**。Haskell 的 ADT 就是**和类型与积类型的自由组合**——这就是"代数"的由来。

**递归 ADT —— 列表的本质**：

```
data List a = Empty | Cons a (List a)
```

这就是 `[a]` 的真实定义（语法糖版本是 `data [a] = [] | a : [a]`）。`Cons` 构造子接受一个 `a` 和一个 `List a`，返回 `List a`——**递归引用自身**。这使得 ADT 能表达任意深度的递归结构：树、表达式、JSON 值……

> 💡 这一手直接呼应第4章：当你写 `sum (Cons 1 (Cons 2 Empty))`，递归下降的方向就是 `Cons` 构造子的方向。**函数的形状追随数据的形状**——这条第4章的法则，此刻在自定义类型上得到了终极验证。

### 8.2 记录语法（Record Syntax）—— 给字段起名字

用位置参数定义 `Car` 有个痛点：

```
data Car = Car String String Int  -- 公司、型号、年份
```

调用时 `Car "Ford" "Mustang" 1967`——但谁能记住第二个 `String` 是型号还是颜色？记录语法解决这个可读性灾难：

```
data Car = Car { company :: String
               , model   :: String
               , year    :: Int }
```

**记录语法的三大福利**：

**① 构造时具名**：

```
Car { company = "Ford", model = "Mustang", year = 1967 }
```

**② 自动生成访问器函数**：

```
ghci> let c = Car "Ford" "Mustang" 1967
ghci> company c
"Ford"
```

`company`、`model`、`year` 都是函数，类型是 `Car -> String` 或 `Car -> Int`。

**③ 优雅的"修改"（Haskell 里是"生成新值"）：

```
birthday :: Car -> Car
birthday car = car { year = year car + 1 }
```

> 📌 **洞见**：记录语法是 Haskell 对"部分产品类型"的人体工学改良。但要注意——**记录语法并不会改变类型的代数本质**，它只是为积类型的字段提供了具名访问。在 Haskell 的工程实践中，为了避免字段名冲突，惯例是给字段名加上类型前缀（如 `userEmail`、`userFirstName`）——这是大型 Haskell 项目的潜规则。

### 8.3 类型参数 —— 类型构造子与值构造子的关键区分

这是全章最容易混淆、也最关键的概念：

```
data Maybe a = Nothing | Just a
```

这里有两个角色：

- **`Maybe`**​ 是**类型构造子**（Type Constructor）——它接受一个类型参数 `a`，返回一个具体类型 `Maybe Int`、`Maybe String`
    
- **`Nothing` 和 `Just`**​ 是**值构造子**（Value Constructor）——`Just` 是函数 `a -> Maybe a`
    

**关键规则**：在类型声明里只能写**类型**，在值声明里只能写**值**。所以：

```
-- ❌ 错误：把值构造子写在类型位置
vplus :: Vector t t t -> Vector t t t -> t

-- ✅ 正确：类型构造子 + 类型参数
vplus :: Vector t -> Vector t -> t
```

**类型参数让 ADT 具有多态性**：

```
data Vector a = Vector a a a deriving (Show)

vplus :: (Num t) => Vector t -> Vector t -> Vector t
(Vector i j k) `vplus` (Vector l m n) = Vector (i+l) (j+m) (k+n)
```

`Vector` 可以实例化为 `Vector Int`、`Vector Float`、`Vector Double`——**一份定义，全数值类型适用**。

> ⚠️ **Haskell 社区的铁律**：**不要在 `data` 声明里加类型约束**。即不要写 `data (Num a) => Vector a = ...`。原因：无论哪种写法，最终都要在函数上加 `Num` 约束——但前者会让**所有**操作 `Vector` 的函数都被迫加约束，污染整个 API。后者只在需要数值运算的函数上加约束，**约束最小化**。

> 📌 **洞见**：类型参数是"参数多态"在类型层面的表达。它和第2章的类型变量 `a`、第5章高阶函数的多态签名，是同一个思想在不同层面的展开——**Haskell 的一致性在于：值可以是多态的（类型变量），类型也可以是多态的（类型参数）**。

### 8.4 派生实例（Derived Instances） —— 让编译器替你写样板代码

很多类型类（`Eq`、`Ord`、`Show`、`Read`、`Enum`、`Bounded`）的实例是"机械生成"的——Haskell 允许你用 `deriving` 关键字让编译器自动生成：

```
data Day = Monday | Tuesday | Wednesday 
         | Thursday | Friday | Saturday | Sunday
         deriving (Eq, Ord, Show, Read, Bounded, Enum)
```

`deriving` 之后，你自动获得：

- **`Eq`**：构造子名相同且参数相等 → `==` 为 `True`
    
- **`Ord`**：构造子声明顺序决定大小（`Monday < Tuesday < ...`）
    
- **`Show`**：`show Monday` 返回 `"Monday"`
    
- **`Read`**：`read "Saturday" :: Day` 返回 `Saturday`
    
- **`Bounded`**：`minBound` 和 `maxBound`
    
- **`Enum`**：`succ`、`pred`、范围语法 `[Monday .. Friday]`
    

```
ghci> Saturday == Saturday
True
ghci> Saturday > Friday
True
ghci> [Thursday .. Sunday]
[Thursday,Friday,Saturday,Sunday]
```

> 💡 **洞见**：`deriving` 机制揭示了类型类的本质——**很多类型类实例是"按结构自动推导"的**。这也解释了为什么 Haskell 社区推崇"让编译器干活"：与其手写 6 个实例的样板代码，不如让编译器基于 ADT 的构造子结构自动生成。这是 Haskell 工业级生产力的秘密之一。

### 8.5 类型构造子的 Kind —— 类型的"类型"

这是全章最深奥的一节，也是通往第11章 `Functor` 的关键。

当我们说 `Maybe` 是一个类型构造子时，`Maybe` 本身是什么"类型"？GHCi 里用 `:k` 查看：

```
ghci> :k Int
Int :: *

ghci> :k Maybe
Maybe :: * -> *

ghci> :k Either
Either :: * -> * -> *
```

这里的 `*` 读作"星"，表示"具体类型"（kind 为 `*` 的类型，如 `Int`、`Maybe Int`）。`Maybe :: * -> *` 表示"`Maybe` 接受一个具体类型，返回一个具体类型"。

**更复杂的例子**：

```
data Barry a b c = Barry { yabba :: a, dabba :: b, doo :: c }
```

`Barry` 有三个类型参数，它的 kind 是：

```
ghci> :k Barry
Barry :: * -> * -> * -> *
```

要让 `Barry a b` 成为 `Functor` 的实例，必须把它部分应用到 `* -> *` 的形状：

```
instance Functor (Barry a b) where
  fmap f (Barry x y) = Barry x (f y)
```

> 📌 **洞见**：Kind 是"类型的类型"，正如类型是"值的类型"。第2章我们用类型给值分类，这里我们用 kind 给类型构造子分类。**Kind 系统保证了类型构造子的正确应用**——你不能把 `Maybe` 当成具体类型使用（它需要参数），正如你不能把 `+` 当成值使用（它需要参数）。

> 💡 **为什么这关系到 `Functor`？**​ 因为 `Functor` 的定义是 `class Functor f where fmap :: (a -> b) -> f a -> f b`——注意 `f` 的 kind 必须是 `* -> *`。也就是说，**只有"接受一个类型参数、返回具体类型"的类型构造子，才能成为 `Functor`**。这就是为什么 `Maybe`、`[]` 可以是 `Functor`，而 `Either` 必须先部分应用（`Either a`）才能是 `Functor`。**Kind 系统是 Haskell 类型类机制的隐形守门人**。

### 8.6 自定义类型类 —— 行为的抽象

类型类定义的本质是"接口 + 默认实现"：

```
class Eq a where
  (==) :: a -> a -> Bool
  (/=) :: a -> a -> Bool
  x == y = not (x /= y)   -- 默认实现
  x /= y = not (x == y)   -- 默认实现
```

**最小完整定义（minimal complete definition）**：类型类里至少要手动实现足够的函数，使得其余函数可以通过默认实现推导出来。对 `Eq` 来说，只需实现 `==` 或 `/=` 中的一个。

**为自定义类型写实例**：

```
data TrafficLight = Red | Yellow | Green

instance Eq TrafficLight where
  Red == Red     = True
  Green == Green = True
  Yellow == Yellow = True
  _ == _ = False
```

**子类约束**：

```
class (Eq a) => Num a where
  ...
```

`Num` 要求 `a` 必须是 `Eq` 的实例——也就是说，**要成为 `Num` 实例，必须先成为 `Eq` 实例**。这是类型类之间的"继承"关系。

**类型构造子的实例**：

```
instance (Eq m) => Eq (Maybe m) where
  Just x == Just y = x == y
  Nothing == Nothing = True
  _ == _ = False
```

注意 `Maybe m` 整体是一个具体类型（kind 为 `*`），而 `Maybe` 本身是类型构造子（kind 为 `* -> *`）。**类型类实例只能针对具体类型，不能针对类型构造子**——所以必须部分应用 `Maybe m`。

> 📌 **洞见**：类型类解决了"特设多态"（ad hoc polymorphism / overloading）的问题。`==` 在 `Int` 上是整数比较，在 `[a]` 上是列表逐项比较，在 `Maybe a` 上是嵌套比较——**行为不同但名字相同**。Haskell 的类型类提供了一种结构化、类型安全的方式来控制这种重载，**避免了 OOP 里"虚函数表 + 继承"的运行时开销**，而是通过"字典传递"（dictionary passing）在编译期解析。

> 💡 **类型类 vs OOP 接口的本质区别**：
> 
> - OOP 接口：数据携带方法，`obj.method()` 是"向对象发消息"
>     
> - Haskell 类型类：函数是独立的，`method obj` 是"用类型类字典解析后的函数调用"
>     
> - 关键差异：Haskell 里**同一个函数 `==` 可以同时作用于 `Int` 和 `Maybe Int`**，而 OOP 里 `int.Equals(otherInt)` 和 `maybe.Equals(otherMaybe)` 是两个不同的函数
>

### 8.7 函子：开始变魔术（Functor） —— 第11章的总预告

章节末尾引入 `Functor` 类型类：

```
class Functor f where
  fmap :: (a -> b) -> f a -> f b
```

`fmap` 接受：

1. 一个函数 `a -> b`
    
2. 一个装了 `a` 的容器 `f a`
    
3. 返回装了 `b` 的容器 `f b`
    

**`Maybe` 的 `Functor` 实例**：

```
instance Functor Maybe where
  fmap f (Just x) = Just (f x)
  fmap f Nothing  = Nothing
```

**列表的 `Functor` 实例**就是第5章的 `map`：

```
instance Functor [] where
  fmap = map
```

> 📌 **洞见**：`Functor` 是本章的高潮，也是全书的转折点。它揭示了一个深刻的事实：**第5章的 `map` 不是列表专属的——任何"容器类型"都可以有自己的 `fmap`**。`Maybe` 是容器（装 0 或 1 个值），`[]` 是容器（装 0 到 N 个值），`Either e` 是容器（装错误或正常值），`IO` 是容器（装副作用里的值）……

> 💡 **`fmap` 和 `map` 的关系**：`map :: (a -> b) -> [a] -> [b]` 是 `fmap` 在 `[]` 上的特例。**第5章你以为在学"列表的高阶函数"，其实你在学"函子的具体实例"**。这一认识会把你直接送到第11章。

**`Functor` 法则**（编译器不检查，但是契约）：

```
fmap id = id                      -- 映射恒等函数不改变容器
fmap (f . g) = fmap f . fmap g    -- 映射函数组合 = 组合映射函数
```

> ⚠️ 违反这些法则的 `Functor` 实例会导致依赖 `fmap` 的抽象（如 `traverse`、`foldMap`）产生诡异行为。**写 `Functor` 实例时，心里要有法则**。

## 🛠 实际工程启示

**1. 用 ADT 建模"封闭"的数据变体**

当你有一组固定的、不会再扩展的数据变体时（如 `Day`、`TrafficLight`、`Shape`），用 ADT 是最优解。编译器会强制穷尽模式匹配，**消除"忘记处理某分支"这类 bug**。这是 Haskell 相比 OOP 的巨大优势——OOP 里加新子类容易，但加新操作难；ADT 反过来，**加新操作容易，加新变体难**——而这恰恰是大多数业务场景的真实需求分布。

**2. 用类型类建模"跨类型的共享行为"**

当多种不同类型需要共享同一种能力时（如 `Int`、`Float`、`Double` 都能做加法），用类型类。Haskell 标准库里 `Eq`、`Ord`、`Show`、`Num`、`Functor`、`Monad` 都是这种思想的产物。

**3. ADT + 类型类的组合是 Haskell 的"杀手锏"**

```
-- 数据建模：用 ADT
data Expr = Const Int | Add Expr Expr | Mul Expr Expr

-- 行为定义：用类型类
class Eval a where
  eval :: a -> Int

-- 连接二者：用 instance
instance Eval Expr where
  eval (Const n) = n
  eval (Add e1 e2) = eval e1 + eval e2
  eval (Mul e1 e2) = eval e1 * eval e2
```

这种模式在 Haskell 编译器、解释器、DSL 设计中无处不在。

**4. 永远用 `deriving` 减少样板代码**

```
data User = User { userId :: Int, userName :: String }
  deriving (Eq, Ord, Show, Read)
```

让编译器自动生成 4 个类型类实例——这是 Haskell 工业级开发的标配。

**5. 类型参数的约束放在函数上，而非 `data` 声明上**

```
-- ❌ 反模式
data (Ord a) => MyContainer a = ...

-- ✅ 推荐
data MyContainer a = ...
myFunc :: (Ord a) => MyContainer a -> Bool
```

前者污染所有操作 `MyContainer` 的函数，后者只在需要的函数上加约束。

**6. 智能构造子 + 模块导出 = 工业级 ADT**

结合第6章的模块导出控制：

```
module Rational (Rational, mkRational, num, denom) where

data Rational = Rat Integer Integer

mkRational :: Integer -> Integer -> Rational
mkRational n d = let g = gcd n d in Rat (n `div` g) (d `div` g)
```

外部用户无法直接调用 `Rat` 构造子，只能通过 `mkRational` 创建——**不变式被类型系统强制执行**。

**7. Kind 意识是 Haskell 进阶的分水岭**

当你看到 `Functor f => ...`、`Monad m => ...` 时，要立刻反应过来：**`f` 和 `m` 的 kind 是 `* -> *`**。这种 kind 敏感性会让你在第11-13章学习高级抽象时事半功倍。

**8. 递归 ADT 是 Haskell 表达树形结构的母语**

```
data Tree a = Empty | Node a (Tree a) (Tree a)

data JSON = JNull | JBool Bool | JNumber Double 
          | JString String | JArray [JSON] | JObject [(String, JSON)]
```

任何递归数据结构都能用 ADT 自然表达——这正是 Haskell 在编译器、解析器、序列化库领域称王的原因。

**9. `Functor` 实例的法则意识**

写 `Functor` 实例时，心里默念两条法则：

- `fmap id = id`（映射恒等不改变容器）
    
- `fmap (f . g) = fmap f . fmap g`（映射组合 = 组合映射）
    

违反法则的 `Functor` 实例会让依赖 `fmap` 的无数抽象产生诡异行为。

## 一句话收束

> 第7章不是在教你 `data` 和 `class` 的语法，而是在交付 Haskell 建模的"双剑"：**ADT 用和类型与积类型的自由组合，让你以"代数"的方式精确描述数据的形状**；**类型类用接口与实例的分离，让你以"能力"的方式精确描述行为的契约**。ADT 是封闭的——这一"限制"换来了编译期穷尽检查的保证和总函数的可能性；类型类是开放的——多种类型可以实现同一个类型类，实现跨类型的特设多态。二者正交配合，构成了 Haskell 对"表达式问题"的独特答案。当你在第10章用 ADT 建模德州扑克、在第11章为 `Maybe` 写 `Functor` 实例、在第13章为自定义类型写 `Monad` 实例时，请记得回头看这一章：你以为在学两个独立的关键字，其实你在学**Haskell 整个抽象体系的两个基石**——而第11章的 `Functor`、第12章的 `Monad`、第13章的 `Applicative`，都不过是类型类机制在特定领域的应用罢了。从这一章开始，你不再是"Haskell 的使用者"，而是"Haskell 类型的创造者"。
