## 🎯 全局脉络：什么是"函数式地解决问题"

命令式思维解决问题的方式是——"**设变量、写循环、改状态**"。函数式思维解决问题的方式是——"**建模型、写纯函数、组合抽象**"。

第10章的两个例题，完美示范了函数式问题解决的**标准三步法**：

```
第1步：领域建模（Modeling）
       ↓ 用 ADT 把问题的"数据形状"精确描述出来
第2步：纯函数核心（Pure Core）
       ↓ 用 fold / 递归 / 高阶函数表达计算逻辑
第3步：I/O 外壳（IO Shell）
       ↓ 用薄薄的 I/O 层读取输入、调用纯函数、写出输出
```

> 📌 **洞见**：这套"纯核心 + I/O 外壳"的架构，是现代 Haskell 工程的黄金法则。Haskell 社区有句话："**IO 是传染性的——一旦你的函数碰了 I/O，它就永远是 I/O 的，会像病毒一样扩散**"。所以正确的做法不是"避免 I/O"，而是"**把 I/O 推到程序的边缘，让核心逻辑保持纯洁**"。纯函数易于推理、易于测试、易于并行化；I/O 函数只负责搬运数据。

这一章的两个例题，本质上都在演示这同一个套路。我们逐个解剖。

## 🔍 逐节洞见

### 10.1 逆波兰式计算器（RPN Calculator）—— `foldl` 的完美舞台

**问题**：逆波兰式（后缀表达式）如 `2 3 +` 表示 `2 + 3`，`2 3 4 * +` 表示 `2 + (3 * 4)`。写一个函数 `solveRPN :: String -> Double`，接受 RPN 字符串，返回计算结果。

**第1步：领域建模**

RPN 的本质是一个**栈机器**——遍历 token 序列，遇到数字就压栈，遇到运算符就从栈顶弹出两个数做运算、把结果压回栈。最终栈里只剩一个数，就是结果。

注意：这里**不需要复杂的 ADT**——RPN 的"数据形状"就是 `String`，token 序列就是 `words str`。这是一个"轻建模"的例子：问题本身的结构足够简单，用基础类型就能表达。

**第2步：纯函数核心——`foldl` 的魔法**

```
solveRPN :: (Num a, Read a, Floating a) => String -> a
solveRPN = head . foldl foldingFunction [] . words
  where foldingFunction (x:y:ys) "*" = (x * y):ys
        foldingFunction (x:y:ys) "+" = (x + y):ys
        foldingFunction (x:y:ys) "-" = (y - x):ys
        foldingFunction (x:y:ys) "/" = (y / x):ys
        foldingFunction (x:y:ys) "^" = (y ** x):ys
        foldingFunction (x:xs) "ln" = log x:xs
        foldingFunction xs "sum" = [sum xs]
        foldingFunction xs numberString = read numberString:xs
```

> 💡 **这是第5章 `foldl` 的巅峰之作**。一行代码 `head . foldl foldingFunction [] . words`，完成了：
> 
> 1. `words` 把字符串切成 token 列表
>     
> 2. `foldl foldingFunction []` 以空栈 `[]` 为初始累加器，遍历每个 token
>     
> 3. `foldingFunction` 是"折叠函数"——它根据 token 是数字还是运算符，决定如何更新栈
>     
> 4. `head` 取出最终栈里的唯一结果
>     

**`foldingFunction` 的精妙之处**：

- **栈表示为列表**：`(x:y:ys)` 模式匹配出栈顶两个元素 `x`、`y` 和栈的剩余 `ys`
    
- **运算符处理**：`(x:y:ys) "*" = (x * y):ys`——弹出 `x` 和 `y`，相乘，结果压回栈
    
- **数字处理**：`foldingFunction xs numberString = read numberString:xs`——把 token 读作数字，压栈
    
- **模式匹配的顺序很重要**：`"*"`、`"+"` 等具体字符串模式必须放在 `numberString` 这个通配模式**之前**，否则数字永远匹配不到
    

> 📌 **洞见**：`solveRPN` 是"**状态机 + 折叠**"的经典范本。栈就是状态，`foldingFunction` 就是状态转移函数，`foldl` 驱动状态机从头跑到尾。这种"用 `foldl` 驱动状态机"的套路，在函数式编程里无处不在——解析器、解释器、编译器、流式处理器，本质上都是状态机，都可以用 `foldl` 表达。

**第3步：I/O 外壳**

```
main = do
  line <- getLine
  print (solveRPN line)
```

薄薄三行——读一行、调用纯函数、打印结果。**所有核心逻辑都在 `solveRPN` 这个纯函数里**，I/O 只是个搬运工。

**扩展性**：10.1.3 节"添加更多的操作符"展示了函数式设计的**开放性**——想加一个新运算符？只需在 `foldingFunction` 里加一个方程：

```
foldingFunction (x:y:ys) "max" = (max x y):ys
foldingFunction (x:y:ys) "min" = (min x y):ys
```

> 💡 **这是 ADT + 模式匹配带来的"表达式问题"优势**：加新操作（新运算符）是零成本的——你只需定义新函数，不需要改旧代码。

**与现代 Haskell 实践的对照**：

更健壮的工业级实现会用 `Maybe` 或 `Either` 处理错误（如栈为空、非法 token）：

```
solveRPN :: (Fractional a, Read a) => String -> Maybe a
solveRPN expr = case foldl (\s e -> s >>= act e) (Just []) (words expr) of
  Just [r] -> Just r
  _ -> Nothing
  where act "+" (x:y:s) = Just $ x + y : s
        act e s = readMaybe e >>= Just . (: s)
```

这是第7章"用 `Maybe` 建模失败"思想的直接应用——**部分函数 `head` 被替换为总函数 `Maybe`**。

### 10.2 从希思罗机场到伦敦 —— ADT + 动态规划的完美舞台

**问题**：从希思罗机场到伦敦有两条平行的主路 A 和 B，路之间有若干交叉小路 C。每段路有不同的长度，求从起点到终点的最短路径。

**第1步：领域建模——ADT 登场**

这是"重建模"的例子——问题本身有丰富的结构，必须用 ADT 精确捕捉：

```
-- 三个连续的路段：A 段、B 段、C 段（交叉小路）
data Section = Section { getA :: Int, getB :: Int, getC :: Int }
  deriving (Show)

-- 整个道路系统就是 Section 的列表
type RoadSystem = [Section]

-- 路径标签：走了 A 段、B 段还是 C 段
data Label = A | B | C
  deriving (Show)

-- 路径就是标签与长度的配对列表
type Path = [(Label, Int)]
```

**为什么这个建模是优雅的？**

- `Section` 用**记录语法**（第7章 8.2 节）精确表达"一个交叉点到下一个交叉点"的三段路
    
- `RoadSystem` 是 `Section` 的列表——整个问题域被压缩成一个列表
    
- `Label` 是**和类型**（第7章 ADT 的核心）——路径上的每一步要么是 A、要么是 B、要么是 C
    
- `Path` 是 `Label` 与 `Int` 的积类型配对列表
    

> 📌 **洞见**：这个建模展示了第7章 ADT 的威力——**"A 段 / B 段 / C 段"这种"有限变体"用和类型表达，"三段路的长度"这种"固定结构"用积类型表达**。Haskell 的 ADT 让"数据形状"在类型层面被精确锁定，编译器能静态证明你处理了所有可能情况。

**第2步：纯函数核心——动态规划**

最短路径问题的关键是**最优子结构**：到达第 N 个交叉点的最短路径，必然包含到达第 N-1 个交叉点的最短路径。

作者用 `roadStep` 函数表达这个递推关系：

```
roadStep :: (Path, Path) -> Section -> (Path, Path)
roadStep (pathA, pathB) (Section a b c) =
  let priceA = sum $ map snd pathA
      priceB = sum $ map snd pathB
      forwardPriceToA = priceA + a
      crossPriceToA = priceB + b + c
      forwardPriceToB = priceB + b
      crossPriceToB = priceA + a + c
      newPathToA = if forwardPriceToA <= crossPriceToA
                   then (A, a):pathA
                   else (C, c):(B, b):pathB
      newPathToB = if forwardPriceToB <= crossPriceToB
                   then (B, b):pathB
                   else (C, c):(A, a):pathB
  in (newPathToA, newPathToB)
```

**`roadStep` 的精妙之处**：

- **输入**：`(pathA, pathB)`——到达当前交叉点时，A 路和 B 路上的最优路径
    
- **输出**：`(newPathToA, newPathToB)`——到达下一个交叉点时，A 路和 B 路上的最优路径
    
- **决策逻辑**：到 A2 有两种选择——从 A1 直行（花费 `priceA + a`）或从 B1 穿越（花费 `priceB + b + c`），选便宜的
    
- **路径累积**：`(A, a):pathA` 把新步骤**压在路径列表的头部**——这是第4章学的"递归 + 累加器"模式
    

> 💡 **这是第4章结构递归思想在动态规划上的应用**：`roadStep` 是"单步递推"，`optimalPath` 用 `foldl` 把 `roadStep` 应用到整个 `RoadSystem`：

```
optimalPath :: RoadSystem -> Path
optimalPath roadSystem =
  let (bestAPath, bestBPath) = foldl roadStep ([], []) roadSystem
  in if sum (map snd bestAPath) <= sum (map snd bestBPath)
     then reverse bestAPath
     else reverse bestBPath
```

`foldl roadStep ([], []) roadSystem` 一行代码，完成了对整个道路系统的动态规划遍历——**这正是 `foldl` 作为"状态机驱动器"的又一次精彩演出**。

**第3步：I/O 外壳——从输入读取道路系统**

10.2.4 节展示了如何从标准输入读取道路系统：

```
main = do
  contents <- getContents
  let roadSystem = parseContents contents
      path = optimalPath roadSystem
      pathString = concat $ map (show . fst) path
      totalPrice = sum $ map snd path
  putStrLn $ "The best path is: " ++ pathString
  putStrLn $ "Total price: " ++ show totalPrice
```

> 💡 **这是第9章 `interact` 思想的完整应用**：I/O 层只负责"读输入 → 调纯函数 → 写输出"，核心算法 `optimalPath` 是完全纯粹的——它可以脱离 I/O 单独测试、可以复用、可以并行化。

**与现代 Haskell 工程实践的对照**：

源代码仓库中的参考实现展示了工业级写法：

```
data Node = Node Road (Maybe Road)
data Road = Road Int Node
```

作者甚至用**递归 ADT**​ 把道路系统建模为图结构——这展示了第7章"递归 ADT 表达树形/图结构"的思想。但在实际解题时，作者选择了**更简单、更扁平的 `Section` 列表表示**——这是一个重要的工程教训：**建模不是越精细越好，而是要找到"恰好够用"的抽象层次**。

## 🛠 实际工程启示

**1. "纯核心 + I/O 外壳"是 Haskell 工程的铁律**

```
-- ✅ 推荐架构
module Core where
  -- 所有业务逻辑都是纯函数
  calculateRPN :: String -> Maybe Double
  findShortestPath :: RoadSystem -> Path

module Main where
  import Core
  main :: IO ()
  main = do
    input <- getLine
    case calculateRPN input of
      Just result -> print result
      Nothing -> putStrLn "Error: invalid expression"
```

```
-- ❌ 反模式：把 IO 和业务逻辑混在一起
badMain = do
  line <- getLine
  -- 直接在 IO 里做所有事
  let tokens = words line
  -- ... 100 行 IO 代码 ...
```

**2. 用 ADT 精确建模领域**

遇到"有限变体"的问题（如方向、状态、类型），**优先用和类型**：

```
data Direction = North | South | East | West
data Status = Pending | Approved | Rejected
data Expr = Lit Int | Add Expr Expr | Mul Expr Expr
```

遇到"固定结构"的问题，**用积类型 + 记录语法**：

```
data User = User { userId :: Int, userName :: String, userEmail :: String }
data Section = Section { getA :: Int, getB :: Int, getC :: Int }
```

**3. `foldl` 是状态机的万能驱动器**

任何"遍历序列 + 累积状态"的问题，都是 `foldl` 的舞台：

```
-- 计数器
count :: (a -> Bool) -> [a] -> Int
count p = foldl (\acc x -> if p x then acc + 1 else acc) 0

-- 状态机
runStateMachine :: (state -> event -> state) -> state -> [event] -> state
runStateMachine transition = foldl transition
```

**4. 用 `Maybe` / `Either` 建模失败，避免部分函数**

```
-- ❌ 部分函数：空栈时崩溃
head :: [a] -> a

-- ✅ 总函数：空栈时返回 Nothing
safeHead :: [a] -> Maybe a
safeHead [] = Nothing
safeHead (x:_) = Just x

-- 在 RPN 计算中：
solveRPN :: String -> Maybe Double
solveRPN expr = case foldl step (Just []) (words expr) of
  Just [r] -> Just r
  _ -> Nothing
```

**5. 模式匹配的顺序是正确性的一部分**

```
foldingFunction (x:y:ys) "*" = (x * y):ys  -- 具体模式在前
foldingFunction xs numberString = read numberString:xs  -- 通配模式在后
```

**通配模式必须放在最后**——这是 Haskell 新手最常见的 bug 源。

**6. 递归 ADT 表达树形/图结构**

```
data Tree a = Empty | Node a (Tree a) (Tree a)
data JSON = JNull | JBool Bool | JNumber Double 
          | JString String | JArray [JSON] | JObject [(String, JSON)]
```

希思罗道路系统也可以用递归 ADT 建模（如参考代码中的 `Node` 和 `Road`），但**实际问题中选择"恰好够用"的抽象**——`[Section]` 比递归图更简单、更易用 `foldl` 处理。

**7. 纯函数的可测试性是 Haskell 的最大红利**

```
-- 在 GHCi 中直接测试纯函数
ghci> solveRPN "2 3 +"
5.0
ghci> solveRPN "2 3 4 * +"
14.0
ghci> optimalPath heathrowToLondon
[(C,30),(B,10),(A,5),(C,20),(B,2),(B,8),(C,0)]
```

**不需要 mock、不需要测试框架、不需要数据库**——纯函数的测试就是"用示例输入调用函数"。这是 Haskell 工程效率的源泉。

**8. I/O 外壳应该尽可能薄**

```
-- 薄 I/O 外壳
main = interact (unlines . map process . lines)
  where process line = case solveRPN line of
                         Just r -> show r
                         Nothing -> "Error"
```

所有核心逻辑都在 `process` 这个纯函数里，I/O 只是个管道。

## 一句话收束

> 第10章不是在教你"如何解决 RPN 计算和最短路径"，而是在交付 Haskell 工程的标准配方：**用 ADT 精确建模领域（Section/Label/Path），用 `foldl` 驱动状态机（RPN 的栈、道路的动态规划），用 `Maybe` 处理失败，用薄薄的 I/O 外壳包裹纯核心**。这两个例题是"纯核心 + I/O 外壳"架构的完美示范——`solveRPN` 和 `optimalPath` 都是纯函数，可以脱离 I/O 单独测试、复用、并行化；而 `main` 只是个搬运工，负责"读输入 → 调纯函数 → 写输出"。更深一层看，这一章是**第11章 Applicative 和第12章 Monad 的"具体而微的预演"**：RPN 计算器的"栈状态机"就是 `State Monad` 解决的问题，希思罗路径的"路径+代价累积"就是 `Writer Monad` 解决的问题；而 `foldl roadStep ([],[]) roadSystem` 这种"用折叠传递状态"的思想，正是 `do` 块里 `>>=` 组合的雏形。从这一章开始，你已经具备了用 Haskell 解决真实问题的全部能力——而接下来第11章的 `Applicative`、第12章的 `Monad`、第13章的具体 Monad 实例，不过是把这一章"手写的模式"抽象成"类型类级别的重用"罢了。函数式地解决问题，本质上就是**"建模数据 → 写纯函数 → 组合抽象 → 薄 I/O 外壳"**——这个配方，是你从"学 Haskell"跨入"用 Haskell"的真正分水岭。
