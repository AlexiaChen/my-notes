
# 第八章 数字相关的类型类 —— 读书笔记

> 💡 如果说第七章教你用类型类把"行为"从"数据"上解耦，那么第八章就是把这套机制**落实到数字世界**的一次完整示范：Haskell 里你天天在用的 `+`、`-`、`*`、`==`、`compare`、`[1..10]`，**没有一个 是语法**——它们全是通过类型类挂在 `Num`、`Ord`、`Enum`、`Bounded` 这些行为契约上的函数。这一章的深层命题是：**为什么 Haskell 宁愿让数字运算"看起来像语法，实则是类型类方法"，也不肯把它们做成真正的语法？**​ 答案关乎类型安全、代码复用，以及一个反直觉的事实——**Haskell 绝不替你做隐式类型转换**。

韩冬在这一章安排了五个小节：**8.1 顺序类**、**8.2 data 和类型约束**、**8.3 枚举类**、**8.4 边界类**、**8.5 数字类**。表面是五个数字相关的类型类，实则在回答一个连贯的问题：**如何用第七章学到的 `class` / `instance` / 约束，把"数字"这件事表达得既安全又通用？**

```
第七章: 类型类（行为抽象机制）
   ↓
第八章: 把"数字行为"分解为 Ord / Enum / Bounded / Num  ← 你在这里
   ↓
第九章: type / newtype / 惰性求值（为自定义数值类型铺垫）
   ↓
第十一章起: Functor / Applicative / Monad（更高层抽象）
```

**这一章是第七章类型类理论的第一次"工业级示范"**。第七章告诉你"类型类可以定义行为契约"；第八章让你看见——连 Haskell 语言最基本的数字运算，都是用类型类定义的。这带来三个深远后果：

1. **数字字面量可以重载**——`7` 的类型是 `Num a => a`（Haskell 官方教程原文：_"Thus, 7 has the type (Num a) => a"_）
    
2. **自定义数值类型能无缝接入**——只要你为 `MyNumber` 实现 `Num` 实例，就能写 `MyNumber 5 + MyNumber 3`
    
3. **类型安全优先于便利**——Haskell 绝不自动把 `Int` 转成 `Double`，你必须显式 `fromIntegral`
    

> 💡 理解这一章的关键，是把"数字运算"从"语法"的心智模型里拽出来，放进"类型类方法"的心智模型里。一旦完成这个切换，`fromIntegral`、`Numeric literal overloading`、`defaulting` 这些看似怪异的设计就全都顺理成章了。

## 8.1 顺序类 `Ord`：全序比较的行为契约

### 类声明

```
class Eq a => Ord a where
  compare :: a -> a -> Ordering
  (<), (<=), (>), (>=) :: a -> a -> Bool
  max, min :: a -> a -> a
```

### 🔑 洞见一：`Ord` 依赖 `Eq`，这是类型类层级的活样本

`class Eq a => Ord a` 这句声明读作：**任何想成为 `Ord` 实例的类型，首先必须是 `Eq` 的实例**。因为要比较大小，你至少要能比较相等——这是"能力依赖"。

> 📌 这呼应了第七章 7.3.1 的"层级和约束"：类型类层级不是 OOP 的继承链，而是**能力的累加**。`Ord` 在 `Eq` 基础上"加"了顺序比较的能力。

### 🔑 洞见二：Deriving 规则揭示了 ADT 的"自然顺序"

韩冬在书中明确指出 `Ord` 的推导规则：**按照构造函数书写的顺序，后面的构造函数创建的值大于前面的；相同的构造函数，则按照从前向后的位置顺序比较参数的大小**。

这意味着：

```
data Color = Red | Green | Blue deriving (Ord)
-- Red < Green < Blue（按声明顺序）

data Shape = Circle Float | Square Float
  deriving (Ord)
-- Circle 2 < Circle 3 < Square 1
-- （Circle 构造子在 Square 前面，所以所有 Circle 都小于所有 Square）
```

**为什么这个规则重要？**​ 因为它是 Haskell "make illegal states unrepresentable" 哲学的延伸——当你给一个 ADT 派生 `Ord` 时，编译器生成的顺序语义是**确定性、可预测的**，不会因为"忘了实现某个 case"而出 bug。

### 🔑 洞见三：`compare` 返回 `Ordering`，这是个被低估的设计

`compare :: a -> a -> Ordering`，其中 `Ordering` 是：

```
data Ordering = LT | EQ | GT
```

**为什么不直接返回 `Bool`？**​ 因为三态 `LT/EQ/GT` 比单态 `Bool` 携带更多信息——它让 `sort`、`maximum`、`minimum` 等函数能基于 `compare` 一次性获取完整顺序信息，而不用多次调用 `<` 和 `==`。这是"用 ADT 表达完整性"的又一范例（呼应第二章）。

### 实际应用

- 任何需要做大小比较的场景：`sort`、`maximum`、`minimum`、`Data.Map` 的键
    
- 自定义类型的"自然排序"：通过 `deriving (Ord)` 免费获得

## 8.2 data 和类型约束：第七章理论的"纪律性延伸"

这是本章**极易被跳过但极其重要**的一节。韩冬在书中给了一条铁律：

> ⚠️ **永远不要在你的数据类型声明前加上类型类的约束。类型约束应该用来约束普通函数的参数类型，进而帮助编译器确定函数的行为，而不是约束数据的行为。**

### 🔑 洞见四：为什么 data 声明前不应加约束？

考虑反面典型：

```
-- ❌ 错误示范
data (Ord a) => MyContainer a = Container a [a]
```

这种写法的问题在于：

1. **约束不会"自动传播"到使用这个类型的函数上**——你每写一个操作 `MyContainer` 的函数，都得重复写 `Ord a =>` 约束
    
2. **data 本身只是"值空间的声明"**——它不该关心"值能做什么"，那是 `instance` 的事
    
3. **违背了类型类"开放世界"的哲学**——加在 data 上的约束等于"封锁"了类型，让后续无法灵活地为它追加行为
    

正确的写法是：

```
-- ✅ 正确示范
data MyContainer a = Container a [a]

-- 约束加在函数上
insert :: Ord a => a -> MyContainer a -> MyContainer a
insert x (Container head tail) = ...
```

### 🔑 洞见五：这条纪律揭示了类型类的本质分工

|构造|职责|是否加约束|
|---|---|---|
|`data`|定义值空间|❌ 不加|
|`class`|定义行为契约|✅ 可以（表达层级依赖）|
|`instance`|把行为绑定到具体类型|✅ 可以（表达约束传播）|
|普通函数|描述计算|✅ 应该（帮助编译器确定行为）|

> 💡 这条纪律是第七章"行为解耦"理论的延伸：**data 是数据，instance 是行为，两者通过类型类松耦合**。把约束加在 data 上，等于把行为和数据的绑定"硬编码"了——这正是 Haskell 要避免的。

### 实际应用

- 定义泛型容器（`Tree`、`Heap`、`Graph`）时，**永远**不在 data 声明上加约束
    
- 约束写在操作这些容器的函数上——这样 `Tree a` 本身对任何 `a` 都成立，只有当你调用 `insert`（需要 `Ord a`）或 `size`（需要 `Num a`）时，约束才被触发

## 8.3 枚举类 `Enum`：可枚举的有序值集合

### 类声明

```
class Enum a where
  succ, pred :: a -> a          -- 后/前一个元素
  toEnum   :: Int -> a          -- 枚举中对应次序的元素
  fromEnum :: a -> Int          -- 元素在枚举中的次序
  enumFrom      :: a -> [a]          -- [n..]
  enumFromThen  :: a -> a -> [a]     -- [n,n'..]
  enumFromTo    :: a -> a -> [a]     -- [n..m]
  enumFromThenTo :: a -> a -> a -> [a]  -- [n,n'..m]
```

### 🔑 洞见六：`Enum` 是 `[1..10]` 语法的幕后英雄

你每天在用的范围语法 `[1..10]`、`['a'..'z']`、`[0,2..10]`，**背后全是 `Enum` 类型类的方法**：

- `[n..]` → `enumFrom n`
    
- `[n,m..]` → `enumFromThen n m`
    
- `[n..m]` → `enumFromTo n m`
    
- `[n,m..p]` → `enumFromThenTo n m p`
    

这意味着——**任何实现了 `Enum` 的类型，都能用范围语法**。字符、Bool、你自己定义的 ADT，统统可以。

### 🔑 洞见七：`Enum` 的 Deriving 规则有讲究

韩冬明确指出：**构造函数不需要参数的数据类型才可以使用 `Enum` 推导**。

```
-- ✅ 可以 deriving Enum
data Color = Red | Green | Blue deriving (Enum)
-- toEnum 0 = Red, toEnum 1 = Green, toEnum 2 = Blue

-- ❌ 不能 deriving Enum（构造子带参数）
data Shape = Circle Float | Square Float
```

为什么？因为 `Enum` 的语义是"一一列举"——`toEnum :: Int -> a` 和 `fromEnum :: a -> Int` 建立了一个 Int 与类型值之间的**双射**。带参数的构造子无法被 Int 唯一确定（Circle 可以有无限多个 Float 参数），所以不符合 `Enum` 的语义。

### 🔑 洞见八：`toEnum` / `fromEnum` 是 Int 与其他枚举类型的"桥"

`fromEnum :: a -> Int` 把枚举值转成它在枚举中的序号；`toEnum :: Int -> a` 做反向转换。这两个函数是**枚举类型与 Int 互转的唯一正规通道**：

```
fromEnum 'a'  -- 97
toEnum 97     -- 'a' :: Char

fromEnum Red  -- 0
toEnum 0      -- Red :: Color
```

> 💡 注意 `toEnum` 的返回类型是多态的（`Enum a => Int -> a`），它和 `fromInteger` 一样是"重载的"——编译器会根据上下文推断你想要哪种枚举类型。

### 实际应用

```
-- 生成所有大写字母
['A'..'Z']  -- "ABCDEFGHIJKLMNOPQRSTUVWXYZ"

-- 生成所有颜色
[Red .. Blue]  -- [Red, Green, Blue]

-- 枚举与 Int 的桥接
map fromEnum ['a'..'e']  -- [97,98,99,100,101]
```

## 8.4 边界类 `Bounded`：有上下界的类型

### 类声明

```
class Bounded a where
  minBound, maxBound :: a
```

### 🔑 洞见九：`Bounded` 是"类型安全的值域声明"

`Bounded` 让你在类型层面声明一个类型的取值范围：

```
-- Int 的边界（64 位平台上通常是 -2^63 到 2^63-1）
minBound :: Int  -- -9223372036854775808
maxBound :: Int  -- 9223372036854775807

-- Bool 的边界
minBound :: Bool  -- False
maxBound :: Bool  -- True

-- Char 的边界
minBound :: Char  -- '\NUL'
maxBound :: Char  -- '\1114111'（Unicode 最大值）
```

韩冬指出：**上边界和下边界是按照构造函数的书写顺序决定的**——第一个构造子是 `minBound`，最后一个构造子是 `maxBound`。

### 🔑 洞见十：`Bounded` + `Enum` = 完整的"值域遍历"

当一个类型同时是 `Enum` 和 `Bounded` 的实例时，你可以**无损地遍历它的整个值域**：

```
[minBound .. maxBound] :: [Bool]  -- [False, True]
[minBound .. maxBound] :: [Int]   -- 所有 Int 值（太多，别这么干）
```

这对测试尤其有用——QuickCheck 等测试框架可以利用 `Bounded` + `Enum` 自动生成所有可能的输入值。

### 🔑 洞见十一：为什么 `Bounded` 是独立的类型类？

你可能会问：为什么不直接把 `minBound` / `maxBound` 塞进 `Ord` 里？因为**不是所有可比较的类型都有上下界**。比如：

- `Integer` 是 `Ord` 的实例，但**没有**​ `Bounded`——它是任意精度整数，没有上下界
    
- `Double` 是 `Ord` 的实例，但**没有**​ `Bounded`——它有 `+Infinity` 和 `-Infinity`，但那些是特殊的浮点值，不是正常的"最大值"
    
- `[a]` 是 `Ord` 的实例（如果 `a` 是 `Ord`），但**没有**​ `Bounded`——列表长度无限
    

**把 `Bounded` 独立成类型类，让"有界"成为一个可选能力**——这正是类型类"按需组合行为"哲学的体现。

### 实际应用

```
-- 安全的整数运算
safeAdd :: Int -> Int -> Maybe Int
safeAdd x y
  | result > maxBound = Nothing
  | result < minBound = Nothing
  | otherwise         = Just result
  where result = x + y

-- 枚举测试
allBools = [minBound .. maxBound] :: [Bool]  -- [False, True]
```

## 8.5 数字类 `Num`：Haskell 数字系统的"总枢纽"

这是本章的重头戏，也是最值得深挖的一节。

### Num 的类声明

```
class Num a where
  (+), (-), (*) :: a -> a -> a
  negate, abs, signum :: a -> a
  fromInteger :: Integer -> a
```

### 🔑 洞见十二：`Num` 是"所有数字类型的父类类型类"

韩冬在书里用了"父类类型类"这个词——意思是 `Num` 是所有具体数字类型类（`Integral`、`Fractional`、`Floating`）的**共同祖先**。

Haskell 的数字类型类层级如下（基于官方 Haskell Report）：

```
Num
       /   \
   Integral  Fractional
      |         |
    Real      Floating
                |
              RealFrac
                |
              RealFloat
```

这条层级的关键点：

1. **`Num` 提供 `+`、`-`、`*`**——所有数字都支持的运算
    
2. **`Integral`（继承 `Num`、`Real`、`Enum`）提供 `div`、`mod`、`toInteger`**——整数特有的运算
    
3. **`Fractional`（继承 `Num`）提供 `/`、`recip`、`fromRational`**——分数运算
    
4. **`Floating`（继承 `Fractional`）提供 `exp`、`log`、`sin`、`cos`、`sqrt`、`**` 等**——浮点特有函数
    
5. **`RealFrac`（继承 `Fractional`、`Real`）提供 `floor`、`ceiling`、`round`、`truncate`**——浮点转整数
    

### 🔑 洞见十三：`Num` 故意"不包含除法"

这是 Haskell 数字系统设计里**最反直觉但最正确**的决定。官方 Haskell Report 明确说：

> _"Note that Num does not provide a division operator; two different kinds of division operators are provided in two non-overlapping subclasses of Num"_

为什么？因为：

- **`Int` 除以 `Int` 不能得到 `Int`**——要么截断（`div`），要么取模（`mod`），普通 `/` 不适用
    
- **复数不能比较大小**——所以 `Num` 不是 `Ord` 的子类，只有 `Real`（实数）才是 `Ord` 的子类
    
- **整数除法和浮点除法语义不同**——必须分开到 `Integral` 和 `Fractional` 两个子类
    

> 💡 这种设计让类型系统**在编译期**就阻止了"用整数除法得到浮点数"或"对复数排序"这类错误。对比 C/Java——`5/2` 得到 `2`（静默截断），Haskell 直接让 `5 / 2` 类型错误，逼你写 `fromIntegral 5 / 2` 或 `5 div 2`。

### 🔑 洞见十四：数字字面量是"语法糖版的 fromInteger / fromRational"

这是本章**最震撼的洞见**，来自 Haskell 官方教程：

> _"An integer numeral (without a decimal point) is actually equivalent to an application of fromInteger to the value of the numeral as an Integer. Similarly, a floating numeral (with a decimal point) is regarded as an application of fromRational to the value of the numeral as a Rational."_

也就是说：

```
7    ≡  fromInteger (7 :: Integer)   -- 类型: Num a => a
7.3  ≡  fromRational (7.3 :: Rational)  -- 类型: Fractional a => a
```

**这意味着数字字面量本身是重载的**——`7` 可以是 `Int`、`Integer`、`Float`、`Double`、`Rational`，甚至可以是你自己定义的某个 `Num` 实例类型，只要那个类型实现了 `fromInteger`。

```
newtype MyNumber = MyNumber Int

instance Num MyNumber where
  MyNumber x + MyNumber y = MyNumber (x + y)
  -- ... 其他方法
  fromInteger n = MyNumber (fromInteger n)

-- 现在你可以写：
myNum = MyNumber 5 + 7  -- 7 被重载为 MyNumber 通过 fromInteger
```

> 💡 **这就是为什么自定义数值类型能无缝使用字面量**——`fromInteger` 是 `Num` 类的方法，你只要在实例里实现它，字面量 `7` 就能自动变成你的类型。

### 🔑 洞见十五：Haskell 绝不隐式转换——`fromIntegral` 是你的桥

这是初学者最大的"坑"，也是 Haskell 数字系统最坚定的设计立场：

```
length [1,2,3,4] + 3.2
-- 类型错误！length 返回 Int，3.2 是 Fractional
-- Int 不是 Fractional，编译器拒绝隐式转换

fromIntegral (length [1,2,3,4]) + 3.2
-- ✅ 正确：fromIntegral 把 Int 转成任意 Num 类型
```

`fromIntegral` 的类型是：

```
fromIntegral :: (Integral a, Num b) => a -> b
```

它定义为 `fromIntegral i = fromInteger (toInteger i)`——先把 `Integral` 转成 `Integer`，再通过 `fromInteger` 转成任意 `Num` 类型。

Haskell Wiki 明确表态：

> _"Repeatedly people ask for automatic conversion between numbers. This is usually not a good idea."_

为什么不好？因为隐式转换会带来：

- **精度丢失**：`Double` 转 `Int` 截断小数部分
    
- **语义模糊**：`5 / 2` 到底得到 `2` 还是 `2.5`？
    
- **性能陷阱**：隐式转换可能在热点路径上悄悄发生
    

Haskell 选择**显式转换**——你明确写 `fromIntegral`，编译器就明确知道你要做什么，类型安全得以保持。

### 🔑 洞见十六：类型默认规则（Defaulting）—— 为了 GHCi 的可用性

既然字面量类型是重载的，`7 + 3.5` 的类型应该是 `(Num a, Fractional a) => a`——但 GHCi 必须给它一个具体类型才能打印结果。Haskell 的报告规定了一套**默认规则**：

- 在 `Num` 约束下，默认选择 `Integer`
    
- 在 `Fractional` 约束下，默认选择 `Double`
    

这就是为什么你在 GHCi 里输入 `7 + 3.5` 会得到 `Double` 类型的结果。

> 💡 默认规则是"工程妥协"——纯理论上 `(Num a, Fractional a) => a` 是合法的多态类型，但为了交互式环境能打印值，Haskell 允许在特定上下文（如 GHCi 顶层、单态化点）应用默认规则。

### 🔑 洞见十七：Haskell 数字类型的"分工"

Prelude 里五个常用数字类型各有定位：

|类型|归属类型类|特点|适用场景|
|---|---|---|---|
|`Int`|`Num`, `Integral`|固定宽度机器整数（通常 64 位）|性能敏感、确定范围内的整数|
|`Integer`|`Num`, `Integral`|任意精度整数（bignum）|安全优先、可能溢出的场景|
|`Float`|`Num`, `Fractional`|单精度浮点|内存敏感|
|`Double`|`Num`, `Fractional`|双精度浮点|通用浮点计算|
|`Rational`|`Num`, `Fractional`|任意精度分数|无舍入误差|

**选择准则**：

- 不确定就用 `Integer`（不会溢出）
    
- 要快且确信不溢出就用 `Int`
    
- 浮点计算默认 `Double`
    
- 需要精确分数运算用 `Rational`
    

### 实际应用

```
-- 泛型数值函数
halve :: (Fractional a) => a -> a
halve x = x * 0.5  -- 0.5 是 Fractional 字面量

-- 显式转换
sqrtOfLength :: [a] -> Double
sqrtOfLength xs = sqrt (fromIntegral (length xs))

-- 整数除法 vs 浮点除法
10 `div` 3  -- 3（Integral）
10 / 3      -- 3.333...（Fractional，要求操作数是 Fractional）

-- 浮点转整数
floor 3.7    -- 3
ceiling 3.2  -- 4
round 3.5    -- 4
truncate 3.9 -- 3
```


**本章给你四件行李**：

1. **数字运算是类型类方法，不是语法**——`+`、`-`、`*`、`/` 全是通过 `Num` 及其子类实现的重载函数
    
2. **数字字面量是重载的**——`7` 的类型是 `Num a => a`，通过 `fromInteger` 实现；`7.3` 的类型是 `Fractional a => a`，通过 `fromRational` 实现
    
3. **Haskell 绝不隐式转换**——`Int` 和 `Double` 不能直接相加，必须显式 `fromIntegral`
    
4. **类型类层级反映了"数字能力"的分解**——`Num` 是总父类，`Integral` 管整数，`Fractional` 管分数，`Floating` 管浮点函数

## 📝 本章核心洞见总结

> **洞见一：数字运算在 Haskell 里是"伪装成语法的类型类方法"**。
> 
> 这不是实现细节，而是核心设计哲学——它让数字运算获得了类型类带来的一切好处：重载、可扩展、类型安全。自定义类型只要实现 `Num` 实例，就能用 `+`、`-`、`*` 和字面量。

> **洞见二：类型类层级反映了"数字能力"的精细分解**。
> 
> `Num` 提供通用运算，`Integral` 加整数除法，`Fractional` 加分数除法，`Floating` 加超越函数。这种分解让"复数不能有 `Ord`"、"整数不能用 `/`" 这类约束在编译期就被强制执行。

> **洞见三：数字字面量的重载是类型类威力的极致展示**。
> 
> `7` 的类型是 `Num a => a`，意味着同一个字面量可以是 `Int`、`Integer`、`Float`、`Double`、甚至是你的自定义 `Num` 实例。这是通过 `fromInteger` 实现的——而 `fromInteger` 正是 `Num` 类的方法。

> **洞见四：Haskell 拒绝隐式类型转换，是"类型安全高于便利"的庄严宣言**。
> 
> `fromIntegral` 是 `Integral` 到 `Num` 的显式桥梁，它的存在时刻提醒你：类型转换是有语义后果的，必须显式表达。这避免了 C/Java 里静默截断、精度丢失的万恶之源。

> **洞见五：data 声明前不加约束，是类型类"行为解耦"纪律的体现**。
> 
> 约束应该加在函数上，而不是数据上。这保持了"数据定义"和"行为定义"的独立，让类型类能灵活组合。

> **洞见六：`Enum` + `Bounded` 是值域的"类型级描述"**。
> 
> `Enum` 让类型可枚举（`[1..10]` 语法），`Bounded` 让类型有上下界。两者结合，让编译器能在类型层面理解"这个值域有多大"——为测试生成、穷举搜索等场景提供基础。

> **洞见七：`Ord` 的 Deriving 规则体现了"约定优于配置"**。
> 
> 按构造子声明顺序比较，让 `deriving (Ord)` 永远产生确定、可预测的结果。这是 Haskell "make illegal states unrepresentable" 哲学的延伸。

## 🛠️ 实践建议

1. **永远用 `fromIntegral` 桥接整型和浮点型**：
    
    ```
    -- ❌ 错误
    sqrt (length xs)
    
    -- ✅ 正确
    sqrt (fromIntegral (length xs))
    ```
    
2. **泛型数值函数优先用类型类约束**：
    
    ```
    -- 好：可用于任何 Num 类型
    double :: Num a => a -> a
    double x = x * 2
    
    -- 差：只能用 Double
    double :: Double -> Double
    double x = x * 2
    ```
    
3. **自定义数值类型时实现 `Num` 实例**：
    
    ```
    newtype Meter = Meter Double deriving (Eq, Ord)
    
    instance Num Meter where
      Meter x + Meter y = Meter (x + y)
      Meter x * Meter y = Meter (x * y)
      -- ... 其他方法
      fromInteger n = Meter (fromInteger n)
    
    -- 现在可以直接写：Meter 5 + Meter 3
    ```
    
4. **`Int` vs `Integer` 的选择准则**：
    
    - 默认用 `Integer`（不会溢出）
        
    - 性能敏感且确信范围安全时用 `Int`
        
    - 不要用 `Int` 存储可能很大的计数（如文件大小、数据库 ID）
        
    
5. **`data` 声明前不要加约束**：
    
    ```
    -- ❌ 错误
    data (Ord a) => Tree a = Empty | Node a (Tree a) (Tree a)
    
    -- ✅ 正确
    data Tree a = Empty | Node a (Tree a) (Tree a)
    
    insert :: Ord a => a -> Tree a -> Tree a
    insert x tree = ...
    ```
    
6. **利用 `Enum` + `Bounded` 做穷举测试**：
    
    ```
    allValues :: (Enum a, Bounded a) => [a]
    allValues = [minBound .. maxBound]
    
    -- 测试 Bool 的所有可能
    allBools = allValues :: [Bool]  -- [False, True]
    ```
