## 🎯 全局脉络：并行 vs 并发——Haskell 的精确术语

GHC 用户指南开宗明义地定义了这两个术语 ：

> _"Parallelism means running a Haskell program on multiple processors, with the goal of improving performance. Ideally, this should be done invisibly, and with no semantic changes. Concurrency means implementing a program by using multiple I/O-performing threads. While a concurrent Haskell program can run on a parallel machine, the primary goal of using concurrency is not to gain performance, but rather because that is the simplest and most direct way to write the program. Since the threads perform I/O, the semantics of the program is necessarily non-deterministic."_

**🔑 洞见一：并行与并发的目标完全不同**

|维度|并行（Parallelism）|并发（Concurrency）|
|---|---|---|
|目标|提升性能|结构化 IO 程序|
|语义|无语义变化（纯计算）|必然非确定性（IO）|
|典型场景|数值计算、数据处理|Web 服务器、UI、网络|
|Haskell 机制|`par`/`pseq`、Strategies|`forkIO`、MVar、STM、async|
|编译/运行|`-threaded` + `+RTS -N`|默认启用|

Haskell.org 的官方描述印证了这一点 ：

> _"Squeeze out the last ticks of your multi-core processors, thanks to best-in-class support for async, concurrent and parallel programming... made possible via garbage collection and green threads."_

## 30.1 运行时工作原理：M:N 调度与 Spark 队列

### GHC 的 M:N 线程模型

Well-Typed 的文章揭示了 GHC 运行时的核心架构 ：

> _"the GHC runtime system uses what is known as a M:N threading model, where many Haskell threads are scheduled across a much smaller number of operating system threads. This model has two key benefits: it can make use of multiple CPU cores; it allows Haskell threads to be very cheap."_

**🔑 洞见二：Haskell 线程极其轻量**

Don Stewart 的数据 ：

- **CPU 核心**：少数几个
    
- **OS 线程**：十几个
    
- **Haskell 线程**：数万个
    
- **Spark（并行火花）**：数百万个
    

每个 Haskell 线程初始仅消耗约 1KB 内存 。这意味着你可以 fork 成千上万个线程而无需担心系统资源耗尽。

### 运行时调度机制

GHC 用户指南详细描述了调度器 ：

> _"Runnable threads are scheduled in round-robin fashion. Context switches are signalled by the generation of new sparks or by the expiry of a virtual timer... When a context switch occurs, pending sparks which have not already been reduced to weak head normal form are turned into new threads."_

**🔑 洞见三：Spark 不是立即执行的**

并行 Haskell 文档指出 ：

> _"Implicit parallelism via sparks... If the runtime detects that there is an idle CPU, then it may convert a spark into a real thread, and run the new thread on the idle CPU."_

Spark 的关键特性：

- **FIFO 队列**：Spark 按 FIFO 顺序排队，但不立即执行
    
- **惰性转换**：只有当运行时检测到空闲 CPU 时，才把 Spark 转换为真实线程
    
- **线程数限制**：活跃线程数有上限（默认 32），可用 `-t<num>` 调整
    
- **溢出处理**：超过限制的 Spark 会被延迟到已有线程完成
    

### 多核并行：`-threaded` 与 `-N`

Parallel Haskell 文档 ：

> _"By default GHC runs your program on one processor; if you want it to run in parallel you must link your program with the -threaded, and run it with the RTS -N ⟨x⟩ option... The runtime will schedule the running Haskell threads among the available OS threads, running as many in parallel as you specified with the -N ⟨x⟩ RTS option."_

**🔑 洞见四：并行需要显式启用**

```
# 编译时启用多线程运行时
ghc -threaded -O2 MyProgram.hs

# 运行时指定核心数
./MyProgram +RTS -N4    # 使用 4 个核心
./MyProgram +RTS -N     # 使用所有可用核心
```

IIJ 的技术文章给出了生产环境的实证 ：

> _"GHC で並行プログラムをコンパイルするときは、必ず -threaded オプションを付けてください"_（编译并发程序时务必使用 -threaded 选项）

他们用 GHC 7.8.4 的 IO 管理器改良，让 Haskell Web 服务器真正在多核上线性扩展 。

### Spark 调度的实际考量

GHC Trac #14330 揭示了一个重要现象 ：

> _"Sparks are not started promptly... By default, this happens every 20ms."_

**🔑 洞见五：Spark 的启动延迟可能影响细粒度并行**

对于 spark 数量少、每个 spark 计算量小的场景，默认的 20ms 调度间隔会导致 spark "fizzle"（失效）。解决方案：

```
# 调整调度间隔为 1ms
./program +RTS -N6 -C0.001
```

但这个方法不实用（用户不会主动调 RTS 参数），因此**并行粒度的设计非常关键**——每个 spark 应有足够的计算量来摊销调度开销。

## 30.2 并行编程：par/pseq 与 Strategies

### par 与 pseq 的基本用法

GHC 用户指南 ：

```
import Control.Parallel

infixr 0 `par`
infixr 1 `pseq`

par :: a -> b -> b
pseq :: a -> b -> b
```

**语义**：

- `x`par`y`：spark 对 x 的求值（到 WHNF），返回 y
    
- `x`pseq`y`：强制求值 x 到 WHNF，然后返回 y
    

### 经典示例：并行 nfib

GHC 用户指南给出的 nfib ：

```
import Control.Parallel

nfib :: Int -> Int
nfib n | n <= 1 = 1
       | otherwise = par n1 (pseq n2 (n1 + n2))
  where
    n1 = nfib (n-1)
    n2 = nfib (n-2)
```

**🔑 洞见六：par/pseq 的"分治"模式**

GHC 用户指南的解释 ：

> _"For values of n greater than 1, we use par to spark a thread to evaluate nfib (n-1), and then we use pseq to force the parent thread to evaluate nfib (n-2) before going on to add together these two subexpressions."_

**关键设计要点**：

1. **只 spark 一个分支**：父线程自己算另一个分支（避免线程爆炸）
    
2. **pseq 确保求值顺序**：保证 n2 在 n1+n2 之前被求值
    
3. **spark 到 WHNF**：`par` 只保证求值到弱头正常形式
    

### Strategies：更高层的并行抽象

虽然搜索材料未直接命中 Strategies 的细节，但基于 GHC 用户指南的线索 ：

> *"Concurrent threads (forkIO) will run in parallel, and you can also use the par combinator and Strategies from the Control.Parallel.Strategies module to create parallelism."

**典型模式**：

```
import Control.Parallel.Strategies

-- 并行 map
parMap :: (a -> b) -> [a] -> [b]
parMap f xs = map f xs `using` parList rdeepseq

-- 并行策略
parList :: Strategy a -> Strategy [a]
rdeepseq :: NFData a => Strategy a
```

### 🔑 洞见七：普通程序不会自动并行

GHC 用户指南的重要警告 ：

> _"Ordinary single-threaded Haskell programs will not benefit from enabling SMP parallelism alone: you must expose parallelism to the compiler."_

**这意味着**：仅仅用 `-threaded` 编译并 `-N` 运行是不够的——你必须在代码中显式使用 `par`、Strategies 或 `forkIO` 来暴露并行性。

### 实际应用

```
import Control.Parallel
import Control.Parallel.Strategies

-- 1. 手动 par/pseq：计算两个独立的大任务
heavyTask1 :: Int
heavyTask1 = sum [1..10000000]

heavyTask2 :: Int
heavyTask2 = product [1..5000]

combined :: Int
combined = heavyTask1 `par` (heavyTask2 `pseq` heavyTask1 + heavyTask2)

-- 2. 使用 Strategies 并行化列表处理
parallelProcess :: [Int] -> [Int]
parallelProcess = map (^2) `using` parList rdeepseq

-- 3. 并行矩阵运算（示意）
parallelMatrixMult :: [[Int]] -> [[Int]] -> [[Int]]
parallelMatrixMult a b = 
  let bT = transpose b
  in map (\row -> map (\col -> sum $ zipWith (*) row col) bT) a
     `using` parList rdeepseq

-- 4. 编译和运行
-- ghc -threaded -O2 -rtsopts ParallelExample.hs
-- ./ParallelExample +RTS -N4 -s
```

## 30.3 并发编程：从 MVar 到 async 的三层抽象

### 并发的基石：forkIO

GHC 用户指南 ：

> _"To the programmer, Concurrent Haskell introduces no new language constructs; rather, it appears simply as a library, Control.Concurrent."_

**核心函数**：

```
forkIO :: IO () -> IO ThreadId
```

UMD 教程精辟描述 ：

> _"forkIO is similar to fork from CMSC216 except we don't have to worry about figuring out which thread is the parent and which is the child, with forkIO we are always the parent and the child thread gets spawned off."_

### 🔑 洞见八：forkIO 创建的是轻量级线程

```
import Control.Concurrent

main :: IO ()
main = do
  forkIO $ print "Hello from a thread!"
  print "Hello from the main thread!"
  -- 主线程退出，整个程序立即终止（不会等待子线程）
```

**关键陷阱**：主线程退出时，整个程序立即终止，不会等待其他线程完成 。

### 30.3.1 MVar：同步的"单槽盒子"

#### MVar 的本质

UMD 教程的定义 ：

> _"An MVar a can be viewed as a container containing a value of type a, but the implementation of MVar ensures that only one entity has access to that value at any given time."_

**MVar 的 API**（UMD 教程 ）：

```
newEmptyMVar :: IO (MVar a)
newMVar :: a -> IO (MVar a)
putMVar :: MVar a -> a -> IO ()
takeMVar :: MVar a -> IO a
```

#### 阻塞语义

UMD 教程明确描述 ：

> _"If you call putMVar on an MVar that already has a value, the current thread will block until the MVar is empty. If you call takeMVar on an MVar that is empty, the current thread will block until the MVar contains a value."_

**🔑 洞见九：MVar 是"空或满"的单槽盒子**

|操作|MVar 为空|MVar 为满|
|---|---|---|
|`takeMVar`|阻塞，等待值|取出值，MVar 变空|
|`putMVar`|放入值，MVar 变满|阻塞，等待变空|
|`readMVar`|阻塞，等待值|读取值，MVar 仍为满|

#### MVar 的公平性

smunix 的文章 ：

> _"MVar implementation is fair in such a way that it blocks threads in a FIFO queue which provides some guarantees that as long as values are repeatedly replaced in a variable, all threads are gettings eventually unblocked."_

#### MVar 的典型应用

**1. 线程间通信（Channel 模式）**

Real World Haskell 给出了经典的 Logger 示例 ：

```
data Logger = Logger (MVar LogCommand)

data LogCommand = Message String | Stop (MVar ())

initLogger :: IO Logger
initLogger = do
  m <- newEmptyMVar
  forkIO $ loop m
  return (Logger m)
  where
    loop m = do
      cmd <- takeMVar m
      case cmd of
        Message msg -> do
          putStrLn msg
          loop m
        Stop s -> do
          putStrLn "logger: stop"
          putMVar s ()
```

**2. 共享状态容器**

Real World Haskell 展示了用 MVar 包装不可变数据结构 ：

> _"We can take any pure immutable data structure such as Map and turn it into mutable shared state by simply wrapping it in an MVar. Using immutable data structures in a mutable wrapper has further benefits."_

```
import qualified Data.Map.Strict as Map

data Container = Container { counters :: MVar (Map.Map String Int) }

inc :: Container -> String -> IO ()
inc container name = 
  modifyMVar_ (counters container) $ \m ->
    return $ Map.insertWith (+) name 1 m
```

**3. 死锁风险**

Devtut 教程给出了经典的死锁示例 ：

```
concurrent ma mb = do
  a <- takeMVar ma
  b <- takeMVar mb
  putMVar ma a
  putMVar mb b

-- 如果两个线程以相反顺序调用：
-- Thread 1: concurrent ma mb
-- Thread 2: concurrent mb ma
-- 结果：Thread 1 持有 ma 等待 mb，Thread 2 持有 mb 等待 ma → 死锁！
```

**🔑 洞见十：MVar 是低层同步原语，需要谨慎使用**

smunix 的文章 ：

> _"Pitfalls of using low-level concurrency abstractions: Deadlocks, Resource management"_

**解决方案**：使用 `withMVar` 和 `modifyMVar` 等异常安全版本，确保即使发生异常也能释放锁 。

### 30.3.2 STM：可组合的软件事务内存

#### STM 的核心思想

School of Haskell 的教程 ：

> _"Atomic blocks... In STM, memory operations occur in transactions, which can be composed and, if any part fails, the entire transaction is retried."_

**核心 API**：

```
import Control.Concurrent.STM

atomically :: STM a -> IO a
newTVar :: a -> STM (TVar a)
readTVar :: TVar a -> STM a
writeTVar :: TVar a -> a -> STM ()

retry :: STM a
orElse :: STM a -> STM a -> STM a
```

#### retry：阻塞与组合

School of Haskell 教程 ：

```
limitedWithdraw :: Account -> Int -> STM ()
limitedWithdraw acc amount = do
  bal <- readTVar acc
  if amount > 0 && amount > bal
    then retry
    else writeTVar acc (bal - amount)
```

**🔑 洞见十一：retry 的魔力**

School of Haskell 解释 ：

> _"When retry is called, the thread blocks until one of the TVars read by the transaction is modified by another thread."_

**RWH 的中文版进一步阐释**​ ：

> _"当我们调用 retry 的时候，它并不是马上重启事务，而是会先阻塞线程，一直到那些在 retry 之前被访问过的变量被其他线程修改。"_

#### orElse：事务的选择组合

School of Haskell 教程 ：

```
limitedWithdraw2 :: Account -> Account -> Int -> STM ()
limitedWithdraw2 acc1 acc2 amt = 
  orElse (limitedWithdraw acc1 amt) (limitedWithdraw acc2 amt)
```

**🔑 洞见十二：orElse 提供事务的组合性**

School of Haskell 解释 ：

> _"The action (orElse a1 a2) first performs a1; if a1 retries, it tries a2 instead; if a2 also retries, the whole action retries."_

**这是 STM 相比锁的最大优势**——事务可以任意组合，而锁的组合容易导致死锁。

#### STM 的类型安全保证

School of Haskell 教程的关键洞察 ：

> _"Since the atomic block is executed without taking locks, it might have an inconsistent view of memory if other threads are concurrently modifying xv and yv... the type system prevents us running IO actions inside STM actions."_

**🔑 洞见十三：STM 中不能有 IO**

```
-- ❌ 编译错误
badAction :: TVar Int -> STM ()
badAction tv = do
  val <- readTVar tv
  launchMissiles  -- IO 操作，不允许！
  writeTVar tv (val + 1)

-- ✅ 正确：IO 操作在 atomically 之外
goodAction :: TVar Int -> IO ()
goodAction tv = do
  val <- atomically $ readTVar tv
  when (val > threshold) $ launchMissiles
  atomically $ writeTVar tv (val + 1)
```

**类型系统保证了 STM 事务的纯洁性**——这是 Haskell 类型系统在并发领域的威力展现。

#### STM 的实战示例

基于 School of Haskell 教程 ：

```
import Control.Concurrent.STM
import Control.Concurrent

type Account = TVar Int

-- 转账：多变量事务
transfer :: Account -> Account -> Int -> STM ()
transfer from to amount = do
  fromBal <- readTVar from
  if fromBal >= amount
    then do
      writeTVar from (fromBal - amount)
      toBal <- readTVar to
      writeTVar to (toBal + amount)
    else retry

-- 带超时的取款
limitedWithdraw :: Account -> Int -> STM ()
limitedWithdraw acc amount = do
  bal <- readTVar acc
  if amount > 0 && amount <= bal
    then writeTVar acc (bal - amount)
    else retry

-- 多账户选择
limitedWithdraw2 :: Account -> Account -> Int -> STM ()
limitedWithdraw2 acc1 acc2 amt = 
  orElse (limitedWithdraw acc1 amt) (limitedWithdraw acc2 amt)

-- 使用 check 组合
check :: Bool -> STM ()
check True = return ()
check False = retry

limitedWithdraw' :: Account -> Int -> STM ()
limitedWithdraw' acc amount = do
  bal <- readTVar acc
  check (amount > 0 && amount <= bal)
  writeTVar acc (bal - amount)

-- 运行
main :: IO ()
main = do
  acc1 <- atomically (newTVar 100)
  acc2 <- atomically (newTVar 100)
  
  -- 转账
  atomically $ transfer acc1 acc2 50
  
  -- 并发存款
  forkIO $ atomically $ do
    bal <- readTVar acc1
    writeTVar acc1 (bal + 100)
  
  -- 等待并取款
  threadDelay 1000000
  atomically $ limitedWithdraw2 acc1 acc2 30
  
  -- 读取最终余额
  final1 <- atomically $ readTVar acc1
  final2 <- atomically $ readTVar acc2
  print (final1, final2)
```

### 30.3.3 async：工程化的异步任务管理

#### async 库的核心抽象

Simon Marlow 的 async 库将异步任务抽象为一级公民 。

**核心 API**：

```
import Control.Concurrent.Async

async :: IO a -> IO (Async a)
wait :: Async a -> IO a
waitAny :: [Async a] -> IO (Async a, a)
waitAll :: [Async a] -> IO [a]
```

#### 基本用法

基于 async 教程 ：

```
import Control.Concurrent.Async

main :: IO ()
main = do
  putStrLn "Starting asynchronous task..."
  a <- async $ do
    threadDelay 1000000
    return "Task completed!"
  result <- wait a
  putStrLn result
```

#### 并发下载：async 的杀手锏应用

async 教程 给出了完美的示例：

```
import Control.Concurrent.Async
import Network.HTTP.Client

fetchData :: String -> IO String
fetchData url = do
  response <- httpLBS (parseRequest_ url)
  return $ "Fetched data from " ++ url

main :: IO ()
main = do
  let urls = ["http://example.com", "http://example.org"]
  asyncs <- mapM (async . fetchData) urls
  results <- mapM wait asyncs
  mapM_ putStrLn results
```

**🔑 洞见十四：async 让"spawn-then-wait"模式变得优雅**

Simon Marlow 在 async 库的 24 Days of Hackage 文章中 ：

> _"Fundamentally, async offers us a handful of routines that enable us to treat concurrent work as a first class citizen. That is - a concurrent job can be passed around in a value, its state inspected and final result extracted."_

#### async 的异常处理

24 Days of Hackage 文章 ：

> _"With Async values though, we can easily inspect a computation to see if it failed or not. The semantics of wait that we saw earlier is to rethrow any exceptions of the asynchronous computation."_

**关键函数**：

```
waitCatch :: Async a -> IO (Either SomeException a)
```

```
main :: IO ()
main = do
  a <- async $ do
    threadDelay 1000000
    throwIO (userError "Task failed!")
  result <- waitCatch a
  case result of
    Left ex -> putStrLn $ "Task failed: " ++ show ex
    Right val -> putStrLn $ "Task succeeded: " ++ show val
```

#### async 的高级组合子

async 教程 ：

> _"Using mapConcurrently we can map over any Traversable concurrently, and using race we can race multiple computations until one of them completes."_

```
-- 并发映射
mapConcurrently :: Traversable t => (a -> IO b) -> t a -> IO (t b)

-- 竞速：第一个完成的胜出
race :: IO a -> IO b -> IO (Either a b)

-- 并发下载示例
concurrentDownloads :: [String] -> IO [String]
concurrentDownloads urls = do
  asyncs <- mapM (async . fetchData) urls
  mapM wait asyncs
```

#### 🔑 洞见十五：async 是并发编程的"最佳实践层"

async 文档明确指出 ：

> _"async is not a silver bullet... but once you've got a good idea for how you want to distribute work, async deals with the nitty-gritty details of exception handling and lets you focus on the interesting stuff."_

**async 解决了 forkIO 的三大痛点**：

1. **异常传播**：`wait` 重新抛出异步任务的异常
    
2. **资源管理**：异步任务与 Async 句柄关联，可被显式取消
    
3. **组合性**：`race`、`mapConcurrently` 等高阶组合子

2. **GHC 运行时用 M:N 调度**：Haskell 线程轻量（~1KB），Spark 队列实现惰性并行
    
3. **并行编程用 par/pseq**：必须显式暴露并行性，编译用 `-threaded`，运行用 `+RTS -N`
    
4. **MVar 是低层同步原语**：单槽盒子，空/满阻塞语义，可能死锁
    
5. **STM 提供可组合的事务内存**：retry/orElse 组合事务，类型系统阻止 IO 进入 STM
    
6. **async 是工程化的并发管理层**：async/wait/waitCatch/race/mapConcurrently 提供安全的任务生命周期管理

## 📝 本章核心洞见总结

> **洞见一：并行与并发的目标根本不同**。
> 
> GHC 用户指南："Parallelism means running a Haskell program on multiple processors, with the goal of improving performance... Concurrency means implementing a program by using multiple I/O-performing threads" 。**并行无语义变化（纯计算），并发必然非确定性（IO）**。

> **洞见二：Haskell 线程极其轻量**。
> 
> Well-Typed："many Haskell threads are scheduled across a much smaller number of operating system threads... it allows Haskell threads to be very cheap" 。**每个 Haskell 线程初始仅 1KB 内存**​ ，可轻松 fork 数万线程。

> **洞见三：Spark 不是立即执行的**。
> 
> GHC 用户指南："pending sparks which have not already been reduced to weak head normal form are turned into new threads" 。**Spark 按 FIFO 排队，只有当 CPU 空闲时才转换为真实线程**​ ；默认调度间隔 20ms，细粒度并行可能需要调整 `-C` 参数 。

> **洞见四：并行需要显式启用**。
> 
> Haskell.org："best-in-class support for async, concurrent and parallel programming... made possible via garbage collection and green threads" 。**编译用 `-threaded`，运行用 `+RTS -N`**​ ；GHC 默认单处理器，必须显式启用 SMP 并行 。

> **洞见五：普通程序不会自动并行**。
> 
> GHC 用户指南："Ordinary single-threaded Haskell programs will not benefit from enabling SMP parallelism alone: you must expose parallelism to the compiler" 。**必须使用 `par`、Strategies 或 `forkIO` 显式暴露并行性**。

> **洞见六：par/pseq 的分治模式**。
> 
> GHC 用户指南的 nfib 示例：用 `par` spark 一个分支，用 `pseq` 强制父线程计算另一个分支 。**只 spark 一个分支避免线程爆炸，pseq 确保求值顺序**。

> **洞见七：MVar 是"空或满"的单槽盒子**。
> 
> UMD 教程："An MVar a can be viewed as a container containing a value of type a" 。**`takeMVar` 在空时阻塞，`putMVar` 在满时阻塞**​ ；FIFO 公平队列保证不死锁单个线程 。

> **洞见八：MVar 可能死锁**。
> 
> Devtut 教程给出了经典死锁：两个线程以相反顺序获取两个 MVar 。**解决方案**：使用 `withMVar`/`modifyMVar` 等异常安全版本 。

> **洞见九：MVar 适合作为"共享状态容器"**。
> 
> Real World Haskell："We can take any pure immutable data structure such as Map and turn it into mutable shared state by simply wrapping it in an MVar" 。**用不可变数据结构 + MVar 包装，兼具安全性和并发性**。

> **洞见十：STM 提供可组合的事务内存**。
> 
> School of Haskell："memory operations occur in transactions, which can be composed and, if any part fails, the entire transaction is retried" 。**`retry` 阻塞直到事务读取的 TVar 被修改**​ ；`orElse` 组合多个事务选择 。

> **洞见十一：STM 中不能有 IO**。
> 
> School of Haskell："the type system prevents us running IO actions inside STM actions" 。**类型系统保证 STM 事务的纯洁性——这是 Haskell 类型系统在并发领域的威力展现**。

> **洞见十二：STM 避免锁的组合性陷阱**。
> 
> `orElse` 允许组合多个可能 retry 的事务 ，而锁的组合容易导致死锁。**这是 STM 相比 MVar 的核心优势**。

> **洞见十三：async 让异步任务成为一级公民**。
> 
> Simon Marlow："async offers us a handful of routines that enable us to treat concurrent work as a first class citizen" 。**Async 句柄可传递、可检查状态、可提取结果**。

> **洞见十四：async 解决 forkIO 的三大痛点**。
> 
> 24 Days of Hackage："async deals with the nitty-gritty details of exception handling" 。**异常传播（wait 重新抛出）、资源管理（显式取消）、组合性（race/mapConcurrently）**。

> **洞见十五：并发编程的抽象层级递进**。
> 
> **MVar（低层同步）→ STM（可组合事务）→ async（任务生命周期管理）**。每个层级都建立在前一层之上，提供更高层的抽象和安全性。

## 🛠️ 实践建议

1. **并行编程的标准流程**：
    
    ```
    import Control.Parallel
    import Control.Parallel.Strategies
    
    -- 编译：ghc -threaded -O2 -rtsopts ParExample.hs
    -- 运行：./ParExample +RTS -N4 -s
    
    -- 1. 使用 par/pseq 手动暴露并行
    parExample :: Int -> Int -> Int
    parExample x y = x `par` (y `pseq` x + y)
    
    -- 2. 使用 Strategies 并行化列表
    parallelProcess :: [Int] -> [Int]
    parallelProcess = map (^2) `using` parList rdeepseq
    
    -- 3. 并行映射
    parMap :: (a -> b) -> [a] -> [b]
    parMap f xs = map f xs `using` parList rdeepseq
    ```
    
2. **MVar 的安全使用**：
    
    ```
    import Control.Concurrent
    import Control.Concurrent.MVar
    
    -- ✅ 使用 withMVar 确保异常安全
    withMVar :: MVar a -> (a -> IO b) -> IO b
    safeUpdate :: MVar Int -> (Int -> Int) -> IO ()
    safeUpdate mvar f = withMVar mvar $ \val -> do
      let newVal = f val
      putMVar mvar newVal
    
    -- ✅ 使用 modifyMVar_ 原子更新
    modifyMVar_ :: MVar a -> (a -> IO a) -> IO ()
    atomicIncrement :: MVar Int -> IO ()
    atomicIncrement mvar = modifyMVar_ mvar $ \val -> return (val + 1)
    
    -- ❌ 避免：手动 takeMVar/putMVar（异常时可能死锁）
    unsafeUpdate :: MVar Int -> IO ()
    unsafeUpdate mvar = do
      val <- takeMVar mvar
      putMVar mvar (val + 1)  -- 如果这里抛出异常，MVar 永远无法释放
    ```
    
3. **STM 的事务组合**：
    
    ```
    import Control.Concurrent.STM
    
    -- 多变量事务
    transfer :: TVar Int -> TVar Int -> Int -> STM ()
    transfer from to amount = do
      fromBal <- readTVar from
      if fromBal >= amount
        then do
          writeTVar from (fromBal - amount)
          toBal <- readTVar to
          writeTVar to (toBal + amount)
        else retry
    
    -- 事务组合 with orElse
    tryWithdraw :: TVar Int -> TVar Int -> Int -> STM Bool
    tryWithdraw acc1 acc2 amount =
      (do limitedWithdraw acc1 amount
          return True)
      `orElse`
      (do limitedWithdraw acc2 amount
          return True)
      `orElse`
      return False
    
    -- 运行事务
    runTransaction :: STM a -> IO a
    runTransaction = atomically
    ```
    
4. **async 的并发任务管理**：
    
    ```
    import Control.Concurrent.Async
    import Control.Concurrent
    
    -- 1. 基本异步任务
    doAsyncWork :: IO a -> IO (Async a)
    doAsyncWork action = async action
    
    -- 2. 等待结果（重新抛出异步异常）
    waitForResult :: Async a -> IO a
    waitForResult = wait
    
    -- 3. 等待并捕获异常
    waitSafely :: Async a -> IO (Either SomeException a)
    waitSafely = waitCatch
    
    -- 4. 并发映射
    concurrentMap :: (a -> IO b) -> [a] -> IO [b]
    concurrentMap f xs = do
      asyncs <- mapM (async . f) xs
      mapM wait asyncs
    
    -- 5. 竞速：第一个完成者胜出
    raceTasks :: IO a -> IO b -> IO (Either a b)
    raceTasks = race
    
    -- 6. 并发下载示例
    fetchURLs :: [String] -> IO [String]
    fetchURLs urls = do
      asyncs <- mapM (async . fetchData) urls
      mapM wait asyncs
      where
        fetchData url = do
          response <- httpLBS (parseRequest_ url)
          return $ "Fetched " ++ url ++ ": " ++ show (B.length response)
    ```
    
5. **完整的并发应用示例**：
    
    ```
    import Control.Concurrent.Async
    import Control.Concurrent.STM
    import Control.Concurrent.MVar
    
    -- Web 爬虫：并发下载 + STM 共享状态
    data CrawlerState = CrawlerState
      { visitedUrls :: TVar (Set String)
      , urlQueue :: TChan String
      , results :: MVar [String]
      }
    
    -- 并发爬取
    crawlUrls :: [String] -> IO [String]
    crawlUrls seedUrls = do
      -- 共享状态
      visited <- atomically $ newTVar Set.empty
      queue <- atomically $ newTChan
      resultsVar <- newMVar []
    
      -- 种子 URL 入队
      atomically $ forM_ seedUrls $ \url -> writeTChan queue url
    
      -- 启动 N 个工作线程
      let numWorkers = 4
      workers <- replicateM numWorkers $ async $ worker 
        (CrawlerState visited queue resultsVar)
    
      -- 等待所有工作线程完成
      mapM_ wait workers
    
      -- 收集结果
      reverse <$> readMVar resultsVar
    
    -- 工作线程
    worker :: CrawlerState -> IO ()
    worker state@(CrawlerState visited queue resultsVar) = do
      mUrl <- atomically $ do
        isEmpty <- isEmptyTChan queue
        if isEmpty
          then return Nothing
          else Just <$> readTChan queue
    
      case mUrl of
        Nothing -> return ()
        Just url -> do
          -- 检查是否已访问
          alreadyVisited <- atomically $ do
            visitedSet <- readTVar visited
            if Set.member url visitedSet
              then return True
              else do
                writeTVar visited (Set.insert url visitedSet)
                return False
    
          if alreadyVisited
            then worker state
            else do
              -- 下载页面
              page <- downloadPage url
    
              -- 提取链接并入队
              let links = extractLinks page
              atomically $ forM_ links $ \link -> writeTChan queue link
    
              -- 保存结果
              modifyMVar_ resultsVar $ \results -> return (page : results)
    
              -- 继续工作
              worker state
    ```
