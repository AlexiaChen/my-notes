## 🎯 全局脉络：为什么"语言扩展 + 程序标注"是 Haskell 工程的基石？

```
第一部分: Haskell 核心语言（类型、函数、类型类）
   ↓
第二部分: 抽象机制（Functor/Applicative/Monad/IO）
   ↓
第三部分: 高级类型类和项目实践  ← 第二十一章在这里
   ↓
第22-27章: Foldable/Traversable、数组散列表、
          Monad 变换、字符串处理、网络编程
```

**这一章是整本书"从正确到高效"的转折点**。前二十章你学的所有内容，都是用"标准 Haskell"表达的。但真实工程会遇到标准 Haskell 表达力不足或性能不够的场景：

- 需要更强的类型级编程 → `TypeFamilies`、`GADTs`、`DataKinds`
    
- 需要控制求值严格性以消除空间泄漏 → `BangPatterns`、`StrictData`、`Strict`
    
- 需要给编译器提示以生成更高效代码 → `INLINE`/`INLINABLE`/`SPECIALIZE` 标注
    
- 需要跨模块优化 → `-O2` 编译选项
    
- 需要定位性能瓶颈 → `+RTS -p` 运行分析
    

稀土掘金上的现代 Haskell 教程总结得精辟 ：

> _"GHC 扩展的本质是：在保证 Haskell 强类型安全的前提下，突破标准语法的限制，解决实际开发中的'表达力不足'问题。所有扩展都需要手动开启（如 `{-# LANGUAGE TypeApplications #-}`），核心原则是'按需开启，够用就好'。"_

**"按需开启，够用就好"**——这是 Haskell 社区使用语言扩展的金科玉律。

## 21.1 语言扩展：突破标准语法的限制

### 扩展的声明方式

Haskell 源文件顶部用 `LANGUAGE` 编译指示开启扩展：

```
{-# LANGUAGE BangPatterns #-}
{-# LANGUAGE StrictData #-}
{-# LANGUAGE TypeApplications #-}
{-# LANGUAGE GADTs #-}
{-# LANGUAGE TypeFamilies #-}
```

### 🔑 洞见一：扩展是"按需开启"的

现代 Haskell（GHC2021/GHC2024）已经默认开启了一部分常用扩展（如 `BangPatterns` ），但更激进的扩展仍需显式声明。

**扩展的核心价值**​ ：

|扩展|解决的问题|
|---|---|
|`TypeApplications`|精确控制类型推断，避免歧义|
|`GADTs`|让类型系统追踪更多 invariants|
|`TypeFamilies`|类型级函数|
|`BangPatterns`|控制求值严格性|
|`StrictData`|按模块让构造字段默认严格|

### 🔑 洞见二：扩展的"经济性"原则

稀土掘金教程明确指出 ：

> _"核心原则是'按需开启，够用就好'。"_

**过度使用扩展的代价**：

- 代码可读性下降（读者需要了解每个扩展的语义）
    
- 与其他 Haskell 代码互操作性降低
    
- 未来 GHC 版本兼容性风险
    

**实践建议**：

```
-- ✅ 好的做法：只开启真正需要的扩展
{-# LANGUAGE BangPatterns #-}
{-# LANGUAGE OverloadedStrings #-}

-- ❌ 坏的做法：开启一堆用不到的扩展
{-# LANGUAGE BangPatterns, StrictData, GADTs, TypeFamilies, 
             DataKinds, PolyKinds, KindSignatures, ... #-}
```

## 21.2 严格求值数据项：用 `!` 控制求值

### 问题：惰性求值可能导致空间泄漏

Haskell 默认是惰性的——这可能导致"thunk 堆积"的空间泄漏。高性能 Haskell 代码（特别是数值计算）需要消除内部循环中的 thunk 。

### BangPatterns 扩展

GHC 用户指南 ：

```
{-# LANGUAGE BangPatterns #-}

-- 严格模式：!x 表示在模式匹配前，先把 x 求值到弱头正常形式（WHNF）
f1 !x = True
-- f1 在 x 上是严格的，而如果没有 !，它就是惰性的

-- 嵌套 bang 模式
f2 (!x, y) = [x, y]
-- f2 在 x 上严格，但在 y 上不严格
```

**🔑 洞见三：BangPatterns 不改变类型系统**

GHC 用户指南明确指出 ：

> _"Bang patterns and strict matching do not affect the type system in any way."_

`!` 只是一个"求值提示"——它告诉编译器"在这里强制求值"，但不影响类型。

### 严格数据字段

```
{-# LANGUAGE BangPatterns #-}

-- 构造函数的字段可以是严格的
data User = User
  { identifier :: !Int      -- 严格字段
  , firstName :: !Text      -- 严格字段
  , lastName  :: Text       -- 惰性字段
  }

data T = MkT !Int !Int      -- 两个字段都是严格的
```

**🔑 洞见四：严格字段在构造时求值到 WHNF**

GHC 用户指南 ：

> _"When the data constructor is applied, those fields will be evaluated to weak head normal form, so the data in the fields is guaranteed to always be in weak head normal form."_

这意味着：当你构造 `User 42 "Alice" "Smith"` 时，`42` 会被立即求值（它已经是 WHNF），但 `"Alice"` 和 `"Smith"` 作为 `Text` 值，它们的"内容"是否完全求值取决于 `Text` 本身的内部表示。关键是——**严格字段保证没有 thunk 堆积在字段位置上**。

### StrictData 扩展

如果你希望整个模块的所有数据字段都默认严格：

```
{-# LANGUAGE StrictData #-}

-- 这个模块中，所有构造字段默认都是严格的（除非显式用 ~ 标记）
data Point = Point Int Int  -- 两个字段都是严格的

-- 等价于：
data Point = Point !Int !Int
```

GHC 用户指南 ：

> _"Strict data types (StrictData) makes constructor fields strict by default, on a per-module basis."_

### Strict 扩展：全局严格化

更激进的扩展：

```
{-# LANGUAGE Strict #-}

-- 这个模块中：
-- 1. 所有函数参数默认严格：f x = ... 被解释为 f !x = ...
-- 2. 所有 let/where 绑定默认严格：let x = ... 被解释为 let !x = ...
-- 3. 所有构造字段默认严格（Strict 隐含 StrictData）
-- 4. case 表达式的最外层模式默认严格
```

GHC 用户指南 ：

> _"Strict pattern (Strict) makes all patterns and let bindings strict by default, on a per-module basis. The latter two extensions are simply a way to avoid littering high-performance code with bang patterns, making it harder to read."_

### 🔑 洞见五：严格性扩展的"模块化"边界

GHC 用户指南明确指出 ：

> _"Strict and StrictData only affects definitions in the module they are used in. Functions and data types imported from other modules are unaffected."_

**这意味着**：`Strict` 和 `StrictData` 是"按模块"生效的。即使你在一个模块中开启了 `StrictData`，从其他模块导入的数据类型**不会**突然变成严格字段——它们的严格性由定义它们的模块决定。这是 Haskell 保持"正确性"的关键设计——严格性改变不能悄悄跨越模块边界破坏语义。

### 实际应用：消除空间泄漏

h2.jaguarpaw.co.uk 的文章给出了经典例子 ：

```
-- 有空间泄漏的版本
pairFoldBad :: (Integer, Integer)
pairFoldBad = foldl' f (0, 0) [1..million]
  where f (count, theSum) x = (count + 1, theSum + x)
-- 问题：每个组件都是 thunk，累积百万层深

-- 用 BangPatterns 修复
pairFoldBangs :: (Integer, Integer)
pairFoldBangs = foldl' f (0, 0) [1..million]
  where f (!count, !theSum) x = (count + 1, theSum + x)
-- 每次循环都强制求值 count 和 theSum，无空间泄漏
```

## 21.3 惰性模式：用 `~` 延迟匹配

### 惰性模式（Irrefutable Patterns）

Haskell 官方教程 ：

```
-- 惰性模式语法：~pat
-- 惰性模式总是匹配成功，无论 pat 是否能匹配值
f1 ~(Right 1) = 42
-- f1 (Right 1) = 42  -- 惰性模式版本
-- f1 (Right 2) = 42  -- 也返回 42！
-- f1 (Left "foo") = 42  -- 也返回 42！
-- f1 (error "oops!") = 42  -- 也返回 42！
```

**🔑 洞见六：惰性模式是"不可反驳的"**

Haskell 官方教程 ：

> _"Lazy patterns are irrefutable: matching a value v against ~pat always succeeds, regardless of pat. Operationally speaking, if an identifier in pat is later 'used' on the right-hand-side, it will be bound to that portion of the value that would result if v were to successfully match pat, and _ _ otherwise."_

**关键语义**：

1. `~pat` 匹配**总是成功**——即使值是 `undefined` 或 `error`
    
2. 绑定的变量在**右侧真正被使用时**才会被求值
    
3. 如果届时匹配失败（如 `~(Right x)` 匹配到 `Left`）→ 运行时异常
    

### 经典用例：递归定义的流

Haskell 官方教程给出了服务器/客户端模拟的经典例子 ：

```
-- 模拟服务器和客户端的消息流
reqs = client init resps
resps = server reqs

-- 问题版本：client 在提交第一个请求前就尝试匹配响应列表
client init (resp:resps) = init : client (next resp) resps
-- 这会导致死锁——client 需要先提交请求才能收到响应

-- 解决方案：用惰性模式
client init ~(resp:resps) = init : client (next resp) resps
-- ~ 让匹配立即成功，允许第一个请求被提交
-- 当 resp 在右侧被使用时，才真正强制匹配
```

**🔑 洞见七：惰性模式在"递归定义的无限数据结构"中是必需的**

Wikibooks 总结 ：

> _"Essentially, use lazy patterns when you only have the single constructor for the type, e.g. tuples. Multiple equations won't work nicely with irrefutable patterns."_

**典型应用场景**：

1. **相互递归的流**（服务器/客户端、生产者/消费者）
    
2. **递归数据结构的定义**（如 `let (x:xs) = 0 : map (+1) (x:xs)` 生成自然数）
    
3. **tuple 的惰性解构**（`~(a, b)` 而非 `(a, b)`）
    

### 🔑 洞见八：惰性模式与惰性求值的微妙关系

Haskell Wikibooks 给出了一个精妙对比 ：

```
-- 严格模式：参数必须能被匹配
let f (x, y) = 1
f undefined
-- *** Exception: Prelude.undefined

-- 惰性模式：参数延迟匹配
let f ~(x, y) = 1
f undefined
-- 1  （因为 x 和 y 从未被使用，所以匹配从未真正发生）
```

**这就是惰性模式的本质**：它把"模式匹配"推迟到"绑定变量被使用"的时刻。如果变量从未被使用，匹配就永远不会发生——这正是递归流定义能够工作的原因。

## 21.4 程序标注：给编译器的优化提示

### 内联标注：INLINABLE / INLINE / NOINLINE

Gabriella Gonzalez 的权威 FAQ ：

```
-- INLINABLE：告诉编译器保存函数源码到 .hi 文件，允许下游内联
-- 但不强制内联，编译器仍用自己的启发式判断
f :: Int -> Int
f x = x + 1
{-# INLINABLE f #-}

-- INLINE：类似 INLINABLE，但强烈偏向内联
-- 覆盖编译器的启发式判断
g :: Int -> Int
g x = x + 1
{-# INLINE g #-}

-- NOINLINE：禁止内联（常用于 unsafePerformIO）
{-# NOINLINE globalVar #-}
globalVar = unsafePerformIO (newIORef 0)
```

**🔑 洞见九：INLINABLE 通常是首选**

Gabriella Gonzalez 明确指出 ：

> _"My general rule of thumb for these compiler directives is: don't use any compiler directive until you benchmark your code to show that it helps. If you do use a compiler directive, INLINABLE is probably the one you should pick."_

**理由**：编译器的内联启发式通常很好。强制 `INLINE` 可能适得其反——除非你有基准测试证明它有帮助。

### SPECIALIZE 标注：多态函数的单态化

```
-- 多态函数
example :: Functor f => f Int -> f Int
example = fmap (+1)

-- 提示编译器为 Maybe 特化版本
{-# SPECIALIZE example :: Maybe Int -> Maybe Int #-}
```

Gabriella Gonzalez 的解释 ：

> _"SPECIALIZE lets you hint to the compiler that it should compile a polymorphic function for a monomorphic type ahead of time."_

**🔑 洞见十：特化消除类型类字典开销**

Haskell Wiki 详细解释了特化的机制 ：

> _"Specialisation is the process of removing typeclass dictionary arguments by creating a new type-specialised definition for an overloaded function. Once specialised, dictionary methods can be easily inlined which usually creates more efficient code."_

**示例**：

```
-- 多态函数 foo 带有 Show 字典参数
foo :: Show a => a -> a -> Bool
foo x y = show x == show y

-- 编译器生成 Core 时，foo 携带字典参数
-- foo = \@a $dShow x y -> eqString (show $dShow x) (show $dShow y)

-- 特化为 Bool 版本后
foo_$sfoo :: Bool -> Bool -> Bool
foo_$sfoo = \x y -> case x of
  False -> case y of
    False -> ...
    True -> ...
  True -> case y of
    _ -> ...
```

**特化后，字典查找被消除，函数可以直接内联**——性能显著提升。

### ANN 标注：源码注解

GHC 用户指南 ：

```
{-# ANN foo (Just "Hello") #-}
foo = ...

{-# ANN type Foo (Just "A `Maybe String' annotation") #-}
data Foo = ...

{-# ANN module (Just "A `Maybe String' annotation") #-}
```

**🔑 洞见十一：ANN 标注供编译器插件和 GHC API 使用**

GHC 用户指南 ：

> _"Annotations are small pragmas that allow you to attach data to identifiers in source code, which are persisted when compiled. These pieces of data can then inspected and utilized when using GHC as a library or writing a compiler plugin."_

**典型用途**：

- 编译器插件读取注解以进行自定义优化
    
- 测试框架通过注解发现测试用例
    
- 序列化库通过注解指导代码生成
    

### 🔑 洞见十二：标注使用的黄金法则

Gabriella Gonzalez 的 FAQ 给出了最务实的建议 ：

> _"Don't use any compiler directive until you benchmark your code to show that it helps."_

**标注不是"越多越好"**：

- 滥用 `INLINE` → 编译时间暴涨，代码膨胀
    
- 滥用 `SPECIALIZE` → .hi 文件膨胀，编译缓慢
    
- 正确做法：先写清晰代码 → 基准测试 → 定位热点 → 针对性标注

## 21.5 编译选项：优化级别与个体优化

### 优化级别包

GHC 用户指南 ：

```
# -O0：关闭所有优化（默认）
ghc -O0 Main.hs

# -O 或 -O1：生成高质量代码，编译时间适中
ghc -O Main.hs

# -O2：启用所有非危险优化，编译时间显著更长
ghc -O2 Main.hs
```

**🔑 洞见十三：-O2 不一定比 -O 更好**

GHC 用户指南明确指出 ：

> _"At the moment, -O2 is unlikely to produce better code than -O."_

**编译选项的实际建议**：

|场景|推荐选项|
|---|---|
|开发迭代|`-O0`（快速编译）|
|生产构建|`-O2`（最大优化）|
|基准测试|`-O2`|
|调试|`-O0`（保留原始语义）|

### 🔑 洞见十四：-O* 与 -f* 的顺序很重要

GHC 用户指南 ：

> _"When multiple flags for the same option appear in the command-line they are evaluated from left to right."_

```
# -fno-specialise 在前，-O1 在后 → 特化被启用（-O1 覆盖了前面的 -fno-specialise）
ghc -fno-specialise -O1 Main.hs

# -O1 在前，-fno-specialise 在后 → 特化被禁用
ghc -O1 -fno-specialise Main.hs
```

### 个体优化标志

GHC 用户指南列举了一些重要的 `-f*` 标志 ：

```
-fspecialise          # 启用特化
-fcse                 # 公共子表达式消除（默认开）
-fcase-merge          # 合并嵌套 case（默认开）
-fcall-arity          # 调用元数分析（默认开）
-fliberate-case       # 解放 case 转换（默认开）
```

### 严格字段拆箱

GHC 用户指南 ：

```
-funbox-strict-fields     # 所有严格字段尽可能拆箱（大锤）
-funbox-small-strict-fields  # 只拆箱"小"的严格字段（更温和）
```

**🔑 洞见十五：拆箱严格字段消除指针间接**

```
data Point = Point !Int !Int  -- 严格字段

-- 启用 -funbox-strict-fields 后
-- Point 在内存中可能直接包含两个整数，而非两个指向整数的指针
-- 这减少了内存分配和指针解引用
```

GHC 用户指南 ：

> _"This option is a bit of a sledgehammer: it might sometimes make things worse."_

**实践建议**：优先使用 `UNPACK` 标注选择性拆箱，而非全局 `-funbox-strict-fields`。

## 21.6 运行分析：Profiling 闭环

### 编译为可分析版本

Real World Haskell ：

```
# 编译时启用 profiling，并自动插入成本中心
ghc -O2 --make Main.hs -prof -auto-all -caf-all -fforce-recomp
```

**关键标志**：

- `-prof`：启用 profiling 支持
    
- `-auto-all`：为每个顶层函数自动插入成本中心
    
- `-caf-all`：为 CAF（Constant Applicative Forms）插入成本中心
    

### 运行并生成分析报告

```
./Main +RTS -p
```

GHC 用户指南 ：

> _"a simple time profile can be generated by running the program with +RTS -p, which generates a file named prog.prof"_

### 🔑 洞见十六：成本中心（Cost Centre）是性能分析的基石

GHC 用户指南 ：

> _"GHC's profiling system assigns costs to cost centres. A cost is simply the time or space (memory) required to evaluate an expression. Cost centres are program annotations around expressions; all costs incurred by the annotated expression are assigned to the enclosing cost centre."_

**手动插入成本中心**：

```
mean :: [Double] -> Double
mean xs = {-# SCC "mean" #-} sum xs / fromIntegral (length xs)
```

### 分析报告解读

Real World Haskell 给出了典型输出 ：

```
COST CENTRE   MODULE   %time %alloc
CAF:sum       Main     78.6   25.0
CAF           GHC.Float 21.4  75.0
```

**关键列**​ ：

- **COST CENTRE**：成本中心名称
    
- **MODULE**：所属模块
    
- **%time**：时间占比
    
- **%alloc**：内存分配占比
    
- **scc**：进入次数
    

### 🔑 洞见十七：Profiling 改变程序行为

Real World Haskell 提出了一个**关键警告**：

> _"adding cost centres to a program modifies how it is optimized, possibly changing its runtime behavior"_

**这意味着**：

1. Profiling 版本的性能数据**不能**直接等同于非 profiling 版本
    
2. 某些空间泄漏可能在 profiling 版本中"消失"或"改变"
    
3. Profiling 版本运行速度显著慢于正常版本
    

**实践建议**：

```
# 1. 先用 profiling 定位热点
./Main +RTS -p

# 2. 针对热点做优化（严格性标注、内联、数据结构改进）

# 3. 用基准测试验证优化效果
# 比较优化前后的运行时间
```

### 🔑 洞见十八：性能优化的闭环

```
1. 写清晰、正确的代码
   ↓
2. 基准测试（criterion 库）
```

## 📝 本章核心洞见总结

> **洞见一：语言扩展的本质是"突破标准语法的限制"**。
> 
> 核心原则是"按需开启，够用就好" ——不要为了"现代感"而开启用不到的扩展。常用扩展：`BangPatterns`（严格模式）、`StrictData`（严格字段）、`TypeApplications`（类型应用）、`GADTs`（广义代数数据类型）等。

> **洞见二：BangPatterns 让"模式匹配和 let 绑定"更严格**。
> 
> `!pat` 在匹配前先求值到 WHNF ；`!x = e` 在 let 绑定中强制求值。Bang 模式**不改变类型系统**​ ——它只是求值提示。

> **洞见三：StrictData 和 Strict 是模块级的严格性开关**。
> 
> `StrictData` 让模块内所有构造字段默认严格；`Strict` 让模块内所有模式、let 绑定、构造字段默认严格 。但两者**只影响当前模块**​ ——从其他模块导入的数据类型保持原有严格性 ，这是 Haskell 保持语义正确性的关键设计。

> **洞见四：惰性模式 `~pat` 是不可反驳的**。
> 
> 匹配总是成功，绑定变量在右侧被使用时才真正求值 ；如果届时匹配失败则抛出运行时异常。典型用例：递归定义的流（服务器/客户端模拟）、无限数据结构的递归定义 。

> **洞见五：INLINABLE 是程序标注的首选**。
> 
> Gabriella Gonzalez 的黄金法则："don't use any compiler directive until you benchmark your code to show that it helps. If you do use a compiler directive, INLINABLE is probably the one you should pick" 。`INLINABLE` 保存函数源码到 .hi 文件，允许下游内联，但让编译器保留启发式判断权 ；`INLINE` 覆盖编译器判断，强制内联 ；`NOINLINE` 禁止内联（常用于 `unsafePerformIO`）。

> **洞见六：SPECIALIZE 消除类型类字典开销**。
> 
> 多态函数 `foo :: Show a => a -> a -> Bool` 在 Core 中携带字典参数；特化为具体类型后，字典查找被消除，函数可被直接内联，生成高效代码 。`SPECIALIZE` 标注告诉编译器"预先为某个具体类型生成特化版本" 。

> **洞见七：ANN 标注是源码元数据，供编译器插件和 GHC API 使用**。
> 
> `{-# ANN foo (Just "Hello") #-}` 将表达式附着到标识符上，编译后持久化到 .hi 文件，可供插件读取以进行自定义优化或分析 。

> **洞见八：-O2 不一定比 -O 产生更好的代码**。
> 
> GHC 用户指南明确指出："At the moment, -O2 is unlikely to produce better code than -O" 。开发时用 `-O0`（快速编译），生产构建用 `-O2`（最大优化），基准测试用 `-O2`。

> __洞见九：-O_ 和 -f_ 标志的顺序影响最终结果**。
> 
> 命令行从左到右求值：`ghc -fno-specialise -O1` 仍然启用特化（`-O1` 覆盖前面的 `-fno-specialise`）；而 `ghc -O1 -fno-specialise` 禁用特化 。

> **洞见十：Profiling 是性能优化的闭环起点**。
> 
> 编译时 `-prof -auto-all -caf-all`，运行时 `+RTS -p` 生成 .prof 报告；成本中心（Cost Centre）将时间和内存分配归因到代码位置 。但要注意：Profiling 会改变程序优化行为，其性能数据不能直接等同于生产版本 。

> **洞见十一：完整的高性能 Haskell 工作流是"基准测试 → Profiling → 优化 → 验证"的循环**。
> 
> 不要盲目添加 `INLINE` 或开启 `Strict`；先用 criterion 等工具基准测试，用 `+RTS -p` 定位热点，针对性优化（严格性标注、内联、数据结构改进），然后重新基准测试验证 。

## 🛠️ 实践建议

1. **按需开启语言扩展**：
    
    ```
    -- ✅ 好的做法：只开启真正需要的
    {-# LANGUAGE BangPatterns #-}
    {-# LANGUAGE OverloadedStrings #-}
    
    -- ❌ 坏的做法：开启一堆用不到的
    {-# LANGUAGE BangPatterns, StrictData, GADTs, TypeFamilies, 
                DataKinds, PolyKinds, KindSignatures, DeriveGeneric,
                GeneralizedNewtypeDeriving, ... #-}
    ```
    
2. **用 BangPatterns 消除空间泄漏**：
    
    ```
    {-# LANGUAGE BangPatterns #-}
    
    -- 严格 fold：避免 thunk 堆积
    sumStrict :: [Int] -> Int
    sumStrict = foldl' (\ !acc x -> acc + x) 0
    
    -- 严格元组组件
    pairFold :: (Integer, Integer)
    pairFold = foldl' f (0, 0) [1..1000000]
      where f (!count, !theSum) x = (count + 1, theSum + x)
    ```
    
3. **用严格数据类型防止空间泄漏**：
    
    ```
    -- 定义严格字段的数据类型
    data StrictPair a b = StrictPair !a !b
    
    -- 使用严格数据类型
    pairFoldSP :: StrictPair Integer Integer
    pairFoldSP = foldl' f (StrictPair 0 0) [1..1000000]
      where f (StrictPair count theSum) x = 
              StrictPair (count + 1) (theSum + x)
    ```
    
4. **用 INLINABLE 指导跨模块优化**：
    
    ```
    -- 首选 INLINABLE（让编译器保留判断权）
    {-# INLINABLE myFunc #-}
    myFunc :: Int -> Int
    myFunc x = x * 2 + 1
    
    -- 仅在基准测试证明有益时使用 INLINE
    {-# INLINE hotLoop #-}
    hotLoop :: Int -> Int -> Int
    hotLoop !acc 0 = acc
    hotLoop !acc n = hotLoop (acc + n) (n - 1)
    ```
    
5. **用 SPECIALIZE 消除字典开销**：
    
    ```
    {-# SPECIALIZE myFold :: (Int -> Int -> Int) -> [Int] -> Int #-}
    {-# SPECIALIZE myFold :: (Double -> Double -> Double) -> [Double] -> Double #-}
    myFold :: (a -> a -> a) -> [a] -> a
    myFold f = foldl' f
    ```
    
6. **编译优化选项**：
    
    ```
    # 开发：快速编译
    ghc -O0 Main.hs
    
    # 生产：最大优化
    ghc -O2 Main.hs
    
    # 性能敏感：启用严格字段拆箱
    ghc -O2 -funbox-strict-fields Main.hs
    ```
    
7. **运行分析与优化闭环**：
    
    ```
    # 1. 编译为可 profiling 版本
    ghc -O2 --make Main.hs -prof -auto-all -caf-all -fforce-recomp
    
    # 2. 运行并生成报告
    ./Main 1000000 +RTS -p -K100M
    
    # 3. 查看 Main.prof 定位热点
    # COST CENTRE MODULE %time %alloc
    # hotFunction Main 85.2 90.1
    
    # 4. 针对热点优化（添加 ! 严格模式、INLINE 标注等）
    
    # 5. 重新编译、重新 profiling、验证优化效果
    ```
    
8. **惰性模式的典型应用**：
    
    ```
    -- 递归定义的流：客户端-服务器模拟
    client :: Request -> Response -> [Request]
    client init ~(resp:resps) = init : client (next resp) resps
    
    -- 惰性模式允许"先提交请求，再匹配响应"
    -- 没有 ~，client 会在提交第一个请求前就尝试匹配 resps，导致死锁
    ```
