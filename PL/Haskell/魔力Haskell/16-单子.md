
# 第十六章 单子 —— 读书笔记

> 💡 如果说第十三章的 Applicative 回答了"函数也在上下文里时怎么应用"，第十四章揭示了"Monoid + Applicative"的化学反应，第十五章把这套组合子用在了 CLI 解析上——那么第十六章就是在回答一个更锋利的问题：**当后续计算必须依赖前文结果时，Applicative 就不够用了**。表面看是 `>>=` 和 `do` 语法，实则在揭示 Haskell 抽象金字塔的第三块基石：**"依赖性计算"本身是一种可抽象、受定律约束的运算**——而 `IO` 正是这种"依赖性计算"最典型、也最必要的实例。

## 🎯 全局脉络：为什么 Monad 是抽象金字塔的第三块基石？

```
第十一章: Functor      fmap :: (a -> b) -> f a -> f b
                       "单参数函数在上下文里应用"
   ↓
第十三章: Applicative  (<*>) :: f (a -> b) -> f a -> f b
                       "多参数函数在上下文里应用（参数独立）"
   ↓
第十六章: Monad        (>>=) :: m a -> (a -> m b) -> m b  ← 你在这里
                       "后续计算依赖前文结果"
   ↓
第十七章: 列表单子 + MonadPlus（非确定性计算 + 选择）
```

**这一章是整本书"抽象跃迁"的巅峰**。前十五章你学了具体列表操作、类型类机制、Functor、Applicative、Alternative、Monoid——但有一个问题一直没解决：**当计算的逻辑本身需要根据"上一步的结果"动态决定时，Applicative 无法表达**。

Haskell 维基教科书对 Monad 类型类的定义一针见血 ：

```
class Applicative m => Monad m where
  return :: a -> m a
  (>>=)  :: m a -> (a -> m b) -> m b
  (>>)   :: m a -> m b -> m b
  fail   :: String -> m a
```

注意 `class Applicative m => Monad m`——**Monad 必须是 Applicative 的超类**。这意味着任何 Monad 自动是 Functor 和 Applicative，但反过来不成立。Monad 是"更强的"抽象，但它不是"替代"Applicative，而是"在 Applicative 基础上增加依赖性"。

> 💡 这种"层级递增"正是 Haskell 抽象金字塔的美学——每一层都比上一层更强，但每一层都建立在下一层之上。理解这种层级，你就能理解为什么 Haskell 有 Functor、Applicative、Monad 三个（而非一个）抽象。

## 16.1 应用函子的局限：当计算逻辑需要"动态决定"

### 起点：一个看似能用 Applicative 解决、实则卡住的问题

韩冬在书中给出了一个尖锐的例子 ：

```
replicateMaybe :: Maybe Int -> Int -> [Int]
replicateMaybe (Just n) x = replicate n x
replicateMaybe Nothing  x = replicate 1 x
```

**🔑 洞见一：应用风格会导致"上下文嵌套"**

我们希望用自然升格来写 `replicateMaybe`——但遇到了障碍：

```
-- 尝试用 Applicative 风格
replicateMaybe mn x = replicate <$> mn <*> pure x
-- 类型推导：
-- replicate :: Int -> a -> [a]
-- mn :: Maybe Int
-- 所以：replicate <$> mn :: Maybe (Int -> [Int])
-- 进一步：<*> pure x :: Maybe [Int]
-- 但我们需要的是 Maybe Int -> Int -> [Int]，不是 Maybe (Maybe Int) -> ...
```

问题出在：**`replicate <$> mn` 的类型是 `Maybe (Int -> [Int])`**，当我们再 `<*>` 时，会产生 **`Maybe (Maybe [Int])`**​ 这样的嵌套上下文 。

韩冬在书中明确指出 ：

> _"由于第一个参数中 Maybe 的存在，会获得一个 `Maybe (Maybe Int) -> Maybe [Int]` 类型的函数"_

而 `Maybe (Maybe Int)` 这个类型的信息和 `Maybe Int` 类型是一样的——`Just (Just 1)` 和 `Just 1` 在语义上都是"有一个值 1"，但类型系统认为它们是不同的。

### 🔑 洞见二：需要一个"坍塌"多余上下文的函数

观察 ：

```
john :: Maybe (Maybe a) -> Maybe a
john (Just x) = x
john Nothing  = Nothing

join :: [[a]] -> [a]
join = concat
```

**这就是 `join` 函数**——它"坍塌"掉一层多余的上下文。对于 `Maybe`：`john (Just (Just 1)) = Just 1`；对于列表：`join [[1,2],[3,4]] = [1,2,3,4]`。

> 💡 **这是 Applicative 局限的本质**：Applicative 的 `<*>` 会产生 `m (m a)` 这样的嵌套，但**它无法把嵌套"压平"**——因为这需要了解 `m` 的具体结构。而 `join` 正是做这件事的函数。

### 🔑 洞见三：更深的局限——"后续计算依赖前文结果"

博客文章给出了一个 Applicative 做不到的经典例子 ：

```
-- 计算边长 1 到 10 的所有矩形的面积
[1..10] >>= \x -> [x..10] >>= \y -> return (x * y)
```

**为什么 Applicative 做不到？**​ 因为第二个列表 `[x..10]` 的**起点依赖于第一个列表的 `x`**——

```
-- 尝试用 Applicative 写：
fmap (*) [1..10] <*> [???..10]  -- ??? 这里应该写什么？
```

`fmap (*) [1..10]` 的类型是 `[Int -> Int]`，当我们用 `<*>` 应用时，**第二个参数 `[???..10]` 必须是一个"静态确定的列表"**——但我们不知道 `x` 的值，所以无法写出第二个列表的起点 。

**这是 Applicative 的致命局限**：`<*>` 的所有参数必须在"组合时"就静态确定，**无法根据前文结果动态决定后续计算**。

### 🔑 洞见四：Applicative vs Monad 的本质差异

博客文章 yzhliu 给出了精辟的总结 ：

> _"观察 `(<*>)`，它最大的问题在于计算逻辑是第一步就决定了的，换言之，它需要计算逻辑作为输入。而单子则以函子为输入，意味着在取得原函子的实例后，还能根据这个实例决定要做什么计算逻辑。"_

Stack Overflow 上的回答进一步阐明 ：

> _"在 Monad 中，`m a` 能够决定是否应用函数 `(a -> m b)`。反过来，函数 `(a -> m b)` 可以'决定'是否绑定的下一个函数得到应用——通过生成那些不包含 b 的 `m b`（例如 `[]`、`Nothing` 或 `Left`）。在 Applicative 中这是不可能的。"_

**表格对比**：

|维度|Applicative|Monad|
|---|---|---|
|后续计算能否依赖前文|❌ 不能|✅ 能|
|控制流能否"提前终止"|❌ 不能（总是应用）|✅ 能（`Nothing` 短路、`[]` 空结果）|
|参数确定时机|组合时静态确定|运行时动态决定|
|典型应用|CLI 解析、独立选项|IO 操作、流式解析、错误处理|

### 实际应用

```
-- 用 Applicative 做不到的事，用 Monad 轻松实现
chain :: Maybe Int -> Maybe Int
chain mx = mx >>= \x ->
  if x > 0 
    then Just (x * 2) 
    else Nothing  -- 控制流决策！

-- 非确定性计算
pythagoreanTriples = 
  [1..10] >>= \x ->
  [x..10] >>= \y ->
  [y..10] >>= \z ->
  if x*x + y*y == z*z 
    then return (x, y, z) 
    else []
```

## 16.2 什么是单子：join 与 `>>=`

### 单子的数学定义

韩冬在书中给出了核心定义 ：

```
join :: (Monad m) => m (m a) -> m a
(>>=) :: m a -> (a -> m b) -> m b
(>>=) = join . fmap f
```

**🔑 洞见五：Monad = 能提供 join 的函子**

"能够提供 `join` 函数的函子类型称为单子" ——这是 Monad 最优雅的数学定义。

`join` 做一件事：**把 `m (m a)` 压平成 `m a`**。对于不同的 `m`，`join` 有不同的实现：

```
-- Maybe 的 join
join (Just (Just x)) = Just x
join (Just Nothing)  = Nothing
join Nothing         = Nothing

-- 列表的 join
join [[1,2],[3,4]] = [1,2,3,4]  -- 即 concat

-- IO 的 join
join (IO (IO a)) = IO a  -- 执行外层 IO，得到内层 IO，再执行内层 IO
```

### 🔑 洞见六：`>>=` 是 join 与 fmap 的组合

`>>= = join . fmap f` 这个等式揭示了 `>>=` 的本质 ：

1. `fmap f`：把 `a -> m b` 应用到 `m a` 上，得到 `m (m b)`（嵌套上下文）
    
2. `join`：把 `m (m b)` 压平成 `m b`
    

**所以 `>>=` 做的是**："映射并压平"。这与第十三章学的"自然升格"形成对比——`fmap` 只做映射（产生嵌套），`>>=` 做映射+压平（消除嵌套）。

### 🔑 洞见七：为什么用 `>>=` 而非 `join` 作为核心方法？

韩冬明确指出 ：

> _"在定义单子时，一般会要求提供粘合函数 `>>=` 的定义，而不是 `join`，因为 `>>=` 使用的场合多得多"_

**原因**：`>>=` 直接表达了"依赖性"——它的类型 `(>>=) :: m a -> (a -> m b) -> m b` 清晰地表明"接受一个 `m a`，一个'消费 `a` 产生 `m b`'的函数，返回 `m b`"。而 `join` 只是 `>>=` 的特例：`join x = x >>= id`。

### 16.2.1 粘合函数：`>>=` 的语义

**🔑 洞见八：`>>=` 定义了严格的计算顺序**

博客文章 yzhliu 指出 ：

> _"`>>=` 实际上还定义了严格的计算顺序。它隐含表达了 `m b` 所包含的计算，必须在 `m a` 的计算完成之后，并且这两个计算操作一定会发生。"_

这意味着 `>>=` 做了三件事：

1. **执行**​ `m a` 的计算，得到值 `a`
    
2. **应用**​ 函数 `a -> m b`，得到 `m b`
    
3. **执行**​ `m b` 的计算，得到最终结果
    

**"依赖性"和"顺序性"是一枚硬币的两面**——因为后续计算依赖前文结果，所以前文必须先计算；因为前文先计算，所以自然形成了"顺序执行"语义。

### 🔑 洞见九：`return` 是"最小上下文"的 Monad 版本

韩冬在书中说 ：

> _"`return` 用来把表达式装进一个含有'最小上下文的'函子中"_
> 
> ```
> return 2 :: [Int]  -- [2]
> return 2 :: Maybe Int -- Just 2
> ```

**`return` 就是 Applicative 的 `pure`**——把值装进"最小上下文"。在 Monad 类型类定义中，`return` 实际上就是 `pure`（从历史原因保留两个名字）。

### 🔑 洞见十：三条 Monad 定律

与 Functor、Applicative 类似，Monad 也有定律：

```
-- 左单位元（Left identity）
return a >>= f = f a

-- 右单位元（Right identity）
m >>= return = m

-- 结合律（Associativity）
(m >>= f) >>= g = m >>= (\x -> f x >>= g)
```

**这三条定律保证 `>>=` 的行为是可预测的**：

- **左单位元**：`return` 是 `>>=` 的左单位元——从 `return a` 开始，等同于直接调用 `f a`
    
- **右单位元**：`return` 是 `>>=` 的右单位元——计算到 `return` 就停止
    
- **结合律**：嵌套的 `>>=` 可以重新分组而不改变语义——这正是"do 语法糖"能够正确脱糖的基础
    

### 16.2.2 do 语法糖：让 Monad 代码读起来像命令式

这是本章**最实用的**一节。Haskell Wikibooks 给出了精确的脱糖规则 ：

```
-- do 语法糖
do { action1
   ; action2
   ; action3 }

-- 脱糖为
action1 >> do { action2
               ; action3 }
-- 继续脱糖
action1 >> (action2 >> action3)
```

对于绑定：

```
-- do 语法糖
do { x1 <- action1
   ; x2 <- action2 x1
   ; action3 x1 x2 }

-- 脱糖为
action1 >>= (\x1 -> action2 x1 >>= (\x2 -> action3 x1 x2))
```

### 🔑 洞见十一：do 块不是命令式语句，是 `>>=` 的语法糖

Haskell Wikibooks 明确强调 ：

> _"Translating the do notation to unsugared Haskell code... The bind operator (>>=) is a bit more difficult to translate to and from the do notation. (>>=) passes a value, namely the result of an action or function, downstream in the binding sequence."_

**关键认知**：do 块里的每一行"看起来像命令式语句"，但**脱糖后只剩下函数应用和 lambda**——没有任何"语句"，只有表达式 。

Wikibook 上的经典例子 ：

```
-- do 语法糖版本
main = do
  putStrLn "What is your first name?"
  first <- getLine
  putStrLn "And your last name?"
  last <- getLine
  let full = first ++ " " ++ last
  putStrLn $ "Pleased to meet you, " ++ full ++ "!"

-- 脱糖版本
main = putStrLn "What is your first name?" 
       >> getLine >>= \first ->
          putStrLn "And your last name?"
          >> getLine >>= \last ->
             let full = first ++ " " ++ last in
             putStrLn $ "Pleased to meet you, " ++ full ++ "!"
```

### 🔑 洞见十二：do 语法糖的真正价值

do 语法糖不是"让 Haskell 变成命令式语言"——**语义仍然是纯函数式的，只是语法像命令式**​ 。它的价值在于：

1. **可读性**：深层嵌套的 lambda 难以阅读，do 块线性展开
    
2. **变量绑定**：`x <- action` 清晰地表达"从 action 中提取 x"
    
3. **顺序直观**：代码从上到下读，对应计算从左到右执行
    

Haskell 维基教科书指出 ：

> _"do works with any monad; there is nothing specific about IO in how it works."_

**do 语法糖是 Monad 的通用语法糖，不仅限于 IO**。它可以用于任何 Monad：`Maybe`、`[]`、`Either`、`State`、`Reader`、`Writer`……

### 🔑 洞见十三：do 块中的 `let` 与 `return`

do 块中有两个特殊形式 ：

```
do 
  let x = expression   -- let 绑定，不产生 Monad 效果
  y <- action           -- 从 action 中提取值
  return value          -- 把 value 装回 Monad 上下文（作为 do 块的返回值）
```

注意 `return` 在 do 块中的作用：**它不是"返回语句"（不会跳出 do 块），而是把值装进 Monad 上下文，作为整个 do 表达式的结果**​ 。

### 实际应用

```
-- Maybe Monad 的 do 语法糖
addMaybe :: Maybe Int -> Maybe Int -> Maybe Int
addMaybe mx my = do
  x <- mx        -- 如果 mx 是 Nothing，整个 do 块返回 Nothing
  y <- my        -- 如果 my 是 Nothing，整个 do 块返回 Nothing
  return (x + y) -- 把 x+y 装回 Maybe 上下文
-- 脱糖版本：mx >>= \x -> my >>= \y -> return (x + y)

-- 列表 Monad 的 do 语法糖（非确定性计算）
pairs :: [Int] -> [(Int, Int)]
pairs xs = do
  x <- xs
  y <- xs
  return (x, y)
-- 等价于：xs >>= \x -> xs >>= \y -> return (x, y)
-- 产生所有 (x, y) 组合
```

## 16.3 IO 单子：当副作用遇上依赖性计算

### IO 的本质

Haskell 维基教科书对 IO 的定义极为精辟 ：

> _"a value of type (IO a) is an action, which if executed would produce a value of type a"_

**`IO a` 是一个"动作"——如果被执行，会产生一个 `a` 类型的值**。关键点：

- **普通 Haskell 求值不会执行 IO 动作**——`IO a` 值本身是"惰性"的、几乎是惰性的（inert）
    
- **只有 `main` 函数中的 IO 动作才会真正执行**​
    
- **所有操纵 IO 动作的 Haskell 函数仍然是纯函数**​
    

Haskell Wikibook 进一步阐述 ：

> _"虽然 IO 操作是不纯的，但所有操纵它们的 Haskell 函数仍然是纯函数。函数式纯度加上 I/O 在类型中出现的事实，以多种方式使 Haskell 程序员受益。关于引用透明性的保证极大地提高了编译器优化的潜力。透过类型本身可以区分 IO 值，这使得我们能够立即知道我们在哪里使用副作用或不透明值。"_

### 🔑 洞见十四：IO 单子让"不纯"在类型中被追踪

这是 Haskell 解决"纯函数式 vs 副作用"悖论的方案：

```
纯函数式世界                    不纯的 IO 世界
─────────                      ─────────────
IO a 是一个"纯的值"            IO a 代表"一个产生 a 的副作用计算"
f :: a -> IO b 是纯函数         f 的描述是纯的，执行是不纯的
main :: IO () 是唯一入口        运行时系统从 main 开始执行
```

**Haskell 没有"逃离"纯函数式**——它用类型追踪不纯 。一个返回 `IO a` 的函数，在类型层面诚实地声明了自己的副作用。这就是为什么 Haskell 程序可以进行等式推理：纯函数对相同输入总是返回相同结果。

### 🔑 洞见十五：IO 的 `>>=` 实现

```
instance Monad IO where
  return = pure  -- 立即返回的 IO 动作
  
  (>>=) :: IO a -> (a -> IO b) -> IO b
  -- 语义：执行第一个 IO 动作得到 a，用 a 调用函数得到第二个 IO 动作，执行之
```

Haskell 维基教科书给出直观解释 ：

> _"`x >>= f` is the action that first performs the action x, and captures its result, passing it to f, which then computes a second action to be performed. That action is then carried out, and its result is the result of the overall computation."_

### 🔑 洞见十六：IO 是 Monad 的"必要性证明"

为什么 Haskell 必须有 Monad？因为 **IO 操作天然具有"依赖性"**——后续 IO 操作常常需要前文 IO 操作的结果。

```
-- 读取用户名，然后用它构造问候语
main = do
  putStrLn "What is your name?"
  name <- getLine              -- 依赖前面的 putStrLn（顺序）
  putStrLn ("Hello, " ++ name ++ "!")  -- 依赖 getLine 的结果 name
```

**如果只有 Applicative，无法写出上面的代码**——因为 `putStrLn ("Hello, " ++ name)` 中的 `name` 必须来自前文的 `getLine`，这是"依赖性"的，Applicative 表达不了。

Haskell Wikibook 指出 ：

> _"单子表示式可以解释为命令式语言的语句。这种解释对于 IO 来说是直接有说服力的"_

但必须明确——**这不是说 Monad 或 do 符号将 Haskell 变成了一种命令式语言。重点仅仅是你可以用命令式语句来查看和理解单子代码。语义可能是命令式的，但单子和 `(>>=)` 的实现仍然是纯函数式的**​ 。

### 🔑 洞见十七：IO 是"描述性"而非"执行性"的

Haskell 维基教科书给出的最深刻洞察 ：

> _"Ordinary Haskell evaluation doesn't cause this execution to occur. A value of type (IO a) is almost completely inert. In fact, the only IO action which can really be said to run in a compiled Haskell program is main."_

**`IO a` 值本身是"惰性的"——它只是对计算的描述，不是计算本身**。这意味着：

```
-- 这两个 IO 动作都被构造了，但都没有执行
action1 :: IO String
action1 = getLine

action2 :: IO ()
action2 = putStrLn "Hello"

-- 只有被 main 引用（直接或间接）的 IO 动作才会执行
main :: IO ()
main = do
  name <- action1
  action2
  putStrLn name
```

**这种"描述性"让 Haskell 获得了巨大的优势**：

- **编译优化**：因为 IO 动作是纯的值，编译器可以自由地内联、重排、消除死代码
    
- **组合性**：IO 动作可以像普通值一样传递、存储、组合
    
- **测试性**：可以构造 IO 动作而不执行它，便于测试和模拟
    

### 🔑 洞见十八：IO 与纯函数的边界

Haskell Wikibook 总结得极好 ：

> _"由于 IO 本身只是一个函子，我们最大程度地保持了与纯函数相关的可预测性和易推理性。"_

**整个 Haskell 程序是纯的**——`main :: IO ()` 只是一个"对计算的描述"，由运行时系统执行。所有操纵 IO 的函数（`>>=`、`fmap`、`pure`）都是纯函数——它们组合 IO 描述，但不执行 IO。

> 💡 **这是 Haskell 最反直觉也最优雅的设计**：用纯函数式的方式描述不纯的计算。IO 单子让"不纯"在类型中被追踪，让"纯"在代码中得到保证。

### 实际应用

```
-- 一个完整的 IO 程序
main :: IO ()
main = do
  putStrLn "Hello, what is your name?"
  firstName <- getLine
  putStrLn "And your last name?"
  lastName <- getLine
  let fullName = firstName ++ " " ++ lastName
  putStrLn $ "Pleased to meet you, " ++ fullName ++ "!"
  
  -- 脱糖版本：
  -- main = putStrLn "Hello, what is your name?"
  --          >> getLine >>= \firstName ->
  --             putStrLn "And your last name?"
  --             >> getLine >>= \lastName ->
  --                let fullName = firstName ++ " " ++ lastName in
  --                putStrLn $ "Pleased to meet you, " ++ fullName ++ "!"

-- 用 return 返回值
greet :: IO String
greet = do
  putStrLn "Enter your name:"
  name <- getLine
  return ("Hello, " ++ name ++ "!")
```

**本章给你三件行李**：

1. **应用函子的局限与 Monad 的解药**——`>>=` 让后续计算依赖前文结果，并由此获得控制流决策能力
    
2. **`>>= = join . fmap`**——Monad 本质是"能提供 join 的 Applicative"
    
3. **do 语法糖是 `>>=` 的语法糖**——它让 Monad 代码读起来像命令式，但语义仍然是纯函数式

## 📝 本章核心洞见总结

> **洞见一：应用函子的局限在于"计算逻辑第一步就确定了"**。
> 
> `<*>` 的所有参数必须在组合时静态确定，无法根据前文结果动态决定后续计算。而 Monad 的 `>>=` 以"函数 `a -> m b`"为参数，意味着取得 `m a` 后还能根据结果决定下一步计算 。

> **洞见二：Monad = 能提供 join 的 Applicative**。
> 
> `join :: m (m a) -> m a` 把嵌套上下文压平。Haskell 要求 Monad 实例提供 `>>=`，但 `>>= = join . fmap f`——`>>=` 做"映射+压平" 。

> **洞见三：`>>=` 定义了严格的计算顺序**。
> 
> `m >>= f` 隐含表达了：`m` 的计算必须先完成，其结果传给 `f` 产生新的计算，新计算再执行。这种"依赖性"自然带来了"顺序性" 。

> **洞见四：do 语法糖是 `>>=` 的语法糖，不是命令式语句**。
> 
> 编译器把 do 块脱糖为嵌套的 `>>` 和 `>>=` 调用 。do 块"看起来像命令式代码"，但语义仍然是纯函数式的——每一行都是函数应用和 lambda。

> **洞见五：IO 单子让"不纯"在类型中被追踪**。
> 
> `IO a` 是一个"动作的描述"，普通求值不会执行它，只有 `main` 会 。一个返回 `IO a` 的函数，在类型层面诚实地声明了自己的副作用，从而保持引用透明性和等式推理能力 。

> **洞见六：IO 是 Monad 的"必要性证明"**。
> 
> IO 操作天然具有"依赖性"——后续 IO 常常需要前文 IO 的结果。如果只有 Applicative，无法写出 `name <- getLine; putStrLn ("Hello, " ++ name)` 这样的代码。Monad 的 `>>=` 正是为这种"依赖性"而设计 。

> **洞见七：return 在 do 块中不是"返回语句"**。
> 
> `return` 只是把值装回 Monad 上下文（等同于 `pure`），作为整个 do 表达式的结果。它不会跳出 do 块 。

> **洞见八：Monad 定律保证 `>>=` 的可预测性**。
> 
> 左单位元（`return a >>= f = f a`）、右单位元（`m >>= return = m`）、结合律——这三条定律是 do 语法糖能够正确脱糖的数学基础 。

> **洞见九：Applicative 是 Monad 的超类**。
> 
> `class Applicative m => Monad m`——任何 Monad 自动是 Applicative 和 Functor 。这意味着 Monad 不是"替代"Applicative，而是在其基础上增加"依赖性"。能用 Applicative 解决的问题，优先用 Applicative（更通用、更可优化）；必须表达"依赖性"时，才升级到 Monad。

> **洞见十：Monad 让"控制流"成为可能**。
> 
> 因为 `a -> m b` 可以"决定"是否应用下一个函数（通过返回 `Nothing`、`[]`、`Left` 等），Monad 获得了 Applicative 没有的控制流能力——失败短路、条件分支、循环 。这正是第十七章 MonadPlus 和列表单子的主题。

## 🛠️ 实践建议

1. **优先用 Applicative，必要时才用 Monad**：
    
    ```
    -- 如果参数独立，用 Applicative
    result = f <$> io1 <*> io2 <*> io3
    
    -- 如果后续依赖前文，用 Monad
    result = do
      x <- io1
      y <- io2 x  -- io2 依赖 x
      return (f x y)
    ```
    
2. **理解 do 块的脱糖**：
    
    ```
    -- 写 do 块时，心里想着脱糖后的 >>= 链
    do { x <- mx; my x }
    -- 等价于
    mx >>= \x -> my x
    ```
    
3. **用 QuickCheck 验证 Monad 定律**：
    
    ```
    monadLeftIdentity :: (Monad m, Eq (m b)) => a -> (a -> m b) -> Bool
    monadLeftIdentity a f = (return a >>= f) == f a
    
    monadRightIdentity :: (Monad m, Eq (m a)) => m a -> Bool
    monadRightIdentity m = (m >>= return) == m
    ```
    
4. **避免 do 块中的反模式**：
    
    ```
    -- ❌ 反模式：单行的 do 块
    do { x <- getLine; return x }
    -- ✅ 简化
    getLine
    
    -- ❌ 反模式：不必要的 return
    do { x <- getLine; return (process x) }
    -- ✅ 简化
    process <$> getLine
    ```
    
5. **理解 IO 的"描述性"**：
    
    ```
    -- 构造 IO 动作但不执行
    lazyAction :: IO String
    lazyAction = getLine
    
    -- 只有被 main 引用才会执行
    main = do
      result <- lazyAction
      print result
    ```
    
6. **用 `>>` 忽略结果**：
    
    ```
    -- 当不需要前一步的结果时
    do
      putStrLn "Starting..."
      _ <- someIOAction  -- 忽略结果
      putStrLn "Done."
    
    -- 等价于
    putStrLn "Starting..." >> someIOAction >> putStrLn "Done."
    ```

## 🔮 承上启下

第十七章"八皇后问题和列表单子"会在本章基础上往前推一步——**展示 Monad 在非确定性计算中的威力**：

- **列表单子**：`[a]` 的 Monad 实例让"非确定性计算"成为 `>>=` 的自然推论
    
- **MonadPlus**：为 Monad 添加"选择/失败回退"能力（`mzero` 和 `mplus`），类似第十四章的 Alternative
    
- **结构控制函数**：`sequence`、`mapM`、`replicateM`、`forever`、`filterM` 等——这些都是 Monad 的通用组合子
    

更深远的连接：

- **第十七章**：`[1..10] >>= \x -> [x..10] >>= \y -> return (x*y)` 是 Monad "依赖性"威力的直接展示——后续列表的起点依赖前文的 `x`
    
- **第二十章 IO Monad**：会深入 `IORef`、`bracket`、`try` 等——这些是 IO Monad 在真实工程中的工具
    
- **第二十四章 Monad Transformers**：多个 Monad 的堆叠组合——`StateT`、`ReaderT`、`WriterT` 等，它们都建立在 `Monad` 类型类之上
    

**第十六章是你理解 Haskell "依赖性计算"的关键一跃**。吃透 `>>= = join . fmap f`、理解 do 语法糖的脱糖规则、明白 IO 单子如何追踪副作用，后面的列表单子、MonadPlus、Monad Transformers 就不再是"新的魔法"，而是"我们已经知道的知识的自然延伸"——你已经知道 Monad 是"能提供 join 的 Applicative"，第十七章只是告诉你"列表的 join 就是 concat"；你已经知道 `>>=` 让后续计算依赖前文，第十七章只是把这种依赖用于"非确定性搜索"；你已经知道 do 语法糖是 `>>=` 的语法糖，第十七章只是用 do 块写出优雅的八皇后问题解法。

> 💡 学习建议：读完本章后，在 GHCi 里做三个实验：
> 
> ```
> -- 1. 体验 Monad 的"依赖性"
> [1,2] >>= \x -> [x..3] >>= \y -> return (x, y)
> -- [(1,1),(1,2),(1,3),(2,2),(2,3)]——第二个列表的起点依赖 x
> 
> -- 2. 体验 Applicative 做不到的事
> -- fmap (*) [1,2] <*> [1..3]  -- 笛卡尔积，第二个列表固定
> -- 而 Monad 可以让第二个列表动态决定
> 
> -- 3. 体验 do 语法糖
> do { x <- [1,2]; y <- [x..3]; return (x, y) }
> -- 与上面的 >>= 链等价
> ```
> 
> 亲眼看见"Monad 的依赖性"与"Applicative 的独立性"的差异，是理解本章精髓的最佳方式。
> 
> 然后尝试用 do 块重写你之前的 `>>=` 链——你会发现 deeply nested lambda 立刻变得清晰可读。这种"可读性跃迁"不是语法糖的魔法，而是 `>>=` 语义的自然展开。
