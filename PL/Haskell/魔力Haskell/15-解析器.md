
# 第十五章 解析器 —— 读书笔记

> 💡 如果说第十三章的 Applicative 和第十四章的 Alternative 还是"抽象层面的组合子"，那么第十五章就是把这两个抽象**第一次大规模落到具体工程场景**——命令行参数解析。表面看是介绍 `optparse-applicative` 这个库，实则在揭示一个深层真相：**命令行参数解析天然就是 Applicative + Alternative 的问题**——选项之间相互独立（Applicative），输入来源需要"二选一"或"多选一"（Alternative）。这一章让你亲眼看见：前面学的抽象不是玩具，它们是工程问题的"最小数学解"。

韩冬在这一章安排了三个小节：**15.1 参数解析**、**15.2 optparse-applicative**、**15.3 选择解析**。表面是从"为什么需要参数解析"到"如何用应用风格构建解析器"再到"如何用 Alternative 处理选择"，实则在铺设一条主线：**解析器就是一个 Functor + Applicative + Alternative 的 `Parser a` 类型，它把"对命令行的规格说明"编码进类型系统，让你用组合子而非手工字符串处理来构建 CLI**。

## 🎯 全局脉络：为什么参数解析是 Applicative + Alternative 的完美舞台？

```
第十三章: Applicative（pure + (<*>)）
   ↓
第十四章: Alternative（empty + (<|>)）← Monoid 在应用函子层面的体现
   ↓
第十五章: 解析器 = Applicative + Alternative 的工程典范  ← 你在这里
   ↓
第十六章: Monad（当解析需要"依赖性"时）
```

**这一章是 Applicative + Alternative 的"工业级样板间"**。前十四章你学了：

- 第十三章：`<$>` 和 `<*>` 让"多参数函数在上下文里应用"变得优雅
    
- 第十四章：`<|>` 让应用函子具备"选择/失败回退"能力，`Monoid` 约束让 `Const` 等成为累积器
    

第十五章告诉你——**命令行参数解析这个看似平凡的问题，恰好是这两个抽象的最佳展示场**：

1. **选项是独立的**​ → 用 Applicative 组合（`Options <$> opt1 <*> opt2 <*> opt3`）
    
2. **选项顺序是自由的**​ → 这正是 Applicative 而非 Monad 的原因（所有选项并行考虑）
    
3. **输入来源需要"二选一"**​ → 用 Alternative 的 `<|>`（`fileInput <|> stdInput`）
    
4. **子命令需要分支**​ → 用 Alternative 组合子命令解析器
    

optparse-applicative 的官方文档一语道破天机：

> _"optparse-applicative is a haskell library for parsing options on the command line, and providing a powerful applicative interface for composing them."_

**"applicative interface"**​ 不是巧合，而是**必然性**——因为命令行选项的本质就是"相互独立、可并行解析"，这正是 Applicative 的语义。

## 15.1 参数解析：声明式 CLI 的必要性

### 命令行解析的传统痛点

在多数命令式语言里，命令行解析是这样的：

```
# Python 伪代码
import sys
args = sys.argv[1:]
opts = {}
i = 0
while i < len(args):
    if args[i] == "--hello":
        opts["hello"] = args[i+1]
        i += 2
    elif args[i] == "-q":
        opts["quiet"] = True
        i += 1
    # ... 手动处理每个参数
```

**这种写法的根本问题**：

1. **顺序敏感**：必须按特定顺序解析参数
    
2. **错误易漏**：忘记处理某个参数、忘记边界检查
    
3. **帮助文本手写**：`--help` 输出要手动维护，容易过时
    
4. **类型不安全**：所有参数都是字符串，需要手动转换和验证
    

### 🔑 洞见一：参数解析的本质是"从字符串列表到结构化值"

命令行解析的数学本质：

```
parse :: [String] -> Maybe Options
```

其中 `Options` 是你的领域类型。问题是——**这个 `parse` 函数怎么构造？**

命令式语言选择"手工编写状态机"；Haskell 选择"**用组合子声明式地描述解析器**"：

```
data Options = Options { optTarget :: String, optQuiet :: Bool }

opts :: Parser Options
opts = Options <$> strOption (long "hello" <> metavar "TARGET")
              <*> switch (long "quiet" <> short 'q')
```

**这段代码读起来就像 `Options` 构造函数的应用**——但每个参数都自动从命令行提取、自动类型转换、自动错误检查、自动生成帮助文本。

### 🔑 洞见二：声明式解析的四大优势

optparse-applicative 的官方文档明确指出，使用应用风格解析器可以获得 ：

1. **选项顺序无关**：`--target world -q` 和 `-q --target world` 等价（排列解析器/permutation parser）
    
2. **自动错误处理**：缺失必填项、类型转换失败都会自动报告
    
3. **自动帮助生成**：`--help` 输出自动从解析器规格生成
    
4. **类型安全**：`option auto` 利用 `Read` 类型类自动转换，编译期保证类型正确
    

> 💡 这四条优势不是 optparse-applicative 的"功能"，而是**Applicative 抽象的自然推论**。因为 `Parser` 是 Applicative，所以 `<*>` 组合出的解析器自动具备"顺序无关"语义；因为解析器规格是类型安全的值，所以帮助文本可以从类型结构自动推导。

### 实际应用

```
-- 声明式地描述 CLI 接口
data Sample = Sample { hello :: String, quiet :: Bool, enthusiasm :: Int }

sample :: Parser Sample
sample = Sample <$> strOption (long "hello" <> metavar "TARGET" <> help "Target for the greeting")
              <*> switch (long "quiet" <> short 'q' <> help "Whether to be quiet")
              <*> option auto (long "enthusiasm" <> help "How enthusiastically to greet" 
                              <> showDefault <> value 1 <> metavar "INT")
```

## 15.2 optparse-applicative：应用风格的工程典范

### Parser 类型的三重身份

optparse-applicative 的 `Parser a` 类型同时是 `Functor`、`Applicative`、`Alternative` 的实例 ：

```
data Parser a
instance Functor Parser
instance Applicative Parser
instance Alternative Parser
```

**这意味着 `Parser a` 是一个"对命令行选项的规格说明"**——当命令行参数成功解析时，它会产出类型 `a` 的值 。

### 基本组合子（Primitive Parsers）

optparse-applicative 提供了一组"基本解析器" ：

|组合子|用途|返回类型|
|---|---|---|
|`strOption`|字符串选项（如 `--hello world`）|`Parser String`|
|`switch`|布尔开关（如 `-q`/`--quiet`）|`Parser Bool`|
|`option auto`|利用 `Read` 的类型化选项|`Parser a`|
|`flag'`|返回特定值的标志|`Parser a`|
|`argument`|位置参数|`Parser a`|
|`subparser`|子命令|`Parser a`|

### Modifier 与 Monoid 的化学反应

这是本章**最精妙的设计**——每个基本解析器接受一个 **Modifier**，而 Modifier 是 Monoid 的实例，用 `(<>)` 组合 ：

```
strOption (long "hello" <> metavar "TARGET" <> help "Target for the greeting")
```

**🔑 洞见三：Modifier 是 Monoid 的工业级应用**

回顾第十四章学的 Monoid——`mempty` + `<>` 提供"可结合的累积"。这里：

- `mempty` 是"空的 Modifier"（不改任何属性）
    
- `<>` 是"组合两个 Modifier"
    

这意味着你可以：

```
let common = long "file" <> short 'f' <> metavar "FILENAME"
    inputMod = common <> help "Input file"
    outputMod = common <> help "Output file"
```

**第十四章学的 Monoid 理论，在此刻变成了工程现实**——Modifier 的组合就是 Monoid 的 `<>`，类型系统保证了组合的顺序无关性和结合性。

### 应用风格组合：从基本解析器到完整 CLI

optparse-applicative 官方文档的经典示例 ：

```
sample :: Parser Sample
sample = Sample <$> strOption (long "hello" <> metavar "TARGET" <> help "Target for the greeting")
              <*> switch (long "quiet" <> short 'q' <> help "Whether to be quiet")
              <*> option auto (long "enthusiasm" <> help "How enthusiastically to greet" 
                              <> showDefault <> value 1 <> metavar "INT")
```

**🔑 洞见四：这是第十三章"应用风格"的完美示范**

`Sample <$> parser1 <*> parser2 <*> parser3` 读起来**几乎和普通函数调用 `Sample x y z` 一模一样**——但每个参数都自动从命令行提取。这正是第十三章 13.2.2 节"自然升格"的威力展现：

- `<$>` 把 `Sample` 构造函数"升格"进 `Parser` 上下文
    
- `<*>` 依次应用各个参数的解析器
    
- 编译器自动推断整个表达式是 `Parser Sample` 类型
    

### 排列解析器（Permutation Parser）：为什么是 Applicative 而非 Monad？

这是本节**最深刻的洞见**。optparse-applicative 官方文档明确指出 ：

> _"It is this property which leads us to an Applicative interface instead of a Monadic one, as all options must be considered in parallel, and can not depend on the output of other options."_

**为什么不用 Monad？**​ 因为：

- **Monad 的 `>>=` 允许后续计算依赖前文结果**——这意味着解析顺序必须固定
    
- **Applicative 的 `<*>` 要求所有参数独立**——这意味着解析顺序可以任意
    

命令行选项的语义是"**用户可以以任意顺序提供选项**"——`--target world -q` 和 `-q --target world` 必须等价。这正是 Applicative 的语义，而非 Monad。

> 💡 **这是本章最反直觉也最重要的设计抉择**：用"更弱"的 Applicative 而非"更强"的 Monad，恰恰是因为 Applicative 的"弱"正是命令行解析所需要的——选项独立、顺序无关。如果用 Monad，你就被迫固定解析顺序，违背了 CLI 的惯例。

### ParserInfo：从"规格"到"可执行程序"

一个 `Parser a` 只是"对命令行选项的规格说明"，要真正运行它，需要用 `info` 函数包装成 `ParserInfo a` ：

```
opts :: ParserInfo Sample
opts = info (helper <*> sample) 
            (fullDesc 
             <> progDesc "Print a greeting for TARGET" 
             <> header "hello - a test for optparse-applicative")
```

然后用 `execParser` 执行：

```
main :: IO ()
main = execParser opts >>= greet
```

**🔑 洞见五：ParserInfo 承载"元信息"**

`ParserInfo` 分离了"解析逻辑"和"程序元信息"：

- **解析逻辑**：`sample :: Parser Sample`——纯解析器
    
- **元信息**：`fullDesc`、`progDesc`、`header`——帮助文本、程序描述
    
- **`helper` 组合子**：自动添加 `--help` 支持
    

这种分离让"解析器"成为可复用、可测试的值，而"程序描述"是独立关注的方面。

### 实际应用

```
-- 完整可运行的 CLI 程序
import Options.Applicative

data Options = Options
  { optFile   :: Maybe FilePath
  , optVerbose :: Bool
  , optCount  :: Int
  }

parser :: Parser Options
parser = Options
  <$> optional (strOption (long "file" <> short 'f' <> metavar "FILE" 
                          <> help "Input file (optional)"))
  <*> switch (long "verbose" <> short 'v' <> help "Enable verbose mode")
  <*> option auto (long "count" <> short 'c' <> value 1 <> showDefault 
                   <> metavar "INT" <> help "Repeat count")

opts :: ParserInfo Options
opts = info (helper <*> parser)
            (fullDesc <> progDesc "Demonstrate optparse-applicative" 
             <> header "demo - a simple CLI demo")

main :: IO ()
main = do
  options <- execParser opts
  putStrLn $ "File: " ++ show (optFile options)
  putStrLn $ "Verbose: " ++ show (optVerbose options)
  putStrLn $ "Count: " ++ show (optCount options)
```

运行结果：

```
$ demo --file input.txt -v --count 3
File: Just "input.txt"
Verbose: True
Count: 3

$ demo --help
demo - a simple CLI demo
Usage: demo [--file FILE] [-v|--verbose] [--count INT]
  Demonstrate optparse-applicative
Available options:
  --file FILE            Input file (optional)
  -v, --verbose          Enable verbose mode
  --count INT            Repeat count (default: 1)
  -h, --help             Show this help text
```

**自动生成的帮助文本、自动的 `--help` 支持、自动的类型转换、自动的错误处理**——全部来自 `parser` 的声明式规格。

## 15.3 选择解析：Alternative 的工程实战

### 选择解析的本质

命令行程序常常需要"二选一"或"多选一"的输入：

- 输入来源：`--file filename` 或 `--stdin`
    
- 模式选择：`--heterozygosity` 或 `--segregatingSites` 或 `--hardyWeinbergDev`
    
- 子命令：`git clone` 或 `git push`
    

这些场景的共同特征是——**多个解析器中恰好选择一个**。这正是 Alternative 的 `<|>` 运算符的语义 。

### 🔑 洞见六：Alternative 让"选择"成为一等公民

optparse-applicative 文档的经典示例 ：

```
data Input = FileInput FilePath | StdInput

fileInput :: Parser Input
fileInput = FileInput <$> strOption (long "file" <> short 'f' <> metavar "FILENAME")

stdInput :: Parser Input
stdInput = flag' StdInput (long "stdin" <> help "Read from stdin")

input :: Parser Input
input = fileInput <|> stdInput
```

**`<|>` 的语义**：

1. 先尝试 `fileInput`：如果命令行有 `--file xxx`，解析成功
    
2. 如果 `fileInput` 失败（没有 `--file`），回退到 `stdInput`
    
3. 如果两者都失败，整个 `input` 解析失败
    

这正是第十四章学的 Alternative 定律的工程体现：`empty <|> x = x`，`x <|> empty = x`。

### 🔑 洞见七：选择解析与和类型的天然契合

注意 `Input` 类型的定义：

```
data Input = FileInput FilePath | StdInput
```

**这是一个和类型（sum type）**——第二章学的 ADT！而 `input` 解析器用 `<|>` 组合两个解析器，**恰好对应和类型的两个构造子**。

这不是巧合，而是**深层的对称性**：

|类型层面|解析器层面|
|---|---|
|`data Input = A B`|`aParser`|
|`data Input = C`|`cParser`|
|`A` 或 `C`|`aParser <|

**解析器的 `<|>` 直接对应和类型的 `|`**——这是 Haskell "类型与解析对称"哲学的极致体现。

Stephan Schiffels 的教程给出了更复杂的实例 ：

```
data SummaryStatSpec = Heterozygosity | SegregatingSites | HardyWeinbergDeviation

summaryStatParser :: Parser SummaryStatSpec
summaryStatParser = hetParser <|> segSitesParser <|> hwParser
  where
    hetParser = flag' Heterozygosity (long "heterozygosity")
    segSitesParser = flag' SegregatingSites (long "segregatingSites")
    hwParser = flag' HardyWeinbergDeviation (long "hardyWeinbergDev")
```

**这个例子的精妙之处**：每个构造子对应一个解析器，`<|>` 组合它们。如果用户提供了多个选项（如 `--heterozygosity --segregatingSites`），解析器会报错——因为 Alternative 的语义是"恰好一个"，而非"任意多个"。

### 子命令：选择解析的层级化

对于 `git clone`、`git push` 这样的子命令，optparse-applicative 提供 `subparser` 组合子 ：

```
data Command = CloneCloneOptions | Push PushOptions

cloneOptions :: Parser CloneOptions
cloneOptions = Clone <$> strArgument (metavar "REPO")

pushOptions :: Parser PushOptions
pushOptions = Push <$> strArgument (metavar "REMOTE")

commandParser :: Parser Command
commandParser = subparser $
  command "clone" (info cloneOptions (progDesc "Clone a repository"))
  <> command "push" (info pushOptions (progDesc "Push to remote"))
```

**🔑 洞见八：子命令是"嵌套的选择解析"**

- 顶层：`clone` 或 `push`——用 `subparser` 组合
    
- 每个子命令内部：用自己的参数解析器——用 Applicative 组合
    
- 子命令解析器本身又是 `Parser Command`——可以和其他解析器继续组合
    

```
data Options = Options
  { optGlobalFlag :: Bool
  , optCommand :: Command
  }

opts :: Parser Options
opts = Options <$> switch (long "global-flag")
              <*> commandParser
```

**这就是"应用风格 + 选择解析"的嵌套组合**——全局选项用 Applicative 组合，子命令用 Alternative 组合，两者无缝融合。

### 🔑 洞见九：Alternative 让"互斥选项"成为类型安全

传统命令式语言中，互斥选项需要手动检查：

```
if args.file and args.stdin:
    parser.error("Cannot specify both --file and --stdin")
```

在 Haskell 中，**互斥性由类型系统和 Alternative 实例自动保证**：

```
input :: Parser Input
input = fileInput <|> stdInput
```

- 如果用户提供了 `--file`，`fileInput` 成功，`input` 成功
    
- 如果用户提供了 `--stdin`，`fileInput` 失败，回退到 `stdInput`，`input` 成功
    
- 如果用户两者都提供，`fileInput` 成功，**`input` 不会尝试 `stdInput`**——因为 `<|>` 的语义是"第一个成功就返回"
    
- 如果用户两者都不提供，`input` 失败，自动报错
    

> 💡 **这是"make illegal states unrepresentable"哲学在 CLI 解析中的体现**——非法组合（同时指定 `--file` 和 `--stdin`）在类型层面就不可能产生合法的 `Input` 值。如果需要"恰好一个"的语义，可以用 `alternative` 组合子进一步约束。

### 实际应用

```
-- 完整子命令示例
data Command = Add AddOptions | Commit CommitOptions

data AddOptions = AddOptions
  { addFile :: FilePath
  , addMessage :: String
  }

data CommitOptions = CommitOptions
  { commitMessage :: String
  }

addParser :: Parser Command
addParser = Add <$> (AddOptions
  <$> argument str (metavar "FILE")
  <*> strOption (long "message" <> short 'm' <> metavar "MSG"))

commitParser :: Parser Command
commitParser = Commit <$> (CommitOptions
  <$> strOption (long "message" <> short 'm' <> metavar "MSG"))

commandParser :: Parser Command
commandParser = subparser $
  command "add" (info addParser (progDesc "Add file to repository"))
  <> command "commit" (info commitParser (progDesc "Commit changes"))

data Options = Options
  { optVerbose :: Bool
  , optCommand :: Command
  }

parser :: Parser Options
parser = Options <$> switch (long "verbose" <> short 'v')
                <*> commandParser

opts :: ParserInfo Options
opts = info (helper <*> parser)
            (fullDesc <> progDesc "A git-like CLI" 
             <> header "mini-git - a simple git-like tool")

main :: IO ()
main = execParser opts >>= \opts -> case optCommand opts of
  Add (AddOptions file msg) -> 
    putStrLn $ "Adding " ++ file ++ " with message: " ++ msg
  Commit (CommitOptions msg) -> 
    putStrLn $ "Committing with message: " ++ msg
```

## 📝 本章核心洞见总结

> **洞见一：命令行参数解析是 Applicative 的天然应用场景**。
> 
> 命令行选项相互独立、顺序无关——这正是 Applicative 的 `<*>` 语义。如果用 Monad 的 `>>=`，就会被迫固定解析顺序，违背 CLI 惯例。optparse-applicative 官方文档明确说："It is this property which leads us to an Applicative interface instead of a Monadic one"。

> **洞见二：Parser 是 Functor + Applicative + Alternative 的三重实例**。
> 
> `Parser a` 表示一个"对命令行选项的规格说明"，成功解析时产出 `a` 类型的值。这三个类型类实例让解析器可以：用 `<$>` 映射（Functor）、用 `<*>` 组合独立选项（Applicative）、用 `<|>` 选择分支（Alternative）。

> **洞见三：Modifier 是 Monoid 的工业级应用**。
> 
> 每个基本解析器（如 `strOption`）接受一个 Modifier 参数，而 Modifier 是 Monoid 实例，用 `<>` 组合。第十四章学的 Monoid 理论在此刻变成工程现实——`long "file" <> short 'f' <> metavar "FILENAME"` 就是 Monoid 的 `<>` 运算。

> **洞见四：应用风格让 CLI 定义读起来像普通函数调用**。
> 
> `Sample <$> strOption ... <*> switch ... <*> option ...` 几乎和普通构造函数调用 `Sample x y z` 一模一样。这是第十三章"自然升格"的威力——`Parser` 上下文里的构造函数应用，与普通函数应用同构。

> **洞见五：排列解析器（Permutation Parser）是 Applicative 的必然推论**。
> 
> 因为 `<*>` 不要求参数依赖，所以 `Options <$> opt1 <*> opt2` 自动支持"选项任意顺序"。`--target world -q` 和 `-q --target world` 等价——这不是 optparse-applicative 的特性，而是 Applicative 语义的数学推论。

> **洞见六：选择解析的 `<|>` 与和类型的 `|` 对称**。
> 
> `data Input = FileInput FilePath | StdInput` 对应 `fileInput <|> stdInput`。解析器的 `<|>` 直接映射和类型的构造子——这是 Haskell "类型与解析对称"哲学的极致体现。

> **洞见七：Alternative 让"互斥选项"成为类型安全**。
> 
> 传统命令式需要手动检查"不能同时指定 --file 和 --stdin"；在 Haskell 中，`fileInput <|> stdInput` 自动保证：如果 `--file` 成功，`--stdin` 不会被尝试。非法组合在类型层面就不可能产生合法的 `Input` 值。

> **洞见八：子命令是"嵌套的选择解析"**。
> 
> `subparser (command "clone" ... <> command "push" ...)` 用 Alternative 组合子命令，每个子命令内部用 Applicative 组合自己的参数。两层组合无缝融合，构成完整的 CLI 解析器。

> **洞见九：ParserInfo 分离"解析逻辑"与"程序元信息"**。
> 
> `Parser a` 是纯解析规格，`ParserInfo a` 添加帮助文本、程序描述、`--help` 支持。这种分离让解析器可复用、可测试，而程序描述是独立关注的方面。

> **洞见十：optparse-applicative 的四大自动能力**。
> 
> 自动错误处理、自动帮助生成、自动类型转换、自动选项顺序无关——这四者不是库的"功能"，而是 Applicative + Alternative + Monoid + ADT 组合的自然推论。声明式规格本身就包含了生成这些信息所需的全部结构。

## 🛠️ 实践建议

1. **从领域类型开始设计 CLI**：
    
    ```
    data Options = Options { ... }
    -- 先定义 Options，再写 parser :: Parser Options
    -- 让类型驱动解析器的结构
    ```
    
2. **用 Monoid 组合 Modifier**：
    
    ```
    let common = long "file" <> short 'f' <> metavar "FILE"
    -- 复用 common，组合不同的 help
    ```
    
3. **用应用风格组合独立选项**：
    
    ```
    opts = MyOptions <$> opt1 <*> opt2 <*> opt3
    -- 永远不要用 do 语法（除非确实需要依赖性）
    ```
    
4. **用 Alternative 组合选择**：
    
    ```
    inputSource = fileInput <|> stdinInput <|> defaultInput
    -- 让 <|> 处理失败回退
    ```
    
5. **用和类型建模子命令**：
    
    ```
    data Command = Clone CloneOpts | Push PushOpts | Pull PullOpts
    -- 每个构造子对应一个子命令解析器
    ```
    
6. **用 `optional` 让选项非必填**：
    
    ```
    import Control.Applicative (optional)
    filePath :: Parser (Maybe FilePath)
    filePath = optional $ strOption (long "file" <> metavar "FILE")
    ```
    
7. **验证 Applicative/Alternative 定律**：
    
    ```
    -- 在测试中验证
    prop_applicative_identity p = (pure id <*> p) == p
    prop_alternative_empty x = (empty <|> x) == x
    ```

## 🔮 承上启下

第十六章"Monad"会在本章基础上往前推一步——**当解析需要"依赖性"时，Applicative 就不够了**：

- **流式解析**：读取一个 token 后，根据其值决定如何解析下一个 token
    
- **上下文敏感解析**：后续解析依赖前文结果（如匹配括号、XML 标签）
    
- **`Parsec`/`Attoparsec`**：通用解析器组合子库，其 `Parser` 是 Monad 实例
    

更深远的连接：

- **第十六章 Monad**：`(>>=) :: m a -> (a -> m b) -> m b` 解除 Applicative 的"独立性"限制。optparse-applicative 的 `Parser` 是 Applicative 而非 Monad——因为命令行选项独立；但 Parsec 的 `Parser` 是 Monad——因为流式解析需要依赖性
    
- **第二十三章 解析器组合子**：会深入 Parsec/Attoparsec，那时你会看到 Monad 在解析中的核心作用
    
- **第二十章 IO Monad**：`IO` 既是 Applicative 又是 Monad，`optparse-applicative` 的 `execParser :: ParserInfo a -> IO a` 正是从"纯解析"过渡到"IO 执行"的桥梁
    

**第十五章是你理解"抽象到工程"转化关键一跃**。吃透 Applicative + Alternative 在 CLI 解析中的应用，后面的 Monad 在 Parsec 中的应用就不再是"新的魔法"，而是"我们已经知道的知识的自然延伸"——你已经知道 Applicative 处理独立选项，Alternative 处理选择分支；第十六章只是告诉你"当解析需要依赖前文时，升级到 Monad"。
