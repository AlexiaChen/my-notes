
# 第七章 类型类 —— 读书笔记

> 💡 如果说第六章的 `map`/`filter`/`fold` 让你看到了"列表操作的四种递归模式"，那么第七章就是在回答一个更深层的问题：**为什么 `==`、`+`、`compare`、`show` 这些操作能"聪明地"根据类型切换行为，同时保持完全的类型安全？**​ 答案就是类型类（Type Class）。它让 Haskell 在纯函数式、强静态类型的前提下，依然拥有"重载"的表达力——而且这种重载不是 OOP 式的继承，而是**行为与数据的解耦**。

韩冬在这一章安排了三个小节：**7.1 实例声明**、**7.2 类声明**、**7.3 类型类的实现**（含 7.3.1 层级和约束、7.3.2 推导类型类、7.3.3 Show/Read）。表面看是语法教学，实则在揭示 Haskell 类型系统的"第二次跃迁"——第一次跃迁是第四章的 Hindley-Milner 参数多态（"对所有类型一视同仁"），第二次跃迁就是本章的**约束多态 / Ad-hoc 多态**（"对某些类型区别对待，但仍在编译期类型安全"）。

---

## 🎯 全局脉络：为什么类型类是 Haskell 的"第二次跃迁"？

```
第一章~第三章: 具体类型与递归
   ↓
第四章: Hindley-Milner 参数多态
         "length :: [a] -> Int"  —— a 可以是任何类型，行为完全相同
   ↓
第七章: 约束多态（Ad-hoc 多态）  ← 你在这里
         "==" :: Eq a => a -> a -> Bool —— a 必须满足 Eq 约束
   ↓
第十一章: Functor / 第十三章: Applicative / 第十六章: Monad
         （类型类抽象的巅峰：把"容器"、"顺序"、"副作用"编码进类型类）
```

**参数多态的局限**：HM 类型推断让函数能"对所有类型一视同仁"地工作——`length :: [a] -> Int` 里，`a` 是什么类型根本不影响 `length` 的行为。但现实里有很多操作**必须**因类型而异：

- `==` 在 `Int` 上是机器级比较，在 `Float` 上是浮点比较，在 `Tree` 上是递归比较
    
- `+` 对不同数字类型有不同的硬件指令
    
- `show` 把值转成字符串，每种类型都有自己的格式
    

如果只用参数多态，你就得给每个类型写一个单独的 `==`——这就是所谓的"指数爆炸"（exponential blow-up）。OOP 用继承解决这个问题，但代价是**行为被绑死在数据上**——想给内置的 `Int` 加个行为？抱歉，改不了源码。

**类型类就是 Haskell 的答案**：它把"行为"抽象成独立的接口（类声明），然后让任意类型通过实例声明"贴上"这个行为。这种行为与数据的解耦，是 Haskell 区别于所有 OOP 语言的根本特征。

## 7.1 实例声明：给类型"贴上"行为

实例声明（`instance`）是类型类的" Half"——它告诉编译器："对于这个具体类型，类型类里声明的那些方法该怎么实现。"

### 基本形态

```
data Color = Red | Green | Blue

instance Eq Color where
  Red   == Red   = True
  Green == Green = True
  Blue  == Blue  = True
  _     == _     = False

instance Show Color where
  show Red   = "Red"
  show Green = "Green"
  show Blue  = "Blue"
```

### 🔑 洞见一：实例声明是"开放"的

这是类型类与 OOP 接口最深刻的差异。在 Java 里，一个类实现哪些接口必须在类定义时就写好；在 Haskell 里，**实例声明可以在任何地方、任何时候追加**——

- 可以给**内置类型**补一个实例（比如给 `Int` 加一个 `MyClass` 实例）
    
- 可以给**别人定义的类型**补一个实例（只要类型类也是你定义的，或遵循 OOP 的孤儿实例规则）
    
- 类型类和类型的定义**完全解耦**
    

> 💡 这种"开放世界假设"（open-world assumption）意味着：行为扩展不再受数据类型源码的限制。这是 Haskell 生态能如此灵活地" retrofit"各种抽象到现有类型上的根本原因。

### 🔑 洞见二：实例可以带约束——这就是"层级"

当你的数据类型是参数化的（如 `Tree a`），要给它加 `Eq` 实例，就需要 `a` 本身也是 `Eq`：

```
instance Eq a => Eq (Tree a) where
  Leaf == Leaf = True
  Node x l r == Node x' l' r' = x == x' && l == l' && r == r'
  _ == _ = False
```

`Eq a =>` 这个约束意味着：**只有当 `a` 是 `Eq` 的实例时，`Tree a` 才是 `Eq` 的实例**。这就是类型类层级的雏形——它会在 7.3.1 节正式展开，也是后续 `Functor`、`Foldable` 等抽象能递归地"传播"约束的机制。

### 🔑 洞见三：实例声明与模式匹配的天然契合

注意上面 `Eq Color` 的实例——方法的实现就是用**模式匹配**写出来的。这呼应了第二章学的核心概念：

- 第二章用 `data` 定义"值空间"
    
- 第七章用 `instance` 为这个值空间定义"行为"
    
- **实例方法的实现 = 对该类型的模式匹配**
    

> 📌 **连接第二章**：`data` 声明定义"这个类型有哪些可能的值"，`instance` 声明定义"这些值如何参与某个行为"。两者配合，构成了 Haskell "数据 + 行为"分离设计的双柱。

### 实际应用

```
-- 在 GHCi 里试：
-- λ> data Color = Red | Green | Blue deriving (Eq, Show)
-- λ> Red == Red
-- True
-- λ> Red == Green  
-- False
-- λ> show Red
-- "Red"
```

## 7.2 类声明：定义"行为契约"

类声明（`class`）是类型类的另一 Half——它定义一组方法（method）的**类型签名**，但不提供实现。

### 标准库中最经典的例子

```
class Eq a where
  (==) :: a -> a -> Bool
  (/=) :: a -> a -> Bool
```

### 🔑 洞见四：类声明是"行为的接口"

类声明定义了一个**契约**：任何想要成为 `Eq` 实例的类型，必须提供 `(==)` 和 `(/=)` 的具体实现。

注意一个精妙之处：`(==)` 和 `(/=)` 在类声明里是**相互独立的**——理论上你可以只实现其中一个。但实际上 Haskell 允许在类声明里给方法提供**默认实现**：

```
class Eq a where
  (==) :: a -> a -> Bool
  (/=) :: a -> a -> Bool
  x == y = not (x /= y)   -- 默认实现
  x /= y = not (x == y)   -- 默认实现
```

这样，实例声明时只需实现其中一个，另一个自动获得默认实现。这是类型类相比 OOP 接口的又一个优势——**原生支持默认方法**。

### 🔑 洞见五：类声明可以带约束——这就是"层级"

类声明本身也可以有约束：

```
class Eq a => Ord a where
  (<)  :: a -> a -> Bool
  (<=) :: a -> a -> Bool
  (>)  :: a -> a -> Bool
  (>=) :: a -> a -> Bool
  compare :: a -> a -> Ordering
  -- ... 默认实现
```

`class Eq a => Ord a` 读作："**任何想成为 `Ord` 实例的类型，首先必须是 `Eq` 的实例**"。

这就是类型类层级（hierarchy）的核心机制：

- `Eq` 是最底层（比较相等）
    
- `Ord` 依赖 `Eq`（比较大小必须先能比较相等）
    
- 后续还会有更多层级关系
    

> 💡 这种层级不是 OOP 的继承链，而是**约束的传递**。一个类型想"升级"到 `Ord`，它必须先"拥有" `Eq`——这是一种**能力依赖**，而非父子关系。

### 🔑 洞见六：类声明与"约束多态"的对接

类声明定义好后，函数的类型签名就可以使用**限定类型（qualified type）**：

```
(==) :: Eq a => a -> a -> Bool
elem :: Eq a => a -> [a] -> Bool
sort :: Ord a => [a] -> [a]
```

`=> 左边的`Eq a`叫**上下文（context）**，它表达了"类型变量`a` 必须满足的约束"。

这意味着：

- `elem` 可以对**任何**是 `Eq` 实例的类型工作
    
- 但不是对**所有**类型工作——`elem (const 1) [const 1]` 会编译失败，因为函数类型没有 `Eq` 实例
    
- **类型安全在编译期就保证了**——你不可能意外地对不可比较的类型调用 `==`
    

### 🔑 洞见七：类型类 vs OOP 接口的本质区别

|维度|Haskell 类型类|OOP 接口|
|---|---|---|
|核心逻辑|行为"贴"到任意类型上|行为必须由子类继承实现|
|内置类型支持|直接给 `Int`/`String` 加行为|必须新建子类|
|默认实现|原生支持|Java 8 后才支持|
|多参数|支持（需解决歧义）|无原生支持|
|世界观|开放（可为已有类型补实例）|封闭（类定义时就固定）|

> 📌 **这是本章最深刻的洞见**：类型类不是"Haskell 版的接口"。它是**行为与数据彻底解耦**的机制——行为定义（class）和数据定义（data）是完全独立的两个维度，通过实例声明（instance）在需要时组合。这种二维自由度，是 OOP 的一维继承链无法企及的。

## 7.3 类型类的实现

这一节是"理论与实践"的桥梁——讲类型类在 Haskell 里如何落地。

### 7.3.1 层级和约束

类型类的层级通过"类声明里的约束"和"实例声明里的约束"双重表达：

```
-- 类声明时的约束：Ord 要求 Eq
class Eq a => Ord a where
  -- ...

-- 实例声明时的约束：Tree a 的 Eq 实例要求 a 是 Eq
instance Eq a => Eq (Tree a) where
  -- ...
```

**🔑 洞见八：约束会沿数据结构"自动传播"**

这是类型类层级最强大的地方。一旦你写了：

```
instance Eq a => Eq (Tree a) where ...
```

那么：

- `Tree Int` 自动成为 `Eq`（因为 `Int` 是 `Eq`）
    
- `Tree (Tree Bool)` 也自动成为 `Eq`（因为 `Tree Bool` 是 `Eq`，因为 `Bool` 是 `Eq`）
    
- 这种传播是**递归的、自动的**
    

> 💡 这种"约束传播"机制，让 Haskell 的抽象能自然地作用于嵌套数据结构。后续的 `Functor`、`Foldable`、`Traversable` 都依赖这个机制——`fmap` 能作用于 `Tree (Maybe [Int])`，正是因为约束沿着每一层自动传播。

### 7.3.2 推导类型类（Deriving）

手工写实例声明很繁琐。Haskell 提供了一个语法糖——`deriving`：

```
data Color = Red | Green | Blue
  deriving (Eq, Ord, Show, Read, Enum, Bounded)
```

编译器会自动为你生成这些类型类的实例。

**🔑 洞见九：Deriving 是"行为的标准实现"**

对于 `Eq`、`Ord`、`Show`、`Read`、`Enum`、`Bounded` 这几个标准类型类，编译器知道"对于一个 ADT，最自然的实例实现是什么"：

- `Eq`：按构造函数和字段逐一比较
    
- `Ord`：按构造函数声明顺序比较（先比较构造子，再递归比较字段）
    
- `Show`：输出 `ConstructorName field1 field2 ...` 形式的字符串
    
- `Read`：解析这种形式的字符串
    
- `Enum`：按构造函数声明顺序枚举
    
- `Bounded`：第一个构造子是 `minBound`，最后一个构造子是 `maxBound`
    

> 💡 **Deriving 的真正意义**：它揭示了 Haskell 的一个设计哲学——**"标准行为应该免费"**。对于 90% 的场景，编译器生成的实例就是你要的；对于那 10% 的特殊需求，你才需要手工写 `instance`。

### 7.3.3 Show/Read：显示与解析的对偶

`Show` 和 `Read` 是一对镜像类型类：

```
class Show a where
  show :: a -> String

class Read a where
  read :: String -> a
```

它们在 GHCi 里扮演了关键角色：

```
λ> show 42
"42"
λ> read "42" :: Int
42
λ> read "True" || False
True
```

**🔑 洞见十：为什么 GHCi 需要 Show 实例？**

当你在 GHCi 里输入一个表达式，它会：

1. 求值表达式得到一个值
    
2. **调用 `show` 把这个值转成字符串**
    
3. 打印字符串
    

如果值的类型没有 `Show` 实例，第二步就会失败：

```
λ> data Foo = Foo Int
λ> Foo 3
-- 错误：No instance for (Show Foo) arising from a use of 'print'
```

这就是为什么很多初学者在 GHCi 里看到自定义类型时遇到 `No instance for (Show ...)` 的错误——**不是值有问题，是没有告诉 Haskell 怎么显示它**。

**🔑 洞见十一：Show 与 Read 的"往返"性质**

理想情况下，`show` 和 `read` 应该互为逆操作：

```
read (show x) == x
```

但这不是类型类强制的——它只是一个**约定**（law）。Haskell 的类型类可以声明"定律"（law），但编译器不会强制检查。这是 Haskell 类型类与 OOP 接口的另一个区别：**类型类可以附带"应该遵守"的代数定律，但这些定律是约定而非强制**。

> ⚠️ 实践中，标准类型类的定律（如 `Eq` 的对称性、传递性，`Monoid` 的结合律）由社区约定遵守。违反定律会导致依赖这些定律的抽象（如 `fold`、`traverse`）行为异常。这是 Haskell "类型类文化"的重要部分。

## 📝 本章核心洞见总结

> **洞见一：类型类解决的是"Ad-hoc 多态"问题**。
> 
> 参数多态让函数对所有类型一视同仁（如 `length`），但 `==`、`+`、`show` 必须因类型而异。类型类通过"约束多态"在保持 HM 类型推断的同时，实现了安全的重载——编译期通过字典传递（dictionary passing）解析重载，无运行时开销。

> **洞见二：类型类是"行为与数据的解耦"**。
> 
> OOP 把行为绑死在数据（类）上，导致改不了内置类型、类爆炸、代码重复。Haskell 反其道而行——`class` 定义行为契约，`data` 定义数据类型，`instance` 在需要时把两者组合。一个类型可以获得任意多个类型类的能力，一个类型类也可以被任意多个类型实现。

> **洞见三：类型类 ≠ OOP 接口**。
> 
> 开放世界假设（可为已有类型补实例）、原生默认方法、多参数支持、约束传播——这些特性让类型类在表达能力上远超 OOP 接口。Rust 的 trait、Scala 的 implicits 都是类型类的精神后裔。

> **洞见四：层级通过约束实现**。
> 
> `class Eq a => Ord a` 意味着"成为 Ord 实例的前提是已经是 Eq 实例"。这种**能力依赖**而非父子继承，让类型类层级能自然地作用于嵌套数据结构——`Tree Int` 自动获得 `Ord` 实例，因为约束沿结构递归传播。

> **洞见五：Deriving 是"标准行为免费化"**。
> 
> 对于 `Eq`、`Ord`、`Show`、`Read`、`Enum`、`Bounded`，编译器知道最自然的实例实现。90% 的场景用 `deriving` 就够了，10% 的特殊需求才手工写 `instance`。这体现了 Haskell "约定优于配置"的设计哲学。

> **洞见六：Show/Read 是显示与解析的对偶**。
> 
> `Show` 让值在 GHCi 里能打印，`Read` 让字符串能解析回值。它们的"往返定律" `read (show x) == x` 是约定而非强制——这揭示了 Haskell 类型类的一个重要特征：**类型类可以声明定律，但编译器不强制检查，遵守定律是社区文化**。

> **洞见七：类型类为后续所有抽象埋下伏笔**。
> 
> 第十一章的 `Functor` 是 `map` 的推广（"容器内的变换"），第十三章的 `Applicative`、第十六章的 `Monad` 都是类型类。理解第七章的 `class` / `instance` / 约束，就等于拿到了打开 Haskell 抽象金字塔的钥匙。

## 🛠️ 实践建议

1. **刻意练习"行为解耦"思维**：
    
    ```
    data Expr = Val Int | Add Expr Expr | Mul Expr Expr
    
    -- 求值：业务行为
    eval :: Expr -> Int
    
    -- 显示：调试行为  
    instance Show Expr where ...
    
    -- 相等：测试行为
    instance Eq Expr where ...
    ```
    
    体会"同一个数据类型，通过不同实例获得不同能力"。
    
2. **多用 deriving，少用手工 instance**：
    
    ```
    data User = User
      { name :: String
      , age  :: Int
      } deriving (Eq, Ord, Show, Read)
    ```
    
    只有默认实现不满足需求时，才手工写 instance。
    
3. **在 GHCi 里用 `:info` 探索类型类**：
    
    ```
    :info Eq
    :info Ord  
    :info Show
    ```
    
    看类声明的方法、默认实现、已知实例。
    
4. **理解约束的传播**：
    
    ```
    -- 这个函数的 a 必须是 Ord（隐含 Eq）
    sort :: Ord a => [a] -> [a]
    
    -- 这个函数的 a 必须同时是 Num 和 Ord
    sumTwoSmallest :: (Num a, Ord a) => [a] -> a
    ```
    
    多个约束用逗号分隔，写在 `=>` 左边。
    
5. **警惕"定律"的约定性质**：
    
    当你为一个类型实现 `Eq`、`Monoid`、`Functor` 等类型类时，主动检查是否满足代数定律。不满足定律的实例会在高层抽象中引发诡异 bug。

## 🔮 承上启下

第八章"数字相关的类型类"会沿着本章建立的框架，具体展开 Haskell 的数字类型类层级：

- **`Ord`**：顺序类——全序比较（第七章已初步涉及）
    
- **`Enum`**：枚举类——可在序列中枚举（支撑 `[1..10]` 语法）
    
- **`Bounded`**：边界类——有上下界
    
- **`Num`**：数字类——提供 `+`、`-`、`*` 等运算
    

这些类型类共同构成了 Haskell 数字系统的抽象层级。理解了第七章的"类声明 + 实例声明 + 约束"，第八章就是看这些机制在标准库里的具体应用。

更深远的连接：

- **第十一章 Functor**：`fmap :: Functor f => (a -> b) -> f a -> f b`——类型类推广了 `map`
    
- **第十六章 Monad**：`(>>=) :: Monad m => m a -> (a -> m b) -> m b`——类型类编码了"带副作用计算"的抽象
    
- **第二十二章 Foldable/Traversable**：类型类推广了 `fold` 和"遍历+映射"
    

**第七章是你理解 Haskell "类型类驱动抽象"的起点**。吃透 `class`、`instance`、约束多态这三块基石，后面的 Functor/Applicative/Monad 就不再是"新的魔法"，而是"我们已经知道的知识的自然延伸"——你已经知道类型类怎么定义行为契约、怎么给类型贴行为、约束怎么沿结构传播；后面只是看这些行为契约越来越抽象、越来越强大。
