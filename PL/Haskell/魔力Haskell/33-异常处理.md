## 33.1 使用 Either/Maybe 表示异常

### Maybe：最简单的失败建模

教学笔记给出了经典示例 ：

```
-- 可能失败的计算
data Maybe a = Nothing | Just a

-- 除零安全版本
safeDivide :: Int -> Int -> Maybe Int
safeDivide _ 0 = Nothing
safeDivide x y = Just (x `div` y)

-- 使用
case safeDivide 10 0 of
  Nothing -> putStrLn "Division by zero!"
  Just result -> putStrLn $ "Result: " ++ show result
```

**🔑 洞见二：Maybe 适用于"失败不需要详细信息"的场景**

Stef Vuckovic 的笔记总结 ：

> *"Use Cases: Partial functions (not defined for all inputs) Functions that could fail without needing detailed error information"

### Either：带错误信息的失败建模

```
-- 自定义错误类型
data DivideError = DivideByZero | OverflowError
  deriving Show

-- 带错误信息的除法
safeDivide' :: Int -> Int -> Either DivideError Int
safeDivide' _ 0 = Left DivideByZero
safeDivide' x y 
  | x > maxBound `div` y = Left OverflowError
  | otherwise = Right (x `div` y)

-- 使用
case safeDivide' 10 0 of
  Left DivideByZero -> putStrLn "Cannot divide by zero!"
  Left OverflowError -> putStrLn "Overflow would occur!"
  Right result -> putStrLn $ "Result: " ++ show result
```

**🔑 洞见三：Either 适用于"调用者需要知道失败原因"的场景**

Stef Vuckovic 的笔记 ：

> *"Either: Used when you need to provide more detailed error information"

### 多错误的组合：do notation 的力量

```
-- 使用 do notation 组合多个可能失败的计算
validatePerson :: String -> Int -> Either String Person
validatePerson name age = do
  validName <- if null name 
    then Left "Name cannot be empty" 
    else Right name
  validAge <- if age < 0 || age > 120 
    then Left "Age is unrealistic" 
    else Right age
  return $ Person validName validAge
```

**关键优势**：do notation 让错误在第一个 `Left` 处短路，后续计算不再执行——这与异常的传播语义完全一致，但在类型层面显式可见。

### Validation：收集所有错误

```
-- 不同于 Either 的短路，Validation 收集所有错误
data Validation err a = Failure err | Success a

-- 并行验证
validateAll :: String -> Int -> Validation [String] Person
validateAll name age = 
  case (validateName name, validateAge age) of
    (Success n, Success a) -> Success (Person n a)
    (Failure e1, Failure e2) -> Failure (e1 ++ e2)
    (Failure e, _) -> Failure e
    (_, Failure e) -> Failure e
```

### 🔑 洞见四：返回类型 vs 异常的决策树

|场景|推荐方式|理由|
|---|---|---|
|失败无信息|`Maybe a`|最简单|
|失败需信息|`Either e a`|显式错误类型|
|收集所有错误|`Validation [e] a`|非短路|
|IO 操作失败|`IO a` + 异常|IO 本质不可纯|
|程序员错误|`error` / `undefined`|不应被捕获|
|第三方库异常|`Control.Exception`|不可避免|

## 33.2 运行时异常

### Control.Exception 的核心 API

Haskell.org 的官方文档 ：

```
import Control.Exception

-- 抛出同步异常
throwIO :: Exception e => e -> IO a

-- 捕获异常
catch :: Exception e => IO a -> (e -> IO a) -> IO a
handle :: Exception e => (e -> IO a) -> IO a -> IO a
try :: Exception e => IO a -> IO (Either e a)

-- 清理
finally :: IO a -> IO b -> IO a
bracket :: IO a -> (a -> IO b) -> (a -> IO c) -> IO c
onException :: IO a -> IO b -> IO a
```

### 异常类型层次

Haskell.org 文档 ：

> _"The exception type. Every exception that GHC throws is a member of this class... The three main groups of exceptions are: Those for IO errors, those for pure errors, and those for asynchronous exceptions."_

**异常类型层次**：

```
SomeException
├── IOException
│   ├── IOError
│   └── ...
├── ArithException
│   ├── DivideByZero
│   ├── Overflow
│   └── ...
├── ErrorCall
│   └── ErrorCall String
├── AsyncException
│   ├── ThreadKilled
│   ├── UserInterrupt
│   └── ...
└── 自定义异常（需 derive Exception）
```

### 自定义异常

Kazu Yamamoto 的文章 给出了完整示例：

```
import Control.Exception

data EarlyReturn = EarlyReturn
  deriving (Eq, Show)

instance Exception EarlyReturn

-- 使用自定义异常实现早期返回
early_return :: IO ()
early_return = handle ignore $ do
  when condition1 $ throwIO EarlyReturn
  when condition2 $ throwIO EarlyReturn
  action1
  action2
  action3
  where
    ignore EarlyReturn = return ()
```

**🔑 洞见五：自定义异常需要 `Typeable` 和 `Show` 实例**

Kazu Yamamoto 解释 ：

> _"The important methods of the Exception class are as follows: class (Typeable e, Show e) => Exception e where toException :: e -> SomeException; fromException :: SomeException -> Maybe e"_

### catch/try/handle 的区别

Tarik Billa 的文章 精准总结：

> _"try :: Exception e => IO a -> IO (Either e a)... catch is similar to try. It first tries to run the specified IO action, but if an exception is thrown the handler is given the exception to get an alternative answer... handle is simply catch with the arguments in the reversed order."_

```
-- try：返回 Either
main = do
  result <- try (evaluate $ 5 `div` 0) :: IO (Either SomeException Int)
  case result of
    Left ex -> putStrLn $ "Caught exception: " ++ show ex
    Right val -> putStrLn $ "The answer was: " ++ show val

-- catch：处理函数
main = catch (print $ 5 `div` 0) handler
  where
    handler :: SomeException -> IO ()
    handler ex = putStrLn $ "Caught exception: " ++ show ex

-- handle：参数反转的 catch
main = handle handler (print $ 5 `div` 0)
  where
    handler ex = putStrLn $ "Caught exception: " ++ show ex
```

### 🔑 洞见六：catch 的非确定性选择

Haskell.org 文档 明确指出：

> _"due to Haskell's unspecified evaluation order, an expression may return one of several possible exceptions: consider the expression error 'urk' + 1 `div` 0. Does catch execute the handler passing ErrorCall 'urk', or ArithError DivideByZero? The answer is 'either': catch makes a non-deterministic choice about which exception to catch."_

**这意味着**：`catch` 只会捕获它声明类型的异常，如果实际抛出的异常类型不匹配，异常会继续向上传播。

### 纯计算中的异常

Tarik Billa 的文章 给出关键警告：

> _"if you want to catch an exception from a pure computation, you will have to use evaluate to force evaluation within the try"_

```
-- ❌ 错误：纯计算不会被 try 捕获
badTry :: IO (Either SomeException Int)
badTry = try $ 5 `div` 0  -- 异常不会在此处抛出！

-- ✅ 正确：用 evaluate 强制求值
goodTry :: IO (Either SomeException Int)
goodTry = try (evaluate $ 5 `div` 0)
```

### 33.2.1 异步异常

#### 同步异常 vs 异步异常

safe-exceptions 文档 给出了清晰定义：

> _"Synchronous exceptions are generated by the current thread. What's important about these is that we generally want to be able to recover from them... Asynchronous exceptions are thrown by either a different user thread, or by the runtime system itself... In contrast to synchronous exceptions, we almost never want to recover from asynchronous exceptions."_

|维度|同步异常|异步异常|
|---|---|---|
|抛出者|当前线程|其他线程或 RTS|
|示例|`throwIO`、`error`、IO 错误|`ThreadKilled`、`timeout`、`race`|
|可恢复性|通常可恢复|**不可恢复**​|
|处理方式|`catch`/`try` 恢复|`bracket`/`mask` 清理后重抛|

#### 异步异常的来源

Kazu Yamamoto 的文章 ：

> _"Asynchronous exception are ones thrown by other threads. You can re-throw them to yourself via throwIO when you catch them."_

典型来源 ：

1. **`throwTo`**：其他线程显式抛出
    
2. **`timeout`**：超时杀死线程
    
3. **`race`**（async 库）：竞速中失败的一方被杀死
    
4. **`BlockedIndefinitelyOnMVar`**：MVar 死锁检测
    
5. **`BlockedIndefinitelyOnSTM`**：STM 死锁检测
    
6. **`UserInterrupt`**：Ctrl+C 信号
    

#### FP Complete 的异步异常安全规则

FP Complete 文章 给出了三条铁律：

> _"If you ever catch an async exception, you must rethrow it (no recovery allowed)... You should minimize the amount of time you spend in a masked state to ensure prompt response to async exceptions... having a complex network protocol run inside cleanup code is a bad idea."_

**三条规则**：

1. **捕获异步异常后必须重抛**——不可恢复
    
2. **最小化掩码时间**——确保及时响应异步异常
    
3. **清理代码要简单**——不要在清理中做复杂 IO
    

#### mask：保护关键区域

```
import Control.Exception

-- 掩码异步异常
mask :: ((forall a. IO a -> IO a) -> IO b) -> IO b

-- 不可中断的掩码
uninterruptibleMask :: ((forall a. IO a -> IO a) -> IO b) -> IO b

-- 典型模式：获取资源 -> 掩码 -> 使用资源 -> 释放
criticalSection :: IO a -> IO a
criticalSection action = mask $ \restore -> do
  acquireResource
  result <- restore action `onException` releaseResource
  releaseResource
  return result
```

### 🔑 洞见七：异步异常的黄金法则

safe-exceptions 文档 ：

> _"Asynchronous exceptions can only be cleaned up after... This library prevents you from making the following mistakes: Catching and swallowing an asynchronous exception; Throwing an asynchronous exception synchronously; Throwing a synchronous exception asynchronously; Swallowing asynchronous exceptions via failing cleanup handlers"_

**四条禁忌**：

1. ❌ 捕获并吞掉异步异常
    
2. ❌ 把异步异常当作同步异常抛出
    
3. ❌ 把同步异常当作异步异常抛出
    
4. ❌ 在清理处理器中吞掉异步异常
    

### 33.2.2 资源的清理和释放

#### bracket：资源管理的黄金标准

safe-exceptions 文档 明确指出：

> _"If you need to perform some allocation or cleanup of resources, use one of the following functions (and don't use the catch/handle/try family of functions): onException, withException, bracket, bracket_, finally, bracketOnError, bracketOnError_"_

```
-- bracket 的标准用法
bracket :: IO a          -- 获取资源
        -> (a -> IO b)  -- 释放资源
        -> (a -> IO c)  -- 使用资源
        -> IO c

-- 文件操作
readFileSafe :: FilePath -> IO String
readFileSafe path = bracket
  (openFile path ReadMode)  -- acquire
  hClose                    -- release
  (\h -> hGetContents h)    -- use
```

#### bracket 的异常安全性

无论使用资源的过程发生什么：

- **正常完成**：资源被释放
    
- **抛出同步异常**：资源被释放，异常继续传播
    
- **收到异步异常**：资源被释放，异步异常被重抛
    

#### finally：简化版本

```
-- finally：无论成功失败都执行清理
finally :: IO a -> IO b -> IO a

-- 等价于 bracket (return ()) (\_ -> cleanup) action
doSomething :: IO ()
doSomething = do
  acquireResource
  action `finally` releaseResource
```

#### onException：仅在异常时清理

```
-- onException：仅当异常发生时才清理
onException :: IO a -> IO b -> IO a

-- 用于"尝试提交，失败则回滚"
commitWithRollback :: IO ()
commitWithRollback = do
  prepareChange
  commitChange `onException` rollbackChange
```

#### FP Complete 的反模式警示

FP Complete 文章 给出了一个"看似正确实则错误"的例子：

> _"Is the following an example of good or bad asynchronous exception handling? bracket openConnection closeConnection $ \conn -> bracket (sendHello conn) (sendGoodbye conn) (startConversation conn) Answer: Bad!"_

**为什么坏**？内层 bracket 的清理代码 `sendGoodbye conn` 是复杂的网络协议操作——如果在清理期间收到异步异常，会导致连接状态不一致。

**正确做法**​ ：

```
-- 最小化清理代码的复杂度
bracket openConnection closeConnection $ \conn -> do
  sendHello conn
  startConversation conn
  -- 不要在内层 bracket 中做复杂清理
  -- 或者：将 sendGoodbye 放在 finally 中，接受它可能失败
  `finally` sendGoodbye conn
```

### 🔑 洞见八：资源清理的四条军规

1. **永远用 bracket 管理资源**——不要手动 `acquire` 后 `release`
    
2. **清理代码必须简单**——复杂 IO 不要在清理中做
    
3. **最小化掩码时间**——`restore` 应尽快调用
    
4. **异步异常不可恢复**——捕获后必须重抛

## 33.3 纯函数中的异常处理

### 纯函数中的异常陷阱

Tarik Billa 的文章 明确指出：

> _"this type of exception handling can only happen in impure code (i.e. the IO monad). If you need to handle errors in pure code, you should look into returning values using Maybe or Either instead"_

### 为什么不在纯函数中使用异常

Haskell.org 文档 给出关键原因：

> _"Note that due to Haskell's unspecified evaluation order, an expression may return one of several possible exceptions"_

```
-- 这个表达式可能抛出 error "urk" 或 DivideByZero
-- 具体哪个取决于求值顺序——不可预测！
badExpr = error "urk" + 1 `div` 0

-- 用 Either 显式建模
goodExpr :: Either String Int
goodExpr = do
  Left "urk"  -- 显式错误
  Right (1 `div` 0)  -- 显式错误
```

### 纯函数异常处理的唯一合法场景

**例外**：当性能至关重要且失败极 rare 时，可以用 `error` 表示"程序员错误"：

```
-- 程序员错误（不应被捕获）
head :: [a] -> a
head (x:_) = x
head [] = error "Prelude.head: empty list"

-- 用户应使用安全的 head
safeHead :: [a] -> Maybe a
safeHead [] = Nothing
safeHead (x:_) = Just x
```

### 🔑 洞见九：错误 vs 异常的哲学区分

教学笔记 总结：

> _"Exceptions: Unexpected conditions that can be handled (e.g., file not found). Errors: Serious issues that typically indicate bugs (e.g., division by zero)."_

|类别|示例|处理方式|
|---|---|---|
|程序员错误|`head []`、`undefined`|`error`，不应捕获|
|可预期失败|文件不存在、除零|`Maybe`/`Either`|
|不可预期 IO 异常|网络断开、权限不足|`Control.Exception`|
|异步异常|`ThreadKilled`、`timeout`|`bracket`/`mask`|

## 33.4 异常和单子变换

### 33.4.1 exceptions 包

#### MonadThrow/MonadCatch/MonadMask 类型类

FP Complete 文章 强烈推荐：

> _"The solution to this is the MonadThrow typeclass from the exceptions package... The MonadThrow typeclass is a tradeoff, but it's a well thought out tradeoff, and usually the right one."_

```
class Monad m => MonadThrow m where
  throwM :: Exception e => e -> m a

class MonadThrow m => MonadCatch m where
  catch :: Exception e => m a -> (e -> m a) -> m a

class MonadCatch m => MonadMask m where
  mask :: ((forall a. m a -> m a) -> m b) -> m b
  uninterruptibleMask :: ((forall a. m a -> m a) -> m b) -> m b
```

#### MonadThrow 的组合性优势

FP Complete 文章 给出对比：

```
-- 不灵活：类型不统一
lookup :: Eq k => k -> [(k, v)] -> Either (KeyNotFound k) v
f :: SomeVal -> SomeVal -> SomeVal -> Either F'sExceptionType F'sResult

-- 灵活：统一接口
lookup :: (MonadThrow m, Eq k) => k -> [(k, v)] -> m v
f :: MonadThrow m => SomeVal -> SomeVal -> SomeVal -> m F'sResult
```

**🔑 洞见十：MonadThrow 是"受控的异常"**

- **组合性**：`Maybe`、`Either`、`IO` 等都是 `MonadThrow` 实例
    
- **统一性**：函数签名使用 `MonadThrow m =>`，调用者可选择具体 monad
    
- **类型安全**：异常类型仍受 `Exception` 约束
    

#### ExceptT IO 反模式

FP Complete 文章 猛烈抨击：

> _"A common (bad) design pattern: myFunction :: String -> ExceptT MyException IO Int... There are (at least) three problems with this: It's non-compositional... It gives an implication which is almost certainly false, namely: the only exception that can be thrown from this function is MyException... It is almost always wrong to wrap an ExceptT, EitherT, or ErrorT around an IO-based transformer stack."_

**三个问题**：

1. **不可组合**：与其他异常类型不兼容
    
2. **虚假保证**：`ExceptT MyException IO` 仍然可能抛出任何其他异常
    
3. **叠加负担**：除了 `MyException`，还可能 `throwIO` 抛出其他异常
    

### 🔑 洞见十一：ExceptT 的正确用法

```
-- ❌ 错误：ExceptT 包裹 IO
badDesign :: String -> ExceptT MyException IO Int

-- ✅ 正确：用 MonadThrow
goodDesign :: MonadThrow m => String -> m Int

-- 或者在纯计算中使用 ExceptT（无 IO）
pureComputation :: Except MyException a
pureComputation = ...

-- 运行
runPureComputation :: Except MyException a -> Either MyException a
runPureComputation = runExcept
```

### 33.4.2 monad-control

#### 问题的起源

当使用 monad 变换器栈时，需要在任意层运行 `IO` 操作并正确处理异常：

```
-- 变换器栈
type App a = ReaderT Config (ExceptT AppError (StateT AppState IO)) a

-- 问题：如何在 App 中运行 bracket？
-- bracket :: IO a -> (a -> IO b) -> (a -> IO c) -> IO c
-- 我们需要：App a -> (a -> App b) -> (a -> App c) -> App c
```

#### monad-control 的解决方案

monad-control 提供了 `MonadBaseControl` 类型类，允许在变换器栈中"提升"基 monad 的控制操作：

```
class MonadBase b m => MonadBaseControl b m | m -> b where
  liftBaseWith :: (RunInBase m b -> b a) -> m a
  restoreM :: StM m a -> m a
  
type RunInBase m b = forall a. m a -> b (StM m a)
```

#### 实际使用

```
import Control.Monad.Trans.Control

-- 在变换器栈中使用 bracket
bracketApp :: MonadBaseControl IO m 
          => IO a 
          -> (a -> m b) 
          -> (a -> m c) 
          -> m c
bracketApp acquire release use = 
  liftBaseWith $ \runInBase ->
    bracket acquire 
            (runInBase . release) 
            (\a -> runInBase (use a))
```

#### 🔑 洞见十二：monad-control 与 exceptions 的协同

- **exceptions 包**：提供 `MonadThrow`/`MonadCatch`/`MonadMask` 类型类
    
- **monad-control**：提供 `MonadBaseControl` 用于在变换器栈中运行基 monad 的控制操作
    
- **safe-exceptions**：结合两者，提供类型安全的异常处理
    

FP Complete 文章 建议：

> _"safe-exceptions uses type typeclasses from the exceptions package, like MonadCatch and MonadMask... I recommend using unliftio for all new code."_

## 33.5 常见的异常处理问题

### 反模式一：ExceptT IO

FP Complete 文章 ：

> _"It is almost always wrong to wrap an ExceptT, EitherT, or ErrorT around an IO-based transformer stack."_

**问题**：`ExceptT MyException IO` 给人一种"只能抛出 MyException"的虚假安全感，但实际上：

- 任何 `liftIO` 的 IO 操作都可能抛出任何异常
    
- 异步异常随时可能到达
    
- 你只是增加了异常可能性的一个额外维度
    

### 反模式二：捕获所有异常

```
-- ❌ 错误：吞掉所有异常
badHandler :: IO a -> IO (Maybe a)
badHandler action = do
  result <- try action :: IO (Either SomeException a)
  case result of
    Left _ -> return Nothing  -- 吞掉异常！
    Right x -> return (Just x)

-- ✅ 正确：只捕获特定异常
goodHandler :: IO a -> IO (Either IOException a)
goodHandler action = try action
```

safe-exceptions 文档 明确禁止：

> _"prevents you from making the following mistakes: Catching and swallowing an asynchronous exception"_

### 反模式三：在清理代码中做复杂操作

FP Complete 文章 ：

> _"having a complex network protocol run inside cleanup code is a bad idea."_

```
-- ❌ 错误
bracket acquire (\resource -> do
  sendGoodbye resource  -- 复杂网络协议
  logCleanup resource  -- 可能失败的 IO
  updateMetrics resource)  -- 外部服务调用
  useResource

-- ✅ 正确
bracket acquire (\_ -> releaseResource) $ \resource -> do
  result <- useResource resource
  -- 清理在 bracket 外进行，且不在掩码区内
  return result
```

### 反模式四：忘记 evaluate 纯计算

```
-- ❌ 错误：异常不会在 try 中捕获
badTry :: IO (Either SomeException Int)
badTry = try $ 5 `div` 0

-- ✅ 正确
goodTry :: IO (Either SomeException Int)
goodTry = try (evaluate $ 5 `div` 0)
```

### 反模式五：异步异常恢复

```
-- ❌ 错误：试图恢复异步异常
badAsyncHandler :: IO a -> IO a
badAsyncHandler action = action `catch` \e -> do
  case e of
    ThreadKilled -> do
      putStrLn "Thread killed, but I'll continue!"  -- 错误！
      return defaultValue
    _ -> throwIO e

-- ✅ 正确：清理后重抛
goodAsyncHandler :: IO a -> IO a
goodAsyncHandler action = mask $ \restore -> do
  result <- restore action `onException` cleanup
  return result
  where
    cleanup = putStrLn "Cleaning up before re-throwing..."
    -- 异步异常会自动重抛，因为 onException 不捕获它
```

### 🔑 洞见十三：异常处理的五条最佳实践

基于 safe-exceptions 文档 和 FP Complete 文章 ：

1. **用 `Maybe`/`Either` 处理可预期失败**
    
2. **用 `MonadThrow` 而非 `ExceptT IO`**
    
3. **用 `bracket`/`mask` 管理资源和异步异常**
    
4. **只捕获你能处理的特定异常**
    
5. **异步异常不可恢复，只能清理后重抛**
    

### 实际应用：完整的异常处理示例

```
{-# LANGUAGE DeriveDataTypeable #-}
{-# LANGUAGE OverloadedStrings #-}

import Control.Exception
import Control.Monad.IO.Class
import Control.Monad.Trans.Control
import Data.Typeable
import qualified Data.ByteString as BS
import System.IO

-- 1. 自定义异常类型
data AppException 
  = ConfigError String
  | DatabaseError String
  | NetworkError String
  deriving (Show, Typeable)

instance Exception AppException

-- 2. 安全的文件读取（使用 bracket）
readConfigFile :: FilePath -> IO (Either AppException String)
readConfigFile path = try $ bracket
  (openFile path ReadMode `catch` \e -> 
    throwIO $ ConfigError $ "Cannot open " ++ path ++ ": " ++ show e)
  hClose
  (\h -> hGetContents h)

-- 3. 使用 MonadThrow 的函数
processFile :: (MonadThrow m, MonadIO m) => FilePath -> m String
processFile path = do
  content <- liftIO $ readFile path
  if null content
    then throwM $ ConfigError "Empty file"
    else return content

-- 4. 资源安全的网络操作
withConnection :: (MonadBaseControl IO m) 
               => IO a 
               -> (a -> m b) 
               -> m b
withConnection connect use = 
  liftBaseWith $ \runInBase ->
    bracket connect 
            (runInBase . closeConnection) 
            (\conn -> runInBase (use conn))
  where
    closeConnection _ = putStrLn "Connection closed"

-- 5. 异步异常安全的长时间运行任务
longRunningTask :: IO a -> IO a
longRunningTask task = mask $ \restore -> do
  putStrLn "Starting task..."
  result <- restore task `onException` do
    putStrLn "Cleaning up after exception..."
  putStrLn "Task completed."
  return result

-- 6. 综合示例：Web 请求处理器
handleRequest :: (MonadBaseControl IO m, MonadThrow m, MonadIO m) 
              => String -> m String
handleRequest url = do
  -- 模拟网络请求
  response <- liftIO $ try $ do
    threadDelay 1000000  -- 模拟网络延迟
    if "error" `elem` words url
      then throwIO $ NetworkError "Simulated network failure"
      else return "Success response"
  
  case response of
    Left (NetworkError msg) -> throwM $ NetworkError msg
    Left e -> throwM e
    Right content -> return content

-- 7. 主函数
main :: IO ()
main = do
  -- 示例1：配置文件读取
  configResult <- readConfigFile "config.txt"
  case configResult of
    Left (ConfigError msg) -> putStrLn $ "Config error: " ++ msg
    Right config -> putStrLn $ "Config loaded: " ++ take 50 config
  
  -- 示例2：异步异常安全任务
  longRunningTask (putStrLn "Working...") `catch` \e -> do
    let _ = e :: SomeException
    putStrLn "Task was interrupted"
  
  -- 示例3：使用 safe-exceptions 模式
  (do
    result <- try $ evaluate (5 `div` 0)
    case result of
      Left e -> putStrLn $ "Caught: " ++ show (e :: SomeException)
      Right x -> putStrLn $ "Result: " ++ show x
   ) `catch` \e -> do
    let _ = e :: SomeException
    putStrLn "Fallback handler"
  
  putStrLn "Done."
```

## 📝 本章核心洞见总结

> **洞见一：Haskell 错误处理的第一定律——纯代码用返回类型，IO 代码用异常**。
> 
> School of Haskell："If you need to handle errors in pure code, you should look into returning values using Maybe or Either instead... This is often preferable as it's more explicit" 。**能用类型表达的失败，就不要用异常**。

> **洞见二：Maybe 适用于"失败无信息"的场景**。
> 
> Stef Vuckovic："Use Cases: Partial functions, Functions that could fail without needing detailed error information" 。**`safeDivide _ 0 = Nothing` 是典型的 Maybe 用法**。

> **洞见三：Either 适用于"失败需详细信息"的场景**。
> 
> Stef Vuckovic："Either: Used when you need to provide more detailed error information" 。**`Left DivideByZero` 比 `Nothing` 提供更多信息**。

> **洞见四：Control.Exception 的 catch/try/handle 只能在 IO 中使用**。
> 
> Haskell.org："all of them may only be used from within the IO monad" 。**纯计算中的异常必须用 `evaluate` 强制求值才能在 `try` 中捕获**​ 。

> **洞见五：catch 对纯计算异常有非确定性**。
> 
> Haskell.org："due to Haskell's unspecified evaluation order, an expression may return one of several possible exceptions... catch makes a non-deterministic choice" 。**``error "urk" + 1 \`div\` 0`` 可能捕获任意一个异常**。

> **洞见六：同步异常可恢复，异步异常不可恢复**。
> 
> safe-exceptions："Synchronous exceptions... we generally want to be able to recover from them... Asynchronous exceptions... we almost never want to recover from asynchronous exceptions" 。**这是 Haskell 异常处理最重要的区分**。

> **洞见七：异步异常的四条禁忌**。
> 
> safe-exceptions："prevents you from making the following mistakes: Catching and swallowing an asynchronous exception; Throwing an asynchronous exception synchronously; Throwing a synchronous exception asynchronously; Swallowing asynchronous exceptions via failing cleanup handlers" 。**违反任何一条都会导致微妙的错误**。

> **洞见八：资源清理必须用 bracket**。
> 
> safe-exceptions："If you need to perform some allocation or cleanup of resources, use one of the following functions... bracket, bracket_, finally, bracketOnError" 。**手动 acquire/release 在异常发生时会导致资源泄漏**。

> **洞见九：清理代码必须简单**。
> 
> FP Complete："having a complex network protocol run inside cleanup code is a bad idea" 。**内层 bracket 的清理代码如果复杂，可能导致异步异常安全问题**。

> **洞见十：MonadThrow 是"受控的异常"**。
> 
> FP Complete："The MonadThrow typeclass is a tradeoff, but it's a well thought out tradeoff, and usually the right one" 。**比 ExceptT IO 更具组合性，与 Maybe/Either/IO 统一**。

> **洞见十一：ExceptT IO 是反模式**。
> 
> FP Complete："It is almost always wrong to wrap an ExceptT, EitherT, or ErrorT around an IO-based transformer stack... It gives an implication which is almost certainly false" 。**三个问题：不可组合、虚假保证、叠加负担**。

> **洞见十二：monad-control 解决变换器栈中的控制操作**。
> 
> `MonadBaseControl` 类型类允许在变换器栈中"提升"基 monad 的控制操作（如 `bracket`），使得 `bracket` 等 IO 操作能在 `ReaderT`/`StateT`/`ExceptT` 栈中正确使用。

> **洞见十三：异常处理的五条最佳实践**。
> 
> 基于 safe-exceptions 和 FP Complete：①用 Maybe/Either 处理可预期失败 ②用 MonadThrow 而非 ExceptT IO ③用 bracket/mask 管理资源和异步异常 ④只捕获你能处理的特定异常 ⑤异步异常不可恢复，只能清理后重抛。

> **洞见十四：自定义异常需要 Exception 实例**。
> 
> Kazu Yamamoto："class (Typeable e, Show e) => Exception e where toException :: e -> SomeException; fromException :: SomeException -> Maybe e" 。**`deriving (Show, Typeable)` + `instance Exception MyException` 即可**。

> **洞见十五：GHC 的世界观——所有 IO 代码都可能抛异常**。
> 
> FP Complete："GHC has already chosen a stance on this: it supports async exceptions, and all code that runs in IO can have exceptions of any type which is an instance of Exception" 。**接受这个世界，写出异步异常安全的代码**。

## 🛠️ 实践建议

1. **纯函数错误处理的选型**：
    
    ```
    -- 最简单：Maybe
    safeHead :: [a] -> Maybe a
    safeHead [] = Nothing
    safeHead (x:_) = Just x
    
    -- 需要错误信息：Either
    data ParseError = UnexpectedChar Char | PrematureEnd
      deriving Show
    
    parseDigit :: Char -> Either ParseError Int
    parseDigit c
      | '0' <= c && c <= '9' = Right (fromEnum c - fromEnum '0')
      | otherwise = Left (UnexpectedChar c)
    
    -- 收集所有错误：Validation
    data Validation e a = Failure e | Success a
    ```
    
2. **IO 异常的正确处理**：
    
    ```
    import Control.Exception
    import qualified Control.Exception.Safe as Safe
    
    -- 读取文件，捕获 IO 异常
    readFileSafe :: FilePath -> IO (Either IOException String)
    readFileSafe path = try (readFile path)
    
    -- 使用自定义异常
    data AppError = ConfigError String | DBError String
      deriving (Show, Typeable)
    instance Exception AppError
    
    loadConfig :: FilePath -> IO Config
    loadConfig path = do
      content <- readFile path `catch` \e ->
        throwIO $ ConfigError $ "Failed to read " ++ path ++ ": " ++ show e
      case parseConfig content of
        Nothing -> throwIO $ ConfigError "Invalid config format"
        Just cfg -> return cfg
    ```
    
3. **资源管理的黄金模式**：
    
    ```
    import Control.Exception
    
    -- 文件操作
    withFileSafe :: FilePath -> IOMode -> (Handle -> IO a) -> IO a
    withFileSafe path mode = bracket
      (openFile path mode)
      hClose
    
    -- 数据库连接
    withDatabase :: ConnectionString -> (DBConn -> IO a) -> IO a
    withDatabase connStr = bracket
      (connect connStr)
      close
    
    -- 锁
    withLock :: MVar () -> IO a -> IO a
    withLock lock action = bracket
      (takeMVar lock)
      (\_ -> putMVar lock ())
      (\_ -> action)
    ```
    
4. **异步异常安全代码**：
    
    ```
    import Control.Exception
    
    -- 关键区域保护
    criticalSection :: IO a -> IO a
    criticalSection action = mask $ \restore -> do
      -- 获取资源（在掩码区内）
      resource <- acquireResource
      -- 使用资源（在 restore 中，允许异步异常）
      result <- restore action `onException` releaseResource resource
      -- 释放资源（在掩码区内）
      releaseResource resource
      return result
    
    -- 最小化掩码时间
    minimalMask :: IO a -> IO a
    minimalMask action = mask $ \restore -> do
      setup
      result <- restore action  -- 尽快进入 restore
      teardown
      return result
    ```
    
5. **变换器栈中的异常处理**：

    {-# LANGUAGE FlexibleContexts #-}
    import Control.Monad.Except
    import Control.Monad.Reader
    import Control.Monad.IO.Class
    import Control.Exception (Exception, throwIO)
    import Control.Monad.Catch (MonadThrow, throwM)
    
    -- 应用变换器栈
    type App a = ReaderT Config (ExceptT AppError IO) a
    
    -- 使用 MonadThrow 而非 ExceptT
    processData :: (MonadThrow m, MonadIO m) => Input -> m Output
    processData input = do
      when (null input) $ throwM $ ValidationError "Empty input"
      liftIO $ validateInput input
    
    -- 运行 IO 操作用于 App 栈
    runIOAction :: (MonadBaseControl IO m) => IO a -> m a
    runIOAction action = liftBaseWith ($ action) >>= restoreM
    
    -- 在 App 中使用 bracket
    withResource :: (MonadBaseControl IO m) 
                 => IO a -> (a -> m b) -> (a -> m c) -> m c
    withResource acquire release use = 
      liftBaseWith $ \runInBase ->
        bracket acquire (runInBase . release) (\a -> runInBase (use a))
