
# 第十二章 透镜组 —— 读书笔记

> 💡 如果说第十一章的 Functor 是"容器可映射性"的抽象，那么第十二章就是在揭示：**Functor 的"多态到类型构造子"这一特性，竟然能让我们把"getter + setter"打包成一个可自由组合的函数**——这就是透镜（Lens）。表面看是"方便地存取嵌套字段"的工程技巧，实则在展示 Haskell 抽象的最高艺术：**用 `forall f. Functor f =>` 这一个类型，同时编码了"读取"、"修改"、"设置"三种操作，而且让它们像函数一样可以用 `.` 组合**。读懂这一章，你就真正理解了"为什么 Functor 是 Haskell 抽象金字塔的基石"。

韩冬在这一章安排了四个小节：**12.1 getter 和 setter**、**12.2 透镜组**、**12.3 view、set 和 over 函数**（含 12.3.1 over、12.3.2 set、12.3.3 view）、**12.4 函数库**。表面是"如何优雅地操作嵌套数据"，实则在回答一个更深层的问题：**为什么 getter 和 setter 必须捆绑？为什么捆绑后还能像函数一样组合？**

## 🎯 全局脉络：为什么透镜是 Haskell 抽象的巅峰之作？

```
第十一章: Functor（fmap :: (a -> b) -> f a -> f b）
   ↓
第十二章: 透镜（Lens s a = forall f. Functor f => (a -> f a) -> s -> f s）  ← 你在这里
   ↓
第十四章: 单位半群 + 应用函子（Const 的应用函子实例）
   ↓
第十六章: 单子（更复杂的"上下文操作"）
```

**这一章是 Functor 抽象能力的"惊艳展示"**。第十一章你学习了 `fmap` 和 Functor 定律，但可能还在疑惑："多态到类型构造子的 `f`，到底能玩出什么花样？" 第十二章给出了最漂亮的答案——**通过让 `f` 在 `Identity` 和 `Const` 之间变化，同一个函数居然能同时充当 getter、setter、modifier**。

更深远的意义在于：透镜组是 Haskell "**让非法状态无法表示**" 哲学的延伸。记录语法允许你直接构造 `Line (Position 0 0) (Position 3 4)`，但如果 `Position` 的不变量是"坐标必须非负"，记录语法无法阻止你写出 `Position (-1) 5`。透镜通过"**必须经过智能构造函数**"来设置字段，从而在字段级别保护不变量——这是第十章"模块导出控制"思想的字段级延伸。

## 12.1 getter 和 setter：嵌套数据的"存取之痛"

### 起点：一个看似简单的问题

韩冬在书中给出了一个直击痛点的例子 ：

```
data Position = Position { positionX :: Double, positionY :: Double }

data Line = Line { lineStart :: Position, lineEnd :: Position }

line1 = Line (Position 0 0) (Position 3 4)
```

现希望将 `line1` 的终点纵坐标从 `4` 变为 `5`。

### 🔑 洞见一：getter 天然可组合，setter 天生不可组合

**getter 的组合是优雅的**——因为 getter 是纯函数 `s -> a`，函数组合天然流畅：

```
-- 获取 line1 终点纵坐标
getY :: Line -> Double
getY = positionY . positionX . lineEnd
-- 或者：getY l = positionY (positionX (lineEnd l))
```

**setter 的组合却是灾难**——因为 setter 的类型是 `a -> s -> s`，它需要"原结构"来构造"新结构"：

```
setPositionY :: Double -> Position -> Position
setPositionY y' p = p { positionY = y' }

setLineEnd :: Position -> Line -> Line
setLineEnd p' l = l { lineEnd = p' }

-- 设置 line1 终点纵坐标 —— 需要 getter 和 setter 配合！
line2 = setLineEnd (setPositionY 5 (lineEnd line1)) line1
```

韩冬在书中尖锐地指出了问题所在 ：

> _"不管是模式匹配还是记录语法，都需要一堆辅助的表达式，而这些额外的绑定都不需要。"_

### 🔑 洞见二：setter 必须"知道原结构"

为什么 setter 不能像 getter 一样组合？因为设置字段 `y` 的新值时，**你必须保留 `x` 的旧值**——这意味着 setter 需要知道"原 `Position` 长什么样"。

```
setPositionY 5 (Position 3 4) = Position 3 5
--                            ↑ 必须保留 x=3
```

**setter 的本质是"基于旧结构构造新结构"**——它无法脱离上下文独立存在。这就是 setter 不可组合的深层原因。

### 🔑 洞见三：getter 和 setter 是"对同一字段的两种视角"

观察 `positionX` 和 `setPositionX`：

```
positionX   :: Position -> Double              -- 提取
setPositionX :: Double -> Position -> Position  -- 嵌入
```

它们操作的是**同一个字段**。这种"提取"与"嵌入"的对偶性，暗示着——**它们应该被捆绑在一起**。

> 💡 这一洞察是透镜思想的种子：与其维护一对函数，不如把"提取"和"嵌入"封装成一个**第一等公民的值**（first-class value）。

### 实际应用

```
-- 传统方式：嵌套记录更新
updateLineY :: Double -> Line -> Line
updateLineY y' line = 
  line { lineEnd = (lineEnd line) { positionY = y' } }

-- 问题：
-- 1. 必须写 lineEnd line 两次（一次读取，一次在更新表达式中）
-- 2. 嵌套越深，代码越丑陋
-- 3. 无法将"终点纵坐标"作为一个可复用的抽象传递
```

## 12.2 透镜组：用 `forall f. Functor f` 统一 getter 和 setter

这是本章**最震撼**的一节。韩冬给出了透镜的类型别名 ：

```
type Lens b a = Functor f => (a -> f a) -> b -> f b
```

（注：标准库 `lens` 的完整形式是 `type Lens s t a b = forall f. Functor f => (a -> f b) -> s -> f t`，韩冬的版本是 `Lens'` 的简化版，聚焦于"类型不变"的场景。）

### 🔑 洞见四：透镜就是一个"被 Functor 参数化的函数"

仔细看这个类型：

```
Lens b a = Functor f => (a -> f a) -> b -> f b
```

它接受一个函数 `a -> f a`（"如何映射字段 `a`"），返回一个函数 `b -> f b`（"如何映射整个结构 `b`"）。

**关键洞察**：这个类型对 `f` 是**全称量化（forall）**的——意味着透镜必须对任意 `Functor f` 都成立。根据参数化定理（parametricity），这极大地限制了透镜的可能实现——它**只能**按照一种方式实现：**先用 getter 从 `b` 中取出 `a`，对其应用给定的函数，再用 setter 把结果放回 `b`**。

### 🔑 洞见五：为什么 `forall f. Functor f` 这么神奇？

这是本章最深刻的数学洞见。根据**参数化（parametricity）**，一个 `forall f. Functor f => (a -> f a) -> b -> f b` 类型的函数，其实现方式是**唯一的**——它必须隐藏一个 `b -> a`（getter）和一个 `b -> a -> b`（setter）。

Haskell 维基百科上 Bartosz Milewski 的推导精辟地指出 ：

> _"Parametricity tells us that there is an IStore hiding inside the van Laarhoven lens. The lens is equivalent to: s -> IStore a b t."_

换句话说，`Lens s t a b` **等价于**​ `s -> IStore a b t`——而 `IStore a b t` 恰好包含了一个 getter (`s -> a`) 和一个 setter (`b -> t`)。**`forall f. Functor f` 这个约束，用数学的强制性，保证了透镜"必须"同时包含 getter 和 setter 的信息**。

### 🔑 洞见六：透镜的具体实现

韩冬在书中给出了基于 getter/setter 对构造透镜的方法：

```
lens :: (b -> a) -> (b -> a -> b) -> Lens b a
lens getter setter = \f b -> fmap (setter b) (f (getter b))
```

展开看：

1. `getter b` 从结构 `b` 中取出字段 `a`
    
2. `f (getter b)` 对字段 `a` 应用函数 `f`，得到 `f a`
    
3. `fmap (setter b)` 把 `a -> b` 的 setter 抬升到 `f a -> f b`
    
4. 最终得到 `f b` —— 即"映射后的整个结构"
    

**这就是透镜的"心脏"**——它用 `fmap` 把"字段级别的映射"提升为"结构级别的映射"。

### 🔑 洞见七：透镜就是函数，所以可以用 `.` 组合！

这是透镜最强大的特性。因为 `Lens b a` 本质上是一个函数，两个透镜的组合就是**普通的函数组合**：

```
-- 假设我们有：
positionY :: Lens Position Double
lineEnd   :: Lens Line Position

-- 组合得到"Line 终点纵坐标"的透镜
lineEndY :: Lens Line Double
lineEndY = lineEnd . positionY
```

**为什么这个组合是"从左到右"的？**​ 因为：

```
lineEnd . positionY 
  :: (Position -> f Position) -> (Line -> f Line)
   . (Double -> f Double) -> (Position -> f Position)
  = (Double -> f Double) -> (Line -> f Line)
```

类型推导自然地把"小结构"的透镜和"大结构"的透镜粘合成"从大结构直达字段"的透镜。

Hackage 的 lens 教程明确指出 ：

> _"Lenses compose through ordinary function composition... Given lens1 :: Lens A B and lens2 :: Lens B C, the composed optic lens1 . lens2 :: Lens A C creates a direct path from the outer structure to the innermost field."_

> 💡 **这是透镜最违背直觉也最优雅的特性**：组合顺序与面向对象语言（如 Java 的 `obj.getLine().getEnd().getY()`）完全一致，但从数学上看只是函数组合。Conal Elliott 最早观察到这个现象——"函数组合的 `.` 恰好与 OO 的 `.` 访问器顺序相同"。

### 实际应用

```
-- 手工定义透镜
positionX :: Lens' Position Double
positionX = lens positionX (\p x -> p { positionX = x })

positionY :: Lens' Position Double  
positionY = lens positionY (\p y -> p { positionY = y })

lineStart :: Lens' Line Position
lineStart = lens lineStart (\l p -> l { lineStart = p })

lineEnd :: Lens' Line Position
lineEnd = lens lineEnd (\l p -> l { lineEnd = p })

-- 组合透镜
lineEndY :: Lens' Line Double
lineEndY = lineEnd . positionY

-- 现在 lineEndY 是一个完整的、可复用的"Line 终点纵坐标"的引用
```

## 12.3 view、set 和 over 函数：从统一类型中提取三种操作

这是本章**最精妙**的一节——展示了"同一个透镜，通过选择不同的 `Functor f`，可以扮演 getter、setter、modifier 三种角色"。

### 12.3.1 over 函数：用 Identity 函子实现"修改"

韩冬在书中给出的定义 ：

```
newtype Identity a = Identity { runIdentity :: a }

over :: Lens b a -> (a -> a) -> b -> b
over lens f x = runIdentity $ lens (Identity . f) x
```

**🔑 洞见八：Identity 函子让透镜"修改"字段**

推导过程：

1. `Identity . f` 的类型是 `a -> Identity a`——这正是透镜期望的第一个参数
    
2. `lens (Identity . f)` 的类型是 `b -> Identity b`——对结构 `b` 做映射
    
3. `lens (Identity . f) x` 得到 `Identity b`——即"修改后的结构，包装在 Identity 里"
    
4. `runIdentity` 解开包装，得到 `b`
    

**为什么 Identity 函子能实现"修改"？**​ 因为：

- `Identity` 的 `fmap` 是恒等：`fmap g (Identity x) = Identity (g x)`
    
- 这意味着 `lens (Identity . f) b` 在做的事是：取出 `a`，应用 `f` 得到新的 `a`，再用 setter 放回 `b`
    
- **`Identity` 函子"不添加任何额外上下文"**——它只是让 `fmap` 透传变换，从而实现了"纯粹修改字段"
    

### 12.3.2 set 函数：over 的特例

```
set :: Lens b a -> a -> b -> b
set lens x = over lens (const x)
```

**🔑 洞见九：设置就是"修改为常量"**

`set` 只是 `over` 的特例——把修改函数设为 `const x`（忽略旧值，始终返回新值 `x`）。

```
set lineEndY 5 line1  -- 把 line1 终点纵坐标设为 5
```

### 12.3.3 view 函数：用 Const 函子实现"读取"

韩冬在 12.3.3 节讲述了 view 的实现原理。结合 Hackage 教程 ：

```
newtype Const a b = Const { getConst :: a }

instance Functor (Const a) where
  fmap _ (Const x) = Const x  -- 忽略映射函数！

view :: Lens b a -> b -> a
view lens b = getConst (lens Const b)
```

**🔑 洞见十：Const 函子让透镜"提取"字段**

推导过程：

1. `Const` 的类型是 `a -> Const a b`——注意第二个类型参数 `b` 是"幽灵类型"，`Const` 根本不存储 `b` 类型的值
    
2. `lens Const` 的类型是 `b -> Const a b`——对结构 `b` 做映射
    
3. `lens Const b` 得到 `Const a b`——其中 `a` 是"从字段提取的值"
    
4. `getConst` 提取出 `a`
    

**为什么 Const 函子能实现"读取"？**​ 因为：

- `Const` 的 `fmap` **忽略映射函数**：`fmap _ (Const x) = Const x`
    
- 这意味着当透镜内部执行 `fmap setter (Const oldValue)` 时，`setter` 被完全丢弃
    
- **`Const` 函子"吃掉"了 setter，只保留了 getter 提取的值**
    

> 💡 **这是透镜设计最精妙之处**：同一个 `lens` 函数，通过选择 `f = Identity` 得到修改能力，通过选择 `f = Const` 得到读取能力。Identity 和 Const 这两个"极端简单"的 Functor（第十一章学的！），在此刻展现出了惊人的威力。

### 🔑 洞见十一：view / set / over 三位一体的数学本质

把三个函数放在一起看：

```
view :: Lens b a -> b -> a
set  :: Lens b a -> a -> b -> b  
over :: Lens b a -> (a -> a) -> b -> b
```

它们都是从 `Lens b a` 这个统一类型中，通过**选择不同的 Functor**​ 提取出来的操作：

|操作|选择的 Functor|效果|
|---|---|---|
|`view`|`Const a`|提取字段值|
|`set`|`Identity` + `const`|替换字段值|
|`over`|`Identity`|修改字段值|

**Hackage 教程对此总结得非常精辟**​ ：

> _"The trick is that we get to pick what Functor we specialize f to and depending on which Functor we pick we get different features."_

### 实际应用

```
-- 读取
view lineEndY line1  -- 4.0

-- 设置  
set lineEndY 5 line1  -- Line (Position 0 0) (Position 3 5)

-- 修改
over lineEndY (+1) line1  -- Line (Position 0 0) (Position 3 5)

-- 组合透镜后使用
view (lineEnd . positionX) line1  -- 3.0
over (lineStart . positionY) (+10) line1  -- 起点纵坐标 +10
```

## 12.4 函数库：lens 生态系统的工程化

这一节韩冬介绍了实际的 `lens` 库用法。基于 Hackage 的官方文档 ：

### 自动生成透镜

使用 Template Haskell 的 `makeLenses`：

```
{-# LANGUAGE TemplateHaskell #-}

data Atom = Atom { _element :: String, _point :: Point }
data Point = Point { _x :: Double, _y :: Double }

makeLenses ''Atom
makeLenses ''Point

-- 自动生成：
-- element :: Lens' Atom String
-- point   :: Lens' Atom Point  
-- x       :: Lens' Point Double
-- y       :: Lens' Point Double
```

**🔑 洞见十二：命名约定**

`makeLenses` 为字段 `_fieldName` 生成名为 `fieldName` 的透镜——去掉下划线前缀。这是 Haskell 生态的约定。

### 操作符语法

`lens` 库提供了一系列操作符，让代码更流畅 ：

```
-- 读取
view _2 (10, 20)        -- 20
(10, 20) ^. _2          -- 20（中缀版 view）

-- 设置
set _2 42 (10, 20)      -- (10, 42)
(10, 20) & _2 .~ 42     -- (10, 42)（中缀版 set）

-- 修改
over _2 (+1) (10, 20)   -- (10, 21)
(10, 20) & _2 %~ (+1)   -- (10, 21)（中缀版 over）

-- 组合
("hello", ("world", 2)) ^. _2 . _1  -- "world"
set (_2 . _1) 42 ("hello", ("world", 2))  -- ("hello", (42, 2))
```

### 🔑 洞见十三：透镜操作符的设计哲学

`lens` 库的操作符设计极其讲究：

- `^.` 是 `view` 的中缀版，左结合，**让"结构 ^. 透镜"读作"从结构中取出透镜指向的值"**
    
- `.~` 是 `set` 的中缀版，配合 `&` 使用：**`structure & lens .~ newValue`**
    
- `%~` 是 `over` 的中缀版：**`structure & lens %~ f`**
    

这种设计的精妙之处在于——**它让 Haskell 代码读起来像面向对象的字段访问**，但背后是纯函数的组合。

### 🔑 洞见十四：透镜是"第一等的 getter/setter"

Hackage 文档明确指出 ：

> _"A lens is a first class getter and setter."_

这意味着透镜可以：

- **作为参数传递**：`map (view positionX) [p1, p2, p3]`
    
- **作为返回值**：`chooseLens :: Bool -> Lens' Position Double`
    
- **存储在数据结构里**：`Map String (Lens' Config Value)`
    
- **与高阶函数组合**：`foldl (flip over) config [lens1 %~ f1, lens2 %~ f2]`
    

**这种"透镜是一等值"的特性，让"数据访问路径"本身成为可操纵的对象**——这是传统 OOP 语言难以企及的。

### 🔑 洞见十五：透镜家族 —— 从 Lens 到 Optics 谱系

`lens` 库不仅提供 `Lens`，还提供了一整个"光学器件"（optics）家族 ：

|光学器件|聚焦|操作|
|---|---|---|
|**Lens**​|乘积类型中的一个字段|get / set / over|
|**Prism**​|和类型中的一个构造子|匹配 / 构造|
|**Traversal**​|容器中的零到多个元素|映射 / 收集|
|**Getter**​|只读访问|提取|
|**Setter**​|只写访问|设置|
|**Fold**​|折叠|聚集|

**所有这些光学器件共享同一个核心思想**：用 `forall f. SomeConstraint f => (a -> f b) -> (s -> f t)` 的形式表示。区别只在 `f` 需要满足的约束：

- `Functor` → Lens
    
- `Applicative` → Traversal
    
- `Choice` → Prism
    

> 💡 **这是本章最深远的洞见**：透镜不是孤立的技巧，而是"用约束多态编码数据访问"这一思想的第一个实例。后续的 Prism、Traversal、Fold 都是这个思想的延伸——通过改变 `f` 的约束，同一套组合机制适用于所有数据类型。

### 实际应用

```
import Control.Lens

data User = User { _name :: String, _age :: Int, _email :: String }
makeLenses ''User

-- 批量更新
validateAndUpdate :: User -> User
validateAndUpdate u = u
  & name %~ trim
  & email %~ toLower
  & age %~ max 0  -- 年龄不能为负

-- 深层访问
data Company = Company { _ceo :: User, _employees :: [User] }
makeLenses ''Company

-- 获取 CEO 的名字
ceoName :: Company -> String
ceoName = view (ceo . name)

-- 给所有员工加薪
giveRaise :: Double -> Company -> Company  
giveRaise pct = employees . traverse . salary %~ \s -> s * (1 + pct)
-- 注：这里 salary 需要是 Lens'，traverse 是 Traversal
```

## 📝 本章核心洞见总结

> **洞见一：getter 可组合，setter 不可组合——这是透镜诞生的根本原因**。
> 
> getter 的类型 `s -> a` 是纯函数，天然可组合；setter 的类型 `a -> s -> s` 需要"原结构"来构造新结构，无法独立组合。这个不对称性迫使我们把 getter 和 setter 捆绑。

> **洞见二：`forall f. Functor f` 是全章的数学灵魂**。
> 
> 这个约束通过参数化定理（parametricity）**数学上强制**透镜的实现必须同时包含 getter 和 setter。你无法写出一个"只有 getter"或"只有 setter"的透镜——类型系统不允许。

> **洞见三：透镜的本质是"被 Functor 参数化的函数"**。
> 
> `Lens b a = Functor f => (a -> f a) -> b -> f b` 看起来复杂，但核心思想简单：给定一个"如何映射字段"的函数，返回一个"如何映射整个结构"的函数。`fmap` 是连接两者的桥梁。

> **洞见四：Identity 和 Const 是透镜的"左右手"**。
> 
> 第十一章看似"简单"的 Identity 和 Const，在透镜里展现出了惊人的威力：Identity 的 `fmap` 是透传（实现 over/set），Const 的 `fmap` 是丢弃（实现 view）。**这两个极简 Functor，通过透镜类型与全称量化结合，解锁了"统一 getter/setter"的能力**。

> **洞见五：透镜组合就是函数组合**。
> 
> 因为 `Lens b a` 本质上是一个函数，所以 `lens1 . lens2` 用普通的 `.` 就能组合。组合顺序与 OO 的 `obj.getA().getB()` 一致——这是 Conal Elliott 发现的"函数组合与 OO 访问器的奇妙对应"。

> **洞见六：`view` / `set` / `over` 是透镜的"三种面孔"**。
> 
> 它们都是从同一个 `Lens` 类型中通过选择不同 Functor 提取的操作。这揭示了 Haskell 抽象的核心美学：**一个统一的抽象，通过参数化产生多种具体操作**。

> **洞见七：透镜是"第一等的 getter/setter"**。
> 
> 透镜可以传递、返回、存储、与高阶函数组合。"数据访问路径"本身成为了可操纵的值——这是传统 OOP 难以企及的灵活性。

> **洞见八：透镜是"光学器件谱系"的起点**。
> 
> Lens、Prism、Traversal、Getter、Setter、Fold 共享同一个核心思想：`forall f. Constraint f => (a -> f b) -> (s -> f t)`。区别只在 `f` 的约束（Functor / Applicative / Choice / ...）。**理解透镜，就是理解整个 optics 谱系**。

> **洞见九：透镜让"make illegal states unrepresentable"延伸到字段级别**。
> 
> 通过透镜设置字段时，可以强制经过智能构造函数，从而在字段级别保护不变量。这是第十章"模块导出控制"思想的字段级延伸。

## 🛠️ 实践建议

1. **从手工透镜开始理解**：
    
    ```
    positionX :: Lens' Position Double
    positionX = lens positionX (\p x -> p { positionX = x })
    ```
    
    亲手实现几个透镜，观察 `lens` 组合子如何把 getter/setter 对转化为 `Lens` 类型。
    
2. **用 QuickCheck 验证透镜定律**：
    
    ```
    -- 透镜必须满足的定律
    law1 :: Eq s => Lens' s a -> s -> Bool
    law1 l s = set l (view l s) s == s  -- 设置后读取 == 原值
    
    law2 :: Lens' s a -> s -> a -> Bool  
    law2 l s a = view l (set l a s) == a  -- 读取设置后的值 == 设置的值
    ```
    
3. **掌握操作符语法**：
    
    ```
    -- 读取
    structure ^. lens
    
    -- 设置
    structure & lens .~ newValue
    
    -- 修改
    structure & lens %~ f
    
    -- 组合
    structure ^. lens1 . lens2 . lens3
    ```
    
4. **用 `makeLenses` 自动生成**：
    
    ```
    data Config = Config { _host :: String, _port :: Int }
    makeLenses ''Config
    ```
    
5. **理解"透镜即函数"的威力**：
    
    ```
    -- 透镜可以作为值传递
    let myLens = positionX
    view myLens (Position 3 4)  -- 3
    
    -- 透镜可以存储在数据结构里
    type Configurator = Map String (Lens' Config String)
    ```
    
6. **警惕透镜的"类型不变"限制**：
    
    ```
    -- Lens' s a 要求设置后仍返回 s 类型
    -- 如果需要改变类型，用完整的 Lens s t a b：
    type Lens s t a b = forall f. Functor f => (a -> f b) -> s -> f t
    ```

## 🔮 承上启下

第十三章"应用函子"会在本章基础上往前推一步——**解决"函子无法处理函数在容器里"的局限**：

```
-- Functor 能做到：
fmap :: (a -> b) -> f a -> f b

-- 但当函数是 f (a -> b)，值是 f a 时，Functor 无能为力
-- Applicative 来解围：
(<*>) :: f (a -> b) -> f a -> f b
```

本章学的 `Identity` 和 `Const` 会在第十四章"单位半群和应用函子"中大放异彩：

- **Const a 的应用函子实例**：结合 Monoid，Const 成为了"从结构中提取 Monoid 值"的强大工具
    
- **Identity 的应用函子实例**：作为"单位"应用函子
    
- **选择应用函子（Alternative）**：`Maybe` 的应用函子实例
    

更深远的连接：

- **第十四章**：`Const a` 的 Applicative 实例 + Monoid，会让你看到——`Const` 不仅是透镜的 view 实现，它本身就是一个强大的抽象
    
- **第十六章 Monad**：`(>>=) :: m a -> (a -> m b) -> m b` 是"函子"+"应用函子"的进一步推广，与透镜的 `forall f. Functor f` 思想同源
    
- **第二十二章 Traversable**：`traverse :: Applicative f => (a -> f b) -> t a -> f (t b)` 是 Traversal 的数学基础——而 Traversal 就是"聚焦多个元素"的透镜
    

**第十二章是你理解 Haskell "约束多态威力"的关键一跃**。吃透"用 `forall f. Functor f` 统一 getter/setter"这一思想，后面的 Applicative、Monad、Traversable 就不再是"新的魔法"，而是"我们已经知道的知识的自然延伸"——你已经知道 `Identity` 和 `Const` 能通过 Functor 约束产生不同行为，Applicative 就是"更强的 Functor 约束"，Monad 就是"再强一点的约束"。
