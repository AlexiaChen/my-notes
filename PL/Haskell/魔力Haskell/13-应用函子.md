
# 第十三章 应用函子 —— 读书笔记

> 💡 如果说第十一章的 Functor 回答了"什么东西可以被 map"，那么第十三章就是在回答一个更锋利的问题：**当函数本身也在上下文里时，怎么应用它？**​ `fmap` 能把 `a -> b` 提升到 `f a -> f b`，但如果你手上的是 `f (a -> b)` 和 `f a`，`fmap` 就不够用了——它会给你 `f (f b)`，而不是 `f b`。Applicative 的出现，就是为了填补这个"函数也在盒子里"的空白。表面看是 `pure` 和 `<*>` 两个函数，实则在揭示 Haskell 抽象金字塔的第二块基石：**"上下文里的函数应用"本身是一种可抽象、可组合、受定律约束的运算**。

韩冬在这一章安排了三个小节：**13.1 函子的局限**、**13.2 什么是应用函子**（含 13.2.1 Reader 应用函子、13.2.2 自然升格）、**13.3 IO 应用函子**。表面是从"函子的不足"到"应用函子的定义"再到"两个关键实例"的递进，实则在铺设一条主线：**Functor 只能做"单参数的函数映射"，Applicative 才能做"多参数函数在上下文里的应用"——而这一步跃迁，开启了 Haskell "应用风格编程"（applicative style）的整个范式**。

## 🎯 全局脉络：为什么 Applicative 是抽象金字塔的第二块基石？

```
第十一章: Functor
  fmap :: (a -> b) -> f a -> f b
  "把普通函数应用到上下文里的值"
   ↓
第十三章: Applicative  ← 你在这里
  pure :: a -> f a
  (<*>) :: f (a -> b) -> f a -> f b
  "把上下文里的函数应用到上下文里的值"
   ↓
第十六章: Monad
  (>>=) :: m a -> (a -> m b) -> m b
  "让后续计算依赖前文结果"
```

**这一章是整本书的"抽象跃迁关键节点"**。前六章你学了具体列表操作，第七章学了类型类机制，第十一章把"可映射性"抽象成 Functor——但 Functor 有一个**结构性的局限**：它只能处理"一个参数在上下文里"的情况。一旦你的函数是多参数的、且所有参数都在上下文里，Functor 就不够用了。

McBride 和 Paterson 在 2008 年的开创性论文《Applicative Programming with Effects》里正式定义了 Applicative，把他们观察到的"函数也在上下文里"这个反复出现的模式孤立出来并命名。**Applicative 填补了 Functor 和 Monad 之间的空白**——它比 Functor 强（能应用多参数函数），但比 Monad 弱（不允后续计算依赖前文结果）。

> 💡 这种"介于两者之间"的地位，恰恰是 Applicative 最宝贵的特性：**因为它比 Monad 受限，所以它能做 Monad 做不到的优化和静态分析**。Haskell wiki 明确指出："Applicative 接口缺乏 `>>=` 的完整能力，但它有更多的实例，足以应对许多用途，例如上下文无关解析"。

## 13.1 函子的局限：当函数也在盒子里

### 起点：一个看似能解决、实则卡住的问题

韩冬在书中指出，我们希望被抽象出来的是"能够提供 `<*>` 定义的应用函子"。要理解为什么需要 `<*>`，先看 Functor 的局限。

考虑这个经典场景：

```
-- 两个数都在 Maybe 里，想要求和
Just 2 :: Maybe Int
Just 3 :: Maybe Int
(+)    :: Int -> Int -> Int
```

用 `fmap` 部分应用：

```
:t (+) <$> Just 2
(+) <$> Just 2 :: Maybe (Int -> Int)
```

**问题来了**：我们现在有 `Maybe (Int -> Int)` 和 `Just 3 :: Maybe Int`，想把前者应用到后者——但 `fmap` 帮不上忙：

```
fmap (+) <$> Just 2 <*> Just 3
```

**🔑 洞见一：Functor 只能处理"函数是普通的"这种情况**

`fmap` 的类型是 `fmap :: (a -> b) -> f a -> f b`——它要求函数是**普通的**​ `a -> b`。但当函数是 `f (a -> b)`（装在上下文里）时，`fmap` 做的是：

```
fmap :: (a -> b) -> f a -> f b
-- 如果我们的"函数"是 f (a -> b)，那么：
fmap (f (a -> b)) :: f (f a) -> f (f b)  -- 类型完全错乱！
```

换句话说，**`fmap` 无法"穿透"两层上下文**。它只能处理一层。

### 🔑 洞见二：这就是 `<*>` 要解决的问题

我们需要一个运算符，类型签名是：

```
(<*>) :: f (a -> b) -> f a -> f b
```

它做的是：**取出装在 `f` 里的函数，取出装在 `f` 里的值，应用之，再把结果装回 `f`**。

用 `<*>` 改写上面的例子：

```
(+) <$> Just 2 <*> Just 3  -- Just 5
```

**这就是"应用风格"（applicative style）**——它读起来几乎和普通的 `(+) 2 3` 一模一样，只是每个参数都"升格"到了 `Maybe` 上下文里。

### 🔑 洞见三：Functor 的局限本质是什么？

更深层地看，Functor 的局限在于——**它只能表达"上下文里的值之间的独立变换"**。当你有多个值在上下文里，且它们之间需要"协同"时，Functor 就不够了。

具体来说：

|场景|需要的抽象|
|---|---|
|单个 `a` 在上下文 `f` 里，应用 `(a -> b)`|Functor (`fmap`)|
|多个 `a, b, c` 在上下文 `f` 里，应用 `(a -> b -> c)`|**Applicative (`<*>`)**​|
|后续计算依赖前文结果|Monad (`>>=`)|

**Functor 是"单点"的，Applicative 是"多点且独立"的，Monad 是"多点且依赖"的**。这就是 Haskell 抽象金字塔三层之间的本质差异。

### 实际应用

```
-- 不用 Applicative 的痛苦写法
addMaybe :: Maybe Int -> Maybe Int -> Maybe Int
addMaybe (Just x) (Just y) = Just (x + y)
addMaybe _ _ = Nothing

-- 用 Applicative 的优雅写法
addMaybe :: Maybe Int -> Maybe Int -> Maybe Int
addMaybe mx my = (+) <$> mx <*> my

-- 三元版本
addThree :: Maybe Int -> Maybe Int -> Maybe Int -> Maybe Int
addThree mx my mz = (+) <$> mx <*> my <*> mz
```

## 13.2 什么是应用函子：pure 与 `<*>`

### 类型类定义

```
class Functor f => Applicative f where
  pure  :: a -> f a
  (<*>) :: f (a -> b) -> f a -> f b
```

### 🔑 洞见四：pure 的直觉——"最小上下文"

韩冬在书中明确指出：**"pure 接收一个参数并把它包裹到函子里。我们把这个升格值的过程叫调价最小上下文（minimum context）"**。

`pure` 把"裸值"装进"最小化的上下文"：

- `Maybe` 的 `pure`：`pure x = Just x`（最小的 Maybe 上下文就是 `Just`）
    
- `[]` 的 `pure`：`pure x = [x]`（最小的列表上下文就是单元素列表）
    
- `IO` 的 `pure`：`pure = return`（最小的 IO 上下文就是"立即返回"）
    
- `((->) r)` 的 `pure`：`pure x = const x`（最小的函数上下文就是"忽略参数，返回常量"）
    

**"最小上下文"的含义**：`pure` 把值装进上下文，但不添加任何"额外效果"——没有失败（`Maybe`）、没有非确定性（`[]`）、没有副作用（`IO`）。它只是**语法上**把值装进 `f`，但**语义上**保持值不变。

### 🔑 洞见五：`<*>` 是"升格计算的核心"

韩冬说：**"`<*>` 是升格计算的核心——函子应用运算符"**。

`<*>` 的类型 `f (a -> b) -> f a -> f b` 告诉我们它在做什么：

1. 从 `f (a -> b)` 中取出函数 `a -> b`（可能伴随上下文效果）
    
2. 从 `f a` 中取出值 `a`（可能伴随上下文效果）
    
3. 应用函数到值，得到 `b`
    
4. 把 `b` 装回上下文 `f b`，**合并两者带来的效果**
    

不同的 `f` 对"合并效果"有不同的定义：

```
-- Maybe：任何一个为 Nothing，结果就是 Nothing
instance Applicative Maybe where
  pure = Just
  (Just f) <*> (Just x) = Just (f x)
  _        <*> _        = Nothing

-- 列表：笛卡尔积式的所有可能组合
instance Applicative [] where
  pure x = [x]
  fs <*> xs = [f x | f <- fs, x <- xs]

-- IO：顺序执行，提取函数，提取参数，应用
instance Applicative IO where
  pure = return
  f <*> x = do
    f' <- f
    x' <- x
    return (f' x')
```

### 🔑 洞见六：四条定律——应用函子的"行为契约"

韩冬在书中明确指出，`pure` 和 `<*>` 必须满足四个条件：单位律、组合律、同态律和互换律。完整表述：

```
-- 单位律（Identity）
pure id <*> v = v

-- 同态律（Homomorphism）  
pure f <*> pure x = pure (f x)

-- 互换律（Interchange）
u <*> pure y = pure ($ y) <*> u

-- 组合律（Composition）
pure (.) <*> u <*> v <*> w = u <*> (v <*> w)
```

**这四条定律的深层含义**：

- **单位律**：用 `pure id` 去应用一个值，等于什么都不做——`pure id` 是 `<*>` 的"单位元"
    
- **同态律**：`pure` 保持函数应用——`pure f <*> pure x` 等于 `pure (f x)`。这意味着"在上下文里应用纯函数"等价于"应用纯函数后再 pure"
    
- **互换律**：当右边是 `pure y` 时，`u <*> pure y` 可以重写为 `pure ($ y) <*> u`——运算顺序可以交换
    
- **组合律**：函子应用满足组合律——`pure (.)` 让函数组合在上下文里仍然成立
    

> 💡 **这四条定律不是任意约定的，它们保证了"应用风格"的行为是可预测的**。特别是组合律，它与 Functor 的组合律 `fmap (g . f) = fmap g . fmap f` 遥相呼应——两者共同保证了"映射"在 Haskell 里的代数结构。

### 🔑 洞见七：Applicative 与 Functor 的关系

一个极其重要的推论：**任何 Applicative 自动是 Functor**，因为 `fmap` 可以用 `pure` 和 `<*>` 定义：

```
fmap f x = pure f <*> x
```

现代 Haskell 在类型类层面强制了这种关系：`class Functor f => Applicative f`——**Applicative 必须是 Functor 的超类**。这意味着你不能为某个类型实现 Applicative 却不实现 Functor。

### 13.2.1 Reader 应用函子：函数即上下文

这是本节第一个关键实例。韩冬给出的 `((->) a)` 的应用函子实例：

```
instance Applicative ((->) a) where
  pure x = \_ -> x  -- pure = const
  
  f <*> g = \x -> f x (g x)
```

**🔑 洞见八：函数 `a -> b` 可以看作"装在函子 `((->) a)` 中的一个 `b` 类型的值"**

这是 Reader 函子最反直觉也最深刻的视角。一个函数 `a -> b`：

- 从"容器视角"看：它装着一个 `b`，但这个 `b` 的"取出"需要提供一个 `a` 作为"钥匙"
    
- 从"上下文视角"看：它是一个"依赖环境 `a` 的计算"，产出 `b`
    

**`pure` 的含义**：`pure x = \_ -> x`——忽略环境，直接返回 `x`。这是"最小上下文"——不依赖任何环境。

**`<*>` 的含义**：`(f <*> g) x = f x (g x)`——关键洞察：

1. `f :: a -> (b -> c)` 是一个"依赖环境 `a` 的函数，产出 `b -> c`"
    
2. `g :: a -> b` 是一个"依赖环境 `a` 的函数，产出 `b`"
    
3. 给定环境 `x`，`f x` 得到函数 `b -> c`，`g x` 得到值 `b`
    
4. 应用之：`(f x) (g x)` 得到 `c`
    

**核心洞察**：`<*>` 让"两个依赖同环境 `a` 的计算"组合成一个"新的依赖同环境 `a` 的计算"——**环境 `a` 被自动"穿线"过整个计算过程**！

这就是为什么 Reader 函子常用于"配置模块化"的问题——韩冬明确指出："这个函子常用在配置模块化的问题上"。

### 🔑 洞见九：Reader 与配置

考虑一个需要从配置中读取多个参数的场景：

```
data Config = Config { host :: String, port :: Int, timeout :: Int }

-- 传统方式：显式传递 config
makeConnection :: Config -> Connection
makeConnection cfg = connect (host cfg) (port cfg) (timeout cfg)

-- Reader 方式：config 自动穿线
makeConnection :: Reader Config Connection
makeConnection = connect <$> asks host <*> asks port <*> asks timeout
  where
    asks f = Reader (f . configField)  -- 简化示意
    connect h p t = ...
```

**应用风格的优势**：`connect <$> host <*> port <*> timeout` 读起来就像普通的 `connect host port timeout`——但每个参数都自动从同一个 `Config` 环境中提取！这就是"应用风格"在 Reader 上下文里的威力。

更深入的视角：Reader 的 `<*>` 本质是**"环境的共享"**——`f <*> g` 中的 `f` 和 `g` 共享同一个环境 `a`。这种"共享环境"的模式，在第十六章 `Monad` 的 `ReaderT` 里会被发扬光大。

### 13.2.2 自然升格：应用风格的书写习惯

韩冬在书中引入了"自然升格"（natural lifting）的概念：

> _"自然升格指的是使用应用函子构建运算的一种书写习惯"_

核心是 `<$>` 这个中缀函数——它是 `fmap` 的中缀版本：

```
(<$>) :: Functor f => (a -> b) -> f a -> f b
f <$> x = fmap f x  -- 左结合
```

**🔑 洞见十：自然升格是一种"风格"，不是新机制**

韩冬强调："`<$>` 是 `fmap` 的中缀版本。和 `$` 不同的是，`<$>` 是一个左结合的函数，在自然升格里的作用是把一个函数先升格至函子的范畴，然后就可以方便地使用 `<*>` 去继续应用计算"。

"自然升格"这个名字来源于——编译器**自动根据参数类型推导出我们需要的应用函子类型**，形如 `f (a -> b) -> f a -> f b`。这种写法就叫自然升格。

```
-- 自然升格的典型形态
replicateB :: Int -> String
replicateB = \x -> replicate x 'x'

-- 参与计算的参数里有包裹在函子里的
a :: Maybe Int
a = Just 3

-- 自然升格写法
result :: Maybe String
result = replicateB <$> a  -- fmap replicateB a

-- 实际遇到的问题往往是，参与计算的参数里不只有一个是包裹在函子类型里面的
-- 这时就需要 <$> 和 <*> 配合
addTwo :: Maybe Int -> Maybe Int -> Maybe Int
addTwo mx my = (+) <$> mx <*> my  -- 自然升格的经典形态
```

**🔑 洞见十一：`<$>` 和 `<*>` 的分工**

|运算符|作用|类比|
|---|---|---|
|`<$>`|把普通函数"升格"到上下文里|相当于"应用风格"中的 `fmap`|
|`<*>`|在上下文里应用函数|相当于"应用风格"中的函数应用|
|`pure`|把值"升格"到最小上下文|相当于"应用风格"中的"裸值"|

三者的组合让你可以写出：

```
-- 完全的应用风格
result = pure f <$> arg1 <*> arg2 <*> arg3
-- 等价于：
result = f <$> arg1 <*> arg2 <*> arg3
-- 因为 pure f <$> x = f <$> x（由 applicative 定律保证）
```

### 🔑 洞见十二：自然升格的"流式"美感

```
-- 解析器的应用风格（预览第十五章）
parsePerson = Person <$> parseName <*> parseAge <*> parseEmail

-- 配置的 Reader 风格
makeConn = Connection <$> asks host <*> asks port <*> asks timeout

-- 验证的应用风格
validate = (&&) <$> checkName <*> checkAge <*> checkEmail
```

**这种写法的美妙之处**：它读起来就像普通的"构造函数 + 参数列表"，但每个参数都自动在上下文里被处理——失败传播（`Maybe`）、环境共享（`Reader`）、顺序执行（`IO`）、非确定性（`[]`）都由上下文自动处理。

> 💡 这就是应用风格的本质力量：**"描述做什么"而非"描述怎么做"**。你写下 `Person <$> parseName <*> parseAge`，表达的是"用这三个解析结果构造一个 Person"——至于解析失败怎么办、顺序如何、副作用如何处理，全部由 `Applicative` 实例的 `<*>` 定义自动处理。

### 实际应用

```
import Control.Applicative

-- 1. Maybe 的应用风格
getName :: Maybe User -> Maybe String
getName = fmap name  -- 或者：name <$> 

-- 2. 列表的应用风格（笛卡尔积）
combinations = (+) <$> [1,2,3] <*> [10,20]  -- [11,21,12,22,13,23]

-- 3. 函数（Reader）的应用风格
type Config = (String, Int)
getHost :: Config -> String
getHost = fst

getPort :: Config -> Int  
getPort = snd

makeURL :: Config -> String
makeURL = (\h p -> h ++ ":" ++ show p) <$> getHost <*> getPort
```

## 13.3 IO 应用函子：当副作用遇上应用风格

### IO 的应用函子实例

韩冬在 13.3 节讲述 IO 应用函子。基于 Haskell 教育资料的定义：

```
instance Applicative IO where
  pure = return
  
  f <*> x = do
    f' <- f
    x' <- x
    return (f' x')
```

### 🔑 洞见十三：IO 的 `<*>` 是"顺序执行 + 提取值 + 应用"

`f <*> x` 的语义：

1. 先执行 `f`（一个 IO 计算），得到函数 `f'`
    
2. 再执行 `x`（另一个 IO 计算），得到值 `x'`
    
3. 应用 `f' x'`，把结果用 `return` 装回 IO
    

**关键点**：`f` 和 `x` 是**顺序执行**的——`f` 先跑，`x` 后跑。这意味着 IO 的 `<*>` 是**有副作用顺序**的。

### 🔑 洞见十四：应用风格让 IO 代码更声明式

考虑"读取两行并拼接"：

```
-- 传统 do 语法
read2 :: IO String
read2 = do
  a <- getLine
  b <- getLine
  return (a ++ b)

-- 应用风格
read2 :: IO String
read2 = (++) <$> getLine <*> getLine
```

**应用风格的优势**：

1. **更简洁**：不需要显式 `do`、`<-`、`return`
    
2. **更声明式**：直接表达"拼接两个 `getLine` 的结果"
    
3. **更组合化**：`(++) <$> getLine <*> getLine` 本身是一个一等公民的值
    

韩冬在书中指出，使用应用风格可以更轻松地创建"读取任意 n 行并拼接"的函数：

```
getLines :: Int -> IO String
getLines 0 = return []
getLines n = pure (++) <*> getLine <*> getLines (n - 1)
```

### 🔑 洞见十五：IO 应用函子揭示了"应用风格 vs do 语法"的本质差异

这是本节最深刻的洞见。比较：

```
-- 应用风格：所有参数独立计算
result1 = f <$> ioAction1 <*> ioAction2 <*> ioAction3

-- do 语法：后续计算可依赖前文结果
result2 = do
  x <- ioAction1
  y <- ioAction2 x  -- ioAction2 可以依赖 x！
  return (f x y)
```

**根本区别**：

- **应用风格（Applicative）**：所有参数**独立**计算，顺序固定但彼此无依赖
    
- **do 语法（Monad）**：后续计算**可以依赖**前文结果
    

这就是为什么 Applicative 比 Monad "弱"——它无法表达"根据第一个 IO 的结果决定第二个 IO 做什么"。但这种"弱"也是优势——**因为无依赖，所以可以并行、可以静态分析、可以优化**。

Haskell wiki 上的经典论述：

> _"Applicative 接口缺乏 `>>=` 的完整能力，但它有更多的实例，足以应对许多用途"_

并举了一个深刻的例子：如果你想在"运行计算前"做初始化（而非"运行计算后"做清理），Monad 做不到，但 Applicative 可以——因为 Applicative 的所有"效果"在组合时是静态已知的。

### 🔑 洞见十六：IO 应用函子与 Monad 的关系

注意一个关键事实——`pure = return`。这意味着：

- **IO 既是 Applicative 又是 Monad**
    
- `pure` 就是 `return`
    
- `<*>` 可以用 `>>=` 定义：`f <*> x = f >>= \f' -> x >>= \x' -> return (f' x')`
    

**Applicative 是 Monad 的"子集"**——任何 Monad 自动是 Applicative（通过 `pure = return` 和 `f <*> x = ap f x`）。但反过来不成立——有些 Applicative 不是 Monad（如 `ZipList`、`Const`）。

### 实际应用

```
-- 读取三个数并求和
sum3 :: IO Int
sum3 = (+) <$> readLn <*> readLn <*> readLn

-- 读取姓名和年龄并格式化
greet :: IO String
greet = (\name age -> "Hello " ++ name ++ ", you are " ++ show age ++ " years old.")
        <$> getLine <*> readLn

-- 并行读取（概念上）
-- 注意：虽然 IO 的 <*> 是顺序的，但 Applicative 的"独立性"语义
-- 让编译器/运行时有机会优化（尽管 GHC 当前实现是顺序的）
```

## 📝 本章核心洞见总结

> **洞见一：Functor 的局限在于"函数也在盒子里"时就失效**。
> 
> `fmap` 的类型 `(a -> b) -> f a -> f b` 要求函数是普通的。当函数是 `f (a -> b)` 时，`fmap` 无法应用——它会给你 `f (f b)` 而非 `f b`。这正是 Applicative 要解决的核心问题。

> **洞见二：Applicative 是 Functor 和 Monad 之间的"中间抽象"**。
> 
> 它比 Functor 强（能应用多参数函数），但比 Monad 弱（不允后续计算依赖前文结果）。这种"受限"反而是优势——Applicative 可以做 Monad 做不到的静态分析和优化。

> **洞见三：pure 的直觉是"最小上下文"**。
> 
> `pure x` 把值 `x` 装进"最小化的 `f` 上下文"——不添加任何额外效果。对 `Maybe` 是 `Just x`，对 `[]` 是 `[x]`，对 `IO` 是 `return x`，对 `((->) r)` 是 `const x`。

> **洞见四：`<*>` 是"升格计算的核心"**。
> 
> 它从 `f (a -> b)` 和 `f a` 中取出函数和值，应用之，再合并两者的上下文效果。不同的 `f` 对"合并效果"有不同定义：`Maybe` 是"短路"、`[]` 是"笛卡尔积"、`IO` 是"顺序执行"、`Reader` 是"共享环境"。

> **洞见五：四条定律保证应用风格的可预测性**。
> 
> 单位律、同态律、互换律、组合律——这四条定律不是任意约定，它们保证了"应用风格"在代数上的良定义。特别是组合律，与 Functor 的组合律遥相呼应。

> **洞见六：Reader 应用函子揭示了"环境自动穿线"的魔力**。
> 
> `((->) a)` 的 `<*>` 定义 `f <*> g = \x -> f x (g x)` 实现了"两个依赖同环境 `a` 的计算共享同一个 `a`"。这是配置管理、依赖注入的函数式解法——环境 `a` 被自动穿过整个计算图。

> **洞见七：自然升格是一种"书写习惯"而非新机制**。
> 
> `<$>` 是 `fmap` 的中缀版，`<*>` 是上下文里的函数应用。两者组合形成的"应用风格"——`f <$> arg1 <*> arg2 <*> arg3`——读起来就像普通函数应用 `f arg1 arg2 arg3`，但每个参数都自动在上下文里被处理。

> **洞见八：IO 应用函子让副作用代码更声明式**。
> 
> `(++) <$> getLine <*> getLine` 比 do 语法更简洁、更声明式。但 IO 的 `<*>` 是顺序执行的——这体现了 Applicative 的"参数独立计算"语义。

> **洞见九：Applicative 与 Monad 的本质差异在于"依赖性"**。
> 
> Applicative 的所有参数独立计算（尽管有顺序），Monad 允许后续计算依赖前文结果。这种差异让 Applicative 可以做静态分析、并行化、编译期优化——而 Monad 不行。

> **洞见十：任何 Monad 自动是 Applicative，但反之不成立**。
> 
> `pure = return`，`<*>` 可以用 `>>=` 定义。但 `ZipList`、`Const` 等是 Applicative 却不是 Monad——这证明了 Applicative 是比 Monad 更普遍的抽象。

## 🛠️ 实践建议

1. **优先使用应用风格而非 do 语法**：
    
    ```
    -- 当后续计算不依赖前文结果时
    result = f <$> io1 <*> io2 <*> io3
    -- 比 do 语法更简洁
    ```
    
2. **用 QuickCheck 验证 Applicative 定律**：
    
    ```
    applicativeIdentity :: (Applicative f, Eq (f a)) => f a -> Bool
    applicativeIdentity v = (pure id <*> v) == v
    
    applicativeHomomorphism :: (Applicative f, Eq (f b)) 
                            => (a -> b) -> a -> Bool
    applicativeHomomorphism f x = 
      (pure f <*> pure x) == pure (f x)
    ```
    
3. **掌握 `<$>` 和 `<*>` 的组合**：
    
    ```
    -- 构造函数在应用风格中
    data Person = Person Name Age Email
    makePerson :: Maybe Name -> Maybe Age -> Maybe Email -> Maybe Person
    makePerson n a e = Person <$> n <*> a <*> e
    ```
    
4. **理解 Reader 的"环境共享"**：
    
    ```
    -- 多个计算共享同一个环境
    config = ("localhost", 8080)
    makeConn = (\(h, p) -> h ++ ":" ++ show p) <$> pure config
    -- 等价于：
    makeConn = (\h p -> h ++ ":" ++ show p) <$> fst <*> snd
    ```
    
5. **识别"何时用 Applicative、何时用 Monad"**：
    
    - 如果后续计算**不依赖**前文结果 → 用 Applicative
        
    - 如果后续计算**依赖**前文结果 → 用 Monad
        
    - 优先用 Applicative——它更通用、更可优化
        
    
6. **使用 `liftA2`、`liftA3` 等辅助函数**：
    
    ```
    import Control.Applicative
    
    addMaybe :: Maybe Int -> Maybe Int -> Maybe Int
    addMaybe = liftA2 (+)
    
    -- 等价于 (+) <$> mx <*> my
    ```

更深远的连接：

- **第十四章**：`Const a` 的 Applicative 实例 + Monoid，会让你看到——第十一章学的 `Const` 不仅是透镜的 view 实现，它本身就是一个强大的抽象

- **第十六章 Monad**：`(>>=) :: m a -> (a -> m b) -> m b` 是"应用函子"的进一步推广——解除"参数独立"的限制，允许后续计算依赖前文结果
