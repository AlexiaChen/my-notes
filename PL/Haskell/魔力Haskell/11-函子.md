
# 第十一章 函子 —— 读书笔记

> 💡 如果说前十章你一直在学习"如何用 Haskell 表达计算"，那么从第十一章开始，你进入了一个全新的境界：**不再创造具体的抽象，而是发现抽象背后的抽象**。函子（Functor）是 Haskell 抽象金字塔的第一块基石——它回答了一个看似简单但极其深刻的问题：**"什么东西可以被 map？"**​ 答案不是"列表"，而是"任何保持结构不变的容器/上下文"。这一章表面在讲 `fmap`，实则在为你打开范畴论（Category Theory）的大门——而范畴论正是 Haskell 整个抽象体系的数学母体。

韩冬在这一章安排了四个小节：**11.1 容器抽象**、**11.2 范畴**、**11.3 Identity 和 Const**、**11.4 IO 函子**。表面是从具体到抽象的四步递进，实则在铺设一条主线：**从"列表的 map"出发，发现"容器的共性"，用数学（范畴论）严格化，用极端简单的实例（Identity/Const）和极端特殊的实例（IO）来验证**。

## 🎯 全局脉络：为什么函子如此根本？

```
第六章: map / filter / foldr  ← 列表的递归模式
   ↓
第七章: 类型类  ← 行为抽象的机制
   ↓
第十一章: Functor  ← "可映射性"本身的抽象  【你在这里】
   ↓           ↓
第十三章: Applicative    第十六章: Monad
（在 Functor 上加能力）
   ↓
第二十二章: Foldable / Traversable
```

**这一章是整本书的"抽象起点"**。前六章你学了具体列表操作，第七章学了类型类机制，但直到第十一章，Haskell 才真正开始它的"抽象舞蹈"——**把"可映射性"这件事本身抽象成一个类型类**。

为什么这件事如此重要？因为一旦你意识到 `[]`、`Maybe`、`IO`、`Tree`、`Either e`、`(->) e` 都有同一个能力——"在保持结构/上下文不变的前提下，对里面的值应用一个函数"——你就可以：

1. **写一个函数，对所有的这些类型都适用**（多态到类型构造子级别）
    
2. **建立这些类型之间的数学定律**（identity、composition）
    
3. **在此基础上继续叠加能力**，得到 Applicative、Monad、Foldable、Traversable
    

> 💡 这是 Haskell 区别于其他语言的"元特征"——它不满足于"列表可以 map"，而要追问"任何东西只要满足某些定律，就可以 map"。这种"二阶抽象"是 Haskell 表达力的真正源泉。

## 11.1 容器抽象：从 `map` 到 `fmap` 的跃迁

### 起点：你已经知道的 `map`

回顾第六章，`map` 的类型是：

```
map :: (a -> b) -> [a] -> [b]
```

它做的是：遍历列表，对每个元素应用 `f`，返回新列表。列表的"结构"（长度、顺序）保持不变，只有元素被变换。

### 🔑 洞见一：同样的结构保持，出现在无数类型上

观察 `Maybe` 的"映射"：

```
mapMaybe :: (a -> b) -> Maybe a -> Maybe b
mapMaybe _ Nothing  = Nothing
mapMaybe f (Just x) = Just (f x)
```

再观察二叉树的"映射"：

```
data Tree a = Empty | Node a (Tree a) (Tree a)

mapTree :: (a -> b) -> Tree a -> Tree b
mapTree _ Empty = Empty
mapTree f (Node x l r) = Node (f x) (mapTree f l) (mapTree f r)
```

**这三个函数的"形状"完全一致**：

|类型构造子 `f`|`fmap` 的语义|
|---|---|
|`[]`|遍历列表，应用 `f` 到每个元素|
|`Maybe`|如果是 `Just x`，应用 `f` 到 `x`；`Nothing` 保持 `Nothing`|
|`Tree`|遍历树，应用 `f` 到每个节点的值|

它们的共同点是：**`f` 不改变容器的"形状"，只改变里面的值**。

### 🔑 洞见二：类型构造子 `f` 是"容器模式"的抽象

注意一个微妙但关键的细节——`map` 的类型是 `(a -> b) -> [a] -> [b]`，这里的 `[a]` 是**具体类型**。而函子的抽象是：

```
class Functor f where
  fmap :: (a -> b) -> f a -> f b
```

这里的 `f` 是一个**类型构造子**（type constructor）——它接受一个类型参数 `a`，产生一个具体类型 `f a`。`f` 本身不是类型，而是"类型的模板"。

> 📌 **这是 Haskell 类型系统的一次"升维"**：之前你看到的类型变量（如 `map :: (a -> b) -> [a] -> [b]` 中的 `a`、`b`）是"具体类型的变量"；而 `Functor` 里的 `f` 是"**类型构造子的变量**"——这种多态被称为"**高阶多态**"（higher-kinded polymorphism）。

### 🔑 洞见三：Functor 定律——结构保持不变的数学保证

光有类型签名还不够。Haskell 社区约定，**任何自称 Functor 的实例，必须遵守两条定律**：

```
-- 恒等律（Identity Law）
fmap id = id

-- 组合律（Composition Law）
fmap (f . g) = fmap f . fmap g
```

**这两条定律在说什么？**

- **恒等律**：对容器里的每个元素应用 `id`（恒等函数），应该等于什么都不做。`fmap id` 不能偷偷改变容器的形状、不能增加元素、不能删除元素。
    
- **组合律**：先 `g` 再 `f` 地映射，应该等于先映射 `g`、再映射 `f`。映射操作可以"融合"——这就是为什么 `fmap f . fmap g` 可以被编译器优化为单次遍历。
    

**为什么定律如此重要？**​ 因为它们捕捉了"结构保持不变"这个直觉：

> _"Together, these laws ensure that fmap g does not change the structure of a container, only the elements."_

换句话说，**定律把"map 应该做什么"从英语描述变成了数学约束**。编译器虽然不强制检查定律，但违反定律的 Functor 实例会导致依赖这些定律的抽象（如后续的 Applicative、Monad、Traversable）行为异常。

### 🔑 洞见四：反例——什么不是 Functor

Haskell 教材给出了一个经典的反例：

```
data CMaybe a = CNothing | CJust Int a

instance Functor CMaybe where
  fmap f CNothing = CNothing
  fmap f (CJust c x) = CJust (c+1) (f x)  -- 偷偷给计数器 +1
```

这个实例**违反了恒等律**：

```
fmap id (CJust 0 'a')  -- 结果是 CJust 1 'a'，不是 CJust 0 'a'！
```

`fmap id` 改变了容器的"形状"（计数器变了），所以它**不是合法的 Functor**。这个反例揭示了 Functor 定律的真正力量——**它排除了那些"假装是映射、实则夹带私货"的实例**。

另一个反例来自标准库：**`Set` 不能是 Haskell 的 Functor**：

```
-- 这不可能实现！
instance Functor Set where
  fmap :: (a -> b) -> Set a -> Set b
```

为什么？因为 `Set` 要求元素满足 `Ord` 约束（`Set a` 要求 `Ord a`），而 `fmap` 的签名要求**对任意的 `a` 和 `b` 都能工作**——`b` 不一定有 `Ord` 实例。所以 `Set` 在数学上确实是函子，但在 Haskell 的类型系统里**无法表达为 `Functor` 实例**。

> 💡 **这是 Haskell "类型安全优先于便利"哲学的又一体现**：宁可让 `Set` 失去 `Functor` 实例，也不放宽 `fmap` 的签名去允许约束。

### 🔑 洞见五：容器 vs 上下文——函子的两种解读

这是本章最深刻的视角转换。一个 `Functor f` 可以从两个角度理解：

**视角一：容器（Container）**

`f a` 是一个装着 `a` 类型值的容器。比如：

- `[] a` 是"装多个 `a` 的容器"
    
- `Maybe a` 是"装零个或一个 `a` 的容器"
    
- `Tree a` 是"装多个 `a` 的树形容器"
    

**视角二：上下文（Context）**

`f a` 是一个"带有附加语义的 `a`"。比如：

- `Maybe a` 是"可能失败的 `a`"
    
- `[] a` 是"非确定性选择的 `a`"（多个可能值中的一个）
    
- `IO a` 是"带有 I/O 副作用的 `a`"
    
- `(->) e a` 是"能读取环境 `e` 的 `a`"
    

**为什么这个区分重要？**​ 因为"容器视角"帮助你理解 `fmap` 做什么（遍历、变换），而"上下文视角"帮助你理解 `fmap` 不做什么（**不碰上下文，只碰里面的值**）。

> 💡 这个"上下文视角"是理解后续 Applicative 和 Monad 的关键——它们在 Functor 的基础上，逐步解锁"操作上下文"的能力。

### 实际应用

```
-- 对 Maybe 映射
fmap (*2) (Just 5)        -- Just 10
fmap (*2) Nothing         -- Nothing

-- 对列表映射（fmap 就是 map）
fmap (*2) [1,2,3]         -- [2,4,6]

-- 对函数映射（fmap 就是 (.)）
fmap (*2) (+3)            -- \x -> (x + 3) * 2
fmap (*2) (+3) 10         -- 26

-- 对树映射
fmap (*2) (Node 1 Empty (Node 3 Empty Empty))
-- Node 2 Empty (Node 6 Empty Empty)
```

## 11.2 范畴：函子的数学母体

这一节韩冬把视角拉到数学层面——**函子来自范畴论**。

### 范畴的定义

一个范畴（Category）由三部分组成：

1. **对象**（Objects）——可以理解为类型
    
2. **态射**（Morphisms）——对象之间的箭头，可以理解为函数
    
3. **恒等态射和组合**——每个对象有一个恒等态射 `id`，态射可以组合
    

范畴必须满足两条定律：

- **恒等律**：`id . f = f` 且 `f . id = f`
    
- **结合律**：`(f . g) . h = f . (g . h)`
    

### 🔑 洞见六：Haskell 中的范畴——Hask

在 Haskell 中，**类型和函数构成一个范畴，称为 Hask**：

- 对象是**类型**（`Int`、`Maybe a`、`[a]` 等）
    
- 态射是**函数**（`f :: a -> b`）
    
- 恒等态射是 `id :: a -> a`
    
- 组合是 `(.) :: (b -> c) -> (a -> b) -> (a -> c)`
    

Hask 范畴满足恒等律和结合律——这是 Haskell "函数组合"之所以优美的数学基础。

### 🔑 洞见七：函子是"范畴之间的映射"

范畴论中，函子 **F: C → D**​ 是两个范畴之间的映射，它：

1. 把范畴 C 中的每个对象 **A**​ 映射到范畴 D 中的对象 **F(A)**
    
2. 把范畴 C 中的每个态射 **f: A → B**​ 映射到范畴 D 中的态射 **F(f): F(A) → F(B)**
    
3. **保持恒等态射**：F(id_A) = id_F(A)
    
4. **保持组合**：F(g ∘ f) = F(g) ∘ F(f)
    

**把这条定义翻译到 Haskell**：

- 范畴 C 和 D 都是 Hask
    
- 函子 F 是一个类型构造子 `f`（如 `Maybe`、`[]`）
    
- 对象映射：`a → f a`（类型 `a` 映射到类型 `f a`）
    
- 态射映射：`fmap :: (a -> b) -> (f a -> f b)`（函数 `g :: a -> b` 映射到函数 `fmap g :: f a -> f b`）
    
- **恒等保持**：`fmap id = id` ← **这就是 Functor 的恒等律！**
    
- **组合保持**：`fmap (g . h) = fmap g . fmap h` ← **这就是 Functor 的组合律！**
    

> 💡 **这是本章最震撼的洞见**：Functor 的两条定律不是 Haskell 社区随意约定的——它们**直接来自范畴论中函子的定义**。Haskell 的 `Functor` 类型类，是数学中"函子"这个概念在类型系统中的**精确落地**。

### 🔑 洞见八：为什么范畴论对 Haskell 程序员重要？

你可能会问："我只是想写代码，为什么要学范畴论？"

答案是：**范畴论给 Haskell 的抽象提供了"正确性标准"**。

- 当你定义一个 `Functor` 实例时，范畴论告诉你**必须满足哪两条定律**
    
- 当你学习 `Applicative` 时，范畴论告诉你它是"幺半范畴"（monoidal category）的体现
    
- 当你学习 `Monad` 时，范畴论告诉你它是"自函子范畴中的幺半群"
    
- 当你学习 `Traversable` 时，范畴论告诉你它与"遍历"和"交换两个函子"有关
    

**范畴论是 Haskell 抽象体系的"宪法"**——所有类型类都必须向它对齐。理解范畴论，你就拥有了判断"这个抽象是否合理"的终极标尺。

### 实际应用

范畴论的实际价值不在于让你手动证明定律，而在于：

1. **建立直觉**：当你看到一个新的类型类，你能猜出它大致的定律
    
2. **识别模式**：当你发现一段代码重复出现，你能认出它对应哪个抽象
    
3. **避免错误**：当你实现类型类实例时，你知道该遵守什么定律
    

```
-- 用 QuickCheck 测试 Functor 定律
functorIdentity :: (Functor f, Eq (f a)) => f a -> Bool
functorIdentity x = fmap id x == x

functorComposition :: (Functor f, Eq (f c)) 
                   => f a -> (a -> b) -> (b -> c) -> Bool
functorComposition x f g = 
  fmap (g . f) x == (fmap g . fmap f) x
```

## 11.3 Identity 和 Const：最纯粹的函子实例

这一节韩冬用两个"极简"的函子实例，帮你建立函子的直觉。

### Identity 函子

```
newtype Identity a = Identity { runIdentity :: a }

instance Functor Identity where
  fmap f (Identity x) = Identity (f x)
```

**🔑 洞见九：Identity 是"裸函子"**

`Identity a` 就是一个把 `a` 原封不动包起来的容器。`fmap f` 对它做的事情就是"解开、应用 `f`、再包回去"——**它不做任何额外的事**。

Identity 函子的意义在于：

1. **它是函子的"单位元"**：`Identity` 在函子组合中扮演的角色，类似于 `1` 在乘法中的角色
    
2. **它是理解"函子本质"的最简模型**：剥掉所有语法糖，`fmap f` 对 `Identity` 做的事，就是 `fmap f` 对任何函子做的事的"原型"
    
3. **它在后续章节扮演关键角色**：在 Monad Transformers（第二十四章）里，`IdentityT` 是 transformer 栈的"基底"
    

### Const 函子

```
newtype Const a b = Const { getConst :: a }

instance Functor (Const a) where
  fmap _ (Const x) = Const x
```

**🔑 洞见十：Const 是"忽略函数参数的函子"**

注意 `Const a b` 有两个类型参数，但**作为 Functor 实例时，被映射的是 `b`，而 `a` 被忽略**。`fmap f` 对 `Const x` 做的是：**完全忽略 `f`，原样返回 `Const x`**。

为什么这个看似"啥也没做"的东西是函子？验证定律：

```
-- 恒等律
fmap id (Const x) = Const x = id (Const x)  ✓

-- 组合律
fmap (f . g) (Const x) = Const x
fmap f (fmap g (Const x)) = fmap f (Const x) = Const x  ✓
```

两条定律都满足！

**🔑 洞见十一：Const 的"矛盾"与其深意**

`Const a b` 的"函子性"体现在 `b` 上，但 `b` 根本没出现在值里——值只有 `a`。这意味着：**`fmap` 对 `Const` 来说，纯粹是个"类型层面的把戏"**。

但正是这个"把戏"，让 `Const` 在后续章节成为**极其强大的工具**：

- **第十四章**：`Const a` 的 Applicative 实例，配合 `Const m` 的 Monoid 实例，可以实现"从结构中提取 `m` 类型的值"——这正是 Lens 库的核心机制之一
    
- **第十二章透镜组**：Lens 的本质是 `forall f. Functor f => (a -> f b) -> (s -> f t)`，`Const a` 和 `Identity` 是理解这个类型签名的钥匙
    

> 💡 **这就是 Haskell 抽象的美学**：一个看似"啥也不做"的 `Const`，通过与 Applicative、Monoid 的组合，变成了透镜（Lens）这种强大抽象的基石。你会在第十二章看到它的威力。

### 实际应用

```
-- Identity：纯粹的包装
runIdentity (fmap (*2) (Identity 5))  -- 10

-- Const：忽略映射函数
getConst (fmap (+100) (Const "hello"))  -- "hello"
-- 注意：(+100) 完全没被使用！

-- Const 与 Monoid 的组合（预览第十四章内容）
import Data.Monoid
getConst (fmap (<> "world") (Const "hello "))  -- "hello world"
```

## 11.4 IO 函子：当函子遇上副作用

这是本章**最具颠覆性**的一节。韩冬要回答的问题是：**IO 能不能是 Functor？**

### IO 的本质

`IO a` 代表"一个可能产生 I/O 副作用、最终产出 `a` 类型值的计算"。从"容器视角"看，它装的是一个 `a`；从"上下文视角"看，它是一个"带副作用的 `a`"。

### 🔑 洞见十二：IO 的 Functor 实例

```
instance Functor IO where
  fmap f m = do
    x <- m
    return (f x)
```

或者更直观地：

```
instance Functor IO where
  fmap f io = io >>= (\x -> return (f x))
```

**这个实例在做的事**：

1. 执行 `io` 这个计算，得到结果 `x`
    
2. 对 `x` 应用 `f`，得到 `f x`
    
3. 把 `f x` 包回 `IO` 上下文
    

**关键洞察**：`fmap f` **不改变 `io` 的副作用**，只是在"最终结果"上应用 `f`。

### 🔑 洞见十三：IO 函子定律的深刻含义

验证 `IO` 的 Functor 定律：

```
-- 恒等律
fmap id io = io  -- 执行 io，对结果应用 id，再包回 IO
               -- 等价于直接执行 io

-- 组合律
fmap (f . g) io = fmap f (fmap g io)
-- 左边：执行 io，应用 (f . g) 到结果
-- 右边：执行 io，应用 g 到结果，再应用 f
-- 两者执行 io 的次数相同（都是 1 次），结果相同
```

**这意味着**：`fmap` 对 `IO` 来说，是**安全的**——它不会让副作用被执行多次，也不会改变副作用的本质。

### 🔑 洞见十四：为什么 `fmap` 对 `IO` 如此重要？

思考下面的代码：

```
-- 读取一行，转换为大写，再输出
main = do
  line <- getLine
  putStrLn (map toUpper line)

-- 用 fmap 改写
main = putStrLn . map toUpper =<< getLine
main = fmap (map toUpper) getLine >>= putStrLn
```

**`fmap (map toUpper) getLine` 的含义**：

- 执行 `getLine`（等待用户输入）
    
- 对输入的字符串应用 `map toUpper`
    
- 返回一个"已经是大写"的 IO 计算
    

**这就是"上下文视角"的威力**：`fmap` 让你能在"不执行 IO"的前提下，描述"IO 完成之后要对结果做什么"。这种"描述而非执行"的风格，正是 Haskell 纯函数式哲学的核心。

### 🔑 洞见十五：IO 函子揭示了"纯"与"不纯"的边界

Haskell 是纯函数式语言——所有函数都必须是引用透明的。但 `IO` 显然涉及副作用（读写文件、网络通信、打印屏幕）。Haskell 的解决方案是：

- **`IO a` 本身是一个纯的值**——它只是"对计算的的描述"，而不是"计算本身"
    
- **`fmap` 和 `>>=` 等操作，都是在纯的环境中组合这些"描述"**
    
- **真正的"执行"发生在 `main :: IO ()` 上**——由运行时系统负责
    

**`IO` 是 `Functor` 这件事，让"纯函数组合"和"不纯的 IO 操作"能够无缝衔接**：

```
-- 这些都是纯函数——它们只是组合 IO 描述
transform1 :: IO String -> IO String
transform1 = fmap (map toUpper)

transform2 :: IO String -> IO (Int, String)
transform2 = fmap (\s -> (length s, s))

-- 组合纯函数
pipeline :: IO (Int, String)
pipeline = transform2 . transform1 $ getLine
```

> 💡 这是 Haskell "用纯函数描述不纯计算"的核心机制。`IO` 的 `Functor`、`Applicative`、`Monad` 实例，让你能用纯函数的组合子来搭建 I/O 管道——这是第十六章"Monad"和第二十章"IO 单子"的主旋律。

### 实际应用

```
-- 读取字符并转为大写
getUpperChar :: IO Char
getUpperChar = fmap toUpper getChar

-- 读取一行并计算长度
lineLength :: IO Int
lineLength = fmap length getLine

-- 组合多个 IO 操作
processInput :: IO String
processInput = fmap (map toUpper . filter isAlpha) getLine

-- 在 GHCi 中试：
-- λ> fmap (*2) (return 21)
-- 42
-- λ> fmap length getLine
-- hello world
-- 12
```

## 📝 本章核心洞见总结

> **洞见一：Functor 是"可映射性"本身的抽象**。
> 
> 它不是"列表的 map"的推广，而是"任何保持结构不变的容器/上下文"的抽象。`fmap :: (a -> b) -> f a -> f b` 中 `f` 是类型构造子——这是 Haskell 的"高阶多态"。

> **洞见二：Functor 定律是"结构保持不变"的数学保证**。
> 
> `fmap id = id` 和 `fmap (f . g) = fmap f . fmap g` 这两条定律，确保了 `fmap` 只改变容器里的值，不改变容器的形状。违反定律的实例（如偷偷计数的 `CMaybe`）不是真正的 Functor。

> **洞见三：Functor 定律直接来自范畴论**。
> 
> 范畴论中，函子 F: C → D 必须保持恒等态射（F(id) = id）和组合（F(g∘f) = F(g)∘F(f)）。翻译到 Haskell，这正是 Functor 的两条定律。**Haskell 的 `Functor` 类型类是数学函子的精确落地**。

> **洞见四：容器与上下文是函子的两种互补视角**。
> 
> "容器视角"帮你理解 `fmap` 做什么（遍历、变换），"上下文视角"帮你理解 `fmap` 不做什么（不碰上下文）。后者是理解 Applicative 和 Monad 的关键。

> **洞见五：Identity 是"裸函子"**。
> 
> 它不做任何额外的事，是函子组合中的"单位元"。理解 Identity，就理解了"函子本质"的最简模型。

> **洞见六：Const 是"忽略函数参数的函子"**。
> 
> 看似啥也没做，但与 Monoid 组合后，它成为了 Lens 库的基石。这是 Haskell 抽象美学的极致——简单的部件通过组合产生巨大的威力。

> **洞见七：IO 是 Functor 这一事实，揭示了"纯"与"不纯"的边界**。
> 
> `IO a` 本身是一个纯的值（对计算的描述），`fmap` 让你在纯的环境中组合这些描述，而真正的执行发生在 `main` 上。这是 Haskell "用纯函数描述不纯计算"的核心机制。

> **洞见八：Set 不能是 Haskell 的 Functor**。
> 
> 因为 `Set` 要求元素满足 `Ord` 约束，而 `fmap` 的签名要求对任意 `a` 和 `b` 都工作。**这是 Haskell "类型安全优先于便利"哲学的又一体现**。

## 🛠️ 实践建议

1. **为你的数据类型实现 Functor 实例**：
    
    ```
    data Tree a = Empty | Node (Tree a) a (Tree a)
    
    instance Functor Tree where
      fmap _ Empty = Empty
      fmap f (Node l x r) = Node (fmap f l) (f x) (fmap f r)
    ```
    
    体会"递归地保持结构"。
    
2. **用 QuickCheck 测试 Functor 定律**：
    
    ```
    functorLaws :: (Functor f, Eq (f a), Eq (f c)) 
               => f a -> (a -> b) -> (b -> c) -> Bool
    functorLaws x f g =
      fmap id x == x &&
      fmap (g . f) x == fmap g (fmap f x)
    ```
    
3. **理解 `fmap` 与 `.` 的关系**：
    
    ```
    -- 对函数映射就是组合
    fmap f g = f . g   -- 当 f 是 ((->) e) 时
    
    -- 这意味着
    fmap (*2) (+3) 1  -- 先 (+3) 得到 4，再 (*2) 得到 8
    ```
    
4. **感受 IO 函子的"描述性"**：
    
    ```
    -- 这些都是"纯"的描述
    getName :: IO String
    getName = fmap (map toUpper) getLine
    
    -- 组合描述
    process :: IO (Int, String)
    process = fmap (\s -> (length s, s)) getName
    ```
    
5. **记住 Functor 的"最小完整定义"**：
    
    - 只需要实现 `fmap`
        
    - `fmap` 必须满足两条定律
        
    - 编译器不检查定律，但你的良心应该检查

-- Functor 做不到的事：
