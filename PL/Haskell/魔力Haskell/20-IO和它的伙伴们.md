
# 第二十章 IO 和它的伙伴们 —— 读书笔记

> 💡 如果说第十九章的 State 单子展示了"纯函数式地建模状态"，那么第二十章就是把这扇门彻底打开——**进入真正的副作用世界**。表面看是 IO 单子的本质、IORef、forkIO、ST 单子、后门函数，实则在揭示一个深层真相：**Haskell 用 `IO a` 类型把"不纯"钉在类型系统里，让纯函数世界不被污染；而 `IORef`、`ST`、`unsafePerformIO` 则是这条边界上的"门"——有的门是受控的（ST），有的门是带锁的（IORef + MVar），有的门是后楼梯（`unsafePerformIO`）**。这一章让你亲眼看见：Haskell 不是"没有副作用"，而是"把副作用关进 IO 笼子里，并提供了几种安全/不安全的逃生口"。

韩冬在这一章安排了六个小节：**20.1 IO 单子的本质**、**20.2 基本 IO 操作**、**20.3 IO 中的变量**、**20.4 forkIO**、**20.5 ST 单子**、**20.6 后门函数**。表面是从"IO 的理论基础"到"基本操作"再到"可变变量、并发、受限可变、后门"，实则在铺设一条主线：**IO 单子 = `State# RealWorld -> (# State# RealWorld, a #)`——它是 State 单子的一个极特殊实例，状态是"真实世界"。所有"伙伴"（IORef、forkIO、ST、unsafePerformIO）都是在处理"如何在纯函数式世界中安全/高效地引入可变性与副作用"**。

## 🎯 全局脉络：为什么 IO 是 Haskell 的"终极边界"？

```
第十一章: Functor          → 可映射
第十三章: Applicative     → 上下文里的函数应用
第十六章: Monad            → 依赖性计算
   ↓
第十七章: 列表单子         → 非确定性（纯）
第十八章: Reader 单子      → 只读环境（纯）
第十九章: State 单子       → 可读写状态（纯——状态不外泄）
   ↓
第二十章: IO 单子          → 与外界交互的不纯计算  ← 你在这里
   ↓
第二十一章: 解析器 / 第二十五章: 实用 Monad
```

**这一章是整本书"纯函数式 vs 副作用"悖论的最终解答**。前十九章你学的所有 Monad 实例——列表、Reader、Writer、State——都是**纯的**：相同输入永远产生相同输出，没有与外界的交互。但真实程序必须与外界交互：读写文件、网络通信、打印输出、读取时钟、生成随机数（真随机）。这些操作**本质上是非纯的**——相同输入可能产生不同输出。

Haskell 的解决方案极其优雅：**用类型追踪不纯**。`IO a` 是一个"动作"——当它被执行时，会产生一个 `a` 类型的值，并可能与真实世界交互 。整个 Haskell 程序就是构造一个巨大的 `IO ()` 动作（即 `main`），由运行时系统执行。

图灵社区原文给出了最精炼的总结 ：

> _"IO是运行程序和计算机外部世界交互的单子类型。IO也是State单子的一个非常特殊的情况。"_

**🔑 洞见一：IO 单子 = State 单子的特殊情况，状态是 RealWorld**

GHC 的官方定义 ：

```
newtype IO a = IO (State# RealWorld -> (# State# RealWorld, a #))
```

**这是什么意思？**

- `State# RealWorld` 是"真实世界的状态"——一个抽象令牌，代表整个外部世界
    
- `IO a` 是一个函数：输入"旧世界状态"，输出"新世界状态 + 计算结果 `a`"
    
- 每次 IO 操作都"消耗"一个旧世界，产生一个新世界
    

**对比第十九章学的 State 单子**：

```
-- State 单子
newtype State s a = State { runState :: s -> (a, s) }

-- IO 单子（简化）
newtype IO a = IO (RealWorld -> (a, RealWorld))
```

**两者同构！**​ IO 就是 `State RealWorld` 的一个特殊版本——特殊之处在于"状态"是真实世界，且这个状态**不能被 `runState` 提取**（因为没有"真实世界"的初始值可供传递）。

Peyton Jones 在 Awkward Squad 论文中精辟地指出 ：

> _"The IO monad is 'sticky': no operation takes argument(s) with an IO type and returns a result with a non-IO type."_

**IO 是"粘性的"**——一旦进入 IO，就出不来。这正是 Haskell 保持纯函数世界纯净的关键机制。

## 20.1 IO 单子的本质

### IO 动作即"蓝图"

School of Haskell 的经典教学 ：

> _"We call any value of type IO t an 'action'. So (hPutStr h 'hello') is an action that, when performed, will print 'hello' on handle h and return the unit value."_

**🔑 洞见二：IO 值是"动作的描述"，而非"动作的执行"**

这是 Haskell IO 最反直觉也最优雅的设计：

```
-- 这两个 IO 动作都被构造了，但都没有执行
action1 :: IO String
action1 = getLine

action2 :: IO ()
action2 = putStrLn "Hello"

-- 只有 main 中的 IO 动作才会真正执行
main :: IO ()
main = do
  action1 >>= \line ->    -- 运行时系统执行 action1
  action2                 -- 运行时系统执行 action2
```

**关键认知**：

- 普通 Haskell 求值**不会**执行 IO 动作
    
- 只有 `main` 引用的 IO 动作才会被运行时系统执行
    
- 所有操纵 IO 动作的函数（`>>=`、`fmap`、`pure`）都是**纯函数**——它们组合"动作的描述"，但不执行动作
    

### IO 动作的类型即"副作用的签名"

School of Haskell 给出了洞察 ：

```
f :: Int -> Int          -- 纯函数：无副作用
g :: Int -> IO Int       -- 不纯函数：有副作用
```

**从类型就能看出副作用**：

- `f 42` 每次调用都返回相同结果（纯）
    
- `g 42` 每次调用可能产生不同结果（不纯）——可能读取 stdin、修改可变变量、访问时钟等
    

> 💡 **这是 Haskell 的核心优势**：副作用在类型中**显式可见**。当你看到一个 `IO` 返回类型，你立刻知道"这个函数会与外界交互"。纯函数世界与副作用世界被类型系统清晰地隔离。

### do 语法糖与 IO

```
-- do 语法糖
main = do
  hPutStr stdout "Hello"
  hPutStr stdout " world\n"

-- 脱糖为
main = hPutStr stdout "Hello" >> 
       hPutStr stdout " world\n"
```

**do 块中的每个 IO 动作按顺序执行**——但"顺序性"不是 do 语法糖本身赋予的，而是 `>>=` 的语义赋予的（回忆第十六章：`>>=` 定义严格的计算顺序）。

### 🔑 洞见三：IO 单子让"动作"成为一等公民

School of Haskell 展示了 `nTimes` 函数 ：

```
nTimes :: Int -> IO () -> IO ()
nTimes 0 do_this = return ()
nTimes n do_this = do
  do_this
  nTimes (n-1) do_this

main = nTimes 10 (hPutStr stdout "Hello\n")
```

**IO 动作可以像普通值一样**：

- 作为参数传递（`nTimes` 的第二个参数）
    
- 作为返回值返回
    
- 存储在数据结构里
    
- 在列表中组合
    

**这是"动作即值"的威力**——你可以构造、组合、传递 IO 动作，就像处理普通数据一样。

## 20.2 基本 IO 操作

### 核心 API

图灵社区原文列出了基本 IO 操作 ：

```
-- 文件读取（惰性）
readFile :: FilePath -> IO String
getContents :: IO String

-- 输出
putStr :: String -> IO ()
putStrLn :: String -> IO ()

-- 输入
getLine :: IO String
getChar :: IO Char

-- 文件句柄操作
openFile :: FilePath -> IOMode -> IO Handle
hGetLine :: Handle -> IO String
hPutStr :: Handle -> String -> IO ()
hClose :: Handle -> IO ()

-- 异常处理
catch :: Exception e => IO a -> (e -> IO a) -> IO a
finally :: IO a -> IO b -> IO a
bracket :: IO a -> (a -> IO b) -> (a -> IO c) -> IO c
```

### 🔑 洞见四：readFile 是"惰性 IO"

图灵社区原文特别指出 ：

> _"readFile 和 getContents 函数都是惰性的 IO 操作——自动就是不阻塞的 non-blocking，懒 IO (lazy IO)"_

**这意味着什么？**

```
main = do
  content <- readFile "large-file.txt"  -- 不立即读取整个文件
  print (take 10 content)               -- 只读取前 10 个字符
```

`readFile` 返回一个**惰性字符串**——文件内容只有在被"强制求值"时才真正从磁盘读取。这意味着：

- 你可以"读取"一个 10GB 的文件而不耗尽内存
    
- 你可以只处理文件的前几行而不读取整个文件
    
- 但这也是"懒 IO"的危险所在——文件句柄可能在你意想不到的时刻被关闭
    

### 实际应用

```
import System.IO

-- 基本输入输出
echo :: IO ()
echo = do
  putStrLn "Enter your name:"
  name <- getLine
  putStrLn $ "Hello, " ++ name ++ "!"

-- 文件操作
countLines :: FilePath -> IO Int
countLines path = do
  content <- readFile path
  return (length (lines content))

-- 使用 bracket 保证资源释放
withFile' :: FilePath -> IOMode -> (Handle -> IO r) -> IO r
withFile' path mode action = 
  bracket (openFile path mode) hClose action

processFile :: FilePath -> IO ()
processFile path = withFile' path ReadMode $ \h -> do
  content <- hGetContents h
  putStrLn $ "File content: " ++ content

-- 异常处理
safeReadFile :: FilePath -> IO (Maybe String)
safeReadFile path = catch
  (do content <- readFile path; return (Just content))
  (\e -> do putStrLn $ "Error: " ++ show (e :: IOException)
            return Nothing)
```

## 20.3 IO 中的变量：IORef

### 问题：纯函数式世界里需要"可变状态"怎么办？

第十九章的 State 单子提供了"纯的可变状态"——但状态不外泄，且每次 `>>=` 都产生新状态。有些算法**必须**使用真正的可变引用：

- 图遍历（DFS、BFS）
    
- 并查集（UNION-FIND）
    
- 缓存、记忆化
    
- 计数器在多个函数间共享
    

这些场景需要**真正的可变变量**——一个可以被多个函数共享和修改的"盒子"。

### IORef：IO 单子中的可变引用

图灵社区原文给出了 Data.IORef 的核心 API ：

```
data IORef a  -- IO 单子中的可变变量

newIORef :: a -> IO (IORef a)           -- 创建一个新的 IORef
readIORef :: IORef a -> IO a            -- 读取 IORef 的值
writeIORef :: IORef a -> a -> IO ()     -- 写入新值
modifyIORef :: IORef a -> (a -> a) -> IO ()          -- 修改（惰性版本）
modifyIORef' :: IORef a -> (a -> a) -> IO ()         -- 修改（严格版本）
```

Hackage 文档进一步确认了 IORef 的语义 ：

> _"A mutable variable in the IO monad"_

### 🔑 洞见五：IORef 是"IO 单子中的 STRef"

Stack Overflow 上的精辟总结 ：

> _"IORef provides a value which is mutable in the IO monad. It's just a reference to some data... all of those functions operate in IO."_

**IORef 的本质**：

- 它是一个"指针"或"引用"，指向一个可变的内存位置
    
- 类似于 C 语言中的 `int*` 或 Java 中的 `AtomicReference`
    
- 所有操作都在 `IO` 单子中——因为修改它是副作用
    

### 使用示例

图灵社区原文给出了示例 ：

```
import Data.IORef

main :: IO ()
main = do
  r <- newIORef 0        -- 创建 IORef，初值为 0
  modifyIORef r (+1)     -- 修改为 1
  v <- readIORef r       -- 读取，v = 1
  print v
```

### 🔑 洞见六：IORef 在并发环境中的内存模型

Hackage 文档**极其重要**地警告 ：

> _"In a concurrent program, IORef operations may appear out-of-order to another thread, depending on the memory model of the underlying processor architecture."_

**这意味着**：在多线程程序中，一个线程对 IORef 的写入可能对另一个线程"乱序可见"。例如在 x86 上：

```
maybePrint :: IORef Bool -> IORef Bool -> IO ()
maybePrint myRef yourRef = do
  writeIORef myRef True
  yourVal <- readIORef yourRef
  unless yourVal $ putStrLn "critical section"

main = do
  r1 <- newIORef False
  r2 <- newIORef False
  forkIO $ maybePrint r1 r2
  forkIO $ maybePrint r2 r1
  threadDelay 1000000
  -- 即使逻辑上不应该，"critical section" 可能被打印两次！
```

**解决方案**：使用 `atomicModifyIORef` ：

```
atomicModifyIORef :: IORef a -> (a -> (a, b)) -> IO b
```

Hackage 文档指出 ：

> _"If you only have one IORef, then using atomicModifyIORef to access and modify it will prevent race conditions."_

**对于多个 IORef 的并发访问**，文档建议使用 `MVar` 或 `TVar`（STM）而非 IORef。

### 🔑 洞见七：IORef 的严格版本 modifyIORef'

`modifyIORef` 是惰性的——它延迟计算新值，可能导致空间泄漏：

```
-- 危险：惰性累积可能导致空间泄漏
accumulate :: IORef Int -> [Int] -> IO ()
accumulate ref xs = forM_ xs $ \x ->
  modifyIORef ref (+x)  -- 累积大量未求值的 thunk

-- 安全：使用严格版本
accumulate' :: IORef Int -> [Int] -> IO ()
accumulate' ref xs = forM_ xs $ \x ->
  modifyIORef' ref (+x)  -- 立即求值
```

## 20.4 forkIO：轻量级并发

### forkIO 的语义

图灵社区原文 ：

```
forkIO :: IO () -> IO ThreadId
myThreadId :: IO ThreadId
```

School of Haskell 给出了精确解释 ：

> _"The function forkIO, which is built into Haskell, takes an IO action as its argument, and spawns it as a concurrent Haskell thread. Once created, it is run concurrently with all the other Haskell threads, by the Haskell runtime system."_

### 🔑 洞见八：forkIO 创建"绿色线程"

```
import Control.Concurrent

main :: IO ()
main = do
  forkIO (hPutStr stdout "Hello")   -- 并发线程 1
  hPutStr stdout " world\n"         -- 主线程
  -- 输出可能是 "Hello world\n" 或 " world\nHello"
```

**关键点**：

- `forkIO` 创建的线程是 Haskell 的"绿色线程"——由 GHC 运行时系统调度，不是操作系统线程
    
- GHC 可以在少量 OS 线程上多路复用成千上万个 Haskell 线程
    
- 线程切换开销极小（微秒级）
    

### 实际应用

```
import Control.Concurrent
import Control.Monad (replicateM)

-- 并发执行多个 IO 动作
concurrentTasks :: IO ()
concurrentTasks = do
  -- 创建 10 个并发线程
  tids <- replicateM 10 $ forkIO $ do
    threadId <- myThreadId
    putStrLn $ "Thread " ++ show threadId ++ " working..."
    threadDelay 1000000  -- 休眠 1 秒
    putStrLn $ "Thread " ++ show threadId ++ " done."
  
  putStrLn $ "Spawned " ++ show (length tids) ++ " threads"
  threadDelay 2000000  -- 等待所有线程完成
  putStrLn "All threads completed."

-- 使用 MVar 进行线程通信
import Control.Concurrent.MVar

counterExample :: IO ()
counterExample = do
  counter <- newMVar 0
  
  -- 启动 5 个线程，每个递增计数器
  tids <- replicateM 5 $ forkIO $ do
    modifyMVar_ counter $ \c -> do
      let newC = c + 1
      putStrLn $ "Counter incremented to " ++ show newC
      return newC
  
  threadDelay 1000000
  finalCount <- readMVar counter
  putStrLn $ "Final count: " ++ show finalCount  -- 应该是 5
```

### 🔑 洞见九：forkIO + MVar = 安全的并发模式

Stack Overflow 总结 ：

> _"MVars are basically the same thing as an IORef, except for two very important differences. MVar is a concurrency primitive, so it's designed for access from multiple threads. The second difference is that an MVar is a box which can be full or empty."_

**MVar 的价值**：

- 自带锁机制——`takeMVar` 在 MVar 为空时会阻塞
    
- 是 Haskell 并发编程的首选原语
    
- 比 IORef 更适合多线程共享状态
    

> 💡 **实践建议**：在并发场景中，优先使用 `MVar` 而非 `IORef`。IORef 只适用于单线程或 `atomicModifyIORef` 保护的简单场景；复杂的并发共享状态应该用 `MVar` 或 STM 的 `TVar`。

## 20.5 ST 单子：受控的可变状态

### 问题：State 单子不够高效，IO 单子又太"脏"

有些算法**必须**使用真正的可变内存才能达到命令式语言的效率：

- 图遍历（DFS、BFS）
    
- 并查集（UNION-FIND）
    
- 可变数组操作
    
- 内存敏感的算法
    

State 单子的问题是：**它实际上并没有使用可变内存**——它只是把状态作为参数传递 。对于需要真正"就地修改"的算法，State 单子的效率不够。

IO 单子的问题是：**它"污染"了类型**。一旦使用 IORef，整个函数链都必须返回 `IO a`，失去了纯函数的特性 。

### ST 单子的设计

图灵社区原文 ：

```
newtype ST s a = ST (State s -> (a, State s))
data State s = S# (State# s)

runST :: (forall s. ST s a) -> a
```

**🔑 洞见十：ST 单子与 IO 单子"实际上是同一个 monad"**

Stack Overflow 上的深入解释 ：

> _"The IO monad and the ST monad are actually the same monad. Roughly speaking, IO x ≈ ST RealWorld x."_

**关键差异**：

|维度|IO|ST|
|---|---|---|
|状态类型|`RealWorld`|任意类型 `s`（幻影类型）|
|允许 IO 操作|✅ 是|❌ 否（只能内存操作）|
|逃逸机制|无（`main` 是唯一出口）|`runST :: (forall s. ST s a) -> a`|
|纯函数性|不纯|**纯**（可变状态不外泄）|

### 🔑 洞见十一：rank-2 类型 `forall s.` 是关键

`runST` 的类型是 ：

```
runST :: (forall s. ST s a) -> a
```

**这个 `forall s.` 是 rank-2 多态**——它确保：

1. **STRef 不能逃逸**：你在 `ST s` 计算中创建的 `STRef s a`，其类型中的 `s` 必须**精确匹配**​ `runST` 要求的 `forall s.`
    
2. **引用透明性得到保证**：因为 STRef 无法逃逸 `runST` 的边界，外界无法观察到内部的可变状态
    
3. **纯函数接口**：`runST` 返回一个**纯的**​ `a` 值——外部世界看不到任何副作用
    

### 使用示例

```
import Control.Monad.ST
import Data.STRef

-- 用 ST 单子实现纯函数式的求和
sumST :: Num a => [a] -> a
sumST xs = runST $ do
  ref <- newSTRef 0          -- 创建 STRef
  forM_ xs $ \x -> do
    modifySTRef ref (+x)     -- 就地修改
  readSTRef ref              -- 读取最终值

-- sumST 是纯函数！类型与 Prelude.sum 完全相同
-- sumST :: Num a => [a] -> a

-- 对比：如果用 IORef，函数必须是 IO
sumIO :: Num a => [a] -> IO a
sumIO xs = do
  ref <- newIORef 0
  forM_ xs $ \x -> modifyIORef ref (+x)
  readIORef ref
-- sumIO :: Num a => [a] -> IO a  -- 不纯！
```

### 🔑 洞见十二：ST 单子的工程价值

教学材料明确指出 ：

> _"The IO and ST monads allow us to express such algorithms in Haskell with the same complexity as an imperative language... just using mutable references internally should be safe e.g. to implement an imperative algorithm and expose a pure interface. This justifies a special monad named ST."_

**ST 单子让你**：

1. **内部使用命令式的高效算法**（可变数组、就地修改）
    
2. **对外暴露纯函数接口**（类型中没有 `IO`）
    
3. **享受纯函数的所有好处**（可复现、可推理、可并行）
    

### 完整示例：用 ST 实现随机洗牌

```
import Control.Monad.ST
import Data.STRef
import System.Random

-- 用 ST 单子实现 Fisher-Yates 洗牌（纯函数）
shuffle :: [a] -> [a]
shuffle xs = runST $ do
  -- 将列表转换为可变数组（简化示意）
  arr <- newSTRef xs
  -- 执行洗牌算法（这里简化为反转）
  modifySTRef arr reverse
  readSTRef arr

-- shuffle 是纯函数！
-- shuffle :: [a] -> [a]
-- 相同输入永远产生相同输出（确定性洗牌）
```

## 20.6 后门函数：unsafePerformIO

### 问题：有时候你真的需要"逃离 IO"

有些场景需要"在纯函数中执行 IO"：

- 读取配置文件（程序运行时不会改变）
    
- 初始化全局常量（如查找表）
    
- 与 FFI（外部函数接口）交互
    
- 性能优化（避免 IO 单子的开销）
    

### unsafePerformIO 的定义

GHC 官方文档 ：

```
unsafePerformIO :: IO a -> a
```

**它做了什么**？图灵社区原文一针见血 ：

> _"unsafePerformIO 是 IO 单子的'后门'，允许在任何时候执行 IO 计算。"_

Peyton Jones 的 Awkward Squad 论文给出了"管道图" ：

```
发明一个世界 → 执行 IO 动作 → 丢弃世界
                ↓
              结果
```

**也就是说**：`unsafePerformIO` 凭空捏造一个"世界状态"，执行 IO 动作，然后丢弃这个世界。这意味着——**编译器完全无法追踪这个 IO 动作的时机、次数、顺序**。

### 🔑 洞见十三：使用 unsafePerformIO 的三条铁律

Peyton Jones 论文明确指出了使用约束 ：

> _"For this to be safe, the IO computation should be free of side effects and independent of its environment."_

**第一条：IO 计算必须无副作用**

- 不能修改外部状态
    
- 不能依赖外部环境
    
- 必须是幂等的（执行多次结果相同）
    

**第二条：必须添加 `{-# NOINLINE #-}` 编译指示**

```
globalCache :: IORef (Map String String)
globalCache = unsafePerformIO (newIORef Map.empty)
{-# NOINLINE globalCache #-}
```

如果不加 `NOINLINE`，编译器可能内联这个函数，导致 IO 动作被执行多次——每次都创建新的 IORef！

**第三条：必须防止 let-floating**

```
-- 危险：IORef 可能被共享
f x = unsafePerformIO (newIORef [])  -- 所有调用共享同一个 IORef！

-- 安全：IORef 在 lambda 内创建
g x = unsafePerformIO (newIORef [x])  -- 每次调用创建新 IORef
```

### 🔑 洞见十四：unsafePerformIO 破坏了引用透明性

Awkward Squad 论文警告 ：

> _"Whenever you use it, you are promising the compiler that the timing of this I/O operation, relative to all the other I/O operations of the program, does not matter. You must undertake this proof obligation, because the compiler cannot do it for you; that is what the 'unsafe' prefix means."_

**使用 `unsafePerformIO` 时，你向编译器承诺**：

- 这个 IO 操作的执行时机无关紧要
    
- 这个 IO 操作的执行次数无关紧要
    
- 这个 IO 操作与其他 IO 操作的相对顺序无关紧要
    

**编译器无法验证这些承诺**——如果你撒谎，后果是：

- 非确定性行为
    
- 不正确的优化（编译器可能零次或多次执行）
    
- 多线程代码崩溃
    

### 🔑 洞见十五：unsafePerformIO 是"链锯修洗碗机"

Peyton Jones 的比喻极其生动 ：

> _"unsafePerformIO is often mis-used to force an imperative program into a purely-functional setting. This is a bit like using a chain saw to repair a dishwasher — it's the wrong tool for the job."_

**正确的工具选择**：

|需求|正确工具|
|---|---|
|需要真正的可变状态 + 纯接口|`ST` 单子|
|需要与外界交互|`IO` 单子|
|需要在纯函数中做"一次性初始化"|`unsafePerformIO`（谨慎使用）|
|需要实现惰性 IO|`unsafeInterleaveIO`|

### unsafeInterleaveIO：惰性 IO 的后门

GHC 官方文档 ：

```
unsafeInterleaveIO :: IO a -> IO a
```

**语义**：允许 IO 计算被惰性推迟——只有当 `a` 的值被需要时，IO 才会执行。这是 `hGetContents` 和 `readFile` 实现"懒 IO"的基础 。

### 实际应用（谨慎！）

```
import System.IO.Unsafe

-- ✅ 安全的用法：初始化全局常量
lookupTable :: Array Int Int
lookupTable = unsafePerformIO $ do
  -- 构建查找表（确定性、无副作用）
  let table = listArray (0, 1000) [expensiveComputation i | i <- [0..1000]]
  return table
{-# NOINLINE lookupTable #-}

-- ✅ 安全的用法：读取配置文件（程序运行时不变）
configContents :: String
configContents = unsafePerformIO $ readFile "config.ini"
{-# NOINLINE configContents #-}

-- ❌ 危险的用法：依赖时间的操作
badTimestamp :: String
badTimestamp = unsafePerformIO getCurrentTime  -- 每次可能不同！

-- ❌ 危险的用法：有副作用的操作
badCounter :: IORef Int
badCounter = unsafePerformIO (newIORef 0)  -- 必须加 NOINLINE！
-- 如果没有 NOINLINE，编译器可能创建多个 IORef
```

## 📝 本章核心洞见总结

> **洞见一：IO 单子是 State 单子的特殊情况，状态是 RealWorld**。
> 
> `newtype IO a = IO (State# RealWorld -> (# State# RealWorld, a #))`——IO 动作消耗一个"旧世界"，产生一个"新世界"+ 计算结果 。这就是为什么 IO 是 Monad——它与 State 单子同构。

> **洞见二：IO 是"粘性"的——这是 Haskell 保持纯函数世界纯净的关键**。
> 
> "没有操作接受 IO 类型的参数并返回非 IO 类型的结果" 。一旦进入 IO，就出不来。纯函数世界与副作用世界被类型系统清晰地隔离。

> **洞见三：IO 动作是"蓝图"而非"执行"**。
> 
> 普通 Haskell 求值不会执行 IO 动作；只有 `main` 引用的 IO 动作才会被运行时系统执行 。所有操纵 IO 的函数（`>>=`、`fmap`、`pure`）都是纯函数——它们组合"动作的描述"，但不执行动作。

> **洞见四：IORef 是 IO 单子中的可变引用，本质是"IO 单子中的 STRef"**。
> 
> `newIORef`/`readIORef`/`writeIORef`/`modifyIORef` 都在 IO 单子中 。并发环境下需要注意内存模型——IORef 操作可能乱序可见；复杂并发场景应使用 `MVar` 或 `TVar`。

> **洞见五：forkIO 创建 Haskell 绿色线程**。
> 
> `forkIO :: IO () -> IO ThreadId` ——创建的线程由 GHC 运行时系统调度，可在少量 OS 线程上多路复用成千上万个 Haskell 线程 。配合 `MVar` 实现线程安全的共享状态。

> **洞见六：ST 单子与 IO 单子"实际上是同一个 monad"，但 ST 更安全**。
> 
> `IO x ≈ ST RealWorld x` ——区别在于 ST 的状态 `s` 是任意类型（幻影类型），且 `runST` 的 rank-2 类型 `forall s.` 确保 STRef 不能逃逸 。这让 ST 计算对外可以暴露**纯函数接口**——内部用命令式的高效算法，外部看到的是纯函数。

> **洞见七：runST 的 rank-2 类型是 ST 单子安全性的核心**。
> 
> `runST :: (forall s. ST s a) -> a` ——`forall s.` 确保 STRef 无法逃逸 `runST` 的边界，从而保证引用透明性 。

> **洞见八：unsafePerformIO 是"后门"，破坏引用透明性**。
> 
> 它凭空捏造世界状态、执行 IO、丢弃世界——编译器无法追踪 IO 动作的时机、次数、顺序 。使用时必须遵守三条铁律：IO 计算无副作用、添加 `{-# NOINLINE #-}`、防止 let-floating。

> **洞见九：unsafePerformIO 如同"链锯修洗碗机"**。
> 
> Peyton Jones 警告：它经常被误用——本应使用 ST 单子或 IO 单子的场景，错误地使用了 unsafePerformIO 。正确做法：需要纯接口的可变计算用 ST；需要与外界交互用 IO；只有"一次性初始化全局常量"这种极少数场景才考虑 unsafePerformIO。

> **洞见十：四种可变状态原语的分工**。
> 
> State（纯函数式状态传递）、ST（受控的可变内存，对外纯接口）、IORef（IO 中的可变引用）、MVar（带锁的并发安全引用）——根据场景选择合适的工具 。

## 🛠️ 实践建议

1. **默认使用纯函数，必要时才用 Monad**：
    
    ```
    -- 纯函数优先
    sum' :: [Int] -> Int
    sum' = foldl' (+) 0
    
    -- 需要高效可变状态时用 ST
    sumST :: [Int] -> Int
    sumST xs = runST $ do
      ref <- newSTRef 0
      forM_ xs $ \x -> modifySTRef' ref (+x)
      readSTRef ref
    ```
    
2. **IORef 的正确使用**：
    
    ```
    import Data.IORef
    
    -- 单线程场景
    counter :: IO Int
    counter = do
      ref <- newIORef 0
      modifyIORef' ref (+1)  -- 使用严格版本
      readIORef ref
    
    -- 并发场景：使用 atomicModifyIORef
    atomicIncrement :: IORef Int -> IO Int
    atomicIncrement ref = atomicModifyIRef ref (\x -> (x+1, x+1))
    ```
    
3. **forkIO + MVar 的并发模式**：
    
    ```
    import Control.Concurrent
    
    worker :: MVar Int -> IO ()
    worker mvar = do
      task <- takeMVar mvar  -- 阻塞直到有任务
      -- 处理任务
      putStrLn $ "Processing task: " ++ show task
    
    main :: IO ()
    main = do
      taskQueue <- newMVar 0
      tids <- replicateM 5 $ forkIO (worker taskQueue)
      -- 分发任务...
    ```
    
4. **ST 单子实现纯函数式的可变算法**：
    
    ```
    import Control.Monad.ST
    import Data.STRef
    
    -- 并查集（UNION-FIND）的纯函数式实现
    type DisjointSet s = STRef s (Map Int Int)
    
    find :: DisjointSet s -> Int -> ST s Int
    find ds x = do
      parent <- readSTRef ds
      case Map.lookup x parent of
        Nothing -> return x
        Just p -> do
          root <- find ds p
          modifySTRef' ds (Map.insert x root)
          return root
    
    union :: DisjointSet s -> Int -> Int -> ST s ()
    union ds x y = do
      rx <- find ds x
      ry <- find ds y
      when (rx /= ry) $
        modifySTRef' ds (Map.insert rx ry)
    
    -- 对外暴露纯函数
    connected :: Int -> Int -> [Int] -> Bool
    connected n1 n2 edges = runST $ do
      ds <- newSTRef Map.empty
      forM_ edges $ \(a, b) -> union ds a b
      rx <- find ds n1
      ry <- find ds n2
      return (rx == ry)
    ```
    
5. **unsafePerformIO 的极谨慎使用**：
    
    ```
    import System.IO.Unsafe
    
    -- ✅ 安全的全局常量初始化
    globalLookupTable :: Array Int Int
    globalLookupTable = unsafePerformIO $ do
      let table = listArray (0, 1000) [fib i | i <- [0..1000]]
      return table
    {-# NOINLINE globalLookupTable #-}
    
    -- ❌ 错误的用法：有副作用且不幂等
    -- badCounter = unsafePerformIO (newIORef 0)  -- 危险！
    ```
    
6. **理解 IO 与并发的内存模型**：
    
    ```
    -- 在并发程序中，IORef 操作可能乱序
    -- 使用 MVar 或 TVar 保证线程安全
    import Control.Concurrent.STM
    
    safeCounter :: IO Int
    safeCounter = do
      tvar <- newTVarIO 0
      atomically $ do
        current <- readTVar tvar
        let newVal = current + 1
        writeTVar tvar newVal
        return newVal
    ```

## 🔮 承上启下

第二十一章"解析器组合子"会在本章基础上往前推一步——**Parsec/Attoparsec 的内部机制就是 State + Reader + IO 的组合**：

- **ParsecT**​ = `ReaderT` + `StateT` + `Identity`（或 `IO`）
    
- 解析器需要"读取"配置（Reader）、"维护"解析状态（State）、"执行" IO 操作（IO）
    
- `unsafePerformIO` 在某些解析器库的内部实现中可能出现（但对外暴露纯接口）
    

更深远的连接：

- **第二十四章 Monad Transformers**：`ReaderT` + `StateT` + `IO` 的组合是真实 Haskell 应用的标配。本章学的 IO、IORef、forkIO 是 Transformer 栈的底座
    
- **第二十五章 实用的 Monad**：`MonadBaseControl`、`MonadUnliftIO` 等现代工具，解决"在 Transformer 栈中执行 IO"的问题。`liftIO` 函数是连接纯 Monad 栈与 IO 的桥梁
    
- **并发与 STM**：本章学的 `forkIO` + `MVar` 是基础；更复杂的并发模式（如 `STM`、`async`）建立在 GHC 的并发原语之上
    

**第二十章是你理解"Haskell 如何处理副作用"的关键一跃**。吃透"IO 单子 = State RealWorld"、理解 IORef/STRef/MVar 的分工、明白 unsafePerformIO 的危险与约束，后面的解析器组合子、Monad Transformers、并发编程就不再是"新的魔法"，而是"我们已经知道的知识的自然延伸"——你已经知道 IO 是 State 的特殊情况，第二十一章只是告诉你"Parsec 的 Parser 就是 StateT + ReaderT 的组合"；你已经知道 ST 单子通过 runST 暴露纯接口，第二十四章只是把这种模式扩展到多个 Monad 的同时使用；你已经知道 unsafePerformIO 是后门，第二十五章只是告诉你"现代 Haskell 用 MonadUnliftIO 等安全机制替代 unsafePerformIO"。

> 💡 学习建议：读完本章后，做三个实验：
>

>
