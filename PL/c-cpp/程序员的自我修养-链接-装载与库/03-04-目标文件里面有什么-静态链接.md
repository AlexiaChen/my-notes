## 第3章 目标文件里有什么

### 3.1 目标文件的格式

Windows 下有 PE，Linux 下有 ELF，两者都是 COFF 格式的变体。不仅是可执行文件，动态链接库 `.dll`/`.so`、静态链接库 `.lib`/`.a` 也都是可执行文件格式 。

**第一性原理视角**：为什么需要一种"标准格式"来存放编译产物？因为**编译器、汇编器、链接器、装载器是四个独立程序**，它们必须通过某种"中间契约"来交换信息。目标文件格式就是这个契约。

> 💡 **目标文件 = 编译器与链接器之间的 API**。就像 HTTP 是客户端与服务端之间的契约一样，ELF 是"编译产出"与"链接消费"之间的契约。

这个契约必须携带四类信息：

1. **代码和数据**（`.text`、`.data`、`.bss`、`.rodata`）——程序本身
2. **元数据**（文件头、节区表）——描述文件结构
3. **链接所需的辅助信息**（符号表、重定位表、字符串表）——留给链接器的"待办事项"
4. **调试信息**（`.debug_*`）——留给调试器的"源码地图"

**工业界对照（2026）**：ELF 自 1990 年代标准化以来，其核心结构惊人地稳定。今天 x86-64、ARM64、RISC-V 全都在用同一种 ELF 格式，只是某些细节（如重定位类型）因架构而异——例如 i386 使用 `SHT_REL`，而 x86_64 强制使用 `SHT_RELA`（带显式加数的重定位条目）。这种"核心不变 + 边缘扩展"的特性，正是优秀二进制格式的标志。

### 3.2 目标文件是什么样的

一个典型的 ELF 目标文件从高处俯瞰是这样的层次：

```
┌─────────────────────────────────┐
│ ELF Header（文件头）             │ ← 描述整个文件
├─────────────────────────────────┤
│ .text        代码段              │
│ .data        已初始化数据        │
│ .bss         未初始化数据        │
│ .rodata      只读数据            │
│ .rel.text    代码段重定位表      │
│ .symtab      符号表              │
│ .strtab      字符串表            │
│ .debug_*     DWARF 调试信息     │
│ ...                             │
├─────────────────────────────────┤
│ Section Header Table（节区表）   │ ← 描述每个 section
└─────────────────────────────────┘
```

**第一性原理视角**：为什么要分"段"（section/segment）？因为**不同类型的字节有不同的"命运"**——`.text` 要被执行、`.data` 要被读写、`.rodata` 只读、`.bss` 不占文件空间只在装载时分配。把相同属性的字节放在一起，装载器才能以"页"为单位批量映射，操作系统才能精确地设置权限位（读/写/执行）。

> 📌 **指令与数据分离的深层原因**：
> 
> 1. **安全性**：代码段可设为只读+可执行，数据段可读写但不可执行（抵御代码注入攻击，配合 NX bit）
> 2. **可共享**：多个进程可共享同一份 `.text`（物理内存只存一份），但 `.data`/`.bss` 各进程私有
> 3. **可重定位**：指令和数据的重定位方式不同，分开处理更清晰

**洞见**：`.bss` 段是个非常巧妙的设计——它"占地址空间但不占文件空间"。未初始化的全局变量反正都是 0，没必要在磁盘上存一堆零字节，只需在节区表里记录"我需要这么大的清零内存"即可。这是"信息压缩"思想在二进制格式里的应用。

### 3.3 挖掘 SIMPLESECTION.O

原书用一个 `simplesection.c` 做实验：

```
int printf(const char* format, ...);
int global_init_var = 84;
int global_uninit_var;
void func1(int i) { printf("%d\n", i); }
int main(void) {
    static int static_var = 85;
    static int static_var2;
    int a = 1;
    int b;
    func1(static_var + static_var2 + a + b);
    return a;
}
```

编译成 `simplesection.o` 后用 `objdump` 查看，会发现：

|变量|存放位置|
|---|---|
|`global_init_var = 84`|`.data`（已初始化）|
|`global_uninit_var`|`.bss`（未初始化）或 COMMON|
|`static_var = 85`|`.data`（局部静态，已初始化）|
|`static_var2`|`.bss`（局部静态，未初始化）|
|`a`, `b`|栈上（不在目标文件里）|
|`"%d\n"`|`.rodata`（字符串常量）|
|`func1`, `main`|`.text`（函数体）|

**第一性原理视角**：这个简单的例子揭示了**作用域与存储期的矩阵**：

> 🎯 **变量的存储位置 = f(作用域, 生命周期, 是否初始化)**。
> 
> - 全局/静态 + 已初始化 → `.data`
> - 全局/静态 + 未初始化 → `.bss` 或 COMMON
> - 局部 + 非 static → 栈（不在目标文件里）
> - 字符串字面量/const 全局 → `.rodata`

**关键观察**：局部变量 `a` 和 `b` **根本没有出现在目标文件里**。因为它们在函数调用时由栈指针动态分配，编译期只需生成"在栈帧偏移 X 处读写"的指令即可。这提示我们：**目标文件只持久化"跨函数/跨文件可见"的状态**，纯局部的瞬时状态留给运行时栈。

用 `objdump -h` 可以查看各段大小，`objdump -s -d` 可以同时查看十六进制内容和反汇编，`readelf -s` 查看符号表。现代工具链推荐用 `llvm-objdump` 和 `llvm-readelf`，它们对最新 ELF 特性的支持更好。

### 3.4 ELF 文件结构描述

这是本章的技术核心。ELF 文件由以下关键结构组成：

**1. ELF 文件头（ELF Header）**

描述整个文件的元信息：魔数、字长（32/64位）、字节序、文件类型（`.o`/可执行/`/so`）、目标机器架构、程序入口地址、节区表的位置和数量 。

**2. 节区表（Section Header Table）**

这是一个数组，每个元素描述一个 section 的属性：

- 节区名称（`.text`、`.data` 等）
- 节区类型（`SHT_PROGBITS` 程序数据、`SHT_SYMTAB` 符号表、`SHT_RELA` 重定位表）
- 节区标志（`SHF_WRITE` 可写、`SHF_ALLOC` 装载时分配内存、`SHF_EXECINSTR` 可执行）
- 文件偏移、大小、对齐方式、链接信息

**3. 节区（Sections）**

按功能划分的数据块。关键节区：

- `.text`：机器指令
- `.data`：已初始化的全局/静态变量
- `.bss`：`SHT_NOBITS` 类型，不占文件空间，装载时清零
- `.rodata`：只读数据（字符串常量、跳转表）
- `.symtab`：符号表（`.symtab`/`.dynsym`）
- `.strtab`：字符串表（存储符号名、节区名）
- `.rel.text`/`.rela.text`：重定位表

**4. 符号表（Symbol Table）**

每个符号包含 ：

- `st_name`：名称（索引到 `.strtab`）
- `st_value`：值（可重定位文件中是节内偏移，可执行文件中是虚拟地址）
- `st_size`：大小
- `st_info`：类型和绑定（绑定：`STB_LOCAL`/`STB_GLOBAL`/`STB_WEAK`；类型：`STT_FUNC`/`STT_OBJECT`）
- `st_shndx`：所在节区索引（`SHN_UNDEF` 未定义、`SHN_COMMON` 公共块、`SHN_ABS` 绝对值）

**5. 重定位表（Relocation Table）**

每个需要重定位的 section 都有一个对应的重定位节区（如 `.rela.text` 对应 `.text`）。每个重定位条目包含 ：

- `r_offset`：要修正的位置（可重定位文件中是节内偏移，可执行文件中是虚拟地址）
- `r_info`：符号表索引 + 重定位类型（如 `R_X86_64_PLT32`）
- `r_addend`（仅 `SHT_RELA`）：显式加数

**第一性原理视角**：ELF 的核心设计哲学是**"一切皆节区，节区皆可被描述和引用"**。

> 💡 注意一个深刻细节：**符号的值 `st_value` 在不同阶段含义不同**。
> 
> - 在 `.o` 文件里：`st_value` 是"节内偏移"
> - 在可执行文件里：`st_value` 是"虚拟地址"
> 
> 这意味着 —— 编译器和汇编器在编译单元内部用"相对视图"工作，链接器把"相对视图"转换为"绝对视图"。**目标文件本质上是"带着待办清单的相对快照"，而可执行文件是"所有待办已完成的绝对终态"**。

**工业界对照（2026）**：现代 ELF 文件还会包含：

- `.note.gnu.property`：描述程序的 ABI 特性（如是否支持 CET 影子栈、GNU2 TLS 等）
- `.gnu.hash`：动态符号哈希表（加速动态链接）
- `.eh_frame` / `.eh_frame_hdr`：异常处理/栈展开信息（C++ 异常、backtrace 都靠它）
- `.comment`：编译器版本信息

LLVM 的 `lld` 链接器在生成 ELF 时，会自动插入这些现代节区。理解 ELF 不只是理解 1990 年代的规范，更要理解这些"当代增补"。

### 3.5 链接的接口——符号

符号是链接的"API"。链接器的工作本质上就是**把"符号引用"匹配到"符号定义"**。

**符号的分类**：

1. **按定义状态** ：
    - **Defined（已定义）**：在本文件中分配了存储空间
    - **Tentative（暂定）**：已创建但尚未确定大小或分配存储——典型如 C 语言的未初始化全局变量，或 Fortran 的 COMMON 块
    - **Undefined（未定义）**：被引用但未在本文件中定义
2. **按绑定属性** ：
    - `STB_LOCAL`：局部符号（C 的 `static`），不参与链接
    - `STB_GLOBAL`：全局符号
    - `STB_WEAK`：弱符号（gcc 的 `__attribute__((weak))`），优先级低于全局符号
3. **强弱符号规则**（Oracle 官方文档给出的 precedence） ：
    
    > **Defined dominates Tentative dominates Undefined**
    
      
    具体规则：
    - 强符号不允许重复定义
    - 一个强符号 + 多个弱符号 → 选强符号
    - 全是弱符号 → 选占用空间最大的（COMMON 机制）

**第一性原理视角**：为什么需要"弱符号"？因为**库设计师无法预知用户会如何定义符号**。弱符号让库的默认实现可以被用户的强符号覆盖——这是"依赖注入"在链接期的体现。

```
// 库代码
#pragma weak my_hook
void my_hook() { /* 默认空实现 */ }

// 用户代码
void my_hook() { /* 用户自定义实现，自动覆盖库的默认版本 */ }
```

**符号修饰（Name Mangling）**：C++ 为了支持函数重载、命名空间、类成员，会把 `void foo(int)` 修饰成 `_Z3fooi` 这样的符号名。这就是为什么 C++ 库要给 C 代码用时必须加 `extern "C"`。

**特殊符号**：链接器在生成可执行文件时会定义一批特殊符号，可以直接在程序里引用 ：

- `__executable_start`：程序起始地址
- `__etext` / `_etext`：代码段结束地址
- `_edata` / `edata`：数据段结束地址
- `_end` / `end`：程序结束地址

**工业界对照（2026）**：现代 C++ 工程的符号管理远比书里描述的复杂：

- **符号可见性**：GCC/Clang 支持 `-fvisibility=hidden`，默认隐藏所有符号，只用 `__attribute__((visibility("default")))` 显式导出。这是构建高性能共享库的标配——减少动态符号表大小，加快动态链接速度
- **符号版本化**：glibc 用 `asm(".symver")` 实现符号版本控制，让同一个 `.so` 可以同时提供 `memcpy@GLIBC_2.2.5` 和 `memcpy@GLIBC_2.14` 两个版本
- **C++20 模块**：正在从根本上改变符号的导出方式，未来 C++ 也许不再依赖 name mangling 做接口隔离

### 3.6 调试信息

编译时加 `-g` 选项，编译器会在 ELF 里写入 **DWARF**​ 格式的调试信息（Debug With Arbitrary Record Format，对 ELF 的双关语）。

**DWARF 的关键节区**​ ：

- `.debug_info`：核心调试信息
- `.debug_abbrev`：缩写表
- `.debug_line`：源码行号 → 机器指令的映射
- `.debug_pubnames` / `.debug_pubtypes`：公开名称和类型
- `.debug_aranges`：地址范围 → 编译单元映射
- `.debug_str`：调试用的字符串
- `.debug_loc`：变量的位置信息

**第一性原理视角**：调试信息本质上是一个**"机器码 ↔ 源代码"的反向映射数据库**。没有它，gdb 看到的就是一堆裸指令；有了它，gdb 才能告诉你"当前执行到 `main.c` 的第 42 行"、"变量 `x` 当前值是 5"。

> 📌 **调试信息有三层价值**：
> 
> 1. **行号映射**：`objdump -l` 可显示每条指令对应的源码行
> 2. **变量追踪**：gdb 能显示变量名和值
> 3. **类型信息**：gdb 能理解 `struct` 的字段布局

**工业界对照（2026）**：调试信息的处理在现代工具链中已经形成标准工作流 ：

```
# 1. 编译时生成调试信息
gcc -g -o app app.c

# 2. 提取调试信息到独立文件
objcopy --only-keep-debug app app.debug

# 3. strip 原始二进制，减小体积
strip app

# 4. 在 strip 后的二进制里添加调试信息链接
objcopy --add-gnu-debuglink=app.debug app
```

这样发布的二进制是精简的，但保留了指向 `.debug` 文件的链接。当 gdb 启动时，会通过 `.gnu_debuglink` 节区的哈希值校验并自动加载调试信息。

现代 Linux 发行版（Fedora、Ubuntu、Debian）普遍采用 **debuginfo 包**​ 机制：二进制本身不带调试信息，但可以从软件源安装 `app-debuginfo` 包来获取。对于内核转储（core dump）调试，这通常配合 **Build ID**​ 使用——每个 ELF 文件都有一个唯一的 Build ID，调试器用它来精确匹配对应的 debuginfo 。

**洞见**：调试信息的分离处理揭示了软件分发的一个核心矛盾——**开发者需要信息，用户需要精简**。DWARF + strip + debuglink 是这个矛盾在工业界的优雅解。

## 第4章 静态链接

### 4.1 空间与地址分配

链接器的第一步是"空间和地址分配"。有两种朴素策略：

**策略一：按序叠加**

把每个 `.o` 的 `.text`/`.data`/`.bss` 简单地首尾相接拼起来。这种方法会产生大量零散的小段，不符合"段(page)对齐"的要求，浪费地址空间，已被淘汰。

**策略二：相似段合并（现代链接器采用）**

把所有 `.o` 的 `.text` 合并成一个大的 `.text`，所有 `.data` 合并成一个大的 `.data`，以此类推。合并后的段在装载时按页对齐，高效且紧凑 。

**第一性原理视角**：这一步的本质是**从"局部相对视图"到"全局绝对视图"的转换**。

在合并之前，每个 `.o` 的 `.text` 都是从地址 0 开始的相对布局；合并之后，链接器确定了最终可执行文件里 `.text` 的整体起始虚拟地址（如 `0x401000`），进而计算出每个函数在合并后 `.text` 里的绝对虚拟地址。

> 💡 这一步完成了两件独立的事：
> 
> 1. **段合并**：把所有输入段按类型归类
> 2. **地址分配**：为每个段、每个符号分配最终的虚拟地址

**工业界对照（2026）**：现代链接器在空间分配上做了大量优化：

- **lld**​ 和 **mold**​ 利用多核并行处理段合并，链接时间比 GNU ld 快 3-10 倍
- **Section GC（垃圾回收）**：`--gc-sections` 选项可以丢弃没有被入口点可达的段，显著减小二进制体积。这对 C++ 模板密集型代码尤其重要
- **ICF（Identical Code Folding）**：`--icf=safe` 可以把完全相同的函数体合并成一份，进一步减小体积

### 4.2 符号解析与重定位

这是静态链接的"灵魂"步骤。

**符号解析（Symbol Resolution）**：

链接器遍历所有输入目标文件，建立一个全局符号表。对于每个符号引用：

- 如果是 `undefined`，去其他目标文件或静态库里找 `defined`
- 如果找不到 → **"undefined reference" 链接错误**
- 如果找到多个 `defined` → 按强弱符号规则裁决

**重定位（Relocation）**：

这一步把"待办清单"逐项完成。链接器扫描每个需要重定位的 section（如 `.rela.text`），对每个重定位条目：

1. 根据 `r_info` 找到对应的符号
2. 根据符号的 `st_value`（现在已经分配了绝对虚拟地址）计算最终值
3. 把计算结果按 `r_offset` 写入目标位置

举例：假设 `main.o` 里有一条 `call` 指令要调用 `func1`，但编译时 `func1` 的地址未知，所以在 `.rela.text` 里留下一条重定位记录。链接器合并段后知道 `func1` 的最终地址是 `0x401234`，于是回到 `main` 的 `call` 指令处，把操作数修正为 `0x401234 - (call指令下一条指令的地址)`（PC 相对寻址）。

**第一性原理视角**：重定位的本质是**"延迟绑定地址"**。

> 🎯 **编译期不知道的地址，留个空位；链接期知道了，回填。**

这个机制之所以必要，是因为**单独编译每个 `.c` 文件时，编译器不可能知道其他文件里符号的最终地址**。重定位表就是"编译器与链接器之间的协作协议"——编译器说"这里我要调用 `func1`，但具体地址你（链接器）之后填"，链接器说"好的，合并完段我就回来填"。

**工业界对照（2026）**：符号解析与重定位在现代工具链中的演变：

- **LTO（Link-Time Optimization）**：把"编译"和"链接"的边界模糊化。Clang/GCC 在 `-flto` 模式下，目标文件里存的不是机器码，而是 LLVM IR 字节码。链接器在合并所有目标文件后，才做全程序优化和机器码生成
- **ThinLTO**：Google 开发的增量式 LTO，兼顾优化效果和编译速度
- **Incremental Linking**：Google 的 `blaze`/Bazel 通过精细的依赖追踪，避免不必要的重链接

一个真实的工业陷阱 ：当静态库包含 LLVM bitcode（用于 LTO）时，传统的 `ranlib` 工具可能无法识别库里的符号，导致"undefined symbol"错误。解决方法是用 `llvm-ranlib` 替代 `ranlib`，或者干脆不用 `ranlib`（链接器会 fallback 到逐个解析 `.o` 文件，代价是链接时间变长）。

### 4.3 COMMON 块

这是 C 语言历史上最微妙、最容易被忽视的机制之一。

**问题起源**：考虑以下代码

```
// a.c
int g;
// b.c  
int g;
```

按照 C 语言标准，未初始化的全局变量声明可以出现在多个编译单元里。编译器无法确定 `g` 的最终大小（万一另一个文件里 `g` 是 `long double` 呢？），所以把它标记为 **tentative symbol（暂定符号）**，放入 **COMMON 块**​ 。

**链接器的处理**​ ：

- 如果只有一个 `defined`（强符号）→ 用它的尺寸
- 如果全是 tentative → 选占用空间最大的那个
- 如果有一个 strong + 多个 tentative → 用 strong 的尺寸
- 如果有两个 strong → **多重定义错误**

**第一性原理视角**：COMMON 机制是**"延迟决策"**的典型——编译期不敢拍板的，推到链接期统一裁决。这种"延迟"哲学在操作系统的虚拟内存、CPU 的乱序执行、甚至分布式系统的 eventually consistency 里都能看到。

> ⚠️ **现代演进**：COMMON 机制虽然灵活，但会掩盖潜在的重复定义 Bug。因此**新版 GCC 已默认使用 `-fno-common`**​ ，即未初始化的全局变量直接放入 `.bss` 段并作为强符号处理。这样一来，上面的 `int g;` 在两处定义会直接报"多重定义"错误，迫使程序员显式用 `extern` 区分声明与定义。

这是个教科书式的例子，说明工业界如何用"默认行为变更"来**推动代码质量提升**——牺牲向后兼容，换取更早暴露 Bug。

### 4.4 C++ 相关问题

C++ 给静态链接带来了几个 C 语言没有的复杂性：

**1. 重复代码消除**

C++ 模板、外部内联函数、虚函数表都可能导致同一份代码被多个编译单元重复生成。例如：

```
// vector<int> 和 vector<double> 会各自生成一份实例化代码
// 每个用到 vector<int> 的 .cpp 文件都会包含一份 vector<int> 方法的副本
```

如果不消除重复，二进制会膨胀数倍。现代编译器/链接器的解法 ：

- **函数级 section**：把每个函数/模板实例放到独立的 section（GCC 的 `-ffunction-sections`）
- **链接器 ICF**：合并相同的 section
- **COMDAT**：使用 `SHT_COMDAT` 节区类型，让链接器知道"这些 section 内容等价，留一份即可"

**2. 函数签名与 Name Mangling**

C++ 的 `void foo(int, double)` 会被修饰成 `_Z3foodi`。这保证了即使函数重载，链接器看到的符号也是唯一的。但也带来一个问题：**跨编译器 ABI 兼容性**。GCC 和 Clang 的 name mangling 规则虽然遵循 Itanium ABI，但极端情况下仍有细微差异。

**3. 全局对象构造与析构**

C++ 全局对象的构造函数必须在 `main` 之前执行，析构函数在 `main` 之后执行。ELF 通过 `.init_array` 和 `.fini_array` 节区实现——链接器把所有全局对象的构造函数指针收集到 `.init_array`，程序启动时 `__libc_csu_init` 会遍历调用。

**4. 异常表（EH Frame）**

C++ 异常机制需要在运行时"展开栈"，这需要知道每个函数的栈帧布局。`.eh_frame` 节区存储了这些信息，由 `__gxx_personality_v0` 异常处理函数消费。

**工业界对照（2026）**：

- **C++20 模块**：从根本上解决重复代码问题。模块显式声明导出接口，编译一次，多处引用，不再需要"头文件文本包含 + 模板重复实例化"的老路
- **lld 对 C++ 的支持**：lld 对 COMDAT、ICF 的处理比 GNU ld 更激进，链接出的 C++ 二进制通常更小
- **符号可见性最佳实践**：现代 C++ 库（如 LLVM、Abseil）默认 `-fvisibility=hidden`，显式导出公共 API，避免符号表膨胀和潜在冲突

### 4.5 静态库链接

静态库（`.a`）本质是 **`ar` 工具打包的一组 `.o` 文件**，外加一个符号索引表。

**链接规则**：链接器从左到右扫描命令行参数，维护两个集合：

- **已定义的符号集合**
- **未定义的符号集合**

当遇到一个 `.a` 时，链接器只看那些**能解析当前未定义符号的 `.o` 文件**，把它们提取出来合并。这就是为什么**静态库的链接顺序很重要**：`-lfoo -lbar` 和 `-lbar -lfoo` 可能产生不同的结果，甚至后者会报 undefined reference。

**第一性原理视角**：静态库链接是**"按需提取"**——链接器不会把整个 `.a` 都链进来，只挑解决当前未定义符号的那些 `.o`。这既节省空间，也避免引入不必要的依赖。

> 💡 这也解释了为什么循环依赖需要特殊处理：如果 `liba.a` 依赖 `libb.a`，`libb.a` 又依赖 `liba.a`，单次从左到右扫描无法解决。解决方案：
> 
> ```
> gcc main.o -la -lb -la   # 重复列出，二次扫描
> # 或用 --start-group / --end-group
> gcc main.o -Wl,--start-group -la -lb -Wl,--end-group
> ```

**工业界对照（2026）**：静态链接在现代工业界的重要性不降反升：

**1. 容器化与微服务**：

Go 语言默认静态链接，生成的二进制可以直接塞进 `FROM scratch` 的 Docker 镜像，体积只有几 MB，启动飞快。Rust 通过 musl 目标（`x86_64-unknown-linux-musl`）也能生成纯静态二进制 。

**2. 静态链接 libc++ 的现实挑战**​ ：

LLVM 论坛上有人报告：试图用 Clang 静态链接 libc++ 时，即使加了 `-static` 也不行，必须用：

```
clang++ -stdlib=libc++ -nostdlib++ \
  -Wl,--push-state,-Bstatic -lc++ -lc++abi -Wl,--pop-state
```

而且还需要用 export map 控制符号导出，否则会引发段错误。这揭示了一个重要事实：**"-static" 标志不是万能的**，尤其是在涉及 C++ 标准库、异常处理、RTTI 时。

**3. 现代静态链接策略**：

|场景|策略|
|---|---|
|CLI 工具 / 容器入口|完全静态链接（musl + static libstdc++）|
|长期运行的服务|动态链接 libc，静态链接 C++ 标准库|
|插件 / 共享库|动态链接一切，避免符号冲突|

**4. mold 链接器**：2021 年出现的现代链接器，比 lld 还快 2-3 倍，专为千万行级别的 C++ 项目优化。Chrome、Clang 本身都已迁移到 mold 或 lld。

### 4.6 链接过程控制

链接器不是黑盒子，它允许通过**链接脚本（Linker Script）**精细控制输出文件的布局。

**典型用途**：

- 指定各个段的起始地址（嵌入式系统常用）
- 定义特殊符号（如 `__executable_start`）
- 控制内存布局（如把 `.text` 放到特定的 ROM 地址）
- 插入自定义的段

**示例链接脚本片段**：

```
SECTIONS {
  . = 0x10000;
  .text : { *(.text) }
  . = 0x8000000;
  .data : { *(.data) }
  .bss : { *(.bss) }
}
```

**第一性原理视角**：链接脚本是**"程序员与链接器的对话协议"**——你告诉链接器"我想要这样的内存布局"，链接器照做。这种"声明式控制"的思想在 Kubernetes 的 YAML、Terraform 的 HCL 里都能看到影子。

**工业界对照（2026）**：

- **默认链接脚本**：`ld -verbose` 可以查看默认脚本，现代 Linux 系统的默认脚本由 glibc 提供，考虑了安全特性（如 RELRO、STACK PROTECTOR）
- **链接器选项**：`-z relro -z now` 启用 FULL RELRO（防御 GOT 覆写攻击），`-fstack-protector` 启用栈保护，这些都是通过链接脚本或链接选项控制的
- **自定义链接脚本在嵌入式领域的应用**：固件、Bootloader、操作系统内核都重度依赖链接脚本来控制内存映射

### 4.7 BFD 库

BFD（Binary File Descriptor）库是 GNU binutils（包括 `ld`、`objdump`、`readelf` 等）背后的核心库，它提供了一个统一的抽象层来处理不同格式（ELF、PE、COFF、Mach-O 等）的二进制文件。

**第一性原理视角**：BFD 是**"适配器模式"**的经典实现——上层工具（链接器、反汇编器）通过统一的 BFD API 操作二进制文件，底层由 BFD 处理不同格式的解析细节。这样 `objdump` 无需关心目标是 ELF 还是 PE，代码一次编写，处处运行。

**工业界对照（2026）**：BFD 虽然历史悠久，但工业界已经开始转向更现代的替代方案：

- **LLVM 的 `libObject`**：LLVM 工具链（clang、lld、llvm-objdump）使用的二进制处理库，比 BFD 更模块化、更类型安全
- **为什么 LLVM 不用 BFD**：BFD 的全局状态设计（global state）不利于多线程/并行处理，而 lld 的核心优势之一就是并行链接。此外 BFD 的错误处理模式（setjmp/longjmp）在现代 C++ 里被认为是不安全的
- **现状**：GNU 工具链仍在用 BFD，但 LLVM 生态已全部转向 `libObject`。两种实现并存，反映出"兼容性 vs 现代性"的权衡

### 4.8 本章小结

第4章的核心脉络：

> 📌 **静态链接 = 空间与地址分配 + 符号解析与重定位**。链接器把多个目标文件的局部相对视图，合并成一个全局绝对视图的可执行文件。这个过程中，COMMON 块解决了未初始化全局变量的延迟决策问题，静态库实现了按需提取的模块化，链接脚本提供了布局控制能力。

从第一性原理看，静态链接在做一件极其深刻的事：

> 🎯 **把"编译期的不确定性"在"链接期变为确定性"。**
> 
> 编译器在编译单个 `.c` 文件时，对外部符号一无所知——它只能留空（重定位条目）。链接器是唯一能看到全局的"上帝视角"，它把所有的"?"替换成具体的地址。这是"分治 + 拼装"哲学的最高体现：分治让编译可并行、可增量；拼装让全局一致、可解析。

**现代工业界对静态链接的重新平衡**：

静态链接在 1960s-1990s 曾被动态链接全面压制（因为节省内存、便于更新）。但 2020s 以来，由于：

- 容器化的兴起（部署便携性 > 内存共享）
- Go/Rust/musl 的工具链支持
- 安全考虑（减少动态库劫持面）
- 链接器性能的提升（lld/mold 让链接不再是瓶颈）

**静态链接迎来了第二春**——但不是简单的"回归"，而是"混合策略"：核心库静态链接保证可重现性，系统库动态链接享受安全更新。

## 跨章节串联洞见

把第3章和第4章合起来看，你会发现一个贯穿始终的第一性原理：

> 💡 **"信息分层 + 延迟决策"是系统软件的通用范式。**
> 
> - 目标文件分层：代码/数据/符号/重定位/调试信息各司其职
> - 链接过程延迟：编译期不确定的地址，延迟到链接期裁定
> - COMMON 块延迟：未初始化变量的大小，延迟到链接期确定
> - 虚拟内存延迟：物理页分配延迟到缺页异常时（第1章内容）
> - 动态链接延迟：符号解析延迟到装载/运行时（后续章节内容）

每一次"延迟"，都是为了在更早的阶段保持"局部性"和"灵活性"——这正是"分而治之"的工程化体现。

**工业界最新实践与书本知识的对照**：

|书本概念（2000s）|2026 工业现实|
|---|---|
|GNU ld 链接器|lld / mold 为主流，并行链接|
|普通静态链接|混合链接（static-libstdc++ + dynamic libc）|
|COMMON 块默认开启|`-fno-common` 成为 GCC 默认|
|调试信息直接嵌入|分离调试信息 + debuginfo 包 + Build ID|
|BFD 库|LLVM libObject|
|传统 `.o` 目标文件|可包含 LLVM bitcode 用于 LTO|
|C++ 头文件包含|C++20 模块逐步普及|

这本书的价值在于**讲透了"为什么"**——即使工具换了、格式增补了、默认行为变了，但"目标文件是编译器和链接器之间的契约"、"链接的本质是符号解析 + 重定位"这些第一性原理从未改变。理解了原理，你就能在任何新工具、新格式面前快速上手。
