# 第7章 管理数据聚集的符号表

> 本章一句话：当"数据聚集"（struct/record/class）出现，**作用域从"线性链"升级为"作用域树"**——类的成员本身构成一个独立作用域，继承则让这棵树长出父子边。学会为聚集类型构建作用域树，是理解面向对象语言语义建模的关键。

## 7.1 为结构体构建作用域树：聚合类型即"命名空间"

### 结构体/记录（struct/record）带来作用域的新形态

Parr 在 7.1 节点出——**C 的 `struct`、Pascal 的 `record` 这类聚合类型，本质上是"把一组相关字段打包成一个新名字空间"**。当你写 `p.x` 时，"`.x`"的查找不是在当前函数的局部作用域里，而是在 `p` 的类型（`struct Point`）这个**独立的成员作用域**里。

**这意味着：一个 `struct` 定义，本身就承载着一个"成员符号表/作用域"**。每个字段（`x`、`y`、`name`）是这个成员作用域里的符号。

### 作用域从"链"升级为"树"

第6章的作用域是**一条链**（全局→函数→块，线性嵌套）。引入 struct 后，作用域变成了一棵**树**：

```
全局作用域 (GlobalScope)
 ├── 函数 f 的作用域
 │     └── 块作用域
 └── struct Point 的成员作用域  ← 新的作用域形态：聚合类型的成员空间
       ├── 字段 x : int
       └── 字段 y : int
```

访问 `p.x` 时的查找路径是：**先在当前作用域链上解析 `p` 的类型（得到 `Point`）→ 再进入 `Point` 的成员作用域查找 `x`**。这是一次"跨作用域"的两段式查找。

### 核心数据结构：聚合类型符号承载成员作用域

Parr 给出的建模方式（工业界事实标准）：

```
class StructSymbol extends Symbol implements Scope {
    Map<String, Symbol> members = new LinkedHashMap<>(); // 成员符号表
    Scope enclosingScope;  // 外层（通常是全局）

    void define(Symbol sym) { members.put(sym.name, sym); }
    Symbol resolve(String name) {
        Symbol s = members.get(name);
        if (s != null) return s;
        // struct 成员通常不上溯到外层（C 的规则），但可设计成上溯
        return null;
    }
}
```

**关键洞察**：`StructSymbol` **同时是一个 `Symbol`（可被变量引用其类型）和一个 `Scope`（承载成员名字空间）**。这种"符号即作用域"的双重身份，是面向对象语义建模的核心技巧。

**💡 我的洞见（第一性原理视角）：**

struct 引入作用域树这件事，揭示了一个比"编译器技术"更普遍的编程语言原理——**"聚合类型 = 把'数据'和'名字空间'合二为一"**。

C 的 `struct` 是这一思想的源头（1970s，让程序员自定义复合类型）；**而"`.` 运算符的本质，就是'进入右操作数类型的成员作用域做一次名字查找'"**——这个统一视角能让你一眼看穿 C 的 `p.x`、Go 的 `p.X`、Python 的 `p.x`、Java 的 `p.x` 在语义上的同构性：它们都是"类型作用域的成员查找"。

工业实证：

- **Clang 的 `RecordDecl`**：C 的 `struct`/union、C++ 的 `class` 在 Clang AST 里都是 `RecordDecl`，其 `decls()` 迭代器给出所有成员 `Decl`。`RecordDecl` 同时是 `DeclContext`（声明上下文=作用域），承载成员查找。
    
- **C 的 `->` vs `.`**：`p->x` 等价于 `(*p).x`——先解引用得到 `struct`，再进入其成员作用域。这是"C 指针+聚合"语义的精确体现。
    
- **Go 的 struct 与 promoted field**：Go 没有继承，但 struct 嵌套时内层 struct 的字段会被"提升（promote）"到外层，形成类似成员作用域链的效果——`outer.innerField` 可简写为 `outer.innerField` 直接访问。
    

### 成员访问表达式的语义动作

在 AST 遍历（Visitor/Listener）中处理 `p.x` 这类成员访问时，动作是：

1. 解析 `p` 的符号 → 得到其类型符号（如 `StructSymbol Point`）
    
2. 在 `Point` 的成员作用域内 `resolve("x")` → 得到字段符号
    
3. 整个表达式 `p.x` 的类型 = 字段 `x` 的类型
    

**这正是第8章类型检查中"成员访问表达式类型推导"的基础**——第7章先把这个"两段式查找"机制建好，第8章才能用它算类型。

## 7.2 为类构建作用域树：继承让作用域树长出父子边

### 类（class）是 struct 的"超集"+ 继承

Parr 在 7.2 节把 7.1 的 struct 成员作用域，扩展到**面向对象 class + 继承**。核心新增复杂度：

1. **方法（method）也是成员**：class 的成员作用域里既有字段（field）也有方法（method）。
    
2. **继承（inheritance）引入"父类作用域"**：子类作用域要能"看到"父类的成员。
    
3. **多态/重写（override）**：子类可重定义父类方法，查找时需按"子类优先"的顺序。
    

### 类作用域树的结构

```
全局作用域
 └── class Animal (ClassSymbol + Scope)
       ├── 字段 name : string
       ├── 方法 eat() : void
       └── 父类 Object 的作用域（继承链上溯）
             └── 方法 toString() : string
```

`ClassSymbol` 的 `resolve` 需要扩展为**沿继承链上溯查找**：

```
class ClassSymbol extends Symbol implements Scope {
    Map<String, Symbol> members;
    ClassSymbol superClass;  // 父类，构成作用域树的父子边

    Symbol resolve(String name) {
        Symbol s = members.get(name);
        if (s != null) return s;
        if (superClass != null)
            return superClass.resolve(name);  // 沿继承链上溯
        return null;
    }
}
```

### 继承查找的语义细节（Parr 结合 C++/Java 规则）

不同语言对"继承成员查找"有细微但关键的差异，Parr 在书中（及工业实证）揭示：

|语言|字段隐藏规则|方法重写规则|多继承/接口|
|---|---|---|---|
|**C++**​|子类字段隐藏父类同名字段（需 `using` 引入）|虚函数重写（`virtual`+`override`）|支持多继承，名字查找含" dominance rule"|
|**Java**​|子类字段隐藏父类字段（不推荐，编译警告）|`@Override` 注解标记重写|单继承类 + 多实现接口|
|**C#**​|字段隐藏需 `new` 关键字显式声明|`virtual`+`override` 显式配对|单继承 + 多接口|
|**Python**​|动态属性查找沿 MRO（方法解析顺序）|动态分派|多继承，MRO 用 C3 线性化|

**💡 我的洞见（第一性原理 + 创新想法）：**

7.2 节（结合工业实证）藏着一个极具深度的洞察——**"面向对象继承的本质，就是'作用域树的边'；而多态/重写的本质，就是'作用域查找的优先级规则'。"**

我从第一性原理把它提炼为**"继承 = 作用域链的一种新形态"**：

> **第6章的'作用域链'是'词法嵌套'（函数套函数、块套块）；第7章的'类作用域树'是'继承嵌套'（子类继承父类）。两者在查找算法上同构——都是'先查当前作用域，查不到沿父边向上'。唯一的区别是：词法作用域链是'线性栈'，继承作用域树是'可能分叉的树'（尤其多继承时）。**

**由此我提出一个"面向对象语义建模"的创新框架（供你设计语言/理解 OO 时参考）：**

> **"当你为一门 OO 语言设计符号表时，把'类'建模成'既是 Symbol 又是 Scope'的节点，把'继承'建模成 Scope 之间的'父边'。这样，成员查找、字段隐藏、方法重写、甚至接口默认方法冲突，全部统一为'在作用域树上按特定优先级做图遍历'的问题。C++ 的 dominance rule、Java 的默认方法冲突、Python 的 MRO，本质都是'作用域树遍历顺序'的不同策略。"**

工业实证（类作用域树 + 继承查找的真实落地）：

- **Clang 的 CXXRecordDecl + CXXBaseSpecifier**：C++ 的 `class` 在 Clang 里是 `CXXRecordDecl`（继承 `RecordDecl`），其基类通过 `CXXBaseSpecifier` 链入。成员查找 `LookupDecl` 会沿基类链上溯，并处理虚继承的 dominance rule（主导规则：若多个父路径汇入同一虚基类，只计一次）。
    
- **Java 的 `ClassSymbol` + `supertype()`**：javac 内部 `ClassSymbol` 有 `supertype_field`（父类）和 `interfaces_field`（接口列表）。成员查找先查本类 → 再查父类（递归）→ 最后查接口（默认方法需解决冲突）。
    
- **Python 的 MRO（Method Resolution Order）**：`class C(A, B):` 的方法查找顺序由 C3 线性化算法决定，存储在 `C.__mro__` 元组中。`p.x` 的查找就是沿 MRO 元组逐个类查 `__dict__`。这是"作用域树遍历顺序"在动态语言里的经典实现。
    
- **Go 的 promoted method**：Go 没有继承，但 struct 嵌套 + interface 实现让"内层类型的方法被提升到外层"——`outer.Method()` 若外层无此方法，会查找内层类型是否实现，形成类似继承方法查找的效果。

# 第8章 静态类型检查

> 本章一句话：有了第6-7章的符号表（名字→声明、类型信息挂在 Symbol 上），第8章终于可以回答——**"如何在不运行程序的情况下，系统地验证每个表达式、每个赋值、每个函数调用的类型使用都是合法的？"**​ 这就是静态类型检查（Static Type Checking）——它让编译器能在编译期捕获一大类错误，也是 Java/C#/TypeScript/Go/Rust 等静态语言的"安全护栏"。

## 8.1 类型检查的本质：在 AST 上做"类型推导 + 类型相容性验证"

### 核心思想：为每个 AST 节点标注一个类型

Parr 在开篇建立的直觉是——**类型检查的过程，就是"遍历 AST（后序，第5章 Visitor 模式），为每个孩子节点算出类型，再依据语言类型规则验证父节点操作是否合法"**。

算法骨架（Visitor 后序遍历）：

```
Type visit(Expr node) {
    Type leftType  = visit(node.left);
    Type rightType = visit(node.right);
    // 依据语言规则验证 + 推导父节点类型
    if (node.op == "+") {
        if (!leftType.isNumeric() || !rightType.isNumeric())
            error("+ 要求数值类型");
        return TypeRegistry.get("int");  // 或按提升规则返回
    }
    if (node.op == "=") {  // 赋值
        if (!rightType.isAssignableTo(leftType))
            error("赋值类型不兼容");
        return leftType;
    }
}
```

**关键数据结构约定**（承接第6-7章）：

- 每个 `Symbol`（变量/参数/字段）都有 `type` 字段
    
- 每个 `ClassSymbol` / `StructSymbol` 本身是 `Type`
    
- 内置类型 `int`/`float`/`string`/`boolean` 在全局作用域预注册
    

### 三类核心类型规则

Parr 在书中系统梳理了类型检查要处理的几类规则：

|规则类别|典型例子|检查逻辑|
|---|---|---|
|**赋值相容**​|`x = expr`|`expr.type` 可赋值给 `x.type`（含子类→父类、 boxing）|
|**运算符重载/类型**​|`a + b`|`a.type` 与 `b.type` 满足 `+` 的操作数类型要求|
|**函数调用**​|`f(arg1, arg2)`|实参类型列表可赋值给形参类型列表；返回类型为 `f` 的返回类型|
|**成员访问**​|`p.x`|`p.type` 的成员作用域内存在 `x`，表达式类型为 `x.type`（第7.2节机制）|
|**控制流条件**​|`if (cond) ...`|`cond.type` 可转为布尔（或可隐式转换）|
|**返回语句**​|`return expr`|`expr.type` 可赋值给函数返回类型|

**💡 我的洞见（第一性原理视角）：**

类型检查的第一性原理是——**"类型是对'值的集合'的分类标签；类型检查就是证明'每个操作都作用在其定义域之内'。"**

- `int` 类型 = "所有 32 位有符号整数的集合"
    
- `+` 操作的定义域 = "两个数值类型"
    
- 类型检查 = "验证每个 `+` 的两个操作数类型，都落在数值类型集合内"
    

**这本质上是'集合论'在程序语义上的应用**——类型相容性 = 子集关系（子类集合 ⊆ 父类集合 → 子类可赋值给父类）。理解到这一层，你就不会再把类型检查当成一堆 ad-hoc 的规则堆砌，而是一个**统一的"类型关系"推导系统**。

工业实证：

- **Java 的类型规则**：javac 的 `Attr`（属性标注）阶段做类型检查。`Attr.visitAssign` 验证右侧类型可赋值给左侧；`Attr.visitApply` 处理方法调用（含重载决议）；`Attr.visitSelect` 处理成员访问（用第7章的类作用域查找）。
    
- **C# 的 `TypeChecker` + 类型推断**：C# 在编译期做完整类型检查，含泛型类型推断（`var` 关键字、方法类型推断）。
    
- **Go 的静态类型 + 结构体等价**：Go 没有继承，类型相容靠"结构等价"（struct 字段相同即相容）而非"名字等价"，这让 Go 的接口实现是隐式的（只要方法集匹配）。
    

## 8.2 类型环境的传递：上下文相关的类型检查

### 为什么类型检查需要"上下文"

很多类型规则依赖**当前上下文**（context），而非只看子节点类型：

- **函数体内 `return expr;`**：需知道"当前函数的返回类型"才能验证 `expr` 是否相容。
    
- **lambda / 闭包**：需知道形参类型（由上下文推断或显式标注）才能检查函数体。
    
- **类型推断**：`var x = 3;` 需从初始化表达式 `3` 的类型（`int`）反向推断 `x` 的类型。
    

**这要求类型检查的 Visitor 在遍历时，把"当前期望类型 / 当前函数返回类型 / 当前类"作为上下文参数向下传递**——正是第5章 Visitor 模式"主动控制遍历+传参"的典型用武之地。

### 工业级类型检查器的架构（Parr 思想 + 现代实证）

综合 Parr 的思想和工业实践，一个完整的静态类型检查器架构是：

```
AST (第4章)
  ↓ 后序 Visitor 遍历（第5章）
类型检查器
  ├── 查符号表：每个名字 → Symbol → type（第6-7章）
  ├── 推导子节点类型（递归 visit）
  ├── 验证当前节点操作类型相容
  ├── 标注当前节点类型（供父节点使用）
  └── 上下文：当前函数返回类型 / 当前类 / 期望类型
  ↓
类型标注后的 AST + 错误列表
```

**💡 我的洞见（创新想法）：**

我把 Parr 第8章的思想，结合现代工业类型系统，提炼为**"类型检查器 = 带上下文传播的 AST 属性文法求值器"**：

> **"类型检查的本质，是用'属性文法（Attribute Grammar）'在 AST 上做一次自底向上的属性求值——每个节点的类型是其子节点类型的函数（合成属性），而某些节点的类型又受父节点/上下文约束（继承属性）。Visitor 模式正是属性文法在 OO 里的自然实现。"**

这个视角把"类型检查"从"一堆 if-else 规则"提升为**"一个统一的、声明式的属性推导系统"**——这也是为什么现代语言（TypeScript、Rust、Scala）的类型检查器都异常复杂却高度结构化：它们本质上都是在实现"带高级特性的属性文法求值器"。

工业实证（现代静态类型系统的前沿）：

- **TypeScript 的 `checker.ts`**：TypeScript 编译器中最大、最复杂的文件（超 10 万行），实现"结构化类型系统"（基于类型结构相容，而非名义类型）。`checker.ts` 用 Visitor 遍历 AST，维护"类型环境（TypeEnvironment）"，处理类型推断、上下文类型（contextual typing）、泛型实例化、交叉/联合类型等高级特性。
    
- **MyPy（Python 静态类型检查器）**：在 Python 源码上做静态类型检查（基于 PEP 484 类型注解）。MyPy 构建自己的 AST + 类型系统，用类似 Visitor 的方式遍历并标注类型，捕获类型错误而不运行程序——这正是 Parr 第8章思想的动态语言版落地。
    
- **Rust 的 `rustc_typeck`**：Rust 的所有权 + 生命周期 + 类型检查高度耦合，`typeck` 模块用" trait 求解器（trait solver）"处理泛型约束和 trait bound，是静态类型系统最前沿的工业实现之一。
    
- **Scala 的 `dotty`（Scala 3 编译器）**：实现"dotted types / 路径依赖类型"，类型检查器基于"依赖对象类型（DOT）"演算，是学术界类型理论与工业实现结合的最前沿。
    

## 8.3 类型检查能（和不能）捕获什么

### 静态类型检查的边界（重要！）

Parr 在章末（及工业实践共识）诚实地指出——**静态类型检查能捕获一大类错误，但不是万能的**：

|类型检查能捕获|类型检查不能捕获（需运行时/测试）|
|---|---|
|类型不匹配的赋值/参数/返回|数组越界（多数语言）|
|未定义/未声明的名字|空指针解引用（多数语言）|
|运算符作用于错误类型|除零、整数溢出（多数语言）|
|方法不存在/参数个数错|逻辑错误（算法写错）|
|继承/接口实现不兼容|资源泄漏（需线性类型/RAII）|

**关键洞察**：静态类型检查保证的是**"类型安全（Type Safety）"**——即"程序不会在运行时出现'把字符串当整数用'这类类型混淆错误"。但**它不保证"程序逻辑正确"**。

**💡 我的洞见（第一性原理 + 创新想法）：**

这里藏着一个深刻的"类型系统表达能力"谱系——**"一门语言的类型系统越强，它能静态捕获的错误就越多，但类型标注/推断的复杂度也越高"**：

```
弱类型检查（C）→ 名义类型（Java/C#）→ 结构化类型（TypeScript/Go）
                                          ↓
                              带泛型/特质（Rust/Scala/Haskell）
                                          ↓
                              依赖类型（Idris/Agda，可表达"数组长度"等运行时属性）
```

**由此我提出一个"类型系统设计"的选型框架（创新想法）：**

> **"为你的 DSL/语言设计类型系统时，先问——'我希望静态捕获多少类错误？'类型系统越强，用户写的代码越安全，但语言实现（类型检查器）越复杂、用户学习成本越高。绝大多数工业 DSL 落在'名义类型 + 轻量类型推断'区间（如 Java/C# 风格）；只有系统编程/形式化验证领域才需要 Rust/Scala/依赖类型级的强类型系统。"**

工业对照：

- **Java 的"类型擦除"妥协**：Java 泛型在运行时被擦除为 `Object`，导致 `List<String>` 和 `List<Integer>` 运行时无法区分——这是"为兼容旧字节码而牺牲类型表达力"的经典权衡。
    
- **TypeScript 的"结构化类型 + 渐进类型"**：TS 允许逐步从 JavaScript 迁移，类型标注可选（渐进类型），类型相容基于结构而非名义——这让 TS 既安全又灵活，是其大规模流行的关键。
    
- **Rust 的"借用检查器 + 生命周期"**：把"内存安全"编码进类型系统，让"空指针/数据竞争"在编译期被捕获——这是"用强类型系统静态捕获更多错误"的极致工业实践。

## 两章联系与全书定位（第7-8章合并视角）

把两章串成一条"语义分析内核"主线：

```
第7章 管理数据聚集的符号表
  7.1 struct/record → 聚合类型即成员作用域（作用域从"链"升级为"树"）
  7.2 class + 继承 → 类作用域树（继承链 = 作用域父边，成员查找沿继承链上溯）
        ↓ 符号表现在能完整解析"扁平名字 + 聚合成员 + 继承成员"
第8章 静态类型检查
  8.1 类型检查本质 = AST 后序 Visitor + 查符号表 type + 验证类型相容
  8.2 类型环境传递 = 属性文法求值（合成属性 + 继承属性/上下文）
  8.3 类型检查的边界 = 类型安全 ≠ 逻辑正确；类型系统越强，捕获越多，实现越复杂
```

**第7-8章在全书的角色**：它们是"分析输入"部分（第4-8章）的**真正内核与高潮**。第4-6章铺垫了 AST、Visitor、符号表这些"基础设施"；第7-8章则用这些设施，**完成了语义分析最核心的两件事——"为聚合/继承类型建模名字空间"（第7章）+"为整个程序做类型正确性证明"（第8章）**。

**贯穿两章的一条主线（我的总结）：**

> **Parr 在第7-8章真正想教你的，不是"如何实现哈希表/类型检查器"这些技术细节，而是"编程语言语义建模的核心秘密——用'作用域树（第7章）+ 类型标注（第8章）'这对组合，让编译器在不运行程序的情况下，就能'理解'程序的名字绑定和类型正确性。"**​ 到这两章结束，你的编译器才真正拥有了"静态语义理解能力"——它知道每个名字指谁、每个表达式是什么类型、哪些使用是合法的。**从这一刻起，后续第9-10章（解释执行）、第11-13章（代码生成）才有了"类型正确的 AST"这个可靠的输入基础。**

**一个给后续阅读的提示**：当你进入第9章"高级解释器"时，请带着两个问题去读——**"解释器执行时，还需要再做类型检查吗？（答案：静态类型语言不需要——第8章已保证类型正确；动态类型语言则在解释执行时做类型检查/分派）""解释器的'执行环境（Environment）'和第7章的'作用域树'有什么关系？（答案：执行环境是'作用域树'在运行时的投影——每个作用域对应一个运行时帧/环境，承载变量当前值）"**​ 想通这两个问题，第9章就不是新知识，而是第7-8章语义模型在"执行"维度的自然延伸。
