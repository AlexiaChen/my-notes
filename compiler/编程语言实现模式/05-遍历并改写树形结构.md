
# 第5章 遍历并改写树形结构 —— 读书笔记

> 一句话定位：第4章你学会了"构建 AST"——把解析出的句子投影成语义树。第5章紧接着回答一个更动手的问题——**"树建好了，怎么上去走一遍？怎么在走的过程中收集信息、做计算、甚至把树本身改掉？"**​ 这一章是全书从"建树"迈向"语义分析"的**第二座桥梁**，也是 Parr 把"造语言思维"从"数据结构"推进到"算法/遍历策略"的关键一跃。

四节是一条极其清晰的演进链：**先理解"树怎么走"（5.1）→ 再把"节点操作"封装成可复用的访问者（5.2）→ 进而让工具根据文法自动生成访问者骨架（5.3）→ 最后把"遍历"和"模式匹配"彻底解耦，进入项重写（term rewriting）的高阶境界（5.4）**。

## 5.1 遍历树以及访问顺序：前序、中序、后序的统一框架

### 树遍历的本质：在"发现节点"和"完成节点"之间插入动作

Parr 在这一节建立的第一个直觉是——**树的深度优先遍历（DFS）天然给了你两个"动作插入点"**：

- **discovery（发现节点）时**：相当于**前序遍历（preorder）**
    
- **finish（完成节点，即子节点都处理完）时**：相当于**后序遍历（postorder）**
    
- 如果是二叉树，在两个子节点之间插入动作，就是**中序遍历（inorder）**
    

换句话说，**"遍历顺序"不是一个固定套路，而是"你在 discovery 还是 finish 时刻挂动作"的自然结果**。深度优先的路径就是：`node discovery → 递归子节点 → finish node`。

### 为什么遍历顺序对语义分析至关重要

这不是学术细节，而是**语义分析正确性的命脉**：

- **符号表构建**必须在"遇到声明"时就做（discovery 阶段），这样后续表达式才能查到。
    
- **类型检查**必须在"子节点类型都算完"后才做（finish 阶段），因为父节点的类型依赖于子节点。
    
- **代码生成**中的"地址分配"往往是 discovery 阶段分配、"指令发射"是 finish 阶段发射——经典的"两遍遍历"。
    
- **常量折叠 / 简化**必须是后序——你得先把子表达式算成常量，才能判断 `x+0` 能不能化简。
    

**💡 我的洞见（第一性原理视角）：**

这一节藏着的深层规律是——**"遍历顺序 = 数据流方向"**。前序适合"自上而下传递上下文"（作用域入栈、选项继承），后序适合"自下而上聚合结果"（类型推导、值计算、代码生成）。**很多语义分析 bug 的根源，就是搞反了数据流方向、在不该挂动作的时刻挂了动作。**

工业实证：PHP-Parser 的 `NodeVisitor` 接口明确给出四个钩子——`beforeTraverse / enterNode / leaveNode / afterTraverse`，其中 `enterNode` 是前序、`leaveNode` 是后序。**几乎所有工业级 AST 遍历框架（Clang ASTVisitor、LLVM InstVisitor、Python ast.NodeVisitor、PHP-Parser）都遵循这个"前序 + 后序"的双钩子模型**——这不是巧合，而是 Parr 这一节所讲原理的工业共识。

### 嵌入式异构树遍历（Embedded Heterogeneous Tree Walker）

Parr 给出的第一个具体模式是**给每种节点类型增加对应的访问方法，递归调用**：

```
public void walk() {
    «preorder-action»
    left.walk();
    «inorder-action»
    right.walk();
    «postorder-action»
}
```

这就是**"嵌入式异构树遍历器"**——遍历逻辑直接写在节点类的方法里。优点是直观，缺点是**每加一种节点类型，所有遍历逻辑都要改**（经典的"表达式问题"）。

## 5.2 封装访问节点的代码：外部访问者模式登场

### 为什么要把"遍历"和"节点操作"分开

5.1 节的嵌入式遍历有个致命缺陷：**遍历算法和节点操作耦合在节点类内部**。每新增一种"操作"（如打印、类型检查、代码生成），就要修改所有节点类。

Parr 在 5.2 节引入**外部树访问者（External Tree Visitor）**——把"遍历逻辑"从节点类里抽出来，放到独立的 Visitor 类里：

```
节点类只保留：accept(visitor) 方法，委托给 visitor.visitXxx(this)
Visitor 类：对每个节点类型实现一个 visitXxx 方法
```

这就是 GoF Visitor 模式在树结构上的应用。**核心收益：新增操作 = 新增一个 Visitor 子类，节点类一行都不用改**。

### Visitor vs Listener：ANTLR 生态的两种现代形态

Parr 在书中讲的是经典的 Visitor 模式。但现代 ANTLR 4 把它发展成两种互补的形态，理解它们的差异是工程选型的关键：

|维度|Listener（监听器）|Visitor（访问者）|
|---|---|---|
|控制权|**被动**：`ParseTreeWalker` 自动遍历，回调你的 `enterX/exitX`|**主动**：你自己调 `visit(child)` 决定走不走、怎么走|
|返回值|通常 `void`，靠外部状态（栈/符号表）传递数据|方法可返回任意类型，适合递归计算|
|遍历顺序|固定深度优先（enter 前序 / exit 后序）|完全自定义——可前序、可后序、可跳过子树|
|适合场景|信息收集、副作用操作、语法检查|表达式求值、类型推断、代码生成、树转换|
|实现复杂度|低（声明式）|高（需手动管理递归）|

**一个典型的 Listener 栈式求值**：

```
class EvalListener extends ExprBaseListener {
    Stack<Integer> stack = new Stack<>();
    @Override public void exitAdd(ExprParser.AddContext ctx) {
        int right = stack.pop(), left = stack.pop();
        stack.push(left + right);
    }
    @Override public void exitInt(ExprParser.IntContext ctx) {
        stack.push(Integer.parseInt(ctx.INT().getText()));
    }
}
```

**一个典型的 Visitor 递归求值**：

```
class CalcVisitor extends ExprBaseVisitor<Integer> {
    @Override public Integer visitAdd(ExprParser.AddContext ctx) {
        int left = visit(ctx.left);
        int right = visit(ctx.right);
        return left + right;
    }
}
```

**💡 我的洞见（第一性原理 + 创新想法）：**

Listener 和 Visitor 的本质差异，可以用一个更深的视角来看——**"控制权在哪个维度上流动"**：

- **Listener 是'事件驱动'的**：你写的代码响应"树遍历框架"发出的事件。控制权在框架手里，你在它的节奏里填动作。**这类似于 SAX 解析 XML**——流式、低内存、但你必须自己维护上下文（栈/状态机）。
    
- **Visitor 是'主动递归'的**：控制权在你手里，你决定何时 `visit(child)`、是否要返回值、是否跳过某棵子树。**这类似于 DOM 遍历**——灵活、直观，但容易写出栈溢出或重复遍历的代码。
    

**由此我提炼一条"遍历范式选型原则"（创新想法，全书通用）：**

> **"如果你的操作是'收集信息'（建符号表、找所有函数调用、收集类型），用 Listener——声明式、低耦合、框架替你管理遍历；如果你的操作是'计算/生成'（求值、类型推导、代码生成、树转换），用 Visitor——你需要子节点的返回值来算父节点。"**

这条原则能让你在后续章节（符号表构建、类型检查、解释执行、代码生成）始终选对范式。Parr 自己在 ANTLR 4 时代也明确推荐这种分工。

工业实证：

- **Clang 的 RecursiveASTVisitor**：C++ 前端用 Visitor 做 AST 遍历，几乎所有静态分析工具（clang-tidy、clang-format）都基于它。
    
- **LLVM 的 InstVisitor**：`InstVisitor.h` 用 CRTP 模式对 LLVM IR 指令做 Visitor 分发，是常量折叠、优化 pass 的基础。
    
- **Vue.js 的编译器**：模板 AST 的转换（v-if、v-for、v-bind）每个都是一个 Visitor，由 `traverseNode` 统一调度。
    
- **Python ast 模块**：`ast.NodeVisitor` 做遍历收集，`ast.NodeTransformer` 专门做树转换。

## 5.3 根据文法自动生成访问者：让工具替你写样板代码

### 文法即访问者骨架的源头

Parr 在这一节的关键洞察是——**既然文法规则已经定义了"有哪些节点类型"，那么访问者接口就可以从文法自动生成**。这就是 ANTLR 的核心魔法之一。

以 ANTLR 4 为例，给定一个文法 `Expr.g4`，ANTLR 工具会自动生成：

1. **`ExprVisitor<T>` 接口**：为每个文法规则生成一个 `visitXxx(XxxContext ctx)` 方法
    
2. **`ExprBaseVisitor<T>` 基类**：提供默认实现（默认调 `visitChildren`，即遍历所有子节点）
    

你只需要继承 `ExprBaseVisitor`，**只 override 你关心的规则**即可。没 override 的规则自动沿用默认遍历行为。

### 自动生成的威力：从"写遍历器"到"填访问方法"

对比 5.2 节的手写 Visitor，自动生成带来的质变是：

- **零样板代码**：不用手动为每个节点类写 `accept` 方法和对应的 `visitXxx` 方法。
    
- **类型安全**：生成的 `XxxContext` 类精确反映文法结构，你能直接 `ctx.ID()`、`ctx.expr(0)` 拿到类型正确的子节点。
    
- **与文法同步**：文法改了，重新生成 Visitor 接口，编译器会强制你处理新增的节点类型——**不会漏**。
    

**💡 我的洞见（第一性原理视角）：**

这一节揭示了一个被很多教材忽略、但对"语言工程"至关重要的原理——**"语言的结构定义（文法）是所有下游工具的'单一事实来源'（Single Source of Truth）"**。Visitor 接口、Listener 接口、AST 节点类、甚至 IDE 的语法高亮，都该从文法自动派生。

这背后的第一性原理是**"Don't Repeat Yourself"**——凡是能从文法推导出的东西，就不该手写第二遍。**ANTLR 的强大，不在于它的解析算法多牛，而在于它把"文法"这个单一事实来源，系统地、可复用地投影到了词法分析器、语法分析器、Visitor/Listener、甚至 IDE 插件等所有下游产物**。

工业实证：

- **ANTLR 4 的 Java/Python/C#/C++/Go/JS 多目标代码生成**：同一份 `.g4` 文件，可生成 6+ 种语言的 Parser + Visitor + Listener。
    
- **LLVM 的 TableGen**：类似理念——用一份声明式描述，自动生成指令选择器、汇编器、反汇编器等多份代码。
    
- **Protocol Buffers / Thrift**：IDL 即单一事实来源，自动生成多语言的序列化/反序列化代码。
    

这些工业系统的共同哲学，正是 Parr 在 5.3 节点出的"从文法自动生成访问者"的思想延伸。

## 5.4 将遍历与匹配解耦：进入"项重写"的高阶境界

### 遍历与匹配的分离

5.1~5.3 节讲的都是"显式遍历整棵树 + 在每个节点做动作"。5.4 节 Parr 抛出了更厉害的思路——**"能不能不遍历整棵树，而是直接说'我要找所有满足 X 模式的子树，对它们做 Y 变换'？"**

这就是**项重写（Term Rewriting）/ 树模式匹配（Tree Pattern Matching）**​ 的核心思想。**遍历是手段，匹配才是意图**。

ANTLR 3 的做法是在 tree grammar 里写带模式匹配的规则：

```
zeroX : ^('*' a=INT b=INT{$a.int==0}?) -> $a ;  // 0*x -> 0
xZero : ^('*' a=INT b=INT{$b.int==0}?) -> $b ;  // x*0 -> 0
```

其中 `^(...)` 是树模式，`$a.int==0` 是**语法谓词（semantic predicate）**，`->` 后面是重写结果。

配合**遍历时机**的控制：

- **topdown 规则**：在 discovery 节点时尝试匹配（前序）
    
- **bottomup 规则**：在 finish 节点时尝试匹配（后序）
    

```
topdown  : scalarVectorMult ;
bottomup : zeroX | xZero ;
```

ANTLR 采用深度优先搜寻，discovery 一个 node 时执行 topdown 规则，finish 一个 node 时执行 bottomup 规则。

### 多次遍历的必要性

有些重写需要**多遍（multi-pass）**才能完成。Parr 举的例子：`3+3` 要重写成 `3<<1`，需要两步：

1. `3+3` → `3 * 2`（常量加法折叠）
    
2. `3 * 2` → `3<<1`（乘法转移位）
    

**每一步都是一次独立的树遍历 + 模式匹配**。这就是为什么工业级优化器（如 LLVM）要做 **多个 Pass 串联**——每个 Pass 就是一遍"遍历 + 模式匹配 + 重写"。

### 现代演进：ANTLR 4 的树模式匹配

Parr 本人在 ANTLR 4 时代进一步把"遍历与匹配解耦"的思想系统化——引入 **`SyntaxPattern` + `XPath` 风格的树查询**：

```
SyntaxPattern pattern = new SyntaxPattern("ID = expr ;", parser.getATN());
for (ParseTreeMatch ass : pattern.findall(tree)) {
    System.out.println(ass.get("ID").getText());  // 直接拿到匹配到的子节点
}
```

还可以结合 XPath 限制匹配范围：

```
for (ParseTree t : XPath.findAll(tree, "/class/assignment", parser)) {
    ParseTreeMatch ass = pattern.match(t);
    // 处理匹配结果
}
```

这套机制的意义是——**你不再需要为了"找某种模式的子树"而写一个完整的 Listener/Visitor**。直接声明模式，工具帮你找。这是"遍历与匹配解耦"的极致形态。

### 三种"改写"层级的区分（重要！）

结合现代工业实践，树/IR 的"改写"其实有三个不同层级，很多人混淆：

|层级|改写对象|典型手段|工业实例|
|---|---|---|---|
|**源码文本级**​|原始字符流|`TokenStreamRewriter` 替换 token|ANTLR 4 的迁移工具：把 `Text(value="x")` 改成 `MyText(val="x")`|
|**解析树级**​|Parse Tree (CST)|Listener 中 `removeLastChild()` / 添加子节点|ANTLR 4 的 `ParserRuleContext` 操作|
|**IR/AST 级**​|语义树|Visitor 返回新节点 / NodeTransformer|Python `ast.NodeTransformer`、PHP-Parser `leaveNode` 返回新节点|

**每种层级有不同的"安全性"考量**：

- **源码文本级**：最安全（不动树结构），适合代码格式化、迁移、重构工具。
    
- **解析树级**：中等风险，因为 Parse Tree 与文法紧密耦合，随意改可能破坏文法一致性。
    
- **IR/AST 级**：最灵活，但需小心——如在 `enterNode` 中替换节点可能导致无限递归（PHP-Parser 文档明确警告的这个坑）。Python 的解决方案是用 `ast.NodeTransformer`，约定 `visit_Xxx` 方法的返回值语义：返回原节点=不变、返回新节点=替换、返回 `None`=删除、返回节点列表=展开。
    

**💡 我的洞见（第一性原理 + 创新想法）：**

5.4 节（结合现代工业实践）揭示了一个极具深度的工程哲学——**"遍历是手段，模式匹配才是意图；而意图的表达方式，决定了你的语言工具链的抽象层级。"**

我把它提炼为**"树处理抽象层级谱系"**：

```
Level 0: 手写递归遍历 + if-else 判断节点类型（最底层、最冗长）
Level 1: Visitor/Listener 模式（关注点分离，但仍需显式遍历）
Level 2: 树模式匹配 + 重写规则（声明式："匹配 X → 替换为 Y"）
Level 3: 策略（Strategy）/ 优化 Pass 框架（"对整棵树应用一组重写规则"）
```

**ANTLR 3 处于 Level 2，ANTLR 4 的 SyntaxPattern 把 Level 2 做得更优雅，LLVM Pass 框架则是 Level 3 的典范**。

**这条谱系给语言实现者的创新启示**：

> **"当你设计一门语言的优化/转换管线时，尽量不要停留在 Level 0/1——那是教科书示例的级别。尽可能上升到 Level 2/3：用声明式的模式匹配表达'什么时候做什么变换'，把'遍历'这件事交给框架。这样你的优化规则可以独立编写、独立测试、独立组合——这正是 LLVM 拥有 300+ 优化 Pass 却能保持可维护性的根本原因。"**

工业实证：

- **LLVM Pass 框架**：300+ 个优化 Pass，每个 Pass 就是一个"遍历 + 模式匹配 + 重写"的独立模块，可任意组合。
    
- **PHP-Parser 的 NodeVisitor**：用 `enterNode/leaveNode` 双钩子 + 返回值语义，实现了安全的 AST 转换。
    
- **Python ast.NodeTransformer**：声明式树转换的典范，被 Black、flake8、mypy 等无数工具使用。
    
- **Vue.js 模板编译器**：每个编译阶段（`transformIf`、`transformFor`、`transformBind`）都是一个独立的 Visitor，由 `traverseNode` 统一调度。

## 章节联系与全书定位

把四小节串成一条"遍历与改写"的演进主线：

```
5.1 遍历树以及访问顺序
   → 深度优先遍历天然提供 discovery/finish 两个动作插入点
   → 前序/中序/后序 = 数据流方向
        ↓
5.2 封装访问节点的代码
   → 外部 Visitor 模式：遍历逻辑与节点类解耦
   → Listener（被动/事件驱动）vs Visitor（主动/递归控制）
        ↓

   → 文法是单一事实来源，Visitor 接口从文法自动派生
   → 零样板、类型安全、与文法同步
        ↓
5.4 将遍历与匹配解耦
   → 项重写 / 树模式匹配：声明式"匹配 X → 替换为 Y"
   → 多遍遍历、SyntaxPattern、三个改写层级
```

**第5章在全书的角色**：它是"分析输入"部分的核心章节，承上（第4章建的 AST）启下（第6章符号表、第7章类型检查、第9-10章解释器、第11-13章代码生成）。**后续所有"语义分析"章节的"操作手法"，本质都是第5章讲的遍历 + 访问者 + 模式匹配的组合应用**。

**贯穿全章的一条主线（我的总结）：**

> **Parr 在第5章真正想教你的，不是"如何用 Visitor 模式遍历树"这个技术招式，而是"语言处理的根本手法谱系"——从最原始的手写遍历，到 Visitor/Listener 关注点分离，到文法驱动的自动生成，再到声明式的项重写。每一级抽象都让你离"业务意图"更近一步，离"遍历细节"更远一步。**​ 这是软件工程"关注点分离"和"声明式优于命令式"两大第一性原理在语言处理领域的集中体现。

**一个给后续阅读的提示**：当你进入第6章"符号表"时，请带着一个问题去读——**"符号表的构建，本质上就是第5章讲的 Listener 模式的一次具体应用：在 discovery 阶段遇到声明就 `define`，在表达式中查 `resolve`。那么，作用域链（scope chain）该如何用 Visitor/Listener 的状态栈来自然表达？"**​ 想通这个问题，第6章的符号表就不是孤立的知识，而是第5章遍历范式的一个优雅实例。
