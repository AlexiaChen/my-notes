

# 第4章 从语法树构建中间表示 —— 读书笔记

## 4.1 为什么要构建树：解析树 ≠ 你要的 IR

### 两个关键区分必须先钉死

Parr 在这一节要建立的第一个、也是最重要的直觉是——**"Parser 自动生成的解析树（Parse Tree / CST，具体语法树），和你真正想要的'中间表示（IR）树'，是两回事。"**

|维度|解析树 / CST（具体语法树）|AST（抽象语法树）|
|---|---|---|
|节点粒度|**细**：含所有 token + 所有文法规则节点，包括括号、分号等"语法噪音"|**粗**：只保留**语义相关**的节点，噪音被剥离|
|与文法关系|**一一对应**文法产生式结构|**重新设计**，按语义概念组织，可与文法不同构|
|用途|调试文法、错误恢复、IDE 增量分析|**语义分析、类型检查、优化、代码生成**的主战场|
|节点类型|同质（规则名/词法名）|通常**异构**（每种语义构造一个节点类）|

**💡 我的洞见（第一性原理视角）：**

为什么非要多此一举建一棵新树？第一性原理的回答是——**"文本是给人类写的（允许冗余、允许噪音），而语义分析和代码生成需要的是'纯净的语义结构'。"**​ 解析树里那些括号、分号、关键字 `if`/`then`，对人类来说是"语法可读性"的必要成分，对机器做语义分析时却是**纯粹的干扰信息**。

> **建 AST 的本质，是一次"从语法表示到语义表示的投影（projection）"——把文法强加的线性化结构，还原成语言设计者真正关心的"语义构造"的树形结构。**

工业实证：GCC/Clang 的 AST（GENERIC/GIMPLE、Clang AST）都**不是解析树**，而是精心设计的中间表示；Java 编译器的 AST 也剥离了分号、括号等噪音节点。**所有工业级编译器都在 Parser 之后、语义分析之前，做一次"解析树 → AST"的翻译**——这本身就是这一节论点的最强背书。

### 什么时候"可以不建树"

Parr 也诚实指出：**并非所有语言应用都需要显式建 AST**。这恰恰是他的实用主义风格：

- **配置读取器 / 简单数据读取器**：输入小、结构浅，Parser 边解析边执行/填充对象即可，**多建一棵树反而多余**。
    
- **一次性的源码到源码翻译**：若目标代码可"边解析边输出"（如 wiki→HTML 的简单转换），可用**语法导向翻译（Syntax-Directed Translation）**，不落 AST。
    
- **必须建树的场景**：需要做**类型检查、语义分析、优化、多次遍历、增量编译、IDE 重构/补全**的语言应用——这些都要在"与源码解耦的语义结构"上反复操作，AST 是刚需。
    

**💡 我的洞见（创新想法）：**

我愿意把 Parr 这个"要不要建树"的讨论，提炼成一个**"AST 必要性决策矩阵"**（供你做语言/DSL 设计时直接套用）：

|语言应用类型|是否需要显式 AST|理由|
|---|---|---|
|配置/数据读取器|❌ 不需要|输入浅、一次性消费|
|简单 Translator（wiki→HTML）|⚠️ 可选|可语法导向翻译，边解析边输出|
|解释器 / 计算器|✅ 需要（轻量）|需遍历求值，AST 即执行结构|
|带类型检查/优化的编译器|✅ 必须|多次遍历 + 语义分析离不开 AST|
|IDE / 重构工具|✅ 必须|增量分析、符号查询依赖 AST|

**这条矩阵的实践价值**：当你接到"我要做一个 DSL"的需求时，先判断它落在哪一行——**这直接决定了你是否需要投入精力设计 AST 节点类型体系**。很多 DSL 项目过度设计（强行建了一棵没人遍历的 AST），或设计不足（该建 AST 却用字符串拼接做翻译，后期无法扩展），根源都是没想清楚这个问题。

## 4.2 构建抽象语法树：设计节点 + 两种遍历范式

### AST 节点设计的核心原则

构建 AST 的第一步是**为每种语义构造设计对应的节点类**。Parr 强调几个设计要点：

1. **异构节点**：每种语言构造（赋值、if、while、二元运算、变量引用……）对应一个**独立的节点子类**（如 `AssignNode`、`IfNode`、`BinOpNode`、`VarNode`），而非用统一的"带类型的节点"凑合。
    
2. **节点只存"语义必要"的信息**：`IfNode` 存 `condition / thenBranch / elseBranch` 三个子节点引用；**不存 `if` 关键字 token、不存括号**——这些是语法噪音。
    
3. **子节点用引用链接**：AST 是**有向无环图（DAG）结构**（严格说是树，共享子表达式时可成 DAG），通过父子/兄弟引用表达嵌套。
    

一个最小 AST 节点体系示例（Java 风格）：

```
abstract class ASTNode { }
class AssignNode extends ASTNode {
    VarNode lhs; ASTNode rhs;
}
class BinOpNode extends ASTNode {
    ASTNode left; ASTNode right; String op;
}
class IfNode extends ASTNode {
    ASTNode cond; ASTNode thenBranch; ASTNode elseBranch;
}
```

### 两种遍历 AST 的范式：Visitor vs Listener（关键！）

建好树之后，所有后续处理（类型检查、解释执行、代码生成）都是**对 AST 的遍历**。Parr 在这一节（结合 ANTLR 的工具链）奠定两种经典遍历范式，这也是全书后续所有"语义分析章节"的操作基础：

|维度|Visitor（访问者模式）|Listener（监听器模式）|
|---|---|---|
|控制权|**主动**：你调用 `visit(node)` 决定下一步遍历谁、是否继续|**被动**：框架自动按遍历序回调你的 `enterX()/exitX()`|
|能否引导遍历|✅ 可以（选择性访问子节点、提前返回）|❌ 不能（遍历路径由框架定）|
|适合场景|**解释执行、代码生成**（需主动控制执行/生成顺序）|**类型检查、符号表构建**（被动收集信息即可）|
|ANTLR 对应|`ParseTreeVisitor<T>` + `visit()`|`ParseTreeListener` + `enter/exit`|

**💡 我的洞见（第一性原理 + 创新想法）：**

这一节（结合 ANTLR 生态）揭示了一个被很多教材轻描淡写、却对工程架构影响巨大的洞见——**"遍历 AST 的'控制权归属'，决定了你的语义分析模块的 shape。"**

- **Listener 是"数据驱动"的**：你写一堆 `enterX/exitX` 回调，框架推着你走。这天然适合**"信息收集型"任务**（建符号表、收集类型信息、找引用）——你只管在节点进出时记笔记，不用操心遍历顺序。
    
- **Visitor 是"控制反转回来"的**：你主动 `visit(child)` 决定先访谁、要不要访。这天然适合**"决策型/生成型"任务**（解释执行、递归代码生成）——你需要掌控"先算左子树还是右子树""是否要为了短路求值提前返回"。
    

**由此我提炼一条"遍历范式选型原则"（创新想法，全书通用）：**

> **"信息收集用 Listener，决策生成为 Visitor。"**​ 符号表构建、类型收集 → Listener；解释器求值、目标代码生成 → Visitor。这条原则能让你在后续第5章（遍历/改写树）、第9-10章（解释器）、第11-13章（代码生成）里，始终选对遍历范式。

工业对照：

- **Clang 的 RecursiveASTVisitor**：C++ 前端用 Visitor 模式遍历 Clang AST，做静态分析、重构、代码生成。
    
- **ANTLR 4 的 ParseTreeWalker + Listener / Visitor**：现代 ANTLR 应用（如 Twitter Search 查询解析、各类 DSL）几乎都走"Parser → Parse Tree → Listener/Visitor 做语义分析"的标准流水线。
    
- **LLVM IR 的遍历**：虽然 LLVM IR 是 SSA 形式的线性指令序列（非树），但其 `FunctionPass`/`ModulePass` 遍历机制，本质也是"对 IR 做 Visitor 式遍历"的变体。

## 4.3 简要介绍 ANTLR：把前两章的工具箱系统化

这一节 Parr 把前面散落的 ANTLR 知识系统化，给出一个**最小可工作的 ANTLR 工作流**。核心要点：

1. **文法即 DSL**：ANTLR 文法（`.g4`）本身是一门"用来定义语言的 DSL"——你写一个 `grammar X;`，ANTLR 工具据此生成 `XLexer` + `XParser` + `XVisitor` + `XListener`。
    
2. **统一文法文件**：词法规则（大写开头，如 `ID`、`INT`、`WS`）和语法规则（小写开头，如 `expr`、`stat`）写在同一个 `.g4` 里，ANTLR 自动拆分 Lexer / Parser。
    
3. **动作与属性**：ANTLR 4 鼓励**用 Listener/Visitor 代替文法内嵌 action**（与本书基于 ANTLR 3、鼓励嵌 action 形成对比——这是版本演进的关键差异，务必留意）。
    

一个最小 ANTLR 4 文法 + 驱动代码骨架：

```
// Expr.g4
grammar Expr;
prog : stat+ ;
stat : expr ';'                # printExpr
     | ID '=' expr ';'         # assign
     ;
expr : expr ('*'|'/') expr     # mulDiv
     | expr ('+'|'-') expr     # addSub
     | INT                      # int
     | ID                       # var
     | '(' expr ')'             # parens
     ;
ID   : [a-zA-Z]+ ;
INT  : [0-9]+ ;
WS   : [ \t\r\n]+ -> skip ;
```

```
// 驱动
ExprLexer lexer = new ExprLexer(CharStreams.fromString("x=3; x+4;"));
CommonTokenStream tokens = new CommonTokenStream(lexer);
ExprParser parser = new ExprParser(tokens);
ParseTree tree = parser.prog();   // 得到解析树
// 后续：new ParseTreeWalker().walk(myListener, tree); 或 visitor.visit(tree);
```

**⚠️ 版本坑再次提醒（本书价值 vs 局限）：**

本书示例基于 **ANTLR 3**（LL(k)、鼓励文法内嵌 action、手动消除左递归）；工业主流是 **ANTLR 4**（ALL(*)、Listener/Visitor 解耦 action、自动处理直接左递归）。**学第4章时，建议"用 ANTLR 4 重写书中示例"**——既掌握 Parr 的"造语言思维"，又用上现代工具。

## 4.4 使用 ANTLR 文法构建 AST：从解析树到 AST 的两种路线

这是全章的"收口"+"动手"小节——**如何用 ANTLR 文法，让工具帮你自动产出 AST**。

### 路线一：利用 ANTLR 的"规则返回值与树构造动作"（本书 ANTLR 3 风格）

ANTLR 3 允许在文法规则里**嵌 action**，通过 `^`（根节点标记）和 `!`（子树省略标记）控制解析树结构，并用规则返回值把构造好的 AST 节点"向上传递"：

```
// ANTLR 3 风格（示意）
expr returns [ASTNode n]
    : a=term      {$n = $a.n;}
      ( '+' b=term {$n = new AddNode($n, $b.n);} )*
    ;
term returns [ASTNode n]
    : INT          {$n = new IntNode(Integer.parseInt($INT.text));}
    | ID           {$n = new VarNode($ID.text);}
    ;
```

思路：**每条规则的返回值就是该规则对应的 AST 节点**；规则体内的 action 负责 `new` 出节点、拼接子节点。这样 Parser 解析完毕，根规则的返回值就是整棵 AST 的根。

### 路线二：ANTLR 4 + Listener/Visitor 手动构建 AST（现代推荐）

ANTLR 4 不鼓励文法内嵌 action，推荐**先让 ANTLR 生成标准 Parse Tree，再用 Listener/Visitor 遍历 Parse Tree、手动构造 AST**：

```
public class BuildASTListener extends ExprBaseListener {
    private ASTNode result;
    private Stack<ASTNode> stack = new Stack<>();

    @Override public void exitAssign(ExprParser.AssignContext ctx) {
        ASTNode rhs = stack.pop(); VarNode lhs = new VarNode(ctx.ID().getText());
        stack.push(new AssignNode(lhs, rhs));
    }
    @Override public void exitAddSub(ExprParser.AddSubContext ctx) {
        ASTNode right = stack.pop(), left = stack.pop();
        stack.push(new BinOpNode(left, right, ctx.getChild(1).getText()));
    }
    @Override public void exitInt(ExprParser.IntContext ctx) {
        stack.push(new IntNode(Integer.parseInt(ctx.INT().getText())));
    }
    // ... 其他 exitX 方法
}
```

**两种路线对比与选型**：

|维度|路线一：文法内嵌 action（ANTLR 3）|路线二：Listener/Visitor 建 AST（ANTLR 4）|
|---|---|---|
|关注点分离|❌ 文法 + 建树逻辑耦合|✅ 文法纯声明，建树逻辑独立|
|可测试性|差（建树逻辑散落在文法）|好（Listener 可独立单测）|
|工具支持|ANTLR 3|ANTLR 4（主流）|
|适合场景|快速原型、教学演示|工业级项目、需要维护/扩展|

**💡 我的洞见（第一性原理 + 创新想法）：**

这一节（结合 ANTLR 3→4 的演进）藏着一个极具工程哲学意味的洞察——**"建 AST 的逻辑，到底该'寄生'在文法里，还是'独立'于文法之外？"**

ANTLR 3→4 的演进方向（从"文法内嵌 action"到"Listener/Visitor 解耦"）给出的答案是：**"文法只管'定义语言结构'，建 AST 是'语义侧'的事，应该独立出来。"**​ 这背后是**"关注点分离（Separation of Concerns）"**​ 这一第一性原理在语言前端的具体应用——

> **解析（Parser）的职责是"判断句子是否合法 + 给出结构"；构建 AST 的职责是"把解析出的结构投影成语义表示"。这两件事一个偏语法、一个偏语义，耦合在一起会让两者都难以演化。**

**由此我提出一个"AST 构建架构"的创新建议（供你做语言项目时参考）：**

> **永远把"文法文件"和"AST 构建代码"分开放**。文法文件保持纯声明（只定义 `grammar`），AST 节点类 + Listener/Visitor 建树逻辑单独成模块。**这样你的文法可以独立测试（用 `grun ... -tree` 验结构），AST 构建逻辑也可以独立单测（构造 Parse Tree 片段 → 验 AST 节点），两者通过"Parse Tree"这个稳定接口解耦。**​ 这正是现代 ANTLR 4 应用（及 Clang/LLVM 等工业前端）的标准架构。

工业对照：

- **Clang/LLVM**：Clang 的 Parser 产出 Clang AST，LLVM 后端消费 LLVM IR——**Parser 和 IR 构建严格分离**，通过 AST 这个接口解耦。
    
- **ANTLR 4 生态项目**：几乎所有现代 ANTLR 4 应用（DSL 实现、查询语言、配置语言）都采用"纯 `.g4` + 独立 Visitor/Listener"的架构，正是路线二的工业落地。
