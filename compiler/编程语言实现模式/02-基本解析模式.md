
# 第2章 基本解析模式 —— 读书笔记

> 一句话定位：如果说第1章给你的是"语言应用全景地图"，那第2章就是**你亲手拿起工具、在地图上踩下的第一个脚印**。它回答的是一个看似朴素、实则决定全书走向的问题——**"计算机到底是怎么把一串扁平的文本，认出它是不是一个合法句子的？"**

Parr 在这一章连抛四个子话题，层层递进：**先教你"看结构"（2.1）→ 再教你"手写一个识别器"（2.2）→ 然后告诉你"其实可以用文法DSL让工具帮你生成"（2.3）→ 最后把视角下沉到字符层，讲"词法单元（token）是怎么切出来的"（2.4）**。这四个小节不是并列，而是一条完整的认知链。

## 2.1 识别式子的结构：解析的本质是"二维化"

开篇那句被反复引用的定义值得抄在笔记本扉页：

> **"The act of recognizing a phrase by computer is called parsing."**（计算机识别一个短语的动作，就叫解析。）

而一句更根本的话是：

> **"A language is just a set of valid sentences."**（语言，不过就是"合法句子"的集合。）

这两句话合在一起，才是这一节的灵魂。**解析的本质任务，是把一个"一维的、扁平的 token 序列"，还原（或验证）成一个"二维的、有层次的短语结构"——也就是解析树（parse tree）**。

为什么是"二维化"？因为自然语言/编程语言写出来都是一行行的字符流（一维），但它承载的"主谓宾""表达式嵌套""if 套 if"都是树形结构（二维）。**解析器做的，就是根据文法规则，为这串 token 找到一棵合法的派生树。**

**💡 我的洞见（第一性原理视角）：**

这一节真正想建立的直觉是——**"结构"是被人写出来的文本隐含携带的，解析器的全部工作就是"把这个隐含结构显式化"**。Parr 让你先学会"肉眼识别短语结构"（比如看出 `if (x) stmt` 的嵌套），再动手写代码，这个顺序是刻意的：**先建立"结构感"，再谈算法**。很多初学者一上来就啃 LL(1)/First-Follow 集，恰恰是本末倒置——他们没搞懂"我们到底在识别什么"，就急着学"怎么识别"。

工程上，这解释了为什么**几乎所有语言工具的调试第一步都是"打印解析树"**：ANTLR 的 `grun ... -tree` 或 `-gui` 会直接把输入文本对应的 LISP 风格解析树画出来。当你不确定自己的文法对不对时，先看树对不对——这是 Parr 系工具最实用的心智模型。

## 2.2 构建递归下降语法解析器：手写派的"内功心法"

这是全章最"硬核"的一节，也是 Parr 作为 ANTLR 作者却**先教你手写、再讲生成器**的用意所在——**你必须先懂手写递归下降，才算真正理解解析器**。

核心思想极其纯粹，纯到让人感动：

> **"文法中的每一个产生式（production），直接对应代码里的一个函数；函数之间互相递归调用，顺着 token 流一路向下探索。"**

- **"Recursive（递归）"**：函数可能调用自身（对应解析树里的递归嵌套）；
    
- **"Descent（下降）"**：从解析树的根（起始符号）出发，自顶向下朝叶子（token）方向"降"下去。
    

**LL(1) 这个名字也在这里被正式拆解**：第一个 L = 从左到右读输入；第二个 L = 按从左到右的顺序展开子节点。

Parr 在本节给出了"文法 → 手写递归下降代码"的系统映射规则（这是本章最值得背下来的"配方"）：

|文法构造|手写代码形态|
|---|---|
|终结符 T|`match(T)`（若当前向前看 token == T 则消费，否则抛异常）|
|非终结符 A|调用函数 `A()`|
|多选一 `alt1 \\| alt2 \\| ...`|`if / switch` 按向前看符号分发|
|`(T)?` 可选|`if (向前看是T) match(T);`|
|`(T)+` 一个或多个|`do { match(T); } while(向前看是T);`|
|`(T)*` 零个或多个|`while(向前看是T) match(T);`|

**两个致命约束（务必记住）：**

1. **不能直接左递归**：`r : r X ;` 会翻译成 `void r() { r(); match(X); }`——函数一进来就无限自调用，栈立即爆掉。必须改写成右递归或迭代形式（`A → βA'`, `A' → αA' | ε`）。
    
2. **同一非终结符的各产生式 Predict 集必须互不相交**：否则解析器在分发时会出现"该选哪条"的二义冲突。这就是 LL(1) 文法的定义——**Predict 集两两交集为空**。
    

**💡 我的洞见（创新想法）：**

这里藏着一个极容易被忽略、却对工程决策至关重要的洞察——**"手写递归下降"和"用生成器"之争，本质不是技术问题，而是"控制权 vs 开发效率"的取舍问题**。我把业界真实证据摆在一起，你会看到一条清晰的规律：

- **手写派（要控制权）**：Clang 的 C++ 前端、GCC 核心、javac、MLIR 的 `.mlir` 文本解析器，全部是手写递归下降。GCC 甚至**主动从生成器切换到手写**，收益是"更好的错误处理、对语言扩展更友好的支持、解析与语义分析更干净的分离"。手写的最大杀手锏是**错误恢复（Error Recovery）**——人类写错代码时（少个括号），手写代码能精准报"第几行第几列缺什么"，甚至智能跳过错误行继续解析；而生成器一旦出错，往往只吐一句晦涩的 `Syntax Error: Unexpected Token`。
    
- **生成器派（要效率）**：Hive、Pig、Hibernate HQL、Oracle SQL Developer、Twitter Search 等 DSL/查询语言，用 ANTLR 快速落地。适合"文法相对稳定、追求快速原型、团队不愿维护大量手写代码"的场景。
    

**由此我提炼一条选型原则（供你全书参照）：**

> **"如果你的语言是给人'写代码'用的（通用语言/大型DSL），优先手写递归下降——因为你欠用户好的报错；如果你的语言是'配置/查询/数据交换'用的（输入由程序或熟练用户产出、报错要求低），用 ANTLR 类生成器——开发效率碾压。"**

这也解释了为什么 Parr 作为 ANTLR 作者仍花整整一节教你手写：**他懂一个道理——只有亲手写过递归下降，你才能真正"看见"生成器替你省掉了什么，从而在两者间做出有依据的选择，而不是盲从工具。**

## 2.3 使用文法DSL来构建语法解析器：让工具替你干活

理解了手写之后，Parr 才引入文法 DSL 和解析器生成器（parser generator）的概念：

> **"有专门描述语言的 DSL，用它写的'程序'叫文法（grammar）；把文法翻译成解析器的工具，叫解析器生成器（parser generator）。"**​ 文法既是"函数规格说明"，也是"可执行程序"。

映射关系非常干净：**解析树里的子结构 ↔ 解析器里的函数 ↔ 文法里的规则**，三者一一对应。你写一个 `.g4` 文件，ANTLR 就帮你生成 `Lexer.java` + `Parser.java` + `Listener/Visitor` 一套脚手架。

一个最小的 ANTLR4 文法示例（Hello）：

```
grammar Hello;
r   : 'hello' ID ;
ID  : [a-z]+ ;
WS  : [ \t\r\n]+ -> skip ;
```

**⚠️ 一个必须提醒你的"版本坑"（本书价值所在，也是它的局限）：**

本书示例基于 **ANTLR 3**，而当前工业主流是 **ANTLR 4**。两者的关键差异你要心里有数：

|维度|ANTLR 3（本书所用）|ANTLR 4（现代主流）|
|---|---|---|
|算法|LL(k)，需手动消除左递归|__LL(_)，几乎接受任意文法，含左递归_*​|
|动作嵌入|鼓励在文法里写 action|**不鼓励**，改用 Listener/Visitor|
|错误处理|生成代码内处理|通过 `ErrorStrategy` 解耦|

**💡 我的洞见：**

这一节最值得品的，是 Parr 对"文法即可执行 DSL"这个定位。**这其实是一种"元语言"思维——用一门语言（文法DSL）去定义另一门语言（你的DSL/查询语言）**。当你写 `.g4` 时，你不是在"配置"什么，你是在"编程"——只是这门语言的运行时是 ANTLR 工具本身。理解到这一层，你就不会再把 ANTLR 当成一个黑箱工具，而会把它当成一门"用来造语言的编程语言"来学。这也是为什么 ANTLR 官方把这本书和《The Definitive ANTLR 4 Reference》并列为学习资料——前者教你"造语言的思维模式"，后者教你"ANTLR 这个工具的具体用法"，两者互补而非替代。

## 2.4 词法单元和句子：把视角下沉到字符层

最后一节完成"从字符到 token 再到句子"的全链路闭环。两个核心概念：

- **词法分析器（Lexer / Scanner / Tokenizer）**：**"以字符流为输入、识别词法模式、产出 token 流"**​ 的识别器。每个 token 有两个核心属性——**token 类型（符号类别）**​ 和 **对应的文本**。
    
- **句子（sentence）**：由 token 按文法规则组合而成的合法序列；**语言 = 合法句子的集合**。
    

关键洞察是——**词法分析和语法分析的结构几乎完全相同，唯一区别是输入符号的层级不同**（字符 vs token）：

> **"Lexer 和 Parser 的设计模式几乎一模一样，唯一区别在于它们输入符号的类型——字符或 token。"**

这也解释了为什么 ANTLR 里**词法规则（大写开头，如 `ID`、`INT`、`WS`）和语法规则（小写开头，如 `expr`、`stat`）写在同一个 `.g4` 文件里**，且都遵循类似的模式匹配语法。`WS : [...] -> skip ;` 这类规则告诉工具"匹配后直接丢弃"，正是词法层处理空白/注释的标准做法。

**💡 我的洞见（第一性原理 + 工业落地）：**

这一节揭示了一个被很多教材拆成两门课（"词法分析""语法分析"）来讲、其实**底层同构**的事实。**从第一性原理看：词法和语法都是在做"模式识别 + 结构显式化"，只是识别的"原子单元"差了一层**。理解这种同构性，你就能用一个统一的思维框架去处理字符级和 token 级的问题，而不是把它们当成两套孤立技术。

工业上，这直接对应 ANTLR 的**"统一文法文件"实践**：你把词法（`lexer grammar`）和语法（`parser grammar`）规则写在一起（或分包），ANTLR 先跑 Lexer 把字符流切成 token，再跑 Parser 把 token 流构造成树。一个典型的拆分写法：

```
// arithmeticlexer.g4（词法）
lexer grammar arithmeticlexer;
WS     : [ \t\n]+ -> skip ;
NUMBER : ('0'..'9')+ ('.' ('0'..'9')+)? ;
ADD    : '+' ;  SUB : '-' ;  MUL : '*' ;  DIV : '/' ;

// arithmeticparser.g4（语法）
parser grammar arithmeticparser;
options { tokenVocab = arithmeticlexer; }
expr     : NUMBER operation NUMBER ;
operation: (ADD | SUB | MUL | DIV) ;
```

这种"先 lex 后 parse"的两段式流水线，正是第1章那条"输入 → 识别 → 构建IR"总流水线在解析阶段的具体落地。

## 章节联系与全书定位

把四小节串成一条线，你会看到 Parr 的良苦用心：

```
2.1 识别结构（建立"结构感"直觉）
   ↓
2.2 手写递归下降（掌握解析器的内功，理解控制权价值）
   ↓
2.3 文法DSL + 生成器（用工具提效，理解"文法即元语言"）
   ↓
2.4 词法单元与句子（下沉到字符层，完成"字符→token→句子"全链路）
```

**第2章在全书的角色**：它是"解析器工具箱"的第一层（基本模式），为第3章"增强解析模式"（LL(k)、回溯、谓词、记忆化等更强解析器）奠基。**没有第2章建立的"手写递归下降 + LL(1) 约束"这两块基石，第3章讲的那些"更强的解析策略"你就无法判断它们到底在解决什么问题。**

**贯穿全章的一条主线（我的总结）**：

> **Parr 始终在教你一件事——"解析器的全部秘密，就是'用函数的递归调用，去模拟文法的递归结构'"。**​ 手写也好、生成器也好、词法也好、语法也好，都只是这条主线的不同投影。抓住这一条，你就抓住了第2章，乃至整本书"造语言"思维的骨架。

一个给后续阅读的提示：当你进入第3章"增强解析模式"时，请带着一个问题去读——**"LL(1) 的两条约束（无左递归 / Predict 集不交）分别在什么场景下会把我逼到墙角？第3章那些'更强解析器'又是如何逐个突破这些约束的？"**​ 这样读，第2→3章的衔接会是顺理成章的。
