
# 第6章 记录并识别程序中的符号 —— 读书笔记

> 一句话定位：前五章你学会了"把文本解析成 AST"。第6章回答一个让所有编程语言"活起来"的问题——**"程序里那些名字（变量名、函数名、类型名）到底指的是谁？它们在哪里声明的？在什么范围内可见？"**​ 这一章是全书从"语法分析"真正跨进"语义分析"腹地的**第三座、也是最具决定性的一座桥梁**。没有符号表，类型检查（第7章）、代码生成（第11-13章）、IDE 重构/补全都无从谈起。

三节是一条严密的"语义建模"递进链：**先解决"收集什么信息"（6.1）→ 再解决"信息按什么结构组织（作用域）"（6.2）→ 最后解决"怎么根据名字找到正确的声明"（6.3）**。

## 6.1 收集程序实体的信息：符号表是什么、存什么

### 符号表的本质：名字到声明的映射 + 语义属性的仓库

Parr 在这一节建立的第一个直觉是——**"符号表（Symbol Table）是编译器/解释器用来记录程序中所有'命名实体'（变量、函数、类型、参数、类等）及其属性的数据结构。"**

它本质上是一个**映射（Map）：`name → Symbol`**，其中每个 `Symbol` 对象承载该类实体的全部语义属性：

|符号类型|典型属性|
|---|---|
|变量符号（VariableSymbol）|类型、偏移量（栈帧位置）、是否只读|
|函数符号（FunctionSymbol）|参数列表（含类型）、返回类型、是否已定义体|
|类型符号（TypeSymbol / ClassSymbol）|成员符号表、父类、实现的接口|
|参数符号（ParameterSymbol）|类型、形参序号、传递方式（值/引用）|

**💡 我的洞见（第一性原理视角）：**

为什么非要有符号表？第一性原理的回答是——**"程序 = 代码（行为）+ 名字绑定（引用关系）。AST 只表达了'代码长什么样'，却没有回答'每个名字指的是哪个声明'。符号表正是为 AST 补上'引用解析'这一半信息的关键数据结构。"**

AST 告诉你"这里有一个变量引用 `x`"，但**只有符号表能告诉你"`x` 指的是第 3 行声明的那个 `int x`，类型为 `int`，在栈帧偏移 8 处"**。**AST + 符号表 = 程序的完整语义骨架**——这也是为什么 Clang/LLVM、javac、CPython 的符号表/语义分析模块，都是编译器里代码量最大、逻辑最复杂的部分。

工业实证：

- **Clang 的 `Sema`（语义分析器）**：维护 `IdentifierTable`（标识符表）+ 每个 `DeclContext`（声明上下文，如函数体、类体、命名空间）内部的 `LookupDecl` 机制。符号信息最终落到 `VarDecl`/`FunctionDecl`/`RecordDecl` 等 `Decl` 子类上。
    
- **Java 编译器（javac）的 `Symtab` + `Resolve`**：`Symtab` 是全局符号表（预填 `int`/`long`/`Object`/`String` 等基本类型），`Resolve` 负责"给定一个名字+环境，找到对应的 `Symbol`"。
    
- **CPython 的 `symtable` 模块**：在编译字节码前，先构建"符号表"（区分局部/全局/自由变量/bound），决定每个名字的加载方式（`LOAD_FAST` vs `LOAD_GLOBAL` vs `LOAD_DEREF`）。
    

### 符号表"何时填、何时查"

Parr 强调一个关键的工作流分工：

- **填表（define）**：在**前序遍历（discovery）**​ AST 时遇到声明（`int x;`、`def f():`）就立即把符号加入当前作用域。
    
- **查表（resolve/lookup）**：在**后序遍历（finish）**​ 或表达式求值时，遇到变量引用/函数调用，就沿着作用域链向上查找。
    

**这个"前序 define、后序 resolve"的节奏，正是第5章 Listener 模式（enter/exit 双钩子）的天然用武之地**——`enterX` 做 define，`exitX` 做 resolve/类型检查。

## 6.2 根据作用域划分符号：作用域链与嵌套符号表

### 为什么作用域是符号表的核心组织原则

Parr 在 6.2 节点出——**"程序中的名字不是全局平铺的，而是按'作用域（Scope）'分层嵌套的。"**​ 函数体内声明的 `x` 和外层的 `x` 是两回事；`if` 块里声明的变量在块外不可见。

**作用域的本质是"名字可见性的嵌套结构"**。符号表要正确建模这种嵌套，最经典、也是 Parr 推荐的数据结构就是——**作用域栈 / 作用域链（Scope Chain）**：

```
全局作用域 (GlobalScope)
 └── 函数 f 的作用域 (FunctionScope)
      └── if 语句块作用域 (BlockScope)
           └── for 循环块作用域 (BlockScope)
```

每个作用域是一个独立的 `Map<name, Symbol>`，所有作用域通过**父指针（enclosingScope）**​ 串成一条链。

### 核心操作：define / resolve 与作用域栈

Parr 给出的核心 API（也是工业界的事实标准）：

```
interface Scope {
    void define(Symbol sym);      // 把符号加入当前作用域
    Symbol resolve(String name);   // 从当前作用域开始，沿父链向上查找
    Scope getEnclosingScope();     // 返回外层作用域
}
```

`resolve` 的查找算法就是**沿作用域链自内向外**的经典链条查找：

```
Symbol resolve(String name) {
    Symbol s = symbols.get(name);   // 先查当前作用域
    if (s != null) return s;
    if (enclosingScope != null)
        return enclosingScope.resolve(name);  // 递归查外层
    return null;  // 未声明
}
```

**作用域栈的管理**（配合 AST 遍历）：

- **进入**一个作用域节点（函数声明、块语句）→ `push` 新作用域到栈顶，设为 `currentScope`
    
- **离开**该节点 → `pop`，恢复 `currentScope` 为外层
    

这正是 Listener 的 `enterX` / `exitX` 钩子的完美映射：`enterBlock` → `pushScope`；`exitBlock` → `popScope`。

### 不同作用域类型的细分

Parr 在书中（结合 ANTLR 的 Cymbol 示例语言）区分了几类典型作用域：

|作用域类型|典型承载者|关键特性|
|---|---|---|
|全局作用域（GlobalScope）|程序根、命名空间|无外层；内置类型/函数在此定义|
|函数作用域（FunctionScope）|函数声明|承载参数 + 局部变量|
|块作用域（BlockScope）|`{...}` 语句块、if/for/while 体|C99/Java/C++ 的块级作用域|
|类作用域（ClassScope）|class/struct 定义|承载成员变量/方法，涉及继承链查找|
|闭包作用域（ClosureScope）|嵌套函数/lambda|需捕获外层局部变量（自由变量）|

**💡 我的洞见（第一性原理 + 创新想法）：**

作用域链的设计，揭示了一个远比"编译器技术"更普遍的计算机科学原理——**"作用域链 = 命名空间的嵌套 + 词法环境（Lexical Environment）"**。

这个概念最早来自 **Scheme/λ 演算的"环境（Environment）"模型**：一个环境是一组绑定（binding）加上一个外层环境指针。**ALGOL 60 首次引入"块结构（block structure）"，C 的"复合语句 `{...}` 引入新作用域"、C++/Java 的类作用域、JavaScript 的词法作用域，全都是这个模型的变奏。**

**由此我提炼一条"作用域建模"的创新框架（供你设计语言/DSL 时参考）：**

> **"设计一门新语言的符号表时，先问三个问题：① 我的语言有哪些作用域类型（全局/函数/块/类/闭包）？② 每种作用域的'父作用域'是谁（词法嵌套规则）？③ 查找名字时是'仅当前作用域'还是'沿链向上'（C 的 `goto` 标签 vs 普通变量）？这三个问题的答案，直接决定了你的 Scope 类层级和 resolve 算法。"**

工业对照（作用域链的真实落地）：

- **Clang 的 `DeclContext` 链**：每个 `DeclContext`（函数体、类体、命名空间、链接规范块 `extern "C"`）都指向其词法外层 `DeclContext`。名字查找 `LookupDecl` 沿 `DeclContext` 链自内向外搜索，并处理 C++ 的"using 声明""实参依赖查找（ADL）"等复杂规则。
    
- **JavaScript 引擎（V8/SpiderMonkey）的 LexicalEnvironment 链**：每个执行上下文有一个 LexicalEnvironment，由 `outer` 指针串成链——这正是闭包能"记住"外层变量的底层机制。
    
- **Python 的 symtable**：构建模块/函数/类三种作用域，分析每个名字是 local / global / free（闭包捕获）/ bound，决定字节码用 `LOAD_FAST`（局部）还是 `LOAD_DEREF`（闭包变量）。
    
- **Java 内部类**：内部类能访问外围实例的成员，编译器会隐式生成 `this$0` 字段指向外围实例——本质是把"词法作用域链"编码进字节码的对象引用链。

## 6.3 解析符号：从"名字字符串"到"正确的声明"

### 符号解析（Symbol Resolution）的本质

6.3 节是本章的"收口"和高潮——**"给定 AST 中的一个名字引用节点（如变量引用 `x`、函数调用 `f`），如何找到它对应的、唯一的那个声明符号？"**​ 这个过程就叫**符号解析 / 名字解析（Name Resolution / Symbol Resolution）**。

Parr 强调：**符号解析 = 在正确的作用域链上，按语言的名字查找规则，找到匹配的符号**。对大多数类 C 语言，这就是 6.2 节的 `Scope.resolve(name)`——沿作用域链自内向外找到第一个匹配。

### 解析的复杂性：当"简单链查找"不够用时

Parr 诚实地指出——**真实语言的符号解析，远比"沿链查第一个匹配"复杂**。工业级语言有一大堆"链查找"处理不了的边界情况：

1. **重载（Overloading）**：C++/Java 的 `f(int)` 和 `f(double)` 同名不同参，解析需结合**实参类型**做重载决议（overload resolution）。
    
2. **类型依赖查找**：C++ 的**实参依赖查找（ADL，Argument-Dependent Lookup）**——对 `f(x)`，`x` 所属命名空间里的 `f` 也会被考虑，即使当前作用域没 `using`。
    
3. **模板/泛型**：C++ 模板实例化时的两阶段查找（two-phase lookup）、Java 泛型的类型擦除后桥接方法。
    
4. **前向引用**：Pascal/C 允许"先使用后声明"（同一作用域内），要求符号表支持"先占位、后填充完整信息"。
    
5. **跨翻译单元**：C/C++ 的 `extern` 声明、Java 的 `import`、Python 的 `import`——需跨文件解析符号。
    
6. **限定名查找**：`A::B::x`、`pkg.Class.method`——需按 `::` / `.` 逐段解析作用域。
    

**💡 我的洞见（第一性原理 + 创新想法）：**

这一节（结合工业实证）藏着一个极具深度的洞察——**"符号解析的本质，是'名字字符串'到'语义实体'的映射；而这个映射的'键'，往往不只是'名字'一个维度。"**

我把它提炼为**"符号解析键的多维化"**​ 规律：

|语言特性|解析键的维度|例子|
|---|---|---|
|无重载的语言（C/Pascal）|仅名字|`x` → 作用域内唯一 `x`|
|重载语言（C++/Java）|名字 + 实参类型列表|`f(int)` vs `f(double)`|
|模板/泛型|名字 + 类型参数|`vector<int>` vs `vector<double>`|
|ADL（C++）|名字 + 实参所属命名空间|`f(x)` 在 `x` 的命名空间找 `f`|
|限定名|名字 + 作用域路径|`A::B::x` 逐段解析|

**由此我提出一个"符号解析复杂度"的选型框架（创新想法，供你设计语言时参考）：**

> **"如果你的 DSL/语言要支持'重载'或'跨作用域复杂查找'，请务必在符号表设计早期就把'解析键'从'名字字符串'升级为'名字 + 类型签名/作用域路径'的结构化键。否则后期加入重载时，整个 resolve 逻辑要推倒重来——这是 javac/Clang 符号表极其复杂（承载重载决议、ADL、模板两阶段查找）的根本原因，也是为什么它们把'名字查找'做成独立的、最复杂的子系统。"**

工业对照（符号解析的工业级复杂度）：

- **Clang 的 `Sema::LookupName` / `CXXScopeSpec`**：C++ 的名字查找是 Clang 里最复杂的代码之一，需处理普通查找、限定查找（`A::B::x`）、ADL、using 声明/指令、类成员查找（含继承链）、构造函数名查找等几十种情形。Clang 用 `LookupResult` 聚合"一组候选声明"，再由重载决议筛选。
    
- **javac 的 `Resolve` 类**：`resolveIdent` / `resolveMethod` / `resolveMember` 分别处理变量/方法/成员解析，结合 `Env<AttrContext>`（当前 attribution 环境 = 作用域链 + 当前类 + 泛型环境）做查找。`Resolve` 是 javac 里最大的类之一。
    
- **C++ 两阶段查找（two-phase lookup）**：模板定义时做"不依赖模板参数的名字查找"，实例化时做"依赖模板参数的名字查找"——这直接源于 C++ 标准对模板语义的严格规定，是 Clang/gcc 都必须精确实现的复杂规则。

## 章节联系与全书定位

把三小节串成一条"符号语义建模"主线：

```
6.1 收集程序实体的信息
   → 符号表 = name → Symbol 映射；Symbol 承载类型/偏移/参数等语义属性
   → 前序 define、后序 resolve（Listener 的 enter/exit 天然适配）
        ↓
6.2 根据作用域划分符号
   → 作用域链（Scope Chain）= 命名空间嵌套 = 词法环境
   → 核心 API：define / resolve / getEnclosingScope；作用域栈配合 enter/exit
        ↓
6.3 解析符号
   → 符号解析 = 按语言规则，在作用域链上把"名字"映射到"唯一声明"
   → 重载/ADL/模板/限定名 → 解析键从"名字"多维化为"名字+类型/作用域路径"
```

**第6章在全书的角色**：它是"分析输入"部分（第4-8章）的**语义分析基石**。第7章（类型检查）、第8章（语义分析综合）的所有"类型查询/重载决议/成员访问"，都建立在第6章的符号表之上。**没有符号表，就没有"名字绑定"，类型检查就无从谈起——你无法判断 `x+1` 是否合法，因为你不知道 `x` 的类型。**

**贯穿全章的一条主线（我的总结）：**

> **Parr 在第6章真正想教你的，不是"如何实现一个哈希表"这种技术细节，而是"编程语言语义建模的核心秘密——用'作用域链 + 符号表'这对组合，把 AST 里的'名字字符串'变成'指向声明实体的引用'"。**​ 这一步完成后，你的编译器才真正"理解"了程序——知道每个名字指的是谁、在什么范围可见、带什么类型。**从这一章开始，你才真正跨进"语义分析"的深层领地，也为后续所有"类型检查/代码生成/IDE 智能"奠定了不可替代的基石。**

**一个给后续阅读的提示**：当你进入第7章"类型检查"时，请带着两个问题去读——**"类型信息存在哪里？（答案：挂在 Symbol 上——第6章的 VariableSymbol/FunctionSymbol 早就预留了 type 字段）""类型检查的本质是什么？（答案：遍历 AST + 查符号表，验证'每个表达式的 type'与'上下文期望的 type'是否相容——这正是第5章 Visitor + 第6章符号表的联合应用）"**​ 想通这两个问题，第7章就不是新知识，而是第5+6章的自然推论。
